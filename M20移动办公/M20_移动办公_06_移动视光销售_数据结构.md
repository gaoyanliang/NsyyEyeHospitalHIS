### 1.1 为什么是这 9 张

回到总纲 §1.4 的红线判据：**这张表存的东西，如果 M20 删库重建，会不会有业务事实丢失？会 → 可以建；不会 → 不许建。**

逐张过一遍：

| 表 | 删掉会丢什么 | 结论 |
|---|---|---|
| `m20_sal_quote_draft` | 顾客在柜台上听到的那个报价、以及我们基于它做的推荐。M10 订单表里只有成交价，**没有「我们先报了多少、后来谈到多少」** | 建 |
| `m20_sal_price_change_log` | 每一次让价的动作与理由。这是移动端最容易被滥用的地方，也是事后无法还原的地方 | 建，且只增不删 |
| `m20_sal_script_record` | 导购对顾客说了哪套话术、顾客接受了哪一项。**话术效果分析的口径**——不是价差业务事实 | 建 |
| `m20_sal_customer_pref` | 顾客的软性偏好（不喜欢金属架、对某个品牌过敏）。M10-05 顾客档案存的是硬档案，这类备忘没有归属 | 建 |
| `m20_sal_photo_archive` | 试戴照与眼底照的**引用与留存**。图像本体在对象存储，但「这张照片是哪个顾客、哪次试戴、谁拍的、拍给谁看」这一层关系只在移动端产生 | 建 |
| `m20_sal_offline_order_ext` | 离线开单时**本地判定用的价目与库存快照**、以及重连后的冲突判定依据。`m20_base_offline_queue` 只存通用队列字段，视光销售特有的 `product_code`/`price_version`/`stock_snapshot` 无法塞进去 | 建（扩展行，不重复队列本体） |
| `m20_sal_product_group` | 门店自己组织的「常配组合」清单。这是配置，不是业务事实，但**没有归属模块**（M01-08 是全院商品主数据，管不到门店组合） | 建 |
| `m20_sal_target_board` | 门店销售目标的看板配置（谁看哪几位、看哪个口径）。目标值本身在 M22/M10，我只存「看板怎么摆」 | 建 |
| `m20_sal_usage_log` | 移动端谁在什么时候对哪张单做了什么（改价、提交审批、离线提交）。这是审计证据 | 建 |

反过来，**明确不建的**：

| 候选表 | 为什么不能建 | 正确做法 |
|---|---|---|
| `m20_sal_order` / `m20_sal_order_item` | 订单是 M10-06 的业务事实，商品明细与光度参数是 M10 的权威 | 调 M10 订单接口；本子模块只存报价草稿与改价留痕 |
| `m20_sal_bill` / `m20_sal_payment` / `m20_sal_receipt` | 收款是 M16 的业务事实。**M20 存一份收款流水，就会与实际收款金额产生第二个版本** | 调 M16 P-08 创建支付，收款结果以 M16 为准 |
| `m20_sal_vision` / `m20_sal_refraction` | 验光数据（球镜/柱镜/轴位）是 M10-01/M10-02 的权威 | 调 M10 验光单接口；报价草稿里只存 `optometry_no` 这个外部单号引用 |
| `m20_sal_stock` / `m20_sal_price` | 价目与库存是 M01-08 + M10-07 的权威 | 离线时缓存到客户端；服务端不存「我们的库存副本」 |
| `m20_sal_member` / `m20_sal_coupon` | 会员与权益是 M03-03/M19 的权威 | 调上游接口；优惠试算调 M01 `discount-policies/calc` |
| `m20_sal_approval` | 审批实例是 M20-04 的 `m20_apr_*` | 调 P-01 发起，不建第二套审批表 |

### 1.2 三张表为什么必须拆开，而不是合并成一张「销售活动日志」

一个自然的想法是：把改价、话术、照片、操作日志合并成一张宽表 `m20_sal_activity`，`activity_type` 区分。

不合并的理由有三条，都是硬理由：

1. **生命周期不同**。`m20_sal_price_change_log` 与 `m20_sal_usage_log` 是只增不删的审计证据，数据库层要 `REVOKE UPDATE, DELETE`；`m20_sal_quote_draft` 是高频修改的草稿（一次报价改七八次很常见），必须允许 `UPDATE`。**一个表不能同时是「可改的草稿」与「不可改的留痕」**——给它加了 `REVOKE UPDATE` 草稿就改不了，不加则留痕可以被人悄悄改掉。
2. **字段密度极不均衡**。改价留痕有 `before_amount`/`after_amount`/`change_amount`/`change_ratio`/`reason_code`/`approval_no` 这些金额与比率字段且都是 `NOT NULL`；操作日志这些字段全空。合并后要么全部放宽为 `NULL`（约束形同虚设），要么让操作日志塞一堆无意义默认值。
3. **查询路径不同**。改价留痕按 `order_no` 或 `staff_id + 日期` 查，为对账与审计服务，量大且要能按门店聚合；操作日志按 `created_at` 做分区与归档。放一张表里索引会互相干扰。

### 1.3 与 `m20_base_offline_queue` 的分工

`m20_base_offline_queue` 由 **M20-01 首建**，M20-06 只读调用，本模块**不写它的 DDL**。

分工界线：

| 数据 | 存哪里 | 理由 |
|---|---|---|
| 队列号 `queue_no`、`biz_type`、`payload_json`、`sync_status`、`entity_version`、`conflict_reason` | `m20_base_offline_queue`（M20-01） | 与业务无关的通用队列机制，所有子模块共用 |
| 视光销售特有的价目版本、库存快照、眼别与光度参数摘要 | `m20_sal_offline_order_ext`（本模块） | 只有视光销售才需要「重连后判断价格变了没、这个 SKU 还有没有货」 |
| 重连后冲突的处理决定（谁按了什么、结果如何） | `m20_sal_usage_log`（本模块） | 冲突处理是一次人工决策，必须留痕 |

两者通过 `queue_no` 关联。**`m20_sal_offline_order_ext` 不是队列的副本**，它没有 `payload_json`、没有 `sync_status`，只有「判定冲突需要的那几个版本号与快照」。

## 2. 设计边界与判据

### 2.1 一句话判据

> **M20 存「在移动端发生、且只有移动端知道」的那一层事实。**
> 业务事实（订单、收款、验光、库存、权益）一律在上游，M20 存的是**过程与上下文**。

### 2.2 「价差」的两层含义（任务书点名要辨明的）

顾客报价 ¥4,800、最终成交 ¥4,500，这 300 元到底是什么，必须分清：

| 概念 | 归属 | 存哪里 | 用途 |
|---|---|---|---|
| **成交价与标价的差额**（折扣额、让价额） | **M16 / M10 的业务事实** | M16 结算单与优惠明细、M10 订单的 `amend_*` 字段 | 财务对账、毛利核算、医保合规 |
| **报价到成交的议价过程**（我先报 4,800，顾客压到 4,500，中间让了两次） | **M20 的过程事实** | `m20_sal_quote_draft` + `m20_sal_price_change_log` | 导购管理、话术效果分析、异常让价预警 |

**判据**：问「这个数字会不会进入财务报表？」——会，就是 M16/M10 的；不会，才是 M20 的。

所以本模块的 `m20_sal_price_change_log` **不是价差台账，是议价动作台账**。它的 `change_amount` 是「本次让价的变动额」，不是「最终成交价与标价的差额」。这个区别写进表注释与 Pydantic 字段说明，避免被误用成财务口径。

### 2.3 改价留痕为什么只增不删

数据结构汇总 §3.3 的判据：「**这张表的不一致或缺失本身是不是要被保留的信息？**」

改价留痕正是。一条被删掉的改价记录，**恰恰是「有人不想让这次让价被看到」这件事本身**——它比留下的记录更有信息量。

因此：

- 数据库层 `REVOKE UPDATE, DELETE ON m20_sal_price_change_log FROM app_m20;`，只 `GRANT INSERT, SELECT`
- 加纵深防御触发器 `trg_m20_sal_price_change_log_bu`，`BEFORE UPDATE OR DELETE` 时 `RAISE EXCEPTION 'PRICE_LOG_IMMUTABLE'`
- 表内**没有 `is_deleted` 列**（汇总 §3.3 的只增不删表一律不设该列）

同样的处理也适用于 `m20_sal_usage_log`（操作日志）。

### 2.4 服务端不存业务数据副本

铁律 4：不缓存业务数据副本到服务端，短 TTL 缓存 ≤60 秒且必须带 `as_of` 与 `degraded`。

所以本模块的表里：

- **没有**任何 `product_name_snap`、`customer_name_snap`、`price_snap` 之外的业务快照列
- `m20_sal_offline_order_ext` 里的 `price_snapshot` / `stock_snapshot` 是**例外且必要**：它是「入队那一刻客户端看到的值」，用于重连后判断「服务端的值还是不是这个」。**这不是缓存，是一次性的事件证据**——它一旦写入就不再更新，与「缓存」的语义相反。
- `m20_sal_quote_draft` 里的金额是「我们报出去的价」，本身就是事实，不是副本。

### 2.5 跨模块引用一律不建外键

汇总 §2.2 第 6 条：跨子模块引用上游表不建外键（上游表由上游管理），M20 内部表之间必须建外键。

本模块涉及的跨模块引用全部是**不透明字符串或 ID**：

| 字段 | 上游 | 说明 |
|---|---|---|
| `customer_no` | M10-05 顾客档案 | 不透明字符串，**不做位数或格式校验** |
| `order_no` | M10-06 配镜订单 | 不透明字符串，不做格式校验 |
| `lab_job_no` | M10-07 加工单 | 不透明字符串 |
| `optometry_no` | M10-01 验光单 | 不透明字符串 |
| `sales_order_no` | M16-04 销售单 | 不透明字符串 |
| `settlement_no` | M16 结算单 | 不透明字符串 |
| `approval_no` | M20-04 审批实例 | 前缀 `SP`，但**本模块同样不做位数校验**（汇总 §1.4） |
| `product_code` | M01-08 视光商品 | 编码，只做 `length > 0` 校验 |
| `patient_id` | M03 `mpi_patient` | BIGINT |

**全局规则（写进验收 DA）**：本模块对任何上游主键/单号只做「非空 + 长度上限」校验，**不做正则、不做位数、不做前缀推断**。

| 关系 | 基数 | 说明 |

#### 4.2.1 `item_json` 结构

```json
[
  {
    "product_code": "FR0012",
    "product_type": "FRAME",
    "quantity": 1,
    "eye_side": "OU",
    "unit_price": 1280.00,
    "line_amount": 1280.00,
    "price_version": "PV20261101-03"
  },
  {
    "product_code": "LN0158",
    "product_type": "LENS",
    "quantity": 2,
    "eye_side": "OU",
    "unit_price": 510.00,
    "line_amount": 1020.00,
    "price_version": "PV20261101-03"
  }
]
```

| 键 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `product_code` | string | 是 | M01-08 视光商品编码 |
| `product_type` | string | 是 | `FRAME` / `LENS` / `CONTACT_LENS` / `SERVICE` / `ACCESSORY` |
| `quantity` | number | 是 | 数量 |
| `eye_side` | string | 否 | `OD` / `OS` / `OU`；镜架等不区分眼别的商品不填 |
| `unit_price` | number | 是 | 单价，两位小数 |
| `line_amount` | number | 是 | 行金额 = `unit_price × quantity` |
| `price_version` | string | 是 | 该行取价时的价目版本号 |

**为什么 `item_json` 用 JSONB 而不是建明细表**

报价明细的行结构与 M10 订单明细高度相似但**不稳定**：不同商品类型的可填属性不同（镜架要框型、镜片要折射率与膜层、护理液要规格）。如果建模成 `m20_sal_quote_item` 加一堆可空列，会得到一张 30 列里 24 列是 `NULL` 的表，而且每次 M01 商品属性扩展都要改我的表结构。

JSONB 在这个场景是合适的，因为：①**它是过程数据，不参与跨表 JOIN**；②它永远整块读写（草稿一次保存写全部，展示一次读全部）；③它的结构由商品主数据的属性定义驱动，本该灵活。

代价是**不能用数据库约束保证金额加总正确**，所以：

- 保存时由 Service 层校验 `sum(line_amount) == current_quote_amount`（误差 ≤ 0.01）
- 该恒等式写进 `m20_sal_usage_log` 的校验结果字段，事后可复核（见 4.10）

#### 4.2.3 约束说明

```sql
ALTER TABLE m20_sal_quote_draft
    ADD CONSTRAINT ck_m20_sal_quote_status
    CHECK (quote_status IN ('DRAFT', 'SUBMITTED', 'CONVERTED', 'ABANDONED', 'EXPIRED'));

-- 金额非负：报价可以为 0（赠送/免单），但不能为负
ALTER TABLE m20_sal_quote_draft
    ADD CONSTRAINT ck_m20_sal_quote_amount_nonneg
    CHECK ((first_quoted_amount IS NULL OR first_quoted_amount >= 0)
       AND (current_quote_amount IS NULL OR current_quote_amount >= 0)
       AND (floor_amount IS NULL OR floor_amount >= 0));

-- 数据质量枚举
ALTER TABLE m20_sal_quote_draft
    ADD CONSTRAINT ck_m20_sal_quote_quality
    CHECK (data_quality IN ('REALTIME', 'CACHED', 'PARTIAL', 'UNKNOWN'));

-- 场景与终端枚举
ALTER TABLE m20_sal_quote_draft
    ADD CONSTRAINT ck_m20_sal_quote_scene
    CHECK (source_scene IN ('COUNTER', 'ON_SITE', 'PHONE_FOLLOW'));

ALTER TABLE m20_sal_quote_draft
    ADD CONSTRAINT ck_m20_sal_quote_client
    CHECK (client_type IN ('IOS', 'ANDROID', 'MINI_PROGRAM', 'H5', 'PAD'));

-- 【组合约束 C-01】降级一致性：degraded = FALSE 时必须没有降级来源
--   防的错误：上游超时了但只写 degraded_sources 忘了翻 degraded 标记，
--   页面因此不显示「数据可能不是最新」，顾客听到的是一个过期的价格。
ALTER TABLE m20_sal_quote_draft
    ADD CONSTRAINT ck_m20_sal_quote_degraded_consistent
    CHECK (degraded = TRUE OR jsonb_array_length(degraded_sources) = 0);

-- 【组合约束 C-02】成交态必须有成交单号与时间，反之亦然
--   防的错误：发了 CONVERTED 却没有 order_no，下游回滚时找不到对应的 M10 订单。
ALTER TABLE m20_sal_quote_draft
    ADD CONSTRAINT ck_m20_sal_quote_converted
    CHECK ( (quote_status = 'CONVERTED')
         = (converted_order_no <> '' AND converted_at IS NOT NULL) );

-- 【组合约束 C-03】放弃态必须有原因
--   防的错误：草稿凭空消失。运营看不到「为什么 100 张报价只有 12 张成交」的原因分布。
ALTER TABLE m20_sal_quote_draft
    ADD CONSTRAINT ck_m20_sal_quote_abandon
    CHECK (quote_status <> 'ABANDONED' OR abandon_reason <> '');

-- 【组合约束 C-04】当前报价不得低于规则允许的最低价
--   防的错误：前端算错了 bottom line 或有人直接调接口，把价格报到规则之外。
--   注意：这是「能落库」的下限，真正的折扣判定仍在 M16/M10，本约束只是兜底。
ALTER TABLE m20_sal_quote_draft
    ADD CONSTRAINT ck_m20_sal_quote_floor
    CHECK (current_quote_amount IS NULL
        OR floor_amount IS NULL
        OR current_quote_amount >= floor_amount);

-- 【组合约束 C-05】首次报价不得低于当前报价（涨价可以，但不能「第一次就报得比现在还低」再降）
--   实际上让价方向是往下走，所以首次报价应 >= 当前报价。
--   防的错误：草稿被反复改后 first_quoted_amount 被覆盖成最新值，
--   导致「首次报价」这个概念失效，议价过程无法还原。
ALTER TABLE m20_sal_quote_draft
    ADD CONSTRAINT ck_m20_sal_quote_first_ge_current
    CHECK (first_quoted_amount IS NULL
        OR current_quote_amount IS NULL
        OR first_quoted_amount >= current_quote_amount);

-- 【组合约束 C-06】VALID 状态机：不能从 CONVERTED 回退
--   防的错误：成交后又把草稿改回 DRAFT 再重新提交，产生两张订单指向同一张报价。
ALTER TABLE m20_sal_quote_draft
    ADD CONSTRAINT ck_m20_sal_quote_terminal
    CHECK (quote_status NOT IN ('CONVERTED')
        OR (converted_at IS NOT NULL));
```

**组合语义约束单独说明（最容易漏的一类）**

上面 C-01~C-06 全部是**跨字段**约束。单看每个字段都合法，组合起来才出错。判别法（汇总 §7.2）：「把这个类型改成另一种，再把各字段填成另一类型的合法值，能通过吗？能通过就缺组合约束。」

举例：`quote_status='CONVERTED'` 且 `converted_order_no=''`、`converted_at=NULL`——三个字段各自都在合法取值域内，但组合起来就是「成交了但不知道成的是哪一单」。C-02 就是堵这个。

**设计说明**

- `customer_no` 用 `NOT NULL DEFAULT ''` 而不是 `NULL`：散客与「没有顾客号」在业务上是同一件事，用空串表达可以避免 `NULL` 参与唯一约束与分组聚合时的不确定行为。
- `first_quoted_amount` 一经写入不更新，这是**「首次报价」这个概念能成立的前提**。C-05 保证它不会低于 `current_quote_amount`。
- `degraded` / `degraded_sources` / `data_quality` / `as_of` 四列是汇总 §8A.2 的强制要求落到了**持久化层**：报价草稿是会被事后复盘的（「这单为什么报这么低」），必须能还原当时的数quality。

### 4.3 表：`m20_sal_price_change_log`（改价留痕）

**用途：** 记录移动端每一次让价/改价动作。**只增不删、不可改**。这是本子模块最重要的表——移动端最容易被滥用的能力就是「私下让价」，而事后唯一能还原的是这张表。

**写入方：** M20-06 移动销售服务（每次改价成功时追加一行）

#### 4.3.1 为什么这张表没有 `updated_at` / `is_deleted`

汇总 §3.3 的只增不删表判据：「这张表的不一致或缺失本身是不是要被保留的信息？」

改价留痕是。而且更强：**这张表的每一条如果有任何一个字段可以被后来的动作改写，它就不再是证据，而只是一个说法**。

因此：

- 没有 `updated_at` / `updated_by`——没有更新动作，就不该有更新的痕迹字段；留一个空列会让人误以为「可以更新，只是现在没写」
- 没有 `is_deleted`——逻辑删除等于「记录还在，但系统不再认为它发生过」
- 数据库层 `REVOKE UPDATE, DELETE ON m20_sal_price_change_log FROM app_m20;` 只 `GRANT INSERT, SELECT`
- 纵深防御触发器（见 4.3.4）

#### 4.3.2 `change_ratio` 为什么允许 NULL 且必须配约束

`before_amount` 为 0（赠送品、0 元服务）时，`(after - before) / before` 无定义。此时**必须存 NULL，不能存 0，也不能存 100%**：

- 存 0 会让「0 元赠品加了一项收费」看起来像「没变化」
- 存 100% 是编的

`ck_m20_sal_price_log_ratio` 强制：`before_amount > 0 OR change_ratio IS NULL`。这条约束保证「分母为 0 时比率不存在」在数据库层成立，而不是靠某处代码记得判断。

```sql
    CHECK (char_length(btrim(reason_text)) >= 5);
```

**组合语义约束单独说明**

C-10 与 C-11 是这道防线最要紧的两条。移动端的典型绕过路径是：

1. 顾客压价，导购算了一下「需审批」，但审批要 10 分钟，顾客站在柜台前等不了
2. 于是点「稍后提交审批」，先把价让出去
3. 顾客走了，单据成了，审批单**永远没人提**

C-10 让第 2 步无法落库——`need_approval = TRUE` 而 `approval_no = ''` 直接报错。**必须先拿到审批单号（哪怕还在审批中）才能写这一行**，而 P-01 是同步返回 `approval_no` 的（P95 ≤ 200ms），所以这个约束在体验上没有代价。

反过来说：如果 P-01 调不通，就**不能写这条改价记录**——这正是「审批不可用即阻断」在数据层的实现（见 4.3.5）。

**设计说明**

- `approval_no` 不做位数校验（汇总 §1.4），但**必须非空才能落库**（C-10）。这两件事不矛盾：不校验它长得对不对，只校验它在不在。
- `offline_flagged` 单独存在的理由：离线产生的改价是重连后才写进来的，`created_at` 是写入时刻而**不是顾客听到那个价格的时刻**。评审时看到「20:15 的改价」但要意识到这单其实是下午 15:30 谈的。这一列让复盘时能区分。

#### 4.4.1 为什么 `customer_reaction` 有 `UNKNOWN` 而且允许它是默认值

如果强制每次都要标「顾客反应」，导购会一律点「积极」——**没有成本的必填项会退化成噪声**。

所以默认值是 `UNKNOWN`，只在导购确实观察到明确反应时才标。分析时把 `UNKNOWN` 排除在分母外，而不是当成「中性」。

这一点与 M20-CALC 体系里「不知道 ≠ 没问题」是同一个原则：**把 `UNKNOWN` 当 `NEUTRAL` 算会让话术效果看起来比实际差，把它当 `POSITIVE` 算会让它看起来比实际好**，两种都是编数据。

C-17 特别值得一提：`outcome = 'CONVERTED'`（成单了）却标 `reaction_evidence = 'LEFT_WITHOUT_ORDER'`（没下单就走了），这是明显的自相矛盾，但三个字段各自合法。如果不加约束，这类脏数据会直接进入话术效果报表，让某套话术显得「转化率异常高」。

#### 4.6.1 为什么必须有 `consent_given`

顾客照片属于个人信息，其中眼底照在严格解释下还可能是**医疗图像信息**。移动端柜台拍照最大的风险是：导购为了方便对比，随手拍了顾客的脸，而顾客从没同意过。

`consent_given` 不是走形式：

- 它为 `FALSE` 时，图片**只在本次会话内可看**（`retain_until = created_at + 24h`），到期后由清理任务删除
- 它为 `TRUE` 时，按 `retain_until`（默认 3 年）留存，可作为复购与售后依据

这条规则写进详细设计的 R-xx 与验收 DA 项。

#### 4.6.2 为什么 `content_hash` 是 `VARCHAR(64)` 而不是 MD5

汇总与 M18 的教训一轮已经确立：哈希必须 SHA-256（64 个十六进制字符）。MD5 在医疗数据完整性场景下已经不是可接受的算法。

`ck_m20_sal_photo_hash` 强制格式为 64 位十六进制，防止有人写进一个 MD5（32 位）或截断值。

```sql
ALTER TABLE m20_sal_photo_archive
    ADD CONSTRAINT ck_m20_sal_photo_type
    CHECK (photo_type IN ('TRY_ON', 'FUNDUS', 'OLD_GLASSES', 'DEFECT', 'REFERENCE'));

ALTER TABLE m20_sal_photo_archive
    ADD CONSTRAINT ck_m20_sal_photo_eye
    CHECK (eye_side IN ('OD', 'OS', 'OU', 'NA'));

-- 哈希必须是 SHA-256：64 个十六进制字符
ALTER TABLE m20_sal_photo_archive
    ADD CONSTRAINT ck_m20_sal_photo_hash
    CHECK (content_hash ~ '^[0-9a-f]{64}$');

-- 文件大小必须为正
ALTER TABLE m20_sal_photo_archive
    ADD CONSTRAINT ck_m20_sal_photo_size
    CHECK (file_size_bytes > 0);

-- 【组合约束 C-21】已上传的必须有对象键与桶，未上传的不能有
--   防的错误：上传失败但对象键已写，清理任务去删一个不存在的对象；
--   或者对象键为空却被当成「已上传」，页面一直显示空白图。
ALTER TABLE m20_sal_photo_archive
    ADD CONSTRAINT ck_m20_sal_photo_uploaded
    CHECK ( (is_uploaded = TRUE) = (object_key <> '' AND bucket <> '') );

-- 【组合约束 C-22】同意留存就必须有同意时间与到期日
--   防的错误：consent_given 被前端默认成 TRUE（省得弹窗），
--   于是所有照片都被认为「顾客同意留三年」，而实际上没有一个人点过同意。
ALTER TABLE m20_sal_photo_archive
    ADD CONSTRAINT ck_m20_sal_photo_consent
    CHECK (consent_given = FALSE OR (consent_at IS NOT NULL AND retain_until IS NOT NULL));

-- 【组合约束 C-23】未同意的图像留存期不得超过 24 小时
--   防的错误：没同意的照片被设了 3 年留存，等于绕过了同意流程。
ALTER TABLE m20_sal_photo_archive
    ADD CONSTRAINT ck_m20_sal_photo_consent_ttl
    CHECK (consent_given = TRUE
        OR retain_until IS NULL
        OR retain_until <= created_at + INTERVAL '24 hours');

-- 【组合约束 C-24】眼底照必须区分眼别
--   防的错误：左右眼眼底照混在一堆 NA 里，对比时无法知道哪张是左眼。
ALTER TABLE m20_sal_photo_archive
    ADD CONSTRAINT ck_m20_sal_photo_fundus_eye
    CHECK (photo_type <> 'FUNDUS' OR eye_side IN ('OD', 'OS', 'OU'));
```

**组合语义约束单独说明**

C-22 与 C-23 是一组。C-22 单独看只要求「同意就要有时间」，但如果不配 C-23，一条 `consent_given = FALSE` 且 `retain_until = 3 年后` 的记录依然能落库——**而同意的缺失正好体现在「没同意却长期留存」这件事上**。

这两条一起构成「未同意 → 最多 24 小时；同意 → 按留存策略」的完整语义。**只写 C-22 是半个约束**，这是组合约束最容易漏的形态：约束覆盖了正向，漏了反向。

```sql
COMMENT ON COLUMN m20_sal_photo_archive.retain_until IS '留存到期日；到期由清理任务删除对象并逻辑删除本行';
COMMENT ON COLUMN m20_sal_photo_archive.is_uploaded IS '是否已成功上传；为假时由补偿任务重传';
```

**设计说明**

- `uk_m20_sal_photo_object (bucket, object_key)` 是**去重键**：同一张照片被重复上传时（移动端弱网下非常常见）不会产生两条记录。
- 图像不落库是硬要求。三年 9 万张照片、单张 1.5MB，就是 135GB 的二进制——塞进 PostgreSQL 会让备份、主从复制、VACUUM 全部失衡。
- `shot_at` 与 `created_at` 分开：`shot_at` 是客户端拍摄时刻，弱网下可能比 `created_at` 早几分钟甚至几小时。**图像分析按 `shot_at`，审计按 `created_at`。**

#### 4.7.1 冲突明细结构

`conflict_detail_json`：

```json
{
  "conflicts": [
    {
      "product_code": "LN0158",
      "kind": "VERSION_CHANGED",
      "field": "unit_price",
      "snapshot_value": 510.00,
      "current_value": 560.00,
      "price_version_snapshot": "PV20261101-03",
      "price_version_current": "PV20261105-01"
    },
    {
      "product_code": "FR0012",
      "kind": "ENTITY_GONE",
      "field": "qty_available",
      "snapshot_value": 3,
      "current_value": 0
    }
  ]
}
```

#### 4.7.2 为什么必须存「入队时的快照」而不是「当前值」

这里是个容易想歪的地方：既然是判断冲突，为什么不直接拿当前值比？

因为**冲突的定义是「客户端当时看到的东西」与「服务端现在的东西」不一致**。如果不存「客户端当时看到的」，重连时就只剩「服务端现在的东西」，此时已经无从知道导购当时是照着什么价、什么库存跟顾客谈的。

具体后果：顾客说「你们刚才说 510」，系统显示「一直都是 560」，**谁也证明不了谁**。有了 `price_snapshot` 与 `price_version`，就能还原出「15:30 那一刻系统里确实是 510，16:10 涨到 560」。

这也是为什么这张表**写入后就不再更新**（快照部分）。更新了它，就失去了证据价值。

```sql
-- 外键指向 M20-01 首建的队列表（同模块体系内，建真实外键）
ALTER TABLE m20_sal_offline_order_ext
    ADD CONSTRAINT fk_m20_sal_offline_queue_ext
    FOREIGN KEY (queue_id) REFERENCES m20_base_offline_queue (id);

ALTER TABLE m20_sal_offline_order_ext
    ADD CONSTRAINT ck_m20_sal_offline_conflict_kind
    CHECK (conflict_kind IN ('', 'VERSION_CHANGED', 'ENTITY_GONE', 'STATE_INVALID'));

ALTER TABLE m20_sal_offline_order_ext
    ADD CONSTRAINT ck_m20_sal_offline_resolution
    CHECK (resolution IN ('', 'PENDING', 'APPLIED', 'DISCARDED', 'MANUAL_FIXED'));

ALTER TABLE m20_sal_offline_order_ext
    ADD CONSTRAINT ck_m20_sal_offline_amount_nonneg
    CHECK (total_amount_snapshot IS NULL OR total_amount_snapshot >= 0);

-- 【组合约束 C-25】检出冲突就必须有冲突类型与明细
--   防的错误：conflict_detected 置真但没说是什么冲突，
--   待处理队列里只显示「有冲突」，处理人不知道要改什么。
ALTER TABLE m20_sal_offline_order_ext
    ADD CONSTRAINT ck_m20_sal_offline_conflict_detail
    CHECK (conflict_detected = FALSE
        OR (conflict_kind <> '' AND jsonb_array_length(conflict_detail_json -> 'conflicts') > 0));

-- 【组合约束 C-26】没检出冲突就不能有冲突类型
ALTER TABLE m20_sal_offline_order_ext
    ADD CONSTRAINT ck_m20_sal_offline_no_conflict
    CHECK (conflict_detected = TRUE OR conflict_kind = '');

-- 【组合约束 C-27】冲突项必须处于待处理，不得自动置为已处理
--   防的错误：同步任务图省事，检出冲突后直接把 resolution 写成 APPLIED，
--   等于「自动覆盖」。M20-CALC-06 明确要求 CONFLICT 一律不自动覆盖也不自动丢弃。
ALTER TABLE m20_sal_offline_order_ext
    ADD CONSTRAINT ck_m20_sal_offline_conflict_pending
    CHECK (conflict_detected = FALSE OR resolution = 'PENDING');

-- 【组合约束 C-28】处理过的必须有处理人与处理时间
ALTER TABLE m20_sal_offline_order_ext
    ADD CONSTRAINT ck_m20_sal_offline_resolved
    CHECK (resolution IN ('', 'PENDING')
        OR (resolved_by IS NOT NULL AND resolved_by > 0 AND resolved_at IS NOT NULL));

-- 【组合约束 C-29】快照必须是对象
ALTER TABLE m20_sal_offline_order_ext
    ADD CONSTRAINT ck_m20_sal_offline_json_type
    CHECK (jsonb_typeof(price_snapshot) = 'object'
       AND jsonb_typeof(stock_snapshot) = 'object'
       AND jsonb_typeof(product_codes) = 'array');
```

**组合语义约束单独说明**

**C-27 是本表最重要的一条，也是 M20-CALC-06 那条硬规则在数据层的落地。**

M20-CALC-06 原文：「`CONFLICT` 一律不自动覆盖也不自动丢弃，进『待处理队列』由人决定」。这条规则如果只写在 Service 层代码里，`CONFLICT` 的最大风险恰恰来自「某个批处理任务图省事」——而批处理任务往往绕开 Service 直接写库。C-27 让「检出冲突却直接标记已处理」在数据库层不可能。

C-25 与 C-26 是配对的正反约束：C-25 保证「有冲突就得说清是什么」，C-26 保证「没冲突就别瞎写」。只写 C-25 会留下「`conflict_detected = FALSE` 但 `conflict_kind = 'VERSION_CHANGED'`」的矛盾数据。

#### 4.9.3 为什么 `refresh_sec` 必须限 300

一条看板要拼 M22 指标 + M10 门店目标 + 本模块自算的报价转化率。移动端在门店里信号不好时，客户端往往会**每秒重试一次**——如果服务端不限制刷新间隔，一台卡住的 iPad 就能把 M22 的指标接口打穿。

300 秒这个上限与总纲 §7.4 的「角标不缓存超 300s」一致，是同一个数量级的约束。

#### 4.10.1 动作编码

| 动作编码 | 业务含义 | 为什么必须留痕 |
|---|---|---|
| `QUOTE_CREATE` | 新建报价草稿 | 报价起点 |
| `QUOTE_SUBMIT` | 提交订单 | 成交动作 |
| `QUOTE_ABANDON` | 放弃报价 | 转化率分母的依据 |
| `PRICE_CHANGE` | 改价 | **敏感：私下让价的第一入口** |
| `PRICE_CHANGE_BLOCKED` | 改价被阻断（审批不可用/超底价） | **敏感：被阻断的动作同样要看，它反映「想绕」的意图** |
| `APPROVAL_APPLY` | 发起审批 | 审批链路起点 |
| `APPROVAL_RECEIPT` | 执行回执 | **M20-04 断点 A 的堵法，必须留痕** |
| `OFFLINE_ENQUEUE` | 离线入队 | 弱网证据 |
| `OFFLINE_SYNC` | 离线同步 | 同步结果 |
| `CONFLICT_RESOLVE` | 冲突处理决定 | **敏感：谁决定覆盖/丢弃** |
| `PHOTO_UPLOAD` | 照片上传 | 隐私相关 |
| `PREF_UPDATE` | 偏好修改 | 偏好被篡改会影响推荐 |
| `EXPORT_QUOTE` | 导出报价 | 数据外带风险 |

`PRICE_CHANGE_BLOCKED` 这个动作值得单独说：**被拦下来的动作比放过去的动作更有信息量**。一个导购一个月被拦 40 次超底价改价，即使一次都没成功，也说明他在反复尝试。

#### 4.10.2 为什么分区

`m20_sal_usage_log` 是唯一需要分区的表：

- 预估 40 万行/年（日均约 1,100 行），三年 120 万行
- 查询几乎全是按时间范围扫（「本周谁改过价」「上个月的阻断记录」）
- 归档策略是「按月保留 3 年，之后导出冷存」

按 `log_time` 月分区 + `DEFAULT` 分区（汇总 §4.3：没有 DEFAULT 分区时新月份第一条 INSERT 直接失败）。

**主键必须是 `(id, log_time)`**——PostgreSQL 要求分区表上的唯一索引必须包含分区键（汇总 §4.2 第 2 条的硬约束）。这里没有业务唯一字段要跨分区，所以代价为零。

```sql
    CHECK (biz_type IN ('QUOTE', 'OFFLINE_SYNC', 'PRICE', 'PHOTO', 'PREF'));

    ADD CONSTRAINT ck_m20_sal_usage_log_client
    CHECK (client_type IN ('IOS', 'ANDROID', 'MINI_PROGRAM', 'H5', 'PAD'));

    ADD CONSTRAINT ck_m20_sal_usage_log_network
    CHECK (network_state IN ('WIFI', 'CELLULAR', 'WEAK', 'OFFLINE'));

ALTER TABLE m20_sal_usage_log
    ADD CONSTRAINT ck_m20_sal_usage_log_duration
    CHECK (duration_ms IS NULL OR duration_ms >= 0);

-- 【组合约束 C-37】失败或阻断必须有原因
--   防的错误：一条 result='BLOCKED' 却没有 blocked_reason 的记录，
--   复盘时无法知道是被哪条规则拦的，无法判断拦得对不对。
ALTER TABLE m20_sal_usage_log
    ADD CONSTRAINT ck_m20_sal_usage_log_reason
    CHECK (result = 'SUCCESS'
        OR error_code <> ''
        OR btrim(blocked_reason) <> '');

-- 【组合约束 C-38】成功不得携带错误码
--   防的错误：一次成功操作写了个残留的错误码，统计「失败率」时被算进去。
ALTER TABLE m20_sal_usage_log
    ADD CONSTRAINT ck_m20_sal_usage_log_success_clean
    CHECK (result <> 'SUCCESS' OR error_code = '');

-- 【组合约束 C-39】详细的 JSON 必须是对象
ALTER TABLE m20_sal_usage_log
    ADD CONSTRAINT ck_m20_sal_usage_log_json_type
    CHECK (jsonb_typeof(detail_json) = 'object');

-- 【组合约束 C-40】离线相关动作的 network_state 必须为 OFFLINE 或 WEAK
--   防的错误：OFFLINE_ENQUEUE 动作发生在稳定 WiFi 下，
--   说明这个「离线队列」其实是被误用的（比如网络正常却走了离线分支），
--   这类数据会污染「离线率」统计。
ALTER TABLE m20_sal_usage_log
    ADD CONSTRAINT ck_m20_sal_usage_log_offline_net
    CHECK (action_code NOT IN ('OFFLINE_ENQUEUE', 'OFFLINE_SYNC')
        OR network_state IN ('OFFLINE', 'WEAK'));
```

**组合语义约束单独说明**

C-37 与 C-38 是一对：C-37 说「非成功必须有原因」，C-38 说「成功必须没有错误码」。只写前者，会留下「成功但带着错误码」的记录；只写后者，会留下「失败但没有原因」的记录。

C-40 是一条**看起来奇怪但很实用**的约束。「离线入队」这个动作如果真的发生在稳定 WiFi 下，说明代码里的离线分支判断写错了，或者有人手工调用了离线接口。这条约束把「离线率的统计口径是否可信」这个问题的证据留在了数据层。

```python
def _in_list(values: tuple[str, ...]) -> str:
    """把枚举元组渲染成 SQL IN 列表字面量，供 CheckConstraint 使用。"""
    rendered = ", ".join("'" + v + "'" for v in values if v != "")
    return rendered
```

**模型层设计说明**

1. **`_in_list()` 辅助函数的理由**：九张表有 20 多个枚举 CHECK。把枚举值写成模块级常量元组、由函数渲染成 SQL 字面量，保证「Python 侧常量」与「DDL 约束」是同一份数据——否则改枚举时两边会漂移。
2. **`SalUsageLog` 的主键是 `(id, log_time)`**：分区表上的唯一索引必须包含分区键（PostgreSQL 硬要求）。这不是设计选择，是约束。
3. **`SalPriceChangeLog` 与 `SalUsageLog` 没有继承 `AuditMixin` / `SoftDeleteMixin`**：只增不删表没有 `updated_at` 与 `is_deleted`，继承会让它们「看起来可以更新或删除」。
4. **`SalOfflineOrderExt.queue_id` 的 `ForeignKey` 是全文档唯一一个**，指向 `m20_base_offline_queue`（M20-01 首建）。

**Schema 层设计说明**

1. **`_float_to_decimal` 用 `repr(value)` 而不是 `str(value)`**：`repr(0.1)` 得到 `'0.1'`，`str` 在这里结果相同；但 `repr(1e-07)` 得到 `'1e-07'` 而某些格式化会给出更多位。统一用 `repr` 是更保守的选择，`Decimal` 能正确解析。
2. **`ApprovalApplyOut.approval_no` 不做任何格式校验**：它是 M20-04 生成的 `SP` 前缀单号，本模块当不透明字符串处理。共享规范 §8.1 明确「调用方当不透明字符串，任何一方都不得做位数或格式校验」。
3. **`OfflineOrderExtOut._conflict_pair` 把 C-27 的数据库约束在 API 层再表达一次**：数据库层挡住绕过 Service 的写入，API 层挡住逻辑写错。
4. **所有 `*Out` 都继承 `QualityMarkedMixin`**：共享规范 §8A.2 要求 `degraded:false` 时四个标记也必须出现。放在基类里比逐字段声明更难漏。
5. **`TargetBoardDataOut.target_missing`**：目标值由 M10/M22 提供，本模块不存。取不到时置 `true` 让页面显示「目标未设定」，而不是显示一个 0 让人以为完成率是 0%。

## 附录 C：关键索引与查询

### C.1 高频查询与命中索引

| 查询场景 | SQL 条件（示意） | 命中索引 | 预期耗时 |
|---|---|---|---|
| 我的报价草稿列表 | `WHERE staff_id = ? AND quote_status = 'DRAFT' ORDER BY created_at DESC LIMIT 20` | `idx_m20_sal_quote_staff_status` | < 5ms |
| 顾客历史报价 | `WHERE customer_no = ? ORDER BY created_at DESC LIMIT 20` | `idx_m20_sal_quote_customer` | < 8ms |
| 门店当日报价 | `WHERE store_id = ? AND created_at >= ?` | `idx_m20_sal_quote_store_date` | < 10ms |
| 过期草稿清理 | `WHERE expire_at < now() AND quote_status = 'DRAFT' AND is_deleted = FALSE` | `idx_m20_sal_quote_expire`（部分索引） | < 15ms |
| 报价内改价序列 | `WHERE quote_id = ? ORDER BY change_seq` | `uk_m20_sal_price_log_seq` | < 2ms |
| 本月超底价改价 | `WHERE store_id = ? AND below_floor = TRUE ORDER BY created_at DESC` | `idx_m20_sal_price_below_floor`（部分索引） | < 6ms |
| 待处理的离线冲突 | `WHERE resolution = 'PENDING' ORDER BY enqueued_at` | `idx_m20_sal_offline_resolution` | < 5ms |
| 我的待上传图片 | `WHERE is_uploaded = FALSE ORDER BY created_at` | `idx_m20_sal_photo_pending`（部分索引） | < 5ms |
| 话术效果统计 | `WHERE script_code = ? AND customer_reaction <> 'UNKNOWN' AND is_deleted = FALSE` | `idx_m20_sal_script_effective`（部分索引） | < 20ms |
| 被阻断动作审计 | `WHERE store_id = ? AND result = 'BLOCKED' ORDER BY log_time DESC` | `idx_m20_sal_usage_log_blocked`（部分索引） | < 12ms |

### C.2 部分索引的价值

本表有 5 个部分索引，共同点是「只在少数行上建索引」：

| 索引 | 全表基数占比 | 不建部分索引的代价 |
|---|---|---|
| `idx_m20_sal_quote_expire` | DRAFT 约占 15% | 全量 B 树多占约 85% 空间，且每次写入非草稿行都要维护 |
| `idx_m20_sal_price_below_floor` | 超底价约 2% | 全表扫一遍找那 2%，索引本身却和主表差不多大 |
| `idx_m20_sal_offline_resolution` | PENDING 冲突约 0.3% | 99.7% 已处理行也在索引里，查询反而变慢 |
| `idx_m20_sal_photo_pending` | 待上传约 0.5% | 同上 |
| `idx_m20_sal_usage_log_blocked` | BLOCKED 约 5% | 日志表本来就大，全量索引会显著拖慢写入 |
