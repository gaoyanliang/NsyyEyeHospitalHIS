## 1. 模块概述

### 1.1 模块定位

M20-06 移动视光销售的定位是一句话：**柜台与上门场景下，销售与视光师手上那台设备该显示什么、能改什么、改了之后留下什么痕迹。**

它解决的是三类具体的现场问题：

| 现场问题 | 现状（没有 M20-06 时） | M20-06 的做法 |
|---|---|---|
| 顾客在柜台前问「这副多少钱」，销售要跑回工位开电脑 | 顾客等待 3~5 分钟，中途可能被同行叫走 | iPad 上扫码直接出报价 |
| 顾客嫌贵要求让价，销售口头答应然后手工改单 | 改了什么、为什么改、谁同意的，事后查不到 | 每次改价写 `m20_sal_price_change_log`，说明 ≤5 字即拒 |
| 试戴效果很好，但照片存在销售私人的手机里 | 顾客日后质疑效果无法举证；照片本身也可能外泄 | 照片走对象存储 + 元数据登记 + 顾客同意才留住 |

**它不是**：不是订单系统的移动版，不是收银台，不是视光业务的主数据入口。

### 1.2 为什么独立成子模块

**理由一：移动端的「过程」与业务系统的「结果」是两类数据，混在一起会互相污染。**

一次销售成交会同时产生两类事实：

| 类别 | 例子 | 权威方 | 特点 |
|---|---|---|---|
| 结果事实 | 订单 `GD2026102800033`、金额 4,500.00、已收 4,500.00 | M10 订单、M16 结算 | 少而确定，进入财务与库存 |
| 过程事实 | 首次报价 4,800.00 → 改价 3 次 → 成交 4,500.00，每次改价的原因与审批 | 无（当前无人保存） | 多而模糊，不进财务但进管理与合规 |

把过程事实塞进 M10 订单表，会让订单表出现「首次报价」「第 3 次改价原因」这类字段——而这些字段对订单状态机毫无意义，却要在每次订单查询时带上。反过来，把 M20-06 的九张表合并成一张「销售活动日志」，则会在 §1.2 的「理由二」里说明它为什么行不通。

**理由二：移动端独有的网络与设备特征，在 PC 端设计中根本不存在。**

门店 iPad 在网络切换时断时续是常态（尤其新店装修期、商场地下室）。一次报价过程中可能经历 `WIFI → CELLULAR → WEAK → OFFLINE` 四次切换。这带来的设计需求——**入队时快照、重连后冲突判定、冲突不自动解决**——在 PC 端是完全不必要的复杂度。放进主业务模块会让主业务模块被迫背上一套它永远用不到的逻辑。

**理由三：改价留痕的合规属性，需要一个只增不删的落点。**

移动端是私下让价的高发场景：销售离顾客最近、离主管最远。合规上需要的是「每一次让价尝试都有记录，包括被系统拦下来的那些」。这类数据有两个特征：**只增不删**、**必须在数据库层保证不可改**（`REVOKE UPDATE, DELETE`）。把它挂在订单表的某个 JSONB 字段里，就失去了数据库层的不可篡改性——任何能改订单的人都能改留痕。

**理由四：扫码录入镜片参数的上游写接口并不存在（这是共享规范 §9.14 待核实项的裁决）。**

`grep -rn "扫码" M10视光业务管理/` 只命中 M10-07 的加工师扫码报工（`scan_code` 加工单条码）与 M10-03 的隐形眼镜试戴片序列号扫码，**都不是销售端扫码录入镜片参数**。M01 侧只有 `M01主数据管理MDM/M01_主数据管理MDM_04_耗材_数据结构.md:324` 的 `mdm_material_barcode`（耗材条码/UDI）。也就是说：扫出来的条码要解析成什么、解析出什么之后放进哪个结构，**没有上游接口负责**。这个解析与落入报价草稿的动作只能在 M20-06 侧完成。

### 1.4 概念辨析

#### 1.4.1 「价差」有两层含义，只有一层归本模块

任务书里点到过一个陷阱：客户报价 ¥4,800、最终成交 ¥4,500，这个「差 300」到底是谁的？

| 含义 | 具体内容 | 归属 | 判据 |
|---|---|---|---|
| **财务折扣额** | 成交价与标价之间的优惠，体现在结算单上 | **M16 结算单 + 优惠明细**；M10 订单的 `amend_*` 字段 | 这个数字会进入财务报表吗？会 |
| **议价过程** | 从 4,800 谈到 4,500 中间经过了几轮、每轮谁说的、说了什么理由、有没有走审批 | **M20-06 `m20_sal_price_change_log`** | 这个数字会进报表吗？不会，但它是管理问题 |

**本模块 `change_amount` 与 `change_ratio` 记录的是议价过程中的金额变化，不是财务折扣额。** 同一笔成交，M16 会有一行折扣明细（金额 −300.00），M20-06 会有三行改价留痕（如 −100.00、−150.00、−50.00），两者不能相加也不能互校——它们是同一件事的两个侧面。

**为什么不做「两边对账」**：曾考虑过做「M20 改价合计 = M16 折扣额」的一致性校验。最终放弃，因为真实业务里存在大量 M16 侧折扣但 M20 侧无记录的情况（顾客出示会员卡、医保优惠、活动满减），也有一轮改价产生多行 M16 明细的情况（改的是组合商品）。**强行对账会产生大量假告警，最后所有人都会关掉这个监控。**

#### 1.4.2 「离线开单」不等于「离线收款」

| 动作 | 能否离线 | 原因 |
|---|---|---|
| 录入顾客、选商品、算报价 | **可以** | 价格与库存有入队时快照，等于「记录下顾客当时看到的」 |
| 生成报价单、拍试戴照 | **可以** | 纯本模块数据 |
| 把订单提交到 M10 | **可以入队** | 入队不等于成功，重连后由 M20-CALC-06 判定冲突 |
| 记录「已收款 4,500.00」 | **绝对不行** | 钱的事必须在线确认（详见 §8.3.2） |

**为什么收款不能离线**：这不是性能问题，是账实相符问题。如果 iPad 允许本地记「已收款」，那么两台 iPad 可以在断网期间各自记一笔同一订单的收款；重连后要合并，就变成「谁先同步谁的算数」——而钱已经进了收银员的口袋或抽屉。**离线记录收款 = 在本地账本上写字，而真正的账本在 M16。**

#### 1.4.3 「审批不可用」不等于「降级提示」

| 依赖不可用 | 正确处置 | 错误处置 |
|---|---|---|
| M10 顾客档案超时 | 降级：用本地缓存 + `degraded=true`，页面提示 | 返回「顾客不存在」 |
| M10 加工进度超时 | 降级：显示「进度暂时无法获取」 | 显示「暂无进度」 |
| **M20-04 审批不可用** | **阻断：改价不生效、订单不改，明确告知「审批服务不可用，请稍后提交」** | **本地放行 / 先改后补审批** |

判据来自 `M10视光业务管理/M10_视光业务管理_06_配镜订单与取镜交付_详细设计.md:7383`：

> `| M20 审批不可用 | 受限改单、免费换新 | **阻断**，不允许执行 | 「审批服务不可用，请稍后提交」 |`

这是上游原文，不是我的判断。**降级朝「更少给」再往前一步就是「一样都不给」——审批是这类接口。**

#### 1.4.4 `degraded` 与 `data_quality` 不是一回事

| 字段 | 含义 | 计算方式 |
|---|---|---|
| `degraded` | 本次返回是否有任何一路上游没成功 | 所有上游成功与否的**逻辑或** |
| `degraded_sources` | 具体哪几路失败了、为什么 | 逐路收集 `{source, reason}` |
| `data_quality` | 数据新鲜度等级 | 按 M20-CALC-05 重算 |
| `as_of` | **数据口径截止时刻** | 所有成功上游 `as_of` 中**最早**的那个 |

**关键约束（共享规范 §8A.2.1）**：M10 与 M20-04 返回的 `data_quality` 值域与 M20 不同（M18 用 `REALTIME/DAILY/ESTIMATED`，M20 用 `REALTIME/CACHED/PARTIAL/UNKNOWN`），**一律不得透传**。M20-06 必须自己按 M20-CALC-05 从「各路成功与否 + 本地缓存年龄」重算。

**为什么不做值域映射**：把 `DAILY` 映射成 `CACHED` 看着能解决问题，但两者成因完全不同——M18 的 `DAILY` 意为「这条数据来自日批汇总」，它可能就是最新最完整的；M20 的 `CACHED` 意为「这是 M20 自己 30 秒前的缓存」。映射成一个值之后，运维看到 `CACHED` 永远无法判断是上游本来就长这样，还是 M20 这边缓存旧了。

### 1.5 模块目标

| 编号 | 目标 | 可度量标准 |
|---|---|---|
| G-01 | 扫码到出价 ≤ 15 秒 | 从扫描完成到页面显示报价金额的 P95 ≤ 15s |
| G-02 | 每一次改价都可追溯 | 改价留痕覆盖率 100%（任何 `current_quote_amount` 变化都必须有对应 `price_change_log` 行） |
| G-03 | 受限场景必须走审批，且审批不可用即阻断 | 审批不可用期间的受限改单成功数 = 0 |
| G-04 | 移动端的每一个数字都能说清截止时刻 | 所有带 `data_quality` 的响应 100% 携带 `as_of` |
| G-05 | 离线产生的单据可回放且冲突不自动解决 | 冲突单自动解决数 = 0；冲突单最终处理率 ≥ 95% |
| G-06 | 收款动作 100% 在线 | 离线状态下的收款成功数 = 0 |
| G-07 | 顾客图像只在授权范围内留存 | 未同意留存记录的 24h 后残留数 = 0 |

### 1.6 关键业务角色

| 角色 | 职责 | 主要操作 | 典型权限 |
|---|---|---|---|
| 视光师 | 验光、选片、给出技术建议 | 扫码录参数、查验光单、出报价 | `m20:sal:quote:create` |
| 销售顾问 | 接待、推荐、议价 | 报价、改价、记录话术、拍试戴照 | `m20:sal:quote:create`、`m20:sal:price:create` |
| 视光主管 | 审批受限改单与让价 | 审阅改价留痕、审批 | `m20:sal:price:approve` |
| 门店店长 | 门店经营与合规 | 查改价统计、看被阻断动作、配置商品组与看板 | `m20:sal:report:view`、`m20:sal:config:edit` |
| 收银员 | 收款 | 在 M16 侧完成收款（本模块只引导跳转） | 无 M20-06 写入权限 |
| 运营管理员 | 话术维护、商品组维护 | 维护商品组、看板配置 | `m20:sal:config:edit` |

**为什么收银员没有 M20-06 写入权限**：收款不在本模块做。收银员出现在这里只是为了说明「移动端的销售环节到哪里结束」——销售环节的最后一屏是「请前往收银台」，而不是「支付成功」。

## 2. 业务范围与边界

### 2.1 范围内

| 编号 | 功能 | 说明 |
|---|---|---|

| S-13 | 会员与顾客信息查询（透传） | 调 M10-05 / M03，不落库 |

| 需求 | 负责方 | 说明 |

| 消息推送与待办 | M20-08 | 本模块不直接发消息 |
| 身份认证、令牌签发、设备指纹 | M02 | 本模块只透传 `device_id` |
| 库存的预留与扣减 | M10-07 | 本模块只读可用量 |
| 员工绩效与提成计算 | M17-07 | 本模块只提供过程数据，不计算结果 |
| 报表与决策看板 | M22 | 本模块只提供配置与过程数据 |

### 2.3 与相邻模块的边界

| 相邻模块 | 边界问题 | 裁决 | 判据 |

### 3.2 状态机

#### 3.2.1 报价草稿状态机

| 当前状态 | 事件 | 触发者 | 条件 | 目标状态 | 副作用 |
|---|---|---|---|---|---|
| — | 新建报价 | 销售/视光师 | 有商品明细 | `DRAFT` | 生成 `quote_no`；写 `usage_log(QUOTE_CREATE)` |
| `DRAFT` | 提交成交引导 | 销售 | 报价金额 > 0 且不低于底价或已有审批 | `SUBMITTED` | 引导跳转收款流程 |
| `DRAFT` | 超时 | APScheduler 每 10 分钟 | `expire_at < now()` | `EXPIRED` | 无 |
| `DRAFT` | 放弃 | 销售 | `abandon_reason` ≥ 1 字 | `ABANDONED` | 记录原因 |
| `SUBMITTED` | 订单关联成功 | 回调 / 轮询 | M10 返回 `order_no` | `CONVERTED` | 写 `converted_order_no` + `converted_at` |
| `SUBMITTED` | 超时未成交 | APScheduler | 超过 `SUBMIT_TIMEOUT`（默认 2 小时） | `EXPIRED` | 无 |
| `CONVERTED` | — | — | **终态** | — | 不可再改金额、不可再改价 |
| `ABANDONED` / `EXPIRED` | — | — | **终态** | — | 只可查 |

**为什么 `CONVERTED` 是终态**：成交之后报价金额的任何变动都必须走 M10 的改单流程（那是订单的事），而不是回头改报价草稿。如果允许改，就会出现「订单 4,500、报价草稿 4,300」的两套说法，且没有任何机制保证它们一致。

#### 3.2.2 改价记录状态

改价记录本身没有状态机——它只有 `approval_result` 一个字段，取值 `''`（无需审批或审批中）、`APPROVED`、`REJECTED`、`TIMEOUT`、`APPROVED_BUT_FAILED`。

| `approval_result` | 含义 | 报价金额是否已改 |
|---|---|---|
| `''` 且 `need_approval = FALSE` | 无需审批 | 是 |
| `''` 且 `need_approval = TRUE` | 审批中 | **否** |
| `APPROVED` | 审批通过 | 是 |
| `APPROVED_BUT_FAILED` | 审批通过但执行失败 | **否** |
| `REJECTED` / `TIMEOUT` | 驳回或超时 | **否** |

**注意 `APPROVED_BUT_FAILED`**：这是 M20-04 状态机里的一个真实状态，意思是「主管批了，但申请方执行没成功」。在本模块的场景下，它出现在「审批通过后写 `price_change_log` 或更新 `quote_draft.current_quote_amount` 失败」的时候。**这个状态下金额绝不能改**——否则主管批的是 4,500，实际成交 4,300，中间的 200 谁也不知道是谁让的。

#### 3.2.3 离线队列冲突状态

| 当前状态 | 事件 | 触发者 | 条件 | 目标状态 |
|---|---|---|---|---|
| — | 客户端离线入队 | 客户端 | `network_state ∈ {OFFLINE, WEAK}` | `QUEUED` |
| `QUEUED` | 重连重放 | 客户端 | 网络恢复 | `SYNCING` |
| `SYNCING` | 判定为 CHANGED | 服务端（M20-CALC-06） | 五种冲突判定之一命中 | `CONFLICT` |
| `SYNCING` | 判定为未变 | 服务端 | 未命中冲突 | `SYNCED` |
| `CONFLICT` | 人工处理 | 店长 | 选择应用/丢弃/手工修正 | `SYNCED` / `ABANDONED` |
| `SYNCING` | 重试耗尽 | 服务端 | 3 次失败 | `FAILED` |
| `FAILED` | 放弃 | 店长 | 明确放弃 | `ABANDONED` |

**冲突绝不自动解决**：这是 M20-CALC-06 的硬规则，在本模块的数据结构层由 `ck_m20_sal_offline_conflict_pending` 保证（冲突未处理前 `resolution` 必须为 `PENDING`）。

### 3.3 关键业务流程

#### 3.3.1 柜台报价主流程

1. 顾客到店，销售在 iPad 上点「新建报价」（P02）。
2. 扫顾客就诊码 → 调 M03 `by-empi` 识别患者；调 M10-05 取顾客档案。
3. 扫镜片/镜架条码 → 本模块解析条码 → 得到商品编码 → 从 M01 价目缓存取单价 → 填入报价明细。
4. 调 M01 `discount-policies/calc` 试算优惠 → 得到当前报价金额。
5. 若当前报价低于底价或触发受限条件 → 调 M20-04 P-01 发起审批 → **P-01 失败则整笔改价不落库，页面提示阻断**。
6. 顾客同意 → 点「提交成交」→ 引导跳转 M16 收款流程（本模块不记收款）。
7. M10 返回订单号 → 报价草稿置 `CONVERTED`。

#### 3.3.2 改价流程（含审批）

1. 顾客要求让价，销售在报价详情页点「改价」。
2. 填写改后金额（或按幅度让价）、选择原因编码、**填写至少 5 个字的说明**。
3. 系统按 M01 优惠规则判定是否需要审批：
   - 不需要 → 直接写 `price_change_log`（`need_approval = FALSE`）→ 更新草稿金额。
   - 需要 → 调 M20-04 P-01。
     - P-01 返回 `need_approval = false`（免审）→ 同「不需要」处理。
     - P-01 返回 `approval_no` → 写 `price_change_log`（`need_approval = TRUE`、`approval_no` 非空、金额不变）→ 页面显示「待审批」。
     - **P-01 调用失败 → 整笔改价不落库**，返回 `"2006003"`，页面显示「审批服务不可用，请稍后提交」。
4. 审批完成后 M20-04 发 `m20.approval.completed`；本模块消费事件：
   - `APPROVED` → 更新 `approval_result`、更新草稿金额 → **回调 receipt（`exec_result = SUCCESS`）**。
   - `REJECTED` / `TIMEOUT` → 更新 `approval_result`，金额不动 → 回调 receipt（`exec_result = FAILED`，原因填驳回或超时）。
   - 更新金额失败 → `approval_result = APPROVED_BUT_FAILED` → 回调 receipt（`exec_result = FAILED`，原因填具体失败）。

**第 4 步的回调不能省**：M20-04 侧那条审批会一直停在「已批准未回执」，超时后置为「执行未确认」并告警。而本模块的改价其实已经成功或已经失败了——**两边说法不同，事后查不清是谁的问题。**

#### 3.3.3 离线开单流程

1. 网络断开（或弱网），销售继续报价。
2. 点「提交成交」时检测到离线 → 入队 `m20_base_offline_queue`（M20-01 负责）+ 写 `m20_sal_offline_order_ext`，**记录入队时的价目版本、单价快照、可用量快照**。
3. 页面明确显示「已离线保存，待网络恢复后提交」，**不显示「已提交成功」**，**不显示「已收款」**。
4. 网络恢复 → 客户端触发重放 → 服务端按 M20-CALC-06 逐项判定：
   - 幂等键已存在 → `SYNCED`（不重复执行）。
   - 实体已不存在 → `CONFLICT / ENTITY_GONE`。
   - 版本不一致 → `CONFLICT / VERSION_CHANGED`。
   - 状态不允许 → `CONFLICT / STATE_INVALID`。
   - 都不命中 → `SYNCED`。
5. 冲突项进「待处理队列」（P09），由店长逐条决定应用/丢弃/手工修正，并填写说明。
6. 处理完写 `usage_log(OFFLINE_RESOLVE)`。

#### 3.3.4 拍照留存流程

1. 销售拍下试戴照。
2. 若顾客同意留存 → 勾选同意 → 记录 `consent_at`、`retain_until`（按留存策略）。
3. 若顾客未明确同意 → **不勾选** → `retain_until = created_at + 24 小时`，图片 24 小时后自动清理，仅本次会话可见。
4. 图片直传对象存储 → 回填 `object_key`、`bucket`、`content_hash`（SHA-256）、`file_size_bytes`。
5. 登记元数据到 `m20_sal_photo_archive`。

**为什么未同意也要存 24 小时**：顾客当场要看效果对比，完全不存会让「刚才那张能再给我看看吗」无法满足。24 小时是「够当场与当日回访用，又不足以长期留存」的折中。

### 3.4 计算模型

本子模块复用总纲 §6 的 M20-CALC-01 / 05 / 06，另定义两个本子模块特有的计算模型。

#### 3.4.1 引用 M20-CALC-05（数据新鲜度判定）

本模块所有带 `data_quality` 的响应都按 M20-CALC-05 计算，不自行另算：

```text
if 任一上游失败:              data_quality = PARTIAL
elif 本地缓存年龄 > 30 秒:    data_quality = CACHED
elif 本地缓存年龄 <= 30 秒:   data_quality = REALTIME
elif 无法判定:                data_quality = UNKNOWN
else:                         data_quality = REALTIME

as_of = min(所有成功上游返回的 as_of)
若某成功上游未返回 as_of:      整个响应 data_quality = UNKNOWN
```

**算例**：P07 订单详情页同时取 M10 顾客档案、M10 订单、M16 收款状态、M20-04 审批状态。

| 来源 | 返回时刻 | 结果 |
|---|---|---|
| M10 顾客档案 | `as_of = 10:09:40` | 成功 |
| M10 订单 | `as_of = 10:09:35` | 成功 |
| M16 收款状态 | `as_of = 10:09:41` | 成功 |
| M20-04 审批 | 超时 200ms 未返回 | 失败 |

→ `degraded = true`，`degraded_sources = [{"source": "M20-04_APPROVAL", "reason": "TIMEOUT"}]`，`data_quality = PARTIAL`，`as_of = 10:09:35`（**取最早的 M10 订单时刻，而不是请求时刻 10:09:42**）。

**常见错误**：把 `as_of` 填成 `now()`。页面会显示「刚刚更新」，而实际上最新的一条数据是 7 秒前的。写进验收 SC-09。

#### 3.4.2 M20-SAL-CALC-01 改价幅度与审批触发判定

**用途**：判定一次改价是否需要审批，并给出需要审批时的金额依据。

**输入**：`before_amount`（改前金额）、`after_amount`（改后金额）、`floor_amount`（规则允许最低价）、`staff_discount_limit`（该员工岗位允许的自主让价比例）。

**公式**：

```text
change_amount = after_amount - before_amount
change_ratio  = (after_amount - before_amount) / before_amount   当 before_amount > 0
change_ratio  = NULL                                             当 before_amount = 0

need_approval = (
      (floor_amount IS NOT NULL AND after_amount < floor_amount)
   OR (change_ratio IS NOT NULL AND abs(change_ratio) > staff_discount_limit)
   OR change_type IN ('FREE_SERVICE', 'FLOOR_ADJUST')
)
```

**单位**：金额 `NUMERIC(14,2)` 元；比率 `NUMERIC(10,6)`，无单位。

**边界**：

| 边界情形 | 处理 |
|---|---|
| `before_amount = 0` | `change_ratio` 存 `NULL`，**不存 0 也不存 100%**；是否需审批只看 `after_amount < floor_amount` 与 `change_type` |
| `floor_amount IS NULL`（商品无底价配置） | 跳过底价判定，**但不等于放行**——比率判定仍然生效 |
| `staff_discount_limit IS NULL` | 视为 0，即任何让价都需要审批 |
| `after_amount = before_amount` | 不产生留痕行，直接返回「金额未变」 |

**舍入**：`change_amount` 保留 2 位小数（与金额同精度，不额外舍入）；`change_ratio` 保留 6 位小数，**四舍五入一次，不二次舍入**。数据库 CHECK `ck_m20_sal_price_ratio_calc` 校验 `change_ratio` 与重算值偏差 ≤ 0.000001。

**失败条件**：`after_amount < 0` → 参数错误 `"2006001"`。

**算例**：

| 场景 | before | after | floor | limit | 判定过程 | need_approval |
|---|---|---|---|---|---|---|
| 正常议价 | 4,800.00 | 4,500.00 | 4,200.00 | 0.10 | ratio = −300/4800 = **−0.062500**；abs(0.0625) ≤ 0.10；不低于底价 | **FALSE** |
| 超自主额度 | 4,800.00 | 4,200.00 | 4,200.00 | 0.10 | ratio = **−0.125000**；abs > 0.10 | **TRUE** |
| 低于底价 | 4,800.00 | 4,100.00 | 4,200.00 | 0.20 | ratio = −0.145833 未超；但 4,100.00 < 4,200.00 | **TRUE** |
| 免费服务 | 300.00 | 0.00 | 0.00 | 0.10 | ratio = **−1.000000**；且 `change_type = FREE_SERVICE` | **TRUE** |
| 零元起加收 | 0.00 | 50.00 | NULL | 0.10 | `before = 0` → ratio = **NULL**；无底价 → 只看 `change_type` 是否为免费服务类，此处不是 | **FALSE** |

**为什么「零元起加收」不因 `change_ratio` 无法计算就默认免审**：`change_ratio = NULL` 只表示「比率算不出来」，不表示「变化很小」。如果把它当成「无需审批」，就会出现「0 元赠品改成 500 元加收」直接放行的漏洞。所以 `before_amount = 0` 时改用绝对金额与底价判定。

#### 3.4.3 M20-SAL-CALC-02 话术有效率

**用途**：评估一条导购话术在特定场景下是否真的有效。

**公式**：

```text
话术有效率 = (customer_reaction = 'POSITIVE' 的记录数)
           / (customer_reaction <> 'UNKNOWN' 的记录数)
```

**边界**：

| 边界 | 处理 |
|---|---|
| 分母 = 0（全是 UNKNOWN） | **返回 NULL + NO_DATA**，不得返回 0%，也不得返回 100% |
| 样本量 < 30 | 返回数值但标记 `insufficient_sample = true`，页面显示「样本不足，仅供参考」 |
| `reaction_evidence` 为 `LEFT_WITHOUT_ORDER` 但 `reaction = POSITIVE` | 数据库层已由 C-17 禁止 |

**为什么分母排除 UNKNOWN，而不是把它算作 NEUTRAL**：`UNKNOWN` 的语义是「没有观察或者没记录」，不是「顾客反应平淡」。把它算进分母会让记录越少的人效率越接近 50%，而实际上他可能只是懒得记。**排除 UNKNOWN 且分母为 0 时返回 NULL，是唯一诚实的处理。**

**算例**：某话术在 `PRICE_PUSH_BACK` 场景下被使用 120 次。

| 反应 | 记录数 | 是否进分母 | 是否进分子 |
|---|---|---|---|
| POSITIVE | 42 | 是 | 是 |
| NEUTRAL | 30 | 是 | 否 |
| NEGATIVE | 18 | 是 | 否 |
| UNKNOWN | 30 | **否** | **否** |

→ 分母 = 42 + 30 + 18 = 90；分子 = 42；有效率 = 42 / 90 = **0.466667 → 46.67%**。

若错误地把 UNKNOWN 计入分母：42 / 120 = 35.00%，**低 11.67 个百分点**，且这个数字会随着「导购勤劳程度」而不是「话术质量」波动——勤于记录的导购反而显得话术差。

#### 3.4.4 M20-SAL-CALC-03 报价转化率

**用途**：衡量从报价到成交的转化情况。

**公式**：

```text
报价转化率 = CONVERTED 状态草稿数
           / (CONVERTED + ABANDONED + EXPIRED 状态草稿数)
```

**边界**：

| 边界 | 处理 |
|---|---|
| 分母 = 0 | 返回 NULL，不返回 0% |
| `SUBMITTED` 状态的草稿 | **不进分母**——还没结束的不能算失败（与总纲 M20-CALC-02「分母不含仍在 PENDING 的」同一原则） |
| `DRAFT` 状态草稿 | 不进分母 |

**算例**：本月某门店草稿 500 张：`CONVERTED` 168、`ABANDONED` 92、`EXPIRED` 40、`SUBMITTED` 60、`DRAFT` 140。

- 分母 = 168 + 92 + 40 = **300**
- 转化率 = 168 / 300 = **0.560000 → 56.00%**

**反例**：若把 `SUBMITTED` 60 张算进分母：168 / 360 = 46.67%，**低 9.33 个百分点**。而这 60 张大概率会成交（已提交成交引导），把它当失败算是错的。

### 3.5 单据模型

| 单据 | 单号格式 | 生成方式 | 说明 |
|---|---|---|---|
| 报价草稿号 | `QT` + `yyyyMMdd` + 6 位流水 | Redis `INCR m20:code:QT:{yyyyMMdd}`，TTL 至次日 00:05 | 例 `QT20261107000123` |
| 改价流水号 | `PC` + `yyyyMMdd` + 6 位流水 | 同上，前缀 `PC` | 例 `PC20261107000456` |
| 话术记录号 | `SC` + `yyyyMMdd` + 6 位流水 | 同上，前缀 `SC` | — |
| 图片编号 | `PH` + `yyyyMMdd` + 6 位流水 | 同上，前缀 `PH` | — |
| 离线队列号 | `OF` + `yyyyMMdd` + 6 位流水 | **M20-01 生成** | 本模块只引用 |
| 审批单号 | `SP` + `yyyyMMdd` + 4 位流水 | **M20-04 生成** | 本模块当**不透明字符串**，不做位数/格式校验 |
| M10 订单号 | 由 M10 生成 | — | 不透明字符串，见 §8.1.2 |
| M10 加工单号 | 由 M10-07 生成 | — | 不透明字符串 |
| M10 顾客号 | 由 M10-05 生成 | — | 不透明字符串 |

**为什么单号不用数据库序列**：跨零点并发生成会重复。数据库序列是全局递增的，但业务要求「当日流水」——用序列值再拼日期，在 23:59:59 与 00:00:00 交界处会得到「同一个日期前缀配两个不相邻的序列值」，看起来不连续；反过来用 `MAX+1` 则在并发下会重复。**Redis `INCR` 是原子且按 key 隔离的，天然满足「当日流水」语义。**

### 6.4 FastAPI 实现要点

1. **依赖参数必须排在带默认值的 Query 参数之前**：`ctx: Ctx = Depends(get_ctx)` 放前面，`page_no: int = Query(1)` 放后面，否则 `ast.parse` 直接报 `non-default argument follows default argument`。
2. 所有写接口都从请求头取 `X-Idempotency-Key`，缺失时**不报错而是记为 `None`**——移动端首版客户端可能不带，拒掉它等于拒掉旧版本。`None` 时退化为「不加幂等保护」，同时在响应头回 `X-Idempotency-Missing: true` 让客户端侧能发现问题。
3. 反序列化金额字段统一用 `Decimal`，Pydantic 层已经把 `float` 转 `repr` 再转 `Decimal`，业务层不得再调 `float()`。
4. 出参一律走 `ApiResponse` 包一层，`trace_id` 由中间件注入，接口里不手写。
5. 四个质量标记由 `QualityMarkedMixin` 统一注入，**接口里不得手工赋值**——手工赋值是「顺手透传上游值」的高发位置。

### 6.5 Service 层要点

```python
from decimal import Decimal, ROUND_HALF_UP


def calc_change_ratio(before_amount: Decimal, after_amount: Decimal) -> Decimal | None:
    """改价幅度。before 为 0 时返回 None，不返回 0 也不返回 100%。

    before_amount 为 0 说明是零元起加收（如 0 元赠品改收费），
    此时「变化了多少倍」没有意义；返回 0 会让这笔加收看起来没变化，
    返回 1.0 是编的。上层看到 None 一律视为「必须审批」。
    """
    if before_amount == Decimal("0.00"):
        return None
    return ((after_amount - before_amount) / before_amount).quantize(
        Decimal("0.000001"), rounding=ROUND_HALF_UP
    )


def need_approval(
    change_type: str,
    ratio: Decimal | None,
    auto_limit: Decimal,
    below_floor: bool,
) -> bool:
    """M20-SAL-CALC-01 的三条件或。"""
    if change_type == "ADD_CHARGE":
        return True
    if ratio is None:
        return True
    if below_floor:
        return True
    return abs(ratio) > auto_limit


def calc_quality(
    upstream_results: list[dict],
    cache_age_sec: int,
) -> dict:
    """M20-CALC-05。注意 here 不看「本地有没有数据」。

    degraded 是「或」不是「与」：任一上游失败即为 true。
    as_of 取所有成功来源里最早的那个，不是请求时刻。
    """
    failed = [r["source"] for r in upstream_results if not r["ok"]]
    ok = [r for r in upstream_results if r["ok"]]
    if failed:
        quality = "PARTIAL"
    elif cache_age_sec > 30:
        quality = "CACHED"
    else:
        quality = "REALTIME"
    if any(r.get("as_of") is None for r in ok):
        quality = "UNKNOWN"
    as_of = min((r["as_of"] for r in ok if r.get("as_of") is not None),
                default=None)
    return {
        "degraded": bool(failed),
        "degraded_sources": [
            {"source": r["source"], "reason": r["reason"]} for r in upstream_results
            if not r["ok"]
        ],
        "data_quality": quality,
        "as_of": as_of,
    }
```

**`calc_quality` 里 `data_quality` 是现算的，不读上游的任何 `data_quality` 字段。** 上游的原始质量描述只放在 `degraded_sources[].reason` 里作说明，见共享规范 §8A.2.1。

## 7. 缓存与异步任务设计

### 7.1 缓存清单

| Key | 类型 | TTL | 内容 | 失效时机 | 容量 |
|---|---|---|---|---|---|
| `m20:sal:quote:{quote_no}` | String(JSON) | 30s | 报价草稿详情（含四个质量标记） | 报价被修改、提交成交、放弃后主动删除 | 峰值约 200 个键，单个约 4KB，总计 < 1MB |
| `m20:sal:workbench:{staff_id}:{store_id}` | String(JSON) | 30s | 工作台首屏聚合结果 | 本人新建报价、本人提交成交后主动删除 | 峰值约 300 个键，单个约 8KB |
| `m20:sal:price:{product_code}` | Hash | 60s | 商品当前价与价格版本号 | 收到 `mdm.optical_product.updated` 后按 `product_code` 删除 | 在售商品约 3,000 个，单个约 0.5KB |
| `m20:sal:floor:{store_id}:{category_code}` | String | 60s | 该门店该类目的最低成交价（底价） | 底价配置变更、`mdm.rule.reload` 后清空 `m20:sal:floor:*` | 门店 × 类目约 120 个键 |
| `m20:sal:lock:quote:{quote_id}` | String | 30s | 报价编辑锁（防同一单两人同时改） | 主动解锁、TTL 到期 | 与在线导购数同阶，峰值约 50 |
| `m20:sal:target:{store_id}:{period}` | String(JSON) | 60s | 看板目标值（从 M10/M22 取回） | 期间切换、收到目标变更后删除 | 门店 × 3 个期间约 90 个键 |

**缓存通用规则（继承共享规范 §14）**：

1. 所有缓存 TTL 不超过 60 秒。报价与工作台取 30 秒，是因为需求方要求「导购改完自己的报价要立刻看到」，30 秒内本人写入时主动删键，不会看到旧值。
2. **缓存值必须带 `as_of`**，且命中缓存时响应里的 `data_quality` 必须是 `CACHED`。这一条不是可选项：`m20:sal:quote` 30 秒内被 5 个导购打开时，第 2~5 个人拿到的都是同一份数据，如果标成 `REALTIME`，页面会显示「刚刚更新」。
3. 缓存里只放报价、商品价、底价、看板配置这类**非身份数据**。不放患者姓名、手机号、证件号，也不放任何 Token。
4. **不得把上游返回的 `data_quality` 原样写进缓存再原样吐出去**（共享规范 §8A.2.1）。M10 的 `data_quality` 值域与 M20 不同，只有 `REALTIME` 一个能对上。缓存里只存上游的原始响应与 `as_of`，M20 自己的 `data_quality` 在出参时按 M20-CALC-05 现算。

## 8. 业务规则与校验

### 8.1 编号与格式规则

| 对象 | 规则 | 生成方式 |
|---|---|---|
| 报价单号 `quote_no` | `QT` + `yyyyMMdd` + 6 位日流水，如 `QT20261107000123` | Redis `INCR m20:code:QT:{yyyyMMdd}`，TTL 到次日 00:05 |
| 改价序号 `change_seq` | 同一报价内从 1 连续递增 | `SELECT COALESCE(MAX(change_seq),0)+1 ... FOR UPDATE`，配 `uk_m20_sal_price_log_seq` |
| 离线队列号 `queue_no` | `OF` + `yyyyMMdd` + 6 位 | **由 M20-01 生成，本模块只读** |
| 审批单号 `approval_no` | `SP` + `yyyyMMdd` + 4 位 | **由 M20-04 生成**。本模块当**不透明字符串**接收与回传，**不做位数、前缀、正则校验** |
| 销售单号 `order_no` | 由 M16 或 M10 生成 | 本模块**不校验格式**，只做非空与长度上限（64） |
| 加工单号 `lab_job_no` | 由 M10-07 生成 | 同上 |
| 顾客号 `customer_no` | 由 M10-05 生成 | 同上 |

**为什么本模块几乎不校验上游单号**：这些单号的格式在各自模块里可能随时调整（M18 那轮已经因为对 `AR` 单号做位数校验返工过一次）。M20-06 只需要保证「非空、不超过字段长度、原样透传」。**对上游单号做格式校验，收益是零，代价是上游改格式时你这里先挂。**

**`data_quality` 的取值来源（强制规则）**：本模块落库与展示的 `data_quality`，其取值**只能来自本模块自己的三个输入**：

| 输入 | 判定 | 对应取值 |
|---|---|---|
| 本模块调用的上游是否全部成功 | 任一失败 | `PARTIAL` |
| 是否命中本模块自己的 M20 缓存（且缓存年龄 > 30 秒） | 命中且超龄 | `CACHED` |
| 上游是否给出了可用的 `as_of` | 任一成功来源缺 `as_of`，或无法判定 | `UNKNOWN` |
| 以上都不成立 | — | `REALTIME` |

**不得读取上游响应里的任何 `data_quality` 字段**。原因见共享规范 §8A.2.1：各模块值域本就不同（M18 是 `REALTIME`/`DAILY`/`ESTIMATED`，M20 是 `REALTIME`/`CACHED`/`PARTIAL`/`UNKNOWN`），只有 `REALTIME` 字面相同；而且同一个词在不同模块含义也不同——上游的 `DAILY` 是「数据来自日批汇总」可能恰恰是最新的，本模块的 `CACHED` 是「自己 30 秒前的缓存」，两者成因完全不同，映射成一个值就把「上游本来就长这样」和「本模块缓存旧了」混成了一件事。**上游对自身新鲜度的原始描述只进 `degraded_sources[].reason`，作为给人看的辅助说明，不参与任何判定。**

具体实现见 §6.5 的 `calc_quality()`：它以（上游结果列表、缓存命中情况、缓存年龄）三个参数计算，函数签名里根本没有上游 `data_quality`，从代码结构上就取不到它。

| 编号 | 规则 | 违反后果 |
|---|---|---|

### 8.3 校验清单

| 编号 | 校验项 | 校验层 | 触发后行为 |

### 8.5 恒等式与闭合校验

| 编号 | 恒等式 | 用途 |
|---|---|---|
| E-01 | `change_amount = after_amount - before_amount` | 改价金额自洽，由 C-07 强制 |
| E-02 | `abs(change_ratio - round((after_amount - before_amount) / before_amount, 6)) <= 0.000001` | 改价比率自洽，由 C-09 强制 |
| E-03 | `need_approval = (abs(change_ratio) > 自主额度) OR below_floor OR (change_type = 'ADD_CHARGE')`（`change_ratio` 为 NULL 时视为触发） | M20-SAL-CALC-01 的三条件或 |
| E-04 | `quote_status = 'CONVERTED'` 当且仅当 `converted_order_no <> '' AND converted_at IS NOT NULL` | 由 C-02 强制 |
| E-05 | `consent_given = TRUE` 当且仅当 `consent_at IS NOT NULL AND retain_until IS NOT NULL` | 由 C-22 强制 |
| E-06 | `conflict_detected = TRUE` ⇒ `conflict_kind <> '' AND resolution = 'PENDING'` | 由 C-25、C-27 强制 |
| E-07 | 任一报价的 `change_seq` 集合必须是从 1 开始连续无空洞 | 并发写改价时的一致性 |
| E-08 | 话术有效率的分母 = 该期间 `customer_reaction <> 'UNKNOWN'` 的记录数 | 由 R-13 保证 |

### 8.6 审批阻断的三道防线

「审批不可用必须阻断」如果只写在第 8.4 的降级表里，它只是一句约定。落地要靠三道彼此独立的防线，任何一道单独失效时另两道仍然拦得住。

| 防线 | 位置 | 拦住什么 | 失效后果 |
|---|---|---|---|
| **第一道：接口层同步门** | API-10 第 3 步：先算 `need_approval`，为真则先调 P-01；P-01 抛错直接 return，不进入落库分支 | 正常的「审批挂了 → 不许改价」路径 | 若只有这一道，任何绕过 API-10 的入口（批处理、脚本、离线重放）都会漏过去 |
| **第二道：数据库组合约束** | `ck_m20_sal_price_log_need_approval CHECK (need_approval = FALSE OR approval_no <> '')`、`ck_m20_sal_price_log_below_floor CHECK (below_floor = FALSE OR approval_no <> '')` | 「先落库再补审批号」的写法：没有单号就写不进去 | 若只有这一道，运维可以手工补一个假单号 |
| **第三道：落库前的外部校验** | 写留痕行前调 P-02 核对该 `approval_no` 是否真实存在且 `approval_status ∈ (APPROVING, APPROVED, APPROVED_BUT_FAILED)` | 伪造/复用一个早已作废的单号 | P-02 不可用时**拒绝写入**，不放行 |

**第三道为什么必要**：第二道只能要求「非空」，不能要求「真实」。如果一个导购手上有上一单的 `approval_no`，在 API 里手工填进去就能过第二道。第三道把它挡住。

**P-02 不可用时为什么是拒绝而不是放行**：这里和 P-14 封存状态是同一个道理——**「查不到」在安全判定上必须等同于「不允许」**。查不到就放行，等于一次 P-02 抖动就打开一个风控缺口。

**三道防线的顺序为什么不能颠倒**：第一道在入口挡住绝大多数，成本最低；第二道兜住所有绕过入口的写入，成本为零；第三道只在真正要写库时执行一次远程调用，最贵，所以放最后。反过来先做第三道，正常路径每次改价都要多一次 200ms 调用。

### 8.7 离线边界的判定规则

「允许离线开单、不允许离线收款」这条边界不是靠一句话，是靠下面四条具体判定：

| 判定项 | 离线时 | 理由 |
|---|---|---|
| 创建报价草稿 | **允许** | 草稿不产生任何对外后果，落 `m20_base_offline_queue` 排队 |
| 计算报价金额 | **允许**，但必须带本地价目表的 `price_version` 与 `as_of` | 没有版本号就无法在重连后判断「当时算的价还算不算数」 |
| 判断库存是否充足 | **允许**，但结果只作为提示，不阻止开单 | 本地库存快照必然过期，用它拦截会拦掉本来有货的单 |
| 提交成交（写 M16 开单） | **禁止** | 必须在线，U-12 失败即 `"2006023"` |
| **记录收款成功** | **禁止，且没有字段可写** | `m20_sal_*` 九张表里没有任何字段能表达「已收款」 |
| 提交改价 | **禁止** | 改价可能触发审批，而审批不可离线 |
| 上传照片 | **允许**，本地入队 | 照片是证据，晚一点到不影响正确性 |

**「允许离线开单」开的是什么单**：开的是一张 `quote_status = DRAFT` 的**报价草稿**，不是 M16 的销售单。顾客离店时如果还没有网络，正确的做法是留联系方式、联网后回访成交，而不是当场收钱。**门店可以用「先付定金」来锁单，但那是 M16 收银台的事，不是 iPad 上的事。**

### 8.8 改价幅度异常的发现规则

改价留痕的价值不只是「事后能查」，更在于「当时能发现」。以下四条在统计页与告警里生效：

| 规则 | 阈值（可配置） | 触发后 |
|---|---|---|
| 单人单日改价次数 | > `M20_SAL.PRICE.MAX_DAILY_TIMES`（默认 20） | 该导购当日改价列表标「高频」，推给店长 |
| 单人单日平均让步幅度 | > `M20_SAL.PRICE.MAX_DAILY_AVG_RATIO`（默认 8%） | 同上 |
| 同一顾客短期内被反复改价 | 7 天内 ≥ 3 次 | 标记该顾客，提示店长关注 |
| 被拦次数（超底价/超额度/审批不可用） | > `M20_SAL.PRICE.MAX_BLOCKED_TIMES`（默认 10） | **即使一次都没成功也告警** |

最后一条最重要：**被拦下来的动作比放过去的动作更有信息量**。一个导购一个月被拦 40 次超底价改价，说明他在反复尝试突破底线——这比 40 次成功的改价更值得看，因为成功的那 40 次至少有审批号，而被拦的 40 次没有任何记录留存，只在 `m20_sal_usage_log` 里。

**为什么阈值可配置而不是硬编码**：门店之间的价格弹性不同（新店促销期让步本来就多）。硬编码会让告警要么天天响要么从不响，两种情况都等于没有告警。

**关于 U-13 与 U-12 的一处契约缺口，必须记录**：M16 总纲 `M16收费结算管理/M16_收费结算管理_详细设计.md:637` 把 P-08 登记为 `POST /internal/v1/m16/payments`（创建支付单），调用方写的是「M16-02/03/04」；M16-05 的 API-31 原文调用方也只列 `M16-02/03/04/06`。**M20 不在 M16 侧的调用方名单里。** 同理 P-10 `POST /internal/v1/m16/optical/order` 的调用方只写了 M10。M20-06 作为移动端，实际需要同时走这两个入口。

处理方式：本模块按共享规范 §9 登记的路径调用，**同时在验收里把这两条标为「需 M16 侧确认调用方名单」**（见 DA-07）。这不是本模块可以自行改的契约，需要向上游提请。**在确认之前，本模块对这两个接口一律按「可能不存在」处理**：U-12 失败时报价停在 `SUBMITTED` 并明确提示，U-13 失败时只展示收银引导文案而不尝试任何写操作。

### 10.3 发布事件

本子模块**不发布跨模块事件**。原因是铁律 5：审批的业务后果在申请方，但 M20-06 是**申请方本身**，它的业务后果（改价生效）落在自己的表里，不需要通过事件通知别人。改价结果通过 §10.2 U-15 的回执告诉 M20-04，这是请求-响应而不是事件。

若后续需要让 M10 感知移动端改价，应并入 `m10.order.amended`（`M10视光业务管理/M10_视光业务管理_06_配镜订单与取镜交付_详细设计.md:3155`），而**不是**新造一个 `m20.sal.*` 事件——两个模块各发一个「订单被改了」的事件，消费方就要处理两套。

**`m20.approval.completed` 的处理要点**：

1. **载荷里的 `result` 只是「审批结论」，不是「改单已生效」**。审批通过后，本模块才执行改单。所以收到 `APPROVED` 时，`approval_result` 先置为 `APPROVED_EXECUTING`（中间态），执行完成后按结果改为 `APPROVED` 或 `APPROVED_BUT_FAILED`，**然后回调 U-15**。
2. **不看 `exec_confirm_status` 做业务判断**（共享规范 §13）。那个字段是 M20-04 记录「申请方有没有回执」用的，本模块自己就是申请方，该由本模块回执，而不是反过来去读。
3. 收到 `REJECTED` 时，报价金额保持「改价前」不变，`approval_result = REJECTED`，并把 `reject_reason` 落到留痕里。**驳回不能只把这行删掉**——「提过一次被否了」本身是合规信息。

## 附录 E：关键决策记录

**E-01 改价留痕独立成表且只增不删，而不是在报价表上加 `last_change_*` 字段。**

如果只在报价草稿上留三个字段（改前金额、改后金额、原因），那么第二次改价时会覆盖第一次。运营想问「这个导购一个月改了多少次价、每次多大」，答案永远只有最后一次。**更根本的是：删掉一条改价记录，事后无法证明「从来没有过这次改价」，也无法证明「有过」**——移动端私下让价一旦发生纠纷，缺少的恰恰是这条链。所以独立成表 + `REVOKE UPDATE, DELETE`。

反过来，如果做成「报价表带一个 JSON 数组存历史」，问题是没有办法对单次改价做审批号关联与外键完整性，也没法按改价幅度建索引做统计。

**E-02 改价审批走「同步拿单号 + 落库」，而不是「先落库再异步提交审批」。**

同步方案下，P-01 返回 200 后才写留痕行（P95 ≤ 200ms，用户无感）。异步方案看起来更快，但它有一个致命裂缝：**用户点下改价的瞬间，报价已经按新价算了，审批还在路上**。这时候如果顾客当场付款，成交价就是未经审批的价格。M10-06 降级表 `:7383` 写的「阻断，不允许执行」正是要堵这条缝。

**代价**：审批服务挂掉的这几十秒到几分钟里，一线完全改不了价。这是有意选的——**改不了价，顾客可以去别家；改了不该改的价，公司要退钱**。

**E-03 离线只到「待收款」为止，`m20_sal_*` 里没有任何字段能表达「已收款」。**

不是靠纪律约束，是靠**表结构上根本没有这个字段**。收款结果只在 M16。断网时允许开单、允许算价、允许排队，但「这笔钱到账了」这句话只有 M16 能说。`POST /internal/v1/m16/payments` 不可用时，本模块连一条「待补收款」的记录都不写——因为写了就一定会有人在联网后忘记补，然后账上少一笔钱而系统里看起来一切正常。

**E-04 报价草稿用 JSONB 存明细行，而不是拆出 `m20_sal_quote_item` 子表。**

验光配镜的商品行结构随品类剧烈变化：镜片有屈光度、折射率、镀膜，镜架有尺寸、材质、颜色，护理液只有数量。拆成子表需要 30 个左右的列，其中 24 个常年为 NULL。JSONB 更贴合。

**代价是放弃了数据库层对「行金额加总等于总额」的约束**。这一点用两道防线补：Service 层重算校验 + 每次写入落 `usage_log` 存档当时的 `item_json`。**这不是理想解，是权衡后的解。**

**什么时候必须重构成 `m20_sal_quote_item` 子表——两条可判定条件，任一成立即触发：**

1. **商品类型收敛到三种以内**：品类趋于一致时，30 列里 24 列常年为 NULL 的代价不再成立，「用 JSONB 省列」这个理由就消失了。
2. **出现「按明细内部字段做统计或查询」的需求**：例如「统计本月卖了多少片某折射率的镜片」「查哪些报价单里含镀膜加硬」。JSONB 在 `GIN` 索引下能做包含查询，但**分组聚合必须在应用层展开 JSON 数组**，随历史数据增长会变成全表扫描。

**JSONB 的根本判据是「只整体读写、从不按内部字段查询」。** 一旦有按内部字段查、分组、聚合的需求，这个前提就不成立了，此时留 JSONB 不是权衡，是欠债。第 2 条尤其要警惕：它往往不是一次性提出来的，而是某天运营在报表里加了一个「按材质统计」，然后逐月变慢。

**E-05 冲突一律不自动解决，包括「服务端版本更新且看起来只是改了个备注」这种情况。**

`ck_m20_sal_offline_conflict_pending` 强制冲突行 `resolution = PENDING`。自动解决的风险在于判定逻辑本身：如果拿 SQL 去比「只有备注变了就自动合并」，那么下一次需求变更说「价格微调也算无损」时，改的就是这一行判断，而**没有人会重新评估这条 SQL 在全店 4 万笔离线单上的影响**。人工处理虽然慢，但每一个冲突都有人看过——这正是 `m20_offline_conflict_total` 指标存在的意义：**它不是要归零，它是要被发现。**

**E-06 看板不存目标值，取不到就显示「目标未设定」。**

存了就会与 M10/M22 的目标不一致，看板是给导购看「还差多少」的，**差错了比不显示更糟**。取不到时显示 0 会让导购以为进度是零而拼命推单，实际是目标压根没配。

**E-07 本模块不发布跨模块事件。**

改价生效的结果只在本模块表里，外部不需要知道。若 M10 需要感知，应并入 `m10.order.amended`，而不是 M20 另发一个「订单被改了」——两个模块各发一个，消费方要处理两套时序，而这两套时序之间没有顺序保证。

**E-08 扫码录入镜片参数在本模块完成，不依赖上游写接口。**

共享规范 §9.14 把这条标为「需核实」。核实结果是：M10 的扫码只用于加工师报工（`scan_code`）与隐形眼镜试戴片序列号，M01 只有耗材条码表 `mdm_material_barcode`，**没有任何「销售端扫码录入镜片参数」的写入接口**。因此本模块自作主张：扫码只做「解析成 `product_code` 与当前价」，然后填入报价草稿的 `item_json`，最终通过 U-12 交给 M16 开单。**这是一次显式的裁决，不是遗漏。**
