### 1.2 判据：这张表存的东西，M20 删库重建后会丢吗

判据直接沿用总纲 §1.4 的红线，一字不改：**M20 删库重建，会不会有业务事实丢失？会 → 可以建；不会 → 不许建。**

本子模块是**纯读**子模块（总纲 §2.3），它不产生任何临床事实，所以按红线能立的表只有两类：

- **一类：检索行为留痕。** 「张护士在 2026-11-07 10:09:41 查了患者 10021 的病历摘要，命中 1 条」——这件事只发生在 M20，删库后重建不出来。它在《医疗机构病历管理规定》的「谁在什么时候看了谁的病历」取证链条里是唯一证据。
- **二类：本子模块自己的适配与统计。** 常用查询、快捷入口、检索词热度、上游可用性采样、响应体体积审计，都是「M20 自己怎么工作」的元数据，不属于任何人。

反过来，**下面这些一张都不能建**，理由不是「嫌麻烦」，是建了就等于制造第二份临床事实：

| 诱惑点 | 会不会建 | 理由 |
|---|---|---|
| `m20_qry_patient` 患者快照 | **不建** | 患者主索引在 M03-01。姓名、性别、年龄、手机号一旦落 M20 库，M20 就多了一个泄露面，且与 M03 分叉后无法判定谁对 |
| `m20_qry_report_cache` 报告正文缓存 | **不建** | M12/M13 报告单份 PDF 可能 200KB（M12-03 `m12_report_file.size_bytes` BIGINT 实测最大 90 万字节）。落本地缓存意味着「PC 端看到新报告、手机看到旧报告且无提示」——共享规范 §17 第 10 条与第 24 条 |
| `m20_qry_bed` 床位快照 | **不建** | 床位权威在 M05-02。床位是护士执行医嘱的定位依据，缓存过期一条就是「按旧床位找人」 |
| `m20_qry_order` 医嘱副本 | **不建** | 医嘱权威在 M07。**这是最不能碰的一条**：副作用是护士按旧剂量给药 |
| `m20_qry_metric_cache` 指标缓存 | **不建** | 指标值权威在 M22。且 M22 的移动看板有硬约束 `cache_ttl_sec <= 120`（`M22报表与决策支持/M22_报表与决策支持_08_财务主题分析与决策看板_数据结构.md:382`），M20 再存一层等于绕过该约束 |
| `m20_qry_search_log` 检索留痕 | **建** | 见上，唯一证据，且是只增不删表 |
| `m20_qry_sensitive_access` 敏感字段访问登记 | **建** | 与检索留痕不同：检索留痕记「谁查了」，本表记「谁看了脱敏字段背后的完整值」。这是共享规范 §5 与总纲 §8.3「看全文另行鉴权并留痕」的落地表 |

### 1.3 为什么 `m20_qry_search_keyword` 不与 `m20_qry_search_log` 合并

直觉上「检索词统计」当然是 SQL 对留痕表做 `GROUP BY` 出来的，为什么还要单独一张表？三条理由：

1. **留痕表不带检索词明文，统计表也不带。** 这是本子模块最硬的一条设计（详见详细设计 §3.4 与 §8.4）：`m20_qry_search_log` 只记 `keyword_length`（**长度**不是内容）、`keyword_hash`（SHA-256 前 16 位，仅用于「同一个词被查了几次」的基数估算，不可逆）、`condition_fields`（条件**字段名**集合）、`hit_count`。因此**留痕表里根本没有一个可以用来 `GROUP BY` 出「热门检索词」的列**。
2. **热门检索词要做「白名单化」才能展示。** `m20_qry_search_keyword` 的 `word_text` 只允许写入**字典白名单内的词**（附录 D.2 的 3,000 条眼科诊疗词表 + M01-01 主数据名称），其余一律记成 `word_text = NULL` 且仅累加 `anonymous_count`。原因见详细设计 §1.2：用户会在搜索框里输入患者姓名甚至粘贴身份证号，把这些原文聚合成「热门搜索 TOP 50」直接展示，等于给自己做了一个无限期保存的敏感信息库。
3. **聚合窗口与保留期不同。** 留痕表按月分区、保留 3 年（汇总 §10）；统计表按 `stat_date` 保留 5 年、单表单行增长。若合并，做年度对比时要扫 4,380 万行。

### 1.4 为什么 `m20_qry_patient_view` 与 `m20_qry_sensitive_access` 要拆开

两者都在「看患者」，区别是**看的是什么粒度**：

- `m20_qry_patient_view`：一次**聚合查询**的调用事实。一条 = 一次「查了 patient_id=10021 的聚合视图」。字段是 `query_scene`（查的是哪个场景）、`upstream_status_json`（这次哪些上游成功/失败）、`degraded`、`as_of`、`elapsed_ms`、`record_count`。**它回答「M20 的这次聚合快不快、全不全」。**
- `m20_qry_sensitive_access`：一次**敏感字段解封**的动作事实。一条 = 「张医生在 10:12:07 查看了患者 10021 的完整身份证号与手机号，理由：核对身份，二次验证通过」。**它回答「谁看了不该随便看的东西」。**

拆开的三条理由：写量与保留期差 10 倍（患者聚合视图日 3 千次 / 敏感解封日约 200 次）；权限不同（前者 `m20:qry:patient:view`，后者 `m20:qry:sensitive:view` 且必须二次验证）；**查询语句不同**——`m20_qry_patient_view` 按 `staff_id + created_at` 查「我今天查过谁」，`m20_qry_sensitive_access` 按 `patient_id + created_at` 查「这个患者的身份证号被谁看过」。合成一张后两条索引都建不全。

### 1.5 为什么要有 `m20_qry_upstream_health`

本子模块的每一次查询都要拼 1~6 个上游（详细设计 §10.2 的对齐表）。**上游慢或抖，本子模块的唯一正确反应是「明说降级」，而降级判定必须基于事实而不是感觉。**

`m20_qry_upstream_health` 每 5 分钟对每个 `upstream_code` 采一次样：最近 1 分钟的成功率、P95 耗时、连续失败次数。它有三处用途：① 首屏聚合时的**主动熔断**（连续失败 3 次且成功率 < 50% 就跳过该上游并置 `degraded = true`，而不是等它超时 300ms）；② `m20_degraded_total` 指标的分母；③ 排障时回答「10:05 那次报告查不出来，是 M12 挂了还是网络」。

它**不是**指标表、不是监控数据副本（监控权威在 Prometheus），只是 M20 服务自己的、可被 `SELECT` 的熔断状态机。判据回到总纲 §1.4：删库重建后这些采样值确实丢了，但它们丢了不影响任何业务事实，**所以它属「可选留存」而非「必须留存」，保留期只给 7 天**。

### 1.6 为什么 `m20_qry_response_audit` 只记体积不记内容

总纲 §8.1 定死了「单次响应体 ≤ 200KB」，共享规范 §17 第 10 条要求「构造 20 条都有长文本的列表，断言响应体 < 200KB」。**要验收这条，就得有生产环境的事实依据，不能只在测试里跑一次。**

本表每次超过阈值（默认 120KB，留 40% 余量）的响应记一行：`page_code`、`api_code`、`response_bytes`、`item_count`、`largest_field`（哪个字段最占体积）、`truncated`（有没有触发截断）。**它不记任何响应内容**——记内容就是把报告全文抄进日志，正是第 10 条要防的事。

### 2.1 只增不删表的落地细节

`m20_qry_search_log` 是共享规范 §12 点名的只增不删表。落地必须同时满足四条，缺一条都等于没做到：

```sql
-- 1) 表上没有逻辑删除列（不是「有但不用」，是根本没有这个列）
-- 2) 应用账号无 UPDATE / DELETE 权限（放在迁移最后，downgrade 里 GRANT 回来）
REVOKE UPDATE, DELETE ON m20_qry_search_log FROM app_user;
-- 3) 更正走追加：发现某条留痕写错，不改原行，追加一条 corrective_of_id 指向原行
-- 4) 真正删除只有一条路：DETACH + DROP 整个过期分区，由 m20_archiver 账号执行（汇总 §10.2 第 6 步）
```

**为什么第 3 条要写进结构而不是留给代码自觉？** 因为留痕表一旦允许 `UPDATE`，它就不再是证据。取证时对方律师只要问一句「你们这张表谁能改」，所有留痕的可信度都归零。追加更正是唯一能同时满足「改错了要能表达」和「原记录不可改」的做法，`corrective_of_id` 列因此不是可选项。

### 2.2 为什么三张跨子模块共用表一张都不用

| 共用表 | 一般会怎么用 | 本子模块为什么不用 |
|---|---|---|
| `m20_base_idempotency` | 写接口的幂等键落库 | 本子模块**全部接口都是只读 GET**（详细设计 §6.1），没有写接口，不需要幂等键 |
| `m20_base_offline_queue` | 离线操作排队重放 | 本子模块**不支持离线**：查询结果必须实时拉取，离线时页面明确显示「网络已断开」，不排任何重放任务 |
| `m20_msg_todo` | 待办聚合 | 待办权威在 M20-08。本子模块的「关注的患者」只做**快捷入口**（§4.6），不是待办 |

### 2.3 为什么 `m20_qry_patient_view` 不被禁止表清单命中

`validate_m20.py` 的 `check_forbidden` 会抓「加了子模块前缀的绕法」——正则 `m20_(base|doc|nur|apr|qry|sal|fol|msg)_(\w+)` 里后缀命中禁止表裸名（`patient`/`order`/`bed`/`report`/`metric`/`dashboard`…）即报错。`m20_qry_patient_view` 的后缀是 `patient_view` 而**不是** `patient`，所以字面不命中；但**字面不命中不等于设计正确**。三条判据：

1. **它不含任何患者字段。** 字段表里只有 `patient_id`（M03 的逻辑外键，不带外键约束）与 `patient_no_hash`（用于「同一个人被查了几次」的基数估算，不可逆）。**没有姓名、没有性别、没有年龄、没有手机号、没有证件号**——这些值一律不落库，每次实时调 M03-01 `GET /internal/v1/patient/{id}/brief`。
2. **它记的是「查」这个动作，不是患者。** 一条记录的主语是 `staff_id`，宾语才是 `patient_id`。删掉整个 `m20_qry_patient_view`，患者的任何信息都不会少一个字段。
3. **它不能被用来还原患者。** 假设有人拿到全表，他能知道「10021 号患者在 10:09 被查过 3 次」，但拿不到 10021 是谁。

**反例对照**：若把它建成 `m20_qry_patient(id, patient_id, patient_name, gender, age, mobile, ...)` 并加个 `cached_at`，那就是标准副本，必须禁止。

## 3. 公共字段与命名约定

| 约定项 | 取值 | 依据 |
|---|---|---|
| 主键 | `BIGINT GENERATED ALWAYS AS IDENTITY` | 共享规范 §2.6 |
| 时间类型 | `TIMESTAMPTZ`，全系统 Asia/Shanghai 展示 | 共享规范 §2.4（**不是**不带时区的时间戳，M20 要跨端比较「几分钟前」） |
| 审计列 | `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`、`created_by BIGINT` | 共享规范 §2.6 四审计列，只增不删表只有前两列 |
| 更新列 | `updated_at TIMESTAMPTZ`、`updated_by BIGINT` | 仅可更新表有 |
| 逻辑删除 | `is_deleted BOOLEAN NOT NULL DEFAULT FALSE` | 仅可更新表有；**`m20_qry_search_log` 与 `m20_qry_sensitive_access` 没有此列** |
| 状态列 | `VARCHAR(32)` + `CHECK` 枚举，不用数据库 ENUM | 共享规范 §2.6 |
| 金额 | `NUMERIC(14,2)` | 共享规范 §2.4（本子模块无金额列，此行为全模块一致性声明） |
| 比率 | `NUMERIC(10,6)` | 共享规范 §2.4 |
| 计数 | `INTEGER`（< 21 亿）/ `BIGINT`（行数类） | 行数类用 BIGINT，其余 INTEGER |
| 索引命名 | `idx_m20_qry_{表简称}_{用途}` / `uk_` / `ck_m20_qry_{表简称}_{含义}` | 汇总 §2.1 |
| 维度空值 | 存 `''` 而非 `NULL` | 共享规范 §17 第 21 条：PostgreSQL 唯一索引认为 NULL 互不相等 |

**关于「维度空值存 `''`」在本子模块的具体落点**：`m20_qry_search_keyword` 的唯一键是 `(stat_date, word_hash, condition_sig)`，其中 `condition_sig` 是条件字段名集合的归一化签名（如 `created_at|dept_id|patient_id`）。当检索只有一个条件时，其余位不填 `NULL`，而是拼成固定长度的短签名，保证同一份签名在唯一索引里能命中。

**关于 `patient_no_hash`**：`SHA-256(patient_no + 服务端盐)[:16]`。用哈希而不用明文的原因：留痕表的每一行都会被 DBA、运维、审计抽查，明文像「10021」这样的连续号会被直接反推为「M20 在存患者号」。哈希后可回答「A 和 B 查的是不是同一个患者」（两张哈希相同即可），但无法从哈希还原出患者号。

#### 4.1.1 为什么本子模块一张物理外键都不建

共享规范 §4.x 硬要求写的是「跨子模块引用不建外键，M20 内部表必须建外键」。本子模块是这条规则的**唯一例外**，理由是这 8 张表全部是**纯追加的留痕与统计表**，它们对外键有天然的反感：

1. **留痕表在业务写入的热路径上。** 一次检索要写 `m20_qry_search_log`，如果它有外键指向另一张 M20 表，每次插入都要对该表加 `FOR KEY SHARE` 行锁——在高并发检索下这把锁会与任何 `UPDATE` 冲突。**留痕宁可写失败进补偿队列，也不能因为锁竞争拖慢查询。**（召回：共享规范 §17 第 11 条同源事故。）
2. **留痕的存在时间长于被引用对象。** `m20_qry_saved_query` 被删了（逻辑删除，物理行仍在），引用它的历史留痕必须仍然可读。外键在 `DROP`/物理清理时会阻断清理流程。
3. **统计表的聚合源本身会过期。** `m20_qry_search_keyword` 的 `stat_date` 早于留痕表保留期的部分仍然保留（统计保留 5 年、留痕 3 年），此时源行已经不在了。
4. **唯一需要的「引用」是审计链条上的软引用**：`m20_qry_search_log.corrective_of_id` 指向同表另一行。这一条用自引用实现，且**不加外键**——更正行的原行可能已被分区 DETACH 归档，加外键会让归档前置检查失败。

**反向约束（必须写清，否则「不建外键」会变成「不校验」）**：

| 关系 | 校验方式 |
|---|---|
| `m20_qry_search_log.staff_id` | 写入前由 U-01 Token 校验与 U-05 权限上下文保证，非可空 |
| `m20_qry_search_log.patient_id` | 可空（检索条件里没有患者时不填）；**写入不做存在性校验**——多做一次 M03 调用会让每次检索多 50ms，且患者被合并后旧 ID 也应保留原样 |
| `m20_qry_search_log.corrective_of_id` | 应用层校验 `target.search_log_id` 存在且 `target.created_at` 在同一分区或已归档（归档时置 `target_archived = true`） |
| `m20_qry_saved_query.quick_entry_id` | 应用层校验，`ON DELETE` 语义由应用实现：快捷入口停用时把订阅的 `quick_entry_id` 置 `NULL` |
| `m20_qry_patient_view.search_log_id` | 不建立列级引用（冗余过重）；靠 `(staff_id, patient_id, created_at)` 三元组关联 |

```sql
ALTER TABLE m20_qry_patient_view

    CHECK (client_type IN ('IOS', 'ANDROID', 'MINI_PROGRAM', 'H5', 'PAD'));

ALTER TABLE m20_qry_patient_view
    ADD CONSTRAINT ck_m20_qry_patient_view_quality
    CHECK (data_quality IN ('REALTIME', 'CACHED', 'PARTIAL', 'UNKNOWN'));

-- 组合语义：degraded 为 TRUE 必须至少有一个上游失败，且成功数 + 失败数 ≤ 上游总数
ALTER TABLE m20_qry_patient_view
    ADD CONSTRAINT ck_m20_qry_patient_view_degraded_combo
    CHECK ((degraded = FALSE AND upstream_fail_count = 0)
        OR (degraded = TRUE AND upstream_fail_count >= 1));

-- 组合语义：命中缓存必须有缓存年龄，未命中必须是 NULL（防「命中缓存但 age 为空」导致
-- 新鲜度判定把 CACHED 误判成 REALTIME）
ALTER TABLE m20_qry_patient_view
    ADD CONSTRAINT ck_m20_qry_patient_view_cache_age
    CHECK ((data_quality = 'CACHED' AND cache_age_sec IS NOT NULL)
        OR (data_quality <> 'CACHED' AND cache_age_sec IS NULL));

-- 组合语义：unknown 质量必须是真的判不出来（以 as_of 是否可判定为标志）
ALTER TABLE m20_qry_patient_view
    ADD CONSTRAINT ck_m20_qry_patient_view_as_of
    CHECK (as_of <= created_at + INTERVAL '120 seconds');
```

**为什么 `ck_m20_qry_patient_view_cache_age` 要这么写？** 总纲 §6 的 M20-CALC-05 规定「有数据来自缓存且缓存年龄 > 30s → `CACHED`」。如果留痕表允许「`data_quality='CACHED'` 但 `cache_age_sec` 为 NULL」，那么事后复核时无法判断当时到底缓存了多少秒，M20-CALC-05 就退化成了一句口号。这条约束把「判定依据」和「判定结论」绑死。

**为什么 `ck_m20_qry_patient_view_as_of` 用 120 秒而不是严格的「小于记录时刻」？** 因为 `as_of` 是**上游的数据口径截止时刻**，在系统时间略有偏差或上游提前生成的情况下可能比 `created_at` 晚几秒到几十秒。120 秒是兜底上界（超过就说明 `as_of` 被错误地填成了 `now() + 未来偏移`）。**这里刻意不用 `as_of <= created_at`**：那会逼着实现者把 `as_of` 截断到请求时刻，正好是总纲 §6 明列的头号常见错误。

**设计说明：**

1. **本表刻意不含任何患者属性列。** 判据见 §2.3。若将来有人提议「顺手存个 patient_name 方便排查」，正确的做法是排查时用 `patient_id` 去 M03 查，而不是往留痕表里加列。
2. **`as_of` 与 `created_at` 是两个不同的时刻，都必须留。** `created_at` 是「这次查询发生在什么时候」，`as_of` 是「数据截止到什么时候」。总纲 §6 的算例里 `created_at = 10:09:42` 而 `as_of = 10:09:35`，两个时刻差 7 秒。**只留一个，事后就无法复现当时的降级判定。**
3. **`degraded` 由「上游是否全部成功」判定，与本表有没有数据无关。** 共享规范 §17 第 3 条：`degraded` 不能按「本地有没有数据」判断。本表是留痕表、本地永远有数据，这条尤其容易写错。
4. **为什么 `upstream_ok_count + upstream_fail_count` 不约束等于 `upstream_codes` 的元素数？** 因为被预算或熔断跳过的上游既不算成功也不算失败，它们记在 `skipped_codes`。若强行约束三者相等，就得把跳过算成失败，那会把「主动保护」误报成「上游故障」。

### 4.3 表：`m20_qry_search_log`（检索留痕 · 只增不删 · 月分区）

**用途：** 记录每一次「用户在移动端发起的检索」这一事实。一条 = 一次检索请求。它服务于两类用途：①《医疗机构病历管理规定》要求的「谁在什么时候查了谁」取证链；②运营侧的「检索命中率 / 热门条件 / 检索无结果比例」分析。

**这是一张只增不删表**（共享规范 §12 名录）：表上没有逻辑删除列，迁移末尾执行 `REVOKE UPDATE, DELETE`，更正走追加行（`corrective_of_id`），物理删除只有「过期分区 DETACH + DROP」一条路且由专门的归档账号执行。

**写入方：** M20-05 检索服务（异步队列 `m20_qry_persist`）。**只读方：** 审计员（M02-06 追溯）、M20-05 检索分析页（P04）、M22-06。

**本表最硬的一条设计：不记完整检索条件。** 详见下方「设计说明」第 1 条。

**分区策略：**

- **分区键：** `created_at`，**按月 RANGE 分区**。
- **预建策略：** 每月 20 日由 APScheduler 任务 `m20_qry_partition_ahead` 预建后两个月的分区，保证「永远有至少 1 个未来分区」。
- **DEFAULT 分区必须存在。** 没有它，预建失败或跨年未预建时，新月份第一条 INSERT 直接报 `no partition of relation "m20_qry_search_log" found for row`。**值班人员看到的不是「少了个分区」，而是「查询功能突然报错」**——因为留痕写入在检索响应的异步链路里，写入失败会触发告警，而运维第一时间拿到的是「检索留痕写不进去」这种二级症状。共享规范 §4 与汇总 §4.3 都点名这条。
- **DEFAULT 分区必须保持为空。** 落到 DEFAULT 的行由巡检 SQL 检出（汇总 §8.3 第 3 条），期望 0 行；非 0 行说明预建链路断了，需要立即补建并把行迁回去。
- **归档：** 保留 3 年（汇总 §10），到期分区 `DETACH PARTITION` 后导出归档库，再由 `m20_archiver` 账号 `DROP`。**这是整张表唯一一次真正的删除**，前置有抽样哈希校验（汇总 §10.2 第 6 步）。

**设计说明：**

1. **为什么「不记完整检索条件」是本表最硬的一条。** 用户在检索框里输入的很可能是患者姓名（「张三」）、就诊号、甚至是一段粘贴进来的身份证号。如果留痕表长成 `WHERE keyword = '张三'` 的样子，它会同时具备三个特征：①**永久保存**（只增不删表，3 年后才归档）；②**权限比业务表低**（运维、DBA、备份都能读到日志表，但不一定有权看患者主索引）；③**看起来合理**（「日志表嘛，记全一点方便排障」）。三者叠加，就是给自己造了一个无限期保存的敏感信息库，且没有任何人会觉得它是敏感信息库。**所以本表只存 `keyword_length`（长度）、`keyword_hash`（不可逆哈希）、`condition_fields`（字段名集合）、`hit_count`（命中数）。**
2. **为什么 `keyword_hash` 对纯数字检索词写 NULL。** 就诊号、手机号这类纯数字串的取值空间有限，拿一个 16 位哈希做字典攻击是可行的（枚举 1 万个就诊号算一遍即可反推）。`ck_m20_qry_search_log_hash_combo` 把这条落成了约束：`keyword_class = 'NUMBER'` 时哈希必须为空。**代价是失去「同一个人被查了几次」的能力，收益是杜绝可逆性。**
3. **`condition_fields` 只记字段名不记值，是刻意的。** 运营侧真正想知道的是「用『科室 + 日期 + 状态』组合的人多」还是「只用姓名的人多」——这是**条件结构**的信息，与字段值无关。记字段名既够用，又不泄露。
4. **`ck_m20_qry_search_log_total_combo` 为什么禁止用 0 或 -999 表达「不知道总数」。** 共享规范 §2.3 允许 `total` 为 `null`（不得为凑 total 扫全表）。若留痕表用 0 表达 null，那么「零命中」和「没算总数」在数仓里就无法区分，运营报表会把两者混成一个数。本约束强制用 `-1` + `is_total_null = TRUE` 这一对组合表达。
5. **`sql_perm_applied` 恒为 TRUE 的约束是一个「自我证伪」设计。** 共享规范 §17 第 3 条与总纲 §8.3 都要求权限过滤在 SQL 层。代码里若某个分支退化成应用层过滤，最直接的证据就是它自己会写一行 `sql_perm_applied = FALSE`——但这条 CHECK 会让它写不进去，从而在写入失败的告警里暴露。**这比让它写进库再事后分析有效得多。**
6. **为什么主键是 `(id, created_at)` 而不是 `id`。** PostgreSQL 分区表的唯一约束必须包含分区键，否则无法保证全局唯一。汇总 §4.2 已写明这一点。副作用：`id` 单独不再唯一，所有按 id 的查询必须带 `created_at` 或走 `search_no`。

**设计说明：**

1. **`ck_m20_qry_search_keyword_text_combo` 是本表的立表之本。** 如果只靠代码里一句 `if word in whitelist`，那么半年后有人加一个「导出全部检索词」的运维功能，就会把患者姓名导出去。把它写成 CHECK，意味着**数据库层面根本不存在「非白名单词带原文」的行**，任何导出功能都导不出不存在的东西。
2. **`DICT_WORD` 的判定发生在聚合任务里，不在请求路径上。** 请求时只做一次集合查找（3,000 条白名单放内存，O(1)），写入留痕表的 `keyword_class`；夜间聚合时再按 `keyword_class = 'DICT_WORD'` 挑出来写 `word_text`。这样检索请求的耗时不受白名单大小影响。
3. **为什么统计表允许 `updated_at`（可更新），而留痕表不允许？** 因为这是**聚合结果**不是**原始事实**。当日滚动累加时同一行会被 `UPDATE` 多次，这是正常且必要的。**原始事实只增不删、聚合结果可重算**——这条边界必须写清楚，否则「为什么这张能改、那张不能改」就成了拍脑袋。

#### 4.4.1 词表姓名风险分级与扫描取证（`name_risk_class`）

**这一节存在的理由：推荐词表是整个 M20-05 防线里唯一一个绕过权限过滤的通道。**

检索建议是这样工作的：用户打了两个字符，系统弹出「你是不是想搜：青光眼术后」。这个弹窗**出现在任何人的屏幕上**，包括没有那个患者权限的人。它不走检索接口、**不产生 `m20_qry_search_log` 记录**、不经过任何脱敏——它只是把一个词显示出来。

于是：**如果词表里存在一个患者或医生的姓名（哪怕这个词条同时也是一个医学术语），推荐列表本身就成了一条跨权限的信息泄露通道，而且它不报错、不留痕、无法追溯。**

更要紧的是它的触发条件：**只有数据里真的存在那个姓名时才会发生**。今天词表里「安宁」是安全的，明天来了一位叫「安宁」的患者，这个词条就开始每天在别人的手机上显示她/他的名字。**所以这是一个「今天查干净不等于以后干净」的问题**——只做一次扫描是不够的，必须把判据落成字段与约束。

##### 判据

对词表每条词条问一个问题：**这个词条单独出现时，能不能同时被当作一个自然人的姓名？**

| 规则 | 内容 | 依据 |
|---|---|---|
| R1 | **音译人名词根**：词条主体是国际命名术式/征/综合征的人名音译（Marfan、Horner、Fuchs、Vogt-Koyanagi 等） | 音译姓氏本身就是姓名片段 |
| R2 | **首字是常见姓氏** | 「黄斑」「白内障」「麦粒肿」——姓氏字只是构词，主体是术语 |
| R3 | **非姓氏开头但两字都是常用名用字** | 「安宁」不是姓氏开头，但它就是一个名字 |
| R4 | **纯数字或纯字母短词条** | 与身份证号、病历号的字符串形态重合，且形如姓名的字母串无法与编号区分 |
| R5 | **与本院职工姓名完全一致** | 由信息科一次性导入职工姓名集合做内存比对；**集合不入库、不进日志、不回显** |

**R5 的执行约束：** 职工姓名集合只在扫描脚本的内存里存在，扫描结果只输出「命中的词条」与「条数」。若该集合文件缺失，**脚本必须显式打印「本规则跳过，上线前必须补齐后重跑」并以非零退出码结束**，不允许静默通过——一条没跑的风险规则比没有这条规则更危险，因为后者至少让人知道要补。

##### 三档处置

| 档 | 判据 | 处置 |
|---|---|---|
| **A** | 该词条单独出现即可作为自然人姓名 | **不进推荐结果集，但仍可被完整检索命中** |
| **B** | 首字是姓氏但主体是术语 | 可推荐，但**推荐语不得以单姓开头**（「黄」不推荐，「黄斑」推荐） |
| **C** | 纯术语，无姓名可能 | 原样保留 |

**A 档为什么是「不推荐」而不是「删除」：** 如果直接删词，「青光眼」这种核心术语万一被误判成姓名，医生就搜不到它了。**一个医生在急诊搜不到「青光眼」的代价，比推荐列表里多显示一个姓名的代价更大。** 所以 A 档的语义是**降级**——检索功能完好，只是系统不主动把它念出来。

##### 落成机制（不只是这一次的扫描结果）

| 关卡 | 位置 | 硬约束 |
|---|---|---|
| 1. 导入必填 | `m20_qry_search_keyword.name_risk_class` | 列**无默认值**，`CHECK (name_risk_class IN ('A','B','C'))`；导入流程漏标直接失败 |
| 2. 组合语义 | `ck_m20_qry_search_keyword_name_risk_combo` | `word_class = 'DICT_WORD' OR name_risk_class IS NULL`——只有带可见原文的词才谈得上推荐 |
| 3. **SQL 层过滤** | 推荐/热门榜查询 | 查询语句必须带 `WHERE name_risk_class <> 'A'`，且写进索引定义 `idx_m20_qry_search_keyword_top` 的 `WHERE` 子句里 |
| 4. 检索不受影响 | 检索接口 | **A 档词条照常参与检索匹配**——过滤只发生在推荐查询上，不在检索查询上 |

**第 3 条为什么必须落在 SQL 层：** 和详细设计 §8.1 权限过滤是同一条理由——应用层过滤的失败模式是「某处忘了过滤，结果全出」，SQL 层是「生成不出条件 → 空结果 → 不显示」。**推荐列表宁可不弹，也不能弹错。** 而且这里还多一层保障：索引的 `WHERE` 子句里也写了 `name_risk_class <> 'A'`，**索引层面就拿不到 A 档词，查询层不可能返回它**。

**第 4 条为什么必须写明：** A 档是「不推荐」，不是「不可用」。如果有人把过滤条件误加到检索路径上，医生就搜不到 `Horner综合征` 了——**这是把一个隐私问题换成了一个临床问题。**

**设计说明：**

1. **`query_params` 里明确禁止放自由文本关键词。** 存下来的条件是「科室=15 AND 状态=待处理 AND 日期=今天」这类结构化条件。**若允许存自由文本，用户很可能把「张三」存进常用查询，而这个字段会一直被复制、被导出、被报表使用**——等于把 4.3 好不容易挡住的敏感信息从另一扇门放进来。应用层在保存时校验 `query_params` 的值类型只能是 ID、枚举、日期、区间。
2. **订阅四件套约束防的是「僵尸订阅」。** 现实里最常见的写法是「勾了『每日提醒』但忘了填时间」，此时 `subscribe_cycle = 'DAILY'` 而 `next_run_at` 为 NULL，调度任务扫到它却不知道几点跑、干脆跳过，用户以为订阅成功了。**这类「静默失效」比报错更难发现。**
3. **`share_scope = 'PUBLIC'` 的含义是「全院可见」，但可见的只是条件不是数据。** 别人点开这个常用查询后，仍然走自己的数据权限过滤，看到的还是自己的患者。这就是为什么 `query_params` 里只能存 ID 与枚举——**存了具体患者 ID 的查询一旦共享，等于泄露了「这个科室在关注哪些患者」。**

### 4.7 表：`m20_qry_upstream_health`（上游可用性采样）

```sql

    ADD CONSTRAINT ck_m20_qry_upstream_health_circuit
    CHECK (circuit_state IN ('CLOSED', 'OPEN', 'HALF_OPEN'));

-- 组合语义：成功 + 失败 必须等于请求总数（否则成功率的分母就错了）
ALTER TABLE m20_qry_upstream_health
    ADD CONSTRAINT ck_m20_qry_upstream_health_sum
    CHECK (success_count + fail_count = request_count);

-- 组合语义：超时次数是失败次数的子集
ALTER TABLE m20_qry_upstream_health
    ADD CONSTRAINT ck_m20_qry_upstream_health_timeout_bound
    CHECK (timeout_count <= fail_count);

-- 组合语义：成功率的定义必须与两个计数一致，且零请求时必须为 NULL
-- 这一条直接把「分母为 0 返回 NULL 不返回 0」写进数据库，避免页面把「没调用」
-- 渲染成「成功率 0%」从而误判上游全挂
ALTER TABLE m20_qry_upstream_health
    ADD CONSTRAINT ck_m20_qry_upstream_health_rate
    CHECK ((request_count = 0 AND success_rate IS NULL)
        OR (request_count > 0 AND success_rate IS NOT NULL
            AND success_rate >= 0 AND success_rate <= 1));

-- 组合语义：OPEN 必须有打开时刻；CLOSED 不得残留打开时刻
ALTER TABLE m20_qry_upstream_health
    ADD CONSTRAINT ck_m20_qry_upstream_health_open_combo
    CHECK ((circuit_state = 'CLOSED' AND circuit_open_at IS NULL)
        OR (circuit_state <> 'CLOSED' AND circuit_open_at IS NOT NULL));

-- 连续失败次数只在前缀有失败时才有意义
ALTER TABLE m20_qry_upstream_health
    ADD CONSTRAINT ck_m20_qry_upstream_health_consecutive
    CHECK (consecutive_fail >= 0 AND consecutive_fail <= 100);

-- 违约判定必须与 p95 和 SLA 一致（有 SLA 才能判违约）
ALTER TABLE m20_qry_upstream_health
    ADD CONSTRAINT ck_m20_qry_upstream_health_sla
    CHECK (sla_breached = FALSE
        OR (sla_p95_ms IS NOT NULL AND p95_ms IS NOT NULL AND p95_ms > sla_p95_ms));
```

**设计说明：**

1. **`success_rate` 零请求返 NULL 而非 0，这条约束是刻意的。** 凌晨 3 点某上游一次都没被调用，若写 0%，P06 排障页会显示「M12 报告服务成功率 0%」——运维第一反应是「M12 挂了」，实际是「没人查报告」。**「没数据」和「数据是坏消息」必须在数据库层就分开。**
2. **`ck_m20_qry_upstream_health_sum` 让成功率的分母成为恒等式。** 若允许 `success_count + fail_count ≠ request_count`，成功率的三个数就互不自洽，任何一次对账都会发现「加起来对不上」，而那时已经不知道是哪个环节漏数了。
3. **为什么保留期只给 7 天？** 见 §1.5：这些采样值不承载业务事实。真正的监控数据在 Prometheus（保留 90 天），本表只是 M20 内部的熔断状态机与排障快照。7 天足够覆盖「周末故障、周一排障」的最长间隔。
4. **`sla_p95_ms` 冗余存在本表是有意为之。** SLA 目标来自详细设计 §10.2 对齐表（写在文档里），若不冗余到行上，事后排查时无法知道「当时用的是哪个版本的 SLA 目标」。**这与「留痕表不冗余」的原则不冲突：本表就是留痕表，冗余是它的职责。**

**设计说明：**

1. **为什么阈值定 120KB 而不是 200KB？** 200KB 是**硬上限**，不是目标。留 40% 余量有三个作用：①在逼近上限前就能看到趋势；②给 gzip 后的传输留空间；③让「偶尔超一点」变成可观测事件而不是线上事故。**若直接用 200KB 作阈值，等这条记录出现时已经违规了。**
2. **`ck_m20_qry_response_audit_trigger` 强制「只在超标时写」的原因。** 若允许所有请求都写一行，本表会变成全量访问日志（日 40 万行），既浪费存储又与留痕表的职责重叠。**本表是异常台账，不是访问日志。**
3. **本表为什么不能记响应内容。** 记录内容等于把报告全文抄进日志——这正是共享规范 §17 第 10 条要防的事，只是换了个位置发生。**要验证「没有返回全文」，靠的是 `response_bytes` 这个数字，不是靠把全文存下来对比。**
4. **`truncate_rule` 与 `truncated` 的组合约束防「静默截断」。** 如果响应因为太大被截断却没记下规则名，事后任何排查都无法区分「这条记录本来就没有摘要」和「摘要被截掉了」。**静默截断是移动端最伤信任的错误之一（共享规范 §17 第 24 条同源）。**

### 4.9 表：`m20_qry_sensitive_access`（敏感字段访问登记）

**用途：** 记录每一次「脱敏字段被解封查看」的动作。一条 = 「某人在某时查看了某患者的某个敏感字段的完整值」。它服务于总纲 §8.3「列表页脱敏，看全文另行鉴权并留痕」与共享规范 §5 的取证要求。

   **这条经历值得留在这里：** 一个规则如果只写在文档里、没有任何机器检查它，那它在下一次重构时消失的概率接近 100%，而且消失的时候不会有任何提示。本表原本就写着「只增不删」，但直到它进了 `APPEND_ONLY_TABLES`，这句话才真正有人替它守着。
2. **被拒绝的尝试也要记（`is_allowed = FALSE`）。** 合规检查真正关心的问题之一是「有人在反复尝试看他不该看的东西」。只记成功的访问，等于把最有价值的那部分证据丢掉了。
3. **`ck_m20_qry_sensitive_access_allow_combo` 把「允许 → 二次验证通过」写成硬约束。** 现实中最危险的实现缺陷是：某个 `if` 分支忘了校验 `second_factor_ok` 就返回了明文。此时若表里写 `is_allowed = TRUE` 而 `second_factor_ok = FALSE`，**这条记录本身就是缺陷证据，而约束会让它写不进去，从而在写入失败处暴露**。这与 4.3 的 `sql_perm_applied` 是同一个思路。
4. **`business_reason` 长度 ≥ 2 而不是「非空」。** 用户可能填一个空格或一个「-」敷衍过去。长度 ≥ 2 抬高一点点门槛，让「扫一扫核对身份」这类真实理由更好填、敷衍理由更难填。**这类约束不追求杜绝，只追求让正确做法比错误做法更省事。**
5. **没有 `patient_name` 这类列。** 本表用 `patient_id` + `patient_no_hash` 定位，姓名不落库。判据同 §2.3。

### 4.12 Pydantic Schema 定义

全部 Schema 放在 `app/schemas/m20/qry.py`，统一继承 `M20BaseSchema`。**关键约定：** ①所有 `Decimal` 字段序列化为字符串（`ser_json_decimal_str=True`），避免前端 JSON 解析丢精度；②四个质量标记 `degraded` / `degraded_sources` / `data_quality` / `as_of` **在响应 Schema 里全部无默认值、必填**——共享规范 §8A.2 要求「false 也必须有」，无默认值是让它不可能被忘记；③可空比率用 `Decimal | None`，用 `None` 表达「分母为 0」，**绝不用 0 代替**。

**Schema 分组总览：**

| 分组 | 数量 | 说明 |
|---|---|---|
| 枚举 | 9 | `ClientTypeEnum`/`NetworkStateEnum`/`DataQualityEnum`/`QuerySceneEnum`/`SearchModeEnum`/`SubscribeCycleEnum`/`MessageChannelEnum`/`CircuitStateEnum`/`SensitiveSceneEnum` |
| 基础结构 | 5 | `M20BaseSchema`/`DegradedSourceSchema`/`QualityMixin`/`PageSchema`/`ApiResponse`/`ErrorDetailSchema` |
| 查询入参 | 3 | `SearchQuerySchema`/`SavedQueryCreateSchema`/`SavedQuerySubscribeSchema` |
| 查询出参 | 6 | `SearchItemSchema`/`SearchResultSchema`/`PatientBriefSchema`/`PatientViewSchema`/`KeywordStatSchema` |
| 运维与审计出参 | 3 | `UpstreamHealthSchema`/`ResponseAuditSchema`/`SensitiveAccessSchema` |

**Schema 设计要点：**

1. **`QualityMixin` 把「四质量标记必带」从文档要求变成了运行时断言。** 共享规范 §8A.2 的三条红线（不允许「看起来正常但不完整」的 200、不允许把「没查到」伪装成空数组加 `degraded:false`、不允许 200+空 data 表达无权限）里，前两条都依赖这四个字段的真实性。**`degraded=true` 却没有 `degraded_sources` 时页面没法告诉用户是哪一块不可用；`degraded=false` 却有降级来源时说明判定逻辑本身就错了。**两种情况都直接抛异常而不是放行。
2. **`SearchQuerySchema` 强制「至少一个检索条件」。** 无条件的全表检索在移动端没有任何正当用途，而它的代价是「把全院数据按每页 20 条慢慢倒出来」。**这条校验在入参层就拒掉，比在 SQL 层加 `LIMIT` 更有效。**
3. **`SavedQueryCreateSchema.query_params` 的值长度限制是 64。** 这条看似随意，实际是为 4.5 设计说明第 1 条兜底：即使前端被绕过、用户把「张三」塞进了条件值里，64 字符的限制也能挡住身份证号粘贴、挡住长病历片段。**同时它对正常条件毫无影响**——ID、枚举、日期都远短于 64。
4. **`UpstreamHealthSchema` 把「零请求返 null 不返 0」写成了校验器。** 数据库层有 `ck_m20_qry_upstream_health_rate`，接口层有这条 `model_validator`，两层都挡——因为一旦漏到页面上，运维会把它读成「上游全挂」。
5. **`SensitiveAccessSchema` 的三条组合校验与表的三个 CHECK 一一对应。** 数据库与应用层说同一件事，是这类「合规凭证表」应有的冗余。**唯一区别是应用层能给出人话错误信息，数据库层只能拒绝。**

## 附录 C：关键索引与查询

### C.1 检索留痕的「某人最近查了什么」

```sql
SELECT search_no, search_scene, patient_no_hash, hit_count,
       degraded, data_quality, as_of, created_at
  FROM m20_qry_search_log
 WHERE staff_id = :staff_id
   AND created_at >= :from_ts
 ORDER BY created_at DESC
 LIMIT 50;
```

**查询计划期望：** `Index Scan using idx_m20_qry_search_log_staff_time on m20_qry_search_log_2026_11`，`rows≈50`，`Buffers: shared hit≈8`，耗时 ≤ 2ms。**若出现 `Seq Scan` 且扫描了 `m20_qry_search_log_default`，说明分区预建链路断了**——数据正落进兜底分区，索引虽在但统计信息未收集。

### C.2 敏感字段访问合规检查

```sql
SELECT s.access_no, s.staff_id, s.field_name, s.access_scene,
       s.business_reason, s.is_allowed, s.created_at
  FROM m20_qry_sensitive_access s
 WHERE s.patient_id = :patient_id
   AND s.created_at BETWEEN :from_ts AND :to_ts
 ORDER BY s.created_at DESC;
```

**查询计划期望：** `Index Scan using idx_m20_qry_sensitive_access_patient`，单患者 30 天内通常 < 20 行，耗时 ≤ 3ms。

### C.3 异常行为识别（同一职工短时间内大量解封）

```sql
SELECT staff_id, count(*) AS access_cnt, count(DISTINCT patient_id) AS patient_cnt
  FROM m20_qry_sensitive_access
 WHERE created_at >= now() - INTERVAL '1 hour'
   AND is_allowed = TRUE
 GROUP BY staff_id
HAVING count(DISTINCT patient_id) > 30
 ORDER BY patient_cnt DESC;
```

**判读：** 单职工 1 小时内解封超过 30 个**不同患者**的敏感字段，需要人工核查。注意用「不同患者数」而不是「次数」——批量打印同一患者 50 次是正常业务，快速翻阅 30 个陌生患者才异常。

### C.4 上游 SLA 违约清单

```sql
SELECT upstream_code, count(*) AS breach_cnt, max(p95_ms) AS worst_p95
  FROM m20_qry_upstream_health
 WHERE sample_at >= now() - INTERVAL '24 hours'
   AND sla_breached = TRUE
 GROUP BY upstream_code
 ORDER BY breach_cnt DESC;
```

**查询计划期望：** `Index Scan using idx_m20_qry_upstream_health_breach`（部分索引 `WHERE sla_breached = TRUE`），扫描量仅为违约样本，耗时 ≤ 5ms。

### C.5 DEFAULT 分区巡检（期望 0 行）

```sql
SELECT count(*) AS default_rows FROM m20_qry_search_log_default;
```

**判读：** 非 0 即告警 P2。处理步骤：①立即补建缺失月份的分区（`CREATE TABLE ... PARTITION OF ... FOR VALUES FROM ... TO ...`）；②`DETACH` DEFAULT 分区 → 建一个同名新 DEFAULT 分区（DEFAULT 分区不能直接 `INSERT` 回带界分区，只能 DETACH 后整体重挂）→ `ATTACH` 回去，PostgreSQL 会在挂载时把行路由到正确分区。

**为什么手机号在详情页也不解封？** 因为「查看患者手机号」在移动端的真实用途是打电话，而 M20 的拨号走的是 `tel:` 链接由客户端发起，不需要展示完整号码。**能不给就不给，是脱敏设计的第一原则。**

## 附录 E：建表依赖顺序与 Alembic 迁移

### E.1 建表顺序

本子模块 8 张表**互不依赖**，也与 M20 其他段（段①M20-01 基础表）无依赖。建表顺序按「先配置、后流水」排列，仅为可读性：

| 步骤 | 表 | 说明 |
|---|---|---|
| 1 | `m20_qry_quick_entry` | 配置类，无依赖 |
| 2 | `m20_qry_saved_query` | 配置类，逻辑引用 1 |
| 3 | `m20_qry_patient_view` | 流水类 |
| 4 | `m20_qry_sensitive_access` | 流水类 |
| 5 | `m20_qry_response_audit` | 流水类 |
| 6 | `m20_qry_upstream_health` | 流水类 |
| 7 | `m20_qry_search_keyword` | 统计类（依赖 2 的留痕聚合结果，但无物理依赖） |
| 8 | `m20_qry_search_log` + 分区 + DEFAULT | **最后建**：它最大，分区与索引创建耗时最长，放在事务尾部便于失败回滚 |

### E.2 Alembic 迁移脚本要点

文件名 `alembic/versions/m20_0007_create_m20_qry_tables.py`。

**五条硬要求（汇总 §8.2）：**

1. **每个 `upgrade()` 必须有对应 `downgrade()`**，且 `downgrade()` 顺序与 `upgrade()` 严格相反（先删表、后删索引、最后 `DROP` 类型）。
2. **分区表必须包含 DEFAULT 分区**，且 DEFAULT 分区在建表语句里一次性建好，不要留给运维手工补。
3. **大表建索引使用 `CREATE INDEX CONCURRENTLY`**，`m20_qry_search_log` 的分区索引需要在每个分区上分别建。
4. **`REVOKE` 放在迁移最后**，且 `downgrade()` 里必须 `GRANT` 回来——否则回滚后应用账号永久失去权限，且这个错误在回滚测试中极难发现。
5. **种子数据用 `INSERT ... ON CONFLICT DO NOTHING`**，保证迁移可重复执行。

**迁移号说明：** 汇总 §8.1 规定段⑥（M20-05）使用 `m20_0007`。本子模块的 8 张表与 3 个分区 + 1 个 DEFAULT 分区全部在这一次迁移中建完。

### E.4 上线必跑的三条校验 SQL（汇总 §8.3）

```sql
-- 1) 只增不删表不得有逻辑删除列
SELECT column_name FROM information_schema.columns
 WHERE table_name = 'm20_qry_search_log'
   AND column_name = 'is_deleted';

-- 2) 应用账号不得有 DELETE 权限
SELECT has_table_privilege('app_user', 'm20_qry_search_log', 'DELETE') AS has_delete;

-- 3) DEFAULT 分区必须为空
SELECT count(*) AS default_rows FROM m20_qry_search_log_default;
```

**期望：** 第 1 条 0 行、第 2 条 `has_delete = false`、第 3 条 `default_rows = 0`。**任一条不符即阻断上线**——这三条不是建议检查，是发布流程的硬闸门。
