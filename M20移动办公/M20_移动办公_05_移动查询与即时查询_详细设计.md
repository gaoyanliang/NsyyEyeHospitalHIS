## 1. 模块概述

### 1.1 模块定位

M20-05 是 M20 移动办公的**只读查询子模块**（总纲 §2.3 明确标注「纯读」）。它把用户在手机上「临时问一件事」的动作，翻译成一次**跨模块、受权限约束、且能说清数据截止时刻**的聚合读取。

本子模块回答以下五个问题，且只回答这五个：

| # | 问题 | 回答方式 | 数据权威方 |
|---|---|---|---|
| 1 | 这个人是谁、现在在哪 | 患者聚合视图（基本信息 + 在院 + 床位） | M03-01 / M05-02 |
| 2 | 他有哪些就诊与诊断 | 按条件检索就诊记录 | M07 |
| 3 | 他做过哪些检查、结果出了没有 | 检查任务与报告摘要检索 | M12 |
| 4 | 他有哪些检验、有没有危急值 | 检验任务与结果摘要检索 | M13 |
| 5 | 我的排班与待我处理的随访 | 排班与随访任务检索 | M04-01 / M19-01 |

**本子模块明确不回答的问题（一句话理由）：**

| 不回答 | 为什么不是 M20-05 |
|---|---|
| 完整病历正文怎么读 | 病历阅读是 M18-02 与 M07-04 的职责，M20-05 只提供「检索到并跳到哪一条」，不做病历浏览器 |
| 检查报告 PDF 全文 | 单份 PDF 可能 200KB，移动端列表放不下（共享规范 §17 第 10 条）。M20-05 只给摘要，全文由客户端二次向 M12-03 请求 |
| 我能批这张单吗 | 那是审批（M20-03）与待办（M20-08）的职责 |
| 这个指标是多少 | 指标值权威在 M22，M20-05 只转发移动看板接口 |
| 患者的历史消费与积分 | 视光客户在 M10-08，消费金额在 M16，会员权益在 M03-03 |

### 1.2 为什么独立成子模块

**理由一：移动查询的失败模式与所有其他子模块相反。**

M20 的其他七个子模块（移动医生站、移动护士站、移动审批、移动排班……）失败的后果是「这件事办不成，去 PC 上办」。移动查询失败的后果是**「越权数据出现在列表里」**。前者是效率问题，后者是医疗隐私事故。**风险方向不同，防护手段就不同，放在一起写一定会互相稀释。**

具体地说，本子模块的每一次响应都要同时满足三个互相拉扯的约束：

| 约束 | 具体要求 | 冲突点 |
|---|---|---|
| 完整性 | 该给的数据要给全，且说清哪些没给到 | 与「查得少才安全」冲突 |
| 安全性 | 不该给的数据一个字节都不能给，连「有多少条」都不能透露 | 与「完整性」冲突 |
| 性能 | 首屏 P95 ≤ 2 秒（总纲 §6 M20-CALC-04） | 与「完整性」冲突（多查一个上游就多一份延迟） |

**理由二：它是全院唯一需要「聚合视图」的地方。**

一个患者屏幕要拼 4~6 个上游（M03 基本信息、M05 在院与床位、M07 就诊诊断、M12 检查、M13 检验、M18 病历计数）。总纲 §2.2 的横向依赖 L-3 明确规定「M20-05 / M20-06 / M20-07 的患者聚合视图，同一患者字段集必须一致，否则手机里两个地方显示不同的床位」。**这条一致性要求必须有唯一实现者，否则三个子模块各拼一遍，字段集必然分叉。**

**理由三：它承担全院移动端的「凭什么不给你看」的取证责任。**

《医疗机构病历管理规定》要求可追溯「谁在什么时候查看了谁的病历」。这条责任落在两处：①检索留痕（谁查了）；②敏感字段访问登记（谁看了脱敏背后的完整值）。**这两类事实只有 M20 知道**——PC 端不经过 M20，其他子模块也不记录跨模块检索。删库重建后它们无法恢复，必须由 M20 自己保存。

**理由四：它是唯一同时被四个硬上限约束的子模块。**

| 硬上限 | 数值 | 出处 |
|---|---|---|
| 首屏渲染预算 | 总 P95 ≤ 2 秒，其中服务端聚合 900ms | 总纲 §6 M20-CALC-04 |
| 单次响应体 | ≤ 200KB | 总纲 §8.1 |
| 缓存 TTL | ≤ 60 秒；移动看板 ≤ 120 秒 | 共享规范 §14 与 M22 硬约束 |
| 分页容量 | 默认 20、上限 100 | 共享规范 §2.3 |

**这四个上限里任何一个单独拿出来都不难，但同时满足需要一整套设计：分级加载、摘要截断、并行聚合、预算熔断、部分降级。** 这套设计的正确性只有在一个地方写清楚才能验收。

### 1.3 与相邻子模块的分工

| 相邻方 | 它负责 | M20-05 负责 | 交界判据 |
|---|---|---|---|
| M20-02 移动医生站 | 查房、写病历、开医嘱等**写操作** | 只提供「找得到患者、看得见摘要」的检索能力 | 有没有产生业务事实：产生 → M20-02；没有 → M20-05 |
| M20-03 移动护士站 | 执行医嘱、护理记录等写操作 | 同上 | 同上 |
| M20-06 移动随访 | 随访任务的处理与跟踪 | 提供患者检索与随访任务**只读**列表 | 改状态 → M20-06；只读 → M20-05 |
| M20-07 移动患者门户视图 | 面向患者的自助查询 | 面向职工的跨患者检索 | 查询主体是职工还是患者 |
| M20-08 待办与消息 | 待办聚合、推送、消息 | 不产生待办、不发推送 | 是否需要「提醒某人去做」 |
| M01 主数据 MDM | 患者/职工/科室/药品权威数据 | 只读引用，不落库属性字段 | 谁是权威 |
| M02 统一权限与安全 | 权限判定、数据权限 SQL 片段、字段脱敏、审计 | 调用方，不在本地做任何权限判定 | 谁说了算 |
| M03 患者服务与 EMPI | 患者主索引、患者合并 | 只读 `patient_id`，**不存患者属性** | 谁拥有患者事实 |
| M22 报表与决策支持 | 指标、报表、移动看板 | 转发移动看板接口，不重算指标 | 有没有聚合计算 |

**最容易混淆的一条：M20-05 与 M20-02 的患者聚合视图。** 两者都要拼同一批上游，字段集必须一致（总纲 §2.2 L-3）。**分工是：M20-05 是聚合视图的唯一实现者，M20-02 通过本子模块的接口取用，而不是自己再拼一遍。** 这条约定写在详细设计 §10.1 的「本子模块提供的对外能力」里，也写进验收 AC-28。

### 1.4 概念辨析

#### 1.4.1 「查了一下」与「看了一眼」

本子模块有两张听起来很像的留痕表，它们回答的问题完全不同：

| | `m20_qry_patient_view` | `m20_qry_sensitive_access` |
|---|---|---|
| 一条记录是什么 | 一次**聚合查询**（首屏拉了 patient 360 视图） | 一次**字段解封**（把 `patient.id_card` 的完整值给了前端） |
| 粒度 | 场景级（`query_scene`） | 字段级（`field_name`） |
| 主语 | `staff_id` | `staff_id` |
| 回答的问题 | 「这次聚合快不快、全不全」 | 「谁看了不该随便看的东西」 |
| 日增 | 约 3,000 条 | 约 200 条 |
| 保留 | 1 年 | 5 年 |
| 是否只增不删 | 否（可清理） | **是**（是合规凭证） |

**为什么要分清楚：** 写代码时最容易犯的错是「一次查询顺便把敏感字段也查回来，反正都在一个 SELECT 里」。一旦这么写，`m20_qry_sensitive_access` 就永远不会有记录，而页面上却已经显示了完整身份证号——**取证链条断了，但泄露已经发生**。本子模块强制**敏感字段必须走独立的解封接口**（`API-14`），在物理上把两条路径分开。

#### 1.4.2 「查不到」与「没权限」

这两个词在用户眼里是两件事，在安全判定上是同一件事。

| | 用户看到 | 安全判定 |
|---|---|---|
| 查不到 | 「没有符合条件的记录」 | 数据确实不存在 |
| 没权限 | **「无权限查看该患者」**（明说） | 403 + 非 0 错误码 |
| 权限服务不可用 | **同样的 403** | **fail-closed，一律拒绝** |

**为什么「没权限」要明说而不是假装不存在：** 护士长在手机上找一个患者，如果系统假装「查不到」，她会反复重试、换个条件再试、最后打电话问别人——**一次 403 可能省下五分钟，一次假装查不到浪费三个人十分钟。** 更重要的是，PC 端能查到、手机端查不到，用户会合理地认为「手机有 bug」，而不是「我没有这个权限」。

**但为什么权限服务不可用时必须拒绝而不是放行：** 共享规范 §17 第 5 条与总纲 §5.4 G-2 都写死了——「查不到权限就当作有权限」是移动端安全底线的破口。**两种「查不到」在代码里必须是同一个分支：`if not perm_ok: raise 403`，而不是 `if perm and not perm.ok: raise 403`。**

#### 1.4.3 「列表摘要」与「详情全文」

| | 列表（`API-08`） | 详情（由上游提供） |
|---|---|---|
| 返回内容 | 标题、状态、时间、脱敏姓名、**≤ 200 字符摘要** | 上游的完整内容 |
| 单条体积 | 通常 300~800 字节 | M12 报告 PDF 可达 200KB |
| 20 条一页 | **约 30KB**（本子模块硬上限 200KB 的 15%） | 4MB（手机浏览器直接崩溃） |

**关键设计：列表接口在物理上不返回正文。** 不是「返回了但让前端不显示」，而是**响应体里根本没有那个字段**（`SearchItemSchema` 没有正文字段）。原因：只要接口返回了，抓包就能看到、缓存就会留下、日志就可能记录。**「不返回」是唯一可靠的隐藏方式。**

### 1.5 模块目标

| 编号 | 目标 | 可验证度量 |
|---|---|---|
| G-01 | 首屏聚合在预算内完成 | 服务端聚合 P95 ≤ 900ms，端到端 P95 ≤ 2 秒 |
| G-02 | 任何一次查询的完整性都可解释 | **100% 的响应带四个质量标记**；`degraded=true` 的响应 100% 带 `degraded_sources` |
| G-03 | 越权数据零泄露 | 权限过滤 100% 在 SQL 层完成；应用层过滤零容忍（见 AC-03/AC-04） |
| G-04 | 列表响应体不超标 | 20 条长文本列表响应体 < 200KB（AC-19） |
| G-05 | 检索留痕可取证且不存隐私 | 留痕表无检索词原文、无患者属性列（DA-03 / SC-06） |
| G-06 | 上游降级不影响可用性 | 单个上游不可用时，其余模块照常显示并明示缺口 |
| G-07 | 敏感字段访问全程留痕 | 每次解封一行，含被拒尝试（AC-24） |

### 2.3 与相邻模块的边界

#### 2.3.1 与 M03 患者服务：谁拥有患者属性

M03-01 是患者属性的**唯一权威**。M20-05 的两张留痕表里**只有 `patient_id` 与 `patient_no_hash`，没有任何患者属性列**。每次查询都实时调用 `GET /internal/v1/patient/{id}/brief`（`M03患者服务与EMPI/M03_患者服务与EMPI_01_患者主索引与建档_详细设计.md:516`，API-37，P95 ≤ 50ms，同文件 `:1741`）。

**为什么不加一列缓存 `patient_name` 省一次调用：** 患者可以改名（更正姓名）、可以合并（`mpi.member.merged`）。**M20 一旦缓存了姓名，患者改名后手机端与 PC 端就会显示不同的名字，而用户无法判断哪个对。** 一次 50ms 的调用换掉这个风险，账很清楚。

#### 2.3.2 与 M05 住院：为什么不能缓存床位

总纲 §2.2 L-3 的原话是「同一患者字段集必须一致，否则手机里两个地方显示不同的床位」。但比字段集更严重的是**床位本身不能过夜缓存**：护士在执行医嘱前核对床位，如果手机显示的是昨天的床位，人会走错房间。

M20-05 的床位数据：**只走 30 秒 TTL 的 Redis 缓存**（`m20:qry:patient:{patient_id}`，共享规范 §14 指定），且命中缓存时 `data_quality` 必须标 `CACHED`，页面显示「数据截至 HH:MM:SS」。

#### 2.3.3 与 M22 报表：为什么不能自带一层缓存

M22 的移动看板有数据库级硬约束（`M22报表与决策支持/M22_报表与决策支持_08_财务主题分析与决策看板_数据结构.md:382`）：

```sql
CHECK (dashboard_type <> 'MOBILE' OR cache_ttl_sec <= 120)
```

**M20-05 转发 `GET /internal/v1/m22/dashboard/{dashboard_code}` 时不得在服务端再套一层更长 TTL 的缓存。** 理由不是「不方便」，是**那等于绕过 M22 的约束**：M22 承诺移动看板的数据最多旧 120 秒，M20 若缓存 10 分钟，用户看到的数字就可能是 M22 已经承诺不存在的旧数据，而 M22 对此一无所知。本子模块的参数 `m20.qry.dashboard.ttl_max_sec` 固定写死 120，不允许配置更大。

#### 2.3.4 与 M02 权限：is_mobile_user 的判定已移交

共享规范 V1.4 明确：`is_mobile_user` 的判定移交 M02，M20 侧使用 `mobile.access.mode` 三值 fail-closed。**M20-05 的权限过滤完全不依赖 `is_mobile_user` 字段**，只依赖 M02-04 的 `perm/check` 与 `perm/filter-sql`。

## 3. 业务模型

### 3.1 核心实体关系

本子模块不拥有任何业务实体，只拥有三类「关于查询这件事本身」的事实：

```
   ┌───────────────────┐         ┌─────────────────────┐
   │  一次聚合查询      │────1:1──▶│ m20_qry_patient_view│
   │ （首屏 / 患者 360）│         └─────────────────────┘
   └───────────────────┘
   ┌───────────────────┐         ┌─────────────────────┐
   │  一次条件检索      │────1:1──▶│ m20_qry_search_log  │（只增不删）
   └───────────────────┘         └──────────┬──────────┘
                                            │ 日聚合
                                            ▼
                                 ┌─────────────────────┐
                                 │m20_qry_search_keyword│
                                 └─────────────────────┘
   ┌───────────────────┐         ┌──────────────────────┐
   │  一次敏感字段解封  │────1:1──▶│m20_qry_sensitive_access│（只增不删）
   └───────────────────┘         └──────────────────────┘
```

**三个「一次」是本子模块的全部业务语义。** 没有订单、没有单据流转、没有状态的业务闭环——因为它只读。

### 3.2 状态机

本子模块唯一的「状态」是**上游熔断状态**与**查询结果的质量状态**。

#### 3.2.1 上游熔断状态机

```
                   连续失败 >= 3
      ┌────────┐  ─────────────▶  ┌────────┐
      │ CLOSED │                    │  OPEN  │
      └────────┘  ◀─────────────   └────────┘
          ▲        半开试探成功          │
          │                              │ 冷却 60 秒
          │        ┌───────────┐         │
          └────────│ HALF_OPEN │◀────────┘
                   └───────────┘
                        │
                        └── 试探失败 ──▶ 回到 OPEN
```

| 状态 | 含义 | 本子模块行为 |
|---|---|---|
| `CLOSED` | 正常 | 正常调用该上游 |
| `OPEN` | 熔断打开 | **直接跳过该上游**，不发起调用，记 `degraded_sources` 的 `reason=CIRCUIT_OPEN` |
| `HALF_OPEN` | 半开试探 | 放行一个请求试探，成功回 `CLOSED`，失败回 `OPEN` |

#### 3.2.2 查询结果质量状态

| `data_quality` | 判定条件（总纲 §6 M20-CALC-05） | 页面表现 |
|---|---|---|
| `REALTIME` | 所有上游成功且无缓存命中，或缓存年龄 ≤ 30 秒 | 无提示 |
| `CACHED` | 有数据来自缓存且缓存年龄 > 30 秒 | **顶部黄条「数据截至 HH:MM:SS」** |
| `PARTIAL` | 任一上游失败/熔断/跳过 | **顶部黄条 + 明示哪一块不可用** |
| `UNKNOWN` | 上游没返回 `as_of`，无法判定截止时刻 | **顶部黄条「数据新鲜度未知」** |

**这是本子模块最重要的一张表。** 共享规范 §17 第 24 条把它上升为一条原则：**「没有提示的降级等于欺骗」**。

### 3.3 关键业务流程

#### 3.3.1 患者聚合视图（首屏）流程

1. 客户端带 Token、`X-Device-Id`、`X-Server-Time` 请求 `GET /api/v1/m20/qry/patient/{patient_id}/view`。
2. 网关校验 Token（U-01），注入 `staff_id`。
3. 服务端查 `m20:qry:patient:{patient_id}:{staff_id}` 缓存。命中且年龄 ≤ 30 秒 → 直接返回，`data_quality=REALTIME`。
4. 未命中 → 调 M02 `perm/check` 校验 `m20:qry:patient:view`。失败 → **403**（fail-closed）。
5. 调 M02 `perm/filter-sql` 取该患者是否在本人数据范围内。失败 → **500**（fail-closed）。
6. 并行发起 6 个上游调用（`asyncio.gather`），每个加 300ms 超时，任一上游熔断则跳过：M03 基本信息、M05 在院、M05 床位、M07 就诊、M16 欠费、M18 病历计数。
7. 归并结果：**`as_of = min(所有成功上游 as_of)`**；`degraded = any(上游非成功)`（是「或」不是「与」）。
8. 调 M02 `perm/mask-fields` 对返回字段做脱敏。失败 → **500**，不放行未脱敏数据。
9. 写入 Redis 缓存（TTL 30 秒，值内带 `as_of`）。
10. 异步写 `m20_qry_patient_view` 留痕（不阻塞响应）。
11. 返回响应，带四个质量标记与 `X-Server-Time` 响应头。

#### 3.3.2 条件检索流程

1. 客户端请求 `POST /api/v1/m20/qry/search`（只读，不产生业务事实）。
2. M02 `perm/check` + `perm/filter-sql`，**生成过滤条件**。失败 → 403/500。
3. **把过滤条件以参数化方式 AND 进最外层 WHERE**（§8.1 详述）。
4. 按 `scene` 路由到对应的上游检索接口。
5. 上游返回后，**在 SQL 层已过滤的结果上**做分页，`total` 也来自过滤后的计数。
6. 摘要截断到 200 字符（`SearchItemSchema.abstract`）。
7. 异步写 `m20_qry_search_log`（只记条件字段名，不记值）。
8. 返回。

#### 3.3.3 敏感字段解封流程

1. 客户端请求 `GET /api/v1/m20/qry/patient/{patient_id}/sensitive/{field_name}`，带 `business_reason`。
2. M02 `perm/check` 校验 `m20:qry:sensitive:view`。
3. **二次验证**：调 M02-07 验证 MFA / 短信验证码 / 手势密码。
4. 校验通过 → 返回完整值，**同步写** `m20_qry_sensitive_access`（`is_allowed=true`）。
5. 校验失败 → **403**，**同样写一行**（`is_allowed=false`，带 `deny_reason`）。
6. 无论成败都调 M02-06 `audit/record`。

**第 5 步是本子模块的一个刻意设计：被拒也要留痕。** 因为「有人试图查看但没有权限」本身就是需要被看见的事实——单次被拒是正常业务，一小时内被拒 10 次就值得关注。

### 3.4 计算模型

#### 3.4.1 M20-CALC-04：首屏聚合预算（本子模块的核心计算）

**公式：**

```
total_p95 = network_ms + gateway_ms + aggregate_ms + render_ms + margin_ms

aggregate_ms = max(各上游实际耗时)     ← 并行
             而非 sum(各上游耗时)       ← 串行（错误实现）
```

**预算分配（总纲 §6 给定，不得修改）：**

| 环节 | 预算 | 本子模块可控部分 |
|---|---|---|
| 网络往返 | 400ms | 否 |
| 网关鉴权 | 60ms | 否 |
| **业务数据聚合** | **900ms** | **是** |
| 客户端渲染 | 400ms | 否 |
| 余量 | 240ms | 否 |
| **合计** | **2,000ms** | — |

**900ms 怎么花：**

| 用途 | 预算 | 说明 |
|---|---|---|
| M02 权限检查 + 过滤条件生成 | 15ms | `perm/check` 10ms + `filter-sql` 5ms |
| 并行上游（6 个取 max） | 300ms | 单上游超时 300ms，并行取最大值 |
| 脱敏 `mask-fields` | 5ms | — |
| 组装与序列化 | 20ms | — |
| 缓存写入 | 5ms | 异步，不占关键路径 |
| 余量 | 555ms | 应对抖动 |

**边界与失败条件：**

- 单上游超时 300ms 后**不等待**，该上游记 `degraded`，其余照常返回。
- 聚合总耗时超过 900ms → 记 `m20_qry_patient_view.is_timeout_budget = true`，触发 P2 告警，但**响应仍正常返回**（已拿到的数据不能因为慢而丢掉）。
- 上游数量 6 个是当前值；将来加第 7 个上游时**必须重新核算并行 max**，不能直接串到后面。

**算例一（正常）：**

| 上游 | 耗时 |
|---|---|
| M03 基本信息 | 48ms |
| M05 在院 | 62ms |
| M05 床位 | 41ms |
| M07 就诊 | 88ms |
| M16 欠费 | 55ms |
| M18 病历计数 | 73ms |

并行取 max = **88ms**。总聚合 = 15 + 88 + 5 + 20 = **128ms**。总 P95 = 400 + 60 + 128 + 400 + 余量 = **988ms**，远低于 2 秒。

**算例二（一个上游超时）：**

M18 病历计数超时打满 300ms，其余同上。并行 max = **300ms**。总聚合 = 15 + 300 + 5 + 20 = **340ms**。总耗时 = 400 + 60 + 340 + 400 = **1,200ms**，仍在预算内，但 `degraded = true`，`degraded_sources = [{"source":"M18_EMR","reason":"TIMEOUT"}]`。

**算例三（错误实现：串行）：**

同样的 6 个上游串行执行：48 + 62 + 41 + 88 + 55 + 73 = **367ms**。看起来还行，但这是**单患者、全部健康**的情况。当用户查的是一个住院患者（M05 返回 3 个在院记录）、且 M12/M13 也要拼进来（变成 8 个上游）时，串行耗时约 520ms；再叠加一个上游接近超时（300ms），**串行变成 820ms**，加上其余环节立刻冲破 900ms。

**更严重的是：串行会让「跳过慢上游」失去意义。** 因为串行时下游必须等上游，你即便知道 M18 会超时，也已经等了 300ms 才跳过。**并行才是让「预算熔断」真正有效的唯一方式。**

**为什么这条算例要写进文档：** 总纲 §6 说「串行是 M20 性能问题第一成因」。这句话如果只是口号，实现者会想「6 个上游 300ms 够了」。**必须给出串行会在什么情况下破防的具体数字，才有人相信。**

#### 3.4.2 M20-CALC-05：缓存新鲜度判定

**判定顺序（严格按此顺序，不可调换）：**

```
1. 任一上游失败/熔断/跳过?          → PARTIAL
2. 有数据来自缓存?
     缓存年龄 > 30 秒               → CACHED
     缓存年龄 <= 30 秒              → REALTIME
3. 上游未返回 as_of（无法判定）?    → UNKNOWN
4. 否则                            → REALTIME
```

**`as_of` 的取值规则：** `as_of = min(所有成功返回的上游的 as_of)`。

**算例（总纲 §6 原例）：**

| 上游 | 返回时刻 | `as_of` |
|---|---|---|
| M05 在院 | 10:09:40 | 10:09:40 |
| M18 病历 | 10:09:35 | 10:09:35 |
| M07 就诊 | 10:09:41 | 10:09:41 |
| M12/M13 检查检验 | — | **超时** |

结果：`degraded = true`，`degraded_sources = [{"source":"M12_M13","reason":"TIMEOUT"}]`，`data_quality = PARTIAL`，**`as_of = 10:09:35`**（三个成功上游里最早的那个）。页面显示「数据截至 10:09:35 · 检查检验模块暂时不可用」。

**常见错误一：`as_of` 用 `now()` 填充。** 会让页面显示「刚刚更新」，而实际最新数据是 7 秒前的。**在给药核对与危急值场景，这个 7 秒是实质风险**——护士会以为看到的是最新医嘱。

**常见错误二：`degraded` 用「本地有没有数据」判断。** 共享规范 §17 第 3 条。本子模块的留痕表里永远有数据，若这么写，`degraded` 会恒为 false，所有降级都被掩盖。

**常见错误三：`degraded` 用「与」而不是「或」。** 正确语义是「只要有任一上游非成功就是降级」。用「与」的话，得等所有上游都挂了才提示降级——那时候页面已经全空了。

**常见错误四：`data_quality` 透传上游。** 共享规范 V1.4 §8A.2.1 明确：M20 必须自己重算，上游的值只能进 `degraded_sources[].reason`。原因：上游的 `data_quality` 描述的是**它自己的数据**，不是**这次聚合结果**的。M12 可能返回 `REALTIME`，但整次聚合因为 M13 超时而是 `PARTIAL`。

#### 3.4.3 检索 `total` 的计算与「计数泄露」

**公式：**

```
total = COUNT(*) FROM (过滤条件 AND 数据权限条件) 的结果集
```

**关键约束：`total` 必须在权限过滤之后统计，且必须与 `items` 用同一套 WHERE 条件。**

**算例（为什么这很重要）：**

呼吸内科张医生在手机上搜「肺癌」，系统数据：全院 120,000 份肺癌病历，其中他有权查看的 340 份。

| 实现方式 | `total` 显示 | 泄露了什么 |
|---|---|---|
| 应用层过滤（错误） | **120,000** | 「全院有 12 万份肺癌病历」——一个他不该知道的事实 |
| SQL 层过滤（正确） | **340** | 他有权看的数量，符合预期 |

**一个 120,000 的数字单独看不敏感，但它告诉了一个不该知道的人「这个病的患者规模」。** 更危险的是可以做差分攻击：搜索「肺癌 + 本院区」再搜「肺癌」，两次的差值就是别的院区的肺癌患者数。

**实现要点：** `total` 与 `items` 必须是**同一条 SQL 的两个投影**（一次 `COUNT(*) OVER()` 窗口函数，或两次用完全相同的 WHERE 子句）。**绝不允许**「先查出全量再在应用层过滤然后 `len()`」——那既慢又错。

**`total` 允许为 `null`：** 共享规范 §2.3 明确「`total` 允许为 null，不得为凑 total 扫全表」。当用户快速翻页（`want_total=false`）时，返回 `total=null` + `has_more`，留痕表用 `hit_count = -1` + `is_total_null = TRUE` 表达，**绝不用 0 代替**（用 0 会被读成「没查到」）。

#### 3.4.4 响应体体积控制

**公式：**

```
response_bytes ≈ base_bytes + Σ(item_bytes)
item_bytes ≈ fixed_bytes + len(title) + len(subtitle) + len(abstract) + ...
```

**约束（两道闸门）：**

| 闸门 | 阈值 | 触发行为 |
|---|---|---|
| 审计阈值 | 122,880 字节（120KB） | 写 `m20_qry_response_audit`，不影响返回 |
| 硬上限 | 204,800 字节（200KB） | **必须二次加载**，不允许一次返回 |

**算例（AC-19 的验收集构造）:**

构造 20 条记录，每条：
- `title` 200 字节（满）
- `subtitle` 200 字节（满）
- `abstract` 200 字符 × 3 字节（UTF-8 中文）= 600 字节
- 其余字段约 300 字节

单条 ≈ 1,300 字节。20 条 = 26,000 字节，加上分页与质量标记约 500 字节，**合计约 26.5KB**。

**对比错误实现：** 若列表返回 `conclusion` 全文（M12 报告结论平均 800 字 ≈ 2,400 字节）与 `findings`（平均 1,200 字 ≈ 3,600 字节），单条就 6,000+ 字节，20 条 = **120KB**，接近审计阈值；若含 PDF 摘要字段则轻松破 200KB。

**这就是为什么 `SearchItemSchema` 里根本没有正文字段**——不是截断，是**没有**。

#### 3.4.5 单号生成

**公式：** `{prefix}{yyyyMMdd}{流水号，6 位，左补零}`

| 前缀 | 用途 | 日峰值 | 流水位宽 |
|---|---|---|---|
| `QV` | 患者聚合视图留痕 | 3,000 | 6 |
| `QS` | 检索留痕 | 40,000 | 6 |
| `SQ` | 常用查询 | 50 | 6 |
| `QA` | 响应体积审计 | 200 | 6 |
| `SA` | 敏感访问登记 | 200 | 6 |

**为什么用 Redis `INCR` 而不是数据库序列：** 数据库序列是全局递增的，无法「按日重置」。若用 `序列 % 1000000` 拼日期，跨零点并发时会出现「2026-11-07 的单号里混进了 2026-11-08 的流水」——单号看似唯一，但按日期前缀检索时会漏。

**Redis key：** `m20:qry:code:{prefix}:{yyyyMMdd}`，`INCR` 后若是 1 则 `EXPIREAT` 到次日 00:05。容量估算：5 个前缀各 1 个 key，合计 5 个 key，这个量级不构成容量压力。

### 3.5 单据模型

本子模块**没有业务单据**，只有三类流水号：

| 单号 | 生命周期 | 是否可变 |
|---|---|---|
| `QV` 视图留痕号 | 生成即固定，1 年后清理 | 否 |
| `QS` 检索留痕号 | 生成即固定，3 年后随分区归档 | 否 |
| `SA` 敏感访问登记号 | 生成即固定，5 年保留 | 否 |

**「没有单据」是本子模块的性质，不是遗漏。** 判据（总纲 §1.4）：M20 只拥有「流程事实」与「通道事实」，不拥有「临床事实」与「账务事实」。**查询不产生任何事实，只产生「查询发生过」这个事实本身。**

1. **检索留痕表里没有检索词原文，只有 `keyword_length` 与 `keyword_hash`。** 用户可能在搜索框里输入患者姓名甚至粘贴身份证号。详细理由与反例见数据结构文件 §1.3 与本文 §8.4。

### 6.3 统一响应格式与错误码

**统一响应（共享规范 §2.2）：**

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "trace_id": "7f3a1c2e"
}
```

**分页响应（共享规范 §2.3）：**

```json
{
  "items": [],
  "page_no": 1,
  "page_size": 20,
  "total": 137,
  "has_more": true,
  "as_of": "2026-11-07T10:09:42+08:00"
}
```

**四个质量标记（共享规范 §8A.2，所有 `data` 必带）：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `degraded` | boolean | 是否降级；**false 也必须出现** |
| `degraded_sources` | array | 降级来源；`degraded=false` 时必须是 `[]` |
| `data_quality` | string | `REALTIME`/`CACHED`/`PARTIAL`/`UNKNOWN` |
| `as_of` | string | **数据口径截止时刻，不是请求时刻** |

**HTTP 状态码约定：**

| 状态码 | 使用场景 |
|---|---|
| 200 | 成功，或**带降级标记的成功** |
| 400 | 参数不合法 |
| 403 | **无权限（含权限服务不可用）** |
| 404 | 资源不存在（患者不存在） |
| 429 | 限流 |
| 500 | 服务内部错误（含生成不出权限过滤条件） |
| 503 | 依赖全部不可用且无法返回降级结果 |

**三条红线：**

1. **不允许 HTTP 200 + 非 0 code 表达系统故障**（共享规范 §2.2）。
2. **不允许 200 + 空 data 表达无权限**，一律 403 + 非 0 错误码（共享规范 §8A.3）。
3. **不允许把「没查到」伪装成空数组 + `degraded:false`**；`record_count=0` 且 `degraded:true` 与 `degraded:false` 是两种完全不同的事实。

**幂等约定：** 本子模块绝大多数接口是只读 GET，天然幂等。三个写接口（API-16/17/18、API-24）遵循：

| 接口 | 幂等机制 |
|---|---|
| API-16 新建常用查询 | 请求头 `X-Idempotency-Key`，键 `(M20_QRY_SAVED, key)` 落 `m20_base_idempotency`，TTL 24h |
| API-17 修改 | 天然幂等（全量覆盖语义） |
| API-18 删除 | 天然幂等（逻辑删除，重复删除返回成功） |
| API-24 导出租 | 不产生业务事实；同一 `X-Idempotency-Key` 返回同一导出任务 |

**业务逻辑：**

1. 校验 `patient_id > 0`。不合法 → `"2005001"`。
2. 调 M02 `perm/check` 校验 `m20:qry:patient:view`。**失败或超时 → 403 `"2005011"`（fail-closed）**。
3. 调 M02 `perm/filter-sql` 取数据权限条件。**失败或返回 `has_condition=false` 但 `scope_type` 为 NULL → 500 `"2005012"`（生成不出条件就不查）**。
4. 用过滤条件判定该患者是否在范围内。不在 → 403 `"2005004"`。
5. `force_refresh=false` 时查 `m20:qry:patient:{patient_id}:{staff_id}` 缓存；命中且年龄 ≤ 30 秒 → 组装返回，`data_quality=REALTIME`。
6. 扫描 `m20_qry_upstream_health`，`circuit_state='OPEN'` 的上游直接跳过，记入 `degraded_sources`（`reason=CIRCUIT_OPEN`）。
7. **`asyncio.gather` 并行**发起未被跳过的上游调用，每个超时 300ms，`return_exceptions=True`。
8. 逐个归并：成功 → 计入 `as_of` 候选集；异常/超时 → 记入 `degraded_sources`（`reason=TIMEOUT` 或 `ERROR`）。
9. `as_of = min(成功上游的 as_of)`；全部失败 → `data_quality=UNKNOWN`，`as_of = 请求时刻`（此时页面必须显示「数据新鲜度未知」）。
10. `degraded = (len(degraded_sources) > 0)`（**是「或」不是「与」**）。
11. 按缓存年龄判定 `REALTIME` / `CACHED`（M20-CALC-05）。
12. 调 M02 `mask-fields` 脱敏。**失败 → 500 `"2005013"`，绝不返回未脱敏数据**。
13. 写 Redis 缓存（TTL 30 秒，值内带 `as_of` 与 `degraded` 快照）。
14. 异步写 `m20_qry_patient_view` 留痕。
15. 返回，带 `X-Server-Time` 响应头。

```python
    """M20-05 查询服务。核心原则：权限 fail-closed、上游并行、降级必提示。"""

    def __init__(self, session: AsyncSession) -> None:
        self.session = session
        self.trace_id = ""
        self.perm = PermClient()
        self.patient = PatientClient()
        self.inpatient = InpatientClient()
        self.encounter = EncounterClient()
        self.emr = EmrClient()

    async def _resolve_perm(self, staff_id: int, feature: str) -> dict[str, Any]:
        """权限两件事：功能权限 + 数据权限过滤条件。任一失败都抛异常（fail-closed）。"""
        allowed = await self.perm.check(staff_id=staff_id, permission=feature)
        if not allowed:
            raise PermissionError("2005011")
        cond = await self.perm.filter_sql(staff_id=staff_id, data_domain="DEPT")
        if cond is None:
            raise RuntimeError("2005012")
        return cond

    async def _call_with_budget(self, coro, code: str, results: list,
                                degraded: list[DegradedSourceSchema]) -> Any:
        """单个上游调用：超时/异常都转成降级来源，不向上抛。"""
        try:
            return await asyncio.wait_for(coro, timeout=UPSTREAM_TIMEOUT_SEC)
        except asyncio.TimeoutError:
            degraded.append(DegradedSourceSchema(source=code, reason="TIMEOUT"))
            return None
        except Exception:
            degraded.append(DegradedSourceSchema(source=code, reason="ERROR"))
            return None

    async def get_patient_view(
        self,
        staff=None,
        staff_id: int | None = None,
        patient_id: int = 0,
        scenes: list[str] | None = None,
        force_refresh: bool = False,
        device_id: str | None = None,
        server_time_hint: str | None = None,
        require_feature_perm: bool = True,
    ) -> PatientViewSchema:
        sid = staff_id if staff_id is not None else int(staff.staff_id)
        self.trace_id = _new_trace_id()
        started = _now_ms()

        cond = await self._resolve_perm(sid, "m20:qry:patient:view")

        degraded: list[DegradedSourceSchema] = []
        as_of_candidates: list[datetime] = []

        tasks = {
            "M03_PATIENT": self.patient.brief(patient_id),
            "M05_ADMISSION": self.inpatient.active_admission(patient_id),
            "M07_ENCOUNTER": self.encounter.recent(patient_id, limit=5),
            "M18_EMR": self.emr.record_count(patient_id),
        }
        wanted = set(scenes) if scenes else set(tasks.keys())
        gathered = await asyncio.gather(*[
            self._call_with_budget(coro, code, [], degraded)
            for code, coro in tasks.items() if code in wanted
        ], return_exceptions=False)

        result = dict(zip([c for c in tasks if c in wanted], gathered))

        patient_obj = None
        raw_patient = result.get("M03_PATIENT")
        if raw_patient:
            masked = await self.perm.mask_fields(staff_id=sid, data=raw_patient)
            if masked is None:
                raise RuntimeError("2005013")
            patient_obj = PatientBriefSchema(**masked)
            as_of_candidates.append(raw_patient.get("as_of"))

        as_of = min([x for x in as_of_candidates if x is not None],
                    default=_now())
        quality = self._resolve_quality(
            degraded=degraded,
            all_failed=not result.get("M03_PATIENT") and len(degraded) == len(wanted),
            cache_age_sec=None,
        )

        elapsed = _now_ms() - started
        await self._write_patient_view_log(
            staff_id=sid, patient_id=patient_id, scene="PATIENT_360",
            degraded=bool(degraded), quality=quality, as_of=as_of,
            elapsed_ms=elapsed, device_id=device_id,
            degraded_sources=degraded,
        )

        return PatientViewSchema(
            patient=patient_obj,
            admission=result.get("M05_ADMISSION"),
            beds=[],
            encounters=result.get("M07_ENCOUNTER") or [],
            charge_summary=None,
            report_summary=None,
            lab_summary=None,
            degraded=bool(degraded),
            degraded_sources=degraded,
            data_quality=quality,
            as_of=as_of,
            record_count=1,
        )

    def _resolve_quality(self, degraded: list, all_failed: bool,
                         cache_age_sec: float | None) -> str:
        """M20-CALC-05 的实现。顺序不可调换。"""
        if degraded:
            return "PARTIAL"
        if cache_age_sec is not None:
            return "CACHED" if cache_age_sec > CACHE_HIT_REALTIME_SEC else "REALTIME"
        if all_failed:
            return "UNKNOWN"
        return "REALTIME"

    async def search(self, staff, query: SearchQuerySchema,
                     device_id: str | None = None) -> SearchResultSchema:
        sid = int(staff.staff_id)
        self.trace_id = _new_trace_id()
        cond = await self._resolve_perm(sid, "m20:qry:search:view")

        rows, total = await self._search_by_scene(
            staff_id=sid, query=query, perm_cond=cond
        )

        items = [
            SearchItemSchema(
                biz_type=r["biz_type"],
                biz_no=r["biz_no"],
                title=r["title"][:120],
                subtitle=(r.get("subtitle") or "")[:120] or None,
                status=r.get("status"),
                abstract=_truncate(r.get("abstract"), ABSTRACT_MAX_CHARS),
                occurred_at=r.get("occurred_at"),
                patient_id=r.get("patient_id"),
                patient_name_masked=r.get("patient_name_masked"),
                has_detail=bool(r.get("has_detail")),
                source_module=r["source_module"],
            )
            for r in rows
        ]

        await self._write_search_log(
            staff_id=sid, scene=query.scene.value, mode=query.mode.value,
            keyword=query.keyword, patient_id=query.patient_id,
            hit_count=total, condition_fields=_condition_fields(query),
            is_total_null=not query.want_total, device_id=device_id,
        )

        return SearchResultSchema(
            items=items,
            page=PageSchema(
                page_no=query.page_no,
                page_size=query.page_size,
                total=total,
                has_more=len(items) == query.page_size,
            ),
            degraded=False,
            degraded_sources=[],
            data_quality="REALTIME",
            as_of=_now(),
            record_count=len(items),
        )

    async def _search_by_scene(self, staff_id: int, query: SearchQuerySchema,
                               perm_cond: dict[str, Any]) -> tuple[list, int | None]:
        """检索核心：权限条件必须在 SQL 层参数化 AND 进最外层 WHERE。

        绝不允许先查全部再在 Python 里过滤：那样 total 会是全量数，
        而「全院有 120,000 份这个病的病历」本身就是一次泄露。
        """
        params: dict[str, Any] = {}
        where = []
        if perm_cond.get("has_condition"):
            where.append("(" + perm_cond["sql_condition"] + ")")
            params.update(perm_cond.get("params") or {})
        if query.patient_id:
            where.append("patient_id = :patient_id")
            params["patient_id"] = query.patient_id
        if query.dept_id:
            where.append("dept_id = :dept_id")
            params["dept_id"] = query.dept_id
        if query.date_from:
            where.append("created_at >= :date_from")
            params["date_from"] = query.date_from
        if query.date_to:
            where.append("created_at < :date_to_exclusive")
            params["date_to_exclusive"] = query.date_to + timedelta(days=1)

        if not where:
            raise ValueError("2005005")

        sql = text(
            "SELECT * FROM (" + self._scene_sql(query.scene.value) + ") t "
            "WHERE " + " AND ".join(where) + " "
            "ORDER BY occurred_at DESC "
            "LIMIT :limit OFFSET :offset"
        )
        params["limit"] = query.page_size
        params["offset"] = (query.page_no - 1) * query.page_size
        res = await self.session.execute(sql, params)
        rows = [dict(r._mapping) for r in res]

        total: int | None = None
        if query.want_total:
            count_sql = text(
                "SELECT count(*) FROM (" + self._scene_sql(query.scene.value) + ") t "
                "WHERE " + " AND ".join(where)
            )
            count_params = {k: v for k, v in params.items()
                            if k not in ("limit", "offset")}
            total = int((await self.session.execute(count_sql, count_params)).scalar() or 0)
        return rows, total

    def _scene_sql(self, scene: str) -> str:
        mapping = {
            "PATIENT": "SELECT * FROM v_m20_qry_patient_search",
            "REPORT": "SELECT * FROM v_m20_qry_report_search",
            "LAB": "SELECT * FROM v_m20_qry_lab_search",
            "INPATIENT": "SELECT * FROM v_m20_qry_inpatient_search",
        }
        return mapping.get(scene, "SELECT * FROM v_m20_qry_global_search")

    async def _write_search_log(self, staff_id: int, scene: str, mode: str,
                                keyword: str | None, patient_id: int | None,
                                hit_count: int | None, condition_fields: str,
                                is_total_null: bool,
                                device_id: str | None) -> None:
        """检索留痕：不保存检索词原文，只保存长度与哈希。"""
        kw_len = len(keyword) if keyword else 0
        kw_class = _classify_keyword(keyword)
        kw_hash = None
        if keyword and kw_class != "NUMBER":
            kw_hash = _sha16(keyword)

        log = QrySearchLog(
            search_no=_next_no("QS"),
            trace_id=self.trace_id,
            staff_id=staff_id,
            search_scene=scene,
            search_mode=mode,
            keyword_length=kw_len,
            keyword_hash=kw_hash,
            keyword_class=kw_class,
            condition_fields=condition_fields,
            hit_count=-1 if is_total_null else int(hit_count or 0),
            is_zero_hit=(hit_count == 0),
            is_total_null=is_total_null,
            data_quality="REALTIME",
            as_of=_now(),
            sql_perm_applied=True,
            patient_id=patient_id,
        )
        self.session.add(log)


def _classify_keyword(keyword: str | None) -> str:
    if not keyword:
        return "OTHER"
    if keyword.isdigit():
        return "NUMBER"
    if _is_dict_word(keyword):
        return "DICT_WORD"
    if keyword.isalnum() and keyword.upper() == keyword:
        return "CODE"
    return "OTHER"


def _truncate(text_value: str | None, limit: int) -> str | None:
    if not text_value:
        return None
    return text_value[:limit]
```

| `"209001"` | 403 | 无 M20 移动办公访问权限 | 网关层移动端准入未通过（职工未被授予移动端使用资格） | 联系管理员开通移动办公权限 |

**错误码使用规则：**

1. **本表是唯一权威。** 正文其他地方引用错误码时，含义必须与本表逐字一致，或只写错误码不写含义。
2. **权限类错误一律 403，系统类一律 500，可降级类一律 200。** 三者的分界线是「谁的责任」：用户无权限是 403，服务端拿不到过滤条件是 500，某个上游不可用但整体仍可用是 200。
3. **`"2005011"` 同时覆盖「无权限」与「权限服务不可用」。** 这是刻意的：共享规范 §17 第 5 条要求「查不到权限就当作没权限」，两种情况的用户动作完全相同（联系管理员），合并为一个码可以避免调用方写出「服务不可用就放行」的分支。
4. **`"2005014"` 至 `"2005020"` 中标注 200 的错误码返回 200 而非 5xx。** 这是共享规范 §8A 的降级形态要求：带质量标记的成功响应，页面据此显示部分内容与明示缺口，而不是整页报错。
5. **错误码不得复用。** 若某码的语义需要改变，新增一个码，并在本表把旧码标注「已废弃，不再返回」。

### 6.8 推荐词的 SQL 层姓名风险过滤

`_hot_keywords()` 是热门词与检索建议的唯一取数入口，**A 档姓名风险词必须在这里被排除**。这条过滤写在 SQL 里，不写在这里之外。

```python
class QryService:
    """查询服务（6.5 节的服务类，此处只补推荐词取数方法）。"""

    async def _hot_keywords(
        self,
        session: AsyncSession,
        stat_date: date,
        limit: int = 10,
    ) -> list[KeywordStatSchema]:
        """取某日热门检索词（供检索建议与 P04 榜单）。

        name_risk_class <> 'A' 是本方法的立身之本，不要挪到应用层：
        应用层过滤的失败模式是「某处忘了过滤，结果全出」，
        而 SQL 层过滤的失败模式是「条件写不成 → 查不到 → 不显示」。
        推荐列表宁可不弹，也不能弹错。
        """
        stmt = (
            select(QrySearchKeyword)
            .where(
                QrySearchKeyword.stat_date == stat_date,
                QrySearchKeyword.word_text.is_not(None),
                # 姓名风险 A 档：可能是自然人姓名 → 不进推荐，但仍可被检索命中
                QrySearchKeyword.name_risk_class != "A",
            )
            .order_by(QrySearchKeyword.search_count.desc())
            .limit(limit)
        )
        rows = (await session.scalars(stmt)).all()
        return [KeywordStatSchema.model_validate(r) for r in rows]
```

**三处防线，缺一不可：**

| 层 | 位置 | 拦截方式 | 若缺失的后果 |
|---|---|---|---|
| 索引层 | `idx_m20_qry_search_keyword_top` 的 `WHERE` 子句 | 索引里根本不收录 A 档词 | A 档词混进索引，查询层拿得到 |
| SQL 层 | `_hot_keywords()` 的 `.where(name_risk_class != "A")` | 条件写死在查询构造里 | 某处漏过滤就全出 |
| Schema 层 | `KeywordStatSchema._reject_name_risk_a` | 序列化时拒绝 A 档 | SQL 被改坏时仍然会把词带给前端 |

**为什么三道都要：** 索引层防的是性能退化后的顺手改写（有人为了走索引把 `WHERE` 简化掉）；SQL 层防的是新人写新查询时漏条件；Schema 层防的是前两层都被改动之后还剩最后一道。**一道防线叫「纪律」，三道防线才叫「设计」。**

**检索路径不走这个方法。** A 档是「不推荐」，不是「不可用」——完整词条检索走的是 `search()`，那里的匹配逻辑里**没有也不能有** `name_risk_class` 条件。SC-13 专门验收这一点：推荐列表里查不到「安宁」，但用「安宁」检索仍能命中。

## 7. 缓存与异步任务设计

### 7.1 缓存清单

| Key | 类型 | TTL | 内容 | 失效时机 | 容量估算 |
|---|---|---|---|---|---|
| `m20:qry:patient:{patient_id}:{staff_id}` | String(JSON) | **30s** | 患者聚合视图（含 `as_of`、`degraded`、质量标记） | TTL 自然过期；数据变更事件不主动失效（30 秒太短，主动失效得不偿失） | 峰值 300 在线 × 平均 3 患者 = 900 个 key，每个约 3KB → **约 2.7MB** |
| `m20:qry:code:{prefix}:{yyyyMMdd}` | String(int) | 到次日 00:05 | 单号流水 | 定时过期 | 5 个 key/天 |
| `m20:qry:dict:keyword` | Set | 永久（随发布刷新） | 检索词白名单（约 3,980 条） | 数据字典变更时刷新 | 约 400KB |
| `m20:qry:upstream:{code}:state` | String | **60s** | 熔断状态机快照 | TTL 到期重算 | 约 20 个 key，可忽略 |
| `m20:qry:dashboard:{code}` | **不使用** | — | — | — | **刻意不使用，见 §7.1.1** |

**总量估算：** 约 **3.2MB**，Redis 单实例足够。

**共享规范 §14 的三条硬规则，本子模块全部遵守：**

1. **所有缓存 TTL ≤ 60 秒**（患者视图 30 秒、熔断状态 60 秒）。
2. **缓存值必须带 `as_of`**，命中缓存时 `data_quality` 必须为 `CACHED`——本子模块的缓存值 JSON 里显式存 `as_of` 与 `cached_at`，命中时用 `now - cached_at` 算缓存年龄。
3. **不得在 Redis 存凭据、Token、患者身份证明文**——本子模块的缓存值里没有任何明文身份字段，姓名与证件号都是脱敏后的（缓存的是**脱敏后**的结果）。

#### 7.1.1 为什么移动看板不做本地缓存

M22 的移动看板有数据库级硬约束（`M22报表与决策支持/M22_报表与决策支持_08_财务主题分析与决策看板_数据结构.md:382`）：

```sql
CHECK (dashboard_type <> 'MOBILE' OR cache_ttl_sec <= 120)
```

**M20-05 若在自己的 Redis 里缓存看板数据，无论 TTL 设多少，都等于把 M22 承诺的「最多旧 120 秒」变成了「最多旧 M20 的 TTL 秒」。** 如果 M20 缓存 5 分钟，用户看到的数字就可能是 M22 已经承诺不存在的旧值，而 M22 对 M20 的这一层一无所知——**排障时会发现「M22 的数据是对的，用户在手机上看到的是错的」，但没有任何日志能说明是谁缓存的。**

正确做法：API-22 每次转发 M22，把 M22 自己的 `data_quality` 与 `as_of` 转成 M20 的四个质量标记。参数 `m20.qry.dashboard.ttl_max_sec = 120` 固定，不允许配置更大，**留它的意义是让这个上限在配置文件里有痕迹**。

### 7.2 异步任务清单

| 任务名 | 触发 | 频率 | 超时 | 失败处理 |
|---|---|---|---|---|
| `m20.qry.persist_search_log` | 检索接口异步投递 | 每请求一次 | 5s | 重试 3 次后写本地补偿表，进入死信队列 |

**为什么留痕写入是异步的：** 检索响应必须在 2 秒内返回，留痕写入是纯追加，放到异步队列可以把响应时间减少 3~8ms。**但异步意味着可能丢**——所以任务失败后写本地补偿表 + 死信队列，由 `m20.qry.cleanup_expired` 每日扫一遍补偿表重投。

**为什么敏感访问登记是同步的：** 它是合规凭证，**丢一条就是丢一条取证记录**。宁可让 API-14 慢 5ms，也不能异步。

## 8. 业务规则与校验

### 8.1 权限过滤必须在 SQL 层参数化

这是本子模块**最重要的一条规则**，单独成节。

**规则：** 所有检索类接口的数据权限过滤，必须把 M02-04 `perm/filter-sql` 返回的 `sql_condition` 与 `params` **以参数化方式 AND 进最外层 WHERE**，不得在应用层遍历结果集做过滤。

**理由一：两种失败模式的错误方向不同。**

| 实现方式 | 典型 bug | 失败表现 |
|---|---|---|
| 应用层过滤 | 某个分支忘了加过滤 | **结果全出**（越权数据出现在列表里） |
| SQL 层参数化 | 生成条件时抛异常 | **500，什么都没出** |

**后者的错误方向是安全的。** 一次 500 用户会重试、会报告，运维当天就能发现；一次越权泄露没人会报告，等发现时已经来不及。

**理由二：应用层过滤时 `total` 是全量数（§3.4.3 已详述）。**

呼吸内科医生搜「肺癌」，应用层实现下 `total = 120,000`，SQL 层实现下 `total = 340`。**「120,000」这个数字本身就是一个泄露**，而且可以被差分攻击（搜「肺癌 + 本院区」与「肺癌」做差）。

**理由三：应用层过滤无法保证分页正确。** 每页取 20 条再过滤，可能过滤后只剩 3 条，用户翻页时会看到「时多时少」，且 `has_more` 完全不可信。

**实现要求：**

1. `perm/filter-sql` 返回 `has_condition=false`（全院范围）时，**不能跳过条件**——`has_condition=false` 是「该角色无数据范围限制」，与「权限服务没返回结果」是两件事。后者必须抛异常。
2. `sql_condition` 里出现的参数名必须以 `:perm_` 前缀，避免与业务参数重名。
3. **不允许把 `sql_condition` 直接字符串拼进 SQL**——必须用 `text()` + 独立 `params`，由驱动做参数化。
4. 这条规则有对应的验收项 AC-03 / AC-04，其中 AC-04 用「让权限服务超时」的方式验证不会退化成不过滤。

### 8.2 业务规则

| 编号 | 规则 | 违反后果 |
|---|---|---|
| R-01 | 权限过滤在 SQL 层参数化，禁止应用层过滤 | 越权泄露 / 计数泄露 |

| 编号 | 恒等式 | 校验方式 |
|---|---|---|
| E-01 | `degraded = (len(degraded_sources) > 0)` | Pydantic `QualityMixin` + 留痕表 CHECK |
| E-02 | `as_of = min(所有成功上游的 as_of)` | 单元测试固定 4 个上游的 as_of，断言取最小值 |
| E-03 | `as_of <= created_at + 120 秒` | 数据库 CHECK `ck_m20_qry_patient_view_as_of` |
| E-04 | `record_count = len(items)` | 响应组装处断言 |
| E-05 | `hit_count = -1 ⇔ is_total_null = TRUE` | 数据库 CHECK `ck_m20_qry_search_log_total_combo` |
| E-06 | `is_zero_hit = TRUE ⇒ hit_count = 0` | 数据库 CHECK `ck_m20_qry_search_log_zero_combo` |
| E-07 | `sql_perm_applied = TRUE`（恒真） | 数据库 CHECK `ck_m20_qry_search_log_perm_applied` |
| E-08 | `success_count + fail_count = request_count` | 数据库 CHECK `ck_m20_qry_upstream_health_sum` |
| E-09 | `request_count = 0 ⇒ success_rate IS NULL` | 数据库 CHECK `ck_m20_qry_upstream_health_rate` |
| E-10 | `word_text IS NOT NULL ⇒ word_class = 'DICT_WORD'` | 数据库 CHECK `ck_m20_qry_search_keyword_text_combo` |
| E-11 | `is_allowed = TRUE ⇒ second_factor_ok = TRUE` | 数据库 CHECK `ck_m20_qry_sensitive_access_allow_combo` |
| E-12 | 一次聚合查询恰好写 1 行 `m20_qry_patient_view` | 对账任务抽样校验 |
| E-13 | 一次敏感解封恰好写 1 行 `m20_qry_sensitive_access` | 对账任务抽样校验 |

**E-07 的解释（一个刻意的自我证伪设计）：** `sql_perm_applied` 是一个恒为 TRUE 的列。它的价值不在于值本身，而在于**如果有人把权限过滤改成应用层实现，这一列会被写成 FALSE，而 CHECK 约束会立刻拒绝这条留痕**。换句话说，这个约束把「R-01 是否被遵守」变成了「留痕表能不能写进数据」——**违规实现会立刻表现为「检索功能报错」，而不是「悄无声息地泄露」。**

#### 10.2.1 M12 / M13 待核实项的核实结论

共享规范 §9.14 的待核实清单里 M12 与 M13 两条由本子模块核实。**结论如下，附带行号。**

**M12 检查报告：**

- **「按患者直接列报告」的内部接口不存在。** M12 有 `GET /internal/v1/m12/review/{id}`（`M12检查管理/M12_检查管理_05_报告审核与发布_详细设计.md:1381`，API-33），但**键是审核记录 ID 而不是 `patient_id`**。M12-05 的 6.4 节（`:1453-1605`）只详述了 API-01/05/10/22 四条，**API-33 没有请求响应样例**。
- **可用的替代路径是两跳**：①`GET /internal/v1/m12/tasks/by-patient/{patient_id}`（`M12检查管理/M12_检查管理_01_检查申请与预约排程_详细设计.md:1046`，API-31 / P-03）拿任务列表；②对每个任务调 `GET /internal/v1/m12/review/{id}` 拿报告。
- **一个旁证：** M12-05 的数据表 `m12_report_review` 有索引 `idx_m12_review_patient` = `(patient_id, created_at DESC)`（`M12检查管理/M12_检查管理_05_报告审核与发布_数据结构.md:154` 起的字段表所在文件中定义），**说明 M12 内部确实按 `patient_id` 建了索引，只是没把列表接口暴露出来**。这说明缺口是「接口未定义」而非「能力不存在」，建议 M12-05 补一条 `GET /internal/v1/m12/review/by-patient/{patient_id}`。
- **本子模块的处置：** 走两跳，且只对当前页的任务取报告（一页最多 50 次调用，并行）。**不因为接口缺失就假装它存在。**

**M13 检验结果：**

- `GET /internal/v1/m13/lab/tasks/by-patient/{patient_id}` 存在（`M13检验管理/M13_检验管理_01_检验申请与标本管理_详细设计.md:4349`，P-04）。
- **M13 比 M12 多一条便利通道**：`GET /internal/v1/m13/review/by-task/{task_id}`（`M13检验管理/M13_检验管理_04_检验结果审核与发布_详细设计.md:3119` 区块，P-04 见 `:3122`），**可按 task 直达报告，一跳完成**。
- **注意编号冲突：** M13 模块总纲 `M13检验管理/M13_检验管理_详细设计.md:744-755` 的 P-01~P-12 是另一套编号，其 P-04 是 `specimens/by-task/{task_no}`。**引用 M13 的 P 编号时必须写清来源文件行号，不能只写「P-04」。**

**M09 手术排班（任务书附带的待核实项）：**

- **M09 没有「按患者列手术排班」的内部接口。** M09 有 `reception/by-schedule/{schedule_id}`（`M09手术麻醉管理/M09_手术麻醉管理_01_手术室接收与麻醉前评估_详细设计.md:938`，API-31 / P-02）、`anesthesia/by-patient/{patient_id}`（`M09_手术麻醉管理_02_麻醉记录与用药_详细设计.md:3038`，P-05，**查的是历史麻醉记录不是排班**）。
- **排班的权威在 M11-05 与 M06-03**：最优选 `GET /internal/v1/m11/reservations/by-patient/{patient_id}`（`M11屈光手术管理/M11_屈光手术管理_05_手术预约与术前准备_详细设计.md:1593`，API-34 / §10.2 `:5552` P-08，**调用方已登记 M06、M09、M07**，P95 ≤ 120ms）。
- **本子模块的处置：** 按患者查手术安排走 M11-05 的 P-08，不走 M09。

### 10.3 发布事件

| 事件名 | 触发时机 | 载荷 | 订阅方 |
|---|---|---|---|
| `m20.qry.sensitive_accessed` | 敏感字段解封成功或被拒 | `access_no`、`staff_id`、`patient_id`、`field_name`、`is_allowed`、`access_scene`、`accessed_at` | M02-06 审计、M22-06 |

**载荷红线（共享规范 §10）：事件载荷不得包含患者姓名、手机号、身份证明文，只允许 ID、编码、状态、时间。** 上表载荷全部是 ID、编码、布尔与时间，无一例外。

**特别注意：`patient_id` 是标识符不是身份信息，允许出现在载荷里；但患者姓名、手机号码、身份证明文字段一律不得出现——连字段名都不该出现在载荷契约里，因为字段名一旦进了契约，下一个开发者就会往里填值。** 这条约束的做法是「载荷里根本不定义这些字段」，而不是「定义了但填 null」。

### 10.4 订阅事件

| 事件名 | 来源 | 本子模块处理 |
|---|---|---|
| `mpi.patient.merged` | M03 | **患者合并后，历史留痕里的 `patient_id` 不重写**（留痕是「当时查的是谁」的事实，重写会篡改取证记录）；但**「最近查过」的展示会做一次重定向**（合并后被合并 ID 的查询记录归到主 ID 下展示） |

**关于 `mpi.patient.merged` 的两句话是本子模块的一条重要取舍：**

- **留痕表不重写 `patient_id`。** 理由：留痕的法律含义是「2026-11-07 10:09 张医生查询了患者 10021」。如果患者 10021 后来被合并进 10088，**当时的查询对象仍然是 10021**。重写等于伪造历史。审计时用「10021 在 2026-11-05 被合并到 10088」这条 M03 的合并记录做串联即可。
- **展示层做重定向。** 「最近查过」是便利功能不是取证功能，合并后如果还显示旧 ID，点进去会 404。所以展示层用 M03 的合并映射做一次重定向。

### 11.2 日志规范

**日志格式（JSON 单行）：**

```json
{
  "ts": "2026-11-07T10:09:42.118+08:00",
  "level": "INFO",
  "logger": "m20.qry.service",
  "trace_id": "7f3a1c2e",
  "staff_id": 1024,
  "patient_id": 10021,
  "query_scene": "PATIENT_360",
  "elapsed_ms": "128.500",
  "upstream_max_ms": "88.000",
  "degraded": false,
  "degraded_count": 0,
  "data_quality": "REALTIME",
  "as_of": "2026-11-07T10:09:35+08:00",
  "msg": "patient_view_ok"
}
```

**日志红线：**

| 不得记录 | 理由 |
|---|---|
| 检索词原文（`keyword`） | 用户可能输入患者姓名、身份证号 |
| 患者姓名、手机号、证件号 | 日志会被长期保留且访问控制弱于业务库 |
| 报告正文、检验结果明细 | 临床内容，日志不是病历库 |
| 完整敏感字段值 | 同上 |
| Token / 二次验证凭证 | 凭据 |

**允许记录：** `keyword_length`、`keyword_class`、`condition_fields`（**字段名**集合）、`patient_id`、`staff_id`、耗时、降级来源、质量标记。

**日志级别：**

| 级别 | 使用场景 |
|---|---|
| `DEBUG` | 逐上游耗时明细（仅测试环境） |
| `INFO` | 每次成功查询的摘要（上述 JSON） |
| `WARN` | 降级、上游熔断打开、预算超支 |
| `ERROR` | 500 类异常、权限服务不可用、脱敏失败 |
| `CRITICAL` | 全部上游不可用、DEFAULT 分区有数据 |

### 11.3 监控指标

| 指标名 | 类型 | 说明 | 告警阈值 |
|---|---|---|---|
| `m20_qry_request_duration_ms` | Histogram | 接口总耗时，按 `api_code` 分 | P95 > 2000ms 持续 5 分钟 → P2 |

**四条必须存在的告警（对应本子模块的四条铁律）：**

1. `m20_qry_perm_service_error_total > 0` → **P1**：权限服务故障意味着所有查询都在 403，且此时**绝不能有任何放行**。
2. `m20_qry_response_bytes` 出现 > 200KB → **P2**：说明有接口违反了列表不返回全文的规则。
3. `m20_qry_default_partition_rows > 0` → **P2**：分区预建链路断了，再不修下一个月的留痕会全落 DEFAULT。
4. `m20_qry_sensitive_denied_total` 单职工 1 小时 > 10 → **P2**：有人在试探敏感字段权限。

| SC-10 | 响应体上限不可绕过 | 构造含最长可能字段的 50 条列表；**响应体 ≤ 200KB，超出部分截断并在 `m20_qry_response_audit` 留痕** |
| SC-11 | 被拒访问可追溯 | 制造 10 次敏感解封被拒；查 API-13；**10 条 `is_allowed=false` 记录全部可见，含 `deny_reason`** |
| SC-12 | 留痕不可篡改 | 用 `app_user` 尝试 UPDATE/DELETE `m20_qry_search_log`；**权限被拒**；审计日志有尝试记录 |
| SC-13 | **A 档姓名风险词条永不出现在推荐结果** | 词表里植入一条 A 档词条（如「安宁」，`name_risk_class='A'`）；调推荐接口（API-25 的热门词）与检索建议接口，输入该词条前 2 个字符；**该词条在返回的候选列表中出现次数为 0**；再用完整词条「安宁」调检索接口，**仍能命中该词条对应的业务数据**（证明它是「不推荐」而不是「不可用」） |
| SC-14 | **推荐查询在 SQL 层排除 A 档** | 把 `_hot_keywords()` 的 `WHERE name_risk_class <> 'A'` 注释掉；跑 SC-13 用例；**必须测试失败**（说明该条件是真在起作用，而不是碰巧没数据）；恢复后测试通过 |
| SC-15 | **导入漏标姓名风险档必须失败** | 直接 `INSERT INTO m20_qry_search_keyword (..., word_class, ...) VALUES (..., 'DICT_WORD', ...)` 不带 `name_risk_class`；**INSERT 报错**（`ck_m20_qry_search_keyword_name_risk` 或 NOT NULL 相关约束），而非静默落进默认档 |

## 附录 E：关键决策记录

| 编号 | 决策 | 备选方案 | 选择理由 | 代价 |
|---|---|---|---|---|
| D-01 | **权限过滤在 SQL 层参数化** | 应用层 Python 过滤 | 应用层失败模式是「结果全出」，SQL 层是「抛异常→500→什么都没出」，后者错误方向安全；且应用层下 `total` 是全量数（泄露） | 需要依赖 M02 `filter-sql`，多一次 5ms 调用 |
| D-02 | **列表不返回报告正文** | 返回全文由前端截断 | 「不返回」是唯一可靠的隐藏方式；抓包、缓存、日志都不会留下正文 | 用户点详情需二次请求 |
| D-03 | **检索留痕不存检索词原文** | 存原文便于分析 | 用户会输入姓名甚至身份证号，存原文等于建一个无限期敏感信息库 | 无法做「热门搜索词」的原文分析，只能白名单化 |
| D-04 | **敏感字段独立解封接口** | 查询时顺带返回 | 顺带返回会让解封登记永远为空，取证链断裂而泄露已发生 | 多一次请求 |
| D-05 | **移动看板不在 M20 缓存** | M20 缓存 5 分钟提性能 | M22 有硬约束 `cache_ttl_sec <= 120`，M20 缓存等于绕过 | 每次都要调 M22（500ms） |
| D-06 | **留痕表不重写 `patient_id`** | 患者合并后批量重写 | 留痕是「当时查的是谁」的事实，重写等于伪造历史 | 审计时需串联 M03 的合并记录 |
| D-07 | **`sql_perm_applied` 恒真列** | 不加这一列 | 把「是否遵守 R-01」变成「留痕表能否写入」——违规实现会立刻表现为「检索报错」而非「悄无声息泄露」 | 多一列冗余 |
| D-08 | **被拒敏感访问也登记** | 只记成功 | 「试图查看但没有权限」本身是需要被看见的事实 | 表容量增加约 20% |
| D-09 | **摘要 200 字符服务端强制截断** | 交给前端截断 | 前端截断时全文已传输，带宽与抓包风险都存在 | 用户需点详情看完整 |
| D-10 | **`total` 允许为 null** | 强制求准确 total | 移动端快速翻页时求 total 可能扫全表 | 前端需处理 null |
| D-11 | **内部契约仍按 `caller_staff_id` 判权限** | 内部服务身份跳过权限 | 否则内部契约成为越权后门 | 内部调用多一次权限检查 |
| D-12 | **M12 走两跳而非自造列表接口** | M20 自己按 `patient_id` 查 M12 表 | 跨模块直连表违反铁律 2；两跳慢但合规 | 一页 20 条约多 200ms |
| D-13 | **本子模块不建任何物理外键** | 按 M20 常规建外键 | 全是纯追加留痕表，外键锁会拖慢检索热路径 | 引用完整性靠应用层校验 |
| D-14 | **检索词纯数字时不存哈希** | 一律存哈希 | 身份证号只有 10^18 种可能，存哈希可被字典攻击暴力还原 | 失去「同一数字串被查几次」的能力 |
