### 本文档的一条主线

M20-03 的九张表，**没有一张存「护理执行结果」**。

护理任务的权威在 M08（`task_status` 六态由总纲 §4.3 明确「M20 不自建状态」），执行记录的权威也在 M08（`/api/v1/m08/executions/*`），体征的权威在 M08-04（`m08_vital_sign`），用药的权威在 M08-06。本子模块存的是三类东西：

1. **床旁核对的过程证据**——「这台设备上，这台手机扫了什么码、和哪个值比、比的结果是什么、为什么没过」。它不是执行结果，因为执行结果由 M08 落库；它的用途是回答「护士说扫过了但系统没让过，到底卡在哪一步」。
2. **离线与弱网的中间态**——断网期间发生的事必须先在设备侧立住，回线后重放。M20-01 定义队列结构，本子模块定义自己的 `biz_type` 与重放逻辑。
3. **个人化与班次级配置**——本班次快捷入口、科室常用医嘱组、交接班备忘、设备配置、操作留痕。

一句话：**M08 回答「这次给药到底做没做」，M20-03 回答「护士在床边按了什么、为什么点不下去、断网时记了什么」。**

### 1.2 为什么是这 9 张，而不是「任务副本 + 执行副本 + 适配」的 20 张

判据回到总纲 §1.4 的红线：**这张表存的东西，如果 M20 删库重建，会不会有业务事实丢失？**

- **会丢失 → 可以建**。本子模块满足这条的只有三类：① 床旁**核对过程证据**（哪台设备、谁、什么时候、扫了什么码、和什么比、结果如何、卡在哪一关），M20 删库后无法重建——M08 只记核对结论，不记「这条码是在哪台手机上用哪个摄像头扫的、扫了几次、失败提示是什么」；② **离线中间态**（断网期间护士真实按下的动作），不回线就永远丢失；③ **个人化与班次级配置**（快捷入口、常用医嘱组、交接班备忘、科室设备配置），描述的是「这批护士在这个病区怎么工作」。
- **不会丢失 → 不许建**。护理任务、执行记录、电子签名、患者身份核对结论、生命体征、用药与滴眼液执行、护理记录正文**全部在 M08**（M08-01 任务、M08-03 执行与签名、M08-04 体征、M08-06 用药、M08-07 交接班），医嘱在 M07，患者身份在 M03，住院与床位在 M05，腕带条码由 M06-04 生成。M20 删库重建后照常可查。

按这个判据逐条对照（每条都对应一个「很想建但没建」的表）：

| 诱惑点 | 会不会建 | 理由 |
|---|---|---|
| `m20_nur_task` 护理任务副本 | **不建** | 任务权威在 M08-01（`m08_task`）。总纲 §4.3 已裁决「M20 不自建状态」，建任务副本必然要建状态列，一旦 M20 的状态列与 M08 分叉，就会出现「M08 说已完成、M20 说执行中」——而护士看的是 M20 |
| `m20_nur_nursing_record` 护理记录正文 | **不建**（校验器 `FORBIDDEN_TABLES` 明令禁止） | 护理记录是**病历事实**，权威在 M08。M20 落一份即产生第二份病历正文，归档时无法判定谁对 |
| `m20_nur_execution` 执行结果副本 | **不建** | 见 §1.3 专门论证。「M20 说打了、M08 说没打」是本模块最高风险的双写 |
| `m20_nur_vital` 体征副本 | **不建** | 体征权威在 M08-04 `m08_vital_sign`（明细在 `values_json` JSONB，判定结果在 `m08_vital_alert`）。体征是临床事实，且是危急值告警的输入 |
| `m20_nur_drug` / `m20_nur_order` 药品与医嘱副本 | **不建** | 药品主数据在 M01、医嘱在 M07。**尤其不能存一份「药品条码 → 药品名」的本地映射**：扫码命中的是本地字典时，改版或停用药品会被旧字典判为「核对通过」，这是扫码闸门最危险的失效形态 |

| `m20_nur_scan_verify` 扫码核对记录 | **建** | M08-03 的 `verify-patient` 只返回 `verified`/`attempt_count`/`is_locked` 与最终结论，**不记设备侧视角**。而「这台设备为什么老是核不过」是真实高频问题（摄像头脏、贴膜、腕带褶皱、光线），没有过程记录就只能靠猜 |
| `m20_nur_offline_item` 离线执行扩展 | **建** | 见 §1.4 论证 |
| `m20_nur_shift_handover` 移动端交接班备忘 | **建** | 见 §1.5 论证（与 M08-07 交接班不是同一件事） |
| `m20_nur_quick_entry` / `m20_nur_order_set` / `m20_nur_order_set_item` | **建** | 见 §1.6 论证 |
| `m20_nur_device_config` | **建** | 科室级差异（是否强制扫码、超时阈值、语音录入开关、字体档位）必须可配置，写死在代码里就会出现「某个病区要求必须扫码、另一个病区要求可手输」的分支蔓延 |
| `m20_nur_oper_log` | **建** | 移动端操作留痕是审计与问题定位的唯一来源；M02-06 记的是「业务动作」，记不了「在哪个页面点了哪个按钮、耗时多少、是否降级」 |
| `m20_nur_stat` 护理移动端统计表 | **不建** | 汇总类表看着像「通道事实」，实际是业务量统计。总纲 §7.1 点名「唯一容易踩线的一类是统计表」，判据回到 §1.4：删库重建后照常可从 M08 明细重算，不丢事实 |

### 1.3 为什么「扫码核对记录」不是「执行记录」

这是本子模块最容易写错的一张表，单独论证。

**诱惑**：护士在床边扫了腕带、扫了药品，把这三条扫码结果连同「已执行」一起落一张 `m20_nur_execution`，看起来既省一次 M08 调用，又留下了「M20 也能证明打了」。**不行。**

**为什么不行**——三条独立理由：

1. **会出现两个执行时刻**。离线场景下，设备记录的给药时间是**设备时间**（可能比服务器慢 3 分钟）；M08 落库的执行时间是**回线后服务器时间**。如果 M20 也存一份执行时刻，同一针就有两个时间戳，且两个都「有记录」。给药时间的法律意义极高（延误给药、给药间隔、不良事件回溯都以它为准），**两个时间戳等于没有时间戳**。
2. **会出现两个执行人**。离线队列可能被同班次另一名护士在同一台设备上重放（交接班后继续用这台机器），设备侧记录的 `executed_by` 与 M08 落库的签名护士可能不是同一个人。多存一份执行人就多一份「谁打的这一针」的争议。
3. **最致命的是「已执行」这个状态会分叉**。M08-03 的执行状态机是 `创建 → 核对 → 开始 → 记录 → 签名（完成）`，签名是终态且法规要求不可降级。M20 若自己标一个「已执行」，就会出现：M08 因签名失败/核对超时/医嘱被停而**未完成**，而 M20 显示**已执行**。这条差异不会报错、不会告警，只会在事后查护理不良事件时被发现——**那时已经无法还原护士到底打没打**。

**所以本表的定位只有一句话：它记录「核对过程」，不记录「执行结果」。**

三个字段层面的落实（DDL 里逐条对应）：

- **没有 `exec_status` 列，也没有任何叫「已执行」的枚举值**。本表只有 `verify_result`（`MATCHED` / `MISMATCH` / `UNREADABLE` / `SKIPPED_BY_CONFIG` / `UPSTREAM_UNAVAILABLE`）——注意 `UPSTREAM_UNAVAILABLE` 是**核对过程**的结论（本次没核成），不是执行结论。
- **`m08_execution_id` 是可空的「关联引用」，不是外键，也不是权威**。它是「这次核对发生在哪一次 M08 执行尝试的上下文中」，用于把核对记录串到 M08 执行时间线上。为空合法（核对时 M08 执行记录还没创建——移动端先扫码后建执行记录是允许的顺序）。
- **`verified_at` 是本表唯一的时间戳语义**：核对发生的时刻（设备时间 + 服务器校正后的 `clock_skew_seconds`），与「给药时刻」无关。

详细设计的 §1.4 会给出这张表与 M08 执行表的字段级对照，并在验收 AC 中设一条：「删除本表全部数据后，M08 的执行记录、体征记录、用药记录必须一条不少」。

### 1.4 为什么离线队列要「M20-01 主表 + 本子模块扩展表」两张

`m20_base_offline_queue` 由 M20-01 首建（数据结构汇总 §1.3），本子模块**只调用、不建、不写**。那为什么还要 `m20_nur_offline_item`？

1. **冲突判定的通用部分与业务部分必须分离**。M20-CALC-06 的五步冲突判定（幂等键已存在 / 实体已不存在 / 版本不一致 / 状态不允许该操作 / 放行）是**所有子模块共用的算法**，M20-01 定义一套；而「这条队列项的 `biz_type` 是 `NUR_MED_EXECUTE` 时，要拿 `(patient_id, drug_code, order_version)` 去 M07 重新校验」是**本子模块独有的重放逻辑**。合并会让 M20-01 被迫知道护理业务字段。
2. **通用表不能长成业务字典**。若把护理专用字段（医嘱号、药品编码、剂量、眼别、执行动作）加进 `m20_base_offline_queue`，M20-06 视光销售、M20-07 随访会各自再加一批字段，通用表会在半年内变成 80 列的宽表，且每一列对 80% 的行都是 NULL。
3. **冲突后的处置不同**。M20-06 的冲突处理是「让销售员重开单」，本子模块的冲突处理是「让护士长确认这一针到底打没打」——需要记录 `resolved_by` / `resolved_action` / `resolved_note` 与**设备侧原始时间**，这些字段对别的子模块没有意义。

**分工边界（一句话）**：`m20_base_offline_queue` 回答「这条离线的动作排到第几位、同步到哪一步了、有没有冲突」；`m20_nur_offline_item` 回答「这条动作在护理语义上是什么、重放时拿什么去重新核对、冲突后护士长怎么处置的」。

**本表与外键**：`queue_id` 对 `m20_base_offline_queue.id` **不建物理外键**——按数据结构汇总 §2.2「跨模块引用不建外键」的同源理由，首建方是另一个子模块的文档，一旦 M20-01 调整主键或做归档分区，本子模块的建表顺序与迁移会被钉死在它后面。替代做法：`queue_id` 建普通索引 + 一条「孤儿队列项巡检」定时任务（详细设计 §7.3）。

### 1.5 为什么「移动端交接班备忘」不是 M08-07 的交接班

M08-07 已有交接班（`m08_handover_*` 表族），本子模块为什么还要一张？

因为**两者的性质不同，不是同一件事的两个端**：

| 维度 | M08-07 交接班 | M20-03 移动端交接班备忘 |
|---|---|---|
| 性质 | **正式交接班记录**，有签发、有双方签名、进护理记录、可被质控抽查 | **个人备忘**，床旁随口记下的「3 床 10:00 后要测眼压」「7 床家属情绪不好」 |
| 权威 | M08（本子模块只读） | 本子模块 |
| 是否进病历 | 是 | **否**（不转录进护理记录，除非护士自己在 M08 补正式交接班） |
| 生命周期 | 不删、随护理记录留存 | 交接给下一班后归档，按班次保留 |
| 失败后果 | 缺失是护理质量问题 | 缺失只是少一条提示，不影响任何临床事实 |

**为什么不干脆让护士直接在 M08-07 里记**：正式交接班有必填项、有签名、有双方的时效要求（M08-07 规定交班簿须在交班后 30 分钟内完成）。床旁拿起手机想记一句「3 床 10 点后测眼压」，如果被迫走正式交接班表单，护士的真实反应是**不记**。备忘表的价值恰恰在于「随手记零成本」，而它的正确性由「有没有签署」分隔开：本表 `status` 只有 `OPEN` / `HANDED_OVER` / `ARCHIVED` / `DROPPED`，**不存在「已签发」这种状态**，从数据层上就无法被误当成正式交接班。

### 1.6 为什么快捷入口与常用医嘱组拆成三张表

`m20_nur_quick_entry`（个人化快捷入口）、`m20_nur_order_set`（科室常用医嘱组，如「白内障日间手术术后医嘱组」）、`m20_nur_order_set_item`（组内每一条）。

拆开的三条理由：

1. **归属主体不同，权限不同**。快捷入口是**某护士自己**的（`staff_id`，只能本人改）；常用医嘱组是**科室级**的（`dept_id` + `scope_type`，科室管理员维护，全科共用）。合并成一张会让「管理员能改别人的配置」这个授权无法在字段级表达。
2. **行数与变化频率差两个数量级**。快捷入口 40,000 行、几乎每天变；医嘱组明细 300,000 行、只在科室流程调整时变。
3. **医嘱组明细必须能存「已停用的条目**。科室调整医嘱组时，历史条目要保留（否则统计「这个组用了多少次」会因删行而失真），但不能再被新开单引用。这要求明细行有独立于组头的 `item_status`，合并成 JSON 就无法在不读全组的情况下判定单个条目的可用性。

**特别说明：`m20_nur_order_set_item` 存的是「医嘱组的模板内容」，不是「医嘱」。** 它不含剂量、频次、途径的**临床解释**，只存 M07 医嘱标准参数的**引用与默认值**，且**任何情况下不能被直接当作医嘱下发**——移动端点「用这个组」时必须逐条进入 M07 的开单流程由医师确认。这条在 DDL 注释与详细设计 §8.2 各写一遍，因为「模板即医嘱」是本模块最容易发生的越权。

## 2. 与共享规范 §12 的对照、本子模块不建的表

### 2.1 与数据结构汇总 §1.1 的对照

| 项目 | 汇总要求 | 本子模块实际 | 结论 |
|---|---|---|---|
| 表前缀 | `m20_nur_` | 9 张全部 `m20_nur_` 前缀 | 符合 |
| 表数 | 8~10 张 | 9 张 | 符合 |
| 建表顺序 | 第 ⑤ 段，依赖第 ① 段 `m20_base_offline_queue` | 见附录 E | 符合 |
| 迁移脚本 | `m20_0006` | 见附录 E | 符合 |

### 2.3 本子模块建的三张只增表的判据

数据结构汇总 §3.3 的判据是：**这张表的不一致或缺失本身是不是要被保留的信息？** 本子模块按此判据自评：

| 表 | 是否只增 | 判据 |
|---|---|---|
| `m20_nur_scan_verify` | **是**（`REVOKE UPDATE, DELETE`，无 `is_deleted`） | 核对记录是**证据**。护士事后说「我扫了但系统不让过」，靠这条记录说话。允许 UPDATE 就等于允许把「扫错了一次」改成「扫对了」 |
| `m20_nur_oper_log` | **是**（`REVOKE UPDATE, DELETE`，无 `is_deleted`） | 操作日志的缺失与不一致本身就是信息。改一条日志等于篡改留痕 |

| 其余 6 张 | 否 | 配置类、备忘类、中间态类，均可改可删（软删） |

### 2.4 关于「危急值清单」与「危急值确认」的边界（V1.1 裁决）

共享规范 §10.4.1 已登记两个上游事实缺口，本子模块必须遵守：

1. **M12/M13 没有「按患者/按就诊列出报告」的内部接口**（全目录无 `review/by-patient`、`review/list`），只有按 `report_id` 单条查的 `GET /internal/v1/m12/review/{id}` 与 `GET /internal/v1/m13/review/{id}`。
   **→ 因此本子模块不做「患者报告清单」功能，也不建任何报告索引表。** 移动护理侧能做的是：收到 `m12.critical.detected` / `m13.critical.detected` 待办后，点进去看**那一份**报告。需要清单的场合登记为「需向上游提请」，不在文档里假设接口存在。
2. **危急值确认属于 M07-04 的业务动作**。M12/M13 的 `POST .../critical/{id}/on-acknowledged` 语义是「M07 确认后回调 M12/M13」，**M20 不得替 M07 调这个回写口**（否则 M07 认为未确认、M13 认为已确认）。
   **→ 因此本子模块不建危急值确认表**，也不在 `m20_nur_oper_log` 之外留任何「已确认」标记。移动端只做通道与待办提醒。

**这两条直接决定：本子模块 9 张表里没有任何一张与报告、危急值、诊断相关。** 若后续 M07-04 提供移动端确认接口，再另行评估（属于 M20 通道层的能力扩展，不是 M20-03 的职责）。

### 3.4 分区结论：本子模块不做分区表

**结论：9 张表全部不分区。**

数据结构汇总 §4 要求「有分区表必须带 DEFAULT 分区」，本子模块干脆不启用分区。理由：

1. **只有 `m20_nur_oper_log` 够得上分区门槛**（年增 876 万）。按数据结构汇总 §4 的分区判据（「单表年增超过 500 万且需要按时间归档」），它是唯一候选。
2. **但 9,000 万行以下、单表 17.6 GB 的日志表在 PostgreSQL 16 上不需要分区**。分区带来三个真实代价：(a) 主键必须含分区键，`id` 不再是全局唯一单列，所有按 `id` 查的代码要改成 `(id, created_at)`；(b) 任何跨分区的唯一约束都无法表达；(c) 分区预建任务漏跑一次就写失败（这正是 §4.3 要求 DEFAULT 分区的原因）。**为了每年省 3 秒的 `DELETE` 而引入这三条，不划算**。
3. **归档需求用「冷热分表 + 定期搬运」解决，不用分区**：`m20_nur_oper_log` 保留 3 年在线；超过 3 年的行由 `nur_oper_log_archive` 定时任务（每月 3 日 02:30）搬进 `m20_nur_oper_log_archive` 表（**同一张表不搬，搬进独立的归档表**，结构完全相同、无索引、不参与业务查询）。搬运用 `INSERT ... SELECT` + `DELETE ... WHERE created_at < ? LIMIT 5000` 分批，避免长事务。

**如果未来行数超出预期需要改分区**：这是高危 DDL（数据结构汇总 §8.2），必须由 M20-01 统一规划，本子模块届时配合改造，**当前版本明确不做**。

### 3.5 只增不删的三张表及其数据库强制

按 §2.3 判据，`m20_nur_scan_verify`、`m20_nur_oper_log`、以及 `m20_nur_verify_exception` 的核对字段，落实为数据库层的三条强制：

| 强制 | 对象 | SQL | 防的真实错误 |
|---|---|---|---|
| 禁止改删 | `m20_nur_scan_verify` | `REVOKE UPDATE, DELETE ON m20_nur_scan_verify FROM app_m20;` + `GRANT INSERT, SELECT ...` | 事后把「扫错」改成「扫对」，伪造合规证据 |
| 禁止改删 | `m20_nur_oper_log` | 同上 | 篡改操作留痕 |
| 可更新列白名单 | `m20_nur_verify_exception` | `REVOKE UPDATE` 后 `GRANT UPDATE (status, reviewer_id, reviewed_at, review_opinion, updated_at, updated_by)` | 申请书落库后改核对结论；列清单**必须逐列显式列出，不能用 `ALL`**（用 `ALL` 等于把刚 revoke 的又发回去） |

**为什么不用触发器实现「禁止改删」**：`REVOKE` 是权限层，触发器是数据层。两者都用最稳，但只用一个时优先 `REVOKE`——触发器对超级用户和 `TRUNCATE` 无效，而 `REVOKE` 对应用账号一定有效。本子模块对两张只增表用 `REVOKE`，对 `m20_nur_verify_exception` 的列白名单也用 `REVOKE` + `GRANT (列)`，**不额外加触发器**（触发器只在需要「跨行/跨表判断」时才用，见 §4.3）。

### 3.6 本子模块不使用 `is_deleted` 的表

| 表 | 有无 `is_deleted` | 理由 |
|---|---|---|
| `m20_nur_scan_verify` | **无** | 只增表，不删 |
| `m20_nur_oper_log` | **无** | 只增表，不删 |
| 其余 7 张 | 有 | 配置类、备忘类、中间态类，允许软删 |

⚠️ **软删表的唯一索引必须注意**：软删表上的业务唯一索引**不能**写成 `WHERE is_deleted = FALSE` 的部分索引（数据结构汇总 §7.3 明确警告）。本子模块的全部唯一索引都把 `is_deleted` **直接放进索引列**，例如 `uk_m20_nur_order_set_code (dept_id, set_code, is_deleted)`——这样「删掉一条后同号再建」会被卡住，而部分索引会放过。

组合约束 6 条（`CHECK` 只保护字段自身，不保护字段之间——数据结构汇总 §7.2）：

```sql
-- 组合约束 1：核对通过必须有匹配时间与方式；防「核对流于形式」
ALTER TABLE m20_nur_scan_verify ADD CONSTRAINT ck_m20_nur_sv_matched_needs_time
    CHECK (verify_result <> 'MATCHED' OR (scan_time IS NOT NULL AND verify_method IS NOT NULL));

-- 组合约束 2：患者核对通过时，命中患者必须等于任务患者；防「把人认错了却记为通过」
ALTER TABLE m20_nur_scan_verify ADD CONSTRAINT ck_m20_nur_sv_matched_patient_equal
    CHECK (verify_stage <> 'PATIENT' OR verify_result <> 'MATCHED'
           OR (matched_patient_id IS NOT NULL AND matched_patient_id = patient_id));

-- 组合约束 3：上游不可用时不得是 MATCHED；防「查不到却算过」
ALTER TABLE m20_nur_scan_verify ADD CONSTRAINT ck_m20_nur_sv_upstream_not_matched
    CHECK (upstream_status = 'OK' OR verify_result <> 'MATCHED');

-- 组合约束 4：不符必须有原因码，且原因码只能在不符时出现
ALTER TABLE m20_nur_scan_verify ADD CONSTRAINT ck_m20_nur_sv_mismatch_reason
    CHECK ((verify_result = 'MISMATCH') = (mismatch_reason IS NOT NULL));

-- 组合约束 5：走例外通道的必须是 MISMATCH 或 UNREADABLE；防「啥都走例外」
ALTER TABLE m20_nur_scan_verify ADD CONSTRAINT ck_m20_nur_sv_exception_scope
    CHECK (exception_flag = FALSE OR verify_result = ANY (ARRAY['MISMATCH','UNREADABLE']));

-- 组合约束 6：扫码方式必须有扫到的码值；手输/语音方式必须为空
ALTER TABLE m20_nur_scan_verify ADD CONSTRAINT ck_m20_nur_sv_code_by_method
    CHECK ((verify_method IN ('WRISTBAND_SCAN','CARD_SCAN','DRUG_SCAN')) = (scanned_code IS NOT NULL));
```

**这六条各自防的真实错误**：

| 约束 | 防的真实错误 | 不写会怎样 |
|---|---|---|
| 1 | 代码里 `verify_result='MATCHED'` 是常量赋值，没有真实核对 | 一条 INSERT 就能造出「全部核对通过」的假证据 |
| 2 | 腕带扫了 5 床的赵明、任务却是 3 床的王建国，代码把 `verify_result` 置为通过 | 串人给药，且事后查记录是「通过」 |
| 3 | M03/M07 上游超时，代码走了「查不到就放行」 | 断网/上游故障期间所有核对都「通过」——**这是扫码闸门最危险的失效形态** |
| 4 | 不符时忘了写原因 | 事后只能看到「不符」，无法回答「哪个环节不符」 |
| 5 | 例外通道被当成「任意情况都能开」 | 例外的定义会被稀释，闸门形同虚设 |
| 6 | 手输方式却填了扫码码值 | 无法区分「真的扫了」和「假装扫了」 |

#### 4.2.4 `verify_result` 的 `UPSTREAM_UNAVAILABLE` 为什么必须是独立值

这是本表最重要的一个设计判断：**上游不可用不能记成 `MISMATCH`，也不能记成 `MATCHED`。**

- 记成 `MISMATCH`：核对记录上写着「不符」，护士会被统计成「扫错了 N 次」，而实际是系统连不上——**把系统故障算到护士头上**。
- 记成 `MATCHED`：等于闸门 fail-open，**这是绝对禁止的**（共享规范 §8A.3 第 1 条「不允许看起来正常但不完整」）。
- 记成 `UNREADABLE`：语义混淆——「码看不清」是设备/腕带的问题，「上游连不上」是网络/服务的问题，排查方向完全不同。

**独立值带来的唯一正确行为**：`UPSTREAM_UNAVAILABLE` 会同时置 `upstream_status='TIMEOUT'` 或 `'HTTP_ERROR'`，前端据此显示「核对服务暂不可用，本次未执行——请改用工作站核对」，且**这条记录既不计入护士的失败次数，也不计入设备的失败率**（按 `verify_result` 分组统计时单独列一栏）。

#### 4.2.5 `clock_skew_seconds` 与服务端校正

| 偏差范围 | 处理 |
|---|---|
| `abs(clock_skew_seconds) <= 60` | 正常，`scan_time` 直接采信 |
| `60 < abs(clock_skew_seconds) <= 300` | 记一条告警指标 `m20_nur_clock_skew_total`，`scan_time` 仍采信设备时间 |
| `abs(clock_skew_seconds) > 300` | **`scan_time` 仍存设备原值**，但该行被标记进入「时钟异常待核实」清单（详细设计 §5.8 页面），且**不得作为给药时刻的依据** |

**为什么超过 5 分钟不是「拒绝落库」而是「落库但标待核实」**：这条记录描述的是**已经发生的事**，护士当时确实扫了。拒绝落库等于销毁这个事实。正确做法是如实记录并标记，由人复核——这与「记录本身是证据」的判断一致。

#### 4.2.7 设计说明

1. **为什么按层级分三行而不是一行存三个结果**。一次完整的给药核对包含患者、药品、剂量途径三个层级，且三个层级的**失败次数、失败原因、耗时各不相同**——「腕带扫了 3 次才扫上，药品一次就过」这类信息决定培训与设备维保的方向。合成一行就只能存一个 `verify_result`，三层的差异全部丢失。代价是行数 ×3（已在 §3.2 容量里计入）。
2. **为什么 `matched_patient_id` 要单独存**。腕带扫码传回的 `patient_id` 是「扫到的这个人」，任务上的 `patient_id` 是「该给药的人」。两者不等时，**这条记录的价值极高**——它是「串人给药被系统拦下」的直接证据。只存一个 `verify_result='MISMATCH'` 无法知道「扫到了谁」。
3. **为什么 `bed_no` 存快照而不是每次联查 M05**。床号是易变字段（换床、转科）。核对记录要回答的是「当时护士站在几床」，必须存当时的床号。联查 M05 得到的是「现在在几床」，两者不是同一个事实。
4. **为什么不存患者姓名**。姓名是敏感字段（校验器 `SENSITIVE_FIELDS`），且本表的用途是排查核对链路，不需要姓名。要显示姓名时按 `patient_id` 现调 U-14 并走脱敏。
5. **为什么 `server_time` 与 `scan_time` 都要存**。`clock_skew_seconds = scan_time - server_time` 是可计算的，但如果只存一个差值，就无法反推「设备认为现在是几点」与「服务器认为现在是几点」。排查时钟问题时这两个绝对时刻是必需的。
6. **`SKIPPED_BY_CONFIG` 的用途**：某些病区在 `m20_nur_device_config` 里配置了「非高危药品可手输核对」，此时该层级不扫码。**这个值必须存在且必须被统计**——它让「哪些核对是被配置跳过的」可查，而不是静默消失。若某病区 `SKIPPED_BY_CONFIG` 占比超过 30%，详细设计 §11.3 的监控会告警（提示配置被滥用）。


### 4.3 表：`m20_nur_verify_exception`（核对例外通道审批）

#### 4.3.1 为什么需要这张表（先讲清「为什么不是强制通过按钮」）

核对不通过时，临床上确实存在无法扫码的正当情形：腕带被血液/碘伏浸透、条码被贴膜反光、药品最小包装未印码、患者拒绝佩戴腕带。如果系统只给一个「强制通过」按钮，这四类情形会让护士卡死，**而人一旦卡死，就会去找绕过系统的办法**——借别人的手机、用旧腕带、把码拍照后对着屏幕扫。这些绕法都不会留下记录，比一个受控通道危险得多。

所以真实的选择不是「开或不开」，而是三选一：

| 方案 | 做法 | 为什么不行 / 为什么可行 |
|---|---|---|
| A 一律拦截，不给任何通道 | 扫不过就做不了 | **不可行**。四类正当情形会变成「护士跑去工作站用 PC 端」，床旁核对的全部价值（减少往返、避免遗忘）消失；更糟的是会催生借用他人设备的绕行 |
| B 给「强制通过」按钮 | 护士点一下就能过 | **绝对不可行**。这个按钮一旦存在，压力大、忙、抢救时它会被条件反射地点下去；而且它不产生任何「为什么没过」的信息，事后完全无法复盘 |
| C 受控例外通道（本方案） | 需**另一名护士**扫码确认 + 填写结构化原因 + 留痕 + 次数监控 | **可行**。它把「绕过」变成「需要两个人共同承担」，并且把「为什么绕过」变成结构化数据 |

**方案 C 的四条硬边界**（逐条落实到本表字段）：

1. **不能由同一人完成两次确认**。`requester_id <> confirmer_id` 由数据库 CHECK 强制，不靠代码判断。
2. **原因必须结构化**，不能只有一段自由文本。`exception_reason` 是枚举 + `exception_note` 是补充说明，枚举值是有限的 6 个。
3. **事后可查**。本表不是黑盒：每条例外都能查到「谁、什么时候、因为什么、由谁确认、对应哪一次核对（`scan_verify_id`）、护士长的复核结论」。
4. **有次数监控**。同一护士、同一病区、同一原因的例外次数都进监控（详细设计 §11.3），超过阈值告警到护理部。

**唯一的触发器**（跨行判断必须用触发器，见 §3.5）：

```sql
CREATE OR REPLACE FUNCTION trg_fn_m20_nur_nxe_confirm_same_device()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.review_status = 'CONFIRMED'
       AND OLD.review_status = 'PENDING'
       AND NEW.confirmer_device_id IS NOT NULL
       AND NEW.confirmer_device_id = NEW.device_id THEN
        RAISE EXCEPTION 'SAME_DEVICE_TWO_PERSON'
            USING HINT = '例外确认必须使用另一台设备与另一名护士；同一设备上的两次确认不能作为双人核对';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m20_nur_nxe_confirm_same_device
    BEFORE UPDATE ON m20_nur_verify_exception
    FOR EACH ROW EXECUTE FUNCTION trg_fn_m20_nur_nxe_confirm_same_device();
```

**为什么这条必须用触发器而不是 CHECK**：CHECK 只能看单行的字段，`confirmer_id <> requester_id` 是单行内比较所以能写；但「确认设备与发起设备相同」需要区分**当前是谁在改**——护士 A 用自己手机发起、护士 B 拿 A 的手机确认，`confirmer_id` 与 `requester_id` 确实不同（B 的账号），CHECK 看不出来。**设备相同就意味着「第二个人可能只是拿着同一部手机点了两下」**，双人核对退化成单人。这个判断必须放在触发器里。

#### 4.3.7 设计说明

1. **为什么例外必须一次性（`used_flag`）**。若一条例外可以反复放行，护士遇到一个无法扫码的药品后就能整班都用它放行同一种药。一次性保证「每次无法扫码都要重新走一次流程」——流程本身是提醒，不是障碍。
2. **为什么 `expire_at` 是 30 分钟**。从发现扫不上到叫来另一名护士确认，30 分钟足够覆盖正常情形；超过 30 分钟说明这次核对已经脱离了当时的情境（患者可能已换、药品可能已回退），必须重来。这个值与 M08-03 的「核对时间 → 签名时间间隔 30 秒~30 分钟」同源，两者口径一致。
3. **为什么本表允许 `is_deleted`**。撤销一份还没被确认的申请是正常操作（护士发现扫错层级、重扫成功了）。软删而不是物理删，保证「申请过又撤了」也留痕。
4. **为什么 `requester_name_snap` / `confirmer_name_snap` 存姓名快照**——注意这些是**护士**姓名，不是患者姓名。审计需要「人事后调岗、离职、改名后仍能看出当时是谁」，人员主数据会变，快照不会变。校验器 `SENSITIVE_FIELDS` 只针对患者/客户信息，不含 `requester_name_snap`。


### 4.4 表：`m20_nur_offline_item`（离线执行队列扩展）

#### 4.4.4 约束

```sql
ALTER TABLE m20_nur_offline_item ADD CONSTRAINT ck_m20_nur_noi_biz_type
    CHECK (biz_type = ANY (ARRAY['NUR_MED_EXECUTE','NUR_VITAL_RECORD','NUR_SCAN_VERIFY','NUR_HANDOVER']));
ALTER TABLE m20_nur_offline_item ADD CONSTRAINT ck_m20_nur_noi_replay_status
    CHECK (replay_status = ANY (ARRAY['NOT_REPLAYED','REPLAYING','REPLAYED','REPLAY_BLOCKED','REPLAY_SKIPPED']));
ALTER TABLE m20_nur_offline_item ADD CONSTRAINT ck_m20_nur_noi_conflict_type
    CHECK (conflict_type IS NULL OR conflict_type = ANY (ARRAY['ENTITY_GONE','VERSION_CHANGED','STATE_INVALID']));
ALTER TABLE m20_nur_offline_item ADD CONSTRAINT ck_m20_nur_noi_eye
    CHECK (eye_side IS NULL OR eye_side = ANY (ARRAY['OD','OS','OU','NA']));

-- 组合约束 1：给药类必须有医嘱、药品、剂量三件套（否则重放时无法再校验）
ALTER TABLE m20_nur_offline_item ADD CONSTRAINT ck_m20_nur_noi_med_needs_key
    CHECK (biz_type <> 'NUR_MED_EXECUTE'
           OR (order_id IS NOT NULL AND order_version IS NOT NULL AND drug_code IS NOT NULL));

-- 组合约束 2：给药类必须有两个扫码码值（重放重新过闸门的依据）
ALTER TABLE m20_nur_offline_item ADD CONSTRAINT ck_m20_nur_noi_med_needs_scan
    CHECK (biz_type <> 'NUR_MED_EXECUTE'
           OR (patient_scan_code IS NOT NULL AND drug_scan_code IS NOT NULL));

-- 组合约束 3：CONFLICT 必须能说清是哪一类冲突（M20-CALC-06）
ALTER TABLE m20_nur_offline_item ADD CONSTRAINT ck_m20_nur_noi_conflict_needs_type
    CHECK (replay_status <> 'REPLAY_BLOCKED' OR conflict_type IS NOT NULL);

-- 组合约束 4：处置必须有处置人、时刻；APPLY_ANYWAY / MANUAL_FIX 必须有说明
ALTER TABLE m20_nur_offline_item ADD CONSTRAINT ck_m20_nur_noi_resolved_needs_who
    CHECK (resolved_action IS NULL OR (resolved_by IS NOT NULL AND resolved_at IS NOT NULL));
ALTER TABLE m20_nur_offline_item ADD CONSTRAINT ck_m20_nur_noi_resolved_needs_note
    CHECK (resolved_action IS NULL OR resolved_action = 'DISCARD'
           OR (resolved_note IS NOT NULL AND length(btrim(resolved_note)) > 0));

-- 组合约束 5：REPLAYED 必须有 M08 执行记录 ID；防「说重放成功了但拿不出执行记录」
ALTER TABLE m20_nur_offline_item ADD CONSTRAINT ck_m20_nur_noi_replayed_needs_exec
    CHECK (replay_status <> 'REPLAYED' OR m08_execution_id IS NOT NULL);

-- 组合约束 6：体征类的 vital_values 必填，且不得混入给药字段
ALTER TABLE m20_nur_offline_item ADD CONSTRAINT ck_m20_nur_noi_vital_needs_values
    CHECK (biz_type <> 'NUR_VITAL_RECORD' OR vital_values IS NOT NULL);
```

**这六条里第 1、2、5 条是本子模块最关键的**：

| 约束 | 防的真实错误 |
|---|---|
| 1 | 离线记录只存「3 床某个药」，回来重放时不知道是哪条医嘱——**没有医嘱版本就永远无法判定这条记录还该不该执行**，只能放弃，等于这一针白打了 |
| 2 | 离线期间没扫码（或扫了没存码值），回线后无法重新过闸门——**等于离线就是闸门的后门**，这正是任务书点名要防的 |
| 5 | 重放代码把上游返回的空响应当成功，`replay_status` 置了 `REPLAYED` 却没有 `m08_execution_id`——事后查这条记录到底落实没有，查不出来 |

#### 4.4.5 重放为什么必须重新过闸门（设计论证）

任务书要求「离线队列里的给药项在重放时必须重新过闸门，不能因为是离线时录的就免检」。落实为三道：

**第一道：数据层不留后门。** 组合约束 2 强制 `patient_scan_code` 与 `drug_scan_code` 都不能为空——**离线时没扫码的给药记录，根本无法落进本表**。这比在重放代码里写一句「必须校验」有力得多：代码可以改，约束改起来要发迁移。

**第二道：重放时用离线时的码值重新比对当前状态。** 具体算法（详细设计 §6.5 有实现）：

```text
对每条 replay_status = 'NOT_REPLAYED' 的给药记录：
  1. 调 M07 API-33 GET /internal/v1/m07/orders/{order_id}/for-execute 取当前医嘱
  2. 若医嘱不存在或已作废/已停/已退          → CONFLICT/ENTITY_GONE
  3. 若 order_version 与当前医嘱版本不一致     → CONFLICT/VERSION_CHANGED
  4. 若当前医嘱 patient_id ≠ 记录的 patient_id → CONFLICT/STATE_INVALID（串人）
  5. 若当前医嘱 drug_code  ≠ 记录的 drug_code  → CONFLICT/STATE_INVALID（换药）
  6. 若 M08 任务状态已 COMPLETED/REJECTED/SKIPPED → CONFLICT/STATE_INVALID（已被他人执行）
  7. 以上都不命中 → 调 M08 执行接口落库 → 成功后置 REPLAYED 并记 m08_execution_id
```

**第三道：冲突不自动解决。** `REPLAY_BLOCKED` 一律进待处理清单，由人决定 `DISCARD` / `APPLY_ANYWAY` / `MANUAL_FIX`，且 `APPLY_ANYWAY` 与 `MANUAL_FIX` 必须写说明（组合约束 4）。

**为什么第 6 步是必须的**（这是 M20-CALC-06 算例 OF-001 的场景）：护士 A 在 3 床断网状态下记了「已给药」，回线时发现同事 B 已经用工作站执行了同一条任务。若不判定 `STATE_INVALID`，重放会把同一次给药执行两遍——**而两次执行在 M08 都留了记录，事后看是「同一针打了两次」，这是护理不良事件上报的典型场景**。

#### 4.4.7 设计说明

1. **为什么 `device_recorded_at` 与 `server_received_at` 分开存**。离线期间的业务时刻是法律事实（给药时间），服务器接收时刻是工程事实。两者的差就是 `offline_duration_seconds`——这个值本身是重要的运营指标（离线时长分布决定要不要增加 AP 点位）。合并成一个 `created_at` 就只剩工程事实。
2. **为什么 `clock_skew_seconds > 300` 不是拒绝而是标注**。离线场景下设备时间本来就不可靠，但**护士确实按了那一下**。拒绝落库等于销毁证据（与 §4.2.5 同源判断）。标注后由人复核，且这条记录在重放时仍会走完整流程。
3. **为什么 `payload_summary` 只有 500 字符**。它是给人快速判断「这条冲突记录大概是什么事」的摘要。完整信息在 `replay_context`（JSONB）。摘要短，列表页一次能拉 20 条而不超 200KB 响应体上限（总纲 §8.1）。
4. **`REPLAY_SKIPPED` 的用途**：离线队列里混有「护士已经手工在工作站重做了一遍」的项，回线后不该再重放。这个状态由人在冲突清单里选「已在工作站完成」触发，是 `DISCARD` 之外的另一条合法出口。

#### 4.5.4 `memo_text` 的隐私边界（重要）

备忘正文是自由文本，最容易泄露患者隐私。三条防护：

1. **客户端与网页端都不允许把备忘正文写进事件载荷**（共享规范 §10.3 红线：载荷不得含患者姓名/手机号/身份证明文）。本表的正文只在本模块内展示。
2. **详细设计 §8.2 设正文校验规则 V-05**：`memo_text` 中检出身份证号、手机号、诊断关键词时提示改写，并记一条 `m20_nur_oper_log`。**提示而不是拦截**——因为拦截会让护士转而口头交接（更不可追溯）。这条规则在验收里定义为「检出率必须记录」，不定义为「必须阻断」。
3. **本表不进病历、不进质控抽样**。归档 24 小时后只对护理部管理员可见。

#### 4.5.6 设计说明

1. **为什么 `memo_text` 与 `memo_items` 并存**。正文给护士自由记录（零成本），结构化条目给机器用（可排序、可提醒、可统计「本班有几个待测眼压」）。**只有结构化条目是不够的**——强迫护士把每句话归类会让她们不记；只有自由文本也不行——无法生成任何提醒。两者并存，条目可后补。
2. **为什么 `urgency` 不产生告警**。它是备忘的排序提示，若接上告警就会变成第二个告警通道（M20-08 才是消息与待办中心），导致同一件事两处响。本表只影响列表排序。
3. **为什么 `voice_url` 只存地址不存文件**。语音文件是二进制，落 M20 库会把库撑爆且无法备份策略统一。对象存储的路径落库，文件本身按 M20-01 的对象存储规范管理。

#### 4.6.5 设计说明

1. **为什么 `entry_label` 冗余存放**。快捷入口一页展示 8~12 条，若每条都要联查来源对象取名字，就是 N+1 查询，在弱网下响应体与耗时都不可接受（首屏预算 900ms，总纲 M20-CALC-04）。冗余的代价是名字可能变旧（医嘱组改名后入口仍显示旧名），处理方式：改医嘱组时同步更新引用它的入口，且这个同步在应用层做、不建外键。
2. **为什么唯一键把 `is_deleted` 放进列而不是用部分索引**。若用 `WHERE is_deleted = FALSE` 的部分索引，护士删掉一个入口再重新添加同一对象时，会与已软删的行冲突（因为软删行的 `is_deleted=TRUE` 不在索引里，实际上不冲突）——**但反过来**，同一对象被删两次会产生两条 `is_deleted=TRUE` 的行，唯一性失效。把 `is_deleted` 放进索引列则「同一对象每次只允许一条有效 + 若干条已删」中的「已删」只允许一条。真正正确做法是不软删而是物理删（这是个人配置，删了就是删了），**本表实际采用「删除即物理删除」**，`is_deleted` 列只为与全模块规范保持一致而保留，正常流程不使用。此说明同步记入附录 F。
3. **`auto_created` 与 `pinned` 互斥**。自动生成是按频次猜的，固定是人的明确意图。若允许两者同时为真，清理任务就无法判断该不该删——互斥后规则清晰：自动生成的可清理、手工固定的永不清理。

```sql
ALTER TABLE m20_nur_order_set ADD CONSTRAINT ck_m20_nur_nos_enabled_needs_who
    CHECK (set_status <> 'ENABLED' OR (enabled_at IS NOT NULL AND enabled_by IS NOT NULL));

ALTER TABLE m20_nur_order_set ADD CONSTRAINT ck_m20_nur_nos_disabled_needs_reason
    CHECK (set_status <> 'DISABLED' OR disabled_reason IS NOT NULL);
```

> **组合约束 2 与 3 的说明**：`item_count` 是冗余计数，它与 `m20_nur_order_set_item` 的实际行数可能不一致（并发下）。**数据库层的 `item_count >= 1` 只保证「声明了有条目」，不能保证「真有条目」**——真正的校验靠应用层在启用时 `SELECT count(*)` 并在事务内写 `item_count`。这条冗余约束的价值是挡住「`item_count=0` 还启用」的明显错误。**不写触发器去维护 `item_count`**，因为触发器维护计数会在批量导入条目时锁住组头行，代价大于收益；改由应用层在事务内维护，并在附录 C 提供一条对账 SQL。

#### 4.7.6 设计说明

1. **为什么 `diagnosis_hint` 只是文字而不是 `diagnosis_code`**。一旦存诊断编码，M20 就有了「按诊断推荐医嘱」的能力，而诊断的权威在 M07-02、诊断编码体系在 M01。存一个诊断编码列会诱导后续写出「按诊断自动匹配医嘱组」，那时就必须维护诊断码的映射与版本，等于在 M20 里长出一个诊断子系统。文字提示让护士自己判断。
2. **为什么 `item_count` 冗余而不是每次 `count(*)`**。护士选组页要展示「这个组有几条」，一页 10 个组就是 10 次聚合查询。冗余计数是最小的代价。一致性靠应用层事务维护 + 附录 C 对账 SQL 兜底。
3. **为什么 `usage_count` 要记**。它同时是三个功能的输入：组列表的排序（高频在前）、清理候选（半年没人用的组提示停用）、以及「这个组是否真的有人用」的评审证据。

1. **为什么 `item_status='DEPRECATED'` 而不是直接删行**。药品停用或诊疗项目下架时，组里那条要保留（历史统计与「这个组为什么少了一条」的解释），但不能再被引用。删行会让历史统计失真且无法解释。
2. **为什么默认值这么多列而不是全塞 `order_param_snap`**。最常用的五个参数（剂量、单位、途径、频次、天数）必须能被 SQL 直接查询与校验（组合约束 1 需要查 `default_dose`）；冷门参数进 JSONB，避免宽表。这个切分口径与 M08-04 的「明细在 JSONB，判定结果在告警表」是同一种思路：**要参与约束与统计的进列，不参与的进 JSONB**。
3. **`spec_text`/`item_name` 存快照的理由**：M01 主数据改名或停用后，组里仍要能显示「当时配的是什么」。快照过期是可见的（名字不同），比显示空白或报错好。

#### 4.9.4 配置变更的四个等级（收紧 / 放宽）

| 等级 | 例子 | 是否需审批 | 理由 |
|---|---|---|---|
| ① 纯展示 | `UI_FONT_SCALE`、`UI_TASK_GROUP_BY` | 不需要 | 不影响安全 |
| ② 更严格 | `SCAN_REQUIRE_DOSE_ROUTE` 由 false 改 true | 不需要 | **收紧不需要审批**——收紧不会有人受害 |
| ③ 放宽 | `SCAN_REQUIRE_PATIENT` 由 true 改 false | **需护士长 + 护理部双签** | 放宽闸门就是削弱 G-1 |
| ④ 禁用闸门 | `EXCEPTION_ENABLED` 改 false | 需护理部审批 | 关掉唯一受控通道，会诱导绕行 |

#### 4.9.5 设计说明

1. **为什么用「键值对」而不是 27 个列**。27 列的表每加一项配置就要一次 DDL 迁移，而配置项的增长远快于业务字段。键值对的代价是无法用列类型约束（所以用 `value_type` + 组合约束 3/4 补），收益是新增配置零迁移。
2. **为什么 `config_value` 统一存字符串**。混合类型的值列会导致 `value_type` 与实际存储类型不一致的坑。统一字符串 + `value_type` 解释，读时按类型转换，转换失败抛错——比存 `JSONB` 更容易写约束（`JSONB` 里无法用 CHECK 直接比较数值范围）。
3. **为什么不按设备存**。设备（手机）会换、会重装、会借给同事。配置必须按**科室/病区**维度，设备只承接「上次同步到的配置快照」。按设备存配置会导致「换了部手机所有设置消失」。
4. **`effective_from` 的用途**：新配置可以预先录入、到点生效（如「下月 1 日起强制剂量核对」）。为空表示立即生效。

#### 4.10.6 设计说明

1. **为什么本表不分区、靠归档搬运**。见 §3.4：9,000 万行以下不需要分区。归档表 `m20_nur_oper_log_archive` 结构相同、无业务索引，由定时任务每月搬运 3 年前的数据。
2. **为什么 `action_result` 有 `DEGRADED` 这个值**。移动端大量操作在弱网下完成，`SUCCESS` 与 `DEGRADED` 的区别是「结果可信」与「结果来自缓存/部分上游」。若不区分，事后分析「为什么这条任务显示已完成但工作站没有」时无法定位。组合约束 3 强制它与 `degraded_flag` 同步，防止日志本身自相矛盾。
3. **为什么 `detail_json` 明令禁止敏感明文**。日志是最容易被导出分析的数据（运维、审计、统计都要拉），一旦日志里出现患者姓名，导出即泄露。本模块的 `m20_nur_scan_verify` 也不存姓名（§4.2.7 第 4 条），两处口径一致。
4. **`client_ts` 与 `created_at` 并存**。`client_ts` 是设备认为的时刻，`created_at` 是服务器落库时刻。二者差值即设备时钟偏差，与 §4.2 的 `clock_skew_seconds` 同源，但本表不单独存差值列——因为日志量太大，每行多一个 INTEGER 就是 2,628 万 × 4 字节 ≈ 100 MB。

### 4.11 SQLAlchemy 2.0 模型定义

#### 4.11.0 统一约定

| 约定项 | 取值 | 理由 |
|---|---|---|
| 基类 | `NurBase(DeclarativeBase)` | 本子模块内部继承；公共 Mixin 由 M20-01 提供，本子模块不重复定义 |
| 主键 | `Mapped[int] = mapped_column(BigInteger, Identity(always=False), primary_key=True)` | 与 DDL 的 `GENERATED ALWAYS AS IDENTITY` 对齐 |
| 时间类型 | `Mapped[datetime] = mapped_column(TIMESTAMP(timezone=True))` | 对应 DDL 的 `TIMESTAMPTZ`；**不得写 `DateTime`**（会生成不带时区的列） |
| 枚举 | `Mapped[str] = mapped_column(String(32))` + `CheckConstraint` | 不用 `sqlalchemy.Enum`，避免 ORM 层与数据库层两套枚举定义漂移 |
| 外键 | 仅 `m20_nur_order_set_item.set_id` 有物理外键 | 其余跨表引用是逻辑引用，加物理外键会把建表顺序钉死 |
| 软删 | 仅 5 张表映射 `is_deleted` | `scan_verify` / `oper_log` / `offline_item` / `shift_handover` 无此列 |
| `__table_args__` | 元组，`comment` 放最后一个元素的字典 | SQLAlchemy 要求表级选项写在元组末尾的 dict |
| 分区 | 本子模块 9 张表均不分区 | 见 §3.4 论证，无需 `postgresql_partition_by` |

## 4.12 Pydantic Schema 定义

### 4.12 Pydantic Schema 定义

#### 4.12.0 统一约定

| 约定项 | 取值 | 理由 |
|---|---|---|
| Pydantic 版本 | V2，`model_config = ConfigDict(...)` | 共享规范 §2.1 |
| 基类 | `NurSchema(BaseModel)` | `from_attributes=True`、`extra="forbid"`、`str_strip_whitespace=True` |
| 时间序列化 | `field_serializer` 输出 ISO 8601 带时区 | 与共享规范 §2.4 一致，如 `2026-11-07T10:09:42+08:00` |
| 响应包装 | `ApiData` / `ApiPage` 由 M20-01 提供 | 本子模块不重复定义响应包装，仅引用 |
| 枚举 | 出参用 `Literal[...]` | 与 ORM 的 `String(32)` + CHECK 双轨：DB 兜底、Schema 早失败 |
| 剂量 | `Decimal` + `max_digits=12, decimal_places=4` | 禁 `float`，浮点会把 0.1 变成 0.10000000000000001 |
| 四质量标记 | `ApiData` 必带 | `degraded` / `degraded_sources` / `data_quality` / `as_of` |

#### 4.12.1 通用类型与包装

```python
"""M20-03 移动护理 —— Pydantic V2 Schema 定义。

响应一律由 ApiData / ApiPage 包装，四质量标记（degraded / degraded_sources /
data_quality / as_of）必带。data_quality 由 M20 按 M20-CALC-05 自己重算，
不透传上游值（共享规范 §8A.2.1）。
"""
from __future__ import annotations

from datetime import date, datetime
from decimal import Decimal
from typing import Annotated, Any, Generic, Literal, TypeVar

from pydantic import (
    BaseModel,
    ConfigDict,
    Field,
    field_serializer,
    model_validator,
)

DataQuality = Literal["REALTIME", "CACHED", "PARTIAL", "UNKNOWN"]
NetworkStateLit = Literal["WIFI", "CELLULAR", "WEAK", "OFFLINE"]

DoseNumber = Annotated[
    Decimal,
    Field(max_digits=12, decimal_places=4, gt=0),
]


class NurSchema(BaseModel):
    """本子模块所有 Schema 的基类。"""

    model_config = ConfigDict(
        from_attributes=True,
        extra="forbid",
        str_strip_whitespace=True,
        use_enum_values=True,
    )


class DegradedSource(NurSchema):
    """降级来源说明。

    reason 取值为机器可读的短码；上游自己的质量词汇只能放在这里，
    不能覆盖 M20 的 data_quality（§8A.2.1）。
    """

    source: str = Field(description="降级来源，如 M08 / M07 / M05 / M18")
    reason: str = Field(
        description="原因码，如 TIMEOUT / HTTP_ERROR / UNMEASURABLE_N / UPSTREAM_DAILY"
    )
    detail: str | None = Field(default=None, description="人类可读补充说明")


T = TypeVar("T")


class ApiData(NurSchema, Generic[T]):
    """单对象响应包装。"""

    code: int = 0
    message: str = "success"
    data: T | None = None
    trace_id: str | None = None
    degraded: bool = Field(
        default=False, description="本次响应是否发生降级（或不是）"
    )
    degraded_sources: list[DegradedSource] = Field(
        default_factory=list, description="降级来源清单，未降级为空数组"
    )
    data_quality: DataQuality = Field(
        default="REALTIME", description="M20 自算的新鲜度，不透传上游"
    )
    as_of: datetime = Field(description="数据口径截止时刻，取所有成功来源的最小值")

    @field_serializer("as_of")
    def _ser_as_of(self, v: datetime) -> str:
        return v.isoformat(timespec="seconds")

    @model_validator(mode="after")
    def _check_degraded_pair(self) -> "ApiData[T]":
        """degraded 与 degraded_sources 必须同向，不允许只填一个。"""
        if self.degraded and not self.degraded_sources:
            raise ValueError("degraded=True 时必须给出 degraded_sources")
        if not self.degraded and self.degraded_sources:
            raise ValueError("degraded=False 时 degraded_sources 必须为空")
        return self


class ApiPage(NurSchema, Generic[T]):
    """分页响应包装。

    record_count 是本次实际返回条数；与 total 不同——total 允许为 None
    （上游不给总数时不要编一个），record_count 必须为真实条数。
    """

    code: int = 0
    message: str = "success"
    items: list[T] = Field(default_factory=list)
    record_count: int = Field(ge=0, description="本次返回条数")
    total: int | None = Field(default=None, description="总条数，上游不给则为 null")
    page_no: int = Field(default=1, ge=1)
    page_size: int = Field(default=20, ge=1, le=100)
    has_more: bool = Field(description="是否还有下一页")
    trace_id: str | None = None
    degraded: bool = False
    degraded_sources: list[DegradedSource] = Field(default_factory=list)
    data_quality: DataQuality = "REALTIME"
    as_of: datetime

    @field_serializer("as_of")
    def _ser_as_of(self, v: datetime) -> str:
        return v.isoformat(timespec="seconds")

    @model_validator(mode="after")
    def _check_page_consistency(self) -> "ApiPage[T]":
        if self.record_count != len(self.items):
            raise ValueError("record_count 必须等于 items 长度")
        if self.degraded and not self.degraded_sources:
            raise ValueError("degraded=True 时必须给出 degraded_sources")
        return self
```

### A.2 为什么只有这两张表是「只增」

判据回到总纲 §1.4 与数据结构汇总 §3.3 的同一句话：**这张表的不一致或缺失本身是不是要被保留的信息？**

- `m20_nur_scan_verify`：核对过程是**合规证据**。护士被投诉「给错药」时，能证明「她扫了、扫到的是 5 床」的只有这张表。允许改就等于允许事后修饰证据，因此 `REVOKE UPDATE, DELETE` + 无 `is_deleted`。
- `m20_nur_oper_log`：操作日志同理，且日志被改过这一事实本身无法察觉。同样 `REVOKE UPDATE, DELETE` + 无 `is_deleted`。

其余 7 张**不是**证据表：

- `m20_nur_verify_exception`、`m20_nur_shift_handover`：需要支持「撤销未确认的申请」「作废写错的备忘」，是正常的业务订正，允许 `is_deleted`，但**已确认/已交接的内容通过权限回收变为不可改**（见 §4.3.6 列清单）。
- `m20_nur_offline_item`：队列项本身是中间态，重放成功后就地更新状态是设计意图，不能只增。
- 快捷入口、医嘱组、配置：纯配置与个人化偏好，天然可删改。

### A.3 无触发器表的说明

九张表里**只有 `m20_nur_verify_exception` 一张带触发器**（`trg_fn_m20_nur_nxe_confirm_same_device`，见 §4.3.6）。其余约束全部用 `CHECK` 或唯一索引表达，理由与数据结构汇总 §3.1 一致：**能用唯一索引或 CHECK 表达的不变量，就不要用触发器**——触发器对 `TRUNCATE`、超级用户、会话级 `session_replication_role = replica` 都无效，而且要随每次 DDL 变更维护。

例外的那一条之所以必须用触发器，是因为它要比较的两个值（发起设备、确认设备）虽然在同一行，但**约束的语义是「两个人两次独立动作」，而 `CHECK` 只能表达「这一行的字段之间满足什么关系」，无法表达「这两个动作不能来自同一手持终端」**。详见 §4.3.6 的论证。

### C.2 为什么不给 `scanned_code` 建索引

`scanned_code` 是要按值查的（「这个码是不是重复用了」），但直接给它建完整 B-Tree 有两个问题：一是长度 128 变长字符串，索引体积大；二是码值本身是患者身份凭据的一部分，索引页会留在备份与 `pg_dump` 里。实际做法是**建 `scanned_code_hash`（SHA-256）的索引，按哈希做等值检索，需要展示明文时再回表 `SELECT scanned_code`**。

### C.3 医嘱组条目数对账 SQL

`m20_nur_order_set.item_count` 是冗余列，由应用层事务维护、不用触发器（理由见 §4.7.4）。对账作业每日跑一次：

```sql
SELECT s.id,
       s.set_code,
       s.item_count                                        AS declared_count,
       count(i.id) FILTER (WHERE i.is_deleted = FALSE)      AS actual_count
FROM m20_nur_order_set s
LEFT JOIN m20_nur_order_set_item i ON i.set_id = s.id
WHERE s.is_deleted = FALSE
GROUP BY s.id, s.set_code, s.item_count
HAVING s.item_count <> count(i.id) FILTER (WHERE i.is_deleted = FALSE);
```

返回行会被记入监控指标 `m20_nur_order_set_count_mismatch`，非零时告警。**不自动修正**：条目数的偏差本身可能是「有人绕过接口直接改库」的信号，自动修正会把信号抹掉。

### C.4 闸门有效性查询（验收与日常监控共用）

```sql
SELECT date_trunc('day', scan_time)                          AS stat_date,
       device_id,
       count(*)                                              AS total_scan,
       count(*) FILTER (WHERE verify_result = 'MATCHED')      AS matched,
       count(*) FILTER (WHERE verify_result = 'MISMATCH')     AS mismatched,
       count(*) FILTER (WHERE verify_result = 'UNREADABLE')   AS unreadable,
       count(*) FILTER (WHERE verify_result = 'UPSTREAM_UNAVAILABLE')
                                                             AS upstream_unavailable,
       round(
           count(*) FILTER (WHERE verify_result = 'MISMATCH')::numeric
           / nullif(count(*) FILTER (
                 WHERE verify_result IN ('MATCHED', 'MISMATCH')), 0),
           6)                                                AS mismatch_rate
FROM m20_nur_scan_verify
WHERE scan_time >= now() - interval '30 days'
GROUP BY 1, 2
ORDER BY 1 DESC, mismatch_rate DESC NULLS LAST;
```

两点说明：

1. **分母只含 `MATCHED` 与 `MISMATCH`**。`UNREADABLE` 与 `UPSTREAM_UNAVAILABLE` 不是护士的错，混进分母会让「设备坏得多的时候护士看起来越合规」——这正是 M20-CALC-02 里那个「更慢反而更好看」陷阱的同一形状。比率在分母为 0 时返回 `NULL` 而不是 0。
2. **按设备分组而不是按人分组**，因为排查方向是「这台机器是不是坏了」。按人分组会退化成考核工具，而考核工具一旦出现，护士的第一反应是少扫而不是扫对。

```sql
JOIN pg_namespace n ON n.oid = c.relnamespace AND n.nspname = 'public'
LEFT JOIN pg_constraint co ON co.conrelid = c.oid AND co.contype = 'c'
WHERE c.relname LIKE 'm20_nur\_%'
GROUP BY c.relname
ORDER BY c.relname;
```

## 附录 F：文档维护约定

### F.1 六条维护约定

1. **本文件与详细设计文件必须同批变更**。表结构改了而详细设计的接口没改，等于给出一个调不通的接口；接口改了而表没改，等于给出一个落不了库的接口。
2. **`CHECK` 里的枚举是全文档唯一落库出处**。§4.11.1 常量类、附录 B、详细设计附录 B 三处必须与它逐字一致；出现不一致时以 `CHECK` 为准，另外三处算缺陷。
3. **新增表必须先过 §1.2 的红线自检**，并在 §1.2 补一行「诱惑点 / 会不会建 / 理由」。判据是删库重建会不会丢业务事实，不是「反正多一张表也不占地方」。
4. **只增表的判定不可随手修改**。要把一张表从「只增」改成「可改」，必须在附录 E.3 记录变更理由并走评审——这是唯一能改证据表权限的入口。
5. **任何 JSONB 列结构变更都要同步 D.3**，包括新增键。JSONB 的价值是可扩展，代价是没人知道里面有什么；不登记就等于没有结构。
6. **M08 的字段变化必须重新核对本文件的 `NurTaskSummary`**。任务列表是同一份数据的另一个窗口，M08 改了字段而 M20 没跟上，页面上就会少一列或者显示错位，而且不会报错。
