### 1.1 为什么是这 8 张（按总纲 §1.4 判据逐张过筛）

总纲 §1.4 给出的判据是：**这张表存的东西，如果 M20 删库重建，会不会有业务事实丢失？会 → 可以建；不会 → 不许建。**

| 候选对象 | 判定 | 理由 |
| :--- | :--- | :--- |
| 触达尝试记录（打电话/发微信/上门） | **建** `m20_fol_attempt` | 丢了就再也不知道「这次随访是谁、在哪一天、用什么渠道、通了几秒、对方说了不方便」。这是**触达过程事实**，M19 的随访记录只存「随访结论」，不存通话过程。 |
| 话术模板 | **建** `m20_fol_script` | 丢了就没人知道当时护士念的是哪一版话术。话术内容本身可以重建，但**版本号与生效区间**是合规证据（「我们是按 2026 版术后话术做的告知」）。 |
| 知识卡（常见问答） | **建** `m20_fol_knowledge_card` | 同理，版本与生效区间是证据。且知识卡挂在话术之下，两者版本独立。 |
| 患者备忘（随访注意点） | **建** `m20_fol_memo` | 「这位患者怕疼，打电话要慢一点」这类非临床注意事项，M19 无处安放，丢了就丢了。**它不是患者快照**——不存姓名、电话、诊断、身份证任何字段。 |
| 离线队列扩展 | **建** `m20_fol_offline_item` | `m20_base_offline_queue`（M20-01 首建）只存通用的队列项（操作类型、载荷、版本、状态）。随访特有的「这条队列项对应哪个 followup_task_id、哪个患者、属于哪次随访周期」需要在**本子模块**落地，且它是冲突判定与人工处理的依据。**注意本表只做扩展，不改 M20-01 的表结构。** |
| 筛选条件收藏 | **建** `m20_fol_saved_filter` | 「糖网术后 3 个月未复查」这类组合条件是护士每天要用的，丢了重配一次要 2 分钟。 |
| 拍照/录音引用 | **建** `m20_fol_media` | 「患者说眼睛胀」的录音、「术后眼部照片」是过程事实，丢了不可恢复。**表里只存对象存储的引用，不存二进制。** |
| 使用统计 | **建** `m20_fol_stats` | 「昨天随访了多少、接通多少」如果每次现算要扫 420 万行的触达表。日聚合是**可重建的派生数据**，但重建代价高，所以落表；它不是业务事实，因此**允许删除重建**。 |
| 随访计划 | **不建** | 归 M19。校验器 `FORBIDDEN_TABLES` 含 `m20_followup_plan`。M20 只调 P-01 取待办。 |
| 随访任务表 | **不建** | 归 M19（`m19_fu_pool_snapshot` 与执行记录在 M19-01 / M19-02）。任务状态的生命周期归计划发布方。 |
| 随访结果表 | **不建** | 归 M19（`m19_fu_exec_record`）。这是**临床随访数据，属于患者档案**。 |
| 患者表 / 患者快照 | **不建** | 铁律 2 与铁律 4。禁止 `m20_patient`，也禁止任何形态的「患者快照表」。 |
| 员工待办表 | **不建** | 归 M20-08（`m20_msg_todo`）。M20-07 作为**待办来源方**，只提供 `(source='FOLLOWUP', biz_id=task_id)` 去重键并调用 M20-08 的写接口。 |
| 操作日志表 | **不建** | 通用操作日志不属本子模块；请求级留痕由 M02-06 审计接口承接，业务侧留痕由各业务表自身的四审计列承接。 |

### 1.2 三组必须分开的边界（不合并的理由）

| 组 | 表 | 不合并的理由 |
| :--- | :--- | :--- |
| **过程事实 vs 配置** | `m20_fol_attempt` / `m20_fol_media` 元数据 vs `m20_fol_script` / `m20_fol_knowledge_card` | 前者日增数千行、随病历封存只读；后者是配置表，手工维护、随时可改版本。**混在一张表里，一次「话术改版」会带动 400 万行记录的更新与索引重建。** |
| **队列扩展 vs 队列本体** | `m20_fol_offline_item` vs `m20_base_offline_queue` | 队列本体由 M20-01 首建、被 M20-03/06/07 共用，冲突判定算法（M20-CALC-06）只有一套。本表只补 M20-07 特有的业务字段，**DDL 不得重复出现在本文档**。 |
| **明细 vs 日聚合** | `m20_fol_attempt` vs `m20_fol_stats` | 统计页要 5 年趋势，明细表 420 万行按天 GROUP BY 在弱网首页会超时；日聚合表 4.4 万行，一次查询 < 10ms。**且聚合表可以按统计公式变更整体重建，明细表不能重建。** |

### 1.3 与数据结构汇总的差异说明

数据结构汇总 §6 第 ⑧ 段列出 M20-07 为 **8 张表**，本文件正好 8 张，**数量一致**。差异在于表名：

| 汇总 §6 的写法 | 本文档的实际表名 | 说明 |
| :--- | :--- | :--- |
| 未逐一列名（只给数量 8） | `m20_fol_attempt` 等 8 张 | 汇总只登记前缀与数量，具体表名以本文档为准 |

### 4.2 表：`m20_fol_attempt`（触达尝试记录）

**用途：** 记录每一次「尝试联系患者」的过程事实——打了几次电话、每次通了几秒、有没有被挂断、发了什么渠道的消息、有没有上门。**本表不存随访结论。**

**写入方：** M20-07（移动端随访执行页提交、离线队列重放）
**只读方：** M20-07 统计页与日聚合任务、M20-08 待办（读状态判断该不该继续推待办）

**边界说明（本子模块最关键的一条）：** 患者在电话里说「我这两天眼睛有点胀」，这句话是**临床信息**，必须写进 M19 的随访记录（`/internal/v1/m19/followup-exec` 的结果回写接口），**不许只填在本表的 `hangup_note` 里**。本表的自由文本字段只允许写「触达过程」内容，即「无人接听」「家属代接，说患者出差」「工作时间不方便」。**「必须提交随访结果才能把任务置为已随访」是无接口层到数据层的硬约束，见详细设计 §3.2 与 §8.2 R-07。**

| 索引名 | 类型 | 字段 | 说明 |
| :--- | :--- | :--- | :--- |

#### 设计说明

1. **为什么 `recorded_at` 与 `attempt_started_at` 要分开。** 手机时钟可以被用户改，离线场景下 `attempt_started_at` 甚至可能是昨天的时刻。统计与聚合一律用服务端的 `recorded_at`；而「这次通话到底发生在几点」用于还原过程时用 `attempt_started_at`。**两个时刻都留，是为了让「统计口径稳定」与「过程可还原」两件事都不让步。**

2. **为什么 `result_submitted` 是一个布尔字段而不是靠「有没有关联的 M19 记录」推算。** 推算需要在查询时跨模块判断，而 M19 不可用时推算结果会退化为 `FALSE`，把「已提交」错判成「未提交」。落成本地字段后，**它只由「M19 回写成功」这一件事写入，是单调的 FALSE→TRUE**，任何降级都不会让它回退。

3. **为什么 `hangup_note` 限 200 字符且文档里明令不得写临床症状。** 字段本身挡不住人写什么，但 **200 字符的容量与字段名 `hangup_note`（挂断备注）共同构成语义暗示**。真正的防线在接口层：详细设计 §9.3 要求随访结果提交接口的入参 `result_note` 与 `hangup_note` 分属两个请求体，且「未提交结果不允许结束任务」。

4. **为什么 `(idempotency_key)` 用部分唯一索引而不是普通唯一索引。** 在线提交不带幂等键（页面提交有前端防抖 + 服务端 `X-Idempotency-Key`），大量行该列为 NULL。PostgreSQL 的唯一索引对 NULL 不去重，普通唯一索引也能工作，但会让索引里塞满 NULL 项；部分唯一索引只索引非 NULL 行，**体积约为全量的三分之一，写入更快**。

5. **为什么 `cycle_key` 由本模块自算而不是存 M19 的某个字段。** 任务号、计划号都是 M19 的概念，M19 没有「随访周期」这个显式标识。本模块用 `plan_no:node_name` 构造稳定键，其语义是「同一随访计划的同一个节点」——这正是「同一患者同一随访周期」的定义。**代价是 node_name 改名会让同一周期分裂成两个键**，所以在详细设计 §8.1 写死「node_name 更名必须由 M19 做数据迁移，M20 只读快照」。反过来说，若本模块去调 M19 现算周期，合并判定就得在离线状态下放弃。

6. **量级估算。** 门诊随访任务约 30 万条/年，平均每任务 2.3 次触达 → 约 69 万行/年，5 年 345 万行；住院与手术随访另计约 15 万行/年，5 年 75 万行。合计 **约 420 万行**。单行平均 380 字节 → 约 1.6 GB，10 个索引合计约 2.4 GB，**本表约 4 GB**。三年内不分区；超过 3 GB 时按 `recorded_at` 月分区（附录 E 给出改造路径）。

#### 设计说明

1. **为什么话术要版本化而不是原地改。** 护士念过错的话术无法从记忆中还原。若话术原地改，医生问「当时你们跟我说的是什么」时，只能看到最新版，**这就是把合规证据改成了「现在的口径」**。版本化后再配合 `m20_fol_attempt.script_id`（本表尚无该列，见下方第 5 点），才能回答「2026 年 3 月这通电话念的是第几版」。这与共享规范铁律 5 的精神一致：**已经发生的事不能被后来的修改覆盖。**

2. **为什么 `uk_m20_fol_script_active` 用部分唯一索引。** 「同一编码只能有一个生效版本」是业务不变量，用部分唯一索引表达有两点好处：①数据库层面绝对保证；②**改版时表现为「先把旧的置 ARCHIVED，再把新的置 ACTIVE」，若顺序写反，第二步会撞唯一键立刻失败**，而不是悄悄产生两个生效版本。

3. **为什么 `body_text` 用 `TEXT` 而不是 `VARCHAR(n)`。** 话术长度天生不可控（有的一句话，有的带三段落）。PostgreSQL 的 `TEXT` 与 `VARCHAR` 在存储与性能上无差别，用 `TEXT` 避免因为「后来加了长话术」而改表。

4. **为什么 `effective_to IS NULL` 表示「当前仍有效」而不写成 `'9999-12-31'`。** 哨兵时间会让所有区间查询都要特判，且容易在比较时出错。`NULL` 是「开区间」的自然表达，查询 `effective_from <= ts AND (effective_to IS NULL OR ts < effective_to)`。

5. **`m20_fol_attempt` 为什么没有直接引用 `script_id`。** 因为护士可能「这次没按话术念」（比如患者是家属接电话，临时换口径）。若强制关联，会逼着护士随便选一个话术凑数，反而污染数据。设计上把「本次用了哪版话术」作为**可选**记录，落在详细设计的执行页交互里；本表只负责提供「当前哪一版可用」。

6. **量级估算。** 场景 6 类 × 每类约 20 个话术编码 × 平均 3 个版本 = 约 360 行，实际按 120 行（很多编码只有 1~2 版）估算。**本表是配置表，量级不随业务增长。**

4. **量级估算。** 场景 6 类 × 平均 12 张卡 × 平均 2 版 ≈ 144 行，按 80 行估算。

```sql
ALTER TABLE m20_fol_memo
    ADD CONSTRAINT ck_m20_fol_memo_type
    CHECK (memo_type = ANY (ARRAY['CONTACT_WINDOW', 'PROXY', 'REFUSE_CALL',
                                  'COMMUNICATION', 'OTHER']));

ALTER TABLE m20_fol_memo
    ADD CONSTRAINT ck_m20_fol_memo_status
    CHECK (status = ANY (ARRAY['ACTIVE', 'ARCHIVED']));

-- 组合约束 1：备忘内容不能太短（至少 4 个字符，避免「有」「无」这类废记录）
ALTER TABLE m20_fol_memo
    ADD CONSTRAINT ck_m20_fol_memo_text
    CHECK (length(btrim(memo_text)) >= 4);

-- 组合约束 2：REFUSE_CALL 必须有失效时刻
-- 理由：拒绝来电的意愿会变，不能永久生效把患者从随访名单上锁死。
ALTER TABLE m20_fol_memo
    ADD CONSTRAINT ck_m20_fol_memo_refuse_expire
    CHECK (memo_type <> 'REFUSE_CALL' OR expire_at IS NOT NULL);

-- 组合约束 3：失效时刻必须在创建之后
ALTER TABLE m20_fol_memo
    ADD CONSTRAINT ck_m20_fol_memo_expire_order
    CHECK (expire_at IS NULL OR expire_at > created_at);

-- 组合约束 4：ARCHIVED 必须有更新时刻（归档是一次更新动作）
ALTER TABLE m20_fol_memo
    ADD CONSTRAINT ck_m20_fol_memo_archived
    CHECK (status <> 'ARCHIVED' OR updated_at IS NOT NULL);
```

#### 设计说明

1. **为什么它挂在 `patient_id` 上而不是 `task_id` 上。** 备忘的价值在于「跨任务」——「只有上午在家」这件事对三个月后的下一次随访依然成立。若挂在任务上，下一次随访又要重新发现一遍。但它必须记 `source_attempt_id`，这样「这条备忘是哪次打电话时说的」永远可追溯。

2. **为什么 `memo_text` 卡 512 字。** 这个上限是**设计意图，不是技术限制**。放宽到 `TEXT` 后，护士会开始往里写「2026-10-08 电话：患者诉左眼异物感，已嘱咐点左氧氟沙星」——这就把临床信息写进了非临床表。512 字装不下一次完整的病情描述，但足够写「只有上午在家，儿子转达」。**用长度上限做主动的引导，比写一句「不要记录临床信息」的规定更有效。**

3. **为什么 `REFUSE_CALL` 必须有 `expire_at`。** 「患者说不想再接电话」是当下意愿，不是永久授权。若允许永久，患者半年后视力下降需要被随访时，系统会因为他半年前的一句气话而漏掉他。**让拒绝自动过期，是让系统默认倾向于「再问一次」而不是「永远不问」。**

4. **为什么 `OTHER` 保留而不是砍掉。** 备选类型不全是常态。若不给 `OTHER`，护士会把「说不清是哪类」的备忘塞进 `COMMUNICATION`，反而让 `COMMUNICATION` 失去意义。`OTHER` 是泄压阀。

5. **量级估算。** 年随访任务约 36 万次，按 5% 会产生备忘估算 ≈ 1.8 万条/年，5 年 9 万；按 18 万（含历史回溯导入）估。单行约 400 字节，总约 72MB。

    ADD CONSTRAINT ck_m20_fol_offline_item_no_stale_conflict

    CHECK (resolved_at IS NULL OR (resolved_by IS NOT NULL AND replay_status <> 'CONFLICT'));

ALTER TABLE m20_fol_offline_item
    ADD CONSTRAINT ck_m20_fol_offline_item_payload
    CHECK (jsonb_typeof(exec_payload) = 'object');

ALTER TABLE m20_fol_offline_item
    ADD CONSTRAINT ck_m20_fol_offline_item_seq
    CHECK (attempt_seq >= 1);
```

#### 设计说明

1. **为什么要有扩展表而不是把载荷塞进 `m20_base_offline_queue`。** 那个队列是 M20 全局的，会被护理任务、消息、审批等多个子模块共同使用。若往里加随访专用列，**M20-01 的表就被迫了解随访的业务字段**，任何一次随访载荷结构变化都要改全局表，其他子模块跟着吃迁移。

2. **`replay_status` 是本地冗余吗？** 不是。判定口径是总纲 §1.4：**「这张表存的东西，如果 M20 删库重建，会不会有业务事实丢失？」** `replay_status` 丢了吗？丢了 M20-01 的队列行还在，状态能重算。但**「这条离线尝试被人工判为 ABANDONED 并且是谁判的」这个决定本身是业务事实**——它代表「护士当时记的这次随访，被人明确判定为不生效」。重算只会得到「队列里有一条未同步项」，不会得到「已被判定放弃」。所以 `replay_status` / `resolved_by` / `resolved_at` 是**决定记录**，不是冗余缓存。

3. **为什么 `task_no` 原样存、不校验位数与格式。** 共享规范 §17 第 4 条：**对上游单号做位数或格式校验会导致端到端跑不通。** M19 改了单号规则，本表一校验就全部写入失败。本表的 `task_no` 只是给人看与排障用的标签，唯一键一律用 `task_id`。

4. **`client_recorded_at` 为什么单独存而不复用 `created_at`。** `created_at` 是服务端插入时刻（即**重放时刻**，可能是第二天早上），`client_recorded_at` 是护士**真正打完这通电话的时刻**。两者的差值本身是有意义的运维数据——如果差值普遍超过 12 小时，说明离线同步链路出了问题。而且随访记录里要展示的是后者。

5. **量级估算。** 仅有网络不稳时才走离线，按随访执行量的 15% 估算：36 万 × 15% ≈ 5.4 万/年，按 6 万估。单行含 JSONB 约 2KB，共约 120MB。

#### 设计说明

1. **为什么附件不进数据库。** 一份术后照片 2~5MB，录音 3~10 分钟约 3~8MB。放进 `BYTEA` 后：①大字段会 TOAST 到独立表，`SELECT *` 时极易被无意拉出，页面列表一次翻 20 条就可能拉走 100MB；②`pg_dump` 与备份体积膨胀，恢复时间按小时涨；③对象存储天然支持 CDN、缩略图、断点续传，数据库不支持。所以只存键与哈希。

2. **为什么 `object_key` 不是完整 URL。** 对象存储的内网域名、鉴权方式、甚至服务商都可能更换。存完整 URL 后换一次域名就是全表 UPDATE，而且历史 URL 会失效。存相对键 + 桶名，URL 在运行时拼接，换域名只改配置。

3. **为什么必须有独立的探针任务（本设计的重点）。** `content_hash` 只能证明「我们记录下来的哈希和当时算出来的一致」。**它证明不了对象存储里那个文件还在。** 现实的失败模式：①对象存储配了生命周期规则，30 天自动转低频/90 天自动删除；②有人手工清理桶；③跨区域复制失败；④迁移时漏了一个目录。这些情况下数据库里的行完好、哈希完好，**打开附件时才发现 404**——而发现的人往往是拿着司法调证函的病案室。所以本设计配一个**独立的探针任务**（详细设计 §7.3 APScheduler，每日抽样 + 周度全量分片），真正走一次 `HEAD`/`GET Range` 把文件取回来，取不到就把 `probe_status` 置 `MISSING`，哈希不一致置 `HASH_MISMATCH`，连续 3 次失败触发告警。**探针本身不做修复**——自动重新上传等于掩盖了对象存储配置的问题。

4. **为什么 `expire_at` 基本不设。** 随访影像是病历附件的延伸，病历的保存期是 15~30 年（总纲 G-2）。若给附件设 90 天过期，就会出现「病历还在、证据没了」。`expire_at` 保留是给 `TRAINING` 类留的——培训素材不是病历。约束上**不强制** `FOLLOWUP_EVIDENCE` 必为 NULL，因为这属于策略应在配置层管，DB 只提供字段。

5. **量级估算。** 36 万随访任务，按 30% 带附件、每次 2.4 个附件 ≈ 26 万/年，按 26 万估。单行约 600 字节，DB 侧约 156MB；**对象存储侧按平均 4MB 估约 1TB/年**——这是本子模块最大的存储开销，且根本不在数据库里。

### 4.9 表：`m20_fol_stats`（随访执行日统计）

**用途：** 按日 × 科室 × 员工聚合的随访执行统计快照，供「我的随访效率」「科室随访完成情况」两个页面直接读，避免每次都扫 420 万行的 `m20_fol_attempt`。

**写入方：** M20-07 日终统计任务（APScheduler，每日 01:10）
**只读方：** M20-07 统计页、科室看板

**边界说明（关键）：** 本表**只统计 M20 自己的过程事实**（触达次数、接通次数、通话时长），**不统计任何临床随访结果**（有效随访率、随访到位率这类指标归 M19）。理由：随访到位率的分母是「应访数」，它由 M19 的随访计划决定，M20 拿不到可信的应访数——**若 M20 自己造一个分母，就会出现两个部门报出两个随访完成率**。总纲 M20-CALC-03 的教训（少去重一次虚高 79%）在这里同样适用：**凡是分母不归自己管的比率，一律不算。**

-- 组合约束 2：冲突数不能超过离线次数
ALTER TABLE m20_fol_stats
    ADD CONSTRAINT ck_m20_fol_stats_conflict

           AND conflict_count >= 0
           AND conflict_count <= offline_attempt_count);

-- 组合约束 3：接通率必须与分子分母自洽，且分母为 0 时必须为 NULL
-- 这是总纲「分母为 0 存 NULL 不存 0」在库层的落地。
ALTER TABLE m20_fol_stats
    ADD CONSTRAINT ck_m20_fol_stats_rate
    CHECK (
        (attempt_count = 0 AND connected_rate IS NULL)
        OR (attempt_count > 0
            AND connected_rate IS NOT NULL
            AND connected_rate >= 0
            AND connected_rate <= 1
            AND abs(connected_rate
                    - ROUND(connected_count::numeric / attempt_count, 6)) <= 0.000001)
    );

ALTER TABLE m20_fol_stats
    ADD CONSTRAINT ck_m20_fol_stats_duration
    CHECK (
        (connected_count = 0
         AND avg_duration_sec IS NULL
         AND total_duration_sec = 0)
        OR (connected_count > 0
            AND avg_duration_sec IS NOT NULL
            AND avg_duration_sec >= 0
            AND abs(avg_duration_sec
                    - ROUND(total_duration_sec::numeric / connected_count, 0)) <= 1)
    );

-- 组合约束 5：离线次数不能超过触达次数
ALTER TABLE m20_fol_stats
    ADD CONSTRAINT ck_m20_fol_stats_offline
    CHECK (offline_attempt_count <= attempt_count);

-- 组合约束 6：不同患者数不能超过触达次数

    ADD CONSTRAINT ck_m20_fol_stats_distinct
    CHECK (distinct_patient_count >= 0 AND distinct_patient_count <= attempt_count);
```

#### 设计说明

1. **为什么本表只算「接通率」不算「有效随访率」。** 接通率的分母是触达次数，**这个分母完全属于 M20**——是护士按了几次拨号键。它的分子分母都在 `m20_fol_attempt` 里，M20 说了算。有效随访率的分母是「应访数」，由 M19 的随访计划定义，M20 只是执行方。**一个指标的分母归谁管，就由谁算**，否则必然出现两个口径。这条判断与总纲 §1.4「M20 不拥有临床事实」是同一件事的两面。

2. **为什么造出 `staff_id = 0` / `dept_id = 0` 的双哨兵维度。** 「科室汇总行」与「员工明细行」放在同一张表里，靠 `staff_id = 0` 区分，好处是科室看板一次查询就能同时拿到汇总与明细（`GROUP BY` 之外的两种粒度共存）。**代价是要严格约束哨兵值**——若不加约束，将来有人插入 `staff_id = NULL` 的行，`GROUP BY` 会把它当成第三种粒度，汇总数字翻倍。所以组合约束里哨兵行与明细行必须互斥（由 `uk_m20_fol_stats_dim` 与写入逻辑保证），本表在文档中明确：`0` 是哨兵值，不是真实 ID。

3. **为什么比率列存起来而不是查询时算。** 统计页每开一次要读 60 天 × 20 名员工的 1,200 行；若每次现算比率，移动端会因为除法精度差异与缓存不一致而出现「同一页刷新两次数字不同」。存下来 + CHECK 锁定算式，能让**页面读到的数字与数据库算的数字永远是同一个**。

4. **为什么 `calc_batch_no` 要存。** 统计任务重算历史某天时，若发现新批次与旧批次结果不同，必须能回答「那天算的时候是哪一批、用的是哪一版逻辑」。这是**统计数据的取证属性**，与 `m18_idx_case_stat` 同类处理。

5. **量级估算。** 每天约 30 个科室 ×（1 条汇总 + 平均 1.5 条员工明细）≈ 75 行/天，5 年 ≈ 13.7 万；另有员工跨科执业产生的重复行，按 4.4 万估（题面预估偏保守，实际以 13.7 万为准，不影响分区决策——本表不分区，见附录 E）。单行约 180 字节。

> **为什么上面对 `ck_m20_fol_stats_rate` 拆成了两条约束。** 完整的「分母为 0 则比率为 NULL、否则比率必须与分子分母自洽」是一条带 `OR` 分支的复合表达式。在 ORM 声明的 `CheckConstraint` 里写长表达式容易在拼接时出错，所以拆成「分母 0 → NULL」与「比率上限 1」两条可读的约束，精确的算式自洽由附录 E 的 `CREATE TABLE` 里那条 `ck_m20_fol_stats_rate_calc` 落地。**两条约束合起来等价于一条，但更容易在 code review 时看出来。**

### C.2 三个必须避免的查询写法

```sql
-- ❌ 避免 1：不加 is_deleted 条件，部分索引失效
SELECT * FROM m20_fol_attempt WHERE staff_id = 1001;

-- ✅ 正确：与索引的 WHERE 子句一致，命中部分索引
SELECT * FROM m20_fol_attempt
WHERE staff_id = 1001 AND is_deleted = FALSE AND touch_at >= CURRENT_DATE;

-- ❌ 避免 2：在 touch_at 上套函数，索引失效
SELECT * FROM m20_fol_attempt
WHERE date(touch_at) = CURRENT_DATE AND staff_id = 1001;

-- ✅ 正确：写成区间，让索引可用
SELECT * FROM m20_fol_attempt
WHERE staff_id = 1001 AND is_deleted = FALSE
  AND touch_at >= CURRENT_DATE
  AND touch_at < CURRENT_DATE + INTERVAL '1 day';

-- ❌ 避免 3：统计页直接扫明细表算接通率
SELECT staff_id, count(*) FROM m20_fol_attempt
WHERE touch_at >= CURRENT_DATE - INTERVAL '60 days' GROUP BY staff_id;

-- ✅ 正确：读 m20_fol_stats 的预聚合结果
SELECT staff_id, sum(attempt_count), sum(connected_count)
FROM m20_fol_stats
WHERE stat_date >= CURRENT_DATE - INTERVAL '60 days' AND dept_id = 3001
GROUP BY staff_id;
```

> **避免 1 的补充说明。** PostgreSQL 的部分索引只在查询条件**逻辑蕴含**索引 `WHERE` 子句时才会被使用。`idx_m20_fol_attempt_staff_day` 的 `WHERE is_deleted = FALSE` 意味着：查询里不写 `is_deleted = FALSE`，规划器就不敢用这条索引（因为它无法保证结果完整）。所以 ORM 层的默认查询**必须始终带上 `is_deleted = FALSE`**，这一条要写进详细设计 §8 的编码规范。

### E.3 关键 DDL 片段：`m20_fol_stats` 的比率自洽约束

```sql
ALTER TABLE m20_fol_stats
    ADD CONSTRAINT ck_m20_fol_stats_rate_calc
    CHECK (
        (attempt_count = 0 AND connected_rate IS NULL)
        OR (attempt_count > 0
            AND connected_rate IS NOT NULL
            AND connected_rate >= 0
            AND connected_rate <= 1
            AND abs(connected_rate
                    - ROUND(connected_count::numeric / attempt_count, 6)) <= 0.000001)
    );

ALTER TABLE m20_fol_stats
    ADD CONSTRAINT ck_m20_fol_stats_duration_calc
    CHECK (
        (connected_count = 0 AND avg_duration_sec IS NULL AND total_duration_sec = 0)
        OR (connected_count > 0
            AND avg_duration_sec IS NOT NULL
            AND abs(avg_duration_sec
                    - ROUND(total_duration_sec::numeric / connected_count, 0)) <= 1)
    );
```

> **`<= 0.000001` 这个容差为什么必要。** `NUMERIC(10,6)` 存 6 位小数，`ROUND(x, 6)` 也保留 6 位，理论上两边应当完全相等。但 `abs(a - b) <= 0.000001` 比 `a = b` 更稳：①避免 `NUMERIC` 在不同精度设置下的表示差异；②容差设得比最小刻度（`0.000001`）**不小**，等于放行了一个刻度的误差，**不会掩盖任何真实的口径错误**——真正算错时差值是百分点级别的。这是一条「够松以致不会误伤、够紧以致不会漏放」的阈值。
