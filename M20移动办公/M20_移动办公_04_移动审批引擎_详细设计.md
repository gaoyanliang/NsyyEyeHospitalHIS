## 1. 模块概述

### 1.1 定位

M20-04 移动审批引擎是 M20 中唯一拥有**真正业务状态机**的子模块。它接收各业务模块发起的审批申请，解析审批链，驱动节点流转，催办与留痕，并把最终结论通知申请方。

它只拥有两件事：**流程事实**（谁在什么时候发了什么申请、谁批了、谁驳了）和**通道事实**（通知发出去了没有、申请方执行了没有）。它**不拥有任何临床事实与账务事实** —— 改单到底改了什么、退费到底退多少钱，那些是 M10 / M11 / M17 的事。

判据保持唯一：**把 M20-04 的库删掉重建，会不会有业务事实丢失？** 不会丢业务事实（业务都在申请方），但会丢流程事实（谁批的这件事无法重建）。审批留痕在医疗机构是法定证据，因此它的存储要求比普通业务表更严 —— 这就是本子模块三张只增不删表的由来。

### 1.2 为什么独立成子模块

M20-04 有 11 页、36 个接口，比 M20 其他子模块都大。复杂度**不来自功能数量，来自边界情况**：加签、转办、委托代理、超时升级、撤回、撤回复审、免审类型、跨级审批、多人会签（会签又有「全部同意」与「任一同意」两种语义）。这些边界每一个都会在真实医院里发生。

| 维度 | 放在各业务模块里各做一套 | 独立成 M20-04 |
| --- | --- | --- |
| 审批链解析 | M10 与 M11 各写一套，改规则要改两处 | 一处解析，规则集中配置 |
| 留痕表 | 每模块一张，跨模块查「这个人批过什么」要 union | 一张表，一次查询 |
| 委托代理 | 各模块各自实现，A 模块能代批 B 模块不能 | 统一授权，一次配置全局生效 |
| 超时处理 | 各模块定时任务重复扫，口径不一 | 一处扫描，一处告警 |
| 回执与执行确认 | 断点 A 与断点 C 无人负责 | 回执接口 + 执行确认双列显式建模 |
| 移动端适配 | 每个模块做一套审批界面 | 一套通用审批界面 |

### 1.4 概念辨析

| 易混概念 | A 是什么 | B 是什么 | 分清的意义 |
| --- | --- | --- | --- |
| 审批通过（APPROVED）vs 业务生效（COMPLETED） | 审批人同意了这个请求 | 申请方真的执行了 | 不区分就会出现「显示已批准、实际没执行」的幽灵单据 |
| 实例状态 vs 执行确认状态 | 审批的结论是什么（9 值） | 这个结论被执行了吗（4 值） | 合在一起会让通过率与审批时长两套口径打架 |
| 节点超时 vs 实例超时 | 某一级停留太久（仍是 PENDING） | 全体审批人都不可用，转管理员 | 混为一谈会把「有人没批」与「没人能批」当成一回事 |
| 待办 vs 抄送 | 必须处理，阻塞流程 | 只是知会，不阻塞 | 混在一起会让真待办淹没在抄送里，最终全部被划掉 |
| 转办 vs 加签 | 换人批（原人就失去操作权） | 加一个人批（原人仍要批） | 两者对节点数量的影响完全不同 |
| 委托代理 vs 转办 | 一段时间的授权，自动生效 | 针对单个节点的换人 | 委托滥用风险最高，必须审批且有有效期 |
| 免审 vs 规则未命中 | 明确配置 need_approval=FALSE | 五级匹配全不中，系统不知道该谁审 | 后者若默认免审就是「不知道就放行」 |

### 1.5 模块目标

| 编号 | 目标 | 可度量指标 |
| --- | --- | --- |
| G-01 | 审批申请接收吞吐与延迟达标 | P-01 P95 ≤ 200ms |
| G-02 | 审批进度查询低延迟 | P-02 P95 ≤ 500ms |
| G-03 | 审批链解析准确且可解释 | 五级匹配命中即停，全不中必报错不默认放行 |
| G-04 | 审批留痕不可篡改 | REVOKE UPDATE, DELETE + 触发器双防线，验收项验证 |
| G-05 | 断点 A / C 可观测 | 执行确认四态，回执超时告警率可统计 |
| G-06 | 待办不丢 | 待办加载失败时必须显式提示，绝不显示「暂无待办」 |
| G-07 | 审批人有效性实时校验 | G-3 闸门，不允许以上次快照为准 |

| 编号 | 依赖对象 | 依赖内容 | 断供后果 | 降级方式 |
| --- | --- | --- | --- | --- |
| D-01 | M02 认证 | 令牌校验（U-01） | 无法识别操作人 | 全部动作失败，返回 503，绝不降级为放行 |
| D-02 | M02 权限 | 权限判定（U-06）、数据范围（U-07） | 无法判断可操作性 | 返回 degraded=true 且拒绝敏感动作 |

| D-04 | M01 主数据 | 科室树（U-10）、职工信息 | 链解析拿不到部门负责人 | 返回"2004008" 审批人无法解析 |

| D-06 | 申请方 | 执行回执 | 执行确认停在 WAITING | 超时置 TIMEOUT 并告警，不改结论 |

### 3.2 审批实例状态机

```
                         ┌─────────┐
                         │  DRAFT  │
                         └────┬────┘
                              │ 提交
                              ▼
                         ┌─────────┐
          ┌──────────────│ PENDING │──────────────┐
          │              └────┬────┘              │
          │ 撤回              │ 一级通过           │ 任一级驳回
          │                   ▼                   │
          │              ┌────────────┐           │
          │              │ APPROVING  │           │
          │              └─────┬──────┘           │
          │                    │ 全部通过          │
          │                    ▼                  ▼
          │              ┌──────────┐       ┌──────────┐
          │              │ APPROVED │       │ REJECTED │
          │              └────┬─────┘       └──────────┘
          │         ┌─────────┴──────────┐
          │ 回执成功│                    │回执失败
          │         ▼                    ▼
          │    ┌──────────┐      ┌───────────────────┐
          │    │COMPLETED │      │APPROVED_BUT_FAILED│
          │    └──────────┘      └───────────────────┘
          │
          │              ┌───────────┐
          └─────────────►│ CANCELLED │
                         └───────────┘

  全体审批人不可用 ─────────► ┌─────────┐
                             │ TIMEOUT │ (管理员介入，非终态)
                             └─────────┘
```

| 编号 | 流转 | 触发条件 | 后置动作 | 错误码 |
| --- | --- | --- | --- | --- |
| T-01 | DRAFT → PENDING | 申请人提交 | 激活第 1 级节点，写留痕 | — |
| T-02 | PENDING → APPROVING | 第 1 级通过且还有后续级 | 激活下一级节点 | — |
| T-03 | PENDING / APPROVING → APPROVED | 全部节点通过 | 写 approved_at，通知申请方 | — |
| T-04 | PENDING / APPROVING → REJECTED | 任一级驳回 | 后续节点置 SKIPPED，通知申请方 | — |
| T-05 | APPROVED → COMPLETED | 回执 SUCCESS | 写 exec_confirm_status=CONFIRMED | — |
| T-06 | APPROVED → APPROVED_BUT_FAILED | 回执 FAILED | 写 exec_fail_reason，**推送申请人** | — |
| T-07 | PENDING → CANCELLED | 申请人撤回 | 置节点 SKIPPED，通知审批人 | "2004020" |
| T-08 | PENDING → TIMEOUT | 全体审批人不可用 | 转管理员，写 timeout_at | "2004021" |
| T-09 | 任一状态尝试回到 `DRAFT` | — | **审批实例不允许回到 DRAFT** | "2004012" |

**T-09 的禁止理由**：允许回退到 DRAFT 意味着「这条审批曾经通过过」这件事可以被抹掉。撤回是从 `PENDING` 直接到 `CANCELLED`（留痕保留），不是回退到草稿。

### 3.3 审批节点状态机

```
   ┌─────────┐  前序全通过  ┌─────────┐  同意   ┌──────────┐
   │ WAITING │─────────────►│ PENDING │────────►│ APPROVED │
   └─────────┘              └────┬────┘         └──────────┘
                                 │ 驳回
                                 ▼
                            ┌──────────┐
                            │ REJECTED │
                            └──────────┘
                                 │ 后续节点
                                 ▼
                            ┌─────────┐
                            │ SKIPPED │
                            └─────────┘

   PENDING ──转办──► ┌─────────────┐
                     │ TRANSFERRED │ (原节点留痕，新节点取代)
                     └─────────────┘

   超时不改变状态：PENDING + timeout_at 非空 + now() > timeout_at
```

| 编号 | 流转 | 条件 | 说明 |
| --- | --- | --- | --- |
| N-01 | WAITING → PENDING | 前序节点全部 APPROVED / SKIPPED | 写 activated_at，计算 timeout_at |
| N-02 | PENDING → APPROVED | 审批人同意（会签 ALL 需全员同意） | 写 acted_at、acted_by |
| N-03 | PENDING → REJECTED | 审批人驳回 | 后续全部节点置 SKIPPED |
| N-04 | PENDING → TRANSFERRED | 审批人转办 | 写 transferred_from_staff_id，新节点替换 |
| N-05 | WAITING → SKIPPED | 免审 / 会签任一已满足 / 前序驳回终止 | 写 skip_reason，三种成因必须区分 |
| N-06 | PENDING → PENDING（加签） | 审批人加签 | 新建节点，原节点保持 PENDING |

**会签 ANY 的 SKIPPED 语义**：`approve_mode = ANY` 时，只要有一个审批人同意，同级其余节点置 SKIPPED 且 `skip_reason = 'ANY_SATISFIED'`。若不区分 `skip_reason`，统计会把「因任一同意而跳过」与「因驳回而终止」都算成 SKIPPED，得出「大量节点被跳过」的错误结论。

### 3.4 关键业务流程

#### 3.4.1 审批申请与链解析（M20-CALC-01）

```
申请人 ──P-01──► M20-04
                    │
                    ├─ 1. 幂等检查 (biz_type, biz_no)
                    ├─ 2. 读链缓存 m20:apr:chain:{biz_type}:{dept_id}
                    │     命中 ──► 用缓存的链形状
                    │     未命中 ──► 五级匹配 ──► 写缓存
                    ├─ 3. 解析 approver_type 得具体审批人
                    │     ROLE ──► U-11 staff-by-roles
                    │     DEPT_HEAD ──► U-10 dept-tree
                    │     SPECIFIC ──► rule_node.approver_id
                    │     APPLICANT_SUPERIOR ──► U-10 + M01-02
                    ├─ 4. 0 人 ──► 返回 2004008，不自动跳过
                    ├─ 5. need_approval=FALSE ──► 直接 APPROVED 免审
                    └─ 6. 建实例 + 批量建节点 + 激活第 1 级 + 写留痕 + 推待办
```

```

                    │

### 3.5 计算模型

#### 3.5.1 M20-CALC-01 五级匹配

**公式**：按 `match_level` 从 1 到 5 逐级尝试，同一级内按 `match_priority` 升序取第一条命中规则，命中即停。

| 级别 | 匹配条件 | 说明 |
| --- | --- | --- |
| 1 | `biz_type` 精确 + 金额精确区间 + 科室精确 | 最具体 |
| 2 | `biz_type` + 金额区间 + 科室 ALL | 中等具体 |
| 3 | `biz_type` + 金额区间 ALL + 科室 ALL | 较通用 |
| 4 | `biz_no` 前缀默认链 | 按单据类型兜底 |
| 5 | `biz_type` 默认链 | 最后兜底 |

**边界**：

- 金额区间为左闭右开 `[amount_min, amount_max)`，避免边界值同时命中两条规则。
- 五级全不中 → 返回 `"2004002"`，**绝不默认免审**。
- 第 1 级解析出 0 人 → 返回 `"2004008"`，**绝不自动跳过**。
- 同一级同一 `match_priority` 出现两条命中 → 返回 `"2004003"`（规则冲突），要求管理员处理。

**算例**：业务类型 `M10_ORDER_AMEND`，金额 `400.00`，科室 12。

| 规则 | match_level | 金额区间 | 科室 | 是否命中 | 说明 |
| --- | --- | --- | --- | --- | --- |
| R-101 | 1 | [0, 500) | 12 | 命中 | 命中即停 |
| R-102 | 1 | [500, 2000) | 12 | 不命中 | 金额不匹配 |
| R-103 | 2 | [0, 2000) | ALL | 未参与 | 更低优先级 |
| R-104 | 3 | ALL | ALL | 未参与 | 兜底规则 |

R-101 定义两级：`node_seq=1` 审批人来源 `ROLE(DEPT_MANAGER)`，`node_seq=2` 审批人来源 `ROLE(FINANCE_MANAGER)`。**结果：2 级审批。**

#### 3.5.2 M20-CALC-02 审批超时率

**公式**：

```
审批超时率 = 超时节点数 / 已终结节点数
```

- **分子**：`acted_at > activated_at + timeout_hours` 的节点数（在已终结节点范围内）。
- **分母**：`node_status IN ('APPROVED','REJECTED','SKIPPED','TRANSFERRED')` 的节点数，**不含仍在 PENDING 的节点**。
- **分母为 0** 时返回 `NULL` + `data_quality = 'NO_DATA'`，**不得返回 0%，更不得返回 100%**。

**算例**：某月已终结节点 1200 个，其中超时 96 个。

```
审批超时率 = 96 / 1200 = 0.080000 = 8.00%
```

**反例（错误算法）**：若分母误含 140 个仍在 PENDING 的节点：

```
96 / 1340 = 0.071642 = 7.16%
```

两者相差 **0.84 个百分点**，且方向是「审批越慢、超时率看起来越低」——因为堆积的未终结节点把分母撑大了。这正是必须显式排除 PENDING 的原因。

**默认超时时长**：`NORMAL` 24 小时、`URGENT` 4 小时、`EMERGENCY` 1 小时。

#### 3.5.3 执行确认超时判定

**公式**：

```
回执超时 = (status = 'APPROVED' AND exec_confirm_status = 'WAITING'
            AND now() > approved_at + receipt_timeout_minutes)
```

默认 `receipt_timeout_minutes = 60`。超时后 `exec_confirm_status` 置 `TIMEOUT`，但**实例状态仍是 APPROVED**——因为系统确实不知道业务到底执行了没有，硬判成功或失败都是编造事实。

#### 3.5.4 待办停留时长

```
pending_hours = ROUND(EXTRACT(EPOCH FROM (now() - activated_at)) / 3600, 2)
```

用于工作台的紧急度排序与超时预警。**注意：这是展示值，不参与超时率计算**——超时率的分子用 `timeout_hours` 判定，不用这个展示值。

**每页共同的移动端考虑**，后续各页不再重复：

1. **四个质量标记必须可见**：任何 `degraded = true` 或 `data_quality = CACHED` 的页面，页面顶部必须出现一条可见提示条，内容含数据截止时刻 `as_of`。没有提示的降级等同于欺骗。
2. **查询失败的列表绝不显示「暂无待办」**：列表为空时必须是「查询成功且确实为空」那一种事实。查询失败时页面显示「加载失败，请下拉重试」，不得渲染空态插画。这一条在 P02 有强化说明。
3. **分页统一**：`page_size` 默认 20、上限 100、`has_more` 必填、`total` 允许为 `null`。下拉刷新是唯一刷新手势，不做无限滚动。
4. **金额与时间格式**：金额一律两位小数带千分位；时间一律显示到分钟并带时区标记；相对时间（「3 小时前」）只在同一自然日内使用，跨日必须显示绝对时间。
5. **离线只读**：本子模块所有写操作（同意、驳回、转办、加签、撤回、催办、回执补录）在离线态一律禁用按钮并提示「当前无网络，请恢复后操作」，不做本地乐观写入。理由见 §8.7。

```

**关键：底部那一条不是「暂无待办」，是「加载失败」。**

| 编号 | 交互 | 校验与规则 |
| --- | --- | --- |
| I-P02-01 | 切换紧急度/业务类型筛选 | 重新请求，页码重置为 1 |
| I-P02-02 | 条目左滑 | 出现「同意」「驳回」快捷操作，点击后必须二次确认 |
| I-P02-03 | 点击条目正文 | 跳转 P03 详情 |
| I-P02-04 | 下拉刷新 | 重新请求；刷新中列表保持旧数据但顶部显示「刷新中」 |
| I-P02-05 | 列表到底 | 显示「没有更多了」，仅当 `has_more = false` 时 |

**校验规则：**

| 编号 | 规则 | 不满足时 |
| --- | --- | --- |
| V-P02-01 | **查询失败时列表必须渲染为「加载失败」态，不得渲染为空态** | 视为严重缺陷：管理者会以为批完了就离开，单据静默超时 |
| V-P02-02 | 快捷「同意」必须二次确认并展示单据关键字段 | 防止左滑误触批量放行 |
| V-P02-03 | 列表条目点击后必须再校验一次 G-3 | 列表数据可能已过期，操作以详情页实时校验为准 |
| V-P02-04 | `record_count = 0` 与 `degraded = true` 同时出现 | 必须同时显示「当前可查部分无待办」与「部分来源不可用」两句话 |

**异常态：**

| 场景 | 页面表现 |
| --- | --- |
| 查询成功、确实无待办 | 空态插画 + 「暂无待审批单据」，允许 |
| 查询失败 | 「待办加载失败，请下拉重试」，**禁止**空态插画 |
| 部分来源降级 | 有数据则显示数据 + 顶部提示条；无数据则显示「当前可查部分无待办」+ 提示条 |
| 审批权限被撤销 | 403 并提示「审批权限已变更，请联系管理员」 |

**移动端特殊考虑：** 列表页不预取详情（详情含金额与业务摘要，提前取会放大泄露面）。左滑操作必须支持「滑出但不执行」，松开即回弹。

### 5.4 P03 审批详情与操作

**页面定位：** 单个审批实例的完整视图与操作入口。

**使用角色：** 当前节点审批人（可操作）、申请人（只读）、抄送人（只读）、管理员（可操作）。

**数据来源：** `GET /internal/v1/m20/approval/{no}`（P-02，本模块自提供）、`m20_apr_node`、`m20_apr_action_log`、`m20_apr_receipt`；业务摘要经申请方接口按需拉取。

**布局：**

```
+--------------------------------------------------+
| < 审批详情                        SP202611070001 |
+--------------------------------------------------+
| 状态: 审批中          紧急        第 1/2 级      |
| 业务: 配镜订单改单   单号 GD2026102800033        |
| 金额: 400.00 元     申请人: 王医生 眼科门诊      |
| 事由: 顾客要求更换镜架                           |
+--------------------------------------------------+
| 审批链                                           |
|  1. 店长审批    陈店长     待办                  |
|  2. 财务审批    —          未开始                |
+--------------------------------------------------+
| 留痕                                             |
|  10:09 王医生 提交申请                           |
+--------------------------------------------------+
| [ 驳回 ]  [ 转办 ]  [ 加签 ]   [ 同意 ]          |
+--------------------------------------------------+
```

**交互与校验：**

| 编号 | 交互 | 校验与规则 |
| --- | --- | --- |
| I-P03-01 | 同意 | 二次确认 → `POST /{no}/approve`，携带 `idempotency_key` |
| I-P03-02 | 驳回 | 弹出必填原因框（1~500 字）→ `POST /{no}/reject` |
| I-P03-03 | 转办 | 选择目标人（`staff-by-roles` 结果）→ `POST /{no}/transfer` |
| I-P03-04 | 加签 | 选择目标人 + 必填理由 → `POST /{no}/add-sign` |
| I-P03-05 | 撤回（申请人可见） | `POST /{no}/cancel`，仅 `PENDING`/`APPROVING` 可撤回 |
| I-P03-06 | 补录回执（申请人可见） | `APPROVED` 状态下若申请方漏发回执，可由申请人手工补录 |

**校验规则：**

| 编号 | 规则 | 错误码 |
| --- | --- | --- |
| V-P03-01 | 操作前实时执行 G-3 闸门（U-05 + U-11） | `"2004010"` |
| V-P03-02 | 驳回原因必填且 1~500 字，超长拒绝不截断 | `"2004016"` |
| V-P03-03 | 转办对象必须在岗且有该业务审批权限 | `"2004011"` |
| V-P03-04 | 加签后仍由本节点原审批人做最终决定（加签是征询不替代） | — |
| V-P03-05 | 非当前节点审批人操作 | `"2004009"` |
| V-P03-06 | `COMPLETED` / `REJECTED` / `CANCELLED` 终态不可操作 | `"2004012"` |

**异常态：**

| 场景 | 页面表现 |
| --- | --- |
| 实例状态查询失败 | 显示「状态查询失败」并禁用全部操作按钮，**不得默认显示「未审批」** |
| 审批链降级 | 链显示「部分节点信息不可用」+ `as_of` |
| 已被他人抢先处理 | 409 并提示「该单据已被处理」，自动刷新 |

**移动端特殊考虑：** 「同意」按钮不做左滑快捷的唯一通道，详情页必须是显式按钮 + 二次确认。金额必须与业务单号同屏，避免批错单。

**移动端特殊考虑：** 本页是申请人唯一会主动打开的页面，`APPROVED_BUT_FAILED` 的条目必须置顶并高亮，不得被普通条目淹没。

### 5.7 P06 审批规则配置（核心）

**页面定位：** 审批链规则的增删改查与发布。

**使用角色：** 审批管理员（`m20:apr:rule:*`）。

**数据来源：** `m20_apr_rule`、`m20_apr_rule_node`。

**布局：**

```
+--------------------------------------------------+
| < 审批规则配置                        [+ 新建]    |
+--------------------------------------------------+
| 搜索: [ 业务类型 或 规则编码 ]                    |
+--------------------------------------------------+
| R-101 配镜订单改单  科室:眼科门诊  金额[0,500)   |
|       级别1  节点2  状态 已启用          免审 否 |
| R-103 配镜订单改单  科室:全部     金额[0,2000)  |
|       级别2  节点1  状态 已启用          免审 否 |
+--------------------------------------------------+
| 规则变更影响 128 个审批链缓存，发布后立即失效     |
+--------------------------------------------------+
```

**交互与校验：**

| 编号 | 交互 | 校验与规则 |
| --- | --- | --- |
| I-P06-01 | 新建规则 | 填 `biz_type`、金额区间、科室范围、`match_level`、`match_priority` |
| I-P06-02 | 编辑节点 | 增删节点、调整 `node_seq`、设 `approve_mode`、`timeout_hours` |
| I-P06-03 | 发布 | `POST /rules/{rule_code}/publish`，发布后主动失效该 `biz_type` 的审批链缓存 |
| I-P06-04 | 停用 | `effective_status` 置 `INACTIVE`，不删除 |
| I-P06-05 | 试算 | 输入 `biz_type` + 金额 + 科室，即时返回命中规则与解析结果 |

**校验规则：**

| 编号 | 规则 | 错误码 |
| --- | --- | --- |
| V-P06-01 | `match_level` 必须 1~5 | `"2004019"` |
| V-P06-02 | `amount_max` 必须大于 `amount_min`（左闭右开） | `"2004020"` |
| V-P06-03 | `dept_scope = SPECIFIC` 时 `dept_ids` 非空 | `"2004021"` |
| V-P06-04 | `node_seq` 必须从 1 连续 | `"2004022"` |
| V-P06-05 | 删除规则前必须检查是否仍有 `ACTIVE` 版本在用 | `"2004023"` |
| V-P06-06 | 同一 `biz_type` 下 `match_level` + 金额区间 + 科室完全重叠的两条规则 | 警告并要求确认 |

**异常态：** 发布失败必须整条规则回滚（草稿态），不得出现「节点发布了一半」。

**移动端特殊考虑：** 规则配置在移动端只做「查看 + 停用 + 简单编辑」，复杂节点编排引导到 PC 端；试算结果必须显示命中的完整节点清单。

### 6.2 统一响应与四质量标记

所有接口统一返回：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "trace_id": "7f3a1c2e"
}
```

`code = 0` 表示成功；系统故障一律返回 5xx 且 `code` 非 0，**不得用 200 + 非 0 code 表达故障**。

所有 `data` 必须携带四个质量标记：

| 标记 | 类型 | 含义 |
| --- | --- | --- |
| degraded | BOOLEAN | 是否有来源不可用；即使为 false 也必须出现 |
| degraded_sources | ARRAY | 不可用来源与原因，元素形如 `{"source":"M02_PERM","reason":"TIMEOUT"}` |
| data_quality | STRING | REALTIME / CACHED / PARTIAL / UNKNOWN |
| as_of | STRING | 数据截止时刻，**不是请求时刻** |

分页响应的 `data` 另含 `items`、`page_no`、`page_size`、`total`、`has_more`、`record_count`。

### 6.3 接口详述

#### API-01 审批工作台聚合

**路径：** `GET /api/v1/m20/approval/workbench`
**权限：** `m20:apr:workbench:view`
**幂等：** 读接口，天然幂等。

**请求参数：**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| staff_id | BIGINT | 是 | 从令牌解析，不接受客户端传入 |
| dept_id | BIGINT | 否 | 部门筛选 |

**响应：**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "pending_count": 7,
    "my_instance_count": 3,
    "overdue_count": 1,
    "longest_wait": [
      {"approval_no": "SP202611070001", "biz_type": "M10_DRUG_PURCHASE",
       "biz_title": "眼科药品临时采购", "urgency": "URGENT", "wait_hours": 51}
    ],
    "degraded": false,
    "degraded_sources": [],
    "data_quality": "CACHED",
    "as_of": "2026-11-07T10:09:35+08:00"
  },
  "trace_id": "7f3a1c2e"
}
```

**业务逻辑：**

1. 从令牌取 `staff_id`，不接受客户端传入。
2. 读 Redis `m20:apr:pending:{staff_id}`（TTL 60 秒）；命中则 `data_quality = CACHED`，`as_of` 取缓存写入时刻。
3. 未命中则查 `m20_apr_node`（`approver_id = staff_id AND node_status = 'PENDING'`）与 `m20_apr_instance`，聚合计三个计数与最久等待 TOP 5。
4. 调 U-05 `permission-context` 判定查看权限；失败时按 §8.4 降级，`degraded = true`、`data_quality = PARTIAL`。
5. 结果写回 Redis，`as_of` 取本次查询完成时刻。
6. **计数查询失败一律返回 `null` 并置 `degraded = true`，绝不返回 0。**

**错误码：** `"2004001"` `"2004031"` `"2004018"`

**调用上游：** U-05 `permission-context`

#### API-05 同意

**路径：** `POST /api/v1/m20/approval/instances/{approval_no}/approve`
**权限：** `m20:apr:instance:approve`
**幂等：** `(biz_type='M20_APPROVAL_ACTION', idempotency_key)` 唯一，24 小时。

**请求参数：**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| approval_no | STRING | 是 | 路径参数 |
| node_seq | INTEGER | 是 | 本次操作的节点序号，用于并发校验 |
| opinion | STRING | 否 | 审批意见，最长 500 |
| idempotency_key | STRING | 是 | 客户端生成，重复提交返回首次结果 |

**响应：**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "approval_no": "SP202611070001",
    "node_seq": 1,
    "node_status": "APPROVED",
    "instance_status": "APPROVING",
    "next_node_seq": 2,
    "next_approver_ids": [1003],
    "idempotent_replay": false,
    "degraded": false,
    "degraded_sources": [],
    "data_quality": "REALTIME",
    "as_of": "2026-11-07T10:15:00+08:00"
  },
  "trace_id": "7f3a1c2e"
}
```

**业务逻辑：**

1. 按幂等键查重；命中且请求体一致返回首次结果并置 `idempotent_replay = true`；不一致返回 `"2004013"`。
2. **执行 G-3 闸门**：调 U-05 `permission-context` 判定该用户是否仍有此业务审批权限，调 U-11 `staff-by-roles` 校验角色有效性。任一失败即拒绝，**不得以上次快照为准**。
3. 校验操作人是当前 `node_status = 'PENDING'` 节点的 `approver_id`；不是则 `"2004009"`。
4. 校验 `node_seq` 与当前激活节点一致，防止并发重复；不一致返回 `"2004012"`。
5. 在事务内 `SELECT ... FOR UPDATE` 锁实例行，更新节点为 `APPROVED`，写 `m20_apr_action_log`。
6. 会签 `ALL`：本节点全部审批人通过才推进；会签 `ANY`：任一通过即推进，其余置 `SKIPPED` 且 `skip_reason = 'ANY_SATISFIED'`。
7. 若非最后一级，激活下一节点（`WAITING → PENDING`），调 M20-08 写接口推送待办。
8. 若为最后一级，实例置 `APPROVED`，置 `exec_confirm_status = 'WAITING'`，启动回执超时计时，并发布 `m20.approval.completed`。
9. 写审计 U-09。

**错误码：** `"2004009"` `"2004010"` `"2004012"` `"2004013"` `"2004005"`

**调用上游：** U-05 `permission-context`、U-11 `staff-by-roles`、U-09 `audit/record`、M20-08 写接口 API-09

async def _next_approval_no(db: AsyncSession) -> str:
    """原子生成审批单号：SP + yyyyMMdd + 4 位当日流水。

    必须走数据库序列，绝不在应用层 SELECT max()+1——并发下必然重号，
    重号意味着两条不同审批共用同一个号，P-02 查询会返回错误的那一条。

    row = await db.execute(
        text(
            "INSERT INTO m20_apr_approval_seq (biz_date, last_seq) "
            "VALUES (CAST(:d AS DATE), 1) "
            "ON CONFLICT (biz_date) DO UPDATE "
            "SET last_seq = m20_apr_approval_seq.last_seq + 1 "
            "RETURNING last_seq"
        ),
        {"d": _now().strftime("%Y-%m-%d")},
    )
    seq = int(row.scalar_one())
    return "SP" + _now().strftime("%Y%m%d") + f"{seq:04d}"


async def _sha256_payload(payload: dict[str, Any]) -> str:
    import hashlib
    import json

    raw = json.dumps(payload, sort_keys=True, ensure_ascii=False, default=str)
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()

    biz_no: str,
    amount: Decimal | None,
    dept_id: int | None,
) -> tuple[M20AprRule, list[M20AprRuleNode]]:
    """M20-CALC-01 五级匹配：命中即停，五级全不中抛 2004002。"""
    stmt = (
        select(M20AprRule)
        .where(
            M20AprRule.biz_type == biz_type,
            M20AprRule.effective_status == "ACTIVE",
        )
        .order_by(M20AprRule.match_level.asc(), M20AprRule.match_priority.asc())
    )
    rules = list((await db.execute(stmt)).scalars())
    for rule in rules:
        if rule.amount_min is not None and (amount is None or amount < rule.amount_min):
            continue
        if rule.amount_max is not None and (amount is not None and amount >= rule.amount_max):
            continue
        if rule.dept_scope == "SPECIFIC":
            if dept_id is None or dept_id not in (rule.dept_ids or []):
                continue
        nodes = list(
            (
                await db.execute(
                    select(M20AprRuleNode)
                    .where(
                        M20AprRuleNode.rule_code == rule.rule_code,
                        M20AprRuleNode.rule_version == rule.rule_version,
                        M20AprRuleNode.is_deleted.is_(False),
                    )
                    .order_by(M20AprRuleNode.node_seq.asc())
                )
            ).scalars()
        )
        return rule, nodes
    raise ChainNotConfigured()


class ChainNotConfigured(Exception):
    """五级匹配全不中。绝不默认免审。"""


class ApprovalService:
    def __init__(self, db: AsyncSession) -> None:
        self.db = db
        self.m02 = M02Client()
        self.msg = M20MsgClient()

    async def _assert_g3(self, staff_id: int, biz_type: str) -> None:
        """G-3 审批人有效性闸门：实时校验权限与在岗，失败即拒绝。

        依据是 U-05 permission-context + U-11 staff-by-roles，
        与「能不能用移动端」是两件事，不使用 is_mobile_user。
        """
        ctx = await self.m02.get_permission_context(staff_id)
        if not ctx.is_active:
            raise ApproverInvalid()
        if ctx.has_denied("m20:apr:instance:approve"):
            raise ApproverInvalid()

    async def approve(
        self,
        approval_no: str,
        staff: Any,
        body: ApprovalActionRequest,
        device_id: str | None,
    ) -> ApprovalActionResponse:
        instance = await self._load_instance(approval_no)
        await self._assert_g3(staff.staff_id, instance.biz_type)

        node = await self._load_active_node(instance.id)
        if node.approver_id != staff.staff_id:
            raise NotCurrentApprover()
        if node.node_seq != body.node_seq:
            raise StaleNode()

        node.node_status = "APPROVED"
        node.acted_at = _now()
        node.last_approver_id = staff.staff_id
        await self._write_log(
            instance, staff.staff_id, "APPROVE", body.opinion, device_id
        )
        next_node = await self._advance(instance)
        await self.db.commit()
        return ApprovalActionResponse(
            approval_no=instance.approval_no,
            node_seq=node.node_seq,
            node_status=node.node_status,
            instance_status=instance.status,
            next_node_seq=next_node.node_seq if next_node else None,
            next_approver_ids=[next_node.approver_id] if next_node else [],
            **quality_block([], _now()),
        )

    async def _load_instance(self, approval_no: str) -> M20AprInstance:
        row = await self.db.execute(
            select(M20AprInstance).where(M20AprInstance.approval_no == approval_no)
        )
        instance = row.scalar_one_or_none()
        if instance is None:
            raise InstanceNotFound()
        return instance

    async def _load_active_node(self, instance_id: int) -> M20AprNode:
        row = await self.db.execute(
            select(M20AprNode)
            .where(
                M20AprNode.instance_id == instance_id,
                M20AprNode.node_status == "PENDING",
            )
            .with_for_update()
        )
        return row.scalar_one()

    async def _advance(self, instance: M20AprInstance) -> M20AprNode | None:
        row = await self.db.execute(
            select(M20AprNode)
            .where(
                M20AprNode.instance_id == instance.id,
                M20AprNode.node_status == "WAITING",
            )
            .order_by(M20AprNode.node_seq.asc())
            .limit(1)
        )
        nxt = row.scalar_one_or_none()
        if nxt is None:
            instance.status = "APPROVED"
            instance.exec_confirm_status = "WAITING"
            instance.finished_at = _now()
            return None
        nxt.node_status = "PENDING"
        nxt.activated_at = _now()
        instance.status = "APPROVING"
        await self.msg.push_todo(
            staff_id=nxt.approver_id,
            source="M20_APPROVAL",
            biz_type=instance.biz_type,
            biz_id=instance.id,
            biz_title=instance.biz_title or instance.biz_type,
            biz_no=instance.approval_no,
        )
        return nxt

    async def submit_receipt(
        self, approval_no: str, staff: Any, body: ReceiptRequest
    ) -> ReceiptResponse:
        instance = await self._load_instance(approval_no)
        if instance.status != "APPROVED":
            raise InvalidStatus()
        try:
            self.db.add(
                M20AprReceipt(
                    instance_id=instance.id,
                    exec_result=body.exec_result,
                    exec_fail_reason=body.exec_fail_reason,
                    executed_at=body.executed_at or _now(),
                    receipt_status="ACCEPTED",
                )
            )
            if body.exec_result == "SUCCESS":
                instance.status = "COMPLETED"
                instance.exec_confirm_status = "CONFIRMED"
            else:
                instance.status = "APPROVED_BUT_FAILED"
                instance.exec_confirm_status = "FAILED"
                instance.exec_fail_reason = body.exec_fail_reason
            await self.db.commit()
        except IntegrityError:
            await self.db.rollback()
            instance = await self._load_instance(approval_no)
            return ReceiptResponse(
                approval_no=instance.approval_no,
                instance_status=instance.status,
                exec_confirm_status=instance.exec_confirm_status,
                receipt_replay=True,
                **quality_block([], _now()),
            )
        return ReceiptResponse(
            approval_no=instance.approval_no,
            instance_status=instance.status,
            exec_confirm_status=instance.exec_confirm_status,
            receipt_replay=False,
            **quality_block([], _now()),
        )

    async def _write_log(
        self,
        instance: M20AprInstance,
        operator_id: int,
        action_type: str,
        opinion: str | None,
        device_id: str | None,
    ) -> None:
        self.db.add(
            M20AprActionLog(
                instance_id=instance.id,
                approval_no=instance.approval_no,
                action_type=action_type,
                operator_id=operator_id,
                opinion=opinion,
                acted_at=_now(),
                device_id=device_id,
            )
        )


class ApprovalInternalService:
    """契约 P-01 / P-02 / P-07 的内部实现。"""

    def __init__(self, db: AsyncSession) -> None:
        self.db = db
        self.m02 = M02Client()
        self.msg = M20MsgClient()

    async def apply(self, body: ApplyRequest, service_id: str) -> ApplyResponse:
        sidem_key = await _sha256_payload(body.model_dump(mode="json"))
        existing = await self._find_unfinished(body.biz_type, body.biz_no)
        if existing is not None:
            return self._to_apply_response(existing, replay=True)

        try:
            rule, rule_nodes = await resolve_chain(
                self.db, self.m02, body.biz_type, body.biz_no,
                body.amount, body.applicant_dept_id,
            )
        except ChainNotConfigured:
            raise RuleNotConfigured()

        approval_no = await _next_approval_no(self.db)
        instance = M20AprInstance(
            approval_no=approval_no,
            biz_type=body.biz_type,
            biz_no=body.biz_no,
            biz_title=body.biz_title,
            amount=body.amount,
            reason=body.reason,
            applicant_id=body.applicant_id,
            applicant_dept_id=body.applicant_dept_id,
            urgency=body.urgency,
            rule_code=rule.rule_code,
            rule_version=rule.rule_version,
            total_node_count=len(rule_nodes),
            payload_json=body.payload_json,
            payload_hash=sidem_key,
        )
        if not rule.need_approval:
            instance.status = "APPROVED"
            instance.exec_confirm_status = "WAITING"
            instance.finished_at = _now()
            self.db.add(instance)
            await self.db.commit()
            return self._to_apply_response(instance, replay=False)

        instance.status = "PENDING"
        instance.exec_confirm_status = "WAITING"
        self.db.add(instance)
        await self.db.flush()

        for seq, rn in enumerate(rule_nodes, start=1):
            approvers = await self.m02.resolve_approvers(rn, body.applicant_dept_id)
            if not approvers and seq == 1 and not rn.skip_when_absent:
                await self.db.rollback()
                raise ApproverUnresolvable()
            self.db.add(
                M20AprNode(
                    instance_id=instance.id,
                    node_seq=seq,
                    node_name=rn.node_name,
                    approver_id=approvers[0] if approvers else None,
                    last_approver_id=approvers[0] if approvers else None,
                    node_status="PENDING" if seq == 1 else "WAITING",
                    approve_mode=rn.approve_mode,
                    timeout_hours=rn.timeout_hours,
                    activated_at=_now() if seq == 1 else None,
                )
            )
        await self.db.commit()

        first = await self._load_active_node(instance.id)
        await self.msg.push_todo(
            staff_id=first.approver_id,
            source="M20_APPROVAL",
            biz_type=instance.biz_type,
            biz_id=instance.id,
            biz_title=instance.biz_title or instance.biz_type,
            biz_no=instance.approval_no,
        )
        return self._to_apply_response(instance, replay=False)

    async def _find_unfinished(
        self, biz_type: str, biz_no: str
    ) -> M20AprInstance | None:
        row = await self.db.execute(
            select(M20AprInstance).where(
                M20AprInstance.biz_type == biz_type,
                M20AprInstance.biz_no == biz_no,
                M20AprInstance.status.notin_(TERMINAL_STATUSES),
            )
        )
        return row.scalars().first()

    async def _load_active_node(self, instance_id: int) -> M20AprNode:
        row = await self.db.execute(
            select(M20AprNode).where(
                M20AprNode.instance_id == instance_id,
                M20AprNode.node_status == "PENDING",
            )
        )
        return row.scalar_one()

    def _to_apply_response(
        self, instance: M20AprInstance, replay: bool
    ) -> ApplyResponse:
        return ApplyResponse(
            approval_no=instance.approval_no,
            status=instance.status,
            current_node_seq=instance.current_node_seq,
            current_approver_ids=[],
            need_approval=instance.status != "APPROVED" or instance.rule_code is not None,
            idempotent_replay=replay,
            **quality_block([], _now()),
        )

    async def get_status(self, approval_no: str, service_id: str) -> ApprovalDetailResponse:
        """P-02：两条常量级查询，不进全表扫描。"""
        row = await self.db.execute(
            select(M20AprInstance).where(M20AprInstance.approval_no == approval_no)
        )
        instance = row.scalar_one_or_none()
        if instance is None:
            raise InstanceNotFound()
        nrow = await self.db.execute(
            select(M20AprNode)
            .where(M20AprNode.instance_id == instance.id)
            .order_by(M20AprNode.node_seq.asc())
        )
        nodes = [
            ApprovalNodeOut(
                node_seq=n.node_seq,
                node_name=n.node_name,
                approver_id=n.last_approver_id or n.approver_id,
                action=n.node_status,
                acted_at=n.acted_at,
            )
            for n in nrow.scalars()
        ]
        return ApprovalDetailResponse(
            approval_no=instance.approval_no,
            biz_type=instance.biz_type,
            biz_no=instance.biz_no,
            status=instance.status,
            exec_confirm_status=instance.exec_confirm_status,
            nodes=nodes,
            approved_at=instance.finished_at,
            **quality_block([], _now()),
        )

    async def submit_receipt(
        self, approval_no: str, body: ReceiptRequest, service_id: str
    ) -> ReceiptResponse:
        svc = ApprovalService(self.db)
        return await svc.submit_receipt(
            approval_no=approval_no, staff=None, body=body
        )

## 7. 缓存与异步任务设计

### 7.1 Redis 缓存清单

本子模块所有缓存键统一前缀 `m20:apr:`。全局规则：**缓存 TTL 除审批链形状外不得超过 60 秒；缓存值必须带 `as_of`；命中缓存时 `data_quality` 必须为 `CACHED`；不得缓存任何凭据、令牌、身份证明文。**

| Key | 类型 | TTL | 内容 | 失效时机 | 容量估算 |
| --- | --- | --- | --- | --- | --- |
| m20:apr:chain:{biz_type}:{dept_id} | String | 3600s | 规则命中结果与节点定义（**不含 approver_id**） | 规则发布/停用、四级变更触发 | 约 400 个键，单值 2KB |
| m20:apr:pending:{approver_id} | ZSet | 60s | 待审批单号与紧急度分值 | 实例推进、审批完成、撤回 | 300 人 × 约 10 条 |
| m20:apr:pending_count:{approver_id} | String | 60s | 待办计数（角标） | 同 pending | 300 个键 |
| m20:apr:stats:{period}:timeout | String | 60s | 超时率分子分母 | 整点刷新 | 12 个键 |
| m20:apr:seq:{yyyymmdd} | String | 至次日 00:05 | 当日已用流水（辅助观测，**不作为发号源**） | 自然过期 | 1 个键 |
| m20:apr:urge_guard:{approval_no}:{urgee_id} | String | 1800s | 催办冷却标记 | 自然过期 | 约 200 个键 |
| m20:apr:lock:{resource}:{id} | String | 30s | 分布式锁 | 主动删或自然过期 | 瞬时少量 |

**审批链缓存是本子模块唯一超过 60 秒的缓存，理由必须写清：**

审批链解析是 P-01 的核心路径，而 P-01 的 SLA 是 **P95 ≤ 200ms**。一次完整解析要做「规则全表扫描（按 `biz_type` + `effective_status` + `match_level` 排序）→ 逐条匹配金额与科室 → 逐级解析审批人（U-10 或 U-11，各一次远程调用）」。审批人解析是网络调用，2 级链就是 2 次远程往返，在跨机房时延下已经吃掉 100ms 以上，加上规则扫描与写库，200ms 无法保证。因此规则命中结果必须缓存。

**但缓存里绝不能存 `approver_id`。** 存了具体审批人意味着：一名科主任离职后，缓存里他仍是审批人，最长一小时内由他批准的单据仍然有效——G-3 闸门形同虚设。所以缓存只存两样东西：**命中的 `rule_code` + `rule_version`**，以及**节点定义（`node_seq`、`node_name`、`approver_type`、`approver_role_code`、`approve_mode`、`timeout_hours`）**。审批人永远实时解析。

**收益核算：** 缓存命中后一次 P-01 只剩「一次 Redis GET + N 次审批人解析（N 为节点数）+ 一次事务写」。以 M10_ORDER_AMEND 的 2 级链为例，2 次 `staff-by-roles`（本地机房 5~15ms/次）+ 一次写入约 30ms，P95 可稳定在 120ms 以内。未命中时（冷启动、规则刚发布）实测约 260ms，**超出 200ms 的部分由缓存预热兜底**：规则发布后异步预热该 `biz_type` 下所有 `(biz_type, dept_id)` 组合。

**审批链缓存的四类主动失效触发**（这是共享规范要求的「至少三条」，我给四条）：

| 触发编号 | 事件 | 影响范围 | 处理 |
| --- | --- | --- | --- |
| CI-01 | 职工调岗或离职（M01-02 事件、M02 会话失效） | 该职工相关的所有链 | 按 `dept_id` 反查并删除 |
| CI-02 | 角色变更（M02 权限变更） | 涉及该角色的链 | 按 `approver_role_code` 反查并删除 |
| CI-03 | 科室负责人变更（M02 `dept-tree` 变更） | 该科室的所有链 | 删除 `m20:apr:chain:*:{dept_id}` |
| CI-04 | 审批规则变更（P06 发布或停用） | 该 `biz_type` 的所有链 | 删除 `m20:apr:chain:{biz_type}:*` |

**注意 CI-01 至 CI-03 并不保证覆盖全部情形**（例如某人的审批权限被收回，M02 未必发事件）。因此审批链缓存是「有上限的优化」而不是「事实来源」：**即使缓存命中，审批人仍然实时解析、G-3 仍然实时校验**。缓存过期导致的宽限窗口，最坏情形也只是「多解析了一次审批人」，不会产生错误审批。

### 7.2 异步任务（Celery）

落盘路径 `app/tasks/m20/apr.py`：

```python
"""M20-04 移动审批引擎 — 异步任务。"""
from __future__ import annotations

import logging
from datetime import timedelta

from celery import shared_task
from sqlalchemy import select, update

from app.db.session import session_scope
from app.models.m20.apr import M20AprInstance, M20AprNode
from app.services.m20.apr import _now

logger = logging.getLogger(__name__)


@shared_task(bind=True, max_retries=3, default_retry_delay=10)
def push_todo_retry(self, staff_id: int, payload: dict) -> None:
    """待办推送失败重试。指数退避 10s / 60s / 300s，仍失败置 FAILED 并留消息中心可见。"""
    from app.clients.m20_msg import M20MsgClient

    try:
        M20MsgClient().push_todo_sync(staff_id=staff_id, **payload)
    except Exception as exc:  # noqa: BLE001
        countdown = [10, 60, 300][min(self.request.retries, 2)]
        logger.warning(
            "待办推送失败 staff_id=%s attempt=%s err=%s", staff_id, self.request.retries, exc
        )
        raise self.retry(exc=exc, countdown=countdown)


@shared_task
def scan_receipt_timeout() -> dict:
    """扫描 APPROVED 且未回执超过阈值的实例，置 exec_confirm_status = TIMEOUT 并告警。

    关键：实例状态仍是 APPROVED。系统确实不知道业务执行了没有，
    硬判成功或失败都是编造事实。
    """
    with session_scope() as db:
        threshold = _now() - timedelta(minutes=60)
        rows = list(
            db.execute(
                select(M20AprInstance).where(
                    M20AprInstance.status == "APPROVED",
                    M20AprInstance.exec_confirm_status == "WAITING",
                    M20AprInstance.finished_at < threshold,
                )
            ).scalars()
        )
        for inst in rows:
            inst.exec_confirm_status = "TIMEOUT"
            logger.warning(
                "回执超时 approval_no=%s biz_type=%s approved_at=%s",
                inst.approval_no, inst.biz_type, inst.finished_at,
            )
        db.commit()
        return {"timed_out": len(rows)}


@shared_task
def scan_node_timeout() -> dict:
    """扫描已超时的 PENDING 节点，发超时通知。

    节点超时只通知，不改节点状态，也不把实例置 REJECTED——
    超时是「还没人批」而不是「被驳回」，折叠会让追责追错人。
    """
    with session_scope() as db:
        now = _now()
        rows = list(
            db.execute(
                select(M20AprNode).where(M20AprNode.node_status == "PENDING")
            ).scalars()
        )
        overdue = [
            n for n in rows
            if n.activated_at is not None
            and now > n.activated_at + timedelta(hours=n.timeout_hours)
        ]
        for n in overdue:
            logger.info("节点超时 approval_instance=%s node_seq=%s", n.instance_id, n.node_seq)
        return {"overdue": len(overdue)}


@shared_task
def invalidate_chain_cache(biz_type: str) -> dict:
    """审批规则变更后主动失效该 biz_type 的全部审批链形状缓存。"""
    from app.cache.redis import get_redis

    r = get_redis()
    pattern = f"m20:apr:chain:{biz_type}:*"
    deleted = 0
    for key in r.scan_iter(match=pattern, count=200):
        r.delete(key)
        deleted += 1
    return {"deleted": deleted, "biz_type": biz_type}


@shared_task
def expire_delegates() -> dict:
    """把已过结束日期的委托置 EXPIRED。不删除，保留可追溯。"""
    from app.models.m20.apr import M20AprDelegate

    with session_scope() as db:
        result = db.execute(
            update(M20AprDelegate)
            .where(
                M20AprDelegate.status == "ACTIVE",
                M20AprDelegate.end_date < _now().date(),
            )
            .values(status="EXPIRED")
        )
        db.commit()
        return {"expired": result.rowcount}
```

    """注册 M20-04 定时任务。

## 8. 业务规则与校验

### 8.1 编号与格式规则

**规则 R-8.1-01（审批单号格式，本子模块唯一权威）：**

审批单号格式为 `SP` + `yyyyMMdd` + 4 位当日流水，共 14 个字符，例如 `SP202611070001`。流水号每日 00:00 重置。

**规则 R-8.1-02（单号生成方式，强制）：**

`approval_no` 必须由数据库原子生成，方式为「当日计数表 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING last_seq`」或等价的事务内序列。**严禁在应用层使用 `SELECT max(...) + 1`**。

理由是并发下的重号：两个请求同时读到 `last_seq = 87`，各自加一写入，产生两条 `SP202611070088`。而 `approval_no` 是 P-02 的唯一查询键，重号意味着**一次查询返回错误的那一条审批**——申请方会据此认为自己的单据被批准了，而实际批准的是别人的单据。这不是格式问题，是数据正确性问题。

**规则 R-8.1-03（不透明字符串，强制，上下游共同遵守）：**

> **任何调用方（包括 M20 自己的其他子模块）均不得对 `approval_no` 做位数或格式校验。** `approval_no` 对调用方是不透明字符串，调用方只允许做三件事：保存、原样回传、原样展示。

理由：单号格式属于本子模块的内部实现。一旦调用方也做格式校验，双方就对位数形成了隐式契约，任何一方调整位数都会导致对方解析失败并报出莫名其妙的错误——而它们本来只需要把它当作一个不透明句柄使用。

同一规则适用于 `biz_no`：**M20 不得对任何上游的 `biz_no` 做位数或格式校验**。各模块单号格式不同（`GD` + 日期 + 流水、`ST` + 日期 + 流水等），且历史上调整过位数。M20 只把它当作一个不透明字符串存储与回传。

**规则 R-8.1-04（路径参数命名等价）：**

P-02 在上游文档中存在两种写法：`/internal/v1/m20/approval/{approval_no}` 与 `/internal/v1/m20/approval/{no}`。**两种写法在 HTTP 语义上完全等价**（路径参数名不参与路由匹配），本模块两者都接受。任何一方不得据此认为对方实现错误，也不得要求对方改写成另一种写法。

**规则 R-8.1-05（其他单号）：**

| 单据 | 格式 | 示例 |
| --- | --- | --- |
| 委托单 | DG + yyyyMMdd + 4 位流水 | DG202611070001 |
| 催办单 | UG + yyyyMMdd + 4 位流水 | UG202611070001 |
| 留痕号 | LG + yyyyMMdd + 6 位流水 | LG202611070002 |
| 导出单 | EX + yyyyMMdd + 4 位流水 | EX202611070001 |

流水统一走 Redis `m20:apr:code:{prefix}:{yyyymmdd}` 的 `INCR`，当日首个请求设置 TTL 至次日 00:05，不使用数据库序列拼接日期。

### 8.4 降级策略

**规则 R-8.4-01（三种合法响应形态）：** 任何接口的响应只允许是三选一——正常（200 + code 0 + 完整数据）、降级（200 + code 0 + `degraded: true` + `degraded_sources` + `as_of`）、失败（4xx 或 5xx + 非 0 code）。**不存在第四种「看起来正常但其实不完整」的形态。**

**规则 R-8.4-02（三种降级形态对应的具体做法）：**

| 依赖 | 不可用时 | 降级后的表现 |
| --- | --- | --- |
| U-05 permission-context | 超时或 5xx | 动作类接口**拒绝**（不降级）；查询类接口 `degraded = true`、`data_quality = PARTIAL` |
| U-11 staff-by-roles | 超时或 5xx | P-01 返回 "2004038"（明确失败）；P-02 返回已解析部分 + `degraded = true` |
| U-10 dept-tree | 超时或 5xx | 同 U-11 |
| M20-08 待办推送 | 超时或 5xx | 审批动作成功但待办未推送 → 进重试队列，响应 `degraded = true`，`degraded_sources` 标注 M20_MSG |
| M20-08 消息推送（催办） | 超时或 5xx | `sent = true` 且 `push_failed = true`，页面明确告知 |
| U-09 审计 | 超时或 5xx | 主流程不阻塞，写补偿队列，`degraded = true` |
| 申请方业务摘要 | 超时或 5xx | 详情页显示「业务摘要不可用」，审批链与留痕照常 |

**规则 R-8.4-03（降级方向，强制）：** 降级一律朝「更少给」而不是「多给」。审批查询失败**不得返回「未审批」**，待办查询失败**不得返回空列表**。

**规则 R-8.4-04（P-01 失败必须是明确失败）：**

M10-06 对 P-01 的降级要求是原文写死的：审批服务不可用时，改单与免费换新业务**阻断，不允许执行**，提示「审批服务不可用，请稍后提交」。

因此 P-01 在无法完成链解析与实例落库时，**必须返回明确的失败**（4xx / 5xx + 非 0 code）。**绝不允许返回一个 `approval_no` 让申请方以为单据已经交出去了**——那会让申请方停在「等审批」状态，而系统里根本没有这条审批。

**规则 R-8.4-05（`degraded` 不得表达写入失败）：** 写入类接口（P-01、同意、驳回、回执）的 `degraded` 只表达「写成功了但后续动作没完成」（如待办未推送、事件未发出）。写入本身失败必须是非 2xx + 非 0 code，不得用 200 + `degraded: true` 表达。

**规则 R-8.4-06（`as_of` 的取值）：** `as_of` 一律取数据截止时刻，取所有成功来源中最早的一个。**不得用 `now()` 填充**——那是请求时刻，不是数据时刻，用它填充会让用户以为数据是刚刚查到的。

### 8.5 恒等式与闭合校验

| 编号 | 恒等式 | 违反说明 |
| --- | --- | --- |
| E-8.5-01 | 实例 `total_node_count` = 该实例节点行数 | 不等说明节点被异常删除 |
| E-8.5-02 | 一个实例在任一时刻 `node_status = 'PENDING'` 的节点数 ≤ 1 | 由部分唯一索引保证，违反即索引失效 |
| E-8.5-03 | 实例处于 `COMPLETED` 时 `exec_confirm_status` 必为 `CONFIRMED` | 否则状态机被绕开 |
| E-8.5-04 | 实例处于 `APPROVED_BUT_FAILED` 时 `exec_fail_reason` 非空 | 否则申请人不知道怎么办 |
| E-8.5-05 | 实例处于 `APPROVED` 且 `exec_confirm_status = 'WAITING'` 时，`finished_at` 必须早于当前时刻 | 否则说明时间被写错 |
| E-8.5-06 | 超时率分母 ≥ 分子 | 否则计算错误 |
| E-8.5-07 | 实例 `finished_at` 非空当且仅当状态属于 {COMPLETED, APPROVED_BUT_FAILED, REJECTED, CANCELLED} | 非终态带完成时间说明状态机漏了清理 |

### 8.6 并发控制

本子模块存在四类并发场景，分别用不同机制处理。**先说明为什么不用同一套机制**：审批动作与实例状态是短事务但冲突概率高；链解析是长调用但只读；待办推送是外部调用不能进事务；发号是单点写入。

**并发场景一：同一节点的两个审批人同时同意（会签）。**

机制：`SELECT ... FOR UPDATE` 悲观行锁锁实例行。

理由：会签节点上的并发冲突是**必然发生**的，不是异常。两名审批人各自点「同意」，两个事务同时读到自己可以推进节点。用乐观锁会大量重试，用户看到「系统繁忙，请重试」，而实际上只要排队 30ms 就能成功。悲观锁让第二个事务等第一个提交后再读写，直接拿到「已经推进」的事实。

代价与边界：持锁时间极短（一次状态更新 + 一次留痕插入），P95 约 15ms，不会形成锁等待队列。

**并发场景二：同一审批人重复点击同意（重试）。**

机制：幂等键 `(biz_type='M20_APPROVAL_ACTION', idempotency_key)` + 24 小时唯一约束。

理由：网络超时后客户端重试是正常行为，不是并发冲突。幂等键让第二次请求返回首次结果并置 `idempotent_replay = true`，不产生第二条留痕、不推进两次节点。**这是防止「最后一级同意重发两次导致申请方执行两次」的唯一可靠手段**——仅靠行锁无法区分「同一请求的重试」与「两个不同请求」。

**并发场景三：P-01 重复提交同一业务单据。**

机制：`(biz_type, biz_no)` 查未终结实例 + 部分唯一索引兜底。

理由：申请方在超时后重试 P-01 是常态。首次查询能覆盖绝大多数情况；但如果两个请求同时到达且都查不到，两个都可能尝试插入。部分唯一索引（`WHERE status NOT IN 终态`）让第二个插入撞约束，捕获后回查返回首次结果，**不抛 500**。

**并发场景四：发号。**

机制：数据库行级原子 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`。

理由：发号必须是单点串行的，应用层无法保证。Redis `INCR` 也可行但存在 Redis 与数据库不一致的风险（Redis 丢数据后重号更危险），因此以数据库为准，Redis 只做观测。

**并发场景五（明确不做的）：离线批量审批。** 本子模块所有写操作在离线态一律禁用，不做本地乐观写入与回放。理由：离线期间审批链、审批人资质、实例状态都可能已经改变，回放需要版本校验与冲突解决，而审批是**不可撤回的业务承诺**，离线批量放行的风险远大于收益。

### 8.7 状态机不可达路径

以下状态转移在实现中必须被**显式拒绝**，不得依赖「正常不会走到」：

### 9.2 三道闸门与错误方向

审批动作必须依次通过三道闸门。**三道闸门的失败方向全部是「拒绝」，没有一道闸门允许「查不到就放行」。**

**G-1 扫码核对（仅限需扫码的审批场景）：** 患者与单据核对不一致时一律拦截。本子模块不自行核对患者身份，核对逻辑由申请方在提交前完成；M20 只接收申请方给出的核对结论，结论为不一致时拒绝推进。

**G-2 移动端接入权限：** 校验调用方会话有效、且具备 `m20:apr:*` 对应权限码。缺少权限返回 403。

**G-3 审批人有效性（本子模块最关键的一道）：**

动作前实时调用：
1. `U-05 GET /internal/v1/auth/{staff_id}/permission-context`，校验该审批人当前是否仍具备该审批环节所需的角色与科室范围；
2. `U-11 GET /internal/v1/auth/staff-by-roles`，用于链解析阶段的审批人解析（`approver_type = ROLE`）。

**G-3 的判定一律实时，不得使用任何缓存的 `approver_id`、不得使用上次成功解析的结果、不得使用会话中缓存的权限快照。** 这就是 §7.1 中「审批链缓存只存链形状、不存具体审批人」的原因。

**G-3 明确不使用 `is_mobile_user`。** 该字段在 M01-02 存在但没有任何内部接口返回它（共享规范 §9.2 V1.3 已裁决 U-12 作废）。一个在岗且有审批权限的科主任，用 PC 登录审批与用手机登录审批，**G-3 的判定结果必须完全一致**——「能不能用移动端」与「能不能批这条单据」是两件事，把前者当后者的判据会导致有权限的人被拦、或没权限的人被放。

**规则 R-9.2-01（错误方向，强制）：**

> **「查不到」与「没有权限」在安全判定上必须是同一个结果：拒绝。**

具体表现：
- U-05 返回 404（该职工不存在）→ 拒绝，返回 "2004010"；
- U-05 返回 403（无权限）→ 拒绝，返回 "2004010"；
- U-05 超时或无响应 → 拒绝，返回 "2004010"（**不是降级放行**）；
- U-05 返回 200 但权限上下文中不含所需角色 → 拒绝，返回 "2004010"。

**四种情况给同一个错误码与同一句提示**，理由是：如果「查不到」与「没有权限」给出不同提示，攻击者可以用这个差异探测某职工是否存在、是否具备某权限。而如果超时放行，那么只要让权限服务超时，就能绕过 G-3——**这会把一次服务可用性事故变成一次权限绕过事故。**

**规则 R-9.2-02（G-3 的审计留痕）：** 无论通过还是失败，G-3 的判定都必须写入 `m20_apr_action_log`，记录 `operator_staff_id`、`verify_result`、`verify_source`、`verify_at`。失败的判定同样留痕——「他试过但不被允许」和「他从没试过」是两件事。

### 9.3 数据权限

本子模块的数据权限按「参与关系」划分，而不是按科室组织树划分。理由：一条审批的可见范围由「谁发起的、谁要批的、谁被抄送的」决定，与发起人当前所在科室无关。

| 角色 | 可见范围 | 实现方式 |
| --- | --- | --- |
| 申请人 | 自己发起的实例 | `applicant_id = 当前职工` |
| 当前审批人 | 当前节点指派给自己的实例 | `m20_apr_node.approver_id = 当前职工 AND node_status = 'PENDING'` |
| 历史审批人 | 自己参与过的实例（含已转出节点） | `m20_apr_node.approver_id = 当前职工 OR last_approver_id = 当前职工` |
| 被抄送人 | 抄送给自己且未被撤回的实例 | 关联 `m20_apr_cc` |
| 审批管理员 | 全部实例（只读 + 管理动作） | 权限码 `m20:apr:instance:*` |
| 审计 | 全部实例与全部留痕（只读） | 权限码 `m20:apr:instance:log` + `export` |

**注意「历史审批人」必须包含 `last_approver_id`。** 如果只按 `approver_id` 过滤，一个把节点转办出去的人就再也看不到自己转办的那条审批了——而转办记录本应是他工作痕迹的一部分，也是事后追责时的第一手材料。

数据权限的过滤必须通过 `U-07 POST /internal/v1/perm/filter-sql` 或等价方式在 SQL 层完成，**不得先查全量再在应用层过滤**——后者一旦某条代码路径漏了过滤，就是把别人的审批暴露出去。

### 9.4 安全措施

| 编号 | 措施 | 说明 |
| --- | --- | --- |
| SEC-01 | 审批留痕不可篡改 | 权限层 `REVOKE UPDATE, DELETE` + 触发器 `trg_m20_apr_action_log_bu`，两道防线都要 |
| SEC-02 | 审批动作幂等 | `(biz_type, idempotency_key)` 唯一，防重复点击与网络重试导致重复推进 |
| SEC-03 | G-3 实时校验 | 见 §9.2，不使用任何缓存审批人 |
| SEC-04 | 单号不透明 | `approval_no` 与 `biz_no` 均不做位数或格式校验，见 §8.1 |
| SEC-05 | 内部接口服务鉴权 | API-34/35/36 校验调用方服务身份，不接受普通用户令牌 |
| SEC-06 | 事件载荷脱敏 | `m20.approval.completed` 等事件只带单号与业务标识，**不带患者姓名、手机号、身份证明文** |
| SEC-07 | 敏感操作二次确认 | 驳回、加签、撤回、规则发布四个动作由移动端做二次确认，服务端记录确认结果 |
| SEC-08 | 会话与设备 | M20-04 不持有令牌、不建第二套身份，全部委托 M02；本子模块无任何凭据存储 |
| SEC-09 | 参数注入防护 | 所有查询参数化；`U-07` 返回的过滤片段只作为预编译条件拼接，不接受字符串拼接 |
| SEC-10 | 越权探测留痕 | G-2/G-3 失败一律写审计（U-09），同一职工短时间多次失败触发告警 |
| SEC-11 | 导出审批留痕脱敏 | 导出文件不含患者身份信息，仅含单号、业务类型、审批人与时间 |
| SEC-12 | 配置修改审计 | 规则、委托、参数三类管理动作全部留痕并可追溯操作人 |

### 10.3 发布的事件

本子模块发布四个事件。**载荷一律不得包含患者姓名、手机号、身份证明文等任何身份信息**（共享规范 §10 红线）。

| 事件名 | 触发时机 | 载荷字段 |
| --- | --- | --- |
| m20.approval.completed | 实例到达 COMPLETED 或 REJECTED | approval_no, biz_type, biz_no, result, approved_by, approved_at |
| m20.approval.rejected | 实例到达 REJECTED（与上一行同时发） | approval_no, biz_type, biz_no, rejected_by, reject_reason, rejected_at |
| m20.approval.exec_failed | 回执结果为 FAILED，实例到达 APPROVED_BUT_FAILED | approval_no, biz_type, biz_no, exec_fail_reason, failed_at |
| m20.approval.timeout | 派生的超时提醒 | approval_no, biz_type, biz_no, node_seq, timeout_at |

`m20.approval.completed` 的载荷六项一个不能少：`approval_no`、`biz_type`、`biz_no`、`result`、`approved_by`、`approved_at`。**只发 `approval_no` 是错误的**——M10-06 与 M11-06 收到事件后需要用 `biz_no` 定位具体的改单或随访单，只给单号它们无法完成定位，这正是总纲 §3.1 断点 A 的成因。

**`result` 的取值只有 `APPROVED` 与 `REJECTED` 两个，没有第三个值。**

**事件时序表（本子模块最关键的一张表，逐行不可少）：**

| 序号 | 状态变化 | 谁触发 | 发什么事件 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | → PENDING | 申请方调 P-01 | 无 | 待办与消息推送走 M20-08 |
| 2 | PENDING → APPROVING | 中间节点同意 | 无 | 逐级推进 |
| 3 | APPROVING → APPROVED | 最后一个节点同意 | **不发** | **审批通过，但不等人**，申请方此时才开始执行 |
| 4 | APPROVED → COMPLETED | 申请方调 P-07 回执 SUCCESS | **m20.approval.completed（result = APPROVED）** | **只有走到这里才发 completed** |
| 5 | APPROVED → APPROVED_BUT_FAILED | 申请方调 P-07 回执 FAILED | **m20.approval.exec_failed** | **不发 completed**，提醒对象是申请人 |
| 6 | APPROVED → APPROVED（不变） | 回执迟迟不来，60 分钟后 | **不发任何事件** | 只把 exec_confirm_status 置 TIMEOUT |
| 7 | 任一节点 → REJECTED | 审批人驳回 | **m20.approval.completed（result = REJECTED）** + m20.approval.rejected | 驳回是终态，直接发 |
| 8 | 任一非终态 → CANCELLED | 申请人撤回 | 无 | 撤回不通知审批评链外的订阅方 |

**第 3 行为什么不发事件，必须写清：** M10-06 对 `m20.approval.completed` 的处理是「改单审批结果回调（等价于调 API-20）」（M10视光业务管理/M10_视光业务管理_06_配镜订单与取镜交付_详细设计.md:7227）。如果第 3 行就发 `completed` 且 `result = APPROVED`，M10-06 会立刻去执行改单；而申请方自身的执行逻辑同样在此时启动，**同一个改单会被两个主体各执行一次**。这不是重试造成的重复，是**双执行**——两边都认为自己是对的，而且都成功了。

**第 5 行为什么不能复用 `completed`：** 若 `APPROVED_BUT_FAILED` 也发 `completed` 且 `result = APPROVED`，M10-06 会**去执行一次已经失败过的改单**；若 `result` 填 `FAILED`，M10-06 那边的枚举里没有这个值，**要么报错要么静默忽略，两种都不会有人知道**。**老事件不改语义，新情况用新事件。**

**第 6 行为什么不发事件：** 系统确实不知道业务到底执行了没有。硬判成功（发 completed）或失败（发 exec_failed）都是编造事实。**没消息就是没消息。**

## 11. 异常处理与日志

### 11.1 异常与降级总表

| 场景 | 响应形态 | 页面表现 | 用户可做什么 |
| --- | --- | --- | --- |
| 参数校验失败 | 4xx + 非 0 code | 字段级红字提示 | 修正后重提 |
| G-3 审批人失效 | 403 + "2004010" | 「您已不具备该审批权限，请联系管理员」 | 无（不得自动放行） |
| 实例不存在 | 404 + "2004005" | 「审批单不存在或已被撤回」 | 返回列表 |
| 状态不允许 | 409 + "2004012" | 「该审批状态已变化，请刷新」 | 刷新 |
| 待办列表查询失败 | 200 + degraded | **「待办加载失败，请下拉重试」** | 下拉重试 |
| 审批链解析失败 | P-01 4xx + 非 0 code | 申请方显示「审批服务异常，请稍后重试」 | 稍后重试 |
| 审批人解析失败 | P-01 4xx + "2004038" | 同上 | 联系管理员修配置 |
| 待办推送失败 | 200 + degraded | 操作成功，待办稍后到达 | 无感 |
| 消息推送失败 | 200 + degraded + push_failed | 「催办已记录，消息发送失败」 | 电话催办 |
| 审计写入失败 | 200 + degraded | 无感 | 无 |
| 数据库不可用 | 5xx | 「系统维护中」 | 等 |

**规则 R-11.1-01（待办加载失败的表现，强制）：**

> **审批列表与待办列表查询失败时，页面绝不能显示「暂无待办」。** 必须显式显示「待办加载失败，请下拉重试」。

理由：这段文字是共享规范 §8A.5 点名的最敏感处。管理者看到「暂无待办」会认为已经批完，直接离开；而实际是查询失败。等到单据超时才发现，追责时那句「系统显示没有待办」根本站不住脚。**空列表与查询失败必须能被用户区分，这只能靠文案，不能靠颜色。**

**规则 R-11.1-02（角标失败不显示 0）：** 待办角标查询失败时，角标显示为不可用状态（灰色圆点或无角标），**不得显示 0**。0 是一个具体的数字，它断言「你没有待办」，而失败时系统并不知道。

**规则 R-11.1-03（四种响应形态的边界）：** 见 §8.4 R-8.4-01。此处强调反面：**绝不允许「200 + 空 data + degraded: false」表示无权限或无数据**。无权限一律 403；无数据是正常的空列表但 `record_count = 0` 且 `degraded: false`；查询失败是 `degraded: true`。三种事实，三种表现。

### 11.4 补偿与恢复

| 场景 | 补偿机制 | 恢复判定 |
| --- | --- | --- |
| 待办推送失败 | Celery 指数退避重试 3 次 | 第 3 次仍失败置 FAILED，消息中心可见 |
| 事件发送失败 | 本地事件表 + 定时重投 | 重投成功即清除 |
| 审计写入失败 | 补偿队列 | 队列清空即恢复 |
| 回执超时 | scan_receipt_timeout 置 TIMEOUT 并告警 | 申请方补录回执（API-10）即恢复 |
| 审批链缓存错误 | 主动失效 + 兜底实时解析 | 无需人工 |

**规则 R-11.4-01（事件发送失败的补偿不使用 MQ 重试）：** MQ 层面的重试可能造成消息重复，而 `m20.approval.completed` 的重复投递会让 M10-06 再执行一次改单。因此事件先落本地事件表（同一事务内），由定时任务按 `(event_type, biz_key)` 幂等投递，投递成功后才标记已发。**这保证「发送」与「业务提交」在同一个事务里，二者同成败。**

## 附录 E：关键决策记录

**K-01 为什么 `approval_status` 扩到 9 态而不是 7 态。**

共享规范 §13 原列 7 态，总纲 §4.1 列 9 态（多出 `COMPLETED` 与 `APPROVED_BUT_FAILED`）。本设计采纳 9 态，理由是：7 态模型把「审批已通过但业务还没执行」和「业务已确认执行完成」折叠成一个 `APPROVED`。折叠之后，任何一个查 `status = 'APPROVED'` 的地方（统计、报表、上游查询）都会把这两类完全不同的情况算在一起，而它们的业务含义差着一整个执行环节。**状态机的职责是把不同的事实分开，不是把字段数省下来。**

**K-02 为什么把 `EXEC_UNCONFIRMED` 拆成独立列而不是第 10 个状态。**

`exec_confirm_status`（`WAITING`/`CONFIRMED`/`FAILED`/`TIMEOUT`）与实例状态正交：`APPROVED` 时可以处于任何一个 `exec_confirm_status`。如果把它塞进主状态机，`APPROVED` 到 `COMPLETED` 与 `APPROVED` 到「执行未确认」这两条路径就不对称了——后者不是状态转移，而是同一状态上的时间演进。**两套口径混在一个字段里，统计时必然打架。**

**K-03 为什么审批链缓存只存链形状、不存审批人。**

短期看缓存审批人能省掉每次解析的网络往返，性能更好。但缓存审批人意味着：科主任离职后，缓存里他仍是审批人，最长一小时内由他批准的单据仍然有效。G-3 闸门的整条逻辑都建立在这条上——**如果审批人来自缓存，G-3 就只是走个过场。** 因此宁可多一次远程调用，也不缓存审批人。

**K-04 为什么单号必须数据库原子生成。**

应用层 `SELECT max(...) + 1` 在并发下必然重号。而 `approval_no` 是 P-02 的唯一查询键，重号意味着一次查询可能返回错误的那一条审批——申请方会据此认为自己的单据被批准了，而实际批准的是别人的单据。**这不是格式问题，是数据正确性问题。** 因此使用数据库行级原子操作，且 `uk_m20_apr_instance_no` 在数据库层兜底。

**K-05 为什么 `m20.approval.completed` 只在 `COMPLETED` 时发。**

M10-06 收到 `result = APPROVED` 就会去执行改单。如果 M20 在「审批刚通过、申请方还没执行」的阶段就发 `completed`，M10-06 会与申请方自身的执行逻辑各执行一次——**同一个改单被执行两次**。`completed` 的名字与订阅方的行为共同决定了它的语义只能是「业务已经完成」，而不是「审批已经通过」。**老事件不改语义，新情况用新事件**：`APPROVED_BUT_FAILED` 另发 `m20.approval.exec_failed`。

**K-06 为什么节点表用部分唯一索引而不是触发器保证「一个实例一个 PENDING 节点」。**

能用唯一索引表达的不变量，就不要用触发器。触发器有竞态窗口（先检查后插入之间可能被插入另一行），而且失败时的报错信息对应用层不友好。部分唯一索引是原子的，冲突直接体现为 `IntegrityError`，应用层捕获后能给出确切语义。

**K-07 为什么审批留痕要同时用 REVOKE 与触发器。**

REVOKE 防的是"应用账号误操作或应用层缺陷"，触发器防的是"有人拿到了超级用户"。只有一条都叫没做——只 REVOKE 则超级用户可改；只触发器则应用层日常 BUG 都要靠异常暴露。

**K-08 为什么离线态不做本地乐观写入。**

离线期间审批链、审批人资质、实例状态都可能已经改变。回放需要版本校验与冲突解决，而审批是**不可撤回的业务承诺**——放行了一个实际已无权的人批的单据，事后无法用技术手段弥补。因此本子模块离线只读。

### F.1 与本模块共享规范的差异登记

**D-01 组合约束归属修正：`TIMEOUT` 的 `timeout_at` 与 `approver_id` 要求应约束在实例表，而非节点表。**

**原条目**（M20_移动办公_数据结构设计汇总.md §7.2 第 3 条）：`TIMEOUT` 必须有 `timeout_at` 且 `approver_id IS NULL`。

**问题**：在总纲 §4.1 中，`TIMEOUT` 是**实例级状态**（语义为「所有审批人不可用」），节点超时不改变 `node_status`，只用 `timeout_at` 标记。节点表的 `approver_id` 在「无人的节点」与「转进来的节点」两种情形下已经承载语义，若再允许其为空以表达「超时」，该列将同时表达三种含义，索引与统计都会失效。

**本设计的处理**：实例级 `timeout_at` 非空即表达实例超时；节点级超时由节点 `timeout_at` 单独表达、`node_status` 不变；节点表增加 `last_approver_id`（最近一次有效责任人），转办/审批/驳回时写入，使得「转过来的节点后来超时了，原审批人是谁」可被回答。

**结论**：**原条目把实例级约束误写成节点级字段约束，由 M20-04 在实现时发现。** 已提请共享规范侧修正，本设计按修正后的语义实现。

**D-02 U-12 作废。** 共享规范 §9.2 V1.3 已裁决 `is_mobile_user` 无任何内部接口返回。本子模块 G-3 判定不使用该字段，改用 U-05 + U-11。

**D-03 审批完成事件需覆盖 `APPROVED_BUT_FAILED`。** 原共享规范只定义了 `m20.approval.completed`，未说明执行失败时如何通知。本设计新增 `m20.approval.exec_failed`，见 §10.3。

**D-04 P-02 路径参数两种写法并存。** 上游文档中 `{approval_no}` 与 `{no}` 各有使用，本模块两者都接受，见 §8.1 R-8.1-04。
