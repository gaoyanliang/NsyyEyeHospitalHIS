## 文档说明

本文档是 M20-04 移动审批引擎的**物理设计**，只回答一个问题：**审批的「流程事实」在数据库里长什么样，以及数据库自己守住了哪些不变量**。

M20-04 拥有的是**流程事实**（谁在什么时候把哪一单推给了谁、谁批了、批完通知了谁、申请方有没有真的执行），它不拥有任何临床事实或账务事实。判断方法只有一句：**把本子模块的库删掉重建，会不会有业务事实丢失？** 审批实例、审批节点、审批留痕会丢，所以它们是本模块的表；申请人改的那张订单不会丢，所以本模块不建它的表。

### 三条不可协商的物理保证

| # | 保证 | 落地手段 | 为什么数据库必须自己守 |
|---|---|---|---|
| 1 | **一个实例同一时刻最多只有一个待办节点** | 部分唯一索引 `uk_m20_apr_node_active (instance_id) WHERE node_status = 'PENDING'` | 应用层「先查有没有待办再插入」有竞态窗口：两个审批人同时点「同意」、或补偿任务与真人操作撞车，都会插出两条待办，事后表现为「同一单被批了两次」。唯一索引是原子的，并发下只有一个事务能成功 |
| 2 | **审批留痕只增不改不删** | `REVOKE UPDATE, DELETE ON m20_apr_action_log FROM app_m20;` + 触发器 `trg_m20_apr_action_log_bu` | 权限只防「应用账号误操作」，防不住「有人拿到超级用户」。触发器在数据库内核里拦，超级用户 UPDATE 时同样抛 `APPROVAL_LOG_IMMUTABLE`。两条都要，只做一条都叫没做 |
| 3 | **审批结论与执行结果必须是两个事实** | 实例表 `status`（9 值）与 `exec_confirm_status`（4 值）分列 | 把「审批已通过但申请方没执行」压进一个字段，就等于宣告「批了 = 生效了」。断点 C 的全部代价就是从这里产生的 |

### 阅读约定

- **跨模块不建外键**，只写逻辑外键并加列注释（M01/M02 的职工与科室随时可能被重建，硬外键会让 M20 的迁移被上游卡住）；**M20 内部表之间必须建外键**（内部关系改不了，让数据库挡住悬空引用比应用层检查可靠）。
- 枚举一律 `VARCHAR(32)` + `CHECK` 显式列出全部取值，不建 PostgreSQL ENUM 类型（ENUM 加值要 `ALTER TYPE`，且不能删值，长跑系统会被锁死）。
- 时间一律 `TIMESTAMPTZ`。审批时效以「几点几分」判超时，跨时区写入用 `TIMESTAMP` 会算错 8 小时。
- **每一个文本列都写长度**。这不是存储优化，而是把「这个字段有没有上限」写进契约：没有上限的列，写入方会以为可以塞任意长度，直到某天有人在 `reason` 里存了一份完整病历正文。

### 1.1 命名与建表硬规范

| 项 | 规则 |
|---|---|
| 主键 | `id BIGINT GENERATED ALWAYS AS IDENTITY` |
| 四审计列 | `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`、`created_by BIGINT`、`updated_at TIMESTAMPTZ`、`updated_by BIGINT` |
| 逻辑删除 | 业务表带 `is_deleted BOOLEAN NOT NULL DEFAULT FALSE`；**只增不删表不带该列** |
| 状态列 | `VARCHAR(32)` + `CHECK` 显式枚举全部取值，取值与共享规范 §13 一字不差 |
| 金额 | `NUMERIC(14,2)`；比率 `NUMERIC(10,6)`；**禁止 FLOAT / DOUBLE / REAL** |
| 时间 | 一律 `TIMESTAMPTZ` |
| 外键 | 跨模块不建；M20 内部表必须建 |
| 命名 | `uk_m20_{表简称}_{列}` / `idx_m20_{表简称}_{列}` / `ck_m20_{表简称}_{含义}` / `fk_m20_{表简称}_{目标表简称}` / `trg_fn_m20_{表简称}_{动作}` / `trg_m20_{表简称}_{时机}_{动作}` |
| 注释 | 每表必须有 `COMMENT ON TABLE`；状态列与关键业务列必须有 `COMMENT ON COLUMN` |

## 2. 与其他子模块的表级关系

| 其他子模块的表 | 关系 | 本模块的处理 |
|---|---|---|
| M20-08 `m20_msg_todo` | 本模块产生的审批待办写进该表 | **只通过 M20-08 的写接口（API-09）写入**，本模块不取得该表的写权限、不直接 INSERT。理由：待办中心是 M20-08 的唯一权威，两个写入方会产生两套去重与两套状态 |
| M20-01 `m20_base_idempotency` | 幂等键登记 | 本模块的 P-01 幂等走自己的 `idempotent_key` 唯一索引（审批单是有业务实体承载的幂等，不借用通用幂等表，避免「幂等记录在、审批单不在」的不一致） |
| M20-08 `m20_msg_delivery_log` | 审批消息的投递日志 | 由 M20-08 自己维护，本模块只发布事件 |
| M02 审计 | 敏感操作留痕 | 本模块的动作留痕在 `m20_apr_action_log`；M02 审计表另由 M02-06 写入，两者不合并（前者是审批业务事实，后者是系统安全事实） |

## 3. 不建的表与理由

| 不建的表 | 理由 |
|---|---|
| 患者主档副本 | 审批只需要患者标识用于展示关联，不需要任何患者属性；建副本会与 M03 主索引产生第二份真相 |
| 业务单据副本（订单、屈光手术方案、财务凭证） | 审批通过后由申请方自己执行，M20 不执行也不持有其数据。存一份就必然要同步，同步就必然有不一致 |
| 员工待办表 | 归 M20-08（`m20_msg_todo`），本模块只通过接口写入 |
| 令牌/会话/设备/角色表 | 身份与凭据的权威在 M02，本模块只透传并校验，绝不落库 |
| 审批链缓存表 | 链解析结果进 Redis（`m20:apr:chain:*`，TTL 3600s）不进数据库。落库会让「缓存失效」变成一次数据库写风暴，而链解析本来就是可重算的派生结果 |
| 审批统计汇总表 | 统计由 M22 从本模块实例表取数聚合，本模块不预先汇总 |
| 消息投递日志 | 归 M20-08 |
| 审批模板表 | 本模块的「模板」就是 `m20_apr_rule` + `m20_apr_rule_node`，不另立一层 |

### 4.1 ER 关系图

```
                        │  m20_apr_rule            │  审批规则（链头）
                        │  rule_code (UK)          │
                        │  biz_type / 金额区间 / 科室范围
                        │  match_level 1~5         │
                        └────────────┬─────────────┘
                                     │ 1 : N
                                     ▼
                        ┌──────────────────────────┐
                        │  m20_apr_rule_node       │  规则节点定义（第几级、谁来批、会签方式）
                        │  UK(rule_code, node_seq) │
                        └──────────────────────────┘
                                     │
                    规则解析时按 node_seq 实例化
                                     │
                                     ▼
  ┌──────────────────────────┐   1:N   ┌──────────────────────────┐
  │  m20_apr_instance        │────────▶│  m20_apr_node            │
  │  approval_no (UK)        │         │  UK_active(instance_id)  │
  │  biz_type + biz_no (UK)  │         │    WHERE node_status=PENDING
  │  status 9 值             │         │  approver_id 快照        │
  │  exec_confirm_status 4 值│         │  transfer_from_id 链     │
  │  idempotent_key (UK)     │         └────────────┬─────────────┘
  └───────┬───────┬──────────┘                      │ 1:N
          │       │                                 ▼
          │       │                       ┌──────────────────────────┐
          │       │                       │  m20_apr_action_log      │
          │       │                       │  只增不改（REVOKE+触发器）│
          │       │                       └──────────────────────────┘
          │       │
          │ 1:N   │ 1:N
          ▼       ▼
  ┌───────────────┐   ┌──────────────────┐
  │ m20_apr_receipt│   │ m20_apr_cc       │
  │ 执行回执       │   │ 抄送             │
  └───────────────┘   └──────────────────┘

  ┌──────────────────────┐   ┌──────────────────────┐
  │ m20_apr_delegate     │   │ m20_apr_urge         │
  │ 委托代理（独立于实例）│   │ 催办（关联节点）      │
  └──────────────────────┘   └──────────────────────┘

  ┌──────────────────────┐   ┌──────────────────────────────┐
  │ m20_apr_config       │   │ m20_apr_oper_log             │
  │ 运行参数（KV）       │   │ 运维日志（月分区 + DEFAULT）   │
  └──────────────────────┘   └──────────────────────────────┘
```

**关系说明**：

| 关系 | 基数 | 说明 |
|---|---|---|
| 规则 → 规则节点 | 1 : N | 一条规则至少一级节点；节点按 `node_seq` 顺序执行 |
| 规则 → 实例 | 1 : N | 实例记录命中规则的 `rule_code` 与 `match_level`，用于事后回答「这单为什么是两级」 |
| 实例 → 节点 | 1 : N | 实例创建时按规则节点一次性全部实例化（含 `WAITING` 态），不留「还没生成的节点」 |
| 节点 → 动作留痕 | 1 : N | 每个节点每次被操作都追加一条留痕，转办会让同一 `node_seq` 有多条留痕 |
| 实例 → 执行回执 | 1 : N | 正常只有一条成功回执；失败后重试成功会产生多条，靠 `receipt_seq` 有序 |
| 实例 → 抄送 | 1 : N | 抄送人在审批终结时收到通知，不参与投票 |
| 委托 / 催办 / 配置 / 运维日志 | 独立 | 不挂在实例下，或只通过逻辑外键弱关联 |

### 4.2 表：`m20_apr_rule`（审批规则主表）

**用途**：一条规则定义「哪一类业务在什么金额与科室范围内，走什么样的审批链」。规则是审批链解析的输入，`M20-CALC-01` 的五级匹配就是在张表上按 `match_level` 从 1 到 5 逐级筛。

**写入方：** M20-04 管理员维护界面（新增/停用）。**只读方：** M20-04 链解析服务、M22 报表（规则覆盖率统计）。

#### 字段定义

| 字段名 | 类型 | 允许空 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | 自增 | 主键 |
| `rule_code` | VARCHAR(64) | 否 | — | 规则编码，格式 `R-` + 3 位数字，如 `R-101`；全表唯一 |
| `rule_name` | VARCHAR(128) | 否 | — | 规则名称，如「视光改单·门店金额 500 元以下」 |
| `biz_type` | VARCHAR(64) | 否 | — | 业务类型，如 `M10_ORDER_AMEND`；与申请方约定，不做格式校验 |
| `match_level` | SMALLINT | 否 | — | 匹配层级 1~5，数值越小越优先，命中即停 |
| `amount_min` | NUMERIC(14,2) | 是 | — | 金额区间下界（含）；空表示无下界 |
| `amount_max` | NUMERIC(14,2) | 是 | — | 金额区间上界（不含）；空表示无上界 |
| `dept_scope` | VARCHAR(32) | 否 | `ALL` | 科室范围：`ALL`（全院）或 `SPECIFIC`（指定科室，见 `dept_ids`） |
| `dept_ids` | BIGINT[] | 是 | — | 指定科室号数组，`dept_scope='SPECIFIC'` 时必填非空 |
| `biz_no_prefix` | VARCHAR(32) | 是 | — | 单号前缀，四级匹配用，如 `GD`；为空表示不按前缀匹配 |
| `match_priority` | SMALLINT | 否 | `100` | 同层级内的先后优先级，数值小者优先 |
| `need_approval` | BOOLEAN | 否 | `TRUE` | 是否免审；`FALSE` 表示命中即直接通过（`need_approval=false` 分支） |
| `effective_status` | VARCHAR(32) | 否 | `DRAFT` | 生效状态：`DRAFT` / `REVIEWING` / `ACTIVE` / `INACTIVE` |
| `effective_from` | TIMESTAMPTZ | 是 | — | 生效起；与 `effective_to` 构成时间窗 |
| `effective_to` | TIMESTAMPTZ | 是 | — | 生效止（不含）；空表示长期有效 |
| `rule_version` | INTEGER | 否 | `1` | 规则版本号，每次结构性修改 +1；实例记下解析时的版本 |
| `remark` | VARCHAR(512) | 是 | — | 备注 |
| `created_at` | TIMESTAMPTZ | 否 | `now()` | 创建时间 |
| `created_by` | BIGINT | 是 | — | 创建人职工号 |
| `updated_at` | TIMESTAMPTZ | 是 | — | 更新时间 |
| `updated_by` | BIGINT | 是 | — | 更新人职工号 |
| `is_deleted` | BOOLEAN | 否 | `FALSE` | 逻辑删除；已停用的规则用 `INACTIVE` 而不是删除 |

#### 索引设计

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m20_apr_rule` | 主键 | `id` | — |
| `uk_m20_apr_rule_code` | 唯一 | `rule_code` WHERE `is_deleted = FALSE` | 规则编码唯一；部分索引让删除后可复用编码 |
| `idx_m20_apr_rule_match` | B-tree | `biz_type`, `match_level`, `match_priority` | 链解析主查询：按业务类型取全部候选规则后按层级排序 |
| `idx_m20_apr_rule_status` | B-tree | `effective_status`, `effective_from` | 后台规则列表与生效扫描 |

#### 约束说明

| 约束名 | 类型 | 表达式 | 说明 |
|---|---|---|---|
| `ck_m20_apr_rule_code` | CHECK | `rule_code ~ '^R-[0-9]{3}$'` | 规则编码格式 |
| `ck_m20_apr_rule_level` | CHECK | `match_level BETWEEN 1 AND 5` | 五级匹配，超出即无意义 |
| `ck_m20_apr_rule_amount` | CHECK | `amount_min IS NULL OR amount_max IS NULL OR amount_min < amount_max` | 区间下界必须小于上界 |
| `ck_m20_apr_rule_dept` | CHECK | `dept_scope IN ('ALL','SPECIFIC')` | 科室范围枚举 |
| `ck_m20_apr_rule_dept_ids` | CHECK | `dept_scope <> 'SPECIFIC' OR (dept_ids IS NOT NULL AND array_length(dept_ids, 1) >= 1)` | 指定科室时必须给科室列表 |
| `ck_m20_apr_rule_status` | CHECK | `effective_status IN ('DRAFT','REVIEWING','ACTIVE','INACTIVE')` | 生效状态枚举 |
| `ck_m20_apr_rule_window` | CHECK | `effective_from IS NULL OR effective_to IS NULL OR effective_from < effective_to` | 生效时间窗有效 |
| `ck_m20_apr_rule_version` | CHECK | `rule_version >= 1` | 版本号从 1 起 |
| `ck_m20_apr_rule_prefix` | CHECK | `biz_no_prefix IS NULL OR char_length(btrim(biz_no_prefix)) BETWEEN 1 AND 32` | 前缀不允许空串或纯空白 |

**为什么 `match_level` 与 `match_priority` 要分两列**：层级表达「精确度」（精确科室 > 科室 ALL > 全院），优先级表达「同精确度下的业务偏好」（例如门诊改单规则优先于通用改单规则）。合成一列后，新增一条通用规则就得重排全部规则的序号，改一次错一次。

**为什么 `need_approval = FALSE` 不单独建一张免审清单表**：免审是规则的属性而不是另一套规则。建第二张表会让「这条业务到底走哪张表」变成判断分支，而判断分支一旦两处实现不一致，免审就会时灵时不灵。

**为什么 `skip_when_absent` 默认 `FALSE`**：如果审批人解析失败就自动跳过，那么一条配置错误的规则会让审批链静默地少一级，而申请人看到的是「已批准」。宁可拒绝服务并让管理员修规则，也不能让审批在没人批的情况下通过。这条默认值就是 `M20-CALC-01` 算例里「第 1 级解析 0 人返回错误码 `2004008`」的物理依据。

**为什么本表不存具体审批人姓名**：姓名在 `m20_apr_node` 里以快照形式存一份（那是历史事实），本表是配置，配置只应存标识。配置里存姓名，改一次名就得改全部规则。

### 4.4 表：`m20_apr_instance`（审批实例表）

**用途：** 一条审批申请的完整生命周期记录，是 M20-04 的**流程事实主表**。它回答三个问题：「这条业务单据有没有发起过审批」「现在走到第几级」「最后结论是什么、什么时候得出的」。它**不承载任何申请方业务数据**——`biz_type`、`biz_no`、`amount`、`reason` 只是发起时抄录的索引与快照，真正的业务事实（改单、停台、退费单）在 M10/M11/M17 各自的库里。

**写入方：** M20-04 审批引擎（P-01 `POST /internal/v1/m20/approval/apply` 建实例；审批动作推进状态；回执接口推进 `exec_confirm_status`）。

**为什么 `exec_confirm_status` 单独成列，而不是让 `status` 变第 10 个值**

如果把「`APPROVED` 之后等待回执超时」塞进 `status`（做成 `EXEC_UNCONFIRMED`），状态机会出现两条**不对称**的出口：`APPROVED → COMPLETED`（回执成功）与 `APPROVED → EXEC_UNCONFIRMED`（回执超时），而 `EXEC_UNCONFIRMED` 之后既可能转为 `COMPLETED` 也可能转为 `APPROVED_BUT_FAILED`。这会让所有按 `status` 分组的统计出现两套口径：

- 审批通过率的分母要不要包含 `EXEC_UNCONFIRMED`？含了会把「审批已通过、只是执行没回执」算成「未通过」，直接压低通过率；
- 审批平均时长的终点怎么取？如果在 `EXEC_UNCONFIRMED` 上追加 `finished_at`，那 `APPROVED`（还没回执）就永远没有 `finished_at`，「审批时长」被无限拉长。

**拆成两列后，两个问题都消失**：`status` 只回答「审批的结论是什么」（9 值，语义纯粹），`exec_confirm_status` 只回答「这个结论被执行了吗」（4 值）。**统计口径按 `status` 分组，执行监控按 `exec_confirm_status` 分组，两套互不干扰。** 代价是查询时多一个条件、展示时需要把两列拼成一句话——这个代价是值得付的，因为口径打架的代价是「同一个数字在两张报表里不一样」，那种问题没人能解释清楚。

### 4.5 表：`m20_apr_node`（审批节点表）

**`TIMEOUT` 与 `TRANSFERRED` 的张力怎么解决**

共享规范 §7.2 第 3 条要求「`TIMEOUT` 必须有 `timeout_at` 且 `approver_id IS NULL`」，但本表的设计里 `approver_id` 在超时后**保留原值**。这两者不矛盾，因为**超时不是节点状态**：

- 节点超时的表达是 `node_status` 仍为 `PENDING` 且 `timeout_at IS NOT NULL`、`now() > timeout_at`。这样 `approver_id` 继续指向那个没批的人——**追责时能答出「是谁没批」**。
- 只有当**全体审批人都不可用**（离职、调岗、角色失效），实例才进入 `status = 'TIMEOUT'`，此时**实例表**的 `timeout_at` 有值，而**节点表**的 `approver_id` 依然保留（它是「当时该批的人」的记录）。
- 共享规范 §7.2 第 3 条「`approver_id IS NULL`」针对的是**节点记录在超时升级后由系统代管**的场景。本设计不用「代管节点」表达升级——系统代管发生在 `m20_apr_oper_log` 与 `m20_apr_action_log`（`action = 'SYSTEM_ESCALATE'`），不新增节点行。**因此本表不实现「`approver_id IS NULL`」这条，而是用「`TIMEOUT` 不是节点状态」从根上避免了这个冲突。** 这条偏离已在附录 B.4 显式登记，理由：如果在节点表上允许 `approver_id IS NULL`，那么 `m20_apr_node.approver_id` 就不能参与「我的待审批」索引与统计，需要额外区分「无人的节点」和「转进来的节点」，列语义会碎。

### 4.7 表：`m20_apr_receipt`（执行回执表）

**用途：** 申请方执行完业务动作后回报的事实记录。它把断点 A 与断点 C 变成可判定的事实：哪一单回执了、是否成功、失败原因是什么。

**写入方：** M20-04 审批引擎（`POST /internal/v1/m20/approval/{no}/receipt`）。**只读方：** M20-04 页面；M22 的审批时效分析（只读统计）；申请人本人的「我的申请」列表。

| ck_m20_apr_receipt_fail_reason | CHECK | `(exec_result = 'FAILED') = (exec_fail_reason IS NOT NULL)` |
| ck_m20_apr_receipt_latency | CHECK | `latency_seconds IS NULL OR latency_seconds >= 0` |

**回执的三种处理结果与幂等**

回执接口必须幂等（申请方会因超时重发）。判定逻辑：

- 同一实例**首次**回执 → `receipt_status = 'ACCEPTED'`，同时推进实例 `exec_confirm_status`。
- 同一实例**重复**回执且 `request_hash` 一致、`exec_result` 相同 → `receipt_status = 'REPLAY'`，返回首次结果，**不新增状态推进**，不改实例表。
- 同一实例重复回执但 `exec_result` **矛盾**（例如已 `SUCCESS` 又来 `FAILED`）→ 写一行 `receipt_status = 'REJECTED_CONFLICT'`，**接口返回业务错误码，不改实例状态**。理由：回执矛盾说明申请方两侧数据不一致，这本身就是需要人工介入的故障，静默接受任意一方都会让「审批已通过、业务到底执行了没有」变成猜谜。

**为什么委托必须审批、必须有有效期、必须可撤销**

委托等于把一个人的审批权临时借给另一个人。若不审批，任何人都能自助获得任意他人的审批权；若无有效期，长期挂着的委托会让「谁批的」永久模糊；若不可撤销，委托人出差回来也要靠别人代批。三个约束缺一个，这个功能就不能上线。**90 天上限**的依据：年度预算级审批的复核周期是一个季度，超过 90 天的委托基本等价于「岗位变更」，应该走人事流程而不是审批委托。

**限频与闸门**

催办次数上限：**同一节点每人每日 2 次**、同一节点每日总计 6 次。超限返回业务错误码而不是静默丢弃——用户需要知道「今天已经催过了」。催办走消息中心时同样受共享规范 §8A 的闸门约束：免打扰时段（21:00 至次日 08:00）抑制、频次超限抑制，被抑制时 `urge_result = 'SUPPRESSED'` 并记原因。**不提供短信通道的理由**：短信成本高且不可撤回，而催办是内部协作动作，站内信与推送足以覆盖；用短信催同事批单在真实医院里会迅速演变成骚扰。

五级匹配全部不中意味着「这张单据该由谁审，系统不知道」。此时默认免审等价于「不知道就放行」，而审批存在的意义恰恰是「不确定就不要放行」。 `M20-CALC-01` 明确规定全不中返回 `"2004002"`，本配置项保留 TRUE 的可能性只是为了 UAT 环境压测，且**上线体检项会检查生产环境该值为 FALSE**。

### 4.12 表：`m20_apr_oper_log`（审批引擎操作日志表）

**用途：** 记录对**配置、规则、委托**这类管理动作的审计日志。它与 `m20_apr_action_log` 的分工是：**后者记「单据上的动作」，本表记「系统配置上的动作」**。两张表不能合并——合并会让「审批轨迹」里混进一堆「某人改了超时时长」，人的动作淹没在配置变更里。

**写入方：** M20-04 审批引擎（规则维护、配置修改、委托审批、数据修复）。**只读方：** 审计与运维；M02 审计中心（只读引用）。

| ck_m20_apr_oper_log_result | CHECK | `result_status IN ('SUCCESS','FAILED')` |
| ck_m20_apr_oper_log_fail | CHECK | `(result_status = 'FAILED') = (fail_reason IS NOT NULL)` |

**分区策略**

按 `created_at` 月 RANGE 分区。容量估算：配置与规则变更约 50 次/日、委托约 20 次/日、数据修复约 5 次/日，合计约 75 行/日、2.7 万行/年、1.2KB/行，一年约 32MB —— **单看容量并不需要分区**。分区的理由是**归档与清理**：审计日志需要「保留 3 年、每月可独立导出、过期分区可整块迁走」，分区让这三件事都变成 `ATTACH`/`DETACH` 而不是 `DELETE`。**必须建 DEFAULT 分区**：没有 DEFAULT 分区时，新月份第一条 INSERT 会直接报 `no partition of relation found for row`，而这个错误会精确地在每月 1 日 00:00 之后的第一次配置变更时炸掉——那时没人会想起是分区的问题。

**三个易写错的 ORM 细节**

1. **部分唯一索引必须用 `Index(..., postgresql_where=...)`，不能用 `UniqueConstraint`。** `UniqueConstraint` 表达不了 `WHERE` 条件，写成 `UniqueConstraint("instance_id")` 会让「每个实例只能有一个节点」而不是「只能有一个 `PENDING` 节点」——后者是致命错误，它会让审批链只能有 1 级。
2. **分区表的主键必须含分区键。** `M20AprOperLog` 的 `primary_key=True` 只标在 `id` 上，实际 DDL 的联合主键由 Alembic 迁移脚本显式写成 `PRIMARY KEY (id, created_at)`；ORM 侧靠 `UniqueConstraint("log_no", "created_at")` 保证业务唯一。
3. **只增不删表不要继承 `CreateUpdateMixin`。** 它带 `updated_at`/`updated_by`，与「不可修改」的语义直接矛盾；一旦有人 `obj.updated_at = now()` 并提交，数据库侧虽然没有列但 ORM 会抛错，且这个错误发生在运行期而非启动期，很难排查。

```python
def quality_block(
    degraded_sources: list[DegradedSource],
    as_of: datetime,
    cached_seconds: int | None = None,
) -> QualityBlock:
    """按共享规范 §6 M20-CALC-05 构造四质量标记。

    判定顺序：任一上游失败 -> PARTIAL；命中缓存且缓存龄 > 30s -> CACHED；
    缓存龄 <= 30s 或未命中缓存 -> REALTIME；无法判定 -> UNKNOWN。
    """
    if degraded_sources:
        return QualityBlock(
            degraded=True,
            degraded_sources=degraded_sources,
            data_quality="PARTIAL",
            as_of=as_of,
        )
    if cached_seconds is not None and cached_seconds > 30:
        return QualityBlock(
            degraded=False,
            degraded_sources=[],
            data_quality="CACHED",
            as_of=as_of,
        )
    return QualityBlock(
        degraded=False,
        degraded_sources=[],
        data_quality="REALTIME",
        as_of=as_of,
    )
```

**Schema 与表字段对照（关键字段）**

| 表 | 对应 Schema | 校验重点 | 说明 |
| --- | --- | --- | --- |
| m20_apr_instance | ApplyRequest / ApplyResponse / ApprovalDetailResponse | reason ≤ 500；biz_no 不校验格式；status 枚举 9 值 | 状态与执行确认两维分别出现在响应中 |
| m20_apr_node | ApprovalNodeOut | approver_id 可空；skip_reason 与 node_status=SKIPPED 联动 | 节点超时不改 node_status |
| m20_apr_action_log | 无输出 Schema | 只写不读 | 对外只通过审计导出，不给移动端读接口 |
| m20_apr_receipt | ReceiptRequest / ReceiptResponse | FAILED 必须有原因；SUCCESS 不得带原因 | receipt_replay 区分重放 |
| m20_apr_config | ConfigOut | config_value 一律字符串 | 解析由 value_type 决定 |
| m20_apr_delegate | RuleNodeIn 家族之外独立 | principal_id ≠ agent_id；end_at > start_at | 委托必须审批 |

**三个容易写漏的校验**

1. **`biz_no` 绝不能加 `pattern`。** 它来自 M10/M11/M17，各模块单号格式不同且历史上改过位数。一旦这里写了正则，任何上游改格式都会让审批申请直接 422，而申请人只想改个单而已。
2. **`reason` 超长必须拒绝而不是截断。** Pydantic 的 `max_length=500` 会抛 `ValidationError`，500 是全局错误处理器映射到 `"2004015"`（申请理由超长）的依据。截断的实现会让「用户填了 800 字，系统只存了前 500 字」在事后追责时无法解释。
3. **`degraded_sources` 与 `degraded` 必须同真同假。** `quality_block()` 是唯一构造入口，避免某处手工拼出 `degraded=true` 但 `degraded_sources=[]` 这种自相矛盾的响应。

## 附录 B：状态枚举与组合约束汇总

### B.1 审批实例状态（9 值，与共享规范 §13 逐字一致）

| 状态值 | 中文 | 是否终态 | 进入条件 | 唯一出口 |
| --- | --- | --- | --- | --- |
| DRAFT | 草稿 | 否 | 申请已创建但未提交 | 提交 -> PENDING |
| PENDING | 待审批 | 否 | 已提交，第一级节点已激活 | 审批动作 -> APPROVING / APPROVED / REJECTED |
| APPROVING | 审批中 | 否 | 至少一级已通过且仍有后续级 | 后续级通过 -> APPROVED；驳回 -> REJECTED |
| APPROVED | 已通过 | 否 | 全部节点通过且已通知申请方 | 收到回执 -> COMPLETED / APPROVED_BUT_FAILED；回执超时 -> 仍是 APPROVED 但 exec_confirm_status=TIMEOUT |
| COMPLETED | 已完成 | 是 | 回执 exec_result=SUCCESS | — |
| APPROVED_BUT_FAILED | 已通过但执行失败 | 是 | 回执 exec_result=FAILED | — |
| REJECTED | 已驳回 | 是 | 任一级驳回 | — |
| CANCELLED | 已撤回 | 是 | 申请人主动撤回 | — |
| TIMEOUT | 超时 | 否 | 全体审批人不可用，转管理员 | 管理员介入后 -> APPROVED / REJECTED / CANCELLED |

**两条硬规则**：`TIMEOUT` 不得折叠进 `REJECTED`（否则「没人能批」与「有人批了不批」在统计里混为一谈）；`APPROVED` 不是终态（审批通过不等于业务生效）。

### B.2 审批节点状态（6 值）

| 状态值 | 中文 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| WAITING | 等待中 | 实例创建时全部节点初始为此状态 | 前序节点全部通过 -> PENDING |
| PENDING | 待处理 | 成为当前激活节点 | 同意 -> APPROVED；驳回 -> REJECTED；转办 -> TRANSFERRED |
| APPROVED | 已同意 | 审批人同意（会签 ALL 需全员同意） | 终态 |
| REJECTED | 已驳回 | 审批人驳回 | 终态；后续节点全部置 SKIPPED |
| SKIPPED | 已跳过 | 免审、会签任一已满足、或前序驳回终止 | 终态 |
| TRANSFERRED | 已转办 | 审批人转办给他人 | 终态；新节点取代其位置 |

**节点超时不是状态。** 超时的表达是 `node_status` 仍为 `PENDING` 且 `timeout_at IS NOT NULL` 且 `now() > timeout_at`。这样 `approver_id` 继续指向没批的那个人，追责时能答出「是谁没批」；若把超时做成状态，就会有人把 `approver_id` 清空，而这个字段一清空，「谁没批」就永远查不出来了。

### B.3 执行确认状态（4 值，与实例状态正交）

| 状态值 | 中文 | 进入条件 | 说明 |
| --- | --- | --- | --- |
| WAITING | 等待回执 | 实例状态为 APPROVED 时的默认值 | 已通知申请方，等它回报 |
| CONFIRMED | 已确认执行 | 收到 exec_result=SUCCESS 的回执 | 实例同时转 COMPLETED |
| FAILED | 执行失败 | 收到 exec_result=FAILED 的回执 | 实例同时转 APPROVED_BUT_FAILED，****必须推给申请人而非审批人**** |
| TIMEOUT | 回执超时 | 超过 approval.receipt.timeout.minutes 仍未收到回执 | 实例状态仍为 APPROVED，但触发告警并进入运维巡检清单 |

### B.4 与共享规范 §7.2 组合约束的对应关系与一处显式偏离

| 规范条目 | 本设计的落地 | 说明 |
| --- | --- | --- |
| APPROVED 或 REJECTED 必须有 finished_at | ck_m20_apr_instance_finished 覆盖 | 另扩展到 COMPLETED / APPROVED_BUT_FAILED / CANCELLED |
| APPROVED_BUT_FAILED 必须有 exec_fail_reason | ck_m20_apr_instance_exec_fail 覆盖 | 用 exec_confirm_status=FAILED 与 exec_fail_reason 双向绑定 |
| TIMEOUT 必须有 timeout_at 且 approver_id IS NULL | **偏离**：本设计 TIMEOUT 记在实例表，timeout_at 必填；节点表 approver_id 保留 | 理由见 §4.5：本设计不引入「代管节点」，超时是实例级事实而非节点级状态。若在节点表允许 approver_id 为空，则该列无法同时表达「无人的节点」与「转进来的节点」，索引与统计都会失效 |
| TRANSFERRED 节点必须有 transfer_from_id | ck_m20_apr_node_transfer 覆盖 | 用 transferred_from_staff_id |
| SKIPPED 必须有 skip_reason | ck_m20_apr_node_skip_reason 覆盖 | 并强制区分三种成因 |

**这处偏离必须在详细设计 §8.2 与附录 A 中同步登记，并由 M20 规范维护人确认**，否则后续子模块按规范原文写审核清单时会把它当成缺陷。

## 附录 C：关键查询与索引使用

### C.1 P-01 审批链解析（目标 P95 ≤ 200ms）

```sql
-- 五级匹配：命中即停，按 match_level 升序、同级按 match_priority 升序取第一条
SELECT rule_code, rule_version, match_level, need_approval
  FROM m20_apr_rule
 WHERE biz_type = :biz_type
   AND effective_status = 'ACTIVE'
   AND is_deleted = FALSE
   AND :amount >= amount_min
   AND (amount_max IS NULL OR :amount < amount_max)
   AND (dept_scope = 'ALL' OR :dept_id = ANY (dept_ids))
 ORDER BY match_level ASC, match_priority ASC
 LIMIT 1;
```
命中索引：`idx_m20_apr_rule_match (biz_type, effective_status, match_level)`。**这一条 SQL 在缓存命中时根本不会执行**——链解析结果按 `(biz_type, dept_id)` 缓存在 `m20:apr:chain:{biz_type}:{dept_id}`，TTL 3600s，缓存里只存链的形状不存 `approver_id`。200ms 的达成靠的是「绝大多数请求走缓存 + 缓存未命中时的单条索引查询」。

```sql
  FROM m20_apr_instance i
 WHERE i.status = 'APPROVED'
   AND i.exec_confirm_status = 'WAITING'
   AND i.approved_at < now() - make_interval(mins => :receipt_timeout_minutes);
```
命中索引：`idx_m20_apr_instance_status (status, created_at DESC)`。

## 附录 D：配置参数与字段字典

### D.1 核心字段字典

| 字段名 | 出现位置 | 语义 | 易错点 |
| --- | --- | --- | --- |
| approval_no | instance / node / action_log / receipt / cc / urge | 审批单号，`SP` + `yyyyMMdd` + 4 位流水 | 不得在任何调用方做位数或格式校验 |

### D.2 `mobile.access.mode` 三值（来自共享规范 V1.3 §9.2 裁决）

| 取值 | 使用环境 | 行为 | 说明 |
| --- | --- | --- | --- |
| STRICT | 生产（默认） | 拿不到准入判定就拒绝移动端登录，提示「移动办公权限未配置，请联系信息科」 | fail-closed，绝不允许「查不到就当作允许」 |
| PERMISSIVE | 仅 UAT | 拿不到判定时放行并记告警 | 上线体检项会拦住该取值 |

**注意：该配置项由 M20-01 使用，M20-04 读它只为在审批动作里给出正确的拒绝文案。审批人有效性（G-3）的判定依据不是它，而是 U-05 `permission-context` 与 U-11 `staff-by-roles`**——「这个人能不能用移动端」与「这个人此刻有没有这条审批权限、是否在岗」是两件事。一个在岗有权限的科主任用 PC 批和用手机批，G-3 的判定必须一样。

### E.2 Alembic 迁移骨架

```python
"""m20_0003: M20-04 移动审批引擎 11 张表

Revision ID: m20_0003
Revises: m20_0002
"""

from alembic import op

revision = "m20_0003"
down_revision = "m20_0002"


def upgrade() -> None:
    op.execute("CREATE SCHEMA IF NOT EXISTS m20")
    # 11 张表按 E.1 顺序建表，DDL 见 §4.2 ~ §4.12
    # 部分唯一索引必须在建表后单独 CREATE UNIQUE INDEX
    op.execute(
        "CREATE UNIQUE INDEX uk_m20_apr_node_active "
        "ON m20_apr_node (instance_id) WHERE node_status = 'PENDING'"
    )
    op.execute(
        "CREATE UNIQUE INDEX uk_m20_apr_instance_idem "
        "ON m20_apr_instance (biz_type, idempotency_key) "
        "WHERE idempotency_key IS NOT NULL "
        "AND status IN ('PENDING', 'APPROVING', 'APPROVED')"
    )
    # 只增不删表回收权限
    for table in ("m20_apr_instance", "m20_apr_node", "m20_apr_action_log", "m20_apr_oper_log"):
        op.execute(f"REVOKE DELETE ON {table} FROM app_m20")


def downgrade() -> None:
    raise RuntimeError("审批表不提供降级：删表会丢失不可重建的流程事实")
```

**降级策略**：审批表**不提供 `downgrade`**。理由：这些表存的是「谁在什么时候批了什么」的不可重建事实，回滚迁移等于删证据。真需要回退时应当回退应用版本而保留表结构与数据。

### E.3 `m20_0004`：审批留痕不可变触发器与权限

```python
"""m20_0004: 审批留痕不可变约束

Revision ID: m20_0004
Revises: m20_0003
"""

from alembic import op

revision = "m20_0004"
down_revision = "m20_0003"


def upgrade() -> None:
    op.execute("REVOKE UPDATE, DELETE ON m20_apr_action_log FROM app_m20")
    op.execute("GRANT INSERT, SELECT ON m20_apr_action_log TO app_m20")
    op.execute(
        """
        CREATE OR REPLACE FUNCTION trg_fn_m20_apr_action_log_immutable()
        RETURNS TRIGGER AS $$
        BEGIN
            RAISE EXCEPTION 'APPROVAL_LOG_IMMUTABLE'
                USING HINT = '审批留痕只允许追加，不允许修改或删除';
        END;
        $$ LANGUAGE plpgsql
        """
    )
    op.execute(
        """
        CREATE TRIGGER trg_m20_apr_action_log_bu
            BEFORE UPDATE OR DELETE ON m20_apr_action_log
            FOR EACH ROW EXECUTE FUNCTION trg_fn_m20_apr_action_log_immutable()
        """
    )


def downgrade() -> None:
    raise RuntimeError("不可变约束不提供降级：撤销它会打开篡改审批证据的通道")
```

### E.4 上线必跑的三条校验

| 序号 | 校验内容 | 期望结果 | 不通过的处置 |
| --- | --- | --- | --- |
| 1 | 只增不删表不得有逻辑删除列 | 1024 行，实际对比：`information_schema.columns` 中 4 张表均无该列 | 删除该列或改表归类 |
| 2 | `has_table_privilege('app_m20', table_name, 'DELETE')` | 4 张表全为 false | 补 REVOKE |
| 3 | DEFAULT 分区行数 | `SELECT count(*) FROM m20_apr_oper_log_p_default` 为 0 | 补建当月分区 |
