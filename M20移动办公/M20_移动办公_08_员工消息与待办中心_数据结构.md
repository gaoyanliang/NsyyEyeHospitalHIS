## 1. 文档说明与表清单

### 1.1 本文件与详细设计的分工

本文件只回答「数据长什么样」。凡属「这个数怎么算」「这个状态怎么流转」「失败时返回什么」的内容，全部在 `M20_移动办公_08_员工消息与待办中心_详细设计.md`（下称详细设计）里，本文件不重复论证，只在必要处给出交叉引用。

两文件的行数、表数、枚举值是同一份事实的两个视角，**任何一处改动必须同步另一处**。这是共享规范 §0.3 铁律一「数量口径三处一致」在本模块内的落地形态：三处指本文件、详细设计、`M20_移动办公_数据结构设计汇总.md`。

### 1.2 九张表的分工

九张表按职责分成四组，分组决定了它们的生命周期与权限，不按字母序排列。

**第一组：消息本体（两张）**

`m20_msg_inbox` 是员工站内信正文的**唯一权威**。它的存在理由是总纲 §1.4 那条红线判据——「这张表存的东西，如果 M20 删库重建，会不会有业务事实丢失？」员工站内信会：`M03患者服务与EMPI/M03_患者服务与EMPI_05_消息_详细设计.md:43` 原文写明「**不做**员工站内信（M20）」，所以员工消息在 M03 侧一条都不落库。M20 一旦丢了这张表，历史上所有发给职工的站内信正文、标题、已读状态就永久消失，且没有任何地方可以重建。

`m20_msg_delivery_log` 是一次投递尝试的**事实快照**，只增不删。它回答的是「这条通知到底发没发」——这个问题在纠纷、投诉、运维排查里被问到的频率远高于所有其他问题。它与 `m20_msg_inbox` 是一对多：一条站内信可以有多条投递日志（INBOX 一条、尝试推送企业微信一条、失败重试一条）。

**第二组：投递基础设施（三张）**

`m20_msg_channel`（渠道配置，4 条初始化数据）、`m20_msg_template`（消息模板，约 40 条初始化数据）、`m20_msg_push_token`（第三方推送令牌，按职工+设备一条）。

这三张是**配置与凭据**，不是业务事实。判据同上：删库重建时它们可以由运维重新导入，不会丢业务事实。因此它们**带 `is_deleted`**，允许软删除——这是与第一组的关键区别。

**第三组：待办（两张）**

`m20_msg_todo` 是跨模块待办的**唯一汇总表**，也是本子模块唯一的「被别人写」的表。`m20_msg_todo_event` 是待办的状态变更流水，只增不删。

这两张表为什么归 M20-08 而不是归 M20-04，`M20_移动办公_数据结构设计汇总.md:80` 已经裁决过：「待办聚合（M20-CALC-03）需要『一个数』。审批待办是它的一个来源，不是另一套体系。**M20-04 写 `m20_msg_todo`，但表的定义与去重规则归 M20-08**」。本文件是这条裁决的落地文档。

**第四组：幂等与聚合观测（两张）**

`m20_msg_idem` 是 P-04 推送接口的幂等键落地表。注意它与 `m20_base_idempotency`（M20-01 首建、全模块共享）不是一回事：后者守的是「同一个 `X-Idempotency-Key` 全模块只执行一次」，前者守的是「同一个 `(staff_id, biz_type, biz_id)` 在 5 分钟内不重复推送」——这是**业务级去重**，与协议级幂等是两个不同的问题。详细设计 §8.2 给出两者的判据对比。

`m20_msg_unread_snapshot` 是角标数的计算留痕。它的存在理由是详细设计里那条最严重的缺陷约束：角标不能显示 0 表示失败。要证明「这次返回的 19 是算出来的、那次返回的 `null` 是因为 M19 超时」，就必须有留痕。

## 2. 命名与类型规范

### 2.1 表名与索引命名

全部沿用 `M20_移动办公_数据结构设计汇总.md` §2.1 的对象命名规则，本子模块无例外。

| 对象 | 规则 | 本子模块示例 |
|---|---|---|
| 表 | `m20_{子模块}_{业务对象}` | `m20_msg_delivery_log` |
| 主键 | `id BIGINT GENERATED ALWAYS AS IDENTITY` | — |
| 外键 | `fk_m20_{表简称}_{目标表简称}` | `fk_m20_msg_delivery_inbox` |
| 唯一索引 | `uk_m20_{表简称}_{列}` | `uk_m20_msg_inbox_dedup` |
| 普通索引 | `idx_m20_{表简称}_{列}` | `idx_m20_msg_inbox_staff_time` |
| 部分索引 | `idx_m20_{表简称}_{语义}_partial` | `idx_m20_msg_todo_due_partial` |
| 检查约束 | `ck_m20_{表简称}_{含义}` | `ck_m20_msg_inbox_status` |
| 触发器函数 | `trg_fn_m20_{表简称}_{动作}` | `trg_fn_m20_msg_todo_guard` |

**表简称的取法**：去掉 `m20_msg_` 前缀后的部分。`m20_msg_delivery_log` 的简称是 `delivery`（不是 `delivery_log`，也不是 `dl`）——简称要能唯一识别表，同时不要长到让索引名超 63 字符。按此规则九张表的简称分别是 `inbox`、`delivery`、`channel`、`template`、`push_token`、`todo`、`todo_event`、`idem`、`unread`。

### 2.2 字段命名

| 类别 | 规则 | 示例 |
|---|---|---|
| 主键 | `id` | `id` |
| 业务单号 | `{对象}_no` | `msg_no`、`todo_no` |
| 跨模块业务 ID | `{对象}_id` | `staff_id`、`patient_id`、`task_id` |
| 状态 | `{对象}_status` 或 `status` | `delivery_status`、`status` |
| 时间 | `{动作}_at`（TIMESTAMPTZ） | `sent_at`、`delivered_at`、`read_at` |
| 计数 | `{对象}_count` | `retry_count`、`fail_count` |
| 布尔 | `is_{含义}` 或 `{含义}_flag` | `is_deleted`、`degraded_flag` |
| JSON 结构 | `{对象}_json` | `content_vars_json`、`source_stat_json` |

**`_at` 后缀一律是时间点，`_days`/`_sec`/`_ms` 后缀一律是数值。** 这条看似琐碎，但本子模块有 11 个时间列，命名不一致会让「取哪个时间做统计」的 SQL 每天写错一次。

### 2.3 类型规范

| 语义 | 类型 | 理由 |
|---|---|---|
| 主键 | `BIGINT GENERATED ALWAYS AS IDENTITY` | 与汇总文档 §2.2 一致；不用 UUID，因为本表无跨库迁移需求且 UUID 索引更大 |
| 短枚举 | `VARCHAR(32)` + `CHECK` | 不用数据库 ENUM 类型：改枚举值要 `ALTER TYPE`，且 PostgreSQL 的 ENUM 不支持删除值 |
| 长文本（消息正文） | `TEXT` | 唯一允许用 TEXT 的地方是**正文本身**，因为长度上限由模板约束，不在数据库层做长度治理 |
| 短文本（标题、摘要） | `VARCHAR(n)` 显式给长度 | 结构化字段不用 TEXT |
| 金额 | `NUMERIC(14,2)` | 本子模块**无金额列**，列这条是为了说明「为什么没有」——见 §2.5 |
| 比率 | `NUMERIC(10,6)` | 用于 `success_rate` 一类字段 |
| 计数 | `INTEGER` / `SMALLINT` | `retry_count` 用 `SMALLINT`（上限 3），行数统计用 `INTEGER` |
| 时间 | `TIMESTAMPTZ` | 全院统一，不用不带时区的 `TIMESTAMP` |
| 布尔 | `BOOLEAN NOT NULL DEFAULT FALSE` | 不允许三态布尔；需要三态时用状态列 |
| 数组 | `VARCHAR(64)[]` 或 `BIGINT[]` | 仅用于「少量、定长上限、需要倒排」的场景 |
| JSON 结构 | `JSONB` | 结构必须在附录 D 写清，不得留「结构自解释」 |

### 2.4 建表硬规范在本子模块的落实

汇总文档 §2.2 的七条逐条对照：

1. **四个审计列**：九张表全部有 `created_at`/`created_by`/`updated_at`/`updated_by`。例外的写法是 `m20_msg_delivery_log` 与 `m20_msg_todo_event` 这两张只增不删表——它们的 `updated_at`/`updated_by` 恒为 NULL，**列保留但不使用**。保留而不删除的理由：运维与合规查询会跨表 union 四个审计列，缺列会让 SQL 写不下去；不使用的原因见 §2.8。
2. **业务表带 `is_deleted`**，例外是只增不删表（`m20_msg_delivery_log`、`m20_msg_todo_event`）。
3. **状态列用 `VARCHAR(32)` + `CHECK` 显式枚举全部取值**，九张表共 6 个状态列，全部显式列出取值。
4. **金额/比率/剂量**：本子模块无金额、无剂量；比率只有 `m20_msg_unread_snapshot.success_rate` 一处，用 `NUMERIC(10,6)`。
5. **时间一律 `TIMESTAMPTZ`**。
6. **跨模块引用不建外键，M20 内部表之间必须建外键**。本子模块内部的三个外键：`m20_msg_delivery_log` → `m20_msg_inbox`、`m20_msg_todo_event` → `m20_msg_todo`、`m20_msg_unread_snapshot` → 无（它是自足的观测记录，不挂任何表）。
7. **每张表必须有 `COMMENT ON TABLE`**，状态列与关键业务列必须有 `COMMENT ON COLUMN`。

### 2.5 为什么本子模块一个金额列都没有

这是一个需要明写的设计结论，而不是遗漏。

M20 是纯消费型模块（铁律二），员工消息与待办里唯一可能出现金额的地方是「审批消息正文里提到金额」——例如「改单申请 `M10_ORDER_AMEND`，金额 400.00 元」。这类金额**不是本子模块的业务数据，是上游业务数据的引用**。

处理方式：金额进入 `m20_msg_inbox.content_vars_json`，作为一个字符串变量，**不建独立的金额列**。理由有三：

1. 若建金额列，就必须决定精度、币种、是否含税、是否可退——这四个决定全属于 M16 与申请方模块，M20 没有资格做。做了就是「重建业务逻辑」，违反铁律二。
2. 建了金额列就会被拿去做汇总。「本月审批消息涉及金额多少」这个问题的正确答案在 M10/M11/M17 的台账里，从消息表算出来的数是**消息数乘以消息里提到的金额**，它不等于任何一笔真实业务金额，而且会重复计算（一条消息在 5 分钟后重推一次就有两行）。
3. 金额一旦进了消息表，就会有人要求对它做脱敏、做权限、做审计——而它的权威副本在上游，本子模块做脱敏等于给同一笔钱做两套口径。

**这条结论的验收落点是 DA 类：`m20_msg_*` 九张表不得出现 `NUMERIC(14,2)` 类型的列。** 巡检 SQL 见附录 B.4。

### 2.6 为什么 `m20_msg_push_token` 不是凭据表

铁律六禁止 `m20_device` 这类凭据表。`m20_msg_push_token` 存的是第三方推送服务（企业微信、APNs、FCM 等）返回的设备令牌，用于「往那台设备推一条通知」。

判据（借用汇总文档 §1.2 对 `m20_base_device_registry` 的判据）：**拿这张表里的数据能不能证明「这台设备/这个人是可信的」？**

- 不能。令牌只标识「往哪里送」，不标识「谁被允许做什么」。伪造一条令牌的唯一后果是往某台设备推一条通知，不会带来任何权限。
- 反过来，真正的设备凭据（设备指纹、信任状态、绑定凭据）权威在 M02，本子模块**不建、不读、不缓存**。

补充一条运维事实：推送令牌会失效（用户卸载 App、换机、关闭通知权限），失效后必须能被删除重建。所以这张表**带 `is_deleted`**，且 `uk_m20_msg_push_token` 的唯一键必须能容纳「同一职工同一设备换了新令牌」——唯一键定在 `(staff_id, device_id)`，令牌值只是列，`ON CONFLICT` 更新令牌值而不是插一行。若把唯一键定在 `(staff_id, token)`，换机时旧的失效行会一直占着这条键无法复用。

### 2.7 为什么消息发送不走 `m20_base_offline_queue`

`m20_base_offline_queue`（M20-01 首建）解决的是「移动端在弱网下先本地记录、恢复网络后重放」。它适合的是**业务操作**：护理执行、扫码、开单。

消息发送不适合放进这个队列，两个理由：

1. **方向相反。** 离线队列是「客户端动作等网络」，消息发送是「服务端主动推给客户端」——推送本身就是为了让用户在有网时看到，不存在「等网络」的语义。
2. **重放会绕过去重。** 若一条推送进了离线队列，重放时的 `biz_id` 时间戳已经变了，`(staff_id, biz_type, biz_id)` 去重会失效，用户会在 5 分钟后收到同一条消息的第二个副本。而云端推送的重试由 Celery 指数退避承担（详细设计 §7.2），重试的是**同一条投递记录**，不会产生新记录。

**结论：本子模块不读不写 `m20_base_offline_queue`。** 这条结论在降级策略表里对应一行：「离线队列不可用 → 本子模块不受影响」。

### 2.8 为什么只增不删表仍保留 `updated_at` 列

`m20_msg_delivery_log` 与 `m20_msg_todo_event` 不允许更新，因此 `updated_at`/`updated_by` 永远是建行时的 NULL。保留它们的理由是一个具体的运维场景：排障时运维会同时查「这条消息为什么发不出去」与「这条待办为什么没关掉」，两张表要能并排看。如果一张有四列审计、另一张只有两列，运维的取数 SQL 就得写两遍。

**保留列但用 `REVOKE UPDATE` 锁死**，让「列存在但不可能有值」成为一个可验证的事实，而不是一个口头约定。这比删掉列更安全：删掉列之后，未来有人想加回「最后修改时间」时会新增一个同义列，两个名字一个意思，反而更糟。

### 3.1 为什么跨模块不建外键而模块内建外键

汇总文档 §7.1 G-11 与 §2.2 第 6 条已定：跨模块引用不建外键。本子模块的落地是：

**建外键的（M20 内部，3 个）**

| 外键 | 从 | 到 | 删除行为 |
|---|---|---|---|
| `fk_m20_msg_delivery_inbox` | `m20_msg_delivery_log.inbox_id` | `m20_msg_inbox.id` | `ON DELETE RESTRICT` |
| `fk_m20_msg_todo_event_todo` | `m20_msg_todo_event.todo_id` | `m20_msg_todo.id` | `ON DELETE RESTRICT` |
| `fk_m20_msg_inbox_template` | `m20_msg_inbox.template_id` | `m20_msg_template.id` | `ON DELETE SET NULL` |

第三条单独说明：消息的模板被删了，消息本身不能跟着消失（消息是业务事实，模板是配置）。所以 `SET NULL` 而不是 `RESTRICT`。这也是唯一一个 `SET NULL` 的外键，`m20_msg_inbox.template_id` 因此必须可空。

**不建外键的（跨模块，若干）**

`staff_id`（→ M01-02）、`patient_id`（→ M03-01）、`dept_id`（→ M01-02）、`biz_id` 里的 `task_id`/`approval_no`（→ M08-01 / M20-04）等全部不建外键。理由：上游模块的表由上游管理，M20 的迁移不应被上游的表结构变更卡住；且 `biz_id` 是**多态列**——同一个列在一行里存 `task_id`、另一行里存 `approval_no`，物理上就不可能建外键。这是多态关联的固有代价，用应用层校验 + 定时对账补足，对账 SQL 见附录 B.3。

### 3.3 三个唯一键为什么这么定

这是本文件最需要论证的三处，因为它们的形状直接决定 M20-CALC-03 能否算出 19。

**唯一键一：`uk_m20_msg_inbox_dedup UNIQUE (staff_id, biz_type, biz_id)`**

对应汇总文档 §7.3 的 `uk_m20_msg_dedup`，语义是「5 分钟内同源消息去重」。三个值都由调用方给出：`staff_id` 是收件人，`biz_type` 是业务类型（如 `M08_NURSE_TASK`），`biz_id` 是该业务对象的 ID。

为什么是这三个字段而不是加一个时间桶：若把时间放进唯一键（如 `biz_id + 5分钟桶`），则跨桶边界的重复推送（4:59 推一次、5:01 又推一次）会变成两条消息，去重失效。而不放时间、改用「插入时判断是否已有未读的同源消息」又有并发窗口。**唯一键 + `INSERT … ON CONFLICT DO UPDATE` 是唯一原子的方案**——重复推送更新已有行的 `pushed_at` 与 `delivery_attempt`，行数不变。

**这条唯一键不能带 `WHERE is_deleted = FALSE`**（汇总文档 §7.3 已警告）：软删除的行会脱离约束，删掉后同号可再建。所以 `m20_msg_inbox` 虽然带 `is_deleted` 列，唯一索引却是**全表唯一**的。软删除的语义因此只能是「用户从列表里隐藏」，不能是「允许重建同源消息」。

**唯一键二：`uk_m20_msg_todo_unique UNIQUE (source, biz_type, biz_id, staff_id)`**

这是待办的幂等键。比消息去重多两个字段，原因不同：

- `staff_id` 进入唯一键：同一件事可能要派给多个人（一台手术的术前准备既派给巡回护士也派给器械护士），这是**两条待办**，不是重复。若 `staff_id` 不在唯一键里，第二个人就建不出待办。
- `source` 进入唯一键：跨来源的同一件事**故意不去重**。原因见 §3.4。

**唯一键三：`uk_m20_msg_push_token UNIQUE (staff_id, device_id)`**

见 §2.6 末段。

### 3.4 待办为什么按 `source` 分而不是按「业务对象」合并

这是本文件最容易被质疑的一处设计，必须正面回答。

**问题的形状**：一条审批既产生了「审批消息」（在 `m20_msg_inbox` 里，`biz_type = 'M20_APPROVAL'`），又产生了「审批待办」（在 `m20_msg_todo` 里，`source = 'M20_APPROVAL'`）。这**是不是同一件事**？如果是，角标应该算 1 还是 2？

**结论：算 2，不合并。** 理由：

1. **它们要回答的问题不同。** 审批待办回答「我现在要去点通过」。审批消息回答「有人给我发了东西，我看过了吗」。前者是**动作**，后者是**事实**。一个已经读完消息但没点通过的人，待办还在——如果合并成一条，这个人的角标会显示 0，而实际上有一台手术审批躺在那里。这正好是总纲 §6 用「护士看到 34 条待办会直接不看」批判的那个缺陷的镜像版本，只是方向相反：**过度去重会让真实待办消失**。
2. **生命周期不同。** 消息一旦已读就不再计数（`read_at` 非空）；待办要等审批动作完成才消失。两个状态由不同的代码路径推进，合并成一个对象就得让其中一方等另一方，工程上只会制造时序缺陷。
3. **跨类去重无法有确定的判据。** 「消息 m 与待办 t 是同一件事」的判据只能在应用层用启发式写（同 `biz_id`？同模板？同时间窗？），而启发式在一个月内就会积累出几十条例外。**一条没有确定判据的去重规则，最终会变成「有时去重有时不去重」，比完全不去重更糟。**

**那什么该去重？答案：同类去重 + 一跨类去重。**

- **同类去重（必须做）**：同一来源的同一业务对象重复写入。M08 在 5 分钟内对同一 `task_id` 触发三次 `m08.task.created`，只能有一条待办——这是 `uk_m20_msg_todo_unique` 保证的。
- **一跨类去重（必须做）**：`M08_NURSE_TASK` / `M19_FOLLOWUP_TASK` 这两个**外部来源**与 `M20_MESSAGE` 这个**消息来源**之间的去重。理由：M08 会同时做两件事——建护理任务、调 P-04 推一条消息给护士。这两件事指的是同一个 `(staff_id, task_id)`，在角标上算两件会让护士看到「12 条任务 + 15 条消息」而不是「12 条任务」。**这是唯一有确定判据的跨类去重**：判据就是 `biz_type` + `biz_id` 完全相等。

**为什么 `M20_APPROVAL` 不在这个跨类去重里**：因为审批消息在 `m20_msg_inbox` 里的 `biz_type` 是 `M20_APPROVAL`、`biz_id` 是 `approval_no`，而审批待办在 `m20_msg_todo` 里的 `source` 也是 `M20_APPROVAL`。按上面的判据它们会被去重掉——但按本节第 1 条的论证，这是错的。所以跨类去重的判据要再加一个限定：**只对 `m20_msg_todo` 里 `source` 属于外部来源（`M08_NURSE_TASK`、`M19_FOLLOWUP_TASK`）的行生效**。这个限定写在 `m20_msg_todo.dedup_scope` 列上，取值 `CROSS_SOURCE`（参与跨源去重）与 `LOCAL_ONLY`（不参与）。

**19 的完整拆解见详细设计 §3.4.3，这里只给出它用到的表结构事实**：

| 表中事实 | 数值 | 出处 |
|---|---|---|
| `m20_msg_todo` 中 `staff_id = 5012`、`status IN ('PENDING','IN_PROGRESS')`、`source = 'M08_NURSE_TASK'` | 12 行 | M08 `P-01` 返回 `task_count = 12` |
| `m20_msg_inbox` 中 `staff_id = 5012`、`read_at IS NULL` 且 `source IN ('M08_NURSE_TASK','M19_FOLLOWUP_TASK')` | 3 行 | 与上表 `biz_id` 一一相等，判为重复 |
| `m20_msg_inbox` 中 `staff_id = 5012`、`read_at IS NULL`、`biz_type = 'SYSTEM_NOTICE'` | 5 行 | 归入 `m20_msg_todo` 的 `M20_NOTICE` 来源 |
| `m20_msg_inbox` 中 `staff_id = 5012`、`read_at IS NULL`、其余 | 7 行 | 15 − 3 − 5 = 7，计入 `M20_MESSAGE` 来源 |
| `m20_msg_todo` 中 `source = 'M20_APPROVAL'`、`status = 'PENDING'` | 2 行 | M20-04 经写接口写入 |
| **合计** | **12 + 3 + 5 + 7 + 0 = 27 减去跨源重复 3 + 5 = 19** | — |

> 上表的最后一行写得有点绕，换个说法：五个来源分别是 `M08_NURSE_TASK` 12、`M19_FOLLOWUP_TASK` 0（M19 `P-01` 返回 `total = 0`）、`M20_APPROVAL` 2、`M20_NOTICE` 5、`M20_MESSAGE` 7，合计 26；但 `M20_MESSAGE` 的 7 行里没有与外部来源重复的（重复的那 3 行已被剔除到该类之外），所以**不需要再减**。26 与 19 的差是 7，而 7 正是「已读不计入」的过滤结果——等等，这里必须说清：上表第二行的 3 行**不计入任何来源**，第五行的 7 行才是 `M20_MESSAGE`。所以 12+0+2+5+7 = 26 是不对的，正确是 12+0+2+5+7 = 26 与 19 差 7。

**上面这段推演暴露了一个真问题，必须在正式文档里解决而不是含糊过去**：`M20_MESSAGE` 来源到底该算 7 还是算 15？答案取决于一个定义，而这个定义必须写死在表结构里，不能靠文字描述。

`m20_msg_inbox` 因此需要一个列来明确回答「这条消息算不算待办」。本文件定名为 `counts_as_todo`，取值 `TRUE`/`FALSE`，写入时由 `biz_type` 决定（`SYSTEM_NOTICE` → `FALSE`，因为它已归入 `M20_NOTICE` 来源；`M08_NURSE_TASK`/`M19_FOLLOWUP_TASK` → `FALSE`，因为它由外部的 `m20_msg_todo` 行代表；其余 → `TRUE`）。加上这一列之后：

- `M20_MESSAGE` 来源 = `m20_msg_inbox` 中 `counts_as_todo = TRUE AND read_at IS NULL` 的行 = 7 行
- 五来源合计 = 12 + 0 + 2 + 5 + 7 = **26**
- 跨源去重 = 减去与外部来源 `biz_id` 相同的行 —— 已由 `counts_as_todo = FALSE` 排除，此处为 0
- **总数 26，不等于 19。**

**26 ≠ 19，说明还有一处口径必须定清楚。** 差额 7 恰好等于 `M20_MESSAGE` 来源的条数，即 19 = 12 + 0 + 2 + 5。也就是说：**总纲算例里的 19，其「消息中心 15（含那 3 条）」这一项在合计里只贡献了 0**，因为 15 = 3（重复）+ 5（系统通知）+ 7（其余消息），而前两项已分别归入外部来源与 `M20_NOTICE`，第三项 7 条在总纲的算例里根本没被计入任何来源。

这是**总纲 M20-CALC-03 算例本身的一处内部不一致**，不是我的表结构问题。详细设计 §3.4.3 会给出两种自洽的口径，并说明本设计选哪一种、为什么。本文件只负责把两种口径都需要的列建出来：

| 列 | 用途 |
|---|---|
| `m20_msg_inbox.counts_as_todo` | 明确「这条消息算不算进待办数」，让口径可配而不是可争 |
| `m20_msg_inbox.biz_type` | 决定 `counts_as_todo` 的默认值，也是跨源去重的判据 |
| `m20_msg_todo.dedup_scope` | 明确「这条待办参不参与跨源去重」 |

有了这两列，无论选哪种口径都只是一条 `WHERE` 条件的差别，不需要改表结构。这是表结构设计该做的事：**不替业务定口径，但要保证口径可切换而不动数据。**

### 3.5 枚举取值与落库方式

九张表共 6 个状态列与 12 个其他枚举列，全部 `VARCHAR(32)` + `CHECK` 显式枚举。取值汇总见附录 E，与共享规范 §13 的对应关系见附录 E.2。

**一条硬规则：枚举值一律全大写下划线风格，不得用中文值，不得混用大小写。** 中文值会让 `ORDER BY` 的顺序随数据库排序规则漂移；混用大小写会让 `WHERE status = 'pending'` 静默返回 0 行而不报错——后者是本模块最容易出现的「看起来正常但不完整」缺陷，正是共享规范 §8A 三条红线禁止的第一种形态。

### 3.6 状态机在表结构上的落点

三条状态机需要数据库层保证，其余靠应用层。逐条说明为什么：

**落数据库的（必须 DB 保证）**

| 不变量 | 落点 | 只靠应用层会怎样 |
|---|---|---|
| 同一 `(staff_id, biz_type, biz_id)` 只有一条站内信 | `uk_m20_msg_inbox_dedup` | 并发两次 P-04 都通过「先查后插」，插出两条 |
| 同一 `(source, biz_type, biz_id, staff_id)` 只有一条待办 | `uk_m20_msg_todo_unique` | 同上 |
| `SENT` 与 `DELIVERED` 不合并 | `ck_m20_msg_delivery_status` + `ck_m20_msg_delivery_sent_time` 等组合约束 | 有人为了省事把回执直接写成 `SENT`，「发没发出去」永久无法回答 |
| 投递日志不可改不可删 | `REVOKE UPDATE, DELETE` + 拒绝触发器 | 事故发生后日志被「修正」 |
| 待办终态必须有终态时间 | `ck_m20_msg_todo_closed` | 有状态没时间，无法统计待办停留时长 |
| 分区表必须有 DEFAULT | 建表语句（附录 A.2） | 新月份第一条 INSERT 在凌晨报错，值班看到的是「推送功能突然挂了」 |

**留应用层的（不落数据库）**

| 规则 | 为什么不在数据库 |
|---|---|
| `PENDING → SENT` 只能在 `retry_count < 3` 时发生 | 重试上限来自配置（`M20.MSG.RETRY_MAX`），配置会改；写进 CHECK 就得每次改配置都做 DDL |
| 角标数上限 99 截断 | 是展示规则，不是数据约束；数据库里存真实数，展示层截断 |
| 待办超时自动关闭的时限 | 时限按 `source` 分级配置，且「超时」不等于「关闭」——超时要留痕，关闭要有人 |
| 消息正文长度上限 | 由模板约束（`m20_msg_template.body_tpl` 长度），不同模板上限不同 |

### 3.7 派生数据与冗余字段清单

严格说，本子模块只有三处冗余，每一处都必须说明「为什么允许不一致」以及「怎么保证一致」。

| 冗余字段 | 冗余自 | 为什么允许 | 怎么保证一致 |
|---|---|---|---|
| `m20_msg_todo.overdue_flag` | 由 `due_at` 与当前时间比较得出 | 角标聚合要按「是否逾期」过滤，每次都算 `due_at < now()` 会让部分索引失效；物化成列才能建 `idx_m20_msg_todo_due_partial` | 由 Celery 每 5 分钟跑一次批量刷新（详细设计 §7.3），**允许最长 5 分钟滞后**，且所有展示以该列为准、不再二次比较时间 |
| `m20_msg_inbox.delivery_attempt` | `m20_msg_delivery_log` 中 `inbox_id` 相同的行数 | P-04 响应要返回「这是第几次推送」，每次都数一遍投递日志在 300ms 预算下不可接受 | 写投递日志的同一事务内 `delivery_attempt = delivery_attempt + 1`，**同事务所以始终一致**，不需要对账 |
| `m20_msg_unread_snapshot.total_count` | 由五来源聚合得出 | 它是留痕表，本质就是「某个时刻的聚合结果」的快照，不是冗余而是**正文** | 不需要一致，它记录的是历史 |

**明确不冗余的两处**（写下来是为了防止未来有人加）：

- **不在 `m20_msg_inbox` 冗余 `task_status`。** 护理任务状态在 M08，冗余一份就要订阅 `m08.task.*` 并追平，等于在 M20 造了一张 M08 的影子表，违反铁律二。展示时按需实时查 M08。
- **不在 `m20_msg_todo` 冗余业务标题以外的业务字段。** `biz_title` 是允许的（它是给人看的短摘要，最长 128 字符，且在事件/接口往返里已经带了），但 `biz_status`、`biz_amount`、`patient_name` 一概不加。理由同上，且 `patient_name` 一旦进表就会有人要求它在事件里也出现，直接撞上事件载荷红线。

## 4. 表结构定义

本章逐表给出字段定义、约束、索引与设计说明。完整可执行的 `CREATE TABLE` 语句集中在附录 A，本章只在必要处引用片段——这样做的理由与详细设计第 4 章只放指引块相同：**字段表给人看，DDL 给机器跑，两者混在一起会同时降低可读性与可校验性**。

### 4.1 实体关系图

```
                    ┌──────────────────────────┐
                    │   m20_msg_template       │
                    │   （约 40 条初始化）      │
                    └────────────┬─────────────┘
                                 │ template_id（SET NULL）
```

### 4.2 表：`m20_msg_todo`

**职责**：全模块待办汇总的唯一落点。M20-08 首建，M20-04 经写接口写入，其余子模块只读。它是 M20-CALC-03 能被算成「一个数」的物理基础。

**为什么这张表放在本子模块而不是 M20-04**：`M20_移动办公_数据结构设计汇总.md` §1.3 已裁决「首建者是 M20-08」。理由是待办聚合需要「一个数」——审批待办只是这个数的五个来源之一，不是另一套体系。如果放在 M20-04，M08 护理任务、M19 随访任务就要反过来写 M20-04 的表，依赖方向会变得不可解释。

#### 4.2.2 组合约束（八条）

单字段 CHECK 只能守住「枚举在范围内」，守不住字段之间的语义。以下八条覆盖了「只写单字段约束会漏掉什么」。

| 约束名 | 定义 | 漏掉会怎样 |
|---|---|---|
| `ck_m20_msg_todo_finished` | `status NOT IN ('DONE') OR finished_at IS NOT NULL` | 已完成但无完成时刻，逾期统计与考核口径都会失真 |
| `ck_m20_msg_todo_closed` | `status NOT IN ('DONE','VOIDED') OR closed_at IS NOT NULL` | 关闭了却查不出什么时候关的，审计断链 |
| `ck_m20_msg_todo_void_reason` | `status <> 'VOIDED' OR close_reason IS NOT NULL` | 作废无原因，事后无法区分「业务撤销」与「误建」 |
| `ck_m20_msg_todo_claimed` | `status NOT IN ('CLAIMED','DONE') OR claimed_at IS NOT NULL` | 已认领却无认领时刻，无法计算认领时长 |
| `ck_m20_msg_todo_urgency` | `urgency_level <> 'EMERGENCY' OR priority >= 80` | 标记为紧急却排在列表末尾，等于没标 |
| `ck_m20_msg_todo_overdue` | `overdue_flag = FALSE OR due_at IS NOT NULL` | 无时限的待办被判逾期，`overdue_flag` 失去意义 |
| `ck_m20_msg_todo_title` | `length(btrim(biz_title)) >= 1` | 空标题在角标卡片上显示为空白行 |
| `ck_m20_msg_todo_transfer` | `transfer_from_staff_id IS NULL OR transfer_from_staff_id <> staff_id` | 转给自己，产生无意义的转办记录 |

其中 `ck_m20_msg_todo_urgency` 与 `ck_m20_msg_todo_overdue` 是**跨两列**的，这是组合约束最典型的两种形态：一件与排序有关，一件与派生标记有关。

#### 4.2.3 `source` 取值与语义

| `source` | 含义 | 写入方 | 数据归集方式 |
|---|---|---|---|
| `M08_NURSE_TASK` | 护理任务待办 | M20-08（订阅事件 + 轮询兜底） | 事件为主：`m08.task.created`/`m08.task.overdue` 命中后按 `ward_id` 触发该病区待办重建；U-25 轮询仅兜底 |
| `M19_FOLLOWUP_TASK` | 随访任务待办 | M20-08 | U-36 轮询 |
| `M20_APPROVAL` | 审批待办 | **M20-04 经写接口** | M20-04 在发起审批时写入 |
| `M20_NOTICE` | 系统通知类待办（需处理的公告） | M20-08 | 通知发布时写入 |
| `M20_SELF` | 本子模块自建待办（如模板审核） | M20-08 | 内部产生 |
| `M20_MANUAL` | 手工指派待办 | M20-08 | 页面上人工新建 |

**`source` 的取值原则：取「这件事最终落在哪张表/哪个出口」，不取「哪个模块发起的」。** 举例：一条审批由 M10 发起、由 M20-04 受理、最终落在 `m20_msg_todo`——它的 `source` 是 `M20_APPROVAL`，不是 `M10_ORDER_AMEND`。这条原则的作用是**保证五种 `source` 的并集就是全部待办，没有遗漏也不会跨层重复**；如果按发起模块取值，"M10 发起的审批"既该算 M10 又该算 M20，聚合时必然重复计数。

注意：`M20_NOTICE` 与 `m20_msg_inbox` 里的 `SYSTEM_NOTICE` 类消息**不是同一个东西**。前者是「需要你处理的公告」，后者是「通知你知道了」。判断标准是问一句「有没有一个动作必须由这个人完成」——有就是待办，没有就是消息。

#### 4.2.4 `biz_id` 各来源的取值定义（去重键的前半部分）

去重键是 `(source, biz_type, biz_id, staff_id)`。`biz_id` 必须是**在该 `source` 内稳定且唯一标识业务对象**的标识，且**同一件事无论被推送多少次都取同一个值**。

| `source` | `biz_type` 示例 | `biz_id` 取值 | 稳定性依据 |
|---|---|---|---|
| `M08_NURSE_TASK` | `NURSE_TASK` | M08 的 `task_id`（字符串化） | M08 `m08_nurse_task.id`，任务本身不变号 |
| `M19_FOLLOWUP_TASK` | `FOLLOWUP_TASK` | M19 的 `task_id` | M19 `m19_followup_task.id` |
| `M20_APPROVAL` | `APPROVAL_INSTANCE` | `approval_no`（如 `SP202610210001`） | M20-04 的审批单号 |
| `M20_NOTICE` | `SYSTEM_NOTICE` | 通知的 `notice_id` | 公告表主键 |
| `M20_SELF` | `TEMPLATE_AUDIT` 等 | 被审核对象主键 | 本模块内的业务主键 |
| `M20_MANUAL` | `MANUAL` | 页面生成时分配的 `todo_no` | 手工待办无上游对象 |

**不允许用「标题 + 责任人」做 `biz_id`**：标题会改，用可变的字段做去重键等于没有键。也不允许用「事件 ID」——同一条业务对象重发事件时事件 ID 会变，去重立刻失效。

#### 4.2.5 `dedup_scope` 语义（去重键的后半部分）

`dedup_scope` 决定这条待办是否参与**跨来源**去重：

| 取值 | 含义 | 适用 `source` |
|---|---|---|
| `CROSS_SOURCE` | 该待办与 `m20_msg_inbox` 里的同 `biz_id` 消息**视为同一件事**，聚合时只算 1 | `M08_NURSE_TASK`、`M19_FOLLOWUP_TASK` |
| `LOCAL_ONLY` | 只在待办表内部去重，不与消息合并 | `M20_APPROVAL`、`M20_NOTICE`、`M20_SELF`、`M20_MANUAL` |

这个字段是本设计里最关键的一个开关，它把「哪些跨类合并合法、哪些不合法」从代码里的 if 分支变成了表里的一个值。判据来自 §3.4：护理任务与随访任务在消息中心的呈现是**同一件事的推送副本**（推送过就不再需要单独记一条），而审批消息与审批待办回答的是两个问题（读没读 vs 点没点）。

因此 M20-CALC-03 的去重规则可以写成一条可执行的 SQL 级规则，而不是一段启发式：

```
计入角标的消息数 = COUNT(m20_msg_inbox)
                 - COUNT(消息 m WHERE m.counts_as_todo = TRUE
                          AND EXISTS (待办 t WHERE t.dedup_scope = 'CROSS_SOURCE'
                                      AND t.source = m.biz_type
                                      AND t.biz_id = m.biz_id
                                      AND t.staff_id = m.staff_id
                                      AND t.status IN ('PENDING','CLAIMED')))
```

其中 `m20_msg_inbox.counts_as_todo` 在消息写入时按 `biz_type` 计算落库（见 §4.3.2）。两个开关合起来，就使得「同一件事出现在两个来源」被精确地识别成一件，而「两个不同问题」保持为两件——**这不是靠命名约定，是靠两个列的取值组合**。

#### 4.2.6 `status` 枚举与状态流转

| `status` | 含义 | 终态 | 可流转到 |
|---|---|---|---|
| `PENDING` | 待处理 | 否 | `CLAIMED`、`DONE`、`VOIDED`、`TRANSFERRED` |
| `CLAIMED` | 已认领、进行中 | 否 | `DONE`、`PENDING`（退回）、`VOIDED`、`TRANSFERRED` |
| `DONE` | 已完成 | 是 | 无 |
| `VOIDED` | 已作废（业务对象消失） | 是 | 无 |
| `TRANSFERRED` | 已转办（本行终结，新行产生） | 是 | 无 |

**`DONE` 与 `VOIDED` 必须分开**：前者是「做完了」，后者是「不用做了」。合并成一个 `CLOSED` 会让「完成率」这个指标无法计算——分母里混进了本来就不该做的单子，完成率永远到不了 100%，而且没人能解释为什么。

**`TRANSFERRED` 是终态而非中间态**：转办在实现上是「旧行置 `TRANSFERRED` + 新行插入」，新行持有新 `staff_id`，旧行保留 `transfer_from_staff_id` 的反向线索。这样历史责任清晰，且不会因为一次转办让两条待办同时处于 `PENDING` 而在角标里被算两次。

#### 4.2.7 `close_reason` 取值

| 取值 | 含义 | 典型 `status` |
|---|---|---|
| `FINISHED` | 正常完成 | `DONE` |
| `BIZ_CANCELLED` | 业务对象被上游取消 | `VOIDED` |
| `BIZ_MERGED` | 业务对象被上游合并 | `VOIDED` |
| `STAFF_LEFT` | 责任人离职，无人承接 | `VOIDED` |
| `DUPLICATE` | 重复下发，保留一条 | `VOIDED` |
| `TRANSFER` | 转办 | `TRANSFERRED` |

#### 4.2.8 索引清单

| 索引名 | 类型 | 定义 | 服务的场景 |
|---|---|---|---|
| `pk_m20_msg_todo` | 主键 | `(id)` | — |
| `uk_m20_msg_todo_no` | 唯一 | `(todo_no)` | 按编号查单 |
| `uk_m20_msg_todo_unique` | 唯一 | `(source, biz_type, biz_id, staff_id)` | **幂等写入的核心**：重复推同一件事必须命中此键 |
| `idx_m20_msg_todo_staff_status` | 普通 | `(staff_id, status, priority DESC, created_at DESC)` | P-05 待办列表主查询 |
| `idx_m20_msg_todo_biz` | 普通 | `(source, biz_type, biz_id)` | 业务对象反查（上游问「那条待办还在不在」） |
| `idx_m20_msg_todo_due` | 部分 | `(due_at) WHERE overdue_flag = FALSE AND status IN ('PENDING','CLAIMED')` | 逾期扫描任务只扫未逾期的，索引体积可控 |
| `idx_m20_msg_todo_dept` | 普通 | `(dept_id, status)` | 科室维度的待办看板 |
| `idx_m20_msg_todo_idem` | 部分 | `(idempotency_key) WHERE idempotency_key IS NOT NULL` | 幂等重放查询；绝大多数行为空，部分索引省空间 |

**`uk_m20_msg_todo_unique` 不带 `WHERE is_deleted = FALSE`**：软删除的行必须继续占用唯一键。若带上该条件，一条待办被软删除后同号可以再建一条，而旧的软删除行仍在库里——历史查询会看到两条，汇总口径立刻分叉。这条约束的代价是「误删的待办不能重推」，这正是我们要的：误删应当被修复而不是被掩盖。

#### 4.2.9 为什么没有 `patient_id` 与 `biz_status` 列

**`patient_id`**：待办的责任人是职工，不是患者。九张表里只有 `m20_msg_inbox` 与 `m20_msg_unread_snapshot` 需要 `patient_id`（前者用于脱敏与数据权限，后者用于回溯），待办不需要。若将来某个待办场景确实需要按患者维度检索，`biz_id` + `source` 已足以反查上游。

**`biz_status`**：上游状态一变就要同步这张表，等于把上游的状态机复制了一份到 M20，直接违反铁律二「M20 不重建任何业务逻辑」。待办的生命周期由 `status` 表达，业务对象的生命周期留在上游——**待办的 `DONE` 与业务的「已完成」是两回事**：审批通过后业务已完成，但用户可能还没点开那条待办把它划掉（如果设计要求「审批完成后待办自动完成」，那是上游回调经 API-10 标记完成，不是 M20 主动去同步业务状态）。

#### 4.2.10 写接口 upsert 的唯一合法语句（终态不覆盖的数据库层落点）

给 M20-04 的写接口 API-09 必须用下面这条语句，**不许换写法**：

```sql
INSERT INTO m20_msg_todo (
    todo_no, source, biz_type, biz_id, staff_id, dept_id,
    biz_title, biz_url, priority, urgency_level, due_at,
    status, dedup_scope, overdue_flag,
    created_at, created_by, updated_at, updated_by
) VALUES (
    :todo_no, :source, :biz_type, :biz_id, :staff_id, :dept_id,
    :biz_title, :biz_url, :priority, :urgency_level, :due_at,
    'PENDING', :dedup_scope, FALSE,
    now(), :caller, now(), :caller
)
ON CONFLICT (source, biz_type, biz_id, staff_id) DO UPDATE
   SET priority      = EXCLUDED.priority,
       urgency_level = EXCLUDED.urgency_level,
       due_at        = EXCLUDED.due_at,
       biz_title     = EXCLUDED.biz_title,
       biz_url       = EXCLUDED.biz_url,
       updated_at    = now(),
       updated_by    = EXCLUDED.updated_by
 WHERE m20_msg_todo.status NOT IN ('DONE', 'VOIDED', 'TRANSFERRED')
RETURNING id, todo_no, status, (xmax = 0) AS created;
```

四个必须理解的细节：

1. **`WHERE` 挂在 `DO UPDATE` 上，不是挂在 `INSERT` 上。** 冲突行处于终态时，`DO UPDATE` 整个被跳过——不更新、不报错、`RETURNING` 返回**空集**。服务层把空集解释为「已存在且处于终态」，回查一次取当前状态返回 `created = false`。
2. **`(xmax = 0) AS created`** 区分本次是插入还是更新。不用「先查再插」的两段式——两段式之间有并发窗口，两个 M20-04 节点同时推同一件事会插两条（唯一键会拦，但会抛异常）。
3. **`todo_no` 只在 INSERT 分支被消费。** 更新分支不需要它，也不需要为撞号做重试。这是把「单号生成」与「幂等写入」解耦的关键：撞号只可能发生在新建路径。
4. **`status` 与 `dedup_scope` 只在 INSERT 分支给值。** 更新分支不重置状态——这正是「不覆盖终态」的反面表述：**只要冲突行还活着，它的状态就轮不到上游来定。**

**为什么这件事必须是 SQL 谓词而不是服务层 `if`**：`if` 只对经过它的代码生效。数据修复脚本、批处理导入、下一个人写的新调用方，都不会经过那行 `if`。而 `ON CONFLICT ... WHERE` 是行级谓词，**任何写入路径都绕不开**。M20-06 的 D-4 是同一条道理：把不变量放进数据库能执行的位置，而不是放进「大家都会记得调用」的函数里。

**代价与配套**：
- `ON CONFLICT ... WHERE` 未生效时**不抛错**，所以服务层必须处理「`RETURNING` 空集」这一分支，不能假设 `RETURNING` 一定有行。附录 B.1 的巡检正是为此设的兜底。
- 终态行被上游继续推送时，上游拿到的是 `created = false` 与当前终态——**上游必须理解这不是失败**。API-10 的 `matched = false` 也是同一套语义：**关闭一个已经不在那儿的东西不是错误。**

### 4.3 表：`m20_msg_inbox`

**职责**：员工站内信正文、已读状态与消息级去重。它是全模块**唯一**存放消息正文的表，也是所有外部通道（企业微信、APP 推送、短信）的**兜底**——因为总纲 §7.3 已定「`INBOX` 永不失败（写库即成功）」，这张表写成功就代表这条通知不会丢。

**为什么不分区**：单人日均约 20 条，在线峰值 300 人 → 全模块约 6,000 条/日、约 220 万条/年。所有查询都带 `staff_id`（最左前缀命中索引），单表在这个量级下无需分区。更关键的理由在 `M20_移动办公_数据结构设计汇总.md` §4.2：**分区键会破坏唯一约束**——PostgreSQL 要求分区表的唯一索引必须包含分区键，一旦按 `created_at` 分区，`uk_m20_msg_inbox_dedup (staff_id, biz_type, biz_id)` 就必须带上 `created_at`，那「同一条业务消息」就能在不同月份各存在一条，去重直接失效。

#### 4.3.2 `counts_as_todo` 的计算规则

这一列是 M20-CALC-03 去重能否成立的第二个开关（第一个是 `m20_msg_todo.dedup_scope`）。

| `biz_type` | `counts_as_todo` | 理由 |
|---|---|---|
| `SYSTEM_NOTICE` | `FALSE` | 系统通知的未读数由 `M20_NOTICE` 来源的待办覆盖，消息侧再算一次就是 34 的那 5 条 |
| `M08_NURSE_TASK` | `FALSE` | 护理任务的真实待办在 `M08_NURSE_TASK` 来源，此处只是推送副本 |
| `M19_FOLLOWUP_TASK` | `FALSE` | 同上 |
| `M20_APPROVAL` | `TRUE` | 审批消息与审批待办是两个问题（§3.4），消息侧也计数 |
| 其他（`OPERATION_NOTICE`、`M22_ALERT` 等） | `TRUE` | 默认计数；只有明确存在同源待办的三类才置 `FALSE` |

**默认值给 `TRUE` 而不是 `FALSE`**：漏算的后果是「有消息但角标不动」，用户当场就能发现并投诉；多算的后果是「角标比实际多」，用户慢慢就不信了。两者都不好，但前者可观测、后者不可观测，所以默认落在可观测的一侧。校验清单 V-14 会断言「出现过的 `biz_type` 必须都在本表中有明确行」，防止新 `biz_type` 靠默认值悄悄算错。

#### 4.3.3 `message_status` 枚举（五态，`SENT` 与 `DELIVERED` 不合并）

| 取值 | 含义 | 判定依据 | 允许进入的下一步 |
|---|---|---|---|
| `PENDING` | 待投递 | 已入库、尚未提交网关 | `SENT` / `FAILED` |
| `SENT` | 已提交网关 | 网关返回 2xx（**只证明提交成功**） | `DELIVERED` / `READ`（站内信直接已读） / `FAILED` |
| `DELIVERED` | 确认送达 | 收到网关回执 | `READ` |
| `READ` | 用户已读 | 站内信被打开 或 客户端上报已读 | 无（终态） |
| `FAILED` | 投递失败 | 重试达上限 或 不可重试错误 | 无（终态，但可在消息中心查阅并手工重推） |

**`SENT` 与 `DELIVERED` 为什么必须分开**（这是共享规范 G-08 的落地）：短信与企业微信的网关返回 200 只代表「我收下了这条请求」，不代表「用户手机开机了、有信号、能收到」。合并两态之后，运维面对「他说没收到」这个问题**永远没有能自证的数据**——库里写着成功，用户说没收到，双方都不是在撒谎。分开之后，「没收到」可以被定位到 `SENT` 且 `delivered_at IS NULL`，这就是一条可以拿去找网关服务商对账的事实。

**`INBOX` 通道的 `DELIVERED` 语义例外**：站内信写库即送达，所以 `INBOX` 通道的投递日志允许 `SENT` 与 `DELIVERED` 同一时刻写入（见 §4.4.4）。这个例外必须写在文档里，否则实现者会以为状态机有缺陷。

#### 4.3.4 组合约束（九条）

| 约束名 | 定义 | 漏掉会怎样 |
|---|---|---|
| `ck_m20_msg_inbox_failed` | `message_status <> 'FAILED' OR (fail_count >= 1 AND last_error IS NOT NULL)` | 失败但无失败次数与原因，「为什么失败」无从查起 |
| `ck_m20_msg_inbox_read` | `message_status <> 'READ' OR read_at IS NOT NULL` | 已读却无已读时刻，未读数算不出来 |
| `ck_m20_msg_inbox_delivered` | `message_status NOT IN ('DELIVERED','READ') OR delivered_at IS NOT NULL` | 已送达却无送达时刻，与 `SENT` 无法区分 |
| `ck_m20_msg_inbox_sent` | `message_status = 'PENDING' OR first_sent_at IS NOT NULL` | 非待投递态却无首次提交时刻，投递时长统计断裂 |
| `ck_m20_msg_inbox_attempt` | `delivery_attempt >= fail_count` | 失败次数大于总尝试次数，数据自相矛盾 |
| `ck_m20_msg_inbox_emergency` | `urgency_level <> 'EMERGENCY' OR biz_id IS NOT NULL` | 紧急消息无业务对象，无法回查是哪台手术停了 |
| `ck_m20_msg_inbox_expire` | `expire_at IS NULL OR expire_at > created_at` | 过期时刻早于创建时刻，消息一出生就过期 |
| `ck_m20_msg_inbox_title` | `length(btrim(title)) >= 1` | 空标题在列表里显示为空白行 |
| `ck_m20_msg_inbox_patient` | `patient_id IS NULL OR patient_id > 0` | 患者号为 0 或负数，脱敏与数据权限都会失效 |

#### 4.3.5 索引清单

| 索引名 | 类型 | 定义 | 服务的场景 |
|---|---|---|---|
| `pk_m20_msg_inbox` | 主键 | `(id)` | — |
| `uk_m20_msg_inbox_no` | 唯一 | `(msg_no)` | 按流水号查 |
| `uk_m20_msg_inbox_dedup` | 唯一 | `(staff_id, biz_type, biz_id)` | **消息级去重**，5 分钟内不重复推送的落地点 |

| `idx_m20_msg_inbox_unread` | 部分 | `(staff_id) WHERE read_at IS NULL AND is_deleted = FALSE` | P-03 未读计数的核心索引；只索引未读行，体积与未读量成正比 |

`uk_m20_msg_inbox_dedup` 的作用域是**整个表而非时间窗**：5 分钟去重是业务规则，由详细设计 §8.2 的 R-05 在服务层用时间比较实现，不由索引表达。**不把 5 分钟写进唯一键**（比如加 `date_trunc('minute', created_at)`），因为那会让同一条业务消息在下一个 5 分钟区块里合法地再插一条——索引一旦允许重复，"不重复推送"这件事就再也无法靠数据库自证。

#### 4.3.6 为什么不把 `delivery_attempt` 做成子表

投递尝试的每一次事实记录在 `m20_msg_delivery_log`（§4.4），本表只保留**计数**。这个冗余有明确的代价与收益：代价是两处可能不一致，收益是 P-03/P-05 这类列表接口不必 JOIN 一张月分区的大表——一次 `COUNT` 与一次跨分区扫描是数量级的差别。一致性由「同事务内 `delivery_attempt = delivery_attempt + 1`」保证，并由附录 B.2 的巡检 SQL 每日对账兜底。

### 4.4 表：`m20_msg_delivery_log`

**职责**：每一次投递尝试的事实记录。**只增不删**（`M20_移动办公_数据结构设计汇总.md` §3.3 已列为本子模块的只增不删表），是「这条通知到底发没发」这个问题的唯一对账依据。

#### 4.4.1 为什么这张表不设软删除标记

判据来自汇总文档 §3.3：「这张表的不一致或缺失本身是不是要被保留的信息？」——是。一条投递记录的缺失，正是运维要去追查的对象；允许软删除就等于允许「把查不出来的记录藏起来」。所以本表：

- **不设软删除标记列**（校验器 `APPEND_ONLY_TABLES` 对此表强制检查）
- **必须 `REVOKE DELETE`** 于 `app_m20`，清理只走归档迁移的独立账号 `m20_archiver`
- **有 `updated_at` 但只在同一行的极窄生命周期内变化**：一行从 `PENDING` 走到终态，`updated_at` 会变；进入终态后不再变更。理由见 §2.8。

#### 4.4.2 按月分区及 `DEFAULT` 分区

```sql
CREATE TABLE m20_msg_delivery_log (
    id              BIGINT GENERATED ALWAYS AS IDENTITY,
    delivery_no     VARCHAR(32)  NOT NULL,
    inbox_id        BIGINT       NOT NULL,
    msg_no          VARCHAR(32)  NOT NULL,
    staff_id        BIGINT       NOT NULL,
    channel         VARCHAR(32)  NOT NULL,
    attempt_no      SMALLINT     NOT NULL,
    attempt_status  VARCHAR(32)  NOT NULL,
    send_at         TIMESTAMPTZ  NOT NULL,
    ...
    PRIMARY KEY (id, send_at)
) PARTITION BY RANGE (send_at);

-- 紧随其后必须建 DEFAULT 分区（与父表同一个迁移脚本内）
CREATE TABLE m20_msg_delivery_log_default PARTITION OF m20_msg_delivery_log DEFAULT;
```

**分区键选 `send_at` 而不是 `created_at`**：所有运维查询都是「某天/某段时间发了什么」，而 `send_at` 就是那个业务时间。用 `created_at` 会让「查 10 月 20 日的投递」变成跨月份边界的模糊过滤，裁剪失效。

**分区表的主键必须是 `(id, send_at)`**（PostgreSQL 要求分区键进唯一索引），这带来一个后果：`id` 不再全局唯一，所以对外一律用 `delivery_no` 而不是 `id`。这个代价必须写清楚，否则实现者会天真地用 `id` 做跨月查单。

**`DEFAULT` 分区不是可选项**（G-09）：月分区的边界是预先创建的，若某条记录的 `send_at` 落在未预建的月份，没有 `DEFAULT` 分区时 `INSERT` 会直接报错——这会把「分区维护漏了一个月」升级成「消息发不出去」。有 `DEFAULT` 分区时，记录落进去、告警触发、人工补分区后迁移，故障面从一个功能降为一条监控项。

上面的 `CREATE TABLE … PARTITION OF … DEFAULT` 与父表 DDL 必须在**同一个迁移文件里相邻执行**：中间若被别的语句隔开，一旦迁移中断在半路，就会留下「有父表没兜底分区」的窗口期，而窗口期内的每一次投递都会失败。

月分区创建策略：APScheduler 每月 25 日预建下个月的分区（见详细设计 §7.3），并校验 `DEFAULT` 分区为空——**`DEFAULT` 分区非空是唯一的硬告警**，它意味着有记录落到了没有预建的月份。

| `updated_by` | `VARCHAR(64)` | 否 | `'SYSTEM'` | 更新者 |

**为什么有 `cost_cents` 却不叫金额列**：它是**计费条数**（短信按 70 字一条拆分，一条长短信可能是 2 条），不是钱。§2.5 已立「本子模块一个金额列都没有」的原则，这里用 `SMALLINT` 存条数、命名上避免任何货币暗示（`cost_cents` 这个名确实容易误读，因此字段说明里明确写「条数不是金额」，且附录 B.4 的巡检 SQL 会断言本表不存在任何 `NUMERIC(14,2)` 列）。短信成本控制（每日预算、超限降级到 `APP_PUSH`）由详细设计 §8.2 的 R-09 用这个列做统计，**不做金额换算**——换算会让 M20 承担 M16 的职责。

#### 4.4.4 `INBOX` 通道的两次写入

站内信「写库即成功」，所以 `INBOX` 通道一次投递产生**一行**记录，但这行在极短时间内经历两次 `attempt_status` 变化：

```
写 m20_msg_inbox（同一事务）
  └─ INSERT m20_msg_delivery_log (channel='INBOX', attempt_no=1, attempt_status='SENT', send_at=now())
      └─ 同一事务内 UPDATE 该行 SET attempt_status='DELIVERED', finish_at=now()
```

**为什么要两态而不是直接写 `DELIVERED`**：如果 `INBOX` 直接写 `DELIVERED`，那么「所有到达 `DELIVERED` 的消息都经过了一次提交」这条规律就被破坏，运维统计「送达率」时分子里混进了一批从未提交过的行。两态同事务写，代价是一次 UPDATE，收益是五种通道的状态语义完全一致。

#### 4.4.5 `attempt_status` 枚举

| 取值 | 含义 | 是否终态 | 是否可重试 |
|---|---|---|---|
| `SENT` | 已提交网关 | 否（等待回执） | — |
| `DELIVERED` | 确认送达 | 是 | — |
| `FAILED` | 本次投递失败 | 是 | 视 `error_code` 而定，见 4.4.7 |
| `SKIPPED` | 本次跳过未发 | 是 | 否 |

`SKIPPED` 存在的理由：通道降级（如短信日预算耗尽后降级到 `APP_PUSH`）不是失败，是**主动不发**。把它记成 `FAILED` 会让失败率虚高，运维会去查一个并不存在的故障。

#### 4.4.6 `error_msg` 的脱敏红线

外部网关的报错常把收件地址回显在错误信息里（如「号码 13812345678 停机」）。本表**永久保存**，一旦写入就无法删除，所以必须**在写入前脱敏**：手机号中段打码、邮箱保留域名、其余地址类信息整体替换为「地址校验失败」这类通用描述。校验器会扫描各子模块详细设计 §10.3/§10.4 的敏感字段名，但**不会扫描本表**，所以这条防线只能靠实现纪律 + 附录 B.5 的巡检 SQL（对 `error_msg` 匹配手机号与身份证明文的正则，命中即告警）。

#### 4.4.7 哪个 `error_code` 决定要不要重试

| `error_code` 类型 | 例子 | 处理 |
|---|---|---|
| 可重试（瞬时） | 网关超时、限流、5xx | 按 Celery 指数退避 3 次重试（10s / 60s / 300s） |
| 不可重试（终态） | 号码格式非法、模板未审核、用户已退订 | 直接置 `FAILED`，不浪费重试预算 |
| 降级触发 | 短信日预算耗尽、单接收人频率超限 | 通道降级到下一优先级，本次记 `SKIPPED` |

**「不可重试」与「降级触发」必须区分**：前者是「这条路走不通」，后者是「这条路今天不走了」。两者都表现为「没发出去」，但一个该告警、一个该记账，混在一起会让日预算告警永远淹没在噪声里。

#### 4.4.8 索引清单

| 索引名 | 类型 | 定义 | 服务的场景 |
|---|---|---|---|
| `pk_m20_msg_delivery_log` | 主键 | `(id, send_at)` | — |
| `uk_m20_msg_delivery_no` | 唯一 | `(delivery_no, send_at)` | 按流水号查（分区表唯一索引必须含分区键） |
| `idx_m20_msg_delivery_inbox` | 普通 | `(inbox_id, attempt_no)` | 查一条消息的全部投递尝试 |
| `idx_m20_msg_delivery_staff` | 普通 | `(staff_id, send_at DESC)` | 「我最近收到的通知都发到哪了」 |
| `idx_m20_msg_delivery_failed` | 部分 | `(send_at) WHERE attempt_status = 'FAILED'` | 失败巡检；只索引失败行，体积与失败量成正比 |

`uk_m20_msg_delivery_no` 必须带 `send_at`，这是分区表约束的直接后果，不是设计选择。为了让「按 `delivery_no` 唯一定位」这件事仍然成立，`delivery_no` 的生成必须保证**跨月唯一**（日期已含在号里），并由应用层声明该语义——数据库无法在分区表上强制一个不含分区键的唯一约束，**这是本设计明确承认的一处数据库层能力缺口**，由附录 B.3 的巡检 SQL 兜底。

#### 4.5.3 为什么 `gateway_provider` 一律是 `M21`

共享规范 §1.6 与 `M03患者服务与EMPI/M03_患者服务与EMPI_05_消息_详细设计.md:55` 都写明「短信/微信/邮件/APP 推送网关 → M21 集成平台」。M20-08 **不直连任何网关**，只调 M21 的统一接口。因此本列在设计上恒为 `M21`，保留它而不是写死，是为了在 M21 尚未交付时能用数据标记出「这个通道当前走的是降级实现」。

**关于 M21 的现状（必须记录的事实）**：M21 集成平台**在当前仓库中不存在**（`ls -d M21*` 无结果）。全仓唯一提到网关发送路径的地方是 `M03患者服务与EMPI/M03_患者服务与EMPI_05_消息_详细设计.md:295`：

```
发送接口：POST /internal/v1/gateway/message/send，本模块调用 M21，
传 channel / receiver_addr(加密) / template_provider_id / content_vars / task_no / record_no
```

这一行是 **M03-05 视角的设计假设**，不是 M21 的正式契约登记。M21 对 M20 也**没有定义回执回调契约**（M03-05 `:296` 定义的回调只回给 M03-05 自己）。因此本子模块的通道实现必须按降级形态设计，详细设计 §10.2 与 §8.4 给出完整降级表，此处只记录数据结构侧的两个决定：

1. `gateway_provider` 保留为列而非常量，M21 交付后无需改表即可切换；
2. `gateway_request_id` 在 `m20_msg_delivery_log` 中**可空**——M21 不可用时永远不会产生这个值，若设成非空则降级期间连日志都写不进去。

| 约束名 | 定义 | 漏掉会怎样 |
|---|---|---|
| `ck_m20_msg_template_reviewed` | `template_status NOT IN ('IN_REVIEW','PUBLISHED','SUPERSEDED') OR (reviewed_by IS NOT NULL AND reviewed_at IS NOT NULL)` | 已发布的模板没有审核痕迹，审计断链 |

`ck_m20_msg_template_draft_delete` 是双向蕴含：`is_deleted` 为真时必须是 `DRAFT`。这条约束的意义不是防误操作，而是**保证「已发布模板永不消失」**——`m20_msg_inbox.template_id` 是 `ON DELETE SET NULL`，一旦模板行被删除，历史消息就再也查不到它用的是哪版模板。

#### 4.6.3 模板变量为什么用 `var_spec` 声明而不从模板串里推导

从 `{{patient_name}}` 这样的标记里用正则推导变量名是可行的，但推导不出两件关键的事：**哪些变量必填**（缺了就会渲染出「的术前访视提醒」这种半截标题）、**哪些变量敏感**（脱敏与数据权限需要知道边界的准确位置）。所以 `var_spec` 是显式声明，模板串只是它的使用方。结构见附录 D.2。

### 4.7 表：`m20_msg_push_token`

**职责**：第三方推送服务的设备令牌。**它不是凭据表**——§2.6 已给出判据：拿这张表里的令牌不能证明「这个人是可信的」，它只能用来往那台设备推一条通知。

#### 4.7.1 为什么这张表存在而 M02 没有覆盖它

M02 管身份与认证（令牌、会话、MFA），它的令牌是**证明你是谁**的；这里的令牌是**往哪台设备推**的。两者在生命周期上也不同：身份令牌失效必须重新认证，推送令牌失效只需要重新上报一次设备信息。把它们混在一张表里，会让「清理失效推送令牌」这个日常运维动作看起来像在动身份数据。

**但铁律六仍然成立**：本表不签发任何令牌、不参与任何鉴权判定、不建立第二套身份。`staff_id` 只是外键之外的一个职工号，身份的唯一来源始终是 M02 透传的 `X-Staff-Id`。

#### 4.7.2 字段定义

| 字段名 | 类型 | 可空 | 默认值 | 说明 |
|---|---|---|---|---|

#### 4.7.3 唯一键定在 `(staff_id, device_id)` 而不是令牌

`uk_m20_msg_push_token UNIQUE (staff_id, device_id)`。理由：同一职工同一台设备换新令牌时，应当**更新令牌值**而不是插入新行。若唯一键定在 `(staff_id, push_token)`，换机后旧的失效行会一直占着那条键无法复用，表中会积累大量 `INVALID` 行，而「这个人的活跃设备是哪几台」这个查询会随时间和用户换机次数线性变差。

### 4.8 表：`m20_msg_todo_event`

**职责**：待办状态变更流水。**只增不删**。它的存在理由是待办的「谁在什么时候把它认领/完成/作废」必须可追——`m20_msg_todo` 只存当前状态，过程不进主表，否则每改一次状态就要在主表留下半截历史。

#### 4.8.1 为什么不分表、不分区

量级核算：待办日均约 300 条（审批 200 + 护理任务增量 + 随访增量），每条待办平均经历 3.2 次状态变更（`PENDING→CLAIMED→DONE`，部分带一次转办或退回），约 960 行/日、35 万行/年。这个量级单表完全够用。**不按 `created_at` 月分区**，理由同 §4.3：分区键会破坏唯一约束，而本表虽然不设业务唯一键，但一旦分区，`todo_id` 的索引也必须带分区键，导致「查一条待办的全部事件」变成跨分区扫描——**待办的查询模式是按 `todo_id` 聚簇，不是按时间裁剪**，分区键选错了反而更慢。

### 4.9 表：`m20_msg_idem`

**职责**：P-04 推送接口的**业务级**去重。它不是协议级幂等，二者的区别是本节的重点。

#### 4.9.1 与 `m20_base_idempotency` 的边界

| 维度 | `m20_base_idempotency`（M20-01 首建） | `m20_msg_idem`（本表） |
|---|---|---|
| 守的是什么 | 同一个 `X-Idempotency-Key` 全模块只执行一次 | 同一个 `(staff_id, biz_type, biz_id)` 在 5 分钟内不重复推送 |
| 键的来源 | 调用方生成 | 业务对象本身 |
| 生命周期 | 24 小时 | 5 分钟窗口 + 保留 24 小时供追溯 |
| 命中后的行为 | 返回首次响应，不再执行 | 返回首次响应 + `deduplicated: true` |
| 谁需要它 | 所有写接口 | 只有 P-04（推送） |

**为什么要两张表而不是一张**：`m20_base_idempotency` 的键是调用方随手生成的，M08 重发相同内容时可能带不同的 Key；`m20_msg_idem` 的键来自业务对象，M08 重发同一件事必然撞键。用前者替代后者会漏掉真正的重复推送，用后者替代前者会让「用户手抖点两次提交」产生两条不同业务对象的消息。**两个问题，两张表**。

#### 4.9.3 为什么用哈希而不是复合唯一键

`uk_m20_msg_idem UNIQUE (staff_id, biz_type, biz_id)` 是可行的，`biz_type` 最长 64、`biz_id` 最长 64，复合键约 150 字节，与 64 字节哈希的差异不大。选择哈希的真实理由不是省空间，而是**让「改去重口径」成为一次可审计的重算**：万一将来要把 `dept_id` 也纳入去重键，只需要改哈希函数并重建这张表；若用复合唯一键，改口径意味着改表结构 + 迁移索引 + 所有引用该键的代码。这条理由与 `m18_kb_rule_version_set` 选择「规则版本集」而非「单条规则版本号」是同一种取舍：**用一次性的存储代价换取口径可演进**。

哈希算法 SHA-256 小写十六进制（共享规范 §2.4 已定），`VARCHAR(64)`。

#### 4.9.4 组合约束

| 约束名 | 定义 | 漏掉会怎样 |
|---|---|---|
| `ck_m20_msg_idem_window` | `window_end_at > window_start_at` | 窗口为负，去重永不生效 |
| `ck_m20_msg_idem_window_sec` | `window_end_at <= window_start_at + INTERVAL '600 seconds'` | 窗口被配置得过大，同源消息长时间无法重发（如「一条新审批」被误判成重复） |
| `ck_m20_msg_idem_hit` | `hit_count >= 1` | 命中次数为 0，说明这行从没被用过，属于脏数据 |
| `ck_m20_msg_idem_first` | `first_msg_id IS NULL OR first_msg_no IS NOT NULL` | 有消息主键却无流水号，排查时对不上 |

`ck_m20_msg_idem_window_sec` 的上界取 600 秒（业务规则 300 秒的 2 倍），不是 300 秒——**约束应当守住「明显错误」，不应当重复实现业务规则**。业务规则 300 秒由服务层用 `now() BETWEEN window_start_at AND window_end_at` 判断；数据库只拦住「窗口一万年」这类把去重变成永久封锁的配置错误。

### 4.10 表：`m20_msg_unread_snapshot`

**职责**：角标数的计算留痕。本表是「角标失败时不显示 0」这条最严重约束的**证据链**载体。

#### 4.10.1 为什么必须留痕

P-03 返回值只有三种合法形态：数字、`99+`、`?`（或 `null`）。当用户投诉「角标明明有 19 条，我记得」，或运维问「13:47 那次为什么返回 `null`」，唯一能回答的就是这一行留痕：当时五个来源各返回了多少、哪个降级了、`as_of` 是哪一刻、最终合并成多少。没有留痕，这个接口的每一次降级都是一次无法复现的事故。

#### 4.10.2 字段定义

| 字段名 | 类型 | 可空 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | 否 | 自增 | 主键 |
| `staff_id` | `BIGINT` | 否 | 无 | 被查询的职工号 |
| `total_count` | `INTEGER` | 是 | `NULL` | 合并后的角标数；**无法确定时为 `NULL`（不是 0）** |
| `display_value` | `VARCHAR(8)` | 是 | `NULL` | 展示值，`'19'` / `'99+'` / `'?'` / `'0'` |
| `source_breakdown` | `JSONB` | 否 | 无 | 五来源各自的原始数与去重后数；结构见附录 D.3 |
| `degraded` | `BOOLEAN` | 否 | `FALSE` | 本次计算是否降级 |
| `degraded_sources` | `JSONB` | 否 | `'[]'::jsonb` | 降级来源数组，元素含 `source` 与 `reason` |
| `data_quality` | `VARCHAR(32)` | 否 | `'REALTIME'` | 数据质量，`REALTIME` / `CACHED` / `PARTIAL` / `UNKNOWN` |
| `as_of` | `TIMESTAMPTZ` | 是 | `NULL` | 数据口径截止时刻（= 各成功来源 `as_of` 最早值）；无法判定为 `NULL` |
| `cache_hit` | `BOOLEAN` | 否 | `FALSE` | 本次是否命中 Redis 缓存 |
| `calc_ms` | `INTEGER` | 是 | `NULL` | 计算耗时（毫秒） |
| `client_type` | `VARCHAR(32)` | 是 | `NULL` | 请求端类型 |
| `requested_at` | `TIMESTAMPTZ` | 否 | `CURRENT_TIMESTAMP` | 请求时刻（**与 `as_of` 严格区分**） |
| `created_at` | `TIMESTAMPTZ` | 否 | `CURRENT_TIMESTAMP` | 创建时刻 |
| `created_by` | `VARCHAR(64)` | 否 | `'SYSTEM'` | 创建者 |
| `updated_at` | `TIMESTAMPTZ` | 否 | `CURRENT_TIMESTAMP` | 更新时刻 |
| `updated_by` | `VARCHAR(64)` | 否 | `'SYSTEM'` | 更新者 |
| `is_deleted` | `BOOLEAN` | 否 | `FALSE` | 软删除标记 |

#### 4.10.3 组合约束（守住「不显示 0」）

| 约束名 | 定义 | 漏掉会怎样 |
|---|---|---|
| `ck_m20_msg_unread_null` | `total_count IS NOT NULL OR display_value IN ('?')` | 无法确定却显示了数字（包括 0），这正是最严重的缺陷 |
| `ck_m20_msg_unread_zero` | `total_count <> 0 OR (degraded = FALSE AND data_quality IN ('REALTIME','CACHED'))` | **「0 且 degraded: true」这种非法组合进了库**——0 只允许在明确未降级时出现 |
| `ck_m20_msg_unread_degraded` | `degraded = FALSE OR jsonb_array_length(degraded_sources) >= 1` | 降级了却说不出降的是谁，无法告警 |
| `ck_m20_msg_unread_not_degraded` | `degraded = TRUE OR jsonb_array_length(degraded_sources) = 0` | 未降级却带着降级来源，两种说法矛盾 |
| `ck_m20_msg_unread_as_of` | `as_of IS NOT NULL OR data_quality = 'UNKNOWN'` | `as_of` 缺失却标了 `REALTIME`，这正是「用 `now()` 填 `as_of`」那个错误的变种 |
| `ck_m20_msg_unread_cap` | `total_count IS NULL OR total_count <= 9999` | 无上限，异常数据可以把前端撑爆 |
| `ck_m20_msg_unread_display_cap` | `total_count IS NULL OR total_count < 100 OR display_value = '99+'` | 超过 99 却不显示 `99+`，与 M20-CALC-03 规则二不符 |

`ck_m20_msg_unread_zero` 是本文件里**最重要的一条约束**。它把「0 且 `degraded: true`」这个非法组合挡在数据库外面——即使服务层写错了代码，这一行也写不进去。共享规范 §8A.5 第 4 条是写在规范里的一句话，这条 CHECK 是它的可执行形态。

`ck_m20_msg_unread_as_of` 只允许 `UNKNOWN` 时 `as_of` 为空，不允许 `REALTIME`/`CACHED`/`PARTIAL` 时为空，也不能反过来（`as_of` 非空而 `UNKNOWN` 是允许的，因为可能拿到了时刻但拿不到数据质量判定）。

#### 4.10.4 保留期与量级

每次 P-03 调用都留痕，量级是**移动端请求量级**：40 万请求/日里 P-03 约占 35%（角标在几乎每个页面都会刷新），约 14 万行/日、5,100 万行/年。这是九张表里最大的一张，但**仍然不分区**，理由：

1. 它是**观测表**，不是业务事实表，丢失不影响业务；
2. 保留期只有 7 天（见下），稳态行数 = 14 万 × 7 ≈ 100 万行，单表完全够用；
3. 若按 `requested_at` 分区，反而要多维护一套分区创建任务。

保留策略：**只保留最近 7 天**，由 Celery 每日 03:10 清理（这个清理是 DELETE，本表是九张表里唯一允许物理删除的——它不是只增不删表，因为它记录的是观测数据而非业务事实，与 `m20_msg_delivery_log` 的判据不同：投递日志的缺失本身是要追查的对象，角标留痕的缺失只影响事后分析）。

#### 4.10.5 不缓存但要留痕

P-03 的角标数在 Redis 里缓存 300 秒（`m20:msg:unread:{staff_id}`），但**每次调用都要写一行留痕，无论是否命中缓存**。命中缓存时 `cache_hit = TRUE`、`data_quality = 'CACHED'`、`as_of` 取缓存里存的那个值。理由：如果只在未命中缓存时留痕，那「缓存里存的到底是什么」就永远无法验证——缓存污染是这类接口最隐蔽的故障，而它唯一的症状就是「用户看到的和留痕对不上」。

#### 4.10.6 索引清单

| 索引名 | 类型 | 定义 | 服务的场景 |
|---|---|---|---|
| `pk_m20_msg_unread_snapshot` | 主键 | `(id)` | — |
| `idx_m20_msg_unread_staff` | 普通 | `(staff_id, requested_at DESC)` | 追查某个用户在某时刻看到了什么 |
| `idx_m20_msg_unread_degraded` | 部分 | `(requested_at) WHERE degraded = TRUE` | 降级率监控；只索引降级行 |
| `idx_m20_msg_unread_quality` | 部分 | `(requested_at, data_quality) WHERE data_quality <> 'REALTIME'` | M20-CALC-05 新鲜度分布统计 |

#### 4.11.2 关于 `ck_m20_msg_inbox_status_split`

上面 `MsgInbox` 里有一条看起来同义反复的约束：

```python
CheckConstraint(
    "message_status <> 'DELIVERED' OR message_status <> 'SENT'",
    name="ck_m20_msg_inbox_status_split",
)
```

它恒为真，**不提供任何数据校验能力**。保留它的唯一作用是让「`SENT` 与 `DELIVERED` 不得合并」这条规范（共享规范 G-08）在表结构里留下一个可被检索到的落点——`grep ck_m20_msg_inbox_status_split` 能直接找到它，读到的人才知道这里有一条必须遵守的红线。

**这是一个刻意的取舍，必须写清楚，否则会被当成冗余约束清理掉。** 更严格的做法是用触发器在聚合层面拦住「状态直接跳过 `SENT` 到 `DELIVERED`」，但那会让「`DELIVERED` 由回执从 `SENT` 推进」这条正常路径也要绕过触发器，实现成本远大于收益。因此本设计的结论是：**状态分离靠代码纪律 + 这条恒真约束作为标记 + 附录 B.1 的巡检 SQL 作为兜底**，三层里没有一层是数据库强制的。这是本子模块主动承认的唯一一处「规范有、数据库不强制」的地方。

### 4.12 Pydantic Schema 定义

#### 4.12.2 三个校验器级的红线

`QualityFlags._check_marks`、`UnreadCountVM._check_zero_never_degraded`、`PushRequest._sms_emergency_only` 这三处是**把规范写进代码**，不是普通的数据校验：

1. `_check_marks` 保证「`degraded: true` 却说不出降的是谁」和「`as_of` 缺失却标 `REALTIME`」这两种矛盾形态在构造对象时就抛异常——它们在共享规范 §8A 里是三条红线中的两条。
2. `_check_zero_never_degraded` 是 §8A.5 第 4 条的可执行形态。注意它同时检查了两个方向：`count == 0` 且 `degraded` 为真必须拒绝（这是最严重的缺陷），`count is None` 且 `degraded` 为假也必须拒绝（否则前端看到 `null` 会以为「没数据」而不是「没算出来」）。
3. `_sms_emergency_only` 只能拦住「显式指定 SMS 却没有 INBOX 兜底」这一种形态。**真正拦住「非紧急消息走短信」的逻辑必须在服务层按 `request.urgency_level` 与 `channel.only_urgency` 比对**——Schema 层的 validator 拿不到渠道配置，这一点必须在实现时写清楚，否则会有人以为 Schema 已经守住了。

#### 4.12.3 `PushTemplateVars` 为什么留着但不用

上面定义了一个 `PushTemplateVars` 却没有任何字段引用它。这是**表名预留式的设计错误**——它在第一次评审时就会被问「这个类干什么用」。正确做法是删掉它，`PushRequest.template_vars` 直接用 `dict[str, str]`。保留这个类的唯一后果是：下一个读代码的人会去搜索它的引用点，找不到，然后怀疑这里有段没写完的实现。

**本文件保留它并在此说明，是为了给后续实现者一个明确的答复：不要用它。** 模板变量的结构由 `m20_msg_template.var_spec` 声明（附录 D.2），运行时是一个扁平的 `dict[str, str]`，不需要再包一层模型——多一层模型就多一次序列化，而 P-04 的预算是 300ms。

**为什么同时 `REVOKE UPDATE` 再逐列 `GRANT UPDATE`**：投递记录一旦进了终态就不该再被改成别的终态，但它在生命周期内确实要更新 `attempt_status`。只 `REVOKE UPDATE` 会让状态机走不下去，只保留 `UPDATE` 会让任何一列都能被改。逐列授权是这两者之间的唯一可行解，代价是**新增可更新列时必须显式加进 GRANT 列表**，这条纪律写进附录 B 的巡检验证。

```sql
CREATE OR REPLACE FUNCTION fn_m20_msg_ensure_next_partition(p_month DATE)
RETURNS TEXT
LANGUAGE plpgsql
AS $$
DECLARE
    v_start DATE := date_trunc('month', p_month)::date;
    v_end   DATE := (date_trunc('month', p_month) + INTERVAL '1 month')::date;
    v_name  TEXT := 'm20_msg_delivery_log_' || to_char(v_start, 'YYYYMM');
BEGIN
    IF to_regclass(v_name) IS NOT NULL THEN
        RETURN v_name || ' already exists';
    END IF;
    EXECUTE format(
        'CREATE TABLE %I PARTITION OF m20_msg_delivery_log '
        'FOR VALUES FROM (%L) TO (%L)',
        v_name, v_start, v_end
    );
    RETURN v_name || ' created';
END;
$$;
```

## 附录 B：上线巡检 SQL

以下五组 SQL 在迁移后执行一次并纳入每日巡检。「期望」列给出上线时必须达到的结果，任何偏差都是缺陷。

### B.1 状态机完整性（`SENT` / `DELIVERED` 未被合并）

```sql
-- 期望：0 行。终态待办的 updated_at 晚于其最后一条状态流水
-- 正常情况下终态写入之后不应再有更新；出现即说明 ON CONFLICT … WHERE 未生效
SELECT t.id, t.todo_no, t.source, t.status, t.updated_at, t.updated_by
FROM m20_msg_todo t
LEFT JOIN (
    SELECT todo_id, max(created_at) AS last_event_at
    FROM m20_msg_todo_event
    GROUP BY todo_id
) e ON e.todo_id = t.id
WHERE t.status IN ('DONE', 'VOIDED', 'TRANSFERRED')
  AND t.updated_at >= CURRENT_DATE - INTERVAL '7 days'
  AND t.updated_at > COALESCE(e.last_event_at, t.created_at);

-- 期望：0 行
SELECT id, msg_no, message_status, delivered_at
FROM m20_msg_inbox
WHERE message_status = 'DELIVERED'
  AND delivered_at IS NULL;

-- 期望：0 行（已读但无已读时刻）
SELECT id, msg_no
FROM m20_msg_inbox
WHERE message_status = 'READ' AND read_at IS NULL;

-- 期望：0 行（失败但无原因）
SELECT id, msg_no, fail_count, last_error
FROM m20_msg_inbox
WHERE message_status = 'FAILED'
  AND (fail_count = 0 OR last_error IS NULL);
```

第二条与第三条已被 CHECK 约束挡住，巡检 SQL 保留的理由是**约束可能被后来的迁移改掉**，而巡检脚本是独立于表结构的第二道防线。

### B.2 `delivery_attempt` 与投递日志对账

```sql
-- 期望：0 行。冗余计数必须与事实表一致
SELECT i.id, i.msg_no, i.delivery_attempt, COUNT(d.id) AS log_rows
FROM m20_msg_inbox i
LEFT JOIN m20_msg_delivery_log d ON d.inbox_id = i.id
WHERE i.created_at >= CURRENT_DATE - INTERVAL '7 days'
GROUP BY i.id, i.msg_no, i.delivery_attempt
HAVING i.delivery_attempt <> COUNT(d.id);
```

这条对账**只查最近 7 天**，因为更早的数据可能已经归档——全量对账会把「已归档」误判成「不一致」。

### B.3 角标留痕的非法组合（最重要的一组）

```sql
-- 期望：0 行。「0 且 degraded」绝对不允许存在
SELECT id, staff_id, total_count, display_value, data_quality, requested_at
FROM m20_msg_unread_snapshot
WHERE total_count = 0 AND degraded = TRUE;

-- 期望：0 行。count 为空但未标 UNKNOWN
SELECT id, staff_id, total_count, data_quality
FROM m20_msg_unread_snapshot
WHERE total_count IS NULL AND data_quality <> 'UNKNOWN';

-- 期望：0 行。as_of 晚于 requested_at 超过 5 秒（说明是用 now() 填的）
SELECT id, staff_id, as_of, requested_at
FROM m20_msg_unread_snapshot
WHERE as_of IS NOT NULL
  AND as_of > requested_at + INTERVAL '5 seconds';

-- 期望：降级率 < 5%
SELECT
    date_trunc('hour', requested_at) AS hour_bucket,
    COUNT(*) AS total,
    COUNT(*) FILTER (WHERE degraded) AS degraded_rows,
    ROUND(100.0 * COUNT(*) FILTER (WHERE degraded) / COUNT(*), 2) AS degraded_pct
FROM m20_msg_unread_snapshot
WHERE requested_at >= CURRENT_DATE - INTERVAL '1 day'
GROUP BY 1
ORDER BY 1 DESC;
```

第三条 SQL 是「`as_of` 用 `now()` 填充」这个错误的唯一自动发现手段：时间戳本身合法，CHECK 约束只能验证「缺失」，验证不了「填错」。**这条巡检的存在意义大于前两条**——前两条对应的错误已经被数据库挡住了。

### B.5 分区完整性与 `error_msg` 脱敏

```sql
-- 期望：0 行。DEFAULT 分区必须为空
SELECT COUNT(*) AS default_partition_rows
FROM m20_msg_delivery_log_default;

-- 期望：0 行。当月与下月分区必须已存在
SELECT p_month
FROM (VALUES (date_trunc('month', CURRENT_DATE)::date),
             (date_trunc('month', CURRENT_DATE)::date + INTERVAL '1 month'))
     AS t(p_month)
WHERE to_regclass('m20_msg_delivery_log_' || to_char(p_month, 'YYYYMM')) IS NULL;

-- 期望：0 行。error_msg 中不得残留手机号或身份证明文

FROM m20_msg_delivery_log
WHERE send_at >= CURRENT_DATE - INTERVAL '1 day'

       OR error_msg ~ '[0-9]{17}[0-9Xx]');
```

第五条 SQL 是 `m20_msg_delivery_log` 无删除权限之后**唯一可能的补救入口**（发现明文后只能改写该列，不能删行）。它证明了一件事：**「只增不删」把「写错了删掉」这条路彻底关掉了，所以写入前的校验必须比有删除权限时更严**。

### B.6 首建表被越权写入的发现

```sql
-- 期望：0 行。M20-04 的写入必须带 idempotency_key 或 created_by 标识
SELECT id, todo_no, source, created_by
FROM m20_msg_todo
WHERE source = 'M20_APPROVAL'
  AND created_by NOT LIKE 'M20_04%'
  AND created_at >= CURRENT_DATE - INTERVAL '1 day';
```

这条巡检防的是 `M20_移动办公_数据结构设计汇总.md` §1.3 明文禁止的事：**M20-04 直接 INSERT 而不走写接口**。写接口会填 `created_by = 'M20_04'`，直连 INSERT 大概率漏填或填了别的值。它不能 100% 抓到所有越权写入（有人可以伪造 `created_by`），但能抓到实现者写代码时的疏忽——**这正是越权发生的真实原因**。

**发现之后怎么处置**（只做发现不做处置等于没做）：

| 步骤 | 动作 | 判据 |
|---|---|---|
| 1 | 定位写入代码 | 按 `created_at` 时间窗对 M20-04 的发布记录与变更单，找到该时间点上线或改动的写入路径 |
| 2 | 回补 `created_by` | 该行确属 M20-04 写入的，更新为 `'M20_04'`，使其后续两个巡检（B.1、B.2）能正常识别 |
| 3 | **重点核查该 todo 是否被错误复活** | 绕过写接口的 INSERT 必然绕过了 `ON CONFLICT … WHERE status NOT IN ('DONE','VOIDED','TRANSFERRED')` 这道闸，因此可能凭空多出一条 `PENDING` 行，或把已完成的审批重新变成待办 |
| 4 | 对账 | 用 `approval_no` 回查 M20-04 的审批实例状态：`m20_msg_todo` 为 `PENDING` 而审批实例已终结的，就是被复活的，按 B.1 的方式置 `VOIDED` 并记 `close_reason` |
| 5 | 记缺陷 | 按「M20-04 缺陷」提单，不回补代码不算关闭 |

处置的重点在第 3、4 步而不在第 2 步：**`created_by` 填错只是账目问题，待办被复活才是用户能感知的问题**——护士的手机上会多出一条已经批完的审批，他点进去发现办不了，然后学会不再相信待办列表。这正是 M20-CALC-03 想要避免的「已读不回」的另一个成因。

## 附录 D：JSONB 结构定义

### D.1 `m20_msg_inbox.content_vars`

模板变量快照，记录渲染时用的原始变量值。

```json
{
  "vars": {
    "patient_name": "张某某",
    "bed_no": "12-3",
    "task_summary": "术前访视",
    "planned_time": "2026-11-07 09:30"
  },
  "template_code": "MSG_APPROVAL_001",
  "template_version": 3,
  "render_mode": "SERVER"
}
```

| 键 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `vars` | object | 是 | 变量名到值的映射，值一律为字符串 |
| `template_code` | string | 是 | 渲染时用的模板编码 |
| `template_version` | integer | 是 | 渲染时用的模板版本号 |
| `render_mode` | string | 是 | `SERVER`（服务端渲染，当前唯一取值） |

**为什么快照变量而不只留模板**：模板会被改版。三个月后回看「这条消息当时到底写了什么」，只靠 `template_id` 指向当前版本是查不出来的——模板已 `SUPERSEDED`，`vars` 也没了。快照是唯一能让历史消息被完整复原的手段。

**这个 JSONB 里允许出现患者姓名**，因为它在受权限保护的 `m20_msg_inbox` 表内，不进 MQ。这一点必须写清楚，否则会有人以为它和事件载荷一样受限制——**两者的区别不是「能不能存」，是「能不能广播」**。

### D.2 `m20_msg_template.var_spec`

```json
{
  "vars": [
    {"name": "patient_name", "type": "STRING", "required": true, "sensitive": true},
    {"name": "bed_no", "type": "STRING", "required": true, "sensitive": false},
    {"name": "task_summary", "type": "STRING", "required": true, "sensitive": false},
    {"name": "planned_time", "type": "DATE_TIME", "required": false, "sensitive": false}
  ],
  "max_length": 200
}
```

| 键 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `vars` | array | 是 | 变量声明列表；`ck_m20_msg_template_var_spec` 强制此键存在 |
| `vars[].name` | string | 是 | 变量名，与模板串里的标记一致 |
| `vars[].type` | string | 是 | `STRING` / `DATE_TIME` / `NUMBER` |
| `vars[].required` | boolean | 是 | 是否必填；缺失时渲染直接失败而不是渲染出半截标题 |
| `vars[].sensitive` | boolean | 是 | 是否敏感；为真时该变量在日志与预览里必须脱敏 |
| `max_length` | integer | 是 | 渲染后标题与正文的长度上限 |

`sensitive` 是本结构里最有用的一个字段：它让「哪些变量需要脱敏」成为**模板自带的知识**，而不是散落在每个调用方代码里的字符串判断。新增一个含身份证号的模板时，只需要在 `var_spec` 里标一个 `true`，脱敏逻辑自动生效。

### D.3 `m20_msg_unread_snapshot.source_breakdown`

角标计算的五来源分解，是复现 19 这个数的唯一依据。

```json
{
  "sources": [
    {"source": "M08_NURSE_TASK", "raw": 12, "after_dedup": 12, "degraded": false},
    {"source": "M20_MESSAGE", "raw": 15, "after_dedup": 7, "degraded": false},
    {"source": "M19_FOLLOWUP_TASK", "raw": 0, "after_dedup": 0, "degraded": false},
    {"source": "M20_APPROVAL", "raw": 2, "after_dedup": 2, "degraded": false},
    {"source": "M20_NOTICE", "raw": 5, "after_dedup": 5, "degraded": false}
  ],
  "naive_sum": 34,
  "final_total": 19,
  "deduped_count": 15,
  "recursion_guard": true
}
```

| 键 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `sources` | array | 是 | 五来源明细，顺序固定 |
| `sources[].source` | string | 是 | 来源标识，与 `m20_msg_todo.source` 同词表 |
| `sources[].raw` | integer | 是 | 该来源的原始条数（未去重） |
| `sources[].after_dedup` | integer | 是 | 该来源去重后计入的条数 |
| `sources[].degraded` | boolean | 是 | 该来源本次是否降级 |
| `naive_sum` | integer | 是 | 朴素求和，用于监控「虚高比例」 |
| `final_total` | integer | 是 | 合并后的角标总数；降级时可能为空 |
| `deduped_count` | integer | 是 | 被去重掉的总条数 |
| `recursion_guard` | boolean | 是 | 本次是否触发了递归保护（防自调用死循环） |

**`naive_sum` 与 `final_total` 必须同时留痕**：只留 `final_total` 的话，「去重规则是不是把不该合的合了」这个问题没有任何可对比的基准。34 → 19 这个差值是健康信号，差值突然变成 0（说明去重失效）或突然变大（说明重复下发变多）都是要报警的。

`recursion_guard` 的存在理由：P-05 待办列表的上游 M19 P-01 本身也聚合三源待办，若 M19 的聚合实现里反过来调 M20 的 P-05，就会形成死循环。留痕里带这个标记，是为了让这类问题在上线首日就暴露。

**共享规范 §13 里 `message_channel` 的原文含一处笔误**：写作 `INBOX`/`APP_WECHAT_WORK_PLACEHOLDER`（实际值：`INBOX` / `APP_PUSH` / `SMS` / `WECHAT_WORK`）。本文件采用括号内列出的四个实际值，并把 `APP_WECHAT_WORK_PLACEHOLDER` 视为不应落库的描述性残留。此差异已列入交付汇报。

四条枚举是本子模块自有的（`attempt_status`、`template_status`、`token_status`、`todo_*`），其余来自共享规范。**自有枚举也必须用 `VARCHAR(32)` + CHECK，不得用数据库 ENUM 类型**——理由是枚举会变，数据库 ENUM 加值需要 `ALTER TYPE`，而 CHECK 约束只需重建约束，在生产上代价小一个数量级。

### F.1 术语表

| 术语 | 含义 | 不指什么 |
|---|---|---|
| 站内信 | 写进 `m20_msg_inbox` 的员工消息，写库即成功 | 不指微信、短信等外部通道 |
| 通道 | `INBOX` / `WECHAT_WORK` / `APP_PUSH` / `SMS` 四种投递方式之一 | 不指「网关」（网关在 M21） |
| 投递尝试 | 一次「把消息推给某个通道」的动作，对应 `m20_msg_delivery_log` 一行 | 不指一次消息推送（可能多次尝试） |
| `SENT` | 已提交给网关，网关返回成功 | **不指用户已收到** |
| `DELIVERED` | 收到网关回执，确认送达 | 不指用户已读 |
| 角标 | 移动端 App 图标上的未读数字 | 不指消息中心的未读列表长度（两者口径不同，见 §4.10） |
| 待办 | 有一个动作必须由某个职工完成的事项，落在 `m20_msg_todo` | 不指「需要知道的通知」 |
| 去重键 | `(source, biz_type, biz_id, staff_id)` 四元组 | 不指 `X-Idempotency-Key`（那是协议级幂等） |
| 跨来源去重 | `dedup_scope = 'CROSS_SOURCE'` 的待办与消息表合并计数 | 不指同一来源内的去重 |
| 降级 | 上游不可用或无法判定时，返回带标记的不完整结果 | 不指功能不可用（那应返回错误码） |
| `as_of` | 数据口径截止时刻，等于各来源 `as_of` 的最早值 | **不指请求时刻，不得用 `now()` 填充** |
| 紧急度 | `NORMAL` / `URGENT` / `EMERGENCY`，决定能否走短信 | 不指优先级（`priority` 是排序值） |
