## 1. 模块概述

### 1.1 模块定位

**M20-02 移动医生站回答一个问题：医生不在办公室的电脑前，在病床边、在走廊上、在值班室，能不能把该做的事做完、该看的东西看到。**

它**不是** M07 医生工作站的缩小版，也不是一个独立系统。它是**同一批事实的另一种呈现与有限写入**：

| 维度 | M20-02 提供 | 权威在 |
|---|---|---|
| 患者定位（谁的床、什么状态） | 聚合 M05 的住院主档与床位、M03 的患者基本信息 | M05、M03 |
| 病历正文（写了什么） | 只读展示，**不落任何副本** | M18-02 |
| 诊断（诊断是什么） | 只读展示 | M07-02 |
| 医嘱与处方（开了什么） | **只读展示，不写入** | M07-03、M07-05 |
| 病程记录（今天记了什么） | 编辑草稿 + 提交给 M18-03 落库 | M18-03 |
| 报告与危急值 | 只读展示，**不确认危急值** | M12、M13、M07-04 |
| 查房这件事本身 | **拥有**：路线、顺序、谁查到哪、时间戳 | M20-02 |
| 医生在这块屏幕上做过什么 | **拥有**：操作日志、使用统计 | M20-02 |

一句话：**M20-02 拥有「查房这件事」和「医生在这块屏幕上做了什么」，不拥有任何临床事实。**

### 1.2 为什么独立成子模块

**理由一：它的读放大是模块内最高的，必须单独设计「取哪些、什么时候取」。**

年门诊量 48 万、住院在院峰值按 300 床计，一名住院医师查房一次要面对 15~20 个患者。M18-02 的 P-01（按就诊取病历正文）单次 P95 是 100ms。**列表页若为 20 个患者各调一次，就是 20 × 100ms = 2 秒串行，正好吃掉总纲 M20-CALC-04 给业务聚合的全部 900ms 预算，还要再超一倍。** 这不是「优化一下」的问题，是**接口设计层面「取不取」的问题**：列表只取摘要，展开某一行才取正文。这个决定必须由承载它的子模块做出并写进验收，不能靠每个调用点自觉。

**理由二：它的写动作必须被明确限定在「两个半」上，而这个限定必须写在一处。**

M20-02 在临床上靠近三类高风险写入（医嘱、处方、病历签署）。这三类如果放开到移动端，后果不是「方便了」而是「一条已下达的真实医嘱」「一张已签名的处方」「一份已签署的病历」——三者在系统里都没有撤回路径（医嘱可作废但留痕、处方签名是签名、病历签署后只能作废重开）。**把它们挡在外面是一个必须显式论证、集中落地的决定**，散落在各接口的注释里等于没有。见 §2.2。

**理由三：查房这个动作有独立的状态与统计口径，且跨 M05/M07/M18 三家。**

一次查房在 M05 是一条在院记录、在 M07 是一串诊断、在 M18 是一次病程记录，**没有任何一家记录「这次查房从几点开始、按什么顺序、查到第几个、谁被跳过了」**。而这个数据是查房质量考核、DRG 入组核查、「医生有没有真的到床边」这三件事的输入。它自然归属承载查房的子模块。

**理由四：移动端特有的失败形态（断网、超时、权限过期）需要单设一套容错与时延处理方案。**

同一个 M18 P-01，在 PC 端超时的处理是「重试一次再报错」；在移动端，医生站在床边、可能正开着一台下一台手术，超时后**唯一正确的行为是「明确告诉他不完整」，而不是「显示一个空的病历」**。这种「失败形态决定返回形态」的设计无法复用 PC 端接口，必须在本子模块单独定义（见 §8.4 与 §11.1）。

### 1.4 概念辨析

**① 「查房计划」不是「住院主档」。** 一次查房是**一个人在某一天走一遍某个病区**；住院主档是**一个患者从入院到出院**。两者是多对多：一个患者在一次住院期间会被查房 3~10 次，同一次查房覆盖 15~20 个患者。所以 `m20_doc_round_plan` / `m20_doc_round_item` 是独立的两张表，**不是住院主档的视图**。

**② 「病程记录草稿」不是「病程记录」。** 草稿是**输入中间态**，存在 M20；病程记录是**病历的一部分**，存在 M18-03。同一条内容在它的生命周期里换了三个位置：医生手机上（内存）→ M20 草稿表（提交前）→ M18 病程记录表（提交后，M20 的草稿正文立即清空）。**草稿一旦被采纳，M20 不允许保留它的正文**——否则同一个临床结论在系统里有两份，将来无法判定哪份是权威。

**③ 「病历正文」不是「文书」。** 病历正文（`m18_emr_record`）是**内容**；文书（`m07_document`）是**渲染出来、签了名、打印出来的那一份**。一份签署的病历可以生成多份文书（门诊病历、诊断证明书、手术同意书）。**M20-02 展示的是内容，不是文书**；要看签了名的那份 PDF，必须去 M07-06。

**④ 「医生查看危急值」不是「医生确认危急值」。** 查看是 M20 自己的行为（记进 `m20_doc_oper_log` 的 `action='VIEW_CRITICAL'`）；确认是**改变危急值状态**的业务动作，属于 M07-04。见 §2.2 决策 D-01。

**⑤ 「首屏」不是「整个页面加载完」。** 首屏指**用户看到第一屏有内容可读**的时刻（M20-CALC-04 的 2 秒 P95）。后续滚动、展开某一行加载病历正文、图片加载都不在首屏预算内——**这正是允许「列表只取摘要」的原因**。

**⑥ 「降级」不是「失败」。** 降级是**成功返回但内容不完整**（HTTP 200 + `code:0` + `degraded:true`）；失败是**没有返回有效内容**（4xx/5xx + 非 0 code）。把降级当失败处理会丢掉已经拿到的部分；把失败当降级处理会让调用方以为拿到了数据。共享规范 §8A 给出了三种合法形态，**没有第四种**。

### 1.5 模块目标

1. **查房一屏在 4G 弱网下 P95 ≤ 2 秒打开**，且列表页不因患者数增长而变慢（硬规则：不为每个患者调一次病历接口）。
2. **任何上游不可用时，页面必须显式告警而不是显示空数据**——「查不到」与「没有」在界面上必须能区分（§8.4）。
3. **移动端不产生任何一个新的临床事实**：医嘱、处方、诊断、病历签署四类写入一律不在本子模块（§2.2）。
4. **医生在手机上写的病程草稿在弱网下不丢**，且提交成功后 M20 不再持有正文（§3.4 CALC-05、§8.3 字段级校验）。
5. **医生看过的每一个患者、打开的每一份病历都有留痕**，可在纠纷复盘时按患者反查（`m20_doc_oper_log`）。
6. **权限判定 fail-closed**：任一权限校验接口失败一律 403，不得「查不到权限就当有权限」（总纲 G-2）。
7. **降级必须有可见提示**：任何 `degraded=true` 或 `data_quality=CACHED` 的响应，页面顶部必须显示黄条（共享规范 §17 第 24 条）。

| 角色 | 典型场景 | 主要页面 | 关键约束 |

### 2.3 与相邻模块的边界（含三条关键决策）

#### 决策 D-01：M20-02 不开医嘱、不开处方、不签署、不确认危急值

**被放弃的选项 A：「移动端只放开低频操作（如长期医嘱停嘱）」**
不行的理由：停嘱在临床上比下医嘱更危险——**下医嘱错了护士执行前还有核对，停嘱错了护士会直接停止给药**。低频不等于低风险；「只放开低频」这个筛选维度选错了。

**被放弃的选项 B：「加二次确认弹窗就能防误触」**
不行的理由：弹窗防的是「手滑」，防不了「看错患者」。**移动端最典型的错误不是点错了按钮，而是在走廊上打开的是上一个患者的页面。** 真正的防护是「不允许在这个端上做这个动作」，而不是「做得慢一点」。

**被放弃的选项 C：「让 M07 提供一个移动端专用的开单接口」**
这是唯一理论上可行的路，但它需要 M07-03 重新设计一套「移动端开单」的服务端校验（患者身份二次核对、剂量上限、过敏校验的强制程度），**等于在 M07 里开第二条开单路径**。而两条路径的校验强度一旦不一致，「手机开的医嘱比电脑开的松」就会成为漏洞。**所以不做，而不是做不了。**

**结论**：移动端可写的是**病程记录**（X-07 例外，走 M18-03）。这是唯一一类「写错了可以在下一份病程里更正、不直接导致患者伤害」的记录。

**与附录 D.2 的重复说明**：X-01（不开医嘱）、X-02（不开处方）、X-03（不签署病历）三条，在**附录 D.2** 的关键决策记录里各有一份完整论证（含被放弃的选项与失败后果）。**同一件事写两遍不是因为冗余，而是因为读者不同**：看这一节的是做范围评审的人，他需要快速判断「这块功能归谁」；看附录 D.2 的是将来维护这段设计的人，他需要知道「当年为什么不这么做」。两处的结论一字不差，论证深度不同。

#### 决策 D-02：M20-02 不接入离线队列，写病程必须在线

**被放弃的选项：「接入 `m20_base_offline_queue`，离线时暂存、恢复网络后自动提交」**
不行的理由：给一个不允许离线的操作留一条离线通道，后果不是「功能多了」，是**「有人会在离线时点提交，界面上写着『已暂存，将自动提交』，然后回家过周末」**。到周一那条病程记录因为冲突进 `CONFLICT`，而它的内容在本地草稿里——**医生以为写完了、系统以为是草稿、病历上是空的**。

**落地**：断网时点「提交病程记录」，前端必须给出明确阻断提示（「当前网络不可用，请连接网络后提交」），**不进入任何队列**；服务端拒绝（`"2002031"`），`m20_base_offline_queue` 无新增行，M18 零调用。这是可测的负面验收项（SC-05）。

**离线可以做的是「本地保存草稿」**，保存目标是自己手机本地存储 + 恢复网络后同步到 `m20_doc_note_draft`。**草稿不是病历**，所以它可以离线；**提交是产生病历，所以必须在线**。

#### 决策 D-03：M20-02 对危急值只读，不确认

**核实结论**：M12/M13 的 `POST /internal/v1/{m12,m13}/review/critical/{id}/on-acknowledged` 语义是「**M07-04 确认后回调 M12/M13**」，不是「谁能确认」。

**被放弃的选项 A：「替 M07-04 调 `on-acknowledged`」**
后果：M07 侧认为未确认、M12/M13 侧认为已确认，**一个危急值两个状态，两边都不报错**。

**被放弃的选项 B：「调 M12/M13 的对外 REST 兜底（带医生本人身份）」**
后果：绕开 M07-04 的确认逻辑（患者身份核对、是否已升级处理），同样是第二份状态，只是路径更隐蔽。

**被放弃的选项 C：「只在 M20 记一条『医生点过确认』」**
这是最坏的：数据上看像确认过，实际危急值仍停在 `NOTIFIED`——**给了一个看起来成功的假象**。

**结论**：M20-02 能看待办、能点进单份报告看结论，确认动作**跳转到 M07 的入口或提示「请在医生工作站确认」**。如果产品要求移动端直接确认，**必须由 M07-04 提供移动端可调用的确认接口并登记进 M07 契约表**，不得由 M20 自行发明。已登记为待确认事项（§10.2）。

### 3.1 核心实体关系

| 关系 | 基数 | 说明 |
|---|---|---|

### 3.2 状态机

#### 3.2.1 查房计划状态机

```
                       ┌──────────┐
          创建           │  DRAFT   │  草稿：路线已铺、还没开始
        ─────────────►  └────┬─────┘
                              │ 开始查房（START_ROUND）
                              ▼
                       ┌──────────────┐
                       │ IN_PROGRESS  │  进行中：可以逐个标已查/跳过
                       └───┬──────┬───┘
              全部有交代    │      │  中途放弃（须写理由）
         （已查+跳过=总数）  ▼      ▼
                    ┌───────────┐ ┌─────────────┐
                    │ COMPLETED │ │  ABANDONED  │
                    └───────────┘ └─────────────┘
                       （终态）        （终态）
```

| 状态 | 含义 | 允许的操作 |
|---|---|---|
| `DRAFT` | 路线已排出，还没开始 | 调整顺序、删除明细、重新铺路线、放弃 |
| `IN_PROGRESS` | 已开始，正在逐个体检查 | 标已查、标跳过、写病程草稿、放弃 |
| `COMPLETED` | 全部患者都有交代（已查或已跳过） | 只读 |
| `ABANDONED` | 中途放弃，有理由 | 只读 |

**流转规则**

| 编号 | 流转 | 触发 | 前置条件 | 副作用 |
|---|---|---|---|---|
| T-01 | （无）→ `DRAFT` | 新建查房计划 API-04 | 医生有权访问该病区 | 生成 `round_no`；铺明细（`m20_doc_round_item`） |
| T-02 | `DRAFT` → `IN_PROGRESS` | API-05 开始查房 | 明细数 ≥ 1 | 记 `started_at` |
| T-03 | `IN_PROGRESS` → `IN_PROGRESS` | API-06 标记已查/跳过 | 该明细状态为 `PLANNED` | 回写 `item_done`/`item_skipped` |
| T-04 | `IN_PROGRESS` → `COMPLETED` | 最后一个患者被标记 | `item_done + item_skipped = item_total` | 记 `finished_at`；触发查房计数 |
| T-05 | `DRAFT`/`IN_PROGRESS` → `ABANDONED` | API-07 放弃 | **必须填 ≥ 5 字理由** | 记 `abandoned_at` + `abandon_reason` |
| T-06 | `COMPLETED`/`ABANDONED` → 任何状态 | — | **❌ 禁止** | 终态不可回退；要重查就新建一次查房 |
| T-07 | `IN_PROGRESS` → `DRAFT` | — | **❌ 禁止** | 已开始的查房不能退回未开始，否则 `started_at` 与会话矛盾 |

**为什么 `ABANDONED` 不复用 `COMPLETED`**：`COMPLETED` 要求 `item_total = item_done + item_skipped`（**每个患者都有交代**），`ABANDONED` 允许查到一半就走。合并后无法回答「这个医生有没有真的查完 20 个患者」，而这正是查房质量考核的输入。

#### 3.2.2 查房明细状态机

```
        ┌───────────┐  标记已查   ┌───────────┐
        │  PLANNED  │───────────►│  VISITED  │
        │  待查     │            └───────────┘
        └──┬─────┬──┘  标跳过     ┌───────────┐
           │     └───────────────►│  SKIPPED  │
           │                      └───────────┘
           │ 出院/转科事件
           ▼
     ┌──────────────┐  ┌─────────────┐
     │  DISCHARGED  │  │ TRANSFERRED │
     └──────────────┘  └─────────────┘
```

| 状态 | 含义 | `visited_at` | `skip_reason` |
|---|---|---|---|
| `PLANNED` | 待查 | `NULL` | `NULL` |
| `VISITED` | 已查 | 必填 | `NULL` |
| `SKIPPED` | 本次跳过 | `NULL` | **必填 ≥ 2 字** |
| `DISCHARGED` | 计划时在院，执行时已出院 | `NULL` | `NULL` |
| `TRANSFERRED` | 计划时在院，执行时已转科 | `NULL` | `NULL` |

**关键规则**：`DISCHARGED`/`TRANSFERRED` 时 `visited_at` 必须为 `NULL`（数据库 `ck_m20_doc_round_item_gone` 强制）。一个已转科的患者不可能同时是「本次查出」，若两者并存，统计会重复计入。

#### 3.2.3 病程草稿状态机

```
      ┌──────────┐   自动保存   ┌──────────┐
      │ EDITING  │────────────►│ EDITING  │（内容更新，version_no+1）
      └────┬─────┘              └──────────┘
           │ 点提交
           ▼
      ┌──────────────┐  上游成功   ┌────────┐
      │  SUBMITTING  │───────────►│ SAVED  │  正文清空，记 saved_record_id
      └──────┬───────┘            └────────┘
             │ 上游失败
             ▼
      ┌──────────┐
      │ EDITING  │  回退，正文保留，可重试
      └──────────┘

      任一状态 ──丢弃──► DISCARDED  正文清空
      expires_at 到期 ──► 物理删除（SAVED 除外）
```

| 状态 | `draft_text` | `saved_record_id` | 说明 |
|---|---|---|---|
| `EDITING` | 非空 | `NULL` | 可编辑，可能被自动保存多次 |
| `SUBMITTING` | 非空 | `NULL` | 正在提交，防重复提交的中间态 |
| `SAVED` | **必须为空串** | 必填 | 已写入 M18，M20 不再持有正文 |
| `DISCARDED` | **必须为空串** | `NULL` | 医生主动丢弃 |

**为什么 `SAVED` 必须清空正文**：提交成功后 M18 那边已有权威内容，M20 还留一份就成了「同一个临床结论两份存储，无法判定权威」。而且 M20 库的权限面比 M18 宽（运维、信息科都能查），留下的正文等于绕过了病历数据权限。

**为什么单号要用统一服务而不是本地 `MAX()+1`**：两个医生同时新建查房时，`MAX(round_no)+1` 会撞号。M20-01 的单号服务用 Redis `INCR` 保证唯一（共享规范 §2.5、§3.3）。

### 3.4 关键计算模型

#### M20-02-CALC-01 首屏可分页患者数

**问题**：查房列表一屏能显示几个患者，才不会破 2 秒预算？

**公式**：设单人摘要数据量 `S` 字节、一屏患者数 `N`、响应体上限 `B = 200KB`（共享规范 §8.1）。

```
N ≤ floor(B / S)
```

**取值**：单人摘要（床号 8B + 患者脱敏名 64B + 诊断 60B + 状态 8B + 标记位 ~20B + JSON 键名开销 ~180B）≈ **350 字节**。

```
N ≤ floor(204800 / 350) = 585
```

**边界**：分页上限另受共享规范 §2.3 约束（移动端 `page_size` 默认 20、上限 100）。**所以实际约束不是字节数，是 `page_size ≤ 100`。** 一个病区在院患者一般 30~50 人，一页装得下。

**算例**：某病区 46 个在院患者，`page_size=50`，响应体 ≈ `46 × 350 = 16.1KB`，远低于 200KB。**首屏耗时由上游决定，不由载荷决定**——这是「列表只取摘要」能成立的前提。

**失败条件**：若单人摘要在某个字段上膨胀（例如把诊断结论全文塞进列表），`S` 会到 2KB 级，`N` 掉到 100 以下，一屏装不完一个病区，翻页又受 `page_size ≤ 100` 限制。**所以列表字段集必须固定，不允许「顺手多带一个字段」。**

#### M20-02-CALC-02 首屏耗时分解与预算判定

**公式**：

```
T_first = T_net + T_auth + max(T_up1, T_up2, ..., T_upk) + T_render + T_jitter
```

**预算**（直接引用总纲 M20-CALC-04）：

| 环节 | 预算 | 取值依据 |
|---|---|---|
| `T_net` | 400ms | 4G 中位往返 |
| `T_auth` | 60ms | U-01 给 20ms，留 3 倍余量 |
| **`max(T_up...)`** | **≤ 900ms** | 业务聚合预算 |
| `T_render` | 400ms | 首屏列表 + 图片懒加载 |
| `T_jitter` | 240ms | 抖动余量 |
| **合计** | **2000ms** | 总纲 P95 ≤ 2s |

**判定**：`T_first ≤ 2000ms` 为达标；`2000 < T_first ≤ 2400ms` 记 WARN；`> 2400ms` 记 FAIL。

**算例（查房一屏，四上游并行）**

| 上游 | SLA | 实测 P95 |
|---|---|---|
| U-17 M05 在院清单 | 150ms | 132ms |
| U-23 M07 诊断（**批量一次**） | 50ms | 61ms |
| U-34 M18 病历正文 | 100ms | **不调用**（列表只取摘要） |
| M12/M13 报告标记（批量） | 200ms | 超时 |

并行取 max：`max(132, 61, 200) = 200ms`（M12/M13 超时按 200ms 计并记降级）。
`T_first = 400 + 60 + 200 + 400 + 240 = 1300ms` ≤ 2000ms，**达标**。

**反例（串行 + 逐患者调病历）**：20 个患者各调一次 U-34（100ms）+ 一次 U-23（50ms）：
`T_聚合 = 20 × (100 + 50) = 3000ms`，`T_first = 400 + 60 + 3000 + 400 + 240 = 4100ms`，**超预算 105%**。这就是「不得为每个患者调一次 M18 P-01」这个硬规则的量化依据。

**失败条件**：任一上游超时必须**按超时值计入**（不无限等），且记 `degraded_sources`。

#### M20-02-CALC-03 数据质量判定（M20 自己重算，不透传上游）

**为什么必须自己算**：M18-02 的 `data_quality` 是 `REALTIME`/`DAILY`/`ESTIMATED`，M20 的是 `REALTIME`/`CACHED`/`PARTIAL`/`UNKNOWN`，**只有 `REALTIME` 一个能对上**。M18 的 `DAILY` 意思是「来自日批汇总」——它可能恰恰是最新最准的；M20 的 `CACHED` 意思是「这是 M20 自己 30 秒前的缓存」。**两个「不实时」的成因完全不同，映射成一个值就把「上游本来就长这样」和「M20 缓存旧了」混成一件事，运维永远查不清是哪边慢。**

**判定算法**（自上而下，命中即停）：

```
if 任一上游失败:                                  → PARTIAL
elif 有数据来自缓存 且 缓存年龄 > 30s:              → CACHED
elif 有数据来自缓存 且 缓存年龄 ≤ 30s:              → REALTIME
elif 无法判定（任一成功上游未返回 as_of）:          → UNKNOWN
else:                                            → REALTIME
```

**`as_of` 的计算**：`as_of = min(所有成功来源的 as_of)`。**未返回 `as_of` 的来源使整个响应 `UNKNOWN`。**

**算例**：

| 来源 | 返回时刻 | `as_of` | 状态 |
|---|---|---|---|
| M05 U-17 | 10:09:41 | 10:09:40 | 成功 |
| M07 U-23 | 10:09:42 | 10:09:41 | 成功 |
| M18 U-34 | 10:09:41 | 10:09:35 | 成功 |
| M12/M13 | 超时 | — | 失败 |

结果：`degraded = true`、`degraded_sources = [{"source":"M12_M13","reason":"TIMEOUT"}]`、`data_quality = PARTIAL`、`as_of = 2026-11-07T10:09:35+08:00`（**取最早，不是请求时刻 10:09:42**）。

**常见错误**：`as_of` 用 `now()` 填充。页面会显示「刚刚更新」，而实际最新数据是 7 秒前的——**这 7 秒在给药核对与危急值场景里是实质风险**。

**失败条件**：`as_of` 无法确定时 `data_quality` 必须是 `UNKNOWN`，**绝不默认 `REALTIME`**。

#### M20-02-CALC-04 脱敏显示名的取值规则

**问题**：列表里显示患者姓名，但列表页权限低于详情页。

**规则**：`patient_display` **一律取上游 U-08 `perm/mask-fields` 处理后的返回值，M20 不自己拼接、不自己脱敏**。

**公式**：`patient_display = mask(patient_name, 当前用户在该上下文下的脱敏规则)`

| 上下文 | 典型脱敏 | 结果示例 |
|---|---|---|
| 本人在院患者列表 | 不脱敏 | `张建国` |
| 跨病区/会诊 | 姓 + 星号 | `张**` |
| 统计与日志 | 姓 + 星号 | `张**` |
| 无数据权限 | 不返回该行 | — |

**算例**：值班医师查看其他病区的患者，`mask-fields` 返回 `张**`；同一医师回到本病区，同一患者返回 `张建国`。

**失败条件**：U-08 不可用时**按最严脱敏**（只显示姓 + 星号），**不得因为「拿不到规则」就显示完整姓名**。这是 B-03 与总纲 G-2 的同一条原则：不确定时选更严的那个。

**为什么不自己在 M20 里写脱敏函数**：脱敏规则属于患者隐私策略，归 M02。M20 自己写一份，就会出现「PC 端脱敏三级、手机端脱敏一级」——**同一个患者在两个端看到的名字不一样，这本身就是泄露线索**。

#### M20-02-CALC-05 草稿容量与过期判定

**问题**：草稿表会不会无限长大？一台手机上的草稿留多久？

**公式**：

```
活跃草稿行数 ≈ 在线医生数 × 每天草稿数 × 保留天数
            = 300 × 2.5 × 1  = 750 行
已终结行数（SAVED/DISCARDED，仅留痕迹）≈ 300 × 2.5 × 30 = 22,500 行
单行平均字节 ≈ 正文 800B + 元数据 400B ≈ 1.2KB
月增数据量 ≈ 22,500 × 1.2KB ≈ 27MB
```

**过期判定**：`expires_at = created_at + doc.draft_expire_hours`（默认 24 小时）。

**边界**：

| 情形 | 处理 |
|---|---|
| `EDITING` 且 `now() > expires_at` | **物理删除**（这是安全要求：老旧草稿 = 一台被转手的手机里留着患者病情） |
| `SUBMITTING` 且 `now() > expires_at` | 保留（正在提交，删了会让医生以为丢稿） |
| `SAVED` | 保留（只留「曾在此编写过」的痕迹，正文已空） |
| `DISCARDED` | 到 `expires_at` 后物理删除 |

**算例**：医生 11-07 09:00 建草稿、11-08 09:00 前一直没提交 → 11-08 09:00 后第一次清理任务运行时被删除。医生再次进入编辑页会看到「无草稿」（而不是旧草稿），**这是正确行为**——24 小时前的病程草稿在临床上已无价值，保留它反而有风险。

**失败条件**：清理任务失败不得影响业务；下次运行继续清。清理任务只允许删 `EDITING`/`DISCARDED`，**绝不删 `SUBMITTING`**。

#### M20-02-CALC-06 查房完查率

**公式**：

```
完查率 = COMPLETED 的查房数 / (COMPLETED + ABANDONED) 的查房数
```

**口径**：

- 分母只算**已经开始过**的查房（`started_at IS NOT NULL`），`DRAFT` 不计入——把排了没开始也算进分母，会让「排的计划越多、完查率越低」，激励医生不排计划。
- **分母为 0 时返回 `NULL`，不返回 0**。返 0 会被理解成「一次都没完成」。
- 按科室、按医生、按月统计。

**算例**：某科室 2026-10 共开始查房 240 次，其中 `COMPLETED` 222 次、`ABANDONED` 18 次 → `222/240 = 0.925000`（存入 `NUMERIC(10,6)` 存小数，展示时 ×100 保留 2 位 = `92.50%`）。

**对比口径（不采用）**：若把 `DRAFT` 也算进分母，同例还有 35 次排了没开始 → `222/(240+35) = 0.807273` → `80.73%`。**两种口径差 11.77 个百分点。** 采用前者，因为「排了计划但当天被手术叫走」不是查房质量问题。

**失败条件**：`m20_doc_round_plan` 数据不可用（分区缺失）时，统计必须返回 `calc_status='PARTIAL'` + `missing_sources`，**不返回 0%**。

- **卡片顺序由自己编辑的编排决定**；没有自己的编排则用全院默认（`scope_type='HOSPITAL', is_default=TRUE`）；再没有则用内置默认顺序。
- **降级黄条不自动消失**，必须等下一次成功刷新后消失。**自动消失会让医生错过「数据不完整」这个信息。**

**校验规则**

| 编号 | 规则 |
|---|---|
| V-P01-01 | 无 `m20:doc:home:view` 权限 → 403 页面，不渲染任何卡片 |
| V-P01-02 | 任一卡片数据源降级 → 黄条显示，且该卡片右上角显示「缓存」角标 |
| V-P01-03 | 最近访问只显示本人访问过的患者，不显示他人 |

**异常态（四种，必须分别显示）**

| 异常态 | 显示 |
|---|---|
| 网络断开 | 顶部红条「网络已断开」；卡片显示本地缓存内容 + 灰化；不禁用整个页面（**允许看上次内容**） |
| 上游超时 | 顶部黄条「部分数据暂不可用（M05/M07/M18），数据截至 HH:MM:SS」；**受影响的卡片显示「暂不可用」，不显示「无数据」** |
| 无权限 | 整页 403 提示「您没有访问移动医生站的权限，请联系信息科开通」，**不显示空页面** |
| 数据为空 | 无查房计划 → 「今日无查房计划」+「新建查房」按钮；无最近访问 → 「还没有访问记录，从查房开始」 |

**移动端特殊考虑**

| 项 | 设计 |
|---|---|
| 屏幕尺寸 | 390×844 竖屏优先；**首页所有卡片单列纵向排列**，不做左右滑动（横滑在单手持握时容易误触） |
| 单手持握 | 底部 Tab 与主要按钮在拇指可达区（屏幕下方 40%）；**顶部不放需要点的按钮**（只有 ⚙ 与 🔔，且尺寸 ≥ 44×44） |
| 网络状态 | 4G/弱网按 2 秒预算；**页面只缓存首页卡片数据，TTL 60 秒**；离线时可展示上次内容但顶部必须红条 |
| 单手/双手 | 全部支持单手操作 |
| 扫码/拍照 | 本页不需要 |
| 横竖屏 | 竖屏为主；**横屏时卡片保持单列并放大字体**，不做双列（医生不会横着拿手机站着看） |

### 6.2 统一响应格式

所有接口统一返回：

```json
{
  "code": 0,
  "message": "OK",
  "trace_id": "6b1f0c3a9d2e4f81",
  "data": { }
}
```

**`data` 必须内嵌四个质量标记**（`degraded=false` 时也必须出现，共享规范 §8A）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `degraded` | boolean | 本次响应是否降级 |
| `degraded_sources` | array | 降级来源，元素含 `source` 与 `reason`；不降级为 `[]` |

**为什么不静默留白**：查房页第三列如果只是少一列，医生不会知道自己少了什么——他会以为这就是全部。**留白等于「本来就没有」，灰条加跳转等于「这里本该有，但现在要去别处看」**。这两者给医生的决策完全不同：前者他会以为这个病人没写病程，可能重复书写；后者他知道要去工作站看。客户端在 `course_summary_available=false` 时，第三列必须显示灰色说明「病程摘要需在医生工作站查看」+ 跳 M07 的入口（SC-17、SC-18 验收项）。

**为什么 `reason` 用 `INTERFACE_NOT_PROVIDED` 而不是 `TIMEOUT`**：这两个降级原因的处置动作相反——`TIMEOUT` 是「等一会重试就好」，`INTERFACE_NOT_PROVIDED` 是「重试一万次也没有」，只有向上游提请补接口才能解决。**用一个笼统的降级原因覆盖两种相反的处置建议，等于让运维去查一个永远不会好的超时。**

**`record_loaded` 必须为空数组**——它是给客户端核对「这个响应里有没有病历正文」的显式标记。列表页出现非空即说明有人违反了硬规则（SC-01 验收项）。

**错误码**：`"2002002"`、`"2002006"`（查房计划不存在，404）

**业务逻辑**

1. 查 `m20_doc_round_plan`（`round_no` 唯一索引）；不存在 → `"2002006"`。
2. 校验该计划归属当前医生或当前医生有该病区数据权限（`perm/filter-sql`）。
3. 查 `m20_doc_round_item` 全部明细（走 `idx_m20_doc_round_item_plan_status`）。
4. **批量**取诊断摘要：把 N 个 `encounter_id` 一次性传给 M07-02 的批量接口（若上游只支持单条，则 `asyncio.gather` 并发 N 个请求并设总超时 200ms；超时部分按失败处理）。

#### API-15 新建或保存草稿

**路径**：`POST /api/v1/m20/doc/note/draft`
**权限**：`m20:doc:note:edit`
**调用上游**：无（**纯本地**，弱网下也要能保存）

**幂等**：**必须支持 `X-Idempotency-Key`**；另有天然语义——同 `(staff_id, encounter_id, course_type)` 已有 `EDITING` 草稿时，**本接口转为更新该草稿**（`upsert`），不新建第二份。

**请求体**

```json
{
  "patient_id": 10032,
  "encounter_id": 81002,
  "round_item_id": 880012,
  "course_type": "DAILY",
  "target_section": null,
  "draft_text": "患者今日诉右眼视力较昨日好转，无明显疼痛。",
  "draft_source": "VOICE",
  "client_type": "IOS",
  "network_state": "WEAK"
}
```

**错误码**：`"2002002"`、`"2002022"`（草稿正文超过 20,000 字，400）、`"2002023"`（草稿正文只含空白，400）、`"2002033"`（幂等键冲突）

**业务逻辑**

1. 幂等键检查。
2. 正文 `strip()` 后为空 → `"2002023"`；`char_length > 20000` → `"2002022"`。
3. `ON CONFLICT (staff_id, encounter_id, course_type) WHERE draft_status IN ('EDITING','SUBMITTING') DO UPDATE`。
4. `expires_at = now() + doc.draft_expire_hours`（默认 24h），**每次保存都顺延**——医生一直在写就不该过期。
5. `text_length = char_length(draft_text)`（数据库 `ck_..._len` 会再校验一次）。
6. 记日志 `action='SAVE_DRAFT'`、`detail` 记 `text_length` 与 `network_state`（**不记正文**）。

#### API-16 更新草稿（乐观锁）

**路径**：`PUT /api/v1/m20/doc/note/draft/{draftId}`
**权限**：`m20:doc:note:edit`
**调用上游**：无
**幂等**：**必须支持 `X-Idempotency-Key`**

**请求体**：同 API-15，另加 `version_no`（必填，客户端持有的版本号）

**错误码**：`"2002002"`、`"2002004"`（版本冲突，409，返回当前 `version_no` 与当前正文供用户合并）、`"2002024"`（草稿不存在，404）、`"2002025"`（草稿已终结，409）、`"2002033"`

**业务逻辑**

1. `UPDATE ... SET draft_text=?, text_length=?, version_no=version_no+1, updated_at=now() WHERE id=? AND version_no=? AND draft_status='EDITING'`。
2. 影响行数 0 → 再查一次区分是「版本冲突」还是「草稿已终结」。
3. **版本冲突时返回当前正文**，让用户能手动合并——**不自动覆盖**（同一条病程在手机和 iPad 上各写了一半，自动覆盖会丢一半）。

#### API-17 提交病程记录到 M18-03

**路径**：`POST /api/v1/m20/doc/note/draft/{draftId}/submit`
**权限**：`m20:doc:note:edit`
**调用上游**：

| 上游 | 契约 | SLA | 失败处理 |
|---|---|---|---|
| M18-03 病程写入 | `POST /api/v1/m18/ipd-record/course-records` | **3000ms** | **不可降级**：返回错误码，草稿保留，**不进入任何队列**（决策 D-02 / SC-05） |

**幂等**：**必须支持 `X-Idempotency-Key`**——提交是最容易被重复点击的动作，重复提交会产生两条病程记录。

**请求体**

```json
{
  "encounter_id": 81002,
  "course_type": "DAILY",
  "record_date": "2026-11-07",
  "written_at": "2026-11-07T10:20:00+08:00",
  "version_no": 4
}
```

**响应示例（成功）**

```json
{
  "code": 0,
  "message": "OK",
  "trace_id": "16ce1be5483df09c",
  "data": {
    "draft_id": 70011,
    "draft_status": "SAVED",
    "record_id": 91002,
    "course_no": "CRS2026110700012",
    "degraded": false,
    "degraded_sources": [],
    "data_quality": "REALTIME",
    "as_of": "2026-11-07T10:20:03+08:00"
  }
}
```

**错误码**：`"2002002"`、`"2002024"`、`"2002025"`（草稿已终结，409）、`"2002027"`（上游写入失败，502，草稿保留可重试）、`"2002028"`（上游超时，504，草稿保留可重试）、`"2002030"`（离线不可提交，400）、`"2002031"`（网络状态为非在线，400）、`"2002032"`（上游返回成功但无法确认，502）、`"2002033"`（幂等键冲突）

**业务逻辑（严格顺序）**

1. 幂等键检查（Redis `m20:base:idem`，TTL 24h）：已存在则返回首次结果原样。
2. **网络前置校验**：请求头 `X-Network-State` 为 `OFFLINE` → `"2002030"`（400）。**这是决策 D-02 的服务端落地**——即使客户端没拦，服务端也拦。
3. 草稿必须 `EDITING` + `version_no` 匹配 → 否则冲突。
4. 置 `draft_status='SUBMITTING'`（防并发重复提交），**提交前正文快照到 outbox 表**（M20-01 的 `m20_base_idempotency` 或本地消息表；本子模块写日志 `detail.snapshot_hash`）。
5. 调 M18-03 的 `course-records`，超时 3000ms，请求带 `X-Idempotency-Key`。
6. 上游成功：
   - `UPDATE m20_doc_note_draft SET draft_status='SAVED', saved_record_id=?, saved_at=now(), draft_text='', text_length=0`（**数据库 `ck_..._editing` 强制正文必须为空**）。
   - 记日志 `action='SUBMIT_COURSE'`、`detail.course_no`、`detail.record_id`。
7. 上游失败/超时：
   - **回滚 `draft_status` 为 `EDITING`**，正文保留。
   - 返回 `"2002027"` / `"2002028"`。
   - **不进入队列、不自动重试**——医生必须在场看着重试（决策 D-02 的核心）。
8. 上游返回成功但响应体无法解析 → `"2002032"`，同时置 `draft_status='SUBMITTING'` 保持，由人工核对（**不能当成成功，也不能当成失败**）。

```python
from __future__ import annotations

import asyncio
import datetime
import hashlib
import json
from dataclasses import dataclass
from typing import Any, Optional

# 首屏聚合预算（总纲 M20-CALC-04）
BUDGET_NET_MS = 400
BUDGET_AUTH_MS = 60
BUDGET_AGG_MS = 900
BUDGET_RENDER_MS = 400
BUDGET_JITTER_MS = 240
BUDGET_TOTAL_MS = 2000

# 上游超时（毫秒）
TIMEOUT_PERM_CONTEXT = 100
TIMEOUT_M05_ADMISSION = 150
TIMEOUT_M07_DIAGNOSIS = 50
TIMEOUT_M18_EMR = 100
TIMEOUT_M03_PATIENT = 50
TIMEOUT_M12_REPORT = 200
TIMEOUT_M13_REPORT = 200
TIMEOUT_M18_COURSE_SUBMIT = 3000

CACHE_FRESH_SECONDS = 30
RESPONSE_SIZE_LIMIT_BYTES = 204800


class BizError(Exception):
    def __init__(self, code: str, http_status: int, message: str) -> None:
        super().__init__(message)
        self.code = code
        self.http_status = http_status
        self.message = message


@dataclass
class QualityComputeResult:
    degraded: bool
    degraded_sources: list[dict[str, str]]
    data_quality: str
    as_of: datetime.datetime


def compute_quality(
    successes: list[dict[str, Any]],
    failures: list[dict[str, str]],
    cache_age_seconds: Optional[int],
    now: datetime.datetime,
) -> QualityComputeResult:
    """M20-02-CALC-03：M20 自己重算数据质量，绝不透传上游的 data_quality。

    判定顺序（命中即停）：
      任一上游失败 -> PARTIAL
      有缓存且年龄 > 30s -> CACHED
      有缓存且年龄 <= 30s -> REALTIME
      无法判定（任一成功来源未给 as_of）-> UNKNOWN
      否则 -> REALTIME
    """
    degraded = len(failures) > 0
    if degraded:
        quality = "PARTIAL"
    elif cache_age_seconds is not None and cache_age_seconds > CACHE_FRESH_SECONDS:
        quality = "CACHED"
    elif cache_age_seconds is not None:
        quality = "REALTIME"
    else:
        quality = "REALTIME"

    as_of_values: list[datetime.datetime] = []
    unknown_as_of = False
    for item in successes:
        value = item.get("as_of")
        if value is None:
            unknown_as_of = True
        else:
            as_of_values.append(value)

    if unknown_as_of and not degraded:
        quality = "UNKNOWN"

    as_of = min(as_of_values) if as_of_values else now
    return QualityComputeResult(
        degraded=degraded,
        degraded_sources=failures,
        data_quality=quality,
        as_of=as_of,
    )


class RecordService:
    """病历正文：只读 M18 P-01，不落副本、不改写哈希。"""

    def __init__(self, m18_client: Any, oper_log_writer: Any, perm_client: Any) -> None:
        self.m18 = m18_client
        self.log = oper_log_writer
        self.perm = perm_client

    async def get_record(
        self,
        auth: Any,
        encounter_id: int,
        record_type: str,
    ) -> dict[str, Any]:
        now = datetime.datetime.now(datetime.timezone.utc)

        if not await self.perm.check(auth.staff_id, "m20:doc:record:view"):
            # 无权限一律 403 + 非 0 错误码，绝不用 200 + 空 data 表达
            raise BizError("2002002", 403, "无权查看病历正文")

        failures: list[dict[str, str]] = []
        try:
            upstream = await asyncio.wait_for(
                self.m18.get_by_encounter(
                    encounter_id, record_type, caller="M20_DOC"
                ),
                timeout=TIMEOUT_M18_EMR / 1000,
            )
        except asyncio.TimeoutError:
            upstream = None
            failures.append({"source": "M18_EMR", "reason": "TIMEOUT"})
        except Exception:
            upstream = None
            failures.append({"source": "M18_EMR", "reason": "ERROR"})

        if upstream is None:
            record: dict[str, Any] = {
                "record_id": None,
                "record_no": None,
                "encounter_id": encounter_id,
                "record_type": record_type,
                "status": None,
                "chief_complaint": None,
                "present_illness": None,
                "past_history": None,
                "physical_exam": None,
                "specialty_exam": None,
                "diagnosis_text": None,
                "treatment_plan": None,
                "content_hash": None,
                "hash_algo": "SHA256",
                # 关键：不知道，不是没有
                "record_exists": None,
                "exists_known": False,
                "sources_complete": False,
                "record_count": 0,
            }
        else:
            record = {
                "record_id": upstream.get("record_id"),
                "record_no": upstream.get("record_no"),
                "encounter_id": encounter_id,
                "record_type": record_type,
                "status": upstream.get("status"),
                "chief_complaint": upstream.get("chief_complaint"),
                "present_illness": upstream.get("present_illness"),
                "past_history": upstream.get("past_history"),
                "physical_exam": upstream.get("physical_exam"),
                "specialty_exam": upstream.get("specialty_exam"),
                "diagnosis_text": upstream.get("diagnosis_text"),
                "treatment_plan": upstream.get("treatment_plan"),
                # content_hash 原样透传，M18 是唯一权威方
                "content_hash": upstream.get("content_hash"),
                "hash_algo": upstream.get("hash_algo", "SHA256"),
                "record_exists": upstream.get("record_exists", True),
                "exists_known": True,
                "sources_complete": upstream.get("sources_complete", True),
                "record_count": upstream.get("record_count", 1),
            }

        successes = [] if upstream is None else [upstream]
        quality = compute_quality(successes, failures, None, now)

        # view_scope 只在真的拿到正文时记为 RECORD_BODY
        scope = "RECORD_BODY" if record["record_exists"] is True else "NONE"
        await self.log.write(
            staff_id=auth.staff_id,
            action="VIEW_RECORD",
            patient_id=upstream.get("patient_id", 0) if upstream else 0,
            encounter_id=encounter_id,
            record_id=record["record_id"] or 0,
            view_scope=scope,
            degraded=quality.degraded,
            data_quality=quality.data_quality,
            detail={"caller": "M20_DOC", "record_count": record["record_count"]},
        )

        return {
            "record": record,
            "degraded": quality.degraded,
            "degraded_sources": quality.degraded_sources,
            "data_quality": quality.data_quality,
            "as_of": quality.as_of,
        }


class NoteService:
    """病程草稿：本地存中间态，提交必须在线直达 M18-03。"""

    def __init__(
        self,
        draft_repo: Any,
        m18_course_client: Any,
        idem_store: Any,
        oper_log_writer: Any,
        config_service: Any,
    ) -> None:
        self.repo = draft_repo
        self.m18 = m18_course_client
        self.idem = idem_store
        self.log = oper_log_writer
        self.config = config_service

    async def save_draft(
        self,
        auth: Any,
        body: Any,
        idempotency_key: str,
    ) -> dict[str, Any]:
        cached = await self.idem.get("M20_DOC_SAVE_DRAFT", idempotency_key)
        if cached is not None:
            return cached

        text = body.draft_text.strip()
        if not text:
            raise BizError("2002023", 400, "草稿内容不能只包含空白字符")
        if len(text) > 20000:
            raise BizError("2002022", 400, "草稿正文超过 20000 字")

        expire_hours = await self.config.get_int("doc.draft_expire_hours", 24)
        now = datetime.datetime.now(datetime.timezone.utc)
        draft = await self.repo.upsert_active(
            staff_id=auth.staff_id,
            patient_id=body.patient_id,
            encounter_id=body.encounter_id,
            round_item_id=body.round_item_id,
            course_type=body.course_type,
            target_section=body.target_section,
            draft_text=text,
            draft_source=body.draft_source,
            client_type=body.client_type,
            network_state=body.network_state,
            expires_at=now + datetime.timedelta(hours=expire_hours),
        )
        await self.log.write(
            staff_id=auth.staff_id,
            action="SAVE_DRAFT",
            patient_id=body.patient_id,
            encounter_id=body.encounter_id,
            view_scope="NONE",
            detail={
                "text_length": len(text),
                "network_state": body.network_state,
                "draft_source": body.draft_source,
            },
        )
        result = {
            "draft": draft,
            "degraded": False,
            "degraded_sources": [],
            "data_quality": "REALTIME",
            "as_of": now,
        }
        await self.idem.set("M20_DOC_SAVE_DRAFT", idempotency_key, result)
        return result

    async def submit(
        self,
        auth: Any,
        draft_id: int,
        body: Any,
        idempotency_key: str,
        network_state: str,
    ) -> dict[str, Any]:
        cached = await self.idem.get("M20_DOC_SUBMIT_COURSE", idempotency_key)
        if cached is not None:
            return cached

        # 决策 D-02 的服务端落地：离线一律拒绝，不排队
        if network_state == "OFFLINE":
            raise BizError("2002030", 400, "当前网络不可用，病程记录必须在线提交")

        draft = await self.repo.get_for_update(draft_id)
        if draft is None:
            raise BizError("2002024", 404, "草稿不存在")
        if draft["draft_status"] != "EDITING":
            raise BizError("2002025", 409, "该草稿已终结，无法再次提交")
        if draft["version_no"] != body.version_no:
            raise BizError("2002004", 409, "草稿已被其他设备修改")

        await self.repo.mark_submitting(draft_id, body.version_no)
        payload = {
            "encounter_id": body.encounter_id,
            "course_type": body.course_type,
            "record_date": body.record_date.isoformat(),
            "written_at": body.written_at.isoformat(),
            "content": draft["draft_text"],
            "template_code": body.template_code,
            "source_module": "M20_DOC",
        }
        snapshot_hash = hashlib.sha256(
            draft["draft_text"].encode("utf-8")
        ).hexdigest()

        try:
            resp = await asyncio.wait_for(
                self.m18.create_course(payload, idempotency_key=idempotency_key),
                timeout=TIMEOUT_M18_COURSE_SUBMIT / 1000,
            )
        except asyncio.TimeoutError:
            await self.repo.revert_to_editing(draft_id)
            raise BizError("2002028", 504, "病程提交超时，草稿已保留，请稍后重试")
        except Exception:
            await self.repo.revert_to_editing(draft_id)
            raise BizError("2002027", 502, "病程提交失败，草稿已保留，请稍后重试")

        record_id = resp.get("record_id")
        if record_id is None:
            # 上游说成功但没给出 record_id：不能当成功，也不能当失败
            raise BizError("2002032", 502, "病程提交结果无法确认，请核查后再操作")

        # 数据库 ck_m20_doc_note_draft_editing 强制 SAVED 时正文必须为空
        await self.repo.mark_saved(draft_id, record_id)

        now = datetime.datetime.now(datetime.timezone.utc)
        await self.log.write(
            staff_id=auth.staff_id,
            action="SUBMIT_COURSE",
            patient_id=draft["patient_id"],
            encounter_id=body.encounter_id,
            record_id=record_id,
            view_scope="NONE",
            detail={
                "course_no": resp.get("course_no"),
                "draft_no": draft["draft_no"],
                "snapshot_hash": snapshot_hash,
            },
        )
        result = {
            "draft_id": draft_id,
            "draft_status": "SAVED",
            "record_id": record_id,
            "course_no": resp.get("course_no"),
            "degraded": False,
            "degraded_sources": [],
            "data_quality": "REALTIME",
            "as_of": now,
        }
        await self.idem.set("M20_DOC_SUBMIT_COURSE", idempotency_key, result)
        return result


class RoundService:
    """查房：建、开始、标已查、结束、放弃。"""

    def __init__(
        self,
        plan_repo: Any,
        admission_client: Any,
        diagnosis_client: Any,
        mask_client: Any,
        code_service: Any,
        idem_store: Any,
        oper_log_writer: Any,
    ) -> None:
        self.plan_repo = plan_repo
        self.m05 = admission_client
        self.m07 = diagnosis_client
        self.mask = mask_client
        self.codes = code_service
        self.idem = idem_store
        self.log = oper_log_writer

    async def create_round(
        self,
        auth: Any,
        body: Any,
        idempotency_key: str,
        network_state: str,
    ) -> dict[str, Any]:
        cached = await self.idem.get("M20_DOC_CREATE_ROUND", idempotency_key)
        if cached is not None:
            if cached.get("payload_hash") != self._hash_payload(body):
                raise BizError("2002033", 409, "同一幂等键提交了不同内容")
            return cached["result"]

        existing = await self.plan_repo.find_open(auth.staff_id, body.ward_id, body.round_date)
        if existing is not None:
            raise BizError("2002004", 409, "该病区今日已有未结束的查房")

        try:
            admissions = await asyncio.wait_for(
                self.m05.list_active_by_ward(body.ward_id),
                timeout=TIMEOUT_M05_ADMISSION / 1000,
            )
        except asyncio.TimeoutError:
            raise BizError("2002026", 503, "在院清单暂不可用，无法新建查房路线")
        except Exception:
            raise BizError("2002026", 503, "在院清单暂不可用，无法新建查房路线")

        if not admissions:
            raise BizError("2002008", 400, "该病区暂无在院患者")

        masked = await self.mask.mask_fields(
            [a["patient_name"] for a in admissions], context="M20_DOC_ROUND_LIST"
        )
        for admission, display in zip(admissions, masked):
            admission["patient_display"] = display

        round_no = await self.codes.next_no("RC")
        rows = self._sort_items(admissions, body.order_strategy)
        plan = await self.plan_repo.create_with_items(
            round_no=round_no,
            staff_id=auth.staff_id,
            ward_id=body.ward_id,
            round_date=body.round_date,
            order_strategy=body.order_strategy,
            client_type=body.client_type,
            items=rows,
        )
        await self.log.write(
            staff_id=auth.staff_id,
            action="CREATE_ROUND",
            view_scope="NONE",
            detail={"round_no": round_no, "item_total": len(rows)},
        )
        now = datetime.datetime.now(datetime.timezone.utc)
        result = {
            "plan": plan,
            "degraded": False,
            "degraded_sources": [],
            "data_quality": "REALTIME",
            "as_of": now,
        }
        await self.idem.set(
            "M20_DOC_CREATE_ROUND",
            idempotency_key,
            {"payload_hash": self._hash_payload(body), "result": result},
        )
        return result

    async def get_detail(self, auth: Any, round_no: str) -> dict[str, Any]:
        plan = await self.plan_repo.get_by_no(round_no)
        if plan is None:
            raise BizError("2002006", 404, "查房计划不存在")
        items = await self.plan_repo.list_items(plan["id"])

        now = datetime.datetime.now(datetime.timezone.utc)
        failures: list[dict[str, str]] = []
        successes: list[dict[str, Any]] = []

        enc_ids = [i["encounter_id"] for i in items if i.get("encounter_id")]
        diagnoses: dict[int, str] = {}
        if enc_ids:
            try:
                batch = await asyncio.wait_for(
                    self.m07.batch_by_encounter(enc_ids),
                    timeout=TIMEOUT_M07_DIAGNOSIS * 2 / 1000,
                )
                diagnoses = batch
                successes.append({"as_of": batch.get("as_of")} if isinstance(batch, dict) else {})
            except asyncio.TimeoutError:
                failures.append({"source": "M07_DIAGNOSIS", "reason": "TIMEOUT"})
            except Exception:
                failures.append({"source": "M07_DIAGNOSIS", "reason": "ERROR"})

        for item in items:
            enc_id = item.get("encounter_id")
            # 失败时给 None，由前端显示「诊断暂不可用」，绝不显示「无诊断」
            item["diagnosis_brief"] = diagnoses.get(enc_id) if enc_id else None
            # 病程摘要：上游无「按就诊列病程」的查询接口（已 grep 复核 0 命中），
            # 因此恒为 None。给 None 而不是「暂无病程」，两者的临床含义相反。
            item["course_summary"] = None

        # 病程摘要这一路接口根本不存在，不是本次失败。
        # 用 INTERFACE_NOT_PROVIDED 而不是 TIMEOUT：处置动作相反，
        # TIMEOUT 等一会重试就好，INTERFACE_NOT_PROVIDED 重试一万次也没有。
        failures.append({"source": "M18_COURSE_LIST", "reason": "INTERFACE_NOT_PROVIDED"})
        course_summary_available = False

        quality = compute_quality(successes, failures, None, now)
        await self.log.write(
            staff_id=auth.staff_id,
            action="VIEW_WARD_ROUND",
            view_scope="SUMMARY",
            detail={"round_no": round_no, "item_count": len(items)},
        )
        return {
            "plan": plan,
            "items": items,
            # 列表页必须为空：这是给客户端核对「本响应不含病历正文」的显式标记
            "record_loaded": [],
            # 恒为 False：服务端明确说这个字段不可用，页面据此显示灰条而不是留白
            "course_summary_available": course_summary_available,
            "degraded": quality.degraded,
            "degraded_sources": quality.degraded_sources,
            "data_quality": quality.data_quality,
            "as_of": quality.as_of,
        }

    async def mark_item(
        self,
        auth: Any,
        round_no: str,
        item_id: int,
        body: Any,
        idempotency_key: str,
    ) -> dict[str, Any]:
        cached = await self.idem.get("M20_DOC_MARK_ITEM", idempotency_key)
        if cached is not None:
            return cached

        plan = await self.plan_repo.get_by_no(round_no)
        if plan is None:
            raise BizError("2002006", 404, "查房计划不存在")
        if plan["plan_status"] != "IN_PROGRESS":
            raise BizError("2002007", 409, "当前查房状态不允许该操作")

        item = await self.plan_repo.get_item(plan["id"], item_id)
        if item is None:
            raise BizError("2002009", 404, "查房明细不存在")
        if item["resident_status"] in ("DISCHARGED", "TRANSFERRED"):
            raise BizError("2002010", 409, "该患者已出院或转科，无法标记")
        if body.resident_status == "SKIPPED":
            if not body.skip_reason or len(body.skip_reason.strip()) < 2:
                raise BizError("2002011", 400, "跳过原因至少 2 个字")

        updated = await self.plan_repo.mark_item(item_id, body.resident_status, body.skip_reason)
        counters = await self.plan_repo.recount(plan["id"])
        next_item = await self.plan_repo.next_planned(plan["id"])

        now = datetime.datetime.now(datetime.timezone.utc)
        result = {
            "item": updated,
            "plan": counters,
            "next_item": next_item,
            "degraded": False,
            "degraded_sources": [],
            "data_quality": "REALTIME",
            "as_of": now,
        }
        await self.idem.set("M20_DOC_MARK_ITEM", idempotency_key, result)
        return result

    async def finish_round(
        self,
        auth: Any,
        round_no: str,
        idempotency_key: str,
    ) -> dict[str, Any]:
        cached = await self.idem.get("M20_DOC_FINISH_ROUND", idempotency_key)
        if cached is not None:
            return cached

        plan = await self.plan_repo.get_by_no(round_no)
        if plan is None:
            raise BizError("2002006", 404, "查房计划不存在")
        if plan["plan_status"] != "IN_PROGRESS":
            raise BizError("2002007", 409, "当前查房状态不允许该操作")
        remaining = plan["item_total"] - plan["item_done"] - plan["item_skipped"]
        if remaining > 0:
            raise BizError("2002014", 409, f"还有 {remaining} 位患者未处理")

        finished = await self.plan_repo.finish(plan["id"])
        await self.log.write(
            staff_id=auth.staff_id,
            action="FINISH_ROUND",
            before_status="IN_PROGRESS",
            after_status="COMPLETED",
            detail={"round_no": round_no},
        )
        now = datetime.datetime.now(datetime.timezone.utc)
        result = {
            "plan": finished,
            "degraded": False,
            "degraded_sources": [],
            "data_quality": "REALTIME",
            "as_of": now,
        }
        await self.idem.set("M20_DOC_FINISH_ROUND", idempotency_key, result)
        return result

    async def abandon_round(
        self,
        auth: Any,
        round_no: str,
        body: Any,
        idempotency_key: str,
    ) -> dict[str, Any]:
        cached = await self.idem.get("M20_DOC_ABANDON_ROUND", idempotency_key)
        if cached is not None:
            return cached

        if len(body.abandon_reason.strip()) < 5:
            raise BizError("2002015", 400, "放弃查房的原因至少 5 个字")

        plan = await self.plan_repo.get_by_no(round_no)
        if plan is None:
            raise BizError("2002006", 404, "查房计划不存在")
        if plan["plan_status"] in ("COMPLETED", "ABANDONED"):
            raise BizError("2002007", 409, "该查房已结束")

        abandoned = await self.plan_repo.abandon(plan["id"], body.abandon_reason.strip())
        await self.log.write(
            staff_id=auth.staff_id,
            action="ABANDON_ROUND",
            before_status=plan["plan_status"],
            after_status="ABANDONED",
            detail={"round_no": round_no, "reason_length": len(body.abandon_reason.strip())},
        )
        now = datetime.datetime.now(datetime.timezone.utc)
        result = {
            "plan": abandoned,
            "degraded": False,
            "degraded_sources": [],
            "data_quality": "REALTIME",
            "as_of": now,
        }
        await self.idem.set("M20_DOC_ABANDON_ROUND", idempotency_key, result)
        return result

    @staticmethod
    def _sort_items(admissions: list[dict[str, Any]], strategy: str) -> list[dict[str, Any]]:
        if strategy == "BED_NO":
            ordered = sorted(admissions, key=lambda a: a.get("bed_no", ""))
        elif strategy == "ADMIT_ORDER":
            ordered = sorted(admissions, key=lambda a: a.get("admission_date", ""))
        elif strategy == "SEVERITY":
            ordered = sorted(admissions, key=lambda a: a.get("severity_rank", 0), reverse=True)
        else:
            ordered = list(admissions)
        for idx, row in enumerate(ordered, start=1):
            row["seq_no"] = idx
        return ordered

    @staticmethod
    def _hash_payload(body: Any) -> str:
        raw = json.dumps(body.model_dump(mode="json"), sort_keys=True, ensure_ascii=False)
        return hashlib.sha256(raw.encode("utf-8")).hexdigest()
```

## 7. 缓存与异步任务设计

### 7.1 缓存清单

本子模块**不缓存任何业务实体数据**（共享规范铁律 ④：移动端不快照、不缓存业务数据到服务端）。下表所有键存的是**个人偏好**、**执行态计数**、**幂等回执**三类，没有一类是「病历/诊断/医嘱/报告的业务副本」。

| 编号 | Key 模式 | 类型 | TTL | 存什么 | 失效策略 | 命中时 data_quality |
|---|---|---|---|---|---|---|
| C-01 | `m20:doc:round:{ward_id}` | String(JSON) | 60s | 病区查房摘要（床号/脱敏名/是否有草稿），**不含诊断、不含正文** | 写操作后主动删 | `CACHED`（年龄 > 30s） |
| C-02 | `m20:doc:idem:{biz}:{key}` | String(JSON) | 86400s | 幂等回执（首次响应体） | TTL 到期 | 不涉及 |
| C-03 | `m20:doc:config:{staff_id}` | String(JSON) | 300s | 该医生生效的配置值 | 配置变更主动删 | `CACHED` |
| C-04 | `m20:doc:layout:{staff_id}` | String(JSON) | 900s | 解析后的首页编排（含回退结果） | 编排变更主动删 | `CACHED` |
| C-05 | `m20:base:lock:round:{round_no}` | String | 30s | 查房并发锁（防两人同时结束同一查房） | 主动释放 + 过期 | 不涉及 |
| C-06 | `m20:doc:audit:rate:{staff_id}` | String(计数) | 60s | 审计查询频次（API-26 限流） | TTL 到期 | 不涉及 |

**为什么幂等回执 TTL 是 24 小时**（C-02）：共享规范 §2.5 规定 `(biz_type, idempotency_key)` TTL 24h。移动端弱网重试窗口最长可到数小时（医生进入电梯、地下室），24h 覆盖了一个完整值班周期。

**为什么查房摘要有 60s 缓存而病历正文没有**（C-01）：查房摘要是一屏 20~50 行、每行 3~4 个字段的轻量数据，且它是**可重建的**（从 `m20_doc_round_item` 一条 SQL 就能出）。病历正文是权威临床内容，缓存一份就意味着 M20 库里躺着临床文本的副本——**这正是铁律 ④ 要挡的事**。

### 7.2 异步任务（Celery）

| 任务 | 触发 | 频率 | 幂等 | 说明 |
|---|---|---|---|---|
| `m20.doc.write_oper_log` | 每个写接口的事务提交后 | 事件驱动 | 是（按 `(trace_id, action)` 去重） | 日志异步入库。**失败进死信队列并告警**，不静默丢 |
| `m20.doc.sync_recent_visit` | API-11 进患者详情后 | 事件驱动 | 是（`ON CONFLICT DO UPDATE`） | 异步 upsert 最近访问，不阻塞响应 |
| `m20.doc.recount_round_items` | 查房明细变更后 | 事件驱动 | 是（按 COUNT 重算，非 +1） | 回写 `item_done`/`item_skipped` 冗余计数 |
| `m20.doc.mask_audit_detail` | 审计日志落库后 | 事件驱动 | 是 | 二次检查 `detail` JSONB 不含姓名/身份证/正文，命中则清空该字段并告警 |
| `m20.doc.rebuild_layout_cache` | 编排变更后 | 事件驱动 | 是 | 清 C-04 |

**日志异步写的取舍**：日志若与业务同事务，业务慢日志也慢；若异步且丢消息，审计缺条。选择是**异步 + 死信 + 告警**，并在 `m20_doc_oper_log` 之外保留 M20-01 通用操作日志的指针——**一条日志写成功、另一条失败时不回滚业务**（审计留痕宁可多不可少）。

### 7.3 定时任务（APScheduler）

| 任务 | 时间 | 说明 |
|---|---|---|
| `m20.doc.calc_usage_stat` | 每日 02:00 | 聚合前一日 `m20_doc_oper_log` → `m20_doc_usage_stat`。上游日志分区不可用 → 行标 `calc_status='PARTIAL'` + `missing_sources`，**不填 0** |
| `m20.doc.flush_expired_draft` | 每 30 分钟 | 物理删除 `expires_at < now()` 的 `EDITING` 与过期的 `DISCARDED` 草稿；**`SUBMITTING`/`SAVED` 一律不动** |
| `m20.doc.monthly_recheck` | 每月 1 日 03:00 | 补算上月缺失的统计行（`calc_status='FAILED'` 的重试） |
| `m20.doc.partition_check` | 每日 04:00 | 检查 `m20_doc_oper_log_pdefault` 有无行；有则告警并提示补建月份分区 |

**`calc_usage_stat` 的失败语义**：若前一日日志分区缺失（例如漏建了月份），任务**必须写一行 `calc_status='PARTIAL'` 并列出缺失时段**，而不是跳过——跳过会让日报显示「今天没人用移动医生站」，而真相是数据没算出来。

## 8. 业务规则与校验

### 8.1 编号与格式

| 编号 | 规则 |
|---|---|
| R-NO-01 | 查房单号 `round_no` = `RC` + `yyyyMMdd` + 4 位流水（如 `RC202611070001`），统一走 M20-01 单号服务（Redis `INCR`），**禁止用数据库序列拼日期**（跨零点并发会重号） |
| R-NO-02 | 草稿号 `draft_no` = `DF` + `yyyyMMdd` + 6 位流水 |
| R-NO-03 | 所有对外暴露的单号（`round_no`/`draft_no`）与内部主键分离；主键不外露 |
| R-NO-04 | `patient_display` 一律取 U-08 脱敏结果；U-08 不可用时按**最严脱敏**（只留姓 + `**`） |

### 8.2 关键业务规则

| 编号 | 规则 | 落地位置 |
|---|---|---|
| R-01 | **同一医生、同一病区、同一日期同时只能有一条未结束的查房计划** | API-04 业务逻辑第 2 步 + `idx_m20_doc_round_plan_active` |
| R-02 | **只有 `DRAFT` 状态的查房可以调整路线**；`IN_PROGRESS` 之后不允许改顺序 | API-08 + `ck_m20_doc_round_plan_status` |
| R-03 | **结束查房要求 `item_done + item_skipped = item_total`**（每个患者都有交代） | API-09 + `ck_m20_doc_round_plan_done` |
| R-04 | **放弃查房必须写 ≥ 5 字的理由** | API-10 + `ck_m20_doc_round_plan_abandoned` |
| R-05 | **已出院/转科的明细不可标「已查」** | API-07 + `ck_m20_doc_round_item_gone` |
| R-06 | **草稿同一 `(staff_id, encounter_id, course_type)` 同时只能有一份活跃行** | `uk_m20_doc_note_draft_active` 部分唯一索引 |
| R-07 | **草稿提交成功后正文必须清空**（M20 不留临床文本副本） | `ck_m20_doc_note_draft_editing` |
| R-08 | **病程记录必须在线提交**；离线一律拒绝，不排队、不自动重试 | API-17 第 2/7 步 + Service `submit()` |
| R-09 | **M20 不写危急值的任何状态**；只读展示 + 提示去 M07 确认 | API-12 第 4 步（无写路径）+ 决策 D-03 |
| R-10 | **列表页不得返回病历正文**；`record_loaded` 必须为空数组 | API-05 + SC-01 |
| R-11 | **`content_hash` 原样透传 M18 的值，M20 永不计算、永不改写** | API-13 第 3 步 |
| R-12 | **草稿版本冲突不自动覆盖**，返回当前正文让用户合并 | API-16 |
| R-13 | **导出内容不含任何患者个体信息** | API-30 |
| R-14 | **维度字段无值存 `''`/`0` 而非 `NULL`**（`dept_id=0`、`bed_no=''`），避免唯一约束失效 | 8 张表全部遵循 |

### 8.3 字段级校验

见第 5 章各页的 `V-Pxx-nn` 校验规则表与数据结构文件 §4.11 Pydantic 的 `model_validator`。三处**双重校验**（Pydantic 与数据库 CHECK 都写）的地方：

| 校验 | Pydantic | 数据库 |
|---|---|---|
| 跳过原因 ≥ 2 字 | `RoundItemDetail._check_shape` | `ck_m20_doc_round_item_skip` |
| 放弃原因 ≥ 5 字 | 路由层 `len(...)<5` | `ck_m20_doc_round_plan_abandoned` |
| `SAVED` 草稿正文必须为空 | `NoteDraftDetail._check_shape` | `ck_m20_doc_note_draft_editing` |
| 降级时 `data_quality` 不得为 `REALTIME` | `QualityMeta._check_shape` | `ck_m20_doc_oper_log_degraded` |

**为什么两处都写**：Pydantic 挡住 99% 的正常写入路径，数据库挡住「运维直连改数据」与「未来新增的写入路径忘了校验」。**只在 Pydantic 写等于假设所有写入都走 API**，而这个假设在真实运维中一定会被打破。

### 8.4 降级策略（逐条对应 §2.4 的上游）

| 上游 | 失败时的行为 | `degraded_sources` | 页面表现 |
|---|---|---|---|
| U-01 Token | 401 `"2002001"` | — | 跳登录 |
| U-05 权限上下文 | **403 `"2002002"`，fail-closed** | — | 提示无权限 |
| U-07 `perm/filter-sql` | **403，fail-closed** | — | 提示无权限 |
| U-08 脱敏 | 按最严脱敏（`李**`）继续 | `{"source":"M02_MASK","reason":"TIMEOUT"}` | 控件显示降级黄条 |
| U-14 M03 患者简讯 | 患者区显示「暂不可用」 | `{"source":"M03_PATIENT","reason":"TIMEOUT"}` | 黄条 + 空态文案「数据暂不可用」 |
| U-16 M05 住院信息 | 住院区显示「暂不可用」 | `{"source":"M05_ADMISSION","reason":"TIMEOUT"}` | 同上 |
| U-17 M05 在院清单 | **拒绝新建查房** `"2002026"` | 失败响应，不走降级 | 提示「在院清单暂不可用，无法新建路线」 |
| U-23 M07 诊断 | 诊断列显示「诊断暂不可用」 | `{"source":"M07_DIAGNOSIS","reason":"TIMEOUT"}` | 黄条；**绝不显示「无诊断」** |
| U-34 M18 病历正文 | **正文 `null` + `record_exists=null` + `exists_known=false`** | `{"source":"M18_EMR","reason":"TIMEOUT"}` | **黄条「病历服务暂不可用」；绝不显示「无病历」** |
| M12/M13 报告 | 报告区显示「暂不可用」 | `{"source":"M12_REPORT" 或 "M13_REPORT","reason":"TIMEOUT"}` | 黄条 |
| M18-03 病程提交 | **不降级**，返回错误码，草稿保留 | 失败响应 | 明确报错 + 草稿未丢 |

**降级三形态（共享规范 §8A）**：正常（200 + `code:0` + 完整 data）/ 降级（200 + `code:0` + 四标记 + `degraded:true`）/ 失败（4xx/5xx + 非 0 code）。**本子模块禁止第四种形态：200 + 空 data 表示「无权限」或「查不到」**——客户端会把它当成「没有数据」，而这正是最危险的静默失效（见 SC-02/SC-03）。

### 8.5 恒等式

| 编号 | 恒等式 |
|---|---|
| E-01 | `m20_doc_round_plan.item_total = count(m20_doc_round_item)` |
| E-02 | `item_done = count(resident_status='VISITED')`，`item_skipped = count(resident_status='SKIPPED')` |
| E-03 | `plan_status='COMPLETED'` ⟹ `item_total = item_done + item_skipped` |
| E-04 | `m20_doc_usage_stat.record_view_count <= patient_view_count` |
| E-05 | `m20_doc_usage_stat.degraded_count <= request_count` |
| E-06 | `m20_doc_usage_stat.draft_save_count + draft_discard_count <= draft_create_count` |
| E-07 | 首屏 `as_of = min(所有成功来源的 as_of)`，**不是请求时刻** |
| E-08 | 任一上游失败 ⟹ `degraded = true`（是「或」不是「与」） |
| E-09 | `degraded = true` ⟹ `data_quality ≠ REALTIME` |

| 危急值待办的内部列表接口 | M12/M13 只有对外 REST `GET /api/v1/m1x/review/critical/list`（需用户权限 `m1x:critical:query`） | 危急值待办来自事件推送的本地缓存（M20-01 承载），不主动拉列表 |
| 危急值确认的移动端接口 | M12/M13 的 `on-acknowledged` 语义是「**M07 确认后回调**」，不是「谁能确认」 | **M20-02 确认动作只读不写**，提示「请在医生工作站确认」（决策 D-03） |
| **按就诊列出病程记录（查房列表的「最近一次病程」列）** | M18-03 的 34 个 API 里无「按 `encounter_id` 列病程记录」的查询口（已 grep 复核，0 命中；只有 `POST course-records` 写入与按 `record_id` 的 `PUT`） | **不静默留白**：API-05 返回 `course_summary_available: false` + `degraded: true` + `degraded_sources: [{"source":"M18_COURSE_LIST","reason":"INTERFACE_NOT_PROVIDED"}]`；页面第三列显示灰色说明「病程摘要需在医生工作站查看」+ 跳 M07 的入口 |

**为什么最后一条必须显式标记而不是留白**：查房页第三列如果只是少一列，医生不会知道自己少了什么——他会以为这就是全部。**留白等于「本来就没有」，灰条加跳转等于「这里本该有，但现在要去别处看」**。这两者给医生的决策完全不同：前者他会以为这个病人没写病程，可能重复书写；后者他知道要去工作站看。

**为什么 `reason` 用 `INTERFACE_NOT_PROVIDED` 而不是 `TIMEOUT`**：这两个降级原因的处置动作相反——`TIMEOUT` 是「等一会重试就好」，`INTERFACE_NOT_PROVIDED` 是「重试一万次也没有」，只有向上游提请补接口才能解决。**用一个笼统的降级原因覆盖两种相反的处置建议，等于让运维去查一个永远不会好的超时。**

### 10.3 发布事件

**本子模块不发布任何事件。** M20 的三类事件分别由其他子模块发布，M20-02 不产生需要通知其他模块的状态变化——查房进度与草稿都是 M20 内部事实，不构成跨模块事件。

| 事件命名空间 | 归属子模块 | 典型事件 |
|---|---|---|
| `m20.approval.*` | M20-04 移动审批引擎 | `m20.approval.completed` 等（审批流状态变化） |
| `m20.message.*` | M20-08 消息与待办 | 消息投递结果类事件 |
| `m20.mobile.*` | M20-01 移动端接入与移动适配基础 | `m20.mobile.device_online` 等（设备上下线等运行态） |

**上表的作用是让读者在这一节就能看到「M20 有哪些事件命名空间、归属谁」，不必翻去另外三个子模块的文档。** M20-02 自己既不发布也不订阅这三类：发布方是别人，而订阅方（本模块）订阅的是上游业务事件（见 §10.4），不是 M20 内部事件。

**为什么不为查房单独发布一类移动端运行态事件**：查房完成后要通知的只有统计，而统计由 M20-02 自己的定时任务从本表聚合，不需要事件。**为一个纯内部事实发事件，等于给未来的订阅方制造一个「我不处理就丢消息」的隐式依赖。**

### 10.4 订阅事件

| 事件名 | 来源 | 本子模块的消费动作 | 载荷安全 |
|---|---|---|---|
| `m12.critical.detected` | M12-05 | 刷新危急值待办缓存（`m20:doc:critical:{staff_id}`），首页角标 +1 | 载荷只取 `review_id`/`patient_id`/`dept_id`/`detected_at` |
| `m13.critical.detected` | M13-04 | 同上 | 同上 |

**载荷红线**：本子模块订阅的事件载荷**不得包含患者姓名、联系电话、身份证明文**；若上游发送了这些字段，M20 只取 ID 与状态，其余字段丢弃（不落库、不进日志）。**M20 的库与日志里不出现患者身份信息**，这是「不建业务副本」在事件层的落地。

## 11. 异常处理与日志

### 11.1 异常与降级总表

| 异常类别 | 表现 | 处理 | HTTP / code |
|---|---|---|---|
| 鉴权失败 | Token 过期/伪造 | 不重试 | 401 / `"2002001"` |
| 权限不足 | `perm/check` 未通过；权限接口不可用 | **fail-closed**，不降级放行 | 403 / `"2002002"` |
| 数据越权 | 患者不在数据范围 | 403（不用 404） | 403 / `"2002002"` |
| 业务状态冲突 | 非 `IN_PROGRESS` 时操作 | 提示刷新 | 409 / `"2002007"` |
| 乐观锁冲突 | 草稿版本不一致 | **返回当前内容供合并，不自动覆盖** | 409 / `"2002004"` |
| 幂等键冲突 | 同 key 不同内容 | 提示更换 | 409 / `"2002033"` |
| 上游超时（读） | M03/M05/M07/M18/M12/M13 | **降级返回 + 四标记** | 200 / `code:0` + `degraded:true` |
| 上游超时（写在路线上的） | U-17 在院清单 | 拒绝新建，不铺空路线 | 503 / `"2002026"` |
| 上游超时（写病程） | M18-03 | **不降级、不排队**，草稿保留 | 504 / `"2002028"` |
| 上游结果不明 | 返回成功但缺 `record_id` | 不当成功也不当失败 | 502 / `"2002032"` |
| 离线提交 | `X-Network-State: OFFLINE` | 服务端主动拒绝 | 400 / `"2002030"` |
| 体量超限 | 报告 > 200KB | 分段加载 | 416 / `"2002020"` |
| 限流 | 单医生 > 60 次/分钟 | 退避重试 | 429 / `"2002048"` |
| 内部错误 | 未捕获异常 | 统一 500，不外泄堆栈 | 500 / `"2002049"` |

### 11.2 日志规范

**结构（JSON，一行一条）**

```json
{
  "ts": "2026-11-07T10:20:03.482+08:00",
  "level": "INFO",
  "logger": "m20.doc",
  "trace_id": "16ce1be5483df09c",
  "staff_id": 20031,
  "action": "SUBMIT_COURSE",
  "patient_id": 10032,
  "encounter_id": 81002,
  "duration_ms": 812,
  "degraded": false,
  "data_quality": "REALTIME",
  "msg": "病程记录提交成功"
}
```

**级别**

| 级别 | 用于 |
|---|---|
| INFO | 正常业务完成（查房开始/结束、草稿保存、病程提交） |
| WARN | 降级返回、幂等命中、版本冲突、配置变更 |
| ERROR | 上游失败、病程提交失败、日志异步入库失败 |
| CRITICAL | 权限 fail-closed 连续触发、审计日志写失败超阈值、发现 `detail` 含身份信息 |

**日志红线**

| 编号 | 规则 |
|---|---|
| LOG-01 | 日志里**不得出现病历正文、草稿正文、报告全文**；只记 `text_length`、`content_hash`、`record_id` |
| LOG-02 | 日志里**不得出现患者姓名、身份证、手机号**；`patient_display` 已是脱敏值，其余一律不记 |
| LOG-03 | 哈希只记前 12 位（`sha256[:12]`），完整哈希留在 `m20_doc_oper_log.detail` 里由权限控制 |
| LOG-04 | `data_quality=CACHED` 或 `degraded=true` 的响应，**页面必须有可见提示（顶部黄条）**。没有提示的降级等于欺骗 |

### D.2 关键决策记录

| 编号 | 决策 | 被放弃的选项与为什么不行 |
|---|---|---|
| D-01 | **移动端不开医嘱、不开处方、不签署病历、不确认危急值** | ① 开医嘱：M07-03 的 `POST /api/v1/m07/orders` 有 `auto_issue` 参数，手机上误触 = 一条已下达的真实医嘱；② 开处方：M07-05 写入后要走签名，移动端做等于自建签名通道；③ 签署：**M18-03 全模块 34 个接口中没有任何签核接口**，移动端签署在系统里根本没有归属模块，硬做就是在 M20 诞生第二份临床事实。M20-02 只做到「提交定稿请求」 |
| D-02 | **不接入 `m20_base_offline_queue`，病程记录必须在线提交** | 放弃「离线暂存后自动提交」：给一个不允许离线的操作留通道，医生会在离线时看到「已暂存，将自动提交」，回家过周末；周一那条记录因冲突进 `CONFLICT`，**医生以为写完了、系统以为是草稿、病历上是空的**。队列里连 `M18_COURSE` 这个 `biz_type` 都不该有 |
| D-03 | **危急值只读，不确认** | 放弃「替 M07 调 `on-acknowledged`」：该接口语义是「M07 确认后回调」，代调会让 **M07 侧认为未确认、M13 侧认为已确认**，一个危急值两个状态且两边都不报错。放弃「调对外 REST 兜底」：绕开 M07-04 确认逻辑，同样制造第二份状态。放弃「本地记一条确认留痕」：**是三者中最坏的**——数据上看像确认过，实际停在 `NOTIFIED` |
| D-04 | **查房列表只取摘要，展开某一行才调 M18 P-01** | 放弃「列表页预取病历状态」：20 个患者 × 100ms = 2000ms 串行，**正好吃掉首屏业务聚合的全部 900ms 预算**（总算 4100ms，超 105%）。用 `record_loaded` 空数组做显式自证 |
| D-05 | **M18 超时返回 `record_exists=null` + `exists_known=false`，绝不返回「无病历」** | 放弃「超时当没有」：M07-06 会据此生成简化版正式文书，**正式病历少了诊断段落而系统、医生、患者三方都不知道**。`null` 与 `false` 的区别就是「不知道」与「没有」的区别 |
| D-06 | **`data_quality` 由 M20 自己重算，不透传上游** | 放弃映射表（`DAILY→CACHED`、`ESTIMATED→PARTIAL`）：它是猜的。M18 的 `DAILY` 意思是「来自日批汇总」，可能恰是最新最准；M20 的 `CACHED` 意思是「这是 M20 30 秒前的缓存」。两个「不实时」的成因完全不同，映射成一个值会让运维永远查不清是这边慢还是那边慢 |
| D-07 | **病历正文与 `content_hash` 原样透传，M20 永不计算** | 放弃「M20 校验一遍哈希」：M18 是唯一权威方，M20 重算会出现「两个模块两个哈希」，而两者不一致时没有判定依据 |
| D-08 | **草稿为独立表而非复用 M18 的段落表** | 放弃「直接写 M18 的 DRAFT 字段」：M18 的 `m18_emr_record` 是病历事实表，M20 往里写就等于 M20 会持有或触碰病历正文，与铁律 ④ 冲突。草稿表在提交成功后正文必须清空，**M20 库里不留临床文本** |
| D-09 | **撤回 `m20_doc_critical_ack`（原计划 9 张改为 8 张）** | 见上 D-03。表本身没有存在的理由——它只是为 D-03 被否决的那条路准备的 |
| D-10 | **操作日志 `detail` 不写正文与患者身份信息** | 放弃「日志记全量便于排障」：日志读取权限面远大于病历正文，塞了正文等于给不需要病历权限的人一条绕过路径。要证明「谁看过哪份病历」，`record_id` + 时间戳足够 |
| D-11 | **`m20_doc_oper_log` 只增不删 + 月分区 + `DETACH` 归档** | 放弃「定期 `DELETE` 旧日志」：`app_m20` 没有 DELETE 权限，掩盖行为无法发生；放弃「永久保留在主表」：主表会无限增长到分区扫描变慢。`DETACH` 是唯一同时满足「不删」与「不涨」的做法 |
| D-12 | **`m20_doc_recent_visit` 允许物理删除** | 放弃「所有表都不给 DELETE」：它是个人工作记忆不是审计事实，不淘汰会随「医生数 × 患者数」无限增长，且删掉任何一条不影响任何业务判断 |
| D-13 | **草稿版本冲突不自动覆盖** | 放弃「最后写入者赢」：医生在手机与 iPad 上各写了一半，自动覆盖会丢一半内容 |
| D-14 | **顶栏黄条是降级提示的必需品** | 放弃「降级只在日志里记」：`data_quality=CACHED` 或 `degraded=true` 时页面无提示，等于让医生拿旧数据做临床判断。**没有提示的降级等于欺骗** |
| D-15 | **不发布任何事件** | 放弃「查房完成发事件」：查房进度是 M20 内部事实，统计由本子模块定时任务聚合。为纯内部事实上发事件，只会给未来的订阅方制造「我不处理就丢消息」的隐式依赖 |
