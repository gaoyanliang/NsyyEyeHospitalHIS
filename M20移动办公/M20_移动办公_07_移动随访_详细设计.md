## 1. 模块概述

### 1.1 模块定位

M20-07 移动随访是**随访工作台在手机上的那一半**。它回答三个问题：

1. **今天打给谁？** —— 把 M19 的随访待办、M20 的到点提醒、护士自己收藏的筛选条件汇成一个可以顺着往下打的队列。
2. **打完了记在哪？** —— 护士不是打完就算，要提交随访结果（归 M19）、要留下触达过程事实（归 M20）、要能看到还剩几个人没打。
3. **打不通怎么办？** —— 离线、无信号、患者拒接、任务被别的护士抢先做了，这些边界情况必须有确定的处理方式，不能靠护士记忆。

一句话：**M20-07 是随访的「执行端」，M19 是随访的「计划端与档案端」。**

### 1.2 为什么独立成子模块

随访这件事在 M20 里为什么不并进 M20-02 移动医生站或 M20-03 移动护理？四条理由：

**理由一：使用者与权限模型完全不同。**
移动医生站的使用者是医生，数据范围是「我的患者」；移动护理的使用者是护士，范围是「我的病区」。随访的使用者是**随访专员**（可能是护士兼任，也可能是专职岗位），数据范围是「分配给我的随访任务」，而任务归属由 M19 的随访计划动态生成。**同一岗位的人，在不同的系统能力下看到的数据范围是不同的对象**，硬并进任何一个都会让那个子模块的权限模型分叉。

**理由二：使用节奏不同。**
医生站的使用节奏是「跟着一次就诊走」（几分钟内看、写、开单、结束）；随访的节奏是「一天打 20~40 通电话」，每通 3~8 分钟，走的是**串行队列**而不是单次会话。这意味着交互模型完全不同：随访需要「打完一个自动跳下一个」「还剩几个」「今天进度」这类队列式 UI，医生站一条也不需要。

**理由三：离线需求强度最高。**
随访的特点是「拿着手机就能干活」，护士可能走到病房、走到患者家里、在楼梯间接电话。**随访是全 M20 里离线使用频率最高的场景**。离线队列、冲突重放这套逻辑如果并进 M20-01，会被其他子模块的低强度需求稀释；并在随访这里，才有足够的使用量来验证它。

**理由四：它是 M19 与 M20 的接缝，接缝需要显式的设计。**
M19 管计划与结果，M20 管执行与触达。这条缝如果不显式设计，最常见的结果是：**护士在 M20 里把随访做完了，M19 不知道；或者 M19 的随访记录显示「未完成」，而手机上的待办已经消失。** 本子模块存在的首要职责就是让这条缝有确定的、可验证的对接方式。

**估算数据支撑：** 眼科院后随访（屈光术后 1 天/1 周/1 月/3 月/6 月/1 年，白内障术后 1 天/1 周/1 月/3 月，慢病随访）年均随访任务约 36 万次；按每通电话含拨号、沟通、记录、提交平均 6 分钟计，全年随访通话工时约 3.6 万小时，折合 18 个全职岗位。**这是一个每天有 1,000 通电话在跑的业务，值得一个子模块。**

### 1.3 与相邻子模块的分工

| 能力 | 归属 | M20-07 做什么 | M20-07 不做什么 |
| :--- | :--- | :--- | :--- |
| 随访计划定义、节点生成 | M19-01 | 调 P-01 取待办 | 不建计划表、不算节点、不生成任务 |
| 随访任务的生命周期（下发/改派/取消/完成） | M19-01 | 只读任务状态，不本地改 | 不存任务状态副本 |
| 随访结果内容（症状、视力、用药、建议） | M19-02 | 调执行接口提交，载荷原样搬运 | 不校验临床字段、不落本地表 |
| 触达过程事实（拨了几次、通没通、多久） | **M20-07** | 全权负责 | — |
| 有效随访率、随访到位率等临床指标 | M19 + M22 | **不算** | 见 §4.9 的表边界说明 |
| 员工待办与角标 | M20-08 | 提供去重键，走写接口 | 不建待办表、不改角标逻辑 |
| 离线队列基础设施 | M20-01 | 只读队列表，写自己的扩展行 | 不改 `m20_base_offline_queue` 结构 |
| 患者基本信息 | M03-01 / M02 | 调 U-06 / U-14 取脱敏摘要 | 不建患者表、不缓存明文 |

**三处最容易越界的地方（必须在 code review 时盯住）：**

1. **「顺手在 M20 存一份随访结果，免得每次都要调 M19」** —— 这是最诱人的错误。存了副本后，M19 的随访记录与 M20 的副本必然在某个时刻不一致，而**患者档案要的是唯一版本**。禁止。
2. **「随访任务从 M19 拉过来在本地建个任务表，这样列表查询快」** —— 这是把 M19 的任务表复制一份。任务一旦被改派，两份数据分叉。正确做法是调 P-01，必要时在 Redis 缓存 30 秒（继承 M19 自己的缓存口径），**不落库**。
3. **「M20 算出随访完成率给科室看板用」** —— 分母（应访数）在 M19 手里，M20 自己造分母必然与 M19 报出的数字不一致。见 §3.4.2。

### 1.4 概念辨析

| 概念对 | 区别 | 为什么容易混 |
| :--- | :--- | :--- |
| **随访任务** vs **触达尝试** | 任务是「该给这个患者打一次电话」这个应办事项（M19）；触达尝试是「我今天拨了三次才接通」这个动作（M20）。**一个任务对应 N 次尝试。** | 都带 `task_id`，都出现在随访页上 |
| **随访结果** vs **触达记录** | 结果是患者说了什么（临床信息，M19）；触达记录是通话这个事件发生了没有（过程事实，M20） | 都在一次通话结束时产生，同一个动作填两张表 |
| **接通率** vs **有效随访率** | 接通率 = 接通次数 / 触达次数，分母归 M20；有效随访率 = 有效随访数 / 应访数，分母归 M19 | 名字里都有「随访」，看起来是一类指标 |
| **随访备忘** vs **患者画像** | 备忘是「这次通话学到的沟通技巧」（只有上午在家、需要儿子转达）；画像是患者的临床与人口学特征（归 M03） | 都挂在 `patient_id` 上 |
| **随访提醒** vs **随访任务** | 提醒是「明天有 5 个随访到期」这个通知（M20-08 通道）；任务是「要给张三打一次」这个应办事项（M19） | 提醒的内容就是任务的数量 |
| **离线队列项** vs **随访触达记录** | 队列项是「还没同步上去的动作」（可能被丢弃）；触达记录是「已经确认发生的动作」（已落库） | 离线时两者内容一模一样 |

**两条最容易搞错、必须写进代码注释的辨析：**

**辨析一：M07-07 的「文书及时率」与随访的「接通率」不是一个东西。**
M07-07 统计的是医生写病历的及时性（`M07医生工作站/M07_医生工作站_07_医生工作量与效率_详细设计.md:250`「就诊后 24h 内签名的文书 / 总文书」）；本子模块的接通率是护士打电话的接通比例。名字里的「及时」与「接通」不构成任何可比性。

**辨析二：「今天有 12 个随访待办」这个数字有至少三个不同来源，取值必然不同。**
- M19 P-01 返回的 `total`：**M19 视角下分配给我的、未完成的任务数**——这是「我还有多少活」。
- M20-08 角标（`m20:msg:unread:{staff_id}`）：**跨子模块去重后的待办总数**——这是「我手机上该点几个红点」。
- M20-07 自己的今日进度（`m20_fol_stats` 的 `attempt_count`）：**我今天已经打了几通**——这是「我干了多少」。

三个数字在一屏里同时出现时，**必须各自标注口径**。若页面只写「待办 12」而护士以为这是「还剩 12 个没打」，就会出现「我明明打完 15 个了怎么还是 12」的困惑。**页面上的每一个数字都要能回答「这个数是怎么来的」。**

### 1.5 模块目标

| 编号 | 目标 | 可验证的判据 |
| :--- | :--- | :--- |
| G1 | 护士能在 3 次点击内开始一通随访电话 | 从打开 App 到进入某个患者的随访执行页，点击次数 ≤ 3 |
| G2 | 随访结果必须落到 M19，M20 不产生第二份 | `information_schema.tables` 中不存在任何存放随访结果内容列的表 |
| G3 | 触达过程事实 100% 可追溯 | 任意一次已提交的随访，都能在 `m20_fol_attempt` 找到对应行并反查 `exec_no` |
| G4 | 离线可用，冲突不丢不覆盖 | 断网状态下能完成触达记录；恢复后冲突项进入待处理队列，需人工处置并留痕 |
| G5 | 附件永不进数据库 | `m20_fol_media` 无任何大字段列；探针任务每日真 GET 校验，`MISSING` 项自动告警 |
| G6 | 统计口径唯一 | 接通率等指标只由 `m20_fol_stats` 产出；页面不存在第二套计算路径 |
| G7 | 敏感信息不落地明文 | 任何 M20-07 接口响应中不出现患者完整姓名、完整手机号、完整身份证号 |

**三条最容易误入的范围外事项：**

1. **O06 特别强调：M20 不接任何患者侧网关。** 共享规范 §1.6 明确「患者短信/微信/邮件/患者端站内信归 M03-05 + M21，M20 不涉及、不建患者消息表、不接网关」。本子模块的「提醒」只推给员工（M20-08 通道），**绝不直接给患者发消息**。若业务方提出「随访电话打不通能不能自动发个短信」，那要走 M03-05，不是本子模块加个接口。
2. **O04 的边界：本子模块只算「接通率」，不算任何以「应访数」为分母的比率。** 原因见 §3.4.2。
3. **O02 的边界：即使页面显示「标记任务完成」，也是调 M19 的执行接口由 M19 改状态，M20 不直接改任务状态。** M20 没有任务表可以改。

### 2.3 三处边界

#### 2.3.1 边界一：随访结果的归属

| 事项 | 归 M19 | 归 M20 | 判据 |
| :--- | :--- | :--- | :--- |
| 患者诉「左眼有点胀」 | ✅ | — | 这是临床信息，下次门诊医生需要知道 |
| 「患者只有上午在家」 | — | ✅ | 这是沟通信息，只有随访专员需要知道 |
| 是否接通、通话 4 分 12 秒 | — | ✅ | 这是过程事实，反映执行工作量 |
| 挂了电话之后要不要再打 | — | ✅（记录尝试次数） | 这是执行策略 |
| 随访结论「恢复良好，正常」 | ✅ | — | 这是临床判断 |
| 本次用了哪一版话术 | — | ✅ | 这是执行规范性的证据 |

**判据的完整表述：** **「这句话如果患者下次来门诊，医生需要知道吗？」**
- 需要 → 是临床信息 → 必须写进 M19 的随访结果。
- 不需要（只是打电话时的技巧）→ 写进 `m20_fol_memo`。

**为什么这条边界必须硬：** 若允许护士把「左眼有点胀」写进 M20 的备忘，这段信息就永远进不了病历。三个月后患者视力出事，医生翻病历看到的是「随访记录：已完成，无异常」——**因为真正的异常被记在了一个医生看不到的表里**。这不是数据冗余问题，是**安全问题**。

**落地为流程约束：** 随访任务在 M20 侧**不能只录触达记录就标记完成**。必须提交随访结果（调 M19-02）才允许结束任务。触达记录只记「打了没打通」，结果才是「打通之后说了什么」。若确实没接通（`connected_flag = FALSE`），允许只录触达记录，任务回到 M19 的下一次随访节点。

#### 2.3.2 边界二：与 M20-08 待办的边界

| 事项 | M20-07 | M20-08 |
| :--- | :--- | :--- |
| 待办表结构 | 只读方，不建表 | 首建方，拥有一票否决权 |
| 写入待办 | **必须走 M20-08 的写接口**，不直接 `INSERT` | 提供写接口 |
| 去重键 | 提供 `(source='FOLLOWUP', biz_id=task_id)` | 按 `(source, biz_id)` 去重 |
| 角标数值 | 不参与计算 | 计算并返回 |
| 「今天该随访的几个」数字 | 页面展示时标注口径 | 角标用它的数字 |

**为什么 M20-07 不建自己的待办表：** 若 M20-07 存一份随访待办、M20-08 再存一份汇总待办，护士在手机上看角标是 8（M20-08 的数字），点进去 M20-07 列表显示 11 条（M20-07 自己的查询）。**这两个数字对不上，护士就再也不信角标了。** 总纲 M20-CALC-03 记录的教训（五来源简单相加 = 34 条而非去重后 19 条，虚高 79%）正是这类问题。

#### 2.3.3 边界三：离线基础设施的边界

| 事项 | M20-01 | M20-07 |
| :--- | :--- | :--- |
| `m20_base_offline_queue` 表结构 | 首建，拥有所有权 | 只读 |
| 重放调度框架 | 提供 | 使用 |
| `biz_type = 'FOLLOWUP_ATTEMPT'` 的载荷结构 | 不关心 | 定义 |
| 随访特有的冲突判定规则 | 提供通用框架（M20-CALC-06） | 落地 `ENTITY_GONE` / `STATE_INVALID` 的具体判据 |
| 冲突待处理队列页面 | 不提供（各子模块自己提供） | 提供（P06） |

**M20-07 往队列表里写什么：** 只写 `biz_type = 'FOLLOWUP_ATTEMPT'` 的行，业务载荷落在 `m20_fol_offline_item` 扩展表里。**另外两种 `biz_type` 归别的子模块，M20-07 一行都不碰。**

### 3.2 状态机

#### 3.2.1 随访任务在 M20 视角下的状态（只读投影）

M20 **不拥有**随访任务的状态，但护士在手机上看到的是经过投影的状态。这个投影必须显式定义，否则「任务到底算不算完成」会由两个系统的实现细节决定。

```
              ┌──────────────────────────────────────────────┐
              │  状态来自 M19 P-01 的 task_status + P-11 的     │
              │  found/exec_status，M20 只做投影，不写回        │
              └──────────────────────────────────────────────┘

  P-01 task_status = PENDING
        │
        ▼
  ┌──────────────┐   本地已录触达但未提交结果   ┌────────────────────┐
  │  PENDING_TOUCH│────────────────────────────▶│  IN_PROGRESS_LOCAL │
  │ 待随访        │                             │ 已触达待提交结果    │
  └──────┬───────┘◀────────────────────────────└────────┬───────────┘
         │         撤销触达记录（未提交前可撤）           │
         │                                              │ 提交结果成功
         │  P-11 found=true                              ▼
         │  ┌───────────────────┐              ┌────────────────────┐
         └─▶│  DONE_ELSEWHERE   │◀─────────────│  SUBMITTING        │
            │ 已被他人完成       │   P-11 回查    │ 提交中（可能离线）  │
            └───────────────────┘   discovered  └────────┬───────────┘
                                                          │ 提交失败
                                                          ▼
                                                 ┌────────────────────┐
                                                 │  SUBMIT_FAILED     │
                                                 │ 提交失败（可重试）  │
                                                 └────────────────────┘
```

| M20 投影状态 | 判据 | 页面表现 | 允许的动作 |
| :--- | :--- | :--- | :--- |
| `PENDING_TOUCH` | P-01 返回该任务且 P-11 `found=false`，且本地无未提交的触达记录 | 「待随访」 | 拨号、记触达 |
| `IN_PROGRESS_LOCAL` | 本地有未提交的触达记录 | 「待提交结果」 | 提交结果、撤销触达 |
| `SUBMITTING` | 结果提交请求已发出、未收到终态 | 「提交中」 | 等待，不可重复提交 |
| `SUBMIT_FAILED` | 提交返回明确失败 | 「提交失败，可重试」+ 原因 | 重试、转离线 |
| `DONE_ELSEWHERE` | P-11 返回 `found=true`，但本地没有对应的提交记录 | 「已由他人完成」+ 完成人与时间 | 只读查看 |
| `CONFLICT` | 离线重放时判定 `STATE_INVALID` | 「已被他人处理」+ 冲突详情 | 进 P06 处置 |

**为什么要有 `DONE_ELSEWHERE` 这个状态而不是直接隐藏任务：** 两个人同时跟一个患者是典型场景（一个打电话、一个发微信）。若被抢先完成后任务直接从列表消失，护士会怀疑「我刚才明明看到有这条」，甚至以为自己记错了。**显式告诉护士「这条已被张三在 10:23 完成」，比让它静默消失更能建立信任。**

#### 3.2.2 离线队列项的完整状态机

```
                          ┌──────────────────────────────────────────┐
                          │ 由 M20-01 的重放调度器驱动状态推进         │
                          └──────────────────────────────────────────┘

  护士离线保存触达
        │
        ▼
  ┌──────────┐   调度器取到    ┌──────────┐   重放成功   ┌──────────┐
  │ QUEUED   │───────────────▶│ SYNCING  │─────────────▶│ SYNCED   │  终态
  └────┬─────┘                └────┬─────┘              └──────────┘
       │                           │
       │                           │ 重放发现冲突
       │                           ▼
       │                      ┌──────────┐
       │                      │ CONFLICT │──── 人工 RETRY 且已无冲突 ──▶ SYNCED
       │                      └────┬─────┘
       │                           │ 人工 DISCARD / MANUAL_APPLY（已记录）
       │                           ▼
       │                      ┌────────────┐
       │                      │ ABANDONED  │  终态（已留痕）
       │                      └────────────┘
       │
       │ 重放失败且可重试（网络/超时）
       ▼
  ┌──────────┐   超过最大重试次数
  │ FAILED   │──────────────────────▶ {需人工介入，进 P06 的「同步失败」页签}
  └────┬─────┘
       │ 人工 RETRY
       └──────────────▶ QUEUED
```

| 状态 | 含义 | 谁推进 | 后续可到 |
| :--- | :--- | :--- | :--- |
| `QUEUED` | 已保存，等待重放 | 客户端写入 | `SYNCING` |
| `SYNCING` | 正在重放 | M20-01 调度器 | `SYNCED` / `CONFLICT` / `FAILED` / `QUEUED`（超时回退） |
| `SYNCED` | 重放成功，M19 已落库 | 调度器 | 终态 |
| `CONFLICT` | 重放发现业务冲突，**不自动处置** | 调度器判定 | `SYNCED`（人工 RETRY 后）/ `ABANDONED` |
| `FAILED` | 技术性失败（网络、M19 5xx），可重试 | 调度器 | `QUEUED`（人工重试）/ `ABANDONED` |
| `ABANDONED` | 人工判定放弃，留痕 | 人工 | 终态 |

**两条硬规则：**

1. **`CONFLICT` 绝不自动覆盖、绝不自动丢弃。** 总纲 M20-CALC-06 的原话是「必须进『待处理队列』由人决定（丢弃/应用/手工修正）并留痕」。本子模块的实现是：冲突进入 P06 页面，处置时必须填理由（`FolConflictResolve.reason` 最少 4 字），处置人与处置时间落在 `resolved_by` / `resolved_at`。
2. **`SYNCING` 超时必须回退到 `QUEUED`，不能停在 `SYNCING`。** 若停在 `SYNCING`，这条记录既不会被重放也没人处理。回退后重试计数 +1，超过上限转 `FAILED`。

#### 3.2.3 话术与知识卡的状态机

```
  ┌────────┐  发布   ┌────────┐  下架   ┌──────────┐
  │ DRAFT  │────────▶│ ACTIVE │────────▶│ ARCHIVED │  终态
  └────────┘         └────────┘         └──────────┘
      ▲                    │
      └────────────────────┘
        撤回发布（仅当该版本从未被任何触达记录引用）

  ACTIVE 状态有且只有一个版本（uk_m20_fol_script_active 部分唯一索引保证）
  改版路径：先把旧版 ACTIVE → ARCHIVED，再把新版 DRAFT → ACTIVE
```

**为什么「撤回发布」多了一条「从未被引用」的限制：** 若某版话术已经被护士念过，撤回后历史触达记录指向一个不存在的生效版本，回溯时无法回答「当时念的是什么」。这是与共享规范「已经发生的事不能被后来的修改覆盖」同一原则。

#### 3.2.4 附件探针状态机

```
  ┌─────────┐  探针成功  ┌──────┐
  │ PENDING │──────────▶│ OK   │── 探针再次失败 ──▶ MISSING / HASH_MISMATCH
  └────┬────┘           └──────┘
       │ 探针失败
       ├──────────────────────────▶ MISSING（对象不存在）
       └──────────────────────────▶ HASH_MISMATCH（对象在但内容变了）
```

**注意 `OK` 不是终态。** 对象存储的生命周期规则、跨区复制、手工清理都会让「昨天还在」的文件「今天不在」。探针是周期性的，所以 `OK` 的附件下个月仍可能变成 `MISSING`。这一点在页面上要体现（见 P07）。

#### 3.3.2 自创枚举的取值说明

**`touch_channel`（触达渠道）**

| 取值 | 中文名 | 说明 | 计入接通率分母 |
| :--- | :--- | :--- | :--- |
| `PHONE` | 电话 | 拨打电话（含手机、固话） | 是 |
| `WECHAT` | 微信 | 通过企业微信或患者微信联系 | 是 |
| `VISIT` | 上门/院内面访 | 护士当面完成随访 | 是 |
| `SMS` | 短信 | 仅发短信，不等回复（部分随访场景） | 是，但通常 `connected_flag = FALSE` |

> **`SMS` 渠道的 `connected_flag` 一律为 `FALSE`。** 短信发出去不等于联系上患者。这一点必须写进接口校验：`touch_channel = 'SMS'` 时不允许传 `connected_flag = true`，否则接通率会被短信虚高。

**`hangup_side`（挂断方）**

| 取值 | 中文名 | 说明 |
| :--- | :--- | :--- |
| `PATIENT` | 患者挂断 | 患者主动结束。**连续 3 次患者挂断应触发备忘提示** |
| `STAFF` | 护士挂断 | 护士主动结束（正常收尾或患者已无问题） |
| `SYSTEM` | 系统挂断 | 网络中断、通话超时、平台异常 |

**`offline_sync_status`（离线重放状态）** —— 使用共享规范 §13 的取值，一字不差。本子模块**不新增取值**。

**`conflict_reason`（冲突原因）**

| 取值 | 中文名 | 触发判据 | 人工可选项 |
| :--- | :--- | :--- | :--- |
| `ENTITY_GONE` | 目标已不存在 | M19 P-11 返回 `found = false` 且任务已被取消/删除 | 丢弃 |
| `VERSION_CHANGED` | 任务已变更 | 任务被改派给他人或改期，本地记录的 `task_version` 与最新不一致 | 丢弃 / 重试 |
| `STATE_INVALID` | 状态不允许 | 任务已被他人完成、或已过随访窗口 | 丢弃 / 手工修正 |

**`task_projection`（M20 投影状态）** —— 见 §3.2.1，**这不是 M19 的 `task_status`**。命名上刻意与上游区分，避免有人拿去当 M19 状态用。

### 3.4 关键计算模型

#### 3.4.1 M20-CALC-07：有效触达率（本子模块唯一自算的比率）

**公式：**

```
有效触达率 = 已有效触达的应访数 / 应访数 × 100%
```

**分母「应访数」的严格定义（这是本设计的核心）：**

应访数 = **计划内、且到今天已到期、且未被取消**的随访任务数。

三个限定条件缺一不可：

| 限定 | 含义 | 若不限定的后果 |
| :--- | :--- | :--- |
| **计划内** | 来自 M19 随访计划生成的任务，排除手工临时加的任务 | 把临时任务算进分母，分母随人为操作波动 |
| **已到期** | `plan_date <= 统计截止日` | 把未到期的算进去，**越临近月末看越低，月初永远是灾难** |
| **未被取消** | `task_status <> 'CANCELLED'` | 患者退号/转院后任务被取消，算进分母等于永久扣分 |

**分子「已有效触达」的定义：**

已有效触达 = 该任务至少有 1 条满足以下全部条件的触达记录：
- `connected_flag = TRUE`（接通了）
- `touch_channel <> 'SMS'`（短信不算触达）
- 对应的随访结果已由 M19 确认落库（`result_submitted_flag = TRUE`）

> **注意分子只要求「接通并提交结果」，不判断「随访结论是否正常」。** 患者说「眼睛不舒服」也是有效触达——**有效触达衡量的是「联系上了没有」，不是「联系上之后结果好不好」。** 若把「结果异常」排除出分子，会让「随访发现问题的科室」触达率更低，形成荒谬的激励。

**完整算例（2026 年 10 月，屈光术后随访，某科室）：**

| 项 | 数值 | 说明 |
| :--- | :--- | :--- |
| 10 月计划生成的任务总数 | 120 | 含 10/26~10/31 生成的、节点在 11 月才到期的 |
| 减去：节点到期日在 10/31 之后 | −20 | 这些任务护士**今天根本不该打**，进了分母就是冤枉 |
| 减去：患者退号/转院被取消 | −6 | 不是护士的责任 |
| **应访数（正确分母）** | **94** | 120 − 20 − 6 |
| 其中：接通且提交了结果 | 77 | 有效触达 |
| 其中：拨了但没接通 | 12 | 进了分母但不在分子 |
| 其中：从未拨过 | 5 | 进了分母但不在分子 |
| **有效触达率（正确）** | **77 / 94 = 81.914894%** | 页面显示 81.91% |

**三种错误分母的对比（这就是为什么要严格定义）：**

| 分母口径 | 分子 | 分母 | 结果 | 偏差 | 为什么错 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| ✅ **应访数（正确）** | 77 | 94 | **81.91%** | — | — |
| ❌ 全部计划任务数 | 77 | 120 | 64.17% | **低 17.75 个百分点** | 20 个未到期的任务被算成「护士没做」 |
| ❌ 已生成的随访任务数（含失败任务） | 77 | 114 | 67.54% | **低 14.37 个百分点** | 6 个已取消的算进去了 |
| ❌ 已拨过的任务数 | 77 | 89 | 86.52% | **高 4.61 个百分点** | 从没拨过的 5 个任务被排除出分母，**不干活的人指标更好看** |

> **「已拨过的任务数」这个错误分母最危险。** 它把「从没打过」排除在分母外，于是**越是不干活的员工，触达率越高**——没拨过就不进分母，拨了没通才进分母。这类指标一旦上了看板，一个季度内就会有人发现规律。**任何分母能被被考核者通过「少做事」改善的指标，都是坏指标。**

**分母为 0 的处理（硬规则）：**

```
if 应访数 == 0:
    有效触达率 = NULL        ← 数据库存 NULL
    rate_status = 'NO_DATA'  ← 页面显示「无数据」
```

- **绝不返回 0%。** 0% 的意思是「该做的全没做」，分母为 0 的意思是「这个月根本没有该做的事」，两者是完全不同的两件事。
- **绝不返回 100%。** 100% 的意思是「该做的全做了」。参照反例：`M07医生工作站/M07_医生工作站_07_医生工作量与效率_详细设计.md:3129-3132` 的实现里，分母为 0 时返回 `100.0`（满分），这个写法会让「一个患者都没有的医生」拿到满分的文书及时率。**本子模块不重复这个错误。**

**为什么本子模块只算这一个比率，不算随访到位率 / 失访率：**

见 §8.4 恒等式与闭合校验与 §2.2 的 O04。**一个指标的分母归谁管，就由谁算**——应访数由 M19 的随访计划定义，M20 只是执行方。若 M20 自己算「随访到位率」，必然与 M19 报出的数字不同，两个部门开会时各拿一份，谁都不认对方的。

> **本模型与 M22 的关系：** M22 指标中心里没有「有效触达率」这个编码（M22 的临床质量指标集中在疾病、手术、护理、院感四组）。若将来要纳入指标中心，应在 M22-01 登记编码并引用本节的公式，**而不是让本子模块自己变成第二个指标中心**。

#### 3.4.2 M20-CALC-08：本层待办合并（同患者同周期去重）

**问题：** M19 的随访计划可能为同一患者同一随访周期生成多条任务（例如「屈光术后 1 周」节点因规则调整重复生成，或是不同来源各生成一条）。若 M20 原样展示，护士会以为要打两通电话。

**合并键：**

```
cycle_key = plan_no || ':' || node_name
```

- `plan_no`：M19 随访计划号
- `node_name`：随访节点名（如「术后1周」）

合并规则：

| 场景 | 处理 |
| :--- | :--- |
| 同 `patient_id` + 同 `cycle_key`，多条都是 `PENDING_TOUCH` | 合并为 1 条展示，取其最早 `plan_date`，取最高 `priority` |
| 同 `patient_id` + 同 `cycle_key`，其中一条已 `DONE_ELSEWHERE` | 合并后整体标「已完成」，不再出现 |
| 同 `patient_id` + 不同 `cycle_key` | **不合并**。「术后1周」与「术后1月」是两次真实不同的随访 |
| 不同 `patient_id` | 不合并 |

**算例（2026-10-15 某随访专员的待办）：**

| 来源行 | 患者 | 计划号 | 节点 | 状态 | 合并后 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | P001 | FP2026100001 | 术后1周 | PENDING_TOUCH | ← 与 2、3 合并为 1 条 |
| 2 | P001 | FP2026100001 | 术后1周 | PENDING_TOUCH | （合并） |
| 3 | P001 | FP2026100001 | 术后1周 | PENDING_TOUCH | （合并） |
| 4 | P001 | FP2026100001 | 术后1月 | PENDING_TOUCH | 独立 1 条（不同节点） |
| 5 | P002 | FP2026100002 | 术后1周 | PENDING_TOUCH | 独立 1 条 |
| 6 | P002 | FP2026100002 | 术后1周 | DONE_ELSEWHERE | （与 5 合并后整体完成，不展示） |

合并前 6 条，合并后 2 条（P001 术后1周、P001 术后1月）。

> **为什么合并要放在本层而不是靠 M19 去重：** 因为**合并键是执行方的语义**。M19 生成任务时不知道谁会同时接两条；M20 拿到的是「分配给我个人的待办」，在这个视角下「同一个患者的同一个节点」才等价。**若靠 M19 去重，就要求 M19 知道每个护士的工作习惯**，边界反了。

#### 3.4.3 M20-CALC-09：随访进度（今日进度）

**用途：** 页面上「今天打了 15 通，还剩 6 个」这两个数字。

```
今日已触达任务数 = COUNT(DISTINCT task_id)
                   FROM m20_fol_attempt
                   WHERE staff_id = :me
                     AND touch_at >= 今日 00:00
                     AND touch_at <  明日 00:00
                     AND is_deleted = FALSE

今日待办剩余 = 合并后待办总数 − 今日已触达任务数（但不小于 0）
```

**为什么不直接用 `m20_fol_stats.attempt_count` 显示「今天打了 15 通」：** 因为 `attempt_count` 是**触达次数**，不是**任务数**。一个任务拨了 3 次才接通，`attempt_count` 是 3，但只完成了 1 个任务。页面上的「今天打了 15 通」若用次数会虚高，用任务数才与「还剩几个」对得上。**两个数字必须同口径**。

`m20_fol_stats` 只用于历史日期的统计页（P07），不用于今日实时进度。

#### 3.4.4 M20-CALC-10：待办优先级排序

护士打开待办列表时，排在前面的必须是最该先打的。排序是五段式（借鉴 M18-07 搜索排序的五段思路，但字段完全不同）：

```
ORDER BY
  p1_flag        DESC NULLS LAST,   -- 1) 紧急标记：EMERGENCY 优先
  overdue_days   DESC NULLS LAST,   -- 2) 逾期天数：越久越靠前
  plan_date      ASC,               -- 3) 计划日期：早的先打
  priority       ASC,               -- 4) 优先级数值（1 最高）
  task_id        ASC                -- 5) 兜底稳定键，保证分页不跳行
```

| 排序段 | 字段 | 来源 | 为什么放在这一位 |
| :--- | :--- | :--- | :--- |
| 1 | `p1_flag` | P-01 的 `priority` 映射 | 紧急（如术后并发症疑似的随访）必须置顶，不能因为逾期天数被压在后面 |
| 2 | `overdue_days` | `今天 − plan_date`（>0 才计入） | 逾期的优先级高于「今天该做但没逾期」 |
| 3 | `plan_date` | P-01 | 同为逾期时，早到期先打 |
| 4 | `priority` | P-01 | M19 定义的优先级数值 |
| 5 | `task_id` | P-01 | **必须有兜底键**，否则同分任务在两次分页请求间顺序可能变化，出现「翻页看到重复行 / 漏行」 |

> **第 5 段不是可有可无的。** PostgreSQL 在 `ORDER BY` 未完全确定顺序时不保证返回顺序稳定。护士翻到第 2 页时，若第 1 页的第 3 条跳到了第 2 页第 1 条，她会在两组里各打一次——**同一个患者被打了两次电话，第二次开场白是「我刚打过吧？」**。

#### 3.4.5 M20-CALC-11：索引/数据滞后阈值

M20-07 的待办数据来自 M19 P-01（本身有 30 秒缓存）。这个滞后是**可接受的设计**而不是缺陷，但必须告诉用户当前数据的时点。

| 滞后程度 | 判据 | `data_quality` | 页面表现 |
| :--- | :--- | :--- | :--- |
| 正常 | 上游全部成功，`as_of` 距今 ≤ 30 秒 | `REALTIME` | 无提示 |
| 轻微滞后 | 上游全部成功，`as_of` 距今 30~300 秒 | `CACHED` | 顶部黄条「数据为 X 分钟前，下拉刷新」 |
| 部分失败 | 至少一个上游失败 | `PARTIAL` | 顶部黄条「部分数据加载失败，以下内容可能不完整」 |
| 未知 | 上游未返回 `as_of` | `UNKNOWN` | 顶部黄条「数据时间未知」 |

**为什么 30 秒就是 `CACHED` 而不是等更久：** M19 的 P-01 自带 30 秒缓存，所以**正常情况下的 `as_of` 本来就可能落后 30 秒**。若阈值设成 60 秒，正常的缓存命中会被标成 `REALTIME`，护士以为看到的是实时的。**阈值必须与实际缓存 TTL 对齐，否则提示会说谎。**

### 3.5 单据模型

#### 3.5.1 编号规则

| 单据 | 前缀 | 格式 | 示例 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| 随访媒体编号 | `FM` | `FM` + `yyyyMMdd` + 6 位流水 | `FM20261107000123` | 本子模块自有 |
| 统计批次号 | `FS` | `FS` + `yyyyMMdd` + 4 位流水 | `FS202611070001` | 日统计任务产出 |
| 话术编码 | — | `[A-Z][A-Z0-9_]{2,31}` | `POSTOP_LASIK_D1` | 业务自定义编码，非流水单号 |
| 知识卡编码 | — | `[A-Z][A-Z0-9_]{2,31}` | `CARD_SWIM_AFTER` | 业务自定义编码 |

**为什么自定义了两个单号却不在共享规范 §3.3 单号表里：**

共享规范 §3.3 登记的是跨子模块有共用语义的单号（审批单号 `SP`、消息流水 `MS`、待办编号 `TD`、离线队列号 `OF`、推送批次号 `PS`）。本子模块的 `FM`（媒体编号）与 `FS`（统计批次号）**只在 M20-07 内部流转，不与其他子模块交换**，因此未列入 §3.3。此处按共享规范要求写死：

- `FM` 走 Redis `INCR`，key `m20:fol:code:FM:{yyyyMMdd}`，TTL 到次日 00:05。
- `FS` 走 Redis `INCR`，key `m20:fol:code:FS:{yyyyMMdd}`，TTL 到次日 00:05。
- **禁用数据库 SEQUENCE 拼日期**（共享规范 §3.5）：序列跨零点不重置，会产生「日期是新的、流水是接着昨天」的乱序号。

3. **本子模块不建任何存放临床信息的表。** 8 张表中没有一张有「症状」「视力」「诊断」「用药」「随访结论」之类的列——这是 §2.3.1 边界在数据层的体现。

**页面定位：** 一次随访的全流程：看患者信息 → 看备忘 → 照着话术打电话 → 记触达 → 填结果 → 提交。**这是本子模块最核心的页面。**

**数据来源：** API-06（执行页详情）、API-07（触达记录）、API-08（提交结果）、API-09（话术）、API-10（知识卡）、API-11（备忘）、API-12（附件）、API-13（离线保存）、API-14（执行状态回查）

```
┌────────────────────────────────────────────┐
│ ← 随访执行          王**  屈光术后1周      │
├────────────────────────────────────────────┤
```

**四段式设计的理由：** 触达记录与随访结果是**两个不同归属**的数据（§2.3.1），必须视觉上分段清楚。护士填的时候能看出「①是记我自己干了什么」「③是写进病历的」。若混在一个表单里，护士会把临床信息写进备注框。

**字段说明：**

| 分区 | 字段 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| ① 触达 | `touch_channel` | ✅ | `PHONE` / `WECHAT` / `VISIT` / `SMS` |
| ① 触达 | `connected_flag` | ✅ | 是否接通；`SMS` 渠道强制 `false` |
| ① 触达 | `call_duration_sec` | 接通时必填 | 0~86400 |
| ① 触达 | `hangup_side` | 接通时必填 | `PATIENT` / `STAFF` / `SYSTEM` |
| ② 话术 | `script_id` | 否 | 本次念的是哪一版 |
| ③ 结果 | `result_payload` | 接通时必填 | **结构由 M19 定义，本页只做表单渲染与透传** |
| ④ 附件 | `media[]` | 否 | 单文件 ≤ 20MB，MIME 白名单 |

**交互：**

1. 页面进入时并行调 API-06 / API-09 / API-10 / API-11 / API-14。
2. 填「接通 = 否」时，「通话时长」「挂断方」自动禁用，③ 随访结果整段收起（没接通就没有结果可填）。
3. 点「提交随访结果」→ 先按顺序执行：
   1. 调 API-07 写触达记录（拿到 `attempt_id`）
   2. 调 API-08 提交结果（转发 M19）
   3. 成功后调 API-14 回查确认，再跳转下一个待办
4. 网络断开时「提交随访结果」变为「离线保存」，走 API-13。
5. 点「暂存」→ 本地草稿（**不上传服务端**），24 小时有效。

**校验规则：**

| 编号 | 规则 | 提示 |
| :--- | :--- | :--- |
| V-P03-01 | `touch_channel = 'SMS'` 时 `connected_flag` 必须为 `false` | 前端禁用「接通」开关 |
| V-P03-02 | `connected_flag = false` 时不得提交随访结果 | 「未接通不应提交随访结果；如需记录联系失败请直接保存」 |
| V-P03-03 | `connected_flag = true` 时 `call_duration_sec` 与 `hangup_side` 必填 | 字段级红字 |
| V-P03-04 | `call_duration_sec` > 0 但 `connected_flag = false` | 阻止提交（自查见 §8.3） |
| V-P03-05 | 附件单文件 > 20MB | 「文件过大，请压缩后上传（上限 20MB）」 |
| V-P03-06 | 附件 MIME 不在白名单 | 「不支持该文件格式」 |
| V-P03-07 | 提交前未填随访结果的必填项 | 逐项标红，**不允许跳过** |

**移动端特殊考虑：**

| V-P07-04 | 数据 `as_of` 早于昨天 | 显示「数据截止 X 日 01:10」，明确是 T+1 快照 |
| V-P07-05 | `data_quality != REALTIME` | 顶部黄条 |

- 数字卡片 2×3 网格在竖屏、3×2 在横屏。
- 表格（按员工）在手机上改为卡片列表，避免横向滚动。

### 6.2 公共约定

#### 6.2.1 统一响应与质量标记

所有接口返回 Envelope `{code, message, data, trace_id}`，`code = 0` 表示成功。**每个 `data` 对象必须携带四个质量标记**，即使不降级也必须有：

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `degraded` | BOOLEAN | 是否有任一上游或缓存来源不可用 |
| `degraded_sources` | ARRAY | 降级来源清单，元素 `{source, reason}`；不降级时为 `[]` |
| `data_quality` | VARCHAR(16) | `REALTIME` / `CACHED` / `PARTIAL` / `UNKNOWN` |
| `as_of` | TIMESTAMP | **数据口径截止时刻**，取所有成功来源 `as_of` 中最早的一个 |

集合类额外带 `record_count`。

#### 6.2.2 `data_quality` 的重算责任

共享规范 §8A.2.1 已裁决：**M20 不得透传上游 `data_quality`，必须自己重算**。上游值只作为 `degraded_sources[].reason` 的证据出现。判定顺序（M20-CALC-11）：

1. 任一必需上游失败 → `PARTIAL`（若完全拿不到数据则 `UNKNOWN`）
2. 数据来自缓存且缓存年龄 > 30 秒 → `CACHED`
3. 全部来源成功且 `as_of` 可确定 → `REALTIME`
4. 任一来源未返回 `as_of` → `UNKNOWN`

#### 6.2.3 分页

`page_no`（默认 1）、`page_size`（默认 20，上限 100）、返回 `items` / `page_no` / `page_size` / `total` / `has_more` / `as_of`。**`total` 允许为 `null`**（M19 P-01 不保证返回精确总数时，不得为凑 `total` 扫全表）。

#### 6.2.4 幂等

所有产生业务后果的写接口（API-06 / 08 / 09 / 12 / 17 / 20 / 23 / 25 / 29）必须接受 `X-Idempotency-Key` 请求头。键 `(biz_type, idempotency_key)` 存 `m20_base_idempotency`（M20-01 首建），TTL 24 小时。**命中已存在键时返回首次结果原样回放，不重复执行。**

#### 6.2.5 上游错误码不得做格式校验

M19 契约（P-01 / P-11）的错误码在 `"1901xxx"` 段。**M20 只判 `code == 0` 与非 0，不得对其位数或前缀做任何格式校验**（共享规范 §17 第 4 条）。同理，M19 返回的 `task_no` / `exec_no` 原样透传与落库，不校验位数。

#### 6.2.6 禁止形态

| 禁止形态 | 为什么禁止 |
| :--- | :--- |
| 上游失败时返回 `200 + code=0 + items=[] + degraded=false` | **空数组表达「今日无待办」会让护士不去打电话，这条随访线索就断了**。必须 `degraded=true` + 黄条 |
| 无权限时返回 `200 + code=0 + items=[]` | 无权限一律 `403` + 非 0 code，不得伪装成空 |
| 用 HTTP 200 + 非 0 code 表达系统故障 | 系统故障必须 5xx |
| 降级时返回比正常态更多的数据 | **降级可以少给，不能多给**；权限过滤失败必须 403/500，绝不退化为「不过滤」 |

  9. 返回。

| "2007041" | 400 | 文件大小超出上限 | `file_size_bytes` 超过 20MB | 压缩后重传 |
| "2007042" | 409 | 对象键已被登记 | `(bucket_name, object_key)` 撞唯一键 | 复用已有 `media_id` |

- **业务逻辑**：
  1. 校验权限与数据范围。
  2. 校验 `object_key` 不是完整 URL（`!~ '^[a-zA-Z][a-zA-Z0-9+.-]*://'`）、`content_hash` 匹配 `^[0-9a-f]{64}$`、大小 ≤ 20MB、MIME 在白名单内。
  3. 生成 `media_no`：`FM` + yyyyMMdd + 6 位流水，走 Redis `INCR` `m20:fol:code:FM:{yyyyMMdd}`，TTL 到次日 00:05。
  4. 插入 `probe_status = 'PENDING'`；**对象存储的上传由客户端直传完成，本接口只登记引用，附件字节永不经过数据库**。
  5. 撞唯一键 → `"2007042"`，回传已有 `media_id`（客户端可复用，不必重传）。
  6. 幂等键 `biz_type = 'FOL_MEDIA'`。
  7. 返回。

- **调用上游**：无（对象存储直传不经本接口）。
- **幂等**：必须带 `X-Idempotency-Key`；`(bucket_name, object_key)` 唯一键天然收敛。

- **错误码**：

| 错误码 | HTTP | 含义 | 触发场景 | 处置建议 |
| :--- | :--- | :--- | :--- | :--- |
| "2007001" | 403 | 无统计重算权限 | 缺 `m20:fol:stats:recalc` | 联系管理员授予权限 |
| "2007047" | 400 | 只能重算近 3 天内的统计 | `stat_date` 早于 3 天前 | 历史数据请走数据修正流程 |

  1. 校验权限。
  2. 校验 `stat_date` 在近 `fol.stats.recalc_days`（默认 3）天内。
  3. 取分布式锁 `SET m20:fol:stats:lock:{stat_date} <token> NX EX 300`；抢不到 → `"2007048"` + 409。

  7. 释放锁；幂等键 `biz_type = 'FOL_STATS'`。
  8. 返回。

- **调用上游**：无。
- **幂等**：必须带 `X-Idempotency-Key`；重算本身幂等（同一 `stat_date` 重复重算结果一致，只是 `calc_batch_no` 更新）。

```python
from __future__ import annotations

from dataclasses import dataclass, field
from datetime import date, datetime, timedelta
from typing import Any, Optional

from sqlalchemy import text


class FolError(Exception):
    """带错误码的业务异常。"""

    def __init__(self, code: str, message: str, http_status: int = 400):
        super().__init__(message)
        self.code = code
        self.message = message
        self.http_status = http_status


@dataclass(frozen=True)
class Quality:
    """四个质量标记，任何响应都必须构造它，不允许用默认值糊过去。"""

    degraded: bool
    degraded_sources: list[dict[str, str]]
    data_quality: str
    as_of: datetime

    def to_dict(self) -> dict[str, Any]:
        return {
            "degraded": self.degraded,
            "degraded_sources": self.degraded_sources,
            "data_quality": self.data_quality,
            "as_of": self.as_of.isoformat(),
        }


class FolService:
    def __init__(self, repo=None, m19_client=None, redis=None, now=None):
        self.repo = repo
        self.m19 = m19_client
        self.redis = redis
        self._now = now or (lambda: datetime.now())

    # ---- 质量标记重算（M20-CALC-11）------------------------------------
    def _build_quality(self, sources: list[dict[str, Any]], cache_age_sec: int = 0) -> Quality:
        """sources: [{'name':..., 'ok':bool, 'as_of':datetime|None}]"""
        failed = [s for s in sources if not s["ok"]]
        as_of_list = [s["as_of"] for s in sources if s["ok"] and s["as_of"]]
        if not as_of_list:
            return Quality(True, [{"source": s["name"], "reason": "NO_AS_OF"} for s in failed] or [],
                           "UNKNOWN", self._now())
        # as_of 取所有成功来源中最小的那个：数据口径截止时刻，不是响应生成时刻
        as_of = min(as_of_list)
        if failed:
            return Quality(True, [{"source": s["name"], "reason": "UPSTREAM_FAIL"} for s in failed],
                           "PARTIAL", as_of)
        if cache_age_sec > 30:
            return Quality(False, [], "CACHED", as_of)
        return Quality(False, [], "REALTIME", as_of)

    # ---- 待办合并（M20-CALC-08）----------------------------------------
    @staticmethod
    def _cycle_key(item: dict[str, Any]) -> str:
        return "%s:%s" % (item.get("plan_no") or "", item.get("node_name") or "")

    def _merge_tasks(self, items: list[dict[str, Any]]) -> list[dict[str, Any]]:
        """同患者同 cycle_key 合并，保留最早到期的一条，其余计入 merged_count。"""
        if not self.repo.config_bool("fol.cycle.merge_enabled", True):
            return items
        buckets: dict[tuple[Any, str], list[dict[str, Any]]] = {}
        for it in items:
            key = (it.get("patient_id"), self._cycle_key(it))
            buckets.setdefault(key, []).append(it)
        merged: list[dict[str, Any]] = []
        for group in buckets.values():
            group.sort(key=lambda x: (x.get("plan_date") or date.max, x.get("task_id") or 0))
            head = dict(group[0])
            head["merged_count"] = len(group) - 1
            merged.append(head)
        return merged

    # ---- 五段式排序（M20-CALC-10）--------------------------------------
    _PRIORITY_ORDER = {"P1": 0, "P2": 1, "P3": 2}

    def _sort_tasks(self, items: list[dict[str, Any]], sort: str) -> list[dict[str, Any]]:
        def due_key(x):
            return (x.get("plan_date") or date.max, x.get("task_id") or 0)

        def overdue_key(x):
            return (-(x.get("overdue_days") or 0), x.get("plan_date") or date.max, x.get("task_id") or 0)

        def prio_key(x):
            return (self._PRIORITY_ORDER.get(x.get("priority"), 9),
                    x.get("plan_date") or date.max, x.get("task_id") or 0)

        chooser = {"DUE_ASC": due_key, "OVERDUE_DESC": overdue_key, "PRIORITY_DESC": prio_key}
        # 第 5 段 task_id 一直是兜底稳定键：没有它翻页会重复或漏行
        return sorted(items, key=chooser.get(sort, due_key))

    # ---- 工作台 --------------------------------------------------------
    async def get_workbench(self, client_type: str, network_state: str, dept_id: Optional[int]):
        if client_type not in {"IOS", "ANDROID", "MINI_PROGRAM", "H5", "PAD"}:
            raise FolError("2007022", "终端类型取值非法", 400)
        if network_state not in {"WIFI", "CELLULAR", "WEAK", "OFFLINE"}:
            raise FolError("2007022", "网络状态取值非法", 400)
        today = self._now().date()
        sources = []
        try:
            pending = await self.m19.pending_tasks(
                assignee_id=self.repo.current_staff_id(),
                dept_id=dept_id,
                date_from=today,
                date_to=today,
                limit=100,
            )
            sources.append({"name": "M19_PENDING_TASKS", "ok": True,
                            "as_of": pending.get("generated_at")})
            items = pending.get("items", [])
        except Exception:
            # 降级：不返回空列表冒充「今日无待办」，改为 PARTIAL + 缓存内容
            cached = self.repo.cached_workbench()
            sources.append({"name": "M19_PENDING_TASKS", "ok": False, "as_of": None})
            items = (cached or {}).get("queue", [])
        merged = self._merge_tasks(items)
        ordered = self._sort_tasks(merged, "PRIORITY_DESC")
        progress = self.repo.today_progress(self.repo.current_staff_id(), today)
        quality = self._build_quality(sources)
        return {
            "staff_id": self.repo.current_staff_id(),
            "today": progress,
            "queue": ordered[:20],
            "record_count": len(ordered[:20]),
            "record_total": len(ordered),
            **quality.to_dict(),
        }

    # ---- 触达记录 ------------------------------------------------------
    async def create_attempt(self, payload, idempotency_key: str):
        cached = self.repo.idempotent_hit("FOL_ATTEMPT", idempotency_key)
        if cached:
            return cached
        item = payload if isinstance(payload, dict) else payload.model_dump()
        if item.get("touch_channel") == "SMS" and item.get("connected_flag"):
            raise FolError("2007009", "短信渠道不得标记为已接通", 400)
        if not item.get("connected_flag") and (
            item.get("call_duration_sec") is not None or item.get("hangup_side")
        ):
            raise FolError("2007010", "未接通不得填写通话时长或挂断方", 400)
        try:
            exec_status = await self.m19.exec_status(item["task_id"])
            upstream_ok = True
            as_of = exec_status.get("as_of")
        except Exception:
            exec_status, upstream_ok, as_of = {"found": False}, False, None
        if exec_status.get("found") and exec_status.get("exec_status") == "COMPLETED":
            raise FolError("2007011", "该随访任务已在别处完成", 409)
        seq = self.repo.next_attempt_seq(item["task_id"])
        attempt_id = self.repo.insert_attempt(item, seq)
        quality = self._build_quality(
            [{"name": "M19_EXEC_STATUS", "ok": upstream_ok, "as_of": as_of}]
        )
        result = {
            "attempt_id": attempt_id,
            "task_id": item["task_id"],
            "attempt_seq": seq,
            "offline_replay": False,
            **quality.to_dict(),
        }
        self.repo.store_idempotent("FOL_ATTEMPT", idempotency_key, result)
        return result

    # ---- 提交随访结果（§2.3.1 边界落地）--------------------------------
    async def submit_result(self, payload: dict, idempotency_key: str):
        cached = self.repo.idempotent_hit("FOL_RESULT", idempotency_key)
        if cached:
            return cached
        summary = (payload.get("result_summary") or "").strip()
        if len(summary) < 4:
            # 没有随访结果就不允许结束任务：临床信息必须写进 M19
            raise FolError("2007013", "随访结果正文不得为空", 400)
        for media_id in payload.get("attachments") or []:
            if self.repo.media_task_id(media_id) != payload["task_id"]:
                raise FolError("2007016", "附件引用不属于本次任务", 400)
        try:
            accepted = await self.m19.submit_exec_record(payload)
        except Exception:
            # 回写失败：进离线队列，绝不本地标记成功
            self.repo.enqueue_offline("FOLLOWUP_RESULT", payload,
                                      client_recorded_at=self._now())
            raise FolError("2007015", "随访结果回写上游失败，已本地保存待同步", 502)
        if not accepted.get("accepted", False):
            reason = accepted.get("reject_reason", "UNKNOWN")
            if reason == "ALREADY_COMPLETED":
                raise FolError("2007011", "该随访任务已在别处完成", 409)
            if reason == "CANCELLED":
                raise FolError("2007014", "该随访任务已被取消", 409)
            raise FolError("2007015", "随访结果被上游拒绝", 502)
        result = {
            "task_id": payload["task_id"],
            "exec_no": accepted.get("exec_no"),
            "exec_status": accepted.get("exec_status", "COMPLETED"),
            "writeback_status": "SUCCESS",
            # 本地投影只表示「已由他人/上游完成」，绝不表示本模块自己完成
            "local_task_state": "DONE_ELSEWHERE",
            "degraded": False,
            "degraded_sources": [],
            "data_quality": "REALTIME",
            "as_of": accepted.get("as_of") or self._now().isoformat(),
        }
        self.repo.store_idempotent("FOL_RESULT", idempotency_key, result)
        return result

    # ---- 统计 ----------------------------------------------------------
    async def get_daily_stats(self, date_from, date_to, dept_id, staff_id, granularity):
        if date_to < date_from:
            raise FolError("2007045", "日期区间非法", 400)
        if (date_to - date_from).days > 92:
            raise FolError("2007044", "查询跨度超出允许范围", 400)
        rows = self.repo.daily_stats(date_from, date_to, dept_id, staff_id)
        for r in rows:
            if not r["attempt_count"]:
                # 分母为 0 一律 NULL + NO_DATA，绝不 0 也绝不 100
                r["connected_rate"] = None
                r["rate_status"] = "NO_DATA"
        calc_at = self.repo.last_calc_at(date_from, date_to)
        return {
            "items": rows,
            "record_count": len(rows),
            "calc_at": calc_at.isoformat() if calc_at else None,
            "degraded": False,
            "degraded_sources": [],
            "data_quality": "CACHED",
            # as_of 是快照的数据截止时刻，绝不是查询时刻
            "as_of": calc_at.isoformat() if calc_at else None,
        }

    # ---- 单号 ----------------------------------------------------------
    def _next_media_no(self) -> str:
        day = self._now().strftime("%Y%m%d")
        key = "m20:fol:code:FM:%s" % day
        seq = self.redis.incr(key)
        if seq == 1:
            # TTL 到次日 00:05，不是固定 24 小时
            self.redis.expireat(key, self._next_midnight_plus_5min())
        return "FM%s%06d" % (day, seq)
```

## 7. 缓存与异步任务设计

### 7.1 Redis 缓存

全部键以 `m20:fol:` 为前缀，**业务数据 TTL 一律不超过 60 秒**（共享规范 §14 硬规则），例外只有单号计数器（它到次日 00:05 失效，与 TTL 上限的语义不同：计数器不是缓存而是流水号）。

| 键 | 类型 | TTL | 值内容 | 失效策略 | 说明 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `m20:fol:workbench:{staff_id}` | String(JSON) | 30s | 首屏聚合结果 + `as_of` | 到期自然失效；提交触达后主动删 | 命中时 `data_quality = CACHED`；主动删是为了护士提交后立刻看到进度变化 |
| `m20:fol:tasklist:{staff_id}:{hash}` | String(JSON) | 30s | 待办列表首页 + `as_of` | 到期自然失效 | `hash` 由筛选条件规范化后计算；**只缓存第一页**，翻页直查上游 |
| `m20:fol:script:{script_code}` | String(JSON) | 60s | 生效话术版本 | 话术发布/归档时删除 | 话术是静态配置，可接受 60 秒延迟 |
| `m20:fol:cards:{scene_code}` | String(JSON) | 60s | 该场景生效知识卡 | 知识卡发布时删除 | 同上 |
| `m20:fol:config:{group}` | String(JSON) | 300s | 配置项清单 | 配置变更时删除 | 配置项不是业务数据，不受 60 秒约束 |
| `m20:fol:code:FM:{yyyyMMdd}` | String(INT) | 到次日 00:05 | 媒体单号流水 | 自然过期 | 走 `INCR`，禁用数据库序列拼日期 |
| `m20:fol:code:FS:{yyyyMMdd}` | String(INT) | 到次日 00:05 | 话术/知识卡版本流水 | 自然过期 | 同上 |
| `m20:fol:stats:lock:{stat_date}` | String | 300s | 重算任务锁 token | 释放或过期 | `SET NX EX`；锁过期不等于业务可重入，重算本身幂等 |
| `m20:fol:media:sign:{media_id}:{staff_id}` | String | 60s | 预签名地址 | 到期自然失效 | **不缓存到客户端以外的位置**；签名地址带时效，落库即泄露 |

**三条硬规矩：**

1. **计数器 TTL 到次日 00:05，不是固定 24 小时。** 固定 24 小时会让同一天里跨零点的两个进程拿到不同基数的流水，出现重号（跨零点乱序是 Redis 计数方案最典型的失效模式）。
2. **只缓存第一页。** 缓存全部翻页结果等于在服务端存了一份业务数据副本，命中率换来的是一致性风险。
3. **撤权立即生效。** 缓存键里带 `staff_id` 但不带权限版本；权限变更时由 M02 广播事件，本模块收到后按 `staff_id` 前缀批量删除 `m20:fol:workbench:*` 与 `m20:fol:tasklist:*`。

### 7.2 Celery 异步任务

| 任务名 | 队列 | 触发 | 频率 | 超时 | 说明 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `m20.fol.media.probe_daily` | `m20_batch` | APScheduler | 每日 03:00 | 1800s | 抽 `fol.media.probe_daily_sample`（默认 200）个 `probe_status = 'OK'` 的附件真 GET 校验 |
| `m20.fol.media.probe_full` | `m20_batch` | APScheduler | 每周日 02:00 | 7200s | 全量巡检，覆盖过去 7 天新增与全部未 `OK` 的行 |
| `m20.fol.stats.daily` | `m20_batch` | APScheduler | 每日 01:10 | 1200s | 汇总前一日 `m20_fol_attempt` 到 `m20_fol_stats` |
| `m20.fol.offline.replay` | `m20_replay` | 客户端上行 / 定时重试 | 每 5 分钟 | 600s | **只驱动 M20-01 的消息总线，本模块不自己实现重放循环**；本任务只负责把 `FOLLOWUP_ATTEMPT` / `FOLLOWUP_RESULT` 两类载荷的冲突判定结果写回扩展表 |
| `m20.fol.media.orphan_scan` | `m20_batch` | APScheduler | 每周一 04:00 | 3600s | 扫描对象存储里存在但 `m20_fol_media` 无引用的对象，产出清单供人工确认后清理 |

**为什么探针任务必须是真 GET 而不是查元数据：** `content_hash` 只能证明「我们记录的哈希与当时算出来的一致」，它证明不了对象存储里那个文件还在。生命周期规则自动删除、手工清理桶、跨区域复制失败、迁移漏目录——这四种失败模式元数据接口都看不出来，只有真读一次才知道。**探针本身不做自动修复**：自动重新上传等于掩盖了对象存储的配置问题。

**为什么离线重放不自己写循环：** M20-01 已经持有 `m20_base_offline_queue` 与重放调度。本模块若再写一套重放，两个循环会并发消费同一条队列项，产生重复提交。本模块只提供「判定这一条该怎么处理」的纯函数（`M20-CALC-06`），调度权归 M20-01。

### 7.3 APScheduler 定时任务

| 任务 | Cron | 说明 |
| :--- | :--- | :--- |
| `fol.stats_daily` | `10 1 * * *` | 触发 `m20.fol.stats.daily`；**01:10 不是 00:00**，因为 M19 侧次日 00:00 之后才完成前一日任务状态收尾，太早跑会漏掉跨零点提交的结果 |
| `fol.media_probe_daily` | `0 3 * * *` | 触发每日抽检；与 M18-07 的索引重建错开 30 分钟，避免同时占满 IO |
| `fol.media_probe_full` | `0 2 * * 0` | 每周日全量巡检 |
| `fol.orphan_scan` | `0 4 * * 1` | 每周一孤儿对象扫描 |
| `fol.stats_recalc_retry` | `30 1 * * *` | 补救：01:30 检查前一日快照是否齐全，缺失则补跑一次 |

**为什么统计在 01:10 而不是 00:05：** M19 的任务状态回写有一个跨零点的收尾窗口（护士 23:55 提交、上游 00:00 后落库）。00:05 跑统计会把这些记录算到「未完成」，第二天早上科室看板上就会有一批「昨天明明打了显示没打」的记录。01:10 留了一小时缓冲。

### 8.4 编码规范

1. **所有 ORM 查询必须显式带 `is_deleted = FALSE`**（对有该列的表）。数据结构附录 C.2 已说明：PostgreSQL 的部分索引只在查询条件逻辑蕴含索引 `WHERE` 子句时才会被使用，漏写条件会让部分索引失效变成全表扫描。
2. **不得在 `touch_at` 等时间列上套 `date()` 函数**做范围过滤，要用半开区间 `touch_at >= :d_from AND touch_at < :d_to + 1`。
3. **不得对上游单号调 `len()` / 正则 / 切片**。所有来自 M19 的单号按不透明字符串处理。
4. **不得使用 `from datetime import datetime as dt` 之类的别名绕开任何检查**。遇到校验器误报，先上报再改，不改文档迁就。
5. **不得在单元测试里构造「降级时返回空列表」的断言**，那等于把错误形态固化成期望值。
6. **`as_of` 必须来自上游返回值或快照写入时刻，绝不允许用 `now()` 兜底填充。** 这是本模块最容易犯且最难发现的错误：一旦 `as_of` 永远是新鲜的，这个字段的全部意义就没了。

### 8.5 状态流转规则

| 从 | 到 | 触发 | 校验 |
| :--- | :--- | :--- | :--- |
| `QUEUED` | `SYNCING` | 队列调度取走 | 同一队列项不得被两个 worker 同时取（M20-01 的锁） |
| `SYNCING` | `SYNCED` | 上游接受 | 幂等键第一次出现 |
| `SYNCING` | `CONFLICT` | 五步判定命中②③④ | 必须带 `conflict_reason` |
| `SYNCING` | `FAILED` | 网络失败且重试次数超限 | |
| `SYNCING` | `QUEUED` | 超时回退 | **不得停在 `SYNCING`** |
| `CONFLICT` | `QUEUED` | 人工选 `RETRY` | 清空 `conflict_reason` |
| `CONFLICT` | `ABANDONED` | 人工选 `DISCARD` / `MANUAL_APPLY` | 必须带 `resolved_by` / `resolved_at` / 理由 |
| `DRAFT` | `ACTIVE` | 发布 | 先归档旧 ACTIVE，顺序不可颠倒 |
| `ACTIVE` | `ARCHIVED` | 归档或新版本发布 | 回填 `effective_to` |

### 9.2 数据范围控制

1. **数据范围由 M02 权限上下文提供**（`U-05 GET /internal/v1/auth/{staff_id}/permission-context`），本模块不自建授权表。
2. **范围过滤必须在 SQL 层参数化**，不采用「查出来再在应用层过滤」的做法——应用层过滤的失败模式是「静默地少过滤了一点，结果全出」；SQL 层过滤的失败模式是「抛异常 → 500 → 什么都没出去」。宁可 500，不可多出。

### 9.4 防篡改

**本子模块不产生病历正文**，病历正文的防篡改见 M18-02 / M18-06。本子模块自有数据的三类防护：

1. **触达记录与统计快照可修正但不可静默改写**：`m20_fol_attempt` 允许在 24 小时内由本人更正（补录笔误），更正必须写审计日志；超期更正走数据修正流程。统计快照重算会留下新的 `calc_batch_no`。
2. **附件引用不可删除**：`m20_fol_media` 没有删除接口，也没有 `is_deleted` 列。文件可能在对象存储侧丢失（由探针标 `MISSING`），但**引用记录永不消失**——否则「这个文件曾经存在过」这件事就没有证据了。
3. **离线冲突处置不可撤销**：一旦置 `ABANDONED`，是「有人对此做过决定」的事实，不提供撤销接口；若判断错了，只能由管理员走数据修正并留痕。

## 10. 集成与契约

### 10.1 本子模块对外提供的接口

**M20-07 不对外提供任何内部契约接口。** 共享规范 §8A 登记的全部内部契约 P-01 至 P-06 分别归属 M20-04、M20-08、M20-01，**本子模块一个都没有**。因此本文档中不存在 `/internal/v1/m20/...` 形式的路径定义，也没有 P-xx 编号的契约表。

本子模块与其他子模块的全部协作都是**作为调用方**：待办取 M19、待办写入 M20-08、身份与权限取 M02。若将来需要向其他模块暴露随访过程数据，须先在共享规范 §8A 登记编号，不得自行占号。

### 10.3 本子模块发布的事件

| 事件名 | 触发时机 | 载荷字段 | 订阅方 |
| :--- | :--- | :--- | :--- |
| `m20.fol.attempt.recorded` | 一次触达记录落库成功后 | `attempt_id` / `task_id` / `patient_id` / `touch_channel` / `connected_flag` / `touch_at` / `trace_id` | M20-08（刷新角标） |
| `m20.fol.offline.conflict` | 重放判定为冲突时 | `item_id` / `task_id` / `patient_id` / `conflict_reason` / `detected_at` | M20-08（推送提醒） |
| `m20.fol.media.missing` | 探针判定文件缺失时 | `media_id` / `patient_id` / `probe_status` / `detected_at` | 运维告警 |

**载荷红线**：三条事件的载荷都**不得包含患者姓名、证件号、联系电话、住址等任何可识别信息**，只允许标识符、状态、时刻。原因：事件总线是多订阅方广播通道，一旦载荷里有可识别信息，任何一个订阅方都能还原「谁在什么时候联系了谁」的横向信息。

### 10.4 本子模块订阅的事件

| 事件名 | 来源 | 本模块处理 | 失败处理 |
| :--- | :--- | :--- | :--- |
| `mpi.patient.merged`（M03-02 `M03患者服务与EMPI/M03_患者服务与EMPI_02_患者主索引_详细设计.md:1192`） | M03 | **只更新 `m20_fol_attempt.patient_id` / `m20_fol_memo.patient_id` / `m20_fol_media.patient_id` 到主患者**（索引类归属列），历史业务表不动 | 失败不阻塞总线，落补偿表重试 |
| `m19.followup.task.cancelled` | M19 | 把本地投影置 `DONE_ELSEWHERE` 之外的取消态，待办中心同步删除 | 同上 |
| `m02.staff.permission.changed` | M02 | 按 `staff_id` 批量删 `m20:fol:workbench:*` / `m20:fol:tasklist:*` 缓存 | 同上 |

**订阅原则：事件只作「该重建了」的信号，不作数据来源。** 本模块收到 `mpi.patient.merged` 后不会用事件载荷去重建任何业务行，只把已有行的归属列改到主患者。`m20_fol_attempt` 记录的是「当时给谁打的电话」，患者合并后这个事实不变，只是归属改到主档——**索引表记「现在属于谁」，业务表记「当时是谁」**，两处不一致是有意的。

## 11. 异常处理与日志

### 11.1 异常分类

| 类别 | HTTP | 错误码 | 处理 |
| :--- | :--- | :--- | :--- |
| 参数校验失败 | 400 | `"2007xxx"` 中的 400 类 | 返回可读提示，前端就地标红 |
| 未登录 / 令牌失效 | 401 | `"209001"` | 跳登录 |
| 无权限 / 超数据范围 | 403 | `"2007001"` / `"2007036"` | **不区分「不存在」与「无权」，统一 403 防枚举** |
| 资源不存在 | 404 | `"2007004"` 等 | 仅对确认存在权限的资源才返回 404 |
| 状态冲突 | 409 | `"2007011"` 等 | 返回最新状态供前端刷新 |
| 上游失败 | 502 | `"2007015"` | 进离线队列或显示黄条 |
| 上游 / 自身不可用 | 500 / 503 | `"2007003"` / `"2007043"` | 黄条 + 重试 |

### 11.2 降级策略

| 场景 | 降级形态 | `data_quality` | 页面表现 |
| :--- | :--- | :--- | :--- |
| M19 待办接口超时，有上一次缓存 | 返回缓存内容 | `PARTIAL` | 顶部黄条 +「数据显示截至 HH:mm」，**不显示空列表** |
| M19 待办接口超时，无缓存 | `degraded: true` + `items: []` + 明确文案 | `PARTIAL` | 红条「待办加载失败，请稍后重试」+ 重试按钮，**绝不显示「今日无待办」** |
| 数据来自缓存且年龄 > 30 秒 | 正常返回缓存 | `CACHED` | 顶部黄条「数据可能有延迟」 |
| 上游未返回 `as_of` | 正常返回，`as_of` 置空 | `UNKNOWN` | 显示「数据时点未知」 |
| 对象存储探针不可达 | 返回上次巡检快照 | `UNKNOWN` | 显示快照时间，**不把不可达显示成 0 异常** |
| 权限上下文不可用 | **不降级** | — | 500，绝不退化为不过滤 |

**降级底线：可以少给，不能多给。** 权限过滤失败必须 500 或 403，绝不允许以「过滤条件构造不出来，先不过滤」的方式返回 200。

### 11.3 日志设计

| 日志类型 | 内容 | 保留期 | 说明 |
| :--- | :--- | :--- | :--- |
| 应用日志 | `trace_id` / 接口 / 耗时 / 错误码 | 30 天 | 不含患者信息 |
| 业务审计日志 | 提交结果、冲突处置、话术发布、附件登记 | 永久 | 推送 M02 审计中心 |
| 越权拦截日志 | `staff_id` / 目标 `task_id` / 权限点 | 1 年 | **拦截次数突增多数是配置问题不是安全问题**，告警阈值需区分 |
| 离线链路日志 | `client_recorded_at` 与 `created_at` 差值 | 90 天 | 差超 12 小时说明离线链路有问题 |
| 附件巡检日志 | 抽查数 / 缺失数 / 哈希不一致数 | 3 年 | 证据类，不删 |

**日志红线**：任何日志都不得打印随访结果正文、患者姓名、完整手机号。日志里出现 `result_summary` 内容等于把边界打穿。

| DA-20 | 单号流水不重 | 并发 200 次生成附件单号，无重号 |
| DA-21 | `as_of` 不用 `now()` 兜底 | 代码扫描 `as_of` 赋值处，无 `now() or` / `or now()` 形态 |
| DA-22 | `data_quality` 不由上游透传 | 代码扫描，无 `data_quality = upstream[...]` 直接赋值 |

### 12.4 安全验收

| 编号 | 验收项 | 验收方法 | 预期 |
| :--- | :--- | :--- | :--- |
| SC-01 | **上游失败不得返回「无待办」形态** | mock M19 P-01 超时，调 API-01 / API-02 | **断言 `degraded = true` 且页面出现黄条**；若返回 `items = []` 且 `degraded = false` 判失败 |
| SC-02 | **权限过滤失败必须报错，不得返回全量** | mock 权限上下文返回缺范围字段 | 断言 HTTP 500 或 403，**响应体不含任何业务行**；若返回 200 且 `items` 非空判失败 |
| SC-03 | **无权限不得伪装成空列表** | 用无 `m20:fol:task:list` 的账号调 API-02 | 断言 403 + `"2007001"`；若返回 `200 + items=[]` 判失败 |
| SC-04 | **降级不得多给数据** | mock 上游返回比正常态更多的行，同时构造部分失败 | 断言返回行数 ≤ 正常态行数 |
| SC-05 | **`as_of` 不得用当前时刻兜底** | mock 上游响应**不含 `as_of` 字段** | **断言响应 `data_quality = 'UNKNOWN'` 且 `as_of` 为空**；若 `data_quality = 'REALTIME'` 且 `as_of` 等于请求时刻判失败 |
| SC-06 | 四标记必须始终出现 | 遍历全部 30 个接口的正常与降级响应 | 每个 `data` 都含 `degraded` / `degraded_sources` / `data_quality` / `as_of` 四键 |
| SC-07 | `degraded_sources` 不降级时为 `[]` | 正常响应 | 断言是空数组而非 `null` 或缺省 |
| SC-08 | 事件载荷不含可识别信息 | 抓三条发布事件的载荷 | 只含 `attempt_id` / `task_id` / `patient_id` / 状态 / 时刻 / `trace_id`，无姓名、证件号、联系电话、住址 |
| SC-09 | 日志不含随访结果正文 | 提交含特征词的 `result_summary` 后全量检索日志 | 零命中 |
| SC-10 | 列表页不返回完整手机号 | 抓 API-01 / 02 / 03 响应 | 手机号形如 `138****5678`，无 11 位明文 |
| SC-11 | 越权访问返回 403 而非 404 | 用无范围账号查他人任务详情 | 403 + `"2007001"`，不泄露「该任务是否存在」 |
| SC-12 | 附件预览地址有时效 | 获取预览地址后等 90 秒再访问 | 401 / 403，不得长期有效 |
| SC-13 | 附件引用不可删除 | 枚举全部路由 | 不存在 `DELETE /media/{id}` 路由 |
| SC-14 | 冲突处置不可批量 | 检查 API-23 入参定义 | 无数组型 `item_id`，单次仅一条 |
| SC-15 | 只能归档本人创建的备忘 | 用他人账号归档 | 403 + `"2007036"` |
| SC-16 | 高危操作全留痕 | 发布话术、处置冲突、重算统计各执行一次 | M02 审计中心各出现一条记录，含操作人与时刻 |

## 附录 E：关键决策记录

| 编号 | 决策 | 备选方案 | 为什么选它 / 为什么不选另一个 |
| :--- | :--- | :--- | :--- |
| D-01 | 随访结果只写 M19，本模块库内不留存 | 在本模块建一张随访结果表 | 若允许护士把「左眼有点胀」写进本模块，三个月后患者视力出事，医生翻病历看到「随访记录：已完成，无异常」——因为真正的异常被记在了医生看不到的表里。**这不是数据冗余问题，是安全问题** |
| D-02 | 有效随访率不由本模块计算，本模块只算接通率 | 本模块也算一个「随访完成率」给科室看板 | 有效随访率的分母是应访数，归 M19；若本模块自己造一个分母，会出现两个部门报出两个随访完成率，且没人能判断哪个对 |
| D-03 | 接通率分母是触达次数 | 用应访数当分母 | 触达次数完全属于 M20，是护士按了几次拨号键；用应访数会把 M19 的口径复制一份 |
| D-04 | 分母为 0 返回 `NULL` + `NO_DATA` | 返回 0 | 0% 会被读成「一次都没接通」，100% 会被读成「全都接通」，两者都是撒谎；`NULL` + 「无数据」是唯一诚实的表达 |
| D-05 | 离线冲突绝不自动覆盖也绝不自动丢弃 | 版本号大的覆盖版本号小的 | 两个人同时跟一个患者是典型场景，自动覆盖等于让后提交的人静默抹掉先提交的人做过的沟通；**决策要留给人，且要留理由** |
| D-06 | 冲突处置一次只处理一条，理由 ≥ 4 字 | 提供「全部丢弃」按钮 | 留痕成本是 4 个字，不留痕成本是事后无法自证；批量按钮会把前者变成零 |
| D-07 | 附件只存对象存储键与哈希 | 存数据库大字段 | TOAST 拉取、`pg_dump` 膨胀、数据库不支持缩略图与断点续传 |
| D-08 | 必须有独立探针任务做真 GET | 靠 `content_hash` 自校验 | 哈希只能证明「记录的哈希与当时算出来的一致」，证明不了对象存储里文件还在；生命周期规则、手工清桶、跨区域复制失败、迁移漏目录四种失败元数据接口都看不出来 |
| D-09 | 探针不做自动修复 | 发现缺失就重新上传 | 自动重新上传等于掩盖了对象存储的配置问题，下一次会有更多文件静默消失 |
| D-10 | 待办写入 `m20_msg_todo`，走 M20-08 写接口 | 本模块建一张 `m20_fol_todo` | 两张待办表的数字对不上，护士就再也不信角标了；总纲算例里五个来源相加不做事得 34 条而实际 19 条，虚高 79% |
| D-11 | 同患者同 `cycle_key` 在本层合并 | 完全依赖 M19 去重 | M19 的去重键是任务级，跨计划的重复节点它看不到；本层合并的键是「患者 + 计划 + 节点」，正是护士视角 |
| D-12 | 备忘正文上限 512 字符 | 不限制长度或允许 TEXT | 长度上限是主动引导：一旦放宽，护士会往里写临床信息；「不要记录临床信息」这句提示的效果远不如让输入框写不下 |
| D-13 | 话术按版本化发布，已发布不得原地改 | 直接改原行 | 原地改等于把合规证据改成「现在的口径」，事后无法证明当时说的是什么 |
| D-14 | 用部分唯一索引表达「同编码只有一个 ACTIVE」 | 用触发器校验 | 能用唯一索引表达的不变量就不要用触发器（数据结构汇总 §3.1 原则）；代价是改版必须先归档再激活，顺序写反会立刻报错——而这正是我们要的：写错时立刻失败，而不是留下两个生效版 |
| D-15 | `as_of` 取所有成功来源的最小值，且绝不用 `now()` 兜底 | 用响应生成时刻 | 一旦 `as_of` 永远是新鲜的，这个字段的全部意义就没了；拿不到就如实返回 `UNKNOWN` |
| D-16 | 权限过滤在 SQL 层参数化，范围判定失败抛异常 | 查出来再在应用层过滤 | 应用层过滤的失败模式是「静默地少过滤了一点，结果全出」；SQL 层是「抛异常 → 500 → 什么都没出去」。计数泄露比明细泄露更隐蔽——应用层过滤下 `total` 会是全量数 |
| D-17 | 无权限一律 403，不用 404 伪装 | 用 404 避免泄露存在性 | 只有「确认无权」时才 403；对有权但目标不存在的资源仍返回 404。两者混用会让排障时无法区分权限问题与数据问题 |
| D-18 | 本模块自定义单号只在内部流转，未占用共享规范 §3.3 号段 | 去共享规范申请新前缀 | 附件编号不跨模块引用，占号只会让号段表变长；已在 §8.1 写死格式与 Redis 键，避免后来人重复发明 |
