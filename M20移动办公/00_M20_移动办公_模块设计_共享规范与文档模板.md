### 0.3 四条铁律（违反即返工）

| # | 铁律 | 原因 |
|---|---|---|
| **1** | **数量口径三处一致**：页面总览树 `P0x` = 第 5 章 `### 5.x P0x` 标题；表清单 = `### 4.x 表：` 标题；接口总览 `API-01` 起连续无断号且每项有 `#### API-xx` 详述 | 全仓统一标准，交叉引用依赖编号稳定 |
| **2** | **M20 只做「移动适配」与「跨端协同」，不重建任何业务逻辑**：所有业务判定（能不能开这刀、这张处方合不合格、这批货够不够、这笔账能不能平）**一律由上游模块裁决**，M20 只负责**聚合展示、采集录入、提交转发**。**绝不在 M20 里再建 `m20_order` / `m20_diagnosis` / `m20_prescription` / `m20_bill` / `m20_patient` / `m20_report`** | M01~M19 已建 1,291 张表并已定稿。M20 若自建一套业务表，同一张处方会有两个状态、同一个诊断会有两个编码来源。**这是本模块最严重的架构错误** |
| **3** | **技术栈 PostgreSQL 16**：不得出现 MySQL / Oracle 专有语法（自增关键字、定长整型、旧式日期时间类型、存储引擎子句、Oracle 字符串类型均禁用，详见 §16 校验项与 §17 第 12 条） | 全仓已统一 PostgreSQL，MySQL 语法是硬错误 |
| **4** | **移动端不快照、不缓存业务数据到服务端**：M20 的服务端**不保存业务数据副本**。所有列表、详情、报告内容一律**实时透传上游**或**短 TTL 缓存（≤ 60 秒，且必须带 `as_of` 与 `degraded` 标记）**。**绝不在 M20 建「患者快照表」「报告副本表」「指标快照表」** | 移动端最大的工程陷阱是「为了快，先存一份」。一旦存了，就会出现「PC 端看到的是新的、手机看到的是旧的、而且没有任何提示」——临床场景下这意味着护士按旧医嘱执行、医生按旧报告决策。**M20 的定位是「同一份数据的另一个窗口」，不是「第二份数据」** |

> **M20 专属铁律（第 5 条）：审批流的「状态机」在 M20，审批的「业务后果」在申请方。**
> M20 拥有审批单据（`m20_approval_instance` / `m20_approval_node` 等）、审批链解析、审批人在线状态、移动端待办与推送；但「审批通过之后这张改单怎么改、这笔反结账怎么记、这台手术怎么停」**一律由申请方模块自己执行**。M20 通过 `POST {申请方回调路径}` 或 `m20.approval.completed` 事件**通知结果**，**不直接改申请方的任何表**。
> 理由：审批通过 ≠ 业务生效。中间可能因为库存不足、收费单已封账、时段已被占用而失败。如果 M20 直接把「审批通过」写成业务生效，那么失败的业务动作会变成一个**显示已批准、实际没执行**的幽灵单据。**M20 只对「审批这件事」负责，不对「审批之后的事」负责。**

> **M20 专属铁律（第 6 条）：不持有任何凭据、不签发任何令牌、不建立第二套身份。**
> 登录、会话、Token 签发与校验、设备指纹与信任、锁屏与登出、二次验证（MFA）、手势密码——**全部在 M02**（M02-02 认证与登录 / M02-03 会话与 Token / M02-05 二次验证 / M02-07 安全策略与风控）。M20 **只做移动端适配**：转发现有 M02 接口、透传 `device_id`、在界面层落实 M02 已给定的锁屏时长与二次验证触发条件
> **绝不在 M20 建 `m20_token` / `m20_session` / `m20_device` / `m20_user` 表，绝不自己生成或校验 JWT。**
> 理由：两套身份体系是安全事故的经典起点。M02-07 §3.6 已经给出设备指纹算法（`SHA256(UA + screen + timezone + language)[:16]`）与四态信任模型（`KNOWN` / `NEW` / `TRUSTED` / `BLOCKED`），M02-05 已经给出 `GESTURE` 手势密码「仅移动端可用、不得用于高风险操作」。M20 再实现一遍必然与 M02 的既有策略产生漂移——**而安全策略漂移的表现是「在手机上能做的，PC 上做不了」或更糟「该拦的没拦」**。

## 1. M20 模块定位与子模块划分

### 1.1 一句话定位

**M20 移动办公是全院业务系统在移动终端上的唯一统一入口**：它不拥有任何临床业务数据，**只拥有三样东西**——① **移动端的聚合与编排**（把 19 个模块的接口按角色与场景重新组织成「一屏能读完、一手能操作」的视图）② **跨模块审批流引擎**（唯一一处承载「谁申请、走几级、谁批、批到哪了、超时催谁」的业务审批）③ **员工消息与待办中心**（M03-05 明确把员工站内信与审批消息划给 M20）。

它把 PC 端的「深度操作」翻译成移动端的「即时决策」：查房时看什么、护士床边扫什么、管理者在外出差时批什么。

### 1.2 M20 与 M01-11 审批引擎的边界（最容易做错的地方，必读）

**这是 M20 设计中最容易犯、且犯了整个模块就失去存在意义的错误。**

全仓有**两个**「审批」相关的能力，它们长得像，但**服务对象完全不同**：

| 维度 | **M01-11 审批与版本**（主数据审批） | **M20 业务审批引擎**（本模块） |
|---|---|---|
| **审批对象** | **主数据**本身：`mdm_drug` 的价格、`mdm_dept` 的层级、`mdm_diagnosis` 的编码 | **业务单据**：改单、退费、停台、反结账、盘亏、让步接受、越权放行 |
| **核心载荷** | `before_json` / `after_json`（字段级变更快照） | `biz_type` / `biz_no` / `amount` / `reason`（业务单据引用） |
| **生效语义** | **审批通过即生效**：写主数据、生成 `md_version` 版本快照 | **审批通过 ≠ 业务生效**：通知申请方，由申请方自己执行（见铁律 5） |
| **域枚举** | `domain_code` ∈ `ORG` / `PAT` / `MAT` / `CLI` / `FEE` / `AUTH` / `DICT` / `OPT`（共 8 个**主数据域**） | `biz_type` 由申请方定义：`M10_ORDER_AMEND` / `M11_STOP_SURGERY` / `M17_REVERSE_CLOSING` … |
| **表前缀** | `md_`（`md_change_request` / `md_approval_chain_rule` / `md_version` / `md_impact_analysis` 等 9 张） | `m20_`（`m20_approval_instance` / `m20_approval_node` …） |
| **数据源** | `md_approval_chain_rule` 按主数据域配置 | `m20_approval_rule` 按业务类型 + 金额 + 科室配置 |
| **权威接口** | `POST /internal/v1/approval/submit`（M01-11 API-35） | `POST /internal/v1/m20/approval/apply`（已被 M10/M11/M17 写死 25 处） |
| **谁能发起** | M01 各主数据子模块 | M10-06 / M10-07 / M11-01/02/05/06/07/08 / M17-01/02/05/06/07/08 / M18-06 |

**核实依据（逐条可 grep 验证）：**

- M01-11 `M01_主数据管理MDM_11_审批与版本_详细设计.md:723`（Pydantic）与 `:940`（另一处）：`domain_code: Literal["ORG", "PAT", "MAT", "CLI", "FEE", "AUTH", "DICT", "OPT"]`——**只有 8 个主数据域，没有任何业务单据域**。
- M01-11 `:1412` 起 API-35 的请求体是 `{"change_type","domain_code","object_type","object_id","object_code","object_name","before_json","after_json",...}`——**主数据变更快照结构，无法表达「改单 GD20261028001 把镜片从 A 换成 B、差额 400 元」**。
- M01-11 的 9 张表全部是 `md_` 前缀，含 `md_version`（主数据版本快照）、`md_impact_analysis`（主数据引用扫描），**无 `biz_type` / `biz_no` / 金额相关字段**。
- M10-06 `M10_视光业务管理_06_配镜订单与取镜交付_详细设计.md:7130` 给出 M20 的载荷原型：`{"biz_type": "M10_ORDER_AMEND", "biz_no": "GD...", "amount": 400.00, "reason": "...", "applicant_id": 5001}` → `{"approval_no": "SP..."}`。
- 全仓 `POST /internal/v1/m20/approval/apply` 被引 **25 次**、`GET /internal/v1/m20/approval/{no}` 被引 **8 次**，**没有一处引用 M01-11 的 `/internal/v1/approval/*` 来做业务审批**。

**裁决：两套并存，不合并、不互相代理。**

- **M20 不调用、不依赖、不复制 M01-11 的审批链表。** 两套审批链规则的数据结构相近是巧合（都是「按条件匹配一条链」），但**业务含义不同**：M01-11 的链规则回答「改药品价格要谁批」，M20 的链规则回答「改单金额 400 元要谁批」。**若强行共用一套表，`domain_code` 枚举要混进业务类型，M01-11 已有的 8 个域约束会被打破，且 M01 会为了 M20 的需求修改自己的核心表。**
- **M20 与 M01-11 之间只允许一件事：审批人来源解析。** 两边都要回答「这个部门的负责人是谁」「这个角色的在岗人员有哪些」——这类问题统一调 **M02**（`GET /internal/v1/auth/dept-tree`、`GET /internal/v1/auth/staff-by-roles`、`GET /internal/v1/auth/{staff_id}/permission-context`）与 **M01-02 职工**，**不从 M01-11 取**。
- **M01 主数据变更的移动端审批**（M01-11 `:2623` 写「M20 移动办公 | 待办、通知 | 实时 | 事件」）：M01-11 自己拥有审批状态机，M20 **只承接它的待办推送与展示入口**——即 M20 展示「你有 3 个主数据变更待审」，点进去跳转到 M01-11 的审批页。**M20 不把 M01 主数据审批纳入自己的 `m20_approval_instance`。** 理由：M01-11 的审批结果是「生成主数据版本快照」，如果 M20 也存一份审批实例，会出现「M20 说批完了、M01 说版本没生成」。

> **一句话边界：** M20 回答「**谁申请了、该走几级、批到哪了、超时了该催谁**」；M01-11 回答「**这次主数据改了什么、以前是什么、能不能退回**」。**前者是流程，后者是内容与版本。**

### 1.3 M20 与 M02 的认证边界（第二处必读）

**核实依据：**

- M02-02 认证与登录：`POST /internal/v1/account/verify-credential`（150ms）、`POST /internal/v1/session/create`（100ms）。
- M02-03 会话与 Token：`POST /internal/v1/token/validate`（20ms，5000 QPS）、双 Token + Refresh 轮换 + 重用检测；`m02_session` 已有 `device_id VARCHAR(64)`「设备指纹（同终端覆盖）」（`M02_统一权限与安全_03_会话与Token_数据结构.md:126`）。
- M02-05 二次验证：`POST /internal/v1/mfa/verify`（100ms）；手势密码 `GESTURE`（`M02_统一权限与安全_05_二次验证_详细设计.md:184`）**仅移动端可用、不得用于高风险操作（退费、手术审批）、连续失败 5 次禁用**（`:1271`、`:956`「0205035 手势密码仅限移动端」）。
- M02-07 安全策略与风控：设备指纹 §3.6（`SHA256(UA + screen + timezone + language)[:16]`，四态 `KNOWN`/`NEW`/`TRUSTED`/`BLOCKED`，`NEW` 强制二次验证，`TRUSTED` 免二次验证 30 天）、锁屏策略 §3.7（**空闲锁屏 15 分钟、强制登出 120 分钟、敏感页面锁屏 5 分钟**，锁屏 vs 登出的区别已定义）、紧急封禁 §3.8。
- M02 总纲 `:760`：「M20 移动办公 | 鉴权 + MFA | —」。
- M02-05 `:2781` AC：「手势仅移动端」；`:2843` 会话级已验证状态模型。

**裁决：M20 把 M02 的能力「翻译成移动端体验」，不新增任何认证能力。**

M20 需要做、也只能做的是：

| M20 要做的事 | 依据 | 不许做的事 |
|---|---|---|
| **透传 `device_id`**：每个请求头带 `X-Device-Id`，值必须等于 M02-07 §3.6.1 的算法结果 | M02-07 §3.6.1 | 不得自行定义设备标识算法或另建 `m20_device` 表 |
| **在 UI 层落实锁屏**：15 分钟空闲锁屏、敏感页面 5 分钟 | M02-07 §3.7 | 不得自行决定锁屏时长（必须从 M02 策略接口读或配置项透传） |
| **高风险操作强制 MFA**：手术审批、退费审批、折扣审批等 | M02-05「手势不得用于高风险操作」 | 不得因「移动端图方便」把手势密码当作高风险操作的认证方式 |
| **新设备登录引导信任** | M02-07 §3.6.2 `NEW` 状态 | 不得跳过 M02 的 `NEW → TRUSTED` 流程自行发信任 |
| **`is_mobile_user` 准入校验** | M01-02 `:131`「可移动办公 `is_mobile_user`」 | 不得自行维护「谁能用移动端」名单 |

**一条最容易踩的坑**：M02-05 手势密码是**会话级**（同 SMS），不是长期凭据。M20 若在客户端「记住手势」并在下次启动直接放行，等于绕过 M02 的策略——**必须每次会话都经 M02 校验**。

## 2. 全局技术约定

### 2.1 技术栈（与 README 7.1 一致，不得增删主项）

| 层 | 选型 | 版本 | 说明 |
|---|---|---|---|
| 语言 | Python | 3.11+ | 与全仓一致 |
| Web 框架 | FastAPI | 0.110+ | 异步路由；内部接口用 `APIRouter(prefix="/internal/v1/m20")` |
| ORM | SQLAlchemy | 2.0 | `Mapped[...]` 声明式，**不用 1.x 风格** |
| 数据库 | PostgreSQL | 16 | 唯一数据库 |
| 缓存 | Redis | 7 | 短 TTL 缓存（≤60s）、幂等键、分布式锁 |
| 消息 | RabbitMQ | 3.12+ | 事件发布与订阅 |
| 异步任务 | Celery | 5.3+ | 推送重试、超时催办、离线队列补偿 |
| 定时任务 | APScheduler | 3.10+ | 审批超时扫描、待办提醒 |
| 校验 | Pydantic | V2 | `model_config = ConfigDict(...)` |
| 迁移 | Alembic | 1.13+ | 迁移号 `m20_0001` ~ `m20_00NN` |
| **移动端** | **不引入服务端模板引擎** | — | M20 输出 JSON，客户端（原生 / 小程序 / H5）自行渲染。**不得使用 Jinja2 在服务端拼 HTML** |

> **为什么不用服务端渲染**：M20 要同时服务原生 App、企业微信工作台与 H5 三端。服务端拼 HTML 会让三端共用一套 DOM 结构，任何一端的交互调整都会牵动另外两端。输出 JSON 让「渲染」成为客户端关注点，服务端只保证**字段契约稳定**。

### 2.2 统一响应格式

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "trace_id": "7f3a1c2e"
}
```

- `code = 0` 表示成功。**业务失败一律用非 0 的 `code`（7 位字符串，见 §11），配合恰当的 HTTP 状态码**。
- **不得用 HTTP 200 + 非 0 `code` 表达「系统故障」**——系统故障必须用 5xx。
- `trace_id` 必填，贯穿 M20 → 上游 → 日志，用于跨模块排障。

### 2.3 分页格式（统一定义，不得自创）

```json
{
  "code": 0,
  "data": {
    "items": [],
    "page_no": 1,
    "page_size": 20,
    "total": 137,
    "has_more": true,
    "as_of": "2026-11-07T10:09:42+08:00"
  }
}
```

- **移动端默认 `page_size = 20`，上限 100**（PC 端上限 500）。理由：移动端网络与内存预算都远小于 PC。
- **`as_of` 必填**：表示 `items` 的数据口径截止时刻。聚合多个上游时取**所有上游里最早的那个时刻**（见 §8A.4）。
- **`has_more` 必填**：移动端用「上拉加载」而不是页码跳转，靠这个字段判断是否继续请求。
- **`total` 允许为 `null`**：当 `total` 的查询开销过大（如跨 5 个上游聚合）时可以返回 `null` 并置 `has_more` 为准。**不得为了凑 `total` 额外扫全表**。

### 2.4 时间与数值

- 时间一律 `TIMESTAMPTZ`，JSON 中为 ISO 8601 带时区（`2026-11-07T10:09:42+08:00`）。
- **移动端必须返回服务端时间**：响应头 `X-Server-Time`，因为手机时钟可能被用户手动改，而「这条医嘱是 3 分钟前还是 3 小时前开的」在移动端是高频判断。
- 金额 `NUMERIC(14,2)`，比率 `NUMERIC(10,6)`。**禁止 `FLOAT` / `DOUBLE PRECISION` / `REAL` 表示金额**。
- 分数、剂量、滴数 `NUMERIC(12,4)`（与 M07 医嘱、M08 给药保持一致）。

### 2.5 幂等与并发

- **写接口必须支持幂等**：请求头 `X-Idempotency-Key`（客户端生成 UUID）。M20 落 `m20_base_idempotency`（或各子模块自己的幂等表），**键 = `(biz_type, idempotency_key)`，TTL 24 小时**。
- **移动端幂等的特殊性**：手机在电梯里、地下车库、手术间信号盲区，**同一笔操作被用户连点 3 次或被客户端自动重发 5 次是常态**，不是异常。所以 M20 的幂等要求比 PC 端更严：**每一个「产生业务后果」的写接口都必须幂等**，包括审批提交、审批动作（同意/驳回）、医嘱录入、随访执行。
- **审批动作的幂等尤其关键**：如果「同意」被重发两次而审批节点正好是「最后一级」，会导致审批完成事件发两次、申请方的业务动作执行两次（改单改两遍、退款退两笔）。
- 分布式锁用 Redis：`SET key value NX EX <秒>`，键见 §14。**锁必须带过期时间**，且**锁失效不等于业务可重入**——真正的保护是数据库唯一约束与状态机校验。

### 2.6 数据库硬规范

- 表名 `m20_` 前缀（见 §12）。
- 主键 `BIGINT GENERATED ALWAYS AS IDENTITY`（**不用 `SERIAL`，不用自增关键字**）。
- 每张表必须有 `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`、`created_by BIGINT`、`updated_at TIMESTAMPTZ`、`updated_by BIGINT`。
- 业务表统一带 `is_deleted BOOLEAN NOT NULL DEFAULT FALSE`（软删除）——**但审批留痕表、消息投递日志表除外**（见 §12，这两类表只增不删）。
- 状态列用 `VARCHAR(32)` + `CHECK` 约束，**不用数据库 `ENUM` 类型**（PostgreSQL 加枚举值需要 `ALTER TYPE`，在全仓多环境同步时是常见事故源）。
- 索引命名：`idx_m20_{表简称}_{列}`、唯一索引 `uk_m20_{表简称}_{列}`、约束 `ck_m20_{表简称}_{含义}`、外键 `fk_m20_{表简称}_{目标}`。

### 2.7 分层结构（目录约定，全模块一致）

```
app/
├── api/
│   ├── v1/m20/            # 对移动端（用户端）
│   └── internal/m20/      # 内部契约（P-xx）
├── services/m20/          # 业务编排
├── repositories/m20/      # 数据访问
├── models/m20/            # SQLAlchemy 模型
```

### 3.5 权限编码规范

M01-05 `M01_主数据管理MDM_05_权限_详细设计.md` 给出的模块权限前缀是 `m20:*`。M20 采用**四段式**：

```
m20:{子模块}:{资源}:{动作}
```

示例：`m20:doc:order:create`、`m20:apr:instance:approve`、`m20:hospital:search:query`。

**允许三段式别名**（M01-05 已写死 `m20:*` 模块级）：`m20:template:view` 这类三段式在 M20 内部**可登记为别名**，但**必须在本模块 §13 登记映射关系**（`m20:template:view` → `m20:msg:template:view`）。

> **原则：不双写双查，授权导入时一次性转换。** 运行时同时按三段式和四段式判权限，会让任一配置错误变成「页面看得见但点不动」的幽灵问题。

- 7 位数字字符串，号段见 §11。
- **错误码一经定义不得改含义**，只能新增。
- **不得在不同子模块复用同一个错误码表达不同含义。**

## 8A. 降级语义（所有内部接口强制）

**这一节是 M18 那轮踩出来的教训，M20 因为全是链式调用上游，比 M18 更容易触发，所以必须逐字遵守。**

### 8A.1 三种合法形态，没有第四种

| 形态 | HTTP | `code` | `data` | 调用方该做什么 |
|---|---|---|---|---|
| **正常** | 200 | 0 | 完整 | 按正常路径处理 |
| **降级返回** | 200 | 0 | 带质量标记 + `degraded: true` | 知道「这次不完整」，自行决定是否接受 |
| **失败** | 4xx / 5xx | 非 0 | 可含错误详情 | 走它自己文档里写死的降级分支 |

### 8A.2 所有 `data` 必须带四标记

```json
{
  "degraded": false,
  "degraded_sources": [],
  "data_quality": "REALTIME",
  "as_of": "2026-11-07T10:09:42+08:00"
}
```

- `degraded` BOOLEAN：**即使为 `false` 也必须出现**。
- `degraded_sources` ARRAY：元素为 `{"source": "M05_INPATIENT", "reason": "TIMEOUT"}`。不降级时为 `[]`。
- `data_quality` VARCHAR(16)：`REALTIME` / `CACHED` / `PARTIAL` / `UNKNOWN`。
- `as_of` TIMESTAMPTZ：**数据口径截止时刻，不是请求时刻**。

集合类响应另加 `record_count`。

#### 8A.2.1 同名质量字段跨模块值域不同——**M20 必须自己重算，不得透传**（V1.1 裁决）

**事实**：`data_quality` 这个字段名在多个模块里都在用，但**值域不统一**。M18（电子病历）的口径是 `REALTIME` / `DAILY` / `ESTIMATED`（按「实时/日批/估算」分档），而 M20 本节定义的是 `REALTIME` / `CACHED` / `PARTIAL` / `UNKNOWN`（按「实时/缓存/部分/未知」分档）。两者**只有 `REALTIME` 一个值能对上**。

**裁决：M20 一律不透传上游的 `data_quality`。**

M20 响应里的 `data_quality` 必须由自己按 §8A.4 与 M20-CALC-05 的规则重算，输入只有三个客观事实：

1. 该上游这次调用**是否成功**（超时/5xx/降级返回都算「不成功」或「部分成功」）；
2. 本次响应**是否命中了 M20 自己的缓存**；
3. 上游响应**是否带了可用的 `as_of`**。

上游返回的 `data_quality` 只能作为 `degraded_sources[].reason` 的**辅助说明文字**（例如 `"reason": "UPSTREAM_DAILY"`），**绝不能直接赋给 M20 响应的 `data_quality` 字段**。

**为什么不能靠映射表**：写一张 `DAILY → CACHED`、`ESTIMATED → PARTIAL` 的映射看起来能解决，但它是**猜的**——M18 的 `DAILY` 意思是「这份数据来自日批汇总」，它可能恰恰是最新最准的（日结后的当日汇总），而 M20 的 `CACHED` 意思是「这是 M20 自己 30 秒前的缓存」。两个「不实时」的成因完全不同，映射成一个值就把「上游数据本来就是这样」和「M20 缓存旧了」混为一谈，运维永远查不清到底是这边慢还是那边慢。

**由此得出一条通用规则**：**同名字段在不同模块值域不同是允许的，因为每个模块回答的质量问题不一样；但消费方必须自己重算，不得透传。** 透传一个别的模块定义的值，等于把一个模块的口径冒充成全系统的口径——这正是「看起来正常但实际不完整」的升级版（§8A.3 第 1 条）。

**通用规则的反向适用**：如果未来发现某个质量字段需要跨模块统一口径，该字段必须**改名**（例如 `emr_freshness_class`），而不是强行统一值域——同名不同义比不同名更危险，因为它骗过的是 grep。

### 8A.3 三条红线

1. **不允许「看起来正常但不完整」的 200。**
2. **不允许把「没查到」伪装成空数组 + `degraded: false`。** `record_count = 0` 且 `degraded: true`（可能还有数据）与 `degraded: false`（确实没有）**是两种完全不同的事实**。
3. **不允许用 200 + 空 `data` 表达「无权限」**，一律 403 + 非 0 错误码。

### 8A.4 M20 特有的聚合口径（`as_of` 的取法）

M20 的绝大多数接口是**多上游聚合**（一屏要调 3~5 个模块）。此时 `as_of` 必须遵守：

> **`as_of` = 所有成功返回的上游 `as_of` 中最早的那一个。**

理由：如果 A 模块数据截止 10:00、B 模块截止 10:05，而 M20 报 `as_of = 10:05`，用户会以为「10:05 时 A 也是这个值」——但实际 A 的数据早 5 分钟。**聚合视图的时间必须取最保守的那个，因为用户看到的是同一个屏幕上的整体。**

并且：**只要有任一上游降级，整体 `degraded` 必须为 `true`**，即使其他上游都正常。**聚合视图的 `degraded` 是「或」不是「与」。**

### 8A.5 M20 的四个具体应用点（给对应子模块）

- **M20-02 移动医生站「查房一屏」**：聚合 M05 在院清单 + M18 病历正文 + M07 诊断 + M12/M13 最新报告。**若 M18 超时，绝不能返回「这个患者没有病历」** ——必须 `degraded: true` + `degraded_sources: [{"source":"M18_EMR","reason":"TIMEOUT"}]`。理由：医生看到「无病历」会认为患者没写病历，可能重复书写，而实际是查不到。
- **M20-03 移动护理「我的任务」**：调 M08 P-01（`≤150ms`）。**若 M08 不可用，绝不能返回空任务列表**——护士会认为「今天没活」而漏掉给药。必须返回 5xx + 明确提示，或 `degraded` 且页面显示醒目告警条。
- **M20-04 移动审批「待我审批」**：**这是安全性最敏感的一处。** 若审批列表查询降级，**绝不能显示「暂无待办」**——管理者会以为批完了就离开，单据超时。必须显式显示「待办加载失败，请下拉重试」。
- **M20-08 员工消息「未读角标」**：角标数可以降级（显示「99+」或「?」），但**绝不能显示 0**——0 的含义是「没有消息」。

**核实结论**：字段存在（`M01主数据管理MDM/M01_主数据管理MDM_02_职工_详细设计.md:131`「可移动办公 | is_mobile_user」；`M01_主数据管理MDM_02_职工_数据结构.md:137`/`:218` 落库 `BOOLEAN NOT NULL DEFAULT FALSE`），但**没有任何内部接口返回它**——M01-02 的 API-01~API-38 逐个核过，`#### API-02 职工详情`（`M01_主数据管理MDM_02_职工_详细设计.md:770-849`）的完整响应体里没有该字段；M01 的 21 个内部接口（`M01主数据管理MDM/M01_主数据管理MDM_详细设计.md:5536-5554`）里也没有，最接近的 `GET /internal/v1/staff/{id}/brief`（`:5539`）的调用方列出的是 M04/M07/M08/M09，**不含 M20**。

**原 V1.1 写的替代方案（走 M02-04 `permission-context` 间接判定）不成立，一并作废**：`permission-context` 返回的是 `perm_codes`/`data_scopes`/`field_rules`，而 `is_mobile_user` 是**职工属性**不是一条权限，它在权限上下文里永远查不到。**给一个查不到东西的查法，比不给更坏——实现的人会发现查不到，然后自己发明一个判据。**

**裁决**：
1. **M20 不直连任何 M01 职工表**（包括 `mdm_employee_account`）。把 `mdm_employee_account.account_type = 'MOBILE'` 当作准入判据是**用实现细节冒充业务规则**——它有记录只说明「这个人在 M01 有一套移动端账号」，不等于「这个人被允许使用移动端」；而一旦按它上线，它就从临时判据变成了事实标准，M01 那边并不知道自己的账号表被人当成了准入开关。
2. **准入判定移交 M02，在做判定的地方判**：请 M02-04 在 `permission-context` 响应中增加 `is_mobile_user`（或三态 `mobile_access` = `ALLOWED`/`DENIED`/`UNKNOWN`）；**备选**请 M01-02 新增 `GET /internal/v1/staff/{id}/mobile-access`，调用方写 M20。**两条均登记为「需向上游提请」。**
3. **接口落地之前，M20 的行为必须 fail-closed 且可解释**：`m20_base_config` 的开关 `mobile.access.mode` 三值 —— `STRICT`（生产默认：拿不到判定则拒绝移动端登录，提示「移动办公权限未配置，请联系信息科」）/ `PERMISSIVE`（仅 UAT，上线体检项会拦住）/ `DISABLED`（整体关停移动端）。**绝不允许「查不到就当作允许」成为默认。**
4. **M20 是消费方不是权威方**：谁能设该属性、何时设、离职时怎么清，属 M01-02 范围，M20 不写。**M20 也不缓存该判定超过一个会话周期**——准入被撤销时，缓存会让已撤销的人继续用。

#### 10.4.1 V1.1 修正：`m13.critical_value.found` 不存在（M20-02 报出）

V1.0 的本节曾登记一行 `| m13.critical_value.found | M13 | 危急值推送 |`。**这个事件名是错的**：M13 与 M12 全目录内都不存在以 `critical_value.` 为段的事件，`critical_value` 在两个模块里只作为**数据表名**出现（`m12_critical_value` / `m13_critical_value`）。把表名当事件名写，是「凭印象写具体值」的典型形态（§17 第 2 条）——**它读起来完全合理，只有去 grep 才会发现不存在**。

实际事件名是 `m12.critical.detected` / `m13.critical.detected`（行号见上表）。**后续子模块（M20-03 危急值提醒、M20-04 待办、M20-08 消息推送）一律按上表订阅，不得使用 `critical_value.found` 这个写法。**

**同时登记一个上游事实缺口**：M12/M13 **没有**「按患者/按就诊列出报告」的内部接口（全目录无 `review/by-patient`、`review/list`），只有按 `report_id` 单条查的 `GET /internal/v1/m12/review/{id}`（`M12_检查管理_05_报告审核与发布_详细设计.md:4152`）与 `GET /internal/v1/m13/review/{id}`（`M13_检验管理_04_检验结果审核与发布_详细设计.md:3121`）。**因此 M20 不做「患者报告清单」功能**——能做的是「从危急值待办点进去看那一份报告」。需要清单的场合登记为「需向上游提请」，**不得在文档里假设该接口存在**。

**危急值确认的边界**：M12/M13 侧的 `POST .../critical/{id}/on-acknowledged`（M12 `:4153`、M13 `:3123`）语义是「**M07 确认后回调 M12/M13**」，不是「任意方可以确认」。M20 移动端让医生点「我已了解」，**不得替 M07 调这个回写口**（会造成 M07 侧状态不一致：M07 认为危急值未确认、M13 认为已确认）。移动端的危急值确认属于 M07-04 的业务动作，M20 只做通道与待办提醒；若产品要求移动端可直接确认，需由 M07-04 提供移动端确认接口，**登记为待确认事项，不得由 M20 自行发明**。

## 14. Redis Key 与缓存分域

| Key 模式 | 类型 | TTL | 用途 |
|---|---|---|---|
| `m20:base:session:{staff_id}:{device_id}` | Hash | 1800s | 移动端会话上下文（**只存 UI 偏好，不存凭据**） |
| `m20:base:idem:{biz_type}:{key}` | String | 24h | 幂等键 |
| `m20:base:lock:{resource}:{id}` | String | 30s | 短锁（**必须带过期**） |
| `m20:doc:round:{ward_id}` | String(JSON) | 60s | 查房列表缓存 |
| `m20:nur:task:{nurse_id}` | String(JSON) | 30s | 护士任务缓存 |
| `m20:apr:pending:{approver_id}` | ZSet | 60s | 待审批列表（按紧急度排序） |
| `m20:apr:chain:{biz_type}:{dept_id}` | String(JSON) | 3600s | 审批链解析结果 |
| `m20:qry:patient:{patient_id}` | String(JSON) | 30s | 患者聚合视图 |
| `m20:msg:unread:{staff_id}` | String | 300s | 未读角标 |
| `m20:msg:token:{staff_id}:{device_id}` | String | 永久（显式删除） | **推送令牌**（第三方推送服务的设备令牌，不是身份凭据） |
| `m20:sal:order:{order_no}` | String(JSON) | 30s | 订单查询缓存 |

**规则：**
1. **缓存分两类，各有 TTL 上限**：
   - **业务聚合缓存**（缓存里含跨模块的业务事实，如查房列表、患者聚合视图、待审批列表、护士任务）——**TTL ≤ 60 秒**。理由：`as_of` 超过 60 秒的聚合结果直接违反 M20-CALC-05，用户看到的会是「一分钟前别的模块的数据」，而且刷新按钮也救不了，因为新请求仍可能命中同一份旧缓存。
   - **计数与状态缓存**（缓存里只有一个本模块自己算出来的数字或布尔，不含任何业务内容，如未读角标、在线数）——**TTL ≤ 300 秒**。理由：这类值的变化对用户的感受是「稍后刷新也看得出」，而为了它每 60 秒刷一遍 300 人的角标是纯粹的负载，换不来任何准确度收益。
   - **不属于以上两类的**（审批链解析这类纯配置、推送令牌这类需持久的）必须在本节表格里单独列出并写明理由，不得默默享受例外。
   - **判据一句话：这个缓存里有没有跨模块的业务事实？有 → 60 秒；只有本模块自己算出来的一个数字 → 300 秒。**
2. **缓存值必须带 `as_of`**，命中缓存时响应的 `data_quality` 必须是 `CACHED`。
3. **不得在 Redis 存任何凭据、Token、患者身份证明文。**
4. 分布式锁**必须带过期时间**，且**锁失效不等于业务可重入**。
5. **只缓存成功的结果，降级结果不进缓存**。把「数据缺」写成 `CACHED`（含义是「数据旧」）比不缓存更糟：一次瞬时的上游抖动会被固化成一个看起来正常的缓存值，`degraded` 在下一个 TTL 周期内全部变回 `false`——**降级被缓存自己抹掉了**，而且此后没有人会再去查那次抖动。
6. **审批链解析缓存只缓存「链的形状」，不缓存具体审批人**。链的形状按制度配置很少变，审批人却随时因调岗、请假、离职而变；缓存具体审批人会让 G-3 审批人有效性闸门直接失效，且失效的表现是「该批的人批不了、不该批的人能批」，两边都不会报错。

## 17. 常见坑

### 1. 引用一个不存在的接口并注明「由某模块提供」

**最危险的一类错误。** 它把不存在的东西写成「已有的、不用管它」，后续所有人都会跳过核实。

**规则：引用任何上游路径前必须 `grep -rn "<路径>" --include=*.md .` 并贴出行号。** 找不到就写「未找到，本子模块首次定义并登记为 P-xx」或「未找到，需向上游模块提请」。

### 2. 凭印象写具体值（比抽象描述错得更严重）

抽象描述错了读者会怀疑，**具体值错了读者会直接引用**。

M18 那轮出现过五次同根因错误：P-02 的 HTTP 方法、`AR` 单号的位数、同意书表名、`mpi.patient.merged` 的出处文件名、附录 D 的编号。**全部是「正文凭印象写、没回头对附表」。**

**规则：凡是文档里出现的具体数字、路径、表名、事件名，都必须能指回一条当场跑出来的 `grep` 输出或一次手算。**

### 3. 把 `degraded` 判定写成「本地有没有数据」

M20 是聚合方，**本地数据库永远有数据**（哪怕是空表也是「查到了，确实没有」）。用「本地有没有」判断 `degraded`，这个标记永远是 `false`，等于没有。

**正确做法：`degraded` 判定依据是「所有上游是否全部成功返回」，是「或」不是「与」。**

### 4. 对上游单号做位数或格式校验

M18 那轮在 `AR` 单号上踩过：共享规范写「14 位」，实际 M05 原文是 15 字符。**双方只要有一方加了位数校验，端到端就跑不通。**

**规则：审批单号 `SP...` 对调用方是不透明字符串。M20-04 必须在 §8.1 写死「任何调用方均不得对 `approval_no` 做位数或格式校验」。**

### 5. 把「无权限」伪装成「空数据」

移动端最常见：查不到就返回空列表 + HTTP 200。用户以为「确实没有」，实际是「你看不到」。

**规则：无权限一律 403 + 非 0 错误码。**

### 6. 审批通过后由 M20 直接改申请方的表

**见铁律 5。** 审批通过 ≠ 业务生效。M20 只发通知，申请方自己执行。

**后果示例**：改单审批通过后 M20 直接改了 `m10_order` 的明细，但库存不足导致 M10-07 重派工失败——订单显示「已改单」但实际加工的还是旧镜片，且没有任何一处报错。

### 7. 角标显示 0 表示「加载失败」

`0` 的语义是「没有消息」。用 `0` 表示失败，会让管理者错过所有待办。

**规则：加载失败必须显式显示「加载失败，点击重试」，不得显示任何数字。**

### 8. 缓存 TTL 设成小程序/App 的「会话级」

M20 允许短 TTL 缓存（≤60s），但**不允许「会话级缓存」**（在 Redis 里按会话存业务数据副本）。

**理由**：会话级缓存 = 每个用户一份副本 = 数据分叉。医生 A 看到旧报告、医生 B 看到新报告，且双方都不知道。

### 9. 离线队列把「已删除的单据」重新提交

移动端离线时排队的操作，恢复网络后逐条重放。若单据在离线期间被作废/改单/退费，重放会**把已作废的单据救活**。

**规则**：离线队列重放前必须做版本校验（携带入队时的实体版本号或 `updated_at`），版本不一致进 `CONFLICT` 状态人工处理，**不得自动覆盖**。

### 10. 移动端返回完整报告全文

检验报告全文可能 200KB，移动端一个列表页拉 20 条就是 4MB。弱网下 40 秒。

**规则：列表页只返回摘要字段（项目名、结果值、异常标志、报告时间）；全文单独一次请求，且必须支持分段。**

### 11. 把 M01-11 的审批链和 M20 的审批链搞混

**见 §1.2。** 两套并存，不合并。M01-11 的 `domain_code` 只有 8 个主数据域，没有业务单据域。

### 12. 在文档里把 MySQL 关键字写成字面量

校验器会当成 MySQL 残留。**连「坑表里说『不要用 MySQL 的某某类型』」也不许写那个类型名**——改写成文字描述（「自增关键字」「旧式日期时间类型」「存储引擎子句」）。

### 13. 禁用词清单里有一个高频日常词

禁用词表（见 `validate_m20.py` 的 `PLACEHOLDERS`）中有一个两字词，日常写法里极容易出现：填表模板、调试代码、预留说明里都会用到它。校验器 **不判断语境，命中即报**。

**统一改用「哨兵值」「缺省标记」「表名预留」。**

### 14. 句末「忽略」会让校验器误判

「……一并忽**略**。」这句话的末尾两个字恰好构成另一个禁用词。**校验器按裸子串匹配，不看词边界。凡句末是「忽略」的都要换说法**（如「一并跳过」「直接不看」「都不再看」）。

> 这两条本身就是「写坑表时也会踩自己的坑」的例证：本节初稿把这些词的字面写进了标题与正文，被自己的校验器抓了一串。**要说明「某词禁用」，就用描述而不是字面。** 写完之后一定要跑一遍脚本，人眼对这类词的敏感度远低于脚本。

### 15. 表格单元格内的裸竖线

`只写「同意书管理 | 模板」` 会让列数错乱。**用 `/` 或 `、`。**

### 16. 同名标题出现两次

尤其出现在「追加写作」的接缝处：文档的 `## 目录` 与模板里的 `## 目录` 撞车。**模板嵌在四反引号代码块里可以，但正文里不行。**

### 17. 一行内挤了两个标题

`## 11. 异常处理与日志## 11. 异常处理与日志`。追加写作时粘贴失误。**写完必须回头扫一眼标题行。**

### 18. 章节目录写在最前面但最不被维护

骨架先写、正文后长，最后正文长成了别的样子，目录还是早期草稿。**M18 那轮一次抓出 15 处目录与正文不符。**

**规则：交付前必须把目录与正文标题逐条比对。** 校验器有这一项。

### 19. `AC-100` 这类三位编号

正则按 `AC-(\d{2})`，三位会被截成 `AC-10` 判重号。**四类各自最多 99。**

### 20. `__table_args__` 里 `comment=` 写在元组元素上

Python 元组不接受关键字参数。**正确写法：`(约束1, 约束2, {"comment": "..."})`，字典必须是元组最后一个元素。**

### 21. 用 `from datetime import datetime as dt` 绕校验器

M18 那轮出现过：因为校验器的大小写不敏感匹配误伤了 `datetime`，成员用别名绕开。**这是把一个问题变成两个。**

**规则：遇到「怎么改都过不了」的检查，先怀疑校验器，直接报告，不要用污染代码规范的绕法迁就。**

### 22. 把「审批超时」当成「审批驳回」

超时的业务含义是「没人处理」，驳回是「有人明确不同意」。两者对申请方的后续动作完全不同（超时要重提或升级，驳回要改内容再提）。

**规则：`TIMEOUT` 是独立状态，不得折叠进 `REJECTED`。**

### 23. 审批链解析结果缓存了但审批人已调岗

`m20:apr:chain:{biz_type}:{dept_id}` TTL 1 小时。若这期间审批人调岗，解析结果仍指向旧人。

**规则：M20-04 必须在文档中说明「审批链缓存失效时机」，并列出至少三条触发删除的事件（职工调岗、角色变更、科室负责人变更、审批规则变更）。**

### 24. 移动端看到的和 PC 端看到的不一致却无任何提示

**这是 M20 最容易犯、也最伤信任的错误。** M20 的缓存 TTL 60 秒意味着移动端数据最多旧 60 秒。

**规则：任何 `data_quality = CACHED` 或 `degraded = true` 的响应，页面必须有可见提示（如顶部黄条「数据截至 10:05」）。没有提示的降级等于欺骗。**

### 25. 用不带长度的字符串类型表达文本列

校验器的 `BAD_SQL` 只抓 MySQL 方言特征（自增关键字、定长整型、日期时间类型、引擎子句、Oracle 字符串类型、超大文本类型），**不带长度的字符串类型是 PostgreSQL 也合法的，所以它不在黑名单里**——这是校验器的盲区，靠人守。

**规则：文本列一律给长度。** 理由不是存储差异，而是：**`VARCHAR(n)` 与不带长度的文本类型的区别不在于怎么存，在于「这个字段有没有上限」这件事有没有被写下来。** 没有上限的字段，写入方会以为可以塞任意长度，直到某天有人在里面存了一份完整的病历正文、一张 base64 图片、或者一整段 SQL 报错堆栈——而那时候已经写进去了几万行。

**校验器管不到的地方，靠的是人。** 这条规则正是它的盲区。

### 26. 禁用词扫描不看语义，只管字面

V1.2 及以前的校验器用**裸子串**匹配禁用词，导致 `m20_base_menu.badge_source` 的合法枚举值「拉丁字母待办词 + 下划线 + 计数后缀」（角标来源 = 待办数）被判成禁用词。**这不是文档写错了，是校验器把「看起来像」当成了「就是」。**

校验器已改为：**拉丁字母类禁用词走标识符边界匹配**（带下划线的业务枚举通过，独立的那个词仍被抓）；**中文类仍走子串**（中文没有词边界）。

**这条坑的普适教训**：**检查一项「不该出现的东西」时，先问「什么东西会长得像它」。** 三个大写字母加中文的那个表名类禁用词是同一类情形——`m20_apr_xxx_table` 这种命名不该被拦，但它作为独立的缺表描述该被拦。

遇到疑似误报，**先怀疑校验器并上报**（§17 第 21 条），不要为了过检查去改一个本来正确的业务枚举——那会把一个检查缺陷变成两个规范缺陷。

> **本节自己踩了自己**：初稿把四个禁用词当字面量写进正文举例，于是这一节本身被校验器判成 4 处违规。规则写下来之后，写规则的人也要遵守它——**坑表不是法外之地**。

### 27. 校验器把「表头」当成「数据」是它最常犯的错

校验器 V1.5 修掉的两处，根因是同一个：**代码里用「行/区间」的几何位置去理解表格，而表格的语义在表头里。**

- **6.6 权威表**：表头是 `| 错误码 | HTTP | 含义 | 触发场景 | 处置建议 |`。比对逻辑取「紧邻错误码的那一列」与「含义列」比重合度，结果取到的是 `HTTP` 状态码列——于是每一条错误码都报一次「语义不一致」（M20-02 一次性报出 48 条）。
- **响应示例**：判断「本文件提供了哪个内部契约」时用「全文出现 `P-0x`」，于是**只是调用上游 P 契约**的子模块（如 M20-07 引 M19 的 `P-01`）也被要求四标记齐全，而它一个 M20 契约都不提供。

**教训**：写「按列比对」的检查时，先确定**列的下标从哪来**，并显式跳过表头行与分隔行。更稳的做法是**按区间跳过**（该行落在被检查的小节内就跳过，如上面对 6.6 小节的整段跳过），而不是逐行猜「这一行看起来像不像数据」——**「看起来像」永远有反例**。

同类风险在 `check_toc`（目录多列表格只取第二列）上也出现过一次，同一种病。

### 28. 双向交互里，「回程」那一段最容易被漏掉编号

M20 的契约分两个方向：**上游提供给我方**（U-xx）、**我方提供给上游**（P-xx）。这两个方向都建了号段，也都在评审时被逐条核过。但还有第三个方向——

> **上游执行完之后回头告诉我结果。**

它既不是「我调它」也不是「它调我」，而是一次**异步回执**。P-01 审批申请被 25 处引用、P-02 审批查询被 8 处引用，全都登记得清清楚楚，**唯独「审批通过之后申请方执行完了要回写结果」这个接口，长期只出现在总纲的一段散文里，没有编号、不在契约表、`validate_m20.py` 也不检查**（M20-06 报出）。

**漏掉的机制**：写契约时脑子里想的是「谁调谁」，于是每一对调用关系都被登记；而回程不是一次调用，是**调用之后的一个承诺**，它不出现在任何一张「调用关系表」里。**凡是不出现在调用图上的接口，都要单独检查一遍。**

**判据**：任何 P-xx 写接口，问一句「**它执行完之后，谁需要知道结果？怎么知道？**」——那个「怎么知道」就是回程接口。异步回执、事件、回调、补偿任务都算。

### 29. 表格单元格里的 SQL 不能用 `||` 拼字符串

附录的巡检 SQL 常常是嵌在 Markdown 表格里的（「校验项 | SQL | 期望结果」这种三列表）。而 SQL 里用 `schemaname || '.' || tablename` 拼限定名是 PostgreSQL 的惯用写法，**`||` 一进表格单元格就把列数算错了**（Markdown 表格以裸竖线分列）。

**这个坑只在「表格里嵌 SQL」时出现，而附录的巡检 SQL 偏偏最容易嵌在表格里**（M20-06 报出）。改用 `concat()` 或 `format()`：

```sql
-- 错：在表格单元格里会破坏列数
SELECT schemaname || '.' || tablename FROM pg_tables;
-- 对
SELECT concat(schemaname, '.', tablename) FROM pg_tables;
```

**推广的教训**：**Markdown 表格是整个文档格式里最脆的构件**——表格单元格对竖线、反引号、竖线转义都有要求，而表格又恰恰是最适合放「对照关系」的地方，所以 SQL、JSON、正则这些「自带特殊字符的语言」都会往表格里跑。**凡是往表格里放代码，先问一句「这段代码里有哪些字符是 Markdown 的元字符」。**

### 30. `6.6` 权威表的错误码首列不能包反引号

校验器认 6.6 权威表的正则要求首列是**裸的** `"2008001"`：

```
| "2008001" | 400 | 参数错误 | ... |    ← 对
| `"2008001"` | 400 | 参数错误 | ... |  ← 错（会被判成「6.6 错误码定义表为空」）
```

M20-08 报出后我选择**不改校验器**：改成也能认反引号会让「6.6 的表格式」变成两种写法，而**两种写法就会有两种错法**，下一个人还得判断该用哪种。**一个格式，一个写法，检查器只认一种。**

顺带说明**为什么这个错误的表现是「表为空」而不是「格式不对」**：正则匹配不到任何一行时，`re.findall` 返回空列表，代码只能判断「一条都没找到」，无法区分「表不存在」和「表存在但写法不对」。**这是所有基于正则的表格检查的共同局限——报错信息只能说明「我没找到」，不能说明「你写错了」。** 遇到这类报错，先按「我写的东西和检查器的期待有形状差异」去想，而不是按「我没写」去想。

### 31. 一处拦截是纪律，四处拦截是结构

判断一条不变量守不守得住，**看它在几个互相独立的层有落点**：

- **只在一处**（比如 Service 层的一句 `if`）——这是**纪律**。改需求的人不会看到它，写批处理脚本的人不会看到它，三个月后的自己也未必记得它。它可以被一次「顺手优化」无声地删掉，而且**删掉之后所有测试仍然通过**。
- **在四个互相独立的地方**——Pydantic 校验 + 数据库 `CHECK` + Service 断言 + 巡检 SQL——这是**结构**。改任何一个都得同时改另外三个，改漏了另外三个会立刻报错。

M20-08 的 `{count: 0, degraded: true}` 四层拦截是范例：`UnreadCountVM._check_zero_never_degraded`（请求校验）+ `ck_m20_msg_unread_zero`（数据库）+ Service 断言 + 附录 B.3 巡检。

**判据**：写下一条「绝对不能发生」的规则之后，问一句「**如果有人不知道这条规则，他会怎么绕过它？绕过去之后谁会报错？**」——如果答案是「没有人会报错」，那这条规则现在只是一句话。

### 32. 降级结果不得写入缓存

把「数据缺」缓存成一个 `CACHED` 值，**比不缓存更糟**。因为 `CACHED` 的语义是「数据旧」，而实际发生的是「数据缺」；更要命的是 `degraded: true` 会在下一个 TTL 周期内全部变回 `false`——**降级被缓存自己抹掉了**，此后没有人会再去追那次上游抖动。

正确做法：**只缓存成功的结果，降级结果一律不写缓存**（缓存 miss 时重新请求上游，请求成功才写）。M20-08 角标、M20-07 待办、M20-02 查房列表都按这条执行。

**推广**：任何「有状态的补偿机制」都要问一句「**我的补偿动作会不会把故障现场覆盖掉？**」——缓存会、自动重传会（M20-07 的附件探针因此明确不做自动修复）、「自动把不一致的数据修复成一致」也会（M18-03 的 `content_hash` 巡检因此只标 `HASH_MISMATCH` 不自动修复）。**凡是「记录本身是证据」的地方，不允许自动修复。**

### 33. 把不变量写进数据库时，要连它的「返回形态」一起写清楚

`INSERT ... ON CONFLICT ... DO UPDATE ... WHERE <谓词>` 在谓词不满足时**不是报错，是静默跳过**，`RETURNING` 返回空集。这个形态和「没有匹配行」完全一样，所以服务层必须显式处理空集并回查，**不能 `scalar_one()`**——否则一次合法的重发会被实现成 500（M20-08 写完 `m20_msg_todo` 的 upsert 之后发现的）。

前面几轮我们一直在讲「把不变量写进数据库」的好处：`uk_m20_apr_node_active` 的原子性、`sql_perm_applied` 的值恒真约束、`ON CONFLICT ... WHERE` 的「批处理也挡得住」。**这一条是它的代价**：数据库用「空集」同时表达了「谓词不满足」和「没有这一行」两件事。

**判据**：凡是让数据库「有条件地什么都不做」的写法（`ON CONFLICT ... WHERE`、`DO NOTHING`、触发器里 `RETURN NULL`、条件 `UPDATE`），调用方都必须先问一句「**它什么都不做的时候，我怎么知道它什么都不做？**」

### 34. 为每一条「写进数据库的不变量」配一条「它失效了吗」的巡检

绝大多数巡检 SQL 查的是「有没有异常数据」。这类 SQL 有个前提：**你得先想到坏数据长什么样，想不到就查不到。**

更有效的一类巡检利用的是「**正常情况下这个条件永远为假**」：

```sql
-- 期望 0 行。终态待办的 updated_at 晚于其最后一条状态流水
SELECT t.id, t.todo_no, t.status, t.updated_at
FROM m20_msg_todo t
LEFT JOIN (SELECT todo_id, max(created_at) AS last_event_at
           FROM m20_msg_todo_event GROUP BY todo_id) e ON e.todo_id = t.id
WHERE t.status IN ('DONE','VOIDED','TRANSFERRED')
  AND t.updated_at > COALESCE(e.last_event_at, t.created_at);
```

正常情况下 `ON CONFLICT ... WHERE` 会让终态行永远不被更新，所以这条 SQL **永远返回 0 行**。**只要它有一次返回非空，就说明那道闸被改了或被绕过了**——不需要预先知道「被绕过之后数据长什么样」。

**判据**：写下一条「写进数据库的不变量」之后，配一条「它不成立时会怎样」的查询。这类巡检的价值不在发现坏数据，**而在发现「防线本身没了」**。

### 35. 章节标题的编号后面直接跟关键词，不要插中间层

`### 4.11 SQLAlchemy 2.0 模型` 是契约；写成 `### 4.11.0 统一约定` + `### 4.11.1 SQLAlchemy` 就断掉了（M20-03 踩到，校验器的正则是 `^###\s+4\.\d+\s+SQLAlchemy`）。

**检查器认的是标题的字面形状，人认的是逻辑层级。两者不一致时吃亏的总是人**——因为检查器不会想，而人会以为检查器会想。

### 36. 引用外部文件时，不要凭记忆写文件名

文件名由「模块前缀 + 子模块号 + 子模块名 + 文档类型」四段拼成，**四段里每一段都极容易凭印象补全**，而补出来的名字在语法上 100% 合理。Lead 在通知里把 `M08_护理工作站_03_医嘱执行与签名_详细设计.md` 写成 `_03_护理记录与文书_`，把 `_06_用药与滴眼液执行_` 写成 `_06_用药执行与核对_`，两个名字都不存在（M20-03 报出）。

**判据**：**任何一个不是从 `ls` 或 `grep` 输出里直接复制来的路径，都不能进文档。**

**连带一条**：改别人的文档时引用自己文档里的路径，等于把坏引用复制一遍。

**再连带一条（同根因，反复出现）**：**上下文里有一个曾经正确的值，我拿它当现在正确。** 事件名用了已废弃的草稿、行数/版本号用了上一版、文件名凭记忆补全——机制完全相同。**发出任何含「文件名 / 接口路径 / 事件名 / 行数 / 版本号」的消息之前，先跑一遍那条命令。**

### 37. 长任务的进度要以「可被外部验证的痕迹」报告

不说「第 12 章写完了」，说「第 12 章已存 `/tmp/m2003d/f6.md`，115 行」（M20-03 提出）。**一句话的代价，换来协作方不必依赖信任。**

反面：一个只存在于对话上下文里的产出，**在协作意义上等于不存在**——别人看不见，就没法在此基础上做决定（比如是否派人帮忙），也没法在出问题时定位到哪一段是谁写的。M20-03 的 4,783 行曾经在磁盘上「一个字节都没有」而实际已写完，Lead 因此误判了进度。

### 38. 粗粒度指标全绿是停止检查的理由，也是最不该停止检查的时刻

M20-05 交付前自查时踩到一个 bug，它的分布很有代表性：**行数、章节数、表格列数全都正常，只有一个检查项挂了。** 所有粗粒度指标都通过时，人会自动认为「这里是好的」，然后跳过细粒度检查。

**粗粒度信号说没问题，细粒度信号说了唯一一次真话。**

交付前必跑的细粒度四项（M20-01 写成可复用片段，四个子模块都在用）：

1. `ast.parse` 全量 python 代码块，逐个报坏块行号；
2. 代码围栏成对计数（开栏与闭栏数量相等）；
3. 四类验收编号实际去重计数，与正文声明比；
4. 三处集合比对必须 `set() ==`：页面树 vs `### 5.x` 标题；§6.1 总览里的接口 vs 全部 `#### API-xx`；附录标题 vs 目录里的附录名。

### 39. 围栏开闭错位：一种「所有内容都在，但检查器看不见」的故障

M20-04 的数据结构 §4.4 与 §4.5 之间、§4.5 与 §4.6 之间各有一处 SQL 围栏跨过了章节边界没有闭合，于是**接下来三张表的全部内容都被围在代码块里**。

这件事的可怕之处在于：**文档渲染出来完全正常**（代码块里照样显示表格和一、二、三级标题），人读不出问题；**文档行数、表数量声明、SQLAlchemy 章节全都在**；只有把围栏状态逐行跟踪一遍，才能发现三张表根本没被当成章节标题。

**规则**：**一次只追加一个小节，追加完先数围栏。** 判断围栏是否闭合看两点——开栏数等于闭栏数的**字面计数**不算数（` ```sql ` 与 ` ``` ` 在计数上各算一个，但它们是同一个块的头尾，数量当然相等），要看的是**逐行状态机的终态**：扫完全文后围栏状态必须是「正文」。

**V1.11 补充（这一条被现实又打了一次脸）**：M20-04 后来查明不是「2 处漏栏」而是「**8 个小节连续漏栏**」，而且**「全文终态是正文」也证明不了没有小节被吞**——少一个闭栏会让状态翻转，后面多一个开栏又翻回来，全程终态都是「正文」，中间 5 个小节的标题却全被围住了。

**所以真正的判据只有一个，而且它便宜到没有理由不做**：**代码块内遇到 `^#{2,3} ` 这类标题行就直接判错。** 一个正常文档的代码块里不该出现 Markdown 标题（四反引号嵌模板的除外）。这一条已经写进 `validate_m20.py` 的 `check_fence_shadow`。

**这一条的覆盖边界必须写明**：`check_fence_shadow` 的判据 1 抓的是「被吞掉的**标题行**」。若某处漏了闭栏、而它后面紧跟的**不是标题而是正文段落**，代码块会一直延续到下一个标题才暴露——若下一个标题恰好不存在（例如漏栏发生在整份文档最后一节），门禁就抓不到。**所以「逐小节围栏终态」这条自查不能因为门禁全绿就省掉**（M20-04 提醒）。

**还有一条元教训**：M20-04 报「已修」的依据是「补上闭栏后围栏配对为真」——**正是本条规定不能用的那个判据**。**当校验器对一个维度是盲的，人在那个维度上的一切「已修」都不成立，包括人自己写的自检脚本。** 修完必须用一个**原本会失败**的新判据去验，而不是用一个**补完就会通过**的旧判据。

**顺带一条**：这个问题是跨文件一致性脚本报出来的，而它报的第一版**报错了原因、报对了位置**——它说「汇总写 11 张、实际定义 4 张」，实际是它自己的围栏配对逻辑有缺陷。**位置对、原因错，仍然比什么都没报有价值**：它把注意力引到了那一页。

### 40. 判断「某个数据该不该存在」时，先问它存的是「事实」还是「窗口」

`m20_base_idempotency` 是 M20 唯一允许物理 DELETE 的 `m20_base_*` 表：24 小时前的幂等登记被清掉，业务事实毫发无损——它只是窗口内的去重登记。**窗口可以过期，事实不行。**

**判据**：这张表存的东西，删掉之后还有没有别处能证明它发生过？能 → 它是窗口，可以清；不能 → 它是事实，只能只增不删，且必须 `REVOKE DELETE`。

**配套一条**：窗口表不许加软删除列。加了会让 `UNIQUE (biz_type, idempotency_key)` 失去意义——软删除之后同一组合还能再插一行，而这个唯一约束正是这张表存在的理由。

### 41. 一处拦截是纪律，四处拦截是结构

M20-08 的「未读数绝不能显示 0 表示加载失败」这条红线，落在四个互不相干的地方：Pydantic 校验器（`UnreadCountVM._check_zero_never_degraded`）、数据库 CHECK（`ck_m20_msg_unread_zero`）、服务层断言、附录巡检 SQL。四处**都要**，缺一处就退回成纪律。

**判据**：写下一条红线之后问一句——**「如果有人不知道这条规则，他会怎么绕过它？绕过去之后谁会报错？」** 如果答案是「没有人会报错」，那么这条规则现在只是一句话。

### 42. 为 0 的分母必须返回空值，不能返回 0 也不能返回 100

M20-07 的通话接通率三种错分母算例：正确 **77/94 = 81.91%**；用全部计划数 77/120 = 64.17%（低 17.75 个百分点）；用已拨过的任务数 77/89 = 86.52%（**高 4.61 个百分点**）。

**第三种最危险**：它让「不干活的人」指标更好看——**任何分母能被被考核者通过「少做事」改善的指标，都是坏指标。**

**规则**：分母为 0 时返回 `NULL` + `rate_status = 'NO_DATA'`，并在数据库侧用 CHECK 强制「次数为 0 时比率必须 IS NULL」。**绝不能返回 100**（把没数据说成满分），**也不必返回 0**（把没数据说成失败）——它是第三种事实，要有第三种表达。

**文档结束。**
