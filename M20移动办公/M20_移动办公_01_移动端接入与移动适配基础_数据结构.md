## 4. 数据结构设计

### 4.1 ER 关系图

```
                        ┌───────────────────────────────┐
                        │      m20_base_config          │
                        │  配置（含页面编排 layout.*）   │
                        └───────────────┬───────────────┘
                                        │ layout_code（逻辑）
                        ┌───────────────▼───────────────┐
                        │       m20_base_menu           │
                        │   菜单树（约 80 条）           │
                        └───────────────────────────────┘

┌──────────────────────┐        ┌──────────────────────┐
│ m20_base_app_version │        │ m20_base_device_     │
│  版本与灰度           │        │ registry（终端台账）  │
└──────────────────────┘        └───────┬──────────────┘
                                        │ device_id（逻辑）
                    ┌───────────────────┼───────────────────┐
                    ▼                   ▼                   ▼
        ┌────────────────────┐ ┌────────────────┐ ┌──────────────────┐
        │m20_base_offline_   │ │m20_base_session│ │m20_base_audit_log│
        │queue（离线队列）    │ │_pref（UI 偏好） │ │（只增留痕）       │
        └────────────────────┘ └────────────────┘ └──────────────────┘

        ┌──────────────────────────────┐
        │  m20_base_idempotency        │   独立事实表，被全部写接口共用
        └──────────────────────────────┘

        ┌──────────────────────────────┐
        │  m20_base_stat               │   独立统计表，由定时任务写
        └──────────────────────────────┘
```

**图例**：连线箭头表示**逻辑引用**，全部不建物理外键（跨子模块与跨生命周期引用的统一处理，见 4.1.2）。

#### 4.1.1 逻辑引用清单

| 源表.字段 | 目标表.字段 | 引用性质 | 为何不建外键 |
|---|---|---|---|
| `m20_base_menu.layout_code` | `m20_base_config.config_key` | 弱引用 | 页面编排被删除或改名时，菜单必须回落到默认布局，**不能因为外键失败而连菜单都渲染不出来** |
| `m20_base_offline_queue.device_id` | `m20_base_device_registry.device_id` | 弱引用 | 终端报废后台账行会被清理，队列项必须保留（否则「这条操作是哪台设备提交的」永远说不清） |
| `m20_base_session_pref.device_id` | `m20_base_device_registry.device_id` | 弱引用 | 同上 |

#### 4.1.2 为什么不建物理外键

1. **跨生命周期的引用会打架**：台账行可清理、队列项不可清理。建了外键就只有两个选择——要么台账永不清理（违反运维要求），要么队列项跟着删（违反留痕要求）。两个都不能接受。
2. **逻辑引用是「提示」不是「约束」**：菜单指向不存在的布局时正确行为是**降级到默认布局并记一条告警**，而不是整个菜单树 500。
3. **移动端接入层是全局热点**：每个请求都可能 `INSERT m20_base_idempotency`、`UPDATE m20_base_device_registry`，外键检查会在这个路径上加一次额外的索引探测。本项目不引入这类可省的开销。

#### 4.1.3 九张表的分层

| 层 | 表 | 特征 |
|---|---|---|
| **配置层**（读多写极少） | `m20_base_config`、`m20_base_menu`、`m20_base_app_version` | 变更走配置管理接口 + 留痕；缓存 TTL ≤ 60 秒 |
| **台账层**（写多、只增不删为主） | `m20_base_device_registry` | 被 P-06 高频 UPDATE，**不含任何可信判定字段** |
| **通道层**（高频、跨子模块共用） | `m20_base_idempotency`、`m20_base_offline_queue` | 首建者 M20-01，M20-02~08 只读不写 |
| **会话层**（高频、可丢） | `m20_base_session_pref` | 丢了不影响业务，只影响体验 |
| **留痕与统计层** | `m20_base_audit_log`、`m20_base_stat` | 台账只增不改；统计由定时任务覆盖写 |

### 4.2 表：`m20_base_config`（移动端配置表）

**用途**

存移动端两类配置，用 `config_group` 区分，**不拆两张表**：

1. **运行参数**（`config_group = 'PARAM'`）：页面大小、缓存时长、离线重试上限、灰度开关等全局可调参数。约 20 条。
2. **页面编排**（`config_group = 'LAYOUT'`）：某个页面由哪些区块组成、区块顺序、默认展开与否、单栏/双栏。约 30 条。

**为什么合表而不是拆成 `m20_base_config` + `m20_base_page_layout`**：两者共用完全相同的结构——「按 `scope_type` + `scope_code` 分层的键值」。拆开后就是两套 `config_key` 解析代码、两套缓存、两套变更留痕，且**运维改一个「默认科室」的默认值时要先分清它属于哪张表**。合表后统一走 `resolve_config(key, scope_ctx)`，只有一处解析逻辑。

**为什么页面编排要存成配置而不是代码里写死**：移动端布局在大字号模式、单手模式、PAD 横屏下是不同的区块组合。写死在客户端就要发版，而发版审批周期是周级；存成配置后，运营在 P01 改完即时生效（≤ 60 秒缓存 TTL）。这也符合铁律 4 的反面：**配置是允许存服务端的，因为它不是业务数据**。

**写入方：** M20-01 配置管理接口（`PUT /api/v1/m20/base/configs/{config_key}`）。
**只读方：** M20-02~08 服务端读全局参数；移动端客户端经配置下发接口读取其可见的配置项。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | N | 自增 | 主键，`GENERATED ALWAYS AS IDENTITY` |
| `config_key` | VARCHAR(128) | N | — | 配置键，`PARAM` 组形如 `page.size.default`，`LAYOUT` 组必须以 `layout.` 开头 |
| `config_group` | VARCHAR(16) | N | — | 配置分组：`PARAM` / `LAYOUT` |
| `config_name` | VARCHAR(128) | N | — | 中文名，供配置页显示 |
| `config_value` | TEXT | N | — | 配置值。`PARAM` 存标量或 JSON 字符串；`LAYOUT` 存区块数组 JSON |
| `value_type` | VARCHAR(16) | N | — | 值类型：`STRING` / `INTEGER` / `BOOLEAN` / `DECIMAL` / `JSON`，决定变更时如何校验 |
| `default_value` | TEXT | N | — | 出厂默认值，**三层解析全部未命中时用它**，不允许为空（否则「配置缺失」会变成运行时 None） |
| `value_constraint` | VARCHAR(256) | Y | NULL | 取值约束描述，如 `1~100`、`ASC/DESC`，变更时按此校验 |
| `scope_type` | VARCHAR(16) | N | `'GLOBAL'` | 生效范围：`GLOBAL` / `CLIENT_TYPE` / `STAFF_ROLE` |
| `scope_code` | VARCHAR(32) | N | `''` | 范围取值；`GLOBAL` 时存空串 `''` 而非 NULL（PG 唯一索引认为 NULL 互不相等，存 NULL 会让 `GLOBAL` 行可以重复插入） |
| `client_type` | VARCHAR(32) | N | `'ALL'` | 适用客户端：`ALL` / `IOS` / `ANDROID` / `MINI_PROGRAM` / `H5` / `PAD` |
| `is_editable` | BOOLEAN | N | TRUE | 是否允许在管理界面修改；`FALSE` 表示只能随版本发布调整 |
| `is_sensitive` | BOOLEAN | N | FALSE | 是否属于敏感配置（变更需二次审批并强制留痕） |
| `effective_from` | TIMESTAMPTZ | Y | NULL | 生效开始时刻；为空表示立即生效 |
| `effective_to` | TIMESTAMPTZ | Y | NULL | 生效结束时刻；为空表示长期有效 |
| `remark` | VARCHAR(512) | Y | NULL | 备注 |
| `sort_no` | INTEGER | N | 0 | `LAYOUT` 组内的区块排序号 |
| `version` | INTEGER | N | 1 | 乐观锁版本号，每次 UPDATE 加 1 |
| `is_deleted` | BOOLEAN | N | FALSE | 逻辑删除。配置项删除后保留行以便审计追溯 |
| `created_at` | TIMESTAMPTZ | N | `now()` | 创建时间 |
| `created_by` | BIGINT | Y | NULL | 创建人 |
| `updated_at` | TIMESTAMPTZ | N | `now()` | 更新时间 |
| `updated_by` | BIGINT | Y | NULL | 更新人 |

**索引设计**

**分区策略**

**设计说明**

| 编号 | 说明 |
|---|---|
| D-01 | **三层解析顺序 `STAFF_ROLE → CLIENT_TYPE → GLOBAL`**，命中即停，全未命中用 `default_value`。绝不能写成「取所有层叠加」，那样一个角色的值会覆盖另一个角色的值，排查时无从下手。 |
| D-02 | **`scope_code` 用空串不用 NULL**。PG 唯一索引把多个 NULL 视为互不相同，若 `GLOBAL` 行存 NULL，同一个 `config_key` 可以无限重复插入，而三层解析会随机取一行——这是「配置改了不生效」的头号成因。 |
| D-03 | **`config_value` 用 TEXT 不用 JSONB**：`PARAM` 组里有大量标量（`20`、`true`），JSONB 的 `"20"` 与 `20` 读出来类型不同，会让 `page.size.default` 这类参数在客户端变成字符串 `"20"` 导致分页失效。用 TEXT 存原样字符串，由 `value_type` 决定解析方式。 |
| D-04 | **`is_sensitive` 的典型成员**：`offline.retry.max`（调大它等于放宽失败上限）、`security.lock.idle_minutes`（虽然权威在 M02，M20 只做 UI 计时，但改小它等于放宽体验上的保护）。敏感配置变更必须走 `POST /api/v1/m20/base/configs/{config_key}/approve`。 |
| D-05 | **页面编排用 `sort_no` 而不是数组下标排序**：配置被部分更新时（只改一个区块的属性），数组下标会被打乱，而 `sort_no` 是每个区块自带的，改谁的属性就只动谁。 |
| D-06 | **`LAYOUT` 键前缀强制**：`config_key LIKE 'layout.%'` 与 `config_group = 'LAYOUT'` 双向绑定（`ck_m20_base_config_layout_prefix`）。这样「分组填错了」在数据库层就不可能发生，而不是等到客户端解析时报错。 |

### 4.3 表：`m20_base_menu`（移动端菜单表）

**用途**

存移动端的菜单树：哪个角色、哪个科室、哪种客户端能看到哪些入口。约 80 条，初始化数据由数据结构汇总 §9 的第 3 步导入。

**为什么菜单要放服务端而不是写死在客户端**：全院 8 个子模块、77 个页面，每个科室开哪些入口不一样（屈光中心要「视光销售」，病案室要「病历检索」，护士站要「护理任务」）。写死在客户端意味着每加一个科室入口就要发一次版，而**发版审批是周级的、科室需求是天级的**。放服务端后，管理员在 P02 勾一下即时生效，代价只是菜单树的 TTL ≤ 60 秒缓存。

**为什么不在本表里做权限判定**：本表只存「这个入口叫什么、指向哪里、归哪个子模块」。**能不能看，一律实时问 M02-04 `POST /internal/v1/perm/check`**（U-06）。本表有一列 `perm_code` 只是「这个入口需要什么权限」的申报，**不是判定结果**——把判定结果落库，就会出现「上午勾掉了某人的权限，手机上的菜单还在」的越权入口。

**写入方：** M20-01 菜单管理接口。
**只读方：** M20-02~08（菜单树渲染）、M02-04（按 `perm_code` 过滤）。

**设计说明**

| 编号 | 说明 |
|---|---|
| D-07 | **`perm_code` 是申报不是判定**。M20 渲染菜单时必须对每个 `perm_code` 实时调 U-06 判定，**不得缓存判定结果超过 60 秒**，且**不得把判定结果写回本表**。一旦写回，「权限收紧了手机还看得见入口」就变成了结构性问题。 |
| D-08 | **`menu_code` 一旦发布不得修改**。客户端会把菜单树缓存在本地（离线时用），以 `menu_code` 为键。改编码等于让老客户端的缓存全部失效且解析失败——表现为「更新后菜单空了」。需要改编码就走「新增一个 + 旧的置 `is_visible=FALSE`」。 |

| D-11 | **`badge_source` 只存标识不存数值**。角标数值必须实时算（M20-CALC-03 待办聚合），存进菜单表就是第二份待办数据，而且会过期。角标查询失败时按 §8A.5 显示「9+」或「?」，**不得显示 0**。 |

### 4.4 表：`m20_base_device_registry`（终端运维台账）

**用途**

存移动终端的**运维信息**：设备型号、操作系统、App 版本、最后活跃时间、最后活跃 IP、当前在线状态。约 2,000 行。

**这张表叫「台账」不叫「设备」，因为它回答不了「这台设备可不可信」。**

判据（数据结构汇总 §1.2 原文）：**这张表能不能用来证明「这台设备是可信的」？能 → 禁止建；不能 → 允许建。**

| 问题 | 本表能不能回答 | 权威在哪里 |
|---|---|---|
| 这台设备的型号/系统/App 版本是什么 | **能** | 本表 |
| 这台设备最后一次活跃是什么时候、哪个 IP | **能** | 本表 |
| 这台设备的指纹是什么 | **不能**（`device_id` 是 M02 透传过来的字符串，M20 不自己算） | M02-07 §3.6 |
| 这台设备可不可信、要不要二次验证 | **不能**（本表没有 `trusted` / `is_trusted` / `trust_level` 列） | M02-07 §3.6 四态 `KNOWN`/`NEW`/`TRUSTED`/`BLOCKED` |
| 这台设备被谁绑定了 | **不能**（本表没有 `bound_user_ids`、没有 `is_binding=TRUE` 这类列，`last_seen_staff_id` 是「最后一次是谁在用」不是「绑定给谁」） | M02-03 `m02_session.device_id` |
| 拿着本表全部数据能不能伪造一次登录 | **不能** | M02 |

**为什么 `last_seen_staff_id` 不算「绑定关系」**：护士站的共享 PAD 一天里会被 20 个护士用，绑定关系对它没有意义；而每位医生的手机也只有他自己用。本表只记录**最后一次是谁用的**，用于排障时回答「这台设备白屏，最后是谁在用、用的哪个版本」。一旦给它加唯一约束 `(staff_id, device_id)` 或加一列 `is_bound`，它就从台账变成了用户-设备关系表，**那时它就具备「设备-身份」关联能力，性质变了**。

**为什么没有任何凭据字段**：铁律 6。凭据（Token、Refresh Token、设备令牌、推送令牌）一律不落本表。推送到第三方的设备令牌由 M20-08 管（`m20:msg:token:{staff_id}:{device_id}`），且它是**第三方推送服务的设备令牌，不是身份凭据**（共享规范 §14 原文）。

**写入方：** M20-01（P-06 上线登记 `POST /internal/v1/m20/device/online`，调用方 M02-07 登录成功后）。
**只读方：** M08（护理调度查在线状态）、M02-07（设备列表对账）、运维看板。

**分区策略**

本表**不分区**。三年累计约 2,000 行，不分区更省事；同时本表有 `device_id` 唯一约束，**分区表的唯一索引必须包含分区键**（数据结构汇总 §4.2），一旦按 `last_seen_at` 分区，唯一约束就会失效，同一台设备可能在不同月份各出现一行——这会让「一台设备一行」这个核心不变量消失。

**设计说明**

| 编号 | 说明 |
|---|---|
| D-12 | **本表没有任何凭据列，这是设计约束不是遗漏**。凭据（Token / Refresh Token / 设备令牌 / 推送令牌）一律不落本表。共享规范 §12 与数据结构汇总 §1.2 把 `m20_device` 列入禁止表，判据正是「这张表能不能用来证明设备可信」。本表不能，所以允许；如果将来有人想加一个 `is_trusted` 列「方便一点」，那是把这张表变成禁止表。 |
| D-13 | **`device_id` 只透传不自算**。M02-07 §3.6 的算法是 `SHA256(UA + screen + timezone + language)[:16]`，M20 若重算一遍，只要取 UA 的方式有细微差别（截断长度、大小写、是否含 App 版本），算出来的 `device_id` 就会与 M02 不同，导致同一个物理设备在两张表里是两条记录、M08 的在线人数虚高一倍。**凡需要指纹，一律问 M02-07。** |
| D-14 | **报废清理要清空与人相关的列**：`device_status='INACTIVE'` + `last_seen_staff_id=NULL` + `last_active_ip=NULL`，保留行只留下 `device_id`/`client_type`/`app_version`/`first_seen_at`。理由：报废设备的台账行带着「最后是谁在用、从哪个 IP」就变成了一个历史人员-设备关联表，**泄露危害比一台在役设备更大**（在役设备关系是公开的，报废设备关系是没人再维护的）。 |
| D-15 | **`device_status` 的 `ONLINE` 靠心跳维持，不靠 `last_seen_at` 猜**。离线判定任务（`m20_base_device_registry_offline_scan`）每 5 分钟扫一次 `ONLINE AND last_seen_at < now() - 30 minutes` 置 `OFFLINE`。**为什么是 30 分钟**：手机在电梯、地下室、手术间信号盲区断网几分钟是常态，阈值取太小会让 M08 护理调度看到「护士一直在掉线」，取太大又会让「人已经下班了还显示在线」。移动端每 5 分钟一次轻量心跳，30 分钟 = 连续 6 次心跳丢失，足以区分「短暂盲区」与「真的离线」。 |
| D-16 | **`login_count` 的口径**：每次 P-06 上线登记 +1，**不去重**（同一会话内重复上报也算，因为它是「活跃次数」不是「登录次数」的严格定义）。若需要严格登录次数，去 M02-03 的会话表查——**本列只用于运维看「这台设备有多活跃」**，不要用它做任何业务判定。 |
| D-17 | **本表不存 `staff_id` 的唯一约束**。护士站共享 PAD 一天 20 个人用，加唯一约束会让人 2 覆盖人 1，看起来像「这台设备被转手了」，实际只是换班。 |
| D-18 | **本表的自我验收标准**：给定本表全部数据，**无法构造出任何一次通过 M02 鉴权的请求**。这是一个安全边界最好的表达方式——不是「禁止写状态字段」这种枚举式禁令，而是「给定这张表的全部内容，能构造出什么攻击」。答案是：什么也构造不出。本表只有「这台设备是什么型号、跑什么系统、上次谁用过、什么时候用的」，没有任何一个字段能参与认证、授权或信任判定。评审时用这条标准逐列核对，比逐条对照禁止清单更可靠。 |

### 4.5 表：`m20_base_app_version`（客户端版本与灰度表）

**用途**

存移动端每个版本的发布状态、强制升级门槛与灰度比例。约 50 行（每年约 15 个版本 × 客户端类型）。

**这张表解决的是「移动端必须先更新才能用新功能」这件事**，而它有三条硬约束，缺一条都会出事：

1. **强制升级必须能拦住老客户端**（拦不住 ⇒ 老客户端调新接口报错，用户看到的是白屏）；
2. **灰度必须能回退**（发新版发现崩溃率高，要能立刻把灰度比例归零，而不是等发下一个版本）；
3. **版本号必须是三段式且可比较**（`2.10.0` 与 `2.9.0`，按字符串比较会判成 `2.10.0 < 2.9.0`）。

**写入方：** M20-01 版本管理接口（发布、调整灰度、下线）。
**只读方：** 移动端客户端（启动时版本检查）、M20-01 自身（灰度分流、强制升级拦截）。

**分区策略**

本表**不分区**，总量约 50 行。

**设计说明**

| 编号 | 说明 |
|---|---|
| D-18 | **版本比较必须按数值逐段比较，不得按字符串比较**。`2.10.0` 与 `2.9.0` 按字符串比较会得出 `2.10.0 < 2.9.0`（因为 `'1' < '9'`）。M20 在 Service 层提供 `compare_version(a, b)`，**拆成三段整数逐个比**；数据库侧只保证格式（`ck_m20_base_app_version_version`），**不做版本比较**——在 CHECK 里写版本比较既慢又难读，而且 DB 层判了也没用，因为分流是在应用层做的。 |
| D-19 | **`gray_ratio` 与 `release_status` 由组合约束绑定**（`ck_m20_base_app_version_status_ratio`）。为什么不在应用层保证：灰度比例没归零就把状态改成 `RELEASED`，是发布流程里最容易犯的错（改了一列忘了另一列），而它的后果是「声称全量、实际只有 60% 的人能升」。CHECK 只保护单列、不保护列间关系，所以这类规则必须显式写成组合约束。 |
| D-20 | **灰度分流用 `hash(staff_id) % 10000 < gray_ratio * 10000`**，不用随机数。用随机数会让同一个人每次启动都判成不同分组——「用了一半功能一半旧功能」，而且灰度期间的问题无法复现。用稳定哈希，同一个人在灰度期间始终在同一组。**白名单（`gray_dept_ids` / `gray_staff_ids`）优先于比例分流**，这样内测账号和大科室能先看到新版。 |
| D-21 | **`ROLLBACK` 是独立状态，不是「把 `RELEASED` 改回 `GRAY`」**。改回去会丢掉「这个版本曾经全量发布过、后来因为崩溃率回退了」这个事实，而这个事实正是复盘要的。回退的动作是：本行置 `ROLLBACK` + `offline_at`，同时把上一个稳定版本重新置 `RELEASED`。 |
| D-22 | **强制升级的判定顺序**：① `min_supported_version` 非空且 `compare_version(current, min_supported_version) < 0` ⇒ 强制升级（**这条最硬，不看灰度**）；② 命中灰度白名单 ⇒ 提示可升级；③ `is_force_update = TRUE` 且该客户端最新版本是本版本 ⇒ 强制升级；④ 否则按比例分流提示。**顺序不能换**：如果先判比例再判 `min_supported_version`，一个灰度比例为 0 的强制升级版本就永远拦不住老客户端。 |
| D-23 | **客户端版本号必须由服务端下发，不得由客户端自称**。客户端上报的 `app_version` 只用于灰度分流与排障，**强制升级判定以「该客户端能调到的最老版本」为准**。理由：客户端谎报版本号是绕过强制升级最简单的方式，而强制升级存在的目的是防止老客户端调新接口崩溃——一旦能绕过，白屏就回来了。 |

### 4.6 表：`m20_base_idempotency`（幂等键表）

**用途**

M20 全部写接口的幂等锚点。**由 M20-01 首建，M20-02~08 一律只是调用方，不得写本表、不得自建幂等表**（数据结构汇总 §1.3 第一条硬规则）。

**为什么这张表只能有一张，不能每个子模块各建一张**：

移动端连点是常态（用户在电梯里点 3 次、客户端网络抖动自动重发 5 次），而幂等的语义是**「同一个意图，无论被表达多少次，只执行一次」**。如果 M20-02 与 M20-06 各建一张幂等表，那么客户端生成的一个 `X-Idempotency-Key` 在两张表里会各存一行——**但这不是问题，问题在反方向**：当同一个业务动作被两个子模块的入口各接一次（例如「医嘱录入」既有医生站的入口也有护士站的快捷入口），两张表各判各的，同一个意图被执行两次，而**两张表都认为自己是幂等的**。这是最难发现的一类重复执行。

**「跨业务唯一」与「跨业务可复用」是两件事，注释里必须分清**：

| 说法 | 含义 | 在本表如何实现 |
|---|---|---|
| **跨业务唯一** | `(biz_type, idempotency_key)` 这个**组合**在全表唯一 | `uk_m20_base_idempotency_key UNIQUE (biz_type, idempotency_key)` |
| **跨业务可复用** | 同一个 `idempotency_key` 在 `M20_02_ORDER_CREATE` 与 `M20_06_SALE_ORDER` 下**各存一行、互不遮挡** | 唯一键是两列组合，不是 `idempotency_key` 单列 |

**如果只把 `idempotency_key` 建唯一**，A 业务的请求会挡住 B 业务——那不是幂等，那是串号：一个护士录医嘱的 key 恰好和收费员的 key 相同（客户端 UUID 碰撞概率极低但**客户端有实现缺陷时用固定值就会撞**），B 业务会拿到 A 业务的响应体当自己的结果返回。

**写入方：** M20-01 幂等中间件（`IdempotencyMiddleware` / `IdempotencyGuard`），全模块唯一入口。
**只读方：** M20-02~08 不直接读，只经中间件。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | N | 自增 | 主键 |
| `biz_type` | VARCHAR(64) | N | — | 业务类型，全大写，如 `M20_02_ORDER_CREATE`、`M20_04_APPROVAL_APPROVE` |
| `idempotency_key` | VARCHAR(128) | N | — | 客户端生成的幂等键（`X-Idempotency-Key` 请求头原值） |
| `staff_id` | BIGINT | N | — | 发起人；**同一 key 被不同人使用视为冲突，不是幂等命中**（见 D-28） |
| `request_hash` | VARCHAR(64) | N | — | 请求体的 SHA-256（小写十六进制）；用于识别「同 key 不同内容」 |
| `request_path` | VARCHAR(256) | N | — | 请求路径，排障用 |
| `request_method` | VARCHAR(8) | N | — | 请求方法 `POST` / `PUT` / `PATCH` / `DELETE` |
| `status` | VARCHAR(16) | N | `'PROCESSING'` | 执行状态：`PROCESSING` 处理中 / `SUCCESS` 成功 / `FAILED` 失败 |
| `response_code` | VARCHAR(16) | Y | NULL | 首次执行的业务 `code`（成功或失败都存），重放时原样返回 |

| `updated_at` | TIMESTAMPTZ | N | `now()` | 更新时间 |
| `updated_by` | BIGINT | Y | NULL | 更新人 |

**设计说明**

| 编号 | 说明 |
|---|---|
| D-24 | **唯一键是 `(biz_type, idempotency_key)` 组合，不是 `idempotency_key` 单列**。理由见用途段的两张表：单列唯一 = 串号。**这条是本子模块对 M20-02~08 的第一条铁律**：任何子模块想「自己建一张幂等表更省事」，都会立刻失去跨入口的判重能力。 |
| D-25 | **`status='PROCESSING'` 的行也是「占用中」，后来的同 key 请求必须返回 409 + 号段内错误码，不得并发执行**。竞态处理：`INSERT ... ON CONFLICT DO NOTHING`，`rowcount=0` 说明已存在，再 `SELECT ... FOR UPDATE` 读状态——`PROCESSING` 返回「正在处理，请勿重复提交」，`SUCCESS`/`FAILED` 原样重放。**不这样做的话，「首次请求还没写完，第二次请求就进来了」会导致两行都执行，而这恰恰是连点最常见的时序**。 |
| D-26 | **`FAILED` 也重放，不重新执行**。听起来反直觉（失败了为什么不让人重试？），但正确做法是：**要重试就换一个新 key**。因为「失败」这件事本身可能已经产生了部分副作用（比如扣了库存但下游超时），自动重试会让副作用叠加。客户端拿到的失败是确定的、可解释的；**服务端擅自重试则不可解释**。 |
| D-27 | **`request_hash` 不一致时返回冲突而不是重放**。同一个 key 配不同请求体，说明客户端复用 key 有 bug。此时若重放首次结果，用户会看到「操作成功」但实际执行的是上一次的内容——**这是最难排查的一类：用户抱怨"我改的没生效"，日志显示成功**。返回冲突会把问题暴露在客户端。 |
| D-28 | **`staff_id` 参与判定但不参与唯一键**。原因：唯一键加 `staff_id` 就变成「每个人各自幂等」，两个人拿同一个 key 都能执行——但它们本来就该是两个不同的意图。所以唯一键不含 `staff_id`，而在命中时**比对 `staff_id`**：若不同，返回冲突（`"2001032"`）。这比「谁先到谁赢」安全得多。 |
| D-29 | **`response_body` 超过 64KB 只存摘要**。移动端响应体上限是 200KB（总纲 §8.1），但幂等表是热点表，存 200KB × 1.2 万行 = 2.4GB 是浪费。超过阈值时 `replay_mode='SUMMARY'`，重放只返回 `code` + `message` + `replay_hint`，**客户端据此知道「这件事已经成功过」**，需要详情就重新查一次（查询接口本身幂等且可重复）。 |
| D-30 | **清理用物理删除，不用 `is_deleted`**。§2.5 的语义是「24 小时幂等窗口」，窗口外本来就该能被重新执行。软删除会让 24 小时窗口变成事实上的永久窗口（软删除行仍占唯一键），与设计意图相反。清理任务 `m20_base_idempotency_purge` 每小时执行，单批上限 5,000 行避免长事务。 |
| D-31 | **本表不存任何业务字段**。它只存 `request_hash` 与 `response_body`，**不拆解请求体、不建 `biz_no` 列**。一旦有人想「加个 `biz_no` 方便查」，这张表就变成了第二份业务索引，而且它与业务表的一致性没有任何保证。要按业务单号查幂等记录，用 `request_body` 里的内容去业务表查。 |

### 4.7 表：`m20_base_offline_queue`（离线队列表）

**用途**

弱网/无网条件下在客户端产生的写操作，先落到本表排队，恢复网络后按序重放。**由 M20-01 首建，M20-03（护理）、M20-06（视光销售）、M20-07（随访）是只读方与业务实现方，不得自建离线队列表**（数据结构汇总 §1.3）。

**这张表是 M20 里唯一「会替用户做决定」的表，所以它的每一条规则都是往保守方向写的**：

离线期间客户端把「给 3 床打 A 药」排进了队列。护士离线时医嘱被医生停用了。恢复网络后，如果系统「聪明地」帮她重放，就等于**执行了一次已停用的医嘱**——这是护理不良事件上报里最典型的一类来源。所以本表的设计原则是：

> **宁可让护士回到护士站手工处理一次，也不允许系统替她判断「这条医嘱应该还能执行」。**

由此推出三条硬规则：① **`CONFLICT` 没有任何自动解决路径**（不自动覆盖、不自动丢弃、不自动重试）；② **重放前必须先做版本与状态校验，校验不通过直接进 `CONFLICT`，业务处理器根本不会被调用**；③ **`FAILED` 必须有一个「人工放弃」的出口**，否则失败项永远悬着。

**写入方：** 客户端经 M20-01 离线队列接口写入；M20-01 重放器更新状态。
**只读方：** M20-03 / M20-06 / M20-07 读取待重放项、实现各自的重放业务处理器。

**分区策略**

本表**不分区**。离线队列是滚动表：稳态约 3,000 行/日，`SYNCED` 项保留 7 天后由清理任务物理删除，`CONFLICT` / `ABANDONED` 保留 90 天（要留痕复盘）。**注意不能按 `created_at` 分区**：本表有两个唯一约束（`queue_no`、`(staff_id, idempotency_key)`），分区会让它们必须带上分区键，从而失去「一个人同一幂等键只能一条」的语义。

**设计说明**

| 编号 | 说明 |
|---|---|
| D-32 | **`CONFLICT` 三条 CHECK 是「正向蕴含」写法，不是「反向排除」**：`ck_m20_base_offline_queue_conflict`（CONFLICT ⇒ 必须有 reason）与 `ck_m20_base_offline_queue_reason_scope`（有 reason ⇒ 必须 CONFLICT）成对存在，形成双向互斥。只写前一条的话，一条 `SYNCED` 的队列项可以带着 `VERSION_CHANGED` 的 reason，看板统计就会出现「已同步的冲突」这种自相矛盾的行。 |
| D-33 | **`ABANDONED` 必须有 `resolved_by` 与 `resolved_at`**（`ck_m20_base_offline_queue_abandoned`）。这是本表最重要的一条：一个操作被「放弃」是需要有人签字的。没有签字人的放弃等于静默丢弃，而静默丢弃在护理场景里就是「护士以为做了、系统里没有」。**`ABANDONED` 是 `FAILED` 唯一出口**——若无此状态，失败项永远悬在 `FAILED`，队列只增不减、待办永远清不掉。 |
| D-34 | **`expected_version` 是必填语义（尽管列可为空，因为部分业务无版本号）**。有版本号的实体必须填：这是 `VERSION_CHANGED` 判定的唯一依据。**校验发生在业务处理器之外**——重放器先做五步判定，判定为冲突时**业务处理器根本没机会被调用**。把正确性放进唯一入口，而不是寄托在每个业务处理器都记得校验版本。 |
| D-35 | **`occurred_at` 与 `queued_at` 分开存**。只存一个时间会丢掉两类信息：客户端时钟可能被改（`occurred_at` 不可信，故不用于任何排序与超时判定），而 `queued_at` 是服务端时间可信但丢失了「护士实际什么时候做的」。业务语义（这条体温是 8 点量的）必须用 `occurred_at`，可观测性（这条在网络里漂了多久）必须用 `queued_at`。`ck_m20_base_offline_queue_time` 只拦明显不可能的情况（入队早于发生）。 |
| D-36 | **重试只有 5 次且指数退避，5 次后不是 `FAILED` 就是 `CONFLICT`**。`ck_m20_base_offline_queue_retry_need` 保证 `FAILED` 项要么还有下次重试时刻、要么已经用尽次数转人工。**无限重试是最坏的实现**：它让一个永远失败的操作在后台每 30 秒敲一次上游，上游的告警里全是这一条。 |
| D-37 | **本表不存「冲突处理结果」的最终业务数据**。人工应用后，动作是「调用业务处理器执行」+ 状态置 `SYNCED` + `resolve_note` 记说明，**不在本表留下业务结果副本**。留下副本就等于第二份业务数据，而它与业务表的一致性没有任何保证——这正是总纲 §1.4 红线要禁止的东西。 |

### 4.8 表：`m20_base_session_pref`（会话 UI 偏好表）

**设计说明**

| 编号 | 说明 |
|---|---|
| D-38 | **本表绝不存任何权限判定结果**。不存 `perm_codes`、不存 `data_scope`、不存 `is_mobile_user`。理由：权限是每请求实时算的（M02-04 `perm/check`），把结果缓到会话偏好里就变成「改权限不生效，要重新登录」。Redis 里那份 `m20:base:session:{staff_id}:{device_id}` 同理，**只存 UI 偏好**（共享规范 §14 原文）。 |

| D-40 | **`expire_at` 取「会话结束」与「空闲 1800 秒」中较早者**。与 Redis 里 `m20:base:session:*` 的 1800 秒 TTL 对齐，避免出现「Redis 里的偏好已过期、MySQL 里的还在」的分叉。**这里必须与 M02 的会话生命周期对齐**：M02-03 的会话空闲超时是 120 分钟（`SYS.SESSION.IDLE_TIMEOUT_MIN`），而 UI 偏好只需要 30 分钟——偏好丢了重设成本很低，而留太久会让「换班后下一个护士看到上一个护士的界面」。 |

### 4.9 表：`m20_base_audit_log`（基础配置与编排留痕表）

**用途**

记录 M20-01 管辖范围内所有**配置类变更**的留痕：移动端配置项改值、菜单增删改、页面编排调整、终端登记信息修改、版本灰度调整、离线队列的人工处置。约 8,000 行/年。

**这张表与 `m20_base_config` 的关系是「当前值 vs 变更历史」**：`m20_base_config` 只保留当前值，谁改的、改前是什么，全在本表。这也是 `m20_base_page_layout` 不需要单独建表的直接原因——编排的每一次调整都在这里有一条 `action_type='CONFIG_CHANGE'` 的记录，`before_value` / `after_value` 里存调整前后的完整 JSON。

**本表只增不改**：`REVOKE UPDATE, DELETE` + 不可变触发器双重强制（数据结构汇总 §3.2 的同一套做法）。理由：一张能被修改的留痕表不是留痕表，它只是「另一张可以被改的业务表」。

**写入方：** M20-01 全部写接口（在业务事务内写，与业务变更同生共死）。
**只读方：** M20-01 配置变更查询、M02-06 审计汇总（经 `POST /internal/v1/audit/record` 上报后的二次留痕）。

**分区策略**

本表**不分区**，约 8,000 行/年，三年约 2.4 万行。**但要求：归档保留期不少于 3 年，且不设计任何「到期自动销毁」逻辑**（数据结构汇总 §10）。如果将来行数增长到需要分区，**必须按月 `RANGE (occurred_at)` 分区并预建 `DEFAULT` 兜底分区**——无 DEFAULT 分区时，新月份首条 INSERT 会直接失败（`no partition of relation ... found for row`），而这张表的 INSERT 在业务事务里，**失败会连带把配置变更一起回滚**。

**设计说明**

| 编号 | 说明 |
|---|---|
| D-42 | **三层强制「只增不改」**：① `REVOKE UPDATE, DELETE` + `GRANT INSERT, SELECT`（权限层）；② 触发器 `trg_fn_m20_base_audit_log_immutable()` 抛 `AUDIT_LOG_IMMUTABLE`（数据库层，连超级用户误操作也拦）；③ Repository 只暴露 `insert` 方法（应用层，让人在写代码时就发现「没有改的方法」）。**只做其中一层都不够**：只做权限层，DBA 用超级用户就能改；只做触发器，写代码的人会以为「改失败了是 bug」。 |
| D-43 | **`before_value` / `after_value` 存完整快照，不存字段 diff**。存 diff 的问题是：读的人必须把整条链上所有 diff 按顺序重放才能知道某时刻的值，而链上任何一条缺失就永远算不出来。存完整快照每条记录都能独立读懂，代价只是多几 KB——这张表一年才 8,000 行。 |
| D-44 | **`operator_name` 冗余存姓名**。这不是反范式失误：留痕表要在三年后还能被人读懂，而职工表里的姓名那时可能已经改了两回。**留痕表可以且应该冗余，因为它的职责是「冻结当时的事实」**，与业务表「存最新值」的目标相反。 |
| D-45 | **与业务变更同一事务**。`INSERT m20_base_audit_log` 必须在配置变更的同一个事务里，业务回滚则留痕一起回滚。**「先改业务、再异步写留痕」是最坏的实现**：异步那一跳失败时，业务改了但没有留痕，而系统的自我认知是「一切正常」。宁可因为留痕写失败而整体失败（用户重试一次即可），也不要出现无痕的变更。 |
| D-46 | **`result='FAILED'` 也留痕**。成功率低的配置接口与「被人尝试改过但被拦截」是两件事，后者在安全审查里很关键（有人反复尝试开启灰度到 100%）。`fail_reason` 必填由 `ck_m20_base_audit_log_fail` 保证。 |

### 4.10 表：`m20_base_stat`（基础运行统计表）

**用途**

按日预聚合 M20-01 的运行指标：在线终端数、请求量、幂等命中数、离线队列入队与冲突数、降级次数。约 1,400 行/年（按 日 × 指标 聚合）。

**这张表存的是「M20 自己的运行事实」，不是业务指标**。它与 M22 的区别要写清楚：**M22 算的是业务指标（门诊人次、手术量），M20 的基础统计算的是「移动端这个通道本身健康不健康」**——请求量、冲突数、降级数。后者不进 M22 的指标中心，因为它们不是业务口径，而且它们的权威来源是监控系统（Prometheus）而不是业务库。本表存在的唯一理由是：**给「我自己的界面」提供查询，不依赖监控系统的留存期**。

**写入方：** M20-01 定时任务 `m20_base_stat_rollup`（每日 02:10 汇总前一日）。
**只读方：** M20-01 工作台、M20-08 消息中心（引用通道健康度做降级提示）。

**分区策略**

本表**不分区**，约 1,400 行/年（约 13 个指标 × 300 天），单机 PostgreSQL 完全可以承载。**不需要 DEFAULT 兜底分区，因为根本没有分区**——这条要写明确，避免后来人看到「统计表」就按经验加上月分区，然后忘了建 DEFAULT 分区，等到下个月第一天才发现。

**设计说明**

| 编号 | 说明 |
|---|---|
| D-47 | **`stat_value` 用 `NUMERIC(20,6)` 而不是 INTEGER**，即使 13 个指标里有 11 个是整数。理由：一旦这张表要加「平均时长」「下降率」这类指标，改列类型就是一次高危迁移；而统一类型让汇总 SQL 不需要按指标分支。**代价**是计数类指标要小心 `ROUND()`，见 D-48。 |
| D-48 | **计数类指标汇总后必须 `ROUND(SUM(...))` 取整**。`NUMERIC(20,6)` 存 400000 没问题，但若某个指标被误当比率算过（例如 `AVG` 而非 `SUM`），会得到 `1234.567891` 这种值——计数指标出现小数就是算错了。汇总任务对 `ONLINE_PEAK`/`REQUEST_TOTAL` 等整数指标统一 `ROUND()`，并在单元测试里断言结果为整数。 |
| D-49 | **`uk_m20_base_stat_key` 保证汇总任务可幂等重跑**。汇总用 `INSERT ... ON CONFLICT (stat_date, stat_metric, client_type) DO UPDATE`。为什么重要：**补数是常态**（上游数据晚到、任务失败重跑），没有唯一键的话重跑一次数据就翻倍，而翻倍的数据看起来完全正常。 |
| D-50 | **`data_quality='UNKNOWN'` 时必须写 `source_note`**（`ck_m20_base_stat_unknown`）。这一条与共享规范 §8A 的 `degraded` 是同一思路的本地化：**「不知道」是可以落库的状态，但必须写明为什么不知道**。汇总时若某指标当天上游全挂，写 `UNKNOWN` + 说明，而不是写 0——写 0 会让看板显示「今天没有人用移动端」。 |
| D-51 | **本表不是 M22 指标中心的来源**。M22 要的是业务指标，本表是通道健康度。**不把本表的数据发往 M22**，避免出现「移动端请求量」这种既不在业务口径里、也没有业务含义的数字混进管理驾驶舱。需要看这些数字的是信息科，用 M20-01 自己的工作台即可。 |

### 4.11 SQLAlchemy 2.0 模型定义

模型文件位置 `app/models/m20/base.py`。全部 9 张表一一对应，无遗漏。约定：

- 基类 `Base` 来自 `app.db.base`，`Mapped` 风格，类型注解与 DDL 逐列对应；
- 金额/比率/统计值一律 `Numeric`，**不使用 `Float`**；
- 时间列一律 `DateTime(timezone=True)`（对应 `TIMESTAMPTZ`）；
- 约束全部写在 `__table_args__` 里，元组最后一个元素是 `dict`（承载 `comment` 等表选项）；
- 跨模块引用（`staff_id` / `dept_id` / `patient_id` 等）**只建索引不建外键**；M20 内部表之间的外键用 `ForeignKey` 声明。

### 4.12 Pydantic Schema 定义

文件位置 `app/schemas/m20/base.py`，Pydantic V2 语法（`model_config = ConfigDict(...)`，不用 `class Config`）。

约定：

- **所有数值字段一律 `Decimal`，不用 `float`**——金额、比率、统计值在 JSON 里出现浮点误差是最难查的一类账不平；
- 时间字段 `datetime`，响应序列化带时区（共享规范 §2.4）；
- 每个出参都继承带四质量标记的基类（共享规范 §8A.2），**`degraded: false` 时四个字段也必须出现**；

| 枚举 | 取值 | 出现位置 | 说明 |

| `list_density` | `COMPACT` / `STANDARD` / `LOOSE` | `m20_base_session_pref.list_density` | 仅界面偏好 |

**状态机（离线队列，权威图形见 4.7 与详细设计 §3）**：

```
QUEUED ──开始同步──▶ SYNCING ──校验通过并执行成功──▶ SYNCED（终态）
SYNCING ──版本/状态校验失败──▶ CONFLICT（无自动出口，只能人工处置）
SYNCING ──执行抛错──▶ FAILED ──重试至上限──▶ 保持 FAILED，转人工
FAILED ──人工放弃──▶ ABANDONED（终态）
```

**这张图有两条不变式，必须同时成立**：① `CONFLICT` 的出边只有「人工处置」一种，**不存在任何自动迁移路径**；② `FAILED` 必须有 `ABANDONED` 这个出口，否则失败项永远悬着。

## 附录 F：文档维护约定

|---|---|

| 变更触发 | 新增/删除表、改动列类型、改动唯一约束或 CHECK → 必须同步更新第 1 章表清单、附录 A、附录 B 与详细设计第 4 章指引块中的表数量 |
