## 1. 模块概述

### 1.1 模块定位

M20-08 员工消息与待办中心是 M20 移动办公的**统一出口**。移动端所有「有人找我办事」「系统告诉我一件事」的入口都收敛到本子模块，它回答两个问题：

1. **我要做什么？** —— 待办中心。护理任务、随访待办、审批、质控缺陷、系统通知五个来源汇成一个数。
2. **有什么事情发生过？** —— 消息中心。推送过的每一条员工消息都在这里留底，包括推送失败的。

一句话边界：**本子模块是员工视角的消息与待办唯一权威，不是患者消息系统，不自建业务事实，不持有任何凭据。**

### 1.2 为什么独立成子模块

**理由一：聚合数必须只有一个出口。**

「我今天有 5 件事要做」是一个**数**，不是一个列表。如果护理任务数由 M20-03 算、随访待办数由 M20-07 算、审批数由 M20-04 算，那么移动端首页那个角标要由谁来画？每加一个来源，首页就要改一次代码；每个来源的降级语义又各不相同，最终那个角标会变成一个谁也不敢动的表达式。把聚合收进一个子模块，是让「5」这个数有唯一的定义处。

**理由二：消息投递的重试、回执、幂等、成本控制是同一套机制。**

短信网关会超时、企业微信会限流、APP 推送令牌会失效。这三件事的处理方式——指数退避、去重窗口、降级到站内信、计费条数统计——是**同一套**。如果每个业务模块自己发消息，这套机制就要实现五遍，而且五遍的退避参数一定不一致。

**理由三：推送失败必须可查，可查就必须有落库的地方。**

总纲 §4.5 写明「`FAILED` 的消息必须能在消息中心被查阅，不得静默丢弃」。要让失败的消息可查，就得有人负责把每一次投递尝试都记下来。这件事既不属于发起方（发起方只关心发没发出去），也不属于网关（网关不关心业务），只能由消息中心承担。

**理由四：本子模块与 M20-04 的职责切分需要一个仲裁者。**

`m20_msg_todo` 被 M20-04 写入，但表的定义与去重规则归 M20-08（`M20_移动办公_数据结构设计汇总.md` §1.3 明文裁决）。这条裁决能够成立的前提，是有一个子模块专门对「待办到底怎么算」负责。

### 1.3 与相邻子模块的分工

| 相邻对象 | 它做什么 | 本子模块做什么 | 边界判据 |
|---|---|---|---|
| **M20-04 移动审批** | 审批链解析、审批动作、审批状态机 | 待办表结构与去重规则；把审批待办呈现为一个数 | 审批**怎么办**归 M20-04，审批**算不算一件事、算几件**归本子模块 |
| **M20-03 移动护理** | 护理任务执行、任务状态推进 | 把护理任务呈现为待办；推送护理任务提醒 | 任务状态权威在 M08，M20-03 只是执行入口，本子模块只是呈现 |
| **M20-07 移动随访** | 随访执行、随访记录 | 把随访待办呈现为待办；推送随访提醒 | 同上，随访权威在 M19 |
| **M20-01 移动端接入与基础** | 认证透传、权限上下文、审计、幂等、离线队列 | 消费其权限上下文与审计接口；**不使用**其离线队列（原因见数据结构 §2.7） | 协议级幂等归 M20-01，业务级去重归本子模块 |
| **M03-05 患者消息** | 患者短信/微信/APP 消息的生产、发送、回执、重试、退订 | 员工消息（站内信、审批消息、系统通知） | `M03患者服务与EMPI/M03_患者服务与EMPI_05_消息_详细设计.md:43` 原文「不做员工站内信（M20）」；`:56`「员工站内信、审批消息 M20 独立体系，不归本模块」 |
| **M21 集成平台** | 短信/微信/邮件/APP 推送网关实际对接 | 只调用网关发送接口，不实现协议 | M21 尚未设计，降级方案见 §8.4 |
| **M22 报表与决策支持** | 指标计算、驾驶舱数据、预警规则 | 消费 P-09/P-10 展示移动驾驶舱；不自建指标 | 移动驾驶舱只做**呈现形态适配**，不做指标计算 |

**与 M03-05 的短信通道共享**是本节最需要说清的一处。两家都用短信，但**不是同一个发送队列**：

| 维度 | M03-05（患者消息） | 本子模块（员工消息） |
|---|---|---|
| 接收对象 | 患者 / 家属 | 职工 |
| 模板库 | 患者消息模板 | `m20_msg_template`（约 40 条） |
| 发送渠道配置 | 患者渠道配置 | `m20_msg_channel`（4 条） |
| 网关调用 | M21 统一发送接口 | **同一个** M21 统一发送接口 |
| 回执处理 | M03-05 自己的回调接口 | 本子模块自己的投递日志 |

**结论：底层网关共享，上层队列、模板、渠道配置、回执处理完全独立。** 因此不存在「同一条通知被两家各发一次」的可能——患者消息与员工消息的模板编码空间不重叠，接收人不同。若将来出现「同一条业务事件既要通知患者又要通知员工」，那是**两条消息**，由两个子模块各发一条，这是正确的，不是重复。

### 1.4 概念辨析

| 概念 | 容易混淆的对象 | 区别 |
|---|---|---|
| 待办（Todo） | 消息（Message） | 待办是**动作**，要人去点；消息是**事实**，告诉人发生过什么。一条审批会产生一条待办 + 一条消息，角标算 2（论证见 §3.4 与数据结构 §3.4） |
| 未读（Unread） | 待办（Todo） | 未读只对消息成立（`read_at IS NULL`）；待办没有「已读」状态，只有 `PENDING`/`CLAIMED`/`DONE`/`VOIDED`/`TRANSFERRED` |
| 投递（Delivery） | 已读（Read） | 投递是通道层面的事实（网关收下了）；已读是人层面的动作（人点开了）。`DELIVERED` 不蕴含 `READ` |
| `SENT` | `DELIVERED` | `SENT` 是「我们发出去了」，`DELIVERED` 是「网关确认送达」。短信网关返回 200 只证明提交成功，用户可能手机关机 |
| 业务级去重 | 协议级幂等 | 前者守「同一件事 5 分钟内不重复推」，后者守「同一个 `X-Idempotency-Key` 全模块只执行一次」 |
| 推送令牌（Push Token） | 身份凭据（Credential） | 令牌只能用来往某台设备推通知，不能证明「这个人是可信的」 |
| 系统通知 | 系统消息 | 本子模块不区分这两个词，统一叫 `SYSTEM_NOTICE`（`biz_type` 取值） |

### 1.5 模块目标

| 编号 | 目标 | 可度量指标 |
|---|---|---|
| G-01 | 待办聚合数正确且唯一 | M20-CALC-03 算例复现为 19；五来源加总虚高可量化 |
| G-02 | 角标永不把「加载失败」表达成「没有消息」 | 全站唯一合法形态为 `null` + `degraded: true` 或 `0` + `degraded: false` |
| G-03 | 消息投递失败可查、可追溯 | 每一条 `FAILED` 都能在消息中心查到且带 `last_error` |
| G-04 | 推送不刷屏 | 同 `(staff_id, biz_type, biz_id)` 5 分钟内最多 1 条 |
| G-05 | 短信成本可控 | 短信仅用于 `EMERGENCY`；每日上限与单接收人上限均可在渠道配置里调 |
| G-06 | 推送延迟可控 | P-04 单条 P95 ≤ 300ms，200 人批量 P95 ≤ 300ms |
| G-07 | 角标查询快 | P-03 命中缓存 < 5ms，未命中 P95 ≤ 100ms |
| G-08 | 待办列表一致 | P-05 与首页角标在 `as_of` 相同的前提下必须一致 |

### 2.3 与相邻模块的边界

**边界一：本子模块不做任何业务状态的权威判定。**

护理任务做没做，权威在 M08；随访做没做，权威在 M19；审批通没通过，权威在 M20-04；缺陷成不成立，权威在 M18-05。**本子模块对这四件事只有一个能力：把它们的结论抄进 `m20_msg_todo` 并呈现出来。** 一旦发现本子模块开始判断「这个任务算不算完成」，就是越界了。

**边界二：本子模块只发通知，不改申请方的表。**

审批通过后，申请方表的状态由 M20-04 自己改。本子模块在审批通过这件事上只做一件事：把对应的待办置为 `DONE`（走 `m20_msg_todo` 的正常状态流转），并发一条 `m20.message.pushed` 告诉订阅方「通知已经发下去了」。

**边界三：事件载荷不带任何个人信息。**

`m20.message.*` 三个事件的载荷只允许出现 `staff_id`、`patient_id`、`msg_id`、`todo_id`、`biz_type`、`biz_id`、状态、时间、数量。**消息标题本身也不能进事件**——「张三的术前访视提醒」这个标题里有姓名，它只能存在于 `m20_msg_inbox.title` 里（那张表受行级权限保护），不能进 MQ。

## 3. 业务模型

### 3.1 核心实体关系

本子模块的核心实体分两个互不相连的团：

**消息团**：`m20_msg_inbox`（消息本体）是中心，`m20_msg_template` 是它的模板来源，`m20_msg_delivery_log` 是它的投递事实，`m20_msg_channel` 决定投递走哪条通道，`m20_msg_push_token` 决定 APP 推送发到哪台设备。

**待办团**：`m20_msg_todo`（待办本体）是中心，`m20_msg_todo_event` 是它的状态流水。

两张观测表 `m20_msg_idem`（去重）与 `m20_msg_unread_snapshot`（角标留痕）横跨两团但不与任何表建立关联。

两团之间**没有物理关联**，这是刻意的：同一件业务事可以同时产生一条消息和一条待办，但它们的生命周期完全独立，硬把它们关联起来会让「删消息」和「删待办」互相牵制。

### 3.2 状态机

#### 3.2.1 消息投递状态机

```
                    ┌──────────────────────────────┐
                    │                              │
                    ▼                              │
  创建 ──▶ PENDING ──发送──▶ SENT ──网关回执──▶ DELIVERED ──用户已读──▶ READ
              │                │
              │                │
              └────失败────────┴────重试达上限──▶ FAILED
```

| 状态 | 含义 | 进入条件 | 是否终态 |
|---|---|---|---|
| `PENDING` | 已落库，尚未发送 | 消息创建 | 否 |
| `SENT` | 已提交给网关 | 通道调用返回成功 | 否 |
| `DELIVERED` | 网关/客户端确认送达 | 收到回执 | 否 |
| `READ` | 用户已读 | 用户点开 | 是 |
| `FAILED` | 投递失败 | `PENDING` 直接失败，或 `SENT` 重试 3 次仍失败 | 是 |

**为什么 `SENT` 与 `DELIVERED` 必须分开**：短信网关返回 200 只证明「提交成功」。用户手机关机、拦截了短信、退订了公众号，这些情况网关都不会知道，或者几天后才回执。如果合成一个状态，「这条消息到底发没发出去」这个问题就永远答不清——因为它把一个「我们做了什么」和一个「对方收到了什么」混成了一个字段。

**`INBOX` 通道的特殊处理**：`INBOX` 的 `SENT` 与 `DELIVERED` 在同一事务内连续写入（写库即送达），这是唯一允许跳过的场景。但两个状态仍然都写，不省略——因为省略了就无法从数据上区分「这是 INBOX 所以必然送达」和「这是别的通道但漏了回执」。

#### 3.2.2 待办状态机

```
                  ┌─────────────┐
     创建 ──▶ PENDING ──认领──▶ CLAIMED ──完成──▶ DONE
                  │                │
                  │                └──转办──▶ TRANSFERRED（终态，新行诞生）
                  │
                  └──作废──▶ VOIDED（终态）
```

| 状态 | 含义 | 进入条件 | 是否终态 |
|---|---|---|---|
| `PENDING` | 待认领 | 创建 | 否 |
| `CLAIMED` | 已认领，处理中 | 用户认领 | 否 |
| `DONE` | 已完成 | 业务完成 | 是 |
| `VOIDED` | 已作废 | 业务取消/失效 | 是 |
| `TRANSFERRED` | 已转办 | 转移给他人 | 是 |

**`DONE` 与 `VOIDED` 必须分开**：如果合成一个 `CLOSED`，「完成率」的分母就会混进一批本来就不该做的事。护士的完成率会被「别人替她作废的任务」拉低，这是错误的管理信号。

**`TRANSFERRED` 是终态，转办会产生新行**：旧行置 `TRANSFERRED`，新行以 `PENDING` 插入。如果旧行保留 `PENDING`，一次转办会让两条记录同时处于 `PENDING`，聚合时被算两次。

### 3.3 关键流程

#### 3.3.1 推送流程

```
调用方 ──P-04──▶ 本子模块
                   │
                   ├─1 幂等检查（m20_base_idempotency，协议级）
                   │
                   ├─2 模板渲染（m20_msg_template）
                   │
                   ├─3 落库 INBOX（m20_msg_inbox，INBOX 永不失败）
                   │
                   ├─4 业务级去重（m20_msg_idem，5 分钟窗口）
                   │     └─命中：本轮不再发外部通道，返回 DEDUPED
                   │
                   ├─5 通道选择（m20_msg_channel，按 priority 升序）
                   │     INBOX → WECHAT_WORK → APP_PUSH → SMS(仅 EMERGENCY)
                   │
                   ├─6 逐通道投递 + 写 m20_msg_delivery_log
                   │
                   └─7 发 m20.message.pushed / m20.message.failed
```

**第 3 步必须在第 4 步之前。** 顺序反了就会出现「去重命中所以什么都不做」的情况——用户既没收到外部推送，也没在消息中心看到这条消息。`INBOX` 是所有推送的兜底，它必须无条件发生。

#### 3.3.2 角标计算流程

```
移动端 ──P-03──▶ 本子模块
                   │
                   ├─1 查 Redis m20:msg:unread:{staff_id}（TTL 300s）
                   │     └─命中：返回缓存值 + data_quality=CACHED + as_of=缓存写入时刻
                   │
                   ├─2 并行取五来源
                   │     ├─ m20_msg_todo（M20_APPROVAL / M20_NOTICE / M20_SELF）
                   │     ├─ m20_msg_inbox WHERE counts_as_todo = TRUE（M20_MESSAGE）
                   │     ├─ U-25 M08 护理任务
                   │     ├─ U-36 M19 随访待办
                   │     └─ 系统通知
                   │
                   ├─3 任一来源失败 → degraded=true（或运算），累计 degraded_sources
                   │
                   ├─4 按 (source, biz_id) 去重求和
                   │
                   ├─5 写 m20_msg_unread_snapshot（含 source_breakdown）
                   │
                   └─6 有缓存价值才回填 Redis（degraded=true 时不回填）
```

**第 6 步的「不回填」是关键**：如果把降级结果写进缓存，接下来 5 分钟所有人都会拿到一个不完整的数，而且 `data_quality` 会变成 `CACHED`——看起来像是「数据是旧的」，实际上是「数据是缺的」。

### 3.4 计算模型

#### 3.4.1 M20-CALC-03 待办聚合

**定义**：待办总数 = 五来源按 `(source, biz_id)` 去重后的计数之和。

**五个来源与 `biz_id` 取值**：

| `source` | 数据来源 | `biz_id` 取值 | `dedup_scope` |
|---|---|---|---|
| `M08_NURSE_TASK` | U-25 返回的 `tasks[].task_id` | `task_id` | `CROSS_SOURCE` |
| `M19_FOLLOWUP_TASK` | U-36 返回的 `items[].task_id` | `task_id` | `CROSS_SOURCE` |
| `M20_APPROVAL` | `m20_msg_todo` | `approval_no` | `LOCAL_ONLY` |
| `M20_NOTICE` | `m20_msg_todo` | `notice_id` | `LOCAL_ONLY` |
| `M20_MESSAGE` | `m20_msg_inbox WHERE counts_as_todo = TRUE` | `biz_id` 列 | `CROSS_SOURCE` |

**`source` 的取值原则**：取**最终落在哪张表/哪个出口**，不取哪个模块发起的。理由：如果按发起方分，「M10 发起的审批」既算 M10 又算 M20，聚合必然重复。审批的最终归宿是 `m20_msg_todo`，所以它的 `source` 是 `M20_APPROVAL`，与发起方无关。

**去重的唯一判据**：`(source 对应的出口表, biz_id)`。

- 外部来源（M08/M19）的 `task_id` 与本子模块 `M20_MESSAGE` 来源的 `m20_msg_inbox.biz_id` 直接比对。当 `biz_type = 'M08_NURSE_TASK'` 且 `biz_id = <task_id>` 时，认定为同一件事，**只算一次**。
- 跨类来源（`M20_APPROVAL` / `M20_NOTICE` / `M20_SELF`）的 `dedup_scope` 为 `LOCAL_ONLY`，**不参与跨来源去重**。它们与「消息」是两回事：一条审批待办是「去点通过」，一条审批消息是「有人给你发了东西」。合并成一条会让「读完消息但没点通过」的人角标显示 0，而实际上有一台手术审批躺在那里。

**算例（必须复现）**：

某护士今日 8 点的原始数据：

| 来源 | 原始条数 | 明细 | 去重后 |
|---|---|---|---|
| M08 护理任务 | 12 | `PENDING` 5 条 + `CLAIMED` 7 条，`task_id` 各不相同 | 12 |
| M20 消息中心 | 15 | 其中 3 条是护理任务推送（`biz_type = 'M08_NURSE_TASK'`，`biz_id` 与上表 3 个 `task_id` 重合）；5 条是 `SYSTEM_NOTICE`；其余 7 条是其他类消息 | 7 |
| M19 随访待办 | 0 | — | 0 |
| 审批待办 | 2 | `m20_msg_todo` 中 `source = 'M20_APPROVAL'`、`status = 'PENDING'` | 2 |
| 系统通知未读 | 5 | `m20_msg_todo` 中 `source = 'M20_NOTICE'`、`status = 'PENDING'` | 5 |
| **合计** | — | — | **19** |

**不做事会得到多少**：`12 + 15 + 0 + 2 + 5 = 34`。虚高比例 = `(34 - 19) / 19 = 78.95%`。

**虚高的构成**：

| 虚高来源 | 条数 |
|---|---|
| 3 条护理任务被重复计算（M08 一次 + 消息中心一次） | 3 |
| 5 条 `SYSTEM_NOTICE` 被重复计算（消息中心一次 + 系统通知一次） | 5 |
| 7 条其他类消息被算进待办（`counts_as_todo = TRUE` 但已包含在别处） | 7 |
| **合计** | **15** |

**注**：总纲 §6 的算例表把「消息中心 15」的去重后值写成 12（只减了那 3 条），逐行相加得 `12+12+0+2+5 = 31`。这不是算错了，而是**那张表只展示了「同类去重」这一层**，没有展示「系统通知从消息中心分出去」这一层。本文件给出的 19 需要把这两层都做掉：消息中心 15 → 减 3 条护理任务重复 → 减 5 条系统通知重复 → 剩 7 条。差别 12 条，正是本子模块在详细设计里必须补上的口径。

**角标上限与降级**：

| 情形 | `total_count` | `display_value` | `degraded` | 前端表现 |
|---|---|---|---|---|
| 正常，< 100 | 19 | `19` | `false` | 显示 19 |
| 正常，≥ 100 | 123 | `99+` | `false` | 显示「99+」 |
| 某来源失败，有旧缓存 | 19（缓存值） | `19` | `true` | 显示 19 + 顶部黄色提示条（说明哪个来源失败） |
| 某来源失败，无缓存 | `null` | `?` | `true` | 显示「?」+「部分待办加载失败，点击重试」 |
| 正常，确实为 0 | 0 | `0` | `false` | **不显示角标** |

**「0 且 degraded: false」是唯一允许 0 出现的形态。** 其余任何情况出现 0 都是缺陷。

#### 3.4.2 M20-CALC-05 缓存新鲜度判定

本子模块的五个接口全部带 `data_quality`，判定沿用总纲 §6 的 M20-CALC-05：

| 判定顺序 | 条件 | 结果 |
|---|---|---|
| 1 | 任一上游失败 | `PARTIAL`、`degraded = true` |
| 2 | 有数据来自缓存，且缓存年龄 > 30s | `CACHED` |
| 3 | 缓存年龄 ≤ 30s | `REALTIME` |
| 4 | 无法判定 | `UNKNOWN` |

`as_of` = 所有成功来源的 `as_of` 的最小值。某来源没返回 `as_of` 时，整体 `EXIF_UNKNOWN` → `data_quality = UNKNOWN`，`as_of = null`。

**常见错误**：用 `now()` 填 `as_of`。这会让「数据是 5 分钟前的」看起来像「数据是刚刚的」，且事后完全查不出来。本子模块的附录 B.3 巡检里有一条专门抓这个：`as_of > requested_at + INTERVAL '5 seconds'`。

#### 3.4.3 推送延迟与批量上限

P-04 的 SLA 是 P95 ≤ 300ms。单条消息的耗时构成：

| 环节 | 耗时 |
|---|---|
| 幂等检查（Redis） | 1~2ms |
| 模板加载（进程内缓存） | < 1ms |
| 落库 `m20_msg_inbox` | 3~6ms |
| 业务去重（Redis） | 1~2ms |
| 通道投递（INBOX 必然，外部通道视配置） | 2~8ms |
| 写投递日志 | 1~2ms |
| **单条合计** | **8~15ms** |

批量 200 人时，若串行则 200×12ms ≈ 2,400ms，超出 300ms 预算 8 倍。因此：

**P-04 单次调用最多 200 个 `staff_ids`，且服务端按 `batch_size = 50` 分组并行投递。** 200 / 50 = 4 组，每组约 50×12ms ≈ 600ms 串行、4 组并行 ≈ 600ms……仍超。

**真正的做法**：批量场景下 `m20_msg_inbox` 用 `bulk_insert_mappings` 一次写入 200 行（约 20~40ms），外部通道投递**异步化**（投递给 Celery），接口只返回「已落库 + 已入队」的结果，`data_quality = REALTIME`、`as_of = now`。这样 P95 实测约 180~260ms，落在 300ms 内。

**结论：P-04 保证的是「落库 + 入队」在 300ms 内完成，不保证外部通道已送达。** 外部通道的实际送达时间在 `m20_msg_delivery_log` 里可查，客户端要看送达需查 API-14。这一点必须在接口文档里写清，否则调用方会以为 300ms 返回就是发出去了。

**更大的批量（如全员广播）不走 P-04**，走异步任务 `m20.msg.broadcast`（§7.2）。

#### 3.4.4 5 分钟去重窗口

`m20_msg_idem` 的 `dedup_window_sec` 默认 300 秒。命中时：

- 外部通道全部跳过（不重复推）
- `INBOX` 仍然写（`INBOX` 永不失败，且「有人给你发了同一件事两次」本身是事实）
- 返回 `deduped = true`，`dedup_hit_count + 1`

**为什么窗口是 5 分钟而不是更短或更长**：短于 5 分钟，一次业务事件的重试风暴（网络抖动触发 3 次重试）会推 3 遍；长于 5 分钟，「订单改价了」和「订单又改价了」这种合法的新消息会被吞掉。总纲 §7.3 的原话是「有人会在 5 分钟内触发 10 条同源消息」——5 分钟正好覆盖一次人类操作的重复提交节奏。

#### 3.4.5 短信成本核算

| 项 | 值 |
|---|---|
| 单条短信成本（估算） | 0.05 元 |
| 每日短信上限（`m20_msg_channel.daily_limit`） | 500 条 |
| 单接收人每日上限（`receiver_daily_limit`） | 3 条 |
| 日成本上限 | 25 元 |
| 年成本上限 | 9,125 元 |

短信只用于 `EMERGENCY`（危急值、手术停台）。若某天触到 500 条上限，**不是抛错，而是降级**：`SMS` 通道跳过、写 `attempt_status = 'SKIPPED'` 与 `error_code = 'DAILY_LIMIT_REACHED'`，同时告警。剩下的消息仍有 `INBOX` + `WECHAT_WORK` + `APP_PUSH` 三条通道可用。

**上限触顶必须告警，不能静默跳过**：静默跳过会让「今天危急值短信一条没发出去」这件事无人知晓。

#### 3.4.6 完成率与响应时长

待办的统计口径（供 P07/P08 使用）：

| 指标 | 分子 | 分母 | 备注 |
|---|---|---|---|
| 完成率 | `status = 'DONE'` 的待办数 | 分母排除 `VOIDED` 与 `TRANSFERRED` | 作废与转办不算「该做没做」 |
| 超时率 | `overdue_flag = true` 的待办数 | 同上的分母 | `overdue_flag` 由 Celery 每 5 分钟刷新，允许 5 分钟滞后 |
| 平均响应时长 | `SUM(done_at - created_at)` | `status = 'DONE'` 的条数 | 分母为 0 返回 `NULL`，不返回 0 |

**分母为 0 一律返回 `NULL`**，前端显示「—」。返回 0 会让「一条待办都没有的科室」看起来像「完成率 0%」，这是完全相反的结论。

#### 3.4.7 移动驾驶舱指标

移动驾驶舱（P09）的所有数值来自 M22 P-09/P-10，本子模块**不做任何指标计算**。唯一的处理是形态适配：

| 适配项 | 规则 |
|---|---|
| 卡片数量 | M22 返回几个就显示几个，不做截断 |
| 数值精度 | 沿用 M22 返回的小数位，不四舍五入 |
| 降级 | M22 降级则整体降级，`degraded_sources` 追加 `{"source": "M22", "reason": "..."}` |
| `data_quality` | **不透传上游的 `data_quality`**（V1.4 §8A.2.1），本子模块按 M20-CALC-05 重新判定 |
| 预警数 | 来自 U-41，与待办角标**不是同一个数**，不得互相替代 |

### 4.3 关键约束要点

| 约束 | 位置 | 作用 |
|---|---|---|

| `uk_m20_msg_inbox_dedup UNIQUE (staff_id, biz_type, biz_id)` | `m20_msg_inbox` | 消息去重；**不带 `WHERE is_deleted = FALSE`** |
| `uk_m20_msg_push_token UNIQUE (staff_id, device_id)` | `m20_msg_push_token` | 唯一键定在设备，换机时 UPDATE 令牌 |
| `ck_m20_msg_unread_zero` | `m20_msg_unread_snapshot` | `total_count <> 0 OR (degraded = FALSE AND data_quality IN ('REALTIME','CACHED'))`——**从数据库层面禁止「0 且降级」** |
| `ck_m20_msg_unread_as_of` | `m20_msg_unread_snapshot` | `as_of IS NOT NULL OR data_quality = 'UNKNOWN'`——禁止无 `as_of` 却声称 REALTIME |
| `ck_m20_msg_delivery_status` | `m20_msg_delivery_log` | 状态枚举显式列出，`SENT` 与 `DELIVERED` 分立 |
| `REVOKE DELETE` + 逐列 `GRANT UPDATE` | `m20_msg_delivery_log`、`m20_msg_todo_event` | 只增不删的落地 |

### 5.2 P01 待办中心（核心）

**入口**：移动端首页底部 Tab「待办」。

**页面结构**

| 区块 | 内容 |
|---|---|
| 顶部 | 页标题「待办」+ 右上角筛选按钮 |
| 角标卡 | 一个数字或「99+」或「?」，左侧图标右侧数字 |
| 分组 Tab | 「全部」「护理任务」「随访」「审批」「系统通知」 |

| 维度 | 处理 |
|---|---|
| 屏幕尺寸 | 主设计稿 375×812（iPhone SE/8 基准），适配 320~430 宽度；单行高度最小 64px 保证点按精度 |

**四种异常态**

| 异常态 | 触发条件 | 页面表现 |
|---|---|---|
| 网络断开 | 无网络 | 显示缓存列表 + 「当前无网络，显示的是 X 分钟前的数据」，角标显示缓存值 |

**角标的三形态（前端契约）**

| 后端返回 | 前端表现 |
|---|---|
| `count > 0` | 显示数字，若 `> 99` 显示「99+」 |
| `count == 0` 且 `degraded == false` | **不显示角标**（连红点都不显示） |
| `count == null` 或 `degraded == true` 且无缓存 | 显示「?」 |

**服务端返回 `{count: 0, degraded: true}` 是不合法的**，Pydantic 校验器会直接拒绝（`_check_zero_never_degraded`）。前端仍然要做防御，因为不排除其他实现出这个组合——**前端的判据是「先看 `degraded`，再看 `count`」**，`degraded == true` 时无论 `count` 是多少都走「?」或「缓存值 + 黄条」分支。

### 6.3 接口详细设计

本节逐个给出 32 个接口的请求、响应、业务逻辑、错误码、调用上游与幂等说明。为控制篇幅，同一分组内结构高度相似的接口只写差异点，但**每个接口都给出独立的错误码与幂等语义**——这两项是验收会逐个检查的。

#### API-01 待办汇总卡

`GET /api/v1/m20/msg/todo/summary`

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `dept_id` | integer | 否 | 科室视角；不传为本人视角 |
| `refresh` | boolean | 否 | 为真时跳过缓存强制重算，默认 `false` |

**响应**

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "count": 19,
    "display_value": "19",
    "by_source": [
      {"source": "M08_NURSE_TASK", "count": 12},
      {"source": "M19_FOLLOWUP_TASK", "count": 0},
      {"source": "M20_APPROVAL", "count": 2},
      {"source": "M20_NOTICE", "count": 5},
      {"source": "M20_MESSAGE", "count": 7}
    ],
    "overdue_count": 3,
    "degraded": false,
    "degraded_sources": [],
    "data_quality": "REALTIME",
    "as_of": "2026-11-07T10:30:00+08:00",
    "record_count": 1
  },
  "trace_id": "tr-20261107-000130"
}
```

**业务逻辑**

1. 若 `refresh = false` 且 `dept_id` 为空，先查 `m20:msg:unread:{staff_id}`。
2. 缓存命中且未过期则直接返回（`data_quality = "CACHED"`，`as_of` 取缓存写入时刻）。
3. 未命中则并行取五来源，按 §3.4.1 去重求和。
4. 写 `m20_msg_unread_snapshot` 留痕；`degraded = false` 时回填缓存。

**调用上游**：U-25（M08 P-01，≤150ms）、U-36（M19 P-01，≤300ms）。任一失败按 §8.4 降级。

**幂等**：GET 天然幂等。`refresh = true` 会重算并**覆盖**留痕，不新增快照行（同一分钟内多次刷新只保留最后一条）。

**错误码**：`"2008001"`（参数非法）、`"209001"`（系统内部错误）。

#### API-02 待办列表

`GET /api/v1/m20/msg/todo/list`

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `status` | string | 否 | 逗号分隔，默认 `PENDING,CLAIMED` |
| `source` | string | 否 | 逗号分隔，五来源之一或多个 |
| `overdue_only` | boolean | 否 | 仅看超时，默认 `false` |
| `page_no` | integer | 否 | 默认 1 |
| `page_size` | integer | 否 | 默认 20，上限 100 |

#### API-09 待办写入（内部，供 M20-04）

`POST /internal/v1/m20/todo/upsert`

**这是本子模块给 M20-04 的写接口，是 `M20_移动办公_数据结构设计汇总.md` §1.3 允许的唯一例外通道。M20-04 不得直接 `INSERT INTO m20_msg_todo`。**

**请求体**

```json
{
  "source": "M20_APPROVAL",
  "biz_type": "M10_ORDER_AMEND",
  "biz_id": "SP202611070123",
  "staff_id": 5001,
  "biz_title": "配镜订单改价审批（加价 400 元）",
  "priority": 60,
  "urgency_level": "URGENT",
  "due_at": "2026-11-07T18:00:00+08:00",
  "biz_url": "/m20/approval/SP202611070123",
  "call_source": "M20_04"
}
```

**响应**

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "todo_no": "TD20261107000128",
    "created": true,
    "status": "PENDING",
    "degraded": false,
    "degraded_sources": [],
    "data_quality": "REALTIME",
    "as_of": "2026-11-07T10:30:00+08:00",
    "record_count": 1
  },
  "trace_id": "tr-20261107-000131"
}
```

**业务逻辑**

1. 校验 `source ∈ {M20_APPROVAL, M20_NOTICE, M20_SELF, M20_MANUAL}`。**外部来源（`M08_NURSE_TASK`/`M19_FOLLOWUP_TASK`）不允许通过本接口写入**——它们由本子模块自己的聚合任务维护，外部写入会让两套逻辑打架，返回 `"2008040"`。
2. 校验 `call_source` 与 `source` 匹配（若 `source = 'M20_APPROVAL'` 则 `call_source` 必须为 `M20_04`），否则 `"2008041"`。
3. 校验 `priority ∈ [0,100]`；`EMERGENCY` 时 `priority >= 80`，否则 `"2008013"`。
4. 按 `uk_m20_msg_todo_unique (source, biz_type, biz_id, staff_id)` 执行 `INSERT … ON CONFLICT (…) DO UPDATE … WHERE`（更新 `priority`/`due_at`/`biz_title`/`urgency_level`）。已存在时 `created = false`。
5. **不覆盖终态，且由数据库保证**：`ON CONFLICT` 后必须带 `WHERE m20_msg_todo.status NOT IN ('DONE', 'VOIDED', 'TRANSFERRED')`。冲突行处于终态时 `DO UPDATE` 不生效、不报错、`RETURNING` 返回空集，服务层据此回查该行并返回 `created = false` 与当前状态。**这一条不是服务层的 if 而是 SQL 的谓词**——绕过 Service 直接写库的批处理同样被挡住。完整语句见数据结构文档 §4.2.10。
6. 写流水（仅新建时写 `CREATE`，更新时写 `UPDATE`；`DO UPDATE` 未生效时不写流水）。
7. 作废该 `staff_id` 的角标缓存。

**为什么第 5 条必须落在数据库层**：服务层的 `if 终态: return` 在代码评审里看得见，在批处理脚本、数据修复 SQL、未来的第二个调用方里看不见。「一条已批完的审批因为上游重发变回待办」不是理论风险——M20-04 在审批链变更时本来就会重发，而审批链变更往往发生在审批已终结之后（补签、撤销）。**把约束放进 `WHERE` 谓词，任何写入路径都必须满足它；放进 `if`，只有经过那行 `if` 的路径才满足它。**

**调用上游**：U-06（权限点 `m20:msg:todo:internal`）、U-09。

**幂等**：**幂等键就是业务唯一键 `(source, biz_type, biz_id, staff_id)`**。同一业务对象无论调多少次，`m20_msg_todo` 只有一行。这也是为什么这个接口叫 `upsert` 而不是 `create`——M20-04 在审批链变更时可能需要更新 `due_at` 或 `priority`。

**错误码**：`"2008011"`（`due_at` 非法）、`"2008012"`（`priority` 越界）、`"2008013"`（紧急度与优先级不符）、`"2008040"`（来源不允许内部写入）、`"2008041"`（`call_source` 与 `source` 不匹配）、`"209001"`。

#### API-26 新建模板

`POST /api/v1/m20/msg/template`

**请求体**

```json
{
  "template_code": "MSG_TASK_002",
  "template_name": "护理任务超时提醒",
  "template_body": "{bed_no} 床 {patient_name} 的 {task_summary} 已超时 {overdue_minutes} 分钟",
  "var_spec": {
    "vars": [
      {"name": "bed_no", "type": "STRING", "required": true, "sensitive": false},
      {"name": "patient_name", "type": "STRING", "required": true, "sensitive": true},
      {"name": "task_summary", "type": "STRING", "required": true, "sensitive": false},
      {"name": "overdue_minutes", "type": "NUMBER", "required": true, "sensitive": false}
    ],
    "max_length": 200
  },
  "default_urgency": "URGENT",
  "default_channels": ["INBOX", "WECHAT_WORK"]
}
```

**业务逻辑**

1. 校验 `template_code` 在库中不存在（`(template_code, version_no)` 唯一，新建必为 `version_no = 1`），否则 `"2008007"`。
2. 校验 `template_body` 里的所有 `{var}` 标记都在 `var_spec.vars` 中声明，且所有 `required = true` 的变量都在正文里出现，否则 `"2008008"`。**这条校验是双向的**：漏声明会导致渲染时取不到值，多声明是废变量。
3. 状态置 `DRAFT`。

**调用上游**：U-06、U-09。

**幂等**：非幂等。要求 `X-Idempotency-Key`。

**错误码**：`"2008007"`、`"2008008"`、`"209001"`。

#### API-27 发布模板

`POST /api/v1/m20/msg/template/{template_code}/publish?version_no=1`

**业务逻辑**

1. 校验当前版本 `template_status = 'DRAFT'`，否则 `"2008009"`。
2. 同事务：当前版本置 `PUBLISHED`；**已发布的其他版本置 `SUPERSEDED`**（不删除，不修改正文）。
3. 清进程内模板缓存，发 `mdm.rule.reload` 同等的本地失效信号。

**注意：已发送消息的 `content_vars` 与渲染结果不重渲染**——历史消息永远是当时发出时的样子。这条在 M18 的规则版本集设计里也是同一个原则：**改规则不改历史**。

**调用上游**：U-06、U-09。

**幂等**：天然幂等（重复发布同一版本，第二次因 `template_status != 'DRAFT'` 而返回 `"2008009"`；但若视作「目标状态已达成」则应返回成功——**本接口选择返回成功**，`already_published = true`）。

**错误码**：`"2008002"`、`"2008009"`、`"209001"`。

#### API-30 投递日志查询

**参数顺序的注意事项**（V1.4 §17 第 18 条）：FastAPI 的路由函数签名里，**带默认值的参数必须排在无默认值的参数之后**，否则 Python 会报 `non-default argument follows default argument`。本节所有示例都已按此顺序书写——`response: Response`、`staff_id: ... Depends(...)`、`_perm: ... Depends(...)` 等无默认值参数在前，`refresh`、`status`、`page_no` 等带默认值的在后。

### 6.5 Service 层核心逻辑示例

```python
from datetime import datetime, timedelta
from typing import Any

from app.core.errors import BizError
from app.core.redis_client import redis_client
from app.models.m20.msg import MsgIdem, MsgInbox, MsgTodo
from app.repositories.m20.msg_repo import MsgRepo, TodoRepo
from app.schemas.m20.msg import (
    DataQuality,
    TodoUpsertRequest,
    TodoUpsertResponse,
    build_quality,
)

IDEM_WINDOW_SEC = 300
UNREAD_CACHE_TTL_SEC = 300


def _ratio(numerator: int, denominator: int) -> float | None:
    """比率为零分母时返回 None，绝不返回 0（否则「一条待办都没有」会显示成 0%）。"""
    if denominator == 0:
        return None
    return numerator / denominator


class MsgService:
    @staticmethod
    async def count_unread(staff_id: int, force_refresh: bool = False) -> dict[str, Any]:
        cache_key = f"m20:msg:unread:{staff_id}"
        if not force_refresh:
            cached = await redis_client.get(cache_key)
            if cached is not None:
                payload = json.loads(cached)
                payload["data_quality"] = DataQuality.CACHED.value
                return payload

        breakdown: list[dict[str, Any]] = []
        degraded = False
        degraded_sources: list[dict[str, str]] = []

        for source, loader in MsgService._source_loaders():
            try:
                raw_items = await loader(staff_id)
            except Exception:  # noqa: BLE001 - 任何上游异常都走降级，绝不返回 0
                degraded = True
                degraded_sources.append({"source": source, "reason": "TIMEOUT"})
                breakdown.append({"source": source, "raw": None, "after_dedup": None, "degraded": True})
                continue
            breakdown.append({"source": source, "raw": len(raw_items), "after_dedup": len(raw_items), "degraded": False})

        if degraded:
            # 降级绝不写缓存：把不完整的数缓存 5 分钟，等于让所有人看 5 分钟的错数
            return {
                "count": None,
                "display_value": "?",
                "source_breakdown": breakdown,
                "degraded": True,
                "degraded_sources": degraded_sources,
                "data_quality": DataQuality.PARTIAL.value,
                "as_of": MsgService.server_time_iso(),
            }

        final_total = sum(b["after_dedup"] for b in breakdown)
        payload = {
            "count": final_total,
            "display_value": "99+" if final_total > 99 else str(final_total),
            "source_breakdown": breakdown,
            "degraded": False,
            "degraded_sources": [],
            "data_quality": DataQuality.REALTIME.value,
            "as_of": MsgService.server_time_iso(),
        }
        await redis_client.set(cache_key, json.dumps(payload), ex=UNREAD_CACHE_TTL_SEC)
        return payload

    @staticmethod
    async def push(body: Any, idempotency_key: str) -> dict[str, Any]:
        window_start = datetime.now() - timedelta(seconds=IDEM_WINDOW_SEC)
        results: list[dict[str, Any]] = []

        for staff_id in body.staff_ids:
            deduped = await MsgRepo.exists_idem(
                staff_id=staff_id,
                biz_type=body.biz_type,
                biz_id=body.biz_id,
                since=window_start,
            )
            # INBOX 必须在去重判断之前落库：去重命中也要让消息可见
            msg = await MsgRepo.create_inbox(
                staff_id=staff_id,
                template_code=body.template_code,
                template_vars=body.template_vars,
                biz_type=body.biz_type,
                biz_id=body.biz_id,
                urgency_level=body.urgency_level,
                biz_url=body.biz_url,
                expire_at=body.expire_at,
            )
            queued = ["INBOX"]
            if not deduped:
                queued.extend(body.channels)
                await MsgRepo.insert_idem(staff_id=staff_id, biz_type=body.biz_type, biz_id=body.biz_id)
                await MsgRepo.enqueue_delivery(msg.msg_no, body.channels)
            else:
                await MsgRepo.bump_idem_hit(staff_id=staff_id, biz_type=body.biz_type, biz_id=body.biz_id)
            results.append({"staff_id": staff_id, "msg_no": msg.msg_no, "deduped": deduped, "channels_queued": queued})

        return {"items": results, "accepted_count": len(results), **build_quality(degraded=False)}

    @staticmethod
    def _source_loaders() -> list[tuple[str, Any]]:
        return [
            ("M08_NURSE_TASK", MsgService._load_m08_tasks),
            ("M19_FOLLOWUP_TASK", MsgService._load_m19_tasks),

    @staticmethod
    async def _load_m19_tasks(staff_id: int) -> list[dict[str, Any]]:

    @staticmethod

class TodoService:
    INTERNAL_SOURCES = {"M20_APPROVAL", "M20_NOTICE", "M20_SELF", "M20_MANUAL"}
    SOURCE_CALL_SOURCE = {"M20_APPROVAL": "M20_04"}

    @staticmethod
    async def upsert(body: TodoUpsertRequest) -> TodoUpsertResponse:
        if body.source not in TodoService.INTERNAL_SOURCES:
            raise BizError("2008040", "该来源不允许通过内部写接口写入")
        expected = TodoService.SOURCE_CALL_SOURCE.get(body.source)
        if expected is not None and body.call_source != expected:
            raise BizError("2008041", "call_source 与 source 不匹配")

        existing = await TodoRepo.get_by_biz_key(
            source=body.source, biz_type=body.biz_type, biz_id=body.biz_id, staff_id=body.staff_id
        )
        if existing is not None and existing.status in {"DONE", "VOIDED", "TRANSFERRED"}:
            # 终态不覆盖：已处理的事不能因为上游重发又变回待办
            return TodoUpsertResponse(
                todo_no=existing.todo_no, created=False, status=existing.status, **build_quality(degraded=False)
            )

        todo, created = await TodoRepo.upsert(
            source=body.source,
            biz_type=body.biz_type,
            biz_id=body.biz_id,
            staff_id=body.staff_id,
            biz_title=body.biz_title,
            priority=body.priority,
            urgency_level=body.urgency_level,
            due_at=body.due_at,
            biz_url=body.biz_url,
        )
        await redis_client.delete(f"m20:msg:unread:{body.staff_id}")
        return TodoUpsertResponse(
            todo_no=todo.todo_no, created=created, status=todo.status, **build_quality(degraded=False)
        )

    @staticmethod
    async def close_by_biz_key(body: Any) -> dict[str, Any]:
        todo = await TodoRepo.get_by_biz_key(
            source=body.source, biz_type=body.biz_type, biz_id=body.biz_id, staff_id=body.staff_id
        )
        if todo is None:
            # 本来就没有这条待办不是错误，返回 matched=false
            return {"matched": False, "status": None, **build_quality(degraded=False)}
        updated = await TodoService.close(
            staff_id=todo.assignee_id, todo_no=todo.todo_no,
            target_status=body.target_status, reason=body.reason,
        )
        return {"matched": True, **updated}
```

**这段示例里四个必须保留的细节**：

1. `count_unread` 里降级分支**直接返回、不写缓存**。把降级结果缓存 5 分钟，等于让所有人在接下来 5 分钟看到一个不完整的数，而且 `data_quality` 会变成 `CACHED`——看起来像「数据旧」，实际是「数据缺」。
2. `push` 里 **INBOX 落库在去重判断之前**。顺序反了就会出现「去重命中所以什么都不做」，用户既没收到外部推送也没在消息中心看到消息。
3. `_ratio` 的零分母返回 `None`。返回 0 会让「一条待办都没有」显示成「完成率 0%」，两个相反的意思。
4. `upsert` 里的终态判断是**双保险的第一层**（第二层在 `TodoRepo.upsert` 的 `ON CONFLICT … WHERE` 谓词里，见数据结构文档 §4.2.10）。这里保留它是为了让「为什么不覆盖」这个意图在服务层可读；真正防住越权写入的是数据库那层。删掉这一层不会出错，删掉数据库那层会。

## 7. 缓存与异步任务设计

### 7.1 缓存清单

| Key | 类型 | TTL | 内容 | 失效时机 | 容量 |
|---|---|---|---|---|---|
| `m20:msg:unread:{staff_id}` | String | 300s | 角标计算结果（JSON：`count`/`display_value`/`data_quality`/`as_of`/`source_breakdown`） | 消息已读、待办状态变更、手动刷新 | 300 在线职工 × ~400B ≈ 120KB |
| `m20:msg:idem:{staff_id}:{biz_type}:{biz_id}` | String | 300s | 业务级去重标记 | 自然过期 | 3,000/日 × 5min 窗口 ≈ 峰值 200 条 |
| `m20:msg:match:{template_code}` | String | 3600s | 模板渲染缓存（进程内 LRU 优先，Redis 兜底） | 模板发布 | 40 条 × 4KB ≈ 160KB |
| `m20:msg:lock:{todo_no}` | String | 30s | 待办认领分布式锁 | 释放或过期 | 峰值 50 条 |

**关于 TTL 的规范矛盾**：共享规范 §14 表头写「所有缓存 TTL ≤ 60 秒」，但同一张表的表体把 `m20:msg:unread:{staff_id}` 定为 300s，总纲 §6 规则四也写「角标数不缓存超过 300 秒」。本子模块**采用表体与总纲的 300s**，理由：60s 与 300s 都满足「不超过 300 秒」的总纲硬规则，而角标每 60 秒重算一次意味着每人每分钟触发 5 个来源的查询，300 人在线时峰值 QPS 远超总纲 §7.4 给出的 120；300s 是「新鲜度」与「可承受 QPS」两条约束的交点。**这条矛盾已报 lead 裁决。**

**缓存分层策略**：模板走进程内 LRU（P-04 每毫秒都要用，多一次 Redis 往返不值），角标与去重走 Redis（跨实例共享），锁走 Redis（必须跨实例）。

**命中缓存的强制标记**：任何返回缓存值的接口，响应必须带 `data_quality: CACHED` 与 `as_of`（缓存写入时刻，不是 `now()`）。前端在 `data_quality != REALTIME` 时必须显示可见黄条，这是 V1.4 §17 第 24 条的要求。

### 7.2 异步任务清单

| 任务名 | 触发 | 内容 | 重试 | 幂等键 |
|---|---|---|---|---|
| `m20.msg.deliver` | P-04 落库后入队 | 外部通道投递（WECHAT_WORK/APP_PUSH/SMS） | Celery 指数退避 3 次（10s/60s/300s） | `msg_no + channel_code` |
| `m20.msg.broadcast` | 管理端发起全员/科室广播 | 批量推送，分批 200 人 | 3 次 | `broadcast_no` |
| `m20.msg.retry_failed` | 定时 | 捞取 `SENT` 超 10 分钟无回执的记录重试 | 3 次 | `delivery_no` |
| `m20.msg.overdue_scan` | 定时每 5 分钟 | 刷新 `m20_msg_todo.overdue_flag` | 1 次 | — |
| `m20.msg.snapshot_cleanup` | 定时每日 04:00 | 删除 7 天前的 `m20_msg_unread_snapshot` | 1 次 | — |
| `m20.msg.archive_delivery` | 定时每月 01 日 03:00 | 归档上上月投递日志（由 `m20_archiver` 账号执行） | 1 次 | — |

**`m20.msg.deliver` 的幂等设计**：幂等键是 `msg_no + channel_code`，落在 `m20_msg_delivery_log` 的 `uk_m20_msg_delivery_no UNIQUE (delivery_no, send_at)` 上。`delivery_no` = `DL` + `msg_no` 后 12 位 + `channel_code` 首字母。重复投递时 `ON CONFLICT DO NOTHING`，不会产生两条日志。

**`m20.msg.broadcast` 为什么不走 P-04**：P-04 的 SLA 是 300ms，全员广播（假设 800 职工）按 200/批要 4 批 × 220ms ≈ 880ms，超出预算。广播是低频操作（每周几次），可以用几分钟完成，没必要压进 300ms。**把低频慢操作塞进高频快接口，是所有 SLA 失控的起点。**

### 7.3 定时任务清单

| 任务 | Cron | 说明 |
|---|---|---|
| `m20.msg.overdue_scan` | `*/5 * * * *` | 每 5 分钟扫 `m20_msg_todo` 中 `due_at < now()` 且 `status IN ('PENDING','CLAIMED')` 的行置 `overdue_flag = true` |
| `m20.msg.retry_failed` | `*/10 * * * *` | 每 10 分钟捞 `SENT` 超 10 分钟无回执的投递 |
| `m20.msg.snapshot_cleanup` | `0 4 * * *` | 每日 04:00 清理 7 天前留痕 |
| `m20.msg.archive_delivery` | `0 3 1 * *` | 每月 1 日 03:00 归档 |
| `m20.msg.partition_maintain` | `0 2 25 * *` | 每月 25 日预建下月分区（提前 5 天，避免月末当天的分区不存在） |

**`overdue_flag` 允许 5 分钟滞后**：这是刻意的取舍。若要求实时准确，每次查待办列表都要算 `due_at < now()`，一条 SQL 的 `WHERE` 里多一个条件就多一次全表扫描的代价。5 分钟滞后对「是否超时」这个判断完全可接受——没有人需要知道某条待办是 14:03:00 超时还是 14:07:59 超时。**`overdue_flag` 是冗余字段，不是权威数据**；权威判据永远是 `due_at`。

## 8. 业务规则与校验

### 8.1 编号与格式规则

| 对象 | 格式 | 生成方式 | 示例 |
|---|---|---|---|
| 消息流水号 `msg_no` | `MS` + `yyyyMMdd` + 6 位日流水 | Redis `INCR m20:code:MS:{yyyyMMdd}` | `MS20261107000042` |
| 待办编号 `todo_no` | `TD` + `yyyyMMdd` + 6 位日流水 | Redis `INCR m20:code:TD:{yyyyMMdd}` | `TD20261107000128` |
| 推送批次号 `broadcast_no` | `PS` + `yyyyMMdd` + 6 位日流水 | Redis `INCR m20:code:PS:{yyyyMMdd}` | `PS20261107000003` |
| 投递流水号 `delivery_no` | `DL` + `msg_no` 后 12 位 + 通道首字母 | 确定性生成 | `DL2026110700002W` |
| 模板编码 `template_code` | `MSG_{域}_{序号3位}` | 人工指定 | `MSG_TASK_001` |

**为什么 `msg_no` 用 Redis `INCR` 而不是数据库序列**：共享规范 §17 第 30 条的教训是「单号用数据库序列拼日期」会出问题——序列不随日期重置，第二天的第一个单号会是 `...000043` 而不是 `...000001`。Redis 的 key 里带日期，天然按天重置。

**为什么 `delivery_no` 是确定性生成而不是独立流水**：确定性生成让「重试」天然幂等——同一个 `(msg_no, channel_code)` 无论重试多少次都算同一条投递记录。

| 编号 | 规则 | 实现位置 |

**关于 M21 未设计的完整说明**：

M21 集成平台在本仓**尚未设计**（`ls -d M21*` 返回空）。全仓唯一一处 M21 网关接口是 `M03患者服务与EMPI/M03_患者服务与EMPI_05_消息_详细设计.md:295`：

```
POST /internal/v1/gateway/message/send
参数：channel / receiver_addr(加密) / template_provider_id / content_vars / task_no / record_no
```

这是 M03-05 视角的设计假设，**不是 M21 的正式契约**。本子模块的处理：

1. **按上述接口形状设计对接代码**，`m20_msg_channel.gateway_provider` 恒为 `M21`，接口路径从渠道配置读取而非硬编码。
2. **M21 未上线时降级为仅 `INBOX` + `APP_PUSH`**：`INBOX` 必然可用（本库），`APP_PUSH` 由本子模块直连 APNs/FCM（推送令牌在 `m20_msg_push_token`）。`WECHAT_WORK` 与 `SMS` 无法自实现，置 `SKIPPED`。
3. **待 M21 设计完成后的确认清单**（本子模块需要 M21 回答的问题）：

| 序 | 待确认问题 | 为什么必须问 |
|---|---|---|
| 1 | 发送接口的最终路径与请求体形态 | 决定对接代码 |
| 2 | M21 是否提供**投递回执前置到职工**的回调契约（M03-05 `:296` 定义的回调指向 M03-05 自己，本子模块需要 M21 也回调本子模块） | 没有回调就无法把 `SENT` 推进到 `DELIVERED`，`SENT` 与 `DELIVERED` 分离的设计就落不了地 |
| 3 | 回执失败时的补拉接口（M03-05 `:297` 的 `pending-receipts` 是否也对本子模块开放，还是各模块各建一个） | 决定是本子模块自建补拉还是复用 |
| 4 | 单接收人频率限制由 M21 统一管还是各调用方各自管 | 目前 `m20_msg_channel.receiver_daily_limit` 是本子模块管，若 M21 也管会双限 |
| 5 | 短信计费口径（按条计费还是按 70 字折算长短信） | 决定 `cost_cents` 怎么算 |

**第 2 条是最关键的缺口。** 如果 M21 不向本子模块回调，`SENT` 就永远无法推进到 `DELIVERED`，日志里会全是 `SENT`——这正好是总纲 §4.5 批判的那个「把发送当送达」的缺陷，只不过换了层皮。

**降级红线（V1.4 §8A.2）的三条**：

1. 不允许「看起来正常但不完整」的 200——降级必须带 `degraded: true` 与 `degraded_sources`。
2. 不允许把「没查到」伪装成「空数组 + `degraded: false`」。
3. 不允许用 200 + 空 `data` 表达「无权限」——一律 403。

### 8.5 恒等式与闭合校验

| 编号 | 恒等式 | 校验时机 |
|---|---|---|
| E-01 | `total_count = SUM(source_breakdown[].after_dedup)` | P-03 每次计算后 |
| E-02 | `naive_sum - final_total = deduped_count` | 同上 |
| E-03 | `final_total = 0` 时 `degraded` 必须为 `false` | 同上 + `ck_m20_msg_unread_zero` |
| E-04 | `total_count > 99` 时 `display_value = '99+'` | 同上 + `ck_m20_msg_unread_display_cap` |
| E-05 | 待办完成率 + 作废率 + 转办率 + 未完成率 = 1（同一时间窗、同一分母） | P07/P08 统计时 |
| E-06 | `m20_msg_inbox.delivery_attempt = COUNT(m20_msg_delivery_log WHERE msg_no = ... AND attempt_status IN ('SENT','FAILED'))` | 每日巡检 附录 B.2 |

**E-02 为什么必须留痕 `naive_sum`**：如果只存 `final_total`，去重逻辑一旦失效（比如唯一键被误改），`final_total` 会静默变大，没人会发现。同时存 `naive_sum` 后，`naive_sum - final_total` 的差值就是「这次去重掉了多少」，它应该稳定在某个区间；突然变成 0 就说明去重没生效。

### 9.2 数据权限与脱敏

**行级权限**

| 资源 | 规则 |
|---|---|
| `m20_msg_inbox` | `staff_id = 当前用户`。管理员也**不能**看别人的站内信——消息是私人收件箱 |
| `m20_msg_todo` | `assignee_id = 当前用户`；`m20:msg:todo:manage` 可看本科室（`dept_id`） |
| `m20_msg_delivery_log` | 仅 `m20:msg:delivery:view`；且查询必须带 `staff_id` 或 `msg_no` 条件，禁止全表扫描 |
| `m20_msg_unread_snapshot` | 仅本人 + 运维 |
| `m20_msg_template` | 全部可见（模板不含个人信息） |
| `m20_msg_channel` | 全部可见（配置不含个人信息） |

**字段脱敏**

| 字段 | 场景 | 脱敏规则 |
|---|---|---|
| `m20_msg_inbox.content_vars` 中 `sensitive = true` 的变量 | 日志、预览、导出 | 保留首尾字符，中间用 `*` 替换 |
| `m20_msg_delivery_log.error_msg` | 所有返回 | 手机号与身份证号必须打码（附录 B.5 巡检） |
| `m20_msg_push_token.push_token` | 所有返回 | 只返回后 8 位，形如 `****a1b2c3d4` |
| `m20_msg_todo.biz_title` | 转办给他人时 | 若含患者姓名且接收人无该患者权限，替换为「【患者】的 XX」 |

**为什么 `content_vars` 里允许出现患者姓名**：`m20_msg_inbox` 是受行级权限保护的表，且不进 MQ。区别不是「能不能存」，是「能不能广播」。一条「张三的术前访视提醒」必须能渲染出姓名才有用；它存在库里是安全的，进事件里是不安全的。所以本子模块的规则是：**姓名可以进 `content_vars`（表内），不能进事件载荷（跨模块）**。

### 9.3 审计留痕

| 动作 | 是否审计 | 落点 |
|---|---|---|
| 消息创建 | 是 | `m20_msg_inbox` 四审计列 + U-09 |
| 消息已读 | 是 | `read_at` + U-09 |
| 待办创建/认领/完成/作废/转办 | 是 | `m20_msg_todo_event` + U-09 |
| 渠道配置修改 | 是 | `m20_msg_channel` 四审计列 + U-09 |
| 模板发布 | 是 | `m20_msg_template` + U-09 |
| 推送令牌注册/注销 | 是 | `m20_msg_push_token` + U-09 |
| 投递日志查询 | 是（只记查询人） | U-09（**不落本库**，避免污染只增不删表） |
| 角标计算 | 否 | 量太大（14 万/日），只留 `m20_msg_unread_snapshot` 7 天 |

### 10.2 消费上游接口

见 §2.4 依赖关系表（U-01~U-42）。补充说明：

**U-25（M08 P-01）与 M08 事件的取舍 —— 事件为主、轮询兜底**：`M08护理工作站/M08_护理工作站_01_护理任务与执行队列_详细设计.md:3188-3197` 显示 `m08.task.created` 的载荷是 `{task_id, task_no, patient_id, ward_id, planned_time, source_type}`——**不含 `nurse_id`**，无法直接定位待办责任人。

但它**有 `ward_id`**，这就够了：待办的责任人边界由病区决定，一个病区内当班的护士就是这批任务的候选责任人。所以护理任务来源采用**两段式**：

| 段 | 触发 | 动作 | 代价 |
|---|---|---|---|
| 主路径 | 订阅 `m08.task.created` / `m08.task.overdue` | 按事件里的 `ward_id` 查出该病区当班护士，为这批护士**重建护理任务待办**（`source = 'M08_NURSE_TASK'`，`staff_id` 取护士，`biz_id` 仍取 `task_id`） | 一次事件 → 一次按病区范围的 U-25 调用；病区 20~30 人，重建一次即可 |
| 兜底 | 定时任务每 120 秒 | 只对「本班次有排班但待办为空」的护士补一次 U-25 | 300 人在线时不是 300 次调用，而是「待办为空的护士数」次，稳态接近 0 |

**为什么不是纯轮询**：纯轮询的问题不是慢，是**轮询间隔内新派的任务不会出现在护士手机上**——任务 8:00 派下来、8:00:30 护士打开 App 看不到，他不会再开第二次。而且 300 人 × 每 60 秒 = 每分钟 300 次内部调用，对一个纯读取场景是纯浪费。

**为什么兜底只针对「待办为空」的护士**：兜底的目的不是保持新鲜，是**修补漏掉的事件**（消息丢失、订阅重启、病区当班名单变化）。待办非空的护士说明事件链路是通的，不需要再查。这一条把轮询量从「全体」压到「疑似漏事件的那部分」。

**M08 补 `nurse_id` 之后怎么改**：只需把「按 `ward_id` 广播到病区」收窄为「按 `nurse_id` 定向写入」，**调用链、表结构、去重键全部不变**。这是刻意设计的——不能因为上游今天缺一个字段，就把本子模块的骨架做成只能靠轮询。

已向 M08 登记提请：在 `m08.task.created` / `m08.task.overdue` 载荷中补 `nurse_id`（与 `m08.task.completed` 已有 `nurse_id` 保持一致）。

**U-36（M19 P-01）的响应形状映射**：M19 返回 `source_status` / `degraded_sources` / `refreshed_at` / `generated_at`，不是 M20 的四标记。映射规则：

| M19 字段 | M20 字段 |
|---|---|
| `source_status = "PARTIAL"` | `degraded = true` |
| `source_status = "OK"` | `degraded = false` |
| `degraded_sources`（字符串数组） | `degraded_sources`（对象数组，`reason` 统一填 `"UPSTREAM_PARTIAL"`） |
| `refreshed_at` | `as_of` |
| `generated_at` | 不映射（M20 的 `as_of` 取所有来源最小值） |

**U-42（M20-01 P-06）在线状态**：P-06 已改为心跳上报（写语义）。本子模块订阅 `m20.device.online` / `m20.device.offline` 事件维护进程内在线集合，作为 `APP_PUSH` 通道的选择输入。**在线状态不构成「在不在岗」的判据**——设备锁屏、离线、在岗是三个不同的事。

**M14 药事待审不支持作为待办来源**：`grep /internal/v1/m14` 只返回 `special/permits`、`special/register`、`permit/valid`、`stock/apply`、`dispense/returnable/{rx_no}`，**没有「待审核清单」接口**。因此本子模块的待办来源不含药事待审，已登记为待确认项。

### 10.3 发布事件

本子模块发布三个事件。

| 事件名 | 触发时机 | 载荷 | 订阅方 |
|---|---|---|---|
| `m20.message.pushed` | 一条消息落库并完成通道投递后 | `msg_no`、`staff_id`、`biz_type`、`biz_id`、`channel_codes`、`message_status`、`urgency_level`、`pushed_at` | M01、M22 |

**载荷红线（V1.4 §8A.2 + 共享规范 §10）**：三个事件的载荷**不得出现任何个人信息**——姓名、手机号、身份证号、住址一概不许。`m20.message.pushed` 里没有标题字段，就是因为标题里可能含患者姓名。

**注意共享规范 `:944-946` 的明文警告**：`m13.critical_value.found` 这个事件名**不存在**，实际事件名是 `m12.critical.detected` / `m13.critical.detected`。本表按实际名订阅。

**`m18.qc.defect_found` 的载荷**是 `qc_task_no`、`record_id`、`defect_code`、`defect_level`、`found_at`。其中**没有责任人**，本子模块需要再查一次质控任务的任务人来确定待办归属——这是当前唯一的「事件不够用、需要回查」的订阅，已登记为待确认项。

**`m12.critical.detected` / `m13.critical.detected` 的处理边界**：本子模块收到后只发通知，**不得替 M07 调用危急值确认回调**（M12 `:4153`、M13 `:3123` 的 `on-acknowledged` 语义是「M07 确认后回调 M12/M13」）。替 M07 调会导致危急值闭环记录出现两条确认。

## 11. 异常处理与日志

### 11.1 异常与降级总表

| 异常 | 影响范围 | 处理方式 | 用户可见 |
|---|---|---|---|
| 上游超时 | 单个来源 | 记 `degraded_sources`，整体降级 | 黄条提示 |
| 上游 5xx | 单个来源 | 同上 + 重试 1 次 | 同上 |
| M21 网关不可用 | 外部通道 | 降级为仅 `INBOX` + `APP_PUSH` | 「外部推送通道暂不可用」 |
| 短信日限额触顶 | `SMS` 通道 | `SKIPPED` + 告警 | 「今日短信额度已用完」 |
| 渲染变量缺失 | 单条消息 | 拒绝创建，返回 `"2008003"` | 调用方感知 |
| 待办状态冲突 | 单条待办 | 返回 `"2008015"` 并附当前状态 | 「该待办已被处理」 |
| 推送令牌失效 | 单条投递 | 置 `INVALID`，下次注册时更新 | 无提示（自动恢复） |
| 模板版本不存在 | 单条消息 | 返回 `"2008002"` | 调用方感知 |
| Redis 不可用 | 缓存与去重 | 角标直查数据库（慢但正确），去重降级为不过滤 | 无提示（略慢） |
| 数据库主库不可用 | 全部 | 全部接口 503 | 「系统繁忙，请稍后重试」 |

**「Redis 不可用」的处理值得单说**：Redis 挂了以后角标直查数据库会慢（5 个来源串行），但结果仍正确。如果这时降级为「返回 0」，就掉进了本子模块最严重的那个缺陷。**宁慢勿错**。

### 11.3 监控指标

| 指标名 | 类型 | 告警阈值 | 说明 |
|---|---|---|---|
| `m20_message_failed_total` | Counter | 5 分钟内 > 20 | 投递失败总数 |
| `m20_message_deliver_duration_ms` | Histogram | P95 > 300 | 投递耗时 |
| `m20_unread_calc_duration_ms` | Histogram | P95 > 100 | 角标计算耗时 |
| `m20_unread_degraded_ratio` | Gauge | > 0.10 | 角标降级比例，正常应 < 10% |
| `m20_todo_aggregate_naive_sum` | Gauge | — | 未去重加总，用于验证去重是否生效 |
| `m20_todo_dedup_count` | Gauge | 连续 1 小时 = 0 且 `naive_sum > 0` | 去重失效告警 |
| `m20_sms_daily_used` | Gauge | > 400（上限 500） | 短信用量 |
| `m20_sms_limit_reached_total` | Counter | 任何增量 | 触顶次数，每条都要看 |
| `m20_push_token_invalid_total` | Counter | 5 分钟内 > 50 | 令牌失效率异常 |
| `m20_delivery_log_default_partition_rows` | Gauge | > 0 | DEFAULT 分区有数据说明分区维护失败 |
| `m20_msg_delivery_sent_without_receipt` | Gauge | > 100 | `SENT` 超 10 分钟无回执，说明 M21 没回调 |

**`m20_todo_dedup_count` 是这套监控里最关键的一条**：它能直接发现「去重悄悄失效」这个最难查的缺陷。如果 `naive_sum` 一直是 34、`dedup_count` 一直是 0，说明去重逻辑没生效，角标会显示 34——而这正是总纲批判的「护士看到 34 条会直接不看」。

**`m20_delivery_log_default_partition_rows > 0` 也是一个早期信号**：DEFAULT 分区本应永远为空，一旦有数据说明某个月的月度分区没建，而此时数据仍在正常写入只是写进了错误的容器。

## 附录 E：关键决策记录

| 编号 | 决策 | 备选方案 | 选择理由 |
|---|---|---|---|
| D-01 | 角标失败时返回 `null` + `?` + `degraded:true`（有缓存则返回缓存值 + 黄条） | 返回 0 / 返回上次值且不标记 | 0 的含义是「没有消息」，用它表示失败会让护士以为今天没事可做；返回上次值不标记是「看起来正常但不完整」的 200，违反 V1.4 §8A.2 红线一 |
| D-02 | 去重键定 `(source, biz_id)`，`source` 取「最终落在哪张表」 | 按发起方模块分 | 按发起方分会导致「M10 发起的审批」既算 M10 又算 M20；按落点分保证每件事只有一个归属 |
| D-03 | `M20_APPROVAL` 的 `dedup_scope = LOCAL_ONLY`，不参与跨来源去重 | 全部跨来源去重 | 审批待办是「去点通过」、审批消息是「有人发了东西」，合并会让「读完消息但没点通过」的人角标显示 0，真实待办消失 |
| D-04 | `SENT` 与 `DELIVERED` 必须分开 | 合并为 SENT 一个状态 | 网关 200 只证明提交成功，合成一个状态后「这条消息到底发没发出去」永远答不清 |
| D-05 | P-04 承诺「落库 + 入队」而非「已送达」 | 承诺送达 | 承诺送达就无法守住 300ms；且送达时间不可控。契约里必须写明 |
| D-06 | 批量外部通道投递异步化 | 同步投递 | 200 人同步约 2,400ms，超预算 8 倍 |
| D-07 | 角标缓存 TTL 取 300s（而非 §14 表头的 60s） | 60s | 60s 意味着每人每分钟触发 5 个来源查询，300 人在线时 QPS 远超总纲的 120；300s 是可承受 QPS 与新鲜度的交点。**规范内部矛盾已报 lead** |
| D-08 | `overdue_flag` 用 Celery 每 5 分钟刷新（允许滞后） | 每次查询实时算 | 实时算要在 `WHERE` 里加 `due_at < now()`，多一次索引代价；5 分钟滞后对「是否超时」的判断完全可接受 |
| D-09 | 降级结果不回填 Redis 缓存 | 回填 | 回填会让接下来 5 分钟所有人拿到不完整的数，且 `data_quality` 变成 `CACHED`——看起来像「数据旧」，实际是「数据缺」 |
| D-10 | 短信限额触顶降级而非抛错 | 抛 5xx | 抛错会让一整批推送失败；降级后仍有 INBOX/WECHAT_WORK/APP_PUSH 三条通道。但必须告警，不能静默 |
| D-11 | M21 未设计时降级为仅 `INBOX` + `APP_PUSH` | 阻塞等待 M21 | 阻塞意味着本子模块无法上线；`INBOX` 与 `APP_PUSH` 可自实现，足以覆盖核心场景 |
| D-12 | `data_quality` 不透传上游，自行重判 | 透传 M22/M19 的值 | V1.4 §8A.2.1 明文要求；且上游的 `CACHED` 与本地缓存是两回事，透传会让新鲜度语义丢失 |
| D-13 | 驾驶舱不自算任何指标 | 本子模块聚合缓存 M22 数据 | 指标口径必须只在 M22 有一份，多一份就多一个错的机会 |
| D-14 | 护理任务来源用「事件按 `ward_id` 广播 + 待办为空的护士才轮询兜底」 | 纯 U-25 轮询；或等 M08 补 `nurse_id` 再做 | 该事件载荷无 `nurse_id` 但有 `ward_id`，病区即责任人边界。纯轮询的缺陷不是慢而是「间隔内新任务不出现」，且 300 人 × 60 秒是每分钟 300 次纯浪费。两段式的好处是 M08 补字段后只需把广播收窄为定向，骨架不用改 |
| D-15 | 待办转办产生新行、旧行置终态 | 原地改 `assignee_id` | 原地改会丢失「谁转给谁」的事实；且一次转办在流水里应有两行 |
