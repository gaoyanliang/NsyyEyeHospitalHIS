### 1.3 跨子模块共用表归表裁决

M20 内部有三张表会被多个子模块读写，必须明确**由谁首建、谁能写**：

| 表 | 首建者 | 只读方 | 裁决理由 |
|---|---|---|---|
| `m20_base_idempotency` | **M20-01** | M20-02~08 | 幂等是所有子模块的共同需求（移动端连点是常态）。若各子模块自建幂等表，会出现「同一个 `X-Idempotency-Key` 在 M20-02 和 M20-06 被当成两次不同的操作」。**幂等键必须是全局的。** |
| `m20_base_offline_queue` | **M20-01** | M20-03 / M20-06 / M20-07 | 离线队列的冲突判定算法（M20-CALC-06）只有一套，各子模块各写一遍必然口径不一。**M20-01 定义队列结构与冲突判定，各子模块只负责定义自己的 `biz_type` 与重放逻辑。** |
| `m20_msg_todo` | **M20-08** | M20-04 | 待办聚合（M20-CALC-03）需要「一个数」。审批待办是它的一个来源，不是另一套体系。**M20-04 写 `m20_msg_todo`，但表的定义与去重规则归 M20-08。** |

**三条硬规则：**
1. **首建者对表结构有一票否决权**。别的子模块需要加字段，必须提给首建者，不得在自己文档里另建一张表。
2. **只读方不得写首建者的表**（`m20_msg_todo` 的 M20-04 写入是**唯一例外**，且必须走首建者提供的写接口，不直接 INSERT）。
3. **跨子模块表的 DDL 只在首建者的数据结构文档里出现一次**，其他子模块只写「本表定义见 M20-01 数据结构 §4.x」。

| 上游 / 其他文档里的写法 | M20 统一为 | 依据 |
|---|---|---|

## 2. 命名与建表规范

### 2.1 对象命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 表 | `m20_{子模块}_{业务对象}` | `m20_apr_instance` |
| 主键 | `id BIGINT GENERATED ALWAYS AS IDENTITY` | — |
| 外键 | `fk_m20_{表简称}_{目标表简称}` | `fk_m20_apr_node_instance` |
| 唯一索引 | `uk_m20_{表简称}_{列}` | `uk_m20_apr_instance_no` |
| 普通索引 | `idx_m20_{表简称}_{列}` | `idx_m20_apr_node_approver` |
| 检查约束 | `ck_m20_{表简称}_{含义}` | `ck_m20_apr_instance_status` |
| 触发器函数 | `trg_fn_m20_{表简称}_{动作}` | `trg_fn_m20_apr_node_guard` |
| 触发器 | `trg_m20_{表简称}_{时机}_{动作}` | `trg_m20_apr_node_bu` |

### 2.2 建表硬规范

1. **每张表必须有四个审计列**：`created_at TIMESTAMPTZ NOT NULL DEFAULT now()`、`created_by BIGINT`、`updated_at TIMESTAMPTZ`、`updated_by BIGINT`。
2. **业务表带 `is_deleted BOOLEAN NOT NULL DEFAULT FALSE`**，**例外**见 §3.3（只增不删表）。
3. **状态列用 `VARCHAR(32)` + `CHECK` 显式枚举全部取值**，不用数据库 `ENUM` 类型。
4. **金额 `NUMERIC(14,2)`，比率 `NUMERIC(10,6)`，剂量 `NUMERIC(12,4)`**。禁止浮点。
5. **时间一律 `TIMESTAMPTZ`**。
6. **跨模块引用不建外键**（上游表由上游模块管理），改为注释说明并在应用层校验；**M20 内部表之间必须建外键**。
7. **每张表必须有 `COMMENT ON TABLE`**，状态列与关键业务列必须有 `COMMENT ON COLUMN`。

## 3. 三处数据库强制

M20 有三件事**必须由数据库保证**，不能只靠应用层。理由统一：**应用层有多个入口（移动端、离线队列重放、定时任务、运维手工 SQL），只要有一个入口忘了校验，约束就失效了。**

### 3.1 审批动作不可跳过（防越级审批）

**问题**：审批必须按节点顺序执行。若只在应用层判断「当前节点的 `node_seq` 是不是最小未完成节点」，离线队列重放或并发请求可能让第 2 级先于第 1 级通过。

**落地方案**：`m20_apr_node` 上加部分唯一约束，保证同一实例同一时刻只有一个节点处于 `PENDING`：

```sql
CREATE UNIQUE INDEX uk_m20_apr_node_active
    ON m20_apr_node (instance_id)
    WHERE node_status = 'PENDING';
```

> **为什么用部分唯一索引而不是触发器**：唯一索引是**原子的**，两个并发事务只有一个能成功；触发器里做 `SELECT` 再 `RAISE` 存在竞态窗口（两个事务都读到「没有 PENDING 节点」，然后都插入成功）。**能用唯一索引表达的不变量，就不要用触发器。**

### 3.2 审批留痕不可篡改（防事后改审批记录）

**问题**：`m20_apr_action_log` 记录「谁在什么时候批了什么」。这张表若能被 UPDATE，审批留痕就没有意义——药事检查追问「这支特殊用药是谁批的」时，记录可以被改。

**落地方案**（两条同时做）：

```sql
-- ① 应用账号不得 UPDATE / DELETE 留痕表
REVOKE UPDATE, DELETE ON m20_apr_action_log FROM app_m20;
GRANT INSERT, SELECT ON m20_apr_action_log TO app_m20;

-- ② 表结构上根本没有可改的业务列（见 §3.3 只增不删表）
```

**并且**在 `m20_apr_action_log` 上加一个拒绝 UPDATE 的触发器作为纵深防御：

```sql
CREATE OR REPLACE FUNCTION trg_fn_m20_apr_action_log_immutable()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'APPROVAL_LOG_IMMUTABLE'
        USING HINT = '审批留痕只允许追加，不允许修改或删除';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m20_apr_action_log_bu
    BEFORE UPDATE OR DELETE ON m20_apr_action_log
    FOR EACH ROW EXECUTE FUNCTION trg_fn_m20_apr_action_log_immutable();
```

### 3.3 只增不删表清单

以下五张表**不得有 `is_deleted` 列**，且必须 `REVOKE DELETE`（部分还要 `REVOKE UPDATE`）：

| 表 | 首建者 | 无 `is_deleted` 的理由 | 权限 |
|---|---|---|---|
| `m20_apr_instance` | M20-04 | 审批实例是流程事实。软删除会让「这条审批从未存在过」成为可能 | `REVOKE DELETE` |
| `m20_apr_node` | M20-04 | 同上 | `REVOKE DELETE` |
| `m20_apr_action_log` | M20-04 | 审批留痕必须不可改不可删 | `REVOKE UPDATE, DELETE` |
| `m20_msg_delivery_log` | M20-08 | 消息投递日志是对账依据（「这条通知到底发没发」） | `REVOKE DELETE` |
| `m20_qry_search_log` | M20-05 | 检索留痕是审计事实（谁查了什么患者） | `REVOKE UPDATE, DELETE` |

> **判据（写进验收）**：问一句「这张表的不一致或缺失本身是不是要被保留的信息？」若是 → 只增不删。这与 M18-03 那轮总结的「记录本身是证据的地方不允许自动修复」是同一个判据，只是这里用在表结构层面。

**"只增不删"不等于"永不清理"**：`m20_qry_search_log` 三年 4,400 万行，必须按 §10 的归档策略迁移到只读归档库，**迁移动作由一个独立账号 `m20_archiver` 执行**，`app_m20` 永远没有 DELETE 权限。

## 4. 分区策略

### 4.1 分区判据（**判据，不是允许清单**）

一张表是否分区，看**增长速率与保留策略**，不看它属于哪个子模块。满足任一条即应分区：

1. 三年行数预计超过 500 万；
2. 存在「按月保留 N 个月后 `DETACH` 转冷库」的保留策略；
3. 查询总带时间范围条件、且需要按时段做批量清理。

**反过来，满足以下任一条就不该分区**：①分区键会破坏本表唯一约束（见 §4.2 第 2 条）；②规模根本不够，分区的建表与索引维护成本大于收益；③查询永远带精确主键，分区只能增加规划开销。

**当前已识别出的分区表**（随各子模块交付补充，不是仅有的两张）：

| 表 | 归属 | 分区方式 | 命中判据 |
|---|---|---|---|
| `m20_qry_search_log` | M20-05 | **月分区 + DEFAULT** | 1,460 万行/年，纯追加，按时间查 |
| `m20_msg_delivery_log` | M20-08 | **月分区 + DEFAULT** | 110 万行/年，按时间查与清理 |
| `m20_doc_oper_log` | M20-02 | **月分区 + DEFAULT** | 600 万行/3 年，保留 36 个月后转冷库 |

**当前已识别出的不分区表**：

| 表 | 归属 | 理由 |
|---|---|---|
| `m20_msg_inbox` | M20-08 | 单用户消息量小（每人日均 20 条），且查询总带 `staff_id` |
| `m20_apr_instance` / `_node` / `_action_log` | M20-04 | 三年 55 万 / 137 万 / 数十万行，规模太小 |
| `m20_base_stat` | M20-01 | 1,400 行/年 |
| `m20_base_offline_queue` | M20-01 | 两个唯一约束 `queue_no`、`(staff_id, idempotency_key)` 分区后会失去语义 |

> **本节判据优先于任何一张清单。** 若某张表既不命中三条正面判据、也不命中三条反面理由，先按「不分区」实现并在数据结构文档里写清「为什么判断它不会长大」；**这个判断本身就是需要被记下来的东西**，因为将来数据长大了要回过头看当初凭什么这么判断。
>
> **分区不是好习惯，是一个有代价的决定。** 代价是：每个月要建分区（漏了就要靠 DEFAULT 兜）、唯一约束受限制、跨分区查询可能更慢、`DETACH` 权限要单独管。**没有增长压力的表分区，是在给自己制造维护工单。**

### 4.2 为什么审批表不分区

三条理由：

1. **规模不够**。三年审批实例 55 万行，即使一行 2KB 也只有 1.1GB，单表完全够用。分区的维护成本（每个月建分区、迁移数据、改索引）远大于收益。
2. **分区键会破坏唯一约束**。PostgreSQL 要求分区表上的唯一索引必须包含分区键。`m20_apr_instance` 的唯一约束是 `approval_no`，若按 `created_at` 分区，唯一索引就得变成 `(approval_no, created_at)`——**同号的审批单可以在不同月份各存在一条**。这与「审批单号全局唯一」直接冲突。
3. **查询总带精确条件**。查审批永远是 `WHERE approval_no = ?` 或 `WHERE approver_id = ? AND status = ?`，几乎不扫全表。分区能带来的顺序扫描优化用不上。

> **第 2 条是硬约束，不是偏好。** 任何「某个字段必须全局唯一」的表，都不要按非该字段分区。

### 4.3 分区表必须带 DEFAULT

```sql
CREATE TABLE m20_qry_search_log (
    id              BIGINT GENERATED ALWAYS AS IDENTITY,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    ...
) PARTITION BY RANGE (created_at);

CREATE TABLE m20_qry_search_log_2026_11
    PARTITION OF m20_qry_search_log
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

CREATE TABLE m20_qry_search_log_default
    PARTITION OF m20_qry_search_log DEFAULT;
```

**没有 `DEFAULT` 分区会怎样**：新月份的第一条 INSERT 直接失败（`no partition of relation ... found for row`）。而这条 INSERT 可能发生在凌晨 0 点 00 分 01 秒——**值班人员看到的是「查询功能突然报错」，而不是「少了一个分区」**。

有了 `DEFAULT` 分区，数据先落进去；运维巡检发现 `DEFAULT` 分区非空就说明「有月份没建分区」，可自动补建并搬迁。

**巡检 SQL**（写进 §8.3 上线必跑）：

```sql
SELECT 'm20_qry_search_log' AS tbl, count(*) AS default_rows
FROM m20_qry_search_log_default
UNION ALL
SELECT 'm20_msg_delivery_log', count(*)
FROM m20_msg_delivery_log_default;
```

**期望值：0 行。** 非 0 说明分区维护失败。

| **合计（含索引约 2.2 倍）** | — | — | — | — | **约 20 GB** |

> `m20_msg_inbox` 三年 110 万条 × 1KB ≈ 1.1 GB，已计入「其余」。

### 5.2 结论

**单机 PostgreSQL 16 完全可承载，不需要任何水平扩展。**

三条不做的事：

1. **不做分库分表**。20 GB 在 PostgreSQL 上是「小库」。分库分表带来的跨库查询、分布式事务、数据一致性成本，远大于它解决的问题。
2. **不引入 Elasticsearch**。M20 的检索需求是「按患者姓名/就诊号/单号精确查」，用 PostgreSQL 索引就够。要全文检索的是病历正文（M18-07 已用 `tsvector` + GIN 解决）。
3. **不把检索留痕放对象存储**。它要支持「某护士上周三查了哪些患者」这类按时间+人查询，放对象存储就查不了了。

### 5.3 增长预警

| 阈值 | 动作 |
|---|---|
| 单表 > 5 GB | 复核分区策略 |
| 单表 > 20 GB | 考虑分区或归档 |
| 磁盘使用 > 70% | 启动 §10 的归档迁移 |

## 7. 全局约束清单

### 7.1 跨子模块通用约束（G-01 ~ G-11）

| 编号 | 约束 | 落地位置 | 违反后果 |
|---|---|---|---|
| **G-01** | 所有表必须有四个审计列 | 全部表 | 无法回答「谁在什么时候改的」 |
| **G-02** | 状态列取值必须在 `CHECK` 里显式枚举 | 全部状态列 | 写入非法状态后页面渲染失败 |
| **G-03** | 金额列必须是 `NUMERIC(14,2)`，禁止浮点 | 全部金额列 | 金额累加出现分位误差 |
| **G-04** | 同一实例同时只有一个 `PENDING` 节点 | `uk_m20_apr_node_active`（§3.1） | 越级审批 |
| **G-05** | 审批留痕不可 UPDATE / DELETE | §3.2 | 审批记录可被篡改 |
| **G-06** | 幂等键全局唯一且 24 小时内有效 | `uk_m20_base_idempotency` | 连点导致重复执行 |
| **G-07** | 离线队列冲突不得自动解决 | `ck_m20_base_offline_queue_conflict` | 已作废单据被救活 |
| **G-08** | 消息 `SENT` 与 `DELIVERED` 不得合并 | `ck_m20_msg_delivery_status` | 把「已提交」当成「已收到」 |
| **G-09** | 分区表必须有 DEFAULT 分区 | §4.3 | 新月份 INSERT 失败 |
| **G-10** | 时间列一律 `TIMESTAMPTZ` | 全部时间列 | 跨时区显示错误 |
| **G-11** | 跨模块引用不建外键 | 全部跨模块 ID 列 | 上游模块变更时 M20 迁移被卡住 |

### 7.2 组合约束判别（只写单字段约束会漏掉什么）

| # | 规则 | 只写单字段约束会漏掉什么 |
|---|---|---|
| 1 | `APPROVED` 或 `REJECTED` 必须有 `finished_at` | 有状态没时间，无法统计审批时长 |
| 2 | `APPROVED_BUT_FAILED` 必须有 `exec_fail_reason` | 有失败状态没原因，申请人不知道怎么办 |
| 3 | `TIMEOUT` 必须有 `timeout_at` 且 `approver_id IS NULL` | 把超时当成有人不批，追责追错了人 |
| 4 | `TRANSFERRED` 节点必须有 `transfer_from_id` | 转办链条断裂 |
| 5 | `SKIPPED` 必须有 `skip_reason` | 免审跳过与驳回跳过混为一谈 |
| 6 | 离线队列 `CONFLICT` 必须有 `conflict_reason` | 无法区分「实体没了」与「版本变了」 |
| 7 | 消息 `FAILED` 必须有 `fail_count >= 1` 与 `last_error` | 失败不可诊断 |
| 8 | 消息 `READ` 必须有 `read_at` | 无法审计「是否真的看过」 |
| 9 | 护理任务 `COMPLETED` 必须有 `executed_at` 与 `executed_by` | 无法追溯谁执行的 |
| 10 | 扫码核对 `VERIFIED` 必须有 `scan_time` 与 `patient_match = TRUE` | 核对流于形式 |

#### 7.2.1 单向蕴含的约束通常都不够——要写成双向互斥

上表第 6 条的完整实现由 M20-01 给出（`M20_移动办公_01_移动端接入与移动适配基础_数据结构.md` 的 `m20_base_offline_queue`），它把一条规则拆成**成对的两条 CHECK**：

```sql
-- 正向：进 CONFLICT 必须有原因
CONSTRAINT ck_m20_base_offline_queue_conflict
    CHECK (sync_status <> 'CONFLICT' OR conflict_reason IS NOT NULL),
-- 反向：有原因就必须是 CONFLICT
CONSTRAINT ck_m20_base_offline_queue_reason_scope
    CHECK (conflict_reason IS NULL OR sync_status = 'CONFLICT')
```

**只写前一条会漏掉什么**：一条 `SYNCED` 的队列项可以带着 `VERSION_CHANGED` 的原因。数据本身没错（每一行都合法），但**数据的形状骗过了统计口径**——所有基于 `conflict_reason IS NOT NULL` 的告警与看板会把这条「已同步的冲突」算进冲突数，而任何基于 `sync_status = 'CONFLICT'` 的统计又看不到它。**同一份数据，两种口径得出两个数，且两边都不报错。**

判别方法：写下一条蕴含式 `状态 X ⇒ 字段 Y 必填` 之后，**立刻问一句「那么 Y 非空时，X 一定成立吗？」** 不成立就再写一条反向约束。这条规则在审批（`TIMEOUT ⇒ timeout_at` 但有 `timeout_at` 不一定是超时）、消息（`FAILED ⇒ last_error` 同理）上同样适用。

#### 7.2.2 能用「结构事实」表达的规则，不要用「规范要求」表达

M20-01 在离线队列的重放设计里给出了一条比约束更强的东西：

> **版本校验不在业务处理器里，业务处理器根本没机会在版本不符时被调用。**

「`CONFLICT` 零自动解决」是一条**要求**（重放器**不应该**写 `SYNCED`）；而「冲突路径上没有任何写 `SYNCED` 的代码」是一条**结构事实**（那条代码路径不存在）。

两者的区别不在于强度，在于**抵抗变更的能力**：要求会被后来的需求改掉（「为什么不能自动解决？用户等着呢」），而结构事实要想被推翻，必须先改调用顺序——那是一次显眼的架构变更，不会悄悄发生。凡是「靠人记得」的规则，都应先找一遍有没有能让它长成结构、长成约束、或长成一条**会让上线检查失败**的表达方式（如 §8 的上线必跑 SQL：`UNIQUE` 是不是两列组合，去 `pg_indexes.indexdef` 里读出来验）。

#### 7.2.3 一张表能不能 DELETE，看它存的是「事实」还是「窗口」

只增不删表清单（§3.3）是**枚举**；生成它的**判据**是这一条：

> **一张表能不能 DELETE，取决于它存的是「事实」还是「窗口」。窗口可以过期，事实不行。**

`m20_base_idempotency` 是这条判据的正面例子：一条 24 小时前的幂等记录被清掉，业务事实毫发无损（真正的业务单据在申请方），它只是**时间窗内的去重登记**。所以它是 `m20_base_*` 里**唯一允许物理 DELETE** 的表，且**不加 `is_deleted`**——软删除会让表无限膨胀，更严重的是会让 `UNIQUE (biz_type, idempotency_key)` 失去意义：软删除后同一组合还能再插一行，等于幂等失效。**这与本节开头的警告是同一个坑换了地方出现。**

### 7.3 唯一约束与部分索引

| 索引 | 表 | 定义要点 | 注意 |
|---|---|---|---|
| `uk_m20_apr_instance_no` | `m20_apr_instance` | `UNIQUE (approval_no)` | 单号全局唯一 |
| `uk_m20_apr_node_active` | `m20_apr_node` | **部分唯一**：`(instance_id) WHERE node_status = 'PENDING'` | 见 §3.1 |
| `uk_m20_base_idempotency_key` | `m20_base_idempotency` | `UNIQUE (biz_type, idempotency_key)` | 幂等键跨子模块共享 |
| `uk_m20_msg_dedup` | `m20_msg_inbox` | `UNIQUE (staff_id, biz_type, biz_id)` | 5 分钟内同源消息去重 |
| `idx_m20_apr_node_approver` | `m20_apr_node` | `(approver_id, node_status)` | 「我的待审批」主查询 |
| `idx_m20_qry_search_log_staff_time` | `m20_qry_search_log` | `(staff_id, created_at DESC)` | 检索留痕查询 |

**警告：`is_deleted` 的部分索引不得这样写**

```sql
-- 错误：部分索引条件里加 is_deleted 会让软删除的行脱离约束
CREATE UNIQUE INDEX uk_m20_apr_instance_no
    ON m20_apr_instance (approval_no) WHERE is_deleted = FALSE;
```

若这样写，删掉一条审批实例后，**同一个 `approval_no` 可以再创建一次**——而审批单号是全局唯一的业务事实。**终态表（只增不删表）本来就没有 `is_deleted`，不存在这个问题；对于有软删除的业务表，唯一约束也不应该带 `is_deleted` 条件。**

```sql
FROM information_schema.columns
WHERE table_schema = 'public'
  AND column_name = 'is_deleted'

                     'm20_msg_delivery_log', 'm20_qry_search_log');

SELECT table_name, has_table_privilege('app_m20', table_name, 'DELETE') AS can_delete
FROM information_schema.tables
WHERE table_schema = 'public'
  AND table_name IN ('m20_apr_instance', 'm20_apr_node', 'm20_apr_action_log',
                     'm20_msg_delivery_log', 'm20_qry_search_log');

-- ③ DEFAULT 分区必须为空（期望 0）
SELECT count(*) FROM m20_qry_search_log_default;
SELECT count(*) FROM m20_msg_delivery_log_default;
```

## 10. 备份与归档

### 10.1 备份策略

| 对象 | 频率 | 保留 | 方式 |
|---|---|---|---|
| 全库 | 每日 02:00 | 30 天 | `pg_basebackup` + WAL 归档 |
| 审批三表（`m20_apr_instance` / `_node` / `_action_log`） | **每周** | **10 年** | 逻辑备份，离线加密 |
| 检索留痕 | 每月 | 3 年 | 归档库 |
| 消息投递日志 | 每月 | 2 年 | 归档库 |

**为什么审批表要单独保留 10 年**：审批记录是医疗行为的合规证据。药事检查、医保飞检、医疗纠纷都可能追溯到多年以前。**全库备份只留 30 天，满足不了这个要求**，所以审批三表必须单独做长期备份。

### 10.2 检索留痕的归档（三年后迁移只读库）

1. 确认目标月份的所有分区已建好（`DEFAULT` 分区为空）。
2. 创建只读归档库实例。
3. `pg_dump` 目标月份分区 → 恢复到归档库。
4. 在归档库上 `REVOKE ALL ... FROM PUBLIC`，只留 `SELECT`。
5. 校验行数一致。
6. **在主库上 `DROP` 该分区**——**必须由 `m20_archiver` 账号执行，且执行前做抽样哈希校验**（随机抽 1,000 行，比对主库与归档库的 `id` 与 `created_at` 一致）。
7. 记录归档日志（归档库实例、分区名、行数、校验结果、执行人）。

> **第 6 步是唯一一次真正的数据删除。** 它必须由独立账号执行（`app_m20` 永远没有 DELETE 权限），且必须有抽样校验前置——**没有校验的删除是一去不回的**。留痕表的价值就在于它记录过的事，删错了没人能补。

### 10.3 不销毁

**M20 不设计任何「到期自动销毁」逻辑。** 即便检索留痕超过三年，也只迁移到只读库，不物理删除。

理由：留痕类数据一旦被判定为「可以删除」，删除逻辑本身就会成为事故源（条件写错一次就是永久损失）。**保留成本是磁盘，删除风险是不可逆。** 磁盘便宜。
