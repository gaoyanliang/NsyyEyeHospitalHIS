### 1.2 为什么是这 9 张，而不是「业务副本 + 适配」的 18 张

判据回到总纲 §1.4 的红线：**这张表存的东西，如果 M20 删库重建，会不会有业务事实丢失？**

- **会丢失 → 可以建**。本子模块满足这条的只有两类：① 医生在移动端的**中间态与个人化配置**（草稿正文、查房路线安排、页面编排、快捷入口、最近访问），它们描述的是「这个医生在什么设备上怎么工作」，M20 删库后重建不出原样；② 医生的**行为留痕**（危急值确认、操作日志、使用统计），它们记录的是「医生做了/看了什么」，是审计与考核的原始证据。
- **不会丢失 → 不许建**。诊断、医嘱、处方、病历正文、检验检查报告、住院主档、床位、患者信息**全部在 M07 / M16 / M18 / M05 / M12 / M13 / M03**，M20 删库重建后照常可查。**一旦在本模块落一份副本，就有了第二份临床事实**——两份数据必然分叉，而分叉时无法判定谁对。

按这个判据逐条对照：

| 诱惑点 | 会不会建 | 理由 |
|---|---|---|
| `m20_doc_order` 医嘱草稿 | **不建** | 医嘱写入在 M07（`POST /api/v1/m07/orders`），草稿也是 M07 的 `status='DRAFT'` 医嘱。M20 建草稿表 = 出现「M07 也有一份草稿」的双写 |
| `m20_doc_prescription` 处方缓存 | **不建** | 处方含剂量，剂量是临床事实。移动端一次缓存过期未刷新就是一次用药分歧 |
| `m20_doc_diagnosis` 诊断副本 | **不建** | 诊断权威在 M07-02，M18 也只取文本段不建诊断表（M18-02 §1.4 红线同源） |
| `m20_doc_report` 报告正文缓存 | **不建** | 报告全文 200KB 级，落库既占空间又制造「旧报告」风险（§17 第 10 条） |
| `m20_doc_patient` 患者快照 | **不建** | 患者主索引在 M03。姓名/手机号/身份证一旦落 M20 库，M20 就多了一个泄露面 |
| `m20_doc_note_draft` 病程草稿 | **建** | 草稿是「还没写进病历的中间态」，不是临床事实。**且这是唯一能让弱网下医生输入不丢失的方案**（见 §4.7 论证） |
| `m20_doc_critical_ack` 危急值确认 | **不建**（原设计要建，已撤回） | 危急值确认是 **M07-04 的业务动作**，权威状态在 M12/M13（`DETECTED→NOTIFIED→ACKNOWLEDGED→HANDLED→CLOSED`）。M20 若记一份「医生确认了」，就有了第二个确认时刻、第二份状态——**一个危急值两条闭环路径，而两边都不报错**。M20-02 对危急值**只读**：能看待办、能看单份报告，确认动作跳 M07 入口。见 §2.4 |

### 1.3 为什么「页面编排」与「快捷入口」要拆成两张

两者都是医生个人化配置，看似可合并成一张 `m20_doc_user_pref(key, value)`。拆开的理由：

1. **变化频率差一个数量级**。页面编排是科室下发的模板（医生很少动，三个月改一次）；快捷入口是医生自己随手加的（高频、几十条）。合并后每次加一个快捷入口都要改写整行大 JSON，MVCC 版本膨胀。
2. **读路径完全不同**。页面编排一次全量读（首屏渲染前一次）；快捷入口按使用频次排序后只取前 8 个。合并成一个 JSON 意味着每次取快捷入口也要反序列化整份编排。
3. **权限不同**。页面编排可被科室管理员批量下发（`scope_type='DEPT'`），快捷入口只能本人改。合并后「管理员能改别人的」这个授权无法在字段级表达。

### 1.4 为什么查房路线要「计划 + 明细」两张而不是一张

`m20_doc_round_plan`（一次查房的安排：哪天、哪个病区、谁查、顺序策略）+ `m20_doc_round_item`（这条路线上的每个患者：顺序号、床号快照、是否已查、查房时刻）。

拆开的三条理由：

1. **明细行数比计划大 100 倍**（40,000 : 400,000）。合并成一张意味着每个患者行都冗余一遍病区、日期、查房人，且「本次查房查了几个」要靠 `count(*)` 全表扫。
2. **计划有状态、明细没有独立状态**。计划是 `DRAFT/IN_PROGRESS/COMPLETED/ABANDONED`；明细的「已查」是附属标记。合并后状态列在明细行上重复，改一次计划状态要 `UPDATE` 400,000 行。
3. **明细必须能存「不在院了」。** 查房路线是早上排的，中午患者可能出院或转科。明细行的 `resident_status` 要能表达「计划时在院、执行时已出院」，这类信息只有明细有。

### 1.5 为什么操作日志要单独成表并分区，而不是复用 M20-01 的通用日志

M20-01 有 `m20_base_oper_log`（通用操作日志）。本子模块**另建 `m20_doc_oper_log`** 的理由：

1. **写量与查询维度都不同**。医生站是全模块写量最大的入口（年 600 万行），查询几乎全是「某个患者最近谁看过」（`patient_id` + `created_at`）与「某个医生今天点了什么」（`staff_id` + `created_at`），M20-01 的通用日志不按这两个维度建索引。
2. **字段不同**。医生站日志要记 `encounter_id` / `record_id` / `view_scope`（看了正文还是只看摘要）/ `is_minimal_view`（移动端最小视图），这些字段通用日志没有。
3. **保留期不同且需要分区**。医生站日志按 `created_at` 月度分 RANGE 分区（月 50 万行），通用日志量小、不分区。合并后要么整体分区（过度），要么整体不分区（日志表撑爆）。

**这带来一个必须写清的一致性约束**：两次写日志（`m20_base_oper_log` 通用 + `m20_doc_oper_log` 专用）在同一事务内写入，`m20_doc_oper_log.id` 是权威索引，通用日志只留 `biz_table`/`biz_id` 指针。**若通用日志写失败不回滚专用日志**——审计留痕宁可多一条也不可少一条，失败进补偿队列。

### 2.1 关于 `m20_doc_oper_log` 分区的说明

数据结构汇总 §4 给的是**分区判据，不是允许清单**。判据原文：

> 一张表是否分区，看**增长速率与保留策略**，不看它属于哪个子模块。满足任一条件即应分区：①三年行数预计 > 500 万；②存在「按月保留 N 个月后 DETACH 转冷库」的保留策略；③查询总带时间范围条件。`m20_qry_search_log` 与 `m20_msg_delivery_log` 是当前已识别到的两个典型，**不是仅有的两个**。反例三条：分区键会破坏唯一约束的（如审批三表）、规模不够的（如 `m20_base_stat` 1,400 行/年）、查询总带精确主键的（分区只会增加规划开销）。**（汇总 §4 已按此判据改述。）**

`m20_doc_oper_log` 对判据的逐条对照：

| 判据 | 本表情况 | 是否满足 |
|---|---|---|
| ① 三年行数预计 > 500 万 | 年 600 万行（在线 300 人 × 日 60 万请求量级），三年约 1,800 万 | **满足** |
| ② 有「按月保留 N 个月后 DETACH 转冷库」策略 | 保留 36 个月，超期 `DETACH PARTITION` 转只读库 | **满足** |
| ③ 查询总带时间范围条件 | 全部查询入口（API-26 按时间范围查、使用统计任务按日聚合）都带 `created_at` 范围 | **满足** |

三条判据全部命中，因此本表分区，与汇总 §4 一致（不是例外、不是差异）。

**反向验证：本表不能采用「不分区 + 定期 DELETE」的做法。** `app_m20` 对 `m20_doc_oper_log` 是 `REVOKE UPDATE, DELETE`（只增不删），逐行删历史在权限层就被禁止。而「主表永久保留」会让分区扫描退化为全表扫描。**`DETACH` 是唯一同时满足「不删」与「不涨」的做法**，这与汇总 §10.2「超期迁只读库而不是删」同源。

**DEFAULT 分区（汇总 §4.3 的硬要求）已落地**：`m20_doc_oper_log_pdefault` 建为 `PARTITION OF m20_doc_oper_log DEFAULT`。没有它，新月份第一条 INSERT 会直接失败（`no partition of relation "m20_doc_oper_log" found for row`），值班人员看到的是「系统突然报错」而不是「少建了一个分区」。**但 DEFAULT 分区是安全网而非常态**：一旦有任何行落进去，就说明有月份分区漏建了，因此监控对 `m20_doc_oper_log_pdefault` 的**行数 > 0 直接告警**，运维补建对应月份分区并迁移数据。

### 2.2 为什么三张跨子模块共用表一张都不用

| 共用表 | 一般会怎么用 | 本子模块为什么不用 |
|---|---|---|
| `m20_base_idempotency` | 写接口的幂等键落库 | 本子模块的写接口（提交定稿、危急值确认）**幂等由上游保证**：M18 的 P-11 自身带 `idempotency_key` 且幂等；危急值确认的目标状态 `ACKNOWLEDGED` 是**幂等的目标状态**（重复确认返回同一结果）。**在 M20 再存一份幂等键 = 两处记录同一件事，且「上游成功后 M20 落幂等键失败」会造成调用方重试时 M20 认为重复而上游又执行一次。** |
| `m20_base_offline_queue` | 离线操作排队重放 | **本子模块的写操作不支持离线**（决策见详细设计 §1.2 与 §8.4）：病程记录必须在线提交、定稿必须在线。理由见 §4.7 的「草稿可离线、提交不可离线」。汇总 §1.3 的只读方名单也没有 M20-02 |
| `m20_msg_todo` | 待办聚合 | 医生待办的权威在 M20-08（员工消息与待办中心）。**M20-02 的「危急值待办」不落本模块待办表**，它来自 M12/M13 的事件与查询，是**通道**不是**账本**。M20-02 连「医生点过确认」也不落库——确认动作归 M07-04（见 §2.4） |

### 2.3 为什么 `m20_doc_note_draft` 不被禁止表清单命中

共享规范 §12 与 `validate_m20.py` 的 `check_forbidden` 会抓「加了子模块前缀的绕法」，如 `m20_doc_record` / `m20_doc_order` / `m20_doc_diagnosis`。`m20_doc_note_draft` **不是绕法**，判据有三条且都成立：

1. **它不是病历正文的副本**。它的字段里没有任何一个 `chief_complaint` / `present_illness` / `diagnosis_text` 之类按段落的正文列，只有一整块 `draft_text`（医生还没决定写进哪一段的临时文本）与一个可空 `target_section`（医生选了段落就是段落草稿，没选就是自由草稿）。
2. **它有明确的生命周期终点**：`SAVED`（已写入病历）或 `DISCARDED`（已丢弃）。**进入 `SAVED` 后 `draft_text` 必须被清空**（`ck_m20_doc_note_draft_saved` 强制），所以提交完成后本表不再持有任何临床文本。
3. **它不被任何其他模块读**。`m18_*` 从不查这张表，M07 也不查。它是「输入法级别的暂存」。

**反例对照**：若把它建成 `m20_doc_record(id, patient_id, chief_complaint, present_illness, ...)` 那就是标准副本，必须禁止。

### 2.4 为什么比目标少一张：撤回 `m20_doc_critical_ack`

数据结构汇总 §1.1 给 M20-02 的目标是 9 张表。本文件只交付 8 张，**少的这一张是原设计里打算建的「危急值确认留痕」，已撤回**。

**撤回的直接原因**：共享规范 §9.14 核实发现 M12/M13 的危急值回写接口 `POST /internal/v1/m12/review/critical/{id}/on-acknowledged` 与 `POST /internal/v1/m13/review/critical/{id}/on-acknowledged`，语义是「**M07-04 确认后回调 M12/M13**」，不是「谁能确认」。也就是说危急值的 `ACKNOWLEDGED` 状态**只能由 M07-04 推进**。

如果 M20-02 在手机上让医生点「我已了解」，只有三种实现：

| 做法 | 后果 |
|---|---|
| 替 M07-04 调 `on-acknowledged` | M07 侧认为未确认、M12/M13 侧认为已确认，**一个危急值两个状态**，两边都不报错 |
| 调 M12/M13 的对外 REST 兜底 | 绕开 M07-04 的确认逻辑，同样是第二份状态，只是路径更隐蔽 |
| 只在本模块记「医生点过确认」 | 记了一条**不改变任何权威状态**的记录。数据上看像确认过，实际危急值仍停在 `NOTIFIED`——**这是三种里最坏的**，因为它给了一个看起来成功的假象 |

所以本子模块对危急值**只读**：能看待办列表、能点进单份报告看结论，**确认动作跳转到 M07 的入口或提示「请在医生工作站确认」**。

**为什么这不是「少做一个功能」**：确认动作在 M07-04 有完整的前置（核对患者身份、确认已理解结果、必要时升级处理），移动端只承担「提醒你去看」这一段。去掉确认不减少闭环能力，**减少的是闭环路径的条数**——从两条（M07 一条、M20 一条）收敛回一条。

**留下的空缺与去向**：如果产品确实要求移动端直接确认，那必须由 **M07-04 提供一个移动端可调用的确认接口**（并登记进 M07 的契约表），**不得由 M20 自行发明**。这已登记为待确认事项，不由本子模块实现。

**因此本子模块的 8 张表里，没有任何一张与危急值状态相关**；危急值只出现在 `m20_doc_oper_log` 的 `action='VIEW_CRITICAL'` 行里（医生看过，这是 M20 自己的行为留痕，不涉及危急值状态）。

## 3. 公共字段与命名约定

### 3.1 每张表都有的公共字段

| 字段名 | 类型 | 含义 | 说明 |
|---|---|---|---|
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | 主键 | 分区表（`m20_doc_oper_log`）另加 `created_at` 进主键 |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | 创建时刻 | 服务器时间，不用客户端时间 |
| `created_by` | `BIGINT NOT NULL DEFAULT 0` | 创建人 `staff_id` | 系统写入用 `0`（哨兵值，不建系统账号） |
| `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | 更新时刻 | 由触发器 `trg_m20_doc_*_touch` 维护 |
| `updated_by` | `BIGINT NOT NULL DEFAULT 0` | 更新人 `staff_id` | 同上 |

### 3.2 `is_deleted` 的取舍

共享规范 §2.2 要求「业务表带 `is_deleted`，只增不删表除外」。本子模块的判定：

| 表 | 有 `is_deleted` | 理由 |
|---|---|---|
| `m20_doc_page_layout` | 是 | 编排会被停用后恢复，需要软删除 |
| `m20_doc_shortcut` | 是 | 医生删掉收藏后可能重建同一目标，软删除保留「曾经加过」 |
| `m20_doc_recent_visit` | 否 | 只有「最近 N 条」，物化成一条即淘汰更早的，语义上不存在删除动作 |
| `m20_doc_round_plan` | 是 | 计划可取消，但取消用 `status='ABANDONED'`；`is_deleted` 只给「录错了」这种录入错误 |
| `m20_doc_round_item` | 否 | 明细随计划走，计划作废后明细不再可读；单独软删没有意义 |
| `m20_doc_note_draft` | 否 | 只有 `SAVED`/`DISCARDED` 两个终态，正文清空后即废弃，无软删需求 |
| `m20_doc_usage_stat` | 否 | 统计行按 `(stat_date, staff_id, ...)` 唯一，重算即覆盖 |
| `m20_doc_oper_log` | 否 | **审计日志，只增不删**，`REVOKE UPDATE, DELETE` + 月分区 |

**注意数据结构汇总 §7.3 的警告：带 `is_deleted` 的表，唯一索引不写 `WHERE is_deleted = FALSE`**——那会让软删除行脱离唯一约束，软删两次同一目标就出现两个「未被约束的相同行」。本子模块的软删除表用**部分唯一索引 + `is_deleted` 参与列**的方式规避，或直接让软删除行改写业务键（例如 `m20_doc_shortcut` 软删时把 `sort_no` 置负）。具体做法见各表。

### 3.3 时间与数值

### 4.2 表：`m20_doc_page_layout`（医生站页面编排）

**用途：** 存医生站首页与各功能页的**卡片编排**——哪些卡片、什么顺序、什么尺寸、对谁生效。它描述「这个医生打开 App 看到的首页长什么样」，是本子模块最纯粹的适配层数据，不含任何临床信息。

**写入方：** M20-02 医生站配置页（P10）；科室管理员批量下发（`scope_type='DEPT'`）。
**只读方：** M20-02 首屏渲染；M20-01 移动端接入层（下发客户端灰度配置）。


**索引说明：**

| 索引 | 用途 |
|---|---|
| `uk_m20_doc_page_layout_code` | 编排编码唯一；配置页按编码取最新版本 |
| `idx_m20_doc_page_layout_scope` | **首屏热路径**：按 `(范围类型, 范围ID, 页面键)` 一次取出当前生效的编排，部分索引只含未删且生效的行，避免首屏扫到历史版本 |
| `idx_m20_doc_page_layout_page` | 配置页按页面键列出所有编排；后台按 `is_default` 找全院默认 |

**设计说明：**

1. **`card_list` 用 JSONB 而不是拆卡片子表。** 判据：卡片集合是**整体读、整体写**的（首屏一次拿全份编排），且卡片之间没有独立生命周期（不存在「只改第 3 张卡」的并发场景）。拆子表会让首屏变成「一次主表 + 一次子表 + 内存拼装」，多一跳 RTT，而首屏预算只有 900ms 业务聚合。**代价**：卡片级查询（「哪些编排用了 BED_SUMMARY 卡」）要靠 GIN 索引，本子模块确实不需要这个查询，所以代价为零。
2. **`card_count` 冗余成列并配组合约束 `card_count = jsonb_array_length(card_list)`。** 这是「有列表就有长度」的通用做法：没有这列，`LIMIT`/排序要靠 `jsonb_array_length()` 表达式，无法建索引；有这列但没约束，就会出现「数组有 5 个元素、计数写 3」的静默错误。
3. **`scope_id` 在 `HOSPITAL` 时填 `0` 而不是 `NULL`。** PostgreSQL 的唯一索引认为 `NULL` 互不相等，若允许 `NULL`，`(layout_code)` 之外的业务唯一键（`page_key + scope_type + scope_id`）在全院默认行上会失效，可以插入无数条「全院默认首页编排」。
4. **`is_default` 只能由 `HOSPITAL` 行承担**（`ck_..._default`）。否则科室可以把自己设成「全院默认」，而全院默认的语义是「所有没配过的医生都用它」，两者冲突时无从裁决。
5. **不加 `(page_key, scope_type, scope_id)` 的唯一约束。** 因为同一范围同一页面**可以有多个历史版本**（`is_effective=FALSE` 的旧版本要留着，供审计与回滚）。生效中的唯一性由「首屏查询按 `layout_version DESC LIMIT 1`」保证，而不是靠唯一约束——**如果加唯一约束，回滚功能就没有数据来源了**。

### 4.3 表：`m20_doc_shortcut`（医生快捷入口与收藏）

**用途：** 医生在移动端首页的快捷入口（「我的患者」「待签病历」「危急值」这类功能位）与收藏（常看的患者、常查的病区）。它决定「医生点两下能到哪」，是纯个人化配置。

**写入方：** M20-02 首页与各列表页的「加星」动作。
**只读方：** M20-02 首屏；M20-01 客户端配置下发。

**索引说明：**

| 索引 | 用途 |
|---|---|
| `uk_m20_doc_shortcut_target` | 同一医生不能重复加星同一目标；**把 `is_deleted` 放进唯一键**，软删后可以重新添加同目标（软删行与新增行键值不同，不冲突） |
| `idx_m20_doc_shortcut_staff_order` | **首屏热路径**：按医生取排好序的快捷项，`is_pinned DESC, sort_no, use_count DESC` 与页面的排序规则完全一致，避免内存排序 |
| `idx_m20_doc_shortcut_patient` | 患者合并（`mpi.patient.merged`）时反查「谁收藏了这个患者」，用于重定向 |

**设计说明：**

1. **唯一键把 `is_deleted` 作为表达式列放进索引，而不是写 `WHERE is_deleted = FALSE`。** 这正是数据结构汇总 §7.3 警告规避法：若只写 `WHERE is_deleted = FALSE`，软删一行后再插同一目标 → 新行不冲突（✓），但**软删的行本身脱离约束**，若有人把同一行软删两次或插入两条已软删的同目标行，约束不管。把 `is_deleted` 作为列放进去后，`(staff, PATIENT, 10001, FALSE)` 与 `(staff, PATIENT, 10001, TRUE)` 是两个键，**至多各一条**——软删可以重加，且软删行也不会无限重复。
2. **`target_name` 是显示名快照，不是权威名。** 患者改名后快照不会自动变。**这不是缺陷而是取舍**：每次渲染快捷项都去 M03 查权威名，8 个快捷项就是 8 次调用，首屏预算直接爆。快照只用于列表展示，进详情必须重新取权威值。**风险是「列表里显示旧名」**——可接受，因为列表里本来就要脱敏显示（`张*明`），改名后脱敏形态差异极小；而**任何临床决策页面都不允许用快照名**（这条写进详细设计 §8）。
3. **`shortcut_type` 与 `target_type` 必须相同**（`ck_..._type_match`）。拆成两列是因为一处是「入口分类」（决定 UI 用哪种卡片样子），一处是「目标实体」（决定点击后跳哪）；但语义上必然一致，所以用组合约束钉死。**为什么不合并一列**：合并后功能位（`FUNCTION`）的 `target_id` 语义（恒 0）与患者（`PATIENT`）的语义（`patient_id`）挤在同一枚举里，取舍规则无法在 CHECK 里表达。
4. **`use_count` 与 `last_used_at` 同生共灭**（`ck_..._use`）。防「有次数没时间」（说明计时没写）或「有时间次数为 0」（说明计数没写），这两种都是静默丢数据的征兆。

### 4.4 表：`m20_doc_recent_visit`（最近访问患者）

**写入方：** M20-02 患者详情页每次打开（`OPEN` 动作）后写一条。

**索引说明：**

| 索引 | 用途 |
|---|---|
| `uk_m20_doc_recent_visit_staff_patient` | 同一医生对同一患者**只有一行**（访问次数累加、时刻更新），避免「最近」列表里同一患者出现 20 次 |
| `idx_m20_doc_recent_visit_staff_time` | **热路径**：按医生取最近 N 条，`last_visit_at DESC` 与页面排序一致 |
| `idx_m20_doc_recent_visit_patient` | 患者合并时把 `patient_id` 改为主患者（`mpi.patient.merged` 订阅处理） |

**设计说明：**

1. **一人一行而不是一行一次访问。** 判据：页面要的是「最近看的患者」，去重后的列表才有用。若一行一次访问，取最近 10 个不同患者需要 `GROUP BY patient_id` 全扫。**代价**：丢失「这个患者我看了几次的具体时刻」，但那正是 `m20_doc_oper_log` 的职责，本表只留 `visit_count` 与 `last_visit_at`。
2. **不存 `is_deleted`。** 语义上不存在「删除一次访问」，超过保留条数时由异步任务物理淘汰最老的行（`app_m20` 对本表有 DELETE 权限，因为**它存的不是审计事实，而是缓存性质的个人工作记忆**，这也是本子模块唯一允许 DELETE 的业务表）。
3. **`patient_display` 存脱敏名，不存真名。** 这条是硬约束：本表会被首页列表高频读取，一旦存真名，M20 库就成了一个「姓名可被批量拉取」的泄露面。脱敏名直接取上游 `brief` 接口的返回值（M03-01 API-37 已按权限脱敏），**M20 不自行拼接脱敏规则**——脱敏规则的权威在 M03，两处各写一套必然分叉。
4. **`bed_no` 用空串不用 NULL。** 与共享规范 §7.2 的「维度字段无值存空串」一致；住院患者出院后床号会变空，用空串表示「当前无床号」。
5. **`visit_type='INPATIENT'` 必须有 `admission_id`、非住院必须有 `encounter_id`**（`ck_..._enc`）。这两类定位键的语义不同：住院靠住院号定位（一次住院可以有多次就诊），门诊靠就诊号定位。**允许两者都填是对的**（住院患者也可能有一次门诊就诊作为入院途径），所以非住院分支只要求 `encounter_id` 非空，不禁止 `admission_id`。

### 4.5 表：`m20_doc_round_plan`（查房路线计划）

**用途：** 一次查房的**安排**——哪天、哪个病区、谁查、按什么顺序、查到哪了。它是「查房这件事本身」的记录，不含任何临床内容（诊断、病历、医嘱全在上游）。

**写入方：** M20-02 查房页新建/开始/结束查房。
**只读方：** M20-02 查房列表与路线页；M20-01 首页卡片（「今日查房进度」）。


**索引说明：**

| 索引 | 用途 |
|---|---|
| `uk_m20_doc_round_plan_no` | 查房单号唯一；对外只暴露单号不暴露主键 |
| `idx_m20_doc_round_plan_staff_date` | 热路径：医生看自己最近几次查房 |
| `idx_m20_doc_round_plan_ward_date` | 科室/病区看今天谁查了房（护士长与科主任的视角） |
| `idx_m20_doc_round_plan_active` | 部分索引只覆盖进行中的计划：**「我有没有一条没结束的查房」是每次进查房页的第一个查询**，全表里进行中的行永远只有个位数，部分索引让它接近 O(1) |

**设计说明：**

1. **`plan_status` 四态，`ABANDONED` 独立于 `COMPLETED`。** 放弃的查房不是完成——`COMPLETED` 要求 `item_total = item_done + item_skipped`（每个患者都有交代），`ABANDONED` 允许查到一半就走了（组合约束 `ck_..._done` 只对 `COMPLETED` 生效）。**为什么不合并成「完成（含中途放弃）」**：合并后无法回答「这个医生有没有真的查完 20 个患者」，而这正是查房质量考核的输入。
2. **`abandon_reason` 与 `abandoned_at` 强制成对**（`ck_..._abandoned`），且理由至少 5 字。「放弃查房」是罕见动作，每一次都值得知道原因（患者突发病情？被叫去手术？设备没电？）；不写理由的放弃无法复盘。
3. **`finished_at` 只在 `COMPLETED` 时非空**（`ck_..._finished`），且 `>= started_at`。放弃用 `abandoned_at`，两者不共用列——**共用会导致「这个时刻到底是完成还是放弃」要靠 `plan_status` 反推**，而状态可以被后面的 UPDATE 改，时刻不会。
4. **`item_total`/`item_done`/`item_skipped` 是冗余计数，不是真相。** 真相在 `m20_doc_round_item`。冗余的理由是查房列表页要显示进度条，每行一次 `count(*)` 子查询是 N+1。**一致性由服务层在同一事务内回写保证**，并由每日 `orphan_check` 任务核对「冗余计数 ≠ 明细实际计数」的漂移；漂移时以明细为准重建计数。
5. **`round_date` 与 `created_at` 分离。** 医生可以 11-06 晚上排好 11-07 的查房，也可以 11-07 早上补录 11-06 的查房（补录是合法的，因为有些科室是事后补记）。用 `created_at` 当业务日期会让统计口径随记录时刻漂移。
6. **`is_deleted` 只在「录错了」时用。** 正常的取消走 `ABANDONED`。两者区别：`ABANDONED` 是**有意义的业务事实**（确实计划过又放弃了），`is_deleted` 是**这条记录本来就不该存在**（建错了病区、重复建了两次）。**把它们合成一个状态，等于把「录入错误」当成了「业务事件」**，统计时会多出一堆假放弃。

| `fk_m20_doc_round_item_plan` | M20 内部外键；删计划时级联阻断（计划不物理删，只有 `is_deleted`） |
| `uk_m20_doc_round_item_seq` | 同一计划内顺序号唯一，防止拖拽后出现两个序号 3 |
| `uk_m20_doc_round_item_adm` | **同一计划内同一次住院只能出现一次**。没有它，重复点「生成路线」就会让 20 个患者变成 40 行 |
| `idx_m20_doc_round_item_plan_status` | 热路径：查房页按「待查→已查」列出，`seq_no` 保证顺序 |
| `idx_m20_doc_round_item_patient` | 患者合并时重定向（`mpi.patient.merged`） |
| `idx_m20_doc_round_item_adm` | 出院/转科事件到达时按 `admission_id` 找到所在路线 |
| `idx_m20_doc_round_item_open` | 部分索引只含待查行：**「下一个待查是谁」是查房页每点一次都要查的**，待查行永远是少数 |

**设计说明：**

1. **床上信息全是快照（`bed_no_snapshot`、`patient_display`），不建触发器去同步。** 理由：查房路线的价值在于「早上 8 点按这个顺序查」，患者 10 点转床不应该让路线图重排。**如果同步，会出现「查着查着床位变了，第 3 个患者跳到第 7 个」——而医生已经按原顺序走到了第 4 床。** 提示「这个患者已转床」用 `resident_status='TRANSFERRED'`，改状态不改顺序。
2. **`resident_status` 五态，`DISCHARGED`/`TRANSFERRED` 是「计划时在院、执行时不在」。** 这是 §1.4 论证里提到的那类信息。**取消它们的 `visited_at`**（`ck_..._gone` 强制 `visited_at IS NULL`）——一个已转科的患者不可能同时是「本次查出」，若两者并存，统计会重复计入。
3. **`uk_m20_doc_round_item_adm` 是防重复的**核心约束。查房页的「生成路线」按钮可以点多次（网络慢时用户会连点），没有这条唯一约束，第二次点就把整批患者再插一遍，进度条变成 `0/40`。
4. **`has_record_view` 是首屏规则的效果度量位。** 它是「医生真的点开了病历看」的直接证据，而不是「列表渲染过」。这个字段让我们能回答一个关键问题：**「把病历正文从列表页挪到详情页」之后，医生实际看病历的比例有没有下降**。如果没有这个字段，这个改动就只能靠感觉判断。
5. **`has_draft` 是冗余标记，不建视图。** 草稿表行数少（12 万），但查房页每屏要显示 20 行的草稿标记；用 `EXISTS` 子查询每行一次是 20 次。冗余一列并由写草稿的服务层同步更新，代价是「草稿被别处删掉时标记没清」——由每日 `orphan_check` 校正。
6. **明细没有 `is_deleted`。** 明细的「不用了」全部落在 `resident_status` 上（`DISCHARGED`/`TRANSFERRED`/`SKIPPED`）。**建一个 `is_deleted` 会让「这个患者本来就不该在这条路线上」与「这个患者不在了」变成同一个操作**，前者是录入错误、后者是业务事实。

### 4.7 表：`m20_doc_note_draft`（病程记录草稿）

**用途：** 医生在移动端写病程记录的**中间态**——语音转文字的结果、手写的要点、还没提交的半成品。它存在的唯一理由是：**弱网下医生输入的内容不能丢**。

**它是本子模块唯一存临床文本的表，因此有三条硬约束**（详见 §2.3 与下方设计说明）：

1. **不被检索**——`draft_text` 不进任何全文索引、不进任何报表、不能被其他医生看到；
2. **有明确终点**——提交成功（`SAVED`）后 `draft_text` 必须清空，24 小时内未提交的行由定时任务物理清除；
3. **归属单一**——一行只属于一个医生，只有本人可读可写。

**写入方：** M20-02 病程记录编辑页保存草稿（自动与手动）。
**只读方：** M20-02 病程记录编辑页恢复草稿；查房页读 `has_draft`（不读正文）。

| `idx_m20_doc_note_draft_expire` | 定时任务按 `expires_at` 扫描待清除行；部分索引排除 `SAVED`（它们是永久痕迹，不清） |
| `idx_m20_doc_note_draft_item` | 查房页按明细查草稿标记 |

**设计说明（这张表的每一条都要紧）：**

1. **`SAVED` 时 `draft_text` 必须清空**（`ck_..._editing` 强制）。这是「草稿被采纳后必须清掉，不能成为第二份来源」的数据库层落地。**不这么做的后果**：提交成功后正文还留在 M20 库里，M18 那边也有了一份；将来病历被作废重开，M20 库里这份「旧草稿」就是一份无法判定权威性的临床文本，而它出现在 M20 库这个权限面更宽的地方。
2. **`expires_at` 是硬性过期，不是软提示。** 24 小时内没有提交的草稿，会由定时任务**物理删除**（本表是 `edit` 语义的中间态，`app_m20` 有 DELETE 权限）。**为什么要物理删**：一台手机可能被借给别人、可能被回收、可能被老婆拿去拍照——只要草稿还在，它就是一个「过了很久还能被翻出来的患者病情文本」。**保留期按「一次值班的时长」定就够了**。
3. **`target_section` 可空，且 `NULL` 有明确语义**（医生还没决定写进哪一段），**不是缺省标记**。这与共享规范「维度字段无值存空串」的规则**看起来冲突，实际不冲突**：那条规则针对的是**参与唯一约束的维度列**（`NULL` 互不相等会让唯一约束失效），`target_section` 不参与任何唯一约束，且 `NULL` 与「空串」在这里是两种语义（空串 = 选了段落但段落编码为空，不可能发生；`NULL` = 还没选）。用 `NULL` 才能与「已选 CHIEF_COMPLAINT」区分开。
4. **`uk_m20_doc_note_draft_active` 只约束 `EDITING`/`SUBMITTING`**，不约束 `SAVED`/`DISCARDED`。**因为「同一就诊写过 3 次日病程」是合法的**（早中晚各一次），历史草稿不该被唯一约束卡住。部分唯一索引的 `WHERE` 只覆盖活跃态，正是为这种「活跃唯一、历史多份」的场景设计的。
5. **本表不被任何其他模块读，也不进任何跨模块视图。** 这是「它不会被当成病历」的架构层保证。
6. **语音草稿的 `draft_text` 是转写结果，不含音频。** 音频不落库、不上传（在客户端内存里转写后丢弃）。**存音频会让 M20 库变成一个有语音病历的库**，权限面、存储、合规全都升级一个量级，而收益只是「重听一遍」——这个功能应该由医生用录音笔记 App 自己做，不该进 HIS。
7. **`text_length` 用 `char_length` 不用 `length`。** PostgreSQL 的 `length(text)` 与 `char_length` 等价（都按字符计），但 `length(bytea)` 按字节。**这里显式写 `char_length` 是为了让人一眼看出口径**——中文按字计，20,000 字是病程记录的一个合理上限。
8. **本表没有 `is_deleted`，`DISCARDED` 就是删除语义。** 但 `DISCARDED` 行只保留到 `expires_at` 之后被物理清除，保留它只是为了排查「我明明写了怎么没了」。

### 4.8 表：`m20_doc_usage_stat`（医生站使用统计）

| `uk_m20_doc_usage_stat_dim` | `(日期, 医生, 科室)` 唯一，**重算即覆盖**（`ON CONFLICT DO UPDATE`），不需要先删后插 |
| `idx_m20_doc_usage_stat_date` | 统计页热路径：按日期看全院/全科室排行 |
| `idx_m20_doc_usage_stat_staff` | 医生看自己的使用趋势 |
| `idx_m20_doc_usage_stat_degraded` | 部分索引只看「有降级的日子」，用于降级专项排查 |

**设计说明：**

1. **首屏 P95 与样本数必须成对**（`ck_..._p95`）。**0 样本时报 0ms 是最典型的假指标**——看板上一片绿，其实那天根本没人用。样本为 0 时 `first_screen_p95_ms` 必须是 `NULL`。
2. **`calc_status` 三态与 `missing_sources` 组合穷尽**（`ck_..._missing`）。这与总纲「上游失败不能当成没有」同源：统计任务读 `m20_doc_oper_log` 时若某个小时分区不可用，结果必须标 `PARTIAL` 并写明缺了哪个来源，**不能把缺失当成 0**——那样日报会显示「今天没人用移动医生站」，而真相是数据没算出来。
3. **`degraded_count <= request_count`**（`ck_..._view`）。降级次数是请求数的子集，违反这条只可能是统计口径错了。
4. **`course_submit_count` 只统计提交成功，不统计编辑次数。** 编辑次数是过程指标，容易靠反复保存刷高；提交成功是结果指标，直接对应「病历上多了一条病程记录」。
5. **`critical_view_count` 只是「看过」**，因为本子模块对危急值只读（§2.4）。这个计数的用途是度量「危急值提醒真的把人引过去了没有」。
6. **本表无 `is_deleted`。** 统计行按维度唯一，重算覆盖；撤销某天统计就是删该天的行（由 `m20_archiver` 或运维处理，`app_m20` 无 DELETE 权限）。

**设计说明：**

1. **日志表只增不删：`REVOKE UPDATE, DELETE` + 月分区。** 两者的分工是：`REVOKE` 挡住「改日志、删日志」这种掩盖行为；分区让**历史清理不靠 `DELETE`**——36 个月后 `ALTER TABLE ... DETACH PARTITION` 后转入只读库，原行仍在，只是不在主表里。**这满足「审计日志不能删」与「主表不能无限长大」两个互相冲突的要求。**
2. **`PRIMARY KEY (id, created_at)` 而不是只有 `id`。** PostgreSQL 分区表的唯一约束必须包含分区键，`created_at` 是分区键，所以主键必须带它。代价是 `id` 单独不唯一**在理论上**——但 `GENERATED ALWAYS AS IDENTITY` 保证全局递增不重复。
3. **`degraded = FALSE OR data_quality <> 'REALTIME'`**（`ck_..._degraded`）。这条把「降级却标实时」这种自相矛盾的日志行挡在数据库外。**它是数据层的一条断言，不是提示**：如果一个响应降级了却记成 REALTIME，后面的降级率分析全是错的，而这个错误没有任何其他检查能发现。
4. **`detail` 里禁止放病历正文与患者姓名。** 这不是习惯问题，是权限问题：**操作日志的读取权限面远大于病历正文**——医务科、质控、运维都可能查日志，而看具体某个患者的病历正文要按 M02 的数据权限走。日志里塞了正文，等于给了一批不需要病历权限的人一条绕过路径。要证明「谁看过哪份病历」，`record_id` + `created_at` 足够；要证明「内容是什么」，回 M18 按权限查。
5. **`result='DENIED'` 也记。** 被拒请求是攻击性探测的最早信号（有人在试能看哪些患者的病历）。**只在成功时记日志，等于把探测行为藏起来了。**
6. **`device_id` 是客户端生成的匿名标识，不是硬件标识。** 不采集 IMEI/IDFA/Android ID——那属于过度采集，且与「M20 不建第二套身份」的红线冲突。
7. **`DEFAULT` 分区必须建，且必须被监控。** 漏建月份时写入会因为 DEFAULT 分区而不报错（**不报错正是危险所在**——数据进了一个没人看的兜底分区，查「上月日志」时一条都没有）。因此监控对 `m20_doc_oper_log_pdefault` 有任何行就告警，运维补建分区并迁移。这与数据结构汇总 §4「分区表必须有 DEFAULT 分区」的要求一致，但补上了汇总没说的那半句：**DEFAULT 分区是安全网，不是设计意图**。
8. **本表与 `m20_base_oper_log`（M20-01 通用操作日志）的关系**：本表是医生站的操作明细（权威），M20-01 通用日志只留一条指向 `(biz_table='m20_doc_oper_log', biz_id=id)` 的指针。两条日志在同一业务动作后各写一条，**本表写成功、通用日志写失败时不回滚本表**——审计留痕宁可多一条，不可少一条；失败项进补偿队列重试。

**为什么只有 `m20_doc_recent_visit` 与 `m20_doc_note_draft` 给了 `DELETE`：**

- `m20_doc_recent_visit`：它是**个人工作记忆**，不是审计事实。不淘汰会无限增长（每个医生 × 每个看过的患者一行），且淘汰哪一条不影响任何业务判断。
- `m20_doc_note_draft`：草稿过期必须**物理**清除（§4.7 设计说明第 2 条），这个删除是安全要求而不是运维便利。
- 其余表的「不要了」全部走状态（`ABANDONED` / `DISCARDED` / `is_deleted`），**没有 DELETE 权限就没有「删错了」的路径**。

**模型与 DDL 的对照说明：**

| 差异点 | DDL | ORM | 原因 |
|---|---|---|---|
| 分区 | `PARTITION BY RANGE (created_at)` + 4 个子表 | `__table_args__` 里 `postgresql_partition_by`，不声明子表 | 子表由迁移脚本建，ORM 只声明父表的逻辑结构 |
| 操作日志主键 | `PRIMARY KEY (id, created_at)` | 只映射 `id` 为 `primary_key` | ORM 声明主键只影响 identity 生成；分区键由 DDL 承担 |
| 部分索引谓词 | `WHERE ...` | `postgresql_where="..."` 字符串 | 保持与 DDL 完全一致的谓词文本，避免 ORM 生成不同表达式 |
| 权限 | `REVOKE UPDATE, DELETE` | ORM 无法表达 | 权限在迁移脚本 `m20_0005_04_grant_revoke.py` 里执行 |
| 数值类型 | `INTEGER` | `Integer`（**不用 `Float`/`Numeric`**） | 本表所有计数与耗时都是整数；本子模块无金额、无剂量 |

```python
    client_version: str = Field(default="", max_length=32)
    network_state: NetworkState = "WIFI"
    detail: dict[str, Any] = Field(default_factory=dict)

    @model_validator(mode="after")
    def _check_fail_code(self) -> "OperLogWrite":
        if self.result == "SUCCESS" and self.fail_code != "":
            raise ValueError("成功结果不得带 fail_code")
        if self.result != "SUCCESS" and self.fail_code == "":
            raise ValueError("失败/被拒结果必须带 fail_code")
        if self.degraded and self.data_quality == "REALTIME":
            raise ValueError("降级日志行的 data_quality 不得为 REALTIME")
        return self
```

**为什么 `plan_status` 不复用 §13 的 `task_status`**：`task_status` 的 `CLAIMED`/`EXECUTING`/`SKIPPED`/`REJECTED` 语义来自「任务分派」（一条任务可被领取、可被驳回），而查房计划是「一个人给自己排的路线」，没有分派、没有驳回。**强行复用会让 `CLAIMED`（被人领走）出现在查房上，而查房不存在「被领走」这个动作。** 共享规范 §17 第 31 条禁止自创枚举值的本意是「不要为同一个概念发明第二套值」，而不是「不许为不同概念定义不同值」。

**回滚**：`m20_0005` 整体可回滚，但**已产生 `m20_doc_note_draft` 的 `SAVED` 行与 `m20_doc_oper_log` 数据时不得回滚**——前者是「曾在此编写过」的痕迹，后者是审计留痕，回滚即丢失。

**上线必跑的三条校验 SQL：**

```sql
-- 1) 冗余计数与明细实际计数是否一致（应返回 0 行）
SELECT p.id, p.round_no, p.item_total, p.item_done, p.item_skipped,
       count(i.id) AS real_total,
       count(i.id) FILTER (WHERE i.resident_status = 'VISITED') AS real_done,
       count(i.id) FILTER (WHERE i.resident_status = 'SKIPPED') AS real_skipped
FROM m20_doc_round_plan p
LEFT JOIN m20_doc_round_item i ON i.round_plan_id = p.id
WHERE p.is_deleted = FALSE
GROUP BY p.id, p.round_no, p.item_total, p.item_done, p.item_skipped
HAVING p.item_total <> count(i.id)
    OR p.item_done <> count(i.id) FILTER (WHERE i.resident_status = 'VISITED')
    OR p.item_skipped <> count(i.id) FILTER (WHERE i.resident_status = 'SKIPPED');

-- 2) 是否有应当清空却仍留正文的草稿（应返回 0 行）
SELECT id, draft_no, draft_status, text_length
FROM m20_doc_note_draft
WHERE draft_status IN ('SAVED', 'DISCARDED') AND draft_text <> '';

-- 3) DEFAULT 分区是否有数据（有行即说明漏建月份分区，需补建并迁移）
SELECT count(*) AS overdue_rows FROM m20_doc_oper_log_pdefault;
```

## 附录 F：文档维护约定

| 约定 | 内容 |
|---|---|
| 表数量口径 | `**合计：N 张表**` 必须等于 `### 4.x 表：` 章节数，增删表必须同步改附录 A 与本行 |
| 枚举口径 | 任何枚举取值变更必须同步改三处：`CREATE TABLE` 的 CHECK、SQLAlchemy 的 `CheckConstraint`、Pydantic 的 `Literal`；引用共享规范 §13 的枚举不得自定义同义值 |
| 跨模块 ID | 新增任何指向其他模块的 ID 列，**不建外键**，并在 `COMMENT ON COLUMN` 里写明来源模块 |
| 分区表 | 新增分区表必须同时写 `DEFAULT` 分区，并在附录 E 的上线校验 SQL 里加一条 `count(*) FROM xxx_pdefault` |
| 敏感数据 | 任何新增列若可能承载患者姓名、手机号、身份证、住址、病历正文，必须先过两道判断：① 是否为其他模块的副本（是→不许建）；② 是否参与唯一约束（`NULL` 语义） |
| 定期评审 | 每季度复查一次：`is_deleted` 但从未出现过 `TRUE` 的表是否该去掉 `is_deleted`；`DEFAULT` 分区是否一直为空；`m20_doc_note_draft` 是否存在长期滞留的 `EDITING` 行 |
