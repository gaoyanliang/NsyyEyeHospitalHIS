## 1. 模块定位

### 1.1 一句话定位

**M20 移动办公是全院 19 个业务系统在移动终端上的唯一统一入口。它不拥有任何临床业务数据，只拥有三样东西：移动端的聚合与编排、跨模块的业务审批流引擎、员工消息与待办中心。**

它要解决的问题不是「把 PC 页面搬到手机上」，而是「**把 PC 端的深度操作翻译成移动端的即时决策**」——

| 场景 | PC 端做什么 | 移动端该做什么 |
|---|---|---|
| 医生查房 | 打开 M07 逐个患者看 8 个页签 | **一屏读完**这个患者的诊断、今日医嘱、最新检查、病历要点，且**只给需要决策的部分** |
| 护士给药 | 打开 M08 任务列表，逐个点开执行 | **床边扫码**核对后一键执行，**扫错立刻拦** |
| 院长批单 | 打开 M17 逐笔看明细 | 出差路上**看到金额与事由就能批**，明细下钻可选 |
| 医生看报告 | 打开 M12/M13 看完整报告 PDF | 先看**有没有异常、异常项是什么**，全文按需加载 |

### 1.2 为什么独立成模块（四条理由，各带事实）

**理由一：M20 的权力边界必须是「零业务数据」，这件事只有独立成模块才守得住。**

若把移动端挂在各业务模块里（例如 M07 自己出移动版），每个模块都会自然地「为移动端建几张轻量表」——M07 建 `m07_mobile_visit`、M05 建 `m05_mobile_round`、M08 建 `m08_mobile_task`。半年后全仓会多出 20 组「移动端专用副本表」，且每一组与主表之间都存在**状态不同步**的可能。

这不是假想：全仓已经因为「同一件事两处存」而反复裁界——M18 铁律 2 禁止自建 `m18_order`/`m18_diagnosis`，M20 铁律 2 禁止自建 `m20_order`/`m20_patient`。**独立成模块的最大价值是把「不许建业务表」变成一条对 8 个子模块统一生效、且可被脚本强制检查的规则。**

**理由二：审批这件事，全仓只有 M20 一处能做，而它服务的申请方横跨 3 个模块、13 个子模块。**

`POST /internal/v1/m20/approval/apply` 在全仓被引用 **25 处**，调用方包括 M10-06、M10-07、M11-01/02/05/06/07/08、M17-01/02/05/06/07/08。这些申请方共同的诉求是「**把一件我不该自己拍板的事，交给一条规则确定的链去批**」——改单 400 元要店长批、停台要科主任批、反结账要财务经理批。

如果这条链由各申请方自己实现，会出现「M10 的改单要 2 级审批、M11 的停台要 3 级」，而**院办改一次制度要改 13 个地方**，且没有任何一处能回答「全院还有哪些单据卡在审批里」。M20 存在的意义就是：**审批链配置、审批人在线状态、超时催办、审批留痕，只在 M20 这一处定义。**

（注意：这与 M01-11 的主数据审批是**两套**，裁决依据见 §5.1 与共享规范 §1.2。）

**理由三：员工消息是一个被明确划出来的空缺，且 M03-05 已经把「不做」写进了自己的范围外。**

`M03患者服务与EMPI/M03_患者服务与EMPI_05_消息_详细设计.md:43` 原文：「本子模块只管『消息的生产、发送、回执、重试、退订与脱敏』；**不做**业务事件产生……**不做**网关实际对接（M21 封装短信/微信/邮件网关），**不做**患者端消息展示页面（M03-06），**不做员工站内信（M20）**」；`:56`「员工站内信、审批消息 | M20 | 独立体系，不归本模块」；`:108` 同。

也就是说：**患者的短信、微信、患者端站内信归 M03-05 + M21；员工的站内信、审批消息、系统通知归 M20。** 这个空缺不填，「护士超时未执行」「质控发现缺陷」「危急值已出」这些事件就没有一个人能收到。

**理由四：移动端的技术约束与 PC 端不是同一套，混在一起写会把两边的设计都做坏。**

| 约束 | PC 端 | 移动端 |
|---|---|---|
| 单次响应载荷 | 无硬约束 | 列表页必须摘要化（报告全文 200KB × 20 条 = 4MB） |
| 网络 | 有线/稳定 WiFi | 电梯、地下车库、手术间、病房拐角**随时断** |
| 身份有效期 | 一次登录管一个班 | **空闲 15 分钟自动锁屏**（M02-07 §3.7） |
| 操作方式 | 键鼠，可多窗口 | 单手持握、单手拇指可达区域、需要扫码/拍照 |
| 连点 | 少见 | **常态**（信号差时用户会连点 3 次，客户端自动重发 5 次） |
| 数据新鲜度 | 刷新即最新 | 60 秒缓存意味着**看到的是 60 秒前的世界**，必须有可见提示 |

把这些差异写成 8 个业务模块各自的一段「移动端注意事项」，是写不住的——**它会被写成一句话然后没人再看**。独立成模块才能让「弱网」「连点」「缓存可见性」「单手可达」成为一等公民。

### 1.3 与相邻模块的边界

| 相邻模块 | M20 做什么 | M20 不做什么 | 边界依据 |
|---|---|---|---|

### 1.4 一条不可逾越的红线

> **M20 的回答是「现在该看什么、现在该批什么、现在该做什么」；它永远不回答「这条数据是什么」。**

这条红线是所有子模块设计的最终判据。当你想在 M20 建一张表时，问自己一句：**这张表存的东西，如果 M20 删库重建，会不会有业务事实丢失？**

- `m20_apr_instance`（审批实例）：**会**。审批链走到第几级、谁批的、什么时候批的，只有 M20 有。→ **可以建。**
- `m20_doc_patient`（患者副本）：**不会**。M03 有权威记录。→ **不许建。**
- `m20_msg_inbox`（员工站内信）：**会**。M03-05 明确不存员工消息。→ **可以建。**
- `m20_qry_search_log`（检索留痕）：**会**。这是审计事实，只有 M20 有。→ **可以建。**

红线的一句话版本：**M20 只拥有「流程事实」与「通道事实」，不拥有任何「临床事实」与「账务事实」。**

### 2.3 为什么这么分

拆分依据是「**使用者 × 场景 × 数据读写方向**」三者同时一致，而不是按「上游模块一对一映射」：

| 子模块 | 主要使用者 | 场景 | 读写方向 |
|---|---|---|---|
| M20-01 | 所有用户 + 运维 | 登录后、断网时、升级时 | 基础设施，不碰业务数据 |
| M20-02 | 医生 | 查房、值班、会诊 | **读多写少**（看的多，开的处方少） |
| M20-03 | 护士 | 床边执行、交接班 | **写多读少**（执行动作密集） |
| M20-04 | 各级管理者 + 申请方系统 | 审批、催办 | **写密集 + 强一致** |
| M20-05 | 全院任意角色 | 临时查一件事 | **纯读** |
| M20-06 | 视光师 + 销售 | 柜台/上门服务 | **写密集 + 需拍照扫码** |
| M20-07 | 随访专员 | 电话/微信随访 | **写中等 + 需消息通道** |
| M20-08 | 所有用户 + 其他模块 | 收消息、看待办 | **通道 + 聚合** |

**为什么没有「移动管理端」独立子模块**：管理者的需求（看板、预警）与查询高度重叠，且 M22-08 已有 `MOBILE` 类型驾驶舱。若独立成子模块，会产生「移动查询页也显示指标、移动管理页也显示指标」的两套聚合逻辑。**因此把管理者看板并入 M20-08（消息与待办中心）——因为它们回答的是同一个问题：「现在有哪几件事需要我处理」。**

**为什么 M20-04 有 11 页、36 个接口，比别的子模块都大**：审批是 M20 唯一「有真正业务状态机」的部分，而它的复杂度不来自功能数量，来自**边界情况**——加签、转办、委托代理、超时升级、撤回、撤回复审、免审类型、跨级审批、多人会签（且会签又有「全部同意」与「任一同意」两种语义）。这些边界每一个都会在真实医院里发生。

## 3. 两条业务闭环

M20 有两条贯通全模块的闭环。子模块设计若破坏任何一条闭环的完整性，就会出现「系统显示做完了，实际没做完」。

### 3.1 闭环一：审批闭环

```
① 申请方发起 ──▶ ② M20 解析审批链 ──▶ ③ 逐级审批 ──▶ ④ 结果通知 ──▶ ⑤ 申请方执行 ──▶ ⑥ 执行结果回执
   P-01 apply      m20_apr_rule          m20_apr_node   事件/回调       申请方自己做事      M20 记录闭环
```

**闭环上的三个典型断点（设计必须逐一堵住）：**

| 断点 | 现象 | 根因 | 堵法 |
|---|---|---|---|
| **断点 A** | 审批已通过，但申请方没收到/没执行 | 事件发到了 MQ 但消费方挂了；或只发了 `approval_no` 而消费方需要 `biz_no` | ① 事件载荷必须含 `biz_type` + `biz_no` + `result`；② 申请方执行完必须回调 `POST /internal/v1/m20/approval/{no}/receipt`；③ 超过 N 分钟未收到回执，M20 置 `EXEC_UNCONFIRMED` 并告警 |
| **断点 B** | 审批一直在「待审批」，但审批人早已离职/调岗 | 审批链解析时把审批人钉死在节点上 | ① 节点落的是 `approver_id` 快照，**但**每日扫描检查该 `staff_id` 是否仍在职且在角色内；② 不在则触发 `TRANSFERRED` 到当前解析出的新审批人，并留痕 |
| **断点 C** | 审批通过后业务执行失败（库存不足、已封账），单据永远停在「已批准」 | 把「审批通过」当成「业务生效」 | **铁律 5**：M20 只发通知不改表；申请方执行失败必须回调 `receipt` 且带 `exec_result = FAILED` + 失败原因，M20 置 `APPROVED_BUT_FAILED`，页面必须显著区分 |

> **`APPROVED_BUT_FAILED` 这个状态是本节的核心。** 没有它，「已批准」与「已生效」就是同一个词，而它们在医院里差着一笔真金白银。M20-04 必须在状态机里显式定义它，并在移动端待办里把它推给**申请人**（「你批过的改单执行失败了，请处理」），而不是推给审批人。

### 3.2 闭环二：移动端数据新鲜度闭环

```
① 移动端请求 ──▶ ② M20 聚合多上游 ──▶ ③ 计算 as_of 与 degraded ──▶ ④ 页面显示截止时刻 ──▶ ⑤ 用户知道数据有多旧
```

**判据（写进 M20-01 的验收）：**

> **同一个屏幕上显示的所有数据，必须能用一句话说清它的截止时刻。如果说不清，就说明这个页面拼了不该拼的数据。**

三个具体的落地要求：

1. **`as_of` 取所有成功上游里最早的那个**（共享规范 §8A.4）。A 模块截止 10:00、B 模块截止 10:05，页面 `as_of` 必须是 10:00。
2. **`data_quality = CACHED` 时页面必须有可见提示**（如顶部黄条「数据截至 10:05，下拉刷新」）。没有提示的降级等于欺骗（共享规范 §17 第 24 条）。
3. **任一上游降级，整体 `degraded = true`**——是「或」不是「与」。

**为什么这条闭环值得单独立一节**：移动端最大的信任问题是「我看到的和 PC 端不一样，而且不知道为什么」。一旦医生发现手机上的数据不可信，他就会退回 PC 端，M20 的存在价值归零。**所以「新鲜度可见」不是体验优化，是 M20 的生存条件。**

## 4. 全局状态机

M20 有五套状态机。**状态取值必须与子模块一字不差**，子模块不得新增状态（确需新增须回改本文件）。

### 4.1 审批实例状态机（M20-04）

```
                    ┌──────────────────────────────────────────┐
                    │                                          │
   [P-01 申请]      ▼                                          │
   ──────────▶ DRAFT ──提交──▶ PENDING ──首节点激活──▶ APPROVING │
                                │                       │      │
                                │ 免审                   │ 全部通过
                                │                       ▼      │
                                └──────────────────▶ APPROVED ─┘
                                                        │
                                    ┌───────────────────┼──────────────────┐
                                    │ 申请方执行成功     │ 申请方执行失败    │ 收到驳回
                                    ▼                   ▼                  ▼
                                COMPLETED        APPROVED_BUT_FAILED   REJECTED

   APPROVING ──任一节点驳回──▶ REJECTED（终态）
   APPROVING ──申请人撤回──▶ CANCELLED（终态）
   APPROVING ──节点超时且无审批人可用──▶ TIMEOUT（非终态，可转办后回到 APPROVING）
```

| 状态 | 是否终态 | 含义 | 谁会看到它 |
|---|---|---|---|
| `DRAFT` | 否 | M20 内部中间态，P-01 落库到首节点激活之间 | 只有 M20 |
| `PENDING` | 否 | 已受理，等待首节点审批人处理 | 申请人、审批人 |
| `APPROVING` | 否 | 至少一个节点审批中 | 申请人、当前节点审批人 |
| `APPROVED` | 否 | 全部节点通过，**已通知申请方，尚未收到执行回执** | 申请人、审批人 |
| `COMPLETED` | **是** | 申请方回执执行成功 | 申请人 |
| `APPROVED_BUT_FAILED` | **是** | 申请方回执执行失败（需人工处理） | **申请人**（重点） |
| `REJECTED` | **是** | 任一节点驳回 | 申请人 |
| `CANCELLED` | **是** | 申请人主动撤回 | 申请人 |
| `TIMEOUT` | 否 | 所有审批人均不可用（离职/封禁/长期未响应），需管理员介入 | 管理员 |

**两条硬规则：**

- **`TIMEOUT` 不得折叠进 `REJECTED`。** 超时的业务含义是「没人处理」，驳回是「有人明确不同意」。前者要重提或升级，后者要改内容再提。折叠会让申请人以为「领导不同意」，实际领导根本没看见（共享规范 §17 第 22 条）。
- **`APPROVED` 不是终态。** 这一条是本状态机设计的关键。把 `APPROVED` 当终态，就等于承认「审批通过 = 业务生效」，而这正是断点 C 的成因。

### 4.2 审批节点状态机（M20-04）

```
WAITING ──前序节点全部通过──▶ PENDING ──审批人同意──▶ APPROVED
                                 │
                                 ├──审批人驳回──▶ REJECTED（后续节点全部 SKIPPED）
                                 ├──转办──▶ TRANSFERRED（原节点留痕，新节点替换）
                                 └──前置条件不满足（免审/条件跳过）──▶ SKIPPED
```

**规则：**
- `SKIPPED` 有两种成因（免审跳过、因前序驳回而终止），**必须在 `skip_reason` 里区分**，否则统计「审批效率」时会把「因驳回而跳过」算成「免审通过」。
- `TRANSFERRED` 保留原审批人记录，**不覆盖**。转办后原审批人不再对该节点有操作权。

### 4.3 护理任务状态机（M20-03）

**M20 不自建状态，直接沿用 M08 的 `task_status`**：`PENDING` / `CLAIMED` / `EXECUTING` / `COMPLETED` / `SKIPPED` / `REJECTED`（与 M08 API-30 `?status=CLAIMED,EXECUTING` 一致）。

> **为什么这里写「沿用」而不写「重新定义」**：护理任务的状态机是 M08 的，M20 只显示与触发。如果 M20 自己定义一套，会出现「M08 说已完成、M20 说执行中」——而护士看的是 M20。共享规范 §13 的 `task_status` 只是引用，不是定义。

### 4.4 离线队列状态机（M20-01）

```
QUEUED ──开始同步──▶ SYNCING ──成功──▶ SYNCED（终态）
                        │
                        ├──版本冲突──▶ CONFLICT（人工处理，禁止自动覆盖）
                        └──失败重试达上限──▶ FAILED ──人工放弃──▶ ABANDONED（终态）
```

**硬规则：`CONFLICT` 不得自动解决。** 离线期间单据可能被作废、改单、退费。重放时版本不一致，自动覆盖等于**把已作废的单据救活**。必须进 `CONFLICT` 由人决定（共享规范 §17 第 9 条）。

### 4.5 消息投递状态机（M20-08）

```
PENDING ──发送──▶ SENT ──网关回执──▶ DELIVERED ──用户已读──▶ READ
   │                 │
   └──失败───────────┴──重试达上限──▶ FAILED
```

**规则：**
- `SENT` 与 `DELIVERED` 必须分开。「已发出」不等于「已收到」——短信网关返回 200 只证明提交成功，用户可能手机关机。
- `FAILED` 的消息必须能在「消息中心」被查阅，**不得静默丢弃**。一条推送失败的系统通知，等于这条通知从未存在。

### 5.4 三道不可关闭的闸门

M20 有三条「宁可拦错也不能放过」的判定。**它们的错误方向必须一律朝「更严格」，子模块不得以「提高效率」「减少打扰」为由放宽。**

| 闸门 | 判定 | 错误方向 | 为什么不可关闭 |
|---|---|---|---|
| **G-1 扫码核对闸门** | 护士床边执行前，扫手腕带得到的 `patient_id` 必须与任务上的 `patient_id` 一致，且扫药品得到的 `drug_code` 必须与医嘱一致 | **不一致一律拦截**，不得因为「护士说就是这个患者」而放行 | 给药错误是不可逆伤害。**核对能力本身在 M08（`M08护理工作站/M08_护理工作站_03_医嘱执行与签名_详细设计.md:288` 患者身份核对四方式、`M08护理工作站/M08_护理工作站_06_用药与滴眼液执行_详细设计.md:315` 用药执行四道关口），M20 不重新定义核对**，只负责「在床边、在离线、在两秒内」把它执行出来——**保证它在弱网下不降级，这才是 M20-03 的增量**。若闸门在移动端可关或可降级，移动护理就只是一个更小屏幕的 M08，它存在的理由（床边、即时、可靠）全部消失 |
| **G-2 移动端权限闸门** | 每个请求除 Token 校验外，必须校验 `is_mobile_user` 与 `m20:*` 权限 | **任一校验接口失败 → 403**，不得「查不到权限就当作有权限」 | 移动端设备可能丢失、被借用、被越狱。PC 端有物理边界（在科室里），移动端没有。**fail-closed 是移动端的安全底线** |
| **G-3 审批人有效性闸门** | 审批人执行审批动作时，必须实时校验其权限与在岗状态 | **校验失败 → 拒绝该动作**，不得以上次快照为准 | 一封「已离职的科主任批了这支特殊用药」的审批单，在药事检查时等于没有审批 |

**G-2 与 G-3 的共同逻辑**：**「查不到」与「没有权限」在安全判定上必须是同一个结果。** 反过来做（查不到就放行）会让一次上游故障变成一次权限绕过。

## 6. 核心计算模型

M20 有六个必须精确复现的计算模型。**子模块实现必须引用这里的模型编号，不得各自另算。** 每个模型都给了完整算例，子模块验收项必须能复现算例结果。

### M20-CALC-01 审批链解析（M20-04）

**问题**：给定「业务类型 + 金额 + 申请人科室 + 紧急度」，确定这条审批单要走几级、每级是谁。

**算法**（按优先级从高到低，命中即停）：

1. **按 `biz_type` + 精确金额区间 + 精确科室匹配规则**（`m20_apr_rule`，`match_level = 1`）
2. **按 `biz_type` + 金额区间 + 科室为 ALL**（`match_level = 2`）
3. **按 `biz_type` + 金额区间为 ALL**（`match_level = 3`，科室不参与）
4. **按 `biz_no` 前缀推导的默认链**（`match_level = 4`，兜底）
5. **都命中不到 → 走 `m20_apr_rule` 的 `biz_type` 默认链**；仍无 → **返回错误码 `"2004002"`，不得默认免审**

**审批人解析**：每个节点给出 `approver_type`，取值与解析来源：

| `approver_type` | 解析方式 | 上游 |
|---|---|---|
| `ROLE` | 调 M02 `staff-by-roles`，取该角色在当前科室的在岗人员 | U-11 |
| `DEPT_HEAD` | 调 M02 `dept-tree` 取科室负责人 | U-10 |
| `SPECIFIC` | 取 `m20_apr_rule_node.approver_id` 快照 | — |
| `APPLICANT_SUPERIOR` | 取申请人所属部门的直接上级 | U-10 + M01-02 |

**会签语义**（`approve_mode` 三值）：

| 取值 | 含义 | 通过条件 |
|---|---|---|
| `ALL` | 全部同意才通过 | 全部 `approver_id` 均为 `APPROVED` |
| `ANY` | 任一同意即通过 | 任一 `approver_id` 为 `APPROVED`，其余置 `SKIPPED`（`skip_reason = ANY_SATISFIED`） |
| `SEQUENTIAL` | 按顺序逐个审 | 前一个通过才激活下一个 |

**算例**：改单申请 `biz_type = M10_ORDER_AMEND`、`amount = 400.00`、`applicant_dept_id = 12（视光中心）`

| 候选规则 | match_level | 金额区间 | 科室 | 命中 |
|---|---|---|---|---|
| R-101 | 1 | [0, 500) | 12 | ✓ **命中，停止** |
| R-102 | 1 | [500, 2000) | 12 | ✗ |
| R-103 | 2 | [0, 2000) | ALL | 未参与 |
| R-104 | 3 | ALL | ALL | 未参与 |

R-101 定义两级：`node_seq=1` 为 `ROLE(DEPT_MANAGER)`，`node_seq=2` 为 `ROLE(FINANCE_MANAGER)`。
解析结果：**2 级**，第 1 级审批人 = M02 返回的科室负责人（1 人），第 2 级 = 财务经理（1 人）。
**若第 1 级解析出 0 人**（科室负责人空缺）→ **不得自动跳过**，须返回 `"2004008"`「审批人无法解析，请联系管理员」，并在页面明确提示。**自动跳过会让一张 400 元的改单在没有人审批的情况下通过。**

### M20-CALC-02 审批时效计算（M20-04）

**问题**：审批超时怎么算、超时率怎么统计。

**每个节点有 `timeout_hours`**（在 `m20_apr_rule_node` 上配置，默认按紧急度）：

| `urgency` | 默认节点超时 |
|---|---|
| `NORMAL` | 24 小时 |
| `URGENT` | 4 小时 |
| `EMERGENCY` | 1 小时 |

**节点级超时**：`node_status = PENDING` 且 `now() > activated_at + timeout_hours` → 超时，触发催办与升级。

**统计口径（必须严格遵守）**：

```
审批超时率 = 超时节点数 / 已终结节点数
```

- 分母 = 已终结（`APPROVED` / `REJECTED` / `SKIPPED` / `TRANSFERRED`）的节点数，**不含仍在 `PENDING` 的**——否则「审批越慢、超时率越低」。
- 分子 = 其中 `acted_at > activated_at + timeout_hours` 的节点数。
- **分母为 0 时返回 `NULL` + `NO_DATA`，不得返回 0%，更不得返回 100%。**

**算例**：某月已终结审批节点 1,200 个，其中 96 个超过节点时限：

`96 / 1200 = 8.00%`

**反例（必须写进验收）**：若把分母写成「全部节点数 1,340」（含 140 个仍在审批中的），得 `96 / 1340 = 7.16%`——**差了 0.84 个百分点，且方向是「更慢反而更好看」**。这与 M18 那轮 `M07-07 :3129` 的 `if doc["count"] else 100.0` 是同一类错误。

### M20-CALC-03 待办聚合口径（M20-08）

**问题**：职工的未读角标数到底怎么算。

**待办总数** = `审批待办数` + `护理任务待办数` + `随访待办数` + `质控缺陷待办数` + `系统通知未读数`

**四条硬规则：**

1. **同一个业务对象在多个来源出现时按 `(source, biz_id)` 去重。** 例：一条护理任务既在 M08 待办里、又在 M20 消息里推送过一次，**只能算 1 件**。
2. **角标上限 99，超过显示「99+」。**
3. **任一来源降级 → 角标显示「?」并显示「部分待办加载失败」。** **绝不显示 0**——0 的语义是「没有待办」。
4. **角标数不缓存超过 300 秒**（Redis `m20:msg:unread:{staff_id}`），且每次下拉必须重新计算。

**算例**：某护士今日 8 点

| 来源 | 原始条数 | 去重后 |
|---|---|---|
| M08 护理任务（`PENDING` + `CLAIMED`） | 12 | 12 |
| M20 消息中心（推送过其中 3 条任务） | 15（含那 3 条） | 12（3 条去重） |
| M19 随访待办 | 0 | 0 |
| 审批待办 | 2 | 2 |
| 系统通知未读 | 5 | 5 |
| **合计** | — | **19** |

不做事的话得 `12 + 15 + 0 + 2 + 5 = 34`，**虚高 79%**。护士看到 34 条待办会直接不看——**这正是「已读不回」的工程成因**。

### M20-CALC-04 移动端首屏渲染预算（M20-02 / M20-03 / M20-05）

**问题**：移动端 P95 ≤ 2 秒（总体设计要求）怎么分摊。

**2 秒预算的分配：**

| 环节 | 预算 | 说明 |
|---|---|---|
| 网络往返（4G 弱网） | 400ms | 医院 WiFi 覆盖不全，按 4G 中位计 |
| 网关 + 鉴权（U-01 `token/validate`） | 60ms | M02 给 20ms，留 3 倍余量 |
| **业务数据聚合** | **900ms** | 下行三条 |
| 客户端渲染 | 400ms | 首屏列表 + 图片懒加载 |
| 余量 | 240ms | 抖动 |

**900ms 聚合预算的分配**（以 M20-02 查房一屏为例，四个上游**并行**）：

| 上游 | SLA | 用途 |
|---|---|---|
| M05 P-02 在院清单 | 150ms | 患者列表 |
| M18 P-01 病历正文 | 100ms | 每个患者一次，**首批只取前 10 个** |
| M07 U-23 诊断 | 50ms | 每个患者一次 |
| M12/M13 最新报告标记 | 200ms | 每页一次（批量） |

**并行取 max ≈ 200ms**，若串行则 `150+100+50+200 = 500ms` 且**按患者数线性放大**（20 个患者串行就是数秒）。

**硬规则：**
- **一屏内的上游调用必须并行**（`asyncio.gather`），串行是 M20 性能问题的第一成因。
- **列表页只取摘要**，不全量取。查房列表 20 个患者，**不得为每人都调一次 M18 P-01**——只在展开某一行时才调。
- **超出预算的上游必须能被跳过**，且跳过后 `degraded = true`。

### M20-CALC-05 缓存新鲜度判定（M20-01 统一实现）

**问题**：一个响应到底该标 `REALTIME` / `CACHED` / `PARTIAL` / `UNKNOWN`。

**判定算法**（自上而下，命中即停）：

```
if 任一上游失败:                      → PARTIAL   （且有数据的来源照常返回）
elif 有数据来自缓存且缓存年龄 > 30s:   → CACHED
elif 有数据来自缓存但缓存年龄 <= 30s:  → REALTIME  （30 秒内视为实时）
elif 无法判定（如上游没返回 as_of）:   → UNKNOWN
else:                                 → REALTIME
```

**`as_of` 的计算**：`as_of = min(所有成功来源的 as_of)`。若某来源根本没返回 `as_of`，**整个响应 `data_quality = UNKNOWN`**，不得默认成 `REALTIME`。

**算例**：M20-02 查房一屏

| 来源 | 返回时刻 | `as_of` | 状态 |
|---|---|---|---|
| M05 P-02 | 10:09:41 | 10:09:40 | 成功 |
| M18 P-01 | 10:09:41 | 10:09:35 | 成功 |
| M07 U-23 | 10:09:42 | 10:09:41 | 成功 |
| M12/M13 | 超时 | — | 失败 |

结果：`degraded = true`、`degraded_sources = [{"source":"M12_M13","reason":"TIMEOUT"}]`、`data_quality = PARTIAL`、`as_of = 10:09:35`（**取最早的 M18 时刻，不是请求时刻 10:09:42**）。

页面必须显示：「数据截至 10:09:35 · 报告模块暂时不可用」。

**常见错误（写进验收）**：`as_of` 用 `now()` 填充。这样做的后果是页面显示「刚刚更新」，而实际最新的数据是 7 秒前的——**这 7 秒在给药核对与危急值场景里是实质风险**。

### M20-CALC-06 离线队列重放冲突判定（M20-01）

**问题**：移动端离线时排队的操作，恢复网络后哪些能直接重放、哪些必须转人工。

**判定算法**（每条队列项都带 `entity_version` —— 入队时业务对象的版本标识）：

```
① 幂等键已存在（该操作早已成功过）           → 直接置 SYNCED，不重复执行
② 目标实体已不存在（作废/删除）               → CONFLICT（reason = ENTITY_GONE）
③ 目标实体版本不一致（entity_version 变化）   → CONFLICT（reason = VERSION_CHANGED）
④ 目标实体状态不允许该操作（如已完成的护理任务再次执行）→ CONFLICT（reason = STATE_INVALID）
⑤ 以上都不命中                                → SYNCED（执行并回写）
```

**硬规则：`CONFLICT` 一律不自动覆盖，也不自动丢弃。** 必须进「待处理队列」由人决定（丢弃 / 应用 / 手工修正），并留痕。

**算例**：护士 P01 的离线队列有 3 条

| 队列项 | 内容 | 目标状态 | 判定 | 结果 |
|---|---|---|---|---|
| OF-001 | 执行医嘱 A 给药 | 任务已完成（同事代为执行） | ④ | `CONFLICT / STATE_INVALID` |
| OF-002 | 记录体征 36.8℃ | 患者在院、版本未变 | ⑤ | `SYNCED` |
| OF-003 | 执行医嘱 B 给药 | 患者在 2 小时内已出院 | ② | `CONFLICT / ENTITY_GONE` |

**若不做 ②④ 判定**，OF-001 会被重放成「同一给药执行两次」，在医嘱执行记录里出现两条——药已经给了，却多记一次，且第二条的 `executed_at` 是半小时后。**这是护理不良事件上报的典型来源。**

## 7. 技术架构

### 7.1 三层架构与"零副本"落地

```
┌──────────────────────────────────────────────────────────────┐
│  客户端层：iOS / Android / 企业微信小程序 / H5 / Pad          │
│  - 只做渲染、扫码、拍照、本地缓存（非业务数据缓存）             │
└──────────────────────────┬───────────────────────────────────┘
                           │ HTTPS + JWT(M02-03 签发) + X-Device-Id
┌──────────────────────────▼───────────────────────────────────┐
│  接入层 M20-01：路由 / 鉴权转发 / 幂等 / 限流 / 版本灰度       │
└──────────────────────────┬───────────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────────┐
│  编排层 M20-02 ~ M20-08：聚合、编排、审批流、消息通道          │
│  - 并行调用多个上游（asyncio.gather）                          │
│  - 计算 as_of / degraded / data_quality                       │
│  - 短 TTL 缓存（≤60s，Redis）                                 │
└──────────────────────────┬───────────────────────────────────┘
                           │ 内部契约（/internal/v1/...）
┌──────────────────────────▼───────────────────────────────────┐
│  上游业务层：M01/M02/M03/M05/M07/M08/M12/M13/M16/M18/M19/M22  │
│  - 唯一业务数据权威                                            │
└──────────────────────────────────────────────────────────────┘
```

**"零副本"的落地方式**：M20 的 72 张表里，**没有一张存业务实体**。全部 72 张表分属四类：

| 类别 | 举例 | 数量级 |
|---|---|---|
| **流程表**（审批） | `m20_apr_instance` / `_node` / `_rule` / `_action_log` | 11 |
| **通道表**（消息与待办） | `m20_msg_inbox` / `_delivery_log` / `_template` | 9 |
| **基础表**（终端/幂等/离线/菜单/配置） | `m20_base_*` | 9 |
| **检索与统计表**（M20 自产的查询留痕与工作量统计） | `m20_qry_search_log` / `m20_idx_*` 等 | 其余 |

> **唯一容易踩线的一类是「统计表」**：`m20_qry_stat` 这类表存的是「某人今天查了多少次」。它是不是业务数据副本？**不是**——M22 有全院的查询统计口径，但「M20 内部的检索行为留痕」只有 M20 有。**判据回到 §1.4 红线：M20 删库重建，会不会有业务事实丢失。** 检索留痕会丢，所以可以建；患者信息会由 M03 补回，所以不许建。

### 7.2 审批链解析的缓存与失效

**缓存**：`m20:apr:chain:{biz_type}:{dept_id}` TTL 3600s，存的是**解析结果**（节点定义 + `approver_type`），**不存具体 `approver_id`**。

> **这是本节最关键的一条**：缓存只缓存「链的形状」，每次使用时**实时解析具体审批人**。理由：链的形状按制度配置、很少变；审批人（角色在职人员、科室负责人）随时因调岗、请假、离职而变。**缓存审批人 id 会让「已离职的科主任批了这支特殊用药」成为可能**（G-3 闸门失效）。

**主动失效的四类触发**（共享规范 §17 第 23 条）：

| 触发 | 来源 | 失效范围 |
|---|---|---|
| 职工调岗 / 离职 | M01-02 事件或 M02 会话失效 | 该职工相关的所有链 |
| 角色变更 | M02 权限变更 | 涉及该角色的链 |
| 科室负责人变更 | M02 `dept-tree` 变更 | 该科室的链 |
| 审批规则变更 | M20-04 管理员操作 | 该 `biz_type` 的链 |

### 7.3 消息推送的降级与重试

**通道优先级**（`m20_msg_channel`）：`INBOX`（站内信，必发）→ `WECHAT_WORK`（企业微信）→ `APP_PUSH`（APP 推送）→ `SMS`（短信，**仅紧急**）。

**规则：**
- **`INBOX` 永不失败**（写库即成功），是所有推送的**兜底**。任何渠道推送失败，消息仍在站内信里可查。
- **短信只用于 `EMERGENCY` 级**（如危急值、手术停台），因为短信有成本且骚扰性强。
- **重试**：Celery 指数退避 3 次（10s / 60s / 300s），仍失败置 `FAILED` 并**在消息中心可见**。
- **去重**：同一 `(staff_id, biz_type, biz_id)` 在 5 分钟内不重复推送（有人会在 5 分钟内触发 10 条同源消息）。

### 7.4 容量估算

| 项 | 估算 | 依据 |
|---|---|---|
| 移动端在线用户峰值 | 300 人 | 全院职工约 600 人，峰值在线率 50% |
| 每日请求量 | 约 40 万次 | 300 人 × 平均 40 次/人/日 × 3（含重发） |
| 峰值 QPS | 约 120 | 门诊高峰 8:00~10:00 集中 30% |
| 审批单据 | 约 200 单/日，7.3 万/年 | 按 M10/M11/M17 的申请量估 |
| 审批节点 | 约 500 个/日，18 万/年 | 平均 2.5 级 |
| 消息投递 | 约 3,000 条/日，110 万/年 | 含系统通知与待办提醒 |
| 检索留痕 | 约 4 万条/日，1,460 万/年 | 每次查询一条 |

**三年数据量**：审批约 55 万行、节点 137 万行、消息 330 万行、检索留痕 4,400 万行。**总量约 8GB（含索引约 20GB）**，单机 PostgreSQL 可承载，不需要分区以外的任何水平扩展。

**唯一需要分区的是检索留痕表**（`m20_qry_search_log`，1,460 万行/年），按 `created_at` 月分区 + `DEFAULT`。

### 8.1 性能

| 指标 | 要求 | 说明 |

| 单次响应体 | ≤ 200KB | 超出的字段必须按需二次加载 |

### 8.2 可用性

| 项 | 要求 |
|---|---|
| 服务可用性 | 99.9%（年停机 ≤ 8.76 小时） |
| 上游不可用时 | **必须降级返回带标记的响应或明确失败，不得静默返回空数据** |

| 离线支持 | 采集类操作（体征、随访记录、拍照）支持离线排队，见 M20-CALC-06 |

### 8.3 安全

| 项 | 要求 |
|---|---|
| 认证 | 全部由 M02 完成，M20 **不签发、不校验令牌**（铁律 6） |
| 数据权限 | 必须走 M02 `perm/filter-sql`，**SQL 层参数化过滤**，不得应用层过滤 |
| 敏感信息 | 列表页脱敏（姓名、手机号、证件号），看全文另行鉴权并留痕 |
| 审计 | 查看患者信息、审批动作、导出必须调 M02 `audit/record` |
| 锁屏 | 空闲 15 分钟、敏感页面 5 分钟（M02-07 §3.7） |

### 8.4 可观测性

| 指标 | 说明 |
|---|---|
| `m20_request_duration_ms` | 按接口与子模块打标签 |
| `m20_upstream_duration_ms` | 按上游模块打标签（**这是定位性能问题的第一入口**） |
