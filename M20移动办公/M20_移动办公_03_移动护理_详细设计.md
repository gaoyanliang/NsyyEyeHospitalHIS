### 一句话定位

**移动护理把「护士站在护士站看电脑、跑一趟病房、回来再录一次」压缩成「在床边扫一下、点一下、走人」，并且在这个过程中把三层核对的证据留下来。**

它不是护士站的小屏幕版本。护士站解决的是「记录得全不全」，移动护理解决的是「这一步在床边做没做对」。

## 1. 模块概述

### 1.1 模块定位

M20-03 移动护理是**住院与日间手术场景下的床旁执行助手**。它服务的核心动作只有三类：

1. **核对**：在给患者做任何处置之前，确认「这个人」「这个药/这项操作」是对的。
2. **记录中间态**：把护士在床旁产生、但还没进正式记录的东西（离线待提交的药、交接班随手记的一句话）安全地暂存。
3. **提醒与入口**：让护士在正确的时刻看到该做的事、用最短路径进入该做的事。

它**不承担**的业务：护理任务的生成与状态（M08）、执行事实的落库与电子签名（M08-03）、用药四道关口的判定规则（M08-06）、体征采集与告警判定（M08-04）、正式交接班记录（M08-07）。

用一句话区分：

> **M08 回答「这个任务应该怎么做、做完了没有」；M20-03 回答「护士此刻在床边，下一步该扫什么」。**

### 1.2 为什么独立成子模块

四条理由，每条带数据。

**理由一：M08 的所有界面都以「工作站有一位护士在电脑前」为前提。**

M08-03 的医嘱执行页面把核对拆成 `verify-patient` → `check-items` → `submit-check` → `sign` 四次调用，M08-06 的用药页把四道关口排成一张表单。这套流程在护士站运行良好，但护士一天里绝大部分时间不在护士站：日均门诊 2,000 人次、住院 60 人次/日在院，按每名责任护士管 8~10 名患者估算，一个班次（8 小时）里护士在病房间走动的次数是 40~60 次，回到护士站坐下打字的时间不到 1 小时。

把这套流程搬到手机上不是「换个屏幕」。**每一次多一次点击，就是这个动作在床边做不成的理由**。M08 的四个接口调用在移动端必须收敛成一次扫码 + 一次确认，收敛的编排逻辑不属于 M08（M08 不该知道手机屏幕多小），只能独立。

**理由二：给药执行是 M20 里唯一的「不可逆动作」。**

审批点错了可以驳回，消息发错了可以撤回，报表出错了可以重生成。**给药没有回退路径**。因此移动护理对可靠性的要求比 M20 其他七个子模块高一个等级：它需要独立的闸门设计、独立的离线设计、独立的数据留痕。这三件事任何一件塞进通用子模块，都会被「其他子模块不需要这么严」的惯性稀释。

**理由三：离线是硬需求，而不是加分项。**

眼科病房的实际情况是老楼厚墙、金属床栏、部分区域无 Wi-Fi 覆盖。护士拿着手机走到床尾时信号断掉是常态。如果移动护理必须联网才能记录，护士的应对一定是「先记在纸上、回护士站再录」，那就回到了移动护理要消灭的那个流程，且纸上的字谁也认不出、事后补录的时刻全是假的。**离线能力必须做，而离线重放的冲突判定（M20-CALC-06）是一套独立的算法，不属于任何一个具体业务模块。**

**理由四：扫码头、腕带、条码这三件事是设备侧问题，不是业务侧问题。**

扫码失败的原因分布很不均匀：条码磨损、腕带卷边反光、摄像头对焦慢、屏幕反光、护士单手拿机。这类问题的排查要看**设备维度**的失败率（`idx_m20_nur_sv_device_result`），而不是看某个任务失败了几次。把设备侧留痕放进 M08 会让 M08 的表里混进大量与护理业务无关的字段。

#### 1.3.1 「M08 已经有核对，为什么还要 M20」

这是评审必问的第一个问题，必须正面回答。M08-03 §3.3 已经定义了四种核对方式，M08-06 §3.1 已经定义了四道关口，M08-06 的页面 5.8 已经有 `[扫码腕带]` `[扫码药品]` 两个按钮。**所以「扫码核对」这件事本身，M08 确实已经有了。**

差异在下面五处，全部是「床边」这个场景带来的，不是重复建设：

| 维度 | M08 工作站 | M20-03 移动护理 | 为什么不能靠改 M08 解决 |
|---|---|---|---|
| 核对入口 | 电脑前手动点击两个按钮 | 手持机摄像头常驻，扫码即判 | 工作站没有摄像头可用 |
| 核对顺序约束 | 靠页面布局与用户自觉 | 三层闸门串行固化，前一关不过不给下一关 | 页面布局约束在移动端会退化成滚动条 |
| 离线 | 无（断网即不可用） | 可离线记录，回线后重新过闸门 | 工作站断网不常见，护士不会为它做补偿设计 |
| 设备侧留痕 | 无 | 设备型号、App 版本、扫码耗时、失败率 | 这些字段对 M08 无业务意义 |
| 时间成本 | 需回护士站 | 床边 5 秒完成 | — |

**M20-03 的真实增量是「把核对搬到床边并保证它在弱网下不降级」**，而不是「新增核对能力」。这个区分写在这里，是为了避免文档把 M08 已有的能力包装成自己的成果——那种写法在评审时一问就穿。

#### 1.3.2 M08 执行接口的位置问题

M08-03 的执行写入接口位于 `/api/v1/m08/executions/*`（面向工作站），内部契约只有三条只读接口（`by-order`、`pending/by-encounter`、`on-order-stopped`）。这意味着 M20 移动端要把执行结果落库，**只能调用面向工作站的接口**，或者由 M08 补充内部契约。

本文档采用**前者**：M20-03 以「一个特殊客户端」的身份调用 `/api/v1/m08/executions/*`，并在 10.1 节登记这一事实与风险。风险有两条，都必须在验收前确认：

1. 该组接口的权限校验以 `m08:execution:execute` / `m08:execution:sign` 为准，护士需要同时持有 M08 权限与 M20 权限。
2. 该组接口没有针对移动端的轻量响应，`check-items` 会返回 7 项核对项全文，移动端首屏预算（M20-CALC-04 的 900ms 聚合预算）需实测。

**已向上游提请**：建议 M08 补充 `POST /internal/v1/m08/executions/execute` 单次完成「核对 + 执行」的内部契约。在补齐之前，本文档按现状设计，不臆造接口。

### 1.4 概念辨析

五对最容易混淆的概念。

| 概念 A | 概念 B | 区别 | 混淆的后果 |
|---|---|---|---|
| **扫码核对记录** | **执行记录** | 核对记录回答「扫了什么、扫到的是什么、对不对」；执行记录回答「药给了没有、谁给的、几点给的」 | 混成一张表就会出现「M20 说打了、M08 说没打」，且两边都不报错 |
| **移动护理的「完成一步」** | **任务的「已完成」** | 前者是护士在手机上推进了一个核对阶段；后者是 M08 任务状态变为 `COMPLETED` | 用前者冒充后者，护士以为做完了，任务仍在待执行 |
| **例外通道放行** | **核对通过** | 例外是「物理原因无法扫码，经二人确认后用其他方式核实」；核对通过是「扫码比对一致」 | 混为一个是 fail-open，闸门形同虚设 |
| **离线记录已提交** | **离线记录已生效** | 前者是数据到了服务端；后者是重放通过闸门并落 M08 | 混为一个是「离线即绕过」，等于给了闸门一个后门 |
| **交接班备忘** | **交接班记录** | 备忘是床旁随手记的一句话；交接班记录是 M08-07 的正式文书 | 用备忘替代正式记录，交班责任无法界定 |

### 1.5 模块目标

七条，每条带可度量指标与当前基线。

| 编号 | 目标 | 指标 | 目标值 | 现状基线 | 度量方式 |
|---|---|---|---|---|---|
| G-01 | 床旁核对不因网络问题被跳过 | 给药执行前完成患者层核对的比例 | ≥ 99.5% | 护士站模式约 92%（手动点击常被跳过） | `m20_nur_scan_verify` 中 `MATCHED` 任务数 / 应有核对任务数 |
| G-02 | 扫码不符必须被拦下 | 不符拦截率 | 100% | — | 不符记录（`MISMATCH`）对应的执行请求全部返回 4xx |
| G-03 | 上游故障不得伪装成正常 | M08 不可用时返回空列表的次数 | 0 | — | SC-02 负面验收 + 监控 `m20_nur_task_list_empty_while_degraded` |
| G-04 | 离线记录可用且不重复执行 | 离线记录重放成功率 / 重复执行次数 | ≥ 97% / 0 | 无离线能力 | 重放日志；`CONFLICT` 分类统计 |
| G-05 | 床旁操作够快 | 单次核对（扫码到出结果）耗时 | P95 ≤ 5 秒 | — | `m20_nur_oper_log.duration_ms` |
| G-06 | 例外通道不被滥用 | 例外单占全部核对的比例 | ≤ 1% | — | 例外单数 / 核对记录数，按月 |
| G-07 | 护士愿意用 | 移动护理日活护士占比 | ≥ 90% | — | 按科室统计有操作日志的护士数 / 在岗护士数 |

#### 2.3.2 危急值边界

共享规范 §10.4.1 记录了两个上游事实缺口，本文档据此收缩范围：

1. **M12 / M13 没有「按患者 / 按就诊列出报告」的内部接口**，只有按 `report_id` 单条查的 `GET /internal/v1/m12/review/{id}` 与 `GET /internal/v1/m13/review/{id}`。因此**本子模块不做患者报告清单功能**；护士从危急值待办点进去，看到的是那一份报告。需要一个清单的场景登记为「需向上游提请」。
2. **危急值确认是 M07-04 的业务动作**。M12/M13 的 `POST .../critical/{id}/on-acknowledged` 语义是「M07 确认后回调」，**M20 不得代 M07 调用**。移动端看到危急值提醒时，页面提供「去确认」按钮，跳转到 M07-04 的入口，不在 M20 内完成确认。

这两条不是设计取舍，是上游能力的客观边界。把边界写清楚比造一个假接口更重要——**假接口在联调那天才会崩，而那时已经没人记得是谁拍的板**。

#### 3.1.1 关系说明

| 关系 | 基数 | 说明 |
|---|---|---|
| M08 任务 → 扫码核对记录 | 1 : N | 一个任务在不同阶段各有一条或多条核对记录（重扫会产生多条） |
| 扫码核对记录 → 例外单 | 1 : 0..1 | 只有在物理原因导致无法扫码时才产生例外单 |
| 扫码核对记录 → M08 执行记录 | N : 1 | 多层核对共同推动一次执行；`m08_execution_id` 可空 |
| 离线记录 → 通用队列 | 1 : 1 | 本子模块只扩展护理语义，不复制队列结构 |
| 医嘱组 → 组内条目 | 1 : N | 唯一的物理外键 |
| 操作日志 | 独立 | 与其余各表是「记录」关系而非「引用」关系，因此不建外键 |

其中最需要强调的一条：**扫码核对记录与执行记录是 N:1 而不是 1:1**。这一条决定了 `m08_execution_id` 必须可空——如果强制非空，那么在「刚扫完患者还没扫药」的中间状态下这条核对记录就写不进去，而恰恰是这个中间状态最需要留痕。

### 3.2 状态机

本子模块有四个状态机：核对判定的**闸门次序**（不是状态机但同样是顺序约束）、例外单状态机、离线重放状态机、备忘状态机。**护理任务状态机不在这里**——它属于 M08。

#### 3.2.1 三层核对闸门的顺序约束

```
   开始（护士到达床旁）
        │
        ▼
┌───────────────────┐
│ 第 1 层 患者核对   │  腕带/就诊卡扫码 → 与任务 patient_id 比对
│ PATIENT           │  不符 → 拦截，最多 SCAN_MAX_ATTEMPTS 次后锁定
└────────┬──────────┘
         │ MATCHED
         ▼
┌───────────────────┐
│ 第 2 层 药品核对   │  药袋/药瓶扫码 → 与医嘱 drug_code 比对
│ DRUG              │  不符 → 拦截
└────────┬──────────┘
         │ MATCHED
         ▼
┌───────────────────┐
│ 第 3 层 剂量途径   │  滴数/眼别/途径 → 与医嘱比对
│ DOSE_ROUTE        │  （默认关闭，科室可开启）
└────────┬──────────┘
         │ MATCHED 或 SKIPPED_BY_CONFIG
         ▼
   调 M08-03 落执行
```

**顺序不可颠倒**，理由与 M08-06 §3.1 完全一致：**先确认对象，再校验规则**。如果先校验剂量再核对患者，护士的注意力会被「剂量差一点」这条提示占满，反而忽略了手里拿的药是不是这个患者的。

这条不只是文字约定。在代码里它体现为 `resolve_gate_sequence()` 返回一个固定顺序的列表，且每层只有在上一层结果为 `MATCHED` 时才允许进入（见 6.5.1）。**口径的区分必须落到两条不同的代码路径上，只写在文档里不算数。**

#### 3.2.2 核对结果的五值语义

| `verify_result` | 含义 | 是否算「核对通过」 | 是否进失败率分母 | 是否可用例外通道 |
|---|---|---|---|---|
| `MATCHED` | 扫到的与期望一致 | 是 | 是 | — |
| `MISMATCH` | 扫到了，但不是这个 | 否 | 是 | 否 |
| `UNREADABLE` | 扫了，读不出/读不全 | 否 | 否 | **是** |
| `SKIPPED_BY_CONFIG` | 该层被科室配置关闭 | 视同通过 | 否 | — |
| `UPSTREAM_UNAVAILABLE` | 上游判定接口不可用 | 否（fail-closed） | 否 | **是** |

两个容易搞错的地方：

1. **`UPSTREAM_UNAVAILABLE` 不能记成 `MISMATCH`**。记成不符，统计上会显示「护士扫错很多」，而实际上系统在坏。护士被指标冤枉一次，下次就会绕过闸门。
2. **`UPSTREAM_UNAVAILABLE` 更不能记成 `MATCHED`**。那是典型的 fail-open，闸门等于不存在。数据库层用 `ck_m20_nur_sv_upstream_not_matched` 直接挡住这种写法。

#### 3.2.3 例外单状态机

```
    申请（护士 A，设备甲）
         │
         ▼
    ┌─────────┐
    │ PENDING │──────── 超 expire_at ────────▶ ┌─────────┐
    └────┬────┘                                │ EXPIRED │
         │                                     └─────────┘
         │ 护士 B 在设备乙确认                    （终态）
         ▼
    ┌───────────┐   护士长驳回   ┌──────────┐
    │ CONFIRMED │──────────────▶│ REJECTED │
    └─────┬─────┘                └──────────┘
          │                        （终态）
          │ 使用一次（used_flag = TRUE）
          ▼
       （仍为 CONFIRMED，但不可再用）
```

三条硬约束：

1. **`PENDING → CONFIRMED` 必须换人与换设备**。数据库有 `ck_m20_nur_nxe_two_person`（`confirmer_id <> requester_id`）+ 触发器 `trg_fn_m20_nur_nxe_confirm_same_device`（`confirmer_device_id <> device_id`）。两个条件缺一不可：只查人，B 拿 A 的手机就能代确认；只查设备，A 换一台手机自己就能确认。
2. **例外单一次性**（`used_flag`）。不做一次性的话，一张例外单能覆盖整个班次的所有核对，闸门就废了。
3. **`EXPIRED` 与 `REJECTED` 是终态，不可复活**。要重新申请就走新单，保留完整的失败轨迹。

#### 3.2.4 离线重放状态机

```
   设备离线记录
        │ 入队
        ▼
   ┌──────────────┐
   │ NOT_REPLAYED │◀──────────┐
   └──────┬───────┘           │ 重试
          │ 回线，开始重放      │
          ▼                   │
   ┌──────────────┐           │
   │  REPLAYING   │───────────┘
   └──────┬───────┘
          │
     ┌────┴─────┬──────────────┬─────────────────┐
     ▼          ▼              ▼                 ▼
┌─────────┐ ┌───────────┐ ┌──────────────┐ ┌────────────┐
│REPLAYED │ │REPLAY_    │ │REPLAY_       │ │REPLAY_     │
│(终态)    │ │BLOCKED    │ │SKIPPED       │ │BLOCKED     │

```

四条硬规则：

1. **`CONFLICT` 一律不自动覆盖、不自动丢弃**（对应通用队列的 `SYNCING` 之外的分支），必须进待处理队列由人决定。
2. **重放必须重新过闸门**，用本地存的 `(patient_id, drug_code, order_version)` 回线后重新向 M07/M08 校验。离线时扫过的码只是「离线当时的证据」，不是「回线后仍然有效的证据」。
3. **`REPLAYED` 必须有 `m08_execution_id`**（`ck_m20_nur_noi_replayed_needs_exec`）。没有执行记录的回填却标记为已重放，是自欺。
4. **超 `OFFLINE_MAX_HOURS`（默认 24 小时）转 `REPLAY_SKIPPED` 并告警**。给药记录超过一天才重放，临床意义已经失去，强行落库反而污染执行时间线。

### 3.3 关键业务流程

#### 3.3.1 床边给药执行（正常路径）

按时间顺序编号：

1. 护士在 P01 点开一个待执行任务（M08 `task_status = PENDING` 或 `CLAIMED`）。
2. 系统调 M08-01 `by-nurse` 取任务列表（若未命中缓存），调 M07-03 `for-execute` 取执行明细。
3. 进入 P03，摄像头常驻，护士扫腕带。
4. 系统调 M08-03 `verify-patient`（`method=WRISTBAND`），返回 `verified=true`。
5. 系统写一条 `m20_nur_scan_verify`（`verify_stage=PATIENT`，`verify_result=MATCHED`，回填 `matched_patient_id`）。
6. 进入 P04，护士扫药袋条码。
7. 系统比对 `drug_code`，一致则写 `scan_verify`（`verify_stage=DRUG`，`MATCHED`）。
8. 若科室开启第 3 层，进入 P05 核对剂量与眼别。
9. 三层通过，系统调 M08-03 `submit-check` → `sign` 落执行。
10. 执行成功后**回填** `m20_nur_scan_verify.m08_execution_id`（同一任务的多条核对记录都指向同一个执行记录）。
11. 页面提示「已完成」，返回 P01，任务状态变为 `COMPLETED`（由 M08 推回或重新拉取）。

关键点在第 10 步：**核对记录先写、执行记录后回填**。顺序反过来会出现「执行已落库但核对记录写失败」的窗口，那个窗口里的执行没有举证。

#### 3.3.2 扫码不符（拦截路径）

1. 护士扫腕带，扫到的是 6 床的码，任务是 5 床。
2. 系统写 `scan_verify`（`MISMATCH`，`mismatch_reason="该条码属于 6床 李红"`）。
3. 页面红色全屏提示，**不提供「继续」按钮**，只提供「重新扫描」。
4. `attempt_seq` 达到 `SCAN_MAX_ATTEMPTS`（默认 2）后，`is_locked=true`，页面提示「已锁定，请联系护士长」。
5. 护士长在 P06 解锁（调 M08-03 `unlock-patient`），或走例外通道。

第 3 步的「不提供继续按钮」是刻意的。有任何形式的「继续」入口，在着急的时候都会被点；而这一类点击在事后无法与「确实核对过」区分。

#### 3.3.3 例外通道（物理原因路径）

1. 护士扫了三次仍是 `UNREADABLE`（腕带被汗浸透、卷边）。
2. 页面出现「申请例外」入口，选择原因 `BARCODE_DAMAGED`，可补一句说明。
3. 系统写例外单（`PENDING`，`device_id=甲`），并写 `scan_verify`（`UNREADABLE`，`exception_flag=TRUE`）。
4. 护士 B 用**自己的手机**（设备乙）在 P06 打开待确认列表，看到「A 申请对 5 床患者层核对使用例外」，核对患者身份后确认。
5. 数据库触发器校验设备不同，写入 `CONFIRMED`。
6. 系统写 `scan_verify`（新的一条，`MATCHED` 需谨慎：这里走的是「例外放行后的人工核实」语义，见 8.4 的解释）。
7. 该例外单 `used_flag=TRUE`，不可再用。
8. 护士长在 P06 复核，可选驳回（不影响已完成的执行，但计入质量指标）。

第 8 步的「驳回不回滚」是刻意设计：回滚意味着要撤销一次已经发生的给药，而系统无法撤销。驳回的价值在于留痕与统计，不在于纠正。

#### 3.3.4 离线执行与重放

1. 护士走到走廊尽头，App 检测到 `network_state=OFFLINE`，页面顶部出现灰色「离线模式」条。
2. 扫腕带、扫药袋。**此时无法调 M08 判定**，系统做本地校验：条码格式合法、与任务快照的 `patient_id` / `drug_code` 一致。
3. 本地校验通过后，记录进本地队列，`replay_status=NOT_REPLAYED`，写入 `device_recorded_at`（设备时间）。
4. 回线后客户端批量提交，服务端写 `m20_nur_offline_item`（+ M20-01 通用队列表），计算 `clock_skew_seconds`。
5. Celery 任务按七步算法重放（见 6.5.3）。
6. 结果分三种：落 M08 成功（`REPLAYED`）；冲突（`REPLAY_BLOCKED` + `conflict_type`）；超时（`REPLAY_SKIPPED`）。
7. 冲突项进入 P07「离线冲突」清单，必须由人处置。

#### 3.3.5 交接班备忘

1. 护士在 P08 写下「5 床引流管在位，夜间注意渗液」。
2. 保存后状态 `OPEN`，接班护士在 P01 顶部看到角标。
3. 接班护士点开确认，状态变 `HANDED_OVER`。
4. 班次结束后自动归档（`ARCHIVED`）。

备忘**不进病历、不进 M08-07**。它的定位是「护士之间的一句话」，写进正式记录会污染病程。

### 3.4 计算模型

本节与总纲 §6 的六个模型对应。凡总纲已定义的（M20-CALC-04 首屏预算、M20-CALC-05 新鲜度、M20-CALC-06 离线重放），本文档直接引用编号不重算；有两个模型是本子模块新增的，在此给出公式与算例。

#### 3.4.1 M20-CALC-05 在本子模块的落地（引用总纲）

本子模块的每个响应都必须带四质量标记，其中 `data_quality` 按总纲 M20-CALC-05 自算，**不得透传上游值**（共享规范 §8A.2.1）。具体到本子模块：

| 情形 | `data_quality` | `degraded` | 说明 |
|---|---|---|---|
| 任务列表实时取到，所有上游成功 | `REALTIME` | `false` | — |
| 任务列表命中 `m20:nur:task:{nurse_id}` 缓存（TTL 30s） | `CACHED` | `false` | 缓存新鲜但非实时，页面要显示「30 秒内数据」 |
| M05/M03 超时，M08 正常 | `PARTIAL` | `true` | `degraded_sources=[{"source":"M05","reason":"TIMEOUT"}]` |
| M08 超时但有缓存 | `CACHED` | `true` | 页面**必须**显示黄条，不允许静默 |
| 任一来源没给 `as_of` | `UNKNOWN` | `true` | 不得默认 `REALTIME` |

`as_of` 取所有成功来源 `as_of` 的**最小值**。这一条特别重要：如果 M08 的数据是 10:09:35 的、M05 的是 10:09:40 的，那么整屏数据的口径截止时刻是 10:09:35。取最大值会让页面显示「刚刚更新」，而实际上任务数据已经旧了 5 秒——**在给药核对场景里，这 5 秒是实质风险**。

#### 3.4.2 M20-NUR-CALC-01 核对合规率

**定义**：某个统计期内，完成患者层核对的任务数占应有核对任务数的比例。

**公式**：

```
eligible_count    = 统计期内处于可执行状态（CLAIMED / EXECUTING / COMPLETED）的给药类任务数
verified_count    = eligible 中至少有一条 verify_stage='PATIENT' 且
                    verify_result IN ('MATCHED', 'SKIPPED_BY_CONFIG') 的任务数
exception_count   = eligible 中通过例外通道（used_flag=TRUE）完成任务数
unmeasurable_count = eligible 中因 NO_TASK_SNAPSHOT 等原因无法判定的任务数

compliance_rate = (verified_count + exception_count)
                  / (eligible_count - unmeasurable_count)
```

**单位**：比率，保留 6 位小数（`NUMERIC(10,6)`）。

**边界与舍入**：
- 分母为 0 时返回 `NULL`，**不返回 0，更不返回 100%**。这是 M20-CALC-02 同一形状的陷阱：如果「没有可执行任务」被算成 100%，那么全科室休假的那一天合规率最漂亮。
- `exception_count` **计入分子但单独列出**。例外的语义是「物理原因导致的受控放行」，它不该被算成不合规，但必须单独可见——如果把它混进 `verified_count`，一个科室可以靠疯狂用例外把合规率维持在 100%。
- `unmeasurable_count` 单列且**不进分母**。

**失败条件**：M08-01 不可用导致无法取得任务快照 → 整个统计返回 `data_quality=PARTIAL`，并在 `degraded_sources` 标注 `M08`。

**算例**：

统计期 2026-10 某病区，`eligible_count = 1,240`。
- `verified_count = 1,198`
- `exception_count = 31`
- `unmeasurable_count = 11`

```
compliance_rate = (1198 + 31) / (1240 - 11)
                = 1229 / 1229
                = 1.000000
```

看起来完美，但拆开看 `exception_count = 31` 占 `eligible` 的 **2.50%**，超过目标 G-06 的 1%。所以页面上必须同时展示三个数：

| 指标 | 值 |
|---|---|
| 合规率 | 100.00% |
| 其中通过例外放行 | 31 单（2.50%） |
| 不可判定 | 11 单 |

**只报合规率会导致误判**。这是本子模块所有统计表都遵循的原则：**合计数好到可疑时，必须能看到它是怎么凑出来的**。

#### 3.4.3 M20-NUR-CALC-02 设备扫码失败率

**定义**：某台设备在统计期内的扫码失败比例，用于判断「是护士手抖还是这台机器坏了」。

**公式**：

```
scan_total       = 该设备 verify_stage='PATIENT' 的记录数
matched_count    = verify_result = 'MATCHED'
mismatched_count = verify_result = 'MISMATCH'
unreadable_count = verify_result = 'UNREADABLE'

barcode_fail_rate = unreadable_count / nullif(scan_total, 0)

patient_mismatch_rate = mismatched_count
                        / nullif(matched_count + mismatched_count, 0)
```

**关键区分**：必须分成两个比率，不能合成一个。

- `barcode_fail_rate`（读不出）**越高越说明设备或耗材有问题**——摄像头脏、对焦慢、腕带磨损。这是设备的错。
- `patient_mismatch_rate`（读出来但不是这个人）**越高越说明流程或人出了问题**——拿错腕带、串床、任务派错。这不是设备的错。

合成一个比率，运维看到数值高会去换设备，而实际上可能是任务派错了。**分开算才能指出该找谁。**

**边界**：
- `UNREADABLE` **不进** `patient_mismatch_rate` 的分母。读不出来不构成「扫错了人」。
- 分母为 0 返回 `NULL`。

**算例**：

设备 `DEV-A001`，2026-10-27 一个班次：

| 项 | 值 |
|---|---|
| `scan_total` | 120 |
| `matched_count` | 108 |
| `mismatched_count` | 4 |
| `unreadable_count` | 8 |

```
barcode_fail_rate     = 8 / 120        = 0.066667  (6.67%)
patient_mismatch_rate = 4 / (108 + 4)  = 0.035714  (3.57%)
```

解读：`barcode_fail_rate` 6.67% 已经超过 5% 的告警阈值，且当天该病区其他设备均在 1% 以下 → **指向设备问题**，检查摄像头镜片。
`patient_mismatch_rate` 3.57% 在正常范围（该院基线 2%~5%，源于护士偶尔扫到邻床腕带），不指向流程问题。

如果只给一个合成比率，比如 `12/120 = 10%`，就既看不出换设备也看不出查流程。

### 3.5 单据模型

本子模块有六种单号。**护理任务号、执行记录号不属于本子模块**（在 M08），因此不在此列。

| 类型 | 前缀 | 格式 | 示例 | 生成方式 | 唯一性 |
|---|---|---|---|---|---|
| 扫码核对流水号 | `SV` | `SV` + `yyyyMMdd` + 6 位 | `SV20261107000123` | Redis `INCR` | 全局唯一 |
| 例外单号 | `NX` | `NX` + `yyyyMMdd` + 4 位 | `NX202611070017` | Redis `INCR` | 全局唯一 |
| 交接班备忘号 | `NH` | `NH` + `yyyyMMdd` + 6 位 | `NH20261107000042` | Redis `INCR` | 全局唯一 |
| 医嘱组编码 | `NURSET_` | `NURSET_{类别}_{3 位}` | `NURSET_POST_OP_001` | 人工指定 | 科室内唯一 |
| 操作日志号 | `NL` | `NL` + `yyyyMMddHHmmss` + 4 位 | `NL202611071031390012` | 应用拼接 | 全局唯一 |
| 离线队列项号 | `OF` | `OF` + `yyyyMMdd` + 6 位 | `OF20261107000031` | M20-01 生成 | 全局唯一 |

**生成规则**（共享规范 §3.5）：Redis `INCR` key 为 `m20:code:{prefix}:{yyyyMMdd}`，当日首单设 TTL 到次日 00:05。**不得用数据库序列自增后拼日期**——序列跨日不回退，会生成 `SV20261108000123` 这样日期与序号错位的单号，事后按日期查会漏。

**离线场景的单号**：离线时无法调 Redis，客户端用 `临时单号`（`OFF-{device_id}-{seq}`），回线提交时服务端重新生成正式单号并在响应里返回映射。冲突时以服务端单号为准。

### 3.6 数据交接点

本子模块与外部有八个交接点，每个都写明「谁写、谁读、失败怎么办」。

| 编号 | 交接内容 | 方向 | 对方 | 时刻 | 失败行为 |
|---|---|---|---|---|---|
| H-01 | 任务列表与状态 | 拉 | M08-01 | 进入 P01、下拉刷新 | 用缓存 + 黄条；**不返回空列表** |
| H-02 | 患者身份核对结果 | 推 | M08-03 | 扫码后 | 无法核对 → 拒绝执行 |
| H-03 | 执行明细（`for-execute`） | 拉 | M07-03 | 进入 P02、重放 | 进入 P02 时降级展示；重放时阻断 |
| H-04 | 执行落库 | 推 | M08-03 | 三层核对通过后 | 失败 → 保留核对记录，提示重试 |
| H-05 | 腕带条码 | 拉 | M06-04 | 扫码解析失败时 | 走手输或例外通道 |
| H-06 | 患者简要信息 | 拉 | M03-01 | 进入 P02 | 显示患者 ID 末四位 |
| H-07 | 住院与床位 | 拉 | M05 | 进入 P02 | 显示床号快照 |
| H-08 | 待办角标 | 推（事件） | M20-08 | 任务变化时 | 页面内轮询兜底 |

#### 3.6.1 H-04 的载荷与顺序

H-04 是本子模块唯一「产生业务后果」的交接点，写清楚它的顺序：

```
写 m20_nur_scan_verify（三层各一条，事务内）
        │
        ▼
调 M08-03 submit-check + 签名
        │
     ┌──┴──┐
     ▼     ▼
   成功   失败
     │     │
     │     └──▶ 核对记录保留（它们是事实），页面提示「执行未完成，请重试」
     ▼
UPDATE m20_nur_scan_verify SET m08_execution_id = ?
```

如果先调 M08 再写核对记录，那么「M08 成功、核对记录写失败」的窗口里就存在一次没有举证的给药。**先写证据再产生后果**，是这一段的全部要点。

#### 3.6.2 事件载荷红线

本子模块发布的任何事件，载荷里**不得出现患者姓名、手机号、证件号、诊断文本、药品名称**。允许的只有 ID、编码、状态、时间。这条由共享规范 §10.1 与校验器 `check_event_payload` 强制，详见 10.3。

### 4.3 九张表与三类约束的分工

| 约束类型 | 落在哪里 | 本子模块的例子 |
|---|---|---|
| 单字段取值 | `CHECK` | `verify_result IN (...)` 五值 |
| 字段之间 | `CHECK`（组合约束） | `ck_m20_nur_sv_upstream_not_matched`：上游不可用则不能是 MATCHED |
| 跨行 / 跨动作 | 触发器或唯一索引 | `trg_fn_m20_nur_nxe_confirm_same_device`：确认设备必须不同于发起设备 |
| 跨表 | 应用层 + 定时对账 | `m20_nur_order_set.item_count` 与明细行数 |

**`CHECK` 只保护字段自身，不保护字段之间的组合语义。** 这一条在数据结构文档里每一张表都写了「防的真实错误」表，本文档不重复。

### 4.4 与分区的取舍

九张表**全部不分区**。最大的 `m20_nur_oper_log` 三年约 2,600 万行（年增 876 万），远低于单表需要分区的量级（通常 1 亿行以上才开始考虑）。分区的三条代价都不划算：主键必须包含分区键、跨分区唯一约束无法表达、漏跑预建即写失败。改用「冷热分表 + 定期搬运」——`m20_nur_oper_log` 保留最近 6 个月，更早的记录迁到独立冷数据区后从主表删除（**不建 `m20_nur_oper_log_archive` 表**：归档表会被当成第二个合法写入口，而冷数据只读，用对象存储上的按日导出即可满足审计要求）。

### 5.2 P01 我的护理任务

**页面目标**：护士打开 App 的第一屏，一眼看出「现在我该去哪个床、做什么、有没有超时的」。

#### 5.2.1 页面结构

| 区域 | 内容 | 数据来源 |
|---|---|---|
| 顶部条 | 护士姓名、班次、科室病区、在线状态点、**降级提示条（条件显示）** | 本地 + 响应标记 |
| 统计卡 | 待执行 / 执行中 / 已完成 / 超时 四个数字 | M08-01 任务列表按 `task_status` 分组 |
| 快捷入口区 | 最近的医嘱组、常用筛选、常看的患者（最多 8 个） | `m20_nur_quick_entry` |
| 任务列表 | 按床号分组的任务卡片 | M08-01 |
| 底部 | 数据截止时刻 + 离线队列角标 | 响应 `as_of` + 本地队列 |

#### 5.2.2 任务卡片

每张卡片显示：床号（大字）、患者姓名（脱敏，如「王*国」）、任务摘要、计划时间、状态、超时标记。

超时标记的判定：`now > planned_time + UI_OVERDUE_HIGHLIGHT_MINUTES`（默认 15 分钟）。超时卡片左侧加红色竖条，但**不改变卡片顺序**——排序依赖 `priority_score`（来自 M08），前端不重排。理由：前端重排会让不同护士看到的顺序不一致，交接班时说不清。

#### 5.2.3 移动端特殊考虑

- **屏幕尺寸**：一屏显示 4~5 张卡片。分组标题吸顶，滑动时床号始终可见。
- **单手操作**：卡片点击区域为整张卡片；常用操作（领取、开始）以底部弹出条形式出现，位于拇指可达区。
- **网络状态**：弱网时统计卡数字降低饱和度并显示「~」，不假装是准确值。
- **扫码/拍照**：本页不扫码；提供右下角悬浮「扫码」入口，直达 P03 并自动带入最近的任务。
- **横竖屏**：竖屏固定；横屏时任务列表改为两列布局。

#### 5.2.4 四种异常态

| 异常 | 表现 | 文案 | 动作 |
|---|---|---|---|
| 网络断开 | 顶部灰条 + 列表显示本地缓存任务 | 「当前离线，显示的是最后一次同步的任务（截止 09:12）」 | 提供「重试」；缓存过期超 2 小时则列表区域整体置灰 |
| 上游超时（M08 不可用） | **整页红色提示区，不显示空列表** | 「任务列表加载失败，请到护士站核对」 | 提供「重试」与「继续查看上次缓存」（后者明确标注缓存时刻） |
| 无权限 | 整页居中提示 | 「当前账号没有护理任务查看权限，请联系护士长开通」 | 无重试按钮，仅「返回」 |
| 数据为空（确实没任务） | 灰色插画 + 一句话 | 「今天没有分配给你的护理任务」 | 提供「刷新」 |

**第二行与第四行的区别是本页最关键的实现要求**。空列表会让护士以为今天没活，回去补觉，而实际上任务派下来了只是接口挂了。这两行的渲染分支必须在代码里分开（见 12.4 SC-02 负面验收）。

#### 5.2.5 交互细节

1. 下拉刷新：重新调 API-01。
2. 左滑卡片：快捷「领取」（调 M08-03 或 M08-01 的领取接口）。
3. 长按卡片：显示更多（查看执行明细、去交接班备忘）。
4. 点击卡片：进入 P02。

### 5.4 P03 患者身份核对

**页面目标**：确认「躺在这张床上的人」就是任务上的患者。这是三层核对的第一层，也是最关键的一层。

#### 5.4.1 页面结构

| 区域 | 内容 |
|---|---|
| 扫码取景区 | 半屏取景框，四角高亮，取景框下方提示「请扫患者腕带」 |
| 当前任务信息 | 床号 + 患者姓名脱敏（大字），提醒护士先看人再看屏 |
| 结果反馈区 | 扫码后占满下半屏：绿色 ✓ / 红色 ✗ / 黄色 ⚠ |
| 备用入口 | 「手输腕带号」「语音输入」「申请例外」三个次要按钮 |

#### 5.4.2 结果反馈的三态

| 结果 | 视觉 | 文案 | 可用动作 |
|---|---|---|---|
| `MATCHED` | 全屏绿色 ✓ + 触觉反馈（短振一次） | 「王*国 5 床 核对通过」 | 自动 1 秒后进入 P04 |
| `MISMATCH` | 全屏红色 ✗ + 触觉反馈（双短振） | 「**扫错了！该条码属于 6床 李红**」 | 仅「重新扫描」；**无「继续」** |
| `UNREADABLE` | 全屏黄色 ⚠ | 「条码无法识别，请调整角度或擦拭腕带」 | 「重新扫描」「手输」「申请例外」 |
| `UPSTREAM_UNAVAILABLE` | 全屏黄色 ⚠ | 「核对服务暂不可用，无法完成核对」 | 「重试」「申请例外」；**无「跳过」** |

**`MISMATCH` 的红色页面必须显示「扫到的是谁」**，不能只说「核对失败」。护士看到「6床 李红」会立刻意识到自己走错了床；只看到「失败」会以为是系统问题，然后重扫三次。

#### 5.4.3 移动端特殊考虑

- **屏幕尺寸**：取景框占屏幕上半部，结果区占下半部，符合「举着手机扫」的姿势。
- **单手操作**：「重新扫描」按钮在屏幕中下部，拇指可直接触及。
- **网络状态**：离线时扫码仍可进行，本地比对任务快照的 `patient_id`，结果计入离线队列（见 5.8 与 3.3.4）。
- **扫码/拍照**：摄像头常驻；连续扫码模式下扫成功后 1.5 秒自动恢复取景（用于连续核对多个患者）。
- **横竖屏**：扫码页允许横屏，横屏时取景框占满整屏，结果以半透明浮层呈现。

#### 5.4.4 四种异常态

| 异常 | 表现 |
|---|---|
| 网络断开 | 顶部灰条「离线核对模式」；扫描后本地比对并提示「已记录，待联网提交」 |
| 上游超时 | **结果区黄色 ⚠，`verify_result=UPSTREAM_UNAVAILABLE`**，明确提示「无法完成核对」，不给跳过入口 |
| 无权限 | 整页提示「无执行核对权限」；扫码入口置灰 |
| 数据为空 | 不适用（本页必须有任务上下文才可进入） |

#### 5.4.5 为什么这一页没有「跳过」

三层核对的每一页都刻意不提供「跳过核对」「我知道我在做什么」这一类按钮。

理由：**任何一个「跳过」按钮，在着急的时候都会被点**，而事后无法从数据上区分「护士确认过」与「护士点掉了」。这不是假设——现有的护士站模式下核对被跳过的比例约 8%（见 1.5 G-01 的基线），跳过的方式就是「不点那个按钮」。移动端把核对变成默认路径，比给一个跳过按钮更有效。

真正需要绕过的场景有两种，各自有受控出口：
- 设备/条码物理问题 → 例外通道（P06），双人确认留痕；
- 患者身份本身有疑义 → 走 M08-03 的手输或护士长授权解锁，不在本页处理。

### 5.5 P04 药品核对

**页面目标**：确认手里拿的药就是这个医嘱的药。三层核对的第二层。

#### 5.5.1 页面结构

| 区域 | 内容 |
|---|---|
| 医嘱摘要条（吸顶） | 药品名、规格、剂量、途径、眼别 |
| 扫码取景区 | 同 P03 |
| 期望值提示 | 「应扫：妥布霉素滴眼液 5ml」 |
| 结果反馈区 | 同 P03 三态 |

#### 5.5.2 「应扫」提示的分寸

页面显示期望药品名，但**不显示药品条码的码值**。理由：显示码值等于告诉护士「可以手输这个码」，手输就等于绕过扫码。显示名称是必要的——护士需要知道拿的对不对。

#### 5.5.3 移动端特殊考虑

- **屏幕尺寸**：医嘱摘要条吸顶不滚动，因为护士扫药时需要一边看药瓶一边对照屏幕。
- **单手操作**：扫码后药品名称以最大字号居中显示，便于远距离确认。
- **网络状态**：离线时本地比对 `drug_code` 与任务快照。
- **扫码/拍照**：同 P03；支持条码与二维码两种格式。
- **横竖屏**：同 P03。

#### 5.5.4 四种异常态

同 5.4.4。补充一条：**上游超时（M08-06 用药规则服务不可用）时，即使药品码比对一致也必须拦截**——因为第 3 层的间隔校验无法完成，而「同眼两药间隔 ≥5 分钟」这条规则恰恰是滴眼液场景最容易出事的规则。

### 5.6 P05 剂量与途径核对

**页面目标**：确认滴数/片数、眼别、给药途径正确。第三层，默认关闭，科室可开启。

#### 5.6.1 页面结构

| 区域 | 内容 |
|---|---|
| 医嘱期望值 | 剂量（如「1 滴」）、眼别（如「右眼 OD」）、途径（如「滴眼」） |
| 实际值录入 | 剂量数字步进器、眼别三选一（OD/OS/OU）、途径下拉 |
| 比对结果 | 逐项绿/红 |
| 确认按钮 | 全部一致才可点 |

#### 5.6.2 为什么这一层默认关闭

前两层是「扫一下」的零输入动作，第三层需要手动录入三个值，在床旁的操作成本约 8~12 秒。眼科滴眼液的剂量基本固定为 1 滴，剂量差错的概率远低于拿错药、走错床（后两者由前两层挡住）。

因此默认关闭，由科室按需开启。**但眼别（OD/OS/OU）在开启后是必填项**——滴错眼是不可逆的，且是眼科特有的高频差错类型。

#### 5.6.3 移动端特殊考虑

- **屏幕尺寸**：三个录入控件竖向排列，每个控件高度 ≥ 48pt。
- **单手操作**：眼别三选一做成大按钮而非下拉菜单（下拉在走动中难点）。
- **网络状态**：离线时本地比对任务快照中的剂量与眼别。
- **扫码/拍照**：不涉及。
- **横竖屏**：竖屏固定。

#### 5.6.4 四种异常态

同 5.5.4。补充：本层若科室未开启，页面直接跳过并在 P02 的核对进度条上显示「已跳过（科室未启用）」——**灰色而非绿色**，让护士与管理者都能看出这一层没做。

### 5.7 P06 核对例外通道

**页面目标**：在物理原因导致无法扫码时，提供一条**留痕、双人、可审计**的放行路径。

#### 5.7.1 页面结构（三种角色三个视图）

| 视图 | 角色 | 内容 |
|---|---|---|
| 申请视图 | 责任护士 | 上下文摘要 + 原因选择 + 补充说明 + 「提交申请」 |
| 确认视图 | 第二确认护士 | 待确认列表 + 申请详情 + 患者身份核对提示 + 「确认」/「驳回」 |
| 复核视图 | 护士长 | 已完成例外列表 + 统计 + 「复核通过」/「驳回」 |

#### 5.7.2 申请视图

| 区域 | 内容 |
|---|---|
| 上下文摘要 | 床号、患者姓名脱敏、任务摘要、哪一层核对、已尝试几次 |
| 原因选择 | 六个枚举值，单选，必选 |
| 补充说明 | 自由文本，`OTHER` 时必填 |
| 提交 | 大按钮 |

原因枚举的中文文案：

| 值 | 文案 |
|---|---|
| `BARCODE_DAMAGED` | 条码破损/磨损 |
| `BARCODE_MISSING` | 条码缺失（腕带脱落、药袋无码） |
| `REFLECTION_UNREADABLE` | 反光/污渍导致无法识别 |
| `PATIENT_REFUSED_WRISTBAND` | 患者拒绝佩戴腕带 |
| `DEVICE_MALFUNCTION` | 本机摄像头故障 |
| `OTHER` | 其他（需说明） |

#### 5.7.3 确认视图的强制提示

确认人页面顶部必须显示：**「请独立核对患者身份。你的确认将作为双人核对记录留痕。」**

并且**必须显示申请人的设备与当前设备不同**的提示：若检测到当前设备与申请设备相同，直接禁止确认并提示「例外确认必须使用你自己的设备」。这是触发器的前端兜底——触发器会挡住，但挡住之后护士看到的是数据库错误，体验很差。

#### 5.7.4 移动端特殊考虑

- **屏幕尺寸**：确认视图的「确认」「驳回」两按钮间距 ≥ 40pt，防止误触。
- **单手操作**：确认按钮在右下，驳回按钮在左下。
- **网络状态**：**例外通道不支持离线**。理由：双人确认依赖另一台设备的实时校验，离线状态下无法确认「另一台设备在线、另一个账号真实在操作」。
- **扫码/拍照**：确认人可以「帮患者扫一次」作为独立核对的辅助，但这不是必需项。
- **横竖屏**：竖屏。

#### 5.7.5 四种异常态

| 异常 | 表现 |
|---|---|
| 网络断开 | 整页提示「例外通道需要联网，请在恢复网络后重试」；申请按钮置灰 |
| 上游超时 | 提交后提示「提交超时，请到 P07 或联系护士长确认是否已提交」（避免重复提交） |
| 无权限 | 无 `m20:nur:exception:confirm` 权限者看不到确认视图入口 |
| 数据为空 | 确认视图无待确认项：「当前没有需要你确认的例外申请」 |

#### 5.7.6 例外通道的四条硬边界

这四条在数据结构文档 §4.3.1 已作为数据库约束落地，此处从页面角度重述，因为**页面是最后一道防线**：

1. **不能同一人两次确认**（`ck_m20_nur_nxe_two_person`）；
2. **不能同一设备两次确认**（触发器 `trg_fn_m20_nur_nxe_confirm_same_device`）；
3. **原因必须结构化**，`OTHER` 必须补充说明；
4. **例外单一次性**，用后即废。

### 5.8 P07 离线记录与冲突处置

**页面目标**：让护士知道「离线时记的哪些已经生效了、哪些需要人来决定」。

#### 5.8.1 页面结构

| 区域 | 内容 |
|---|---|
| 顶部统计 | 待提交 / 已生效 / 待处置 三个数字 |
| 待处置清单 | 冲突项，每项显示冲突原因与当前状态 |
| 已生效清单 | 最近 50 条 `REPLAYED` |
| 处置入口 | 点开冲突项进入处置弹层 |

#### 5.8.2 冲突项的展示

每项必须显示三样东西，缺一不可：

1. **冲突类型的中文说明**（不是枚举值直出）：

| `conflict_type` | 文案 |
|---|---|
| `ENTITY_GONE` | 医嘱已作废或不存在 |
| `VERSION_CHANGED` | 医嘱已被修改 |
| `STATE_INVALID` | 该任务已被处理（可能由其他护士完成） |

2. **离线时的事实**：设备记录时间、扫到的患者与药品。
3. **当前的事实**：从 `replay_context` 取，如「医嘱状态：已停止」。

护士要根据这两组事实判断该丢弃还是人工补录。

#### 5.8.3 处置三个动作

| 动作 | 含义 | 后果 |
|---|---|---|
| `DISCARD` | 丢弃这条离线记录 | 不落 M08，标记已处置 |
| `APPLY_ANYWAY` | 仍按离线时的事实落库 | 需要说明理由，落 M08 但标记为延迟补录 |
| `MANUAL_FIX` | 人工修正后重新提交 | 进入 P02 重新核对执行 |

**`APPLY_ANYWAY` 必须显示二次确认弹窗**，写明「本次给药将按离线时记录的时间补录，可能与实际给药时间存在偏差」。

#### 5.8.4 移动端特殊考虑

- **屏幕尺寸**：冲突项卡片较高（含两组事实），一屏约 2 张。
- **单手操作**：处置动作放弹层底部。
- **网络状态**：本页只在联网时可用（冲突处置必须实时查上游）。
- **扫码/拍照**：不涉及。
- **横竖屏**：竖屏。

#### 5.8.5 四种异常态

| 异常 | 表现 |
|---|---|
| 网络断开 | 整页提示「冲突处置需要联网」；显示本地待提交数量 |
| 上游超时 | 处置提交失败：提示「处置未保存，请重试」，不本地记账 |
| 无权限 | 只能看不能处置，处置按钮置灰并提示需要 `m20:nur:offline:resolve` |
| 数据为空 | 「没有待处置的离线记录」 |

### 5.9 P08 交接班备忘

**页面目标**：护士在床旁用 10 秒记下一句话，交给下一班。

#### 5.9.1 页面结构

| 区域 | 内容 |
|---|---|
| 备忘输入 | 大文本框（最多 1000 字）+ 语音输入按钮 |
| 结构化条目 | 可选的条目列表（管路/伤口/用药/设备/其他） |
| 关联患者 | 可选：绑定当前患者或床号，或留空（病区级事项） |
| 紧急程度 | 普通 / 紧急 / 危重 三选一 |
| 提交 | 「保存」 |

#### 5.9.2 移动端特殊考虑

- **屏幕尺寸**：文本框占屏幕 60%，键盘弹出时不遮挡提交按钮。
- **单手操作**：语音输入为主路径（护士一手扶患者、一手拿手机）。
- **网络状态**：离线可写，进本地队列，联网后提交。
- **扫码/拍照**：支持拍照附在备忘上（如伤口照片），图片存对象存储，只在 `voice_url` 类字段存地址。
- **横竖屏**：竖屏。

#### 5.9.3 隐私边界

备忘正文 `memo_text` 是**自由文本，护士会写任何东西**。三条边界：

1. **不进事件载荷**。事件里只放 `memo_id`、`patient_id`、`urgency`。
2. **不拦截敏感词**。拦截会让护士改用口头交接，更不可追溯。改为提交时提示「备忘将展示给本科室接班护士」。
3. **不进病历**。备忘不是正式交接班记录（M08-07），不进病历也不进病案。

#### 5.9.4 四种异常态

| 异常 | 表现 |
|---|---|
| 网络断开 | 顶部灰条「已本地保存，联网后提交」 |
| 上游超时 | 同离线 |
| 无权限 | 输入框置灰「无写备忘权限」 |
| 数据为空 | 「本班还没有备忘」 |

### 5.10 P09 常用医嘱组与快捷入口

**页面目标**：把科室高频的操作模板化，减少重复点击。

#### 5.10.1 页面结构

两个 Tab：

| Tab | 内容 |
|---|---|
| 医嘱组 | 按分类（术前/术后/常规/出院）列出可用医嘱组；每组显示名称、条目数、使用次数 |
| 快捷入口 | 个人化的常用筛选、常看患者、常进页面 |

#### 5.10.2 医嘱组的边界（重要）

**医嘱组是模板参数，不是医嘱。**

护士点「使用这个组」时，系统不会直接生成医嘱，而是：
1. 展示组内每一条的默认参数；
2. 护士可逐条修改；
3. 点「提交」后，**逐条进入 M07 的开单流程，由医师确认签发生效**。

这一点必须在页面上明确提示：「医嘱组仅为常用参数模板，提交后需医师确认」。如果护士误以为点一下就开好医嘱了，就会出现「我以为开好了」而医嘱从未存在。

#### 5.10.3 移动端特殊考虑

- **屏幕尺寸**：医嘱组卡片列表，每卡片最多 4 行。
- **单手操作**：Tab 切换位于屏幕底部。
- **网络状态**：医嘱组数据可缓存（非业务数据），离线可看不可用。
- **扫码/拍照**：不涉及。
- **横竖屏**：竖屏。

#### 5.10.4 四种异常态

| 异常 | 表现 |
|---|---|
| 网络断开 | 显示缓存医嘱组，标注「离线不可使用」 |
| 上游超时 | 「医嘱组加载失败」+ 重试 |
| 无权限 | 只读视图，无编辑入口 |
| 数据为空 | 「本科室还没有配置常用医嘱组」+ 护士长可去 P10 引导 |

### 5.11 P10 护理端配置与合规统计

**页面目标**：护士长看合规率与设备情况，改科室参数。

#### 5.11.1 页面结构

三个 Tab：

| Tab | 内容 |
|---|---|
| 合规统计 | 核对合规率（M20-NUR-CALC-01）、设备扫码失败率（M20-NUR-CALC-02）、例外占比 |
| 配置 | 27 个配置键，按组折叠（核对/例外/离线/界面/性能）；每项显示当前值、来源作用域、默认值 |
| 设备自检 | 本机摄像头、网络、时钟偏差自检；设备登记信息 |

#### 5.11.2 合规统计的展示要求

**不允许只显示一个合规率数字**。页面必须同时展示：

| 指标 | 说明 |
|---|---|
| 合规率 | M20-NUR-CALC-01 的结果，分母为 0 时显示「—」而非 100% |
| 通过扫码 | `verified_count` |
| 通过例外 | `exception_count` + 占比（超 1% 标黄） |
| 不可判定 | `unmeasurable_count` + 点击下钻看明细 |
| 设备失败率 | 按设备分组的 `barcode_fail_rate` |

理由见 3.4.2 的算例：合规率 100% 的背后可能是 2.5% 的例外。只报一个数就会得出错误的结论。

#### 5.11.3 配置变更的四个等级

| 变更类型 | 例子 | 审批要求 |
|---|---|---|
| 收紧（更严） | 把 `SCAN_REQUIRE_DOSE_ROUTE` 从 false 改 true | 无需审批 |
| 放宽（更松但保留闸门） | 把 `SCAN_MAX_ATTEMPTS` 从 2 改 3 | 科室双签 |
| 影响离线 | 把 `OFFLINE_MAX_HOURS` 从 24 改 48 | 科室双签 + 留痕 |
| **禁用闸门** | 把 `SCAN_REQUIRE_PATIENT` 从 true 改 false | **护理部审批 + 全院公告** |

第四条是重点：**禁用闸门不是配置项，是管理决策**。数据库层用 `ck_m20_nur_ndc_...` 限制了取值范围，但真正的保护是审批流程。页面上这类配置项必须显示红色警示图标与「需护理部审批」字样。

#### 5.11.4 移动端特殊考虑

- **屏幕尺寸**：统计页图表用横向条形图而非饼图（小屏上饼图角度难辨）；配置页每项一行，右侧开关/数值。
- **单手操作**：配置项开关在行尾右侧，配合整行点击。
- **网络状态**：统计需联网；配置修改需联网。
- **扫码/拍照**：设备自检含扫码测试（扫测试码验证摄像头）。
- **横竖屏**：统计页支持横屏看图表。

#### 5.11.5 四种异常态

| 异常 | 表现 |
|---|---|
| 网络断开 | 统计页显示「需联网查看」；配置页可看缓存值但不可改 |
| 上游超时 | 单项统计显示「—」并标注失败，不显示 0 |
| 无权限 | 统计页只读；配置项全部置灰 |
| 数据为空 | 「统计期内没有核对记录」+ 说明可能原因 |

## 6.2.3 通用响应约定

```json
{"code": 0, "message": "success", "data": {}, "trace_id": "7f3a1c2e"}
```

降级返回（HTTP 仍为 200）：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "degraded": true,
    "degraded_sources": [{"source": "M08", "reason": "TIMEOUT", "detail": "任务服务 1.5s 未响应"}],
    "data_quality": "PARTIAL",
    "as_of": "2026-11-07T10:09:35+08:00"
  },
  "trace_id": "7f3a1c2e"
}
```

失败返回：

```json
{"code": "2003005", "message": "核对失败：该条码属于 6床 李红", "data": null, "trace_id": "7f3a1c2e"}
```

**三条红线**（共享规范 §8A.3）：

1. 不允许「看起来正常但不完整」的 200——不完整必须带四质量标记；
2. 不允许把「没查到」伪装成空数组 + `degraded: false`；
3. **不允许用 200 + 空 data 表达「无权限」，一律 403 + 非 0 错误码**。

#### 6.2.4 HTTP 状态码约定

| 状态码 | 含义 | 本子模块的例子 |
|---|---|---|
| 200 | 成功（含降级返回） | 任务列表降级 |
| 201 | 资源创建成功 | 新建备忘、新建医嘱组 |
| 400 | 参数错误 | 缺 `X-Device-Id`、`scan_time` 无时区 |
| 401 | 未认证 | M02 令牌校验失败 |
| 403 | 无权限（**含无数据权限**） | 无 `m20:nur:execute:verify` |
| 404 | 资源不存在 | 任务不存在、例外单不存在 |
| 409 | 状态冲突 | 例外单已被确认、同一设备双确认 |
| 422 | 语义校验失败 | 给药类离线记录缺扫码码值 |
| 429 | 频率超限 | 例外申请过于频繁 |
| 500 | 服务内部错误 | 证据落库失败 |
| 503 | 上游不可用且不可降级 | M08 任务服务不可用且无缓存 |

#### 6.2.5 质量标记的重算规则

`data_quality` **只由 M20 按 M20-CALC-05 从三个客观事实重算**：

1. 上游是否全部成功（`degraded` 与否）；
2. 是否命中 M20 自己的 30 秒缓存（`CACHED` 与否）；
3. 上游是否给出了可用的 `as_of`（给不出则 `UNKNOWN`）。

**不透传上游的值**。上游自己的质量词汇只能出现在 `degraded_sources[].reason` 里，例如 M18 的 `DAILY` 写成 `"reason": "UPSTREAM_DAILY"`。理由：M18 的 `DAILY` 意思是「来自日批汇总」，可能恰恰是最新的；M20 的 `CACHED` 意思是「这是 M20 自己 30 秒前的缓存」。两者成因不同，映射成一个值会把「上游本来就长这样」与「M20 缓存旧了」混为一谈。

**不写映射表**。共享规范 §8A.2.1 明确禁止。

**业务逻辑**

2. 从 `permission-context` 取 `staff_id`、`dept_id`、`ward_ids`；`is_mobile_user=false` 直接 403（G-2 闸门）。

6. **调 M08-01 失败且有未过期缓存**：返回缓存，`degraded=true`，`degraded_sources=[{"source":"M08","reason":"TIMEOUT"}]`，`data_quality=PARTIAL`，`as_of` 取缓存原值，`banner="UPSTREAM_DEGRADED"`。

9. `overdue_flag` 由 M20 按 `now > planned_time + UI_OVERDUE_HIGHLIGHT_MINUTES` 计算，不用 M08 的值。
10. 返回；`as_of` 取所有成功来源的最早值。

| 上游 | 契约 | SLA | 失败怎么降级 |
|---|---|---|---|

1. 校验 `m20:nur:execute:verify` 权限与 `X-Device-Id`，失败 403 / 400。
2. 校验幂等键：命中则返回上次结果，**不重复调上游**（否则第二次会因 attempt 累积触发锁定）。
3. 校验 `patient_id` 与任务上的患者一致；不一致**不报错**，因为参数是客户端带的，改为以 `execution_id` 反查任务的 `patient_id` 为准。
4. 查 M08 该执行记录的核对状态，若已锁定（连续失败达 `SCAN_MAX_ATTEMPTS`）→ 409 `"2003007"`，`next_action=CONTACT_HEAD_NURSE`。
5. 按时钟偏差分级处理 `scan_time` 与服务器时间的差：
   - ≤60 秒：采信，`clock_skew_seconds` 照实记录；
   - 60~300 秒：采信，但计指标 `m20_nur_clock_skew_total`；
   - >300 秒：**落库但标记可疑**，返回时 `clock_skew_suspicious=true`，且该时刻**不得作为给药时刻依据**（给药时刻以 M08 的 `actual_time` 为准）。
6. 调 M08-03 `verify-patient`：
   - 返回 `verified=true` → `verify_result=MATCHED`，`upstream_status=OK`；
   - 返回「患者身份核对未通过」错误（M08-03 自定义码，含义为核对不符）→ `verify_result=MISMATCH`，`matched_patient_id` 取 M08 返回的值；若 M08 未返回归属，用 M06-04 反查腕带归属补上，反查也失败则 `mismatch_reason` 写「扫到的码值不属于当前患者」，**不写具体是谁**（宁可不写也不写错）；
   - 返回「身份核对已锁定需护士长授权」错误（M08-03 自定义码）→ 409 `"2003007"`；
   - 超时/5xx → **`verify_result=UPSTREAM_UNAVAILABLE`，`upstream_status=TIMEOUT|HTTP_ERROR`，绝不落成 MATCHED**。
7. 写 `m20_nur_scan_verify`（这一条是证据，**先写证据**）；写失败 → 500 `"2003012"`，**不返回通过**。理由：证据没落下就说核对通过，等于没有证据。
8. 写 `m20_nur_oper_log`（`SCAN_PATIENT`/`SCAN_DRUG`/`SCAN_DOSE_ROUTE`）。
9. 计算 `next_stage` 与 `is_locked`。
10. 返回。

**为什么第 7 步必须先于第 10 步**：如果反过来，护士看到「核对通过」而数据库里没有这条记录，事后查不到任何核对痕迹。这类「显示成功但没留痕」的缺陷在护理系统里是最严重的一类。

`POST /api/v1/m20/nursing/offline/replay`

| 项 | 内容 |
|---|---|
| 权限 | `m20:nur:offline:submit` |

**请求体**

```json
{"queue_nos": ["OF20261107000421"], "dry_run": false}
```

**响应（要点）**

```json
{
  "code": 0,
  "data": {
    "total": 1,
    "replayed": 0,
    "blocked": 0,
    "skipped": 0,
    "conflicts": [
      {
        "queue_no": "OF20261107000421",
        "replay_status": "REPLAY_BLOCKED",
        "conflict_type": "STATE_INVALID",
        "resolved_action": null,
        "must_surface_to_human": true,
        "device_recorded_at": "2026-11-07T08:05:12+08:00"
      }
    ],
    "must_surface_to_human": true
  }
}
```

**业务逻辑（七步，即 3.3.4 与数据结构 §4.4.5 的落地）**

1. 校验权限与幂等。
2. 取待重放项（`replay_status IN ('NOT_REPLAYED','REPLAY_BLOCKED')` 且 `resolved_at IS NULL`）。
3. 对每一项依次判定：
   1. 调 M07-03 `for-execute` 取**当前**医嘱；
   2. 医嘱不存在/已作废/已停止/已退费 → `CONFLICT/ENTITY_GONE`；
   3. `order_version` 不一致 → `CONFLICT/VERSION_CHANGED`；
   4. `patient_id` 不符 → `CONFLICT/STATE_INVALID`（串人）；
   5. `drug_code` 不符 → `CONFLICT/STATE_INVALID`（换药）；
   6. M08 任务已 `COMPLETED`/`REJECTED`/`SKIPPED` → `CONFLICT/STATE_INVALID`（已被他人执行）；
   7. 以上都不命中 → 调 M08 落库，成功置 `REPLAYED` 并记 `m08_execution_id`。
4. **冲突项一律不自动覆盖、不自动丢弃**，置 `REPLAY_BLOCKED` 并保持 `resolved_at` 为空，等待人工处置。
5. M07 或 M08 不可用 → 保持 `NOT_REPLAYED`，下次再试，不消耗次数上限。
6. 逐条写操作日志 `OFFLINE_REPLAY`。
7. 返回汇总；**`must_surface_to_human` 必须为 true**（有冲突时），客户端必须弹窗到人面前，不允许静默处理。

**第 6 步防的真实错误**：不做这一步，`OF-001` 会被重放成「同一给药执行两次」，而这是护理不良事件上报的典型来源（M20-CALC-06 算例）。

```json
{
  "code": 0,
  "data": {
    "from": "2026-11-01",
    "to": "2026-11-07",
    "verified_count": 1198,
    "exception_count": 31,
    "unmeasurable_count": 11,
    "eligible_count": 1240,
    "compliance_rate": 1.000000,
    "exception_rate": 0.025000,
    "unmeasurable_items": [
      {"reason": "NO_ENCOUNTER", "count": 6},
      {"reason": "CLOCK_INCONSISTENT", "count": 5}
    ],
    "warnings": ["例外占比 2.50% 超过 1% 阈值"],
    "degraded": true,
    "degraded_sources": [{"source": "VERIFY_WINDOW", "reason": "UNMEASURABLE_N"}],

    "as_of": "2026-11-07T10:00:00+08:00"
  }
}
```

**业务逻辑（按 M20-NUR-CALC-01，见 3.4.2）**

1. 校验权限与数据权限。
2. 统计 `eligible_count`：期间内有执行记录的护理任务数。
3. 统计 `verified_count`：`m20_nur_scan_verify` 中 `verify_result='MATCHED'` 且三层中至少患者层通过的记录数。
4. 统计 `exception_count`：`m20_nur_verify_exception` 中 `review_status='CONFIRMED'` 且 `used_flag=true` 的记录数。
5. 统计 `unmeasurable_count`：因任务或患者数据缺失无法判定的数量，**按原因分项返回**。
6. `compliance_rate = (verified_count + exception_count) / (eligible_count - unmeasurable_count)`：
   - **分母为 0 → 返回 `null`，不返回 0 也不返回 1**；
   - `unmeasurable_count > 0` → `degraded=true` + `degraded_sources=[{"source":"VERIFY_WINDOW","reason":"UNMEASURABLE_N"}]` + `data_quality=PARTIAL`。
7. `exception_rate = exception_count / 分母`，超 1% 写 `warnings`。
8. **必须同时返回分项**（`verified_count` / `exception_count` / `unmeasurable_count`），不允许只给一个合规率——3.4.2 的算例说明了原因：合规率 100% 背后可能是 2.5% 的例外。

**路由实现的三条注意事项**

1. **参数顺序**：无默认值的依赖参数（`svc`、`staff`、`_`、`payload`）必须排在有默认值的查询参数之前，否则 Python 语法错误。
2. **`status` 冲突**：`status` 是 `fastapi.status` 模块名，故路由参数名用 `status_filter`，通过 `Query(alias="status")` 对外仍叫 `status`。
3. **响应包装统一走 `respond()`**：它负责注入四质量标记与 `trace_id`，也负责把 `.http_status` 映射到正确的 HTTP 状态码。**不要在路由里手写 `JSONResponse`**，否则很容易忘记带质量标记。

```python
    def __init__(
        self,
        m08: M08Client | None = None,
        m06: M06Client | None = None,
        repo: ScanVerifyRepo | None = None,
        cfg: DeviceConfigRepo | None = None,
    ) -> None:
        self.m08 = m08 or M08Client()
        self.m06 = m06 or M06Client()
        self.repo = repo or ScanVerifyRepo()
        self.cfg = cfg or DeviceConfigRepo()

    async def submit(
        self,
        staff: dict,
        device_id: str,
        payload: ScanVerifyCreate,
        idempotency_key: str,
    ) -> Any:
        # 1) 幂等：命中直接返回上次结果，不重复调上游
        #    重复调上游会让 attempt 累积，第二次就触发锁定了
        cached = await redis_client.get(
            "m20:base:idem:verify:%s" % idempotency_key
        )
        if cached is not None:
            return self.repo.load_result(cached)

        # 2) 时钟偏差分级
        skew = self._clock_skew(payload.scan_time)
        skew_suspicious = skew > CLOCK_SKEW_WARN_SECONDS

        # 3) 以 execution_id 反查任务的患者为准，不采信客户端传的 patient_id
        task = await self.m08.get_execution(payload.task_id)
        if task is None:
            raise BizError("2003002", "任务不存在或已失效", http_status=404)
        expected_patient_id = task["patient_id"]

        # 4) 上游调用 —— 任何异常都落成 UPSTREAM_UNAVAILABLE
        result: str
        upstream_status: str
        matched_patient_id: int | None = None
        mismatch_reason: str | None = None
        try:
            resp = await self.m08.verify_patient(
                execution_id=payload.task_id,
                method=payload.verify_method,
                barcode=payload.scanned_code,
            )
            upstream_status = "OK"
            if resp.get("verified"):
                result = VerifyResult.MATCHED.value
                matched_patient_id = resp.get("matched_patient_id")
            else:
                result = VerifyResult.MISMATCH.value
                matched_patient_id = resp.get("matched_patient_id")
                mismatch_reason = resp.get("message") or "扫到的码值与任务患者不一致"
        except Exception as exc:  # noqa: BLE001 —— 闸门必须吃掉所有异常
            upstream_status = self._classify_upstream_error(exc)
            result = VerifyResult.UPSTREAM_UNAVAILABLE.value
            # 注意：这里绝不能 fallback 成 MATCHED。
            # 「查不到就当核对通过」是 fail-open，给药场景下等于没有闸门。

        # 5) M08 未给出归属时，用 M06-04 反查腕带属于谁；
        #    反查失败则只写「不属于当前患者」，宁可不写也不写错
        if (
            result == VerifyResult.MISMATCH.value
            and matched_patient_id is None
            and payload.verify_method in ("WRISTBAND_SCAN", "CARD_SCAN")
        ):
            owner = await self.m06.reverse_lookup_wristband(payload.scanned_code)
            if owner is not None:
                matched_patient_id = owner["patient_id"]
            elif mismatch_reason is None:
                mismatch_reason = "扫到的码值不属于当前患者"

        # 6) 先写证据再返回结果 —— 写失败就不许说通过
        record = self.repo.insert(
            verify={
                "task_id": payload.task_id,
                "order_id": payload.order_id,
                "patient_id": expected_patient_id,
                "verify_stage": payload.verify_stage,
                "verify_method": payload.verify_method,
                "scanned_code": payload.scanned_code,
                "scanned_code_hash": self._hash(payload.scanned_code),
                "expected_code": payload.expected_code,
                "matched_patient_id": matched_patient_id,
                "verify_result": result,
                "mismatch_reason": mismatch_reason,
                "upstream_status": upstream_status,
                "attempt_seq": payload.attempt_seq,
                "device_id": device_id,
                "network_state": payload.network_state,
                "scan_time": payload.scan_time,
                "clock_skew_seconds": skew,
                "scan_duration_ms": payload.scan_duration_ms,
            },
            staff=staff,
        )

        # 7) 记录幂等结果
        await redis_client.set(
            "m20:base:idem:verify:%s" % idempotency_key,
            record["verify_no"],
            ex=86400,
        )

        max_attempts = int(
            await self.cfg.get(
                "SCAN_MAX_ATTEMPTS", device_id=device_id,
                default=str(DEFAULT_MAX_ATTEMPTS),
            )
        )
        return self._build_result(
            record=record,
            result=result,
            max_attempts=max_attempts,
            skew_suspicious=skew_suspicious,
            expected_patient_id=expected_patient_id,
        )

    @staticmethod
    def _hash(code: str | None) -> str | None:
        """码值只存哈希用于检索，明文另存；两者都落库但检索走哈希。"""
        if not code:
            return None
        return hashlib.sha256(code.encode("utf-8")).hexdigest()

    @staticmethod
    def _clock_skew(scan_time: datetime) -> int:
        now = datetime.now(timezone.utc)
        t = scan_time.astimezone(timezone.utc)
        return int(abs((now - t).total_seconds()))

    @staticmethod
    def _classify_upstream_error(exc: Exception) -> str:
        name = type(exc).__name__.lower()
        if "timeout" in name:
            return "TIMEOUT"
        if getattr(exc, "status_code", None):
            return "HTTP_ERROR"
        return "DEGRADED"

    def _build_result(
        self,
        record: dict,
        result: str,
        max_attempts: int,
        skew_suspicious: bool,
        expected_patient_id: int,
    ) -> Any:
        blocked = result != VerifyResult.MATCHED.value
        attempt = int(record.get("attempt_seq") or 1)
        is_locked = blocked and attempt >= max_attempts
        code = 0
        if result == VerifyResult.MISMATCH.value:
            code = "2003005"
        elif result == VerifyResult.UPSTREAM_UNAVAILABLE.value:
            code = "2003008"
        return {
            "code": code,
            "data": {
                "verify_record_id": record["id"],
                "verify_no": record["verify_no"],
                "verify_stage": record["verify_stage"],
                "verify_result": result,
                "matched_patient_id": record.get("matched_patient_id"),
                "mismatch_reason": record.get("mismatch_reason"),
                "upstream_status": record["upstream_status"],
                "attempt_seq": attempt,
                "is_locked": is_locked,
                "clock_skew_suspicious": skew_suspicious,
                "server_time": record["server_time"].isoformat(timespec="seconds"),
                "degraded": result == VerifyResult.UPSTREAM_UNAVAILABLE.value,
                "degraded_sources": (
                    [{"source": "M08", "reason": record["upstream_status"]}]
                    if result == VerifyResult.UPSTREAM_UNAVAILABLE.value
                    else []
                ),
                "data_quality": (
                    "PARTIAL"
                    if result == VerifyResult.UPSTREAM_UNAVAILABLE.value
                    else "REALTIME"
                ),
                "as_of": record["server_time"].isoformat(timespec="seconds"),
            },
            "http_status": 200 if not blocked else (
                409 if is_locked else 200
            ),
        }
```

**这段代码的三个要点**

1. **`except Exception` 是刻意的**。闸门必须吃掉所有异常并落成 `UPSTREAM_UNAVAILABLE`，不允许任何异常 escape 到「跳过核对继续执行」的分支。注释里写明了原因：fail-open 在给药场景下等于没有闸门。
2. **第 6 步的顺序不可调**。先写证据，再返回「通过」。如果证据写失败（数据库异常），异常会向上抛成 500，护士看到的不是「通过」。
3. **反查腕带归属失败时宁可不写**。「扫到的码值不属于当前患者」比「属于 6 床李红」信息量少，但至少不错。写错患者姓名是比不写更严重的事故。

#### 6.5.2 例外确认的双人双设备校验

```python
"""例外通道第二人确认。

三重校验，缺一不可：
1. 确认人 != 申请人（数据库 CHECK 兜底）
2. 确认设备 != 申请设备（触发器兜底，此处前置）
3. 例外单未过期、未被使用
"""
from __future__ import annotations

from datetime import datetime, timezone

from app.core.errors import BizError
from app.core.redis import redis_client
from app.modules.m20.nursing.repo import VerifyExceptionRepo


class VerifyExceptionService:
    def __init__(self, repo: VerifyExceptionRepo | None = None) -> None:
        self.repo = repo or VerifyExceptionRepo()

    async def confirm(
        self,
        staff: dict,
        exception_no: str,
        payload,
        idempotency_key: str,
    ) -> dict:
        row = self.repo.get_by_no(exception_no)
        if row is None:
            raise BizError("2003013", "例外单不存在", http_status=404)

        if row["review_status"] != "PENDING":
            raise BizError(
                "2003014",
                "例外单当前状态不允许确认（当前：%s）" % row["review_status"],
                http_status=409,
            )

        # 校验一：换人
        if int(row["requester_id"]) == int(staff["staff_id"]):
            raise BizError(
                "2003015",
                "例外申请不能由申请人自己确认",
                http_status=409,
            )

        # 校验二：换设备
        # 同一个人换个账号在自己手机上点确认，账号不同但设备相同；
        # CHECK 约束看不出这一点，所以由触发器兜底，这里先给可读的提示。
        if row["device_id"] and payload.device_id == row["device_id"]:
            raise BizError(
                "2003015",
                "例外确认必须使用你自己的设备；同一设备上的两次确认不算双人核对",
                http_status=409,
            )

        # 校验三：未过期
        now = datetime.now(timezone.utc)
        if now > row["expire_at"]:
            self.repo.mark_expired(exception_no)
            raise BizError("2003014", "例外单已过期，请重新申请", http_status=409)

        # 校验四：确认人与申请人看到的原因必须一致
        # 不一致说明沟通有误，应驳回重新申请，而不是各说各话
        if payload.exception_reason != row["exception_reason"]:
            raise BizError(
                "2003015",
                "你选择的原因与申请人填写的不一致，请核对后重新确认",
                http_status=409,
            )

        updated = self.repo.confirm(
            exception_no=exception_no,
            confirmer_id=staff["staff_id"],
            confirmer_name=staff["staff_name"],
            confirmer_dept_id=staff.get("dept_id"),
            confirmer_device_id=payload.device_id,
            confirmed_at=now,
        )
        await redis_client.delete("m20:nur:exception:pending:%s" % exception_no)
        return {"code": 0, "data": updated, "http_status": 200}
```

**为什么校验二必须在应用层再写一遍**：触发器会挡住，挡住之后抛的是数据库异常 `SAME_DEVICE_TWO_PERSON`，护士看到的是「系统错误」而不是「你需要换一台设备」。同一件事，应用层给出可读提示，数据库层保证绝对拦得住——**两层都要有，不是冗余**。

#### 6.5.3 离线重放七步判定

```python
"""离线记录重放 —— M20-CALC-06 的落地实现。

七步判定，任一步命中即 CONFLICT，一律不自动覆盖也不自动丢弃。
最关键的是第 6 步：不做它，同一给药会被重放成执行两次。
"""
from __future__ import annotations

from datetime import datetime, timezone
from typing import Any

from app.modules.m20.nursing.clients import M07Client, M08Client
from app.modules.m20.nursing.repo import OfflineItemRepo


TERMINAL_TASK_STATUS = {"COMPLETED", "REJECTED", "SKIPPED"}
GONE_ORDER_STATUS = {"STOPPED", "CANCELLED", "REFUNDED", "REJECTED", "ABANDONED"}


class OfflineReplayService:
    def __init__(
        self,
        m07: M07Client | None = None,
        m08: M08Client | None = None,
        repo: OfflineItemRepo | None = None,
    ) -> None:
        self.m07 = m07 or M07Client()
        self.m08 = m08 or M08Client()
        self.repo = repo or OfflineItemRepo()

    async def replay_one(self, item: dict) -> dict[str, Any]:
        # 第 1 步：取当前医嘱
        try:
            order = await self.m07.for_execute(item["order_id"])
        except Exception:
            # 上游不可用不算冲突，保持待重放，下次再试
            return {"status": "NOT_REPLAYED", "reason": "UPSTREAM_UNAVAILABLE"}

        # 第 2 步：实体已不存在
        if order is None or order.get("order_status") in GONE_ORDER_STATUS:
            return self._conflict(item, "ENTITY_GONE", {
                "order_status": (order or {}).get("order_status"),
                "fetched_at": self._now_iso(),
            })

        # 第 3 步：版本已变
        if order.get("order_version") != item["order_version"]:
            return self._conflict(item, "VERSION_CHANGED", {
                "order_version": order.get("order_version"),
                "recorded_version": item["order_version"],
                "fetched_at": self._now_iso(),
            })

        # 第 4 步：串人（离线时扫的人与医嘱患者不一致）
        if int(order.get("patient_id") or 0) != int(item["patient_id"] or 0):
            return self._conflict(item, "STATE_INVALID", {
                "reason": "PATIENT_MISMATCH",
                "order_patient_id": order.get("patient_id"),
                "fetched_at": self._now_iso(),
            })

        # 第 5 步：换药（离线时扫的药与当前医嘱不一致）
        current_drugs = {d.get("drug_code") for d in order.get("items", [])}
        if item["drug_code"] not in current_drugs:
            return self._conflict(item, "STATE_INVALID", {
                "reason": "DRUG_CHANGED",
                "current_drug_codes": sorted(x for x in current_drugs if x),
                "fetched_at": self._now_iso(),
            })

        # 第 6 步：任务已被别人处理 —— 这一步最容易被漏掉
        # 漏掉它，OF-001 会被重放成「同一给药执行两次」
        task = await self.m08.get_task(item["task_id"])
        if task is not None and task.get("task_status") in TERMINAL_TASK_STATUS:
            return self._conflict(item, "STATE_INVALID", {
                "reason": "TASK_ALREADY_HANDLED",
                "task_status": task.get("task_status"),
                "handled_by": task.get("executed_by"),
                "fetched_at": self._now_iso(),
            })

        # 第 7 步：都通过，落 M08
        execution = await self.m08.create_execution(
            task_id=item["task_id"],
            order_id=item["order_id"],
            patient_scan_code=item["patient_scan_code"],
            drug_scan_code=item["drug_scan_code"],
            dose_quantity=item["dose_quantity"],
            dose_unit=item["dose_unit"],
            route_code=item["route_code"],
            eye_side=item["eye_side"],
            actual_time=item["device_recorded_at"],
            source="M20_OFFLINE_REPLAY",
        )
        self.repo.mark_replayed(item["queue_no"], execution["execution_id"])
        return {"status": "REPLAYED", "execution_id": execution["execution_id"]}

    def _conflict(self, item: dict, conflict_type: str, ctx: dict) -> dict:
        """冲突一律不自动覆盖、不自动丢弃，等人工处置。"""
        self.repo.mark_conflict(
            item["queue_no"],
            conflict_type=conflict_type,
            replay_context=ctx,
        )
        return {
            "status": "REPLAY_BLOCKED",
            "conflict_type": conflict_type,
            "must_surface_to_human": True,
        }

    @staticmethod
    def _now_iso() -> str:
        return datetime.now(timezone.utc).isoformat(timespec="seconds")
```

#### 6.5.4 任务列表的降级判定（SC-02 的实现）

```python
"""任务列表 —— 「绝不能返回空列表」的实现。

空列表会让护士以为今天没活而漏给药。三种情形必须严格区分：
1. 确实没任务     -> items=[] + banner=NONE，前端显示灰色插画
2. 上游降级有缓存 -> items=缓存 + banner=UPSTREAM_DEGRADED，前端显示黄条
3. 上游失败无缓存 -> 503 + items=[] + banner=UPSTREAM_DEGRADED，前端显示红条
"""
from __future__ import annotations

from datetime import date, datetime, timezone
from typing import Any

from app.core.redis import redis_client
from app.modules.m20.nursing.clients import M08Client
from app.modules.m20.nursing.repo import DeviceConfigRepo


class TaskService:
    def __init__(
        self,
        m08: M08Client | None = None,
        cfg: DeviceConfigRepo | None = None,
    ) -> None:
        self.m08 = m08 or M08Client()
        self.cfg = cfg or DeviceConfigRepo()

    async def list_tasks(
        self,
        staff: dict,
        device_id: str,
        query_date: date,
        status_filter: str | None,
        group_by: str,
        page_no: int,
        page_size: int,
    ) -> dict[str, Any]:
        nurse_id = staff["staff_id"]
        ttl = int(
            await self.cfg.get(
                "PERF_TASK_CACHE_TTL_SECONDS",
                device_id=device_id,
                default="30",
            )
        )
        cache_key = "m20:nur:task:%s:%s" % (nurse_id, query_date.isoformat())
        cache_age = await redis_client.ttl(cache_key)

        try:
            upstream = await self.m08.tasks_by_nurse(
                nurse_id=nurse_id,
                query_date=query_date,
                status=status_filter,
            )
        except Exception:
            # 上游失败：有缓存用缓存，没缓存就 503，绝不静默返回空列表
            cached = await redis_client.get_json(cache_key)
            if cached is not None:
                return self._wrap(
                    cached,
                    banner="UPSTREAM_DEGRADED",
                    degraded=True,
                    reason="TIMEOUT",
                    data_quality="PARTIAL",
                    as_of=cached["as_of"],
                    http_status=200,
                )
            return self._wrap(
                {"items": [], "counts_by_status": {}, "overdue_count": 0},
                banner="UPSTREAM_DEGRADED",
                degraded=True,
                reason="TIMEOUT",
                data_quality="UNKNOWN",
                as_of=datetime.now(timezone.utc).isoformat(timespec="seconds"),
                http_status=503,
                code="2003001",
                message="护理任务服务暂不可用，请到护士站核对",
            )

        as_of = upstream.get("as_of")
        if as_of is None:
            # 上游没给 as_of，整个响应的新鲜度就无法判定
            data_quality = "UNKNOWN"
        elif cache_age is not None and 0 < cache_age < ttl:
            data_quality = "CACHED"
        else:
            data_quality = "REALTIME"

        if as_of is not None:
            await redis_client.set_json(
                cache_key, {"items": upstream["tasks"], "as_of": as_of}, ex=ttl
            )

        return self._wrap(
            {
                "items": upstream["tasks"],
                "counts_by_status": self._count_by_status(upstream["tasks"]),
                "overdue_count": self._overdue_count(upstream["tasks"]),
            },
            banner="NONE",
            degraded=False,
            reason=None,
            data_quality=data_quality,
            as_of=as_of,
            http_status=200,
        )

    def _wrap(
        self,
        payload: dict,
        banner: str,
        degraded: bool,
        reason: str | None,
        data_quality: str,
        as_of: str,
        http_status: int,
        code: Any = 0,
        message: str = "success",
    ) -> dict[str, Any]:
        items = payload.get("items") or []
        return {
            "code": code,
            "message": message,
            "http_status": http_status,
            "data": {
                "items": items,
                "record_count": len(items),
                "counts_by_status": payload.get("counts_by_status", {}),
                "overdue_count": payload.get("overdue_count", 0),
                "banner": banner,
                "degraded": degraded,
                "degraded_sources": (
                    [{"source": "M08", "reason": reason}] if degraded else []
                ),
                "data_quality": data_quality,
                "as_of": as_of,
            },
        }

    @staticmethod
    def _count_by_status(tasks: list[dict]) -> dict[str, int]:
        """按 M08 的 task_status 六值分组；不认识的键也算进去，不吞掉。"""
        out: dict[str, int] = {}
        for t in tasks:
            key = str(t.get("status") or "UNKNOWN")
            out[key] = out.get(key, 0) + 1
        return out

    @staticmethod
    def _overdue_count(tasks: list[dict]) -> int:
        """超时判定由 M20 算，不用 M08 的值。

        理由：M08 的超时口径是「任务侧超时」，M20 的页面口径是
        「超过计划时间 N 分钟提醒」，两者阈值不同。
        """
        now = datetime.now(timezone.utc)
        count = 0
        for t in tasks:
            planned = t.get("planned_time")
            if not planned:
                continue
            try:
                p = datetime.fromisoformat(str(planned))
            except ValueError:
                continue
            if p.tzinfo is None:
                p = p.replace(tzinfo=timezone.utc)
            if now > p:
                count += 1
        return count
```

**三条实现纪律**

1. **`banner` 与 `degraded` 必须同时给**。只给 `degraded` 前端不知道显示黄条还是红条；只给 `banner` 会让 `data_quality` 的语义丢失。
2. **上游异常一律 `except Exception`**。这里与闸门不同——这里可以降级用缓存，但**不能降级成空列表**。
3. **`_overdue_count` 由 M20 自己算**。M08 的超时口径与页面提醒口径不同，直接透传会导致「M08 说没超时、手机标红」的对不上的情况。

### 6.6 错误码定义表（唯一权威）

**错误码使用纪律**

1. **本表是唯一权威**。其他章节若引用错误码，语义必须与本表一致；不一致时以本表为准。
2. **号段不得越界复用**。`"2003xxx"` 属于 M20-03，不得使用 M20 其他子模块的码（如 M20-04 的 `"2004xxx"`）。
3. **`"2003005"`、`"2003008"`、`"2003042"` 三个码的 HTTP 是 200**。它们不是"操作失败"而是"核对结论"，携带完整 `data` 供前端渲染。用 200 是因为核对本身的查询是成功的。
4. **纯设计约束型规则挂 `—`**。例如「扫码记录只增不改」「执行结果一律落 M08」这类约束没有运行时错误码，不应硬塞一个。

## 7. 缓存与异步任务设计

### 7.1 缓存设计

本子模块的缓存目标只有一个：**让床边的那一次扫码尽可能不发生网络等待**。缓存不承担任何业务判定，凡是「能不能继续」的判断都必须现场取数。

| Key 模式 | 类型 | TTL | 内容 | 失效时机 | 峰值容量估算 |
|---|---|---|---|---|---|
| `m20:nur:task:{staff_id}:{date}` | String(JSON) | 30 秒 | 该护士当日 M08 任务摘要列表（`task_id`/`planned_time`/`bed_no`/`patient_id`/`status`/`task_summary`） | M08 `m08.task.*` 事件到达即删；超 TTL 自然过期 | 在线峰值 300 人 × 1 个约 1.2 MB |
| `m20:nur:dashboard:{staff_id}` | String(JSON) | 30 秒 | 工作台聚合卡片数字 | 同上 | 约 0.3 MB |
| `m20:nur:config:{dept_id}` | Hash | 300 秒 | 该科室生效配置项（27 个键的合并结果） | 配置写入即删同科室 key | 60 科室 × 60 项，约 0.8 MB |
| `m20:nur:order-set:{dept_id}` | String(JSON) | 60 秒 | 该科室启用中的医嘱组列表（不含明细） | 医嘱组启用/停用即删 | 约 0.5 MB |
| `m20:nur:scan-code:{code_hash}` | String | 120 秒 | 条码 → 实体类型的解析结果（`WRISTBAND`/`DRUG`/`UNKNOWN`） | 自然过期 | 约 0.4 MB |
| `m20:nur:quiet:{staff_id}` | String | 300 秒 | 连续扫错锁定的临时标记（与数据库 `is_locked` 双写，仅用于快速失败） | 护士长解锁或锁定解除 | 极小 |
| `m20:lock:record:{resource}:{id}` | String | 30 秒 | 通用互斥锁（复用共享规范 §14） | 释放或过期 | 极小 |
| `m20:idem:{biz_type}:{key}` | String | 24 小时 | 幂等键（复用 M20-01 `m20_base_idempotency`，本地只为加速） | 自然过期 | 约 3 MB |

**容量合计约 6 MB**，毫秒级可重建，`maxmemory-policy` 使用 `volatile-lru` 即可，不需要独立实例。

#### 7.1.1 缓存不进判定链的三条硬规则

1. **缓存命中时 `data_quality` 必须是 `CACHED`**，且 `as_of` 取缓存写入时刻而不是当前时刻。共享规范 §14 已规定「缓存值必须带 `as_of`，命中缓存时 `data_quality` 必须是 `CACHED`」，本子模块在 `_wrap()` 里强制。
2. **三层核对的判定结果一律不走缓存**。腕带码、药品码、剂量途径的比对必须现场调 M08；哪怕 120 秒前刚比对成功，也不能复用——两次给药之间患者可能换了床位、药品可能换了批次。
3. **配置可以缓存但不能缓存超过 300 秒**。`SCAN_REQUIRE_DRUG` 这类闸门开关被人为改成 `false` 时，最坏情况下仍有 5 分钟的窗口期在用旧值。这个 5 分钟是刻意接受的代价：配置读取走数据库会在每次扫码上多一次往返，而闸门开关变更是极低频的管理动作。**接受的代价必须写清楚，否则运维会以为是缓存没刷。**

#### 7.1.2 为什么任务列表缓存 TTL 是 30 秒而不是 60 秒

共享规范 §14 给的上限是 60 秒，但本子模块取 30 秒。原因：M20-CALC-05 规定「缓存年龄 > 30 秒判 `CACHED`、≤ 30 秒判 `REALTIME`」，如果 TTL 也取 60 秒，那么 30~60 秒这一段的缓存一定会被判成 `CACHED` 并触发页面黄条——而这 30 秒的窗口恰好是护士从护士站走到床边的真实耗时。**让缓存活到它不能被判成 REALTIME 的那一刻就停，比让护士看着一条永远在闪的黄条更好。**

### 7.2 Celery 异步任务

| 任务名 | 触发方式 | 频率 | 职责 | 幂等与失败处理 |
|---|---|---|---|---|
| `nur_offline_replay` | 客户端回线回调 + 定时兜底 | 每 2 分钟扫一次待重放项 | 按 6.5.3 的七步算法重放离线队列 | 按 `queue_no` 幂等；单条失败只重试该条，最多 5 次后置 `REPLAY_BLOCKED` |
| `nur_scan_verify_archive` | 定时 | 每月 1 日 03:00 | 把 24 个月前的 `m20_nur_scan_verify` 搬到 `m20_nur_scan_verify_archive` | 按 `server_time` 区间分批删除并插入，单批 5,000 行，失败回滚该批 |
| `nur_oper_log_archive` | 定时 | 每月 1 日 03:30 | 把 12 个月前的 `m20_nur_oper_log` 搬到 `m20_nur_oper_log_archive` | 同上，单批 20,000 行 |
| `nur_device_failure_rollup` | 定时 | 每小时 05 分 | 按设备汇总扫码失败率，写入日报缓存供 API-32 读取 | 按 `(device_id, stat_hour)` 唯一，`ON CONFLICT DO UPDATE` |
| `nur_compliance_rollup` | 定时 | 每日 01:10 | 汇总核对合规率分项供 API-31 读取 | 按 `(dept_id, stat_date)` 唯一，重跑覆盖当日 |
| `nur_exception_expire` | 定时 | 每 5 分钟 | 把过期的例外单从 `PENDING` 置 `EXPIRED` | 只处理 `review_status='PENDING' AND NOW() > expire_at`，重复执行无副作用 |
| `nur_offline_conflict_notify` | 事件驱动 | 冲突产生时 | 给产生冲突的护士与护士长推待办（订阅侧，只发不写业务表） | 按 `queue_no` 去重 |
| `nur_stale_queue_cleanup` | 定时 | 每日 02:20 | 清理 `SYNCED` 且超过 90 天的离线项本地扩展记录 | 只删 `m20_nur_offline_item`，不动 `m20_base_offline_queue` |

**为什么离线重放要有定时兜底**：客户端回线后的主动重放可能因为 App 被杀、切换网络、锁屏而没跑到。只靠客户端触发，会出现「护士以为已经同步了、其实队列还在手机上」。定时兜底每 2 分钟扫一次服务端已收到的离线项，保证只要记录已经到服务端就一定会被重放或明确标记为冲突。

### 7.4 降级总则

**本子模块的降级方向一律朝「更严格」，不朝「更宽松」。** 这条与总纲 §5.4 一致，落地为三档：

| 依赖 | 正常 | 不可用时 | 为什么不能反过来 |
|---|---|---|---|
| M08 任务服务 | 返回任务列表 | `degraded=true` + `data_quality=PARTIAL` + 明确提示，**不返回空列表** | 返回空列表等于告诉护士「今天没活儿」 |
| M08 核对校验 | 三层比对 | 落 `UPSTREAM_UNAVAILABLE`，判定为**不许继续** | 放行等于闸门不存在 |
| M02 权限校验 | 200 | 403 + `"2003028"` | 查不到权限就当作有权限是越权 |
| M07 医嘱明细 | 返回明细 | 页面保留任务但核对页禁用「继续」，提示到工作站确认 | 没有医嘱明细就无法判断剂量途径 |
| M20-01 离线队列 | 正常收发 | 暂存端侧，不落本地扩展表 | 落一半比不落更难排查 |

### 8.3 状态流转规则

本子模块五个状态机的取值与流转已在 §3.2 定义，这里只列**校验层面的硬约束**：

- **BR-S-01**：护理任务状态**不由本子模块写入**。任何接口都不得返回「M20 自己算出来的任务状态」，状态一律取 M08 返回值原样透出。
- **BR-S-02**：`review_status` 只能从 `PENDING` 流转到 `CONFIRMED`/`REJECTED`/`EXPIRED`，其余任何流转一律拒绝（`"2003014"`）。
- **BR-S-03**：`review_status` 进入终态后不可再改，包括不可从 `EXPIRED` 手工改成 `CONFIRMED`。要重新核对就重新申请一张。
- **BR-S-04**：`replay_status='REPLAYED'` 之后不得再次重放（`"2003019"`）。
- **BR-S-05**：`replay_status='CONFLICT'` 只能通过 API-15 人工处置，不得被自动重放覆盖。
- **BR-S-06**：备忘 `status` 从 `OPEN` 到 `HANDED_OVER` 只能由接收人执行，不得由创建人自确认。

### 8.5 恒等式与闭合校验

#### 8.5.1 核对合规率三元组恒等式

合规率由三个互斥分项构成，任何时刻必须满足：

```
verified_count + exception_count + missed_count = eligible_count - unmeasurable_count
```

- `verified_count`：通过扫码核对完成的任务数
- `exception_count`：通过例外通道放行的任务数
- `missed_count`：既未扫码也未走例外就完成的任务数
- `eligible_count`：统计期内产生的应核对任务数
- `unmeasurable_count`：因上游不可用、任务被取消等原因无法判定的任务数

**分母 = `eligible_count - unmeasurable_count`**，`unmeasurable_count` 既不进分子也不进分母。分母为 0 时 `compliance_rate` 必须返回 `null`，**绝不能返回 0 或 100%**。

反例对照（把 `unmeasurable` 折进分母会让比率虚高，方向恰好是「数据越烂指标越好看」）：

| 口径 | 计算 | 结果 |
|---|---|---|
| 正确 | 1,229 / (1,240 − 11) = 1,229 / 1,229 | 1.000000，但例外占 2.50%，超 G-06 的 1% 阈值 |
| 错把不可判定进分母 | 1,229 / 1,240 | 0.991129，看起来「更真实」，实际是拿不可判定当未完成 |
| 错把不可判定当完成 | (1,229 + 11) / 1,240 | 1.000000，数据越烂比率越高 |

#### 8.5.2 设备扫码失败率两个比率不可合并

```
barcode_fail_rate    = unreadable_count / scan_total
patient_mismatch_rate = mismatched_count / (matched_count + mismatched_count)
upstream_unavailable 不进任何分母
```

合并成一个「失败率」会掩盖最关键的区别：**码扫不出来是设备或标签的问题（换设备），扫出来对不上是流程的问题（查流程）**。两者的处置动作完全不同，合成一个数就只能得到「这个设备不行」的模糊结论，然后换设备、再试、再失败。

#### 8.5.3 离线队列闭合校验

```
offline_received_count = replay_replayed_count + replay_blocked_count + replay_skipped_count + not_replayed_count
```

四项之和必须等于已收到的离线项总数，任何一项对不上说明有记录被静默丢弃。该恒等式在附录 C 有对应校验 SQL，纳入上线必跑清单。

### 8.6 引用与删除

- 本子模块九张表对 M08/M07/M05/M03 的引用**全部是逻辑引用**，不建外键。上游删除或作废时由本子模块在重放与展示阶段判定，不做级联。
- 内部唯一物理外键 `fk_m20_nur_osi_set` 使用 `ON DELETE RESTRICT`：删除医嘱组必须先显式处理条目。**不用 `CASCADE` 的理由**：`CASCADE` 会让「删掉一个组」变成一个不易察觉的批量删除，而组内条目是科室积累的资产，误删后无法从任何地方恢复。
- `m20_nur_scan_verify` 与 `m20_nur_oper_log` **不允许删除**，只允许归档搬运；数据库层 `REVOKE DELETE` 已落地。

### 8.7 并发控制

| 场景 | 手段 | 冲突处理 |
|---|---|---|
| 同一任务被两名护士同时领取 | 数据库 `UPDATE ... WHERE status='PENDING'` 影响行数为 0 即视为抢单失败 | 返回 `"2003009"` 并刷新列表 |
| 同一护士在两台设备上执行 | `m20:nur:quiet:{staff_id}` + 数据库 `is_locked` | 后到者拒绝，提示在另一台设备上继续 |
| 例外单被两人同时确认 | 乐观锁 `version_no` | 后到者 `"2003006"` |
| 配置并发修改 | 乐观锁 `version_no` | 后到者 `"2003006"` |
| 离线重放与在线执行并发 | 重放前重新过闸门（6.5.3 第 6 步） | 任务已终结则置 `CONFLICT/STATE_INVALID` |

**并发控制的判据**：凡是「两个护士可能同时做同一件事」的地方，都不依靠先查后写，而依靠单条带条件的 `UPDATE` 或唯一约束。先查后写在并发下必错，而且错得安静。

### 9.5 安全措施

1. **闸门不可绕过**：核对判定只有一条代码路径（`VerifyService.submit`），没有任何接口可以「直接置为已核对」。例外通道是唯一旁路，且需要第二人 + 第二台设备 + 原因 + 事后复核。
2. **防重放**：所有写接口要求 `X-Idempotency-Key`，键 `(biz_type, key)` 24 小时唯一。
3. **防超权**：每个请求除 Token 外必须校验 `is_mobile_user` 与 `m20:nur:*` 权限；任一校验接口失败一律 403（`"2003028"`），不得「查不到权限就当作有权限」。
4. **防时间作弊**：核对时间以服务器时间为准落 `server_time`，端侧时间只落 `scan_time` 并计算 `clock_skew_seconds`；偏差 >300 秒的记录进「时钟异常待核实」清单，且**不得作为给药时刻依据**。
5. **防设备共享**：例外确认记录 `device_id` 与 `confirmer_device_id`，两者相同直接由数据库触发器拒绝（`SAME_DEVICE_TWO_PERSON`）。
6. **防静默降级**：任何 `degraded=true` 或 `data_quality≠REALTIME` 的响应，页面必须有可见提示。没有提示的降级等于欺骗。
7. **脱敏不落库**：查询 SQL 只取脱敏后的值，完整值通过单独鉴权接口逐次获取并留痕。

## 10. 集成与契约

### 10.1 本子模块提供的内部契约

**本子模块不对外提供内部契约。**

M20-03 移动护理的 33 个接口全部是面向移动客户端（App / Pad）的对外 REST 接口，前缀 `/api/v1/m20/nursing`，没有任何模块需要调用本子模块的内部接口：

- 护理任务的真相在 M08，其他模块要查任务清单直接调 M08 的 P-01，绕道 M20 只会增加一跳。
- 扫码核对记录是护士端的操作留痕，其他模块需要核对结论时应当调 M08 的执行记录（`m08_execution_id` 上溯），而不是调 M20。
- 例外通道单的处置后果落在 M08 的执行记录上，M20 只是过程中间态。
- 交接班备忘按 §2.2 明确不进病历、不进事件载荷之外的任何系统。

因此共享规范 §8A 的 14 个 P-xx 中**没有一个是本子模块的**。若未来其他模块确实需要 M20-03 的数据，应当先评估是否应该改为由 M08 提供，而不是把 M20 变成一个新的下游依赖点。

#### 10.2.1 质量字段一律自算，不透传

`data_quality` 这个字段名多个模块都在用但值域不同。**M20 响应里的 `data_quality` 必须按 M20-CALC-05 自己重算**，上游返回值只能进 `degraded_sources[].reason`。例如 M18 返回 `DAILY`（含义是「来自日批汇总，可能恰恰是最新的」）时，M20 不得映射成 `CACHED`（含义是「M20 自己 30 秒前的缓存」）——两者成因完全不同，映射成一个值就让运维永远查不清是上游慢还是 M20 缓存旧。

正确写法：

| 情形 | `data_quality` | `degraded_sources` |
|---|---|---|
| 全部上游成功，缓存年龄 ≤30 秒 | `REALTIME` | `[]` |
| 全部上游成功，缓存年龄 >30 秒 | `CACHED` | `[]` |
| 有上游失败 | `PARTIAL` | `[{"source":"M08_TASK","reason":"TIMEOUT"}]` |
| 有上游返回了 `DAILY` 类标记 | `PARTIAL` | `[{"source":"M18","reason":"UPSTREAM_DAILY"}]` |
| 有来源未返回可用的 `as_of` | `UNKNOWN` | `[{"source":"M05","reason":"MISSING_AS_OF"}]` |

#### 10.5.1 床边给药核对时序

```
护士App        M20-03            M02         M08-01       M08-03       M08-06
   |              |                |            |            |            |
   |--扫腕带----->|                |            |            |            |
   |              |--perm/check--->|            |            |            |
```

#### 10.5.2 离线记录回线重放时序

```
App            M20-01            M20-03          M07-03       M08-03
 |               |                 |               |            |
 |--回线-------->|                 |               |            |
 |               |--队列项-------->|               |            |
 |               |                 |--for-execute->|            |
 |               |                 |<---医嘱当前态--|            |
```

## 11. 异常处理与日志

### 11.1 异常分类与统一处理

| 类别 | 典型场景 | HTTP | 错误码 | 处理方式 |
|---|---|---|---|---|
| 参数类 | 缺字段、类型错、枚举非法 | 400/422 | `"2003002"`、`"2003003"`、`"2003017"` | 直接返回，不重试 |
| 权限类 | 无权限、非移动用户 | 403 | `"2003028"`、`"2003030"` | 直达 403，不降级为「无数据」 |
| 不存在类 | 任务/例外单/离线项不存在 | 404 | `"2003004"`、`"2003010"`、`"2003020"` | 直接返回 |
| 状态冲突类 | 锁定、终态不可改、并发抢单 | 409 | `"2003006"`、`"2003007"`、`"2003009"`、`"2003014"`、`"2003016"`、`"2003019"` | 返回当前状态供前端刷新 |
| 闸门类（业务内失败） | 核对不符、核对层已跳过 | **200** | `"2003005"`、`"2003042"` | 走正常响应形态，`code` 非 0 且 `data` 完整 |
| 上游不可用类 | M08/M07 超时或 5xx | 503 或 **200** | `"2003001"`、`"2003008"` | 闸门类必须 fail-closed |
| 系统类 | 数据库异常、未预期异常 | 500 | `"209001"` | 记录 trace_id，不向前端暴露堆栈 |

**为什么「核对不符」是 HTTP 200 而不是 4xx**：从 HTTP 语义看请求是合法且被成功处理的，业务结论是「这次核对的结果是不符」。如果返回 4xx，前端和网关的通用错误处理会把 `data` 丢掉，而 `data` 里带着「扫到的是谁」——这正是护士最需要看到的信息。这一条与共享规范 §8A.3「不允许用 200 + 空 data 表达无权限」不冲突：那条禁止的是**用 200 掩盖权限失败**，而这里是**用 200 传递一个真实的业务结论**。

### 11.2 降级策略

#### 11.2.1 三种合法响应形态

| 形态 | HTTP | `code` | `data` | 场景 |
|---|---|---|---|---|
| 正常 | 200 | 0 | 完整 + `degraded=false` + `data_quality=REALTIME` | 全部成功 |
| 降级返回 | 200 | 0 | 完整但标注 + `degraded=true` + `degraded_sources=[...]` | 部分上游失败但结论仍可用 |
| 失败 | 4xx/5xx | 非 0 | 可为空或携带诊断信息 | 无法给出结论 |

#### 11.2.2 逐依赖降级方向

| 依赖 | 降级后 | 方向判定 |
|---|---|---|
| M08 任务列表 | 返回缓存 + `degraded=true`，**绝不返回空 items** | 更少信息但更诚实 |
| M08 核对校验 | 落 `UPSTREAM_UNAVAILABLE`，判定不许继续 | 更严格 |
| M07 医嘱明细 | 禁用「继续」，提示到工作站 | 更严格 |
| M08-06 药品依据 | 阻断药品核对 | 更严格 |
| M03 患者摘要 | 姓名显示「——」 | 不阻断核对，只减少展示 |
| M06 腕带取值 | 转就诊卡或双项手输 | 不降低核对等级，只换方式 |
| M02 审计写入 | 只记本地日志 + 标注 | 不丢证据，只降精度 |
| M02 权限校验 | 403 | 更严格 |

**判据**：降级后如果护士更可能给错药，这个降级就不成立。上表每一行都按这个判据过过一遍——凡是通过「让它过去」来实现降级的方向，一律不采用。

### 12.4 安全验收 SC

| 编号 | 验收项 | 判据 |
|---|---|---|
| SC-01 | 闸门不可关闭 | 唯一能改 `SCAN_REQUIRE_PATIENT`/`SCAN_REQUIRE_DRUG` 的接口是 API-29，且无审批单号时拒绝 |

| SC-03 | 核对校验不可用不得放行 | 打桩使 M08-03 超时，提交核对后断言未产生 `MATCHED`，且判定结果为不许继续 |

| SC-06 | 事件载荷无敏感信息 | 抓取 `m20.nur.*` 全部事件，断言载荷无姓名/手机号/证件号/诊断文本 |

| SC-08 | 例外通道不可绕过双人 | 尝试单人单设备完成例外闭环，任一路径均被拒 |
| SC-09 | 离线不支持例外 | 端侧断网时发起例外申请被拒 |
| SC-10 | 操作日志无正文明文 | 抽查 `detail_json` 无姓名/手机号/证件号 |
| SC-11 | 完整姓名查看留痕 | 调用完整姓名接口后 `m20_nur_oper_log` 有对应记录 |
| SC-12 | 幂等键生效 | 同 `X-Idempotency-Key` 重复提交只产生一条记录 |
| SC-13 | 时钟异常不入给药时刻 | 偏差 >300 秒的记录不出现在给药时刻统计中 |
| SC-14 | 未绑定设备不可执行 | 新设备未信任前执行高危动作被拒或强制 MFA |
| SC-15 | 数据权限在 SQL 层过滤 | 断言查询 SQL 含参数化过滤条件，非应用层 `if` 过滤 |

## 附录 E：关键决策记录

| 编号 | 决策 | 选择 | 被放弃的选项及为什么不行 |
|---|---|---|---|
| D-01 | 扫码核对记录与执行记录分属两表 | M20 只存核对过程，执行结果落 M08 | 若 M20 也存执行结果，一个给药动作会有两个执行时刻、两个执行人，「已执行」状态会分叉，且两边都不报错 |
| D-02 | 核对闸门 fail-closed | 上游不可用一律不许继续 | 若 fail-open，闸门在系统抖动时等于不存在，而抖动恰恰是最需要它的时候 |
| D-03 | 条码破损走受控例外通道 | 第二人 + 第二设备 + 结构化原因 + 事后复核 | ①一律拦截不给通道：会催生借用他人设备绕行，绕行完全不留痕；②「强制通过」按钮：压力下会被条件反射点下去，且不产生任何可复盘信息 |
| D-04 | 例外单一次性 | `used_flag` 用完即废 | 若允许整班复用，一次例外会演变成整班的默认路径 |
| D-05 | 任务状态不自建 | 直接沿用 M08 六值 | 两套状态名必然出现「手机上完成、护士站待执行」 |
| D-06 | 任务列表不可返回空 | 降级必须显式 | 空列表等于告诉护士今天没活儿，会直接导致漏给药 |
| D-07 | 离线重放重新过闸门 | 回线后重新校验医嘱与任务 | 离线时扫过的码只能证明「那一刻拿对了药」，不能证明「现在医嘱还有效」 |
| D-08 | 离线冲突不自动解决 | 一律进人工处置队列 | 自动覆盖或自动丢弃都会让一条给药事实无声消失 |
| D-09 | 设备失败率拆两个比率 | 扫不出码 / 扫出来不符 分开统计 | 合并成一个数只能得出「设备不行」，而两者的处置动作完全不同（换设备 vs 查流程） |
| D-10 | 合规率不折不可判定 | `unmeasurable` 单列不进分母 | 折不按时会让科室背锅，折按时会让数据越烂比率越高 |
| D-11 | `data_quality` 自算不透传 | 按 M20-CALC-05 重算 | 透传上游值等于把上游口径冒充全系统口径，运维永远查不清谁慢 |
| D-12 | 关闭闸门需护理部审批 | 不给护士长该权限 | 护士长是最有动机关掉闸门、最没能力评估后果的角色 |
| D-13 | 交接班备忘不进病历 | 只进 M20 与待办 | 进病历会让口头交接的碎片被当成正式记录，反而降低记录质量 |
| D-14 | M08 执行接口按现状调用 | 以特殊客户端身份调工作站接口 | 臆造一个不存在的内部接口会在联调时直接崩，且把风险推给下游 |
