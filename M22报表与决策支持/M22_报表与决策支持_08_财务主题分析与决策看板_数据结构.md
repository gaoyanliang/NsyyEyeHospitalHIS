## 1. 表清单

> ### 本子模块建表边界（必读）
>
> **本子模块自建 10 张表**，全部使用 `m22_finance_` 与 `m22_dashboard_` 前缀。
>
> **不重复建表（引用 M22-03 权威定义）：**
>
> | 骨架表 | 定义方 | 本子模块用法 |
> |---|---|---|
> | `m22_report_template` | M22-03 | 财务主题报表模板通过 `template_code` 引用，不新建 |
> | `m22_report_instance` | M22-03 | 财务主题报表实例通过 `report_no` 引用，不新建 |
> | `m22_report_row` | M22-03 | 报表行数据读 M22-03，不落新表 |
> | `m22_report_subscription` | M22-03 | 报表订阅走 M22-03；本子模块的 `m22_dashboard_subscription` **只管看板订阅**，不重复报表订阅 |
>
> **不重复定义口径与事实：**
>
> | 对象 | 定义方 | 本子模块用法 |
> |---|---|---|
> | 指标口径 `m22_metric_def` | M22-01 | 通过 `metric_code` + `metric_version` 引用；**看板与预警不得自建口径** |
> | 指标事实 `m22_fact_metric` | M22-02 | 看板取数一律读指标事实；**不直查业务表** |
> | 目标值 | M22-01 | 预算与目标达成读 M22-01 目标值，本子模块只存「目标达成快照」 |
>
> **法定财务报表不重做：** 资产负债表、收入费用表、现金流量表由 M17-08 出；本子模块通过 `GET /internal/v1/m17/reports/{report_code}` 取数展示，**不落财务报表行数据**。

| 序号 | 表名 | 中文名 | 用途 | 预估行数 |
|---|---|---|---|---|
| 4.2 | `m22_dashboard_def` | 看板定义表 | 看板/大屏/移动端的配置主档（`dashboard_code` + 类型 + 版本） | 小 |
| 4.3 | `m22_dashboard_layout` | 看板布局表 | 组件的 JSONB 组件树、栅格、刷新策略、主题 | 中 |
| 4.4 | `m22_dashboard_snapshot` | 看板数据快照表 | 每个看板每期/每时刻的组件数据快照（含 `source_status` 溯源） | 大 |
| 4.5 | `m22_dashboard_subscription` | 看板订阅表 | 谁在什么周期以什么渠道接收哪个看板（只覆盖看板，不含报表订阅） | 小 |
| 4.6 | `m22_finance_topic` | 财务主题定义表 | 财务主题分析的主题分组与指标编排（收入/成本/结余/现金流四大主题） | 小 |
| 4.7 | `m22_finance_topic_data` | 财务主题数据表 | 主题内指标的事实快照（含同比环比、目标对比、来源溯源） | 大 |
| 4.8 | `m22_finance_target` | 预算与目标达成本地表 | 期间目标、实际、达成率快照（目标值引用 M22-01，本地只存达成结果） | 中 |
| 4.9 | `m22_finance_alert_rule` | 经营预警规则表 | 预警规则（指标 + 比较符 + 阈值 + 窗口 + 级别 + 抑制参数） | 小 |
| 4.10 | `m22_finance_alert` | 经营预警记录表 | 预警触发记录（含冷却抑制、升级计数、确认与关闭流程） | 中 |
| 4.11 | `m22_finance_export` | 看板与主题导出任务表 | 财务看板/主题分析/预警清单的导出任务与文件 | 小 |

**表数量：** 10 张

**量级假设（二级眼科医院）：**
- 科室约 20 个，院区 1 个，职工约 500 人。
- 看板：管理驾驶舱 1 套、科室看板 20 套、院长大屏 3 块（门诊大厅/住院部/行政区）、移动端看板 6 套，共约 **30 个 `dashboard_code`**；每个看板每年约 4 个版本，年增 **120 行**。
- 看板快照：30 个看板 × 每日 1 次 × 365 天 ≈ **10,950 行/年**；大屏 3 块 × 每日 288 次（5 分钟粒度不落快照，只落小时级 24 次）× 365 ≈ **26,280 行/年**；合计约 **3.7 万行/年**，10 年约 37 万行。
- 财务主题数据：4 大主题 × 约 25 指标 × 12 月 × 20 科室 ≈ **24,000 行/年**，10 年约 24 万行。
- 目标达成：20 科室 × 25 指标 × 12 月 = **6,000 行/年**，10 年约 6 万行。
- 预警规则：约 **60 条**（收入类 15、成本类 12、结余类 10、现金流类 8、运营质量类 15）。
- 预警记录：日均触发约 8 条（经冷却抑制后），年约 **3,000 行**，10 年约 3 万行。
- 导出任务：月均 40 次，年约 **480 行**。

**全局设计约定：**

| 约定 | 内容 |
|---|---|
| 主键 | `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| 时间戳 | `TIMESTAMP`（不用 `TIMESTAMPTZ`，全系统统一东八区） |
| 日期 | `DATE` |
| 统计期间 | `VARCHAR(7)`，格式 `YYYY-MM`；日粒度用 `DATE` |
| **指标值** | **`NUMERIC(20,6)`**，6 位小数（比率与金额都够用） |
| **金额类指标** | **`NUMERIC(18,2)`**，2 位小数 |
| **比率/百分比** | **`NUMERIC(9,6)`**，如 `0.297297` 表示 29.7297% |
| 目标值 | `NUMERIC(20,6)` |
| 数量/人次 | `BIGINT` |
| **禁止类型** | **`FLOAT` / `DOUBLE PRECISION` / `REAL` 一律禁止**，指标值差一分钱都会被质疑 |
| 枚举 | `VARCHAR(32)` + `CHECK` 约束，**不建 PostgreSQL ENUM 类型** |
| 逻辑删除 | `is_deleted BOOLEAN NOT NULL DEFAULT FALSE`（快照表与流水表为只增，不含该字段） |
| 物理外键 | **不建**，由应用层与每日 02:40 一致性任务保证 |
| 索引 | 部分索引 `WHERE is_deleted = FALSE` 必备 |
| 分区 | 快照表与主题数据表按 `period` 月分区，**必须有 `DEFAULT` 分区** |
| 约束命名 | `ck_{表名去前缀}_{语义}` |
| 索引命名 | `idx_{表名}_{字段}` / `uk_{表名}_{语义}` |

> **四条溯源字段（快照类表必备）：** 任何落库的指标快照都必须能回答「这个数是哪来的」——必须有 `source_module`、`source_api`、`collect_batch_no`、`source_status`。这是 M22 共享规范第 4.x 节第 9 条硬要求。

### 4.2 表：`m22_dashboard_def`（看板定义表）

**用途：** 看板/大屏/移动端看板的**配置主档**。一个 `dashboard_code` 代表「一块看板」，`dashboard_type` 区分它长在哪、怎么刷新、怎么缓存。

> **为什么大屏不是「驾驶舱放大版」：** 院长大屏（`SCREEN`）与管理驾驶舱（`DASHBOARD`）在六件事上完全不同——刷新频率（60s vs 300s）、缓存 TTL（60s vs 300s）、字体尺寸策略（远距离阅读，最小字号 28px vs 桌面 12px）、主题（强制深色 vs 亮/暗可选）、交互（无交互、不支持下钻 vs 全交互）、投放方式（固定大屏机 vs 个人 PC）。把它们做成一套配置会导致「驾驶舱改个配色，大屏跟着花」和「大屏 5 秒一刷，把 Redis 打穿」。因此用 `dashboard_type` 在配置层就分开，并在布局与缓存策略上分道。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | N | IDENTITY | 主键 |
| `dashboard_code` | VARCHAR(64) | N | — | 看板编码，见 8.1 编码规则；与 `dashboard_type` 联合唯一 |
| `dashboard_name` | VARCHAR(128) | N | — | 看板名称 |
| `dashboard_type` | VARCHAR(16) | N | — | `DASHBOARD` 驾驶舱 / `SCREEN` 大屏 / `MOBILE` 移动端 |
| `status` | VARCHAR(16) | N | `DRAFT` | `DRAFT` / `ACTIVE` / `INACTIVE` / `ARCHIVED` |
| `scope_type` | VARCHAR(16) | N | `HOSPITAL` | 数据范围：`HOSPITAL` 全院 / `DEPT` 科室 / `PERSONAL` 个人 |
| `scope_dept_id` | BIGINT | Y | NULL | `scope_type=DEPT` 时的科室 ID（引用 `mdm_dept`） |
| `owner_id` | BIGINT | Y | NULL | 看板负责人（引用 `mdm_staff`） |
| `owner_name` | VARCHAR(64) | Y | NULL | 负责人姓名快照 |
| `default_period_type` | VARCHAR(16) | N | `MONTH` | 默认期间粒度：`DAY` / `WEEK` / `MONTH` / `QUARTER` / `YEAR` |
| `default_period` | VARCHAR(7) | Y | NULL | 默认展示期间，空表示取最新 |
| `refresh_mode` | VARCHAR(16) | N | — | 刷新模式：`INTERVAL` 定时间隔 / `SCHEDULE` 定时点 / `ON_DEMAND` 按需 / `MANUAL` 手工 |
| `refresh_interval_sec` | INTEGER | Y | NULL | `refresh_mode=INTERVAL` 时的刷新间隔秒数（`SCREEN` 必须 ≤ 300） |
| `cache_ttl_sec` | INTEGER | N | — | 看板级缓存 TTL（秒），按 `dashboard_type` 有硬上限，见 8.5 计算规则 |
| `theme_mode` | VARCHAR(16) | N | `LIGHT` | 主题：`LIGHT` 亮色 / `DARK` 深色 / `AUTO` 跟随系统；`SCREEN` 强制 `DARK` |
| `min_font_size_px` | SMALLINT | N | 12 | 最小字号（像素）；`SCREEN` 必须 ≥ 28 |
| `interactive_enabled` | BOOLEAN | N | TRUE | 是否允许交互（下钻、筛选、跳转）；`SCREEN` 必须 FALSE |
| `drill_enabled` | BOOLEAN | N | TRUE | 是否允许下钻到业务模块；`SCREEN` 必须 FALSE |
| `sensitive_mask_enabled` | BOOLEAN | N | TRUE | 是否对敏感指标脱敏（非授权角色看模糊值） |
| `warmup_enabled` | BOOLEAN | N | FALSE | 是否后台主动预热缓存；`SCREEN` 必须 TRUE |
| `warmup_lead_sec` | INTEGER | Y | NULL | 预热提前量（秒），`SCREEN` 默认 10，必须小于 `refresh_interval_sec` |
| `sort_no` | SMALLINT | N | 0 | 看板列表排序 |
| `remark` | VARCHAR(500) | Y | NULL | 备注 |
| `version_lock` | INTEGER | N | 0 | 乐观锁版本号（与业务 `version` 区分，避免混淆） |
| `created_by` | BIGINT | N | — | 创建人 ID |
| `created_by_name` | VARCHAR(64) | N | — | 创建人姓名快照 |
| `created_at` | TIMESTAMP | N | `CURRENT_TIMESTAMP` | 创建时间 |
| `updated_at` | TIMESTAMP | N | `CURRENT_TIMESTAMP` | 更新时间（触发器维护） |
| `is_deleted` | BOOLEAN | N | FALSE | 逻辑删除标记 |

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m22_dashboard_def` | PRIMARY KEY | `id` | — |
| `uk_m22_dashboard_def_code` | UNIQUE | `(dashboard_code, dashboard_type)` WHERE `is_deleted = FALSE` | 编码 + 类型唯一 |

### 4.3 表：`m22_dashboard_layout`（看板布局表）

**用途：** 存看板的**布局与组件树**。组件树用 JSONB 存，因为看板布局天然是嵌套结构（行 → 列 → 组件 → 子组件），且不同 `dashboard_type` 的组件类型差异大。每个看板可有多版本布局，同时刻只有一版 `ACTIVE`。

> **为什么布局与定义分表：** 定义的变更（改名、改负责人）很频繁但很轻；布局的变更（加组件、调栅格）很重，且**必须可回滚**——院长大屏改成新版如果显示错乱，要能一键退回上一版。分表后布局天然带版本链，回滚只是把旧版本置 `ACTIVE`。

### 4.4 表：`m22_dashboard_snapshot`（看板数据快照表）

**用途：** 存**每一块看板在某一时刻的完整数据快照**。这是看板性能的核心——P-09 要求 P95 ≤ 500ms，靠的不是每次实时查指标，而是读这里已算好的快照 + Redis 缓存。

> **为什么不直接查指标事实表：** 管理驾驶舱一屏约 20 个组件，每个组件背后是 1~8 个指标，还有同比、环比、目标值。实时算一遍要 20 次 × 3 期 = 60 次指标查询，实测 2~4 秒。落成快照后单次查询是一次主键/唯一键命中，约 8ms。驾驶舱打开速度从「转圈 3 秒」变成「秒开」。

> **只增不改：** 快照是历史事实的记录，生成后不再修改（除 `source_status` 的降级标注与 `is_valid` 失效标记）。不含 `is_deleted`，只允许插新快照。

### 4.5 表：`m22_dashboard_subscription`（看板订阅表）

**用途：** 管理**看板**的订阅推送（谁、什么周期、什么渠道、收哪块看板）。**不覆盖报表订阅**——报表订阅走 M22-03 的 `m22_report_subscription`。

> **为什么看板订阅要独立建表：** 报表订阅是「发一份 Excel/PDF 到你邮箱」，看板订阅是「每天 8:00 把驾驶舱截图推到你微信」——载荷不同（截图 vs 文件）、失败语义不同（截图渲染失败可重试 3 次；文件生成失败要重新生成报表）、时效要求不同（看板推送要求 5 分钟内送达，报表可等）。共用一张表会让两边的字段互相污染。通过 `template_code` 与 `report_no` 两张表都不引用对方，边界干净。

### 4.6 表：`m22_finance_topic`（财务主题定义表）

**用途：** 定义**财务主题分析的分组结构**。四大主题（收入 / 成本 / 结余 / 现金流）下挂哪些指标、什么粒度、按什么顺序展示、谁可见。这是 P03「财务主题分析」的配置源。

> **为什么不直接把指标硬编码在页面里：** 财务主题的分析口径会随管理重点变化——今年重点是「药占比与耗占比」，明年可能变成「人均结余」。硬编码意味着每换一次分析重点就要发一次版。改用主题配置后，财务主管自己在 P08「数据字典与口径说明」页调整 `metric_codes`，刷新即生效。

### 4.7 表：`m22_finance_topic_data`（财务主题数据表）

**用途：** 存财务主题下每个指标每期的**实际值、同比环比、目标对比**。这是 P03 财务主题分析与 P04 成本收益分析的数据底座。

> **只增不改 + 口径版本：** 每条记录带 `metric_version`，记录「这个数是用哪一版口径算出来的」。口径变更后产生新版本记录，**历史记录永不按新口径回溯重算**（M22 专属铁律第 5 条）。这是财务与等级评审审计的硬要求——去年的报表必须能用去年的口径复现。

> **不重算业务统计：** 本表所有 `actual_value` 一律来自 M22-02 指标事实（`m22_fact_metric`），本表只做「取数 → 计算同比环比 → 与目标比对 → 落快照」。本表不含任何跨模块直查业务表的逻辑。

### 4.8 表：`m22_finance_target`（预算与目标达成本地表）

### 4.9 表：`m22_finance_alert_rule`（经营预警规则表）

**用途：** 定义**经营预警的触发条件**。一条规则 = 指标 + 比较符 + 阈值 + 窗口 + 级别 + 抑制参数。这是预警系统「会不会被信任」的根源——规则配得好，预警是帮手；配得差，每天刷 200 条，院长直接关掉不看。

> **反抖动三重设计（本表核心）：**
>
> | 机制 | 字段 | 默认值 | 解决什么问题 |
> |---|---|---|---|
> | **冷却期** | `cooldown_hours` | **24 小时** | 同一条规则同一个对象，24 小时内只触发一次。避免「某科室收入降 30%」这条规则在一天内被扫描 24 次、触发 24 次 |
> | **升级阈值** | `escalate_times` | **3 次** | 连续 3 次触发（跨冷却期，即连续 3 天）才升级为 `CRITICAL`。避免单日波动（如周末、节假日、单日促销结束）被误判为严重问题 |
> | **确认抑制** | `suppress_on_ack` | TRUE | 已确认的预警在其生命周期内不再重复通知，只累加 `suppress_count`。避免「我已经知道了，还在给我发」 |
>
> 这三条合起来的效果：一条真正的趋势性问题（连续下跌）会在第 1 天 `WARN`、第 2 天继续 `WARN`（不升级）、第 3 天升级 `CRITICAL`；而一次单日波动只会在第 1 天报一次 `WARN`，第二天恢复正常就不再有下文。院长看到的每一条 `CRITICAL` 都值得点开看。

### 4.10 表：`m22_finance_alert`（经营预警记录表）

**用途：** 记录**每一次预警触发的事实**，承载冷却抑制、级别升级、确认、关闭的完整生命周期。

> **只增不改（除生命周期字段）：** 预警记录是「系统当时确实报了警」的证据。业务字段（`trigger_value`、`threshold_value`、`alert_level`、`triggered_at`）一经写入不得修改；只有状态流转字段（`status`、`acknowledged_*`、`resolved_*`）允许更新。为此本表**不提供 `is_deleted`**，并提供表级 `REVOKE DELETE`。

> **反抖动如何落在这张表上：**
> 1. 扫描器发现规则命中 → 先查本表「同一条 `rule_id` + `object_type` + `object_id` 且 `triggered_at > NOW() - cooldown_hours`」是否存在记录；
> 2. 存在 → **不再插入新记录**，只把已有记录的 `suppress_count` 加 1；
> 3. 不存在 → 插入新记录，`status = 'OPEN'`，`escalate_count = 1`；
> 4. 每次新插入前，统计「同一对象在最近 `escalate_times × cooldown_hours` 内已触发次数」，达到 `escalate_times` 则本次直接以 `escalate_level`（`CRITICAL`）落库。
>
> 这套机制让「单日波动」只留 1 条记录、「持续恶化」在第 3 天变成 `CRITICAL`，而 `suppress_count` 让运维能看到「这条预警被压了多少次」，不丢信息。

**模型层设计要点**

| 序号 | 要点 | 说明 |
|---|---|---|
| 1 | **三类看板差异用 CHECK 而非代码** | SCREEN 的字体 ≥28px、深色主题、禁交互、TTL=60 全部写进数据库约束。代码可以绕过，DDL 绕不过 |
| 2 | **分区表复合主键** | `M22DashboardSnapshot.id` 与 `snapshot_date` 同为 `primary_key=True`，因为 PostgreSQL 要求分区表主键包含分区键 |
| 3 | **溯源四字段 NOT NULL** | 四个模型都声明为 `nullable=False`，写快照时若忘了传来源，插入直接失败 |
| 4 | **JSONB 用 list/dict 默认值** | `default=list` / `default=dict` 而非 `default=[]`，避免可变对象共享 |
| 5 | **PARTIAL 强制带缺失来源** | 三条 `ck_*_missing` 约束把「上游不可用不填 0」落成物理约束 |
| 6 | **目标值来源锁死 M22-01** | `ck_m22_finance_target_source` 保证本表不会成为第二份目标值真相 |
| 7 | **升级逻辑自洽** | `ck_m22_finance_alert_escalate` 保证 `is_escalated=TRUE` 时必然 `escalate_count>=2` 且级别真的变了 |
| 8 | **人工关闭必须写字数** | `ck_m22_finance_alert_manual_note` 要求 ≥10 字，杜绝「敷衍关闭」 |

**Schema 设计要点**

| 序号 | 要点 | 说明 |
|---|---|---|
| 1 | **金额/比率一律 `Decimal`，绝不 `float`** | 金融与考核数据用 float 会累积二进制误差，0.1+0.2 != 0.3 在报表上就是「差一分钱」，必须用 Decimal |
| 2 | **`Optional[...] = None` 承载「无数据」语义** | `value`、`achieve_rate`、`compare_rate` 允许为 null，前端渲染为 `—`；这是「上游不可用绝不填 0」在 API 层的体现 |
| 3 | **三类看板差异在 Create 时前置校验** | `DashboardDefCreate.check_type_rules` 把 SCREEN 的字体/主题/TTL/无交互四条规则提前拦住，报错信息直白说明原因（如「3 米外可读」），比让 DDL 抛约束名友好得多 |
| 4 | **DDL CHECK 依然保留** | Schema 可被绕过（脚本、直连、其他服务），DDL 是最后防线。两层校验不是冗余 |
| 5 | **`AlertRuleCreate` 强制升级方向** | `check_escalate_higher` 保证 `escalate_level > alert_level`，防止配出「升级到 INFO」这种无意义规则 |
| 6 | **`AlertResolveIn` 强制 ≥10 字说明** | 与 `ck_m22_finance_alert_manual_note` 双保险，杜绝「点一下关掉」式敷衍处置 |
| 7 | **`AlertListOut` 带按级别统计** | P-10 供 M20 与 M03-05 调用，返回 `counts_by_level` 让调用方不必再查一次就能显示角标 |
| 8 | **`DashboardDataOut` 带 `missing_sources`** | PARTIAL 时前端不仅要显示「数据不完整」，还要能说出「缺 M16-09 日结」，否则用户只会质疑系统 |
| 9 | **`cache_ttl_sec` 随响应返回** | 缓存 TTL 是看板自身属性（SCREEN 60s / DASHBOARD 300s / MOBILE 120s），由服务端下发给前端与网关，避免两端各写一套常量而逐渐漂移 |
| 10 | **`MetricDefOut` 双键 `metric_code` + `version`** | 口径变更不覆盖历史，同一指标多版本并存，`is_current` 标记当前生效版本 |
| 11 | **查询入参 `pattern` 校验期间格式** | `^\d{4}-\d{2}$` 在 API 边界拦住 `2026-13` 这类脏参数，避免打到数据库才发现 |

### B.1 看板类型（`dashboard_type`，3 类）

| 代码 | 中文 | 使用方 | 关键差异化参数 |
|---|---|---|---|
| `DASHBOARD` | 管理驾驶舱 | PC 端 P01 | 刷新 ≤1800s、缓存 TTL ≤300s、可交互可下钻 |

## 附录 C：关键索引与查询

### C.1 Redis 缓存 TTL 分级（本子模块核心设计）

| 缓存对象 | Redis Key 模式 | TTL | 预热策略 | 设计理由 |
|---|---|---|---|---|
| 看板数据（SCREEN） | `m22:dashboard:data:{code}:v{ver}` | **60s** | **后台每 60s 主动预热** | 大屏是常驻展示，用户不会主动刷新。若等过期后首次访问再算，大屏会出现 1~3 秒空白。预热让缓存永不失温，TTL 只为保证数据新鲜度 |
| 看板数据（DASHBOARD） | `m22:dashboard:data:{code}:v{ver}` | **300s** | 按需（访问时回填） | 驾驶舱是主动打开查看，5 分钟新鲜度足够；打开时若缓存过期，回填一次快照查询约 8ms，用户无感 |
| 看板数据（MOBILE，P-09） | `m22:dashboard:data:{code}:v{ver}` | **120s** | 按需 | 移动端弱网，长 TTL 降低流量与等待；但契约要求 P95 ≤ 500ms，120s 既保证新鲜也保证命中率 |
| 看板布局 | `m22:dashboard:layout:{code}:v{ver}` | **3600s** | 发布时主动写入 | 布局几乎不变，只有在 P01 发布新版本时才失效 |
| 预警列表（P-10） | **不缓存** | **0（不缓存）** | — | **预警必须实时**。用户点开预警中心时，若看到的是 5 分钟前的列表，可能就错过了刚触发的一条 `CRITICAL`。P95 ≤ 200ms 靠部分索引 `idx_m22_finance_alert_pending` 保证，不靠缓存 |
| 预警计数角标 | `m22:dashboard:alert-count` | **10s** | — | 角标允许 10 秒延迟（用户能接受），但绝不能缓存 5 分钟（否则刚处理完的预警角标一直不变） |
| 财务主题数据 | `m22:dashboard:topic:{code}:{period}` | **600s** | 按需 | 主题分析是翻阅历史，10 分钟新鲜度足够 |
| 指标口径 | `m22:dashboard:metric-def:{code}:v{ver}` | **86400s** | 口径变更时主动失效 | 口径变更走审批，变更频率极低（月级） |
| 看板定义 | `m22:dashboard:def:{code}:v{ver}` | **1800s** | 按需 | 配置类 |

**TTL 为什么这么定（统一理由）：**

1. **大屏 60s 而非实时**：实时意味着每次刷新都要算，一台大屏 5 秒刷一次，一天 17,280 次计算，纯浪费。60s 的 TTL 配 60s 预热，等于「数据最多滞后 1 分钟」，对经营大屏完全够用，计算量降到 1,440 次/天。
2. **预警不缓存**：这是唯一一个「宁可慢也要准」的场景。预警的价值在于「及时发现问题」，缓存 5 分钟可能让 `CRITICAL` 晚 5 分钟被看到。用部分索引 + 覆盖索引把查询压到 20ms 内，比缓存更可靠。
3. **移动端 120s 折中**：太长（如 300s）则用户看到的是 5 分钟前的数；太短（如 30s）则弱网下频繁穿透，既慢又费流量。120s 是「新鲜度可接受 + 命中率 > 90%」的平衡点。
4. **配置类 1800s+ 主动失效**：配置几乎不变，靠「变更时主动删 key」比靠 TTL 更准确。

**缓存失效规则**

| 触发事件 | 失效的 Key | 说明 |
|---|---|---|
| 看板布局发布 | `m22:dashboard:layout:{code}:*` | 布局变了，旧缓存必须清 |
| 看板定义更新 | `m22:dashboard:def:{code}:*` | 参数变了（如 TTL），需重新下发 |
| 指标口径变更审批通过 | `m22:dashboard:metric-def:{code}:*` | 口径变了，展示说明要跟着变 |
| 快照生成完成 | `m22:dashboard:data:{code}:*` | 有新快照，旧缓存可清 |
| 预警触发 | `m22:dashboard:alert-count` | 角标数字要变 |
| 预警确认/关闭 | `m22:dashboard:alert-count` | 同上 |

### C.3 核心查询 SQL

**① P-09 取看板最新快照（P95 ≤ 500ms 的主力查询）**

```sql
SELECT dashboard_code, dashboard_name, dashboard_type, layout_version,
       period_type, period, scope_type, scope_dept_id,
       components_data, component_count, source_status, missing_sources,
       snapshot_at, cache_ttl_sec
FROM m22_dashboard_snapshot
WHERE dashboard_code = :dashboard_code
  AND snapshot_date = :snapshot_date
  AND period_type = :period_type
  AND period = :period
  AND source_status <> 'FAILED'
  AND is_valid = TRUE
ORDER BY snapshot_at DESC
LIMIT 1;
```

**② P-10 取未处理预警（走部分索引，P95 ≤ 200ms）**

```sql
SELECT alert_no, rule_code, rule_name, alert_level, base_level,
       object_type, object_id, object_name,
       trigger_value, threshold_value, deviation_rate,
       escalate_count, is_escalated, trigger_desc, status, triggered_at
FROM m22_finance_alert
WHERE status IN ('OPEN', 'ACKNOWLEDGED')
  AND (:alert_level IS NULL OR alert_level = :alert_level)
  AND (:object_type IS NULL OR object_type = :object_type)
ORDER BY
    CASE alert_level WHEN 'CRITICAL' THEN 1 WHEN 'WARN' THEN 2 ELSE 3 END,
    triggered_at DESC
LIMIT :limit;
```

**③ 冷却判定（反抖动核心查询）**

```sql
-- 查询同一规则同一对象在冷却期内是否已有预警
SELECT id, alert_no, alert_level, escalate_count, triggered_at
FROM m22_finance_alert
WHERE rule_id = :rule_id
  AND object_type = :object_type
  AND COALESCE(object_id, 0) = COALESCE(:object_id, 0)
  AND triggered_at > :now - make_interval(hours => :cooldown_hours)
ORDER BY triggered_at DESC
LIMIT 1;
```

> **注意 `COALESCE(object_id, 0)`：** 全院级预警的 `object_id` 是 NULL，而 SQL 里 `NULL = NULL` 不成立。若直接写 `object_id = :object_id`，全院级预警的冷却判定永远查不到历史记录，就会每条都重复触发。用 `COALESCE` 统一成 0 才能正确匹配。

**④ 升级计数（判断本次是否应升级为 CRITICAL）**

```sql
SELECT COUNT(*) AS recent_count
FROM m22_finance_alert
WHERE rule_id = :rule_id
  AND object_type = :object_type
  AND COALESCE(object_id, 0) = COALESCE(:object_id, 0)
  AND triggered_at > :now - make_interval(hours => :escalate_window_hours);
```

**⑤ 财务主题趋势（P03 多指标多月对比）**

```sql
SELECT metric_code, metric_name, period,
       actual_value, prev_value, mom_rate,
       last_year_value, yoy_rate,
       target_value, achieve_rate, target_status,
       source_status
FROM m22_finance_topic_data
WHERE topic_code = :topic_code
  AND period BETWEEN :period_start AND :period_end
  AND granularity = :granularity
  AND (:dept_id IS NULL OR dept_id = :dept_id)
  AND metric_code = ANY(:metric_codes)
ORDER BY metric_code, period;
```

**⑥ 科室目标达成排名（P05）**

```sql
SELECT t.dept_id, t.dept_name, t.metric_code, t.metric_name,
       t.target_value, t.actual_value, t.achieve_rate, t.target_status,
       RANK() OVER (PARTITION BY t.metric_code ORDER BY t.achieve_rate DESC NULLS LAST) AS rank_no
FROM m22_finance_target t
WHERE t.period = :period
  AND t.granularity = :granularity
  AND t.metric_code = :metric_code
  AND t.dept_id IS NOT NULL
  AND t.achieve_rate IS NOT NULL
ORDER BY rank_no;
```

**⑦ 预警统计（P06 预警看板）**

```sql
SELECT rule_group, alert_level, status,
       COUNT(*) AS alert_count,
       COUNT(DISTINCT object_id) AS object_count,
       ROUND(AVG(EXTRACT(EPOCH FROM (COALESCE(resolved_at, CURRENT_TIMESTAMP) - triggered_at)) / 3600), 2)
           AS avg_handle_hours
FROM m22_finance_alert
WHERE triggered_at >= :start_at
  AND triggered_at < :end_at
GROUP BY rule_group, alert_level, status
ORDER BY rule_group, alert_level, status;
```

**⑧ 数据完整性巡检（哪些快照是 PARTIAL）**

```sql
SELECT snapshot_date, dashboard_code, source_status, missing_sources,
       snapshot_at, calc_duration_ms
FROM m22_dashboard_snapshot
WHERE snapshot_date >= CURRENT_DATE - 7
  AND source_status <> 'COMPLETE'
ORDER BY snapshot_date DESC, dashboard_code;
```

**⑨ 冷却抑制效果统计（评估反抖动是否有效）**

```sql
SELECT r.rule_code, r.rule_name,
       COUNT(a.id)                AS alert_count,
       SUM(a.suppress_count)      AS suppressed_total,
       ROUND(AVG(a.suppress_count), 2) AS avg_suppressed,
       SUM(CASE WHEN a.is_escalated THEN 1 ELSE 0 END) AS escalated_count
FROM m22_finance_alert a
JOIN m22_finance_alert_rule r ON r.id = a.rule_id
WHERE a.triggered_at >= :start_at
GROUP BY r.rule_code, r.rule_name
ORDER BY suppressed_total DESC;
```

> **第 ⑨ 条查询的用途：** 如果某条规则 `suppressed_total` 极高（比如一天被压 200 次），说明阈值配得太敏感，规则本身需要调整；如果 `suppressed_total` 接近 0 但 `alert_count` 也很低，说明规则配得合适。这是「预警系统是否被信任」的量化指标。

### C.4 索引体积与收益测算

| 索引 | 表 10 年行数 | 覆盖行数 | 体积 | 查询耗时对比 |

### E.3 迁移脚本示例（分区表 + REVOKE DELETE）

```python
"""M22-08 看板数据快照表建表迁移（按月分区 + DEFAULT 分区）。"""

from alembic import op

revision = "20261115_m22_08_006"
down_revision = "20261115_m22_08_005"


def upgrade() -> None:
    """建看板快照表：按月分区，带 DEFAULT 兜底分区。"""
    op.execute("""
        CREATE TABLE IF NOT EXISTS m22_dashboard_snapshot (
            id                  BIGINT GENERATED BY DEFAULT AS IDENTITY,
            dashboard_def_id    BIGINT       NOT NULL,
            dashboard_code      VARCHAR(64)  NOT NULL,
            dashboard_type      VARCHAR(16)  NOT NULL,
            layout_version      SMALLINT     NOT NULL,
            snapshot_date       DATE         NOT NULL,
            snapshot_at         TIMESTAMP    NOT NULL,
            period_type         VARCHAR(16)  NOT NULL,
            period              VARCHAR(7)   NOT NULL,
            scope_type          VARCHAR(16)  NOT NULL,
            scope_dept_id       BIGINT,
            components_data     JSONB        NOT NULL DEFAULT '[]'::jsonb,
            component_count     SMALLINT     NOT NULL DEFAULT 0,
            metric_count        SMALLINT     NOT NULL DEFAULT 0,
            payload_bytes       INTEGER      NOT NULL DEFAULT 0,
            source_status       VARCHAR(16)  NOT NULL,
            missing_sources     JSONB        NOT NULL DEFAULT '[]'::jsonb,
            source_module       VARCHAR(32)  NOT NULL,
            source_api          VARCHAR(256) NOT NULL,
            collect_batch_no    VARCHAR(32)  NOT NULL,
            source_period_start DATE,
            source_period_end   DATE,
            calc_duration_ms    INTEGER,
            is_valid            BOOLEAN      NOT NULL DEFAULT TRUE,
            invalid_reason      VARCHAR(256),
            trace_id            VARCHAR(32),
            created_at          TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
            PRIMARY KEY (id, snapshot_date)
        ) PARTITION BY RANGE (snapshot_date);
    """)

    # DEFAULT 分区：任何未预建月份的快照都落到这里，保证写入永不失败
    op.execute("""
        CREATE TABLE IF NOT EXISTS m22_dashboard_snapshot_default
            PARTITION OF m22_dashboard_snapshot DEFAULT;
    """)

    op.execute("""
        ALTER TABLE m22_dashboard_snapshot
            ADD CONSTRAINT ck_m22_dashboard_snapshot_source_status
            CHECK (source_status IN ('COMPLETE', 'PARTIAL', 'FAILED', 'STALE'));
    """)
    op.execute("""
        ALTER TABLE m22_dashboard_snapshot
            ADD CONSTRAINT ck_m22_dashboard_snapshot_type
            CHECK (dashboard_type IN ('DASHBOARD', 'SCREEN', 'MOBILE'));
    """)
    # 上游不可用绝不静默填 0：PARTIAL/FAILED 必须列出缺失来源
    op.execute("""
        ALTER TABLE m22_dashboard_snapshot
            ADD CONSTRAINT ck_m22_dashboard_snapshot_missing
            CHECK (source_status = 'COMPLETE'
                   OR jsonb_array_length(missing_sources) > 0);
    """)
    op.execute("""
        ALTER TABLE m22_dashboard_snapshot
            ADD CONSTRAINT ck_m22_dashboard_snapshot_complete
            CHECK (source_status <> 'COMPLETE'
                   OR jsonb_array_length(missing_sources) = 0);
    """)
    op.execute("""
        ALTER TABLE m22_dashboard_snapshot
            ADD CONSTRAINT ck_m22_dashboard_snapshot_at
            CHECK (CAST(snapshot_at AS DATE) = snapshot_date);
    """)
    op.execute("""
        ALTER TABLE m22_dashboard_snapshot
            ADD CONSTRAINT ck_m22_dashboard_snapshot_invalid
            CHECK (is_valid = TRUE OR invalid_reason IS NOT NULL);
    """)
    op.execute("""
        ALTER TABLE m22_dashboard_snapshot
            ADD CONSTRAINT ck_m22_dashboard_snapshot_components
            CHECK (jsonb_typeof(components_data) = 'array');
    """)
    op.execute("""
        ALTER TABLE m22_dashboard_snapshot
            ADD CONSTRAINT ck_m22_dashboard_snapshot_trace
            CHECK (char_length(source_module) > 0
                   AND char_length(source_api) > 0
                   AND char_length(collect_batch_no) > 0);
    """)

    op.execute("""
        CREATE UNIQUE INDEX uk_m22_dashboard_snapshot_key
            ON m22_dashboard_snapshot
               (dashboard_def_id, snapshot_date, period, period_type,
                scope_type, scope_dept_id);
    """)
    op.execute("""
        CREATE INDEX idx_m22_dashboard_snapshot_latest
            ON m22_dashboard_snapshot
               (dashboard_code, snapshot_date DESC, snapshot_at DESC);
    """)
    op.execute("""
        CREATE INDEX idx_m22_dashboard_snapshot_type
            ON m22_dashboard_snapshot (dashboard_type, snapshot_date DESC);
    """)
    op.execute("""
        CREATE INDEX idx_m22_dashboard_snapshot_partial
            ON m22_dashboard_snapshot (snapshot_date, source_status)
            WHERE source_status <> 'COMPLETE';
    """)


def downgrade() -> None:
    """回滚：分区表连同 DEFAULT 分区一起删除。"""
    op.execute("DROP TABLE IF EXISTS m22_dashboard_snapshot_default CASCADE;")
    op.execute("DROP TABLE IF EXISTS m22_dashboard_snapshot CASCADE;")
```

```python
"""M22-08 经营预警记录表建表迁移（只增不改，禁止 DELETE）。"""

from alembic import op

revision = "20261115_m22_08_010"
down_revision = "20261115_m22_08_009"


def upgrade() -> None:
    """建预警记录表并收回删除权限。"""
    op.execute("""
        ALTER TABLE m22_finance_alert
            ADD CONSTRAINT ck_m22_finance_alert_escalate
            CHECK (is_escalated = FALSE
                   OR (escalate_count >= 2 AND alert_level <> base_level));
    """)
    op.execute("""
        ALTER TABLE m22_finance_alert
            ADD CONSTRAINT ck_m22_finance_alert_manual_note
            CHECK (resolve_type IS DISTINCT FROM 'MANUAL'
                   OR (resolve_note IS NOT NULL
                       AND char_length(resolve_note) >= 10));
    """)
    # 预警记录是「系统报过警」的证据，禁止删除
    op.execute("REVOKE DELETE ON m22_finance_alert FROM app_user;")


def downgrade() -> None:
    """回滚：先恢复权限。"""
    op.execute("GRANT DELETE ON m22_finance_alert TO app_user;")
```
