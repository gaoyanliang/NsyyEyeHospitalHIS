## 文档说明

本文件是 M22-07 临床质量与绩效指标的**数据结构唯一依据**，包含详细设计文档第 4 章的全部内容。

**定位一句话：** M22-07 是全院**临床质量与绩效口径的落地层**——它把「国家三级公立医院绩效考核指标」「二级综合医院评审标准指标」「护理质量指标」「院感与安全指标」这套**外部标准**，翻译成本院可采集、可核对、可追溯的**指标值记录**，并输出一份**只有指标值与权重、绝无金额**的绩效指标池给 M17-07 算钱。

**本子模块数据结构的三个「必须能回答」：**

| # | 必须能回答 | 靠哪些字段/表 |
|---|---|---|
| 1 | **这个指标值是哪来的** | `m22_clinical_metric_fact` 的 `source_module` / `source_api` / `collect_batch_no` / `source_status` 四个溯源字段 + `m22_clinical_collect_task` |
| 2 | **这个数算不算达标** | `m22_clinical_quality.indicator_value` 与 `target_value` / `warn_threshold` / `alert_threshold` 三阈值对比，`achieve_status` 五态 |
| 3 | **院的绩效指标池里有没有钱** | **没有任何金额字段**。`m22_clinical_perf_pool` 只有指标值、权重、得分，绩效金额由 M17-07 按 P-10 计算 |

## 七条与数据结构强相关的铁律（违反即返工）

| # | 铁律 | 在数据结构上的体现 |
|---|---|---|
| 1 | **指标值必须可溯源** | `m22_clinical_metric_fact` 必备 `source_module`、`source_api`、`collect_batch_no`、`source_status`、`collected_at`、`metric_code` 六个溯源字段，缺一不可 |
| 2 | **指标值禁浮点** | 所有 `value` / `rate` / `ratio` / `score` / `target` / `actual` 类字段一律 `NUMERIC(20,6)`；比率类用 `NUMERIC(9,6)`；**绝不用 `FLOAT` / `DOUBLE` / `REAL`** |
| 3 | **分母为 0 绝不给 0** | 所有比率指标行必须满足 `ck_..._ratio_denominator`：`(denominator > 0 AND ratio_value IS NOT NULL) OR (denominator = 0 AND ratio_value IS NULL)`。数据库层杜绝「0/0 存成 0」，让页面能明确区分「未发生」与「发生了但很差」 |
| 4 | **历史不重算** | 指标值一经 `PUBLISHED` 不可改写，口径变更走 `m22_clinical_review_std` 版本与 `m22_metric_def` 新版本；已往期间保留当时的 `calc_version` |
| 5 | **绩效池不含钱** | `m22_clinical_perf_pool` 及全部 `m22_clinical_*` 表**没有任何金额字段**。金额由 M17-07 `m17_perf_result` 唯一持有；M22 只通过 P-10 读展示 |
| 6 | **评审指标挂版本** | `m22_clinical_review_ind.standard_version` 必须回指 `m22_clinical_review_std.standard_version`；版本切换只影响切换后的期间，历史达标结论 `m22_clinical_review_achv` 永不重算 |
| 7 | **院感数据必须可识别为手工** | 院感指标无上游模块，`m22_clinical_infection` 的 `entry_source` 默认 `MANUAL`，且 `ck_..._manual_confirm` 强制手工行必须有填报人、填报时刻、审核人，**不允许把手工数伪装成接口采集数** |

### 1.2 表分组说明

| 分组 | 表 | 说明 |
|---|---|---|
| **地基**（2 张） | `m22_clinical_metric_fact`、`m22_clinical_collect_task` | 指标值的唯一落地处与采集编排。其余所有主题表都是它的**主题化视图**（按域聚合并加达标判定） |
| **质量主题**（4 张） | `m22_clinical_quality`、`m22_clinical_surgery`、`m22_clinical_nursing`、`m22_clinical_infection` | 对应详细设计 P02~P05 四个页面。每张表解决一个「谁来填、谁来核」的问题，因**责任人与审核链不同**而不能合并 |
| **绩效池**（2 张） | `m22_clinical_perf_pool`、`m22_clinical_perf_weight` | 配置（权重）与事实（得分）分离。权重是方案的一部分需版本化，得分是每月算出来的 |
| **等级评审**（3 张） | `m22_clinical_review_std`、`m22_clinical_review_ind`、`m22_clinical_review_achv` | 标准版本 / 指标定义 / 达标记录三层。**版本与达标分离**是 2022 版切换后历史不重算的物理保证 |
| **导出审计**（1 张） | `m22_clinical_export` | 质控报表要报卫健委，导出必须留痕 |

### 1.3 为什么是 12 张而不是 8~10 张

共享规范 §12 给 M22-07 的建议表数是 8~10 张。本子模块落在 **12 张**，超上限 2 张，理由如下（逐条说明不合并的原因）：

| # | 为什么不能合并 | 具体事实 |
|---|---|---|
| 1 | **四个质量主题不能合并成一张** | 医疗质量、手术效率、护理、院感的指标结构差异超过 60%：医疗质量的判定基准是「病案首页质量」与「住院日」，手术效率的核心是「分钟级时效」（首台准点、接台间隔），护理是「率」（完成率、及时率），院感是「例数与率」且**必须区分手工填报与接口采集**。合成一张宽表会有 40+ 个列、其中 30 个列对任一主题恒为 NULL，且无法为不同主题设置不同的必填规则 |
| 2 | **院感必须独立** | 院感的 `entry_source` 是 `MANUAL`（无上游模块），其余三个主题是 `API_CALL`。混在一张表里会让「这条数据是人工填的还是系统采的」这个**最关键的可信度判断**丢失 |
| 3 | **绩效权重必须独立于得分** | 权重属于**方案配置**，一年只改 1~2 次且需审批留痕；得分属于**月度事实**，每月全域重算。二者生命周期完全不同，合并会导致「改一次权重就把历史得分全部改写」 |
| 4 | **评审标准与评审指标必须分层** | 2022 版标准相对 2012 版：条款数、编号体系、部分指标口径都变了。标准版本表存「这一版有哪些章节、生效日期」，指标表存「这一条指标的编码与口径」。分层的价值在于**切换版本时只需新增版本行与新指标行，历史达标记录外键不变** |
| 5 | **达标记录必须独立且只增** | 等级评审是**举证**场景：评审专家会问「2025 年第三季度这条指标达没达标、当时的口径是哪一版」。若达标结论写在指标定义表上，口径一改历史结论就被覆盖，无法举证 |
| 6 | **采集任务与指标事实不能合并** | 采集任务是**配置**（百行级，人工维护），指标事实是**数据**（百万行级，机器写入）。合并后一条配置变更要动百万行数据，且无法表达「某指标本月停采」 |

> **与共享规范的关系：** 共享规范 §12 原文末句「**表数不做硬性限制**，以「一张表只表达一件事」为准。若超出建议上限，需在数据结构汇总里写明理由」。本节即为该理由的展开，汇总文档登记时请引用本文 §1.3。

### 1.4 不算在 12 张内的「借用表」

本子模块**不重复建表**，以下表由其他子模块定义，M22-07 只读引用：

| 表 | 定义方 | M22-07 的用法 |
|---|---|---|
| `m22_metric_def` | M22-01 | 指标编码 → 口径版本、单位、方向、`min_sample_size` 的唯一来源。本子模块所有 `metric_code` 都必须能在该表查到 |

> `FK*` 表示**逻辑外键**（不建物理约束，由应用层保证）。全表统一约定：
>
> - 主键 `id BIGINT GENERATED BY DEFAULT AS IDENTITY`
> - 时间戳一律 `TIMESTAMP`（东八区，不用 `TIMESTAMPTZ`）
> - 枚举一律 `VARCHAR(32)` + `CHECK`，不建 PostgreSQL ENUM 类型
> - **不建物理外键**，跨表引用由应用层校验（理由见各表「设计说明」）
> - 逻辑删除 `is_deleted BOOLEAN NOT NULL DEFAULT FALSE`，配套部分索引 `WHERE is_deleted = FALSE`
> - 事实类表按月 `RANGE` 分区，**必须带 `DEFAULT` 分区**

### 4.2 表：`m22_clinical_metric_fact`（临床指标事实表）

**用途：** 本子模块的**地基表**。每一行是「某个指标编码、在某个统计期间、某个责任科室、某个业务维度上的一个值」。所有主题表（质量 / 手术 / 护理 / 院感 / 绩效池 / 评审达标）最终都从这张表取数或与它勾稽。

**为什么需要它，而不是直接用 M22-02 的 `m22_fact_metric`：** 通用事实表只表达「指标 = 值」，回答不了临床质量场景最关键的三个问题：**这个指标归谁负责**（`owner_dept_id`）、**有没有达标**（三阈值 + `achieve_status`）、**这属于哪条评审条款**（`review_clause_code`）。这些是临床质量主题独有的语义，塞进通用表会让通用表被单一主题污染。

**写入方 / 只读方：**

| 角色 | 权限 | 说明 |
|---|---|---|
| M22-02 采集任务 | INSERT / UPDATE（仅 `DRAFT`、`CALCULATED`） | 主写入方，通过 `collect_batch_no` 幂等 |
| M22-07 手工补录 | INSERT / UPDATE（仅 `DRAFT`） | 补采场景，`source_api` 记 `MANUAL` |
| M22-07 发布任务 | UPDATE（`CALCULATED` → `PUBLISHED`） | 仅改状态与 `published_at` |
| M17-07 | 只读 | 通过 P-10 取绩效指标值，不直读本表 |
| 全部业务模块 | 只读 | 通过详细设计 §10.2 的 P-01~P-04 |
| 任何角色 | **禁止 UPDATE / DELETE `PUBLISHED` 行** | 由 `trg_m22_clinical_fact_freeze` 触发器强制 |

**字段表**

ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_direction
    CHECK (value_direction IN ('HIGHER_BETTER', 'LOWER_BETTER', 'NEUTRAL'));

ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_achieve
    CHECK (achieve_status IS NULL
           OR achieve_status IN ('ACHIEVED', 'ON_TRACK', 'AT_RISK',
                                 'MISSED', 'NOT_SET', 'NO_DATA'));

-- 6. 数据完整性枚举
ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_source_status
    CHECK (source_status IN ('COMPLETE', 'PARTIAL', 'FAILED', 'STALE'));

--    比率类指标：分母 > 0 时值必须有；分母 = 0 时值必须为空
ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_rate_zero_denominator
    CHECK (
        calc_type NOT IN ('RATE', 'RATIO', 'AVG')
        OR (denominator > 0 AND value IS NOT NULL)
        OR (denominator = 0 AND value IS NULL)
    );

-- 8. 比率类必须填分母
ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_rate_denominator
    CHECK (calc_type NOT IN ('RATE', 'RATIO', 'AVG') OR denominator IS NOT NULL);

ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_count_value
    CHECK (calc_type NOT IN ('COUNT', 'AMOUNT', 'DURATION', 'SCORE')
           OR value IS NOT NULL);

-- 10. 分子不得为负、分母不得为负
ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_nonneg
    CHECK ((numerator IS NULL OR numerator >= 0)
           AND (denominator IS NULL OR denominator >= 0));

-- 11. 期间顺序
ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_period_range
    CHECK (period_end_date >= period_start_date);

-- 12. 不完整数据必须说明缺什么
ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_missing
    CHECK (source_status = 'COMPLETE'
           OR (source_missing IS NOT NULL AND length(btrim(source_missing)) >= 2));

-- 13. 作废必须写原因且长度 >= 10
ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_void
    CHECK (status <> 'VOID'
           OR (void_reason IS NOT NULL AND length(btrim(void_reason)) >= 10));

-- 14. 发布必有发布时刻与发布人
ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_published
    CHECK (status NOT IN ('PUBLISHED', 'VOID')
           OR (published_at IS NOT NULL AND published_by IS NOT NULL));

ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_sample
    CHECK (sample_count IS NULL
           OR min_sample_size IS NULL
           OR sample_sufficient = (sample_count >= min_sample_size));

    ADD CONSTRAINT ck_m22_clinical_fact_biz_dim
    CHECK (
        (biz_dim = 'NONE' AND biz_dim_value = 'ALL')
        OR (biz_dim <> 'NONE' AND biz_dim_value <> 'ALL')
    );

-- 17. 三项阈值若都配置，必须满足方向一致
ALTER TABLE m22_clinical_metric_fact
    ADD CONSTRAINT ck_m22_clinical_fact_threshold
    CHECK (
        target_value IS NULL OR warn_threshold IS NULL
        OR ((value_direction = 'HIGHER_BETTER' AND warn_threshold <= target_value)
            OR (value_direction = 'LOWER_BETTER' AND warn_threshold >= target_value)
            OR value_direction = 'NEUTRAL')
    );

-- 18. 科室名称与编码不允许空白

    CHECK (length(btrim(dept_code)) >= 1 AND length(btrim(dept_name)) >= 1);

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | 唯一键含 `period_start_date` 而非仅 `period` | PostgreSQL 分区表要求**唯一约束必须包含分区键**。`period_start_date` 是分区键，因此唯一索引必须带上它。由于 `period` 与 `period_start_date` 在应用层一一对应（月粒度 `2026-10` 必对应 `2026-10-01`），带上它**不削弱幂等性**，反而多一层「期间与起日不一致」的拦截（见详细设计 §8.2） |
| 2 | `value` 可空而非 `NOT NULL DEFAULT 0` | 这是铁律 3 的核心。分母为 0 时值必须为空，页面才敢显示「—」而不是 `0.00%`。若设默认 0，任何忘记赋值的代码路径都会静默产生「0 分」的假数据，且**不可事后区分**是「真的是 0」还是「没算出来」 |
| 3 | 约束 7 用 `calc_type` 分支而非统一规则 | 计数类指标（手术台次）没有分母概念，不能要求 `denominator > 0`；比率类（感染率）必须先有分母才能谈值。两类语义用一条 `CHECK` 按 `calc_type` 分支表达，比在代码里 `if` 判断更可靠——代码可以被绕过，约束不能 |
| 4 | `metric_name` / `dept_name` 冗余快照 | 指标改名、科室合并后，历史报表仍应显示当时的名称。若 join 当前主数据，2025 年的报表会突然显示 2027 年的科室名，评审举证时无法解释 |
| 5 | `sample_sufficient` 用 `CHECK` 而非生成列 | 需要允许 `sample_count` 或 `min_sample_size` 为空的中间态（如数据未到齐），生成列无法表达 NULL 语义。用 `CHECK` 在两者都有值时强制一致，兼顾灵活与正确 |
| 6 | 约束 13 要求作废原因长度 ≥ 10 | 与 M05-01 / M17-07 的作废规范一致。一个字「错」无法复盘，10 个字符强制说明真实原因 |
| 7 | 不建物理外键 | 全仓约定。分区表上的外键在 PostgreSQL 中需带分区键、维护成本高；且 `dept_id` 在科室合并时会历史失效，物理外键会让历史数据无法保全 |
| 8 | 必须有 `DEFAULT` 分区 | 采集任务可能补采半年前的指标、跨年修正也可能发生。没有 `DEFAULT` 分区时，`period_start_date` 落在未预建月份会直接 `ERROR: no partition of relation found`，**整批采集失败**。这是共享规范 §2.6 的硬要求 |
| 9 | `review_clause_code` 放在事实表而非另建关联表 | 一个指标可能对应 1 个条款（绝大多数），多对多的情况罕见。用可空列 + 部分索引覆盖 95% 场景，避免为少数情况增加一张关联表 |
| 10 | 状态用四态而非三态 | `CALCULATED`（已算完待发布）与 `PUBLISHED`（已发布他人可见）分开，是因为发布前要复核。合并后无法表达「算完了但复核发现口径有问题」这个中间态 |

**量级估算**

| 项 | 估算 | 依据 |
|---|---|---|
| 指标数 | 约 120 个 | 临床质量 45 + 手术麻醉 25 + 护理 20 + 院感安全 15 + 评审专项 15 |
| 维度组合 | 每指标平均 4 个（全院 + 科室 + 医生 + 手术室等） | 部分指标只到全院 |
| 月粒度行数 | 120 × 4 = 480 行/月 | — |
| 日粒度行数 | 约 20 个指标有日粒度 × 3 维度 = 60 行/日 ≈ 1,800 行/月 | 只对时效敏感指标采日粒度 |
| 年增长 | (480 + 1,800) × 12 ≈ 2.7 万行/年 | — |
| 10 年累积 | 约 27 万行 | — |
| 单行宽度 | 约 600 字节 | 含文本字段 |
| 10 年数据量 | 约 162 MB，含索引约 260 MB | — |

> 实际行数比预估「年增约 120 万行」小，但**预留了 40 倍余量**：若将来把「每个医生 × 每个指标 × 每日」全部落库（约 200 医生 × 120 指标 × 365 天 = 876 万行/年），分区与索引设计仍能支撑。

**分区结论**

按 `period_start_date` **月 RANGE 分区**，保留全部历史（不自动删分区）。

| 决策 | 理由 |
|---|---|
| 用 `period_start_date` 而非 `period` 作分区键 | `period` 是 `VARCHAR`，`2026-10` / `2026-Q3` / `2026` 三种粒度格式字符串排序不等于时间排序，无法作为 RANGE 分区键。`period_start_date` 是 `DATE`，天然有序且与粒度无关 |
| 月分区而非年分区 | 临床质量最热查询是「本月各科室达标情况」，月分区可保证只扫 1 个分区。年分区（12 个月数据）会让该查询扫 12 倍数据 |
| 不自动删分区 | 等级评审要追溯上一周期的举证材料，通常要求保留 ≥ 3 年、评审周期 4 年。自动删除会在评审年造成「数据找不到了」的灾难 |
| 必须有 `DEFAULT` 分区 | 见设计说明第 8 条 |

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | `metric_codes` 用 `JSONB` 数组而非子表 | 一个任务平均管 3~5 个指标，用子表会多一张百行表与一次 join。任务配置只有管理员手工维护、无按指标反查的高频需求，JSONB 足够；若将来需要「按指标查任务」，可加 `jsonb_path_ops` GIN 索引 |
| 2 | `uk_..._api` 唯一约束防重复采集 | 同一个上游接口同一粒度只应有一个任务。两个任务采同一接口会产生两份不同 `collect_batch_no` 的事实，唯一键冲突时会让人困惑「到底以哪份为准」；提前在配置层拦住 |
| 3 | `delay_minutes` 默认 30 | 上游日结通常在 01:00~02:00 跑完，M22 若与之同时启动会拿到「半成品」（如日结中途的中间值）。默认让 30 分钟是实测经验值：M16 日结 P95 耗时 22 分钟 |
| 4 | `fill_mode` 区分 STRICT / TOLERANT | 评审指标要求「一个都不能少」，缺数必须整批失败让人介入（STRICT）；探索性指标可以容忍单条失败（TOLERANT）。用配置而非硬编码，让运维按指标重要性选择 |
| 5 | `consecutive_fail_days` 落库而非实时算 | 实时算需要扫 3 天以上的批次记录，告警任务每秒都在算。落成一个计数器，每次执行后更新，告警只需 `> 3` 判断，O(1) |
| 6 | 不建分区 | 百行级配置表，无分区必要 |
| 7 | 约束 4 强制 `/internal/v1/` 前缀 | 防止把对外接口 `/api/v1/` 写进采集配置。对外接口有网关鉴权与限流，内网直调会被限流拒绝且暴露在非信任区 |
| 8 | 表达 `cron_expr` 用 6 段（含秒） | APScheduler 的 `CronTrigger.from_crontab` 支持 6 段；用秒级精度可以让多个任务错峰（`0 10 2` 与 `30 10 2`），避免同一秒并发打满上游 |

**量级估算**

| 项 | 估算 |
|---|---|
| 任务数 | 约 40 个（每个上游接口一个任务） |
| 年增长 | 约 10 行/年（新增或拆分任务） |
| 单行宽度 | 约 450 字节 |
| 10 年数据量 | 约 500 行、0.2 MB |

**分区结论**

不分区。百行级配置表，`PRIMARY KEY` + 两个唯一索引即可，分区只会增加调度器查询的规划成本。

### 4.4 表：`m22_clinical_quality`（医疗质量指标明细表）

**用途：** 承载「医疗质量」主题（P02）每期每科室的指标明细，是**从指标事实表拆出的主题视图的物化快照**，额外保存医疗质量专属的四项语义：病案首页质量分项得分、核心制度落实项、三基考核结果、处方点评结果。

**为什么不能只靠 `m22_clinical_metric_fact`：** 医疗质量指标的「值」可以在事实表里，但医疗质量管理需要回答的一组问题不是单一数值——「本月甲科室病案首页甲级率 96.2%，其中病案首页的 7 个检查项分别扣了多少分、缺哪一项」。这是**分项扣分明细**，事实表每个指标一行放不下。因此本表按「每条医疗质量记录 = 一个指标在一个分项上的一次取值」组织，用 `item_code` 区分分项。

    PARTITION OF m22_clinical_quality

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | 拆出独立主题表而非全塞事实表 | 医疗质量管理的日常动作是「按检查项看扣分明细」，一个指标下有 3~10 个检查项。塞进事实表需要把检查项编码拼成一个 JSON 字段，无法按检查项建立索引、无法用 SQL 做「哪个检查项全院最差」的聚合 |
| 2 | 约束 4 在库层校验缺陷率算式 | 只靠应用层算，任何一处复用错误（如用了 `ROUND(x,2)`）都会产生与分子分母不符的率。约束容忍 ±0.000001 是 6 位小数的舍入容差 |
| 3 | `deduct_score` 命名避开「金额」语义 | 医疗质量扣分是**质量分**（100 分制），不是钱。用 `deduct_score` 而非 `deduct_amount`，从字段名上杜绝被误当绩效金额参与计算 |
| 4 | `is_estimable` 显式落库 | 分母为 0 时页面必须显示「无样本」而非「0%」。页面的渲染分支需要一个布尔字段而不是靠 `defect_rate IS NULL` 再判断——后者在有 TRUE 值但分母为 0 的脏数据下会误判 |
| 5 | 用季度分区而非月分区 | 本表行数比事实表少一个量级（约 4.3 万行/年），季度分区已能保证「查一个季度」只扫一个分区，分区数从 12 降到 4，元数据开销更低 |
| 6 | `fact_no` 可空 | 部分检查项是纯扣分明细，不对应独立指标值（如「主要诊断选择正确」只有对错，没有百分比）。强制非空会让这类记录无处安放 |
| 7 | `core_system_code` 用可空列而非独立表 | 18 项医疗质量安全核心制度是固定清单，用编码列 + 部分索引即可。独立表会引入一次 join 和一个「18 行」的维护负担 |
| 8 | 不建物理外键 | 全仓约定（见 `m22_clinical_metric_fact` 设计说明第 7 条） |

**量级估算**

| 项 | 估算 |
|---|---|
| 医疗质量指标数 | 约 45 个 |
| 每指标检查项 | 平均 4 个 |
| 维度组合 | 每指标平均 2 个（全院 + 科室） |
| 月行数 | 45 × 4 × 2 × 12 科室 ≈ 4,320 行/月 |
| 年行数 | 约 5.2 万行 |
| 单行宽度 | 约 500 字节 |
| 10 年数据量 | 约 52 万行，约 260 MB，含索引约 430 MB |

**分区结论**

按 `period_start_date` **季度 RANGE 分区**，必须有 `DEFAULT` 分区。

| 决策 | 理由 |
|---|---|
| 季度而非月 | 本表总行数仅 5.2 万行/年，月分区会让每个分区只有 4,000 行，分区数达 40 个（10 年）反而增加规划开销。季度分区每年 4 个，单分区 1.3 万行，扫描效率与元数据开销平衡最佳 |
| 保留全部历史 | 等级评审追溯需 ≥ 3 年，病案首页质量更是「越老越可能被抽查」，不删 |

### 4.5 表：`m22_clinical_surgery`（手术与麻醉效率表）

**用途：** 承载「手术与麻醉效率」主题（P03）。记录每期、每手术间 / 每麻醉类型的**台次、台均时长、首台准点、接台间隔、麻醉方式分布、麻醉并发症**等效率指标。

**为什么单独一张表而不是复用事实表：** 手术效率的核心指标是**时长类**（台均手术时长、接台间隔中位数、术前等待时长），而事实表用 `value` 单值 + `calc_type` 表达。时长类指标既需要「均值」也需要「中位数 / P90」，一个 `value` 放不下；且效率分析必须能按 **手术间号** 与 **麻醉方式** 两个维度交叉，事实表的 `biz_dim` 只有一个槽位。本表用 `or_room_code` + `anesthesia_type` 两个独立列解决交叉问题。

| M22-07 手术室护士长 | 只读 | 通过 P03 页面 |
| 医务科 | 只读 | 通过 P03 / P08 |
| M22-07 发布任务 | UPDATE（`PUBLISHED`） | 只改状态 |

**约束说明**

```sql
-- 1. 状态枚举
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_status
    CHECK (status IN ('DRAFT', 'PUBLISHED', 'VOID'));

-- 2. 麻醉方式枚举
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_anes_type
    CHECK (anesthesia_type IN ('ALL', 'GENERAL', 'LOCAL', 'SEDATION', 'NERVE_BLOCK'));

-- 3. 停台率：分母为 0 时必须为空
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_cancel_rate
    CHECK (
        cancel_rate IS NULL
        OR (surgery_case_count + cancel_count) > 0
    );

-- 4. 首台准点率：无手术间日时必须为空
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_first_rate
    CHECK (
        (first_case_total > 0 AND first_case_on_time_rate IS NOT NULL)
        OR (first_case_total = 0 AND first_case_on_time_rate IS NULL)
    );

-- 5. 首台准点台数不得超过首台总数
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_first_count
    CHECK (first_case_on_time_count >= 0
           AND first_case_total >= 0
           AND first_case_on_time_count <= first_case_total);

-- 6. 麻醉并发症率：麻醉例数为 0 时必须为空
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_anes_rate
    CHECK (
        (anesthesia_count > 0 AND anesthesia_complication_rate IS NOT NULL)
        OR (anesthesia_count = 0 AND anesthesia_complication_rate IS NULL)
    );

-- 7. 并发症例数不得超过麻醉例数
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_anes_count
    CHECK (anesthesia_complication_count >= 0
           AND anesthesia_count >= 0
           AND anesthesia_complication_count <= anesthesia_count);

-- 8. 手术间利用率：可用时长为 0 时必须为空
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_util
    CHECK (
        utilization_rate IS NULL
        OR (available_minutes > 0 AND utilization_rate >= 0 AND utilization_rate <= 1)
    );

-- 9. 时长非负且 P90 不小于中位数
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_minutes
    CHECK (
        (avg_surgery_minutes IS NULL OR avg_surgery_minutes >= 0)
        AND (median_surgery_minutes IS NULL OR median_surgery_minutes >= 0)
        AND (p90_surgery_minutes IS NULL OR p90_surgery_minutes >= 0)
        AND (avg_turnover_minutes IS NULL OR avg_turnover_minutes >= 0)
        AND (avg_preop_wait_minutes IS NULL OR avg_preop_wait_minutes >= 0)
    );

-- 10. P90 不得小于中位数
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_p90
    CHECK (p90_surgery_minutes IS NULL OR median_surgery_minutes IS NULL
           OR p90_surgery_minutes >= median_surgery_minutes);

-- 11. 无手术时不得有台均时长
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_no_case
    CHECK (surgery_count > 0 OR avg_surgery_minutes IS NULL);

-- 12. 可估算标记如实反映
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_estimable
    CHECK (is_estimable = (surgery_count > 0));

-- 13. 台次非负
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_count
    CHECK (surgery_count >= 0 AND surgery_case_count >= 0 AND cancel_count >= 0);

-- 14. 期间顺序
ALTER TABLE m22_clinical_surgery
    ADD CONSTRAINT ck_m22_clinical_surgery_period
    CHECK (period_end_date >= period_start_date);
```

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | `or_room_code` 与 `anesthesia_type` 两列而非放进 `biz_dim` | 手术效率分析必须能交叉「3 号手术间的全麻台均时长」。事实表的 `biz_dim` 单槽位无法表达二维交叉；本表把两个维度都做成列，唯一键天然覆盖交叉组合 |
| 2 | 同时存 `avg` / `median` / `p90` 三个时长 | 手术时长是长尾分布，均值会被个别超长手术拉偏。手术室排班看中位数，质控看 P90（长尾风险）。只存均值会让「P90 超 4 小时的手术占多少」无法回答 |
| 3 | 三条比率都写了「分母为 0 必须有空」的独立约束 | 判空条件各不相同（停台率分母是「例数 + 停台数」、首台率分母是手术间日数、麻醉并发症率分母是麻醉例数）。写成一个笼统的 `denominator > 0` 约束会让每条率的判空逻辑被压缩，反而容易漏 |
| 4 | `available_minutes` 与 `utilization_rate` 同时存 | 只存率无法复核。运维看到「利用率 120%」时第一反应是数据错，必须能立刻看分子分母。存了分母原值，异常排查无需跨模块取数 |
| 5 | 约束 11：无手术时不得有台均时长 | 采集任务若在上游返回空数组时忘了置空 `avg_surgery_minutes`，会残留上一次的值，产生「0 台手术但台均 45 分钟」的荒谬数据 |
| 6 | `p90 >= median` 约束 | 数学上必然成立。若违反说明中位数与分位数的计算口径不一致（如一个按台次一个按例数），是严重的口径错误，必须在库层拦住 |
| 7 | 季度分区 | 行数比医疗质量表还少（每期约 4 手术间 × 5 麻醉方式 × 12 科室 ≈ 240 行/月），季度分区足够 |
| 8 | 不建物理外键 | 全仓约定 |

**量级估算**

| 项 | 估算 |
|---|---|
| 手术间数 | 4 个（二级眼科医院典型规模，含 1 个感染手术间） |
| 麻醉方式组合 | 5 种（含 ALL） |
| 科室数 | 约 12 个（含手术室与 4 个病区） |
| 月行数 | 4 × 5 × 12 ≈ 240 行/月（去重后实际约 180 行） |
| 年行数 | 约 2,200 行 |
| 单行宽度 | 约 600 字节 |
| 10 年数据量 | 约 2.2 万行，约 13 MB |

**分区结论**

按 `period_start_date` **季度 RANGE 分区** + `DEFAULT` 分区。

| 决策 | 理由 |
|---|---|
| 分区而非不分区 | 2.2 万行本可不分区，但本表与 `m22_clinical_quality` 同属「主题明细」，保持一致的「按 period_start_date 分区」范式，便于运维统一编写分区维护脚本与归档作业。**一致性带来的运维简化价值大于分区本身的空间收益** |
| 必须有 `DEFAULT` 分区 | 同事实表理由 |

### 4.6 表：`m22_clinical_nursing`（护理质量指标表）

**用途：** 承载「护理指标」主题（P04）。每期每病区 / 每护理单元的**护理任务完成率、健康宣教执行率、生命体征采集及时率、给药执行准确率、交接班规范率、压疮与跌倒发生率**等。

**为什么单独一张表：** 护理指标有 5 个独立上游（M08-01 任务、M08-02 计划、M08-04 体征、M08-06 给药、M08-07 交接班），每个上游返回的口径不同（完成的分子分母定义、统计单元）。合并成一行需要把 5 个来源拼成一个超宽行；拆成多行又难以「一次看完某病区所有护理指标」。本表采用 **`indicator_group`（指标分组）+ 一行一个指标** 的折中：同一病区同期有 6~10 行，页面一次查出即可拼成完整护理质量表。

**写入方 / 只读方：**

| 角色 | 权限 | 说明 |

| M22-07 采集任务 | INSERT | 合并 5 个 M08 接口返回值 |
| 护理部 | 只读 + 手工补录（`source_api` 记 `MANUAL`） | 少数上游未覆盖的指标（如护理不良事件）由护理部填报 |
| M22-07 发布任务 | UPDATE（`PUBLISHED`） | 只改状态 |

**约束说明**

```sql
-- 1. 状态枚举
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_status
    CHECK (status IN ('DRAFT', 'PUBLISHED', 'VOID'));

-- 2. 指标分组枚举
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_group
    CHECK (indicator_group IN ('TASK', 'PLAN', 'VITAL',
                               'MED', 'HANDOVER', 'ADVERSE'));

-- 3. 计算类型枚举
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_calc_type
    CHECK (calc_type IN ('RATE', 'COUNT', 'AVG', 'DURATION'));

-- 4. 分母为 0 时值必须为空（铁律 3）
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_zero_denominator
    CHECK (
        calc_type NOT IN ('RATE', 'AVG')
        OR (denominator > 0 AND value IS NOT NULL)
        OR (denominator = 0 AND value IS NULL)
    );

-- 5. 比率类必须有分母
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_denominator
    CHECK (calc_type NOT IN ('RATE', 'AVG') OR denominator IS NOT NULL);

-- 6. 比率类值域 [0, 1]
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_rate_range
    CHECK (calc_type <> 'RATE' OR value IS NULL OR (value >= 0 AND value <= 1));

-- 7. 分子不得大于分母
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_numerator
    CHECK (calc_type <> 'RATE' OR numerator IS NULL OR denominator IS NULL
           OR numerator <= denominator);

-- 8. 比率与分子分母一致
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_rate_calc
    CHECK (
        calc_type <> 'RATE' OR value IS NULL OR denominator IS NULL
        OR denominator = 0 OR numerator IS NULL
        OR abs(value - ROUND(numerator / denominator, 6)) <= 0.000001
    );

-- 9. 可估算标记如实反映
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_estimable
    CHECK (calc_type NOT IN ('RATE', 'AVG')
           OR is_estimable = (denominator > 0));

-- 10. 人工填报必须有填报人与时刻
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_manual
    CHECK (entry_mode = 'AUTO'
           OR (entry_by IS NOT NULL AND entry_at IS NOT NULL));

-- 11. 不良事件等级仅 ADVERSE 分组有值
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_adverse
    CHECK (indicator_group = 'ADVERSE' OR adverse_level IS NULL);

-- 12. 不良事件等级枚举
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_adverse_level
    CHECK (adverse_level IS NULL
           OR adverse_level IN ('NONE', 'NEAR_MISS', 'NO_HARM', 'HARM'));

-- 13. 期间顺序
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_period
    CHECK (period_end_date >= period_start_date);

-- 14. 发布必有发布时刻与发布人
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_published
    CHECK (status <> 'PUBLISHED'
           OR (published_at IS NOT NULL AND published_by IS NOT NULL));

-- 15. 班次枚举
ALTER TABLE m22_clinical_nursing
    ADD CONSTRAINT ck_m22_clinical_nursing_shift
    CHECK (shift_type IN ('ALL', 'DAY', 'EVENING', 'NIGHT'));
```

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | 用 `indicator_group` 而非一列一指标 | 若把 6 类共 20 个护理指标做成 20 个列，新增一个指标就要改表结构、改 ORM、改接口。分组 + 一指标一行是**可扩展**的：新指标只需在指标定义表注册，无需 DDL 变更 |
| 2 | 约束 4/5/6/7/8 五条一起保比率正确 | 单靠「分母为 0 则空」不够。护理指标最典型的错误是「完成数 120 / 应完成 100 = 120%」——这违背 `numerator <= denominator`（约束 7）；还有「值 0.85 但分子分母算出 0.92」（约束 8）。多条约束合起来才构成完整的比率正确性 |
| 3 | `entry_mode = MANUAL` 时强制填报人与时刻 | 护理不良事件目前无上游模块，只能人工填报。**必须留下谁在何时填报**，否则评审举证时无法说明数据的可追溯性。这是「不假装有数据来源」的具体落地 |
| 4 | `adverse_level` 仅 ADVERSE 分组有值 | 用 `CHECK (indicator_group = 'ADVERSE' OR adverse_level IS NULL)` 防止其他分组误填。若允许任意填，页面在渲染「任务完成率」时会多出无意义的「不良事件等级」列 |
| 5 | `target_value` 注释明确「非金额」 | 护理目标是「完成率 ≥ 95%」这类比值。为避免被误当绩效金额，字段名用 `target_value`（值）而非任何含 amount 的词，且校验脚本对 `target` 前缀字段只做类型检查不做金额检查 |
| 6 | 季度分区 | 每期 20 指标 × 6 病区 × 3 班次 ≈ 360 行/月，季度分区足够 |
| 7 | `shift_type` 默认 `ALL` | 大部分指标按月汇总不分班次。只有给药准确率、交接班规范率需要分班次看（夜班质量是护理管理重点）。默认 `ALL` 让日常查询免于 `WHERE shift_type = 'ALL'` 的心智负担 |

**量级估算**

| 项 | 估算 |
|---|---|
| 护理指标数 | 约 20 个 |
| 病区数 | 6 个 |
| 班次组合 | 月汇总为 1，分班次为 3 |
| 月行数 | 20 × 6 ≈ 120 行（分班次指标 × 3 = 约 240 行） |
| 年行数 | 约 2,900 行 |
| 10 年数据量 | 约 2.9 万行，约 18 MB |

**分区结论**

按 `period_start_date` **季度 RANGE 分区** + `DEFAULT` 分区。理由同 `m22_clinical_surgery`：与其余主题明细表保持同一分区范式，运维脚本统一。

### 4.7 表：`m22_clinical_infection`（院感与安全指标表）

**用途：** 承载「院感与安全」主题（P05）。记录每期院感科填报的**感染例数、手术例数、感染率、I 类切口感染率、多重耐药菌检出、职业暴露、器械相关感染**等。

#### 本表是「手工填报为主」的过渡方案，必须读懂这一段

**事实：全院没有院感管理模块。** 本项目模块清单为 M01~M17 + M22，其中没有院感（医院感染管理）模块，也没有任何模块在内部契约总线中提供院感的接口。M09-04 只提供手术器械清点统计（`GET /internal/v1/m09/instrument/statistics/daily`），能间接支撑「器械相关感染」的**分母**（器械使用次数），但**没有感染例数**这个分子。

**因此本模块采取「首次定义 + 手工填报」的过渡方案，不做任何假设：**

1. M22-07 **首次定义**内部契约 `GET /internal/v1/m22/clinical/nosocomial/collect`（详见详细设计 §10.1 与 §6.3 的 API 详述），作为院感数据的**唯一标准入口**。将来若建设院感模块，只需由该模块实现此接口，M22-07 的消费方代码与数据结构**零改动**。
2. 在院感模块建成前，此接口由 M22-07 自身实现，数据来自**院感科每月手工填报**（P05 页面的填报表单 → API-xx 手工填报接口）。
3. 所有手工填报的记录必须落 `entry_mode = 'MANUAL'`、`entry_by`、`entry_at`、`data_quality_level`，并在页面上**显著标注「手工填报，待院感系统对接」**。
4. **绝不假装有数据来源**：不能把「M09-04 器械清点次数」当成感染分子，不能把分子为空的感染率显示为 `0.00%`，不能在上游缺失时静默落 0。缺失就是缺失——`infection_rate` 为空，页面显示「—」，`source_status` 标 `PARTIAL`，`source_missing` 写明缺什么。

**写入方 / 只读方：**

| 角色 | 权限 | 说明 |
|---|---|---|
| 院感科（`m22:clinical:create` + `m22:clinical:sensitive`） | INSERT / UPDATE（仅 `DRAFT`、`MANUAL` 记录） | 手工填报的唯一合法写入方 |
| M22-07 采集任务 | INSERT（`entry_mode = 'AUTO'`） | 未来对接院感模块后，由采集任务写入；当前只用于写入来自 M09-04 的分母类数据 |
| M22-07 发布任务 | UPDATE（`PUBLISHED`） | 只改状态 |
| 感染管理委员会 / 医务科 | 只读 | 通过 P05 / P07 |
| 任何人 | **禁止删除已发布记录** | 作废走 `VOID` + 原因 |

ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_status
    CHECK (status IN ('DRAFT', 'PUBLISHED', 'VOID'));

-- 2. 感染类别枚举
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_category
    CHECK (infection_category IN ('GENERAL', 'SURGICAL_SITE', 'DEVICE',
                                  'MULTIDRUG', 'OCCUPATIONAL', 'HAND_HYGIENE'));

-- 3. 录入方式枚举
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_entry_mode
    CHECK (entry_mode IN ('MANUAL', 'AUTO'));

-- 4. 数据质量等级枚举
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_quality
    CHECK (data_quality_level IN ('MANUAL_PENDING', 'MANUAL_VERIFIED', 'SYSTEM_AUTO'));

-- 5. 数据完整性与数据质量必须自洽
--    手工填报未复核 + 声称完整 = 矛盾（尚未与任何系统核对，不能声称完整）
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_quality_consistency
    CHECK (data_quality_level <> 'MANUAL_PENDING' OR source_status <> 'COMPLETE');

-- 6. 感染率：分子或分母缺失、或分母为 0 时必须为空
--    这是本表最重要的约束：绝不把「没填」变成「0%」
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_rate
    CHECK (
        infection_rate IS NULL
        OR (
            infection_case_count IS NOT NULL
            AND surgery_case_count IS NOT NULL
            AND surgery_case_count > 0
        )
    );

-- 7. 感染率与分子分母一致
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_rate_calc
    CHECK (
        infection_rate IS NULL
        OR abs(infection_rate
               - ROUND(infection_case_count::numeric / surgery_case_count::numeric, 6))
           <= 0.000001
    );

-- 8. 感染例数不得超过手术例数（同一类别下）
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_case
    CHECK (infection_case_count IS NULL OR surgery_case_count IS NULL
           OR (infection_case_count >= 0 AND infection_case_count <= surgery_case_count));

-- 9. 发病密度：观察人日为 0 时必须为空
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_density
    CHECK (infection_density IS NULL OR observation_days > 0);

-- 10. 手卫生率：观察次数为 0 时必须为空
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_hand
    CHECK (
        (hand_hygiene_obs_count > 0 AND hand_hygiene_rate IS NOT NULL)
        OR (hand_hygiene_obs_count IS NULL AND hand_hygiene_rate IS NULL)
        OR (hand_hygiene_obs_count = 0 AND hand_hygiene_rate IS NULL)
    );

-- 11. 手卫生正确次数不得超过观察次数
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_hand_count
    CHECK (hand_hygiene_ok_count IS NULL OR hand_hygiene_obs_count IS NULL
           OR (hand_hygiene_ok_count >= 0
               AND hand_hygiene_ok_count <= hand_hygiene_obs_count));

-- 12. 手工填报必须有填报人与时刻
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_manual
    CHECK (entry_mode = 'AUTO'
           OR (entry_by IS NOT NULL AND entry_at IS NOT NULL));

-- 13. 已复核等级必须有复核人与时刻
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_verify
    CHECK (data_quality_level <> 'MANUAL_VERIFIED'
           OR (verify_by IS NOT NULL AND verify_at IS NOT NULL));

-- 14. 作废必须写原因且长度 >= 10
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_void
    CHECK (status <> 'VOID'
           OR (void_reason IS NOT NULL AND length(btrim(void_reason)) >= 10));

-- 15. 不完整数据必须说明缺什么
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_missing
    CHECK (source_status = 'COMPLETE'
           OR (source_missing IS NOT NULL AND length(btrim(source_missing)) >= 2));

-- 16. 发布必须有发布时刻与发布人
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_published
    CHECK (status <> 'PUBLISHED'
           OR (published_at IS NOT NULL AND published_by IS NOT NULL));

-- 17. 期间顺序
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_period
    CHECK (period_end_date >= period_start_date);

-- 18. 各类例数非负
ALTER TABLE m22_clinical_infection
    ADD CONSTRAINT ck_m22_clinical_infection_nonneg
    CHECK (
        (infection_case_count IS NULL OR infection_case_count >= 0)
        AND (surgery_case_count IS NULL OR surgery_case_count >= 0)
        AND (observation_days IS NULL OR observation_days >= 0)
        AND (device_days IS NULL OR device_days >= 0)
        AND (multidrug_case_count IS NULL OR multidrug_case_count >= 0)
        AND (occupational_exposure_count IS NULL OR occupational_exposure_count >= 0)
    );

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | `infection_case_count` 允许空而非 `DEFAULT 0` | **这是整张表最重要的一个决策**。若默认 0，院感科还没填报的月份会自动呈现「0 例感染、感染率 0.000000」，这是**欺骗性数据**。允许空 + 约束 6 强制「分子为空则率必为空」，页面才会显示「—」并提示「未填报」。**宁可让评审看到「未填报」，也不能看到假的「零感染」** |
| 2 | 约束 5 把手数据质量与完整性挂钩 | `MANUAL_PENDING`（未复核）不允许同时是 `COMPLETE`。手工填完还没跟任何系统核对，就不该被下游当成可信完整数据。这条约束让「数据质量」不只是一句备注，而是会**阻断**错误状态组合 |
| 3 | `data_quality_level` 三档而非布尔 `is_manual` | 布尔只区分手工/系统，无法表达「手工填了但复核过」。三档让评审举证时能说清「这些数是院感科填的，且由院感科主任复核签字（`code` 记录在 `verify_by`）」 |
| 4 | `source_api` 默认值就是 `MANUAL` | 让「没有上游接口」这个事实在数据里显式可见。任何按 `source_api` 做的溯源报告都会在手工记录上看到 `MANUAL`，而不是一片看似正常的接口路径 |
| 5 | 手工填报也生成 `collect_batch_no` | 让手工数据与自动数据走同一套批次追溯链路。发布任务、缺口告警、报表溯源都按批次号走，不需要为手工数据写第二套逻辑 |
| 6 | `source_status` 默认 `PARTIAL` 而非 `COMPLETE` | 手工填报的默认状态就是「不完整」，只有分子分母都填齐时由应用层显式改 `COMPLETE`。**默认值取悲观侧**，忘记更新的后果是「过度谨慎」而非「虚假完整」 |
| 7 | 约束 10 手卫生率的三分支写法 | 需要覆盖三种情况：有观察必须有余、观察次数为空则率必须为空、观察次数为 0 则率必须为空。写成 `obs > 0 AND rate IS NOT NULL OR obs = 0 AND rate IS NULL` 会漏掉 `obs IS NULL` 分支（SQL 中 `NULL > 0` 为 NULL，整个 CHECK 变成 NULL 即通过，反而放行脏数据） |
| 8 | 季度分区 + `DEFAULT` 分区 | 院感数据每月只几十行，分区收益极小，但为与主题明细表范式统一而分区。`DEFAULT` 分区尤其重要：手工填报可能补填报多年前的月份 |

**量级估算**

| 项 | 估算 |
|---|---|
| 感染类别 | 6 类 |
| 科室数 | 约 13 个（含全院） |
| 月行数 | 6 × 13 ≈ 78 行 |
| 年行数 | 约 950 行 |
| 单行宽度 | 约 700 字节 |
| 10 年数据量 | 约 9,500 行，约 7 MB |

**分区结论**

按 `period_start_date` **季度 RANGE 分区** + `DEFAULT` 分区。分区收益极小（十年不到 1 万行），分区目的是**范式统一**与**补填报兜底**，后者是实质价值。

### 4.8 表：`m22_clinical_perf_pool`（绩效指标池表）

**用途：** 承载「绩效指标池」主题（P06）。按绩效周期、按科室/人员，输出**指标实际值、单位分值、权重、得分**四要素。

#### 本表绝不含任何绩效金额字段 —— 这是全模块最重要的边界

**分工写死如下：**

| 环节 | 负责方 | 输出 |
|---|---|---|
| 指标实际值采集 | M22-07（本表） | `actual_value`（如门诊 680 人次） |
| 单位分值 | KPI 方案配置（本表 `unit_score`） | 8.00 分/人次 |
| 权重 | KPI 方案配置（本表 `weight`） | 0.40 |
| **得分** | M22-07（本表） | `score` = 实际值 × 单位分值 × 权重 = 680 × 8.00 × 0.40 = **2,176.000000** |
| **绩效金额** | **M17-07 绩效核算** | 2,176.00 分 × 科室系数 1.05 × 质量系数 0.98 → **5,350.80 元** |

**M22-07 到此为止，一个字都不往前算。** 本表没有、也不允许有任何字段承载「元」「金额」「单价（钱的单价）」「系数」「应发」「实发」语义：

- 没有 `amount` / `money` / `salary` / `wage` / `pay` 字段；
- 没有科室系数、质量调整系数、绩效基数（这些是 M17-07 的输入，由 M17-04 的科室结余与 M11-07 的质量指标决定）；
- 本表的 `score` 是**分值**（无量纲的分数），不是钱；`unit_score` 是「每单位指标值折多少分」，不是单价。

**为什么要这样切：** 绩效金额一旦散落在两个模块里计算，就会出现两套算法、两种口径、两个数对不上。M17-07 是绩效金额的**唯一计算方**（它是财务模块，有科室系数、质量系数、发放、审批、红冲全套流程）；M22-07 只负责把「指标值 + 权重」这本账算清楚。M17-07 通过内部契约 `POST /internal/v1/m17/performance/base`（由 M06-07 推送基础数据）与 `GET /internal/v1/m17/performance/result` 消费本模块的指标值，并自己乘系数算钱。

| 角色 | 权限 | 说明 |

| M22-07 采集任务 | INSERT | 从 M07-07 等工作量接口取实际值 |
| M22-07 绩效管理员 | UPDATE（仅 `DRAFT`） | 维护单位分值与权重（KPI 方案调整） |
| M17-07 绩效核算 | **只读** | 通过详细设计 §10.2 的 P-06 接口批量取指标值 |

ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_status

-- 2. 指标层级枚举
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_level
    CHECK (indicator_level IN ('STAFF', 'DEPT', 'HOSPITAL'));

-- 3. 绩效域枚举
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_domain
    CHECK (perf_domain IN ('WORKLOAD', 'QUALITY', 'EFFICIENCY',
                           'SATISFACTION', 'LEARNING'));

-- 4. 权重范围 (0, 1]
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_weight
    CHECK (weight > 0 AND weight <= 1);

-- 5. 单位分值非负
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_unit_score
    CHECK (unit_score >= 0);

-- 6. 得分必须严格等于 实际值 × 单位分值 × 权重
--    这是本表的核心约束：得分不允许"手工微调"
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_score_calc
    CHECK (
        score IS NULL
        OR abs(score - ROUND(actual_value * unit_score * weight, 6)) <= 0.000001
    );

-- 6b. 【金额污染防线】权重纯度约束：weight 必须是"纯权重"，不得并入系数
--     背景：约束 6 只能保证 score 严格等于"实际值 × 单位分值 × 权重"这个算式，
--     它防的是"手工微调得分"，防不住"把系数乘进权重"。举例：若有人把
--     weight 由 0.400000 改成 0.411600（= 0.4 × 1.05 科室系数 × 0.98 质量系数），
--     约束 6 依然通过，因为 0.411600 × 实际值 × 单位分值 完全自洽 ——
--     但此时 score 已经含了系数，M22 就等于在事实上算了钱，边界被击穿。
--     因此追加本条：单指标权重上限 0.5；科室级/全院级单指标权重为 1 属合法特例。
--     系数必须在 M17-07 侧作用于 score，不得回流改写 weight。
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_weight_pure
    CHECK (
        weight <= 0.5
        OR (weight = 1 AND indicator_level IN ('DEPT', 'HOSPITAL'))
    );

-- 7. 未乘权重的得分必须等于 实际值 × 单位分值
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_raw_score
    CHECK (
        raw_score IS NULL
        OR abs(raw_score - ROUND(actual_value * unit_score, 6)) <= 0.000001
    );

-- 8. 实际值缺失时 score 与 raw_score 必须为空
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_no_value
    CHECK (actual_value IS NOT NULL OR (score IS NULL AND raw_score IS NULL));

-- 9. 人员级指标必须有人员
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_staff
    CHECK (indicator_level <> 'STAFF'
           OR (staff_id IS NOT NULL AND staff_no IS NOT NULL AND staff_name IS NOT NULL));

-- 10. 科室级、全院级指标不得挂人员
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_no_staff
    CHECK (indicator_level = 'STAFF' OR (staff_id IS NULL AND staff_no IS NULL));

-- 11. 目标达成率：目标为 0 或未设时必须为空
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_achieve
    CHECK (achieve_rate IS NULL OR (target_value IS NOT NULL AND target_value > 0));

-- 12. 封顶保底区间合法
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_cap
    CHECK (
        score_cap IS NULL OR score_floor IS NULL OR score_cap >= score_floor
    );

-- 13. 封顶生效时得分不得超过封顶值
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_cap_applied
    CHECK (cap_applied = FALSE OR score_cap IS NOT NULL OR score_floor IS NOT NULL);

-- 14. 剔除必须写原因
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_exclude
    CHECK (is_excluded = FALSE
           OR (exclude_reason IS NOT NULL AND length(btrim(exclude_reason)) >= 10));

-- 15. 确认状态必须有确认人与时刻
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_confirmed
    CHECK (status NOT IN ('CONFIRMED', 'PUBLISHED')
           OR (confirmed_at IS NOT NULL AND confirmed_by IS NOT NULL));

-- 16. 幂等键三要素非空
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_key
    CHECK (length(btrim(scheme_code)) >= 1 AND scheme_version >= 1);

-- 17. 周期顺序
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_period
    CHECK (period_end_date >= period_start_date);

-- 18. 不完整数据必须说明缺什么
ALTER TABLE m22_clinical_perf_pool
    ADD CONSTRAINT ck_m22_clinical_perf_pool_missing
    CHECK (source_status = 'COMPLETE'
           OR (source_missing IS NOT NULL AND length(btrim(source_missing)) >= 2));

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | **表内无任何金额字段** | 见上文「分工写死」表。绩效金额的唯一计算方是 M17-07。字段名全部避开 amount / money / salary / wage / pay，连 `unit_price` 都不叫（叫 `unit_score`，「每单位折多少分」） |
| 2 | `unit_type` 允许 `CURRENCY_UNIT` 但注释写明「仅作指标值」 | 有些医院的 KPI 方案会设「人均创收额」这类指标。这个值本身是钱，但它作为**指标值参与评分**（乘单位分值变分数），不参与绩效金额计算。为避免歧义，枚举值名字写成 `CURRENCY_UNIT`（货币单位）而非 `AMOUNT`，并在说明里点明它只是评分输入 |
| 3 | 约束 6 在库层强校验得分算式 | 得分必须严格等于 `实际值 × 单位分值 × 权重`。这一条把「M22 只算分、不算钱」的分工**钉死在数据库里**——任何想让 score 掺杂系数的尝试都会违反约束（因为约束的算式里根本没有系数字段） |
| 4 | 同时存 `raw_score` 与 `score` | 绩效管理员核对时习惯先看「680 × 8 = 5,440 分」再看「× 0.4 = 2,176 分」。存中间值让页面可以直接展示两段计算，避免前端重算 |
| 5 | 约束 9 / 10 让人员级与科室级互斥 | 若科室级指标误挂了 `staff_id`，按人员汇总时会被重复计入。用成对约束从库层杜绝 |
| 6 | 约束 8：实际值缺失则得分必为空 | 不能因为「没采到数据」就把得分算成 0 分。这会让被考核人员无端丢分，是绩效系统最招人恨的 bug |
| 7 | `status` 用四态且 `CONFIRMED` 起只读 | 与 M17-07 的对接需要「确认后不可改」的语义：M17 拉取绩效基础数据时只认 `CONFIRMED`，若 M22 后续又改了值，会导致 M17 已算的结果与 M22 显示不一致。确认 + 只读把两边锁在同一份数据上 |
| 8 | `scheme_version` 参与唯一键 | KPI 方案调整（改权重、改分值）必须升版本。同周期两个版本并存，M17-07 按指定版本取数，历史可追溯。**绝不原地改已确认周期的权重**——那会让已发的绩效无法解释 |
| 9 | 季度分区 + `DEFAULT` 分区 | 人员数约 200 × 指标 12 × 周期 1 ≈ 2,400 行/月，季度分区合理 |

### 4.9 表：`m22_clinical_perf_weight`（绩效权重快照表）

**用途：** 记录每个 KPI 方案版本下、每个指标在每类人员/科室上的**权重与单位分值**配置快照。

**为什么需要快照表：** `m22_clinical_perf_pool` 每行都冗余了 `unit_score` 与 `weight`，看起来快照表冗余。但两者职责不同：

- 快照表是**配置**：一个方案版本下「门诊量指标权重 0.40、单位分值 8.00」，与具体人员和周期无关；
- 池表是**应用结果**：张三 2026-10 的门诊量指标，其 `unit_score = 8.000000` 是**从快照复制过来的**。

快照的必要性在于：绩效管理员 2027-01 把门诊量权重从 0.40 调到 0.35，若只改配置不改快照，2026-10 的得分会在下次刷新时被重算成新权重下的值，**已发的绩效就与页面显示对不上了**。快照表 + 池表的 `scheme_version` 一起，保证「任一历史周期的得分都能复算出来并与当时一致」。

**同样不含任何金额字段。** 本表只有「权重」与「单位分值」，没有金额、没有系数。

### 4.10 表：`m22_clinical_review_std`（等级评审标准版本表）

**用途：** 记录医院等级评审标准的**版本**。二级综合医院评审标准会改版（2012 版 → 2022 版 → 未来的 2027 版），每个版本的条款体系、指标清单、达标准则都不同。

#### 为什么必须有版本概念

评审标准版本化的三个硬理由：

1. **历史达标情况不得重算。** 2026 年按 2022 版标准评定「达标」，2028 年标准改版后，2026 年的达标结论**仍然成立**——因为当时就是照 2022 版评的。若把指标挂在「无版本的当前标准」下，标准一改，历史结论会跟着变，评审举证时说不清「当年到底算不算达标」。
2. **新旧版本并行过渡。** 2022 版标准发布后，通常有 1~2 年过渡期，期间院内既要做 2012 版的自查收尾，又要开始 2022 版的准备。两套指标必须能同时存在、同时展示、互不干扰。
3. **复核与申诉需要确定基线。** 评审不通过时复核，必须明确「依据哪一版标准的哪一条款判定」，版本号就是这个基线的锚点。

**因此本表 + 4.11 指标表 + 4.12 达标表构成三层结构：**

```
m22_clinical_review_std (标准版本 standard_version='2022')
    └── m22_clinical_review_ind (该版本下的条款与指标，一条款一指标)
            └── m22_clinical_review_achv (某期某科室在该版本某条款上的达标情况)
```

**关键规则：`m22_clinical_review_achv` 通过 `std_id` 直连标准版本，绝不允许仅靠 `clause_code` 字符串去猜属于哪个版本**（不同版本可能有相同条款号但含义不同）。

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | `uk_..._std_current` 用**部分唯一索引**实现「全表只有一个当前版本」 | 这是数据库层表达「唯一真理」最干净的方式。若不用索引而靠应用层保证，一次并发或一次误操作就可能出现两个 `is_current = TRUE`，页面上「当前标准」就有了歧义。**部分唯一索引让这种状态在物理上无法存在** |
| 2 | 约束 2 用正则强制 4 位年份格式 | 版本号会被大量用于展示与关联（`standard_version = '2022'`）。若允许 `2022版`、`v2022`、`22` 混存，将来按版本过滤时必然漏数据。正则 `^[0-9]{4}$` 从库层卡死格式 |
| 3 | 约束 8：`is_current = TRUE` 必须 `status = 'ACTIVE'` | 防止「当前版本」指向一个 `DRAFT`（录入中未启用）或 `ARCHIVED`（已退役）的版本，那会让所有默认查询失效 |
| 4 | 约束 4 校验 `total_weight = 1` | 指标权重之和必须为 1，否则「整体加权达标率」的计算会失真。这条约束是在指标录完后由应用层回写校验值，再由库层把关 |
| 5 | `transition_months` 单独成列 | 过渡期不是简单的时间范围，它有明确政策含义（过渡期内新标准不追责）。把它落成列，页面能算出「过渡期还剩几个月」，提醒质控办。若只存 `effective_from` / `effective_to`，页面得自己在代码里猜 |
| 6 | 归档必须有停用日 + 原因 | 归档不是删除，历史达标记录仍要能引用。强制填停用日让「该版本在什么时间窗内有效」可被时间轴查询准确回答 |
| 7 | 不分区 | 20 年也超不过 5 行 |
| 8 | `calc_caliber_note` 允许 1000 字符 | 每版标准都有若干口径变化（如「I 类切口感染率」分母定义从「手术例数」改为「手术例数 − 术前已有感染」）。这段说明是**跨版本对比时唯一的解释依据**，值得给足长度 |

**量级估算**

| 项 | 估算 |
|---|---|
| 版本数 | 2~3 个（2012 / 2022 / 未来版本） |
| 10 年数据量 | 3~5 行，可忽略 |

**分区结论**

不分区。配置表，行数在个位数。

### 4.11 表：`m22_clinical_review_ind`（等级评审指标表）

**用途：** 记录**某一标准版本下**的条款与指标。一行 = 一个版本下的一个条款及其承载的指标。

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | **`std_id` 外键 + `standard_version` 冗余双列** | 只存 `std_id` 则按版本过滤要 join 标准表；只存 `standard_version` 字符串则无法在库层保证「版本存在」。两列都存：`std_id` 保结构完整性，`standard_version` 免 join 且可读。应用层写入时由 `std_id` 反查 `standard_version` 填入 |
| 2 | 约束 12 强制 `clause_code` 以版本号开头 | 2022 版与 2012 版**都有** `3.2.1` 这样的条款号，含义完全不同。若不带版本前缀，人工核对时极易串号。强制 clause_code 必须以 standard_version 加连字符开头（即形如 `2022-3.2.1`）让条款号自身就带版本信息，导出到 Excel 给人看时也不会混 |
| 3 | 唯一键是 `(std_id, clause_code)` 而非 `clause_code` 全局唯一 | 不同版本可以有相同条款号。全局唯一会逼着把 2012 版的条款号改成 `2012-3.2.1` 而 2022 版改成 `2022-3.2.1`，虽然本设计确实这么做了（约束 12），但唯一键仍按 `std_id` 组织，语义更准确 |
| 4 | `target_value` 注释三重澄清（非金额、非绩效、是分数线） | 该字段名很容易被误读为「绩效目标值」。用 `pass_rule` + `target_value` 组合表达达标准则，并在注释里点明它是**达标分数线**。若将来有人想在这里塞金额，注释本身就是阻力 |
| 5 | 约束 9 要求有指标必须写口径 ≥ 10 字符 | 每条评审指标必须写清口径（分子、分母、样本条件），这是共享规范 §0.3 铁律 4「每指标九要素口径」的直接落地。**口径不写清楚，评审现场无法自证** |
| 6 | 约束 13 要求分子分母描述成对出现 | 只写分子不写分母的「口径」等于没写。成对约束逼着写完整 |
| 7 | `source_type` 含 `MANUAL` | 部分评审条款无系统数据来源（如「院感管理组织是否健全」），只能人工举证。用 `MANUAL` 显式标注，并从约束上禁止这类条款填 `data_source_api`，**不假装它有上游接口** |
| 8 | `evidence_desc` 单独成列 | 评审现场要的是材料而非数字。「举证材料说明」写「提供近 3 年院感委员会会议记录、培训签到表」这类信息，对质控办的价值不亚于指标本身 |
| 9 | 不分区 | 2 个版本 × 约 60 条款 = 120 行 |

**量级估算**

| 项 | 估算 |
|---|---|
| 每版本条款数 | 约 60 条（2022 版二级综合医院标准核心 + 一般） |
| 版本数 | 2~3 个 |
| 20 年数据量 | 约 180 行，0.2 MB |

**分区结论**

不分区。百行级配置表。

### 4.12 表：`m22_clinical_review_achv`（等级评审达标记录表）

**用途：** 记录「某期、某科室、在**某一标准版本**的某一条款上」的达标情况。

#### 这张表是「版本切换不重算历史」的物理落点

**写入方 / 只读方：**

|---|---|---|
| M22-07 达标计算任务 | INSERT | 按 `std_id` 逐条款计算并写入 |

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | **唯一键含 `std_id`** | 这是「版本切换不重算历史」的物理保证。若不含量本，2028 年新标准启用后重算 2026 年数据，会因 `(clause_code, period, dept_id)` 已存在而 **UPDATE 掉 2026 年的旧结论**——历史达标情况就被篡改了。含 `std_id` 后，2026 年在 2022 版下的记录与 2028 年在 2027 版下的同期间记录**共存**，各说各话，都对 |
| 2 | 约束 5 要求条款号带版本前缀 | 与 4.11 同一规约。达标记录会导出给评审专家看，若 2022 版与 2012 版都叫 `3.2.1`，纸上无法分辨 |
| 3 | 约束 7 / 8 双向约束达标状态与值的自洽 | 「没有实际值却判定 ACHIEVED」和「有实际值却标 NO_DATA」都是严重的数据错误。前者的后果是**评审时被质询却拿不出数据**，后者会掩盖短板 |
| 4 | 约束 6 用三分支覆盖分母为空、为 0、大于 0 | 与 `m22_clinical_infection` 手卫生约束同源问题：SQL 中 `NULL > 0` 为 NULL，若不显式写 `den_value IS NULL` 分支，整个 CHECK 会被 NULL 短路成通过，脏数据放行 |
| 5 | `manual_value` 与 `actual_value` 分列 | 人工举证的条款（如「有院感管理组织并有效运行」）没有系统值，只有人工判定。分列后，页面可以清楚区分「系统算出来的」与「人工填的」，评审举证时不会混淆 |
| 6 | `gap_value` 单独落库 | 质控办日常动作是「找短板并排序」。差距值可以在应用层算，但落库后可直接 `ORDER BY gap_value DESC` 建部分索引，页面秒出「最需要改进的 10 条」。这是把**高频查询的计算结果物化** |
| 7 | 按年分区（而非季度） | 评审达标通常是年度或评审周期口径，行数也少（约 60 条款 × 13 科室 × 1 = 780 行/年）。年分区足够，且 `period_start_date` 为年度起日 |
| 8 | `caliber_version` 与 `standard_version` 分开 | 同一版标准在实施中可能微调口径（如「手术例数」是否含门诊手术），这种小修订不需要升标准版本，但要留痕。`caliber_version` 如 `2022.1`、`2022.2` |

**量级估算**

| 项 | 估算 |
|---|---|
| 条款数 | 约 60 条/版本 |
| 科室数 | 13 个（含全院） |
| 年行数 | 60 × 13 = 780 行 |
| 10 年数据量 | 约 7,800 行，约 8 MB |

**分区结论**

按 `period_start_date` **年 RANGE 分区** + `DEFAULT` 分区。年行数仅 780 行，年分区足够；`DEFAULT` 分区保证补算历史年份不会因缺分区失败。

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | **不复用 M22-03 的四张报表骨架表** | M22-03 的表承载报表**行列结构**（模板定义 + 实例 + 行数据 + 订阅），本表只记录**导出动作与文件**。把导出塞进报表骨架会让 `m22_report_row` 被填入「文件路径」这种非行数据，污染通用表。共享规范明确要求「通过 `template_code` 引用，不得重复建表」，本表严格遵守：只用 `template_code` 一列引用，不建同名表 |
| 2 | `has_manual_data` + `data_quality_note` 强制联动 | 院感类导出必然含手工填报数据。若导出给评审专家后没有任何提示，就会造成「用手工填报的数据冒充系统数据」。约束 6 要求只要含手工数据就必须写 ≥ 10 字的说明，**让「数据来路」随文件一起交付** |
| 3 | `file_path` 与 `download_url` 分列 | 服务器路径绝对不能给前端（目录结构泄露）。`download_url` 是带签名、有时效的地址。两者分开是安全基线 |
| 4 | `file_md5` 落库 | 用于去重（同参数重复导出可复用已有文件）与防篡改（下载时校验）。医疗质控数据外发须可追溯完整性 |
| 5 | 约束 9 评审导出必须带 `std_id` | 评审材料必须注明依据哪一版标准。不带版本号的评审导出在法律与行政意义上无法自洽 |
| 6 | 过期用状态 `EXPIRED` 而非删除记录 | 记录要保留（谁在何时导出过什么），只清理文件。删记录会让审计断档 |
| 7 | 不分区 | 每年约 2,000 条导出记录，十年 2 万行，单表足够 |

**量级估算**

| 项 | 估算 |
|---|---|
| 日导出次数 | 约 5 次 |
| 年行数 | 约 1,800 行 |
| 10 年数据量 | 约 1.8 万行，约 9 MB |

**分区结论**

不分区。含 `TEXT` / `JSONB` 的长文本列，但行数少（十年 1.8 万行），单表 + 部分索引完全够用。按时间分区反而会让「我最近 10 次导出」这类查询跨分区。

### C.1 非比率类边界约束：金额污染防线

上表列的是「分母为 0 置空」这一类比率约束。本子模块还有一类边界约束不属于比率口径，
但同样承担「防止口径被悄悄改变」的职责，单列于此，必须在评审与代码审查时一并核对。

| 表 | 约束名 | 约束表达式 | 防的是什么（不是随意魔数） |
|---|---|---|---|
| `m22_clinical_perf_pool` | `ck_m22_clinical_perf_pool_weight_pure` | `weight <= 0.5 OR (weight = 1 AND indicator_level IN ('DEPT','HOSPITAL'))` | **防「系数并入 weight 造成的金额污染」。** 本表的 `weight` 在语义上是「指标在同层级中的占比」，不是「占比 × 科室系数 × 质量系数」。若不设上限，把 `weight` 由 0.400000 改成 0.411600（= 0.4 × 1.05 × 0.98）仍能通过 `ck_m22_clinical_perf_pool_score_calc` 的算式校验，但 `score` 已含系数，M22 就事实上算了钱，「M22 不算钱」这条铁律被击穿。上限取 0.5 的依据是：单指标占同层级权重的一半以上，意味着其余所有指标被压到 0.5 以下，在 KPI 方案中不合理；而科室级/全院级方案只考核单一指标时 `weight = 1` 是合法形态，故开此特例。**修改此上限前必须先确认 M17-07 侧没有引入「系数回流到 weight」的实现。** |
| `m22_clinical_perf_pool` | `ck_m22_clinical_perf_pool_score_calc` | `score IS NULL OR abs(score - ROUND(actual_value * unit_score * weight, 6)) <= 0.000001` | 防「得分被手工微调」。注意：本条只保证算式自洽，**不保证 weight 是纯权重**，纯权重的职责由上一条承担。两条约束互补，缺一不可。 |
| `m22_clinical_perf_pool` | `ck_m22_clinical_perf_pool_no_value` | `actual_value IS NOT NULL OR (score IS NULL AND raw_score IS NULL)` | 防「实际值缺失却把得分算成 0」。0 分与「没采到数据」是两种完全不同的语义，混淆会让被考核人无端丢分。 |

**约束之外的第三道防线（接口层白名单）**

上述 CHECK 属于「数据层」防线，只能拦住「库里的值」。真正更根本的是「接口层」：
M22 从头就不应当产出系数字段。详见详细设计 API-22 / API-23 的出参白名单与验收项 DA-16。
