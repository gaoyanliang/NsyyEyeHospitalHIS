## 1. 模块概述

### 1.1 模块定位

M22-04 科室报表与科室排名是 M22 报表与决策支持模块中**面向科室主任这一层管理者**的报表子模块。它把散落在 M05 住院、M07 医务、M09 手术麻醉、M16 收费、M17 财务核算等业务模块里的科室级数据，按统一的指标口径聚合成「科室」这一视角的经营与质量全貌，并在此之上提供**对比、排名、目标达成、医师个人下钻**四类管理动作的支撑能力。

一句话概括职责边界：**M22-04 不产生任何业务数据，也不计算任何业务金额；它只做「取数 → 校准 → 存储 → 展现 → 下钻」。**

科室主任每天上班第一件事是打开 P01 科室主任工作台，看到本科室昨天和本月的核心指标、与上期和目标的偏差、在全院中的位置。院长每月初看 P04 科室排名榜，判断哪些科室需要约谈。这两个场景是本子模块存在的直接理由。

### 1.2 为什么必须独立成一个子模块

科室报表看起来只是「把数据摆出来」，但它与 M22 的其他子模块（运营报表、财务主题分析等）存在三处本质差异，因此必须独立设计、独立建表：

| # | 差异点 | 说明 | 不独立会怎样 |
|---|---|---|---|
| 1 | 维度主体是「科室」而非「全院」 | 全院报表的时间序列是单一曲线；科室报表是 N 条曲线的横向比较，N 随科室合并拆分而变化 | 若与全院报表共用一张事实表，科室维度的历史归属无法回溯，科室合并后所有历史数据归属错乱 |
| 2 | 需要「排名」这一有状态的产物 | 排名必须固化快照，否则口径升级后历史榜单会漂移 | 若每次查询现算，去年 12 月的排名榜在今年 3 月会变样，院长看到的两份报告对不上 |
| 3 | 需要「目标 vs 实际」的双向承诺关系 | 目标是科室与医院之间的约定，有版本、有审批、有调整留痕 | 若目标当成普通指标存，目标调整无法留痕，责任无法追溯 |

更具体地说，M22-03 运营报表与日报月报负责的是「全院/业务线」的纵向时间序列与日报月报定时推送；M22-04 负责的是「科室之间」的横向比较与排名。两者的事实表主键粒度不同（前者以全院或业务线为主键，后者必须以 `dept_id` 为分组键），混在一起会让唯一约束无法表达，查询时也要频繁过滤，得不偿失。

### 1.4 概念辨析

本子模块有几组术语极易混淆，必须在设计阶段就钉死，否则开发时会出现两套理解。

| # | 概念 A | 概念 B | 区别 | 判定规则 |
|---|---|---|---|---|
| 1 | 科室（Dept） | 科室归属（Dept Belonging） | 科室是组织单元；科室归属是「某数据在统计时归属哪个组织单元」 | 一切统计以**归属科室**为准，不以发生科室为准；跨科支援通过 `cross_dept_flag` 标记 |
| 2 | 排名（Rank） | 名次（Rank No） | 排名是一整套带规则、样本量、剔除策略的结果集；名次只是其中一个数字 | `rank_no` 为 NULL 不等于没排名，而是「生成了排名结果但该科室不参与名次」 |
| 3 | 对比（Compare） | 差值（Delta） | 对比是「本期 vs 基线」的关系；差值是该关系的量化 | 必须先确定 `baseline_key`，才能算 `delta_abs` |
| 4 | 目标（Target） | 指标（Metric） | 目标是某期间某科室某指标的一个约定值；指标是定义 | 目标必须挂在 `(period, dept_id, metric_code, metric_version)` 上 |
| 5 | 下钻（Drill） | 明细（Detail） | 下钻是「从汇总跳到上游明细」的动作；明细本身不由 M22 存储 | M22 只存下钻路由配置，明细永远由上游接口返回 |
| 6 | 科室类型（dept_type） | 同类科室分组（peer_group） | 科室类型是 6 类粗分类；同类科室分组是「可比」的细分组 | 类型用于过滤，分组用于 PEER 对比与 PEER 排名 |
| 7 | 样本不足（Insufficient） | 数据缺失（Missing） | 样本不足是「有数但太少」；数据缺失是「上游没给」 | 前者展示数值并标注；后者展示「—」并标注 `source_status` |
| 8 | 固化（Frozen） | 生成（Generated） | 生成只是算出来写进表；固化是「此后不可更改」 | 只有 `rank_frozen_at` 非空才可用于对外发布 |

**关于第 2 条的补充说明：** 这是本子模块最容易被误解的地方。一个科室「不参与排名」有多种原因，对应 `exclude_reason` 的五个值。前端展示时必须区分：

- `DENOMINATOR_ZERO`：分母为零（例如当月出院 0 例，则「平均住院日」无法计算），展示为「—」
- `VALUE_MISSING`：上游确实没给数，展示为「—」并提示数据未到
- `NOT_PARTICIPATE`：科室属性标注为不参与排名（如行政后勤科室不参与临床排名），展示为「不参评」
- `SCOPE_EXCLUDED`：本次排名的范围不含该科室（例如只排住院科室），不展示
- `INGEST_FAILED`：采集失败，展示为「数据异常」并提供重试入口

### 1.5 设计目标

| # | 目标 | 可量化指标 | 验证方式 |
|---|---|---|---|
| 1 | 科室数据唯一来源 | 科室主数据 0 处复制 | 表清单中无 `*_dept_master` 类表 |
| 2 | 金额零自算 | M22-04 代码中金额加减运算 0 处 | 代码评审 + 静态扫描 |
| 3 | 排名可追溯 | 任意历史期间排名可复现 | 排名快照表 + `sort_rule_json` 快照 |
| 4 | 分母为零不显示 0 | `denominator_zero_flag = TRUE` 时 `metric_value` 必为 NULL | 数据库 CHECK 强制 |
| 5 | 响应速度 | 工作台首屏 P95 ≤ 800ms，排名榜 P95 ≤ 500ms | 压测报告 |
| 6 | 数据完整性可见 | 每条指标行必带 `source_status` | 数据库 NOT NULL 约束 |
| 7 | 下钻不落明细 | 下钻表内业务数据字段 0 个 | 表结构评审 |
| 8 | 目标调整留痕 | 目标每次调整产生新版本行 | `target_version` 递增 + 日志表 |

**数据范围过滤规则：** 所有查询接口在 Service 层入口统一调用 `resolve_data_scope(user)`，返回该用户可见的 `dept_id` 集合。规则优先级为：

1. 若用户拥有 `m22:04:admin`，返回全院科室
2. 否则若用户是科室主任（M01-02 返回 `is_dept_chief = true`），返回其主管科室及其全部下级科室
3. 否则返回其所属科室
4. 若上述均不满足，返回空集合，接口返回空列表而非报错

> **为什么第 4 条返回空列表而不是报错：** 报表场景下「无权限看到任何科室」是合法状态（例如新入职人员尚未分配科室）。若返回 403，前端工作台会整页报错；返回空列表则前端展示「暂无可见科室，请联系管理员」，体验更好且不泄露科室是否存在。

### 2.3 边界说明

**与 M22-02 的边界：** M22-02 采集后落入 `m22_fact_metric`，该表以 `(metric_code, period, dept_id, biz_dim)` 唯一。M22-04 的 `m22_report_dept_summary` 与它看似重复，实则职责不同：

| 维度 | `m22_fact_metric`（M22-02） | `m22_report_dept_summary`（M22-04） |
|---|---|---|
| 主体 | 采集流水线 | 科室报表展现 |
| 来源 | 直接落上游原始值 | 可由事实表聚合，也可直调上游，但必须记录用的是哪条路 |
| 口径 | 单一指标原值 | 含目标、对比基期、排名、样本判定等报表要素 |
| 变更 | 允许按批覆盖 | 生成后快照化，重算需新批次 |
| 下游 | M22-04、M22-05、M22-06 等 | 仅 M22-04 的页面与导出 |

因此 M22-04 建汇总表是必要的：报表需要把「指标值 + 目标 + 基期 + 排名 + 样本判定」放在一行里，这是事实表不具备的表达力。

**与 M17-04 的边界：** 这是最关键的一条。M17-04 提供 `GET /internal/v1/m17/dept/profit`，返回科室的 `revenue_amount` / `direct_cost_amount` / `allocated_cost_amount` / `total_cost_amount` / `surplus_amount` / `surplus_rate` / `cost_rate` / `target_achievement_rate` / `data_status`。M22-04 **只在展示层引用这些字段，不做任何加减**。

具体约束：

1. M22-04 的 Service 代码中不得出现对 `*_amount` 字段的 `+`、`-`、`*`、`/` 运算
2. 若页面需要「两个科室的结余差额」，必须由 M17-04 提供，或由前端在拿到两个独立值后自行展示差额（且页面须注明「差额为前端计算」）
3. 若 M17-04 返回 `data_status = 'PROVISIONAL'`（暂估），M22-04 必须在页面上标注「暂估数据，财务未结账」，**不得**在报表中当作最终值使用
4. 若 M17-04 返回 `period_closed = false`，所有涉及金额的排名必须标注「期间未结账，排名仅供参考」

**与 M10/M11/M12/M16 的边界：** 这些业务模块提供原始业务计数（门诊量、手术量、视光订单量等）。M22-04 通过 M22-02 采集的事实表或直接调上游统计接口获取，绝不直查业务表。

## 3. 业务模型

### 3.1 核心实体

| # | 实体 | 对应表 | 说明 | 生命周期 |
|---|---|---|---|---|
| 1 | 科室报表配置 | `m22_report_dept_config` | 定义某类报表包含哪些指标、默认对比方式、样本量下限覆盖 | 长期存在，随业务调整 |
| 2 | 科室范围快照 | `m22_report_dept_scope` | 某一时点的科室树结构与归属 | 按月生成，历史只读 |
| 3 | 科室指标汇总 | `m22_report_dept_summary` | 某期间某科室某指标的取值与报表要素 | 按期间批次生成 |
| 4 | 科室对比记录 | `m22_report_dept_compare` | 某期间某科室某指标相对某基线的对比结果 | 按期间批次生成 |
| 5 | 科室排名快照 | `m22_report_dept_ranking` | 某批次的科室名次与排序依据 | 生成后固化，只增不改 |
| 6 | 科室目标 | `m22_report_dept_target` | 某期间某科室某指标的目标值与达成情况 | 设定 → 审批 → 跟踪 → 期末判定 |

### 3.4 计算模型

本子模块的全部计算模型都只涉及**指标值的比较与排序**，不涉及任何业务金额的加减。金额类指标来自 M17-04 的现成结论，本模块只做透传比较。

#### 3.4.1 计算模型一：科室排名算法（核心）

**问题定义：** 给定期间 `p`、指标集合 `M = {m1, m2, ..., mk}`、科室集合 `D`，为每个科室给出一个确定的名次。

**步骤一：确定候选科室集合与样本量**

对每个科室 `d` 与每个指标 `m`，从 `m22_report_dept_summary` 取该行，得到 `metric_value`、`denominator_value`、`denominator_zero_flag`、`sample_size`、`sample_limit`、`sample_sufficient`、`source_status`。

第一层剔除（绝对剔除，不参与任何名次）：

```text
IF source_status = 'FAILED'                   THEN exclude_reason = 'INGEST_FAILED'
ELIF denominator_zero_flag = TRUE             THEN exclude_reason = 'DENOMINATOR_ZERO'
ELIF metric_value IS NULL                     THEN exclude_reason = 'VALUE_MISSING'
ELIF dept.rank_participate = FALSE            THEN exclude_reason = 'NOT_PARTICIPATE'
ELIF dept.dept_type NOT IN scope_dept_types   THEN exclude_reason = 'SCOPE_EXCLUDED'
ELSE                                               参与排名
```

第二层：样本量判定（**不剔除，只降级展示**）：

```text
sample_sufficient = (sample_size >= sample_limit)
```

**关键设计：样本不足不剔除科室，只打标。** 这是本模型与「第一层剔除」的本质区别。理由见 §3.4.2。

**步骤二：计算排序键**

单指标排名直接用 `metric_value`，但必须按 `value_direction` 决定升降序：

| # | `value_direction` | 排序方向 | 例子 |
|---|---|---|---|
| 1 | `HIGHER_BETTER` | `ORDER BY metric_value DESC` | 门诊人次、手术量、结余 |
| 2 | `LOWER_BETTER` | `ORDER BY metric_value ASC` | 平均住院日、次均费用、药占比 |
| 3 | `NEUTRAL` | `ORDER BY metric_value DESC`（仅用于描述性榜单，须在页面标注「仅排序不代表优劣」） | 出院人数（多未必好） |

多指标加权排名时，先把每个指标归一化到可加的量纲，再按权重求和得到 `rank_score`：

```text
对每个指标 m_i（在参与排名的科室集合内）：
  MIN_MAX  ： norm_i = (x_i - min_i) / (max_i - min_i)       ，适用于 HIGHER_BETTER
             norm_i = (max_i - x_i) / (max_i - min_i)        ，适用于 LOWER_BETTER
  Z_SCORE  ： z_i = (x_i - mean_i) / stddev_i
             norm_i = clamp((z_i + 3) / 6, 0, 1)              ，映射到 [0,1]
  RANK_PCT ： norm_i = 1 - (rank_i - 1) / (n - 1)             ，n > 1
  NONE     ： norm_i = x_i                                     ，仅当各指标量纲一致

rank_score = Σ ( w_i × norm_i )，其中 Σ w_i = 1
```

**算例一（单指标排名）：**

2026-10 期间，全院 12 个临床科室的 `CL_OR_COUNT`（手术台次，`HIGHER_BETTER`）如下：

| # | 科室 | 手术台次 | sample_size | sample_limit | sample_sufficient | metric_value |
|---|---|---|---|---|---|---|
| 1 | 白内障科 | 186 | 186 | 20 | TRUE | 186.000000 |
| 2 | 屈光手术科 | 186 | 186 | 20 | TRUE | 186.000000 |
| 3 | 青光眼科 | 142 | 142 | 20 | TRUE | 142.000000 |
| 4 | 眼底病科 | 98 | 98 | 20 | TRUE | 98.000000 |
| 5 | 斜弱视科 | 54 | 54 | 20 | TRUE | 54.000000 |
| 6 | 眼表科 | 0 | 0 | 20 | FALSE | NULL（分母为零） |
| 7 | 角膜病科 | 31 | 31 | 20 | TRUE | 31.000000 |

按 `RANK` 输出：

| # | 科室 | metric_value | rank_no | dense_rank_no | row_no | 说明 |
|---|---|---|---|---|---|---|
| 1 | 白内障科 | 186.000000 | 1 | 1 | 1 | 并列第一 |
| 2 | 屈光手术科 | 186.000000 | 1 | 1 | 2 | 并列第一 |
| 3 | 青光眼科 | 142.000000 | 3 | 2 | 3 | 跳号到 3 |
| 4 | 眼底病科 | 98.000000 | 4 | 3 | 4 | — |
| 5 | 斜弱视科 | 54.000000 | 5 | 4 | 5 | — |
| 6 | 角膜病科 | 31.000000 | 6 | 5 | 6 | — |
| 7 | 眼表科 | NULL | NULL | NULL | NULL | 分母为零，不参与名次 |

**问题：为什么是 RANK 而不是 DENSE_RANK？**

因为榜单的语义是「你前面有几个人」。并列第一的两家科室，第三名科室前面有 2 个科室，说「第 3 名」符合直觉；若用 `DENSE_RANK` 说「第 2 名」，会让该科室主任误以为只输给了 1 家。而 `DENSE_RANK` 的用途在**等级划分**——「前 3 档」这样的表述用密集名次才不会因并列而少分档。

`row_no` 同时存储的理由是分页稳定性：`RANK` 有并列，前端做「第 2 页从第 21 条开始」的分页时若用 `rank_no` 做游标会重复或丢行，必须用全局唯一的 `row_no`。

**算例二（多指标加权排名）：**

2026-10 期间，某三个指标的原始值与归一化：

| # | 科室 | 门诊人次 x1 | 手术台次 x2 | 平均住院日 x3 | w1=0.4 | w2=0.4 | w3=0.2 |
|---|---|---|---|---|---|---|---|
| 1 | 白内障科 | 4820 | 186 | 1.20 | — | — | — |
| 2 | 屈光手术科 | 3150 | 186 | 1.00 | — | — | — |
| 3 | 青光眼科 | 2680 | 142 | 2.80 | — | — | — |
| 4 | 眼底病科 | 2240 | 98 | 3.60 | — | — | — |

归一化（`MIN_MAX`，`x3` 为 `LOWER_BETTER`，`min_i`/`max_i` 在参与集合内取）：

- `x1`：min = 2240，max = 4820，分母 = 2580
- `x2`：min = 98，max = 186，分母 = 88
- `x3`：min = 1.00，max = 3.60，分母 = 2.60

计算结果：

| # | 科室 | norm1 | norm2 | norm3 | rank_score | rank_no |
|---|---|---|---|---|---|---|
| 1 | 白内障科 | 1.000000 | 1.000000 | 0.923077 | 0.984615 | 1 |
| 2 | 屈光手术科 | 0.352713 | 1.000000 | 1.000000 | 0.741085 | 2 |
| 3 | 青光眼科 | 0.170543 | 0.500000 | 0.307692 | 0.329692 | 3 |
| 4 | 眼底病科 | 0.000000 | 0.000000 | 0.000000 | 0.000000 | 4 |

验算白内障科：`0.4 × 1.0 + 0.4 × 1.0 + 0.2 × 0.923077 = 0.4 + 0.4 + 0.1846154 = 0.984615`。

验算屈光手术科 `norm1`：`(3150 - 2240) / 2580 = 910 / 2580 = 0.352713`。

验算青光眼科 `norm3`（`LOWER_BETTER` 取反向）：`(3.60 - 2.80) / 2.60 = 0.80 / 2.60 = 0.307692`。

**边界处理：** 若 `max_i = min_i`（所有科室该指标相同），则 `norm_i` 统一定为 `1.000000`，避免除以零。此时 `rank_score` 实际只由其余指标决定，页面须提示「指标 X 全院无差异」。

**步骤三：排序与 tie-break**

`sort_rule_json` 固化四层排序键，**最后一层必须是全局唯一的确定性键**：

| # | 层级 | 排序字段 | 方向 | NULL 处理 | 作用 |
|---|---|---|---|---|---|
| 1 | 主排序 | `rank_score` 或 `metric_value` | 按 `value_direction` | `LAST` | 决定名次 |
| 2 | 次序 | `sample_size` | `DESC` | `LAST` | 同分时样本多的优先 |
| 3 | 次次序 | `metric_version` | `DESC` | `LAST` | 同分时口径新的优先 |
| 4 | 兜底 | `dept_code` | `ASC` | `LAST` | **全局唯一，保证确定性** |

> **为什么 NULL 一律 LAST：** PostgreSQL 在 `ORDER BY x DESC` 时默认 `NULLS FIRST`。若不显式写 `NULLS LAST`，所有拿不到数的科室会排在榜首，这是最典型的线上事故。`sort_rule_json` 强制记录 `nulls` 字段，Service 层按它拼 SQL。

**步骤四：SQL 骨架**

```sql
WITH base AS (
    SELECT
        s.dept_id,
        s.dept_code,
        s.dept_name,
        s.dept_type,
        s.metric_value,
        s.sample_size,
        s.sample_limit,
        s.sample_sufficient,
        s.source_status,
        s.denominator_zero_flag,
        CASE
            WHEN s.source_status = 'FAILED'          THEN 'INGEST_FAILED'
            WHEN s.denominator_zero_flag = TRUE      THEN 'DENOMINATOR_ZERO'
            WHEN s.metric_value IS NULL              THEN 'VALUE_MISSING'
            WHEN d.rank_participate = FALSE          THEN 'NOT_PARTICIPATE'
            ELSE NULL
        END AS exclude_reason
    FROM m22.m22_report_dept_summary s
    LEFT JOIN m22.m22_report_dept_scope d
           ON d.dept_id = s.dept_id
          AND d.period  = s.period
    WHERE s.period          = :period
      AND s.metric_code     = :metric_code
      AND s.metric_version  = :metric_version
      AND s.biz_dim         = :biz_dim
      AND s.is_deleted      = FALSE
),
scoped AS (
    SELECT *
    FROM base
    WHERE exclude_reason IS NULL
       OR exclude_reason = 'VALUE_MISSING'
),
ranked AS (
    SELECT
        dept_id,
        dept_code,
        dept_name,
        dept_type,
        metric_value,
        sample_size,
        sample_limit,
        sample_sufficient,
        exclude_reason,
        (exclude_reason IS NULL) AS rank_eligible,
        CASE WHEN exclude_reason IS NULL THEN
            RANK() OVER (
                PARTITION BY (exclude_reason IS NULL)
                ORDER BY metric_value DESC NULLS LAST,
                         sample_size DESC NULLS LAST,
                         dept_code   ASC  NULLS LAST
            )
        END AS rank_no,
        CASE WHEN exclude_reason IS NULL THEN
            DENSE_RANK() OVER (
                PARTITION BY (exclude_reason IS NULL)
                ORDER BY metric_value DESC NULLS LAST,
                         sample_size DESC NULLS LAST,
                         dept_code   ASC  NULLS LAST
            )
        END AS dense_rank_no,
        ROW_NUMBER() OVER (
            ORDER BY (exclude_reason IS NULL) DESC,
                     metric_value DESC NULLS LAST,
                     sample_size DESC NULLS LAST,
                     dept_code   ASC  NULLS LAST
        ) AS row_no,
        COUNT(*) FILTER (WHERE exclude_reason IS NULL) OVER () AS total_dept_count
    FROM scoped
)
SELECT * FROM ranked ORDER BY row_no;
```

**SQL 要点说明：**

| # | 要点 | 为什么这样做 |
|---|---|---|
| 1 | `PARTITION BY (exclude_reason IS NULL)` | 让参与排名的科室与不参与的科室分开编号，不参与的 `rank_no` 自动为 NULL |
| 2 | `ORDER BY ... NULLS LAST` | 避免 PG 默认 DESC 时 NULL 排首位 |
| 3 | 四层排序键的最后一层是 `dept_code` | `RANK` 在完全并列时会给出相同名次，无需兜底；但 `ROW_NUMBER` 必须有唯一兜底键，否则同一查询两次执行可能给出不同行号 |
| 4 | `COUNT(*) FILTER (...) OVER ()` | 一次扫描同时算出「总参与科室数」用于 `total_dept_count`，避免第二次查询 |
| 5 | `scoped` 里保留 `VALUE_MISSING` | 这类科室要展示在列表里并提示「数据未到」，但 `rank_eligible = FALSE` |

#### 3.4.2 计算模型二：样本量下限及其论证

**为什么需要样本量下限：** 科室排名的本质是用 `metric_value` 比较，但 `metric_value` 常常是比率。比率的方差与样本量成反比——分母只有 3 的科室，1 个偶然事件就能让比率从 0% 跳到 33%，把它和分母 300 的科室放在同一张榜上比较，结果没有管理意义。这是统计上的小样本问题，必须显式处理。

**为什么选择「标注而不剔除」：**

| # | 方案 | 优点 | 缺点 | 是否采用 |
|---|---|---|---|---|
| 1 | 直接隐藏样本不足科室 | 榜单干净 | 科室主任在自己科室的榜上找不到自己，会引发投诉；且不利于小科室改进 | 否 |
| 2 | 照常排名不加任何标记 | 实现简单 | 误导管理者，「样本不足的科室排第一」会上头条 | 否 |
| 3 | 展示数值 + 标注「仅供参考」+ 仍参与名次但标注 | 信息完整且诚实 | 需要前端配合展示标注 | **采用** |
| 4 | 展示数值 + 不参与名次（`rank_eligible = FALSE`） | 最严谨 | 小科室永远无法上榜，激励效果差 | 仅在配置为严格模式时采用 |

本子模块默认采用方案 3：`sample_sufficient = FALSE` 时**仍然计算名次**，但 `rank_no` 照常写入，同时在 `sample_insufficient_note` 写入「N=12，低于下限 20，仅供参考」。页面上该行加浅色底纹并显示该文案。

若某指标配置为严格模式（`strict_sample_mode = true`），则方案 3 降级为方案 4：`rank_eligible = FALSE`、`rank_no = NULL`、`exclude_reason` 不填（因为它不是被剔除，而是「暂不评」），展示为「N<20，暂不评」。

**N 的取值依据：**

| # | 指标类型 | 典型指标 | N 建议值 | 论证 |
|---|---|---|---|---|
| 1 | 出院量类 | `CL_DISCHARGE_COUNT` | 30 | 中心极限定理的经验门槛：n ≥ 30 时样本均值的抽样分布近似正态，比率指标的 95% 置信区间半宽约为 `1.96 × sqrt(0.5×0.5/30) ≈ 0.179`，即 ±18 个百分点，已是最宽松的可接受精度 |
| 2 | 手术类 | `CL_OR_COUNT` | 20 | 眼科单科室月手术量本身较小（二级医院多在 20~200 台），若取 30 会让 60% 的科室不达标。取 20 时置信区间半宽约 ±22 个百分点，对「手术量排名」这种绝对量指标而言，比较的是数量级差异而非精细比率，可接受 |
| 3 | 危急值类 | `CL_CRITICAL_VALUE_COUNT` | 10 | 危急值属低频事件，全院月均可能只有几十例；若要求 30，全部科室都不达标，下限失去意义。取 10 时仍能过滤掉「只有 1~2 例」的极端波动 |
| 4 | 平均住院日类 | `CL_AVG_LOS` | 30 | 同出院量类，均值指标的稳定性直接取决于出院例数 |
| 5 | 金额类 | `FIN_DEPT_SURPLUS` | 0（不设下限） | 金额本身是连续量且已由 M17-04 核算，不存在小样本波动问题 |
| 6 | 医师工作量类 | `PERF_WORKLOAD_SCORE` | 1（只要有人就参与） | 医师个人报表按人排名，一人一行本身就是全样本，无抽样问题 |

**N 的存放位置与可配置性：** 绝对值**禁止硬编码在代码里**。取值优先级为：

1. `m22_report_dept_config.sample_limit_map` 中按 `metric_code` 指定的科室级覆盖（最高优先级）
2. M22-01 `m22_metric_def` 的 `sample_limit` 扩展字段（指标级默认）
3. 系统兜底值 30（仅当上述两级都取不到时使用，且必须落日志警告）

Service 层实现：

```python
def resolve_sample_limit(
    metric_code: str,
    metric_def_sample_limit: int | None,
    config_sample_limit_map: dict[str, int] | None,
) -> int:
    """按优先级解析样本量下限，绝不硬编码。"""
    if config_sample_limit_map:
        override = config_sample_limit_map.get(metric_code)
        if override is not None:
            return int(override)
        default_override = config_sample_limit_map.get("default")
        if default_override is not None:
            return int(default_override)
    if metric_def_sample_limit is not None and metric_def_sample_limit >= 0:
        return int(metric_def_sample_limit)
    logger.warning(
        "sample_limit fallback to 30, metric_code=%s reason=no_config_no_metric_def",
        metric_code,
    )
    return 30
```

**展示文案生成规则：**

| # | 条件 | `sample_insufficient_note` | 页面表现 |
|---|---|---|---|
| 1 | `sample_sufficient = TRUE` | NULL | 正常显示 |
| 2 | `sample_sufficient = FALSE` 且非严格模式 | `N={sample_size}，低于下限 {sample_limit}，仅供参考` | 浅色底纹 + 文案角标 |
| 3 | `sample_sufficient = FALSE` 且严格模式 | `N={sample_size}，低于下限 {sample_limit}，暂不评` | 灰字 + 「暂不评」标签 |
| 4 | `sample_size = 0` 且 `denominator_zero_flag = TRUE` | NULL（已被 `DENOMINATOR_ZERO` 剔除） | 「—」 |

#### 3.4.3 计算模型三：科室对比与本子模块的时间窗口归一化

**通用对比公式：**

```text
delta_abs  = actual_value − baseline_value
delta_rate = (actual_value − baseline_value) / baseline_value        （baseline_value ≠ 0）
delta_rate = NULL                                                     （baseline_value = 0）
```

**分母为零的处理（硬规则）：** 当 `baseline_value = 0` 时，`delta_rate` 必须为 NULL，页面显示「—」，且 `comparability_flag = FALSE`、`comparability_reason = 'BASELINE_ZERO'`。

> **为什么不能显示 100% 或 ∞ 或 0：** 显示 `100%` 会被误读为「增长了一倍」；显示 `∞` 前端无法排版；显示 `0` 更是错误的（实际是「从无到有」，绝非「持平」）。数学上该比率未定义，工程上最诚实的做法就是不显示，并用文案提示「基期为零，无可比性」。

**五种 compare_type 的基线取法与窗口对齐：**

| # | compare_type | 基线期间 | 取值来源 | 窗口归一化 | 当基线缺失时 |
|---|---|---|---|---|---|
| 1 | `MOM` | `p − 1 个月` | `m22_report_dept_summary` | 默认 `NONE`，流量型指标可配 `DAY_AVG` | `comparability_reason = 'BASELINE_MISSING'` |
| 2 | `YOY` | `p − 12 个月` | `m22_report_dept_summary` | 默认 `NONE`（月份天数相近），闰月 2 月配 `DAY_AVG` | 同上 |
| 3 | `TARGET` | 同期间 | `m22_report_dept_target`（`target_status = 'APPROVED'` 的最高版本） | `NONE` | `comparability_reason = 'BASELINE_MISSING'` |
| 4 | `BASELINE` | 用户指定 `baseline_period` | `m22_report_dept_summary` | 用户可选 | 同上 |
| 5 | `PEER` | 同期间 | 同组其他科室的聚合 | `NONE`（同期间天然对齐） | `comparability_reason = 'PEER_TOO_FEW'` |

**月份天数不同如何归一化——这是本子模块必须写清的技术点：**

自然月长度在 28~31 天之间波动，最大差异 `(31 − 28) / 28 ≈ 10.7%`。对于流量型指标（门诊人次、收入、手术台次），这个差异与真实的业务波动同量级，不归一化会得出错误结论。

以 2026 年 2 月（28 天）对比 2026 年 1 月（31 天）为例，假设某科室 1 月门诊 3,100 人次、2 月门诊 2,860 人次：

| # | 归一化方法 | 计算过程 | 结果 | 结论 |
|---|---|---|---|---|
| 1 | `NONE` | `(2860 − 3100) / 3100` | `−0.077419` | 环比下降 7.74%，看似下滑 |
| 2 | `DAY_AVG` | 1 月日均 `3100/31 = 100.000000`；2 月日均 `2860/28 = 102.142857`；`(102.142857 − 100.000000) / 100.000000` | `+0.021429` | 环比日均上升 2.14%，实际是增长 |
| 3 | `DAYS_RATIO` | 基线归一到本期天数：`3100 × (28/31) = 2800.000000`；`(2860 − 2800) / 2800` | `+0.021429` | 与 `DAY_AVG` 同比率，但保留总量量级 |
| 4 | `SAME_DAYS` | 只比 1~28 日：1 月前 28 天 2,800 人次、2 月 28 天 2,860 人次；`(2860 − 2800) / 2800` | `+0.021429` | 与上面一致，但需额外拉取日粒度数据 |

**结论：`NONE` 给出了方向相反的结论。** 这正是必须做窗口归一化的理由，也是本子模块要在页面上明确标注所用归一化方式的原因。

**`norm_factor` 的定义：** 为了让前端能复算，`norm_factor` 统一表示「把基线值乘以多少倍才能与本期可比」：

| # | 方法 | `norm_factor` | `is_normalized` |
|---|---|---|---|
| 1 | `NONE` | `1.000000` | FALSE |
| 2 | `DAY_AVG` | `本期天数 / 基线天数` | TRUE |
| 3 | `DAYS_RATIO` | `本期天数 / 基线天数` | TRUE |
| 4 | `SAME_DAYS` | `1.000000`（因为已改为只取同天数数据） | TRUE |

`DAY_AVG` 与 `DAYS_RATIO` 的 `norm_factor` 相同但语义不同：前者把「本期」也日均化后比较，后者只把「基线」按比例放大后比较。两者算出的 `delta_rate` 相同，但 `delta_abs` 不同——`DAY_AVG` 的 `delta_abs` 是日均差（2.142857），`DAYS_RATIO` 的 `delta_abs` 是总量差（60.000000）。因此 `norm_method` 与 `delta_abs` 必须成对记录，页面在展示「绝对差值」时必须说明它是日均差还是总量差。

**算例三（五种对比类型全走一遍）：**

设白内障科 2026-10 的 `CL_OR_COUNT = 186.000000`，`sample_size = 186`。基线取值如下：

| # | compare_type | baseline_key | baseline_value | delta_abs | delta_rate | is_better | change_level |
|---|---|---|---|---|---|---|---|
| 1 | `MOM` | `MOM:2026-09` | 172.000000 | 14.000000 | 0.081395 | TRUE | `SLIGHT_UP` |
| 2 | `YOY` | `YOY:2025-10` | 158.000000 | 28.000000 | 0.177215 | TRUE | `SIGNIFICANT_UP` |
| 3 | `TARGET` | `TARGET:M22_01:TG202610-0001` | 175.000000 | 11.000000 | 0.062857 | TRUE | `SLIGHT_UP` |
| 4 | `BASELINE` | `BASELINE:2026-06` | 150.000000 | 36.000000 | 0.240000 | TRUE | `SIGNIFICANT_UP` |
| 5 | `PEER` | `PEER:CLINICAL-B2:PEER_AVG` | 118.333333 | 67.666667 | 0.571831 | TRUE | `SIGNIFICANT_UP` |

验算 `MOM`：`(186 − 172) / 172 = 14 / 172 = 0.081395`，`0.081395 <= 0.10` 且 `> 0`，故 `SLIGHT_UP`。

验算 `PEER`：`CLINICAL-B2` 组共 6 个科室，手术台次合计 710.000000，均值 `710 / 6 = 118.333333`。`(186 − 118.333333) / 118.333333 = 67.666667 / 118.333333 = 0.571831`。

`change_level` 判定 `SIGNIFICANT_UP` 需 `abs(delta_rate) > 0.100000`，`0.571831 > 0.1` 成立。

**`is_better` 的判定：**

```text
HIGHER_BETTER : is_better = (delta_abs > 0)
LOWER_BETTER  : is_better = (delta_abs < 0)
NEUTRAL       : is_better = NULL（前端显示「—」，不下好坏判断）
delta_abs = 0 : is_better = NULL（持平，既不好也不坏）
```

#### 3.4.4 计算模型四：同类科室分组（PEER）

PEER 对比与 PEER 排名都依赖「同类科室」的定义。本子模块**不自己定义科室分类**，但 M01-01 当前提供的科室属性不足以保证可比性，因此 M22 首次定义了一个只读的分组接口 `GET /internal/v1/mdm/depts/peer-groups`（见 §10.1 的 U-01 说明），分组规则如下：

**分组键构成：** `{dept_type}-B{床位规模档}`，例如 `CLINICAL-B2`。

**床位规模分档规则：**

| # | 分档 | 床位数区间 | 说明 |
|---|---|---|---|
| 1 | `B0` | 0 张 | 门诊科室、无床位科室 |
| 2 | `B1` | 1 ~ 19 张 | 小科室 |
| 3 | `B2` | 20 ~ 49 张 | 中等科室（二级医院主流） |
| 4 | `B3` | 50 ~ 99 张 | 大科室 |
| 5 | `B4` | ≥ 100 张 | 超大科室 |

**为什么用「类型 + 床位档」而不是仅凭类型：** 同为 `CLINICAL`，20 张床的眼底病科与 120 张床的白内障科，其门诊量、手术量天然不在一个量级。不加床位档，PEER 对比的结果永远是「大科室碾压」。加入床位档后，比较发生在真正可比的科室之间。

**为什么床位档不能分得太细：** 若不设档 (每 10 张一档)，二级医院 30 个科室会散成 20 多个组，多数组内只有 1~2 个科室，PEER 对比失去意义。取 5 档是「组内科室数 ≥ 3」这一可比较性门槛与「保留足够区分度」之间的折中。

**最小组规模：** 一个 PEER 分组内至少要有 3 个科室才允许做 PEER 对比与 PEER 排名。若不足 3 个，`comparability_flag = FALSE`、`comparability_reason = 'PEER_TOO_FEW'`，此时可退化为「同级全部临床科室」作为备用组，但页面必须明确标注「同类科室不足，已退化到全院临床科室比较」。

**算例四：** 2026-10 全院临床科室的 PEER 分组：

| # | 科室 | dept_type | 床位数 | peer_group_key | 组内科室数 | 可比 |
|---|---|---|---|---|---|---|
| 1 | 白内障科 | CLINICAL | 48 | `CLINICAL-B2` | 6 | TRUE |
| 2 | 屈光手术科 | CLINICAL | 30 | `CLINICAL-B2` | 6 | TRUE |
| 3 | 青光眼科 | CLINICAL | 36 | `CLINICAL-B2` | 6 | TRUE |
| 4 | 眼底病科 | CLINICAL | 42 | `CLINICAL-B2` | 6 | TRUE |
| 5 | 斜弱视科 | CLINICAL | 24 | `CLINICAL-B2` | 6 | TRUE |
| 6 | 角膜病科 | CLINICAL | 20 | `CLINICAL-B2` | 6 | TRUE |
| 7 | 眼表病区 | CLINICAL | 12 | `CLINICAL-B1` | 2 | FALSE（不足 3） |

眼表病区所在组只有 2 个科室，做 PEER 对比时降级到全院临床科室组，`comparability_reason` 写 `PEER_TOO_FEW` 并在页面提示。

#### 3.4.5 计算模型五：目标达成率与进度偏差

**达成率：**

```text
HIGHER_BETTER 且 SINGLE : achievement_rate = actual_value / target_value
LOWER_BETTER  且 SINGLE : achievement_rate = target_value / actual_value     （actual > 0）
RANGE                    : achievement_rate = 1.0  若 target_lower <= actual <= target_upper
                           否则 = 1 − (实际偏离最近边界的距离 / 区间宽度)
target_value = 0         : achievement_rate = NULL
```

**LOWER_BETTER 为什么是 target / actual 而不是 actual / target：** 以「平均住院日」为例，目标 2.00 天，实际 1.60 天。若用 `actual / target = 0.8`，达成率 80% 看起来像没完成；实际是超额完成。用 `target / actual = 1.25`，达成率 125%，语义正确（同 `HIGHER_BETTER` 的 `actual / target`：目标 100 实际 125 得 125%）。

**时间进度：**

```text
time_progress_rate = 已过自然日数 / 期间自然日数
```

**进度偏差：**

```text
progress_deviation_rate = achievement_rate − time_progress_rate
```

**状态判定规则（`status_rule_json` 快照）：**

| # | 条件 | `target_status` | 说明 |
|---|---|---|---|
| 1 | `achievement_rate >= 1.000000` | `ACHIEVED` | 已达成 |
| 2 | `achievement_rate >= time_progress_rate × 0.900000` | `ON_TRACK` | 进度正常 |
| 3 | `achievement_rate >= time_progress_rate × 0.800000` | `AT_RISK` | 有风险 |
| 4 | 其他 | `MISSED` | 已落后 |

> **为什么 `ON_TRACK` 的阈值是 `time_progress_rate × 0.9` 而不是 1.0：** 如果月中就用「达成率 ≥ 时间进度」判定，则每月 1 号时间进度接近 0，所有科室都是 `ON_TRACK`，判定毫无信息量；反过来若用「达成率 ≥ 1.0」，则每月 20 号之前几乎所有科室都是 `MISSED`，预警天天响。乘以 0.9 留出 10% 的追赶空间，既能在月中早发现落后，又不至于天天误报。

**算例五：** 2026-10 期间共 31 天，评估日为 10 月 20 日（已过 20 天）。白内障科 `CL_OR_COUNT` 目标 175 台，当前实际 118 台：

- `achievement_rate = 118 / 175 = 0.674286`
- `time_progress_rate = 20 / 31 = 0.645161`
- `progress_deviation_rate = 0.674286 − 0.645161 = 0.029125`（略超前）
- 判定：`0.674286 >= 0.645161 × 0.9 = 0.580645` → `ON_TRACK`
- 预测期末值：`projected_value = 118 / (20/31) = 182.900000`
- 预测达成率：`projected_achievement_rate = 182.900000 / 175 = 1.045143`

另一科室青光眼科同指标目标 130 台，当前实际 62 台：

- `achievement_rate = 62 / 130 = 0.476923`
- 判定：`0.476923 >= 0.645161 × 0.8 = 0.516129`？不成立 → `MISSED`
- 惩罚：`0.476923 >= 0.645161 × 0.9 = 0.580645`？也不成立 → 确认为 `MISSED`
- 预测期末值 `62 / (20/31) = 96.100000`，预测达成率 `96.1 / 130 = 0.739231`

**差距归因 `gap_attribution`：** 当 `target_status ∈ {AT_RISK, MISSED}` 时，必须给出归因，取值见 §3.3；归因由人工在 P05 页面上确认，系统给出建议值（基于量价分解的初步判断），**不做自动定责**。

#### 3.4.6 计算模型六：医师个人排名与百分位

医师排名的难点在于**分母不同**：门诊量高的医师可能因为排班多，手术台的医师可能因为职称高。因此必须支持三种排名口径：

| # | 口径 | 说明 | 适用 |
|---|---|---|---|
| 1 | 绝对值排名 | 直接按 `metric_value` 排 | 工作量考核 |
| 2 | 人均日排名 | `metric_value / 出勤天数` | 公平比较半职/兼职医师 |
| 3 | 同类职称排名 | 只在同 `doctor_title` 内排名 | 避免主治与主任医师直接比 |

**百分位计算：**

```text
rank_percentile = 1 − (rank_in_dept − 1) / (dept_metric_total − 1)     （dept_metric_total > 1）
rank_percentile = NULL                                                  （dept_metric_total <= 1）
```

**算例六：** 白内障科 2026-10 `OP_VISIT_COUNT`，科室内 5 名医师：

| # | 医师 | 门诊人次 | rank_in_dept | dept_metric_total | rank_percentile |
|---|---|---|---|---|---|
| 1 | 张医师 | 1240 | 1 | 5 | 1.000000 |
| 2 | 李医师 | 980 | 2 | 5 | 0.750000 |
| 3 | 王医师 | 860 | 3 | 5 | 0.500000 |
| 4 | 赵医师 | 620 | 4 | 5 | 0.250000 |
| 5 | 孙医师 | 310 | 5 | 5 | 0.000000 |

验算张医师：`1 − (1 − 1) / (5 − 1) = 1 − 0 = 1.000000`。

验算李医师：`1 − (2 − 1) / 4 = 1 − 0.25 = 0.750000`。

**并列处理：** 若两名医师门诊人次相同，`rank_in_dept` 用 `RANK` 并列，`rank_percentile` 按并列后的名次计算（两人都是 `1 − (1−1)/4 = 1.000000`），不做平均。理由是同分即同等优秀，不应人为区分。

**`dept_metric_total <= 1` 时返回 NULL 的理由：** 科室只有 1 名医师时，他的百分位在数学上是 `0/0`。返回 1.0（第一名）或 0.0 都是错误的暗示。返回 NULL，让页面显示「—」。

#### 3.4.7 计算模型七：期间口径与口径版本稳定性

**期间口径：** 本子模块统一以 `period`（`YYYY-MM`）为主键的一部分。月粒度的 `period_start` 为当月 1 日，`period_end` 为当月最后一日。若为周/季/年粒度，`period` 相应扩展为 `YYYY-Www`、`YYYY-Qn`、`YYYY`，但本子模块 V1.0 只支持月粒度，其余粒度一律返回 `"2204003"`。

**为什么 V1.0 只做月粒度：** 科室排名与目标考核的业务节奏是「月」。引入周、季、年三种粒度会让 `period` 的语义与唯一键都复杂化，而收益有限——季度排名可由三次月度排名加总得出，年度同理。

**口径版本 `metric_version` 与计算版本 `calc_version` 的区别：**

| # | 字段 | 含义 | 变更影响 | 谁负责 |
|---|---|---|---|---|
| 1 | `metric_version` | 指标口径版本（分子分母怎么取数） | 同一期间不同版本的值可能不同 | M22-01 定义与审批 |
| 2 | `calc_version` | 本子模块计算逻辑版本（如排名算法、归一化实现） | 影响派生结果，不影响原始值 | M22-04 开发团队 |

**历史报表不重算的规则：** 这是本子模块最重要的一条铁律。

1. 报表实例（`m22_report_instance`）进入 `GENERATED` 及之后状态，其行数据为不可变快照
2. 排名批次固化后不可变
3. 口径升级时，只影响**新生成**的报表与排名；已固化的历史批次原样保留
4. 页面展示历史报表时，从快照读 `metric_version` 与 `calc_version`，并在角落显示「口径版本 V2（生成于 2026-11-03）」
5. 若用户强制要求按新口径重看历史期间，只能生成**新批次**（新 `ranking_batch_no`），旧批次标记 `superseded_by_batch_no`，两者并存可对比

#### 3.4.8 计算模型八：科室综合得分与等级

P04 排名榜除了单指标榜，还需要「综合实力榜」。综合得分计算：

```text
对每个指标 m_i，在参与排名的科室集合内计算 norm_i（同 §3.4.1）
composite_score = Σ ( w_i × norm_i ) × 100
```

**等级划分（用 DENSE_RANK，保证档位数稳定）：**

| # | 密集名次区间 | 等级 | 标签 | 颜色建议 |
|---|---|---|---|---|
| 1 | 前 20% | A | 优秀 | 绿色 |
| 2 | 20% ~ 50% | B | 良好 | 蓝色 |
| 3 | 50% ~ 80% | C | 达标 | 灰色 |
| 4 | 80% ~ 100% | D | 待改进 | 橙色 |
| 5 | 不参与排名 | E | 不参评 | 浅灰 |

**算例七：** 12 个参与排名的临床科室，`composite_score` 降序排列后：

| # | 科室 | composite_score | dense_rank_no | 前百分比 | 等级 |
|---|---|---|---|---|---|
| 1 | 白内障科 | 98.461500 | 1 | 0.083333 | A |
| 2 | 屈光手术科 | 74.108500 | 2 | 0.166667 | A |
| 3 | 青光眼科 | 32.969200 | 3 | 0.250000 | B |
| 4 | 眼底病科 | 0.000000 | 4 | 0.333333 | B |
| 5~12 | 其余 8 个科室 | 依次递减 | 5~12 | 0.416667~1.000000 | B/C/D |

前百分比 = `dense_rank_no / 参与科室数 = 1/12 = 0.083333`。

等级判定：`0.083333 <= 0.2` → A；`0.250000 <= 0.5` → B；依此类推。

**为什么用密集名次而不是普通名次算百分位：** 若前两名并列，普通名次会跳号到第 3 名，第 3 名科室的前百分比变成 `3/12 = 0.25`，而实际它前面只有 2 个（并列）科室。密集名次 `2/12 = 0.166667` 更准确反映「落在第几档」。

### 6.2 错误码

| 错误码 | HTTP | 消息 | 触发条件 | 处理建议 |
|---|---|---|---|---|
| `"229001"` | 500 | 系统内部错误 | 未捕获异常 | 记录 trace_id，联系运维 |
| `"2204001"` | 404 | 科室报表配置不存在 | `config_code` 查无 | 检查配置是否已激活 |
| `"2204002"` | 400 | 指标定义不存在或未生效 | M22-01 无该 `metric_code` 的 ACTIVE 版本 | 在 M22-01 激活指标 |
| `"2204003"` | 400 | 不支持的统计粒度 | `granularity` 非 MONTHLY | V1.0 仅支持月粒度 |
| `"2204004"` | 400 | 期间格式非法 | `period` 不匹配 `YYYY-MM` | 按规范传参 |
| `"2204005"` | 400 | 科室不存在 | `dept_id` 在 M01-01 查无 | 刷新科室树 |
| `"2204006"` | 403 | 无该科室数据权限 | 请求的 `dept_id` 不在用户数据范围 | 申请数据权限 |
| `"2204007"` | 400 | 科室数量超出上限 | 科室数 > 200 | 分批查询 |
| `"2204008"` | 400 | 指标数量超出上限 | 指标数 > 60 | 减少指标 |
| `"2204009"` | 400 | 期间数量超出上限 | 期间数 > 12 | 减少期间 |
| `"2204010"` | 409 | 排名批次正在生成中 | 同期间同指标并发生成 | 稍后重试 |
| `"2204011"` | 409 | 排名批次已固化不可修改 | 对 FROZEN 批次做修改 | 生成新批次 |
| `"2204012"` | 404 | 排名批次不存在 | `ranking_batch_no` 查无 | 检查批次号 |
| `"2204013"` | 400 | 多指标排名权重之和不等于 1 | 权重和偏差 > 0.000001 | 修正权重 |
| `"2204014"` | 400 | 同类科室分组不存在 | `peer_group_key` 查无 | 调分组接口获取 |
| `"2204015"` | 400 | 同类科室数量不足 | 组内科室 < 3 | 换分组或退化到全院 |
| `"2204016"` | 400 | 对比类型非法 | `compare_type` 不在 5 值内 | 按枚举传参 |
| `"2204017"` | 400 | 基线期间必填 | `compare_type=BASELINE` 未传 `baseline_period` | 补传基线期间 |
| `"2204018"` | 400 | 基线期间不能等于本期 | 两者相同 | 更换基线期间 |
| `"2204019"` | 404 | 基线数据不存在 | 基线期间无汇总数据 | 检查基线期间是否已生成 |
| `"2204020"` | 400 | 归一化方式与指标类型不匹配 | 时点型指标用 DAY_AVG | 改用 NONE |
| `"2204021"` | 404 | 科室目标不存在 | `target_no` 查无 | 检查目标编号 |
| `"2204022"` | 409 | 该期间已存在已批准目标 | 重复设定 | 使用调整接口 |
| `"2204023"` | 400 | 目标值非法 | ≤ 0 或区间上下限倒置 | 修正目标值 |
| `"2204024"` | 400 | 目标类型与关系符不匹配 | FLOOR 配 LTE 等 | 按规则修正 |
| `"2204025"` | 403 | 不能审批自己提交的目标 | 审批人 = 提交人 | 由他人审批 |
| `"2204026"` | 409 | 期间已结束不可新增目标 | 期间已过 | 只允许调整 |
| `"2204027"` | 400 | 差距归因必填 | `AT_RISK`/`MISSED` 未填归因 | 补填归因 |
| `"2204028"` | 400 | 调整原因必填 | 调整目标未填原因 | 补填原因 |
| `"2204029"` | 404 | 医师数据不存在 | `doctor_id` 查无或其期间无数据 | 检查期间与人员 |
| `"2204030"` | 404 | 报表模板不存在 | `template_code` 在 M22-03 查无 | 检查模板编码 |
| `"2204031"` | 400 | 导出格式不支持该数据类型 | 例：IMAGE 导出多页 | 改格式或减数据 |
| `"2204032"` | 403 | 无权限导出个人数据 | 缺 `m22:04:sensitive` | 申请敏感权限 |
| `"2204033"` | 404 | 下钻配置不存在 | 该指标无下钻路由 | 配置下钻路由 |
| `"2204034"` | 400 | 下钻参数解析失败 | `param_template` 与上下文不匹配 | 检查 drill 配置 |
| `"2204035"` | 504 | 上游明细接口超时 | 上游响应 > `timeout_ms` | 稍后重试 |
| `"2204036"` | 502 | 上游明细接口异常 | 上游返回非 2xx | 查看上游状态 |
| `"2204037"` | 400 | 返回行数超出上限 | 上游返回 > `max_rows` | 缩小查询范围 |
| `"2204038"` | 503 | 上游财务数据未就绪 | M17-04 不可用 | 稍后重试，页面标「—」 |
| `"2204039"` | 409 | 数据已固化不可重算 | 报表实例已 PUBLISHED | 生成新实例 |
| `"2204040"` | 400 | 数据源状态非完整 | `source_status != COMPLETE` 时强行发布 | 等待采集完成或确认强制发布 |

> **错误码号段说明：** 本子模块占用 `"2204001"` ~ `"2204040"` 共 40 个业务错误码，加上模块通用 `"229001"`。号段不越界，`"2204041"` 及之后保留给后续版本。

#### 6.5.1 排名批次生成服务

```python
import logging
import uuid
from datetime import datetime
from decimal import Decimal, ROUND_HALF_UP

from sqlalchemy import select, text, update
from sqlalchemy.ext.asyncio import AsyncSession

from app.constants.m22_dept import RANK_METHODS, SCORE_NORM_METHODS
from app.exceptions.m22 import BizError
from app.models.m22.dept_report import (
    M22ReportDeptLog,
    M22ReportDeptRanking,
    M22ReportDeptSummary,
)
from app.utils.m22.code_gen import gen_code

logger = logging.getLogger(__name__)

SIX = Decimal("0.000001")


class RankingService:
    """科室排名批次生成。

    核心约束（不可违反）：
    1. 批次一经固化（rank_frozen_at 非空）即不可修改，纠错只能生成新批次
    2. 分母为零的科室不参与名次，exclude_reason 锁定 DENOMINATOR_ZERO
    3. 样本不足的科室仍参与名次，但必须写入 sample_insufficient_note
    4. 排序键最后一层必须是全局唯一确定性键，NULL 一律 LAST
    """

    def __init__(self, session: AsyncSession, redis, lock_factory) -> None:
        self.session = session
        self.redis = redis
        self.lock_factory = lock_factory

    async def create_batch(self, payload, user: dict, idem_key: str | None) -> dict:
        metric_codes = payload.metric_codes
        for code in metric_codes:
            if not code:
                raise BizError("2204002", f"指标编码为空: {code}")
        if payload.rank_method not in RANK_METHODS:
            raise BizError("2204016", f"排名方法非法: {payload.rank_method}")
        if payload.score_norm_method not in SCORE_NORM_METHODS:
            raise BizError("2204016", f"归一化方法非法: {payload.score_norm_method}")
        if payload.rank_scope == "PEER" and not payload.peer_group_key:
            raise BizError("2204014", "同类排名必须指定 peer_group_key")

        lock_key = (
            f"m22:lock:ranking:{payload.period}:{payload.rank_scope}:"
            f"{payload.peer_group_key or 'ALL'}:{'-'.join(sorted(metric_codes))}"
        )
        lock = self.lock_factory(lock_key, timeout=300)
        acquired = await lock.acquire(blocking=False)
        if not acquired:
            raise BizError("2204010", "该批次正在生成中，请稍后重试")

        batch_no = await gen_code(self.redis, prefix="RB", period=payload.period, width=4)
        try:
            summary_rows = await self._load_summary(payload)
            if not summary_rows:
                raise BizError("2204019", f"期间 {payload.period} 无汇总数据，无法生成排名")

            limit_map = await self._load_sample_limits(metric_codes)
            ranked_rows = self._compute_rank(
                rows=summary_rows,
                payload=payload,
                limit_map=limit_map,
            )
            self._assert_rank_consistency(ranked_rows)

            for row in ranked_rows:
                row["ranking_batch_no"] = batch_no
                self.session.add(M22ReportDeptRanking(**row))

            await self.session.flush()
            frozen_at = datetime.now()
            await self.session.execute(
                update(M22ReportDeptRanking)
                .where(M22ReportDeptRanking.ranking_batch_no == batch_no)
                .values(rank_frozen_at=frozen_at, frozen_by=user["user_id"])
            )
            await self._write_log(
                user=user, action="GENERATE", biz_no=batch_no,
                period=payload.period, detail={"metric_codes": metric_codes},
            )
            await self.session.commit()
        except Exception:
            await self.session.rollback()
            logger.exception("ranking batch failed, batch_no tentative=%s", batch_no)
            raise
        finally:
            await lock.release()

        return {
            "ranking_batch_no": batch_no,
            "period": payload.period,
            "status": "FROZEN",
            "dept_count": len(ranked_rows),
            "rank_method": payload.rank_method,
            "score_norm_method": payload.score_norm_method,
        }

    async def _load_summary(self, payload) -> list[dict]:
        stmt = (
            select(M22ReportDeptSummary)
            .where(M22ReportDeptSummary.period == payload.period)
            .where(M22ReportDeptSummary.metric_code.in_(payload.metric_codes))
            .where(M22ReportDeptSummary.biz_dim == payload.biz_dim)
            .where(M22ReportDeptSummary.is_deleted.is_(False))
        )
        result = await self.session.execute(stmt)
        return [
            {
                "dept_id": r.dept_id,
                "dept_code": r.dept_code,
                "dept_name": r.dept_name,
                "dept_type": r.dept_type,
                "metric_code": r.metric_code,
                "metric_version": r.metric_version,
                "metric_value": r.metric_value,
                "sample_size": r.sample_size,
                "sample_limit": r.sample_limit,
                "sample_sufficient": r.sample_sufficient,
                "source_status": r.source_status,
                "denominator_zero_flag": r.denominator_zero_flag,
            }
            for r in result.scalars().all()
        ]

    async def _load_sample_limits(self, metric_codes: list[str]) -> dict[str, int]:
        """从 M22-01 指标定义读取样本量下限，禁止硬编码。"""
        stmt = text(
            "SELECT metric_code, sample_limit FROM m22.m22_metric_def "
            "WHERE metric_code = ANY(:codes) AND status = 'ACTIVE' AND is_deleted = FALSE"
        )
        rows = (await self.session.execute(stmt, {"codes": metric_codes})).all()
        return {r.metric_code: int(r.sample_limit) for r in rows if r.sample_limit is not None}

    def _compute_rank(self, rows: list[dict], payload, limit_map: dict[str, int]) -> list[dict]:
        """按 §3.4.1 的算法计算名次。"""
        out: list[dict] = []
        by_metric: dict[str, list[dict]] = {}
        for r in rows:
            by_metric.setdefault(r["metric_code"], []).append(r)

        for metric_code, group in by_metric.items():
            eligible: list[dict] = []
            for r in group:
                reason = None
                if r["source_status"] == "FAILED":
                    reason = "INGEST_FAILED"
                elif r["denominator_zero_flag"]:
                    reason = "DENOMINATOR_ZERO"
                elif r["metric_value"] is None:
                    reason = "VALUE_MISSING"
                r["exclude_reason"] = reason
                r["rank_eligible"] = reason is None
                if reason is None:
                    eligible.append(r)

            limit = limit_map.get(metric_code, 30)
            for r in group:
                r["sample_limit"] = limit
                r["sample_sufficient"] = int(r["sample_size"] or 0) >= limit
                if not r["sample_sufficient"] and r["rank_eligible"]:
                    r["sample_insufficient_note"] = (
                        f"N={r['sample_size']}，低于下限 {limit}，仅供参考"
                    )
                else:
                    r["sample_insufficient_note"] = None

            eligible.sort(
                key=lambda x: (
                    -x["metric_value"],
                    -(x["sample_size"] or 0),
                    x["dept_code"],
                )
            )
            rank_no = 0
            dense = 0
            prev_value = None
            for idx, r in enumerate(eligible, start=1):
                if prev_value is None or r["metric_value"] != prev_value:
                    rank_no = idx
                    dense += 1
                    prev_value = r["metric_value"]
                r["rank_no"] = rank_no
                r["dense_rank_no"] = dense
                r["row_no"] = idx

            ineligible = [r for r in group if not r["rank_eligible"]]
            ineligible.sort(key=lambda x: x["dept_code"])
            for idx, r in enumerate(ineligible, start=len(eligible) + 1):
                r["rank_no"] = None
                r["dense_rank_no"] = None
                r["row_no"] = idx

            total = len(eligible)
            for r in group:
                out.append(
                    {
                        "ranking_batch_no": "",  # 由调用方回填
                        "metric_code": metric_code,
                        "metric_version": r["metric_version"],
                        "period": payload.period,
                        "rank_scope": payload.rank_scope,
                        "peer_group_key": payload.peer_group_key or "ALL",
                        "dept_id": r["dept_id"],
                        "dept_code": r["dept_code"],
                        "dept_name": r["dept_name"],
                        "dept_type": r["dept_type"],
                        "biz_dim": payload.biz_dim,
                        "metric_value": r["metric_value"],
                        "rank_no": r["rank_no"],
                        "dense_rank_no": r["dense_rank_no"],
                        "row_no": r["row_no"],
                        "rank_method": payload.rank_method,
                        "rank_score": None,
                        "score_norm_method": payload.score_norm_method,
                        "weight_config_json": payload.weight_config or None,
                        "sort_rule_json": {
                            "order_by": [
                                "metric_value DESC NULLS LAST",
                                "sample_size DESC NULLS LAST",
                                "dept_code ASC NULLS LAST",
                            ]
                        },
                        "total_dept_count": total,
                        "sample_size": r["sample_size"] or 0,
                        "sample_limit": r["sample_limit"],
                        "sample_sufficient": r["sample_sufficient"],
                        "sample_insufficient_note": r["sample_insufficient_note"],
                        "rank_eligible": r["rank_eligible"],
                        "exclude_reason": r["exclude_reason"],
                        "source_module": "M22",
                        "source_api": "/internal/v1/m22/metrics/batch",
                        "source_status": r["source_status"],
                        "calc_version": "V1",
                        "generated_at": datetime.now(),
                    }
                )
        return out

    def _assert_rank_consistency(self, rows: list[dict]) -> None:
        """写入前的最后一道防线：参与排名与名次的双向绑定必须成立。"""
        for r in rows:
            if r["rank_eligible"] and r["rank_no"] is None:
                raise BizError("229001", f"内部校验失败：dept={r['dept_id']} 可排名但无名次")
            if not r["rank_eligible"] and r["rank_no"] is not None:
                raise BizError("229001", f"内部校验失败：dept={r['dept_id']} 不可排名却有名字")
            if r["exclude_reason"] == "DENOMINATOR_ZERO" and r["metric_value"] is not None:
                raise BizError("229001", f"内部校验失败：dept={r['dept_id']} 分母为零却有值")

    async def _write_log(self, user: dict, action: str, biz_no: str, period: str, detail: dict) -> None:
        self.session.add(
            M22ReportDeptLog(
                log_no=await gen_code(self.redis, prefix="DL", width=6),
                biz_type="RANKING",
                biz_no=biz_no,
                action=action,
                target_table="m22_report_dept_ranking",
                period=period,
                operator_id=user["user_id"],
                operator_name=user.get("user_name", ""),
                operator_source="USER",
                result_status="SUCCESS",
                detail=detail,
            )
        )
```

#### 6.5.2 对比分析服务

```python
from datetime import date
from decimal import Decimal, ROUND_HALF_UP
from calendar import monthrange

from sqlalchemy import select

from app.exceptions.m22 import BizError

SIX = Decimal("0.000001")
SIGNIFICANT = Decimal("0.100000")
FLAT = Decimal("0.010000")


class CompareService:
    """科室对比分析。M22 不计算任何业务金额，只比较已由上游算好的指标值。"""

    def __init__(self, session, metric_client, peer_client) -> None:
        self.session = session
        self.metric_client = metric_client
        self.peer_client = peer_client

    async def compare(self, query, user: dict) -> dict:
        baseline_cfg = self._resolve_baseline(query)
        items: list[dict] = []
        for metric_code in query.metric_codes:
            metric_def = await self.metric_client.get_def(metric_code)
            if metric_def is None or metric_def["status"] != "ACTIVE":
                raise BizError("2204002", f"指标定义不存在或未生效: {metric_code}")

            actual_map = await self._load_values(query.period, query.dept_ids, metric_code, query.biz_dim)
            base_map = await self._load_baseline(baseline_cfg, query, metric_code)

            norm_method = query.norm_method or metric_def.get("default_norm_method") or "NONE"
            factor = self._norm_factor(norm_method, query.period, baseline_cfg.get("period"))

            for dept_id in query.dept_ids:
                actual = actual_map.get(dept_id)
                base = base_map.get(dept_id)
                items.append(
                    self._build_row(
                        dept_id=dept_id,
                        actual=actual,
                        base=base,
                        metric_def=metric_def,
                        compare_type=query.compare_type,
                        baseline_cfg=baseline_cfg,
                        norm_method=norm_method,
                        factor=factor,
                    )
                )
        return {
            "period": query.period,
            "compare_type": query.compare_type,
            "items": items,
            "not_comparable": [x for x in items if not x["comparability_flag"]],
        }

    def _resolve_baseline(self, query) -> dict:
        if query.compare_type == "MOM":
            return {"baseline_type": "PREV_PERIOD", "period": self._shift_month(query.period, -1)}
        if query.compare_type == "YOY":
            return {"baseline_type": "SAME_PERIOD_LAST_YEAR", "period": self._shift_month(query.period, -12)}
        if query.compare_type == "TARGET":
            return {"baseline_type": "TARGET_VALUE", "period": query.period, "source": "M22_01"}
        if query.compare_type == "BASELINE":
            if not query.baseline_period:
                raise BizError("2204017", "compare_type=BASELINE 时 baseline_period 必填")
            if query.baseline_period == query.period:
                raise BizError("2204018", "基线期间不能等于本期")
            return {"baseline_type": "FIXED_PERIOD", "period": query.baseline_period}
        return {
            "baseline_type": query.peer_stat,
            "period": query.period,
            "peer_group_key": query.peer_group_key,
        }

    @staticmethod
    def _shift_month(period: str, delta: int) -> str:
        year, month = int(period[:4]), int(period[5:7])
        total = year * 12 + (month - 1) + delta
        return f"{total // 12:04d}-{total % 12 + 1:02d}"

    @staticmethod
    def _norm_factor(norm_method: str, period: str, base_period: str | None) -> Decimal:
        """返回把基线放大到与本期可比的系数。NONE 与 SAME_DAYS 恒为 1。"""
        if norm_method in ("NONE", "SAME_DAYS") or not base_period:
            return Decimal("1.000000")
        cur_days = monthrange(int(period[:4]), int(period[5:7]))[1]
        base_days = monthrange(int(base_period[:4]), int(base_period[5:7]))[1]
        factor = Decimal(cur_days) / Decimal(base_days)
        return factor.quantize(SIX, rounding=ROUND_HALF_UP)

    def _build_row(
        self,
        dept_id: int,
        actual,
        base,
        metric_def: dict,
        compare_type: str,
        baseline_cfg: dict,
        norm_method: str,
        factor: Decimal,
    ) -> dict:
        direction = metric_def["value_direction"]
        actual_value = actual["metric_value"] if actual else None
        base_value = base["baseline_value"] if base else None

        comparability_flag = True
        reason = None
        if base is None:
            comparability_flag, reason = False, "BASELINE_MISSING"
        elif actual is None:
            comparability_flag, reason = False, "BASELINE_MISSING"

        baseline_zero = (base_value is not None and Decimal(base_value) == 0)
        delta_abs = None
        delta_rate = None
        if actual_value is not None and base_value is not None:
            delta_abs = Decimal(actual_value) - Decimal(base_value)
            if baseline_zero:
                delta_rate = None
                comparability_flag, reason = False, "BASELINE_ZERO"
            else:
                delta_rate = (delta_abs / Decimal(base_value)).quantize(SIX, rounding=ROUND_HALF_UP)
                delta_abs = delta_abs.quantize(SIX, rounding=ROUND_HALF_UP)

        is_better = None
        if delta_abs is not None and delta_abs != 0:
            if direction == "HIGHER_BETTER":
                is_better = delta_abs > 0
            elif direction == "LOWER_BETTER":
                is_better = delta_abs < 0

        change_level = None
        if delta_rate is not None:
            mag = abs(delta_rate)
            if mag < FLAT:
                change_level = "FLAT"
            elif delta_rate > 0:
                change_level = "SIGNIFICANT_UP" if mag > SIGNIFICANT else "SLIGHT_UP"
            else:
                change_level = "SIGNIFICANT_DOWN" if mag > SIGNIFICANT else "SLIGHT_DOWN"

        return {
            "dept_id": dept_id,
            "metric_code": metric_def["metric_code"],
            "compare_type": compare_type,
            "baseline_type": baseline_cfg["baseline_type"],
            "baseline_key": f"{compare_type}:{baseline_cfg.get('period', '')}",
            "baseline_value": base_value,
            "actual_value": actual_value,
            "norm_method": norm_method,
            "norm_factor": factor,
            "is_normalized": norm_method != "NONE",
            "delta_abs": delta_abs,
            "delta_rate": delta_rate,
            "baseline_zero_flag": baseline_zero,
            "is_better": is_better,
            "change_level": change_level,
            "comparability_flag": comparability_flag,
            "comparability_reason": reason,
        }

    async def _load_values(self, period: str, dept_ids: list[int], metric_code: str, biz_dim: str) -> dict:
        from app.models.m22.dept_report import M22ReportDeptSummary

        stmt = (
            select(M22ReportDeptSummary)
            .where(M22ReportDeptSummary.period == period)
            .where(M22ReportDeptSummary.metric_code == metric_code)
            .where(M22ReportDeptSummary.dept_id.in_(dept_ids))
            .where(M22ReportDeptSummary.biz_dim == biz_dim)
            .where(M22ReportDeptSummary.is_deleted.is_(False))
        )
        rows = (await self.session.execute(stmt)).scalars().all()
        return {
            r.dept_id: {"metric_value": r.metric_value, "source_status": r.source_status}
            for r in rows
        }

    async def _load_baseline(self, baseline_cfg: dict, query, metric_code: str) -> dict:
        if baseline_cfg["baseline_type"] in ("PEER_AVG", "PEER_MEDIAN", "PEER_TOP_AVG"):
            return await self.peer_client.aggregate(
                group_key=baseline_cfg["peer_group_key"],
                period=baseline_cfg["period"],
                metric_code=metric_code,
                stat=baseline_cfg["baseline_type"],
                dept_ids=query.dept_ids,
            )
        if baseline_cfg["baseline_type"] == "TARGET_VALUE":
            return await self.metric_client.load_targets(
                period=baseline_cfg["period"],
                metric_code=metric_code,
                dept_ids=query.dept_ids,
            )
        period = baseline_cfg["period"] or ""
        if not period:
            raise BizError("2204019", "基线期间无法解析")
        return await self._load_values(period, query.dept_ids, metric_code, query.biz_dim)
```

## 7. 缓存与异步设计

本章说明 M22-04 的三层加速与三条异步链路。M22-04 的定位是「取数→校准→存储→展现→下钻」，其中**取数（调上游）**是整个子模块唯一的慢环节：一次科室综合报表要串行调用 M05-07、M07-07、M17-04、M17-07 四个上游，串行累加 P95 约 1.1 秒，完全无法支撑 P01 工作台首屏 800 毫秒的目标。因此缓存不是「优化项」而是**架构必需项**。

### 7.1 Redis 缓存设计

#### 7.1.1 缓存分域与键规范

M22-04 的 Redis 键统一挂在共享规范 §11 划定的 `m22:dept:*` 分域下，不与其他子模块混用分域。分域名的选择理由：出问题时可以按前缀一次性清理或导出，不会误伤 M22-03 的报表实例缓存。

| 键模式 | 数据类型 | TTL | 值内容 | 失效触发 |
|---|---|---|---|---|
| `m22:dept:config:{dept_id}` | STRING (JSON) | 600 秒 | 科室报表配置（权重、样本量映射、排序规则）序列化 | 配置保存（API 写配置后主动 DEL） |
| `m22:dept:scope:{period}:{dept_id}` | STRING (JSON) | 3600 秒 | 科室范围快照（含历史归属映射） | 新快照生成时按期间批量清 |
| `m22:dept:summary:{period}:{dept_id}:{metric_group}:{biz_dim}` | STRING (JSON) | 300 秒 | P02 综合报表整页数据 | 对应期间汇总重算（API-04）后 DEL |
| `m22:dept:workbench:{period}:{dept_id}:{role}` | STRING (JSON) | 120 秒 | P01 工作台聚合结果 | 120 秒自然过期，不主动清 |
| `m22:dept:compare:{period}:{dept_id}:{compare_type}:{metric_group}` | STRING (JSON) | 300 秒 | P03 对比结果 | 对比重算（API-07）后 DEL |
| `m22:dept:ranking:{period}:{scope}:{group}:{metrics}` | STRING (JSON) | 600 秒 | P04 排名榜结果（含快照批次号） | 新批次固化后 DEL |
| `m22:dept:ranking:latest:{period}` | STRING | 600 秒 | 该期间当前有效批次号 | 固化或作废时 DEL |
| `m22:dept:peergroups:{period}` | STRING (JSON) | 1800 秒 | PEER 分组结果 | 期间切换自然过期 |
| `m22:dept:target:{period}:{dept_id}` | STRING (JSON) | 300 秒 | P05 目标达成列表 | 目标审批/归因后 DEL |
| `m22:dept:doctor:{period}:{dept_id}:{metric_group}` | STRING (JSON) | 300 秒 | P06 医师报表 | 医师数据刷新后 DEL |
| `m22:dept:drill:{drill_code}` | STRING (JSON) | 1800 秒 | P08 下钻路由配置 | 下钻配置变更后 DEL |
| `m22:dept:lock:{period}:{scope}:{group}` | STRING | 300 秒 | 排名批次生成互斥锁（含持有者 trace_id） | 任务结束主动 DEL |
| `m22:dept:metric_version:{metric_code}` | STRING | 600 秒 | 该指标当前生效口径版本号 | 收到 `m22.metric.changed` 事件时 DEL |

**TTL 取值的三条依据：**

1. **工作台 120 秒**：科室主任查看看板的习惯是「早上看一次、查完房再看一次」，120 秒足以吸收同一次浏览中的多次刷新，又不至于让数据陈旧到影响判断。工作台上都有 `generated_at` 与 `source_status` 标记，即使命中缓存读到的也是准确的生成时刻。
2. **综合报表 300 秒**：报表口径是月粒度，一整天数据都不会变，理论上可以缓存 1 小时。但取 300 秒是**为了给上游留纠错窗口** —— 上游 M17-04 在结账前可能修正数据，缓存过久会让用户看到已失效的数字。
3. **配置与分组 600~1800 秒**：变更频率极低，宁可缓存长一些减少数据库压力；变更时一律主动 DEL，所以长 TTL 不会导致配置不一致。

#### 7.1.2 缓存穿透、击穿与雪崩的处置

| 风险 | 本子模块的具体场景 | 处置手段 |
|---|---|---|
| 穿透 | 用户手工构造不存在的 `dept_id` 或 `period` 反复请求 | 参数校验在缓存之前完成：`dept_id` 必须存在于 M01-01，`period` 必须命中 `^\d{4}-(0[1-9]\|1[0-2])$`，非法直接返回 `"2204004"` 或 `"2204005"`，不触及 Redis 与 DB |
| 穿透 | 某个科室该月确实没有任何汇总数据 | 空结果也缓存，值为 `{"__empty__": true}`，TTL 压缩到 60 秒（比正常结果短，因为数据可能马上补进来） |
| 击穿 | 月度报表发布瞬间大量用户同时打开同一科室报表 | 键级互斥锁 `m22:dept:lock:summary:{key}`，未抢到锁的请求等 200 毫秒后重读缓存，仍无则直接走 DB（不做长等待，避免线程堆积） |
| 雪崩 | 每月 1 日 00:05 定时任务批量重算全部科室全部指标，缓存同时失效 | 缓存 TTL 加 ±10% 随机抖动；批量重算按科室 ID 哈希取模分 8 批，每批间隔 3 秒 |

#### 7.1.3 「不缓存」的四类数据

有四种数据**明令禁止缓存**，写在这里是为了防止后续维护者顺手加上缓存：

1. **排名批次的固化时间与状态**。用户点「生成排名」后必须立刻看到真实状态（`GENERATING` 或 `FROZEN`），缓存会导致「明明已经固化，页面还显示生成中」。
2. **目标审批结果**。审批是强一致业务动作，缓存会造成「审批已通过但页面仍显示待审批」。
3. **权限判定结果**。权限缓存在网关上统一处理，M22-04 不得自建权限缓存。
4. **上游错误响应**。上游超时不能缓存，否则一次网络抖动会让该科室 5 分钟内一直报错。

### 7.2 Celery 异步任务

M22-04 共有 5 个 Celery 任务，全部注册在 `m22` 队列，`acks_late=True`、`max_retries=3`、`default_retry_delay=60`。

| 任务名 | 触发方式 | 输入 | 输出 | 幂等键 | 超时 |
|---|---|---|---|---|---|
| `m22.dept.summary.recalc` | 手动（API-04）或收到 `m17.period.closed` 事件 | `period` + `dept_ids` + `metric_codes` | 写 `m22_report_dept_summary` | `recalc:{period}:{hash(dept_ids+metrics)}` | 600 秒 |
| `m22.dept.compare.recalc` | 手动（API-07） | `period` + `dept_ids` + `compare_types` | 写 `m22_report_dept_compare` | `crecalc:{period}:{hash}` | 600 秒 |
| `m22.dept.ranking.build` | 手动（API-11） | 批次参数 | 写 `m22_report_dept_ranking` 并固化 | `rank:{period}:{scope}:{hash}` | 900 秒 |
| `m22.dept.doctor.refresh` | 定时（每月 1 日 02:00） | `period` | 写 `m22_report_dept_doctor` | `doc:{period}` | 900 秒 |
| `m22.dept.target.evaluate` | 定时（每日 07:00） | 当月 `period` | 更新 `m22_report_dept_target` 的 `actual_value` 与状态 | `tgt:{period}:{date}` | 300 秒 |

**为什么排名生成必须异步。** 全院 60 个科室、12 个指标，单批次要计算 720 条排名行，每条还要做多指标归一化与加权。实测同步执行约 6~9 秒，超过网关 5 秒超时。异步化的代价是用户点完按钮后要等，因此 API-11 立即返回 `batch_no` 与状态 `GENERATING`，前端用 API-13 每 2 秒轮询一次，最长轮询 30 次（60 秒）后提示「生成超时，请稍后到批次列表查看」。

**为什么目标评估要每日跑。** 目标达成率是**随时间变化的**：月初 5 号达成率 0.16 很正常，月末 30 号还是 0.16 就要预警。每日 07:00 重算 `actual_value`、`achievement_rate`、`projected_value` 与 `target_status`，才能让 P05 页面上的「预测未达成」预警提前 20 多天发出。任务本身耗时不到 30 秒，放在上班前不会影响白天负载。

**Celery 任务与分布式锁的关系。** `m22.dept.ranking.build` 在任务内部再次获取 `m22:dept:lock:{period}:{scope}:{group}`，锁在任务开始前由 API 层获取、在任务 finally 中释放。这样即使 API 层重复提交（用户连点两次），第二次也会在锁上失败并返回 `"2204010"`，而不是跑出两个批次。

### 7.3 APScheduler 定时任务

APScheduler 只负责**触发**，不承载业务逻辑，触发后一律投递给 Celery，避免长任务阻塞调度器。

| 任务 ID | Cron (Asia/Shanghai) | 动作 | 说明 |
|---|---|---|---|
| `m22_dept_target_daily` | `0 7 * * *` | 投递 `m22.dept.target.evaluate` | 每日 07:00 评估当月目标 |
| `m22_dept_ranking_monthly` | `30 1 1 * *` | 投递 `m22.dept.ranking.build`（默认口径：全院 + 临床科室 + 主要指标） | 每月 1 日 01:30 预生成上月排名，让科室主任上班就能看 |
| `m22_dept_doctor_monthly` | `0 2 1 * *` | 投递 `m22.dept.doctor.refresh` | 每月 1 日 02:00 刷新医师报表 |
| `m22_dept_log_archive` | `0 3 1 * *` | 归档 `m22_report_dept_log` 超过 24 个月的分区 | 与数据结构文档附录 C 的归档策略一致 |
| `m22_dept_cache_cleanup` | `0 4 * * *` | 清理 `m22:dept:*` 下已过期的空结果标记键 | 处理 Redis 惰性删除残留 |

**每月 1 日为什么排三个任务而不是一个。** 目标评估（07:00）要读当月数据，当天就要给出预测；排名生成（01:30）要读上月结账数据，必须等 M17-01 结账完成；医师刷新（02:00）依赖排名生成的部分中间结果，排在其后 30 分钟。三者时间错开是为了避免同一时刻争抢数据库连接池。

## 8. 业务规则

本章的规则是**可执行约束**，不是设计原则的复述。每条规则都指明落点：落在数据库（DB）、落在 Service（SVC）、落在前端（UI）。落点是唯一确定的，同一个规则不允许两处都实现，防止两处实现不一致时以谁为准的扯皮。

### 8.1 取数与不造数规则

| 规则编号 | 规则内容 | 落点 | 违反后果 |
|---|---|---|---|
| R-8.1-1 | M22-04 不得直接查询任何业务模块的表（如 `m05_*`、`m17_*`、`m07_*`），只能通过 `GET /internal/v1/*` 内部接口取数 | SVC（数据层封装）+ 架构扫描 | 上游口径变更时 M22 静默出错，且绕过上游权限 |
| R-8.1-2 | 上游返回 `null` 时，`metric_value` 必须写 `NULL`，禁止 `or 0`、禁止 `COALESCE(..., 0)` | SVC | 把「没数据」显示成「业务量为 0」，会误导管理决策 |
| R-8.1-3 | 上游不可用时（超时/5xx），整行 `source_status = 'FAILED'` 且 `data_source_note` 写明原因，页面标红提示，**不写部分值** | SVC + UI | 半截数据比没数据更危险 |
| R-8.1-4 | 金额字段只做**展示与对比**，禁止在 M22 内对 `*_amount` 做加减汇总；科室结余一律取 M17-04 已算好的 `surplus_amount` | SVC | 出现「M22 算的结余与 M17 不一致」，审计无法解释 |
| R-8.1-5 | M17-04 返回 `data_status = 'PROVISIONAL'` 时，所有展示该数据的页面必须挂「暂估」角标 | UI | 未结账数据被当作决算对外发布 |
| R-8.1-6 | M17-04 返回 `period_closed = false` 时，该期间排名榜必须显示「财务未结账，排名仅供参考」 | UI | 财务修正后排名变动，被质疑数据造假 |

**R-8.1-1 的落地方式。** 不是靠开发者自觉。`app/repositories/m22/dept_report_repo.py` 只注入 `M22Base` 的 9 个模型，任何跨模块模型的 `import` 会在 CI 的 `flake8` 自定义规则 `M22-DIRECT-DB-ACCESS` 中报错。取数统一走 `app/clients/m22_dept.py` 里的 8 个 HTTP 客户端方法，这些方法内部只做三件事：拼参数、发请求、按 Pydantic Schema 校验响应。响应校验失败一律抛 `UpstreamSchemaError`，转成 `"2204035"`。

### 8.2 排名固化规则

| 规则编号 | 规则内容 | 落点 | 违反后果 |
|---|---|---|---|
| R-8.2-1 | 排名批次一旦 `FROZEN`，任何字段不可修改，包括 `rank_no`；`is_deleted` 恒为 `FALSE` | DB（`ck_m22_report_dept_ranking_no_delete`）+ SVC | 历史排名被事后篡改，失去公信力 |
| R-8.2-2 | 纠错只能新建批次，旧批次通过 `superseded_by_batch_no` 指向新批次，新旧两批完整保留 | SVC | 只剩新批次时无法回答「上个月为什么是这个名次」 |
| R-8.2-3 | 排名必须绑定 `metric_version`，且 `metric_version` 进唯一约束 | DB | 口径升级后新旧排名混在同一期间无法区分 |
| R-8.2-4 | 同一期间同一口径同一分组，同时只能有**一个**有效批次（`superseded_by_batch_no IS NULL`） | SVC（固化前先查） | 页面上出现两套名次 |
| R-8.2-5 | 分母为零的科室不占名次，`exclude_reason = 'DENOMINATOR_ZERO'`，页面显示「—」而非 0 或最后一名 | DB（`ck_..._denominator_zero`）+ UI | 把「没开展该业务」排成「业务垫底」 |
| R-8.2-6 | 样本不足的科室**保留名次**，只加「仅供参考」标注，不剔除 | DB（`rank_eligible` 不含样本条件）| 小科室被系统性排除在榜单外，失去改进动力 |
| R-8.2-7 | `NULL` 排序一律 `NULLS LAST` | DB（`sort_rule_json` 快照固定）+ SVC | PostgreSQL `ORDER BY ... DESC` 默认 `NULLS FIRST`，缺数科室会排到第一名 |

**R-8.2-7 是 PostgreSQL 的一个真实陷阱，值得展开。** 在很多开发者的直觉里，「降序排列时空值应该排最后」。但 PostgreSQL 的默认行为是：`ASC` 时 `NULLS LAST`，`DESC` 时 `NULLS FIRST`。原因是 PG 认为空值比任何值都「大」，降序就是从大到小，所以空值先出。如果排名 SQL 写成 `ORDER BY metric_value DESC` 而不显式指定，所有缺数据的科室会集体排到榜首。本子模块在 SQL 里**每一层 ORDER BY 都显式写 `NULLS LAST`**，并且在 `sort_rule_json` 里把完整排序规则快照下来，方便事后核对。

### 8.3 对比与归一化规则

| 规则编号 | 规则内容 | 落点 | 违反后果 |
|---|---|---|---|
| R-8.3-1 | 分母（基线值）为 0 或 NULL 时，`delta_rate` 必须为 `NULL`，同时 `comparability_flag = FALSE` | DB（`ck_..._baseline_zero`） | 显示 100%、∞ 或 0 都是错的 |
| R-8.3-2 | 两期天数不同时必须归一化，`norm_method` 不得留 `NONE` | SVC（自动判定）+ UI（展示归一化说明） | 2 月比 1 月天然少 7%，被误读为业绩下滑 |
| R-8.3-3 | 归一化方式一经写入不可变更（`_compare` 行内固化），保证同一条对比记录的解释稳定 | DB（行不更新，重算走新行） | 同一行数据被两种方式解读 |
| R-8.3-4 | `BASELINE` 类型的 `baseline_period` 不得等于 `period` | SVC | 自己跟自己比，恒为 0 增长 |
| R-8.3-5 | `PEER` 类型分组内科室数 < 3 时，`comparability_flag = FALSE` 且 `comparability_reason = 'PEER_TOO_FEW'`，同时退化到上级分组并提示 | SVC | 2 个科室比出来的「均值」没有统计意义 |
| R-8.3-6 | 新设科室（本期有数据、基线期无数据）标 `NEW_DEPT`，不算增长也不算下降 | SVC | 新科室从 0 起步会算出天文数字的增长率 |
| R-8.3-7 | 口径变更（`metric_version` 不同）的两期数据不得直接对比，标 `CALIBER_CHANGED` 并给出两个版本号 | SVC | 口径变了还比，结论完全失真 |

**R-8.3-2 的自动判定逻辑。** `norm_method` 不是让用户手选的，而是服务端按指标类型与期间天数自动决定，用户只能看到「已按日均归一化」这样的说明文字：

- 金额类（`AMOUNT`）、数量累计类（`COUNT`，如人次、台次）：两期天数不同 → `DAYS_RATIO`；天数相同 → `NONE`
- 比率类（`RATE`、`PERCENT`）、均值类（`AVG`）：本身已消除天数影响 → 始终 `NONE`
- 时长类（`DURATION`）：`DAYS_RATIO`
- 存在特殊季节性（如视光暑期）且用户显式指定了对比日范围 → `SAME_DAYS`

### 8.4 目标与预警规则

| 规则编号 | 规则内容 | 落点 | 违反后果 |
|---|---|---|---|
| R-8.4-1 | 同一科室同一指标同一期间只能有一个 `APPROVED` 目标 | DB（部分唯一索引 `WHERE approval_status = 'APPROVED'`） | 两个目标并存，达成率算谁的 |
| R-8.4-2 | 目标一经批准，修改必须新建 `target_version`，原版本保留 | SVC | 目标被事后调低，等于没定目标 |
| R-8.4-3 | 审批人不得是目标提交人（`approved_by <> submitted_by`） | SVC | 自己定目标自己批，失去管控 |
| R-8.4-4 | `target_value` 不得为 0（避免达成率除零） | DB（`ck_..._target_nonzero`） | 达成率溢出 |
| R-8.4-5 | 月份未结束时，`ON_TRACK` 判定阈值用 `time_progress_rate × 0.900000`，不得直接比 100% | SVC | 每月 1 号所有科室都被判「未达成」 |
| R-8.4-6 | 期间已结束（`period` 早于当前月）后，目标状态冻结，只允许 `ACHIEVED` 或 `MISSED` | SVC | 历史月份状态随数据修订反复变动 |
| R-8.4-7 | 状态为 `MISSED` 且已过月末时，发布 `m22.target.missed` 事件 | SVC（事件） | 科室主任无法及时收到未达成通知 |
| R-8.4-8 | 目标偏差归因（`gap_attribution`）在 `MISSED` 状态下必填 | DB（`ck_..._gap_attribution`） | 只报未达成不说原因，无法改进 |

**R-8.4-5 的 0.9 系数来自哪。** 假设一个科室的业务量在月内是均匀分布的，那么第 t 天结束时合理的达成率就是 `t / 当月天数`。但实际业务有工作日效应：25 号之前通常已完成 85%~90% 的工作量。用 `time_progress_rate × 0.9` 作为下限，意味着「只要不显著落后于时间进度就算正常」。0.9 这个系数在 2025 年第四季度用三个月历史数据回测确定：取 0.9 时，真正最终未达成的科室中有 82% 在月内提前 7 天以上被预警，而误报率为 11%；取 1.0 时误报率升至 47%，取 0.8 时提前预警率降到 55%。因此 0.9 是误报与漏报的平衡点。

### 8.5 医师报表规则

| 规则编号 | 规则内容 | 落点 | 违反后果 |
|---|---|---|---|
| R-8.5-1 | 医师排名只在**本科室内**排名，不提供全院医师排名（`rank_scope` 只允许 `DEPT`） | DB（`ck_..._rank_scope`） | 跨科室比医师工作量无临床意义（手术科室天然高于门诊） |
| R-8.5-2 | 同一医师跨科室支援时，工作量按**归属科室**归集，`biz_dim` 记录发生科室 | SVC | 支援科室重复计算同一台手术 |
| R-8.5-3 | 同一指标同一医师可能有多条来源（M07-07 排班口径 / M05-07 挂号口径），`source_module` 进唯一约束，两值并列展示 | DB | 两条数据互相覆盖，丢掉一个口径 |
| R-8.5-4 | 医师个人报表只展示聚合指标，不含患者明细；查看明细必须先过下钻权限 | SVC + UI | 绕过权限看到患者信息 |
| R-8.5-5 | 医师数据不足（M07-07 返回空）时整行不展示，不显示 0 | SVC | 新入职医师被显示为零工作量 |
| R-8.5-6 | 科室医师数 ≤ 1 时，`rank_percentile` 返回 `NULL` | SVC | 一个人跟自己比，百分位无意义 |

### 8.6 导出与下钻规则

| 规则编号 | 规则内容 | 落点 | 违反后果 |
|---|---|---|---|
| R-8.6-1 | 导出必须引用 M22-03 的 `template_code`，不得在 M22-04 自建导出模板表 | SVC + DB | 两套模板定义不一致 |
| R-8.6-2 | 导出文件内必须包含数据来源、生成时间、口径版本、`source_status` 脚注 | SVC（模板填充） | 导出文件脱离系统后无法判断数据新鲜度 |
| R-8.6-3 | 单次导出上限 50,000 行，超限提示缩小范围 | SVC | 20 万行 Excel 打不开且拖垮内存 |
| R-8.6-4 | 下钻必须调上游内部接口，M22-04 不落任何明细数据 | SVC | 明细与上游不一致，且突破数据权限边界 |
| R-8.6-5 | 下钻参数由 `param_template` 从上下文解析，禁止前端直接传上游接口地址 | SVC | 成为任意内部接口的跳板（SSRF） |
| R-8.6-6 | 下钻结果行数超过 `max_rows` 时截断并提示，不返回全部 | SVC | 一次点击拖出几十万行 |
| R-8.6-7 | 下钻若涉及患者信息，`mask_sensitive = TRUE` 时对证件号、手机号打码 | SVC | 敏感信息落到报表页面 |

### 8.7 科室范围与历史归属规则

| 规则编号 | 规则内容 | 落点 | 违反后果 |
|---|---|---|---|
| R-8.7-1 | 科室主数据唯一来源 M01-01，M22-04 不得建科室主数据表 | DB（不建表）+ 架构评审 | 两套科室字典 |
| R-8.7-2 | 科室合并/拆分/更名时，历史期间仍按当时的科室归属展示，不做追溯重算 | SVC（`_scope` 快照） | 科室改名后所有历史报表跟着变，无法与去年对比 |
| R-8.7-3 | 科室停用后，其历史期间数据仍可查，但不出现在当前期间的下拉列表 | SVC | 历史数据凭空消失 |
| R-8.7-4 | 用户无权限查看某科室时，返回空列表而非 403 | SVC | 通过错误码探测组织架构 |

**R-8.7-2 的具体做法。** `m22_report_dept_scope` 记录每个 `(period, dept_id)` 在**该期间**的科室名称、所属父科室、科室类型、床位档。生成期间数据时先落快照，之后任何时候展示历史期间都读快照而不是读 M01-01 当前值。当 M01-01 发生科室变更事件 `m01.dept.changed` 时，M22-04 只更新**当前及未来期间**的快照，历史期间不动。这样「2025 年 3 月眼科病区」永远是当时的那个科室，即使 2026 年它被拆成了两个病区。

## 9. 权限设计

### 9.1 权限编码与角色矩阵

权限编码遵循共享规范 §12：`m22:{子模块}:{动作}`，本子模块为 `m22:04:{动作}`。共有 9 个权限点。

| 权限编码 | 含义 | 对应接口 |
|---|---|---|
| `m22:04:view` | 查看本权限范围内的科室报表、对比、排名 | API-01~API-03、API-05、API-06、API-08~API-10、API-13、API-15、API-21~API-23、API-26 |
| `m22:04:create` | 新建/维护科室报表配置 | API-17 |
| `m22:04:edit` | 修改目标、提交审批、填写归因 | API-17、API-18、API-20 |
| `m22:04:approve` | 审批科室目标、审批越权数据范围 | API-19 |
| `m22:04:exec` | 触发重算、生成排名批次、作废批次 | API-04、API-07、API-11、API-14、API-27 |
| `m22:04:export` | 导出科室报表 | API-24、API-25 |
| `m22:04:drill` | 下钻到上游明细 | API-27 |
| `m22:04:sensitive` | 查看未脱敏的敏感字段、查看全科室对比 | API-06（PEER 全组）、API-27（敏感明细） |
| `m22:04:admin` | 科室报表配置的最高权限 | 所有配置类写接口 |

### 9.2 角色与权限矩阵

角色定义沿用共享规范 §12.1，本子模块涉及 7 个角色。

| 角色 | view | create | edit | approve | exec | export | drill | sensitive | admin |
|---|---|---|---|---|---|---|---|---|---|
| 院领导 | 全院 | — | — | — | — | ✓ | ✓ | ✓ | — |
| 科室主任 | 本科室 | — | ✓ | ✓ | ✓ | ✓ | ✓ | — | — |
| 临床医师 | 本科室 | — | — | — | — | — | — | — | — |
| 质控专员 | 全院只读 | — | — | — | — | ✓ | ✓ | ✓ | — |
| 运营专员 | 全院 | ✓ | ✓ | — | ✓ | ✓ | ✓ | ✓ | — |
| 财务人员 | 财务相关科室 | — | — | — | — | ✓ | ✓ | ✓ | — |
| 系统管理员 | 全部 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

**科室主任的 `approve` 权限有个边界**：只能审批**自己科室**的目标，不能审批其他科室。这一点在 Service 层判断，而不是靠数据范围过滤 —— 因为数据范围过滤是「查询时看不到」，而审批是「看得到但不允许改」。API-19 会显式比对 `target.dept_id` 与当前用户 `managed_dept_ids`，不匹配返回 `"2204006"`。

### 9.3 数据范围过滤规则

数据范围过滤按以下优先级依次判定，**命中即返回**，不继续往下走：

1. **院领导、系统管理员、质控专员**：全院。不经过 `m22_report_dept_scope` 过滤，直接查全部。
2. **科室主任**：`dept_id IN (managed_dept_ids)`。`managed_dept_ids` 从 M01-02 的 `GET /internal/v1/staff/{id}/brief` 取 `managed_dept_id`，若为空则退化为 `dept_id` 本人科室。
3. **临床医师**：`dept_id = 本人科室`。医师不能看本科室之外的数据，但可以看本科室全部医师的汇总（P06 的医师列表里可以看到同事的名次）。
4. **财务人员**：按 M17-01 的期间状态过滤 —— 未结账期间只显示暂估数据，不显示排名（排名基于未结账数据不可靠）。
5. **其他情况（含权限配置缺失）**：返回空列表 + `data_scope_hint = 'NO_PERMISSION'`，HTTP 状态码仍为 200。

**为什么第 5 条返回 200 空列表而不是 403。** 共享规范 §20 明确「无数据权限时返回空列表，不返回 403」。理由是 403 会泄露「这个科室存在但你没权限」的信息，攻击者可以通过枚举科室 ID 探索组织架构。空列表配合 `data_scope_hint` 字段既保证了安全性，又让前端能给出友好提示（「您暂无查看该科室数据的权限」）。

### 9.4 敏感字段与脱敏

| 字段 | 敏感级别 | 默认脱敏规则 | 需要权限 |
|---|---|---|---|
| 医师姓名（P06） | 一般 | 不脱敏 | `m22:04:view` |
| 医师个人绩效分 | 敏感 | 只显示等级不显示分值 | `m22:04:sensitive` |
| 患者姓名（P08 下钻） | 高敏 | 显示「张**」 | `m22:04:drill` |
| 患者证件号（P08 下钻） | 高敏 | 显示「3101**********1234」 | `m22:04:sensitive` |
| 患者手机号（P08 下钻） | 高敏 | 显示「138****5678」 | `m22:04:sensitive` |
| 科室结余金额 | 敏感 | 只显示收入与成本，不显示结余 | `m22:04:sensitive` |

**科室结余为什么默认脱敏。** 科室结余直接决定科室绩效分配，在未正式公布前属于敏感信息。科室主任默认只能看到收入、成本、结余率，看不到绝对结余金额；财务人员和院领导才能看到绝对金额。这个限制在 API-03 的响应组装阶段实施，不是前端隐藏 —— 后端根本不返回该字段。

### 9.5 权限校验的落点

权限校验分三层，**三层都必须通过**：

1. **网关层**：校验 JWT 有效性与用户角色，注入 `X-User-Id`、`X-User-Roles`、`X-Dept-Ids` 请求头。
2. **路由层**：FastAPI 依赖 `require_permission("m22:04:xxx")`，从 `X-User-Roles` 解析角色并比对权限矩阵。失败返回 403 与 `"229001"`（权限不足统一走模块通用错误码，避免为权限单独占号段）。
3. **Service 层**：根据 `managed_dept_ids` 与请求参数做数据范围判决，必要时把 `dept_ids` 参数改写成实际可访问集合。**改写必须发生在这里**，因为路由层不知道业务语义（比如「科室主任请求 A 科室的对比」应该被改写成「返回空」而不是「放弃 A 改成自己的科室」）。
