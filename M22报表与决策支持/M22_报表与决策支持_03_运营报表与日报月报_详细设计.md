## 1. 业务概述

### 1.1 业务背景

二级眼科医院的管理层每天早会前需要一眼看清昨天的经营情况：门诊量多少、收入多少、手术做了几台、视光配镜卖了多少、与上周同期比是涨是跌。每月初需要一份覆盖全院、分科室、带同比环比的经营月报，作为院务会材料与绩效核定依据。

在没有统一报表模块之前，这组需求由三类临时手段满足：财务导出 Excel 手工拼接、HIS 厂商提供的固定格式报表、各科室自己维护的统计表。由此产生三个反复出现的问题：

| 问题 | 表现 | 后果 |
|---|---|---|
| 同一指标多个数 | 门诊量在财务报表、医务报表、院长日报三个地方不一致 | 会上对不上数，决策依据失效 |
| 口径改了老报表跟着变 | 收入口径调整后，重新打开上个月的报表，数字变了 | 审计无法回溯，「上月的数跟当时汇报的不一样」 |
| 上游异常时静默填 0 | 医保接口超时，日报里医保收入显示 0 | 院长误判为「医保收入归零」 |

M22-03 的职责就是把这组需求固化成一套**有模板、有快照、有口径、有留痕、有降级策略**的报表生产流水线。

### 1.2 为什么必须是独立子模块

运营报表与日报月报之所以独立成一个子模块，而不是并入 M22-04 科室报表或 M22-08 财务看板，有四个不可合并的理由。

**理由一：它是 M22 全模块的骨架提供者，具有先决依赖地位。**

M22 全模块 8 个子模块共需生成 40 余种报表（日报 3 种、月报 6 种、科室报表 8 种、视光分析 5 种、屈光分析 4 种、临床质量 7 种、财务看板 7 种）。若各子模块各自定义模板结构、实例编号、行数据存储、订阅机制，则会出现：`m22_optical_template`、`m22_dept_template`、`m22_finance_template` 等 5~8 套同义表；报表实例编号规则各自一套（`OPT_REPORT_NO` / `DEPT_RPT_ID` / `VIEW_ID`）；订阅推送各自实现（重试次数 3 次 / 5 次 / 不重试）。结果是「同一个报表在两个子模块里长得不一样」。

本子模块通过定义 4 张通用骨架表（`m22_report_template` / `m22_report_instance` / `m22_report_row` / `m22_report_subscription`）把「报表长什么样、这一次是哪一份、每个格子是什么数、谁要定期收」这四件事一次性定义清楚，其他子模块只提供**内容**（各自的指标与事实表），不提供**结构**。这是 M22 能保持 40 余种报表一致性的前提。

**理由二：日报与月报是「有时间承诺」的报表，调度与容错要求高于分析类报表。**

日报有硬时间承诺：每日 06:00 生成、07:30 投递到院长及班子成员微信，早会 08:00 开始。月报有硬时间承诺：财务封账后第 1 个工作日 18:00 前出数（院务会前）。这意味着本子模块必须具备：定时调度（日 1 次 + 月 1 次 + 补偿补跑）、上游依赖等待（月报等 M17 封账）、失败重试与告警、幂等防重（补跑不产生重复日报）。

而 M22-04 科室报表、M22-05 视光分析等属于「点开即算」的按需分析类报表，无时间承诺，可承受 2~3 秒响应。两类报表的调度模型、缓存策略、失败处理完全不同，合并会导致日报被分析类报表的慢查询拖累。本子模块独立后，日报生成可以走独立的 Celery 队列与独立连接池，与分析类查询物理隔离。

**理由三：审计要求的强度不同——日报月报必须「历史不重算」。**

院长日报一旦发出，就构成对外汇报的事实。三个月后审计追问「10 月 15 日日报上的门诊量为什么是 1,832」，系统必须能原样还原当时的数字、当时的口径版本、当时的数据采集批次。这不是「再算一次」能满足的——再算一次会得到今天的数字，而口径与源数据可能已经变了。

因此本子模块的实现策略是**生成即固化**：`m22_report_instance` 固化模板版本、口径版本表 `metric_versions`、采集批次号；`m22_report_row` 固化每一行的数值、单位、来源接口。查询 P-06 时直接读固化快照，不触发任何聚合计算。而分析类报表（M22-04~M22-08）是大都允许按当前口径实时计算的。两类报表对「数据能不能变」的答案相反，合在一个模块里会让开发者混淆，最终两边都做错。

**理由四：缺数降级策略是本子模块独有的强约束。**

共享规范 §17 坑 8 明确：上游不可用时指标填 0 是严重错误。但「不能填 0」之后要做什么？答案是：标记 `source_status = PARTIAL`、记录缺失来源清单 `missing_sources`、在报表页脚输出缺数说明、在发布记录里强制填写 `missing_notice`、在订阅推送时把缺数说明带进正文。

这一整套降级行为链路（实例级标记 → 行级占位 → 页脚说明 → 发布说明 → 推送说明 → 导出水印页脚）横跨 6 个环节，是本子模块最核心的差异化设计。任何一处缺失，都会导致「半份数据静默发出」。分析类报表没有这条链路需求（点开即看，缺数时前端可直接提示），因此不适合与本子模块合并。

**小结：** 本子模块 = M22 的结构基座 + 时间承诺型报表 + 不可变快照 + 缺数降级链路。四项均具有先决性或强约束性，必须独立。

#### 1.3.3 边界判定规则

| 场景 | 判定 | 理由 |
|---|---|---|
| 需要一张新的分析报表 | 若属于 8 个子模块已有的业务主题，归对应子模块；若属于运营总览，归本子模块 | 按主题归属 |

### 1.5 核心业务价值

| 价值 | 量化目标 | 衡量方式 |
|---|---|---|
| 消除同一指标多个数 | 运营指标一致率 100% | 任取 10 个指标，日报/月报/科室报表三处数值必须相同 |

#### 3.3.2 「口径改了老报表变了」问题的解决论证

**问题陈述：** 传统实现中，报表是「查询视图 + 实时聚合」。当指标口径调整（例如「门诊人次」从「挂号数」改为「实际就诊数」），历史报表重新打开时会用新口径重算，导致 10 月 15 日日报上的门诊量从 1,832 变成 1,756。审计时无法解释：当时汇报的是哪个数？

**本设计的解决路径（四层保障）：**

| 层次 | 手段 | 解决什么 |
|---|---|---|
| 存储层 | 指标值直接落库到 `m22_report_row.value_num`，不是查询时计算 | 报表数字与口径解耦，口径变了行数据也不变 |
| 版本层 | 实例固化 `metric_versions = {"OP_VISIT_COUNT": 2}` 与 `calc_version` | 能回答「当时用的是哪版口径」 |
| 权限层 | `REVOKE UPDATE ON m22_report_row` | 即使有 bug 也改不动历史数据 |
| 流程层 | 重算 = 新实例；旧实例保留并可通过 `parent_report_no` 关联 | 口径演进可对比、可追溯 |

**效果对比：**

| 场景 | 传统实现 | 本设计 |
|---|---|---|
| 10 月 15 日日报门诊量，当天报 1,832 | 今天打开显示 1,756（新口径重算） | 今天打开仍显示 1,832（固化快照） |
| 审计问「当时用哪版口径」 | 无法回答 | 查 `metric_versions` 得 `{"OP_VISIT_COUNT": 2}` |
| 想按新口径看 10 月 15 日 | 只能看到新数，无法对比 | 生成新实例，与旧实例并列对比 |
| 发现某份报表有录入错误 | 直接改库，无痕 | 无法直接改；只能归档 + 新建 + 记操作日志 |

**代价与取舍（必须写清楚）：**

| 代价 | 影响 | 缓解措施 |
|---|---|---|
| 存储膨胀 | `m22_report_row` 年增约 58 万行 | 月分区 + 冷热分离，历史分区压缩存储 |
| 无法「一键按新口径重算全部历史」 | 需要逐期生成新实例 | 提供批量重生成任务（每期一个新实例），不覆盖旧实例 |
| 模板结构缺陷无法回溯修复 | 已生成报表结构错误只能废弃 | 生成前 DSL 强校验 + 发布前预览 |

**结论：** 用存储换可审计性。对于「构成对外汇报事实」的日报月报，可审计性优先于存储成本。分析类报表（M22-04~M22-08）可按当前口径实时计算，因为它们不构成对外汇报的固化事实。

### 3.8 报表状态机

#### 3.8.1 实例状态机

```
                     ┌──────────────┐
                     │  GENERATING  │  ← 创建实例
                     └──────┬───────┘
              生成成功       │       生成失败 / 超时 30min
              ┌─────────────┴──────────────┐
              ▼                            ▼
       ┌──────────────┐           ┌──────────────┐
       │  GENERATED   │           │    FAILED    │
       └──────┬───────┘           └──────┬───────┘
              │                          │ 人工重跑 → 新实例
   复核通过   │  ┌───────────────────────┘（旧实例保持 FAILED）
              ▼  ▼
       ┌──────────────┐
       │   REVIEWED   │
       └──────┬───────┘
              │ 发布
              ▼
       ┌──────────────┐
       │  PUBLISHED   │
       └──────┬───────┘
              │ 归档
              ▼
       ┌──────────────┐
       │   ARCHIVED   │  （终态）
       └──────────────┘

  说明：
  - GENERATED → PUBLISHED 直连：模板 require_review=FALSE 时允许跳过复核
  - GENERATED/REVIEWED → ARCHIVED：未发布的废弃实例
  - FAILED 不可直接转 GENERATED（必须新建实例，保证 report_no 不复用）
```

#### 3.8.2 实例状态定义表

| 状态 | 含义 | 是否可查看 | 是否可发布 | 是否可重跑 | 是否终态 |
|---|---|---|---|---|---|
| `GENERATING` | 正在取数并写入行数据 | 否（显示进度） | 否 | 否 | 否 |
| `GENERATED` | 生成完成，待复核 | 是 | 是（无需复核时） | 否 | 否 |
| `REVIEWED` | 复核通过，待发布 | 是 | 是 | 否 | 否 |
| `PUBLISHED` | 已发布对外 | 是 | 否 | 否 | 否 |
| `FAILED` | 生成失败 | 是（仅错误信息） | 否 | 是（生成新实例） | 否 |
| `ARCHIVED` | 已归档 | 是（历史查询） | 否 | 否 | 是 |

#### 3.8.4 推送状态机

```
     ┌─────────┐   发送成功    ┌───────────┐
     │ PENDING │──────────────►│  SUCCESS  │（终态，可写 read_at）
     └────┬────┘               └───────────┘
```

### 4.2 通用报表骨架表权威声明

`m22_report_template`、`m22_report_instance`、`m22_report_row`、`m22_report_subscription` 四张通用报表骨架表**由 M22-03 定义一次**。其他 M22 子模块（M22-04~M22-08）**通过 `template_code` 引用本表，不得重复建表**。详见数据结构文档第 1 章、4.1 节与附录 A。

### 5.1 P01 运营日报核心

#### 5.1.1 页面定位

P01 是本子模块使用频率最高的页面。院长每日 08:00 早会前需要看到「昨日全院运营快照」：门诊量、手术量、视光与屈光收入、平均客单价、床位使用率、退费金额及各自的环比与目标达成率。页面的设计目标不是「展示尽可能多的指标」，而是「让院长在 90 秒内判断昨日经营是否正常，若异常能一键定位到科室」。

因此 P01 遵守三条界面原则：

1. **首屏不超过 20 个指标行**。超过 20 行后眼球扫视效率断崖下降，超出部分必须折叠进「更多指标」分组或下钻。
2. **每个数字都必须能回答「多还是少」**。没有对比值的孤立数字一律不直接展示，必须带环比或目标达成率其中之一。
3. **缺数必须显式可见**。任何未取到的指标行显示 `—` 加悬浮原因，绝不以 0 或空白呈现。

#### 5.1.2 布局与区域

页面自上而下分为五个区域：

| 区域编号 | 区域名称 | 高度占比 | 说明 |
| --- | --- | --- | --- |
| A | 报表头与状态条 | 8% | 报表号、统计日期、生成时刻、数据完整性徽标、操作按钮 |
| B | 关键指标卡片区 | 22% | 6~8 张卡片，每张含主值、环比、目标达成率、趋势火花线 |
| C | 日报正文表格 | 45% | 按 `row_type` 渲染的分组表，含环比列与达标列 |
| D | 图表区 | 15% | 收入趋势（近 14 日）与科室贡献对比两张图 |
| E | 缺数说明页脚 | 10% | `source_status` 非 COMPLETE 时展开，完整时折叠为一行提示 |

区域 A 的字段：

| 界面元素 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| 报表号 | 文本（只读） | 是 | — | `report_no`，格式 `RI20261103-0001`，可点击复制 |
| 统计日期 | 日期选择器 | 是 | 昨日 | 可选过去 400 天内任意已生成日期 |
| 数据截至 | 文本（只读） | 是 | — | 由 `generated_at` 渲染，格式 `2026-11-03 06:00:12` |
| 完整性徽标 | 徽标 | 是 | — | `COMPLETE` 绿、`PARTIAL` 橙、`FAILED` 红、`STALE` 灰 |
| 对比基准 | 下拉 | 是 | 昨日环比 | 昨日环比 / 上周同日 / 上年同日 / 本年月日均 |
| 生成模式 | 文本（只读） | 是 | — | `AUTO` 自动 / `MANUAL` 手动 / `SUBSCRIBE` 订阅触发 |
| 刷新按钮 | 按钮 | 否 | — | 仅在 `status=FAILED` 或管理员可见 |
| 导出按钮 | 按钮 | 否 | — | 跳转 P05 并带入当前实例 |

区域 B 的关键指标卡片由模板的 `row_def` 中 `highlight_level` 非空的指标行驱动，不硬编码。默认 8 张卡片对应的指标编码：

| 卡片序号 | 指标编码 | 卡片名称 | 主值单位 | 次要信息 |
| --- | --- | --- | --- | --- |
| 1 | `OP_VISIT_COUNT` | 门诊人次 | 人次 | 环比 + 目标达成率 |
| 2 | `OP_SURGERY_COUNT` | 手术台次 | 台 | 环比 + 目标达成率 |
| 3 | `FIN_REVENUE_AMOUNT` | 总收入 | 元 | 环比 + 上年同日均对比 |
| 4 | `OPTICAL_REVENUE_AMOUNT` | 视光收入 | 元 | 环比 + 占比 |
| 5 | `REFRACTIVE_REVENUE_AMOUNT` | 屈光收入 | 元 | 环比 + 占比 |
| 6 | `AVG_ORDER_AMOUNT` | 平均客单价 | 元 | 环比 + 分位数说明 |
| 7 | `BED_OCCUPANCY_RATE` | 床位使用率 | 百分比 | 环比 + 目标线 |
| 8 | `REFUND_AMOUNT` | 退费金额 | 元 | 环比 + 退费率 |

卡片区的渲染规则：若模板未定义某个 `highlight_level` 指标（例如某院区不做屈光业务），则卡片自动隐藏并重排，不显示占位卡片。若指标值缺失（`is_null_placeholder=true`），卡片主值显示 `—`，同时整张卡片加 1px 橙色虚线边框并在右上角显示「数据未到」角标。

#### 5.1.3 字段与控件

区域 C 的正文表格按模板 `row_def` 的 `row_type` 渲染，各类型的渲染差异如下：

| 行类型 | 视觉样式 | 主值列 | 环比列 | 达标列 | 可下钻 |
| --- | --- | --- | --- | --- | --- |
| `HEADER` | 加粗深色底，跨列合并 | 空 | 空 | 空 | 否 |
| `GROUP` | 中等字重，浅灰底，`indent_level` 级缩进 | 组小计值 | 有 | 有 | 是 |
| `METRIC` | 常规字重 | 指标值 | 有 | 有（配置了目标时） | 是 |
| `SUBTOTAL` | 上边框加粗 | 小计值 | 有 | 有 | 是 |
| `TOTAL` | 上下双线，加粗 | 合计值 | 有 | 有 | 否 |

正文表格列定义：

| 列序号 | 列名 | 宽度 | 对齐 | 数据来源 | 特殊说明 |
| --- | --- | --- | --- | --- | --- |
| 1 | 序号 | 48px | 居中 | `row_seq` | 自动编号 |
| 2 | 项目名称 | 240px | 左对齐 | `row_name` | 按 `indent_level` 缩进 |
| 3 | 本期值 | 120px | 右对齐 | `value_num` 或 `col_values["current"]` | 缺失时显示 `—` |
| 4 | 单位 | 64px | 居中 | `metric_unit` | 金额显示「元」 |
| 5 | 环比 | 110px | 右对齐 | `mom_value` | 正增长绿、负增长红、缺失显示 `—` |
| 6 | 同比 | 110px | 右对齐 | `yoy_value` | 同上 |
| 7 | 目标值 | 110px | 右对齐 | `target_value` | 未配置目标时显示 `—` |
| 8 | 达成率 | 100px | 右对齐 | `achieve_rate` | 低于 0.9 显示橙色，低于 0.8 显示红色 |
| 9 | 排名 | 72px | 居中 | `rank_no` | 仅科室维度行展示 |
| 10 | 操作 | 80px | 居中 | — | 下钻、溯源、标记疑问 |

数值格式规则：金额一律两位小数并千分位分隔（`1,234,567.89`）；人次、台次为整数；比率与达成率显示为百分比并保留一位小数（`12.3%`）；`DURATION` 单位（如平均候诊时长）显示为 `12.5 分钟` 形式；`SCORE` 与 `INDEX` 显示两位小数。

对 `is_null_placeholder=true` 的行，第 3 列渲染为 `—` 并附加悬浮提示，提示文案取 `null_reason` 映射后的中文说明，例如「上游接口 `/internal/v1/m16/daily/summary/{date}` 超时，数据未取到，本次不计入合计」。

#### 5.1.4 交互与操作

P01 的主要交互路径：

| 交互 | 触发方式 | 行为 | 是否二次确认 |
| --- | --- | --- | --- |
| 切换统计日期 | 日期选择器 | 重新拉取该日期实例，页面不整页刷新 | 否 |
| 切换对比基准 | 下拉选择 | 只重算环比/同比展示列，不重新取数 | 否 |
| 展开分组行 | 点击 `GROUP` 行的展开图标 | 显示该组子行，默认全部展开 | 否 |
| 下钻科室明细 | 点击 `METRIC` 行的「下钻」 | 右侧抽屉展示该指标按科室拆分 | 否 |
| 查看指标溯源 | 点击行尾「溯源」图标 | 弹出面板显示 `metric_code`、`metric_version`、`data_source_module`、`data_source_api`、`data_batch_no` | 否 |
| 标记疑问 | 点击行尾「标记疑问」 | 生成一条待核对记录，跳转 P09 | 否 |
| 导出为 PDF | 点击导出按钮 | 跳转 P05 并预填当前 `report_no` | 否 |

下钻抽屉的行为约定：抽屉宽度占视口 40%，标题显示「`指标名称` 按科室分布」，内容为一维表格（科室、本期值、占比、环比）。抽屉数据来源为 API-03，参数为 `report_no` + `metric_code`。当该指标不支持科室维度时，抽屉显示「该指标无科室维度」空态，且「下钻」入口在渲染时即置灰，避免用户点击后才发现无数据。

「标记疑问」生成的核对记录会进入 P09 待核对队列，其 `verify_mode` 记为 `MANUAL`，并在 P08 留痕时间轴中产生一条 `VERIFY_REQUESTED` 记录。

#### 5.1.6 异常与空态

| 场景 | 判定条件 | 页面表现 |
| --- | --- | --- |

| 该日日报部分缺数 | `source_status=PARTIAL` | 橙色横幅 + 页脚缺数说明展开，正文缺数行显示 `—` |

空态与异常状态都必须保留报表头区域，使院长能够确认「我看的是哪一天、哪个报表」，避免误读为「昨日无业务」。

### 5.3 P03 报表模板管理

#### 5.3.1 页面定位

### 5.5 P05 报表导出中心

#### 5.5.1 页面定位

P05 负责把已生成的报表带出系统。报表一旦离开系统，就失去了访问控制和行级权限，因此本页面的设计重心不在「导出方便」，而在「导出可追溯」。每一次导出都要回答四个问题：谁导的、什么时候导的、导了多大范围、导出了多少行。这四个答案落库在导出任务表，形成不可删改的审计流水。

页面同时承担水印配置与下载链接生命周期管理：导出文件默认 24 小时过期，下载链接带签名，过期后需重新导出。这条设计来自一个真实教训——早期版本使用永久链接，导致离职人员的邮箱里仍保留着可访问的经营数据下载地址。

### 5.6 P06 报表订阅

### 5.8 P08 报表版本与留痕

### 5.9 P09 报表数据核对

#### 5.9.1 页面定位

P09 是「报表数字可信度」的兜底工具。报表的数据来自上游多个模块的统计接口，任何一环出错都会体现在报表上，而报表的阅读者（尤其是院长）没有能力判断数字是否可信。P09 让内控与财务能够主动发起核对：把报表中的某个指标值，与上游接口直接返回的值做比对，差异超过容差即告警。

本页面解决的是一类特殊且高频的争议：「报表上个月收入是 1,234,567.89，但财务系统里是 1,234,500.00，差 67.89 是谁错了？」核对结果会明确给出三选一的结论：一致、口径差异（预期内）、真差异（需排查）。

#### 5.9.2 布局与区域

| 区域编号 | 区域名称 | 高度占比 | 说明 |
| --- | --- | --- | --- |
| A | 核对任务发起区 | 25% | 选实例、选指标、选基准接口 |
| B | 核对结果表 | 45% | 逐指标比对结果 |
| C | 差异分析面板 | 20% | 差异明细与可能原因 |
| D | 核对报告导出 | 10% | 生成核对报告 |

区域 A 的字段：

| 界面元素 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| 报表实例 | 搜索下拉 | 是 | 当前实例 | — |
| 核对范围 | 单选 | 是 | 全部指标 | 全部指标、仅指标行、指定指标 |
| 指定指标 | 多选 | 条件必填 | — | 范围选指定指标时必填 |
| 基准接口 | 只读展示 | 是 | 自动带出 | 由指标定义中的来源接口决定 |
| 容差率 | 数字 | 是 | 0.000100 | 默认万分之一 |
| 是否含预期差异 | 开关 | 否 | 开启 | 开启后把口径差异单独标注 |

| --- | --- | --- | --- | --- |

#### 5.9.3 字段与控件

核对结论的判定规则：

| 结论 | 判定条件 | 界面表现 | 后续动作 |
| --- | --- | --- | --- |
| 一致 | 差异率绝对值不超过容差率 | 绿色对勾 | 无 |
| 不一致且预期 | 差异率超容差且 `is_expected_mismatch=true` | 蓝色信息标 | 说明口径差异来源 |
| 不一致非预期 | 差异率超容差且非预期 | 红色警告 | 需填写处理意见并派单 |
| 源不可用 | 上游接口调用失败 | 灰色 | 记录失败原因，稍后重试 |
| 跳过 | 指标无可用上游接口 | 灰色 | 展示跳过原因 |

预期差异的判定依据来自指标定义的元数据：例如某指标定义为「按收费时间统计」，而上游接口按「业务发生时间」统计，跨月时点必然出现差异，这类差异在指标定义中被标注为「允许跨期差异」。核对时系统自动读取该标记，把差异归入预期类别，避免内控人员反复排查同一类必然差异。

容差率的设定原则：

| 指标类型 | 建议容差率 | 理由 |
| --- | --- | --- |
| 金额类（AMOUNT） | 0.000100 | 金额精确到分，仅容许舍入误差 |
| 计数类（COUNT） | 0.000000 | 人次台次必须完全相等 |
| 比率类（RATE、PERCENT） | 0.000500 | 分母取整导致的合理波动 |
| 时长类（DURATION） | 0.005000 | 取整与进位差异较大 |

#### 5.9.4 交互与操作

| 交互 | 触发方式 | 行为 | 是否二次确认 |
| --- | --- | --- | --- |
| 发起核对 | 点击开始核对 | 调上游接口逐指标比对 | 否 |
| 查看来源 | 点击行尾图标 | 展示接口 URL、请求参数、响应摘录 | 否 |
| 标记处理 | 点击标记 | 填写处理意见，标记为已处理 | 否 |
| 批量核对 | 选择多个实例 | 串行执行，避免上游压力 | 是 |
| 导出核对报告 | 点击导出 | 生成含结论与差异明细的报告 | 否 |
| 重跑源不可用 | 点击重试 | 仅对源不可用行重新比对 | 否 |

核对任务的执行约束：单次核对最多 50 个指标，且对上游接口的调用采用串行加 200ms 间隔，避免核对行为本身把上游打挂。批量核对时总耗时可能达到数分钟，因此必须异步执行并在页面上显示进度。

#### 5.9.8 验收要点

| 编号 | 验收要点 |
| --- | --- |
| P09-01 | 核对结果区分四种结论，其中不一致且预期与不一致非预期在界面上颜色与文案不同 |
| P09-02 | 差异值等于报表值减上游值，界面展示值与库内存储值精度一致 |
| P09-03 | 金额类指标默认容差率 0.000100，计数类默认 0.000000 |
| P09-04 | 核对的上游调用串行执行且带间隔，避免压垮上游 |
| P09-05 | 不一致非预期的行必须填写处理意见后方可关闭 |
| P09-06 | 核对报告导出包含结论汇总、差异明细与上游接口信息 |

#### 6.2.1 请求头

| 请求头 | 必填 | 说明 |
| --- | --- | --- |
| `Authorization` | 是 | `Bearer <JWT>`，内部契约使用服务间令牌 |

#### 6.2.2 响应包装

所有对外接口统一使用如下包装结构，`code` 为 `"0"` 表示成功，非 `"0"` 为业务错误码（错误码定义见 6.6）：

```json

  "code": "0",
  "message": "成功",
  "request_id": "req-20261103-000001",
  "data": {},
  "timestamp": "2026-11-03T06:00:12+08:00"
}
```

分页接口在 `data` 中返回 `items`、`total`、`page`、`page_size`：

```json
{
  "code": "0",
  "message": "成功",
  "request_id": "req-20261103-000002",
  "data": {
    "items": [],
    "total": 0,
    "page": 1,
    "page_size": 20
  },
  "timestamp": "2026-11-03T06:00:12+08:00"
}
```

#### 6.2.3 数值精度约定

| 数据类型 | 传输格式 | 说明 |
| --- | --- | --- |
| 金额 | 字符串，两位小数 | `"1234567.89"`，避免 JavaScript 浮点误差 |
| 指标值 | 字符串，最多六位小数 | `"1234567.890000"` |
| 比率 | 字符串，六位小数 | `"0.333333"` |
| 计数 | 整数 | `12345` |
| 期间 | 字符串 | 日报 `"2026-11-03"`、月报 `"2026-10"` |

金额与指标值必须以字符串传输。原因是一旦用 JSON 数字传输，JavaScript 的 IEEE 754 双精度在超过 2 的 53 次方后会丢精度，虽在 1 亿范围内尚可，但前端做累加时仍会产生误差。用字符串可让前端明确使用定点运算库。

### 6.5 Service 层实现

Service 层承载全部业务规则。以下四个 Service 是本子模块最核心的实现，其余 Service 结构相似，此处列出其职责与关键方法签名。

**职责一览：**

| Service | 主要职责 | 关联规则 |
| --- | --- | --- |
| `TemplateService` | 模板保存、发布、DSL 校验、指标引用完整性 | BR-TPL、BR-DSL |
| `InstanceService` | 实例查询、行数据、下钻、缺数明细 | BR-INS、BR-NUL |
| `GenerateService` | 取数编排、完整性判定、行固化 | BR-INS、BR-STS、BR-HIS |
| `ExportService` | 导出台账、水印、签名链接 | BR-EXP |
| `SubscriptionService` | 订阅配置校验、下次推送时刻计算 | BR-SUB |
| `PublishService` | 复核、发布、撤回、缺数说明强制 | BR-PUB |
| `TraceService` | 口径快照、留痕查询 | BR-HIS |
| `VerifyService` | 核对编排、容差判定 | BR-VER |
| `ContractService` | P-06、P-07 契约实现 | 契约稳定性 |

`GenerateService` 是本模块最关键的实现。它必须同时满足「绝不静默填 0」与「历史不重算」两条铁律：

```python
"""报表生成服务：取数编排、完整性判定、行固化。"""

from __future__ import annotations

import asyncio
from dataclasses import dataclass
from datetime import datetime, timedelta
from decimal import Decimal
from typing import Any, Final

from sqlalchemy import select, update
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.errors import BizError
from app.models.m22.report import ReportInstance, ReportRow, ReportTemplate
from app.services.m22.metric_client import MetricClient, MetricValue

# 单期取数允许的上游并发数，避免把上游统计接口打满
MAX_UPSTREAM_CONCURRENCY: Final[int] = 8
# 取数超时（秒）；超时即视为该指标缺失，不做重试填充 0
UPSTREAM_TIMEOUT_SEC: Final[float] = 6.0
# 缺数占比超过该阈值视为上游整体不可用，任务判定失败
FAIL_FAST_RATIO: Final[Decimal] = Decimal("0.300000")


@dataclass(frozen=True)
class MetricFetchError:
    """单个指标取数失败的结构化记录，用于组装 missing_sources。"""

    metric_code: str
    source_module: str
    source_api: str
    reason: str


class GenerateService:
    """报表生成：模板解析 -> 指标取数 -> 行固化 -> 完整性标记。"""

    def __init__(self, session: AsyncSession, metrics: MetricClient) -> None:
        self.session = session
        self.metrics = metrics

    async def generate(self, report_no: str, template_code: str, period: str) -> ReportInstance:
        """生成一期报表。

        步骤：
        1. 读取模板当前已发布版本，计算行定义与所需指标集合；
        2. 并发取数，超时或异常的指标记入 errors，绝不填 0；
        3. 按 row_def 计算行值，缺失行写 NULL 占位并标记 is_null_placeholder；
        4. 判定 source_status；缺数占比超阈值则整单失败；
        5. 固化行数据并更新实例状态。
        """
        tpl = await self._load_published_template(template_code)
        metric_codes = self._collect_metric_codes(tpl)
        values, errors = await self._fetch_metrics(metric_codes, period, report_no)

        total = len(metric_codes)
        missing = len(errors)
        ratio = (Decimal(missing) / Decimal(total)) if total else Decimal("0")
        if total and ratio > FAIL_FAST_RATIO:
            await self._mark_failed(report_no, errors, ratio)
            raise BizError("2203018", f"上游不可用指标比例 {ratio:.2%}，超过阈值，任务失败")

        rows = self._build_rows(tpl, values, report_no, period)
        source_status = "COMPLETE" if missing == 0 else "PARTIAL"
        await self._persist(report_no, rows, source_status, errors)
        return await self._reload(report_no)

    async def _fetch_metrics(
        self, codes: list[str], period: str, report_no: str
    ) -> tuple[dict[str, MetricValue], list[MetricFetchError]]:
        """并发取数；任何异常都转成 MetricFetchError，不向上抛、不填 0。"""
        sem = asyncio.Semaphore(MAX_UPSTREAM_CONCURRENCY)

        async def one(code: str) -> tuple[str, MetricValue | MetricFetchError]:
            async with sem:
                try:
                    value = await asyncio.wait_for(
                        self.metrics.fetch(code, period, trace_id=report_no),
                        timeout=UPSTREAM_TIMEOUT_SEC,
                    )
                    return code, value
                except asyncio.TimeoutError:
                    return code, MetricFetchError(code, "UNKNOWN", "UNKNOWN", "TIMEOUT")
                except BizError as exc:
                    return code, MetricFetchError(code, "UNKNOWN", "UNKNOWN", exc.code)

        results = await asyncio.gather(*(one(code) for code in codes))
        values: dict[str, MetricValue] = {}
        errors: list[MetricFetchError] = []
        for code, payload in results:
            if isinstance(payload, MetricFetchError):
                errors.append(payload)
            else:
                values[code] = payload
        return values, errors

    def _build_rows(
        self,
        tpl: ReportTemplate,
        values: dict[str, MetricValue],
        report_no: str,
        period: str,
    ) -> list[ReportRow]:
        """按模板 row_def 展开行；缺失指标生成 NULL 占位行而非 0。"""
        rows: list[ReportRow] = []
        metric_acc: dict[str, Decimal] = {}
        for idx, definition in enumerate(tpl.row_def, start=1):
            row_type = definition["row_type"]
            row = ReportRow(
                report_no=report_no,
                template_code=tpl.template_code,
                period=period,
                row_seq=definition.get("row_seq", idx),
                row_key=definition["row_key"],
                row_type=row_type,
                row_name=definition["row_name"],
                indent_level=definition.get("indent_level", 0),
                group_key=definition.get("group_key"),
                metric_unit=definition.get("metric_unit", "COUNT"),
            )
            if row_type == "METRIC":
                code = definition["metric_code"]
                if code in values:
                    row.metric_code = code
                    row.metric_version = values[code].version
                    row.value_num = values[code].value
                    row.source_status = "COMPLETE"
                    metric_acc[definition["group_key"] or ""] = (
                        metric_acc.get(definition["group_key"] or "", Decimal("0")) + values[code].value
                    )
                else:
                    row.metric_code = code
                    row.metric_version = definition.get("metric_version", 1)
                    row.value_num = None
                    row.is_null_placeholder = True
                    row.null_reason = f"指标 {code} 未取到数据，见缺数明细"
                    row.source_status = "PARTIAL"
            elif row_type in {"GROUP", "SUBTOTAL", "TOTAL"}:
                key = definition.get("group_key") or ""
                if key in metric_acc:
                    row.value_num = metric_acc[key]
                elif definition.get("sum_from"):
                    sources = definition["sum_from"]
                    present = [values[s] for s in sources if s in values]
                    if present:
                        row.value_num = sum((v.value for v in present), Decimal("0"))
                row.source_status = "COMPLETE"
            rows.append(row)
        return rows

    def _collect_metric_codes(self, tpl: ReportTemplate) -> list[str]:
        """从模板 row_def 收集全部指标编码，去重保序。"""
        seen: dict[str, None] = {}
        for definition in tpl.row_def:
            code = definition.get("metric_code")
            if code and code not in seen:
                seen[code] = None
        return list(seen)

    async def _load_published_template(self, template_code: str) -> ReportTemplate:
        stmt = select(ReportTemplate).where(
            ReportTemplate.template_code == template_code,
            ReportTemplate.is_published.is_(True),
            ReportTemplate.status == "PUBLISHED",
        )
        tpl = (await self.session.execute(stmt)).scalar_one_or_none()
        if tpl is None:
            raise BizError("2203002", f"模板 {template_code} 不存在或未发布")
        return tpl

    async def _persist(
        self,
        report_no: str,
        rows: list[ReportRow],
        source_status: str,
        errors: list[MetricFetchError],
    ) -> None:
        """行数据与实例状态在同一事务内落库，保证不出现有实例无行的情况。"""
        self.session.add_all(rows)
        metric_rows = sum(1 for r in rows if r.row_type == "METRIC")
        await self.session.execute(
            update(ReportInstance)
            .where(ReportInstance.report_no == report_no)
            .values(
                source_status=source_status,
                missing_sources=[
                    {
                        "metric_code": e.metric_code,
                        "source_module": e.source_module,
                        "source_api": e.source_api,
                        "reason": e.reason,
                    }
                    for e in errors
                ]
                or None,
                degraded_count=len(errors),
                row_count=len(rows),
                metric_row_count=metric_rows,
                generated_at=datetime.now(),
                status="GENERATED",
            )
        )
        await self.session.commit()

    async def _mark_failed(self, report_no: str, errors: list[MetricFetchError], ratio: Decimal) -> None:
        await self.session.execute(
            update(ReportInstance)
            .where(ReportInstance.report_no == report_no)
            .values(
                status="FAILED",
                source_status="FAILED",
                source_status_reason=f"上游不可用指标比例 {ratio:.2%} 超过阈值",
                missing_sources=[
                    {
                        "metric_code": e.metric_code,
                        "source_module": e.source_module,
                        "source_api": e.source_api,
                        "reason": e.reason,
                    }
                    for e in errors
                ],
            )
        )
        await self.session.commit()

    async def _reload(self, report_no: str) -> ReportInstance:
        stmt = select(ReportInstance).where(ReportInstance.report_no == report_no)
        instance = (await self.session.execute(stmt)).scalar_one()
        await self.session.refresh(instance)
        return instance
```

`TraceService` 的口径快照是「历史报表不重算」的可见证据，实现要点是**只读**——它不允许改写实例上的 `metric_versions`：

```python
"""留痕服务：口径快照与操作留痕查询。"""

from __future__ import annotations

from typing import Final

from sqlalchemy import func, select
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.errors import BizError
from app.models.m22.report import ReportInstance, ReportOperLog
from app.services.m22.metric_client import MetricClient

CONSISTENT_NOTE: Final[str] = "口径未变，可直接比较"
FROZEN_NOTE: Final[str] = (
    "该报表按 V{used} 计算，当前最新为 V{latest}，"
    "后续报表按 V{latest} 计算，本报表不做回溯重算"
)


class TraceService:
    def __init__(self, session: AsyncSession, metrics: MetricClient) -> None:
        self.session = session
        self.metrics = metrics

    async def get_metric_versions(self, report_no: str) -> dict:
        """返回实例口径快照；快照一经写入永不修改。"""
        stmt = select(ReportInstance).where(ReportInstance.report_no == report_no)
        instance = (await self.session.execute(stmt)).scalar_one_or_none()
        if instance is None:
            raise BizError("2203004", f"报表实例 {report_no} 不存在")
        snapshot: dict[str, int] = instance.metric_versions or {}
        if not snapshot:
            raise BizError("2203040", "该实例生成于口径快照功能上线前，无版本留痕")

        latest = await self.metrics.latest_versions(list(snapshot.keys()))
        items = []
        for code, used in snapshot.items():
            current = int(latest.get(code, used))
            consistent = current == used
            items.append(
                {
                    "metric_code": code,
                    "metric_name": latest.names.get(code, code),
                    "used_version": used,
                    "latest_version": current,
                    "is_consistent": consistent,
                    "note": CONSISTENT_NOTE
                    if consistent
                    else FROZEN_NOTE.format(used=used, latest=current),
                }
            )
        return {
            "report_no": report_no,
            "period": instance.period,
            "calc_version": instance.calc_version,
            "items": items,
        }

    async def list_trace(self, filters: dict, page: int, size: int) -> dict:
        """按对象与时间查询留痕，利用分区裁剪减少扫描量。"""
        stmt = select(ReportOperLog)
        if filters.get("object_type"):
            stmt = stmt.where(ReportOperLog.object_type == filters["object_type"])
        if filters.get("object_id"):
            stmt = stmt.where(ReportOperLog.object_id == filters["object_id"])
        if filters.get("operator_id"):
            stmt = stmt.where(ReportOperLog.operator_id == filters["operator_id"])
        if filters.get("time_from"):
            stmt = stmt.where(ReportOperLog.operated_at >= filters["time_from"])
        if filters.get("time_to"):
            stmt = stmt.where(ReportOperLog.operated_at <= filters["time_to"])

        total = (
            await self.session.execute(select(func.count()).select_from(stmt.subquery()))
        ).scalar_one()
        rows = (
            await self.session.execute(
                stmt.order_by(ReportOperLog.operated_at.desc()).offset((page - 1) * size).limit(size)
            )
        ).scalars().all()
        return {"items": [r.to_dict() for r in rows], "total": total, "page": page, "page_size": size}
```

`ContractService` 实现 P-06 与 P-07。P-06 的 300ms 指标依靠两项措施达成：一是只按主键查实例单行，二是行数据仅在 `include_rows=true` 时才查分区子表且限流 100 行；P-07 的 200ms 依靠「同步只落库、异步做分发」：

```python
"""内部契约服务：P-06 报表取数、P-07 导出就绪回调。"""

from __future__ import annotations

from datetime import datetime
from typing import Final

from sqlalchemy import select, update
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.errors import BizError
from app.models.m22.report import ReportExportTask, ReportInstance, ReportOperLog, ReportRow
from app.tasks.m22 import dispatch_export_ready

# P-06 同步返回行数据时允许的最大行数，确保 SLA 可控
P06_ROW_HARD_LIMIT: Final[int] = 500


class ContractService:
    def __init__(self, session: AsyncSession, dispatcher=dispatch_export_ready) -> None:
        self.session = session
        self.dispatcher = dispatcher

    async def get_instance(
        self, report_no: str, include_rows: bool, row_limit: int, caller
    ) -> dict:
        """P-06：按报表号取实例，P95 <= 300ms。"""
        stmt = select(ReportInstance).where(ReportInstance.report_no == report_no)
        instance = (await self.session.execute(stmt)).scalar_one_or_none()
        if instance is None:
            raise BizError("2203004", f"报表实例 {report_no} 不存在")
        if instance.status == "GENERATING":
            raise BizError("2203005", f"报表 {report_no} 仍在生成中，请稍后重试")

        payload = {
            "report_no": instance.report_no,
            "template_code": instance.template_code,
            "template_version": instance.template_version,
            "period": instance.period,
            "source_status": instance.source_status,
            "source_status_reason": instance.source_status_reason,
            "generated_at": instance.generated_at,
            "status": instance.status,
            "is_stale": instance.is_stale,
            "metric_versions": instance.metric_versions,
            "rows": [],
        }
        if include_rows:
            limit = min(row_limit, P06_ROW_HARD_LIMIT)
            rows = (
                await self.session.execute(
                    select(ReportRow)
                    .where(ReportRow.report_no == report_no)
                    .order_by(ReportRow.row_seq)
                    .limit(limit)
                )
            ).scalars().all()
            payload["rows"] = [r.to_contract_dict() for r in rows]
        await self._write_log("INSTANCE", report_no, "CONTRACT_READ", caller.operator_id or caller.app_id)
        return payload

    async def on_export_ready(self, body, caller) -> dict:
        """P-07：导出就绪回调，P95 <= 200ms；仅落库，分发异步执行。"""
        stmt = select(ReportExportTask).where(ReportExportTask.export_no == body.export_no)
        task = (await self.session.execute(stmt)).scalar_one_or_none()
        if task is None:
            raise BizError("2203025", f"导出记录 {body.export_no} 不存在")
        if task.status not in {"PENDING", "RUNNING", "SUCCESS"}:
            raise BizError("2203027", f"导出 {body.export_no} 当前状态 {task.status} 不可回调")
        if task.status == "SUCCESS" and task.file_sha256 == body.file_sha256:
            return {
                "export_no": body.export_no,
                "accepted": True,
                "idempotent_hit": True,
                "export_status": task.status,
            }

        await self.session.execute(
            update(ReportExportTask)
            .where(ReportExportTask.export_no == body.export_no)
            .values(
                status="SUCCESS",
                file_path=body.file_path,
                file_sha256=body.file_sha256,
                file_size=body.file_size,
                exported_at=body.ready_at or datetime.now(),
            )
        )
        await self._write_log("EXPORT", body.export_no, "EXPORT_READY", caller.operator_id or caller.app_id)
        await self.session.commit()

        # 分发、归档、通知全部异步，保证同步段在 200ms 内返回
        self.dispatcher.delay(body.export_no, body.report_no, body.file_path)
        return {
            "export_no": body.export_no,
            "accepted": True,
            "idempotent_hit": False,
            "export_status": "SUCCESS",
        }

    async def _write_log(self, object_type: str, object_id: str, action: str, operator: str | None) -> None:
        self.session.add(
            ReportOperLog(
                object_type=object_type,
                object_id=object_id,
                action=action,
                operator_id=operator or "SYSTEM",
                operate_result="SUCCESS",
                operated_at=datetime.now(),
            )
        )
        await self.session.flush()
```

`SubscriptionService` 的送达时刻校验与下次推送计算：

```python
"""订阅服务：配置校验与下次推送时刻计算。"""

from __future__ import annotations

from datetime import date, datetime, time, timedelta
from decimal import Decimal
from typing import Final

from app.core.errors import BizError

# 每月送达日上限，保证 2 月等短月也能命中
MAX_DAY_OF_MONTH: Final[int] = 28


def next_push_at(
    cycle: str,
    deliver_time: time,
    now: datetime,
    weekday: int | None = None,
    day: int | None = None,
) -> datetime:
    """计算下次推送时刻。

    DAILY   ：今日未过点则今日，否则明日；
    WEEKLY  ：下一个 weekday（1=周一，7=周日）；
    MONTHLY ：本月 day 未过点则本月，否则下月；
    QUARTERLY：下一个季首月的 day。

    边界：day 超过 28 时抛错，避免短月永远不推送。
    """
    if cycle == "DAILY":
        candidate = datetime.combine(now.date(), deliver_time)
        return candidate if candidate > now else candidate + timedelta(days=1)
    if cycle == "WEEKLY":
        if weekday is None or not 1 <= weekday <= 7:
            raise BizError("2203029", "每周订阅必须指定 1 至 7 的送达星期")
        delta = (weekday - now.isoweekday()) % 7
        candidate = datetime.combine(now.date() + timedelta(days=delta), deliver_time)
        return candidate if candidate > now else candidate + timedelta(days=7)
    if cycle == "MONTHLY":
        if day is None or not 1 <= day <= MAX_DAY_OF_MONTH:
            raise BizError("2203029", f"每月订阅的送达日必须为 1 至 {MAX_DAY_OF_MONTH}")
        candidate = datetime.combine(now.date().replace(day=day), deliver_time)
        if candidate > now:
            return candidate
        year, month = (now.year + 1, 1) if now.month == 12 else (now.year, now.month + 1)
        return datetime.combine(date(year, month, day), deliver_time)
    if cycle == "QUARTERLY":
        if day is None or not 1 <= day <= MAX_DAY_OF_MONTH:
            raise BizError("2203029", f"每季订阅的送达日必须为 1 至 {MAX_DAY_OF_MONTH}")
        quarter_month = ((now.month - 1) // 3 + 1) * 3 + 1
        year = now.year + (1 if quarter_month > 12 else 0)
        month = quarter_month - 12 if quarter_month > 12 else quarter_month
        return datetime.combine(date(year, month, day), deliver_time)
    raise BizError("2203029", f"不支持的订阅周期 {cycle}")
```

**Service 层分层带来的三条约束：**

| 约束 | 内容 | 检查方式 |
| --- | --- | --- |
| 路由层不写业务规则 | 路由只做鉴权、参数校验、调用与包装 | Code Review + 单测覆盖路由层为薄层 |
| Service 不直接拼 SQL 跨模块 | 一切跨模块数据通过 `MetricClient` 调上游接口 | 架构测试扫描 SQL 中出现其他模块表前缀 |
| 数值一律 Decimal | Service 内不得出现 `float()`；取数结果直接是 Decimal | 静态检查禁用 float 字面量参与金额运算 |

第二条约束是本子模块架构的红线：只要有人在 Service 里写了一句 `SELECT SUM(amount) FROM m16_xxx`，M22 的数字就再也不能追溯到 M22-01 的指标口径，所有关于「这个数怎么来的」的审计链路都会断开。因此用架构测试而不是口头约定来守住它——测试用例遍历全部 ORM 与原生 SQL，一旦命中 `m09_`、`m10_`、`m11_`、`m12_`、`m13_`、`m14_`、`m15_`、`m16_`、`m17_` 前缀即失败。

### 6.6 错误码定义

本子模块错误码号段为 `2203001` 至 `2203999`，当前定义 40 个（`2203001` 至 `2203040`），另有模块通用错误码 `229001`。
