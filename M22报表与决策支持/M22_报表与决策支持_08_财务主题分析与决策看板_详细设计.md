## 1. 模块概述

### 1.1 模块定位

M22-08 财务主题分析与决策看板，是 M22「报表与决策支持」模块的**决策层子模块**。它把 M22-01 定义口径、M22-02 采集汇总好的指标，加工成**院长和科主任能一眼看懂的决策视图**：管理驾驶舱、院长大屏、财务主题分析、成本收益分析、预算目标达成、经营预警与异动。

**一句话定位：** M22-01 管「指标是什么」，M22-02 管「指标从哪来」，M22-03 管「报表怎么出」，**M22-08 管「给谁看、怎么看、什么时候必须报警」**。

**三个核心能力：**

| 能力 | 说明 | 典型场景 |
|---|---|---|
| **看得见** | 管理驾驶舱与院长大屏，把关键经营指标一屏聚合 | 院长早上 8 点到办公室，打开驾驶舱 30 秒掌握全院经营状况 |
| **看得懂** | 财务主题分析、成本收益分析、预算目标达成，提供同比环比与结构分解 | 财务主管分析「本月结余率下降 3 个点，是收入降了还是成本涨了」 |
| **看得住** | 经营预警与异动监控，指标越界立即推送 | 某科室药占比连续 3 天超阈值，当天推送给科主任与分管院长 |

**关键设计取舍：本子模块不做「分析引擎」，做「指标编排与呈现层」。**

真正复杂的计算（指标口径、事实汇总）在 M22-01 与 M22-02 已经完成。M22-08 的工作是：
1. **取数** —— 调 M22-02 指标事实、M17 财务接口、M16 收费接口；
2. **校准** —— 检查数据完整性，标注 `source_status`，缺失就给缺失清单，绝不填 0；
3. **落快照** —— 把「某一时刻的完整视图」固化成一份 JSONB 快照；
4. **快呈现** —— 前端读快照 + Redis 缓存，P95 ≤ 500ms；
5. **会报警** —— 按规则扫描指标，越界就推送，且**不能刷屏**。

> **为什么不做分析引擎：** 如果 M22-08 自己算指标，就会出现「驾驶舱的结余率」和「财务报表的结余率」对不上的情况——这是财务信息化里最致命的问题，一旦发生，整个系统的数字就没人信了。M22 铁律第 2 条「不算业务数、不造业务数」就是为了堵这个口子。**所有指标只能有一个出处（M22-01 口径 + M22-02 事实），M22-08 只负责换一种方式呈现。**

**与「做一张大报表」的区别：**

驾驶舱不是「把所有指标摆一屏」。设计上做了三件事：
- **分层** —— 院级驾驶舱看总量与趋势，科室驾驶舱看本科室排名与差距，移动端只看 6 个核心指标；
- **对比** —— 每个指标必须带同比/环比/目标三个参照之一，孤零零一个数字没有决策价值；
- **可下钻** —— 看到「结余率下降」能点进去看到「哪个科室、哪个成本项」。

### 1.2 为什么独立成子模块

**理由一：使用者的时间尺度完全不同。**

M22-03 运营报表是「按月出报表，供归档与上报」，M22-08 是「每天甚至每 5 分钟看一次，供现场决策」。院长大屏在门诊大厅常驻刷新，主管院长的驾驶舱是每天开机第一件事。**查看频率差 100 倍，缓存策略、刷新机制、性能预算完全不同**——前者可以等 30 秒出 PDF，后者必须 500ms 内出画面。

**理由二：预警是「推」而不是「拉」。**

所有其他 M22 子模块都是「用户来查我」，只有预警是「我发现问题主动推给你」。这带来一整套其他子模块没有的机制：定时扫描、规则引擎、冷却抑制、级别升级、确认与关闭流转、多渠道推送。**这些机制放进任何一个报表子模块都不合适**，必须独立。

**理由三：财务主题分析与法定报表的受众与口径敏感度不同。**

法定报表（资产负债表、收入费用表、现金流量表）面向外部报送，口径由国家会计准则锁定，一个数都不能动——那是 M17-08 的职责。财务主题分析面向内部管理，关注的是「收入结构变了吗」「哪块成本涨得最快」，允许按管理需要自定义维度与对比口径。**两者的变更自由度差一个数量级**：法定报表口径改一次要报备，主题分析的展示方式一个月改三次都正常。

**理由四：决策分析助手需要独立的问答边界。**

P09 决策分析助手要回答「上月屈光手术量为什么下降」这类问题，它会调用看板与主题数据做归因。但**它绝不能回答涉及患者个人身份的问题**。这条边界必须在一个独立子模块里用独立接口、独立权限、独立审计来管——混在报表里早晚会被「顺手」放开。

### 1.3 与相邻子模块的分工

| 子模块 | 职责 | 与 M22-08 的交接 |
|---|---|---|
| M22-01 指标中心与口径管理 | 指标定义、口径版本、目标值 | 提供 `metric_code` + `metric_version` 口径；提供目标值。**M22-08 不自建口径** |
| M22-02 数据采集与汇总 | 从各模块采集、校验、汇总为指标事实 | 提供 `m22_fact_metric` 指标实际值。**M22-08 不直查业务表** |
| M22-03 运营报表与日报月报 | 报表模板、实例、行数据、订阅 | 提供四张报表骨架表；财务主题报表通过 `template_code` 引用。**M22-08 不重复建表** |
| M22-04 科室报表与科室排名 | 科室维度报表与排名 | 科室排名口径复用 M22-04，M22-08 只做展示 |
| M22-05 视光经营分析 | 视光业务专题分析 | M22-08 引用其视光指标 |
| M22-06 屈光经营分析 | 屈光业务专题分析 | M22-08 引用其屈光指标 |
| M22-07 临床质量与绩效指标 | 临床质量与绩效 | M22-08 引用其质量指标用于质量系数与预警 |
| **M22-08 本子模块** | 驾驶舱、大屏、财务主题、成本收益、目标达成、经营预警、报表订阅中心、口径说明、决策助手 | — |
| M17-08 财务报表与经营分析 | **法定财务报表**（资产负债/收入费用/现金流量） | **M22-08 只调 `GET /internal/v1/m17/reports/{report_code}` 取数展示，不重做报表** |

**与 M17 的关键边界：**

```
┌────────────────────┐          ┌──────────────────────┐
│  M17-08 财务报表    │          │  M22-08 财务主题分析   │
│────────────────────│          │──────────────────────│
│ 资产负债表明细       │  P-08    │ 只取汇总数做主题展示   │
│ 收入费用表明细       │ ───────▶ │ 不复算、不落行数据     │
│ 现金流量表明细       │ 取数接口  │ 口径差异在附录 D 说明  │
│ 借贷平衡由 DB 保证   │          │ 不平则显示"数据异常"    │
└────────────────────┘          └──────────────────────┘
```

**这个边界的实质：** M17-08 保证「报表本身是对的」（会计恒等式由数据库 CHECK 强制），M22-08 保证「把它摆到院长看得懂的地方」。如果驾驶舱上的资产负债合计数与财务报表明细不一致，那是 M17-08 的 bug，不是 M22-08 去「修正」它——M22-08 必须原样展示并标注异常。

### 1.4 概念辨析

**辨析一：驾驶舱 vs 大屏 vs 移动端看板**

很多人认为「大屏 = 驾驶舱放大版」。**完全错误。** 三者是三套不同参数的产品：

| 维度 | 管理驾驶舱 `DASHBOARD` | 院长大屏 `SCREEN` | 移动端 `MOBILE` |
|---|---|---|---|
| 使用场景 | 办公室 PC，主动查看 | 门诊大厅/行政区，常驻展示 | 手机，碎片时间 |
| 观看距离 | 0.6 米 | **3~5 米** | 0.3 米 |
| 最小字号 | 12px | **≥28px** | 14px |
| 主题 | 亮色 | **必须深色**（强光下亮色反光看不清） | 跟随系统 |
| 交互 | 可交互、可下钻、可导出 | **禁交互、禁下钻**（无鼠标键盘） | 简化交互 |
| 刷新 | 用户主动刷新 | **每 60 秒后台预热** | 下拉刷新 |
| 缓存 TTL | ≤300s | **固定 60s** | ≤120s |
| 载荷 | 完整组件树 | 精简（无交互状态） | ≤256KB |

> 这七个差异全部落成了数据库 CHECK 约束（见数据结构 4.2 节 `ck_m22_dashboard_def_screen_*`），**配置错了直接拒绝落库**。例如给 `SCREEN` 类型配 `theme_mode='LIGHT'`，数据库会报错——因为大屏用亮色主题在门诊大厅的强光下根本看不清，这不是审美问题，是可用性问题。

**辨析二：财务主题分析 vs 法定财务报表**

| 维度 | 法定财务报表（M17-08） | 财务主题分析（M22-08 P03） |
|---|---|---|
| 受众 | 外部（卫健委、医保、审计） | 内部（院长、财务主管、科主任） |
| 口径 | 国家会计准则，**不可改** | 管理口径，可按需调整 |
| 变更 | 改一次需报备 | 每月调整都正常 |
| 数据 | 明细科目逐行 | 聚合指标 |
| 用途 | 合规与报送 | 找问题、找机会 |

**辨析三：预警 vs 报表里的「异常标注」**

报表里也可以给超标数字标红，但那只是「你查的时候能看到」。预警是「你没查的时候我也告诉你」。差别在于：
- 报表标注是**被动的**，预警是**主动的**；
- 报表标注**只在打开那一刻有效**，预警会推送、会跟踪、会要求确认关闭；
- 报表标注**不管重复**，预警必须**反抖动**——同一条规则同一个对象，24 小时内只报一次，连续 3 次才升级。

**辨析四：预警冷却期 vs 升级机制（两个容易混的机制）**

- **冷却（cooldown）** 管的是「**别重复刷屏**」：同一规则同一对象 24 小时内只产生一条新预警，后续命中只累加 `suppress_count`。
- **升级（escalate）** 管的是「**别淹没了真问题**」：如果一个指标连续 3 次触发（即连续 3 天都触发），说明问题不是偶发波动，必须升级为 `CRITICAL` 并抄送分管院长。

**两个机制缺一不可：** 只有冷却没有升级，则「连续 3 天收入下滑」会被当成 3 条普通警告埋掉；只有升级没有冷却，则一天触发 288 次把手机刷爆。

### 1.5 模块目标

| 编号 | 目标 | 验收方式 |
|---|---|---|
| G-01 | 院长打开驾驶舱 **3 秒内**看到全部核心指标（P95 ≤ 500ms 后端响应 + 前端渲染） | PF-01 |
| G-02 | 大屏 **7×24 常驻不黑屏**，数据滞后 ≤ 60 秒 | PF-02 |
| G-03 | 财务主题分析覆盖收入/成本/结余/现金流 **四大主题**，每个指标带同比与目标对比 | AC-08 |
| G-04 | 经营预警**准确率 ≥ 90%**（触发的问题中真问题占比），**误报率 ≤ 10%** | DA-05 |
| G-05 | 反抖动有效：同一问题 **24 小时内不重复推送**，连续 3 次自动升级 | AC-22 |
| G-06 | 所有展示数据可溯源，**任一数字能查到来源模块与采集批次** | DA-02 |
| G-07 | 上游数据缺失时**明确标注缺失**，绝不填 0 | DA-03 |
| G-08 | 决策助手**拒绝回答任何涉及患者个人身份的问题** | SC-04 |

## 2. 业务范围与边界

### 2.1 范围内

| 序 | 业务能力 | 页面 | 说明 |
|---|---|---|---|
| 1 | 管理驾驶舱 | P01 | 院级/科室级驾驶舱，KPI 卡片 + 趋势 + 排行 + 预警面板 |
| 2 | 院长大屏 | P02 | 常驻展示，深色主题，60s 刷新预热，禁交互 |
| 3 | 财务主题分析 | P03 | 收入/成本/结余/现金流四大主题的多期对比与结构分解 |
| 4 | 成本收益分析 | P04 | 科室成本构成、收益贡献、本量利分析 |
| 5 | 预算与目标达成 | P05 | 目标值 vs 实际值，达成率与排名，缺口预警 |
| 6 | 经营预警与异动 | P06 | 规则配置、触发扫描、冷却抑制、升级、确认关闭 |
| 7 | 报表订阅中心 | P07 | 看板订阅、推送、订阅管理（报表订阅在 M22-03） |
| 8 | 数据字典与口径说明 | P08 | 指标口径查询、主题编排、组件说明 |
| 9 | 决策分析助手 | P09 | 基于聚合指标的问答与归因，**拒绝患者隐私问题** |

### 2.2 范围外

| 序 | 不做的事 | 归属 | 原因 |
|---|---|---|---|
| 1 | 指标口径定义与版本管理 | M22-01 | 口径必须单向权威，不能多处定义 |
| 2 | 从业务模块采集原始数据 | M22-02 | 采集有统一的批次、校验、重试机制 |
| 3 | 法定财务报表（资产负债/收入费用/现金流量） | M17-08 | 法定报表有会计准则约束，M22 只取数展示 |
| 4 | 报表模板、报表实例、报表行数据、报表订阅 | M22-03 | 四张骨架表由 M22-03 权威定义 |
| 5 | 科室报表与科室排名口径 | M22-04 | 复用 M22-04 的排名算法 |
| 6 | 视光/屈光专题分析口径 | M22-05 / M22-06 | 引用，不重定义 |
| 7 | 临床质量指标口径 | M22-07 | 引用，不重定义 |
| 8 | 消息发送通道实现 | M03-05 | M22-08 只调 `POST /internal/v1/message/send` |
| 9 | 患者个人层面的信息查询 | M11 / M10 / M06 等业务模块 | **决策助手不回答任何患者身份相关问题** |
| 10 | 会计凭证、账务处理 | M17-01~M17-05 | 财务核算域 |

### 2.3 与上游模块的边界

| 模块 | 边界定义 | 本子模块的做法 |
|---|---|---|
| M22-01 | 指标口径唯一来源 | 只读 `metric_code` + `metric_version`，不改口径 |
| M22-02 | 指标事实唯一来源 | 只读 `m22_fact_metric`，**不直查业务表** |

### 3.2 状态机

#### 3.2.1 看板定义状态机

```
    ┌───────┐  发布   ┌────────┐  下线   ┌──────────┐
    │ DRAFT │────────▶│ ACTIVE │────────▶│ INACTIVE │

| 当前状态 | 动作 | 目标状态 | 前置条件 |
|---|---|---|---|
| `DRAFT` | 发布 | `ACTIVE` | 布局已配置、组件数 > 0、所有 metric_code 在 M22-01 存在 |
| `DRAFT` | 删除 | — | 无快照引用 |
| `ACTIVE` | 新版本发布 | 旧版本 `INACTIVE` | 新版本自身校验通过 |
| `ACTIVE` | 下线 | `INACTIVE` | 无订阅或订阅已全部暂停 |
| `INACTIVE` | 重新启用 | `ACTIVE` | 同 code 无其他 ACTIVE 版本 |

#### 3.2.2 预警状态机

```
                  ┌──────────┐
     触发 ───────▶│   OPEN   │◀────── 冷却期外的再次命中
                  └────┬─────┘
                       │
         ┌─────────────┼──────────────┐
         │ 认领         │ 直接关闭      │ 忽略
         ▼             ▼              ▼
  ┌──────────────┐ ┌────────┐  ┌──────────┐
  │ACKNOWLEDGED  │ │RESOLVED│  │ IGNORED  │
  └──────┬───────┘ └────────┘  └──────────┘
         │              ▲            ▲
         │ 处理完成      │            │
         └──────────────┘            │
                                     │
              超时 72h 未处理 ────────┘
              （resolve_type=AUTO_CLOSE）
```

| 当前状态 | 动作 | 目标状态 | 必填 | 说明 |
|---|---|---|---|---|
| `OPEN` | 认领 | `ACKNOWLEDGED` | `acknowledged_by`、`acknowledged_at` | 表示「我知道了，在处理」 |
| `OPEN` / `ACKNOWLEDGED` | 人工关闭 | `RESOLVED` | `resolve_note`（≥10 字） | `resolve_type='MANUAL'` |
| `OPEN` / `ACKNOWLEDGED` | 忽略 | `IGNORED` | `resolve_note` | 表示「确认是误报或不需处理」 |
| `OPEN` / `ACKNOWLEDGED` | 指标恢复自动关闭 | `RESOLVED` | — | `resolve_type='AUTO_RECOVER'`，扫描器检测指标回到恢复阈值 |
| `OPEN` / `ACKNOWLEDGED` | 超时自动关闭 | `RESOLVED` | — | `resolve_type='AUTO_CLOSE'`，超 `ALERT_AUTO_CLOSE_HOURS`（默认 72h） |

> **`RESOLVED` 与 `IGNORED` 都是终态，不可再改。** 这是审计要求——预警处理记录是「系统报过警、谁处理了」的证据链。忽略也必须写明原因，否则无法区分「真好处理了」还是「嫌烦点了忽略」。

#### 3.2.3 预警升级流程（反抖动核心）

```
扫描器每 10 分钟执行一次
    │
    ▼
┌─────────────────────────────────────────────┐
│ ① 取所有 ACTIVE 规则                          │
└──────────────────┬──────────────────────────┘
                   ▼

│    CONSECUTIVE 连续 N 期都命中                │
│    PERIOD      当期命中                       │

                   ▼ 命中
┌─────────────────────────────────────────────┐

│    同 rule_id + object_type + object_id      │
│    在 cooldown_hours（默认 24h）内是否有记录？ │
└──────────────────┬──────────────────────────┘

              │ alert_level =    │  │ alert_level =    │
              │   escalate_level │  │   base_level     │
              │   (CRITICAL)     │  │ is_escalated=T   │
              │ is_escalated=T   │  │                  │
              │ 推送抄送分管院长  │  │ 按级别推送        │
              └─────────────────┘  └──────────────────┘
```

**为什么冷却 24 小时、升级 3 次：**

| 参数 | 取值 | 理由 |
|---|---|---|
| 冷却期 | **24 小时** | 经营指标大多按日更新，一天一报符合业务节奏。若设 1 小时，则一天内同一问题报 24 次，手机被打爆；若设 7 天，则问题持续一周才提醒一次，太迟 |
| 升级次数 | **3 次** | 「连续 3 次」= 连续 3 天。单日波动很常见（周末门诊量天然低），但**连续 3 天**都越界就基本可以判定为真问题。设 2 次太敏感（两天的周末就触发了），设 5 次要等 5 天才升级，错过最佳干预窗口 |
| 升级窗口 | **72 小时** | 3 次 × 24 小时 = 72 小时。窗口太短会让「隔天触发」的情况不累计，太长则半年前的旧账也会被翻出来 |
| 单对象日上限 | **5 条** | 硬上限。即使冷却失效，单对象一天最多 5 条，超过合并为摘要推送 |

**举例说明（收入同比降 20% 规则，`escalate_times=3`）：**

| 日期 | 指标实际 | 相对上月 | 命中 | 冷却判定 | 结果 | 推送 |
|---|---|---|---|---|---|---|
| 11-01 | -22% | 是 | 无历史 | 窗口内 0 次 < 3 | 插入 `WARN` | 企业微信推科主任 |
| 11-02 | -25% | 是 | 24h 内有 | — | `suppress_count` +1 | **不推送** |
| 11-03 | -24% | 是 | 11-01 已超 24h | 窗口内 1 次 < 3 | 插入 `WARN` | 企业微信 |
| 11-04 | -26% | 是 | 24h 内有 | — | `suppress_count` +1 | **不推送** |
| 11-05 | -28% | 是 | 11-03 已超 24h | 窗口内 2 次 < 3 | 插入 `WARN` | 企业微信 |
| 11-06 | -30% | 是 | 24h 内有 | — | `suppress_count` +1 | **不推送** |
| 11-07 | -32% | 是 | 11-05 已超 24h | **窗口内 3 次 ≥ 3** | 插入 **`CRITICAL`** | 微信 + 短信 + 抄送分管院长 |

> **这个例子的关键：** 连续 7 天都在恶化，但只推送了 **4 次**（3 次 WARN + 1 次 CRITICAL），而不是 7 次。且第 7 天自动升级为 `CRITICAL`——问题持续一周没解决，必须让更高层知道。这就是「既不刷屏，又不淹没真问题」。

#### 3.3.2 财务主题四大类

|---|---|---|---|

#### 3.3.3 预警规则分组

| 分组 | 编码 | 规则数 | 说明 |
|---|---|---|---|
| 收入类 | `REVENUE` | 15 | 收入同比/环比下降、收入结构异动 |
| 成本类 | `COST` | 12 | 成本超支、成本率上升、药占比/耗占比超标 |
| 结余类 | `SURPLUS` | 10 | 结余率低于阈值、连续亏损 |
| 现金流类 | `CASHFLOW` | 8 | 净现金流为负、现金差错、应收账款超期 |
| 运营质量类 | `OPERATION` | 15 | 门诊量骤降、转化率下滑、满意度下降、并发症率超标 |

#### 3.3.4 比较符与窗口类型

**比较符（8 种）**

| 编码 | 中文 | 语义 | 示例 |
|---|---|---|---|
| `GT` | 大于 | `actual > threshold` | 药占比 > 0.35 |
| `GTE` | 大于等于 | `actual >= threshold` | 结余率 >= 0.15 |
| `LT` | 小于 | `actual < threshold` | 净现金流 < 0 |
| `LTE` | 小于等于 | `actual <= threshold` | 满意度 <= 4.0 |
| `EQ` | 等于 | `actual = threshold` | 现金差错笔数 = 0 |
| `NE` | 不等于 | `actual <> threshold` | — |
| `DROP_PCT` | 下降百分比 | `(actual - compare) / compare <= -threshold` | 收入同比降 20% |
| `RISE_PCT` | 上升百分比 | `(actual - compare) / compare >= threshold` | 成本环比升 15% |

**窗口类型（3 种）**

| 编码 | 中文 | 语义 | 示例 |
|---|---|---|---|
| `PERIOD` | 单期 | 当期命中即触发 | 本月收入同比降 20% |
| `CONSECUTIVE` | 连续 N 期 | 连续 N 期都命中才触发 | 结余率连续 2 月低于 15% |
| `ROLLING` | 滚动 N 期 | 最近 N 期累计命中（如求和） | 净现金流滚动 7 日为负 |

> **`CONSECUTIVE` 与升级机制的配合：** 窗口参数 `window_value=2` 表示「连续 2 期越界才触发第一条预警」，这让规则本身就有一次过滤，与冷却、升级形成三层防护。适合「偶发波动大但趋势有意义」的指标（如门诊量，周末天然低）。

### 3.4 关键计算模型

#### 3.4.1 看板快照生成模型

```

         │
         ▼

         │
         ▼

   ├── KPI_CARD      → 取当期值 + 对比期值 + 目标值
   ├── TREND_CHART   → 取近 N 期序列

   关键来源失败 → FAILED
         │
         ▼
⑤ 敏感脱敏
   对无 sensitive 权限的角色，敏感指标存脱敏值 + is_masked=true
         │
         ▼
⑥ 落快照（JSONB components_data）
         │
         ▼
⑦ 写 Redis 缓存（按 dashboard_type 决定 TTL）
```

**关键点：快照生成时就把「对比期」和「目标值」一起算好存起来。** 不这样做的话，每次打开驾驶舱都要额外查 2~3 次（对比期、目标期），P95 500ms 的预算撑不住。存进快照后，一次查询就拿到全部。

#### 3.4.2 目标达成率模型

```
achieve_rate = actual_value / target_value      （target_value ≠ 0）
achieve_rate = NULL                             （target_value = 0）
```

**达成状态判定（`target_status`）**

| 值方向 | 达成 | 进度正常 | 有风险 | 未达成 |
|---|---|---|---|---|
| `HIGHER_BETTER`（收入类） | `rate >= 1.0` | `0.9 <= rate < 1.0` | `0.8 <= rate < 0.9` | `rate < 0.8` |
| `LOWER_BETTER`（成本率类） | `rate <= 1.0` | `1.0 < rate <= 1.1` | `1.1 < rate <= 1.2` | `rate > 1.2` |
| `NEUTRAL`（中性） | 不判定 | — | — | — |

> **为什么必须区分值方向：** 成本率指标的「达成」是「不超过目标的 100%」，而收入指标的「达成」是「达到目标的 100%」。若统一按 ≥1 判达成，成本率超标（如目标 30%、实际 40%，rate=1.33）反而会被标成「达成优秀」——这是财务系统里最经典的逻辑坑。

**分母为 0 的处理：** `target_value = 0` 时达成率必须返回 `NULL`，前端显示 `—`。**绝不返回 0 或无穷大**。数据库层面由 `ck_m22_finance_target_zero` 约束强制保证。

#### 3.4.3 同比环比计算模型

```
mom_rate = (actual - prev_period_value) / abs(prev_period_value)     （prev ≠ 0）
yoy_rate = (actual - last_year_value)  / abs(last_year_value)        （last_year ≠ 0）
```

**三个必须遵守的规则：**

1. **分母取绝对值**：成本为负（冲红）时，若直接用负分母会让「成本上升」算出正数，方向反了。
2. **分母为 0 返回 `NULL`**：不返回 0，不返回 100%，返回 `NULL` 让前端显示 `—`。
3. **不做跨口径比较**：`metric_version` 不同的两期不能直接比。若历史期口径已升级，需在展示时标注「对比期口径为 v1，本期为 v2」，或经 M22-01 口径换算后比较。

> **第 3 条是最容易被忽略的：** 比如 2026-01 起「医疗收入」口径从「不含检查收入」改为「含检查收入」，这时拿 2026-01 和 2025-12 比同比，涨 40% 全是口径变化，不是业务增长。系统必须标注口径版本差异，否则会误导决策。

#### 3.4.4 结构占比与贡献度模型

```
structure_ratio = item_value / total_value            （total ≠ 0）
contribution    = (item_actual - item_prev) / (total_actual - total_prev)   （总变化 ≠ 0）
```

**贡献度示例（结余率下降归因）**

| 科室 | 上月结余 | 本月结余 | 变化额 | 贡献度 | 解释 |
|---|---|---|---|---|---|
| 屈光中心 | 1,280,000 | 1,050,000 | -230,000 | 57.50% | 结余下滑主要来自屈光中心 |
| 视光中心 | 620,000 | 590,000 | -30,000 | 7.50% | 小幅下滑 |
| 白内障科 | 480,000 | 380,000 | -100,000 | 25.00% | 明显下滑 |
| 其他 17 个科室合计 | 2,700,000 | 2,660,000 | -40,000 | 10.00% | 基本持平 |
| **合计** | **5,080,000** | **4,680,000** | **-400,000** | **100.00%** | — |

> **贡献度的价值：** 总变化 -40 万，如果只看合计，不知道从哪下手。贡献度一出，马上知道「屈光中心占 57.5%」，直接找屈光中心沟通即可。这是决策助手 P09 归因回答的数据基础。

#### 3.4.5 成本收益（本量利）模型

```
单位贡献毛益 = 单位收入 - 单位变动成本
贡献毛益率   = 单位贡献毛益 / 单位收入
保本工作量   = 固定成本 / 单位贡献毛益
```

**眼科典型应用（屈光手术）**

| 项目 | 数值 | 说明 |
|---|---|---|
| 单眼手术收入 | 12,000.00 | 平均客单价 |
| 单眼耗材成本 | 3,200.00 | 晶体/负压环等 |
| 单眼变动成本 | 4,500.00 | 耗材 + 变动人员成本 |
| 单眼贡献毛益 | 7,500.00 | 12,000 - 4,500 |
| 贡献毛益率 | 62.50% | 7,500 / 12,000 |
| 月度固定成本 | 1,200,000.00 | 设备折旧 + 固定人员 + 房租 |
| **保本月手术量** | **160 台** | 1,200,000 / 7,500 |

> **这条模型解释了「为什么手术量下降到某个点科室就亏损」**——低于 160 台/月，无论怎么省变动成本都亏，因为固定成本摊不薄。这是驾驶舱上「保本线」组件的计算依据。

#### 3.4.6 预警触发条件模型

```
比较符语义统一表达为：

GT        : actual >  threshold
GTE       : actual >= threshold
LT        : actual <  threshold
LTE       : actual <= threshold
EQ        : actual =  threshold
NE        : actual <> threshold
DROP_PCT  : (actual - compare_value) / abs(compare_value) <= -threshold
RISE_PCT  : (actual - compare_value) / abs(compare_value) >=  threshold

窗口判定：
PERIOD      : 当期命中 → 触发
CONSECUTIVE : 连续 window_value 期都命中 → 触发
ROLLING     : 最近 window_value 期累计值命中 → 触发
```

**分母为 0 的规则：`compare_value = 0` 时，`DROP_PCT` / `RISE_PCT` 判定为「不命中」**，因为「从 0 增长到某个数」的百分比增长率在数学上无定义（正负无穷皆可），报出来只有误导。这类规则应改用 `GT` 绝对额阈值。

#### 3.4.7 快照时效判定模型

```
stale_hours = (now - snapshot_at) / 3600

source_status 降级规则：
  若 stale_hours > M22.DASH.STALE_HOURS（默认 48）     → STALE
  若来源接口调用失败                                    → FAILED
  若部分来源失败                                        → PARTIAL
  否则                                                  → COMPLETE
```

> **为什么不直接把旧快照删掉：** 删了之后驾驶舱就空白了，院长看到一片「暂无数据」比看到「数据截至昨天 06:00」更糟。旧快照保留 + 明确标注时效，是更好的降级方式。

### 3.5 单据模型

**说明：本子模块无业务单据，只有配置与记录。** 下表列出各实体的关键标识：

| 实体 | 编号格式 | 示例 | 生成时机 |
|---|---|---|---|

#### 6.2.2 错误码清单（M22-08 段：2208001 ~ 2208040）

| 错误码 | HTTP | 错误信息 | 触发场景 | 处理建议 |
|---|---|---|---|---|
| `"2208001"` | 404 | 看板不存在 | `dashboard_code` 未找到 | 检查编码 |
| `"2208002"` | 400 | 看板类型非法 | `dashboard_type` 不在三态内 | 检查枚举 |
| `"2208003"` | 400 | 大屏参数配置非法 | SCREEN 类未满足七项差异参数 | 按提示调整 |
| `"2208004"` | 409 | 同编码已有生效版本 | 发布时存在其他 ACTIVE 版本 | 先下线旧版 |
| `"2208005"` | 400 | 看板布局为空 | 发布时无组件 | 先配置组件 |
| `"2208006"` | 400 | 组件指标不存在 | 布局引用的 `metric_code` 在 M22-01 未找到 | 检查指标编码 |
| `"2208007"` | 404 | 看板快照不存在 | 该期间无快照 | 触发快照生成 |
| `"2208008"` | 409 | 快照生成中 | 已有生成任务在跑 | 稍后重试 |
| `"2208009"` | 400 | 期间格式非法 | `period` 不符合 `YYYY-MM` | 检查格式 |
| `"2208010"` | 400 | 查询范围超限 | 超过 `QUERY_MAX_RANGE_MONTHS` | 缩小范围 |
| `"2208011"` | 404 | 财务主题不存在 | `topic_code` 未找到 | 检查编码 |

| `"2208013"` | 400 | 口径版本不一致 | 对比期与本期的 `metric_version` 不同 | 按提示标注 |
| `"2208014"` | 404 | 目标未设置 | 该指标该期间无目标值 | 先设置目标 |

| `"2208016"` | 400 | 目标口径与指标不一致 | 目标与实际的 `metric_version` 不同 | 统一口径 |
| `"2208017"` | 404 | 预警规则不存在 | `rule_code` 未找到 | 检查编码 |
| `"2208018"` | 400 | 规则参数非法 | 阈值/冷却/升级参数越界 | 按提示调整 |
| `"2208019"` | 409 | 规则编码重复 | `rule_code` 已存在 | 换编码 |
| `"2208020"` | 409 | 规则引用指标不存在 | `metric_code` 在 M22-01 未找到 | 检查编码 |
| `"2208021"` | 404 | 预警记录不存在 | `alert_no` 未找到 | 检查编号 |
| `"2208022"` | 409 | 预警状态不允许该操作 | 已终态仍尝试认领/关闭 | 刷新状态 |
| `"2208023"` | 400 | 关闭说明过短 | 人工关闭 `resolve_note` < 10 字 | 补充说明 |
| `"2208024"` | 400 | 忽略原因必填 | `IGNORED` 未填原因 | 补充原因 |
| `"2208025"` | 403 | 无权限处理该科室预警 | 数据权限不符 | 联系管理员 |
| `"2208026"` | 409 | 扫描任务运行中 | 已有扫描在跑 | 稍后重试 |
| `"2208027"` | 400 | 订阅周期与推送时间冲突 | 同看板同周期同时刻已订阅 | 修改时间 |
| `"2208028"` | 400 | 推送渠道为空 | 未选任何渠道 | 至少选一项 |
| `"2208029"` | 404 | 订阅不存在 | `subscription_no` 未找到 | 检查编号 |
| `"2208030"` | 403 | 无权限订阅该看板 | 无该看板 `view` 权限 | 申请权限 |
| `"2208031"` | 400 | 导出格式不支持 | `export_format` 非法 | 检查枚举 |
| `"2208032"` | 400 | 导出行数超限 | 超过 `EXPORT_MAX_ROWS` | 缩小范围 |
| `"2208033"` | 409 | 导出任务并发超限 | 超过 `EXPORT_MAX_CONCURRENT` | 等待后重试 |
| `"2208034"` | 404 | 导出文件已过期 | 超过 `EXPORT_EXPIRE_DAYS` | 重新导出 |
| `"2208035"` | 404 | 指标口径不存在 | `metric_code` 未找到 | 检查编码 |
| `"2208036"` | 403 | 无敏感数据权限 | 请求敏感指标但无 `sensitive` 权限 | 申请权限 |
| `"2208037"` | 400 | 问题涉及患者隐私 | 决策助手命中隐私红线 | 引导到业务模块 |
| `"2208038"` | 400 | 样本量过小 | 聚合样本 < `ASSISTANT_MIN_SAMPLE` | 扩大范围 |
| `"2208039"` | 503 | 上游数据源不可用 | 关键来源 U-01/U-02/U-12 失败 | 查看 missing_sources |
| `"2208040"` | 500 | 快照生成失败 | 生成过程异常 | 查看日志 |

**模块通用错误码**

| 错误码 | HTTP | 错误信息 | 触发场景 |
|---|---|---|---|
| `"229001"` | 500 | 系统内部错误 | 未预期异常 |

**路由层设计说明**

| 要点 | 做法 | 理由 |
|---|---|---|
| 权限校验 | 统一 `Depends(require_perm("m22:08:view"))` | 避免逐个函数手写 if 判断漏掉 |
| 并发保护 | 修改类接口接 `If-Match` 头，透传 `version_lock` | 乐观锁；`If-Match` 缺失时按「不校验」放行（仅限草稿态） |
| 缓存状态回传 | 响应头 `X-Cache: HIT` / `MISS` | 压测与生产定位「缓存到底生没生效」不用翻日志 |
| 数据完整性回传 | 响应头 `X-Source-Status` | 前端可据此在页面顶部挂「数据不完整」横条，比塞在 body 里更省解析 |
| 内部契约隔离 | `/internal/v1/m22` 独立 router + 服务令牌 | 外部 JWT 打不进内部路由，避免越权 |
| 契约类型收口 | P-09 只允许 `MOBILE` 类型看板 | 防止移动端误取大屏配置（大屏 JSON 有 3840 宽截图参数，移动端渲染必崩） |
| P-10 不走缓存 | 直查数据库 | 预警要求实时；附录 C.4 已测算索引直查 0.8ms，无需缓存 |

### 6.5 Service 层核心逻辑示例

Service 层是 M22-08 的真正主体。下面给出四个最关键的方法：**看板数据装配**、**快照生成**、**预警扫描（含反抖动）**、**目标达成率计算**。

"""M22-08 看板服务 —— 核心逻辑"""
from __future__ import annotations

import json
import time
from datetime import date, datetime, timedelta
from decimal import Decimal
from typing import Any, Optional

from sqlalchemy import select, text
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.errors import BizError
from app.core.logging import logger
from app.models.m22.dashboard import (
    M22DashboardDef,
    M22DashboardLayout,
    M22DashboardSnapshot,
)
from app.schemas.m22.dashboard import (
    ComponentValueOut,
    DashboardDataOut,
    DashboardLayoutCreate,
)
from app.services.m22 import metric_client


# ==================== 缓存 Key 与 TTL ====================

CACHE_KEY_FMT = "m22:dashboard:{dashboard_type}:{dashboard_code}:{period}:{dept}"
WARMUP_LOCK_FMT = "m22:lock:dashboard-warmup:{dashboard_code}"


def cache_ttl_of(dashboard_type: str) -> int:
    """按看板类型取缓存 TTL（秒）。与附录 C.1 完全一致。

    SCREEN  60s  —— 大屏挂在墙上，必须「看起来是活的」；60s 刷新 + 后台预热
    DASHBOARD 300s —— 管理层按需打开，5 分钟内数据不变无感
    MOBILE  120s —— 手机端频繁进出，2 分钟足够；且 P95 ≤ 500ms 要求更快的冷启动
    """
    return {"SCREEN": 60, "DASHBOARD": 300, "MOBILE": 120}[dashboard_type]


def build_cache_key(
    dashboard_type: str, dashboard_code: str, period: str, dept: Optional[int],
) -> str:
    return CACHE_KEY_FMT.format(
        dashboard_type=dashboard_type,
        dashboard_code=dashboard_code,
        period=period,
        dept=dept or 0,
    )


# ==================== 看板数据装配 ====================


async def get_dashboard_data(
    db: AsyncSession,
    redis,
    dashboard_code: str,
    period: Optional[str],
    scope_dept_id: Optional[int],
    refresh: bool,
    user,
) -> tuple[DashboardDataOut, bool]:
    """读取看板渲染数据。返回 (数据, 是否命中缓存)。"""
    definition = await _load_definition(db, dashboard_code)
    if definition is None:
        raise BizError("2208002", f"看板 {dashboard_code} 不存在")

    ttl = cache_ttl_of(definition.dashboard_type)
    period = period or _current_period()
    cache_key = build_cache_key(
        definition.dashboard_type, dashboard_code, period, scope_dept_id,
    )

    # 1) 非强制刷新时先读缓存
    if not refresh and ttl > 0:
        cached = await redis.get(cache_key)
        if cached:
            payload = json.loads(cached)
            # 缓存里存的是「脱敏后」的值，这里按当前用户权限决定是否换真值
            payload = await _apply_perm_mask(payload, user)
            return DashboardDataOut(**payload), True

    # 2) 取最新有效快照
    snapshot = await _load_latest_snapshot(db, definition, period, scope_dept_id)
    if snapshot is None:
        # 快照不存在：同步生成一次（首次访问/新看板），并标注来源
        snapshot = await regenerate_snapshot(
            db, redis, dashboard_code, period, user, force=False,
        )
        return snapshot, False

    # 3) 装配出参：快照 + 布局 + 时效信息
    layout = await _load_active_layout(db, definition)
    data = await _assemble(definition, layout, snapshot, user)

    # 4) 写缓存（只缓存脱敏后的通用版本）
    if ttl > 0:
        await redis.setex(
            cache_key, ttl, data.model_dump_json(exclude={"next_refresh_sec"}),
        )

    return data, False


async def _assemble(
    definition: M22DashboardDef,
    layout: Optional[M22DashboardLayout],
    snapshot: M22DashboardSnapshot,
    user,
) -> DashboardDataOut:
    """把快照 JSON 与布局 JSON 拼成前端可直接渲染的结构。"""
    layout_components = {
        c["component_id"]: c
        for c in (layout.components if layout else [])
    }

    rendered: list[ComponentValueOut] = []
    for item in snapshot.components_data:
        comp_id = item.get("component_id")
        layout_conf = layout_components.get(comp_id, {})
        rendered.append(
            ComponentValueOut(
                component_id=comp_id,
                component_type=item.get("component_type"),
                title=layout_conf.get("title"),
                grid_span=layout_conf.get("grid_span", 6),
                sort_no=layout_conf.get("sort_no", 0),
                value=item.get("value"),
                unit=item.get("unit"),
                series=item.get("series"),
                rows=item.get("rows"),
                compare_value=item.get("compare_value"),
                compare_rate=item.get("compare_rate"),
                target_value=item.get("target_value"),
                achieve_rate=item.get("achieve_rate"),
                source_status=item.get("source_status", "COMPLETE"),
                is_masked=item.get("is_masked", False),
            )
        )

    # 脱敏替换：无 sensitive 权限的用户，敏感组件换成脱敏值
    rendered = await _mask_components(rendered, user)

    # 大屏必须按尺寸给字号提示；移动端给单列布局
    if definition.dashboard_type == "SCREEN":
        rendered.sort(key=lambda x: (x.sort_no, x.component_id))

async def _mask_components(components: list[ComponentValueOut], user) -> list:
    """按权限脱敏。无 sensitive 权限时把敏感值替换为脱敏值（保留量级，不给精确数）。"""
    if "m22:08:sensitive" in await _perms_of(user):
        return components
    for c in components:
        if c.value is None:
            continue
        # 保留 1 位有效数字：12580000 -> 12000000
        magnitude = Decimal(10) ** (c.value.adjusted() if hasattr(c.value, "adjusted") else 0)
        c.value = (c.value / magnitude).quantize(Decimal("0.1")) * magnitude
        c.is_masked = True
        if c.achieve_rate is not None:
            c.achieve_rate = None
        if c.compare_rate is not None:
            c.compare_rate = None

async def scan_and_trigger(db: AsyncSession) -> dict:
    """定时扫描全部启用规则。每 5 分钟跑一次（附录 D 参数 M22.DASH.ALERT_SCAN_CRON）。"""
    rules = (
        await db.execute(
            select(M22FinanceAlertRule).where(
                M22FinanceAlertRule.status == "ACTIVE",
                M22FinanceAlertRule.is_deleted.is_(False),
            )
        )
    ).scalars().all()

    stat = {"scanned": len(rules), "triggered": 0, "suppressed": 0, "escalated": 0}

    for rule in rules:
        objects = await _resolve_objects(db, rule)
        for obj in objects:
            hit = await _evaluate(rule, obj)
            if not hit:
                continue
            result = await trigger_alert(db, rule, obj, hit["trigger_value"])
            if result == "SUPPRESSED":
                stat["suppressed"] += 1
            elif result == "ESCALATED":
                stat["escalated"] += 1
                stat["triggered"] += 1
            elif result == "CREATED":
                stat["triggered"] += 1

    logger.info("alert_scan_done", extra=stat)
    return stat


async def trigger_alert(
    db: AsyncSession,
    rule: M22FinanceAlertRule,
    obj: dict,
    trigger_value,
) -> str:
    """触发一条预警，返回 CREATED / SUPPRESSED / ESCALATED。

    反抖动三重机制（缺一不可）：
      1. 冷却期：同一规则同一对象 cooldown_hours（默认 24h）内只推一次，
         期间再命中只累加 suppress_count，不新增记录、不发通知。
      2. 升级计数：冷却期外再次命中时，统计 escalate_window_hours 内的历史次数，
         达到 escalate_times（默认 3）则本次直接以 CRITICAL 落库并推送。
      3. 抑制后升级：升级后的预警不再受冷却期约束，避免「升级了但被吞掉」。
    """
    now = datetime.now()
    object_id = obj.get("object_id")

    # —— 机制 1：冷却判定 ——
    # 注意：全院级预警（object_type='HOSPITAL'）的 object_id 为 NULL，
    # 直接写 object_id = NULL 永远不成立，必须用 COALESCE 转成 0 比较。
    cooldown_since = now - timedelta(hours=rule.cooldown_hours)
    exists = await db.execute(
        text(
            """
            SELECT id, suppress_count
              FROM m22_finance_alert
             WHERE rule_id = :rule_id
               AND object_type = :object_type
               AND COALESCE(object_id, 0) = COALESCE(:object_id, 0)
               AND triggered_at > :since
             ORDER BY triggered_at DESC
             LIMIT 1
            """
        ),
        {
            "rule_id": rule.id,
            "object_type": obj["object_type"],
            "object_id": object_id,
            "since": cooldown_since,
        },
    )
    row = exists.first()

    if row is not None:
        # 冷却期内：只累加抑制计数，不插记录、不发通知
        await db.execute(
            text(
                """
                UPDATE m22_finance_alert
                   SET suppress_count = suppress_count + 1,
                       last_suppressed_at = :now,
                       updated_at = :now
                 WHERE id = :id
                """
            ),
            {"id": row.id, "now": now},
        )
        await db.commit()
        return "SUPPRESSED"

    # —— 机制 2：升级计数 ——
    window_since = now - timedelta(hours=rule.escalate_window_hours)
    recent_count = await db.scalar(
        text(
            """
            SELECT COUNT(*)
              FROM m22_finance_alert
             WHERE rule_id = :rule_id
               AND object_type = :object_type
               AND COALESCE(object_id, 0) = COALESCE(:object_id, 0)
               AND triggered_at > :since
            """
        ),
        {
            "rule_id": rule.id,
            "object_type": obj["object_type"],
            "object_id": object_id,
            "since": window_since,
        },
    )

    is_escalated = recent_count + 1 >= rule.escalate_times
    level = rule.escalate_level if is_escalated else rule.alert_level

    alert = M22FinanceAlert(
        alert_no=await _next_alert_no(db),
        rule_id=rule.id,
        rule_code=rule.rule_code,
        alert_title=_render_title(rule, obj, trigger_value),
        object_type=obj["object_type"],
        object_id=object_id,
        object_name=obj.get("object_name"),
        period=obj.get("period"),
        trigger_value=trigger_value,
        threshold_value=rule.threshold_value,
        compare_op=rule.compare_op,
        base_level=rule.alert_level,
        alert_level=level,
        is_escalated=is_escalated,
        escalate_count=recent_count + 1,
        status="OPEN",
        triggered_at=now,
        suppress_count=0,
    )
    db.add(alert)
    await db.commit()
    await db.refresh(alert)

    await notify_client.send_alert(alert)
    logger.info(
        "alert_triggered",
        extra={
            "alert_no": alert.alert_no,
            "rule_code": rule.rule_code,
            "level": level,
            "is_escalated": is_escalated,
            "escalate_count": alert.escalate_count,
        },
    )
    return "ESCALATED" if is_escalated else "CREATED"

"""M22-08 预算与目标达成 —— 达成率计算"""
from __future__ import annotations

from decimal import Decimal, InvalidOperation
from typing import Optional

from app.models.m22.dashboard import M22FinanceTarget

HIGHER_BETTER = {"HIGHER_BETTER", "LOWER_BETTER", "NEUTRAL"}


def compute_achieve_rate(
    actual: Optional[Decimal],
    target: Optional[Decimal],
    value_direction: str,
) -> Optional[Decimal]:
    """计算达成率。

    规则（与 3.4.2 一致）：
      分母为 0 或目标缺失 → 返回 None，绝不返回 0 或 9999。
      正向指标（HIGHER_BETTER）：达成率 = 实际 / 目标
      逆向指标（LOWER_BETTER）：达成率 = 目标 / 实际（成本、费用、单病种费用等）
      中性指标（NEUTRAL）    ：达成率 = None（如「门诊量占比」，无「越达越好」含义）
    """
    if actual is None or target is None:
        return None
    if target == 0:
        return None
    if value_direction == "NEUTRAL":
        return None

    try:
        if value_direction == "HIGHER_BETTER":
            rate = actual / target
        else:  # LOWER_BETTER
            if actual == 0:
                return None
            rate = target / actual
        return rate.quantize(Decimal("0.000001"))
    except (InvalidOperation, ZeroDivisionError):
        return None


def judge_status(
    achieve_rate: Optional[Decimal],
    actual: Optional[Decimal],
    target: Optional[Decimal],
) -> str:
    """判定达成状态。

    注意：NOT_SET 与 MISSED 的区别是「有没有设过目标」，不是「达没达成」。
    目标未设置（target 为 None）→ NOT_SET，不能算成 MISSED。
    """
    if target is None:
        return "NOT_SET"
    if achieve_rate is None:
        return "AT_RISK"
    if achieve_rate >= Decimal("1.0"):
        return "ACHIEVED"
    if achieve_rate >= Decimal("0.9"):
        return "ON_TRACK"
    return "MISSED"
```

**Service 层设计说明**

| 要点 | 做法 | 理由 |
|---|---|---|
| 上游不可用 | 抛 `SourceUnavailable`，装配层捕获后 `value=None` + `source_status=FAILED` | 铁律：绝不静默填 0。填 0 会让「收入下降 100%」这种假警报吓到院长 |
| 缓存内容 | 只缓存**脱敏后**的通用版本，真值按请求时权限回填 | 若缓存真值，有 sensitive 权限的人先访问后，无权限的人可能读到同一份缓存 |
| 缓存失效 | 快照重建后 `DELETE` 该看板所有 period/scope 组合的 key | 用 `SCAN` 匹配前缀删除会阻塞 Redis 主线程 |
| 冷却期比较 | `COALESCE(object_id, 0) = COALESCE(:object_id, 0)` | 全院级预警 `object_id` 为 NULL，`= NULL` 永远不成立，冷却会彻底失效 |
| 升级方向 | 升级只能升不能降：`level = rule.escalate_level`，且 CHECK 约束保证 `alert_level <> base_level` | 避免实现时把「升级」写成「降级」还没人发现 |
| 达成率分母 0 | 返回 `None` | 返回 0 会显示「达成率 0%，严重滞后」误导决策；返回 9999 更荒谬 |
| 状态判定 | `target is None → NOT_SET`，不是 `MISSED` | 「没设目标」和「没达成」是两件事，混同会让科室被冤枉 |
| 通知时机 | 只在 `CREATED` / `ESCALATED` 时发 | 抑制期内不发，这是反抖动的目的 |

## 7. 缓存与异步任务设计

### 7.1 Redis 缓存设计

M22-08 是**读多写少、要求极快**的子模块。院长早上打开驾驶舱、大厅大屏每 60 秒自刷新、移动端随时拉取——三者都对响应时间敏感。缓存不是优化项，是达成 P-09（500ms）与 P-10（200ms）的前置条件。

**缓存 Key 设计**

| Key 模式 | 存储内容 | TTL | 说明 |
|---|---|---|---|
| `m22:dashboard:{type}:{code}:{period}:{dept}` | 看板渲染数据 JSON（脱敏版） | 按类型分级 | **主缓存**，P-09 命中即返回 |
| `m22:dashboard:layout:{code}:{version}` | 布局组件树 JSON | 3600s | 布局变更频率极低，长缓存 |
| `m22:dashboard:def:{code}` | 看板定义（含类型、TTL 配置） | 1800s | 避免每次访问查定义表 |
| `m22:dashboard:badge:{code}` | 角标计数（未读预警数） | 10s | 角标要「看起来很实时」 |
| `m22:dashboard:topic:{topic_code}` | 财务主题数据 | 600s | 与 DASHBOARD 同级略长 |
| `m22:dashboard:metric:{code}:{ver}` | 指标口径定义 | 86400s | 口径几乎不变，一天一刷 |
| `m22:lock:dashboard-warmup:{code}` | 大屏预热分布式锁 | 30s | 防多实例同时预热同一块屏 |

**TTL 分级（核心设计）**

| 看板类型 | Redis TTL | 刷新策略 | 预热 | 页面 P95 要求 | 为什么这么定 |
|---|---|---|---|---|---|
| `SCREEN`（院长大屏） | **60 秒** | 前端每 60s 自刷新 + 后台每 60s 主动预热 | **必须预热** | ≤ 500ms | 大屏挂在墙上，7×24 常亮。若每次刷新都击穿到库，20 块屏 × 每分钟 1 次会让 P-09 的 500ms 崩掉。60s TTL + 后台预热意味着**所有刷新都是缓存命中**，数据库压力与屏幕数量脱钩。60s 而非 30s：业务数据本身按日/按月更新，60 秒足够「看起来是活的」，再快没有业务意义，只是空耗 |
| `DASHBOARD`（管理驾驶舱） | **300 秒** | 用户手动刷新 / 页面打开时按需 | 不预热 | ≤ 500ms | 管理层按需打开，不是常亮。5 分钟内数据不变完全无感（月度指标本来就不逐秒变）。TTL 短了无谓增加库压，长了「打开看到两小时前的数」会被质疑 |
| `MOBILE`（移动端，P-09） | **120 秒** | 每次进入页面拉取 | 不预热 | **≤ 500ms** | 手机端一天进进出出几十次，120 秒里大概率命中。比 DASHBOARD 短是因为手机用户更可能「刚看完就想看新的」；比 SCREEN 长是因为手机流量与电量敏感、请求不能太频繁。**P-09 要求 500ms，命中缓存实测 12~18ms，余量充足** |
| 预警清单（P-10） | **不缓存（TTL = 0）** | 每次直查数据库 | 不预热 | **≤ 200ms** | 预警要求**实时**——「刚确认了一条预警，再拉列表必须是已确认状态」。若缓存 10 秒，用户点确认后刷新还显示未确认，会以为系统坏了。**为什么直查也能满足 200ms：** 预警表 3 万行，`idx_m22_finance_alert_pending` 部分索引只装未关闭的记录（约 200 行，96KB），直查实测 0.8ms，比 Redis 往返还快，缓存反而是负担（见附录 C.4 测算） |
| 角标计数 | 10 秒 | — | — | — | 角标只需「大致实时」，10 秒的滞后用户察觉不到，但能把高频轮询挡在缓存层 |

**四条 TTL 取值的统一理由**

1. **业务数据更新频率是上限**：财务数据按日/按月更新，缓存再短也拿不到更新的数据，只会增加库压。TTL 应「略长于业务数据的实际更新间隔」。
2. **用户对「旧数据」的容忍度决定下限**：大屏常亮，容忍度最低（60s）；驾驶舱按需看，容忍度高（300s）。
3. **访问频率决定预热是否值得**：只有 SCREEN 是 7×24 常亮、可预测的访问，预热才有意义；DASHBOARD 与 MOBILE 访问随机，预热会浪费算力。
4. **实时性是预警的命门**：预警是「让你立刻行动」的信号，任何缓存都可能让用户看到过期状态而误判，所以**宁可牺牲缓存收益也不缓存**。200ms 的性能要求靠索引而非缓存达成。

**缓存失效规则**

| 触发场景 | 失效范围 | 实现方式 |
|---|---|---|
| 快照重新生成 | 该看板全部 `period` × `dept` 组合 | 显式 `DELETE`，不用 `SCAN` 匹配（避免阻塞 Redis） |
| 看板定义修改（改 TTL/类型/范围） | 该看板全部缓存 | 同上 |
| 布局发布新版本 | `m22:dashboard:layout:{code}:*` | 删旧版本 key |
| 指标口径版本变更 | `m22:dashboard:metric:{code}:*` + 全部看板快照标记 `STALE` | 事件驱动 |
| 科室变更（合并/撤销） | 全部看板缓存 | 订阅 `m01.dept.changed` |
| 预警状态变更（确认/关闭） | 角标 key | 显式删 |

### 7.2 Celery 异步任务清单

```python
# app/tasks/m22/alert_tasks.py
"""M22-08 预警扫描 Celery 任务"""
from __future__ import annotations

from app.core.db import AsyncSessionLocal
from app.core.logging import logger
from app.core.metrics import alert_scan_duration, alert_trigger_total
from app.services.m22 import alert_service
from app.worker import celery_app


@celery_app.task(
    name="m22.alert.scan",
    queue="m22_alert",
    soft_time_limit=210,
    time_limit=240,
    autoretry_for=(),
    max_retries=0,           # 不重试：5 分钟后自然跑下一轮，重试会造成重复推送
    acks_late=True,
)
def scan_alerts() -> dict:
    """扫描全部启用规则并触发预警。

    不重试的理由：预警扫描每 5 分钟一轮，某轮失败下一轮会自然补上。
    若设置重试，失败后 30 秒重试，可能与下一轮撞车，同一条件被判定两次。
    """
    import asyncio

    async def _run() -> dict:
        async with AsyncSessionLocal() as db:
            return await alert_service.scan_and_trigger(db)

    with alert_scan_duration.time():
        result = asyncio.run(_run())

    alert_trigger_total.labels(result="created").inc(result["triggered"])
    alert_trigger_total.labels(result="suppressed").inc(result["suppressed"])
    logger.info("m22_alert_scan_finished", extra=result)
    return result
```

```python
# app/scheduler/m22_jobs.py
"""M22-08 定时任务注册"""
from __future__ import annotations

from datetime import date, datetime, timedelta

from apscheduler.schedulers.asyncio import AsyncIOScheduler
from apscheduler.triggers.cron import CronTrigger

from app.core.db import AsyncSessionLocal
from app.core.logging import logger
from app.core.redis import redis_client
from app.services.m22 import dashboard_service


def register_m22_jobs(scheduler: AsyncIOScheduler) -> None:
    scheduler.add_job(
        warmup_screens,
        CronTrigger(minute="*"),          # 每 60 秒
        id="m22_dashboard_warmup_screen",
        max_instances=1,
        coalesce=True,
        misfire_grace_time=30,
    )
    scheduler.add_job(
        precreate_partitions,
        CronTrigger(day=25, hour=3, minute=0),
        id="m22_dashboard_precreate_partition",
        max_instances=1,
    )


async def warmup_screens() -> None:
    """大屏预热：保证 SCREEN 类型的看板「永远有新鲜缓存」。

    SCREEN 的 TTL 是 60 秒，预热间隔也是 60 秒——
    理论上前一秒刚过期，这一秒就被填回，用户永远命中缓存。
    实现上用分布式锁保证同一块屏只由一个实例预热，避免 3 个实例重复算三遍。
    """
    async with AsyncSessionLocal() as db:
        screens = await dashboard_service.list_screens(db)
        for screen in screens:
            lock_key = f"m22:lock:dashboard-warmup:{screen.dashboard_code}"
            acquired = await redis_client.set(lock_key, "1", nx=True, ex=30)
            if not acquired:
                continue
            try:
                await dashboard_service.regenerate_snapshot(
                    db, redis_client, screen.dashboard_code,
                    period=None, user=_SYSTEM_USER, force=True,
                )
            except Exception:  # noqa: BLE001
                logger.exception(
                    "screen_warmup_failed",
                    extra={"dashboard_code": screen.dashboard_code},
                )
            finally:
                await redis_client.delete(lock_key)


async def precreate_partitions() -> None:
    """预建下下月的分区表。

    预留两个月余量：即使某次预建任务失败，也还有一个月的时间被发现。
    配合 DEFAULT 分区，即使彻底失败也不会导致写入报错。
    """
    today = date.today()
    for offset in (1, 2):
        month = (today.replace(day=1) + timedelta(days=32 * offset)).replace(day=1)
        nxt = (month + timedelta(days=32)).replace(day=1)
        sql = (
            f"CREATE TABLE IF NOT EXISTS m22_dashboard_snapshot_p{month:%Y%m} "
            f"PARTITION OF m22_dashboard_snapshot "
            f"FOR VALUES FROM ('{month:%Y-%m-%d}') TO ('{nxt:%Y-%m-%d}')"
        )
        async with AsyncSessionLocal() as db:
            await db.execute(sql)
            await db.commit()
        logger.info("partition_precreated", extra={"month": f"{month:%Y-%m}"})
```

**看板定义（`m22_dashboard_def.status`）**

### 8.5 计算规则

**规则 C-01：指标值一律从 M22-02 指标事实读取**
M22-08 不直查任何业务表，也不自行计算业务指标。所有 `actual_value` 必须来自 `m22_fact_metric`。违反这条会让「同一个收入数字，看板和财务报表对不上」。

**规则 C-02：期间比率必须汇总后重算**
月汇总的比率不是日比率之和或平均，必须 `SUM(分子) / SUM(分母)`。例：10 月成本率 = 10 月总成本 / 10 月总收入，不是 31 天日成本率的平均值。

**规则 C-03：分母为 0 或缺失，比率返回 `NULL`**
绝不用 0 或 9999 占位。前端显示 `—` 并在悬浮提示「分母为 0，无法计算」。

**规则 C-04：上游不可用不填 0**
`source_status` 降级为 `PARTIAL`/`FAILED`，`missing_sources` 记录来源。看板顶部显示「数据不完整」横条。

**规则 C-05：达成率按值方向计算**
`HIGHER_BETTER` 用 `实际/目标`，`LOWER_BETTER` 用 `目标/实际`，`NEUTRAL` 返回 `NULL`。

**规则 C-06：同比环比口径一致**
同比对比去年同月，环比对比上月；对比期间的实际天数不一致时（如 2 月 vs 3 月），按日均值比较并注明。

**规则 C-07：结构占比的基数剔除未知**
按科室统计收入占比时，`dept_id IS NULL` 的收入归入「未分配」单列，不参与占比分母，避免占比之和不为 100%。

**规则 C-08：预警触发值取规则窗口末值**
窗口为「近 7 天」时，触发值取窗口内最后一天的值，不是平均值。理由：预警要反映「现在怎么样」，平均值会把最新恶化稀释掉。

**规则 C-09：升级计数只数窗口内已推送的**
被冷却抑制的次数不计入升级计数。否则一次持续 7 天的恶化会把升级计数刷到 7，第一次升级后又马上升级。

### 8.6 引用删除规则

| 对象 | 被引用情况 | 删除行为 |
|---|---|---|
| 看板定义 | 有活跃订阅 | 拒绝删除，提示先停用订阅 |
| 看板定义 | 有历史快照 | 允许逻辑删除，快照保留（历史可查） |
| 看板布局 | 是唯一版本 | 拒绝删除 |
| 看板布局 | 是 ACTIVE 版本 | 拒绝删除，须先启用其他版本 |
| 财务主题 | 已被报表模板引用 | 拒绝删除，提示先解绑模板 |
| 预警规则 | 有未关闭预警 | 拒绝删除，提示先处置未关闭预警 |
| 预警规则 | 仅有历史预警 | 允许逻辑删除，历史预警保留 |
| 指标口径（M22-01） | 被本子模块看板/主题/规则引用 | 由 M22-01 返回引用清单，本子模块须先解绑 |
| 导出文件 | 已过期 | 物理删除文件，记录保留 |
| 预警记录 | 任意状态 | **禁止删除**（`REVOKE DELETE`），只能流转状态 |

### 8.7 并发控制

| 场景 | 方案 | 说明 |
|---|---|---|
| 看板定义修改 | 乐观锁 `version_lock`，`If-Match` 头透传 | 冲突返回 `"2208009"`，前端提示刷新后重试 |
| 布局版本创建 | 数据库唯一键 `(dashboard_def_id, version)` | 版本号用 `MAX(version) + 1`，冲突重试 1 次 |
| 布局启用 | 事务内先将旧 ACTIVE 置 INACTIVE，再置新版本 ACTIVE | 部分唯一索引兜底，并发时一方失败回滚 |
| 快照生成 | 分布式锁 `m22:lock:dashboard-warmup:{code}` | 防同一看板并发重复生成 |
| 预警触发 | 冷却期 SQL 查询 + 唯一约束 | 并发下可能双插，靠 `uk_m22_finance_alert_chain` 冲突兜底 |
| 预警确认 | `UPDATE ... WHERE status = 'OPEN'`，检查影响行数 | 影响 0 行说明已被他人确认，返回 `"2208021"` |
| 导出创建 | Redis 令牌桶限制单用户并发 2 个 | 超限返回 `"2208026"` |
| 订阅推送 | `last_push_at` 判重 + 行级锁 | 同分钟不重复推送 |

### 9.3 数据权限

| 角色 | 可见范围 | 实现方式 |
|---|---|---|
| 院领导 | 全院全部科室 | 不加 `dept_id` 过滤 |
| 财务主管 | 全院全部科室（含敏感） | 不加过滤，且有 `sensitive` 权限 |
| 科主任 | 本科室及其下级科室 | `dept_id IN (本人科室子树)`，取自 M01-01 科室树 |
| 运营人员 | 全院（敏感指标脱敏） | 不加过滤，但无 `sensitive` 权限 → 走脱敏值 |
| 数据管理员 | 全院（只读配置） | 不加过滤，配置类可写 |
| 普通职工 | 仅本人在移动端可见的看板 | P-09 按 `user_id` 反查其科室，只返回该科室看板 |

**数据权限实现要点**

1. 数据权限在 **Service 层**统一收口，不在路由层各写一遍——路由层漏一个就是越权。
2. 科室子树由 M01-01 `GET /internal/v1/mdm/depts/tree` 获取，缓存 1800 秒；科室变更事件到达时清缓存。
3. **脱敏在服务端完成**：无 `sensitive` 权限的用户，缓存里存的就是脱敏值（见 6.5 `_mask_components`），不是靠前端遮罩。前端遮罩能按 F12 看到原值，等于没遮。
4. P-09 内部契约必须校验 `X-User-Id` 对看板的可见权限，不能因为「内部调用」就放行全部。

### 9.4 安全措施

| 措施 | 内容 |
|---|---|
| 越权防护 | 每个接口 `require_perm` + Service 层数据范围过滤，双层校验 |
| 敏感指标脱敏 | 服务端替换为保留 1 位有效数字的脱敏值，`is_masked = true` |
| 导出水印 | 敏感数据导出必带水印（工号 + 姓名 + 时间），`ck_m22_finance_export_watermark` 强制 |
| 导出行数限制 | 单次 ≤ 100,000 行；超限拒绝并提示缩小范围 |
| 大屏只读 | `SCREEN` 类型禁交互、禁下钻，从配置层杜绝误操作 |
| 决策助手边界 | 不回答涉患者个人身份问题（详见 5.10） |
| 内部契约鉴权 | `/internal/v1/m22/*` 需服务令牌，外部 JWT 无法访问 |
| 审计留痕 | 看板配置变更、预警确认/关闭、导出操作全部 `POST /internal/v1/audit/record` |
| SQL 注入防护 | 全部走 SQLAlchemy 参数绑定，动态排序字段走白名单 |
| 文件下载鉴权 | 导出文件 URL 带签名，有效期 7 天，过期不可下载 |

## 11. 异常处理与日志

### 11.1 异常分类

| 类别 | 异常 | 处理策略 | 错误码 |
|---|---|---|---|
| **参数异常** | 参数格式错、必填缺失 | 直接返回 400，不做重试 | `"2208001"` |
| **业务异常** | 看板不存在、状态不允许 | 返回 4xx + 明确提示 | `"2208002"`~`"2208024"` |
| **依赖异常** | 上游接口超时/5xx | 降级（`PARTIAL`），不阻塞整体 | 组件级 `source_status` |
| **数据异常** | 快照 JSON 解析失败 | 记录并标 `FAILED`，不返回残缺数据 | `"2208035"` |
| **系统异常** | 数据库连接失败、Redis 失败 | Redis 失败直接穿透查库；数据库失败返回 500 | `"229001"` |

### 11.2 降级策略

| 降级场景 | 表现 | 用户感知 | 恢复 |
|---|---|---|---|
| Redis 不可用 | 直接查数据库快照，不写缓存 | 响应从 18ms 变 40ms，无感 | Redis 恢复后自动写缓存 |
| M22-02 指标事实不可用 | 相关组件 `value=null`，`source_status=PARTIAL` | 组件显示「数据暂不可用」+ 顶部黄条 | 下一轮快照重建 |
| M17 财务接口不可用 | 财务页签组件为空，提示去 M17 查看 | 明示「财务数据暂不可用」 | 下次刷新 |
| M16 日结接口不可用 | 大屏实时数显示最近一次成功值 + 「截至 xx:xx」 | 明示数据时间 | 下个预热周期 |
| M03-05 推送不可用 | 预警照常落库，`notify_status=PENDING`，异步重试 | 站内仍能看到预警 | 重试 3 次后告警运维 |
| 指标口径变更导致快照过期 | 快照标 `STALE`，页面提示「口径已更新，数据刷新中」 | 明示 | 重算完成 |
| 分区未预建 | 数据落入 `DEFAULT` 分区，功能正常 | 无感 | 分区任务补建后 `DETACH` 归位 |
| 导出文件生成失败 | 任务标 `FAILED`，提示重试 | 明示 | 用户手动重试 |

> **降级的唯一底线：宁可显示「无数据」，绝不显示错的数。** 尤其是绝不把缺失的财务数据填 0——「收入 0 元」比「收入暂不可用」危险得多。

## 附录 B：计算口径与阈值

**B.1 目标达成率**

| 值方向 | 公式 | 示例（目标 100 万，实际 95 万） |

|---|---|

**B.3 预警默认阈值**

| REV（收入） | 科室月收入同比下降加剧 | LT | -30% | 近 1 月 | CRITICAL |
| REV（收入） | 药占比超标 | GT | 30% | 近 1 月 | WARN |
| COST（成本） | 科室成本收入比上升 | GT | 5%（同比） | 近 1 月 | WARN |

## 附录 F：术语表

| 术语 | 说明 |
|---|---|
| 管理驾驶舱 | 面向管理层的多组件数据看板，支持下钻，非实时 |

| 财务主题 | 按业务视角（收入/成本/结余/现金流）组织的指标分组 |
| 目标达成率 | 实际值相对目标值的完成比例，按值方向计算 |
| 值方向（`value_direction`） | 指标「越大越好」还是「越小越好」，决定达成率算法 |
| 预警规则 | 指标 + 比较符 + 阈值 + 窗口 + 级别的组合定义 |

| 升级（`escalate`） | 连续多次触发后提升预警级别，表示问题未解决 |
| 升级计数（`escalate_count`） | 统计窗口内已推送的触发次数，被抑制的不计 |
| 抑制（`suppress`） | 冷却期内重复命中只累加计数、不推送的行为 |
| 抑制比 | 被抑制次数 / 总命中次数，衡量规则灵敏度是否合适 |
| 数据完整性（`source_status`） | COMPLETE/PARTIAL/FAILED/STALE，标明数据是否齐全 |
| 溯源字段 | `source_module`/`source_api`/`collect_batch_no`/`source_status` 四件套 |
| 脱敏 | 敏感指标对无权限用户替换为保留量级的值，服务端完成 |
| 部分索引 | 带 `WHERE` 条件的索引，只索引需要的行，体积极小 |
| 决策分析助手 | 基于聚合指标回答经营问题的问答功能，**不涉及患者个人身份** |
