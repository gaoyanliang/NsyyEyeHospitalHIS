## 2. 全局命名与建表规范

### 2.1 字段类型标准

| 语义 | PostgreSQL 类型 | SQLAlchemy | Pydantic |
|---|---|---|---|
| 主键 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `BigInteger, primary_key=True` | `int` |
| 单号/编码 | `VARCHAR(32)` / `VARCHAR(64)` | `String(32)` | `str` |
| **指标编码** | `VARCHAR(64)` | `String(64)` | `str` |
| **指标值** | `NUMERIC(20,6)` | `Numeric(20, 6)` | `Decimal` |
| 金额 | `NUMERIC(18,2)` | `Numeric(18, 2)` | `Decimal` |
| 比率/权重 | `NUMERIC(9,6)` | `Numeric(9, 6)` | `Decimal` |
| 数量 | `NUMERIC(14,2)` | `Numeric(14, 2)` | `Decimal` |
| 统计期间 | `VARCHAR(10)`（日 `YYYY-MM-DD` / 月 `YYYY-MM`） | `String(10)` | `str` |
| 枚举 | `VARCHAR(32)` + CHECK | `String(32)` | `str` |
| 时间戳 | `TIMESTAMP` | `TIMESTAMP` | `datetime` |
| 日期 | `DATE` | `Date` | `date` |
| 布尔 | `BOOLEAN` | `Boolean` | `bool` |
| 扩展属性 | `JSONB` | `JSONB` | `dict` |

> ⚠️ **严禁使用 `FLOAT` / `DOUBLE PRECISION` / `REAL`。** 指标值、金额、比率全部用 `NUMERIC`。校验脚本 `validate_m22.py` 的 `check_metric_invariants` 会逐表扫描并报告任何浮点类型。原因：浮点数的二进制表示无法精确表达 `0.1`，累加 10 万次后误差可达 `1e-10` 量级，在「收入合计」这种场景下会变成看得见的分位偏差。

### 2.2 必备字段

**业务主表（有生命周期）：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 主键 |
| `created_at` | TIMESTAMP | 创建时间 |
| `created_by` | BIGINT | 创建人 |
| `updated_at` | TIMESTAMP | 更新时间 |
| `updated_by` | BIGINT | 更新人 |
| `is_deleted` | BOOLEAN | 逻辑删除 |
| `version` | SMALLINT | 乐观锁版本 |

**流水表（只增不改）：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 主键 |
| `created_at` | TIMESTAMP | 创建时间 |
| `created_by` | BIGINT | 创建人 |

> 流水表**不含** `updated_at` / `updated_by` / `is_deleted` / `version`，并在表用途里注明「只增不改」，同时 `REVOKE UPDATE, DELETE`。
> M22 中属于流水表的典型有：`m22_collect_log`、`m22_report_row`、`m22_fact_metric`、`m22_dashboard_alert`（触发记录）。

### 2.3 溯源字段（M22 特有，强制）

**所有指标事实类表（`m22_fact_*`、`m22_optical_*_fact`、`m22_refractive_*_fact` 等）必须包含以下六个溯源字段：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `metric_code` | `VARCHAR(64)` | ✅ | 指标编码，关联 `m22_metric_def.metric_code` |
| `period` | `VARCHAR(10)` | ✅ | 统计期间 |
| `source_module` | `VARCHAR(16)` | ✅ | 来源模块，如 `M16` |
| `source_api` | `VARCHAR(200)` | ✅ | 来源接口路径，如 `/internal/v1/m16/daily/summary` |
| `collect_batch_no` | `VARCHAR(32)` | ✅ | 采集批次号，如 `CB20261031-0001` |
| `source_status` | `VARCHAR(16)` | ✅ | `COMPLETE` / `PARTIAL` / `FAILED` / `STALE` |

**为什么这六个字段「缺一不可」：**

| 字段 | 缺失后果 |
|---|---|
| `metric_code` | 报表无法说出「这个数字是什么」，无法做口径追溯 |
| `period` | 无法按期间查询与分区，也无法判断是否重复采集 |
| `source_module` | 出问题时不知道该找哪个模块的负责人 |
| `source_api` | 上游接口变更时无法定位受影响的数据范围 |
| `collect_batch_no` | 无法重放/撤销某次采集 |
| `source_status` | **最危险** —— 缺失会让「上游失败」被显示成正常数字 |

### 2.4 指标事实表的唯一约束（强制）

```sql
-- 每个指标在每个期间、每个科室、每个业务维度上只有一条事实记录
ALTER TABLE m22_fact_metric
    ADD CONSTRAINT uk_m22_fact_metric_dim
    UNIQUE (metric_code, period, dept_id, biz_dim);
```

> **`biz_dim` 的取值约定：** 无业务维度时存空字符串 `''`，**不要存 `NULL`**。
> 原因：PostgreSQL 的 `UNIQUE` 约束把 `NULL` 视为互不相等，若 `biz_dim` 允许 `NULL`，同一 `(metric_code, period, dept_id)` 可以被插入任意多条 `NULL` 行，唯一约束形同虚设。

### 2.5 命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 表 | `m22_{子模块语义}_{实体}` 单数 | `m22_metric_def` |
| 主键索引 | `pk_{表名}` | `pk_m22_metric_def` |
| 唯一索引 | `uk_{表名}_{语义}` | `uk_m22_metric_def_code_ver` |
| 普通索引 | `idx_{表名}_{字段}` | `idx_m22_fact_metric_period` |
| 检查约束 | `ck_{表名}_{语义}` | `ck_m22_fact_metric_status_value` |
| 分区表 | `{表名}_p{yyyymm}` / `{表名}_pdefault` | `m22_fact_metric_p202610` |

### 2.6 指标编码规范

**格式：** `{模块域}_{主题}_{指标名}`，全大写，下划线分隔

| 段 | 长度 | 取值 |
|---|---|---|
| 模块域 | 2~4 位 | `OP` / `CL` / `OPT` / `REF` / `FIN` / `PERF` |
| 主题 | 2~6 位 | 如 `VISIT` / `SALES` / `SURGERY` / `CONVERSION` |
| 指标名 | 2~20 位 | 如 `COUNT` / `AMOUNT` / `RATE` |

**数据库强制：**

```sql
ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_code_format
    CHECK (metric_code ~ '^(OP|CL|OPT|REF|FIN|PERF)_[A-Z0-9]{2,6}_[A-Z0-9]{2,20}$');
```

> **正则在 SQL 字符串里的写法：** 由于本文档是 Markdown，`~` 后面的单引号字符串里若出现竖线 `|` 会被表格解析器误认为列分隔符，因此**在表格中描述时写作文字**，在实际 DDL 代码块中正常书写。

## 3. 指标口径的数据库强制

> **这是 M22 与普通业务模块最大的技术差异：指标口径的唯一性、分母不为 0、降级可见性，都不是「业务规则」，是「数据库约束」。**

### 3.1 同一指标同一时刻只有一个生效版本

```sql
-- 部分唯一索引：只约束 ACTIVE 且未删除的行
CREATE UNIQUE INDEX uk_m22_metric_def_active
    ON m22_metric_def (metric_code)
    WHERE status = 'ACTIVE' AND is_deleted = FALSE;
```

**为什么不用触发器：**

| 手段 | 并发安全 | 说明 |
|---|---|---|
| 应用层「先查后改」 | ❌ | 两个管理员同时审批会双 ACTIVATE |
| 触发器 | ✅ 但复杂 | 需要处理递归、性能开销 |
| **部分唯一索引** | ✅ | 由 PostgreSQL 唯一索引在写入瞬间保证，零竞态 |

**版本切换的事务边界：**

```python
def activate_metric_version(metric_code: str, new_version: int) -> None:
    with session.begin():
        # 1. 行锁住该 metric_code 的全部版本，防止并发审批
        versions = session.execute(
            select(MetricDef)
            .where(MetricDef.metric_code == metric_code)
            .with_for_update()
        ).scalars().all()
        # 2. 先降级旧 ACTIVE，再升级新版本（同事务，唯一索引不会瞬时冲突）
        for v in versions:
            if v.status == "ACTIVE":
                v.status = "DEPRECATED"
                v.effective_to = date.today()
        session.flush()
        # 3. 启用新版本
        target = next(v for v in versions if v.version == new_version)
        target.status = "ACTIVE"
        target.effective_from = date.today()
```

> **顺序不能反：** 若先 `ACTIVE` 新的再降级旧的，第二条 UPDATE 会撞上唯一索引。必须先降后升。

### 3.2 分母为 0 时必须存 NULL 不能存 0

```sql
ALTER TABLE m22_fact_metric
    ADD CONSTRAINT ck_m22_fact_metric_ratio_null
    CHECK (calc_type <> 'RATE' OR denominator IS NULL OR denominator > 0
        OR metric_value IS NULL);
```

**这条约束拦的是什么：**

| 场景 | 错误做法 | 后果 |
|---|---|---|
| 新科室 0 例手术的安全率 | 存 `0.000000` | 报表显示「安全率 0%」，被误读成「发生了大量不良事件」 |
| 正确做法 | 存 `NULL` | 报表显示「—」，并标注「无手术，不适用」 |

### 3.3 降级状态与值的自洽性

```sql
ALTER TABLE m22_fact_metric
    ADD CONSTRAINT ck_m22_fact_metric_status_value
    CHECK (source_status = 'COMPLETE'
        OR metric_value IS NULL
        OR value_is_estimated = TRUE);
```

**含义：** 如果指标源状态不是 `COMPLETE`（即有降级），那么该行的值要么是 `NULL`（彻底没有数据），要么必须打上 `value_is_estimated = TRUE` 标记（用了估算值或旧值）。**不允许一个「不完整」的数据被当成完整值用。**

### 3.4 报表完整性从事实层推导

```sql
ALTER TABLE m22_report_instance
    ADD CONSTRAINT ck_m22_report_instance_status
    CHECK (source_status IN ('COMPLETE', 'PARTIAL', 'FAILED', 'STALE'));
```

报表的 `source_status` 由 Service 层按「取最差」规则计算后写入，并同时写入 `missing_sources` JSONB（形如 `[{"metric_code": "CL_OR_UTILIZATION", "reason": "上游超时"}]`），**不允许出现 `source_status = 'COMPLETE'` 但 `missing_sources` 非空**：

```sql
ALTER TABLE m22_report_instance
    ADD CONSTRAINT ck_m22_report_instance_consistency
    CHECK (source_status <> 'COMPLETE' OR missing_sources IS NULL
        OR missing_sources = '[]'::jsonb);
```

### 3.5 已生成报表行不可变

```sql
REVOKE UPDATE, DELETE ON m22_report_row FROM app_user;

-- 更正只能通过「重新生成新实例 + 旧实例置 SUPERSEDED」实现
```

### 3.6 三道防线对照

| 防线 | 位置 | 拦截什么 |
|---|---|---|
| 第 1 道 | Pydantic Schema | 格式、必填、长度、枚举取值 |
| 第 2 道 | Service 事务 | 状态机合法性、口径版本存在性、上游可用性、权限 |
| 第 3 道 | **数据库 CHECK / 唯一索引 / REVOKE** | **口径双生效、分母为 0 存 0、降级状态与值矛盾、篡改已生成报表** |

## 4. 分区策略

### 4.1 分区表清单

| 表 | 分区键 | 粒度 | 保留策略 |
|---|---|---|---|
| `m22_fact_metric` | `period` | 月 | 永久 |
| `m22_fact_dept_metric` | `period` | 月 | 永久 |
| `m22_report_row` | `period` | 月 | 10 年 |
| `m22_collect_log` | `created_at` | 月 | 3 年 |
| `m22_dashboard_alert` | `created_at` | 月 | 3 年 |

### 4.2 分区 DDL 模式（必须有 DEFAULT 分区）

```sql
CREATE TABLE m22_fact_metric (
    id                 BIGINT GENERATED BY DEFAULT AS IDENTITY,
    metric_code        VARCHAR(64)   NOT NULL,
    metric_version     SMALLINT      NOT NULL,
    period             VARCHAR(10)   NOT NULL,
    dept_id            BIGINT,
    biz_dim            VARCHAR(64)   NOT NULL DEFAULT '',
    metric_value       NUMERIC(20,6),
    denominator        NUMERIC(20,6),
    value_is_estimated BOOLEAN       NOT NULL DEFAULT FALSE,
    source_module      VARCHAR(16)   NOT NULL,
    source_api         VARCHAR(200)  NOT NULL,
    collect_batch_no   VARCHAR(32)   NOT NULL,
    source_status      VARCHAR(16)   NOT NULL,
    collected_at       TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, period)
) PARTITION BY RANGE (period);

-- 按月分区
CREATE TABLE m22_fact_metric_p202610 PARTITION OF m22_fact_metric
    FOR VALUES FROM ('2026-10') TO ('2026-11');

-- ★ 必须有 DEFAULT 分区，否则写入未知期间会报错
CREATE TABLE m22_fact_metric_pdefault PARTITION OF m22_fact_metric DEFAULT;
```

> **坑一：** 忘记 `DEFAULT` 分区 → 新月份第一批采集写入直接失败，且错误信息不明显（`no partition of relation found for row`）。自动化建分区任务必须在每月 25 日预建下月分区。
>
> **坑二：** 分区键必须是业务期间 `period` 而不是采集时间 `collected_at`。补采场景下三月份的数据可能在五月采集，若按采集时间分区，查三月数据要扫 12 个分区。
>
> **坑三：** 分区表的主键必须包含分区键（`PRIMARY KEY (id, period)`），否则 PostgreSQL 拒绝创建。

### 4.3 分区维护任务

```python
# APScheduler：每月 25 日 01:00 预建下月分区
def create_next_month_partitions() -> None:
    next_month = (date.today().replace(day=1) + timedelta(days=32)).replace(day=1)
    table_list = ["m22_fact_metric", "m22_fact_dept_metric",
                  "m22_report_row", "m22_collect_log", "m22_dashboard_alert"]
    for table in table_list:
        suffix = next_month.strftime("%Y%m")
        start = next_month.strftime("%Y-%m")
        end = (next_month + timedelta(days=32)).strftime("%Y-%m")
        execute_ddl(f"""
            CREATE TABLE IF NOT EXISTS {table}_p{suffix}
            PARTITION OF {table}
            FOR VALUES FROM ('{start}') TO ('{end}')
        """)
```

| `m22_dashboard_alert` | 约 5 条 | 约 1,825 条 | 约 9,125 条 |

### 5.2 存储估算

| 项 | 估算 |
|---|---|
| 5 年指标事实（含索引） | 约 4.2 GB |
| 5 年报表行数据 | 约 1.1 GB |
| 5 年采集日志 | 约 0.5 GB |
| 5 年主题事实与看板数据 | 约 0.4 GB |
| 元数据与配置 | 约 0.05 GB |
| **合计** | **约 6.3 GB** |

> 体量不大，分区主要是为了**按期间快速归档与只读挂载**，以及「查某月指标」时的分区裁剪，而非性能压力。

### 5.3 指标事实表的增长风险

**`m22_fact_metric` 是 M22 唯一有显著增长压力的表。** 若未来增加指标数量或科室数量，年增量会线性放大：

| 指标数 | 科室数 | 年增行数 | 5 年行数 |
|---|---|---|---|
| 400 | 15 | 2,190,000 | 10,950,000 |
| 600 | 20 | 4,380,000 | 21,900,000 |
| 800 | 30 | 8,760,000 | 43,800,000 |

**应对措施（按优先级）：**

| # | 措施 |
|---|---|
| 1 | 月粒度事实与日粒度事实分表；日粒度事实只保留 3 年，之后归档到只读历史库 |
| 2 | 对长期无人查询的 `metric_code` 设置 `is_active = FALSE`，采集任务跳过 |
| 3 | 分区按年归档：结账满 3 年的分区 `DETACH PARTITION` 后转只读表空间 |
| 4 | 若仍需扩展，考虑将「低基数维度（指标×科室）」预聚合为宽表，牺牲灵活性换查询性能 |

### 6.2 关键依赖说明

| 表 | 依赖 | 原因 |
|---|---|---|
| `m22_fact_metric` | `m22_metric_def` | 每个事实必须对应一个已注册指标（逻辑依赖，**不建物理外键**） |
| `m22_metric_target` | `m22_metric_def` | 目标值挂在指标版本下 |
| `m22_report_row` | `m22_report_instance` | 行数据属于某个实例 |
| `m22_report_instance` | `m22_report_template` | 实例必须由模板产生 |
| `m22_collect_batch` | `m22_collect_task` | 批次由任务产生 |
| `m22_dashboard_alert` | `m22_dashboard_alert_rule` | 预警由规则触发 |

> **M22 全模块不建物理外键。** 与其余 21 个模块一致，逻辑约束由 Service 层 + 定期数据一致性巡检任务保证。原因：分区表上的外键会导致分区裁剪失效，且跨分区 `DELETE` 需要全分区扫描。

### 6.3 逻辑依赖的巡检任务

```python
# 每日 04:00 巡检，发现孤儿数据即告警（不自动删除）
def check_orphan_records() -> list[dict]:
    checks = [
        ("m22_fact_metric", "metric_code", "m22_metric_def", "metric_code"),
        ("m22_metric_target", "metric_code", "m22_metric_def", "metric_code"),
        ("m22_report_row", "instance_id", "m22_report_instance", "id"),
    ]
    problems = []
    for child, child_col, parent, parent_col in checks:
        count = session.execute(text(f"""
            SELECT COUNT(*) FROM {child} c
            WHERE NOT EXISTS (
                SELECT 1 FROM {parent} p WHERE p.{parent_col} = c.{child_col}
            )
        """)).scalar_one()
        if count > 0:
            problems.append({"child": child, "parent": parent, "orphans": count})
    return problems
```

```python
def upgrade() -> None:
    op.execute("""
        CREATE TABLE m22_fact_metric (
            id                 BIGINT GENERATED BY DEFAULT AS IDENTITY,
            metric_code        VARCHAR(64)   NOT NULL,
            period             VARCHAR(10)   NOT NULL,
            ...
            PRIMARY KEY (id, period)
        ) PARTITION BY RANGE (period)
    """)
    # 预建未来 12 个月分区 + DEFAULT

        CREATE TABLE m22_fact_metric_pdefault
        PARTITION OF m22_fact_metric DEFAULT
    """)
```

### 9.4 采集任务的初始化规则

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `schedule_cron` | `0 0 2 * * *` | 每日 02:00 |
| `timeout_ms` | `5000` | 单接口超时 |
| `max_retry` | `5` | 最大重试次数 |
| `retry_backoff` | `EXPONENTIAL` | 指数退避：2s / 4s / 8s / 16s / 32s |

## 10. 备份与归档

| 项 | 策略 |
|---|---|
| 全量备份 | 每日 01:00，保留 30 天 |
| 增量备份 | 每小时，保留 7 天 |
| WAL 归档 | 持续，支持 PITR 到秒 |
| 指标事实归档 | 满 3 年的日粒度分区 `DETACH` 后转只读表空间，保留永久 |
| 报表实例归档 | 发布后的实例固化不可变，保留 10 年 |
| 采集日志 | 保留 3 年，之后按分区 `DROP` |
| 审计日志 | 独立库，保留 10 年，不可删除 |

### 10.1 归档不影响报表可读性

> **关键设计：** 报表实例的行数据（`m22_report_row`）是**已固化的快照**，不依赖指标事实表。因此即使指标事实的 3 年前分区已归档，3 年前的报表仍可原样打开。
>
> 这样设计的原因：报表的审计价值在于「当时看到的是什么」，而不是「现在重算会得到什么」。若报表依赖实时重算，口径一变历史报表就全变了。

### 10.2 恢复演练

| 频次 | 内容 |
|---|---|
| 每周 | 从最近全量备份恢复到一个临时库，跑一次数据一致性巡检 |
| 每季度 | 从 3 个月前的备份做完整恢复，验证归档数据可取回 |
| 每年 | 全链路灾备切换演练 |
