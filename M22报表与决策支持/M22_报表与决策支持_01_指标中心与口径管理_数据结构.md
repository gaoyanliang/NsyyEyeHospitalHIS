**四个设计要点说明：**

1. **为什么「指标定义」与「指标版本」不做成两张表。** 有些设计会把 `metric` 与 `metric_version` 拆成主表 + 版本表。本设计**刻意合并**为一张 `m22_metric_def` 自引用表，理由是：拆表后「指标当前生效的是哪个版本」需要跨表 JOIN，而 `P-03` 单指标取值接口的 SLA 是 `P95 ≤ 100ms`，每次都 JOIN 得不偿失；合并后一次索引扫描即可命中 `(metric_code, status='ACTIVE')` 组合。代价是 `metric_code` 在多行重复出现，但 `metric_code` 长度上限 64 字符，300 个指标 × 3.2 版本 = 960 行，重复存储完全可接受。
2. **为什么 `uk_m22_metric_def_active` 用部分唯一索引而不是应用层校验。** 「同一指标只能有一个生效版本」是**并发敏感**约束：两个管理员同时审批 v2 与 v3 时，应用层先查后写会产生竞态（中间结果两个都写成 `ACTIVE`）。PostgreSQL 16 的部分唯一索引在**索引层**排他，第二个事务必然收到 `unique_violation`，这是唯一可靠的保证方式。**这一条是本子模块最重要的一个索引**，详见 4.2 节设计说明第 2 条。
3. **为什么血缘表要存「逐跳」而不是「直接来源」。** 报表上看到 `OP_REVENUE_TOTAL` 时，业务方问的往往是「这个数从哪个系统来的」，而答案链条是「M22-01 定义 → M22-02 采集 → M16-09 日结接口 → M16 收费明细」。如果血缘只存最后一跳（`M16_REVENUE`），中间经过哪张表、被谁校准过就丢失了。逐跳存储使 `P07 指标血缘` 页面可以画出完整链路，也为「某上游接口变更时影响哪些指标」的反向查询提供索引依据。
4. **为什么目标值要独立成表而不是挂在定义表上。** 目标值是「期间 × 层级 × 组织」的三维事实，一行一个组合；指标定义是「口径」的单维元数据。两者的变更节奏、权限、审计要求完全不同：口径变更走审批流（月度级，由质控办主任批准），目标下达走下达流（年度 / 季度 / 月度，由院长批准）。混在一张表里会让 `m22_metric_def` 行数膨胀十倍，且版本语义被污染。

### 4.2 表：`m22_metric_def`（指标定义表）

> ★ **核心表** —— 本子模块的地基，也是全 M22 唯一的口径注册处。

**用途：** 登记每一个指标的**口径定义**。一条记录 = 某个指标编码的某个版本。指标编码全局唯一且**永不复用**（废弃只置 `is_active = FALSE`，编码本身保留）；口径变更时新增一条 `version + 1` 的记录，旧版本保留并置为 `DEPRECATED`，**历史报表按当时版本号取值，永不按新口径回溯重算**。

**为什么这张表是整个 M22 最关键的一张表：** 全院报表最大的纠纷不是「数据算错了」，而是「同一件事两个地方两个数」。例如「门诊人次」这张报表写 1,842，M04 门诊模块首页写 1,850 —— 差的 8 个是因为一个含退号一个不含。口径散落在各模块代码里时，这种差异永远说不清。把口径**收口成一张可查询、可版本化、可审批、可追溯**的表，是 M22 存在的首要理由。

```sql
ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_nine_elements
    CHECK (status IN ('DRAFT', 'REJECTED')
           OR (numeric_desc_ok(numerator_desc)
               AND numerator_desc IS NOT NULL
               AND sample_filter IS NOT NULL
               AND granularity IS NOT NULL
               AND source_module IS NOT NULL
               AND refresh_freq IS NOT NULL
               AND null_policy IS NOT NULL));

ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_active_effective
    CHECK (status <> 'ACTIVE' OR effective_from IS NOT NULL);

ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_active_flag
    CHECK ((status = 'ACTIVE') = is_active);

ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_effective_range
    CHECK (effective_to IS NULL OR effective_from IS NULL

ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_breaking_note
    CHECK (change_type <> 'BREAKING' OR compat_note IS NOT NULL);

-- v1 不得有 supersedes_id；v>1 必须有
ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_supersedes
    CHECK ((version = 1 AND supersedes_id IS NULL)
           OR (version > 1 AND supersedes_id IS NOT NULL));

-- 自引用不得指向自己
ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_no_self_parent
    CHECK (supersedes_id IS NULL OR supersedes_id <> id);
ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_no_self_root
    CHECK (root_id IS NULL OR root_id <> id);

-- 派生指标必须有 derived_from
ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_derived
    CHECK (is_derived = FALSE OR derived_from IS NOT NULL);

-- RETURN_ZERO 仅允许纯计数类（铁律：分母为 0 一律返回 NULL）
ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_zero_policy
    CHECK (null_policy <> 'RETURN_ZERO' OR metric_unit = 'COUNT');

-- 来源接口路径格式：必须以内 /internal/v1/ 开头（禁直查业务表）
ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_source_api
    CHECK (source_api_path IS NULL
           OR source_api_path LIKE '/internal/v1/%');

-- 生效日与审批日期一致
ALTER TABLE m22_metric_def
    ADD CONSTRAINT ck_m22_metric_def_approve_consistency
    CHECK (status <> 'ACTIVE' OR approve_at IS NOT NULL);
```

> **`numeric_desc_ok()` 说明：** 上面 `ck_m22_metric_def_nine_elements` 中的 `numeric_desc_ok` 是文档为可读性使用的占位函数名，实际 DDL 中直接展开为 `char_length(trim(numerator_desc)) >= 10`。完整可执行版本见下方 DDL 段落。

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | `(metric_code, version)` 双键而非单键 `id` | 历史报表要能回答「当时用的是第几版口径」，必须能按 `(code, version)` 精确定位；`calc_version` 在各报表子模块冗余存储 |
| 2 | **部分唯一索引 `uk_m22_metric_def_active`** | 「同一编码只能一个 ACTIVE」是并发敏感约束。应用层「先查后写」在两个管理员同时审批 v2/v3 时会双写成功；部分唯一索引在索引层排他，第二个事务必然 `unique_violation`，这是唯一可靠保证 |
| 3 | 部分索引 `WHERE status='ACTIVE'` 而非 `is_active=TRUE` | `is_active` 有 CHECK 约束与 `status` 强绑（`ck_m22_metric_def_active_flag`），用 `status` 更贴近语义，且不会被误更新标志位绕过 |
| 4 | `root_id` + `supersedes_id` 双指针 | `root_id` 让「取某编码全部版本」只需两次索引扫描（先查 v1 得 root，再按 root 查全集）；`supersedes_id` 让版本链可视化（P04 版本对比页沿链前后翻页） |
| 5 | 九要素在 CHECK 里强制 | 「九要素不全不得提交」如果只写在 Service 层，任何绕过 Service 的脚本导入都会污染数据；CHECK 是最后一道闸 |
| 6 | `source_api_path` 必须 `/internal/v1/` 开头 | 这是「M22 不直查业务表」铁律在 DDL 层的体现，从数据上堵死写 `SELECT ... FROM m05_admission` 的可能 |
| 7 | `precision_scale` 与 `round_mode` 进定义表 | 精度与舍入属于口径的一部分。「同一指标在报表是 0.333、在大屏是 0.33」同样是口径不一致，必须统一登记 |
| 8 | `draft_json` 存草稿内容 | 编辑中的口径不能污染正式字段（正式字段一改就影响所有查询），草稿期写入 JSONB，提交审批时再落到正式字段 |
| 9 | `version_lock` 而非 `version` 做乐观锁 | 业务字段 `version` 已被口径版本号占用，乐观锁字段改名 `version_lock` 避免语义冲突（这是本表一个易错点） |
| 10 | `is_deleted` 只允许 DRAFT / REJECTED | `ACTIVE` 版本被引用后物理语义上就不存在「删除」，只能置 `DEPRECATED`；日志触发器与 Service 层双重拦截 |

### 4.3 表：`m22_metric_version_history`（口径版本变更轨迹表）

**用途：** 记录口径版本的**每一次状态迁移**，而不只是结果。一行 = 一次迁移事件（提交 / 审批通过 / 驳回 / 生效 / 停用 / 废弃 / 回滚），包含变更类型、审批链、影响面快照。这样「这个指标的口径为什么在 2026-07 变了」这类问题，不需要翻操作日志（`m22_metric_log` 是全模块混杂的），直接查本表即可。

**为什么需要独立于 `m22_metric_log`：** `m22_metric_log` 是技术审计日志，按天分区、保留 3 年、体量大（60 万行/年）；本表是业务语义表，只记口径版本的**业务事件**（约 1.3 倍版本数），保留期与指标定义一致（永久）。两者保留策略、查询模式、访问权限都不同，合并会让 P04 版本对比页每次查询都做全表扫描。

### 4.4 表：`m22_metric_target`（指标目标值与基线表）

#### 用途

`m22_metric_target` 保存「某指标在某统计周期、某层级（医院级 / 科室级 / 个人级）、某责任对象上的目标值与基线值」。它是 M22-08 预算与目标达成看板、M22-04 科室目标达成、M22-07 绩效指标池的唯一目标来源。

三条设计约束：

1. **周期键用 `period_type` + `period` 双字段**，`period_type` 取 MONTHLY / QUARTERLY / YEARLY，`period` 分别形如 `2026-10` / `2026-Q4` / `2026`。用单字段 `VARCHAR(7)` 存不下季度与年度的语义边界，所以必须双字段并由 CHECK 约束保证格式与 `period_type` 一致。
2. **唯一键是 (metric_code, period, dept_id, staff_id, target_level)**，`dept_id` 与 `staff_id` 用 `0` 表示「不适用」而非 NULL。原因：PostgreSQL 唯一索引对 NULL 不去重（多个 NULL 视为互不相同），若用 NULL 表示「医院级」则医院级目标可以被重复下达，唯一约束失效。这是本表最重要的一条约定，全表 `dept_id` / `staff_id` 均 `NOT NULL DEFAULT 0`。
3. **年 → 季 → 月的分解关系不在本表用触发器强校验，而由 `m22_metric_target_breakdown` 在「分解确认」事务内强校验**。理由见 4.5：分解是 1 对 N 的集合关系，用 CHECK 无法表达「子项之和等于父项」，用触发器则会在逐行插入时误报（插入第 1 个月时 12 个月之和必然不等于年目标）。因此约定：**分解的完整性判定发生在 `POST /api/v1/m22/metrics/targets/{target_no}/breakdown-confirm` 这一事务的末尾**，事务内 `SELECT sum(target_value) FROM m22_metric_target_breakdown WHERE parent_target_no = ...` 与父目标比对，不一致则 `RAISE EXCEPTION` 回滚。这与共享规范「数量口径三处一致」铁律在本表的落地方式一致。

### 4.5 表：`m22_metric_target_breakdown`（目标分解明细表）

#### 用途

`m22_metric_target_breakdown` 保存一个父目标（YEARLY 或 QUARTERLY）向下一级周期（QUARTERLY 或 MONTHLY）的分解明细。它是 4.4 中「年 → 季 → 月」分解的落地表：一个年度目标最多 4 条季度分解，一个季度目标最多 3 条月度分解。

设计要点：

1. **只存分解出来的子项，不存父项本身**。父项就是 `m22_metric_target` 里的那一条，用 `parent_target_no` 逻辑引用。这样父目标与分解行不会出现两份互相打架的数值。
2. **`breakdown_status` 三态 DRAFT / CONFIRMED / INVALIDATED**，只有 CONFIRMED 状态参与「子项之和 = 父项」的报表展示与达成率计算；DRAFT 只是草稿，允许保存不完整的分解（例如先填了 12 个月中的 9 个月）。
3. **确认时的求和校验在事务内完成**，容差为 `abs(差额) <= 0.000001 * 父项目标值`（即相对误差 1e-6），以覆盖 `NUMERIC(20,6)` 的末位舍入。校验不通过返回 `"2201043"` 并在 message 中给出差额。
4. **分摊尾差由最后一项吸收**。当用户选择「按期均分」时，Service 层把 `父项 / n` 向下取到 6 位小数分配给前 n-1 项，最后一项取 `父项 - sum(前 n-1 项)`，保证求和严格相等，不做四舍五入。这条规则与共享规范 §0.3 铁律「分摊尾差由最后一项吸收」一致。

### 4.6 表：`m22_metric_lineage`（指标血缘表）

#### 用途

`m22_metric_lineage` 回答三个问题，且答案可被程序读取而不只是文档描述：

1. **这个指标从哪个上游模块的哪个接口取数** —— `upstream_module` + `upstream_api_path`。
2. **数据经过了 M22 的哪个子模块、落在哪张表** —— `via_submodule` + `via_table`。
3. **取数用的是什么方式、什么粒度、什么延迟** —— `source_type` + `source_granularity` + `latency_estimate_ms`。

本表是详细设计 10.1 节 U-xx 上游调用清单的**数据化投影**：10.1 是人读的表，本表是程序读的表，两者由 `m22_metric_lineage_check` 定时任务做一致性比对（比对失败不阻断，只告警）。M22-08 的「数据字典与口径说明」页与 M22-02 的「采集血缘追溯」页都从本表取数。

设计要点：

1. **一个指标可以有 N 条血缘**（多来源合并，如「门诊人次」来自 M04 与 M06-01 两个接口），因此唯一键是 `(metric_code, metric_version, upstream_module, upstream_api_path, via_submodule, via_table)` 六元组，而不是只有 metric_code。
2. **`lineage_role` 区分主来源与辅来源**：PRIMARY（主来源，缺它则指标不可算）/ SUPPLEMENT（补充来源，缺它可用主来源）/ FALLBACK（降级来源）。这决定了上游不可用时的处理策略，与共享规范「绝不静默填 0」铁律配套。
3. **`via_table` 指向 M22 内部表而非业务表**。因为铁律规定 M22 不直查业务表，所有数据都经过 M22-02 的采集批次落到 M22 自己的表，所以血缘的第二跳必然落在 M22 内部。
4. **`schema_hash` 用于上游接口变更告警**：记录上游接口响应结构的指纹，定时任务比对，变化时提示「上游接口结构变更，血缘可能失效」，返回提示码 `"2201045"`。

### 4.7 表：`m22_metric_group`（指标分组与目录表）

#### 用途

`m22_metric_group` 定义指标的分组树（`m22_metric_def` 的 `group_code` 字段与其实现 `m22_metric_group_item` 指向的位置）。M22-03 的报表模板、M22-04 的科室报表、M22-08 的驾驶舱都需要按「业务域 → 主题 → 指标」三级树组织指标，本表就是这棵树。

设计要点：

1. **树形结构用 `parent_group_code` + `group_path` 双字段**，`group_path` 是物化的路径（如 `/OP/DEPT/`），这样「取某节点下全部子孙分组的指标」只需 `group_path LIKE '/OP/%'`，一次索引扫描即可，避免 PostgreSQL 递归 CTE 在深树上的性能问题。`group_path` 由 Service 层在插入/移动节点时重算并级联更新子树。
2. **`group_level` 限制 1~3 级**：1 = 业务域（对应 metric_domain），2 = 主题，3 = 自定义分组。共享规范 §3.3 的指标编码 `{域}_{主题}_{指标名}` 天然是两段拓扑，第 3 级留给运营再细分（如「视光-儿童近视防控」子集）。
3. **`group_code` 全局唯一且不可修改**：修改分组编码会让所有引用它的报表模板失效。需要改编码时走「新建分组 + 迁移指标 + 废弃旧分组」，与企业编码永不复用规则一致。
4. **系统内置分组不可删除**：`is_system = TRUE` 的分组（6 个业务域根节点）不允许删除，也允许在 P03 页面隐藏删除按钮，但后端仍须二次校验并返回 `"2201046"`。

```sql
### 4.8 表：`m22_metric_group_item`（指标与分组关联表）

#### 用途

`m22_metric_group_item` 是指标与分组的多对多关联表。一个指标可以同时挂在「主题分组」和「自定义分组」下（例如 `OPT_SALES_AMOUNT` 既在 `OPT_SALES` 主题组，又可能在「院长关注指标」自定义组），因此必须是关联表而非 `m22_metric_def` 上的单个外键字段。

设计要点：

1. **主分组与辅分组区分**：`m22_metric_def.group_code` 保存的是**主分组**（唯一，用于编码与血缘归属），本表的 `is_primary = TRUE` 行必须与之一致，由 Service 层在保存时同步校验，不一致返回 `"2201048"`。辅分组（`is_primary = FALSE`）只影响目录树展示，不影响口径。
2. **指标版本粒度**：关联到 `metric_code` 而不是 `metric_version`。分组是运营视角的归类，不随口径版本走；口径升级后指标仍然属于同一分组。
3. **删除分组时的处理**：删除分组前必须把其下的指标迁移或摘除，禁止级联删除关联行导致指标「无家可归」。Service 层在校验通过后才允许逻辑删除分组，否则返回 `"2201049"`。
```

```
### 4.9 表：`m22_metric_usage`（指标使用统计表）

#### 用途

`m22_metric_usage` 记录指标被谁、在哪个报表模板、以什么方式引用，用于回答 P07「指标使用分析」页的核心问题：**改这个指标的口径，会影响哪些报表？** 它同时也是「废弃指标」的前置校验依据——一个指标还有活跃引用时不允许直接废弃。

设计要点：

1. **只是引用关系的登记与计数，不做实时统计**。`usage_count` 由每日定时任务 `m22_metric_usage_refresh` 从 M22-03 的报表实例、M22-08 的看板配置等处汇总刷新，而不是在每次查询时累加，避免热点行锁竞争。
2. **`ref_type` 区分引用类型**：REPORT_TEMPLATE / REPORT_INSTANCE / DASHBOARD / TARGET / LINEAGE / EXTERNAL_API。其中 EXTERNAL_API 表示**外部模块通过 P-03/P-04/P-05 契约直接引用该指标**，这类引用最危险，废弃前必须逐一确认。
3. **`consumer_module` 记录消费方模块编号**。因为 P-05 是全部业务模块都会调的热点接口，一旦某指标被 M17 或 M20 直接引用，本表必须有记录，这是 10.1 契约清单与血缘表的下游对照。
```

### 4.10 表：`m22_metric_log`（操作日志表）

#### 用途

`m22_metric_log` 记录 M22-01 全部写操作与关键状态流转，用于审计追溯与问题定位。它是**只增不改**的表：任何 UPDATE / DELETE 都由数据库权限与触发器双重阻断。

设计要点：

1. **按月 RANGE 分区 + DEFAULT 分区**。指标定义变更日志属于低频数据（每月数千行），但审计要求保留 3 年，按年分区粒度不够、按月分区最合适。DEFAULT 分区兜底，防止超出预建分区范围时插入失败（生产事故的常见来源）。
2. **`before_snapshot` / `after_snapshot` 用 JSONB**，记录变更前后的完整业务字段快照（不含大字段），支持「任意时点回放」。为了控制行大小，快照只记录发生变化的字段加上主键，不做整行拷贝。
3. **只增不改的强制手段有三层**：
   - 应用层：Repository 只暴露 `insert` 方法，无 `update_log` 与 `delete_log`。
   - 数据库触发器：`BEFORE UPDATE OR DELETE` 触发函数直接 `RAISE EXCEPTION`。
   - 权限层：对应用连接账号 `REVOKE UPDATE, DELETE ON m22_metric_log FROM app_rw;`，只授 `INSERT, SELECT`。

```sql
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'm22_metric_log 只增不改：禁止对审计日志执行 % 操作', TG_OP
        USING ERRCODE = 'P0001',
              HINT = '如需更正，请追加一条更正说明日志';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m22_metric_log_immutable
    BEFORE UPDATE OR DELETE ON m22_metric_log
    FOR EACH ROW EXECUTE FUNCTION fn_m22_metric_log_immutable();

REVOKE UPDATE, DELETE ON m22_metric_log FROM app_rw;
```

### 4.11 表：`m22_metric_config`（指标参数配置表）

#### 用途

`m22_metric_config` 保存 M22-01 的运行参数与业务开关，采用 key-value 形式，避免为新开关而频繁改表。它是「配置即数据」的落地：审批是否强制双人复核、缓存 TTL、目标值预警阈值默认值、口径变更通知对象、脏数据容忍度等都在这里。

设计要点：

1. **配置按作用域分层**：`scope_type` 取 GLOBAL / DOMAIN / METRIC，`scope_code` 分别对应空、业务域编码、指标编码。取值优先级 METRIC > DOMAIN > GLOBAL，Service 层加载配置时按此顺序覆盖，与 Spring 配置覆盖思路一致。
2. **配置项必须有默认值**：`default_value` 与 `config_value` 分离。`config_value` 为 NULL 时使用 `default_value`，这样运维不需要为每个指标都显式配一遍，也不会因缺行导致空指针。
3. **变更必须审计**：配置变更写 `m22_metric_log`（object_type=CONFIG），并且 `is_hot_reload = TRUE` 的配置项在变更后立即发 Redis Pub/Sub 通知各实例刷新本地缓存（`m22:config:refresh` 频道）。
4. **`config_value` 用 TEXT 而非统一 JSONB**：虽然 JSONB 更灵活，但配置校验需要根据 `value_type` 做严格类型校验（INT / BOOL / DECIMAL / STRING / JSON），用 TEXT + `value_type` 能在数据库层用 CHECK 粗校验格式，应用层再做精确校验，比全 JSONB 更容易发现问题配置。

```sql
### 4.12 SQLAlchemy 2.0 模型定义

本节给出 10 张表全部对应的 SQLAlchemy 2.0 声明式模型。约定：

- 统一使用 `Mapped` / `mapped_column` 新式写法，不用 `declarative_base()` 经典写法。
- 主键统一 `BigInteger` + `Identity(always=False)`，对应数据库 `GENERATED BY DEFAULT AS IDENTITY`。
- 金额、比率、指标值一律 `Numeric(precision, scale)`，**模型层不出现 `Float`**，与共享规范数值铁律一致。
- 枚举统一用 `String + CheckConstraint`，不用 `Enum` 类型，避免 PostgreSQL 原生 ENUM 的迁移难题。
- 分区表 `m22_metric_log` 在模型层标注 `postgresql_partition_by = "RANGE (log_time)"`，Alembic 生成 DDL 时保留分区声明。
- 部分索引与表达式索引用 `Index(..., postgresql_where=...)` 声明，Alembic autogenerate 会忽略这类索引，因此 `env.py` 中需开启 `include_object` 白名单，由初始化脚本人工作保。

```

```
### 4.13 Pydantic Schema 定义

本节定义 M22-01 对外接口与内部契约使用的 Pydantic v2 模型。约定：

- 全部继承统一的 `M22BaseModel`，开启 `from_attributes = True`，便于从 ORM 对象直接转换。
- **数值字段一律用 `Decimal`**，不用 `float`；比率字段用 `Decimal` 并配置 `max_digits=9, decimal_places=6`。
- 枚举字段用 `Literal` 而非 `Enum` 类，序列化即字符串，与数据库 `VARCHAR + CHECK` 保持一致。
- 请求模型命名后缀 `Create` / `Update` / `Query` / `Action`，响应模型后缀 `VO` / `Resp`。
- 分页响应统一 `PageResp[T]` 泛型。

```
"""M22-01 指标中心与口径管理 Pydantic v2 Schema 定义。

数值铁律：
1. 指标值与目标值用 Decimal(NUMERIC(20,6))，绝不用 float。
2. 比率用 Decimal(NUMERIC(9,6))。
3. 金额用 Decimal(NUMERIC(18,2))。

字段命名铁律：
1. 与外键一致的字段用 xxx_code / xxx_id。
2. 快照字段统一 _snap 后缀。
3. 时间字段统一 _at 后缀，日期统一 _date 后缀，布尔统一 is_ / has_ / need_ 前缀。
"""

from __future__ import annotations

from datetime import date, datetime
from decimal import Decimal
from typing import Any, Generic, Literal, Optional, TypeVar

from pydantic import BaseModel, ConfigDict, Field, field_validator, model_validator


M22BaseModelT = TypeVar("M22BaseModelT")

MetricDomain = Literal["OP", "CL", "OPT", "REF", "FIN", "PERF"]
Granularity = Literal[
    "REALTIME", "HOURLY", "DAILY", "WEEKLY", "MONTHLY", "QUARTERLY", "YEARLY"
]
MetricUnit = Literal["COUNT", "RATE", "PERCENT", "AMOUNT", "DURATION", "RATIO", "SCORE", "INDEX"]
ValueDirection = Literal["HIGHER_BETTER", "LOWER_BETTER", "NEUTRAL"]
MetricStatus = Literal["DRAFT", "PENDING", "ACTIVE", "INACTIVE", "DEPRECATED"]
ChangeType = Literal["BREAKING", "NON_BREAKING"]
TargetLevel = Literal["HOSPITAL", "DEPT", "STAFF"]
PeriodType = Literal["MONTHLY", "QUARTERLY", "YEARLY"]
TargetStatus = Literal["NOT_SET", "ON_TRACK", "AT_RISK", "ACHIEVED", "MISSED"]
LineageRole = Literal["PRIMARY", "SUPPLEMENT", "FALLBACK"]
RefType = Literal[
    "REPORT_TEMPLATE", "REPORT_INSTANCE", "DASHBOARD", "TARGET", "LINEAGE", "EXTERNAL_API"
]


class M22BaseModel(BaseModel):
    """M22 全模块公共基类。"""

    model_config = ConfigDict(
        from_attributes=True,
        populate_by_name=True,
        str_strip_whitespace=True,
        use_enum_values=True,
    )


class PageResp(M22BaseModel, Generic[M22BaseModelT]):
    """统一分页响应。"""

    items: list[M22BaseModelT] = Field(default_factory=list, description="当前页数据")
    total: int = Field(ge=0, description="总记录数")
    page: int = Field(ge=1, description="当前页码，从 1 起")
    page_size: int = Field(ge=1, le=200, description="每页条数")
    pages: int = Field(ge=0, description="总页数，total 为 0 时为 0")

    @model_validator(mode="after")
    def check_pages(self) -> "PageResp[M22BaseModelT]":
        expected = 0 if self.total == 0 else (self.total + self.page_size - 1) // self.page_size
        if self.pages != expected:
            self.pages = expected
        return self


class ApiResp(M22BaseModel, Generic[M22BaseModelT]):
    """统一响应体，code 为 7 位字符串错误码，成功为 '0'。"""

    code: str = Field(default="0", description="业务码，成功 '0'，失败为 7 位错误码字符串")
    message: str = Field(default="success", description="提示信息")
    data: Optional[M22BaseModelT] = Field(default=None, description="业务数据")
    trace_id: str = Field(description="全链路追踪 ID")


class MetricDefCreate(M22BaseModel):
    """新建指标定义（草稿）。九要素必填，缺一不可。"""

    metric_code: str = Field(min_length=5, max_length=64, pattern=r"^[A-Z][A-Z0-9_]*$")
    metric_name: str = Field(min_length=2, max_length=128)

```
## 附录 E 常用查询 SQL 参考

以下 SQL 均为 M22-01 内部使用，**只查 M22 自己的表**，不出现任何业务表名，符合「M22 不直查业务表」铁律。

**E.1 取某指标当前 ACTIVE 版本（P-03 主查询）**

```
SELECT metric_code, metric_name, version, metric_domain, group_code,
       numerator_desc, denominator_desc, valid_sample_cond,
       zero_denominator_policy, metric_unit, value_scale, ref_module,
       source_api_path, granularity, value_direction, status,
       effective_from, effective_to
FROM m22_metric_def
WHERE metric_code = $1
  AND status = 'ACTIVE'
  AND is_deleted = FALSE
LIMIT 1;
```

**E.2 批量取多指标当前 ACTIVE 版本（P-04 主查询）**

```
SELECT metric_code, metric_name, version, metric_domain,
       metric_unit, value_scale, value_direction, granularity,
       zero_denominator_policy, status
FROM m22_metric_def
WHERE metric_code = ANY($1::varchar[])
  AND status = 'ACTIVE'
  AND is_deleted = FALSE;
```

**E.3 取某指标的全部历史版本（P04 版本对比页）**

```
SELECT version, metric_name, status, effective_from, effective_to,
       numerator_desc, denominator_desc, valid_sample_cond, metric_unit, value_scale
FROM m22_metric_def
WHERE metric_code = $1
  AND is_deleted = FALSE
ORDER BY version DESC;
```

**E.4 口径变更影响面（P08 指标变更影响分析）**

```
SELECT u.ref_type,
       count(*)                              AS ref_cnt,
       array_agg(DISTINCT u.ref_code)        AS ref_codes,
       array_agg(DISTINCT u.consumer_module) AS modules
FROM m22_metric_usage u
WHERE u.metric_code = $1
  AND u.is_active_ref = TRUE
  AND u.is_deleted = FALSE
GROUP BY u.ref_type
ORDER BY ref_cnt DESC;
```

**E.5 目标达成看板（分母为 0 时达成率为 NULL 而非 0）**

```
SELECT t.target_no, t.metric_code, t.metric_name_snap, t.period,
       t.target_level, t.dept_name_snap, t.staff_name_snap,
       t.target_value,
       t.actual_value,
       CASE WHEN t.target_value = 0 THEN NULL
            ELSE round(t.actual_value / t.target_value, 6)
       END AS achieve_rate_calc,
       t.target_status
FROM m22_metric_target t
WHERE t.period_type = $1
  AND t.period = $2
  AND t.is_deleted = FALSE
ORDER BY t.metric_code, t.target_level, t.dept_id, t.staff_id;
```

**E.6 目标分解求和校验（breakdown-confirm 事务内执行）**

```
SELECT p.target_value                        AS parent_value,
       coalesce(sum(b.target_value), 0)      AS child_sum_value,
       p.target_value - coalesce(sum(b.target_value), 0) AS gap
FROM m22_metric_target p
LEFT JOIN m22_metric_target_breakdown b
       ON b.parent_target_no = p.target_no
      AND b.breakdown_status <> 'INVALIDATED'
      AND b.is_deleted = FALSE
WHERE p.target_no = $1
GROUP BY p.target_value;
```

**E.7 分组树取某节点及其子孙的指标数（P03 目录树徽标）**

```
SELECT g.group_code, g.group_name, g.group_path, g.group_level,
       count(DISTINCT i.metric_code) AS subtree_metric_cnt
FROM m22_metric_group g
LEFT JOIN m22_metric_group_item i
       ON i.group_code = g.group_code
      AND i.is_deleted = FALSE
WHERE g.group_path LIKE $1 || '%'
  AND g.is_deleted = FALSE
GROUP BY g.group_code, g.group_name, g.group_path, g.group_level
ORDER BY g.group_path;
```

**E.8 血缘四跳链路（P07 血缘图）**

```
SELECT l.lineage_order, l.lineage_role,
       l.upstream_module, l.upstream_submodule, l.upstream_api_path,
       l.via_submodule, l.via_table, l.formula_fragment,
       l.required_flag, l.degrade_strategy, l.is_verified
FROM m22_metric_lineage l
WHERE l.metric_code = $1
  AND l.metric_version = $2
  AND l.is_deleted = FALSE
ORDER BY l.lineage_order;
```

**E.9 上游模块反查依赖它的指标（上游改版时的影响面）**

```
SELECT DISTINCT l.metric_code, d.metric_name, d.version, d.status
FROM m22_metric_lineage l
JOIN m22_metric_def d
  ON d.metric_code = l.metric_code
 AND d.version = l.metric_version
WHERE l.upstream_module = $1
  AND l.upstream_api_path = $2
  AND l.is_deleted = FALSE
  AND d.is_deleted = FALSE
ORDER BY l.metric_code;
```

**E.10 长期未被引用的指标（可建议停用）**

SELECT d.metric_code, d.metric_name, d.version, d.status,
       coalesce(max(u.usage_last_at), d.created_at) AS last_used_at
FROM m22_metric_def d
LEFT JOIN m22_metric_usage u
       ON u.metric_code = d.metric_code
      AND u.is_active_ref = TRUE
      AND u.is_deleted = FALSE
WHERE d.status = 'ACTIVE'
  AND d.is_deleted = FALSE
GROUP BY d.metric_code, d.metric_name, d.version, d.status, d.created_at
HAVING coalesce(max(u.usage_last_at), d.created_at) < CURRENT_TIMESTAMP - INTERVAL '180 days'
ORDER BY last_used_at;
```

## 附录 F 术语表与版本历史

### F.1 术语表

| 术语 | 英文或代码 | 定义 |
| --- | --- | --- |
| 指标 | metric | 用统一口径描述的、可定量测量的经营管理或临床业务度量，本模块的一等公民 |
| 指标编码 | metric_code | `{域}_{主题}_{指标名}` 全大写，全局唯一且永不复用 |
| 指标版本 | metric_version | 口径的一次正式定义，从 1 递增，同一编码可多版本并存但只有一个 ACTIVE |
| 九要素口径 | nine elements | 分子、分母、有效样本条件、分母为零策略、单位、精度、数据来源模块、来源接口路径、统计周期 |
| 口径 | caliber | 指标的计算定义，包括取数范围、过滤条件、聚合方式、异常处理 |
| BREAKING 变更 | breaking change | 分子分母或统计范围变化的变更，历史报表不可比，必须升版本 |
| NON_BREAKING 变更 | non-breaking change | 只改描述文字或展示精度的变更，可原地修改不升版本 |
| 血缘 | lineage | 指标从上游接口取数、经过 M22 子模块、落到 M22 内部表的完整链路 |
| 目标值 | target | 某期间、某层级、某责任对象上期望达到的指标值 |
| 基线 | baseline | 用于对比的历史参考值，来源可为上年同期、近三月均值或手工设定 |
| 目标分解 | breakdown | 把年目标按季、季目标按月拆解的过程，子项之和须等于父项 |
| 尾差吸收 | tail absorption | 均分产生的舍入差额由最后一项吸收，保证求和严格相等 |
| 达成率 | achieve rate | 实际值除以目标值，目标值为 0 时返回 NULL 不返回 0 |
| 指标分组 | metric group | 业务域、主题、自定义三级目录，用于报表组织与导航 |
| 影响面 | impact analysis | 口径变更前分析会影响哪些报表、看板、目标与外部模块 |
| 口径说明书 | caliber spec | 面向业务人员的指标口径文档，由 P06 页面导出 |
| 数据字典 | data dictionary | 全量指标定义的结构化清单，供外部模块与运维查阅 |
