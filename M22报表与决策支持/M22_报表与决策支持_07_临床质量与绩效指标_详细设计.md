## 1. 模块概述

### 1.1 模块定位

M22-07 是**临床质量与绩效指标的数据组织与呈现模块**。它回答三个问题：

1. **医院的质量到底怎么样？** —— 医疗质量、手术麻醉效率、护理质量、院感安全四类指标，按期按科室呈现。
2. **这个月的绩效该照什么算？** —— 输出绩效指标池：指标实际值、单位分值、权重、得分。
3. **等级评审过不过得了？** —— 按评审标准版本逐条款判定达标情况，指出短板。

**一句话定位：M22-07 是全院临床质量数据的「汇总呈现层」与「绩效指标的「数据供给侧」。它取数、组织、呈现，但既不产生业务事实，也不计算绩效金额。**

### 1.2 为什么必须独立成子模块

这个问题在 M22 模块设立时就有人质疑过：临床质量指标看起来只是「几个统计报表」，为什么值得一个独立子模块？下面用四组事实回答。

#### 1.2.1 数据源极度分散，汇总逻辑无法塞进任何一个业务模块

临床质量指标的全部数据来源清单：

| 主题 | 上游模块 | 接口数量 | 归属系统 |
|---|---|---|---|
| 医疗质量 | M05 住院管理（病案首页质量） | 1 | 住院系统 |
| 医疗质量 | M12 门诊 / M13 医技 | 2 | 门诊系统、医技系统 |
| 手术麻醉效率 | M09 手术麻醉管理 | 2 | 手术麻醉系统 |
| 护理质量 | M08 护理管理 | 5 | 护理系统 |
| 院感与安全 | M09-04 器械清点 + **无上游** | 1 | 手术麻醉系统 / 手工 |
| 绩效指标值 | M07 门诊工作量 | 1 | 门诊系统 |
| 屈光并发症 | M11 屈光手术管理 | 1 | 屈光系统 |
| 评审指标值 | 上述全部 | — | — |

**合计跨 7 个模块、13 个接口。**

这 13 个接口分属 7 个业务模块、由 7 个不同的开发小组维护，各自发布节奏、返回结构、统计口径都不同。如果让任何一个业务模块（比如 M09）来「顺便做」临床质量汇总，它就要去调另外 6 个模块的接口——**这在架构上是反向依赖**：手术麻醉系统不应该依赖护理系统的数据形状。

**因此必须在业务模块之上有一层汇总层。** 这就是 M22。

#### 1.2.2 指标的「口径」本身就是一项需要治理的资产

看一个具体例子。同一个月、同一个指标，「I 类切口感染率」在院内三个地方可能算出三个数：

| 口径定义 | 分子 | 分母 | 算出的值 |
|---|---|---|---|
| 口径 A（传统） | I 类切口感染例数 | I 类切口手术**例数** | 0.012500 |
| 口径 B（2022 版评审标准） | I 类切口感染例数 | I 类切口手术例数 **减术前已感染例数** | 0.013158 |
| 口径 C（含门诊手术） | I 类切口感染例数（含门诊） | 全部 I 类切口手术（含门诊） | 0.009804 |

**三个数都对，只是口径不同。** 而评审现场只认一种口径。如果口径散落在各业务模块的代码里，评审前要改口径就得改 7 个模块的代码，且改完还不知道改全了没有。

M22 把「口径」提升为**一等公民**：每个指标有编码、有版本、有分子分母定义、有排除条件。口径变更走版本升级，历史数据不重算。**这项治理工作必须有一个专门模块承担。**

#### 1.2.3 绩效不能既由 M22 算又由 M17 算

绩效金额的计算链路是：

```
M07 工作量 → M22-07 指标池（实际值 + 单位分值 + 权重 → 得分）
                        ↓
        M17-07 绩效核算（得分 × 科室系数 × 质量系数 → 绩效金额）
                        ↓
        M17-07 发放（公示、申诉、发放、红冲）
```

**若 M22 也输出金额**，就会有两套金额算法、两个数对不上、审计时说不清以谁为准。**金额只能有一个计算方，就是 M17-07**（它是财务模块，有科室系数、质量系数、发放审批、红冲全套流程）。

因此 M22-07 的边界卡死在「得分」为止。这不是技术取舍，是**责任边界**。

#### 1.2.4 等级评审要求「举证可追溯」，这需要独立的数据结构

评审现场被质询时，必须能回答：

- 这个数是**哪一版标准**判的？（`standard_version`）
- 这个数的**分子分母**是什么？（`num_value` / `den_value`）
- 数据**什么时候采的**？（`calc_at` / `collect_batch_no`）
- 如果没数据，是**真的没有**还是**没采到**？（`achieve_status = 'NO_DATA'` vs 值为 0）
- 举证**材料在哪**？（`evidence_url`）

这些字段不属于任何业务模块的自然领域模型。**它们只能活在 M22 的评审数据结构里。**

### 1.4 关键概念辨析

| 概念 | 定义 | 容易混淆的邻居 | 区别 |
|---|---|---|---|
| **指标事实（metric_fact）** | 一个指标在一期一维度上的一次取值 | 指标定义 | 指标定义是「怎么算」（口径），事实是「算出来是多少」 |
| **可销售量 vs 指标值** | — | — | 本模块不涉库存，此处不适用，见 M10-07 |
| **绩效指标池（perf_pool）** | 指标值 × 单位分值 × 权重 = 得分 | 绩效金额 | 池只到「得分」（无量纲），金额由 M17-07 乘系数得到 |
| **标准版本（standard_version）** | 评审标准的一次改版（2012/2022） | 条款号 | 条款号 `3.2.1` 在不同版本含义不同，必须靠版本区分 |
| **达标记录（review_achv）** | 某期某科室在某版本某条款上的判定结论 | 指标事实 | 达标记录是「判了没判到」，事实是「值是多少」 |
| **手工填报（entry_mode=MANUAL）** | 由人工填写的数据 | 接口采集 | 手工填报的数据质量等级默认 `MANUAL_PENDING`，绝不冒充系统数据 |
| **数据完整性（source_status）** | COMPLETE/PARTIAL/FAILED/STALE | 值是否为 0 | 不完整 ≠ 值为 0；不完整时值为 NULL |
| **达标 vs 目标达成** | 评审达标是「是否过分数线」 | 目标达成率 | 目标达成率是连续值（1.057692），达标是离散判定（ACHIEVED） |

### 1.5 设计目标

| # | 目标 | 可度量指标 |
|---|---|---|
| 1 | 指标值**永不造假** | 分母为 0 或数据缺失时值必为 NULL；全库 13 条比率字段均有对应 CHECK 约束 |
| 2 | 绩效边界**不可逾越** | `m22_clinical_perf_pool` 与 `m22_clinical_perf_weight` 零金额字段；得分算式在库层强校验 |
| 3 | 口径变更**历史不重算** | 达标记录唯一键含 `std_id`；标准版本 `is_current` 用部分唯一索引保证唯一 |
| 4 | 院感数据**诚实标注** | 无上游模块时 `source_api='MANUAL'`、`data_quality_level` 三档、`source_status` 默认 `PARTIAL` |
| 5 | 高并发可读 | 看板查询 P95 ≤ 800ms；指标计算批量 SQL 单批 ≤ 5000 行 |
| 6 | 全链路可追溯 | 每条指标值可追到 `collect_batch_no` → `source_api` → 上游记录 |

## 3. 业务模型

### 3.1 核心实体

```
                         ┌─────────────────────────┐
                         │ m22_clinical_metric_fact│
                         │  指标事实（月分区）      │
                         │  metric_code + period   │
                         │  + dept_id + biz_dim    │
                         └───────────┬─────────────┘
                                     │ 按主题拆解
        ┌────────────────┬───────────┼───────────┬─────────────────┐
        │                │           │           │                 │
┌───────▼──────┐ ┌───────▼──────┐ ┌──▼────────┐ ┌▼──────────────┐ │
```

### 3.2 状态机

#### 3.2.1 指标事实/主题数据状态机

```
                  ┌──────────┐
        采集/计算  │  DRAFT   │  草稿：可修正
                  └────┬─────┘
                       │ 发布操作（需 approve 权限）
                       │ 校验：source_status 非 FAILED
                       ▼
                  ┌──────────────┐
                  │  PUBLISHED   │  已发布：全表只读
                  └──────┬───────┘
                         │ 作废（须填 void_reason ≥ 10 字）
                         ▼
                  ┌──────────┐
                  │   VOID   │  已作废：保留痕迹，不参与统计
                  └──────────┘

  旁路：FAILED 的采集批次不产生 DRAFT 记录，直接告警
```

**状态转移表**

| 当前状态 | 事件 | 目标状态 | 前置条件 | 副作用 |
|---|---|---|---|---|
| （无） | 采集/计算完成 | DRAFT | `source_status ≠ FAILED` | 写 `collect_batch_no` |
| DRAFT | 修正 | DRAFT | 有 `edit` 权限；写 `adjust_reason` ≥ 10 字 | 更新值与 `updated_at` |
| DRAFT | 发布 | PUBLISHED | 有 `approve` 权限；`source_status ≠ FAILED` | 写 `published_at`/`published_by`；清 Redis 缓存；发事件 |
| DRAFT | 作废 | VOID | `void_reason` ≥ 10 字 | 不参与统计 |
| PUBLISHED | 作废 | VOID | 有 `admin` 权限；`void_reason` ≥ 10 字 | 发事件通知下游重取 |
| PUBLISHED | 再发布 | PUBLISHED | 禁止 | — |
| VOID | 任何 | — | 终态 | — |

**为什么不设 `CALCULATED` 中间态：** 计算与落库在同一个事务里完成（计算失败则整个事务回滚，不落半成品），因此不需要「已计算未发布」这个中间态。计算结果一落库就是 DRAFT。**少一个状态就少一条脏数据路径。**

**关键规则：`CONFIRMED` 起只读，M17-07 只消费 `CONFIRMED` 及之后状态的数据。**

| 当前状态 | 事件 | 目标状态 | 前置条件 |
|---|---|---|---|

#### 3.4.6 绩效指标池计算模型

**三步计算，全部分值，无量纲，无金额。**

```
第 1 步：未乘权重的得分
    raw_score = actual_value × unit_score
    例：门诊量 680.000000 人次 × 8.000000 分/人次 = 5,440.000000

第 2 步：乘权重得最终得分
    score = actual_value × unit_score × weight
    例：680.000000 × 8.000000 × 0.400000 = 2,176.000000

第 3 步：封顶保底（可选）
    若 score_cap 非空且 score > score_cap：score = score_cap, cap_applied = TRUE
    若 score_floor 非空且 score < score_floor：score = score_floor, cap_applied = TRUE
```

**数据库强校验：**

```
ck_m22_clinical_perf_pool_score_calc:
    score IS NULL
    OR abs(score - ROUND(actual_value * unit_score * weight, 6)) <= 0.000001
```

**规则 R8：得分必须严格等于公式值。数据库约束不容忍「手工微调得分」。**

**规范算例（本院眼科 2026-10 月，门诊医生张三）：**

| 指标 | 实际值 | 单位分值 | 权重 | raw_score | score |
|---|---|---|---|---|---|
| 门诊量 | 680 | 8.000000 | 0.400000 | 5,440.000000 | 2,176.000000 |
| 手术量 | 42 | 120.000000 | 0.600000 | 5,040.000000 | 3,024.000000 |
| **小计** | — | — | **1.000000** | — | **5,200.000000** |

**到此为止。M22-07 的输出就是「5,200.000000 分」。**

**下一步（不属本模块）：M17-07 绩效核算**取 5,200.000000 分，乘科室系数 1.05、质量调整系数 0.98：

```
5,200.000000 × 1.05 = 5,460.000000
5,460.000000 × 0.98 = 5,350.800000  → 5,350.80 元
```

**这最后一步永远在 M17-07 里做。** M22-07 的数据库里没有任何字段能装下「5,350.80」这个数，也不应该能装下。

#### 3.4.7 等级评审达标判定模型

```
第 1 步：取实际值
    actual_value = 该条款关联指标在该期该科室的值
    若 actual_value IS NULL → achieve_status = 'NO_DATA'

第 2 步：样本充足性判定
    sample_sufficient = (sample_count >= required_sample)

第 3 步：按达标准则判定
    pass_rule = 'RATE_GTE'  → ACHIEVED 当 actual_value >= target_value
    pass_rule = 'RATE_LTE'  → ACHIEVED 当 actual_value <= target_value
    pass_rule = 'COUNT_GTE' → ACHIEVED 当 actual_value >= target_value
    pass_rule = 'ALL_MUST'  → 全部子项达标才 ACHIEVED
    pass_rule = 'EXIST'     → manual_value 非空即 ACHIEVED

第 4 步：计算差距
    pass_rule = 'RATE_GTE'  → gap_value = target_value - actual_value（正数表示差距）
    pass_rule = 'RATE_LTE'  → gap_value = actual_value - target_value

第 5 步：整体达标率
    overall_rate = 达标条款数 / 条款总数
    条款总数为 0 → overall_rate = NULL（不是 0）
    core_achieved_rate = 核心条款达标数 / 核心条款总数
    核心条款数为 0 → core_achieved_rate = NULL
```

**关键规则 R9：`NO_DATA` 绝不等于 `NOT_ACHIEVED`，也绝不等于 `ACHIEVED`。** 数据库约束 `ck_m22_clinical_review_achv_no_data` 强制：判为 `ACHIEVED`/`NOT_ACHIEVED` 必须有实际值或人工值；判为 `NO_DATA` 必须确实无值。

**业务逻辑**

1. 汇总本期所有采集任务的最近运行状态。
2. `overall_status` 判定优先级：`FAILED` > `PARTIAL` > `STALE` > `COMPLETE`（与模块总纲 §6.6 一致）。

**缓存失效策略**

1. **精确失效**：数据变更时按 `metric_code` / `period` 拼出受影响的 key 精确 `DEL`，不用 `FLUSHDB`。
2. **版本号兜底**：`m22:version:{domain}`（如 `clinical_fact`）单调递增，key 中可选带版本前缀，版本提升后旧 key 自然失效。
3. **缓存穿透防护**：查不到数据时缓存空对象（`{"empty": true}`），TTL 60s。
4. **缓存雪崩防护**：TTL 加 ±10% 随机抖动。
5. **绝不缓存 `null` 指标值为 `0`**：空值就缓存 `null`，语义不能变。

**任务通用约定**

```python
from celery import shared_task
from celery.exceptions import MaxRetriesExceededError
import structlog

logger = structlog.get_logger(__name__)


@shared_task(
    bind=True,
    name="m22_clinical_collect",
    queue="m22.collect",
    max_retries=3,
    soft_time_limit=280,
    time_limit=300,
)
def collect_metrics(self, task_code: str, period_type: str, period: str) -> dict:
    """按采集任务配置批量采集指标。

    幂等：同一 (task_code, period_type, period) 重复执行结果一致，
    依靠 fact 表唯一键 ON CONFLICT DO UPDATE 保证。
    """
    from app.modules.m22.clinical.services.collect import CollectService

    service = CollectService()
    try:
        result = service.run_task(task_code, period_type, period)
    except Exception as exc:
        logger.warning(
            "clinical_collect_retry",
            task_code=task_code,
            period=period,
            retry=self.request.retries,
            error=str(exc),
        )
        try:
            raise self.retry(exc=exc, countdown=60 * (2 ** self.request.retries))
        except MaxRetriesExceededError:
            logger.error("clinical_collect_exhausted", task_code=task_code, period=period)
            service.mark_failed(task_code, period_type, period, str(exc))
            return {"status": "FAILED", "task_code": task_code}
    return {"status": result["status"], "batch_no": result["batch_no"]}
```

### 10.6 绩效金额边界的防线分层（P-CL-02 出参白名单）

#### 10.6.1 为什么需要专门定义白名单

「M22 不算钱」这条铁律，最容易被误解成「建表时不放 amount 字段就完成了」。
事实不是这样。**一条 `CHECK` 约束只能拦住「库里的某个值」，拦不住「M22 从头就不该产出某个字段」。**
真正把边界钉死的是一组分层防线，任何一层单独存在都不够：

| 层 | 防线 | 挡得住什么 | 挡不住什么 |
|---|---|---|---|
| 第 1 层：**接口层白名单**（本节） | P-CL-02 出参字段白名单，逐字段枚举 | 「M22 从一开始就产出系数字段」——这是最根本的一层 | 绕过接口直改数据库 |
| 第 2 层：**数据层约束** | `ck_m22_clinical_perf_pool_weight_pure`（weight 纯度）、`ck_..._score_calc`（算式自洽） | 「系数被乘进 weight」「得分被手工微调」 | 通过接口新造字段 |
| 第 3 层：**流程层状态机** | `CONFIRMED` 后只读，改配置必须新建 `scheme_version` | 「历史周期被悄悄改写」 | 首次录入时的人为误填 |

**第 1 层比第 2 层更根本的原因：** CHECK 只能挡「权重被改成可疑值」，白名单能挡「M22 压根不该有这些字段」。
前者是事后审判一个已经存在的坏值，后者是事前拒绝一整个不该存在的数据类别。

#### 10.6.2 P-CL-02（API-23）出参字段白名单

`GET /internal/v1/m22/clinical/perf/pool/export` 的响应体中，**`items[]` 每一项只允许出现下列字段**，
白名单之外的字段一律视为缺陷：

| 序号 | 允许字段 | 类型 | 语义 |
|---|---|---|---|
| 1 | `staff_id` | integer | 人员 ID |
| 2 | `staff_no` | string | 人员工号 |
| 3 | `staff_name` | string | 人员姓名 |
| 4 | `dept_id` | integer | 科室 ID |
| 5 | `dept_code` | string | 科室编码 |
| 6 | `dept_name` | string | 科室名称 |
| 7 | `indicator_level` | string | 指标层级 STAFF/DEPT/HOSPITAL |
| 8 | `metric_code` | string | 指标编码 |
| 9 | `metric_name` | string | 指标名称 |
| 10 | `caliber_type` | string | 口径类型 SUM/AVG/COUNT/RATIO |
| 11 | `unit_type` | string | 单位类型 |
| 12 | `actual_value` | number | 指标实际值，缺失为 null |
| 13 | `unit_score` | number | 单位分值（分值，不是钱） |
| 14 | `weight` | number | 权重（占比，不是系数） |
| 15 | `score` | number | 得分 = 实际值 × 单位分值 × 权重 |
| 16 | `score_cap` | number | 得分封顶值 |
| 17 | `cap_applied` | boolean | 是否触发封顶/保底 |
| 18 | `is_excluded` | boolean | 是否剔除 |
| 19 | `source_status` | string | 数据完整性 |

**顶层字段白名单：** `period`、`scheme_code`、`scheme_version`、`item_count`、`all_confirmed`、
`boundary_notice`、`items`、`excluded_items`。

**响应体一律禁止出现的字段名（含同义变形）：**

| 禁止类别 | 正则匹配 | 说明 |
|---|---|---|
| 金额 | `AMOUNT` | `original_amount`、`final_amount`、`adjust_amount` 等 |
| 金钱 | `MONEY` | `money`、`money_value` 等 |
| 薪酬 | `SALARY`、`WAGE` | `salary`、`salary_base`、`wage` 等 |
| 发放 | `PAY` | `pay`、`payout`、`payable`、`paid_at` 等 |
| 系数 | `COEFFICIENT` | `dept_coefficient`、`quality_coefficient`、`coefficient` 等 |
| 应发实发 | `PAYABLE`、`PAID` | `payable_amount`、`paid_amount` 等 |

**系数为什么必须在 M17-07 侧乘、不能回流到 M22：**

| 系数 | 由谁产出 | 依赖的数据 | 若回流到 M22 会怎样 |
|---|---|---|---|
| 科室系数 | M17-07（依据 M17-04 科室结余） | 科室收入、成本、结余率 | M22 需要读财务成本数据，越界到 M17 职责范围，且结余口径会二次实现 |
| 质量调整系数 | M17-07（依据 M11-07 质量指标、M16 差错率） | 质量得分、差错率 | M22 需要读 M16 差错数据，同样是跨模块越界；且质量系数会随复核变化，M22 的 CONFIRMED 只读语义无法承载 |

结论：**两个系数都不属于 M22 的可信数据范围**，让它们回流到 `weight` 或 `score` 等于把 M17 与 M11/M16 的口径强行塞进 M22，制造第二套算法。这正是「M22 不算钱」要避免的。

#### 10.6.3 正常业务链路（系数永不回流）

```
M22-07：score = actual_value × unit_score × weight      ← 纯分值，库层算式约束保证
   │     （weight 纯度约束保证 weight 里没有系数）
   ↓  P-CL-02 白名单出参（无系数、无金额）
M17-07：绩效金额 = score × 科室系数 × 质量调整系数        ← 系数只在这一侧出现
```

若考核规则需要调整（含权重变化），**正确路径是新建 `scheme_version` 重算**（API-27），
旧版本的池表记录因冗余了当时的 `unit_score` / `weight` 而保持不变，历史可复算。
**绝不存在「M17 回头让 M22 用带系数的值重写 score」这种正常场景。**

### 11.2 上游调用降级策略

```python
import time
import structlog
import httpx

logger = structlog.get_logger(__name__)


class UpstreamResult:
    """上游调用结果封装。"""

    def __init__(self, ok: bool, data: dict | None,
                 source_status: str, missing: str | None = None) -> None:
        self.ok = ok
        self.data = data
        self.source_status = source_status
        self.missing = missing


def call_upstream(url: str, params: dict, timeout_ms: int = 2000) -> UpstreamResult:
    """调用上游接口，失败时降级为 FAILED 而不是编造数据。"""
    started = time.monotonic()
    try:
        resp = httpx.get(url, params=params, timeout=timeout_ms / 1000.0)
    except httpx.TimeoutException:
        logger.warning("upstream_timeout", url=url, params=params,
                       elapsed_ms=int((time.monotonic() - started) * 1000))
        return UpstreamResult(False, None, "FAILED", "上游接口超时")
    except httpx.HTTPError as exc:
        logger.warning("upstream_error", url=url, error=str(exc))
        return UpstreamResult(False, None, "FAILED", "上游接口不可用")

    if resp.status_code >= 500:
        logger.warning("upstream_5xx", url=url, status=resp.status_code)
        return UpstreamResult(False, None, "FAILED", "上游返回服务端错误")

    if resp.status_code == 404:
        return UpstreamResult(False, None, "PARTIAL", "上游无该期间数据")

    body = resp.json()
    if body.get("code") != "0":
        logger.warning("upstream_biz_error", url=url, code=body.get("code"))
        return UpstreamResult(False, None, "PARTIAL", body.get("message", "上游业务错误"))

    return UpstreamResult(True, body.get("data"), "COMPLETE")
```

**降级铁律：** 上游失败时指标值一律置 `NULL` 并标 `source_status`，**绝不补 0**。这是本模块最重要的一条异常处理原则——`0` 在质量指标里代表「真实的零缺陷」，与「没取到数」是完全不同的语义，混淆会导致质控报告失真。

### 11.3 日志规范

**结构化日志字段**

| 字段 | 必填 | 说明 |
|---|---|---|
| `trace_id` | 是 | 链路追踪 ID，全链路透传 |

| `submodule` | 是 | 固定 `M22-07` |
| `action` | 是 | 操作名，如 `metric.calc` |

| `period` | 指标相关必填 | 统计期间 |
| `metric_code` | 指标相关必填 | 指标编码 |
| `api_path` | 是 | 请求路径 |
| `elapsed_ms` | 是 | 耗时 |
| `result` | 是 | `SUCCESS` / `FAILED` / `PARTIAL` |
| `error_code` | 失败必填 | 错误码 |
| `extra` | 否 | 补充信息 JSON |

**日志级别使用**

| 级别 | 使用场景 |
|---|---|
| `DEBUG` | SQL 参数、缓存 key、计算结果明细（仅开发环境） |
| `INFO` | 接口调用、任务开始结束、数据发布、导出完成 |

**日志保留：** 应用日志保留 30 天，审计日志保留 3 年（调 M02-06）。

### 11.4 关键监控指标

| 监控项 | 阈值 | 告警级别 |
|---|---|---|
| 采集任务成功率 | < 95% | WARN |
| 采集任务连续失败天数 | ≥ 3 天 | CRITICAL |
| 指标数据 `FAILED` 占比 | > 5% | WARN |
| 院感填报缺口数 | > 0 且已过每月 5 日 | WARN |
| 指标计算耗时 P95 | > 5000ms | WARN |
| 导出任务失败率 | > 10% | WARN |
| 绩效池 `score` 与计算式不符行数 | > 0 | CRITICAL |
| 评审 `NO_DATA` 条款占比 | > 10% | WARN |

**严重不一致的定义与处置：**

- **绩效池得分被篡改**：库层 CHECK 应保证不可能发生。若监控发现违反，说明约束被绕过，立即 CRITICAL 告警并冻结该周期确认操作。
- **缓存与库数据不一致**：以库为准，强制清空相关缓存并重算。
- **评审历史被改动**：任何针对已确认期间达标记录的 UPDATE 都应告警，因为这违反「版本切换不重算」铁律。

## 附录 E 等级评审达标判定规则

| 达标准则 | 判定逻辑 | 差距计算 | 零值处理 |
|---|---|---|---|
| `RATE_GTE` | `actual_value >= target_value` → ACHIEVED；否则 NOT_ACHIEVED | `target_value - actual_value` | 实际值为 NULL → NO_DATA |
| `RATE_LTE` | `actual_value <= target_value` → ACHIEVED；否则 NOT_ACHIEVED | `actual_value - target_value` | 实际值为 NULL → NO_DATA |
| `COUNT_GTE` | `actual_value >= target_value` → ACHIEVED | `target_value - actual_value` | 实际值为 NULL → NO_DATA |
| `ALL_MUST` | `manual_value = 1` → ACHIEVED | 无 | 未举证 → NO_DATA |
| `EXIST` | `manual_value = 1` → ACHIEVED | 无 | 未举证 → NO_DATA |

**比率型条款的统一约束（库层强制）：**

| 场景 | 结果 |
|---|---|
| 分母 > 0 且分子有值 | 正常计算 `actual_value`，按 `pass_rule` 判定 |
| 分母 = 0 | `actual_value = NULL`，`achieve_status = NO_DATA` |
| 分母为 NULL | `actual_value = NULL`，`achieve_status = NO_DATA` |
| 分母 > 0 但分子缺失 | `actual_value = NULL`，`achieve_status = NO_DATA`，`source_missing` 必填 |

**核心条款与整体达标率：**

| 计算项 | 公式 | 分母为 0 时 |
|---|---|---|
| 整体达标率 | `achieved_count / total_clause` | NULL |
| 核心条款达标率 | `core_achieved_count / core_total` | NULL |

**版本切换不重算的规定：**

| 场景 | 处理 |
|---|---|
| 2026 年按 2022 版评定的结论 | 永久保留在 `std_id = 2` 的记录下，任何标准版本变更都不影响 |
| 2027 版启用后重算 2026 年 | 禁止（`"2207611"` 期间与版本不匹配） |
| 2027 年按 2027 版评定 | 写入 `std_id = 3` 的新记录，与 2022 版记录共存 |
| 同一期间两版记录并存 | 允许，唯一键含 `std_id` |

## 附录 F 术语表

| 术语 | 定义 |
|---|---|
| 指标事实 | 某指标在某期间某维度上的取值记录，落 `m22_clinical_metric_fact` |
| 指标口径 | 指标的分子、分母、有效样本条件、排除条件、零分母处理规则的完整定义 |
| 口径版本 | 指标口径的修订版本号，口径变更时升版本，历史值按当时口径留存 |
| 零分母处理 | 分母为 0 或 NULL 时指标值置 NULL（不是 0）的规则 |
| 有效样本 | 满足口径排除条件后参与计算的实际样本量 |
| 最小样本量 | 低于该样本量时结论仅供参考，`sample_sufficient = FALSE` |
| 绩效指标池 | 按周期、按人员或科室汇总的「指标值 + 单位分值 + 权重 + 得分」集合 |
| 单位分值 | 每 1 单位指标值折算的分数，如门诊量 8.00 分/人次 |
| 权重 | 指标在同层级中的占比，同层级权重和必须为 1 |
| 得分 | `实际值 × 单位分值 × 权重` 的结果，是**分值不是金额** |
| 绩效金额 | 得分 × 科室系数 × 质量调整系数，由 M17-07 计算，**本模块不产生** |
| 封顶 / 保底 | 限制单项指标得分的上 / 下限，触发时 `cap_applied = TRUE` |
| 剔除 | 某人某期不参与考核（如产假、借调），须填原因 |
| 评审标准版本 | 医院等级评审标准的版次，如 2012 版、2022 版，指标挂其下 |
| 条款号 | 评审条款编号，形如 `2022-3.2.1`，前缀即标准版本号 |
| 核心条款 | 评审中必须达标的条款，级别 `CORE` |
| 达标准则 | 判定条款是否达标的方法，共 5 种 |
| 达标差距 | 实际值与阈值的差，用于排序找短板 |
| 无数据 | 指标值为 NULL 的状态，`NO_DATA`，**不等于未达标** |
| 数据完整性 | `COMPLETE` / `PARTIAL` / `FAILED` / `STALE`，反映上游取数情况 |
| 数据质量等级 | 院感数据专用，`MANUAL_PENDING` / `MANUAL_VERIFIED` / `SYSTEM_AUTO` |
| 手工填报 | 无系统来源的数据由人工录入，全程留填报人与时刻 |
| 院感标准入口 | `GET /internal/v1/m22/clinical/nosocomial/collect`，院感数据唯一标准入口 |
| 采集任务 | 配置化的定时取数作业，落 `m22_clinical_collect_task` |
| 采集批次 | 一次采集作业产生的数据批次，用于溯源 |
| 完整性判定 | 报表整体状态按 `FAILED` > `PARTIAL` > `STALE` > `COMPLETE` 取最严重 |
| 模板编码 | `template_code`，引用 M22-03 报表骨架模板，不重复建表 |
