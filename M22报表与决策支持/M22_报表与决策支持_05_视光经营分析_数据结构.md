> **表前缀说明：** 全部表以 `m22_optical` 为前缀，符合共享规范 §12 为 M22-05 分配的「视光主题事实与配置」前缀。

> **表数量口径：** 共享规范 §12 建议本子模块 8~10 张表，本文档为 9 张，落在建议区间内。其中 4 张（`m22_optical_sales_fact`、`m22_optical_optometry_fact`、`m22_optical_conversion_fact`、`m22_optical_repurchase_fact`）支撑核心页面 P01/P02/P03/P06，3 张（`m22_optical_product_fact`、`m22_optical_turnover_fact`、`m22_optical_perf_fact`）支撑 P04/P05/P07，1 张（`m22_optical_export_task`）支撑 P08，1 张（`m22_optical_sync_log`）为全部取数链路提供可追溯性。

> `FK*` 表示**逻辑外键**（不建物理约束，由应用层保证）。

> ### ⚠️ 再次声明：通用报表骨架表归属
>
> 上图中 `m22_optical_export_task.template_code` 指向的 `m22_report_template` 属于 **M22-03 运营报表与日报月报**，本子模块**只引用不定义**。同理 `m22_report_instance`、`m22_report_row`、`m22_report_subscription` 三张表也全部由 M22-03 定义。本子模块的数据结构文件中**不存在**这四张表的建表语句。

**设计要点说明：**

1. **7 张事实表统一按 `period` 月度 RANGE 分区，且每张都带 `_pdefault` DEFAULT 分区。** 视光经营分析的取数粒度是「日」，但存储粒度对齐 M22 全模块约定的是 `period`（`YYYY-MM-DD` 或 `YYYY-MM`），按月分区后单分区数据量在 2,000~16,000 行量级，`period BETWEEN` 的区间查询能命中分区裁剪。DEFAULT 分区是保命的：漏建下个月分区时新数据会落进 `_pdefault` 而不是直接报 `no partition of relation found for row`，后者会让整条采集链路失败并导致当日报表空白。

2. **金额字段一律带 `_snap` 后缀并标注来源 M16。** 这不是命名洁癖。视光销售金额在本院有唯一权威来源 M16-04 的 `m16_optical_daily_summary`（`total_amount = gross_amount - discount_amount` 有 CHECK 约束保证）。M22 若在「销售额」字段上做任何加减乘除（比如把退货额从销售额里扣掉改口径），就产生了第二个金额定义，院周会两个数字打架时无从对账。`_snap` 后缀在代码 review 时就是一道显式红线：看到 `_snap` 的字段只能赋值、不能运算。

3. **转化率、复购率、周转率等比率字段允许 NULL，且 NULL 有明确语义。** 共享规范 §2.4 要求比率为 `NUMERIC(9,6)`，但分母为 0 时该比率在数学上无定义。存 `0` 会被业务误读成「一个都没转化」，存 `NULL` 并在展示层渲染为「—」才是正确表达。因此每张带比率的表都配 `ck_*_ratio_null` 约束强制「分母 ≤ 0 时比率必须为 NULL」。

4. **`m22_optical_sync_log` 是只增不改的流水表，不带 `updated_at`/`is_deleted`/`version`。** 排障与审计要求日志不可篡改：若同步失败后有人改了日志里的 `error_msg`，补采追溯就失去意义。因此对该表执行 `REVOKE UPDATE, DELETE`，并用触发器阻断，详见 4.10。

### 4.2 表：`m22_optical_sales_fact`（视光销售日汇总事实表）

**用途：** 存放按「统计期间 + 门店 + 业务维度」切片的视光销售金额与数量指标。本表是 P01 视光经营看板、P02 视光销售分析两张核心页面的唯一数据底座，也是 P04 产品结构、P07 门店业绩的总额校验基准（下钻各项之和必须等于本表的门店合计，差异超过阈值触发 `"2205019"`）。

**为什么金额必须来自 M16-04 而不能自己算：** 视光销售订单的金额构成在 M16-04 中有精确定义——`total_amount = gross_amount - discount_amount`，其中 `gross_amount` 是商品金额与服务金额之和，`discount_amount` 是各类优惠（会员折扣、套餐、优惠券、抹零）之和。这套口径涉及定金 30% / 尾款 70% 的分次收款、退款单的反向记账、以及「`total_amount` 按下单日归属、`paid_amount` 按收款日归属」的双时间轴。M22 若跨模块直查 `m16_optical_order` 自己做 `SUM`，第一会漏掉退款单的反向处理，第二会绕开 M16-04 的口径版本控制，第三违反共享规范 §0.3 铁律 2。因此本表的全部金额字段都带 `_snap` 后缀，由 Service 层从 `GET /internal/v1/m16/optical/statistics` 的响应原样落库，**不做任何再计算**。

**字段设计：**

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | `BIGINT` | 否 | `GENERATED BY DEFAULT AS IDENTITY` | 主键，分区表主键必须包含分区键 `period` |
| `metric_code` | `VARCHAR(64)` | 否 | `'OPT_SALES_AMOUNT'` | 指标编码，指向其他子模块（M22-01）定义的 `m22_metric_def.metric_code`；本表按 indicator 维度存"一条指标一行"的语义，视光销售额固定为 `OPT_SALES_AMOUNT` |
| `period` | `VARCHAR(10)` | 否 | 无 | 统计期间，日粒度写 `YYYY-MM-DD`（如 `2026-10-31`），月汇总行写 `YYYY-MM`；分区键 |
| `granularity` | `VARCHAR(32)` | 否 | `'DAILY'` | 数据粒度，取值 `DAILY` / `MONTHLY` / `QUARTERLY` / `YEARLY`；同一期间只允许一种粒度占位，避免日行与月行被重复求和 |
| `dept_id` | `BIGINT` | 否 | `0` | 门店/科室 ID，`0` 表示全院汇总行；逻辑外键 `FK*` → `m01_dept.id` |
| `dept_code` | `VARCHAR(32)` | 是 | `NULL` | 门店编码快照，取值当时 `m01_dept.dept_code`；冗余用于报表导出不依赖主数据实时关联 |
| `dept_name_snap` | `VARCHAR(100)` | 是 | `NULL` | 门店名称快照，门店改名后历史报表仍显示当时的名称 |
| `biz_dim` | `VARCHAR(64)` | 否 | `''` | 业务维度串，格式 `seller_id=0;channel=ALL`；空串表示无下钻维度；**不能为 NULL**，因为 PostgreSQL 的 UNIQUE 约束把 NULL 视为互不相等 |
| `seller_id` | `BIGINT` | 是 | `NULL` | 销售员 ID（验光师或配镜顾问），为空表示未按销售员拆分；逻辑外键 `FK*` → `m01_staff.id` |

**设计说明：**

1. **`granularity` 进唯一键是刻意的。** 视光经营看板会同时展示「今日」与「本月累计」，如果日行和月行共用一个 `(period, dept_id, biz_dim)`，月汇总行就会覆盖当日行或被当日行覆盖。把粒度纳入唯一键后，日、月、季、年四套数据可以共存，查询时按 `granularity` 过滤即可，避免「先 SUM 出日行再除天数」这种容易出错的做法。

2. **`dept_id` 默认 `0` 表示全院汇总行。** 这里不用 NULL，理由和 `biz_dim` 相同：NULL 在 UNIQUE 约束里互不相等，会让全院汇总行可以无限重复插入。用 `0` 作为「不针对特定门店」的哨兵值，`m01_dept` 的 IDENTITY 从 1 开始，`0` 永远不会与真实门店冲突。

3. **`data_version` 进唯一键支撑「口径变更不重算历史」。** 当 `OPT_SALES_AMOUNT` 的口径从 V1 升级到 V2（比如明确排除员工内购），新口径的数据以 `data_version='V2'` 写入，与 V1 数据并存。看板默认读最新 ACTIVE 版本，历史报表仍按冻结时的版本渲染，两不相扰。这是共享规范 §0.3 铁律 5 在存储层的落地。

4. **`avg_order_amount_snap` 存快照而不是由总额除笔数。** M16-04 的客单价在计算时会对退单做摊薄处理（退货订单计入分母但不计入分子），如果 M22 用 `total_amount_snap / order_count_snap` 重算，得到的数会比 M16 报表上的小，财务对账时会被追问「同一家店为什么两个客单价」。既然 M16 已经算好，就原样搬运。

### 4.3 表：`m22_optical_optometry_fact`（验光量事实表）

**用途：** 存放按「统计期间 + 门店 + 验光师 + 验光类型」切片的验光服务量指标，是 P03 验光量与配镜转化页面的分母来源，也是 P07 门店与验光师业绩的分子来源。主数据源为 M04-07 `GET /internal/v1/m04/log/statistics/daily`（门诊工作量日统计，P95 ≤ 100ms），补充源为 M10 验光业务对外统计接口 `GET /api/v1/m10/optometry/statistics/summary`。

**为什么验光量不走 M10 而走 M04-07：** 验光在院里是「门诊诊疗活动」的一种，M10-01 验光与视功能检查是业务执行方，其统计接口（`/api/v1/m10/optometry/statistics/summary`）面向前台管理，口径里含「已开单未执行」「已退费」等中间态。而 M04-07 的日统计口径是「实际发生的诊疗工作量」，与手术量、门诊量同源，横向比较时不会出现「验光 380 人次占门诊 800 人次的 47%」这种乍看合理实则重复计数的现象。因此本文档以 M04-07 为主源，M10 统计仅用于交叉校验，两者差异超过 5% 时在 P03 页面显示「口径待核」角标并记录到 `m22_optical_sync_log`。

**设计说明：**

1. **`exam_count` 与 `exam_order_count` 是两个不同口径，都在本表落地。** 验光人次（`exam_count`）用于衡量服务工作量，一个患者当天既验光又复查会算两次；验光单数（`exam_order_count`）用于配镜转化率的分母，同一张验光单产生多个镜片规格仍然只算一单。把两者都存下来，页面才能同时展示「今日验光 380 人次 / 312 单」，并让转化率的分母口径唯一确定。

2. **`cross_check_count` 与 `cross_check_diff_rate` 是口径治理的抓手。** 共享规范 §1.2 提到「院周会三个数字对不上」的痛点，其根因就是同一含义指标有多个来源。M22 不消灭这个现状（消灭不了，各模块统计口径都有业务理由），但可以把它显性化：把两个来源的数都落库、算出差值，超阈值就报警。这比事后猜哪个数对要省事得多。

3. **`avg_duration_minutes` 用 `NUMERIC(9,2)` 而不是整数分钟。** 单次验光 18 分 30 秒是常态，取整会让 300 人次的门店日均时长偏差累积到 20 分钟以上，排班测算就会失真。两位小数的精度足够，也符合共享规范「比率 6 位、数量 2 位」的取值习惯。

4. **`optometrist_name_snap` 冗余姓名而不是只存 `optometrist_id`。** 验光师离职后 `m01_staff` 会被置为停用而非删除，但姓名可能因更正而变更。历史业绩报表需要「当时是谁做的」，冗余快照是唯一能保证的手段；M22 全模块不建物理外键也正是为了允许这种冗余。

### 4.4 表：`m22_optical_conversion_fact`（验光配镜转化事实表）

**用途：** 存放配镜转化率的分子、分母与派生比率，是 P03 验光量与配镜转化页面的核心数据表，也是 P01 看板「今日转化率」卡片的直接来源。本表的分子分母各自独立落库、比率由应用层按口径计算后写入，保证任何一次展示都能追溯到分子分母的原始值。

**口径必须写进表结构的三个理由：** 配镜转化率是本子模块最容易被质疑的指标——同一家店，运营部算出来 62%，院长算出来 48%，差异来自三件事：分母是「验光人次」还是「验光单数」、分子是否扣减退单、退单发生在窗口内还是窗口外。这三件事若不在表结构里固化，每次口径争议都要重写一次 SQL。因此本表把这三个维度都做成显式字段：`denominator_type` 记录分母口径，`numerator_count` 与 `return_reduced_count` 分开存（分子 = `numerator_count - return_reduced_count`），`is_final` 标记该行是否已被后续冲正覆盖。

**设计说明：**

1. **`denominator_type` 进唯一键是这张表最关键的设计。** 运营部按月看转化率时习惯用「验光单数」（一单多镜片不重复计），而院长看「验光人次」是因为那反映投入的人力。两种口径都合法，但绝不能在同一行里混着算。把口径做成维度后，同一期间同一门店可以有两行，页面通过切换器选择，历史留痕完整，任何一次口径争议都能回溯到「当时用的是哪个 denominator_type」。

2. **`numerator_final` 用 `GENERATED ALWAYS AS ... STORED` 生成列而非普通列。** 分子 = 原始分子 − 退单减项，这个减法必须永远成立。如果做成普通列由应用层赋值，一旦某处代码只更新了 `numerator_count` 而忘了同步 `numerator_final`，转化率就会和分子分母对不上，而这种错误在报表里极难发现。生成列把这条不变量下沉到数据库，应用层只能写原料值。

3. **`is_final` + `freeze_date` 是「历史报表不重算」的落地机制。** 视光配镜订单的退单风险期通常在交付后 30 天内。日行在窗口内可以反复重采更新（`is_final = FALSE`）；一旦跨过冻结日（默认 T+30，见附录 D 的 `optical.conversion.freeze_days`），该行置 `is_final = TRUE` 并写 `freeze_date`，此后任何退单都不再触碰这一行，而是由冲正任务在当期写一条 `is_final = TRUE` 的负向调整记录。这样「8 月的转化率」在 9 月、12 月看到的永远是一个数，而「全年的转化率」把冲正行算进去后仍是准确的。

4. **`conversion_rate_display` 存展示串看起来反范式，但很有用。** 报表导出（P08）与订阅推送（走 M22-03）都需要把 NULL 渲染成「—」而不是空白。如果每个出口各写一遍渲染逻辑，迟早有一处漏掉显示成 `null`。把展示串在写入时一起算好，导出和推送直接取用，是典型的「用一点点冗余换一致性」。

5. **`attach_rate` 的分子只统计「镜架 + 镜片同时成交」的订单。** 只买镜架或只换镜片的订单不算连带，这是行业内对连带率的通行定义。表里只存比率不存明细，因为明细需要订单行级数据，而 M22 不做行级存储（订单行在 M16-04，M22 只在需要时按下钻接口取）。

### 4.5 表：`m22_optical_product_fact`（视光产品结构事实表）

**用途：** 存放按「统计期间 + 门店 + 产品品类 + 折射率 + 光度区间」切片的销量、销售额与毛利指标，支撑 P04 产品结构与毛利页面。本表的维度取自 M01-08 视光产品主数据（`mdm_optical_product` 的品类、折射率、膜层、折射率档位），度量值取自 M16-04 销售明细快照。

**为什么按折射率与光度区间切而不是按 SKU 切：** 视光产品 SKU 数量极多——一个品牌的镜片按折射率（1.50/1.56/1.60/1.67/1.74）× 球镜（−20.00~+12.00，每 0.25 一档）× 柱镜（0~−6.00，每 0.25 一档）组合，单单一个系列就能产生上万 SKU。按 SKU 存事实会造成三个问题：表体积膨胀到千万行、M01-08 每新增一个 SKU 就要回填历史、且「哪个折射率卖得好」这个问题回答不了。按折射率与光度区间切是视光行业的通行分析粒度：经营者关心的是「高折射率镜片的占比是否在提升」「高度近视人群是否被引导到 1.67 以上」，而不是「某个镜片代码卖了几片」。需要 SKU 级明细时，从 P04 下钻到 M16-04 的销售明细接口取，M22 不存。

**设计说明：**

1. **`cost_amount_snap` 必须来自上游，这是 M22 最容易犯的错。** 「镜架进货价 × 1 = 成本」听起来天经地义，但实际成本至少有五种：标准成本（M01-08 主数据维护）、移动加权（M15-01 出库时结转）、最近采购价、批次实际成本、以及财务口径的期间加权成本。M22 若自选一种算，毛利数字必然与财务报表对不上，而且没人说得清差在哪。所以本字段只接受快照，来源顺序为「M16-04 销售明细带出的 `cost_source` → M15-01 出库成本接口」，Service 层按此优先级回填，两个源都取不到时 `source_status` 置 `PARTIAL` 并把毛利率置 NULL，宁可不显示也不给错数。

2. **光度区间用枚举标识而不是原始度数。** 存 `sphere_range = 'HIGH'` 与存 `sphere_degree = -8.25` 是两种思路。后者精确但维度爆炸（40 档球镜 × 24 档柱镜 × 5 档折射率组合过万），且业务问题从来不是「−8.25 度卖了多少片」而是「高度近视人群占比多少」。因此本表存区间标识，区间边界写在约束与附录 D 的参数里（`optical.product.sphere_boundaries`），业务确认边界调整后，历史数据仍按当时的区间标识保留，不重算——这与共享规范「口径变更不重算历史」一致。

3. **`gross_profit_amount` 有 CHECK 强制等于销售额减成本。** 毛利额是完全可推导的量，之所以还要单独存一列，是因为它是 P04 页面排序、Top N 排名、导出报表的主排序键，每次查询都现算会带来额外的算术开销（尤其是分区表上百万行聚合）。用 CHECK 约束把这个派生列钉死，既享受预计算的好处，又不会出现「毛利额和销售额减成本对不上」这种报表级事故。

4. **`sales_amount_share` 在写入时算好而不是查询时算。** 产品结构占比是 P04 的核心可视化（饼图、堆叠柱）。若每次查询都做窗口函数求占比，跨多个分区时性能会退化到 P95 超过 500ms 的红线。写入时一次性算好占比，代价是同一期间的数据必须整批重采（不能只补一个品类），这个约束由 Service 层保证：任何重采都以「期间 + 门店」为最小重算单元，整体覆盖。

### 4.6 表：`m22_optical_turnover_fact`（视光库存周转事实表）

**用途：** 存放按「期间 + 仓库」切片的视光库存周转指标，支撑 P05 视光库存周转页面。库存数量与金额来自 M15-01 `GET /internal/v1/m15/stock/statistics/daily`，销售成本来自 M16-04 快照。本表不存库存明细，只存计算周转率所需的四项原料与两项结果。

**为什么 M22 不建库存表：** 视光门店是「库房 + 展示柜 + 加工区」的三级库存结构，M15-01 已经把这套台账做得很细（批次、货位、效期、调拨、盘点）。M22 若复制一份库存表，第一会与 M15 的实时库存产生时间差（M15 每笔出入库都会更新，M22 只能在采集时刻取一次），第二会在盘点差异时产生两个真相。因此 M22 只存**每日快照值**：`closing_qty`、`closing_amount`，用于事后算日均加权平均库存。谁问「现在库里还有多少副镜架」去 M15 查，谁问「上个月周转了多少次」来 M22 查，职责清晰。

**周转率与周转天数的口径（写死在表注释与字段说明里）：**

- 库存周转率 = 销售成本 ÷ 平均库存，单位「次/期」，无量纲。
- 库存周转天数 = 期间天数 ÷ 库存周转率；季度按 90 天算，月度按 30 天算，年度按 360 天算。
- 平均库存采用**日均加权平均**，即 Σ(每日期末库存金额) ÷ 期间自然日数，而非「（期初 + 期末）÷ 2」。
- 销售成本一律取 M16-04 或 M15-01 的快照，M22 绝不用「销售额 × (1 − 毛利率)」反推。

**设计说明：**

1. **为什么平均库存选日均加权而不是期初期末算术平均。** 眼镜零售的季节性极强：寒暑假是学生配镜高峰（7—8 月、1—2 月），门店在高峰前一个月集中备货，期末库存会显著高于期间平均水平；开学后又快速消化。若用「（期初 + 期末）÷ 2」，一个 3 月备货、4 月出货的门店会算出偏高的平均库存，周转率被人为压低，与它实际的经营效率不符。日均加权平均把每天的库存水平都纳入，能真实反映「平均占用了多少资金」，这也是库存管理领域的主流口径。代价是需要逐日取数（M15-01 的日统计接口正好提供），`daily_snapshot_count` 记录实际取到几天，缺日过多时页面会提示「平均库存基于 N/M 天快照，仅供参考」。

2. **`turnover_days` 存在表里而不是查询时算，是为了冻结口径。** 季度周转天数的分母是 90 天，年度是 360 天，这个「期间天数」在不同页面可能被误用为「实际日历天数」（比如 2026 年 Q1 是 90 天，但 Q1 实际有 90 天；2026 年全年是 365 天却按 360 天算）。把 `period_days` 和 `turnover_days` 一起落库，等于把「当时用的分母」永久记录，任何争议都能查到。

3. **`avg_method` 字段保留了期初期末算术平均的选项。** 这不是为了给两种口径都留后门，而是为了让口径切换可以灰度验证：新口径上线后，可以同时算两种方式的周转率，对比一个季度确认新口径方向正确后再下线旧口径。历史数据带 `avg_method` 标识，看板默认只取 `DAILY_WEIGHTED`，需要对比时才把两边都拉出来。

4. **`slow_moving_qty` 与 `slow_moving_amount` 让周转分析从「数字」变成「可行动」。** 单看「某店周转天数 180 天」管理者无从下手。把呆滞库存（M15-01 定义为超过 180 天无出库）单独拎出来，管理者立刻知道「这 180 天里有一半是五年前的老款镜架压着」，处置动作（打折清仓、调拨、退货）就明确了。这两个字段是 P05 页面「周转差归因」的下钻入口。

### 4.7 表：`m22_optical_repurchase_fact`（视光会员复购事实表）

**用途：** 存放按「期间 + 门店」切片的顾客复购指标，支撑 P06 会员与复购分析页面。复购是本子模块口径争议最多的指标，本表通过「顾客识别键上卷 + 多卡合并 + 退货冲减隔离」三重设计把口径钉死。

**顾客为什么以 `patient_id` 为主键而不是 `member_id`：** 视光消费有两类顾客来源。第一类是在本院就诊过、有 `patient_id` 的患者，他们可能办卡也可能不办卡；第二类是只来配镜、从没挂过号的纯顾客，M10-05 会给他们建 `m10_customer` 档案但 `patient_id` 为空。如果复购只按 `member_id` 统计，那么「没办卡的回头客」全部被排除，复购率会被系统性低估——一家店如果办卡率只有 40%，按会员卡算出来的复购率大约是真实值的一半，管理者会误判「顾客忠诚度很差」并做出错误的营销投入决策。因此本表的顾客识别以 `patient_id` 为主：有 `patient_id` 的一律按 `patient_id` 归并；没有 `patient_id` 的，退而用 `m10_customer.customer_no` 作为替代键；`member_id` 只作为附加属性参与「多卡一号合并」与会员权益分析，不作为主识别键。

**多卡一号合并规则：** 同一 `patient_id` 办了多张会员卡（A、B 两张），两次消费分别刷 A 卡和 B 卡——按 `patient_id` 归并后仍视为**同一个顾客**，两次消费合并计入该顾客的消费次数。`member_card_count` 字段记录该顾客在窗口内的持卡张数，`distinct_member_card_used` 记录实际用了几张卡，二者不等时说明存在多卡，看板会在「数据说明」里提示。

**复购与退货的口径：** 复购的定义是「同一顾客在统计窗口内发生 ≥2 次有效消费」。其中「有效消费」= 窗口内创建的配镜订单或验光服务单，**退单从有效消费中扣除**；窗口结束后的退单不回溯修改本表已冻结的行，而是在下一期写冲正行（`is_reversal = TRUE`）。这样 8 月的复购率在 12 月看仍是 8 月冻结时的值，而全年累计复购率会把冲正算进去。

**算例（同一患者在 2026 年 10 月窗口内的 3 次消费）：**

设顾客张先生 `patient_id = 10086`，窗口 2026-10-01 至 2026-10-31：

| 序号 | 消费日期 | 消费类型 | 使用会员卡 | 金额(元) | 是否退单 | 计入有效消费 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 2026-10-03 | 验光 | 卡 A | 80.00 | 否 | 是 |
| 2 | 2026-10-03 | 配镜 | 卡 A | 2,680.00 | 否 | 是 |
| 3 | 2026-10-18 | 配镜 | 未使用卡 | 1,250.00 | 否 | 是 |

按 `patient_id` 归并：3 次消费全部归属 `patient_id = 10086`，有效消费 3 次，≥2，因此该顾客在 10 月**计为 1 个复购顾客**，复购次数 = 3 − 1 = **2 次**（首单之后的每一次都算一次复购）。

若改用 `member_id` 作为识别键：第 1、2 次能归并（都刷卡 A），第 3 次没有卡，会被当成「另一个没有会员身份的顾客」，其 1 次消费不构成复购。结果本节门店的复购顾客数会少 1 人，而复购率的分母（消费顾客数）也会少 1 人，复购率出现偏差。

若其中第 3 次消费在 2026-11-05 发生退单：窗口内退单，`return_reduced_count` = 1，有效消费降为 2 次，仍 ≥2，该顾客**仍计为 1 个复购顾客**，但复购次数降为 1；若第 1、2 次中的一次也退单，有效消费降为 1 次，该顾客**不再计为复购顾客**，`repurchase_customer_count` 减 1。

**设计说明：**

1. **`identity_key_type` 进唯一键，让三种识别口径可以并存对照。** 只保留一种口径最省事，但业务上确实需要对照：院长可能会问「如果只按会员卡算复购率是多少」，这需要 `MEMBER_ID` 口径的数据同时存在。三种口径各占一行，页面默认展示 `PATIENT_ID`，其余作为口径对照藏在「口径说明」抽屉里。这样既不打乱主口径，又能随时回答「换一种口径会怎样」。

2. **`repurchase_count` 有 CHECK 强制等于 `total_consume_count - customer_count`。** 复购次数的业务含义就是「首次消费之外又消费了几次」，这个恒等式是定义级的事实，不是可选的算法。用约束钉死之后，任何试图「按订单金额加权计算复购次数」的改动都会直接在写入时失败，逼着改动者显式提出新口径并升版本号。

3. **`avg_repurchase_interval_days` 是流失预警的量化基础。** 只知道「平均复购周期 168 天」还不够，它真正的作用是给流失预警设阈值：超过 2 倍复购周期未再消费即标记为流失风险。`churn_risk_count` 直接把这个人数落库，P06 页面上的「流失预警 47 人」不是临时算出来的，而是可追溯、可下钻到名单的确定值。

4. **`is_reversal` + `reversal_of_period` 实现「历史报表不重算」的第二种形态。** 4.4 节的转化率表用 `is_final` 冻结原行；复购表除了冻结原行，还额外支持写冲正行。两者并存的原因不同：转化率的冲正可以直接改当期分子，而复购率的冲正会影响「顾客消费次数」，进而影响「是否构成复购」这个二元判断，必须用独立冲正行才能表达「某个顾客从复购变成非复购」这种非线性变化。看板在计算全年累计时必须把冲正行与原行一起求和。

### 4.8 表：`m22_optical_perf_fact`（门店与验光师业绩事实表）

**用途：** 存放按「期间 + 门店 + 员工」切片的验光师业绩与门店经营业绩指标，支撑 P07 门店与验光师业绩页面。工作量数据来自 M07-07 `GET /internal/v1/m07/workload/by-doctor`，金额数据来自 M16-04 快照，加工工单数据来自 M10-07 `GET /internal/v1/m10/lab/jobs/{lab_job_no}` 的统计封装接口。

**为什么验光师业绩要单独成表而不并入销售事实表：** 销售事实表的天然维度是「订单归谁」，而验光师业绩的天然维度是「服务由谁提供」。两者并不重合——一副眼镜的验光可能由验光师甲完成、开单由配镜顾问乙完成、加工由加工师丙完成。如果把这些塞进同一张表的 `seller_id` 维度，就会出现「验光师甲的配镜额包含乙开单的部分」这种口径混乱。因此本表用 `staff_role` 区分角色（验光师 / 配镜顾问 / 加工师），每个角色只填属于自己的度量列，其余留空。

**设计说明：**

1. **`staff_role` 与度量列的条件 CHECK 是防止跨角色串数的关键。** 加工师的 `lab_job_count` 如果被错误写到验光师行上，页面就会出现「验光师甲一人做了 320 个加工工单」的荒谬数字。约束层直接禁止这种赋值，应用层想犯错会被数据库拒绝。这也是无物理外键体系下，用 CHECK 承担一部分数据完整性职责的典型做法。

2. **`sample_sufficient` 与 `min_sample_size` 成对出现，落实共享规范 §6.4 的要求。** 「样本不足」和「本月无业务」必须是两种不同的提示：前者说明该员工在岗但业务量太小，排名无意义；后者说明该员工本月没上班或门店停业。如果只用一个 `rank_no IS NULL` 表达，页面只能显示「—」，管理者无法区分是哪种情况。用两个字段把语义分开，前端才能给出准确提示。

3. **`workload_score` 原样搬运不在 M22 重算。** 绩效评分涉及大量院内规则（工作量权重、质量扣分、职称系数、夜班补贴折算），每一次规则调整都会带来历史数据重算的争议。M07-07 的 `for-performance` 接口是这套规则的唯一权威实现，M22 只是它的显示器。若 M22 自己算一遍，绩效发放时一旦与 M07 不一致，就会变成一场「谁算的对」的漫长争论。

4. **`fit_rate`（个人推荐转化率）与 4.4 节门店转化率是两个不同指标，不要混淆。** 门店转化率的分母是验光单数（因为一单可多人），个人转化率的分母是该验光师的验光人次（因为一人只归一个验光师）。两者数值天然不同，页面必须标注清楚，否则会出现「门店 62% 但每个验光师都只有 30%」的困惑——这在只有部分订单关联验光师时才成立，本表的 `recommend_fit_count` 只统计明确关联了验光师的订单，页面上会同时给出「关联率」，提醒读者转化率的分母覆盖度。

### 4.9 表：`m22_optical_export_task`（视光报表导出任务表）

**用途：** 记录 P08 视光报表导出页发起的每一次异步导出任务。本表是**业务主表**，需要完整的 `id` / `created_at` / `updated_at` / `is_deleted` 四件套与 `version` 字段。

**为什么不复用 M22-03 的 `m22_report_export_task`：** M22-03 定义的导出任务表服务于「运营报表与日报月报」的通用导出，其行数巨大（月报、日报批量导出），且它的报表定义来自 `m22_report_template`。视光导出有自己的特点：第一，导出参数包含视光专有维度（折射率、光度区间、验光师）；第二，导出必须携带数据口径版本号与 `source_status`，因为经营分析报表常用于院周会决策，数据不完整时如果还导出一个漂亮整齐的 Excel，就是最危险的错误；第三，视光导出需要记录水印信息以满足敏感经营数据管控。因此 M22-05 保留自己的导出任务表，但 **`template_code` 仍然引用 M22-03 的 `m22_report_template`**，不重复定义模板结构——导出模板的内容仍由 M22-03 统一维护。

**字段设计：**

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | `BIGINT` | 否 | `GENERATED BY DEFAULT AS IDENTITY` | 主键 |
| `export_no` | `VARCHAR(32)` | 否 | 无 | 导出任务单号，格式 `EX` + `YYYYMMDD` + `-` + 4 位序号，如 `EX20261031-0001` |

**设计说明：**

1. **`template_code` 覆盖 M22-03 的模板而不重建。** 这是共享规范反复强调的红线。本子模块引入了视光专有的筛选项（折射率、光度区间、验光师角色），但这些是**模板的 `column_def` 与 `filter_def` 内容**，由 M22-03 的 `m22_report_template` 统一存储。M22-05 只在导出任务表里记录「用了哪个模板 + 本次的 `filter_json`」，模板本身改动只需改一处，不会有「同一份视光日报在两个页面导出格式不一样」的问题。

2. **`include_source_status` 可以关闭但需 `admin` 权限，这是刻意设的坎。** 视光经营分析的数据依赖 M16、M15、M04、M07 四个上游，任何一家取数失败都会让报表「数字变少但看起来正常」。默认必须标注数据完整度；管理者确实需要一份不含标注的对外材料时，必须显式关闭且系统会写审计日志（附录 E 中有对应记录）。这比一律强制标注更现实，也比一律不做更安全。

3. **`retry_count` + `error_code` 支撑重试与自动恢复。** 视光报表导出涉及大区间数据（比如年度全部门店的产品结构），单次执行可能 30~90 秒，遇到上游超时是常态。任务失败后可重试，`retry_count` 上限 3 次（附录 D `optical.export.max_retry`），超限后置 `FAILED` 并需要人工介入，避免无限重试把队列堵死。

4. **`watermark_text` 冗余而非导出时实时拼接。** 若导出时实时拼水印，那么导出人为空（比如系统定时导出）时会丢失信息，且同一文件被第二次下载时水印会变化，造成审计追溯困难。把水印在创建时就确定并落库，MB 级文件生成一次后即使多次下载也是同一份内容（`file_md5` 可校验），这是审计场景的正确处理方式。

### 4.10 表：`m22_optical_sync_log`（视光指标同步日志表）

**用途：** 记录每一次向 M16-04 / M15-01 / M04-07 / M07-07 / M01-08 / M10 取数同步的完整过程：请求参数、响应摘要、耗时、落库行数、失败原因与重试轨迹。本表是**只增不改的流水表**，按共享规范 §2.2 的流水表约定，不设 `updated_at` / `updated_by` / `is_deleted` / `version`，并对应用账号执行 `REVOKE UPDATE, DELETE` 与触发器阻断。

**为什么流水日志必须不可篡改：** 视光经营数据进入院周会的决策链条，一旦某期指标被质疑，第一个要回答的问题是「这个数是从哪里来的、什么时候取的、上游当时返回了什么」。如果日志可以被修改，这条证据链就断了：有人把失败的同步日志改成成功，事后完全无法发现。因此本表在数据库层禁止更新与删除，落库即定稿，唯一允许的后续动作是插入一条新日志描述重试过程。

**设计说明：**

1. **分区键用 `operated_at` 而不是 `period`，这是流水表与事实表的关键差别。** 事实表按业务期间分区是因为查询永远带期间条件（「看 10 月的销售额」）；而同步日志的查询模式是「最近一小时失败了哪些」「昨天补采了小批数据吗」，按操作时间分区才能命中裁剪。若沿用 `period` 分区，补采一年前数据的日志会落进旧分区，运维查「最近失败」反而要扫全部历史分区。

2. **`response_summary` 只存摘要不存全量响应体，这是容量设计的必然选择。** 一次视光销售月统计的响应可能有上百 KB，一天同步 8 次、一年 2,920 次，全量存下来日志表会膨胀到数 GB 且几乎无人查询明细。只存「返回行数、合计金额、状态码」这些能判断对错的摘要，需要看原始响应时用 `trace_id` 去找上游日志系统，两级分工，各司其职。

3. **`REVOKE UPDATE, DELETE` 与触发器双保险的做法与 M17 凭证表一致。** 只 REVOKE 不够——超级用户（DBA）仍有权限，且应用如果有其他账号也会绕过。加触发器后连 DBA 误操作也会被拦。触发器抛出 `ERRCODE = '2205013'`，这个错误码同时登记在详细设计第 8 章，形成「数据库层拦截 → 错误码 → 前端提示」的闭环。

4. **`row_expected` 是漏数检测的锚点。** 光有 `row_affected` 无法判断「这天只同步到 3 家店」是正常的（只有 3 家店营业）还是异常的（本该 5 家店但 2 家取数失败）。`row_expected` 由 Service 层按「期间天数 × 当日营业门店数」估算，实际行数显著少于预期时 `sync_status` 置 `PARTIAL`，触发 11.1 节的补采流程。这个字段是数据完整性从「事后发现报表缺了一块」变成「实时告警」的关键。

5. **`metric_codes` 用 JSONB 数组而非拆行存储。** 一次同步往往覆盖多个指标（销售额、订单数、客单价在同一响应里），若拆成多行日志，一次同步会写 5~8 行，日志表体积翻几倍且查询时要 GROUP BY 才能拼回一次请求。用 JSONB 数组一行记录一次请求，既省空间又符合「一次请求一条日志」的自然语义。需要按指标检索时用 GIN 索引（在附录 C 中已登记为可选索引，因查询频率不高默认不建）。

### 4.12 Pydantic Schema 定义

本子模块的 Pydantic V2 Schema 分为四组：**查询入参**、**事实行出参**、**下钻明细出参**、**任务与日志出参**。全部 Schema 统一继承 `M22BaseSchema`，开启 `str_strip_whitespace`，并通过 `ConfigDict(from_attributes=True)` 支持 `model_validate(orm_obj)`。

**关于数值类型的 Schema 声明约定：**

| 语义 | Python 类型 | 说明 |
| --- | --- | --- |
| 金额 | `Decimal` | 序列化为字符串，保留两位小数，禁止 `float` |
| 指标值 | `Decimal` | 序列化为字符串，保留六位小数 |
| 比率 | `Decimal` | 序列化为字符串，保留六位小数 |

from datetime import date
from decimal import Decimal

from pydantic import Field, field_validator, model_validator

class PeriodQuerySchema(M22BaseSchema):
    """按期间查询的公共入参（GET 查询串）。"""

    period_start: str = Field(
        ..., description="期间起，YYYY-MM 或 YYYY-MM-DD", examples=["2026-07"])
    period_end: str = Field(
        ..., description="期间止，YYYY-MM 或 YYYY-MM-DD", examples=["2026-09"])
    granularity: GranularitySchema = Field(
        GranularitySchema.MONTHLY, description="统计粒度")
    dept_ids: list[int] | None = Field(
        None, description="门店/科室 ID 列表，空表示按数据权限范围")
    metric_codes: list[str] | None = Field(
        None, description="指标编码列表，空表示该页面全部指标")

    @field_validator("period_start", "period_end")
    @classmethod
    def _check_period_format(cls, v: str) -> str:
        """期间必须是 YYYY-MM 或 YYYY-MM-DD，禁止 2026-1 这类写法。"""
        if len(v) == 7:
            year, month = v.split("-")
            if not (year.isdigit() and month.isdigit() and 1 <= int(month) <= 12):
                raise ValueError("期间格式非法，应为 YYYY-MM")
        elif len(v) == 10:
            date.fromisoformat(v)
        else:
            raise ValueError("期间格式非法，应为 YYYY-MM 或 YYYY-MM-DD")
        return v

    @field_validator("metric_codes")
    @classmethod
    def _check_metric_code(cls, v: list[str] | None) -> list[str] | None:
        """指标编码必须符合 {域}_{主题}_{指标名} 全大写格式。"""
        if not v:
            return v
        import re

        pattern = re.compile(METRIC_CODE_PATTERN)
        bad = [c for c in v if not pattern.match(c)]
        if bad:
            raise ValueError(f"指标编码格式非法：{','.join(bad)}")
        return v

    @model_validator(mode="after")
    def _check_range(self) -> PeriodQuerySchema:
        """期间起不能晚于期间止，跨度不得超过 36 个月。"""
        if self.period_start > self.period_end:
            raise ValueError("period_start 不能晚于 period_end")
        start_year, start_month = int(self.period_start[:4]), int(self.period_start[5:7])
        end_year, end_month = int(self.period_end[:4]), int(self.period_end[5:7])
        months = (end_year - start_year) * 12 + (end_month - start_month) + 1
        if months > 36:
            raise ValueError("期间跨度不得超过 36 个月")
        return self

#### 4.12.5 错误响应与校验约定

统一响应体的 `code` 非 0 时，`data` 为 `null`，`message` 为面向用户的中文短语，`trace_id` 用于排查。校验失败（Pydantic 抛出 `ValidationError`）由全局异常处理器统一转换为 `code=2205007`（期间参数非法）或对应业务码，不向前端暴露 Python 堆栈。

```python
# app/schemas/m22/optical/response.py
"""M22-05 统一响应封装。"""
from __future__ import annotations

from typing import Generic, TypeVar

from pydantic import BaseModel, Field

T = TypeVar("T")


class ApiResponse(BaseModel, Generic[T]):
    """统一响应体，与共享规范 §2.2 一致。"""

    code: int = Field(0, description="0 表示成功，非 0 为错误码数值形式")
    message: str = Field("success", description="提示信息")
    data: T | None = Field(None, description="业务数据，失败时为 null")
    trace_id: str = Field(..., description="链路追踪 ID")


class ErrorDetail(BaseModel):
    """错误详情，仅在 code 非 0 时出现在日志中，不返回前端。"""

    error_code: str = Field(..., description="7 位错误码字符串，如 2205001")
    field: str | None = Field(None, description="出错字段")
    upstream_module: str | None = Field(None, description="失败的上游模块")
    upstream_api: str | None = Field(None, description="失败的上游接口")
    retryable: bool = Field(False, description="是否可重试")


class PageMeta(BaseModel):
    """分页元信息，与共享规范 §2.3 一致。"""

    total: int = Field(0, description="总条数")
    page: int = Field(1, description="当前页")
    page_size: int = Field(20, description="每页条数")
    pages: int = Field(0, description="总页数")
```

**校验失败与错误码映射：**

| 触发条件 | 抛出层 | 返回错误码 | 前端提示 |
| --- | --- | --- | --- |
| 期间格式不是 `YYYY-MM`/`YYYY-MM-DD` | Pydantic | `"2205007"` | 请选择正确的统计期间 |
| 期间跨度 > 36 个月 | Pydantic | `"2205008"` | 统计跨度不得超过 36 个月 |
| 粒度与期间不匹配（如年度粒度传月度期间） | Service | `"2205009"` | 统计粒度与期间不匹配 |
| 分母为 0 | Service | `"2205010"` | 该期间无有效样本，比率不参与计算 |
| 导出任务状态不允许当前操作 | Service | `"2205015"` | 当前任务状态不可执行该操作 |
| 幂等键重复但参数不同 | Service | `"2205025"` | 相同的幂等键已用于不同参数 |
| 乐观锁版本冲突 | Service | `"2205026"` | 数据已被他人修改，请刷新后重试 |

## 附录 C：关键查询与索引使用说明

**C.1 看板汇总查询（P01 首屏，目标 P95 ≤ 500ms）**

```sql
-- 视光销售额与订单数，按门店汇总
SELECT dept_id,
       SUM(total_amount_snap) AS total_amount_snap,
       SUM(order_count)       AS order_count,
       SUM(return_count)      AS return_count
  FROM m22_optical_sales_fact
 WHERE metric_code = 'OPT_SALES_AMOUNT'
   AND granularity = 'MONTHLY'
   AND period BETWEEN '2026-07' AND '2026-09'
   AND data_version = 2
   AND is_deleted = FALSE
 GROUP BY dept_id;
```

> 命中索引 `idx_m22_optical_sales_fact_period (period, dept_id)`，配合分区裁剪只扫 3 个分区。**不允许**把 `metric_code` 条件省掉，否则会把全部指标行一起扫出来再靠 `SUM` 过滤，行数放大 6 倍。

**C.2 配镜转化率查询（P03，分母为 0 返回 NULL）**

```sql
-- 注意：分母为 0 时返回 NULL，绝不使用 COALESCE(..., 0)
SELECT period,
       dept_id,
       denominator_count,
       numerator_final,
       CASE WHEN denominator_count > 0
            THEN ROUND(numerator_final::numeric / denominator_count, 6)
            ELSE NULL
       END AS conversion_rate
  FROM m22_optical_conversion_fact
 WHERE denominator_type = 'EXAM_ORDER'
   AND granularity = 'MONTHLY'
   AND period BETWEEN '2026-07' AND '2026-09'
   AND is_deleted = FALSE
 ORDER BY period, dept_id;
```

**C.3 库存周转查询（P05）**

```sql
-- 周转率与周转天数，两者都必须允许 NULL
SELECT period,
       dept_id,
       period_days,
       avg_inventory_amount,
       cogs_amount_snap,
       CASE WHEN avg_inventory_amount > 0
            THEN ROUND(cogs_amount_snap / NULLIF(avg_inventory_amount, 0), 6)
            ELSE NULL
       END AS turnover_rate,
       CASE WHEN avg_inventory_amount > 0 AND cogs_amount_snap > 0
            THEN ROUND(period_days * avg_inventory_amount / cogs_amount_snap, 2)
            ELSE NULL
       END AS turnover_days
  FROM m22_optical_turnover_fact
 WHERE avg_method = 'DAILY_WEIGHTED'
   AND period BETWEEN '2026-07' AND '2026-09'
   AND is_deleted = FALSE;
```

> `turnover_days` 用 `period_days × 平均库存 ÷ 销售成本` 直接展开计算，与「`period_days ÷ 周转率`」数学等价但避免了二次除法带来的舍入误差累积。

**C.4 复购率查询（P06）**

```sql
-- 注意：只统计 source_status = 'COMPLETE' 的期间作为分母来源
SELECT period,
       dept_id,
       identity_key_type,
       customer_count,
       repurchase_customer_count,
       total_consume_count,
       repurchase_count,
       CASE WHEN customer_count > 0
            THEN ROUND(repurchase_customer_count::numeric / customer_count, 6)
            ELSE NULL
       END AS repurchase_rate
  FROM m22_optical_repurchase_fact
 WHERE identity_key_type = 'PATIENT_ID'
   AND identity_merge_rule = 'MULTI_CARD_MERGED'
   AND period BETWEEN '2026-01' AND '2026-09'
   AND is_deleted = FALSE;
```

**C.5 业绩排名查询（P07，样本不足返回 NULL 排名）**

```sql
SELECT staff_id,
       staff_name,
       staff_role,
       optometry_count,
       fit_amount_snap,
       CASE WHEN sample_sufficient
            THEN RANK() OVER (PARTITION BY dept_id
                              ORDER BY fit_amount_snap DESC)
            ELSE NULL
       END AS rank_no,
       sample_sufficient
  FROM m22_optical_perf_fact
 WHERE staff_role = 'OPTOMETRIST'
   AND period = '2026-09'
   AND granularity = 'MONTHLY'

```

> **分区子表必须用原生 SQL 创建，不能用 `op.create_table`：** Alembic 的 `create_table` 不支持 `PARTITION OF ... FOR VALUES` 语法，使用后会在 `m22_0009` 升级时静默漏建分区子表，导致新月份数据写入直接失败。

"""M22-05 视光经营分析 9 张表

Revision ID: m22_0008
Revises: m22_0007
Create Date: 2026-10-20
"""
from alembic import op

revision = "m22_0008"
down_revision = "m22_0007"
branch_labels = None
depends_on = None

_PARTITIONED = [
    ("m22_optical_sales_fact", "period", ["202601", "202612"]),
    ("m22_optical_optometry_fact", "period", ["202610", "202612"]),
    ("m22_optical_conversion_fact", "period", ["202610", "202612"]),
    ("m22_optical_product_fact", "period", ["202610", "202612"]),
    ("m22_optical_turnover_fact", "period", ["202610", "202612"]),
    ("m22_optical_repurchase_fact", "period", ["202610", "202612"]),
    ("m22_optical_perf_fact", "period", ["202610", "202612"]),
    ("m22_optical_sync_log", "operated_at", ["202610", "202612"]),
]


def _month_bounds(yyyymm: str) -> tuple[str, str]:
    """返回分区的 [起, 止) 月份字符串，如 ('2026-10', '2026-11')。"""
    year, month = int(yyyymm[:4]), int(yyyymm[4:6])
    end_year, end_month = (year + 1, 1) if month == 12 else (year, month + 1)
    return f"{year:04d}-{month:02d}", f"{end_year:04d}-{end_month:02d}"


def upgrade() -> None:
    """建表、建分区、建索引、建触发器、收紧权限。

    DDL 正文见第 4 章各表小节，本脚本只负责编排顺序与分区子表创建。
    """
    bind = op.get_bind()
    for table, _key, (first, last) in _PARTITIONED:
        year, month = int(first[:4]), int(first[4:6])
        stop_year, stop_month = int(last[:4]), int(last[4:6])
        while (year, month) <= (stop_year, stop_month):
            yyyymm = f"{year:04d}{month:02d}"
            start, end = _month_bounds(yyyymm)
            key_type = "date" if table == "m22_optical_sync_log" else "text"
            if key_type == "date":
                clause = (f"FOR VALUES FROM ('{start}-01') "
                          f"TO ('{end}-01')")
            else:
                clause = f"FOR VALUES FROM ('{start}') TO ('{end}')"
            bind.exec_driver_sql(
                f"CREATE TABLE IF NOT EXISTS {table}_p{yyyymm} "
                f"PARTITION OF {table} {clause}")
            year, month = (year + 1, 1) if month == 12 else (year, month + 1)
        bind.exec_driver_sql(
            f"CREATE TABLE IF NOT EXISTS {table}_pdefault "
            f"PARTITION OF {table} DEFAULT")
    bind.exec_driver_sql(
        "REVOKE UPDATE, DELETE ON m22_optical_sync_log FROM app_user")


def downgrade() -> None:
    """按建表逆序删除，分区子表随父表级联删除。"""
    for table, _key, _range in reversed(_PARTITIONED):
        op.execute(f"DROP TABLE IF EXISTS {table} CASCADE")
    op.execute("DROP TABLE IF EXISTS m22_optical_export_task CASCADE")
