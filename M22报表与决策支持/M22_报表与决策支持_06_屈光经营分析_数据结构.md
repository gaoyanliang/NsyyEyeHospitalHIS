## 文档说明

本文件是 M22-06 屈光经营分析的**数据结构唯一依据**，包含详细设计文档第 4 章的全部内容。

**定位一句话：** M22-06 是屈光业务的**跨期、跨维度、跨模块汇总层**——它自己不产生任何一个业务数字，只把 M11-08 的漏斗、M11-07 的质量四性、M16 的金额快照**搬过来、对齐期间、拉成时间序列、做横向比较、并在明确的数学前提外推未来**。因此它的数据结构和 M22-01 指标中心一样，「存的东西比算的东西少」，但比 M22-01 多两类真正的「本子模块自产数据」：**渠道投放台账**（全系统唯一来源，M11-08 反过来向它取数）与**预测结果**（带方法与置信区间，绝不允许与实测值混存）。

**五条与数据结构强相关的铁律（违反即返工）：**

| # | 铁律 | 在数据结构上的体现 |
|---|---|---|
| 1 | M22 不算钱、不造业务数 | 本子模块**没有任何一张表存业务事实的原始值**。`m22_refractive_metric` 存的是「从上游取回来的快照值」，六个溯源字段强制填写；`amount_snap` 类字段一律 `_snap` 后缀，且 `source_module` 必须为 `M16` 或 `M11` |
| 2 | 屈光金额的唯一来源是 M16，不由 M22 计算 | `m22_refractive_channel` 只有一张 `m22_refractive_ad_spend` 存「花出去的钱」（投放台账，本子模块自产），**没有任何一张表存「收进来的钱」**；收入一律 `_snap` 直传 |
| 3 | 预测值必须与实测值物理可分 | `m22_refractive_metric.value_type` 为独立列（`ACTUAL` / `FORECAST`），并由 CHECK 约束强制：`value_type = 'FORECAST'` 的行必须有 `forecast_method` 与 `confidence_interval`；两种值分属不同唯一索引，互不覆盖 |
| 4 | 分母为 0 或上游不可用时，存 NULL 不存 0 | `ck_m22_refractive_metric_zero_denom`：`denominator IS NULL OR denominator > 0 OR metric_value IS NULL`；`ck_m22_refractive_metric_status_value`：非 `COMPLETE` 状态的值必须为 NULL 或打 `is_estimated` |
| 5 | 投放台账只有 `APPROVED` 的才计入 P-02 与 ROI | `ck_m22_refractive_ad_spend_approve`：`audit_status <> 'APPROVED'` 时 `approved_by`/`approved_at` 必须为空；P-02 查询强制 `audit_status = 'APPROVED' AND is_deleted = FALSE` |

**数值铁律（与共享规范 §2.4 一致）：** 指标值一律 `NUMERIC(20,6)`，比率一律 `NUMERIC(9,6)`，金额一律 `NUMERIC(18,2)`，数量 `BIGINT`，**全文不得出现 `FLOAT` / `DOUBLE` / `REAL`**。

## 1. 表清单

> ### 声明一：本子模块建表边界（必读）
>
> **本子模块自建 9 张表**，全部使用 `m22_refractive` 前缀（共享规范 §12 分配的 M22-06 专属前缀）。
>
> **不重复建表（引用 M22-03 权威定义）：**
>
> | 骨架表 | 定义方 | 本子模块用法 |
> |---|---|---|
> | `m22_report_template` | M22-03 | 屈光报表模板（P08）通过 `template_code` 引用，取值形如 `RPT_REF_MONTHLY_OPS`，不新建 |
> | `m22_report_instance` | M22-03 | 屈光报表实例如 `RI20261101-0023` 由 M22-03 生成，本子模块只读取 `report_no` |
> | `m22_report_row` | M22-03 | 报表行数据落 M22-03 的分区表，本子模块不落新表 |
> | `m22_report_subscription` | M22-03 | 报表订阅统一走 M22-03，本子模块不重复实现推送 |
>
> **不重复建表（引用 M22-01 / M22-02）：**
>
> | 表 | 定义方 | 本子模块用法 |
> |---|---|---|
> | `m22_metric_def` | M22-01 | 本子模块全部 `REF_*` 指标编码在 M22-01 注册口径，这里只存 `metric_code` 与 `metric_version` 快照 |
> | `m22_metric_target` | M22-01 | 屈光目标值（如年度手术量 2,400 例）由 M22-01 维护，本子模块 P01 只读 |
> | `m22_fact_metric` | M22-02 | 通用指标事实；本子模块**不落通用事实表**，因为屈光主题有大量「维度组合 + 预测 + 漏斗停滞点」等通用事实表装不下的结构 |
>
> **为什么屈光主题要单独建表而不是塞进 `m22_fact_metric`：**
>
> | 理由 | 说明 |
> |---|---|
> | 结构不同 | 漏斗需要 7 个环节 + 6 个环节转化率 + 停滞环节，是一行 7 列的宽结构，通用事实表只有单值 + 单分母 |
> | 预测需要附加字段 | 通用事实表没有 `value_type` / `forecast_method` / `confidence_interval`，塞进去就要给全模块加字段 |
> | P-02 需要独立台账 | `m22_refractive_ad_spend` 是**本子模块唯一自产的业务数据**，有审批流，不属于「指标事实」 |
> | 医师维度需要横表 | 医师行同时承载手术量、转化率、并发症率、满意度四类指标，纵表要 4 行再透视，查询代价高 |
>
> 关于第 4 条，本子模块的 `m22_refractive_doctor` 确实做了适度反范式：把「医师 × 期间」的十余个指标横铺成一行。这是**报表层的事实表**，不是业务主表，反范式的代价（新增指标要加列）由版本化迁移承担，收益是 P04 页面的单次查询从 4 次往返降到 1 次。

**表清单：**

| 序号 | 表名 | 中文名 | 用途 | 预估行数 |
|---|---|---|---|---|
| 4.2 | `m22_refractive_metric` | 屈光主题指标快照表 | 按「指标 × 期间 × 维度」存屈光主题指标值，含实测与预测两类 | 约 219,000 行 |
| 4.3 | `m22_refractive_funnel` | 屈光转化漏斗快照表 | 七环节漏斗快照，含环节量、环节转化率、整体转化率、最大流失环节 | 约 10,950 行 |
| 4.4 | `m22_refractive_procedure` | 术式结构与价格带表 | 「期间 × 术式 × 价格带」的例数与金额快照 | 约 87,600 行 |
| 4.5 | `m22_refractive_doctor` | 医师业绩表 | 「医师 × 期间」的手术量、转化率、质量、满意度横表 | 约 4,380 行 |
| 4.6 | `m22_refractive_ad_spend` | 渠道投放台账表 | **本子模块自产**的渠道投放费用台账，含审批流，P-02 的数据源 | 约 2,190 行 |
| 4.7 | `m22_refractive_channel` | 渠道经营效果表 | 「期间 × 渠道」的咨询量、手术量、收入快照、ROI、CPA | 约 10,950 行 |
| 4.8 | `m22_refractive_quality` | 术后质量与经济性表 | 「期间 × 术式/医师」的质量四性与经济性交叉快照 | 约 2,190 行 |
| 4.9 | `m22_refractive_trend` | 屈光趋势与预测表 | 时间序列聚合 + 预测值 + 置信区间 + 异常归因 | 约 8,760 行 |
| 4.10 | `m22_refractive_log` | 操作与采集日志表 | 只增不改的采集/导出/审批日志，按月 RANGE 分区 | 约 146,000 行 |

**合计：9 张表**

> **表前缀说明：** 9 张表全部以 `m22_refractive` 开头，符合共享规范 §12 与《M22 数据结构设计汇总》§1.2 的分配。第 4.6 节 `m22_refractive_ad_spend` 虽然业务上是「台账」，但前缀仍归本子模块，因为投放台账是屈光业务的专有概念，视光（M22-05）与临床（M22-07）都不共享。

**为什么是 9 张而不是 6 张：**

| 表 | 不合并的理由 |
|---|---|
| `m22_refractive_metric` 与 `m22_refractive_funnel` | 漏斗是 7 环节宽结构且带「停滞环节」这种非数值字段；塞进指标表要么把 7 个环节变成 7 行（查询要做 7 次自连接），要么把 `metric_value` 换成 JSONB（失去数值约束） |
| `m22_refractive_metric` 与 `m22_refractive_doctor` | 医师行是十余列的横表，与纵表指标表并存的收益是 P04 单查询完成；合并后 P04 要扫 4 倍行数再做透视 |
| `m22_refractive_ad_spend` 与 `m22_refractive_channel` | 台账有审批流、有草稿态、有驳回，是「业务单据」；渠道效果是「计算结果」，一行对应一个「期间 × 渠道」，由台账 + M11-08 快照派生。合并会让 P-02 的查询命中一个混合表，SLA 难保证 |
| `m22_refractive_trend` 与 `m22_refractive_metric` | 趋势表同时承载「多粒度聚合（日/周/月/季）」与「预测」，预测要求 `value_type` 分离与 `forecast_method` 强制；指标表按 `metric_code` 组织的唯一索引不适合多粒度 |
| `m22_refractive_quality` 与 `m22_refractive_metric` | 质量四性来自 M11-07（五个固定指标编码），但质量与经济性要**并列展示**（如「SMILE 并发症率 1.20% + 客单价 15,932.66」），单独成表让 P06 一次查询取齐 |

**表间关系总览（基数）：**

| 主表 | 从表 | 关系 | 关联键 |
|---|---|---|---|
| `m22_refractive_metric` | `m22_refractive_trend` | 1 : N | `(metric_code, period, dimension_type, dimension_value)` 派生 |
| `m22_refractive_funnel` | `m22_refractive_trend` | 1 : N | `funnel_overall_cvr` 落趋势表做时间序列 |
| `m22_refractive_procedure` | `m22_refractive_quality` | N : 1 | `(period, refractive_type)` |
| `m22_refractive_doctor` | `m22_refractive_quality` | N : 1 | `(period, doctor_id)` |
| `m22_refractive_ad_spend` | `m22_refractive_channel` | 1 : 1（按月渠道聚合） | `(channel, period)` 聚合到一行 |
| `m22_refractive_channel` | `m22_refractive_trend` | 1 : N | 渠道 ROI 落趋势表 |
| `m22_refractive_metric` | `m22_refractive_log` | 1 : N | 采集与导出写入日志 |

> **逻辑外键约定：** 全部表**不建物理外键**（共享规范 §2.6）。`metric_code` 逻辑引用 M22-01 `m22_metric_def.metric_code`；`dept_id` 逻辑引用 M01-01 科室；`doctor_id` 逻辑引用 M01-02 职工；`template_code` / `report_no` 逻辑引用 M22-03 骨架表。引用完整性由 Service 层与定时一致性巡检保证，巡检失败写 `m22_refractive_log` 并发布 `m22.collect.failed`。

> `FK*` 表示逻辑外键，**数据库层不建 `FOREIGN KEY`**，由 Service 层校验 + 每日一致性巡检兜底。原因见《M22 数据结构设计汇总》§2.5：物理外键在按期间分区的表上会导致跨分区约束开销，且上游模块（M11、M16）的数据修正在夜间批量执行，物理外键会把 M22 的采集任务拖成分布式事务。

| 表 | 是否分区 | 分区键 | 说明 |
|---|---|---|---|
| `m22_refractive_metric` | 是 | `period`（月） | 按业务期间分区，不按采集时间；补采三月数据不必扫 12 个分区。必须有 `_pdefault` |
| `m22_refractive_funnel` | 是 | `period`（月） | 同上 |
| `m22_refractive_procedure` | 否 | — | 年约 87,600 行，索引可覆盖 |

### 4.2 表：`m22_refractive_metric`（屈光主题指标快照表）

**用途：** 按「指标 × 期间 × 维度 × 值类型」存屈光主题指标值。它是 P01 看板、P03 术式结构、P05 渠道指标、P06 质量指标的**统一取数入口**。

本表只存**快照**，不存原始事实：每个 `metric_value` 都由 Service 层调上游接口取回后写入，六个溯源字段（`source_module` / `source_api` / `collect_batch_no` / `source_status` + `metric_code` / `period`）强制非空，确保任何一个数字都能回答「从哪来、哪次采的、当时上游是否正常」。

**为什么必须把实测值与预测值放在同一张表而不是两张：**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 两张表（实测表 + 预测表） | 物理隔离彻底 | P07 趋势图要 `UNION ALL` 两表；任何按序列查询都要写两遍 SQL；口径变更要改两处 | 否决 |
| 单表 + 文字标注「预测」 | 简单 | 无法约束；前端靠字符串判断；导出时容易把预测当真值 | 否决 |
| **单表 + `value_type` 独立列 + CHECK 强制附加字段** | 查询统一；约束由数据库保证；导出时 `WHERE value_type = 'ACTUAL'` 即可排除预测 | 需多占 3 个字段 | **采用** |

**为什么 `dimension_value` 在无维度时存空字符串而不存 NULL：** 唯一索引 `uk_m22_refractive_metric_key` 含 `dimension_value`。PostgreSQL 的唯一约束把 `NULL` 视为互不相等，若允许 NULL，「全院汇总」这一维度组合可以插入任意多条，唯一约束形同虚设。这与《M22 数据结构设计汇总》§2.4 对 `biz_dim` 的约定一致。

#### 约束说明

```sql
-- 值类型只允许实测与预测两种
ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_value_type
    CHECK (value_type IN ('ACTUAL', 'FORECAST'));

-- 【铁律三】预测行必须有方法与置信区间，且上下界必须包住点值
ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_forecast_fields
    CHECK (value_type <> 'FORECAST'
        OR (forecast_method IS NOT NULL
            AND confidence_interval IS NOT NULL
            AND forecast_horizon IS NOT NULL
            AND forecast_base_period IS NOT NULL));

ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_forecast_ci
    CHECK (ci_lower IS NULL OR ci_upper IS NULL
        OR (ci_lower <= ci_upper
            AND (metric_value IS NULL
                 OR (metric_value >= ci_lower AND metric_value <= ci_upper))));

-- 实测行不得带预测方法，防止两条路径都写造成混淆
ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_actual_no_forecast
    CHECK (value_type <> 'ACTUAL'
        OR (forecast_method IS NULL AND confidence_interval IS NULL));

-- 【铁律四】分母为 0 时值必须为 NULL
ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_zero_denom
    CHECK (denominator IS NULL OR denominator > 0 OR metric_value IS NULL);

-- 【铁律四】非 COMPLETE 状态的值必须为 NULL 或打估算标记
ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_status_value
    CHECK (source_status = 'COMPLETE'
        OR metric_value IS NULL
        OR is_estimated = TRUE);

-- 估算标记为真必须有原因
ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_estimate_reason
    CHECK (is_estimated = FALSE OR estimate_reason IS NOT NULL);

ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_source_status
    CHECK (source_status IN ('COMPLETE', 'PARTIAL', 'FAILED', 'STALE'));

ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_dim_type
    CHECK (dimension_type IN ('HOSPITAL', 'DEPT', 'REFRACTIVE_TYPE',
                              'DOCTOR', 'CHANNEL', 'PRICE_BAND'));

-- 全院维度的维度值必须是空串，不与其他维度混淆
ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_hospital_dim
    CHECK (dimension_type <> 'HOSPITAL' OR dimension_value = '');

-- 覆盖率必须在 (0, 1] 闭区间内
ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_coverage
    CHECK (coverage_rate IS NULL OR (coverage_rate >= 0 AND coverage_rate <= 1.000000));

-- 达成率允许超过 1（超额完成），但不允许为负
ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_achieve
    CHECK (achieve_rate IS NULL OR achieve_rate >= 0);

ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_period_format
    CHECK (period ~ '^[0-9]{4}-[0-9]{2}$');

ALTER TABLE m22_refractive_metric
    ADD CONSTRAINT ck_m22_refractive_metric_period_range
    CHECK (period_start <= period_end);
```

#### 设计说明

| # | 决策 | 理由 |
|---|---|---|
| 1 | `value_type` 独立成列而非写在 `remark` 里 | 校验脚本与导出模块都按列过滤；写在备注里等于没有约束，历史上「导出把预测当实测汇报」的事故都源于此 |
| 2 | 唯一索引含 `value_type` | 同一指标同一期间同一维度，实测一条、预测一条，两条都要能共存；若唯一索引不含 `value_type`，先写实测后写预测会撞键 |
| 3 | `denominator` / `numerator` 冗余存储 | 比率指标重算与审计需要分子分母；只存结果值的话，上游改了分母口径就无从复盘 |
| 4 | 保留 `metric_domain` 字段恒为 `'REF'` | M22-02 的通用事实表有同名字段，保留便于跨表 `UNION ALL` 做全院主题汇总报表，不必在 UNION 里硬编码常量 |
| 5 | `calculated_at` 与 `collected_at` 分开 | 上游可能用昨晚的批次算今天的数据（`calculated_at` 是昨天），本模块今天采集（`collected_at` 是今天）；只存一个时间就无法判断数据新鲜度 |
| 6 | `is_final` 单独标记 | 月内每天采集都在更新当月值，月末封账后 `is_final = TRUE`；报表生成时必须等 `is_final`，否则月报数字会随日期漂移 |
| 7 | 分区键用 `period` 不用 `collected_at` | 补采三月数据可能发生在五月，按采集时间分区会导致查三月要扫全部分区 |

---
### 4.3 表：`m22_refractive_funnel`（屈光转化漏斗快照表）

**用途：** 存「咨询 → 到院 → 术前检查 → 出方案 → 预约 → 手术 → 完成」七环节的漏斗快照，一行对应「一个期间 × 一个维度组合」的完整漏斗。

**为什么不直接用 M11-08 的 `m11_stat_funnel`：**

| 理由 | 说明 |
|---|---|
| 数据库边界 | M11 与 M22 是不同 schema、不同实例边界，M22 不得跨模块直查业务表（共享规范 §0.3 铁律二） |
| 需要在 M22 侧可追溯 | 报表生成后如果 M11 重算了历史期间，M22 的历史报表不能跟着变；必须在 M22 侧留快照并注明 `collect_batch_no` |
| 需要与 M22 其他主题对齐 | P02 漏斗图右侧要叠加「同期投放费用」（来自 4.6 台账）与「同期收入」（来自 M16 快照），三者必须落在同一行同一期间 |
| 需要记录「停滞环节」判断结果 | `lost_stage` 是 M11-08 给出的判定，M22 侧要存下来，否则 P02 只能重新实时调一次 M11 |

**七个环节与六个环节转化率一一对应：**

| 环节码 | 环节名 | 环节量字段 | 上游来源指标编码（M11-08 附录 A） |
|---|---|---|---|
| `CONSULT` | 咨询量 | `consult_count` | `RA01001` |
| `ARRIVE` | 到院量 | `arrive_count` | `RA01003` |
| `EXAM` | 术前检查量 | `exam_count` | 漏斗阶段二分母 |
| `PLAN` | 出方案量 | `plan_count` | 漏斗阶段三分母 |
| `BOOK` | 预约量 | `book_count` | 漏斗阶段四分母 |
| `SURFACE` | 手术量 | `surface_count` | `RA03001` |
| `DONE` | 完成量 | `done_count` | 漏斗阶段六分母 |

```sql
COMMENT ON COLUMN m22_refractive_funnel.lost_amount_snap IS '流失环节的潜在金额快照 = 流失量 × 当期客单价快照，客单价来源 M16，本模块不计算金额';
```

#### 设计说明

| # | 决策 | 理由 |
|---|---|---|
| 1 | 六环节转化率落成 6 个独立列而非 1 个 JSONB | 报表要按单个环节排序（「哪个环节跌得最狠」），JSONB 无法走索引排序；6 列虽多但类型受 CHECK 约束保护 |
| 2 | `ck_m22_refractive_funnel_monotonic` 由数据库强制 | 漏斗单调性是最容易出错的地方：M11 侧的「咨询去重口径」与「到院去重口径」若不一致，会出现「到院 836 > 咨询 800」。数据库直接拒绝比报表层事后解释更省成本 |
| 3 | `lost_count` 与 `lost_stage` 成对非空 | 用 `(lost_stage IS NULL) = (lost_count IS NULL)` 一条约束保证，避免「有流失环节没流失量」的空壳行 |
| 4 | `benchmark_cvr` / `health_lower` / `health_upper` 存快照 | 健康区间来自 M11-08 附录 B.2，但基准会随年度目标调整而变；M22 存快照后，历史报表的「是否低于基准」结论不随基准调整而漂移 |
| 5 | `sample_condition` 存有效样本条件文本 | P02 页面必须在漏斗旁展示「哪些咨询被排除」，这是口径可解释性的最低要求；文本存表比写在代码常量里更容易与报表一起归档 |
| 6 | `cvr` 允许等于 1 | 「全部咨询到院」在个别渠道（如仅电话预约的复诊渠道）是真实现象，不应报错；只拦 > 1 |

### 4.4 表：`m22_refractive_procedure`（术式结构与价格带表）

**用途：** 存「期间 × 术式 × 价格带」的手术例数、金额快照、占比与集中度，支撑 P03 页面的术式结构柱状图、价格带分布与 CR2 集中度。

**为什么术式与价格带必须交叉存储而不是两张表：**

| 方案 | 问题 |
|---|---|
| 术式表 + 价格带表分开 | P03 的「SMILE 在 PB4（20,000~25,000）的占比」这种交叉透视要两表 JOIN 后重算，且两表的期间口径可能不一致 |
| 交叉表（采用） | 一行 = 期间 × 术式 × 价格带；任意切片都是 `WHERE` 过滤，合计由 `GROUPING SETS` 一次算出 |
| 只存交叉不存合计 | 需要合计时 `SUM` 会重复计入明细，故本表额外存 `aggregate_level` 区分「明细」与「小计」两层 |

**价格带边界（与 M11-08 附录 B.3 一字不差，左闭右开）：**

| 价格带码 | 下界（含） | 上界（不含） | 说明 |
|---|---|---|---|
| `PB1` | 0.00 | 10,000.00 | 低价格带 |
| `PB2` | 10,000.00 | 15,000.00 | 次低价格带 |
| `PB3` | 15,000.00 | 20,000.00 | 中价格带 |
| `PB4` | 20,000.00 | 25,000.00 | 中高价格带 |
| `PB5` | 25,000.00 | 30,000.00 | 高价格带 |
| `PB6` | 30,000.00 | 无上界 | 超高价格带 |
| `PB_UNKNOWN` | — | — | 金额缺失无法归桶 |
| `ALL` | — | — | 不区分价格带的汇总行 |

| # | 决策 | 理由 |
|---|---|---|
| 1 | 三层聚合同表（`BAND` / `TYPE` / `TOTAL`） | 报表层若要合计必须 `GROUPING SETS` 实时算，而 `cr2` 这种「需要先排序再取前两名」的指标无法用简单聚合表达；落表后 P03 单查询取齐 |

| 3 | `amount_collect_batch_no` 与 `collect_batch_no` 分开 | 例数来自 M11-08，金额来自 M16-04，两次采集批次不同；合并成一个批次号会让「金额是昨天采的、例数是今天采的」这种情况无法追溯 |
| 4 | `revenue_share_ref` 与 `revenue_share` 都存 | M11-08 已算出 `RA06005` 术式收入占比参考。本模块自己按 `revenue_snap` 重算一个 `revenue_share` 做交叉核对，两者偏差 > 0.01 说明 M16 快照或 M11 口径有一方变了，需要人工介入 |
| 5 | `band_lower_snap` / `band_upper_snap` 存快照 | 价格带边界会随年度调价调整（如 PB4 从 20,000 调到 22,000）；存快照后历史报表的价格带归属可复盘 |
| 6 | `ck_m22_refractive_procedure_eye_ge_case` | 「眼数 ≥ 例数」是硬逻辑；这条约束能拦住「把眼数误填成例数」这类最常见的录入错误 |

### 4.5 表：`m22_refractive_doctor`（医师业绩表）

**用途：** 存「医师 × 期间」的横表，把 M11-08 医师类十个指标（`RA04001`~`RA04010`）与 M11-07 医师维度质量指标（`EI_UCVA` 等）铺成一行，供 P04 医师业绩榜、医师对比雷达图使用。

**为什么这张表要反范式横铺：**

| 方案 | P04 页面查询代价 | 新增指标代价 |
|---|---|---|
| 纵表（指标 × 医师 × 期间一行） | 12 医师 × 14 指标 = 168 行，再 `PIVOT` 成 12 行 × 14 列 | 0（加行即可） |
| **横表（采用）** | 1 次索引扫描取 12 行 | 加列 + 迁移 + 报文版本升级 |
| 混合（核心指标横铺 + 长尾纵表） | 复杂，两套代码 | 复杂 |

P04 的典型请求是「2026-10 全院医师业绩榜，按手术量降序，展示 14 个指标」，横表把这变成一次 `ORDER BY`。代价是新增指标要改表结构，而医师业绩指标是**受 M11-08 指标体系控制**的（M11-08 附录 A.4 固定 10 个 + M11-07 质量指标），本模块预测其变化频率为「每年一次评审会调整」，可以接受版本化迁移。

### 4.6 表：`m22_refractive_ad_spend`（渠道投放台账表）

**用途：** **本子模块唯一自产的业务数据表**。记录各渠道（`DOUYIN` / `XIAOHONGSHU` / `MEITUAN` / `ONLINE_AD` 等）在各期间实际发生的投放费用，带完整的「草稿 → 提交 → 审批 → 生效」流程。

这张表是内部契约 **P-02 `GET /internal/v1/m22/ad-spend`** 的数据源。M11-08 每天 03:10 调用它取渠道投放成本快照，用于计算渠道 ROI 与 CPA。若本表为空或未审批，M11-08 侧 `cost_snap = NULL`，ROI 与 CPA 无法计算。

**「没投钱」与「查不到」必须可区分：**

| 情形 | P-02 应当返回 | M11-08 侧行为 |
|---|---|---|
| 该渠道该期间有已审批台账，金额 0.00（如自然流量渠道 `REFERRAL`） | `spend_snap: 0.00` + `has_spend_record: true` | `cost_snap = 0.00`，ROI 置 NULL（分母 0），明确标注「零投放」 |
| 该渠道该期间无任何台账（未录入） | `spend_snap: 0.00` + `has_spend_record: false` | `cost_snap = NULL`，ROI 置 NULL，标注「未录入投放数据」 |
| 该渠道不存在 / 参数非法 | HTTP 404 + `"2206011"` | 记录失败，`cost_snap = NULL` |
| M22 服务不可用 | HTTP 503 | 降级 `cost_snap = NULL`，下轮重试 |

> **为什么无台账时不返回 404：** 404 表示「这个渠道不存在」，「未录入投放数据」是正常业务状态（新开渠道第一周还没结账）。返回 404 会让 M11-08 的记录里出现大量「接口错误」，掩盖真正的接口故障。

**为什么只在 `APPROVED` 状态计入：** 投放费用涉及预算与业绩考核，草稿与待审批的数据随时可能被驳回或改数。若 P-02 把 `PENDING` 的台账也算进去，M11-08 算出的 ROI 会在审批通过后突然变化，历史报表不可复现。

**为什么必须建索引 `(channel, period, audit_status)`：** P-02 的 SLA 是 P95 ≤ 300ms，且被 M11-08 每日调用 9 个渠道 × 若干期间。若不建索引，每次查询要全表扫描台账（含草稿、驳回、作废），随年月增长逼近 SLA 边界。见附录 C 的实测执行计划。

#### 设计说明

| # | 决策 | 理由 |
|---|---|---|
| 1 | 无台账时 P-02 返回 `spend_snap: 0.00` + `has_spend_record: false`，不返回 404 | 「没投钱」与「查不到接口」是两种完全不同的情况，M11-08 必须能区分才能正确标注降级原因；404 会让 M11 侧记录大量伪故障 |
| 2 | 只有 `APPROVED` 计入（铁律五） | 草稿与待审批数据可能被驳回或改数；计入后 ROI 会在审批通过时跳变，历史报表无法复现 |
| 3 | `is_p2_included` 由触发器维护而非应用层 | 应用层有多处（P05 手工录入、批量导入、API 推送）会写这张表，任何一处漏写都会让 P-02 多算或少算；触发器是唯一可靠位置 |
| 4 | 覆盖索引 `(channel, period, spend_amount) WHERE audit_status = 'APPROVED' AND is_deleted = FALSE` | P-02 只查已审批未删除行，部分索引把候选集从全表缩到实际需要的那部分；`spend_amount` 在索引里使 `SUM` 无需回表 |
| 5 | 已审批不可删除只能作废 | 删除会让 P-02 的历史快照无法解释「为什么上个月有这个数这个月没了」；作废保留痕迹且作废行不计入 P-02 |
| 6 | `channel` 与 `channel_category` 的匹配约束 | 渠道大类用于 P05 的「线上/线下/转介」三分组；若 `DOUYIN` 被误标成 `OFFLINE`，分组汇总会错 |
| 7 | `batch_no` 与 `period` 组合唯一 | 月度结算常分「月初预付 + 月末补差」两次录入，需要允许多批；用批次号保证同批不重复 |

### 4.7 表：`m22_refractive_channel`（渠道经营效果表）

**用途：** 存「期间 × 渠道」的经营效果：咨询量、到院量、手术量、收入快照、投放费用、ROI、CPA、到院成本。它是 P05「渠道与投放 ROI」页面的主表，也是 M11-08 渠道类十个指标（`RA05001`~`RA05010`）在 M22 侧的快照。

**收入与成本的方向必须写清：** 本表有两个方向的金额，语义完全相反，混淆会导致 ROI 计算反向：

| 字段 | 方向 | 来源 | 能否为负 |
|---|---|---|---|
| `revenue_snap` / `revenue_net_snap` | 收进来的钱 | M16-04 `GET /internal/v1/m16/optical/statistics`（屈光口径走 M16-01 `POST /internal/v1/billing/statistics`） | 退费超过收入时净收入可为负，毛收入不为负 |
| `spend_snap` | 花出去的钱 | 本子模块 `m22_refractive_ad_spend` 汇总 | 不为负 |
| `roi` | 收 / 花 | 本模块派生 | 可为负（净收入为负时） |
| `cpa` | 花 / 例 | 本模块派生 | 不为负 |

**ROI 的定义（与 M11-08 侧 `RA05007` 口径一致）：** `roi = ROUND(revenue_net_snap / spend_snap, 6)`。分母 `spend_snap` 为 0.00 或 NULL 时，`roi` 必须为 NULL，**绝不返回 `Infinity` 或 999999**。

#### 设计说明

| # | 决策 | 理由 |
|---|---|---|
| 1 | `roi` 类型用 `NUMERIC(20,6)` 而非 `NUMERIC(9,6)` | ROI 是「倍数」不是「比率」，屈光单月 ROI 可达 33.74（M11-08 示例值），量纲不同故用 20 位精度；`NUMERIC(9,6)` 整数位只有 3 位，会溢出 |
| 2 | `ck_m22_refractive_channel_roi` 强制分母 > 0 | 这是本表最重要的一条约束。ROI 分母为 0 时若存 0，报表显示「ROI 0」会被误读成「白投了钱」；若存极大值，排序榜会被垃圾值霸榜。正确表达只有 NULL |
| 3 | `has_spend_record` 与 `spend_snap` 双字段 | P-02 的降级契约在表内同样需要表达：M11-08 拿到 `cost_snap = NULL` 后要区分「M22 说没投放」与「M22 没数据」，靠这个布尔 |
| 4 | `roi_source` 区分 `M22_CALC` 与 `M11_REF` | 两种来源的 ROI 口径可能有微差（M11 用其内部快照，M22 用本模块台账）。标清来源后，两者不一致时能定位是口径差还是数据错 |
| 5 | `attribution_model` + `attribution_window_days` 落表 | 「首触点 ROI」与「末触点 ROI」结论可能完全相反；不存归因模型的话，同一份报表换个模型看就对不上 |
| 6 | `amount_source_module` 恒为 `M16` | 金额来源不是可选项，用固定值 + CHECK 锁死，杜绝将来有人图省事从 M11 快照里取金额 |
| 7 | ROI 榜索引加 `WHERE roi IS NOT NULL` | 无 ROI 的渠道（如自然流量）不该参与 ROI 榜排序；部分索引同时缩小索引体积 |

### 4.8 表：`m22_refractive_quality`（术后质量与经济性表）

**用途：** 把 M11-07 的质量四性与 M16 的经济性快照**并列存一行**，支撑 P06「术后质量与经济性」的核心问题：**「质量好的术式，是不是也赚钱？」**

**为什么必须与经济性并列：** 这个问题的答案常常是反直觉的——SMILE 的客单价最高但并发症率也最高，ICL 客单价最高但样本量最小。如果质量与收入分两张表，P06 就得做两次查询再由前端拼装，而「按并发症率排序后看对应客单价」这种交叉排序无法在两次查询中完成。

**五个质量指标编码（与 M11-07 一字不差，不得自创）：**

| 指标编码 | 名称 | 单位 | 告警阈值（M11-07） | 方向 |
|---|---|---|---|---|
| `EI_UCVA` | 有效性指数 | 无量纲 | warn 0.90 / alert 0.80 | `HIGHER_BETTER` |
| `SI_BCVA_LOSS` | 安全性指数 | 行 | warn 0.10 / alert 0.20 | `LOWER_BETTER` |
| `ST_REFRACT_CHANGE` | 稳定性 | D | warn 0.25 / alert 0.50 | `LOWER_BETTER` |
| `PR_WITHIN_0_50` | 可预测性 | 比率 | warn 0.80 / alert 0.70 | `HIGHER_BETTER` |
| `COMPLICATION_RATE` | 并发症率 | 比率 | warn 0.03 / alert 0.05 | `LOWER_BETTER` |

```sql
COMMENT ON TABLE m22_refractive_quality IS 'M22-06 术后质量与经济性：M11-07 质量四性 + M16/M17 经济性并列存储，支撑「质量好是否也赚钱」';
COMMENT ON COLUMN m22_refractive_quality.followup_case_count IS '有效随访例数，是有效性/安全性/可预测性的真实分母；为 0 时上述三项必须 NULL';
COMMENT ON COLUMN m22_refractive_quality.indicators_available IS '可用质量指标个数 0~5；< 5 说明部分指标分母为 0，页面对应位置显示「—」';
COMMENT ON COLUMN m22_refractive_quality.quality_revenue_corr IS '质量与收入 Pearson 相关系数；样本期间数 < 6 时必须 NULL，避免用小样本下确定性结论';
COMMENT ON COLUMN m22_refractive_quality.reoperation_cost_snap IS '再手术成本快照，来源 M17-04 科室成本，本模块不计算';
```

#### 设计说明

| # | 决策 | 理由 |
|---|---|---|
| 1 | 质量与经济性同表 | P06 的核心问题是交叉的（「并发症率最低的术式，客单价是多少」），分表后无法在数据库层完成排序，只能拉到内存排 |
| 2 | `followup_case_count` 与 `surgery_case_count` 分开 | 质量四性的真实分母是**有效随访例数**而不是手术例数（随访率通常只有 60~80%）。若用手术例数做分母，随访率低的术式会显得「质量好」——这是最典型的指标欺骗 |
| 3 | `ck_m22_refractive_quality_zero_followup` | 随访例数为 0 时，有效性/安全性/可预测性必须 NULL；`ST_REFRACT_CHANGE` 与 `COMPLICATION_RATE` 可由手术记录直接得到，不受此限 |
| 4 | `corr_sample_periods >= 6` 才允许非空 | 用 2~3 个月数据算相关系数没有统计意义；数据库层直接拦掉，避免 P06 汇报「质量与收入强相关 r = 0.92」这种基于 2 个点的结论 |
| 5 | `alert_indicators` 与 `alert_level` 成对 | 只报「有告警」不报「哪个指标告警」的报表没法用；一个 `WARN` 背后可能是五性中任何一项 |
| 6 | `indicators_available` 单独存 | 前端要知道「该显示几个格子」；靠逐个判空算会让报文逻辑散落在前端，且分组统计时要重复算 |
| 7 | `gross_margin_snap` / `reoperation_cost_snap` 标 `_snap` | 毛利与成本归 M17 核算；M22 只搬运，字段名后缀即契约，任何不带 `_snap` 的金额字段都会被代码评审打回 |

### 4.9 表：`m22_refractive_trend`（屈光趋势与预测表）

**用途：** 存储 P07 屈光趋势与预测页的全部序列点。同一张表同时容纳**实测点**（`value_type = 'ACTUAL'`）与**预测点**（`value_type = 'FORECAST'`），由 `value_type` 物理区分，并强制预测点必须携带 `forecast_method` + `confidence_interval` + `ci_lower` / `ci_upper` + `forecast_base_period`。

> ★ **本表的预测量是本子模块唯二自产的数据之一**（另一个是 `m22_refractive_ad_spend`）。凡 `value_type = 'FORECAST'` 的行，其 `metric_value` 不是从任何上游模块取来的，M22 必须为其正确性负责，因此必须能回答「用什么方法、基于哪几期、置信区间多宽、事后实际偏差多少」这四个问题，分别对应 `forecast_method` / `forecast_base_period` / `confidence_interval` / `mape` 四列。

按 `period` 月 RANGE 分区，并建 `_pdefault` 兜底分区。

**分区与主键：**

| 项 | 取值 | 说明 |
|---|---|---|
| 分区方式 | `PARTITION BY RANGE (period)` | 趋势查询永远带期间范围，天然裁剪 |
| 分区粒度 | 月，`m22_refractive_trend_p202610` 形式 | 每月一个分区 |
| 兜底分区 | `m22_refractive_trend_pdefault` | 超出预建范围的数据落此，不报错 |
| 主键 | `(id, period)` | 主键必须包含分区键 `period` |
| 唯一键 | `(granularity, period, series_date, metric_code, dimension_value, value_type)` | 序列点唯一 |

**约束说明**

```sql
-- 【铁律】预测点必须能自证：方法、基准期、所用期数、置信水平、上下界，缺一不可
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_forecast_fields
  CHECK (
    value_type <> 'FORECAST'
    OR (forecast_method IS NOT NULL
        AND confidence_interval IS NOT NULL
        AND ci_lower IS NOT NULL
        AND ci_upper IS NOT NULL
        AND forecast_base_period IS NOT NULL
        AND forecast_base_periods IS NOT NULL
        AND forecast_horizon IS NOT NULL)
  );

-- 实测点不得携带预测元数据，否则「这一列到底是实测还是预测」永远说不清
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_actual_no_forecast
  CHECK (
    value_type <> 'ACTUAL'
    OR (forecast_method IS NULL
        AND confidence_interval IS NULL
        AND ci_lower IS NULL
        AND ci_upper IS NULL)
  );

-- 置信区间必须包住预测值，且下界不高于上界
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_ci_order
  CHECK (
    value_type <> 'FORECAST'
    OR (ci_lower <= metric_value AND metric_value <= ci_upper AND ci_lower <= ci_upper)
  );

-- 置信水平落在 (0,1)，0.95 而不是 95
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_ci_level
  CHECK (confidence_interval IS NULL OR (confidence_interval > 0 AND confidence_interval < 1));

-- 预测基准期必须早于预测期，禁止用未来预测未来
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_base_before
  CHECK (forecast_base_period IS NULL OR forecast_base_period < period);

-- 预测步长 >= 1，等于 0 说明是「预测已知期」
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_horizon
  CHECK (forecast_horizon IS NULL OR forecast_horizon >= 1);

-- 预测所用实测期数至少 3 期，否则移动平均无法成立
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_base_periods
  CHECK (forecast_base_periods IS NULL OR forecast_base_periods >= 3);

-- 误差三列必须同时存在或同时为空：只回填 mape 不回填 abs_error 无法复核
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_error_triplet
  CHECK (
    (is_error_evaluated = FALSE
     AND mape IS NULL AND abs_error IS NULL AND actual_value IS NULL)
    OR (is_error_evaluated = TRUE
        AND actual_value IS NOT NULL AND abs_error IS NOT NULL)
  );

-- 只有预测点才谈误差；实测点填 mape 无意义
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_eval_only_forecast
  CHECK (is_error_evaluated = FALSE OR value_type = 'FORECAST');

-- 异常点必须写清原因与命中的规则码，否则运维无法处置
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_anomaly_reason
  CHECK (
    anomaly_flag = FALSE
    OR (anomaly_reason IS NOT NULL AND anomaly_rule_code IS NOT NULL)
  );

-- 预测点不参与异常判定：预测本身就是估算，再说它异常毫无意义
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_anomaly_actual
  CHECK (anomaly_flag = FALSE OR value_type = 'ACTUAL');

-- 预测点来源必为本模块，避免「拿别人的数冒充我的预测」
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_forecast_source
  CHECK (value_type <> 'FORECAST' OR (source_module = 'M22' AND collect_batch_no IS NULL));

-- 实测点必须能溯源到上游接口与批次
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_actual_source
  CHECK (
    value_type <> 'ACTUAL'
    OR (source_module <> 'M22' AND source_api IS NOT NULL AND collect_batch_no IS NOT NULL)
  );

-- 上游不可用时值必须为空，绝不静默填 0
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_status_value
  CHECK (
    source_status = 'COMPLETE'
    OR ((metric_value IS NULL) OR value_type = 'FORECAST')
  );

-- 全院维度必须用空串占位，保证唯一约束有效
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_hospital_dim
  CHECK (dimension_type <> 'HOSPITAL' OR dimension_value = '');

-- 变化率只在对比值非 0 时存在
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_change_rate
  CHECK (change_rate IS NULL OR (compare_value IS NOT NULL AND compare_value <> 0));

-- 期间格式与粒度配对
ALTER TABLE m22_refractive_trend ADD CONSTRAINT ck_m22_refractive_trend_period_fmt
  CHECK (
    (granularity = 'DAY' AND period ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}$')
    OR (granularity = 'WEEK' AND period ~ '^[0-9]{4}-W[0-9]{2}$')
    OR (granularity = 'MONTH' AND period ~ '^[0-9]{4}-[0-9]{2}$')
    OR (granularity = 'QUARTER' AND period ~ '^[0-9]{4}-Q[1-4]$')
  );
```

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | 实测与预测**同表不同行**，用 `value_type` 区分 | 若拆成两张表，趋势图要 UNION ALL 且排序时无法保证同一序列的点序一致；同表后 `ORDER BY series_date` 天然连续，且 `ck_m22_refractive_trend_forecast_fields` 能在同一行上强制预测元数据完整性 |
| 2 | `value_type` 必须是**独立列**而非 `remark` 里的文字 | 靠文字说明「这是预测」的报表，一旦导出到 Excel 就丢失语义，业务方会把预测当实际汇报给院长。做成列后可被索引、被 CHECK、被权限过滤、被导出水印统一处理 |
| 3 | 18 条 CHECK 中有 6 条专管预测 | 预测是本模块唯一「自己造数」的地方，也是最容易被滥用的地方；把方法论写死在数据库层，比写在接口文档里可靠 |
| 4 | `ck_m22_refractive_trend_base_before` 限制基准期早于预测期 | 这条约束排除了「用 2026-11 的实测预测 2026-10」这类脏数据；同时保证 `forecast_horizon` 的语义是「往前第 N 期」 |
| 5 | `mape` / `abs_error` / `actual_value` 三列成组 | 单一 `mape` 无法复核（分子分母都丢了）；三列成组后任何人都能重算 `mape`，且 `ck_..._error_triplet` 保证不会只写一半 |
| 6 | 预测点 `source_module` 恒为 `M22` 且 `collect_batch_no` 为 NULL | 这是「自产数据」的数据库级标记；M22-02 采集任务与 M22-03 报表生成都能据此自动区分「搬运的数据」与「本模块算的数据」 |
| 7 | 分区键用 `period` 而非 `created_at` | P07 的查询永远是「某指标 2026-01 到 2026-10 的趋势」，按 `period` 分区可直接裁剪到 10 个分区；按创建时间分区则要扫全表 |
| 8 | `moving_avg_3` 落库而非实时算 | 趋势图上叠加的平滑线需要与导出的 Excel 数值一致；实时算会因数据修订导致报表值与页面值不符 |

### 4.10 表：`m22_refractive_log`（操作与采集日志表）

**用途：** 记录 P01~P08 全部页面与本子模块异步任务的操作留痕，以及每一次上游取数、每一次预测计算、每一次台账审批的完整过程。**只增不改**：本表不允许 `UPDATE`、`DELETE`，不设 `updated_at` / `updated_by` / `is_deleted` / `version`。

> ★ **为什么日志必须独立成表并且不可改**：投放台账 `m22_refractive_ad_spend` 是本子模块唯一的自产业务数据，也是 P-02 的数据源。M11-08 每天 03:10 用 P-02 取数算渠道 ROI，一旦台账被静默改动，M11 侧的 ROI 会与 M22 侧的 ROI 长期不一致，且双方都无法举证谁先改的。日志表承担唯一举证责任，因此必须数据库级阻止改写。

按 `log_time` 月 RANGE 分区，并建 `_pdefault` 兜底分区。

**只增不改的三层保障（与 M22-01 `m22_metric_log` 一致）：**

| 层 | 手段 | 实现位置 | 效果 |
|---|---|---|---|
| 第一层 | Repository 只暴露 `insert` 方法 | `app/models/m22/refractive_log.py` | 应用代码没有改写入口 |
| 第二层 | 触发器拦截 `UPDATE` / `DELETE` | `fn_m22_refractive_log_immutable()` | 绕过 ORM 直接发 SQL 也会失败 |
| 第三层 | 回收数据库权限 | `REVOKE UPDATE, DELETE ON m22_refractive_log FROM app_rw` | 即使触发器被禁用，权限层仍拒绝 |

| # | 决策 | 理由 |
|---|---|---|
| 1 | 只增不改，不设 `updated_at` / `is_deleted` | 审计日志一旦可改就失去举证价值；与 M22-01 `m22_metric_log` 保持同一范式，避免模块内两套日志规则 |
| 2 | 三层保障而非只靠应用层 | 应用层约束可被「直接连库改数据」绕过；触发器拦 SQL、`REVOKE` 拦权限，三处都失守的概率极低 |
| 3 | `before_snapshot` / `after_snapshot` 用 JSONB | 台账审批要留完整的金额与发票号，指标改数要留完整口径；JSONB 避免为每种对象建一张审计表 |
| 4 | `before_value` / `after_value` 用 `NUMERIC(20,6)` 而非 JSONB | 数值类变更（如投放金额 46800.00 → 52800.00）要能被直接聚合与比对，塞进 JSONB 后只能取出再转 |
| 5 | `caller_module` 单独成列 | P-02 被 M11 每天调用，出问题时第一个要回答的是「M11 什么时候取的数、取到了什么」；日志里能直接查到比翻 access log 快得多 |
| 6 | `ck_m22_refractive_log_reason` 列举必须填原因的动作码 | 台账审批、作废、人工改数这三类是被反复追问的动作；在数据库层强制填原因，比事后追责有效 |
| 7 | 按 `log_time` 分区而非按类别 | 日志查询 90% 是「某天出什么事了」，按时间分区裁剪最有效；类别用普通索引解决 |
| 8 | 日志不落患者隐私 | 本子模块粒度到「科室 × 渠道/术式/医师」，不含患者维度；`error_message` 与 `action_desc` 中若出现患者标识由第 9.4 节脱敏规则拦截 |

```python
from sqlalchemy.ext.asyncio import AsyncSession


class RefractiveLogRepository:
    """日志仓库：只暴露 insert，物理上不存在 update / delete 方法。"""

    __slots__ = ("_session",)

    def __init__(self, session: AsyncSession) -> None:
        self._session = session

    async def insert(self, row: RefractiveLog) -> None:
        """写入一条审计日志；不允许修改已有行。"""
        self._session.add(row)
        try:
            await self._session.flush()
        except IntegrityError:
            # 日志号冲突说明同一动作被重放，忽略即可，不影响主流程
            await self._session.rollback()
```

### 4.12 Pydantic Schema 定义

全部 Schema 放在 `app/schemas/m22/`，使用 Pydantic V2 写法（`ConfigDict` + `field_validator` + `model_validator`）。本模块 Schema 分四层：**基类层**（统一响应与分页）、**实体层**（对应五张主表）、**查询层**（各页面入参）、**响应层**（各页面出参，含 `source_status` 与 `value_type`）。

**基类层：**

```python
from __future__ import annotations

from datetime import date, datetime
from decimal import Decimal
from enum import Enum
from typing import Generic, Optional, TypeVar

from pydantic import BaseModel, ConfigDict, Field, field_validator, model_validator

M22BaseModelT = TypeVar("M22BaseModelT", bound=BaseModel)


class M22BaseModel(BaseModel):
    """M22 模块 Schema 基类：统一 ORM 读取、去空格、枚举取值输出。"""

    model_config = ConfigDict(
        from_attributes=True,
        populate_by_name=True,
        str_strip_whitespace=True,
        use_enum_values=True,
        extra="forbid",
    )


class ApiResp(M22BaseModel, Generic[M22BaseModelT]):
    """统一响应：与共享规范 §2.2 一致，code 恒为非负字符串，成功为 "0"。"""

    code: str = Field(default="0", description="业务码，'0' 表示成功")
    message: str = Field(default="success", description="提示信息")
    data: Optional[M22BaseModelT] = Field(default=None, description="业务数据")
    trace_id: str = Field(min_length=16, max_length=32, description="链路追踪 ID")


class PageResp(M22BaseModel, Generic[M22BaseModelT]):
    """分页响应：与共享规范 §2.3 一致，pages 由 total 与 page_size 推导。"""

    items: list[M22BaseModelT] = Field(default_factory=list)
    total: int = Field(ge=0)
    page: int = Field(ge=1, default=1)
    page_size: int = Field(ge=1, le=200, default=20)
    pages: int = Field(ge=0)

    @model_validator(mode="after")
    def check_pages(self) -> "PageResp[M22BaseModelT]":
        """pages 必须等于 ceil(total / page_size)，避免前后端翻页错位。"""
        expect = 0 if self.total == 0 else (self.total + self.page_size - 1) // self.page_size
        if self.pages != expect:
            raise ValueError(f"pages 应为 {expect}，实际 {self.pages}")
        return self


class ValueType(str, Enum):
    """序列点类型：实测或预测。预测值必须与本枚举一同传递，禁止用文字说明替代。"""

    ACTUAL = "ACTUAL"
    FORECAST = "FORECAST"


class SourceStatus(str, Enum):
    """取数状态：上游不可用时绝不落 COMPLETE，也绝不填 0。"""

    COMPLETE = "COMPLETE"
    PARTIAL = "PARTIAL"
    FAILED = "FAILED"
    STALE = "STALE"


class Granularity(str, Enum):
    DAY = "DAY"
    WEEK = "WEEK"
    MONTH = "MONTH"
    QUARTER = "QUARTER"


class PeriodMixin(M22BaseModel):
    """统计期间入参公共校验：period 形如 2026-10，from 不得晚于 to。"""

    period_from: str = Field(pattern=r"^[0-9]{4}-(0[1-9]|1[0-2])$", description="起始期间")
    period_to: str = Field(pattern=r"^[0-9]{4}-(0[1-9]|1[0-2])$", description="截止期间")

    @model_validator(mode="after")
    def check_range(self) -> "PeriodMixin":
        if self.period_from > self.period_to:
            raise ValueError("period_from 不得晚于 period_to")
        if self.period_from < "2020-01":
            raise ValueError("统计期间不得早于 2020-01，系统上线前无数据")
        return self
```

```python
    metric_code: str
    metric_name: str
```

```python
    def check_split(self) -> "TrendResp":

            raise ValueError("forecast_points 中出现非 FORECAST 点")
        return self
```

| 2 | 屈光金额唯一来源 M16 | `m22_refractive_procedure` / `_channel` / `_quality` | `ck_..._amount_source` | 从 M11 取金额会导致重复计负数 |
| 3 | 预测值必须与实测物理可分 | `m22_refractive_metric` / `_trend` | `value_type` 独立列 + 6 条预测专用 CHECK | 预测当实测汇报，经营决策失真 |
| 4 | 分母为 0 / 上游不可用存 NULL | 三张指标表 | `ck_..._zero_denom` / `ck_..._status_value` | 静默填 0 会让「没数据」变成「业绩为零」 |
| 5 | 投放台账只有 APPROVED 计入 P-02 | `m22_refractive_ad_spend` | `is_p2_included` + 触发器 + P-02 覆盖索引 | 未审批金额进入 ROI，M11 与 M22 对不上 |
| 6 | 不直查业务表 | — | 无跨模块外键、无 `FROM m11_*` 语句 | 上游表结构变更即导致 M22 全线崩溃 |

## 附录 C 分区 DDL 与维护脚本

```sql
-- 每月 25 日由 APScheduler 任务预先创建下个月分区，避免落入 _pdefault
CREATE OR REPLACE FUNCTION fn_m22_refractive_create_partitions(p_months_ahead INTEGER DEFAULT 3)
RETURNS INTEGER AS $$
DECLARE
    v_month     DATE;
    v_suffix    TEXT;
    v_next      DATE;
    v_count     INTEGER := 0;
BEGIN
    FOR i IN 0..p_months_ahead - 1 LOOP
        v_month  := date_trunc('month', CURRENT_DATE) + (i || ' month')::interval;
        v_next   := v_month + interval '1 month';
        v_suffix := to_char(v_month, 'YYYYMM');

        EXECUTE format(
            'CREATE TABLE IF NOT EXISTS m22_refractive_metric_p%s PARTITION OF m22_refractive_metric '
            'FOR VALUES FROM (%L) TO (%L)', v_suffix, to_char(v_month, 'YYYY-MM'),
            to_char(v_next, 'YYYY-MM'));
        EXECUTE format(
            'CREATE TABLE IF NOT EXISTS m22_refractive_trend_p%s PARTITION OF m22_refractive_trend '
            'FOR VALUES FROM (%L) TO (%L)', v_suffix, to_char(v_month, 'YYYY-MM'),
            to_char(v_next, 'YYYY-MM'));
        EXECUTE format(
            'CREATE TABLE IF NOT EXISTS m22_refractive_log_p%s PARTITION OF m22_refractive_log '
            'FOR VALUES FROM (%L) TO (%L)', v_suffix, v_month, v_next);

        v_count := v_count + 3;
    END LOOP;
    RETURN v_count;
END;
$$ LANGUAGE plpgsql;

-- 分区命中检查：自建分区有数据而 _pdefault 也有数据，说明预建滞后
SELECT 'metric'  AS tbl, count(*) FROM m22_refractive_metric_pdefault
UNION ALL
SELECT 'trend',   count(*) FROM m22_refractive_trend_pdefault
UNION ALL
SELECT 'log',     count(*) FROM m22_refractive_log_pdefault;
```
