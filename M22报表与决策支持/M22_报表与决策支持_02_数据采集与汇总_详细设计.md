## 文档说明

本文件是 M22-02 数据采集与汇总子模块的详细设计说明书。M22-02 在 M22 模块中的位置是「引擎」：M22-01 指标中心定义「算什么」，M22-02 负责「怎么把数取回来、怎么落库、怎么保证完整性」，M22-03 及之后的报表与看板消费 M22-02 落下的事实数据。

阅读顺序建议：第 1、2 章了解边界（尤其 1.1 与 2.3 反复强调的「M22 不直查业务表」），第 3 章了解数据模型与口径，第 5 章看页面，第 6 章看接口，第 8、10 章看规则与契约。数据结构细节一律不在本文件展开，见配套的数据结构文档。

**三条贯穿全文的铁律**（凡是与这三条冲突的设计一律不成立）：

| 编号 | 铁律 | 具体含义 | 违反后果 |
|---|---|---|---|
| L-01 | 不直查业务表 | 禁止 `SELECT ... FROM m16_xxx` / `m05_xxx` / `m17_xxx` 等任何业务模块的表。所有数据必须通过共享规范 §9 登记的上游统计接口获取 | 表结构变更导致 M22 集体崩溃；口径绕过业务模块自行解释；审计无法追溯 |

## 1. 模块概述

### 1.1 模块定位

M22-02 数据采集与汇总，是全院指标数据从「各业务模块的统计接口」流向「全院报表与驾驶舱」的**唯一通道**。

用一句话描述它的职责：**按既定的任务与节奏，去上游统计接口把指标数据取回来，核对完整性，落到指标事实表，并在取不到的时候诚实地标注「取不到」，而不是编一个数。**

它与相邻子模块的分工是一条单向数据流水线：

```
上游业务模块统计接口（M04~M17 共 104 条）
        │  只经过登记过的接口，绝不直查库
        ▼
   ┌─────────────┐
   │  M22-02     │  采集计划 → 批次执行 → 完整性校验 → 事实落库
   │  采集引擎   │  补采重算 → 质量告警 → 失败重试 → 全程留痕
   └─────────────┘
        │  只暴露「已落库且标注完整性」的事实数据
        ▼
   ┌─────────────┐
   │  M22-03~08  │  日报周报月报 / 科室排名 / 视光 / 屈光 / 绩效 / 驾驶舱
   │  报表消费方 │  只读事实数据 + 指标定义，不重复取数
   └─────────────┘
        ▲
        │  提供指标定义（metric_code / 单位 / 方向 / 口径版本）
   ┌─────────────┐
   │  M22-01     │  指标中心：全院指标口径唯一注册中心
   └─────────────┘
```

M22-02 在整个体系里承担三件别人不做的事：

1. **唯一取数入口**：任何报表需要的指标数据，都必须先经过 M22-02 落成事实行。报表层不允许自己去调上游接口，否则同一指标在不同报表里会出现两次取数、两个值。
2. **完整性守门人**：上游接口超时、返回结构变化、某科室确实没开展业务，这些情况 M22-02 要逐条判定并标注 `COMPLETE`/`PARTIAL`/`FAILED`/`STALE`。完整性标记会一路传递到报表页面的「数据不完整」提示上。
3. **可追溯的账本**：每一个事实值都能回答「这个数从哪来、什么时候取的、哪一批取的、用了哪个口径版本、中途失败重试过几次」。这是后面做口径审计与数据争议处理的基础。

### 1.2 为什么独立成子模块

**理由一：采集与指标定义是两件演化节奏完全不同的事。**

指标定义（M22-01）会随着管理需要频繁调整：这个月新增 5 个视光转化率指标、下个月把「门诊人次」的口径从挂号数改为就诊数。但采集任务（M22-02）的配置相对稳定——接口路径、超时、重试、调度节奏。两者混在一个子模块里，每次调口径都要碰采集代码，回归测试范围会被不必要地放大。分开之后，M22-01 改口径只影响「指标定义表 + 口径版本号」，M22-02 通过 `metric_version` 字段自然承接，历史事实保留旧版本口径，不需要重算（对应 M22 铁律 5）。

**理由二：采集是唯一的高频、长耗时、易失败路径，需要独立的容量与可靠性设计。**

一个典型的工作日，M22-02 要执行：日粒度任务约 120 个（覆盖 16 个上游模块、日均 3000 条指标行）、小时粒度健康检查任务 24 次、事件驱动的日结任务 2 次（`m16.daily.frozen` 与 `m17.period.closed`）、以及不定期的补采重算。这个量级与报表渲染（M22-03 的读路径）完全是两种负载特征。M22-02 需要自己的分布式锁、自己的重试退避、自己的超时熔断、自己的健康度看板；把它塞进报表子模块会让报表页面的响应时间被采集任务拖垮。

**理由三：数据完整性的判定逻辑只能有一份。**

「上游返回 200 但 8 个科室里只给了 6 个」这算成功还是部分成功？「M17 期间尚未结账」算失败还是待采？这些判定如果散落在 M22-03 日报、M22-04 排名、M22-08 驾驶舱各自的取数代码里，必然出现同一批数据在三个报表里分别被标成 COMPLETE、PARTIAL、COMPLETE 的荒唐局面。把判定收敛到 M22-02 一处，下游只消费结果，是唯一能保证「同一份数据全院只有一个完整性结论」的做法。

**理由四：P-01 是全院唯一的多源推送聚合点。**

M06-07 与 M09-06 两个上游子模块各自会主动推送指标（日间手术质量、手术室运营），推送是异步的、可能重复、可能乱序、可能推送尚未注册的指标。这类「外来数据入口」必须有独立的幂等、冲突检测、待认领缓冲、回放机制，不能和内部采集的主动调用路径混在一起。M22-02 承担这个入口，用 `push_batch_no` 幂等 + 内容指纹冲突检测 + 待认领指标表三道机制兜住。

### 1.4 概念辨析

这一节是本子模块最容易被误解的地方，逐组辨析。

**① 指标事实（fact）vs 业务事实（business record）**

业务事实是「张三今天挂了一个号」，存在于 M04 的挂号表里，是原始交易记录。指标事实是「今天全院挂了 1,284 个号」，是聚合后的统计结论，存在于 M22 的 `m22_fact_metric` 里。M22 永远不生产业务事实，只接收业务模块算好的统计结论。典型错误写法是 `SELECT COUNT(*) FROM m04_registration WHERE ...`，正确写法是 `GET /internal/v1/m04/statistics/summary?period=2026-10-31`。

**② 采集（collect）vs 汇总（aggregate）**

采集是「从上游拿数并落库」，一行指标一个期间一条事实。汇总是「把已有事实再往上一层合并」，比如把 12 条日粒度事实合成 1 条月粒度事实。M22-02 两件事都做，但界面上是两条不同的路径：P03 采集批次管采集，P06 补采与重算管汇总重算。汇总不改变源数据，只新增上层粒度的行，两者靠 `derived_from` 与 `parent_batch_no` 串起来。

**③ 完整性（completeness）vs 准确性（accuracy）**

完整性回答「该有的数是不是都拿到了」，只有四个取值 COMPLETE/PARTIAL/FAILED/STALE，由 M22-02 判定。准确性回答「拿到的数对不对」，由 M22-02 的质量校验规则（P05）与后续的校准流程（P06）处理。一个数据可以「完整但错误」（上游全给了但算错了），也可以「部分但不离谱」（缺了两个科室，其余都对）。混淆这两件事会导致把「准确性告警」写进 `source_status`，让下游误以为数据缺失。

**④ 补采（supplement）vs 重算（rerun）vs 重试（retry）**

重试是「同一次采集失败了，隔一会儿再试一遍」，失败本身没解决而是靠时间碰运气，次数有上限（默认 5 次），由调度器自动发起。补采是「原来没采过或者采漏了，现在补上」，比如三月的数五月份才发现少了一个指标，这时发起一个新批次，`trigger_mode = SUPPLEMENT`，落库仍然落到三月分区。重算是「数据已经在了，但口径变了或者发现算错了，整批重新算一遍」，`trigger_mode = RERUN`，会覆盖已有事实行并递增 `data_version`。三者共用 `parent_batch_no` 追溯，但语义与权限要求不同——重算因为会改写历史，必须走审批。

**⑤ 采集批次（collect batch）vs 推送批次（push batch）**

采集批次是 M22 自己发起的，编号形如 `CB20261031-0001`，由 M22 生成。推送批次是上游推过来的，编号由调用方生成（如 `M09-20261031-0001`），存在 `push_batch_no` 字段。P-01 收到推送时会为它在 M22 侧建一个 `source_type = EVENT_PUSH` 的采集批次，把两个编号都记住。这样「上游说自己推了」「M22 说自己收了」在同一个批次对象上能对账。

**⑥ 事实的期间（period）vs 采集时刻（collected_at）**

期间是数据描述的业务时间（2026-10-31 这一天的数据），采集时刻是 M22 实际把数据取回来的时间（可能是 2026-11-03 凌晨）。两者必须分开存，因为补采场景下它们会差很远。`m22_fact_metric` 的分区键是 `period` 派生的 `period_month` 而不是 `collected_at`，原因就在这里——三月的数五月份补采，必须落进三月分区，否则「查三月」会漏、按月归档会错。

### 1.5 模块目标

| 编号 | 目标 | 可度量指标 |
|---|---|---|
| G-01 | 全院指标数据 100% 经 M22-02 落库后才进入报表 | 报表层代码中上游接口调用数为 0（静态扫描验收） |
| G-02 | 日粒度采集在每日 07:00 前完成 | 连续 30 天统计：日采集批次 `finished_at` 早于当日 07:00 的比例 ≥ 99% |
| G-03 | 采集数据完整性可判定、可追溯 | 每条事实行六个溯源字段齐全率 100%；`source_status` 非空的比率 100% |
| G-04 | 绝不出现静默填 0 | 抽查 100 条 `PARTIAL`/`FAILED` 事实行，`metric_value` 为 NULL 或 `value_is_estimated = TRUE` 的比率 100% |
| G-05 | 采集失败可在 5 次重试内自愈 | 首轮失败但最终成功（`retry_status = RECOVERED`）的比率 ≥ 90% |
| G-06 | 上游接口异常可提前发现 | 上游接口健康度 DEGRADED/DOWN 状态在失败后 1 小时内可见 |
| G-07 | 推送入口具备幂等与冲突防护 | 同一 `push_batch_no` 重推 5 次，事实表行数增量为 0；同号不同内容 100% 报冲突 |

## 2. 业务范围与边界

### 2.1 范围内

M22-02 承担以下八项业务能力，全部围绕「把数取回来并说清楚」。

| 编号 | 能力 | 具体内容 | 对应页面 | 关键落库对象 |
|---|---|---|---|---|
| S-01 | 采集任务配置 | 建立「指标集合 → 上游接口 → 调度节奏 → 超时重试」的任务模板；支持 CRON 定时、事件驱动、手工三种触发；支持科室范围与指标子集裁剪 | P02 | `m22_collect_task` |
| S-02 | 采集批次执行 | 按任务发起批次，加分布式锁防并发，逐指标调用上游接口，逐条判定成功/失败/被拒/未认领，统计批次汇总数 | P03 | `m22_collect_batch`、`m22_collect_batch_item` |
| S-03 | 指标事实落库 | 按 `(metric_code, period, dept_id, biz_dim)` 幂等 upsert 到事实表，记录六要素溯源，值未变时跳过写入 | P01、P04 | `m22_fact_metric` |
| S-04 | 日结月结汇总 | 订阅 `m16.daily.frozen` 触发当日收入类指标采集；订阅 `m17.period.closed` 触发该期间财务指标采集；把日粒度事实按需汇总成月粒度事实 | P01 | `m22_fact_metric`（上层粒度） |
| S-05 | 补采与重算 | 对漏采期间发起补采批次；对口径变更或数据错误发起重算批次；补采落原期间分区，重算覆盖并递增 `data_version` | P06 | `m22_collect_batch`（`trigger_mode` 区分） |
| S-06 | 数据质量校验 | 内置规则集（区间校验、环比突变、合计校验、跨指标勾稽、空值率、口径一致性），命中后落质量问题并分级告警 | P05 | `m22_collect_quality_check` |
| S-07 | 采集监控告警 | 上游接口健康度按小时聚合、SLA 违约检测、连续失败天数累计、降级与熔断、告警推送 | P07 | `m22_collect_source_health` |

### 2.3 与业务模块的边界

这一节是 M22 最容易做错的地方，共享规范 §1.2 已经把它列为「最容易做错的边界」，这里逐条落到 M22-02 的实现层面。

**核心原则：M22 是权限最低的跨模块角色——只许调接口，不许碰数据库。**

| 层面 | 允许 | 禁止 |
|---|---|---|
| 数据获取 | 通过 `app/clients/m22/` 下为每个上游模块封装好的 client，调用共享规范 §9 登记的 104 条路径之一 | 直接 `SELECT`/`INSERT`/`UPDATE` 任何非 `m22_` 前缀的表；连只读视图都不行 |
| 数据库账号 | M22-02 的数据库账号只有 `m22_*` 表的读写权限；上游表权限为 `REVOKE ALL` | 复用主业务库账号；用超级用户连接 |
| 统计口径 | 上游给什么就是什么，原样落库 | 拿到明细后自行重新聚合、自行改口径、自行补齐上游没给的数 |
| 时间语义 | 上游返回的期间的业务时间原样使用 | 拿 `collected_at` 当业务时间 |
| 缺失处理 | 标 `PARTIAL`/`FAILED`，写 `missing_sources` 与 `degraded_reason` | 填 0、填上期值而不标注、跳过不落库 |
| 一致性 | 以「上游接口是唯一事实源」为原则，上游变了就跟着变 | 本地维护一份业务数据的副本表 |

**三条落地铁律**

**铁律一：所有上游调用必须走 client 封装。** 不允许在 Service 或 Celery 任务里出现裸 `httpx.get("http://...")`。每个上游模块一个 client 文件，路径常量集中定义，超时与重试策略集中在 client 基类，便于统一加埋点与熔断。

**铁律二：client 的返回值必须带上溯源信息。** 每次调用返回的不只是数据，还有 `source_api`（实际调用的路径）、`upstream_trace_id`、`http_status`、`elapsed_ms`。这些信息会一路带到 `m22_collect_batch_item` 与 `m22_collect_log`，是事后追溯的唯一依据。

**铁律三：上游不可用时，禁止「顺手补一个」。** 见 2.2 的 L-02。具体到代码层面，client 抛出的异常类型分为 `UpstreamUnavailable`（网络/超时/5xx）、`UpstreamRejected`（4xx）、`UpstreamSchemaChanged`（返回结构不符合预期）三类，三类一律转成 `source_status = 'FAILED'` 或 `'PARTIAL'`，绝不返回 0 或空列表冒充成功。

**上游不可用的四个判定档位**

| 判定 | 触发条件 | `source_status` | `metric_value` | 下游表现 |
|---|---|---|---|---|
| 全部成功 | 所有指标、所有科室都取到值 | `COMPLETE` | 实际值 | 正常显示 |
| 部分成功 | 部分科室或部分指标缺失，但至少有一条取到 | `PARTIAL` | NULL 或估算值（`value_is_estimated = TRUE`） | 显示「数据不完整」+ 缺失清单 |
| 完全失败 | 上游超时、5xx、所有指标都没取到 | `FAILED` | NULL | 显示「本期无数据」+ 失败原因 |
| 陈旧数据 | 上游返回的是缓存或上次的值，且超过允许陈旧时长 | `STALE` | 上次的值（明确标注） | 显示「数据未更新，为 X 时刻的数据」 |

## 3. 业务模型

### 3.1 核心实体关系

```
   ┌──────────────────────┐
   │ m22_collect_task     │  采集任务配置
   │  任务 = 指标集+接口  │
   └──────────┬───────────┘
              │ 1 : N 发起
              ▼
   ┌──────────────────────┐        ┌──────────────────────┐
   │ m22_collect_batch    │◄───────│ m22_collect_calibra  │
   │  批次（CB 单号）     │ 校准关联│ 校准单（CL 单号）    │
   └──┬───────┬────────┬──┘        └──────────────────────┘
      │1:N    │1:N     │1:N
      ▼       ▼        ▼
 ┌─────────┐┌────────┐┌──────────────────┐
 │ batch_  ││ failure││ quality_check    │
 │ item    ││重试流水││ 质量命中（QC）   │
 └────┬────┘└────────┘└──────────────────┘
      │ 成功后 upsert
      ▼
   ┌──────────────────────┐        ┌──────────────────────┐
   │ m22_fact_metric      │        │ m22_collect_source_  │
   │  指标事实（按月分区）│        │ health 上游健康度    │
   └──────────────────────┘        └──────────────────────┘

   ┌──────────────────────┐        ┌──────────────────────┐
   │ m22_collect_unclaim  │        │ m22_collect_log      │
   │ 待认领指标（P-01 收）│        │ 日志（只增不改）     │
   └──────────────────────┘        └──────────────────────┘
```

**关系说明**

| 关系 | 基数 | 说明 | 是否建物理外键 |
|---|---|---|---|
| 任务 → 批次 | 1 : N | 一个任务可产生多个批次（定时、补采、重算） | 否，用 `task_code` 逻辑关联 |
| 批次 → 批次（父子） | 1 : N | 补采/重算/重试批次通过 `parent_batch_no` 指回原批次 | 否，自关联用字符串 |
| 批次 → 明细 | 1 : N | 一个批次按指标 × 科室展开为多条明细 | 否，用 `batch_no` 逻辑关联 |
| 批次 → 失败流水 | 1 : N | 一条明细可能失败多次，每次一条重试记录 | 否，用 `batch_no` + `metric_code` |
| 批次 → 质量命中 | 1 : N | 一个批次执行后跑质量规则，命中多条 | 否 |
| 明细 → 事实 | N : 1 | 多条明细 upsert 到同一 `(metric_code, period, dept_id, biz_dim)` 时后者覆盖 | 否 |
| 校准单 → 事实 | 1 : 1 | 一份校准单精确修正一条事实行的值或状态 | 否，记录 `fact_id` 与 `old_value` |
| 批次 → 日志 | 1 : N | 批次状态流转每次写一条日志 | 否 |
| 上游模块 → 健康度 | 1 : N | 每个上游接口每小时一条健康度记录 | 否 |

**为什么全部不建物理外键**：M22-02 的批次与明细表是高频写入的流水表，物理外键会给每次 upsert 带来额外的行锁开销；且分区表无法被其他表以外键引用（PostgreSQL 限制）。逻辑关联由 Service 层保证，数据库层用唯一索引兜底。

### 3.2 状态机

**3.2.1 采集批次状态机**

```
                       ┌──────────┐
        发起采集       │  PENDING │  已创建待执行
        ──────────────►│          │
                       └────┬─────┘
                            │ 获取分布式锁成功、开始调用上游
                            ▼
                       ┌──────────┐
                       │ RUNNING  │  正在采集
                       └────┬─────┘
                ┌───────────┼───────────┬────────────┐
        全部成功│   部分成功│  全部失败 │ 进程异常退出│
                ▼           ▼           ▼            ▼
          ┌──────────┐┌─────────┐┌────────┐  ┌────────┐
          │COMPLETED ││ PARTIAL ││ FAILED │  │ FAILED │
          └──────────┘└─────────┘└────────┘  │(超时)  │
                                              └────────┘
                            │
                            │ 发起补采/重算（新批次）
                            ▼
                      ┌──────────┐
                      │ 新批次   │  trigger_mode=SUPPLEMENT/RERUN
                      └──────────┘   parent_batch_no 指回
```

| 状态 | 含义 | 可流转到 | 触发动作 | 说明 |
|---|---|---|---|---|
| `PENDING` | 批次已创建，等待执行 | `RUNNING`、`FAILED` | 调度器领取 / 超时未领取 | 超过 30 分钟未流转则自动置 FAILED 并告警 |
| `RUNNING` | 正在调用上游并落库 | `COMPLETED`、`PARTIAL`、`FAILED` | 执行完成 | 持有 `lock_token`，可被强制终止 |
| `COMPLETED` | 全部指标全部科室成功 | — | — | 终态，`source_status = COMPLETE` |
| `PARTIAL` | 部分成功 | — | — | 终态，`source_status` 记 `PARTIAL`，必须有 `missing_sources` |
| `FAILED` | 全部失败或进程异常 | — | — | 终态，`source_status = FAILED` |

**状态流转规则**：只有 `PENDING → RUNNING`、`RUNNING → COMPLETED/PARTIAL/FAILED`、`PENDING → FAILED` 三条合法路径。一旦进入终态，批次不可回退，只能通过发起新批次（`parent_batch_no` 指回）来处理。

**3.2.2 采集任务状态机**

```
   ┌────────┐  启用   ┌────────┐  开始执行  ┌──────────┐
   │DISABLED│────────►│  IDLE  │───────────►│ RUNNING  │
   └────────┘         └────────┘            └────┬─────┘
        ▲                  ▲                    │执行结束
        │禁用              │                                               │
        │                  └────────────────────┴──────┐
        │                                              ▼
        │                     ┌─────────┬─────────┬─────────┐
        │                     │ SUCCESS │ PARTIAL │ FAILED  │
        │                     └─────────┴─────────┴─────────┘
        └──────────────────────────────────────────────────┘
```

| 状态 | 含义 | 说明 |
|---|---|---|
| `IDLE` | 空闲，等待下次触发 | 任务从未执行或上次执行已结束且下次未到 |
| `RUNNING` | 正在执行 | 同一任务同时只允许一个 RUNNING 实例（由任务级锁保证） |
| `SUCCESS` | 上次执行全部成功 | 仅反映最近一次 |
| `PARTIAL` | 上次执行部分成功 | 需人工关注 |
| `FAILED` | 上次执行失败 | 连续 3 次 FAILED 触发告警 |
| `DISABLED` | 人工停用 | 停用后不参与调度，可手工强制发起 |

**3.2.3 失败重试状态机**

```
   ┌─────────┐  调度到期  ┌──────────┐  成功  ┌───────────┐
   │ WAITING │───────────►│ RETRYING │───────►│ RECOVERED │
   └─────────┘            └────┬─────┘        └───────────┘
        ▲                      │再次失败
        │ 计算下次退避时刻      ▼
        └─────────────────┌─────────┐
                          │ 判断次数│
                          └────┬────┘
                    未达上限 │    │ 已达上限
                             ▼    ▼
                      (回 WAITING) ┌──────────┐
                                   │EXHAUSTED │
                                   └──────────┘
                                        │ 人工放弃
                                        ▼
                                   ┌──────────┐
                                   │ABANDONED │
                                   └──────────┘
```

| 状态 | 含义 |
|---|---|
| `WAITING` | 等待下次重试，`next_retry_at` 已设定 |
| `RETRYING` | 正在重试 |
| `RECOVERED` | 重试成功，`recovered_batch_no` 记录成功的批次 |
| `EXHAUSTED` | 重试次数用尽（默认 5 次），不再自动重试，需人工介入 |
| `ABANDONED` | 人工判定放弃，不再重试 |

### 3.4 关键计算模型

这一节给出 M22-02 涉及的九个核心计算的口径，每个都写清公式、单位、边界条件、舍入方式与算例。

**3.4.1 指标事实值的落库口径**

| 项 | 内容 |
|---|---|
| 公式 | `metric_value = upstream_response.data.value`（上游给什么就是什么，不做任何转换） |
| 单位 | 由 `metric_unit` 决定；AMOUNT 类为元，RATE/RATIO 类为 0~1 的小数 |
| 存储精度 | `NUMERIC(20,6)` —— 保留 6 位小数。上游给 `0.8235` 则存 `0.823500` |
| 边界条件 | 空值：上游返回 `null` 或字段缺失 → `metric_value = NULL`，`source_status = 'PARTIAL'`；负值：允许（如退款为负），但 `metric_unit` 为 RATE/RATIO/PERCENT 时必须在 `[0,1]` 内，越界判为 `VALIDATE` 阶段失败 |
| 舍入 | 落库不舍入，原值存 6 位。仅对外展示时按 `metric_unit` 舍入 |
| 失败条件 | 上游值无法解析为数字 → 明细 `item_status = 'FAILED'`，`failure_stage = 'PARSE'` |
| 算例 | 上游返回 `value = 0.8235`，`unit = 'RATE'`，落库 `metric_value = 0.823500`，`metric_unit = 'RATE'` |
| 可空性规则 | `source_status = 'COMPLETE'` 时 `metric_value` 必填；`'FAILED'` 时必为 NULL；`'PARTIAL'` 时可 NULL 或估算值 |

**3.4.2 目标达成率**

| 项 | 内容 |
|---|---|
| 公式 | 正向指标（HIGHER_BETTER）：`达成率 = metric_value / target_value`；反向指标（LOWER_BETTER）：`达成率 = target_value / metric_value`；目标为 0 时不可计算 |
| 单位 | 无量纲小数，`NUMERIC(9,6)` |
| 边界条件 | `metric_value` 为 NULL → 达成率返回 NULL（绝不返回 0）；`target_value` 为 NULL 或 0 → 返回 NULL 并标「未设目标」 |
| 舍入 | 保留 6 位小数，四舍五入 |
| 失败条件 | `value_direction = 'NEUTRAL'` 时该公式不适用，直接返回 NULL |
| 算例 | 手术室利用率：`metric_value = 0.823500`，`target_value = 0.800000`，正向指标 → `达成率 = 0.823500 / 0.800000 = 1.029375`，即 102.94% |
| 反向算例 | 平均住院日：`metric_value = 3.500000` 天，`target_value = 4.000000` 天，反向指标 → `达成率 = 4.000000 / 3.500000 = 1.142857`，即 114.29% |
| 零值防护 | `LOWER_BETTER` 且 `metric_value = 0` 时（如退费率 0），达成率无意义，返回 NULL 并标「无发生」 |

**3.4.3 环比与同比增长率**

| 项 | 内容 |
|---|---|
| 公式 | 环比：`(本期值 - 上期值) / 上期值`；同比：`(本期值 - 去年同期值) / 去年同期值` |
| 单位 | 无量纲小数，`NUMERIC(9,6)` |
| 边界条件 | 上期值或去年同期值为 NULL → 增长率 NULL；上期值为 0 → 增长率 NULL（不做除零特判为 100% 之类的伪值）且标记「基期为零」 |
| 舍入 | 保留 6 位小数 |
| 算例 | 本月门诊收入 1,284,500.00 元，上月 1,120,000.00 元 → `(1284500 - 1120000) / 1120000 = 0.146875`，即环比增长 14.69% |
| 说明 | M22-02 只提供计算所需的原始事实与上一期事实的取数能力，实际计算在报表层（M22-03/04）完成。本子模块不把环比结果落库（属于派生指标，非事实） |

**3.4.4 数据完整度**

| 项 | 内容 |
|---|---|
| 公式 | `完整度 = 成功明细条数 / 计划明细条数` |
| 单位 | 无量纲小数，`NUMERIC(9,6)` |
| 边界条件 | 计划条数为 0 → 完整度为 NULL（不是 1，不是 0） |
| 舍入 | 保留 6 位小数 |
| 算例 | 某批次计划采集 12 个指标 × 8 个科室 = 96 条明细，实际成功 88 条 → `完整度 = 88 / 96 = 0.916667`，落 `source_status = 'PARTIAL'` |
| 阈值联动 | 完整度 = 1.0 → COMPLETE；0 < 完整度 < 1.0 → PARTIAL；= 0 → FAILED |

**3.4.5 批次级完整性判定**

| 判定顺序 | 条件 | 结果 |
|---|---|---|
| 1 | 所有明细 `item_status = 'SUCCESS'` | `source_status = 'COMPLETE'` |
| 2 | 至少一条 SUCCESS，且存在 FAILED/SKIPPED/UNCLAIMED | `source_status = 'PARTIAL'` |
| 3 | 无任何 SUCCESS | `source_status = 'FAILED'` |
| 4 | 明细结果全部来自上游缓存且缓存年龄超过阈值 | `source_status = 'STALE'`（优先于 1、2） |

**3.4.6 上游接口健康度**

| 项 | 内容 |
|---|---|
| 公式 | `success_rate = call_success / call_total`（按小时聚合）；`latency_p95_ms` 取该小时全部调用的 95 分位耗时 |
| 单位 | success_rate 无量纲，latency 单位毫秒 |
| 边界条件 | `call_total = 0` → success_rate 为 NULL，`health_status = 'UNKNOWN'` |
| 判定规则 | `success_rate ≥ 0.99` 且 `latency_p95_ms ≤ sla_p95_ms` → HEALTHY；`success_rate ≥ 0.95` → DEGRADED；`success_rate < 0.95` → DOWN；连续失败天数 ≥ 配置阈值（默认 3 天）→ 强制 DOWN 并告警 |
| 算例 | 某小时调用 240 次，成功 228 次，p95 = 820ms，SLA = 500ms → `success_rate = 0.950000`，p95 超 SLA → `sla_breached = TRUE`，`health_status = 'DEGRADED'` |

**3.4.7 重试退避时长**

| 项 | 内容 |
|---|---|
| 公式 | 指数退避：`backoff_s = backoff_base_s × 2^(retry_seq - 1)`；固定退避：`backoff_s = backoff_base_s` |
| 单位 | 秒 |
| 边界条件 | `backoff_s` 上限截断为 3600 秒（1 小时）；`retry_seq > max_retry` 时不再计算，直接置 EXHAUSTED |
| 算例 | 基数 30 秒，指数退避：第 1 次 30s、第 2 次 60s、第 3 次 120s、第 4 次 240s、第 5 次 480s，累计 930 秒（约 15.5 分钟）内完成 5 次重试，与 M06-07 / M09-06 约定的「重试 5 次」一致 |
| 抖动 | 实际等待时间加 `±10%` 随机抖动，避免多个批次同时重试打爆上游 |

**3.4.8 事实数据版本号（data_version）**

| 项 | 内容 |
|---|---|
| 公式 | 每次对同一条事实行 upsert 且值发生变化时，`data_version = data_version + 1`；值未变时不递增 |
| 用途 | 下游缓存失效判断。报表层缓存 key 含 `data_version` 的聚合值，值不变则缓存继续有效 |
| 与 `version` 的区别 | `version` 是乐观锁版本（任何字段变更都递增），`data_version` 只反映指标值变化，用于缓存 |
| 算例 | 首次落库 `data_version = 1`；补采得到相同值，`data_version` 仍为 1，缓存不失效；重算得到新值，`data_version = 2`，缓存失效 |

**3.4.9 采集期间与分区归属**

| 项 | 内容 |
|---|---|
| 公式 | `period_month = substr(period, 1, 7)`，取 `period` 前 7 位作为月份；格式不合法（不匹配 `^[0-9]{4}-[0-9]{2}`）时置 `0000-00` |
| 用途 | 决定事实行落到哪个月分区 |
| 边界条件 | 补采三月份的数据，即使采集发生在五月份，`period = '2026-03-15'` → `period_month = '2026-03'` → 落三月分区 |
| 算例 | `period = '2026-10-31'` → `period_month = '2026-10'` → 分区 `m22_fact_metric_p202610` |
| 兜底 | 超出预建 12 个月分区范围的期间（如异常年份）落 `m22_fact_metric_p_default`，并由质量规则 `QC_PARTITION_FALLBACK` 告警 |

### 4.2 关键设计决策摘要

以下是数据结构层面最关键、也最容易被后来修改者破坏的六个设计决策，改动前必须先读这一节。

| 编号 | 决策 | 理由 | 破坏后的后果 |
|---|---|---|---|
| DD-01 | `m22_fact_metric` 分区键是 `period` 派生的 `period_month`，不是 `collected_at` | 补采场景下期间与采集时刻可能相隔数月，三月的数五月补采必须落三月分区 | 「查三月数据」漏掉补采行；按月归档错位 |
| DD-02 | `m22_fact_metric` 必须有 DEFAULT 兜底分区 | 上游返回非法期间时 `INSERT` 不会因无匹配分区而失败，整批采集不崩 | 一条脏期间导致整批 96 条明细全部回滚 |
| DD-03 | 事实表 `metric_value` 可空 + `value_is_estimated` 标志位 + `ck_m22_fact_metric_no_silent_zero` | 既保留「部分科室确实无业务」的合法部分和，又让任何非精确值都带可见标记 | 静默填 0，报表出现「本月收入 0 元」 |
| DD-04 | 同一 `(metric_code, period, dept_id, biz_dim)` 唯一索引 `uk_m22_fact_metric_dim` | 采集幂等的数据库级保障，重复采集走 upsert 而不是插两行 | 同一指标同一期间出现多条事实，报表重复计数 |
| DD-05 | `push_batch_no` 唯一索引 + `push_batch_hash` 内容指纹 | 只有唯一索引无法区分「幂等重放」与「同号不同内容」 | 要么重推报错（上游重试 5 次全失败），要么静默覆盖（数据被篡改无人知） |
| DD-06 | 全部表不建物理外键 | 流水表高频写入，外键带来额外锁开销；分区表无法被外键引用 | 插入性能下降；分区表建外键直接报错 |

### 6.3 接口详述

#### API-01 采集监控工作台今日概况

| 项 | 内容 |
|---|---|
| 方法路径 | `GET /api/v1/m22/collect/dashboard` |
| 权限 | `m22:collect:view` |
| 幂等 | 是（只读） |
| 缓存 | Redis `m22:collect:dashboard:{yyyyMMdd}`，TTL 60 秒 |

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `stat_date` | string | 否 | 统计日期，默认今日，格式 `2026-10-31` |

**响应示例**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "stat_date": "2026-10-31",
    "batch_total": 128,
    "batch_completed": 121,
    "batch_partial": 5,
    "batch_failed": 2,
    "fact_rows": 3842,
    "unclaimed_count": 12,
    "quality_open_count": 8,
    "completeness": {
      "COMPLETE": 96.1,
      "PARTIAL": 3.1,
      "FAILED": 0.8,
      "STALE": 0.0
    },
    "generated_at": "2026-10-31 07:12:33"
  },
  "trace_id": "a1b2c3d4e5f60718"
}
```

**业务逻辑**

1. 按 `created_at` 落在 `stat_date` 全天的批次聚合，统计各状态计数。
2. `fact_rows` 取当日 `m22_collect_batch.fact_inserted + fact_updated` 之和，不从事实表按 `created_at` 计数（避免补采历史期间的行被算进今日）。
3. `unclaimed_count` 取待认领表 `claim_status = 'PENDING'` 的计数，`quality_open_count` 取质量问题 `handle_status = 'OPEN'` 的计数。
4. 结果缓存 60 秒；`m22.collect.completed` 事件会主动清除当日缓存 key。

**错误码**：`"229001"`

#### API-07 新建采集任务

| 项 | 内容 |
|---|---|
| 方法路径 | `POST /api/v1/m22/collect/tasks` |
| 权限 | `m22:collect:create` |
| 幂等 | 支持 `Idempotency-Key` 头 |

**请求体**：见数据结构文档 `CollectTaskCreate` Schema。

**业务逻辑**

1. 校验 `task_code` 唯一，重复返回 `"2202006"`。
2. 校验 `source_api` 在共享规范 §9 白名单内，否则 `"2202011"`。
3. 调 U-01（`POST /internal/v1/m22/metrics/batch`）批量校验 `metric_codes` 全部存在且 `status = ACTIVE`，否则 `"2202012"`。采集任务配置属于「人工显式声明要采集哪些指标」，配置阶段要求一次性给全，`missing_codes` 非空即拒绝保存——此处不允许「先配一半、等注册了再补」的模糊状态。注意这与 P-01 推送路径的处理相反：推送是上游已经把数算出来了，丢掉就永久丢失，所以只把 `missing_codes` 进待认领、其余照常落库。
4. 校验 `granularity` 不细于上游接口最细粒度，否则 `"2202013"`。
5. `trigger_type = CRON` 时用 croniter 解析 `cron_expr`，失败 `"2202014"`；`EVENT` 时校验 `event_code` 在共享规范 §10.2 事件清单内。
6. `dept_scope = CUSTOM` 时校验 `dept_ids` 非空且科室存在，否则 `"2202015"`。
7. 落库并写日志（`event_type = 'TASK_CREATED'`），同时由 APScheduler 注册调度作业。

**错误码**：`"2202006"`、`"2202011"`、`"2202012"`、`"2202013"`、`"2202014"`、`"2202015"`、`"229001"`

**业务逻辑（核心）**

1. **入口校验**：校验服务令牌、`metrics` 非空（否则 `"2202029"`）、`metrics` 内 `(metric_code, dept_id)` 无重复（否则 `"2202030"`）。
2. **计算内容指纹**：对 `metrics` 按 `metric_code` 升序（相同则按 `dept_id`）排序，取 `metric_code|dept_id|value|unit|target` 逐条拼接后做 SHA-256，得到 `push_batch_hash`。**不参与指纹计算的字段**：`pushed_at`（每次推送都会变）、`trace_id`。
3. **幂等判定**：按 `push_batch_no` 查 `m22_collect_batch.push_batch_no`。
   - 不存在 → 新建批次，继续第 4 步。
   - 存在且 `push_batch_hash` **相同** → **幂等重放**：不落库、不改事实表，直接从该批次回读当时的 `metric_success`/`metric_rejected`/明细结果组装响应，`idempotent_replay = true`。
   - 存在且 `push_batch_hash` **不同** → 返回 `"2202028" PUSH_BATCH_CONFLICT`（HTTP 409），消息中说明「同一推送批次号已存在不同内容」，`data` 段返回已有批次的 `collect_batch_no` 与首次推送时间，**不覆盖任何数据**。
4. **逐条校验指标**（关键：单条失败不影响整批）：
   - 调 U-01（`POST /internal/v1/m22/metrics/batch`，1~200 个编码一批，P95 300ms）批量查指标定义，响应里的 `items` 构建 `metric_code → (unit, status, ...)` 映射，`missing_codes` 即未注册编码（Redis 缓存 10 分钟）。**上游返回部分缺失不算调用失败**——`missing_codes` 非空时只把这几条进待认领，其余条目照常走后续校验与落库，绝不因为一个编码没注册就把整批推开。只有当 U-01 整个不可用（超时/5xx 且缓存也失效）时，才无法判定任何编码的注册状态，此时整批返回 `"2202012"` 并进重试队列。两种情形的分界在于「上游明确告诉我哪些没注册」与「我根本不知道哪些注册了」——前者信息充分可精细处理，后者信息缺失只能整批退回。
   - 未找到或 `status <> 'ACTIVE'` → 该条 rejected，`reason = METRIC_NOT_REGISTERED`，错误码 `"2202031"`，并**写入 `m22_collect_unclaimed_metric`**（`claim_status = 'PENDING'`）等后续认领回放，`unclaimed` 计数 +1。
   - 单位与注册单位不一致 → rejected，`reason = UNIT_MISMATCH`，错误码 `"2202032"`。
   - `unit IN ('RATE','RATIO','PERCENT')` 且 `value` 不在 `[0,1]` 内 → rejected，`reason = VALUE_OUT_OF_RANGE`，错误码 `"2202035"`。
   - `value` 为 `null` → 合法，落 `metric_value = NULL` 且 `source_status = 'PARTIAL'`，**不是** rejected。
5. **落库**：通过校验的条目按 `(metric_code, period, dept_id, biz_dim)` upsert 到 `m22_fact_metric`，`biz_dim` 统一为 `'NONE'`（若 `dept_id` 为空则 `biz_dim = 'SCOPE=ALL'`），`source_api` 记为 `P-01`，`collect_batch_no` 记本批次号，`source_status = 'COMPLETE'`。
6. **更新批次汇总**：写入 `metric_total`/`metric_success`/`metric_rejected`/`metric_unclaimed`/`fact_inserted`/`fact_updated`/`fact_skipped`，批次状态置 `COMPLETED`（无拒绝）或 `PARTIAL`（有拒绝）。
7. **发布事件**：批次完成后发布 `m22.collect.completed`。
8. **响应组装**：`accepted` = 通过校验的条数，`rejected` = 被拒条数（其中未注册的部分计入 `unclaimed`），`rejected_detail` 按 `index` 升序。

**关键设计说明**

| 编号 | 决策 | 理由 |
|---|---|---|
| P1-01 | 幂等键由调用方生成，M22 只按它去重 | M22 无法为「调用方认为是同一批」的请求重新生成标识；上游重试时带的是同一个 `push_batch_no` |
| P1-02 | 幂等重放返回**首次结果原样**，包括当时的 `rejected_detail` | 调用方 5 次重试里可能中间 M22-01 恰好注册了某指标，若重放时重新计算，第 5 次会得到与第 1 次不同的结果，调用方无法判断「到底哪次是真的」 |
| P1-03 | 同号不同内容必须报冲突而不是覆盖 | 覆盖会让「首次结果可追溯」这一条失效；且覆盖可能把正确数据改错 |
| P1-04 | 未注册指标进待认领表而不是整批失败 | 上游推了 100 条，其中 1 条是新指标还没注册，因为这一条丢掉另外 99 条正确数据是荒谬的 |
| P1-05 | 用 HTTP 200 + `code: 0` 表示部分成功，不用 4xx | 4xx 会让上游的重试机制再次推送，而部分成功重推也只会得到同样的部分成功，白白浪费 5 次重试 |

**错误码**：`"2202028"`、`"2202029"`、`"2202030"`、`"2202031"`、`"2202032"`、`"2202035"`、`"229001"`

#### API-34 P-08 采集批次状态查询

| 项 | 内容 |
|---|---|
| 方法路径 | `GET /internal/v1/m22/collect/status` |
| 权限 | 内部服务令牌 |
| 调用方 | 上游 M06-07 / M09-06（推送后自检）、M23 运维平台、运维排查 |
| 性能要求 | P95 ≤ 100ms |

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `batch_no` | string | 条件 | 采集批次号，三选一 |
| `push_batch_no` | string | 条件 | 上游推送批次号，三选一 |
| `task_code` | string | 条件 | 任务编码，返回该任务最近一批，三选一 |
| `period` | string | 否 | 配合 `task_code` 使用 |

**响应示例**

**业务逻辑**

1. 三种定位方式必须至少提供一个，全部缺失返回 400。
2. `batch_no` 精确匹配；`push_batch_no` 精确匹配（走 `uk_m22_collect_batch_push`）；`task_code` + `period` 取该任务该期间最新的批次。
3. 查不到时返回 `found = false`、`items = []`，**HTTP 仍为 200**（运维巡检时需要区分「接口错了」与「确实没采」）。
4. `failed_metrics` 最多返回前 50 条，超出时附 `truncated: true` 并在 `error_summary` 注明总数。
5. `lag_seconds` = 当前时刻 − 最近批次的 `updated_at`，用于判断采集是否积压。
6. 只读查询，不触发任何采集动作。

**错误码**：`"2202003"`（仅在显式给了 `batch_no` 且不存在时）、`"229001"`

### 6.5 Service 层核心逻辑

#### 6.5.1 PushService —— P-01 幂等与逐条校验

这是本子模块最关键的一段代码：幂等的三条分支（新建 / 重放 / 冲突）与逐条校验的容错边界都集中在这里。

```python
"""P-01 推送处理服务。

文件：app/services/m22/collect/push_service.py
"""
from __future__ import annotations

import hashlib
import json
from datetime import datetime
from decimal import Decimal, InvalidOperation
from typing import Any, Dict, List, Optional, Tuple

from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.errors import BizError
from app.core.time import now_local
from app.models.m22.collect import (
    CollectBatch,
    CollectUnclaimedMetric,
    FactMetric,
)
from app.schemas.m22.collect import (
    PushMetricItem,
    PushRejectedDetail,
    ReportPushRequest,
    ReportPushResponse,
)
from app.services.m22.collect.batch_no import next_batch_no
from app.services.m22.collect.metric_gateway import MetricDefCache
from app.services.m22.collect.event_bus import publish_collect_event

RATE_UNITS = frozenset({"RATE", "RATIO", "PERCENT"})


class PushService:
    """处理上游推送（P-01）。

    幂等三分支：
      1. push_batch_no 不存在           -> 新建批次并落库
      2. 存在且 push_batch_hash 相同    -> 幂等重放，返回首次结果
      3. 存在且 push_batch_hash 不同    -> 抛 PUSH_BATCH_CONFLICT
    """

    def __init__(self, db: AsyncSession) -> None:
        self.db = db

    # ---------------- 对外入口 ----------------
    async def push(self, payload: ReportPushRequest, trace_id: str) -> ReportPushResponse:
        self._assert_metrics_shape(payload)
        content_hash = self._content_hash(payload)

        existing = await self._find_batch_by_push_no(payload.push_batch_no)
        if existing is not None:
            return await self._replay_or_conflict(existing, content_hash, trace_id)

        return await self._create_and_apply(payload, content_hash, trace_id)

    # ---------------- 入口校验 ----------------
    @staticmethod
    def _assert_metrics_shape(payload: ReportPushRequest) -> None:
        if not payload.metrics:
            raise BizError("2202029", "推送指标列表为空")

        seen: set = set()
        for item in payload.metrics:
            key = (item.metric_code, item.dept_id)
            if key in seen:
                raise BizError(
                    "2202030",
                    f"推送内指标重复：{item.metric_code} / dept_id={item.dept_id}",
                )
            seen.add(key)

    # ---------------- 内容指纹 ----------------
    @staticmethod
    def _content_hash(payload: ReportPushRequest) -> str:
        """对 metrics 排序后规范化序列化再取 SHA-256。

        刻意排除的字段：
          - pushed_at：每次推送都会变，纳入指纹会让重试永远判为冲突
          - trace_id：同理，每次请求都不同
        排序键用 (metric_code, dept_id)，保证「同样的数据无论上游按什么顺序
        塞进数组，都得到同一个指纹」。
        """
        ordered = sorted(payload.metrics, key=lambda m: (m.metric_code, m.dept_id or 0))
        norm: List[Dict[str, Any]] = []
        for m in ordered:
            norm.append(
                {
                    "metric_code": m.metric_code,
                    "dept_id": m.dept_id,
                    "value": None if m.value is None else format(Decimal(str(m.value)), "f"),
                    "unit": m.unit,
                    "target": None if m.target is None else format(Decimal(str(m.target)), "f"),
                }
            )
        raw = json.dumps(norm, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
        return hashlib.sha256(raw.encode("utf-8")).hexdigest()

    # ---------------- 幂等分支 ----------------
    async def _find_batch_by_push_no(self, push_batch_no: str) -> Optional[CollectBatch]:
        stmt = select(CollectBatch).where(
            CollectBatch.push_batch_no == push_batch_no,
            CollectBatch.is_deleted.is_(False),
        )
        return (await self.db.execute(stmt)).scalar_one_or_none()

    async def _replay_or_conflict(
        self,
        existing: CollectBatch,
        content_hash: str,
        trace_id: str,
    ) -> ReportPushResponse:
        if existing.push_batch_hash != content_hash:
            raise BizError(
                "2202028",
                "同一推送批次号已存在不同内容",
                detail={
                    "push_batch_no": existing.push_batch_no,
                    "collect_batch_no": existing.batch_no,
                    "first_pushed_at": existing.created_at.strftime("%Y-%m-%d %H:%M:%S"),
                },
            )

        # 幂等重放：不落库、不改事实表，从批次头回读首次结果
        return ReportPushResponse(
            push_batch_no=existing.push_batch_no,
            accepted=existing.metric_success,
            rejected=existing.metric_rejected,
            rejected_detail=self._load_rejected_detail(existing),
            unclaimed=existing.metric_unclaimed,
            idempotent_replay=True,
            collect_batch_no=existing.batch_no,
            fact_written=existing.fact_inserted + existing.fact_updated,
            fact_upsert_skipped=existing.fact_skipped,
        )

    @staticmethod
    def _load_rejected_detail(batch: CollectBatch) -> List[PushRejectedDetail]:
        """首次推送时的拒绝明细存在 attach_snap 里，原样返回。"""
        snap = batch.attach_snap or {}
        items = snap.get("rejected_detail") or []
        return [PushRejectedDetail(**item) for item in items]

    # ---------------- 正常落库 ----------------
    async def _create_and_apply(
        self,
        payload: ReportPushRequest,
        content_hash: str,
        trace_id: str,
    ) -> ReportPushResponse:
        metric_defs = await MetricDefCache(self.db).bulk_get(
            [m.metric_code for m in payload.metrics]
        )

        batch = CollectBatch(
            batch_no=await next_batch_no(self.db, prefix="CB"),
            push_batch_no=payload.push_batch_no,
            push_batch_hash=content_hash,
            task_code=None,
            source_module=payload.source_module,
            source_submodule=payload.source_submodule,
            granularity=payload.granularity,
            period=payload.period,
            trigger_mode="PUSH",
            collect_status="RUNNING",
            source_status="COMPLETE",
            metric_total=len(payload.metrics),
            started_at=now_local(),
            trace_id=trace_id,
        )
        self.db.add(batch)
        await self.db.flush()

        accepted = 0
        fact_written = 0
        rejected_detail: List[PushRejectedDetail] = []
        unclaimed = 0

        for index, item in enumerate(payload.metrics):
            reason = self._validate_one(item, metric_defs)
            if reason is not None:
                code, detail_text = reason
                rejected_detail.append(
                    PushRejectedDetail(
                        index=index,
                        metric_code=item.metric_code,
                        dept_id=item.dept_id,
                        reason=code,
                        error_code=f"2202{self._reason_seq(code):03d}",
                        detail=detail_text,
                    )
                )
                if code == "METRIC_NOT_REGISTERED":
                    unclaimed += 1
                    await self._write_unclaimed(item, payload, trace_id)
                continue

            inserted = await self._upsert_fact(item, payload, batch.batch_no)
            accepted += 1
            fact_written += 1 if inserted else 0

        batch.metric_success = accepted
        batch.metric_rejected = len(rejected_detail)
        batch.metric_unclaimed = unclaimed
        batch.fact_inserted = fact_written
        batch.fact_updated = accepted - fact_written
        batch.fact_skipped = 0
        batch.finished_at = now_local()
        batch.collect_status = "COMPLETED" if not rejected_detail else "PARTIAL"
        batch.source_status = "COMPLETE" if not rejected_detail else "PARTIAL"
        batch.attach_snap = {
            "rejected_detail": [d.model_dump() for d in rejected_detail],
        }
        await self.db.commit()

        await publish_collect_event(
            "m22.collect.completed",
            {
                "batch_no": batch.batch_no,
                "period": batch.period,
                "metric_count": accepted,
                "status": batch.collect_status,
            },
        )

        return ReportPushResponse(
            push_batch_no=payload.push_batch_no,
            accepted=accepted,
            rejected=len(rejected_detail),
            rejected_detail=rejected_detail,
            unclaimed=unclaimed,
            idempotent_replay=False,
            collect_batch_no=batch.batch_no,
            fact_written=fact_written,
            fact_upsert_skipped=0,
        )

    # ---------------- 逐条校验 ----------------
    @staticmethod
    def _validate_one(
        item: PushMetricItem,
        metric_defs: Dict[str, Any],
    ) -> Optional[Tuple[str, str]]:
        """返回 None 表示通过；返回 (reason, detail) 表示拒绝。

        注意：value 为 None 不算拒绝 —— 上游明确给了 null 表示「确实采不到」，
        应当落 source_status='PARTIAL' 的空值行，而不是当作错误丢掉。
        """
        definition = metric_defs.get(item.metric_code)
        if definition is None or definition.get("status") != "ACTIVE":
            return (
                "METRIC_NOT_REGISTERED",
                "指标未在指标中心注册，已写入待认领指标表",
            )

        if item.unit != definition.get("metric_unit"):
            return (
                "UNIT_MISMATCH",
                f"注册单位为 {definition.get('metric_unit')}，本次传入 {item.unit}",
            )

        if item.value is not None and item.unit in RATE_UNITS:
            try:
                ratio = Decimal(str(item.value))
            except InvalidOperation:
                return ("VALUE_OUT_OF_RANGE", "比率值无法解析为数值")
            if ratio < Decimal("0") or ratio > Decimal("1"):
                return ("VALUE_OUT_OF_RANGE", "比率值必须落在 [0, 1] 区间内")

        return None

    @staticmethod
    def _reason_seq(reason: str) -> int:
        mapping = {
            "METRIC_NOT_REGISTERED": 31,
            "UNIT_MISMATCH": 32,
            "VALUE_OUT_OF_RANGE": 35,
        }
        return mapping.get(reason, 1)

    # ---------------- 落库 ----------------
    async def _upsert_fact(
        self,
        item: PushMetricItem,
        payload: ReportPushRequest,
        collect_batch_no: str,
    ) -> bool:
        """按 (metric_code, period, dept_id, biz_dim) upsert，返回是否为新插入。"""
        biz_dim = "NONE" if item.dept_id is not None else "SCOPE=ALL"
        stmt = select(FactMetric).where(
            FactMetric.metric_code == item.metric_code,
            FactMetric.period == payload.period,
            FactMetric.dept_id == (item.dept_id if item.dept_id is not None else -1),
            FactMetric.biz_dim == biz_dim,
        )
        fact = (await self.db.execute(stmt)).scalar_one_or_none()

        source_status = "COMPLETE" if item.value is not None else "PARTIAL"
        if fact is None:
            fact = FactMetric(
                metric_code=item.metric_code,
                metric_version=1,
                period=payload.period,
                granularity=payload.granularity,
                dept_id=item.dept_id if item.dept_id is not None else -1,
                biz_dim=biz_dim,
                metric_value=item.value,
                metric_unit=item.unit,
                target_value=item.target,
                source_module=payload.source_module,
                source_api="P-01",
                collect_batch_no=collect_batch_no,
                source_status=source_status,
                collected_at=now_local(),
                data_version=1,
            )
            self.db.add(fact)
            return True

        fact.metric_value = item.value
        fact.target_value = item.target
        fact.source_status = source_status
        fact.collect_batch_no = collect_batch_no
        fact.collected_at = now_local()
        fact.data_version = (fact.data_version or 0) + 1
        return False

    async def _write_unclaimed(
        self,
        item: PushMetricItem,
        payload: ReportPushRequest,
        trace_id: str,
    ) -> None:
        self.db.add(
            CollectUnclaimedMetric(
                unclaimed_no=await next_batch_no(self.db, prefix="UM"),
                push_batch_no=payload.push_batch_no,
                source_module=payload.source_module,
                source_submodule=payload.source_submodule,
                metric_code=item.metric_code,
                dept_id=item.dept_id,
                granularity=payload.granularity,
                period=payload.period,
                metric_value=item.value,
                metric_unit=item.unit,
                target_value=item.target,
                claim_status="PENDING",
                first_pushed_at=now_local(),
                trace_id=trace_id,
            )
        )
```

```python
"""采集批次服务：发起、执行、锁与降级判定。

文件：app/services/m22/collect/batch_service.py
"""
from __future__ import annotations

from datetime import datetime
from decimal import Decimal
from typing import Any, Dict, List, Optional

from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.errors import BizError
from app.core.lock import RedisLock
from app.core.time import now_local
from app.models.m22.collect import CollectBatch, CollectBatchItem, CollectFailure, CollectTask
from app.schemas.m22.collect import CollectBatchCreate, CollectBatchOut
from app.services.m22.collect.batch_no import next_batch_no
from app.services.m22.collect.upstream import UpstreamClient, UpstreamError
from app.services.m22.collect.event_bus import publish_collect_event
from app.tasks.m22.collect import execute_collect_batch

LOCK_TTL_SECONDS = 1800


class BatchService:
    def __init__(self, db: AsyncSession) -> None:
        self.db = db

    async def create_batch(
        self,
        payload: CollectBatchCreate,
        operator: Any,
        idempotency_key: Optional[str],
        trace_id: str,
    ) -> CollectBatchOut:
        task = await self._load_task(payload.task_code)
        if not task.enabled:
            raise BizError("2202002", f"采集任务 {task.task_code} 已停用")

        if payload.batch_type in ("RECOLLECT", "RERUN"):
            if not payload.recollect_reason or not payload.recollect_reason.strip():
                raise BizError("2202017", "补采或重算必须说明原因")
            if payload.batch_type == "RERUN" and not operator.has_permission("m22:collect:approve"):
                raise BizError("2202018", "重算需要审批权限")

        lock_key = f"m22:lock:collect:{task.task_code}:{payload.period}:{payload.granularity}"
        lock = RedisLock(lock_key, ttl=LOCK_TTL_SECONDS)
        if not await lock.acquire():
            raise BizError("2202007", "该期间正在采集中，请稍后重试")

        try:
            batch = CollectBatch(
                batch_no=await next_batch_no(self.db, prefix="CB"),
                task_code=task.task_code,
                source_module=task.source_module,
                source_submodule=task.source_submodule,
                granularity=payload.granularity,
                period=payload.period,
                trigger_mode=payload.batch_type,
                collect_status="PENDING",
                source_status="COMPLETE",
                metric_total=0,
                parent_batch_no=payload.parent_batch_no,
                recollect_reason=payload.recollect_reason,
                operator_id=operator.user_id,
                trace_id=trace_id,
            )
            self.db.add(batch)
            await self.db.commit()
        except Exception:
            await lock.release()
            raise

        # 真正的采集丢给 Celery，HTTP 立即返回批次号
        execute_collect_batch.delay(batch.batch_no)
        return CollectBatchOut.model_validate(batch)

    async def execute(self, batch_no: str) -> None:
        """由 Celery worker 调用。

        完整性判定规则（详见 §3.4.5）：
          - 全部明细成功且值均非空 -> COMPLETE
          - 存在成功但值缺失，或有可重试失败 -> PARTIAL
          - 全部失败 -> FAILED
        绝不把缺失值写成 0。
        """
        batch = await self._load_batch(batch_no)
        task = await self._load_task(batch.task_code)
        client = UpstreamClient()

        success = 0
        failed = 0
        missing_value = 0
        missing_sources: List[str] = []

        for metric_code in task.metric_codes:
            try:
                result = await client.call(
                    source_api=task.source_api,
                    metric_code=metric_code,
                    period=batch.period,
                    granularity=batch.granularity,
                    dept_scope=task.dept_scope,
                    dept_ids=task.dept_ids,
                )
            except UpstreamError as exc:
                failed += 1
                missing_sources.append(metric_code)
                await self._record_failure(batch, metric_code, exc)
                continue

            for row in result.rows:
                if row.value is None:
                    missing_value += 1
                await self._upsert_fact_and_item(batch, metric_code, row)
                success += 1

        total = success + failed
        if failed == 0 and missing_value == 0:
            source_status = "COMPLETE"
            collect_status = "COMPLETED"
            degraded_reason = None
        elif success == 0 and failed > 0:
            source_status = "FAILED"
            collect_status = "FAILED"
            degraded_reason = "全部指标采集失败"
        else:
            source_status = "PARTIAL"
            collect_status = "PARTIAL"
            degraded_reason = f"缺失 {len(missing_sources)} 个指标来源"

        batch.metric_total = total
        batch.metric_success = success
        batch.metric_failed = failed
        batch.source_status = source_status
        batch.collect_status = collect_status
        batch.degraded_reason = degraded_reason
        batch.missing_sources = missing_sources or None
        batch.finished_at = now_local()
        await self.db.commit()

        event = "m22.collect.completed" if collect_status != "FAILED" else "m22.collect.failed"
        await publish_collect_event(
            event,
            {
                "batch_no": batch.batch_no,
                "period": batch.period,
                "metric_count": success,
                "status": collect_status,
                "failed_metric": missing_sources[:1],
                "reason": degraded_reason,
            },
        )

    async def _record_failure(self, batch: CollectBatch, metric_code: str, exc: UpstreamError) -> None:
        retryable = exc.is_retryable()
        self.db.add(
            CollectFailure(
                failure_no=await next_batch_no(self.db, prefix="FL"),
                collect_batch_no=batch.batch_no,
                task_code=batch.task_code,
                metric_code=metric_code,
                period=batch.period,
                dept_id=None,
                failure_stage=exc.stage,
                error_code=exc.biz_code,
                upstream_code=exc.upstream_code,
                http_status=exc.http_status,
                upstream_trace_id=exc.upstream_trace_id,
                failure_msg=str(exc)[:500],
                retryable=retryable,
                retry_seq=0,
                max_retry=5,
                backoff_s=30,
                retry_status="WAITING" if retryable else "EXHAUSTED",
                next_retry_at=now_local() if not retryable else None,
            )
        )

    async def _load_task(self, task_code: str) -> CollectTask:
        stmt = select(CollectTask).where(
            CollectTask.task_code == task_code,
            CollectTask.is_deleted.is_(False),
        )
        task = (await self.db.execute(stmt)).scalar_one_or_none()
        if task is None:
            raise BizError("2202001", f"采集任务不存在：{task_code}")
        return task

    async def _load_batch(self, batch_no: str) -> CollectBatch:
        stmt = select(CollectBatch).where(
            CollectBatch.batch_no == batch_no,
            CollectBatch.is_deleted.is_(False),
        )
        batch = (await self.db.execute(stmt)).scalar_one_or_none()
        if batch is None:
            raise BizError("2202003", f"采集批次不存在：{batch_no}")
        return batch
```

#### 6.5.3 CollectStatusService —— P-08 状态查询

```python
"""P-08 采集批次状态查询。

文件：app/services/m22/collect/status_service.py
"""
from __future__ import annotations

from typing import List, Optional

from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.errors import BizError
from app.core.time import now_local
from app.models.m22.collect import CollectBatch, CollectBatchItem
from app.schemas.m22.collect import CollectStatusItem, CollectStatusResponse

MAX_FAILED_METRICS = 50


class CollectStatusService:
    def __init__(self, db: AsyncSession) -> None:
        self.db = db

    async def query(
        self,
        batch_no: Optional[str],
        push_batch_no: Optional[str],
        task_code: Optional[str],
        period: Optional[str],
    ) -> CollectStatusResponse:
        if not any([batch_no, push_batch_no, task_code]):
            raise BizError("2202003", "必须指定 batch_no / push_batch_no / task_code 之一")

        batches = await self._locate(batch_no, push_batch_no, task_code, period)
        if not batches:
            return CollectStatusResponse(found=False, items=[], generated_at=now_local())

        items: List[CollectStatusItem] = []
        for batch in batches:
            failed_metrics = await self._failed_metrics(batch.batch_no)
            items.append(
                CollectStatusItem(
                    batch_no=batch.batch_no,
                    task_code=batch.task_code,
                    period=batch.period,
                    granularity=batch.granularity,
                    collect_status=batch.collect_status,
                    source_status=batch.source_status,
                    metric_total=batch.metric_total,
                    metric_success=batch.metric_success,
                    metric_failed=batch.metric_failed,
                    fact_written=batch.fact_inserted + batch.fact_updated,
                    started_at=batch.started_at,
                    finished_at=batch.finished_at,
                    elapsed_ms=self._elapsed_ms(batch),
                    retry_count=batch.retry_count,
                    push_batch_no=batch.push_batch_no,
                    failed_metrics=failed_metrics[:MAX_FAILED_METRICS],
                    truncated=len(failed_metrics) > MAX_FAILED_METRICS,
                    error_summary=batch.degraded_reason,
                    updated_at=batch.updated_at,
                )
            )

        latest = max(b.updated_at for b in batches)
        return CollectStatusResponse(
            found=True,
            items=items,
            generated_at=now_local(),
            lag_seconds=int((now_local() - latest).total_seconds()),
        )

    async def _locate(
        self,
        batch_no: Optional[str],
        push_batch_no: Optional[str],
        task_code: Optional[str],
        period: Optional[str],
    ) -> List[CollectBatch]:
        stmt = select(CollectBatch).where(CollectBatch.is_deleted.is_(False))
        if batch_no:
            stmt = stmt.where(CollectBatch.batch_no == batch_no)
        elif push_batch_no:
            stmt = stmt.where(CollectBatch.push_batch_no == push_batch_no)
        else:
            stmt = stmt.where(CollectBatch.task_code == task_code)
            if period:
                stmt = stmt.where(CollectBatch.period == period)
            stmt = stmt.order_by(CollectBatch.created_at.desc()).limit(1)
        return list((await self.db.execute(stmt)).scalars().all())

    async def _failed_metrics(self, batch_no: str) -> List[str]:
        stmt = (
            select(CollectBatchItem.metric_code)
            .where(
                CollectBatchItem.collect_batch_no == batch_no,
                CollectBatchItem.item_status.in_(("FAILED", "REJECTED")),
            )
            .distinct()
        )
        return [row[0] for row in (await self.db.execute(stmt)).all()]

    @staticmethod
    def _elapsed_ms(batch: CollectBatch) -> Optional[int]:
        if batch.started_at is None:
            return None
        end = batch.finished_at or now_local()
        return int((end - batch.started_at).total_seconds() * 1000)
```

## 7. 缓存与异步任务

### 7.1 Redis 缓存设计

M22-02 的缓存分三类：**字典类**（几乎不变，长 TTL）、**结果类**（可短暂陈旧，短 TTL + 事件失效）、**控制类**（锁与进度，非缓存）。命名遵循共享规范 §14，本子模块统一前缀 `m22:collect:`。

| Key 模式 | 类型 | TTL | 内容 | 失效时机 | 估算容量 |
|---|---|---|---|---|---|
| `m22:collect:dashboard:{yyyyMMdd}` | String(JSON) | 60 秒 | 工作台概况 | 60 秒自然过期 + `m22.collect.completed` 事件主动删 | 每日期 1 个，约 2 KB |
| `m22:collect:upstream_api_list` | String(JSON) | 1 天 | 上游接口白名单 | 版本发布时随进程重启失效 | 1 个，约 80 KB |
| `m22:collect:metric_def:{metric_code}` | String(JSON) | 10 分钟 | 指标定义（单位、状态、口径版本） | 订阅 `m22.metric.changed` 事件删除 | 按指标数，约 500 个 |
| `m22:collect:metric_def:bulk` | String(JSON) | 10 分钟 | 全量指标字典（供批量校验用） | 同上 | 1 个，约 1.5 MB |
| `m22:collect:dept_tree` | String(JSON) | 1 小时 | 科室树（数据权限用） | 订阅 `m01.dept.changed` 事件删除 | 1 个，约 200 KB |
| `m22:collect:health:{source_api}:{yyyyMMddHH}` | String(JSON) | 2 小时 | 单接口当小时健康度 | 自然过期 | 每接口每小时 1 个 |
| `m22:collect:batch_progress:{batch_no}` | Hash | 1 小时 | 批次进度（已完成指标数 / 总数） | 批次终态后保留 1 小时供前端刷新 | 并发批次数，约 20 个 |
| `m22:lock:collect:{task_code}:{period}:{granularity}` | String | 1800 秒 | 采集互斥锁 | 采集结束主动删除 | 并发采集数 |
| `m22:idem:collect:{idempotency_key}` | String(JSON) | 24 小时 | 写接口幂等结果 | 自然过期 | 按日调用量 |

**缓存一致性策略**

1. **字典类只读不改**：指标定义、科室树的写操作都在 M22-01 / M01，M22-02 只订阅变更事件删缓存，不做双写。
2. **结果类允许短暂陈旧**：工作台概况 60 秒内不一致可接受（页面本身也在轮询）。
3. **事实数据不缓存**：`/facts` 查询直接打库。事实表按月分区 + 组合索引，单次查询已在 100ms 内，加缓存反而引入「缓存里是校准前的值」这类难以排查的问题。
4. **缓存穿透防护**：指标定义缓存未命中且上游也查不到时，写入 `{"__miss__": true}` 占位 60 秒，避免同一批请求反复打 M22-01。

### 7.2 Celery 异步任务

| 任务名 | 队列 | 触发方式 | 超时 | 最大重试 | 说明 |
|---|---|---|---|---|---|
| `m22.collect.execute` | `m22_collect` | API-13 投递、定时调度投递 | 900 秒 | 0（失败由重试任务接手） | 执行一个采集批次 |
| `m22.collect.retry` | `m22_retry` | 定时扫描 `next_retry_at` | 300 秒 | 0 | 执行单条失败的重试 |
| `m22.collect.quality_check` | `m22_collect` | 批次完成后链式触发 | 600 秒 | 0 | 跑质量规则 |
| `m22.collect.aggregate` | `m22_collect` | `m16.daily.frozen` / `m17.period.closed` 事件 | 600 秒 | 3 | 日结 / 月结汇总 |
| `m22.collect.health_rollup` | `m22_ops` | 每小时定时 | 120 秒 | 2 | 汇总上游健康度 |
| `m22.collect.partition_maintain` | `m22_ops` | 每月 1 日 02:00 | 120 秒 | 2 | 预建未来 3 个月分区 |
| `m22.collect.unclaimed_replay` | `m22_collect` | 订阅指标注册事件 | 120 秒 | 2 | 回放待认领指标 |

**任务幂等与失败处理**

- `m22.collect.execute` 的任务 ID 固定为 `collect:{batch_no}`，同一批次重复投递会被 Celery 结果后端去重。
- 采集锁在任务开始处再次校验；若锁已被他人持有（例如上一批次卡死未释放），任务立即退出并把批次置 `FAILED`，`degraded_reason = '锁被占用'`，不排队等待。
- `acks_late = True` + `task_reject_on_worker_lost = True`，worker 崩溃时任务回队列。
- 任何任务都**不允许**把异常吞掉后返回成功；异常必须记录 `m22_collect_failure` 后抛出，让 Celery 侧可见。

```python
"""M22-02 Celery 任务定义。

文件：app/tasks/m22/collect.py

from __future__ import annotations

    """Celery worker 是同步上下文，这里用独立事件循环跑 async service。"""
    return asyncio.get_event_loop().run_until_complete(coro)


@shared_task(
    name="m22.collect.execute",
    queue="m22_collect",
    time_limit=900,
    soft_time_limit=840,
    acks_late=True,
    task_reject_on_worker_lost=True,
)

    async def _inner() -> Dict[str, Any]:
        async with AsyncSessionLocal() as db:
            await BatchService(db).execute(batch_no)

    return _run(_inner())


@shared_task(name="m22.collect.quality_check", queue="m22_collect", time_limit=600)

    return _run(_inner())


@shared_task(name="m22.collect.retry", queue="m22_retry", time_limit=300)
def retry_due_failures(limit: int = 100) -> Dict[str, Any]:
    async def _inner() -> Dict[str, Any]:
        async with AsyncSessionLocal() as db:
            done = await RetryService(db).dispatch_due(limit=limit)

    return _run(_inner())


@shared_task(name="m22.collect.aggregate", queue="m22_collect", time_limit=600)
def aggregate_period(period: str, granularity: str, metric_codes: List[str]) -> Dict[str, Any]:
    async def _inner() -> Dict[str, Any]:

                period=period,
                granularity=granularity,

    return _run(_inner())


@shared_task(name="m22.collect.health_rollup", queue="m22_ops", time_limit=120)
def rollup_source_health() -> Dict[str, Any]:
    async def _inner() -> Dict[str, Any]:

        return {"rows": n}

    return _run(_inner())


@shared_task(name="m22.collect.partition_maintain", queue="m22_ops", time_limit=120)

    return _run(_inner())
```

### 7.3 APScheduler 定时任务

| 作业 ID | 触发规则 | 执行内容 | 说明 |
|---|---|---|---|
| `m22_collect_sync_tasks` | 每 5 分钟 | 把 `collect_task` 表里 `trigger_type = 'CRON'` 且启用的任务同步到调度器 | 任务表是真相源，调度器只是执行器 |

**调度器高可用**：多个 API 实例共用同一 Redis 作为 APScheduler 的 jobstore，并启用 `max_instances=1` + `coalesce=True`，避免多实例重复触发。真正执行前再由 `m22:lock:scheduler:{job_id}` 二次抢占。

**任务同步策略**：`collect_task` 表的 `next_run_at` 由调度器在触发后回写；运维在 P02 页面看的是表里的值而不是内存里的值，保证重启后视图不丢。

## 8. 业务规则与校验

本章每条规则都标注了违反时返回的错误码，第 6 章接口详述里的校验步骤是这里的落地实现。

### 8.1 编码规则

| 规则编号 | 规则 | 违反时错误码 |
|---|---|---|
| R-01-01 | 采集任务编码 `task_code` 格式为 `T_{模块}_{主题}`，大写字母、数字、下划线，长度 4~64 | `"2202006"` |
| R-01-02 | 采集批次号格式 `CB` + `yyyyMMdd` + `-` + 4 位序号，序号当日从 0001 递增，**不跨日续号** | `"229001"` |
| R-01-03 | 质量问题编号 `QC` + `yyyyMMdd` + `-` + 4 位序号 | `"229001"` |
| R-01-04 | 校准单号 `CL` + `yyyyMMdd` + `-` + 4 位序号 | `"229001"` |
| R-01-05 | 采集日志号 `LG` + `yyyyMMdd` + `-` + 6 位序号（日志量大，用 6 位） | `"229001"` |
| R-01-06 | 待认领指标编号 `UM` + `yyyyMMdd` + `-` + 4 位序号 | `"229001"` |
| R-01-07 | 失败记录编号 `FL` + `yyyyMMdd` + `-` + 6 位序号 | `"229001"` |
| R-01-08 | 编号生成走 Redis 计数器 `m22:code:{prefix}:{yyyyMMdd}`，`INCR` 后拼接；计数器当天首次使用时 `EXPIREAT` 到次日 00:05 | `"229001"` |

**编号不复用的理由**：批次号是审计追溯的主键。如果删除批次后复用序号，同一批次号可能在不同时间指代不同数据，日志与事件里的 `batch_no` 就无法回溯。

### 8.2 唯一性约束

| 规则编号 | 约束 | 违反时错误码 |
|---|---|---|
| R-02-01 | `m22_collect_task.task_code` 全局唯一（`is_deleted = FALSE` 部分索引） | `"2202006"` |
| R-02-02 | `m22_collect_batch.batch_no` 全局唯一 | `"229001"` |
| R-02-03 | `m22_collect_batch.push_batch_no` 全局唯一（推送批次才有值） | `"2202028"` |
| R-02-04 | `m22_fact_metric` 的 `(metric_code, period, dept_id, biz_dim)` 唯一（含 `period_month` 构成分区内唯一） | `"229001"` |
| R-02-05 | `m22_collect_batch_item` 的 `(collect_batch_no, metric_code, dept_id, biz_dim)` 唯一 | `"229001"` |
| R-02-06 | `m22_collect_source_health` 的 `(source_api, stat_hour)` 唯一 | `"229001"` |
| R-02-07 | `m22_collect_unclaimed_metric` 的 `(push_batch_no, metric_code, dept_id)` 唯一 | `"229001"` |

**唯一约束的分工**：数据库唯一索引是最后一道防线；Service 层在写入前先查一次，是为了返回业务语义清晰的错误码而不是把 `IntegrityError` 翻译成 500。

### 8.3 状态流转规则

| 规则编号 | 规则 | 违反时错误码 |
|---|---|---|
| R-03-01 | 批次 `PENDING -> RUNNING -> COMPLETED / PARTIAL / FAILED`，`PENDING` 可直接转 `FAILED` | `"2202004"` |
| R-03-02 | 终态（`COMPLETED`/`PARTIAL`/`FAILED`）批次不可再流转，只能通过新建补采批次修正 | `"2202004"` |
| R-03-03 | 只有 `RUNNING` 状态可终止 | `"2202005"` |
| R-03-04 | 任务停用前不得有 `RUNNING` 批次 | `"2202037"` |
| R-03-05 | 失败记录 `WAITING -> RETRYING -> RECOVERED / EXHAUSTED / ABANDONED`；`EXHAUSTED` 可被人工重置回 `RETRYING` | `"2202020"` |
| R-03-06 | 校准单 `DRAFT -> PENDING -> APPROVED -> APPLIED`，`PENDING` 可转 `REJECTED`，`APPLIED` 可转 `REVOKED` | `"2202040"` |
| R-03-07 | 质量问题 `OPEN -> ACKED -> FIXED / IGNORED`，只能从 `OPEN` 或 `ACKED` 出发 | `"2202023"` |

**状态机不落数据库的理由**：PostgreSQL 里 `CHECK` 约束只能校验单行单列取值，跨行状态流转的前态校验必须在 Service 层用 `SELECT ... FOR UPDATE` 读取当前行再判断。数据库只做「取值必须在枚举内」这一层。

**关于 R-04-16 的论证**：lead 提出的两种方案中，本项目采用「可空 + 标志位」而非「PARTIAL 时禁止给值」。理由是：部分成功的场景下**已经有 88/96 个科室的真实值**，此时把整个指标标成 NULL 会让报表完全不可用；正确做法是给出值但明确标注「这是基于部分来源估算的」，报表层可以选择不展示或加角标。禁止给值等于把「部分可用」降级成「完全不可用」，信息损失更大。

| 规则编号 | 规则 | 违反时错误码 |
|---|---|---|

| R-06-02 | 采集批次、批次明细、事实行、失败记录、日志**不允许删除**，只能通过校准修正 | `"229001"` |

### 8.7 并发控制

| 规则编号 | 场景 | 控制手段 | 违反时错误码 |
|---|---|---|---|
| R-07-01 | 同一任务同期间并发采集 | Redis 分布式锁 `m22:lock:collect:{task_code}:{period}:{granularity}`，TTL 1800 秒 | `"2202007"` |
| R-07-02 | 同一事实行并发 upsert | PG 唯一约束 + `INSERT ... ON CONFLICT DO UPDATE`，冲突时以 `collected_at` 较新者为准 | `"229001"` |
| R-07-03 | 任务配置并发修改 | 乐观锁 `version` 字段，`UPDATE ... WHERE version = ?` 影响行数为 0 即冲突 | `"2202010"` |
| R-07-04 | 校准单并发审批 | `SELECT ... FOR UPDATE` 锁单行，审批前重读状态 | `"2202040"` |
| R-07-05 | 调度器多实例重复触发 | APScheduler `max_instances=1` + Redis `m22:lock:scheduler:{job_id}` 二次抢占 | `"229001"` |

**锁粒度选择**：锁到 `(task_code, period, granularity)` 而不是全局，是为了让不同任务的采集可以并行；也不锁到单个指标，因为那样会让一个任务的上百个指标串行化，失去并发意义。

该差异已向 lead 报告，等待 M16 侧在下一版文档中修正登记。

**上游重试行为对本契约的影响**

两个调用方都是「超时 10 秒 + 重试 5 次」的配置。这直接决定了幂等设计的必要性：

- 若 M22 处理耗时超过 10 秒（例如大量指标 upsert），调用方会超时并重推同一个 `push_batch_no`；
- 若 M22 不幂等，5 次重试会产生 5 个批次、5 倍事实行写入、5 条 `m22.collect.completed` 事件；
- 因此 P-01 必须在**落库前**完成幂等判定，且判定要快（走 `uk_m22_collect_batch_push` 索引，P95 在 5ms 内）。

**P-08 的时间语义**

`lag_seconds` = 当前时刻 − 该批次 `updated_at`。运维平台上看到 `lag_seconds` 持续增大说明采集积压。上游推送后可以立即调 P-08 确认落库结果，此时 `lag_seconds` 应接近 0。

| `m22.collect.completed` | 批次状态转为 `COMPLETED` 或 `PARTIAL` | `batch_no`、`period`、`metric_count`、`status` | M22-03（触发报表刷新）、M22-08（驾驶舱刷新）、M23（运维看板） | 至少一次，消费方必须幂等 |
| `m22.collect.failed` | 批次状态转为 `FAILED` | `batch_no`、`period`、`failed_metric`、`reason` | M23（告警）、M22-02 自身（告警扫描） | 至少一次 |
| `m22.collect.partial` | 批次状态转为 `PARTIAL` 且有事实行标为估算 | `batch_no`、`period`、`missing_sources` | M22-03（报表加「数据不完整」角标） | 至少一次 |
| `m22.fact.changed` | 事实行被采集覆盖或校准修改 | `metric_codes`、`period`、`data_version` | M22-03、M22-04~08（缓存失效） | 至少一次 |
| `m22.collect.unclaimed` | 待认领指标写入 | `metric_code`、`source_module`、`count` | M22-01（管理员待办）、M23 | 至少一次 |

**载荷示例**

```json
{
  "event": "m22.collect.completed",
  "event_id": "evt-7f3a2c91",
  "occurred_at": "2026-10-31 06:20:04",
  "trace_id": "a1b2c3d4e5f60718",
  "payload": {
    "batch_no": "CB20261031-0008",
    "period": "2026-10-31",
    "metric_count": 96,
    "status": "COMPLETED"
  }

```

**发布可靠性**：事件先写入本地 `outbox` 表（与业务写在同一事务），再由独立投递器扫表发到消息总线，保证「业务成功但事件丢失」不会发生。投递失败按 1/5/30 秒退避重试，24 小时未成功的进死信队列并告警。

### 10.4 事件订阅

| 事件名 | 发布方 | 本模块处理 | 幂等键 | 失败处理 |
|---|---|---|---|---|
| `m16.daily.frozen` | M16-09 | 触发指定日期的日结汇总采集（`aggregate_period`，`granularity = DAILY`） | `(event, period)` | 进重试队列，最多 3 次 |
| `m17.period.closed` | M17-05 | 触发该期间的月结汇总采集（`granularity = MONTHLY`） | `(event, period)` | 进重试队列，最多 3 次 |
| `m01.dept.changed` | M01 | 删除 `m22:collect:dept_tree` 缓存 | 无（幂等删除） | 记 WARN，靠 TTL 兜底 |
| `m01.subject.changed` | M01 | 删除科目映射缓存（供 M17 类指标使用） | 无 | 同上 |
| `m22.metric.registered` | M22-01 | 触发 `m22.collect.unclaimed_replay`，回放待认领指标 | `(metric_code, period)` | 进重试队列 |
| `m22.metric.changed` | M22-01 | 删除 `m22:collect:metric_def:*` 缓存 | 无 | 同上 |
| `m09.operation.completed` | M09 | 触发当日手术类指标的实时补采 | `(event, operation_id)` | 记 WARN |

**`m16.daily.frozen` 的处理细节**

M16-09 冻结某日账目后会发出该事件。M22-02 收到后：
1. 校验 `period` 是否是合法日期且不晚于今天，非法直接丢弃并记 ERROR；
2. 用幂等键 `(m16.daily.frozen, 2026-10-30)` 查 `m22_collect_log`，已处理过则直接返回（M16 可能因重投发多次）；
3. 查询 `collect_task` 中 `event_code = 'm16.daily.frozen'` 且启用的任务，逐个发起采集批次（`trigger_mode = 'EVENT'`）；
4. 采集是异步的，事件处理立即返回，不阻塞 M16 的冻结流程。

**订阅不使用「同步回调」的理由**：如果 M22 在事件处理里同步完成采集，M16 的日结冻结就会被 M22 的采集耗时拖住。事件语义应是「通知」而非「调用」。

## 11. 异常处理与日志

### 11.1 异常分类

| 类别 | 典型场景 | 处理策略 | 用户可见性 |
|---|---|---|---|
| **参数异常** | 字段缺失、格式错误、枚举越界 | 直接返回 400 + 对应错误码，不记 ERROR 日志 | 前端表单提示 |
| **业务异常** | 任务停用、批次已终态、锁冲突、指纹冲突 | 返回 4xx + 业务错误码，记 INFO 日志 | 前端 toast 提示 |
| **上游异常** | 超时、5xx、结构变更 | 记 `m22_collect_failure`，批次降级为 `PARTIAL`/`FAILED`，进重试 | 前端显示「部分数据未采集」 |
| **数据异常** | 唯一约束冲突、分区缺失 | 返回 500 + `"229001"` 或专用码，记 ERROR 并告警 | 前端显示「系统繁忙」 |
| **系统异常** | 数据库连接断、Redis 不可用 | 返回 500，记 CRITICAL 并告警 | 前端显示「系统繁忙」 |
| **未预期异常** | 未捕获的 Exception | 兜底中间件捕获，返回 `"229001"`，记 CRITICAL 带完整堆栈 | 前端显示「系统繁忙」，trace_id 供排查 |

**异常分层原则**：`BizError` 携带业务错误码，由全局异常处理器翻译成统一响应；其他异常一律翻译成 `"229001"` 并记录完整堆栈到日志，响应体**不返回堆栈**（防信息泄露）。

### 11.2 降级策略

| 场景 | 降级动作 | 数据完整性影响 | 恢复方式 |
|---|---|---|---|
| 上游接口超时 | 标 `source_status = 'FAILED'`，事实行落 NULL 值；批次降 `PARTIAL` | 该指标该期间缺失，报表显示「数据不完整」 | 重试成功或补采后自动恢复 |
| 上游全部失败 | 批次降 `FAILED`，发布 `m22.collect.failed` 事件 | 该期间完全无新增事实 | 人工补采 |
| M22-01 指标中心不可用 | 用 Redis 指标字典缓存（10 分钟）降级校验 | 无（缓存陈旧可能误判新指标） | 缓存过期后自动恢复 |
| Redis 不可用 | 采集锁降级为数据库行锁 `SELECT ... FOR UPDATE NOWAIT`；幂等降级为 DB 唯一索引 | 并发度下降但正确性不变 | Redis 恢复后自动切回 |
| 数据库主库不可用 | 写操作全部拒绝返回 503；读操作切只读副本 | 无法采集，但报表仍可读历史 | 主库恢复 |
| 消息总线不可用 | 事件进 outbox 表等待投递 | 报表刷新延迟，但事件不丢 | 总线恢复后补投 |
| 分区缺失 | 插入落到 DEFAULT 分区并告警 | 无（DEFAULT 分区兜底） | `partition_maintain` 任务补建 |

**降级红线**：任何降级都**不允许**把缺失值写 0、不允许把 `FAILED` 伪装成 `COMPLETE`、不允许吞掉异常返回成功。这是铁律 L-02 的直接体现。

### 11.3 日志规范

**结构化日志字段**

| 指标名 | 类型 | 说明 | 告警阈值 |
|---|---|---|---|
| `m22_collect_batch_total` | Counter | 批次总数（按 status、trigger_mode 标签） | — |
| `m22_collect_batch_duration_seconds` | Histogram | 批次耗时分布 | P95 > 300 秒告警 |
| `m22_collect_fact_written_total` | Counter | 写入事实行数（按 source_status） | — |
| `m22_collect_upstream_error_total` | Counter | 上游调用失败数（按 source_api、error_code） | 5 分钟内 > 10 次告警 |

| `m22_collect_quality_open` | Gauge | 未处置质量问题数 | > 50 告警 |

## 附录 F 术语表与版本历史

### F.1 术语表

| 术语 | 英文 / 缩写 | 定义 |
|---|---|---|
| 采集任务 | Collect Task | 一个「从哪个接口、取哪些指标、多久取一次」的配置单元 |
| 采集批次 | Collect Batch | 一次采集执行的实体，有唯一批次号 `CB...`，是审计追溯的主键 |
| 批次明细 | Batch Item | 批次内单个指标的单次取数结果，含成功/失败状态 |
| 指标事实 | Metric Fact | 落库后的指标值，最小粒度 `(指标, 期间, 科室, 业务维度)` |
| 推送批次 | Push Batch | 上游主动推上来的数据批次，编号 `push_batch_no` 由上游生成 |
| 幂等重放 | Idempotent Replay | 同一 `push_batch_no` 内容一致时重复推送，返回首次结果不改数据 |
| 内容指纹 | Content Hash | 对推送内容的规范化摘要，用于区分「重放」与「同号不同内容」 |
| 待认领指标 | Unclaimed Metric | 上游推送了但尚未在指标中心注册的指标，暂存待处理 |
| 完整性状态 | Source Status | `COMPLETE` / `PARTIAL` / `FAILED` / `STALE`，描述数据是否齐全 |
| 估算标志 | Estimated Flag | `value_is_estimated`，标记该值是基于部分来源估算而非全量真值 |
| 数据质量规则 | Quality Rule | 对事实数据做合理性检查的规则，命中后落质量问题记录 |
| 校准 | Calibration | 人工修正已落库事实值的审批流程，必须双人复核且有证据 |
| 补采 | Recollect | 对历史期间缺失数据的重新采集 |
| 重算 | Rerun | 对已有数据重新执行计算（非重新取数），需审批 |
| 重试 | Retry | 对失败取数的自动重发，有退避与次数上限 |
| 数据版本 | Data Version | `data_version`，事实行每次变更 +1，用于缓存失效与增量同步 |
| 口径版本 | Metric Version | `metric_version`，指标定义的版本号，锁定该行按哪个口径采集 |
| 上游健康度 | Source Health | 基于调用记录聚合的接口可用性指标 |
| 降级原因 | Degraded Reason | `degraded_reason`，说明批次为何不是 `COMPLETE` |
| 缺失来源 | Missing Sources | `missing_sources`，`PARTIAL` 批次中缺失的指标清单 |
