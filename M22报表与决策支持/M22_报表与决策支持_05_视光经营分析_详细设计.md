## 1. 模块概述

### 1.1 模块定位

M22-05 视光经营分析是 M22 报表与决策支持模块中**面向视光业务主题的分析子模块**。它把散落在验光（M10-01）、处方（M10-02）、销售结算（M16-04）、库存（M15-01）、工作量（M04-07/M07-07）中的视光业务数据，按统一口径收敛成八张分析视图，供视光中心主任、门店店长、运营管理者在同一套数字上做经营判断。

一句话概括本子模块的职责：**把视光的「钱、量、品、货、客、人」六件事，用一套口径讲成一张能下钻到单据的经营账。**

- **钱** —— 视光销售额、客单价、毛利、目标达成（数据来源 M16-04，M22 一分钱都不自己算）
- **量** —— 验光人次、验光单数、配镜订单数、配镜转化率
- **品** —— 产品结构（镜架/镜片/隐形/太阳镜/配件/服务）、折射率结构、光度区间结构
- **货** —— 库存周转率、周转天数、滞销占压
- **客** —— 会员复购率、复购次数、流失预警
- **人** —— 门店排名、验光师业绩、加工工单量

本子模块**不产生任何业务数据**，只做「取数 → 校准 → 存储 → 展现 → 下钻」五件事。所有业务事实的权威方都在上游模块，M22-05 落库的每一个金额字段都带 `_snap` 后缀，明确表示「这是某一时刻从上游取回来的快照值」。

### 1.2 为什么独立成子模块

**理由一：视光经营分析的指标体系与临床、财务主题高度不重合，混在同一套模型里会把无关指标带进查询路径。**

视光业务的核心指标是验光量、配镜转化率、产品结构、库存周转、会员复购，共 13 个主指标（详见附录 B）。这些指标与 M22-07 临床质量指标（手术并发症率、危急值处置及时率）、M22-08 财务主题指标（收入构成、成本率、科室贡献）在**维度**上就不同：视光按「门店 × 商品大类 × 折射率 × 光度区间」切，临床按「科室 × 病种 × 术式」切，财务按「会计科目 × 成本中心」切。若混在一张宽表里，任意一侧新增维度都要改主表，且查询时必须靠大量 `WHERE` 排除无关指标行，行数放大 3~6 倍。独立成子模块后，视光 7 张事实表各自只承载本主题的指标，查询路径最短。

**理由二：视光口径的争议点集中在「转化率」和「复购率」这两个比率上，必须有一份口径写进表结构的权威定义。**

同一个「配镜转化率」，如果分母取「验光人次」而不是「验光单数」，数值会相差约 1.2 倍（一次验光可能出多张单，也可能一人多副）。同一份数据，若复购按「会员卡号」归并而不是按「患者主索引」归并，在办卡率 40% 的门店会把复购率压低到真实值的一半左右。这类口径差异无法靠「文档约定」维持，必须落成**带 CHECK 约束的表结构 + 建表时写死的枚举**。本子模块把分母口径做成 `denominator_type` 进入唯一键，把识别键做成 `identity_key_type` 进入唯一键，使「换口径」变成「新写一行」而不是「改一行代码」。

**理由三：视光数据的上游是 5 个模块的 8 个统计接口，接口失败时的降级语义必须由分析侧统一定义。**

视光金额来自 M16-04、库存来自 M15-01、验光量来自 M04-07、工作量来自 M07-07、主数据来自 M01-08 与 M10。任一接口失败，如果各页面各自决定「填 0 还是留空」，就会出现「销售额 0 元但订单数 128 单」这种不可能的数字。本子模块把「上游失败 → 该指标存 NULL 且 `source_status` 降级为 PARTIAL → 前端显示角标」这一条规则做成**统一的事实表列约束**（`ck_..._status_value`），从数据库层消灭「失败当 0」的可能。

**理由四：视光分析需要「下钻到最后一张单据」，而跨模块直查业务表是被明令禁止的。**

看板上「本月视光销售额 128.64 万元」这个数字，主任一定会问「哪几单」。若 M22 直接 `SELECT ... FROM m16_optical_order`，就意味着 M22 与 M16 的表结构强耦合，M16 一次字段改名就会打穿 M22。本子模块的做法是：在事实表中保留**单据编号列**（如 `order_no`、`optometry_no`）与**明细快照列**（如 `total_amount_snap`），下钻时先在本子模块内展开到单据粒度，再让前端凭单号调上游的详情接口。这样既满足下钻诉求，又保持模块解耦。

### 1.4 概念辨析

**辨析一：视光销售额 vs 实收金额 vs 财务确认收入**

| 概念 | 定义 | 归属口径 | 本子模块字段 |
| --- | --- | --- | --- |
| 视光销售额 | 视光销售单的商品金额 + 服务金额 − 折扣金额 | 按下单日归属 | `total_amount_snap` |
| 实收金额 | 当日实际收到的现金/扫码/刷卡金额 | 按收款日归属 | `paid_amount_snap` |
| 财务确认收入 | 按权责发生制确认的收入 | 按 M17 会计期间 | 不在本子模块 |

三者**不是同一批订单**：10 月 31 日下单定金 30%、11 月 5 日付尾款，则 10 月的销售额含全额、10 月的实收金额只含定金、11 月的实收金额含尾款。本子模块在 P02 页面**同时展示三个数字并显式标注归属规则**，避免运营误以为"卖得多收得少"是收款问题。

**辨析二：验光量（人次）vs 验光单数（单量）**

一次到店验光可能产生 1 张验光单；同一顾客同一天为不同需求验两次则产生 2 张单但不增加独立人次。本子模块：
- **验光人次** `exam_count` 用于衡量服务承载量、人力排班
- **验光单数** `exam_order_count` 用于**唯一分母**计算配镜转化率

混用会导致转化率虚低：若某月 856 人次验光产生 812 张验光单、成交 128 单，按人次的转化率是 14.95%，按单数则是 15.76%。本子模块固定使用单数，并在 P03 页面把两个数字并列展示。

**辨析三：配镜订单数 vs 销售明细行数 vs 成交顾客数**

- 配镜订单数 `order_count`：已达成成交的**销售单**数量，是转化率分子
- 销售明细行数 `item_count`：一张单里可能含镜架+镜片+配件 3 行
- 成交顾客数 `customer_count`：同一顾客一天两单算 1 人

连带率 = `item_count / order_count`（一单带几件），客单价 = `total_amount_snap / order_count`。用错分母会把连带率算成「一件商品平均卖多少钱」。

**辨析四：复购顾客数 vs 复购次数**

- **复购顾客数** `repurchase_customer_count`：窗口内有效消费 ≥2 次的**人**数
- **复购次数** `repurchase_count`：有效消费总次数 − 复购顾客数

某顾客窗口内消费 3 次，则贡献「1 个复购顾客」和「2 次复购」。若把两者混同，会得出"复购率 300%"这种不可能的数字。

**辨析五：周转率 vs 周转天数**

- **周转率** `turnover_rate` = 销售成本 ÷ 平均库存，是一个**倍数**（季度周转 1.20 次）
- **周转天数** `turnover_days` = 期间天数 ÷ 周转率，是**天数**（季度 75.00 天）

两者互为倒数关系但**单位不同、方向相反**（周转率越高越好，周转天数越低越好）。在考核里若把两者放进同一张「越大越好」的排名表，会把周转天数最差的门店排到第一名。

**辨析六：历史报表不重算 vs 冲正**

- **不重算**：已冻结的期间 `is_final = TRUE` + `freeze_date` 有值，任何后续数据变化都不回改该期数字
- **冲正**：窗口结束后才发生的退单，在**下一期**写一条 `is_reversal = TRUE` 的行，`reversal_of_period` 指向原期间

这样做的原因是「报表的审计价值在于当时看到的是什么」。若允许回改，9 月经营会上的数字在 11 月会变，无法追责。

### 1.5 模块目标

| 序号 | 目标 | 可量化验收 |
| --- | --- | --- |
| 1 | 视光金额一数一源 | 100% 金额字段来自 M16-04，不存在 `SELECT SUM(...) FROM m16_*` |
| 2 | 转化率口径可审计 | 分母口径进入唯一键，任一期可查「当时用的哪个分母」 |
| 3 | 复购口径不低估 | 识别键默认按 `patient_id`，多卡归并率可查询 |
| 4 | 上游失败不伪装成 0 | 所有事实表强制 `source_status`，非 COMPLETE 时比率必须为 NULL |
| 5 | 历史期永不回改 | 冻结期写入被 CHECK 与触发器双重拦截 |
| 6 | 所有数字可下钻 | 每个汇总值可下钻到单据编号，分项合计差额 > 0.01 元即报错 |
| 7 | 看板首屏够快 | 看板汇总 P95 ≤ 500ms，单指标查询 P95 ≤ 300ms |
| 8 | 导出可追溯 | 每份导出文件带口径说明页、数据版本、水印与导出人 |

### 2.3 与业务模块的边界

M22-05 与 M16-04（视光销售结算）的边界最关键，用一个具体场景说明：

```text
顾客在视光中心配镜
    │
    ├── 验光（M10-01）───────────────► 验光单 OPT2026101500031
    │                                        │ 产生 1 条验光记录
    │                                        ▼
    ├── 开方（M10-02）───────────────► 处方 RX2026101500018
    │
    ├── 选配（M10-05）───────────────► 选配会话 + 销售单草稿
    │
    ├── 结算（M16-04）───────────────► 销售单 SO2026101500127（金额在此产生）

    │                                        ▼
    │                                   m16_optical_order / m16_optical_item
    │                                        │
    │                                        │ 定时调 GET /internal/v1/m16/optical/statistics
    │                                        ▼
    └── 分析（M22-05）───────────────► m22_optical_sales_fact 等 7 张事实表
                                             │
                                             ▼
                                       看板 / 分析页 / 导出
```

**边界四问：**

1. **金额能不能在 M22-05 算？** 不能。M22-05 只接受 M16-04 返回的金额字段，原样落成 `*_snap` 列。若需要「客单价」，用 `total_amount_snap / order_count` 推导，且推导结果命名不带 `_snap`（因为它不是上游给出的原值）。
2. **订单数能不能在 M22-05 数？** 不能。M16-04 统计接口已给出 `order_count`，M22-05 不查 `m16_optical_order` 数行数。
3. **退单怎么处理？** M16-04 统计接口的返回中同时含 `order_count`（已剔除退单或含退单，按其口径）与 `refund_amount`（退款金额）。M22-05 的转化率分子必须用「配镜订单数」并**按 3.4.3 的冲减规则**处理，绝不自行从明细表数单。
4. **M10 的数据能不能直接查？** 不能。M10 只提供 4 个与 M22 相关的内部契约（M10-06 P-12 订单详情、M10-07 P-16 加工工单、M10-09 P-25 视力档案、M10-02 P-05/P-06 处方）。M22-05 只调这 4 个，不查 M10 的表。

### 3.2 状态机

M22-05 涉及四个状态机：**事实行完整度**、**期间冻结状态**、**导出任务状态**、**同步日志结果**。

#### 3.2.1 事实行完整度状态机

```text
                  ┌──────────┐
                  │ 写入开始  │
                  └────┬─────┘
                       │
          ┌────────────┼────────────┬────────────┐
          │            │            │            │
          ▼            ▼            ▼            ▼
    ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
    │ COMPLETE │ │ PARTIAL  │ │  FAILED  │ │  STALE   │
    │ 上游全成  │ │ 部分缺失  │ │ 上游失败  │ │ 长期未更新│
    └────┬─────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘
         │            │            │            │
         │  重试成功   │            │            │
         │  ◄──────────┘            │            │
         │            │            │            │
         │            │  重试成功    │            │
         │            │  ◄──────────┘            │
         │            │                         │
         │            │            超 48h 未更新  │
         │            │            ◄─────────────┘
         ▼            ▼
    ┌──────────────────────┐
    │ 可参与报表出具        │  COMPLETE 才允许对外发布
    │ COMPLETE 才允许发布   │
    └──────────────────────┘
```

**状态定义：**

| 状态 | 含义 | 价值字段 | 是否允许对外发布 | 前端表现 |
| --- | --- | --- | --- | --- |
| `COMPLETE` | 上游接口全部成功且行数校验通过 | 全部有值 | 允许 | 正常显示 |
| `PARTIAL` | 上游部分成功（如部分门店缺数、部分维度缺失） | 缺失部分为 NULL，有值部分保留 | 允许但必须带角标 | 黄色角标「部分数据」 |
| `FAILED` | 上游接口调用失败 | 全部金额/比率字段为 NULL | **禁止** | 红色角标「数据未就绪」 |
| `STALE` | 超过 48 小时未成功更新 | 保留上次成功值 | 允许但必须带角标 | 灰色角标「数据陈旧」 |

**流转规则：**

| 当前状态 | 触发事件 | 目标状态 | 条件 | 错误码 |
| --- | --- | --- | --- | --- |
| 无 | 首次采集成功且行数校验通过 | `COMPLETE` | `row_affected == row_expected` | 无 |
| 无 | 首次采集部分成功 | `PARTIAL` | `0 < row_affected < row_expected` | `"2205001"` 记录 |
| 无 | 首次采集完全失败 | `FAILED` | 上游返回错误或超时 | `"2205001"` |
| `FAILED` | 重试成功且行数校验通过 | `COMPLETE` | 幂等覆盖写入 | 无 |
| `PARTIAL` | 重试成功补全 | `COMPLETE` | 幂等覆盖写入 | 无 |
| `COMPLETE` | 距上次成功采集超 48h | `STALE` | 定时巡检任务判定 | 无 |
| `STALE` | 补采成功 | `COMPLETE` | 幂等覆盖写入 | 无 |
| `FAILED` | 期间已冻结 | 保持 `FAILED` | **禁止**用后续数据覆盖冻结行 | `"2205035"` |

> **PARTIAL 不允许降级为 FAILED，也不允许被当作 COMPLETE：** 这是为了防止「重试时上游彻底挂了，把原本部分有值的数据覆盖成全空」。重试逻辑必须先读旧行，若旧行 `PARTIAL` 而新结果 `FAILED`，则保留旧行并记录重试失败日志，不覆盖。

```text
      ┌──────────┐   冻结触发   ┌──────────┐

      │ 开放计算  │              │ 已冻结    │
      └────┬─────┘              └────┬─────┘
           │                         │
           │ 运营申请重算             │ 退单发生在闭窗后
           ▼                         ▼
      ┌──────────┐              ┌──────────┐
      │ RECALC   │              │ REVERSAL │
      │ 重算中    │              │ 下期冲正  │

           ▼
      ┌──────────┐
      │  FROZEN  │
      └──────────┘
```

**冻结触发条件（满足任一即冻结）：**

| 触发条件 | 冻结时间点 | 说明 |
| --- | --- | --- |
| 期间结束 + N 天（N 由 `m22.optical.freeze.delay_days` 配置，默认 5） | 期间结束后第 5 天 03:00 | 给上游补录留出窗口 |
| 该期间已被用于出具对外报表（`m22.report.published` 事件） | 报表发布瞬间 | 对外发布后不得再变 |
| 运营/财务手动冻结 | 操作瞬间 | 需 `m22:optical:approve` 权限 |

**冻结后的写入约束：**

| 操作 | 冻结期是否允许 | 拦截层 | 错误码 |
| --- | --- | --- | --- |
| 幂等覆盖写入事实行 | 禁止 | CHECK + Service | `"2205035"` |
| 新增冲正行（`is_reversal=TRUE`） | 允许，但必须写入**下一期** | Service | `"2205034"`（若期间相同） |
| 更新导出任务 | 允许 | 无 | 无 |
| 删除事实行 | 禁止 | `REVOKE DELETE` + Service | `"2205035"` |

#### 3.2.3 导出任务状态机

```text
   ┌─────────┐  开始执行  ┌─────────┐  完成  ┌─────────┐
   │ PENDING │───────────►│ RUNNING │───────►│ SUCCESS │
   └────┬────┘            └────┬────┘        └────┬────┘
        │                      │                  │ 超过保留期
        │ 排队超时              │ 执行失败          ▼
        │                      ▼             ┌─────────┐
        │                 ┌─────────┐        │ EXPIRED │
        │                 │  FAILED │        └─────────┘
        │                 └────┬────┘
        │                      │ 重试（≤3 次）
        ▼                      └──────► RUNNING
   ┌─────────┐
   │ FAILED  │
   └─────────┘
```

**状态定义与流转：**

| 状态 | 含义 | 允许操作 | 流转条件 |
| --- | --- | --- | --- |
| `PENDING` | 已创建待执行 | 取消、查询 | Celery worker 取到任务 |
| `RUNNING` | 正在生成 | 查询进度 | 生成成功 → `SUCCESS`；异常 → `FAILED` |
| `SUCCESS` | 已生成可下载 | 下载、重新导出 | 超保留期 → `EXPIRED` |
| `FAILED` | 生成失败 | 重试（`retry_count` ≤ 3） | 重试 → `RUNNING` |
| `EXPIRED` | 文件已清理 | 重新导出（新建任务） | 终态 |

| 非法流转 | 错误码 |
| --- | --- |
| `SUCCESS` → `RUNNING`（不允许原地重跑） | `"2205015"` |
| `EXPIRED` → 下载 | `"2205016"` |
| `FAILED` 第 4 次重试 | `"2205015"` |

```text
       │             │              │
       │             │              │
       └─────────────┴──────────────┘
                     │
              全部为终态，不可更新
              （REVOKE UPDATE, DELETE + 触发器）
```

| 结果 | 判定条件 | 写入事实表的 `source_status` |
| --- | --- | --- |
| `SUCCESS` | HTTP 2xx 且 `row_affected == row_expected` | `COMPLETE` |
| `PARTIAL` | HTTP 2xx 但 `row_affected < row_expected` | `PARTIAL` |
| `FAILED` | HTTP 非 2xx、超时、解析失败 | `FAILED` |

### 3.4 关键计算模型

#### 3.4.2 视光销售额与客单价

**公式：**

```text
视光销售额 = Σ(商品金额) + Σ(服务金额) − Σ(折扣金额)
客单价 = 视光销售额 ÷ 配镜订单数
```

**单位：** 金额为元（CNY），精确到分；客单价单位元，展示保留两位小数。

**边界与失败条件：**

| 条件 | 处理 | 错误码 |
| --- | --- | --- |
| M16-04 接口失败 | 金额与订单数全部 NULL，`source_status=FAILED` | `"2205001"` |
| 配镜订单数为 0 | 客单价 NULL，展示「—」，**不展示 0.00** | `"2205010"` |
| 折扣金额 > 商品+服务金额 | 视为上游数据异常，整行 `source_status=PARTIAL` | `"2205012"` |
| 退款金额 > 销售额 | 保留负值展示，不截断为 0 | 无 |

**舍入规则：** 上游返回的金额**不再二次舍入**，原样落库；客单价计算时保留 6 位小数落库，展示时保留 2 位并采用**四舍五入（ROUND_HALF_UP）**。

**算例：**

| 项目 | 数值 | 说明 |
| --- | --- | --- |
| 商品金额合计 | 1,320,000.00 元 | 来自 M16-04 |
| 服务金额合计 | 96,000.00 元 | 验光费、调整费 |
| 折扣金额合计 | 129,600.00 元 | 会员折扣 + 套餐折扣 |
| **视光销售额** | **1,320,000.00 + 96,000.00 − 129,600.00 = 1,286,400.00 元** | |
| 配镜订单数 | 856 单 | |
| 客单价 | 1,286,400.00 ÷ 856 = 1,502.803738… → **1,502.80 元** | 落库 1502.803738，展示 1502.80 |
| 若订单数为 0 | 客单价 NULL，展示「—」 | 不展示 0.00 |

#### 3.4.3 配镜转化率（退单冲减规则，写死）

**公式：**

```text
配镜转化率 = 配镜订单数终值 ÷ 验光单数
配镜订单数终值 = 配镜订单数原始 − 窗口内退单冲减数
```

**三条写死的规则：**

| 规则 | 内容 | 理由 |
| --- | --- | --- |
| 规则一 | **分母（验光单数）不减。** 即使这单验光对应的配镜订单被退了，验光服务已经实际发生，人力与设备成本已经付出 | 验光是一次真实的服务交付，不受后续配镜成交与否影响 |
| 规则二 | **分子（配镜订单数）减。** 窗口内发生退单的订单，从分子中扣除 | 退了就不算成交，转化率应因此下降 |
| 规则三 | **窗口结束后的退单不回改历史报表。** 历史期间已冻结，不重算；在**下一期**写一条 `is_reversal = TRUE` 的冲正行，`reversal_of_period` 指向原期间 | 报表的审计价值在于「当时看到的是什么」，会变的数字无法追责 |

**单位：** 无量纲比率，取值 0~1，落库 6 位小数，展示为百分比保留 2 位。

**边界与失败条件：**

| 条件 | 处理 | 错误码 |
| --- | --- | --- |
| 验光单数为 0 | 转化率 NULL，展示「—」，**绝不展示 0.000000 或 0%** | `"2205010"` |
| 验光单数来源 M04-07 失败 | 分母 NULL，转化率 NULL，`source_status=FAILED` | `"2205003"` |
| 配镜订单数来源 M16-04 失败 | 分子 NULL，转化率 NULL，`source_status=FAILED` | `"2205001"` |
| 退单冲减数 > 配镜订单数原始 | 分子终值为负，保留负值并标 `PARTIAL`，人工排查 | `"2205012"` |
| 分母口径切换（`EXAM_ORDER` ↔ `EXAM_VISIT`） | 写入新行，唯一键含 `denominator_type`，两行并存可比对 | `"2205020"` |

**舍入规则：** 落库 6 位小数（`NUMERIC(9,6)`），展示 2 位百分比（乘 100 后四舍五入保留 2 位）。

**算例一：正常无退单**

| 项目 | 数值 |
| --- | --- |
| 验光单数（分母） | 812 |
| 配镜订单数（分子原始） | 128 |
| 窗口内退单冲减数 | 0 |
| 分子终值 | 128 |
| **配镜转化率** | 128 ÷ 812 = 0.157635… → 落库 **0.157635**，展示 **15.76%** |

**算例二：窗口内退单，只减分子**

| 项目 | 数值 | 说明 |
| --- | --- | --- |
| 验光单数（分母） | 812 | **不减**，验光已实际发生 |
| 配镜订单数（分子原始） | 128 | |
| 窗口内退单冲减数 | 5 | 10 月 20 日下的单，10 月 28 日退了 |
| 分子终值 | 128 − 5 = 123 | |
| **配镜转化率** | 123 ÷ 812 = 0.151478… → 落库 **0.151478**，展示 **15.15%** | 比无退单时下降 0.62 个百分点，符合经营直觉 |
| 若错误地把分母也减 5 | 123 ÷ 807 = 0.152416 → 15.24% | **错误做法**，会掩盖退单对体验的影响 |

**算例三：窗口结束后才退单，走下一期冲正**

| 时间 | 事件 | 10 月报表 | 11 月报表 |
| --- | --- | --- | --- |
| 2026-10-20 | 下单 SO2026102000087，金额 2,680.00 元 | 10 月分子 +1 | — |
| 2026-10-31 | 10 月期间结束，11 月 5 日冻结 | 分子终值 = 128，转化率 15.76% | — |
| 2026-11-08 | 顾客退单，退款 2,680.00 元 | **10 月报表不回改**，仍显示 15.76% | 11 月写冲正行 `is_reversal=TRUE`，`reversal_of_period='2026-10'`，冲减数 = 1 |
| 2026-11-30 | 11 月期间结束 | 不变 | 11 月分子终值 = 11 月原始订单数 − 1，转化率反映冲减 |

> **冲正行在页面上的展示方式：** P03 页面在 11 月的柱状图上叠加一条「含上期冲正 −1 单」的注记，并在明细表中以红色标注。使用者能看到「这个月为什么少了一单」，同时 10 月的数字保持不变。

#### 3.4.4 验光量与验光单数

**公式：**

```text
验光人次 = Σ 当日到店验光的独立人次（同一患者同日多次验光算 1 人次）
验光单数 = Σ 当日生成的验光单数量
```

**单位：** 整数（BIGINT）。

**边界与失败条件：**

| 条件 | 处理 | 错误码 |
| --- | --- | --- |
| M04-07 接口失败 | 两项均 NULL，`source_status=FAILED` | `"2205003"` |
| `exam_count < exam_order_count` | 违反 `ck_m22_optical_optometry_fact_count`，拒绝写入 | `"2205019"` |
| 与 M10 交叉核对差异率 > 5% | 行标记 `PARTIAL`，推送告警 | `"2205019"` |
| 首诊 + 复诊 ≠ 验光人次 | 拒绝写入 | `"2205019"` |

**算例：**

| 项目 | 数值 | 说明 |
| --- | --- | --- |
| 当日验光人次 | 856 | 856 位不同患者各验一次 |
| 其中复诊人次 | 312 | 有历史验光记录 |
| 首诊人次 | 544 | 544 + 312 = 856 ✓ |
| 当日验光单数 | 812 | 有 44 人验光后未出单（如仅做视功能筛查） |
| M10 交叉核对单数 | 815 | 差异 3 张 |

| 差异率 | 计算 | 结果 |
| --- | --- | --- |
| 交叉核对差异率 | `abs(815 − 812) ÷ 812` | **0.003695** = 0.37%，低于 5% 阈值，正常 |

> 注意单元格内使用 `abs(x)` 写法而非竖线，避免破坏表格解析。

#### 3.4.5 产品结构与毛利

**公式：**

```text
毛利额 = 销售额 − 销售成本
毛利率 = 毛利额 ÷ 销售额
销售额占比 = 该品类销售额 ÷ 总销售额
```

**单位：** 毛利额与销售额为元（两位小数）；毛利率与占比为比率（6 位小数）。

**边界与失败条件：**

| 条件 | 处理 | 错误码 |
| --- | --- | --- |
| 销售额为 0 | 毛利率与占比 NULL，展示「—」 | `"2205010"` |
| 销售成本快照缺失 | 毛利额与毛利率 NULL，行标 `PARTIAL` | `"2205031"` |
| 销售成本 > 销售额（负毛利） | 保留负值，标红展示，不截断 | 无 |
| 品类映射失败 | 归入 `UNKNOWN` 桶，`source_status=PARTIAL` | `"2205005"` |
| 折射率不在 5 档之内 | 归入 `OTHER` 桶，不写 `refractive_index` | `"2205005"` |

**舍入规则：** 毛利额与销售额原样落库（两位小数，来自上游）；毛利率落库 6 位小数；占比落库 6 位小数，展示 2 位百分比。

**算例（某门店季度产品结构）：**

| 商品大类 | 销售额（元） | 销售成本（元） | 毛利额（元） | 毛利率 | 占比 |
| --- | --- | --- | --- | --- | --- |
| 镜片 LENS | 686,400.00 | 315,744.00 | 370,656.00 | 370,656 ÷ 686,400 = 0.539930 | 0.533519 |
| 镜架 FRAME | 411,840.00 | 164,736.00 | 247,104.00 | 0.600000 | 0.320149 |
| 隐形 CONTACT | 102,912.00 | 61,747.20 | 41,164.80 | 0.400000 | 0.080000 |
| 配件 ACCESSORY | 51,456.00 | 18,009.60 | 33,446.40 | 0.650000 | 0.040000 |
| 太阳镜 SUNGLASS | 25,728.00 | 11,577.60 | 14,150.40 | 0.550000 | 0.020000 |
| 服务 SERVICE | 8,064.00 | 1,612.80 | 6,451.20 | 0.800000 | 0.006332 |
| **合计** | **1,286,400.00** | **573,427.20** | **712,972.80** | **0.554236** | **1.000000** |

| 校验 | 计算 | 结果 |
| --- | --- | --- |
| 毛利额合计 | 370,656.00 + 247,104.00 + 41,164.80 + 33,446.40 + 14,150.40 + 6,451.20 | 712,972.80 ✓ |
| 占比合计 | 各占比之和 | 1.000000 ✓（允许 1e-6 误差，超差报 `"2205019"`） |
| 整体毛利率 | 712,972.80 ÷ 1,286,400.00 | 0.554236 = 55.42% |

#### 3.4.6 视光库存周转率与周转天数

本节是**最容易算错**的一节：周转率与周转天数是两个不同单位、不同方向的指标；平均库存有多种算法，选错会让门店排名完全颠倒；销售成本必须来自上游快照，M22 绝不能自己算。

**公式（写死）：**

```text
周转率 = 销售成本 ÷ 平均库存
周转天数 = 期间天数 ÷ 周转率
        = 期间天数 × 平均库存 ÷ 销售成本        （等价展开式，避免二次除法）
平均库存 = Σ(每日库存金额 × 该日权重) ÷ Σ(每日权重)   （日均加权平均）
期间天数：季度 90、月度 30、年度 360
```

**为什么必须区分周转率与周转天数：**

| 维度 | 周转率 | 周转天数 |
| --- | --- | --- |
| 单位 | 倍数（次/期） | 天 |
| 方向 | 越高越好 | 越低越好 |
| 典型值（季） | 1.20 次 | 75.00 天 |
| 常见误用 | 与周转天数混排在同一「越大越好」榜单，把最差门店排第一 | 同上，方向相反 |

**为什么销售成本必须来自上游：**

销售成本（COGS）= 期初库存 + 本期进货 − 期末库存。M22 无法知道本期进货（在 M15）与真实进货成本（在 M15 的入库单），若用「销售额 × (1 − 目标毛利率)」反推，只是把目标值当成事实值，永远算不出真实的毛利偏差。因此本子模块的 `cogs_amount_snap` 只接受两个来源：

| 来源 | 接口 | 适用场景 | 优先级 |
| --- | --- | --- | --- |
| M16-04 | `GET /internal/v1/m16/optical/statistics` 的 `cost_amount` 字段 | 已按商品大类归集的销售成本 | 高 |
| M15-01 | `GET /internal/v1/m15/consume/cost` | 出库成本归集 | 次 |

若两者都取不到，`cogs_amount_snap` 为 NULL，周转率与周转天数均为 NULL，行标 `PARTIAL`，报 `"2205031"`。**绝不回退到「销售额 × 假定毛利率」这种自造数据的方式。**

**为什么平均库存用日均加权平均而不是期初期末算术平均（选型理由）：**

眼镜零售库存的**季节性极强**，这是选型的唯一理由，展开如下：

| 现象 | 数据表现 | 对算术平均的影响 |
| --- | --- | --- |
| 寒暑假学生配镜高峰在 7~8 月与 1~2 月 | 高峰月销售额约为平月的 1.8~2.2 倍 | 门店会在**高峰前一个月**（6 月、12 月）集中备货 |
| 备货集中在月末到货 | 期末库存金额显著高于期间**平均**水平 | 期初期末算术平均把「峰值库存」当成「平均库存」 |
| 高峰后快速去库存 | 期初（如 7 月初）库存处于高位，因为 6 月备货 | 算术平均进一步抬高高库存的权重 |

具体算例（某门店 2026 年第三季度）：

| 日期 | 库存金额（元） | 说明 |
| --- | --- | --- |
| 07-01（期初） | 2,860,000.00 | 6 月为暑期高峰备货，期初已在高位 |
| 07 月日均 | 2,940,000.00 | 备货继续到货 |
| 08 月日均 | 2,680,000.00 | 高峰销售去库存 |
| 09 月日均 | 2,180,000.00 | 持续去库存 |
| 09-30（期末） | 1,960,000.00 | 已回落至常态水平 |

| 算法 | 计算 | 平均库存 | 相对差异 |
| --- | --- | --- | --- |
| 期初期末算术平均 | (2,860,000.00 + 1,960,000.00) ÷ 2 | **2,410,000.00** | 基准 |
| 日均加权平均 | (2,940,000 × 31 + 2,680,000 × 31 + 2,180,000 × 30) ÷ 92 | **2,604,021.74** | +8.05% |

| 指标 | 用算术平均 | 用日均加权 | 结论 |
| --- | --- | --- | --- |
| 销售成本（M16-04 快照） | 3,200,000.00 | 3,200,000.00 | 相同 |
| 周转率（季） | 3,200,000.00 ÷ 2,410,000.00 = **1.327801** | 3,200,000.00 ÷ 2,604,021.74 = **1.228868** | 算术平均**虚高 8.05%** |
| 周转天数 | 90 ÷ 1.327801 = **67.78 天** | 90 ÷ 1.228868 = **73.24 天** | 算术平均**少算 5.46 天** |

> **结论：** 期初期末算术平均把 6 月备货形成的「峰值」混入分母，得到偏高的平均库存，反而**压低**周转率；但在这个例子里期初库存同样处于高位，两者叠加后算术平均略高于真实均值。**更普遍的问题是：算术平均只取两个时点，完全丢失了期中 3 个月的波动轨迹，任何一个月末的异常（如大盘点、大批退货）都会直接扭曲整季结果。** 而眼镜零售的月末库存受备货节奏影响极大，恰恰是最不可靠的两个时点。日均加权平均用 92 个日快照平滑了波动，反映的是「这批货真正在库里待了多少天」，与周转率的经济含义一致。

**日均加权平均的落地规则：**

| 规则 | 内容 |
| --- | --- |
| 快照来源 | M15-01 每日 23:59 的库存金额快照 |
| 权重 | 按各日实际天数加权，缺快照的日期按相邻快照线性插值 |
| 最小快照数 | 季度 ≥ 80 天、月度 ≥ 26 天、年度 ≥ 340 天，不足则拒绝计算报 `"2205030"` |
| 门店新开 | 不足一个完整期间的门店不参与周转对比排名，但单独展示 |
| 算法留痕 | `avg_method` 字段记录本次用的算法，可与 `OPENING_CLOSING` 做对比分析 |

**单位与舍入：**

| 字段 | 单位 | 精度 | 展示 |
| --- | --- | --- | --- |
| `cogs_amount_snap` | 元 | `NUMERIC(18,2)` | 两位小数 |
| `avg_inventory_amount` | 元 | `NUMERIC(18,2)` | 两位小数 |
| `turnover_rate` | 倍数 | `NUMERIC(9,6)` | 两位小数 |
| `turnover_days` | 天 | `NUMERIC(9,2)` | 两位小数 |

**边界与失败条件：**

| 条件 | 处理 | 错误码 |
| --- | --- | --- |
| 平均库存为 0（空库或数据缺失） | 周转率 NULL，展示「—」 | `"2205010"` |
| 销售成本为 0 | 周转率为 0，周转天数 NULL | `"2205010"` |
| 期初库存缺失 | 拒绝计算，行标 `FAILED` | `"2205029"` |
| 日快照天数不足 | 拒绝计算日均加权的周转率 | `"2205030"` |
| 销售成本来源均不可用 | 周转率与天数 NULL，标 `PARTIAL` | `"2205031"` |
| 同时请求两种算法 | 写入两行，唯一键含 `avg_method` | 无 |

**周转健康度分级：**

| 等级 | 周转天数区间 | 业务含义 | 处置建议 |
| --- | --- | --- | --- |
| `FAST` | < 60 天 | 库存周转快，资金效率高 | 注意是否缺货 |
| `NORMAL` | 60 ~ 90 天 | 健康区间 | 维持 |
| `SLOW` | 90 ~ 180 天 | 周转偏慢，有占压 | 排查滞销 SKU |
| `STAGNANT` | > 180 天 | 严重滞销 | 促销清理，计提跌价准备 |

#### 3.4.7 会员复购率与复购次数（顾客识别键写死）

本节是 Lead 特别强调的**最容易翻车的一节**。核心问题是：用什么键把「同一个人」的不同次消费归到一起？

**顾客识别键选型：`patient_id` 为主，`member_id` 为辅**

| 候选键 | 覆盖率 | 跨店能力 | 主要缺陷 |
| --- | --- | --- | --- |
| `patient_id`（M03 患者主索引） | 视光顾客中约 85% 有患者主索引 | 强，全院统一 | 无就诊记录的纯配镜顾客无 `patient_id` |
| `member_id`（M10-08 会员卡） | 视光顾客中约 40% 办卡 | 强，但一人可多卡 | **丢掉 60% 没办卡的回头客** |
| `customer_no`（M10-05 顾客号） | 视光顾客中约 92% 有顾客号 | 中，可能重复建档 | 同一人可能有多条顾客号 |

**选定理由（必须写清）：**

1. **视光消费可能由未办卡的患者产生。** 一位顾客来配副眼镜，未必愿意办会员卡。若只用 `member_id`，这位顾客的第二次、第三次消费会被当作「新顾客」，**复购顾客数被系统性低估、分母也被低估**，最终复购率偏离真实值。
2. **量化影响：** 办卡率 40% 的门店，假设真实复购顾客 100 人、有效顾客 400 人，真实复购率 25%。若只用 `member_id` 归并，只有约 40% 的消费能归到卡上，重复到店的顾客中有相当比例（约一半）未被识别为同一人，实测复购顾客数可能只有 52 人、有效顾客约 208 人，复购率变成 25%（分母分子同比例缩小的理想情况）到 12%~18%（实际缩减不同步的情况）。**无论哪种情形，都无法直接用于跨店比较**，因为各店办卡率不同，误差方向也不同。
3. **`patient_id` 是全院唯一的主索引，天然支持跨店合并。** 同一患者在南石总院和分院各配一副眼镜，`patient_id` 相同，能正确识别为同一顾客的两次消费。
4. **无 `patient_id` 的顾客用 `customer_no` 兜底**，因此实际识别键是「`patient_id` 优先，缺失时用 `customer_no`」，二者都不具备时该笔消费**不计入复购分母的分母**（即无法归并的消费，只计入总消费额，不计入复购统计），避免污染比率。

**多卡一号（同一患者多张会员卡）的归并规则：**

| 场景 | 处理 | 原因 |
| --- | --- | --- |
| 同一 `patient_id` 名下有多张会员卡（卡 A、卡 B） | 按 `patient_id` 归并，卡号只作展示，`identity_merge_rule = MULTI_CARD_MERGED` | 同一个人不应因办卡渠道不同被算成两个人 |
| 卡 A 属于 `patient_id=10086`，卡 B 未绑定患者 | 卡 B 的消费若带手机号且手机号与 10086 一致，归并；否则按独立顾客计 | 手机号是次优识别依据 |
| 两张卡分属不同 `patient_id`，但手机号相同 | **不自动归并**，标记冲突待 M03 合并后重算，报 `"2205033"` | 可能是家人共用手机号，自动合并会产生错误牵引 |
| 患者主索引发生合并（`m03.patient.merged` 事件） | 订阅事件后，在**下一期**重算受影响顾客的复购；已冻结期不改 | 尊重历史不重算原则 |

**复购口径定义：**

```text
复购顾客数 = 窗口内有效消费次数 ≥ 2 的顾客数
有效顾客数（分母） = 窗口内有效消费次数 ≥ 1 的顾客数
复购次数 = 有效消费总次数 − 复购顾客数
复购率 = 复购顾客数 ÷ 有效顾客数
平均复购间隔天数 = Σ(相邻两次有效消费间隔) ÷ Σ(间隔个数)，仅对 ≥2 次的顾客计算
```

**「有效消费」的定义（退单的处理）：**

| 情况 | 是否计入有效消费 | 说明 |
| --- | --- | --- |
| 正常成交且已交付 | 是 | |
| 窗口内退单 | **否**，从有效消费中扣除 | 退货即不构成一次有效消费 |
| 窗口结束后退单 | 原期照旧计入，下一期写冲正行 | 与 3.4.3 规则三一致 |
| 仅支付定金未付尾款 | 否，直到付清才计为有效消费 | 未完成的交易不算复购依据 |
| 纯服务单（如仅验光） | 是，验光也是有效服务消费 | 但不计入配镜订单 |

**单位与舍入：** 复购率为比率，落库 6 位小数，展示 2 位百分比；间隔天数落库 2 位小数。

**完整算例（Lead 要求的场景）：**

**场景：** 张先生（`patient_id = 10086`），窗口 2026-10-01 ~ 2026-10-31 内共 3 次消费，其中 2 次使用会员卡 A（`member_id = 801236`），1 次未用卡。

| 序号 | 日期 | 单据号 | 金额（元） | 是否用卡 | 卡号 | 是否有效消费 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 2026-10-03 | SO2026100300011 | 80.00（验光费） | 是 | A | 是 |
| 2 | 2026-10-03 | SO2026100300012 | 2,680.00（配镜） | 是 | A | 是 |
| 3 | 2026-10-18 | SO2026101800047 | 1,250.00（配镜） | **否** | — | 是 |

**按 `patient_id` 归并（本子模块采用的口径）：**

| 计算步骤 | 值 | 说明 |
| --- | --- | --- |
| 归并依据 | `patient_id = 10086` | 三笔消费均可通过 M16-04 的单据关联到该患者 |
| 有效消费次数 | 3 | 三次都成功交付，无退单 |
| 该顾客是否算复购顾客 | **是**（3 ≥ 2） | |
| 该顾客贡献的复购次数 | 3 − 1 = **2 次** | 第一次不算复购，第二、三次各算一次 |
| 平均复购间隔 | 10-03 到 10-03 间隔 0 天；10-03 到 10-18 间隔 15 天 | (0 + 15) ÷ 2 = **7.50 天** |
| **本窗口该顾客计入** | **复购顾客数 +1，复购次数 +2** | |

**若错用 `member_id` 归并：**

| 计算步骤 | 值 | 问题 |
| --- | --- | --- |
| 卡 A 关联的消费 | 第 1、2 笔 | |
| 第 3 笔 | 无卡，被当作「无会员身份的独立顾客」 | **错误** |
| 卡 A 归并结果 | 有效消费 2 次 → 仍算 1 个复购顾客，贡献 1 次复购 | 复购次数少算 1 |
| 第 3 笔结果 | 新增 1 个「有效顾客」，有效消费 1 次，不算复购 | **分母虚增 1，分子未增** |
| 对整体复购率影响 | 分子少 1、分母多 1，**复购率被低估** | 这就是 Lead 指出的系统性低估 |

**再叠加「多卡一号」情形：** 若张先生后来又办了卡 B（`member_id = 802007`），并在 10-25 用卡 B 买了 480.00 元的配件。

| 计算步骤 | 值 | 说明 |
| --- | --- | --- |
| 有效消费次数 | 4（10-03 两笔、10-18 一笔、10-25 一笔） | |
| 归并依据 | `patient_id = 10086`，卡 A 与卡 B 都挂在同一患者名下 | `identity_merge_rule = MULTI_CARD_MERGED` |
| 该顾客是否算复购顾客 | 是（4 ≥ 2），仍只算 **1 个复购顾客** | 多卡不产生多个顾客 |
| 复购次数 | 4 − 1 = **3 次** | |
| 若按 `member_id` 归并 | 卡 A 一个顾客、卡 B 一个顾客，各贡献 2 次和 1 次消费 | 复购顾客数 **+2**、复购次数 **+1**，严重虚高 |

**窗口结束后的退单：** 假设 11-05 第 3 笔（2026-10-18，1,250.00 元）被退单。

| 期间 | 处理 |
| --- | --- |
| 2026-10（已冻结） | **回改，仍显示：有效消费 3 次、复购次数 2 次、复购率不变** |
| 2026-11 | 写一条冲正行：`is_reversal = TRUE`、`reversal_of_period = '2026-10'`、该顾客有效消费冲减 1 次 |
| 2026-11 页面展示 | 「含上期冲正：张先生 有效消费 −1，复购次数 −1」 |
| 若冲减后该顾客有效消费 < 2 | 在 11 月的复购顾客数中扣减 1，并在明细中标注原因 |

**复购率整体算例：**

| 项目 | 数值 |
| --- | --- |
| 窗口内有效顾客数（分母） | 1,240 人 |
| 其中有效消费 ≥ 2 次的顾客 | 428 人 |
| **复购率** | 428 ÷ 1,240 = 0.345161… → 落库 **0.345161**，展示 **34.52%** |
| 有效消费总次数 | 2,180 次 |
| 复购次数 | 2,180 − 1,240 = **940 次** |（注意：不是 428）
| 校验 | 有效消费总次数 = 有效顾客数 + 复购次数 = 1,240 + 940 = 2,180 ✓ |

**流失预警：**

```text
平均复购周期 = 该门店历史平均复购间隔天数（默认取近 12 个月）

churn_factor 默认 1.5
```

| 情景 | 平均复购周期 | churn_factor | 阈值 | 老李距上次消费 | 是否预警 |
| --- | --- | --- | --- | --- | --- |
| 常规 | 240 天 | 1.5 | 360 天 | 380 天 | 是 |
| 常规 | 240 天 | 1.5 | 360 天 | 300 天 | 否 |

#### 3.4.8 门店与验光师业绩

**公式：**

```text
推荐成交率 = 推荐成交数 ÷ 推荐数
验光师工作量评分 = 0.4 × 验光量归一化 + 0.35 × 成交金额归一化 + 0.25 × 准时率归一化
目标达成率（方向 UP）= 实际值 ÷ 目标值
目标达成率（方向 DOWN，如周转天数）= 目标值 ÷ 实际值
排名 = RANK() OVER (PARTITION BY dept_id ORDER BY 指定指标 DESC)
```

**单位：** 金额为元；比率为 6 位小数；排名为整数。

**边界与失败条件：**

| 条件 | 处理 | 错误码 |
| --- | --- | --- |
| 推荐数为 0 | 成交率 NULL | `"2205010"` |
| 目标未设置 | 达成率 NULL，展示「未设目标」（**与「达成 0%」必须区分**） | `"2205021"` |
| 样本量 < `min_sample_size` | `rank_no` NULL、`sample_sufficient = FALSE` | `"2205022"` |
| 该月完全无业务 | 不出行，页面显示「本月无业务」（**与「样本不足」必须区分**） | 无 |
| 员工不属于所选门店 | 拒绝查询 | `"2205037"` |
| 跨门店查看需更高权限 | 拒绝 | `"2205023"` |

**方向 DOWN 的目标达成率算例：**

| 项目 | 实际值 | 目标值 | 达成率计算 | 结果 |
| --- | --- | --- | --- | --- |
| 周转天数（方向 DOWN） | 73.24 天 | 80.00 天 | 80.00 ÷ 73.24 | **1.092299** → 109.23%，达成 |
| 周转天数（方向 DOWN，未达） | 92.50 天 | 80.00 天 | 80.00 ÷ 92.50 | **0.864865** → 86.49%，未达成 |
| 视光销售额（方向 UP） | 1,286,400.00 | 1,200,000.00 | 1,286,400 ÷ 1,200,000 | **1.072000** → 107.20%，达成 |

> **方向 DOWN 的陷阱：** 若把周转天数也按「实际 ÷ 目标」算，92.50 ÷ 80.00 = 1.156250 → 115.63%，会把最差的门店显示成超额完成。

### 3.5 单据模型

M22-05 不产生业务单据，只产生两类**管理单据**：导出任务与同步日志，以及一类**事实记录**。

#### 3.5.1 导出任务单（Export Task）

| 项目 | 说明 |
| --- | --- |
| 单号规则 | `EX` + `YYYYMMDD` + 4 位流水，如 `EX202610310001` |
| 生成时机 | 用户在 P08 点击「导出」时创建，状态 `PENDING` |
| 归属 | 归属创建人，仅创建人与管理员可下载 |
| 状态 | `PENDING` → `RUNNING` → `SUCCESS` / `FAILED`；`SUCCESS` 超期 → `EXPIRED` |
| 幂等 | 带 `idempotency_key`，5 分钟内同键同参数返回同一任务，同键不同参数报 `"2205025"` |
| 内容 | 数据页 + 口径说明页 + 数据版本 + 水印（导出人、时间、`data_version`） |
| 保留 | 文件 7 天（可配 `m22.optical.export.expire_days`），任务记录 3 年 |
| 上限 | 单次 ≤ 200,000 行（`m22.optical.export.max_rows`），超限报 `"2205018"` |

#### 3.5.2 同步日志（Sync Log）

| 项目 | 说明 |
| --- | --- |
| 单号规则 | `SG` + `YYYYMMDD` + 4 位流水，如 `SG202610310007` |
| 生成时机 | 每次调用上游统计接口时记录一条 |
| 归属 | 系统级，不可修改 |
| 关联 | `collect_batch_no`（`CB` + 日期 + 流水）关联本次写入的事实行 |
| 内容 | 目标表、指标编码、期间范围、来源模块/接口、HTTP 状态、耗时、实际行数/应有行数、结果、错误码、重试次数、`trace_id` |
| 保留 | 3 年，按 `operated_at` 月分区，`REVOKE UPDATE, DELETE` + 触发器禁改 |
| 用途 | 数据健康度看板、失败原因排查、批次追溯 |

#### 3.5.3 事实记录（Fact Record）

事实记录不是单据，但需说明其「不可重复」的保证：

| 表 | 唯一键 | 重复写入行为 |
| --- | --- | --- |
| 销售事实 | `metric_code, period, granularity, dept_id, biz_dim, data_version` | `ON CONFLICT DO UPDATE`，幂等覆盖 |
| 验光事实 | 同上 | 同上 |
| 转化事实 | `metric_code, period, granularity, dept_id, denominator_type, data_version` | 同上 |
| 产品事实 | `metric_code, period, dept_id, product_category, refractive_index, data_version` | 同上 |
| 周转事实 | `metric_code, period, dept_id, product_category, avg_method, data_version` | 同上 |
| 复购事实 | `metric_code, period, dept_id, identity_key_type, data_version` | 同上 |
| 业绩事实 | `metric_code, period, dept_id, staff_id, staff_role, data_version` | 同上 |

> **为什么唯一键里必须有 `data_version`：** 口径版本升级后，同一期间的同一个指标会有「按旧口径算的值」与「按新口径算的值」两组。若唯一键不含 `data_version`，新口径写入时会覆盖旧口径，导致历史报表引用旧版本时取不到数据。含 `data_version` 后两组并存，报表实例记录当时用的版本号即可精确还原。
