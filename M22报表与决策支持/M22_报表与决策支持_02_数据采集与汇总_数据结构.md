## 文档说明

本文件是 M22-02 数据采集与汇总的**数据结构唯一依据**，包含详细设计文档第 4 章的全部内容。

**定位一句话：** M22-02 是 M22 的**引擎**——它从十六个上游模块的统计接口把数字取回来、校验、落成「指标事实」，下游 M22-03~08 的每一张报表、每一个看板都从这里的指标事实表取数。本子模块的数据结构必须能回答三个问题：**这个数是从哪个接口取的**、**取的时候完整不完整**、**取回来之后谁改过**。

## 1. 表清单

| 序号 | 表名 | 中文名 | 用途 | 预估行数 |
|---|---|---|---|---|
| 4.2 | `m22_collect_task` | 采集任务配置 | 一类指标的采集编排配置：采集哪个上游接口、什么粒度、什么时点、超时与重试、启用状态 | 小（百余行） |
| 4.3 | `m22_collect_batch` | 采集批次 | 一次采集执行的头：批次号 `CB20261031-0001`、触发方式、期间、状态、计数、耗时、数据完整性 | 中（每期每任务一行，年增约 5 万行） |
| 4.4 | `m22_collect_batch_item` | 采集批次明细 | 批次内逐指标的取数结果：上游返回、转换后值、状态、耗时、异常摘要 | 大（每期每指标一行，年增约 200 万行） |
| 4.5 | `m22_fact_metric` | 指标事实 | **本子模块的核心产出**：按 `(metric_code, period, dept_id, biz_dim)` 唯一的指标值，带六个溯源字段，按月分区 | 大（年增约 300 万行） |
| 4.6 | `m22_collect_unclaimed_metric` | 待认领指标 | P-01 推送中出现的、M22-01 尚未注册的指标编码，等指标中心认领后再回灌 | 极小（年增数百行） |
| 4.7 | `m22_collect_failure` | 采集失败与重试 | 逐次失败与重试流水：重试序号、退避秒数、错误码、错误摘要、下次重试时刻 | 中（年增约 10 万行） |
| 4.8 | `m22_collect_quality_check` | 数据质量校验 | 采集后与汇总后的质量规则命中结果：空值、突变、勾稽不平、跨期漂移 | 中（年增约 20 万行） |
| 4.9 | `m22_collect_calibration` | 校准与修正 | 人工校准与修正的审批单串：原值、新值、原因、审批人、生效时刻 | 极小（年增数百行） |
| 4.10 | `m22_collect_source_health` | 上游接口健康度 | 上游接口按小时聚合的可用性：调用数、成功率、P95 耗时、连续失败天数 | 大（十六模块 × 接口数 × 24 × 365） |
| 4.11 | `m22_collect_log` | 采集日志与追溯 | 追加写的事件流水：创建任务、启动批次、落库、重试、告警、人工干预，供审计追溯 | 大（年增约 500 万行） |

**合计： 10 张表**

**表分组说明：**

| 分组 | 表 | 说明 |
|---|---|---|
| 采集编排 | `m22_collect_task` | 定义「采什么、什么时候采」，属配置，可编辑可停用 |
| 采集执行 | `m22_collect_batch`、`m22_collect_batch_item` | 一次执行的父子两张表，批次是头、明细是逐指标结果 |
| 指标事实 | `m22_fact_metric` | 全子模块唯一的事实表，下游报表与看板全部从这里取数 |
| 异常与治理 | `m22_collect_unclaimed_metric`、`m22_collect_failure`、`m22_collect_quality_check`、`m22_collect_calibration` | 未认领、失败重试、质量校验、人工校准四类治理数据 |
| 观测与审计 | `m22_collect_source_health`、`m22_collect_log` | 上游健康度与全链路日志，只增不改 |

**为什么不把「采集明细」和「指标事实」合并成一张表：** 采集明细记录的是「这一次取数**发生了什么**」（含取数失败、上游超时、口径不符被拒），即使没有落成事实也必须留痕；指标事实记录的是「**当前有效的值是什么**」，同一 `(metric_code, period, dept_id, biz_dim)` 只保留一行、重复采集覆盖。一张表同时承担「流水」与「快照」两种语义，必然出现「事实表里到底有几行才是对的」这类无法回答的问题，因此拆成两张。

**为什么「待认领指标」要单独建表：** P-01 是 M06-07 与 M09-06 已经写死的推送契约，调用方不会因为 M22 尚未注册某个 `metric_code` 就停止推送。如果直接拒收整批，会连带丢掉同批次里已注册的合法指标；如果静默丢弃，上游的数字就凭空消失。单独建表把「未注册」这件事本身变成一条可见的待办数据，指标中心补齐定义后由定时任务回灌成事实，这条链路才闭环。

**关系说明：**

| 关系 | 基数 | 说明 | 约束方式 |
|---|---|---|---|
| `m22_collect_task` → `m22_collect_batch` | 1 : N | 一个任务可产生多个批次（每次执行一个） | 逻辑外键 `task_id`，不建物理约束 |
| `m22_collect_batch` → `m22_collect_batch_item` | 1 : N | 一个批次含多条逐指标明细 | 逻辑外键 `batch_id` + 冗余 `batch_no` |
| `m22_collect_batch_item` → `m22_fact_metric` | 1 : 0..1 | 明细成功且通过质量校验才落事实 | 事实表记 `collect_batch_no` 回溯 |
| `m22_collect_batch` → `m22_collect_failure` | 1 : N | 一个批次可产生多次失败与重试 | 逻辑外键 `batch_id` |
| `m22_fact_metric` → `m22_collect_quality_check` | 1 : N | 一个事实可被多条质量规则命中 | 逻辑外键 `fact_id`（可空，采集前校验无 fact） |
| `m22_fact_metric` → `m22_collect_calibration` | 1 : N | 一个事实可被多次校准（历史不可删） | 逻辑外键 `fact_id` + `metric_code` + `period` |
| `m22_fact_metric` → `m22_collect_log` | 1 : N | 事实的每次落库/校准/失效都记日志 | 日志记 `biz_no` 与 `biz_type` |
| `m22_metric_def` → `m22_fact_metric` | 1 : N | 指标定义约束事实的编码与单位 | 应用层校验 `metric_code` 存在且 `is_active` |

> `FK*` 表示**逻辑外键**（不建物理约束，由应用层保证）。全系统统一不建物理外键，原因是分区表上的外键无法跨分区维护，且上游模块与 M22 分库部署时物理外键直接不可用。

**ER 图与分区的关系：** 图中 `m22_fact_metric` 标了「月分区」，其余九张表为单表。分区的理由见 4.5 节设计说明：事实表按 `period` 的年份月份做 RANGE 分区，每年 12 个分区 + 1 个 `DEFAULT` 分区，历史分区可整分区归档而不影响在线查询。

### 4.2 表：`m22_collect_task`（采集任务配置）

**用途：** 定义「采什么、从哪个接口采、什么粒度、什么时点采、超时多重试几次、当前启用与否」。一个任务对应一组同口径、同上游接口、同粒度的指标采集。任务由运维在 P02 页面配置，修改后下次调度即生效，**历史批次不受影响**（批次表里冗余了当时的任务参数快照）。

**为什么要有这张表而不是把配置写死在代码里：** 上游十六个模块的统计接口会新增、改路径、改返回结构；采集时点要随医院作息调整（比如日结从 01:00 改到 02:00 等 M16 冻结后）；某次接口故障需要临时停掉某个任务。这些都必须**不发版就能改**。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | N | IDENTITY | 主键 |
| `task_code` | VARCHAR(64) | N | — | 任务编码，全局唯一，格式 `CT_{来源模块}_{主题}`，如 `CT_M16_REVENUE_DAILY` |
| `task_name` | VARCHAR(128) | N | — | 任务名称，如「M16 收入日结采集」 |
| `source_module` | VARCHAR(8) | N | — | 来源模块编码，如 `M16`，取值见附录 B |
| `source_submodule` | VARCHAR(16) | Y | NULL | 来源子模块编码，如 `M16-09`，仅用于展示与排障 |
| `source_api` | VARCHAR(200) | N | — | 上游接口路径（含占位符），如 `/internal/v1/m16/daily/summary/{date}` |
| `http_method` | VARCHAR(8) | N | `GET` | 调用方法，`GET` / `POST` |
| `granularity` | VARCHAR(16) | N | — | 采集粒度，取值 `REALTIME` / `HOURLY` / `DAILY` / `WEEKLY` / `MONTHLY` / `QUARTERLY` / `YEARLY` |
| `period_format` | VARCHAR(16) | N | `YYYY-MM-DD` | 期间格式，`YYYY-MM-DD`（日）/ `YYYY-MM`（月）/ `YYYY`（年）/ `YYYY-MM-DD HH24`（时） |
| `cron_expr` | VARCHAR(64) | Y | NULL | APScheduler 的 cron 表达式；手工触发型任务为空 |
| `trigger_mode` | VARCHAR(16) | N | `SCHEDULE` | 触发方式：`SCHEDULE` 定时 / `EVENT` 事件驱动 / `MANUAL` 仅手工 / `MIXED` 定时与事件并存 |
| `trigger_event` | VARCHAR(64) | Y | NULL | 事件驱动时订阅的事件名，如 `m16.daily.frozen` |
| `request_template` | TEXT | Y | NULL | 请求体模板（`POST` 型上游接口用），JSON 字符串，支持 `${period}` 占位 |
| `metric_codes` | TEXT | N | — | 本任务负责的指标编码清单，JSON 数组字符串，如 `["M09_OR_COUNT","M09_OR_UTILIZATION"]` |
| `metric_count` | INT | N | 0 | 指标数量，写入时由 `metric_codes` 求值得出，供列表页快速展示 |
| `timeout_ms` | INT | N | 10000 | 单次调用超时毫秒，范围 1000~60000 |
| `max_retry` | SMALLINT | N | 5 | 最大重试次数，范围 0~5 |
| `retry_backoff_base_s` | INT | N | 30 | 指数退避基数秒，第 n 次重试等待 `base × 2^(n-1)` 秒 |
| `concurrency_limit` | SMALLINT | N | 4 | 该任务内部并发调用数上限 |
| `lock_ttl_s` | INT | N | 900 | 采集分布式锁 TTL 秒，必须大于最坏执行时长 |
| `schedule_offset_s` | INT | N | 0 | 定时触发相对偏移秒，用于错峰（如排在 M16 日结后再等 300 秒） |
| `depends_on_task_code` | VARCHAR(64) | Y | NULL | 前置任务编码：前置任务本期间成功后本任务才可执行 |
| `source_status_required` | VARCHAR(16) | N | `COMPLETE` | 前置任务需达到的最低数据完整性，`COMPLETE` / `PARTIAL` / `FAILED` / `STALE` |
| `allow_partial` | BOOLEAN | N | FALSE | 上游不可用时是否允许标 `PARTIAL` 继续落事实；`FALSE` 则整任务判 `FAILED` |
| `status` | VARCHAR(16) | N | `IDLE` | 任务状态，取值 `IDLE` / `RUNNING` / `SUCCESS` / `PARTIAL` / `FAILED` / `DISABLED` |
| `priority` | SMALLINT | N | 50 | 调度优先级，0（最高）~99（最低），同队列按优先级出队 |
| `owner_dept_id` | BIGINT | Y | NULL | 归口科室 ID（逻辑外键 → M01-01），用于数据权限 |
| `owner_staff_id` | BIGINT | Y | NULL | 责任人职工 ID（逻辑外键 → M01-02） |
| `remark` | VARCHAR(500) | Y | NULL | 备注 |
| `last_run_at` | TIMESTAMP | Y | NULL | 上次执行时刻 |
| `last_success_at` | TIMESTAMP | Y | NULL | 上次成功时刻 |
| `last_period` | VARCHAR(16) | Y | NULL | 上次成功采集的期间 |
| `version` | INT | N | 1 | 乐观锁版本号，每次修改 +1 |
| `created_by` | BIGINT | Y | NULL | 创建人职工 ID |
| `created_at` | TIMESTAMP | N | `CURRENT_TIMESTAMP` | 创建时间 |
| `updated_by` | BIGINT | Y | NULL | 修改人职工 ID |
| `updated_at` | TIMESTAMP | N | `CURRENT_TIMESTAMP` | 修改时间 |
| `is_deleted` | BOOLEAN | N | FALSE | 逻辑删除标记 |

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m22_collect_task` | PRIMARY KEY | `id` | — |
| `uk_m22_collect_task_code` | UNIQUE | `task_code` WHERE `is_deleted = FALSE` | 任务编码唯一 |

| # | 决策 | 理由 |
|---|---|---|
| 1 | 任务编码 `task_code` 用业务语义（`CT_M16_REVENUE_DAILY`）而非自增 ID | 运维在日志、告警、排障邮件里引用的是编码；自增 ID 无法人读，且迁移环境后 ID 会变 |

### 4.3 表：`m22_collect_batch`（采集批次）

**用途：** 一次采集执行的**头**。批次号 `CB20261031-0001` 是本子模块对外的执行标识，P-08 采集状态查询、`m22.collect.completed` / `m22.collect.failed` 事件、以及下游报表的「数据是哪次采集来的」全部以批次号为锚点。

**批次与任务的区别：** 任务是「怎么采」的配置，只有一个；批次是「采了一次」的记录，每期一条。同一个任务在 10 月 30 日、10 月 31 日各产生一个批次。**批次写入后不可改期、不可改任务归属**，只允许状态推进与计数累加。

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | `uk_m22_collect_batch_push` 唯一索引是 P-01 幂等的**最后一道防线** | Redis 幂等键会过期、会被清、会在故障切换时丢；数据库唯一索引不会。即使两个请求同时穿过 Redis 判断，第二条也必然在 `INSERT` 时被拒，随后回读已存在批次返回同一结果。这是「重试 5 次不能把同一批指标写成五行」的唯一可靠保证 |
| 2 | `push_batch_no` 与 `batch_no` 分开两个字段 | `batch_no` 是 M22 自己的编号体系（`CB...`），`push_batch_no` 是调用方的编号（如 `M09-20261031-0001`）。两者格式、生成方、生命周期都不同，合并会导致「幂等键被 M22 内部重编号破坏」 |
| 3 | 用 `push_batch_hash` 区分「幂等重放」与「同号不同内容」 | 只有 `push_batch_no` 唯一索引，做不到两件事都正确：同一批重推 5 次应返回首次结果（幂等），而同一批号换了内容重推必须报错（防覆盖）。加一列内容指纹后两条路径都明确：指纹相同走重放，指纹不同抛 `PUSH_BATCH_CONFLICT`。指纹在 Service 层计算，对 `metrics` 按 `metric_code` 升序排序后规范化序列化，排除 `pushed_at` 等易变字段，保证「同样的数据无论推送顺序如何都得到同一个指纹」 |
| 3 | `params_snap` 存执行时的参数快照 | 任务配置随时可能被改。半年后审计问「2026-10-31 那次为什么超时」，需要知道当时的 `timeout_ms`；若只 join 任务表，拿到的是**现在**的参数，会得出错误结论 |
| 4 | `metric_success + metric_failed + metric_rejected + metric_unclaimed` 拆成四个计数字段而不是一个 `metric_count` | 部分成功是常态，报表层与运维必须能区分「采回来了 90 条、失败了 5 条、被拒 3 条、未注册 2 条」。只给一个总数就无法判断该不该告警 |
| 5 | `source_status` 取 `ck_..._partial_flag` 强制要求 PARTIAL 必须有 `missing_sources` | 铁律「绝不静默填 0」在数据库层的落地：任何标成 `PARTIAL` 的批次必须写清楚缺了哪些来源，否则不允许写入 |
| 6 | `period_start_date` / `period_end_date` 冗余 | `period` 是字符串（日/月/年三种格式混放），范围查询无法走索引。冗余两个 DATE 字段后，`WHERE period_start_date BETWEEN ...` 可以稳定走索引，也为将来跨粒度混查留出扩展余地 |
| 7 | `parent_batch_no` 而不只 `parent_batch_id` | 追溯链在日志与告警中以编号呈现；用编号可直接跨表、跨环境阅读，且批次重导时编号仍可对应 |
| 8 | 允许删除的条件限定为 `PENDING` | `RUNNING` 删掉会留下无人收尾的锁；`COMPLETED` / `PARTIAL` / `FAILED` 是审计证据，只能归档不能删（Service 层强制，数据库层用 `is_deleted` 标记） |

### 4.4 表：`m22_collect_batch_item`（采集批次明细）

**用途：** 批次内**逐指标**的取数结果。一条明细对应「这次执行里，这个 `metric_code` + `dept_id` + `biz_dim` 的组合，上游返回了什么、被转成了什么值、成没成功、为什么没成功」。明细记的是过程证据，最终数值另存于指标事实数据表 `m22_fact_metric`，本表**只增不改**，保留完整取数痕迹。

**为什么必须单独建表：** 取数失败、上游超时、口径不符被拒、`metric_code` 未注册这四种情况**都不会产生落库行**，但运维排障时必须知道它们发生过。若把过程写进存数值的那张表，就会出现「值为空的行」，而那表的唯一键语义是「这个维度组合的当前有效值」，两者语义冲突，必然导致「到底几行才对」无法回答。

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | `raw_value` 用 `TEXT` 而非 NUMERIC | 上游返回可能是 `"0.823500"`、`"82.35%"`、`"1234"` 甚至 `null`。原样存文本才能回答「上游到底给了什么」，转换失败时也能据此定位是格式问题还是口径问题 |
| 2 | `value` 用 `NUMERIC(20,6)` | 与事实表同精度。若明细用 `DECIMAL(10,2)` 而事实用 6 位，会出现「明细看着对、事实差一点」的核对失败 |
| 3 | `ck_..._success_value` 保证成功必有值 | 反向堵住「成功但值为空」这种最危险的状态：一旦允许，下游 `SUM` 会静默少算而不报错 |
| 4 | `ck_..._failure_msg` 保证失败必有码有因 | 铁律「上游不可用绝不静默」在明细层的落地。任何 `FAILED` / `REJECTED` / `UNCLAIMED` 必须带错误码与原因文字 |
| 5 | 重试新增明细而非改写 | 保留 `retry_seq` 与多条记录，才能统计「同一个指标连续几天失败」「重试第几次成功」 |
| 6 | `biz_dim` 默认 `NONE` 而非 NULL | 唯一键 `(metric_code, period, dept_id, biz_dim)` 里若含 NULL，PostgreSQL 的 NULL 不等于 NULL 会让唯一约束失效——同一维度组合可以插无数行。默认 `NONE` 是为了让唯一约束真正生效 |
| 7 | `metric_name` / `dept_name` 冗余快照 | 指标改名、科室改名后，历史批次详情仍应显示当时的名称；join 当前主数据会篡改历史展示 |
| 8 | 不建分区 | 年增约 200 万行，单表配合 `batch_no` / `period` 索引足够；且明细需保留整个审计期（≥3 年），分区后跨分区 join 事实表成本更高。若将来行数超过 5000 万，可按 `period` 月分区，届时需同时加 `DEFAULT` 分区 |

### 4.5 表：`m22_fact_metric`（指标事实）

**用途：** **本子模块的核心产出**。按 `(metric_code, period, dept_id, biz_dim)` 唯一的指标值行，每一行代表「某个指标、某个期间、某个科室、某个业务维度」的当前有效值，并携带六个溯源字段与完整性标志。M22-03~M22-08 的每一张报表、每一个看板、每一次排名，取数都从这张表出发。

**六要素溯源（本表的立表之本）：**

| 字段 | 回答什么问题 |
|---|---|
| `metric_code` | 这是哪个指标 |
| `period` | 是哪一期 |
| `dept_id` | 是哪个科室的口径 |
| `biz_dim` | 拆到什么维度 |
| `source_module` / `source_api` | 从哪个上游模块的哪个接口取的 |
| `collect_batch_no` | 是哪一次采集批次采回来的 |
| `source_status` | 这次取到的数据完整不完整 |
| `collected_at` | 什么时候取的 |

任何一个数字被质疑时，运维必须能只凭这一行回答上面八个问题。回答不了就说明这一行不该入库。

**分区策略（重要）：** 本表按 `period` 做**月 RANGE 分区**，分区键是 `period`（`period_month` 生成列），**不是** `collected_at`。理由：存在补采与重算场景——三月份的数据可能在五月份才补齐，此时数据必须落到三月分区，否则「按期间查三月数据」会漏掉它，按月归档历史分区时也会把补采数据错误地留在热区。同时必须有 `DEFAULT` 分区兜底，防止因为 `period` 格式异常（上游返回了非法期间）导致 `INSERT` 直接失败、整批采集崩溃。

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | 分区键用 `period_month` 生成列而非直接 `period` | `period` 是 `VARCHAR(16)`，日/月/年/时四种格式混放，直接拿它做 RANGE 分区键虽然可行但边界值写不对（`'2026-10-31' >= '2026-10'` 与字符串比较语义混淆）。生成列把「取前 7 位」这件事固化在数据库层，分区边界就是干净的 `2026-10` 到 `2026-11`。生成列还可以对非法期间给 `0000-00` 兜底，使脏数据落 DEFAULT 分区而不是报错整批失败 |
| 2 | **分区键是 `period` 不是 `collected_at`** | 补采场景必须落回原期间分区。若按落库时间分区，三月数据五月补采就进了五月分区，按期间查三月直接漏行，按月归档历史分区时也会把补采数据留在热区、越积越多 |
| 3 | 必须有 `DEFAULT` 分区 `m22_fact_metric_p_default` | PostgreSQL 对无匹配分区的行直接报 `no partition of relation ... found for row`。凌晨自动采集一旦因为上游返回了非法 `period` 而整批失败，就是「报表整天没有数」。DEFAULT 分区吸收脏行，再由质量校验任务把它们挑出来修正，可用性优先 |
| 4 | 唯一索引包含 `period_month` | 分区表上的唯一索引必须包含分区键，否则 PostgreSQL 拒绝创建。语义上不损失：`period` 决定 `period_month`，两者一一对应 |
| 5 | **采用「`metric_value` 可空 + `value_is_estimated` 标志」方案而不是禁止非 COMPLETE 时给值** | 两种方案对比：①禁止给值——最干净，但会丢掉「上游只给了 8 个科室、另外 2 个科室确实没有业务」这种合法的部分求和，报表层拿不到任何可用的数；②允许给值但强制标记——保留了部分可用的信息，同时用 `estimate_method` 强制说明「这个值是怎么来的」。选方案②，并用 `ck_m22_fact_metric_no_silent_zero` 把规则写进数据库：`source_status <> 'COMPLETE'` 时，要么值为 NULL，要么必须 `value_is_estimated = TRUE`。**「填 0」在这套约束下不可能发生**，因为填 0 而标 COMPLETE 需要伪造完整性，标非 COMPLETE 则必须同时置 `value_is_estimated` 并写 `estimate_method`，任何一步都会在报表层留下可见痕迹 |
| 6 | `ck_m22_fact_metric_estimate_method` 与 `ck_m22_fact_metric_estimate_method_null` 成对出现 | 前者禁止「估算了却不说怎么估的」，后者禁止「不是估算值却挂着估算方式」。单个 CHECK 无法同时表达两个方向，必须成对 |
| 7 | `ck_m22_fact_metric_failed_no_value` 单独约束 `FAILED` | `FAILED` 与 `PARTIAL` 不同：`PARTIAL` 是「有一部分」，可以给部分值；`FAILED` 是「完全没取到」，此时任何数值都是编的。所以在 `no_silent_zero` 之上再加一层，`FAILED` 一律不许有值 |
| 8 | 比率区间用 `metric_unit NOT IN ('RATE','RATIO')` 的正向白名单 | 若写成 `metric_value BETWEEN 0 AND 100` 一刀切，金额类（可能上千万）与人次类会被误伤。只有明确是比率/百分比的才限制区间 |
| 9 | `biz_dim` 默认 `NONE` 而非允许 NULL | 唯一键里有 NULL 时，PostgreSQL 认为 NULL 互不相等，唯一约束形同虚设——同一维度组合可以插进无数行，「采集幂等」直接失效。这是本表最容易踩的坑 |
| 10 | `missing_sources` 用 JSON 数组文本而非字符串拼接 | 报表层需要逐条列给用户看「缺了哪几项」，JSON 可被 `jsonb` 函数直接展开；逗号拼接在来源名本身含逗号时立刻崩 |
| 11 | `data_version` 与 `version` 两个版本号分开 | `data_version` 是**数据内容**版本，每次 upsert 覆盖 +1，下游 Redis 缓存以它判断是否失效；`version` 是**并发控制**版本，乐观锁更新失败重试用。合成一个会让「缓存失效」与「乐观锁冲突」互相干扰 |
| 12 | `metric_version` 记录口径版本 | M22-01 的指标口径允许升版。历史值必须锁在采集当时的口径版本上，否则口径一改，去年的数与今年的数就不可比，趋势图会凭空出现「跳变」 |

### 4.7 表：`m22_collect_failure`（采集失败与重试）

**用途：** 逐次失败与重试的流水账。一条记录对应「某个批次里某个指标有一次调用失败、准备第 n 次重试」。这张表是 P04 采集失败与重试页面的数据来源，也是「为什么今天的日报缺了视光收入」这个问题的第一手证据。

**与 `m22_collect_batch_item` 的分工：** 明细记录「这个指标最后是什么结果」，失败流水记录「这个指标中间失败了几次、每次为什么失败、下次什么时候重试」。一个指标重试 3 次后成功，明细只有一条 `SUCCESS`，失败流水有 3 条 `FAILED`。

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | `retryable` 区分确定性失败与临时性失败 | 上游返回「该科室不存在」这种错误，重试 5 次仍然是同样的结果，只会把失败队列拖长、把告警刷爆。只有超时、5xx、连接重置这类才值得退避重试。判定逻辑写在 Service 层，结果落库，重试调度器直接按 `retryable` 过滤 |
| 2 | `next_retry_at` 由落库时算出而不是调度时算 | 排障时能直接看到「它本该在 03:12:30 重试」，而不是只能看到「退避基数 30 秒」再自己算。也能让多个重试任务共用一条扫描 SQL |
| 3 | `retry_seq` 上限 CHECK 到 5 | 共享规范规定最大重试 5 次。数据库层挡住 6、7 次的无界重试，避免退避公式被误用后出现「隔 8 小时才重试昨天数据」这种荒谬调度 |
| 4 | `upstream_trace_id` 单独存 | 跨系统排障时，M22 的 `trace_id` 与上游的 `trace_id` 是两条链路，必须各自记录才能拼起来。只存一个会让上游说「我这边没报错」时无法对账 |
| 5 | `recovered_batch_no` 记录恢复后的批次 | 手动重试会另开一个批次（带 `parent_batch_no`），必须能把「哪次失败最终由哪个批次救回来」串上，否则补采链条断裂 |
| 6 | 不建分区 | 年增约 10 万行，体量小；且失败记录需要长期保留供故障复盘 |

### 4.8 表：`m22_collect_quality_check`（数据质量校验）

**用途：** 记录采集后与汇总后**质量规则的命中结果**。质量规则包括：空值检查、数值突变（环比超过阈值）、勾稽不平（收入各项之和 ≠ 总额）、跨期漂移（本期与历史同期偏离）、维度缺失（某科室应有数据却缺失）、单位异常（比率超出 0~100）。

**为什么质量结果要单独成表而不是塞进事实表的字段：** 一个事实可能同时命中三条规则（既突变又勾稽不平又维度缺失），是「一对多」；而且规则本身会随运营调整，历史命中结果必须按「当时的规则版本」留档，事后调规则不该改写历史。事实表只保留一个汇总性的 `quality_status` 字段供报表层快速过滤，明细在这里。

### 4.9 表：`m22_collect_calibration`（校准与修正）

**用途：** 人工校准与修正的**审批单串**。当采集回的数与业务实际明显不符（上游口径有偏差、本院有特殊换算、上游数据本身错了），由数据管理员提出校准申请，经审批后覆盖事实值。表里同时保留原值与新值，形成「谁在什么时候把 128,650.00 改成了 131,200.00、为什么改、谁批的」的完整审计链。

**为什么必须走单据而不是直接改事实表：** 直接 `UPDATE m22_fact_metric` 会把「这个数原来是多少」永久抹掉，而这正是审计最想知道的信息。校准单据把修正动作变成一个**可审查、可回滚、可追责**的业务事件：事实表被改的同时，`calibrated = TRUE`、`data_version` 自增，而原值仍在单据里。

| `dept_id` | BIGINT | Y | NULL | 科室 ID |

| `calibration_type` | VARCHAR(16) | N | `VALUE_FIX` | 校准类型：`VALUE_FIX`（数值修正）/ `STATUS_FIX`（完整性修正）/ `DIM_FIX`（维度归并） |

| 2 | `recheck_fact_version` 记录校准时的 `data_version` | 校准申请提出后、审批前，可能又发生了一次重新采集，把事实值改了。若审批时盲目覆盖，会覆盖掉更新的数据。生效前比对 `data_version`，不一致则退回重提 |
| 3 | `old_value` 允许为空 | 「原本没有值（`PARTIAL`）现在补上了准确值」是真实场景，此时原值就是 NULL，不能因为原值为空就拒绝校准 |
| 4 | `VALUE_FIX` 禁止新旧值相同 | 改动等于没改，说明申请人查错了行或上游其实是对的。让申请人重新确认比默默通过一个无效单据好 |
| 5 | `evidence` 存 JSON 数组而非单值 | 一次校准可能需要多份佐证（上游工单 + 科室说明 + 系统导出截图），JSON 数组可以容纳任意多份 |
| 6 | 允许删除 `DRAFT` | 草稿阶段的单据可以丢弃；一旦提交（`PENDING`）就是不删不改的审计对象 |
| 7 | 校准不新建事实行，而是就地更新 + 置 `calibrated = TRUE` | 事实现有唯一键不允许同一维度有两行。若追加一行，下游 `SUM` 会重复计算。修正必须「就地覆盖 + 留单据」 |

### 4.10 表：`m22_collect_source_health`（上游接口健康度）

**用途：** 按「上游模块 × 接口 × 小时」聚合的可用性指标。这张表回答 P07 上游接口健康度页面的核心问题：**哪个上游接口在今天上午 09 点挂了、挂了多久、现在恢复了没有、连续挂几天了**。它是采集失败与质量异常的**根因层**——报表缺数的原因往往不是 M22 采错，而是上游那一端没供上数。

**设计说明**

| # | 决策 | 理由 |
|---|---|---|
| 1 | 主键唯一键用 `source_api` + `stat_hour`，不含 `source_module` | 接口路径在全系统唯一（`/internal/v1/...` 前缀已含模块归属）。若把模块也算进唯一键，一旦某接口在配置里改了归属模块，同一小时会出现两行，健康度统计翻倍 |
| 2 | 保留 `latency_p95_ms` 而不只平均值 | 共享规范里上游契约都是按 P95 约定的（如 P-08 P95 ≤ 100ms）。平均值 50ms 但 P95 3 秒的接口，用户体验是「每分钟卡一次」，平均值会把它完全掩盖 |
| 3 | `sla_p95_ms` 随行存储 | 契约里的 P95 目标会变（比如 M16 从 2000ms 降到 500ms）。只存 `sla_breached` 布尔值，事后无法判断当时用的是哪个标准 |
| 4 | `alert_sent` 防重复告警 | 告警任务每小时跑一次，若不加标志，一个持续故障的接口每小时都会再发一条，一晚上能把值班手机充满 |
| 5 | `consecutive_fail_days` 由日聚合任务回填 | 「连续挂 3 天」需要跨日聚合，实时写入时算不出来。由每日 00:10 的任务回填前一天的连续天数，写入本表当天最后一行 |
| 6 | `health_status` 由成功率与 P95 双维度判定 | 只看成功率会漏掉「成功但极慢」；只看耗时漏掉「快速返回错误」。两者同时满足才算 `HEALTHY` |
| 7 | 不建分区 | 十六模块 × 平均 6.5 个接口 × 24 小时 × 365 天 ≈ 91 万行/年。单表加索引完全够用，若超过 5000 万再按 `stat_date` 月分区 |

### 4.11 表：`m22_collect_log`（采集日志与追溯）

**用途：** 追加写的事件流水。任务创建/修改/停用、批次启动/完成、事实落库覆盖、重试、告警发出、人工干预、校准生效，每一个改变系统状态的动作都在这里留一条。这是「审计追溯」与「问题复现」的最后一道依据。

**为什么有了 `m22_collect_failure` 还要日志表：** 失败表只记失败；日志表记**所有**状态变更，包括成功路径。当有人问「这个指标的值昨天是 96.5，今天变成 91.2，谁改的」，答案可能不是「失败后重算」，而是「昨天那次采集的批次被人工重算覆盖了」——这种正常路径的变化只能从日志里看出来。

## 4.13 Pydantic Schema 定义

本节给出 M22-02 对外与内部契约使用的全部 Pydantic V2 Schema。Schema 与 ORM 模型严格分离：ORM 只负责持久化映射，Schema 负责接口入参校验与出参序列化。所有 Schema 继承统一的 `CollectBaseSchema`，统一开启 `from_attributes=True`（V2 中替代 V1 的 `orm_mode`）与 `extra="forbid"`（入参严禁多余字段，避免调用方传错字段被静默忽略）。

### 4.13.5 内部契约 P-01 Schema（推送报表）

P-01 `POST /internal/v1/m22/report/push` 的请求/响应结构在共享规范 §8 已给定，本节把它落成可执行的 Schema。要点有三：

1. **`metrics` 逐条校验而不是整批失败**：单条 `metric_code` 未在 M22-01 注册、单位不匹配、值域越界，都只把该条判为 rejected，其余照常落库。响应里的 `accepted` / `rejected` 计数让调用方自行决定是否重推。
2. **`push_batch_no` 幂等**：同一 `push_batch_no` 重复推送，返回第一次的结果原样（含当时的 `rejected_detail`），不重新落库。若同一 `push_batch_no` 推送的内容与首次不一致，返回冲突错误码 `PUSH_BATCH_CONFLICT`，绝不静默覆盖。
3. **未注册指标进「待认领指标」表**：不是丢弃、不是失败，而是落 `m22_collect_unclaimed_metric` 等 M22-01 注册后由运维回放。

## 附录 E 建表依赖顺序与 Alembic 迁移

10 张表之间没有物理外键，因此建表顺序理论上互不依赖。但为了让 Alembic 自动生成的迁移脚本可读、可回滚，本节仍给出建议顺序与迁移步骤。

| 步骤 | 内容 | 说明 |
|---|---|---|
| 1 | `m22_collect_task` | 最先建，其余表都要引用 task_code |
| 2 | `m22_collect_batch` | 批次头，引用 task_code 但不建外键 |
| 3 | `m22_collect_batch_item` | 批次明细，只增不改 |
| 4 | `m22_fact_metric` 主表 | 建主表并声明 PARTITION BY RANGE (period_month) |
| 5 | `m22_fact_metric` 12 个月分区 | 从当前月起 12 个分区，命名 `p` 加 YYYYMM |
| 6 | `m22_fact_metric` DEFAULT 分区 | `PARTITION OF m22_fact_metric DEFAULT`，补采历史期间必须有它兜底 |
| 7 | `m22_collect_unclaimed_metric` | 待认领指标，独立于批次 |
| 8 | `m22_collect_failure` | 失败重试流水 |
| 9 | `m22_collect_quality_check` | 质量校验命中结果 |
| 10 | `m22_collect_calibration` | 校准单 |
| 11 | `m22_collect_source_health` | 上游健康度 |
| 12 | `m22_collect_log` | 日志表最后建，其余表写入时可留痕 |

Alembic 迁移注意事项：

1. 分区表的 `CREATE TABLE` 与 `CREATE TABLE ... PARTITION OF` 必须放在同一个迁移脚本里，中间不能插入其他 DDL，否则回滚会留下孤儿分区。
2. 新增月份分区用独立迁移脚本，每月 25 日由运维预建下月分区；漏建时数据落到 DEFAULT 分区，由质量规则 `QC_PARTITION_FALLBACK` 告警。
3. 所有索引一律带 `WHERE is_deleted = FALSE`（仅对有 `is_deleted` 列的表），事实表与只增不改表不加该条件。
4. 迁移脚本不得包含 `DROP TABLE`，下线表走「先改名为 `_bak_` 前缀，观察 30 天后再手工删除」的流程。
