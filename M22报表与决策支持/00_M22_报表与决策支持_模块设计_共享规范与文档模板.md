### 0.3 四条铁律（违反即返工）

| # | 铁律 | 原因 |
|---|---|---|
| **1** | **数量口径三处一致**：页面总览树 `P0x` = 第 5 章 `### 5.x P0x` 标题；表清单 = `### 4.x 表：` 标题；接口总览 `API-01` 起连续无断号且每项有 `#### API-xx` 详述 | 全仓统一标准，交叉引用依赖编号稳定 |
| **2** | **M22 不算业务数、不造业务数**：所有指标值一律从上游模块的统计接口取，**M22 只做「取数 → 校准 → 存储 → 展现 → 下钻」**。绝不在 M22 里写 `SELECT COUNT(*) FROM m05_admission` 这类跨模块直查业务表的 SQL | 跨库直查绕过上游口径，数字必然与业务模块对不上；且上游一改表结构 M22 就崩 |
| **3** | **技术栈 PostgreSQL 16**：不得出现 `AUTO_INCREMENT` / `TINYINT` / `DATETIME` / `ENGINE=` / `VARCHAR2` | 全仓已统一 PostgreSQL，MySQL 语法是硬错误 |
| **4** | **每个指标必须有唯一口径定义**：指标编码、名称、分子、分母、过滤条件、统计粒度、数据来源、刷新频率、异常处理（分母为 0 / 数据缺失 / 上游不可用）**九要素齐全**，且写进 `m22_metric_def` 表，不得散落在代码里 | 报表最大的纠纷是「这个数和那个数为什么不一样」。口径必须可查询、可追溯、可对比 |

> **M22 专属铁律（第 5 条）：口径变更必须走版本 + 审批，历史报表不重算。**
> `m22_metric_def` 采用「编码 + 版本」双键，口径一旦生效不得原地修改；变更生成新版本并记 `effective_from`。历史报表保留当时版本号（`calc_version`），**永不按新口径回溯重算**——这是财务与等级评审审计的硬要求。

> **M22 专属铁律（第 6 条）：报表必须标注「数据来源 + 生成时刻 + 是否完整」。**
> 每张报表实例必须带 `source_status`（`COMPLETE` / `PARTIAL` / `FAILED`）与 `generated_at`。上游任一数据源不可用时，报表可以出但它必须显式标注 `PARTIAL` 并列出缺失来源，**绝不静默填 0**。

## 1. M22 模块定位与子模块划分

### 1.1 一句话定位

**M22 报表与决策支持是全院唯一的「指标与报表中心」**：它把分散在 16 个业务模块里的统计口径**统一收口**，按「指标定义 → 数据采集 → 计算 → 存储 → 展现 → 下钻 → 导出」的链路，产出**日报、月报、科室报表、运营看板、管理驾驶舱**，为院领导、科室主任、财务提供决策依据。

### 1.2 与业务模块的边界（最容易做错的地方，必读）

| 维度 | 业务模块（M04/M05/M06/M09/M10/M11/M12/M13/M14/M15/M16/M17/M08/M07） | **M22 报表与决策支持** |
|---|---|---|
| **谁定义业务事实** | ✅ 业务事实的产生方 | ❌ 不产生任何业务事实 |
| **谁算业务统计** | ✅ 各模块自带统计（如 M05-07 床位效率、M09-06 手术室运营、M16-09 日结、M17-08 财务报表） | ❌ **不重算业务统计** |
| **谁定义指标口径** | 模块内口径（用于本模块页面） | ✅ **全院指标口径的唯一注册中心**（跨模块统一口径在 M22 定义） |
| **谁做跨模块汇总** | ❌ 各模块只管自己 | ✅ **唯一的跨模块汇总方**（如「全院收入 = 门诊 + 住院 + 视光 + 屈光」，只能 M22 拼） |
| **谁做趋势与对比** | 部分模块有本模块趋势 | ✅ **跨模块、跨期间、跨科室的趋势/同比/环比/排名** |
| **谁做报表模板与订阅** | ❌ | ✅ 报表模板、实例、订阅推送、导出 |
| **谁做数据下钻** | 本模块内 | ✅ 从汇总指标下钻到各模块明细（通过上游接口） |
| **谁做大屏驾驶舱** | ❌ | ✅ 管理驾驶舱、科室大屏、实时看板 |

**一句话：业务模块回答「发生了什么」，M22 回答「全院的指标是多少、和上期比怎样、哪个科室好、点进去明细是什么」。**

> ⚠️ **典型错误（务必避免）：** 在 M22 里写 `SELECT SUM(amount) FROM m16_settlement WHERE ...`。
> **正确做法：** 调 M16-09 的 `GET /internal/v1/m16/daily/summary/{date}` 或 M16-01 的 `POST /internal/v1/billing/statistics` 取数。

### 1.3 八个子模块划分

| 编号 | 子模块 | 核心职责 | 对应总体设计关键词 |
|---|---|---|---|

| 能力 | 归属 | 说明 |

## 2. 全局技术约定

### 2.2 统一响应格式

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "trace_id": "9f2c1d3e4b5a6c7d"

```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | int | `0` 成功；非 0 为错误码（**转成字符串比较**） |
| `message` | string | 提示信息 |
| `data` | object/array/null | 业务数据 |
| `trace_id` | string | 链路 ID，16 位十六进制 |

### 2.4 时间与数值

| 类型 | 规则 | 示例 |
|---|---|---|
| 时间戳 | `TIMESTAMP`，东八区，精确到秒 | `2026-10-31 14:30:00` |
| 日期 | `DATE` | `2026-10-31` |
| 统计期间 | `VARCHAR(7)` 格式 `YYYY-MM`；日粒度用 `DATE` | `2026-10` |
| **指标值** | `NUMERIC(20,6)`（6 位小数，比率与金额都够用） | `1234567.890000` |
| **金额类指标** | `NUMERIC(18,2)` | `1234567.89` |
| 比率/百分比 | `NUMERIC(9,6)`（`0.333333` 表示 33.3333%） | `0.297297` |
| 目标值 | `NUMERIC(20,6)` | `1500000.000000` |
| 数量/人次 | `BIGINT` | `12345` |

> **数值铁律：** 指标值一律 `NUMERIC`，**禁止 `FLOAT` / `DOUBLE` / `REAL`**。报表数字差一分钱都会被质疑。

### 2.5 幂等与并发

| 场景 | 方案 |
|---|---|
| 写接口 | 支持 `Idempotency-Key` 请求头，Redis `m22:idem:{biz}:{key}` TTL 24h |
| 采集任务 | 幂等键 `(metric_code, period, dept_id, biz_dim)` 唯一索引 |
| 报表生成 | 同一 `(template_id, period, scope)` 只允许一个实例，重复触发返回已有实例 |
| 采集并发 | Redis 分布式锁 `m22:lock:collect:{period}` |
| 指标读取 | 纯读，Redis 缓存 + `version` 失效广播 |

### 2.6 数据库硬规范

| 项 | 规则 |
|---|---|
| 主键 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| 布尔 | `BOOLEAN`，默认 `FALSE` |
| 时间戳 | `TIMESTAMP`（不用 `TIMESTAMPTZ`，全系统统一东八区） |
| 枚举 | `VARCHAR(32)` + `CHECK` 约束，**不建 PostgreSQL ENUM 类型** |
| 逻辑删除 | `is_deleted BOOLEAN DEFAULT FALSE` |
| 物理外键 | **不建**，由应用层与校验脚本保证 |
| 索引 | 部分索引 `WHERE is_deleted = FALSE` 必备 |
| 分区 | 指标事实表、报表行表按 `period` 月分区，**必须有 `DEFAULT` 分区** |
| 约束命名 | `ck_{表名}_{语义}` |
| 索引命名 | `idx_{表名}_{字段}` / `uk_{表名}_{语义}` |

> - **P-02 写错 → M11-08 的渠道 ROI 与 CPA 无法计算，降级为 `cost_snap = NULL`**
> - P-03 写错 → 各模块无法标注口径，数字对不上时无法追溯

## 17. 常见坑

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 页面总览写了 P09，第 5 章只写到 P08 | 先列总览，再逐页写，最后用脚本核对 |
| 2 | 接口总览跳号（API-12 直接到 API-14） | 分组标题行不占编号，写完用脚本扫 |
| 3 | 第 4 章留了表定义 | 详细设计第 4 章只放指引块 |
| 4 | 表数与指引块写的 N 不一致 | 数据结构文件写完 → 回填 N |
| 5 | 错误码用 M17 号段 `"1701xxx"` | M22 一律 `"220Nxxx"` |
| 6 | **在 M22 里直查业务表算指标** | 一律调上游统计接口，M22 只做汇总与展现 |
| 7 | **指标口径原地修改** | 口径变更走新版本 + 审批，历史报表不重算 |
| 8 | **上游不可用时指标填 0** | 标 `source_status = PARTIAL`，绝不静默填 0 |
| 9 | 指标值用 `FLOAT` | 一律 `NUMERIC(20,6)` |
| 10 | 枚举中文值（`'已发布'`） | 枚举一律英文大写，中文放附录字典 |
| 11 | **P-01 推送路径写错** | 必须 `POST /internal/v1/m22/report/push`，一字不差 |
| 12 | **P-02 投放成本路径写错** | 必须 `GET /internal/v1/m22/ad-spend`，一字不差 |
| 13 | 指标编码自创且重复 | 严格按 `{域}_{主题}_{指标名}` 全大写，全局唯一永不复用 |
| 14 | 多人并行写同一文件产生重复章节 | 用 `cat >>` 追加，交付前跑校验脚本的章节唯一性检查 |
| 15 | 表格单元格里出现裸竖线：绝对值符号、正则里的「或」、`\|\|` 逻辑或 | 单元格内禁用 `除转义外的裸竖线`。绝对值写 `abs(x)`；正则与含竖线的表达式一律**移到代码块里**写，表格中只写文字描述；确需在单元格内保留时用反斜杠转义 |
| 16 | 验收表编号加粗 | 写纯文本编号，不要加粗；脚本正则只匹配纯文本 |
| 17 | 报表实例缺少数据来源标注 | 必须有 `source_status` + `generated_at` + 缺失来源清单 |
| 18 | 把 M17 的法定财务报表在 M22 重做一遍 | M22 只做**分析看板**，法定报表仍读 M17 |
| 19 | **FastAPI 路由示例参数顺序错误**：`Annotated[str, Query()] = None` 写在 `user = Depends(...)` 之前，`ast.parse` 报 `non-default argument follows default argument` | 无默认值的依赖参数一律排在有默认值的查询参数之前；无法调整顺序时给依赖参数显式默认值 |
| 20 | **计数口径假警**：接口总览里出现 `API-05 新建模板` 这类引用行，被当成接口定义多数了一次 | 统计接口数时正则必须带方法列（`API-编号 后紧跟 GET/POST/PUT/PATCH/DELETE`），并限定在第 6.1~6.2 区段内统计 |
| 21 | **重复章节假警**：共享规范里模板嵌在四反引号代码块内，被重复检查脚本误判为重复附录 | 做唯一性检查前先剔除四反引号代码块再匹配 |
| 22 | 表单/接口里 `biz_dim` 之类的维度字段无值时存 `NULL` | 存空字符串 `''`。PostgreSQL 的 `UNIQUE` 认为 `NULL` 互不相等，存 `NULL` 会让唯一约束形同虚设 |
| 23 | 预警的 `object_id` 为空时用 `object_id = :object_id` 比较 | `NULL = NULL` 结果不为真，冷却期会彻底失效；必须 `COALESCE(object_id, 0) = COALESCE(:object_id, 0)` |
| 24 | 分区表忘记建 `DEFAULT` 分区 | 新月份第一批写入直接失败（`no partition of relation found for row`）；建分区表必须同时建 DEFAULT 分区，并每月 25 日预建下月分区 |
| 25 | 分区键用采集时间 `collected_at` | 必须用业务期间 `period`。补采场景下三月数据可能五月才采，按采集时间分区会让「查某月」扫全年 |
| 26 | 指标事实表只存最新值，不存口径版本 | 必须存 `metric_version`，否则无法回答「这份报表按哪版口径算的」 |
| 27 | **CHECK 只保护字段自身，不保护字段之间的组合语义** | 凡是「某个类型/状态必须配一整套参数」的场景，光写 `type <> 'X' OR col = 期望值` 是不够的——每条独立判定，组合起来仍可非法。必须另写一条**组合约束**，把这套参数作为整体判定。**判别方法：问「把这个类型改成另一种，再把各字段分别填成另一类型的合法值，能通过吗？」能通过，就缺组合约束。** 两个真实案例：①`m22_dashboard_def` 的 SCREEN 七项单列 CHECK 全过，但写成 DASHBOARD 的布尔位组合 + SCREEN 的 TTL/主题就能存进一块「开着交互的大屏」，已补 `ck_m22_dashboard_def_screen_combo`；②`m22_clinical_perf_pool.score` 的算式 CHECK 挡不住「把科室系数并入 `weight`」（`0.4 × 1.05 × 0.98 = 0.4116` 仍 ≤ 1 可通过），已补 `ck_m22_clinical_perf_pool_weight_pure` |
