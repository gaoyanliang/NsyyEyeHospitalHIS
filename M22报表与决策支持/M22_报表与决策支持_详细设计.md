## 1. 模块定位

### 1.1 一句话定位

**M22 报表与决策支持是全院唯一的「指标与报表中心」**：把分散在 16 个业务模块里的统计口径统一收口，按「指标定义 → 数据采集 → 计算 → 存储 → 展现 → 下钻 → 导出」的链路，产出日报、月报、科室报表、运营看板、管理驾驶舱，为院领导、科室主任、财务提供决策依据。

### 1.2 为什么报表与决策支持必须独立成模块

| # | 理由 | 事实支撑 |
|---|---|---|
| 1 | **口径分裂已经发生** | 上游 13 个模块自带统计接口（M04=2、M05=16、M06=11、M07=2、M08=9、M09=9、M10=3、M11=7、M12=7、M13=8、M14=9、M15=9、M16=5、M17=9，合计约 104 条路径），同一含义的指标在不同模块用不同名字（`m09_oper_count` / `m06_surgery_count` / `m11_surgery_count`），院周会上三个数字对不上 |
| 2 | **跨模块汇总无处安放** | 「全院收入 = 门诊 + 住院 + 视光 + 屈光」，这四个数字分别来自 M16、M16、M16-04、M11，**没有任何一个业务模块有权把别人的数字加起来** |
| 3 | **报表模板与订阅是横切能力** | 日报月报、科室报表、院长大屏都需要「模板 + 实例 + 订阅 + 导出」，在每个业务模块各做一遍会产生 8 套导出逻辑、8 套水印策略、8 套权限模型 |
| 4 | **决策支持需要独立的数据时效策略** | 业务模块的统计要求实时（下单即可见），决策看板要求稳定（同一份日报上午看和下午看必须一样），两者对缓存、快照、重算的要求相反 |
| 5 | **审计要求报表可回溯** | 三月份的报表必须能回答「按哪一版口径算的」，这要求口径版本与报表实例一起固化，业务模块没有这个概念 |

### 1.3 与相邻模块的边界

| 模块 | 归它的 | 归 M22 的 |
|---|---|---|
| M04 / M05 / M06 / M09 | 门诊日志、住院统计、日间手术、手术室运营的**业务事实与模块内统计** | 跨模块汇总、跨期间对比、排名、报表模板化 |
| M10 视光 / M11 屈光 | 视光销售事实、屈光咨询与手术事实、模块内转化漏斗（M11-08） | 视光/屈光主题的跨期趋势、多维度横向对比、投放 ROI |
| M12 检查 / M13 检验 / M14 药房 / M15 耗材 | 检查检验药耗的业务量与成本 | 主题分析、科室分摊后的对比 |
| M16 收费结算 | **金额的唯一权威**（收钱、开票、日结、退费） | 金额快照的汇总、对比、展示；**M22 不计算任何金额** |
| M17 财务核算 | **法定财务报表**（资产负债表、收入费用表、现金流量表）、科室损益、绩效金额 | 财务**主题分析**与看板；绩效**指标池**（不算钱） |
| M01 主数据 | 科室、职工、收费项目、术式、渠道等主数据 | **指标口径定义**（口径元数据不属于主数据） |
| M20 移动端 | 移动端界面与交互 | 通过 P-09 / P-10 提供驾驶舱数据与预警 |
| M23 系统管理 | 用户、角色、权限、日志存储 | 通过 P-06 / P-07 / P-08 提供报表与采集状态 |

> **一句话边界：业务模块回答「发生了什么」，M22 回答「全院的指标是多少、和上期比怎样、哪个科室好、点进去明细是什么」。**

### 1.4 一条不可逾越的红线

```
❌ 禁止：SELECT SUM(amount) FROM m16_settlement WHERE ...
❌ 禁止：SELECT COUNT(*) FROM m05_admission WHERE ...
❌ 禁止：SELECT SUM(total_amount) FROM m11_plan WHERE ...

✅ 正确：GET  /internal/v1/m16/daily/summary/2026-10-31
✅ 正确：POST /internal/v1/billing/statistics
✅ 正确：GET  /internal/v1/m11/statistics/metrics
```

**为什么这条红线必须硬性执行：**

| 直查业务表的问题 | 具体后果 |
|---|---|
| 绕过业务口径 | M16 的「净收入」在业务表里是三张表相减得到的，M22 直查 `m16_settlement.amount` 会得到毛额，与财务口径差一个退费额 |
| 表结构变更即失效 | 上游模块加索引、改分区、拆表时 M22 的 SQL 静默返回错误结果而不报错 |
| 无法溯源 | 报表上的数字说不出「来自哪个接口的哪个字段」 |
| 无法降级 | 上游不可用时 M22 直查会超时拖垮整个报表页 |

## 3. 指标与报表闭环

### 3.1 主闭环：定义 → 采集 → 计算 → 存储 → 展现

```
【上线前】M22-01 指标注册
   指标编码 / 九要素口径 / 单位 / 精度 / 数据来源接口
            │
            ▼
【每日 02:00】M22-02 采集任务编排（APScheduler 触发）
            │
            ├─▶ 调用上游统计接口（M04~M17 共约 104 条路径）
            │       │
            │       ├─ 成功 → 校验 metric_code 已注册 → 落 m22_fact_*
            │       └─ 失败 → 指数退避重试 5 次 → 仍失败标 FAILED + 告警
            ▼
【每日 03:00】M22-02 日结汇总（订阅 m16.daily.frozen）
   指标事实 → 日粒度 → 月粒度累加
            │
            ▼
【每月 1 日】M22-02 月结汇总（订阅 m17.period.closed）
            │
            ▼
【按需/定时】M22-03/04/05/06/07/08 报表生成
   取指标事实 → 套报表模板 → 生成实例 → 固化行数据 → 标记 source_status
            │
            ├─▶ 订阅推送（M03-05 message/send）
            └─▶ 导出（附水印 + 审计）
            │
            ▼
【实时】M22-08 驾驶舱 / 大屏 / 预警
   Redis 缓存（分级 TTL）→ 命中即返回；未命中回落指标事实表
```

### 3.2 外部推送入口（反向流）

**这是 M22 唯一的「被动接收」通道**，来自两个上游模块：

```
M06-07 日间手术质量与统计 ──┐
                            ├──POST /internal/v1/m22/report/push──▶ M22-02
M09-06 手术室运营与术中统计 ─┘        （push_batch_no 幂等）
                                            │
                                            ▼
                              校验 metric_code 是否已注册
                                     │            │
                                  已注册        未注册
                                     │            │
                                     ▼            ▼
                              落指标事实表   进「待认领指标」表
                                             （不整批失败）
```

> **M09-06 的铁律必须尊重：** M09-06 的 §10.1 写明「U-01 与 U-02 失败必须阻断统计。业务库不可用时任何数字都不可信」。这意味着 M09 在推送前已经做过自校验，M22 侧应当**优先信任并落库**，跳过的校验仅限「metric_code 是否注册」「period 格式」「数值类型」，**不得对业务合理性做二次判断**（例如不得因为「手术间利用率 > 1」就拒收——M09 可能真的超负荷运行）。

### 3.3 关键勾稽关系（必须成立的六条）

| # | 关系 | 说明 |
|---|---|---|
| 1 | **指标定义唯一生效** | 同一 `metric_code` 在任一时刻只有一个 `ACTIVE` 版本 |
| 2 | **事实唯一性** | 同一 `(metric_code, period, dept_id, biz_dim)` 只有一条事实记录 |
| 3 | **汇总守恒** | 日粒度事实按天累加 = 月粒度汇总值（除率值外） |
| 4 | **报表可溯源** | 报表每一行都能说出 `metric_code` + `metric_version` + `collect_batch_no` |
| 5 | **降级可见** | `source_status != COMPLETE` 的报表必须在页面上可见，不得显示成正常数字 |
| 6 | **历史不重算** | 已发布报表的口径与数值固化，口径升级只影响之后生成的报表 |

### 3.4 第 3~6 条勾稽关系的技术实现

| # | 关系 | 实现手段 |
|---|---|---|
| 3 | 汇总守恒 | 日结/月结汇总任务在事务内先删后插，并在汇总表上建 `CHECK (period_days > 0)`；每日汇总后跑一次对账任务比对日累加与月汇总，差异 > 0 即告警 |
| 4 | 报表可溯源 | `m22_report_instance.metric_versions` JSONB 字段记录 `{"OP_VISIT_COUNT": 3, ...}`；`m22_report_row` 每行带 `metric_code` / `metric_version` / `collect_batch_no` |
| 5 | 降级可见 | 报表实例的 `source_status` 由所有依赖指标的 `source_status` 中最差的一个决定（`FAILED` > `PARTIAL` > `STALE` > `COMPLETE`），报表页眉强制显示该状态与缺数说明 |
| 6 | 历史不重算 | `m22_report_row` 一经写入 `REVOKE UPDATE, DELETE`，重新生成产生新实例（新 `report_no`），旧实例置 `SUPERSEDED` |

## 4. 全局状态机

### 4.1 指标定义版本状态机（M22-01）

```
   ┌───────┐ 提交  ┌─────────┐ 审批通过 ┌────────┐ 废弃  ┌────────────┐
   │ DRAFT │──────▶│ PENDING │─────────▶│ ACTIVE │──────▶│ DEPRECATED │
   └───────┘       └─────────┘          └────────┘       └────────────┘
       │                 │                    │
       │ 作废            │ 驳回               │ 新版本生效时
       ▼                 ▼                    ▼ 自动降级
  ┌───────────┐    (回 DRAFT)           (变为 DEPRECATED)
  │ CANCELLED │
  └───────────┘
```

| 状态 | 中文 | 可否修改 | 说明 |
|---|---|---|---|
| `DRAFT` | 草稿 | ✅ | 可反复修改口径描述 |
| `PENDING` | 待审批 | ❌ | 需先驳回才能改 |
| `ACTIVE` | 生效中 | ❌ | 数据库部分唯一索引保证同编码仅一条 |
| `DEPRECATED` | 已废弃 | ❌ | 保留供历史报表溯源，不可再被采集任务引用 |
| `CANCELLED` | 已作废 | ❌ | 从未生效的版本 |

**强制手段：**

```sql
CREATE UNIQUE INDEX uk_m22_metric_def_active
    ON m22_metric_def (metric_code)
    WHERE status = 'ACTIVE' AND is_deleted = FALSE;
```

### 4.2 采集批次状态机（M22-02）

```
   ┌─────────┐ 开始 ┌─────────┐ 全部成功 ┌───────────┐
   │ PENDING │─────▶│ RUNNING │─────────▶│ COMPLETED │
   └─────────┘      └─────────┘          └───────────┘
                         │  │
                部分成功 │  │ 全部失败
                         ▼  ▼
              ┌────────────┐ ┌────────┐
              │  PARTIAL   │ │ FAILED │
              └────────────┘ └────────┘
                    │              │
                    └──────┬───────┘
                           │ 重试（指数退避，最多 5 次）
                           ▼
                      (回 RUNNING)
```

| 状态 | 中文 | 说明 |
|---|---|---|
| `PENDING` | 待执行 | 已建批次未开始 |
| `RUNNING` | 执行中 | 正在调上游 |
| `COMPLETED` | 全部成功 | 所有指标源状态均 `COMPLETE` |
| `PARTIAL` | 部分成功 | 有指标源状态为 `PARTIAL`（上游返回不完整） |
| `FAILED` | 失败 | 全部指标取数失败，已重试 5 次 |

> **`PARTIAL` 不允许降级为 `COMPLETED`。** 一旦批次被标记为 `PARTIAL`，只有「补采后重新生成新批次」才能得到 `COMPLETED`，原批次记录保持 `PARTIAL` 供审计。这是「绝不静默填 0」原则在状态机上的体现。

### 4.3 报表实例状态机（M22-03）

```
   ┌───────────┐ 生成完成 ┌───────────┐ 发布 ┌───────────┐
   │ GENERATING│─────────▶│ GENERATED │─────▶│ PUBLISHED │
   └───────────┘          └───────────┘      └───────────┘
         │                      │                   │
         │ 失败                 │ 重新生成           │ 被新实例替代
         ▼                      ▼                   ▼
   ┌────────┐            ┌────────────┐     ┌────────────┐
   │ FAILED │            │ GENERATING │     │ SUPERSEDED │
   └────────┘            │  (新实例号) │     └────────────┘
                         └────────────┘
```

| 状态 | 中文 | 可否改行数据 | 说明 |
|---|---|---|---|
| `GENERATING` | 生成中 | — | 后台任务执行中，前端轮询 |
| `GENERATED` | 已生成 | ❌ | 行数据已固化，待发布 |
| `PUBLISHED` | 已发布 | ❌ | 已推送订阅、已允许导出 |
| `FAILED` | 生成失败 | — | 记录失败原因与失败的上游接口 |
| `SUPERSEDED` | 已替代 | ❌ | 被新实例替代，保留供审计 |

### 4.4 经营预警状态机（M22-08）

```
   ┌─────────┐ 触发 ┌──────┐ 确认 ┌───────────┐ 关闭 ┌───────┐
   │ PENDING │─────▶│ OPEN │─────▶│ ACKNOWLEDGED│─────▶│ CLOSED│
   └─────────┘      └──────┘      └───────────┘      └───────┘
                        │                                   ▲
                        │ 冷却期内重复触发                   │ 自动关闭
                        ▼                                   │（指标回归正常）
                   (不新建，累加 trigger_count) ─────────────┘
```

| 状态 | 中文 | 说明 |
|---|---|---|
| `OPEN` | 待处理 | 刚触发，未有人确认 |
| `ACKNOWLEDGED` | 已确认 | 有人认领处理，记 `acked_by` / `acked_at` |
| `CLOSED` | 已关闭 | 人工关闭或指标回归正常后自动关闭 |

> **冷却与升级规则：** 同一条规则对同一对象（`rule_id` + `target_key`）在 24 小时内只触发一次新记录，重复命中累加 `trigger_count`；`trigger_count` 连续达到 3 次时级别由 `WARN` 升级为 `CRITICAL`。

## 5. 全局契约

### 5.1 M22 对外提供（P-01 ~ P-10）

## 6. 核心计算模型

> **本章只定义「跨子模块通用」的六个计算模型。** 各子模块自己的指标口径（如转化漏斗每环节、产品结构毛利）在子模块第 3.4 节详细定义，本章不重复。

### 6.1 指标取值（单指标单期间）

```
metric_value = f(分子, 分母)
```

其中 `f` 由 `m22_metric_def.calc_type` 决定：

| `calc_type` | 公式 | 单位 | 精度 |
|---|---|---|---|
| `COUNT` | 直接取上游返回的计数 | `COUNT` | 整数 |
| `AMOUNT` | 直接取上游返回的金额快照 | `CNY` | `NUMERIC(18,2)` |
| `RATE` | 分子 / 分母 | `RATE` | `NUMERIC(9,6)` |
| `AVG` | 合计 / 样本数 | 由单位决定 | `NUMERIC(20,6)` |
| `RATIO` | 本期值 / 基期值 | `RATIO` | `NUMERIC(9,6)` |
| `INDEX` | 组件加权求和 | `INDEX` | `NUMERIC(20,6)` |

- 存储精度：`NUMERIC(20,6)`
- **失败条件：** 分母为 0 → `metric_value` 存 `NULL`，不存 0，返回错误码 `"2202001"`
- **舍入：** 只在展示层舍入，存储层不提前舍入（避免层层舍入累积误差）

**算例：** 屈光转化率 `REF_CONVERSION_RATE`

| 项 | 值 |
|---|---|
| 分子：完成手术数 | 128 |
| 分母：初诊咨询数 | 856 |
| 计算 | 128 / 856 = 0.149533 |
| 存储 | `NUMERIC(20,6)` → `0.149533` |
| 展示 | `14.95%` |

**分母为 0 的算例：** 某新建科室本月初诊咨询 0 人、完成手术 0 台

| 处理方式 | 结果 | 是否正确 |
|---|---|---|
| 直接相除 | ZeroDivisionError 或 NULL | 需显式处理 |
| 填 0 | 显示 `0.00%` | ❌ **错误**，会被误读成「转化率极差」 |
| 存 NULL + 展示「—」 | 显示 `—`（无数据） | ✅ **正确** |

### 6.2 同比与环比

```
环比（MOM）= (本期值 − 上期值) / 上期值
同比（YOY）= (本期值 − 去年同期值) / 去年同期值
```

- 精度：`NUMERIC(9,6)`，展示为百分比两位小数
- **边界一：** 基期为 0 → 返回 `NULL`，展示「—」，错误码 `"2204001"`
- **边界二：** 基期为负（如结余为负）→ **不计算变化率**，改为计算「差值」并在页面标注「基期为负，变化率无意义」
- **边界三：** 窗口天数不同（如 2026-02 有 28 天、2026-03 有 31 天）→ 月环比看的是整月，**不做日均归一化**；但「本月至今 vs 上月同期」必须按天对齐，见 6.3

**算例：** 门诊收入 2026-10 = 1,286,400.00，2026-09 = 1,152,000.00，2025-10 = 1,034,500.00

| 指标 | 计算 | 结果 |
|---|---|---|
| 环比 | (1,286,400.00 − 1,152,000.00) / 1,152,000.00 | `0.116667`（11.67%） |
| 同比 | (1,286,400.00 − 1,034,500.00) / 1,034,500.00 | `0.243499`（24.35%） |

### 6.3 同期对齐（Month-to-Date 归一化）

**问题：** 2026-10-15 查看日报时，10 月才过 15 天，与 9 月整月对比毫无意义。

**规则：**

```
MTD 对比 = (本月第 1 天 ~ 第 N 天的值) vs (上月第 1 天 ~ 第 N 天的值)
```

- `N` = 当前月的日序号
- 若上月天数 < N（如 3 月 31 日对比 2 月）→ 上月取到月末，并标注「基期天数不足」
- 归一化展示：`日均值 = 区间值 / 区间天数`，保留 2 位小数

**算例：** 2026-10-15（N=15），本月门诊量 4,520 人次，上月同期（2026-09-01~09-15）4,180 人次

| 项 | 本期 | 基期 | 变化率 |
|---|---|---|---|
| 区间值 | 4,520 | 4,180 | `0.081340`（8.13%） |
| 区间天数 | 15 | 15 | — |
| 日均值 | 301.33 | 278.67 | `0.081340`（一致） |

### 6.4 科室排名

```
排名键 = 排序指标值（DESC 或 ASC，由 metric_def.rank_direction 决定）
排名方法 = RANK / DENSE_RANK / ROW_NUMBER（由指标配置决定）
```

**并列处理：**

| 方法 | 并列时 | 用于 |
|---|---|---|
| `ROW_NUMBER` | 不并列，按 tie-break 键（`dept_id`）强制定序 | 需要唯一名次（如绩效排名） |
| `RANK` | 并列同名次，后续跳号（1,1,3） | 需要体现「并列第一」的场景 |
| `DENSE_RANK` | 并列同名次，后续不跳号（1,1,2） | 需要「分档」的场景 |

**样本量下限：**

```
样本充足 = 样本量 >= metric_def.min_sample_size
```

- `min_sample_size` 按指标类型配置，默认：出院量类 `30`、手术类 `20`、危急值类 `10`
- 样本不足的科室**仍参与计算与展示**，但 `sample_sufficient = FALSE` 且不进入排名序列（`rank_no` 为 `NULL`），页面标注「样本不足，仅供参考」

**算例：** 5 个科室按手术量排名，`min_sample_size = 20`

| 科室 | 手术量 | 样本充足 | RANK | DENSE_RANK | ROW_NUMBER |
|---|---|---|---|---|---|
| 屈光 | 128 | ✅ | 1 | 1 | 1 |
| 白内障 | 96 | ✅ | 2 | 2 | 2 |
| 视光门诊 | 42 | ✅ | 3 | 3 | 3 |
| 眼底病 | 12 | ❌ | — | — | — |
| 门诊 | 0 | ❌ | — | — | — |

> 眼底病与门诊的 `rank_no` 为 `NULL`，页面显示「样本不足（12 < 20）」与「本月无手术」两种不同提示——**这是两个不同的降级原因，不能合并成同一句「数据不足」**。

### 6.5 目标达成率

```
达成率 = 实际值 / 目标值
```

- 精度：`NUMERIC(9,6)`
- **分母为 0 → 返回 `NULL`**，展示「未设目标」，错误码 `"2204002"`
- **目标方向：** `UP`（越大越好，如收入）与 `DOWN`（越小越好，如平均住院日），达成判定的比较方向相反
- **超标封顶：** 展示层可配置是否封顶 100%，**存储层永不封顶**

**算例：** 屈光科室 10 月收入目标 1,800,000.00，实际 1,850,000.00 → 达成率 = 1,850,000.00 / 1,800,000.00 = `1.027778`（102.78%）

**算例（目标方向 DOWN）：** 平均住院日目标 5.50 天，实际 5.20 天 → 达成率 = 5.50 / 5.20 = `1.057692`（超额完成）。注意**不是** 5.20 / 5.50 = 0.945455，方向不同分子分母要反过来。

### 6.6 报表完整性状态判定

```
source_status(报表) = 最差( 所有依赖指标的 source_status )
```

偏差序（差 → 好）：`FAILED` > `PARTIAL` > `STALE` > `COMPLETE`

| 组成 | 含义 |
|---|---|
| `COMPLETE` | 全部依赖接口成功且数据完整 |
| `STALE` | 数据是缓存的旧值（如上游今日未更新） |
| `PARTIAL` | 部分指标缺失或部分指标源状态为 PARTIAL |
| `FAILED` | 关键指标全部缺失 |

**算例：** 院长日报依赖 12 个指标，其中 10 个 `COMPLETE`、1 个 `STALE`、1 个 `PARTIAL`

→ 报表 `source_status = PARTIAL`（取最差），页面页眉显示「本报表有 1 项指标数据不完整（手术间利用率），1 项数据为昨日缓存（门诊人次）」
