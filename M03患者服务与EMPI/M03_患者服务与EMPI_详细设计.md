## 1. 模块概述

### 1.1 模块定位

M03 患者服务与EMPI 是全院**患者身份的唯一权威源**，同时承担面向患者的**服务触点**。

它回答三个问题：

1. **"这个人是唯一的一个患者吗？"** —— 患者主索引（EMPI）
2. **"这个患者在我们医院是什么身份？"** —— 会员
3. **"我们如何触达和服务这个患者？"** —— 随访、消息、门户

```
┌──────────────────────────────────────────────────────────────────────┐
│  M04 门诊 │ M05 住院 │ M07 医生站 │ M10 视光 │ M11 屈光 │ M12 检查   │
│  M13 检验 │ M14 药房 │ M16 收费  │ M18 EMR │ M19 随访运营 │ M20 移动 │
└────────────────────────────┬─────────────────────────────────────────┘
                             │ 全部以 patient_id / empi_no 引用

│  └────────────────────┬───────────────────────────────────────────┘  │
│         ┌─────────────┼─────────────┐                                │
```

### 1.2 模块目标

| 目标 | 指标 |
|---|---|
| **一人一档** | 同一患者只有一个 EMPI，重复率 < 0.1% |
| **院内外统一** | 挂号、检查、检验、药房、收费共用同一 `patient_id` |
| **可合并** | 疑似重复可匹配、可合并、可追溯 |
| **服务闭环** | 建档 → 预约 → 诊疗 → 随访 → 复诊 |
| **患者自助** | 公众号/小程序/自助机覆盖核心场景 |
| **数据合规** | 授权可查、撤回即时生效、全量审计 |
| **高性能** | 患者查询 P95 ≤ 50ms，建卡 P95 ≤ 300ms |

### 1.3 建设优先级依据

总体设计第 8.2 节：
> 2. **核心业务层**：患者服务与EMPI、门诊挂号、医生工作站…

M03 是核心业务层的第一个模块，理由：
- M04~M23 **全部业务模块**都以患者为主体
- 先建 M03，后续模块可直接引用 `patient_id` 契约

### 2.2 患者身份判定的三层机制

```
第一层：证件精确匹配（最强）
   primary_id_type + primary_id_no_hash → 唯一患者
        ↓ 未命中
第二层：多要素匹配评分（M03-02）
   姓名 + 性别 + 出生日期 + 手机号 + 地址 → 相似度评分
        ↓ 分数 ≥ 阈值 → 疑似重复，需人工确认
第三层：人工判断 + 合并（M03-02）
   确认同一人 → 合并 → 保留 survivor，其余重定向
```

## 4. 与相邻模块的职责分工

### 4.1 与 M01 的职责分工

**核心约定：`md_patient` 是 M01 侧的只读镜像，由 M03 单向推送。**

| 项 | M01 | M03 |
|---|---|---|
| `md_patient` 表 | **拥有（只读镜像）** | **推送数据** |
| 患者主档写入 | ❌ 不写 | ✅ **唯一写入方** |
| 患者查询（提供给其他模块） | ✅ 只读 | ✅ 权威 |
| 患者同步接口 | `POST /internal/v1/mdm/patients/sync`（接收方） | 调用方 |
| 职工档案 | ✅ 拥有 | 引用 |
| 科室字典 | ✅ 拥有 | 引用 |

**同步链路：**

```
M03-01 建档/修改/合并
   ↓ 写 mpi_patient + mpi_patient_sync_log(PENDING)
   ↓ 事务提交后发 Celery 任务
M03 推送客户端
   ↓ POST /internal/v1/mdm/patients/sync
M01 接收并 UPSERT md_patient
   ↓ 按 sync_version 判断新旧，防乱序覆盖
返回结果 → 更新 sync_log.sync_status
```

**失败处理：** 指数退避重试 5 次，仍失败则 `FAILED`，由每日对账任务兜底。

## 6. 核心流程

### 6.1 患者建档流程（院内）

```
导医查询患者
   ↓
按证件号精确查询
   ├─ 命中 → 直接使用 patient_id
   └─ 未命中 ↓
提交建档
   ↓
M03-02 匹配检查
   ├─ 无候选 → 直接建档
   └─ 有候选 → 提示"疑似重复"，人工判断
        ├─ 确认为同一人 → 使用已有 patient_id
        └─ 确认为不同人 → 建档
   ↓
M03-01 生成 EMPI + 落库
   ↓
M03-01 推送至 M01 md_patient
   ↓
返回 patient_id + empi_no
```

### 6.2 患者自助建档流程（院外）

```
患者扫码进入门户
   ↓
微信授权 / 手机号登录
   ↓
选择"自助建档"
   ↓
① 身份证拍照 OCR
   ↓
② M03-01 查重（by-id-card）
   ├─ 已存在 → 直接绑定
   └─ 不存在 ↓
③ 填写补充信息
   ↓
④ M21 二要素核验（不可跳过）
   ├─ 失败 → 重试，3 次锁定
   └─ 通过 ↓
⑤ 签署三份协议
   ↓
⑥ M03-01 建档（内部接口）
   ├─ 疑似重复 → 返回候选，患者确认
   └─ 成功 ↓
⑦ 绑定关系建立，verify_level = STRONG
   ↓
可预约
```

### 6.3 患者合并流程

```
发现疑似重复（自动检测 / 人工上报）
   ↓
M03-02 匹配评分
   ↓
生成合并申请
   ↓
审批（病案管理员）
   ├─ 驳回 → 结束
   └─ 通过 ↓
执行合并（事务）
   ├─ 确定 survivor（保留哪个）
   ├─ 更新 mpi_patient_merge
   ├─ 业务表重定向 patient_id（各模块配合）
   ├─ 写 mpi_patient_merge_detail
   └─ 发布事件 mpi.patient.merged
        ↓
   订阅方处理：
   ├─ M03-06 门户绑定重定向
   ├─ M03-03 会员重定向
   ├─ M03-04 随访计划重定向
   ├─ M03-05 消息接收人重定向
   └─ 其他业务模块按需处理
   ↓
推送 M01 更新镜像
```

### 6.4 随访任务生成流程

```
触发事件（手术完成 / 出院 / 诊断 / 手动）
   ↓
M03-04 匹配随访模板
   ↓
生成随访计划
   ├─ 计划主档
   └─ 按模板节点展开为任务
        ↓
   按分派规则分配执行人
   ├─ 按科室 / 按医生 / 按随访组 / 轮询
   └─ 计算计划执行日期
   ↓
M19 拉取任务
   ↓
M19 执行（电话/微信/门诊）
   ↓
M19 回写结果
   ↓
M03-04 更新任务状态
   ↓
逾期未执行 → M03-04 标记逾期 + 升级提醒
```

### 6.5 消息发送流程

```
业务事件（预约成功/报告已出/随访提醒）
   ↓
M03-05 匹配消息模板
   ↓
渲染内容（变量替换）
   ↓
黑名单检查
   ├─ 患者已退订 → 跳过
   └─ 未退订 ↓
频控检查
   ├─ 超频 → 延后或跳过
   └─ 通过 ↓
选择渠道（短信 / 微信模板消息 / 公众号）
   ↓
经 M21 发送
   ↓
记录发送结果与回执
```

## 12. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|
| **重复患者率高** | 医疗安全、统计失真 | **高** | 强证件校验 + 匹配评分 + 定期治理 |
| **患者合并出错** | 数据混乱 | 中 | 审批 + 事务 + 可回滚 + 全量留痕 |
| **合并后业务未重定向** | 数据孤岛 | **高** | 事件驱动 + 各模块必须订阅 + 对账 |
| **门户患者越权** | 隐私事故 | **高** | 强制归属校验 + 验证等级 + 审计 |
| **M01 镜像不同步** | 查询不一致 | 中 | 异步推送 + 对账任务 |
| **证件信息泄露** | 合规事故 | 中 | 三列存储（加密/哈希/掩码） |
| **门户高并发** | 服务不可用 | 中 | 限流 + 缓存 + 弹性扩容 |
| **随访任务量大** | 执行不过来 | 中 | 分派规则 + 优先级 + 逾期升级 |
| **消息被投诉** | 患者投诉 | 中 | 黑名单 + 频控 + 授权管理 |
| **自助建档误建** | 重复数据 | 中 | 查重 + 候选确认 + 强制核验 |

### 12.1 最大风险：患者重复与越权

**风险 1：重复患者**

一旦出现重复患者，会导致：
- 病历分散在两个 EMPI
- 用药、过敏史不完整（医疗安全）
- 统计失真

**对策：**
1. 建档前强制查重（证件 + 匹配评分）
2. 高相似度必须人工确认
3. 定期数据质量扫描（M03-02）
4. 合并机制完善且可追溯

**风险 2：门户越权**

患者看到他人数据是**重大隐私事故**。

**对策：**
1. **强制归属校验**：每个查询都必须校验 `binding.patient_id`（不是靠前端）
2. 验证等级门槛：报告、病历需 STRONG
3. 唯一索引保护：一个患者只绑一个账号
4. 全量审计：每次敏感查看写 `sys_audit_log`
5. 越权测试用例：不同患者交叉验证
