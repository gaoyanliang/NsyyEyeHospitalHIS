### 三条不可动摇的数据设计原则

| # | 原则 | 在本文件中的体现 |
|---|---|---|
| **1** | **会员身份唯一权威在 M03-03** | `m10_member_profile.member_no` 是**引用字段**而非生成字段，唯一索引只保证「一个成员号最多一张视光档案」；M10 不建会员号序列、不建等级表、不建成长值字段 |
| **2** | **金额真值只在 M16** | 本文件 9 张表中**没有任何一张表存储实收金额、折扣后金额、优惠金额**；只有「比例参数」「标价参考额（仅供占比展示）」「快照金额（只读镜像）」三类，且每一类在字段说明中都标注了权威方 |
| **3** | **核销必须幂等且可追溯冲减** | `m10_member_package_use` 用两重唯一索引实现幂等（`uk_pkg_use_idem` + `uk_pkg_use_occur`），任何冲减都用「新增负向流水」实现，**从不 UPDATE 历史核销行** |

| 4.3 | `m10_member_level_snap` | 会员等级与权益快照表 |
| 4.4 | `m10_member_benefit` | 视光专属权益定义表 |
| 4.5 | `m10_member_package` | 配镜套餐定义表 |
| 4.6 | `m10_member_package_item` | 套餐内容项表 |
| 4.7 | `m10_member_package_sale` | 套餐售出记录表 |
| 4.8 | `m10_member_package_use` | 套餐核销记录表 |
| 4.9 | `m10_member_care` | 会员关怀与召回任务表 |
| 4.10 | `m10_member_stat` | 视光会员经营统计表 |

**为什么是这 9 张表：**

| 表 | 回答的问题 | 若不建这张表会怎样 |
|---|---|---|
| `m10_member_profile` | 这个会员在**视光场景**下是什么人（首次配镜、累计配镜、儿童防控、OK 镜戴镜） | 每次判断套餐准入都要回查 M10-06 订单，500ms 级联调用 |
| `m10_member_level_snap` | 他现在的等级与视光权益参数是多少（M03-03 的本地投影） | 每次收银都要同步调 M03-03，且 M03 不可用时视光收银直接瘫痪 |
| `m10_member_benefit` | 视光专属权益（清洗/调整/质保/验光折扣）长什么样 | 只能把视光权益塞进 M03-03 的通用权益表，破坏 M03 的「全院通用」语义 |
| `m10_member_package` | 我们卖哪些配镜套餐、卖多少钱、有效期多久 | 套餐只能当普通商品卖，无法表达「2 次验光 + 4 次复查」这种多次权益 |
| `m10_member_package_item` | 套餐里包含什么（几次/几件/哪些服务） | 套餐内容硬编码在代码里，运营改一次要发一次版 |
| `m10_member_package_sale` | 谁在什么时候买了哪个套餐、卖出的套餐剩多少 | 无法追溯套餐来源销售单，退换时不知道冲减哪一个 |
| `m10_member_package_use` | 每次核销了哪个套餐的哪一项、几次 | 无法防重复核销，也无法回答「为什么他的复查免费」 |
| `m10_member_care` | 该给谁打电话（久未配镜召回、生日、复查提醒） | 召回靠人工翻 Excel，遗漏率高且无法量化效果 |
| `m10_member_stat` | 会员经营得怎么样（新增、复购、套餐核销率、召回转化） | 每日经营看板实时聚合 5 张表，P95 超过 8 秒 |

### 4.2 表：`m10_member_profile`（视光会员档案表）

**用途：** 视光会员档案表，**一会员一档案**。本表不是会员主档，而是 M03-03 会员在**视光场景下的投影 + 视光专属属性**。

**三方分工（这张表存在的唯一理由）：**

| 数据 | 权威方 | 本表角色 |
|---|---|---|
| 会员号 `member_no`、患者 `patient_id`、等级 `level_code`、状态 `status` | **M03-03 `mpi_member`** | 引用与冗余快照，**M10 不生成、不改写、不降级判定** |
| 成长值、积分、消费额 | **M19（成长值与积分）/ M16（消费额）** | **本表不存储**，按需实时查 M19 |
| 首次配镜日期、累计配镜次数、儿童近视防控绑定、OK 镜戴镜会员 | **M10-08 本表** | 唯一权威 |
| 累计配镜金额 | **M16-04 `m16_optical_order`** | 只读镜像（`total_fit_amount_snap`），仅供列表展示，**不得用于任何金额计算** |

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键，视光档案 ID |

**设计要点：**

1. **为什么 `member_no` 是 NOT NULL 且带唯一索引，而 M10 不生成它？**
   因为视光档案**必须挂在真实会员上**。若允许 M10 自建 `VM` 号（共享规范 §3.4 预留了 `VM` 前缀），就会出现「两个会员号指向同一个患者」的分裂。本设计**明确放弃 `VM` 号**：视光会员号 = M03-03 会员号。`VM` 号段保留给未来的「视光储值卡卡号」，不作为会员标识。唯一索引的作用是保证「同一个 M03 会员不会有两份视光档案」。

2. **为什么 `profile_status` 与 `member_status` 要分开？**
   M03 的会员状态是**全院商业身份**（是否还能享受挂号折扣、积分倍率），M10 的档案状态是**视光场景可用性**。典型场景：会员在门诊欠费被 M03 冻结，但他在视光中心上周买的护理液套餐还没领完——若直接用 M03 状态控制，会导致「已付钱的 8 瓶护理液领不到」，这是典型的客诉源。分开后：`member_status = FROZEN` 时视光权益折扣不可用，但 `m10_member_package_sale` 的核销不受影响（见 8.3 规则）。

3. **为什么 `total_fit_amount_snap` 要专门加注释禁止参与计算？**
   这是本子模块**最容易踩的坑**。字段名叫「累计配镜金额」，实现者很容易写 `if amount >= 10000: 给 VIP 价`。但金额的权威在 M16，镜像可能因延迟而落后几分钟到一天；用它做决策会导致「同一笔单在 10:00 判定为金卡、10:05 判定为银卡」。因此：**该字段只允许出现在 `ORDER BY`、列表展示、日报分组中**，任何折扣/套餐判定只能读 `m10_member_level_snap`。

4. **为什么用表达式索引 `(EXTRACT(MONTH...), EXTRACT(DAY...))` 做生日索引？**
   生日关怀任务每天需要扫「今天过生日的会员」。若写成 `WHERE EXTRACT(MONTH FROM birth_date) = 10 AND EXTRACT(DAY FROM birth_date) = 31`，普通 B-Tree 索引完全失效（函数计算），6 万行全表扫约 12ms。表达式索引后走索引扫描约 0.4ms。代价是索引必须在 `birth_date` 更新时重建——生日几乎不变，代价可以可以忽略，

5. **为什么 `care_opt_in` 默认 `TRUE`？**
   视光中心的召回是靠微信/短信拉客到店的，默认关闭会显著降低召回率。但同时必须遵守合规要求：会员在 M03-03 或门户可以关闭，关闭后本表的 `care_opt_in` 由 `m03.member.preference_changed` 事件同步为 `FALSE`，`job_member_recall_scan` 直接跳过。

6. **为什么不建物理外键？**
   ①`member_no` / `patient_id` 指向 M03 的库表，跨模块外键会让 M03 的会员注销被 M10 阻塞 ②`store_id` / `primary_optometrist_id` 指向 M01 主数据 ③`m10_order` / `m16_optical_order` 的引用同样不建外键（全模块统一约定，见共享规范 §2.6）。一致性由应用层校验 + 每日 01:30 的 `reconcile_member_refs` 对账任务保证。

### 4.3 表：`m10_member_level_snap`（会员等级与权益快照表）

**用途：** 会员等级与视光权益参数的**本地投影 + 版本留痕**。每个会员每次等级变化或权益参数变化产生**一条新版本**，旧版本置 `is_current = FALSE` 保留。

**为什么需要快照，而不直接每次调 M03-03：**

| 角度 | 直接调 M03-03 | 本地快照 |
|---|---|---|
| 收银耗时可接受度 | 每次开单多一次 30ms 远程调用，叠加 M01-08 取价、M16 试算后总耗时 +30ms | 本地索引点查 ≤ 1ms |
| M03 不可用 | 视光收银**直接瘫**（无法判断折扣率） | 用最近一次快照，`is_stale = TRUE` 标记，按 `MEMBER.LEVEL_SNAP_MAX_STALE_MIN` 判定是否放行 |
| 追溯「当时是什么等级」 | M03-03 只存当前等级，历史在 M03 日志里且格式不定 | 本表按版本留存，直接可查「2026-10-31 该会员是金卡，视光折扣 9 折」 |
| 视光专属权益参数 | M03-03 无此概念 | 本表合并「M03 等级权益参数」+「M10 视光专属权益参数」为一体，输出给 M16-06 |

**设计要点：**

1. **为什么权益要合并「M03 等级权益」与「M10 视光专属权益」成一个快照？**
   M16-06 做优惠试算时，需要一次拿到「该患者在本单可用的全部优惠参数」。如果拆成两次调用（M03 一次 + M10 一次），会产生 ①两次往返 ②两次调用之间的时间差导致参数不一致 ③M16-06 需要自己合并去重。合并后：**P-22 一次返回全部，M16-06 只做纯计算**，职责最干净。

2. **为什么 `benefit_digest` 用 SHA-256 而不是 MD5？**
   安全审计要求（M02）对权益参数这类可篡改即等于「可直接改钱」的数据，摘要算法不得使用 MD5/SHA-1。64 位十六进制同时用于缓存 Key 与幂等比对：M03 推送等级变化事件时若 `benefit_digest` 未变（只是等级名称文案变了），**不产生新版本**，避免快照表被无意义的版本刷爆。

3. **为什么 `is_current` 用部分唯一索引而不是触发器保证？**
   PostgreSQL 16 的部分唯一索引 `WHERE is_current = TRUE` 天然保证「一会员最多一条 TRUE」，且并发事务中第二个 UPDATE 会直接抛唯一约束冲突（比触发器更早阻断、开销更低）。应用层配合 `UPDATE ... SET is_current = FALSE WHERE member_no = ? AND is_current = TRUE` 再 INSERT 的顺序执行，即为「版本切换」的原子操作。

4. **为什么 `level_change_type` 区分 `UP` / `DOWN` / `MANUAL` / `INIT` / `BENEFIT`？**
   前四类来自 M03-03 的 `mpi.member.level_changed`（对应 M03 的 `level-up` / `level-down` / 手工调整 / 初始化）。第五类 `BENEFIT` 是 M10 独有的：**等级没变，但运营调整了视光权益参数**（例如把金卡的验光折扣从 85% 改为 80%）。若把 `BENEFIT` 也当成等级变化上报，会导致 M19 的成长值统计被污染。

5. **快照陈旧时怎么办（`is_stale = TRUE`）？**
   分两档（详见详细设计 §8.7）：
   - 陈旧时长 ≤ `MEMBER.LEVEL_SNAP_MAX_STALE_MIN`（默认 60 分钟）：P-22 正常返回参数 + `degraded = true`，M16-06 正常试算。
   - 陈旧时长 > 60 分钟：P-22 返回 `"1008018"`，M16-06 按「无会员权益」处理（等于普通客户），保证收银不堵。

**量级估算：**

| 项目 | 数值 | 说明 |
|---|---|---|
| 年版本数 | 约 60,000 条 | 4,000 会员 × 平均 15 次变更（等级 + 权益调整） |
| 15 年总量 | 约 90 万行 | 视光会员分层活跃，等级变更频次远高于全院平均 |
| 单行平均长度 | 约 1,150 字节 | 含 `benefit_snapshot` JSONB |
| 表大小（15 年） | 约 1.0 GB | — |
| 当前版本行（`is_current`） | 约 6 万行 | 部分索引只覆盖这一部分 |
| 当前版本索引体积 | 约 4 MB | 相比全量索引 90 MB，节省 95% |

**分区：** 不分区。虽然 90 万行较大，但**热查询只命中 `is_current = TRUE` 的 6 万行**（部分索引），历史版本仅供追溯（按月批量查询，单月约 5,000 行）。若未来需要归档，可按 `effective_from` 年做 `DETACH PARTITION` 离线归档，但这属于运维优化，不属于首版设计。

### 4.4 表：`m10_member_benefit`（视光专属权益定义表）

**用途：** 定义视光中心自己卖的会员权益 — 镜布、清洗、免费调整、验光折扣、质保延长等。这些权益**不属于 M03-03 的全院通用权益体系**（M03 的权益是「检查费 9 折」「积分 2 倍」这类跨科室通用的），而是视光场景特有的、带次数与期间的权益。

**与 M03-03 权益体系的关系（最容易混淆的地方）：**

| 维度 | M03-03 `mpi_member_benefit` | M10-08 `m10_member_benefit` |

| 记录什么 | 全院通用权益**定义**（折扣率、积分倍率、生日礼） | 视光专属权益**定义**（清洗、调整、质保延长、验光折扣） |
| 作用域 | `ALL` / `CHARGE_CLASS` / `CHARGE_ITEM` / `OPTICAL` / `REFRACTIVE` / `MEMBER_ONLY` | 固定为 `OPTICAL`（视光域），细分到「品类 + 动作」 |

| 谁能改 | 信息科 / 财务科（M03-03 P05） | **视光中心运营主管**（M10-08 P04） |
| 谁在用 | M04/M11/M16 全部消费场景 | **仅 M16-06 视光优惠试算 + M10 内部** |

**设计要点：**

1. **为什么权益要带 `times_limit` / `times_period`，而 M03-03 的权益不带？**
   M03-03 的权益是「资格型」的（金卡就享 9 折，没有次数概念），核销记录归 M19。视光权益大量是「次数型服务」：免费清洗不限次、免费抛光每年 1 次、质保延长每年 1 次。若强行塞进 M03，会把 M03 的通用权益表变成一张塞满视光语义的杂表。

2. **`fixed_price_ref` / `deduct_amount_ref` 为什么叫「参考」？**
   因为**本模块不产出任何金额真值**。这两个字段只出现在：①P04 权益配置页的「试算对比」预览 ②P04 权益说明文案。任何真正的成交价计算都必须走 `POST /internal/v1/m16/discount/calc`。字段名加 `_ref` 后缀就是给实现者的一个物理提醒：**看到 `_ref` 就不能拿它算钱。**

3. **为什么 `require_child_myopia` 单独设一个布尔位，而不是用 `scope_value` 表达？**
   儿童近视防控是一个**会员属性**（`m10_member_profile.is_child_myopia`），不是商品属性。用 `scope_value` 表达会需要写 `scope_value = 'CHILD_MYOPIA'` 这种伪商品码，污染品类字典。用布尔位后，P-22 组装权益时的判定变成一次 `IF profile.is_child_myopia`，语义清晰且可索引。

4. **`times_used_by_member` 是冗余计数，为什么要放？**
   因为 P-22 要求 P95 ≤ 100ms，且被 M16-06 在每次优惠试算时调用（一天 300+ 次）。若每次都从 `m10_member_package_use`（27 万行）`SUM(use_qty)` 聚合，单会员聚合约 3ms，尚可；但一次优惠试算要评估 3~5 条次数型权益，累计 15ms 就吃掉 SLA 的 15%。冗余计数字段让 P-22 变成纯点查。一致性靠 **核销事务内同步更新 + 每日 02:10 的 `reconcile_benefit_count` 对账**保证。

5. **为什么 `approval_no` 的 CHECK 里带了一个 `created_at < '2026-11-01'`？**
   这是一条**过渡期兼容条款**：初始化脚本会预置 12 条权益，这些行没有审批单号（配置初始化不属于变更）。用 `created_at` 早于上线日来放行，避免初始化时因 CHECK 失败导致建库中断。上线后的任何折扣率变更都必须带审批单号，否则插入/更新被数据库直接拒绝。

**量级估算：** 配置类表，约 120 行（含停用历史版本），单行约 600 字节，总计约 72 KB。**不分区。**

### 4.5 表：`m10_member_package`（配镜套餐定义表）

**用途：** 视光套餐的**产品定义**。一个套餐 = 一组打包销售的组合权益，例如「儿童近视防控年卡 = 2 次验光 + 1 副离焦镜片 + 4 次复查 + 无限次调整」。

**套餐与普通商品的本质区别：** 普通商品是「一手交钱一手交货」，一次交易一次交付；套餐是「一次付钱、多次交付」，**付钱和交付在时间上是分离的**。这决定了套餐必须有：

1. **内容项定义**（`m10_member_package_item`）：告诉系统「这张卡里到底有什么」。
2. **售出记录**（`m10_member_package_sale`）：告诉系统「谁买了、哪一单买的、还剩多少」。
3. **核销流水**（`m10_member_package_use`）：告诉系统「这一次消耗了什么、还能不能退」。

本表只负责第 1 层的「定义」。

| `grace_days` | number | 否 | 未核销全额退的宽限天数 | 默认 7 |

```json
{

  "mode": "ITEM_ALLOWED",

  "refund_basis": "REMAINING_RATIO",

```

> ⚠️ **`refund_basis` 只给口径，不给算法。** 真正的退款金额由 M16-08 退费与冲红计算；M10 的职责是提供「已核销比例」与「已核销项标价扣减口径」两个参数。参见详细设计 §3.4.5。

**设计要点：**

1. **为什么要版本号 `version_no` + `is_active` + `prev_package_id`，而不是直接改行？**
   套餐一旦售出，其内容就是**合同**。如果运营在 2026-11 把防控年卡从「4 次复查」改成「3 次复查」，已经买卡的 500 位会员不应受影响。版本化后：老卡继续按老版本核销（`sale.package_version` 指向旧版本），新卡按新版本。`prev_package_id` 让运营能一眼看到「这个套餐改过几次、每次改了什么」。

2. **为什么 `price_ref` 只是「参考额」，实际收费走 `charge_item_code`？**
   因为视光套餐的收费是由 M16-04 建销售单、走 M16-01 计费引擎的。如果 M10 自己存一个「成交价」，就出现了**第二份价格真值**，必然与 M16 对不上账。正确做法是：套餐在 M01-06 建档为一个组合收费项目，M10 只记它的编码；M16 按该项目取价，M10 的 `price_ref` 仅用于「套餐内项目原价对比」（如「原价 2,180 元，套餐价 1,680 元」这类营销话术），而这句话里的 1,680 也必须是**从 M16 取价接口拿到的**，不是本字段。

3. **为什么 `is_active = FALSE` 时历史售出的仍可核销？**
   这是套餐设计的生命线。运营下架一个套餐（卖不动了 / 供应商断货）不等于「已卖的卡作废」。核销逻辑（`m10_member_package_use`）只校验 `sale.sale_status` 与 `sale.expire_date`，**不校验 `package.is_active`**。

4. **为什么 `max_extend_days <= valid_days`？**
   防止「365 天的卡通过权益延长 3 年」这类异常。延长总量不得超过套餐本身有效期，这是业务底线。注意 `valid_days = 0`（永久套餐）时此约束自动放行。

5. **为什么 `refund_policy` 用 JSONB 而不用关系表？**
   退换策略是**按套餐类型整体配置**的（防控年卡一个策略、护理液套餐另一个策略），不存在「按项配置不同策略」的需求，且查询方式是「整条取回后由服务层判定」，不做按策略字段的 SQL 过滤。用 JSONB 避免为 4 个字段建 1 张表 1 个 1:N 关联。代价是数据库层无法约束内部键——因此加了 `? 'allow_return'` 与 `? 'mode'` 两个结构完整性 CHECK 兜底。

**量级估算：** 配置类表，约 80 行（含历史版本），单行约 1,600 字节（含两个 JSONB），总计约 128 KB。**不分区。**

### 4.6 表：`m10_member_package_item`（套餐内容项表）

**用途：** 定义套餐「里面到底有什么」。一个套餐包含 1~N 个内容项，每个内容项必须是**三类之一**：次数型、商品型、服务型。这是本子模块最核心的建模决策。

**三类内容项模型（本表的核心）：**

| 类型 | 代码 | 语义 | 计量单位 | 剩余计算 | 典型例子 | 核销触发 |
|---|---|---|---|---|---|---|
| **次数型** | `TIMES` | 可执行 N 次的服务（可重复、有时点） | 次 | `total_times - used_times` | 复查 4 次、验光 2 次、OK 镜随访 6 次 | M10-06 或 M10-09 调用 P-23 `on-consumed` |
| **商品型** | `GOODS` | 可领取 N 件的实物（有库存、可分批领） | 件（瓶/副/块） | `total_qty - used_qty` | 护理液 12 瓶、镜布 2 块、镜盒 1 个 | 出库/领取时调用 P-23 |
| **服务型** | `SERVICE` | **不限次**的持续性服务承诺（无数量概念） | 无 | `total_times` 为 NULL 时为 `UNLIMITED` | 免费调整、免费清洗、质保延长 6 个月 | 每次执行时记 1 条 `use_qty = 1` 流水，但不减额度 |

**为什么必须分三类，而不能统一成「次数」：**

| 若统一成次数 | 问题 |
|---|---|
| 护理液 12 瓶写成「12 次领取」 | 无法与库存/出库关联，领 1 瓶和领 1 副镜架在数据上无区别 |
| 免费清洗写成「999 次」 | 会员会问「到底能不能洗」，且 999 次用完后需要人工改数；语义上它本来就是「不限次」 |
| 复查 4 次与护理液 12 瓶混在一起 | 无法回答「这个会员的套餐还剩多少**可核销的实物**」，而这是退换货判定的关键输入 |

**约束说明：**

```sql
-- 内容项类型枚举（三类，不可扩展）
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_type
    CHECK (item_type IN ('TIMES', 'GOODS', 'SERVICE'));

-- 内容项编码格式
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_code
    CHECK (item_code ~ '^PKG-[A-Z0-9-]{3,40}-I[0-9]{2}$');

-- 内容项序号 ≥ 1
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_seq
    CHECK (item_seq >= 1);

-- 【核心约束】次数型：必须有总次数且 ≥ 1，且不得有总数量
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_times
    CHECK (item_type <> 'TIMES'
           OR (total_times IS NOT NULL AND total_times >= 1 AND total_qty IS NULL));

-- 【核心约束】商品型：必须有总数量且 > 0，且必须有商品编码
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_goods
    CHECK (item_type <> 'GOODS'
           OR (total_qty IS NOT NULL AND total_qty > 0
               AND linked_product_code IS NOT NULL
               AND total_times IS NULL));

-- 【核心约束】服务型：必须有不限次标记（total_times = NULL）或有限次数，且必须有服务动作
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_service
    CHECK (item_type <> 'SERVICE'
           OR (service_action IS NOT NULL AND total_qty IS NULL));

-- 已用次数不得超过总次数
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_times_used
    CHECK (total_times IS NULL OR used_times <= total_times);

-- 已领数量不得超过总数量
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_qty_used
    CHECK (total_qty IS NULL OR used_qty <= total_qty);

-- 已用计数不得为负
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_used_nonneg
    CHECK (used_times >= 0 AND used_qty >= 0);

-- 服务动作枚举
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_action
    CHECK (service_action IS NULL
           OR service_action IN ('CLEAN', 'ADJUST', 'POLISH', 'REPAIR_CHECK',
                                 'WARRANTY', 'EXAM'));

-- 商品品类枚举（与 M01-08 一致）
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_kind
    CHECK (linked_product_kind IS NULL
           OR linked_product_kind IN ('FRAME', 'LENS', 'CONTACT', 'ORTHO_K',
                                      'RGP', 'CARE', 'SUN', 'ACCESSORY'));

-- 周期类型枚举
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_period
    CHECK (period_type IN ('NONE', 'MONTH', 'QUARTER', 'YEAR'));

-- 有周期限制必须有每周期数量
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_period_pair
    CHECK ((period_type = 'NONE' AND period_limit_qty IS NULL)
           OR (period_type <> 'NONE' AND period_limit_qty IS NOT NULL
               AND period_limit_qty > 0));

-- 冷却天数非负
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_cooldown
    CHECK (cooldown_days >= 0);

-- 单价参考额非负
ALTER TABLE m10_member_package_item
    ADD CONSTRAINT ck_m10_pkg_item_value
    CHECK (unit_value_ref IS NULL OR unit_value_ref >= 0);

COMMENT ON TABLE m10_member_package_item
    IS '套餐内容项表：三类项模型（TIMES 次数型 / GOODS 商品型 / SERVICE 服务型）';
COMMENT ON COLUMN m10_member_package_item.item_type
    IS '内容项类型：TIMES 次数型（有 total_times）/ GOODS 商品型（有 total_qty）/ SERVICE 服务型（不限次或有限次、有 service_action）';
COMMENT ON COLUMN m10_member_package_item.unit_value_ref
    IS '单项标价参考额（元），用于套餐价值展示与退换按项扣减口径；不参与实收金额计算';
COMMENT ON COLUMN m10_member_package_item.period_limit_qty
    IS '每周期最多可领/可用数量，如护理液季度领 3 瓶 => period_type=QUARTER, period_limit_qty=3';
```

|---|---|---|---|---|---|---|---|---|---|---|
| 1 | `TIMES` | OK 镜戴镜复查 | 6 | NULL | 次 | `EXAM` | `NONE` | NULL | 0 | 120.00 |

**`m10_member_package_item` 的「剩余额度」计算口径（重要）：**

```
次数型剩余 = total_times − used_times
商品型剩余 = total_qty   − used_qty
服务型剩余 = 'UNLIMITED'（total_times IS NULL）
           或 total_times − used_times（若配置了有限次数）
```

> ⚠️ 上述「剩余」是**本表冗余计数**的结果，用于列表展示与快速判定。**权威剩余额度必须由 `m10_member_package_use` 的 `SUM(use_qty)` 计算**（`use_qty` 带符号，冲减为负）。冗余计数每日 02:10 由 `reconcile_package_quota` 任务对账，差异 > 0 立即告警并自动修复。参见附录 C 的对账 SQL。

**设计要点：**

1. **为什么 `item_code` 要带套餐编码前缀？**
   核销流水表 `m10_member_package_use.item_id` 是指向本表的主键，但审计导出与客服索要「这条核销是哪个套餐的哪一项」时，如果只看到 `item_id = 8821` 无法交流。`item_code = 'PKG-MYOPIA-ANNUAL-I03'` 自带语义（防控年卡第 3 项 = 视力复查），客服可以直接在电话里核对。

2. **为什么服务型允许 `total_times` 有值？**
   「服务型」的定义核心是**有 `service_action`、无实物**，而不在于是否不限次。样例 1 的「镜架调整」不限次，但样例 4 的「镜片参数复测」180 天冷却、样例 3 的「终身免费调整」是终身。因此允许 `total_times` 在服务型上有限次（如「免费维修 3 次」）。判定规则：服务型 `total_times IS NULL` 即不限次。

3. **为什么 `cooldown_days` 不放在套餐主表？**
   冷却期是**单项粒度**的：OK 镜随访卡里「清洗每月 1 次（冷却 20 天）」与「参数复测 90 天一次」冷却期完全不同。放主表只能取一个值，会导致要么过严（洗不了）要么过松（一天测三次参数）。

4. **为什么商品型必须有 `linked_product_code`，服务型必须有 `service_action`？**
   这是**可核销性**的最低保证。商品型不带商品编码，核销时无法调 M15/M10-07 出库；服务型不带动作，核销时无法与 M10-06 的订单行或 M10-09 的复查记录匹配。数据库 CHECK 强制这一点，避免运营配出「无法核销的套餐」。

5. **`is_gift` 的含义是什么？**
   赠送项（如「满额赠护理套装」）在 M16 金额体系里是 0 元行。本表 `is_gift = TRUE` 是给 M16-06 的**一个参数**：告诉它「这一行不应参与任何折扣叠加计算」（因为已经是 0 元），而不是让 M10 算钱。M10 依然不做任何金额计算。

**量级估算：** 配置类表，约 500 行（80 个套餐版本 × 平均 6 项），单行约 520 字节，总计约 260 KB。**不分区。**

**状态定义表：**

| 状态 | 代码 | 可核销 | 可退 | 说明 |
|---|---|---|---|---|
| 待生效 | `PENDING` | 否 | 是 | `start_date` 未到（如次日生效或指定日期激活） |
| 生效中 | `ACTIVE` | 是 | 依 `refund_policy` | 正常使用中 |
| 额度用完 | `EXHAUSTED` | 否 | 否（没额度了） | 所有项剩余均为 0 或 SERVICE 项已失效 |
| 已过期 | `EXPIRED` | 否 | 否 | 超过 `effective_expire_date` |
| 冻结 | `FROZEN` | 否 | 否 | 风控/纠纷冻结，可解冻 |
| 已退 | `RETURNED` | 否 | — | 已通过 M16-08 退款 |
| 作废 | `VOID` | 否 | — | 销售单作废且未支付，终态 |

**状态转移表：**

| 当前状态 | 动作 | 目标状态 | 触发方 | 校验 |
|---|---|---|---|---|
| —（新建） | 售出 | `PENDING` / `ACTIVE` | M16-04 `m16.optical.paid` 事件 / P-23 | 支付完成（`paid_status=PAID`） |
| `PENDING` | 到达生效日 | `ACTIVE` | APScheduler `job_member_package_activate` | `start_date <= today` |
| `ACTIVE` | 核销至额度用尽 | `EXHAUSTED` | P-23 `on-consumed` | 全部项剩余 = 0 |
| `ACTIVE` / `PENDING` | 到期 | `EXPIRED` | APScheduler `job_member_package_expire` | `effective_expire_date < today` |
| `ACTIVE` | 冻结 | `FROZEN` | 客服主管 | 原因 ≥5 字（`"1008026"`） |
| `FROZEN` | 解冻 | `ACTIVE` | 客服主管 | — |
| `ACTIVE` | 退卡 | `RETURNED` | M16-08 退款回调 | 已核销比例 ≤ `used_ratio_limit`（`"1008027"`） |
| `PENDING` | 作废 | `VOID` | M16-04 销售单作废 | `paid_status != 'PAID'` |

**设计要点：**

1. **为什么 `uk_m10_pkg_sale_order (sales_order_no, package_code)` 是幂等键？**
   M16-04 支付成功后会发布 `m16.optical.paid` 事件（可能重复投递），M10 收到后要创建售出记录。若没有唯一索引，一次重试就会产生两张卡（会员白拿一份套餐）。加上唯一索引后，重复事件直接撞唯一约束，应用层捕获后返回「已存在」即幂等。

2. **为什么 `item_snapshot` 要存整份内容项快照，而不是只存 `package_version`？**
   只存版本号的前提是「历史版本永远可查」。但运营在清理数据时可能把旧版本 `m10_member_package_item` 行逻辑删除，或旧的 `m10_member_package` 行被归档。一旦历史版本查不到，已售出的卡就无法核销。存快照后，**核销逻辑只依赖本表的 `item_snapshot`**，与定义表完全解耦。代价是每行多约 1.2 KB，`m10_member_package_sale` 年 1,200 行 → 1.4 MB/年，完全可接受。

3. **`total_quota` 为什么把「次数」与「商品件数」直接相加？**
   这是一个**展示用的粗略量**（如「这张卡还剩 6/11 额度」）。严格来说次和瓶不可相加，但用于「还剩几成」的百分比 `remaining_ratio` 时，按项数加权是合理的近似。真正的剩余额度必须逐项看（见 4.6 的「剩余额度计算口径」）。本字段加 CHECK `used_quota <= total_quota` 只是防止显负。

4. **`remaining_ratio` 的精度为什么是 NUMERIC(5,2)？**
   退换判定阈值 `used_ratio_limit` 常配 50 / 60 / 75。若只保留整数，49.6% 与 50.4% 都会变成 50，判定边界模糊。保留 2 位小数后，护理液套餐「用了 4 瓶 / 12 瓶 = 33.33%」与「用了 9 瓶 / 12 瓶 = 75.00%」精确可判。计算规则见详细设计 §3.4.3。注意 **`ROUND_HALF_UP`，例如 5/12 的剩余 = `ROUND(7/12 × 100, 2) = 58.33`**。

5. **为什么 `ck_m10_pkg_sale_paid_active` 要强制「ACTIVE 必须已付清」？**
   这是本表最重要的一条业务底线：**没付钱的套餐卡不能核销**。曾出现的真实风险场景：售货员先建卡让顾客「先用着」，顾客复查 3 次后不付尾款离店，系统里那 3 次已经白送了。用 CHECK 约束在数据库层兜底，即使应用层漏判也无法产生这样的行。

### 4.8 表：`m10_member_package_use`（套餐核销记录表）

**用途：** 记录「**每一次**核销/冲减的明细」。这是本子模块**唯一可信的额度流水**，也是**只增表**（禁止 UPDATE / DELETE）。

**本表的四条铁律：**

| # | 铁律 | 实现方式 |

| **1** | **只增不改** | 触发器 `trg_m10_pkg_use_immutable` 禁止 UPDATE / DELETE |

**幂等键设计（本表最关键的设计）：**

#### 两道防线

```
第一道（应用层 + 唯一索引）
  idempotency_key = "{source_type}:{source_biz_no}:{sale_no}:{item_code}:{usage_seq}"
  ├── 例：ORDER_DELIVER:PO202610310021:MS202610310007:PKG-MYOPIA-ANNUAL-I03:2
  └── uk_m10_pkg_use_idem(idempotency_key)  → 重复调用 → 唯一冲突 → 应用层返回 code=0 + is_idempotent=true

第二道（数据库层，独立于键拼接逻辑）
  uk_m10_pkg_use_occur(sale_id, item_id, usage_seq) WHERE use_type='CONSUME'
  └── 即使键拼接逻辑写错（如 source_biz_no 传了不同值），同一张卡同一项同一序号仍只能写一次
```

**为什么需要两道？** 因为幂等键依赖**调用方正确传递 `source_biz_no`**。P-23 的调用方是 M16-04，如果 M16 在重试时把 `source_biz_no` 从 `PO202610310021` 变成了带后缀的 `PO202610310021-R1`，第一道防线就失效了。第二道防线用「卡 ID + 项 ID + 序号」三元组兜底，这三个值都是 M10 内部生成的（不依赖调用方），可靠度更高。

#### 幂等键的六种构造场景

| 场景 | source_type | idempotency_key 示例 | usage_seq 来源 |
|---|---|---|---|
| 配镜核销（订单交付） | `ORDER_DELIVER` | `ORDER_DELIVER:PO202610310021:MS202610310007:PKG-MYOPIA-ANNUAL-I02:1` | 首次核销该商品项，序号 1 |
| 复查核销 | `FOLLOWUP` | `FOLLOWUP:FC202611020003:MS202610310007:PKG-MYOPIA-ANNUAL-I03:1` | 套餐第 1 次复查 |
| 免费清洗/调整 | `SERVICE` | `SERVICE:SVC2026110200012:MS202610310007:PKG-MYOPIA-ANNUAL-I05:6` | 服务型也计序号（便于统计第几次） |
| 商品领取 | `GOODS_PICKUP` | `GOODS_PICKUP:PICK202612010004:MS202610310009:PKG-CARE-ANNUAL-I01:1` | 第 1 瓶 |
| 退换冲减 | `RETURN` | `RETURN:RT202611100002:MS202610310007:PKG-MYOPIA-ANNUAL-I03:1` | **复用被冲减行的 `usage_seq`** |
| 活动赋值（运营补发） | `CAMPAIGN` | `HEADER:5f2c9a1e-...`（调用方传 `Idempotency-Key`） | 序号由系统计算 |

> **退换冲减的 `usage_seq` 为什么复用原行的序号？** 因为冲减不产生新的「第 N 次核销」，它只是撤销第 N 次。若冲减也用新序号，`uk_m10_pkg_use_occur` 的语义就乱了（同一序号出现 CONSUME 与 REVERSE 两行），而该唯一索引只对 `use_type = 'CONSUME'` 生效，因此 REVERSE 行可以复用序号而不冲突——这正是部分唯一索引 `WHERE use_type = 'CONSUME'` 的价值。

#### 有效期延长的核销（`use_type = 'EXTEND'`）

`OPTB-PKG-EXT` 权益（套餐有效期延长 30 天）也写入本表，`use_qty = 0`，同时在 `m10_member_package_sale` 上 `extended_days += 30` 并重算 `effective_expire_date`。这样核销流水是「会员权益使用历史」的唯一完整视图。

**`use_type = 'REVERSE'` 的三种冲减口径（订阅 `m16.optical.returned` 后）：**

| 退换场景 | 判定 | `use_qty` | `free_residual_policy` | 说明 |
|---|---|---|---|---|
| **整单退**（`FULL_RETURN`） | M16-04 `m16_optical_return.return_type = 'FULL'` | 该销售单关联的**全部 CONSUME 行**逐条反向冲减 | `NULL`（套餐仍在有效期内） | 每条原核销行生成一条 REVERSE 行，`reversed_use_id` 一一对应 |
| **部分退**（`PARTIAL_RETURN`） | `return_type = 'PARTIAL'` 且退的是套餐内商品 | 仅冲减与该退换商品对应项的行 | `NULL` | 例：退 1 副镜片 → 只冲减 `I02` 那 1 副 |
| **套餐已过期**（`sale_status = 'EXPIRED'`） | 过期后才收到退换事件 | 逐条反向冲减 | **`WRITE_OFF`**（默认） | 已过期卡的额度加回没有意义；若配置额外权益则口径为 `COMPENSATE` |

**套餐过期/退换的剩余额度处理（`free_residual_policy`）：**

| 取值 | 语义 | 适用 |
|---|---|---|
| `KEEP` | 冲减后额度**加回**，卡恢复 `ACTIVE`（若未过期） | 卡仍在有效期内（默认） |
| `WRITE_OFF` | 冲减流水照记，但**额度不加回**（`used_qty` 不变） | 卡已过期，退的是「过期未用的东西」 |
| `COMPENSATE` | 额度加到一张**新补偿卡**（`sale_status='ACTIVE'`，`valid_days = 剩余天数`） | 运营策略：过期后退换给等价新卡 |

**为什么分区主键是 `(id, created_at)` 而不是 `id`：** PostgreSQL 要求分区表的主键必须包含分区键。业务上不依赖主键查询（都走 `sale_id` / `member_no` / `idempotency_key`），因此无影响。`uk_m10_pkg_use_idem` 与 `uk_m10_pkg_use_occur` 是**全局唯一索引**（PostgreSQL 16 支持分区表上的唯一索引，条件是不含分区键则需要所有分区都有该约束——本设计用 `idempotency_key` 自带日期前缀 `source_biz_no` 里的日期段实现分区亲和，跨分区重复仍被全局唯一索引阻断）。

> **PostgreSQL 16 实现要点：** 分区表上的唯一索引必须包含分区键。本设计采用**折中方案**：`uk_m10_pkg_use_idem(idempotency_key, created_at)` —— 唯一性按 `(幂等键, 写入时间)` 保证。由于同一幂等键的重试必然发生在同一事务/同一日内（幂等键 TTL 24 小时），同日重复会被阻断。跨日重试的极端情况由应用层 Redis 幂等键（`m10:idem:member_use:{key}` TTL 24h）兜底，并由 `reconcile_package_quota` 对账任务发现并告警。

**设计要点：**

1. **为什么冲减不用 UPDATE 原行，而要新增负向行？**
   三方面原因：①**审计要求**：医保与物价检查要求「核销流水不可篡改」，UPDATE 会留下「这条记录被改过」但改前值难追溯，INSERT 则完整保留两条记录 ②**并发安全**：两条并发核销同时 UPDATE 同一行会互相覆盖计数，INSERT 无此问题 ③**对账简单**：`SUM(use_qty)` 天然等于净消耗，不需要判断「这条是有效还是已作废」。

2. **`quota_before` / `quota_after` 为什么存而不是算？**
   这是「事后复盘」的关键。当会员投诉「我明明只用了 2 次复查，怎么说我用了 4 次」时，有前后额度可以让客服 3 秒内定位问题行；没有则需要把该卡所有行拉出来重算，容易出错。这两个字段由核销事务内用 `SELECT ... FOR UPDATE` 拿到当前计数后写入，与 `SUM` 的一致性由每日对账保证。

3. **为什么 `patient_id`（受益患者）与 `member_no`（持有人）分开？**
   全家配镜套餐是「一人买、全家用」。若只用 `member_no`，就查不出「张三爸爸买的全家套餐，妈妈用了 2 次」。分开后，按 `patient_id` 可以回答「这个患者用过别人套餐的哪些权益」，这正是医疗与合规审计关心的。

4. **`usage_seq` 为什么在服务型项上也递增？**
   服务型（清洗/调整）不计额度，但**次数本身是运营关心的数据**（「这张卡的会员今年洗了 26 次镜片，说明他很爱惜，是召回的高价值客户」）。递增序号让人能一眼看到「第几次」，无需聚合。

5. **为什么不给 `use_qty` 建 CHECK 保证「不超过剩余额度」？**
   因为「不超过剩余」需要读另一张表（售出记录），CHECK 约束无法跨表。这个校验必须在应用层用 `SELECT ... FOR UPDATE` 做。数据库层的 `ck_m10_pkg_use_quota` 只保证 `quota_after >= 0` 作为结构性兜底。

**设计要点：**

1. **为什么用 `uk_m10_member_care_dedup(member_no, care_type, due_date)` 去重？**
   关怀的失败模式是**过度打扰**。若每日扫描任务因重试、补跑、并发执行而重复生成任务，会员一天内可能收到 3 条一模一样的「您的镜片该换了」短信。唯一索引在数据层直接封死这种可能。重跑逻辑：`ON CONFLICT DO NOTHING`。

2. **`converted_order_no` 为什么不是外键，而是 `VARCHAR(32)`？**
   因为转化可能发生在任务生成后很久（例如 3 月发的召回短信，7 月才来配镜）。若用外键且订单后来被逻辑删除，会阻塞。用单号字符串 + 每日对账（`reconcile_care_conversion`）方式，既轻量又可追溯。

3. **`NOTIFY_RESULT = 'NO_CONSENT'` 这个状态解决什么问题？**
   它是合规留痕：当会员在 M03 关闭了消息授权，系统不去发短信，但任务本身仍然生成（因为还要在门店层面做电话跟进，只是不发短信）。记录 `NO_CONSENT` 后，日后如有投诉，可以证明「我们尊重了授权设置」。

4. **为什么生日关怀不用 `birth_date = today` 直接查，而要生成任务？**
   生成任务的目的在于**分派与量化**：谁负责打这个电话、打完有没有到店、转化率多少。生日当天直接发短信是另一条路径（由 `job_member_care_notify` 批量推送），但电话回访必须有人负责，必须有任务。

### 4.10 表：`m10_member_stat`（视光会员经营统计表）

**用途：** 会员经营指标的**预聚合**，按「日期 × 门店 × 等级」三粒度汇总，供 P01 主页与 P08 经营分析使用。

```sql
ALTER TABLE m10_member_stat

    CHECK (calc_status IN ('CALCULATED', 'PAUSED', 'FAILED'));

-- 所有计数类指标非负
ALTER TABLE m10_member_stat
    ADD CONSTRAINT ck_m10_stat_counts

           AND active_member_cnt >= 0 AND churn_member_cnt >= 0

    CHECK (fit_amount_snap >= 0 AND package_sold_amount_snap >= 0);

    CHECK (care_converted_cnt <= care_contacted_cnt);

    ADD CONSTRAINT ck_m10_stat_repeat
    CHECK (repeat_member_cnt <= fit_member_cnt);

ALTER TABLE m10_member_stat
    ADD CONSTRAINT ck_m10_stat_rates
    CHECK ((package_exhaust_rate IS NULL
            OR (package_exhaust_rate >= 0 AND package_exhaust_rate <= 100))
           AND (package_use_rate IS NULL
                OR (package_use_rate >= 0 AND package_use_rate <= 100))

                OR (care_convert_rate >= 0 AND care_convert_rate <= 100)));

    IS '视光会员经营统计表：按日期×门店×等级预聚合，P01/P08 数据源';

    IS '配镜金额只读镜像，权威在 M16-04 日报；仅用于趋势展示，不参与任何计算';

    IS '门店 ID，0 表示全店汇总行（P01 主页取该行）';
COMMENT ON COLUMN m10_member_stat.calc_version
    IS '计算口径版本，口径调整时 +1，用于新旧口径对比';
```

**设计要点：**

1. **为什么 `store_id = 0` 作为汇总行，而不是查询时 SUM？**
   因为 P01 主页要「全店汇总 + 各门店明细」一起展示。查询时 `SUM` 需要扫 11 行（10 门店 + 汇总），虽然不慢，但汇总行在一张 4.4 万行的表里能让「只查汇总」的场景（如院长看板）退化为一次主键级别命中。同时，汇总行由批次任务在明细行算完后写入，顺序明确，不存在「SUM 时明细行还没写完」的不一致。

2. **`calc_version` 为什么存在？**
   统计口径是会变的。2027 年可能把「复购」从「历史配镜 ≥1 次」改成「近 2 年内配镜 ≥1 次」。口径变了之后，历史行的数值与新口径不可比。加版本号后，P08 可以明确标注「2027-01 起口径 V2.0，此前为 V1.0」，而不是让运营看着一条断崖式下跌的曲线困惑。

3. **为什么统计表不设 `is_deleted`？**
   统计表是**派生数据**，每天由任务全量重算（覆盖写）。若某天的数据算错，正确的处理是重跑任务，而不是标记删除。不设 `is_deleted` 也避免了「被逻辑删除的统计行还在 `SUM` 里」这类隐蔽问题。

4. **`package_use_rate` 与 `package_exhaust_rate` 为什么都用 NULL 而非 0 表示「无数据」？**
   分子分母都为 0 时（当期没卖卡），「核销率 0%」与「没有数据」是两件事。运营会误读「0% 说明卖了卡没人用」。用 NULL 表达「样本不足」，前端显示 `—`，语义准确。

**量级估算：**

| 项目 | 数值 | 说明 |
|---|---|---|
| 日粒度行数 | 约 120/日 | 10 门店 × 5 等级 + 11 汇总行 ≈ 61；按需保留 6 个等级维度约 120 |
| 年行数 | 约 43,800 行 | 365 × 120 |
| 5 年总量 | 约 219,000 行 | 日粒度保留 5 年，月粒度永久 |
| 单行平均长度 | 约 340 字节 | — |
| 表大小（5 年） | 约 74 MB | — |

**分区：** 不分区（5 年 22 万行；日粒度行可按 `stat_date` 批量清理，清理任务 Month 级执行）。

**模型定义要点说明：**

| 要点 | 说明 |
|---|---|
| `Mapped[]` + `mapped_column()` | 全量采用 SQLAlchemy 2.0 声明式风格，与共享规范 §2.1 一致 |
| `Identity()` | 主键统一 `BIGINT GENERATED BY DEFAULT AS IDENTITY`（共享规范 §2.6） |
| `JSONB` | 来自 `sqlalchemy.dialects.postgresql`，不依赖第三方包 |
| 无 `ForeignKey` | 全模块不建物理外键（共享规范 §2.6），引用以注释标注来源表 |
| `postgresql_where` | 部分索引统一用 `text()` 表达，与 4.2~4.10 的索引表一一对应 |
| `M10MemberPackageUse.created_at` | 同时声明 `primary_key=True`，与「分区表主键必须含分区键」对应 |
| 无 `updated_at`（`PackageUse`） | 只增表刻意不设，强化「不可改」语义 |
| 反引号内部无 `%` | 避免与 SQLAlchemy 文本解析冲突 |

```python
        "NONE", description="叠加等级")

    require_orthok: bool = Field(False, description="是否仅 OK 镜戴镜会员可购")
    require_age_min: Optional[int] = Field(None, ge=0, le=120, description="最小年龄")
    require_age_max: Optional[int] = Field(None, ge=0, le=120, description="最大年龄")
    refund_policy: Dict[str, Any] = Field(..., description="退换策略 JSONB")
    description: Optional[str] = Field(None, max_length=1024, description="套餐说明")
    items: List["PackageItemIn"] = Field(..., min_length=1, max_length=30,
                                         description="套餐内容项")

    @field_validator("refund_policy")
    @classmethod
    def _check_refund_policy(cls, v: Dict[str, Any]) -> Dict[str, Any]:
        """退换策略必须含 allow_return 与 mode。"""
        required = {"allow_return", "mode"}
        if not required.issubset(v.keys()):
            raise ValueError("退换策略必须包含 allow_return 与 mode")
        if v["mode"] not in ("FULL_ONLY", "ITEM_ALLOWED"):
            raise ValueError("退换模式必须为 FULL_ONLY 或 ITEM_ALLOWED")
        return v

    @model_validator(mode="after")
    def _check_extend_and_age(self) -> "PackageCreateIn":
        """延长天数不得超过有效期；年龄区间必须正向。"""
        if self.valid_days > 0 and self.max_extend_days > self.valid_days:
            raise ValueError("最长可延长天数不得超过套餐有效期天数")
        if (self.require_age_min is not None and self.require_age_max is not None
                and self.require_age_min > self.require_age_max):
            raise ValueError("最小年龄不得大于最大年龄")
        seqs = [it.item_seq for it in self.items]
        if len(seqs) != len(set(seqs)):
            raise ValueError("内容项序号不得重复")
        return self


class PackageItemIn(BaseModel):
    """套餐内容项入参（三类项模型的校验集中在此）。"""

    item_seq: int = Field(..., ge=1, le=99, description="内容项序号")
    item_type: PackageItemType = Field(..., description="类型 次数/商品/服务")
    item_name: str = Field(..., max_length=128, description="内容项名称")

                                       description="次数型总次数；服务型 NULL=不限次")

                                         description="商品型总数量")

    linked_product_code: Optional[str] = Field(
        None, max_length=32, description="商品型必填：M01-08 商品编码")
    linked_product_kind: Optional[str] = Field(
        None, max_length=16, description="商品品类")
    linked_charge_code: Optional[str] = Field(
        None, max_length=32, description="服务型可填：M01-06 收费项目编码")
    service_action: Optional[Literal["CLEAN", "ADJUST", "POLISH",
                                     "REPAIR_CHECK", "WARRANTY", "EXAM"]] = Field(
        None, description="服务型必填：服务动作")
    period_type: Literal["NONE", "MONTH", "QUARTER", "YEAR"] = Field(
        "NONE", description="发放周期")
    period_limit_qty: Optional[Decimal] = Field(
        None, gt=0, decimal_places=2, description="每周期上限")
    cooldown_days: int = Field(0, ge=0, le=3650, description="两次核销最小间隔天数")
    is_gift: bool = Field(False, description="是否赠送项")
    unit_value_ref: Optional[Decimal] = Field(None, ge=0, decimal_places=2,
                                              description="单项标价参考额（元）")

    @model_validator(mode="after")
    def _check_three_types(self) -> "PackageItemIn":
        """三类项模型的互斥校验。"""
        if self.item_type == "TIMES":
            if self.total_times is None:
                raise ValueError("次数型内容项必须填写 total_times")
            if self.total_qty is not None:
                raise ValueError("次数型内容项不得填写 total_qty")
        elif self.item_type == "GOODS":
            if self.total_qty is None:
                raise ValueError("商品型内容项必须填写 total_qty")
            if not self.linked_product_code:
                raise ValueError("商品型内容项必须填写 linked_product_code")
            if self.total_times is not None:
                raise ValueError("商品型内容项不得填写 total_times")
        else:
            if not self.service_action:
                raise ValueError("服务型内容项必须填写 service_action")
            if self.total_qty is not None:
                raise ValueError("服务型内容项不得填写 total_qty")
        if (self.period_type == "NONE") != (self.period_limit_qty is None):
            raise ValueError("period_type 与 period_limit_qty 必须同时给出或同时为空")
        return self
```

**Schema 设计要点：**

| # | 要点 | 说明 |
|---|---|---|
| 1 | **建档请求不接收 `member_no` / `level_code`** | 这是「M03-03 是会员身份唯一权威」在代码层的物理体现：M10 的 DTO 里根本不存在可写入会员号的字段，从架构上杜绝「M10 自造会员号」 |
| 2 | **`MemberBenefitsOut.calc_owner = "M16-06"`** | P-22 响应里显式带上「金额计算归属方」，调用方（M16-06）一眼可见本模块不产出金额 |
| 3 | **`PackageItemIn` 三类互斥校验** | `TIMES` 必须有 `total_times` 且不得有 `total_qty`；`GOODS` 必须有 `total_qty` + `linked_product_code` 且不得有 `total_times`；`SERVICE` 必须有 `service_action` 且不得有 `total_qty` — 与 4.6 的数据库 CHECK 双重把关 |
| 4 | **`PackageUseIn` 定位二选一** | 要么给 `item_code`（精确到项），要么给 `service_action`（按服务动作匹配），不可同时或同时缺省 |
| 5 | **`PackageReverseIn` 整单/部分互斥** | 整单退不得传 `item_codes`，部分退必须传 `item_codes` |
| 6 | **`PackageItemOut.remaining_times` 用 `None` 表示不限次** | 不用 `-1` 或 `9999` 这类魔术值，前端可直接判 `null` 显示「不限次」 |
| 7 | **`BenefitCalcContextIn.settlement_base`** | M16-06 传入「可优惠基数」供 M10 做**门槛判定**（如「实付满 2000 才享受」），M10 只用它比较大小，**不做任何金额运算**，返回体中亦不出现任何计算出的金额 |

**② 核销前校验剩余额度（并发安全，用行锁）**

```sql
-- 锁住售出记录，串行化同一张卡的核销

       total_quota, used_quota, package_version
FROM m10_member_package_sale
WHERE sale_no = 'MS202610310007'
  AND is_deleted = FALSE
FOR UPDATE;

-- 取该内容项的实时剩余额度（权威口径 = SUM(use_qty)）
SELECT i.id AS item_id,
       i.item_type,
       i.total_times,
       i.total_qty,
       i.period_type,
       i.period_limit_qty,
       i.cooldown_days,
       COALESCE(SUM(u.use_qty), 0) AS net_used,
       MAX(CASE WHEN u.use_type = 'CONSUME' THEN u.usage_seq END) AS max_seq,
       MAX(CASE WHEN u.use_type = 'CONSUME' THEN u.used_at END) AS last_used_at
FROM m10_member_package_item i
LEFT JOIN m10_member_package_use u
       ON u.item_id = i.id
      AND u.sale_id = 7001
WHERE i.item_code = 'PKG-MYOPIA-ANNUAL-I03'
GROUP BY i.id, i.item_type, i.total_times, i.total_qty,
         i.period_type, i.period_limit_qty, i.cooldown_days;
```
