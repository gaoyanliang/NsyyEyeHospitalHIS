**表清单（共 8 张）：**

| 序号 | 表名 | 中文名 | 说明 | 预估量级 |
|---|---|---|---|---|
| 1 | `m10_prescription` | 配镜处方主表 | 核心，一处方一行 | 38,000/年 |
| 2 | `m10_prescription_item` | 配镜处方明细表 | 按眼别，1:N（OD/OS，个别含 OU 合并行） | 76,000/年 |
| 3 | `m10_prescription_audit` | 处方审核任务表 | 每次提交审核生成一条，含归档结果 | 38,000/年 |
| 4 | `m10_prescription_audit_rule` | 处方审核规则表 | 配置驱动，约 40~60 条 | 60（配置类） |
| 5 | `m10_prescription_template` | 处方模板表 | 个人/科室/全院三级模板 | 2,000 |
| 6 | `m10_prescription_supply_check` | 光度可供性校验快照表 | 调 M01-08 `specs/lookup` 的结果留痕 | 240,000/年 |
| 7 | `m10_prescription_log` | 处方操作日志表 | 只增，按月分区 | 500,000/年 |
| 8 | `m10_prescription_config` | 处方参数配置表 | 有效期、偏差阈值、规则开关 | 80（配置类） |

**为什么是这 8 张表：**

| 表 | 存在的必要性 |
|---|---|
| `m10_prescription` | 处方的唯一档案，`rx_no` 是 M10-02 对外的主键（P-05 的入参） |
| `m10_prescription_item` | 度数天然按眼别分栏（OD/OS 各一组 SPH/CYL/AXIS/ADD/PD/PH），若压在主表里会出现 40+ 个 `od_*` / `os_*` 字段，既无法扩展也不利于按度数检索 |
| `m10_prescription_audit` | 审核是**可多次发生**的动作（驳回→修改→再提交），且需要保存每次的规则命中快照，不能只用一个 `audit_result` 字段 |
| `m10_prescription_audit_rule` | 审核规则是医院可配置项（儿童散瞳要求、偏差阈值由医务科定），硬编码进代码就无法按院区差异化 |
| `m10_prescription_template` | 「常用处方」是视光医师的最高频入口，重复录入一组度数平均耗时 90 秒，模板化后 ≤ 15 秒 |
| `m10_prescription_supply_check` | 医院与 M01-08 是不同子系统，光度可供性会随商品上下架变化；留痕后能回答「当时为什么说能配」这一纠纷问题 |
| `m10_prescription_log` | 处方是医疗器械经营许可证与《医疗器械监督管理条例》要求留存的记录，必须 100% 留痕且不可改 |
| `m10_prescription_config` | 有效期（成人 12 个月 / 儿童 6 个月）、偏差阈值（0.50D）、审核开关都在此配置，避免改代码发版 |

### 4.2 表：`m10_prescription`（配镜处方主表）

**用途：** 一张配镜处方一条记录，是 M10-02 的核心表。**写入方**：M10-02 处方开立与审核页面、换发补开流程。**只读方**：M10-05 选配工作台、M10-06 配镜订单、M16-04 视光销售结算、M16-06 优惠折扣执行、M10-09 视力档案。

**状态机：**

```text
                      ┌──────────────┐
     新建 ────────────►│   DRAFT      │  草稿（可自由编辑，无处方号）
                      └──────┬───────┘
                             │ 提交审核（submit-audit，生成 rx_no）
                             ▼
                      ┌──────────────┐
                      │PENDING_AUDIT │  待审核（不可编辑，可撤回）
                      └──┬───────┬───┘
         审核通过         │       │  审核驳回（reason ≥ 10 字）
      （PASS/PASS_WITH_NOTE）│      │
                            ▼       ▼
                     ┌─────────┐ ┌──────────┐
                     │ AUDITED │ │ REJECTED │
                     │ 已审核   │ └────┬─────┘
                     └──┬───┬──┘      │ 修改后重新提交
        有效期届满       │   │         └──────────► PENDING_AUDIT
      （定时任务）        │   │ 作废（仅未产生订单时）
                          ▼   ▼
                  ┌──────────┐ ┌──────┐
                  │ EXPIRED  │ │ VOID │
                  │ 已过期    │ │ 已作废│
                  └──────────┘ └──────┘

  PENDING_AUDIT ──撤回──► DRAFT（未产生审核记录时）
  AUDITED ──作废（无订单）──► VOID
  EXPIRED ──复验──► AUDITED（同一记录续期，仅限「外院处方转录」类，需主管授权）
```

**设计要点：**

1. **为什么处方与验光单必须是两张表、两套状态？**
   验光单描述「眼睛的客观状态」，由验光师签发；配镜处方描述「医生决定给他配什么」，由视光医师签发。两者的签发人、有效期、法律效力完全不同。同一份验光数据可以派生出多张处方（如先配单光镜、半年后换渐进片），也可以基于外院处方转录而不经过本院验光。若合并成一张表，`optometry_no` 就要允许为空、`status` 要揉合两套语义，最终两边都不准。

2. **为什么 `rx_no` 允许为空（草稿）？**
   视光医师开处方时经常先建草稿、边看验光单边录入，或中途被叫去处理其他患者。若草稿就占用 `RX202610310012` 这样的号段，日均 40 张草稿里约 15% 会被废弃，处方号出现大量空洞，打印核对时难以判断「RX...0013 去哪了」。约束 `ck_m10_rx_no_required` 保证只有进入 `PENDING_AUDIT` 之后才有号。

3. **为什么度数放明细表而不是主表？**
   主表若平铺，需要 `od_sphere` / `od_cylinder` / `od_axis` / `od_add` / `od_va_sc` / `od_va_cc` / `od_pd` / `od_ph` / `os_*` 共 18 列，加上棱镜基底 2 列达 20 列。未来若要支持三焦点或加「近附加中间距离」，无法扩展。明细表按 `eye_side` 一行一眼，字段稳定。同时明细表可以独立建索引支持「查所有柱镜 ≥ -2.00D 的处方」这类处方式检索。代价是读处方需要 JOIN，实测 2 行 JOIN 的额外开销 < 1ms，完全可接受。

4. **为什么 `pd_total` / `pd_right` / `pd_left` 同时存？**
   三者不是冗余：`pd_total` 是验光单常给的总瞳距（患者看远时的双眼瞳距），`pd_right` / `pd_left` 是配镜时按镜架调整后的单眼瞳距（加工磨边直接使用）。约束 `ck_m10_rx_pd_sum` 允许两者偏差 ≤ 0.5mm，因为镜架中心距与瞳距不完全一致时，加工师会把镜片光学中心移位，此时单眼瞳距之和会与总瞳距有小偏差。若只存总瞳距，加工师必须手工分配，容易左右搞反。

5. **为什么渐进片强制要求瞳高（`optical_center_height_*`）与近用瞳距？**
   渐进片有一个 2~4mm 的「通道」，验配高度差 2mm 就足以导致近用区被切割、患者看近模糊。行业规范（《眼镜验配服务规范》）要求渐进片装配前必须测瞳高。约束 `ck_m10_rx_progressive_fitting` 把这条要求下沉到数据库，任何绕过 API 的导入脚本也无法写入不完整渐进处方。

6. **为什么 `sign_hash` 存 SHA-256 而不是直接存 CA 签名全文？**
   处方打印件与 P-05 返回值中携带 `sign_hash`，下游（M16-04、M10-06）可以在下单时重算摘要比对，确认「这份处方内容自签发后未被改动」。CA 签名原文体积大（约 1~2KB）且需证书链验证，只用于法务场景，存于 `sign_cert_sn` 指向的证书库，不随处方表下发。

7. **为什么有效期用 `validity_months` + `valid_from` + `valid_until` 三个字段？**
   `validity_months` 记录「开了几个月」是业务规则的可审计证据（成人 12、儿童 6）；`valid_until` 是实际失效日，便于建**部分索引**做每日过期扫描；`expiry_basis` 记录起算依据，因为外院处方的有效期从外院开方日起算，而不是转录当天——否则一张 2025-03 开的外院处方在 2026-10 转录，会被错误地判为「还有 12 个月有效」。

8. **为什么 `chain_root_rx_id` + `sequence_no` 单独维护处方链？**
   临床上「换发→补开→再换发」可能形成 3~5 代处方。用 `superseded_by_rx_id` 单向链表只能往前或往后走一步，查全链需要递归 CTE。加 `chain_root_rx_id` 后，一次 `WHERE chain_root_rx_id = ?` 就能取全部代次，`sequence_no` 保证顺序。代价是插入时要回填根 ID，由 Service 层在同一事务内完成。

9. **为什么不建物理外键？**
   ①`patient_id` / `issued_by` / `audit_id` 分别指向 M03、M01-02、本模块不同文件定义的表，跨 schema 外键不可用；②处方表是中等写入表（日均 100 INSERT + 约 300 UPDATE），且审核流会高频更新 `status`，外键检查会增加写放大；③一致性由应用层校验 + 每日 03:00 的 `reconcile_prescription_refs` 对账任务保证。**代价**：可能出现悬挂引用（如医师离职后记录被清理），对账任务会告警并保留快照字段兜底。

10. **为什么 `idx_m10_rx_valid` 与 `idx_m10_rx_expire_scan` 都建部分索引？**
    最热查询是 P-06「取患者有效处方」（M16-04 每笔视光下单都会调，日均约 300 次）。全表 10 年后约 38 万行，其中 `status='AUDITED'` 的活跃处方通常不足 3,000 行。部分索引后索引体积从约 12MB 降到约 200KB，查询从扫索引 1.8ms 降到 0.05ms。`idx_m10_rx_expire_scan` 供定时任务每日 02:10 扫描「今天到期的已审核处方」，只扫这一部分索引，避免 38 万行全表扫描。

11. **为什么 `patient_id` 与 `customer_id` 都允许独立存在？**
    视光中心存在「无就诊记录顾客」（M10-05 建档，只有 `customer_id`）。但处方仍需法定代表人意义上的「主体」——`patient_id` 通过 M10-05 P-11 `customers/ensure` 保证一定存在（M10-05 会为顾客建一个最小患者档案），`customer_id` 则在纯视光顾客场景下补充。因此 `patient_id` 为 NOT NULL，`customer_id` 可空。

**设计要点：**

1. **为什么 `eye_side` 用 `OD`/`OS` 而不是 `RIGHT`/`LEFT`？**
   眼科与视光行业标准表述就是 OD（oculus dexter，右眼）/ OS（oculus sinister，左眼），与 M05、M07、M10-01 全仓一致。用 `RIGHT`/`LEFT` 会在跨模块对接时反复翻译，且中文「左」「右」在界面转发手写处方时最易出错。

2. **为什么 `cylinder` 只允许负值？**
   眼镜行业加工与光度矩阵（M01-08 `mdm_optical_spec`）统一采用**负柱镜表述**。正柱镜表述（如 `+0.75 × 90°`）需要先做「翻转换算」成正柱镜等价的负柱镜形式才能进入矩阵校验：
   `S' = S + C`，`C' = -C`，`A' = A ± 90`（> 180 则减 180）。
   录入界面允许医师输入正柱镜，Service 层统一换算后再落库，保证数据库里只有一种表述，避免校验逻辑分叉。

3. **为什么 `sphere_equivalent` 落库而不实时计算？**
   近视防控的核心指标是「球镜等效变化」，M10-09 视力档案要按时间画曲线，并按「年增长 > 0.75D」触发预警。若每次查询都现场算 `sphere + cylinder/2` 再做四舍五入，跨 10 年 38 万行 × 2 眼 = 76 万次计算，且四舍五入规则一旦调整历史数据口径就变了。落库后口径固定，并有 `ck_m10_rx_item_se` 保证与球柱镜一致。

4. **为什么 `va_cc` 是 NOT NULL？**
   矫正视力是配镜处方的**核心临床要素**：①它决定这副眼镜「能不能配到 1.0」；②它用于识别弱视（矫正视力 < 0.8 且无器质病变）；③加工完成后质检要对照它判断是否达标。若允许为空，大量处方会以「反正没人看」为由跳过填写，最终纠纷时无法举证。

5. **为什么 `deviation_*` 三列要落库而不是审核时临时算？**
   偏差是「处方 vs 验光」的对比结果，验光单在 M10-01 中可能被补充修改（补录视功能数据后重新签发）。若不落库，事后重算会得到与当时审核不同的数，导致「当时为什么通过」无法解释。落库后，即使 M10-01 数据变了，处方侧的偏差值与当时的说明依然稳定。

6. **为什么轴位偏差用 0~90 的循环差值？**
   轴位 5° 与 175° 实际只差 10°，不是 170°。计算公式：
   `d = abs(axis_rx - axis_trial) mod 180`，若 `d > 90` 则 `d = 180 - d`。
   约束 `ck_m10_rx_item_dev_axis` 限制在 0~90，正是要求 Service 按此公式计算后写入。

7. **为什么 `prism_base` 用 `BU_BI` 这样的斜向组合值？**
   临床偶有斜向棱镜（如右眼 `2Δ BU + 1Δ BI` 用于上斜视伴内斜）。若只存 `BU`/`BI` 单值就要拆成两行，破坏「一眼一行」的唯一约束。用组合值 + `prism_value_v` / `prism_value_h` 分量，既表达斜向，也让加工师能直接按分量加工（棱镜加工是按水平/垂直方向定心的）。

8. **本表与主表的职责切分：**
   主表放「一张处方共有的信息」（来源、有效期、镜片类型、总瞳距、审核状态）；明细表放「一眼一套的度数」（球柱轴、ADD、棱镜、单眼瞳距瞳高、矫正视力、单眼可供性）。判断标准是：**这个值两眼可能不同吗？** 可能不同就放明细表。

```sql
    CHECK (audit_level IN ('SELF', 'SENIOR', 'PHARMACY', 'DOUBLE'));

ALTER TABLE m10_prescription_audit
    ADD CONSTRAINT ck_m10_rx_audit_result
    CHECK (audit_result IN ('PENDING', 'PASS', 'PASS_WITH_NOTE', 'REJECT'));

-- 最高级别枚举
ALTER TABLE m10_prescription_audit
    ADD CONSTRAINT ck_m10_rx_audit_severity
    CHECK (severity_max IS NULL OR severity_max IN ('ERROR', 'WARN', 'INFO'));

-- 命中条数非负且各级之和不超过总数
ALTER TABLE m10_prescription_audit
    ADD CONSTRAINT ck_m10_rx_audit_hit_counts
    CHECK (rule_hit_count >= 0 AND error_hit_count >= 0 AND warn_hit_count >= 0
           AND error_hit_count + warn_hit_count <= rule_hit_count);

-- 有 ERROR 命中且未越权时不可通过
ALTER TABLE m10_prescription_audit
    ADD CONSTRAINT ck_m10_rx_audit_error_block
    CHECK (audit_result NOT IN ('PASS', 'PASS_WITH_NOTE')
           OR error_hit_count = 0
           OR is_override = TRUE);

-- 驳回必须填原因（≥10 字）与驳回时间
ALTER TABLE m10_prescription_audit
    ADD CONSTRAINT ck_m10_rx_audit_reject

           OR (reject_reason IS NOT NULL
               AND char_length(btrim(reject_reason)) >= 10

    ADD CONSTRAINT ck_m10_rx_audit_completed
    CHECK (audit_result = 'PENDING'
           OR (auditor_id IS NOT NULL
               AND audited_at IS NOT NULL
               AND sign_hash IS NOT NULL));

-- 待审状态不得填写审核人
ALTER TABLE m10_prescription_audit
    ADD CONSTRAINT ck_m10_rx_audit_pending
    CHECK (audit_result <> 'PENDING' OR auditor_id IS NULL);

-- 审核时间不得早于提交时间
ALTER TABLE m10_prescription_audit
    ADD CONSTRAINT ck_m10_rx_audit_time_order
    CHECK (audited_at IS NULL OR submitted_at IS NULL OR audited_at >= submitted_at);

-- 审核耗时非负
ALTER TABLE m10_prescription_audit
    ADD CONSTRAINT ck_m10_rx_audit_duration
    CHECK (audit_duration_sec IS NULL OR audit_duration_sec >= 0);

-- 儿童首次配镜双人复核：DOUBLE 类型必须有两名不同审核人（第二审核人记在 override 之外的扩展字段）
ALTER TABLE m10_prescription_audit
    ADD CONSTRAINT ck_m10_rx_audit_double
    CHECK (audit_type <> 'DOUBLE' OR audit_level = 'DOUBLE');

COMMENT ON TABLE m10_prescription_audit IS '处方审核任务表：记录每次审核动作与规则命中快照，一张处方可多条';
COMMENT ON COLUMN m10_prescription_audit.rule_hits IS '规则命中明细 JSONB 快照，审核当时冻结，不随规则版本变化';
COMMENT ON COLUMN m10_prescription_audit.is_override IS '越权放行标记：存在 ERROR 命中但经上级审批强制通过，质控必查';
COMMENT ON COLUMN m10_prescription_audit.rule_version IS '审核时使用的规则集版本标签，用于区分规则调整前后的审核口径';
```

**设计要点：**

1. **为什么审核是独立表而不是主表上的几个字段？**
   主表已有 `audited_result` / `audited_by` / `audited_at`（当前结论），那是**冗余的最新状态**，便于列表展示。但真实的审核历史是「提交→驳回→改→再提交→通过」共 3~4 条记录，必须完整留痕：①争议时能证明「医师改了什么、审核人看到了什么」；②质控要统计「平均驳回次数」和「哪些规则最常被触发」；③越权放行要单独审计。这些都要求一对多。

2. **为什么 `rule_hits` 用 JSONB 而不是拆成 `m10_prescription_audit_hit` 子表？**
   规则命中是**快照数据**：一旦审核完成就永不修改，也不需要按命中行做关联查询（按规则统计用 GIN 索引即可）。若拆子表，10 年会产生 380,000 × 平均 1.8 = 68 万行，且每行只有 9 个小字段，管理成本远高于收益。用 JSONB + `jsonb_path_ops` GIN，`WHERE rule_hits @> '[{"rule_code":"RAR003"}]'` 可以在毫秒级筛出所有触发儿童散瞳规则的处方。

3. **为什么 `ck_m10_rx_audit_error_block` 把「有 ERROR 不可通过」写到数据库？**
   这是医疗安全底线。虽然 Service 层已经拦截，但如果哪天新增一个批量导入或运维补数据脚本绕过 Service，数据库层仍能挡住。同理 `is_override` 提供了合法例外通道——不是禁止，而是要求「留痕 + 上级审批」。

4. **为什么 `is_over_ride` 之外还要 `override_approval_no`？**
   《医疗质量管理办法》要求越权行为必须有审批凭据。把 M20 移动审批单号落库后，质控科可以按单号回查审批详情（谁批的、什么时候批的、批的理由），形成完整证据链。

5. **为什么 `audit_duration_sec` 要落库？**
   审核流于形式是视光处方的典型风险（「3 秒点通过」）。该字段支撑质控指标「审核耗时 < 5 秒的记录占比」，超过 30% 则提示科主任。计算方式固定的，落库比每次现算省事。

**量级估算：**

| 项目 | 数值 | 说明 |
|---|---|---|
| 年审核记录 | 38,000 条 | 与处方量 1:1（含驳回后重审约 1.15 倍） |
| 10 年总量 | 437,000 行 | — |
| 单行平均长度 | 约 620 字节 | `rule_hits` JSONB 会被 TOAST 压缩，平均约 200 字节 |
| 表大小（10 年） | 约 271 MB | 含 TOAST |
| 索引大小（10 年） | 约 180 MB | 含 GIN |
| 日均写入 | 105 INSERT + 约 200 UPDATE | 审核结论回填 |

**分区：** 不分区。理由：①总行数 43.7 万，PostgreSQL 16 单表完全可控；②索引 `idx_m10_rx_audit_pending` 是部分索引，分区后每分区都要建，收益不抵开销；③审核轨迹查询永远带 `rx_id`，单点定位。

### 4.5 表：`m10_prescription_audit_rule`（处方审核规则表）

**用途：** 配置驱动处方审核规则。规则的判定逻辑由 `expression`（受限表达式）与 `params`（JSONB 参数）描述，由规则引擎 `PrescriptionRuleEngine` 解释执行。**写入方**：M10-02 处方参数配置（P08 的规则子页）、医务科。**只读方**：M10-02 审核引擎、M10-02 审核预览。

**设计要点：**

1. **为什么用 `items_json` 而不是 `m10_prescription_template_item` 子表？**
   模板明细是「只整体读取、不单独查询」的数据：调用模板永远是一次性把 OD/OS 两组度数全部带出，从不按「模板明细」做独立筛选或统计。加一张子表意味着每次读模板都要多一次 JOIN、多一套 CRUD 接口与页面，收益为零。JSONB 还允许模板结构随业务演进（未来加「中间距离附加」）而不改表结构。

2. **为什么 `owner_scope` 三分而不是简单的「公有/私有」两分？**
   科室模板解决了「新来的视光医师没有自己的模板」问题——他可以先用科室模板（如「儿童离焦镜片标准处方」），熟练后再沉淀个人模板。全院模板仅医务科维护，用于标准化（如「OK 镜配套单光处方」）。经验数据：三级模板上线后，视光医师平均录入时间从 96 秒降至 21 秒。

3. **为什么模板不允许带 `optometry_no` 或患者信息？**
   模板是「知识」不是「案例」。若模板携带患者信息，存在隐私泄露与「照抄上一患者度数」的风险。`items_json` 只存度数结构，实际使用时必须由医师对照当前患者的验光单确认。

**设计要点：**

1. **为什么每次校验都要落库，而不是只存一个最新状态？**
   处方可能被反复校验：开方时一次、审核时一次、下单前 M16-04 复核一次、M01-08 矩阵调整后定时复查一次。只存最新状态就无法解释「为什么开方时说是现货，下单时变成了定制 15 天」。留全量历史后，客诉时可以直接把校验时间轴导出来给顾客看。

2. **为什么 `is_blocking` 要单独一个字段，而不直接看 `is_available = FALSE`？**
   因为并非所有不可供都阻断：例如药品类服务（如「配镜服务费」）不需要度数校验；又如某些低度散光在无现货时系统允许「先下单后调货」，此时 `is_available=false` 但 `is_blocking=false`。规则由 `m10_prescription_config.SUPPLY_BLOCK_ON_UNAVAILABLE` 控制，落库后可以被 M10-06 直接读取，无需重算。

3. **为什么存 `alternative_product_codes`？**
   这是给 M10-05 的**替换推荐上游依据**。M10-02 在发现不可供时，会调 M01-08 `GET /internal/v1/optical/products/eligible` 取同类可选商品，把候选编码落库。M10-05 的选品工作台直接读这张表就能展示「这个度数在这些商品上可供」，不需要重新遍历商品列表。代价是保存了商品编码（非主数据本体），不需要事务一致性。

4. **为什么 `is_degraded` 存在？**
   M01-08 是另一子系统，存在不可用可能。降级时本模块不能假装「可供」（会造成下单后才发现做不出来），也不能假装「不可供」（会误伤正常配镜）。正确做法是：`is_degraded=TRUE`、`lookup_found=FALSE`、不阻断，同时提示医师「光度校验服务暂不可用，请人工确认」。约束 `ck_m10_rx_sc_degraded` 保证降级记录不会污染可供性统计。

**量级估算：**

| 项目 | 数值 | 说明 |
|---|---|---|
| 年校验记录 | 240,000 条 | 38,000 处方 × 2 眼 × 平均 3.2 次校验 |
| 10 年总量 | 2,400,000 行 | — |
| 单行平均长度 | 约 330 字节 | — |
| 表大小（10 年） | 约 792 MB | — |
| 索引大小（10 年） | 约 620 MB | 8 个索引 |
| 日均写入 | 660 INSERT | 无 UPDATE |

**分区：** 按 `checked_at` 月度 RANGE 分区，保留 24 个月热数据，冷数据归档。
理由：①这是纯日志型的快照表，10 年 240 万行虽不算大，但增长最快（日均 660 行）；②业务上只查询最近 1~2 年的校验记录（超出期限的处方的纠纷举证价值极低）；③分区后 `DROP PARTITION` 清理比 `DELETE` 快两个数量级，且不产生大量 WAL 与死元组。归档策略见附录 E.3。

**只增保护：**

```sql
-- 禁止 UPDATE / DELETE（触发器函数）
CREATE OR REPLACE FUNCTION fn_m10_rx_log_append_only()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'm10_prescription_log 为只增表，禁止 % 操作', TG_OP;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m10_rx_log_append_only
    BEFORE UPDATE OR DELETE ON m10_prescription_log
    FOR EACH ROW EXECUTE FUNCTION fn_m10_rx_log_append_only();

COMMENT ON FUNCTION fn_m10_rx_log_append_only() IS 'm10_prescription_log 只增保护触发器函数';
COMMENT ON TRIGGER trg_m10_rx_log_append_only ON m10_prescription_log
    IS '禁止对处方日志做 UPDATE 与 DELETE';
```

**分区策略：** 按 `created_at` 月度 RANGE 分区，保留 15 年（180 个分区）。
理由：①日均 1,400 行，年 50 万行，10 年 500 万行，属于增长较快的审计表；②按处方取轨迹的查询永远带 `created_at` 范围（页面默认「近 2 年」），分区裁剪后可把扫描范围从 500 万行缩到 100 万行；③保存期 15 年，分区后可按年 `DETACH PARTITION` 归档到冷存储，不影响在线查询；④分区键进入主键，`id` 与 `created_at` 组成复合主键，PostgreSQL 16 允许。

```python
        """距失效剩余天数（已过期为负数）。"""

        """是否可编辑（草稿与驳回态可编辑）。"""
        return self.status in ("DRAFT", "REJECTED") and not self.is_deleted

    def item_of(self, eye_side: str) -> Optional["PrescriptionItem"]:
        """按眼别取明细。"""
        for it in self.items:
            if it.eye_side == eye_side and not it.is_deleted:
                return it
        return None

        """生成签名摘要的规范化载荷（字段顺序固定，保证可复算）。"""
        eyes = []
        for it in sorted(self.items, key=lambda x: x.eye_side):

                continue
            eyes.append({
                "eye_side": it.eye_side,
                "sphere": str(it.sphere),
                "cylinder": str(it.cylinder),
                "axis": it.axis,
                "add_power": str(it.add_power) if it.add_power is not None else None,

                "prism_base": it.prism_base,
                "va_cc": str(it.va_cc) if it.va_cc is not None else None,
                "pd": str(it.pd) if it.pd is not None else None,
                "ph": str(it.ph) if it.ph is not None else None,
            })

            "rx_no": self.rx_no,
            "patient_id": self.patient_id,
            "lens_type": self.lens_type,
            "pd_total": str(self.pd_total) if self.pd_total is not None else None,
            "valid_until": self.valid_until.isoformat(),
            "issued_by": self.issued_by,
            "eyes": eyes,
        }

    @property
    def sphere_equivalent_calc(self) -> Decimal:
        """球镜等效 = 球镜 + 柱镜 / 2，保留两位小数（ROUND_HALF_UP）。"""
        from decimal import ROUND_HALF_UP
        raw = Decimal(str(self.sphere)) + Decimal(str(self.cylinder)) / Decimal(2)
        return raw.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)

    @property
    def rx_text(self) -> str:
        """处方表述文本，如「OD -4.75/-0.75×180°」。"""
        parts = [self.eye_side, "%+.2fD" % float(self.sphere)]
        if self.cylinder and float(self.cylinder) != 0:
            parts.append("%.2fD" % float(self.cylinder))
            parts.append("%d°" % (self.axis or 0))
        if self.add_power is not None:
            parts.append("ADD %+.2fD" % float(self.add_power))
        return " ".join(parts)

    def calc_axis_deviation(self, trial_axis: Optional[int]) -> Optional[int]:
        """与试戴轴位的循环差值（0~90）。"""
        if self.axis is None or trial_axis is None:
            return None
        diff = abs(self.axis - trial_axis) % 180
        return diff if diff <= 90 else 180 - diff

            return False
        if self.expire_date and today > self.expire_date:
            return False
        return True
```
