### 4.2 表：`m10_followup_rule`（复查规则模板表）

**用途：** 定义「什么情况 → 什么时间点 → 谁负责 → 怎么通知」。视光复查有四类触发源（配镜后 / OK 镜戴镜 / 近视监测 / 年度检查），每类都有自己的节点体系与通知策略，系统把规则抽成模板后，M10-06 配镜完成、M10-04 OK 镜发放、儿童建档等场景只需引用 `rule_code` 即可批量生成复查计划，避免各子模块硬编码节点天数。

**写入方：** M10-09 规则配置（P09 配置页 / 系统初始化）。**只读方：** M10-06 / M10-04 / M10-09 计划生成。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |
| rule_code | VARCHAR(32) | N | — | 规则编码 `FR` + 3 位流水，如 `FR001` |
| rule_name | VARCHAR(128) | N | — | 规则名称，如「OK 镜标准复查规则」 |
| trigger_type | VARCHAR(24) | N | — | 触发类型 `POST_FITTING` 配镜后 / `POST_ORTHOK` OK镜戴镜 / `PROGRESSION` 近视监测 / `ANNUAL` 年度检查 / `REPAIR` 维修后 |

**约束说明：**

```sql
-- 规则编码格式 FR + 3 位数字
ALTER TABLE m10_followup_rule
    ADD CONSTRAINT ck_m10_followup_rule_code_format
    CHECK (rule_code ~ '^FR[0-9]{3}$');

-- 触发类型枚举
ALTER TABLE m10_followup_rule
    ADD CONSTRAINT ck_m10_followup_rule_trigger
    CHECK (trigger_type IN ('POST_FITTING', 'POST_ORTHOK', 'PROGRESSION',
                            'ANNUAL', 'REPAIR'));

-- 状态枚举
ALTER TABLE m10_followup_rule
    ADD CONSTRAINT ck_m10_followup_rule_status
    CHECK (status IN ('ENABLED', 'DISABLED'));

-- OK 镜复查必须阻断换片
ALTER TABLE m10_followup_rule
    ADD CONSTRAINT ck_m10_followup_rule_orthok_blocking
    CHECK (trigger_type <> 'POST_ORTHOK' OR is_blocking_renew = TRUE);

-- 节点列表必须是 JSON 对象且含 nodes 数组
ALTER TABLE m10_followup_rule
    ADD CONSTRAINT ck_m10_followup_rule_nodes
    CHECK (jsonb_typeof(node_list) = 'object' AND node_list ? 'nodes');

-- 脱管天数必须大于 0
ALTER TABLE m10_followup_rule
    ADD CONSTRAINT ck_m10_followup_rule_lock_days
    CHECK (overdue_lock_days > 0);

-- 版本号必须为正
ALTER TABLE m10_followup_rule
    ADD CONSTRAINT ck_m10_followup_rule_version
    CHECK (rule_version >= 1);
```

**设计要点：**

1. **规则版本化**：`rule_version` 递增，已生成的 `m10_followup_plan` 保存 `rule_code` + `rule_version` 快照。改规则不追溯已有计划，避免历史计划被静默改写。
2. **节点可重复**：M3 节点用 `repeat_interval_days` + `repeat_until_days` 表达「每 3 个月重复到第 540 天」，展开后生成多个 `m10_followup_task`。
3. **OK 镜强制阻断**：`is_blocking_renew = TRUE` 时，逾期 > `overdue_lock_days` 会阻断 M10-04 的再次验配入口（角膜安全）。
4. **人群区分**：儿童（<18 岁）与成人节点不同，`patient_scope` 用于自动匹配。

### 4.3 表：`m10_followup_plan`（复查计划主表）

**用途：** 一次配镜 / 一次 OK 镜验配 / 一个儿童的近视监测周期，对应**一组**复查计划。计划是复查业务的「档案袋」，`m10_followup_task` 是里面的每一次待办。**这是 M10-09 的核心表**，`plan_no` 被 `m10_followup_task`、`m10_followup_notify`、`m10_followup_visit` 三方引用，也被 M03-04 全院随访引用（通过 P-26 推送）。

**写入方：** M10-09（计划生成与维护）。**只读方：** M03-04（全院随访框架，通过 P-26 接收）、M19（会员运营）、M22（报表）。

**设计要点：**

1. **计划 = 档案袋，任务 = 待办。** 一次 OK 镜验配会生成 1 个计划 + 8~10 个任务。计划上冗余 `series_total/series_done/series_missed` 是为了列表页不必聚合任务表。
2. **`next_due_date` 是到期扫描的主键。** 任务完成时同步更新计划的 `next_due_date`，使 P-24 只需扫描计划表的**部分索引**（`idx_m10_followup_plan_due`），不必 JOIN 任务表。
3. **`node_snapshot` 冻结规则。** 规则改版后，历史计划的节点定义仍按生成时快照执行，避免"规则一改，所有人复查节点全变"。
4. **儿童必须有监护人。** 通过 CHECK 约束用 `birth_date + 18 years > start_date` 判定，避免应用层遗漏。
5. **OK 镜强制来源约束。** `followup_type = 'POST_ORTHOK'` 必须来自 `ORTHOK_FITTING`，防止手工伪造 OK 镜复查计划绕过验配记录。
6. **拒收不删计划。** 患者拒收通知时置 `notify_enabled = FALSE` 并记 `notify_rejected_at`，计划仍保留（复查仍是医疗需要），但到期扫描跳过通知阶段、直接计为待提醒人工跟进。

**设计要点：**

1. **只增不删。** 用只增触发器保护（见附录 E）。通知记录是合规证据（「我们确实提醒过」），不可修改。
2. **骚扰控制。** 同一患者 30 天内通知超过 6 次时置 `send_status = 'SKIPPED'` 并记 `fail_reason = 'FREQUENCY_LIMIT'`，防止重复骚扰。
3. **回执对齐。** `message_record_no` 关联 M03-05 的消息记录，订阅 `m03.message.receipt` 事件回填 `receipt_status`，用于判断「短信是否真的送达」。
4. **分区表主键必须含分区键**（`PRIMARY KEY (id, created_at)`），因此业务侧按 `id` 单独查时需带 `created_at` 范围或走索引。

### 4.8 表：`m10_vision_archive_record`（档案纵向记录点表）

**用途：** 视力档案的**时间序列数据点**。每次验光签发（`m10.optometry.signed`）、每次复查到访、每次 OK 镜配适评估，都会写入一个记录点。这是画「屈光进展曲线」的原始数据。

**关键设计说明（为什么 M10-09 不建第二套验光表）：**

> 验光数据（SPH/CYL/AXIS/PD/眼轴/角膜曲率）的**唯一权威源是 M10-01 的 `m10_optometry` + `m10_optometry_refraction`**。M10-09 若自建一套验光字段，会立刻出现「档案里的度数和验光单对不上」的问题，且验光单作废时档案数据无法同步。
>
> 因此本表**不重复存储验光明细的完整结构**，而是：
> - 存 `source_type` + `source_id` + `source_no`（指针，可追溯回原始单据）
> - **冗余存储**画曲线必需的 6 个关键值（SE、球镜、柱镜、矫正视力、眼轴），因为曲线渲染要读 100~200 个点，不能 JOIN 200 次
> - 冗余值在写入时**从原始单据复制**，并有 `sync_status` 字段标记是否与源一致，每日对账校验

**写入方：** M10-09（订阅事件与复查完成后写入）。**只读方：** M10-09 曲线页、P-25 摘要、M22 报表。

**设计要点：**

1. **唯一索引保证幂等入档。** 同一验光单重复推送事件时，`uk_m10_vision_archive_record_src` 会拦截，用 `ON CONFLICT DO NOTHING`。
2. **`measure_state` 区分散瞳前后。** 儿童散瞳前后 SE 可差 1.00D 以上，混在一起画曲线会失真。曲线默认只画非散瞳数据，散瞳数据单独标记。
3. **`sync_status` 支持源作废传播。** 验光单作废时，M10-01 发布 `m10.optometry.voided`，本模块把对应记录置 `SOURCE_VOID` 并从曲线中排除（不物理删除，保留审计）。
4. **`record_age` 冗余。** 年龄-屈光曲线是儿童近视分析的核心视图，不能每次从 `birth_date` 现算（涉及浮点月龄），写入时算好。

### 4.9 表：`m10_vision_progression`（屈光进展与预警表）

**用途：** 把 4.8 的**纵向记录点**两两相减，算出「某个观察窗口内屈光与眼轴变化了多少、折合每年多少、是否达到预警门槛」。一行代表一个**进展评估窗口**（相邻两次有效记录之间，或固定 6/12 个月的评估期）。屈光进展曲线上的「年化进展 0.92 D/年」「眼轴 0.31 mm/年」这些数字直接来自本表，**不靠页面临时计算**。

**为什么必须独立成表（不能由页面实时算）：**

1. **预警要有留痕。** 一旦判定 `HIGH`/`CRITICAL` 并触发提醒、医生干预（换镜、加阿托品、角膜塑形镜），这条判断必须可回溯——「当时依据哪两个记录点、阈值是多少、算出来多少」。页面现算无法留痕，也无法在阈值调参后解释历史结论。
2. **进展评估是批量任务。** 每晚 `job_m10_progression_refresh` 要对「近 90 天有新记录点的档案」重算窗口。若不落表，每个档案每次打开都要现算 10~20 个窗口，P-25 摘要的 150ms 预算撑不住。
3. **阈值判定需要多阈值组合。** 等效球镜年化进展、眼轴年化增速、以及两者**同时**超标（`RAPID_COMBINED`）三种告警口径，落在表里才能做「近 90 天新增高危档案」这类运营查询。

**写入方：** M10-09 进展评估任务（每日批量 + 新增记录点后的事件驱动单档案重算）。**只读方：** M10-09 曲线页与预警看板、P-25 摘要（只读档案表上的汇总值）、M07 医生站、M11 屈光（手术时机评估）、M22 报表。

**分区策略：** 不分区。年增量约 5 万条（2.5 万在管档案 × 人均 2 个/年），5 年 25 万条；单档案窗口序列最多几十行，走 `idx_m10_vision_progression_archive` 是索引内顺序扫描。

**设计要点：**

1. **唯一的「窗口」定义在数据库层。** `uk_m10_vision_progression_period(archive_id, period_start, period_end)` 保证同一档案同一窗口只有一条结论。夜间批量重算时用 `INSERT ... ON CONFLICT (archive_id, period_start, period_end) DO UPDATE`，天然幂等，任务重跑不会产生「一个窗口两条互相矛盾的预警」。
2. **按较差眼判定，不按平均值判定。** `delta_se_worse` 取双眼变化绝对值较大的一侧。临床上单眼快速进展（如单眼 OK 镜偏位）远比双眼均速平均更要紧，若按 `delta_se_avg` 判定会被另一只稳定的眼稀释掉告警。
3. **阈值版本化，历史预警不被追溯改写。** 参数 `M10.FOLLOWUP.PROGRESSION_WARN` 从 0.75 调到 0.50 后，只影响新计算的窗口；已产生的预警保留 `threshold_version = 1` 与原 `alert_rules` 明细，便于解释「去年为什么没报警」。
4. **`MIXED` 强制降级。** 基线非散瞳、当前散瞳的对比毫无意义（假性近视被剥掉，SE 会「变好」）。约束把 `measure_state = 'MIXED'` 的等级压到 `LOW`/`MEDIUM`，避免制造虚假高危。真正的做法是窗口构造时优先配对同测量状态的记录点。
5. **窗口过短要有 RATE_ABNORMAL 兜底。** `interval_months < 2` 时年化折算会把 0.25 D 的变化放大成 1.5 D/年。此时类型记 `RATE_ABNORMAL`、`review_required = TRUE`，提示医生「观察期太短，结论仅供参考」，而不是直接判高危。
6. **失效不删行。** 基线记录点被置 `SOURCE_VOID`（验光单作废）后，本表把记录置 `is_effective = FALSE` 并写明原因，曲线页与看板按 `is_effective = TRUE` 过滤。这样「曾经的预警」仍可审计。
7. **不冗余年龄区间阈值。** 学龄儿童年化进展 0.75 D/年才算预警，而低龄（6~9 岁）与青春期后的阈值不同。年龄相关阈值由服务层按 `birth_date` 与参数表换算，本表只记录**算完后**的判定结果与阈值版本。

### 4.10 表：`m10_followup_stat`（复查依从性统计表）

**用途：** 按「统计日 × 统计粒度 × 复查类型 × 责任医生」预聚合的四张计数（到期 / 已做 / 漏查 / 取消）与依从率，外加 OK 镜脱管专项的三个计数。复查依从性是视光中心最核心的运营指标（「配镜后 3 个月回访率 68%」），也是 OK 镜安全管理的抓手（「超过 30 天未复查的戴镜者 12 人」）。

**为什么不实时聚合 `m10_followup_task`：**

1. **任务表是「流水」，统计要的是「快照」。** 到期数、已做数是**按时间窗**滚动的：今天到期 120 个任务，30 天后这批任务的状态全变了，但「10 月 31 日到期 120 个」这个历史事实不应改变。实时聚合会得到「同一个历史日期，今天查和昨天查结果不同」的漂移。
2. **看板要求秒开。** P09 依从性报表要在一个屏上同时展示「近 12 个月 × 5 种复查类型 × 20 位医生」共 1,200 个格子的依从率。实时 GROUP BY 任务表 + 到访表 + 通知表三表关联，在 60 万行任务上不可接受；预聚合后只需读 1,200 行。
3. **脱管监控必须能看趋势。** 「本月 OK 镜逾期 > 30 天 12 人，上月 8 人」——判断脱管是否恶化，靠的是每日快照的序列，而不是今天的现状。

**粒度说明（关键）：** `stat_type = 'DAILY'` 的 `stat_date` 是**统计快照日**（即「在这一天统计得出的数字」），而**不是**到期日；`stat_type = 'MONTHLY'` 的 `stat_date` 取当月**月末最后一天**。两套粒度并存是因为日常巡检看「今天」，运营复盘看「本月」，分别落一份避免月度报表时回算日快照的加权口径争议。

**写入方：** M10-09 统计任务（APScheduler `job_m10_followup_stat_daily` 每日 00:30、`job_m10_followup_stat_monthly` 每月 1 日 01:00）。**只读方：** M10-09 P09 依从性报表与 OK 镜脱管看板、M22（院长驾驶舱）、M10-04（戴镜随访质量）。

**分区策略：** 不分区。按「日 × 5 类型 × 20 医生 × 3 门店 + 节点维度」估算，日快照约 300 行/天，年 11 万行；月汇总约 400 行/月，年 5 千行。若节点维度全量展开导致年增超 100 万行，可按 `stat_date` 年度分区并仅保留 36 个月日快照（月汇总永久保留）。

**设计要点：**

1. **计数器恒等式在库层兜底。** `done + missed + cancelled + pending = due` 是依从率可信的前提。约束一旦违反说明统计 SQL 逻辑有误（例如 `LEFT JOIN` 漏行、`is_deleted` 漏过滤），让它在写库时就失败，而不是让错误的比率流到院长驾驶舱。
2. **比率与计数同时存，且互相校验。** 报表页直接读 `compliance_rate` 免现算；`ck_m10_stat_compliance_consist` 用 0.05 个百分点容差反向校验比率与计数一致，防止「口径改了但比率没重算」。
3. **`doctor_id = 0` 表达「全科室汇总」。** 若用 NULL 表达汇总，唯一索引 `uk_m10_followup_stat` 会因 `NULL <> NULL` 失效，同一维度会插入多行。固定用 0 让唯一约束可靠生效（业务上 M01 的职工 ID 从 1 开始）。
4. **`DAILY` 与 `MONTHLY` 分开写，不做「日汇总成月」。** 月度依从率的分母是「当月应查数」，而月内可能因计划终止而撤销任务；日快照累加会与月末口径不一致。两条独立 SQL 各算各的，`period_start/period_end` 明确落在哪一行。
5. **OK 镜脱管指标单列而非复用 `missed_count`。** 脱管的定义是「应复查日已过 30 天仍未到访」（`overdue_days > 30`），与「窗口结束即判 `MISSED`」不同——窗口结束 10 天时任务已是 `MISSED`，但还不算脱管。两个口径混用会导致「脱管人数」在月初暴涨、月末回落的假象。
6. **`is_final` 明确可覆盖边界。** 当日日快照与当月月汇总允许反复重算（`is_final = FALSE`），`ON CONFLICT DO UPDATE` 覆盖；已过去的日期一旦定稿不再改写，保证历史报表稳定。若需修正历史，走「重算并记录 `remark`」的显式流程。
7. **`calc_version` 与 `calc_duration_ms` 是运维抓手。** 口径升级后新旧行并存，报表按 `calc_version` 过滤或换算；耗时字段用于监控统计任务随数据增长是否劣化（超过 60 秒告警）。

class M10VisionProgression(Base):
    """屈光进展与预警表：把纵向记录点折算为年化进展量与预警级别。

    公式：rate_per_year = delta_se_worse / interval_months * 12
          axial_growth_rate = delta_axial_worse / interval_months * 12
    阈值：近视加深 > 0.50D/年 关注；> 0.75D/年 预警；> 1.00D/年 高危；
          儿童眼轴增速 > 0.20mm/年 预警。命中结果落在 alert_rules JSONB 供回溯。
    """

    __tablename__ = "m10_vision_progression"
    __table_args__ = (
        Index("uk_m10_vision_progression_period", "archive_id", "period_start", "period_end",
              unique=True, postgresql_where=text("is_deleted = FALSE")),
        Index("uk_m10_vision_progression_no", "progression_no", unique=True),
        Index("idx_m10_vision_progression_alert", "alert_level", text("created_at DESC")),
        Index("idx_m10_vision_progression_archive", "archive_id", text("period_end DESC")),
        Index("idx_m10_vision_progression_unhandled", "alert_level", "notified_at",

## 附录 F：文档维护约定

| 约定 | 说明 |
|---|---|
| 变更入口 | 表结构以本文档为准，变更须同步更新《详细设计》第 4 章指引块的表数 |
| 命名不可变 | 已发布的表名、字段名不可改名（影响 M03-04、M10-04、M07、M11、M19、M22 的只读引用） |
| 新增字段 | 只允许在表尾部追加可空字段，禁止在中间插入（避免代码按位置映射） |
| 枚举扩展 | `node_code` / `notify_type` 类枚举扩展须同步更新 CHECK 约束与附录 B |
| 规则演进 | 修改 `m10_followup_rule` 必须递增 `rule_version`，不得在已发布版本上原地改节点天数（历史计划靠 `node_snapshot` 冻结） |
| 验光数据 | `m10_vision_archive_record` 的冗余值与源单据不一致时，以 M10-01 为准并重同步，禁止直接改本表数值 |
| 临床记录 | `m10_followup_visit` 与 `m10_vision_archive_record` 只允许更正（amend 留痕），逻辑删除仅对管理员的作废入口开放 |
| 敏感字段 | `contact_phone` / `guardian_phone` / `receiver_phone` 明文不入普通列，展示掩码；导出须审计 |
| 容量治理 | `m10_followup_stat` 当前不分区（年约 11 万行，见 4.10 分区策略）；若节点维度全量展开致年增超 100 万行，再按 `stat_date` 年度分区。`m10_followup_task` 终态按季度归档至 `_hist` 表 |
| 阈值版本 | 附录 D 的 `M10.FU.*` 阈值调整须递增 `m10_vision_progression.threshold_version` |
