### 4.2 表：`m10_customer`（视光顾客档案主表）

**用途：** 视光顾客档案的**权威主表**，一行代表一个「来视光中心消费的人」。本表解决的核心问题是：**视光中心可以接待从未在本院挂号的配镜顾客**。这类顾客在 M03 患者主索引里没有 `patient_id`，也不应该为了卖一副眼镜而在 M03 造一个假患者。因此本表用自有的 `customer_no`（`KH` + 6 位流水）作为主键业务标识，`patient_id` **允许为空**；当该顾客日后在本院就诊并产生就诊记录时，再由应用层单向回填 `patient_id`，绝不反向在 M03 创建或污染患者档案。

写入方：M10-05（前台建档、顾客维护、P-11 ensure）；只读方：M10-06 订单、M10-08 会员、M16-04 开单时通过 P-10 取顾客摘要。

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m10_customer` | 主键 | `id` | — |
| `uk_m10_customer_no` | 唯一（部分） | `customer_no` WHERE `is_deleted = FALSE` | 顾客号唯一 |
| `uk_m10_customer_phone` | 唯一（部分） | `phone_hash` WHERE `is_deleted = FALSE AND customer_status <> 'MERGED'` | **手机号唯一（业务主键）**，已合并记录让出唯一性 |
| `idx_m10_customer_patient` | B-Tree（部分） | `patient_id` WHERE `patient_id IS NOT NULL` AND `is_deleted = FALSE` | **按患者反查顾客（M16-04 开单、M10-06）主力索引** |
| `idx_m10_customer_idcard` | B-Tree（部分） | `id_card_hash` WHERE `id_card_hash IS NOT NULL` | 身份证查重 |
| `idx_m10_customer_name_trgm` | GIN | `customer_name` `gin_trgm_ops` | 中文姓名模糊查 |
| `idx_m10_customer_phone_suffix` | B-Tree（表达式） | `right(phone, 4)` | **按手机尾号 4 位检索**（前台最常用） |
| `idx_m10_customer_pinyin` | B-Tree | `name_pinyin`, `name_pinyin_short` | 拼音检索 |
| `idx_m10_customer_link` | B-Tree（部分） | `link_status` WHERE `link_status IN ('PENDING','CONFLICT')` | 待关联/冲突队列 |
| `idx_m10_customer_status` | B-Tree | `customer_status`, `last_visit_at` DESC | 状态筛选与最近到店排序 |
| `idx_m10_customer_source` | B-Tree | `source`, `created_at` DESC | 来源分析 |
| `idx_m10_customer_last_purchase` | B-Tree（部分） | `last_purchase_at` WHERE `is_deleted = FALSE` | 复购/流失统计扫描 |
| `idx_m10_customer_churn` | B-Tree（部分） | `churn_risk`, `last_purchase_at` WHERE `churn_risk = 'HIGH'` | 流失预警清单 |
| `idx_m10_customer_wechat` | B-Tree（部分） | `wechat_open_id` WHERE `wechat_open_id IS NOT NULL` | 线上来源匹配 |
| `idx_m10_customer_store` | B-Tree | `org_id`, `store_code`, `created_at` DESC | 门店数据权限与统计 |

**约束说明：**

```sql
-- 顾客号格式：KH + 6 位流水
ALTER TABLE m10_customer
    ADD CONSTRAINT ck_m10_cust_no_format
    CHECK (customer_no ~ '^KH[0-9]{6}$');

-- 身份标识兜底：手机号与身份证至少有一个（手机号实为 NOT NULL，此约束防未来放宽）
ALTER TABLE m10_customer
    ADD CONSTRAINT ck_m10_cust_identity
    CHECK (phone IS NOT NULL OR id_card_hash IS NOT NULL);

-- 手机号格式：11 位大陆手机号或以 0 开头的座机
ALTER TABLE m10_customer
    ADD CONSTRAINT ck_m10_cust_phone_format
    CHECK (phone ~ '^1[3-9][0-9]{9}$' OR phone ~ '^0[0-9]{9,11}$');

-- 性别枚举
ALTER TABLE m10_customer
    ADD CONSTRAINT ck_m10_cust_gender
    CHECK (gender IN ('M', 'F', 'U'));

-- 顾客状态枚举
ALTER TABLE m10_customer
    ADD CONSTRAINT ck_m10_cust_status
    CHECK (customer_status IN ('ACTIVE', 'MERGED', 'DISABLED', 'BLACKLIST'));

-- 已合并必须有目标顾客号，且不能合并到自己
ALTER TABLE m10_customer
    ADD CONSTRAINT ck_m10_cust_merged
    CHECK (customer_status <> 'MERGED'
           OR (merged_into_no IS NOT NULL
               AND merged_into_no <> customer_no));

**关联状态机（`link_status` 与 `patient_id` 的双向约束是本表最关键设计）：**

| `link_status` | `patient_id` | 含义 | 允许的迁移动作 |
|---|---|---|---|
| `UNLINKED` | NULL | 纯配镜顾客，从未就诊 | → `LINKED`（挂号/就诊带出）、→ `PENDING`（多候选） |
| `PENDING` | NULL | 有候选患者但需人工确认 | → `LINKED`（人工确认）、→ `UNLINKED`（人工否决） |
| `LINKED` | 非空 | 已关联患者档案 | 不可回退；`patient_id` 只读 |
| `CONFLICT` | NULL | 命中多个患者候选 | → `LINKED`、→ `UNLINKED` |

**设计要点：**

1. **为什么 `patient_id` 必须允许为空，而不是「先建患者再配镜」？**
   视光中心日均到店 110 人，其中约 62% 是从未在本院挂号的「纯配镜顾客」（含外地顾客、陪同家属、团购到手顾客）。若强制在 M03 建档：①M03 `mpi_patient` 年增 2.5 万条假患者，直接污染患者主索引查重与统计口径；②这些「患者」没有就诊记录，却会进入门诊量、患者满意度、随访池等所有患者维度报表；③M03-02 患者匹配合并任务会把它们与真实患者反复误配。因此本模块自持顾客档案，`patient_id` 为空是**合规且正常**的状态，不是缺陷。

2. **为什么用 `phone_hash` 而不是直接对 `phone` 建唯一索引？**
   手机号是个人敏感信息，明文唯一索引会在 `pg_stat_statements`、慢查询日志、备份中留下大量明文。改为 `phone_hash`（SHA-256 + 固定盐，盐存 KMS）后，索引与日志中只见哈希；同时 `phone_hash` 天然等值匹配，索引效率与明文一致。查询时先算哈希再走索引，业务代码感知不到差异。

3. **为什么唯一索引要带 `customer_status <> 'MERGED'` 的部分条件？**
   合并场景：顾客 A（`KH000128`）与顾客 B（`KH000341`）同手机号，合并后 B 被标记 `MERGED`。若唯一索引不含该条件，合并后两条记录同 `phone_hash` 会直接违反唯一约束。加条件后，被合并记录让出唯一性，`ACTIVE` 记录独占，既保证「活跃顾客手机号唯一」，又保留历史档案可追溯。

4. **为什么 `link_status` 与 `patient_id` 要做双向 CHECK？**
   单向约束（只保证 LINKED 时非空）会留下「`UNLINKED` 但 `patient_id` 有值」的脏数据——这类数据的后果是 P-10 取顾客时把没有确认关联的患者信息带出去，属于隐私事故。`ck_m10_cust_unlinked` 从数据库层封死了这条路径。

5. **为什么有 `customer_no` 还要 `id` 作为主键？**
   与全模块一致：`id` 是 BIGINT 代理主键，供内部 JOIN 与 Redis 键使用；`customer_no` 是业务单号，对外暴露、可打印、可口头播报。若用 `customer_no` 做主键，一旦单号规则调整（如扩位）就要改所有关联表。

6. **为什么金额类字段（`total_amount` / `avg_amount`）只做快照并标注「禁止本模块计算」？**
   M16 是唯一的钱账权威方。本表这些字段仅供「消费分析页（P08）」列表展示与流失预警排序，**由 M16-04 事件回写**；每日 02:30 由 `m10_customer_amount_reconcile` 任务与 M16-04 对账，差异 > 0.01 元告警。若本模块自行累加，一旦出现退换/冲红，两套数必然对不上。

7. **为什么 `churn_risk` / `next_expected_date` 落在主表而不是单独统计表？**
   这两个字段是「流失预警」清单（P08）的过滤与排序键，高频查询。放在主表可建部分索引 `idx_m10_customer_churn`，直接命中；若单开统计表则每次都要 JOIN，且统计表与主表的一致性维护成本更高。代价是主表增加 4 个统计字段，可接受。

8. **为什么不建物理外键？**
   ①`patient_id` 指向 M03，跨 schema 时外键不可用；②`last_rx_no` 指向 M10-02 的表，属不同子模块文件，外键会增加建表顺序耦合；③本表为高写入表（日均 110 INSERT + 数百 UPDATE），外键检查拖慢；④一致性由应用层校验 + 每日对账任务保证。**代价**是可能出现悬挂引用，由 `m10_customer_ref_reconcile` 每日检查并告警。

    ADD CONSTRAINT ck_m10_cust_ext_se_range
    CHECK (myopia_degree_ou IS NULL
           OR (myopia_degree_ou >= -30.00 AND myopia_degree_ou <= 30.00));

COMMENT ON TABLE m10_customer_ext IS '视光专属扩展：职业/用眼场景/驾驶需求/运动需求，驱动场景化选品推荐';
COMMENT ON COLUMN m10_customer_ext.face_shape IS '脸型，镜架匹配度推荐的主输入（P04 选品工作台）';
COMMENT ON COLUMN m10_customer_ext.myopia_degree_ou IS '双眼等效球镜快照，由 m10.optometry.created 事件回写，非本表计算';
COMMENT ON COLUMN m10_customer_ext.ortho_k_candidate IS 'OK 镜候选标记，命中后供 M10-04 验配准入参考';
```

**设计要点：**

1. **为什么拆出扩展表而不是全放主表？** 主表已有 50+ 字段，其中扩展字段读频率低（仅选品页与营销页使用），但列宽（`previous_concerns` 512 字符等）会显著增大主表行宽，拖慢最高频的「按手机尾号查顾客（P01/P02）」。拆表后主表行宽从约 1.2 KB 降到 760 B，主表点查 I/O 减少约 37%。

2. **为什么 `usage_scene` 存逗号分隔而 `primary_scene` 单独存？** 多选用逗号分隔是为了避免再开一张从表（低频字段，从表收益低于成本）；但推荐算法需要**单一主场景**做权重排序，故冗余一个 `primary_scene`。写入时由应用层保证 `primary_scene` 必在 `usage_scene` 集合中（`1005032`）。

3. **为什么 `face_shape` / `face_width_level` 在这里而不是在主表？** 它们是**选配专用**参数，不属于顾客身份。放扩展表后，P04 选品工作台一次 JOIN 即可取到全套推荐输入，不会污染主表。

4. **`myopia_degree_ou` 为什么是快照？** 它是验光结果的派生值（等效球镜 `SE = SPH + CYL/2`），权威在 M10-01 验光单。本表只存快照供筛选；每次 `m10.optometry.created` 事件到达时由事件处理器重算并回写，不作为验光数据源。

### 4.5 表：`m10_customer_tag`（顾客标签关系表）

**用途：** 顾客与标签的**多对多关系表**，一行代表「某顾客在某时间被打上某标签」。标签是视光运营的核心抓手：`STUDENT`（学生）驱动开学季营销，`HIGH_MYOPIA`（高度近视）驱动高折射率推荐，`MYOPIA_CONTROL`（近视防控）驱动离焦镜片与 OK 镜推荐，`DR_RETINA`（糖尿病视网膜病变相关配镜）驱动轻薄化与复查提醒。

标签分**自动标签**（规则命中，由事件与定时任务写入）与**手工标签**（前台/店长手工打标）。自动标签可被规则收回，手工标签只能人工移除。

写入方：M10-05 标签服务、事件处理器（`m10.optometry.created`、`m16.optical.order.created`）、定时任务；只读方：P04 选品推荐、P07 标签关怀、P08 消费分析。

```sql
-- 标签编码枚举

    ADD CONSTRAINT ck_m10_cust_tag_code
    CHECK (tag_code IN ('STUDENT', 'HIGH_MYOPIA', 'MYOPIA_CONTROL', 'DR_RETINA',

                        'CONTACT_LENS', 'SENIOR', 'CHILD', 'NIGHT_DRIVER',

                        'CHURN_RISK', 'NEW_CUSTOMER'));

-- 标签分组枚举
ALTER TABLE m10_customer_tag
    ADD CONSTRAINT ck_m10_cust_tag_group
    CHECK (tag_group IN ('BUSINESS', 'CLINICAL', 'MARKETING', 'RISK', 'PROFILE'));

-- 标签来源枚举
ALTER TABLE m10_customer_tag
    ADD CONSTRAINT ck_m10_cust_tag_source
    CHECK (tag_source IN ('AUTO', 'MANUAL', 'IMPORT'));

-- 自动标签必须给规则编码与置信度
ALTER TABLE m10_customer_tag
    ADD CONSTRAINT ck_m10_cust_tag_auto
    CHECK (tag_source <> 'AUTO'
           OR (rule_code IS NOT NULL AND confidence IS NOT NULL));

-- 置信度范围
ALTER TABLE m10_customer_tag
    ADD CONSTRAINT ck_m10_cust_tag_confidence
    CHECK (confidence IS NULL OR (confidence >= 0 AND confidence <= 1));

-- 收回必须填时间与原因
ALTER TABLE m10_customer_tag
    ADD CONSTRAINT ck_m10_cust_tag_revoke
    CHECK (is_active = TRUE
           OR (revoked_at IS NOT NULL
               AND revoke_reason IS NOT NULL
               AND char_length(btrim(revoke_reason)) >= 2));

-- 生效日期不晚于失效日期
ALTER TABLE m10_customer_tag
    ADD CONSTRAINT ck_m10_cust_tag_period
    CHECK (effective_to IS NULL OR effective_to >= effective_from);

COMMENT ON TABLE m10_customer_tag IS '顾客标签关系表：自动标签可被规则收回，手工标签仅可人工移除';
COMMENT ON COLUMN m10_customer_tag.hit_value IS '命中判定值快照，用于解释标签来源（如等效球镜 -7.25）';
COMMENT ON COLUMN m10_customer_tag.confidence IS '自动标签置信度 0.000~1.000，手工标签固定 1.000';
```

**设计要点：**

1. **为什么用「关系表 + 布尔生效位」而不是简单的多对多关联表？** 标签需要**可追溯**：顾客曾经是「新客」，一年后不再是，这个事实要在历史里留存以便分析转化率。若物理删关系行，「曾被标记为新客」这一信息就丢了。因此用 `is_active` 软收回 + `revoked_at/revoke_reason` 留痕，配合部分唯一索引保证「生效标签不重复」。

2. **为什么 `uk_m10_customer_tag` 是部分唯一索引？** 一个顾客可能先后多次被标为 `HIGH_MYOPIA`（配镜 → 度数加深 → 又被标一次），历史行必须允许重复；只有 `is_active = TRUE` 的行需要唯一。部分索引精准表达了这个业务语义。

3. **为什么 `tag_name` 冗余存而不是只存 `tag_code`？** 标签字典可能改名（如「高度近视」改「高度近视人群」）。历史记录应反映打标当时的口径，故存快照。这是与 M05 快照策略一致的做法。

4. **为什么 `hit_value` 存字符串？** 不同标签的判定值类型不同（等效球镜是 decimal、订单数是 int、场景是文本）。统一存 `VARCHAR` 便于展示与解释，避免为每个标签开列。

**量级估算：** 年新增 130,000 行（人均 3.2 个标签），10 年 1,300,000 行，表约 208 MB。

**分区：** 不分区。理由：①130 万行仍属单表舒适区间；②主查询是「按 `tag_code` + `is_active` 查顾客」（`idx_m10_customer_tag_code`），分区剪枝无收益；③`uk_m10_customer_tag` 是活跃行部分唯一索引，分区后会失去跨分区唯一性保证。

**设计要点：**

1. **为什么把「报价快照」存在会话上（`quote_snapshot` + `quote_no`）？**
   顾客看到的报价必须**可复现**。视光商品价格有版本（M01 收费价格版本化）、度数加价会随矩阵变更、M16-06 的优惠活动有生效期。若只存一个 `payable_amount`，事后顾客质疑「你当时说 2,871 元怎么现在 3,120 元」就无从举证。存完整快照 + 报价单号 + 有效期，既满足合规（价格告知留痕），也支撑「报价过期须重新试算」的规则。

2. **为什么 `session_ttl_at` 落库而不是只用 Redis TTL？**
   Redis 的 `m10:selection:{customer_no}` 是**热态会话缓存**（TTL 4h），进程重启即丢。落库的 `session_ttl_at` 是**权威过期时间**，Redis 未命中时从库重建；过期扫描任务（`job_m10_selection_expire`）也扫库。两层各司其职：Redis 负责低延迟读写，DB 负责持久与审计。

3. **为什么 `item_count` / `unavailable_count` 冗余？**
   P01 前台工作台的「我的接待」列表要显示每个会话有几件商品、几件缺货，若不冗余就要对 `m10_selection_draft` 做 N+1 聚合。冗余计数在草稿增删时同事务更新，读性能提升一个量级。

4. **为什么会话要支持「换人接待」（`handler_log`）？**
   视光中心是**低峰位接待**：一个销售员同时接待 2~3 位顾客，顾客在等试戴时销售员可能被叫去协助他人。若会话绑定销售员强校验，换人就要重建会话并丢失已选商品。因此会话以 `customer_no` 为 Redis 键（而非 `salesperson_id`），换人只需更新 `salesperson_id` 并追加 `handler_log`，草稿与会话号全部保留。

5. **为什么 `gross_amount` / `payable_amount` 是字段而不是视图计算？**
   它们全部是**上游返回值的落库快照**（`frame_amount`/`lens_amount`/`surcharge_amount` 来自 M01-08 pricing，`service_amount` 来自 M01-06 计费试算，`discount_amount`/`payable_amount` 来自 M16-06 discount/calc）。本模块**不对它们做任何算术推导**，只做存储与展示。`ck_m10_sess_payable_le_gross` 只是防御性校验，不是业务计算。

6. **为什么 `ABANDONED` 要强制填原因？**
   放弃原因是选配转化率分析的唯一抓手。没有原因的「流失」只能得出「没买」这个无用结论；有了 `PRICE`/`NO_STOCK`/`STYLE` 分类，才能指导商品结构优化（如「无货」占比高 → 补货；「价格贵」占比高 → 调整中低端 SKU）。

### 4.7 表：`m10_selection_draft`（选配草稿明细表）

**用途：** 选配会话中**每一行商品**的草稿记录。一行 = 「一个商品 + 一组度数 + 一次光度校验结果 + 一次取价结果 + 一次替换建议」。本表是选品工作台（P04）与替换推荐（P05）的**唯一数据落点**。

三个关键设计：
- **光度校验结果落库（`lookup_result`）**：M01-08 `specs/lookup` 的返回整包快照，避免每次刷新页面重调上游；同时为「为什么当时推荐这个」留证。
- **取价结果落库（`pricing_snapshot`）**：M01-08 `pricing` 的返回整包快照（含度数加价明细），**本模块不参与任何金额计算**。
- **替换推荐落库（`replacement_json`）**：光度不可供时的候选替换清单与推荐理由，供 P05 展示与店长复盘。

**设计要点：**

1. **为什么 `sphere`/`cylinder`/`axis` 落在草稿行而不是引用验光单？**
   选配时销售员可能**微调度数**（如顾客试戴后接受 `-4.00D` 而非处方的 `-4.25D`），也可能为术后/渐进片单独指定 ADD。草稿行必须持有「本次实际要售卖的度数」，不能只挂 `rx_no`。`rx_snapshot` 在会话上留档原始处方，草稿行记录实际售卖值，两者对照即为「处方执行偏差」的审计基础。

2. **为什么 `lookup_result` 和 `pricing_snapshot` 都存整包 JSONB 而不是拆列？**
   ①M01-08 返回结构可能扩展（新增字段不影响本模块）；②整包快照是**上游返回的原始凭证**，事件追溯时可原样比对，若拆列则丢失未建模字段；③关键字段（`final_price`/`surcharge`/`lead_time_days`/`supply_type`）已冗余为独立列供索引与展示，JSONB 只做证据留存。这是「**结构化列供查询 + JSONB 供留证**」的双轨设计。

3. **`face_match_score` 的计算口径（0~100 分）：**
   ```
   score = 40 × 脸型分 + 30 × 宽度分 + 20 × 瞳距分 + 10 × 材质分
   脸型分：镜架适用脸型包含顾客脸型 → 1.0；互补脸型（圆脸↔方脸）→ 0.8；否则 0.3
   宽度分：|镜架总宽 − (顾客PD + 2×镜框宽×0.06)| ≤ 4mm → 1.0；≤ 8mm → 0.7；否则 0.3
   瞳距分：PD 落在镜框光学中心 ±2mm → 1.0；±4mm → 0.6；否则 0.2
   材质分：顾客 skin_sensitive 且镜架非纯钛 → 0.3；weight_sensitive 且重量 > 20g → 0.4；否则 1.0
   ```
   **该得分只用于排序推荐，不参与任何金额计算**，也不写回 M01-08。

4. **为什么 `is_selected` 与 `draft_status` 两个状态位并存？**
   它们回答不同问题：`is_selected` 是「临时勾选」（顾客说先不要镜盒，销售员取消勾选但保留行，方便再聊回）；`draft_status` 是「行的生命周期」。两者正交：可以 `ACTIVE + 未勾选`（暂不买），也可以 `REMOVED + 未勾选`（明确删除）。报价与转单只取 `draft_status = 'ACTIVE' AND is_selected = TRUE`。

5. **为什么删除用 `draft_status = 'REMOVED'` 而不删行？**
   选配过程是动态的：顾客试了 5 副镜架最后选了第 3 副。**「试过哪些、最后为什么没选」是极高价值的商品推荐训练数据与店长复盘数据**。物理删除会让这类信息彻底丢失。因此所有行保留，让 P08 消费分析能量化「试戴转化率 = 成交行 / 出现过的行」。

6. **为什么 `quantity` 对镜片默认 2？**
   一副眼镜两片镜片。若只配单片（如单眼术后、单眼遮盖），销售员手工改 1 并填 `eye_side`。默认值 2 符合 90% 以上场景，减少录入。

### 4.8 表：`m10_customer_log`（顾客操作审计日志表）

**用途：** 记录顾客档案生命周期上**所有关键变更**与**选配会话关键动作**的审计日志：建档、修改、手机号变更、身份证变更、`patient_id` 回填、合并、标签打标/收回、会话换人接待、报价试算、会话成交/放弃。本表是**只追加（append-only）**表，任何情况下不允许 UPDATE 业务内容、不允许物理 DELETE。

**为什么必须有这张表：**
- **合规**：顾客手机号、身份证属于《个人信息保护法》敏感个人信息，**变更必须留痕**（谁在什么时候把手机号从 A 改成 B）。
- **争议举证**：顾客投诉「你们把我的信息和别人搞混了」，需要用日志证明 `patient_id` 回填的时点与操作人。
- **合并追溯**：档案合并后源记录被打标 `MERGED`，只有日志能还原「合并前长什么样、合并到哪、谁操作的」。

写入方：M10-05 全子模块（服务层统一拦截）；只读方：P02 顾客详情「变更历史」页签、审计导出。

| 项目 | 数值 | 说明 |
|---|---|---|
| 年新增 | 480,000 行 | 日均 1,300 条操作日志 |
| 月分区大小 | 约 40,000 行 / 约 48 MB | 含索引约 76 MB |
| 保留 36 个月 | 1,440,000 行 / 约 1.7 GB | 含索引约 2.7 GB |
| 单分区查询 | 索引扫描 < 5ms | 「按顾客查最近变更」只命中近月分区 |

**设计要点：**

1. **为什么分区键选 `created_at` 而不选 `customer_id`？**
   日志的访问模式是**时间窗口内的合规核查**（「查一下 10 月所有手机号变更记录」），不是「查某个顾客的全部历史」。按时间分区后，这类查询只扫 1 个分区；同时老分区可以整块 `DETACH` 归档，不影响在线表。

2. **为什么分区表主键必须是 `(id, created_at)`？**
   PostgreSQL 分区表要求主键包含全部分区键列，否则无法保证全局唯一。这不是设计妥协，而是分区表的硬约束。`log_no` 唯一索引同理需带 `created_at`。

3. **为什么 `customer_name_mask` 用掩码而不用明文？**
   日志表的读取权限比主表宽（合规/审计角色需要读日志）。若日志存明文姓名，等于把顾客姓名泄露给了本不该看的人。掩码（保留首字与末字）既能定位「是哪条记录」，又满足隐私最小化原则。需要明文时按 `customer_no` 回主表取，并记录 `VIEW_SENSITIVE`。

4. **为什么 `PHONE_CHANGE` / `IDCARD_CHANGE` 强制 `is_sensitive = TRUE`？**
   手机号与身份证是《个人信息保护法》第 28 条列举的敏感个人信息。用 CHECK 约束在数据库层面强制，任何绕过服务层直接 INSERT 的脚本也无法标记为「非敏感」，避免合规漏洞。

5. **为什么日志里也记 `FAILED` / `REJECTED`？**
   成功的变更记录价值有限，**失败的尝试才是安全审计的重点**（「有人反复尝试把 A 的档案合并到 B」）。记录失败与错误码后，可做「高频失败操作」告警（见第 11 章监控指标 `customer_log_failed_rate`）。

        """球镜/柱镜必须为 0.25 的整数倍。"""
        if v is None:
            return v

            raise ValueError("球镜/柱镜必须为 0.25 的整数倍")
