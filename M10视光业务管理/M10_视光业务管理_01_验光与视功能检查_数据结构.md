**设计说明：**

1. **`m10_optometry` 是本子模块唯一的主表，一次验光一条记录。** `optometry_no` 是全局唯一业务单号（`YG` + `YYYYMMDD` + 4 位），被 M10-02 配镜处方、M10-05 选配工作台、M10-09 视力档案、M16-04 视光销售单以字段形式引用，同时是本子模块 4 个对外契约（P-01~P-04）的主键。**它承载的是「人在某一时刻的眼睛状态」，不是「卖了什么货」**，所以与 M16-04 的销售单严格分离。

2. **`m10_optometry_refraction` 是屈光数据的唯一权威表，按「眼别 × 阶段 × 验光方式」一条记录。** 不做「一行一字段 OD/OS 各存一遍」的设计，原因见 4.3 设计要点 1：散瞳验光需要同时保留散瞳前与散瞳后两套数据，横向加列会立刻变成 4 套（散瞳前 OD/OS + 散瞳后 OD/OS），再加过矫、试戴接受变成 10 套，字段数爆炸且索引失效。

3. **视力与瞳距独立成表（`m10_optometry_vision`）而非塞进屈光明细。** 视力（裸眼/矫正/近视力）、瞳距（远/近、单/双眼）、瞳高、眼压、主导眼这些是**基础检查项**，它们与屈光度不是一对一关系——散瞳前、散瞳后各有一组矫正视力，但瞳距只在最终试戴时存在；一台电脑验光仪不测瞳距。分开建表让「哪些字段必填」由 `check_kind` 决定，校验规则清晰。

4. **视功能检查独立成表（`m10_optometry_visual_func`）且按「眼别 × 检查项」竖表存储。** 视功能有 12 类以上检查项（Worth 4 点、立体视、融合范围 BO/BI、调节幅度、调节灵敏度、AC/A、远隐斜、近隐斜、色觉、注视性质、对比敏感度、瞳孔），每项字段完全不同。竖表用 `item_code + value_num/value_text/value_json` 表达，新增检查项不需要改表结构，这正是视光设备迭代快、检查项目逐年增加的现实要求。

5. **不建物理外键。** 与 M05-01 同一策略：①`patient_id` 指向 M03、`optometrist_id` 指向 M01-02，跨 schema 外键不可用 ②`m10_optometry_refraction` 写入频率高（一次验光 4~10 条），外键检查拖慢批量写入 ③`regen_from_id` 是自关联（作废重开），自引用外键会导致删除困难。一致性由应用层校验 + 每日 03:20 的对账任务 `reconcile_optometry_refs` 保证。

6. **`m10_optometry_log` 是只增表**，触发器禁止 UPDATE/DELETE，按 `created_at` 月度 RANGE 分区，保留 36 个月。签字、盖章、作废三类动作必须留痕，这是医疗文书合规底线。

7. **`m10_optometry_stat` 是预聚合统计表**，按「日期 × 验光师 × 验光类型」汇总工作量与质量指标。验光工作量考核（每人每日验光单数、平均耗时、作废率、复验率）是视光中心月度绩效的输入，实时从明细聚合要扫 10 万行以上，预聚合后单次查询 < 5ms。

8. **`m10_optometry_device_sync` 记录设备对接的原始报文与解析结果**。自动验光仪/综合验光仪/角膜地形图通过 M21 或文件导入，无法直连时手工录入。无论哪种方式，**原始报文必须留存**，因为：①出现录入歧义时（如设备导出 `-4.25 / -0.75 x 180` 的轴位解析争议）可回溯 ②设备通信故障排查 ③不良反应/纠纷时证明数据来源。

**设计要点：**

1. **为什么需要 `DRAFT` 状态且草稿无单号？**
   验光是一次「边测边录」的过程：电脑验光数据要录入、检影要看、综合验光仪要调、试戴要改。中途患者去缴费、接电话、接孩子，都可能中断 1~30 分钟。若每按一次保存就生成单号，一天 60 人次验光会产生大量废号，且号码被无意义的中间态占用。草稿不占号段（`optometry_no IS NULL`），提交签发时才取号，一次性生成。代价是草稿需要过期清理（`DRAFT_EXPIRE_HOURS` = 48 小时），由定时任务处理。

2. **为什么 `status` 只有 4 个值，不像 M05 住院单那样有 13 个？**
   验光的业务链路极短：录入 → 签发 → （可能）作废。没有「审核」「结算」「出院」这类中间态。**刻意保持状态少，是因为验光单的核心价值是「不可变的检查快照」**，状态越多，越容易出现「某个中间态下数据不完整、但被下游读到」的风险。P-01 只对 `SIGNED`/`ARCHIVED` 返回数据，`DRAFT` 一律返回 `"1001002"`。

3. **为什么 `is_cycloplegic` 与 `cycloplegic_agent` 拆成两个字段，不合成一个枚举？**
   因为「是否散瞳」是**检索维度**（统计散瞳率、核查儿童首诊合规），「用哪种药」是**临床细节**（阿托品慢散需 3 天、环喷托酯快散需 30 分钟，影响复诊安排）。合成一个字段后，`is_cycloplegic = TRUE` 的查询会退化为 `IN ('ATROPINE','CYCLOPENTOLATE',...)` 的枚举列表匹配，新增药物时全库代码都要改。拆开后，统计查询恒为 `is_cycloplegic = TRUE`，且这是部分索引的可索引条件。

4. **为什么 `cycloplegic_drops` 与 `cycloplegic_effect_at` 必须记录？**
   环喷托酯 1% 需滴 2~3 次、间隔 5 分钟，末次滴药后 30~45 分钟才达最大麻痹；阿托品 1% 需连续 3 天每日 2 次（共 6 次）。**若验光在药物未充分起效时进行，散瞳验光结果会显著偏向近视（残余调节）**，这是儿童验光最常见的质量事故。记录滴药次数与起效时间，让质量核查可以反查「哪些散瞳验光的起效时间不足 30 分钟」。

5. **为什么 `patient_id` 允许为空，改用 `customer_id` 补充？**
   视光中心存在大量「无就诊记录的到店顾客」（配老花镜、买太阳镜顺带验光）。若强制 `patient_id`，前台就得为每个买镜顾客建患者主索引，M03 会被大量无意义的患者记录污染，且这些记录永远不会有门诊/住院业务。共享规范第 17 章坑 10 明确要求「`customer_id` 可独立存在」。约束 `ck_m10_optometry_subject` 保证两者至少有一个，杜绝「无主的验光单」。

6. **为什么签发必须有 `e_signature_hash`？**
   验光单是要给患者、给配镜处、给厂家看的医疗文书。电子签名后若有人直接改数据库（绕过应用），签名就失去意义。`e_signature_hash` 是**对主表关键字段 + 全部屈光明细 + 全部视功能明细**序列化后的摘要值，任何一处被改，验签即失败。这是「签发后不可修改」的技术兜底，与业务层的状态校验双保险。

7. **为什么 `anisometropia` / `is_amblyopia_suspect` / `is_progression_alert` 要落库而不是实时算？**
   这三个值都要跨「本单」与「历史单」对比（进展量要和上一次比），且被 M10-09 视力档案与召回任务批量消费。若实时算，M10-09 查 1,000 个患者的预警清单就要 1,000 次跨单比对。落库后配部分索引（`idx_m10_optometry_progression`、`idx_m10_optometry_amblyopia`），预警清单查询从秒级降到毫秒级。代价是「历史单作废后需重算后续单的进展量」，由作废接口同步触发重算（见详细设计 8.3）。

8. **为什么 `optometry_type` 与 `optometry_purpose` 分成两个维度？**
   `optometry_type` 回答「用什么方法测的」（电脑/主觉/检影/综合验光仪/散瞳），`optometry_purpose` 回答「为什么测」（配镜/OK镜基线/隐形/术前/筛查/复查）。一次 OK 镜基线验光通常是 `PHOROPTER` + `ORTHO_K`，一次近视筛查通常是 `COMPUTER` + `SCREEN`。合成一个字段会有 5×6 = 30 种组合，枚举失控。分开后统计口径清晰：按方式统计设备使用率，按目的统计业务构成。

9. **为什么 `idx_m10_optometry_latest` 用部分索引且按 `signed_at` 排序？**
   这是 P-02（`by-patient/{patient_id}/latest`）的主干查询，M07 医生工作站每次打开患者详情都会调，M11 屈光手术、M16-04 开单也会调。全表 15 年约 90 万行，其中 `status = 'SIGNED'` 占 92%（约 83 万行）、`DRAFT` 与 `VOID` 只占 8%。部分索引排除了 8% 的无效行，更重要的是**让索引只服务一个明确的查询形状**（患者 + 倒序取 1），避免与其他查询争抢。实测下来单次查询从「索引扫描 1.8ms」降到 < 0.2ms。

10. **为什么不分区？**
    年验光量约 60,000 条（日均 170 人次，二级眼科医院视光中心典型量），15 年 90 万行，单行约 1.2KB（`prescription_suggestion_json` 与 `device_codes` 占大头），表大小约 1.1GB，6 个常用索引合计约 700MB。PostgreSQL 16 单表在 1 亿行以内都不需要分区，90 万行完全在舒适区间。且 `uk_m10_optometry_no` 若分区必须含分区键，会破坏跨年单号唯一性——这一点与 M05-01 的 `m05_admission` 处理方式一致。

**设计要点：**

1. **为什么用竖表（眼别 × 阶段 × 方式）而不是「一行一单，OD/OS 各一组字段」？**
   横表方案中一张单的字段是 `sph_od / cyl_od / axis_od / sph_os / cyl_os / axis_os`（6 个）。但散瞳验光需要同时保留散瞳前后两套 → 12 个。再加上过矫（`OVER_REF`）与试戴接受（`ACCEPTED`）→ 24 个。再加棱镜（水平/垂直/基底 × 2 眼 × 4 套）→ 48 个。**字段数按「阶段数 × 眼别 × 属性」三倍增长，每新增一个阶段就要加 12 列**，且大量列在特定场景为 NULL，索引与统计全部退化。竖表方案固定 12 个核心字段，新增阶段只是多几行，代价可控。

2. **为什么 `refraction_stage` 只有 4 个值而不是 8 个？**
   因为「散瞳前/散瞳后」不是阶段，而是一个**布尔维度** `is_cycloplegic_stage`。若把 `CYCLO_BEFORE_FINAL` / `CYCLO_AFTER_FINAL` 做成独立阶段值，那么「散瞳前过矫」「散瞳前试戴」又要各拆一个，阶段数从 4 增殖到 8~12。用「阶段 × 是否散瞳后」两个维度表达，组合数 = 4×2 = 8，语义清晰且枚举稳定。**这是把「正交维度」拆开而不是拍平到枚举的典型处理**。

3. **为什么 `cylinder_form` 需要区分正负柱镜？**
   国产电脑验光仪（如某些型号）输出正柱镜 `+0.75 × 90`，而综合验光仪与国标配镜处方用负柱镜 `-0.75 × 180`。两者是**同一光学状态的不同表达**（转换规则：CYL 变号、AXIS ±90°）。若统一强制负柱镜再落库，设备原始数据就丢失了，无法与设备导出文件核对。保留 `cylinder_form`，服务层在写入 FINAL 阶段时统一转换为负柱镜（`ck_m10_optometry_ref_cyl_range` 对 `PLUS` 放行），但 RAW 阶段原样保留。

4. **为什么 `axis` 的 CHECK 这么严格（柱镜=0 必须 NULL，柱镜≠0 必须 1~180）？**
   这是共享规范指定的错误码 `"1001004"`（柱镜为 0 时不可填写轴位）在数据库层的兜底。业务上，柱镜为 0 却填了轴位是设备解析错误的典型症状（例如把 `-0.00/-0.75 x 180` 解析成 `-0.75/0 x 180`）；柱镜不为 0 却漏填轴位则会让配镜厂直接退单（无法加工）。数据库约束让这类错误在写入时立刻暴露，而不是等到 M10-02 开方才发现。

5. **为什么 `stage_seq` 与 `remark` 组合约束？**
   检影验光经常要「反复测量 3 次取可重复值」；试戴也可能因患者不适而换一组度数再试。允许同阶段多条记录，但要求 `stage_seq` 唯一且 `stage_seq > 1` 时必须写备注说明原因。这样质量检查可以回答「谁的验光平均要测 4 次」——反复测量是操作不熟练的信号，也是考核指标。

6. **为什么 `double_check_by` 出现在屈光明细表而不是主表？**
   「手工录入需双人核对」的粒度是**每一行数据**，不是整张单。一张单上，电脑验光的 OD 是设备直连导入（无需核对），检影的 OS 是手工录入（需核对）。若放主表只能表达「整单核对过」，无法定位到具体哪一行。放明细表后，`idx_m10_optometry_refraction_doublecheck` 可以精确列出「所有手工录入但未核对的行」，这是儿童验光质量管控的核心手段。

7. **为什么 `compare_to_previous` 只比较球镜而不比较等效球镜？**
   因为「度数跳动」的现场判断依赖球镜本身：患者上一副是 −3.00D，这次是 −4.50D，患者第一反应是「怎么一下涨了 1.5 度」——即使等效球镜只变了 0.75D。现场要解释的是球镜的变化，所以存球镜差。等效球镜的年进展量在 `m10_optometry.progression_delta` 中单独存。

8. **为什么本表没有分区也没有 `version` 乐观锁？**
   明细行是「整单提交」的从属数据，不与主表并发修改——并发控制在主表 `m10_optometry.version` 上做（编辑锁 `m10:lock:optometry:{id}` 串行化），明细行无需独立乐观锁。分区层面，15 年约 720 万行（每单平均 7.7 行），单行约 180 字节，合计约 1.3GB，仍是单表舒适区间；且查询模式几乎全部带 `optometry_id`（唯一索引前缀），分区收益为零。

COMMENT ON COLUMN m10_optometry_vision.dominant_eye IS '主导眼 OD/OS：近视防控与 OK 镜验配的参考依据';

**设计要点：**

1. **为什么视力与瞳距放同一张表，而不用两张表？**
   它们共享完全相同的粒度（验光单 × 眼别）与生命周期（同一次验光录入、同一次签发锁定、同一次作废），且都是**高频读取的基础项**（P-01 每次都要返回裸眼视力与瞳距）。分成两张表后，P-01 要联 2 次、M10-09 取视力要联 1 次、M10-02 取瞳距要联 1 次，收益为零而成本翻倍。用 `check_kind` 区分，同表不同行，约束用 CHECK 表达差异（如 `ck_m10_optometry_vision_pd_required`）。

2. **为什么 `check_kind` 与 `va_with` 是两个维度？**
   `check_kind = 'VA_CORRECTED'`（矫正视力）+ `va_with = 'TRIAL'`（试片矫正）与 `check_kind = 'VA_UNCORRECTED'`（裸眼）+ `va_with = 'UNCORRECTED'` 是同一张视力表上的不同测量条件。把 `va_with` 拍平进 `check_kind` 会得到 `VA_CORRECTED_TRIAL`、`VA_CORRECTED_GLASSES`、`VA_CORRECTED_CONTACT`… 枚举爆炸。拆开后唯一索引 `(optometry_id, eye_side, check_kind, va_with)` 精确表达「同一次测量的同一条件只有一条」。

3. **为什么 `pd_binocular` 要求等于左右单眼之和（容差 0.5mm）？**
   这是**录入错误的兜底**。实际工作中，验光师可能从瞳距仪读双眼值 63.0，又手填单眼 32.0 / 32.0，而验光仪给出的是 31.50 / 31.50。允许 ±0.5mm 容差覆盖仪器舍入。若误差超限，说明数据来源不一致（一半来自仪器、一半手填），必须人工确认。加工阶段 M10-07 会用这个值做光学中心定位，1mm 误差会导致患者出现棱镜效应。

4. **为什么角膜曲率要区分 `k_unit`（D / MM）？**
   综合验光仪与电脑验光仪输出 D（如 43.25 / 44.00），角膜地形图输出 mm（如 7.80 / 7.67），两者互为倒数关系（`D = 337.5 / mm`）。OK 镜验配的 BC 选片用 mm，屈光手术筛查用 D。若统一强制换算成 D，mm 侧的精度会丢失（7.80mm ↔ 43.27D，反算回 7.7997mm，用于选片时 0.01mm 差异会影响贴合）。保留原单位在数据结构层，换算在服务层做。

5. **为什么 `iop_mmhg` 放在验光单里？**
   严格说眼压属 M12 检查管理的检查项目。但验光室通常配有非接触眼压计，验光师在散瞳前**必须测眼压**——因为散瞳会诱发闭角型青光眼急性发作（前房浅者禁忌）。`iop_mmhg` 在这里作为**散瞳安全性筛查的必备记录**，与 M12 的正式眼压检查报告是两回事（后者是收费检查、有报告号）。字段说明中已标注「参考值，非验光必需」，`is_abnormal` 为 TRUE 时提示转诊。

6. **为什么 `is_abnormal` 与 `abnormal_hint` 落库？**
   异常的判断需要年龄上下文（儿童视力 0.6 是正常，成人 0.6 是异常）与多个字段组合（角膜散光 > 2.00D 提示圆锥角膜可能）。落库后，医生工作站与验光复核页可以直接按 `idx_m10_optometry_vision_abnormal` 拉出所有异常项，无需重复实现判定规则。`abnormal_hint` 是给人看的解释文本，避免医生自己去猜「为什么标红」。

7. **为什么 `value_json` 存在？**
   眼科检查项在持续扩展：睑裂高度、角膜反光点位置、结膜充血程度、泪膜破裂时间（BUT）。这些项不是所有验光都做，字段结构也各不相同。`value_json` 作为兜底承载「暂未结构化」的项目，一年一次的评审中若某项使用率超过 20%，再提升为独立字段。这是**避免表结构被低频需求反复改动的工程妥协**。

**设计要点：**

1. **为什么视功能用竖表而屈光度用「半横」表？**
   视功能检查项之间**字段完全不通用**：立体视是一个数值（秒弧），Worth 4 点是一个分类结果，融合范围是 6 个数值的集合，色觉是「正常/色盲/色弱 + 具体类型」。强行横表化需要 12 类 × 平均 4 字段 = 48 列的稀疏表。屈光度则相反，所有阶段共享 `SPH/CYL/AXIS` 三个字段，横表的稀疏度低。**判断标准是「字段跨行共享度」：共享度高用横表，共享度低用竖表。**

2. **为什么需要 `value_normal` 冗余存储正常范围？**
   正常范围随年龄变化（调节幅度 8 岁约 14D、40 岁约 4.5D，用 Hofstetter 公式 `最小值 = 15 − 0.25 × 年龄` 计算），且判定规则会随临床指南更新。若只存判定结论 `is_abnormal`，三年后回看历史数据，无法知道「当时是按哪个标准判的」。存 `value_normal` 保留当时的判定基线，是**医疗数据可解释性**的要求。

3. **为什么 `is_reliable` 与 `retest_reason` 必须存在？**
   视功能检查比验光更依赖患者配合：Worth 4 点要看患者是否真的「看到 4 个点」，调节灵敏度要患者按指令翻转镜片并报清晰度。儿童配合欠佳时会产生**假的异常结果**（比如把「不理解指令」判成「抑制」）。标 `is_reliable = FALSE` 后，异常判定与统计都跳过该行，避免给医生错误信号，也避免给儿童贴上「功能障碍」的标签。

4. **为什么融合范围用 `value_json` 而不是拆 6 列？**
   融合范围（`FUSION_RANGE`）是三棱镜（BO 底朝外）与四棱镜（BI 底朝内）各测 3 个点：模糊点（blur）、破裂点（break）、恢复点（recovery）。6 个值只有这一个检查项用。拆成 6 列后，其余 12 个检查项这 6 列全是空。用 JSON 表达既保持语义完整（一个对象就是「一组融合范围」），又不污染表结构。约束 `ck_m10_optometry_vf_fusion_json` 保证它是对象，防止被误写成数组或标量。

5. **为什么 `test_condition` 与 `test_distance_cm` 分开？**
   `test_condition` 是**语义**（远/近），`test_distance_cm` 是**参数**（40cm 还是 33cm）。隐斜的远距标准是 5m 或 6m，近距标准是 40cm 或 33cm；不同医院、不同设备口径不同。查询时按语义过滤（`test_condition = 'NEAR'`），统计时按具体距离分组（看 33cm 与 40cm 的结果是否有系统性差异）。**语义与参数分离是数据可分析性的前提。**

6. **为什么异常要分三级（MILD/MODERATE/SEVERE）而不是布尔值？**
   视功能异常的临床意义差别很大：立体视 100 秒弧是轻度减退（正常 ≤60），400 秒弧是中度（影响精细操作），>800 秒弧或无立体视是重度（影响双眼视正常发育，需立即干预）。布尔值无法支撑「哪些需要紧急召回」的分级处理。三级配合 `abnormal_hint` 让人与机器都能快速分诊。

7. **为什么本表不存 `patient_name` 等患者快照？**
   视功能明细从不单独展示给患者，永远是「验光单详情」的一个区块，患者信息由主表带出。冗余患者快照会带来双写不一致的风险（主表改名、明细没改），而查询收益为零（永远带着 `optometry_id` 查）。

**设计要点：**

1. **为什么单独建日志表而不复用 M02-06 审计？**
   M02-06 是全院级审计，记录「谁在什么时间访问了哪个模块」，粒度是**接口级**；本表是**验光单级**的业务时间线，记录「这张单从生到死发生了什么」，且必须能被 P08 详情页以时间线形式完整展示、被质量核查按动作聚合。两者受众不同：审计给信息科与合规，日志给验光师主管与质控。事件双写（M02-06 与本表）是合规的常见做法。

2. **为什么 `signature_hash` 要在日志里再存一份？**
   主表上的 `e_signature_hash` 只保留「当前」摘要。若一张单签发后被作废、再重开，主表的摘要会被新单覆盖（新单是新行，但日志能串起来）。日志中每次签发、打印、作废都记当时的摘要，形成**不可篡改的摘要链**。患者拿着 2026-10-31 打印的纸质验光单来质疑「你们系统里不是这个度数」，用日志里的 `signature_hash` 与纸质单的条码内容比对即可定责。

3. **为什么记录 `PATIENT_VIEW`？**
   验光数据属于患者隐私（含屈光状态、可能存在全身病史）。患者端可查是便民功能，但**谁在什么时间看了谁的验光单**属于《个人信息保护法》要求的访问审计。`PATIENT_VIEW` 与 `PATIENT_VIEW_CLOSE`（关闭患者端可查）成对记录，支撑「患者撤回授权后不再展示」的合规要求。

4. **为什么 `action_result` 要有 `DENIED`？**
   越权尝试是安全事件的重要信号：某验光师尝试签发不属于自己的验光单、某账号尝试导出大批验光数据。记录 `DENIED` 后，`idx_m10_optometry_log_failure` 可以支撑「异常行为告警」（同一操作人 1 小时内 DENIED ≥5 次即告警，见详细设计 11.4）。

5. **为什么 `operator_id` 允许为 NULL / 0？**
   系统动作（P-04 检查完成通知自动建单、定时任务归档、草稿过期清理）没有自然人操作人。设 NOT NULL 会强制造假值（如统一填 1），反而破坏追溯。用 `operator_role = 'SYSTEM'` + `operator_id = 0` 表达，约束 `ck_m10_optometry_log_system` 保证系统动作不会挂着真实用户的 ID。

6. **为什么按 `created_at` 月度分区？**
   日志是纯追加、按时间范围查询的模式，天然适合分区。年日志量约 45 万条（每单平均 7.2 次动作），15 年 675 万条，单行约 400 字节，合计约 2.6GB。若不分区，`DELETE` 归档 3 年前数据会产生大量 dead tuple 并锁表；分区后直接 `DETACH PARTITION`，秒级完成。热查询（近 90 天）只落在 3 个分区，扫描量从 675 万行降到约 11 万行。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 每单日志条数 | 7.2 条（创建 1 + 修改 3 + 设备导入 1 + 签发 1 + 打印 1 + 查看 0.2） |
| 年日志量 | 446,400 条 |
| 15 年总量 | 6,696,000 行 |
| 单行平均长度 | 约 400 字节 |
| 表大小 | 约 2,540 MB |
| 索引大小 | 约 1,900 MB |
| 合计 | 约 4,440 MB |

**分区：** **按 `created_at` 月度 RANGE 分区**，预建 36 个月，热数据保留 90 天，总保留期 36 个月（超出部分 DETACH 后归档到冷存储）。

**设计要点：**

1. **为什么预聚合而不是实时算？**
   验光师绩效报表要查「本月每位验光师的签发数、平均耗时、作废率、儿童散瞳率」。实时从 `m10_optometry` + 三张明细表聚合，需扫 30 天约 5,100 行主表 + 4 万行明细，耗时 300~800ms；月份汇总排行要扫 6.2 万行主表 + 60 万行明细，耗时 3~8 秒。预聚合后单条查询 < 5ms，前端切换维度（今日/本周/本月/某验光师）体验流畅。

2. **为什么同时有 `ALL` 汇总行与按类型明细行？**
   报表有两种看数方式：「张三今天共验光 18 人」与「张三今天 12 台电脑验光 + 6 台综合验光仪」。若只存明细行，汇总要 GROUP BY；若只存汇总行，类型明细丢失。两类行都在同一张表里，用 `optometry_type = 'ALL'` 区分，查询时按需取。**冗余是有意识的**：存储成本约 2 倍，但查询永远单行或单组，无聚合开销。

3. **为什么要有 `calc_version`？**
   统计口径会变：2026 年「作废率」定义为「作废数 ÷ 总人次」，2027 年可能改为「作废数 ÷ 签发数」。口径一变，历史数据与当期数据不可直接比较。存口径版本号后，报表可以标注「2026 年数据按 v1 口径、2027 年按 v2 口径」，避免误导决策。

4. **为什么用 `COALESCE(dept_id, 0)` 表达式唯一索引？**
   `dept_id` 允许 NULL（跨院区的全科汇总行没有科室）。PostgreSQL 中 `NULL` 互不相等，普通唯一约束无法阻止「同一天同一验光师两行 dept_id 为 NULL 的 ALL 汇总」。`COALESCE(dept_id, 0)` 把 NULL 归一为 0（0 不是合法科室 ID），这是 PG 15 以下 `NULLS NOT DISTINCT` 的兼容写法，与 M05-01 `m05_admission_config` 的处理方式一致。

5. **为什么 `rx_created_count` 由 M10-02 回写？**
   验光转处方转化率是视光中心的核心经营指标（验光 62,000 人次，多少变成了配镜）。处方是 M10-02 的数据，本表通过 M10-02 的 `m10.prescription.issued` 事件回写计数。若自算，需要反向查 M10-02 表，违反「本子模块不直连他人表」的边界。

6. **为什么不分区？**
   一行一天一人一类型，62,000 人次/年 ÷ 平均 8 种类型组合 ≈ 年 22,000 行，15 年 33 万行，表大小约 60MB。分区收益为零。同时，统计表需要跨年对比（同比、环比），分区反而增加查询复杂度。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 验光师数 | 12 人（视光中心编制） |
| 每人每日行数 | ALL 汇总 1 + 类型明细平均 3 = 4 行 |
| 日行数 | 12 × 4 + 1（科室汇总）= 49 行 |
| 年行数 | 17,885 行 |
| 15 年总量 | 268,275 行 |
| 单行平均长度 | 约 320 字节 |
| 表大小 | 约 86 MB |
| 合计（含索引） | 约 130 MB |

**分区：** 不分区。

**设计要点：**

1. **为什么散瞳参数拆成 6 条而不是 1 个 JSON？**
   拆开后每条参数可独立授予不同角色修改权限（`is_editable`），也可以按科室覆盖。眼科（儿童患者多）与视光中心（成人多）的散瞳策略不同：眼科可能把强制散瞳年龄定到 12 岁，视光中心定到 6 岁。JSON 方案无法表达「科室级只覆盖其中 2 个字段」。拆表是**配置可治理性**的必然选择。

2. **为什么 `CYCLO_MANDATORY_AGE` 与 `CYCLO_REFUSE_REQUIRE` 设为 `is_editable = FALSE`？**
   这两条是**合规底线**，不是业务偏好。6 岁以下首诊必须散瞳、家长拒绝必须留痕，这是《儿童青少年近视防控适宜技术指南》与《综合防控儿童青少年近视实施方案》的明确要求。设为只读后，即使有配置权限的人也无法把它改成 0 或 false，避免事后追责时出现「系统允许不散瞳」的空子。真要调整，必须走代码发布流程，留痕在 Git 历史里。

3. **为什么 `param_code` 强制三段格式 `M10.OPTOMETRY.<参数名>`？**
   与 M05、M08、M14、M16 的配置表保持同一格式，便于全院的参数管理工具统一处理（导出、比对、审计）。三段格式也让「按分组检索」可以用 `param_code LIKE 'M10.OPTOMETRY.CYCLO%'` 精确命中，而不必依赖 `param_group` 字段是否填对。

**量级估算：** GLOBAL 15 条 + 每科室覆盖平均 3 条 × 4 个验光室 = 27 条，约 18 KB。永久保留，不分区。

**设计要点：**

1. **为什么原始报文与解析结果要分开存？**
   解析规则会演进：某品牌设备把轴位导出为 `0~180`，另一品牌用 `1~180`；把正柱镜导出为 `+0.75 x 90`。解析器升级后重新解析历史报文，是排查「某批数据看起来不对」的标准手段。若只存解析结果，原始依据就丢了。**原始报文是不可再生的一次性数据，必须有独立字段保存**（超过 64KB 时转对象存储，只存地址与摘要）。

2. **为什么需要 `raw_payload_hash` 唯一索引？**
   设备集成常见的重复推送场景：网络抖动导致设备重发、批量导入时文件被点两次、定时同步与实时推送重叠。同一报文重复入库会导致屈光明细出现重复行（虽然明细表有唯一索引兜底会报错，但用户会看到无意义的失败提示）。用「设备编码 + 报文摘要」做唯一约束，重复推送直接识别为幂等成功返回，体验干净。

3. **为什么 `is_manual_fallback` 与 `is_double_checked` 要记录在同步表？**
   设备不可用时的手工录入是**验光质量的最大风险点**：验光师照着一台旧设备的小票手敲，小数点错一位就是 −4.25 → −42.5 或者 −4.25 → −4.75。共享规范与本文档的全部设计都坚持「手工录入必须双人核对」。把核对状态记录在数据来源表，`idx_m10_optometry_device_manual` 就能直接列出「所有手工降级但未核对的记录」，这是质控每日必查清单。

4. **为什么 `deviation_flag` 由系统自动标记？**
   电脑验光仪的结果与检影/主觉结果差异超 2.00D 时，通常意味着：①设备未校准 ②患者配合差（眨眼、未看固视点）③设备故障。人工比对每张单的 3~4 组数据不现实，系统自动比对并标记，验光师复核时只看被标记的单，效率提升 10 倍以上。

5. **为什么不合并进 `m10_optometry_refraction`？**
   屈光明细表存的是「最终采用的度数」，本表存的是「设备说了什么、系统怎么理解的、有没有用上」。两者是一对多关系（一次验光可能有 3 台设备的数据），且本表还要存解析失败（此时没有屈光数据可用）。合并会导致屈光明细表出现大量 `parse_status = 'FAILED'` 的空行，破坏「明细即有效数据」的语义。

| 年记录数 | 210,800 条 |

    @property
    def power_text(self) -> str:
        """度数文本，如 -4.25DS / -4.25DC×180（处方书写格式）。"""
        sph = "%+.2f" % float(self.sphere)
        if self.cylinder == 0:
            return "%sDS" % sph
        cyl = "%+.2f" % float(self.cylinder)
        return "%sDS %sDC×%d" % (sph, cyl, self.axis or 0)

def _check_quarter(value: Optional[Decimal], field_name: str) -> Optional[Decimal]:
    """校验 0.25 步进。"""
    if value is None:
        return value
    if (Decimal(str(value)) * 4) != (Decimal(str(value)) * 4).to_integral_value():
        raise ValueError("%s 必须为 0.25 的整数倍" % field_name)
    return value

### E.3 分区建表脚本（`m10_optometry_log`）

```sql
-- 主表按 created_at 月度 RANGE 分区
CREATE TABLE m10_optometry_log (
    id               BIGINT GENERATED BY DEFAULT AS IDENTITY,
    optometry_id     BIGINT NOT NULL,
    optometry_no     VARCHAR(32),
    patient_id       BIGINT,
    action           VARCHAR(32) NOT NULL,
    action_result    VARCHAR(16) NOT NULL DEFAULT 'SUCCESS',
    target_table     VARCHAR(64),
    target_id        BIGINT,
    changed_fields   JSONB,
    old_value        JSONB,
    new_value        JSONB,
    detail_json      JSONB,
    signature_hash   VARCHAR(128),
    operator_id      BIGINT,
    operator_name    VARCHAR(64),
    operator_role    VARCHAR(32),
    operator_ip      VARCHAR(64),
    operator_device  VARCHAR(128),
    trace_id         VARCHAR(64),
    request_id       VARCHAR(64),
    remark           VARCHAR(512),
    created_at       TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- 预建 36 个月分区
DO $$
DECLARE
    i INT;
    start_date DATE;
    end_date DATE;
    part_name TEXT;
BEGIN
    FOR i IN 0..35 LOOP
        start_date := (DATE_TRUNC('month', CURRENT_DATE) + (i || ' months')::INTERVAL)::DATE;
        end_date := (start_date + INTERVAL '1 month')::DATE;
        part_name := 'm10_optometry_log_p' || TO_CHAR(start_date, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m10_optometry_log '
            'FOR VALUES FROM (%L) TO (%L)',
            part_name, start_date, end_date
        );
    END LOOP;
END $$;

-- 分区表上的索引（每分区独立建，PG 会自动传播）
CREATE INDEX IF NOT EXISTS idx_m10_optometry_log_biz
    ON m10_optometry_log (optometry_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_m10_optometry_log_action
    ON m10_optometry_log (action, created_at DESC);
```

**为什么主键是 `(id, created_at)` 而不是 `(id)`：**
PostgreSQL 要求分区表的主键必须包含分区键，所以主键改为 `(id, created_at)`。业务查日志用 `optometry_id + created_at`，不依赖主键，因此无影响。这一点与 M05-01 的 `m05_admission_log` 处理一致。
