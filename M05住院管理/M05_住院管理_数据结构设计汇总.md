### 1.2 标准字段

每张常规表均含以下 6 个标准字段（日志/台账表除外）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `created_by` | `BIGINT` | 创建人；`0` 表示系统自动 |
| `created_at` | `TIMESTAMP` | 创建时间，默认 `CURRENT_TIMESTAMP` |
| `updated_by` | `BIGINT` | 更新人 |
| `updated_at` | `TIMESTAMP` | 更新时间，由触发器维护 |
| `is_deleted` | `BOOLEAN` | 逻辑删除，默认 `FALSE` |
| `version` | `INT` | 乐观锁版本号，默认 `0`（并发写敏感的表才有） |

**例外：**

| 表 | 缺哪些字段 | 理由 |
|---|---|---|
| `m05_admission_log` / `m05_bed_status_log` / `m05_stay_log` / `m05_charge_task_log` / `m05_archive_log` / `m05_home_log` | `updated_at` / `is_deleted` / `version` | 只增表，由触发器禁止 UPDATE/DELETE |
| `m05_admission` / `m05_bed` / `m05_stay` / `m05_discharge` / `m05_archive` / `m05_medical_record_home` | 无 `is_deleted` 例外，但**业务上不允许物理删除** | 病历是法定证据，删除会破坏可追溯性 |
| `m05_archive_seal` | `is_deleted` | 封存记录是法律证据，永不可删 |

**`created_by = 0` 约定的意义：** 定时任务、事件回调、系统补偿创建的记录统一写 `0`。报表可以直接用 `created_by = 0` 过滤出「系统自动产生的数据」，避免把系统行为算成人工工作量。

### 1.3 枚举字段用 VARCHAR + CHECK，不用 PG ENUM

**三条理由：**

1. **`ALTER TYPE ... ADD VALUE` 不能在事务块中执行。** Alembic 迁移本身跑在事务里，一旦需要新增枚举值就得写 `op.execute("COMMIT")` 提前提交，会破坏迁移的原子性。
2. **删除或修改枚举值必须重建类型。** 需要 `CREATE TYPE _new` → `ALTER TABLE ... TYPE _new USING ...` → `DROP TYPE old`，大表会锁表很久，且 `DROP TYPE` 在有依赖（如函数默认值）时会失败。
3. **应用层的校验已由 Pydantic 的 `Literal[...]` 完成。** 数据库端用 `CHECK` 兜底即可，不需要额外的类型系统。

### 1.4 时间语义（8 个核心时刻）

| 字段 | 语义 | 用途 |
|---|---|---|
| `admission_time` | 入院时刻 | 住院天数计算起点、统计口径 |
| `bed.occupied_at` | 占床时刻 | 床位使用率计算起点 |
| `bed.cleaning_started_at` / `cleaning_expected_end_at` | 消毒开始/预计结束 | 消毒超时扫描 |
| `stay.admitted_at` | 入科时刻 | 在院时长 |
| `discharge_time` | 出院时刻 | 住院天数计算终点 |
| `treatment_at` | 治疗/记费业务发生日 | 床日费用归属 |
| `settled_at` | 结算完成时刻 | 财务口径 |
| `archived_at` | 归档完成时刻 | 归档时效统计 |

**统一规则：**

- 所有时刻字段一律 `TIMESTAMP`（不带时区），由应用层统一按 `Asia/Shanghai` 解释；
- **分区键统一用 `created_at`**（而非业务时刻），因为业务时刻可回填，`created_at` 单调递增；
- 住院天数 `actual_stay_days` 由应用层按自然日切分计算后落库，不做生成列——因为出院当天是否计费是配置项。

### 1.5 软删除与部分唯一索引

**软删除的存在意义：** 病案是法定证据，住院主档、床位台账、在院记录、出院记录、归档记录**永不做物理删除**，只标记状态。

**软删除与唯一索引的冲突：** 若唯一索引不含 `is_deleted` 条件，则「已删除记录」会永久占用唯一值，导致同一业务编号无法重新使用。

**统一写法：**

```sql
-- 正确：部分唯一索引
CREATE UNIQUE INDEX uk_m05_admission_no
    ON m05_admission (admission_no)
    WHERE is_deleted = FALSE;

-- 错误：全表唯一
CREATE UNIQUE INDEX uk_m05_admission_no
    ON m05_admission (admission_no);
```

**可空列参与唯一索引时必须 `COALESCE`：**

```sql
CREATE UNIQUE INDEX uk_m05_charge_config_key
    ON m05_charge_config (param_code, COALESCE(ward_id, 0))
    WHERE is_deleted = FALSE;
```

原因为 PostgreSQL 唯一索引认为 `NULL` 互不相等，`(param_code, NULL)` 可以插入两次。`COALESCE(ward_id, 0)` 用 `0` 表达「全院级配置」，而 `0` 不是合法的病区 ID，无冲突风险。**不用 `NULLS NOT DISTINCT`** 是因为 PG 15+ 才支持，本项目部分环境仍是 PG 14。

### 1.6 不建数据库物理外键

**四条理由：**

1. **跨模块外键不可能建立。** `m05_admission.patient_id` 指向 M03 的 `mpi_patient`，两个模块可能分库或被拆分部署。
2. **高频写入表的外键检查开销明显。** `m05_admission` 创建时会同时插入多条附属记录，每条都要回查主表。
3. **「撤销归档 + 重新归档」这类操作会多次更新主表**，外键的 `ON DELETE` 语义在这里没有意义（我们从不物理删除）。
4. **建表顺序解耦。** 没有外键，任何表都可以先建，便于分阶段上线与回滚。

**一致性保障方式：** 应用层事务 + 每小时一致性守护任务（见总纲 §10.4）。

### 1.7 金额与数量精度

| 语义 | 类型 | 理由 |
|---|---|---|
| 单价（床位费日单价） | `NUMERIC(12,4)` | 与 M01-06 定价精度一致 |
| 金额（费用、预交金、结算） | `NUMERIC(12,2)` / `NUMERIC(14,2)` | 人民币最小单位是分 |
| 数量（床日数、次数） | `NUMERIC(12,4)` 或 `INTEGER` | 床日费数量恒为 1 |
| 比例（使用率、折扣率） | `NUMERIC(8,6)` | 保留 6 位小数，避免统计累计误差 |

**金额计算铁律：行级先舍入再汇总。**

```
错误：SUM(unit_price × qty) 后 ROUND
正确：SUM(ROUND(unit_price × qty, 2))
```

30 行明细按比例分摊时，先汇总再舍入会产生几分钱误差，导致「明细之和 ≠ 合计」，退费按行退永远对不上账。

### 1.8 中文模糊搜索用 pg_trgm + GIN

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_m05_admission_name_trgm
    ON m05_admission USING gin (patient_name gin_trgm_ops);
```

**不用 `tsvector` 的理由：** PostgreSQL 内置分词器对中文按单字切分，`'王小明'` 会被切成 `王/小/明` 三词，搜索「小明」能中、「王明」也能中——误召回率极高。使用中文分词需要安装 `zhparser` 或 `pg_jieba` 扩展，二级医院运维能力有限，不引入额外扩展。

**实测收益（11 万行）：** `LIKE '%晶体%'` 无索引 42ms → trgm 索引 1.8ms。

### 1.9 参数表统一结构

M05 有 7 张参数表（`m05_admission_config`、`m05_bed_config`、`m05_stay_config`、`m05_charge_config`、`m05_archive_config`、`m05_home_config`、`m05_stat_config`），统一采用：

```sql
CREATE UNIQUE INDEX uk_m05_<域>_config_key
    ON m05_<域>_config (param_code, COALESCE(<scope_col>, 0))
    WHERE is_deleted = FALSE;
```

| 子模块 | scope 列 | 支持的层级 |
|---|---|---|
| M05-01 | `scope` + `scope_id` | GLOBAL / DEPT |
| M05-02 | `ward_id` | 全院（NULL）/ 病区 |
| M05-03 | `ward_id` | 全院（NULL）/ 病区 |
| M05-04 | `ward_id` | 全院（NULL）/ 病区 |
| M05-05 | `scope` + `scope_id` | GLOBAL / DEPT |
| M05-06 | `scope` + `scope_id` | GLOBAL / DEPT |
| M05-07 | `scope` + `scope_id` | GLOBAL / DEPT |

**读取优先级：** 最具体层级 → 上级 → 代码默认值。参数统一缓存 Redis Hash `m05:<域>:config`，TTL 600 秒，修改后主动 `DEL`。

### 1.10 只增表的触发器保护

**6 张只增表**，均由触发器禁止 UPDATE / DELETE：

| 表 | 触发器函数 | 保留期 |
|---|---|---|
| `m05_admission_log` | `fn_m05_admission_log_readonly()` | 3 年 |
| `m05_bed_status_log` | `fn_m05_bed_status_log_readonly()` | 5 年 |
| `m05_stay_log` | `fn_m05_stay_log_readonly()` | 15 年 |
| `m05_charge_task_log` | `fn_m05_charge_task_log_readonly()` | 3 年 |
| `m05_archive_log` | `fn_m05_archive_log_readonly()` | 3 年 |
| `m05_home_log` | `fn_m05_home_log_readonly()` | 15 年 |

**触发器模板：**

```sql
CREATE OR REPLACE FUNCTION fn_m05_admission_log_readonly()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'm05_admission_log 为只增表，禁止 UPDATE/DELETE';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m05_admission_log_update
    BEFORE UPDATE ON m05_admission_log
    FOR EACH ROW EXECUTE FUNCTION fn_m05_admission_log_readonly();

CREATE TRIGGER trg_m05_admission_log_delete
    BEFORE DELETE ON m05_admission_log
    FOR EACH ROW EXECUTE FUNCTION fn_m05_admission_log_readonly();
```

**为什么用触发器而不是只靠应用层：** 应用层可能被 DBA 手工 SQL、数据修复脚本、ORM 的 `delete()` 绕过。审计日志一旦可被修改，就不再是证据。

### 5.2 分区表建表模板

```sql
CREATE TABLE m05_admission_log (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY,
    biz_type      VARCHAR(32)  NOT NULL,
    biz_id        BIGINT       NOT NULL,
    action        VARCHAR(32)  NOT NULL,
    operator_id   BIGINT       NOT NULL,
    operator_name VARCHAR(64),
    operator_ip   VARCHAR(64),
    detail_json   JSONB,
    old_value     TEXT,
    new_value     TEXT,
    remark        VARCHAR(512),
    trace_id      VARCHAR(64),
    created_at    TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

DO $$
DECLARE
    i INT;
    p_start DATE;
    p_end   DATE;
BEGIN
    FOR i IN 0..35 LOOP
        p_start := date_trunc('month', CURRENT_DATE)::date + (i || ' month')::interval;
        p_end   := p_start + INTERVAL '1 month';
        EXECUTE format(
            'CREATE TABLE IF NOT EXISTS m05_admission_log_%s PARTITION OF m05_admission_log FOR VALUES FROM (%L) TO (%L)',
            to_char(p_start, 'YYYYMM'), p_start, p_end
        );
    END LOOP;
END $$;
```

**复合主键 `(id, created_at)` 的必要性：** PostgreSQL 要求分区表的主键必须包含分区键。`id` 本身是全局唯一 IDENTITY，所以 `(id, created_at)` 不损失唯一性。

### 5.4 归档策略

**四步流程（以 `m05_admission_log` 为例）：**

```sql
    (LIKE m05_admission_log INCLUDING DEFAULTS INCLUDING CONSTRAINTS);

-- 第 2 步：搬数据
INSERT INTO archive.m05_admission_log_y2026
SELECT * FROM m05_admission_log
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';

-- 第 3 步：核对行数（必须完全一致才能继续）
-- SELECT (SELECT count(*) FROM archive.m05_admission_log_y2026) AS archived,
--        (SELECT count(*) FROM m05_admission_log
--         WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01') AS live;

DROP TABLE m05_admission_log_202601, m05_admission_log_202602, ..., m05_admission_log_202612;
```

**归档铁律：归档表行数与被删行数必须完全一致，才可删主表。** 这不是建议，是硬性检查——少搬一行就是丢了一份病案证据。

**归档周期表：**

| 表 | 保留期 | 归档时机 |
|---|---|---|
| `m05_admission_log` | 3 年 | 每年 1 月 |
| `m05_bed_status_log` | 5 年 | 每年 1 月 |
| `m05_stay_log` | 15 年 | 每 5 年 |
| `m05_charge_task_log` | 3 年 | 每年 1 月 |
| `m05_archive_log` | 3 年 | 每年 1 月 |
| `m05_home_log` | 15 年 | 每 5 年 |
| `m05_medical_record_home` | **30 年** | 不归档（法定保存期） |
| 其余业务表 | 15 年 | 每 5 年归档到历史库 |

**为什么病案首页保留 30 年而住院主档只保留 15 年：** 《医疗机构病历管理规定》要求住院病案保存不少于 30 年。M05 的住院主档是「索引信息」，完整病案（含文书内容）在 M18；但病案首页是 DRG/DIP 结算的法律依据，且医保稽核可追溯多年，因此本模块按 30 年保留。

| `m05_charge_task` | `amount` | `NUMERIC(12,2)` | 金额 = `ROUND(unit_price × quantity, 2)` | 2 位，行级先舍入 |
| `m05_charge_daily_stat` | `charge_amount` / `reversal_amount` / `net_amount` | `NUMERIC(14,2)` | 日汇总金额 | 2 位 |
| `m05_charge_daily_stat` | `success_rate` | `NUMERIC(8,6)` | 记账成功率 | 6 位 |
| `m05_charge_alert` | `accumulated_charge` / `available_balance` / `owed_amount` | `NUMERIC(14,2)` | 欠费三要素 | 2 位 |
| `m05_charge_alert` | `threshold_ratio` | `NUMERIC(8,6)` | 预警阈值比例 | 6 位 |
| `m05_discharge` | `total_amount` / `deposit_total` / `settle_amount` | `NUMERIC(14,2)` | 出院结算三要素 | 2 位 |
| `m05_discharge` | `stay_days` | `SMALLINT` | 住院天数 | 整数 |
| `m05_archive` | `document_count` / `present_count` / `missing_count` / `unknown_count` / `exempt_count` | `INTEGER` | 归档检查计数 | 整数，且五项关系自洽 |
| `m05_medical_record_home` | 费用合计类字段 | `NUMERIC(14,2)` | 与 M16 结算金额核对 | 2 位 |
| `m05_stat_daily` / `m05_ward_daily` | 使用率、周转次数、平均住院日 | `NUMERIC(8,6)` / `NUMERIC(8,2)` | 效率指标 | 见 M05-07 |

**金额字段三条铁律：**

1. **所有金额字段一律 `NUMERIC`，禁止 `FLOAT` / `REAL` / `DOUBLE`**——浮点二进制无法精确表示 0.1，累加会漂移。
2. **行级先舍入再汇总。** `SUM(ROUND(unit_price × quantity, 2))`，不是 `ROUND(SUM(unit_price × quantity), 2)`。
3. **单价 4 位、金额 2 位、比例 6 位。** 床日费虽然通常整数，但床日半价（当日出入院）会产生 0.5 元，需保留 4 位以免后续乘除丢精度。
