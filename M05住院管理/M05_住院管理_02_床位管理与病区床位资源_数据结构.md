**设计说明：**

1. **`m05_bed` 是核心表**，被 M05-02 全部接口与 M08 护理站、M05-04 床位费记账引用。`current_admission_id` 上必须有唯一索引，这是「一床只能一个在院患者」的数据库级保证。
2. **`m05_bed_status_log` 是只增台账，月度分区**。年写入约 46,000 条（47 床 × 3 次日均 × 365 天 / 1.1），保留 5 年约 23 万行。
3. **`m05_bed_reserve` 独立于 `m05_bed`**：虽然 `m05_bed` 上已有 `reserve_*` 字段（当前有效预留），但历史预留记录需要独立表——「这张床过去被预留过几次、每次预留多久、最后被谁用了」是床位效率分析的必要数据。
4. **`m05_bed_snapshot` 是每日床位状态快照**，用于 M05-07 的「期末占用床位数法」床位使用率口径，也用于趋势图。
5. **`m05_bed_type_snap` 是 M01-13 `md_bed_type` 的本地副本**，让床位列表能直接显示类型名称与日费用而不每次调 M01。
6. **不建外键**，理由见 4.2 设计要点第 7 条。

**约束说明：**

```sql
-- 床位状态枚举（6 态）
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_status
    CHECK (status IN ('EMPTY', 'RESERVED', 'OCCUPIED', 'CLEANING',
                      'MAINTENANCE', 'DISABLED'));

-- 性别限制枚举（NULL 等同 ANY）
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_gender_limit
    CHECK (gender_limit IS NULL OR gender_limit IN ('M', 'F', 'ANY'));

-- 预留类型枚举（NULL 表示无预留）
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_reserve_type
    CHECK (reserve_type IS NULL
           OR reserve_type IN ('PRE_ADMISSION', 'PRE_DISCHARGE'));

-- 占用状态必须同时有住院单、患者、占用时刻
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_occupied
    CHECK (status <> 'OCCUPIED'
           OR (current_admission_id IS NOT NULL
               AND current_patient_id IS NOT NULL
               AND occupied_at IS NOT NULL));

-- 非占用状态不能有当前患者信息
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_not_occupied
    CHECK (status = 'OCCUPIED'
           OR (current_admission_id IS NULL
               AND current_patient_id IS NULL
               AND current_patient_name IS NULL
               AND occupied_at IS NULL));

-- 预留状态必须同时有预留类型、对象、截止时刻
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_reserved
    CHECK (status <> 'RESERVED'
           OR (reserve_type IS NOT NULL
               AND reserve_patient_id IS NOT NULL
               AND reserve_until IS NOT NULL
               AND reserved_by IS NOT NULL));

-- 非预留状态不能有预留信息
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_not_reserved
    CHECK (status = 'RESERVED'
           OR (reserve_type IS NULL
               AND reserve_admission_id IS NULL
               AND reserve_patient_id IS NULL
               AND reserve_until IS NULL));

-- 消毒状态必须有消毒开始时刻
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_cleaning
    CHECK (status <> 'CLEANING'
           OR (cleaning_started_at IS NOT NULL
               AND cleaning_expected_end_at IS NOT NULL));

-- 非消毒/非维修状态不能有消毒进行中的时刻（保留 last_cleaned_at）
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_not_cleaning
    CHECK (status IN ('CLEANING', 'MAINTENANCE')
           OR (cleaning_started_at IS NULL
               AND cleaning_expected_end_at IS NULL));

-- 维修状态必须有维修原因
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_maintenance
    CHECK (status <> 'MAINTENANCE'
           OR (maintenance_started_at IS NOT NULL
               AND maintenance_reason IS NOT NULL
               AND char_length(btrim(maintenance_reason)) >= 10));

-- 停用状态必须有停用原因与停用人
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_disabled
    CHECK (status <> 'DISABLED'
           OR (disabled_reason IS NOT NULL
               AND char_length(btrim(disabled_reason)) >= 10
               AND disabled_at IS NOT NULL
               AND disabled_by IS NOT NULL));

-- 非停用状态不能有停用信息
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_not_disabled
    CHECK (status = 'DISABLED'
           OR (disabled_reason IS NULL AND disabled_at IS NULL
               AND disabled_by IS NULL));

-- 日费用不能为负
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_daily_fee
    CHECK (daily_fee >= 0);

-- 使用轮次不能为负
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_service_round
    CHECK (service_round >= 0);

-- 消毒预计结束必须晚于开始
ALTER TABLE m05_bed
    ADD CONSTRAINT ck_m05_bed_cleaning_time
    CHECK (cleaning_expected_end_at IS NULL
           OR cleaning_started_at IS NULL
           OR cleaning_expected_end_at > cleaning_started_at);

    ON m05_bed (current_admission_id)
```

**设计要点：**

1. **为什么患者姓名要快照（`current_patient_name`）？**
   床位看板一次显示 47 张床，若每张床都调 M03-01 取姓名，就是 47 次调用。快照后在 `m05_bed` 一张表里就能渲染完整看板。代价是患者改名不同步——但改名极低频，且看板是当值数据，可接受。

2. **为什么 `current_admission_id` 用唯一索引而不是普通外键？**
   这是「一床只能一个在院患者」的数据库级防线。若只有应用层校验，两个收费员并发分同一张床时，两边都读到 EMPTY、都通过校验、都 UPDATE——后者覆盖前者，最终床位只记一个患者，但两张住院单都显示「在院」，患者 B 会走到已经住着 A 的床边。

3. **为什么 `status` 与 `current_*` 字段要双向约束（`ck_m05_bed_occupied` + `ck_m05_bed_not_occupied`）？**
   单向约束只能保证「OCCUPIED 一定有患者」，不能保证「EMPTY 一定没患者」。若 EMPTY 状态残留 `current_admission_id`，唯一索引会让下一张住院单无法分到这张床，排查极其困难。

4. **为什么预留信息在 `m05_bed` 里冗余一份，同时还有 `m05_bed_reserve` 表？**
   - `m05_bed` 里的冗余字段（`reserve_type`/`reserve_admission_id`/`reserve_until` 等）用于「当前有效预留」，分床时需要 O(1) 判断「这张床预留给了谁」
   - `m05_bed_reserve` 存**历史**预留记录（每次预留新建一条），用于「这张床过去被预留过几次」的统计
   - 类比：`m05_bed` 的 `reserve_*` 是状态机的一部分，`m05_bed_reserve` 是审计台账

5. **为什么 `service_round` 是必需字段？**
   日间病区单床一天可能服务 3~4 个患者，中间不做完整消毒有院感风险。`service_round` 累计使用次数，配合参数 `M05.BED.DAY_SERVICE_MAX = 4`，达到上限时强制要求完整消毒流程。

6. **为什么 `version` 乐观锁？**
   床位状态变更可能被多个端并发触发（护士站改消毒完成、住院处分床、定时任务自动释放）。但真正防并发靠的是 `SELECT ... FOR UPDATE`（行锁），`version` 是补充——用于检测「读到的数据是否已被改过」，避免「护士看到 CLEANING 点完成，实际上此时已是 EMPTY」的误操作。

7. **为什么不建外键？**
   - `ward_id` → `md_ward` 在 M01（可能跨 schema），外键不可用
   - `bed_type_code` → `md_bed_type` 同上
   - `current_admission_id` → `m05_admission` 在同模块，但 `m05_bed` 是高写入表（状态变更频繁），外键检查会增加开销
   - 建表顺序会耦合：`m05_bed` 要在 `m05_admission` 之后建，而 `m05_admission` 分床时又要引用 `m05_bed.bed_id`（逻辑引用，不建外键就没问题）
   - **一致性由应用层事务 + 每日 03:00 对账任务保证**

8. **为什么床位表不分区？**
   全院 47 张床（含加床约 50），永远不会超过几百行。分区只会增加管理复杂度。

**量级估算：**

| 项目 | 数值 | 说明 |
|---|---|---|
| 小计行数 | 47 行 | 眼科一病区 23 + 眼科二病区 20 + 日间手术中心 6 + 门诊治疗区（不计入住院） |
| 加床 | 0~3 行 | 极少使用 |
| 15 年累计（含新增/停用） | 约 120 行 | 床位只增不减（停用不删） |

| 表大小 | 约 100 KB | — |
| 索引大小 | 约 200 KB | 10 个索引 |
| 合计 | 约 300 KB | — |

**分区：** 不分区。理由：行数太少（< 300 行），分区无收益。

```sql
-- 状态枚举（与 m05_bed 一致）
ALTER TABLE m05_bed_status_log
    ADD CONSTRAINT ck_m05_bed_log_status
    CHECK (from_status IS NULL
           OR from_status IN ('EMPTY', 'RESERVED', 'OCCUPIED', 'CLEANING',
                              'MAINTENANCE', 'DISABLED'));

ALTER TABLE m05_bed_status_log
    ADD CONSTRAINT ck_m05_bed_log_to_status
    CHECK (to_status IN ('EMPTY', 'RESERVED', 'OCCUPIED', 'CLEANING',
                         'MAINTENANCE', 'DISABLED'));

-- 前后状态不能相同（无变化不记日志）
ALTER TABLE m05_bed_status_log
    ADD CONSTRAINT ck_m05_bed_log_changed
    CHECK (from_status IS NULL OR from_status <> to_status);

-- 变更原因枚举
ALTER TABLE m05_bed_status_log
    ADD CONSTRAINT ck_m05_bed_log_reason
    CHECK (change_reason IN ('CREATE', 'ASSIGN', 'BED_CHANGE_OUT', 'BED_CHANGE_IN',
                             'DISCHARGE', 'CLEAN_COMPLETE', 'AUTO_CLEAN_TIMEOUT',
                             'MAINTENANCE_START', 'MAINTENANCE_COMPLETE',
                             'DISABLE', 'ENABLE', 'RESERVE', 'RELEASE_RESERVE',
                             'RESERVE_TIMEOUT', 'ADMISSION_CANCELLED',
                             'ADMISSION_TRANSFERRED', 'ADMISSION_DECEASED'));

-- 转入 OCCUPIED 必须有住院单与患者
ALTER TABLE m05_bed_status_log
    ADD CONSTRAINT ck_m05_bed_log_occupied
    CHECK (to_status <> 'OCCUPIED'
           OR (admission_id IS NOT NULL AND patient_id IS NOT NULL));

-- 持续时长不能为负
ALTER TABLE m05_bed_status_log
    ADD CONSTRAINT ck_m05_bed_log_duration
    CHECK (duration_seconds IS NULL OR duration_seconds >= 0);

-- 系统操作 changed_by = 0
ALTER TABLE m05_bed_status_log
    ADD CONSTRAINT ck_m05_bed_log_operator
    CHECK (changed_by = 0 OR changed_by > 0);

-- 只增触发器：禁止 UPDATE / DELETE
CREATE OR REPLACE FUNCTION fn_m05_bed_log_readonly()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'm05_bed_status_log 为只增表，禁止 %', TG_OP;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m05_bed_log_update
    BEFORE UPDATE ON m05_bed_status_log
    FOR EACH ROW EXECUTE FUNCTION fn_m05_bed_log_readonly();

CREATE TRIGGER trg_m05_bed_log_delete
    BEFORE DELETE ON m05_bed_status_log
    FOR EACH ROW EXECUTE FUNCTION fn_m05_bed_log_readonly();

COMMENT ON TABLE m05_bed_status_log IS '床位状态变更台账（只增，禁止 UPDATE/DELETE），月度分区';
COMMENT ON COLUMN m05_bed_status_log.duration_seconds IS '变更前状态持续秒数，占用时长统计的唯一数据来源';
COMMENT ON COLUMN m05_bed_status_log.change_reason IS '变更原因代码，AUTO_CLEAN_TIMEOUT/RESERVE_TIMEOUT 为系统自动触发';
COMMENT ON COLUMN m05_bed_status_log.changed_by IS '操作人 ID，0 表示系统自动（定时任务）';
```

**设计要点：**

1. **为什么必须记录 `duration_seconds`？**
   床位使用率的四种口径都需要「占用时长」。若不入库，统计时要按时间顺序配对 from/to（窗口函数 LEAD），既慢又容易错。写入时一次算好，统计时 SUM 即可。

2. **为什么带宽 `ward_name` / `patient_name` 快照？**
   病区改名、患者改名后，历史记录不能跟着变——那是台账，要反映「当时」的事实。同时避免统计时 JOIN。

3. **为什么 `from_status` 允许为 NULL？**
   新建床位时是「无 → EMPTY」，没有前置状态。

4. **为什么用月度分区？**
   - 数据只追加，天然适合分区
   - 查询几乎总是「某个月/某段日期」，分区裁剪有效
   - 归档可用 `DETACH PARTITION`，比 DELETE 快得多
   - 年写入约 46,000 行（47 床 × 2.6 次/床/天 × 365），5 年 23 万行

5. **为什么 `idx_m05_bed_log_occupied` 是部分索引？**
   占用时长统计只要 `from_status = 'OCCUPIED'` 的行，全部日志中约 1/3。部分索引后，统计查询扫描 1/3 的数据量。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 日均变更次数 | 47 床 × 2.6 次 = 122 次/天 |
| 年写入 | 约 44,500 行 |
| 5 年累计（保留期） | 约 222,500 行 |
| 单行平均长度 | 约 200 字节 |
| 表大小 | 约 45 MB |
| 索引大小 | 约 30 MB |
| 合计 | 约 75 MB |

**分区：** 按 `changed_at` 月度 RANGE 分区，预建 36 个月，**保留 5 年**（超过 5 年的台账在 M05 层面价值低，且 M05-07 的年度报表已固化）。

```sql
-- 预留单号格式：YY + 8 位日期 + 4 位序号
ALTER TABLE m05_bed_reserve

    CHECK (reserve_no ~ '^YY[0-9]{12}$');

-- 预留类型枚举
ALTER TABLE m05_bed_reserve
    ADD CONSTRAINT ck_m05_bed_reserve_type
    CHECK (reserve_type IN ('PRE_ADMISSION', 'PRE_DISCHARGE'));

-- 状态枚举
ALTER TABLE m05_bed_reserve
    ADD CONSTRAINT ck_m05_bed_reserve_status
    CHECK (status IN ('ACTIVE', 'CONFIRMED', 'RELEASED', 'EXPIRED', 'CANCELLED'));

-- 截止时刻必须晚于预留时刻
ALTER TABLE m05_bed_reserve
    ADD CONSTRAINT ck_m05_bed_reserve_time
    CHECK (reserve_until > reserved_at);

-- 已确认必须有确认时刻
ALTER TABLE m05_bed_reserve
    ADD CONSTRAINT ck_m05_bed_reserve_confirmed
    CHECK (status <> 'CONFIRMED' OR confirmed_at IS NOT NULL);

-- 已释放/超时/取消必须有释放时刻与原因
ALTER TABLE m05_bed_reserve
    ADD CONSTRAINT ck_m05_bed_reserve_released
    CHECK (status NOT IN ('RELEASED', 'EXPIRED', 'CANCELLED')
           OR (released_at IS NOT NULL AND release_reason IS NOT NULL));

-- 释放原因枚举
ALTER TABLE m05_bed_reserve
    ADD CONSTRAINT ck_m05_bed_reserve_release_reason
    CHECK (release_reason IS NULL
           OR release_reason IN ('MANUAL', 'TIMEOUT', 'ADMISSION_CANCELLED',
                                 'BED_ASSIGNED_OTHER', 'WARD_CHANGED', 'OTHER'));

-- 只允许一条 ACTIVE 预留（同一床位）
-- 唯一约束在 m05_bed 的 reserve_* 字段上已由 status 保证，
-- 这里再加一层防重复（同一床位同一时刻只允许一个 ACTIVE 预留）
CREATE UNIQUE INDEX uk_m05_bed_reserve_active
    ON m05_bed_reserve (bed_id)
    WHERE status = 'ACTIVE' AND is_deleted = FALSE;

COMMENT ON TABLE m05_bed_reserve IS '床位预留历史表，每次预留新建一条';
COMMENT ON COLUMN m05_bed_reserve.reserve_type IS 'PRE_ADMISSION 预约入院 / PRE_DISCHARGE 预出院';
COMMENT ON COLUMN m05_bed_reserve.status IS 'ACTIVE 有效 / CONFIRMED 已分床 / RELEASED 主动释放 / EXPIRED 超时释放 / CANCELLED 对象取消';
COMMENT ON COLUMN m05_bed_reserve.release_reason IS 'TIMEOUT 为定时任务自动释放，MANUAL 为人工释放';
```

**设计要点：**

1. **为什么 `reserve_until > reserved_at` 而不只是 `>=`？**
   预留必须至少有一秒有效期，`>=` 会导致「预留即超时」，定时任务立即释放。

2. **为什么 `uk_m05_bed_reserve_active` 用部分唯一索引？**
   同一张床可以有很多历史预留，但**同时只能有一个有效预留**。部分唯一索引只约束 `status = 'ACTIVE'`，其他状态（RELEASED/EXPIRED/CONFIRMED）可以有任意多条。

3. **为什么 `reserve_no` 与 `bed_id` 都存？**
   `reserve_no` 是业务单号（打印、查询用），`bed_id` 是关联键。`m05_bed` 上的冗余字段避免每次分床都 JOIN 这张历史表。

| 项目 | 数值 |
|---|---|
| 日均预留次数 | 约 3 次/天（约 5% 的入院提前预留） |
| 年写入 | 约 1,100 行 |
| 5 年累计 | 约 5,500 行 |
| 单行平均长度 | 约 250 字节 |
| 表大小 | 约 1.4 MB |
| 合计（含索引） | 约 2.5 MB |

**分区：** 不分区。5 年约 5,500 行，完全不需要。

**设计要点：**

1. **为什么 `COALESCE(ward_id, 0)` 而不是分离两张表？**
   全院默认与病区覆盖放同一张表，取值时按「病区 > 全院 > 代码默认」三级回退。分离两张表会导致配置查询要 UNION 两次，代码复杂度上升。

2. **为什么 `COALESCE(ward_id, 0)` 而不是 `NULLS NOT DISTINCT`？**
   PostgreSQL 15+ 才有 `NULLS NOT DISTINCT`，本项目部分环境是 PG 14。`COALESCE(ward_id, 0)` 兼容 PG 12+，且 0 不是合法病区 ID，无冲突风险。

3. **为什么参数编码带 `M05.BED.` 前缀？**
   与全模块其他配置表（M01-10 `md_sys_param`、M05-01 `M05.ADMISSION.*`、M14 的 `M14.STOCK.*`）风格一致，便于全局参数检索与运维。

**量级估算：** 12 条全院 + 每病区约 2 条覆盖 × 6 病区 = 24 条，约 8 KB。永久保留。

**约束说明：**

```sql
-- 计数不能为负
ALTER TABLE m05_bed_snapshot
    ADD CONSTRAINT ck_m05_bed_snap_counts
    CHECK (total_beds >= 0 AND standard_beds >= 0 AND extra_beds >= 0
           AND occupied >= 0 AND reserved >= 0 AND cleaning >= 0
           AND empty >= 0 AND maintenance >= 0 AND disabled >= 0
           AND available_beds >= 0 AND new_admissions >= 0
           AND discharges >= 0);

-- 总床位数 = 标准 + 加床
ALTER TABLE m05_bed_snapshot
    ADD CONSTRAINT ck_m05_bed_snap_total
    CHECK (total_beds = standard_beds + extra_beds);

-- 六态之和 = 总床位
ALTER TABLE m05_bed_snapshot
    ADD CONSTRAINT ck_m05_bed_snap_sum
    CHECK (occupied + reserved + cleaning + empty + maintenance + disabled = total_beds);

-- 可开放床位 = 总 - 维修 - 停用
ALTER TABLE m05_bed_snapshot
    ADD CONSTRAINT ck_m05_bed_snap_available
    CHECK (available_beds = total_beds - maintenance - disabled);

-- 使用率范围 0~1
ALTER TABLE m05_bed_snapshot
    ADD CONSTRAINT ck_m05_bed_snap_rate
    CHECK (usage_rate >= 0 AND usage_rate <= 1
           AND standard_usage_rate >= 0 AND standard_usage_rate <= 1);

-- 平均住院日不能为负
ALTER TABLE m05_bed_snapshot
    ADD CONSTRAINT ck_m05_bed_snap_stay
    CHECK (avg_stay_days IS NULL OR avg_stay_days >= 0);

-- ward_id = 0 表示全院汇总，ward_name 必须为空
ALTER TABLE m05_bed_snapshot
    ADD CONSTRAINT ck_m05_bed_snap_ward
    CHECK ((ward_id = 0 AND ward_name IS NULL)
           OR (ward_id > 0 AND ward_name IS NOT NULL));

COMMENT ON TABLE m05_bed_snapshot IS '床位日快照表，每日 00:05 生成，用于期末占用率与趋势分析';
COMMENT ON COLUMN m05_bed_snapshot.ward_id IS '病区 ID，0 表示全院汇总行';
COMMENT ON COLUMN m05_bed_snapshot.bed_days_occupied IS '当日占用床日数，按床位台账累计；与 occupied 不同，它反映全天累计而非某一时刻快照';
COMMENT ON COLUMN m05_bed_snapshot.standard_usage_rate IS '标准床使用率，排除加床，用于「实际占用床日数法」口径';
```

**设计要点：**

1. **为什么 `ck_m05_bed_snap_sum` 要求六态之和严格等于总床位数？**
   这是快照的可信度根基。若不等，说明生成任务漏了床位（比如某床位状态是脏数据），报表数字不可信。约束强制检查，生成失败则告警。

2. **为什么 `bed_days_occupied` 与 `occupied` 分开？**
   - `occupied` 是「快照时刻占用数」（比如 00:05 这一刻有 38 张床占用）
   - `bed_days_occupied` 是「全天累计占用床日」（比如某床上午占用 0.4 天、下午占用 0.6 天，合计 1.0）
   - 前者用于「期末占用床位数法」，后者用于「实际占用床日数法」——**两种算法的差异可达 30 个百分点**

3. **为什么 `ward_id = 0` 表示全院汇总？**
   报表既看科室也要看全院。存储一行全院汇总，保证「科室之和 = 全院」恒成立。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 日行数 | 7 行（6 病区 + 1 全院） |
| 年行数 | 2,555 行 |
| 15 年累计 | 38,325 行 |
| 单行平均长度 | 约 250 字节 |
| 表大小 | 约 9.6 MB |
| 合计（含索引） | 约 13 MB |

**分区：** 不分区。15 年 3.8 万行完全不需要。

**设计要点：**

1. **为什么需要本地快照而不直接调 M01？**
   床位列表要显示「普通三人间 ¥80.00」这类信息。如果每次调 M01，47 行列表就是 47 次 RPC。快照后一次 JOIN 完成。

2. **为什么 `daily_fee` 要存快照而不是每次同步？**
   床位费是每日记账的依据（M05-04 每日 00:30 生成床位费）。若 M01 不可用，记账会失败。本地快照让记账在 M01 短时故障时仍能完成，代价是可能用旧价格（次日对账可发现）。

3. **为什么 `standard_bed` 独立于 `bed_category`？**
   `bed_category` 是 M01 的原始类别枚举，`standard_bed` 是 M05 的统计口径字段。加床类别一定不是标准床（`ck_m05_bed_type_extra`），但标准床也可能不是加床——两个字段语义不同，都保留。

### B.6 床位类别（`m05_bed_type_snap.bed_category`，5 类）

### B.7 性别限制（`gender_limit`，3 类）

`M` 男 / `F` 女 / `ANY` 不限（NULL 等同 ANY）

### E.3 分区建表脚本（`m05_bed_status_log`）

```sql
CREATE TABLE m05_bed_status_log (
    id                      BIGINT GENERATED BY DEFAULT AS IDENTITY,
    bed_id                  BIGINT NOT NULL,
    bed_no                  VARCHAR(16) NOT NULL,
    ward_id                 BIGINT NOT NULL,
    ward_name               VARCHAR(64),
    from_status             VARCHAR(16),
    to_status               VARCHAR(16) NOT NULL,
    admission_id            BIGINT,
    patient_id              BIGINT,
    patient_name            VARCHAR(64),
    change_reason           VARCHAR(64) NOT NULL,
    remark                  VARCHAR(512),
    duration_seconds        INTEGER,
    changed_by              BIGINT NOT NULL,
    changed_by_name         VARCHAR(64),
    changed_at              TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, changed_at)
) PARTITION BY RANGE (changed_at);

DO $$
DECLARE
    i          INT;
    start_date DATE;
    end_date   DATE;
    part_name  TEXT;
BEGIN
    FOR i IN 0..35 LOOP
        start_date := (DATE_TRUNC('month', CURRENT_DATE)
                       + (i || ' months')::INTERVAL);
        end_date := start_date + INTERVAL '1 month';
        part_name := 'm05_bed_status_log_p' || TO_CHAR(start_date, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m05_bed_status_log '
            'FOR VALUES FROM (%L) TO (%L)',
            part_name, start_date, end_date
        );
    END LOOP;
END $$;
```

**为什么主键是 `(id, changed_at)`：**
PostgreSQL 要求分区表主键包含分区键。业务查询走 `bed_id + changed_at`，不依赖主键，改为复合主键无影响。
