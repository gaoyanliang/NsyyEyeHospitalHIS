**设计说明：**

1. **不建物理外键**。`admission_id`、`patient_id`、`surgeon_id` 等均只做逻辑引用。理由：①首页创建时需要 JOIN 7~10 张外部表，外键检查会让创建耗时从 80ms 涨到 300ms 以上；②数据归档时无外键解耦更简单；③跨模块外键在本系统架构下无法建立。
2. **`m05_home_diagnosis` 与 `m05_home_operation` 各 1:N**。首页有 6 种诊断角色（受 `diag_role` 约束），手术有 2 种角色（`op_role`），同一角色下按 `seq_no` 排序。
3. **`m05_home_quality` 按批次累积**。一次质控一批，旧批次保留——「第一次质控发现了什么」是病案质控档案的一部分，可以用于分析「哪些编码员经常犯哪类错误」。
4. **`m05_home_log` 月分区 + 只增触发器**。日志只增不改，用 `DROP PARTITION` 归档比 `DELETE` 少产生死元组。
5. **`m05_home_config` 独立无关联**。参数表不参与任何业务 JOIN。

**设计要点：**

1. **`uk_m05_home_admission` 是幂等基石**。`on_discharged` 事件可能因消息重投、运维补发而重复投递 3 次，业务层虽有先查后插，但并发场景下（两个 Pod 同时消费）必然漏。数据库唯一索引是最后一道防线。
2. **`ck_m05_home_sod_coder_auditor` 是唯一能在 DB 层实现的 SoD**。因为编码员与审核人在同一行，CHECK 可以比较。其他 SoD（如「审核人≠填写人」）需要跨表，只能服务层 + 审计兜底。
3. **`principal_diag_code` / `principal_op_code` 冗余存储**。诊断明细在 `m05_home_diagnosis`，但列表页与统计报表需要「按主要诊断筛选」，每次都 JOIN 明细表（一年 14,600 份 × 平均 4 条诊断 = 58,400 行）会慢。冗余一个主诊断编码，列表查询从 45ms 降到 8ms。
4. **`id_card` / `phone` 应用层加密**。数据库列类型仍是 `VARCHAR`，但存的是 AES-256-GCM 密文。这样 DBA 直接看表拿不到明文，符合个人信息保护要求。索引不可建于加密列（密文排序无意义），所以身份证明文检索需要单独的 `id_card_hash` 列——见 4.2 补充说明。

**设计要点：**

1. **`uk_m05_home_diag_principal` 是 Q-02 的数据库级兜底**。服务层在提交时会检查主要诊断唯一，但当两个标签页同时保存、或前端被绕过时，唯一索引能保证不会出现两条 `PRINCIPAL`。这类约束一旦失效，上报医保会被直接拒绝（格式不符）。
2. **`ck_m05_home_diag_eye_required` 用 `code LIKE 'H%'` 判断眼科**。眼科诊断在 ICD-10 中全部落在 H00~H59，前缀判断是可靠的。但 `EXTERNAL`（损伤中毒外部原因）是 V~Y 章节，不涉及眼别，所以通过 `diag_role NOT IN ('PRINCIPAL','OTHER')` 豁免。
3. **为什么 `admission_condition` 必须在 `PRINCIPAL` 和 `OTHER` 上填**。`ADMISSION` 角色的入院病情恒为「1 有」，`OUTPATIENT` 角色无意义，只有主要/其他诊断的入院病情才影响 DRG。质控 Q-04 只检查这两个角色。
4. **`eye_side` 默认 `'NA'` 而不是 NULL**。用 `'NA'` 表示「明确不适用」，与「尚未填写」区分。质控 Q-07 检查的是「眼科诊断但 `eye_side='NA'`」，所以默认值让问题可被检出；若用 NULL，`NULL <> 'NA'` 恒为 UNKNOWN，约束失效。

2. **`implant_code` 独立字段而非塞进 `remark`**。人工晶体是医院价值最高的耗材之一（单枚 2,000~15,000 元），UDI 监管要求「能追到具体病人在哪个手术用了哪一个晶体」。塞在备注里无法索引、无法统计、无法与 M15 耗材追溯对账。
3. **`is_intraocular` 用于感染风险分级**。内眼手术（白内障、玻璃体切除）与眼睑手术（霰粒肿切除）的感染风险差 10 倍以上，院内感染率是首页质量指标之一。

-- 规则级别枚举
ALTER TABLE m05_home_quality
    ADD CONSTRAINT ck_m05_home_qc_level
    CHECK (level IN ('BLOCK', 'WARN', 'INFO'));

-- 执行结果枚举
ALTER TABLE m05_home_quality
    ADD CONSTRAINT ck_m05_home_qc_result
    CHECK (result IN ('PASS', 'FAIL', 'WARN', 'INFO'));

-- BLOCK 级规则只能 PASS 或 FAIL
ALTER TABLE m05_home_quality
    ADD CONSTRAINT ck_m05_home_qc_block_result
    CHECK (level <> 'BLOCK' OR result IN ('PASS', 'FAIL'));

-- 失败必须有描述
ALTER TABLE m05_home_quality
    ADD CONSTRAINT ck_m05_home_qc_fail_desc
    CHECK (result IN ('PASS', 'INFO')
           OR (issue_desc IS NOT NULL AND char_length(btrim(issue_desc)) >= 3));

-- 批次号格式
ALTER TABLE m05_home_quality
    ADD CONSTRAINT ck_m05_home_qc_batch_no
    CHECK (qc_batch_no ~ '^QC[0-9]{9,20}$');

COMMENT ON COLUMN m05_home_quality.result IS 'PASS通过/FAIL失败/WARN警告/INFO提示';

**参数读取优先级：**

```
科室级（scope='DEPT' AND scope_id=当前科室）
    │ 未命中
    ▼
全局级（scope='GLOBAL'）
    │ 未命中
    ▼
代码默认值（常量表）
```

**为什么用 `COALESCE(scope_id, 0)` 而不是 `NULLS NOT DISTINCT`：** PostgreSQL 唯一索引认为 `NULL` 互不相等，`(param_code='X', scope='GLOBAL', scope_id=NULL)` 可以插入两次，导致「同一参数有两条全局配置」。`NULLS NOT DISTINCT` 是 PG 15+ 特性，本项目部分环境仍是 PG 14。用 `COALESCE(scope_id, 0)` 把 NULL 归一化为 0（0 不是合法科室 ID），语义等价且全版本兼容。

**量级估算：** 22 条固定 + 少量科室覆盖，共约 40 条，永久保留，约 20 KB。

**分区：** 不分区（极小表）。

| `idx_m05_home_pending_qc` | `m05_medical_record_home` | 21.9 万行 / 750MB / 约 38ms | 约 12 行 / 1 页 / < 0.1ms | **380 倍** |
| `idx_m05_home_pending_audit` | `m05_medical_record_home` | 同上 | 约 8 行 / < 0.1ms | **380 倍** |
| `idx_m05_home_report_failed` | `m05_medical_record_home` | 同上 | 约 2 行 / < 0.1ms | **380 倍** |
| `idx_m05_home_overdue` | `m05_medical_record_home` | 同上 | 约 10 行 / < 0.1ms | **380 倍** |
| `idx_m05_home_qc_fail` | `m05_home_quality` | 657 万行 / 2.8GB / 约 1.2s | 约 120 行 / 3 页 / < 0.2ms | **6000 倍** |
| `idx_m05_home_op_implant` | `m05_home_operation` | 48 万行 / 400MB / 约 90ms | 约 5,800 行 / 30KB / 约 3ms | **30 倍** |
| `idx_m05_home_diag_source` | `m05_home_diagnosis` | 175 万行 / 800MB / 约 300ms | 约 170 万行（几乎全覆盖）/ 略差 | 不适用（M07 全同步） |
| `idx_m05_home_name_trgm` | `m05_medical_record_home` | `LIKE '%张%'` 无索引 65ms | GIN 索引 3ms | **21 倍** |
| `idx_m05_home_id_card_hash` | `m05_medical_record_home` | 哈希列无索引必须全表 38ms | 精确匹配 < 0.1ms | **380 倍** |

**为什么部分索引对病案首页收益特别大：** 病案首页的「待办」极不均匀——一年 14,600 份首页，任何时刻待质控约 12 份（0.08%）、待审核约 8 份（0.05%）、上报失败约 2 份（0.01%）。质控员工作台每分钟刷新一次，若每次都全表扫 750MB，一天 480 次刷新就是 360GB 的 I/O。部分索引让每次刷新只读 1~2 页。

**`idx_m05_home_qc_fail` 的 6000 倍收益最显著**：质控结果表一年 43.8 万行、15 年 657 万行，但「当前失败的质控项」任何时刻只有约 120 条（12 条规则 × 10 份待整改）。这是「历史累积」与「当前活跃」差距最大的表。

### E.3 分区建表 SQL（`m05_home_log`）

```sql
CREATE TABLE m05_home_log (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY,
    home_id       BIGINT       NOT NULL,
    admission_id  BIGINT       NOT NULL,
    action        VARCHAR(32)  NOT NULL,
    operator_id   BIGINT       NOT NULL DEFAULT 0,
    operator_name VARCHAR(64),
    operator_ip   VARCHAR(64),
    detail_json   JSONB,
    old_value     TEXT,
    new_value     TEXT,
    remark        VARCHAR(500),
    trace_id      VARCHAR(64),
    operated_at   TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, operated_at)
) PARTITION BY RANGE (operated_at);

DO $$
DECLARE
    i INT;
    p_start DATE;
    p_end   DATE;
BEGIN
    FOR i IN 0..35 LOOP
        p_start := date_trunc('month', CURRENT_DATE)::date + (i || ' month')::interval;
        p_end   := p_start + INTERVAL '1 month';
        EXECUTE format(
            'CREATE TABLE IF NOT EXISTS m05_home_log_%s PARTITION OF m05_home_log '
            'FOR VALUES FROM (%L) TO (%L)',
            to_char(p_start, 'YYYYMM'), p_start, p_end
        );
    END LOOP;
END $$;

-- 索引（分区表上的索引会自动应用到每个分区）
CREATE INDEX idx_m05_home_log_home ON m05_home_log (home_id, operated_at DESC);
CREATE INDEX idx_m05_home_log_admission ON m05_home_log (admission_id);
CREATE INDEX idx_m05_home_log_action ON m05_home_log (action, operated_at);
CREATE INDEX idx_m05_home_log_operator ON m05_home_log (operator_id, operated_at);

-- 只增触发器
CREATE OR REPLACE FUNCTION fn_m05_home_log_readonly()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'm05_home_log 为只增表，禁止 UPDATE/DELETE';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m05_home_log_update
    BEFORE UPDATE ON m05_home_log
    FOR EACH ROW EXECUTE FUNCTION fn_m05_home_log_readonly();

CREATE TRIGGER trg_m05_home_log_delete
    BEFORE DELETE ON m05_home_log
    FOR EACH ROW EXECUTE FUNCTION fn_m05_home_log_readonly();
```

| 8 | **M01-09 编码表接口幂等验证** | 同一编码连查 3 次结果一致，避免缓存击穿时返回空 |
| 9 | 医保/卫健/质控中心上报接口已联通 | 三条链路各自的报文格式已用样例验证 |
