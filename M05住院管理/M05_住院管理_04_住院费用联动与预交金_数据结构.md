**设计说明：**

1. **不建物理外键**：与 M05-01/M05-02/M05-03 保持一致。理由 —— ①`m05_charge_task` 是高频写入表（日 141 条 × 365 = 5.1 万/年），外键在每次 INSERT 时都要查一次 `m05_admission` 并加共享锁，与 M05-01 的 UPDATE 冲突概率提升 ②`m16_inpatient_charge` 在另一个模块，跨模块外键在分库时会失效 ③建表顺序会与 `m05_admission.bed_id` 形成循环耦合。一致性由应用层事务 + 每日 03:00 对账任务保证。
2. **`m05_charge_task` 是「意图表」，`m16_inpatient_charge` 是「结果表」**：M05-04 只知道「我要记这一笔」，M16-03 返回 `charge_id` 后回填。若 M16 不可用，意图表里有记录，第二天对账时能发现漏记并补。
3. **`m05_charge_alert` 与 `m05_charge_task` 无关联**：预警基于「余额 vs 已记账」的实时计算结果，与具体的计费任务无关。同一患者可能因多笔任务失败而欠费，但只有一个预警记录。
4. **`m05_charge_daily_stat` 是「可重建的派生数据」**：任何时候都能从 `m16_inpatient_charge` 重算。它的存在只为让报表查询从「扫 500 万行」变成「扫 1000 行」。
5. **`m05_charge_task_log` 按 `operated_at` 月度分区**：日志表是只增表，15 年数据量约 78 万行，分区后单分区约 4,300 行，查询与清理都更高效。

**约束说明：**

```sql
-- 任务号格式
ALTER TABLE m05_charge_task ADD CONSTRAINT ck_m05_charge_task_no
    CHECK (task_no ~ '^JFRW[0-9]{12}$');

-- 费用类别枚举
ALTER TABLE m05_charge_task ADD CONSTRAINT ck_m05_charge_task_category
    CHECK (charge_category IN ('BED', 'NURSING', 'CLINIC'));

-- 状态枚举
ALTER TABLE m05_charge_task ADD CONSTRAINT ck_m05_charge_task_status
    CHECK (status IN ('PENDING', 'SUCCESS', 'FAILED', 'DEAD', 'SKIPPED'));

-- 金额自洽：床日费数量恒为 1，金额必须等于单价
ALTER TABLE m05_charge_task ADD CONSTRAINT ck_m05_charge_task_amount
    CHECK (quantity > 0 AND amount = ROUND(unit_price * quantity, 2));

-- 金额非负
ALTER TABLE m05_charge_task ADD CONSTRAINT ck_m05_charge_task_amount_pos
    CHECK (unit_price >= 0 AND amount >= 0);

-- 重试次数范围
ALTER TABLE m05_charge_task ADD CONSTRAINT ck_m05_charge_task_retry
    CHECK (retry_count >= 0 AND retry_count <= 10);

-- 成功必须有记账结果
ALTER TABLE m05_charge_task ADD CONSTRAINT ck_m05_charge_task_success
    CHECK (status <> 'SUCCESS' OR (charge_id IS NOT NULL AND charged_at IS NOT NULL));

-- 失败必须有原因与下次重试时刻
ALTER TABLE m05_charge_task ADD CONSTRAINT ck_m05_charge_task_failed
    CHECK (status NOT IN ('FAILED') OR (fail_reason IS NOT NULL AND next_retry_at IS NOT NULL));

-- DEAD 必须有失败原因
ALTER TABLE m05_charge_task ADD CONSTRAINT ck_m05_charge_task_dead
    CHECK (status <> 'DEAD' OR fail_reason IS NOT NULL);

-- 人工补记完整性
ALTER TABLE m05_charge_task ADD CONSTRAINT ck_m05_charge_task_manual
    CHECK (is_manual = FALSE
           OR (manual_reason IS NOT NULL
               AND char_length(btrim(manual_reason)) >= 10
               AND manual_by IS NOT NULL
               AND manual_at IS NOT NULL));

-- 幂等键格式
ALTER TABLE m05_charge_task ADD CONSTRAINT ck_m05_charge_task_idem
    CHECK (idempotency_key ~ '^(DAILY|MANUAL):[0-9]+:[0-9]{4}-[0-9]{2}-[0-9]{2}:[A-Za-z0-9_-]+$');

-- source_id 非负
ALTER TABLE m05_charge_task ADD CONSTRAINT ck_m05_charge_task_source
    CHECK (source_id >= 0);

-- 注释
COMMENT ON TABLE m05_charge_task IS '住院计费任务表：每笔床日费的触发意图与执行状态';
COMMENT ON COLUMN m05_charge_task.task_no IS '任务号，JFRW + YYYYMMDD + 6 位序号';
COMMENT ON COLUMN m05_charge_task.charge_date IS '计费日期：业务发生日，00:30 补记前一天';
COMMENT ON COLUMN m05_charge_task.idempotency_key IS '幂等键，保证同一患者同日同项目只成功记账一次';
COMMENT ON COLUMN m05_charge_task.source_id IS '幂等键的 64 位哈希压缩到 2^53 以内，传给 M16-03 作为 source_id';
COMMENT ON COLUMN m05_charge_task.next_retry_at IS '下次重试时刻，退避 2/4/8/.../1024 分钟';
COMMENT ON COLUMN m05_charge_task.charge_id IS 'M16-03 m16_inpatient_charge.id 回填';
```

**状态机：**

```
                  ┌──────────┐
                  │ PENDING  │ 任务已生成，待执行
                  └────┬─────┘
                       │ 执行记账
          ┌────────────┼────────────┐
          ▼                         ▼
   ┌─────────────┐          ┌─────────────┐
   │  SUCCESS    │          │  FAILED     │
   │  终态        │          │  可重试      │
   └─────────────┘          └──────┬──────┘
                                   │ 重试
                          ┌────────┴────────┐
                          ▼                 ▼
                    ┌──────────┐      ┌──────────┐
                    │ PENDING  │      │  DEAD    │
                    │ (重试中)  │      │ 终态      │
                    └──────────┘      └────┬─────┘
                                           │ 人工补记（force）
                                           ▼
                                     ┌──────────┐
                                     │ PENDING  │
                                     └──────────┘

  SKIPPED：生成阶段发现已存在 SUCCESS 记录，直接跳过（终态）
```

**设计要点：**

1. **`idempotency_key` 全表唯一（不带 `is_deleted` 条件）**：这是「同一患者同日同项目只记一次」的数据库级防线。若按软删除加条件，删除后重跑能生成第二条，破坏幂等。若需重跑，应改回原记录（把 `status` 置 `PENDING`、`retry_count` 清零），而非新建。
2. **`source_id` 与 `idempotency_key` 同时存**：`source_id` 是给 M16-03 的，`idempotency_key` 是人能读懂、能排查的原文。只存 `source_id` 无法反推为什么冲突，只存 `idempotency_key` 无法传给 M16（M16 要求 BIGINT）。
3. **`quantity` 恒为 1 但仍存**：`ck_m05_charge_task_amount` 用 `amount = ROUND(unit_price * quantity, 2)` 表达「金额是按单价乘数量算出来的」，若将来有按床日 × 折扣的变体，`quantity` 留有了扩展位。
4. **快照字段（`admission_no`/`patient_name`/`ward_name`/`bed_no`/`charge_item_name`/`unit_price`）**：①任务列表 141 行，若每行都去查 `m05_admission`/`m01_charge_item` 会变成 282 次调用 ②患者改名、收费项目改名、价格调整后，历史任务必须显示当时的值，否则对账时金额与分析表不符。
5. **`charge_date` 与 `created_at` 是两个概念**：`charge_date` 是业务发生日（10-27），`created_at` 是任务生成时刻（10-28 00:30）。查询「10-27 的床位费记了没有」必须用 `charge_date`。
6. **金额 `NUMERIC(12,2)`、单价 `NUMERIC(12,4)`**：与 M16-03 一致，避免精度截断。
7. **`next_retry_at` 而非重试计数驱动**：Celery 定时任务每 10 分钟扫 `WHERE status='FAILED' AND next_retry_at <= NOW()`，比用 `retry_count` 计算「应该几点重试」简单可靠（应用重启后不用重算）。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 日均生成 | 47 在院 × 3 类 = 141 条 |
| 年行数 | 141 × 365 = 51,465 条 |
| 单行大小 | 约 700 字节 |
| 年数据量 | 约 34 MB |
| 保留期 | 15 年 |
| 15 年行数 | 约 77 万行 |
| 15 年数据量 | 约 540 MB（含索引约 1.1 GB） |

**分区：** 不分区。理由：①按 `charge_date` 年度分区会迫使 `uk_m05_charge_task_idem` 与 `uk_m05_charge_task_source` 包含分区键，**幂等语义退化为「同年唯一」**，跨年补记会重复记账 ②15 年 77 万行在 PostgreSQL 单表舒适区间内。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |

**`category_dist` 示例：**

```json
{
  "BED": {"count": 47, "amount": 3760.00},
  "NURSING": {"count": 47, "amount": 1410.00},
  "CLINIC": {"count": 47, "amount": 470.00},
  "EXAM": {"count": 12, "amount": 8200.00},
  "DRUG": {"count": 35, "amount": 3400.00}
}
```

**设计要点：**

1. **`dept_id` / `ward_id` 用 `0` 而非 NULL 表示不适用**：与唯一索引配合，避免 NULL 互不相等的坑（同 `m05_charge_config` 的理由）。
2. **`net_amount` 单独存**：报表常用「净收入」，若每次查都算 `charge_amount + reversal_amount`，聚合时容易漏掉 `NULL`（若 `reversal_amount` 允许 NULL）。存成实体列并加 CHECK 保证自洽。
3. **`success_rate` 存 `NUMERIC(6,4)`**：`0.9860` 表示 98.60%。精度 4 位足够表达「98.6%」与「99.99%」的差异。
4. **`category_dist` 用 JSONB 而非拆 17 列**：类别有 12 种，拆列会让表宽从 18 涨到 30，且新增类别要改表结构。查询时用 `category_dist -> 'DRUG' ->> 'amount'`。
5. **UPSERT 幂等**：`INSERT ... ON CONFLICT (stat_date, stat_type, dept_id, ward_id, category) DO UPDATE`，重跑任务不会产生重复行。
6. **可重建性**：任何时候都能 `TRUNCATE` 后从 `m16_inpatient_charge` 全量重算，所以不需要备份策略。

| 年行数 | 18 × 365 = 6,570 行 |
| 单行大小 | 约 480 字节 |
| 年数据量 | 约 3.2 MB |
| 保留期 | 15 年 |

```sql
-- 预警号格式
ALTER TABLE m05_charge_alert ADD CONSTRAINT ck_m05_charge_alert_no
    CHECK (alert_no ~ '^YJ[0-9]{12}$');

-- 预警类型
ALTER TABLE m05_charge_alert ADD CONSTRAINT ck_m05_charge_alert_type
    CHECK (alert_type IN ('OWED', 'INTERIM'));

-- 级别
ALTER TABLE m05_charge_alert ADD CONSTRAINT ck_m05_charge_alert_level
    CHECK (level IN ('WARN', 'NORMAL', 'SEVERE'));

-- 状态
ALTER TABLE m05_charge_alert ADD CONSTRAINT ck_m05_charge_alert_status
    CHECK (status IN ('PENDING', 'NOTIFIED', 'RESOLVED', 'IGNORED'));

-- 欠费金额自洽
ALTER TABLE m05_charge_alert ADD CONSTRAINT ck_m05_charge_alert_owed
    CHECK (owed_amount = accumulated_charge - available_balance);

-- OWED 类型欠费金额必须 > 0
ALTER TABLE m05_charge_alert ADD CONSTRAINT ck_m05_charge_alert_owed_pos
    CHECK (alert_type <> 'OWED' OR owed_amount > 0);

-- INTERIM 类型必须有触发原因
ALTER TABLE m05_charge_alert ADD CONSTRAINT ck_m05_charge_alert_interim
    CHECK (alert_type <> 'INTERIM'
           OR (interim_reason IS NOT NULL
               AND char_length(btrim(interim_reason)) >= 5));

-- WARN 级必须有比例
ALTER TABLE m05_charge_alert ADD CONSTRAINT ck_m05_charge_alert_warn
    CHECK (level <> 'WARN' OR threshold_ratio IS NOT NULL);

-- 已通知必须有通知时刻
ALTER TABLE m05_charge_alert ADD CONSTRAINT ck_m05_charge_alert_notified
    CHECK (notify_count = 0 OR last_notified_at IS NOT NULL);

-- 已处置必须有完整信息
ALTER TABLE m05_charge_alert ADD CONSTRAINT ck_m05_charge_alert_resolved
    CHECK (status NOT IN ('RESOLVED', 'IGNORED')
           OR (resolved_at IS NOT NULL
               AND resolved_by IS NOT NULL
               AND resolve_note IS NOT NULL
               AND char_length(btrim(resolve_note)) >= 5));

-- 通知日志类型校验
ALTER TABLE m05_charge_alert ADD CONSTRAINT ck_m05_charge_alert_notify_json
    CHECK (notify_log IS NULL OR jsonb_typeof(notify_log) = 'array');

-- 24 小时去重：同一住院单同类型同日期只一条
ALTER TABLE m05_charge_alert ADD CONSTRAINT uk_m05_charge_alert_dedup
    UNIQUE (admission_id, alert_type, alert_date);

COMMENT ON TABLE m05_charge_alert IS '住院欠费预警表，含欠费与中途结算两类提示';
COMMENT ON COLUMN m05_charge_alert.owed_amount IS '欠费金额快照，预警生成时计算一次，不随余额变动';
COMMENT ON COLUMN m05_charge_alert.notify_log IS '通知记录数组：[{"channel":"SMS","at":"...","result":"SENT"}]';
```

**`notify_log` 示例：**

```json
[
  {
    "channel": "INBOX",
    "sent_at": "2026-10-27T09:00:12+08:00",
    "receiver": "护士站",
    "result": "SENT"
  },
  {
    "channel": "SMS",
    "sent_at": "2026-10-27T09:00:15+08:00",
    "receiver": "138****5678",
    "result": "SENT"
  }
]
```

**设计要点：**

1. **`uk_m05_charge_alert_dedup` 用普通唯一约束而非部分索引**：`(admission_id, alert_type, alert_date)` 三列都不为空，无 NULL 问题，直接用 `UNIQUE` 约束。这保证「同一住院单同类型同日期只生成一条预警」，即使扫描任务重复执行也只会 UPSERT 或冲突。
2. **`owed_amount` 存快照而非实时算**：预警生成时算一次，「10-27 王**欠 ¥1240」这条记录是通知当时的依据。若实时算，患者缴费后这条记录会变成「欠 ¥0」，看历史时无法理解当时为什么发提醒。
3. **`interim_reason` 单独字段而非塞进 `resolve_note`**：中途结算的三个触发条件（天数/金额/预交金）需要在 P01 页面上显示给住院处看，塞进自由文本就没法解析。
4. **`notify_log` 用 JSONB 数组而非独立通知表**：①一次预警最多 3~5 条通知 ②总是整体读取（详情页一次性展示）③不需要按渠道统计（按渠道统计走 M03-05）。独立建表会产生一张年 5 万行的表 + JOIN，不划算。
5. **`notify_count` 与 `last_notified_at` 是冗余的聚合字段**：列表页要显示「已通知 2 次 / 最近 10-27 09:00」，若从 `notify_log` 里 `jsonb_array_length` 再取最后一个元素，列表 50 行要展开 50 次 JSONB。
6. **`status = 'IGNORED'` 而非删除**：护士判断「这个患者是单位记账，不用催」可以忽略，但保留记录供审计。

### E.3 分区建表 SQL

```sql
-- m05_charge_task_log 月分区
CREATE TABLE m05_charge_task_log (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY,
    task_id      BIGINT      NOT NULL,
    task_no      VARCHAR(24) NOT NULL,
    action       VARCHAR(24) NOT NULL,
    from_status  VARCHAR(16),
    to_status    VARCHAR(16),
    retry_count  SMALLINT    NOT NULL DEFAULT 0,
    message      VARCHAR(500),
    operated_by  BIGINT      NOT NULL DEFAULT 0,
    operated_at  TIMESTAMP   NOT NULL DEFAULT NOW(),
    PRIMARY KEY (id, operated_at)
) PARTITION BY RANGE (operated_at);

DO $$
DECLARE
    i INT;
    p_start DATE;
    p_end   DATE;
    p_name  TEXT;
BEGIN
    FOR i IN 0..35 LOOP
        p_start := (DATE '2026-10-01' + (i || ' months')::interval)::date;
        p_end   := (DATE '2026-10-01' + ((i + 1) || ' months')::interval)::date;
        p_name  := 'm05_charge_task_log_p' || to_char(p_start, 'YYYYMM');
        EXECUTE format(
            'CREATE TABLE %I PARTITION OF m05_charge_task_log '
            'FOR VALUES FROM (%L) TO (%L)',
            p_name, p_start, p_end
        );
    END LOOP;
END $$;
```
