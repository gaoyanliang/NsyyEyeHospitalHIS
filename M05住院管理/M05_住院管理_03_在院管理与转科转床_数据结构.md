**设计说明：**

1. **`m05_stay` 是核心表**，一位在院患者对应一条记录，从分床开始到出院结案结束。`admission_id` 上必须有部分唯一索引（同一住院单只能有一个进行中的在院记录）。
2. **`m05_stay_log` 只增月分区**，记录每一次在院信息变更，年写入约 44,000 条，保留 15 年（与在院记录同）。
3. **`m05_transfer` 与 `m05_transfer_approval` 是主从关系**，一个转科申请对应 0~3 个审批节点（转床/换主诊为 0 个）。
4. **`m05_discharge` 与 `m05_stay` 一对一**（一次在院最多一条出院记录）。
5. **`m05_stay_config` 独立成表**，与 M05-01/M05-02 的配置表结构同构。
6. **不建外键**，理由见 4.2 设计要点第 9 条。

**状态转移矩阵：**

| 从 ↓ / 到 → | IN_HOSPITAL | TRANSFERRING | DISCHARGING | CLOSED |
|---|---|---|---|---|
| IN_HOSPITAL | — | ✅ 转科申请 | ✅ 出院通知 | ✅ 出院登记（免通知） |
| TRANSFERRING | ✅ 取消/驳回 | — | ❌ | ✅ 转院执行 |
| DISCHARGING | ✅ 撤销通知 | ❌ | — | ✅ 出院登记 |
| CLOSED | ❌ | ❌ | ❌ | — |

**设计要点：**

1. **为什么 `admission_id` 用部分唯一索引而非普通唯一索引？**
   一位患者可能有多条在院记录（出院后再次入院）。普通唯一索引会禁止同一住院单多次创建，但业务上更关键的是「同一时间只能有一个进行中的在院记录」。若用普通唯一索引，则出院后再次入院要新建住院单（正常会新建），但历史在院记录的 `admission_id` 会冲突。部分唯一索引只约束进行中的状态，允许历史记录存在。

2. **为什么患者信息要快照（`patient_name` / `gender` / `age` / `id_card_masked`）？**
   - 在院列表一次显示 200 条，若每条都调 M03-01 取姓名就是 200 次调用
   - 患者改名后，历史在院记录应保留「当时」的姓名（在院记录是台账）
   - 快照存脱敏后的证件号与手机号，避免直接存明文敏感数据

3. **为什么 `stay_days` 是冗余字段而非生成列？**
   `stay_days = DATEDIFF(出院日, 入院日) + 1` 在 `< CLOSED` 状态下是「已住院天数」（动态变化，截至今天），在 `CLOSED` 状态下是「最终住院天数」（固定）。生成列无法表达这种「依赖当前时间」的逻辑，所以用定时任务每天 00:05 更新。

4. **为什么 `ck_m05_stay_critical_level` 在 DB 层也加校验？**
   应用层会在 `change_condition` / `change_nursing_level` 里检查并给出友好的错误提示，但 DB 层兜底能防止「绕过接口直接改库」或「两个接口并行导致的组合冲突」。这是病案质量的红线。

5. **为什么 `summary_exempt` 是持久化字段而非计算得出？**
   豁免规则依赖出院类型，而出院类型在 `m05_discharge` 表（本表不存出院类型避免冗余）。若计算得出需要跨表查询。持久化后在院列表可以直接展示「该患者出院可豁免小结」以便住院处判断。

6. **为什么 `change_count` 单独存？**
   工作台的「活跃患者」判定、日志量预估需要这个数。若每次 `COUNT(m05_stay_log)` 会增加查询开销。

7. **为什么 `eye_side` 冗余到在院记录？**
   眼科患者的在院管理、护理任务、床位牌都要显示眼别（区分左右手术眼）。在院记录冗余后，M08 护理站查询在院患者时无需再调 M07。

8. **为什么乐观锁 `version` 与行锁 `FOR UPDATE` 都用？**
   - `FOR UPDATE` 防并发写入（两人同时改同一患者状态）
   - `version` 检测「读到的数据是否已被改过」（长时间的编辑页面）

9. **为什么不建外键？**
   - `admission_id` → `m05_admission`：M05-01 与 M05-03 同模块，但 `m05_stay` 是高写入表，外键检查开销
   - `bed_id` → `m05_bed`：同上
   - 建表顺序会耦合：`m05_admission` 创建后才有在院记录，但 `m05_admission` 又要引用 `m05_bed`，而 `m05_bed` 独立于患者
   - **一致性由应用层事务 + 每日 03:00 对账任务保证**

10. **为什么不分区？**
    在院记录年约 15,000 条（与住院人数一致），15 年 22.5 万行，PostgreSQL 单表完全可承受。按年份分区会让 `uk_m05_stay_admission` 必须含分区键，破坏「同一住院单只能有一个进行中记录」的约束。

| 15 年累计 | 225,000 行 | — |

| 表大小 | 约 158 MB | — |

**设计要点：**

1. **为什么带宽快照（`stay_no` / `admission_no` / `patient_name` / `bed_no`）？**
   日志是台账，要反映「当时」的事实。患者改名、换床后历史日志不能跟着变。同时避免查日志时 JOIN 多表。

2. **为什么带宽 `field_name` / `old_value` / `new_value`？**
   通用三段式记录任何字段的变更，无需为每个字段建列。`old_value` / `new_value` 用 `VARCHAR(512)` 而非 JSONB——变更的都是标量值（等级代码、ID、饮食类型），JSONB 反而更重。

3. **为什么 `related_id` 要单独存？**
   转科变更（`BED_CHANGE` / `WARD_CHANGE` / `DEPT_CHANGE`）需要关联到具体的 `m05_transfer` 记录，「这个床位是哪个转科单产生的变换」。出院类关联到 `m05_discharge`。

4. **为什么月度分区？**
   - 数据只追加，天然适合分区
   - 查询几乎总是「某患者在院期间的日志」或「某段时间病区日志」，分区裁剪有效
   - 归档可用 `DETACH PARTITION`，比 DELETE 快
   - 年写入约 44,000 条（15,000 × 2.9 次变更），15 年 66 万行，分区后每月约 3,700 行

5. **为什么保留 15 年而不是 3 年？**
   在院变更日志是病历的组成部分（护理等级变更记录是医疗行为的证据），《医疗机构病历管理规定》要求住院病历保存 ≥30 年。这里 15 年与 `m05_admission` 保留期一致，长期归档在 M18 病历归档中。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 日均变更次数 | 约 120 次/天（15,000 年 ÷ 365 × 2.9） |
| 年写入 | 约 44,000 行 |
| 15 年累计（保留期） | 约 660,000 行 |
| 单行平均长度 | 约 260 字节 |
| 表大小 | 约 172 MB |
| 索引大小 | 约 120 MB |
| 合计 | 约 290 MB |

**分区：** 按 `changed_at` 月度 RANGE 分区，**预建 60 个月**（5 年），保留 15 年（后续按需扩展）。

**状态机：**

```
   ┌──────────────────┐
   │  PENDING_APPLY   │  待提交（草稿）
   └────────┬─────────┘
            │ submit（仅需审批的类型）
            ▼
   ┌──────────────────┐
   │   PENDING_OUT    │  待转出科室主任审批
   └────────┬─────────┘
            │ approve
            ▼
   ┌──────────────────┐
   │   PENDING_IN     │  待转入科室主任审批
   └────────┬─────────┘
            │ approve
      ┌─────┴─────┐
      │ 转科需医务科 │ 转病区不需
      ▼           ▼
┌─────────────┐  ┌────────────┐
│PENDING_     │  │  APPROVED  │
│MEDICAL      │  │  已批准     │
└──────┬──────┘  └─────┬──────┘
       │ approve       │
       ▼               │
   ┌────────────┐      │
   │  APPROVED  │──────┤
   └─────┬──────┘      │
         │ execute     │
         ▼             │
   ┌────────────┐      │
   │ EXECUTING  │      │
   └─────┬──────┘      │
         │ 成功         │
         ▼             │
   ┌────────────┐      │
   │  EXECUTED  │      │
   └────────────┘      │

   任一审批可 ──► REJECTED（终态）
   草稿/审批中/已批准可 ──► CANCELLED（终态）
```

**转床与换主诊（免审批）状态流：**

```
  PENDING_APPLY ──► APPROVED（自动跳过审批）
                    │ execute
                    ▼
                 EXECUTING
                    │
                    ▼
                 EXECUTED
```

**设计要点：**

1. **为什么有 `EXECUTING` 这个中间状态？**
   执行转科要跨多个模块（M05-02 换床 → 本地更新 → M05-01 回写 → 异步通知）。若没有 `EXECUTING` 中间态，中途崩溃后无法区分「还没开始执行」与「执行到一半」。有中间态后定时任务可以扫「`EXECUTING` 且 `updated_at` 超过 30 分钟」的僵尸记录并回滚。

2. **为什么 `uk_m05_transfer_active` 用部分唯一索引？**
   同一住院单可以有多次历史转科（出院前的多次换床），但**同一时间只能有一个进行中的申请**。否则可能有两个申请同时审批通过，执行时互相覆盖。

3. **为什么 `to_dept_id` 在换主诊时也必填（= `from_dept_id`）？**
   保持字段一致性，查询「患者从哪个科室转到哪个科室」时无需判断类型。

4. **为什么 `total_nodes` 与 `approved_count` 冗余？**
   审批列表要显示「1/3 通过」，若每次 `COUNT(m05_transfer_approval WHERE status = 'APPROVED')` 会增加查询。冗余后直接读字段。

5. **为什么 `actual_at` 与 `executed_at` 分开？**
   `executed_at` 是系统执行时刻（点「执行」按钮那一刻），`actual_at` 是护士录入的实际转科时刻（患者真正被推到新病区可能是 10 分钟前）。业务报表用 `actual_at`，系统审计用 `executed_at`。

6. **为什么「转床必须同病区」在 DB 层也校验？**
   转床与转病区的审批规则不同（转床免审、转病区需审批）。若 DB 层不校验，应用层 bug 可能导致「标记为转床但实际跨病区」，绕过审批。

7. **为什么 `remark` 的最小长度按类型区分？**
   转床是物理位置调整，护士长确认即可，说明可短；转科/转院是责任与费用转移，说明必须详细（≥10 字）；转院涉及跨机构，说明更详细（≥20 字）。

| 项目 | 数值 |

| 年转科次数 | 约 1,100 行（15,000 住院 × 7.3% 有转科） |
| 15 年累计 | 约 16,500 行 |
| 单行平均长度 | 约 900 字节 |
| 表大小 | 约 15 MB |
| 索引大小 | 约 18 MB |

**分区：** 不分区。15 年 1.6 万行完全不需要。

```sql
-- 节点代码
ALTER TABLE m05_transfer_approval
    ADD CONSTRAINT ck_m05_approval_node

-- 节点状态
ALTER TABLE m05_transfer_approval
    ADD CONSTRAINT ck_m05_approval_status
    CHECK (status IN ('WAITING', 'PENDING', 'APPROVED', 'REJECTED',

-- 节点序号合理范围

    ADD CONSTRAINT ck_m05_approval_seq
    CHECK (seq_no >= 1 AND seq_no <= 10);

-- 已同意必须有审批人与同意时刻
ALTER TABLE m05_transfer_approval
    ADD CONSTRAINT ck_m05_approval_approved
    CHECK (status <> 'APPROVED'
           OR (approver_id IS NOT NULL AND approved_at IS NOT NULL));

-- 已驳回必须有审批人与驳回时刻及意见
ALTER TABLE m05_transfer_approval
    ADD CONSTRAINT ck_m05_approval_rejected
    CHECK (status <> 'REJECTED'
           OR (approver_id IS NOT NULL AND rejected_at IS NOT NULL
               AND opinion IS NOT NULL
               AND char_length(btrim(opinion)) >= 10));

-- 已跳过必须有跳过时刻
ALTER TABLE m05_transfer_approval
    ADD CONSTRAINT ck_m05_approval_skipped
    CHECK (status <> 'SKIPPED' OR (approved_at IS NOT NULL OR opinion IS NOT NULL));

-- 截止时刻必须晚于到达时刻

    ADD CONSTRAINT ck_m05_approval_deadline
    CHECK (deadline_at IS NULL OR arrived_at IS NULL
           OR deadline_at > arrived_at);

COMMENT ON TABLE m05_transfer_approval IS '转科审批节点表，一次转科 0~3 个节点';
```

**审批路径模板：**

| 转科类型 | 节点数 | 节点序列 |
|---|---|---|
| `CHANGE_BED` | 0 | —（免审批） |
| `CHANGE_WARD` | 2 | `OUT_DEPT` → `IN_DEPT` |
| `CHANGE_DEPT` | 3 | `OUT_DEPT` → `IN_DEPT` → `MEDICAL` |
| `CHANGE_DOCTOR` | 0 | —（免审批） |
| `TRANSFER_OUT` | 1 | `MEDICAL` |

**设计要点：**

1. **为什么审批节点独立成表而非 JSONB？**
   - 需要按审批人查待办（`idx_m05_approval_pending`），JSONB 无法高效索引
   - 需要按状态更新（同意/驳回），JSONB 整体重写有风险
   - 审批链结构化存储，审计时能明确每个节点谁在什么时刻做了什么

2. **为什么不建外键到 `m05_transfer`？**
   与全模块一致（不建外键）。但 `m05_transfer_approval` 是子表，删除主表时应用层必须同时软删子表（`ON DELETE` 行为由应用层控制）。

3. **为什么 `required_role` 而非 `approver_id` 在创建时填写？**
   转病区时，转入科室主任是谁在创建申请时可能还不确定（转入科室还没确定具体哪个主任）。`required_role` 是角色，`approver_id` 在审批时确定。

4. **`SKIPPED` 状态的用途**
   若转出与转入是同一科室（转病区），`OUT_DEPT` 与 `IN_DEPT` 可能是同一个主任。系统允许「第一次审批时勾选『同一主任，同时批准两节点』」，第二个节点置 `SKIPPED`。这样不违反「不能重复审批」，又减少一次点击。

**设计要点：**

1. **为什么 `stay_days` 在 DB 层用约束保证（而非应用层计算）？**
   住院天数是医保结算的核心依据，算错会直接导致医保拒付。DB 层约束 `stay_days = (discharge_date - admission_date) + 1` 保证任何写入路径都不会算错。

2. **为什么 `summary_status` 与 `summary_exempt` 两个字段？**
   `summary_status` 表示「小结写到哪一步」，`summary_exempt` 表示「是否允许不写」。两者组合：
   - `summary_status = 'PENDING'` + `summary_exempt = FALSE`：必须写但还没开始
   - `summary_status = 'SIGNED'` + `summary_exempt = FALSE`：正常完成
   - `summary_status = 'EXEMPT'` + `summary_exempt = TRUE`：豁免
   若合并为单字段，无法表达「死亡患者的小结可能事后补写」的场景（出院时豁免，事后补写后状态回 `SIGNED`，但 `summary_exempt` 仍为 TRUE 供审计）。

3. **为什么 `settle_status` 有 `OWED` 状态？**
   「欠费出院」是客观存在的：患者要求先走，费用后付。`OWED` 表示已出院但费用未结清。这种状态下 `m05_stay.stay_status` 是 `CLOSED`（床位已释放），但 `m05_admission.settle_status` 是 `DISCHARGED_OWED`。

4. **为什么 `archived_status` 在 `m05_discharge` 而非在 M05-05？**
   M05-05 负责病案归档流程，但「是否已归档」这个状态需要在本表上才能被出院记录列表直接展示（否则每次列表要 JOIN M05-05 的归档表）。M05-05 在归档完成后回写此字段。

5. **为什么签字信息（`patient_signature` / `signer_name` / `signer_relation`）存本表？**
   出院登记是患者离院的最后一道手续，签字具有法律效力。存本表避免与 M07-06 文书混在一起（M07-06 管医生签字的文书，本表管患者签字的离院确认）。

6. **为什么 `medical_record_no`（病案号）允许为空？**
   出院登记时还没有病案号（病案室归档时才分配）。`archived_status = 'ARCHIVED'` 时 DB 约束强制非空。

### E.3 分区建表脚本（`m05_stay_log`）

```sql
CREATE TABLE m05_stay_log (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY,
    stay_id             BIGINT NOT NULL,
    stay_no             VARCHAR(32) NOT NULL,
    admission_id        BIGINT NOT NULL,
    admission_no        VARCHAR(32) NOT NULL,
    patient_id          BIGINT NOT NULL,
    patient_name        VARCHAR(64),
    ward_id             BIGINT,
    bed_no              VARCHAR(16),
    change_type         VARCHAR(24) NOT NULL,
    field_name          VARCHAR(64),
    old_value           VARCHAR(512),
    new_value           VARCHAR(512),
    reason              VARCHAR(512),
    related_id          BIGINT,
    changed_by          BIGINT NOT NULL,
    changed_by_name     VARCHAR(64),
    changed_at          TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    client_ip           VARCHAR(64),
    trace_id            VARCHAR(64),
    PRIMARY KEY (id, changed_at)
) PARTITION BY RANGE (changed_at);

DO $$
DECLARE
    i          INT;
    start_date DATE;
    end_date   DATE;
    part_name  TEXT;
BEGIN
    FOR i IN 0..59 LOOP
        start_date := (DATE_TRUNC('month', CURRENT_DATE)
                       + (i || ' months')::INTERVAL);
        end_date := start_date + INTERVAL '1 month';
        part_name := 'm05_stay_log_p' || TO_CHAR(start_date, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m05_stay_log '
            'FOR VALUES FROM (%L) TO (%L)',
            part_name, start_date, end_date
        );
    END LOOP;
END $$;
```

**为什么主键是 `(id, changed_at)`：**
PostgreSQL 要求分区表主键包含分区键。业务查询走 `stay_id + changed_at` 或 `admission_id + changed_at`，不依赖主键，改为复合主键无影响。
