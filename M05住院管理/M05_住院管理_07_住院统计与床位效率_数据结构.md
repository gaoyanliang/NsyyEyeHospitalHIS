## 4. 数据结构设计

### 4.1 ER 关系图

**设计说明：**

1. **`m05_stat_daily` 是核心，采用「三级同表」设计。** 全院、科室、病区三级统计用同一个表，通过 `stat_level` 区分，`scope_id` 存科室/病区 ID（全院级为 NULL）。理由：①三级的结构完全一致（同样的 L0 基础量）；②查询时可按层级过滤，无需 UNION；③新增「按医师」「按病种」等维度时，只需增加 `stat_level` 枚举值。
2. **`m05_ward_daily` 与 `m05_stat_daily` 的 WARD 级看似重复。** 实际上 `m05_stat_daily` 的 WARD 级只存 L0 汇总值，而 `m05_ward_daily` 存病区特有的加床明细、床位占用分布、清洁周转时长等，字段结构不同，不能合并。
3. **`m05_bed_efficiency` 存四种算法的计算结果。** 4.4 节会列出全部 4 种算法（A/B/C/D），因为报表需要同时展示对照。这本可以在查询时实时计算，但落库的好处是：①历史快照冻结当时算法与结果，算法定义调整后历史报表不变；②排名需要跨行比较，落库后可建索引排序。
4. **`m05_discharge_stat` 是「长表」而非「宽表」。** 出院者构成有 8 个维度（离院方式、性别、年龄组、费用区间、住院日区间、医保类型、入院途径、是否手术），每维度 3~11 个取值。若做成宽表需要 60+ 列，且每加一个维度就要 ALTER TABLE；用 `(dim_type, dim_code)` 长表结构，加维度只是插数据。
5. **`m05_stat_config` 独立无业务关联。** 参数表不参与业务 JOIN，只被服务层读取缓存。
6. **不建物理外键。** `scope_id`、`dept_id`、`ward_id` 都是逻辑引用。理由：①统计表由定时任务批量写入，外键检查会显著拖慢；②数据归档时无外键解耦更简单；③跨模块外键在本架构下无法建立。

### 4.2 表：`m05_stat_daily`（住院统计日快照表）

**用途：** 存储全院/科室/病区三级、每日的住院统计 L0 基础量。是全院住院指标的**唯一数据来源**，所有 L1/L2 派生指标都从这里计算。数据一经发布即不可修改。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | `BIGINT` | 否 | 自增 | 主键 |
| `stat_date` | `DATE` | 否 | — | 统计日期（T-1 日） |
| `stat_level` | `VARCHAR(16)` | 否 | — | 统计层级：`HOSPITAL` / `DEPT` / `WARD` |
| `scope_id` | `BIGINT` | 是 | NULL | 层级对象 ID（科室 ID 或病区 ID），全院级为 NULL |
| `scope_name` | `VARCHAR(100)` | 是 | NULL | 层级对象名称（快照，防止主数据变更后历史报表失真） |
| `parent_dept_id` | `BIGINT` | 是 | NULL | 病区级时的上级科室 ID |
| `parent_dept_name` | `VARCHAR(100)` | 是 | NULL | 上级科室名称（快照） |
| **L0 床位量** | | | | |

| `extra_beds` | `INTEGER` | 否 | `0` | 加床数 |
| `package_beds` | `INTEGER` | 否 | `0` | 包床数 |
| `occupied_beds` | `INTEGER` | 否 | `0` | 占用床位数（日末快照） |
| `open_bed_days` | `INTEGER` | 否 | `0` | 开放床日（当日） |
| `occupied_bed_days` | `INTEGER` | 否 | `0` | 实际占用床日（当日） |
| `extra_bed_days` | `INTEGER` | 否 | `0` | 加床床日（当日） |
| `package_bed_days` | `INTEGER` | 否 | `0` | 包床床日（当日） |
| **L0 患者量** | | | | |
| `in_hospital_count` | `INTEGER` | 否 | `0` | 在院人数（日末） |

| `death_count` | `INTEGER` | 否 | `0` | 死亡人数（当日） |
| `discharged_bed_days` | `INTEGER` | 否 | `0` | 出院者占用总床日（当日出院患者） |
| `transfer_in_count` | `INTEGER` | 否 | `0` | 转入人次（当日） |
| `transfer_out_count` | `INTEGER` | 否 | `0` | 转出人次（当日） |
| `bed_move_count` | `INTEGER` | 否 | `0` | 转床人次（当日） |
| **L0 手术与病案** | | | | |

| `home_grade_a_count` | `INTEGER` | 否 | `0` | 病案首页甲级份数 |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m05_stat_daily` | 主键 | `id` | — |
| **`uk_m05_stat_daily_key`** | 唯一 | `(stat_date, stat_level, COALESCE(scope_id, 0)) WHERE is_deleted=FALSE` | **三级快照唯一** |

**约束说明：**

```sql
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT pk_m05_stat_daily PRIMARY KEY (id);

-- 三级快照唯一（COALESCE 处理全院级 scope_id 为 NULL）
CREATE UNIQUE INDEX uk_m05_stat_daily_key
    ON m05_stat_daily (stat_date, stat_level, COALESCE(scope_id, 0))
    WHERE is_deleted = FALSE;

-- 统计层级枚举
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_level
    CHECK (stat_level IN ('HOSPITAL', 'DEPT', 'WARD'));

-- 层级与 scope_id 一致性：全院级必须 NULL，其他必须非空
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_scope
    CHECK ((stat_level = 'HOSPITAL' AND scope_id IS NULL)
           OR (stat_level <> 'HOSPITAL' AND scope_id IS NOT NULL));

-- 病区级必须有上级科室
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_parent
    CHECK (stat_level <> 'WARD' OR parent_dept_id IS NOT NULL);

-- 床位量非负且关系合理
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_beds_nonneg
    CHECK (total_beds >= 0 AND open_beds >= 0 AND extra_beds >= 0
           AND package_beds >= 0 AND occupied_beds >= 0
           AND open_bed_days >= 0 AND occupied_bed_days >= 0
           AND extra_bed_days >= 0 AND package_bed_days >= 0);

ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_beds_relation
    CHECK (open_beds <= total_beds AND extra_beds <= open_beds
           AND package_beds <= open_beds);

ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_days_relation
    CHECK (extra_bed_days <= open_bed_days
           AND package_bed_days <= open_bed_days);

-- 患者量非负
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_patients_nonneg
    CHECK (in_hospital_count >= 0 AND admission_count >= 0
           AND discharge_count >= 0 AND death_count >= 0
           AND discharged_bed_days >= 0
           AND transfer_in_count >= 0 AND transfer_out_count >= 0
           AND bed_move_count >= 0
           AND operation_count >= 0 AND home_completed_count >= 0
           AND home_grade_a_count >= 0 AND drg_group_count >= 0);

-- 死亡人数不超过出院人数
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_death
    CHECK (death_count <= discharge_count);

-- 甲级份数不超过已审核份数
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_grade
    CHECK (home_grade_a_count <= home_completed_count);

-- 手术例数不超过出院人数
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_op
    CHECK (operation_count <= discharge_count);

-- 使用率合理区间（允许加床时略超 100%）
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_usage_rate
    CHECK (bed_usage_rate IS NULL OR (bed_usage_rate >= 0 AND bed_usage_rate <= 2.0));

-- 平均住院日合理
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_stay_days
    CHECK (avg_stay_days IS NULL OR (avg_stay_days >= 0 AND avg_stay_days <= 365));

-- 加床占比 0~1
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_extra_ratio
    CHECK (extra_bed_ratio IS NULL OR (extra_bed_ratio >= 0 AND extra_bed_ratio <= 1));

-- 手术占比 0~1
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_op_ratio
    CHECK (operation_ratio IS NULL OR (operation_ratio >= 0 AND operation_ratio <= 1));

-- 状态枚举
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_status
    CHECK (status IN ('PENDING', 'COLLECTING', 'COLLECTED', 'VERIFIED',
                      'PUBLISHED', 'ABNORMAL', 'FAILED', 'RECALC'));

-- 算法枚举
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_algorithm
    CHECK (algorithm IN ('A', 'B', 'C', 'D'));

-- 计算版本合理
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_version
    CHECK (calc_version >= 1);

-- 已发布必须有发布时间
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_published
    CHECK (status <> 'PUBLISHED'
           OR (published_at IS NOT NULL AND collected_at IS NOT NULL));

-- 人工发布必须留痕
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_manual_publish
    CHECK (status <> 'PUBLISHED' OR published_by IS NULL
           OR (publish_note IS NOT NULL AND char_length(btrim(publish_note)) >= 5));

-- 异常必须有原因
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_abnormal
    CHECK (status <> 'ABNORMAL'
           OR (abnormal_reason IS NOT NULL AND char_length(btrim(abnormal_reason)) >= 5));

-- 降级必须有原因
ALTER TABLE m05_stat_daily
    ADD CONSTRAINT ck_m05_stat_daily_degraded
    CHECK (data_degraded = FALSE
           OR (degraded_reason IS NOT NULL AND char_length(btrim(degraded_reason)) >= 5));

-- 注释

**状态机：**

```
   ┌──────────┐
   │ PENDING  │  当日 00:30 前（尚未采集）
   └────┬─────┘
        │ 00:30 APScheduler 触发
        ▼
   ┌──────────┐
   │COLLECTING│  采集中
   └────┬─────┘
        │ 采集成功              │ 采集失败
        ▼                       ▼
   ┌──────────┐            ┌──────────┐
   │COLLECTED │            │  FAILED  │
   └────┬─────┘            └────┬─────┘
        │ 三项校验               │ 重试 3 次
        │                       │
   ┌────┴─────┐                 │
   │          │                 │
   ▼          ▼                 │
┌────────┐ ┌──────────┐         │
│VERIFIED│ │ ABNORMAL │◄────────┘
└───┬────┘ └────┬─────┘
    │ 自动/手动   │ 手动确认后发布
    ▼            ▼
  ┌───────────────┐
  │   PUBLISHED   │  对外可见、不可修改
  └───────┬───────┘
          │ 重算（生成新 calc_version）
          ▼
     ┌──────────┐
     │  RECALC  │ ──► COLLECTED（重算完成）
     └──────────┘
```

**设计要点：**

1. **为什么 L1 派生指标也落库。** 虽然 L1（使用率、平均住院日等）完全可以由 L0 实时计算，但落库有三个好处：①「科室使用率排行」需要 `ORDER BY bed_usage_rate`，落库后可建索引；②跨日/跨期聚合时，直接用日快照的派生值做加权平均比重新算更直观；③与外部系统（M22 报表、等级评审）交互时，标准字段直接可取。代价是需要在采集时确保 L1 与 L0 一致——这点由 `ck_` 约束与采集代码保证。
2. **`scope_name` / `parent_dept_name` 冗余名称。** 科室名可能变更（如「眼一科」改「眼底病科」），若只存 `dept_id`，历史报表会显示新名称。快照当时名称，历史报表才真实。
3. **`uk_m05_stat_daily_key` 用 `COALESCE(scope_id, 0)`。** PostgreSQL 唯一索引认为 `NULL` 互不相等，全院级 `scope_id=NULL` 可以插入两次，导致「同一天两条全院快照」。`COALESCE(scope_id, 0)` 把 NULL 归一化为 0（0 不是合法科室/病区 ID），全版本兼容（PG 14 无 `NULLS NOT DISTINCT`）。
4. **`ck_m05_stat_daily_usage_rate` 上限设为 2.0（200%）而非 1.0。** 加床场景下占用床日可以超过开放床日，例如开放 40 床但收治 45 人（加床 5 张但加床未计入开放）。若上限设为 1.0，加床日会被判非法。200% 是理论极限，超过必然是数据错误。
5. **「人工发布必须留痕」的约束。** `published_by` 非空时必须有 ≥5 字的说明，防止「手一抖就发布」。这条约束把「发布」这个敏感动作的审计从应用层下沉到数据库。
6. **为什么不分区。** 15 年 × 3 级 × 约 200 个对象/天 ≈ 330 万行。`uk_m05_stat_daily_key` 必须跨年生效（若按年分区则唯一索引须含分区键，「同日同层级同对象唯一」会退化为「同年唯一」）。330 万行完全在 PG 单表舒适区间（< 5,000 万行），加分区反而增加管理成本。

ALTER TABLE m05_ward_daily
    ADD CONSTRAINT pk_m05_ward_daily PRIMARY KEY (id);

    WHERE is_deleted = FALSE;

    CHECK (occupied_beds + empty_beds + cleaning_beds + disabled_beds = total_beds);

    ADD CONSTRAINT ck_m05_ward_daily_beds_nonneg

           AND occupied_beds >= 0 AND empty_beds >= 0

ALTER TABLE m05_ward_daily

-- 周转量非负
ALTER TABLE m05_ward_daily
    ADD CONSTRAINT ck_m05_ward_daily_flow
    CHECK (admission_count >= 0 AND discharge_count >= 0
           AND transfer_count >= 0 AND bed_move_count >= 0
           AND bed_turnover_count >= 0);

-- 清洁任务数关系
ALTER TABLE m05_ward_daily
    ADD CONSTRAINT ck_m05_ward_daily_clean
    CHECK (clean_total_count >= 0 AND clean_timeout_count >= 0
           AND clean_timeout_count <= clean_total_count);

-- 清洁时长合理
ALTER TABLE m05_ward_daily
    ADD CONSTRAINT ck_m05_ward_daily_clean_minutes

-- 峰值小时 0~23
ALTER TABLE m05_ward_daily

    ADD CONSTRAINT ck_m05_ward_daily_usage

-- 清洁效率 0~1

           OR (clean_efficiency >= 0 AND clean_efficiency <= 1));

COMMENT ON COLUMN m05_ward_daily.bed_turnover_count IS '当日床位周转次数 = 出院人数 + 转出人次';
```

**设计要点：**

1. **`ck_m05_ward_daily_bed_sum` 是病区统计可信度的核心。** 「占用 + 空床 + 清洁中 + 停用 = 实有」这条恒等式必须成立，否则说明床位状态采集遗漏。病区护士长看日报第一眼就是这个数，一旦平不了账，整份报表都不可信。
2. **`hourly_occupied` 用 JSONB 存 24 小时占用曲线。** 用 24 个独立列（`h00_occupied` ~ `h23_occupied`）会让表宽到 50+ 列且增加字段时需 ALTER；用 JSONB 数组，读写都是一次操作，且能直接给前端画图。代价是无法对单个小时建索引——但业务上从不「查所有病区的第 14 点占用」，所以无影响。
3. **`extra_bed_reason_breakdown` 用 JSONB 存加床原因。** 加床原因有 4 类（`EMERGENCY` 急诊、`OVER_CAPACITY` 超收、`BED_SHORTAGE` 床位不足、`VIP` 特殊需求），做成 JSONB 便于按原因统计且不占用固定列。
4. **`clean_efficiency` 衡量床位周转的后台能力。** 眼科日间手术多、周转快，清洁不及时会直接卡住下一台。`CLEAN_TIMEOUT_MINUTES=30` 是参数，超时率超过 20% 说明后勤跟不上。
5. **`peak_occupied <= total_beds + extra_beds`。** 峰值占用不可能超过「实有 + 加床」，这是逻辑上限。若触犯说明采样有误。

| 15 年行数 | 约 109,500 |

**设计要点：**

1. **为什么四种算法都落库。** 主推算法 A，但 B/C/D 是「对照口径」。当科室主任质疑「我们病区明明很忙，怎么使用率才 75%」时，可以直接展示 C（有效使用率）86%，说明差异来自加床。若只存 A，无法解释差异，指标就失去说服力。实测 A 与 C 差最多 10 个百分点以上。
2. **`algorithm_used` 与四个结果字段并存。** `algorithm_used` 记录「采集时全院统一用的哪种算法」，是报表页脚「口径：算法 A」的来源；四个结果字段是「四种都算了」。若只存 `algorithm_used`，切换口径后历史报表会变成「当时用什么算的」，无法回溯对照。
3. **`rank_in_parent` 与 `rank_in_hospital` 两级排名。** 病区排名既要在本科室内比（`rank_in_parent`：眼一科病区 vs 眼二科病区），也要在全院比（`rank_in_hospital`：全部 20 个病区）。两个口径用途不同，都保留。
4. **`efficiency_level` 与 `efficiency_score` 双字段。** 评级是给管理者的「一眼结论」（优秀/良好/一般/偏低/告警），评分是给排序与考核的精确值。评分模型：使用率 40 分 + 周转 30 分 + 平均住院日 20 分 + 加床控制 10 分，各维度按阈值线性映射。
5. **`usage_rate_d` 特殊说明。** 算法 D 的数值（约 9.5%）因为分母是「平均开放床位 × 出院人数」，与 A/B/C 完全不同量级，**不能与 A/B/C 横向比较**。文档 3.5 节已说明，但数据库层面无法约束，需要报表端标注。
6. **`uk_m05_bed_eff_key` 用 `COALESCE(scope_id, 0)`**，原因与 `m05_stat_daily` 相同：全院级 `scope_id=NULL` 的唯一性问题。

**8 个维度定义：**

| dim_type | 中文 | 取值示例 | 区间型 |
|---|---|---|---|

| `COST_RANGE` | 费用区间 | `0-2000` / `2001-5000` / `5001-10000` / `10001-20000` / `20000+` | ✅ |
| `STAY_RANGE` | 住院日区间 | `1` / `2-3` / `4-7` / `8-14` / `15+` | ✅ |
| `INSURANCE_TYPE` | 医保类型 | `URBAN_EMPLOYEE` / `URBAN_RESIDENT` / `RURAL_COOP` / `COMMERCIAL` / `SELF_PAY` / `OTHER` | ❌ |
| `ADMISSION_WAY` | 入院途径 | `OUTPATIENT` / `EMERGENCY` / `TRANSFER_IN` / `OTHER` | ❌ |
| `OPERATION_FLAG` | 是否手术 | `Y` / `N` | ❌ |

**设计要点：**

1. **长表 vs 宽表的取舍。** 若用宽表，8 个维度 × 平均 5 个取值 = 40 个「取值计数字段」+ 40 个「占比字段」= 80 列，且每加一个维度就要 ALTER TABLE。用长表，加维度就是插几行数据。代价是查询时需 `WHERE dim_type='DISCHARGE_TYPE'` 过滤——但这正是最常用的查询模式，配合索引完全无压力。
2. **`ck_m05_discharge_stat_limit` 保证分项不超过总数。** 这是长表最容易出的一类错误：「同一维度下各取值之和 > 总数」说明统计逻辑重复计数（如一个患者同时满足两个条件）。约束不能直接保证「之和 = 总数」（跨行），但至少拦住了「抄错数」。
3. **区间型维度存 `dim_value_min` / `dim_value_max`。** 因为「65-79 岁」这类区间在 `dim_code` 里是字符串，无法排序与比较。存上下限后，前端可正确排序，也便于「按年龄组算加权平均」。
4. **`item_bed_days` 与 `item_amount` 让构成分析有深度。** 不只是「多少人的离院方式是医嘱离院」，还能算「医嘱离院患者平均住院日」「自费患者次均费用」，一张表满足多种透视需求。
5. **不设 `status` 字段。** 构成统计随日快照一起冻结，`m05_stat_daily.status` 已是权威状态。重复存一遍会有一致性风险。

**量级估算：**

| 项目 | 估算 |
|---|---|
| 维度数 | 8 |
| 每维度平均取值数 | 5.5 |
| 每日对象数 | 1（全院）+ 12（科室）= 13 |
| 每日行数 | 13 × 8 × 5.5 ≈ 572 |
| 年行数 | 约 208,780 |
| 15 年行数 | 约 3,131,700 |
| 单行大小 | 约 220 B |
| 15 年数据量 | 约 690 MB |
| 含索引 | 约 1.6 GB |

**分区：** 不分区。理由：①虽然 313 万行较大，但 `uk_m05_discharge_stat_key` 需跨年生效；②主要查询是「某日某维度构成」，命中 `idx_m05_discharge_stat_date`；③若未来需归档，按 `stat_date` 年归档即可。

**优化建议：** 科室级构成统计（12 个科室 × 8 维度 × 5.5 ≈ 528 行/日）占总行数的 92%，但业务上科室构成图很少查。可考虑只保留全院级 `dept_id IS NULL`（44 行/日，年 16,060 行）与月度/年度科室级聚合，日级科室构成按需实时算。这样 15 年行数降到约 24 万。

**参数读取优先级：**

```
科室级（scope='DEPT' AND scope_id=当前科室）
    │ 未命中
    ▼
全局级（scope='GLOBAL'）
    │ 未命中
    ▼
default_value（出厂默认值）
    │ 未命中
    ▼
代码常量
```

**为什么 `UNFREEZE_NEED_DOUBLE_SIGN` 不可编辑：** 解冻意味着「财务已封账的历史数据可以重算」，这是审计红线。若允许配置成 `false`，等于给了「一人就能改历史账」的口子。

**量级估算：** 30 条固定 + 少量科室覆盖（假设 10 个科室各覆盖 2 条）= 50 条，永久保留，约 30 KB。

**分区：** 不分区（极小表）。

| `idx_m05_bed_eff_rank` | `m05_bed_efficiency` | 按排名取前 20，需全表排序 | 约 20 行 | **约 200 倍** |
| `idx_m05_stat_daily_scope` | `m05_stat_daily` | 18 万行 / 约 35ms（含全院级） | 约 16 万行 / 约 30ms | 1.2 倍（意义有限） |

**为什么统计表的部分索引收益特别大：** 「待采集」「异常」「待发布」「降级」这几类状态在稳态下几乎为空——每天只有 1~2 天处于这些状态。`idx_m05_stat_daily_status` 的部分索引让「找待处理的天」从扫 18 万行变成扫 1~2 行。运维监控看板每 5 分钟查询一次，一天 288 次，全表扫就是 6.3 GB 的 I/O。

**`idx_m05_bed_eff_alert` 的 500 倍收益最显著**：评级为 `ALERT` 的病区在稳态下只有 2~3 个（20 个病区中），但历史累积 19 万行。管理者最关心「哪些病区告警」，这个查询必须快。

**`idx_m05_stat_daily_scope` 不值得保留的理由**：虽然建了部分索引（`scope_id IS NOT NULL`），但全院级只有 1/33 的行，剔除后仍需扫 97% 的数据，收益仅 1.2 倍。真正有效的是 `idx_m05_stat_daily_level`（`(stat_level, stat_date)`），因为查询「某科室的历史」时 `stat_level='DEPT' AND scope_id=101`，先按 `stat_level` 过滤到 1/3，再过滤 `scope_id`。

**关键参数说明：**

| 参数 | 为什么重要 |
|---|---|
| `M05.STAT.ALGORITHM` | 全院统一口径，决定所有报表「床位使用率」的取值。改动需二次确认，且不影响历史快照 |
| `M05.STAT.MOM_DEVIATION_LIMIT` | 环比异常检测阈值。太小会天天告警（周末/节假日波动正常），太大会漏掉真实异常。默认 30% |
| `M05.STAT.INCLUDE_DAY_SURGERY` | 日间手术不过夜、不占床日，默认 `false`。若设为 `true`，周转次数会虚高、平均住院日会虚低 |
| `M05.STAT.INCLUDE_PACKAGE_BED` | 包床是医院主动预留不用的床位，默认 `false`。设为 `true` 会使使用率虚高 |
| `M05.STAT.UNFREEZE_NEED_DOUBLE_SIGN` | 财务封账后解冻的双签开关，`is_editable=false` 锁定为 `true`，防一人改历史账 |
| `M05.STAT.EXPORT_SYNC_MAX_ROWS` | 超过此行走异步，避免前端等 30 秒以上超时。默认 5 万行 |

| # | 检查项 | 说明 |
|---|---|---|
| 1 | m05_sta_001 ~ 006 七个迁移脚本已执行 | `SELECT count(*) FROM alembic_version` 校验版本 |
| 2 | 30 条参数已预置 | `SELECT count(*) FROM m05_stat_config WHERE is_deleted=FALSE` 应为 30 |
| 3 | `M05.STAT.ALGORITHM` 已确认为 `A` | 全院统一口径 |
| 4 | M05-01/02/03 接口已联通 | `/internal/v1/m05/admission/stats/daily` 等可返回 |
| 5 | APScheduler 采集任务已注册 | `job_m05_stat_collect` cron `30 0 * * *` |
| 6 | **首日采集验证** | 上线 T+1 日 00:30 检查三级快照是否全部生成（1+12+20=33 行） |
| 7 | **内部一致性验证** | `Σ科室 open_bed_days = 全院 open_bed_days`，不等则查床位归属 |
| 8 | **四种算法结果交叉验证** | 同一区间 A/B/C/D 四种算法都能算出，差值符合预期（A 与 C 差约加床比例） |
| 9 | 历史数据追溯方案已定 | 若需导入历史统计，需保证 `uk_m05_stat_daily_key` 不冲突 |
| 10 | 报表模板已与 M22 联调 | XLSX/PDF 版式与院方要求一致 |
| 11 | 等级评审指标映射已确认 | I-01~I-32 与评审细则的对应关系 |
| 12 | 分级权限已配置 | 科室主任只能看本科室（`m05:stat:drill` 需单独授权） |

**第 6 项最关键：** 首日采集若只生成了全院级（1 行）而缺科室/病区级，说明 `_collect_depts` 或 `_collect_wards` 的 SQL 关联 M01-01/M01-13 失败，此时所有科室报表为空，且要等到第二天才能发现。建议上线首日人工触发 `POST /api/v1/m05/stat/recalc` 验证。

**第 8 项的理由：** 四种算法必须都能算出结果。若 `usage_rate_c` 为空，说明 `extra_bed_days` 未正确采集（`open_bed_days - extra_bed_days` 分母为 0 时算法 C 无法计算）；若 `usage_rate_d` 为空，说明 `discharged_bed_days` 或 `discharge_count` 为 0。这比等到用户提问「为什么算法 C 没数」再排查要快得多。
