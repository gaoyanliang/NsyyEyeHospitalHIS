## 1. 模块概述

### 1.1 一句话定位

**M05 回答「这个患者现在是不是住在我们医院、住在哪个床、由谁管、住了多久、能不能出院」，并管住从入院到出院这条链上的每一次床位流转。**

### 1.2 为什么 M05 是模块而不是 M04 的一个分支

| 维度 | 门诊（M04） | 住院（M05） |
|---|---|---|
| 时间跨度 | 分钟级（一次就诊 10~30 分钟） | **天级**（眼科平均 5~7 天） |
| 空间归属 | 诊室（患者来医院） | **床位**（患者住医院） |
| 主键 | 挂号单 `registration_id` | **住院号 `admission_id`** |
| 核心资源 | 号源、诊室 | **床位**（有限且必须独占） |
| 费用模式 | 先付费后诊疗 | **先交预交金、诊疗后结算** |
| 责任归属 | 接诊医生 | **责任医生 + 责任护士 + 病区** |
| 状态数量 | 5 态（挂号状态机） | **13 态住院单 + 6 态床位 + 4 态在院** |

**四条独立理由：**

1. **核心资源完全不同。** 门诊卖的是「号源」，是一天内的时段切片；住院卖的是「床位」，是持续占用且有独占性——同一张床同一时刻只能有一个患者。号源超卖扣分了事，床位超卖患者就无处安置。
2. **住院有门诊完全不存在的「床位流转」。** 入院分床、转床、转科、包床、加床、离院占床、床位消毒——这一整套是住院管理的核心工作量，门诊没有任何对应概念。
3. **住院有独立的法定文书体系。** 住院病案首页、入院记录、出院小结、住院医嘱单——完整性检查、归档、保存期限都由住院规则决定。**病案首页是 DRG/DIP 支付的数据基础，直接决定医院收入。**
4. **费用模型不同。** 住院是「预交金 + 记账 + 出院结算」三段式，存在「欠费」这个门诊不存在的状态；床位费按天自动计费，需要每日定时任务。

### 1.4 概念辨析

| 概念 A | 概念 B | 区别 |
|---|---|---|
| **住院号 `admission_no`** | **住院单 `admission_id`** | 住院号是业务编号（可读），`admission_id` 是数据库主键 |
| **入院申请 `admission_request`** | **住院单 `admission`** | 申请是「医生开的住院证」，住院单是「患者真的住进来了」 |
| **分床 `bed_assign`** | **转床 `bed_change`** | 分床是首次占床，转床是已占床患者换床 |
| **转床** | **转科** | 转床是同病区内换床；转科是换科室（连带换病区、换床位、换主诊） |
| **预出院 `PENDING_DISCHARGE`** | **已出院 `DISCHARGED`** | 预出院 = 医生下了出院医嘱但手续未办；已出院 = 手续办完床位已释放 |
| **已出院 `DISCHARGED`** | **已结算 `SETTLED`** | 出院是临床动作（可先走），结算是财务动作（可后补）。**两状态必须分开**，否则床位上永远显示占用 |
| **归档 `archive`** | **结算 `settle`** | 归档管病历完整性，结算管钱。两者互不阻塞——欠费出院也能归档，未归档也能结算 |
| **病案首页** | **出院小结** | 首页是结构化数据（DRG 用），小结是叙述性文书（医生写） |
| **包床** | **加床** | 包床 = 单人房独占（仍按 1 床收费）；加床 = 走廊临时增设的床（眼科极少用，因需陪护空间） |

### 1.5 模块目标

| 指标 | 目标值 | 度量方式 |
|---|---|---|
| 入院登记平均耗时 | ≤ 4 分钟/人 | P50 埋点 |
| 入院登记 P95 响应 | ≤ 500ms | APM |
| 分床到入科 | ≤ 15 分钟 | `bed.occupied_at − registered_at` |
| 出院办理平均耗时 | ≤ 6 分钟/人 | P50 埋点 |
| 出院结算 P95 响应 | ≤ 3s（含 M16-03 往返） | APM |
| 病历 24h 归档率 | ≥ 95% | 归档时效分布 |
| 病案首页 3 日完成率 | ≥ 98% | 首页填报时长 |
| 床位使用率统计误差 | ≤ 0.5% | 与财务口径对账 |
| 重复分床事故 | **0** | 数据库唯一索引保证 |
| 一床两患者事故 | **0** | `uk_m05_bed_current_admission` 保证 |
| 一住院单两在院记录 | **0** | `uk_m05_stay_admission` 保证 |
| 住院号重复 | **0** | `uk_m05_admission_no` 保证 |

### 2.3 六条拆分主线

#### 主线一：按「一次住院的时间轴」分，不按功能清单分

```
[想住院] ─①入院登记─► [已登记] ─②分床─► [在院]
                                           │
              ┌────────────────────────────┼──────────────────┐
              ▼                            ▼                  ▼
        ③转床/转科                   ④在院日常管理        ⑤费用催缴
              │                            │                  │
              └────────────────────────────┴──────────────────┘
                                           ▼
                                  ⑥出院办理 ─► [已出院]
                                           ▼
                                  ⑦病案首页 ─► [已归档]
                                           ▼
                                  ⑧统计 ───► [床位释放]
```

**为什么按时间轴而不按功能分：** 如果按「床位管理」「转科管理」「出院管理」分，每个子模块都要写 `m05_admission` 主表，都会产生「谁能改这个字段」的争议。按时间轴分，每个环节有明确的输入状态与输出状态，主表字段的写入权归属清晰。

| 环节 | 主责人 | 可逆性 | 关键约束 |
|---|---|---|---|
| ① 入院登记 | 住院处收费员 | 可作废（未入科前） | 需先交预交金 |
| ② 分床 | 病区护士 / 住院处 | 可退床 | **床位必须空闲** |
| ③ 转床转科 | 病区护士长 | 可撤销（执行前） | 需原病区与新病区双确认 |
| ④ 在院日常 | 责任医生 / 责任护士 | — | 病情等级影响护理费 |
| ⑤ 费用催缴 | 住院处 | — | 预交金不足需提醒 |
| ⑥ 出院办理 | 责任医生 + 住院处 | **结算后不可逆** | 必须已结算或已审批欠费 |
| ⑦ 病案首页 | 病案室编码员 | 可修改（限 7 天内） | 需通过 12 项质控 |
| ⑧ 统计 | 系统 | — | 床日数按自然日切分 |

#### 主线二：床位必须独立成子模块

**四条理由：**

1. **M01 只有「床位类型」，没有「床位实例」。** M01-13 明确写「床位明细（具体床位号）归 **M05 住院管理**」。M01 的 `md_ward.bed_count` 是规划床位，`actual_bed_count` 由 M05 维护，但具体床位台账在 M05。
2. **床位的状态变化频率远高于患者状态。** 一张床一年被 60 个患者轮流使用，每次都有「空 → 预约 → 占用 → 预出院 → 消毒 → 空」的循环。床位状态与患者状态放一张表，患者出院后那条记录就无意义了，但床位还在。
3. **床位的独占性需要数据库级保障。** 同一床同一时刻只能一个患者——这必须用唯一索引 `uk_m05_bed_current_admission` 而不是应用层检查，否则两个护士同时分床就会一张床两个人。
4. **床位是医院最贵的资源之一，需要独立的管理视图。** 床位使用率、周转次数、平均住院日是医院核心 KPI。

#### 主线三：M05 不管钱，但必须管「钱的状态」

M05 **不实现**任何金额计算、预交金存取、费用明细、结算——这些全在 M16-03。M05 只做三件事：

1. **入院登记时**调 M16-03 收预交金（或要求先到收费处交）；
2. **每日 00:30** 触发床日费用记账（M16-03 `source_type='DAILY'`）；
3. **出院办理时**调 M16-03 试算与结算，拿到结算完成结果。

**为什么这么切：** 钱的计算有唯一答案且必须审计，M16 有 9 个子模块专门管这事。如果 M05 也算一遍，就会出现「M05 算出的欠费和 M16 的预交金余额不一致」——这是 HIS 最常见的扯皮问题。**M05 只显示 M16 给的余额，不自己算。**

#### 主线四：病案首页独立，且必须做质控

病案首页是住院病案的第一页，也是唯一必须上报卫健委的结构化数据。与其他文书相比三点不同：

1. **格式由国家规定**（《住院病案首页数据填写质量规范》），字段 300+ 项且分必填/条件必填/选填；
2. **12 项质控规则**（DRG 入组必需项），不通过无法上报；
3. **决定 DRG/DIP 支付**——首页填错，医院拿到的医保结算金额就是错的。

因此独立成 M05-06，而不是塞进 M05-05。

#### 主线五：统计独立，因为口径必须唯一

床位使用率有四种算法（按实际占用床日 / 按出院人数 / 按开放床日 / 按规划床位），同一批数据算出来能差 **36 个百分点**（M09-06 有同类论证：72% / 58% / 81% / 94%）。如果各病区自己算，报表永远对不上。M05-07 集中定义口径并提供预聚合。

#### 主线六：M06 日间手术不并入 M05

M06 是**独立业务形态**（当天来当天走，不占长期床位、按日间结算），不是住院的一种：

| 维度 | 日间手术（M06） | 住院（M05） |
|---|---|---|
| 是否占床位 | 不占长期床位（用日间观察床 2~6 小时） | **占床位，按天计费** |
| 结算方式 | 术后一次结算 | 预交金 + 记账 + 出院结算 |
| 病历 | 日间手术病历（M06-06） | 住院病案（M05-06 首页 + M18 内容） |
| 业务主线 | `m06_or_schedule`（台次） | `m05_admission`（住院号） |
| 两者关系 | **M06 可转 M05**，通过 `POST /internal/v1/m05/admission/from-day-surgery` | M05 接收，生成新住院号 |

## 3. 核心业务模型

### 3.1 住院单状态机（13 态）

```
                ┌─────────────────────────────────────────┐
                │ ①DRAFT（入院申请草稿，M07 开单）          │
                └──────────────┬──────────────────────────┘
                               │ 提交
                               ▼
                ┌─────────────────────────────────────────┐
                │ ②PENDING（待登记，等待患者到住院处）       │
                └──────────────┬──────────────────────────┘
                               │ 入院登记 + 交预交金
                               ▼
                ┌─────────────────────────────────────────┐
                │ ③REGISTERED（已登记，待分床）             │
                └──────────────┬──────────────────────────┘
                               │ 分床
                               ▼
                ┌─────────────────────────────────────────┐
                │ ④IN_HOSPITAL（在院）◄──────┐             │
                └──┬────────────────┬────────┴─────────────┘
                   │                │      转科/转床
                   │                │      (回到 IN_HOSPITAL)
        出院办理    │                │ 中途结算
                   ▼                ▼
    ┌──────────────────────────┐  ┌──────────────────────┐
    │ ⑤DISCHARGING（出院办理中）│  │ ⑨INTERIM_SETTLED     │
    └──────┬───────────────────┘  │（中途结算已完成）      │
           │                      └──────────────────────┘
   ┌───────┴────────┐
   ▼                ▼
┌──────────────┐  ┌──────────────────┐
│⑥DISCHARGED   │  │⑦DISCHARGED_OWED  │（欠费出院，需审批）
│（已出院）      │  │                  │
└──────┬───────┘  └────────┬─────────┘
       │                   │
       ▼                   ▼
┌──────────────────────────────────┐
│ ⑧SETTLED（已结算，终态）            │
└──────────────────────────────────┘

旁支：
  ②PENDING / ③REGISTERED ──► ⑩CANCELLED（作废，退预交金）
  ④IN_HOSPITAL ──► ⑪TRANSFER_OUT（转院）
  ④IN_HOSPITAL ──► ⑫DECEASED（死亡，必须走死亡流程）
  ③REGISTERED ──► ⑬PENDING_BED（日间手术转住院，等分床）
```

**为什么 `DISCHARGED` 与 `SETTLED` 是两个状态：** 现实中「已出院但尚未结算」是常态（患者先走，家属后补交钱）。如果合并，床位上就永远显示「占用」直到钱交完，**床位使用率失真**。两状态分开后，床位在 `DISCHARGED` 时即释放，`SETTLED` 只影响财务。

**为什么 `DECEASED` 独立：** 死亡需走独立的死亡病例讨论、死亡记录归档、病理报告等法定流程，不能与普通出院共用。

### 3.2 床位状态机（6 态）

```
┌────────┐   预约   ┌──────────┐   患者入住   ┌──────────┐
│ ①EMPTY │────────►│②RESERVED │────────────►│③OCCUPIED │
│（空闲） │◄────────│（已预约）  │◄────────────│（占用）    │
└───┬────┘  取消预约 └──────────┘   患者转出    └────┬─────┘
    │                                               │ 患者出院
    │    ┌─────────────────┐                        ▼
    └───►│ ⑥DISABLED（停用） │◄───────────── ┌──────────────┐
         └─────────────────┘                │④CLEANING     │（消毒中）
                ▲                            └──────┬───────┘
                │   启用                            │ 消毒完成
                │                            ┌──────▼───────┐
                └────────────────────────────│⑤MAINTENANCE  │（维修中）
                                             └──────────────┘
```

**`CLEANING` 必须独立：** 患者出院后床位不能立刻给下一个人——必须消毒。眼科术后患者使用滴眼液、眼罩，感染控制要求高。消毒时长由 `m05_bed_config.clean_minutes` 配置（默认 30 分钟）。

**床位的独占性由三条索引保证：**

| 索引 | 保证 |
|---|---|
| `uk_m05_bed_no (ward_id, bed_no)` | 病区内床号不重复 |
| `uk_m05_bed_current_admission (current_admission_id) WHERE NOT NULL` | 一床只能一个在院患者 |
| `uk_m05_bed_reserve_active (bed_id) WHERE status='ACTIVE'` | 同床同时只有一个有效预留 |

### 3.3 在院状态机（`m05_stay`，4 态）

```
        分床
         │
         ▼
   ┌─────────────┐  转科执行   ┌──────────────┐
   │ IN_HOSPITAL │◄───────────►│ TRANSFERRING │
   │  在院中      │             │  转科中       │
   └──┬──────────┘             └──────────────┘
      │ 出院医嘱
      ▼
   ┌──────────────┐  出院登记   ┌──────────┐
   │ DISCHARGING  │────────────►│  CLOSED  │
   │  出院流程中    │             │ 已结案    │
   └──────────────┘             └──────────┘
```

`m05_stay` 与 `m05_admission` 的区别：**一次住院可能有多条在院记录**（转科会产生新的在院记录），但始终只有一条处于 `IN_HOSPITAL/TRANSFERRING/DISCHARGING`——由 `uk_m05_stay_admission` 部分唯一索引保证。

### 3.4 三套状态机的联动

```
  m05_admission.status        m05_bed.status        m05_stay.stay_status
  ────────────────────        ───────────────       ────────────────────
  REGISTERED ──分床──►        → OCCUPIED            → (创建) IN_HOSPITAL
  IN_HOSPITAL                                     ⇄ TRANSFERRING (转科)
       │                                            │
       │ 出院医嘱                                    │
       ▼                                            ▼
  DISCHARGING ──出院──► IN_HOSPITAL → CLEANING   → CLOSED
       │                      │
       ▼                      │ 消毒完成
  DISCHARGED ──────────► EMPTY
       │
       │ 结算完成
       ▼
  SETTLED
```

**三条铁律：**

1. **床位状态由在院状态驱动，不由住院单状态驱动。** 住院单 `DISCHARGED` 时床位变 `CLEANING`，但住院单 `SETTLED` 不影响床位。因为床位关心「物理占用」，不关心「钱结没结」。
2. **转科是一次状态组合变更，必须在一个事务里完成。** 旧床位 → `CLEANING`、新床位 → `OCCUPIED`、旧 `m05_stay` → `CLOSED`、新 `m05_stay` → `IN_HOSPITAL`、住院单 `bed_id` 更新。任何一步失败全部回滚。
3. **`m05_admission` 的 `bed_id`/`bed_no`/`nursing_level`/`stay_state` 是冗余快照**，权威数据在 `m05_bed` 与 `m05_stay`。冗余是为了让 M08、M14-08、M16-03 查住院主档时一次拿到床位信息（P-01 接口 P95 ≤ 100ms）。

### 3.5 床日费用模型

**为什么床日费用必须由 M05 触发而不是 M16 自己算：** 因为「今天这个患者该按几级护理收费」只有 M05 知道（病情等级与护理等级在 `m05_stay`）。M16 拿不到这个信息。所以 M05 算好「该记多少钱、什么项目」再调 M16 记账。

```
每日 00:30
   │
   ▼
扫描所有在院患者（m05_stay.stay_status IN ('IN_HOSPITAL','TRANSFERRING','DISCHARGING')）
   │
   ├─ 床位费：m05_bed_type_snap.daily_fee
   ├─ 护理费：按 nursing_level 映射到 M01-06 收费项目
   │     SPECIAL → M05.CHARGE.NURSING_SPECIAL_ITEM (默认 C0800010)
   │     LEVEL_1 → M05.CHARGE.NURSING_LEVEL_1_ITEM (默认 C0800011)
   │     LEVEL_2 → M05.CHARGE.NURSING_LEVEL_2_ITEM (默认 C0800012)
   │     LEVEL_3 → M05.CHARGE.NURSING_LEVEL_3_ITEM (默认 C0800013)
   └─ 诊查费：M05.CHARGE.CLINIC_ITEM (默认 C0200001)
   │
   ▼
写 m05_charge_task（幂等键 DAILY:{admission_id}:{date}:{charge_item_code}）
   │
   ▼
异步调 M16-03 POST /internal/v1/m16/inpatient/charge
   │    source_type=DAILY, source_id=哈希压缩
   │
   ├─ 成功 → task.status=SUCCESS
   └─ 失败 → task.status=FAILED, next_retry_at=+2^n 分钟（最多 10 次）→ DEAD
```

**床日切分规则：** 按自然日 0 点切分。住院当天收全天床位费，出院当天不收（`M05.CHARGE.DISCHARGE_DAY_CHARGE` 可配置）。举例：10 月 1 日 15:00 入院、10 月 3 日 10:00 出院 → 收 10-01、10-02 两天。

**幂等三重保障：**

1. `m05_charge_task.idempotency_key` 全表唯一 —— 重复生成直接冲突，不发请求；
2. `m05_charge_task.source_id` 传给 M16-03，M16 侧也有 `uk_m16_inpcharge_source (source_type, source_id)` 唯一索引；
3. `next_retry_at` 保证重试不会在同一秒内并发发出。

### 3.6 出院办理的六道关卡

```
出院登记（医生下出院医嘱 → m05_discharge 创建）
   │
   ├─ G-01 未执行医嘱检查：M07-03 是否有 status IN ('ISSUED','EXECUTING') 的医嘱
   │       └─ 有 → WARN（可强制，需理由 ≥10 字）
   │
   ├─ G-02 出院小结：m05_archive.summary_status 必须 SIGNED 或 EXEMPT
   │       └─ 未签 → BLOCK（催办医生）
   │
   ├─ G-03 结算试算：调 M16-03 C-06 settle/preview
   │       ├─ 应补交 > 0 → 引导缴费
   │       └─ 应退 > 0  → 引导退费
   │
   ├─ G-04 正式结算：调 M16-03 C-07 settle
   │       └─ 失败 → BLOCK（保留 DISCHARGING）
   │
   ├─ G-05 出院带药：M14-08 住院退药/带药核对
   │       └─ 有未使用药品 → WARN（提醒退药，避免患者带药回家后无法退）
   │
   └─ G-06 欠费出院审批：结算未完成但患者要走
           └─ 调 M01-11 审批（医务科）→ approval_id
   │
   ▼
住院单 → DISCHARGED / DISCHARGED_OWED
床位   → CLEANING
在院   → CLOSED
触发 M05-05 归档检查 + M05-06 首页填写任务
发 m05.admission.discharged 事件
```

**为什么 G-02 是 BLOCK：** 眼科住院日短（1~7 天），患者出院当天就走。出院小结若允许事后补，医生会因为门诊忙而拖到第二天——此时患者已离开、复查信息传不到。**这是眼科的特殊要求，综合医院通常允许 8 小时内补。**

### 3.7 病历归档的 D-01~D-15 完整性检查

M05-05 并发调用四个来源模块，判定 15 项文书是否齐备：

| 编号 | 检查项 | 来源模块 | 判定依据 |
|---|---|---|---|
| D-01 | 入院记录 | M07-06 | `POST /internal/v1/m07/documents/by-source` |
| D-02 | 住院通知单 | M05-01 | `m05_admission` 存在 |
| D-03 | 首次病程记录 | M07-06 | 同上 |
| D-04 | 日常病程记录 | M07-06 | 同上 |
| D-05 | 上级医师查房记录 | M07-06 | 同上 |
| D-06 | 术前讨论记录 | M07-06 | 同上（无手术则 EXEMPT） |
| D-07 | 手术记录 | M09 | `GET /internal/v1/m09/records/by-schedule/{id}` |
| D-08 | 麻醉记录 | M09 | 同上 |
| D-09 | 术后首次病程记录 | M07-06 | 同上（无手术则 EXEMPT） |
| D-10 | 手术安全核查记录 | M09 | 同上 |
| D-11 | 手术清点记录 | M09 | 同上 |
| D-12 | 手术同意书 | M07-06 | 同上 |
| D-13 | 麻醉同意书 | M09 | 同上 |
| D-14 | 护理记录 | M08 | `GET /internal/v1/m08/records/completeness` |
| D-15 | 出院小结 | M07-06 | `m05_discharge.summary_status` |

**四态判定（不是布尔）：**

| 结果 | 含义 | 后续动作 |
|---|---|---|
| `PRESENT` | 文书存在 | — |
| `MISSING` | 确定没有 | 生成缺陷单 + 催办责任人 |
| `UNKNOWN` | **来源模块不可用，不知道有没有** | 24h 后可人工豁免 |
| `EXEMPT` | 满足豁免条件（如无手术则无手术记录） | — |

**为什么必须四态：** 若用布尔 `exists`，则「M09 挂了」与「确实没写手术记录」无法区分，催办会错人（把系统故障当成医生失职）。UNKNOWN 单独成态并给 24 小时人工豁免窗口，是这套设计的核心。

### 3.8 病案首页质控与 DRG

**12 项质控规则**（DRG/DIP 入组必需）：

| 编号 | 校验项 | 级别 |
|---|---|---|
| Q-01 | 主诊断必填且有效 | BLOCK |
| Q-02 | 主手术必填（有手术时） | BLOCK |
| Q-03 | 入院病情必填（主诊断） | BLOCK |
| Q-04 | 出院情况必填 | BLOCK |
| Q-05 | 离院方式必填 | BLOCK |
| Q-06 | 主诊断与主手术不能冲突 | BLOCK |
| Q-07 | 手术分级与主刀职称匹配 | WARN |
| Q-08 | 住院天数与入出院日期一致 | BLOCK |
| Q-09 | 费用合计与 M16 结算金额一致 | WARN |
| Q-10 | 眼别（眼科特有）必填 | WARN |
| Q-11 | 麻醉方式与麻醉记录一致 | WARN |
| Q-12 | 血型与输血记录一致 | WARN |

**为什么 Q-10 眼别是眼科特有：** 综合医院病案首页没有眼别字段。眼科主诊断「年龄相关性白内障」若不写眼别，DRG 分组无法区分单眼/双眼手术，直接影响结算权重。

### 3.9 床位效率的四种口径

同一个病区同一批数据，四种算法差异巨大：

| 算法 | 公式 | 示例值（M09 同类测算） |
|---|---|---|
| A. 按实际占用床日 | 实际占用床日 / 实际开放床日 | 72% |
| B. 按出院人数 | 出院人数 × 平均住院日 / 开放床日 | 58% |
| C. 按开放床日（含加床） | 实际占用床日 / (标准床 + 加床) | 81% |
| D. 按规划床位 | 实际占用床日 / 规划床日 | 94% |

**最大差 36 个百分点。** 如果各病区自己算，报表永远对不上。M05-07 集中定义口径：

- **主推口径 = A（实际占用床日 / 实际开放床日）**，与卫健委《医疗机构床位使用率计算公式》一致；
- **实际开放床日** = 标准床 × 天数 + 加床占用天数 − 维修/停用床日；
- 其余三种口径在报表中作为「参考口径」并列展示，但**不作为考核依据**；
- 预聚合：`m05_stat_daily` 每日 02:30 计算，查询 48ms（实时计算 2.8s，快 58 倍）。

### 4.3 分区策略

| 表 | 分区 | 理由 |
|---|---|---|
| `m05_admission_log` | 月 RANGE | 只增日志，年 7.4 万行 |
| `m05_bed_status_log` | 月 RANGE | 只增台账，年 4.45 万行 |

| `m05_archive_log` | 月 RANGE | 只增日志，年 3 万行 |
| 其余 35 张 | 不分区 | 行数可控；含跨年唯一约束（分区会使唯一性退化为「同年唯一」） |

**为什么含跨年唯一约束的表不分区：** 以 `m05_admission` 为例，若按 `admitted_at` 年度分区，则 `CREATE UNIQUE INDEX uk_m05_admission_no (admission_no)` 会报错——PostgreSQL 要求分区表上的唯一索引必须包含分区键。加上分区键后，唯一性从「住院号全局唯一」退化为「同年唯一」，跨年重复住院号检测不出来。

### 7.1 模块结构（单体多模块）

```
app/
├── modules/
│   ├── m05_01_admission/        # 入院登记与住院主档
```

**为什么单体多模块而不是微服务：**

1. 七个域共享 `m05_admission` 主表与 `m05_bed` 床位台账，拆微服务会让「分床」变成跨服务分布式事务；
2. 转科一次要改 5 张表（床位×2 + 在院×2 + 住院单），必须在一个事务内，拆服务后极难保证一致性；
3. 二级医院日均住院 40 人次，单体完全撑得住。

## 8. 全局业务规则

### 8.1 住院号规则

```
格式：ZY + YYYYMMDD + 4 位序号
示例：ZY20261028001
```

- 用 Redis `m05:admission:seq:{yyyymmdd}` INCR 生成（TTL 172800s），保证跨窗口不重复；
- 序号超 9999 时报 `"0501008"` 住院号生成失败；
- **住院号全局唯一，由 `uk_m05_admission_no` 保证**；
- 住院号**不复用**——作废的住院号永久占用。

### 8.2 状态机三铁律

| 规则 | 说明 |
|---|---|
| **R-01 状态只能单向前进** | 除明确标注可逆的边（如 `INTERIM_SETTLED → IN_HOSPITAL`），不得回退 |
| **R-02 状态转移必须留痕** | 每次转移写 `m05_admission_log` / `m05_bed_status_log` / `m05_stay_log` |
| **R-03 终态不可改** | `SETTLED` / `DECEASED` / `CANCELLED` 为终态，任何字段修改都要走撤销流程 |

### 8.3 幂等规则

| 场景 | 幂等键 | 落点 |
|---|---|---|
| 住院申请提交 | `(source_type, source_id)` | `uk_m05_request_source` |
| 日间手术转住院 | `related_day_surgery_id` | `idx_m05_admission_day_surgery` |
| 床日计费 | `DAILY:{admission_id}:{date}:{item_code}` | `m05_charge_task.idempotency_key` |
| 欠费预警 | `(admission_id, alert_type, alert_date)` | `uk_m05_charge_alert_dedup` |
| 床位日快照 | `(snap_date, ward_id)` | `uk_m05_bed_snapshot_key` |
| 归档单 | `admission_id` | `uk_m05_archive_admission` |

### 8.4 分床并发规则

```
护士 A 与护士 B 同时给同一个患者分床
    │
    ├─ Redis m05:lock:bed:{bed_id} SETNX EX 10 —— 第一道（熔断）
    │
    ├─ UPDATE m05_bed SET current_admission_id=?
    │     WHERE id=? AND current_admission_id IS NULL
    │     → rowcount=0 表示已被占用 —— 第二道（真正防超卖）
    │
    └─ uk_m05_bed_current_admission 唯一索引 —— 第三道（DB 兜底）
```

**为什么不用纯 `SELECT FOR UPDATE`：** 分床高峰（上午 8:00~9:00）床位图上十几次点击并发，纯行锁会串行化，`FOR UPDATE` 排队时间可能超过 2 秒。条件 UPDATE 在冲突时才失败，不冲突时零等待。

### 8.5 金额与数量规则

| 字段 | 类型 | 精度 | 理由 |
|---|---|---|---|
| 单价 | `NUMERIC(12,4)` | 4 位小数 | 与 M01-06 定价精度一致 |
| 金额 | `NUMERIC(12,2)` | 2 位小数 | 人民币最小单位是分 |
| 数量 | `NUMERIC(12,4)` | 4 位小数 | 床日费恒为 1 |
| 床日数 | `INTEGER` | 整数 | 按自然日切分 |

**金额计算铁律：行级先舍入再汇总。** `amount = ROUND(unit_price × quantity, 2)`，不是先汇总再舍入。30 行明细按比例分摊时，先汇总会差几分钱，退费按行退永远对不上。

## 10. 异常处理与降级策略

### 10.1 降级总原则

> **住院主流程不能因外部模块故障而停摆，但「一床一人」「不重复计费」「不计错床位」三条底线不能降级。**

### 10.2 依赖降级矩阵

| 依赖 | 阻断性 | 降级后行为 |
|---|---|---|
| M03-01 患者服务 | **阻断** | 无患者信息无法登记，报 `"0501009"` |
| M01-13 病区/床位类型 | 缓存降级 | 读本地 `m05_bed_type_snap` 快照 |
| M01-02 职工 | 缓存降级 | 显示 `staff_id`，姓名显示「加载中」 |
| M01-01 科室 | 缓存降级 | 读 `m05_dict_item` |
| M16-03 预交金收取 | **阻断**（除零预交金特批） | 不能登记，报 `"0501015"` |
| M16-03 预交金余额查询 | 降级 | 显示「—」，不阻断 |
| M16-03 床日记账 | 补偿重试 | 写 `m05_charge_task` FAILED，Celery 重试 10 次 |
| M16-03 结算试算 | **阻断** | 不能出院，报 `"0505032"` |
| M16-03 正式结算 | **阻断** | 不能出院；或走欠费出院审批 |
| M07-06 文书查询 | 降级 | 该检查项判 UNKNOWN |
| M08-05 护理记录 | 降级 | 该检查项判 UNKNOWN |
| M09-03 手术记录 | 降级 | 该检查项判 UNKNOWN |
| M18 病案库 | 补偿重试 | 归档置 FAILED，Celery 重试 |
| M02-06 审计 | 异步补偿 | 进审计补偿队列 |

### 10.3 异常分类

| 类别 | 处理 | 示例 |
|---|---|---|
| **参数校验** | 直接返回 `40001` | 日期格式错误 |
| **业务规则** | 返回业务错误码 | `"0501002"` 已有在院记录 |
| **并发冲突** | 返回 409 + 重试提示 | 分床时床位已被占用 |
| **外部超时** | 按降级矩阵处理 | M16-03 超时 |
| **数据不一致** | 告警 + 人工介入 | 床位占用但无在院记录 |
| **系统异常** | 返回 `50000` + 错误日志 | DB 连接失败 |

### 10.4 数据一致性守护任务

| 任务 | 频率 | 检查内容 | 发现不一致 |
|---|---|---|---|
| `check_bed_admission_consistency` | 每小时 | `m05_bed.status='OCCUPIED'` 是否都有对应 `m05_stay` | 告警 + 自动修复 |

## 12. 实施路线与验收

### 12.1 六阶段实施（18 周）

| 阶段 | 子模块 | 周期 | 理由 |
|---|---|---|---|
| ① | **M05-01 入院登记与住院主档** | 3 周 | **数据地基**。没有 `m05_admission` 谁也无处挂靠 |
| ② | **M05-02 床位管理** | 3 周 | 紧随其后。分床是登记之后第一个动作 |
| ③ | **M05-03 在院管理与转科转床** | 3 周 | 在院日常。转科联动 M16-03 `TRANSFER` 记账 |
| ④ | **M05-04 住院费用联动** | 2 周 | 依赖 M16-03 已上线。床位费占住院收入 8~15% |
| ⑤ | **M05-05 出院办理** | 3 周 | 与 M07-06（出院小结）、M16-03（结算）三方联调 |
| ⑥ | **M05-06 病案首页 + M05-07 统计** | 4 周 | 首页依赖全部临床数据齐全 |

**为什么 M05-04 排第④而不是最后：** 床位费是住院收入最大一块（占 8~15%），没有自动计费只能人工补录，很容易漏收。M16-03 已完整设计，M05-04 只需调接口，工作量小但对收入影响大。
