**设计说明：**

1. **`m05_admission` 是核心表，被 M05 全部子模块引用。** `m05_bed`（M05-02）、`m05_stay`（M05-03）、`m05_transfer`（M05-03）、`m05_discharge`（M05-05）、`m05_medical_record_home`（M05-06）都以 `admission_id` 与它关联。**但本文件不建外键**，理由见 4.2 设计要点。
2. **`m05_admission_request` 与 `m05_admission` 是 1:0..1 关系。** 一个申请单最多生成一个住院单（防止重复登记），但直收入院、日间转住院可能没有申请单。
3. **`m05_admission.related_admission_id` 是自关联**，用于双眼分期手术的两次住院串起来。自关联不建外键（避免自引用删除问题）。
4. **`m05_admission_log` 是只增表**，用触发器禁止 UPDATE/DELETE，保存期 15 年。
5. **`m05_admission_deposit_snap` 是预交金的本地快照**，权威数据在 M16-03 的 `m16_deposit_account`。这张表存在是为了：①M16 不可用时能显示「上次已知余额」②对账时能比对本地快照与 M16 实际值。
6. **`m05_dict_item` 是 M01-10 字典的本地缓存**，因为入院途径/病情/离院方式等字典是高频读取的枚举，每次查 M01 不合适；且这些字典短期内不会变化。
7. **`m05_admission_stat` 是统计预聚合表**，由 M05-07 使用，但数据结构定义在本文件（因为它按 `admission` 粒度）。

**约束说明：**

```sql
-- 住院号格式：ZY + 8 位日期 + 4 位序号
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_no_format
    CHECK (admission_no IS NULL OR admission_no ~ '^ZY[0-9]{12}$');

-- 住院号必须在非草稿状态下有值
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_no_required
    CHECK (status IN ('DRAFT', 'CANCELLED') OR admission_no IS NOT NULL);

-- 住院状态枚举（12 态）
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_status
    CHECK (status IN ('DRAFT', 'PENDING', 'PENDING_BED', 'REGISTERED',
                      'IN_HOSPITAL', 'DISCHARGING', 'INTERIM_SETTLED',
                      'DISCHARGED', 'DISCHARGED_OWED', 'SETTLED',
                      'CANCELLED', 'TRANSFER_OUT', 'DECEASED'));

-- 入院途径枚举
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_way
    CHECK (admission_way IN ('OUTPATIENT', 'EMERGENCY', 'TRANSFER', 'OTHER'));

-- 入院病情枚举
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_condition
    CHECK (patient_condition IN ('CRITICAL', 'URGENT', 'GENERAL'));

-- 眼别枚举
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_eye_side
    CHECK (eye_side IN ('OD', 'OS', 'OU', 'NA'));

-- 有手术计划时，眼别不能是 NA
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_surgery_eye
    CHECK (surgery_plan IS NULL OR eye_side <> 'NA');

-- 有手术计划时，手术分期必须填写
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_surgery_seq
    CHECK (surgery_plan IS NULL OR surgery_plan_sequence IN (1, 2, 3));

-- 手术分期必须在 1~3 之间
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_seq_range
    CHECK (surgery_plan_sequence IS NULL
           OR (surgery_plan_sequence >= 1 AND surgery_plan_sequence <= 3));

-- 自关联不能指向自己
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_related_self
    CHECK (related_admission_id IS NULL OR related_admission_id <> id);

-- 作废必须填原因与时间
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_cancelled
    CHECK (status <> 'CANCELLED'
           OR (cancel_reason IS NOT NULL
               AND char_length(btrim(cancel_reason)) >= 10
               AND cancelled_by IS NOT NULL
               AND cancelled_at IS NOT NULL));

-- 已出院必须有出院时间与住院天数
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_discharged
    CHECK (status NOT IN ('DISCHARGED', 'DISCHARGED_OWED', 'SETTLED', 'TRANSFER_OUT', 'DECEASED')
           OR (discharge_time IS NOT NULL
               AND actual_stay_days IS NOT NULL
               AND actual_stay_days >= 0));

-- 已结算必须有结算单号
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_settled
    CHECK (settle_status <> 'SETTLED'
           OR (settlement_no IS NOT NULL AND settled_at IS NOT NULL));

-- 出院时间不能早于入院时间
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_time_order
    CHECK (discharge_time IS NULL OR discharge_time >= admission_time);

-- 有床位时 bed_no 与 bed_id 必须同时存在
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_bed_paired
    CHECK ((bed_id IS NULL AND bed_no IS NULL)
           OR (bed_id IS NOT NULL AND bed_no IS NOT NULL));

-- 住院期间的金额不能为负
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_amounts
    CHECK (deposit_total >= 0 AND total_charge >= 0
           AND (settle_amount IS NULL OR settle_amount >= 0));

-- 中途结算次数不能为负
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_interim
    CHECK (interim_settle_count >= 0);

-- 草稿状态必须有过期时间
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_draft_expire
    CHECK (status <> 'DRAFT' OR draft_expire_at IS NOT NULL);

-- 日间转住院必须有关联日间手术 ID 与审批单号
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_from_ds
    CHECK (source_type <> 'DAY_SURGERY'
           OR (related_day_surgery_id IS NOT NULL AND approval_no IS NOT NULL));

-- 医保类型枚举
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_insurance
    CHECK (insurance_type IS NULL
           OR insurance_type IN ('EMPLOYEE', 'RESIDENT', 'SELF_PAY',
                                 'COMMERCIAL', 'MILITARY', 'OTHER'));

-- 护理等级枚举
ALTER TABLE m05_admission
    ADD CONSTRAINT ck_m05_admission_nursing_level
    CHECK (nursing_level IS NULL
```

**设计要点：**

1. **为什么患者信息要快照（`patient_name` / `gender` / `age` / `id_card_no` / `phone` / `address`）？**
   病案要求还原「住院当时的信息」。患者 2026 年改了手机号和住址，2020 年那次住院记录里的联系方式不应跟着变——那会影响病历真实性核查。同时快照能避免每次列表都调 M03 接口。

2. **为什么 `admission_no` 允许为空？**
   草稿状态（`DRAFT`）还没生成住院号。约束 `ck_m05_admission_no_required` 保证非草稿状态必须有住院号。这样草稿不会占用号段。

3. **为什么 `uk_m05_admission_no` 是部分唯一索引（`WHERE is_deleted = FALSE`）？**
   逻辑删除后住院号可以重发。但实际上住院号永不重发——这里加条件是为了与全模块其他表的命名规范一致，同时避免软删除记录阻塞。

4. **为什么 `eye_side` 是 NOT NULL DEFAULT 'NA'？**
   与 M07-03 `m07_order.eye_side` 保持一致（那是 `NOT NULL DEFAULT 'NA'`）。眼科业务里「眼别」是高频过滤条件，允许 NULL 会导致索引失效与查询漏行。

5. **为什么 `surgery_plan_sequence` 单独存在而不是用 `related_admission_id` 推算？**
   序列号是业务语义（第 1 期/第 2 期），`related_admission_id` 是关系。两者独立更清晰：一次住院可能关联对侧，但序列号在入院时就定了，不依赖对侧是否存在。

6. **为什么 `status` 有 13 个值而不是「合并同类」？**
   `DISCHARGED` 与 `SETTLED` 必须分开——现实中「已出院未结算」是常态（患者先走，家属后补交钱）。合并会导致床位永远显示占用直到钱交完，床位使用率失真。
   `DECEASED` 必须独立——死亡要走独立的死亡病例讨论、死亡记录归档流程。

7. **为什么不建外键？**
   ①`m05_admission` 是高写入表（日均 40 条 INSERT + 大量 UPDATE），外键检查会拖慢 ②`admission_dept_id` / `ward_id` / `attending_doctor_id` 指向 M01 主数据，跨库或跨 schema 时外键不可用 ③`bed_id` 指向 M05-02 的表，同模块内但在不同文件定义，外键会增加建表顺序耦合 ④一致性由应用层与每日 03:00 的对账任务保证。
   **代价**：可能出现悬挂引用（dept 已被删但 admission 还引用）。对账任务 `reconcile_admission_refs` 每日检查并告警。

8. **为什么 `deposit_total` / `total_charge` 是快照而不是实时计算？**
   实时计算要调 M16-03 P-04 查明细并汇总，列表页 40 行就是 40 次调用，不可接受。快照由事件更新，每天 01:00 定时与 M16 对账（`reconcile_deposit_snapshot`）。差异 > 0.01 元告警。

9. **为什么 `version` 乐观锁？**
   住院主档可能被多个操作并发修改（分床时改 `bed_id`，同时住院处在改 `insurance_type`）。乐观锁比悲观锁更适合这种低频写、长时间持有场景。

10. **为什么索引 `idx_m05_admission_active` 用部分索引？**
    最热查询是「查患者在院记录」（P-06，M16-03 每次记账前都会调）。全表 15 年约 15 万行，其中在院状态只有几十行。部分索引后索引体积从约 8MB 降到约 20KB，查询从「扫索引 2ms」变成「<0.1ms」。

**量级估算：**

| 项目 | 数值 | 说明 |
|---|---|---|
| 年入院量 | 14,600 人次 | 二级眼科医院日均 40 人 |
| 15 年总量 | 219,000 行 | — |
| 单行平均长度 | 约 900 字节 | 含患者快照与诊疗信息 |
| 表大小（15 年） | 约 197 MB | 不含索引 |

理由：①15 年 21.9 万行对 PostgreSQL 16 是完全舒适区间（单表 1 亿行才开始考虑分区）②`uk_m05_admission_no` 若分区则必须含分区键，导致跨年住院号可重复，破坏唯一性 ③`idx_m05_admission_active` 是部分索引，分区后每个分区都要建，收益远小于开销。

**设计要点：**

1. **为什么申请单与住院单分两张表？**
   ①状态机完全不同（申请 4 态、住院 13 态）②申请单可能永远不变成住院单（患者不来），若合并则住院单表会有大量废记录 ③申请单有「来源追溯」需求（哪个门诊接诊开的单），住院单有「床位/费用/出院」需求，字段差异大。

2. **为什么 `uk_m05_request_source` 是部分唯一索引而不是全表唯一？**
   同一就诊理论上只能开一次入院申请，但如果开错了作废后重开，就要允许同一 `source_id` 有多条记录。所以条件加上 `status <> 'CANCELLED'`。

3. **为什么 `create_type` 与 `direct_reason` 在申请单而不是住院单？**
   直收入院这个动作发生在「创建申请」环节，不是登记环节。住院单上记 `approval_no`（审批单）就够了。

4. **为什么 `patient_name` / `dept_name` / `doctor_name` 要冗余？**
   待登记列表页要显示姓名、科室、医生，如果每次都调 M03/M01，40 行就是 120 次调用。冗余后一次查询拿全。代价是改名不同步——但申请单是短期临时数据（一般 1~7 天），可以接受。

```sql

-- 动作枚举

                      'FROM_DAY_SURGERY', 'INTERIM_SETTLED', 'SETTLED',
                      'PRINT', 'EXPORT'));

-- JSONB 类型校验
ALTER TABLE m05_admission_log
    ADD CONSTRAINT ck_m05_admission_log_detail
    CHECK (detail_json IS NULL OR jsonb_typeof(detail_json) = 'object');

-- 变更前后值必须同为对象或同为 NULL
ALTER TABLE m05_admission_log
    ADD CONSTRAINT ck_m05_admission_log_change
    CHECK ((old_value IS NULL AND new_value IS NULL)
           OR (jsonb_typeof(old_value) = 'object'
               AND jsonb_typeof(new_value) = 'object'));

-- 只增触发器：禁止 UPDATE / DELETE
CREATE OR REPLACE FUNCTION fn_m05_admission_log_readonly()
RETURNS TRIGGER AS $$

    RAISE EXCEPTION 'm05_admission_log 为只增表，禁止 %', TG_OP;
END;
$$ LANGUAGE plpgsql;

    BEFORE UPDATE ON m05_admission_log
    FOR EACH ROW EXECUTE FUNCTION fn_m05_admission_log_readonly();

    BEFORE DELETE ON m05_admission_log
    FOR EACH ROW EXECUTE FUNCTION fn_m05_admission_log_readonly();

COMMENT ON COLUMN m05_admission_log.detail_json IS '变更明细，如 {"admission_no":"ZY...","way":"OUTPATIENT"}';
COMMENT ON COLUMN m05_admission_log.old_value IS '字段级变更前值，如 {"insurance_type":"SELF_PAY"}';
COMMENT ON COLUMN m05_admission_log.new_value IS '字段级变更后值';
```

**设计要点：**

1. **为什么 `biz_type` + `biz_id` 而不是两张日志表？**
   申请单与住院单的日志字段完全一致，两张表会有 90% 重复代码。用 `biz_type` 区分，查询时加条件即可。

2. **为什么 `operator_id` 允许为 NULL / 0？**
   系统操作（结算回调 P-07、事件驱动的更新）没有操作人，用 0 表示系统。若设 NOT NULL 会强制造假值。

3. **为什么同时有 `detail_json` 和 `old_value`/`new_value`？**
   `detail_json` 是「这个动作的上下文」（如登记时的入院途径、预交金金额），`old_value`/`new_value` 是「哪些字段变了」。前者用于理解动作语义，后者用于字段级追溯（「上次是谁把医保类型从自费改成职工」）。两者互补。

4. **为什么只增？**
   日志是审计证据。如果可以改，就失去了追溯价值。触发器强制保证。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 年日志量 | 约 74,000 条（日均 40 登记 + 160 更新） |
| 15 年总量 | 1,110,000 行 |
| 单行平均长度 | 约 400 字节 |
| 表大小 | 约 423 MB |
| 索引大小 | 约 260 MB |
| 合计 | 约 683 MB |

**分区：** **按 `created_at` 月度 RANGE 分区**，预建 36 个月，热数据保留 180 天。
理由：①日志是纯追加、按时间范围查询的模式，天然适合分区 ②15 年 111 万行但超过 1 年的几乎不查，分区后热分区只有约 1.2 万行 ③分区可直接 DETACH 归档，比 DELETE 快得多（DELETE 111 万行会产生大量 dead tuple 与锁）。

### 4.5 表：`m05_admission_deposit_snap`

**用途：** 预交金快照表。权威数据在 M16-03 的 `m16_deposit_account`。本表存在的目的是：
1. M16-03 不可用时能显示「上次已知余额」
2. 每日对账时比对本地快照与 M16 实际值，发现异常
3. 记录预交金变化的历史轨迹（用于分析「什么时候交的钱、什么时候用完的」）

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |
| admission_id | BIGINT | N | — | 住院流水号 |
| admission_no | VARCHAR(32) | Y | NULL | 住院号（冗余） |
| patient_id | BIGINT | N | — | 患者 ID |
| snap_time | TIMESTAMP | N | — | 快照时刻 |
| total_deposit | NUMERIC(14,2) | N | 0 | 累计预交金 |
| total_refund | NUMERIC(14,2) | N | 0 | 累计退还 |
| frozen_amount | NUMERIC(14,2) | N | 0 | 冻结金额 |
| available_balance | NUMERIC(14,2) | N | 0 | 可用余额 |
| total_charge | NUMERIC(14,2) | N | 0 | 累计记账 |
| source | VARCHAR(16) | N | — | 快照来源 EVENT / SCHEDULE / MANUAL |
| is_reconciled | BOOLEAN | N | FALSE | 是否已与 M16 对账 |
| reconcile_diff | NUMERIC(14,2) | Y | NULL | 对账差异 |
| reconciled_at | TIMESTAMP | Y | NULL | 对账时间 |
| trace_id | VARCHAR(64) | Y | NULL | 链路 ID |
| created_at | TIMESTAMP | N | CURRENT_TIMESTAMP | 创建时间 |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m05_admission_deposit_snap` | 主键 | `id` | — |
| `idx_m05_deposit_snap_admission` | B-Tree | `admission_id`, `snap_time` DESC | 按住院查快照历史 |
| `idx_m05_deposit_snap_latest` | B-Tree（部分） | `admission_id`, `snap_time` DESC WHERE `source = 'SCHEDULE'` | 取最新快照 |
| `idx_m05_deposit_snap_unreconciled` | B-Tree（部分） | `snap_time` WHERE `is_reconciled = FALSE` | 待对账扫描 |

**约束说明：**

```sql
-- 金额不能为负
ALTER TABLE m05_admission_deposit_snap
    ADD CONSTRAINT ck_m05_deposit_snap_amounts
    CHECK (total_deposit >= 0
           AND total_refund >= 0
           AND frozen_amount >= 0
           AND total_charge >= 0);

-- 可用余额 = 累计预交金 - 累计退还 - 冻结金额
ALTER TABLE m05_admission_deposit_snap
    ADD CONSTRAINT ck_m05_deposit_snap_balance
    CHECK (available_balance = total_deposit - total_refund - frozen_amount);

-- 来源枚举
ALTER TABLE m05_admission_deposit_snap
    ADD CONSTRAINT ck_m05_deposit_snap_source
    CHECK (source IN ('EVENT', 'SCHEDULE', 'MANUAL'));

-- 已对账必须有差异与对账时间
ALTER TABLE m05_admission_deposit_snap
    ADD CONSTRAINT ck_m05_deposit_snap_reconciled
    CHECK (is_reconciled = FALSE
           OR (reconcile_diff IS NOT NULL AND reconciled_at IS NOT NULL));

COMMENT ON TABLE m05_admission_deposit_snap IS '预交金快照表：M16 不可用时的降级显示源与每日对账依据';
COMMENT ON COLUMN m05_admission_deposit_snap.source IS 'EVENT 事件触发 / SCHEDULE 定时拉取 / MANUAL 手工刷新';
COMMENT ON COLUMN m05_admission_deposit_snap.reconcile_diff IS '与 M16 账户的差异（本地 - M16），非 0 需告警';
```

**设计要点：**

1. **为什么允许 `available_balance` 为负？**
   `ck_m05_deposit_snap_balance` 只保证等式成立，不保证非负。因为记账超过预交金是正常的（先治疗后付费），此时可用余额确实为负。

2. **为什么 `source` 分三种？**
   - `EVENT`：由 `m16.inpatient.deposit.created` 等事件触发，实时
   - `SCHEDULE`：每日 01:00 定时全量拉取，用于对账
   - `MANUAL`：页面点「刷新余额」触发

   区分来源让对账任务只处理 `SCHEDULE` 类型的快照（因为它是独立拉取的权威值），而事件类型的快照可能与 M16 有轻微延迟。

3. **为什么不在主表存历史？**
   预交金变化可能一天多次（充值、记账、退还），若存在主表只能存最新值，历史轨迹丢失。独立表可以完整记录。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 年快照量 | 约 73,000 条（在院患者每日 1 条 `SCHEDULE` + 事件触发约 4 次/住院） |
| 15 年总量 | 1,095,000 行 |
| 单行平均长度 | 约 120 字节 |
| 表大小 | 约 132 MB |
| 索引大小 | 约 90 MB |
| 合计 | 约 222 MB |

**分区：** 不分区，但**保留期 3 年**（超过 3 年的快照价值很低，因为权威数据在 M16）。3 年约 21.9 万行，约 44 MB。

**设计要点：**

2. **为什么支持 DEPT 级覆盖？**
   眼科病区与普通病区的最低预交金不同（手术病区需要预留更多）。科室级配置覆盖全局，查询时按「科室 > 全局」优先级取值。

3. **为什么 `param_code` 强制三段格式 `M05.<分组>.<参数名>`？**
   与全模块其他配置表保持一致（M08/M14/M16 都是这个格式），便于跨模块检索与参数管理工具统一处理。

**量级估算：** GLOBAL 13 条 + 每个科室 3 条覆盖 = 5 个住院科室 × 3 + 13 = 28 条，约 15 KB。永久保留，不分区。

```sql
    ADD CONSTRAINT ck_m05_admission_stat_stay
    CHECK (avg_stay_days IS NULL OR avg_stay_days >= 0);

-- JSONB 类型校验
ALTER TABLE m05_admission_stat
    ADD CONSTRAINT ck_m05_admission_stat_json
    CHECK ((admission_way_json IS NULL OR jsonb_typeof(admission_way_json) = 'object')
           AND (patient_condition_json IS NULL
                OR jsonb_typeof(patient_condition_json) = 'object')
           AND (insurance_type_json IS NULL
                OR jsonb_typeof(insurance_type_json) = 'object')
           AND (eye_side_json IS NULL OR jsonb_typeof(eye_side_json) = 'object'));

-- dept_id = 0 表示全院汇总行，dept_name 必须为空
ALTER TABLE m05_admission_stat
    ADD CONSTRAINT ck_m05_admission_stat_dept
    CHECK ((dept_id = 0 AND dept_name IS NULL)
           OR (dept_id > 0 AND dept_name IS NOT NULL));

COMMENT ON TABLE m05_admission_stat IS '入院登记日维度统计预聚合表，每日 00:30 生成';

COMMENT ON COLUMN m05_admission_stat.admission_way_json IS '入院途径分布，如 {"OUTPATIENT":268,"EMERGENCY":12}';
COMMENT ON COLUMN m05_admission_stat.stat_version IS '统计版本，重算时 +1，用于识别数据是否已刷新';
```

**设计要点：**

1. **为什么 `dept_id = 0` 表示全院？**
   报表既要看科室明细也要看全院合计。若全院合计每次现算，就要对科室行做 SUM，多次查询后口径可能不一致。存一行全院汇总保证「科室之和 = 全院」恒成立。

2. **为什么分布用 JSONB 而不是拆列？**
   入院途径 4 类、病情 3 类、医保 6 类、眼别 4 类，拆列要 17 个 INTEGER 列。而这几类分布未来可能加值（如新增「远程会诊入院」途径），拆列要改表结构。JSONB 只存非零项，体积更小。

3. **为什么 `stat_version` 存在？**
   统计任务可能重跑（补数、修正）。`stat_version` 让下游能判断「这份数据是不是最新的」。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 日行数 | 6 行（5 个住院科室 + 1 行全院） |
| 年行数 | 2,190 行 |
| 15 年总量 | 32,850 行 |
| 单行平均长度 | 约 512 字节（含 4 个 JSONB） |
| 表大小 | 约 17 MB |
| 合计（含索引） | 约 22 MB |

**分区：** 不分区。15 年 3.3 万行完全不需要。

### E.3 分区建表脚本（`m05_admission_log`）

```sql
-- 主表按 created_at 月度 RANGE 分区
CREATE TABLE m05_admission_log (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY,
    biz_type    VARCHAR(16) NOT NULL,
    biz_id      BIGINT NOT NULL,
    action      VARCHAR(32) NOT NULL,
    operator_id BIGINT,
    operator_name VARCHAR(64),
    operator_ip VARCHAR(64),
    detail_json JSONB,
    old_value   JSONB,
    new_value   JSONB,
    remark      VARCHAR(512),
    trace_id    VARCHAR(64),
    created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- 预建 36 个月分区
DO $$
DECLARE
    i INT;
    start_date DATE;
    end_date DATE;
    part_name TEXT;
BEGIN
    FOR i IN 0..35 LOOP
        start_date := (DATE_TRUNC('month', CURRENT_DATE) + (i || ' months')::INTERVAL);
        end_date := start_date + INTERVAL '1 month';
        part_name := 'm05_admission_log_p' || TO_CHAR(start_date, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m05_admission_log '
            'FOR VALUES FROM (%L) TO (%L)',
            part_name, start_date, end_date
        );
    END LOOP;
END $$;
```

**为什么主键是 `(id, created_at)` 而不是 `(id)`：**
PostgreSQL 要求分区表的主键必须包含分区键。所以主键改为 `(id, created_at)`。这不会影响业务——业务查日志用 `biz_type + biz_id`，不靠主键。
