## 4. 数据结构设计

### 4.1 ER 关系图

```
┌────────────────────────┐
│ m14_stocktake          │ 盘点单（主表）
│  take_no / status      │
│  diff_amount / level   │
└───┬────┬────┬────┬─────┘
    │    │    │    │
    │1:1 │1:N │1:N │1:N
    ▼    ▼    ▼    ▼
┌──────┐┌──────────┐┌────────────┐┌──────────────┐
│scope ││   item   ││  approval  ││    adjust    │
│范围  ││ 明细(批次)││  审批链    ││  调整记录    │
└──────┘└────┬─────┘└────────────┘└──────┬───────┘
             │                            │
             │ 关联                        │ 写流水
             ▼                            ▼
      ┌──────────────┐          ┌────────────────────┐
      │m14_stock_batch│         │ m14_stock_txn      │
      │   (M14-01)    │         │   (M14-01)         │
      └──────────────┘         └────────────────────┘

┌────────────────────────┐
│ m14_stocktake_cycle_rule│ 循环盘点规则（独立配置）
└────────────────────────┘

┌────────────────────────┐
│ m14_stocktake_log      │ 操作日志（只增）
└────────────────────────┘
```

**设计说明**

| 决策 | 内容 | 理由 |
|---|---|---|
| 范围与明细分离 | `scope` 存范围参数，`item` 存展开后的批次 | 范围可能复杂组合（多条件交集），参数留档便于复现 |
| 明细粒度到批次 | `m14_stocktake_item` 一行 = 一个批次 | 盘盈盘亏是批次级的，不是药品级的 |
| 审批独立成表 | `approval` 而非主表加字段 | 支持多级审批链、每级不同人、超时升级 |
| 调整独立成表 | `adjust` 而非复用明细 | 记录**执行结果**（成功/失败/流水号），与盘点结论分开 |
| 循环规则独立成表 | `cycle_rule` | 是配置数据，不属于某次盘点 |
| 日志独立成表 | `log` | 只增不改，独立于业务表生命周期 |

```sql
    ADD CONSTRAINT ck_m14_stocktake_level

           OR diff_level IN ('SMALL', 'MEDIUM', 'LARGE', 'HUGE'));

    ADD CONSTRAINT ck_m14_stocktake_count
    CHECK (total_count >= 0
           AND counted_count >= 0 AND counted_count <= total_count
           AND match_count >= 0 AND profit_count >= 0

           AND match_count + profit_count + loss_count
               <= counted_count);

    ADD CONSTRAINT ck_m14_stocktake_amount
    CHECK (book_amount >= 0 AND profit_amount >= 0
           AND loss_amount >= 0 AND diff_amount >= 0);

ALTER TABLE m14_stocktake
    ADD CONSTRAINT ck_m14_stocktake_diff_amount
    CHECK (ABS(diff_amount - (profit_amount + loss_amount)) <= 0.01);

-- 差异率在 0~1 之间

    ADD CONSTRAINT ck_m14_stocktake_rate

    ADD CONSTRAINT ck_m14_stocktake_generated

    ADD CONSTRAINT ck_m14_stocktake_submitted

           OR (submitted_at IS NOT NULL AND diff_level IS NOT NULL));

ALTER TABLE m14_stocktake
    ADD CONSTRAINT ck_m14_stocktake_approved
    CHECK (status NOT IN ('APPROVED', 'EXECUTING', 'EXEC_FAIL',

           OR approved_at IS NOT NULL);

ALTER TABLE m14_stocktake
    ADD CONSTRAINT ck_m14_stocktake_closed
    CHECK (status <> 'CLOSED'
           OR (executed_at IS NOT NULL AND closed_at IS NOT NULL));

    ADD CONSTRAINT ck_m14_stocktake_cancel
    CHECK (status <> 'CANCELLED'

    ADD CONSTRAINT ck_m14_stocktake_reject
```

**状态机**

```
DRAFT ──► GENERATED ──► COUNTING ──► SUBMITTED ──┬─► APPROVED ──► EXECUTING ──┬─► CLOSED
                                                  │                            └─► EXEC_FAIL ──► EXECUTING
                                                  └─► REJECTED ──► COUNTING
任意非终态 ──► CANCELLED
```

**关键设计说明**

**为什么 `diff_amount` 存绝对值之和而不是净额？**

假设某次盘点：

- 盘盈 18 批，合计 +860 元
- 盘亏 20 批，合计 −1,480 元
- 净差异 = −620 元

如果只存净额 −620，管理者会以为"只差了 620 元"。但实际上有 2,340 元的账实不符——860 元多出来的找不到来源，1,480 元少了找不到去向。这两个问题完全不同，不能相抵。

所以：

- `profit_amount` = 860.00（盘盈合计，正数）
- `loss_amount` = 1,480.00（盘亏合计，正数，取绝对值）
- `diff_amount` = 2,340.00（差异合计，两者相加）

约束 `ABS(diff_amount - (profit_amount + loss_amount)) <= 0.01` 保证三者永远自洽。

**为什么 `book_amount` 要存？**

差异率的分母是账面金额，且必须在生成盘点表时锁定。如果实时算（读当前库存），盘点到一半时又进了货，差异率就变了，审批人看到的和提交时的不是同一个数。

**为什么 `counted_count <= total_count` 要约束？**

理论上不会超出（每行只能录一次），但如果并发录入同一个批次（两个盘点人员用 PDA 同时扫同一批号），可能产生重复计数。约束强制数据库层面拒绝，而不是靠应用层保证。

```sql
    CHECK (matched_count >= 0);
```

**为什么要存 `scope_json`（原始快照）？**

结构化字段（`drug_category`、`abc_class` 等）只覆盖了已知条件。如果将来新增条件（比如"按供应商筛选"），老的结构化字段就表达不了。

`scope_json` 存完整的原始请求体，无论条件怎么扩展都能完整复现，用于：

- 审计：这次盘的到底是什么范围
- 复现：同样的范围再盘一次
- 排查：为什么匹配出 320 个批次而不是预期的 300

| 项 | 数值 |

| 年行数 | 约 700（与盘点单 1:1） |
| 单行大小 | 约 2 KB（含 JSONB） |
| 年增量 | 约 1.4 MB |

**分区：** 不分区。


**`uk_m14_stocktake_item_batch`（同单同批次唯一）的必要性**

这是本表最关键的约束。没有它会发生：

**场景一：重复生成。** 用户点了两次「生成盘点表」，第二次没清干净旧数据，于是同一批次出现两行：

```
行 1: A261001  账面 120
行 2: A261001  账面 120    ← 重复
```

统计差异时会把这一批算两次，如果两行都录了 118，差异变成 −4 而不是 −2。

**场景二：并发录入。** 两个盘点人员用 PDA 同时扫同一批号录入实盘数：

- A 录入 118
- B 录入 120（重新点了一遍，发现是 120）

两行都存在的话，系统不知道该信谁。有唯一约束，第二个录入会更新第一行，最终结果确定。

**场景三：调整重复执行。** 生成调整单时按 `take_id + batch_id` 遍历，如果同批次有两行，会调用两次 `stock/apply`。虽然幂等键能挡住，但调整记录会有两条，报表统计错误。

唯一索引从结构上排除这三种情况。

**`diff_type` 与 `actual_qty` 的三态约束**

`ck_m14_stocktake_item_type` 这条约束看起来很复杂，但它把四种状态精确绑定：

| `diff_type` | `actual_qty` | `diff_qty` |
|---|---|---|
| `UNCOUNTED` | NULL | 任意（应为 0） |
| `MATCH` | 非 NULL | 绝对值 ≤ 0.0001 |
| `PROFIT` | 非 NULL | > 0.0001 |
| `LOSS` | 非 NULL | < −0.0001 |

没有这条约束，可能出现：

- `diff_type = 'MATCH'` 但 `diff_qty = 5`（数据说不符却标相符）
- `actual_qty IS NULL` 但 `diff_type = 'LOSS'`（没录数却判亏）

这类不一致会导致"报表显示有 13 个盘亏，但差异明细列表一个都没有"，排查起来极费时间。

**为什么 `management_class` 和 `is_cold_chain` 要冗余？**

这两个字段在药品主数据里有，按理说可以关联查询。但盘点需要频繁判断"哪些行需要复核""哪些行需要质量会签"，如果每次都 JOIN 药品表：

- 3,000 行 × JOIN = 性能下降
- 药品主数据变更后，历史盘点的属性会跟着变（错）

快照下来，既快又准。

**为什么 `take_no` 要冗余？**

为了报表查询和日志关联。盘点明细的分组统计经常按单号排，冗余后不用 JOIN。这是典型的"空间换时间"取舍：每行多 32 字节，换来免 JOIN。

**量级估算**

| 项 | 数值 |
|---|---|
| 全盘规模 | 3,000 批次（中心药库） |
| 循环盘 | 20 批次/天 |
| 年全盘 | 12 次 × 3,000 = 36,000 行 |
| 年循环 | 365 × 20 = 7,300 行 |
| 年合计 | 约 43,300 行 |
| 单行大小 | 约 550 B |
| 年增量 | 约 24 MB |
| 10 年累计 | 约 433,000 行 / 240 MB |

**分区：** 不分区。43,300 行/年，10 年 43 万行，单表完全可承受。若未来药房规模扩大，可按 `take_id` 的范围或按年分区（见附录 D 迁移说明）。

**为什么审批链独立成表而不是主表加字段？**

盘点差异最多需要 4 级审批（主任 → 财务 → 院长 → 质量会签）。如果在主表加字段：

```
approver1_id, approver1_at, approver1_comment,
approver2_id, approver2_at, approver2_comment,
approver3_id, ...
```

会产生三个问题：

**问题一：字段爆炸。** 3 个审批人 × 3 个字段 = 9 个字段，再加质量会签就 12 个。将来要加"纪检会签"又要加 3 个。

**问题二：不知道审批到哪一步了。** 只能靠"查哪个字段非空"来判断，SQL 写起来是：

```sql
CASE
  WHEN approver3_id IS NOT NULL THEN 3
  WHEN approver2_id IS NOT NULL THEN 2
  WHEN approver1_id IS NOT NULL THEN 1
  ELSE 0
END
```

**问题三：不知道谁该审批。** 主表不存"每个节点由哪个角色审批"，只能靠代码硬编码第 1 步是主任、第 2 步是财务。配置改了要改代码。

独立成表后，审批链就是一组行，每行有角色、状态、时限。查待办就是 `WHERE role_code = :mine AND status = 'PENDING'`，简洁且可配置。

**`TIMEOUT` 状态的作用**

如果某级审批超时，系统不直接跳过，而是标记为 `TIMEOUT` 并把下一级提到 `PENDING`。保留这条记录能回答"这次审批是谁拖了 3 天"，为管理改进提供依据。

**量级估算**

| 项 | 数值 |
|---|---|
| 年审批节点 | 700 单 × 2 平均 = 1,400 |
| 单行大小 | 约 300 B |
| 年增量 | 约 420 KB |

**分区：** 不分区。

**为什么调整独立成表，而不是在明细表加字段？**

盘点明细表（`m14_stocktake_item`）记录的是**结论**（账实差多少），调整表记录的是**执行**（这个差异实际改了多少、走的是哪条流水）。

分开的理由：

| 理由 | 说明 |
|---|---|
| 生命周期不同 | 明细在生成时创建，调整在审批通过后才创建 |
| 失败重试 | 调整可能失败多次，每次要有记录；明细只有一条 |
| 一差异多流水 | 正常情况下一条调整一条流水；将来若支持分批调整，需要 1:N |
| 审计清晰 | 查"这次盘点改了哪些库存流水"，直接查调整表，不用过滤明细 |

**`uk_m14_stocktake_adjust_idem` 的作用**

幂等键 = `STOCKTAKE:{take_no}:{batch_id}`，格式由约束 `ck_m14_stocktake_adjust_idem` 保证。

这个唯一索引是**防止重复扣减/增加库存的最后一道防线**：

1. 用户点了「执行调整」
2. 请求发出，服务器处理了 900 条，第 901 条时网络超时
3. 用户刷新页面看到"执行中"，又点了一次
4. 第二次请求到达，前 900 条如果没唯一索引，会被再次执行 → 库存被改了两次

有唯一索引，第二次的前 900 条插入都失败（幂等键冲突），服务层捕获后跳到下一条，只有第 901 条会真正执行。

**`book_qty_before` 与 `qty_after` 的意义**

这两个字段记录调整前后的系统数量，用于：

- 验证：`qty_after - book_qty_before` 应等于 `±adjust_qty`
- 排查：如果调整后对不上，可以看是不是并发改动导致

**量级估算**

| 项 | 数值 |
|---|---|
| 年调整条数 | 全盘 25 条/次 × 12 + 循环 2 条/天 × 365 ≈ 1,030 |
| 单行大小 | 约 350 B |
| 年增量 | 约 360 KB |

**分区：** 不分区。

**`uk_m14_stocktake_cycle_sig` 的必要性**

如果同一分类方式 + 同一频率有两个启用规则，比如：

- 规则 A：ABC 分类，每日，20 个药品
- 规则 B：ABC 分类，每日，30 个药品

每天会生成两个盘点单，覆盖的药品可能重叠。盘点人员每天看到 50 个待盘批次，实际只有 40 个不同药品，重复劳动且容易混淆。

唯一索引强制"同类型同频率只能有一个启用规则"。要改数量就改规则，不要新建。

**`coverage_days` 的作用**

循环盘的核心问题是"随机抽样可能永远抽不到某些药品"。`coverage_days = 90` 表示：系统会记录每个药品上次被盘的时间，超过 90 天没盘的药品在下一轮优先选入。

这条规则保证了"每个药品一个季度至少盘一次"，避免抽样盲区。

**量级估算**

|---|---|
| 规则数 | 5~10 条 |
| 单行大小 | 约 400 B |
| 合计 | 约 4 KB |

**分区：** 不分区。

```sql
CREATE OR REPLACE FUNCTION fn_m14_stocktake_log_readonly()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'm14_stocktake_log 为只增表，禁止 UPDATE/DELETE';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m14_stocktake_log_update
    BEFORE UPDATE ON m14_stocktake_log
    FOR EACH ROW EXECUTE FUNCTION fn_m14_stocktake_log_readonly();

CREATE TRIGGER trg_m14_stocktake_log_delete
    BEFORE DELETE ON m14_stocktake_log
    FOR EACH ROW EXECUTE FUNCTION fn_m14_stocktake_log_readonly();
```

**为什么日志表要禁止修改？**

盘点是唯一能"无单据改库存"的操作，它的日志就是**证据链**。

如果没有只读保护：

1. 某人私自拿走药品
2. 盘点时把账调平（差异归因"原因不明"）
3. 事后把日志里的归因改成"系统错误"
4. 审计查到"系统错误"，定性为技术问题，无人担责

触发器保证日志写入后不可改。即使 DBA 要改，必须先删触发器（这本身会写进 PostgreSQL 的 DDL 审计日志），成本很高。

**量级估算**

| 项 | 数值 |
|---|---|
| 每单日志条数 | 约 15 条（创建/生成/冻结/多次录入/提交/审批/调整/解冻） |
| 年行数 | 700 × 15 = 10,500 |
| 单行大小 | 约 350 B |
| 年增量 | 约 3.7 MB |

**分区：** 按月 RANGE 分区，预建 36 个月，热数据保留 180 天。

```sql
CREATE TABLE m14_stocktake_log (
    ...
) PARTITION BY RANGE (created_at);

CREATE TABLE m14_stocktake_log_202610
    PARTITION OF m14_stocktake_log
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

**分区原因：** 日志是典型的"写多读少、按时间查"数据。分区后历史日志可整体归档，不影响热数据查询性能。

**分区迁移说明**

当前 `m14_stocktake_item` 不分区。若未来需要分区（例如药房规模扩大、单次全盘超过 10 万批次），推荐方案：

```sql
-- 1. 新建分区表
CREATE TABLE m14_stocktake_item_new (
    LIKE m14_stocktake_item INCLUDING ALL
) PARTITION BY HASH (take_id);

-- 2. 建 8 个分区
CREATE TABLE m14_stocktake_item_p0
    PARTITION OF m14_stocktake_item_new
    FOR VALUES WITH (MODULUS 8, REMAINDER 0);
-- ... p1 ~ p7

-- 3. 迁移数据
INSERT INTO m14_stocktake_item_new
    SELECT * FROM m14_stocktake_item;

-- 4. 重命名
ALTER TABLE m14_stocktake_item RENAME TO m14_stocktake_item_old;
ALTER TABLE m14_stocktake_item_new RENAME TO m14_stocktake_item;
```

**为什么用 HASH(take_id) 而不是 RANGE(created_at)？**

因为盘点明细的查询模式是「按 `take_id` 查」（打开某个盘点单看明细），不是「按时间范围查」。如果用 RANGE 时间分区，查一个盘点单的明细可能跨多个分区，反而更慢。HASH 保证同一单的明细落在同一个分区，查询只扫一个分区。

**注意：** 分区后 `uk_m14_stocktake_item_line` 与 `uk_m14_stocktake_item_batch` 必须包含分区键 `take_id` 才能建唯一索引。当前这两个唯一索引已经包含 `take_id`，所以分区方案无需改索引。
