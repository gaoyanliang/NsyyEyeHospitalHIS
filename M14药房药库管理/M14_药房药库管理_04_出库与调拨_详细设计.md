## 1. 模块概述

### 1.1 模块定位

M14-04 负责药品**在医院内部从一个仓库走到另一个位置**的全过程：从中心药库出库到门诊药房、从药房退回到药库、从药库调到住院药房、以及报损销毁。

它解决的是一条"责任转移"链路的中间段问题：**药品离开一个仓库的时候，必须有人签字、有单据、有去向；药品进入另一个仓库的时候，必须有人核对、有差异记录**。

### 1.2 为什么独立成子模块

M14-04 之所以要从 M14-01（库存台账）里拆出来，原因有三个：

**理由一：出库和入库虽然都改库存，但风险性质完全不同。**

入库的风险是"供应商可能送错、送少、送过期"——责任在外部，控制手段是验收。
出库的风险是"药品可能被拿错、被拿走、被扔掉"——责任在内部，控制手段是**审批 + 双人签字 + 去向可查**。

一个管的是外部质量，一个管的是内部管控，放在同一个子模块里会导致权限模型混乱：验收员需要"收货权"，出库员需要"发货权"，这两个权限绝不能给同一个人。

**理由二：调拨是"一次业务、两条库存流水"的特殊结构。**

调拨不是"药库少了 100 支"，而是"药库少 100 支、门诊药房多 100 支，这两件事必须同时成功或同时失败"。

如果放在 M14-01 里做，M14-01 就得知道"哪两个仓库、什么业务原因、谁批准的"——这会让库存台账从"只管数量"膨胀成"管业务流程"，违背它在 M14-01 里确立的单一职责。

M14-04 承接这个业务流程，然后向 M14-01 发起两次 `apply` 调用，M14-01 依然只做它擅长的事。

**理由三：报损与销毁是 GSP 强制要求独立留痕的业务。**

《药品经营质量管理规范》要求：不合格药品的销毁必须**有申请、有审批、有监销人、有销毁记录、有照片**，记录保存 5 年以上。

这条业务在结构上就是一张独立的单据表，有自己的一套状态机和审批链，硬塞进库存台账会污染台账的字段设计。

### 1.3 与相邻子模块分工

| 子模块 | 唯一责任 | 不做的事 |
|---|---|---|
| **M14-04 出库与调拨** | ✅ 决定"哪个仓库的哪些批次、出多少、去哪、为什么" | ❌ 不直接改 `qty_on_hand`（一律走 M14-01） |
| M14-01 库存台账 | ✅ 决定"库存现在是多少"、执行数量增减、写流水 | ❌ 不判断出库是否合理、不做出库单 |
| M14-02 分配与效期 | ✅ 决定"这一单该用哪几个批次"（FEFO） | ❌ 不创建出库单、不执行出库 |
| M14-03 采购与入库 | ✅ 决定"货从哪来、验收是否合格、入库多少" | ❌ 不做仓间移动 |
| M14-05 盘点 | ✅ 决定"账实差异是多少" | ❌ 差异调整走独立调整单，不走报损 |
| M14-07/08 发药 | ✅ 决定"发给哪个患者、发多少" | ❌ 发药出库由 M14-07/08 直接调 M14-01，不经 M14-04 |

**一句话边界：** M14-04 只回答"药品要从 A 仓库移动到 B 仓库（或销毁），这个移动该不该发生、发生了多少"。**它不回答"库存还剩多少"（M14-01），也不回答"该发给谁"（M14-07/08）。**

### 1.4 概念辨析

这一节用三个最常见的问题澄清边界。

**Q1：出库和发药是一回事吗？**

不是。虽然两者都让库存减少，走的都是 `qty_on_hand` 减少：

| 维度 | 出库（M14-04） | 发药（M14-07/08） |
|---|---|---|
| 触发方 | 药房/药库内部需求 | 患者处方/医嘱 |
| 单据对象 | 领用科室、目标仓库 | 患者 |
| 处方关联 | 无 | 必须有 |
| 是否收费 | 不产生收费 | 产生收费（M16） |
| 状态机 | 申请→审批→执行 | 待发药→已发药 |
| 库存流水类型 | `ISSUE_OUT` | `DISPENSE_OUT` |

在流水类型上分开，是为了让"药房发了多少给患者"和"药房补了多少货"两类统计能分别出报表。如果都混成 `OUT`，月度盘点时分不清"少了 500 支"是因为发了 480 支给患者还是调走了 500 支到别的药房。

**Q2：调拨和出库+入库是同一件事吗？**

从库存数字上看是：`A 仓 −100` 且 `B 仓 +100`。但业务上必须当成**一个原子操作**处理。

如果实现成"先做一个出库单，再做一个入库单"，会出现三种故障场景：

1. 出库成功、入库失败 → 100 支药凭空消失，账上两天都对不上
2. 出库成功、入库单被审核员驳回 → 药已经在 B 仓的架子上，但单据说它不该在这
3. 两个操作之间有人做了盘点 → 盘点数据包含了中间态，差异无法解释

所以 M14-04 的调拨单是**一张单据、两次库存调用、一个事务边界**。见 3.3 节。

**Q3：报损和盘亏是同一件事吗？**

不是，虽然都让库存减少：

| 维度 | 报损（M14-04） | 盘亏（M14-05） |
|---|---|---|
| 发现方式 | 主动发现（过期、破损） | 被动发现（盘点才知） |
| 有明确数量 | 是，损耗多少已知 | 否，盘出来才知道 |
| 有实物去向 | 有（销毁或退回） | 无（就是不见了） |
| 审批要求 | 必须审批 + 监销人 | 差异确认 + 差异处理 |
| 库存流水 | `LOSS_OUT` | `STOCKTAKE_OUT` |

分开的理由：报损有实物可查（可以拍照、可以监销），盘亏没有实物可查（只能写"原因不明"）。两者的审计要求完全不同，混在一起会让"报损销毁记录"里混入无法解释的盘亏，GSP 检查通不过。

### 1.5 模块目标

| 指标 | 目标值 | 说明 |
|---|---|---|
| 出库单据可追溯率 | 100% | 每一支出库药都能查到单据、审批人、去向 |
| 调拨账实相符率 | ≥ 99.9% | 调拨后两仓合计数量不变 |
| 出库单平均处理时长 | ≤ 10 分钟 | 从创建到执行完成 |
| 调拨审批通过率 | ≥ 95% | 合理调拨申请基本都能过 |
| 报损占比（药占库存） | ≤ 0.5% | 反映库存管理质量 |
| 调拨差异率 | ≤ 0.1% | 收货方短少的调拨占全部调拨的比例 |
| 出库单作废率 | ≤ 2% | 反映下单准确性 |

## 2. 业务范围与边界

### 2.1 范围内

- 出库单创建、审批、执行、作废

### 2.2 范围外

| 不属于 M14-04 的事 | 归属模块 | 原因 |

| 住院摆药出库 | M14-08 住院药房 | 按医嘱周期批量 |
| 采购退货出库 | M14-03 采购退货 | 退货对象是供应商，不是内部仓库 |
| 盘点差异调整 | M14-05 盘点 | 差异调整有独立单 |
| 成本核算与结转 | M17 财务 | 出库单只提供成本金额，不做账务 |
| 供应商退货物流 | 外部 | — |

## 3. 业务模型

### 3.1 出库业务模型

#### 3.1.1 出库类型

| 类型代码 | 名称 | 典型场景 | 是否需要审批 |
|---|---|---|---|
| `REQUISITION` | 领用出库 | 药房向药库领药 | 金额 ≥ 5000 需审批 |
| `TRANSFER_OUT` | 调拨出库 | 仓间调拨的发货方 | 是（走调拨审批） |
| `LOSS` | 报损出库 | 过期、破损、变质 | 是 |
| `SCRAP` | 销毁出库 | 不合格药品销毁 | 是（质量负责人） |
| `SAMPLE` | 样品出库 | 药事活动、免费用药 | 是（科主任） |
| `RETURN_SUPPLIER` | 退供应商 | 退货给供应商 | 走 M14-03 |

本子模块的**主流程**是 `REQUISITION`（领用出库）。`TRANSFER_OUT` 和 `LOSS` 分别走 3.3 与 3.4 专节。

#### 3.1.2 出库单状态机

```
              ┌────────────────────────────────────────────┐
              │                                            │
              ▼                                            │
       ┌────────────┐   提交    ┌──────────────┐  审批通过  ┌──────────┐
       │   DRAFT    │─────────►│ SUBMITTED    │──────────►│ APPROVED │
       │   草稿     │          │  待审批       │           │ 已审批   │
       └─────┬──────┘          └──────┬───────┘           └────┬─────┘
             │                        │ 驳回                   │
             │ 作废                   ▼                        │ 执行出库
             │                 ┌──────────────┐                ▼
             │                 │  REJECTED    │         ┌──────────────┐
             │                 │  已驳回       │         │  EXECUTING   │
             │                 └──────┬───────┘         │  执行中       │
             │                        │ 修改重提         └──────┬───────┘
             │                        └──────────┐             │
             │                                   │       ┌─────┴──────┐
             ▼                                   │       │            │
       ┌────────────┐                            │       ▼            ▼
       │ CANCELLED  │◄───────────────────────────┘ ┌──────────┐ ┌──────────┐
       │  已作废     │                              │EXECUTED  │ │ EXEC_FAIL│
       └────────────┘                              │ 已执行    │ │ 执行失败 │
              ▲                                    └──────────┘ └────┬─────┘
              │                                                       │ 重试
              └───────────────────────────────────────────────────────┘
```

**状态说明**

| 状态 | 含义 | 可转入 | 说明 |
|---|---|---|---|
| `DRAFT` | 草稿 | SUBMITTED / CANCELLED | 可自由修改 |
| `SUBMITTED` | 待审批 | APPROVED / REJECTED / CANCELLED | 锁定编辑 |
| `APPROVED` | 已审批 | EXECUTING / CANCELLED | 待执行，可撤销 |
| `REJECTED` | 已驳回 | DRAFT / CANCELLED | 驳回后可修改重提 |
| `EXECUTING` | 执行中 | EXECUTED / EXEC_FAIL | 短暂中间态 |
| `EXECUTED` | 已执行 | — | 终态，库存已扣减 |
| `EXEC_FAIL` | 执行失败 | EXECUTING / CANCELLED | 库存未扣减，可重试 |
| `CANCELLED` | 已作废 | — | 终态 |

**关键约束：** `EXECUTED` 是终态，库存已扣减。要撤销必须新建一张反向入库单（`RETURN_IN`），不能直接改状态。理由见 8.2 节。

#### 3.1.3 出库单创建方式

| 方式 | 说明 | 使用场景 |
|---|---|---|
| 手工创建 | 逐行选择药品、数量 | 常规领用 |
| 从补货建议创建 | 一键带入 M14-02 的补货建议 | 门诊药房月度补货 |
| 从模板创建 | 预设的常用领用清单 | 固定品种的周期性领用 |
| 从盘点差异创建 | 盘点后补记漏账 | M14-05 差异处理 |

#### 3.1.4 出库流程

```

    │ ①创建出库单      │                   │                 │
    ├─────────────────►│                   │                 │
    │                  │ ②确认并提交       │                 │
    │                  ├──────────────────►│                 │
    │                  │                   │ ③审批           │
    │                  │                   ├────────────────►│
    │                  │                   │                 │ ④分配批次
    │                  │                   │                 │  (M14-02)
    │                  │                   │                 │ ⑤拣货
    │                  │                   │                 │ ⑥核对
    │                  │                   │                 │ ⑦执行出库
    │                  │                   │                 │  (M14-01)
    │                  │                   │                 │ ⑧打印
    │                  │                   │                 │   出库单
    │                  │                   │                 │
```

**说明：** 金额 < 5000 的出库单跳过步骤③，直接进入批次分配。

### 3.2 批次与数量模型

#### 3.2.1 出库明细的三层结构

```
出库单 m14_issue
  └── 出库明细 m14_issue_item（按药品汇总）
        └── 批次分配明细 m14_issue_batch（按批次拆开）
```

**为什么要两层明细？**

药师申请时想的是"领 200 支玻璃酸钠滴眼液"，他并不关心这 200 支来自哪几个批次。但实际出库时可能来自：

- 批号 A261001，100 支（效期 2027-01）
- 批号 A260803，100 支（效期 2026-11）

这两支批次在扣减库存时是**两笔独立流水**，因为它们的效期、成本价不同。所以明细要拆成两层：上层是业务意图（200 支），下层是执行事实（2 个批次各 100 支）。

**两层明细的用途**

| 层级 | 存什么 | 谁看 |
|---|---|---|
| `m14_issue_item` | 药品、申请数量、实际出库数量、金额 | 药师、审批人、财务 |
| `m14_issue_batch` | 批次 ID、批号、效期、出库数量 | 药库管理员、审计、GSP 追溯 |

#### 3.2.2 数量三个值

| 字段 | 含义 | 何时确定 |
|---|---|---|
| `request_qty` | 申请数量 | 创建时 |
| `approved_qty` | 批准数量 | 审批时（审批人可减量） |
| `issued_qty` | 实际出库数量 | 执行时 |

三个值都可能不同，这是有意的：

- 药师申请 200 支 → 审批人认为太多，批 150 支
- 批准 150 支 → 药库实际只剩 148 支，出 148 支

差异记录在 `m14_issue_item` 上，报表可查"申请 vs 批准 vs 实际"的偏差率。

#### 3.2.3 拆零出库

如果药品可拆零（`is_split = TRUE`）且库存只有整盒，出库时可以按最小单位出：

```
出库 30 支玻璃酸钠滴眼液（每盒 10 支）
库存：整盒批次 A261001 有 5 盒（50 支），拆零批次 A261001-S 有 3 支

方案一：只用拆零批次 → 只能出 3 支，不够 30 支
方案二：拆零批次 3 支 + 整盒批次 3 盒（30 支）→ 总数 33 支，超了 3 支
```

正确做法是**先出拆零批次的余量，再拆一整盒补足**：

- 拆零批次出 3 支
- 整盒批次 A261001 拆 1 盒 → 生成新拆零批次，出 27 支
- 结果是拆零批次余 0，新建拆零批次余 3

这个过程调用 M14-02 的 `split/execute` 完成，M14-04 只负责组织流程。见 3.2.4。

#### 3.2.4 出库执行算法

```
输入：issue_item（药品、approved_qty）、warehouse_id
1. 调 M14-02 分配批次（FEFO，最多 5 个批次）
2. 计算分配结果 total_allocated
3. IF total_allocated < approved_qty AND 药品可拆零：
       计算缺口 gap = approved_qty - total_allocated
       调 M14-02 split/execute 拆整盒补足
       重新分配
4. IF total_allocated < approved_qty：
       记录 short_qty = approved_qty - total_allocated
       按实际分配数出库（不报错，单据标记部分出库）
5. 调 M14-01 stock/apply 逐批次扣减
6. 写 m14_issue_batch 明细
```

**为什么第 4 步不报错？**

药房领药时经常出现"我要 200 支，库里只有 180 支"。这时有两个选择：

- 报错让药师改单重提 → 药师要重新走一遍审批
- 按 180 支出库，单据标记短出 → 药师知道实到 180 支，后续补

第二个选择更符合实际。短出数量记在 `short_qty` 上，收货方确认时可以"接受短出"或"退回整单"。

### 3.3 调拨业务模型

#### 3.3.1 调拨方向

| 方向 | 场景 | 审批层级 |
|---|---|---|
| 药库 → 药房 | 常规补货 | 金额 < 5000 免审 |
| 药房 → 药房 | 门诊药房借给急诊药房 | 双方组长确认 |
| 药房 → 药库 | 退回、集中管理 | 药库管理员确认 |
| 药库 → 药库 | 中心库 → 分库 | 药事科主任 |

#### 3.3.2 调拨单状态机

```
    ┌──────────┐  提交   ┌──────────────┐  审批  ┌──────────┐
    │  DRAFT   │───────►│ SUBMITTED    │──────►│ APPROVED │
    │  草稿    │        │  待审批       │       │ 已审批   │
    └────┬─────┘        └──────┬───────┘       └────┬─────┘
         │                     │ 驳回                │
         │ 作废                ▼                     │ 发货
         │              ┌──────────────┐             ▼
         │              │  REJECTED    │      ┌──────────────┐
         │              └──────────────┘      │  SHIPPED     │
         │                                    │  已发货       │
         ▼                                    └──────┬───────┘
    ┌──────────┐                                     │ 收货
    │CANCELLED │                                     ▼
    │ 已作废    │◄──────────────┐            ┌──────────────┐
    └──────────┘               │            │  RECEIVED    │
                               │            │  已收货       │
                               │            └──────┬───────┘
                               │                   │ 差异处理
                               │                   ▼
                               │            ┌──────────────┐
                               └────────────│  DISPUTED    │
                                            │  有差异       │
                                            └──────────────┘
```

**关键点：`SHIPPED` 状态的重要性**

调拨单在发货和收货之间必然有一个时间窗口，通常几小时到一天。这段时间里，药品：

- 已经从发货仓扣减（`qty_on_hand` 减少）
- 还没到达收货仓（收货仓 `qty_on_hand` 未增加）

这段时间药品在哪？答案是：**在途库存**。

`m14_transfer` 表上有 `in_transit_qty` 字段，发货仓扣减后记录在途数量。全院汇总库存时，必须把在途算进去，否则出现"少了 100 支药"的假警报。

#### 3.3.3 调拨的原子性

调拨执行分两步，两步之间必须用一个字段保护：

```python
# 步骤一：发货方扣减
ship_result = await stock_service.apply(
    warehouse_id=transfer.from_warehouse_id,
    direction="OUT",
    txn_type="TRANSFER_OUT",
    idem_key="TRANSFER:%s:OUT" % transfer.transfer_no,
    items=[...],
)

# 写调拨明细，状态置 SHIPPED
transfer.status = "SHIPPED"
transfer.shipped_at = now()
transfer.in_transit_qty = total_qty
await session.commit()

# 步骤二：收货方增加
receive_result = await stock_service.apply(
    warehouse_id=transfer.to_warehouse_id,
    direction="IN",
    txn_type="TRANSFER_IN",
    idem_key="TRANSFER:%s:IN" % transfer.transfer_no,
    items=[...],
)

transfer.status = "RECEIVED"
transfer.in_transit_qty = 0
```

**为什么不用一个数据库事务包住两步？**

理论上可以，但实际不行，原因有两个：

1. M14-01 的 `stock/apply` 是内部接口调用，跨服务不能共享事务
2. 两步之间往往间隔几小时（发货车在路上），不可能长事务

所以采用 **Saga 模式**：两步各自成功，通过 `SHIPPED` 状态标记中间态，通过幂等键 `TRANSFER:{no}:OUT` 和 `TRANSFER:{no}:IN` 防止重复执行。

如果步骤一成功、步骤二失败，调拨单停在 `SHIPPED`，系统会：

- 每 30 分钟扫描 `SHIPPED` 超过 24 小时的调拨单
- 自动重试步骤二（幂等键保证不会重复加）
- 重试 10 次仍失败则告警，人工介入

#### 3.3.4 调拨差异处理

收货方清点时发现数量与发货方不符：

| 差异类型 | 场景 | 处理 |
|---|---|---|
| `SHORT` | 少到 2 支 | 发货方补发或按实际收货数入账 |
| `OVER` | 多到 3 支 | 补记一笔入库，通知发货方 |
| `WRONG_DRUG` | 到的是另一种药 | 整批退回 |
| `WRONG_BATCH` | 批号不对 | 若效期合适可接受，记录差异 |
| `DAMAGED` | 破损 | 拒收 + 报损单 |

**差异处理原则：** 收货方的库存数一律以**实际清点数为准**。发货方的账面数只作为参考，不作为对账依据。

原因：药品离开发货方仓库后，在运输途中可能发生任何事。如果以发货方账面为准，差异就被掩盖了，下次还会犯同样的错。

### 3.4 报损业务模型

#### 3.4.1 报损原因

| 代码 | 名称 | 典型场景 | 需附件 | 审批 |
|---|---|---|---|---|
| `EXPIRED` | 过期 | 超过有效期 | 药品照片 | 药事科主任 |
| `BROKEN` | 破损 | 玻璃瓶碎了、滴眼液瓶裂 | 照片 | 药事科主任 |
| `DETERIORATED` | 变质 | 浑浊、变色、沉淀 | 照片 | 药事科主任 + 质量负责人 |
| `RECALLED` | 召回 | 厂家召回、药监通知 | 召回通知 | 质量负责人 |
| `CONTAMINATED` | 污染 | 发现异物 | 照片 | 质量负责人 |
| `OTHER` | 其他 | 上述之外 | 说明 | 财务 + 主任 |

#### 3.4.2 报损状态机

```
    ┌──────────┐  提交   ┌──────────────┐  审批  ┌──────────┐
    │  DRAFT   │───────►│ SUBMITTED    │──────►│ APPROVED │
    └────┬─────┘        └──────┬───────┘       └────┬─────┘
         │                     │ 驳回                │
         │ 作废                ▼                     │ 执行销毁
         ▼              ┌──────────────┐             ▼
    ┌──────────┐        │  REJECTED    │      ┌──────────────┐
    │CANCELLED │        └──────────────┘      │  DESTROYED   │
    └──────────┘                              │  已销毁       │
                                              └──────────────┘
```

#### 3.4.3 销毁流程（GSP 强制要求）

```
申请药师              药事科主任          质量负责人        监销人
    │                     │                  │               │
    │ ①创建报损单          │                  │               │
    │  上传药品照片         │                  │               │
    ├────────────────────►│                  │               │
    │                     │ ②审批             │               │
    │                     ├─────────────────►│               │
    │                     │                  │ ③质量审核      │
    │                     │                  ├──────────────►│
    │                     │                  │               │ ④现场监销
    │                     │                  │               │ ⑤拍照
    │                     │                  │               │ ⑥签字确认
    │                     │                  │◄──────────────┤
    │                     │                  │ ⑦执行出库      │
    │                     │                  │  (LOSS_OUT)   │
```

**监销人不能是申请人或审批人**，这是 GSP 的硬性要求。数据库约束 `ck_m14_loss_witness` 强制 `witness_id <> applicant_id AND witness_id <> approver_id`。

**销毁记录保存**：报损单、照片、监销记录保存 **5 年以上**（GSP 第 145 条）。

#### 3.4.4 报损金额计算

```
报损金额 = Σ(批次成本单价 × 报损数量)
```

成本单价来自 `m14_stock_batch.unit_cost`，不是零售价。理由：报损是**资产损失**，损失的是医院的采购成本，不是可以卖出去的零售额。

财务上，这笔金额进"待处理财产损溢"科目，月末转入"营业外支出"。

### 3.5 麻精药品出库专项

麻精药品（`is_narcotic = TRUE` 或 `is_psychotropic = TRUE`）的出库有额外要求：

| 要求 | 说明 | 实现 |
|---|---|---|
| 双人核验 | 发货人和复核人必须不同 | `ck_m14_issue_double` |
| 专柜出库 | 必须从 `NARCOTIC`/`PSYCHOTROPIC` 库位出 | 库位类型校验 |
| 逐支登记 | 每支出库要记录用途 | `purpose` 必填 |
| 班次交接 | 每班次结束必须盘点余量 | 调 M14-09 |
| 空安瓿回收 | 使用后空瓶必须回收记录 | `m14_special_drug_log` |

这些校验在 M14-04 里只做**单据层**的把关（双人、专柜），实际登记与回收走 M14-09 特殊管理药品。

### 3.6 出库成本模型

每笔出库要记录成本，用于财务结转。

**成本单价来源**

| 场景 | 取值 |
|---|---|
| 批次出库 | `m14_stock_batch.unit_cost` |
| 拆零出库 | 整盒成本 / 换算比，保留 4 位小数 |
| 批次成本为空 | 取最近一次入库单价 |

**金额计算**

```
出库成本金额 = ROUND(Σ(unit_cost × issued_qty), 2)
```

**行级先舍入**：每行明细先 `ROUND(..., 2)` 再汇总，不是汇总后再舍入。理由与 M16 一致——明细多时误差累积，退费/对账时对不上。

```python
class IssueService:
    """出库单服务"""

    MAX_BATCHES = 5

    async def allocate(self, issue_id, payload, user):
        """批次分配：调 M14-02 FEFO"""
        issue = await self._get_issue(issue_id)
        if issue.status != "APPROVED":
            raise BizError(55352, "出库单状态不允许分配")

        await self.repo.clear_batches(issue_id)

        allocated = []
        short_items = []
        for line in payload.items:
            result = await m14_02_client.allocate(
                warehouse_id=issue.from_warehouse_id,
                drug_id=line.drug_id,
                qty=line.request_qty,
                strategy=payload.strategy,
                max_batches=self.MAX_BATCHES,
            )
            batches = result.get("batches", [])
            total = sum(Decimal(str(b["qty"])) for b in batches)
            if total < line.request_qty:
                short_items.append({
                    "issue_item_id": line.issue_item_id,
                    "request_qty": str(line.request_qty),
                    "allocated_qty": str(total),
                    "short_qty": str(line.request_qty - total),
                })
            await self.repo.bulk_create_batches(
                issue_id, line.issue_item_id, batches)
            allocated.append({
                "issue_item_id": line.issue_item_id,
                "drug_id": line.drug_id,
                "approved_qty": str(line.request_qty),
                "batches": batches,
            })

        await self.audit.log("M14_ISSUE_ALLOCATE", issue_id, user)
        return {"issue_no": issue.issue_no,
                "allocated": allocated,
                "short_items": short_items}
```

```python
class IssueService:
    """出库单服务"""

    async def execute(self, issue_id, payload, user):
        """执行出库：调 M14-01 扣库存"""
        issue = await self._lock_issue(issue_id)
        if issue.status not in ("APPROVED", "EXEC_FAIL"):
            raise BizError(55352, "出库单状态不允许执行")

        items = await self.repo.list_items(issue_id)
        batches = await self.repo.list_batches(issue_id)
        if not batches:
            raise BizError(55359, "存在未分配的明细行")

        # 麻精药品双人核验
        if await self._has_narcotic(items):
            if not payload.checker_id:
                raise BizError(55357, "麻精药品出库必须双人核验")
            if payload.checker_id == payload.operator_id:
                raise BizError(55357, "复核人不能与操作人相同")

        await self.repo.update_status(issue_id, "EXECUTING")

        apply_items = []
        for b in batches:
            apply_items.append({
                "batch_id": b.batch_id,
                "qty": str(b.issued_qty),
            })

        try:
            result = await m14_01_client.apply(
                warehouse_id=issue.from_warehouse_id,
                direction="OUT",
                txn_type=self._txn_type(issue.issue_type),
                idem_key="ISSUE:%s" % issue.issue_no,
                items=apply_items,
                operator_id=payload.operator_id,
            )
        except Exception as exc:
            await self.repo.update_status(issue_id, "EXEC_FAIL")
            await self.repo.update_fail_reason(
                issue_id, str(exc)[:512])
            raise BizError(55360, "出库执行失败：%s" % exc)

        total_issued = sum(
            Decimal(str(b.issued_qty)) for b in batches)
        await self.repo.update_issued(issue_id, total_issued)
        await self.repo.update_status(issue_id, "EXECUTED")
        await self.audit.log("M14_ISSUE_EXECUTE", issue_id, user)

        return {
            "issue_no": issue.issue_no,
            "status": "EXECUTED",
            "issued_qty": str(total_issued),
            "stock_txn_ids": result.get("txn_ids", []),
            "short_qty": str(self._calc_short(items, batches)),
        }
```

#### 6.6.5 TransferService 收货

```python
class TransferService:
    """调拨服务"""

    async def receive(self, transfer_id, payload, user):
        """确认收货：按实收量入库"""
        transfer = await self._lock_transfer(transfer_id)
        if transfer.status != "SHIPPED":
            raise BizError(55364, "调拨单状态不允许收货")

        items = await self.repo.list_items(transfer_id)
        item_map = {it.id: it for it in items}

        has_diff = False
        apply_items = []
        for rec in payload.items:
            it = item_map.get(rec.transfer_item_id)
            if it is None:
                raise BizError(55364, "调拨明细不存在")
            diff = Decimal(str(rec.received_qty)) - it.transfer_qty
            if diff != 0:
                has_diff = True
                if not rec.diff_reason:
                    raise BizError(
                        55365, "差异必须说明原因")
                if rec.diff_reason == "DAMAGED" and not rec.attachments:
                    raise BizError(55366, "破损差异必须上传照片")
            apply_items.append({
                "batch_id": it.batch_id,
                "qty": str(rec.received_qty),
            })

        result = await m14_01_client.apply(
            warehouse_id=transfer.to_warehouse_id,
            direction="IN",
            txn_type="TRANSFER_IN",
            idem_key="TRANSFER:%s:IN" % transfer.transfer_no,
            items=apply_items,
            operator_id=payload.operator_id,
        )

        new_status = "DISPUTED" if has_diff else "RECEIVED"
        await self.repo.mark_received(
            transfer_id, new_status, payload, result.get("txn_ids", []))
        await self.audit.log("M14_TRANSFER_RECEIVE", transfer_id, user)

        received_total = sum(
            Decimal(str(r.received_qty)) for r in payload.items)
        return {
            "transfer_no": transfer.transfer_no,
            "status": new_status,
            "received_qty": str(received_total),
            "in_transit_qty": "0",
```

#### 6.6.6 LossService 执行销毁

```python
class LossService:
    """报损服务"""

    MIN_DESTROY_PHOTOS = 3

    async def destroy(self, loss_id, payload, user):
        """执行销毁"""
        loss = await self._lock_loss(loss_id)
        if loss.status != "APPROVED":
            raise BizError(55364, "报损单状态不允许销毁")

        if payload.witness_id in (loss.applicant_id, loss.approver_id):
            raise BizError(55369, "监销人不能是申请人或审批人")

        if payload.destroy_method == "ONSITE":
            if len(payload.attachments or []) < self.MIN_DESTROY_PHOTOS:
                raise BizError(55370, "现场销毁至少需要 3 张照片")
        else:
            if not payload.delegate_no:
                raise BizError(55370, "委托销毁必须填写委托单号")

        items = await self.repo.list_items(loss_id)
        apply_items = [{"batch_id": it.batch_id,
                        "qty": str(it.loss_qty)} for it in items]

        result = await m14_01_client.apply(
            warehouse_id=loss.warehouse_id,
            direction="OUT",
            txn_type="LOSS_OUT",
            idem_key="LOSS:%s" % loss.loss_no,
            items=apply_items,
            operator_id=payload.operator_id,
        )

        await self.repo.mark_destroyed(loss_id, payload,
                                       result.get("txn_ids", []))
        await self.audit.log("M14_LOSS_DESTROY", loss_id, user)

        return {
            "loss_no": loss.loss_no,
            "status": "DESTROYED",
            "loss_amount": str(loss.total_cost),
            "stock_txn_ids": result.get("txn_ids", []),
            "destroyed_at": payload.destroy_at.isoformat(),
        }
```

### 8.2 状态与库存一致性规则

**规则的核心：状态机必须与库存变更严格对应。**

| 状态转换 | 库存变化 | 关键保障 |
|---|---|---|
| APPROVED → EXECUTING | 无 | — |
| EXECUTING → EXECUTED | 扣减 | 幂等键 `ISSUE:{no}` |
| EXECUTING → EXEC_FAIL | 无变化 | 事务回滚 |
| SHIPPED → RECEIVED | 调入仓增加 | 幂等键 `TRANSFER:{no}:IN` |
| DESTROYED | 扣减 | 幂等键 `LOSS:{no}` |

**为什么 EXECUTED 不能回退到 APPROVED？**

如果允许状态回退，运维人员可以"改一下状态"把已扣的库存还回去，但这时候：

- `m14_stock_txn` 里已经有出库流水，流水表是只增不改的，删不掉
- 库存批次表 `qty_on_hand` 已经减了
- 如果状态回退但不改库存，单据说"没执行"库存说"执行了"，对不上
- 如果状态回退同时反向写一条入库流水，那等于做了一次撤销，**这就是新建反向单据做的事**

所以正确做法是：新建一张 `RETURN_IN` 类型的入库单，写明"撤销 CK202610210001 的出库"。这样两张单据都在，审计链完整。

|---|---|---|

## 附录 C：术语表

| 术语 | 说明 |
|---|---|
| 在途库存 | 调拨发货后、收货前，库存既不在调出仓也不在调入仓 |

| 短出 | 实际出库数量小于申请/批准数量 |
