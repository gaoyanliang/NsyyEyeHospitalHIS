## 4. 数据结构设计

### 4.1 ER 关系图

```
┌───────────────────────────────────────────────────────────────────────────┐
│  M14-01（只读引用）                                                       │
│  m14_stock_batch（batch_id / drug_id / qty_available / expiry_date）      │
└───────┬─────────────────┬──────────────────┬──────────────────────────────┘
        │                 │                  │
        ▼                 ▼                  ▼
┌───────────────┐ ┌───────────────┐ ┌────────────────────┐
│ m14_alloc_task│ │m14_expiry_alert│ │m14_replenish_sugg.│
│ 预占任务      │ │ 效期预警      │ │ 补货建议           │
│ lock_no       │ │ level         │ │ trigger_type       │
│ items JSONB   │ │ days_to_expiry│ │ suggested_qty      │
└───────────────┘ └───────┬───────┘ └────────────────────┘
                          │ alert_id
                          ▼
                  ┌──────────────────┐
                  │m14_expiry_handle │
                  │ 处理方案         │
                  │ action           │
                  └──────────────────┘

┌──────────────────┐        ┌──────────────────────┐
│ m14_split_record │        │  m14_alloc_config    │
│ 拆零记录         │        │  策略参数（键值表）  │
│ source_batch_id  │        └──────────────────────┘
│ target_batch_id  │
└──────────────────┘
```

**设计说明**

| 决策 | 内容 | 理由 |
|---|---|---|
| 不存候选批次快照 | `m14_alloc_task.items` 用 JSONB 存分配明细 | 分配结果是瞬时决策，不需要长期可查（超过 24h 的锁已被释放） |
| 预警与处理分离 | `m14_expiry_alert` 存"发现了什么"，`m14_expiry_handle` 存"做了什么" | 一个预警可能被多次处理（退厂失败改报损） |
| 拆零双批次引用 | `source_batch_id` + `target_batch_id` | 完整记录"从哪来、到哪去" |
| 参数键值表 | `m14_alloc_config` 不建固定列 | 策略参数会随业务演进增加，固定列每次都要 DDL |

**items JSONB 结构**

```json
[
  {
    "batch_id": 8801,
    "batch_no": "240815",
    "expiry_date": "2026-08-14",
    "allocated_qty": "3.0000",
    "qty_available_at_lock": "45.0000",
    "location_code": "A-01",
    "is_cold_chain": false

```

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| pk_m14_alloc_task | PRIMARY | id | 主键 |
| uk_m14_alloc_lock_no | UNIQUE | lock_no | 锁号唯一 |
| idx_m14_alloc_status | NORMAL | status, expire_at | **超时释放扫描（最热）** |
| idx_m14_alloc_source | NORMAL | source_type, source_id | 按来源单据查 |
| idx_m14_alloc_operator | NORMAL | operator_id, locked_at DESC | 按人查 |
| idx_m14_alloc_drug | NORMAL | drug_id, locked_at DESC | 按药品查 |
| idx_m14_alloc_locked | NORMAL | locked_at WHERE status = 'LOCKED' | 活动锁 |

**约束说明**

```sql
ALTER TABLE m14_alloc_task
    ADD CONSTRAINT ck_m14_alloc_status
    CHECK (status IN ('LOCKED', 'CONSUMED', 'RELEASED', 'EXPIRED'));

ALTER TABLE m14_alloc_strategy
    ADD CONSTRAINT ck_m14_alloc_strategy
    CHECK (strategy IN ('FEFO', 'FIFO', 'SPECIFIED',
                        'SPLIT_FIRST', 'LARGEST_FIRST'));

ALTER TABLE m14_alloc_task
    ADD CONSTRAINT ck_m14_alloc_qty
    CHECK (need_qty > 0 AND allocated_qty > 0
           AND allocated_qty <= need_qty);

ALTER TABLE m14_alloc_task
    ADD CONSTRAINT ck_m14_alloc_batch_count
    CHECK (batch_count BETWEEN 1 AND 20);

-- JSONB 必须是数组且非空
ALTER TABLE m14_alloc_task
    ADD CONSTRAINT ck_m14_alloc_items
    CHECK (jsonb_typeof(items) = 'array'
           AND jsonb_array_length(items) >= 1);

-- 状态与时间戳自洽
ALTER TABLE m14_alloc_task
    ADD CONSTRAINT ck_m14_alloc_consumed
    CHECK (status <> 'CONSUMED' OR consumed_at IS NOT NULL);

ALTER TABLE m14_alloc_task
    ADD CONSTRAINT ck_m14_alloc_released
    CHECK (status NOT IN ('RELEASED', 'EXPIRED')
           OR released_at IS NOT NULL);

-- 过期时间必须晚于锁定时间
ALTER TABLE m14_alloc_task
    ADD CONSTRAINT ck_m14_alloc_expire
    CHECK (expire_at > locked_at);

-- 锁号格式
ALTER TABLE m14_alloc_task
    ADD CONSTRAINT ck_m14_alloc_no
    CHECK (lock_no ~ '^LK[0-9]{8}[0-9]{6}$');
```

**状态机**

```
        ┌──────────┐
        │  LOCKED  │  创建
        └────┬─────┘
             │
   ┌─────────┼──────────┬──────────────┐
   │发药成功 │主动放弃  │超过 expire_at│
   ▼         ▼          ▼              │
┌────────┐ ┌────────┐ ┌──────────┐    │
│CONSUMED│ │RELEASED│ │ EXPIRED  │◄───┘
└────────┘ └────────┘ └──────────┘
   终态       终态        终态
```

**量级估算**

| 项 | 数值 |
|---|---|
| 日均预占任务 | 1,500（门诊发药 1,400 + 摆药 100） |
| 年行数 | 550,000 |
| 单行大小 | 约 1,200 B（含 JSONB） |
| 年数据量 | 约 660 MB |
| 保留 | 热 90 天（在线），90 天后归档 |

**分区：** 不分区，但设置 90 天归档策略。

```sql
-- 每日 03:30 归档 90 天前的已完成任务
INSERT INTO m14_alloc_task_archive
SELECT * FROM m14_alloc_task
 WHERE status <> 'LOCKED' AND created_at < NOW() - INTERVAL '90 days';

DELETE FROM m14_alloc_task
 WHERE status <> 'LOCKED' AND created_at < NOW() - INTERVAL '90 days';
```

```sql
    ADD CONSTRAINT ck_m14_expiry_status
    CHECK (status IN ('ACTIVE', 'RESOLVED', 'IGNORED'));

    ADD CONSTRAINT ck_m14_expiry_notify

           OR (level = 'WARNING' AND days_to_expiry > 0
               AND days_to_expiry <= 30)

ALTER TABLE m14_expiry_alert
    ADD CONSTRAINT ck_m14_expiry_amount
    CHECK (amount IS NULL OR unit_cost IS NULL
           OR ABS(amount - ROUND(qty_available * unit_cost, 2)) <= 0.01);

-- 已解决必须有解决人

    ADD CONSTRAINT ck_m14_expiry_resolved
    CHECK (status = 'ACTIVE'
           OR (resolved_at IS NOT NULL AND resolved_by IS NOT NULL));

ALTER TABLE m14_expiry_alert
    ADD CONSTRAINT ck_m14_expiry_action
    CHECK (suggested_action IN (
        'OUTBOUND_FIRST', 'RETURN_SUPPLIER',
        'TRANSFER_OUT', 'PROMOTION', 'DESTROY'));
```

**为什么按天生成预警记录而不是查询时实时计算**

如果每次打开预警看板都实时扫描 `m14_stock_batch` 并计算等级，会有三个问题：

1. **无法统计"这个预警持续了多少天"** —— 药房主任最关心的是"这个批次的预警已经挂了 20 天了，为什么还没处理"
2. **无法记录"是谁在什么时候处理了"** —— 实时计算没有持久化载体
3. **通知无法去重** —— 每天 08:00 推送给药房负责人，只能靠推送记录去重

按天落库后，`SELECT * FROM m14_expiry_alert WHERE batch_id=X ORDER BY alert_date` 就能看到完整的预警生命周期。

**量级估算**

| 项 | 数值 |
|---|---|
| 日新增预警 | 15~30 条 |
| 年行数 | 约 8,000 |
| 单行大小 | 约 600 B |
| 年数据量 | 约 5 MB |
| 保留 | 3 年 |

**分区：** 不分区。

**为什么拆零记录要分区**

拆零记录是**高频写入**：日均 300~500 次（门诊发药 1,400 张处方中约 30% 需要拆零）。3 年累计约 50 万行，单表查询会逐渐变慢。

分区后：

- 查询"最近 3 个月"只扫 3 个分区
- 归档"3 年前"直接 `DROP PARTITION`

| 年行数 | 146,000 |
| 单行大小 | 约 700 B |
| 年数据量 | 约 102 MB |
| 保留（热） | 36 个月 |

**分区：** 按 `created_at` 月度 RANGE 分区，预建 36 个月。

```sql
CREATE TABLE m14_split_record (
    ...
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_at_month VARCHAR(7) NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE m14_split_record_2026_10
    PARTITION OF m14_split_record
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

**COALESCE(scope_id, 0) 的必要性**

PostgreSQL 的唯一索引把 `NULL` 当作互不相等。如果索引是 `(param_code, scope, scope_id)`，而 `scope='GLOBAL'` 时 `scope_id` 恒为 `NULL`，那么：

```sql
INSERT INTO m14_alloc_config (param_code, scope, scope_id, param_value)
VALUES ('M14.EXPIRY.ALERT_DAYS', 'GLOBAL', NULL, '90');
INSERT INTO m14_alloc_config (param_code, scope, scope_id, param_value)
VALUES ('M14.EXPIRY.ALERT_DAYS', 'GLOBAL', NULL, '120');
```

两条都能成功插入。之后 `SELECT param_value ... ORDER BY id LIMIT 1` 取到 `90`，但 `ORDER BY id DESC` 取到 `120` —— 同一个参数两个值，取决于查询写法，这是最难排查的一类 bug。

`COALESCE(scope_id, 0)` 把 `NULL` 归一为 `0`，唯一索引才能真正生效。

```python
class AllocationPreviewIn(BaseModel):
    warehouse_id: int
    drug_id: int
    need_qty: Decimal = Field(..., gt=0, decimal_places=3)
    strategy: AllocStrategy = "FEFO"
    specified_batch_no: Optional[str] = Field(None, max_length=64)

    @model_validator(mode="after")
    def check_specified(self):
        if self.strategy == "SPECIFIED" and not self.specified_batch_no:
            raise ValueError("指定批号策略必须填写批号")
        return self

class ExpiryHandleIn(BaseModel):
    batch_id: int
    action: ExpiryAction
    handle_qty: Decimal = Field(..., gt=0)
    supplier_id: Optional[int] = None
    return_ratio: Optional[Decimal] = Field(None, gt=0, le=1)
    target_warehouse_id: Optional[int] = None
    reason: str = Field(..., min_length=10, max_length=512)
    remark: Optional[str] = Field(None, max_length=512)

    @model_validator(mode="after")
    def check_action(self):
        if self.action == "RETURN_SUPPLIER":
            if not self.supplier_id:
                raise ValueError("退厂必须选择供应商")
            if not self.return_ratio:
                raise ValueError("退厂必须填写退厂比例")
        if self.action == "TRANSFER_OUT" and not self.target_warehouse_id:
            raise ValueError("调拨必须选择目标仓库")
        return self

            raise ValueError("预警天数必须大于警告天数")
        return self
```

## 附录 B：策略与动作代码表

### B.1 分配策略

| 代码 | 名称 | 排序依据 | 适用 |
|---|---|---|---|
| `FEFO` | 先到期先出 | `expiry_date ASC` | 默认 |
| `FIFO` | 先进先出 | `first_in_at ASC` | 无批次管理 |
| `SPECIFIED` | 指定批号 | 精确匹配 | 临床试验 |
| `SPLIT_FIRST` | 拆零优先 | 拆零批次前置 | 零散发药 |
| `LARGEST_FIRST` | 大包装优先 | `qty_available DESC` | 批量出库 |

### B.2 效期等级

| 代码 | 名称 | 判定 | 颜色 |
|---|---|---|---|
| `NEAR_EXPIRY` | 临近效期 | `30 < days <= 90` | 黄 |
| `WARNING` | 警告 | `0 < days <= 30` | 橙 |
| `EXPIRED` | 已过期 | `days <= 0` | 红 |

### B.3 处理动作

| 代码 | 名称 | 后续单据 |
|---|---|---|
| `OUTBOUND_FIRST` | 优先出库 | 无（仅标记） |
| `RETURN_SUPPLIER` | 退厂 | M14-03 采购退货单 |
| `TRANSFER_OUT` | 调拨 | M14-04 调拨单 |
| `PROMOTION` | 加速使用 | 无（通知临床） |
| `DESTROY` | 报损销毁 | M14-05 报损单 |

### B.4 补货触发条件

| 代码 | 名称 | 判定 | 优先级 |
|---|---|---|---|
| `ZERO_STOCK` | 零库存 | `total <= 0` | HIGH |
| `BELOW_SAFETY` | 低于安全库存 | `total <= safety` | HIGH |
| `BELOW_REORDER` | 低于订货点 | `total <= reorder` | MEDIUM |
| `ABOVE_MAX` | 超上限 | `total > max * 1.2` | LOW |
| `SLOW_MOVING` | 慢动销 | 90 天无出库 | LOW |
