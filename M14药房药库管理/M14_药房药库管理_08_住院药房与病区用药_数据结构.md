**设计说明**

| 决策 | 内容 | 理由 |
|---|---|---|
| 摆药明细不分「药品行」与「批次行」两表 | 一个 `ward_dispense_item` 对应「患者 × 医嘱 × 时段」，批次信息存 JSONB | 住院摆药一行通常只用一个批次（单患者单医嘱单时段），拆表反而增加连接 |
| 分包独立成表 | `m14_ward_package` | 分包袋有唯一条码，需独立追溯 |
| 退药独立成表 | `m14_ward_return` + `_item` | 退药是独立业务事实，不能改写摆药记录 |
| 住院快照独立成表 | `m14_ward_admission_snap` | M05 未实现，先自建最小快照；M05 完成后改为只读同步表 |
| 不建外键到 M05/M07/M14-01 | 仅存 ID 与冗余快照 | 跨模块解耦，避免跨库锁定 |

> **⚠️ 只读铁律：** 摆药单进入 `RECEIVED` 后，其明细由**只读触发器**保护，任何 UPDATE/DELETE 都会被拒绝。退药必须新建 `m14_ward_return`，不得改写摆药记录。

    ADD CONSTRAINT ck_m14_ward_dispense_check_result
    CHECK (check_result IS NULL OR check_result IN ('PASS', 'REJECT'));

    ADD CONSTRAINT ck_m14_ward_dispense_stock
    CHECK (stock_status IN ('NONE', 'SUCCESS', 'FAILED'));

-- 数量

    ADD CONSTRAINT ck_m14_ward_dispense_qty

           AND total_qty >= 0 AND prepared_qty >= 0
           AND shortage_count >= 0);

ALTER TABLE m14_ward_dispense
    ADD CONSTRAINT ck_m14_ward_dispense_prepared_limit
    CHECK (prepared_qty <= total_qty);

-- 有缺药标志与笔数一致
ALTER TABLE m14_ward_dispense
    ADD CONSTRAINT ck_m14_ward_dispense_shortage
    CHECK ((has_shortage = TRUE AND shortage_count > 0)

ALTER TABLE m14_ward_dispense
    ADD CONSTRAINT ck_m14_ward_dispense_prepared

           OR (dispatcher_id IS NOT NULL
               AND prepared_at IS NOT NULL));

ALTER TABLE m14_ward_dispense

    CHECK (checker_id IS NULL OR dispatcher_id IS NULL
           OR checker_id <> dispatcher_id);

ALTER TABLE m14_ward_dispense
    ADD CONSTRAINT ck_m14_ward_dispense_checked
    CHECK (status NOT IN ('CHECKED', 'SHIPPED', 'RECEIVED',

               AND checked_at IS NOT NULL

**关键设计说明**

**为什么 `uk_m14_ward_dispense_active` 是必须的？**

考虑并发场景：06:00 定时任务生成「上午」摆药单时，恰好有人在手工点击「生成摆药单」：

```
id  dispense_no      date        period  ward_id  status
1   WD20261022M01  2026-10-22  MORNING  101     PENDING  ← 定时任务
2   WD20261022M02  2026-10-22  MORNING  101     PENDING  ← 手工点击
```

后果极其严重：

- 药剂员看到两张单子，**同一批药摆两次**
- 库存扣两次，账实不符
- 病区收到两份药，可能给患者用双倍剂量

部分唯一索引（只约束非终态）从数据库层面杜绝。

**`ck_m14_ward_dispense_double` 是摆药准确率的核心保障**

这条约束在数据库层面强制「摆药人 ≠ 复核人」：

```sql
CHECK (checker_id IS NULL OR dispatcher_id IS NULL
       OR checker_id <> dispatcher_id)
```

它的意义在于：**即使应用层有 bug，也无法产生同人复核的记录**。

理论依据：《医疗机构处方审核规范》第十五条「调配药师与核对药师不得为同一人」。

真实故障场景：某医院住院药房在早班人员少时，让一位药师同时担任摆药与复核。某次摆药时把「左氧氟沙星滴眼液 0.5%」拿成了「0.3%」规格，复核时因为是自己配的，只扫了一眼药名就通过，病区给三位患者用了一周错误浓度。

数据库约束让管理要求变成技术强制。

**为什么 `diff_items` 用 JSONB 数组而不是子表？**

差异登记结构：

```json
[
    {"dispense_item_id": 5001, "required": 3, "received": 1, "diff": -2},
    {"dispense_item_id": 5002, "required": 4, "received": 4, "diff": 0}
]
```

特点：

- 永远整体读写（一次签收登记一份差异清单）
- 无人按差异项做聚合查询
- 项数少（一个病区通常 0~5 条）

用 JSONB 数组而非子表，减少一张表和一次 JOIN。若未来需要按药品统计签收差异率，从子表改成独立的 `m14_ward_dispense_diff` 表即可迁移。

**`ck_m14_ward_dispense_received` 中的 `seal_match = TRUE`**

签收时封条必须一致，否则必须拒收。这条约束把「封条不一致也能签收」这条路堵死：

```sql
CHECK (status NOT IN ('RECEIVED', 'RETURNED', 'CLOSED')
       OR (... AND seal_match = TRUE))
```

如果护士点「确认签收」时封条号码不一致，应用层先拒绝（`55566`），即使绕过应用层直接写库，数据库也会拒绝。

背景：封条是药车运输途中的防篡改标识。封条破了的药车理论上可能被调包，必须整车上报药房核查，不能签收使用。

**`uk_m14_ward_dispense_item_key` 的必要性**

```
同单同医嘱只出现一次
```

考虑场景：一张住院长期医嘱「左氧氟沙星 QID 连用 7 天」，在「上午」时段的执行次数是 1（QID 每天 4 次，分到 4 个时段，上午 1 次）。

如果系统在生成时把这条医嘱算了两次（比如既按 `QD` 又按 `QID` 处理），会生成两条明细：

```
seq  order_id  drug         required_qty
1    7001      左氧氟沙星    1
2    7001      左氧氟沙星    1    ← 重复
```

药剂员按单子摆 2 支，病区收到 2 支，可能给患者用双倍剂量。

唯一约束从数据库层面杜绝。

**`ck_m14_ward_dispense_item_balance` 的必要性**

```
已摆 + 缺药 = 应摆
```

这条等式保证「没有凭空消失的药」：

- 应摆 3 支，已摆 3 支，缺药 0 → 3 + 0 = 3 ✅
- 应摆 3 支，已摆 1 支，缺药 2 → 1 + 2 = 3 ✅
- 应摆 3 支，已摆 1 支，缺药 0 → 1 + 0 ≠ 3 ❌ 拦住

第三种情况是「少摆了但没登记」，会让住院费用少记、病区拿不到药也不会被告知。

**`ck_m14_ward_dispense_item_return_limit` 的行级防超退**

```sql
CHECK (returned_qty <= issued_qty)
```

住院退药的特点：可以多次退。比如患者住院 10 天，第 3 天停了某个药，退回剩余 8 天量；第 7 天又停另一个药，再退。

如果没有这条约束，第二次退药可能退超过实际发出的量：

```
实发 10，第 1 次退 4 → returned_qty = 4 ✅
第 2 次退 8 → 4 + 8 = 12 > 10 ❌ 拦住
```

**为什么一个明细只存一个批次？**

住院摆药的特点是：**单患者、单医嘱、单时段**，通常一个批次就够。

例如「张三 · 左氧氟沙星 · 上午 · 1 支」，药房在摆药时从批次 240815 取 1 支即可。极少数情况需要两个批次（如批次 240815 只剩半支不足），此时拆成两条明细（一条 `exec_count=1` 拆两个 `batch`），或者登记部分缺药后再补摆。

这比门诊简单：门诊一张处方可能一次发 7 支，跨两个批次，必须拆；住院一次只发 1~2 支，跨批概率低。

> 若未来出现高频跨批场景，可将 `batch_id`/`batch_no`/`prepared_qty` 拆到独立的 `m14_ward_dispense_batch` 子表。当前设计已保留 `batch_id` 索引，迁移成本低。

| 项 | 数值 |
|---|---|
| 每摆药单平均明细 | 25 条 |
| 年行数 | 约 146,000 |
| 单行大小 | 约 700 B |

**`uk_m14_ward_package_patient_time` 的 `WHERE has_error = FALSE` 说明**

这个部分唯一索引保证「同一患者同一天同一时点只有一个有效分包袋」。

**为什么排除 `has_error = TRUE` 的？**

分包出现差错时，正确流程是：

1. 登记差错（`has_error = TRUE`）
2. 重新分包生成新袋

如果唯一索引不排除差错的袋子，重新分包会被拒绝（因为旧袋子还在）。排除后，同一时点可以有一个「差错的旧袋」和一个「正确的新袋」共存，符合真实业务。

**`items` JSONB 结构**

```json
[
    {
        "drug_id": 5101,
        "drug_code": "D0101",
        "drug_name": "泼尼松片",
        "specification": "5mg",
        "quantity": 2,
        "unit": "片",
        "batch_id": 8001,
        "batch_no": "240815"
    },
    {
        "drug_id": 5102,
        "drug_code": "D0102",
        "drug_name": "甲钴胺片",
        "specification": "0.5mg",
        "quantity": 1,
        "unit": "片",
        "batch_id": 8002,
        "batch_no": "240901"
    }
]
```

**为什么分包明细用 JSONB 而不是子表？**

- 分包袋的明细永远是整体读写（生成时一次性写入，打印时整体读取）
- 无按药品聚合查询需求（药品统计走 `m14_ward_dispense_item`）
- 项数少（1~5 项）

**为什么分包要有独立条码？**

护士在病区给药前扫分包袋条码，M08 护士站记录「几点几分给谁用了这袋药」。

条码是打通「药房分包 → 病区执行」的关键：
- 药房知道这袋药配了什么
- 病区知道这袋药给了谁
- 两者通过条码一一对应

条码 = 包号，简化实现（避免两套编号体系）。

**`ck_m14_ward_return_qty_balance` 的意义**

```
可再用数量 + 报废数量 = 退药总数量
```

这保证「退回来的每一支药都有去处」：

- 进了库存（可再用）
- 或者报废了（不可再用）

不能出现「退了 4 支，但只记录了 3 支入库、0 支报废」这种账实不符。

**`ck_m14_ward_return_self_approve` 与 `_self_judge` 是退药的双重底线**

退药是**资金流向反转**的动作（住院费用要冲减）。如果申请人自己就能判定或审批自己的退药，等于没有控制。

真实风险场景：某药师与外部人员串通，虚构退药（实际药品未退回），自己提交、自己判定「可再用」、自己审批，住院费用冲减后退费到指定账户。有这两条约束，这条路走不通。

**为什么 `need_approve` 与金额绑定？**

```sql
CHECK ((need_approve = TRUE AND total_amount > 500.00)
       OR (need_approve = FALSE))
```

如果分开写，可能出问题：

- 金额 2000 元但 `need_approve = FALSE`（审批阈值被绕过）
- 金额 100 元但 `need_approve = TRUE`（无谓审批）

约束强制两者绑定。注意：`need_approve = FALSE` 时金额可以是任意值（包括 > 500），这允许「参数被从 500 改到 5000 后，历史数据不受影响」——参数变更只影响新单。

**`ck_m14_ward_return_self_judge` 的实施说明**

判定人必须 ≠ 申请人。但病区护士发起的退药，药房药师判定——天然是两个人。

问题在药房自家人：药师自己发起，自己判定。这条约束拦住。

**`ck_m14_ward_return_item_limit` 是防超退的最后一道防线**

```sql
CHECK (returned_before + return_qty <= issued_qty)
```

这条约束在**行级**保证累计退药不超过原实发。

为什么必须有？因为住院退药可以分多次：

```
第 3 天：停医嘱，退 8 支（issued=10, returned_before=0, return_qty=8）→ 0+8 ≤ 10 ✅
第 7 天：又停另一部分，退 3 支（returned_before=8, return_qty=3）→ 8+3 > 10 ❌ 拦住
```

没有这条约束，第二次退药会通过，住院费用被多冲减 1 支的钱。

**`returned_before` 是快照而非计算值**

应用层在插入时计算 `returned_before = SUM(已退数量)`，然后写死。

这是"乐观"的做法——用唯一约束 + 校验兜底。更严格的做法是在 `ward_dispense_item` 上维护 `returned_qty` 累积列并加行锁。

本项目采用**两者结合**：

- `m14_ward_dispense_item.returned_qty` 累积列（快速查询剩余可退）
- `m14_ward_return_item.returned_before` 快照（审计追溯本次退药前的基线）

退药提交时，服务层在事务内先 `SELECT ... FOR UPDATE` 锁 `ward_dispense_item`，再读 `returned_qty` 作为 `returned_before`，插入后更新累积列。这样并发两笔退药时，第二笔会被行锁阻塞，读到最新值。

**`ck_m14_ward_return_item_special` 是特殊药品退药的红线**

```sql
CHECK (is_special = FALSE
       OR (special_sign_1 IS NOT NULL
           AND special_sign_2 IS NOT NULL
           AND special_sign_1 <> special_sign_2))
```

麻醉药品、第一类精神药品的退药，**必须两人同时在场签字**，且不能是同一人（自签自核无意义）。

依据：《麻醉药品和精神药品管理条例》第四十四条要求专册登记、双人复核。

**当前策略（阶段一）：** 由 M07-03 医嘱接口带入的 `admission_id` / `ward_id` / `bed_no` / `patient_id` 构建快照，`source = 'M07'`。

**M05 上线后（阶段二）：**

1. M05 推送 `POST /internal/v1/m14/inpatient/on-admission-sync` 更新本表
2. `source = 'M05'`，`synced_from_m05 = TRUE`
3. 本表退化为**只读镜像**，所有写入必须来自 M05
4. M14-08 不再从 M07 反推

**为什么不能直接用 M07 的医嘱数据而不建表？**

因为摆药需要按「病区 → 床号 → 患者」组织，而 M07 的医嘱数据是按「患者 → 医嘱」组织的。没有病区-患者关系，无法生成按病区的摆药单。

**过敏史、肝肾功能为什么在这张表？**

摆药时的用药安全检查需要它们：

- 过敏史：摆药前核对（如青霉素过敏患者禁用相关药品）
- 肝肾功能：影响剂量（肾功能不全患者需调整剂量）

这些信息在 M05 才有，当前从 M07 的入院记录带入。

**量级估算**

| 项 | 数值 |
|---|---|
| 在院患者 | 约 100 人 |
| 年新增（含历史） | 约 4,800 |
| 单行大小 | 约 800 B |
| 年增量 | 约 3.8 MB |

**分区：** 不分区。

**归档迁移说明**

`m14_ward_dispense` 保留 5 年（GSP 要求）。归档流程：

```sql
-- 1. 建归档表
CREATE TABLE IF NOT EXISTS m14_ward_dispense_archive (
    LIKE m14_ward_dispense INCLUDING DEFAULTS
);

-- 2. 归档 5 年前数据（仅终态）
INSERT INTO m14_ward_dispense_archive
SELECT * FROM m14_ward_dispense
WHERE dispense_date < CURRENT_DATE - INTERVAL '5 years'
  AND status IN ('CLOSED', 'CANCELLED')
ON CONFLICT (id) DO NOTHING;

-- 3. 归档关联明细
INSERT INTO m14_ward_dispense_item_archive
SELECT i.* FROM m14_ward_dispense_item i
JOIN m14_ward_dispense_archive a ON a.id = i.dispense_id;

-- 4. 确认行数一致后删除
DELETE FROM m14_ward_dispense
WHERE id IN (SELECT id FROM m14_ward_dispense_archive)
  AND status IN ('CLOSED', 'CANCELLED');
```

> **⚠️ 归档铁律：** 归档表行数必须与被删除行数**完全一致**才能删主表。摆药明细的批次信息是药监追溯依据，归档后必须仍可按 `batch_no` 查到患者。
