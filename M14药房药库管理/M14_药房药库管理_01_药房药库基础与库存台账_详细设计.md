## 1. 模块概述

### 1.1 模块定位

药房药库基础与库存台账是 M14 药房药库管理的**地基**。它回答："**这个药现在有多少、在哪、是哪个批号、什么时候过期？**"

```
┌──────────────────────────────────────────────────────────────┐
│  M01-03 药品主数据                                            │
│  "世界上有这种药，它长什么样，采购价零售价多少"                 │
└────────────────────────┬─────────────────────────────────────┘
                         │ 药品属性（drug_code / 单位 / 转换比 / 批次管理标志）
                         ▼
┌──────────────────────────────────────────────────────────────┐
│  M14-01 基础与库存台账（本文档）★ 数量的唯一真相              │
│  · 定义全院有哪些仓库、库位                                    │
│  · 按批次记录每一批药的库存                                   │
│  · 所有增减库存的动作都写一条不可变的库存流水                   │
│  · 对外提供"某药可用库存多少"的唯一答案                        │
└────────────────────────┬─────────────────────────────────────┘
                         │ 库存可用量
        ┌────────────────┼────────────────┬──────────────┐
        ▼                ▼                ▼              ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ M14-03 采购  │ │ M14-04 出库  │ │ M14-05 盘点  │ │ M14-02 效期  │
│ 入库 +N      │ │ -N           │ │ 调平          │ │ 批号分配     │
└──────────────┘ └──────────────┘ └──────────────┘ └──────────────┘
```

**一句话边界：** M14-01 只管**数量**。管不了"该不该采购"（M14-03）、"该给谁发"（M14-07/08）、"该扣哪一批"（M14-02）。

### 1.2 为什么独立成子模块

| 如果不独立 | 会出什么问题 |
|---|---|
| 采购自己维护一个库存数 | 采购和发药各算一份，两边永远对不上 |
| 出库直接 UPDATE `stock_qty` | 查不到"这 5 支为什么少了"，账实不符时无从追溯 |
| 效期放在发药里算 | 药库里已过期 3 个月的药没人知道，直到发药才发现 |
| 仓库定义散落在各业务表 | 新增一个病区药房要改 6 张表 |

**核心论点：** 库存是全院最不容许"各说各话"的一类数据。M14 有 10 个子模块，其中 6 个会改变库存数量、2 个会读取库存。**只有让数量的变化有一个唯一入口、唯一记录、唯一查询口径，账才能对得上。**

### 1.3 与相邻子模块分工

| 能力 | 唯一负责方 | M14-01 做什么 |
|---|---|---|
| ✅ 定义仓库/库位 | **M14-01** | 主数据 + 状态管理 |
| ✅ 记录批次台账 | **M14-01** | 每批一行，跟踪结存 |
| ✅ 写库存流水 | **M14-01** | 唯一入口 `StockService.apply()` |
| ✅ 回答"可用库存多少" | **M14-01** | 唯一查询口径 |
| ❌ 该采购多少 | M14-03 | 只提供库存数与安全库存比对结果 |
| ❌ 该出哪一批 | M14-02 | 只提供批次候选集，不做出库决策 |
| ❌ 该发给谁 | M14-07/08 | 只扣减库存，不关心发给谁 |
| ❌ 盘点差异怎么处理 | M14-05 | 接收调整流水，不判断合理性 |
| ❌ 药品本身是什么 | M01-03 | 只引用 `drug_code`，不冗余全字段 |

**判断口诀：** M14-01 只回答"有多少"。谁让它变少、变多、变到哪去，都是别人决定的事。

### 1.4 概念辨析

#### 1.4.1 仓库 / 库位 / 货架

| 概念 | 定义 | 例子 | 层级 |
|---|---|---|---|
| **仓库（Warehouse）** | 独立核算、独立盘点的物理或逻辑库存单元 | 中心药库、门诊西药房、住院药房、急诊药房 | 1 |
| **库位（Location）** | 仓库内的存储区域 | 冷藏柜 A、麻醉药品保险柜、拆零区 | 2 |
| **货架/货位（Shelf）** | 库位内的具体位置 | A-03-02（A 架第 3 层第 2 位） | 3 |

**为什么库位要独立成表而不是一个字符串字段**

因为**冷藏药品和麻精药品必须绑定到特定库位**：

- 冷藏药品：`is_cold_chain=TRUE` 的药品只能放在 `storage_type='COLD'` 的库位
- 麻精药品：`is_narcotic=TRUE` 的药品只能放在 `storage_type='NARCOTIC_CABINET'` 的库位
- 拆零药品：拆零后只能放在 `storage_type='SPLIT'` 的库位

如果把库位写成 `stock.location` 字符串，这些校验就只能在应用层用 `if` 判断，且无法做"某库位温度超标影响哪些批次"的反查。

#### 1.4.2 批次 / 批号 / 有效期

| 概念 | 定义 |
|---|---|
| **批次（Batch）** | 生产厂家一次投料生产的、质量均一的一批产品 |
| **批号（Batch No）** | 标识该批次的生产编号，同一药品可能多个批号并存 |
| **有效期（Expiry Date）** | 该批次的有效截止日期 |

**关键约束：同一药品可以有多个批次同时存在，每个批次有独立库存。** 发药时必须按批号追溯——这是药品不良反应溯源、召回、麻精药专账的基础。

``` 
阿托品滴眼液 0.5%（drug_code=D0001）
├── 批次 A231201  效期 2027-11-30  库存 120 支
├── 批次 A240301  效期 2028-02-28  库存 250 支
└── 批次 A220801  效期 2026-07-31  库存  15 支  ← 近效期，应优先出
```

#### 1.4.3 库存事务（Stock Transaction）

库存事务是**每一次数量变化的最小记录单位**。

| 属性 | 说明 |
|---|---|
| 不可变 | 只增不改不删（物理禁止 UPDATE/DELETE） |
| 有原因 | `txn_type` 必填，如 `PURCHASE_IN` / `DISPENSE_OUT` / `RETURN_IN` |
| 有方向 | `direction` = `IN` / `OUT`，数量恒为正数 |
| 有前后值 | `qty_before` / `qty_after` 同时记录，可直接看出这次变化的上下文 |
| 有来源 | `source_type` + `source_id` 指向触发它的业务单据 |

**为什么数量恒为正数，方向单独一个字段？**

如果允许负数，`qty=-5` 到底是"出库 5"还是"入库 -5"，不同人写法不同，汇总时容易漏加负号。用 `direction` + 正数，聚合逻辑就是：

```sql
SUM(CASE WHEN direction = 'IN' THEN qty ELSE -qty END)
```

一行写完，无需猜测。

#### 1.4.4 结存（Balance）与流水（Ledger）的关系

```
m14_stock_txn（流水，只增）           m14_stock_batch（结存，可更新）
┌───────────────────────────────┐    ┌──────────────────────────┐
│ 09:00 PURCHASE_IN   +100      │    │ batch A231201            │
│ 10:30 DISPENSE_OUT  - 20      │ ─► │   qty_on_hand = 95       │
│ 11:00 RETURN_IN     + 10      │    │   qty_available = 95     │
│ 14:00 DISPENSE_OUT  - 15      │    │ （每次流水同步更新）      │
└───────────────────────────────┘    └──────────────────────────┘
              │
              └──► 两者的加总必须相等
                   不等 = 数据损坏，触发 CRITICAL 告警
```

**为什么要维护结存表，而不是每次都 SUM 流水？**

| 方案 | 查询"当前库存"耗时 | 写入成本 |
|---|---|---|
| 纯流水（每次 SUM） | 单个药品 3 年约 2,000 行 → 15ms；全量 500 药品 → 不可用 | 无 |
| 流水 + 结存 | 主键查一行 → 1ms | 每次多写一次 UPDATE |
| 只结存 | 1ms | 丢失追溯能力 |

M14-01 选**流水 + 结存**，并以流水为准（reconciliation 定时比对）。

**代价**：并发扣减需要加锁，否则两个人同时发药会超发。方案见 3.5 节。

## 3. 业务模型

### 3.1 仓库模型

#### 3.1.1 仓库分类

| 类型 | 编码 | 说明 | 是否对外发药 | 是否核算成本 |
|---|---|---|---|---|
| 中心药库 | `CENTER` | 全院药品总库，从供应商采购 | 否 | 是 |
| 门诊药房 | `OUTPATIENT` | 门诊发药窗口 | 是 | 是 |
| 住院药房 | `INPATIENT` | 住院摆药与病区发药 | 是 | 是 |
| 急诊药房 | `EMERGENCY` | 急诊 24 小时发药 | 是 | 是 |
| 手术室药房 | `OPERATING` | 手术室麻醉与术中用药 | 是 | 是 |
| 病区药柜 | `WARD` | 病区备用小药柜 | 是 | 否（视为门诊/住院药房的消耗） |
| 待检区 | `QUARANTINE` | 待验收、待退货、不合格待处理的暂存 | 否 | 否 |
| 虚拟库 | `VIRTUAL` | 供应商寄售、在途库存 | 否 | 是 |

**为什么要"待检区"这个仓库类型**

到货验收时，药品先入待检区；验收合格才转入中心药库。如果直接入库，验收发现不合格时已经污染了可用库存。

**为什么要"病区药柜"这个仓库类型**

病房里确实存在一个备用小药柜（抢救车、常用药）。它的库存也要能查到，但核算口径上是"已经下发到科室的消耗"，不参与中心库存的盘亏计算。

#### 3.1.2 仓库状态机

```
  ┌─────────┐   启用   ┌──────────┐   停用   ┌───────────┐
  │ DRAFT   │────────►│ ENABLED  │────────►│ DISABLED  │
  │ 草稿    │         │ 启用中   │         │ 已停用    │
  └─────────┘         └────┬─────┘◄────────└───────────┘
                           │       重新启用
                           │ 关闭（库存为零才可）
                           ▼
                      ┌─────────┐
                      │ CLOSED  │  终态，不可恢复
                      └─────────┘
```

**停用 vs 关闭的区别**

| 状态 | 能否出库 | 能否入库 | 能否恢复 | 场景 |
|---|---|---|---|---|
| `DISABLED` | 否 | 否 | 能 | 装修、搬迁、临时停用 |
| `CLOSED` | 否 | 否 | **不能** | 撤销该药房，历史数据只读保留 |

关闭条件：`SUM(qty_on_hand) = 0` 且无在途单据。有库存时关闭报错 **55203**。

### 3.2 库位模型

#### 3.2.1 存储类型

| 类型 | 编码 | 温控 | 绑定药品条件 | 典型场景 |
|---|---|---|---|---|
| 常温区 | `NORMAL` | 10~30℃ | 无 | 普通片剂 |
| 阴凉区 | `COOL` | ≤20℃ | `storage_condition='阴凉'` | 部分滴眼液 |
| 冷藏区 | `COLD` | 2~8℃ | `is_cold_chain=TRUE` | 生物制品、部分眼用凝胶 |
| 麻精柜 | `NARCOTIC_CABINET` | 常温 | `is_narcotic=TRUE OR is_psychotropic=TRUE` | 麻醉药品 |
| 毒性药品柜 | `TOXIC_CABINET` | 常温 | `is_toxic=TRUE` | 毒性药品 |
| 拆零区 | `SPLIT` | 常温 | `is_split=TRUE` | 拆零分装 |
| 退货区 | `RETURN` | 常温 | 无 | 患者退药暂存 |
| 不合格区 | `REJECT` | 常温 | 无 | 破损、过期待销毁 |
| 待检区 | `QUARANTINE` | 常温 | 无 | 到货待验收 |

**库位与药品的硬绑定校验**

当 `stock_type` 是 `COLD` / `NARCOTIC_CABINET` / `TOXIC_CABINET` 时，写入该库位的药品必须满足对应条件，否则报错 **55205**。

```python
STORAGE_RULES = {
    "COLD": lambda d: d.is_cold_chain,
    "NARCOTIC_CABINET": lambda d: d.is_narcotic or d.is_psychotropic,
    "TOXIC_CABINET": lambda d: d.is_toxic,
    "SPLIT": lambda d: d.is_split,
}
```

#### 3.2.2 库位状态机

```
  ENABLED ⇄ DISABLED
     │
     └──► CLOSED（库存为 0 才可关闭）
```

### 3.3 批次台账模型

#### 3.3.1 批次标识

批次由三元组唯一确定：

```
(warehouse_id, drug_id, batch_no)
```

**但同一批号在同一仓库可能有不同效期吗？** 理论上不会——同一厂家同一批号只有一个有效期。但实际存在供应商重复录入、进口药分装后效期不同的情况。

**决策：** 唯一键用 `(warehouse_id, drug_id, batch_no, expiry_date)`，四元组。理由是：宁可多一个批次行，也不能因为唯一键冲突而无法入库。

#### 3.3.2 批次数量字段

| 字段 | 含义 | 是否可变 |
|---|---|---|
| `qty_on_hand` | 在库数量（含已占用未出库） | 每笔流水同步更新 |
| `qty_locked` | 锁定数量（已分配给出库单但未确认） | 分配/释放时更新 |
| `qty_available` | 可用数量 = `qty_on_hand - qty_locked` | **生成列，不手写** |
| `qty_in_transit` | 在途数量（调拨出库未入库期间） | 调拨时更新 |

**三者关系（这是最容易写错的地方）：**

```
qty_on_hand     = 实际在库的药品数量
qty_locked      = 已被某张出库单预定但还没真正搬走
qty_available   = 可以再被别的单据预定的数量
                = qty_on_hand - qty_locked

约束：0 <= qty_locked <= qty_on_hand
```

**举例：**

```
09:00  批次 A231201 入库 100 支     on_hand=100  locked=0    available=100
09:10  门诊发药单分配 30 支         on_hand=100  locked=30   available= 70
09:15  另一张发药单想分配 80 支     → 失败，只有 70 可用（报错 55208）
09:20  第一张单确认发药             on_hand= 70  locked=0    available= 70
```

#### 3.3.3 批次状态机

```
     ┌────────────┐
     │  NORMAL    │  正常可用
     └──────┬─────┘
            │ 效期进入预警期
            ▼
     ┌────────────┐
     │ NEAR_EXPIRY│  近效期，可出但要提示
     └──────┬─────┘
            │ 过期
            ▼
     ┌────────────┐
     │  EXPIRED   │  过期，禁止出库
     └──────┬─────┘
            │ 销毁
            ▼
     ┌────────────┐
     │ DESTROYED  │  终态
     └────────────┘

  旁支：NORMAL ──质检发现问题──► HOLD（冻结，禁止出库）
        HOLD ──处理完成──► NORMAL / REJECTED
        NORMAL ──厂家召回──► RECALLED（可退厂）
```

**`EXPIRED` 是计算出来的还是存下来的？**

**决策：存下来，但每日重算。**

理由：过期是随日期自然发生的，不是某个操作触发的。如果只在查询时算，需要每条 SQL 都加 `expiry_date > CURRENT_DATE` 条件，容易漏。

做法：
- 每日 00:05 的 Celery 任务扫描 `expiry_date <= CURRENT_DATE` 且 `status IN ('NORMAL','NEAR_EXPIRY')` 的批次，置为 `EXPIRED`
- 查询时**仍然加 `expiry_date > CURRENT_DATE` 兜底条件**（当天的过期在任务跑之前就已生效）

### 3.4 库存事务模型

#### 3.4.1 事务类型全表

| 类型 | 编码 | 方向 | 触发方 | 说明 |
|---|---|---|---|---|
| 采购入库 | `PURCHASE_IN` | IN | M14-03 | 供应商到货验收合格 |
| 采购退货 | `PURCHASE_RETURN` | OUT | M14-03 | 退回供应商 |
| 领用出库 | `ISSUE_OUT` | OUT | M14-04 | 药库发到药房 |
| 调拨入库 | `TRANSFER_IN` | IN | M14-04 | 从他库调入 |
| 调拨出库 | `TRANSFER_OUT` | OUT | M14-04 | 调往他库 |
| 门诊发药 | `DISPENSE_OUT` | OUT | M14-07 | 发给患者 |
| 住院摆药 | `WARD_DISPENSE_OUT` | OUT | M14-08 | 摆药到病区 |
| 患者退药 | `RETURN_IN` | IN | M14-07 | 患者退回 |
| 病区退药 | `WARD_RETURN_IN` | IN | M14-08 | 病区退回 |
| 盘盈 | `STOCKTAKE_IN` | IN | M14-05 | 盘点多于账面 |
| 盘亏 | `STOCKTAKE_OUT` | OUT | M14-05 | 盘点少于账面 |
| 报损 | `LOSS_OUT` | OUT | M14-05 | 破损、过期销毁 |
| 拆零分装 | `SPLIT_IN` / `SPLIT_OUT` | IN/OUT | M14-02 | 整包拆零 |
| 冻结 | `LOCK` / `UNLOCK` | — | 内部 | 只改 `qty_locked`，不改 `qty_on_hand` |
| 期初建账 | `OPENING` | IN | 系统初始化 | 上线首日库存导入 |
| 冲销 | `REVERSE` | IN/OUT | 各业务方 | 反向冲销原事务 |

#### 3.4.2 事务状态机

```
  ┌─────────┐   执行完   ┌──────────┐
  │ PENDING │─────────►│ CONFIRMED│  正常生效
  └────┬────┘          └────┬─────┘
       │ 失败                │ 冲销
       ▼                     ▼
  ┌─────────┐          ┌──────────┐
  │ FAILED  │          │ REVERSED │  已被冲销
  └─────────┘          └──────────┘
```

**注意：`CONFIRMED` 的流水不能被 UPDATE，只能通过新增一条 `REVERSE` 流水冲销。** 这是账务的基本原则。

#### 3.4.3 冲销规则

| 规则 | 说明 |
|---|---|
| R-01 | 冲销必须引用原流水 `reverse_of_txn_id` |
| R-02 | 冲销流水的 `txn_type` 为 `REVERSE`，方向与原流水相反 |
| R-03 | 一条流水只能被冲销一次（唯一索引） |
| R-04 | 已冲销的流水不能再次冲销 |
| R-05 | 跨月冲销需要主管审批（月度已结账） |

### 3.5 并发扣减模型

#### 3.5.1 问题

两个药师同时给两个患者发同一种药，库存只有 10 支：

```
T1: 药师A 查询 → 库存 10
T2: 药师B 查询 → 库存 10
T1: 药师A 扣减 8 → 库存 2
T2: 药师B 扣减 7 → 库存 -5   ← 超发！
```

#### 3.5.2 方案对比

| 方案 | 实现 | 并发性能 | 风险 |
|---|---|---|---|
| A. 先查后改（无锁） | `SELECT` 后 `UPDATE` | 最高 | **必然超发** |
| B. 数据库行锁 | `SELECT ... FOR UPDATE` | 中 | 正确，但热点批次会排队 |
| C. 乐观锁 | `UPDATE ... WHERE version = N` | 高 | 冲突时重试，热点批次重试率高 |
| D. 带条件的原子更新 | `UPDATE ... WHERE qty_available >= N` | 最高 | 正确，无需重试逻辑 |
| E. Redis 分布式锁 | `SET NX` + 数据库 | 中 | 多一层依赖 |

**决策：D 为主 + C 为辅。**

```sql
-- 核心扣减语句
UPDATE m14_stock_batch
   SET qty_on_hand = qty_on_hand - :qty,
       qty_locked  = qty_locked  - :lock_qty,
       version     = version + 1,
       updated_at  = CURRENT_TIMESTAMP
 WHERE id = :batch_id
   AND qty_on_hand >= :qty            -- ★ 条件在 SQL 里
   AND qty_locked  >= :lock_qty
   AND version     = :expected_version -- 乐观锁兜底
```

`rowcount = 0` 即表示条件不满足，抛 **55208**「库存不足或已被并发修改」。

**为什么不用纯行锁（方案 B）？**

眼科门诊高峰时，热门药品（如玻璃酸钠滴眼液）一天 300 张处方集中在上午。如果每个发药都对批次加 `FOR UPDATE` 行锁，同时 5 个发药窗口会排队，单个发药从 30ms 变成 150ms。

用条件原子更新，5 个窗口可以真正并行——数据库行锁只在语句执行的那一瞬间持有。

**锁定量（`qty_locked`）为什么也要条件校验？**

因为锁定和扣减是两个动作。分配时 `locked += N`，确认发药时 `on_hand -= N, locked -= N`。如果中间被其他流程改了 `locked`，扣减就会把 `locked` 变成负数。

### 3.6 库存查询模型

#### 3.6.1 查询维度

| 维度 | 说明 | 典型场景 |
|---|---|---|
| 按药品 | `drug_code` / 名称 / 拼音 | 药师查某药有多少 |
| 按仓库 | `warehouse_id` | 门诊药房库存 |
| 按批次 | `batch_no` | 追溯某批号 |
| 按效期 | 近效期 / 已过期 | 效期管理 |
| 按库位 | `location_id` | 盘点某库位 |
| 组合 | 上述任意组合 | 几乎全部实际场景 |

#### 3.6.2 汇总口径

```
药品在仓库的总库存 = Σ(该仓库下该药品所有可用批次的 qty_on_hand)
药品在仓库的可用库存 = Σ(该仓库下该药品所有可用批次的 qty_available)
```

**"可用批次"的定义：** `status NOT IN ('EXPIRED','DESTROYED','REJECTED','RECALLED')` 且 `expiry_date > CURRENT_DATE`。

**为什么过期批次仍计入 `qty_on_hand` 但不计入可用？**

因为过期药品物理上还在药架上，盘点能数到。如果把过期批次的数量直接减掉，盘点时就会出现"账面 0 但实际有 15 支"的差异。

正确做法是：过期批次 `qty_on_hand` 保持不变，但状态置 `EXPIRED`，并在查询时排除。销毁时才写 `LOSS_OUT` 流水真正减掉。

#### 3.6.3 库存快照

月末结账、财务核算、审计检查都需要"某个时点"的库存。

**两种实现：**

| 方案 | 说明 | 代价 |
|---|---|---|
| 从流水重放 | 把所有流水按时间累加 | 单药品 3 年 2,000 行，全院 500 药品 = 100 万行，难以实时 |
| 定时快照 | 每日 23:59 生成 `m14_stock_snapshot` | 每日多 500~3,000 行 |

**决策：定时快照（每日 23:59）+ 按需快照（手动触发）。**

快照粒度：`(snapshot_date, warehouse_id, drug_id, batch_no)`。

### 3.7 库存对账模型

#### 3.7.1 对账两个层次

| 层次 | 对比对象 | 频率 | 不一致含义 |
|---|---|---|---|
| L1 流水 vs 结存 | `SUM(流水)` vs `m14_stock_batch.qty_on_hand` | 每日 | 数据损坏或并发 bug |
| L2 结存 vs 实物 | `m14_stock_batch.qty_on_hand` vs 盘点数 | 月度/随时 | 管理问题（丢失、错发、记录错误） |

**L1 不通过是系统故障，必须告警；L2 不通过是业务差异，走盘点流程。**

#### 3.7.2 L1 对账算法

```sql
-- 对每个批次，重放其全部流水，与结存比对
WITH txn_sum AS (
    SELECT batch_id,
           SUM(CASE WHEN direction = 'IN' THEN qty ELSE -qty END) AS qty_calc
      FROM m14_stock_txn
     WHERE status = 'CONFIRMED'
       AND batch_id IS NOT NULL
     GROUP BY batch_id
)
SELECT b.id, b.batch_no, b.qty_on_hand, COALESCE(t.qty_calc, 0) AS qty_calc,
       b.qty_on_hand - COALESCE(t.qty_calc, 0) AS diff
  FROM m14_stock_batch b
  LEFT JOIN txn_sum t ON t.batch_id = b.id
 WHERE b.qty_on_hand <> COALESCE(t.qty_calc, 0);
```

不一致时：
1. 写报警日志 `CRITICAL`
2. 记录到 `m14_stock_reconcile_log`
3. **不自动修复**——数据损坏时自动修复会掩盖真实原因

### 6.2 错误码规范

| 错误码 | 消息 | 触发条件 |
|---|---|---|
| 55201 | 仓库或库位编码格式错误或已存在 | V-01/V-02 |
| 55202 | 仓库或库位状态不允许此操作 | 已关闭/未启用 |
| 55203 | 存在库存，无法关闭或停用 | `qty_on_hand > 0` |
| 55204 | 该仓库类型不允许对外发药 | 中心药库/虚拟库/待检区 |
| 55205 | 库位存储类型与药品属性不匹配 | 冷藏药品放常温区 |
| 55206 | 冻结原因不完整 | 少于 10 字 |
| 55207 | 批次状态不允许此操作 | 过期批次解冻 |
| 55208 | 库存不足或已被并发修改 | 条件更新 `rowcount=0` |
| 55209 | 库存数量必须通过库存事务调整 | 直接改 `qty_on_hand` |
| 55210 | 快照日期不在允许范围 | 晚于今天 |
| 55211 | 无快照或对账操作权限 | — |
| 55212 | 已有对账任务在执行 | 并发触发 |
| 55213 | 批次不存在或已删除 | — |
| 55214 | 库存流水不可修改或删除 | 物理禁止 |
| 55215 | 冲销流水状态不允许 | 已冲销/已失败 |
| 55216 | 锁定数量超过在库数量 | `qty_locked > qty_on_hand` |
| 55217 | 仓库不存在或已关闭 | — |
| 55218 | 药品不存在或已停用 | M01-03 查询失败 |
| 55219 | 出库数量必须为正数 | `qty <= 0` |
| 55220 | 批次效期已过，不允许出库 | `expiry_date <= today` |

### 6.6 Service 层核心逻辑

#### 6.6.1 StockService.apply() —— 库存变更的唯一入口

```python
import hashlib
from datetime import datetime
from decimal import Decimal

from app.core.exceptions import BizError
from app.core.logger import logger
from app.db.session import async_session


class StockService:
    """库存台账服务"""

    # 增加库存的事务类型
    INBOUND_TYPES = {
        "PURCHASE_IN", "TRANSFER_IN", "RETURN_IN",
        "WARD_RETURN_IN", "STOCKTAKE_IN", "SPLIT_IN",
        "OPENING",
    }
    # 减少库存的事务类型
    OUTBOUND_TYPES = {
        "PURCHASE_RETURN", "ISSUE_OUT", "TRANSFER_OUT",
        "DISPENSE_OUT", "WARD_DISPENSE_OUT", "STOCKTAKE_OUT",
        "LOSS_OUT", "SPLIT_OUT",
    }

    async def apply(self, body: StockApply, user) -> dict:
        """应用一笔库存事务。

        这是全模块唯一的库存变更入口。任何业务子模块
        （采购/出库/盘点/发药）都必须通过这里改库存。
        """
        async with async_session() as db:
            # 1. 幂等检查
            if body.idempotency_key:
                existed = await self._find_by_idem(
                    db, body.idempotency_key)
                if existed:
                    return self._txn_dict(existed, is_idem=True)

            # 2. 校验方向与类型
            self._check_direction(body)

            # 3. 定位批次
            batch = await self._get_batch(
                db, body.batch_id, for_update=False)
            if batch is None:
                raise BizError(55213, "批次不存在")

            # 4. 业务前置校验
            await self._pre_check(batch, body)

            # 5. 计算新数量
            qty = Decimal(str(body.qty))
            if qty <= 0:
                raise BizError(55219, "数量必须为正数")
            delta = qty if body.direction == "IN" else -qty
            new_on_hand = (
                Decimal(str(batch.qty_on_hand)) + delta)

            # 6. 原子更新（带条件）
            affected = await self._update_batch_atomic(
                db, batch, qty, delta, body.direction)
            if affected == 0:
                raise BizError(55208, "库存不足或已被并发修改")

            # 7. 写流水
            txn = await self._write_txn(
                db, batch, body, qty, delta)

            # 8. 更新 M01 库存策略预警标记（异步）
            await self._mark_stock_alert(db, batch, new_on_hand)

            await db.commit()

            logger.info(
                "m14.stock.apply",
                extra={
                    "txn_no": txn.txn_no,
                    "txn_type": body.txn_type,
                    "drug_code": batch.drug_code,
                    "batch_no": batch.batch_no,
                    "qty": str(qty),
                    "direction": body.direction,
                    "qty_before": str(batch.qty_on_hand),
                    "qty_after": str(new_on_hand),
                    "source_no": body.source_no,
                },
            )
            return self._txn_dict(txn, is_idem=False)

    def _check_direction(self, body: StockApply) -> None:
        if body.txn_type in self.INBOUND_TYPES:
            if body.direction != "IN":
                raise BizError(
                    55219, "事务类型 %s 方向应为 IN"
                    % body.txn_type)
        elif body.txn_type in self.OUTBOUND_TYPES:
            if body.direction != "OUT":
                raise BizError(
                    55219, "事务类型 %s 方向应为 OUT"
                    % body.txn_type)
        else:
            raise BizError(55219, "未知事务类型 %s" % body.txn_type)

    async def _pre_check(self, batch, body) -> None:
        """出库前的业务校验"""
        if body.direction != "OUT":
            return
        # 过期批次禁止出库
        if batch.expiry_date <= date.today():
            raise BizError(55220, "批次 %s 已过期"
                           % batch.batch_no)
        # 冻结核次禁止出库
        if batch.status in ("HOLD", "EXPIRED",
                            "DESTROYED", "REJECTED",
                            "RECALLED"):
            raise BizError(55207, "批次状态 %s 不允许出库"
                           % batch.status)

    async def _update_batch_atomic(
        self, db, batch, qty, delta, direction,
    ) -> int:
        """带条件的原子更新，防超发。

        出库时额外扣减锁定数量（如果是从锁定转扣减）。
        """
        if direction == "OUT":
            stmt = text("""
                UPDATE m14_stock_batch
                   SET qty_on_hand = qty_on_hand - :qty,
                       qty_locked = GREATEST(
                           qty_locked - :qty, 0),
                       version = version + 1,
                       updated_at = CURRENT_TIMESTAMP
                 WHERE id = :bid
                   AND qty_on_hand >= :qty
                   AND version = :ver
            """)
        else:
            stmt = text("""
                UPDATE m14_stock_batch
                   SET qty_on_hand = qty_on_hand + :qty,
                       version = version + 1,
                       updated_at = CURRENT_TIMESTAMP
                 WHERE id = :bid
                   AND version = :ver
            """)
        result = await db.execute(stmt, {
            "qty": qty, "bid": batch.id,
            "ver": batch.version})
        return result.rowcount
```

```python
class StockLockService:
    """库存锁定服务（接续 StockService）"""

    async def lock(self, body: LockInput, user) -> dict:
        """锁定库存（分配但未出库）。

        锁定只改 qty_locked，不改 qty_on_hand。
        锁有超时，超时后由定时任务自动释放。
        """
        async with async_session() as db:
            locked = []
            for item in body.items:
                qty = Decimal(str(item.qty))
                if qty <= 0:
                    raise BizError(55219, "锁定数量必须为正数")

                # 条件更新：可用量足够才锁
                result = await db.execute(text("""
                    UPDATE m14_stock_batch
                       SET qty_locked = qty_locked + :qty,
                           version = version + 1
                     WHERE id = :bid
                       AND qty_on_hand - qty_locked >= :qty
                       AND status IN ('NORMAL', 'NEAR_EXPIRY')
                """), {"qty": qty, "bid": item.batch_id})

                if result.rowcount == 0:
                    raise BizError(
                        55216,
                        "批次 %s 可用库存不足"
                        % item.batch_id)

                # 写锁记录（Redis + 数据库）
                await self._write_lock_record(
                    db, body, item.batch_id, qty)

                row = await self._get_batch(db, item.batch_id)
                locked.append({
                    "batch_id": item.batch_id,
                    "qty": str(qty),
                    "qty_available_after": str(
                        row.qty_available),
                })

            await db.commit()
            return {
                "lock_no": body.lock_no,
                "locked": locked,
                "expire_at": self._expire_at(
                    body.expire_seconds),
            }
```

| 事件 | 失效 Key |

```python
async def _reconcile() -> dict:
    from app.db.session import async_session
    from sqlalchemy import text

    async with async_session() as db:
        rows = (await db.execute(text("""
            WITH txn_sum AS (
                SELECT batch_id,
                       SUM(CASE WHEN direction = 'IN'
                                THEN qty ELSE -qty END) AS q
                  FROM m14_stock_txn
                 WHERE status = 'CONFIRMED'
                   AND batch_id IS NOT NULL
                 GROUP BY batch_id
            )
            SELECT b.id, b.batch_no, b.qty_on_hand,
                   COALESCE(t.q, 0) AS qty_calc
              FROM m14_stock_batch b
              LEFT JOIN txn_sum t ON t.batch_id = b.id
             WHERE b.qty_on_hand <> COALESCE(t.q, 0)
        """))).fetchall()

        for r in rows:

                     qty_book, qty_ledger, qty_diff,
                     result, created_at)

                        CURRENT_TIMESTAMP)

                   "qb": r[2], "ql": r[3],
                   "qd": r[2] - r[3]})
        await db.commit()
```
