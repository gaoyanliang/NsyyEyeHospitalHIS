## 4. 数据结构设计

### 4.1 ER 关系图

```
┌──────────────────────────────────┐
│ m14_special_cabinet              │ 专柜主表
│  cabinet_no / cabinet_type       │ 麻精柜 / 毒柜 / 放射柜
│  lock_type / 双锁管理人           │
└──┬───────────────────────────────┘
   │1:N
   ▼
┌──────────────────────────────────┐
│ m14_special_stock                │ 专柜库存（按批次）
│  cabinet_id + drug_id + batch_no │
│  quantity / 当前数量             │
└──┬───────────────────────────────┘
   │ 逻辑关联（登记时读取并更新）
   │
┌──▼───────────────────────────────┐        ┌───────────────────────┐
│ m14_special_record               │◄───────│ m14_special_permit    │
│  逐支登记台账（只增不改）        │ 记账时  │  印鉴卡               │
│  action / 双签 / 数量前后        │ 校验    │  permit_no / 有效期   │
└──┬────────────────┬──────────────┘        └───────────────────────┘
   │1:1            │1:N
   ▼               ▼
┌──────────────┐  ┌──────────────────────┐
│special       │  │ m14_special_incident │ 异常事件
│_ampoule      │  │  失窃/破损/盘点差异  │
│ 空安瓿回收   │  │  24h 上报时限跟踪    │
└──────────────┘  └──────────────────────┘

外部依赖（不建外键，通过接口获取）：
  M01-03 药品主档    drug_id / drug_code / management_class
  M01-01 科室        warehouse_id（所属药房）
  M01-02 职工        operator_id / checker_id / 双锁管理人
  M07-05 处方        prescription_id / prescription_no
  M14-01 库存        batch_id（批次基础信息）
  M14-07/08 发药     dispense_id（触发登记的来源）
```

**设计说明**

| 决策 | 内容 | 理由 |
|---|---|---|
| 专柜库存独立成表，不复用 `m14_stock_batch` | `m14_special_stock` | 特殊药品按「支/片/毫升」管理，与普通库存的「盒」单位不同；且每次出入必须双签，不能混入普通流水 |
| 登记台账只增不改 | `m14_special_record` + 只读触发器 | 药监台账是法律凭证，任何改写都会导致追溯断链 |
| 空安瓿独立成表 | `m14_special_ampoule` | 空瓿回收有独立的时限（24h）与核对逻辑，与库存无关 |
| 印鉴卡独立成表 | `m14_special_permit` | 印鉴卡有有效期、发卡机构、核定品种清单，是行政许可凭证 |
| 异常事件独立成表 | `m14_special_incident` | 失窃有 24h 法定上报时限，需要独立跟踪 `is_overdue` |
| 不建外键到 M01/M07/M14-01 | 仅存 ID 与冗余快照 | 跨模块解耦，避免跨库锁定 |

> **⚠️ 只增铁律：** `m14_special_record` 插入后不可 UPDATE/DELETE。写错只能用「反向登记」（如误入库用 `STOCKTAKE_ADJUST` 冲正），不能删原记录。

| cabinet_name | VARCHAR(64) | N | — | 柜名称，如「麻精保险柜A」 |

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| pk_m14_special_cabinet | PRIMARY | id | 主键 |
| **uk_m14_special_cabinet_no** | UNIQUE | cabinet_no WHERE is_deleted = FALSE | 柜号全局唯一 |
| idx_m14_special_cabinet_wh | NORMAL | warehouse_id, cabinet_type | 按药房查柜 |
| idx_m14_special_cabinet_status | NORMAL | status | 按状态查 |
| idx_m14_special_cabinet_holder | NORMAL | key_a_holder_id, key_b_holder_id | 按管理人查（休假交接） |

**约束说明**

```sql
ALTER TABLE m14_special_cabinet
    ADD CONSTRAINT ck_m14_special_cabinet_no
    CHECK (cabinet_no ~ '^CAB-[A-Z]{2,4}-[0-9]{2}$');

ALTER TABLE m14_special_cabinet
    ADD CONSTRAINT ck_m14_special_cabinet_type
    CHECK (cabinet_type IN ('NARCOTIC', 'TOXIC', 'RADIOACTIVE',
                            'HIGH_RISK'));

ALTER TABLE m14_special_cabinet
    ADD CONSTRAINT ck_m14_special_cabinet_lock
    CHECK (lock_type IN ('SINGLE', 'DOUBLE'));

ALTER TABLE m14_special_cabinet
    ADD CONSTRAINT ck_m14_special_cabinet_status
    CHECK (status IN ('ENABLED', 'DISABLED', 'SEALED'));

-- 麻精柜、毒柜必须是双锁（法规强制）
ALTER TABLE m14_special_cabinet
    ADD CONSTRAINT ck_m14_special_cabinet_double_lock
    CHECK (cabinet_type NOT IN ('NARCOTIC', 'TOXIC')
           OR lock_type = 'DOUBLE');

-- 双锁柜必须配置 2 名不同管理人
ALTER TABLE m14_special_cabinet
    ADD CONSTRAINT ck_m14_special_cabinet_holders
    CHECK (lock_type <> 'DOUBLE'
           OR (key_a_holder_id IS NOT NULL
               AND key_b_holder_id IS NOT NULL
               AND key_a_holder_id <> key_b_holder_id));

-- 停用必须有原因与时间
ALTER TABLE m14_special_cabinet
    ADD CONSTRAINT ck_m14_special_cabinet_disabled
    CHECK (status <> 'DISABLED'
           OR (disabled_reason IS NOT NULL
               AND disabled_at IS NOT NULL));

-- 温度区间
ALTER TABLE m14_special_cabinet
    ADD CONSTRAINT ck_m14_special_cabinet_temp
    CHECK (temp_min IS NULL OR temp_max IS NULL
           OR temp_min < temp_max);

-- 备选管理人必须是数组
ALTER TABLE m14_special_cabinet
    ADD CONSTRAINT ck_m14_special_cabinet_backup
    CHECK (backup_holder_ids IS NULL
           OR jsonb_typeof(backup_holder_ids) = 'array');
```

**关键设计说明**

**`ck_m14_special_cabinet_double_lock` 是法规硬约束**

```sql
CHECK (cabinet_type NOT IN ('NARCOTIC','TOXIC') OR lock_type = 'DOUBLE')
```

《麻醉药品和精神药品管理条例》第四十四条要求麻醉药品专柜**双人双锁**。这条约束让「把麻精柜设成单锁」在数据库层面就无法写入。

为什么约束写在数据库而不是应用层？因为配置页面可能被误操作，或被管理员图方便改成单锁。数据库约束是最后一道防线。

**`ck_m14_special_cabinet_holders` 的双锁管理人不重复**

```sql
CHECK (lock_type <> 'DOUBLE'
       OR (key_a_holder_id IS NOT NULL
           AND key_b_holder_id IS NOT NULL
           AND key_a_holder_id <> key_b_holder_id))
```

如果 A、B 两把钥匙给同一个人，双锁就形同单锁。这条约束堵住这种配置。

**`backup_holder_ids` 为什么用 JSONB？**

专管药师休假、进修时要有替班人。备选管理人是一个短列表（通常 2~4 人），永远整体读写，不按人聚合查询，用 JSONB 数组比独立关联表更轻。

**`location_id` 与 `m14_location` 的关系**

M14-01 的库位表已定义 `NARCOTIC_CABINET`、`TOXIC_CABINET` 两种存储类型，且约束要求这两类库位必须 `is_locked = TRUE AND requires_double_sign = TRUE`。

专柜与库位是**一一对应**的：
- 库位负责「物理位置」与「温湿度」
- 专柜负责「锁具、管理人、柜型」

保留 `location_id` 但允许为空，是为了兼容「专柜由 M14-01 建库位、M14-09 建柜」的部署顺序。

**量级估算**

| 项 | 数值 |
|---|---|
| 全院专柜数 | 5~10 个 |
| 年增量 | 0~2 个 |
| 单行大小 | 约 500 B |
| **保留** | **永久** |

**分区：** 不分区。

**约束说明**

```sql
ALTER TABLE m14_special_stock
    ADD CONSTRAINT ck_m14_special_stock_class
    CHECK (special_class IN ('NARCOTIC', 'PSYCHOTROPIC_1',
                             'PSYCHOTROPIC_2', 'TOXIC',
                             'RADIOACTIVE', 'HIGH_RISK'));

ALTER TABLE m14_special_stock
    ADD CONSTRAINT ck_m14_special_stock_status
    CHECK (status IN ('NORMAL', 'FROZEN', 'EXPIRED', 'CONSUMED'));

-- 库存不允许为负（数据完整性底线）
ALTER TABLE m14_special_stock
    ADD CONSTRAINT ck_m14_special_stock_qty
    CHECK (quantity >= 0);

-- 累计收支非负
ALTER TABLE m14_special_stock
    ADD CONSTRAINT ck_m14_special_stock_total
    CHECK (init_quantity >= 0 AND total_in >= 0 AND total_out >= 0);

-- 累计流水与当前库存的理论关系（允许盘点调整差异）
ALTER TABLE m14_special_stock
    ADD CONSTRAINT ck_m14_special_stock_calc
    CHECK (init_quantity + total_in >= total_out);

-- 已出完的批次状态应为 CONSUMED
ALTER TABLE m14_special_stock
    ADD CONSTRAINT ck_m14_special_stock_consumed
    CHECK (quantity > 0 OR status IN ('CONSUMED', 'EXPIRED'));

-- 最近登记字段成对出现
ALTER TABLE m14_special_stock
    ADD CONSTRAINT ck_m14_special_stock_last
    CHECK ((last_record_no IS NULL AND last_record_at IS NULL)
           OR (last_record_no IS NOT NULL
               AND last_record_at IS NOT NULL));

-- 批号非空
ALTER TABLE m14_special_stock
    ADD CONSTRAINT ck_m14_special_stock_batch
    CHECK (char_length(btrim(batch_no)) > 0);
```

**`uk_m14_special_stock_key` 唯一约束的必要性**

```
柜 + 药品 + 批号 唯一
```

同一批号药品在同一柜子里只能有一条记录。

反例：如果没有唯一约束，两次入库（FEFO 分配或手工操作失误）会生成两条同柜同批号的记录：

```
cabinet  drug    batch   quantity
OP-01    芬太尼  240815  18
OP-01    芬太尼  240815  20    ← 重复
```

后果：
- 发药时可能读到错误的库存（读到 18 而不是 38）
- 盘点时两条记录都要盘，账实核对混乱

**`ck_m14_special_stock_qty` 的 `quantity >= 0`**

这条约束看似平凡，但对特殊药品极其重要：

- 普通药品库存为负，可能只是「退货先到、入库后到」的时序问题
- 特殊药品库存为负，几乎必然意味着**账实不符**，可能涉及失窃

数据库层面直接拒绝负库存，应用层错误码 55613 提示人工核查。

**`init_quantity` / `total_in` / `total_out` 的设计意图**

这三个字段是**快速对账的验证列**：

```
理论库存 = init_quantity + total_in − total_out
```

若 `理论库存 ≠ quantity`，说明发生过盘点调整（`STOCKTAKE_ADJUST`），这是允许的，但差异必须能用调整记录解释。

约束 `init_quantity + total_in >= total_out` 保证不会出现「理论库存为负」这种明显错误。

为什么不直接用 `SUM(record)`？因为每次查库存都要扫流水表，10 万条记录聚合要 200ms。冗余三个累计列后查库存是单行 O(1)。

**`status = 'FROZEN'` 的用途**

| 场景 | 说明 |
|---|---|
| 药监飞检期间 | 全部批次冻结，禁止出入库，配合检查 |
| 质疑问批次 | 某批次疑似质量问题，冻结待检 |
| 案件调查 | 涉窃批次冻结 |
| 系统对账异常 | 自动冻结，人工核查后解冻 |

**`ck_m14_special_record_double` 是这张表存在的灵魂**

```sql
CHECK (operator_id <> checker_id)
```

这是**整个 M14-09 子模块最重要的约束**。

普通的复核（如 M14-07 的调配与核对）在应用层校验即可，但特殊药品的「双人双签」是法律强制要求。如果只靠应用层，一旦应用有 bug、或有内鬼绕过接口直接写库，就会产生「一人双签」的假记录，让事后追溯彻底失效。

数据库约束保证：**任何写入路径都无法产生同人双签的记录**。

真实风险：麻醉药品流失案件的典型手法，就是一个人同时掌握两个账号，或趁同事不在时用其账号补签。系统层面的双人核验拦不住盗用账号，但至少：

- 时间戳是服务端生成的，无法伪造
- `check_gap_seconds` 记录两签字间隔，为事后审计提供线索
- `is_late_check` 标记超 15 分钟补签的记录，自动进入季度检查清单

**`ck_m14_special_record_balance` 与 `quantity_before/after` 的意义**

每条记录都保存「本次操作前后」的库存快照：

```
记录 1: 入库 20，前 0 → 后 20
记录 2: 发放 2，前 20 → 后 18
记录 3: 空瓿 2，前 18 → 后 18（空瓿不改库存）
```

这样即使 `m14_special_stock` 被误改，也能通过流水链路完整还原每次操作时的库存状态。药监检查时可以逐条核对「流水上的前值是否等于上一条的后值」，这是发现篡改的最后手段。

**动作方向与库存变化的一致性**

| action | 库存变化 | 说明 |
|---|---|---|
| `IN` | `after = before + qty` | 入库 |
| `OUT` | `after = before − qty` | 出库到普通库 |
| `DISPENSE` | `after = before − qty` | 发给患者/病区 |
| `AMPOULE_BACK` | `after = before` | 空瓿不改库存 |
| `RESIDUE_DESTROY` | `after = before` | 残液不改库存（药已发出） |
| `EXPIRED_DESTROY` | `after = before − qty` | 过期销毁 |
| `DAMAGED_DESTROY` | `after = before − qty` | 破损销毁 |
| `STOCKTAKE_ADJUST` | 双向 | 盘盈或盘亏 |

上述关系由应用层保证，数据库只校验 `before`、`after` 非负与 `qty > 0`。不写成 CHECK 约束的原因：`STOCKTAKE_ADJUST` 是双向的，枚举判断在 SQL 里会非常冗长，且未来新增动作类型需要改约束。

**分区说明**

`m14_special_record` **按月 RANGE 分区**（分区键 `seq_date`）。

理由：
- 台账保留 5 年，600 条/年 × 5 = 3,000 条，数据量不大
- 但综合查询（按药品、按日期、按操作人）非常多，分区可做分区裁剪
- 更重要的：保留期满后归档可以 `DETACH PARTITION` 一次性移走，比逐条 DELETE 快几个数量级

分区约束带来的代价：主键必须含分区键，所以是 `(id, seq_date)` 复合主键。唯一索引也含 `seq_date`。

**量级估算**

| 项 | 数值 |
|---|---|
| 日均登记 | 2~3 条（眼科特殊药品用量少） |
| 年行数 | 约 800 |
| 单行大小 | 约 700 B |
| 年增量 | 约 0.6 MB |
| **保留** | **5 年（法规）**，分区按月 |

**分区：** 按 `seq_date` 月度 RANGE 分区，预建 60 个月。

**`uk_m14_special_ampoule_record` 一条发放对应一个回收任务**

发放 2 支就产生一个「应回收 2 支」的任务。多次回收时更新同一行的 `collected_qty`，而不是每条回收记录都插入一行。

这样查「这支药的空瓿回了没有」只需查一行。

**`ck_m14_special_ampoule_progress` 的精确状态绑定**

```
PENDING   ⟺ collected_qty = 0
PARTIAL   ⟺ 0 < collected_qty < dispense_qty
BACK      ⟺ collected_qty = dispense_qty
MISSING   / EXPLAINED  ⟺ 人工判定
```

这条约束让状态字段不可能与数量脱节。若应用层漏更新状态，数据库直接拒绝。

**`collected_by <> witness_id` 的空瓿双人**

即使回收空瓿看起来是「小事」，法规要求与药品本身的操作一致：**必须两人在场**。回收人 ≠ 监督人。

**`MISSING` 与 `EXPLAINED` 的区别**

| 状态 | 含义 | 后续 |
|---|---|---|
| `MISSING` | 超期未回收，系统自动标记 | 进季度检查清单，通知护士长 |
| `EXPLAINED` | 已登记合理说明（如「患者拒绝交回」或「院外使用」） | 需药房主任签字，不再告警 |

注意：`EXPLAINED` 需要 `resolved_note` ≥ 10 字。不能写「无」「忘记」这种敷衍的说明。

**`missing_qty` 用生成列的考虑**

```sql
missing_qty NUMERIC(10,2) GENERATED ALWAYS AS
    (dispense_qty - collected_qty) STORED
```

由于本表有 `dispense_qty` 与 `collected_qty` 两个可直接推导的字段，用生成列避免手工维护出错。CHECK 约束 `ck_m14_special_ampoule_missing` 作为冗余校验（实际上生成列不会违反）。

**`ck_m14_special_incident_deadline` 用数据库算 24 小时**

```sql
CHECK (report_deadline = found_at + INTERVAL '24 hours')
```

上报截止时间不是应用层传入的，而是数据库强制等于「发现时间 + 24 小时」。

为什么？因为这是**法定时限**。如果允许应用层传入，就可能被篡改（例如把截止时间改晚一点，让超时看起来没超时）。用约束固定计算关系，杜绝这种可能。

**`ck_m14_special_incident_theft` 的三态设计**

失窃单有三种合法状态：

1. `PENDING_REPORT`：刚登记，还没上报（允许 `reported_at` 为空）
2. `REPORTED` / `INVESTIGATING` / `CLOSED`：已上报，必须有上报时间与受理编号
3. 其他类型（破损/盘点差异/超期空瓿）：不受此约束

约束里写 `status = 'PENDING_REPORT' OR (...)` 允许「刚登记还没上报」的中间态。

**为什么破损必须有照片？**

破损销毁涉及把药品从库存扣掉（`DAMAGED_DESTROY`）。如果没有照片证据，事后无法证明「这 2 支药确实是破损的」，可能被用于掩盖药品流失。

照片是破损销毁的必要证据。

**三人职责分离的三条约束**

```
登记人 ≠ 复核人
确认人 ≠ 登记人 且 确认人 ≠ 复核人
```

失窃涉及法律责任，三条约束保证至少三人参与，杜绝一人包办。

**`uk_m14_special_permit_active` 同类型同时只有一张有效卡**

印鉴卡是**行政许可凭证**，一个医疗机构在同一时刻只能有一张有效的麻醉药品印鉴卡。

如果允许同时有多张 ACTIVE：
- 入库校验时会随机取一张，可能取到即将过期的
- 无法确定「当前用哪张卡采购」

这张部分唯一索引让「同时激活两张卡」在数据库层面不可能。

换卡流程：旧卡置 `REVOKED` 或 `EXPIRED` → 新卡置 `ACTIVE`。

**`drug_scope` JSONB 的结构**

```json
[
    {"drug_code": "D05101", "drug_name": "盐酸吗啡注射液", "spec": "1ml:10mg"},
    {"drug_code": "D05102", "drug_name": "芬太尼注射液", "spec": "2ml:0.1mg"},
    {"drug_code": "D05103", "drug_name": "盐酸哌替啶注射液", "spec": "2ml:50mg"}
]
```

这是药监核定的**允许采购品种清单**。采购麻醉药品时，M14-03 会校验 `drug_code` 是否在 `drug_scope` 中，不在则拒绝采购。

**`renew_log` JSONB 的结构**

```json
[
    {"old_permit_no": "YJK2022000123", "new_permit_no": "YJK2024001234",
     "renew_date": "2024-03-01", "operator": "王主任"},
    {"old_permit_no": "YJK2024001234", "new_permit_no": "YJK2026002345",
     "renew_date": "2026-03-01", "operator": "王主任"}
]
```

保留续期历史便于追溯「哪几年用的哪张卡」。

**分区预建 SQL**

```sql
-- 按月预建 60 个分区（5 年）
DO $$
DECLARE
    start_month DATE := DATE_TRUNC('month', CURRENT_DATE);
    i INT;
    part_start DATE;
    part_end DATE;
    part_name TEXT;
BEGIN
    FOR i IN 0..59 LOOP
        part_start := start_month + (i || ' month')::INTERVAL;
        part_end := part_start + INTERVAL '1 month';
        part_name := 'm14_special_record_p'
                     || TO_CHAR(part_start, 'YYYYMM');
        EXECUTE format(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF '
            'm14_special_record FOR VALUES FROM (%L) TO (%L)',
            part_name, part_start, part_end);
    END LOOP;
END $$;
```

**归档迁移说明**

`m14_special_record` 保留 5 年（法规要求）。归档流程：

```sql
-- 1. 建归档表（结构同主表）
CREATE TABLE IF NOT EXISTS m14_special_record_archive (
    LIKE m14_special_record INCLUDING DEFAULTS
);

-- 2. 归档 5 年前数据
INSERT INTO m14_special_record_archive
SELECT * FROM m14_special_record
WHERE seq_date < CURRENT_DATE - INTERVAL '5 years'
ON CONFLICT (id, seq_date) DO NOTHING;

-- 3. 确认行数一致
SELECT
    (SELECT COUNT(*) FROM m14_special_record
     WHERE seq_date < CURRENT_DATE - INTERVAL '5 years')
    AS src_cnt,
    (SELECT COUNT(*) FROM m14_special_record_archive
     WHERE seq_date < CURRENT_DATE - INTERVAL '5 years')
    AS dst_cnt;

-- 4. 一致后删除
DELETE FROM m14_special_record
WHERE seq_date < CURRENT_DATE - INTERVAL '5 years';
```

> **⚠️ 归档铁律：** 归档表行数必须与被删除行数**完全一致**才能删主表。特殊药品台账是法律凭证，删错无法补救。
