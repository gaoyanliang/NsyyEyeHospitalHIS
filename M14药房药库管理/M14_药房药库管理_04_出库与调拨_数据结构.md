## 4. 数据结构设计

### 4.1 ER 关系图

```
┌──────────────────────┐
│ m14_issue            │ 出库单（领用/样品）
│  issue_no / status   │
└──────┬───────┬───────┘
       │1:N    │
       ▼       │
┌──────────────┐│
│m14_issue_item││ 出库明细（按药品）
│ approved_qty ││
└──────┬───────┘│
       │1:N     │
       ▼        │
┌──────────────┐│
│m14_issue_batch││ 批次分配明细（按批次）
│ batch_id/qty ││
└──────┬───────┘│
       │        │
       ▼        │
┌──────────────────┐
│ m14_stock_txn    │（M14-01，本子模块只调用）
└──────────────────┘

┌──────────────────────┐        ┌──────────────────────┐
│ m14_transfer         │ 1:N ──►│ m14_transfer_item    │
│  transfer_no/status  │        │  transfer_qty        │
│  in_transit_qty      │        │  batch_id            │
└──────┬───────────────┘        └──────────────────────┘
       │1:N
       ▼
┌──────────────────────┐
│ m14_transfer_receive │ 收货记录（可多次）
│  received_qty/diff   │
└──────────────────────┘

┌──────────────────────┐        ┌──────────────────────┐
│ m14_loss             │ 1:N ──►│ m14_loss_item        │
│  loss_no / status    │        │  batch_id/loss_qty   │
│  witness_id          │        │  unit_cost           │
└──────────────────────┘        └──────────────────────┘

┌──────────────────────┐
│ m14_issue_log        │ 操作日志（出库/调拨/报损共用）
│  biz_type / biz_id   │
└──────────────────────┘
```

**设计说明**

| 决策 | 内容 | 理由 |
|---|---|---|
| 三层出库结构 | `issue` → `issue_item` → `issue_batch` | 业务意图（药品级）与执行事实（批次级）分离 |
| 调拨收货独立成表 | `transfer_receive` 而非在 `transfer` 上加字段 | 支持多次收货（分批到货）、差异明细留痕 |
| 报损独立成表 | `loss` 不并入 `issue` | GSP 强制独立留痕、独立审批链、独立保存年限 |
| 日志表三业务共用 | `m14_issue_log` 用 `biz_type` 区分 | 三类业务的操作留痕结构一致，共用减少重复 |
| 冗余药品名称 | 所有明细表都存 `drug_code`/`drug_name`/`specification` | 药品改名后历史单据不变 |
| 记录成本单价 | `issue_batch.unit_cost`、`loss_item.unit_cost` | 财务结转需要，且成本会随批次变化 |

| 索引名 | 类型 | 字段 | 说明 |

**约束说明**

```sql
ALTER TABLE m14_issue
    ADD CONSTRAINT ck_m14_issue_type
    CHECK (issue_type IN ('REQUISITION', 'TRANSFER_OUT', 'LOSS',
                          'SCRAP', 'SAMPLE', 'RETURN_SUPPLIER'));

ALTER TABLE m14_issue
    ADD CONSTRAINT ck_m14_issue_status
    CHECK (status IN ('DRAFT', 'SUBMITTED', 'APPROVED',
                      'REJECTED', 'EXECUTING', 'EXECUTED',
                      'EXEC_FAIL', 'CANCELLED'));

-- 单号格式
ALTER TABLE m14_issue
    ADD CONSTRAINT ck_m14_issue_no
    CHECK (issue_no ~ '^CK[0-9]{8}[0-9]{4}$');

-- 数量非负且短出 = 申请 − 实出
ALTER TABLE m14_issue
    ADD CONSTRAINT ck_m14_issue_qty
    CHECK (total_qty >= 0 AND issued_qty >= 0 AND short_qty >= 0
           AND ABS(short_qty - (total_qty - issued_qty)) <= 0.0001);

-- 金额非负
ALTER TABLE m14_issue
    ADD CONSTRAINT ck_m14_issue_amount
    CHECK (total_amount >= 0);

-- 需要审批的必须最终有审批人（非草稿/驳回/作废时）
ALTER TABLE m14_issue
    ADD CONSTRAINT ck_m14_issue_approved
    CHECK (approval_required = FALSE
           OR status IN ('DRAFT', 'SUBMITTED', 'REJECTED',
                         'CANCELLED')
           OR (approver_id IS NOT NULL AND approved_at IS NOT NULL));

-- 申请人不能是审批人
ALTER TABLE m14_issue
    ADD CONSTRAINT ck_m14_issue_self_approve
    CHECK (approver_id IS NULL
           OR applicant_id IS NULL
           OR approver_id <> applicant_id);

-- 执行人不能是复核人
ALTER TABLE m14_issue
    ADD CONSTRAINT ck_m14_issue_double
    CHECK (checker_id IS NULL
           OR operator_id IS NULL
           OR checker_id <> operator_id);

-- 已执行必须有执行时间
ALTER TABLE m14_issue
    ADD CONSTRAINT ck_m14_issue_executed
    CHECK (status <> 'EXECUTED' OR executed_at IS NOT NULL);

-- 执行失败必须有原因
ALTER TABLE m14_issue
    ADD CONSTRAINT ck_m14_issue_fail
    CHECK (status <> 'EXEC_FAIL' OR fail_reason IS NOT NULL);

-- 驳回必须有原因
ALTER TABLE m14_issue
    ADD CONSTRAINT ck_m14_issue_reject
    CHECK (status <> 'REJECTED'
           OR (reject_reason IS NOT NULL
               AND char_length(btrim(reject_reason)) >= 5));

-- 调拨类必须有目标仓库
ALTER TABLE m14_issue
    ADD CONSTRAINT ck_m14_issue_target
    CHECK (issue_type <> 'TRANSFER_OUT' OR to_warehouse_id IS NOT NULL);
```

**状态机**

```
DRAFT ──┬──► SUBMITTED ──┬──► APPROVED ──► EXECUTING ──┬──► EXECUTED
        │                │                             └──► EXEC_FAIL ──► EXECUTING
        │                └──► REJECTED ──► DRAFT
        └──► CANCELLED（各中间态均可作废）
```

| 年行数 | 2,900 |
| 单行大小 | 约 700 B |

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| pk_m14_issue_item | PRIMARY | id | 主键 |
| uk_m14_issue_item_line | UNIQUE | issue_id, line_no | 行号唯一 |
| uk_m14_issue_item_drug | UNIQUE | issue_id, drug_id | 同一单内药品不重复 |
| idx_m14_issue_item_drug | NORMAL | drug_id, created_at DESC | 按药品查历史 |

**约束说明**

```sql
ALTER TABLE m14_issue_item
    ADD CONSTRAINT ck_m14_issue_item_qty
    CHECK (request_qty > 0 AND approved_qty >= 0
           AND issued_qty >= 0 AND short_qty >= 0
           AND approved_qty <= request_qty
           AND issued_qty <= approved_qty
           AND ABS(short_qty - (approved_qty - issued_qty)) <= 0.0001);

ALTER TABLE m14_issue_item
    ADD CONSTRAINT ck_m14_issue_item_amount
    CHECK (unit_price >= 0 AND amount >= 0);

-- 金额 = 单价 × 实出数量
ALTER TABLE m14_issue_item
    ADD CONSTRAINT ck_m14_issue_item_calc
    CHECK (ABS(amount - ROUND(unit_price * issued_qty, 2)) <= 0.01);

ALTER TABLE m14_issue_item
    ADD CONSTRAINT ck_m14_issue_item_status
    CHECK (line_status IN ('OPEN', 'CLOSED'));

ALTER TABLE m14_issue_item
    ADD CONSTRAINT ck_m14_issue_item_ratio
    CHECK (conversion_ratio >= 1);

ALTER TABLE m14_issue_item
    ADD CONSTRAINT ck_m14_issue_item_batch_count
    CHECK (batch_count >= 0 AND batch_count <= 20);
```

**三层数量关系的意义**

| 关系 | 约束 | 业务含义 |
|---|---|---|
| `approved_qty <= request_qty` | 硬约束 | 审批只能减量不能加量 |
| `issued_qty <= approved_qty` | 硬约束 | 出库不能超过批准量 |
| `short_qty = approved_qty - issued_qty` | 硬约束 | 短出必须有账，不能凭空消失 |

第三条最关键。如果允许 `short_qty` 与两个数量脱钩，运维可以"手工修一下 short_qty"来掩盖差额，审计查不出问题。这个约束让差额永远可计算。

**量级估算**

| 项 | 数值 |
|---|---|
| 年明细数 | 2,900 × 5 = 14,500 |
| 单行大小 | 约 400 B |

**分区：** 不分区。

```sql

    ADD CONSTRAINT ck_m14_issue_batch_qty
    CHECK (allocated_qty > 0 AND issued_qty >= 0
           AND issued_qty <= allocated_qty);

ALTER TABLE m14_issue_batch
    ADD CONSTRAINT ck_m14_issue_batch_cost
    CHECK (unit_cost >= 0 AND amount >= 0);

-- 成本金额 = 成本单价 × 实际出库数量（行级先舍入）
ALTER TABLE m14_issue_batch
    ADD CONSTRAINT ck_m14_issue_batch_amount
    CHECK (ABS(amount - ROUND(unit_cost * issued_qty, 2)) <= 0.01);
```

**`uk_m14_issue_batch_idem`（同一单同一批次只出现一次）的必要性**

假设玻璃酸钠滴眼液有两个明细行（理论上被 `uk_m14_issue_item_drug` 拦住，但拆单后可能出现），或者重试分配时没有清干净旧的批次记录，就会出现：

```
批次 A261001: 分配 120
批次 A261001: 分配 80    ← 同一批次两行
```

执行时会调用 M14-01 两次 `stock/apply`，如果幂等键相同，第二次会被判为重复而跳过，导致实际只扣了 120 而不是 200。但界面上显示的是 200，库存却少了 80 支的账。

用唯一索引从结构上禁止。

**`unit_cost` 与 `amount` 必须落到批次级**

不同批次的进价可能不同（供应商调价、不同批次不同折扣）。如果只在明细行上记一个"平均成本"，财务结转时无法按批次核算成本，也无法准确计算报损金额。

例如：

- 批次 A261001 进价 6.00，出 120 支 → 720.00
- 批次 A260803 进价 5.80，出 80 支 → 464.00
- 明细行合计 1,184.00，平均单价 5.92

    ADD CONSTRAINT ck_m14_transfer_shipped

           OR (shipped_at IS NOT NULL AND seller_id IS NOT NULL));

ALTER TABLE m14_transfer
    ADD CONSTRAINT ck_m14_transfer_received
    CHECK (status NOT IN ('RECEIVED', 'DISPUTED')
           OR (received_at IS NOT NULL AND receiver_id IS NOT NULL));

-- 收货后有差异必须是 DISPUTED，无差异必须是 RECEIVED
ALTER TABLE m14_transfer
    ADD CONSTRAINT ck_m14_transfer_dispute
    CHECK ((status = 'RECEIVED' AND ABS(diff_qty) <= 0.0001)
           OR (status = 'DISPUTED' AND ABS(diff_qty) > 0.0001)
           OR status NOT IN ('RECEIVED', 'DISPUTED'));

-- 在途数量只在 SHIPPED 状态非零
ALTER TABLE m14_transfer
    ADD CONSTRAINT ck_m14_transfer_transit
    CHECK (status = 'SHIPPED' OR in_transit_qty = 0);
```

**`in_transit_qty` 与状态的一致性约束**

最后一条约束是这套设计的核心：

```
status = 'SHIPPED'  ←→  in_transit_qty > 0
status ≠ 'SHIPPED'  ←→  in_transit_qty = 0
```

如果没有这条约束，可能出现：

- 单据已 `RECEIVED` 但在途数量还是 80 → 全院汇总多算 80 支，月度盘点会"多出"这批药
- 单据 `SHIPPED` 但在途是 0 → 货在途中但从账上消失，同样对不上

这条约束让"在途"这个中间态永远与单据状态同步。

**`ck_m14_transfer_dispute` 的意义**

这条约束把"有差异"与"状态 DISPUTED"绑死：

- 无差异 → 只能 `RECEIVED`
- 有差异 → 只能 `DISPUTED`

理由是这两种状态在后续流程中走完全不同的分支：

| 状态 | 后续动作 |
|---|---|
| `RECEIVED` | 直接结案，无后续 |
| `DISPUTED` | 进差异跟踪，需要发货方核查、可能补发或核销 |

如果把有差异的单据也标成 `RECEIVED`，差异就不会进入跟踪队列，过几天就没人记得了。约束强制它进跟踪。

**为什么把收货独立成表而不是在 `transfer` 上加字段？**

有三个理由：

**理由一：支持分批到货。** 调拨 100 支，可能第一次到 60 支、第二次到 40 支。如果在主表上加 `received_qty`，只能记总量，记不了"哪次到多少、每次是谁收的"。

**理由二：差异留痕。** 第一次到 60 支（少 40），写了"短少"的说明；第二次到 42 支（多 2），写了"多到"的说明。两次差异原因和照片都要保留，不能只留最后一次。

**理由三：责任可追溯。** "这批药是张伟收的还是李静收的"必须能查。主表上只有一个 `receiver_id` 字段，分批收货时无法对应。

| 项 | 数值 |
|---|---|
| 年记录数 | 1,460 × 5 × 1.2 = 8,760 |
| 单行大小 | 约 350 B |

**分区：** 不分区。

           OR destroy_at >= approved_at);
```

**`ck_m14_loss_photos` 的 GSP 依据**

《药品经营质量管理规范》第 146 条要求：不合格药品的确认、标识、处理应由质量管理人员负责，处理过程应有完整记录。

对医院药房的实际含义是：**报损必须能证明"这药确实坏了"**。一张糊不清的照片、一段文字描述都不够——必须有可核查的照片。

只有 `OTHER` 类豁免，因为"其他"本身就没有明确可拍照的对象（比如"系统账目串了，需要账务调整"）。

**`ck_m14_loss_witness` 的三方互斥**

这条约束是 GSP 的核心要求，也是最容易被内部人规避的控制点。如果没有这条约束：

1. 药房组长自己报损 100 盒药（说"过期了"）
2. 自己审批
3. 自己当监销人签个字
4. 药品其实没销毁，拿出去卖了

全程一个人操作、一个签名，审计查不出来。要求"申请人 ≠ 审批人 ≠ 监销人"这三个角色互斥，就至少需要三个人合谋才能作案，成本大幅提高。

|---|---|
| 月报损单 | 8 张 |
| 年行数 | 96 |
| 单行大小 | 约 1 KB（含 JSONB） |
| 保留 | **10 年**（GSP 要求 5 年以上，按 10 年设计） |

**分区：** 不分区。

**为什么报损必须指定批次？**

这是 GSP 追溯的要求。如果只写"过期玻璃酸钠滴眼液 10 支"，追溯时无法回答：

- 哪一批过期的？
- 这批药有没发出去？
- 同一批的其他药要不要一起召回？

必须指定 `batch_id`，才能在必要时反查出这批药的所有去向（发药记录、调拨记录、其他报损单）。

**`retail_price` 为什么存？**

报损的**账务金额**按成本价（`unit_cost`），但**管理口径**要知道"这批药本来能卖多少钱"（`retail_price`）。

两者用于不同报表：

| 字段 | 用途 | 报表 |
|---|---|---|
| `unit_cost` | 财务损失 | 财务报表、成本核算 |
| `retail_price` | 经营损失 | 药事管理报表、绩效考核 |

如果只存成本价，药事科主任看到"本月报损 860 元"会觉得影响不大；如果同时看到"零售价值 1,320 元"，会意识到这相当于少服务了多少患者。

| 单行大小 | 约 350 B |

**为什么日志表要禁止修改？**

操作日志的价值在于"原样保存当时的操作"。如果允许修改：

- 事后可以把"审批人：张三"改成"李四"
- 可以把"操作时间 22:00"改成"14:00"
- 可以把 ERROR 记录删掉

这样日志就失去了审计价值。触发器保证即使数据库管理员也无法修改（除非显式先删除触发器，这本身会留下痕迹）。

class TransferCreate(BaseModel):
    from_warehouse_id: int
    to_warehouse_id: int
    transfer_reason: str = Field(..., min_length=5, max_length=512)
    expected_date: Optional[date] = None

        if self.from_warehouse_id == self.to_warehouse_id:

class LossDestroy(BaseModel):

    destroy_location: Optional[str] = Field(None, max_length=128)

    operator_id: int
    attachments: Optional[List[str]] = None
    delegate_no: Optional[str] = Field(None, max_length=64)
    delegate_org: Optional[str] = Field(None, max_length=128)

    @model_validator(mode="after")

        return self
