```
   ▼          ▼          ▼
┌──────────────┐ ┌──────────────────┐ ┌────────────────┐
│dispense_item │ │                 │ │ dispense_error │

└──────────────┘ │                 │

┌────────────────┼─────────────────┘
│  m14_drug_return（退药单主表）
│    return_no / dispense_id / 判定汇总
└──┬──────────────
   │1:N

┌────────────────────┐

外部依赖（不建外键，通过接口获取）：
  M07-05 处方主档    rx_id / rx_no
  M14-06 审核任务    review_id / review_conclusion
  M16-01 结算单      settlement_id / settlement_no
  M14-01 库存批次    batch_id / batch_no
  M01-03 药品主档    drug_id / drug_code
```

**设计说明**

| 决策 | 内容 | 理由 |
|---|---|---|
| 明细与批次分两层 | `dispense_item` → `dispense_batch` | 一个药品可能来自多个批次，批次追溯是强制要求 |
| 差错独立成表 | `m14_dispense_error` | 一次发药可能发生多次差错，需完整留痕 |
| 退药独立成表 | `m14_drug_return` + `_item` | 退药是独立业务事实，不能在发药记录上改写 |
| 不建外键到 M07/M16/M14-01 | 仅存 ID 与冗余快照 | 跨模块解耦，避免级联与跨库锁定 |
| 零金额明细 | 赠送药品 `unit_price = 0` 允许 | 眼科赠药（试用装）是真实业务场景 |

> **⚠️ 只读铁律：** 发药单一旦进入 `DISPENSED`，其明细与批次记录由**只读触发器**保护，任何 UPDATE/DELETE 都会被拒绝。退药必须新建 `m14_drug_return`，不得改写发药记录。

**关键设计说明**

**为什么 `uk_m14_dispense_active_rx` 是必须的？**

考虑并发场景：患者缴费后，M16 通过事件创建一个发药单（预调配），同时患者到窗口扫码，收方接口又创建了一个：

```
id  dispense_no  rx_no   status
1   FY...000001  RX001   RECEIVED   ← M16 事件创建
2   FY...000002  RX001   RECEIVED   ← 窗口收方创建
```

后果：

- 药师看到同一患者两张发药单，重复调配（药房多发一份药）
- 扣库存两次，账实不符
- 患者拿到两份药

`uk_m14_dispense_active_rx` 用部分唯一索引（只约束在途状态）从数据库层面杜绝。已发药（`DISPENSED`）和已取消（`CANCELLED`）不参与唯一性，因为它们不是"在途"，允许同一处方历史上有过多个发药单（例如先取消再重收）。

**为什么 `idempotency_key` 与 `uk_m14_dispense_active_rx` 两者都要？**

两者解决不同问题：

| 约束 | 解决的问题 |
|---|---|
| `uk_m14_dispense_idem` | 同一个请求重复发送（网络重试、事件重投） |
| `uk_m14_dispense_active_rx` | 不同来源同时创建（事件 + 人工收方） |

只有幂等键，无法阻止"事件创建 + 人工收方"两条不同路径同时建单；只有在途唯一，无法在幂等重放时返回原记录（唯一冲突后需要判断是幂等命中还是业务冲突）。

**`ck_m14_dispense_double` 是资金与用药安全的核心**

这条约束在数据库层面强制「调配员 ≠ 复核员」：

```sql
CHECK (checker_id IS NULL OR dispatcher_id IS NULL
       OR checker_id <> dispatcher_id)
```

它的意义在于：**即使应用层有 bug，也无法产生同人复核的记录**。

真实故障场景：某医院药房在人员紧张时，让一位药师兼做调配与复核。某次调配时拿了同名不同规格的眼药水（5ml 与 10ml），复核时因为是自己配的，只看了药名就通过，患者拿到错误规格，用了两周才发现。

数据库约束让这条管理要求变成技术强制。

**`ck_m14_dispense_instruction` 用 JSONB 做完整性校验**

```sql
(instruction_confirmed ->> 'usage')::boolean IS TRUE
AND (instruction_confirmed ->> 'precaution')::boolean IS TRUE
AND (instruction_confirmed ->> 'storage')::boolean IS TRUE
AND (instruction_confirmed ->> 'understood')::boolean IS TRUE
```

这样即使应用层漏勾，也无法把状态写成 `DISPENSED`。

之所以用 JSONB 而不是 4 个布尔字段：用药交代的项数将来可能扩展（比如新增"已说明复诊时间"），字段结构不变。

**为什么 `returnable_until` 要冗余存储？**

退药时限由参数决定（默认 7 天）。如果只存 `dispensed_at`，退药时用 `dispensed_at + 参数天数` 计算：

- 参数被修改后，历史发药单的可退时限跟着变
- 药监或审计问"这张处方当时可退到什么时候"，答不上来

冗余存储 `returnable_until`，把"发药那一刻的规则"固化下来。参数变更只影响新发药单。

```sql
    ADD CONSTRAINT ck_m14_dispense_item_qty

           AND short_qty >= 0);

-- 调配数量不能超过处方数量
ALTER TABLE m14_dispense_item
    ADD CONSTRAINT ck_m14_dispense_item_limit
    CHECK (dispensed_qty <= prescribed_qty);

-- 实发数量不能超过调配数量

    ADD CONSTRAINT ck_m14_dispense_item_issue_limit
    CHECK (issued_qty <= dispensed_qty);

ALTER TABLE m14_dispense_item
    ADD CONSTRAINT ck_m14_dispense_item_balance
    CHECK (ABS(dispensed_qty + short_qty - prescribed_qty) < 0.0001);

-- 金额 = 单价 × 实发（行级先舍入）
ALTER TABLE m14_dispense_item
    ADD CONSTRAINT ck_m14_dispense_item_amount
    CHECK (unit_price IS NULL OR amount IS NULL
           OR ABS(amount
                  - ROUND(unit_price * issued_qty, 2)) < 0.01);

ALTER TABLE m14_dispense_item
    ADD CONSTRAINT ck_m14_dispense_item_price
    CHECK (unit_price IS NULL OR unit_price >= 0);

-- 缺药必须有原因
ALTER TABLE m14_dispense_item
    ADD CONSTRAINT ck_m14_dispense_item_short_reason
    CHECK (short_qty = 0 OR shortage_reason IS NOT NULL);

-- 眼别枚举
ALTER TABLE m14_dispense_item
    ADD CONSTRAINT ck_m14_dispense_item_eye
    CHECK (eye_side IS NULL
           OR eye_side IN ('OD', 'OS', 'OU', 'NA'));

-- 打印次数

    ADD CONSTRAINT ck_m14_dispense_item_print
    CHECK (label_print_count >= 0 AND label_print_count <= 20);

ALTER TABLE m14_dispense_item
    ADD CONSTRAINT ck_m14_dispense_item_printed
    CHECK (label_printed = FALSE OR label_print_count >= 1);
```

**`ck_m14_dispense_item_balance` 的必要性**

```
调配数量 + 缺药数量 = 处方数量
```

这条等式保证「没有凭空消失的药」。举例：

- 处方 2 支，调配 2 支，缺药 0 → 2 + 0 = 2 ✅
- 处方 2 支，调配 1 支，缺药 1 → 1 + 1 = 2 ✅
- 处方 2 支，调配 1 支，缺药 0 → 1 + 0 ≠ 2 ❌ 拦住

第三种情况就是"配少了但没登记"，这是药房最常见的操作疏漏，会导致患者少拿药、退费算不清。

**为什么允许 `unit_price = 0`？**

眼科常有赠药场景：术后赠送人工泪液试用装、厂家活动赠送滴眼液。这些药必须**走正常的调配与发药流程**（患者要知道怎么用，药监要知道流向了哪），但金额为 0。

如果强制 `unit_price > 0`，这些药就只能绕过系统发放，导致账实不符。

**这张表是药监追溯的唯一入口**

药监飞检的典型问题：「批号 240815 的左氧氟沙星滴眼液，共进了 500 支，都发给了谁？现在还有多少？」

回答这个问题的路径完全依赖 `m14_dispense_batch`：

```sql
SELECT d.rx_no, d.patient_name, d.dispensed_at, b.quantity
FROM m14_dispense_batch b
JOIN m14_dispense d ON d.id = b.dispense_id
WHERE b.batch_no = '240815'
ORDER BY d.dispensed_at;
```

如果没有这张表，只有 `m14_dispense_item`（药品级），就答不出「哪一支来自哪个批次」。

**`idx_m14_dispense_batch_no` 是召回的核心索引**

当厂家宣布某批号召回时，必须**当天**把所有发出去的药找回来。这个查询按 `batch_no` 精确匹配，索引命中后按 `created_at` 倒序（先找最近的、患者还在用药的）。

**为什么 `expiry_warning_days` 要快照？**

发药时该批次还剩多少天效期，是判断"药师是否在效期管理上失职"的依据。

如果只存 `expiry_date`，事后用 `expiry_date - dispensed_at` 计算也能得到，但发药时的"今天"如果发生了变化（比如跨时区、系统时间被调），结果会漂移。快照固化。

- 复核在走过场（所有单子都直接通过）
- 或者没人登记差错

所以监控上要同时看「差错率」和「复核时长」，两者都异常低时告警。

**`ck_m14_drug_return_qty_balance` 的意义**

```
可再用数量 + 报废数量 = 退药总数量
```

这保证「退回来的每一支药都有去处」：

- 进了库存（可再用）
- 或者报废了（不可再用）

不能出现「退了 2 支，但只记录了 1 支入库、0 支报废」这种账实不符。

**`ck_m14_drug_return_self_approve` 是退药审核的底线**

退药是资金流出动作。如果办理人自己就能审批自己提交的大额退药，等于没有审批。

真实风险场景：某收银员与外部人员串通，虚构退药（实际没有患者），自己提交自己审批，退费到指定账户。有职责分离约束，这条路走不通。

**为什么退药原因说明要 ≥ 10 字？**

「退药」两个字填不了。系统强制要求药师写清楚：

- 「患者症状好转，医生建议停药，剩余一支未拆封」
- 「药物过敏，出现眼睑红肿，已就医处理」

10 字是底线，能筛掉「无」「其他」「退了」这类无效输入。

**`ck_m14_drug_return_item_limit` 是防超退的最后一道防线**

```sql
CHECK (returned_before + return_qty <= issued_qty)
```

这条约束在**行级**保证累计退药不超过原实发。

为什么必须有？因为退药可以分批：

```
第 1 天：退 1 支（issued=2, returned_before=0, return_qty=1）→ 0+1 ≤ 2 ✅
第 3 天：再退 1 支（returned_before=1, return_qty=1）→ 1+1 ≤ 2 ✅
第 5 天：又退 1 支（returned_before=2, return_qty=1）→ 2+1 > 2 ❌ 拦住
```

没有这条约束，第三次退药会通过，患者拿到 3 支的钱（实际只买了 2 支）。

**`returned_before` 是快照而非计算值**

应用层在插入时计算 `returned_before = SUM(已退数量)`，然后写死。这样即使并发两笔退药同时到达，第二笔的 `returned_before` 是错的，约束会拒绝它（因为第一笔已经插入了）。这是"乐观"的做法——用唯一约束 + 校验兜底。

更严格的做法是在 `dispense_item` 上维护 `returned_qty` 累积列并加行锁。本项目采用**前者**（快照 + 约束），理由：退药是低频动作（1.48%），并发冲突概率极低，重试代价小；而维护累积列需要行锁，反而增加复杂度。

**`ck_m14_drug_return_item_reusable` 防"判定与入库不一致"**

```
judge_result = 'REUSABLE'  ⟺  is_reusable = TRUE
```

如果分开写这两个字段，应用层很容易出现：

- 判定为 `REUSABLE`（药师认为还能用）
- 但 `is_reusable = FALSE`（某个分支漏赋值）
- 结果药没入库，凭空消失

约束强制两者绑定。

| 年行数 | 约 2,650 |

**归档迁移说明**

`m14_dispense` 保留 5 年（GSP 要求）。归档流程：

```sql
-- 1. 建归档表
CREATE TABLE IF NOT EXISTS m14_dispense_archive (
    LIKE m14_dispense INCLUDING DEFAULTS
);

-- 2. 归档 5 年前数据（仅终态）
INSERT INTO m14_dispense_archive
SELECT * FROM m14_dispense
WHERE dispensed_at < NOW() - INTERVAL '5 years'
  AND status IN ('DISPENSED', 'RETURNED', 'CANCELLED')
ON CONFLICT (id) DO NOTHING;

-- 3. 归档关联明细与批次
INSERT INTO m14_dispense_item_archive
SELECT i.* FROM m14_dispense_item i
JOIN m14_dispense_archive a ON a.id = i.dispense_id;

INSERT INTO m14_dispense_batch_archive
SELECT b.* FROM m14_dispense_batch b
JOIN m14_dispense_archive a ON a.id = b.dispense_id;

-- 4. 确认行数一致后删除
DELETE FROM m14_dispense
WHERE id IN (SELECT id FROM m14_dispense_archive)
  AND status IN ('DISPENSED', 'RETURNED', 'CANCELLED');
```

> **⚠️ 归档铁律：** 归档表行数必须与被删除行数**完全一致**才能删主表。批次表（`m14_dispense_batch`）是药监追溯依据，归档后必须仍可按 `batch_no` 查到患者。
