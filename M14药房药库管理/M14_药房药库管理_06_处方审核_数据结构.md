## 4. 数据结构设计

### 4.1 ER 关系图

```
┌────────────────────────────────────┐
│ m14_rx_review                      │ 审核任务主表
│  review_no / rx_id / rx_version    │
│  priority / status / conclusion    │
│  auto_result / auto_issues         │
└───┬──────────┬──────────┬───────┬──┘
    │1:N       │1:N       │1:N    │1:N
    ▼          ▼          ▼       ▼
┌────────┐ ┌──────────┐ ┌───────┐ ┌──────────────────┐
│ issue  │ │confirmation││consult│ │      log         │
│自动问题│ │ 问题确认  ││ 会诊  │ │  操作日志（只增）  │
└────────┘ └──────────┘ └───────┘ └──────────────────┘

┌────────────────────────┐
│ m14_rx_review_rule     │ 规则配置（独立，不随任务）
└────────────────────────┘

外部依赖（不建外键，通过接口获取）：
  M07-05 处方主档   rx_id / rx_no / rx_version
  M01-03 药品主档   drug_id / drug_code
  M03-01 患者主档   patient_id
```

**设计说明**

| 决策 | 内容 | 理由 |
|---|---|---|
| 问题独立成表 | `m14_rx_review_issue` 而非 JSONB 存主表 | 需要按规则码统计、按严重度筛选、逐条确认 |
| 确认独立成表 | `m14_rx_review_confirmation` | 一条问题可能被多次确认（撤销后重新确认），需留痕 |
| 会诊独立成表 | `m14_rx_review_consult` | 一条审核可能有多次会诊，每次多人多轮 |
| 规则独立成表 | `m14_rx_review_rule` | 规则是配置，跨任务共享 |
| 日志独立成表 | `m14_rx_review_log` | 只增不改，独立于业务表生命周期 |
| 不建外键到 M07/M01/M03 | 仅存 ID 与冗余快照 | 跨模块解耦，避免级联与锁定 |

> **⚠️ JSONB 的取舍说明：** 主表保留了 `auto_result`（汇总计数）与 `auto_issues`（问题快照）两个 JSONB 字段作为**冗余快照**，用于详情页一次查询返回全部信息。**权威数据以 `m14_rx_review_issue` 表为准**，两者在任务创建时同时写入。留存 JSONB 快照的理由是：审核提交后问题清单不可变，快照即完整历史；表查询用于统计与筛选。

**关键设计说明**

**为什么 `uk_m14_rx_review_idem` 是必须的？**

M07 发送 `m07.rx.signed` 事件时可能重发（网络抖动、Outbox 重试、MQ 重复投递）。没有幂等键，一张处方会创建两个审核任务：

```
review_no  YS2026102100001  rx_id 512  V1  PENDING
review_no  YS2026102100002  rx_id 512  V1  PENDING   ← 重复
```

后果：

- 药师看到同一个患者两张待审处方，重复劳动
- 两张都点了通过，第二次回写 `on-reviewed` 时 M07 会认为"重复审核"
- 台账统计里审核数虚高

幂等键 `RX:{rx_id}:V{rx_version}` 从数据库层面保证唯一。第二次请求捕获唯一冲突后返回原记录（`is_idempotent = true`）。

**为什么用 `rx_version` 而不是 `rx_id` 单独做幂等？**

处方被退回后医生修改，M07 会升版本号（V1 → V2）并重新签名。如果幂等键只用 `rx_id`：

- V1 审核任务存在（RETURNED）
- V2 的新审核任务想插入，撞上唯一键 → 失败

带上版本号，V1 与 V2 是两个不同的幂等键，各建各的任务，台账里能看到完整链条。

**`ck_m14_rx_review_conclusion_match` 的必要性**

这条约束强制 `status` 与 `conclusion` 同步。看一个真实故障场景：

某系统没有这条约束，运维手工改了一条记录的 `status = 'PASSED'`，忘了改 `conclusion`（还是 `NULL`）。结果：

- 列表页显示"通过"（读 `status`）
- 导出报表统计通过率时 `WHERE conclusion = 'PASSED'` 一条都查不到
- 药师绩效算出来是 0

约束让这种不一致在数据库层面就写不进去。

**`ck_m14_rx_review_done` 的完整性要求**

终态必须有：`reviewer_id` + `reviewed_at` + `review_opinion`（≥10 字）。

这是 GSP 检查的核心证据链。药监来查"这张处方的审核意见是什么"，必须能立刻答上。如果数据库允许空意见，应用层一旦有 bug 就会产生"审了但说不出理由"的记录。

**为什么不给 `auto_issues` JSONB 建 GIN 索引？**

问题清单的查询模式是"查某个审核任务的全部问题"（按 `review_id` 过滤，走主键），不是"查包含某规则码的所有任务"（那走 `m14_rx_review_issue` 表）。JSONB 在这里纯粹是详情页快照，按主键读，不需要索引。

**量级估算**

| 项 | 数值 |
|---|---|
| 日门诊处方量 | 350 张 |
| 退回后重审 | +8% |
| 日审核任务 | 约 378 |
| 年行数 | 约 138,000 |
| 单行大小 | 约 1.2 KB（含 JSONB 快照） |
| 年增量 | 约 166 MB |
| **保留** | **2 年**（GSP 处方审核记录要求） |

**分区：** 不分区，按需归档。

GSP《药品经营质量管理规范》第 141 条要求"处方审核记录保存不少于 2 年"。2 年约 27.6 万行 / 332 MB，单表完全可承受。

3 年后归档方案：

```sql
-- 每年 1 月 10 日执行
INSERT INTO m14_rx_review_archive
    SELECT * FROM m14_rx_review
    WHERE reviewed_at < NOW() - INTERVAL '2 years'
      AND status IN ('PASSED','CONDITIONAL','RETURNED','REJECTED');
```

> **注意：** 归档前必须确认对应日志已保留（`m14_rx_review_log` 保留 3 年），否则证据链断裂。

**`uk_m14_rx_review_issue_rule` 的必要性**

同一个规则可能对同一张处方的**不同行**命中（比如三种药都超剂量），所以唯一键要带 `line_no`。

但**同一个规则不能对同一行的同一个问题重复命中**。如果没有这条约束：

场景：处方有 `DOSE_DAILY_MAX`（日剂量超上限）这条规则。某次代码变更导致引擎跑了两次（比如事件重复消费），于是：

```
seq 1  DOSE_DAILY_MAX  line 2  日剂量 12 片，上限 8 片
seq 2  DOSE_DAILY_MAX  line 2  日剂量 12 片，上限 8 片   ← 重复
```

药师看到"2 条阻断"，实际只有 1 个问题。而且提交时 `confirmed_issue_ids` 要确认两次，交互混乱。

`COALESCE(line_no, 0)` 的作用是处理"整单级问题"（如 `IND_NO_DIAG` 无诊断开方，不针对具体行）。如果直接写 `line_no`，NULL 在唯一索引里互不相等，同样的整单级问题会重复插入。

**`ck_m14_rx_review_issue_block` 的语义**

阻断级问题**不能被确认为已忽略** —— 只能通过"退回"或"拒审"处理。这条约束是数据层的兜底，防止应用层 bug 让药师"勾选确认后通过"一条禁忌用药的处方。

**为什么 `evidence` 用 JSONB？**

不同规则的证据结构完全不同：

```
// DOSAGE 规则
{"daily_dose": 12, "max_daily_dose": 8, "times_per_day": 4}

// DDI 规则
{"drug_a": "拉坦前列素", "drug_b": "溴莫尼定", "severity": "MAJOR"}

// CONTRA_ALLERGY 规则
{"allergy": "磺胺类", "drug_name": "复方托吡卡胺", "cross": "磺酰胺基"}
```

用固定列表达不了，用文本会丢失结构（前端无法高亮字段）。JSONB 既能存任意结构，也支持 `->>` 查询。

**为什么用 `round_no` 而不是直接追加行？**

会诊是**对话**，每一轮都是一问一答。`round_no` 明确表达"第几轮"，前端聚合查询一次就能按顺序渲染完整对话。如果不带轮次，只能按 `created_at` 排序，秒级相同时间并发写入时顺序不确定，对话会错乱。

**为什么 `initiator_id <> consultant_id` 要写约束？**

自我会诊没有意义，但代码里一个疏忽（下拉框把当前用户也列进去了）就会产生。数据库拒绝比应用层校验更可靠。

**为什么把 `adopt` 也作为一种 `msg_type`？**

这样整条会诊的时间线可以用一次 `ORDER BY round_no` 完整呈现：

```
round 1  INITIATE  李药师 → 张临床药师   问题：激素+干眼症防腐剂累积风险？
round 2  REPLY     张临床药师 → 李药师   回复：建议激素控制 14 天内...
round 3  ADOPT     李药师 → 张临床药师   采纳会诊意见
```

如果采纳单独存一个字段，前端要拼接两个数据源才能画完整时间线。

**为什么确认要独立成表，而不是 `m14_rx_review_issue.is_confirmed` 一个布尔？**

**场景：** 药师确认了一条警告（"已了解，患者已知情"），后来发现搞错了，撤销确认重新审视，再确认一次。

```

```

```
id 2031  issue 90002  CONFIRM  李药师  10:35:20  active=TRUE
id 2035  issue 90002  CONFIRM  李药师  10:36:10  active=FALSE  revoked 10:36:30
id 2036  issue 90002  CONFIRM  李药师  10:37:05  active=TRUE
```

药监或内部审计问"这条警告是谁确认的、有没有反复"，一目了然。

**`uk_m14_rx_review_confirm_active` 的作用**

**为什么阻断级规则不可关闭？**

`ck_m14_rx_review_rule_block` 强制 `default_severity = 'BLOCK'` 的规则必须：

- `is_enabled = TRUE`（不能停用）
- `is_closable = FALSE`（不能通过配置关闭）
- `current_severity = 'BLOCK'`（不能降级为 WARN）

这三条是硬性的。阻断级规则对应的是**法规红线**：

| 规则码 | 对应法规条款 |
|---|---|
| `CONTRA_ALLERGY` | 处方管理办法第 14 条：有配伍禁忌或不良相互作用不得调配 |
| `DDI_CONTRA` | 同上 |
| `CONTRA_PREGNANT` | 孕妇禁忌 |
| `DOSE_SINGLE_MAX` / `DOSE_DAILY_MAX` | 超剂量用药 |
| `IND_NO_DIAG` | 处方管理办法第 6 条：处方必须有临床诊断 |
| `OPH_MYDRIATIC_ANGLE` | 眼科专业规范：闭角型青光眼禁用散瞳药 |
| `DUP_SAME_DRUG` | 同一药品重复 |

如果允许配置关闭，某个药房主任为了"提高效率"关掉了过敏检查，出了事故就是医院责任。数据库层面锁死比制度约束可靠。

**`threshold_json` 的作用**

有些规则需要阈值参数，比如：

```json
{"max_days_default": 30, "max_days_ophthalmic_liquid": 14}
```

发药天数上限规则：普通药品 30 天，眼科液体剂型 14 天。

```json
{"steroid_max_days": 14, "warn_days": 10}
```

激素类滴眼液规则：连续使用超过 14 天触发警告，10 天起提示。

```json
{"min_drug_count": 2, "min_daily_times": 4}
```

多防腐剂叠加规则：含防腐剂滴眼液种类不少于 2 种且合计频次不少于 4 次每日时触发。

阈值与代码分离，调参数不用发版。

**`keep_forever` 的用途**

绝大多数日志 3 年后可清理，但某些日志必须永久保留：

- 涉及医疗纠纷的审核（法务标记）
- 药监飞检查到的样本
- 内部审计发现问题的审核

标记 `keep_forever = TRUE` 后，清理任务跳过该行。

**为什么审核日志必须只增不改？**

审核结论是本模块最敏感的字段。一旦允许修改：

1. 药师误点了"通过"（本应退回）
2. 事后发现，改写日志把"通过"改成"退回"
3. 现场看记录是"退回"，但实际处方已经调配出去了
4. 责任无法认定

只读触发器保证写入后不可改，即使 DBA 要改，必须先删触发器（DDL 会进 PostgreSQL 审计日志）。

**量级估算**

| 项 | 数值 |
|---|---|
| 每任务日志条数 | 约 6 条（创建/锁定/确认/提交/回写/…） |
| 年行数 | 约 828,000 |
| 单行大小 | 约 400 B |
| 年增量 | 约 332 MB |
| **保留** | **3 年** |

**分区：** 按月 RANGE 分区，预建 36 个月，热数据保留 180 天。

```sql
CREATE TABLE m14_rx_review_log (
    ...
) PARTITION BY RANGE (created_at);

CREATE TABLE m14_rx_review_log_202610
    PARTITION OF m14_rx_review_log
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

**分区原因：** 年 82.8 万行、332 MB，且只按时间查询。分区后历史日志可整段 DROP，不影响热数据性能。

**归档迁移说明**

`m14_rx_review` 保留 2 年（GSP 要求）。归档流程：

```sql
-- 1. 建归档表（结构同主表）
CREATE TABLE IF NOT EXISTS m14_rx_review_archive (
    LIKE m14_rx_review INCLUDING DEFAULTS INCLUDING CONSTRAINTS
);

-- 2. 每年 1 月 10 日归档 2 年前数据
INSERT INTO m14_rx_review_archive
SELECT * FROM m14_rx_review
WHERE reviewed_at < NOW() - INTERVAL '2 years'
  AND status IN ('PASSED','CONDITIONAL','RETURNED','REJECTED')
ON CONFLICT (id) DO NOTHING;

-- 3. 归档关联从表
INSERT INTO m14_rx_review_issue_archive
SELECT i.* FROM m14_rx_review_issue i
JOIN m14_rx_review r ON r.id = i.review_id
WHERE r.reviewed_at < NOW() - INTERVAL '2 years'
  AND r.status IN ('PASSED','CONDITIONAL','RETURNED','REJECTED');

-- 4. 确认归档成功后删除主表数据
DELETE FROM m14_rx_review
WHERE reviewed_at < NOW() - INTERVAL '2 years'
  AND status IN ('PASSED','CONDITIONAL','RETURNED','REJECTED')
  AND id IN (SELECT id FROM m14_rx_review_archive);
```

> **⚠️ 归档铁律：** 归档**必须先确认成功再删除**，且归档表的行数必须与删除行数完全一致。日志表（`m14_rx_review_log`）保留 3 年，比主表长 1 年，保证归档后证据链仍完整。
