## 1. 模块概述

### 1.1 模块定位

M14 是医院**药品实物的唯一管理者**。它回答四个问题：

1. **有多少？** —— 现在是账面多少、实际多少、可用多少
2. **从哪来、到哪去？** —— 采购进来、调拨出去、发给患者
3. **该不该发？** —— 处方审核、限量控制、特殊药品管控
4. **合规吗？** —— GSP 追溯、麻精双签、药监报表

│                        M14 在 HIS 中的位置                            │

### 1.2 为什么 M14 是一个模块而不是功能

四条理由：

**① 库存必须只有一个真相源**

药品库存是全院最不容许「各说各话」的数据：

- 药房说「还有 30 支」
- 收费系统说「已经收了 5 支的钱」
- 医生工作站说「开了 8 支的医嘱」

三个数对不上时，没人说得清到底该进多少货。

如果库存分散在多个模块各自维护，必然出现：出库扣了但入库没加、调拨只有出没有入、盘点调整只改了账没改批次。最终结果是**账实不符且无法定位原因**。

M14 的做法：**库存数量只有一个唯一入口**（M14-01 的 `POST /internal/v1/m14/stock/apply`），任何模块想让数量变化都必须走这个接口，每次变化写一条只增不改的流水。

**② 药品管理的法规密度远高于其他物资**

| 法规 | 对系统的硬性要求 |
|---|---|
| 《药品管理法》 | 全程可追溯，进货查验记录保存 5 年 |
| 《药品经营质量管理规范》(GSP) | 批号管理、效期管理、温湿度记录 |
| 《麻醉药品和精神药品管理条例》 | 专柜双锁、双人双签、空安瓿回收、印鉴卡 |
| 《医疗机构药事管理规定》 | 调剂四环节（审核/调配/核对/发药） |
| 《医疗机构处方审核规范》 | 药师审核是发药前置条件 |

这些要求彼此关联（批号追溯要串起采购→入库→出库→发药→退药），拆到不同模块会产生大量跨模块事务。

**③ 药库与药房的业务本质不同**

| 维度 | 药库（面对供应商） | 药房（面对患者） |
|---|---|---|
| 主要风险 | 账实不符、采购舞弊 | 发错药、发错人 |
| 控制手段 | 审批 + 验收 + 盘点 | 双人复核 + 扫码核对 |
| 时间粒度 | 按批次、按订单 | 按处方、按患者 |
| 失败后果 | 资金损失 | 患者伤害 |

风险不同，权限模型就必须不同。这是一个模块内必须分两个子模块的原因，而不是分成两个模块——因为它们共享同一套库存台账。

**④ 与 M16 收费的边界必须清晰**

M16 管「钱」，M14 管「药」。二者的交界处最容易出错：

- 收了钱但没发药 → 库存没减，患者投诉
- 发了药但没收费 → 库存减了，收入少了
- 退了费但药没退回 → 账上多了，实际少了

M14 的边界：**M14 只在「实物动了」的时候改库存**。M16 收费成功是 M14 发药的前置条件（需校验），但收费本身不动库存。

### 1.3 眼科药房的特殊性

| 特殊性 | 对设计的影响 |
|---|---|
| **滴眼液是主力剂型** | 拆零逻辑与口服药完全不同：1 支 5ml 滴眼液按「支」发，不是按「毫升」；但拆零销售时又按支 |
| **处方量集中在上午** | 90% 门诊处方在 8:30~11:30 产生，需要预调配与叫号 |
| **单剂量分包需求低** | 眼科住院患者少、口服药少，分包机使用率低于综合医院 |
| **药占比天然偏低** | 眼科用药量小、单价低，药占比一般 8~15%（综合医院 30%+），指标阈值需单独设定 |
| **抗菌药物以局部用药为主** | 左氧氟沙星滴眼液占抗菌药物使用量 30%+，与全身用药的强度计算口径不同 |
| **散瞳药是特色风险点** | 散瞳药 + 青光眼 = 绝对禁忌（前房浅者可能诱发急性闭角型青光眼），必须 BLOCK 级拦截 |
| **激素类滴眼液长期使用风险** | 眼科常用糖皮质激素滴眼液，超过 14 天需监测眼压，需审核拦截 |

### 1.4 模块目标

| 目标 | 指标 | 说明 |
|---|---|---|
| 库存账实相符 | ≥ 99.9% | 盘点相符批次数 / 盘点总批次数 |
| 批次可追溯 | 100% | 任一批次可查完整链路 |
| 处方审核覆盖 | 100% | 所有处方经药师审核 |
| 发药差错率 | ≤ 0.05% | 差错数 / 发药数 |
| 特殊药品合规 | 100% | 双签、空瓿回收、专册台账 |
| 系统可用性 | ≥ 99.9% | 药房全年无中断 |
| 发药响应 | P95 ≤ 2 分钟 | 从患者到窗口到药品交付 |

### 2.2 拆分主线一：库存唯一真相

**判断口诀：M14-01 只回答「有多少」。谁让它变少、变多、变到哪去，都是别人决定的事。**

10 个子模块中有 6 个会**改变**库存数量：

| 子模块 | 改库存的动作 | 流水类型 |
|---|---|---|
| M14-03 | 采购入库、采购退货 | `PURCHASE_IN` / `PURCHASE_RETURN` |
| M14-04 | 出库、调拨出入、报损 | `ISSUE_OUT` / `TRANSFER_IN/OUT` / `LOSS_OUT` |
| M14-05 | 盘点调整 | `STOCKTAKE_IN` / `STOCKTAKE_OUT` |
| M14-07 | 门诊发药、退药 | `DISPENSE_OUT` / `RETURN_IN` |
| M14-08 | 病区摆药、退药 | `WARD_DISPENSE_OUT` / `WARD_RETURN_IN` |
| M14-09 | 专柜出入、空瓿核销 | `SPECIAL_IN` / `SPECIAL_OUT` |

如果每个模块自己 `UPDATE` 库存表，会出现：

- 有人在事务里改了两张表，回滚不一致
- 有人忘了写流水，事后查不出为什么少了
- 两个人同时扣同一批次，一个成功一个覆盖

**解法：统一入口 + 只增流水**

```
任何模块想改库存
        │
        ▼
POST /internal/v1/m14/stock/apply
        │
        ├── ① 校验幂等键（防重复提交）
        ├── ② 校验方向与流水类型匹配
        ├── ③ 条件原子更新（WHERE qty >= n AND version = v）
        ├── ④ 写 m14_stock_txn（只增，触发器禁止改删）
        └── ⑤ 返回 before/after 数量
```

**并发扣减用「条件原子更新」而非纯行锁：**

```sql
UPDATE m14_stock_batch
SET qty_on_hand = qty_on_hand - :qty,
    qty_locked = qty_locked - :qty,
    version = version + 1
WHERE id = :batch_id
  AND qty_locked = :qty
  AND version = :version
```

`rowcount = 0` 说明被并发修改，重试下一批次。

为什么不用 `SELECT ... FOR UPDATE`？门诊高峰时热门滴眼液一天 300 张处方，5 个窗口用行锁会串行排队，单笔从 30ms 涨到 150ms。条件更新在冲突时才失败重试，无冲突时零等待。

### 2.3 拆分主线二：药库与药房分界

| 维度 | 药库（M14-03 / M14-04 / M14-05） | 药房（M14-06 / M14-07 / M14-08） |
|---|---|---|
| 面对谁 | 供应商 | 患者 |
| 主要风险 | 账实不符、采购舞弊 | 发错药、发错人 |
| 控制手段 | 三级审批 + GSP 四必查 + 双人盘点 | 药师审核 + 双人复核 + 扫码核对 |
| 时间粒度 | 按批次、按订单 | 按处方、按人次 |
| 失败后果 | 资金损失 | **患者伤害** |
| 法规依据 | GSP、药品管理法 | 药事管理规定、处方审核规范 |

**为什么采购、出库、盘点要拆成三个子模块？**

| 子模块 | 核心问题 | 特有复杂度 |
|---|---|---|
| M14-03 采购与入库 | 买得对不对、验得严不严 | 供应商资质 7 项校验、GSP 四必查、冷链温度、拒收处理、税额倒算 |
| M14-04 出库与调拨 | 移得对不对、去向清不清 | 一次业务两条流水（调拨 Saga）、报损五要素、双人监销 |
| M14-05 盘点与库存调整 | 差多少、怎么改 | 范围冻结、差异分级审批、循环盘点、盘盈也要审 |

三者都是「改变库存」，但**触发原因、审批链、失败处理完全不同**。合在一起会导致状态机膨胀到 20 多个状态。

### 2.4 拆分主线三：门诊与住院必须分开

| 维度 | 门诊（M14-07） | 住院（M14-08） |
|---|---|---|
| 作业模式 | **人找药** | **药找人** |
| 触发 | 患者到窗口 | 「病区 × 时段」批量 |
| 频次来源 | 一张处方一次 | 医嘱频次展开成执行点 |
| 归并方式 | 不归并 | 按时段归并（早/中/下午/晚） |
| 特有环节 | 窗口叫号、用药交代、代取人登记 | 摆药、药车、药筐、单剂量分包、护士签收 |
| 退药去向 | M16 退现金 | 冲减住院费用账（M16-03） |
| 数量级 | 350 张/日 | 4 病区 × 4 时段 |

**如果合并会怎样？** 每个函数都要写 `if 门诊 then ... else ...`，且两套流程的权限、状态、退药路径都被搅在一起。分开后 M14-07 的 9 态状态机与 M14-08 的 10 态状态机各自清晰。

**住院的「医嘱 → 摆药」四步转换**（这是 M14-08 不可省的复杂度）：

```
医嘱：「左氧氟沙星滴眼液 每日4次 连用7天」
   │
   ├─① 频次展开：28 个执行点
   │
   ├─② 按时段归并：每时段 1 次 × 4 时段/天
   │
   ├─③ 按病区汇总：4 病区 × 4 时段 = 16 张摆药单
   │
   └─④ 按批次拆解（FEFO）：每行取 1~2 个批次
```

为什么要按时段而不是按天？护士按班次给药。一次发 24 小时的药，等于把分药工作从药房推到了病区——病区没有按人分装的设施。

### 2.5 拆分主线四：审核是药师的独立职责

**法规依据：**《医疗机构处方审核规范》（国卫办医发〔2018〕14 号）第十二条——**药师是处方审核的第一责任人，所有处方须审核通过后方可调配**。

这不是流程建议，是硬性要求。M07 在设计时就假设了「审核通过后才收费」：

- M07-05 提供三个独立回调：`on-reviewed` / `on-returned` / `on-dispensed`
- M07-05 发布 `m07.rx.reviewed` 事件，M16 与 M14 都订阅

**为什么审核不能放进 M14-07 发药？**

| 维度 | 审核（M14-06） | 发药（M14-07） |
|---|---|---|
| 执行人 | 药师（有处方审核权） | 药师复核 + 药士调配 |
| 输入 | 处方内容 + 患者信息 + 诊断 | 已审核通过的处方 + 实物 |
| 输出 | 通过 / 有条件通过 / 退回 / 拒审 | 发药 / 退药 |
| 工作方式 | 知识判断，30 秒~3 分钟 | 物理操作，1~3 分钟 |
| 失败后果 | 用药不安全 | 拿错药 |

两者的**输入输出完全不同**，合并会让 M14-07 既要做规则引擎又要做实物管理。

**审核退回是终态而非回到待审**（重要设计）：医生修改后的处方是**新版本 V2**，若回 PENDING，台账看不到「退回了几次」、分不清两次审核的药师。M14-06 让退回即终结，新版本生成新任务，台账形成链条：

```
YS2026102200001  V1  RETURNED（药师甲）
YS2026102200017  V2  PASSED  （药师乙）
```

### 2.6 拆分主线五：特殊药品独立成子模块

用户明确要求 M14-09 独立。理由是充分的：

| 特殊点 | 普通药品 | 特殊管理药品 |
|---|---|---|
| 数量精度 | 按盒/支 | **按最小单位逐支**（芬太尼 2ml 用 1.5ml，剩 0.5ml 必须销毁） |
| 操作人数 | 1 人 | **必须 2 人同时在场**（双人双签） |
| 用完还要管 | 不管 | **空安瓿必须回收、残液必须销毁** |
| 失窃处理 | 报主管 | **24 小时内报药监 + 公安** |
| 台账 | 普通流水 | **专册台账（保存 5 年）** |

六类特殊管理药品：

| 类别 | 判定字段 | 双签 | 专柜 | 空瓿 | 限量 |
|---|---|---|---|---|---|
| 麻醉药品 | `is_narcotic` | ✅ | ✅ | ✅ | ✅ |
| 一类精神药品 | `is_psychotropic` + `PSYCHOTROPIC_1` | ✅ | ✅ | ✅ | ✅ |
| 二类精神药品 | `PSYCHOTROPIC_2` | ✅ | ✅ | ✅ | ✅ |
| 毒性药品 | `is_toxic` | ✅ | ✅ | ✅ | ✅ |
| 放射性药品 | `is_radioactive` | ✅ | ✅ | ✅ | ✅ |
| 高警示药品 | `is_high_risk` | ❌ | ❌ | ❌ | ✅ |

**判定优先级（命中即停）：** 放射 → 麻醉 → 一类精神 → 二类精神 → 毒性 → 高警示 → 普通。

放射性先判是因为放射性药品可能同时是麻精药，但管理以**放射防护**为准。

**为什么高警示药品不双签？**

氯化钾这类常用药如果按麻精管理，每次领取要两人到场，病房抢救时根本来不及。高警示的管理重点是**给药环节的标识与双核对**（M08 护理站负责），不是领用环节的双签。

### 2.7 拆分主线六：统计必须独立

M14-10 是唯一只读子模块。独立理由见 [其详细设计 §1.2](M14_药房药库管理_10_药事统计与报表_详细设计.md)：

1. 指标口径必须唯一（「抗菌药物使用率」至少有三种算法）
2. 政策会变但历史数据不能变（用指标版本号）
3. 计算量大不能实时（库存周转要扫全年 87 万条流水）
4. 输出格式由外部定义（药监季报有固定行列）

### 3.2 库存三层概念

```
仓库（Warehouse）
  │  8 类：中心药库/门诊药房/住院药房/急诊药房/手术室药房/
  │        病区药柜/待检区/虚拟库
  │  独立性：每个仓库独立盘点、独立核算
  │
  ├── 库位（Location）
  │     │  9 类存储类型：常温区/阴凉区/冷藏区/麻精柜/毒性柜/
  │     │               高警示专区/待检区/退货区/不合格品区
  │     │  约束：冷链药必须入冷藏/阴凉；麻精必须入专柜
  │     │
  │     └── 货架（Shelf）
  │           JSONB shelf_codes 数组，如 ["A-01-03","A-01-04"]
  │
  └── 批次（Batch） ★ 库存的最小单元
        唯一四元组：(warehouse_id, drug_id, batch_no, expiry_date)
        ├── qty_on_hand   在手数量（含过期、含锁定）
        ├── qty_locked    预占数量（分段分配时锁定）
        └── qty_available 可用数量 = on_hand − locked（生成列）
```

**为什么过期的批次仍计入 `qty_on_hand`？**

因为物理上它还在药架上，盘点能数到。如果过期就减掉，盘点时会出现「账上没有、柜子里有」的差异。过期货通过 `status = 'EXPIRED'` 排除在可用范围外。

### 3.3 批次与效期模型

**FEFO（先过期先出）是默认策略：**

```sql
SELECT * FROM m14_stock_batch
WHERE warehouse_id = :wh AND drug_id = :drug
  AND qty_available > 0
  AND status IN ('NORMAL', 'NEAR_EXPIRY')
  AND expiry_date > CURRENT_DATE
ORDER BY expiry_date ASC
LIMIT :n
```

**并发下用 `FOR UPDATE SKIP LOCKED`：**

5 个窗口同时发同一药品，普通 `FOR UPDATE` 会串行排队（3 秒 → 12 秒）。`SKIP LOCKED` 让后到的窗口跳到下一批次——并发下 FEFO 退化为近似，但**绝不会发出过期药**。

**效期四档：**

| 档位 | 剩余天数 | 处理 |
|---|---|---|
| `NORMAL` | > 90 天 | 正常发放 |
| `NEAR_EXPIRY` | 30~90 天 | 优先发出，预警 |
| `WARNING` | 0~30 天 | 近效期处理（退厂/调拨/促销） |
| `EXPIRED` | ≤ 0 天 | 锁定不可发，走报损 |

**`WARNING` 不落库**，是计算属性（`expiry_date <= TODAY + warning_days`）。原因：`WARNING` 与 `HOLD`、`RECALLED` 交叉，落库会导致状态机组合爆炸（7 态 × 4 档 = 28 种组合）。

**按药品类型差异化预警天数**（来自 M01-03 `mdm_drug_stock_policy`）：

| 类型 | 预警（天） | 警告（天） |
|---|---|---|
| 普通药品 | 90 | 30 |
| 冷链药品 | 120 | 45 |
| 麻精药品 | 180 | 60 |
| 高值药品 | 120 | 45 |
| 拆零药品 | 60 | 20 |

### 3.4 拆零模型

**拆零是「一次减、一次加」，不是「减少一点」。**

错误的做法：

```
1 盒 10 支的滴眼液，发 3 支
→ qty_on_hand = 1 - 0.3 = 0.7 盒   ❌ 0.7 盒是什么？
```

正确的做法（一次业务三条流水）：

```
① SPLIT_OUT  −1 盒  （原批次减 1 盒）
② SPLIT_IN   +10 支 （新建拆零批次加 10 支）
③ DISPENSE_OUT −3 支（拆零批次减 3 支）

净变化：盒数 −1，支数 +7
```

**拆零批次的新批号 = 原批号 + `-S`**（如 `240815-S`），`package_unit` 换成 `min_unit`，`conversion_ratio = 1`。这样药监追溯时输入原批号 `240815` 能模糊匹配到 `240815-S`。

**禁拆四类：** 麻精药品、冷链药品、缓释控释制剂、无菌眼膏。

### 3.5 处方到发药的完整链路

```
① 医生开方
   M07-05 → 处方 SIGNED
   发布事件 m07.rx.signed
        │
        ▼
② 药师审核（M14-06）
   ├── 自动审核引擎跑 26 条规则（P95 ≤ 50ms）
   ├── 人工审核给结论：PASSED / CONDITIONAL / RETURNED / REJECTED
   └── 结论回写 M07-05（POST on-reviewed）
        │
        ├─ RETURNED → 医生修改 → 新版本 V2 → 重新审核
        ├─ REJECTED → 处方作废
        │
        ▼ PASSED
③ 收费（M16）
   M07 处方成为待收费项 → 患者缴费 → 状态 PAID
        │
        ▼
④ 药房收方（M14-07）
   校验：审核通过 ✅ 已收费 ✅ 3 天有效期内 ✅
   建发药单，入叫号队列
        │
        ▼
⑤ 调配（药士）
   FEFO 分配批次 → 扫码核对 → 提交
        │
        ▼
⑥ 复核（药师，不能是同一人）
   8 项核对全勾 → PASS
        │
        ▼
⑦ 发药（药师/窗口）
   4 项用药交代全确认 → 扣库存 → 状态 DISPENSED
   回写 M07（POST on-dispensed）
        │
        ▼
⑧ 患者取药
   可退药（7 天内，非麻精，未开封）
```

**六道安全闸门（每道都有过人之处）：**

| 闸门 | 校验 | 失败后果若缺失 |
|---|---|---|
| 审核闸 | 处方必须 PASSED | 无适应证用药、配伍禁忌 |
| 收费闸 | 结算单必须 PAID | 漏收费 |
| 有效期闸 | 处方开具 ≤ 3 天 | 病情已变化 |
| 调配闸 | 调配人 ≠ 复核人 | 调配错误无人发现 |
| 核对闸 | 8 项核对全完成 | 拿错药 |
| 交代闸 | 4 项交代全确认 | 患者用错用法 |

### 3.6 特殊药品双锁模型

```
┌──────────────────────────────────────────────────────────┐
│                    麻精专柜（CAB-NR-01）                  │
│  ┌────────────────────────────────────────────────────┐  │
│  │  电子锁 A（由药师甲持钥）                          │  │
│  │  电子锁 B（由药师乙持钥）                          │  │
│  │  → 任一持钥人无法单独开启                          │  │
│  └────────────────────────────────────────────────────┘  │
│                                                          │
│  系统强制：                                              │
│  ① operator_id ≠ checker_id                             │
│  ② 两人都有专管资质                                     │
│  ③ 两次签字时间差 ≤ 15 分钟                             │
│  ④ 必须同一次登录会话内完成                             │
│  ⑤ 双方都要勾选「实物核对已完成」                        │
└──────────────────────────────────────────────────────────┘
```

**为什么限制 15 分钟？**

最常见的违规做法是「一人操作、另一人下班前补签」。通过限制时间差 + 要求同会话 + 超过则标 `is_late_check` 进入季度检查清单，让这种做法既麻烦又留痕。

**空安瓿守恒等式：**

```
发放数量 = 回收空瓿数量 + 在用数量 + 销毁数量
```

| 状态 | 含义 | 期限 |
|---|---|---|
| `PENDING` | 已发放待回收 | 24 小时内 |
| `BACK` | 已全部回收 | — |
| `PARTIAL` | 部分回收 | 需说明 |
| `MISSING` | 超期未回收 | 触发告警 |
| `EXPLAINED` | 已说明原因 | 需药房主任签字，原因 ≥ 10 字 |

### 3.7 退药模型

**退药 = 发药倒着走 + 一道质量判定。**

```
退款金额 = 实付净额（扣优惠后），不是项目原价
```

例：某检查 800 元打八折实收 640 元，患者要求退这项 —— 退 **640**，不是 800。

**退药时限七种场景：**

| 场景 | 时限 | 说明 |
|---|---|---|
| 常规 | 7 天 | 未开封 |
| 质量问题 | 无时限 | 需药师判定 |
| 医生开错 | 3 天 | 需医生确认 |
| 麻精药品 | 不退 | 除质量问题 |
| 冷链药品 | 2 小时 | 离柜后温控失效 |
| 视光产品 | 15 天 | 见 M16-04 |
| 人工调整 | 30 天 | 需审批 |

**四种判定结果：** `REUSABLE`（入原批次）/ `UNUSABLE` / `PARTIAL` / `REFUSE`。

**退回药品必须入原批次**，不能新建批次。否则同批号出现两条记录、库存虚增、药监追溯断链。

**退药不回改发药记录。** `DISPENSED` 后发药明细与批次由只读触发器保护，退药**新建**关联记录。这样「当时到底发了多少」永远说得清。

### 3.8 盘点差异模型

**盘点是唯一允许「把账上数量改成柜子里数量」的地方。**

其他所有改数量动作都有单据解释（采购单、出库单、发药单），只有盘点没有——所以必须有最严的约束：

```
差异金额 = |实盘数量 − 账面数量| × 成本价
```

用**成本价**不用零售价：丢 100 元零售价的药，损失是 60 元成本。

**三色差异：**

| 类型 | 条件 | 流水 |
|---|---|---|
| `MATCH` | 差异 ≤ 0.0001 | 无 |
| `PROFIT` | 实盘 > 账面 | `STOCKTAKE_IN` |
| `LOSS` | 实盘 < 账面 | `STOCKTAKE_OUT` |

**差异分级（三维判定，取最高级）：**

1. 金额：≤500 `SMALL` / ≤5000 `MEDIUM` / ≤50000 `LARGE` / >50000 `HUGE`
2. 品类提级：麻精毒放 +2 级，高值/冷链 +1 级
3. 差异率 >5% 再提一级

**审批矩阵：** SMALL→药房组长 48h / MEDIUM→药械科主任 48h / LARGE→主任+财务 72h / HUGE→主任+财务+院长 72h。质量相关（冷链/麻精）**强制并联质量负责人会签**。

**盘盈也必须审批。** 盘盈最常见的真实原因是「出库没记录」（药发了系统没扣），账实相符是假象。

### 4.2 三条数据铁律

**铁律一：库存数量只有一个入口**

任何表任何模块想让 `m14_stock_batch.qty_on_hand` 变化，必须调 `POST /internal/v1/m14/stock/apply`。该接口：
- 校验幂等键（`m14_stock_txn.idem_key` 部分唯一）
- 条件原子更新（`WHERE qty >= n AND version = v`）
- 同时写 `m14_stock_txn` 流水

**铁律二：六张表只增不改**

| 表 | 保护方式 |
|---|---|
| `m14_stock_txn` 库存流水 | 触发器 `trg_m14_stock_txn_immutable` 禁 DELETE 与关键字段 UPDATE |
| `m14_stock_snapshot` 库存快照 | 触发器禁 UPDATE/DELETE |
| `m14_special_record` 特殊药品台账 | 触发器 `fn_m14_special_record_readonly()` 抛异常 |
| `m14_rx_review_log` 审核日志 | 触发器 `fn_m14_rx_review_log_readonly()` |
| `m14_issue_log` 出库日志 | 触发器 `fn_m14_issue_log_readonly()` |
| `m14_stocktake_log` 盘点日志 | 触发器 `fn_m14_stocktake_log_readonly()` |

**铁律三：金额行级先舍入**

```
line_amount = ROUND(unit_price × quantity × eye_multiplier, 2)
总金额 = Σ line_amount
```

不是 `ROUND(Σ(price × qty), 2)`。原因：明细 30 行按比例分摊优惠时，先累加再舍入会差几毛钱，退费按行退永远对不上。

### 4.4 分区策略

| 表 | 分区键 | 预建 | 保留 | 理由 |
|---|---|---|---|---|
| `m14_stock_txn` | `created_at` 月度 | 36 月 | 永久（归档） | 年 87.6 万条，全表扫描慢 |
| `m14_stock_snapshot` | `snapshot_date` 月度 | 36 月 | 5 年 | 年 124 万条 |
| `m14_split_record` | `created_at` 月度 | 36 月 | 3 年 | 年 14.6 万条 |
| `m14_issue_log` | `started_at` 月度 | 36 月 | 热 180 天 | 年 2.9 万条 |
| `m14_rx_review_log` | `created_at` 月度 | 36 月 | 3 年 | 年 82.8 万条 |
| `m14_stocktake_log` | `created_at` 月度 | 36 月 | 3 年 | 年 1 万条 |
| `m14_special_record` | `seq_date` 月度 | 60 月 | 5 年 | 年 800 条但保留最久（GSP） |
| `m14_stat_daily` | `stat_date` 年度 | 5 年 | 5 年 | 年 21.9 万条 |

**分区与唯一索引的冲突（重要取舍）：**

PostgreSQL 要求分区表的唯一索引**必须包含分区键**。若 `m14_stock_txn` 的幂等键 `idem_key` 加唯一索引，加上分区键后就退化为「每月唯一」，跨月重复提交不会被拦。

**解法：** 应用层写幂等键时拼接月份戳：

```python
month_key = occurred_at.strftime("%Y%m")
idem_key = "%s:%s" % (month_key, raw_key)
```

这样「每月内唯一」等价于「全局唯一」。

**`m14_stock_batch` 明确不分区：** 稳态 3,400 行，分区毫无意义。同理 `m14_stocktake_item`（年 4.3 万）也不分区。

                                              │

                                              │
                                              ▼
                                         M07 状态 DISPENSED
```

**退费联动（M16-08 ← M14）：**

```
M16-08 退费单创建
    │
    ├──► GET /internal/v1/m14/dispense/returnable/{rx_no}
    │    查可退明细（已发数量、已退数量、判定结论）
    │

    │         │
    │         ▼
    │    M14-07 生成退药任务，药师判定后入库原批次
    │

## 8. 全局业务规则

### 8.1 库存六铁律

| 编号 | 规则 |
|---|---|
| INV-01 | 库存数量只能通过 `POST /internal/v1/m14/stock/apply` 改变 |
| INV-02 | 每次数量变化必须写一条 `m14_stock_txn`，只增不改 |
| INV-03 | 并发扣减必须用条件原子更新（`WHERE qty >= n AND version = v`） |
| INV-04 | 过期批次计入在手数，但排除在可用数外 |
| INV-05 | 退回药品必须入原批次，不得新建批次 |
| INV-06 | 负库存默认禁止（`ALLOW_NEGATIVE=false`） |

### 8.2 批次与效期五铁律

| 编号 | 规则 |
|---|---|
| BAT-01 | 默认 FEFO（先过期先出），除非显式指定批次 |
| BAT-02 | 发放时剩余效期必须 > 0 天 |
| BAT-03 | 拆零批次批号 = 原批号 + `-S` |
| BAT-04 | `WARNING` 级效期是计算属性，不落库 |
| BAT-05 | 召回批次立即锁定，任何环节不可发放 |

### 8.3 处方审核五铁律

| 编号 | 规则 |
|---|---|
| RX-01 | 所有处方必须经药师审核通过才能调配（法规） |
| RX-02 | 自动审核结果的 `BLOCK` 级问题不可被人工确认绕过 |
| RX-03 | `BLOCK` 级规则不可配置关闭（数据库约束） |
| RX-04 | 「通过」结论也必须填审核意见（≥10 字） |
| RX-05 | 审核人 ≠ 开方医生 |

### 8.4 发药七铁律

| 编号 | 规则 |

| DSP-01 | 处方必须审核通过且已收费才能收方 |
| DSP-02 | 处方开具超过 3 天不可发药 |
| DSP-03 | **调配人 ≠ 复核人**（数据库硬约束） |

## 10. 异常与降级策略

### 10.1 降级原则

**总原则：药品安全不能降级，管理便利可以降级。**

| 场景 | 是否降级 | 理由 |
|---|---|---|
| M07 处方接口超时 | ✅ 用本地快照 | 已收方，不能用旧数据重发 |
| M14-02 分配超时 | ✅ 手工选批次 | 但必须校验效期 |
| M01 药品主数据超时 | ❌ 阻断 | 没有药品分类无法判断是否特殊药品 |
| M14-06 审核不可用 | ❌ 阻断 | 法规要求必须先审核 |
| M16 收费状态超时 | ❌ 阻断 | 未收费不可发药 |
| M14-09 专柜服务不可用 | ❌ 阻断 | 麻精不可绕过双签 |
| 库存扣减失败 | ✅ 补偿队列 | 药已交给患者，不能收回 |
| M03-05 消息失败 | ✅ 异步重试 | 不影响主流程 |

### 10.2 关键降级实现

**库存扣减失败进补偿队列（不阻断发药）：**

药已经交到患者手上，不能因为库存服务超时就拒绝。做法：

```
① 发药单置 DISPENSED（患者拿到药）
② 库存扣减失败 → 写 m14_daily_transaction 补偿任务
③ Celery 每 2 分钟重试，指数退避
④ 10 次失败 → 标记 COMPENSATION_FAILED → 人工处理 + 告警
⑤ 每日 03:00 一致性检查：发药笔数 vs 库存流水笔数
```

**批次分配超时降级手工选批：**

```
① 调 M14-02 allocation/allocate，超时 5 秒
② 超时则调 M14-01 stock/batches-for-dispense
③ 药师手工选批次
④ 系统仍然校验：批次未过期、数量充足
⑤ 标记 degraded=True 记录
```

### 10.3 异常分类

| 类型 | 处理 |
|---|---|
| 参数异常 | 返回对应错误码 4xx |
| 业务冲突 | 返回对应错误码 409 |
| 依赖不可用 | 按上表降级或阻断 |
| 数据不一致 | 阻断 + 告警 + 人工介入 |
| 系统异常 | 500 + 详细日志 |

| 库存对账差异数 | > 0 | ERROR |

## 附录 A：术语表

| 术语 | 说明 |
|---|---|
| **GSP** | 药品经营质量管理规范 |
| **FEFO** | First Expired First Out，先过期先出 |
| **FIFO** | First In First Out，先进先出 |
| **批次** | 同一次生产、同一批号、同一效期的药品集合 |
| **拆零** | 将整包装拆分成最小销售单位 |
| **摆药** | 住院药房按病区按时段集中调配 |
| **单剂量分包** | 将一次口服剂量分装成独立包装 |
| **双人双签** | 特殊药品操作需两名药师同时在场并各自签字 |
| **空安瓿回收** | 麻精注射剂使用后回收空瓶并核销 |
| **印鉴卡** | 麻醉药品购用印鉴卡，医疗机构采购麻精的凭证 |
| **调剂四环节** | 审核、调配、核对、发药 |
| **DDD** | 限定日剂量 |
| **AUD** | 抗菌药物使用强度 = DDDs / 患者人天数 × 100 |
| **基药** | 国家基本药物目录内药品 |
| **药占比** | 药品收入 / 医疗总收入 |
| **高警示药品** | 使用不当易造成严重伤害的药品 |
| **近效期** | 剩余效期进入预警区间的药品 |
| **盘点** | 清点实物并与账面核对 |
| **循环盘点** | 按计划分批盘点不同药品，保证每季覆盖一次 |
| **盘点冻结** | 盘点期间禁止范围内药品出入库 |
| **拒收** | 验收不合格退回供应商 |
| **让步接收** | 轻微不合格但经审批接收 |
| **在途库存** | 调拨已发出但未签收的药品 |
| **报损** | 药品因过期/破损/召回而销毁 |
| **监销人** | 见证销毁过程的第三人 |
| **补偿队列** | 主流程失败后异步重试的机制 |
| **幂等键** | 保证同一请求重复提交只生效一次 |
| **FEFO 降级** | 并发冲突时跳过锁定批次取下一批次 |
