### 1.1 为什么本子模块不建黑名单表

黑名单与退订的唯一权威在 **M03-05 消息中心**（`mpi_message_blacklist`）。若本子模块再建一张 `m19_care_blacklist`，会出现两个真相：

- 患者在门诊端回复「TD」退订，M03-05 更新了自己的黑名单，本子模块的表不变，第二天照发 → 合规事故；
- 本子模块运营手工拉黑，M03-05 不知道，随访短信照发 → 同样是事故。

因此本子模块**只存判定结果快照**（`m19_care_blacklist_snapshot`），不存名单本身。快照的作用只有两个：一是闸门一调用失败时用于复盘「当时到底查到了什么」，二是合规检查时证明「我们在发送前确实查过」。

### 1.2 为什么触达记录与任务要分两张表

| 维度 | `m19_care_task`（任务） | `m19_care_touch`（触达） |
| --- | --- | --- |
| 语义 | 「我们**打算**关怀这个患者」 | 「我们**确实**对外发了（或尝试发了）一条消息」 |
| 一条任务对应几条触达 | 0 条（被闸门拦下）或 1 条 | 1 条，且**不可修改** |
| 可否改状态 | 可以（PENDING→SENDING→DELIVERED） | 不可以，只增不改 |
| 失败重试 | 任务可以再调度一次，产生**新的**触达行 | 每一行是一个不可变的历史事实 |

如果合成一张表，「被闸门拦下的任务」和「发了但失败的触达」就会混在一张表里，报表上「未触达数」永远对不上。**任务回答「该做的做了没有」，触达回答「实际发生了什么」，两者必须分开。**

### 1.3 建表顺序

| 批次 | 表 | 依赖 |
| --- | --- | --- |
| 第 1 批 | `m19_care_trial_rule`、`m19_care_rule` | 无 |
| 第 2 批 | `m19_care_plan` | `m19_care_rule` |
| 第 3 批 | `m19_care_task`、`m19_care_recall_list` | `m19_care_plan` |
| 第 4 批 | `m19_care_touch`、`m19_care_recall_item`、`m19_care_blacklist_snapshot` | `m19_care_task`、`m19_care_recall_list` |
| 第 5 批 | `m19_care_effect_daily`、`m19_care_oper_log` | 全部 |

### 4.2 表：`m19_care_rule`（关怀规则）

**用途：** 定义「什么时候、对谁、发什么」的关怀触发规则。规则是关怀的配置面，一条规则可生成多期关怀计划。规则本身不承载业务数据，只承载触发条件与话术绑定。

**写入方：** 运营管理员（P02 关怀规则配置页） **只读方：** APScheduler 调度器、计划生成服务、M19-08 运营分析

| id | BIGINT | N | IDENTITY | 主键 |

--   防的错误：计划被置为 COMPLETED 但没有 finish_at，
--   效果报表按「完成时刻 - 开始时刻」算耗时全部为空。
ALTER TABLE m19_care_plan

    CHECK (status <> 'COMPLETED' OR finish_at IS NOT NULL);

-- 组合约束 2：已取消必须填原因
--   防的错误：运营批量取消 5000 人的召回计划，事后查不出为什么取消。
ALTER TABLE m19_care_plan
    ADD CONSTRAINT ck_m19_care_plan_cancel
    CHECK (status <> 'CANCELLED' OR length(btrim(cancel_reason)) > 0);

-- 组合约束 3：排除数与覆盖数不能同时为 0 且状态已执行
--   防的错误：计划显示 RUNNING 但 member_count = 0，

ALTER TABLE m19_care_plan
    ADD CONSTRAINT ck_m19_care_plan_member
    CHECK (status IN ('DRAFT', 'CANCELLED') OR (member_count + exclude_count) > 0);

-- 组合约束 4：实际触达数不得超过覆盖数
--   防的错误：重试逻辑把同一患者发了 3 次，actual_touch_count 超过 member_count，
--   效果报表的触达率出现 300%。

    ADD CONSTRAINT ck_m19_care_plan_touch_ratio
    CHECK (actual_touch_count <= member_count * 3);

**设计说明**

- `uk_m19_care_plan_rule_date` 是**防重复生成的核心**：APScheduler 每 5 分钟扫一次规则，若某次执行超时导致两次扫描都触发了生成，唯一键会让第二次插入失败并回滚，而不是产生两期计划把患者打扰两遍。
- `member_count * 3` 而不是更宽的上限：任务最多重试 3 次（与 M03-05 的消息重试次数一致），所以实际触达条数不可能超过覆盖数的 3 倍。写成乘法而不是常量，是因为计划规模是变量。
- `exclude_reason_json` 存排除原因分布，让运营在**生成阶段**就能看到「这次有多少人因为退订被排除了」，而不是等发完了才发现触达率只有 40%。

### 4.4 表：`m19_care_task`

**中文名：** 关怀任务表（关怀触发的任务实例，一行代表「给某个患者发某一条关怀」）

**表说明：** 关怀任务由关怀计划展开生成，或由内部契约 P-09 单点触发。它是**三道闸门判定的落点**：每一条任务都要么被发出（`DELIVERED`）、要么被闸门拦下（`SUPPRESSED`）、要么发送失败（`FAILED`）。把 `SUPPRESSED` 单独列为状态并强制填 `suppress_reason`，是为了让运营在报表上能一眼分清「没发」和「发失败」——这两件事的处置方式完全相反：前者要查规则配置，后者要查通道。

**只读方：** M19-03 任务列表/触达记录/效果追踪页面、M19-08 运营分析、M22-02（经 `m19.care.delivered` 事件）

##### 组合约束（CHECK 之外的语义约束，逐条单列）

组合约束 1：**已抑制必须有抑制闸门与抑制原因**。

```sql
ALTER TABLE m19_care_task
    ADD CONSTRAINT ck_m19_care_task_suppressed_reason
    CHECK (status <> 'SUPPRESSED' OR (suppress_gate IS NOT NULL AND suppress_reason IS NOT NULL));
```

防的真实错误：任务被闸门拦下后只把状态改成 `SUPPRESSED` 而没有写原因，运营看到「已抑制 320 条」却说不清是哪道闸门拦的、依据是什么。合规检查时被问到「这个患者为什么没收到术后关怀」，答不出来就是举证失败。

组合约束 2：**抑制原因与抑制闸门必须成对出现且互相匹配**。

```sql
ALTER TABLE m19_care_task
    ADD CONSTRAINT ck_m19_care_task_suppress_pair
    CHECK (
        (suppress_gate = 'BLACKLIST' AND suppress_reason = ANY (ARRAY['UNSUBSCRIBED', 'BLACKLISTED']))
        OR (suppress_gate = 'QUIET_HOURS' AND suppress_reason = 'QUIET_HOURS_CANCEL')
        OR (suppress_gate = 'FREQUENCY' AND suppress_reason = 'FREQUENCY_LIMIT')
        OR (suppress_gate = 'TEMPLATE_PRIVACY' AND suppress_reason = 'PRIVACY_VIOLATION')
        OR (suppress_gate = 'CONFLICT_WITH_FOLLOWUP' AND suppress_reason = 'FOLLOWUP_CONFLICT')
        OR (suppress_gate IS NULL AND suppress_reason = ANY (ARRAY['NO_VALID_CONTACT', 'RULE_DISABLED', 'DEADLINE_EXCEEDED', 'MSG_SERVICE_DOWN']))
        OR (suppress_gate IS NULL AND suppress_reason IS NULL)
    );
```

防的真实错误：开发图省事一律写 `suppress_reason = 'OTHER'`，或把「黑名单」的闸门配上「频次超限」的原因。判别法：把 `suppress_gate` 改成另一个合法值而 `suppress_reason` 不动，若仍能通过，说明缺这条约束。

组合约束 3：**非抑制状态不得残留抑制字段**。

```sql
ALTER TABLE m19_care_task
    ADD CONSTRAINT ck_m19_care_task_suppress_clean
    CHECK (status = 'SUPPRESSED' OR (suppress_gate IS NULL AND suppress_reason IS NULL));
```

防的真实错误：任务先被抑制、后来运营手动重发成功，状态改成 `DELIVERED` 但 `suppress_reason` 没清理，导致报表同时把这条计入「已抑制」和「已送达」，抑制率与送达率之和超过 100%。

组合约束 4：**已送达必须有送达时刻与消息任务号**。

```sql
ALTER TABLE m19_care_task
    ADD CONSTRAINT ck_m19_care_task_delivered
    CHECK (status <> 'DELIVERED' OR (delivered_at IS NOT NULL AND msg_task_no IS NOT NULL));
```

防的真实错误：只靠 M03-05 的异步回执改状态，回执丢了也把状态置成 `DELIVERED`，实际没送达；要求 `msg_task_no` 非空至少能保证有 M03-05 的受理记录可对账。

组合约束 5：**发送失败必须有失败原因**。

```sql
ALTER TABLE m19_care_task
    ADD CONSTRAINT ck_m19_care_task_failed
    CHECK (status <> 'FAILED' OR (fail_code IS NOT NULL AND fail_reason IS NOT NULL));
```

防的真实错误：通道返回非零响应但代码只 catch 后置 `FAILED`，不落失败码，运维无法按失败码聚类定位是模板变量超长、号码停机还是网关限流。

组合约束 6：**顺延只允许发生在未发送状态，且必须落下一次触达时刻**。

```sql
ALTER TABLE m19_care_task
    ADD CONSTRAINT ck_m19_care_task_defer
    CHECK (gate_quiet_result <> 'DEFER' OR (status = 'PENDING' AND defer_to_at IS NOT NULL AND defer_count = 1));
```

防的真实错误：判定为顺延但没写 `defer_to_at`，任务永远停在 `PENDING`；或任务已经 `DELIVERED` 了还把 `gate_quiet_result` 改成 `DEFER`，导致「顺延了多少条」的统计把已发送的也计入。

组合约束 7：**医疗必要标记与关怀类型一致**。

```sql
ALTER TABLE m19_care_task
    ADD CONSTRAINT ck_m19_care_task_medical
    CHECK (medical_necessary = FALSE OR care_type = 'POSTOP');
```

防的真实错误：运营为了让召回短信突破频次限制，把 `RECALL` 任务的 `medical_necessary` 改成 TRUE，绕过「24 小时非医疗必要最多 1 次」的红线。这条约束让「医疗必要」只能落在术后关怀上。

组合约束 8：**被闸门拦下就不可能有发送尝试与消息任务号**。

```sql
ALTER TABLE m19_care_task
    ADD CONSTRAINT ck_m19_care_task_suppressed_no_send
    CHECK (status <> 'SUPPRESSED' OR (msg_task_no IS NULL AND delivered_at IS NULL));
```

防的真实错误：先发给 M03-05 再补记一个 `SUPPRESSED`，形成「既发了又说没发」的双重口径；更坏的情况是这条记录被用于证明「我们遵守了退订」，属于伪造合规证据。

#### 4.4.4 模板变量白名单

`template_vars` 是本表唯一允许承载患者相关信息的自由字段，因此必须白名单化。**白名单之外一律拒绝**，校验发生在任务创建阶段（写入前）与发送前（二次校验），任一不通过则 `status = 'SUPPRESSED'`、`suppress_gate = 'TEMPLATE_PRIVACY'`、`suppress_reason = 'PRIVACY_VIOLATION'`。

**允许的键（白名单）：**

| 变量键 | 示例值 | 用途 | 为何允许 |
| --- | --- | --- | --- |
| `patient_name` | `张**` | 称谓 | 已脱敏，不含完整姓名 |
| `gender_title` | `先生` | 称谓 | 无临床含义 |
| `clinic_name` | `南石眼科医院` | 落款 | 无临床含义 |
| `dept_name` | `视光中心` | 落款 | 只到科室，不到诊断 |
| `staff_name` | `李医生` | 落款 | 无临床含义 |
| `care_date` | `2026-10-21` | 关怀日期 | 日期本身不隐私 |
| `booking_phone` | `0000-00000000` | 预约电话 | 院内公开号码 |
| `days_since_last_visit` | `90` | 召回文案 | 只体现「久未到店」，不含病种 |
| `birthday_month_day` | `10月21日` | 生日文案 | 不含出生年份，避免年龄推断 |
| `benefit_name` | `免费验光` | 权益文案 | 权益名称本身不指向疾病 |

**禁止的键（黑名单，出现即拒绝）：**

| 变量键 | 泄露内容 | 后果 |
| --- | --- | --- |
| `diagnosis` / `diagnosis_name` | 诊断名称 | 家属可据此判断病情 |
| `surgery_type` / `operation_name` | 手术方式 | 直接泄露做过手术 |
| `operated_eye` / `eye_side` | 术眼（左/右/双眼） | 直接泄露手术部位 |
| `vision_value` / `diopter` | 视力值、屈光度 | 属个人健康信息 |
| `postop_day` | 术后第几天 | 结合发送时间可反推手术日 |
| `doctor_advice` / `medication` | 医嘱、用药 | 属诊疗内容 |
| `cost_amount` / `order_amount` | 费用金额 | 属消费隐私 |
| `id_card` / `full_name` / `address` | 身份信息 | 超范围收集使用 |

白名单校验伪代码：

```python
ALLOWED_VAR_KEYS = frozenset({
    "patient_name", "gender_title", "clinic_name", "dept_name", "staff_name",
    "care_date", "booking_phone", "days_since_last_visit",
    "birthday_month_day", "benefit_name",
})

def assert_template_vars_allowed(template_vars: dict[str, str]) -> None:
    illegal = set(template_vars) - ALLOWED_VAR_KEYS
    if illegal:
        raise BizError("1903016", f"模板变量含非白名单键：{sorted(illegal)}")
    for key, value in template_vars.items():
        if not isinstance(value, str):
            raise BizError("1903016", f"模板变量值必须为字符串：{key}")
        if len(value) > 64:
            raise BizError("1903016", f"模板变量值超长：{key}")
```

**为什么「术后关怀」四个字本身也要处理：** 短信内容形如「XX 医院提醒您：您的术后关怀…」，接收方若是家属，未点开正文也已经知道患者做过手术。因此术后关怀类短信的**模板文案必须中性化**：标题统一写「复查提醒」，正文不出现「术后」「手术」「眼科手术」等词，只写「您在院期间的诊疗已进入复查阶段，建议于 X 月 X 日来院复查」。这一条在 M19-03 里落为**模板准入检查**：`care_type = 'POSTOP'` 的规则保存时，必须调用 M03-05 模板详情接口读取模板正文，正文中出现手术相关词则该规则不允许置为 `ENABLED`。

#### 4.4.6 设计说明

- **为什么 `SUPPRESSED` 必须是独立状态而不能并入 `CANCELLED`**：`CANCELLED` 是「人为决定不发」（规则停用、运营取消），`SUPPRESSED` 是「系统按合规规则拦下」。两者在合规举证里的含义完全相反——前者要说明人为决策依据，后者要说明触发的规则条款。合并会让「本月因退订未触达 1,240 人次」这个数字无法从库里算出来。
- **为什么 `gate_*` 三个字段要分别存判定结果而不是一个 `gate_result`**：三道闸门是依次执行的，第一道不过就不会执行第二道。分开存才能回答「有多少条走到了第二道闸门」这种漏斗分析问题；合成一个字段只能知道最终结果，丢掉了过程。
- **为什么 `template_var_hash` 要独立成列并加唯一约束的一部分**：同一患者同一模板，如果变量内容完全相同（例如连续两天都推同一条节日祝福，文案一字不差），本就属于重复打扰，应当由幂等键拦下。把变量哈希纳入幂等键，比单看 `biz_no` 更严格——因为运营可能给每次生成都分配新的 `biz_no`。
- **为什么 `contact_phone` 存明文快照**：患者改号或销号后，若只存 `patient_id`，事后无法举证「当时发到了哪个号码」。合规检查要的恰恰是「你发到哪个号码了」。该字段的查询权限单独控制（`m19:care:view_phone`），列表接口默认返回脱敏值。
- **为什么 `send_deadline_at` 必须有**：「顺延到次日 08:05」在生日关怀场景下是合理的，但在「术后 7 天复查提醒」场景下顺延到次日可能已经错过复查窗口。`send_deadline_at` 为空表示不设截止，一旦设置则超过即置 `SUPPRESSED` + `DEADLINE_EXCEEDED`，而不是继续发一条已经没有意义的消息。

#### 4.5.3 约束定义

##### 字段级 CHECK

```sql
ALTER TABLE m19_care_touch
    ADD CONSTRAINT ck_m19_care_touch_result
    CHECK (result = ANY (ARRAY['SENT', 'SUPPRESSED', 'FAILED'])),
    ADD CONSTRAINT ck_m19_care_touch_care_type
    CHECK (care_type = ANY (ARRAY['BIRTHDAY', 'RECALL', 'POSTOP', 'FOLLOWUP', 'ANNIVERSARY', 'HOLIDAY', 'OTHER'])),
    ADD CONSTRAINT ck_m19_care_touch_channel
    CHECK (channel = ANY (ARRAY['SMS', 'WECHAT', 'PHONE', 'INBOX', 'MAIL', 'PUSH'])),
    ADD CONSTRAINT ck_m19_care_touch_biz_type
    CHECK (biz_type = ANY (ARRAY['MEMBER', 'MARKETING', 'FOLLOWUP'])),
    ADD CONSTRAINT ck_m19_care_touch_attempt
    CHECK (attempt_no BETWEEN 1 AND 3),
    ADD CONSTRAINT ck_m19_care_touch_trigger_source
    CHECK (trigger_source = ANY (ARRAY['PLAN', 'CONTRACT', 'MANUAL'])),
    ADD CONSTRAINT ck_m19_care_touch_receipt
    CHECK (receipt_type IS NULL OR receipt_type = ANY (ARRAY['DELIVERED', 'READ', 'FAILED', 'CLICKED', 'REPLIED', 'UNSUBSCRIBED'])),
    ADD CONSTRAINT ck_m19_care_touch_cost

```

##### 组合约束

组合约束 1：**被抑制必须有闸门与原因，且不得有消息任务号**。

```sql
ALTER TABLE m19_care_touch
    ADD CONSTRAINT ck_m19_care_touch_suppressed
    CHECK (
        result <> 'SUPPRESSED'
        OR (suppress_gate IS NOT NULL AND suppress_reason IS NOT NULL AND msg_task_no IS NULL)
    );
```

防的真实错误：被拦下却仍然拿到一个 `msg_task_no`，说明实际已经提交给 M03-05 了——闸门形同虚设。「发出去之后再补一条抑制记录」是最隐蔽的合规事故：日志看起来很规范，实际患者已经收到了短信。

组合约束 2：**已发送必须有消息任务号与受理结论**。

```sql
ALTER TABLE m19_care_touch
    ADD CONSTRAINT ck_m19_care_touch_sent
    CHECK (result <> 'SENT' OR (msg_task_no IS NOT NULL AND msg_opinion IS NOT NULL));
```

防的真实错误：只记了「本地认为发出去了」而没有 M03-05 的受理凭证，通道方丢了消息时双方各执一词。

组合约束 3：**三道闸门的判定结果都必须有值，不允许 PENDING 落库**。

约束语义：闸门第 0 道与闸门一必须是终态；只有当上一道 `PASS` 时下一道才有值；只有当闸门二 `PASS` 时闸门三才有值。逐条实现如下：

```sql
ALTER TABLE m19_care_touch
    ADD CONSTRAINT ck_m19_care_touch_gate0
    CHECK (gate_member_result <> 'PASS' OR gate_blacklist_result IS NOT NULL),
    ADD CONSTRAINT ck_m19_care_touch_gate0_status
    CHECK ((gate_member_result = 'PASS' AND gate_member_status = ANY (ARRAY['ACTIVE', 'NON_MEMBER']))
           OR (gate_member_result = 'BLACKLIST' AND gate_member_status = 'CANCELLED')),
    ADD CONSTRAINT ck_m19_care_touch_gate1
    CHECK (gate_member_result = ANY (ARRAY['PASS', 'BLACKLIST'])),
    CHECK (gate_blacklist_result = ANY (ARRAY['PASS', 'BLOCK', 'FAIL_CLOSED'])),
    ADD CONSTRAINT ck_m19_care_touch_gate2
    CHECK (gate_blacklist_result <> 'PASS' OR gate_quiet_result = ANY (ARRAY['PASS', 'EXEMPT', 'DEFER'])),
    ADD CONSTRAINT ck_m19_care_touch_gate3
    CHECK (gate_quiet_result <> 'PASS' OR gate_freq_result = ANY (ARRAY['PASS', 'BLOCK'])),
    ADD CONSTRAINT ck_m19_care_touch_freq_pair
    CHECK ((gate_freq_result IS NULL AND gate_freq_used IS NULL)
           OR (gate_freq_result IS NOT NULL AND gate_freq_used IS NOT NULL));
```

防的真实错误：闸门判定结果用默认值 `PENDING` 落库，事后无法区分「这道闸门没跑」和「这道闸门跑了且通过了」。审计看到 `PENDING` 只能推断是程序异常，但要证明程序异常就得翻应用日志，而应用日志只保留 30 天。

组合约束 4：**退订回执必须与业务类型匹配**。

```sql
ALTER TABLE m19_care_touch
    ADD CONSTRAINT ck_m19_care_touch_unsub
    CHECK (receipt_type <> 'UNSUBSCRIBED' OR biz_type = ANY (ARRAY['MEMBER', 'MARKETING', 'FOLLOWUP']));
```

防的真实错误：把验证码、通知类消息的回执也标记成 `UNSUBSCRIBED`，进而错误地给患者打上退订标记，导致后续医疗随访也停了。M03-05 的规则是只有 `FOLLOWUP` / `MEMBER` / `MARKETING` / `SATISFACTION` 可退订，本表与之对齐。

#### 4.5.5 写回执的做法与理由

本表禁止 UPDATE，那么 M03-05 的异步回执（送达、点击、退订）如何记录？答案是**追加一行回执行**，而不是更新原行：

| 行类型 | `result` | `receipt_type` | `msg_task_no` | 说明 |
| --- | --- | --- | --- | --- |
| 发送行 | `SENT` | NULL | 有值 | 提交 M03-05 时的原始记录 |
| 送达回执行 | `SENT` | `DELIVERED` | 同上 | 同 `msg_task_no` 的第二行 |
| 点击回执行 | `SENT` | `CLICKED` | 同上 | 同 `msg_task_no` 的第三行 |
| 退订回执行 | `SENT` | `UNSUBSCRIBED` | 同上 | 触发 M03-05 退订登记 |

**为什么不改成 UPDATE：** 合规举证要的不是「这条消息现在什么状态」，而是「在什么时刻发生了什么」。回执可能在 72 小时后才到，若用 UPDATE，就丢失了「72 小时才送达」这个事实——而送达延迟本身就是通道质量的关键指标。追加行的代价是行数变多（实测送达回执到达率约 96%，点击回执约 8%，整体行数约为发送行数的 1.05 倍），对分区表来说可以接受。

**聚合查询的处理方式：** 需要「一条消息最终状态」时，按 `msg_task_no` 聚合取最新回执：

```sql
SELECT
    msg_task_no,
    max(receipt_at)                                                   AS last_receipt_at,
    (array_agg(receipt_type ORDER BY receipt_at DESC NULLS LAST))[1]  AS final_receipt
FROM m19_care_touch
WHERE created_at >= CURRENT_DATE - INTERVAL '30 days'
  AND receipt_type IS NOT NULL
GROUP BY msg_task_no;
```

#### 4.5.6 设计说明

- **为什么触达记录要和任务分两张表**：任务是「打算做什么」，一条任务最多 3 次重试，每次重试都可能被不同的闸门拦下；触达记录是「实际发生了什么」。合并成一张表的话，重试会覆盖首次的失败原因，合规举证时「第一次为什么失败」就查不到了。分开之后，任务表是当前状态（可 UPDATE），触达表是事件流水（不可 UPDATE）。
- **为什么保存 `gate_freq_limit`**：规则里的频次上限是可配置的，且可能随时间调整。如果只存「已用次数」而不存「当时的上限」，事后复核「当时判 BLOCK 是否合理」就没有依据——规则改了之后，用新规则去校验旧记录永远对不上。这与「历史报表不重算」是同一个原则。
- **为什么 `gate_seq` 要存成字符串轨迹**：排查时最常见的问题是「这条到底卡在哪道闸门」。有轨迹字段后，按轨迹模式做 `GROUP BY` 就能一眼看出「本周 68% 的抑制都停在第一道闸门」。用三个独立字段虽然信息等价，但做漏斗统计时要写三段条件，容易写错。
- **为什么 `phone_hash` 与 `phone_masked` 并存**：`phone_hash` 用于「同一手机号被多少个不同患者登记」与「同一号码一周内收到几条」的分析，这两个问题对骚扰治理很关键；但它不能用于展示。`phone_masked` 用于展示。两者都不含完整号码，完整号码只在 `m19_care_task.contact_phone` 里且有独立权限控制。
- **`cost_cent` 为什么按分存 INTEGER**：短信通道成本按条计价，单价在 0.03~0.05 元之间，用元存需要 `NUMERIC(14,2)`，量级小但精度够；按分存 INTEGER 在汇总求和时不会有任何舍入累积问题，且效果追踪的「单条触达成本」直接除即可。

防的真实错误：名单用 T+1 的日汇总数据生成，但 `data_as_of` 为空，运营以为看到的是实时数据，名单里已经到店的患者仍然收到「您很久没来了」的召回短信——这是最伤客诉的一类错误。

#### 4.6.6 设计说明

- **为什么存 `criteria_json` 快照而不是只存规则 ID**：召回条件会在运营侧频繁调整（今天 90 天、下月改 120 天）。若只存规则 ID，三个月后回看「这批 800 人为什么被选中」，只能看到当前规则，得到的结论是错的。快照 + 哈希让「同条件同一天」可去重（唯一键），同时保留了历史口径。
- **为什么 `exclude_flags` 是固定四类而不是自由文本**：失访、投诉、已退订、已故这四类是硬性排除条件，不允许运营自定义——自定义就会出现「运营为了凑量把已投诉患者拉回名单」的操作空间。写进 JSON 结构定义里并配 CHECK 校验，再在服务层做一次白名单过滤。
- **`data_quality` 取 `DAILY` 是常态**：本子模块的「到店」「消费」数据来自 M16 与 M10，均为 T+1 汇总口径，实时查询代价太高（一次召回名单计算涉及数十万行）。因此列表页必须显式展示「数据截止到 X 月 X 日」，避免运营误以为看到的是此刻状态。
- **`expire_at` 默认 30 天**：召回名单的时效性很强，一个月前的「久未到店」名单里可能已经有人来过。过期名单不允许再据此生成触达任务，必须重新生成。

#### 4.7.4 召回资格判定规则与 `score` 计算

**资格判定（按顺序执行，任一命中即 `EXCLUDED`）：**

| 序号 | 条件 | `exclude_flag` | 数据来源 |
| --- | --- | --- | --- |
| 1 | 患者标记为失访 | `LOST_CONTACT` | M03-01 患者标记 |
| 2 | 近 180 天内有投诉记录 | `COMPLAINT` | M03 投诉模块 |
| 3 | 已退订关怀类消息 | `UNSUBSCRIBED` | M03-05 黑名单（批量查询） |
| 4 | 已故 | `DECEASED` | M03-01 患者状态 |
| 5 | 最近 N 天内已被其他关怀触达 | `RECENT_TOUCHED` | `m19_care_touch` |
| 6 | 无有效手机号 | `NO_VALID_CONTACT` | M03-01 联系方式 |
| 7 | 名单过期（`expire_at < 今日`） | `EXPIRED_BY_LIST` | 本表所属主档 |

**注意第 3 条：这里查黑名单与闸门一的关系。** 名单生成阶段的黑名单为**批量预筛**，只用于提高名单质量（少生成必然被拦的任务），**不能替代闸门一**：从名单生成到实际触达之间可能间隔数天，患者可能在这期间退订。两道都要执行，这是「宁可重复校验，不可漏检」的取舍。

**`score` 计算模型：**

```text
score = 0.40 * norm_days + 0.30 * norm_amount + 0.20 * norm_visit_gap + 0.10 * norm_recent

其中：
    各分量均为 [0, 1] 区间的归一化值，归一到小数点后 6 位。

    norm_days       = min(days_since_last_visit / 365, 1.0)
                      越久没来越优先，365 天封顶

    norm_amount     = min(total_amount / 20000, 1.0)
                      累计消费越高越优先，2 万元封顶

    norm_visit_gap  = 1 - min(abs(days_since_last_visit - 90) / 180, 1.0)
                      越接近 90 天这个「召回黄金窗口」越优先

    norm_recent     = 0                     若最近 30 天内有触达
                    = 1                     若最近 30 天无触达

边界与舍入：
    - days_since_last_visit 为空（从未到店）时，norm_days = 1.0，norm_visit_gap = 0
    - total_amount 为 0 时 norm_amount = 0
    - score 保留 6 位小数，采用 ROUND_HALF_UP
失败条件：
    - 任一输入为 NULL 且不在上述空值规则内，则该患者不进入名单（记 exclude_flag）
```

**算例：**

| 患者 | 距上次到店 | 累计消费 | 30 天内触达 | 计算 | score |
| --- | --- | --- | --- | --- | --- |
| A | 95 天 | 8,600.00 | 无 | 0.40×0.260274 + 0.30×0.43 + 0.20×0.972222 + 0.10×1 | 0.518534 |
| B | 140 天 | 15,200.00 | 无 | 0.40×0.383562 + 0.30×0.76 + 0.20×0.722222 + 0.10×1 | 0.567903 |
| C | 400 天 | 2,100.00 | 有 | 0.40×1.0 + 0.30×0.105 + 0.20×0 + 0.10×0 | 0.431500 |
| D | 60 天 | 900.00 | 无 | 0.40×0.164384 + 0.30×0.045 + 0.20×0.833333 + 0.10×1 | 0.373087 |

患者 B 得分最高：既久未到店又消费高且落在召回窗口附近，客服优先回访他。患者 C 虽然 400 天没来，但消费低且最近刚被别的关怀打扰过，排在后面。

**与 M19-05/M19-06 的数据边界：**

| 数据 | 本子模块是否持有 | 权威来源 | 说明 |
| --- | --- | --- | --- |
| 会员等级、会员标签 | 否 | M03-03 / M19-06 | 本表只存筛选结果的 `member_id` |
| 风险流失分层 `risk_level` | 否 | M19-06 | M19-06 是「分层」，本子模块是「名单」，分层结果可作筛选条件输入 |
| 权益与优惠券 | 否 | M19-05 | 召回触达不带券，券的发放是 M19-05 的职责 |
| 到店与消费金额 | 否 | M10 / M16 | 本表冗余 `last_visit_date`、`total_amount` 作为快照 |
| 触达历史 | 是 | 本子模块 `m19_care_touch` | 唯一真相 |

**为什么 M19-06 的分层不直接当作名单用：** 分层回答「这个会员属于哪一类」，名单回答「这一批要联系谁、为什么是现在、按什么顺序」。分层是静态属性，名单是一次性行动，两者的生命周期与更新频率完全不同。把分层结果直接当名单，会出现「名单永远不过期」的问题——一个已经被反复触达 5 次的患者仍留在「高价值流失风险」分层里。

#### 4.7.6 设计说明

- **为什么 `total_amount` 存快照而不实时关联 M16**：M16 的成交数据会变（退款会冲减金额）。名单在生成那一刻记录当时看到的金额，用于解释「当时为什么把他排在第 3 位」。若实时关联，退款后回看名单会发现排序依据已经对不上了。
- **为什么 `observe_until` 固定 60 天**：召回转化观察期太短会把「一个月后才来」的有效召回判成无效，太长则名单永远关不掉。60 天覆盖了「收到召回短信 → 犹豫 → 下次需要配镜时想到你」的典型决策周期，也与本院验光复诊周期（半年到一年）不冲突。
- **`priority_rank` 与 `score` 并存**：`score` 是可解释的业务口径（客服能看懂「因为他 140 天没来且消费高」），`priority_rank` 是名单内的稳定序号（用于分批下发，第一批前 500 名）。前者便于复盘，后者便于分批执行，缺一不可。
- **`hit_reason` 存自然语言而 `hit_rule_codes` 存键名**：前者直接进客服话术脚本，后者用于统计「多少人是因金额门槛命中」。如果只存键名，客服看到的 `["no_visit_days"]` 需要翻译一次，现场效率会掉。

组合约束 1：**作用范围与维度字段必须匹配**。

```sql
ALTER TABLE m19_care_trial_rule
    ADD CONSTRAINT ck_m19_care_trial_rule_scope_dims
    CHECK (
        (scope_type = 'GLOBAL' AND channel IS NULL AND care_type IS NULL)
        OR (scope_type = 'CHANNEL' AND channel IS NOT NULL AND care_type IS NULL)
        OR (scope_type = 'CARE_TYPE' AND channel IS NULL AND care_type IS NOT NULL)
        OR (scope_type = 'CHANNEL_TYPE' AND channel IS NOT NULL AND care_type IS NOT NULL)
    );
```

防的真实错误：`scope_type = 'GLOBAL'` 却填了 `channel = 'SMS'`，判定时按全局读取会拿到一个渠道限定的规则，导致微信渠道也被按短信规则限频。判别法：把 `scope_type` 改成另一合法值、维度字段不动，若仍能通过就缺这条约束。

组合约束 2：**医疗必要频次上限不得低于非医疗必要上限**。

```sql
ALTER TABLE m19_care_trial_rule
    ADD CONSTRAINT ck_m19_care_trial_rule_freq_order
    CHECK (freq_limit_medical >= freq_limit_24h);
```

防的真实错误：配置出错把 `freq_limit_24h` 配成 3、`freq_limit_medical` 配成 1，结果是术后关怀反而比营销召回更容易被拦——医疗必要性被配置反了。

组合约束 3：**免打扰例外只能是术后关怀类型**。

```sql
ALTER TABLE m19_care_trial_rule
    ADD CONSTRAINT ck_m19_care_trial_rule_exempt
    CHECK (quiet_exempt_types <@ '["POSTOP"]'::jsonb);
```

防的真实错误：运营把 `RECALL`（召回）加进免打扰例外，于是晚上 22 点给患者发「您很久没来配镜了」——这是最典型的合规投诉场景。

组合约束 4：**放宽默认值必须有审批人**。

```sql
ALTER TABLE m19_care_trial_rule
    ADD CONSTRAINT ck_m19_care_trial_rule_approval
    CHECK (
        (quiet_enabled = TRUE AND freq_enabled = TRUE AND quiet_exempt_types = '["POSTOP"]'::jsonb
         AND freq_limit_24h = 1 AND freq_limit_medical = 2
         AND quiet_start = '21:00:00' AND quiet_end = '08:00:00')
        OR (approved_by IS NOT NULL AND approved_at IS NOT NULL)

```

防的真实错误：有人直接把 `freq_limit_24h` 从 1 改成 5 让召回跑得更快，没有留下任何审批痕迹。这条约束让任何偏离默认安全值的配置都必须有审批人落库。

组合约束 5：**启用状态必须有生效日期与生效区间校验**。

```sql
ALTER TABLE m19_care_trial_rule
    ADD CONSTRAINT ck_m19_care_trial_rule_enabled
    CHECK (status <> 'ENABLED' OR (effective_from IS NOT NULL AND (effective_to IS NULL OR effective_to >= CURRENT_DATE)));
```

防的真实错误：规则配了结束日期但没做状态联动，过期后仍处于 `ENABLED`，判定逻辑照旧读取它。

#### 4.8.6 设计说明

- **为什么默认值写进表级默认而不是代码常量**：默认值写进代码意味着「改默认值要发版」。更重要的原因是——合规检查要看的不是「现在配置是什么」，而是「每条触达发生时，规则是什么」。规则落库并带生效区间后，可以精确回答「10 月 15 日 22:13 那条短信为什么没有被免打扰拦下」，答案是「当天生效的 TR002 对 POSTOP 豁免」。
- **为什么 `defer_jitter_minutes` 要有随机抖动**：如果所有顺延任务都在 08:05 整点发送，通道侧看到的是同一秒几百条短信，容易触发网关频控，且患者端若同一小区多人收到会产生「群发」观感。30 分钟内的均匀抖动把这个峰摊平。
- **为什么 `quiet_start` / `quiet_end` 是 TIME 而不是 TIMESTAMP**：免打扰时段是每日周期性规则，与时区无关（院区固定东八区）。用 TIME 让「21:00~08:00 跨零点」这种区间无需特殊处理，判定逻辑见 4.8.4 下方的伪代码。
- **`TR001` 不可停用的实现方式**：`status` 可以改成 `DISABLED`，但服务层在读取规则时若发现所有规则都被停用，会回退到内置的硬编码兜底（21:00~08:00、1 次/2 次），并写一条 `WARN` 日志与告警指标 `care_throttle_rule_missing_total`。这样「误操作把所有规则停用」不会导致完全不限频——**降级方向必须是更保守，不是更宽松**。

**免打扰时段判定伪代码（含跨零点）：**

```python
import random

from datetime import datetime, time, timedelta

def in_quiet_hours(now: datetime, start: time, end: time) -> bool:
    """判断 now 是否落在 [start, end) 免打扰区间内，支持跨零点。"""
    cur = now.time()
    if start <= end:
        return start <= cur < end
    return cur >= start or cur < end


def next_allowed_at(now: datetime, rule: "ThrottleRuleAuth") -> datetime:
    """返回下一次允许发送的时刻；若当前不在免打扰期，返回 now 本身。"""
    if not in_quiet_hours(now, rule.quiet_start, rule.quiet_end):
        return now
    base = datetime.combine(now.date(), rule.quiet_end)
    if rule.quiet_start > rule.quiet_end:
        base = base + timedelta(days=1) if now.time() >= rule.quiet_start else base
    offset = timedelta(minutes=rule.defer_offset_minutes)
    jitter = timedelta(minutes=random.randint(0, rule.defer_jitter_minutes))
    return base + offset + jitter
```

#### 4.9.3 约束定义

```sql
ALTER TABLE m19_care_effect_daily
    ADD CONSTRAINT ck_m19_care_effect_daily_quality
    CHECK (data_quality = ANY (ARRAY['REALTIME', 'DAILY', 'ESTIMATED'])),
    ADD CONSTRAINT ck_m19_care_effect_daily_care_type
    CHECK (care_type = '' OR care_type = ANY (ARRAY['BIRTHDAY', 'RECALL', 'POSTOP', 'FOLLOWUP', 'ANNIVERSARY', 'HOLIDAY', 'OTHER'])),
    ADD CONSTRAINT ck_m19_care_effect_daily_channel
    CHECK (channel = '' OR channel = ANY (ARRAY['SMS', 'WECHAT', 'PHONE', 'INBOX', 'MAIL', 'PUSH'])),
    ADD CONSTRAINT ck_m19_care_effect_daily_count
    CHECK (task_count >= 0 AND sent_count >= 0 AND delivered_count >= 0 AND failed_count >= 0
           AND suppressed_count >= 0 AND cost_cent_total >= 0 AND conv_amount >= 0),
    ADD CONSTRAINT ck_m19_care_effect_daily_rate_range
    CHECK ((touch_rate IS NULL OR (touch_rate >= 0 AND touch_rate <= 1))
           AND (deliver_rate IS NULL OR (deliver_rate >= 0 AND deliver_rate <= 1))
           AND (suppress_rate IS NULL OR (suppress_rate >= 0 AND suppress_rate <= 1))
           AND (conv_rate IS NULL OR (conv_rate >= 0 AND conv_rate <= 1)));
```

组合约束 1：**任务数必须等于已发送加已抑制加待发送**（不含失败，失败属于已发送的分支）。

```sql
ALTER TABLE m19_care_effect_daily
    ADD CONSTRAINT ck_m19_care_effect_daily_balance
    CHECK (task_count = sent_count + suppressed_count OR task_count >= sent_count + suppressed_count);
```

约束说明：`task_count` 是当日生成的任务总数，包含尚未执行的 `PENDING`，因此只能要求 `task_count >= sent_count + suppressed_count`，等号成立当且仅当日终态任务已全部处理完。这一条防的是「各分项统计口径不一致导致分项之和大于总数」——出现这种情况时报表页会显示「已发送 1,240 / 任务 1,100」这种自相矛盾的数字。

组合约束 2：**抑制分项之和必须等于抑制总数**。

```sql
ALTER TABLE m19_care_effect_daily
    ADD CONSTRAINT ck_m19_care_effect_daily_suppress_sum
    CHECK (suppressed_count = suppress_blacklist_count + suppress_quiet_count + suppress_freq_count
                             + suppress_privacy_count + suppress_conflict_count);
```

防的真实错误：新增了一道闸门（如模板隐私校验）但汇总作业没有同步加进总和，导致「抑制总数 320 条，但分项加起来只有 286 条」，运营每次都要手工解释这 34 条的差额。等式约束让漏加分项在写入时立即暴露。

组合约束 3：**分母为 0 的比率必须为 NULL，不为 0 的比率必须非空**。

```sql
ALTER TABLE m19_care_effect_daily
    ADD CONSTRAINT ck_m19_care_effect_daily_rate_null
    CHECK (
        (task_count = 0 AND touch_rate IS NULL AND suppress_rate IS NULL)
        OR (task_count > 0 AND touch_rate IS NOT NULL AND suppress_rate IS NOT NULL)
    ),
    ADD CONSTRAINT ck_m19_care_effect_daily_deliver_null
    CHECK (
        (sent_count = 0 AND deliver_rate IS NULL AND conv_rate IS NULL)
        OR (sent_count > 0 AND deliver_rate IS NOT NULL AND conv_rate IS NOT NULL)
    );
```

防的真实错误：没有触达的日期，代码直接算 `0 / 0` 得到 `0.000000` 写库，然后在前端折线图上画出一条「抑制率 0%」的假低谷——实际那天是没有数据而不是表现好。NULL 在图表上显示为空缺，这才是正确表达。

#### 4.9.4 计算口径

| 指标 | 公式 | 分母为 0 时 | 说明 |
| --- | --- | --- | --- |
| 触达率 `touch_rate` | `sent_count / task_count` | NULL | 任务中被真实提交触达的比例 |
| 送达率 `deliver_rate` | `delivered_count / sent_count` | NULL | 已送达回执占已提交的比例 |
| 抑制率 `suppress_rate` | `suppressed_count / task_count` | NULL | 被闸门拦下的任务占比 |
| 转化率 `conv_rate` | `conv_count / sent_count` | NULL | 7 日内到店人数占触达条数之比 |
| 单条成本 | `cost_cent_total / sent_count` | NULL | 单位分，展示时转元并保留 2 位 |

**舍入规则：** 所有比率统一 `ROUND_HALF_UP` 保留 6 位小数；金额保留 2 位，单位元；成本的中间计算按分处理，仅在展示层转元。

**转化归因规则：** 一个患者在观察期内到店，归因到**最近一次触达**所属的规则与渠道（末次触达归因）。若同一患者 7 日内被两条不同规则的关怀触达后到店，只计入最后一次——这是为了保守估计效果，避免「多个活动都把同一次到店算成自己的功劳」导致各活动转化之和超过实际到店人数。

#### 4.9.6 设计说明

- **为什么维度列用空串表示合计而不是 NULL**：PostgreSQL 的唯一索引里 NULL 互不相等，若用 NULL 表示合计行，`uk (stat_date, rule_code, care_type, channel)` 会允许同一日期插入无穷多行合计行。用空串既满足唯一约束，又与共享规范「维度字段无值存空串」的约定一致。
- **为什么 `calc_version` 是必须字段而不是可选项**：效果口径会变（例如从「点击归因」改为「末次触达归因」）。改了口径后，历史的转化率数字如果不标注版本，运营会拿新口径数据跟旧口径数据做同比，得出完全错误的结论。本表和 M22 报表都遵循同一条原则：**口径变更必须留痕，历史数据不重算**。
- **为什么 `avg_click_hour` 是 `NUMERIC(6,2)` 而不是整数**：平均点击时段若取整，08:30 和 20:30 平均成 14 点毫无意义。保留 2 位小数可以表达「平均 19.75 点」即晚 7 点 45 分左右，这对确定最佳发送时间很关键。
- **为什么会话作业在 01:30 而不是 00:05**：M03-05 的回执可能在 23:59 之后仍在到达（通道回执有延迟），00:05 汇总会漏掉尾部长尾。01:30 汇总前一日，保留 90 分钟缓冲。

    CHECK ((decision = 'FAIL_CLOSED' AND fail_closed = TRUE AND fail_reason IS NOT NULL)
           OR (decision <> 'FAIL_CLOSED' AND fail_closed = FALSE));
```

防的真实错误：把「上游超时」当成「未在黑名单」直接放行（`decision = 'PASS'`），事后追查时看到 `PASS` 完全查不出这是降级放行。这条约束强制把「查到没被拦」与「没查到所以拦下」分开表述。

    CHECK ((decision = 'PASS' AND upstream_available = TRUE AND upstream_status = 'ALLOWED')
           OR (decision = 'BLOCK' AND upstream_available = TRUE AND upstream_status = 'BLOCKED' AND blocked_reason IS NOT NULL)
           OR (decision = 'FAIL_CLOSED' AND upstream_available = FALSE));
```

防的真实错误：`decision = 'PASS'` 但 `upstream_available = FALSE`——这正是最危险的组合：上游没查到却放行了。约束在数据库层直接禁止这种组合存在。

- **本表与 M03-05 的关系必须写清楚给后来人**：本表**不是**退订名单，任何需要做退订判断的地方都必须实时调 M03-05（或读其缓存），不得以本表的快照为判断依据。本表的数据永远滞后于真实黑名单，只用于举证与复盘。

### 4.11 表：`m19_care_oper_log`

**中文名：** 关怀操作日志表（规则/计划/名单/配置的全部变更留痕）

**表说明：** 本表记录本子模块内所有「影响触达行为」的配置变更与人工操作。规则改了免打扰时段、名单被手动排除了一批人、配置被放宽了频次——这些都必须能回答「谁在什么时候改的、改前改后是什么」。按 `created_at` 月度分区，只增不改。

**写入方：** M19-03 全部写操作的服务层（统一 AOP 切面记录）+ P-09 内部契约
**只读方：** 合规审计、P02/P03/P04 操作历史面板

#### 4.11.1 字段定义

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | N | 自增标识 | 主键之一 |

#### 4.11.3 约束定义

```sql
ALTER TABLE m19_care_oper_log
    ADD CONSTRAINT ck_m19_care_oper_log_object_type
    CHECK (object_type = ANY (ARRAY['RULE', 'PLAN', 'TASK', 'RECALL_LIST', 'TRIAL_RULE', 'CONFIG'])),
    ADD CONSTRAINT ck_m19_care_oper_log_action
    CHECK (action = ANY (ARRAY['CREATE', 'UPDATE', 'ENABLE', 'DISABLE', 'DELETE', 'EXECUTE', 'RETRY', 'CANCEL', 'EXCLUDE', 'EXPORT', 'TRIGGER', 'APPROVE', 'REJECT'])),
    ADD CONSTRAINT ck_m19_care_oper_log_risk
    CHECK (risk_level = ANY (ARRAY['NORMAL', 'SENSITIVE', 'CRITICAL'])),
    ADD CONSTRAINT ck_m19_care_oper_log_source
    CHECK (operate_source = ANY (ARRAY['PAGE', 'API', 'CONTRACT', 'SCHEDULER', 'EVENT'])),
    ADD CONSTRAINT ck_m19_care_oper_log_result
    CHECK (operate_result = ANY (ARRAY['SUCCESS', 'FAIL']));
```

组合约束 1：**更新操作必须有字段级变更明细**。

```sql
ALTER TABLE m19_care_oper_log
    ADD CONSTRAINT ck_m19_care_oper_log_changes
    CHECK (action <> 'UPDATE' OR field_changes IS NOT NULL);
```

防的真实错误：只记「某人修改了规则 RULE_RECALL_90」而不记改了什么，审计时无法判断这次修改是否放宽了频次限制。

组合约束 2：**失败操作必须写明失败原因**。

```sql
ALTER TABLE m19_care_oper_log
    ADD CONSTRAINT ck_m19_care_oper_log_fail
    CHECK (operate_result <> 'FAIL' OR fail_reason IS NOT NULL);
```

防的真实错误：批量操作部分失败，日志只记 `FAIL` 不记原因，运营无法知道是权限不足、参数越界还是唯一键冲突，只能重试碰运气。

组合约束 3：**页面与接口操作必须有操作人**。

```sql
ALTER TABLE m19_care_oper_log
    ADD CONSTRAINT ck_m19_care_oper_log_operator
    CHECK (operate_source <> 'PAGE' OR operator_id IS NOT NULL);
```

防的真实错误：接口层漏传当前用户，日志里操作人为空，出现问题时无法追到人。定时作业与事件驱动来源允许为空，因为其主体是系统。

#### 4.11.5 设计说明

- **为什么 `risk_level` 要在写入时就定级**：审计人员不可能逐条回顾所有变更。定级后可以只看 `CRITICAL` 的（放宽触达限制的操作），数量从每月 2,000 条降到每月 5~10 条，审计才真正可执行。
- **判定 `CRITICAL` 的具体规则**：`object_type = 'TRIAL_RULE'` 且（`quiet_enabled` 由 TRUE 改 FALSE，或 `freq_limit_24h` 增大，或 `quiet_exempt_types` 增加元素，或 `quiet_start` 推迟/`quiet_end` 提前）；`object_type = 'RULE'` 且 `template_vars` 新增了非白名单键；`object_type = 'TASK'` 且 `action = 'RETRY'` 且原任务是 `SUPPRESSED`。
- **为什么操作人姓名要快照**：人员离职后 M01 的员工记录可能被逻辑删除或改名，而审计要看的是「当时是谁操作的」。快照让日志自解释。
- **为什么本表不做「修改留档表 + 当前表」双写**：本表与业务表是同一次事务写入的（服务层切面统一处理），不是异步补写。若异步补写，进程崩溃时会丢失这次变更的留痕，而这恰恰是审计最需要的那几条。

### 4.14 生日数据来源与同步模型（跨表专题）

本节不定义新表，说明 `m19_care_plan.birthday_source` / `birthday_at_build` / `birthday_changed` 与 `m19_care_task.birthday_snapshot` 四个字段背后的数据流转。**这些字段存在的唯一目的：让「客户在错误的日子收到生日祝福」这件事可被发现、可被阻止。**

#### 4.14.1 出生日期的唯一权威与读取路径

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 唯一权威 | M03-03 会员主档 | 不在本子模块存生日主数据 |
| 读取接口 | `GET /internal/v1/member/by-patient/{patient_id}` | 返回会员主档，含出生日期、等级、会员状态 |
| 兜底来源 | M03-01 `GET /internal/v1/patient/{id}/brief` | 非会员患者从患者主档取出生日期 |
| 落库字段 | `m19_care_plan.birthday_source` | 记录本次用的是哪个来源，`M03_03` / `M03_01` / `MANUAL` |
| 禁止做法 | 在 `m19_care_rule.audience_json` 里存生日值 | 规则是「怎么算」，不应内嵌患者个人数据 |

#### 4.14.2 生日变更的三条同步链路

| 链路 | 触发 | 检测方式 | 处理动作 |
| --- | --- | --- | --- |
| 实时链路 | 患者在本院任何触点修改出生日期 | M03-03 发布 `mpi.member.status_changed` 不覆盖生日，故本模块**每日 02:10 全量比对**当日与次日生日名单中患者的出生日期 | 不一致则置 `birthday_changed = TRUE`，作废该计划下未发送的生日任务（`CANCELLED` + `fail_reason = '生日已变更'`），重新生成 |
| 事件链路 | 会员合并（`mpi.patient.merged` / `mpi.member.merge_conflict`） | 订阅事件，重定向 `patient_id` | 合并后以主患者的出生日期为准，从患者的生日任务作废；冲突记录写 `m19_care_oper_log`（`object_type = 'PLAN'`）待人工确认 |
| 兜底链路 | 生日当天发现算错 | P03 页面「生日快照」列显式展示 `birthday_snapshot` | 运营手工取消任务，用 `MANUAL` 来源重建 |

**为什么不用事件驱动做主链路：** M03-03 的事件清单里没有「生日变更」事件（`mpi.member.status_changed` 是会员状态、`mpi.member.tag_changed` 是标签），靠事件拿不到生日变化。**没有的事件不能假设它存在**——这是本项目此前踩过的坑：订阅一个不存在的事件名不会有任何报错，事件一条也收不到，链路静默失效。因此生日变更用「写入前快照 + 每日比对」兜底，不依赖任何未登记事件。

#### 4.14.3 生日计算的口径与边界

```
是否生日 = (MONTH(birthday_at_build) = MONTH(stat_date))
       AND (DAY(birthday_at_build) = DAY(stat_date))
       OR (birthday 为 2-29 AND 当年非闰年 AND 当日为 2-28)
```

| 边界情形 | 处理 | 理由 |
| --- | --- | --- |
| 2 月 29 日出生、当年非闰年 | 按 2 月 28 日发送 | 顺延到 3 月 1 日会被患者认为记错了生日 |
| 出生日期为空 | 排除，`exclude_flag = 'NO_BIRTHDAY'` | 不能猜 |
| 出生日期明显异常（年份早于 1900 或晚于当前） | 排除并告警 | 这类多半是录入错误，按错误日期发祝福比不发更糟 |
| 当日生日但已在本年触达过 | 排除，`exclude_flag = 'ALREADY_TOUCHED'` | 判重键 `(patient_id, care_type='BIRTHDAY', 年份)` |
| 生日当天 21:30 才生成任务 | 顺延到次日 08:05 | 生日祝福次日早上送达仍属当月，比深夜打扰好 |

#### 4.14.4 与会员等级相关的应用边界（明确不消费的事件）

| 事件 | 本子模块是否消费 | 说明 |
| --- | --- | --- |
| `mpi.member.status_changed` | **是** | 驱动闸门第 0 道：会员状态变为 `CANCELLED` 时立即停发该会员全部未执行关怀任务 |
| `mpi.member.merged` | **是** | 患者合并后重定向 `m19_care_task` / `m19_care_touch` / `m19_care_recall_item` 的 `patient_id` |
| `mpi.member.merge_conflict` | **是** | 写 `m19_care_oper_log` 待人工确认 |
| `mpi.patient.merged` | **是** | 同上，患者域合并事件 |
| `mpi.member.level_changed` | **否** | 等级变化不产生关怀任务。「升级礼遇关怀」属于 M19-07 营销活动域（发券 + 权益说明），本子模块只负责在触达时判定会员状态是否有效。此处明确不消费，避免后来人以为漏接 |
| `mpi.member.created` | **否** | 新人入会不触发关怀；欢迎类触达由 M19-07 营销活动负责 |

**为什么把等级事件排除在外：** 等级变化的业务含义是「权益变了」，对应的动作是发券、通知权益，属于营销活动域的一次性动作，有明确的券与核销闭环。若本子模块也接，同一次升级会出现「等级变化关怀短信」+「营销活动欢迎短信」两条，且两条互不感知对方，频次闸门只拦得住第三条。**一个业务动作只在一个子模块产生对外触达。**

#### 4.14.5 会员状态快照与闸门第 0 道

| 项 | 内容 |
| --- | --- |
| 状态取值 | `ACTIVE` 正常 / `FROZEN` 冻结 / `CANCELLED` 注销 / `INACTIVE` 未激活 / `NON_MEMBER` 非会员 |
| 判为 `BLACKLIST` | 仅 `CANCELLED`（注销）。`FROZEN` 与 `INACTIVE` **不拦**，只降级为站内信渠道并记录 |
| 为什么 `FROZEN` 不直接拦 | 冻结常见于「欠费冻结」或「临时停用」，患者本人仍是在册客户，完全停发会误伤；改为站内信既不失礼也不打扰 |
| 为什么存快照而不回查 | 会员状态会变。举证要回答的是「发送那一刻该会员是什么状态」，回查只能得到「现在是什么状态」 |
| 上游不可用时 | 按「非合规闸门」处理：**不 fail-closed**，降级为**仅允许 `INBOX` 站内信**，`gate_member_status` 记空串并在 `m19_care_blacklist_snapshot` 同事务写一条 `check_scene = 'TASK_SEND'` 的失败记录 |

**闸门第 0 道不 fail-closed 的论证：** 铁律 5 要求「任一条不过宁可漏触达也不发」，其保护对象是**患者的意愿**——退订与黑名单表达的是患者明确拒绝，猜错一次就是合规事故。会员状态表达的是**账户可用性**，猜错的代价是「给一个冻结会员发了一条站内信」，可撤回、无打扰、不复现。因此这里选择「降级到最低打扰渠道」而不是「全线停摆」，否则 M03-03 一次 10 分钟抖动会让全院关怀停两小时，运营侧必然要求加一个「跳过闸门」的后门，那才是真正的风险。**降级的方向必须是打扰更少，而不是校验更松。**
