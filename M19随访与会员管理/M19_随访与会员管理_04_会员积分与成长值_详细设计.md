## 1. 模块概述

### 1.1 定位

积分与成长值子系统是会员体系里**唯一一个「有账」的部分**。等级定义、权益定义、标签、会员主档都归 M03-03；M19-04 负责的是「钱怎么发、怎么扣、怎么过期、怎么对账、怎么折算成负债」。

一句话概括本子模块的职责：

> 把每一次会员消费与互动，按**消费发生当时**的规则与等级，折算成一笔不可篡改的积分流水，并保证任何时刻「账户余额 = 流水代数和」。

这里的「不可篡改」不是一句设计口号，而是物理保证：数据库层 `REVOKE UPDATE, DELETE`、触发器拦截、`CHECK (balance_after >= 0)`、每日对账四道防线叠加。详细手段见数据结构文档附录 A。

### 1.2 为什么独立成子模块

积分看起来只是「加个数减个数」，但它的失败模式与随访、关怀、券完全不同，放在一起会被其他子模块的假设污染：

| 关注点 | 随访执行（M19-02） | 权益核销（M19-05） | 积分与成长值（M19-04） |
| --- | --- | --- | --- |
| 数据的可变性 | 结果可补录、可修改 | 核销状态可流转 | **只增不改，只能追加反向流水** |
| 失败的代价 | 少做一次随访 | 权益用错了可人工纠正 | **多发一次积分就是真金白银的损失，且无法回收** |
| 时间语义 | 以执行时刻为准 | 以核销时刻为准 | **以业务发生时刻为准，且必须固化当时的等级快照** |
| 并发要求 | 弱 | 中（防重复核销） | **强（同一账户并发扣减必须串行化）** |
| 与财务的关系 | 无 | 无 | **积分余额直接构成 M17 的负债科目** |
| 审计要求 | 一般 | 一般 | **每一笔都要能回答「谁、什么时候、依据哪条规则、当时什么等级」** |

如果积分和随访放在同一个服务里，随访数据「可补录可修改」的默认习惯会渗透到积分表上——而只要有一次 `UPDATE m19_points_ledger`，整个积分账就不可信了。物理隔离职责、单独设计表与权限，是这一类账务型子模块的常规做法。

### 1.4 概念辨析

以下六组概念最容易在实现时混淆，每一组都给出判定标准。

**（1）积分余额 vs 冻结积分**

`points_balance` 是已入账、可自由使用的积分；`frozen_points` 是已下单未完成兑换而暂时锁定的积分。两者都占用「会员以为自己的积分」，但只有前者能直接扣。可兑付总额 = `points_balance - frozen_points`。这两个字段永远不能被同一个更新语句写成「余额减掉冻结额」，否则冻结额被扣两次。

**（2）等级快照 `level_at_txn` vs 当前等级 `current_level_code`**

`level_at_txn` 写在流水上，是不可变的历史事实；`current_level_code` 在 M03-03 的会员主档上，是当前值。发放积分时，倍率必须按 `level_at_txn` 取；展示「您现在是什么等级」时，用 `current_level_code`。混用会导致用户升级后历史消费被按新倍率重算——这是本子模块最贵的一个 bug，算例见 3.4.1。

**（3）成长值 vs 积分**

成长值只增不减（除管理员调整），用来决定等级；积分可增可减，用来兑换。用户消费 328.50 元，同时得到 32.85 积分与 328.50 成长值。积分可以花掉，成长值花不掉。把成长值当成「另一种积分」来做扣减，用户一降级就再难升回来。

**（4）过期 vs 扣减 vs 冲正**

三者的流水类型不同、触发方不同、能否逆转不同：

| 操作 | `txn_type` | 方向 | 触发方 | 可否逆转 |
| --- | --- | --- | --- | --- |
| 过期 | `EXPIRE` | 负 | 定时任务 | 不可逆转，过期即是权益消灭 |
| 扣减 | `DEDUCT` | 负 | 兑换、活动消耗 | 可追加 `REFUND` 返还 |
| 冲正 | `REVERSE` | 负 | 退费、兑换失败 | 冲正本身不可再被冲正 |

**（5）积分规则 vs 积分倍率**

`m19_points_rule` 是「什么业务场景给分」（门诊结算给分、住院结算给分、随访完成给分）；`m19_points_rule_item` 是「这个场景下，各等级给几倍」。一条规则有 N 行倍率（N = 等级数 + 1 个兜底行）。规则决定分子结构，倍率决定分子大小。

**（6）账户余额 vs 流水代数和**

`m19_points_account.points_balance` 是**派生值**，不是权威值。权威值是流水代数和。账户表的余额字段存在的唯一理由是性能（每次查余额都扫流水太慢）。一旦两者不一致，以流水为准，并且必须写一条对账差异记录。任何时候都不允许「先改账户余额，事后补流水」。

### 1.5 模块目标

| # | 目标 | 可量化指标 |
| --- | --- | --- |
| 1 | 积分发放准确 | 发放金额与规则计算值误差为 0（`NUMERIC(14,2)` 精确小数，无浮点） |

### 2.3 边界说明

**边界一：等级定义在 M03-03，等级→倍率在 M19-04。**

M19-04 建两张表 `m19_points_rule_item`（等级→倍率）与 `m19_points_level_rule`（等级→成长值门槛），其中的 `level_code` 必须与 M03-03 `mpi_member_level.level_code` 逐字一致。系统在启动时与每日 02:00 各做一次校验：把 M03-03 的等级清单拉下来与本地两张表的 `level_code` 全集比对，出现 M03-03 有而本地没有的等级时，记一条告警并自动以「最低等级倍率」补一行兜底映射，绝不允许该等级发放时取到 0 倍率。

**边界二：积分倍率必须取消费发生时的等级。**

发放接口收到 `occurred_at` 与 `biz_no` 后，先用 `member_id + occurred_at` 回查「该时点会员是什么等级」。这个等级来自 M03-03 的等级变更历史；若该历史在 M03-03 不可得，则退化为「以 `m19_points_growth_ledger` 中 `occurred_at` 之前最近一条流水的 `level_after` 作为当时等级」。两种来源都在 `level_source` 字段里标明，便于事后质疑时追溯。

**边界三：M19-04 不出会计凭证。**

积分负债的计提、兑付时的费用确认，都由 M17 依据 M19-04 提供的日汇总数据生成凭证。M19-04 只回答「截至某日未消耗多少积分、按什么比例折成多少钱」。

**边界四：过期提醒必须过三道闸门。**

M19-04 决定「提醒谁」，但不直接发送。所有提醒都通过 M19-03 的触达通道发出，并逐条过：黑名单与退订筛查 → 免打扰时段（21:00 至次日 08:00）→ 同患者 24 小时内频次上限。被闸门拦下的提醒，在 `m19_points_expire_record` 上写 `remind_suppressed = TRUE` 与原因，而不是静默丢弃。

### 3.2 状态机

#### 3.2.1 积分账户状态机

```
                    +----------------+
                    |    ACTIVE      |<--------------+
                    |  正常可收发    |               |
                    +----------------+               |
                       |        ^                    |
              冻结     |        |  解冻              |
                       v        |                    |
                    +----------------+               |
                    |    FROZEN      |               |
                    | 只收不发       |               |
                    +----------------+               |
                       |                             |
              注销     |                             |
                       v                             |
                    +----------------+               |
                    |    CLOSED      |               |
                    | 余额必须为 0   |---------------+
                    +----------------+   不可复活
```

| 状态 | 含义 | 可发放 | 可扣减 | 可查询 |
| --- | --- | --- | --- | --- |
| `ACTIVE` | 正常 | 是 | 是 | 是 |
| `FROZEN` | 冻结（风控、投诉、账号异常） | 是 | 否 | 是 |
| `CLOSED` | 已注销（会员注销或合并迁出） | 否 | 否 | 是（只读历史） |

| # | 流转 | 触发条件 | 前置校验 | 副作用 |
| --- | --- | --- | --- | --- |
| 1 | `ACTIVE` → `FROZEN` | 运营手工冻结、风控规则命中 | 有 `m19:points:config` 权限 | 写 `frozen_reason`、写 `m19_points_log` |
| 2 | `FROZEN` → `ACTIVE` | 人工解冻 | 冻结原因已消除 | 清空 `frozen_reason`、写日志 |
| 3 | `ACTIVE` → `CLOSED` | 会员注销 | **余额与冻结额均为 0** | 写 `closed_at` |
| 4 | `FROZEN` → `CLOSED` | 会员注销且余额已清零 | 余额与冻结额均为 0 | 写 `closed_at` |
| 5 | `CLOSED` → 任何 | 禁止 | — | `ck_m19_points_account_closed` 与业务层双重拦截 |

关于「注销前必须清零」的理由：如果允许带余额注销，那部分积分就变成了「永远不会被消耗、也永远不会被过期」的幽灵负债，M17 会一直计提但永远兑付不出去。

#### 3.2.2 兑换单状态机

```
   +-----------+
   |  CREATED  |  下单成功，积分尚未扣
   +-----------+
         |  扣减成功
         v
   +-----------+
   | DEDUCTED  |  积分已扣，等待发货
   +-----------+
         |  发货中
         v
   +-------------+
   | DELIVERING  |
   +-------------+
      |       |
 成功 |       | 失败
      v       v
 +----------+  +----------+
 |DELIVERED |  |  FAILED  |  必须追加 REVERSE 返还
 +----------+  +----------+
```

| # | 流转 | 触发 | 前置校验 | 副作用 |
| --- | --- | --- | --- | --- |
| 1 | → `CREATED` | 会员下单 | 余额充足、商品可兑 | 无流水 |
| 2 | `CREATED` → `DEDUCTED` | 扣减成功 | 行锁扣减成功 | 写一条 `DEDUCT` 流水，记 `deduct_ledger_no` |
| 3 | `DEDUCTED` → `DELIVERING` | 发货开始 | — | 无 |
| 4 | `DELIVERING` → `DELIVERED` | 发货完成 | — | 无 |
| 5 | `DEDUCTED`/`DELIVERING` → `FAILED` | 发货失败、超时、人工取消 | — | **必须**追加 `REFUND` 流水，`reverse_ledger_no` 非空 |
| 6 | `CREATED` → `CANCELLED` | 下单后主动取消 | 未扣减 | 无流水 |

### 3.3 分类与枚举

**积分流水类型 `txn_type`（共享规范 §13，一字不差）**

| 值 | 中文 | 方向 | 符号来源 | 典型场景 |
| --- | --- | --- | --- | --- |
| `GRANT` | 发放 | 正 | `direction = 1` | 消费结算、活动奖励 |
| `DEDUCT` | 扣减 | 负 | `direction = -1` | 兑换消耗、活动消耗 |
| `EXPIRE` | 过期 | 负 | `direction = -1` | 到期批次清零 |
| `ADJUST` | 调整 | **由 points 自带正负** | 不取 `direction` | 管理后台补录、差错更正 |
| `REFUND` | 退还 | 正 | `direction = 1` | 兑换失败返还、退费返还 |
| `REVERSE` | 冲正 | 负 | `direction = -1` | 退费冲回已发积分 |

**积分规则类型 `rule_type`**

| 值 | 含义 | 计算方式 |
| --- | --- | --- |
| `BY_AMOUNT` | 按金额 | `ROUND(biz_amount × ratio × grow_coefficient, 2)` |
| `BY_TIMES` | 按次数 | `fix_points × 次数`，受 `times_limit_daily` 限制 |
| `BY_ACTION` | 按行为 | `fix_points`，如完成随访、完善资料 |
| `FIXED` | 固定值 | `fix_points`，不随任何变量变化 |

**成长值来源 `source`**

| 值 | 含义 | 是否可为负 |
| --- | --- | --- |
| `CONSUME` | 消费产生 | 否 |
| `ACTIVITY` | 活动获得 | 否 |
| `FOLLOWUP` | 随访完成 | 否 |
| `MANUAL` | 人工补录 | 否 |
| `ADJUST` | 管理员调整 | **是（唯一允许负值的来源）** |

**积分负债预警级别 `warn_level`**

| 值 | 条件 | 处置 |
| --- | --- | --- |
| `NORMAL` | 消耗率 ≥ 30% | 无 |
| `ATTENTION` | 20% ≤ 消耗率 < 30% | 运营复核发放规则 |
| `WARNING` | 10% ≤ 消耗率 < 20% | 上报会员运营主管 |
| `CRITICAL` | 消耗率 < 10% | 暂停新增发放规则，专项清理 |

### 3.4 关键计算模型

#### 3.4.1 积分发放计算（含等级快照）

**公式**

```
发放积分 = ROUND(biz_amount × points_ratio × grow_coefficient, 2)
其中 points_ratio 取自 (rule_code, rule_version, level_at_txn) 对应的倍率行
     grow_coefficient 取自 m19_points_rule.grow_coefficient，默认 1.000000
舍入方式：四舍五入到 2 位小数（ROUND_HALF_UP），与 PostgreSQL NUMERIC 默认舍入一致
```

**边界条件**

| 条件 | 处理 |
| --- | --- |
| `biz_amount < min_biz_amount` | 不发放，返回成功但 `granted_points = 0.00`，`skip_reason = BELOW_MIN_AMOUNT` |
| 计算值 > `max_points_per_txn` | 截断为 `max_points_per_txn`，`capped = true` |
| 计算值 < 0.01 | 视为 0，不落流水（避免产生大量 0.00 流水污染账本） |
| 倍率行缺失 | 取 `is_fallback = TRUE` 的兜底行，同时写告警 |
| 账户 `FROZEN` | 允许发放（冻结只限制支出） |
| 账户 `CLOSED` | 拒绝，返回 `"1904006"` |

**算例一（必须复现的正确行为）**

李女士（`member_id = 88001`）在 2026-10-21 10:30:00 门诊结算 328.50 元。

```
业务发生时刻：occurred_at = 2026-10-21 10:30:00
该时点等级：  level_at_txn = 'SILVER'（银卡）
银卡倍率：    points_ratio = 0.100000
规则权重：    grow_coefficient = 1.000000

发放积分 = ROUND(328.50 × 0.100000 × 1.000000, 2) = 32.85
发放前余额 = 1000.00
balance_after = 1000.00 + 32.85 = 1032.85
```

落库的流水行：

```json
{
  "ledger_no": "PL20261021000001",
  "account_id": 1001,
  "member_id": 88001,
  "txn_type": "GRANT",
  "direction": 1,
  "points": 32.85,
  "balance_after": 1032.85,
  "level_at_txn": "SILVER",
  "points_ratio_snapshot": 0.100000,
  "rule_code": "PR_OUTPATIENT_VISIT",
  "rule_version": 1,
  "biz_type": "OUTPATIENT_SETTLEMENT",
  "biz_no": "ST20261021000123",
  "occurred_at": "2026-10-21 10:30:00",
  "expire_at": "2028-10-21 23:59:59"
}
```

**算例二（必须被测试捕获的错误行为）**

2027-01-15 李女士消费达标升为金卡（`level_at_txn` 本应是 `GOLD`，`points_ratio = 0.300000`）。此时若上游因网络重试在 2027-01-15 15:00:00 重放 2026-10-21 那笔结算（同一 `biz_no`），系统必须：

1. 命中幂等键 `OUTPATIENT_SETTLEMENT:ST20261021000123:PR_OUTPATIENT_VISIT`；
2. 返回首次结果 `granted_points = 32.85`、`idempotent_replay = true`；
3. **绝不**按金卡倍率重算。

假如实现错误地取「当前等级」，重算结果会是：

```
错误计算 = ROUND(328.50 × 0.300000 × 1.000000, 2) = 98.55
多发 = 98.55 - 32.85 = 65.70 分
```

若按原设计中单位金额倍率差异放大（金卡 1.5 倍、银卡 0.1 倍的口径），同笔 328.50 元会被算成 492.75 分，多发 459.90 分。无论是 65.70 还是 459.90，都是一笔凭空产生、无法回收的负债。验收用例 AC-12 专门针对此场景：先发银卡流水，再改等级，再重放，断言 `granted_points` 仍为 32.85 且只存在一条流水。

**算例三（小数积分与舍入）**

某规则 `PR_ACTIVITY_CHECKIN` 是 `FIXED` 类型、`fix_points = 0.33`，用户连续签到 3 次：

```
第 1 次：ROUND(0.33 × 1.000000, 2) = 0.33，balance_after = 1032.85 + 0.33 = 1033.18
第 2 次：0.33，balance_after = 1033.51
第 3 次：0.33，balance_after = 1033.84
```

如果实现里用浮点，`0.33 + 0.33 + 0.33` 可能得到 `0.9900000000000001`，落库为 `0.99` 后三次合计变成 `0.98` 或 `1.00`，一个季度下来账就差了。所有积分字段使用 `NUMERIC(14,2)`，Python 侧一律用 `Decimal`，禁止 `float`。

#### 3.4.2 成长值计算与等级判定

**公式**

```
成长值增量 = ROUND(biz_amount × grow_coefficient, 2)      默认系数 1.000000
当前成长值 = Σ(正向成长值流水) − Σ(负向成长值流水)
当前等级   = MAX(level_rank) WHERE growth_threshold <= 当前成长值
```

**算例**

李女士累计成长值 12,800.00，门槛配置：

| 等级 | `level_rank` | `growth_threshold` |
| --- | --- | --- |
| `NORMAL` 普通 | 1 | 0.00 |
| `SILVER` 银卡 | 2 | 5000.00 |
| `GOLD` 金卡 | 3 | 10000.00 |
| `PLATINUM` 白金 | 4 | 30000.00 |

```
判定：12800.00 >= 10000.00（金卡门槛）且 12800.00 < 30000.00（白金门槛）
结果：当前等级 = GOLD（金卡）
距升级白金还需 = 30000.00 - 12800.00 = 17200.00
```

**为什么成长值只增不减**

如果按「滚动 12 个月消费额」计算等级，一个 2026 年消费 12,000 元升到金卡的用户，2027 年 1 月会直接掉回银卡——他的积分倍率从 0.30 掉到 0.10 而没有任何预警。用户看到的体验是「我什么都没做，权益就没了」。这是公认的反人性设计。

本子模块的做法是：成长值只增不减，等级只升不降（除非管理员显式调整）；活跃度下降用另一套指标（近 90 天消费笔数、最近到店时间）通过 M19-08 的「会员分层」「流失预警」识别，并用运营手段挽回，而不是靠降级惩罚。

**降级路径的唯一合法方式**

只有 `source = 'ADJUST'` 的成长值流水可以为负，且必须走 `m19_points_adjust` 审批。数据库约束 `ck_m19_points_growth_ledger_monotonic` 强制：`source = 'ADJUST' OR growth_delta > 0`。这条 CHECK 拦住的是「代码里某个 `reduce_growth()` 方法被误调用」——一旦调用就会在数据库层抛错，而不是悄悄把用户降级。

#### 3.4.3 积分过期：FIFO 批次模型

**问题**

积分有有效期（默认 24 个月）。用户 2026-10 得到 100 分（2028-10 过期），2027-03 得到 200 分（2029-03 过期）。若他在 2027-06 花掉 150 分，应该扣哪一批？

**答案：先进先出（FIFO）。** 先扣最早到期的那批。花掉 150 分后，2026-10 那批已经用完（100 分），2027-03 那批用掉 50 分，剩 150 分。

**批次结构**

每条正向发放流水（`GRANT`、正向 `ADJUST`、`REFUND`）落一条 `m19_points_expire_record`：

| 字段 | 含义 | 算例 |
| --- | --- | --- |
| `expire_batch_no` | 批次号，`EX` + yyyyMMddHHmmss | `EX202610210001` |
| `source_ledger_no` | 来源流水号，唯一 | `PL20261021000001` |
| `granted_points` | 批次原始积分 | 100.00 |
| `used_points` | 已被消耗掉的（FIFO 扣） | 100.00 |
| `expired_points` | 过期清零的 | 0.00 |
| `expire_at` | 到期时刻 | `2028-10-21 23:59:59` |
| `status` | `WAITING` / `REMINDED` / `EXPIRED` / `CANCELLED` | `EXPIRED` |

约束 `ck_m19_points_expire_balance` 保证 `expired_points = granted_points - used_points`，任何时刻都成立。

**FIFO 扣减算法（必须整体在事务内）**

```python
from decimal import Decimal

def consume_batches(session, account_id: int, points_to_use: Decimal) -> list[dict]:
    """按 expire_at 升序扣减批次，返回每批消耗明细。

    调用方必须已对账户行加锁（SELECT ... FOR UPDATE），
    且本函数与账户余额扣减处于同一事务。
    """
    # 1. 取未用完的批次，按过期时间升序，锁住
    rows = session.execute(
        text("""
            SELECT id, expire_batch_no, granted_points, used_points
              FROM m19.m19_points_expire_record
             WHERE account_id = :account_id
               AND status IN ('WAITING', 'REMINDED')
               AND granted_points - used_points > 0
             ORDER BY expire_at ASC, id ASC
             FOR UPDATE
        """),
        {"account_id": account_id},
    ).mappings().all()

    remaining = points_to_use
    detail: list[dict] = []
    for row in rows:
        if remaining <= 0:
            break
        available = row["granted_points"] - row["used_points"]
        take = min(available, remaining)
        session.execute(
            text("""
                UPDATE m19.m19_points_expire_record
                   SET used_points = used_points + :take,
                       version_no  = version_no + 1,
                       updated_at  = CURRENT_TIMESTAMP
                 WHERE id = :id
            """),
            {"take": take, "id": row["id"]},
        )
        detail.append({"expire_batch_no": row["expire_batch_no"], "used": take})
        remaining -= take

    if remaining > 0:
        # 理论不可达：余额已被账户层校验过，批次总额应当等于余额
        raise RuntimeError("批次可用总额小于待扣积分，账实不符，触发对账")
    return detail
```

注意：`m19_points_expire_record` 是普通表不是流水表，允许 `UPDATE`，所以这里可以累加 `used_points`。但**积分流水表 `m19_points_ledger` 绝不允许 UPDATE**，因此一笔扣减跨 N 个批次时，落库的方式是：

1. 写**一条** `DEDUCT` 流水（`points = 150.00`，`balance_after` 为扣后余额）；
2. 在该流水的 `batch_detail` JSONB 字段里记录每批消耗明细；
3. 更新各批次的 `used_points`。

这样流水条数与业务笔数一一对应，对账时用流水即可；批次明细用于过期计算，与流水互为校验。

**过期执行**

每日 00:30 扫描 `expire_at <= now()` 且 `status IN ('WAITING','REMINDED')` 且 `granted_points - used_points > 0` 的批次：

```
过期积分 = granted_points - used_points
为每个账户生成一条 EXPIRE 流水（points = 该账户所有到期批次之和）
逐批把 status 置为 EXPIRED，expired_points = granted_points - used_points
账户余额 -= 过期积分
```

**算例**

| 批次 | 发放 | 已用 | 到期日 | 余额 |
| --- | --- | --- | --- | --- |
| `EX202610210001` | 100.00 | 100.00 | 2028-10-21 | 0.00 |
| `EX202703050002` | 200.00 | 50.00 | 2029-03-05 | 150.00 |

2029-03-05 00:30 任务执行：第二批过期 150.00，账户余额 150.00 → 0.00，落一条 `EXPIRE` 流水 `points = -150.00`、`balance_after = 0.00`、`expire_batch_no = 'EX202703050002'`。

#### 3.4.4 积分负债计算

**公式**

```
期末积分负债（元） = 期末未消耗积分总额 × 积分兑付比例
积分兑付比例默认 0.01 元/分（可由 P01 全局配置调整）
期末未消耗积分总额 = Σ m19_points_account.points_balance WHERE status <> 'CLOSED'
```

**算例**

```
2026-10-31 未消耗积分总额 = 12,860,000.00 分
积分兑付比例 = 0.010000 元/分
积分负债 = 12,860,000.00 × 0.010000 = 128,600.00 元
```

**辅助指标与超发判断**

```
积分消耗率 = 期间消耗积分 / 期间发放积分
积分过期率 = 期间过期积分 / 期间到期积分
单客平均积分余额 = 期末未消耗积分总额 / 有余额会员数
```

消耗率长期低于 30% 意味着发放的积分大部分没被使用——这既是负债累积，也是规则设计有问题的信号（用户要么不记得积分，要么兑换门槛太高）。此时负债会持续增长而兑付不会发生，一旦某天做一次「积分秒杀」，短时间内兑付需求会远超预期。

**「明天最多要兑付多少现金」的答案**

系统在 P09 页面直接给出三个数：

| 指标 | 口径 | 算例 |
| --- | --- | --- |
| 明日最大兑付额 | 当前未消耗积分总额 × 兑付比例 | 128,600.00 元 |
| 未来 30 天到期积分 | `expire_at` 在未来 30 天内且未用完的批次余额合计 | 420,000.00 分 |
| 高活跃会员潜在兑付 | 近 90 天有到店记录会员的余额合计 × 兑付比例 | 46,800.00 元 |

第一个数是理论极值（假设所有会员明天全部兑付），第二个数是「不兑就会过期消失」的部分，第三个数是更现实的短期压力。三个数一起看才能判断现金流是否安全。

#### 3.4.5 兑换扣减与失败返还

**先扣后发**

兑换必须「先扣积分，后发货」，不能「先发货，后扣积分」。理由：如果先发货再扣，扣减时余额不足或账户已冻结，货已经发出去了，损失无法挽回；先扣则最坏情况是积分扣了货没到，可以退。

**扣减流程（事务内）**

```
1. 校验兑换单状态为 CREATED
2. SELECT ... FOR UPDATE 锁账户行
3. 校验 status = 'ACTIVE'
4. 校验 points_balance - frozen_points >= points_total
5. 按 FIFO 扣减批次
6. 写 DEDUCT 流水，balance_after = 扣后余额
7. 账户 points_balance -= points_total，total_consumed += points_total
8. 兑换单 status = 'DEDUCTED'，deduct_ledger_no = 新流水号
9. 提交事务
```

**失败返还**

发货失败（库存不足、超时未发、人工取消）时：

```
1. 兑换单 status 置为 FAILED（条件：当前为 DEDUCTED 或 DELIVERING）
2. 写一条 REFUND 流水，points = points_total，reverse_of_ledger_no = deduct_ledger_no
3. 账户 points_balance += points_total
4. 兑换单 reverse_ledger_no = 新流水号
5. 把原 DEDUCT 流水扣掉的批次 used_points 减回去（按 batch_detail 逆序还）
```

约束 `ck_m19_points_exchange_reverse` 强制 `status <> 'FAILED' OR reverse_ledger_no IS NOT NULL`——只要兑换单失败，就必须有返还流水。这条 CHECK 拦住的是「代码里 catch 了异常、把状态改成 FAILED 但忘了退积分」。

**为什么返还只能追加反向流水，不能 UPDATE 原流水**

因为原流水是事实：那个时刻，那些积分确实被扣过。抹掉它就等于篡改历史。追加一条 `REFUND` 后，账本读起来是「扣了 500，又退了 500」，净额为零，审计时一眼能看懂发生了什么。如果直接 UPDATE 原流水为 0，事后没人能回答「那天到底发生了什么」。

#### 3.4.6 等级判定的边界与幂等

成长值增长可能一次跨多个门槛：

```
原成长值 = 9,800.00，本次消费 500.00 元
新成长值 = 9,800.00 + 500.00 = 10,300.00
判定：10,300.00 >= 10,000.00（金卡）且 < 30,000.00（白金）→ GOLD
level_before = 'SILVER'，level_after = 'GOLD'
```

跨两级的情况不可能发生（除非单笔成长值超过两个门槛差），但算法不依赖这个假设——`MAX(level_rank) WHERE threshold <= value` 天然支持跨多级。

**降级的合法触发**

只有管理员调整导致成长值下降时才可能降级。此时：

```
1. 调整单审批通过
2. 写 ADJUST 成长值流水，growth_delta 为负
3. 重新判定等级
4. 若 level_after 低于 level_before，调用 M03-03 等级回写接口降级
5. 发 m19.member.level_changed 事件，payload 里带 direction = 'DOWN' 与 reason
```

降级必须带 `reason`，且必须通知会员——这是 M03-05 的消息，不是静默发生的事。

| 兑换单号 | `EX` + yyyyMMdd + 6 位流水 | `EX20261021000123` | Redis `m19:code:XG:{yyyyMMdd}` INCR | 16 |
| 调整单号 | `AJ` + yyyyMM + 6 位流水 | `AJ202610000001` | Redis `m19:code:AJ:{yyyyMM}` INCR | 14 |
| 对账记录号 | `RC` + yyyyMMdd + 6 位流水 | `RC20261031000001` | Redis `m19:code:RC:{yyyyMMdd}` INCR | 16 |
| 日志号 | `LG` + yyyyMMdd + 6 位流水 | `LG20261021000001` | Redis `m19:code:LG:{yyyyMMdd}` INCR | 16 |

单号生成统一规则：

1. 用 Redis `INCR m19:code:{prefix}:{period}` 取序号；
2. 当日/当月首单时设置 TTL 到次日 00:05；
3. **不得用数据库序列拼日期**——DB 序列在实例重启、主从切换后可能回退或跳跃，导致流水号重复或出现未来日期；
4. Redis 不可用时降级为「时间戳（毫秒）+ 4 位随机」，同时写告警，并在响应头标注 `X-Id-Fallback: 1`。

兑换单号与过期批次号都用 `EX` 前缀会造成阅读混淆，因此兑换单的 Redis key 前缀用 `XG` 而单号本身仍是 `EX` 开头（共享规范 §3.3 规定兑换单号为 `EX` + yyyyMMdd + 6 位）。两者靠长度区分：批次号 14 位、兑换单号 16 位，且 `ledger_no` 与 `exchange_no` 在不同表的不同字段上，不会互相解析错。

### 4.6 关键字段读取约定

| # | 约定 | 反例 |
| --- | --- | --- |
| 1 | 余额一律从 `points_balance` 读，不实时 `SUM(ledger)` | 每次查余额都全表扫流水，P95 从 30ms 涨到 2s |
| 2 | 金额与积分一律走 `Decimal` / `NUMERIC` | 用 `float` 后 0.33 × 3 = 0.9900000000000001 |
| 3 | 比率分母为 0 时返回 `NULL`，不返回 0 | 消耗率分母为 0 显示 0%，运营误以为不消耗 |
| 4 | 无值的维度字段存空串而非 `NULL` | `NULL` 在 PG 唯一索引里互不相等，幂等约束失效 |
| 5 | 写入流水必须同时写 `balance_after` | 事后要靠对账重算，无法证明当时的余额 |
| 6 | 读流水按 `created_at` 前缀裁剪分区 | 不带时间条件全表扫，876 万行下 P95 超 5s |
| 7 | `is_deleted` 只用于配置类表 | 流水表加 `is_deleted` 等于给了「软删除」的口子 |
| 8 | 禁止 `or 0` 兜底缺失值 | 上游超时被兜成 0 元，悄悄少发积分 |

```
| 积分对账                                   对账日期 [2026-10-31]  [执行对账] [导出]     |
+----------------------------------------------------------------------------------------+

|                                          [重新对账] [追加调整单] [标记已处理]           |
```

**页面字段说明**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| 对账日期 | 日期 | `biz_date` |
| 账户余额 | 积分 | `m19_points_account.points_balance` |
| 流水代数和 | 积分 | 按 `direction` 汇总 |
| 差额 | 积分 | `account_balance - ledger_sum` |
| 差异原因 | 枚举 | `TIMING` / `MISSING_LEDGER` / `MISSING_ADJUST` / `DATA_CORRUPT` / `UNKNOWN` |
| 处理状态 | 枚举 | `OPEN` / `FIXING` / `FIXED` / `IGNORED` |

**对账 SQL（权威口径）**

```sql
WITH ledger_sum AS (
    SELECT account_id,
           SUM(CASE
                 WHEN txn_type IN ('GRANT', 'REFUND') THEN points
                 WHEN txn_type IN ('DEDUCT', 'EXPIRE', 'REVERSE') THEN -points
                 ELSE points
               END) AS sum_points
      FROM m19.m19_points_ledger
     WHERE created_at >= DATE '2026-10-31'
       AND created_at <  DATE '2026-11-01'
     GROUP BY account_id
)
SELECT a.id                AS account_id,
       a.account_no,
       a.points_balance    AS account_balance,
       COALESCE(l.sum_points, 0) AS ledger_sum,
       a.points_balance - COALESCE(l.sum_points, 0) AS diff_points
  FROM m19.m19_points_account a
  LEFT JOIN ledger_sum l ON l.account_id = a.id
 WHERE a.is_deleted = FALSE
   AND a.points_balance <> COALESCE(l.sum_points, 0);
```

`ADJUST` 落进 `ELSE points` 分支，因为它的符号由 `points` 自带正负——`-points` 会把这个符号再翻一次，导致所有负向调整的对账都差两倍。这是本子模块对账能否对上的关键口径。

**交互说明**

| # | 操作 | 行为 |
| --- | --- | --- |
| 1 | 执行对账 | 支持单日与区间，区间按日拆批 |
| 2 | 查看差异 | 只显示有差异的账户 |
| 3 | 重新对账 | 对单账户重跑，若差异消失则标 `FIXED` |
| 4 | 追加调整单 | 跳 P06 并预填会员与差额 |
| 5 | 标记已处理 | 填原因后置 `IGNORED`，需审计权限 |

**校验规则**

| # | 规则 | 不满足时 |
| --- | --- | --- |
| 1 | 对账日期必须是过去日期 | 返回 `"1904040"` |
| 2 | 同一日期同一账户不能重复发起进行中的对账 | 返回 `"1904041"` |
| 3 | 区间对账跨度不超过 31 天 | 返回 `"1904042"` |
| 4 | 标记已处理必须填原因 | 返回 `"1904043"` |
| 5 | 差异未闭环时不允许归档流水分区 | 归档脚本前置校验，不通过则拒绝 |

### 6.5 Service 层实现

```python
from __future__ import annotations

import logging
from datetime import datetime
from decimal import ROUND_HALF_UP, Decimal
from typing import Any

from sqlalchemy import text

logger = logging.getLogger(__name__)

TWO = Decimal("0.01")
ZERO = Decimal("0.00")
MIN_POINTS = Decimal("0.01")


class PointsService:
    """积分与成长值核心服务。

    所有写操作遵循三条铁律：
    1. 只往 m19_points_ledger 追加，绝不 UPDATE；
    2. 每条流水必须计算并写入 balance_after；
    3. 同一账户的写操作必须在事务内对账户行加锁。
    """

    def __init__(self, session, redis, client_m03, client_m16, client_m03_message):
        self.session = session
        self.redis = redis
        self.client_m03 = client_m03
        self.client_m16 = client_m16
        self.client_m03_message = client_m03_message

    # ------------------------------------------------------------------ 金额工具
    @staticmethod
    def round_points(value: Decimal) -> Decimal:
        """积分一律四舍五入到 2 位，禁止 float。"""
        return value.quantize(TWO, rounding=ROUND_HALF_UP)

    # ------------------------------------------------------------------ 单号
    async def next_no(self, prefix: str, period: str) -> str:
        key = f"m19:code:{prefix}:{period}"
        seq = await self.redis.incr(key)
        if seq == 1:
            await self.redis.expire(key, 3600 * 6)
        return f"{prefix}{period}{seq:06d}"

    # ------------------------------------------------------------------ 幂等
    async def _find_idempotent(self, idem_key: str) -> dict | None:
        row = self.session.execute(
            text("""
                SELECT ledger_no, points, balance_after
                  FROM m19.m19_points_ledger
                 WHERE idempotent_key = :idem_key
                 LIMIT 1
            """),
            {"idem_key": idem_key},
        ).mappings().first()
        return dict(row) if row else None

    # ------------------------------------------------------------------ 发放
    async def grant(self, payload) -> dict:
        idem_key = f"{payload.biz_type}:{payload.biz_no}:{payload.rule_code}"

        # 1. 幂等命中直接返回首次结果
        first = await self._find_idempotent(idem_key)
        if first is not None:
            logger.info("idempotent replay idem_key=%s ledger_no=%s",
                        idem_key, first["ledger_no"])
            return {
                "ledger_no": first["ledger_no"],
                "granted_points": first["points"],
                "points_balance": first["balance_after"],
                "growth_value_delta": ZERO,
                "idempotent_replay": True,
            }

        # 2. 取账户并锁行
        account = self.session.execute(
            text("""
                SELECT id, member_id, points_balance, growth_value, status
                  FROM m19.m19_points_account
                 WHERE member_id = :member_id
                   FOR UPDATE
            """),
            {"member_id": payload.member_id},
        ).mappings().first()

        if account is None:
            account = self._create_account(payload.member_id)
        elif account["status"] == "CLOSED":
            raise BusinessError("1904006", "积分账户已注销，不能发放")

        # 3. 取业务发生时点的等级快照
        level_at_txn = await self._resolve_level_at(payload.member_id, payload.occurred_at)

        # 4. 取规则与倍率
        rule, ratio = self._load_rule(payload.rule_code, level_at_txn)

        # 5. 计算
        if payload.biz_amount is None:
            points = rule["fix_points"]
        else:
            if payload.biz_amount < rule["min_biz_amount"]:
                return self._skipped_response("BELOW_MIN_AMOUNT")
            points = self.round_points(
                payload.biz_amount * ratio * rule["grow_coefficient"]
            )
        if rule["max_points_per_txn"] is not None:
            points = min(points, rule["max_points_per_txn"])
        if points < MIN_POINTS:
            return self._skipped_response("ROUNDED_TO_ZERO")

        balance_after = self.round_points(account["points_balance"] + points)

        # 6. 落流水
        ledger_no = await self.next_no("PL", payload.occurred_at.strftime("%Y%m%d"))
        self.session.execute(
            text("""
                INSERT INTO m19.m19_points_ledger
                    (ledger_no, account_id, member_id, patient_id, txn_type,
                     direction, points, balance_after, level_at_txn,
                     points_ratio_snapshot, rule_code, rule_version,
                     biz_type, biz_no, idempotent_key, occurred_at, expire_at,
                     created_at, created_by)
                VALUES
                    (:ledger_no, :account_id, :member_id, :patient_id, 'GRANT',
                     1, :points, :balance_after, :level_at_txn,
                     :ratio, :rule_code, :rule_version,
                     :biz_type, :biz_no, :idem_key, :occurred_at, :expire_at,
                     CURRENT_TIMESTAMP, :created_by)
            """),
            {
                "ledger_no": ledger_no,
                "account_id": account["id"],
                "member_id": payload.member_id,
                "patient_id": payload.patient_id,
                "points": points,
                "balance_after": balance_after,
                "level_at_txn": level_at_txn,
                "ratio": ratio,
                "rule_code": payload.rule_code,
                "rule_version": rule["rule_version"],
                "biz_type": payload.biz_type,
                "biz_no": payload.biz_no,
                "idem_key": idem_key,
                "occurred_at": payload.occurred_at,
                "expire_at": self._expire_at(payload.occurred_at),
                "created_by": 0,
            },
        )

        # 7. 建过期批次
        batch_no = await self.next_no("EX", payload.occurred_at.strftime("%Y%m%d"))
        self.session.execute(
            text("""
                INSERT INTO m19.m19_points_expire_record
                    (expire_batch_no, account_id, member_id, source_ledger_no,
                     granted_points, used_points, expired_points, expire_at,
                     status, created_at)
                VALUES
                    (:batch_no, :account_id, :member_id, :ledger_no,
                     :points, 0.00, 0.00, :expire_at, 'WAITING', CURRENT_TIMESTAMP)
            """),
            {
                "batch_no": batch_no,
                "account_id": account["id"],
                "member_id": payload.member_id,
                "ledger_no": ledger_no,
                "points": points,
                "expire_at": self._expire_at(payload.occurred_at),
            },
        )

        # 8. 成长值
        growth_delta = ZERO
        if payload.biz_amount is not None and rule["grow_coefficient"] > 0:
            growth_delta = self.round_points(
                payload.biz_amount * rule["grow_coefficient"]
            )
            await self._apply_growth(
                account=account,
                delta=growth_delta,
                source="CONSUME",
                occurred_at=payload.occurred_at,
                biz_no=payload.biz_no,
            )

        # 9. 账户派生值
        self.session.execute(
            text("""
                UPDATE m19.m19_points_account
                   SET points_balance = :balance_after,
                       total_granted  = total_granted + :points,
                       version_no     = version_no + 1,
                       updated_at     = CURRENT_TIMESTAMP
                 WHERE id = :account_id
            """),
            {
                "balance_after": balance_after,
                "points": points,
                "account_id": account["id"],
            },
        )

        self.session.commit()
        return {
            "ledger_no": ledger_no,
            "granted_points": points,
            "points_balance": balance_after,
            "growth_value_delta": growth_delta,
            "idempotent_replay": False,
        }

    # ------------------------------------------------------------------ 扣减
    async def deduct(self, payload) -> dict:
        idem_key = f"{payload.biz_type}:{payload.biz_no}:{payload.rule_code}"
        first = await self._find_idempotent(idem_key)
        if first is not None:
            return {
                "ledger_no": first["ledger_no"],
                "deducted_points": first["points"],
                "points_balance": first["balance_after"],
                "idempotent_replay": True,
            }

        account = self.session.execute(
            text("""
                SELECT id, member_id, points_balance, frozen_points, status
                  FROM m19.m19_points_account
                 WHERE member_id = :member_id
                   FOR UPDATE
            """),
            {"member_id": payload.member_id},
        ).mappings().first()

        if account is None:
            raise BusinessError("1904001", "积分账户不存在")
        if account["status"] != "ACTIVE":
            raise BusinessError("1904006", "积分账户状态不允许扣减")

        available = self.round_points(
            account["points_balance"] - account["frozen_points"]
        )
        if payload.deduct_points is None:
            raise BusinessError("1904010", "扣减积分必须由调用方明确给出")
        if available < payload.deduct_points:
            raise BusinessError(
                "1904032",
                f"可兑付积分不足，需要 {payload.deduct_points}，可用 {available}",
            )

        detail = self._consume_batches(account["id"], payload.deduct_points)
        balance_after = self.round_points(
            account["points_balance"] - payload.deduct_points
        )

        ledger_no = await self.next_no("PL", payload.occurred_at.strftime("%Y%m%d"))
        self.session.execute(
            text("""
                INSERT INTO m19.m19_points_ledger
                    (ledger_no, account_id, member_id, txn_type, direction,
                     points, balance_after, rule_code, biz_type, biz_no,
                     idempotent_key, occurred_at, batch_detail, created_at, created_by)
                VALUES
                    (:ledger_no, :account_id, :member_id, 'DEDUCT', -1,
                     :points, :balance_after, :rule_code, :biz_type, :biz_no,
                     :idem_key, :occurred_at, CAST(:batch_detail AS JSONB),
                     CURRENT_TIMESTAMP, 0)
            """),
            {
                "ledger_no": ledger_no,
                "account_id": account["id"],
                "member_id": payload.member_id,
                "points": payload.deduct_points,
                "balance_after": balance_after,
                "rule_code": payload.rule_code,
                "biz_type": payload.biz_type,
                "biz_no": payload.biz_no,
                "idem_key": idem_key,
                "occurred_at": payload.occurred_at,
                "batch_detail": self._json(detail),
            },
        )

        self.session.execute(
            text("""
                UPDATE m19.m19_points_account
                   SET points_balance = :balance_after,
                       total_consumed = total_consumed + :points,
                       version_no     = version_no + 1,
                       updated_at     = CURRENT_TIMESTAMP
                 WHERE id = :account_id
            """),
            {
                "balance_after": balance_after,
                "points": payload.deduct_points,
                "account_id": account["id"],
            },
        )
        self.session.commit()
        return {
            "ledger_no": ledger_no,
            "deducted_points": payload.deduct_points,
            "points_balance": balance_after,
            "idempotent_replay": False,
        }

    # ------------------------------------------------------------------ 成长值与等级
    async def _apply_growth(self, account: dict, delta: Decimal, source: str,
                            occurred_at: datetime, biz_no: str) -> None:
        growth_after = self.round_points(account["growth_value"] + delta)
        level_before = account.get("current_level_code") or "NORMAL"
        level_after = self._resolve_level(growth_after)

        growth_no = await self.next_no("GV", occurred_at.strftime("%Y%m"))
        self.session.execute(
            text("""
                INSERT INTO m19.m19_points_growth_ledger
                    (growth_no, account_id, member_id, source, growth_delta,
                     growth_after, level_before, level_after, biz_no,
                     occurred_at, created_at)
                VALUES
                    (:growth_no, :account_id, :member_id, :source, :delta,
                     :growth_after, :level_before, :level_after, :biz_no,
                     :occurred_at, CURRENT_TIMESTAMP)
            """),
            {
                "growth_no": growth_no,
                "account_id": account["id"],
                "member_id": account["member_id"],
                "source": source,
                "delta": delta,
                "growth_after": growth_after,
                "level_before": level_before,
                "level_after": level_after,
                "biz_no": biz_no,
                "occurred_at": occurred_at,
            },
        )

        self.session.execute(
            text("""
                UPDATE m19.m19_points_account
                   SET growth_value = :growth_after,
                       version_no   = version_no + 1,
                       updated_at   = CURRENT_TIMESTAMP
                 WHERE id = :account_id
            """),
            {"growth_after": growth_after, "account_id": account["id"]},
        )

        if level_after != level_before:
            # 等级回写放在事务外，避免 M03-03 抖动拖垮记账
            self.session.commit()
            await self._write_back_level_stepwise(
                member_id=account["member_id"],
                level_before=level_before,
                level_after=level_after,
            )

    async def _write_back_level_stepwise(
        self,
        member_id: int,
        level_before: str,
        level_after: str,
    ) -> None:
        """逐级回写等级：一次一级，绝不跨级跳。

        M03-03 的 mpi.member.level_changed 事件与等级变更日志是逐条记的，一次性传
        目标等级会让历史里少掉中间等级的全部记录（用户从 NORMAL 直跳 PLATINUM 时，
        账上看不到何时升的 SILVER、何时升的 GOLD，等级权益生效区间也无法回溯）。
        方向由 level_rank 比较决定，降级必须走 level-down，禁止用 level-up 实现降级，
        否则事件里的 operate_type 语义就是反的。
        """
        ranks = self._load_level_ranks()
        before_rank = ranks.get(level_before, 0)
        after_rank = ranks.get(level_after, 0)
        if after_rank == before_rank:
            return

        ascending = after_rank > before_rank
        path = self._build_level_path(before_rank, after_rank, ascending)
        current = level_before
        for target in path:
            try:
                await self.client_m03.write_back_level_step(
                    member_id=member_id,
                    from_level_code=current,
                    to_level_code=target,
                    direction="UP" if ascending else "DOWN",
                    reason="GROWTH_CHANGE",
                )
            except Exception as exc:  # noqa: BLE001
                logger.error(
                    "level write-back failed member_id=%s from=%s to=%s: %s",
                    member_id, current, target, exc,
                )
                break
            current = target

    def _load_level_ranks(self) -> dict:
        """取全部等级及其 rank，用于计算逐级回写路径。"""
        rows = self.session.execute(
            text("""
                SELECT level_code, level_rank
                  FROM m19.m19_points_level_rule
                 WHERE effective_from <= CURRENT_DATE
            """)
        ).all()
        return {r[0]: r[1] for r in rows}

    def _resolve_level(self, growth_value: Decimal) -> str:
        row = self.session.execute(
            text("""
                SELECT level_code
                  FROM m19.m19_points_level_rule
                 WHERE growth_threshold <= :growth_value
                   AND effective_from <= CURRENT_DATE
                 ORDER BY level_rank DESC
                 LIMIT 1
            """),
            {"growth_value": growth_value},
        ).first()
        return row[0] if row else "NORMAL"

    async def _resolve_level_at(self, member_id: int, occurred_at: datetime) -> str:
        """还原业务发生时点的会员等级快照。

        优先查 M03-03 的等级变更历史；不可用时退化为本模块成长值流水推断。
        """
        try:
            return await self.client_m03.get_level_at(member_id, occurred_at)
        except Exception as exc:  # noqa: BLE001
            logger.warning("level_at fallback member_id=%s: %s", member_id, exc)
            row = self.session.execute(
                text("""
                    SELECT level_after
                      FROM m19.m19_points_growth_ledger
                     WHERE member_id = :member_id
                       AND occurred_at <= :occurred_at
                     ORDER BY occurred_at DESC
                     LIMIT 1
                """),
                {"member_id": member_id, "occurred_at": occurred_at},
            ).first()
            return row[0] if row else "NORMAL"

    # ------------------------------------------------------------------ FIFO
    def _consume_batches(self, account_id: int, points: Decimal) -> list[dict]:
        rows = self.session.execute(
            text("""
                SELECT id, expire_batch_no, granted_points, used_points
                  FROM m19.m19_points_expire_record
                 WHERE account_id = :account_id
                   AND status IN ('WAITING', 'REMINDED')
                   AND granted_points - used_points > 0
                 ORDER BY expire_at ASC, id ASC
                   FOR UPDATE
            """),
            {"account_id": account_id},
        ).mappings().all()

        remaining = points
        detail: list[dict] = []
        for row in rows:
            if remaining <= 0:
                break
            available = row["granted_points"] - row["used_points"]
            take = min(available, remaining)
            self.session.execute(
                text("""
                    UPDATE m19.m19_points_expire_record
                       SET used_points = used_points + :take,
                           version_no  = version_no + 1,
                           updated_at  = CURRENT_TIMESTAMP
                     WHERE id = :id
                """),
                {"take": take, "id": row["id"]},
            )
            detail.append({"expire_batch_no": row["expire_batch_no"], "used": str(take)})
            remaining -= take

        if remaining > 0:
            raise BusinessError("1904009", "批次可用总额小于待扣积分，账实不符")
        return detail
```

### 7.1 Redis 键设计

| 键 | 类型 | TTL | 用途 | 失效策略 |
| --- | --- | --- | --- | --- |
| `m19:code:PL:{yyyyMMdd}` | String | 至次日 00:05 | 流水号自增 | 自然过期 |
| `m19:code:GV:{yyyyMM}` | String | 至次月 1 日 00:05 | 成长值流水号 | 自然过期 |
| `m19:code:EX:{yyyyMMdd}` | String | 至次日 00:05 | 过期批次号 | 自然过期 |
| `m19:code:XG:{yyyyMMdd}` | String | 至次日 00:05 | 兑换单号 | 自然过期 |
| `m19:code:AJ:{yyyyMM}` | String | 至次月 1 日 00:05 | 调整单号 | 自然过期 |
| `m19:code:RC:{yyyyMMdd}` | String | 至次日 00:05 | 对账记录号 | 自然过期 |
| `m19:points:balance:{member_id}` | Hash | 60s | 余额热点缓存 | 记账成功后主动删除 |
| `m19:points:rule:{rule_code}:{version}` | Hash | 300s | 规则与倍率矩阵 | 规则变更时按前缀删除 |
| `m19:points:level:threshold` | String | 300s | 门槛列表 | 门槛变更时删除 |
| `m19:points:idem:{idem_key}` | String | 24h | 幂等结果缓存 | 自然过期 |
| `m19:points:lock:account:{account_id}` | String | 10s | 账户级分布式锁 | 释放或自然过期 |
| `m19:points:reconcile:{biz_date}` | String | 24h | 对账任务去重 | 自然过期 |
| `m19:throttle:{patient_id}:{date}` | String | 至次日 00:00 | 触达频次计数 | 自然过期 |

缓存的关键原则：**余额缓存只是加速手段，权威值永远是数据库**。缓存未命中时回源查账户表，绝不因为缓存缺失返回 0。

### 7.2 Celery 异步任务

```python
from celery import shared_task

from app.core.db import session_scope
from app.services.m19.points_service import PointsService


@shared_task(bind=True, max_retries=3, default_retry_delay=60)
def task_expire_points(self, as_of_date: str) -> dict:
    """每日 00:30 执行积分过期。

    按账户分批处理，每批 500 个账户，单批失败只重试该批。
    """
    try:
        with session_scope() as session:
            service = PointsService(session, None, None, None, None)
            return service.expire_points(as_of_date=as_of_date, batch_size=500)
    except Exception as exc:  # noqa: BLE001
        raise self.retry(exc=exc)


@shared_task(bind=True, max_retries=3, default_retry_delay=300)
def task_reconcile_daily(self, biz_date: str) -> dict:
    """每日 03:00 全量对账。"""
    try:
        with session_scope() as session:
            service = PointsService(session, None, None, None, None)
            return service.reconcile(biz_date=biz_date, check_scope="GLOBAL")
    except Exception as exc:  # noqa: BLE001
        raise self.retry(exc=exc)


@shared_task(bind=True, max_retries=2, default_retry_delay=120)
def task_send_expire_remind(self, remind_stage: str) -> dict:
```

### 8.2 唯一性规则

| # | 唯一约束 | 表 | 语义 |
| --- | --- | --- | --- |
| 1 | `(idempotent_key, created_at)` | `m19_points_ledger` | 幂等三元组唯一，重复调用只落一条 |
| 2 | `(member_id)` | `m19_points_account` | 一个会员一个账户 |
| 3 | `(rule_code, rule_version, level_code)` | `m19_points_rule_item` | 一规则一版本一等级一个倍率 |

| 7 | `(biz_date, check_scope, account_id)` | `m19_points_reconcile` | 同账户同日只对一次 |

幂等键的构成必须写清楚，否则「唯一」形同虚设：

```
idempotent_key = biz_type + ':' + biz_no + ':' + rule_code
例：OUTPATIENT_SETTLEMENT:ST20261021000123:PR_OUTPATIENT_VISIT
```

三个字段任一为空时拼接会产生连续冒号（如 `::PR_X`），导致不同业务撞同一个键。因此约束 `ck_m19_points_ledger_idem_fields` 强制：`GRANT`/`DEDUCT`/`REFUND`/`REVERSE` 四种类型下三个字段都不允许为空。

**空串与 NULL 必须同等对待。** 只判 `IS NOT NULL` 是不够的：调用方传 `biz_type=""`、`biz_no="ST20261021000123"`、`rule_code=""` 时，三个字段都非 NULL，`IS NOT NULL` 一路放行，幂等键拼出来是 `":ST20261021000123:"`；下一次另一个调用方传 `biz_type=""`、`biz_no=""`、`rule_code="PR_X"`，拼出来是 `"::PR_X"`——两个完全不同的业务，键不同但**都在漏字段**，而真正该命中的 `"OUTPATIENT_SETTLEMENT:ST20261021000123:PR_OUTPATIENT_VISIT"` 永远拼不出来。后果是同一笔结算被重复发放，或者真实发放被一个残缺键静默吞掉。

因此约束在 `IS NOT NULL` 之外追加 `btrim(...) <> ''` 三个条件，纯空白串（`"  "`）也一并拒绝：

```sql
ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_idem_fields
    CHECK (
        (idempotent_key IS NULL
            AND biz_type IS NULL AND biz_no IS NULL AND rule_code IS NULL)
        OR (idempotent_key IS NOT NULL
            AND biz_type IS NOT NULL AND biz_no IS NOT NULL AND rule_code IS NOT NULL
            AND btrim(biz_type) <> ''
            AND btrim(biz_no)   <> ''
            AND btrim(rule_code) <> '')
    );
```

应用层在拼接前先做同样校验，命中即返回 `"1904011"`，不要指望把非法输入丢给数据库抛 23514——P-03 的调用方是 M16 结算，它需要的是一个能读懂的业务错误码，而不是一个裸的约束冲突。

### 8.7 并发控制

本子模块对同一积分账户的写操作**一律采用悲观行锁 `SELECT ... FOR UPDATE`**，不使用乐观锁 `version_no` 作为主控制手段。理由如下。

**为什么选悲观锁而不是乐观锁**

积分扣减的典型冲突概率不低：一个会员在收银台兑换实物、同时在前台下单用积分抵扣，两次操作可能在同一秒到达。乐观锁的实现是「读余额 → 计算 → 带 `version_no` 条件更新 → 若影响行数为 0 则重试」。问题在于重试时**已经扣除的批次需要回滚重来**，而批次表是普通表、FIFO 位置会影响结果——重试路径复杂且容易漏。

悲观锁把整个「读余额 → 扣批次 → 写流水 → 更新余额」串行化，实现简单、正确性容易论证。代价是并发下会排队，但积分扣减是低频操作（单会员每秒 1 次已是极端），排队时间在毫秒级。

**并发正确性论证**

设两个并发请求 A 与 B 对同一账户各扣 500 分，账户余额 800 分。

| 时刻 | 请求 A | 请求 B | 账户余额 | 说明 |
| --- | --- | --- | --- | --- |
| T1 | 开始事务 | — | 800.00 | — |
| T2 | `SELECT ... FOR UPDATE` 获得行锁 | — | 800.00 | B 阻塞等待 |
| T3 | 校验 800.00 ≥ 500.00 通过 | — | 800.00 | — |
| T4 | 扣批次、写流水、余额置 300.00 | — | 300.00 | — |
| T5 | 提交，释放锁 | — | 300.00 | — |
| T6 | — | 获得行锁 | 300.00 | — |
| T7 | — | 校验 300.00 ≥ 500.00 **失败** | 300.00 | 返回 `"1904032"` |
| T8 | — | 回滚 | 300.00 | 无任何写入 |

如果没有行锁，两个请求可能都在 T3 读到 800.00 并通过校验，各自扣 500，最终余额变成 -200。`CHECK (balance_after >= 0)` 会在写流水时拦截，但那是**事后**拦截——错误信息是「约束违反」，而不是「积分不足」，用户体验与可诊断性都差。

**死锁预防**

加锁顺序统一为「账户行 → 批次行」。批量过期任务按 `account_id ASC` 排序逐个加锁，避免两个批处理互等。

**version_no 的角色**

`m19_points_account.version_no` 仍然保留，但只用于两件事：

1. 乐观并发检测的辅助——更新时带上 `WHERE version_no = :expected`，若影响行数为 0 说明有意外并发，记告警并按当前值重算；
2. 对外提供「数据是否变化」的判断依据，供前端做冲突提示。

它**不是**主要的并发控制手段，也不是正确性的依赖。

**幂等与并发的关系**

幂等键唯一约束在并发重复调用时提供第二层保护：两个相同 `(biz_type, biz_no, rule_code)` 的请求如果同时到达，行锁会让它们串行执行，第二个请求在锁释放后重新查幂等键时会命中第一个的结果并返回 `idempotent_replay = true`。若 Redis 缓存未命中且锁粒度不足，数据库唯一约束会抛冲突，应用捕获后重新查一次并返回首次结果。

关于 U-02 / U-03 的说明：M03-03 真实提供的是**两个方向各一个接口**——`POST /internal/v1/member/{id}/level-up`（等级升级，M19 调用）与 `POST /internal/v1/member/{id}/level-down`（等级降级，M19 调用），见其 §10.3 内部契约表。共享规范 V1.0 曾登记 `/internal/v1/mpi/members/{member_id}/level`，经 lead 核实该路径为误记（`/internal/v1/mpi/` 前缀在 M03 侧不存在），已更正，本子模块按 `level-up` / `level-down` 两条真实接口实现，不做双路径兼容。

**两条硬约束（lead 裁决，已写入 §8.4 与客户端实现）：**

1. **不允许用 `level-up` 实现降级。** 降级必须走 `level-down`，否则 M03-03 的 `mpi.member.level_changed` 事件会携带错误的 `operate_type`，下游（会员详情页、权益引擎、运营看板）拿到的事件语义就是反的。
2. **跨级跳升由 M19 侧循环调用 `level-up` 逐级完成，一次一级。** M03-03 的升级事件与等级变更日志是逐条记的，一次性传 `target_level_code` 跨级跳会让历史里少掉中间等级的全部记录——用户从普通直接升白金，账上就看不到「什么时候升的银卡、什么时候升的金卡」，等级权益的生效区间也没法回溯。

### 10.4 事件订阅

| 事件 | 来源 | 处理 |
| --- | --- | --- |
| `mpi.member.created` | M03-03 | 自动创建积分账户，`status = ACTIVE` |
| `mpi.member.level_changed` | M03-03 | 刷新 `m19:points:rule:*` 与等级缓存 |
| `mpi.patient.merged` | M03-02 | **主触发点**：患者合并后积分账户重定向到主患者对应的会员，`merged_to_member_id` 记录来源；被合并账户置 `CLOSED`，余额迁移到主账户并追加一条 `ADJUST` 流水 |
| `mpi.member.merged` | M03-03 | 会员级合并重定向（会员主档自己合并时），幂等处理：账户已重定向则直接返回，不重复追加 `ADJUST` 流水 |
| `m16.settlement.completed` | M16 | 调 P-03 发放积分 |
| `m16.settlement.refunded` | M16 | 调 P-04 的冲正分支，落 `REVERSE` 流水 |
| `m19.followup.executed` | M19-02 | 按 `PR_FOLLOWUP_DONE` 规则发放互动积分 |

患者合并的处理是本子模块最容易漏的一处：如果合并后账户没跟着走，用户在新会员号下查不到积分，旧账户余额成为无人认领的死账。处理方式是「迁移 + 追加流水 + 关闭旧账户」，而不是直接改旧账户的 `member_id`——后者会让历史流水的归属错乱。两个合并事件的关系：`mpi.patient.merged` 由 M03-02 在患者匹配合并时发布，是主触发点；`mpi.member.merged` 由 M03-03 在会员主档自身合并时发布。两者处理逻辑相同，靠「账户已重定向则直接返回」的幂等判断避免重复迁移，**不能只订阅其中一个**——只订 `member.merged` 会漏掉绝大多数患者合并场景。

## 11. 异常与日志

### 11.1 异常分类

| # | 异常类别 | 示例 | 处理方式 | 是否告警 |
| --- | --- | --- | --- | --- |
| 1 | 参数异常 | 期间格式错、倍率超区间 | 返回 4xx 与具体错误码 | 否 |
| 2 | 业务规则异常 | 余额不足、状态不允许 | 返回 409 与错误码 | 否 |

| 5 | 账实不符 | 批次总额小于待扣积分 | 立即中止事务，落对账，告警 | 是 |

| 7 | 数据库异常 | 唯一约束冲突、连接断开 | 唯一冲突转幂等返回，其他重试 | 是 |
| 8 | 定时任务失败 | 过期任务异常 | 重试 3 次，仍失败告警 | 是 |

## 附录 A 积分规则配置手册

### A.1 规则类型选择指引

| 业务场景 | 推荐规则类型 | 理由 |
| --- | --- | --- |
| 门诊结算 | `BY_AMOUNT` | 金额差异大，按比例才公平 |
| 住院结算 | `BY_AMOUNT` | 同上 |
| 随访完成 | `BY_ACTION` | 与金额无关，鼓励行为 |
| 完善资料 | `BY_ACTION` | 一次性行为 |
| 连续签到 | `FIXED` | 固定值，配合每日次数上限 |
| 活动奖励 | `BY_TIMES` 或 `FIXED` | 按参与次数或固定值 |

### A.2 倍率设计建议

| 等级 | 建议倍率区间 | 说明 |
| --- | --- | --- |
| 普通会员 | 0.05 ~ 0.10 | 基础倍率，体现「有积分」即可 |
| 银卡 | 0.10 ~ 0.20 | 有明显差异但不夸张 |
| 金卡 | 0.20 ~ 0.35 | 主要激励层级 |
| 白金 | 0.35 ~ 0.50 | 顶级，覆盖用户占比应小于 2% |

倍率差距过大（例如银卡 0.1、金卡 1.5）会导致同一笔消费在不同等级下发放 15 倍差异，一旦等级判定出错，差错金额被放大 15 倍。

### A.3 兜底行设置

每条规则必须有且仅有一行 `is_fallback = TRUE`。兜底行的 `level_code` 固定为 `*`，倍率建议取最低等级倍率。当 M03-03 新增等级而 M19 尚未配置倍率时，兜底行保证发放照常进行，而不是静默按 0 倍率少发。同时每日 02:00 的任务会扫描缺失等级并告警，推动运营补配。

## 附录 B 积分账本对账手册

### B.1 每日对账流程

```
00:30  执行过期任务（改变余额与流水）
02:00  校验等级清单完整性
03:00  全量对账（校验余额与流水一致）
03:30  差异告警推送财务
09:00  财务处理差异
```

顺序不可颠倒：过期先于对账，否则当日的过期扣减会被当成差异。

### B.2 差异原因判定

| 差异特征 | 可能原因 | 处理 |
| --- | --- | --- |
| 差额为正且流水缺失同额记录 | 余额被直接更新未写流水 | 补 `ADJUST` 流水并追查代码 |
| 差额为负且存在未提交流水 | 并发期间时序差 | 重新对账 |
| 差额等于某笔流水的两倍 | `ADJUST` 符号被翻 | 检查对账 SQL 的 `ELSE` 分支 |
| 差额为零但流水总额异常 | 数据损坏 | 从备份恢复并逐笔核对 |

### B.3 对账口径说明

对账的权威口径是 `direction` 之外的第三种表达：

```
GRANT   → +points
REFUND  → +points
DEDUCT  → -points
EXPIRE  → -points
REVERSE → -points
ADJUST  →  points（符号自带）
```

任何一种实现只要把 `ADJUST` 也做了取负，负向调整就会差两倍，正向调整会被当成负向。这是对账对不上的第一大原因。

## 附录 C 常见错误与防范

| # | 错误 | 后果 | 防范 |
| --- | --- | --- | --- |
| 1 | 直接 `UPDATE` 账户余额 | 账实不符且无痕迹 | 所有余额变更必须伴随流水；`REVOKE` + 审计 |
| 2 | 实时查当前等级算倍率 | 升级后历史消费被重算 | `level_at_txn` 快照 + AC-12 用例 |
| 3 | 幂等键只用 `biz_no` | 不同规则的同一单据互相压制 | 三元组唯一约束 |
| 4 | 用 `float` 算积分 | 小数累积误差 | `NUMERIC` + `Decimal` |
| 5 | 扣减不做行锁 | 并发下负余额 | `SELECT FOR UPDATE` + `CHECK` |
| 6 | 兑换失败忘记返还 | 积分被吞 | `ck_m19_points_exchange_reverse` |
| 7 | 过期按批次倒序扣 | 用户未用最早到期的积分 | FIFO 按 `expire_at ASC` |
| 8 | 成长值可减 | 用户降级后升不回来 | `ck_m19_points_growth_ledger_monotonic` |
| 9 | 提醒不过闸门 | 骚扰用户、投诉 | 三道闸门 + 拦截留痕 |
| 10 | 患者合并后账户不迁移 | 积分成为死账 | `merged_to_member_id` + 迁移流水 |

## 附录 D 关键 SQL 汇总

**账户余额与流水查询（按会员）**

```sql
SELECT a.account_no,
       a.points_balance,
       a.frozen_points,
       a.growth_value,
       a.status,
       l.ledger_no,
       l.txn_type,
       l.points,
       l.balance_after,
       l.level_at_txn,
       l.occurred_at
  FROM m19.m19_points_account a
  LEFT JOIN m19.m19_points_ledger l
         ON l.account_id = a.id
        AND l.created_at >= TIMESTAMP '2026-10-01 00:00:00'
        AND l.created_at <  TIMESTAMP '2026-11-01 00:00:00'
 WHERE a.member_id = 88001
 ORDER BY l.occurred_at DESC
 LIMIT 20;
```

**积分负债计算**

```sql
SELECT SUM(a.points_balance)                        AS total_unconsumed_points,
       SUM(a.points_balance) * 0.010000             AS liability_amount,
       COUNT(*) FILTER (WHERE a.points_balance > 0) AS members_with_balance
  FROM m19.m19_points_account a
 WHERE a.is_deleted = FALSE
   AND a.status <> 'CLOSED';
```

**消耗率与过期率**

```sql
SELECT SUM(points) FILTER (WHERE txn_type = 'GRANT')  AS issued_points,
       SUM(points) FILTER (WHERE txn_type = 'DEDUCT') AS consumed_points,
       SUM(points) FILTER (WHERE txn_type = 'EXPIRE') AS expired_points,
       ROUND(
           SUM(points) FILTER (WHERE txn_type = 'DEDUCT')
           / NULLIF(SUM(points) FILTER (WHERE txn_type = 'GRANT'), 0),
           6
       ) AS consume_rate
  FROM m19.m19_points_ledger
 WHERE created_at >= TIMESTAMP '2026-10-01 00:00:00'
   AND created_at <  TIMESTAMP '2026-11-01 00:00:00';
```

`NULLIF(..., 0)` 保证分母为 0 时返回 `NULL` 而不是抛除零错误，也不是返回 0。
