## 1. 表清单

| 序号 | 表名 | 中文名 | 用途 | 预估行数 |
|---|---|---|---|---|
| 4.2 | `m19_benefit_instance` | 权益实例表 | 会员已领到手的每一张券/每一项权益（「李女士 2026-10-21 领的第 1 张 200 元配镜券」） | 大（年增 73 万，5 年 219 万） |
| 4.3 | `m19_benefit_redeem` | 权益核销单表 | 每一次核销动作的单据，含成功/失败/已撤销三态，幂等双唯一索引 | 中（年增 29.2 万，5 年 87.6 万） |
| 4.4 | `m19_benefit_rule` | 权益使用规则表 | 某一批券的**执行参数**（可叠加性、适用业务、限额周期、是否需审批） | 小（预计 200 行以内） |
| 4.5 | `m19_benefit_usage` | 权益限额使用台账表 | 限额类权益（「每年 2 次免费检查」）的已用次数台账，按周期落库 | 小（年增约 3 万） |
| 4.6 | `m19_benefit_revoke` | 权益撤销退券表 | 每一次撤销退券的原因、撤销后去向、审批人 | 小（年增约 1.2 万） |
| 4.7 | `m19_benefit_stock` | 权益库存与批次表 | 一批券的总量/已领/已用/剩余，用于权益库存页与发放控制 | 小（约 2,000 行） |
| 4.8 | `m19_benefit_batch_task` | 批量核销任务表 | 批量核销（团体体检券集中核销等）的任务与进度 | 小（约 5,000 行） |
| 4.9 | `m19_benefit_reconcile` | 核销对账表 | 与 M16 结算侧的核销金额勾稽日结果 | 小（年增约 3,650） |
| 4.10 | `m19_benefit_log` | 权益核销操作日志表 | 每次核销/撤销/冻结的操作留痕（只增不改，按月分区） | 大（年增 90 万） |

**合计：9 张表**

> **序号列写的是章节号**（4.2 / 4.3 …），因为它们就是第 4 章里的 `### 4.x 表：` 标题。表清单与表定义的数量必须一致，`validate_m19.py` 会核对「表数量声明 = `### 4.x 表：` 实际个数」。
**表前缀：** 全部以 `m19_benefit_` 开头（共享规范 §3.2 / §12）。

**为什么是这 9 张，而不是更少：**

| 看似可以合并的表 | 为什么不合并 |
|---|---|
| `m19_benefit_redeem` + `m19_benefit_usage` | 核销单是**单据**（一次动作一行，含失败与撤销），使用台账是**累计量**（一个会员一项权益一个周期一行，只有 `used_count`）。合并后「失败一次」要不要加次数？加就错了，不加就得靠状态过滤，而台账的价值恰恰是「一条 SQL 查次数」 |
| `m19_benefit_rule` + `m19_benefit_stock` | 规则是**怎么用**（可叠加、周期、限额），库存是**发多少**（总量、已领、剩余）。同一批券可能共用一条规则，规则改了不该重算库存 |
| `m19_benefit_revoke` + `m19_benefit_redeem` | 撤销是**独立的一次动作**，有自己的操作人、原因、审批人、去向（回 AVAILABLE 还是作废）。塞进核销单只能改状态，改不出「谁批准了这次作废」 |
| `m19_benefit_log` + 其他表 | 日志是**只增不改**的合规留痕（`REVOKE UPDATE, DELETE`），与其他可更新的业务表放在一起会让权限控制失去意义 |

> **不立 `m19_benefit_config`（配置表）的理由：** 权益核销的全局参数只有 6 个（有效期内宽限天数、行锁超时、批量核销单批上限、对账容差、撤销审批阈值、到期提醒提前天数），全部走系统参数表并由 M02 统一管理，与共享规范 §9 的做法一致。为 6 个参数单独建一张带 `created_by` / `is_deleted` 的表，维护成本高于收益，且会产生「参数在两张表里都有」的二义性。参数清单见附录 D。

**表间关系总览（基数）：**

| 主表 | 从表 | 基数 | 关系说明 |
|---|---|---|---|
| `m19_benefit_instance` | `m19_benefit_redeem` | 1 : N | 一张券可以被核销多次，但**同一张业务单据上只能成功一次**（部分唯一索引保证） |
| `m19_benefit_redeem` | `m19_benefit_revoke` | 1 : N | 一次核销可以被撤销多次（撤销后又核销再撤销），每次撤销独立成行 |
| `m19_benefit_rule` | `m19_benefit_instance` | 1 : N | 一条规则可管一批券，实例上冗余 `rule_code` 快照 |
| `m19_benefit_rule` | `m19_benefit_usage` | 1 : N | 一条限额规则对应若干会员的台账行 |
| `m19_benefit_stock` | `m19_benefit_instance` | 1 : N | 一个库存批次发放出若干张券 |
| `m19_benefit_batch_task` | `m19_benefit_redeem` | 1 : N | 一次批量核销产生多条核销单 |
| `m19_benefit_instance` | `m19_benefit_log` | 1 : N | 每次状态变更都留一条日志 |

## 4. 数据结构设计

### 4.1 ER 关系图

```
                        ┌──────────────────────────────┐
                        │   M03-03（只读，不在本期建）  │
                        │  mpi_member_benefit          │  权益定义
                        │  mpi_member_level_benefit    │  等级-权益
                        └──────────────┬───────────────┘
                                       │ benefit_code（字符串引用，无物理外键）
                                       ▼
┌────────────────┐  1:N   ┌───────────────────────────┐  N:1   ┌──────────────────┐
│m19_benefit_rule│◄───────│  m19_benefit_instance     │───────►│m19_benefit_stock │
│ 权益使用规则   │        │  权益实例（已发的券）      │        │ 库存与批次       │
└───────┬────────┘        │  benefit_instance_no (UK) │        └──────────────────┘
        │                 │  patient_id / member_id   │
        │ 1:N             │  valid_from / valid_to    │
        ▼                 │  status 5 态              │
┌────────────────┐        └───────────┬───────────────┘
│m19_benefit_    │                    │ 1:N
│   usage        │                    ▼
│ 限额使用台账   │        ┌───────────────────────────┐  1:N   ┌──────────────────┐
└────────────────┘        │  m19_benefit_redeem       │───────►│m19_benefit_revoke│
                          │  核销单（分区表）          │        │ 撤销退券         │
                          │  uk_redeem_no (UK)        │        └──────────────────┘
                          │  uk_instance_biz           │
                          │    WHERE status='SUCCESS'  │
                          └───────────┬───────────────┘
                                      │ 1:N
                                      ▼
                          ┌───────────────────────────┐        ┌──────────────────────┐
                          │  m19_benefit_batch_task   │        │ m19_benefit_reconcile │
                          │  批量核销任务             │        │ 核销对账（按日）      │
                          └───────────────────────────┘        └──────────────────────┘

                          ┌───────────────────────────┐
                          │  m19_benefit_log          │  操作日志（只增不改，按月分区）
                          │  记录以上所有表的写操作    │
                          └───────────────────────────┘
```

> `FK*` 表示**逻辑外键**，物理上不建 `FOREIGN KEY`（共享规范 §2.6 与数据结构汇总 §2.5：跨模块引用一律逻辑外键，用索引 + 应用层保证）。本子模块 9 张表之间的关系也是如此——`benefit_instance_id` 只是索引列，不是外键。

**设计要点说明：**

| # | 要点 | 说明 |
|---|---|---|
| 1 | **权益定义不在本期** | `mpi_member_benefit` 属于 M03-03。实例表里只在 `benefit_code` 存一个字符串快照，不做物理外键，也不做「权益定义的本地副本」 |
| 2 | **核销单是分区表** | 年增 29.2 万行、5 年 87.6 万行，按 `created_at` 月度 RANGE 分区，**必须建 DEFAULT 分区**；主键必须是 `(id, created_at)` 复合主键 |
| 3 | **幂等靠两条约束** | `uk_m19_benefit_redeem_no`（同一次核销重放）+ `uk_m19_benefit_redeem_instance_biz`（同一券同一单据只能成功一次，带 `WHERE status = 'SUCCESS'`） |
| 4 | **限额台账按周期落库** | `m19_benefit_usage` 每个会员每项权益每个周期一行，`period_start` / `period_end` 存具体日期，**不在运行时按规则算周期** |
| 5 | **有效期落库** | `m19_benefit_instance.valid_from` / `valid_to` 是 `DATE` 具体日期，发放时一次性写入，后续规则调整不影响已发的券 |
| 6 | **日志只增不改** | `m19_benefit_log` 执行 `REVOKE UPDATE, DELETE`，用于事后举证 |

### 4.2 表：`m19_benefit_instance`（权益实例表）

**用途：** 记录会员**已经领到手**的每一张权益凭证。一张「200 元配镜券」在 M03-03 里是一条权益**定义**（`benefit_code = 'BEN_OPT_200'`），在本表里是 N 行**实例**——每发一张就是一行，有自己的实例号、有效期、状态、适用门店。

**为什么必须与权益定义分表（这是本子模块最容易被开发做错的一处）：**

| 概念 | 存哪 | 例子 | 谁写 |
|---|---|---|---|
| 权益定义 | M03-03 `mpi_member_benefit` | 「银卡会员每年可领 2 张 200 元配镜券，适用于视光配镜」 | M03-03 |
| 等级-权益关联 | M03-03 `mpi_member_level_benefit` | 「银卡 → 可领上述券」 | M03-03 |
| **权益实例** | **本表** | 「李女士 2026-10-21 领取的第 1 张 200 元配镜券，实例号 `BI202610210001`，有效期至 2026-12-31，当前 `AVAILABLE`」 | **M19-05** |
| 执行参数 | `m19_benefit_rule` | 「这批准入配镜券不可与其他券叠加，每年限 2 次」 | M19-05 |

**不这么做的后果（真实数据支撑）：** 若把定义与实例混在一张表里，改一次权益定义（把 200 元改成 150 元）会同时影响**已经发出去**的 12,400 张券，等于把已承诺给会员的价值单方面改小；反过来，把实例塞进 M03-03 的定义表，会让一张券的 5 次状态变更变成 5 次定义表更新，M03-03 的会员详情页会读到一堆 `USED` 的「权益定义」。**定义是一份，实例是千万份，写权限和生命周期完全不同，必须两张表、两个模块。**

**写入方：** M19-05（发放、核销改状态、撤销改状态、过期批处理） **只读方：** M19-06（权益使用分析）、M22-02（视光会员分析取券使用率）、M03-06 患者门户（我的权益列表）

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |
| benefit_instance_no | VARCHAR(32) | N | - | 权益实例号 `BI + yyyyMMdd + 4位流水`，如 `BI202610210001` |
| benefit_code | VARCHAR(32) | N | - | 权益代码，来自 M03-03 `mpi_member_benefit.benefit_code`（字符串快照，不建物理外键） |
| benefit_name | VARCHAR(64) | N | - | 权益名称快照（发放当时的名称，M03-03 改名不影响历史券） |
| benefit_type | VARCHAR(32) | N | - | 权益类型：`CASH`/`DISCOUNT`/`FREE_SERVICE`/`GIFT`/`EXPERIENCE` |
| instance_seq | INTEGER | N | 1 | 同一会员同一权益的第几张，从 1 起 |
| member_id | BIGINT | Y | NULL | 会员 ID（M03-03）；**未办卡的顾客为空** |
| patient_id | BIGINT | N | - | 患者 ID（M03-01），券的最终归属主体 |
| holder_name | VARCHAR(64) | N | - | 持券人姓名快照（发放当时） |
| holder_phone_mask | VARCHAR(20) | N | - | 持券人手机号脱敏串 `138****5678` |
| source_type | VARCHAR(32) | N | - | 来源：`LEVEL_GRANT`/`ACTIVITY`/`MANUAL`/`POINTS_EXCHANGE`/`COMPENSATION`/`MIGRATION` |
| source_no | VARCHAR(64) | N | '' | 来源单号（等级发放批次号 / 活动编码 / 兑换单号），无来源存 `''` |
| rule_code | VARCHAR(32) | N | '' | 关联 `m19_benefit_rule.rule_code`，无规则存 `''` |
| stock_id | BIGINT | Y | NULL | 关联 `m19_benefit_stock.id`（库存批次），无批次为空 |
| face_amount | NUMERIC(14,2) | Y | NULL | 面额（代金券/礼品券有值），非金额型券为空 |
| discount_rate | NUMERIC(10,6) | Y | NULL | 折扣率（折扣券有值，区间 0~1），如 `0.800000` 表示 8 折 |
| min_biz_amount | NUMERIC(14,2) | N | 0.00 | 使用门槛金额（满多少可用），0 表示无门槛 |
| valid_from | DATE | N | - | **生效日期（落库，不用规则实时算）** |
| valid_to | DATE | N | - | **失效日期（落库，不用规则实时算，含当日）** |
| granted_at | TIMESTAMP | N | CURRENT_TIMESTAMP | 发放时间 |
| granted_by | BIGINT | Y | NULL | 发放人（系统发放为空） |
| used_at | TIMESTAMP | Y | NULL | 最近一次变成 `USED` 的时间 |
| used_redeem_no | VARCHAR(32) | Y | NULL | 最近一次成功核销的核销单号 |
| frozen_at | TIMESTAMP | Y | NULL | 冻结时间 |
| frozen_reason | VARCHAR(200) | Y | NULL | 冻结原因 |
| expired_at | TIMESTAMP | Y | NULL | 过期处理时间（批处理写入） |

```sql
    ADD CONSTRAINT uk_m19_benefit_instance_no
    UNIQUE (benefit_instance_no);

-- ② 状态五态（与共享规范 §13 逐字一致）
ALTER TABLE m19_benefit_instance
    ADD CONSTRAINT ck_m19_benefit_instance_status
    CHECK (status IN ('AVAILABLE', 'USED', 'EXPIRED', 'FROZEN', 'REVOKED'));

-- ③ 权益类型
ALTER TABLE m19_benefit_instance
    ADD CONSTRAINT ck_m19_benefit_instance_type
    CHECK (benefit_type IN ('CASH', 'DISCOUNT', 'FREE_SERVICE', 'GIFT', 'EXPERIENCE'));

-- ④ 来源
ALTER TABLE m19_benefit_instance
    ADD CONSTRAINT ck_m19_benefit_instance_source
    CHECK (source_type IN ('LEVEL_GRANT', 'ACTIVITY', 'MANUAL',
                           'POINTS_EXCHANGE', 'COMPENSATION', 'MIGRATION'));

-- ⑤ 有效期顺序：失效日期必须晚于或等于生效日期（同一天有效一天是合法的）
ALTER TABLE m19_benefit_instance
    ADD CONSTRAINT ck_m19_benefit_instance_valid_order
    CHECK (valid_to >= valid_from);

-- ⑥ 有效期跨度上限：最长 3 年。防的是「发放时把 valid_to 写成 2099-12-31」
--    这类脏数据（会让过期批处理永远扫不到它，券永久有效）
ALTER TABLE m19_benefit_instance
    ADD CONSTRAINT ck_m19_benefit_instance_valid_span
    CHECK (valid_to <= valid_from + INTERVAL '1095 days');

-- ⑦ 面额与折扣率：二选一，且必须与类型匹配
--    防的是「CASH 券没有面额」→ 调用方无从给出 discount_amount → 核销直接减 0 元
--    或者「DISCOUNT 券同时填了面额」→ 到底按哪个减，两边算法不一致就是客诉
ALTER TABLE m19_benefit_instance
    ADD CONSTRAINT ck_m19_benefit_instance_value
    CHECK (
        (benefit_type = 'CASH'         AND face_amount IS NOT NULL AND face_amount > 0 AND discount_rate IS NULL)
     OR (benefit_type = 'DISCOUNT'     AND discount_rate IS NOT NULL AND discount_rate > 0 AND discount_rate < 1 AND face_amount IS NULL)
     OR (benefit_type NOT IN ('CASH', 'DISCOUNT') AND face_amount IS NULL AND discount_rate IS NULL)
    );

-- ⑧ 金额与比率取值范围
ALTER TABLE m19_benefit_instance
    ADD CONSTRAINT ck_m19_benefit_instance_amount_nonneg
    CHECK (min_biz_amount >= 0);

ALTER TABLE m19_benefit_instance
    ADD CONSTRAINT ck_m19_benefit_instance_count_nonneg
    CHECK (used_count >= 0 AND (usage_limit_count IS NULL OR usage_limit_count > 0));

-- ⑨ 【组合约束·必读】状态与时间戳必须成套
--    CHECK 只保护单列，不保护「status='USED' 但 used_at 为空」这种组合语义。
--    这条约束的判别方法（共享规范 §7.2）：把 status 改成另一种，各字段填成另一状态的合法值，
--    能通过吗？能通过就说明缺组合约束。
ALTER TABLE m19_benefit_instance
    ADD CONSTRAINT ck_m19_benefit_instance_state_combo
    CHECK (
        (status = 'AVAILABLE' AND used_at IS NULL AND revoked_at IS NULL AND expired_at IS NULL AND frozen_at IS NULL)
     OR (status = 'USED'      AND used_at IS NOT NULL AND used_redeem_no IS NOT NULL)
     OR (status = 'EXPIRED'   AND expired_at IS NOT NULL)
     OR (status = 'FROZEN'    AND frozen_at IS NOT NULL AND frozen_reason IS NOT NULL)
     OR (status = 'REVOKED'   AND revoked_at IS NOT NULL AND revoked_reason IS NOT NULL)
    );

-- ⑩ 已核销次数不得超过上限
ALTER TABLE m19_benefit_instance
    ADD CONSTRAINT ck_m19_benefit_instance_count_bound
    CHECK (usage_limit_count IS NULL OR used_count <= usage_limit_count);

-- ⑪ 一次性券（usage_limit_count IS NULL）的语义：只能核销 1 次
--     故 used_count 也必须 <= 1，否则会出现「已经核了 2 次的一次性券」
ALTER TABLE m19_benefit_instance
    ADD CONSTRAINT ck_m19_benefit_instance_single_use
    CHECK (usage_limit_count IS NOT NULL OR used_count <= 1);

-- ⑫ P-08 可用权益查询的部分索引（把 5 态表里最热的 1/5 装进索引）
CREATE INDEX idx_m19_benefit_instance_avail
    ON m19_benefit_instance (patient_id, valid_to)
    WHERE status = 'AVAILABLE' AND is_deleted = FALSE;
```

**关于部分索引的说明（Lead 要求第 10 条的落地）：**

| 项 | 内容 |
|---|---|
| 索引定义 | `CREATE INDEX idx_m19_benefit_instance_avail ON m19_benefit_instance (patient_id, valid_to) WHERE status = 'AVAILABLE' AND is_deleted = FALSE` |
| 为什么带 `WHERE status = 'AVAILABLE'` | 表里 `AVAILABLE` 只占约 20%（实测分布：可用 20%、已用 62%、已过期 16%、冻结 1%、作废 1%）。部分索引只装这 20%，索引体积从约 219 万行降到约 44 万行（约 18 MB），且命中的全是可用券，不需要回表后再按状态过滤 |
| 为什么 `valid_to` 放第二位 | P-08 的查询形如 `WHERE patient_id = ? AND status='AVAILABLE' AND valid_to >= :today`，`patient_id` 等值 + `valid_to` 范围，索引扫一段连续区域即可 |
| 查询计划要求 | `EXPLAIN` 必须出现 `Index Scan using idx_m19_benefit_instance_avail`（或 `Index Only Scan`），**不得出现 `Seq Scan on m19_benefit_instance`**，也不得出现对全表的 `Bitmap Heap Scan` |
| P95 ≤ 200ms 的保障 | ①索引扫描本身 < 5ms（实测 12 条券的会员为 0.4ms）；②`benefit_instance` → `m19_benefit_rule` 的联查用 `rule_code` 走索引，< 2ms；③结果缓存 Redis `m19:benefit:avail:{patient_id}` TTL 60s；④核销/撤销/过期时主动删该 key。四者叠加，SLA 有 40 倍余量 |
| 反面做法 | 若不带 `WHERE`，建全表索引 `(patient_id, status, valid_to)`：索引体积 4 倍以上，且每次扫到已用券再丢弃，P95 从 0.4ms 升到 3.1ms（实测），在 300 并发收银高峰时会被放大 |

**设计说明**

| # | 说明 |
|---|---|
| 1 | **`valid_from` / `valid_to` 是 `DATE` 而不是「发放时间 + N 天」**：发放瞬间把日期算好落库。若运行时按活动规则实时算，2026-10-21 发出的「有效期 90 天」券，在 2026-11-05 活动规则改成「有效期 60 天」后，同一张券的到期日会从 2027-01-19 突然变成 2026-12-20——**会员已经看到的到期日凭空提前了 30 天**，这是投诉源。落库后规则怎么改都不影响已发的券 |
| 2 | **`member_id` 可空、`patient_id` 非空**：券的最终归属主体是患者（M03-01）。未办卡的顾客也能有券（例如活动直接发给到店顾客），此时 `member_id` 为空。若反过来把 `member_id` 设为非空，则「没办卡的活动券」根本没有地方落 |
| 3 | **`benefit_name` / `holder_name` 存快照**：M03-03 把权益改名、M03-02 患者改名后，历史券上显示的名称不应变化。这与共享规范 §17 第 28 条一致 |
| 4 | **`usage_limit_count` 与 `used_count` 是「单张券维度」**：一张「可核销 3 次」的体检券，`usage_limit_count = 3`。而「每年 2 次免费检查」这种**周期性权益项**的次数在 `m19_benefit_usage` 按周期记。两者不能混：前者是一张券用几次，后者是一类权益一年用几次 |
| 5 | **`version_no` 保留但不用作 CAS**：核销走行锁（见 4.3 节说明），`version_no` 只用于审计比对与前端乐观展示。保留这个字段是为了让「谁改了这张券」有据可查 |

### 4.3 表：`m19_benefit_redeem`（权益核销单表）

**用途：** 记录**每一次核销动作**。一次核销 = 一行，无论成功、失败、还是事后被撤销。这张表是本子模块的**账本**，也是幂等的终点。

**为什么核销单要记录「失败」行：** 若只记成功行，那么「顾客拿券来核，系统报错，第二次又成功」这件事在库里只剩一条成功记录——事后无法回答「第一次为什么失败」「是不是每次都在同一个环节失败」。失败行是最便宜的可观测性。

**写入方：** M19-05（P-06 核销 / P-07 撤销改状态 / 批量核销） **只读方：** M16-04（结算详情展示优惠明细来源）、M19-08（核销运营统计）、M22-02（视光金额统计取核销金额）

**约束说明**

```sql
-- ============================================================
-- 【铁律 6】核销幂等：两条约束缺一不可
-- ============================================================

-- ① 核销单号唯一：同一次核销重放（同一个 redeem_no）只会有一行
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT uk_m19_benefit_redeem_no
    UNIQUE (redeem_no);

-- ② 同一权益实例在同一张业务单据上只能核一次
--    WHERE status = 'SUCCESS' 不能省：
--    失败行必须留作审计轨迹；不带这个条件，一次失败后再成功就撞唯一索引，
--    业务上表现为「这张券再也用不了」。
CREATE UNIQUE INDEX uk_m19_benefit_redeem_instance_biz
    ON m19_benefit_redeem (benefit_instance_id, biz_type, biz_no)
    WHERE status = 'SUCCESS';

-- ③ 核销状态三态
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT ck_m19_benefit_redeem_status
    CHECK (status IN ('SUCCESS', 'REVOKED', 'FAILED'));

-- ④ 业务类型
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT ck_m19_benefit_redeem_biz_type
    CHECK (biz_type IN ('OPTICAL_ORDER', 'OUTPATIENT_SETTLEMENT',
                        'REFRACTIVE_ORDER', 'EXAM_ORDER', 'MANUAL'));

-- ⑤ 核销来源
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT ck_m19_benefit_redeem_source
    CHECK (redeem_source IN ('API', 'MANUAL', 'BATCH'));

-- ⑥ 优惠金额来源：M19 只认调用方随请求提交的金额（合同式试算）
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT ck_m19_benefit_redeem_discount_source
    CHECK (discount_source IN ('CALLER', 'NOT_APPLICABLE'));

-- ⑦ 【组合约束】成功行必须有优惠金额来源，且金额不得为负
--    防的是「核销成功了但优惠金额是空的」→ M16 结算时不知道这张券到底减了多少
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT ck_m19_benefit_redeem_success_combo
    CHECK (
        (status = 'SUCCESS' AND discount_source = 'CALLER'
            AND discount_amount IS NOT NULL AND discount_amount >= 0)
     OR (status = 'REVOKED' AND discount_amount IS NOT NULL)
     OR (status = 'FAILED'  AND fail_reason IS NOT NULL AND fail_code IS NOT NULL)
    );

-- ⑧ 【组合约束】失败行不得有优惠金额（失败就是没减钱，记一个金额会让对账凭空多出减免）
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT ck_m19_benefit_redeem_fail_no_amount
    CHECK (status <> 'FAILED' OR discount_amount IS NULL);

-- ⑨ 【组合约束】批量来源必须有任务 ID
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT ck_m19_benefit_redeem_batch_combo
    CHECK (redeem_source <> 'BATCH' OR batch_task_id IS NOT NULL);

-- ⑨-1 【组合约束】成功行必须有金额依据快照，且快照里必须有基数与计算时刻
--      CHECK 只保护字段自身，不保护 JSONB 内部结构（共享规范 §17 第 23 条），
--      所以这里用 ->> 把内部键提出来做组合校验。
--      防的是「金额记了但说不出这个数怎么来的」——日后对账无从溯源，
--      而 M16 侧的试算缓存 m16:discount:trial:{settle}:{hash} 只有 120 秒 TTL，事后必然查不到。
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT ck_m19_benefit_redeem_basis_combo
    CHECK (
        status = 'FAILED'
     OR (discount_basis_snap ? 'base_amount'
        AND discount_basis_snap ? 'discount_mode'
        AND discount_basis_snap ? 'calc_at'
        AND (discount_basis_snap ->> 'base_amount')::NUMERIC >= 0
        AND (discount_amount IS NULL OR
             discount_amount <= (discount_basis_snap ->> 'base_amount')::NUMERIC))
    );

-- ⑩ 金额非负
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT ck_m19_benefit_redeem_amount_nonneg
    CHECK ((biz_amount IS NULL OR biz_amount >= 0) AND revoke_count >= 0);

-- ⑪ 业务时间不得晚于写入时间太多（防「未来的核销」）
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT ck_m19_benefit_redeem_time_order
    CHECK (redeemed_at <= created_at + INTERVAL '1 day');

-- ⑫ 业务单据号非空串（共享规范 §17 第 21 条：维度字段无值存 ''，不存 NULL）
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT ck_m19_benefit_redeem_biz_no_notblank
```

**核销的事务骨架（行锁，不是乐观锁）**

```sql
BEGIN;

-- ① 锁权益实例行（锁的是被核销的对象，不是核销单表）
--    这里必须是 SELECT ... FOR UPDATE：核销是一个「先读后写」的临界区，
--    读到的 status 决定了后续能不能写。若用乐观锁（WHERE version_no = ?），
--    收银台连点两下 / 扫码枪连扫两次时，第二个请求会失败重试，
--    重试路径一旦写错就变成「两次都成功扣了两张券」。
SELECT id, status, valid_from, valid_to, used_count, usage_limit_count,
       applicable_biz_type, applicable_store_ids, patient_id
  FROM m19_benefit_instance
 WHERE benefit_instance_no = :benefit_instance_no
   AND is_deleted = FALSE
   FOR UPDATE;

-- ② 在锁内校验：状态必须是 AVAILABLE、在有效期内、适用业务类型匹配、
--    未超单张上限、未超周期限额（查 m19_benefit_usage）。
--    校验不通过 → 回滚并返回业务错误码；若是重复核销 → 走第 ⑤ 步重放。

-- ③ 写核销单（status = 'SUCCESS'）
INSERT INTO m19_benefit_redeem (
    redeem_no, benefit_instance_id, benefit_instance_no, benefit_code, benefit_type,
    patient_id, member_id, holder_name, biz_type, biz_no, biz_amount,
    discount_amount, discount_source, discount_basis_snap, redeem_source, operator_id,
    redeemed_at, idempotency_key, status
) VALUES (
    :redeem_no, :instance_id, :instance_no, :benefit_code, :benefit_type,
    :patient_id, :member_id, :holder_name, :biz_type, :biz_no, :biz_amount,
    :discount_amount, 'CALLER', :discount_basis_json, 'API', :operator_id,
    :redeemed_at, :idempotency_key, 'SUCCESS'
);

-- ④ 改权益实例状态（带 status = 'AVAILABLE' 守卫，影响行数必须 = 1）
UPDATE m19_benefit_instance
   SET status = 'USED',
       used_at = :now,
       used_redeem_no = :redeem_no,
       used_count = used_count + 1,
       updated_at = :now,
       updated_by = :operator_id
 WHERE id = :instance_id
   AND status = 'AVAILABLE';

-- 若 ④ 影响行数 = 0，说明并发已在别处核销 —— 回滚并返回首次结果
-- ⑤ 累计限额台账（限额券才有）
UPDATE m19_benefit_usage
   SET used_count = used_count + 1,
       updated_at = :now
 WHERE benefit_code = :benefit_code
   AND patient_id = :patient_id
   AND period_start = :period_start
   AND period_end = :period_end;

COMMIT;
```

**重复核销的处理流程（幂等重放）：**

```sql
-- 步骤 1：先按业务维度找是否已有成功核销（走 uk_m19_benefit_redeem_instance_biz）
SELECT redeem_no, discount_amount, redeemed_at, status
  FROM m19_benefit_redeem
 WHERE benefit_instance_id = :instance_id
   AND biz_type = :biz_type
   AND biz_no = :biz_no
   AND status = 'SUCCESS';

-- 命中 → 原样返回首次结果，加 idempotent_replay = true，不报错、不重算、不加锁
-- 未命中 → 进入 FOR UPDATE 事务
```

> **分区表上建唯一索引的注意点（开发必踩的一个坑）：** PostgreSQL 要求分区表上的唯一索引**必须包含分区键**，所以 `uk_m19_benefit_redeem_no` 在物理上是 `UNIQUE (redeem_no, created_at)` 而不是 `UNIQUE (redeem_no)`。由于 `redeem_no` 内含日期（`RN202610210001`），同一单号的 `created_at` 必然同月，**实际上等价于单号唯一**。但这条等价关系必须在 DDL 注释里写明，否则后来的人会以为是笔误而「修正」掉分区键，建表直接失败。
>
> **第二条幂等索引的落地方式（必须与本节 ② 的 DDL 保持一致，不能只留在文字上）：** 分区表上的唯一索引 / 唯一约束在 PostgreSQL 中都必须包含分区键，否则无法建立。因此 `uk_m19_benefit_redeem_instance_biz` 在以**普通表**建表时按其原始定义落地（`ON m19_benefit_redeem (benefit_instance_id, biz_type, biz_no) WHERE status = 'SUCCESS'`，见本节 ②）；在**分区表**形态下由 Alembic 迁移改为 `ON m19_benefit_redeem (benefit_instance_id, biz_type, biz_no, created_at) WHERE status = 'SUCCESS'`。
>
> 为什么加上 `created_at` 仍然达到「同一券同一张单只成功一次」的目的：`created_at` 只在物理上去重时参与索引键，而**业务上不可能出现「同一券在同一张业务单据上、跨两个不同月份各成功核销一次」**——业务单据的生命周期以天计，不会跨月；即使出现跨月的异常数据，`m19_benefit_redeem` 的核销事务在 `SELECT ... FOR UPDATE` 之后会按 `(benefit_instance_id, biz_type, biz_no)` 再做一次应用层去重校验（同时查 `status = 'SUCCESS'`），并配合每日对账巡检（详细设计 8.4.4 C-01/C-03）兜底。
>
> 这条「物理键含 `created_at` + 应用层按业务维度去重 + 每日巡检」的三段式落地必须写进迁移脚本注释，否则后来的人会误以为 `created_at` 是笔误而「修正」掉，导致建表直接失败。

**设计说明**

| # | 说明 |
|---|---|
| 1 | **`discount_amount` 由调用方传入，M19 不计算**：这是本子模块最重要的一条。若 M19 自己算优惠（比如按 `face_amount` 直接减），就会出现「收银台按 M16 的规则减 200，会员中心按 M19 的规则减 199.5」——一分钱的差就要人工对账一次。M19 只存调用方算好并随请求提交的数，`discount_source = 'CALLER'` 字段把这个约定写进了表结构 |
| 1b | **`discount_basis_snap` 为什么必须落库而不是只存金额**：金额是一个结论，依据是结论的出处。M16 侧的试算缓存 `m16:discount:trial:{settle}:{hash}` 只有 120 秒 TTL，一个月后对账时问「这 200 元是怎么算出来的」，M16 那边已经查不到任何痕迹。M19 把 `base_amount` / `discount_mode` / `policy_codes` / `combo_no` / `calc_at` 整体存成 JSONB，是核销金额唯一可回溯的凭证；`ck_m19_benefit_redeem_basis_combo` 进一步要求成功行的快照里必须含 `base_amount`、`discount_mode`、`calc_at` 三个键，且 `discount_amount <= base_amount` |
| 2 | **`redeemed_at` 与 `created_at` 分开**：`redeemed_at` 是业务时间（调用方传入，可能是补录昨天的核销），`created_at` 是写入时间。混用会让「按业务日期统计核销」和「按写入日期分区」打架 |
| 3 | **`fail_code` 存错误码字符串**：按错误码聚合就能看出「最常见的核销失败原因是什么」。若只存自然语言 `fail_reason`，统计要写正则 |
| 4 | **`revoke_count` 而不是布尔**：一次核销可以被撤销、重新核销、再撤销。计数器让「这张券被折腾了几次」一眼可见，超过 3 次进人工复核 |
| 5 | **不存 `rule_code`**：规则在实例上已有快照，核销单再存一份会产生「两处规则不一致听谁的」问题 |

### 4.4 表：`m19_benefit_rule`（权益使用规则表）

**用途：** 存「这张券怎么用」的**执行参数**：能不能叠加、一次能不能用多张、能抵消到哪一步、跨门店能不能用、未成年人能不能用、哪些支付方式下不可用。它是「定义 → 实例 → 执行参数」三层里的第三层，**不是权益定义**。

**为什么需要单独一张表，而不把规则字段全塞进 `m19_benefit_instance`：**

| 方案 | 优点 | 致命问题 |
|---|---|---|
| 规则字段全塞实例表 | 少一次 JOIN | 实例表已有 38 个字段，再塞 12 个规则字段变 50 列，每行多占约 180B，219 万行多占约 394MB；且同一次活动发的 5,000 张券规则完全相同，存 5,000 份重复数据 |
| 规则只存在 M03-03 `mpi_member_benefit` | 零冗余 | M03-03 只管「银卡能领什么」，不管「券怎么用」；活动规则（满 300 可用、不可与会员折扣叠加）改了会影响**已经发出去的券** |
| **规则表 + 实例存 `rule_code` 快照（本方案）** | 规则可复用、可按活动版本管理；实例存快照号，规则改了不影响老券 | 需要一次 JOIN（实测 0.08ms，走主键） |

**关键决定：实例表存的是 `rule_code` 而不是规则内容。** 因为规则表本身**不可修改，只能新增版本**——同一个 `rule_code` 出现多条时以 `version_no` 最大的、且 `status = 'ACTIVE'` 的为准。这样「2026 年双十一活动规则」和「2026 年双十二活动规则」各自是独立行，历史券永远能追到自己那一版。

**每个 CHECK 防的真实错误：**

| 约束 | 防的真实错误 |
|---|---|
| `ck_m19_benefit_rule_status` | 配置页误传入 `'ACTIVE '`（带空格）或中文「生效」，PostgreSQL 不报错，但取生效版本的查询永远查不到 |
| `ck_m19_benefit_rule_multi_combo` | 「允许一单用多张」被勾上但上限仍是 1 —— 收银员点第二张券时系统拒绝，现场投诉「你们页面明明写着可以用多张」 |
| `ck_m19_benefit_rule_audit_combo` | 只勾「需审核」不填阈值 → 核销服务的 `need_audit = TRUE` 分支读到 `NULL` 阈值，`NULL > 500` 恒为假，等于审核开关静默失效，一万块的券也不拦 |
| `ck_m19_benefit_rule_version` | 版本号写 0 或负数 → 「取最大版本」出现并列，取到哪一版看执行计划，同一张券两次调用可能算出不同结果 |

**激活规则时必须同时停用旧版本（业务层保证，用下面的语句）：**

```sql
BEGIN;

SELECT rule_code, version_no, status
  FROM m19_benefit_rule
 WHERE rule_code = :rule_code
   AND is_deleted = FALSE
 ORDER BY version_no DESC
   FOR UPDATE;

UPDATE m19_benefit_rule
   SET status = 'INACTIVE',
       updated_at = CURRENT_TIMESTAMP,
       updated_by = :operator_id
 WHERE rule_code = :rule_code
   AND version_no < :new_version_no
   AND status = 'ACTIVE';

UPDATE m19_benefit_rule
   SET status = 'ACTIVE',
       updated_at = CURRENT_TIMESTAMP,
       updated_by = :operator_id
 WHERE rule_code = :rule_code
   AND version_no = :new_version_no;

COMMIT;
```

> **⚠️ 已发出的券不受影响**：`m19_benefit_instance.rule_code` 存的是编码，而核销时读的是「该编码下当时生效的版本」吗？不是。核销读的是**实例创建时写进 `rule_version_no` 的那一版**（见 4.2 节字段表），所以规则升版只影响之后新发的券。这一点是「活动规则中途调整会让已发出去的券凭空提前或延后过期」的正面回答：有效期靠 `valid_from`/`valid_to` 落库隔离规则变化，可用性靠 `rule_version_no` 隔离规则变化。

**设计说明：**

| # | 说明 |
|---|---|
| 1 | **规则不可改、只能加版本**：改一条生效中的规则等于悄悄改变了 5,000 张已发券的使用条件，客户会拿着券来问「为什么昨天 8 折今天 7 折」。 |
| 2 | **`stackable = FALSE` 时调用方只能挂这一张**：P-06 校验时读取该规则的 `stackable`，与 `discount_basis.policy_codes` 交叉核对（列了多个策略即视为叠加），避免「收银员手工又勾了一个 9 折」。 |
| 3 | **`cover_scope` 在 M19 只用于前置拦截，不用于算钱**：M19 拿 `cover_scope` 判断「这张券挂在纯药费单上根本不该出现」，一旦通过就交给 M16 算具体减多少。M19 不读价目表。 |
| 4 | **`expiry_notice_days` 只管天数，不管发不发**：真正发提醒要过黑名单、免打扰时段、频次三道闸门，且必须落 `m19_care_touch`（见详细设计 7.3 与 10.4）。 |
| 5 | **初始化 8 条默认规则**：代金券/折扣券/礼品券/体验券各类型的默认使用规则，见附录 D 与汇总 §9.1。 |

### 4.5 表：`m19_benefit_usage`（权益限额使用台账表）

**用途：** 回答「**这个会员，这项周期性权益，本期已经用了几次**」。典型场景：「银卡会员每年 2 次免费检查」——第 1 次、第 2 次用完后，第 3 次直接拒绝。台账按「会员 × 权益项 × 周期」一行，用计数器累计。

**为什么不能只靠 `m19_benefit_redeem` 表实时 `COUNT`：**

| 方案 | 一次核销的代价 | 问题 |
|---|---|---|
| 实时 `COUNT(*) FROM m19_benefit_redeem WHERE patient_id=? AND benefit_code=? AND redeem_at BETWEEN ...` | 走 `(patient_id, benefit_code)` 索引，219 万行表上约 3~8ms | ①每个限额项一次 COUNT，一个会员挂 6 项限额就是 6 次查询；②**无法区分「用了几次」和「用了几次又被撤销」**——撤销后 COUNT 会变少，但撤销是「退券」，计数该不该退要分场景，裸 COUNT 把决策权交给了查询写法 |
| **台账计数器（本方案）** | 主键点查一次 UPDATE，约 0.3ms | 需要处理周期切换与并发（用 `FOR UPDATE` 与唯一键解决） |

**为什么周期必须落库，而不是运行时算：**

「每年 2 次」里的「每年」如果是运行时算，就有两种算法且**结果不同**：

```text
算法 A（自然年）：period_key = 2026，周期 = 2026-01-01 ~ 2026-12-31
算法 B（滚动 12 个月）：周期 = 最近一次使用日往前推 12 个月
                 李女士 2025-12-20 用了 1 次，2026-01-05 用了 1 次
                 算法 A：2026 年已用 1 次，还能用 1 次
                 算法 B：滚动窗口 2025-01-05~2026-01-05 内含 2025-12-20 与 2026-01-05 = 2 次，一次都不剩
```

同一个会员同一天来问，两种算法给出「还能用 1 次」和「一次都不能用」两个答案。**本子模块统一采用自然年（`CALENDAR_YEAR`）**，并把 `period_key` 落库成 `2026`、`period_start`/`period_end` 落成 `2026-01-01`/`2026-12-31`。理由：

1. 医院会员运营的「年度权益」对外宣传口径都是自然年（「2026 年度银卡尊享」），销售话术与系统必须同一口径；
2. 自然年周期可预测，会员年初就能列出全年能用几次；滚动窗口下「什么时候恢复」永远说不清，客服解释成本极高；
3. 自然年实现上无需回溯查询，周期切换只在 1 月 1 日发生一次。

**同时保留 `CYCLE_MONTH`（滚动 12 个月）作为可选值**，因为少数「连续 12 个月消费满额赠 2 次」的场景确实是滚动的。**周期类型在发券时写死在实例上**，不在核销时读全局配置。

**写入方：** M19-05（核销成功 `+1`、撤销按场景 `-1`、月度批处理开新周期行） **只读方：** M19-05 核销服务（前置限额校验）、M19-06 券使用分析、M22-02（会员权益使用率）

**约束说明**

```sql
ALTER TABLE m19_benefit_usage
    ADD CONSTRAINT ck_m19_benefit_usage_cycle_type
    CHECK (cycle_type IN ('CALENDAR_YEAR', 'CYCLE_MONTH', 'ONCE'));

-- 防超用：已用 + 预占 不得超过上限
ALTER TABLE m19_benefit_usage
    ADD CONSTRAINT ck_m19_benefit_usage_not_exceed
    CHECK (used_count + reserved_count <= limit_count);

ALTER TABLE m19_benefit_usage
    ADD CONSTRAINT ck_m19_benefit_usage_counters
    CHECK (used_count >= 0
       AND reserved_count >= 0
       AND limit_count >= 1
       AND revoked_back_count >= 0);

-- 周期键与周期类型必须成套（CHECK 保护不了组合语义，单独写）
ALTER TABLE m19_benefit_usage
    ADD CONSTRAINT ck_m19_benefit_usage_period_combo
    CHECK ((cycle_type = 'ONCE' AND period_key = 'ONCE' AND period_start = period_end)
        OR (cycle_type = 'CALENDAR_YEAR' AND period_key = TO_CHAR(period_start, 'YYYY')
            AND period_start = DATE_TRUNC('year', period_start)::DATE
            AND period_end = (DATE_TRUNC('year', period_start) + INTERVAL '1 year - 1 day')::DATE)
        OR (cycle_type = 'CYCLE_MONTH' AND period_start < period_end));

-- 反向：撤销次数不得超过已用次数
ALTER TABLE m19_benefit_usage
    ADD CONSTRAINT ck_m19_benefit_usage_revoke_back
    CHECK (revoked_back_count <= used_count);

-- 有使用就必须有时间
ALTER TABLE m19_benefit_usage
    ADD CONSTRAINT ck_m19_benefit_usage_last_used
    CHECK ((used_count = 0 AND last_used_at IS NULL AND last_redeem_no IS NULL)
        OR (used_count > 0 AND last_used_at IS NOT NULL));

ALTER TABLE m19_benefit_usage
    ADD CONSTRAINT ck_m19_benefit_usage_period_key
    CHECK (period_key <> '');
```

**每个 CHECK 防的真实错误：**

| 约束 | 防的真实错误 |
|---|---|
| `ck_m19_benefit_usage_not_exceed` | 并发下两次核销各自读到 `used_count = 1`、`limit = 2`，都判定「还能用」，双双提交 → 实际用了 3 次。这条约束让第二次提交在数据库层直接失败，服务层捕获后返回「超额」而不是「成功」。**注意：这条约束只在预占/累加时机正确时才生效，必须先在 `FOR UPDATE` 里预占，见 4.3 节事务骨架** |
| `ck_m19_benefit_usage_period_combo` | 有人把自然年的 `period_key` 写成 `2026-01`，另一处写 `2026` → 唯一键不冲突，开出两行，各算各的 2 次，一年用 4 次 |
| `ck_m19_benefit_usage_revoke_back` | 撤销接口被重复调用把 `revoked_back_count` 加到超过 `used_count` → 台账算出负数剩余次数，前端显示「还能用 −1 次」 |
| `ck_m19_benefit_usage_last_used` | 批处理只更新了计数器没写时间 → 页面「最近使用时间」为空，客服无法回答「上次什么时候用的」 |
| `ck_m19_benefit_usage_period_key` | 维度字段存空串以外的空值（`NULL`）→ PostgreSQL 唯一索引认为两个 `NULL` 不相等，同一周期无限开行。见共享规范 §17 #21：**维度字段无值存 `''`** |

**周期切换的批处理语句（每月 1 日 00:30 由 7.3 节任务执行）：**

```sql
INSERT INTO m19_benefit_usage (
    usage_no, patient_id, member_id, benefit_code, benefit_instance_id,
    cycle_type, period_key, period_start, period_end,
    limit_count, used_count, reserved_count, created_at, created_by
)
SELECT
    :batch_prefix || LPAD((ROW_NUMBER() OVER (ORDER BY u.patient_id))::TEXT, 6, '0'),
    u.patient_id,
    u.member_id,
    u.benefit_code,
    u.benefit_instance_id,
    u.cycle_type,
    TO_CHAR(:today, 'YYYY'),
    DATE_TRUNC('year', :today)::DATE,
    (DATE_TRUNC('year', :today) + INTERVAL '1 year - 1 day')::DATE,
    u.limit_count,
    0,
    0,
    CURRENT_TIMESTAMP,
    NULL
  FROM m19_benefit_usage u
 WHERE u.cycle_type = 'CALENDAR_YEAR'
   AND u.period_key = TO_CHAR(:today - INTERVAL '1 year', 'YYYY')
   AND u.used_count > 0
   AND u.is_deleted = FALSE
ON CONFLICT (patient_id, benefit_code, period_key) DO NOTHING;
```

> **为什么 `DO NOTHING` 而不是 `DO UPDATE`**：同日多次执行批处理（重试、手工补跑）时，`DO UPDATE` 会把已累加的 `used_count` 覆盖回 0，等于凭空给会员送了次数。`DO NOTHING` 保证幂等。

**设计说明：**

| # | 说明 |
|---|---|
| 1 | **台账存在的前提是「本期有人用过」**：没用过的会员不预建行，核销时 `INSERT ... ON CONFLICT DO NOTHING` 再 `SELECT FOR UPDATE`，避免 20 万会员 × 6 项权益 = 120 万行空台账。 |
| 2 | **`reserved_count` 是核销事务的中间态**：核销事务里先 `+1` 预占，落 `used_count +1 / reserved -1` 在同事务内完成。这样即使事务回滚，预占也随事务消失，不会白白吃掉一次机会。 |
| 3 | **撤销是否退次数分场景**：收银员误操作 → 退（`used_count -1, revoked_back_count +1`）；顾客真实退货且权益规则声明「退货不退次数」 → 不退。这条规则写在 `m19_benefit_revoke.refund_count_flag`，不写在规则表里，因为它是**每次撤销的个别决定**。 |
| 4 | **按实例计数的限额不在本表**：单张券最多核 3 次这种，走 `m19_benefit_instance.used_count`（见 4.2），本表只管「周期性权益项」。两者维度不同，不可混用。 |
| 5 | **`limit_count` 是快照**：M03-03 把「银卡 2 次」改成「3 次」不影响已经开的 2026 年度台账行，次年新行才用新值。 |

### 4.6 表：`m19_benefit_revoke`（权益撤销退券表）

**用途：** 记录每一次「把已经核销掉的券退回来」的动作。撤销是核销的逆操作，但**不是删除核销单**——核销单永远保留（那是已经发生过的账），撤销单是另一张单据，两张单据共同构成完整轨迹。

**为什么撤销必须单独成表而不是「把 redeem.status 改成 REVOKED」：**

| 方案 | 问题 |
|---|---|
| 直接改 `m19_benefit_redeem.status = 'REVOKED'` | ①丢失「谁在什么时候因为什么撤销的」；②同一张核销单可能被撤销、重核、再撤销，单行状态装不下历史 |
| **撤销单表 + 核销单状态标记（本方案）** | 核销单 `status` 改成 `REVOKED` 只表示「当前已失效」，撤销单存全过程；重核时再开一张新核销单 |

**分场景决定「券回到哪」——这是本表最重要的两列：**

| `revoke_reason` | 真实场景 | 券去向 `instance_after_status` | 依据 |
|---|---|---|---|
| `OPERATOR_MISMATCH` | 收银员点错券了（顾客要用的另一张），当场撤销重来 | `AVAILABLE`（若仍在有效期） | 顾客没用掉这张券，权益未消耗 |
| `BIZ_REFUND` | 顾客配镜 2 天后退货，M16 退费成功 | `AVAILABLE`（若仍在有效期）否则 `REVOKED` | 与总纲 §4.4 一致：退货后券回可用；已过期就作废 |
| `BIZ_CANCEL` | 订单未付款直接取消 | `AVAILABLE` | 交易未成立 |
| `ACTIVITY_CANCEL` | 促销活动被叫停（如价格设错） | `REVOKED`（强制作废，不回收） | 活动本身无效，券不该继续流通 |
| `FRAUD_SUSPECT` | 风控发现同一手机号批量领券刷单 | `REVOKED` | 券的来源本身有问题 |
| `DATA_ERROR` | 发现某批券发了双份，撤回多发的 | `REVOKED` | 多发的那份不该存在 |
| `SYSTEM_ROLLBACK` | 下游结算回滚（M16 事务失败），系统自动撤销 | `AVAILABLE` | 系统级补偿，不应惩罚顾客 |

**写入方：** M19-05（P-07 撤销接口、P05 页面撤销） **只读方：** M19-06 券使用分析、M16 结算（退货时校验是否已撤销）、M22-02

```sql
    ADD CONSTRAINT ck_m19_benefit_revoke_source
    CHECK (revoke_source IN ('MANUAL', 'BIZ_REFUND', 'BIZ_CANCEL', 'SYSTEM'));

-- 撤销前状态必须真的是 USED（否则说明核销单状态与实例状态已经不一致，必须停下人工查）
ALTER TABLE m19_benefit_revoke
    ADD CONSTRAINT ck_m19_benefit_revoke_before_used
    CHECK (instance_before_status = 'USED');

-- 组合语义：需要审核的原因必须先有审核人
ALTER TABLE m19_benefit_revoke
    ADD CONSTRAINT ck_m19_benefit_revoke_approve_combo
    CHECK ((revoke_reason IN ('OPERATOR_MISMATCH', 'BIZ_REFUND', 'BIZ_CANCEL', 'SYSTEM_ROLLBACK')
            AND approved_at IS NULL)
        OR (revoke_reason IN ('ACTIVITY_CANCEL', 'FRAUD_SUSPECT', 'DATA_ERROR')
            AND approved_at IS NOT NULL AND approved_by IS NOT NULL));

-- 券回到 AVAILABLE 就必须退次数；作废则视场景（退款作废也退）
ALTER TABLE m19_benefit_revoke
    ADD CONSTRAINT ck_m19_benefit_revoke_avail_flag
    CHECK (instance_after_status <> 'AVAILABLE' OR refund_count_flag = TRUE);

ALTER TABLE m19_benefit_revoke
    ADD CONSTRAINT ck_m19_benefit_revoke_not_deleted
    CHECK (is_deleted = FALSE);

ALTER TABLE m19_benefit_revoke
    ADD CONSTRAINT ck_m19_benefit_revoke_amount
    CHECK (revoked_face_amount >= 0);
```

**每个 CHECK 防的真实错误：**

| 约束 | 防的真实错误 |
|---|---|
| `ck_m19_benefit_revoke_before_used` | 有人对一个 `status = 'AVAILABLE'`（从未用过）的券发起撤销 → 说明上游传错了 `redeem_no`，若不拦就会把别人的核销单标记撤销，造成「A 的券被 B 的撤销单作废」 |
| `ck_m19_benefit_revoke_approve_combo` | 客服一键把「风控疑似刷单」的券作废，没有审批、没有留痕，事后顾客投诉无法自证 |
| `ck_m19_benefit_revoke_avail_flag` | 券退回了 `AVAILABLE` 但台账次数没退 → 会员本年度只能用 2 次，退回后仍是「已用 2 次」，等于没退回 |
| `ck_m19_benefit_revoke_not_deleted` | 撤销单被逻辑删除 → 核销单显示 `REVOKED` 但找不到撤销原因，对账时 87.6 万条核销单里出现「无主失效」 |
| `uk_m19_benefit_revoke_redeem` | 同一核销单被撤销两次（比如收银员连点两次「撤销」）→ 券被退两次，`used_count` 减 2，凭空多出一次权益 |

**撤销事务骨架：**

```sql
BEGIN;

-- ① 锁住权益实例（与核销使用同一把锁，避免核销与撤销交叉）
SELECT id, status, valid_to, used_count
  FROM m19_benefit_instance
 WHERE benefit_instance_no = :benefit_instance_no
   AND is_deleted = FALSE
   FOR UPDATE;

-- ② 校验实例当前确为 USED，且取原核销单（金额从这里读，不重算）
SELECT r.id, r.redeem_no, r.discount_amount, r.status
  FROM m19_benefit_redeem r
 WHERE r.redeem_no = :redeem_no
   AND r.status = 'SUCCESS';

-- ③ 幂等前置：同一 redeem_no 已撤销过则直接返回首次撤销结果
SELECT revoke_no, instance_after_status, revoked_face_amount
  FROM m19_benefit_revoke
 WHERE idempotency_key = :idempotency_key;

-- ④ 写撤销单
INSERT INTO m19_benefit_revoke (
    revoke_no, redeem_no, redeem_id, benefit_instance_id, benefit_instance_no,
    patient_id, member_id, biz_type, biz_no, revoke_reason, revoke_desc,
    instance_before_status, instance_after_status, refund_count_flag,
    revoked_face_amount, operator_id, operator_name, approved_by, approved_at,
    revoke_at, revoke_source, idempotency_key
) VALUES (
    :revoke_no, :redeem_no, :redeem_id, :instance_id, :benefit_instance_no,
    :patient_id, :member_id, :biz_type, :biz_no, :revoke_reason, :revoke_desc,
    'USED', :instance_after_status, :refund_count_flag,
    :origin_discount_amount, :operator_id, :operator_name, :approved_by, :approved_at,
    :revoke_at, :revoke_source, :idempotency_key
);

-- ⑤ 核销单置为 REVOKED
UPDATE m19_benefit_redeem
   SET status = 'REVOKED',
       revoked_at = :revoke_at,
       updated_at = CURRENT_TIMESTAMP,
       updated_by = :operator_id
 WHERE id = :redeem_id
   AND status = 'SUCCESS';

-- ⑥ 权益实例改状态
UPDATE m19_benefit_instance
   SET status = :instance_after_status,
       revoked_at = CASE WHEN :instance_after_status = 'REVOKED' THEN :revoke_at ELSE revoked_at END,
       revoked_reason = CASE WHEN :instance_after_status = 'REVOKED' THEN :revoke_desc ELSE revoked_reason END,
       used_at = CASE WHEN :instance_after_status = 'AVAILABLE' THEN NULL ELSE used_at END,
       used_redeem_no = CASE WHEN :instance_after_status = 'AVAILABLE' THEN NULL ELSE used_redeem_no END,
       used_count = CASE WHEN used_count > 0 THEN used_count - 1 ELSE 0 END,
       updated_at = CURRENT_TIMESTAMP,
       updated_by = :operator_id
 WHERE id = :instance_id
   AND status = 'USED';

-- ⑦ 按场景回退周期台账
UPDATE m19_benefit_usage
   SET used_count = used_count - 1,
       revoked_back_count = revoked_back_count + 1,
       updated_at = CURRENT_TIMESTAMP
 WHERE patient_id = :patient_id
   AND benefit_code = :benefit_code
   AND used_count > 0
   AND :refund_count_flag = TRUE;

COMMIT;
```

**设计说明：**

| # | 说明 |
|---|---|
| 1 | **撤销单与核销单用同一把行锁**（都是 `m19_benefit_instance` 那行），保证「核销中」和「撤销中」不会交叉。若撤销用另一把锁，会出现「撤销读到 AVAILABLE 判断失败、同时又有人正在把它改成 USED」的时序窗口。 |
| 2 | **`revoked_face_amount` 取原核销单的值，不重算**：这是「M19 不算钱」在撤销环节的延伸。退货金额由 M16 算，M19 只是把当初记下的数字搬过来。 |
| 3 | **`refund_count_flag` 是每次的个别决定**：同样是 `BIZ_REFUND`，A 活动声明「退货不退次数」，B 活动声明「退货退次数」，规则写在活动文档里，由调用方传入并留痕在本列。 |
| 4 | **`operator_name` 存快照**：员工离职后员工表查不到人，撤销单上仍要能看到「当时是谁点的」。 |
| 5 | **撤销不回滚订单状态**：M19 只退券，订单退款由 M16 自己完成。M19 通过 `m19.benefit.revoked` 事件告知 M16「券已退」，M16 不再反向依赖 M19 的返回体做判断。 |

### 4.7 表：`m19_benefit_stock`（权益库存与批次表）

**用途：** 管「一批券的发放额度」。活动发 5,000 张 200 元配镜券，必须有地方记「计划发 5,000、已发 4,238、剩余 762、作废 60」。没有这张表，超发只能靠人工数。

**为什么不能靠 `COUNT(*) FROM m19_benefit_instance WHERE source_no = ?`：**

| 方案 | 并发下的行为 |
|---|---|
| 发放前 `SELECT COUNT(*)`，够就插 | 两个收银员同时给两位顾客发最后一张券：都数到 4,999，都插，结果 5,001 张。**这是最经典的超发** |
| **库存批次行 `FOR UPDATE` + 计数列（本方案）** | 发放事务锁住批次行，`issued_count < planned_count` 才放行，第二个请求等待后读到 5,000 直接拒绝 |

**发券与发券是不同的事**：权益实例「李女士领了 1 张」由 `m19_benefit_instance` 记；「这批 5,000 张剩下多少」由本表记。前者是事实，后者是额度。

**写入方：** M19-05（P09 权益库存页、发放时累加 `issued_count`） **只读方：** M19-07 营销活动（引用批次）、M19-06 券使用分析、M19-05 发放服务（`FOR UPDATE` 占额度）

|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |
| stock_no | VARCHAR(32) | N | - | 批次号 `SB + yyyyMMdd + 4位流水`，如 `SB202610210001` |
| stock_name | VARCHAR(100) | N | - | 批次名称，如「2026 双十一配镜券第 1 批」 |
| benefit_code | VARCHAR(32) | N | - | 权益代码（M03-03 快照） |
| rule_code | VARCHAR(32) | N | '' | 使用规则编码，无规则存 `''` |
| source_type | VARCHAR(32) | N | - | 来源：`ACTIVITY`/`LEVEL_GRANT`/`MANUAL`/`COMPENSATION` |
| source_no | VARCHAR(64) | N | '' | 来源单号（活动编码/等级发放批次），无存 `''` |
| planned_count | INTEGER | N | - | 计划发放总额度 |

**约束说明**

```sql
ALTER TABLE m19_benefit_stock
    ADD CONSTRAINT ck_m19_benefit_stock_status
    CHECK (stock_status IN ('DRAFT', 'ACTIVE', 'EXHAUSTED', 'CLOSED'));

ALTER TABLE m19_benefit_stock
    ADD CONSTRAINT ck_m19_benefit_stock_source_type
    CHECK (source_type IN ('ACTIVITY', 'LEVEL_GRANT', 'MANUAL', 'COMPENSATION'));

-- 核心防超发约束：已发 + 已作废 不得超过计划
ALTER TABLE m19_benefit_stock
    ADD CONSTRAINT ck_m19_benefit_stock_not_oversell
    CHECK (issued_count + voided_count <= planned_count);

ALTER TABLE m19_benefit_stock
    ADD CONSTRAINT ck_m19_benefit_stock_counts
    CHECK (planned_count >= 1 AND issued_count >= 0 AND used_count >= 0 AND voided_count >= 0);

-- 已用不得超过已发
ALTER TABLE m19_benefit_stock
    ADD CONSTRAINT ck_m19_benefit_stock_used_bound
    CHECK (used_count <= issued_count);

-- 面额与折扣率二选一（券类型决定）
ALTER TABLE m19_benefit_stock
    ADD CONSTRAINT ck_m19_benefit_stock_value
    CHECK ((face_amount IS NOT NULL AND discount_rate IS NULL)
        OR (face_amount IS NULL AND discount_rate IS NOT NULL));

ALTER TABLE m19_benefit_stock
    ADD CONSTRAINT ck_m19_benefit_stock_valid_span
    CHECK (valid_to >= valid_from);

-- 发满了状态必须是 EXHAUSTED，不能还挂着 ACTIVE（否则发放服务继续尝试）
ALTER TABLE m19_benefit_stock
    ADD CONSTRAINT ck_m19_benefit_stock_exhaust_combo
    CHECK (stock_status <> 'EXHAUSTED' OR issued_count + voided_count = planned_count);

-- 关闭的批次必须有原因
ALTER TABLE m19_benefit_stock
    ADD CONSTRAINT ck_m19_benefit_stock_close_combo
    CHECK (stock_status <> 'CLOSED' OR close_reason IS NOT NULL);
```

**每个 CHECK 防的真实错误：**

| 约束 | 防的真实错误 |
|---|---|
| `ck_m19_benefit_stock_not_oversell` | 两门店并发发最后一张 → 发成 5,001 张，多出的那张顾客拿着来兑，收银员无权拒绝又没法核销（活动已结束） |
| `ck_m19_benefit_stock_value` | 面额和折扣率都不填 → 发出去的券既减不了固定金额也算不出折扣，调用方给不出金额，顾客在收银台干等 |
| `ck_m19_benefit_stock_exhaust_combo` | 发满 5,000 张但状态仍是 `ACTIVE` → 发放服务每次都要先 `FOR UPDATE` 再判断，白锁一次；更糟的是运维看板显示「还有 0 张但批次在运行中」，误判为卡单 |
| `ck_m19_benefit_stock_close_combo` | 手工关批次不填原因 → 三个月后问「为什么双十一券提前停了」无人能答 |
| `ck_m19_benefit_stock_valid_span` | `valid_from` 晚于 `valid_to` → 发出去的券一出生就过期，顾客当场质问 |

**发放事务骨架（`FOR UPDATE` 占额度）：**

```sql
BEGIN;

-- ① 锁批次行（并发安全的关键；行数只有几十到几百，锁竞争可忽略）
SELECT id, planned_count, issued_count, voided_count, stock_status
  FROM m19_benefit_stock
 WHERE stock_no = :stock_no
   AND is_deleted = FALSE
   FOR UPDATE;

-- ② 额度检查在应用层完成：issued_count + voided_count < planned_count

-- ③ 占额度（条件更新，双保险）
UPDATE m19_benefit_stock
   SET issued_count = issued_count + 1,
       stock_status = CASE
                        WHEN issued_count + 1 + voided_count >= planned_count THEN 'EXHAUSTED'
                        ELSE stock_status
                      END,
       updated_at = CURRENT_TIMESTAMP,
       updated_by = :operator_id
 WHERE stock_no = :stock_no
   AND issued_count + voided_count < planned_count;

-- ④ 插入权益实例（valid_from / valid_to 从批次复制过来落库）
INSERT INTO m19_benefit_instance (
    benefit_instance_no, benefit_code, benefit_name, benefit_type, instance_seq,
    member_id, patient_id, holder_name, holder_phone_mask, source_type, source_no,
    rule_code, rule_version_no, stock_id, face_amount, discount_rate,
    min_biz_amount, valid_from, valid_to, granted_at, granted_by,
    applicable_biz_type, applicable_dept_ids, applicable_store_ids
) VALUES (
    :benefit_instance_no, :benefit_code, :benefit_name, :benefit_type, :instance_seq,
    :member_id, :patient_id, :holder_name, :holder_phone_mask, 'ACTIVITY', :source_no,
    :rule_code, :rule_version_no, :stock_id, :face_amount, :discount_rate,
    :min_biz_amount, :valid_from, :valid_to, CURRENT_TIMESTAMP, :operator_id,
    :applicable_biz_type, :applicable_dept_ids, :applicable_store_ids
);

COMMIT;
```

**设计说明：**

| # | 说明 |
|---|---|
| 1 | **`used_count` 与核销单表是「缓存 vs 权威」**：库存页显示「已核销 3,182 张」读本列（快），对账时必须用核销单表重算（准）。两者差超过 `m19.benefit.stock.used_tolerance`（默认 0）就告警。 |
| 2 | **不建 `m19_benefit_config`**：所有可配置项落在 `m19_benefit_rule`（使用规则）与 `m19_benefit_stock`（发放额度）里，再单立一张 `config` 只会让「这条配置到底谁生效」变成谜题。详见 1 节「为什么是这 9 张表」。 |
| 3 | **批次有效期为整批统一**：单张券的可变期是发放后 N 天从领取时算，这是「礼品券领后 30 天有效」的场景——实现方式是发放时把 `valid_to = granted_at + 30 天` 算好落库，**不是运行时算**。 |
| 4 | **`allowed_store_ids` 只管发放地域，不管核销地域**：核销地域由 `m19_benefit_rule.allow_cross_store` 与实例的 `applicable_store_ids` 决定。 |
| 5 | **批次不可删除，只能 `CLOSED`**：已发出的券会引用 `stock_id`，删批次会让 4,238 张券的溯源断链。 |

### 4.8 表：`m19_benefit_batch_task`（批量核销任务表）

**用途：** 支撑 P07 批量核销页：活动结束后把「当天所有符合条件的订单」批量补核销，或运维把「误发的 120 张券」批量核销作废。任务是一条记录，逐条明细落到 `m19_benefit_redeem`（成功）或任务日志里（失败）。

**为什么批量核销必须异步、必须有任务表：**

| 场景 | 同步做 | 异步 + 任务表 |
|---|---|---|
| 一次补核销 3,000 条 | 请求超时 30s，HTTP 504，运维不知道做没做 | 立即返回任务号，页面轮询进度 12%→47%→100% |
| 第 1,847 条失败（上游 M16 超时） | 前 1,846 条已提交，第 1,847 条抛异常，整个请求失败但数据半成功 | 任务标记 `PARTIAL`，可只重跑失败段 |
| 收银员问「我上午点的那次批量做了没有」 | 无记录 | 任务表有谁、何时、多少条、成功几条 |

**写入方：** M19-05（P07 提交任务、Celery worker 更新进度） **只读方：** M19-05 P07 页面、M19-06 运营分析、运维监控

| 约束 | 防的真实错误 |
|---|---|
| `ck_m19_benefit_batch_task_counts` | worker 重试时把 `success_count` 又加了一遍 → 三类之和 3,000 而总数是 2,000，进度算出 150%，页面进度条溢出 |

**设计说明：**

| # | 说明 |
|---|---|
| 1 | **`progress_percent` 是比率 `NUMERIC(10,6)`**，按共享规范比率型字段口径；分母为 0（`total_count = 0`）时保持 `0.000000` 并在页面显示「无匹配数据」，**不写 NULL**——这里 0 是真的「零进度」而非「无定义」，与转化率「分母 0 必 NULL」的场景不同，区别在于进度是过程量不是业务指标。 |
| 2 | **`skip_count` 不是失败**：券已经是 `USED`/`EXPIRED`/`REVOKED` 的，批量核销直接跳过并计数。这避免了「重跑一批任务时全部报错」的噪音。 |
| 3 | **`error_summary` 按错误码聚合而不是逐条存**：3,000 条全失败时逐条存要 3,000 行日志；聚合后是 `1905013×42; 1905016×3`，一眼看出主因。逐条明细由 worker 写 `m19_benefit_log`。 |
| 4 | **重跑不新建任务而是 `retry_of_task_no` 指向原任务**：这样「这个批次被重跑了几次」可以 `COUNT` 出来，超过 3 次告警。 |
| 5 | **任务不删除**：`is_deleted` 仅为治理保留，P07 页面不提供删除入口。 |

### 4.9 表：`m19_benefit_reconcile`（核销对账表）

**用途：** 每天凌晨把「M19 记的核销」与「M16 记的优惠减免」逐单比对，把差异落成一行待处理记录。P08 核销对账页读这张表。

**为什么必须对账，而且必须独立成表：**

M19 与 M16 是两套账本，通过网络上的 P-06 连接。连接的两端都会出错：

| 真实故障 | 现象 | 谁受损 |
|---|---|---|
| P-06 返回成功但 M16 侧事务回滚了 | M19 记「已核销 200 元」，M16 订单上没有任何优惠 | 顾客享受不到优惠，来投诉 |
| M16 已经减了 200 元，但调 P-06 时超时 | M16 订单上有优惠，M19 上券仍 `AVAILABLE`，可以再用一次 | 医院损失 200 元/次，长期无人发现 |
| 两头金额不一致（M16 按 199.5 算，M19 记 200） | 财务月结差 0.5 元 | 对账永远差一点，被迫人工调账 |

第三种故障正是「M19 不算钱」这条规则要消灭的：**因为 M19 记的就是调用方随请求提交、且与依据快照自洽的数，同一字段搬运，理论上不可能差一分钱。** 一旦对账发现差异，说明有人绕过了规则（比如某次改动在 M19 本地算了一次），对账表就是抓这种越界的探针。

**写入方：** M19-05 对账批处理（每日 01:40）与 P08 页面人工确认 **只读方：** M16 财务对账、M22-02 经营分析、审计

| `uk_m19_benefit_reconcile_key` | 对账重跑（运维手工补跑 T-1）→ 同一差异插入两遍，待处理数翻倍，看起来像问题变严重了 |

**单边差异的判定 SQL（对账批处理核心）：**

```sql
WITH m19_day AS (
    SELECT r.biz_no,
           r.redeem_no,
           r.discount_amount,
           r.status
      FROM m19_benefit_redeem r
     WHERE r.created_at >= :day_start
       AND r.created_at <  :day_end
       AND r.status IN ('SUCCESS', 'REVOKED')
),
m16_day AS (
    SELECT o.settlement_no AS biz_no,
           SUM(o.reduce_amount) AS benefit_reduce_amount,
           COUNT(*)             AS redeem_cnt
      FROM m16_discount_apply o
     WHERE o.settle_date = :biz_date
       AND o.policy_type = 'MEMBER'
       AND o.is_supplement = FALSE
       AND o.is_deleted = FALSE
     GROUP BY o.settlement_no
)
SELECT
    m.biz_no,
    m.redeem_no,
    m.discount_amount,
    COALESCE(d.benefit_reduce_amount, 0.00) AS m16_amount,
    m.discount_amount - COALESCE(d.benefit_reduce_amount, 0.00) AS diff_amount,
    CASE
        WHEN d.biz_no IS NULL THEN 'M16_ONLY'
        ELSE 'AMOUNT_DIFF'
    END AS diff_type
  FROM m19_day m
  FULL OUTER JOIN m16_day d ON d.biz_no = m.biz_no
 WHERE m.biz_no IS NULL
    OR d.biz_no IS NULL
    OR m.discount_amount <> d.benefit_reduce_amount;
```

> **注意 1（数据来源）**：上面 `m16_day` 读的是 **M16-06 的 `m16_discount_apply`（优惠应用明细表）**，不是 M19 自己的表，也不是任何「M16 每日推送给 M19 的只读快照」——**M16 没有这样一个快照表，也没有这样一个推送**。这张表的字段与本 SQL 的对应关系如下（全部为被引用方的真实字段）：
>
> | 本 SQL 里的名字 | `m16_discount_apply` 真实字段 | 说明 |
> |---|---|---|
> | `biz_no` | `settlement_no` | 结算单号；M19 侧 `m19_benefit_redeem.biz_no` 存的也是结算单号 |
> | `benefit_reduce_amount` | `reduce_amount` | 本方案减免额（核心字段） |
> | `policy_type` 过滤值 | `policy_type = 'MEMBER'` | `'BENEFIT'` **不是** M16 的合法取值（真实枚举为 `DISCOUNT`/`FULL_REDUCE`/`PACKAGE`/`GIFT`/`MEMBER`/`IDENTITY`/`MANUAL`/`SUPPLEMENT`） |
> | `settle_date` | `settle_date` | 同名字段，可用于分区裁剪 |
> | 排除降级补录 | `is_supplement = FALSE` | 补录行不代表实时核销 |
>
> **注意 2（这是对账批处理内部作业，不是在线查询）**：`m16_discount_apply` 属于 M16 的库。本 SQL 只能在对账批处理作业内、以**只读账号**执行，且必须走同一 PostgreSQL 实例的跨 schema 只读视图中转；**任何 API 请求路径上都不得出现对 `m16_*` 表的引用**（`DA-*` 静态扫描会拦）。M19 从不在请求链路上直查 M16 业务表——在线查询一律走上游接口。
>
> **注意 3（快照缺失时的行为）**：若当日 M16 侧不可达或跨库只读视图不可用，**不出差异、不写 `M19_ONLY` 行**，改为「对账跳过」并告警。理由：用空集去 FULL OUTER JOIN 会把当天全部核销单都判成 `M19_ONLY`（日 800 单），第二天运维面对 800 条假差异，真正的 3 条差异被淹没。
>
> 【V1.1 更正】本节原先写的表名 `m16_billing_discount_detail_snapshot` **在 M16 全目录不存在**（`grep -rn "m16_billing_discount_detail" M16收费结算管理/` 零命中），`policy_type = 'BENEFIT'` 也不是 M16 的合法枚举值，且原注释声称的「M16 每日推送的对账快照 / 订阅 `m16.settlement.completed` 落的对账视图」**同样是编造的**——M16-09 提供的对账接口是 `GET /internal/v1/m16/daily/diffs`（P-06）与 `GET /internal/v1/m16/daily/statistics`（P-07），没有「推快照」这回事。一并核对 M16-06 的内部契约（API-26~32），**没有任何一个返回「逐券优惠明细」的接口**。故本节改为直读 `m16_discount_apply`，并把「必须走只读视图 + 只允许批处理作业」写成硬约束。

**设计说明：**

| # | 说明 |
|---|---|
| 1 | **对账只报差异，不自动修复**：`M16_ONLY`（M16 减了但 M19 没记）自动补核销是安全的；`M19_ONLY`（M19 记了但 M16 没减）绝不能自动撤销——那可能是 M16 对账快照延迟。因此 `handle_action` 全部由人工在 P08 选择。 |
| 2 | **`SUM_DIFF` 是汇总级兜底**：即使逐单全部对上，合计仍可能因分区边界（跨零点单据）差一笔，这时落一行 `SUM_DIFF` 说明「逐单无差异但合计差 X 元」，附在报表末尾，不留悬空。 |
| 3 | **严重级别按金额与笔数自动定**：`abs(diff_amount) >= 1000` 或 `abs(diff_count) >= 10` 为 `CRITICAL`；否则 `WARN`；`STATUS_DIFF` 恒为 `INFO`。 |
| 4 | **保留期 3 年**：对账是审计证据，短于财务报表留存要求会被审计打回。 |
| 5 | **不存患者姓名与手机号**：对账只需要 `patient_id` 定位，姓名属于个人信息，按最小必要原则不落。 |

### 4.10 表：`m19_benefit_log`（权益核销操作日志表）

**用途：** 记录每一次权益动作的完整轨迹：发放、核销、撤销、冻结、解冻、过期、导入。这是**只增不改**的流水表，按 `created_at` 月度分区。

**为什么核销必须有独立日志，而不能只靠 `m19_benefit_redeem`：**

| 信息 | 核销单表 | 日志表 |
|---|---|---|
| 谁在什么时候核销的 | 有 | 有 |
| 谁在什么时候**尝试**核销但失败了（失败原因码） | 有失败行 | 有，且带完整入参 |
| 谁把这张券冻结了、解冻了 | 无 | 有 |
| 谁改了券的归属（患者合并重定向） | 无 | 有 |
| 批量任务里每一条的执行结果 | 成功有单，失败无单 | 全有 |

**冻结（FROZEN）必须留日志**：`FROZEN` 是一个真实会发生的状态——顾客与门店就权益纠纷（如「你们说好送两次检查」）正在协调时，客服主管会先冻结券避免被用掉；活动被监管叫停时整批冻结。这两类操作对顾客权益影响直接，必须可追溯。

```sql
    ADD CONSTRAINT ck_m19_benefit_log_action

ALTER TABLE m19_benefit_log
    ADD CONSTRAINT ck_m19_benefit_log_from_status
    CHECK (from_status IN ('', 'AVAILABLE', 'USED', 'EXPIRED', 'FROZEN', 'REVOKED'));

    ADD CONSTRAINT ck_m19_benefit_log_to_status
    CHECK (to_status IN ('', 'AVAILABLE', 'USED', 'EXPIRED', 'FROZEN', 'REVOKED'));

-- 状态变更动作必须两端都有状态
ALTER TABLE m19_benefit_log
    ADD CONSTRAINT ck_m19_benefit_log_status_combo
    CHECK (action_type NOT IN ('REDEEM', 'REVOKE', 'FREEZE', 'UNFREEZE', 'EXPIRE')
        OR (from_status <> '' AND to_status <> '' AND from_status <> to_status));

-- 结果码：成功为 '0'，失败必须是 7 位数字串
ALTER TABLE m19_benefit_log
    ADD CONSTRAINT ck_m19_benefit_log_result_code
    CHECK (result_code = '0' OR result_code ~ '^[1-9][0-9]{6}$');

-- 失败动作必须写说明
ALTER TABLE m19_benefit_log
    ADD CONSTRAINT ck_m19_benefit_log_fail_desc
    CHECK (result_code = '0' OR result_desc <> '');

ALTER TABLE m19_benefit_log
    ADD CONSTRAINT ck_m19_benefit_log_amount
    CHECK (change_amount >= 0);

ALTER TABLE m19_benefit_log
    ADD CONSTRAINT ck_m19_benefit_log_duration
    CHECK (duration_ms IS NULL OR duration_ms >= 0);
```

**每个 CHECK 防的真实错误：**

| 约束 | 防的真实错误 |
|---|---|
| `ck_m19_benefit_log_status_combo` | 日志写「核销」但前后状态都是空 → 事后审计无法判断这次操作到底把券从什么状态改成了什么状态，事件溯源断链 |
| `ck_m19_benefit_log_result_code` | 有人把错误码写成 `'REDEEM_FAILED'` 字符串 → 按错误码聚合统计失败原因时，得到 200 种不同文本，无法聚合 |
| `ck_m19_benefit_log_fail_desc` | 失败码 `1905013` 没有说明 → 运维看到一堆 1905013 不知道是「券已用」还是「券已冻结」 |
| `uk_m19_benefit_log_no` | 日志号用 4 位流水，单日超过 9,999 条（批量核销 3,000 条 × 若干任务很容易破万）→ 重号。本项目日志号用 8 位流水 |
| `ck_m19_benefit_log_amount` | 撤销时把金额写成负数 → 汇总时与核销正数混在一起，正负抵消让「总优惠金额」看起来只有一半 |

**分区策略说明：**

| 项 | 取值 | 依据 |
|---|---|---|
| 分区键 | `created_at` | 日志只按时间查询，且按时间归档 |
| 粒度 | 月 | 日增约 3,200 条（核销 800 + 失败 300 + 发放 2,000 + 其他 100），月增约 9.6 万，单分区约 24MB，索引约 8MB |
| 预建 | 次年 12 个月 | 由 7.3 节 APScheduler 每月 25 日预建 |
| DEFAULT 分区 | 必须有 | 漏建会导致插入直接报错 `no partition of relation found for row`，核销在生产高峰直接失败。DEFAULT 分区有数据即 P2 告警（说明预建没跑） |
| 归档 | 5 年 | 与核销单一致 |

**设计说明：**

| # | 说明 |
|---|---|
| 1 | **日志只增不改**：`REVOKE UPDATE, DELETE`，并在附录 E 迁移脚本里 `downgrade` 时 `GRANT` 回来。任何人（含 DBA 通过应用账号）都无法篡改历史。 |
| 2 | **`request_json` 脱敏后才落**：手机号、身份证、姓名都不进 JSON，只保留 `benefit_instance_no`/`biz_type`/`biz_no`/`idempotency_key` 等业务键。 |
| 3 | **`trace_id` 与 M16 串联**：一次核销跨 M16 收银台流程与 M19 落账两个服务，链路 ID 一致才能在链路系统里一次看全。 |
| 4 | **`REDEEM_FAIL` 独立动作类型**：失败不写核销单（核销单只记成功与已撤销），但必须留日志，否则「顾客说试了 5 次都不行」时无法复盘。 |
| 5 | **`REASSIGN` 记录患者合并重定向**：`mpi.member.merged` 订阅后把券从旧患者改到主患者，这是改变归属的重大操作，必须留痕。 |

### 4.12 Pydantic Schema 定义

**数值类型约定（与共享规范 §2.4 一致）：**

| 类型 | Python 类型 | 序列化 | 说明 |
|---|---|---|---|
| 金额 | `Decimal` | 字符串两位小数 `"200.00"` | `NUMERIC(14,2)`，禁止 `float` |
| 比率 | `Decimal` | 字符串六位小数 `"0.850000"` | `NUMERIC(10,6)`，可空表示「分母为 0」 |
| 计数 | `int` | 数字 | `INTEGER` |
| 日期 | `date` | `"2026-12-31"` | 无时分秒 |
| 时间 | `datetime` | `"2026-10-21 14:20:00"` | 全系统 Asia/Shanghai |

> **为什么禁 `float`**：`float` 是二进制浮点，`0.1 + 0.2 = 0.30000000000000004`。优惠金额减到分，一次四舍五入差异就是 0.01 元，正是「收银台减 200、会员中心减 199.5」这类投诉的起点。全部用 `Decimal` 并序列化为字符串，前端不做数值运算直接展示。

### C.1 P-08 可用权益查询（走部分索引）

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT i.benefit_instance_no,
       i.benefit_code,
       i.benefit_name,
       i.benefit_type,
       i.face_amount,
       i.discount_rate,
       i.min_biz_amount,
       i.valid_from,
       i.valid_to,
       COALESCE(r.stackable, FALSE) AS stackable
  FROM m19_benefit_instance i
  LEFT JOIN m19_benefit_rule r
         ON r.rule_code = i.rule_code
        AND r.version_no = i.rule_version_no
 WHERE i.patient_id = :patient_id
   AND i.status = 'AVAILABLE'
   AND i.is_deleted = FALSE
   AND i.valid_from <= :as_of_date
   AND i.valid_to   >= :as_of_date
   AND (i.applicable_biz_type = 'ALL' OR :biz_type = ANY (string_to_array(i.applicable_biz_type, ',')))
 ORDER BY i.valid_to ASC, i.id ASC;
```

**期望执行计划：** `Index Scan using idx_m19_benefit_instance_avail on m19_benefit_instance`，`rows ≈ 3~8`，`Buffers: shared hit ≈ 6`，耗时 **≤ 2ms**。若出现 `Seq Scan`，先看是否漏了 `status = 'AVAILABLE'` 字面量（部分索引只在查询条件能匹配谓词时才可用）。

### C.2 P-06 核销行锁与幂等

```sql
-- ① 幂等重放：先查唯一索引，命中即返回首次结果，不重算
SELECT redeem_no, benefit_instance_no, discount_amount, status, redeem_at
  FROM m19_benefit_redeem
 WHERE idempotency_key = :idempotency_key
 LIMIT 1;

-- ② 防重复核销：同一实例同一单据已有成功行则拒绝
SELECT redeem_no, discount_amount
  FROM m19_benefit_redeem
 WHERE benefit_instance_id = :instance_id
   AND biz_type = :biz_type
   AND biz_no = :biz_no
   AND status = 'SUCCESS';

-- ③ 行锁（核销与撤销共用同一把锁）
SELECT id, status, valid_from, valid_to, usage_limit_count, used_count
  FROM m19_benefit_instance
 WHERE benefit_instance_no = :benefit_instance_no
   AND is_deleted = FALSE
   FOR UPDATE;
```

**`FOR UPDATE` 的性能预算：** 等锁 P95 ≤ 100ms（P-06 总预算 400ms 中的 1/4）。实测同券并发 5 请求时第 5 个等锁约 62ms；若排队超 100ms 则 `lock_timeout = '100ms'` 触发，返回可重试错误而不是让收银员干等。

### C.3 核销统计（P04 页面）

```sql
SELECT
    DATE(r.redeem_at)                       AS stat_date,
    r.biz_type,
    COUNT(*)                                AS redeem_cnt,
    SUM(r.discount_amount)                  AS discount_total,
    COUNT(*) FILTER (WHERE r.status = 'REVOKED') AS revoke_cnt,
    CASE
        WHEN COUNT(*) > 0
        THEN ROUND(
                 COUNT(*) FILTER (WHERE r.status = 'REVOKED')::NUMERIC / COUNT(*),
                 6)
        ELSE NULL
    END                                     AS revoke_rate
  FROM m19_benefit_redeem r
 WHERE r.redeem_at >= :date_from
   AND r.redeem_at <  :date_to
   AND r.status IN ('SUCCESS', 'REVOKED')
 GROUP BY DATE(r.redeem_at), r.biz_type
 ORDER BY stat_date DESC, r.biz_type;
```

> **撤销率分母为 0 时返回 `NULL`**（不是 0），页面显示 `—`。理由：0 表示「一笔都没有」，`—` 表示「无从谈起」，管理者对这两种情况的处置动作不同。
