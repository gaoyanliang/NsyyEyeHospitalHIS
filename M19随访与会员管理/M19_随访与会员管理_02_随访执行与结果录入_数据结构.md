## 文档说明

本文件是 **M19-02 随访执行与结果录入**的**数据结构唯一依据**，包含第 4 章全部内容。

**本子模块的数据职责一句话：** 记录「这次随访打出去了没有、问出了什么」，并把结果可靠地送回 M03-04。**随访任务本身不在这里**（在 M03-04 的 `mpi_followup_task`），**随访结果最终也不在这里**（回写到 M03-04 的 `mpi_followup_task_result`），这里存的是**执行过程与执行态**。

**三条铁律（本子模块专属，违反即返工）：**

| # | 铁律 | 落地手段 | 违反后果 |
|---|---|---|---|
| **L-01** | **不重造任务表**：本文件不含 `m19_followup_plan` / `m19_followup_task` / `mpi_followup_task` 的任何 DDL，只存 `task_id` 引用 | `m19_fu_exec_record.task_id` 逻辑外键 + `uk_m19_fu_exec_record_task` 唯一约束 | 同一台手术产生两份随访任务，护士看到两套待办，患者被骚扰两次 |
| **L-02** | **回写状态必须可查**：`writeback_status` 三态（`PENDING`/`SUCCESS`/`FAILED`）+ `writeback_attempt` 计数，绝不允许「执行记录已完结、但 M03-04 不知道」这种静默断层 | 本地消息表 `m19_fu_writeback` + 组合约束 `ck_m19_fu_exec_record_closed_writeback` | 随访员打完电话、结果丢了，明天还得再打一遍 |
| **L-03** | **问卷答案必须能区分「未答」与「答否」**：JSONB 里**键缺失 = 未答**，`false` / `NO` = 明确答否，`null` 一律视为未答并在入库前剔除 | `m19_fu_answer.answer_json` + `answered_count` / `total_count` 双计数 + 应用层归一化 | 「患者说没有眩光」被统计成「患者没回答」，异常升级漏报 |

**命名与类型红线（与汇总文件 §2.3 一致）：**

| 对象 | 类型 | 禁止 |
|---|---|---|
| 金额 | `NUMERIC(14,2)` | `FLOAT` / `DOUBLE PRECISION` / `REAL` |
| 比率 | `NUMERIC(10,6)`，存 0~1 不存百分数 | 同上 |
| 比率分母为 0 | 比率字段必须 `NULL`，不得写 0 | 写 0 会让科室排名垫底 |
| 状态/枚举 | `VARCHAR(32)` + `CHECK` | 不建 PostgreSQL `ENUM` 类型 |
| 时间戳 | `TIMESTAMP`（Unspecified，全系统 Asia/Shanghai） | 不带时区类型 |
| 布尔 | `BOOLEAN` | 整型 0/1 |

## 1. 表清单

| 序号 | 表名 | 中文名 | 用途 | 预估行数 |
|---|---|---|---|---|
| 4.2 | `m19_fu_exec_record` | 随访执行记录表 | 一次随访执行的**主档**：谁、何时、对哪条 M03-04 任务、执行成什么样、回写了没有 | 130 万（3 年） |
| 4.3 | `m19_fu_call_log` | 外呼记录表 | 每一通电话一条：拨号、接通、时长、录音 URL、挂机原因。**月分区** | 98.6 万（3 年） |
| 4.4 | `m19_fu_answer` | 随访问卷答案表 | 一次执行填一份问卷：JSONB 答案 + 结构化评分 + 未答/答否双计数 | 130 万（3 年） |
| 4.5 | `m19_fu_result_detail` | 随访结果明细表 | 结果的结构化明细：视力、眼压、症状、用药依从、宣教完成项等逐项一行 | 620 万（3 年） |
| 4.6 | `m19_fu_abnormal` | 异常结果上报表 | 命中异常规则后有据可查：命中了哪条、严重度、4 小时人工复访是否闭环 | 8.6 万（3 年） |
| 4.7 | `m19_fu_lost` | 失访登记表 | 失访原因、最后联系尝试、是否已回写 M03-04 `FAILED`、是否已进召回名单 | 4.3 万（3 年） |
| 4.8 | `m19_fu_writeback` | 回写本地消息表 | 待回写 M03-04 的消息队列：重试次数、下次重试时间、死信标记。**只增不改** | 130 万（3 年） |
| 4.9 | `m19_fu_touch_log` | 执行侧触达记录表 | 执行阶段每一次对外触达（电话/短信/微信）的三道闸门判定结果，用于频次控制与合规举证 | 130 万（3 年） |
| 4.10 | `m19_fu_config` | 随访执行配置表 | 执行侧可配参数：有效期宽限、异常阈值、退避策略、免打扰时段 | 200（配置级） |

**合计：9 张表**

**为什么是 9 张，不是更少也不是更多：**

| 合并/拆分的候选 | 结论 | 理由 |
|---|---|---|
| `m19_fu_call_log` 并入执行记录 | **不合并** | 一通随访可能拨 3 次（无人接、忙、接通），执行记录只有 1 条。合并后要么丢拨打历史，要么执行记录被迫膨胀成「一次执行 N 行」，`uk (task_id)` 唯一约束直接失效 |
| `m19_fu_answer` 并入执行记录 | **不合并** | 问卷答案动辄 30～80 个键，JSONB 塞进执行记录会让热表每行膨胀到 4KB 以上，而执行记录要按科室/日期高频扫描。答案只在打开详情时读 |
| `m19_fu_result_detail` 并入答案 | **不合并** | 答案回答「患者说了什么」（原始），明细回答「这次随访的结论是什么」（结构化、可统计）。异常规则与统计要的是明细，不是原始答案 |
| `m19_fu_abnormal` 并入执行记录 | **不合并** | 一次执行可能命中多条异常规则（如同时视力低于阈值 + 主诉眼痛）；异常还要独立跟踪「4 小时内复访闭环」，有独立生命周期 |
| `m19_fu_writeback` 并入执行记录 | **不合并** | 回写是**可重试的异步动作**，与执行记录是 1:N（回写成功前可能重试 5 次，每次都要留痕）；且这张表是跨子模块消费的队列，被扫描任务高频读取，混进执行记录会互相拖累 |
| `m19_fu_touch_log` 并入 `m19_care_touch`（M19-03） | **不合并** | `m19_care_touch` 是**关怀触达**（营销/召回），本表是**医疗随访触达**，频次规则不同（医疗必要类每日 ≤ 2 次，关怀类 24h ≤ 1 次）。混表后频次闸门要按 origin 分流，且 M19-03 的合规导出会把随访电话混进去 |

**表归属边界（与 M19-01 的 `m19_fu_` 前缀共用规则）：** 本子模块只建**事实类**表（execution / call / answer / result / abnormal / lost / writeback / touch / config）；`m19_fu_script`、`m19_fu_script_node`、`m19_fu_questionnaire`、`m19_fu_question`、`m19_fu_channel_rule`、`m19_fu_pool_snapshot`、`m19_fu_calendar_config` 由 **M19-01** 定义完整 DDL，本子模块**只引用不建**（见汇总文件 §1.2）。

```
                        │──────────────────────────────│

                        │ exec_no (UK)                 │

        │ m19_fu_call_log      │ │ m19_fu_answer│ │m19_fu_lost   │
        │ 月分区 by created_at  │ │ uk(exec_id)  │ │uk(exec_id)   │

        ┌──────────────────────────────┐   ┌──────────────────────────────┐
        │ m19_fu_writeback             │   │ m19_fu_touch_log             │
        │ 本地消息表（只增不改）          │   │ 三道闸门判定留痕               │
```

**关系说明**

| 关系 | 基数 | 说明 |
|---|---|---|
| `mpi_followup_task` → `m19_fu_exec_record` | 1 : 1 | 一个 M03-04 任务最多一条执行记录（`uk_m19_fu_exec_record_task`）。任务状态由 M03-04 维护，M19 只能写 `EXECUTING`/`COMPLETED`/`FAILED` |
| `m19_fu_exec_record` → `m19_fu_call_log` | 1 : N | 一通随访可能拨多次（未接、忙、接通后重拨）。通话明细是频次与话术优化的原始素材 |
| `m19_fu_exec_record` → `m19_fu_answer` | 1 : 1 | 一次执行填一份问卷快照。**只存提交那一刻的答案**，问卷模板改版不影响历史记录 |
| `m19_fu_exec_record` → `m19_fu_result_detail` | 1 : N | 逐项结构化明细（视力、眼压、症状…），供统计与异常规则消费 |
| `m19_fu_exec_record` → `m19_fu_abnormal` | 1 : N | 一次执行可命中多条异常规则，每条独立跟踪 4 小时复访闭环 |
| `m19_fu_exec_record` → `m19_fu_lost` | 1 : 0..1 | 只有 `ABANDONED` 且原因属失访类时才有一条失访登记 |
| `m19_fu_exec_record` → `m19_fu_writeback` | 1 : N（逻辑） | 一次执行可能需要多次回写动作（`RESULT` 回写结果、`LOST` 回写失访、`ABANDON` 放弃）。按 `(biz_type, biz_no, action)` 唯一 |

> `FK*` 表示**逻辑外键**，物理上不建 `FOREIGN KEY`。理由见汇总文件 §2.6：① `task_id` 指向 M03-04 的表，跨模块物理上不可能建外键；② 逻辑删除 + 物理外键会让「删除父行」变成死结；③ 本模块的 `task_id` 是**外部事实的镜像**，M03-04 侧删除任务不应级联删掉执行历史（合规要求留痕）。

**分区说明：** 仅 `m19_fu_call_log` 按月 RANGE 分区（年增 32.9 万 + 录音 URL 需按时间归档），其余表不分区。`m19_fu_writeback` 虽然是 130 万级，但它是**滚动队列**——成功的消息 7 天后归档删除，稳态行数只有几万，分区反而增加维护负担。

### 4.2 表：`m19_fu_exec_record`（随访执行记录表）

**用途：** 一次随访执行的**主档**。回答四个问题：**对哪条 M03-04 任务**（`task_id`）、**谁在什么时候执行**（`executor_id` / `executed_at`）、**执行成什么样**（`status` / `result_status` / `call_result`）、**结果送回 M03-04 了没有**（`writeback_status` / `writeback_at`）。

**写入方：** M19-02 工作台（全部状态流转）；回写任务只更新 `writeback_*` 与 `status→CLOSED`。 **只读方：** M19-08 运营分析（依从性/完成率）、M19-03 关怀召回（失访与异常名单）、P-11 契约（M03-04/M11-06 查执行状态）、M22-02 指标采集。

**为什么要有这张表：** M03-04 的 `mpi_followup_task` 只记录任务自身的状态（`PENDING`/`ASSIGNED`/`EXECUTING`/`COMPLETED`/`FAILED`），它**不知道**这次随访是怎么打的、打了几次、问了什么、有没有异常。如果 M19 不落这张表，三件事会立刻出问题：① 护士填了 30 分钟问卷，保存后刷新页面只剩一个 `COMPLETED`，草稿丢了；② 患者主诉「夜间眩光」这种异常信号无处存放，只能塞进 `result_summary` 的 1000 字符里，无法统计分析；③ `SUBMITTED`（本地已填完）与 `CLOSED`（已回写 M03-04）无法区分，回写失败的记录会被当成完成。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |

| task_id | BIGINT | N | - | **M03-04 `mpi_followup_task.id`**（逻辑外键，唯一约束保证一任务一记录） |
| task_no | VARCHAR(32) | N | - | M03-04 任务号（冗余快照，如 `FTK20261021001`） |
| patient_id | BIGINT | N | - | 患者 ID（逻辑外键 → M03-01） |
| empi_no | VARCHAR(32) | Y | NULL | EMPI 号（快照） |
| patient_name | VARCHAR(64) | Y | NULL | 患者姓名（快照，列表展示用） |
| patient_age_years | SMALLINT | Y | NULL | 执行时年龄（快照，异常规则按年龄分档） |
| patient_gender | VARCHAR(8) | Y | NULL | `M` / `F` / `U`（快照，问卷题目可依赖性别） |
| phone_mask | VARCHAR(32) | Y | NULL | 手机号掩码（如 `138****5678`），列表展示用 |
| phone_encrypted | VARCHAR(255) | Y | NULL | 手机号密文（仅 `m19:fu:exec:view_phone` 权限可解，用于实际外呼） |
| followup_scene | VARCHAR(32) | N | - | 随访场景快照：`POSTOP`/`CHRONIC`/`OPTICAL`/`REVIEW`/`DISCHARGE`/`OTHER` |
| node_name | VARCHAR(64) | Y | NULL | M03-04 节点名快照（如「术后1周」） |
| plan_date | DATE | Y | NULL | 计划执行日期（快照，算依从性用） |
| priority | VARCHAR(16) | N | 'NORMAL' | 优先级快照：`HIGH`/`NORMAL`/`LOW` |
| dept_id | BIGINT | N | - | 执行科室 ID（快照） |
| dept_name | VARCHAR(128) | Y | NULL | 执行科室名（快照，防主数据改名后失真） |
| executor_id | BIGINT | N | - | 实际执行人 ID（M01 `md_staff.id`） |
| executor_name | VARCHAR(64) | N | - | 执行人姓名（快照，共享规范 §17 第 28 条） |
| followup_method | VARCHAR(16) | N | - | 本次实际执行方式：`PHONE`/`WECHAT`/`SMS`/`VISIT`/`ONLINE`/`MAIL` |
| status | VARCHAR(20) | N | 'DRAFT' | 执行记录状态：`DRAFT`/`IN_PROGRESS`/`SUBMITTED`/`CLOSED`/`ABANDONED`/`EXPIRED` |

```sql
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_submitted_fields
    CHECK (status NOT IN ('SUBMITTED', 'CLOSED')
           OR (submitted_at IS NOT NULL AND result_status IS NOT NULL));

-- 【组合约束 2】CLOSED 必须已回写成功
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_closed_writeback
    CHECK (status <> 'CLOSED'
           OR (writeback_status = 'SUCCESS' AND writeback_at IS NOT NULL
               AND closed_at IS NOT NULL));

-- 【组合约束 3】回写成功必须有回写时刻
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_wb_success_at
    CHECK (writeback_status <> 'SUCCESS' OR writeback_at IS NOT NULL);

ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_started
    CHECK (status NOT IN ('IN_PROGRESS', 'SUBMITTED', 'CLOSED')
           OR started_at IS NOT NULL);

-- 【组合约束 5】失访标记必须配套失访原因与结果状态
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_lost
    CHECK (is_lost = FALSE
           OR (result_status IN ('UNREACHABLE', 'REFUSED')
               AND status IN ('SUBMITTED', 'CLOSED', 'ABANDONED')));

-- 【组合约束 6】异常标记必须配套条数与升级时刻
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_abnormal
    CHECK ((abnormal_flag = FALSE AND abnormal_count = 0)
           OR (abnormal_flag = TRUE AND abnormal_count > 0
               AND abnormal_escalated_at IS NOT NULL
               AND review_deadline_at IS NOT NULL));

-- 【组合约束 7】复访截止必须晚于升级时刻（4 小时窗口）
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_review_deadline
    CHECK (abnormal_escalated_at IS NULL
           OR review_deadline_at > abnormal_escalated_at);

-- 【组合约束 8】外呼类方式必须有拨打记录；非外呼类不得有
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_call_count
    CHECK ((followup_method = 'PHONE' AND call_count >= 0)
           OR (followup_method <> 'PHONE' AND call_count = 0));

-- 【组合约束 9】通话时长非负且不超过耗时 + 合理等待
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_duration
    CHECK ((duration_seconds IS NULL
            OR (duration_seconds >= 0 AND duration_seconds <= 86400))
           AND (call_duration_seconds >= 0
                AND call_duration_seconds <= 86400));

-- 【组合约束 10】回写失败必须有错误原因
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_wb_error
    CHECK (writeback_status <> 'FAILED' OR writeback_error IS NOT NULL);

-- 【组合约束 11】提交时间不得早于开始时间，闭环不得早于提交
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_time_order
    CHECK ((started_at IS NULL OR submitted_at IS NULL
            OR submitted_at >= started_at)
           AND (submitted_at IS NULL OR closed_at IS NULL
                OR closed_at >= submitted_at));

-- 【组合约束 12】问卷必须有版本快照（防止模板改版后无法还原）
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_qn_version
    CHECK (questionnaire_id IS NULL
           OR (questionnaire_code IS NOT NULL
               AND questionnaire_version IS NOT NULL));

-- 【组合约束 13】逾期参考位必须四分支穷尽（不是单向蕴含）
-- 防的错误：只写 (flag = FALSE OR days IS NOT NULL) 会放过
--   (TRUE, NULL) 这个矛盾组合——标记了逾期却不知道逾期几天；
-- 也会放过 (FALSE, 3) 这个更隐蔽的矛盾——没标记逾期却带着 3 天，
-- 报表按 days 求和会把这条算进去，而按 flag 统计会漏掉，两个口径打起来。
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_overdue_pair
    CHECK ((task_overdue_flag = FALSE AND task_overdue_days IS NULL)
           OR (task_overdue_flag = TRUE AND task_overdue_days >= 1));

-- 【组合约束 14】逾期天数不得为负或零
ALTER TABLE m19_fu_exec_record
    ADD CONSTRAINT ck_m19_fu_exec_record_overdue_days
    CHECK (task_overdue_days IS NULL OR task_overdue_days >= 1);
```

**设计说明**

| # | 设计点 | 为什么这样定 | 不这么做会怎样 |
|---|---|---|---|
| 1 | **`status` 用 6 态，`SUBMITTED` 与 `CLOSED` 分开** | `SUBMITTED` = 随访员在本地点了提交；`CLOSED` = **已经把结果成功回写到 M03-04**。两者之间隔着一次网络调用（P95 ≤ 100ms，但会断网、会超时、会 503） | 合并成一态后，断网那一刻的记录会被标成「已完成」，而 M03-04 侧任务仍停在 `EXECUTING`。第二天逾期报表把这条算成逾期，护士看到「本该昨天完成的随访今天还没做」，于是**再给患者打一遍电话**——患者被同一个随访骚扰两次。更糟的是运营分析把「已完成」算成 100%，而真实回写率可能只有 87%，管理层的判断完全落空 |
| 2 | `writeback_status` 与 `status` **两套状态并存** | `status` 描述「执行过程走到哪」，`writeback_status` 描述「结果送达走到哪」。二者正交：一条记录可以 `SUBMITTED` + `PENDING`（等回写）、`SUBMITTED` + `FAILED`（回写失败待人工）、`CLOSED` + `SUCCESS`（正常闭环） | 用单状态表达二维语义，状态数会爆炸成笛卡尔积（6 × 3 = 18 个），且无法回答「回写失败的有几条」 |
| 3 | **`ck_..._closed_writeback` 在数据库层强制** | 组合约束，防「手工改库把状态改成 CLOSED 却没回写」这类脏数据。判别方法（共享规范 §17 第 23 条）：把 `writeback_status` 填成 `PENDING`、`status` 填成 `CLOSED`，单列约束全过——说明缺组合约束 | 报表显示闭环率 100%，实际有 13% 从未送达 M03-04。这类数据一旦被下游拿去算依从性，错误会一路传导到管理层看板 |
| 4 | `uk_m19_fu_exec_record_task` **数据库唯一** | 一任务一记录是硬规则，不能靠「应用层先查再插」（并发下查-插之间有窗口） | 护士双击、PC 与移动端同时开，产生两条执行记录；结果回写两次，M03-04 的 `mpi_followup_task_result` 出现两行，逾期统计翻倍 |
| 5 | `start_key` 幂等键 | 兜底第二道：万一同一个任务换了执行人 / 跨天重开，`uk (task_id)` 已经拦住；`start_key` 拦的是「同一人同一天对同一任务重复开执行」这种 UI 抖动 | 页面上出现两条一模一样的「待执行」，护士打开其中一条填、另一条永远挂着 |
| 6 | **快照字段（`executor_name` / `dept_name` / `node_name` / `plan_date` / `priority` / `questionnaire_version`）** | M03-04 与 M01 的主数据会变：护士调科室、模板改版、任务重排期。历史记录必须保留**当时的**样子 | 共享规范 §17 第 28 条的真实场景：M03-04 改人名后，去年 3 月的随访记录显示成现在的护士，纠纷时无法举证是谁做的 |
| 7 | `phone_mask` 与 `phone_encrypted` **分两列** | 列表页只需要掩码（脱敏要求）；实际外呼需要完整号码，而完整号码是敏感数据，必须加密存储 + 权限 + 审计（总纲 §8.3 第 2 条） | 单列存明文 → 任何有列表权限的人都能导出全量手机号；单列存密文 → 列表页每次都要解密 N 条，性能与审计都失控 |
| 8 | `m03_task_status` 镜像列 | P-11 要求 P95 ≤ 100ms，若每次查都实时调 M03-04，网络往返就已用掉大半预算。镜像列在每次回写成功/查询时刷新，读取 O(1) | P-11 变成「M03-04 的代理」，M03-04 一抖动，M11-06 的术后随访页就跟着卡 |
| 9 | `abnormal_count` / `call_count` / `is_lost` 冗余 | 列表页要按「有异常」「失访」筛红，若每次 `EXISTS (SELECT 1 FROM m19_fu_abnormal ...)` 会退化成 N+1 | 一页 50 条待办 = 51 次查询，工作台首屏从 180ms 涨到 1.2s |
| 10 | `ck_..._call_count` 组合约束 | `followup_method <> 'PHONE'` 却有 `call_count > 0` 是自相矛盾的数据（微信随访不可能有拨号次数） | 外呼工作量统计把微信随访也算进通话量，绩效虚高 |
| 11 | `review_deadline_at > abnormal_escalated_at` | 4 小时复访窗口是硬性 SLA（task-35 §6 要点），截止时间必须晚于升级时间 | 计算窗口时用了错误基准（如用 `created_at` 而非 `escalated_at`），异常单可能一生成就已「逾期」 |
| 12 | 不设物理外键 | 见 4.1 说明 | — |
| 13 | **`task_overdue_flag` / `task_overdue_days` 落库（而非现算）** | 逾期在 M19 侧有两个完全不同的用途：① P-11 契约（P95 ≤ 100ms）要回答「这个任务执行得怎么样」，若逾期现算就得再跨一次 M03-04 查任务状态，把 100ms 预算变成「M19 耗时 + M03-04 耗时」，M03-04 一抖动 M11-06 的术后随访页就跟着卡；② 报表要统计「本月有多少条逾期后补做」，这要求逾期是一条**历史事实**而不是当前状态。落库同时满足两者 | 现算方案下，任务一旦被补做完成变 `COMPLETED`，逾期信息立刻消失——管理层的「逾期补做率」永远是 0，因为能算出来的分母里已经没有逾期任务了。这与设计说明第 1 条「一个任务可以既 OVERDUE 又被正常执行」是同一个论点：**状态会前进，历史必须守恒** |
| 14 | **逾期字段是「参考位，非权威」** | 逾期判定的唯一权威是 M03-04 的 `mpi.followup.task.overdue` 事件（含 `overdue_days` 载荷）。M19 只是把收到的事件据实落一份快照，**不自己算逾期**（不拿 `plan_date` 与当前时间比较） | 两边各算一遍，只要宽限期/时区/节假日规则有一点差异，就会出现「M19 说逾期 3 天、M03-04 说逾期 2 天」，对账时无从裁决。算逾期的模块只能有一个 |
| 15 | **`ck_..._overdue_pair` 写成四分支穷尽而非单向蕴含** | 单向蕴含 `(flag = FALSE OR days IS NOT NULL)` 只拦住了 `(TRUE, NULL)` 一种矛盾，漏掉 `(FALSE, 3)`——没标记逾期却带着 3 天。后者更隐蔽：报表按 `days` 求和会把这条算进逾期，按 `flag` 统计会漏掉，同一份数据两个口径打起来。四分支把「标记与否 × 有无天数」四种组合全部枚举 | 数据质量校验报不出错，因为两种取值都「合法」；直到某天运营发现两个报表的逾期数差 17 条，才回头查数据 |
| 16 | **逾期字段只在「有执行记录的任务」上存在** | M19 只为**被随访员点开过**的任务建记录（`uk_..._task` 决定了这一点）。从未被点开的任务，在 M19 侧本来就不该有记录——为了存一个逾期标志而造一条「没人执行过」的记录，会让「本次随访由谁在何时开始」这条审计线出现假数据（`executor_id` / `started_at` 填什么？填系统账号等于伪造审计） | **报表口径差异**：`SELECT COUNT(*) FROM m19_fu_exec_record WHERE task_overdue_flag` 只覆盖「有执行记录且收到过逾期事件」的任务，会**少算**那些至今无人问津的逾期任务。因此逾期总数必须回 M03-04 的数据源统计，M19 只能用于「逾期后补做率」这类以执行记录为分母的指标。这条口径差异必须写进报表说明，否则管理层看到的逾期数会系统性偏低 |

### 4.3 表：`m19_fu_call_log`（外呼记录表）

**用途：** 记录**每一通电话**的完整过程：谁拨的、拨给谁、什么时间、响了几声、通了多久、录音在哪、患者挂机原因。这是外呼工作量统计、话术优化、以及「患者说没人给他打过电话」这类纠纷举证的**唯一原始依据**。

**写入方：** M19-02 外呼服务（呼叫中心回调 + 前端拨号事件）。**只读方：** M19-08 运营分析（外呼量、接通率）、护士长（质控抽查录音）、合规审计（举证）。

**为什么要有这张表：** 一次随访可能拨 3 次（第一次无人接、第二次通话 40 秒患者说要忙、第三次接通 3 分钟完成问卷）。如果只在 `m19_fu_exec_record` 上记 `call_count = 3`，就丢失了「每次为什么失败」——而这恰恰是话术优化的入口。实测一家二级眼科医院术后随访，**首次接通率约 62%**，第二次拨打能再捞回 21%，剩余 17% 才进失访。没有逐通记录，就永远不知道应该在第几次拨打、什么时段拨打。

**分区策略（本表唯一的分区表）**

| 项 | 取值 | 理由 |
|---|---|---|
| 分区类型 | RANGE | — |
| 分区键 | `created_at`（系统写入时间） | 外呼记录是**即时写入**的，`created_at` 与业务发生时刻一致；且录音需要按时间归档（汇总文件 §4.1 明确本表分区键为 `created_at`） |
| 粒度 | 月 | 年增 32.9 万，月均 2.7 万；单分区 2.7 万行，索引全内存 |
| 主键 | `PRIMARY KEY (id, created_at)` | **PostgreSQL 强制：分区表的主键必须包含分区键**。写成 `PRIMARY KEY (id)` 会直接建表失败（汇总文件 §4.2 已踩过这个坑） |
| DEFAULT 分区 | **必须建** | 没有它，新月份第一批写入直接报 `no partition of relation "m19_fu_call_log" found for row`（共享规范 §17 第 22 条） |
| 保留期 | 2 年 | 录音 1 年后删、元数据 2 年（汇总文件 §10.2） |

```sql
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_result
    CHECK (call_result IN ('CONNECTED', 'NO_ANSWER', 'BUSY', 'REJECTED',
                           'INVALID_NUMBER', 'FAILED'));

ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_type
    CHECK (call_type IN ('MANUAL', 'AUTO', 'CALLBACK'));

ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_hangup
    CHECK (hangup_party IS NULL
           OR hangup_party IN ('PATIENT', 'AGENT', 'SYSTEM', 'NETWORK'));

-- 【组合约束 1】接通必须有接通时刻与通话时长
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_connected
    CHECK (call_result <> 'CONNECTED'
           OR (answer_at IS NOT NULL AND talk_seconds IS NOT NULL
               AND talk_seconds >= 0));

-- 【组合约束 2】未接通不得有接通时刻与通话时长
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_not_connected
    CHECK (call_result = 'CONNECTED'
           OR (answer_at IS NULL AND talk_seconds IS NULL));

-- 【组合约束 3】失败必须有失败码与原因
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_failure
    CHECK (call_result IN ('CONNECTED', 'NO_ANSWER')
           OR (failure_code IS NOT NULL AND failure_reason IS NOT NULL));

-- 【组合约束 4】录音三字段同生共死
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_recording
    CHECK ((recording_url IS NULL AND recording_seconds IS NULL
            AND recording_size_bytes IS NULL AND recording_expire_at IS NULL)
           OR (recording_url IS NOT NULL AND recording_seconds IS NOT NULL
               AND recording_expire_at IS NOT NULL));

-- 【组合约束 5】只有接通的通话才可能有录音
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_recording_connected
    CHECK (recording_url IS NULL OR call_result = 'CONNECTED');

-- 【组合约束 6】录音时长与通话时长不得相差过大（允许 5 秒误差）
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_recording_match
    CHECK (recording_seconds IS NULL OR talk_seconds IS NULL
           OR abs(recording_seconds - talk_seconds) <= 5);

-- 【组合约束 7】质检分必须有质检人
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_quality
    CHECK (quality_score IS NULL
           OR (quality_scored_by IS NOT NULL AND quality_scored_at IS NOT NULL));

-- 【组合约束 8】质检分区间 0~1
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_quality_range
    CHECK (quality_score IS NULL OR (quality_score >= 0 AND quality_score <= 1));

-- 【组合约束 9】时间顺序：拨号 <= 振铃 <= 接通 <= 挂机
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_time_order
    CHECK ((dial_at IS NULL OR ring_at IS NULL OR ring_at >= dial_at)
           AND (ring_at IS NULL OR answer_at IS NULL OR answer_at >= ring_at)
           AND (dial_at IS NULL OR end_at IS NULL OR end_at >= dial_at));

-- 【组合约束 10】转写文本 URL 与可用标记一致
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_transcript
    CHECK ((transcript_available = FALSE AND transcript_url IS NULL)
           OR (transcript_available = TRUE AND transcript_url IS NOT NULL));

-- 【组合约束 11】首次接通标记只能出现在接通的通话上
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_first_connect
    CHECK (is_first_connect = FALSE OR call_result = 'CONNECTED');

-- 【组合约束 12】序号从 1 起
ALTER TABLE m19_fu_call_log
    ADD CONSTRAINT ck_m19_fu_call_log_seq
    CHECK (call_seq >= 1);
```

**设计说明**

| # | 设计点 | 为什么这样定 | 不这么做会怎样 |
|---|---|---|---|
| 1 | **分区键 `created_at`，主键 `(id, created_at)`** | 汇总文件 §4.1 指定本表按月分区，§4.2 明确「分区表主键必须包含分区键」 | 写成 `PRIMARY KEY (id)` → 建表直接失败 `unique constraint on partitioned table must include all partitioning columns`，开发照着文档抄会卡在第一步 |
| 2 | **必须建 DEFAULT 分区** | 分区预建脚本每年 12 月跑一次，万一漏跑或部署在新院区 | 新月份第一通电话写入就报 `no partition of relation found for row`，护士拨号直接报错，随访停摆（共享规范 §17 第 22 条） |
| 3 | **录音只存 URL + 时长 + 大小** | 录音是二进制大对象，1 小时通话约 28MB；年增 32.9 万通 × 60% 接通 × 平均 3 分钟 = 约 12 万条录音 × 1.4MB ≈ 168GB/年 | 存进数据库 → 单表暴涨到几百 GB，备份窗口从 20 分钟变成几小时，`pg_dump` 直接超时 |
| 4 | `ck_..._recording_match` 允许 5 秒误差 | 录音是「振铃结束后开始录」，与 `talk_seconds`（接通到挂机）天然差几秒 | 不加容差 → 每条接通记录都违反约束；不加约束 → 录音文件损坏被截断也发现不了 |
| 5 | **`uk (provider_call_id, created_at)`** | 呼叫中心回调会重试（网络抖动、超时重发），同一通电话可能推 2~3 次 | 无唯一约束 → 外呼量统计翻倍，接通率算成 120% 这种荒谬数字 |
| 6 | `REVOKE UPDATE, DELETE` | 外呼记录是合规举证材料（《个人信息保护法》要求处理记录可追溯） | 有人可以改掉「这通电话其实没打通」，患者投诉时无法自证 |
| 7 | 质检分与转写字段**允许事后补写** | 与「不可修改」并不冲突：业务事实（拨打结果、时长、录音）冻结，事后的质量评估是**新增属性** | 全部冻结 → 无法接入 AI 质检；全部放开 → 有人改通话时长粉饰工作量。折中：只允许 NULL → 非 NULL 的单向变更（触发器实现） |
| 8 | `is_first_connect` 冗余 | 「首次接通率」是 M19-08 的核心指标，若每次用窗口函数算 `ROW_NUMBER()`，300 万行上约 900ms | 首屏看板超时 |
| 9 | 不设 `updated_at` / `is_deleted` | 流水表语义：只增不改 | 见第 6 点 |

### 4.4 表：`m19_fu_answer`（问卷答案表）

**用途：** 存放一次执行中**每道题的作答**。核心设计目标是让「**未答**」与「**答否**」在数据层就不可混淆——这是随访问卷最容易出的错，也是最贵的一个错。

**写入方：** M19-02 问卷填写页（逐题自动保存 + 提交时终态写）。**只读方：** M19-02 结果录入页、M19-08 运营分析（题目维度统计）、异常规则引擎（按答案关键词触发升级）。

**为什么要有这张表：** 术后随访问卷里有一道题「是否出现眼痛、畏光、视力骤降等不适？」。如果患者答「否」，说明随访到位、没问题；如果患者**没答**（电话里没问到、患者中途挂断），说明这次随访**信息缺失**。这两者的业务含义完全相反：前者可以关单，后者必须复查。如果用一张只有 `answer_value` 的表，两个情况都会存成空或 `'0'`，异常规则引擎会把「没问」当成「没事」，**真正的并发症信号就此丢失**。

**约束说明**

```sql
ALTER TABLE m19_fu_answer
    ADD CONSTRAINT ck_m19_fu_answer_state
    CHECK (answer_state IN ('UNANSWERED', 'ANSWERED', 'SKIPPED', 'NOT_ASKED'));

ALTER TABLE m19_fu_answer
    ADD CONSTRAINT ck_m19_fu_answer_type
    CHECK (question_type IN ('SINGLE', 'MULTI', 'TEXT', 'NUMBER',
                             'SCALE', 'DATE'));

-- 【组合约束 1】已作答必须有答案内容（三条中至少一条）
ALTER TABLE m19_fu_answer
    ADD CONSTRAINT ck_m19_fu_answer_answered_value
    CHECK (answer_state <> 'ANSWERED'
           OR answer_value IS NOT NULL
           OR answer_text IS NOT NULL
           OR answer_numeric IS NOT NULL);

-- 【组合约束 2】未作答 / 未问及 / 跳过，三个字段必须全空
ALTER TABLE m19_fu_answer
    ADD CONSTRAINT ck_m19_fu_answer_unanswered_blank
    CHECK (answer_state = 'ANSWERED'
           OR (answer_value IS NULL AND answer_text IS NULL
               AND answer_numeric IS NULL AND answer_code IS NULL));

-- 【组合约束 3】作答时间与状态一致
ALTER TABLE m19_fu_answer
    ADD CONSTRAINT ck_m19_fu_answer_answered_at
    CHECK ((answer_state = 'ANSWERED' AND answered_at IS NOT NULL
            AND answered_by IS NOT NULL)
           OR (answer_state <> 'ANSWERED' AND answered_at IS NULL));

-- 【组合约束 4】数值题必须有数值答案，非数值题不得有
ALTER TABLE m19_fu_answer
    ADD CONSTRAINT ck_m19_fu_answer_numeric
    CHECK ((question_type IN ('NUMBER', 'SCALE') AND answer_state = 'ANSWERED'
            AND answer_numeric IS NOT NULL AND answer_numeric_unit IS NOT NULL)
           OR (question_type NOT IN ('NUMBER', 'SCALE')
               AND answer_numeric IS NULL AND answer_numeric_unit IS NULL));

-- 【组合约束 5】文本题必须有文本
ALTER TABLE m19_fu_answer
    ADD CONSTRAINT ck_m19_fu_answer_text
    CHECK (question_type <> 'TEXT' OR answer_state <> 'ANSWERED'
           OR answer_text IS NOT NULL);

-- 【组合约束 6】单选 / 量表必须同时有答案编码
ALTER TABLE m19_fu_answer
    ADD CONSTRAINT ck_m19_fu_answer_code
    CHECK (question_type NOT IN ('SINGLE', 'SCALE')
           OR answer_state <> 'ANSWERED'
           OR answer_code IS NOT NULL);

-- 【组合约束 7】异常标记必须配套规则编码
ALTER TABLE m19_fu_answer
    ADD CONSTRAINT ck_m19_fu_answer_abnormal
    CHECK ((is_abnormal = FALSE AND abnormal_rule_code IS NULL)
           OR (is_abnormal = TRUE AND abnormal_rule_code IS NOT NULL));

-- 【组合约束 8】未作答的题不可能是异常
ALTER TABLE m19_fu_answer
    ADD CONSTRAINT ck_m19_fu_answer_abnormal_answered
    CHECK (is_abnormal = FALSE OR answer_state = 'ANSWERED');
```

**设计说明**

| # | 设计点 | 为什么这样定 | 不这么做会怎样 |
|---|---|---|---|
| 1 | **`answer_state` 四值，`UNANSWERED` 是显式状态而非 NULL** | 「没答」是一个**业务事实**，不是一个「值不存在」。四种情况各有不同处置：`UNANSWERED` 要补录、`SKIPPED` 患者主动不答（尊重意愿）、`NOT_ASKED` 中途挂断（信息不完整，必答项算缺失） | 用 NULL 表达 → 无法区分「护士漏问了」和「患者拒答」，补录提醒会骚扰已经明确拒绝的患者，同时漏掉真正漏问的题 |
| 2 | **`ck_..._unanswered_blank` 在数据库层** | 组合约束。判别法（§17 第 23 条）：把 `answer_state` 填 `UNANSWERED`、`answer_text` 填「无」，单列约束全过——说明缺组合约束 | 前端 bug 导致「未答」行残留了上一题的答案，统计时「未答率」永远是 0，异常规则把别人的答案算到这个人头上 |
| 3 | `answer_value` 用 **JSONB** | 题型差异太大：单选是字符串、多选是数组、量表是数字。若强行拉平成 `VARCHAR`，多选要自己编码成 `"眼痛,畏光"`，检索时又要解析 | 拉平存储 → 「查所有出现畏光的随访」需要 `LIKE '%畏光%'`，既走不了索引，又会把「不畏光」这种文本误命中 |
| 4 | 单选 / 量表**额外存 `answer_code`** | 统计聚合按编码比按文本稳定：`answer_code='YES'` 不会因为选项文案从「有」改成「是」而漏统计 | 按中文文本聚合 → 运营改一次选项文案，历史数据切成两段，「眼痛发生率」出现断崖 |
| 5 | 数值题**单独 `answer_numeric NUMERIC(14,4)`** | 视力 0.8、眼压 14.5 这类要参与阈值比较（如「眼压 > 21 触发异常」） | 存进 JSONB 再比较 → 每次都要 `(answer_value->>'v')::numeric`，走不了索引且精度易丢；用 FLOAT → 0.1 + 0.2 ≠ 0.3，阈值判断抖动 |
| 6 | **题干与题型全部快照** | M19-01 的问卷模板会改版；去年的随访记录必须显示当年的题目 | 只存 `question_id` → 模板改版后历史记录显示新题干，「你当时问的明明是……」这类纠纷无法自证 |
| 7 | `question_text` 用 **GIN trigram 索引** | 异常规则要按关键词匹配（「视力骤降」「剧烈疼痛」「出血」）；`LIKE '%关键词%'` 无索引时 620 万行全表扫约 4.8 秒 | 关键词规则只能定时批量跑，异常发现从 4 小时延迟到次日 |
| 8 | `answered_by` 与执行人分开 | 电话随访中护士代患者勾选是常态；但「谁说的」与「谁录的」在纠纷时是两个问题 | 只存执行人 → 患者主张「我没说这话」时无法说明是代录 |
| 9 | 唯一键 `(exec_id, question_id)` | 逐题自动保存会反复 UPDATE 同一行；用 insert 语义就必须靠唯一键 + `ON CONFLICT` 兜住 | 每次自动保存插一行，一份 20 题问卷填完变成 200 行，完整度算成 1,000% |

### 4.5 表：`m19_fu_result_detail`（随访结果明细表）

**用途：** 把一次执行的随访结果**拆成可统计的结构化条目**。与 `m19_fu_answer`（问卷题目的原始作答）不同，本表存的是**业务结论维度**的明细，例如「术后视力：右眼 0.8 / 左眼 1.0」「主诉症状：畏光」「用药依从：按时」——这些条目跨问卷、跨场景通用，是 M19-08 做纵向对比的基础。

**写入方：** M19-02 结果录入页（提交时由问卷答案**映射**生成）。**只读方：** M19-08 分析、M19-03 关怀召回（按症状召回）、M10-09 视光随访联动、M11-06 术后随访联动。

**为什么要有这张表：** 问卷模板是**每个场景一份**，术后一周问卷与术后一个月问卷题目不同。若要回答「这个患者术后 1 周视力 0.6、1 个月 1.0，恢复趋势如何」，就必须把不同问卷里「视力」这一项**归一化**成同一个指标编码。这个归一化层如果不在建表时做，就只能每次查询时写一堆 `CASE question_code WHEN ...`，而且新增场景就要改 SQL。

**设计说明**

| # | 设计点 | 为什么这样定 | 不这么做会怎样 |
|---|---|---|---|
| 1 | **独立于 `m19_fu_answer` 的归一化层** | 问卷题目随场景变，业务指标跨场景不变。归一化层让「术后 1 周 / 1 月 / 3 月视力趋势」变成一条简单 SQL | 每次跨场景对比都要写 `CASE question_code`，新增一个场景就要改所有报表 SQL；且不同科室问卷题目措辞不同时根本无法合并 |
| 2 | `uk (exec_id, detail_code, eye_side)` | 右眼视力在一次执行中只能有一个值。眼别进唯一键是眼科特有的要求 | 只按 `(exec_id, detail_code)` → 左右眼视力互相覆盖，患者右眼 1.0 左眼 0.3 被记成 0.3×2 |
| 3 | **`value_type` 四型 + 组合约束** | 一张表装数值（视力/眼压）、文本（主诉）、编码（症状）、布尔（是否遵医嘱）。用组合约束保证「说自己是数值就真有数值」 | 全部用 `VARCHAR` → 比较视力大小要 `::numeric` 转换，脏数据（「看不清」）会让整批查询报 `invalid input syntax for type numeric` |
| 4 | **`ref_low` / `ref_high` 成对存参考范围** | 参考范围随场景变（术后 1 天眼压上限 25，术后 1 月 21），且随技术进步会调整。把当时的判定依据存下来，事后复查能解释「为什么当时判为异常」 | 只存 `is_abnormal` → 半年后有人问「这条为什么是异常」，查不出来；只存代码里的常量 → 改常量后历史判定无法复现 |
| 5 | `patient_id_hash` 脱敏列 | 总纲 §8.3 第 1 条要求患者身份信息不出 M19；给 M22 或外部报表做趋势分析时用哈希代替真实 ID | 直接给 `patient_id` → 数据出域即违规；不给任何键 → 无法做去重统计 |
| 6 | `source_answer_id` 溯源 | 明细是从问卷答案映射来的，必须能回溯到原始回答 | 患者质疑「你们记的视力是 0.6，我说的是 0.8」时，无法定位到是谁录错 |
| 7 | `severity` 只允许症状组 | 组合约束：视力值谈「严重度」没有意义 | 「视力严重度」这种字段被误用后，各种维度混乱统计 |
| 8 | `collected_at` 独立于 `created_at` | `collected_at` 是业务发生时刻（执行提交时），`created_at` 是入库时刻（可能因补偿而晚） | 用 `created_at` 做趋势分析 → 断网补传的历史随访全挤在恢复的那一天，趋势线出现虚假尖峰 |

### 4.6 表：`m19_fu_abnormal`（异常结果上报表）

**用途：** 当随访中发现患者有异常信号（术后视力低于阈值、出现并发症关键词、眼压超范围），本表记录**这条异常本身**及其处置闭环：谁发现的、多严重、转给谁、4 小时内有没有人复访、复访结论是什么。

**写入方：** M19-02 异常规则引擎（提交时自动生成）+ 异常结果上报页（人工补录）。**只读方：** 护士长（异常待办）、M19-03 关怀召回（按异常触发关怀）、M11-06 术后随访（并发症追踪）、M19-08 分析（并发症发生率）。

**为什么要有这张表：** `m19_fu_exec_record.abnormal_flag` 只是一个布尔标记，回答不了三个致命问题：**多严重**（畏光 vs 视力骤降到 0.1，处理优先级天差地别）、**转给谁了**（不能只标红不管）、**有没有人在 4 小时内跟进**（这是医疗质量的核心 SLA）。真实场景：某院术后随访发现患者主诉「视力突然下降」，护士在系统里标了个红点就下班了，三天后患者来院已是视网膜脱离。事后追责时系统**无法证明**异常信号曾被任何人看到过。本表就是为了让这条链路可证明：升级时刻、复访截止、复访人、复访结论，一环不缺。

**设计说明**

| # | 设计点 | 为什么这样定 | 不这么做会怎样 |
|---|---|---|---|
| 1 | **4 小时窗口写进 CHECK** | `ck_..._window` 保证 `review_deadline_at <= escalated_at + 4 hours`。这是医疗质量 SLA，不能靠「代码里记得加 4 小时」 | 某次改动把基准写成 `discovered_at`（发现时刻），而升级发生在 40 分钟后 → 实际复访窗口变成 3 小时 20 分，SLA 静默缩水 |
| 2 | `severity='CRITICAL'` **必须有 `escalate_channel`** | 组合约束：危重异常不允许「只在系统里挂个待办」，必须有一条真实的升级动作（电话/短信/站内） | 危重异常躺在待办列表里没人看，与「危险信号必须触达具体的人」的要求背道而驰 |
| 3 | `is_overdue` + `overdue_minutes` 冗余 | 超时看板要按「超时最久」排序，若每次用 `EXTRACT(EPOCH FROM now() - review_deadline_at)` 计算，无法走索引 | 8.6 万行异常单上每次排序扫全表约 210ms，看板刷新卡顿 |
| 4 | `uk (exec_id, rule_code)` | 规则引擎可能因重试/补跑执行两次 | 同一异常生成两条单，接收人收到两条通知，重复复访 |
| 5 | `rule_version` 快照 | 异常规则会调整阈值（如眼压上限从 21 调到 22）。半年后复查要能解释当时的判定 | 只存 `rule_code` → 无法复现判定；患者质疑「你们凭什么说我不正常」时无法回答 |
| 6 | `trigger_detail` JSONB | 不同异常类型的触发依据结构不同：视力异常要记「实测 0.3 / 阈值 0.5 / 眼别 OD」；眼压异常要记「实测 24 / 阈值 21」。用 JSONB 记录证据本身 | 只存一句描述文本 → 结构化分析（「视力下降超过 2 行的有多少例」）无法做 |
| 7 | `care_task_id` 与 `touch_log_id` 外键 | 异常升级的**通知动作**必须走 M19-03 触达闸门并留痕 | 直接发短信不经闸门 → 违反总纲 §5.4 三道闸门；患者已退订仍收短信，合规风险 |
| 8 | `disposition_ref_no` | 闭环时若转门诊/急诊，要能关联到挂号号或住院号，形成完整证据链 | 结论写了「已来院复查」但查不到是哪次就诊，等于没有证据 |
| 9 | 本表**不设分区** | 年增 8.6 万（按 1,200 执行/天 × 20% 异常率），三年 25.8 万行，索引可全内存 | 过度分区 → 每次查询要多扫分区元数据，小表分区反而更慢 |

### 4.7 表：`m19_fu_lost`（失访登记表）

**用途：** 记录「这次随访最终**没做成**」的正式判定：为什么失访、什么时候判的、判定人是谁、有没有回写 M03-04、M03-04 是否确认收下。失访是一个**有法律与质控含义的业务结论**，不能只是「任务超时了」。

**写入方：** M19-02 失访登记页（P06）+ 超时自动判定任务。**只读方：** M19-08（失访率分析）、M19-03（召回名单）、护士长（失访审核）、M03-04（通过回写间接知道）。

### 4.8 表：`m19_fu_writeback`（回写消息表 / 本地消息表）

**用途：** 实现「**回写 M03-04 绝不丢失**」的本地消息表（Transactional Outbox）。每次需要调用 M03-04（标记 EXECUTING、回写结果、回写失访）时，先在**同一个本地事务**里写一条本表的待办消息，再由后台任务异步消费、退避重试、失败告警。

**写入方：** M19-02 业务 Service（与执行记录同事务写入）；重试任务更新 `attempt`/`next_retry_at`/`msg_status`。**只读方：** 运维（死信排查）、M19-08（回写成功率）、对账任务。

**为什么要有这张表（这是本子模块最关键的一张表）：** 一个随访员每天打 40 通电话，每通 3~8 分钟。结果录完点「提交」的那一刻，如果 M03-04 正在发布、网络抖动、或数据库连接池耗尽，回写就失败了。此时有两条路：

- **同步重试到成功才返回** → 护士的页面卡住甚至报错，她会以为没保存，重新录一遍；40 通电话的成果挂在一次 RPC 上。
- **写进本地消息表，异步重试** → 护士立刻看到「已提交，正在同步」；后台退避重试 30s/60s/120s/240s/480s，绝大多数故障在 60 秒内自愈。

**为什么不能丢（不是技术洁癖）：** 随访员已经把电话打完了——患者被问过一遍、被打扰了一次。如果结果丢了，系统显示任务未完成，护士**明天必须再打一遍**，患者**被同样的随访骚扰两次**。这既是患者体验事故，也直接违反「非医疗必要 ≤ 1 次/24h」的频次闸门精神（同一个任务打两遍，患者感知就是骚扰）。更严重的是：如果这条随访里含异常信号（术后视力骤降），丢失意味着**危险信号永久消失**，没人再去处理。

**字段定义**

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |

**设计说明**

| # | 设计点 | 为什么这样定 | 不这么做会怎样 |
|---|---|---|---|
| 1 | **本地消息表而非直接 RPC** | 业务提交与「待发送」写在同一事务里：要么都成功，要么都回滚。这是 outbox 模式的核心保证 | 先写业务再发 MQ/RPC → 消息发失败就永久丢；先发 MQ 再写业务 → 消息先到、业务回滚，下游收到一条不存在的数据 |
| 2 | **退避 30s / 60s / 120s / 240s / 480s（累计 930s）** | 30 秒足够跨过 M03-04 的滚动发布窗口（典型 20~40 秒）；5 次覆盖约 15.5 分钟 | 立即重试 → M03-04 还在重启，5 次在 2 秒内全部撞死；固定间隔 → 把下游打得更惨 |
| 3 | **`request_body` 必须快照** | 重试时用**原始请求体**重发，而不是重查数据库重新构造——后者可能因期间有人改了备注而发出不同内容 | 重构造 → 重试发出的内容与首次不同，M03-04 收到矛盾数据；且幂等键对应的内容变了，语义失效 |
| 4 | **`uk (biz_type, biz_no, action)`** | 同一次执行的回写只能有一条消息 | 护士反复点提交 → 5 条消息各自重试 → M03-04 收到 5 次回调，若它不做幂等就产生 5 条结果 |
| 5 | **`ck_..._exhausted` 强制 `alert_sent = TRUE`** | 组合约束：重试耗尽的定义就是「已告警」。不告警的 FAILED 消息等于静默丢弃 | 消息躺在表里没人管，表越来越大，实际丢失率无人知晓——这正是「静默丢弃」的排队实现方式 |
| 6 | `msg_status='FAILED'` 而非新增「放弃」状态 | `FAILED` = 自动重试已穷尽、等人工；`DEAD` = 人工明确终止。两个词含义清晰 | 只用 `FAILED` 一态 → 无法区分「等人处理」与「已知不用处理」，死信列表永远清不掉 |
| 7 | `manual_result='MANUAL_SYNC'` | 有些故障无法靠重放解决（如 M03-04 那条任务已被别处删了），只能人工线下同步并留痕 | 强行重放 100 次也没用；不留痕则事后查不出这条结果到底有没有交付 |
| 8 | `trace_id` 与原请求链路打通 | 排查时能从这条消息直接跳到当时的业务请求日志 | 只剩一个 5 位错误码，排查变成猜谜 |
| 9 | 仅有 `created_at`，无 `updated_at` | 消息本体不可变，只有进度推进 | 见上文「本表不设 …」说明 |

### 4.9 表：`m19_fu_touch_log`（随访触达记录表）

**用途：** 记录随访执行过程中**每一次对外触达**（外呼、短信、微信、站内），以及**三道闸门（意愿/时段/频次）的判定结果**——包括被判为 `SUPPRESSED` 而**没有真正发出**的情况。这是合规举证材料，也是频次闸门的计数依据。

**写入方：** M19-02 触达服务（每次发送尝试前后各写一次终态）。**只读方：** 合规审计、M19-08（触达成功率/压制率）、M19-03（频次计数复核）。

**为什么要有这张表：** 总纲 §5.4 规定每次触达前必须过三道闸门，且「宁可漏发也不能错发」。但**没发出去也要留痕**——这是最容易漏的一点。真实场景：患者投诉「你们半夜给我发短信」。系统里查不到那条短信（因为被免打扰闸门拦下了），于是无法自证「我们拦住了」。反过来，如果审计要问「上个月有多少条触达被频次闸门压制」，没有本表就只能回答「不知道」。

```sql
-- 【组合约束 2】已发送必须三道闸门全过、有发送时刻、有消息 ID
ALTER TABLE m19_fu_touch_log
    ADD CONSTRAINT ck_m19_fu_touch_log_sent
    CHECK (touch_status NOT IN ('SENT', 'DELIVERED')
           OR (gate_all_passed = TRUE AND sent_at IS NOT NULL
               AND msg_id IS NOT NULL AND suppress_reason IS NULL));

-- 【组合约束 3】三道闸门全部通过当且仅当三个 passed 都为真
ALTER TABLE m19_fu_touch_log
    ADD CONSTRAINT ck_m19_fu_touch_log_gate_all
    CHECK (gate_all_passed = (gate_blacklist_passed
                              AND gate_time_passed
                              AND gate_frequency_passed));

-- 【组合约束 4】闸门结果与通过标记必须一致
ALTER TABLE m19_fu_touch_log
    ADD CONSTRAINT ck_m19_fu_touch_log_gate_consistent
    CHECK ((gate_blacklist_passed = TRUE) = (gate_blacklist_result = 'PASS')
           AND (gate_time_passed = TRUE)
               = (gate_time_result IN ('PASS', 'MEDICAL_EXCEPTION'))
           AND (gate_frequency_passed = TRUE)
               = (gate_frequency_result = 'PASS'));

-- 【组合约束 5】频次计数不得超出阈值（除非本次就是超限那条）
ALTER TABLE m19_fu_touch_log
    ADD CONSTRAINT ck_m19_fu_touch_log_freq
    CHECK (freq_count_before IS NULL OR freq_limit IS NULL
           OR freq_count_before <= freq_limit);

-- 【组合约束 6】医疗necessary 阈值只能是 2，非医疗必要只能是 1
ALTER TABLE m19_fu_touch_log
    ADD CONSTRAINT ck_m19_fu_touch_log_freq_limit
    CHECK (freq_limit IS NULL
           OR (is_medical_necessary = TRUE AND freq_limit = 2)
           OR (is_medical_necessary = FALSE AND freq_limit = 1));

-- 【组合约束 7】延迟发送必须有延迟时刻
ALTER TABLE m19_fu_touch_log
    ADD CONSTRAINT ck_m19_fu_touch_log_delayed
    CHECK (touch_status <> 'DELAYED'
           OR (delayed_until IS NOT NULL AND suppress_reason = 'QUIET_HOURS'));

-- 【组合约束 8】发送失败必须有失败码
ALTER TABLE m19_fu_touch_log
    ADD CONSTRAINT ck_m19_fu_touch_log_failed
    CHECK (touch_status <> 'FAILED'
           OR (fail_code IS NOT NULL AND fail_reason IS NOT NULL));

-- 【组合约束 9】成本非负
ALTER TABLE m19_fu_touch_log
    ADD CONSTRAINT ck_m19_fu_touch_log_cost
    CHECK (cost_amount IS NULL OR cost_amount >= 0);
```

**设计说明**

| # | 设计点 | 为什么这样定 | 不这么做会怎样 |
|---|---|---|---|
| 1 | **被判压制的触达也要落库** | 「没发」比「发了」更需要在合规上举证。总纲 §5.4 要求三者必须落库 | 只记录成功发送 → 患者投诉「半夜收到短信」时无法证明我们拦住了；审计问「上个月压制了多少条」答不出来，等于三道闸门形同虚设 |
| 2 | **三道闸门各存 passed + result 两列** | `passed` 是布尔结论（供组合约束与统计），`result` 是具体原因（供追溯）。只存布尔 → 只知道被拦，不知道为什么被拦 | 排查「为什么这条随访通知没发出去」时只能看日志，日志只能保留 30 天 |
| 3 | **`ck_..._gate_all` 用等价式而非聚合判断** | 组合约束保证 `gate_all_passed` 绝不能与三个子闸门不一致 | 应用层写错（只判了两个闸门就置 true）→ 未过频次闸门的消息被发出去 |
| 4 | **`ck_..._sent`：已发送必须三闸全过** | 这是把业务规则**钉进数据库**：物理上不可能存在一条「没通过闸门却已发送」的记录 | 只靠代码保证 → 新增一条发送路径（如运营手动补发）忘了过闸门，直接违规 |
| 5 | **`FAIL_CLOSED` 作为独立的闸门结果** | 总纲 §7.4 要求黑名单校验不可用时**失败关闭**。这个状态必须可统计——如果它频繁出现，说明 M03-05 不稳定 | 把「校验服务挂了」混进 `BLACKLISTED` → 看起来像患者退订很多，实际是故障；也不会触发告警 |
| 6 | `freq_limit` 快照 | 阈值来自配置（医疗必要 2 / 非医疗必要 1），配置会调整。存下当时用的阈值才能解释当时的判定 | 只存 `freq_count_before=2` → 半年后不知道当时阈值是 1 还是 2，无法判断压制是否正确 |
| 7 | `touch_date` 生成列 | 频次闸门是「每 24 小时」维度计数；用 `created_at::date` 做索引，查询变成 `WHERE patient_id = ? AND touch_date = ?` 的等值查找 | 每次用 `created_at >= date_trunc('day', now())` → 范围扫描，随着数据增长从 8ms 涨到 120ms |
| 8 | `is_medical_necessary` 显式存 | 医疗必要例外是合规敏感字段（免打扰时段唯一例外），必须可审计 | 靠场景码推断 → `POSTOP` 是否一定医疗必要取决于配置，事后无法复现 |
| 9 | **不存完整消息正文** | 正文在 M03-05，重复存储会导致「两边内容不一致」的争议，且正文含患者信息，多存一份多一份泄露面 | 全量复制正文 → 触达表膨胀 10 倍，且成为事实上的「第二个消息库」 |

### 4.10 表：`m19_fu_config`（随访执行配置表）

**用途：** 存放 M19-02 的**运行参数**：回写重试策略、异常升级阈值、失访判定规则、超时设置、导出限制等。让这些参数可在运行时调整（P08 配置页），而不必改代码发版。

**写入方：** M19-02 配置页（P08，需 `m19:fu:exec:config` 权限）。**只读方：** M19-02 全部服务（启动时加载 + 变更事件刷新缓存）。

**为什么要有这张表：** 三个参数在真实运营中一定会变：① 回写重试次数——M03-04 稳定后可以从 5 次降到 3 次；② 失访自动判定天数——旺季随访积压时运营希望放宽到 15 天；③ 异常视力阈值——不同术式（SMILE vs 高度近视 ICL）的术后合理视力范围不同。写死在代码里意味着每次调整都要走「改代码 → 测试 → 发版 → 重启」，一次发版 4 小时，而运营的需求是当天生效。

**设计说明**

| # | 设计点 | 为什么这样定 | 不这么做会怎样 |
|---|---|---|---|
| 1 | **`scope_id` 用 0 占位而非 NULL** | 共享规范 §17 第 21 条：PostgreSQL 的 UNIQUE 约束认为两个 NULL 互不相等。若 `GLOBAL` 用 NULL，可以插入无数条同 key 的全局配置 | 全局配置出现 3 条重复行，取值取决于查询顺序，行为不可预测——这是最难查的一类线上问题 |
| 2 | `version_no` 单调递增 | Redis 缓存与本地缓存靠版本号判断是否需要重载；比 TTL 更实时 | 只靠 TTL → 配置改了最多 5 分钟才生效，运营改完刷新页面没变化，反复改 |
| 3 | `min_value` / `max_value` / `enum_options` | 参数校验前置到配置页：把重试次数改成 500 次这种输入直接拒绝 | 无校验 → 运维手误把 `max_attempt` 配成 500，M03-04 故障时被重试 500 次，等于对下游发起一次小型攻击 |
| 4 | `is_editable = FALSE` | 有些参数是系统契约的一部分（如 `m19.fu.writeback.biz_type` 枚举），不允许页面改 | 允许改 → 把 `biz_type` 改成不存在的值，回写任务全部失败 |
| 5 | `is_sensitive` + 审计 | 修改异常阈值属于医疗质控敏感操作，必须留痕（写 `m19_fu_log` 并调 M02-06） | 有人把术后视力阈值从 0.5 偷偷改成 0.1，异常上报量骤降，看板「变好了」而实际风险在积累 |
| 6 | `default_value` 单独存 | 支持「一键恢复默认」，出事故时能快速回滚 | 临时改错后无法知道原值是多少，只能翻日志或重新讨论 |
| 7 | 配置分组 `config_group` | P08 页面按 6 个分组渲染，避免 40 个参数平铺成一大坨 | 平铺 → 运维找不到要改的那一项 |

## 附录 E 建表顺序与 Alembic 迁移

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1 | `CREATE EXTENSION IF NOT EXISTS pg_trgm` | 问卷文本检索依赖 trigram |
| 2 | 建 `m19_fu_exec_record` | 无依赖，最先建 |
| 3 | 建 `m19_fu_call_log` 及 12 个月分区 + DEFAULT 分区 | 依赖 `exec_record.id`（逻辑外键） |
| 4 | 建 `m19_fu_answer` | 依赖 `exec_record.id` |
| 5 | 建 `m19_fu_result_detail` | 依赖 `exec_record.id`、`answer.id` |
| 6 | 建 `m19_fu_abnormal` | 依赖 `exec_record.id` |
| 7 | 建 `m19_fu_lost` | 依赖 `exec_record.id`、`call_log` 汇总 |
| 8 | 建 `m19_fu_writeback` | 依赖 `exec_record.id`、`lost.id` |
| 9 | 建 `m19_fu_touch_log` | 依赖 `exec_record.id` |
| 10 | 建 `m19_fu_config` | 无依赖 |
| 11 | 授权 `GRANT SELECT, INSERT, UPDATE ON m19_fu_exec_record, m19_fu_answer, m19_fu_result_detail, m19_fu_abnormal, m19_fu_lost, m19_fu_writeback, m19_fu_config TO app_m19` | 可改的表 |
| 12 | 授权 `GRANT SELECT, INSERT ON m19_fu_call_log, m19_fu_touch_log TO app_m19` | 只增不改的表（配合 REVOKE UPDATE, DELETE） |
| 13 | 初始化 `m19_fu_config` 的 20 条参数（附录 D） | 与配置文件默认值一致 |

**注意事项：**

1. Alembic 迁移脚本必须显式建 DEFAULT 分区，`op.create_table` 之后单独 `op.execute` 建分区，不能依赖 ORM 自动建表。
2. 每月 25 日由 `m19.fu.partition.maintain` 定时任务预建下下月分区，失败告警。
3. `REVOKE UPDATE, DELETE` 必须在数据初始化**之后**执行，否则初始化脚本本身会被拒。
4. 回滚顺序与建表顺序相反；`m19_fu_call_log` 因分区表需先 `DROP TABLE ... CASCADE` 再逐个删分区（PG 16 支持一次删父表级联）。
