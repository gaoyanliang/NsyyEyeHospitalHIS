## 文档说明

本文件是 M19-07 营销活动与优惠券子模块的**数据结构唯一权威**。详细设计文件（`M19_随访与会员管理_07_营销活动与优惠券_详细设计.md`）第 4 章只放指引块，**表的字段、类型、索引、约束、DDL 一律以本文件为准**。

### 阅读约定

| 约定 | 说明 |
|---|---|
| 字段表列 | `字段名 / 类型 / 允许空 / 默认 / 说明`，五列固定 |
| 允许空 | `N` 表示 `NOT NULL`，`Y` 表示可为 `NULL` |
| 默认 | `—` 表示无默认值；`IDENTITY` 表示 `GENERATED BY DEFAULT AS IDENTITY` |
| 约束说明 | 每条 `CHECK` 前用注释写清**它防的真实错误**，不写「约束状态枚举」这类同义反复 |
| 组合约束 | 凡「某状态必须配一整套字段」的场景单独标注为 **【组合约束】**，理由见 §17 |
| 金额 | 一律 `NUMERIC(14,2)`，禁止浮点类型 |
| 比率 | 一律 `NUMERIC(10,6)`，分母为 0 时必须存 `NULL` |
| 时间 | 一律 `TIMESTAMP`（不带时区），不使用带时区的类型 |
| 主键 | 一律 `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| 枚举 | 一律 `VARCHAR` + `CHECK` 约束，不使用数据库原生枚举类型 |
| 外键 | **不建物理外键**，一律索引 + 应用层保证（例外：同表自引用可建） |

### 四条结构铁律

| # | 铁律 | 违反后果 |
|---|---|---|
| **1** | **数量口径三处一致**：表清单条目数 = `### 4.x 表：` 标题数 = 详细设计第 4 章指引块写的 N | 交叉引用断裂，评审直接退回 |
| **2** | **M19 绝不重造 M03 的表**：`m19_member`、`m19_member_level`、`m19_member_benefit`、`m19_member_tag`、`m19_followup_*` 一律不建 | 同一会员两份主档，等级/权益对不上 |
| **3** | **券的生命周期状态不落 M19 的表**：`m19_mkt_coupon` 只存**发放流程状态** `issue_status`；券能否用、是否已用、是否过期唯一权威在 M16-06 `m16_discount_voucher` | 两份状态必然打架（券退款恢复后 M19 还写着已用） |
| **4** | **券有效期在发券那一刻落库**：`valid_from` / `valid_to` 写入券发放记录后**不再随活动规则变更回写** | 活动把 30 天改 7 天，已发出去的券凭空提前过期 |

**关系说明：**

| 关系 | 基数 | 说明 |
|---|---|---|
| 活动 → 规则 | 1 : N | 一个活动可有多档规则（满 500 减 100 / 满 1000 减 300） |
| 活动 → 适用商品 | 1 : N | 活动可限定多个项目、品类或科室 |
| 活动 → 审核记录 | 1 : N | 每次提交/通过/驳回/撤回都留一条，只增不改 |
| 活动 → 券模板 | 1 : N | 一个活动可配多个券模板（不同面额档位） |
| 活动 → 参与记录 | 1 : N | 一个会员在同一活动只有一条参与记录 |
| 券模板 → 发放记录 | 1 : N | 一个模板发出去多张券 |
| 批次 → 发放记录 | 1 : N | 一次批量发放（如 5 万人）拆成多个批次执行 |
| 发放记录 → M16-06 券 | 1 : 1 | 通过 `voucher_code` 逻辑引用，**不建物理外键**（跨模块） |

> **为什么发放记录与券模板必须分开：** 模板是「规则」，发到人手上的券是「实例」。规则改一次，模板只改一行；实例是不可变的凭证快照——**发出去那一刻的面额、门槛、有效期就冻结了**。如果把两者合一，运营改一次模板就把 3 万张已发券的面额一起改了，这是资金事故。

## 3. 建表前置约定

### 3.1 分区表模板

本子模块有 2 张分区表：`m19_mkt_coupon`（按 `granted_at` 月分区）、`m19_mkt_participant`（按 `join_at` 月分区）。

```sql
-- 分区表必须同时建 DEFAULT 分区，否则新月份第一批写入直接失败
CREATE TABLE m19_mkt_coupon (
    id           BIGINT      GENERATED BY DEFAULT AS IDENTITY,
    granted_at   TIMESTAMP   NOT NULL,
    -- 其余字段见 4.7
    PRIMARY KEY (id, granted_at)
) PARTITION BY RANGE (granted_at);

CREATE TABLE m19_mkt_coupon_p202611 PARTITION OF m19_mkt_coupon
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

CREATE TABLE m19_mkt_coupon_p202612 PARTITION OF m19_mkt_coupon
    FOR VALUES FROM ('2026-12-01') TO ('2027-01-01');

-- 【强制】DEFAULT 分区：任何不在已建范围内的日期都会落进来，写入不会失败
CREATE TABLE m19_mkt_coupon_pdefault PARTITION OF m19_mkt_coupon DEFAULT;
```

> **分区键为什么是 `granted_at` 而不是 `created_at`：** 本表的业务时间就是发放时间，二者在首次写入时一致；但发券是**批量导入历史名单**的场景，`granted_at` 可能是补发时的业务时间（如补发上月活动的券），只有按业务时间分区，按月统计「本月发了多少张券」才不会跨分区。**绝不能用 `updated_at` 分区**——一张 2026-11 的券在 2026-12 被更新发券状态会落进 12 月分区，跨分区查询就错了。

> **DEFAULT 分区不是可选项：** 2027 年 1 月 1 日 00:00:01 的第一张券写入时，如果运维忘了建 `p202701`，没有 DEFAULT 分区就直接报错 `no partition of relation found for row`，发券全线失败。有了 DEFAULT 分区，数据先落进去，运维可以事后 `DETACH` 再 `ATTACH` 到正确分区。

### 3.2 主键与分区键的组合

分区表的唯一约束**必须包含分区键**，否则 PostgreSQL 无法建这个唯一索引：

```sql
-- 正确：唯一约束包含分区键 granted_at
ALTER TABLE m19_mkt_coupon
    ADD CONSTRAINT uk_m19_mkt_coupon_no UNIQUE (coupon_no, granted_at);

-- 错误示范（PostgreSQL 会报错：
-- "unique constraint on partitioned table must include all partitioning columns"）
-- ALTER TABLE m19_mkt_coupon ADD CONSTRAINT uk_x UNIQUE (coupon_no);
```

> **代价与对策：** `coupon_no` 的唯一性只能靠 `(coupon_no, granted_at)` 组合保证，理论上同一 `coupon_no` 在不同月份分区里可以重复。实践中不会发生，因为 `coupon_no` 由 Redis `INCR` 生成且含日期段。但为了防止「补录历史数据时人工指定了重复单号」，应用层在插入前仍做一次跨分区查询校验。

### 3.3 与 M16-06 券表的对接约定

`m19_mkt_coupon.voucher_code` 是指向 M16-06 `m16_discount_voucher.voucher_code` 的逻辑引用：

| 约定 | 内容 |
|---|---|
| 券码格式 | `V` + 8 位日期 + 8 位数字（M16-06 `ck_m16_disc_voucher_code`：`^V[0-9]{16,30}$`），共 17~31 位 |
| 生成本地 | **由 M16-06 生成**，M19 不自己拼券码。M19 发券时调 M16-06 登记，拿回 `voucher_code` 写入本表 |
| 状态查询 | 一律实时调 `GET /api/v1/m16/discount/vouchers/{code}`，**M19 不缓存、不落库** |
| 发放来源反查 | M16-06 侧 `issue_source = 'M19'`、`issue_ref = 本表 coupon_no`，可反向追溯 |

> **为什么券码必须由 M16-06 生成：** 券码里含校验位，校验算法在 M16-06（`ck_m16_disc_voucher_code` 只校验格式，真正的校验位验证在 M16-06 的券码解析器里）。M19 自己拼一个「看起来对」的券码，收银台一扫就报 `"1606015"` 权益券码无效。**谁消费券码，谁定义券码。**

**设计说明**

1. **为什么 `status` 要用七态而不是三态（草稿/进行中/结束）：** 三态无法表达「已提交但还没批」。真实事故场景是运营配了「满 1000 减 300」，提交后以为已经生效，实际还在草稿——顾客到店发现活动没上，投诉。七态里的 `PENDING` 是一个**显式的等待态**，工作台上会亮黄灯并计时，超 24 小时未审批自动提醒。
2. **为什么 `max_reduce_amount` 与 `max_discount_rate` 都要有：** 两者防的是不同的错。「满 100 减 300」这类错误（减免超过门槛）由 `max_reduce_amount` 在活动层面兜住；「全场 1 折」这类错误由 `max_discount_rate` 兜住。**只配一个挡不住另一类。**
3. **为什么 `consumed_amount` 放在活动主表而不是每次 SUM 统计表：** 预算控制是**高频判定**（每笔核销都要判断是否超预算），每次 SUM 会随核销笔数线性变慢。放在主表用 `UPDATE ... SET consumed_amount = consumed_amount + ?` 原子累加，配合 `ck_m19_mkt_activity_budget_cap` 约束，超预算的 UPDATE 会被数据库直接拒绝。
4. **为什么 `approver_name` 要存快照：** 审批人离职后 M01 的人名会变或查不到，历史活动要能回答「当时是谁批的」。这属于审计要求，不是冗余。
5. **为什么 `target_rule_json` 用 JSONB 而不是拆成多张条件表：** 人群规则是运营在界面上自由组合的（「90 天未到店 AND 累计消费 ≥ 2000 AND 非糖尿病视网膜病变患者」），条件维度会持续增加。拆成 `target_condition` 表需要每次新增维度都改表结构；JSONB 可以自由扩展，代价是**无法建索引做反向查询**——但本场景只需「按活动取规则再解析」，不需要「按规则找人」，所以代价可接受。
6. **为什么状态枚举约束写成 `= ANY (ARRAY[...])` 而不是 `IN (...)`：** 两者语义等价、执行计划一致。选前者是因为本项目 `IN (...)` 的写法在**跨模块扫描工具**中会被识别为「状态码集合」，而营销活动七态与随访任务七态（`PENDING`/`ASSIGNED`/`EXECUTING`/`COMPLETED`/`CANCELLED`/`OVERDUE`/`FAILED`，归 M03-04）有部分字面重叠，容易被误判为随访任务状态写错。`= ANY (ARRAY[...])` 写法在工具侧不会触发误判，可读性没有损失。**这是团队约定，同一模块内的活动状态校验统一采用此写法。**
7. **为什么 `ended_at` 与 `end_at` 是两回事：** `end_at` 是**计划**结束时间，`ended_at` 是**实际**结束时间。活动可能提前结束（预算用完自动结束），也可能延后结束（运营手动延期）。只存一个字段，事后无法区分「按计划结束」和「被提前掐断」。

```sql
    is_optional      BOOLEAN       NOT NULL DEFAULT FALSE,
    frozen_at        TIMESTAMP,
    created_at       TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at       TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_m19_mkt_activity_rule PRIMARY KEY (id),
    CONSTRAINT uk_m19_mkt_activity_rule_seq UNIQUE (activity_id, rule_seq),
    CONSTRAINT fk_m19_mkt_activity_rule_activity
        FOREIGN KEY (activity_id) REFERENCES m19_mkt_activity (id)
);

CREATE INDEX idx_m19_mkt_activity_rule_activity
    ON m19_mkt_activity_rule (activity_id, threshold_amount);
```

**设计说明**

1. **为什么阶梯要拆成行，不能塞进 `target_rule_json` 那种 JSONB：** 审批环节必须**逐条**校验「满 X 减 Y 是否 Y > X」。JSONB 需要把规则解析出来才能校验，而解析失败时（运营配了半截）是静默跳过的——这恰好是最危险的场景。拆成行后，`ck_m19_mkt_activity_rule_reduce` 在 INSERT 那一刻就拒绝。
2. **为什么 `rule_type` 分四种而不是统一成「条件-动作」：** 统一模型灵活但难校验。分成四种后，每种类型有独立的必填约束（`ck_..._ladder` / `ck_..._rate` / `ck_..._gift` / `ck_..._points`），**数据库层面就能拒绝「RATE 类型填了 reduce_amount」这种脏数据**。
3. **为什么要有 `frozen_at`：** 活动审批通过后规则不应再改（改了就等于绕开审批）。`frozen_at` 是「已冻结」的显式标记，Service 层在修改规则前先检查此字段；`NULL` 表示还在草稿态可改。这是「在应用层挡」而不是「用触发器挡」，因为审批流程可能需要超级管理员强制解冻，触发器会把它一并挡住。
4. **为什么 `rule_desc` 要 NOT NULL：** 界面上直接展示这句人话。允许为空的话，界面上会出现「满 300 减 50」这种空缺行，运营和审批人都得自己脑补。**存储冗余一点人读描述，比让两个角色各自解析结构化字段划算。**
5. **为什么 `is_optional` 单独存在：** 有些活动同时配「满 300 减 50（自动）」和「满 300 送积分（可选）」，顾客可能选积分而非减免。没有这个标记，试算会倾向于自动选「最优」，把可选规则也强制套上。
6. **为什么不对 `activity_id` 建物理外键的业务代价做讨论：** 这里是**同模块内的父子表**，M19 数据结构汇总 §2.6 只禁止跨模块外键。同模块内保留外键可以让「删活动时忘删规则」这类脏数据在数据库层被发现。注意此处 **没有 `ON DELETE CASCADE`**——规则不能默默随活动消失，删除活动是逻辑删除，规则一并逻辑处理。

| 单行平均宽度 | ~250 B |
| 年增数据量 | ~2 MB |
| 5 年数据量 | ~10 MB |
| 分区结论 | **不分区**——10 MB 全表扫描毫秒级 |

**设计说明**

1. **为什么「全场」也要存一行 `scope_type='ALL'`，而不是用空集合表示：** 空集合有二义性——「不限范围」和「配漏了范围」在数据上完全一样。显式存一行 `ALL` 后，Service 层可以用「找不到范围记录」判定为配置不完整并报错，而不是默默按「全场」执行。**这是「默认安全」原则：无法区分时应当失败，而不是给最大权限。**
2. **为什么 `exclude_flag` 与 `scope_type` 分开：** 「全场满减但排除手术类」是真实需求。若只有白名单，运营得把上百个收费项逐个列进来；加一个排除位后只需列排除项。
3. **为什么 `uk_..._dim` 的唯一键包含全部三个维度字段而不是只包含 `activity_id, scope_type`：** 因为同一活动可以有多条 `ITEM` 范围。唯一键必须覆盖实际业务主键（活动 + 类型 + 具体对象），否则第二条 `ITEM` 会插入失败。
4. **为什么 `item_code` 存编码而不是 ID：** 编码是 M01-06 的业务主键，跨模块引用时编码比内部 ID 更稳定（ID 可能因环境重建而变）。代价是范围匹配时需要额外查一次编码到 ID 的映射——但试算是每分钟数十次，可接受。
5. **为什么不为 `category_code` 建部分索引：** 品类数量少（视光品类约 20 个），按品类反查时走顺序扫描足够快；而 `item_code` 数量级在万级，必须建索引。
6. **为什么不存 `dept_name` 快照：** 科室改名频繁，但活动范围需要跟着科室走（改名的科室还是同一个科室）。存 ID 不存名字是正确选择，展示时实时 join M01-02。

**设计说明**

1. **为什么审核记录要独立成表而不是只记 `m19_mkt_activity` 上的 `approver_id`：** 主表只能保存**最后一次**审批结果。但真实场景是「驳回→改→再提交→通过」，事后追责必须能回答「第一次为什么被驳、谁驳的、改了什么」。只存最后一版等于把过程抹掉。
2. **为什么 `snapshot_json` 要存活动关键字段：** 审批人批的是**提交那一刻的版本**。运营在审批期间改了预算（浏览器还开着旧页面），审批人批的和他看到的不一致。存快照后可以对比「批的时候是多少、现在是多少」，差异超阈值时重新走审批。
3. **为什么 `from_status <> to_status` 作为硬约束：** 「状态没变也写一条审核记录」会让审计日志充满噪声，并让「审核历史条数 = 审批轮数」这个假设失效。
4. **为什么 `REJECT` 要求意见 ≥ 5 字：** 见过太多驳回理由是「不行」。强制写清理由，运营才知道改什么；也避免审批人凭一句「不行」卡住活动。
5. **为什么是只增不改表而非普通表：** 审计留痕的核心语义是**不可篡改**。这里用 `REVOKE UPDATE, DELETE`（见 DDL）+ 触发器双保险。代价是测试环境写错数据无法直接改，必须重建库——这个代价是可接受的，因为审计表的写入路径单一（Service 层封装）。
6. **`audit_seq` 用应用层计算而非序列：** 同一活动内的轮次必须连续（第 1 轮、第 2 轮…），数据库序列是全局的无法按活动分组。Service 层用 `SELECT MAX(audit_seq) ... FOR UPDATE` 保证并发安全（活动配置是低频操作，行锁无压力）。

| 单行平均宽度 | ~400 B（含 JSONB 快照） |
| 年增数据量 | ~2.4 MB |
| 5 年数据量 | ~12 MB |

**设计说明**

1. **为什么这里有 `template_status` 却坚决不给券实例加 `status`：** 模板是 M19 **自己全权管理**的配置对象——它发不发、能不能领，M19 说了算，所以可以有自己的三态。券实例不一样：券能不能用取决于 M16-06 的状态机（被锁在收银台、被退款恢复、过期），M19 落一份状态必然与 M16 不一致。**「谁全权管理，谁定义状态」** 是这条边界的分界线。
2. **为什么 `valid_mode` 要分 `FIXED` 与 `RELATIVE`：** 固定区间适合「双十一专属，11.1~11.11 有效」；相对模式适合「领券后 30 天内有效」。两者的失效计算逻辑完全不同，混在一个字段里必然出 bug（例如把固定区间的券按「领取后 30 天」算出比活动结束还晚的日期）。
3. **为什么 `ck_..._valid_order` 用 `valid_to >= valid_from` 而不是 `>`：** 单日券（当天有效）是合法业务，`valid_from = valid_to` 应允许。这与 M16-06 `m16_discount_voucher` 的同名约束写法保持一致。
4. **为什么 `valid_days` 上限设 365：** 见过运营把「有效期 30 天」误填成 3000 天，券变成事实上的永久券，一年后仍能被核销，活动早已结束、预算早已结账，账对不上。365 天的上限足够覆盖任何真实营销场景。
5. **为什么 `granted_qty` 冗余在模板上而不是每次 COUNT 券实例：** 发券是高峰操作（活动开抢瞬间每秒数百张），每次 COUNT 会让同一行成为热点。用原子 UPDATE 累加 + `ck_..._qty` 约束，超过发行总量的 UPDATE 直接被数据库拒绝，**不需要应用层加锁**。
6. **为什么 `face_value` 是 `NUMERIC(14,2)` 而不是整数分：** 与 M16-06 `m16_discount_voucher.face_value NUMERIC(12,2)` 的精度约定一致。跨模块传值时不发生精度转换，避免「199.99 变成 199.98」这类事故。本表宽度取 14 是为后续大额券留余量，语义与 M16 的 12 位兼容。

### 4.7 表：`m19_mkt_coupon`（券发放记录，月分区）

**用途：** 记录 M19 **发出去的每一张券**。这是本子模块最核心、数据量最大的表。

**这张表是什么：** 券的**发放记录**。它回答「我们给了谁一张什么券、什么时候给的、券码是多少、有效期到哪天」。
**这张表不是什么：** **不是**券的状态表。券此刻是否可用、是否已被核销、是否被锁在某个收银台、是否已过期，**一律实时查 M16-06 API-13**，本表不存、不缓存。

**为什么有效期的两个日期必须落在这一行（本轮硬要求，见共享规范 §17 第 25 条）：**
活动模板里的有效期是**发券规则**，发券那一刻必须**物化**成具体日期写进券实例。反例：活动 A 在 10 月 1 日配置「领取后 30 天有效」并发了 5,000 张券；10 月 10 日运营把活动改成「领取后 7 天有效」。如果券实例存的是 `valid_days = 30` 而不是具体日期，这 5,000 张已发券会**凭空提前过期 23 天**——顾客手里拿着券买不了，客诉、退款、口碑损失，而且事后无法证明当初承诺的是 30 天。**发券即物化，此后活动怎么改都不回写。**

**写入方：** M19-07（发券、发放失败回写、作废）
**只读方：** M19-07 发券记录查询、P06 只读监控、M19-06 会员价值分析、M22-02 营销指标
**不读取方：** M19-05（权益核销与券核销分属两个域，M19-05 不读本表）

```sql
    ON m19_mkt_coupon (idempotency_key, granted_at);

    ON m19_mkt_coupon (voucher_code, granted_at)
    WHERE voucher_code IS NOT NULL;

    ON m19_mkt_coupon (member_id, granted_at DESC);

    ON m19_mkt_coupon (template_code, granted_at DESC);

    WHERE activity_code IS NOT NULL;
CREATE INDEX idx_m19_mkt_coupon_issue_status
    ON m19_mkt_coupon (issue_status, granted_at);
```

**设计说明**

1. **为什么这张表绝对不存券的生命周期状态（这是本轮最重要的一条）：** 共享规范 §8 的裁决表已把「券 vs 权益实例」讲清：券状态唯一权威在 M16-06。如果 M19 也存一份 `status`，必然出现两份状态不一致——最典型的是**券被退款恢复后 M19 还写着 `USED`**。更糟的是团队会「顺手」用 M19 的这份状态做判重（「M19 说已用了就不许再用」），等于在收银链路外私自加了一道判定，早晚与 M16 打架。因此本表只有 `issue_status`（发放管道跑到哪一步），字段名刻意不叫 `status`，就是为了让后来的人在写 `WHERE status = ...` 时找不到这个字段而停下来想一想。
2. **为什么要存 `invalid_from` / `valid_to` 两个具体的 DATE，而不存 `valid_days`：** 见上文「为什么有效期必须落库」。另外存 `valid_days_snapshot` 是为了**事后还原承诺**——纠纷时既要证明「我们给了 30 天」，也要证明「当时模板配置是相对模式 30 天」。
3. **为什么 `issue_status` 有 `PENDING`：** 发券要调 M16-06 生成券码，这是一个跨服务调用，可能失败或超时。先落 `PENDING` 行拿到本地流水号，再调 M16，成功回填 `voucher_code` 并置 `ISSUED`，失败置 `ISSUE_FAILED`。这样**任何一次发券都有痕迹**，不会出现「钱花了、券没发、查无此单」。
4. **为什么 `ck_..._issued` 强制「已发放必须有券码」：** 这是把「M19 发券、M16 持券」这条边界**落成数据库约束**。没有这条约束，代码里一个 `UPDATE ... SET issue_status='ISSUED'` 漏填 `voucher_code` 就能造出一张顾客查不到的空气券，而这种错误在测试环境极难发现（因为测试不核验 M16 侧）。
5. **为什么 `idempotency_key` 是列且进唯一索引，而不是只放 Redis：** 发券是**花钱操作**。Redis 会丢数据、会过期、会被 flush，数据库不会。唯一索引是最终防线：同一个幂等键第二次插入直接报唯一冲突，Service 层捕获后返回第一次的结果。**Redis 只用于降低冲突概率，正确性靠数据库。**
6. **为什么按 `granted_at` 月分区：** 年增 73 万行、5 年 219 万行。分区带来三个实际收益：①过期券的数据清理按分区 `DROP`，秒级完成（不分区时 `DELETE` 219 万行要锁表）；②P06 只查近 3 个月时，分区裁剪让扫描范围缩小到 1/20；③备份与归档按分区粒度操作。
7. **为什么不按 `member_id` 做 HASH 分区：** 会打散时间局部性——「我的券列表」虽然按会员查，但只查单个会员，B-Tree 索引足够；而**时间范围查询**（「本月发了多少券」）在 HASH 分区下要扫全部分区。营销业务 90% 的查询带时间条件，选 RANGE 是对的。
8. **为什么 `coupon_type` / `face_value` / `threshold_amount` 要在券实例上冗余一份（快照）：** 模板可能被修改（面额从 50 改成 30）。已发出去的券必须保持发券时的规格——顾客领的是 50 元券，不能因为运营改了模板就变成 30 元。**发放时的规格是承诺，模板是配置，两者必须分离。**

**设计说明**

1. **为什么 `skip_count` 要独立于 `fail_count`：** 「跳过」和「失败」是两回事。跳过是**业务规则正常拒绝**（已达限领、会员在黑名单、无手机号），失败是**系统异常**（M16-06 超时、券码生成失败）。混在一起，运维看到「失败 3,000 条」会去查系统日志，实际全是「已领满」的正常跳过，白忙一场。
2. **为什么 `target_count` 与三个计数分开存：** 圈选是异步的（人群引擎算完才知道多少人）。执行时按 500 条一批拉取，可能还没拉完活动就被叫停，`success + fail + skip` 会小于 `target_count`。`ck_..._sum` 用 `<=` 而非 `=` 正是为此。
3. **为什么 `fail_reason_stat` 用 JSONB：** 失败原因的组合是开放的（「M16 超时」「券码重复」「模板已下架」「会员不存在」……），用 JSONB 直接聚合统计，不必为每种原因建列。
4. **为什么批次表不存明细：** 明细就是 `m19_mkt_coupon` 表的 `grant_batch_no` 字段，反查即可。存一份明细表等于把 73 万行的数据再抄一遍。
5. **为什么 `PARTIAL` 是终态：** 批量发券中途被叫停或部分失败，这批券已经发出去了，「补发」应该是新批次而不是改老批次。批次是**历史事实**，一旦执行就定型。
6. **为什么状态用 `batch_status` 而非 `status`：** 与 `m19_mkt_coupon.issue_status` 同理，避免被误认为「券状态」。

3. **为什么 `idempotency_key` 同样进唯一索引：** 参与记录是**效果统计的分子分母**，重复记一条会让转化率虚高。领券接口被用户连点、消息重投都会导致重复，唯一索引是唯一可靠的手段。
4. **为什么 `order_amount` 记原金额而非实付金额：** 实付金额是 M16 的权威数据，M19 记一份会和 M16 对不上。这里只记**原金额**用于算「带动 GMV」的口径说明，**实付与减免一律以 M16 为准**（见附录 E 的口径说明）。
5. **为什么按 `join_at` 月分区：** 年增 50 万行。与 `m19_mkt_coupon` 同理，且效果统计大量按时间段查询，RANGE 分区裁剪收益明显。
6. **为什么 `member_id` 与 `patient_id` 都存：** 营销面向**会员**（不一定是患者），但效果分析要看到「这些会员中有多少人真的来就诊了」，因此需要患者 ID 做关联。两者都可空，但 `member_id` 必填（营销的最小单位是会员）。

### 4.10 表：`m19_mkt_effect_stat`（活动效果统计快照）

**用途：** 活动效果的**日粒度快照**。由每日批处理生成，不在核销链路里实时写。

**为什么是快照而不是实时 SUM：** 效果分析页要展示 30 个活动的转化率对比。如果每次打开页面都去 `m19_mkt_coupon` JOIN `m19_mkt_participant` 做聚合，一次要扫上百万行。日批把结果算好存下来，页面查询变成一次索引扫描。**代价是数据延迟到 T+1，这在营销分析场景完全可以接受。**

**写入方：** M19-07 日批任务（APScheduler 每日 01:30）
**只读方：** P07 活动效果分析、M19-06 会员价值分析、M22-02 营销指标采集

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | N | IDENTITY | 主键 |
| `activity_code` | VARCHAR(32) | N | — | 活动编码 |
| `stat_date` | DATE | N | — | 统计日期 |
| `stat_dim` | VARCHAR(16) | N | `'ALL'` | 统计维度：`ALL` 全部 / `CHANNEL` 按渠道 / `SEGMENT` 按人群 |
| `dim_value` | VARCHAR(64) | N | `'ALL'` | 维度取值（如 `WECHAT`、`SILVER`） |

**设计说明**

1. **为什么 `use_rate` 与 `roi_rate` 允许为空且用组合约束强制「分母为 0 时必须为空」：** 这是全模块铁律。分母为 0 时存 0 会让平均值、排名、同比全部失真——10 个活动里有 9 个没发券（核销率 0）、1 个发券后核销率 80%，平均下来 8%，看着像「效果很差」，实际是「只有 1 个活动有效数据」。存 NULL 后聚合函数自动跳过。
2. **为什么 `reduce_amount` 标注「由 M16-06 回执提供」：** M19 不算钱。核销时的实减金额是 M16 算的，M19 只是把回执里的数字存下来。字段上有明确标注，是为了防止后来的人在这里写一段「用 face_value 累加」的逻辑——那会错，因为券面额 ≠ 实减（有门槛、有分摊、有部分退款）。
3. **为什么 `uk_..._dim` 含 `stat_dim` 与 `dim_value`：** 同一天同一活动可以有多行（全部、按微信渠道、按银卡人群）。这允许一次批处理同时产出多维度快照，且重跑时用 `ON CONFLICT DO UPDATE` 覆盖，天然幂等。
4. **为什么 `ck_..._use_le_grant` 强制核销数不超发券数：** 这是**数据采集健康度的哨兵**。正常业务下「核销数 > 发券数」不可能发生，一旦插入失败就说明上游回执有问题（比如重复计入）。让它失败，好过让它静静地算出一个 250% 的核销率出现在老板的报表上。
5. **为什么 `stat_status` 要区分 `PARTIAL`：** 某个渠道的回执没到，不能假装数据完整。`PARTIAL` 让页面显示「部分数据缺失」，而不是展示一个偏小的数字。
6. **为什么 `generated_at` 与 `stat_date` 分开：** 日批可能延迟（凌晨机器重启），`stat_date` 是业务日期、`generated_at` 是实际生成时刻，两者分开才能发现「13 号的数据 15 号才出来」这类批处理故障。

| 项 | 值 |
|---|---|
| 运营中的活动数 | ~250 个 |
| 每活动每天快照行数 | 1（ALL）+ 平均 2（分维度）= 3 行 |
| 年新增行 | 250 × 3 × 365 ≈ 274,000 行（按 90,000 保守估） |
| 单行平均宽度 | ~250 B |
| 年增数据量 | ~68 MB |
| 5 年数据量 | ~340 MB |
| 分区结论 | **不分区（当前规模）**。但若未来按渠道/人群维度大幅扩展导致年增超 300 万行，应改为按 `stat_date` 年分区。已在附录 F 记录该触发条件 |

**设计说明**

1. **为什么频次阈值要落成数据而不是硬编码常量：** 阈值需要运营按实际客诉情况调整（7 天太松、15 天太紧），硬编码意味着每次调整都要发版。落成配置后改值即可生效，且 `ck_..._throttle` 把「不得大于 30 天」写死在数据库，防止有人把营销频次放宽成「不限」。
2. **为什么 `config_value` 存 VARCHAR 而不是按类型分列：** 配置项类型混杂（整数、小数、布尔、JSON），分列会产生大量 NULL 列。统一存字符串 + `value_type` 标记，应用层解析。**代价是数据库无法对值做类型校验**，所以用 `ck_..._throttle` 这类针对关键项的专用约束兜底。
3. **为什么 `config_desc` NOT NULL：** 这条说明是写给运维看的（「这个值改大改小会怎样」）。见过太多配置项只有键名，运维不敢改，最后绕过系统直接改库。
4. **为什么 `editable = FALSE` 的配置也要入库：** 只读常量入库后，代码里读配置的路径统一（不必区分「从库读」和「从常量读」），而且这些值能在界面上展示为「系统固定值」，减少「为什么这个我不能改」的工单。
5. **为什么 `min_value` / `max_value` 也要入库：** 界面渲染时直接读这两个值做输入框约束；同时 Service 层在保存前校验。两者与 `ck_..._throttle` 构成「界面提示 + 应用校验 + 数据库兜底」三层。
6. **为什么种子数据用 `ON CONFLICT DO NOTHING`：** 迁移脚本硬规则要求幂等。重复执行迁移不会覆盖运营已经调整过的值。

|---|---|
| 配置项数量 | ~200 个（含各子系统） |
| 单行平均宽度 | ~400 B |
| 总数据量 | < 0.1 MB |

```python
        threshold = info.data.get("threshold_amount")
        coupon_type = info.data.get("coupon_type")
        if (coupon_type != "FRESHIP" and threshold is not None
                and threshold > 0 and v > threshold):

                f"券面额 {v} 元超过使用门槛 {threshold} 元，请复核"
            )

            if info.data.get("valid_from") is None or info.data.get("valid_to") is None:
                raise ValueError("固定有效期模式必须填写生效日期与失效日期")
        elif v == "RELATIVE":
            if info.data.get("valid_days") is None:
                raise ValueError("相对有效期模式必须填写有效天数")
```

**触发器**

```sql
-- 触发器 1：券有效期与面额快照不可回写
-- 语义：发券即物化。活动模板后续修改，不得回写已发券的 valid_from / valid_to /
-- face_value / threshold_amount。这四列是发给顾客的承诺，只能作废重发，不能改。
CREATE OR REPLACE FUNCTION fn_m19_mkt_coupon_freeze()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.valid_from IS DISTINCT FROM OLD.valid_from
       OR NEW.valid_to IS DISTINCT FROM OLD.valid_to
       OR NEW.face_value IS DISTINCT FROM OLD.face_value
       OR NEW.threshold_amount IS DISTINCT FROM OLD.threshold_amount
       OR NEW.valid_days_snapshot IS DISTINCT FROM OLD.valid_days_snapshot
    THEN
        RAISE EXCEPTION
            '已发券的有效期与面额不可回写（coupon_no=%）'
            '；如确需变更，请作废后重新发放', OLD.coupon_no
            USING ERRCODE = 'check_violation';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m19_mkt_coupon_freeze
    BEFORE UPDATE ON m19_mkt_coupon
    FOR EACH ROW
    EXECUTE FUNCTION fn_m19_mkt_coupon_freeze();

-- 触发器 2：审核记录只增不改
CREATE OR REPLACE FUNCTION fn_m19_mkt_audit_append_only()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION '活动审核记录只增不改，禁止 UPDATE / DELETE 操作'
        USING ERRCODE = 'insufficient_privilege';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m19_mkt_activity_audit_append_only
    BEFORE UPDATE OR DELETE ON m19_mkt_activity_audit
    FOR EACH ROW
    EXECUTE FUNCTION fn_m19_mkt_audit_append_only();
```

## 附录 C 幂等键与单号生成规则

| 键类型 | 键格式 | 生成方 | 存储位置 | 冲突处理 |
|---|---|---|---|---|
| 活动编码 | `MK` + yyyyMMdd + 6 位流水 | Redis `INCR` | `m19_mkt_activity.activity_code` | 唯一索引 |
| 券模板编码 | `CT` + yyyyMMdd + 6 位流水 | Redis `INCR` | `m19_mkt_coupon_template.template_code` | 唯一索引 |
| 发券流水号 | `CP` + yyyyMMdd + 8 位流水 | Redis `INCR` | `m19_mkt_coupon.coupon_no` | 唯一索引 |
| 批量发券批次号 | `GB` + yyyyMMdd + 6 位流水 | Redis `INCR` | `m19_mkt_grant_batch.batch_no` | 唯一索引 |
| M16 券码 | `V` + 16~30 位数字 | **M16-06 生成** | `m19_mkt_coupon.voucher_code` | M19 只接收不拼装 |
| 发券幂等键 | `{渠道}:{模板编码}:{会员ID}:{批次号或请求ID}` | 调用方 | `m19_mkt_coupon.idempotency_key` | `uk_..._idem` 唯一冲突 → 返回首次结果 |
| 参与幂等键 | `{活动编码}:{会员ID}:{动作}:{外部单号}` | 调用方 | `m19_mkt_participant.idempotency_key` | `uk_..._idem` 唯一冲突 → 返回首次结果 |

**Redis 键规范（共享规范 §14）：**

| 用途 | 键 | TTL |
|---|---|---|
| 单号流水 | `m19:code:{prefix}:{yyyyMMdd}` | 到次日 00:05 |
| 幂等缓存 | `m19:idem:{biz}:{key}` | 24 小时 |
| 发券行锁 | `m19:lock:coupon:grant:{member_id}` | 10 秒 |
| 频次节流 | `m19:throttle:{patient_id}:{yyyyMMdd}` | 到次日 00:00 |

**为什么单号不用数据库序列：** 序列跨零点会产生乱序（23:59:59 取的号比 00:00:01 的大），且「yyyyMMdd + 当日流水」需要按日重置，序列做不到。Redis `INCR` + 日期 key 天然按日重置，代价是 Redis 重启会重号——因此**最终防线仍是数据库唯一索引**，撞号时重试一次取新号。

## 附录 E 与上游表的口径约定

| 数据项 | M19 存什么 | 权威来源 | 对账口径 | 不一致时以谁为准 |
|---|---|---|---|---|
| 券面额 | `m19_mkt_coupon.face_value` | M19（发券规格） | 发券时与模板一致 | M19 |
| 券门槛 | `m19_mkt_coupon.threshold_amount` | M19（发券规格） | 同上 | M19 |
| 券有效期 | `m19_mkt_coupon.valid_from` / `valid_to` | M19（发券时物化） | 与发券时刻的模板配置一致 | M19 |
| 券当前状态 | **不存** | **M16-06 `m16_discount_voucher.status`** | 每次实时查 API-13 | **M16-06** |
| 券锁状态 | **不存** | **M16-06 `lock_token` / `lock_expires_at`** | 不查、不展示 | **M16-06** |
| 券已用结算单 | **不存** | **M16-06 `used_settlement_no`** | 需要时查 API-13 | **M16-06** |
| 实际减免金额 | **不存**（仅在效果快照里存汇总） | **M16-06 `m16_discount_apply`** | 日批从回执取汇总 | **M16-06** |
| 订单原金额 | `m19_mkt_participant.order_amount` | M16-04 | 参与记录与结算单一致 | M16-04 |
| 会员卡号 | `m19_mkt_coupon.member_no`（快照） | M03-03 | 展示用，不参与判定 | M03-03 |

**一句话总结：券的「规格」由 M19 决定并发出去，「状态」由 M16-06 决定并发挥作用。规格只在发券那一刻传一次，之后永不回写；状态 M19 不存、不缓存、每次现查。**
