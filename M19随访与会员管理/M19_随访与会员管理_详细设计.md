## 1. 模块定位

### 1.1 一句话定位

**M19 随访与会员管理是全院「患者关系运营」的执行层与运营层**：一手抓**随访执行**（把 M03-04 已经生产出来的随访任务真正打出去、问出结果、把异常捞出来），一手抓**会员运营**（积分、成长值、权益核销、营销活动、关怀召回），并为视光、屈光、门诊提供统一的会员识别、触达与运营分析能力。

### 1.2 为什么随访执行与会员运营必须独立成模块

| # | 理由 | 事实支撑 |
|---|---|---|
| 1 | **任务生产与任务执行是两种完全不同的能力，必须解耦** | M03-04 已经建好 11 张随访表（模板 / 节点 / 计划 / 任务 / 分派规则 / 各种日志），它回答的是「谁该在术后第几天被随访」。但「这次随访有没有真的打出去」这个问题它答不了：M03-04 的 1.1 节原文明确写着「不做电话外呼、问卷填写、随访结果归档、随访运营分析（这些归 M19）」。**没有 M19，M03-04 生产的随访任务永远停在 PENDING** |
| 2 | **积分是负债，必须有独立的账本** | 未消耗积分是医院的**预计负债**：1 积分抵 0.01 元时，100 万积分就是 1 万元待兑付负债。M03-03 会员子模块的 1.1 节明确把「积分、成长值、权益核销、优惠券、营销活动」划给 M19。把积分流水放在会员主档模块里，会出现「改个会员名字把积分流水也改掉了」的风险 |
| 3 | **权益核销横跨收费、配镜、屈光三个场景，不属于任何单一业务模块** | 一张 200 元代金券，可能在 M16 门诊结算用、在 M10 配镜用、在 M11 屈光手术用。三个模块各自实现核销 → 一张券被核三次。必须有一个中立的核销服务，用「核销单号 + 权益实例号」双唯一索引挡住重复 |
| 4 | **触达需要全院统一的频次闸门** | 患者术后第一天收到 M11 的术后随访短信、第二天收到 M10 的复查提醒、第三天收到 M19 的生日关怀短信、第四天收到营销活动的券到账短信——**四条短信来自四个模块，每个模块都觉得自己只发了一条**。只有集中到 M19，才能实现「24 小时内非医疗必要触达不超过 1 次」这种跨模块的约束 |
| 5 | **随访与会员的运营分析需要同时具备两条业务线的数据** | 「术后随访依从性高的患者，会员复购率是否更高」这个问题跨了随访和会员两条线，只有同时拥有两侧事实的模块才答得了 |

### 1.3 与相邻模块的边界

| 模块 | 归它的 | 归 M19 的 |
|---|---|---|
| **M03-04 随访** | 随访模板、随访节点、随访计划生成、随访任务生成、任务分派规则、任务状态与逾期监控 | **随访任务的执行**（外呼、问卷、结果录入）、随访执行过程记录、随访依从性与失访率分析 |
| **M03-03 会员** | 会员主档、会员等级定义、权益定义、等级与权益的对应、会员标签定义 | **积分账户与流水、成长值计算与等级回写、权益实例（已领的券）、权益核销单、优惠券、营销活动** |
| **M03-05 消息** | 短信 / 微信 / 站内信 / 邮件的**实际发送**与回执 | 触达的**编排与决策**（该不该发、发什么、什么时间发）、触达记录与效果 |
| **M03-01/02 患者** | 患者主档、EMPI、患者合并 | 患者合同时**积分与权益的重定向**（订阅 `m03.patient.merged`） |
| **M03-06 门户** | 患者端界面 | 通过 P-08 提供可用权益，通过 `m19.coupon.granted` 事件通知 |
| **M10-08 视光会员** | 视光专属会员档案、配镜套餐、视光权益 | 通用积分与券；视光套餐不走 M19 |
| **M10-09 / M11-06 复查与术后随访** | 到期复查清单（P-24）、术后随访清单（P-12）、随访计划创建通知（P-26 / P-13） | 聚合这些清单到统一待办（P-01），执行后回写 |
| **M16 收费结算** | **金额的唯一权威**：收钱、开票、日结、退费、优惠试算的最终计算 | 消费后**发积分**、结算时**核销权益**；M19 不计算任何收退金额 |
| **M17 财务核算** | 积分负债的会计科目归集 | 积分负债与消耗的**业务口径统计**；不算钱、不做账 |
| **M22 报表与决策支持** | 全院统一指标口径与跨模块报表 | 本模块运营指标（随访完成率、依从性、失访率、复购率、积分负债）的事实产出与内部契约（P-02 / P-12） |
| **M20 移动办公** | 移动端界面 | 通过 P-01 提供移动随访待办 |
| **M02 权限与安全** | 用户、角色、权限、审计 | 通过 `POST /internal/v1/m02/audit/record` 留痕；积分调整与权益核销**必须**审计 |

> **一句话边界：M03-04 回答「谁该在什么时候被随访」，M19 回答「这次随访打出去了吗、问出了什么、异常有没有捞出来」；M03-03 回答「这个患者是什么等级、享有哪些权益」，M19 回答「他还剩多少积分、券核销了没有、这个月比上月多花了还是少花了」。**

### 1.4 一条不可逾越的红线

```
❌ 禁止：CREATE TABLE m19_followup_plan / m19_followup_task / m19_followup_template
❌ 禁止：CREATE TABLE m19_member_level / m19_member_benefit / m19_member
❌ 禁止：UPDATE m19_points_account SET points_balance = ...   -- 绕开流水改余额
❌ 禁止：UPDATE m19_points_ledger SET points = ...            -- 流水只增不改
❌ 禁止：直接读 mpi_followup_task 表                          -- 必须走 M03-04 内部接口
❌ 禁止：直接读 mpi_member / mpi_member_level 表              -- 必须走 M03-03 内部接口
❌ 禁止：在未校验黑名单/退订的情况下调用消息发送接口
✅ 正确：M19-02 待办 = GET /internal/v1/followup/tasks/pending
✅ 正确：会员等级 = GET /api/v1/mpi/members/{member_id}
✅ 正确：积分发放 = INSERT m19_points_ledger（含 balance_after）+ 校验账户余额一致性
```

> **这条红线是被真实风险逼出来的。** 如果 M19 自建随访计划表，同一台屈光手术会同时被 M11-06（术后随访清单）和 M19（自建计划）各生成一条随访任务，护士在 M03-04 的任务监控里看到一条、在 M19 的工作台里看到另一条，两条都标「术后第 1 天复查」，患者接到两个电话。**同一个业务事实只能有一份权威数据。**

### 2.3 为什么这八个、不是别的分法

| 备选分法 | 为什么不采用 |
|---|---|
| 只分「随访」+「会员」两个大子模块 | 两个子模块各要 33 页、120+ 接口、200+ 错误码，单个文件会超过 15,000 行，无法维护 |
| 把「积分」与「权益核销」合成一个（都是「会员权益」） | 积分是**数值型余额**（可部分使用、可过期、有倍率），权益实例是**离散凭证**（一次性、有有效期、可冻结）。两者的事务模型、幂等策略、对账方式完全不同：积分对账对的是「余额 = 流水累加」，核销对账对的是「已用数 = 单据数」 |
| 把「关怀召回」与「营销活动」合起来 | 关怀是**一对一服务行为**（生日祝福、术后关怀），营销是**一对多触达**（满减活动、发券）。关怀失败是服务缺失，营销失败是流量损失；两者的审批、预算、频次闸门不同 |
| 把「随访运营分析」并入「会员运营分析」 | 两者的服务对象不同：随访分析给护理部与医务科看（依从性、失访率），会员分析给市场部与运营看（复购、分层）。混在一起会导致看板权限无法切分 |
| 把「随访执行」并入「随访中心」 | M03-04 已经把「生产」与「执行」拆开了，M19 内部再合成一个，会出现「改了执行逻辑要重新回归任务池」的耦合。分开后 M19-01 是配置与聚合，M19-02 是高频写操作（外呼一次写 5 张表），两者数据库负载特征完全不同 |

## 3. 随访与会员双闭环

### 3.1 随访闭环

```
  手术 / 出院 / 配镜 / 门诊（M06 / M09 / M11 / M10 / M04）
                    │
                    ▼ 业务事件
        ┌───────────────────────────┐
        │  M03-04 生成随访计划与任务   │  ← 模板 + 节点偏移 + 分派规则
        │  (mpi_followup_plan/task)  │
        └─────────────┬─────────────┘
                      │ m03.followup.task.created 事件 / P-12 / P-24 清单
                      ▼
        ┌───────────────────────────┐
        │  M19-01 任务池聚合          │  ← 三源合并 + 优先级排序 + 分派
        └─────────────┬─────────────┘
                      │ 护士看到待办
                      ▼
        ┌───────────────────────────┐
        │  M19-02 执行               │  外呼 / 发微信 / 填问卷
        │  POST .../start → .../result │  ← 回写 M03-04
        └─────────────┬─────────────┘
                      │ m19.followup.executed / m19.followup.lost
        ┌─────────────┴─────────────┐
        ▼                           ▼
   正常完成                     异常 / 失访
        │                           │
        ▼                           ▼
  ┌───────────┐            ┌────────────────┐
  │ M19-08 统计 │            │ M19-03 关怀召回 │  ← 失访患者进召回名单
  │ 依从性/失访 │            └────────────────┘
  └───────────┘
```

**闭环的关键一环：失访必须回写。** M03-04 的任务只有 `FAILED` 这一个终态能表达「这个病人找不到了」。如果 M19 只在本地记一条失访、不回写，M03-04 里这条任务会一直停在 `EXECUTING`，逾期监控统计就会永远偏高。所以 §8 定死：**失访登记成功 = 本地写 `m19_fu_lost` + 调 `POST /internal/v1/followup/tasks/{id}/result` 回写 `FAILED`**，两步必须在同一事务 + 本地消息表保证最终一致。

### 3.2 会员闭环

```
    消费（M16 结算 / M10 配镜 / M11 手术）
                    │
                    ▼ m16.settlement.completed / P-03
        ┌───────────────────────────┐
        │  M19-04 积分发放            │  ← 规则的倍率取「消费时的等级快照」
        │  INSERT points_ledger      │
        └─────────────┬─────────────┘
                      │ 积分累加 → 成长值累加
                      ▼
        ┌───────────────────────────┐
        │  成长值达到阈值 → 等级变化   │
        │  POST /internal/v1/mpi/members/{id}/level 回写 M03-03
        └─────────────┬─────────────┘
                      │ m19.member.level_changed
                      ▼
        ┌───────────────────────────┐
        │  M19-07 营销活动发券         │  ← 按新等级定向发券
        └─────────────┬─────────────┘
                      │ m19.coupon.granted
                      ▼
        ┌───────────────────────────┐
        │  M19-05 权益核销            │  ← 下次消费时核销
        │  P-06 / P-08               │
        └─────────────┬─────────────┘
                      │ 核销数据
                      ▼
        ┌───────────────────────────┐
        │  M19-06 会员运营分析         │  ← 复购 / 分层 / 流失
        │  识别沉默客户 → M19-03 召回   │
        └───────────────────────────┘
```

**闭环的关键一环：积分倍率必须取消费发生时的等级快照。** 举例：李女士 2026-10 消费 2,000 元时是银卡（1 元 = 1 分），2027-01 升到金卡（1 元 = 1.5 分）。如果积分倍率是实时计算的，2027-03 做「2026 年积分补算」时，会按金卡倍率把她 10 月的消费算成 3,000 分，比实际多发 1,000 分。所以 `m19_points_ledger` 必须有 `level_at_txn` 列，记录**消费发生时**的等级。

### 3.3 两条线的交叉点

| 交叉场景 | 数据流 | 说明 |
|---|---|---|
| 术后随访发现异常 → 关怀召回 | M19-02 判 `abnormal_flag` → 发 `m19.followup.executed` → M19-03 生成 `POSTOP` 关怀计划 | 例：屈光术后 1 月随访主诉「夜间眩光」→ 自动生成「预约复查提醒」关怀 |
| 随访依从性低 → 会员流失预警 | M19-08 算依从性 → M19-06 纳入流失模型特征 | 依从性是流失的强预测因子：连续 2 次随访未接通的会员，6 个月流失率显著更高 |
| 会员消费 → 触发随访 | M16 结算完成 → M19-04 发积分 → M19-03 判是否需关怀（如大额屈光手术） | 例：单笔屈光消费 ≥ 20,000 元 → 生成 `POSTOP` 关怀 |
| 关怀触达 → 随访任务提醒 | M19-03 触达前查 M03-04 计划（`GET /internal/v1/followup/plans/by-patient/{patient_id}`） | 避免同一天既发关怀短信又发随访短信 |

| 状态 | 含义 | 谁能改 | M19 的动作 |
|---|---|---|---|
| `PENDING` | 计划已生成任务，尚未分派 | M03-04 | 只读（出现在任务池「未分派」） |

| `COMPLETED` | 执行完成并录入结果 | **M19**（`POST .../result`） | 写 |
| `FAILED` | 执行失败（拒访、号码无效、联系不上） | **M19**（`POST .../result`） | 写 |
| `OVERDUE` | 超过计划日期未执行 | M03-04 定时任务 | 只读（M19 标红提示） |
| `CANCELLED` | 业务上取消 | M03-04 | 只读 |

> **M19 只能写 `EXECUTING` / `COMPLETED` / `FAILED` 三个状态**，其余四个由 M03-04 维护。M19 内部的「执行态」是另一套对象（见 4.2），两者用 `task_id` 关联。

### 4.2 M19 随访执行记录状态

```
   ┌──────────┐  开始执行   ┌────────────┐  提交结果   ┌───────────┐
   │  DRAFT   │───────────▶│  IN_PROGRESS│───────────▶│ SUBMITTED │
   │ 待执行    │            │  执行中      │            │ 已提交     │
   └────┬─────┘            └──────┬─────┘             └─────┬─────┘
        │                         │ 放弃                    │ 回写 M03-04 成功
        │                         ▼                        ▼
        │                   ┌──────────┐            ┌───────────┐
        │                   │ ABANDONED│            │  CLOSED   │
        │                   │ 已放弃    │            │  已闭环    │
        │                   └──────────┘            └───────────┘
        │ 超时未开始
        ▼

   │ EXPIRED  │  超时失效（任务池缓存过期）
   └──────────┘
```

> **`SUBMITTED` 与 `CLOSED` 必须分开。** `SUBMITTED` 表示 M19 本地已经录完结果，`CLOSED` 表示**已经成功回写 M03-04**。如果只用一个状态，回写失败的记录会混在「已完成」里，M03-04 侧的逾期统计就错了。回写失败进本地消息表重试，重试 5 次仍失败则告警 + 人工介入。

### 4.3 积分账户与流水状态

**账户状态：** `ACTIVE`（正常）→ `FROZEN`（冻结，风控或争议）→ `ACTIVE`；`ACTIVE`/`FROZEN` → `CLOSED`（会员注销，余额必须清零）。

**流水状态：** 积分流水**没有状态**——它是只增事实，一旦写入即终态。任何更正都通过**新增一条反向流水**（`REVERSE` / `ADJUST`）实现，而不是改原行。

```
  余额 = Σ(GRANT + REFUND + 正向 ADJUST) − Σ(DEDUCT + EXPIRE + 反向 ADJUST + REVERSE)
```

> **为什么流水没有状态：** 一旦允许「把某条流水改成已撤销」，就必须回答「余额要不要回退」「回退了别的流水引用它怎么办」「并发时读到一半的状态怎么办」。只增流水 + 反向流水是记账业几百年的成熟做法，也让「这条积分是怎么来的」这个问题永远答得出来。

```
   发放
    │

┌──────────┐   核销   ┌────────┐   撤销   ┌──────────┐
│AVAILABLE │────────▶│  USED  │────────▶│ REVOKED  │
```

|---|---|---|
| `AVAILABLE` | ✅ | 在有效期内且未使用 |

| `EXPIRED` | ❌ | 超过 `valid_to`（定时任务批量置位） |
| `FROZEN` | ❌ | 争议或风控冻结（如怀疑刷单） |
| `REVOKED` | ❌ | 已撤销，券回到 `AVAILABLE` 或作废（按撤销原因） |

> **`USED → REVOKED` 是一个真实业务需求，但要分清走哪条链**（V1.1 裁决后修订）：
>
> - **金额型优惠凭证（券）**：患者配镜用了 200 元**券**，第二天来退货。该券的状态机在 **M16-06 `m16_discount_voucher`**（`USED → ISSUED` 由 M16-06 在退费成功后自行恢复），**M16 不调 P-07**。M19 只有 `m19_mkt_coupon` 发放记录（`issue_status`），不感知券的使用与恢复。
> - **非金额型/跨场景权益实例**：患者用了「免费停车」权益后要求撤销，M16 调 `P-07 revoke`，`m19_benefit_instance` 从 `USED` 回到 `AVAILABLE`（若仍在有效期内）或直接 `REVOKED`（若已过期）。
>
> **判据：核销发生在收银台且改变应付金额 → 归 M16-06；否则 → 归 M19-05。** 详见共享规范 §8「券 vs 权益实例」对照表。

## 6. 核心计算模型

### 6.1 积分发放金额

```
发放积分 = ROUND(消费金额 × 积分倍率 × 规则权重, 2)
```

| 要素 | 取值来源 | 边界 |
|---|---|---|
| 消费金额 | `P-03` 请求体的 `biz_amount`（**调用方传入，M19 不自行计算**） | `> 0`；退费为负时走冲正流程而非本公式 |
| 积分倍率 | `m19_points_ledger.level_at_txn` 对应的 `m19_points_rule` 倍率表 | 取**消费发生时**的等级，不是当前等级 |
| 规则权重 | `m19_points_rule.rule_type = 'BY_AMOUNT'` 时的 `ratio` | `> 0` |

**算例：** 李女士 2026-10-21 门诊结算 328.50 元，当时等级为银卡（`level_at_txn = 'SILVER'`），银卡规则 `ratio = 0.10`（1 元 = 0.1 分）。
- 发放积分 = ROUND(328.50 × 0.10 × 1.0, 2) = **32.85 分**
- 流水写 `txn_type = 'GRANT'`，`points = 32.85`，`balance_after = 1000.00 + 32.85 = 1032.85`

若同一笔结算在 2027-01 被重放（幂等），`(biz_type, biz_no, rule_code)` 命中已有流水，返回首次结果 `idempotent_replay = true`，**不会**按新等级重算。

### 6.2 成长值

```
成长值增量 = ROUND(消费金额 × 成长值系数, 2)          （系数默认 1.0，即 1 元 = 1 成长值）
成长值 = Σ 全部正向成长值流水 − Σ 全部负向成长值流水
```

**成长值只增不减**（除管理员调整 `ADJUST`）。等级判定：

```
等级 = MAX( level_threshold WHERE threshold <= 当前成长值 )
```

**算例：** 李女士累计成长值 12,800。
- 银卡门槛 5,000、金卡门槛 10,000、白金 30,000
- 12,800 ≥ 10,000 → **金卡**（下次升级需 30,000）
- 等级变化后调 `POST /internal/v1/mpi/members/{member_id}/level` 回写 M03-03，成功后发 `m19.member.level_changed`

> **成长值为什么只增不减：** 如果按消费额滚动计算（最近 12 个月消费额），金银卡用户在某些月份会掉级。掉级会在毫无预警的情况下减少用户的积分倍率与权益，是最伤害用户感情的体验。所以成长值做**终身累计**，另外单独用「会员分层」和「流失预警」来识别活跃度下降（见 6.5）。这两件事必须分开，不能用一个指标同时承担。

### 6.3 随访完成率与依从性

```
随访完成率 = 完成随访任务数 / 应完成随访任务数 × 100%
依从性     = 按期完成随访任务数 / 应完成随访任务数 × 100%
```

| 指标 | 分子 | 分母 | 差异说明 |
|---|---|---|---|
| 完成率 | `status = 'COMPLETED'` 且 `executed_at` 在统计期内 | 统计期内 `plan_date` 落在区间的全部任务（含 CANCELLED 之外的所有状态） | 逾期后补做也算完成 |
| 依从性 | `status = 'COMPLETED'` 且 `executed_at <= plan_date + 宽限期（默认 3 天）` | 同上 | **严格口径**，逾期补做不算 |

**算例：** 某科室 2026-10 共有 120 条应随访任务。
- 完成 96 条（其中 84 条在计划日后 3 天内完成，12 条逾期补做）、失败 18 条、逾期未做 6 条
- 随访完成率 = 96 / 120 = **80.00%**
- 依从性 = 84 / 120 = **70.00%**
- 两者相差 10 个百分点，全部来自「逾期补做」——这正是需要被管理层看到的信息

> **分母为 0 时返回 `NULL` 而不是 0。** 一个新开的科室某月 0 条应随访任务，完成率应该是「无数据」而不是「0%」。返回 0 会让科室排名把它排在最后一名，这是对数据的误用。所有比率字段都遵循这一条：`CHECK (denominator > 0 OR ratio_value IS NULL)`。

### 6.4 权益核销的优惠金额

**M19 不计算优惠金额。** M19 只回答两个问题：「这张券现在能不能用」（P-08）与「这张券已经用了，请把结果记账」（P-06）。

```
可用券 = 满足全部条件的 availabile 权益实例：
         ① status = 'AVAILABLE'
         ② valid_from <= 结算时刻 <= valid_to
         ③ 券适用的业务类型与当前结算匹配（applicable_biz_type）
         ④ 券适用的科室/项目与当前结算匹配（如限定眼科门诊）
         ⑤ 未达限额（usage_limit_per_member）

优惠金额 = 调用方（M16 收银台）自行试算后的结果，随核销请求传入 discount_amount 字段
计算依据 = 同请求传入 discount_basis（策略编码 / 叠加模式 / 组合序号 / 计税基数 / 试算时刻），
           M19 原样存为 discount_basis_snap，不重算
核销记录 = M16 结算成功后调 P-06 落账
```

> **为什么 M19 不算钱：** 算优惠要读商品价格、项目折扣、医保政策、结算方式——这些全在 M16。如果 M19 也算一遍，两边算法只要有一分钱差异，就是「收银台显示减 200，会员中心显示减 199.5」的对账噩梦。**算钱的模块只能有一个，M19 只是券的账本。**

> **为什么 M19 也不「调 M16 试算」（V1.2 更正）：** V1.0/V1.1 曾写「优惠金额 = M16 试算（`POST /internal/v1/billing/discount/trial`）的结果」，该路径已撤回，完整核查见共享规范 §9.7 的裁决块。一句话概括：M16-06 的 `calc`（API-27）没有详述块、调用方只写 M16-01；对外的 `trial`（API-02）要求 `settlement_no` 且第一步就 `_load_base` 加载结算单清单——**而 M19 核销时结算单尚未建立**（核销发生在收银台算完价之后、落单之前），还需要收费员身份。**能通用的形态只有一种：调用方已经算好了，把它连同依据一起送过来。**
>
> M19 侧只做两件不涉及算钱的事：① 校验 `0 <= discount_amount <= discount_basis.base_amount`；② 校验通过后把 `discount_basis` 原样落 JSONB。**校验是为了挡住明显错传（把 400 元减到 1000 元基数上），不是为了替 M16 复核算法。**
>
> 依据快照必须落库：M16-06 的试算缓存 `m16:discount:trial:{settle}:{hash}` 只有 120s TTL，事后再对账已无据可查；把依据留在核销记录里，才能回答「这 200 元当时是怎么算出来的」。

### 6.5 会员复购率（**必须与 M22-05 口径一致**）

```
复购率 = 窗口内有 ≥ 2 次有效消费的顾客数 / 窗口内有 ≥ 1 次有效消费的顾客数 × 100%
```

**识别键必须同时给两个口径：**

| 口径 | 主键 | 特点 |
|---|---|---|
| **主口径** | `patient_id` | 覆盖全部回头客（含未办卡的） |
| **辅助口径** | `member_id` | 只覆盖办了卡的会员 |

**实测差距（来自 M22-05 的算例）：** 同一门店同一窗口
- `patient_id` 口径：1,240 个顾客中 428 人复购 → **34.52%**
- `member_id` 口径：682 个顾客中 186 人复购 → **27.27%**
- **相差 7.24 个百分点**，因为办卡率约 40%，只按会员卡统计会把未办卡的回头客全部漏掉

> **M19-06 必须同时给出两个口径并注明差异原因。** 只给 `member_id` 口径会让运营误以为复购率只有 27%，进而做出「加大力度发卡」的错误决策——而真正的问题是复购本身没被识别出来。

### 6.6 积分负债

```
期末积分负债（元） = 期末未消耗积分总额 × 积分兑付比例
积分兑付比例 = 1 积分可抵扣的金额（默认 0.01 元/分）
```

**算例：** 2026-10-31 全系统未消耗积分合计 12,860,000 分，兑付比例 0.01 元/分 → 预计负债 **128,600.00 元**。

**必须同时给出的辅助指标：**

| 指标 | 公式 | 用途 |
|---|---|---|
| 积分消耗率 | 期间消耗积分 / 期间发放积分 | 判断是否在「超发」：长期 < 30% 说明积分发了但用不出去，负债在累积 |
| 积分过期率 | 期间过期积分 / 期间到期积分 | 判断有效期设置是否合理 |
| 单客平均积分余额 | 未消耗积分总额 / 有余额会员数 | 结合兑付比例看人均负债 |

> **积分负债是会计意义上的负债**：医院已经承诺「这些积分将来可以抵现」，但还没有实际支出。M19-08 只提供业务口径的数字与趋势，**会计科目的归集与计提由 M17 负责**，M19 不出任何会计凭证。

## 7. 技术架构

### 7.1 分层架构

```
┌──────────────────────────────────────────────────────────────────────┐
│ 接入层：网关（鉴权 / 限流 / 灰度）                                    │
├──────────────────────────────────────────────────────────────────────┤
│ 接口层 FastAPI                                                       │
│   对外 /api/v1/m19/{sub}/*      内部 /internal/v1/m19/*  + P-05      │
├──────────────────────────────────────────────────────────────────────┤
│ 业务层 Service                                                        │
│   随访执行编排 · 积分记账 · 权益核销 · 关怀判定 · 营销活动 · 运营计算    │
├──────────────────────────────────────────────────────────────────────┤
│ 领域层                                                               │
│   PointsLedger（记账） · BenefitRedeemer（核销） · TouchGate（三闸门）  │
│   FollowupExecutor（执行） · MemberSegmenter（分层）                   │
├──────────────────────────────────────────────────────────────────────┤
│ 数据层                                                               │
│   PostgreSQL 16（事实与账本）  Redis 7（缓存/幂等/锁/频次）            │
├──────────────────────────────────────────────────────────────────────┤
│ 异步层                                                               │
│   Celery（外呼回调/批量发券/积分批算） APScheduler（到期任务/生日关怀）│
├──────────────────────────────────────────────────────────────────────┤
│ 集成层                                                               │
│   M03-04 FollowupClient · M03-03 MemberClient · M03-05 MessageClient  │
│   M11 PostopClient · M10 OpticalClient · M16 BillingClient · M01 Mdm  │
└──────────────────────────────────────────────────────────────────────┘
```

### 7.2 各层职责与约束

| 层 | 职责 | 约束 |
|---|---|---|
| 接口层 | 参数校验、权限、限流、响应包装 | **不写业务逻辑**；禁止直接操作 ORM |
| 业务层 | 事务边界、业务编排、跨模块调用 | 一个 Service 方法 = 一个事务（除非显式声明） |
| 领域层 | 纯业务规则（记账公式、核销判定、闸门判定） | **不依赖 FastAPI、不依赖 Session**，可单测 |
| 数据层 | 持久化 | 所有写操作必须落审计（积分调整/权益核销/参数变更） |
| 异步层 | 不阻塞主链路的操作 | 必须幂等；必须有死信队列 |

### 7.3 关键技术决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **积分余额存账户表 + 流水表双写，以流水为准** | 只存流水则每次查余额都要 SUM（百万级流水性能不可接受）；只存账户则无法审计。双写 + 每日对账任务（`余额 == Σ流水` ）是最务实的方案 |
| 2 | **核销用行锁 `SELECT ... FOR UPDATE` 而非乐观锁** | 核销是低频（相比查询）但绝对不能出错的操作，行锁的等待成本可以接受；乐观锁的「重试」会让重复点击变成两次成功核销 |
| 3 | **随访任务不落库，只缓存 30 分钟** | 任务事实的唯一权威在 M03-04；M19 落库会产生两份状态互相打架 |
| 4 | **触达频次用 Redis 计数器而不是查库** | 每条触达前都要查当日次数，走库会成为瓶颈；Redis `INCR` + `EXPIRE` 到当日 23:59:59 是最轻的方案。**代价**：Redis 丢数据会重置当日计数，最多多打扰一次，可接受 |
| 5 | **统计类查询走预计算快照表，不实时算** | 复购率、依从性这类指标需要扫全量流水，实时算会拖垮库；按日/月批量预计算落 `m19_stat_*`，查询时直接读快照 |
| 6 | **患者合并走事件重定向而不是外键级联** | 积分账户、权益实例、券、关怀记录分散在 4 个子模块，外键级联无法表达「重定向」语义（要改的是逻辑归属，不是删除）。订阅 `m03.patient.merged` 逐类重定向最直观 |
| 7 | **回写 M03-04 用本地消息表 + 重试** | 回写失败不能阻塞用户操作（护士点了提交就得返回），但也不能丢。本地消息表 + 5 次退避重试 + 死信告警 |

### 7.4 外部依赖清单与降级

| 依赖 | 用途 | 不可用时的降级 |
|---|---|---|
| M03-04 待办接口 | 拉待办 | **功能不可用**（无降级手段），显示「随访服务暂不可用」并告警 P1 |
| M03-04 回写接口 | 回写结果 | 本地消息表重试，不阻塞用户；`exec_record.status` 停在 `SUBMITTED` |
| M03-05 消息发送 | 触达 | 转站内信，若站内信也不可用则 `SUPPRESSED` 并在次日重试 |
| M03-05 黑名单校验 | 闸门① | **必须失败关闭（fail-closed）**：宁可全部不发，也不能在不知道对方是否退订的情况下群发 |
| M03-03 会员主档 | 等级/权益定义 | 降级到 Redis 缓存（TTL 30 分钟，可容忍）；超时 30 分钟则拒绝积分发放 |
| M10-09 / M11-06 清单 | 待办聚合补充 | 降级到只显示 M03-04 的任务，顶部提示「术后/视光随访清单暂不可用」 |
| M16 结算事件 | 积分发放 | 走补偿任务（每日扫 `m16_settlement` 的增量，通过 M16 的统计接口），最多延迟 1 天 |
