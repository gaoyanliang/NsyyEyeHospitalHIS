**三处落在目标区间端点的说明（为什么不裁）：**

1. **M19-04 取到上限 11 张、M19-01/M19-03/M19-06/M19-07 各 10 张。** 判定标准是「这张表是否承载了其它表无法承载的事实」，而不是「凑够几张」。M19-04 的 11 张里，`m19_points_ledger`（积分流水）与 `m19_points_growth_ledger`（成长值流水）是两条独立的只增流水（成长值只增不减、积分可正可负，合并会让「只增」约束失效）；`m19_points_expire`（过期记录）也无法并进流水——过期是批量判定、一条流水可能对应多批过期。硬合并会把「余额可追溯」这条铁律打折。
2. **M19-02 只有 9 张（区间下限）。** 它的「事实」高度集中在 `m19_fu_exec_record` 一张表上，外呼记录、问卷答案、结果明细、异常上报、失访登记各自承载不同粒度的事实，无法再压缩；但也没有为凑数而增设日志表——操作留痕复用了 M19-01 的 `m19_fu_log`。
3. **合计 78 张落在 66~82 区间内、偏上限（95%）。** 这与 M22 那次「80 张贴上限」的判断一致：`m19_fu_*` 与 `m19_stat_*` 分别承载「执行事实」与「统计快照」，快照表按指标域切分是必要的（一张大宽表会让 NULL 比例超过 60%，且每个域的重算周期不同）。

### 1.1 M19 不自建的表（**边界红线**）

> **M19 绝不建这些表。** 它们由 M03-04 / M03-03 拥有，M19 只能通过内部接口读写。

| 表名 | 归属 | M19 的正确访问方式 |
|---|---|---|
| `mpi_followup_template` / `_template_node` | M03-04 | 只读，或完全不管（M19 用自己执行态的话术模板 `m19_fu_script`） |
| `mpi_followup_plan` | M03-04 | `POST /internal/v1/followup/plans/trigger`、`GET /internal/v1/followup/plans/by-patient/{patient_id}` |
| `mpi_followup_task` | M03-04 | `GET /internal/v1/followup/tasks/pending`、`POST .../start`、`POST .../result` |
| `mpi_followup_assign_rule` | M03-04 | 不接触（分派是 M03-04 的职责） |
| `mpi_member` / `mpi_member_level` | M03-03 | `GET /api/v1/mpi/members/{member_id}` |
| `mpi_member_benefit` / `mpi_member_level_benefit` | M03-03 | 只读（权益定义），M19 只存权益实例 `m19_benefit_instance` |
| `mpi_member_tag` / `mpi_member_tag_rel` | M03-03 | 回写走 `PATCH /internal/v1/mpi/members/{member_id}/tags` |

**为什么 `m19_benefit_instance` 不叫 `m19_member_benefit`：** 名字太像会导致开发误以为 M19 在重定义权益。`mpi_member_benefit` 是**权益定义**（「银卡会员每年可领取 2 张 200 元配镜券」），`m19_benefit_instance` 是**权益实例**（「李女士 2026-10-21 领取的第 1 张 200 元配镜券，有效期至 2026-12-31，当前 AVAILABLE」）。两者是一对多关系，缺一不可。

## 2. 全局命名与建表规范

### 2.1 表命名

```
m19_{子模块域}_{对象}[_{明细}]
```

| 段 | 取值 | 示例 |
|---|---|---|
| `m19` | 固定 | — |
| 域 | `fu` / `care` / `points` / `benefit` / `member` / `mkt` / `stat` | `fu` |
| 对象 | 单数名词 | `exec_record` |
| 明细 | 可选 | `_item` / `_log` / `_snap` |

### 2.2 字段命名

| 类型 | 规范 | 示例 |
|---|---|---|
| 主键 | `id` | `id BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| 业务单号 | `{对象}_no` | `exec_no`、`ledger_no`、`redeem_no` |
| 逻辑外键 | `{对象}_id` | `member_id`、`patient_id`、`task_id` |
| 编码 | `{对象}_code` | `rule_code`、`template_code` |
| 名称 | `{对象}_name` | `level_name` |
| 状态 | `status` | `'AVAILABLE'` |
| 时间 | `{动作}_at` / `{动作}_date` | `executed_at`、`valid_to` |
| 金额 | `{对象}_amount` | `biz_amount`、`spend_amount` |
| 积分 | `{对象}_points` | `granted_points`、`expired_points` |
| 余额 | `balance_after` | **流水表强制** |
| 比率 | `{对象}_rate` | `completion_rate` |
| JSON | `{对象}_json` / `detail` | `sort_rule_json` |

### 2.3 类型规范（强制）

| 数据类型 | PostgreSQL 类型 | Pydantic 类型 |
|---|---|---|
| 主键 / 外键 ID | `BIGINT` | `int` |
| 单号 / 编码 | `VARCHAR(32)` ~ `VARCHAR(64)` | `str` |
| 名称 | `VARCHAR(100)` ~ `VARCHAR(200)` | `str` |
| 状态 / 枚举 | `VARCHAR(32)` + CHECK | `str`（或 Enum） |
| **金额** | `NUMERIC(14,2)` | `Decimal` |
| **积分** | `NUMERIC(14,2)` | `Decimal` |
| **比率** | `NUMERIC(10,6)` | `Decimal` |
| 计数 | `INTEGER` | `int` |
| 布尔 | `BOOLEAN` | `bool` |
| 日期 | `DATE` | `date` |
| 时间戳 | `TIMESTAMP`（不带时区，全系统 Asia/Shanghai） | `datetime` |
| 大文本 | `TEXT` | `str` |
| 结构化 | `JSONB` | `dict` |
| 手机号 | `VARCHAR(20)` | `str` |

> **禁止 `FLOAT` / `DOUBLE PRECISION` / `REAL`。** 浮点的 0.1 + 0.2 = 0.30000000000000004 在积分上就是「多了 0.0000000000000004 分，余额校验失败」。

### 2.4 公共字段（除纯配置表外，每张表必须）

| 字段 | 类型 | 说明 |
|---|---|---|
| `created_at` | `TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP` | 创建时间 |
| `created_by` | `BIGINT` | 创建人 |
| `updated_at` | `TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP` | 更新时间 |
| `updated_by` | `BIGINT` | 更新人 |
| `is_deleted` | `BOOLEAN NOT NULL DEFAULT FALSE` | 逻辑删除 |

> **流水类表（`m19_points_ledger` / `m19_care_touch` / `m19_benefit_redeem`）不设 `is_deleted`**（不允许删除，也就无所谓逻辑删除），且必须 `REVOKE UPDATE, DELETE`。

### 2.5 索引命名

| 类型 | 前缀 | 示例 |
|---|---|---|
| 主键 | `pk_` | `pk_m19_points_account` |
| 唯一 | `uk_` | `uk_m19_points_account_member` |
| 普通 | `idx_` | `idx_m19_points_ledger_account` |
| 部分索引 | `idx_` + 语义后缀 | `idx_m19_benefit_instance_avail` |
| 约束 | `ck_` | `ck_m19_points_ledger_txn_type` |

### 2.6 逻辑外键约定

**M19 内部跨子模块、以及跨模块的引用一律不建物理 `FOREIGN KEY`**，用索引 + 应用层保证。理由：

1. 跨模块引用（`patient_id` → M03-01）在物理上不可能建外键（跨服务/跨库）。
2. 随访任务事实在 M03-04，M19 只有 `task_id`，物理外键无从谈起。
3. 逻辑删除 + 物理外键会让「删除父行」变成需要级联处理的死结。

**但同表内的自引用（如 `m19_mkt_activity.parent_activity_id`）可以建物理外键。**

## 3. 三处数据库强制（M19 特有）

### 3.1 积分账本的物理保证

**① 流水表只增不改：**

```sql
REVOKE UPDATE, DELETE ON m19_points_ledger FROM app_m19;
REVOKE UPDATE, DELETE ON m19_points_growth_ledger FROM app_m19;
```

**② 流水必须有余额快照 `balance_after`：**

```sql
-- 每条流水记录记账后的余额，使得「任意时点余额」= 该时点最后一条流水的 balance_after，
-- 而不需要 SUM 整个历史。也让对账时的差异能精确定位到第一条不一致的流水。
ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_balance_after
    CHECK (balance_after >= 0);
```

> **`balance_after >= 0` 是硬约束而非要求**：任何会导致余额为负的记账都是 bug（扣减前必须先校验余额足够）。这条 CHECK 让 bug 在写入时就崩，而不是等对账时才发现。

**③ 余额是派生值，每日对账：**

```sql
-- 每日 03:00 跑，不一致即 P1 告警
SELECT a.member_id, a.points_balance,
       COALESCE(SUM(CASE WHEN l.txn_type IN ('GRANT','REFUND') THEN l.points
                         WHEN l.txn_type IN ('DEDUCT','EXPIRE','REVERSE') THEN -l.points
                         ELSE l.points END), 0) AS ledger_sum
FROM m19_points_account a
LEFT JOIN m19_points_ledger l ON l.account_id = a.id
WHERE a.is_deleted = FALSE
GROUP BY a.member_id, a.points_balance
HAVING a.points_balance <> COALESCE(SUM(...), 0);
```

> **`ADJUST` 的符号由 `points` 自带正负**，所以 SUM 里 `ADJUST` 直接取 `l.points`。这个细节如果不写清，正负调整混算会让对账永远对不上。

### 3.2 权益核销的幂等

```sql
-- 核销单号唯一（同一次核销重放）
ALTER TABLE m19_benefit_redeem
    ADD CONSTRAINT uk_m19_benefit_redeem_no UNIQUE (redeem_no);

-- 同一权益实例在一张业务单据上只能核一次
CREATE UNIQUE INDEX uk_m19_benefit_redeem_instance_biz
    ON m19_benefit_redeem (benefit_instance_id, biz_type, biz_no)
    WHERE status = 'SUCCESS';
```

> **第二条索引的 `WHERE status = 'SUCCESS'` 不能省。** 核销失败的行（`status = 'FAILED'`）必须保留为审计轨迹，如果不带这个条件，一次失败后再成功就撞唯一索引了。

**核销的事务骨架：**

```sql
BEGIN;
-- ① 锁权益实例行（不是锁核销表，锁的是被消费的对象）
SELECT * FROM m19_benefit_instance
 WHERE benefit_instance_no = :no AND is_deleted = FALSE
   FOR UPDATE;
-- ② 校验状态必须是 AVAILABLE、在有效期内、未被限额
-- ③ 写核销单
INSERT INTO m19_benefit_redeem (...) VALUES (...);
-- ④ 改权益实例状态
UPDATE m19_benefit_instance SET status = 'USED', used_at = :now
 WHERE id = :id AND status = 'AVAILABLE';
-- 若 ④ 影响行数 = 0，说明并发已核销，回滚并返回首次结果
COMMIT;
```

### 3.3 触达频次的落地

```sql
-- 触达记录只增不改（合规举证要求）
REVOKE UPDATE, DELETE ON m19_care_touch FROM app_m19;

ALTER TABLE m19_care_touch
    ADD CONSTRAINT ck_m19_care_touch_channel
    CHECK (channel IN ('SMS','WECHAT','PHONE','INBOX','MAIL','PUSH'));
```

频次计数落 Redis（`m19:throttle:{patient_id}:{yyyyMMdd}`），**但每次触达必须落 `m19_care_touch` 行**——Redis 只是加速，真相在表里。Redis 丢数据最多多打扰一次；表里没记录，事后无法回答「我们到底给他发了几条」。

## 4. 分区策略

### 4.1 需要分区的表

| 表 | 分区键 | 粒度 | 理由 |
|---|---|---|---|
| `m19_points_ledger` | `created_at` | 月 | 年增 292 万，三年 876 万 |
| `m19_points_growth_ledger` | `created_at` | 月 | 同量级（略小） |
| `m19_care_touch` | `created_at` | 月 | 年增 109.5 万 |
| `m19_fu_call_log` | `created_at` | 月 | 年增 32.9 万，且有录音引用需要按时间归档 |
| `m19_benefit_redeem` | `created_at` | 月 | 年增 29.2 万 |
| `m19_mkt_coupon` | `granted_at` | 月 | 年增 73 万 |

> **分区键必须是业务发生时间而不是系统写入时间。** 本模块的分区键统一用 `created_at`（流水是即时写入的，两者一致），但**绝不能用 `updated_at`**——一条 2026-01 的流水在 2026-03 被更新会落进 `p202603` 分区，跨分区查询就错了。

### 4.2 分区模板（**必须同时建 DEFAULT 分区**）

```sql
CREATE TABLE m19_points_ledger (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    ledger_no VARCHAR(32) NOT NULL,
    account_id BIGINT NOT NULL,
    member_id BIGINT NOT NULL,
    patient_id BIGINT,
    txn_type VARCHAR(16) NOT NULL,
    points NUMERIC(14,2) NOT NULL,
    balance_after NUMERIC(14,2) NOT NULL,
    level_at_txn VARCHAR(32),
    rule_code VARCHAR(64),
    biz_type VARCHAR(32),
    biz_no VARCHAR(64),
    occurred_at TIMESTAMP NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_by BIGINT,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- 每年 12 月由 pg_partman 或运维脚本预建次年 12 个月分区
CREATE TABLE m19_points_ledger_p202610
    PARTITION OF m19_points_ledger
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

-- 【强制】DEFAULT 分区：没有它，新月份第一批写入直接报
--   "no partition of relation found for row"
CREATE TABLE m19_points_ledger_p_default
    PARTITION OF m19_points_ledger DEFAULT;
```

> **注意主键写法**：分区表的主键必须包含分区键，所以是 `PRIMARY KEY (id, created_at)` 而不是 `PRIMARY KEY (id)`。这一点如果不写清，开发照抄 `PRIMARY KEY (id)` 会建表失败。

### 4.3 分区维护

| 项 | 要求 |
|---|---|
| 预建 | 每年 12 月预建次年的 12 个月分区；用 `pg_partman` 自动或运维脚本 |
| 监控 | 若 `p_default` 有数据 → 说明预建失败，P2 告警 |
| 归档 | 超过保留期的分区 `DETACH` 后导出到对象存储，再 `DROP` |
| 查询 | 所有跨月查询必须带 `created_at` 范围条件（否则扫全部分区） |

### 5.1 大字段与外部存储

| 内容 | 存储位置 | 说明 |
|---|---|---|
| 外呼录音 | 对象存储（MinIO / OSS） | 表中只存 `recording_url` 与 `recording_duration_sec`；保留期 1 年，到期删除录音保留元数据 |
| 问卷答案 | 表内 `JSONB` | 单份问卷约 2~5 KB，日增 1,200 份 → 年增约 2 GB |
| 导出文件 | 对象存储 | 表中只存 `file_url` 与 `expire_at`（默认 7 天） |

> **录音为什么不进库：** 1,000 通/天 × 60 秒 × 8 KB/s ≈ 480 MB/天，一年 175 GB。放进 PostgreSQL 会让备份窗口从 30 分钟变成 3 小时。对象存储 + 表内 URL 是标准做法。

## 7. 全局约束清单

### 7.1 每个子模块必须有的 CHECK

| 约束类型 | 示例 | 说明 |
|---|---|---|
| 状态枚举 | `CHECK (status IN ('AVAILABLE','USED','EXPIRED','FROZEN','REVOKED'))` | 取值与共享规范 §13 逐字一致 |
| 金额非负 | `CHECK (biz_amount >= 0)` | 负数走冲正，不出现在正向单据 |
| 比率区间 | `CHECK (completion_rate BETWEEN 0 AND 1)` | 比率一律存 0~1，不存百分数 |
| 比率分母 | `CHECK (denominator > 0 OR ratio_value IS NULL)` | **分母为 0 时比率必须 NULL，不能是 0** |
| 有效期顺序 | `CHECK (valid_to > valid_from)` | — |
| 单号格式 | `CHECK (exec_no ~ '^FE[0-9]{12}$')` | — |
| 余额非负 | `CHECK (balance_after >= 0)` | — |
| 组合约束 | 见 7.2 | — |

### 7.2 组合约束（**最容易漏的一类**）

> **判别方法**（共享规范 §17 第 23 条）：把这个类型改成另一种，再把各字段分别填成另一类型的合法值，能通过吗？能通过，就缺组合约束。

| 场景 | 单列约束 | 缺失的组合约束 |
|---|---|---|
| 关怀任务「已抑制」必须有抑制原因 | `status`、`suppress_reason` 各自合法 | `CHECK (status <> 'SUPPRESSED' OR suppress_reason IS NOT NULL)` |
| 失访记录必须有联系方式失效或拒访原因 | `lost_reason` 合法 | `CHECK (lost_reason IS NOT NULL)`（其实应 NOT NULL） |
| 券发放记录「已发放」必须有券码 | `issue_status = 'ISSUED'` 合法 | `CHECK (issue_status <> 'ISSUED' OR voucher_code IS NOT NULL)` |
| 券有效期必须在发券时刻落库 | `valid_from`/`valid_to` 非空且 `valid_to > valid_from` | `CHECK (valid_from IS NOT NULL AND valid_to IS NOT NULL AND valid_to > valid_from)`（**活动规则后续修改不回写已发券**） |
| 积分 `DEDUCT` 必须有业务单据 | `txn_type`、`biz_no` 各自合法 | `CHECK (txn_type NOT IN ('DEDUCT','GRANT') OR biz_no IS NOT NULL)` |
| 随访执行「已闭环」必须已回写 | `status` 合法 | `CHECK (status <> 'CLOSED' OR m03_writeback_at IS NOT NULL)` |
| 营销活动「已结束」必须有结束时间 | — | `CHECK (status <> 'ENDED' OR ended_at IS NOT NULL)` |

### 7.3 全局索引要求

| 表 | 必需索引 | 理由 |
|---|---|---|
| `m19_points_account` | `uk (member_id)` | 一人一账户 |
| `m19_points_ledger` | `idx (account_id, created_at DESC)` | 查某账户的流水 |
| | `uk (biz_type, biz_no, rule_code)` | **幂等键** |
| `m19_benefit_instance` | `idx (patient_id, status) WHERE status = 'AVAILABLE'` | P-08 可用券查询（部分索引） |
| | `uk (benefit_instance_no)` | — |
| `m19_benefit_redeem` | `uk (redeem_no)` | **幂等** |
| | `uk (benefit_instance_id, biz_type, biz_no) WHERE status = 'SUCCESS'` | **防重复核销** |
| `m19_care_touch` | `idx (patient_id, created_at DESC)` | 频次与效果分析 |
| `m19_fu_exec_record` | `uk (task_id)` | 一个 M03-04 任务只有一条执行记录 |
| `m19_mkt_coupon` | `uk (coupon_no)` | — |
| | `idx (member_id, issued_at DESC)` | 我的券列表（状态需回查 M16-06，故不建状态部分索引） |

### 7.4 单号生成

**统一走 Redis `INCR`，禁用数据库序列：**

```python
def next_no(prefix: str, date_str: str, width: int) -> str:
    """生成业务单号：{prefix}{yyyyMMdd}{流水}。

    key 的 TTL 设到次日 00:05，避免日期切换时计数器残留。
    """
    key = "m19:code:%s:%s" % (prefix, date_str)
    seq = redis.incr(key)
    if seq == 1:
        redis.expireat(key, next_day_0005_ts(date_str))
    return "%s%s%0*d" % (prefix, date_str, width, seq)
```

> **为什么不能用 `SEQUENCE` 拼日期：** `SELECT nextval('seq')` 得到 999，然后拼 `FE20261021999`。跨零点时，22:59:59 拿到 999 还没来得及拼，00:00:01 的另一请求拿到 1000 拼成 `FE20261022000`——两个单号的日期部分不同但流水顺序反了，排序就乱了。更糟的是如果序列按周期重置（每日子序列），重置那一刻的并发会重号。Redis `INCR` 是原子的，天然没有这个问题。

## 8. Alembic 迁移策略

### 8.1 迁移文件组织

```
alembic/versions/
├── 20261106_001_create_m19_points_*.py
├── 20261106_002_create_m19_benefit_*.py
├── 20261106_003_create_m19_fu_*.py
├── 20261106_004_create_m19_care_*.py
├── 20261106_005_create_m19_mkt_*.py
└── 20261106_006_create_m19_stat_*.py
```

**命名规范：** `{yyyyMMdd}_{序号}_{动作}_{对象}.py`

### 8.2 迁移的硬规则

| # | 规则 |
|---|---|
| 1 | **每个 `upgrade()` 必须有对应的 `downgrade()`**（除数据种子迁移） |
| 2 | **分区表创建必须包含 DEFAULT 分区**，否则上线当天就会挂 |
| 3 | **大表加索引一律 `CREATE INDEX CONCURRENTLY`**（在 `op.execute()` 里执行，且不能在事务里） |
| 4 | **改列类型必须三步走**：加新列 → 双写 → 回填 → 切读 → 删旧列，不能 `ALTER COLUMN TYPE`（会锁表） |
| 5 | **`REVOKE` 语句放在建表迁移的最后**，且必须在 `downgrade` 里 `GRANT` 回来 |
| 6 | **数据种子用 `INSERT ... ON CONFLICT DO NOTHING`**，保证可重复执行 |
| 7 | **迁移脚本不得依赖应用代码**（不能 import 模型类），只写原生 SQL |

### 8.3 迁移示例

```python

Revises:

"""

revision = "20261106_001"

            growth_value NUMERIC(14,2) NOT NULL DEFAULT 0,
            level_code VARCHAR(32),
            status VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
            version_no INTEGER NOT NULL DEFAULT 0,
            created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
            created_by BIGINT,
            updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
            updated_by BIGINT,
            is_deleted BOOLEAN NOT NULL DEFAULT FALSE,
            CONSTRAINT uk_m19_points_account_member UNIQUE (member_id, is_deleted),
            CONSTRAINT uk_m19_points_account_no UNIQUE (account_no),
            CONSTRAINT ck_m19_points_account_balance CHECK (points_balance >= 0),
            CONSTRAINT ck_m19_points_account_status
                CHECK (status IN ('ACTIVE', 'FROZEN', 'CLOSED'))

```

> **`uk_m19_points_account_member UNIQUE (member_id, is_deleted)` 里的 `is_deleted` 不能省。** 因为 M19 在患者合并、会员注销等场景下可能删了再建，不带 `is_deleted` 的唯一键会让「删了重建」失败。这是本仓通用的唯一索引模式。

### 9.3 会员等级与积分的对接说明

**会员等级定义归 M03-03（`mpi_member_level`），M19 不建等级定义表。** 但 M19-04 需要「每个等级对应的积分倍率」与「每个等级对应的成长值门槛」，这两份数据存在 M19：

| 数据 | 归属 | 说明 |
|---|---|---|
| 等级定义（等级编码、名称、排序、图标） | **M03-03** | M19 只读 |
| 等级权益（该等级享有哪些权益） | **M03-03** | M19 只读 |
| **等级 → 积分倍率** | **M19-04** | `m19_points_rule_item` |
| **等级 → 成长值门槛** | **M19-04** | `m19_points_level_rule` |

> 初始化的关键：**M19 的 `level_code` 必须与 M03-03 的等级编码逐字一致**。初始化脚本必须先读 M03-03 的等级列表，再按编码生成 M19 的倍率与门槛行。若 M03-03 新增了一个等级，M19 侧必须有人维护倍率——否则新等级用户按什么倍率发积分没人知道。**建议：M19-04 提供「倍率缺失时按最低等级倍率兜底 + 每日扫描缺失等级并告警」的机制**，而不是默认 0 倍率（会静默少发积分）。
