## 1. 子模块概述

### 1.1 定位

M19-07 营销活动与优惠券是会员运营的**执行层**：把「给谁、给什么、什么时候给」这三个运营决策，变成可审批、可执行、可追溯的活动与券。

它管三件事：

1. **活动**：从创建、配置规则、提交审批、上线运行、暂停、结束到取消的完整生命周期；
2. **券**：券模板定义、批量或单人发放、发放结果追踪；
3. **效果**：触达量、发券量、核销量的日粒度统计与对比分析。

它**不管**三件事：

1. **不管钱怎么算**——优惠金额由 M16-06 计算；
2. **不管券能不能用**——券状态由 M16-06 持有；
3. **不管消息怎么发**——触达执行由 M19-03 与 M03-05 完成。

### 1.2 为什么营销需要独立子模块

有人会问：营销活动和「发优惠券」不就是给结算打个折吗，为什么不能并入 M16-06？

**因为它管的东西根本不是一回事。** M16-06 是「这一笔结算怎么收钱」，它的时间尺度是**秒级**（一次收费窗口的交互）；营销是「这个月给哪 8 万会员发什么券、预算多少、效果如何」，时间尺度是**周与月级**，并且有审批、有预算、有多渠道、有效果归因。

把它们放一起会出三个具体问题：

| 问题 | 具体表现 |
|---|---|
| **审批流放不进去** | M16-06 的接口都是同步收银链路，响应时间要求 < 200ms。营销活动审批要人工介入、可能跨天，塞进结算主链路会把主链路拉成异步 |
| **预算控制无处安放** | 营销预算（「这个活动最多花 50 万」）天然属于营销域，M16 的模型里没有预算这个概念 |
| **效果分析无从下手** | 「这次活动带来了多少 GMV」需要触达量、领券量、核销量、带动订单量四个数，横跨 M19-03（触达）、M19-07（发券）、M16-06（核销）。放 M16 里只能看到核销这一段 |

**更关键的一条：营销和收银的失败代价完全不同。** 收银算错一分钱，是账务问题，可以冲正；营销配错一个活动（「满 1000 减 300」写成「满 100 减 300」），一晚上就能亏几十万，而且**不可冲正**——券已经发出去、已经被核销、顾客已经享受了优惠。所以营销必须有自己的审批与拦截闸门，这套东西和收银链路必须**物理分离**。

### 1.4 概念辨析：券 vs 权益实例（本子模块最重要的边界）

> **「券（voucher）」与「权益实例（benefit instance）」是两个不同的东西，核销归属不同，绝不能合并。**

| 维度 | 券 | 权益实例 |
|---|---|---|
| **本质** | 可核销一次的**金额型**优惠凭证 | 非金额型或跨场景的会员权益：免费停车、免费复查、优先预约、生日礼遇 |
| **是否挂结算单** | **必须**（`used_settlement_no` 反向追溯） | **不挂** |
| **是否改变应付金额** | **是**（收银链路内唯一能改金额的环节） | 通常否 |
| **定义表** | 券模板 `m19_mkt_coupon_template` + 发放实例 `m19_mkt_coupon`（M19-07） | `mpi_member_benefit`（M03-03）+ `m19_benefit_instance`（M19-05） |
| **状态机唯一权威** | **M16-06 `m16_discount_voucher`** 五态含 `lock_expires_at`、`used_settlement_no`、Redis 锁 30 分钟 | **M19-05 `m19_benefit_instance`** |
| **核销台账** | `m16_discount_apply` | `m19_benefit_redeem` |
| **锁定 lock/release** | M16-06（收银窗口会话态，天然属于收银台） | 不适用 |

**判据一句话：核销这件事是否发生在收银台且改变应付金额——是，归 M16-06；否，归 M19-05。**

**四条推论：**

1. M19 绝不建自己的券核销状态表，也绝不定义券的生命周期状态枚举；`m19_mkt_coupon` 是**发放记录**，只存 `issue_status`（`PENDING`/`ISSUED`/`ISSUE_FAILED`/`VOIDED`）。
2. 「这张券现在能不能用」只能实时查 M16-06 API-13，**不缓存不落库**。
3. 若某条会员权益本质是减免金额（如会员免费验光券），必须落成 M16-06 的 `m16_discount_voucher`，M19 只负责发放。
4. M16-06 原文「M16-06 只做核销」与 `m16_discount_voucher.issue_source` 取值 M03/M19/M16 互为印证：券码由 M03-03 或 M19-07 发放，券状态由 M16-06 持有。

**为什么这条边界如此重要（一个反例）：** 假设 M19 也存一份券状态。顾客用券结算后又退货，M16-06 把券从 `USED` 恢复成 `ISSUED`。此时 M19 那份还是 `USED`。三天后同一顾客想再用这张券，如果 M19 的「我的券列表」按自己那份状态过滤，这张券**不会显示**——顾客明明手里有券却看不到，投诉到门店。而如果 M19 也学 M16 做恢复，就变成了两套状态机互相追，同步逻辑一定会有遗漏的路径（退款、撤销、超时释放、批量作废……）。**唯一可靠的做法是只留一套。**

### 1.5 设计目标

| 目标 | 量化标准 |
|---|---|
| 活动配错能在上线前被拦住 | 「满减超过门槛」「面额超过门槛」两类错误，100% 在创建或审批环节被拒绝，配置层与应用层双重拦截 |
| 已发券不受活动规则修改影响 | 活动有效期变更后，已发券的 `valid_from` / `valid_to` 变更数为 **0**（触发器强制） |
| 发券不重复 | 同一幂等键重复提交，券实例新增数为 **0**，返回首次结果 |
| 券状态不出现两份 | `m19_mkt_*` 表中任何字段都不表达券的可使用性；全表扫描无 `coupon_status` 类字段 |
| 营销频次不挤占随访渠道 | 同一会员营销短信间隔 ≥ 7 天，且必须让路于术后随访等医疗必要触达 |
| 触达前必过三道闸门 | 营销触达接口未携带闸门校验结果时直接拒绝 |
| 效果数据可回溯 | 每条统计快照带 `source_module` + `collect_batch_no` + `generated_at`，可定位到采集批次 |

### 1.6 角色与权限

| 角色 | 权限码 | 可做什么 | 不可做什么 |
|---|---|---|---|
| 营销专员 | `m19:mkt:create` / `m19:mkt:edit` | 创建、编辑草稿活动与券模板 | 不能提交审批、不能审批、不能发放 |
| 营销主管 | `m19:mkt:submit` / `m19:mkt:grant` / `m19:mkt:export` | 提交审批、发起发券、导出效果报表 | 不能审批自己提交的活动 |
| 市场总监 | `m19:mkt:approve` | 审批通过、驳回、取消活动 | 不能修改活动内容 |
| 运营分析员 | `m19:mkt:view` | 查看活动、券、效果 | 不能做任何写操作 |
| 系统管理员 | `m19:mkt:admin` | 配置维护、失败补偿 | 不能替业务审批 |
| 内部服务 | `内部服务` | 调 `/internal/v1/m19/marketing/*` | 无权访问对外接口 |

**职责分离硬约束：** 一个活动**不能由创建者自己审批**。Service 层在审批时校验 `approver_id <> created_by`，违反返回 `"1907021"`。

### 3.4 关键计算模型

#### 3.4.1 券有效期物化（本子模块的核心算法之一）

**输入：** 模板的 `valid_mode`、`valid_from`、`valid_to`、`valid_days`；发券时刻 `granted_at`。
**输出：** 券实例的 `valid_from`、`valid_to`（DATE），以及 `valid_days_snapshot`。

```
算法 ISSUE_VALIDITY(template, granted_at) -> (vf, vt, days_snapshot)

1. 若 template.valid_mode = 'FIXED':
      vf = template.valid_from
      vt = template.valid_to
      days_snapshot = (vt - vf) + 1          -- 含首尾两天

2. 否则 (valid_mode = 'RELATIVE'):
      vf = DATE(granted_at)                   -- 取发券当天的日期
      vt = vf + (template.valid_days - 1)     -- 含首尾，第 N 天为最后一天
      days_snapshot = template.valid_days

3. 校验（应用层 + 数据库层双检）:
      若 vt < vf:  抛 1907008（有效期倒挂）
      若 (vt - vf) > 366: 抛 1907009（有效期跨度超限）

4. 返回 (vf, vt, days_snapshot)
```

**算例：**

| 场景 | 模板配置 | 发券时刻 | 计算结果 | 说明 |
|---|---|---|---|---|
| 固定区间 | `FIXED`, 2026-11-01 ~ 2026-11-11 | 2026-10-25 14:30 | `vf=2026-11-01`, `vt=2026-11-11`, 快照 11 天 | 提前发券，有效期仍从活动开始算 |
| 相对 30 天 | `RELATIVE`, `valid_days=30` | 2026-10-25 14:30 | `vf=2026-10-25`, `vt=2026-11-23`, 快照 30 天 | 当天算第 1 天 |
| 相对 30 天 | `RELATIVE`, `valid_days=30` | 2026-10-25 23:59 | `vf=2026-10-25`, `vt=2026-11-23` | 跨零点前发券，仍按当天算 |
| 相对 1 天 | `RELATIVE`, `valid_days=1` | 2026-10-25 09:00 | `vf=2026-10-25`, `vt=2026-10-25` | 单日券，`vf = vt` 合法 |
| 秒杀券 | `RELATIVE`, `valid_days=7` | 2026-10-25 09:00 | `vf=2026-10-25`, `vt=2026-10-31` | 7 天 = 10-25 到 10-31（含首尾） |

**为什么 `vt = vf + (days - 1)` 而不是 `vf + days`：** 「领取后 7 天有效」在日常语义里包含领取当天。10-25 领取、说「7 天有效」，顾客预期最后一天是 10-31，不是 11-01。多算一天看着是「对顾客更好」，但它会让「活动总时长」与配置值产生系统性偏差，且与 M16-06 的 `valid_to >= valid_from` 语义不一致。**统一按含首尾计算。**

#### 3.4.2 活动预算消耗与自动熔断

```
算法 ACCUMULATE_BUDGET(activity_id, reduce_amount, settlement_no) -> ok | OVER_BUDGET

1. UPDATE m19_mkt_activity
      SET consumed_amount = consumed_amount + :reduce_amount
    WHERE id = :activity_id
      AND (budget_amount IS NULL OR consumed_amount + :reduce_amount <= budget_amount)
    RETURNING consumed_amount, budget_amount;

2. 若影响行数 = 0:
      → 说明预算不足（或活动不存在）
      → 抛 1907014（活动预算已用尽）
      → 若 budget_amount 非空且 consumed_amount >= budget_amount:
            触发 T09 自动结束活动

3. 若影响行数 = 1:
      返回 ok
```

**为什么用「条件 UPDATE + 检查影响行数」而不是「先 SELECT 再判断再 UPDATE」：** 后者存在竞态——两个并发的核销回执同时读到 `consumed_amount = 499000`（预算 500000），都判断「还够」，都执行 UPDATE，最终消耗 510000 超预算。条件 UPDATE 把判断和写入合并成一条原子语句，超预算的 UPDATE 影响 0 行，天然防并发。**这也是为什么 `ck_m19_mkt_activity_budget_cap` 是数据库约束而非应用层校验——它是最后一道物理防线。**

#### 3.4.3 效果指标计算

| 指标 | 公式 | 分母为 0 时 | 数据来源 |
|---|---|---|---|
| 触达人数 `reach_count` | 去重后的触达会员数 | — （计数，不存在分母） | M19-03 触达回执 |
| 发券数 `grant_count` | `issue_status = 'ISSUED'` 的券记录数 | — | `m19_mkt_coupon` |
| 领券人数 `grant_member_count` | 上述记录去重会员数 | — | `m19_mkt_coupon` |
| 核销数 `use_count` | **M16-06 回执中的核销笔数** | — | M16-06 回执（**非 M19 自算**） |
| 核销人数 `use_member_count` | 回执中去重会员数 | — | M16-06 回执 |
| 核销率 `use_rate` | `use_count / grant_count` | **NULL** | 计算 |
| 带动订单数 `order_count` | 参与记录中 `join_type='ORDER'` 数 | — | `m19_mkt_participant` |
| 带动金额 `gmv_amount` | 参与记录 `order_amount` 求和 | — | `m19_mkt_participant` |
| 实际减免 `reduce_amount` | **M16-06 回执中的实减合计** | — | M16-06（**M19 不算钱**） |
| ROI `roi_rate` | `gmv_amount / reduce_amount` | **NULL** | 计算 |

**规范算例（2026 年 11 月「双十一视光满减」活动，统计日 2026-11-11）：**

```
触达人数 reach_count        = 82,540
发券数   grant_count        = 68,215
领券人数 grant_member_count = 41,308
核销数   use_count          = 19,447      （M16-06 回执）
核销人数 use_member_count   = 17,902
带动订单 order_count        = 18,130
带动金额 gmv_amount         = 5,842,360.00 元
实际减免 reduce_amount      = 1,168,472.00 元

核销率 use_rate  = 19,447 / 68,215
                 = 0.285098  （四舍六入五成双保留 6 位）
                   → NUMERIC(9,6) 存 0.285098

ROI roi_rate     = 5,842,360.00 / 1,168,472.00
                 = 5.000000  （保留 6 位）
                   → NUMERIC(9,6) 存 5.000000
```

**反例算例（分母为 0 的情形，2026 年 11 月「银卡召回」活动，统计日 2026-11-12）：**

```
触达人数 reach_count  = 1,200
发券数   grant_count  = 0        （券模板在当天 10:00 才上架，尚未发券）
核销数   use_count    = 0
带动金额 gmv_amount   = 0.00
实际减免 reduce_amount = 0.00

核销率 use_rate  = 0 / 0 → NULL    ← 绝不能存 0
ROI    roi_rate  = 0.00 / 0.00 → NULL  ← 绝不能存 0
```

**为什么必须存 NULL 而不是 0：** 若存 0，则「月度平均核销率」会把「尚未开始发券」的活动算成 0% 并把整体拉低。存 NULL 后 `AVG()` 自动跳过，平均值反映的才是真实效果。数据库层由 `ck_m19_mkt_effect_stat_use_rate` 与 `ck_m19_mkt_effect_stat_roi` 强制：**分母为 0 时对应列必须为 NULL，分母大于 0 时必须非 NULL**（两个方向都卡死，不给「填 0 蒙混」留口子）。

### 3.5 单据模型

| 单据 | 编号前缀 | 编号规则 | 生成方式 | 示例 |
|---|---|---|---|---|
| 营销活动 | `MK` | `MK` + yyyyMMdd + 6 位流水 | Redis `INCR` | `MK20261106000001` |
| 券模板 | `CT` | `CT` + yyyyMMdd + 6 位流水 | Redis `INCR` | `CT20261106000012` |
| 发券流水 | `CP` | `CP` + yyyyMMdd + 8 位流水 | Redis `INCR` | `CP2026110600012345` |
| 批量发券批次 | `GB` | `GB` + yyyyMMdd + 6 位流水 | Redis `INCR` | `GB20261106000003` |
| M16 券码 | `V` | `V` + 16~30 位数字 | **M16-06 生成** | `V2026110600012345` |

**单号生成器（Redis INCR + 数据库唯一索引兜底）：**

```python
from datetime import datetime, timedelta

import redis


def next_no(client: redis.Redis, prefix: str, width: int,
            now: datetime | None = None) -> str:
    """生成业务单号：{prefix}{yyyyMMdd}{流水}。

    Redis 仅用于降低冲突概率；最终唯一性由数据库唯一索引保证。
    """
    now = now or datetime.now()
    date_str = now.strftime("%Y%m%d")
    key = f"m19:code:{prefix}:{date_str}"

    seq = client.incr(key)
    if seq == 1:
        # 首次生成当天流水，设置到次日 00:05 过期
        tomorrow = (now + timedelta(days=1)).replace(
            hour=0, minute=5, second=0, microsecond=0
        )
        ttl = max(1, int((tomorrow - now).total_seconds()))
        client.expire(key, ttl)

    return f"{prefix}{date_str}{seq:0{width}d}"
```

| 核销率 | 核销数 ÷ 发券数，六位小数 | 比率 | **分母为 0 → NULL，显示「—」，不显示 0** |
| GMV | 用了本活动券的结算单金额合计 | 元 | 恒有值 |
| 减免金额 | M16-06 回传的实际减免合计 | 元 | 恒有值 |
| 客单价 | GMV ÷ 核销数 | 元 | **分母为 0 → NULL** |
| ROI | GMV ÷ 减免金额 | 比率 | **分母为 0 → NULL** |

**交互说明**

1. 六张指标卡点击可下钻到明细表按该指标排序。
2. 趋势图支持按日/按周/按月切换粒度，切换后重新请求不重新计算口径。
3. 每张图表右上角有小问号，鼠标悬停显示该指标完整口径（分子、分母、取数范围、空值规则）。
4. 底部「数据完整性」标签来自统计任务的 `source_status`，值为 `PARTIAL` 时黄色提示「部分上游数据未采集完整，指标值可能偏低」。**绝不静默显示为 0 而不提示。**
5. 导出走 M22 报表框架，文件内附口径说明页。
6. 若活动尚未结束，页面显示「活动进行中，数据为截至 {now} 的快照」并提供「刷新统计」按钮（异步重算）。

**校验规则**

| --- | --- | --- |

### 6.3 接口详述

#### API-01 营销工作台概览

**请求**

```
GET /api/v1/m19/marketing/dashboard
```

| 参数 | 位置 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| period_start | query | date | 否 | 统计起始日，默认当月 1 日 |
| period_end | query | date | 否 | 统计截止日，默认今日 |

**响应**

```json
{
  "code": "0",
  "message": "ok",
  "data": {
    "running_activity_count": 3,
    "pending_audit_count": 7,
    "today_grant_count": 1240,
    "today_redeem_count": 388,
    "month_grant_count": 68215,
    "month_redeem_count": 19447,
    "month_redeem_rate": 0.285098,
    "month_discount_amount": 1168472.00,
    "budget_total": 1200000.00,
    "budget_consumed": 967340.00,
    "budget_usage_rate": 0.806117,
    "source_status": "COMPLETE"
  },
  "trace_id": "7f3c1a2e9b4d4c8ea1f5b2c3d4e5f607",
  "server_time": "2026-11-06T10:12:31+08:00"
}
```

**业务逻辑**

1. 校验 `period_start <= period_end`，跨度不超过 366 天，否则返回 `"1907002"`。
2. 运行中活动数取 `status='RUNNING'` 的活动计数；待审批数取 `status='PENDING'` 计数。
3. 今日发券/核销数走 Redis 计数器 `m19:mkt:stat:daily:{yyyyMMdd}`，未命中则回源聚合。
4. 本月核销率 = 本月核销数 ÷ 本月发券数；**分母为 0 时返回 `null`，不返回 0**。
5. 预算使用率 = 已消耗预算 ÷ 总预算；分母为 0 时返回 `null`。
6. `source_status` 取当日统计任务的采集状态，值为 `FAILED` 时前端整卡置灰。

**错误码**

| 错误码 | 场景 |
| --- | --- |
| `"1907002"` | 统计起止日期倒挂或缺失 |
| `"1907009"` | 统计区间跨度超过 366 天 |
| `"1907034"` | 统计任务失败，数据不可用 |

#### API-02 工作台趋势

**请求**

```
GET /api/v1/m19/marketing/dashboard/trend
```

| 参数 | 位置 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| days | query | integer | 否 | 最近天数，默认 30，范围 7~180 |
| granularity | query | string | 否 | DAY/WEEK，默认 DAY |

**响应**

```json
{
  "code": "0",
  "message": "ok",
  "data": {
    "granularity": "DAY",
    "points": [
      {"period": "2026-11-01", "grant_count": 5200, "redeem_count": 1402, "redeem_rate": 0.269615},
      {"period": "2026-11-02", "grant_count": 4980, "redeem_count": 1318, "redeem_rate": 0.264658}
    ]
  },
  "trace_id": "7f3c1a2e9b4d4c8ea1f5b2c3d4e5f607",
  "server_time": "2026-11-06T10:12:31+08:00"
}
```

**业务逻辑**

1. `days` 越界（<7 或 >180）返回 `"1907001"`。
2. 按 `granularity` 从 `m19_mkt_effect_stat` 按 `stat_granularity` 与 `granularity` 取值。
3. 每个点的核销率独立计算，分母为 0 的点 `redeem_rate` 返回 `null`。
4. 缺失日期补点位（发券数 0、核销数 0、核销率 `null`），不跳点，避免趋势图误读斜率。
5. 结果缓存 Redis `m19:mkt:stat:trend:{granularity}:{days}`，TTL 300 秒，统计任务完成后主动失效该前缀。

**错误码**

| 错误码 | 场景 |
| --- | --- |
| `"1907001"` | days 超出 7~180 范围 |

### 6.5 Service 层关键实现

**有效期物化（B3 边界的代码落点）**

```python
from datetime import date, datetime, timedelta


def materialize_validity(template, granted_at: datetime) -> tuple[date, date]:
    """把模板的有效期规则物化成这一张券的绝对起止日期。

    这是本子模块最关键的一处实现：一旦算出就写入 m19_mkt_coupon，
    此后无论活动规则或模板如何修改，都不再重算。
    """
    if template.valid_type == "DAYS_AFTER_GRANT":
        valid_from = granted_at.date()
        # 30 天有效期 = 发券日 + 29 天，保证可用天数正好 30 天（含发放当日）
        valid_to = valid_from + timedelta(days=template.valid_days - 1)
    else:  # FIXED_RANGE
        valid_from = template.valid_from
        valid_to = template.valid_to
    if valid_to < valid_from:
        raise BusinessError("1907008", "券有效期倒挂")
    return valid_from, valid_to
```

**发放主流程（含幂等与部分失败）**

```python
async def grant_single(self, body, idempotency_key: str, user) -> dict:
    cache_key = f"m19:idem:grant:{idempotency_key}"
    cached = await redis.get(cache_key)
    if cached:
        return json.loads(cached)

    async with self.uow.transaction():
        template = await self.uow.template_repo.get_for_update(body.template_code)
        if template is None or template.status != "ACTIVE":
            raise BusinessError("1907012", "模板不存在或未生效")

        granted_this_year = await self.uow.coupon_repo.count_by_member_year(
            body.member_no, template.template_code, date.today().year
        )
        if granted_this_year + body.quantity > template.limit_per_member:
            raise BusinessError("1907011", "超出每人限领张数")

        used = await self.uow.coupon_repo.count_issued(template.template_code)
        if template.total_quota is not None and used + body.quantity > template.total_quota:
            raise BusinessError("1907013", "模板总发放上限剩余不足")

        valid_from, valid_to = materialize_validity(template, datetime.now())
        coupon_no = await self.seq.next_no("CP", datetime.now().strftime("%Y%m%d"), 7)
        record = await self.uow.coupon_repo.create(
            coupon_no=coupon_no,
            template_code=template.template_code,
            member_no=body.member_no,
            face_value=template.face_value,
            valid_from=valid_from,
            valid_to=valid_to,
            issue_status="PENDING",
            reason=body.reason,
        )
        try:
            voucher = await self.m16_client.issue_voucher(
                template_code=template.template_code,
                member_no=body.member_no,
                face_value=template.face_value,
                threshold_amount=template.threshold_amount,
                valid_from=valid_from,
                valid_to=valid_to,
                issue_source="M19",
                issue_ref=coupon_no,
            )
        except Exception as exc:
            await self.uow.coupon_repo.mark_issue_failed(coupon_no, str(exc))
            raise BusinessError("1907032", "券码生成失败，已记录待补发") from exc

        await self.uow.coupon_repo.mark_issued(coupon_no, voucher["voucher_code"])
        await self.uow.audit_repo.write(user, "GRANT", coupon_no)

    result = {
        "coupon_no": coupon_no,
        "voucher_code": voucher["voucher_code"],
        "issue_status": "ISSUED",
        "valid_from": valid_from.isoformat(),
        "valid_to": valid_to.isoformat(),
        "face_value": str(template.face_value),
    }
    await redis.setex(cache_key, 86400, json.dumps(result))
    return result
```

```python
async def approve_activity(self, activity_code: str, body, user) -> dict:
    async with self.uow.transaction():
        row = await self.uow.activity_repo.get_for_update(activity_code)
        if row is None:
            raise BusinessError("1907025", "活动不存在")
        if row.status != "PENDING":
            raise BusinessError("1907023", "当前状态不允许审批")
        if row.created_by == user.staff_id:
            raise BusinessError("1907021", "审批人不得为提交人")

        await self.risk_check(row, body.allow_high_discount)

        row.status = "APPROVED"
        row.approver_id = user.staff_id
        row.approver_name = user.staff_name
        row.approved_at = datetime.now()
        await self.uow.activity_repo.save(row)
        await self.uow.audit_repo.write(
            user, "APPROVE", activity_code,
            before={"status": "PENDING"}, after={"status": "APPROVED"},
            remark=body.comment,
        )

def run_grant_batch(self, batch_no: str) -> dict:
    batch = batch_repo.get(batch_no)
    batch.status = "RUNNING"

    members = resolve_target_members(batch.target_type, batch.target_value)

            success += 1
        except BusinessError as exc:
            failed.append({"member_no": member_no, "code": exc.code, "reason": exc.message})
            continue
        if batch.notify_channels and not touch_gates.blocked(member_no):
            notify_client.send_marketing(member_no, batch.template_code)
        elif batch.notify_channels:
            skipped += 1

    batch.success_count = success
    batch.fail_count = len(failed)
    batch.notify_skipped_count = skipped
    batch.fail_detail_json = failed
    batch.status = "SUCCESS" if not failed else ("PARTIAL" if success else "FAILED")
    batch.finished_at = datetime.now()
    batch_repo.save(batch)
    return {"batch_no": batch_no, "success": success, "failed": len(failed)}
```

## 7. 技术实现要点

### 7.1 缓存设计

| 缓存键 | 内容 | TTL | 失效时机 |
| --- | --- | --- | --- |
| `m19:mkt:config` | 营销配置全量 | 600 秒 | 配置保存后主动删除 |
| `m19:mkt:stat:daily:{yyyyMMdd}` | 当日发券/核销计数 | 到次日 00:05 | 自然过期 |
| `m19:mkt:stat:trend:{granularity}:{days}` | 工作台趋势 | 300 秒 | 统计任务完成后删除 `m19:mkt:stat:trend:*` |
| `m19:mkt:effect:{activity_code}:{period}` | 活动效果汇总 | 300 秒 | 统计任务完成后删除 |
| `m19:code:{prefix}:{yyyyMMdd}` | 单号流水计数器 | 到次日 00:05 | 自然过期 |
| `m19:idem:{biz}:{key}` | 幂等键结果 | 86400 秒 | 自然过期 |
| `m19:lock:activity:{code}` | 活动审批/状态变更分布式锁 | 30 秒 | 事务结束主动释放 |
| `m19:throttle:{member_id}:mkt` | 营销触达频次 | 7 天 | 自然过期 |

**券状态不在上表中——因为 M19 不缓存券状态。** 任何需要判断券能否可用的地方都必须实时调 M16-06 API-13。这是 B2 边界在缓存层的体现。

### 7.2 异步任务

| 任务 | 触发方式 | 幂等保证 | 失败重试 |
| --- | --- | --- | --- |
| 批量发券 `run_grant_batch` | API-14 投递 | `batch_no` 天然唯一，重复执行先查已发 | 3 次，间隔 60/120/240 秒 |
| 券码补发 `retry_failed_issue` | 定时 10 分钟 | 只处理 `ISSUE_FAILED` 且重试次数 <5 | 5 次后转人工 |
| 活动状态机巡检 `scan_activity_status` | 定时每 5 分钟 | 状态迁移带 `WHERE status = 旧值` 条件 | 下一轮自动重试 |
| 效果统计 `calc_effect_stat` | 定时每日 02:10 | 按 `(activity_code, stat_date, granularity)` UPSERT | 3 次 |
| 触达闸门判定 | 随批量发放内联 | 频次键原子 INCR | 不重试，失败即跳过推送 |

### 7.3 事务边界

| 场景 | 事务范围 | 事务外 |
| --- | --- | --- |
| 单张发放 | 占额度 + 落记录 + 写审计 | 调 M16-06 生成券码（长调用不占事务） |
| 批量发放 | 单会员单事务 | 批次汇总统计、触达推送 |
| 审批通过 | 锁行 + 状态更新 + 审计 | 通知审批结果 |
| 配置保存 | 整组更新 + 历史版本 | 缓存失效 |

**为什么调 M16-06 不放在事务里**：跨服务调用耗时不可控（网络抖动、下游慢查询），放在事务里会长时间持锁，批量发放时直接把活动行锁死。正确做法是先落 `PENDING` 记录、提交事务，再调下游；下游失败就更新为 `ISSUE_FAILED` 并进补发队列。

## 8. 并发控制

| 并发场景 | 控制手段 | 失败表现 |
| --- | --- | --- |
| 同一活动被两人同时审批 | `SELECT ... FOR UPDATE` + 状态条件更新 | 后到者拿到的状态已是 `APPROVED`，返回 `"1907023"` |
| 批量发放与单张发放同时占额度 | 模板行锁 + 已发数实时统计 | 超限者返回 `"1907013"` |
| 同一会员并发多批发放 | 每人限领在事务内统计 | 超限返回 `"1907011"` |
| 幂等键重复提交 | Redis `SETNX` + DB 唯一索引双保险 | 返回首次结果，不重复发放 |
| 活动状态巡检与人工暂停冲突 | Redis 锁 `m19:lock:activity:{code}` | 拿不到锁的一方跳过本轮 |
| 统计任务重跑 | 按唯一键 UPSERT | 幂等覆盖，不产生重复行 |

## 9. 事务边界与数据一致性

### 9.1 一致性等级

| 数据 | 一致性要求 | 实现 |
| --- | --- | --- |
| 活动状态 | 强一致 | 单库事务 + 行锁 |
| 发放额度 | 强一致 | 事务内统计 + 行锁，不依赖缓存 |
| 券有效期 | 强一致（一次写定） | 发券时物化落库 |
| 券生命周期状态 | **不在本模块** | 实时调 M16-06，不缓存不落库 |
| 效果统计 | 最终一致 | 每日异步重算，标注 `source_status` |
| 预算消耗 | 最终一致 | 由 M16-06 回传后累加，允许延迟 |

### 9.2 失败补偿

| 失败点 | 补偿动作 | 是否影响用户 |
| --- | --- | --- |
| M16-06 生成券码失败 | 记录 `ISSUE_FAILED`，进补发队列，5 次后转人工 | 是，提示「稍后到账」 |
| M16-06 查询券状态超时 | 页面显示「状态暂不可查」，不回退本地值 | 是，但数据不误导 |
| 触达闸门服务不可用 | 跳过推送，只发券 | 否，券照发 |
| 统计任务失败 | `source_status='FAILED'`，页面显示「数据不可用」 | 否 |
| 批量发放中断 | 已完成部分保留，批次置 `PARTIAL`，可续发 | 否 |

## 10. 监控与告警

| 指标 | 阈值 | 告警级别 |
| --- | --- | --- |
| 发券失败率 | > 1% 持续 5 分钟 | P2 |
| M16-06 券接口 P95 耗时 | > 2000ms | P2 |
| 活动预算消耗率 | > 90% | P3 |
| 单活动日核销率 | > 0.60（异常偏高） | P1 |
| 批量发放任务积压 | > 10 个批次排队 | P2 |
| 统计任务失败 | 任意一次 | P2 |

**为什么单活动日核销率过高要报 P1**：正常营销活动核销率在 0.20~0.40 之间。若某天突然超过 0.60，要么规则配错（比如门槛写少了），要么有刷单，两种都需要立刻人工介入止损。这条告警是 API-22 审批拦截的事后兜底。

| 中间 | `PENDING`/`APPROVED`/`RUNNING`/`PAUSED` | — | `RUNNING` |
| 成功终态 | `ENDED` | `ISSUED` | `SUCCESS`/`PARTIAL` |

**券的生命周期状态（`ISSUED`/`LOCKED`/`USED`/`EXPIRED`/`VOIDED`）不在本表，归 M16-06 `m16_discount_voucher`。**

## 附录 C 券 vs 权益实例对照

| 维度 | 券（voucher） | 权益实例（benefit instance） |
| --- | --- | --- |
| 本质 | 可核销一次的**金额型**优惠凭证 | 非金额型或跨场景的会员权益 |
| 是否挂结算单 | **必须**（`used_settlement_no` 反向追溯） | **不挂** |
| 是否改变应付金额 | **是** | 通常否 |
| 定义表 | `m19_mkt_coupon_template` + `m19_mkt_coupon` | `mpi_member_benefit` + `m19_benefit_instance` |
| 状态机唯一权威 | **M16-06 `m16_discount_voucher`** | **M19-05 `m19_benefit_instance`** |
| 核销台账 | `m16_discount_apply` | `m19_benefit_redeem` |
| 锁定 lock/release | M16-06（收银窗口会话态） | 不适用 |

**判据一句话：核销这件事是否发生在收银台且改变应付金额——是，归 M16-06；否，归 M19-05。**
