## 1. 模块概述

### 1.1 定位

M19-06「会员运营与消费分析」回答一个问题：**谁是我们的好客户，谁正在离开，下一步该找谁。**

它是 M19 随访与会员管理里唯一的**纯分析型子模块**——不产生任何业务动作，只做三件事：把会员的分散消费事实归集成可用的分析数据、按统一口径判定每个会员的状态、把结论交给该采取动作的人（M19-03 关怀召回、M22 经营报表、M10-08 视光会员）。

一句话界定：**M22 回答「本月复购率是多少」，M19-06 回答「哪些会员复购了、哪些没复购、下一步该找谁」。**

### 1.2 为什么独立成模块

**理由一：会员分析的三个维度无法归入任何现有子模块。**

M19 其余七个子模块都是「执行型」的：随访中心派任务（M19-01）、随访执行录结果（M19-02）、关怀召回发消息（M19-03）、积分成长值算账（M19-04）、权益核销（M19-05）、营销活动（M19-07）、运营分析（M19-08，看的是随访与会员运营的**过程指标**）。

而 M19-06 看的是**结果指标**：消费额、复购率、生命周期、价值分群、流失风险。它需要的数据横跨 M16（结算）、M03（会员）、M19-04（积分）、M19-05（券）、M19-07（活动）五个模块。放进任何一个执行型子模块，都会让该子模块从「执行一件事」变成「执行 + 分析所有事」，边界失控。

**理由二：口径必须集中在一个地方。**

复购率有双口径（`PATIENT_ID` 34.52% vs `MEMBER_ID` 27.27%，差 7.24 个百分点）、生命周期有六阶段、价值分群有 RFM 三档、流失风险有四级。这些口径若分散在 M19-03（要名单）、M22（要指标）、M10-08（要标签）三个地方各自实现，一定会出现「同一个会员在三个页面显示三种状态」。集中到 M19-06 一处定义、一处计算、一处存储，其余地方只读，是从结构上消灭口径分叉。

**理由三：计算成本需要独立的时间预算。**

生命周期与分群要对 5 万会员每日重算，消费同步要每日两次，复购事实要每期重算。这些计算加起来约 40 分钟/天，与随访任务的实时性要求（随访任务派发 P95 ≤ 800ms）完全不同。独立成模块才能给它们独立的调度队列、独立的失败重试策略、独立的资源配额。

**理由四：隐私约束需要集中收口。**

会员分析是 M19 里唯一会「批量输出会员名单」的地方。小样本抑制（n < 5）、导出审批、脱敏等级、水印这些约束只在分析场景有意义。集中在一处收口，比散落在五个页面里各守一遍可靠。

### 1.4 概念辨析

#### 1.4.1 生命周期 vs 价值分群

这是本子模块最容易混淆的一对概念，任务书第 4 条明确要求说明。两者都用「会员」做主语、都有 `SILENT` / `LOST` 取值，但**是两个正交维度**：

  | 维度 | 生命周期 `lifecycle_stage` | 价值分群 `member_segment` |
  | --- | --- | --- |
  | 回答什么问题 | 这个人在时间上走到哪一步了 | 这个人对我们值多少钱 |
  | 数据来源 | 消费次数趋势、`silent_days`、会员年龄 | R 近期性 / F 频次 / M 金额三档打分 |
  | 变化规律 | 基本单向推进 | 可双向跳动 |
  | 与钱的关系 | 无关 | 直接相关 |
  | 谁在用 | 运营（决定何时联系） | 市场部（决定给谁花钱） |
  | 典型取值组合 | `DECLINING` + `VIP` = 高价值客户开始减少，**最高优先级挽回** | 同上 |

**反例：** 若合并成一个 `member_status` 字段，取值就是 `VIP` / `NEW` / `SILENT` 混在一起的大杂烩。运营要查「所有快流失的人」，写 `WHERE member_status IN ('SILENT','LOST')` 会漏掉 `VIP` 里那个 200 天没来的高净值客户；市场部要查「该重点维护的高价值客户」，写 `WHERE member_status IN ('VIP','CORE')` 会漏掉 `SILENT` 里的高价值客户。两个需求都做不到。

**落地：** 两个字段分别在 `m19_member_lifecycle.stage` 与 `m19_member_segment_snapshot.member_segment`，两张表、两个字段，靠 `member_id + period` 关联。6×6 = 36 种组合中约 12 种有运营意义。

#### 1.4.2 复购率双口径

**主口径 `PATIENT_ID`**：按患者 ID 归并消费。一个患者无论办几张卡、用几个手机号，都算一个人。

**辅口径 `MEMBER_ID`**：按会员 ID 归并消费。只有办了会员卡的患者才进入统计。

**为什么两个都要：** 只按 `MEMBER_ID` 会丢掉未办卡的回头客。实测数据（2026-10）：

  | 口径 | 有效顾客 | 复购顾客 | 复购率 |
  | --- | --- | --- | --- |
  | `PATIENT_ID`（主） | 1,240 | 428 | **34.52%** |
  | `MEMBER_ID`（辅） | 682 | 186 | **27.27%** |
  | 差异 | −558 | −242 | **−7.24 个百分点** |

差 7.24 个百分点不是小数。只报 `MEMBER_ID` 口径，市场部会以为复购率只有 27% 而做出「加大发卡力度」的错误决策——实际那些未办卡的回头客已经在复购了，问题不在发卡。

**落地方案：** `identity_key_type` **进唯一键**，同窗口两口径各存一行、永不混算。详见 §3.4.1 与数据结构文件 §4.5.1。

#### 1.4.3 单次消费 vs 复购

**单次消费顾客**：窗口内有效消费正好 1 次。
**复购顾客**：窗口内有效消费 ≥ 2 次。

二者互斥且穷尽，`单次顾客数 + 复购顾客数 = 有效顾客数`。这条恒等式在数据库层由 CHECK 强制。

#### 1.4.4 有效消费 vs 全部消费

**有效消费**必须同时满足：正常成交、已交付、非窗口内退单、非仅付定金未付尾款、有身份标识。窗口结束后发生的退单不追溯改变原期，而是在下一期写冲正行。

口径与 M22-05 逐字一致，详见 §8.5.1。

### 1.5 目标

1. **复购率双口径可并排对比**：同一窗口两口径各自成行，页面并排展示并给出差异归因，差异可算出精确到 0.01 个百分点。
2. **生命周期与价值分群判定可执行**：六个阶段与六个分群各有明确的阈值与快速短路顺序，任意会员可在 50ms 内判定，且判定依据（`rule_code` + `rule_desc`）可展示。
3. **消费数据不丢**：`m16.settlement.completed` 事件丢失时，日终对账 + 7 天短期补数 + 封账前终检三层兜底，最终缺失率 < 0.01%。
4. **流失预警可行动**：风险分 0~100 分四级，只有 MEDIUM 以上才推送，避免「沉默天数排序」误伤低价值客户浪费外呼成本。
5. **口径变更可重算可对比**：`calc_version` 升版后新旧两版结果并存，页面可并排展示差异，历史封账期不被改写。
6. **隐私红线可验证**：分组样本 < 5 一律抑制，导出必留痕并带水印，含敏感字段必须审批，全部有验收用例。
7. **性能达标**：看板 P95 ≤ 1,500ms，P-10 契约接口 P95 ≤ 200ms，导出 1 万行 ≤ 30s。

### 2.3 边界判定原则

遇到归属争议时按三条判断：

1. **「算」与「判」分离**：计算结果（金额、笔数、比率）归 M16/M22，本子模块只做「判定」（这个会员是什么阶段、什么分群、什么风险）。例如复购率**算法**由 M22-05 定义，本子模块按该算法判出「哪些会员复购了」。
2. **「执行」与「建议」分离**：一切对外触达动作归 M19-03，本子模块只给建议（`recall_suggest`、`recall_channel`）。
3. **「主数据」与「快照」分离**：任何 M03 已有的会员字段，本子模块只能存快照（`*_snap`），不能建表、不能回写。

### 3.4 关键计算模型

#### 3.4.1 复购率双口径模型

**公式：**

```
复购率 = 窗口内有效消费 ≥ 2 次的顾客数 ÷ 窗口内有效消费 ≥ 1 次的顾客数
```

**身份口径 `identity_key_type`：**

- `PATIENT_ID`（主）：以 `patient_id` 归并
- `MEMBER_ID`（辅）：以 `member_id` 归并
- `CUSTOMER_NO`（兜底）：无 `patient_id` 时用 M16 客户号

**多卡归并与身份冲突（与 M22-05 逐字对齐）：**

  | 情形 | 处理 | 明细行标记 |
  | --- | --- | --- |
  | 同一 patient 多张卡 | 按 `patient_id` 归并 | `identity_merge_rule = 'MULTI_CARD_MERGED'` |
  | 卡未绑定患者，手机号与某 patient 一致 | 归并到该 patient | `identity_merge_rule = 'PHONE_MATCHED'` |
  | 两卡分属不同 patient_id 但手机号相同 | **不自动归并** | `identity_merge_rule = 'CONFLICT'`，`is_valid_consume = FALSE` |
  | 完全无身份标识 | 只计入总消费额，不进分母 | `invalid_reason = 'NO_IDENTITY'` |

**算例（2026-10，与总纲 §6.5 一致）：**

`PATIENT_ID` 口径：

- 有效顾客 1,240 人，其中复购 428 人、单次 812 人
- 有效消费笔数 2,180 笔，复购笔数 = 2,180 − 428 = 940 笔
- 复购率 = 428 ÷ 1,240 = 0.345161 → **34.52%**

`MEMBER_ID` 口径：

- 有效顾客 682 人，其中复购 186 人、单次 496 人
- 有效消费笔数 1,058 笔，复购笔数 372 笔（按「有效笔数 − 复购顾客数」规则，与主口径同法）
- 复购率 = 186 ÷ 682 = 0.272727 → **27.27%**

**两口径的笔数校验：** 主口径 `812 + 428 = 1,240` ✓、`1,240 + 940 = 2,180` ✓；辅口径 `496 + 186 = 682` ✓、`682 + 372 = 1,054`，与 1,058 差 4 笔——这 4 笔属于 `member_id` 相同但 `patient_id` 不同的冲突行，已按 M22-05 规则排除（`identity_merge_rule = 'CONFLICT'`），在 `conflict_cnt` 中单独留痕。

**差异归因：** 34.52% − 27.27% = **7.24 个百分点**。原因是办卡率约 40%——未办卡的回头客在 `PATIENT_ID` 口径下被算作复购顾客，在 `MEMBER_ID` 口径下根本不存在。

**边界与失败条件：**

- 分母为 0 → `repurchase_rate IS NULL`，**不得为 0**（CHECK 强制）
- `SAVEPOINT`/事务失败 → 整期不写入，保留上一版
- 同日多次重算 → 唯一键 `(period, window_type, dept_id, identity_key_type, calc_version)` 保证幂等

**舍入规则：** 比率 `NUMERIC(10,6)` 由数据库精确计算，页面展示时保留 2 位小数（百分比），四舍五入。

#### 3.4.2 生命周期判定模型

**判定顺序（短路，命中即停）：**

  | 顺序 | 阶段 | 条件 | 规则编码 |
  | --- | --- | --- | --- |
  | 1 | `LOST` | `silent_days > 365` | `LC_LOST_01` |
  | 2 | `SILENT` | `silent_days` 在 [91, 365] | `LC_SILENT_01` |
  | 3 | `NEW` | `member_age_days <= 90` 且 `consume_cnt_total <= 2` | `LC_NEW_01` |
  | 4 | `DECLINING` | `consume_cnt_recent_3m < consume_cnt_prev_3m` 且 `silent_days <= 90` | `LC_DECLINING_01` |
  | 5 | `GROWING` | `consume_cnt_recent_3m > consume_cnt_prev_3m` 且 `consume_cnt_recent_3m >= 1` | `LC_GROWING_01` |
  | 6 | `MATURE` | `consume_cnt_recent_6m_months >= 4` 且 `silent_days <= 90` | `LC_MATURE_01` |
  | 7 | `MATURE` | 兜底 | `LC_MATURE_02` |

**算例一（DECLINING）：** 会员 M000123，入会 966 天，最近消费 47 天前，近 3 月消费 1 次、前 3 月 4 次。

规则 1：`47 > 365`？否。规则 2：`47` 在 [91,365]？否。规则 3：`966 <= 90`？否。规则 4：`1 < 4` 且 `47 <= 90`？**是** → `DECLINING`。

**算例二（SILENT / LOST 分界）：** `silent_days = 365` → 规则 1 不命中（不大于 365）→ 规则 2 命中 → `SILENT`；`silent_days = 366` → 规则 1 命中 → `LOST`。分界取「大于 365」，让「整整一年没来」仍算沉默而非流失——一年是常见复诊周期。

**算例三（NEW 的边界）：** 入会 88 天、累计消费 2 次 → `NEW`；入会 10 天但累计消费 3 次 → 不判 `NEW`（10 天消费 3 次已是活跃复购客户，标成新人会让运营发错招新券）。

**算例四（从未消费）：** `silent_days IS NULL`，`first_consume_date IS NULL`。SQL 中 `NULL > 365` 结果为 NULL 不命中，继续按规则 3 判定。写入时 `silent_days` 置为 `member_age_days`，`last_consume_date` 保持 NULL，页面显示「从未消费（入会 400 天）」。

**舍入与边界：** `silent_days` 为整数天，用 `stat_date − last_consume_date` 计算。`silent_threshold_days = ROUND(avg_repurchase_days × churn_factor)::INTEGER`，CHECK 强制自洽。

#### 3.4.3 RFM 价值分群模型

**定义：**

- **R（Recency）** = `stat_date − last_consume_date` 天数，越小越好
- **F（Frequency）** = 近 12 个月有效消费次数，越大越好
- **M（Monetary）** = 近 12 个月有效消费金额，越大越好

**打分（分位法，1~5 分）：** 对全体有消费记录的会员取 20/40/60/80 分位为档位边界：

  | 分档 | R（天，越小越好） | F（次，越大越好） | M（元，越大越好） |
  | --- | --- | --- | --- |
  | 5 | ≤ R20 | ≥ F80 | ≥ M80 |
  | 4 | (R20, R40] | [F60, F80) | [M60, M80) |
  | 3 | (R40, R60] | [F40, F60) | [M40, M60) |
  | 2 | (R60, R80] | [F20, F40) | [M20, M40) |
  | 1 | > R80 | < F20 | < M20 |

**2026-10 实际阈值：** R20/R40/R60/R80 = 21/58/112/210 天；F20/F40/F60/F80 = 1/2/3/5 次；M20/M40/M60/M80 = 480.00/1,250.00/2,880.00/6,400.00 元。

**为什么用分位法：** 固定阈值（如「≥ 5,000 元算高价值」）三年后可能一半人超过，分群失去区分度。分位法保证永远有 20% 的人拿 5 分，结构稳定可横向比较。本期阈值写入 `threshold_json` 便于重算对比。

**分群映射（短路）：**

  | 顺序 | 分群 | 条件 | 规则编码 |
  | --- | --- | --- | --- |
  | 1 | `LOST` | 生命周期 = `LOST` | `SG_LOST_01` |
  | 2 | `SILENT` | 生命周期 = `SILENT` | `SG_SILENT_01` |
  | 3 | `VIP` | `m_score >= 4` 且 `f_score >= 4` | `SG_VIP_01` |
  | 4 | `CORE` | (`m_score >= 4` 且 `f_score = 3`) 或 (`m_score = 3` 且 `f_score >= 4`) | `SG_CORE_01` |
  | 5 | `POTENTIAL` | `r_score >= 4` 且 `m_score >= 3` | `SG_POTENTIAL_01` |
  | 6 | `ORDINARY` | 其余 | `SG_ORDINARY_01` |

**任务书指定算例：R=5、F=3、M=4**

- 规则 1、2：`recency_days` 未超 90 天，不命中
- 规则 3：`m_score = 4 >= 4` 成立，但 `f_score = 3 >= 4` **不成立** → 不命中
- 规则 4：`m_score >= 4 且 f_score = 3` → **命中** → `CORE`

**结论：R=5、F=3、M=4 属于 `CORE`（核心客户），不是 `VIP`。**

运营差别：`VIP` 是「又勤又来又花钱」，直接给权益维护即可；`CORE` 是「花钱多但来得不勤」，需要**提频**动作（发到店券、做复购提醒），单纯给折扣不会改变频次。

**对照算例：** R=5、F=4、M=4 → 规则 3 命中 → `VIP`；R=5、F=2、M=3 → 规则 3、4 不命中，规则 5 命中（`r_score=5>=4` 且 `m_score=3>=3`）→ `POTENTIAL`。

#### 3.4.4 流失风险评分模型

**公式：**

```
risk_score = score_silent_part + score_value_part + score_trend_part + score_stage_part
```

  | 分项 | 上限 | 公式 |
  | --- | --- | --- |
  | 沉默分 `score_silent_part` | 40 | `LEAST(40, silent_ratio × 20)`，`silent_ratio = silent_days ÷ silent_threshold_days` |
  | 价值分 `score_value_part` | 35 | `LEAST(35, amount_recent_12m ÷ 1000 × 5)` |
  | 趋势分 `score_trend_part` | 15 | `trend_rate = (近 3 月 − 前 3 月) ÷ 前 3 月`；NULL→7，≥0→0，<0→`LEAST(15, abs(trend_rate) × 15)` |
  | 阶段分 `score_stage_part` | 10 | `LOST` → 10，`SILENT` → 0（不存字段，由 `lifecycle_stage` 反推） |

**等级门槛：**

  | 等级 | 分数 | 推送 | 优先级 |
  | --- | --- | --- | --- |
  | `CRITICAL` | ≥ 75 | 是 | 1 |
  | `HIGH` | 50 ~ 75 | 是 | 2 |
  | `MEDIUM` | 25 ~ 50 | 是 | 3~4 |
  | `LOW` | < 25 | 否 | 0 |

**算例一（任务书指定：90 天未到店 + 历史年消费 ≥ 5,000）：**

会员 M000888 实际 95 天未到店（属 `SILENT`，进本表），平均复购周期 200 天，流失系数 1.5 → 阈值 300 天。

- 沉默分：`95 ÷ 300 = 0.316667` → `0.316667 × 20 = 6.33`
- 价值分：近 12 月消费 12,000.00 元 → `LEAST(35, 12 × 5) = LEAST(35, 60) = 35.00`（触顶）
- 趋势分：前 3 月 3,000.00、近 3 月 800.00 → `trend_rate = (800 − 3,000) ÷ 3,000 = -0.733333` → `LEAST(15, 0.733333 × 15) = 11.00`
- 阶段分：`SILENT` → 0
- `risk_score = 6.33 + 35.00 + 11.00 + 0 = 52.33` → **`HIGH`**，优先级 2

页面展示：「该会员 95 天未到店（阈值 300 天），近 12 个月消费 12,000.00 元，近 3 个月消费 800.00 元环比下降 73.33%。风险分 52.33（HIGH）。建议：人工外呼 + 到店礼。」

**算例二（CRITICAL）：** 400 天未到店、复购周期 180（阈值 270）、近 12 月消费 8,000.00、近 3 月 0、前 3 月 1,500.00。

- 沉默分：`400 ÷ 270 = 1.481481` → `LEAST(40, 29.63) = 29.63`
- 价值分：`LEAST(35, 8 × 5) = 35.00`
- 趋势分：`trend_rate = -1.000000` → `15.00`
- 阶段分：`LOST` → 10
- `risk_score = 29.63 + 35.00 + 15.00 + 10 = 89.63` → **`CRITICAL`**，优先级 1

**算例三（LOW，不该打扰）：** 100 天未到店、无复购样本（阈值兜底 180）、近 12 月消费 200.00、近 3 月 100.00、前 3 月 100.00。

- 沉默分：`100 ÷ 180 = 0.555556` → `11.11`
- 价值分：`200 ÷ 1000 × 5 = 1.00`
- 趋势分：`trend_rate = 0` → `0`
- 阶段分：`SILENT` → 0
- `risk_score = 12.11` → **`LOW`**，不推送

**为什么价值分必须存在：** 若只按沉默天数排序，这位只花过 200 元的会员会排在很前面触发外呼——外呼成本约 15 元/次，召回成功率不到 5%，投入产出为负。价值分这一项把这类打扰挡在门外。

**边界与失败条件：**

- `silent_threshold_days = 0` → `silent_ratio` NULL → 沉默分按 0 计（不因分母为 0 而报错）
- `amount_prev_3m = 0` → `trend_rate` NULL → 趋势分给 7（中间值）
- 会员在生命周期表里是 `NEW`/`GROWING`/`MATURE`/`DECLINING` → **不进本表**

#### 3.4.5 会员注销与合并的口径模型

  | 事件 | 对历史数据的影响 | 对当期数据的影响 |
  | --- | --- | --- |
  | `mpi.member.status_changed`（注销/停用） | **不重算**，历史照算 | 主口径含已注销会员，另存 `cancelled_customer_cnt` 与 `rate_excl_cancelled` |
  | `mpi.member.merged`（合并） | 已封账期**不重算** | 下一期重算时自然归并到主会员 |
  | `mpi.member.merge_conflict` | 标记冲突，不算 | 明细行 `identity_merge_rule = 'CONFLICT'`，`is_valid_consume = FALSE` |

**算例（注销口径）：** 2026-10 `PATIENT_ID` 口径，有效顾客 1,240 中含已注销 96 人（其中复购 18 人）。

- 主口径（含已注销）：428 ÷ 1,240 = 0.345161 → **34.52%**
- 剔除已注销：(428 − 18) ÷ (1,240 − 96) = 410 ÷ 1,144 = 0.358392 → **35.84%**
- 差异：**+1.32 个百分点**

差异方向是剔除后更高，符合直觉：已注销会员里「消费一次就走」的比例偏高（96 人中仅 18 人复购，复购率 18.75%，远低于整体 34.52%）。

**为什么主口径选「含已注销」：** M22-05 已定复购率的分子分母都由窗口内实际消费的人构成，会员状态不是筛选条件。改主口径会造成与 M22 指标永久差 1.32 个百分点。

**算例（合并口径）：** 患者 A（10086）窗口内消费 1 次，患者 B（20001）窗口内消费 2 次，实为同一人，8 月合并。

- 合并前：两行，各分母 1
- 合并后：一行，分母 1，按 3 次消费判复购
- 若强行把 B 的消费 `UPDATE` 到 A：分母从 1,240 变 1,200（合并 40 对），复购率从 34.52% 虚高到 428 ÷ 1,200 = **35.67%**，凭空多 1.15 个百分点且不可追溯

#### 3.4.6 生命周期迁移率与分群结构

**阶段迁移率：**

```
阶段迁移率 = 本期发生阶段变更的会员数 ÷ 本期有判定结果的会员数
```

**分群结构（页面 P05）：**

```
分群人数占比 = 该分群人数 ÷ 有消费记录会员总数
分群金额占比 = 该分群消费金额 ÷ 全部会员消费金额
```

**分母为 0 的规则（任务书第 9 条）：** 上述所有比率在分母为 0 时一律 `NULL`，**不得为 0**。原因：新开科室、新开渠道当期可能一个顾客都没有，填 0 会让它在排序里排到最后，看起来像「表现最差」，实际是「没有数据」。

**算例：** 某新开科室 2026-10 只有 0 个有效顾客。其复购事实行的 `valid_customer_cnt = 0`、`repurchase_rate IS NULL`。页面显示「—（无数据）」，排序时排在最后并单独标注，而不是显示「0.00%」，避免被误读为「复购率 0」。

- 圈人器命中人数 < 5 时拒绝导出并提示 `"1906009"`

### 5.7 P06 会员流失预警

**页面定位：** 客服主管每天的工作清单。

**区块一：风险分布（4 个数字卡）**

  | 等级 | 人数 | 占比 | 行动 |
  | --- | --- | --- | --- |
  | `CRITICAL` | 38 | 6.21% | 优先级 1，当日外呼 |
  | `HIGH` | 164 | 26.80% | 优先级 2，3 日内联系 |
  | `MEDIUM` | 210 | 34.31% | 优先级 3~4，本周触达 |
  | `LOW` | 200 | 32.68% | 不推送，仅展示 |

**区块二：待召回名单（主表格）**

列：优先级、会员号（脱敏）、会员等级快照、价值分群、沉默天数、阈值天数、近 12 月消费、近 3 月环比、风险分、风险等级、建议动作、推送状态。

按 `recall_priority ASC, risk_score DESC` 排序。每行可展开看到风险分四项分解：

```
风险分 52.33 = 沉默分 6.33（95 天 ÷ 阈值 300 天 × 20）
             + 价值分 35.00（近 12 月 12,000.00 元 ÷ 1000 × 5，触顶 35）
             + 趋势分 11.00（近 3 月 800.00 元 vs 前 3 月 3,000.00 元，-73.33%）
             + 阶段分 0（SILENT）
```

**区块三：风险分算法说明** — 静态说明卡，展示 §3.4.4 的四项公式与四档门槛。

**区块四：召回效果追踪** — 展示「已推送会员中，30 天内重新消费的比例」，数据来自 M19-03 的执行结果回传。

**交互约束：**

- 名单**不含手机号**，只显示脱敏会员号（任务书第 10 条隐私红线）

- 页面顶部固定提示：「本页只提供召回建议。实际触达由 M19-03 关怀与召回执行，并需通过退订/黑名单、免打扰时段、频次三道闸门。」

```python
"""M19-06 Service 层核心逻辑摘要。"""

from __future__ import annotations

from decimal import Decimal

from app.repositories.m19 import member_analysis_repo


def calc_repurchase_rate(repurchase_cnt: int, valid_cnt: int) -> Decimal | None:
    """复购率。分母为 0 时返回 None，绝不返回 0。

    返回 None 而不是 Decimal("0") 是任务书第 9 条的硬要求：
    新会员、新科室、新渠道在当期可能没有任何有效顾客，
    若返回 0 会被排序逻辑排到末位并显示为「复购率 0%」，
    让运营误判为「表现最差」而非「没有数据」。
    """
    if valid_cnt <= 0:
        return None
    return (Decimal(repurchase_cnt) / Decimal(valid_cnt)).quantize(Decimal("0.000001"))


def calc_risk_score(
    silent_days: int,
    threshold_days: int,
    amount_recent_12m: Decimal,
    amount_recent_3m: Decimal,
    amount_prev_3m: Decimal,
    lifecycle_stage: str,
) -> dict:
    """流失风险分四项分解，返回分项与总分。

    各项上限：沉默 40 / 价值 35 / 趋势 15 / 阶段 10。
    """
    if threshold_days > 0:
        silent_ratio = Decimal(silent_days) / Decimal(threshold_days)
        silent_part = min(Decimal("40"), silent_ratio * Decimal("20"))
    else:
        silent_ratio = None
        silent_part = Decimal("0")

    value_part = min(Decimal("35"), amount_recent_12m / Decimal("1000") * Decimal("5"))

    if amount_prev_3m > 0:
        trend_rate = (amount_recent_3m - amount_prev_3m) / amount_prev_3m
        if trend_rate >= 0:
            trend_part = Decimal("0")
        else:
            trend_part = min(Decimal("15"), abs(trend_rate) * Decimal("15"))
    else:
        trend_rate = None
        trend_part = Decimal("7")

    stage_part = Decimal("10") if lifecycle_stage == "LOST" else Decimal("0")
    total = silent_part + value_part + trend_part + stage_part

    if total >= 75:
        level = "CRITICAL"
        priority = 1
    elif total >= 50:
        level = "HIGH"
        priority = 2
    elif total >= 25:
        level = "MEDIUM"
        priority = 3
    else:
        level = "LOW"
        priority = 0

    return {
        "silent_part": silent_part,
        "value_part": value_part,
        "trend_part": trend_part,
        "stage_part": stage_part,
        "risk_score": total,
        "risk_level": level,
        "recall_priority": priority,
        "silent_ratio": silent_ratio,
        "trend_rate": trend_rate,
    }


async def ensure_sync_complete(biz_date) -> bool:
    """判断某业务日的数据是否已完整同步，供看板完整性提示使用。"""
    row = await member_analysis_repo.latest_sync_log(biz_date)
    if row is None:
        return False
    return row.source_status == "COMPLETE" and row.failed_cnt == 0
```

**Service 层三条硬约束：**

1. **比率函数一律先判分母**，分母 ≤ 0 返回 `None`。不允许在调用方补 0。
2. **风险分四项分别计算后再相加**，不允许内联成一个大表达式——分项要落库供页面展示「这 52.33 分是怎么来的」。
3. **所有跨模块数据都通过 `app/clients/` 里的客户端取**，Service 层不直接 `SELECT` 其他模块的表。

**缓存击穿防护：** 所有带 TTL 的 Key 在写入时 TTL 加 0–60 秒随机抖动，避免同一时刻集中失效。热点 key（`value-segment:{member_id}`）在同一秒内被 M22 与 M10-08 同时请求时，用 `SETNX` 互斥重建，未抢到的请求短暂等待 50ms 后重读。

**为什么 P-10 必须走缓存：** P95 ≤ 200ms 要求单次查询不能超过两次索引扫描。分群表有 184 万行明细，即便有 `idx_m19_member_segment_member (member_id, period)`，查一次最新期间也需 3–8ms；加上生命周期与风险两次查询、加上 ORM 序列化，实测约 25ms——看似够快，但 M22 在做批量指标采集时会连续调用数百次，总耗时会超出 200ms 的单次预算要求。缓存命中后单次约 2ms。

**任务依赖与顺序：** 每日链路为串行依赖——`consume_sync`（02:30）→ `consume_repair`（03:00）→ `consume_aggregate`（03:30）→ `repurchase_calc`（04:00）→ `lifecycle_calc`（05:00）→ `segment_calc`（05:30）→ `churn_calc`（06:00）→ `churn_push` + `profile_calc`（06:30）。每步完成写入 `m19_member_sync_log` 或 `m19_member_oper_log`，下一步启动前检查前置任务是否成功；失败则阻断后续并告警。

**复购双口径的唯一性要点：** `identity_key_type` 是唯一键的一部分。同一 `(period, window_type, dept_id)` 下 `PATIENT_ID` 与 `MEMBER_ID` 是**两行**，永不互相覆盖。若写入时漏了 `identity_key_type`，PostgreSQL 会用默认值 `PATIENT_ID`，`MEMBER_ID` 那一行永远写不进去——这是本子模块最危险的静默失败。防法是 `ck_m19_member_repurchase_merge_sum`：`MEMBER_ID` 口径下三类归并计数必须为 0，一旦写串就会撞约束。

### 8.3 状态流转规则

**生命周期：** 迁移规则见 §3.2.1。约束：

- `LOST` 必须有 `silent_days > 365`（CHECK 强制）
- 阶段判定顺序短路，不允许并列判定

**流失推送：**

- 只有 `risk_level <> 'LOW'` 才推送（CHECK 强制 `is_pushed = TRUE` 时等级非 LOW）
- 推送后置 `is_pushed = TRUE` 并写 `pushed_at`
- 次日重算产生**新行**，历史行不改

**导出：** `RUNNING` → `SUCCESS` / `FAILED` → `EXPIRED`。

### 8.5 计算规则

#### 8.5.1 有效消费判定

判定顺序短路，命中第一条即判定为无效：

  | 顺序 | 条件 | 结论 | `invalid_reason` |
  | --- | --- | --- | --- |
  | 1 | 无 `patient_id` 且无 `member_id` 且无 `customer_no` | 无效 | `NO_IDENTITY` |
  | 2 | 仅支付定金未付尾款 | 无效 | `DEPOSIT_ONLY` |
  | 3 | 结算发生在窗口内但已被退单 | 无效 | `REFUNDED_IN_WINDOW` |
  | 4 | 订单未交付（如配镜未取镜） | 无效 | `NOT_DELIVERED` |
  | 5 | 以上都不命中 | 有效 | 空串 |

**窗口结束后退单：** 原期照旧计入，下一期写冲正行（与 M22-05 一致）。这样已封账期的数据不会被改写。

**纯服务单（仅验光）：** 有效（但 `biz_type = 'SERVICE'`，不计入配镜订单统计）。

#### 8.5.2 分母为 0 的统一处理

**规则：** 所有比率在分母为 0 时一律返回/存储 `NULL`，**绝不为 0**。

  | 指标 | 分母 | 分母为 0 时的值 | CHECK 名 |
  | --- | --- | --- | --- |
  | 复购率 | 有效顾客数 | NULL | `ck_m19_member_repurchase_rate_denom` |
  | 单次消费占比 | 有效顾客数 | NULL | `ck_m19_member_repurchase_single_denom` |
  | 人均消费 | 有效顾客数 | NULL | `ck_m19_member_repurchase_avg_denom` |
  | 平均复购间隔 | 参与间隔计算人数 | NULL | `ck_m19_member_repurchase_days_denom` |
  | 剔除注销后复购率 | 有效顾客 − 注销顾客 | NULL | `ck_m19_member_repurchase_excl_denom` |
  | 分群金额占比 | 分群人数 | NULL | `ck_m19_member_segment_share_denom` |
  | 分群人均消费 | 分群人数 | NULL | `ck_m19_member_segment_avg_denom` |
  | 沉默比例 | 沉默阈值天数 | NULL | `ck_m19_member_churn_ratio_denom` |
  | 消费趋势环比 | 前 3 月金额 | NULL | `ck_m19_member_churn_trend_denom` |
  | 阶段迁移率 | 有判定结果会员数 | NULL | — |
  | 金额占比（P02） | 合计金额 | NULL | — |

**为什么这条这么重要（任务书第 9 条）：** 若新会员 / 新科室 / 新渠道的复购率写成 0，会同时造成三个后果：①排序时排到末位，被误判为「表现最差」；②环比计算里 `(0 − 上期) ÷ 上期 = -100%`，图上出现断崖；③聚合时若用 `AVG()`，0 会被计入平均拉低整体指标。用 NULL 则 `AVG()` 自动跳过，排序可用 `NULLS LAST` 明确置底。

#### 8.5.3 舍入规则

  | 对象 | 存储精度 | 展示精度 | 舍入方式 |
  | --- | --- | --- | --- |
  | 金额 | `NUMERIC(14,2)` | 2 位小数 | `ROUND(x, 2)` |
  | 比率 | `NUMERIC(10,6)` | 百分比 2 位小数 | 先 `quantize(0.000001)` 再乘 100 |
  | 天数 | `NUMERIC(10,2)` 或 `INTEGER` | 2 位/整数 | `ROUND` |
  | 风险分 | `NUMERIC(10,6)` | 2 位小数 | `ROUND` |

**不允许多次舍入：** 所有比率在数据库层一次算准，前端只做展示格式化。不允许「后端舍入到 2 位，前端再舍入一次」。

#### 8.5.4 小样本抑制

**阈值：** 分组样本数 < 5 时抑制。

  | 场景 | 抑制方式 |
  | --- | --- |
  | 分群汇总行人数 < 5 | `is_suppressed = TRUE`，金额与占比返回 `null` |
  | 交叉表格子 < 5 | `member_cnt = null`，前端显示 `*` |
  | 名单命中 < 5 | 返回空列表 + 报 `"1906009"` |
  | 圈人命中 < 5 | `hit_cnt = null` + 报 `"1906009"` |
  | 导出抑制 | 抑制行不写入文件，`suppressed_row_cnt` 计数 |
  | 单会员明细行 | **不抑制**（个体不涉及反推） |

### 8.6 引用与删除规则

  | 对象 | 规则 |
  | --- | --- |
  | 消费明细快照 | 只增不改。写 `REVOKE UPDATE, DELETE`，退费以冲正行表达 |
  | 消费快照 | 重算覆盖（`ON CONFLICT DO UPDATE`），封账后不改 |
  | 复购事实 | 口径升版时写新版本行，旧版本保留 |
  | 生命周期 / 分群 / 流失 | 每日新增行，历史保留至保留期 |
  | 画像标签 | 失效置 `is_active = FALSE`，不物理删 |
  | 导出任务 | 逻辑删除，文件 7 天清理 |
  | 操作日志 | 只增不改，`REVOKE UPDATE, DELETE` |

**封账保护：** `is_final = TRUE` 的行任何接口都不得修改。重算请求报 `"1906019"`。

### 8.7 并发规则

  | 场景 | 并发问题 | 处理 |
  | --- | --- | --- |
  | 同一业务日两次同步 | 重复写入明细 | 唯一键 `(settle_no, row_type, source_event_id)` + `ON CONFLICT DO NOTHING` |
  | 同一期间两次重算 | 数据交错 | Redis 锁 `m19:member:lock:recalc:{period}`，抢不到报 `"1906023"` |
  | 同步任务并发 | 重复拉取 | Redis 锁 `m19:member:lock:sync:{biz_date}` |
  | 同一导出重复提交 | 多份文件 | Idempotency-Key 24h |
  | 同一召回重复提交 | 多次关怀 | Idempotency-Key 24h + 30 秒窗口 |
  | 缓存同时失效 | 击穿 | `SETNX` 互斥重建 + TTL 抖动 |
  | 分群计算与 P-10 查询并发 | 读到半成品 | 计算写新版本行（新 `calc_version`），查询读已提交的最新完整版本 |
  | 单号生成并发 | 重复单号 | Redis `INCR` 原子操作 |

**为什么必须用 Redis `INCR` 而不是数据库序列拼日期（共享规范 §3.5）：** 数据库序列在跨零点时，若 23:59:59 的请求拿到序列值 9999，00:00:01 的请求拿到 10000，但两次记录的日期分别是 `20261105` 与 `20261106`，拼出来是 `MS202611059999` 与 `MS2026110610000`——后者是 13 位，格式校验直接失败；更糟的是若两个请求几乎同时且日期都记为 `20261106`，会拼出两个 `MS20261106` 前缀但流水不连续的号。Redis `INCR` 的 key 里带日期，跨零点自动切换到新 key，从根上避免。

**关于 U-09 `mpi.member.level_changed` 的特别说明：** 这条事件**不是**营销动作的结果，而是 M19-04 算完成长值后调 `POST /internal/v1/member/{id}/level-up`，M03-03 处理后发出的**回执**。本子模块订阅它只用于「等级变更分析」（升级/降级人数与趋势），**不能**把它当作「营销活动带来了等级提升」的因果证据——那会把 M19 自己触发的闭环误读成营销效果。

**关于会员状态与等级的回写：** 本子模块需要写入会员标签时调用 `POST /internal/v1/member/{id}/tags/sync`，需要调整等级时调用 `POST /internal/v1/member/{id}/level-up` / `level-down`。**不直接改 `mpi_member` 表。**

**P-10 契约详述（API-28）：**

- 路径**一字不差**：`/internal/v1/m19/member/value-segment/{member_id}`

## 11. 异常与日志

### 11.1 异常分类

  | 类别 | 示例 | HTTP | 处理策略 |
  | --- | --- | --- | --- |
  | 参数异常 | `period` 格式错、`identity_key_type` 非法 | 400 | 直接返回，不重试 |
  | 权限异常 | 科室越权、敏感字段无权限 | 403 | 直接返回，记审计日志 |
  | 资源不存在 | 会员无分群、导出单号不存在 | 404 | 直接返回 |

  | 上游异常 | M16 超时、M19-03 不可用 | 503 | 重试 3 次（指数退避），失败后降级 |
  | 计算异常 | 分群任务失败、复购数据不完整 | 500 | 保留上一版结果，告警 |
  | 系统异常 | 未捕获异常 | 500 | 返回 `"199001"`，记完整堆栈，带 `trace_id` |

### 11.2 降级策略

  | 依赖 | 不可用时的表现 | 用户可见影响 |
