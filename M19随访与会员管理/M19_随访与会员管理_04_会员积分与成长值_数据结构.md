## 1. 表清单

| 序号 | 表名 | 中文名 | 用途 | 预估行数 |
|---|---|---|---|---|
| 4.2 | `m19_points_rule` | 积分规则主表 | 定义一类业务行为如何产生积分（按金额/按次数/按行为/固定值） | 小（约 80 行） |
| 4.3 | `m19_points_rule_item` | 积分规则明细表 | 规则 × 会员等级的倍率矩阵，是「等级 → 积分倍率」的唯一归属 | 小（约 600 行） |
| 4.4 | `m19_points_account` | 积分账户表 | 一个会员一个账户，保存余额派生缓存与状态 | 中（约 12 万行） |
| 4.5 | `m19_points_ledger` | 积分流水表（分区） | **只增不改**的积分账本，每条流水带 `balance_after` | 大（约 292 万行/年） |
| 4.6 | `m19_points_growth_ledger` | 成长值流水表（分区） | **只增不改**的成长值账本，成长值只增不减 | 大（约 240 万行/年） |
| 4.7 | `m19_points_level_rule` | 等级门槛规则表 | 成长值门槛 → 会员等级，是「等级 → 成长值门槛」的唯一归属 | 小（约 12 行） |
| 4.8 | `m19_points_expire_record` | 积分过期记录表 | 按批次先进先出的过期明细，可回答「哪些批次先过期」 | 中（约 60 万行/年） |
| 4.9 | `m19_points_exchange` | 积分兑换表 | 积分兑换订单，「先扣积分后发货」+ 失败追加 REVERSE | 中（约 8 万行/年） |
| 4.10 | `m19_points_adjust` | 积分调整申请单表 | 人工调整与补录的审批单，杜绝绕过流水的直接改余额 | 小（约 3000 行/年） |
| 4.11 | `m19_points_reconcile` | 积分对账表 | 每日 03:00 账户余额 vs 流水汇总的差异明细 | 小（约 5000 行/年） |
| 4.12 | `m19_points_log` | 积分操作日志表（分区） | 规则变更、调整、过期、对账等关键动作的审计日志 | 中（约 40 万行/年） |

**合计：11 张表**

**分区表（2 张流水 + 1 张日志）：** `m19_points_ledger`、`m19_points_growth_ledger`、`m19_points_log`，均按 `created_at` 月 RANGE 分区，且均建 `DEFAULT` 分区。

> **边界红线（M19 不建的表）**：`m19_member_level`（等级定义）、`m19_member_benefit`（权益定义）、`m19_member_level_benefit`（等级权益）、`m19_member_tag`（会员标签）、`m19_member`（会员主档）全部归 M03-03。本子模块只在 `m19_points_rule_item.level_code` 与 `m19_points_level_rule.level_code` 中以**逻辑外键**引用 M03-03 的等级编码，取值必须与 `mpi_member_level.level_code` 逐字一致。

**复用 M19-05 的表（不重复建）：** 兑换实物或权益时的核销由 M19-05 `m19_benefit_redeem` 承担，本子模块的 `m19_points_exchange` 只记录积分侧扣减，两者通过 `exchange_no` 双向关联。

### 4.2 表：`m19_points_rule`（积分规则主表）

**用途：** 定义「一类业务行为如何产生积分」。例如「门诊结算按金额 1 元 = 0.1 分」是一条规则，「视光配镜按金额 1 元 = 0.2 分」是另一条。规则本身不含等级维度，等级维度在 `m19_points_rule_item` 中展开。

**写入方：** P04 积分规则配置（`m19:points:rule:config`） **只读方：** P03 积分流水（展示规则快照）、P04 规则列表、P09 对账（差异归因）

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |
| rule_code | VARCHAR(64) | N | - | 规则编码，格式 `PR_{业务}_{动作}` 全大写，如 `PR_OUTPATIENT_VISIT`；**调用方 P-03 传入的就是它**，一经启用不可改 |
| rule_name | VARCHAR(128) | N | - | 规则名称，如「门诊结算积分」 |
| rule_type | VARCHAR(32) | N | - | 规则类型：`BY_AMOUNT` / `BY_TIMES` / `BY_ACTION` / `FIXED` |
| biz_scene | VARCHAR(32) | N | - | 业务场景：`OUTPATIENT` / `INPATIENT` / `OPTICAL` / `REFRACTIVE` / `FOLLOWUP` / `ACTIVITY` / `OTHER` |
| grow_coefficient | NUMERIC(10,6) | N | 1.000000 | 成长值系数（1 元 = N 成长值），默认 1.000000 |
| fix_points | NUMERIC(14,2) | Y | NULL | `rule_type = 'FIXED'` 时的固定积分值；其余类型必须为 NULL |
| amount_step | NUMERIC(14,2) | Y | NULL | `rule_type = 'BY_AMOUNT'` 时的取整步长（如每 1 元一档）；NULL 表示按实际金额连续计算 |
| times_limit_daily | INT | Y | NULL | `rule_type = 'BY_TIMES'` 时每日最多计次；NULL 表示不限 |
| max_points_per_txn | NUMERIC(14,2) | Y | NULL | 单笔最多发放积分上限，防止大额结算异常；NULL 表示不限 |
| min_biz_amount | NUMERIC(14,2) | N | 0.00 | 触发本规则的最低消费金额，低于此额不发积分 |
| valid_from | DATE | N | - | 规则生效日期 |
| valid_to | DATE | Y | NULL | 规则失效日期，NULL 表示长期有效 |
| priority | INT | N | 100 | 同一业务场景多条规则命中时的优先级，**数值小的先命中，命中即停止** |
| is_exclusive | BOOLEAN | N | TRUE | 是否排他：TRUE 表示命中后不再匹配同场景其他规则 |
| effective_status | VARCHAR(32) | N | 'DRAFT' | 生效状态：`DRAFT` / `REVIEWING` / `ACTIVE` / `INACTIVE` |
| rule_version | INT | N | 1 | 规则版本号，**每次修改倍率矩阵或系数即 +1**，用于流水追溯「当时用的是哪一版规则」 |
| approved_by | BIGINT | Y | NULL | 审批人 |
| approved_at | TIMESTAMP | Y | NULL | 审批时间 |
| change_reason | VARCHAR(512) | Y | NULL | 本次版本变更原因，**非首次版本必填** |
| remark | VARCHAR(512) | Y | NULL | 备注 |
| created_at | TIMESTAMP | N | CURRENT_TIMESTAMP | 创建时间 |
| created_by | BIGINT | Y | NULL | 创建人 |
| updated_at | TIMESTAMP | N | CURRENT_TIMESTAMP | 更新时间 |
| updated_by | BIGINT | Y | NULL | 更新人 |
| is_deleted | BOOLEAN | N | FALSE | 逻辑删除 |

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| pk_m19_points_rule | PRIMARY | id | 主键 |
| uk_m19_points_rule_code | UNIQUE | rule_code | 规则编码全局唯一（不区分逻辑删除，编码不可复用） |
| idx_m19_points_rule_scene | NORMAL | biz_scene, priority, effective_status | 命中的主查询路径 |
| idx_m19_points_rule_valid | NORMAL | valid_from, valid_to | 有效期扫描 |

**约束说明**

```sql
ALTER TABLE m19_points_rule
    ADD CONSTRAINT ck_m19_points_rule_type
    CHECK (rule_type IN ('BY_AMOUNT', 'BY_TIMES', 'BY_ACTION', 'FIXED'));

ALTER TABLE m19_points_rule
    ADD CONSTRAINT ck_m19_points_rule_scene
    CHECK (biz_scene IN ('OUTPATIENT', 'INPATIENT', 'OPTICAL',
                         'REFRACTIVE', 'FOLLOWUP', 'ACTIVITY', 'OTHER'));

ALTER TABLE m19_points_rule
    ADD CONSTRAINT ck_m19_points_rule_effective_status
    CHECK (effective_status IN ('DRAFT', 'REVIEWING', 'ACTIVE', 'INACTIVE'));

-- 单列约束：各字段自身合法
ALTER TABLE m19_points_rule
    ADD CONSTRAINT ck_m19_points_rule_fix_points_nonneg
    CHECK (fix_points IS NULL OR fix_points > 0);

ALTER TABLE m19_points_rule
    ADD CONSTRAINT ck_m19_points_rule_grow_coefficient
    CHECK (grow_coefficient >= 0);

ALTER TABLE m19_points_rule
    ADD CONSTRAINT ck_m19_points_rule_valid_range
    CHECK (valid_to IS NULL OR valid_to >= valid_from);

-- 组合约束：FIXED 类型必须有 fix_points，且不能有 amount_step / times_limit_daily
-- 防的错误：把 BY_AMOUNT 规则改成 FIXED 后忘了填 fix_points，发放时算出 NULL 积分，
--          下游 P-03 返回 granted_points = null，会员收到「+null 分」的短信。
ALTER TABLE m19_points_rule
    ADD CONSTRAINT ck_m19_points_rule_fixed_fields
    CHECK (
        (rule_type = 'FIXED'
            AND fix_points IS NOT NULL
            AND amount_step IS NULL
            AND times_limit_daily IS NULL)
        OR
        (rule_type <> 'FIXED' AND fix_points IS NULL)
    );

-- 组合约束：BY_AMOUNT 与 BY_TIMES/ACTION 的可选参数互斥
ALTER TABLE m19_points_rule
    ADD CONSTRAINT ck_m19_points_rule_type_fields
    CHECK (
        (rule_type = 'BY_TIMES' AND times_limit_daily IS NOT NULL)
        OR (rule_type <> 'BY_TIMES' AND times_limit_daily IS NULL)
    );

-- 组合约束：只有 ACTIVE 才必须审批，且必须审批人非空
ALTER TABLE m19_points_rule
    ADD CONSTRAINT ck_m19_points_rule_approved
    CHECK (effective_status <> 'ACTIVE' OR (approved_by IS NOT NULL AND approved_at IS NOT NULL));

-- 组合约束：版本 > 1 必须有变更原因
ALTER TABLE m19_points_rule
    ADD CONSTRAINT ck_m19_points_rule_change_reason
    CHECK (rule_version = 1 OR change_reason IS NOT NULL);

-- 组合约束：编码格式
ALTER TABLE m19_points_rule
    ADD CONSTRAINT ck_m19_points_rule_code_format
    CHECK (rule_code ~ '^PR_[A-Z][A-Z0-9_]*$');
```

**为什么这样设计**

| # | 决策 | 理由 | 不这么做会怎样 |
|---|---|---|---|
| 1 | 规则主表与倍率明细表**拆成两张** | 规则是「怎么算」，倍率是「不同等级算多少」，两者变更频率差一个数量级 | 合成一张表后，改银卡倍率要复制出 4 行整条规则，4 个等级之间不一致的风险随等级数线性上升 |
| 2 | `rule_code` 不允许逻辑删除后复用 | 流水表用 `rule_code` 做幂等键与追溯键，编码复用会让历史流水指向新规则 | 复用后同一个 `PR_OUTPATIENT_VISIT` 在 2026 年指银卡 0.10、2027 年指金卡 0.15，对账与审计都无法还原 |
| 3 | `rule_version` 独立于 `updated_at` | 流水要能说清「这笔积分按哪一版规则算的」，时间戳做不到 | 用时间戳反推版本，一旦出现规则修改时间与流水时间同秒，就无法确定 |
| 4 | `priority` + `is_exclusive` 而非「唯一命中」 | 实际运营中会同时有「门诊基础积分」与「眼科专项积分」，需要可控的多规则叠加 | 只允许一条规则命中，专项活动就得复制整套基础规则 |

### 4.3 表：`m19_points_rule_item`（积分规则明细表）

**用途：** 规则 × 会员等级的倍率矩阵。这是 M19 内**唯一的「等级 → 积分倍率」数据源**。等级定义本身归 M03-03 的 `mpi_member_level`，本表只按 `level_code` 引用它。

**写入方：** P04 积分规则配置（`m19:points:rule:config`） **只读方：** P04 规则详情、P05 成长值与等级规则（只读展示倍率）、积分发放服务（P-03 热路径）

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |
| rule_code | VARCHAR(64) | N | - | 逻辑外键 → `m19_points_rule.rule_code` |
| rule_version | INT | N | - | 与主表同版本的规则版本号，本明细随主表版本一起产生 |
| level_code | VARCHAR(32) | N | - | 逻辑外键 → M03-03 `mpi_member_level.level_code`，**取值逐字一致** |
| points_ratio | NUMERIC(10,6) | N | - | 积分倍率（1 元 = N 分），如 0.100000 表示 1 元积 0.1 分 |
| points_fix | NUMERIC(14,2) | Y | NULL | `rule_type = 'FIXED'` 时该等级的固定积分；只有 FIXED 类型允许非空 |
| is_fallback | BOOLEAN | N | FALSE | 是否为兜底倍率：当会员等级在本规则中缺失时，用兜底行；**同一规则最多一行 TRUE** |
| remark | VARCHAR(512) | Y | NULL | 备注 |
| created_at | TIMESTAMP | N | CURRENT_TIMESTAMP | 创建时间 |
| created_by | BIGINT | Y | NULL | 创建人 |
| updated_at | TIMESTAMP | N | CURRENT_TIMESTAMP | 更新时间 |
| updated_by | BIGINT | Y | NULL | 更新人 |
| is_deleted | BOOLEAN | N | FALSE | 逻辑删除 |

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| pk_m19_points_rule_item | PRIMARY | id | 主键 |
| uk_m19_points_rule_item_level | UNIQUE | rule_code, rule_version, level_code | 同一规则版本下每个等级只有一行倍率 |
| idx_m19_points_rule_item_lookup | NORMAL | level_code, rule_code | 按等级反查全部倍率（P05 页面） |
| uk_m19_points_rule_item_fallback | UNIQUE | rule_code, rule_version | 部分唯一索引，`WHERE is_fallback = TRUE`，保证每条规则版本最多一个兜底 |

**约束说明**

```sql
ALTER TABLE m19_points_rule_item
    ADD CONSTRAINT ck_m19_points_rule_item_ratio
    CHECK (points_ratio >= 0 AND points_ratio <= 100);

-- 组合约束：FIXED 类型必须有 points_fix，非 FIXED 必须为 NULL
-- 防的错误：BY_AMOUNT 规则被误填了 points_fix，发放时两个口径并存，
--          上游与 M19 各取一个，同一笔结算出现两个积分值。
ALTER TABLE m19_points_rule_item
    ADD CONSTRAINT ck_m19_points_rule_item_fix
    CHECK (
        (points_fix IS NOT NULL AND points_ratio = 0)
        OR (points_fix IS NULL AND points_ratio > 0)
    );

CREATE UNIQUE INDEX uk_m19_points_rule_item_fallback
    ON m19_points_rule_item (rule_code, rule_version)
    WHERE is_fallback = TRUE AND is_deleted = FALSE;

-- 兜底行不允许再指定等级，避免语义歧义
ALTER TABLE m19_points_rule_item
    ADD CONSTRAINT ck_m19_points_rule_item_fallback_level
    CHECK (is_fallback = FALSE OR level_code = '*');
```

**为什么这样设计**

| # | 决策 | 理由 | 不这么做会怎样 |
|---|---|---|---|
| 1 | 倍率落在 M19 而非 M03-03 | 倍率是「积分怎么发」的一部分，改倍率的人就是运营积分的人；M03-03 只管等级名称与权益 | 倍率放 M03-03 后，改一次倍率要跨模块发版，运营会被研发排期卡住 |
| 2 | `is_fallback` 兜底行而非「缺失即 0 倍率」 | 新等级上线后 M19 侧尚未配置倍率时，兜底至少按最低等级发放 | 默认 0 倍率会让新等级用户静默少发积分，且没有任何报错，只能靠客诉发现 |
| 3 | `rule_version` 冗余在主表与明细 | 倍率矩阵整体换版，流水按 `(rule_code, rule_version)` 精确追溯 | 只按 `rule_code` 关联，历史流水会显示成最新倍率，审计时「当时为什么发这么多」永远算不清 |
| 4 | `points_ratio` 上限 100 | 1 元最多 100 分是防呆边界，真实业务上限约 2 分 | 配置失误填了 1000，一笔 328.50 元结算发出 328,500 分 |

**口径说明（必读）：** 同一 `rule_code` 下，**同一时刻只有一个 `rule_version` 处于生效状态**，历史版本的明细行保留不删，供流水追溯。查询倍率时必须带上流水所属的 `rule_version`，不得只按 `rule_code` 查。

### 4.4 表：`m19_points_account`（积分账户表）

**写入方：** 积分发放/扣减/过期/兑换/调整服务（均为事务内）、对账任务（只校验写入 `reconcile`） **只读方：** P01 积分中心工作台、P02 账户查询、P-05 会员积分查询

| 索引名 | 类型 | 字段 | 说明 |

| pk_m19_points_account | PRIMARY | id | 主键 |
| uk_m19_points_account_no | UNIQUE | account_no | 账户号唯一 |

**约束说明**

```sql
ALTER TABLE m19_points_account
    ADD CONSTRAINT ck_m19_points_account_status
    CHECK (status IN ('ACTIVE', 'FROZEN', 'CLOSED'));

-- 余额与冻结积分都不能为负
-- 防的错误：扣减时没校验余额，直接把余额减成 -12.50，
--          此后每一次对账都会报差异，且无法判断是这一次扣错还是累计扣错。
ALTER TABLE m19_points_account
    ADD CONSTRAINT ck_m19_points_account_balance
    CHECK (points_balance >= 0);

ALTER TABLE m19_points_account
    ADD CONSTRAINT ck_m19_points_account_frozen
    CHECK (frozen_points >= 0 AND frozen_points <= points_balance);

ALTER TABLE m19_points_account
    ADD CONSTRAINT ck_m19_points_account_growth
    CHECK (growth_value >= 0);

ALTER TABLE m19_points_account
    ADD CONSTRAINT ck_m19_points_account_totals
    CHECK (total_granted >= 0 AND total_consumed >= 0);

-- 组合约束：FROZEN 必须有原因与时间
ALTER TABLE m19_points_account
    ADD CONSTRAINT ck_m19_points_account_frozen_reason
    CHECK (status <> 'FROZEN' OR (frozen_reason IS NOT NULL AND frozen_at IS NOT NULL));

-- 组合约束：CLOSED 必须有注销时间，且余额必须清零
-- 防的错误：会员注销后账户还留着 320.00 分，这部分积分在 M19-08 的负债口径里
--          变成永远兑不出去的「僵尸负债」，负债数字虚高。
ALTER TABLE m19_points_account
    ADD CONSTRAINT ck_m19_points_account_closed
    CHECK (status <> 'CLOSED'
           OR (closed_at IS NOT NULL AND points_balance = 0 AND frozen_points = 0));

-- 组合约束：CLOSED 之后不允许再改余额（应用层 + 触发器双重保护）
ALTER TABLE m19_points_account
    ADD CONSTRAINT ck_m19_points_account_no_self_merge
    CHECK (merged_to_member_id IS NULL OR merged_to_member_id <> member_id);

ALTER TABLE m19_points_account
    ADD CONSTRAINT ck_m19_points_account_no_format
    CHECK (account_no ~ '^PA[A-Z][0-9]{6,}$');
```

**为什么这样设计**

| # | 决策 | 理由 | 不这么做会怎样 |
|---|---|---|---|
| 1 | `points_balance` 存**派生缓存**而非每次 SUM 流水 | 会员详情页 P95 要求 100ms，SUM 三年 876 万行流水不可能达标 | 纯 SUM 方案在 P-05 上必然超时，M03-03 会员详情页积分展示会拖垮整个页面 |
| 2 | 缓存列由**记账事务内**同步，而非异步更正 | 事务内 `points_balance = balance_after` 与流水插入原子提交，永远一致 | 异步更正存在窗口期，窗口内对账必报差异，且并发下更正顺序错乱会把余额改错 |
| 3 | 冗余 `total_granted` / `total_consumed` | 负债与消耗率指标要扫全表 SUM，改账时顺手累加成本为 0 | 每天 03:00 的负债统计要 SUM 876 万行，与对账任务抢资源 |
| 4 | 患者合并用 `merged_to_member_id` 重定向而非删账户 | 合并后两条积分来源都要保留可追溯 | 删掉旧账户后，合并前的那段积分永远说不清来源，客诉无法还原 |
| 5 | `version_no` 乐观锁 | 跨账户的批量操作（如兑换）用乐观锁，与行锁分工不同 | 全部用行锁在批量兑换时会产生大量等待；全部用乐观锁在单笔高频场景又频繁重试 |

### 4.5 表：`m19_points_ledger`（积分流水表，分区）

**用途：** 积分账本。**只增不改**——一旦写入即终态，任何更正一律追加反向流水（`REVERSE` / `ADJUST`），绝不修改原行。这是铁律 4 的物理落地。

**写入方：** 积分发放服务（P-03）、积分扣减服务（P-04）、过期任务、兑换服务、调整服务（全部 INSERT ONLY） **只读方：** P03 积分流水、P01 工作台、P09 对账、M19-08 积分负债统计

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键的一部分 |
| created_at | TIMESTAMP | N | CURRENT_TIMESTAMP | **分区键**，同时是主键的一部分 |

| txn_type | VARCHAR(16) | N | - | 流水类型：`GRANT` / `DEDUCT` / `EXPIRE` / `ADJUST` / `REFUND` / `REVERSE` |

| idx_m19_points_ledger_reverse | NORMAL | reverse_of_ledger_no | `WHERE reverse_of_ledger_no IS NOT NULL`，冲正追溯 |

**约束说明**

```sql

    ADD CONSTRAINT pk_m19_points_ledger
    PRIMARY KEY (id, created_at);

ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_txn_type
    CHECK (txn_type IN ('GRANT', 'DEDUCT', 'EXPIRE', 'ADJUST', 'REFUND', 'REVERSE'));

ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_direction
    CHECK (direction IN (1, -1));

-- 余额非负：任何导致余额为负的记账都是 bug
-- 防的错误：并发下两个扣减都读到余额 100、都认为够扣，各扣 80，
--          balance_after 分别写成 20 和 -60。这条约束让第二个事务直接崩掉。
ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_balance_after
    CHECK (balance_after >= 0);

-- points 绝对值必须为正，唯一的例外是 ADJUST（符号自带）
ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_points_sign
    CHECK (
        (txn_type = 'ADJUST' AND points <> 0)
        OR (txn_type <> 'ADJUST' AND points > 0)
    );

-- 方向与类型必须一致，且与 points 符号自洽
-- 防的错误：把 EXPIRE 写成正数，对账 SUM 里 EXPIRE 又被取负，
--          结果过期一次余额反而增加两次，对账永远差一个 2 倍。
ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_direction_type
    CHECK (
        (txn_type IN ('GRANT', 'REFUND') AND direction = 1 AND points > 0)
        OR (txn_type IN ('DEDUCT', 'EXPIRE', 'REVERSE') AND direction = -1 AND points > 0)
        OR (txn_type = 'ADJUST'
            AND ((points > 0 AND direction = 1) OR (points < 0 AND direction = -1)))
    );

-- 防的错误：只填了 biz_no 没填 biz_type，幂等键拼成 ":ST20261021000123:PR_OUTPATIENT_VISIT"，
--          不同业务的相同单号会互相命中，直接吞掉真实发放。
ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_idem_fields
    CHECK (
        (idempotent_key IS NULL
            AND biz_type IS NULL AND biz_no IS NULL AND rule_code IS NULL)
        OR (idempotent_key IS NOT NULL
            AND biz_type IS NOT NULL AND biz_no IS NOT NULL AND rule_code IS NOT NULL
            AND btrim(biz_type) <> ''
            AND btrim(biz_no)   <> ''
            AND btrim(rule_code) <> '')
    );

-- 组合约束：DEDUCT / GRANT / REFUND 必须有业务单据
ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_biz_no
    CHECK (txn_type NOT IN ('DEDUCT', 'GRANT', 'REFUND') OR biz_no IS NOT NULL);

-- 组合约束：REVERSE 必须指向原流水
ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_reverse_of
    CHECK (txn_type <> 'REVERSE' OR reverse_of_ledger_no IS NOT NULL);

-- 组合约束：EXPIRE 必须有批次号
ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_expire_batch
    CHECK (txn_type <> 'EXPIRE' OR expire_batch_no IS NOT NULL);

-- 组合约束：只有 GRANT / REFUND 能有到期日
ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_expire_at
    CHECK (expire_at IS NULL OR txn_type IN ('GRANT', 'REFUND'));

-- 等级与倍率快照必须非空且自洽（倍率为 0 只在 FIXED 规则下允许）
ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_level_snapshot
    CHECK (length(level_at_txn) > 0);

    CHECK (points_ratio_snapshot >= 0 AND points_ratio_snapshot <= 100);

ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_no_format
    CHECK (ledger_no ~ '^PL[0-9]{14}$');

ALTER TABLE m19_points_ledger
    ADD CONSTRAINT ck_m19_points_ledger_occurred
    CHECK (occurred_at <= created_at + INTERVAL '1 day');
```

**分区策略**

按 `created_at` 月度 RANGE 分区，**必须同时建 `DEFAULT` 分区**，在线保留 36 个月，超期分区归档到 `m19_points_ledger_archive` 后 DETACH。

```sql
CREATE TABLE m19_points_ledger (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    ledger_no VARCHAR(32) NOT NULL,
    row_no BIGINT GENERATED BY DEFAULT AS IDENTITY,
    account_id BIGINT NOT NULL,
    member_id BIGINT NOT NULL,
    patient_id BIGINT,
    txn_type VARCHAR(16) NOT NULL,
    direction SMALLINT NOT NULL,
    points NUMERIC(14,2) NOT NULL,
    balance_after NUMERIC(14,2) NOT NULL,
    level_at_txn VARCHAR(32) NOT NULL,
    points_ratio_snapshot NUMERIC(10,6) NOT NULL,
    rule_code VARCHAR(64),
    rule_version INT,
    biz_type VARCHAR(32),
    biz_no VARCHAR(64),
    idempotent_key VARCHAR(160),
    reverse_of_ledger_no VARCHAR(32),
    expire_batch_no VARCHAR(32),
    exchange_no VARCHAR(32),
    adjust_no VARCHAR(32),
    occurred_at TIMESTAMP NOT NULL,
    expire_at DATE,
    used_points NUMERIC(14,2) NOT NULL DEFAULT 0.00,
    remark VARCHAR(512),
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_by BIGINT,
    trace_id VARCHAR(64),
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- 按月分区，示例：2026 年 10 月
CREATE TABLE m19_points_ledger_p202610
    PARTITION OF m19_points_ledger
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

CREATE TABLE m19_points_ledger_p202611
    PARTITION OF m19_points_ledger
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

CREATE TABLE m19_points_ledger_p202612
    PARTITION OF m19_points_ledger
    FOR VALUES FROM ('2026-12-01') TO ('2027-01-01');

-- 【强制】DEFAULT 分区：没有它，新月份第一批写入直接报
--   "no partition of relation found for row"
CREATE TABLE m19_points_ledger_p_default
    PARTITION OF m19_points_ledger DEFAULT;

-- 【铁律 4】流水只增不改：撤销应用账号的 UPDATE / DELETE 权限
REVOKE UPDATE, DELETE ON m19_points_ledger FROM app_m19;

-- 子分区同样需要收回（PostgreSQL 权限不自动继承到已建分区）
REVOKE UPDATE, DELETE ON m19_points_ledger_p202610 FROM app_m19;
REVOKE UPDATE, DELETE ON m19_points_ledger_p202611 FROM app_m19;
REVOKE UPDATE, DELETE ON m19_points_ledger_p202612 FROM app_m19;
REVOKE UPDATE, DELETE ON m19_points_ledger_p_default FROM app_m19;

-- 兜底：即使将来有人误给了权限，触发器仍拒绝 UPDATE / DELETE
CREATE OR REPLACE FUNCTION trg_fn_m19_points_ledger_append_only()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION
        'm19_points_ledger is append-only: use a REVERSE or ADJUST ledger row instead of % ', TG_OP;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m19_points_ledger_no_update
    BEFORE UPDATE OR DELETE ON m19_points_ledger
    FOR EACH ROW EXECUTE FUNCTION trg_fn_m19_points_ledger_append_only();
```

**为什么这样设计**

| # | 决策 | 理由 | 不这么做会怎样 |
|---|---|---|---|
| 1 | `REVOKE UPDATE, DELETE` + 触发器**双保险** | REVOKE 只约束应用账号，运维误用超级用户仍能改；触发器拦住所有角色 | 只有 REVOKE 时，一次 `psql` 的 UPDATE 就能改掉历史流水，且无痕迹 |
| 2 | 表**没有** `updated_at` / `is_deleted` | 字段本身存在就会诱导人去写它 | 留了 `is_deleted` 后，有人会把冲正实现成 `UPDATE ... SET is_deleted = TRUE`，流水与余额立刻脱钩 |
| 3 | 幂等键用拼接列 `idempotent_key` 而非三列联合唯一 | 三个字段中 `rule_code` 可为 NULL，而 PostgreSQL 唯一索引认为 NULL 互不相等，三元组唯一会失效 | 用三列联合唯一时，`rule_code = NULL` 的流水可以无限重复插入，重放会重复发放 |
| 4 | `direction` 冗余列 + CHECK 与 `txn_type` 自洽 | 对账 SUM 只写 `direction * points` 一行，不写 6 个 CASE 分支 | 对账 SQL 用 CASE 时，`ADJUST` 的符号靠 `ELSE` 兜底，一旦新增类型就静默算错 |
| 5 | `level_at_txn` + `points_ratio_snapshot` 双快照 | 等级名与倍率值都落库，M03-03 改名或 M19 改倍率都不影响历史 | 只存 `level_code` 时，倍率要回查当前规则版本，升级后去年消费被按新倍率解释 |
| 6 | `used_points` 直接记在发放行上 | 过期与扣减的 FIFO 必须知道「这条发放还剩多少」，否则每次都要重算 | 每次扣减都 SUM 历史消耗，扣一笔要扫该会员全部流水，越用越慢 |

**对账口径（必须与本表定义一致）**

```sql
-- 每日 03:00 对账：账户派生余额 vs 流水汇总
SELECT a.member_id,
       a.points_balance,
       COALESCE(SUM(l.direction * l.points), 0) AS ledger_sum
FROM m19_points_account a
LEFT JOIN m19_points_ledger l ON l.account_id = a.id
WHERE a.is_deleted = FALSE
GROUP BY a.member_id, a.points_balance
HAVING a.points_balance <> COALESCE(SUM(l.direction * l.points), 0);
```

> **`ADJUST` 的符号由 `points` 自带正负**：`direction` 列在 `ADJUST` 行上直接等于 `sign(points)`，所以 `direction * points` 天然就是带符号增量。这个细节如果不写清，正负调整混算（例如对 `ADJUST` 统一按 `direction = 1` 处理），新增那一刻余额对得上，下一次负向调整就对不上，而差异值恰好是一个偶数倍，极难定位。

**约束说明**

```sql

    ADD CONSTRAINT ck_m19_points_expire_status
    CHECK (status IN ('WAITING', 'REMINDED', 'EXPIRED', 'CANCELLED'));

ALTER TABLE m19_points_expire_record
    ADD CONSTRAINT ck_m19_points_expire_parts
    CHECK (granted_points > 0 AND used_points >= 0 AND expired_points >= 0);

-- 防的错误：只按「发放数」过期而不减去已消耗，同一批积分被消耗后再过期一次，

    ADD CONSTRAINT ck_m19_points_expire_math
    CHECK (used_points <= granted_points
           AND expired_points = granted_points - used_points);

    ADD CONSTRAINT ck_m19_points_expire_zero
    CHECK (expired_points > 0 OR status IN ('WAITING', 'REMINDED', 'CANCELLED'));

    CHECK (remind_suppressed = FALSE OR remind_suppress_reason IS NOT NULL);

    ADD CONSTRAINT ck_m19_points_expire_reason
    CHECK (remind_suppress_reason IS NULL
           OR remind_suppress_reason IN ('UNSUBSCRIBED', 'BLACKLIST', 'QUIET_HOURS',
                                          'FREQ_LIMIT', 'NO_CONTACT'));

    ADD CONSTRAINT ck_m19_points_expire_batch_format
    CHECK (expire_batch_no ~ '^EX[0-9]{12}$');
```

**FIFO 扣减的正确性论证**

| 步骤 | 操作 | 为什么必须这样 |
|---|---|---|
| 1 | 取该账户所有 `expire_at IS NOT NULL` 且 `used_points < points` 的发放流水，按 `occurred_at ASC, ledger_no ASC` 排序 | 先发的先到期，`ledger_no` 兜底保证同一秒内发放顺序确定 |
| 2 | 从左到右依次扣减，直到本次扣减额分配完 | 只有 FIFO 能保证「先过期的先被用掉」，否则会留下即将到期的积分白白过期 |
| 3 | 每次扣减在 `m19_points_ledger.used_points` 上累加，**这是唯一允许 UPDATE 的流水字段** | 该字段是批次台账而非账务事实；账务事实由 `DEDUCT` 流水行承载 |
| 4 | 若需过期，`expired_points = granted_points - used_points`，写一条 `EXPIRE` 流水 | `EXPIRE` 只过期「尚未用掉」的部分 |

> **`used_points` 的例外必须明说**：本表（`m19_points_ledger`）已 `REVOKE UPDATE`，但批次台账需要累加。落地做法是把 `used_points` 的累加**移到一个 SECURITY DEFINER 函数** `fn_m19_points_consume_batch(p_account_id, p_points)` 中执行，应用账号对该函数有 EXECUTE 权限但不直接持有 UPDATE 权限。这样既保住「应用不能随意改流水」，又满足 FIFO 台账的更新需求。

```sql
CREATE OR REPLACE FUNCTION fn_m19_points_consume_batch(
    p_account_id BIGINT,
    p_points NUMERIC
) RETURNS NUMERIC AS $$
DECLARE
    v_remain NUMERIC := p_points;
    v_row RECORD;
    v_take NUMERIC;
BEGIN
    FOR v_row IN
        SELECT id, created_at, ledger_no, points - used_points AS available
        FROM m19_points_ledger
        WHERE account_id = p_account_id
          AND expire_at IS NOT NULL
          AND used_points < points
        ORDER BY occurred_at ASC, ledger_no ASC
        FOR UPDATE
    LOOP
        EXIT WHEN v_remain <= 0;
        v_take := LEAST(v_remain, v_row.available);
        UPDATE m19_points_ledger
           SET used_points = used_points + v_take
         WHERE id = v_row.id AND created_at = v_row.created_at;
        v_remain := v_remain - v_take;
    END LOOP;
    RETURN p_points - v_remain;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

GRANT EXECUTE ON FUNCTION fn_m19_points_consume_batch(BIGINT, NUMERIC) TO app_m19;
```

**为什么「返还只能追加 REVERSE 流水」**

| 做法 | 结果 |
|---|---|
| 失败时 `UPDATE m19_points_ledger SET is_reversed = TRUE` | 流派生在「余额」和「流水」之间断链，此后每一次对账都差这一笔，且无法看出它曾发生过 |
| 失败时删除原扣减流水 | 删除是只增表禁止的动作；即使能删，扣减发生过的痕迹也没了，客诉无法还原 |
| **追加 `REVERSE`，指向 `reverse_of_ledger_no`** | 扣减与返还两条都在，`balance_after` 前后可对，「什么时候扣的、什么时候退的」一目了然 |

**对账 SQL（每日 03:00 执行）**

```sql
-- ① 逐账户对账：账户派生余额 vs 流水汇总
INSERT INTO m19_points_reconcile (
    reconcile_no, biz_date, account_id, member_id,
    account_balance, ledger_sum, diff_points, check_scope, handle_status)
SELECT 'RC' || to_char(CURRENT_DATE, 'YYYYMMDD') || lpad(row_number()::text, 4, '0'),
       CURRENT_DATE,
       b.account_id,
       b.member_id,
       b.account_balance,
       b.ledger_sum,
       b.account_balance - b.ledger_sum,
       'ACCOUNT',
       'OPEN'
FROM (
    SELECT a.id AS account_id,
           a.member_id,
           a.points_balance AS account_balance,
           COALESCE(SUM(l.direction * l.points), 0) AS ledger_sum
    FROM m19_points_account a
    LEFT JOIN m19_points_ledger l ON l.account_id = a.id
    WHERE a.is_deleted = FALSE
    GROUP BY a.id, a.member_id, a.points_balance
) b
WHERE b.account_balance <> b.ledger_sum;

-- ② 全量总额对账：用于回答「明天最多要兑付多少现金」
--    兑付比例 0.01 元/分 由 m19_points_config 提供，此处以常量示例
SELECT SUM(points_balance)                        AS total_points,
       SUM(points_balance) * 0.01                 AS liability_amount
FROM m19_points_account
WHERE is_deleted = FALSE AND points_balance > 0;
```

### 4.14 Pydantic Schema 定义

落盘路径 `app/schemas/m19/points.py`。全部使用 Pydantic V2 语法，`from_attributes=True` 以支持 ORM 直接序列化；金额与积分一律 `Decimal`，**在入口处把 `float` 转成 `str` 再解析**，避免二进制浮点误差在积分上放大。

```python
"""M19-04 会员积分与成长值 Pydantic V2 Schema。"""

from __future__ import annotations

from datetime import date, datetime
from decimal import Decimal
from typing import Any, Generic, Literal, TypeVar

from pydantic import BaseModel, ConfigDict, Field, field_validator, model_validator

T = TypeVar("T")

PointsAmount = Decimal
Rate = Decimal


class M19PointsBaseSchema(BaseModel):
    """M19-04 所有 Schema 的公共基类。"""

    model_config = ConfigDict(
        from_attributes=True,
        extra="forbid",
        str_strip_whitespace=True,
        validate_assignment=True,
    )

    @field_validator("*", mode="before")
    @classmethod
    def _float_to_str(cls, v: Any) -> Any:
        """防止二进制浮点误差：33.85 这类值不得超过 2 位小数进入 Decimal。"""
        if isinstance(v, float):
            return format(v, ".6f").rstrip("0").rstrip(".")
        return v

def signed_points(txn_type: str, points: Decimal) -> Decimal:
    """把流水换算成带符号增量，供对账使用。

    GRANT / REFUND 为正；DEDUCT / EXPIRE / REVERSE 为负；
    ADJUST 的符号由 points 自带正负，此处原样返回。
    """
    if txn_type in POSITIVE_TXN_TYPES:
        return abs(points)
    if txn_type in NEGATIVE_TXN_TYPES:
        return -abs(points)
    if txn_type == "ADJUST":
        return points
    raise ValueError("未知的积分流水类型: %s" % txn_type)
```

## 附录 A 积分账本只增不改的物理保证清单

积分账本是本子模块的「钱」，任何一处可写权限的疏漏都会导致余额无法追溯。本附录把保证手段按「作用层级」列全，便于 DBA 部署后逐项核对。

| # | 保证层级 | 具体手段 | 作用对象 | 拦住的具体错误 |
| --- | --- | --- | --- | --- |
| 1 | 权限层 | `REVOKE UPDATE, DELETE ON ... FROM app_m19` | 两张流水表及各子分区 | 应用代码误写 `UPDATE m19_points_ledger SET points = 32.86` |
| 2 | 触发器层 | `trg_fn_m19_points_ledger_append_only()` `BEFORE UPDATE OR DELETE` 抛异常 | 两张流水表 | 以表属主身份连接的运维脚本绕过权限层 |
| 3 | 约束层 | `CHECK (balance_after >= 0)` | 两张流水表 | 先扣后校验实现里出现的负余额落库 |
| 4 | 约束层 | `UNIQUE (idempotent_key, created_at)` | `m19_points_ledger` | 同一业务重复发放产生两条 GRANT |
| 5 | 约束层 | `CHECK (txn_type IN ('GRANT','REFUND') OR biz_no IS NOT NULL)` | `m19_points_ledger` | 无业务单据的凭空发放无法追溯来源 |
| 6 | 约束层 | `CHECK (source = 'ADJUST' OR growth_delta > 0)` | `m19_points_growth_ledger` | 滚动 12 个月口径下成长值被扣减导致掉级 |
| 7 | 派生层 | 账户余额是派生值，每日 03:00 对账 | `m19_points_account` | 账户表余额与流水总额长期漂移而无人发现 |
| 8 | 快照层 | `level_at_txn` 与 `points_ratio_snapshot` 落库；倍率精度 `NUMERIC(10,6)` 定点，`CHECK (points_ratio_snapshot >= 0 AND points_ratio_snapshot <= 100)` | `m19_points_ledger` | 用户升级后被按新倍率重算历史发放；倍率若用浮点，100 笔累加后会出现 0.30000000000000004 这类尾差，32.85 与 32.86 的到账通知分歧正是从这里来的 |
| 9 | 审批层 | `approve_by <> apply_by`、`adjust_reason` 长度下限 | `m19_points_adjust` | 管理员自审自批大额调账 |
| 10 | 账务层 | 兑换失败必须追加 REVERSE，`reverse_ledger_no` 非空 | `m19_points_exchange` | 兑换失败后积分被吞且无痕迹 |
