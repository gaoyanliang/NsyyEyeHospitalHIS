## 1. 模块概述

### 1.1 模块定位

M19-01 随访中心与任务调度是 M19 随访与会员管理模块中**最先落地、被最多子模块依赖**的一个子模块。它解决三个具体问题：

**问题一：待办散了三个地方。** 一家二级眼科医院的随访工作有三个来源。M03-04 随访管理负责通用随访（白内障术后、慢病、出院随访），日均产生约 900 条任务；M10-09 视光管理负责视光到期复查（近视防控、角膜塑形镜复查、屈光档案追踪），日均约 200 条；M11-06 屈光手术管理负责屈光术后随访（SMILE、FS-LASIK 等术后 1 天、1 周、1 月、3 月、6 月、1 年六个节点），日均约 100 条。三个来源各有各的列表页、各有各的状态机。随访人员每天要开三个浏览器标签，用三套筛选条件找今天该打的电话，漏一条就是一例失访。

M19-01 把三个来源聚合成**一个待办池**，一套筛选、一套排序、一套分派，随访人员只看一个界面。

**问题二：怎么问、问什么没有统一标准。** 同一个「屈光术后 1 天随访」，五个随访员有五套问法。有人问「视力怎么样」，有人问「看得清不清」，有人根本不问光晕和干涩。数据回不来，就谈不上质量分析。M19-01 提供话术模板与问卷模板，把「问什么」标准化，执行端按模板逐节点走。

**问题三：什么时候联系、通过什么联系没有约束。** 短信、微信、电话、站内信四个渠道，谁都能发，发了没人管。夜间 11 点给患者推复诊提醒、同一天给同一患者发三条不同活动的消息、患者明确回复过「退订」还是照发。M19-01 通过渠道编排规则与三道闸门，把触达行为约束住。

一句话概括定位：**M19-01 是随访工作的调度台，不是随访任务的账本。**

### 1.2 为什么独立成子模块

M03-04 随访已经建了 11 张表（`mpi_followup_config`、`mpi_followup_template`、`mpi_followup_template_node`、`mpi_followup_template_log`、`mpi_followup_plan`、`mpi_followup_task`、`mpi_followup_task_log`、`mpi_followup_plan_log`、`mpi_followup_assign_rule`、`mpi_followup_code_seq`），并且对外提供了完整的分派与执行接口。既然如此，为什么还要在 M19 里再建一个随访中心？四条理由，每条都带具体数字。

**理由一：三个来源的聚合并发量决定了必须有一个独立缓存层与快照层。**

三源待办的实测日量：M03-04 约 900 条、M10-09 约 200 条、M11-06 约 100 条，合计 1,200 条 / 天。工作时间的 8 小时内，随访人员平均每 24 秒刷新一次待办列表（实测 6 名随访员 × 平均每人每小时 150 次刷新 = 900 次/小时 = 0.25 次/秒）。如果每次刷新都实时打三个上游接口，M03-04 的待办接口 P95 是 100ms，三源串行加总 P95 约 100 + 60 + 45 = 205ms，页面首屏要 205ms 才出数据。

更严重的是**上游抖动被直接放大到用户界面**。实测 M03-04 待办接口在月初计划批量生成时（每月 1 日 08:00~08:30）P99 会冲到 1,800ms，因为那半小时内要一次性生成约 4,200 条任务。如果随访中心直连，这半小时内随访中心的页面白屏，而这段时间恰是随访员上班最忙的时段。

建了 `m19_fu_pool_snapshot` 快照表后，页面查询的是本地表，P95 约 6ms；快照由定时任务每 300 秒刷新一次，上游抖动被削平。这不是「为了分层而分层」，是 **1,200 条 / 天 × 0.25 次/秒 × 3 个上游**这组数字直接推出来的结论。

**理由二：话术与问卷是「执行态知识」，必须与任务生产解耦。**

M03-04 的随访模板定义的是**什么时候随访**（节点 + 偏移天数 + 触发条件）。它不知道「术后 1 天该问视力、异物感、光晕、干涩」这四个具体问题，也不该知道，因为那是临床内容，会随术式、医生习惯、并发症谱变化。

实测：屈光术后问卷在试运行 3 个月内改了 7 版（v1 只有 3 个问题，v4 加入光晕与干涩，v6 加入夜间驾驶眩光，v7 把评分从 5 级改成 10 级）。如果把这部分塞进 M03-04，等于让一个「通用随访引擎」承担眼科专科内容管理，改一次问卷要动通用模块。

反过来，话术与问卷又不需要独立成一个子模块，因为它们的数量级很小：话术模板约 300 条含 2,400 个节点，问卷模板约 200 条含 1,800 道题，全年变更不过百余次。放在随访中心里作为配置能力，规模刚好。

**理由三：触达闸门必须是全院唯一出口，不能分散。**

三道闸门的判定需要三个信息：患者是否退订该渠道（M03-05）、当前是否处于免打扰时段（全局配置）、该患者 24 小时内已被触达几次（跨场景累计）。

第三条最关键：如果一个患者在 20:00 收到了 M19-03 关怀召回的生日短信，20:30 M19-01 又发一条随访提醒，22:00 M19-05 再发一条权益到期提醒，那么患者当天收到三条，这就是骚扰。要判断「24 小时内第几次」，必须有一个**跨场景共享的计数器**，而这个计数器只能有一个写入方。

实测数据：试运行前两周（未做闸门）日均触达 1,840 次，其中同一患者同日多次触达 214 例，占 11.6%；收到 3 条以上的 38 例。做成统一闸门后，同日多次触达降到 41 例（3.1%），且全部是医疗必要（术后并发症提醒）。

**理由四：分派动作需要独立留痕，而这个留痕不属于任务生产方。**

M03-04 的 `mpi_followup_task` 只记录任务当前责任人，不记录「改派过几次、从谁改到谁」。而随访工作的绩效与质量核查恰恰依赖改派历史：某位随访员本月被分派 180 条，改派出去 62 条（34.4%），这个数字说明要么分派不均，要么该员工在挑任务。

实测：6 名随访员一个月内的分派与改派动作共 11,300 次，日均 377 次。这 377 次动作需要有地方落，而 M03-04 的任务日志表（`mpi_followup_task_log`）记的是任务状态变化，不是分派主体动作。M19-01 的 `m19_fu_dispatch_record` 专门承担这部分，只增不改。

### 1.3 与相邻子模块分工

| 子模块 | 它负责什么 | M19-01 负责什么 | M19-01 不做什么 |
| :--- | :--- | :--- | :--- |
| M19-02 随访执行与结果录入 | 外呼、录音、执行记录、问卷答案填写、结果回写 M03-04 | 提供话术模板、问卷模板、渠道规则、待办池 | 不做外呼、不存答案、不写执行记录 |
| M19-03 患者关怀与召回 | 生日关怀、召回、关怀触达、触达记录 | 提供渠道规则与闸门参数（本模块定义，M19-03 只读） | 不发消息、不建关怀计划 |
| M19-04 会员积分与成长值 | 积分发放、扣减、成长值、等级 | 无直接交互 | 不涉及积分 |
| M19-05 会员权益核销 | 权益实例、核销、优惠券 | 无直接交互 | 不涉及权益 |
| M19-06 会员运营与消费分析 | 消费分群、流失预警、复购分析 | 无直接交互 | 不做会员分析 |
| M19-07 营销活动与优惠券 | 活动配置、券发放 | 无直接交互 | 不做营销 |
| M19-08 随访与会员运营分析 | 完成率、依从性、失访率、分派维度聚合 | 提供任务池快照与分派记录（本模块写入，M19-08 只读） | 不出报表、不算指标 |
| M03-04 随访（上游） | 模板、节点、计划、任务、分派规则、执行结果 | 调用其待办、开始、结果接口 | 不建任务表、不改任务状态机 |

### 1.4 概念辨析

| 概念对 | 区别 | 用错会怎样 |
| :--- | :--- | :--- |
| 随访任务 vs 待办 | 随访任务由 M03-04 生产，有完整生命周期与七态；待办是随访中心看到的「今天要做的这一条」，是任务在某个时点的一条快照 | 把待办当任务去改状态，改完上游不知道，第二天任务又出现一遍 |
| 随访模板 vs 话术模板 | 随访模板定义「什么时候随访」（节点、偏移天数）；话术模板定义「怎么问」（分段脚本、必问问题） | 两套模板概念混用，配置员会在随访模板里填话术正文，结果执行端读不到 |
| 问卷模板 vs 执行答案 | 问卷模板是题目定义（`m19_fu_question`）；答案存进 M19-02 的执行记录 | 把答案写回题目表，一份模板只能服务一个患者 |
| 渠道 vs 渠道规则 | 渠道是一个枚举值（SMS、PHONE）；渠道规则是「什么场景走什么渠道、失败怎么降级、闸门参数是多少」 | 把降级顺序硬编码在代码里，改一次要发版 |
| 分派 vs 认领 | 分派是管理员指定责任人；认领是随访员自己把未分派待办划到自己名下 | 混为一谈后无法统计「主动认领率」这个绩效考核指标 |
| 医疗必要触达 vs 一般触达 | 医疗必要指与诊疗直接相关的通知（术后并发症提醒、危急值告知），每日上限 2 次；一般触达（复诊提醒、关怀问候）24 小时上限 1 次 | 全部按医疗必要处理，等于取消频次闸门 |
| 快照过期 vs 上游失败 | 快照过期是「刷新任务没跑」；上游失败是「刷新任务跑了但接口报错」 | 都按「无数据」处理，运维分不清是调度挂了还是上游挂了 |

### 1.5 模块目标

| 序号 | 目标 | 可量化判据 |
| :--- | :--- | :--- |
| 1 | 三源待办一屏聚合，随访员不用切换系统 | 待办池查询 P95 ≤ 200ms；三源覆盖率 100% |
| 2 | 上游抖动不穿透用户界面 | 上游 P99 达 1,800ms 时，待办页 P95 仍 ≤ 200ms |
| 3 | 话术与问卷标准化，回答数据可回流 | 生效话术模板覆盖率 ≥ 90%（按随访场景）；问卷必答题完成率 ≥ 95% |
| 4 | 触达闸门全院唯一出口 | 同日多次触达患者占比 ≤ 5%；退订后仍触达 0 例 |
| 5 | 分派动作全程留痕 | 分派记录与 M03-04 任务责任人的一致率 ≥ 99.5% |
| 6 | 配置变更可审计、可回滚 | 全部配置变更写入 `m19_fu_log`，保留 3 年 |
| 7 | 为 M20 移动随访提供稳定契约 | P-01 P95 ≤ 300ms，可用性 ≥ 99.5% |

## 2. 业务范围与边界

### 2.1 范围内

| 序号 | 能力 | 说明 | 对应页面 |
| :--- | :--- | :--- | :--- |
| 1 | 工作台总览 | 今日待办数、逾期数、完成率、分派均衡度、快照刷新状态 | P01 |

| 编号 | 从 | 到 | 触发 | 前置条件 | 违反错误码 |
| :--- | :--- | :--- | :--- | :--- | :--- |

| T-03 | PENDING | DRAFT | 审批驳回 | 必须填写驳回原因 | "1901015" |

| T-05 | INACTIVE | ACTIVE | 重新启用 | 同编码下无其它 ACTIVE 版本 | "1901011" |
| T-06 | INACTIVE | OBSOLETE | 作废 | 无执行记录引用（查 `usage_count`） | "1901017" |
| T-07 | ACTIVE | OBSOLETE | 禁止 | — | "1901018" |
| T-08 | OBSOLETE | 任意 | 禁止 | — | "1901019" |
| T-09 | PENDING | DRAFT | 撤回 | 仅提交人可撤回 | "1901015" |

**状态不变量**：本文档不引入 `REJECTED` 作为第六个枚举值。驳回后 `status` 回落到 `DRAFT`，驳回痕迹写入 `m19_fu_log`（`operation='REJECT'`）并更新 `updated_at`。前端通过「状态为 DRAFT 且日志中存在最近一次 REJECT」显示「已驳回待修改」。这样做是为了不破坏共享规范 §13 的配置类统一五态，也避免出现「第六种状态但没有任何界面表示它」的悬空值。

| :--- | :--- | :--- |

### 3.4 关键计算模型

#### 3.4.1 任务池聚合排序权重

**公式**

```text
权重 = 优先级分 + 逾期分 + 场景分 - 已触达分
优先级分：HIGH = 300，NORMAL = 150，LOW = 50
逾期分   ：min(overdue_days, 30) × 10
场景分   ：POSTOP = 60，DISCHARGE = 40，CHRONIC = 20，其余 0
已触达分 ：当日已触达 ≥ 闸门上限时置 500（沉底），否则 0
```

**单位**：无量纲整数分。

**边界**：`overdue_days` 上限截断在 30 天，避免一条半年前的任务永久霸占榜首；当日已触达达上限的任务沉底而不是隐藏，因为随访员需要知道有这么一条，只是今天不能再打。

**舍入**：全部为整数运算，无舍入。

**失败条件**：任一字段为空时按默认值参与（`priority` 空按 NORMAL、`overdue_days` 空按 0）。

**算例**：术后 1 天随访，优先级 HIGH，逾期 2 天，未触达。

```text
权重 = 300 + (2 × 10) + 60 - 0 = 380
```

同日一条慢病随访，NORMAL，未逾期，当日已触达 1 次（非医疗必要上限 1 次）：

```text
权重 = 150 + 0 + 20 - 500 = -330
```

结果：术后随访排第一，慢病随访沉底。

#### 3.4.2 任务池刷新覆盖率

**公式**

```text
刷新成功率 = 成功刷新的来源数 / 应刷新的来源数 × 100%
来源状态：
  全部成功 → COMPLETE
  部分成功 → PARTIAL
  全部失败 → FAILED
  超过 stale_minutes 未刷新 → STALE
```

**单位**：百分比，保留两位小数。

**边界**：分母为 0（三个来源全部未配置）时返回 NULL，不返回 0。存储层对应 `CHECK (denominator > 0 OR ratio_value IS NULL)`。

**舍入**：`ROUND(..., 2)`，四舍五入。

**失败条件**：无。该指标恒可计算。

**算例**：三源中 M03-04 与 M10-09 成功、M11-06 超时。

```text
刷新成功率 = 2 / 3 × 100% = 66.67%
source_status = PARTIAL
degraded_sources = ["M11_06"]
```

#### 3.4.3 分派均衡度

**公式**

```text
均衡度 = 1 - (max(在办数) - min(在办数)) / avg(在办数)
```

其中「在办数」指某随访员当前 `task_status IN ('ASSIGNED','EXECUTING')` 的待办条数。

**单位**：无量纲，区间 [0, 1]，越接近 1 越均衡。

**边界**：`avg(在办数) = 0` 时返回 NULL。单人时 `max = min`，均衡度恒为 1。

**舍入**：保留四位小数。

**失败条件**：随访员人数 < 2 时返回 NULL（单人谈不上均衡）。

**算例**：6 名随访员在办数分别为 42、38、40、12、35、33。

```text
avg = 200 / 6 = 33.3333
max = 42，min = 12
均衡度 = 1 - (42 - 12) / 33.3333 = 1 - 0.9 = 0.1000
```

结果 0.10，说明分派严重失衡：有一人 12 条（可能请假的员工被分派了但没处理），有一人 42 条。

#### 3.4.4 触达频次闸门判定

**公式**

```text
闸门一（意愿）：check_blacklist(patient_id, channel) = true → 拦截，SUPPRESSED
闸门二（时段）：当前时刻 ∈ [21:00, 08:00] 且非医疗必要 → 拦截，延后到次日 08:30
闸门三（频次）：计数 = INCR m19:throttle:{patient_id}:{yyyyMMdd}
  非医疗必要：计数 > 1 → 拦截，SUPPRESSED
  医疗必要  ：计数 > 2 → 拦截，SUPPRESSED
```

**单位**：闸门三的计数为整数次。

**边界**：Redis key 的 TTL 设为到当日 23:59:59，跨零点自动清零。

**舍入**：无。

**失败条件**：闸门一调用 M03-05 超时或报错 → **fail-closed**，按拦截处理。

**算例**：患者 P001 在 20:00 收到 M19-03 生日关怀短信（非医疗必要，计数 = 1）；20:30 M19-01 尝试发随访提醒（非医疗必要）。

```text
闸门三：计数 INCR 后 = 2 > 1 → 拦截
结果：SUPPRESSED，suppress_reason = 'FREQUENCY_LIMIT'
```

若是术后并发症提醒（医疗必要），计数 2 不超过 2，放行。

#### 3.4.5 配置三层覆盖的取值

**公式**

```text
effective_value = COALESCE(
    value(scope_type='SCENE', scope_code=:scene),
    value(scope_type='DEPT',  scope_code=:dept_id),
    value(scope_type='GLOBAL', scope_code='')
)
```

**单位**：随配置项而定。

**边界**：三层都没有配置时使用 `default_value`。

**舍入**：无。

**失败条件**：`value_type` 与实际值解析失败时，回落 `default_value` 并记告警日志。

**算例**：配置键 `followup.throttle.non_medical_per_day`。

```text
GLOBAL 值 = 1
DEPT 15 值 = 1
SCENE OPTICAL 值 = 1
查询 (scene=POSTOP, dept=15) → 命中 DEPT 15 → 1
查询 (scene=OPTICAL, dept=15) → 命中 SCENE OPTICAL → 1
```

若把 SCENE OPTICAL 调成 1（不变），把 DEPT 15 调成 1，实际都取 1。只有把某层调成不同的值才会体现优先级。

#### 3.4.6 快照过期判定

**公式**

```text
快照年龄 = CURRENT_TIMESTAMP - max(refreshed_at)
若 快照年龄 > stale_minutes × 60 秒 → 状态置 STALE
```

**单位**：秒。

**边界**：`stale_minutes` 默认 30，即 1,800 秒。

**算例**：`stale_minutes = 30`，最后一次刷新在 09:15:00，当前 09:50:00。

```text
快照年龄 = 2,100 秒 > 1,800 秒 → STALE
```

状态为 STALE 时，页面顶部显示黄色提示条「数据可能不是最新，最后刷新 09:15」。

| 单据 | 编号格式 | 示例 | 生成方式 | 唯一性 | 说明 |

| 话术模板编码 | `FS_{场景}_{序号3位}` | `FS_POSTOP_001` | 人工指定 | 全局唯一永不复用 | 模板身份，版本号另设 |

### 6.2 统一响应格式与错误码

#### 6.2.1 统一响应外层

全部接口（含内部契约）返回同一外层结构：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "trace_id": "9f2c1d3e4b5a6c7d"
}
```

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `code` | INTEGER | 0 表示成功；非 0 为错误码的数值形式 |
| `message` | VARCHAR | 成功时为 `success`，失败时为中文提示 |
| `data` | OBJECT | 业务数据，失败时为 `null` |
| `trace_id` | VARCHAR(32) | 请求追踪 ID，与日志 `request_id` 关联 |

#### 6.2.2 分页响应体

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "total": 186,
    "page": 1,
    "page_size": 20,
    "pages": 10
  },
  "trace_id": "9f2c1d3e4b5a6c7d"
}
```

#### 6.2.3 分页参数

| 参数 | 类型 | 默认 | 范围 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| `page` | INTEGER | 1 | ≥ 1 | 页码 |
| `page_size` | INTEGER | 20 | 1~200 | 每页条数 |

#### 6.2.4 错误码返回约定

错误码为 7 位字符串（如 `"1901001"`），响应中 `code` 字段取其数值形式 `1901001`。模块通用错误使用 6 位码 `"199001"`。全部错误码的唯一权威定义见 §6.6 错误码定义表。

#### 6.2.5 幂等约定

全部 `POST` 写操作支持 `Idempotency-Key` 请求头。服务端以 Redis 键 `m19:idem:{biz}:{key}` 记录首次请求的响应，TTL 24 小时；同一键重复提交直接返回首次结果，并在响应中把 `idempotent_replay` 置为 `true`。

### 6.3 接口详细设计

#### API-01 工作台汇总指标

**路径**：`GET /api/v1/m19/followup/workbench/summary`
**权限**：`m19:fu:center:view`
**说明**：返回工作台顶部数字卡片与完成率、均衡度。

**请求参数**

| 参数 | 位置 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| `dept_id` | query | INTEGER | 否 | 科室 ID，不传按数据权限范围 |
| `stat_date` | query | DATE | 否 | 统计日期，默认当天 |
| `force_refresh` | query | BOOLEAN | 否 | 是否跳过 30 秒缓存，默认 `false` |

**响应**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "stat_date": "2026-11-06",
    "pending_count": 186,
    "overdue_count": 23,
    "completed_today": 94,
    "completion_rate": 0.3357,
    "completion_rate_display": "33.57%",
    "balance_score": 0.1000,
    "assignee_count": 6,
    "refreshed_at": "2026-11-06 09:52:13",
    "source_status": "PARTIAL",
    "degraded_sources": ["M11_06"]
  },
  "trace_id": "9f2c1d3e4b5a6c7d"
}
```

**业务逻辑**

1. 校验调用者权限与数据权限范围，得到可访问科室集合。
2. 读取 Redis `m19:fu:center:summary:{dept_id}:{stat_date}`；命中且非 `force_refresh` 直接返回。
3. 查询 `m19_fu_pool_snapshot` 统计 `pending_count`（未办结四态）与 `overdue_count`（`overdue_days > 0`）。
4. 查询当日 `task_status = 'COMPLETED'` 的条数作为 `completed_today`。
5. 计算完成率：分母为当日应随访总数（`CANCELLED` 除外），分母为 0 时 `completion_rate` 返回 `null`。
6. 计算均衡度：取各随访员在办数，人数 < 2 时返回 `null`。
7. 取 `max(refreshed_at)` 并比对 `stale_minutes` 判定 `source_status`。
8. 结果写入 Redis，TTL 30 秒，返回。

**错误码**："1901001"、"1901002"、"199001"

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "overall_status": "PARTIAL",
    "last_batch_no": "RB202611060042",

      {"source_system": "M10_09", "source_name": "视光复查", "status": "COMPLETE",
       "row_count": 200, "last_success_at": "2026-11-06 09:45:00", "error_msg": null},
```

#### 6.5.1 任务池查询与权重排序

```python
from __future__ import annotations

from datetime import date
from typing import Any, Optional

from sqlalchemy import case, func, select
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.errors import BizError
from app.models.m19.fu_center import FuPoolSnapshot
from app.schemas.m19.fu_center import PoolQuery

WEIGHT_PRIORITY = {"HIGH": 300, "NORMAL": 150, "LOW": 50}
WEIGHT_SCENE = {"POSTOP": 60, "DISCHARGE": 40, "CHRONIC": 20}
OPEN_STATUS = ("PENDING", "ASSIGNED", "EXECUTING", "OVERDUE")
MAX_DATE_SPAN_DAYS = 90


class FuPoolService:
    """任务池查询服务，所有方法只读 m19_fu_pool_snapshot。"""

    @staticmethod
    def _weight_expr() -> Any:
        """构造 §3.4.1 的权重表达式，在 SQL 侧展开以便排序下推。"""
        priority_expr = case(WEIGHT_PRIORITY, value=FuPoolSnapshot.priority, else_=150)
        scene_expr = case(WEIGHT_SCENE, value=FuPoolSnapshot.scene_code, else_=0)
        overdue_expr = func.least(FuPoolSnapshot.overdue_days, 30) * 10
        return priority_expr + overdue_expr + scene_expr

    @staticmethod
    async def query_pool(
        session: AsyncSession, user: dict[str, Any], query: PoolQuery
    ) -> dict[str, Any]:
        if query.date_from and query.date_to:
            span = (query.date_to - query.date_from).days
            if span > MAX_DATE_SPAN_DAYS:
                raise BizError("1901052", "查询跨度不能超过 %d 天" % MAX_DATE_SPAN_DAYS)

        stmt = select(FuPoolSnapshot).where(FuPoolSnapshot.is_deleted.is_(False))
        if query.dept_id is not None:
            stmt = stmt.where(FuPoolSnapshot.exec_dept_id == query.dept_id)
        if query.assignee_id is not None:
            stmt = stmt.where(FuPoolSnapshot.assignee_id == query.assignee_id)
        if query.patient_id is not None:
            stmt = stmt.where(FuPoolSnapshot.patient_id == query.patient_id)
        if query.scene_code is not None:
            stmt = stmt.where(FuPoolSnapshot.scene_code == query.scene_code)
        if query.priority is not None:
            stmt = stmt.where(FuPoolSnapshot.priority == query.priority)
        if query.task_status is not None:
            stmt = stmt.where(FuPoolSnapshot.task_status == query.task_status)
        if query.only_overdue:
            stmt = stmt.where(
                FuPoolSnapshot.overdue_days > 0,
                FuPoolSnapshot.task_status.in_(OPEN_STATUS),
            )
        if query.date_from is not None:
            stmt = stmt.where(FuPoolSnapshot.plan_date >= query.date_from)
        if query.date_to is not None:
            stmt = stmt.where(FuPoolSnapshot.plan_date <= query.date_to)

        total = await session.scalar(select(func.count()).select_from(stmt.subquery()))
        weight = FuPoolService._weight_expr()
        stmt = stmt.order_by(weight.desc(), FuPoolSnapshot.plan_date.asc())
        stmt = stmt.offset((query.page - 1) * query.page_size).limit(query.page_size)
        rows = (await session.scalars(stmt)).all()

        return {
            "items": [FuPoolService._to_vo(row) for row in rows],
            "total": int(total or 0),
            "page": query.page,
            "page_size": query.page_size,
            "pages": -(-int(total or 0) // query.page_size),
        }

    @staticmethod
    def _to_vo(row: FuPoolSnapshot) -> dict[str, Any]:
        """把 ORM 行转为出参，手机号保持脱敏形态，权重按同一公式计算。"""
        weight = (
            WEIGHT_PRIORITY.get(row.priority, 150)
            + min(row.overdue_days, 30) * 10
            + WEIGHT_SCENE.get(row.scene_code, 0)
        )
        return {
            "source_system": row.source_system,
            "task_id": row.task_id,
            "task_no": row.task_no,
            "patient_id": row.patient_id,
            "patient_name": row.patient_name,
            "phone_mask": row.phone_mask,
            "node_name": row.node_name,
            "scene_code": row.scene_code,
            "plan_date": row.plan_date.isoformat(),
            "exec_dept_id": row.exec_dept_id,
            "assignee_id": row.assignee_id,
            "assignee_name": row.assignee_name,
            "priority": row.priority,
            "task_status": row.task_status,
            "overdue_days": row.overdue_days,
            "weight": weight,
        }
```

#### 6.5.2 分派事务与异步回写

```python
from __future__ import annotations

from datetime import datetime
from typing import Any

from sqlalchemy import select, update
from sqlalchemy.ext.asyncio import AsyncSession

from app.clients.followup_client import FollowupClient
from app.core.code_seq import next_no
from app.core.errors import BizError
from app.core.idempotency import idem_guard
from app.models.m19.fu_center import FuDispatchRecord, FuPoolSnapshot
from app.schemas.m19.fu_center import DispatchCreate

FINAL_STATUS = ("COMPLETED", "CANCELLED")


class FuDispatchService:
    """分派服务：本地留痕同步写，上游回写异步做。"""

    @staticmethod
    async def dispatch(
        session: AsyncSession, user: dict[str, Any], payload: DispatchCreate, idem_key: str
    ) -> dict[str, Any]:
        cached = await idem_guard.get("fu:dispatch", idem_key)
        if cached is not None:
            cached["idempotent_replay"] = True
            return cached

        row = await session.scalar(
            select(FuPoolSnapshot).where(
                FuPoolSnapshot.source_system == payload.source_system,
                FuPoolSnapshot.task_id == payload.task_id,
                FuPoolSnapshot.is_deleted.is_(False),
            )
        )
        if row is None:
            raise BizError("1901042", "待办不存在或已被上游删除")
        if row.task_status in FINAL_STATUS:
            raise BizError("1901059", "该待办已办结，不能再分派")
        if row.task_status == "OVERDUE" and payload.action_type == "CLAIM":
            raise BizError("1901059", "逾期待办只能由主管改派")

        if user["role"] == "FOLLOWUP_STAFF":
            if payload.action_type not in ("CLAIM", "RELEASE"):
                raise BizError("1901071", "随访员只能认领或取回自己的待办")
            if payload.action_type == "CLAIM" and payload.to_assignee_id != user["user_id"]:
                raise BizError("1901071", "不能替他人认领")

        await FollowupClient.assert_staff_active(payload.to_assignee_id)

        dispatch_no = await next_no("FD", datetime.now().strftime("%Y%m%d"), 6)
        record = FuDispatchRecord(
            dispatch_no=dispatch_no,
            source_system=payload.source_system,
            task_id=payload.task_id,
            task_no=row.task_no,
            patient_id=row.patient_id,
            patient_name=row.patient_name,
            action_type=payload.action_type,
            from_assignee_id=row.assignee_id,
            from_assignee_name=row.assignee_name,
            to_assignee_id=payload.to_assignee_id,
            to_dept_id=payload.to_dept_id,
            plan_date=row.plan_date,
            priority_snap=row.priority,
            scene_snap=row.scene_code,
            dispatch_reason=payload.dispatch_reason,
            operator_id=user["user_id"],
            operator_name=user["user_name"],
            upstream_sync_status="PENDING",
            idempotency_key=idem_key,
        )
        session.add(record)
        await session.execute(
            update(FuPoolSnapshot)
            .where(FuPoolSnapshot.id == row.id)
            .values(assignee_id=payload.to_assignee_id, exec_dept_id=payload.to_dept_id or row.exec_dept_id)
        )
        await session.commit()

        result = {
            "dispatch_no": dispatch_no,
            "source_system": payload.source_system,
            "task_id": payload.task_id,
            "task_no": row.task_no,
            "action_type": payload.action_type,
            "from_assignee_id": record.from_assignee_id,
            "to_assignee_id": record.to_assignee_id,
            "upstream_sync_status": "PENDING",
            "idempotent_replay": False,
            "dispatched_at": datetime.now().strftime("%Y-%m-%d %H:%M:%S"),
        }
        await idem_guard.set("fu:dispatch", idem_key, result)
        return result
```

#### 6.5.3 触达闸门判定

```python
from __future__ import annotations

from datetime import time
from typing import Any

from app.clients.message_client import MessageClient
from app.core.redis_client import redis_client

THROTTLE_KEY = "m19:throttle:%s:%s"


class TouchGateService:
    """三道闸门，任一不过即不触达；闸门一失败时 fail-closed。"""

    @staticmethod
    async def check(
        patient_id: int, channel: str, medical_necessary: bool, today: str
    ) -> dict[str, Any]:
        try:
            blocked = await MessageClient.check_blacklist(patient_id, channel)
        except Exception:
            return {
                "allowed": False,
                "suppress_reason": "GATE_UNAVAILABLE",
                "detail": "黑名单校验不可用，按 fail-closed 拦截",
            }
        if blocked:
            return {
                "allowed": False,
                "suppress_reason": "UNSUBSCRIBED",
                "detail": "患者已退订该渠道或命中黑名单",
            }

        now = time.fromisoformat(__import__("datetime").datetime.now().strftime("%H:%M:%S"))
        quiet = TouchGateService._in_quiet_hours(now, time(21, 0), time(8, 0))
        if quiet and not medical_necessary:
            return {
                "allowed": False,
                "suppress_reason": "QUIET_HOURS",
                "delay_to": "08:30",
                "detail": "免打扰时段内，非医疗必要触达延后",
            }

        limit = 2 if medical_necessary else 1
        key = THROTTLE_KEY % (patient_id, today)
        touched = int(await redis_client.incr(key))
        if touched == 1:
            await redis_client.expireat(key, TouchGateService._end_of_day(today))
        if touched > limit:
            await redis_client.decr(key)
            return {
                "allowed": False,
                "suppress_reason": "FREQUENCY_LIMIT",
                "touched_today": touched - 1,
                "limit": limit,
                "detail": "当日触达次数已达上限",
            }
        return {"allowed": True, "suppress_reason": None, "touched_today": touched, "limit": limit}

    @staticmethod
    def _in_quiet_hours(now: time, start: time, end: time) -> bool:
        if start <= end:
            return start <= now < end
        return now >= start or now < end

    @staticmethod
    def _end_of_day(today: str) -> int:
        from datetime import datetime, timedelta

        day = datetime.strptime(today, "%Y-%m-%d")
        return int((day + timedelta(days=1)).timestamp())
```

## 7. 缓存与异步任务设计

### 7.1 Redis 缓存设计

全部缓存键以 `m19:fu:center:` 为前缀，与 M19-02 的 `m19:fu:exec:`、公共的 `m19:code:` / `m19:idem:` / `m19:lock:` / `m19:throttle:` 分域隔离，互不覆盖。

| Key 模式 | 类型 | TTL | 说明 | 失效时机 |
| :--- | :--- | :--- | :--- | :--- |
| `m19:fu:center:summary:{dept_id}:{stat_date}` | String(JSON) | 30 秒 | 工作台汇总指标（API-01） | 到期自然失效；分派动作后主动删 |
| `m19:fu:center:dist:{dept_id}:{stat_date}` | String(JSON) | 30 秒 | 待办分布（API-02） | 同上 |
| `m19:fu:center:pending:{hash}` | String(JSON) | 30 秒 | P-01 待办聚合结果（API-28） | 快照刷新完成后按前缀批量删 |

| `m19:fu:center:script:{code}:{version}` | String(JSON) | 600 秒 | 话术模板详情（API-12） | 模板保存、审批后删除 |
| `m19:fu:center:qn:{code}:{version}` | String(JSON) | 600 秒 | 问卷模板详情（API-20） | 问卷保存后删除 |
| `m19:fu:center:lock:refresh` | String | 120 秒 | 快照刷新分布式锁（API-07） | 刷新结束主动删除 |
| `m19:fu:center:batch:last` | String | 无（常驻） | 最近一次刷新批次号 | 每次刷新后覆盖 |

**容量估算**

| Key 组 | 数量 | 单条大小 | 合计 |
| :--- | :--- | :--- | :--- |
| `summary` | 50 科室 × 1 天 | 约 600 字节 | 30 KB |
| `dist` | 50 × 1 | 约 4 KB | 200 KB |
| `pending` | 峰值约 2,000 个不同过滤组合（按 120 秒窗口内活跃组合估算） | 约 20 KB | 40 MB |
| `rule:list` / `rule:*` | 约 30 个场景 × 优先级组合 | 约 8 KB | 240 KB |
| `config` | 约 200 个不同参数组合 | 约 3 KB | 600 KB |
| `calendar` | 24 月 × 5 科室 | 约 12 KB | 1.4 MB |
| `script` / `qn` | 约 500 个模板版本 | 约 6 KB | 3 MB |

合计峰值约 45 MB，单 Redis 实例即可承载，无需分片。其中 `pending` 占 89%，因此给它 30 秒短 TTL 并限制 `limit ≤ 200`，防止组合爆炸。

**缓存与一致性约定**

1. **写后删而不是写后改**：任何写操作完成后直接 `DEL` 相关键，下次读取时重建，绝不在写路径上计算新缓存值，避免并发两次写产生互相覆盖的错误缓存。
2. **P-01 允许 30 秒陈旧**：契约文档明确 `generated_at` 字段，M20 移动端据此显示「数据截至 09:52」，不承诺实时。
3. **快照刷新后批量清空**：刷新完成后 `SCAN` + `DEL` 全部 `m19:fu:center:pending:*` 与 `summary:*`，保证下一批请求拿到新数据。
4. **缓存不可用降级**：Redis 异常时直接查库，不阻断请求；但分布式锁拿不到时 API-07 返回 "1901043" 而不是并发刷新。

```python
from __future__ import annotations

from celery import shared_task
from celery.utils.log import get_task_logger

logger = get_task_logger(__name__)


@shared_task(
    bind=True,
    name="m19_fu.refresh_pool",
    max_retries=2,
    default_retry_delay=30,
    time_limit=120,
    soft_time_limit=100,
)
def refresh_pool(self, batch_no: str, sources: list[str] | None = None, dept_id: int | None = None) -> dict:
    """三源待办快照刷新。单源失败不影响其他源，失败源保留上轮数据。"""
    from app.services.m19.fu_refresh_service import FuRefreshService

    target_sources = sources or ["M03_04", "M10_09", "M11_06"]
    results = []
    for source in target_sources:
        try:
            stat = FuRefreshService.refresh_one(source=source, batch_no=batch_no, dept_id=dept_id)
            results.append({"source": source, "status": "COMPLETE", "upserted": stat["upserted"]})
        except Exception as exc:
            logger.error("refresh_pool source=%s failed: %s", source, exc)
            results.append({"source": source, "status": "FAILED", "error": str(exc)})
    FuRefreshService.clear_pending_cache()
    return {"batch_no": batch_no, "results": results}
```

```python
from apscheduler.schedulers.asyncio import AsyncIOScheduler
from apscheduler.triggers.cron import CronTrigger
from apscheduler.triggers.interval import IntervalTrigger

from app.core.redis_client import redis_client
from app.tasks.m19.fu_center import refresh_pool

REFRESH_LOCK_KEY = "m19:fu:center:lock:refresh"


async def tick_refresh_pool() -> None:
    """定时刷新入口：先抢锁，抢到才投递 Celery，避免多副本同时刷新。"""
    acquired = await redis_client.set(REFRESH_LOCK_KEY, "1", nx=True, ex=120)
    if not acquired:
        return
    try:
        from app.core.code_seq import next_no

        batch_no = await next_no("RB", "20261106", 4)
        refresh_pool.delay(batch_no)
    finally:
        await redis_client.delete(REFRESH_LOCK_KEY)


def register_jobs(scheduler: AsyncIOScheduler) -> None:
    """注册全部随访中心定时任务。"""
    scheduler.add_job(
        tick_refresh_pool,
        trigger=IntervalTrigger(seconds=300),
        id="job_fu_refresh_pool",
        replace_existing=True,
        max_instances=1,
        coalesce=True,
    )
    scheduler.add_job(
        "app.tasks.m19.fu_center:check_stale",
        trigger=IntervalTrigger(seconds=60),
        id="job_fu_check_stale",
        replace_existing=True,
        max_instances=1,
    )
    scheduler.add_job(
        "app.tasks.m19.fu_center:refresh_usage",
        trigger=CronTrigger(hour=1, minute=30),
        id="job_fu_refresh_usage",
        replace_existing=True,

    scheduler.add_job(

        trigger=CronTrigger(month=12, day=1, hour=2),
```

## 8. 业务规则与校验

### 8.1 编码规则

| 对象 | 正则 | 示例 | 规则说明 |
| :--- | :--- | :--- | :--- |
| 话术模板编码 | `^FS_[A-Z][A-Z0-9_]{1,12}_[0-9]{3}$` | `FS_POSTOP_001` | `FS` 前缀 + 场景 + 3 位序号 |
| 问卷模板编码 | `^FQ_[A-Z][A-Z0-9_]{1,12}_[0-9]{3}$` | `FQ_POSTOP_001` | `FQ` 前缀 + 场景 + 3 位序号 |
| 渠道规则编码 | `^CR_[A-Z][A-Z0-9_]{1,12}_[0-9]{3}$` | `CR_POSTOP_001` | `CR` 前缀 + 场景 + 3 位序号 |
| 话术节点回填字段 | `^[a-z][a-z0-9_]{1,31}$` | `vision_status` | 小写蛇形，供执行端存答案 |
| 题目编码 | `^Q_[A-Z][A-Z0-9_]{1,29}$` | `Q_VISION` | `Q_` 前缀 + 大写语义 |
| 刷新批次号 | `^RB[0-9]{8}[0-9]{4}$` | `RB202611060042` | Redis INCR，当日 4 位 |
| 分派记录号 | `^FD[0-9]{8}[0-9]{6}$` | `FD20261106000123` | Redis INCR，6 位 |
| 操作日志号 | `^FL[0-9]{8}[0-9]{6}$` | `FL20261106000456` | Redis INCR，6 位 |
| 导出单号 | `^EX[0-9]{8}[0-9]{3}$` | `EX20261106001` | Redis INCR，3 位 |

**编码不可复用规则**：话术、问卷、渠道规则三类编码一旦创建，即使逻辑删除也不允许再次使用。原因是编码会出现在历史执行记录与报表里，复用一个编码会让两个不同模板的数据混在一起。校验点在 API-13、API-21、API-25，查询时**不加** `is_deleted = FALSE` 条件。

**单号生成**：统一走 `next_no(prefix, date_str, width)`，key 为 `m19:code:{prefix}:{yyyyMMdd}`，当日首单设 TTL 到次日 00:05。禁止用数据库序列，因为序列不随日期回绕，跨日序号不归零，运维按单号排序会看到乱序。

### 8.3 状态流转

状态流转的完整规则见 §3.2.2 的 T-01~T-09 表。本节补充三条实现层面的硬规则：

| 编号 | 规则 | 实现方式 | 违反返回 |
| :--- | :--- | :--- | :--- |
| S-01 | 状态只能通过状态流转接口改变，不能在编辑接口里顺带改 | 编辑接口的入参 Schema 不含 `status` 字段 | "1901013" |
| S-02 | 审批通过的「停旧启新」必须在同一事务内 | `BEGIN` → `SELECT ... FOR UPDATE` → 两次 UPDATE → `COMMIT` | "1901011" |
| S-03 | 驳回不留第六状态 | 状态回落 `DRAFT`，痕迹写 `m19_fu_log` | "1901015" |

**为什么不引入 REJECTED 状态**：共享规范 §13 定义配置类状态为五态。若在子模块里私自加第六个枚举值，M19-08 做报表聚合时按五态写的 `CASE WHEN` 会漏掉这一类，导致「被驳回的模板数」在报表里恒为 0。用日志承载驳回痕迹，既保留审计能力，又不破坏枚举契约。

**审批的并发安全**：两个管理员同时对同一 `script_code` 的两个不同版本点「通过」，若不加锁会出现两个 `ACTIVE` 版本。我们的防护分三层：①事务内按 `script_code` 对全部版本行 `SELECT ... FOR UPDATE`；②部分唯一索引 `uk_m19_fu_script_active` 作为数据库最后防线；③Service 层校验 `expected_current_version` 与库内实际 ACTIVE 版本一致。任一层失败都回滚并返回 "1901011" 或 "1901017"。

### 8.4 业务校验分场景

#### 8.4.1 分派动作语义校验

| 动作 | 允许的前置状态 | 目标责任人 | 原因必填 | 其他约束 |
| :--- | :--- | :--- | :--- | :--- |
| DISPATCH | PENDING / OVERDUE | 必填 | 否 | 主管及以上 |
| REASSIGN | ASSIGNED / EXECUTING / OVERDUE | 必填且 ≠ 原责任人 | 是 | 主管及以上 |
| CLAIM | PENDING / ASSIGNED 且本人无分派 | 只能是本人 | 否 | 随访员可用 |
| RELEASE | ASSIGNED / EXECUTING 且本人为责任人 | 必须为空 | 否 | 释放后回 PENDING |
| ESCALATE | 任意未办结 | 必填（上级） | 是 | 仅主管 |

判别法检查：把 `action_type` 从 `DISPATCH` 改成 `REASSIGN`、把 `dispatch_reason` 留空，能通过吗？不能——`REASSIGN` 要求原因必填。这条规则防的是「改派理由不明」，事后无法解释为什么把一条术后 1 天的随访从张三换给李四。

| :--- | :--- | :--- | :--- |
| 医疗必要 | 非医疗必要 | 允许 | 收紧，降低触达频次 |
| 非医疗必要 | 医疗必要 | 需主管审批 | 放宽，会突破频次闸门 |
| 医疗必要 | 医疗必要 | 允许 | 不变 |
| 非医疗必要 | 非医疗必要 | 允许 | 不变 |

这条规则的原因是「医疗必要」这个标记直接决定每日触达上限从 1 次放宽到 2 次。若能随意放宽，等于取消闸门。因此放宽必须走审批，并且审批记录写入 `m19_fu_log` 的 `change_summary`。

#### 8.4.3 快照刷新的写入规则

| 情况 | 处理 | 说明 |
| :--- | :--- | :--- |
| 上游返回该任务 | `INSERT ... ON CONFLICT DO UPDATE` | 更新状态、责任人、优先级等全部字段 |
| 上游不再返回该任务（已办结或删除） | 本地行 `is_deleted = TRUE` | 不物理删除，保留供分派记录追溯 |
| 上游接口失败 | 保留上轮数据，写 `upstream_error` | 绝不清空，否则一次超时就让待办全消失 |
| 上游返回但字段缺失 | 缺失字段保留原值，不覆盖为空 | 防止上游版本升级时把本地数据冲掉 |

第三行是最重要的一条。实测中 M03-04 待办接口在月初批量生成时有约 30% 概率超时。如果超时就清空快照，随访员会在最忙的那半小时看到「今天没有待办」，实际有 900 条。

### 8.5 计算规则与舍入

| 计算项 | 公式 | 舍入 | 精度 | 空值规则 |
| :--- | :--- | :--- | :--- | :--- |
| 完成率 | 已办 / 应办 | 四舍五入 4 位 | NUMERIC(10,6) | 分母 0 → NULL |
| 分布占比 | 分组数 / 总数 | 四舍五入 4 位 | NUMERIC(10,6) | 分母 0 → NULL |
| 分派均衡度 | `1 - (max-min)/avg` | 四舍五入 4 位 | NUMERIC(10,6) | 人数 < 2 → NULL |
| 任务权重 | 见 §3.4.1 | 整数无舍入 | INTEGER | 空值按默认值 |
| 快照年龄 | 当前时间 - 刷新时间 | 取整到秒 | INTEGER | 无刷新 → NULL |
| 问卷总分 | 各题分值之和 | 两位小数 | NUMERIC(10,2) | 无分值 → 0.00 |

**统一约定**：所有比率的存储与传输一律 `NUMERIC(10,6)`，JSON 序列化为字符串保留 6 位小数，前端按需格式化为百分比。**严禁使用浮点**，因为 0.1 + 0.2 在二进制浮点下等于 0.30000000000000004，累积到 60 道题的问卷总分上会出现 0.01 的漂移，正好跨越异常阈值边界。

**分母为 0 的处理**：全部比率的 `denominator = 0` 时结果返回 `null`，页面显示「—」。数据库层对应约束 `CHECK (denominator > 0 OR ratio_value IS NULL)`。这条规则防的是「把无数据当成 0」：某科室今天没有应随访任务，完成率显示 0.00% 会被主管误读为「一条都没完成」。

### 8.7 并发控制

| 场景 | 并发风险 | 控制手段 | 违反返回 |
| :--- | :--- | :--- | :--- |
| 两人同时审批同一模板的不同版本 | 出现两个 ACTIVE | `SELECT ... FOR UPDATE` + 部分唯一索引 | "1901011" |
| 两人同时编辑同一模板 | 后写覆盖前写 | 乐观锁 `version_no` | "1901003" |
| 多个副本同时触发快照刷新 | 重复刷新、批次号冲突 | Redis `SET NX EX 120` | "1901043" |
| 同一分派动作重复提交 | 产生两条分派记录 | 幂等键唯一索引 | "1901060" |
| 刷新与分派并发 | 刷新覆盖分派结果 | 刷新只更新上游字段，不动 `assignee_id`（本地分派优先） | — |
| 触达频次并发 | 计数少算导致超发 | Redis `INCR` 原子操作 | — |
| 配置并发修改 | 后写覆盖前写 | 每项独立乐观锁 | "1901003" |

**刷新与分派并发**这一条在评审时最容易被跳过。快照刷新会整体 upsert 上游返回的 `assignee_id`，而本地刚做过分派但上游还没同步回来，此时刷新会把责任人改回旧的。处理办法是：刷新任务对 `m19_fu_dispatch_record` 中 `upstream_sync_status = 'PENDING'` 的相关待办**跳过 `assignee_id` 与 `assignee_name` 字段**，只更新 `task_status` / `priority` / `plan_date` / `overdue_days` 等上游字段。这样本地的分派结果在回写成功前不会被刷新抹掉。

**边界钉死：M19-01 不持有独立的任务状态位。** 快照的 `task_status` 全权以上游 M03-04 为准，随每轮刷新覆盖；本地唯一自治的列是 `assignee_id` / `assignee_name`，且它们的保护不靠快照自身，靠分派记录的 `upstream_sync_status = 'PENDING'`。因此「分派了但未同步」的窗口里 `task_status` 被上游改回是正确行为——真实推进必须由 M19-02 走 U-02/U-03 完成，M19-01 不提供任何直接改写 `task_status` 的入口。后来人若要加本地状态位，必须同步加进跳过列表，否则每条本地标记都会在下一轮刷新静默消失。

**判定依据落在字段上，不是靠内存判断**：`m19_fu_dispatch_record.upstream_sync_status` 是这条跳过的唯一依据，取值为 `PENDING`（本地已落库、上游未确认）、`SYNCED`（回写成功，终态）、`FAILED`（5 次重试耗尽，可人工补偿回 PENDING）。三者单向流转，不存在 `SYNCED` 回到未同步的路径。字段定义、CHECK 约束（`ck_m19_fu_dispatch_record_sync` / `_sync_at` / `_sync_err` / `_retry`）与刷新时的实际查询语句见数据结构文档 4.9 节的「同步状态语义与离开条件」，那里给出了可直接执行的 `SELECT DISTINCT source_system, task_id ... WHERE upstream_sync_status = 'PENDING'` 及其 1 天时间窗的理由。

**为什么带 1 天时间窗而不是全量跳过**：24 小时前的 `PENDING` 已由 `m19_fu.sync_dispatch` 的 5 次退避重试覆盖（总退避约 21 分钟），若仍停留在 `PENDING` 说明 Celery 队列积压异常。此时若继续无限期跳过，本地会永远拿不到上游真实责任人；因此让刷新恢复上游值，并由 `fu_center_dispatch_sync_fail` 指标告警介入。这是一个「宁可短暂回退，也不能永久卡住」的取舍。

**审批并发的事务边界**：`BEGIN` → `SELECT ... FROM m19_fu_script WHERE script_code = :code FOR UPDATE`（锁全部版本行）→ 校验 `expected_current_version` → `UPDATE` 旧 ACTIVE 为 INACTIVE → `UPDATE` 本版本为 ACTIVE → 写日志 → `COMMIT`。缓存失效与事件发布在事务提交**之后**执行，避免事务回滚但缓存已删或事件已发的「假通知」。

### 9.3 数据权限

| 数据范围 | 规则 | 实现 |
| :--- | :--- | :--- |
| 全院 | 管理员、质控可看全院待办与全部模板 | 不加科室谓词 |
| 本科室 | 科室主任只看 `exec_dept_id` 属本科室的待办 | `exec_dept_id IN (:dept_scope)` |
| 本人 | 随访员只看 `assignee_id = 当前用户` 或本科室未分派的待办 | `assignee_id = :uid OR (assignee_id = 0 AND exec_dept_id IN (:dept_scope))` |

数据权限在 Service 层统一注入，不允许 Controller 层各自拼接。实现方式是 `user["dept_scope"]` 由 `require_permission` 依赖一并返回，Service 在任何查询构造前先调用 `apply_dept_scope(stmt, user)`。若发现 Controller 直接查表绕过数据权限，代码评审直接拒绝。

科室主任跨科室查询时的行为：请求带其它 `dept_id` 时，服务端把 `dept_id` 强制改写成授权范围内的第一个科室，并在响应头 `X-Scope-Adjusted: true` 提示前端。**不返回 403**，因为多数场景是分享链接带错了参数，直接拒绝会让用户困惑。

**载荷安全红线**：`m19.fu.dispatch.created` 只允许出现 `task_id` 与 `to_assignee_id`，**禁止出现 `patient_id`、姓名、手机号、随访节点名称**。分派事件被 M19-08 用于分派均衡统计，只需要工号维度，不需要患者维度。若 M19-08 需要患者维度，改为读表而非订阅事件。

**事件命名**：本子模块事件用 `m19.fu.*` 而不是模块总纲的 `m19.followup.*`。原因：`m19.followup.executed` 与 `m19.followup.lost` 已由 M19-02 定义且载荷含 `patient_id`，若本子模块也用 `m19.followup.*` 前缀，订阅方难以区分「配置生效」与「随访执行完成」两类语义差别极大的事件，容易误把配置事件当执行事件处理。`fu` 是随访中心专用的短前缀，与表前缀 `m19_fu_` 对应。

### 10.4 事件订阅

| 事件 | 发布方 | 处理逻辑 | 幂等 |
| :--- | :--- | :--- | :--- |
| `mpi.followup.task.created` | M03-04 | 任务已生成，写入快照但标为「未到窗口」（不可执行） | 按 `(source_system, task_id)` 去重 |
| `mpi.followup.task.ready` | M03-04 | 任务进入可执行窗口，转为可执行待办（待办池主增量来源） | 同上去重，并只升不降状态 |
| `mpi.followup.task.updated` | M03-04 | 同步任务状态（含 M19 自己回写后的回声） | 按 `(task_id, new_status)` 去重，回声不重复处理 |
| `mpi.followup.task.overdue` | M03-04 | 标记逾期，刷新 `overdue_days` | 按 `task_id` 去重 |
| `mpi.followup.plan.created` | M03-04 | 清空 `m19:fu:center:pending:*` 与 `summary:*` | 按键删除天然幂等 |
| `mpi.followup.plan.cancelled` | M03-04 | 该计划下任务置 `CANCELLED` 并从待办池移除 | 按 `plan_id` 去重 |
| `m10.followup.created` | M10-09 | 增量加入待办快照 | 按 `(source_system, task_id)` 去重 |
| `m11.postop.followup.created` | M11-06 | 增量加入待办快照 | 同上 |
| `mpi.member.merged` | M03-03 | 按保留患者号重写快照行的 `patient_id` | 按事件内 `member_id` 去重 |

**增量加入而不是等全量刷新**的理由：全量刷新间隔 300 秒，若一条术后 1 天随访在 09:05 生成，等到 09:10 才出现在待办池，随访员可能已经打完了这一批电话。事件驱动增量加入让新任务在 1 秒内可见，全量刷新只做兜底与状态同步。

**`mpi.followup.task.created` 与 `mpi.followup.task.ready` 的区别**：前者表示任务记录已生成，但可能还没到可执行窗口（比如计划随访日在 3 天后）；后者表示任务已进入可执行窗口，可以打电话了。两者都订阅是合理的，但处理方式必须有别：

- 收到 `task.created` 时，快照行写入但 `task_status` 标记为上游原值，并在 M19 侧按 `plan_date > 当前日期 + 提前可见天数` 判定为「未到窗口」，此类行在待办池默认筛选下不出现，只在「未来待办」视图可见。
- 收到 `task.ready` 时，把该行转为可执行待办，**状态只升不降**（已是从 `EXECUTING` 往后的推进状态的，不被 `task.ready` 拉回 `PENDING`）。待办池的日常增量主要来自这条事件。
- 只订 `task.created` 而不订 `task.ready`，会出现「任务生成了但永远不出现」的静默失效：因为它可能生成时就在窗口外，等到窗口到达时没有任何事件通知本地。这是本子模块必须两条都订的原因，也是把 `task.ready` 列为待办池主增量来源的原因。

**`mpi.followup.task.updated` 的回声处理**：M19-02 通过 U-02/U-03 回写结果后，M03-04 会发 `mpi.followup.task.updated`。这个事件看起来像是「上游改了状态」，实际上它的业务触发点就是 M19 自己的写动作，属于回声。处理方式是按 `(task_id, new_status)` 与本地最近一次写动作比对，命中则跳过，不做二次处理。若不识别回声，会出现「本地刚置 COMPLETED，收到 UPDATE 事件后又触发一遍完成流程与积分联动」的重复副作用。

**`mpi.member.merged` 的处理**：患者合并后，快照里旧 `patient_id` 的行会变成孤儿，P-01 按新患者号查不到历史随访。处理方式是按事件载荷里的 `old_patient_id` 与 `new_patient_id` 更新 `patient_id`，并同步更新分派记录中的 `patient_id`（分派记录虽只增不改，但患者号重定向是唯一的例外，单独走一个受限的 UPDATE 通道，只允许改 `patient_id` 一列）。

### 11.1 异常分类

### 11.2 降级策略

| 场景 | 降级行为 | 前端表现 | 告警级别 |
| :--- | :--- | :--- | :--- |
| M03-04 待办接口不可用 | 用上轮快照，`source_status='STALE'` | 顶部黄条「随访服务暂不可用，数据截至 …」 | P1 |
| M10-09 不可用 | 只显示两源，`PARTIAL` | 黄条列出降级来源 | P2 |
| M11-06 不可用 | 同上 | 同上 | P2 |
| M03-05 黑名单校验不可用 | **fail-closed**，全部触达拦截 | 触达页提示「合规校验不可用，暂不发送」 | P1 |
| M03-04 分派回写不可用 | 本地记录 `PENDING`，Celery 重试 5 次 | 行内显示「同步中」小图标 | P2 |
| M01 人员接口不可用 | 用快照姓名 | 姓名后加「（数据可能过期）」 | P3 |
| Redis 不可用 | 直接查库，跳过缓存 | 无明显变化，仅 P95 升到约 60ms | P2 |
| PostgreSQL 不可用 | 返回 "199001" | 全页错误提示 | P0 |

**fail-closed 的理由**：黑名单校验不可用时若放行，就是把「已退订的患者」也发一遍。这条错误无法撤回，而漏发一条随访提醒的代价只是打个电话补上。因此这一类依赖必须是 fail-closed，其他依赖则可以是 fail-open（用缓存或旧数据）。

| 指标 | 类型 | 阈值 | 告警级别 | 处置 |

**快照过期的判定与告警链路**：`check_stale` 任务每 60 秒检查一次 `max(refreshed_at)`，超过 `stale_minutes`（默认 30）则发 `m19.fu.pool.stale` 事件并打 P2 告警。之所以给 30 分钟这么长的阈值，是因为正常刷新间隔是 300 秒，30 分钟意味着连续 6 轮刷新都失败，此时不是抖动而是真故障，值得叫醒人。
