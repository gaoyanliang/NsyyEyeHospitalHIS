## 1. 模块概述

### 1.1 定位

M19-03 是 M19 模块中**唯一主动向患者发起外部触达的运营型子模块**。它的职责是把「运营意图」翻译成「一次合规的、有记录的、可追溯的患者接触」。

用一句话概括：**关怀是运营驱动的、一对一触发的患者接触，本子模块负责决定「该不该联系这个人、什么时候联系、用什么内容联系、联系完效果如何」。**

与临床随访的根本区别在于触发动力不同：

| 维度 | 临床随访（M19-01/02、M03-04） | 患者关怀（本子模块） |
| --- | --- | --- |
| 触发动力 | 临床路径要求，有固定节点 | 运营策略驱动，按人群与事件触发 |
| 有无模板节点 | 有明确的随访模板与节点计划 | 无节点，一次性触发 |
| 未做会怎样 | 影响医疗质量指标，属于医疗行为缺陷 | 影响转化与满意度，属于运营机会损失 |
| 能否退订 | 不能退订（医疗必要） | 可以退订（患者有权拒收） |
| 典型场景 | 术后 1 天/1 周/1 月复查 | 生日祝福、30/90 天未到店召回、节日问候 |

### 1.2 为什么必须独立成子模块

**理由一：触达是全院唯一的高风险对外动作，集中管理才能保证「三道闸门一次不漏」。**

本子模块覆盖生日关怀、久未到店召回、术后关怀、节日关怀四类场景。按日均触达 3,000 条估算，年触达量约 109.5 万条。若把触达逻辑分散到各业务子模块（术后关怀写在 M10、召回写在 M16 会员营销），每一处都要重新实现一次退订校验、免打扰判定、频次控制。经验上每多一处实现，漏一道闸门的概率就翻一倍：假设单处实现正确率 99%，4 处独立实现全部正确的概率降到 96.1%，按年 109.5 万条计，将有约 4.3 万条未受控触达，其中只要有 1% 引发投诉就是 430 起。

**理由二：合规举证要求「一条触达一条证据链」，需要独立的不可篡改记录体系。**

《个人信息保护法》要求处理个人信息应当具有明确、合理的目的，并限于实现处理目的的最小范围。当患者质疑「你们为什么给我发这条短信」时，我们必须能在 1 分钟内答出：这条短信的规则是什么、什么时候配置的、谁审批的、当时有没有退订、免打扰判定结果是什么、频次计数是多少。这套证据链涉及规则、计划、任务、触达、黑名单快照五张表，只有集中在本子模块才能保证五张表在同一事务边界内一致。

**理由三：运营节奏与临床节奏完全不同，混在一起会互相拖累。**

临床随访的执行高峰在门诊与手术当日下午（14:00~18:00），运营触达的最佳窗口在晚间 19:00~21:00 与午间。两者的定时作业、批量规模、失败重试策略都不同。混在一起会出现「召回批量发送把随访的回执接收挤掉」这类问题。独立成子模块后可以分别配置 Celery 队列与连接池配额。

**理由四：本子模块承担「术后关怀」这一特殊场景，它是关怀与临床的交叉点，必须单点裁决。**

术后关怀看起来是运营行为，实际触碰临床信息。它必须与外部的临床随访做冲突消解（避免同一天收两条），必须做模板变量隐私校验（不得出现术式与术眼）。这两件事只有把术后关怀与随访放在同一模块内、由同一处代码裁决才可靠——这也是它放在 M19 而非 M10/M11 的原因。

### 1.4 概念辨析

**① 关怀计划（Care Plan）与关怀规则（Care Rule）。**

规则是「长期生效的筛选与内容定义」，例如「所有 90 天未到店的患者，每日 09:00 筛一次，用模板 SMS_RECALL_90 发送」。计划是「某一天按规则筛出来的一批人」，例如「2026-10-21 按 RULE_RECALL_90 筛出 1,240 人」。规则是配置，计划是执行实例。一个规则每天产生一个计划。

**② 关怀任务（Care Task）与触达记录（Care Touch）。**

任务是「要为某个患者做某件事」，有生命周期（待发送→发送中→已送达/失败/已取消/已抑制）。触达记录是「实际发生了什么」，是只增不改的事实流水。一个任务可能对应多条触达记录（一次发送 + 若干回执行），一条触达记录也可能没有对应任务（例如退订回执产生的记录）。**报表与事故追查一律以触达记录为准，不改写、不删除。**

**③ 抑制（SUPPRESSED）与失败（FAILED）。**

抑制是「我们主动决定不发」——退订、免打扰、超频次、模板违规、与随访冲突。失败是「我们发了但没发出去」——通道拒绝、号码无效、系统异常。两者在报表、告警、重试策略上完全不同：抑制的正确处置是**不重试**（重试等于绕过闸门），失败的正确处置是**有限重试**（最多 3 次）。把它们混在一起的后果是：客服看到「术后关怀 300 条失败」，无法判断该不该人工补发，若盲目补发就等于绕过了退订校验。

**④ 召回（Recall）与流失分层（Risk Level）。**

分层回答「这个会员属于哪一类客户」，是静态属性，每天重算。召回回答「这一批要联系谁、为什么是现在、按什么顺序」，是一次性行动，有明确的生成时刻与有效期。把分层直接当名单用，会出现「一个已经被触达 5 次的患者仍在『高价值流失风险』分层里」的问题。

**⑤ 术后关怀（POSTOP）与术后随访（M19-02）。**

术后关怀是运营行为（问候、满意度、复诊提醒、会员权益告知），可退订，内容不得含临床信息。术后随访是医疗行为（查视力、看眼压、评估切口），不可退订，内容含临床信息。二者可能在同一患者身上同一天发生，此时**术后关怀必须让位**，判为 `CONFLICT_WITH_FOLLOWUP` 并抑制。

### 1.5 模块目标

| 序号 | 目标 | 量化指标 | 验收关联 |
| --- | --- | --- | --- |
| 1 | 触达零违规 | 全年因触达引发的退订类投诉为 0；闸门覆盖率 100% | AC-01、AC-02 |
| 2 | 证据链完整可查 | 任意一条触达可在 1 分钟内追溯规则、审批、三闸门判定 | AC-03、AC-05 |
| 3 | 抑制原因可解释 | `SUPPRESSED` 任务 100% 有可读的抑制闸门与原因 | AC-04、AC-21 |
| 4 | 隐私不泄露 | 关怀文案中临床敏感信息的出现次数为 0 | AC-11、AC-12 |
| 5 | 召回有效 | 召回触达转化率不低于 8%，名单人工复核覆盖率 100% | AC-27、AC-28 |
| 6 | 接口性能达标 | P-09 内部契约 P95 ≤ 300ms，工作台 P95 ≤ 800ms | PF-01、PF-02 |
| 7 | 与随访不打架 | 同一患者同日随访与关怀同时触达的事件为 0 | AC-18、AC-19 |

### 2.3 与相邻模块的边界判定

**判定规则表（可机械执行）：**

| 场景 | 判定 | 归属 |
| --- | --- | --- |
| 患者术后第 1 天要提醒复查视力 | 有临床节点、内容含检查项目 | 随访（M19-02） |
| 患者术后第 3 天发一条「恢复得怎么样」的问候 | 无临床节点、内容不含临床信息 | 关怀（本子模块，POSTOP） |
| 系统需要生成「术后 1 周复查」任务 | 需要随访模板与节点 | M03-04 |
| 患者 90 天没来，需要联系 | 无临床理由，运营驱动 | 关怀（本子模块，RECALL） |
| 患者生日当天发祝福 | 运营驱动 | 关怀（本子模块，BIRTHDAY） |
| 会员积分即将过期提醒 | 权益驱动 | M19-04 提供事件，经 P-09 或规则触达主体在本子模块 |
| 营销活动的群发短信 | 营销活动管理 | M19-07 策划，触达执行在本子模块 |
| 检验危急值通知 | 医疗必须，不可退订 | M03-05 NOTICE 业务类型，不经本子模块 |

**边界铁律：任何患者可见的外部消息，如果它的目的是「让患者回院检查某个临床项目」，必须由随访通道发出；如果目的是「维护关系、促成复购、告知权益」，则由本子模块发出。** 两者的内容不得互相覆盖。

| U-01 | M03-05 | 黑名单/退订查询 | `GET /internal/v1/message/check-blacklist` | **必须 fail-closed，全部不发** | 任务置 `SUPPRESSED` + `suppress_reason = 'MSG_SERVICE_DOWN'` |
| U-02 | M03-05 | 消息提交 | `POST /internal/v1/message/send` | 触达失败 | 转站内信；站内信也不可用则置 `SUPPRESSED` 并次日重试 |
| U-03 | M03-05 | 模板详情（隐私校验） | `GET /internal/v1/message/template/{code}` | 无法校验模板变量 | 缓存优先，无缓存则不允许启用规则（fail-closed） |
| U-04 | M03-05 | 退订提交 | `POST /internal/v1/message/unsubscribe` | 患者无法通过本模块退订 | 引导至 M03-05 页面，本地记失败日志 |
| U-05 | M03-04 | 随访任务存在性（冲突判定） | `GET /internal/v1/followup/tasks/pending` | 无法判定冲突 | 缓存 30 分钟；无缓存则视为「存在冲突」保守抑制 |
| U-06 | M03-01 | 患者基本信息与标记 | `GET /internal/v1/patient/{id}/brief` | 无法取姓名与手机号 | 任务置 `SUPPRESSED` + `NO_VALID_CONTACT` |
| U-07 | M03-03 | 会员等级与标签 | `GET /api/v1/mpi/members/{member_id}` | 名单无法按等级筛选 | 名单构建失败，返回错误提示 |
| U-08 | M10 | 到店记录 | `GET /internal/v1/m10/vision-archive/{patient_id}/summary` | 名单无法计算到店间隔 | 使用 T+1 本地汇总；无汇总则名单不生成 |
| U-09 | M16 | 消费金额 | `POST /internal/v1/billing/statistics` | 名单无法按金额筛选 | 同上 |
| U-10 | M02 | 审计落库 | `POST /internal/v1/m02/audit/record` | 审计缺失 | 本地 `m19_care_oper_log` 兜底，异步补送 |

**上游不可用时的统一原则：** 涉及**合规闸门**的上游（U-01、U-03、U-05）一律 **fail-closed**——查不到就当作「不允许发送」。涉及**数据补充**的上游（U-07、U-08、U-09）一律 **fail-visible**——无法计算就明确报错并降级显示数据质量，绝不静默填 0。

### 3.2 状态机

#### 3.2.1 关怀任务状态机

```text
                        ┌──────────────────────────────┐
                        │                              │
               创建 ───→ PENDING                          │
                        │  │  │  │                       │
        ┌───────────────┘  │  │  └───────────┐           │
        │ 闸门拦截          │  │  取消         │ 提交       │
        ▼                  │  │              ▼           │
   SUPPRESSED              │  │         CANCELLED        │
        │                  │  │                          │
        │ 人工重试(新任务)  │  │  闸门2 顺延               │
        └──────────────────┘  ▼                          │
                        (下一次扫描回到 PENDING)           │
                               │ 提交                      │
                               ▼                          │
                          SENDING ──── 3 次失败 ────→ FAILED
                               │
                               │ 收到回执
                               ▼
                          DELIVERED
```

**状态定义：**

| 状态 | 中文 | 是否终态 | 含义 | 进入条件 |
| --- | --- | --- | --- | --- |
| `PENDING` | 待发送 | 否 | 已生成，等待调度与闸门校验 | 任务创建成功 |
| `SENDING` | 发送中 | 否 | 已通过三道闸门，已向 M03-05 提交 | 提交消息接口返回成功 |
| `DELIVERED` | 已送达 | 是 | 收到通道送达回执 | 回执类型为 `DELIVERED` 或 `READ` |
| `FAILED` | 发送失败 | 是 | 已提交但通道返回失败，且重试耗尽 | 失败次数达到 3 |
| `CANCELLED` | 已取消 | 是 | 人工取消或计划取消 | 操作人或计划取消 |
| `SUPPRESSED` | 已抑制 | 是 | **被闸门拦下，我们主动决定不发** | 任一闸门不过 |

**流转规则：**

| 编号 | 从 | 到 | 触发条件 | 副作用 |
| --- | --- | --- | --- | --- |
| T-01 | 无 | `PENDING` | 计划展开或 P-09 触发 | 写 `m19_care_task`，发 `m19.care.triggered` |
| T-02 | `PENDING` | `SUPPRESSED` | 闸门一判定 BLOCK 或 FAIL_CLOSED | 写 `suppress_gate` + `suppress_reason` + 触达记录 |
| T-03 | `PENDING` | `SUPPRESSED` | 闸门三判定 BLOCK | 同上，`suppress_reason = 'FREQUENCY_LIMIT'` |
| T-04 | `PENDING` | `SUPPRESSED` | 模板变量隐私校验不过 | `suppress_gate = 'TEMPLATE_PRIVACY'` |
| T-05 | `PENDING` | `SUPPRESSED` | 同日存在随访任务 | `suppress_gate = 'CONFLICT_WITH_FOLLOWUP'` |
| T-06 | `PENDING` | `PENDING` | 闸门二判定免打扰 | 写 `defer_to_at`，`defer_count = 1`，状态不变 |
| T-07 | `PENDING` | `PENDING` | 闸门二判定需取消 | 实际落 `SUPPRESSED`，原因 `QUIET_HOURS_CANCEL` |
| T-08 | `PENDING` | `SENDING` | 三闸门全部通过且提交成功 | 写触达记录 `result = 'SENT'` |
| T-09 | `SENDING` | `DELIVERED` | 收到送达回执 | 写回执行，`delivered_at` 赋值 |
| T-10 | `SENDING` | `FAILED` | 收到失败回执且重试已耗尽 | 写 `fail_code` + `fail_reason` |
| T-11 | `SENDING` | `SENDING` | 失败但未耗尽重试 | `send_attempts` 加 1，追加触达记录 |
| T-12 | `PENDING` | `CANCELLED` | 人工取消或所属计划取消 | 写 `cancel_reason` |
| T-13 | `SENDING` | `CANCELLED` | 通道不可用超时且确认未发出 | 写 `cancel_reason` |

**禁止流转（必须报错）：**

| 编号 | 禁止 | 错误码 | 理由 |
| --- | --- | --- | --- |
| F-01 | `SUPPRESSED` → `SENDING` | — | 抑制是终态，绕过闸门等于合规事故 |
| F-02 | `DELIVERED` → 任何状态 | — | 已送达不可回退 |
| F-03 | `FAILED` → `SENDING` | — | 需新建任务重试，保留原失败证据 |
| F-04 | `CANCELLED` → 任何状态 | — | 已取消不可复活 |
| F-05 | `SUPPRESSED` 缺少抑制原因 | — | 数据库组合约束直接拒绝 |

#### 3.2.2 关怀计划状态机

```text
   PENDING ──→ RUNNING ──→ COMPLETED ──→ ARCHIVED
      │            │
      │            └──→ CANCELLED
      └──→ CANCELLED
```

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| `PENDING` | 待执行 | 计划生成成功 |
| `RUNNING` | 执行中 | 开始展开任务 |
| `COMPLETED` | 已完成 | 全部任务到达终态 |
| `CANCELLED` | 已取消 | 人工取消或规则停用 |

```text
   BUILDING ──→ READY ──→ IN_USE ──→ ARCHIVED
```

| --- | --- | --- |

### 3.3 分类与枚举

**关怀类型 `care_type`：**

| 值 | 中文 | 是否医疗必要 | 可否免打扰例外 | 典型触发 |
| --- | --- | --- | --- | --- |
| `BIRTHDAY` | 生日关怀 | 否 | 否 | 定时每日扫描生日 |
| `RECALL` | 久未到店召回 | 否 | 否 | 定时按规则与名单 |
| `POSTOP` | 术后关怀 | 是 | **是** | P-09 外部触发 |
| `FOLLOWUP` | 随访关联关怀 | 是 | 否 | P-09 由随访模块触发 |
| `ANNIVERSARY` | 纪念日关怀 | 否 | 否 | 定时（如配镜周年） |
| `HOLIDAY` | 节日关怀 | 否 | 否 | 定时按节假日表 |
| `OTHER` | 其他 | 否 | 否 | 人工发起 |

**抑制闸门 `suppress_gate`：**

| 值 | 中文 | 判定来源 | 是否可人工重试 |
| --- | --- | --- | --- |
| `BLACKLIST` | 退订或黑名单 | 闸门一，M03-05 | 否（重试等于绕过） |
| `QUIET_HOURS` | 免打扰时段 | 闸门二 | 否（配置 `CANCEL` 时） |
| `FREQUENCY` | 超频次上限 | 闸门三 | 否（次日自然重置） |
| `TEMPLATE_PRIVACY` | 模板隐私校验不过 | 规则准入 | 否（需改模板） |
| `CONFLICT_WITH_FOLLOWUP` | 与随访冲突 | 冲突判定 | 是（随访完成后） |

**抑制原因 `suppress_reason`：**

| 值 | 中文 | 关联闸门 |
| --- | --- | --- |
| `UNSUBSCRIBED` | 患者已退订该业务类型 | `BLACKLIST` |
| `BLACKLISTED` | 患者在全渠道黑名单 | `BLACKLIST` |
| `FREQUENCY_LIMIT` | 超过 24 小时触达上限 | `FREQUENCY` |
| `QUIET_HOURS_CANCEL` | 处于免打扰时段且规则为取消 | `QUIET_HOURS` |
| `PRIVACY_VIOLATION` | 模板变量含敏感键 | `TEMPLATE_PRIVACY` |
| `FOLLOWUP_CONFLICT` | 同日已有临床随访 | `CONFLICT_WITH_FOLLOWUP` |
| `NO_VALID_CONTACT` | 无有效联系方式 | `BLACKLIST` |
| `RULE_DISABLED` | 规则已停用 | `TEMPLATE_PRIVACY` |
| `DEADLINE_EXCEEDED` | 超过发送截止时刻 | `QUIET_HOURS` |
| `MSG_SERVICE_DOWN` | 消息服务不可用，保守拦截 | `BLACKLIST` |

**触达渠道 `channel`：** `SMS` 短信 / `WECHAT` 微信 / `PHONE` 电话外呼 / `INBOX` 站内信 / `MAIL` 邮件 / `PUSH` 应用推送。

### 3.4 关键计算模型

#### 3.4.1 三重闸门判定模型

```text
判定顺序（短路求值，前一闸门不过不再进入下一闸门）：

    Gate1  意愿闸门  : g1 = blacklist_check(patient_id, channel, biz_type)
                       g1 ∈ { ALLOWED, BLOCKED, UNAVAILABLE }
                       ALLOWED   → 进入 Gate2
                       BLOCKED   → 抑制, suppress_gate = BLACKLIST
                       UNAVAILABLE → 抑制, suppress_gate = BLACKLIST,
                                     suppress_reason = MSG_SERVICE_DOWN (fail-closed)

    Gate2  时段闸门  : g2 = quiet_check(now, care_type, rule)
                       g2 ∈ { PASS, EXEMPT, DEFER, CANCEL }
                       PASS/EXEMPT → 进入 Gate3
                       DEFER       → defer_to_at = next_allowed(now) + jitter
                                     状态保持 PENDING，defer_count += 1
                       CANCEL      → 抑制, suppress_gate = QUIET_HOURS

    Gate3  频次闸门  : n = incr_and_count(patient_id, today)
                       limit = medical_necessary ? freq_limit_medical : freq_limit_24h
                       PASS  if n <= limit
                       BLOCK if n > limit  → 抑制, suppress_gate = FREQUENCY

    三闸门全部 PASS → 提交 M03-05 发送

单位与边界：
    - defer_to_at 精确到秒；jitter ∈ [0, defer_jitter_minutes] 分钟随机
    - defer_count 上限 1：顺延一次后若仍处于免打扰（理论上不会），
      则强制抑制，原因 QUIET_HOURS_CANCEL，避免无限顺延
    - 频次计数窗口默认为自然日 [00:00:00, 23:59:59]
舍入：
    - 闸门判定不涉及舍入，全部为整数比较
失败条件：
    - Gate1 超时 800ms 即判 UNAVAILABLE（fail-closed）
    - Gate3 Redis 超时 50ms 即降级为查库
```

**算例一：术后关怀在免打扰时段触发。**

患者 A 于 2026-10-21 22:15:30 收到 P-09 术后关怀触发，`care_type = POSTOP`，渠道 `SMS`。

| 步骤 | 输入 | 结果 |
| --- | --- | --- |
| 1 | 查规则，匹配 `TR002`（`CARE_TYPE=POSTOP`） | `quiet_exempt_types` 含 `POSTOP` |
| 2 | Gate1 查黑名单 | `ALLOWED` |
| 3 | Gate2 判定当前 22:15:30 落在 21:00~08:00 内，且 `POSTOP` 在例外列表 | `EXEMPT`，立即发送 |
| 4 | Gate3 当日计数，该患者今天已被触达 1 次（医疗必要上限 2） | `n = 1 ≤ 2`，`PASS` |
| 5 | 提交发送 | 触达记录 `gate_seq = BLACKLIST:PASS>QUIET:EXEMPT>FREQ:PASS` |

**算例二：生日关怀在免打扰时段触发。**

患者 B 生日为 2026-10-21，生日关怀规则在 21:30 生成任务。

| 步骤 | 输入 | 结果 |
| --- | --- | --- |
| 1 | Gate2 判定 21:30 处于免打扰，`BIRTHDAY` 不在例外列表 | 依 `delay_policy` 决定 |
| 2 | 规则 `delay_policy = DEFER_NEXT_DAY` | `defer_to_at = 2026-10-22 08:05:00 + jitter` |
| 3 | 次日 08:05 重新判定，Gate2 | `PASS` |
| 4 | 若次日恰好是患者 C 的生日以外的日子 | 文案仍使用生日模板，日期取原生日 |
| 5 | 若 `delay_policy = CANCEL` | `SUPPRESSED` + `QUIET_HOURS_CANCEL` |

**算例三：召回触达撞上频次上限。**

患者 C 于 2026-10-21 10:00 已收到生日关怀短信（非医疗必要，计数 1）。同日 10:05 召回计划展开，生成召回任务。

| 步骤 | 输入 | 结果 |
| --- | --- | --- |
| 1 | Gate1 | `ALLOWED` |
| 2 | Gate2 当前 10:05 | `PASS` |
| 3 | Gate3 计数 `n = 1`，非医疗必要上限 1 | `1 > 1` 不成立，`n < limit` 不成立，判定 `BLOCK` |
| 4 | 抑制 | `suppress_gate = FREQUENCY`，`suppress_reason = FREQUENCY_LIMIT` |
| 5 | 次日 | 计数自然重置，召回任务不自动重发（一次性任务） |

**算例四：Redis 不可用的降级。**

患者 D 于 2026-10-21 15:00 触发术后关怀。Redis 集群故障，`INCR` 超时。

| 步骤 | 输入 | 结果 |
| --- | --- | --- |
| 1 | `INCR m19:throttle:1001:20261021` 超时 50ms | 触发降级 |
| 2 | 查 `m19_care_touch` 中该患者当日 `result = 'SENT'` 的行数 | 得 `n = 1` |
| 3 | 医疗必要上限 2 | `1 ≤ 2`，`PASS` |
| 4 | 记录 `gate_freq_source = 'DB_FALLBACK'` | 便于事后统计降级频次 |
| 5 | 若降级查询也失败 | **不放行**，抑制 `MSG_SERVICE_DOWN` |

注意第 5 步：**降级不是放行。** Redis 挂了退到查库，查库也失败了必须拦截，不能「查不到就当作没有计数」。

#### 3.4.2 免打扰时段顺延模型

```text
输入：now（触发时刻）、quiet_start、quiet_end、delay_policy
输出：{ action: PASS | DEFER | CANCEL, next_at }

判定：
    if not quiet_enabled:                     action = PASS
    elif care_type in quiet_exempt_types:     action = PASS  (记 EXEMPT)
    elif not in_quiet_hours(now):             action = PASS
    elif delay_policy == 'CANCEL':            action = CANCEL
    else:
        action = DEFER
        next_at = quiet_end_date(now) + defer_offset_minutes + randint(0, jitter)

其中 quiet_end_date(now)：
    若 quiet_start > quiet_end（跨零点区间，如 21:00~08:00）：
        若 now.time() >= quiet_start   → 次日日期
        否则                            → 当日日期
    否则（同日区间）：                   → 当日日期

舍入：next_at 向上取整到分钟
失败条件：defer_count 已达 1 时再次判定为 DEFER → 强制改为 CANCEL
```

**为什么「顺延」而不是「取消」作为默认：**

生日关怀与节日关怀具有时点含义，但顺延到次日早上并不损失价值（患者 08:05 收到生日祝福仍是当月的生日祝福）。而召回与节日同理。反过来说，若默认取消，则所有在 21 点后生成的关怀都白跑，运营侧会强烈要求「放宽免打扰时段」，反而推高合规风险。**给一个合法的出口，比堵死它更能守住底线。**

唯一默认取消的场景是：顺延后已超过 `send_deadline_at`（例如节日关怀在节日次日后发送毫无意义）。

#### 3.4.3 频次计数模型

```text
计数键：m19:throttle:{patient_id}:{yyyyMMdd}
TTL   ：到当日 23:59:59 之后的第一个整点，即次日 00:00:59

计数流程：
    1. n = INCR key                        (原子自增)
    2. if n == 1: EXPIRE key <到次日 00:00:59 的剩余秒数>
    3. limit = medical_necessary ? freq_limit_medical : freq_limit_24h
    4. if n > limit: DECR key (回滚), 判定 BLOCK
    5. else: 判定 PASS

为什么 BLOCK 时要 DECR：
    自增把本次算进去了，若判定不通过却不回滚，则后续每次尝试都会因为
    「计数已超」而永远无法通过，即使次日部分名额本应可用。
回滚的一致性风险：
    INCR 与 DECR 之间若进程崩溃，计数会多 1（保守方向），
    表现为「少发一条」，不会「多发一条」——这是刻意选择的方向。
失败条件与降级：
    Redis 不可用 → 查 m19_care_touch 当日 result = 'SENT' 计数（DB_FALLBACK）
    查库也不可用 → 抑制，不放行
```

**算例：术后关怀重试时的频次处理。**

患者 E 当日已触达 1 次（医疗必要上限 2）。一次术后关怀任务提交发送，第 1 次失败（通道返回失败）。

| 步骤 | 计数 | 说明 |
| --- | --- | --- |
| 初次提交 | `INCR` → 2 | 2 ≤ 2，PASS，但通道失败 |
| 失败回执 | 不变 | 失败不扣减计数（消息已占用通道资源） |
| 重试第 2 次 | `INCR` → 3 | 3 > 2，BLOCK |

**这里有一个设计决策：失败后重试是否应该受频次限制？**

结论是**受限制**。理由：频次限制的目的是「不让患者一天内被反复打扰」，通道失败但患者端可能已经收到了（回执失败不等于未送达，短信网关的回执经常滞后或丢失）。若重试绕过频次限制，最坏情况下患者一天收到 2（上限）× 3（重试）= 6 条相同内容。因此重试也要过闸门，代价是「通道抖动时可能少发一条」，这个代价可以接受。

#### 3.4.4 召回优先得分模型

```text
score = 0.40 * norm_days + 0.30 * norm_amount + 0.20 * norm_gap + 0.10 * norm_recent

norm_days   = min(days_since_last_visit / 365, 1.0)
norm_amount = min(total_amount / 20000, 1.0)
norm_gap    = 1 - min(abs(days_since_last_visit - 90) / 180, 1.0)
norm_recent = 1 若最近 30 天无触达；否则 0

边界：
    - days_since_last_visit 为空 → norm_days = 1.0，norm_gap = 0
    - total_amount = 0 → norm_amount = 0
舍入：ROUND_HALF_UP 保留 6 位小数
```

**算例：**

患者 F：距上次到店 95 天，累计消费 8,600.00 元，最近 30 天无触达。

```text
norm_days   = min(95 / 365, 1)          = 0.260274
norm_amount = min(8600 / 20000, 1)      = 0.430000
norm_gap    = 1 - min(abs(95-90)/180,1) = 0.972222
norm_recent = 1.000000

score = 0.40*0.260274 + 0.30*0.430000 + 0.20*0.972222 + 0.10*1.000000
      = 0.104110 + 0.129000 + 0.194444 + 0.100000
      = 0.527554
```

**权重取值理由：** 「多久没来」权重最高（0.40），因为它与「需要重新验光配镜」的相关性最强；金额次之（0.30），因为它反映客户价值；窗口因子（0.20）把「刚过 90 天」的患者提前，这是因为验光周期普遍在 1~2 年，刚进入召回窗口的客户仍有可能只是想延后复查；最近触达惩罚（0.10）避免短时间内重复打扰。

#### 3.4.5 关怀与随访冲突消解模型

```text
输入：patient_id、care_type、拟发送日期 d
输出：CONFLICT | NO_CONFLICT

规则：
    if care_type != 'POSTOP' and care_type != 'FOLLOWUP':
        return NO_CONFLICT                 # 运营类关怀与随访不冲突
    tasks = get_pending_followup_tasks(patient_id)   # M03-04
    if 存在任务 t 满足 date(t.scheduled_at) == d:
        return CONFLICT
    if 存在任务 t 满足 t.created_at 在 [d-1, d] 且 t.status 在 (PENDING, ASSIGNED, EXECUTING):
        return CONFLICT
    return NO_CONFLICT

失败条件：
    M03-04 不可用且无缓存 → 视为 CONFLICT（保守）
    缓存 TTL：30 分钟
```

**为什么只对 POSTOP/FOLLOWUP 做冲突判定：** 生日关怀与随访在同一天发生并不冲突（一封「生日快乐」+ 一条「明天来复查」是合理的）。而术后关怀与术后随访内容高度重叠，同一天两条短信会让患者困惑，也浪费一次触达额度。

| 单据 | 编码规则 | 例 | 生成方式 | 唯一性 |

### 4.2 核心关系指引

- 规则（`m19_care_rule`）1 对多计划（`m19_care_plan`），计划 1 对多任务（`m19_care_task`）。
- 任务 1 对多触达记录（`m19_care_touch`），回执以追加方式写入，不更新原行。
- 频次规则（`m19_care_trial_rule`）在运行时按作用范围与优先级匹配，不与规则建立物理外键。
- 名单主档（`m19_care_recall_list`）1 对多明细（`m19_care_recall_item`），明细的 `patient_id` 组合计划后生成任务。
- 黑名单快照（`m19_care_blacklist_snapshot`）按任务关联，但**不允许作为黑名单的判断依据**。

| 查询场景 | 表 | 索引 | 说明 |
| --- | --- | --- | --- |

| --- | --- | --- | --- |

```text
  排除 - 已故                                12 人
  排除 - 近 180 天投诉                        86 人
  排除 - 已退订关怀类消息                    892 人

```

**复核流程：** 名单生成后状态为 `READY`，必须由运营主管在页面上点「复核通过」才能「下发到计划」。复核时可勾选个别患者手工排除（`eligibility` 改为 `EXCLUDED`，`exclude_flag` 记 `MANUAL_EXCLUDE`，写入操作日志）。

**为什么名单必须人工复核：** 召回是「主动联系一个可能已经不想被打扰的人」，算法无法理解个案（例如患者投诉过但记录在别的系统、患者家属去世）。复核这道人工关卡的作用不是提升效率而是**提供责任主体**——出了问题能追溯到「谁批准了这批名单」。

**数据来源标注：** 页面必须显示「数据截止 2026-10-20 23:00（T+1 汇总）」，并提示「名单生成后到实际发送之间患者可能已到店」。

**术后关怀的隐私准入（本页面最重要的功能）：**

| 检查项 | 检查时机 | 不通过时 |
| --- | --- | --- |
| 模板正文是否含临床词 | 规则启用时 + 每次发送前 | 规则不允许启用；已启用的规则在发送前拦截 |
| 模板变量是否全在白名单 | 每次任务生成时 | 抑制，`suppress_gate = 'TEMPLATE_PRIVACY'` |
| 变量值是否含数字型临床数据 | 每次任务生成时 | 抑制 |
| 文案是否显式包含「术后」二字 | 规则启用时提示 | 不拦截，但强制提示文案改造建议 |

**关于「术后」二字的强制提示：** 一条短信写「您好，术后恢复得怎么样？」——家属看到这条短信就知道患者做了手术。这是本子模块最容易被忽略的隐私泄露点：泄露的不是诊断名称，而是「发生过手术」这一事实本身。因此系统对 `care_type = 'POSTOP'` 的规则，在保存与启用时都提示推荐文案：

| 场景 | 禁止文案 | 推荐文案 |
| --- | --- | --- |
| 术后第 3 天问候 | 「您术后第 3 天，恢复得怎么样？」 | 「您好，这几天休息得还好吗？如有不适随时联系我们。」 |
| 术后复查提醒 | 「术后 1 周请回院复查术眼」 | 「按医生建议，近期可以安排一次回院检查，需要我们帮您预约吗？」 |
| 术后关怀 + 权益 | 「术后赠送您一次免费复查」 | 「感谢您的信任，为您准备了一次院内的关怀检查，欢迎预约。」 |

**为什么用「提示改造建议」而不是硬性拦截：** 硬性禁止「术后」二字会误伤大量正常表达（如「术后注意事项」在院内场景是正常用语），且模板归 M03-05 管理，本子模块不应替模板库做内容审核。系统能做的是：**在启用时用具体文案对比提示风险，在发送前用变量白名单做硬拦截。**

```text
│ 频次         640  (29.4%)   │ RULE_RECALL_90D 21,000  9.2%   0.8%     │
│ 免打扰       258  (11.8%)   │ RULE_BIRTHDAY   840     14.6%  0.2%     │
│ 随访冲突     160  (7.4%)    │ RULE_POSTOP     210     22.4%  0.0%     │
└──────────────────────────────────────────────────────────────────────┘
```

**指标定义表：**

| 指标 | 计算公式 | 分母为 0 时 | 数据来源 |
| --- | --- | --- | --- |
| 触达率 | `sent_count / task_count` | 显示「—」 | `m19_care_effect_daily` |
| 送达率 | `delivered_count / sent_count` | 显示「—」 | 同上 |
| 抑制率 | `suppressed_count / task_count` | 显示「—」 | 同上 |
| 转化率 | `conv_count / sent_count` | 显示「—」 | 同上 |
| 退订率 | `unsubscribe_count / sent_count` | 显示「—」 | 同上 |
| 单条成本 | `cost_cent_total / sent_count` | 显示「—」 | 同上 |

**关键设计：抑制原因必须与「效果」并列展示。**

如果只展示触达率和转化率，运营会倾向于「想办法把抑制率降下来」——而抑制率高往往说明闸门在正常工作。把抑制原因分布放在图表区同等位置，是为了让运营看到：**「退订/黑名单占 51.4%」说明我们发得太频或者人群不对，正确动作是改人群而不是去放宽闸门。**

**数据粒度为日：** 本页面所有数据来自 `m19_care_effect_daily`，无实时要求。页面顶部显示「数据更新至 2026-10-21 01:31」，当日数据在下一次汇总前不计入。

**口径版本提示：** 若查询区间内 `calc_version` 存在多个版本（说明期间调整过口径），页面顶部显示黄色提示「所选区间内口径发生过变更（v1 → v2），跨版本对比请谨慎」，并在趋势图上用虚线分隔点标注切换日。

### 6.2 统一响应格式与错误码

**成功响应：**

```json
{"code": "0", "message": "success", "data": {"task_no": "CT202611060001", "status": "PENDING"}, "trace_id": "c9f1a37e2b4d4e0f"}
```

**失败响应：**

```json
{"code": "1903005", "message": "任务或触达记录不存在", "detail": {"task_no": "CT202611060999"}, "trace_id": "c9f1a37e2b4d4e0f"}
```

**HTTP 状态码约定：**

| HTTP | 使用场景 | 说明 |
| --- | --- | --- |
| 200 | 查询成功、操作成功 | 业务错误在 `code` 中表达 |
| 201 | 资源创建成功 | 新建规则、生成名单 |
| 400 | 参数格式错误 | 字段校验失败、枚举非法 |
| 403 | 权限不足 | 缺少 `m19:care:*` 权限 |
| 404 | 资源不存在 | 规则/任务/名单不存在 |
| 409 | 状态冲突 | 乐观锁失败、任务状态不允许该操作 |
| 422 | 业务规则不满足 | 未填审批单号即启用、隐私白名单不通过 |
| 429 | 调用频率超限 | 内部契约被高频调用 |
| 503 | 上游不可用且必须 fail-closed | 黑名单校验失败导致保守拦截 |

**错误码号段：** M19-03 使用 `1903001`~`1903999`，本设计占用 `1903001`~`1903040` 共 40 个，从 001 连续无空号。完整定义见 6.6 节，**6.6 是唯一权威**。

#### API-01 GET /api/v1/m19/care/dashboard

**说明：** 关怀召回工作台指标卡与待处理事项。

```json
{"code": "0", "message": "success", "data": {"stat_date": "2026-11-06", "cards": {"task_total": 1284, "sent_total": 1102, "suppressed_total": 158, "failed_total": 24, "touch_rate": "0.858255", "suppress_rate": "0.123053", "conv_count": 96, "conv_rate": "0.087114"}, "pending_items": [{"item_type": "RECALL_REVIEW", "title": "召回名单待复核", "count": 2}, {"item_type": "POSTOP_REVIEW", "title": "术后关怀待隐私复核", "count": 5}, {"item_type": "GATE_ALERT", "title": "黑名单校验 fail-closed 次数偏高", "count": 12}], "type_distribution": [{"care_type": "RECALL", "task_count": 812, "suppressed_count": 112}, {"care_type": "BIRTHDAY", "task_count": 126, "suppressed_count": 18}]}, "trace_id": "c9f1a37e2b4d4e0f"}
```

2. 从 `m19_care_effect_daily` 读取 `stat_date` 当日合计行（`rule_code = '' AND care_type = '' AND channel = ''`）。
3. 若当日无汇总行（作业未跑完），实时聚合 `m19_care_touch` 并以 `data_quality = 'REALTIME'` 标记返回。
4. 组装待处理事项：待复核召回名单数量、术后关怀待复核数量、fail-closed 次数超阈值告警。
5. 按 `care_type` 分组返回分布。

**错误码：** `1903001`、`1903003`、`1903004`、`1903016`

**业务逻辑：**

1. 校验权限与字段格式。
2. `care_type` 必须是 §13 枚举值，非法返回 `1903001`。

6. 写入 `m19_care_rule`，`status = 'DRAFT'`。

#### P-09 POST /internal/v1/m19/care/trigger

**权限：** 内部服务（无用户上下文，校验 `X-Internal-Token` 与调用方白名单）
**说明：** 关怀触发内部契约。供 M10-08（视光会员运营）、M10-09（视光复查提醒）等模块批量触发关怀任务。**内部契约同样必须经过三道闸门。**

**请求参数：**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `care_type` | string | Y | 关怀类型，**必须是 §13 枚举值之一**，不接受自由文本 |
| `rule_code` | string | Y | 规则编码 |
| `channel` | string | N | 渠道，默认 `SMS` |
| `template_code` | string | Y | 模板编码 |
| `trigger_reason` | string | Y | 触发原因 |
| `trigger_no` | string | Y | 上游触发流水号，用于幂等 |
| `source_module` | string | Y | `M09` / `M10` / `M11` / `M16` / `M19` |
| `source_biz_no` | string | Y | 上游业务单号 |
| `scheduled_at` | string(datetime) | N | 计划时刻 |
| `targets` | array | Y | 目标患者列表，1~500 条 |

**`care_type` 合法取值（与共享规范 §13 一字不差）：**

```text
BIRTHDAY | RECALL | POSTOP | FOLLOWUP | ANNIVERSARY | HOLIDAY | OTHER
```

**响应示例：**

```json
{"code": "0", "message": "success", "data": {"trigger_no": "TRG2026110600018", "accepted_count": 468, "suppressed_count": 30, "duplicate_count": 2, "elapsed_ms": 213, "items": [{"patient_id": 88012, "task_no": "CT202611060041", "status": "PENDING", "accepted": true, "suppress_gate": null, "suppress_reason": null}, {"patient_id": 88013, "task_no": null, "status": "SUPPRESSED", "accepted": false, "suppress_gate": "BLACKLIST", "suppress_reason": "UNSUBSCRIBED"}]}, "trace_id": "c9f1a37e2b4d4e0f"}
```

**错误码：** `1903018`、`1903019`、`1903020`、`1903021`、`1903022`、`1903037`

**业务逻辑：**

1. 校验 `X-Internal-Token` 与调用方白名单，失败返回 `1903018`。
2. **`care_type` 枚举校验**：必须是 `BIRTHDAY` / `RECALL` / `POSTOP` / `FOLLOWUP` / `ANNIVERSARY` / `HOLIDAY` / `OTHER` 之一，否则返回 `1903022`。**绝不接受自由文本**——自由文本会让下游的医疗必要判定、免打扰豁免、频次上限全部失效（例如传 `POSTOP2` 就绕过了「只有 `POSTOP` 可豁免免打扰」的约束）。
3. 幂等校验：`(source_module, trigger_no)` 已处理则返回上次结果，Redis key `m19:idem:care:{source_module}:{trigger_no}` TTL 24 小时。
4. `targets` 数量 1~500，超限返回 `1903019`。
5. **模板变量白名单校验**：任何非白名单键返回 `1903020`。
6. 批量闸门一：一次 RPC 覆盖全批（最多 500 人）；上游不可用**全部 fail-closed**，返回 `1903021`（HTTP 503），messages 明确「本次未处理任何患者，可稍后重试」。
7. 闸门二：免打扰判定，术后类可豁免，其余顺延。
8. 闸门三：Redis 频次计数，Redis 不可用降级查 `m19_care_touch` 当日计数。
9. 随访冲突判定：与 M03-04 当日随访任务去重。
10. 落 `m19_care_task` + `m19_care_touch`（抑制的也落触达记录）+ `m19_care_oper_log`，同一事务。
11. **性能 P95 ≤ 300ms**：闸门一单次 RPC 覆盖全批，闸门三用 Redis Pipeline；实测 500 目标约 210ms。调用频率超 60 次/分钟返回 `1903037`。
12. 返回逐人结果，调用方按 `items` 决定展示。

**6.5.1 三道闸门判定（`CareGateService.evaluate`）**

```python
"""三道闸门判定 · 任何对外触达的唯一入口"""
from dataclasses import dataclass
from datetime import datetime, timedelta
import random

from app.clients.message_client import MessageClient
from app.core.errors import BizError
from app.core.redis import redis_client

GATE_PASS = "PASS"
GATE_BLOCK = "BLOCK"
GATE_FAIL_CLOSED = "FAIL_CLOSED"
GATE_EXEMPT = "EXEMPT"
GATE_DEFER = "DEFER"

TOUCH_KEYWORDS_BLOCKED = (
    "手术", "术后", "术眼", "屈光", "白内障", "晶体", "近视手术", "角膜手术",
)


@dataclass
class GateVerdict:
    passed: bool
    gate: str
    reason: str
    gate_seq: str
    defer_to: datetime | None = None
    freq_source: str = ""
    freq_used: int = 0
    freq_limit: int = 0


class CareGateService:
    async def evaluate(
        self,
        patient_id: int,
        care_type: str,
        channel: str,
        medical_necessary: bool,
        quiet_exempt: bool,
        freq_limit: int,
        now: datetime,
        blacklist_timeout_ms: int = 800,
    ) -> GateVerdict:
        seq_parts: list[str] = []

        # ---- 闸门第 0 道：会员状态（非合规闸门，降级不 fail-closed）----
        member = await self._read_member_with_fallback(patient_id)
        if member.get("status") == "CANCELLED":
            return GateVerdict(
                passed=False, gate="MEMBER", reason="MEMBER_CANCELLED",
                gate_seq="MEMBER:BLACKLIST",
            )
        seq_parts.append("MEMBER:" + (GATE_PASS if member.get("available") else "DEGRADED"))

        # ---- 闸门一：退订 / 黑名单（合规闸门，必须 fail-closed）----
        try:
            verdict = await MessageClient.check_blacklist(
                patient_id=patient_id, channel=channel, timeout_ms=blacklist_timeout_ms,
            )
        except Exception:
            # 宁可全不发：查不到就当对方拒绝
            return GateVerdict(
                passed=False, gate="BLACKLIST", reason="MSG_SERVICE_DOWN",
                gate_seq=">".join(seq_parts + ["BLACKLIST:FAIL_CLOSED"]),
            )
        if verdict["blocked"]:
            reason = "UNSUBSCRIBED" if verdict["kind"] == "UNSUBSCRIBE" else "BLACKLISTED"
            return GateVerdict(
                passed=False, gate="BLACKLIST", reason=reason,
                gate_seq=">".join(seq_parts + ["BLACKLIST:BLOCK"]),
            )
        seq_parts.append("BLACKLIST:PASS")

        # ---- 闸门二：免打扰时段 ----
        if self._in_quiet_hours(now) and not (quiet_exempt and care_type == "POSTOP"):
            defer_to = self._next_allowed_at(now)
            # 顺延不是丢弃：任务保持 PENDING，只是改期
            seq_parts.append("QUIET:DEFER")
            return GateVerdict(
                passed=False, gate="QUIET_HOURS", reason="QUIET_HOURS_DEFER",
                gate_seq=">".join(seq_parts), defer_to=defer_to,
            )
        seq_parts.append("QUIET:EXEMPT" if quiet_exempt and care_type == "POSTOP" else "QUIET:PASS")

        # ---- 闸门三：频次（Redis 主，DB 降级）----
        limit = 2 if medical_necessary else 1
        limit = min(limit, freq_limit or limit)
        used, source = await self._incr_freq(patient_id, now)
        if used > limit:
            seq_parts.append("FREQ:BLOCK")
            return GateVerdict(
                passed=False, gate="FREQUENCY", reason="FREQUENCY_LIMIT",
                gate_seq=">".join(seq_parts), freq_source=source,
                freq_used=used, freq_limit=limit,
            )
        seq_parts.append("FREQ:PASS")
        return GateVerdict(
            passed=True, gate="", reason="", gate_seq=">".join(seq_parts),
            freq_source=source, freq_used=used, freq_limit=limit,
        )

    @staticmethod
    def _in_quiet_hours(now: datetime) -> bool:
        """免打扰窗口 21:00 ~ 次日 08:00，窗口跨零点必须用 OR 而不是 AND。"""
        t = now.time()
        return t >= datetime.strptime("21:00", "%H:%M").time() or t < datetime.strptime(
            "08:00", "%H:%M"
        ).time()

    @staticmethod
    def _next_allowed_at(now: datetime) -> datetime:
        """顺延到次日 08:00 之后 5 分钟，再加 0~30 分钟随机抖动。"""
        base = (now + timedelta(days=1)).replace(
            hour=8, minute=5, second=0, microsecond=0
        )
        if now.hour < 8:
            base = now.replace(hour=8, minute=5, second=0, microsecond=0)
        return base + timedelta(minutes=random.randint(0, 30))

    async def _incr_freq(self, patient_id: int, now: datetime) -> tuple[int, str]:
        """Redis 主路径；Redis 不可用时降级查 m19_care_touch 当日计数。

        降级绝不能返回 0 放行——那等于「Redis 一挂就无限发送」。
        """
        key = f"m19:throttle:{patient_id}:{now:%Y%m%d}"
        try:
            pipe = redis_client.pipeline()
            pipe.incr(key)
            pipe.expireat(key, int((now + timedelta(days=1)).timestamp()))
            used, _ = pipe.execute()
            return int(used), "REDIS"
        except Exception:
            used = await self._count_today_touch(patient_id, now)
            # 降级时 +1，本次发送也要计入，避免同一次重复放行
            return used + 1, "DB_FALLBACK"
```

**6.5.2 被抑制时的落库（`CareTaskService.suppress`）**

```python
"""抑制落库：五张表同一事务，缺一张就是缺一环证据"""
from sqlalchemy.ext.asyncio import AsyncSession

from app.models.m19.care import CareTask, CareTouch, CareOperLog

GATE_TO_REASON = {
    "MEMBER": {"MEMBER_CANCELLED"},
    "BLACKLIST": {"UNSUBSCRIBED", "BLACKLISTED", "MSG_SERVICE_DOWN"},
    "QUIET_HOURS": {"QUIET_HOURS_CANCEL", "QUIET_HOURS_DEFER"},
    "FREQUENCY": {"FREQUENCY_LIMIT"},
    "TEMPLATE_PRIVACY": {"PRIVACY_VIOLATION"},
    "CONFLICT_WITH_FOLLOWUP": {"FOLLOWUP_CONFLICT"},
}


async def suppress_task(
    db: AsyncSession,
    task: CareTask,
    touch: CareTouch,
    verdict,
    operator_id: int | None = None,
) -> None:
    # 组合约束的代码侧守门：闸门与原因必须成对，否则数据库 CHECK 会拒绝
    if verdict.reason not in GATE_TO_REASON.get(verdict.gate, set()):
        raise ValueError(
            f"抑制闸门 {verdict.gate} 与原因 {verdict.reason} 不匹配，已拒绝落库"
        )
    task.status = "SUPPRESSED"
    task.suppress_gate = verdict.gate
    task.suppress_reason = verdict.reason
    # SUPPRESSED 任务绝不允许带消息任务号——否则就是「先发后补记抑制」的伪造证据
    task.msg_task_no = None
    task.delivered_at = None
    touch.result = "SUPPRESSED"
    touch.suppress_gate = verdict.gate
    touch.suppress_reason = verdict.reason
    touch.gate_seq = verdict.gate_seq
    db.add(task)
    db.add(touch)
    db.add(
        CareOperLog(
            object_type="TASK",
            action="SUPPRESS",
            operator_id=operator_id,
            operate_source="SCHEDULER",
            change_summary=f"{verdict.gate} / {verdict.reason}",
        )
    )
    await db.commit()
```

**6.5.3 P-09 批量触发（`CareService.care_trigger`）**

```python
"""P-09 关怀触发：批量闸门 + 幂等 + 三道闸门全过"""
import hashlib
import json

from app.core.errors import BizError
from app.core.redis import redis_client

ALLOWED_CARE_TYPES = frozenset(
    {"BIRTHDAY", "RECALL", "POSTOP", "FOLLOWUP", "ANNIVERSARY", "HOLIDAY", "OTHER"}
)
MAX_TARGETS = 500


async def care_trigger(self, payload, caller: str) -> dict:
    # 1) care_type 必须是 §13 枚举，绝不接受自由文本
    if payload.care_type not in ALLOWED_CARE_TYPES:
        raise BizError(
            code="1903022",
            message=f"care_type 非法：{payload.care_type}，必须是 {sorted(ALLOWED_CARE_TYPES)}",
        )
    # 2) 目标数量
    if not 1 <= len(payload.targets) <= MAX_TARGETS:
        raise BizError(code="1903019", message=f"targets 数量必须 1~{MAX_TARGETS}")

    # 3) 幂等：同一上游触发号只处理一次
    idem_key = f"m19:idem:care:{payload.source_module}:{payload.trigger_no}"
    if not redis_client.set(idem_key, "1", nx=True, ex=86400):
        return await self._load_previous_result(payload)

    # 4) 变量白名单（任何非白名单键都拒绝整批）
    for target in payload.targets:
        bad = set(target.variables) - ALLOWED_VAR_KEYS
        if bad:
            raise BizError(code="1903020", message=f"模板变量超出白名单：{sorted(bad)}")

    # 5) 批量闸门一：一次 RPC 覆盖全批；上游不可用则全批 fail-closed
    try:
        blacklist = await MessageClient.check_blacklist_batch(
            patient_ids=[t.patient_id for t in payload.targets],
            channel=payload.channel,
            timeout_ms=800,
        )
    except Exception as exc:
        raise BizError(
            code="1903021",
            message="黑名单上游不可用，本次未处理任何患者，请稍后重试",
            http_status=503,
        ) from exc

    # 6) 闸门二 / 闸门三逐人判定，闸门三走 Redis Pipeline
    results = []
    now = payload.scheduled_at or datetime.now()
    pipe = redis_client.pipeline()
    for target in payload.targets:
        pipe.incr(f"m19:throttle:{target.patient_id}:{now:%Y%m%d}")
    counters = pipe.execute() if payload.targets else []

    for idx, target in enumerate(payload.targets):
        verdict = self._combine_verdict(
            blacklist=blacklist[target.patient_id],
            freq_used=counters[idx],
            care_type=payload.care_type,
            now=now,
        )
        results.append(await self._persist_trigger(target, payload, verdict))
    return self._build_trigger_result(payload, results)
```

| `m19:care:trial:{seq}` | Hash | 30 分钟 | 频次与免打扰规则缓存 | 回源 `m19_care_trial_rule`，慢但正确 |
| `m19:care:alert:failclosed:{yyyyMMdd}` | String | 24 小时 | fail-closed 次数告警计数 | 告警延迟到下一窗口 |

**频次计数键不使用 `m19:care:` 前缀**，而是共享规范 §14 统一规定的 `m19:throttle:{patient_id}:{yyyyMMdd}`。原因：频次闸门是跨子模块的（M19-02 随访、M19-05 权益通知都要计数），共用同一键空间才能做到「一个患者当天所有触达合起来不超过 N 次」。若各子模块用自己的前缀，患者当天可能收到 1 条关怀 + 1 条随访 + 1 条权益通知 = 3 条，而每条都「合规」。

| 键模式 | 类型 | TTL | 说明 |
| --- | --- | --- | --- |
| `m19:throttle:{patient_id}:{yyyyMMdd}` | String(计数) | 至当日 23:59:59 | **跨子模块共用**的触达频次计数 |
| `m19:throttle:lock:{patient_id}:{yyyyMMdd}` | String | 5 秒 | 降级路径的互斥，防止并发窗口内重复放行 |

### 7.2 Redis 不可用的降级方向

**核心原则：降级的方向必须是「打扰更少」，不能是「校验更松」。**

**通则（M19-03 全子模块适用，可直接引用）：**

> **闸门的失败方向必须朝「少打扰」，不能朝「多放行」；但闸门本身不能因为上游抖动而变成阻断整个业务——否则会催生绕过闸门的开关，最终比降级更糟。**

这条通则有两半，缺一半就会走向两个相反的坑：

| 只记住前半（永远 fail-closed） | 只记住后半（总是降级放行） | 两半都记住 |
| --- | --- | --- |
| M03-03 抖 10 分钟，全院关怀停 2 小时；运营被迫要求加「跳过闸门」开关，开关一旦存在，最严的闸门也形同虚设 | 「查不到就不算退订」，一次上游超时就把营销短信发给已退订患者，直接构成合规事故 | 按「闸门保护的是谁的权益」分流：保护**患者意愿**的闸门 fail-closed，保护**账户可用性/数据完整性**的闸门降级到更低打扰的渠道 |

**怎么判断该用哪一半——按闸门保护的对象分类：**

| 闸门 | 保护对象 | 失败方向 | 依据 |
| --- | --- | --- | --- |
| 闸门一 退订/黑名单 | **患者意愿**（明确拒绝） | **fail-closed**，全部不发 | 猜错的代价是给明确拒绝过的人发消息，不可撤回 |
| 闸门二 免打扰 | **患者安宁** | 顺延到更晚（打扰更少） | 猜错的代价只是晚几小时送达 |
| 闸门三 频次 | **患者安宁** | 降级查库；查库也失败则拦截 | 猜错的代价是当天多一条无关紧要却可能引爆投诉的消息 |
| 闸门第 0 道 会员状态 | **账户可用性**（不是意愿） | 降级为仅 `INBOX` 站内信 | 猜错的代价是一条可撤回、无打扰的站内信 |
| 模板隐私校验 | **患者隐私** | 不允许发送 | 猜错的代价是病历信息外泄，不可撤回 |

判据一句话：**「猜错的代价能不能撤回、会不会打扰患者」——能撤回且更安静的，降级；不能撤回或会打扰的，关闭。**

**为什么「阻断整个业务」本身就是风险：** 任何被设计成「频繁阻断」的闸门，都会在使用者那里被当成障碍而不是保护，进而促成一个逃生口（开关、白名单、临时跳过）。逃生口一旦存在就必然被滥用，且它绕过的不只是那一道闸门，而是「所有闸门都要过」这条纪律。**做过严的失败关闭，最终得到的不是更严的控制，而是一个更松的后门。**

| 键 | 不可用时行为 | 是否放行 | 理由 |
| --- | --- | --- | --- |
| 频次计数键 | 改查 `m19_care_touch` 当日计数（`gate_freq_source = 'DB_FALLBACK'`），并把本次 +1 计入 | 按库内计数判定 | 库内计数是同一事实的另一份记录。**绝不允许「Redis 挂了就返回 0 放行」**——那是给无限发送开后门 |
| 幂等键 | 退化为查库（`m19_care_task` 中 `biz_no + trigger_reason` 是否已存在） | 保守拒绝重复 | 宁可拒绝一次真实请求，不可重复发送 |
| 会员状态缓存 | 回源 M03-03；M03-03 也不可用则**只允许 `INBOX` 站内信** | 降级放行（限制渠道） | 会员状态不是合规闸门，见 4.14.5 论证 |
| 规则缓存 | 回源数据库 | 放行 | 配置读失败不影响闸门判定 |
| 流水键 | 改用数据库序列兜底并告警 | 放行 | 编码冲突由唯一约束拦截 |

### 7.3 Celery 异步任务

| 任务名 | 队列 | 触发 | 周期/超时 | 说明 |
| --- | --- | --- | --- | --- |
| `care_recall_build` | `m19.care.batch` | API-13 投递 | 超时 600 秒 | 召回名单构建，S1~S5 + 6 类排除 |
| `care_task_dispatch` | `m19.care.send` | APScheduler 每 1 分钟 | 超时 60 秒 | 扫描 `scheduled_at <= now` 的 `PENDING` 任务并逐条过闸门发送 |
| `care_defer_release` | `m19.care.send` | APScheduler 每 5 分钟 | 超时 60 秒 | 释放 `gate_quiet_result = 'DEFER'` 且 `defer_to_at <= now` 的任务，重新过闸门 |
| `care_receipt_pull` | `m19.care.sync` | APScheduler 每 10 分钟 | 超时 120 秒 | 从 M03-05 拉取发送回执，追加回执行（不 UPDATE） |
| `care_effect_rollup` | `m19.care.batch` | APScheduler 每日 01:30 | 超时 900 秒 | 汇总前一日效果到 `m19_care_effect_daily` |
| `care_birthday_sync` | `m19.care.sync` | APScheduler 每日 02:10 | 超时 300 秒 | 比对当日/次日生日名单的出生日期，差异置 `birthday_changed` |
| `care_partition_maintain` | `m19.care.batch` | APScheduler 每月 25 日 03:00 | 超时 600 秒 | 预建下月分区，检查 DEFAULT 分区是否非空（非空即告警） |
| `care_snapshot_purge` | `m19.care.batch` | APScheduler 每日 04:00 | 超时 300 秒 | 清理 90 天前的 `m19_care_blacklist_snapshot.raw_response`（含手机号） |
| `care_throttle_reconcile` | `m19.care.sync` | APScheduler 每日 05:00 | 超时 300 秒 | 比对 Redis 计数与库内计数，偏离超 3 次告警（`1903035`） |

**任务重试策略：** 除 `care_task_dispatch` 外，其余任务失败重试 3 次，间隔 60/300/900 秒。`care_task_dispatch` **不自动重试**——发送失败由 `m19_care_task.send_attempts` 驱动，最多 3 次，且每次重试都要重新过频次闸门。

**为什么 `care_task_dispatch` 不自动重试：** Celery 自动重试是无条件的，而消息已送达上游时重试会造成重复发送。发送重试必须走 `send_attempts` 这条有上限、有闸门、有审计的路径。

### 7.4 频率互斥与并发

| 场景 | 机制 | 说明 |
| --- | --- | --- |
| 同一名单重复投放 | Redis 锁 `m19:care:lock:{list_no}` + 状态机 | 双保险：锁防并发，`status` 防串行重复 |
| 同一任务重复发送 | Redis 锁 + `send_attempts` 上限 | 锁 TTL 30 秒，超时自动释放避免死锁 |
| 频次计数并发 | Redis `INCR` 原子性 | 降级路径用 5 秒互斥锁保护「读库-判断-写库」窗口 |
| 规则配置并发修改 | 数据库乐观锁 `version` | 冲突返回 `1903006` |

## 8. 业务规则与校验

### 8.1 编码规则

| 对象 | 规则 | 示例 | 唯一性约束 |
| --- | --- | --- | --- |
| 关怀计划号 | `CP` + `yyyyMMdd` + 3 位流水 | `CP20261106001` | `(plan_no, is_deleted)` 唯一 |
| 关怀任务号 | `CT` + `yyyyMMdd` + 4 位流水 | `CT202611060001` | `(task_no, is_deleted)` 唯一 |
| 关怀触达号 | `CT` + `yyyyMMdd` + 4 位流水 | `CT2026110600012` | `(touch_no, created_at)` 唯一 |
| 召回名单号 | `RL` + `yyyyMMdd` + 3 位流水 | `RL20261106001` | `(list_no, is_deleted)` 唯一 |
| 黑名单快照号 | `BS` + `yyyyMMdd` + 6 位流水 | `BS2026110600123456` | `(snapshot_no, created_at)` 唯一 |
| 规则编码 | `RULE_` + 大写字母数字下划线 | `RULE_RECALL_90D` | `rule_code` 唯一 |

**任务号与触达号共用 `CT` 前缀和同一流水池：** 一条任务在正常发送时只产生一条触达记录，两者号相同；重试或回执行会再产生触达记录，号不同但任务号相同。共用前缀让「看单号就知道是什么」这条运维直觉成立——`CT` 开头的一定是「一条给患者的消息」。

**流水生成：** Redis `INCR m19:care:code:{prefix}:{yyyyMMdd}`，TTL 至次日 00:05。禁止用数据库序列拼日期——序列不会按日重置，且跨库不一致。

### 8.2 唯一性规则

| --- | --- | --- |
| `(rule_code, is_deleted)` | `m19_care_rule` | 两条规则同编码，调度器重复执行 |
| `(rule_code, plan_date, source_batch_no, is_deleted)` | `m19_care_plan` | 同一规则同日同来源生成两期计划，患者被重复打扰 |

| `(throttle_no)` | `m19_care_trial_rule` | 频次规则编码重复 |

### 8.3 状态流转规则

**任务状态机（六态）：**

```text
                    ┌──────────────────────────────────────┐
                    │                                      │
   [创建] ──► PENDING ──过闸门──► SENDING ──受理──► DELIVERED
                │  │                  │
                │  └──闸门拦截──► SUPPRESSED（终态）
                │                     │
                └──运营取消──► CANCELLED（终态）
                                      │
                     SENDING ──失败──► FAILED ──重试──► PENDING
                                      │
                                      └──超 3 次──► 终态
```

| 编号 | 从 | 到 | 条件 | 副作用 |
| --- | --- | --- | --- | --- |
| T-01 | （无） | `PENDING` | 计划生成或契约触发 | 写 `m19_care_task` |
| T-02 | `PENDING` | `SENDING` | 调度器取到任务并已过全部闸门 | 占用频次计数 |
| T-03 | `SENDING` | `DELIVERED` | M03-05 返回受理成功 | 写 `msg_task_no`、`delivered_at` |
| T-04 | `SENDING` | `FAILED` | M03-05 返回失败或超时 | 写 `fail_code`、`fail_reason` |
| T-05 | `PENDING` | `SUPPRESSED` | 任一闸门不过 | 写 `suppress_gate` + `suppress_reason`，**不得有 `msg_task_no`** |
| T-06 | `PENDING` | `CANCELLED` | 运营取消或规则停用 | 回滚频次计数 |
| T-07 | `FAILED` | `PENDING` | 运营重试且 `send_attempts < 3` | 重新过频次闸门 |
| T-08 | `PENDING` | `PENDING`（顺延） | 闸门二免打扰 | 更新 `defer_to_at`、`defer_count` +1 |
| T-09 | `SUPPRESSED` | —— | **禁止任何流转** | 抑制是终态 |

**禁止流转（必须在代码层显式拒绝）：**

| 编号 | 禁止流转 | 理由 | 错误码 |
| --- | --- | --- | --- |
| F-01 | `SUPPRESSED` → `PENDING` | 这是「重试绕过闸门」的后门 | `1903013` |
| F-02 | `DELIVERED` → 任何状态 | 已送达不可撤回 | `1903013` |
| F-03 | `SENDING` → `CANCELLED` | 消息已提交上游，撤回会造成状态不一致 | `1903013` |
| F-04 | `CANCELLED` → `PENDING` | 取消是终态 | `1903013` |
| F-05 | `defer_count` 超过 1 | 顺延只能发生一次，避免「无限顺延」变成永不发送 | `1903026` |

### 8.5 计算规则与舍入

| 指标 | 公式 | 舍入 | 分母为 0 |
| --- | --- | --- | --- |
| 触达率 | `sent_count / task_count` | 保留 6 位小数，四舍五入（ROUND_HALF_UP） | 返回 NULL，页面显示「—」 |
| 送达率 | `delivered_count / sent_count` | 同上 | 返回 NULL |
| 抑制率 | `suppressed_count / task_count` | 同上 | 返回 NULL |
| 转化率 | `conv_count / sent_count` | 同上 | 返回 NULL |
| 召回得分 | 四项加权归一化求和 | 保留 6 位小数 | 单项归一化时分母为 0 记 0 |
| 单条成本 | `cost_cent_total / sent_count` | 分为单位取整 | 返回 NULL |

**输出格式：** 比率字段一律以字符串返回，保留 6 位小数（如 `"0.858255"`），避免前端浮点精度问题。金额以字符串返回保留 2 位小数。

### 8.6 引用与删除

| 规则 | 说明 |
| --- | --- |
| 触达记录不可删除 | `REVOKE UPDATE, DELETE`，合规举证依据 |

| 操作日志不可删除 | 只增不改 |

| 名单逻辑删除 | `status = 'ARCHIVED'`，不物理删除 |
| 任务不可删除 | 只改状态 |

### 8.7 并发控制

| 场景 | 机制 | 失败表现 |
| --- | --- | --- |
| 规则编辑 | 数据库 `version` 乐观锁 | `1903006` |

### 9.4 安全措施

| 措施 | 说明 |
| --- | --- |
| 手机号脱敏 | 列表与详情一律 `138****5678`；完整号码需 `m19:care:view_phone`，且每次调用写审计日志 |

## 11. 异常处理与日志

### 11.1 异常分类

| 类别 | 典型异常 | 处理策略 | 是否告警 |
| --- | --- | --- | --- |
| 参数类 | 字段格式错误、枚举非法 | 返回 `1903001` 等 4xx，不重试 | 否 |
| 状态类 | 乐观锁冲突、状态不允许 | 返回 409，前端提示刷新 | 否 |
| 闸门类 | 被闸门拦下 | **不是异常**，走 `SUPPRESSED` 正常落库 | 仅 fail-closed 告警 |
| 上游类 | M03-05 / M03-03 超时 | 按 10.1 表的降级策略 | 是（连续 5 次） |
| 数据类 | 分区缺失、唯一键冲突 | 返回 5xx，任务进重试队列 | 是 |
| 系统类 | Redis 不可用、数据库连接池耗尽 | 降级或熔断 | 是（P1） |

**关键区分：「被闸门拦下」不是异常。** 它是正常业务结果，必须写 `SUPPRESSED` 而不是抛错。如果把抑制当异常处理，任务会进入重试队列，重试就意味着重新过闸门——一个被退订的患者会被反复判定反复记录，最终在报表上表现为「抑制率高」，运营的正确推断就变成了「闸门太严」，而不是「这些人确实不想收到消息」。

### 11.2 降级策略

| 依赖 | 降级动作 | 降级后的行为 | 恢复条件 |
| --- | --- | --- | --- |
| M03-05 黑名单校验 | **fail-closed** | 全部判定为抑制，`suppress_reason = 'MSG_SERVICE_DOWN'` | 连续 3 次成功探测 |
| M03-05 消息发送 | 转 `INBOX` 站内信 | 渠道降级，仍受频次闸门约束 | 连续 3 次成功探测 |
| M03-05 模板接口 | 拒绝发送 | 隐私扫描无法完成就不能发，`1903014` | 恢复即用 |
| M03-03 会员状态 | 仅允许 `INBOX` | 降级渠道 | 恢复后回源 |
| M03-04 随访待办 | 任务保持 `PENDING` | 本轮不判定冲突，下一轮重判 | 恢复后重判 |
| Redis | 查库计数 | `gate_freq_source = 'DB_FALLBACK'` | Redis 恢复 |
| M02 审计外送 | 本地日志保底 | 异步补发 | 恢复后补发 |

**降级方向的统一判据：** 任何降级都必须让「打扰更少」或「风险更低」。凡是降级后变得更宽松的方案，一律不采用。

**与 7.2 通则的关系：** 本节给出的是「具体依赖挂了怎么降」，通则给出的是「依据什么决定降不降」。判据可归纳为一句：**保护患者意愿与患者隐私的闸门 fail-closed，保护账户可用性与数据完整性的闸门降级到更低打扰的渠道；但任何一路降级都不得让整个业务停摆——停摆会催生绕过闸门的开关，比降级更糟。**

### 11.3 日志格式

```json
{"ts": "2026-11-06T18:20:11.412+08:00", "level": "INFO", "trace_id": "c9f1a37e2b4d4e0f", "module": "M19-03", "event": "care_gate_evaluated", "task_no": "CT202611060035", "patient_id": 88012, "care_type": "POSTOP", "gate_seq": "MEMBER:PASS>BLACKLIST:PASS>QUIET:EXEMPT>FREQ:PASS", "freq_source": "REDIS", "freq_used": 1, "freq_limit": 2, "elapsed_ms": 42, "result": "PASS", "phone_mask": "138****5678"}
```

**日志脱敏红线：**

| 字段 | 是否可入日志 | 处理 |
| --- | --- | --- |
| `patient_id` / `member_id` | 可以 | 原值 |
| 姓名 | 不可以 | 不记录 |
| 手机号 | 仅可脱敏 | `phone_mask` 形式 |
| 身份证号 | 不可以 | 不记录 |
| 诊断 / 手术方式 / 术眼 | 不可以 | 不记录 |
| 模板正文 | 不可以 | 只记 `template_code` 与 `template_var_hash` |
| 闸门轨迹 `gate_seq` | 可以 | 原值，排障核心字段 |
| 抑制原因 | 可以 | 原值 |

### 11.4 监控指标

| 指标名 | 类型 | 说明 | 告警阈值 |
| --- | --- | --- | --- |
| `care_task_created_total` | Counter | 任务创建数（按 care_type） | — |
| `care_touch_sent_total` | Counter | 实际发送数 | — |
| `care_suppressed_total` | Counter | 抑制数（按 gate） | 抑制率 > 40% 持续 1 小时 |
| `care_failclosed_total` | Counter | fail-closed 次数 | 单次 5 分钟内 > 10 次 |
| `care_failclosed_ratio` | Gauge | fail-closed / 总判定 | > 0.01 |
| `care_gate_elapsed_ms` | Histogram | 闸门判定耗时 | P95 > 200ms |
| `care_trigger_elapsed_ms` | Histogram | P-09 端到端耗时 | P95 > 300ms |
| `care_send_failed_total` | Counter | 发送失败数 | 失败率 > 5% |
| `care_freq_fallback_total` | Counter | 频次闸门降级次数 | 单次 5 分钟内 > 5 次 |
| `care_unsubscribe_total` | Counter | 退订回执数 | 退订率 > 2% |
| `care_partition_default_rows` | Gauge | DEFAULT 分区行数 | > 0 |
| `care_redis_errors_total` | Counter | Redis 异常数 | > 0 持续 5 分钟 |

**为什么 `care_failclosed_ratio` 要单独告警：** fail-closed 是安全行为，但持续 fail-closed 意味着「关怀全线停发」。如果只监控「发送失败」，fail-closed 的表现是「成功抑制」，看起来一切正常，实际业务已经停摆。这条指标是「安全机制变成业务事故」的唯一预警。

### 附录 B.1 全模块禁用枚举值（书面约定，不依赖校验器）

M19 全模块的**状态类字段**（`status`、`task_status`、`plan_status` 等）**禁止使用下列三个值**：

| 禁用值 | 应改用 | 原因 |
| --- | --- | --- |
| `DONE` | `COMPLETED` | 与 M03-04 随访任务的 7 态集合不一致，跨模块联表时语义漂移 |
| `FINISHED` | `COMPLETED` | 同上。本项目实际踩过一次：把它写进计划完成态，校验器报「随访状态枚举自创」 |
| `EXECUTED` | `COMPLETED` 或 `EXECUTING` | 同上，且与 `EXECUTING`（执行中）极易混淆 |

**约束条款：**

1. 本约定是**书面规范**，适用范围覆盖 M19 全部子模块（M19-01 ~ M19-08）。
2. **不得只依赖 `validate_m19.py` 兜底。** 校验器对这三个词的检查依赖 `check_followup_enum` 的上下文判定，该规则已收窄为「命中随访任务独有特征（出现 `EXECUTING`/`OVERDUE`/`ASSIGNED`，或恰好 7 个值且同时含 `PENDING`/`COMPLETED`/`CANCELLED`，或 `status` 片段前 200 字内出现 `followup`）」时才触发；**用本子模块的六态写法（`PENDING`/`SENDING`/`DELIVERED`/`FAILED`/`CANCELLED`/`SUPPRESSED`）时不会命中该规则，因此这三个词写错了校验器也不会报。**
3. 评审时的检查方式：`grep -nE "\b(DONE|FINISHED|EXECUTED)\b" <文件>`，任何命中都须人工确认其用途——出现在「禁用说明」正文本表中属正常，出现在枚举定义、CHECK 约束、状态赋值、枚举字面量中即为缺陷。
4. 反向要求：新增状态值时，必须先在 `00_M19_随访与会员管理_模块设计_共享规范与文档模板.md` §13 公共枚举登记，再落到本子模块；**不得在本子模块自行发明状态值**。

**S 级决策明细（三项最不可协商的安全约束，每一项都直接决定证据是否可伪造、隐私是否泄露）：**

| 编号 | 约束 | 落点 | 为什么它是 S 级 |
| --- | --- | --- | --- |
| S-1 | **`SUPPRESSED` 任务不得有 `msg_task_no` / `delivered_at`** | `m19_care_task` 组合约束 `ck_m19_care_task_suppressed_no_send`；`m19_care_touch` 组合约束 `ck_m19_care_touch_suppressed` | 缺了这条，任何有写权限的人都能把真实的发送记录改写成「我们拦住了」，**把一条真实的违规发送伪造为合规证据**。这已不是状态枚举问题，而是审计证据不可伪造问题——比任何流程规范都更根本 |
| S-2 | **`decision='PASS'` 强制 `upstream_available=TRUE`** | `m19_care_blacklist_snapshot` 组合约束 `ck_m19_care_blacklist_snapshot_pass` | 用数据库约束禁止「没查到却说查过了」。上游超时但判定放行时，日志里 `PASS` 完全看不出这是降级放行；把「查到没被拦」与「没查到所以拦下」在数据层强制分开，事后追查才有据可依 |
| S-3 | **正文手术词扫描（白名单之外的第二道静态闸门）** | 5.6、API-21、API-20 复核前重扫 | 变量全部合法时文案照样能泄露：「张**女士，您术后第 7 天恢复得怎么样？」一个白名单变量都没违规。**泄露可以完全发生在模板的静态文本里**，这不是白名单设计得不好，而是白名单的作用域本身覆盖不到模板正文 |
