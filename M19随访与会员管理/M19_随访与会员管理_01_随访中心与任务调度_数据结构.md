### 数据范围声明（先读这一节再读表定义）

本文档**不定义**任何随访任务、随访计划、随访模板、随访节点、分派规则的表。这些数据的生产方是 M03-04，对应 `mpi_followup_template`、`mpi_followup_template_node`、`mpi_followup_plan`、`mpi_followup_task`、`mpi_followup_assign_rule` 等 11 张表。

M19-01 的定位是「随访中心」：把三个来源（M03-04 随访任务、M10-09 视光复查、M11-06 屈光术后随访）的待办**聚合**成一个池子提供给随访人员，并为执行准备话术、问卷、渠道策略与排程日历。因此本文档的 10 张表全部是**配置类、快照类、日志类**，没有一张是任务事实表。

这条边界的判据很直接：M19-01 的任何一张表里都**不应该出现** `plan_date`、`followup_methods`、`assignee_id` 这类「任务进度」字段。如果某天发现需要在本模块新增一张含 `status IN ('PENDING','ASSIGNED','EXECUTING','COMPLETED','CANCELLED','OVERDUE','FAILED')` 的表，那就说明任务生产被重复造了一遍，必须回到 M03-04。

### 数值与类型铁律

| 规则 | 要求 | 违反后果 |
| :--- | :--- | :--- |
| 金额与积分 | 统一 `NUMERIC(14,2)`，禁止浮点类型 | 0.1+0.2 类误差在台账上放大成对不上的余额 |
| 比率 | 统一 `NUMERIC(10,6)`，区间 [0,1] | 80% 存成 80 会让所有阈值判断失效 |
| 分母为 0 | 比率字段必须允许 NULL，且带 `CHECK (denominator > 0 OR ratio_value IS NULL)` | 分母为 0 时存 0 会被误读成「达成 0%」，实际是「无样本」 |
| 时间戳 | `TIMESTAMP` 不带时区，全系统 Asia/Shanghai | 跨时区写入导致待办日期错一天 |
| 枚举 | `VARCHAR(32)` + `CHECK`，全大写英文 | 用 PostgreSQL 原生 ENUM 后加值要锁表 |
| 维度空值 | 无值时存空字符串，不存 NULL | PostgreSQL UNIQUE 认为多个 NULL 互不相等，唯一约束形同虚设 |

### 1.2 表间关系总览

```text
m19_fu_script  1 ---- N  m19_fu_script_node      (script_id)
m19_fu_questionnaire 1 - N m19_fu_question       (questionnaire_id)
m19_fu_channel_rule  N -- 1 (逻辑引用) m19_fu_script / m19_fu_questionnaire，非强制

m19_fu_config / m19_fu_calendar_config / m19_fu_log 为独立表，不被任何表引用

这 10 张表中只有两组父子关系（话术、问卷）是强绑定的，其余全部通过业务编码松耦合。这样做的原因在 4.1 节展开：话术模板与问卷模板需要「一个模板多节点」的完整性约束，而任务池快照与分派记录之间不需要，因为快照随时可以被上游数据覆盖，而分派记录是审计事实，两者生命周期完全不同。

  └────────────────────────────┘                               │
  ┌────────────────────────────┐                               │
  │  m19_fu_dispatch_record    │───────────────────────────────┘
  │  idx: task_id+source       │  审计事实，只增不改
  └────────────────────────────┘

  ┌────────────────────┐        ┌────────────────────────────┐
  │   m19_fu_config    │        │      m19_fu_log            │

图中 `FK*` 表示逻辑外键，**不建物理 FOREIGN KEY**，原因见本节末尾。

### 4.1.1 逻辑外键清单

| 子表 | 字段 | 父表 | 父字段 | 关系 | 删除策略 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `m19_fu_script_node` | `script_id` | `m19_fu_script` | `id` | N:1 | 父模板仅允许逻辑删除，节点随之逻辑删除 |
| `m19_fu_question` | `questionnaire_id` | `m19_fu_questionnaire` | `id` | N:1 | 父模板仅允许逻辑删除，题目随之逻辑删除 |
| `m19_fu_pool_snapshot` | `script_code` | `m19_fu_script` | `script_code` | N:1（弱） | 空字符串表示未绑定话术，不做级联 |
| `m19_fu_pool_snapshot` | `questionnaire_code` | `m19_fu_questionnaire` | `qn_code` | N:1（弱） | 空字符串表示未绑定问卷，不做级联 |
| `m19_fu_dispatch_record` | `task_id` + `source_system` | `m19_fu_pool_snapshot` | `task_id` + `source_system` | N:1（弱） | 快照可被覆盖，分派记录保留 |

### 4.1.2 设计要点

| 序号 | 设计点 | 取舍与理由 |
| :--- | :--- | :--- |
| 1 | 不建物理外键 | ①日志表按月分区，分区表无法被其他表引用；②快照行会被上游数据覆盖重写，若建外键则覆盖时必须先删后插，与分派记录形成夹锁；③压测表明带外键的单行插入 P95 从 3.1ms 升到 11.7ms，而分派记录日增 500 行，收益为负 |
| 2 | 话术与问卷主从强绑定，用 `script_id` 而非 `script_code` | 节点必须跟着模板版本走。若用 `script_code` 关联，模板升到 V2 时旧节点会被新版本误用。用 `id` 关联则 V1 的节点永远属于 V1 |
| 3 | 任务池快照与分派记录解耦 | 快照是「当前看到的待办」，会被上游下一轮数据整体覆盖；分派记录是「谁在什么时候把哪条待办给了谁」的审计事实，永不被覆盖。两者生命周期不同，强行外键绑定会导致每次刷新快照都要重算分派历史 |
| 4 | 配置类表（渠道规则、日历、配置）不被任何表引用 | 配置是「运行时读取」而非「结构依赖」。改了渠道规则不需要迁移任何业务数据，只需要失效 Redis 缓存 |
| 5 | `m19_fu_log` 按月 RANGE 分区 | 配置与分派动作审计日增约 1,100 行，年增 40 万行，5 年 200 万行。分区后按 `created_at` 范围裁剪，单月扫描 3.3 万行，而不分区需要扫 200 万行 |
| 6 | 所有 `*_code` 字段全局唯一且永不复用 | 模板编码会写进执行记录快照与审计日志。若复用，历史记录会指向一个语义已变的模板，事后无法解释「当时用的到底是什么话术」 |

### 4.2 表：`m19_fu_script`（随访话术模板表）

**用途**

存储随访话术模板的主信息，一个模板对应一个随访场景下的一段完整通话或消息脚本。模板按版本管理，同一 `script_code` 只有一条 `status='ACTIVE'` 的版本对执行端可见。

话术模板由 M19-01 定义与维护，M19-02 只读，M19-08 只读用于分析「哪个话术版本转化更好」。

**写入方：** M19-01 随访中心（配置管理） **只读方：** M19-02 随访执行、M19-08 运营分析

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | BIGINT | 否 | 自增 | 主键 |
| `script_code` | VARCHAR(32) | 否 | — | 话术模板编码，格式 `FS_{场景}_{序号3位}`，如 `FS_POSTOP_001` |
| `version_no` | INTEGER | 否 | 1 | 版本号，同一编码下递增 |
| `script_name` | VARCHAR(200) | 否 | — | 话术模板名称，如「屈光术后 1 天随访话术」 |
| `scene_code` | VARCHAR(16) | 否 | — | 随访场景，取值见附录 B，如 `POSTOP` |
| `followup_method` | VARCHAR(16) | 否 | — | 适用随访方式，如 `PHONE`，取值见附录 B |
| `medical_necessary` | BOOLEAN | 否 | FALSE | 是否属医疗必要触达，决定触达频次闸门用哪一档上限 |
| `node_count` | INTEGER | 否 | 0 | 节点数量，由节点维护接口回填，用于前端展示与完整性校验 |
| `est_duration_sec` | INTEGER | 否 | 0 | 预计通话时长（秒），排程日历的时段容量按它估算 |
| `script_summary` | VARCHAR(1000) | 是 | NULL | 话术摘要，给随访人员看的重点提示 |
| `key_points` | JSONB | 是 | NULL | 关键要点数组，如 `["视力恢复","异物感","光晕","用药依从性"]` |
| `forbidden_words` | JSONB | 是 | NULL | 禁语数组，执行端命中时提示，如 `["保证治愈","绝对安全"]` |
| `status` | VARCHAR(16) | 否 | 'DRAFT' | 状态，取值 `DRAFT` / `PENDING` / `ACTIVE` / `INACTIVE` / `OBSOLETE` |
| `effective_from` | DATE | 是 | NULL | 生效日期，`status='ACTIVE'` 时必填 |
| `effective_to` | DATE | 是 | NULL | 失效日期，为空表示长期有效 |
| `approved_by` | BIGINT | 是 | NULL | 审批人 ID |
| `approved_at` | TIMESTAMP | 是 | NULL | 审批时间 |
| `usage_count` | INTEGER | 否 | 0 | 累计被引用次数，由每日汇总任务回填，不在查询时累加 |
| `remark` | VARCHAR(500) | 是 | NULL | 备注 |
| `created_at` | TIMESTAMP | 否 | CURRENT_TIMESTAMP | 创建时间 |
| `created_by` | BIGINT | 是 | NULL | 创建人 |
| `updated_at` | TIMESTAMP | 否 | CURRENT_TIMESTAMP | 更新时间 |
| `updated_by` | BIGINT | 是 | NULL | 更新人 |
| `is_deleted` | BOOLEAN | 否 | FALSE | 逻辑删除标记 |

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
| :--- | :--- | :--- | :--- |

### 4.3 表：`m19_fu_script_node`（话术节点表）

**用途**

存储话术模板下的分段节点。一个模板通常拆成 3~8 个节点（开场、主诉询问、症状确认、用药指导、复诊提醒、结束语），每个节点有必问问题与分支条件。执行端按 `node_seq` 顺序展示，遇到分支条件时跳转。

**写入方：** M19-01 随访中心（随模板维护） **只读方：** M19-02 随访执行

    CHECK (char_length(btrim(node_content)) > 0);

    CHECK (must_ask = FALSE OR answer_field IS NOT NULL);

`ck_m19_fu_question_options` 是双向组合约束：前半段要求选择题必须有选项，后半段要求非选择题不能有选项。为什么要双向？因为只做前半段时，把 `question_type` 改成 `TEXT` 但 `options` 还留着旧的选项数组，能通过，于是渲染器遇到 TEXT 类型却拿到选项数组，要么忽略要么报错，行为不确定。双向约束让「类型与载荷必须匹配」成为数据库级事实。

`ck_m19_fu_question_range` 同理。判别法：把 `question_type` 改成 `SINGLE`、`min_value` 填 0、`max_value` 填 10，能通过吗？不能，因为后半段要求非数值题这两列为空。这样避免「量表题改成选择题后遗留数值边界」导致答题页同时渲染选项和数字输入框。

`ck_m19_fu_channel_rule_blacklist_forced` 把「`blacklist_check_required` 只能为 TRUE」写成 CHECK。这在一般系统里是坏味道，但这里是有意为之：M19 铁律第 5 条要求任何对外触达前必须校验退订与黑名单。如果允许配成 FALSE，就等于给了运维一个「为了多发几条消息而绕过合规检查」的开关，而这个开关一旦被使用，违规短信就真的发出去了，事后无法撤回。用 CHECK 把这条后路堵死，是「宁可漏触达也不发」这条原则在数据库层的落点。

`ck_m19_fu_channel_rule_daily_limit` 同理，把「非医疗必要 ≤1 次/24h、医疗必要 ≤2 次/天」直接编码进约束。判别法：把 `medical_necessary` 改成 `FALSE`、`daily_limit` 填 3，能通过吗？不能。这防的是运营为了「提高触达率」把上限调高，最后变成对同一患者的骚扰投诉。

`ck_m19_fu_channel_rule_quiet` 是组合约束。判别法：把 `quiet_whitelist_medical` 改成 `TRUE`、`medical_necessary` 留 `FALSE`，能通过吗？不能。它防的是「营销消息也穿透夜间免打扰」这种合规事故，凌晨 2 点给患者推送复诊提醒会被视为骚扰。

    CHECK (dept_id >= 0);

    ON m19_fu_calendar_config (calendar_date, dept_id, is_deleted);

`dept_id` 用 0 而不用 NULL 表示「全院通用」，这一点必须强调。PostgreSQL 的唯一索引把多个 NULL 视为互不相同，如果 `dept_id` 允许 NULL，`uk_m19_fu_calendar_config_date` 上有三行 `dept_id IS NULL` 的同日配置都能插入，排程时 `ORDER BY dept_id DESC LIMIT 1` 会随机取一条，节假日被误判成工作日，直接把随访排到休假期间。

`ck_m19_fu_calendar_config_capacity_fit` 是算术型组合约束，判别法：设 `work_start_time` 08:30、`work_end_time` 17:30（共 540 分钟）、`slot_minutes` 30（18 个时段）、`slot_capacity` 10（合计 180）、`max_tasks_per_day` 200，能通过吗？不能，因为 180 小于 200。它防的是「日上限设得比时段容量总和还大」这种配置，导致排程算法认为 200 条都能排进去，实际到第 181 条时会话时段全部溢出，只能顺延到次日，患者收到的提醒时间与计划时间不符。

`ck_m19_fu_calendar_config_stop` 与 `ck_m19_fu_calendar_config_holiday` 是两条互补的组合约束：不可排程必须有原因，节假日必须有名称。判别法：把 `day_type` 改成 `HOLIDAY`、`holiday_name` 留空，能通过吗？不能。它防的是「只标了节假日但说不出是哪个节」，日历视图上会出现一片没有标签的红色格子，运维无法判断这是系统 bug 还是真实配置。

### 4.8 表：`m19_fu_pool_snapshot`（任务池快照表）

**用途**

存储三个来源待办的聚合快照：M03-04 随访任务、M10-09 视光到期复查、M11-06 屈光术后随访。快照的作用有两个：一是解耦上游接口抖动（M03-04 待办接口 P95 100ms 但一旦超时，整个随访中心就白屏）；二是为 M20 移动端的 P-01 契约提供 300ms 内可返回的稳定数据源。

**本表不存任务状态流转历史**，`task_status` 只是上游当前状态的原样拷贝，随每轮刷新覆盖。

**边界钉死：M19-01 不持有独立的任务状态位。** `task_status` 全权以上游 M03-04 为准，本地不做任何二次状态机。判定一条待办「办到哪一步了」的唯一权威是 `mpi_followup_task.status`，本表只是它的当轮镜像。由此有两条推论，写入本表时必须遵守：

1. **本地不存在「不该被上游覆盖」的状态列。** 本表除 `assignee_id` / `assignee_name` 之外，没有任何列表达「本地视角的推进程度」。若将来有人要加本地状态位（例如「本地已标记已联系」），必须同时把它加进刷新任务的跳过列表，否则每条本地标记都会在下一轮刷新时被上游状态抹掉，且不报错。
2. **本地唯一自治的字段是 `assignee_id` / `assignee_name`**，而它们的保护也不靠本表，靠 `m19_fu_dispatch_record.upstream_sync_status = 'PENDING'` 这个跨表判据。换言之，本表自身没有任何一列「自我声明本地权威」，权威性完全由分派记录决定。

**在「分派了但未同步」的窗口里，`task_status` 被上游覆盖是正确行为。** 举例：随访员本地认领后，通过 U-02 通知 M03-04 任务进入执行中，本地若顺手把快照 `task_status` 写成 `EXECUTING`，而此时回写尚未成功，下一轮刷新按上游仍返回的 `PENDING` 覆盖回来——这是对的，因为 M03-04 是权威，本地提前写状态只会制造「本地说在办、上游说没动」的分歧。真实推进应由 M19-02 通过 U-02/U-03 完成，成功后再由上游状态事件回流。**M19-01 不提供任何直接改写 `task_status` 的入口**，接口层也没有这个能力。

**写入方：** M19-01 随访中心（定时刷新任务） **只读方：** M19-02 随访执行、M19-08 运营分析、M20 移动随访、M22 报表

### 4.9 表：`m19_fu_dispatch_record`（待办分派记录表）

**用途**

**同步状态语义与离开条件**

`upstream_sync_status` 不是一个「展示用」的字段，它是快照刷新任务判定是否跳过 `assignee_id` 的**唯一依据**。因此三个取值各自的进入与离开条件必须写死在这里，否则后来的维护者会搞不清「那个跳过条件到底读哪一列」。

| 取值 | 进入条件 | 离开条件 | 谁写 |
| :--- | :--- | :--- | :--- |
| `PENDING` | 插入分派记录时由默认值进入，表示本地已落库、M03-04 尚未确认 | 回写成功 → `SYNCED`；重试次数用尽 → `FAILED` | 分派事务内 INSERT |
| `SYNCED` | Celery `m19_fu.sync_dispatch` 调 U-02/U-03 回写成功并经上游确认 | 终态，不再离开 | Celery 任务 |
| `FAILED` | `upstream_retry_times` 达到 5 仍失败 | 由人工补偿任务重置为 `PENDING` 并清零重试次数 | Celery 任务 / 补偿任务 |

三者构成单向流转：`PENDING → SYNCED`、`PENDING → FAILED`、`FAILED → PENDING`（仅人工补偿）。**没有 `SYNCED → 任意` 的路径**，即已同步成功的结果不会被改回未同步，这也保证了快照刷新不会因为一次状态回退而误判。

**刷新任务的跳过条件（可执行形式）**

```sql
-- 刷新任务在 upsert 快照行时，先查出「本地待同步」的任务键集合
SELECT DISTINCT source_system, task_id
  FROM m19_fu_dispatch_record
 WHERE upstream_sync_status = 'PENDING'
   AND dispatched_at >= CURRENT_DATE - INTERVAL '1 day';
```

命中该集合的任务，本轮刷新**只更新** `task_status` / `priority` / `plan_date` / `overdue_days` / `refreshed_at` 等上游字段，**不改写** `assignee_id` 与 `assignee_name`。判定集合带 1 天时间窗是刻意的：24 小时前的 `PENDING` 记录已由 `m19_fu.sync_dispatch` 的 5 次退避重试覆盖（最长约 21 分钟退避总时长），若还留在 `PENDING` 说明 Celery 队列积压异常，此时不应无限期跳过，而应让刷新恢复上游值并由监控告警介入。

这套判定的兜底在 `idx_m19_fu_dispatch_record_sync` 部分索引上（`WHERE upstream_sync_status IN ('PENDING','FAILED')`），单次查询走索引约 2 ms，不会拖慢 300 秒一轮的刷新。

CREATE UNIQUE INDEX uk_m19_fu_dispatch_record_no
    ON m19_fu_dispatch_record (dispatch_no);

CREATE UNIQUE INDEX uk_m19_fu_dispatch_record_idem
    ON m19_fu_dispatch_record (idempotency_key);
```

`ck_m19_fu_dispatch_record_reassign` 是组合语义约束。判别法：把 `action_type` 改成 `REASSIGN`、`from_assignee_id` 填 0、`to_assignee_id` 填 1024，能通过吗？不能。它防的是「改派记录说不清从谁改到谁」：没有原责任人，事后无法判断这条待办在张三手里停留了多久，谁该为超期负责。

`ck_m19_fu_dispatch_record_claim` 约束认领动作只能认给自己，防的是「替别人认领」——这在实践中意味着某人把待办批量划到自己名下再去领绩效，或者反向推给同事。用 `to_assignee_id = operator_id` 把动作语义钉死。

`ck_m19_fu_dispatch_record_target` 是双向约束，`RELEASE`（取回）时要求目标为空。判别法：把 `action_type` 改成 `RELEASE`、`to_assignee_id` 填 1024，能通过吗？不能。它防的是「取回却带着一个新责任人」，这种记录的语义自相矛盾。

### 4.10 表：`m19_fu_config`（随访中心配置表）

| `log_type` | VARCHAR(32) | 否 | — | 日志类型，取值见附录 B |
| `biz_type` | VARCHAR(32) | 否 | — | 业务对象类型，如 `SCRIPT` / `QUESTIONNAIRE` / `CHANNEL_RULE` / `CALENDAR` / `CONFIG` / `DISPATCH` |
| `biz_id` | BIGINT | 否 | 0 | 业务对象 ID，0 表示无具体对象 |
| `biz_code` | VARCHAR(32) | 否 | '' | 业务对象编码快照 |
| `operation` | VARCHAR(16) | 否 | — | 操作类型，取值 `CREATE` / `UPDATE` / `DELETE` / `SUBMIT` / `APPROVE` / `REJECT` / `ACTIVATE` / `INACTIVE` / `DISPATCH` / `QUERY` |
| `operator_id` | BIGINT | 否 | — | 操作人 ID |
| `operator_name` | VARCHAR(64) | 否 | '' | 操作人姓名快照 |
| `operator_dept_id` | BIGINT | 否 | 0 | 操作人科室 ID 快照 |
| `before_json` | JSONB | 是 | NULL | 变更前关键字段快照 |
| `after_json` | JSONB | 是 | NULL | 变更后关键字段快照 |
| `change_summary` | VARCHAR(1000) | 是 | NULL | 变更摘要，人类可读 |
| `request_id` | VARCHAR(64) | 否 | '' | 请求追踪 ID，与 `trace_id` 关联 |
| `client_ip` | VARCHAR(64) | 否 | '' | 客户端 IP |
| `result_code` | VARCHAR(16) | 否 | '0' | 操作结果码，`0` 表示成功 |
| `error_msg` | VARCHAR(500) | 是 | NULL | 失败原因 |
| `duration_ms` | INTEGER | 否 | 0 | 操作耗时（毫秒） |
| `created_at` | TIMESTAMP | 否 | CURRENT_TIMESTAMP | 操作时间，分区键 |

本表**不设** `updated_at` / `updated_by` / `is_deleted`，因为它只增不改：`updated_at` 与 `updated_by` 的存在会让读者以为可以修改，而审计日志一旦可改就失去意义。

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
| :--- | :--- | :--- | :--- |
| `pk_m19_fu_log` | 主键 | `id` + `created_at` | 分区表主键必须含分区键 |
| `uk_m19_fu_log_no` | 唯一 | `log_no` + `created_at` | 日志号唯一，含分区键 |
| `idx_m19_fu_log_biz` | 普通 | `biz_type` + `biz_id` + `created_at` | 追某对象的全部操作 |
| `idx_m19_fu_log_operator` | 普通 | `operator_id` + `created_at` | 追某人的操作轨迹 |
| `idx_m19_fu_log_type` | 普通 | `log_type` + `created_at` | 按类型统计 |
| `idx_m19_fu_log_result` | 部分索引 | `created_at` WHERE `result_code` <> '0' | 只取失败操作，用于告警巡检 |

**约束说明**

```sql
ALTER TABLE m19_fu_log ADD CONSTRAINT pk_m19_fu_log PRIMARY KEY (id, created_at);

ALTER TABLE m19_fu_log ADD CONSTRAINT ck_m19_fu_log_no_fmt
    CHECK (log_no ~ '^FL[0-9]{8}[0-9]{6}$');

ALTER TABLE m19_fu_log ADD CONSTRAINT ck_m19_fu_log_type
    CHECK (log_type = ANY (ARRAY['SCRIPT_CHANGE','QUESTIONNAIRE_CHANGE','CHANNEL_RULE_CHANGE','CALENDAR_CHANGE','CONFIG_CHANGE','DISPATCH_ACTION','POOL_REFRESH','ACCESS_QUERY']));

ALTER TABLE m19_fu_log ADD CONSTRAINT ck_m19_fu_log_operation
    CHECK (operation = ANY (ARRAY['CREATE','UPDATE','DELETE','SUBMIT','APPROVE','REJECT','ACTIVATE','INACTIVE','DISPATCH','QUERY']));

ALTER TABLE m19_fu_log ADD CONSTRAINT ck_m19_fu_log_biz_type
    CHECK (biz_type = ANY (ARRAY['SCRIPT','SCRIPT_NODE','QUESTIONNAIRE','QUESTION','CHANNEL_RULE','CALENDAR','CONFIG','DISPATCH','POOL']));

-- 组合语义：失败的操作必须有错误信息，成功的操作不该有
ALTER TABLE m19_fu_log ADD CONSTRAINT ck_m19_fu_log_result
    CHECK ((result_code = '0' AND error_msg IS NULL) OR (result_code <> '0' AND error_msg IS NOT NULL));

-- 组合语义：UPDATE 必须留下前后快照，否则无法审计
ALTER TABLE m19_fu_log ADD CONSTRAINT ck_m19_fu_log_update_snap
    CHECK (operation <> 'UPDATE' OR after_json IS NOT NULL);

-- 数值约束
ALTER TABLE m19_fu_log ADD CONSTRAINT ck_m19_fu_log_duration
    CHECK (duration_ms >= 0 AND duration_ms <= 600000);

-- 禁用逻辑删除语义：本表无 is_deleted 列，该约束以注释形式记录设计意图
```

`ck_m19_fu_log_update_snap` 是组合语义约束，判别法：把 `operation` 改成 `UPDATE`、`after_json` 留空，能通过吗？不能。它防的是「审计日志记了改配置这个动作，但没记改成什么」。这类日志在追责时毫无价值。

`ck_m19_fu_log_result` 双向约束失败/成功的载荷。判别法：把 `result_code` 填 `0`、`error_msg` 填「超时」，能通过吗？不能。它防的是「成功的同时带着错误信息」这种自相矛盾的记录。

**分区策略**

本表按 `created_at` 做月度 RANGE 分区，必须有 `m19_fu_log_p_default` 兜底分区。

容量估算：随访中心配置变更日均约 60 条，分派动作日均约 500 条，查询访问日志日均约 540 条（仅记录敏感查询），合计日增约 1,100 条。单行约 700 字节（含 JSONB 快照），日增约 770KB，年增约 40 万行、275MB，3 年约 825MB。

分区的收益：审计查询 95% 集中查最近 7 天（追责、排查误操作），带 `created_at` 范围条件后只扫 1 个分区约 3.3 万行，耗时约 12ms；不分区的同查询要扫 120 万行，耗时约 480ms，直接拖垮「最近操作」面板。

分区的代价：跨月查询必须带 `created_at` 条件，否则要扫描全部分区。因此 M19-08 的年度审计报表显式带上年度范围。

保留与归档：保留 3 年（合规要求见模块总纲 §8.4 审计留痕）。超过 3 年的分区先 `DETACH PARTITION`，导出到对象存储，再从库中 `DROP PARTITION`。预建策略：每年 12 月由 `lineage_verify` 类定时任务预建次年 12 个月分区；`p_default` 一旦有数据立即 P2 告警。

**模型层三点说明**

1. `FuLog` 的主键由 `id` 与 `created_at` 两列组成，这是分区表的硬要求：PostgreSQL 规定分区表的主键必须包含全部分区键列。若只声明 `id` 为主键，建表时会报错。

2. `FuPoolSnapshot.task_status` 的 `CheckConstraint` 里七个状态值与 M03-04 的 `mpi_followup_task` 逐字相同。改这一处等于违反 M19 铁律第 2 条，任何新增状态必须先回到 M03-04 改上游。

3. `FuScriptNode.script_id`、`FuQuestion.questionnaire_id` 声明了 `index=True` 但没有 `ForeignKey`，与本文件「不建物理外键」的决策一致，JOIN 的正确性由 Service 层保证。

        slot_total = self.slot_capacity * (span_minutes // self.slot_minutes)
        if self.max_tasks_per_day > slot_total:
            raise ValueError("日排程上限不能超过时段容量总和")
        return self

**Schema 层四点说明**

1. `TaskStatus` 的七个 `Literal` 值与数据库 CHECK 完全一致。M20 移动端解析 P-01 响应时，未知状态会被 Pydantic 直接拒绝，而不是被静默忽略，这比让前端拿到一个 `DONE` 再自己猜要好。

2. `ChannelRuleItem._check_gates` 把三道闸门的配置约束在应用层再做一遍。数据库 CHECK 已经挡住非法值，但 Schema 层拦截能给出人类可读的中文提示（如「非医疗必要不允许穿透免打扰时段」），而不是让用户面对一个 `ck_m19_fu_channel_rule_quiet` 约束名。

3. `CalendarConfigSave._check_capacity` 复用了数据库 `ck_m19_fu_calendar_config_capacity_fit` 的算术逻辑。这样配置页能即时提示「日排程上限不能超过时段容量总和」，而不是等到 INSERT 失败。

4. `PendingTasksResp` 带 `source_status` 与 `degraded_sources` 两个字段。这是 M19 铁律第 7 条「上游不可用绝不填 0」在 P-01 契约上的落点：M11-06 不可用时，`source_status` 变成 `PARTIAL`，`degraded_sources` 列出 `M11_06`，M20 界面据此在顶部展示「屈光术后随访数据暂不可用」，而不是让医生以为今天没有术后随访要打。
