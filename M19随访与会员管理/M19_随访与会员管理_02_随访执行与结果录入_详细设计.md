### 三条铁律

| 编号 | 铁律 | 为什么 | 违反后果 |
|---|---|---|---|
| L-01 | **随访任务事实不落 M19 的库** | 任务唯一权威在 M03-04。M19 再存一份就是双写，两边永远不一致 | 双写 → M03-04 侧任务取消了 M19 还在催，或反之；对账时无从判断哪边对 |

## 1. 模块概述

### 1.1 定位

M19-02 是**随访闭环的执行环节**。上游 M03-04 生产随访任务，M19-01 把任务聚合进任务池并配好话术与问卷，M19-02 负责真正把电话打出去、把问卷问完、把结果录进来、把状态回写出去。

```
┌──────────────┐ mpi.followup.task.created   ┌──────────────┐
│  M03-04 随访 │ ─────────────────────────────> │  M19-01 计划 │
│  任务事实源  │                                │  与配置      │
└──────────────┘                                └──────┬───────┘
        ▲                                              │ 任务池 + 话术 + 问卷
        │ API-33 回写结果                              ▼
        │ API-34 标记执行中                    ┌──────────────┐
        │                                      │  M19-02 执行 │
┌───────┴──────┐   m19.followup.executed       │  与结果录入  │
│  M19-08 分析 │ <───────────────────────────  │   （本子模块）│
│  M19-03 关怀 │                               └──────┬───────┘
└──────────────┘                                      │
                                                      ▼
                                        ┌──────────────────────────┐
                                        │ M03-05 短信/微信 · 呼叫中心│
                                        └──────────────────────────┘
```

**一句话概括：** M19-02 不决定「随访谁、问什么、什么时候问」（那是 M03-04 与 M19-01 的事），只负责「把这次随访做完并证明做完了」。

### 1.2 为什么独立成子模块

**理由一：执行过程数据与任务事实是两类数据，生命周期完全不同。**
M03-04 的 `mpi_followup_task` 是**计划性数据**：一条任务从生成到关闭，字段十几个。M19-02 的执行记录是**过程性数据**：一通电话就有 38 个字段（拨号时刻、振铃时长、接通结果、挂机方、录音 URL、质检得分……），一份 20 题的问卷有 20 行答案。实测日均 1,200 次随访产生 1,200 条执行记录、900 条外呼记录、24,000 行答案。把这些塞进 M03-04，会让一个「计划表」变成「流水表」，M03-04 自己的待办查询（P95 ≤ 100ms）会被拖垮。

**理由二：执行侧有自己的状态机，且与任务状态机不是一对一。**
M03-04 的任务状态是 `PENDING/ASSIGNED/EXECUTING/COMPLETED/CANCELLED/OVERDUE/FAILED` 七态。执行记录是 `DRAFT/IN_PROGRESS/SUBMITTED/CLOSED/ABANDONED/EXPIRED` 六态，另有 `writeback_status` 三态。一个 M03-04 任务在执行侧可能经历「打 3 次电话都无人接 → 判失访」：任务侧只从 `EXECUTING` 变 `FAILED` 一步，执行侧却记了 3 通电话、1 次失访登记、1 条回写消息。**把两套状态机压进一张表，状态数会爆炸成 7×6×3 = 126 种组合**，而其中真正有业务意义的不到 20 种。

**理由三：回写失败必须能在本地重试，而这是纯执行侧的问题。**
M03-04 不可用时（滚动发布 20~40 秒窗口、网络抖动、数据库主从切换），M19 不能让护士的操作失败——她刚打完 3 分钟电话，结果不能因为对面 502 就丢掉。所以必须本地先落库、再异步回写、失败退避重试。这个「本地消息表 + 扫描补偿」的机制是执行侧独有的，放在 M03-04 里没有任何意义。

**理由四：异常结果升级需要 4 小时窗口的计时器，这是执行侧的业务规则。**
术后视力从 0.8 掉到 0.4、患者主诉「眼前有黑影飘动」——这些是执行侧识别出来的，需要在 4 小时内有人复访。M03-04 不知道什么叫「视力下降」，它的 `result` 字段只有一个自由文本。异常规则、升级通道、复访计时器全部属于执行侧。

### 1.4 概念辨析

#### 1.4.1 「执行记录」与「随访任务」

| 维度 | 随访任务（M03-04） | 执行记录（M19-02） |
|---|---|---|
| 回答什么问题 | 该不该给这个患者做随访、什么时候做 | 这次随访实际怎么做的 |
| 谁生成 | M03-04 按计划规则自动生成 | 护士点「开始执行」时生成 |
| 数量关系 | 1 条任务 | 对应 0 或 1 条执行记录（唯一键约束） |
| 状态含义 | 计划的推进状态 | 执行的推进状态 |
| 修改权限 | 只有 M03-04 能改 | 只有 M19-02 能改 |

**为什么是 1:0 或 1:1 而不是 1:N：** 一条任务就是一个患者的一个随访节点，做一次就够了。若允许一对一交叉（一条执行记录挂多条任务），则「合并随访」场景会出现——一次电话里同时完成术后 1 周随访和视光复查提醒。**当前设计不支持合并随访**，理由：两条任务属于不同的随访场景，报告与统计口径不同，合并后回写要看两条任务、异常要挂到哪个任务上都会歧义。若将来需要，应当由 M03-04 在计划层合并成一个任务，而不是在执行层拆。

#### 1.4.2 「SUBMITTED」与「CLOSED」

这是本子模块最重要的一个概念区分。

| 状态 | 含义 | M03-04 侧的表现 | 谁在等 |
|---|---|---|---|
| `SUBMITTED` | **M19 本地已经录完结果**，等待回写 | 仍是 `EXECUTING`（可能已逾期） | 回写任务在等 |
| `CLOSED` | **已经成功回写 M03-04 并收到确认** | `COMPLETED` 或 `FAILED` | 没有人等了，闭环 |

**为什么必须分开（不这么做会怎样）：**

假设只有一个「已完成」状态。护士上午 10:00 打完电话、录完问卷，此时 M03-04 正在滚动发布，回写 502。系统把记录标成「已完成」，护士看到「做完了」就下班了。

- M03-04 侧这条任务仍然是 `EXECUTING`，凌晨的逾期扫描把它标成 `OVERDUE`。
- 第二天早上的随访看板显示「昨日逾期 47 条」，护士长要求解释。
- 护士翻自己的记录：「我明明做完了呀。」于是她再打一遍电话。
- 患者昨天已经被告知一切正常，今天又被问一遍「术后有没有不适」——**被骚扰两次**。

分成两个状态后，`SUBMITTED` 且 `writeback_status = 'PENDING'` 的记录会出现在「待回写」列表里，重试 5 次仍失败会告警到工程师，而不是让护士重打。

#### 1.4.3 「未答」与「答否」

见数据结构文件 §4.4。核心：`answer_state` 四值中，只有 `ANSWERED` 才是「作答了」。

| 场景 | `answer_state` | `answer_code` | 业务含义 | 后续动作 |
|---|---|---|---|---|
| 患者答「没有眼痛」 | `ANSWERED` | `NO` | 明确无异常 | 可关单 |
| 患者答「有点眼痛」 | `ANSWERED` | `YES` | **异常信号** | 触发异常规则 |
| 电话里没问到这题 | `UNANSWERED` | NULL | 信息缺失 | 补录提醒 |
| 患者说「这个不想说」 | `SKIPPED` | NULL | 患者拒答 | 尊重意愿，不算缺失 |
| 问到一半患者挂断 | `NOT_ASKED` | NULL | 执行中断 | 必答项算缺失，影响完整度 |

#### 1.4.4 「执行结果」与「回写状态」

`m19_fu_exec_record` 上有两套独立状态：`status`（执行推进到哪一步）与 `writeback_status`（回写 M03-04 的进展）。**二者正交。**

举例：一条记录可以是 `status = 'SUBMITTED'` + `writeback_status = 'FAILED'`（录完了但回写 5 次都失败，等人工），也可以是 `status = 'CLOSED'` + `writeback_status = 'SUCCESS'`（正常闭环）。但**不可能是** `status = 'CLOSED'` + `writeback_status = 'PENDING'`——那自相矛盾，用数据库组合约束禁止。

### 1.5 设计目标

| 编号 | 目标 | 量化指标 |
|---|---|---|
| G-01 | 护士能在 3 秒内拿到今天的待办并开始执行 | 待办列表 P95 ≤ 300ms |
| G-02 | 结果录入后 200ms 内完成本地落库与回写发起 | 提交接口 P95 ≤ 200ms |
| G-03 | 回写失败不阻塞护士，且结果绝不丢失 | 本地成功率 100%，回写最终成功率 ≥ 99.9% |
| G-04 | 异常结果在 4 小时内必有复访记录 | 超时率 ≤ 1% |
| G-05 | 失访必须回写 M03-04，任务不悬挂 | 失访回写成功率 ≥ 99.9% |
| G-06 | 任何对外触达必须先过三道闸门 | 未过闸门的触达数 = 0 |
| G-07 | 执行记录 3 年内可查、可举证 | 查询 P95 ≤ 500ms |

### 2.3 与业务模块的边界

**铁律：只许调接口，不许碰数据库。**

M19-02 与 M03-04 之间是**跨模块**关系。M19-02 的数据库账号 `app_m19` 对 `mpi_followup_task` 没有任何权限（连 SELECT 都没有）。所有任务读写必须走 M03-04 的内部接口。

| 检查项 | 允许 | 禁止 |
|---|---|---|
| 读 M03-04 任务 | `GET /internal/v1/followup/tasks/pending` | `SELECT * FROM mpi_followup_task` |

**为什么这条铁律不能破：** 一旦允许直查，M03-04 下次改表结构（加字段、拆表、换编码）时 M19-02 会在生产环境 500，而 M03-04 的开发者完全不知道自己在破坏谁。接口是一份合约，改合约至少要走版本协商。

### 3.2 状态机

#### 3.2.1 执行记录状态机

```
                       ┌─────────┐
                       │  DRAFT  │ 护士点了「开始执行」
                       │ 待执行  │ 已调 M03-04 API-34
                       └────┬────┘
                            │ 拨号 / 打开问卷
                            ▼
                     ┌─────────────┐
                     │ IN_PROGRESS │ 执行中
                     │  执行中     │
                     └──┬───┬───┬──┘
          提交结果       │   │   │  判定失访
        ┌───────────────┘   │   └──────────────┐
        ▼                   │                  ▼
  ┌─────────────┐           │           ┌──────────┐
  │  SUBMITTED  │           │           │   LOST   │
  │  已提交     │           │           │  → 见 3.2.4│
  │ (等回写)    │           │           └──────────┘
  └──────┬──────┘           │
         │ 回写成功          │ 放弃执行
         ▼                  ▼
  ┌─────────────┐    ┌─────────────┐
  │   CLOSED    │    │  ABANDONED  │
  │  已闭环     │    │  已放弃     │
  └─────────────┘    └─────────────┘

  ┌──────────┐
  │ EXPIRED  │  DRAFT 超时未开始（默认 7 天）
  │ 超时失效 │
  └──────────┘
```

| 状态 | 含义 | 可迁移到 | 触发条件 |
|---|---|---|---|
| `DRAFT` | 已创建，尚未开始 | `IN_PROGRESS`、`EXPIRED` | 创建时默认 |
| `IN_PROGRESS` | 执行中 | `SUBMITTED`、`ABANDONED` | 首次拨号或打开问卷 |
| `SUBMITTED` | 本地结果已录完，等待回写 | `CLOSED` | 提交结果接口调用成功 |
| `CLOSED` | 已成功回写 M03-04 | 终态 | 收到 M03-04 的 2xx 确认 |
| `ABANDONED` | 已放弃（如患者要求改天） | 终态 | 护士主动放弃 |
| `EXPIRED` | 超时失效（DRAFT 超过 7 天） | 终态 | 定时任务扫描 |

**关键约束：** `CLOSED` 必须同时满足 `writeback_status = 'SUCCESS'` 且 `writeback_at IS NOT NULL`（数据结构 `ck_m19_fu_exec_record_closed_writeback`）。

#### 3.2.2 回写状态流转

```
   ┌─────────┐   扫描到待发   ┌─────────┐   2xx    ┌─────────┐
   │ PENDING │──────────────>│ SENDING │─────────>│ SUCCESS │
   │ 待回写  │               │ 发送中  │          │ 成功    │
   └────┬────┘               └────┬────┘          └─────────┘
        │                         │ 非 2xx / 超时
        │                         ▼
        │                    ┌─────────┐  attempt < 5   ┌──────────┐
        │                    │ 重试排队 │───────────────>│ PENDING  │
        │                    │next_retry│  (退避后)      └──────────┘
        │                    └────┬────┘
        │                         │ attempt >= 5
        │                         ▼
        │                    ┌─────────┐  人工处置  ┌──────────┐
        └───────────────────>│ FAILED  │───────────>│ SUCCESS  │
                             │重试耗尽 │  重放成功   └──────────┘
                             └─────────┘
```

**退避序列：** 30s → 60s → 120s → 240s → 480s，累计 930 秒（15.5 分钟）。第 5 次失败后置 `FAILED` 并告警。

为什么第一次退避是 30 秒而不是立即重试：M03-04 滚动发布窗口约 20~40 秒，立即重试必然再次撞上；30 秒后大概率已恢复。而累计 930 秒也足够覆盖一次主从切换（通常 30~60 秒）。

#### 3.2.3 异常处置状态流转

```
  ┌─────────┐  护士长接手  ┌───────────┐  有结论  ┌──────────┐
  │ PENDING │─────────────>│ IN_REVIEW │─────────>│ REVIEWED │
  │ 待复访  │              │ 复访中    │          │ 已复访   │
  └────┬────┘              └─────┬─────┘          └────┬─────┘
       │                         │ 需上级介入           │ 归档
       │ 超 4 小时未接手          ▼                     ▼
       │                  ┌────────────────┐      ┌─────────┐
       │                  │ESCALATED_HIGHER│      │ CLOSED  │
       │                  │ 已升级上级     │      │ 已关闭  │
       │                  └────────────────┘      └─────────┘
       ▼
  ┌──────────┐
  │ OVERDUE  │  复访超时（> 4 小时）
  │ 复访超时 │
  └──────────┘
```

| 状态 | 含义 | 时限 |
|---|---|---|
| `PENDING` | 待复访 | 须在 `review_deadline_at`（= `escalated_at` + 4 小时）前接手 |
| `IN_REVIEW` | 复访中 | — |
| `REVIEWED` | 已复访，有结论 | — |
| `ESCALATED_HIGHER` | 已升级到上级（科主任/医务科） | — |
| `CLOSED` | 已关闭归档 | — |
| `OVERDUE` | 复访超时 | 定时任务扫描 |

#### 3.2.4 失访登记流转

```
  执行中              判失访               审核               回写M03-04
┌─────────┐      ┌──────────┐      ┌──────────┐      ┌──────────────┐
│IN_PROGRESS│─────>│  PENDING │─────>│ APPROVED │─────>│ FAILED 状态   │
│         │      │ 待审核   │      │ 已通过   │      │ 回写 + 消息表 │
└─────────┘      └────┬─────┘      └──────────┘      └──────────────┘
                      │ 驳回
                      ▼
                 ┌──────────┐
                 │ REJECTED │  回到 IN_PROGRESS
                 └──────────┘
```

**失访回写必须用 `status = 'FAILED'`：** M03-04 的任务状态枚举里只有 `FAILED` 能表达「这个患者找不到了」。用 `COMPLETED` 会让逾期统计把失访算成完成；不回写会让任务永远停在 `EXECUTING`（总纲 §3.1 明确指出的闭环漏洞）。

**为什么不用数据库序列拼日期（汇总 §7.4）：** `SEQUENCE` 的 `nextval` 与 `CURRENT_DATE` 不在同一事务快照里。跨零点并发时，序列已到 20261022 而代码取的还是 `20261021`，结果生成 `FE202610220001` 却挂在 21 号的分区语义下；或者两笔并发都取到 `20261021`，序号却连号跳空。Redis `INCR` 是原子操作，key 里带日期，天然不跨天。

Redis key 过期策略：`seq == 1` 时设置 `EXPIREAT` 到次日 `00:05`，留 5 分钟缓冲。

### 3.4 计算模型

#### 3.4.1 随访完整度

```
随访完整度 = 已作答必答题数 / 必答题总数

其中：
  已作答必答题数 = COUNT(answer_state = 'ANSWERED' AND is_required = TRUE)
  必答题总数     = COUNT(is_required = TRUE)

边界：
  - 必答题总数为 0（无问卷）→ 完整度 = NULL，不返回 0 或 1
  - 完整度 < 100% 时不允许提交（可配置为「仅告警」）
```

**算例：** 术后 1 周随访问卷 12 题，其中必答 9 题、选答 3 题。护士答完必答 8 题、选答 2 题，第 9 题患者说「不清楚」标为 `SKIPPED`。

```
完整度 = 8 / 9 = 0.888889
```

界面显示「必答 8/9（88.9%）」，并高亮那一道 `SKIPPED` 的必答题要求补答。**注意 `SKIPPED` 虽然不惩罚患者，但必答题被跳过时仍算不完整**——因为必答题的存在意义就是医生必须知道这个信息。

#### 3.4.2 随访完成率与依从性（引用总纲 §6.3）

```
随访完成率 = 完成随访任务数 / 应完成随访任务数
依从性     = 按期完成随访任务数 / 应完成随访任务数
```

| 指标 | 分子 | 分母 |
|---|---|---|
| 完成率 | `status = 'COMPLETED'` 且 `executed_at` 在统计期内 | 统计期内 `plan_date` 落区间的全部任务（除 `CANCELLED`） |
| 依从性 | `status = 'COMPLETED'` 且 `executed_at <= plan_date + 宽限期（默认 3 天）` | 同上 |

**算例（总纲 §6.3 原例）：** 某科室 2026-10 共 120 条应随访任务。

- 完成 96 条（其中 84 条在计划日后 3 天内完成，12 条逾期补做）、失败 18 条、逾期未做 6 条

```
随访完成率 = 96 / 120 = 0.800000 = 80.00%
依从性     = 84 / 120 = 0.700000 = 70.00%
差值       = 12 / 120 = 0.100000 = 10.00 个百分点
```

两者相差的 10 个百分点**全部来自逾期补做**——这正是要暴露给管理层的信号：随访做完了，但做得太晚。

**分母为 0 时返回 NULL。** 新开科室某月 0 条任务，完成率是「无数据」而不是「0%」。若返回 0，科室排名会把它排到最后一名，这是对数据的误用。数据库层用 `CHECK (denominator > 0 OR ratio_value IS NULL)` 保证。

**本子模块的责任边界：** 这两个指标由 M19-08 计算输出，M19-02 只保证**输入正确**——即 `executed_at` 的准确性（取提交时刻而非入库时刻）、`plan_date` 的准确性（取 M03-04 的快照）、以及失访任务不会被算成 `COMPLETED`。

#### 3.4.3 首次接通率（话术优化用）

```
首次接通率 = 第一通电话即接通的执行数 / 有外呼的执行总数

其中：
  第一通电话即接通 = call_seq = 1 且 call_result = 'CONNECTED'
  有外呼的执行总数 = COUNT(DISTINCT exec_id) WHERE 有 call_log 记录
```

**算例：** 某月有外呼的执行 1,200 次，其中第 1 通即接通 744 次。

```
首次接通率 = 744 / 1200 = 0.620000 = 62.00%
```

再算「第 2 通累计接通」：第 1、2 通内接通 996 次。

```
两通内接通率 = 996 / 1200 = 0.830000 = 83.00%
```

**边际收益：** 第 2 通只多打了 1 次，把接通率从 62% 拉到 83%，边际提升 21 个百分点。而第 3 通只再拉到 89.7%（1,076 次），边际只剩 6.7 个百分点。**结论：最多打 3 次就该判失访**，第 4 次开始投入产出比急剧下降——这就是 `m19.fu.lost.min_call_attempts` 默认 3 的依据。

#### 3.4.4 异常触发判定

```
对每个答案 a：
  若 a.answer_state ≠ 'ANSWERED' → 跳过（未答不触发，但要计入完整度缺失）

  数值型规则（如眼压）：
    a.answer_numeric > 规则.upper_limit → 触发
    a.answer_numeric < 规则.lower_limit → 触发

  编码型规则（如症状）：
    a.answer_code ∈ 规则.trigger_codes → 触发

  关键词型规则（如文本主诉）：
    EXISTS(kw ∈ 规则.keywords WHERE a.answer_text LIKE '%' + kw + '%') → 触发

  趋势型规则（如视力下降）：
    令 prev = 该患者上一次同 detail_code 的数值
    若 (prev - a.answer_numeric) > 规则.drop_threshold → 触发
```

**算例（趋势型）：** 患者术后 1 周右眼裸眼视力 0.8（记入 `m19_fu_result_detail`，`detail_code = 'VA_R'`）。术后 1 月复查录入 0.5。

```
drop = 0.8 - 0.5 = 0.300000
规则阈值 m19.fu.abnormal.vision_drop_threshold = 0.2
0.300000 > 0.2 → 触发 VISION_DROP 异常，severity = SEVERE
复访截止 = triggered_at + 4 小时
```

为什么用「差值」而不是「绝对阈值」：视力 0.5 对术前 0.1 的白内障患者是巨大成功，对术前 1.2 的年轻人是灾难。只有**相对自身的变化**才有意义。

#### 3.4.5 异常复访时限

```
review_deadline_at = escalated_at + review_window_hours  （默认 4 小时）

超时判定：
  若 review_status ∈ ('PENDING', 'IN_REVIEW') 且 now() > review_deadline_at
  → 置 OVERDUE 并二次告警
```

**为什么是 4 小时：** 眼科术后急症的时间窗很紧——视网膜动脉阻塞的黄金抢救时间是 90 分钟，眼内炎的视力预后以小时计。4 小时是「当天工作时间内必有人处理」的保守估计：上午 10:00 触发的异常，当天下班前必定有结论。数据库层用 `CHECK (... review_deadline_at <= escalated_at + INTERVAL '4 hours')` 防止有人把它配成 24 小时。

#### 3.4.6 退避重试间隔

```
第 n 次重试的间隔（秒） = backoff_base_seconds × 2^(n-1)

n=1:  30 × 2^0 =  30  秒   累计  30 秒
n=2:  30 × 2^1 =  60  秒   累计  90 秒
n=3:  30 × 2^2 = 120  秒   累计 210 秒
n=4:  30 × 2^3 = 240  秒   累计 450 秒
n=5:  30 × 2^4 = 480  秒   累计 930 秒
```

5 次重试覆盖 15.5 分钟。选择指数退避而非固定间隔的理由：如果是网络抖动，30 秒内大概率恢复；如果是 M03-04 在发布，需要等 20~40 秒；如果是数据库主从切换，可能 60 秒。固定 10 秒间隔会在前 3 次全部撞在故障窗口内白白消耗重试次数，5 次用完只覆盖了 50 秒。

#### 3.4.7 触达频次判定

```
当日已触达次数 = COUNT(m19_fu_touch_log WHERE patient_id = ? AND touch_date = today()
                                        AND touch_status IN ('SENT', 'DELIVERED'))

限额：
  is_medical_necessary = TRUE  → 限额 2
  is_medical_necessary = FALSE → 限额 1

判定：当日已触达次数 >= 限额 → 压制（FREQUENCY_LIMIT）
```

**算例：** 患者今日上午已收到 1 条术后随访短信（医疗必要），下午护士还要发 1 条复查提醒（医疗必要）。

```
当日已触达 = 1
限额 = 2（医疗必要）
1 >= 2 ? 否 → 放行，触达后计数变为 2

若再来第 3 条：当日已触达 = 2，2 >= 2 → 压制
```

**为什么医疗必要能到 2 次：** 术后当天既要发随访问卷邀请，又要发用药提醒，这两条都是医疗必要。但对营销类触达 1 次就够——总纲 §5.4 明确「宁可漏发也不能错发」。

#### 3.4.8 逾期任务判定辅助

```
任务是否逾期 = plan_date + grace_days < today() AND status NOT IN ('COMPLETED', 'CANCELLED', 'FAILED')

grace_days 默认 3
```

M19-02 不负责判定逾期（那是 M03-04 的事），但**执行页面要用这个公式给护士排序**：逾期越久的越靠前。排序权重：

```
排序权重 = 逾期天数 × 10 + (priority = 'HIGH' ? 100 : priority = 'NORMAL' ? 50 : 0)
```

**算例：** 任务 A 逾期 5 天、优先级 NORMAL → 5×10 + 50 = 100；任务 B 逾期 0 天、优先级 HIGH → 0×10 + 100 = 100。两者同分，此时按 `plan_date` 升序，A 在前。

#### API-03 开始执行

**方法/路径：** `POST /api/v1/m19/followup-exec/exec-records`

**权限：** `m19:fu:exec:create`

**请求参数：**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| task_id | bigint | 是 | M03-04 任务 ID |
| followup_method | string | 是 | 随访方式 |
| demand_channel | string | 否 | 触达渠道，默认 `PHONE` |
| idempotency_key | string | 是 | 幂等键（前端生成 UUID） |

**响应示例：**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "exec_id": 55001,
    "exec_no": "FE202610210001",
    "status": "DRAFT",
    "replayed": false,
    "task_status": "EXECUTING",
    "questionnaire_id": 301,
    "script_code": "FS_POSTOP_001"
  },
  "trace_id": "a1b2c3d4e5f6"
}
```

**错误码：** `"1902001"`、`"1902002"`、`"1902004"`、`"1902004"`

**业务逻辑：**

1. 校验 `idempotency_key`：Redis `m19:idem:exec:{key}` TTL 24h，命中则返回首次结果（`replayed = true`）。
2. 查本地 `m19_fu_exec_record` 是否已有 `task_id` 的记录：有则直接返回该记录（`uk` 唯一键兜底）。
3. **先调 M03-04 API-34** 把任务置 `EXECUTING`；失败则整体回滚，返回 `"1902008"`。
4. 从 M03-04 任务快照：`patient_id`、`patient_name`、`followup_scene`、`node_name`、`priority`、`plan_date`、`exec_dept_id`、`dept_name`、`executor_id`、`executor_name`。
5. 从 M19-01 取问卷模板 ID 与话术编码。
6. 生成 `exec_no`（Redis `INCR`），插入 `m19_fu_exec_record`，`status = 'DRAFT'`。
7. 写回写消息 `FW`（`action = 'TASK_START'`），立即尝试回写（记录任务已开始）。
8. 返回。

> **注意顺序：先调 M03-04 再落本地。** 反过来会出问题：本地落了记录但 M03-04 没置 `EXECUTING`，若护士随后提交结果，M03-04 会以「任务当前状态不允许」拒绝回写，记录永远停在 `SUBMITTED`。先置 `EXECUTING` 则 M03-04 侧状态是「进行中」，后续回写一定被接受。

#### API-13 提交随访结果

**方法/路径：** `POST /api/v1/m19/followup-exec/exec-records/{exec_no}/submit`

**权限：** `m19:fu:exec:edit`

**请求参数：**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| exec_result | string | 是 | `exec_result` 五值 |
| result_summary | string | 是 | 结果摘要，10~500 字 |
| details | array | 否 | 归一化明细（不传则由答案自动映射） |

**响应示例：**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "exec_no": "FE202610210001",
    "status": "SUBMITTED",
    "writeback_status": "PENDING",
    "writeback_msg_no": "FW202610210002",
    "abnormals": [
      {"abnormal_no": "FA202610210001", "abnormal_type": "VISION_DROP", "severity": "SEVERE"}
    ],
    "executed_at": "2026-10-21 10:35:00"
  },
  "trace_id": "a1b2c3d4e5f6"
}
```

**错误码：** `"1902002"`、`"1902003"`、`"1902005"`、`"1902006"`

**业务逻辑：**

1. 校验 `status = 'IN_PROGRESS'`，否则 `"1902003"`。
2. 校验必答完整度 = 1.0（`m19.fu.exec.require_full` 为 true 时强校验），否则 `"1902005"`。
3. 校验 `result_summary` 长度 10~500。
4. 由问卷答案映射生成 `m19_fu_result_detail`（若未显式传 `details`）。
5. 生成异常单 `m19_fu_abnormal`（对每条命中的规则，含 `review_deadline_at = now() + 4h`）。
6. 在**同一事务**内：置 `status = 'SUBMITTED'`、`executed_at = now()`、`writeback_status = 'PENDING'`，写 `m19_fu_writeback`（`action = 'TASK_RESULT'`，快照请求体）。
7. 事务提交后发送 Celery 任务立即尝试回写。
8. 返回。

> **为什么消息表与状态更新必须在同一事务：** 若先更新状态再写消息，进程在两步之间崩溃 → 记录永远停在 `SUBMITTED` 且没有消息，扫描任务扫不到它，**结果永久丢失**。反之先写消息再更新状态，崩溃会导致重复发送（有幂等键兜底，无害）。**宁可重复，不可丢失。**

```json
      "time_window": {"passed": true, "result": "PASS"},
      "frequency": {"passed": true, "result": "PASS", "count_before": 0, "limit": 2}
    },
    "msg_id": "MSG20261021000123"
  },
  "trace_id": "a1b2c3d4e5f6"
}
```

**错误码：** `"1902002"`、`"1902015"`、`"199001"`

**业务逻辑（触达三道闸门，严格按总纲 §5.4）：**

1. 校验执行记录存在与权限。
2. **闸门一 — 意愿闸门：** 调 M03-05 `GET /internal/v1/message/check-blacklist`。
   - 不通过（`UNSUBSCRIBED`/`BLACKLISTED`）→ 落 `m19_fu_touch_log`，`touch_status = 'SUPPRESSED'`，`suppress_reason` 取对应值，返回 `"1902015"`。
   - **接口不可用 → 失败关闭（fail-closed）**：`gate_blacklist_result = 'FAIL_CLOSED'`、`touch_status = 'SUPPRESSED'`、`suppress_reason = 'FAIL_CLOSED'`，返回 `"1902015"`。**宁可全部不发，也不能给已退订的患者发。**
3. **闸门二 — 时段闸门：** 当前时刻在免打扰时段（`21:00 ~ 次日 08:00`）内？
   - 是，且 `is_medical_necessary = true` 且场景为 `POSTOP`/`DISCHARGE` → 允许（`gate_time_result = 'MEDICAL_EXCEPTION'`）。
   - 是，其他情况 → `touch_status = 'DELAYED'`、`delayed_until = 次日 08:30`，或改投站内信；`suppress_reason = 'QUIET_HOURS'`。
4. **闸门三 — 频次闸门：** 读 Redis `m19:throttle:{patient_id}:{yyyyMMdd}` 计数值。
   - `count >= limit`（医疗必要 2，否则 1）→ `touch_status = 'SUPPRESSED'`、`suppress_reason = 'FREQUENCY_LIMIT'`。
5. 三道闸门全过 → 调 M03-05 `POST /internal/v1/message/send`。
6. **无论结果如何都落 `m19_fu_touch_log`**，逐条记录三闸门的 `passed` 与 `result`。
7. 全过后 `INCR` Redis 频次计数，`EXPIRE` 到次日 00:05。

> **为什么失败的触达也要落库：** 患者投诉「你们半夜给我发短信」，我们需要证明当时拦住了。只记录成功的触达，等于把「我们做对了」的证据丢掉。数据结构 `ck_m19_fu_touch_log_gate_all` 保证 `gate_all_passed` 等于三个闸门的逻辑与，不可能出现「三闸门都过了但状态是 SUPPRESSED」这种矛盾。

### 6.6 错误码定义表（唯一权威）

> **本节是 M19-02 错误码的唯一权威定义。** 全文其他位置提及错误码时只能逐字引用本表含义，或标注 `—`。`validate_m19.py` 的 `check_errcode_semantics()` 以本表为基准校验全文一致性。

**号段：** 本子模块占用 `"1902001"` 起的连号段，已使用 16 个（至 `"1902016"`），模块通用错误码为 `"199001"`。共享规范 §11 分配给 M19-02 的号段容量充足，本次只用到前 16 个，后续新增错误码一律接在 `"1902016"` 之后，不复用、不跳号。

| 错误码 | HTTP | 含义 | 触发场景 | 处置建议 |
|---|---|---|---|---|
| `"1902001"` | 404 | 随访任务不存在 | 调 M03-04 取任务时任务 ID 不存在或已被删除 | 刷新待办列表；确认任务是否已被 M03-04 取消 |
| `"1902002"` | 404 | 执行记录不存在 | 按 `exec_no` 查不到执行记录 | 检查执行号是否输错；重新从工作台进入 |
| `"1902003"` | 409 | 执行状态不允许该操作 | 对非 `IN_PROGRESS` 的记录保存答案、对非 `FAILED` 的消息重放、对已 `CLOSED` 的异常做处置 | 刷新页面看当前状态；按状态机判断可行操作 |
| `"1902004"` | 409 | 数据已存在 | 同一任务重复创建执行记录、同一执行重复创建同规则异常单、同一任务重复登记失访 | 直接使用已存在的记录；不要重复提交 |
| `"1902005"` | 400 | 必答项未完成 | 提交结果时问卷必答题未全部作答 | 回到问卷补齐必答题；`SKIPPED` 的必答题也需要补答 |
| `"1902006"` | 400 | 请求参数不合法 | 时间跨度超 365 天、数值越界、文本长度不符、`CRITICAL` 未指定升级通道 | 按提示修正参数后重试 |
| `"1902007"` | 400 | 问卷模板不可用 | 问卷模板未启用或当前版本不存在 | 联系 M19-01 维护人员确认模板状态 |
| `"1902008"` | 503 | 随访任务服务不可用 | 调 M03-04 标记 `EXECUTING` 时超时或 5xx | 稍后重试；若持续请检查 M03-04 健康度 |
| `"1902009"` | 400 | 拨打次数不足 | 未达 `m19.fu.lost.min_call_attempts` 就判失访 | 至少拨打 3 次后再登记失访 |
| `"1902010"` | 409 | 回写消息状态不允许重放 | 对非 `FAILED` 状态的消息执行重放或忽略 | 只有重试耗尽的消息才需要人工处置 |
| `"1902011"` | 400 | 导出数据量超限 | 导出预估行数超过 `m19.fu.export.max_rows` | 缩小时间范围或增加筛选条件 |
| `"1902012"` | 400 | 任务池数据已过期 | 待办缓存超过 30 分钟未刷新，任务派中医嘱已变更 | 点「刷新」重新拉取待办 |
| `"1902013"` | 403 | 无权查看完整手机号 | 未授权 `m19:fu:exec:view_phone`，或执行记录不在执行中状态，或审计写入失败 | 申请权限；确认执行记录处于执行中 |
| `"1902014"` | 409 | 配置版本冲突 | 修改配置时 `expected_version_no` 与库中不一致（他人已改） | 重新拉取配置后再次提交 |
| `"1902015"` | 200 | 触达已被压制 | 三道闸门之一未通过（退订/黑名单/免打扰/频次超限/失败关闭），业务上不算失败 | 查看 `gate_results` 确定哪道闸门拦下；不要重试 |
| `"1902016"` | 400 | 服务令牌无效 | 内部接口未带 `X-Service-Token` 或令牌已过期 | 更新服务令牌配置 |
| `"199001"` | 403 | 无权限访问该资源 | 缺少所需权限编码，或数据权限范围外 | 向管理员申请对应权限 |

> **`"1902015"` 返回 HTTP 200 而非 4xx。** 触达被闸门拦住是**正常的业务结果**，不是系统错误——按总纲 §5.4「宁可漏发也不能错发」，压制是设计预期的行为。用 200 + `touch_status = 'SUPPRESSED'` 表达，调用方看 `touch_status` 而不是 HTTP 码。

```python
# app/services/m19_fu.py
import hashlib
import json
from datetime import datetime, timedelta
from decimal import Decimal
from typing import Any, Dict, List, Optional

from sqlalchemy import exists, func, select
from sqlalchemy.dialects.postgresql import insert as pg_insert
from sqlalchemy.orm import Session

from app.core.errors import BizError
from app.core.redis_client import RedisLock, redis_client
from app.models.m19_fu import (
    Abnormal,
    Answer,
    CallLog,
    ExecRecord,
    Lost,
    ResultDetail,
    TouchLog,
    Writeback,
)
from app.services.m03_client import M03Client
from app.services.m19_config import FuConfigResolver


class ExecService:
    """随访执行核心服务。"""

    def __init__(
        self,
        db: Session,
        m03: M03Client,
        config: FuConfigResolver,
    ) -> None:
        self.db = db
        self.m03 = m03
        self.config = config

    async def start_exec(self, payload, user):
        """开始执行：先调 M03-04 置 EXECUTING，再落本地记录。"""
        idem_key = "m19:idem:exec:%s" % payload.idempotency_key
        cached = await redis_client.get(idem_key)
        if cached is not None:
            data = json.loads(cached)
            data["replayed"] = True
            return data

        existing = self.db.execute(
            select(ExecRecord).where(
                ExecRecord.task_id == payload.task_id,
                ExecRecord.is_deleted.is_(False),
            )
        ).scalar_one_or_none()
        if existing is not None:
            return self._to_start_response(existing, replayed=True)

        # 步骤 1：先调 M03-04 标记 EXECUTING（失败则整体不做）
        try:
            task = await self.m03.start_task(payload.task_id)
        except Exception as exc:
            raise BizError("1902008", "随访任务服务不可用") from exc

        # 步骤 2：快照任务关键字段
        exec_no = self._next_no("FE")
        record = ExecRecord(
            exec_no=exec_no,
            task_id=task["task_id"],
            task_no=task["task_no"],
            patient_id=task["patient_id"],
            patient_name=task["patient_name"],
            followup_scene=task["followup_scene"],
            node_name=task["node_name"],
            priority=task["priority"],
            plan_date=task["plan_date"],
            exec_dept_id=task["exec_dept_id"],
            dept_name=task.get("dept_name", ""),
            executor_id=user.id,
            executor_name=user.name,
            followup_method=payload.followup_method,
            status="DRAFT",
            writeback_status="PENDING",
            started_at=datetime.now(),
            created_by=user.id,
        )
        self.db.add(record)
        self.db.flush()

        # 步骤 3：同一事务写回写消息（TASK_START）
        self.db.add(
            Writeback(
                msg_no=self._next_no("FW"),
                biz_type="EXEC",
                biz_no=exec_no,
                action="TASK_START",
                target_url="/internal/v1/followup/tasks/%s/start" % task["task_id"],
                request_body={"task_id": task["task_id"]},
                msg_status="PENDING",
                attempt=0,
                max_attempt=self.config.get_int("m19.fu.writeback.max_attempt"),
                next_retry_at=datetime.now(),
            )
        )
        self.db.commit()

        resp = self._to_start_response(record, replayed=False)
        await redis_client.setex(idem_key, 86400, json.dumps(resp, default=str))
        return resp

    async def save_answers(self, exec_no: str, payload, user):
        """逐题保存问卷答案（幂等 upsert，区分未答与答否）。"""
        record = self._get_record_or_raise(exec_no)
        if record.status != "IN_PROGRESS":
            raise BizError("1902003", "执行状态不允许该操作")

        saved = 0
        abnormal_hits = 0
        for item in payload.answers:
            self._assert_answer_shape(item)
            stmt = pg_insert(Answer).values(
                exec_id=record.id,
                exec_no=record.exec_no,
                questionnaire_id=payload.questionnaire_id,
                questionnaire_version=payload.questionnaire_version,
                question_id=item.question_id,
                question_code=item.question_code,
                question_no=item.question_no,
                question_type=item.question_type,
                question_text=item.question_text,
                answer_state=item.answer_state,
                answer_value=item.answer_value,
                answer_text=item.answer_text,
                answer_code=item.answer_code,
                answer_numeric=item.answer_numeric,
                answer_numeric_unit=item.answer_numeric_unit,
                answered_at=datetime.now() if item.answer_state == "ANSWERED" else None,
                answered_by=user.id if item.answer_state == "ANSWERED" else None,
                is_required=item.is_required,
                sort_no=item.question_no,
                created_by=user.id,
            )
            update_cols = {
                "answer_state": stmt.excluded.answer_state,
                "answer_value": stmt.excluded.answer_value,
                "answer_text": stmt.excluded.answer_text,
                "answer_code": stmt.excluded.answer_code,
                "answer_numeric": stmt.excluded.answer_numeric,
                "answer_numeric_unit": stmt.excluded.answer_numeric_unit,
                "answered_at": stmt.excluded.answered_at,
                "answered_by": stmt.excluded.answered_by,
                "updated_at": datetime.now(),
                "updated_by": user.id,
            }
            stmt = stmt.on_conflict_do_update(
                index_elements=["exec_id", "question_id"],
                set_=update_cols,
            )
            self.db.execute(stmt)
            saved += 1
            if item.answer_state == "ANSWERED" and item.hit_abnormal_rule:
                abnormal_hits += 1

        if record.status == "DRAFT":
            record.status = "IN_PROGRESS"
        self.db.commit()

        progress = self._calc_progress(record.id)
        return {
            "code": 0,
            "message": "success",
            "data": {
                "saved": saved,
                "progress": progress,
                "abnormal_hits": abnormal_hits,
                "saved_at": datetime.now().strftime("%Y-%m-%d %H:%M:%S"),
            },
        }

    async def submit_result(self, exec_no: str, payload, user):
        """提交结果：本地落库 + 写消息表，同一事务，然后异步回写。"""
        record = self._get_record_or_raise(exec_no)
        if record.status != "IN_PROGRESS":
            raise BizError("1902003", "执行状态不允许该操作")

        progress = self._calc_progress(record.id)
        if self.config.get_bool("m19.fu.exec.require_full"):
            if progress["required"] > 0 and progress["answered"] < progress["required"]:
                raise BizError("1902005", "必答项未完成")

        if not (10 <= len(payload.result_summary) <= 500):
            raise BizError("1902006", "结果摘要长度必须为 10~500 字")

        try:
            details = payload.details or self._map_details(record.id)
            for d in details:
                self.db.add(
                    ResultDetail(
                        exec_id=record.id,
                        exec_no=record.exec_no,
                        task_id=record.task_id,
                        patient_id=record.patient_id,
                        patient_id_hash=self._hash_id(record.patient_id),
                        followup_scene=record.followup_scene,
                        detail_code=d.detail_code,
                        detail_name=d.detail_name,
                        detail_group=d.detail_group,
                        value_type=d.value_type,
                        value_numeric=d.value_numeric,
                        value_text=d.value_text,
                        value_code=d.value_code,
                        value_unit=d.value_unit,
                        eye_side=d.eye_side,
                        severity=d.severity,
                        is_abnormal=d.is_abnormal,
                        ref_low=d.ref_low,
                        ref_high=d.ref_high,
                        source_answer_id=d.source_answer_id,
                        source_question_code=d.source_question_code,
                        collected_at=datetime.now(),
                        created_by=user.id,
                    )
                )

            abnormals = self._raise_abnormals(record, user)
            msg_no = self._next_no("FW")
            now = datetime.now()
            record.status = "SUBMITTED"
            record.exec_result = payload.exec_result
            record.result_summary = payload.result_summary
            record.executed_at = now
            record.submitted_at = now
            record.writeback_status = "PENDING"
            self.db.add(
                Writeback(
                    msg_no=msg_no,
                    biz_type="EXEC",
                    biz_no=record.exec_no,
                    action="TASK_RESULT",
                    target_url="/internal/v1/followup/tasks/%s/result"
                    % record.task_id,
                    request_body={
                        "status": "COMPLETED"
                        if payload.exec_result == "COMPLETED"
                        else "FAILED",
                        "executed_at": now.strftime("%Y-%m-%d %H:%M:%S"),
                        "executed_by": user.id,
                        "executed_by_name": user.name,
                        "result_summary": payload.result_summary,
                    },
                    idempotency_key="%s:TASK_RESULT" % record.exec_no,
                    msg_status="PENDING",
                    attempt=0,
                    max_attempt=self.config.get_int("m19.fu.writeback.max_attempt"),
                    next_retry_at=now,
                )
            )
            self.db.commit()
        except Exception:
            self.db.rollback()
            raise

        from app.tasks.m19_fu import send_writeback

        send_writeback.delay(msg_no)

        return {
            "code": 0,
            "message": "success",
            "data": {
                "exec_no": record.exec_no,
                "status": record.status,
                "writeback_status": "PENDING",
                "writeback_msg_no": msg_no,
                "abnormals": abnormals,
                "executed_at": now.strftime("%Y-%m-%d %H:%M:%S"),
            },
        }

    async def get_exec_status_by_task(self, task_id: int):
        """P-11 契约实现：单索引查询，P95 <= 100ms。"""
        record = self.db.execute(
            select(ExecRecord).where(
                ExecRecord.task_id == task_id,
                ExecRecord.is_deleted.is_(False),
            )
        ).scalar_one_or_none()

        if record is None:
            return {
                "code": 0,
                "message": "success",
                "data": {
                    "task_id": task_id,
                    "found": False,
                    "exec_no": None,
                    "exec_status": None,
                    "exec_result": None,
                    "writeback_status": None,
                    "executed_at": None,
                    "closed_at": None,
                    "abnormal_flag": False,
                    "lost_flag": False,
                },
            }

        abnormal_flag = self.db.execute(
            select(exists().where(Abnormal.exec_id == record.id))
        ).scalar()
        lost_flag = self.db.execute(
            select(exists().where(Lost.exec_id == record.id))
        ).scalar()

        return {
            "code": 0,
            "message": "success",
            "data": {
                "task_id": task_id,
                "found": True,
                "exec_no": record.exec_no,
                "exec_status": record.status,
                "exec_result": record.exec_result,
                "writeback_status": record.writeback_status,
                "executed_at": self._fmt(record.executed_at),
                "closed_at": self._fmt(record.closed_at),
                "abnormal_flag": bool(abnormal_flag),
                "lost_flag": bool(lost_flag),
            },
        }

    def _get_record_or_raise(self, exec_no: str) -> ExecRecord:
        record = self.db.execute(
            select(ExecRecord).where(
                ExecRecord.exec_no == exec_no,
                ExecRecord.is_deleted.is_(False),
            )
        ).scalar_one_or_none()
        if record is None:
            raise BizError("1902002", "执行记录不存在")
        return record

    def _calc_progress(self, exec_id: int) -> Dict[str, Any]:
        row = self.db.execute(
            select(
                func.count().filter(Answer.is_required.is_(True)),
                func.count().filter(
                    Answer.is_required.is_(True),
                    Answer.answer_state == "ANSWERED",
                ),
            ).where(Answer.exec_id == exec_id, Answer.is_deleted.is_(False))
        ).one()
        required = int(row[0] or 0)
        answered = int(row[1] or 0)
        completeness = None
        if required > 0:
            completeness = round(Decimal(answered) / Decimal(required), 6)
        return {
            "answered": answered,
            "required": required,
            "completeness": float(completeness) if completeness is not None else None,
        }

    @staticmethod
    def _assert_answer_shape(item) -> None:
        has_value = any(
            v is not None
            for v in (
                item.answer_value,
                item.answer_text,
                item.answer_numeric,
                item.answer_code,
            )
        )
        if item.answer_state == "ANSWERED" and not has_value:
            raise BizError("1902006", "已作答状态必须提供答案内容")
        if item.answer_state != "ANSWERED" and has_value:
            raise BizError("1902006", "非作答状态不得携带答案内容")

    def _map_details(self, exec_id: int) -> List[Any]:
        mapping = self.config.get_json("m19.fu.detail.mapping")
        rows = self.db.execute(
            select(Answer).where(
                Answer.exec_id == exec_id,
                Answer.is_deleted.is_(False),
            )
        ).scalars().all()
        details = []
        for ans in rows:
            spec = (mapping or {}).get(ans.question_code)
            if not spec or ans.answer_state != "ANSWERED":
                continue
            details.append(
                self._build_detail(ans, spec)
            )
        return details

    @staticmethod
    def _build_detail(ans: Answer, spec: Dict[str, Any]) -> Any:
        from app.schemas.m19_fu import ResultDetailItem

        return ResultDetailItem(
            detail_code=spec["detail_code"],
            detail_name=spec.get("detail_name", spec["detail_code"]),
            detail_group=spec.get("detail_group", "GENERAL"),
            value_type=spec.get("value_type", "TEXT"),
            value_numeric=ans.answer_numeric,
            value_text=ans.answer_text,
            value_code=ans.answer_code,
            value_unit=ans.answer_numeric_unit,
            eye_side=spec.get("eye_side", "NA"),
            severity=spec.get("severity"),
            is_abnormal=ans.is_abnormal,
            ref_low=spec.get("ref_low"),
            ref_high=spec.get("ref_high"),
            source_answer_id=ans.id,
            source_question_code=ans.question_code,

    def _raise_abnormals(self, record: ExecRecord, user) -> List[Dict[str, Any]]:
        rows = self.db.execute(

                Answer.is_abnormal.is_(True),
                Answer.is_deleted.is_(False),

        created = []
        now = datetime.now()
        window_hours = self.config.get_int("m19.fu.abnormal.review_window_hours")
        for ans in rows:

                    "abnormal_no": abnormal.abnormal_no,
```

```python
from typing import Any, Dict

from sqlalchemy import select
from sqlalchemy.orm import Session

from app.core.errors import BizError
from app.core.redis_client import RedisLock
from app.models.m19_fu import ExecRecord, Lost, Writeback
from app.services.m03_client import M03Client
from app.services.m19_config import FuConfigResolver


class WritebackService:
    """回写 M03-04 的本地消息表驱动服务。"""

    def __init__(
        self,
        db: Session,
        m03: M03Client,
        config: FuConfigResolver,
    ) -> None:
        self.db = db
        self.m03 = m03
        self.config = config

    async def send_one(self, msg_no: str) -> Dict[str, Any]:
        """发送一条回写消息，失败则按指数退避安排下次重试。"""
        msg = self.db.execute(
            select(Writeback).where(Writeback.msg_no == msg_no)
        ).scalar_one_or_none()
        if msg is None:
            raise BizError("1902002", "回写消息不存在")
        if msg.msg_status == "SUCCESS":
            return {"msg_no": msg_no, "skipped": True, "reason": "already_success"}

        lock = RedisLock("m19:lock:writeback:%s" % msg_no, ttl=60)
        if not lock.acquire():
            return {"msg_no": msg_no, "skipped": True, "reason": "locked"}

        try:
            msg.msg_status = "SENDING"
            msg.attempt = (msg.attempt or 0) + 1
            self.db.commit()

            try:
                resp = await self.m03.post_raw(
                    url=msg.target_url,
                    body=msg.request_body,
                    idempotency_key=msg.idempotency_key,
                    timeout=10.0,
                )
                msg.msg_status = "SUCCESS"
                msg.http_status = 200
                msg.resp_body = str(resp)[:2000]
                msg.succeeded_at = datetime.now()
                self.db.commit()
                self._on_success(msg)
                return {"msg_no": msg_no, "msg_status": "SUCCESS"}
            except Exception as exc:
                self._on_failure(msg, exc)
                self.db.commit()
                return {"msg_no": msg_no, "msg_status": msg.msg_status}
        finally:
            lock.release()

    def _on_success(self, msg: Writeback) -> None:
        """回写成功后推进业务状态到终态。"""
        if msg.biz_type == "EXEC" and msg.action == "TASK_RESULT":
            record = self.db.execute(
                select(ExecRecord).where(ExecRecord.exec_no == msg.biz_no)
            ).scalar_one_or_none()
            if record is not None:
                record.writeback_status = "SUCCESS"
                record.writeback_at = datetime.now()
                record.status = "CLOSED"
                record.closed_at = datetime.now()
                self.db.commit()
        if msg.biz_type == "LOST":
            lost = self.db.execute(
                select(Lost).where(Lost.lost_no == msg.biz_no)
            ).scalar_one_or_none()
            if lost is not None:
                lost.m03_writeback_status = "SUCCESS"
                lost.m03_writeback_at = datetime.now()
                self.db.commit()

    def _on_failure(self, msg: Writeback, exc: Exception) -> None:
        """失败：未超上限则退避重试，超上限则置 FAILED 并告警。"""
        max_attempt = msg.max_attempt or 5
        base = self.config.get_int("m19.fu.writeback.backoff_base_seconds")
        msg.last_error_code = getattr(exc, "code", "M03_ERROR")
        msg.last_error_msg = str(exc)[:500]

        if msg.attempt >= max_attempt:
            msg.msg_status = "FAILED"
            msg.exhausted_at = datetime.now()
            msg.alert_sent = True
            self.db.commit()
            self._alert_dead(msg)
        else:
            delay = base * (2 ** (msg.attempt - 1))
            msg.msg_status = "PENDING"
            msg.backoff_s = delay
            msg.next_retry_at = datetime.now() + timedelta(seconds=delay)
            self.db.commit()

    async def scan_due(self, limit: int = 100, dry_run: bool = False):

        now = datetime.now()

        if dry_run:

                "message": "success",
                "data": {
                    "scanned": len(rows),
                    "triggered": 0,
                    "skipped": 0,
                    "dry_run": True,
                    "duration_ms": 0,
                },

            triggered += 1

        return {
            "code": 0,
            "message": "success",
            "data": {
                "scanned": len(rows),
                "triggered": triggered,
                "skipped": 0,
                "dry_run": False,
                "duration_ms": 0,
            },
        }

    async def replay(self, msg_no: str, payload, user):
        """人工重放：只有重试耗尽的消息可重放。"""
```

## 7. 缓存与异步任务

本章说明 M19-02 的缓存策略、异步任务与定时作业。M19-02 是「执行侧」子模块，它的性能瓶颈不在自身 SQL，而在**每一次操作都要同步调用 M03-04**。因此缓存设计的第一原则是：**缓存只缓存「可以短暂过期而无害」的东西，绝不缓存状态判断的权威事实**。

### 7.1 Redis 缓存设计

#### 7.1.1 Key 规范与总表

M19-02 的 Redis key 统一遵循共享规范 §14：

```
m19:fu:exec:{资源}:{标识}          # M19-02 专属前缀
m19:code:{prefix}:{yyyyMMdd}       # 公共：单号生成器
m19:idem:{biz}:{key}               # 公共：幂等键
m19:lock:{biz}:{id}                # 公共：分布式锁
m19:throttle:{patient_id}:{date}   # 公共：触达频次计数
```

**为什么 M19-02 的 key 前缀是 `m19:fu:exec:` 而不是 `m19:fu:`？** 共享规范 §12 把 `m19_fu_` 前缀分给了 M19-01（配置类，`m19_fu_script` 等 7 张表）和 M19-02（事实类，9 张表）共用。如果 Redis 前缀也只写到 `m19:fu:`，M19-01 的话术缓存与 M19-02 的执行缓存会混在同一个命名空间下，运维用 `SCAN m19:fu:*` 清理时无法区分归属，一次误清就会把另一个子模块的缓存打掉。加上 `exec` 这一段后，边界与表归属完全对齐。

| # | Key 模板 | 类型 | TTL | 写入方 | 读取方 | 失效时机 |
|---|---|---|---|---|---|---|
| C-01 | `m19:fu:exec:status:{task_id}` | String(JSON) | 60 秒 | P-11 查询结果回填 | P-11 | 执行记录状态变更时主动 DEL |
| C-02 | `m19:fu:exec:progress:{exec_id}` | Hash | 300 秒 | 问卷答案保存后更新 | 工作台进度条 | 答案保存、结果提交 |
| C-03 | `m19:fu:exec:todo:cnt:{executor_id}:{date}` | String | 120 秒 | 工作台统计卡片 | P01 统计卡片 | 任务开始/完成/回写成功 |
| C-04 | `m19:fu:exec:pool:{dept_id}` | String(JSON) | **30 分钟** | 待办列表回填 | P01 列表 | 到期自然失效，不主动删 |
| C-05 | `m19:fu:exec:cfg:{scope_type}:{scope_id}` | Hash | 600 秒 | 配置读取回填 | 全部业务校验 | 配置更新时主动 DEL |
| C-06 | `m19:idem:exec:start:{idempotency_key}` | String | 86400 秒 | 开始执行接口 | 开始执行接口 | 24 小时后自然过期 |
| C-07 | `m19:lock:exec:submit:{exec_id}` | String | 30 秒 | 结果提交 | 结果提交 | 提交完成后主动释放 |
| C-08 | `m19:lock:writeback:{msg_no}` | String | 120 秒 | 回写投递 | 回写投递 | 投递完成后主动释放 |
| C-09 | `m19:code:{prefix}:{yyyyMMdd}` | String(INCR) | 至次日 00:05 | 单号生成 | 全部建单接口 | 次日 00:05 过期 |
| C-10 | `m19:fu:exec:partition:{yyyyMM}` | String | 3600 秒 | 分区存在性探测 | 外呼记录写入 | 新建分区后 DEL |

#### 7.1.2 缓存一致性策略

**策略一：状态类缓存（C-01）使用「写后删」而非「写后改」。**

```
变更流程：
  ① 事务内更新 m19_fu_exec_record.status
  ② 事务提交成功
  ③ DEL m19:fu:exec:status:{task_id}
  ④ 若 DEL 失败（Redis 不可用）→ 记 WARN 日志，不阻断业务
```

**为什么是删而不是改？** 「写后改」在并发下会产生旧值覆盖新值：线程 A 读到 status=DRAFT，线程 B 读到 status=DRAFT，A 先更新为 IN_PROGRESS 并写缓存，B 后更新为 SUBMITTED 但写缓存时被 A 的请求延迟打断，最终 A 的 IN_PROGRESS 覆盖了 SUBMITTED。删除则不会——删除后下一次读必然回源查库，而数据库里的值是唯一的。代价是多一次回源查询，但 P-11 的回源查询 P95 只有 45ms（`uk_m19_fu_exec_record_task` 唯一索引覆盖），完全可以承受。

**策略二：任务池缓存（C-04）宁可返回旧数据也不返回错误数据。**

M03-04 的待办接口 P95 ≤ 100ms，但按科室一次可能返回 200~500 条。如果每次打开工作台都实时拉取，日均 2000 门诊量下 M03-04 会被打穿。因此 M19-02 缓存任务池 30 分钟（总纲 §7.3 决策 3 明确规定）。

但缓存的任务池会与真实状态产生偏差：护士在 A 电脑上完成了一个任务，B 电脑上的列表缓存里它还在「待执行」。处理方式是**缓存只用于「列表展示」，任何「状态判断」都回源**：

| 场景 | 数据来源 | 理由 |
|---|---|---|
| 列表渲染任务标题、患者姓名、计划日期 | C-04 缓存 | 这些字段几乎不变，过期 30 分钟无害 |
| 点击「开始执行」时的状态校验 | **实时调 M03-04** | 状态判断绝不能靠缓存，否则会重复执行 |
| 统计卡片数字 | C-03（120 秒） | 允许 2 分钟偏差，但会比列表新 |
| 提交结果时的幂等判断 | **实时查库** | 幂等靠 `uk_m19_fu_exec_record_task` 兜底 |

**策略三：缓存穿透保护。**

P-11 是内部接口，调用方只会传真实存在的 `task_id`。但 M03-04 的定时核对作业会扫描全量历史任务的执行状态，其中大量是「从来没有被 M19 处理过」的老任务。这类 `task_id` 在 `m19_fu_exec_record` 里查不到，如果每次都回源查库，一次全量扫描 43.8 万条任务会打出 43.8 万次无效查询。

因此 P-11 对「查不到」的结果也做缓存，用空值占位：

```json
{"__miss__": true, "checked_at": "2026-11-06 10:12:33"}
```

TTL 固定 60 秒，比正常结果更短。**为什么可以缓存「不存在」而不会漏掉后续产生的新记录？** 因为 `m19_fu_exec_record` 只在「开始执行」时创建，而开始执行一定会走 `ExecService.start_exec`，该方法在创建记录后立即 `DEL m19:fu:exec:status:{task_id}`。所以新记录不会落在空值占位的 60 秒窗口里。

**策略四：配置缓存（C-05）支持分域覆盖。**

`m19_fu_config` 有 `scope_type`（GLOBAL/DEPT/ORG）+ `scope_id` 三维。读取顺序是 `DEPT` → `ORG` → `GLOBAL`，第一个命中的生效。如果缓存 key 只写 `m19:fu:exec:cfg`，科室级配置会互相覆盖。因此 key 必须带 scope：

```
m19:fu:exec:cfg:DEPT:12    → 科室 12 的全部配置（Hash，field = config_key）
m19:fu:exec:cfg:GLOBAL:0   → 全局配置（Hash）
```

一次业务校验通常要读 3~5 个配置项，用 Hash 一次 `HMGET` 取回，比 5 次 GET 少 4 次往返。配置更新接口（API-27）在事务提交后 DEL 对应 `{scope_type}:{scope_id}` 的整个 Hash——因为一次更新可能改多个 key，逐个 DEL 容易漏。

#### 7.1.3 缓存容量估算

| Key 类型 | 基数 | 单条大小 | 总量 | 说明 |
|---|---|---|---|---|
| C-01 状态 | 活跃任务约 3,000 | ~400 B | ~1.2 MB | 60 秒 TTL，实际同时存活远小于基数 |
| C-02 进度 | 执行中记录约 50 | ~200 B | ~10 KB | 活跃窗口极短 |
| C-03 计数 | 随访员约 40 人 × 1 天 | ~100 B | ~4 KB | 可忽略 |
| C-04 任务池 | 科室约 30 个 | ~150 KB | ~4.5 MB | 这是最大的占用，30 分钟 TTL |
| C-05 配置 | 配置域约 80 个 | ~2 KB | ~160 KB | 10 分钟 TTL |
| C-06 幂等键 | 日 1,200 × 24 小时窗口 | ~80 B | ~2.3 MB | 24 小时 TTL |
| C-07/C-08 锁 | 并发提交约 20 | ~100 B | ~2 KB | 秒级存活 |

**合计峰值约 8.2 MB。** 相对 Redis 实例通常分配的 2~4 GB 内存，占比不到 0.5%，不需要单独扩容。C-04 是唯一需要关注的一项：如果某科室任务池超过 500 条，单条 key 会涨到 300 KB 以上，此时应按 `page` 分片缓存（`m19:fu:exec:pool:{dept_id}:1`），避免单 key 过大导致 `GET` 阻塞主线程。

### 7.2 异步任务（Celery）

M19-02 的异步任务分两类：**业务驱动型**（由用户操作触发）与**定时扫描型**（由调度器触发）。所有任务都必须满足幂等——Celery 在 worker 崩溃后会重投，任务体必须能承受重复执行。

#### 7.2.1 任务总表

| 任务名 | 触发方式 | 队列 | 重试策略 | 幂等保证 | 说明 |
|---|---|---|---|---|---|
| `m19.fu.writeback.send` | 业务驱动 | `q_m19_writeback` | Celery 最多 3 次，自带退避 | `m19:lock:writeback:{msg_no}` + 消息状态机 | 投递单条回写消息到 M03-04 |
| `m19.fu.writeback.scan` | 定时 60 秒 | `q_m19_scan` | 不重试 | `next_retry_at` 乐观条件更新 | 扫描到期消息并投递 |
| `m19.fu.exec.expire` | 定时每小时 | `q_m19_scan` | 不重试 | 状态条件更新 `WHERE status='DRAFT'` | 把超时未开始的记录置 EXPIRED |
| `m19.fu.abnormal.overdue` | 定时 5 分钟 | `q_m19_scan` | 不重试 | 状态条件更新 | 把超过 4 小时未复访的异常置 OVERDUE 并告警 |
| `m19.fu.partition.ensure` | 定时每日 02:00 | `q_m19_scan` | 不重试 | `CREATE TABLE IF NOT EXISTS` | 预建下个月的外呼记录分区 |
| `m19.fu.stats.settle` | 定时每日 01:00 | `q_m19_stats` | 不重试 | 按 `stat_date` upsert | 结算前一日接通率与完成率快照 |
| `m19.fu.export.record` | 业务驱动 | `q_m19_export` | 不重试（用户可重发） | 导出任务号唯一 | 异步导出执行记录 |

#### 7.2.2 回写投递任务

这是本子模块最关键的异步任务。它的失败直接等于「随访员白干了一次电话」。

```python
# app/tasks/m19_fu_writeback.py
from __future__ import annotations

import logging
from datetime import datetime, timedelta

from celery import shared_task
from sqlalchemy import select

from app.core.redis import RedisLock
from app.db.session import session_scope
from app.models.m19_fu import Writeback
from app.services.m19_fu_writeback import WritebackService

logger = logging.getLogger(__name__)

BACKOFF_BASE_SECONDS = 30
BACKOFF_MAX_DELAY = 1800


@shared_task(
    name="m19.fu.writeback.send",
    bind=True,
    max_retries=3,
    default_retry_delay=10,
    acks_late=True,
)
def send_writeback(self, msg_id: int) -> dict:
    """投递单条回写消息。acks_late=True 保证 worker 崩溃时消息不丢。"""
    with session_scope() as db:
        msg = db.get(Writeback, msg_id)
        if msg is None:
            return {"ok": False, "reason": "MSG_NOT_FOUND"}
        if msg.msg_status in ("SUCCESS", "DEAD"):
            return {"ok": True, "reason": "SKIPPED", "status": msg.msg_status}

    lock_key = "m19:lock:writeback:%s" % msg_no_of(msg_id)
    try:
        with RedisLock(lock_key, ttl=120, wait_timeout=5):
            with session_scope() as db:
                service = WritebackService(db)
                result = service.send_one(msg_id)
            return {"ok": True, "result": result}
    except RedisLock.Timeout:
        logger.info("writeback %s is being delivered by another worker", msg_id)
        return {"ok": True, "reason": "LOCKED_ELSEWHERE"}
    except Exception as exc:  # 网络抖动等可重试异常交给 Celery 的 3 次重试
        logger.exception("writeback %s delivery raised", msg_id)
        raise self.retry(exc=exc, countdown=min(60, 10 * (self.request.retries + 1)))


@shared_task(name="m19.fu.writeback.scan")
def scan_writeback() -> dict:
    """扫描到期消息并逐条投递。只做「挑出来」，不做投递本身。"""
    with session_scope() as db:
        service = WritebackService(db)
        due_ids = service.scan_due(limit=200)
    for msg_id in due_ids:
        send_writeback.delay(msg_id)
    return {"scanned": len(due_ids)}
```

**为什么扫描任务是「挑出来」而不是「自己投递」？** 如果扫描任务自己循环调用 M03-04，一次扫到 200 条就要在同一个任务里串行发 200 次 HTTP，单次超时 3 秒的话最坏要 600 秒，早已超过 Celery 的 task time limit，任务被杀掉后已完成的部分不会回滚，下次扫描会重复投递前 100 条。拆成「扫描 + 单条投递」后，每条消息有独立的超时与重试上下文，扫到 200 条只会产生 200 个短任务，任何一个失败都不影响其他，也不会出现「整批超时」这种灾难性失败模式。

#### 7.2.3 超时失效任务

```python
# app/tasks/m19_fu_expire.py
from datetime import datetime, timedelta

from celery import shared_task
from sqlalchemy import update

from app.db.session import session_scope
from app.models.m19_fu import ExecRecord

DRAFT_EXPIRE_HOURS = 48


@shared_task(name="m19.fu.exec.expire")
def expire_stale_drafts() -> dict:
    """把超过 48 小时仍停在 DRAFT 的执行记录置为 EXPIRED。

    置 EXPIRED 不删除记录：M03-04 的任务仍然是 PENDING/ASSIGNED，
    第二天会重新出现在待办池里，由别的随访员接手。
    """
    deadline = datetime.now() - timedelta(hours=DRAFT_EXPIRE_HOURS)
    with session_scope() as db:
        stmt = (
            update(ExecRecord)
            .where(ExecRecord.status == "DRAFT")
            .where(ExecRecord.created_at < deadline)
            .where(ExecRecord.is_deleted.is_(False))
            .values(status="EXPIRED", expired_at=datetime.now())
        )
        result = db.execute(stmt)
        return {"expired": result.rowcount}
```

**为什么是 48 小时？** 太短会在周末误杀——周五下午开始的执行，周一早上就过期了，可随访员本来就是周一来处理。48 小时能跨过一个周末而不跨过两个工作日，是经验值，通过配置项 `m19.fu.exec.draft_expire_hours` 可调（默认 48，范围 12~168）。

#### 7.2.4 异常复访超时任务

```python
# app/tasks/m19_fu_abnormal.py
from celery import shared_task
from sqlalchemy import update

from app.db.session import session_scope
from app.models.m19_fu import Abnormal


@shared_task(name="m19.fu.abnormal.overdue")
def mark_overdue_abnormal() -> dict:
    """把超过复访时限仍无人处置的异常置为 OVERDUE 并告警。

    只改 review_status，不改 review_deadline_at —— 时限是「应该什么时候做完」，
    过期后仍然要知道原来是几点到期，否则事后无法计算超期时长。
    """
    from app.services.m19_fu_alert import alert_abnormal_overdue

    with session_scope() as db:
        stmt = (
            update(Abnormal)
            .where(Abnormal.review_status == "PENDING")
            .where(Abnormal.review_deadline_at < __import__("datetime").datetime.now())
            .values(review_status="OVERDUE")
            .returning(Abnormal.id, Abnormal.abnormal_no, Abnormal.patient_id)
        )
        rows = db.execute(stmt).all()
    if rows:
        alert_abnormal_overdue(rows)
    return {"overdue": len(rows)}
```

### 7.3 定时作业（APScheduler）

APScheduler 负责触发上面这些 Celery 任务。它与 Celery beat 二选一，M19-02 选 APScheduler 是为了与模块内其他子模块保持一致，并且它能把每次触发记录写进 `m19_fu_config` 无关的独立表，便于运维排查「为什么今天没跑」。

| 作业 ID | Cron 表达式 | 触发的 Celery 任务 | 错过补偿 | 说明 |
|---|---|---|---|---|
| `job_fu_writeback_scan` | `* * * * *`（每分钟） | `m19.fu.writeback.scan` | 不补偿 | 回写扫描，间隔短不需要补偿 |
| `job_fu_exec_expire` | `0 * * * *`（每小时整点） | `m19.fu.exec.expire` | 补偿一次 | 漏跑一小时会在下次跑时一起处理 |
| `job_fu_abnormal_overdue` | `*/5 * * * *`（每 5 分钟） | `m19.fu.abnormal.overdue` | 不补偿 | 5 分钟窗口，漏跑一次影响小 |
| `job_fu_partition_ensure` | `0 2 * * *`（每日 02:00） | `m19.fu.partition.ensure` | 补偿一次 | 分区必须提前建，漏跑会导致写入失败 |
| `job_fu_stats_settle` | `0 1 * * *`（每日 01:00） | `m19.fu.stats.settle` | 补偿一次 | 统计快照 |

**为什么分区维护作业放在 02:00 而不是 00:00？** 00:00 是单号 Redis key 的过期边界与绝大部分日结任务的时间点，M16/M17 的日结也在这一时段。M19-02 的分区维护虽然很轻（一条 `CREATE TABLE IF NOT EXISTS`），但没必要挤在同一分钟。02:00 门诊系统完全空闲，且离下个月还有足够余量。

**错过补偿的实现方式**：APScheduler 的 `misfire_grace_time` 设为 3600 秒，作业因故未执行时在一次宽限期内补跑一次。补偿只做一次而不是无限补跑——分区维护这类作业天然幂等，补一次就够；无限补跑会在服务重启后产生大量重复触发。

### 7.4 缓存与异步的失败处理

| 失败场景 | 影响 | 处理方式 |
|---|---|---|
| Redis 不可用（缓存读） | 全部请求回源，数据库压力上升约 3 倍 | 熔断缓存层，直接查库；请求仍可用，只是变慢 |
| Redis 不可用（幂等键 C-06） | 无法用幂等键去重 | 降级为数据库唯一键 `uk_m19_fu_exec_record_task` 兜底，行为不变 |
| Redis 不可用（分布式锁 C-07） | 并发提交可能重复 | 数据库唯一键 + 行锁 `SELECT ... FOR UPDATE` 兜底 |
| Redis 不可用（单号 C-09） | **单号无法生成，建单失败** | 这是硬依赖，直接返回 503 并告警 P1 |
| Celery worker 全部宕机 | 回写消息积压，记录停在 SUBMITTED | 消息不丢（已落库），worker 恢复后积压消息被 `scan` 任务全部捞起 |
| Celery worker 部分宕机 | 部分消息投递慢 | `acks_late=True` 保证未确认消息回到队列 |

**为什么单号生成不能降级？** 单号（`FE202611060001`）是业务主键，患者与随访员都会拿它来对账。如果用数据库序列兜底，序列不受日期约束，`FE` 后面接一个小时不能表达当日的序号，运维查单时会看到 `FE000000123` 这种东西。宁可这一次建单失败让用户重试，也不产生一个格式异常的号——异常号一旦进入数据库就无法修正（它已经印在打印件上了）。

## 8. 业务规则与校验

#### 8.3.1 执行记录状态流转

| R-03-02 | IN_PROGRESS | 保存问卷答案 | IN_PROGRESS | `"1902003"` |
| R-03-03 | IN_PROGRESS | 提交结果 | SUBMITTED | `"1902003"` |
| R-03-04 | IN_PROGRESS | 放弃执行 | ABANDONED | `"1902003"` |
| R-03-05 | SUBMITTED | 回写成功（系统内部触发） | CLOSED | `"1902003"` |
| R-03-06 | DRAFT | 超时未开始（系统内部触发） | EXPIRED | — |
| R-03-07 | SUBMITTED | 恢复为 IN_PROGRESS | IN_PROGRESS | `"1902003"` |
| R-03-08 | CLOSED / ABANDONED / EXPIRED | 任何人工动作 | 不允许 | `"1902003"` |

**R-03-07 为什么允许 SUBMITTED 回退到 IN_PROGRESS？** 因为随访员提交后才发现「刚才那个 0.8 记错了，应该是 0.6」。此时如果回写已经成功（CLOSED），就必须走「补录」流程而不是直接改——已经写进 M03-04 的结果是别的模块在用的。只有还在 SUBMITTED（回写未成功或未开始）时才允许撤回修改，此时 M03-04 侧还没有收到任何结果，改完重新提交即可，不会产生不一致。

**R-04-29 是本子模块存在的核心理由之一。** 共享规范 §17 第 27 条把「失访登记后没回写 M03-04」列为高危坑，总纲 §3.1 指出了后果链：只记本地 → M03-04 任务永远停在 EXECUTING → 逾期监控永远把这批算成逾期 → 随访完成率失真 → 随访考核体系失效。因此失访登记的写回写消息不是「可选补偿」，而是与落库同一个事务的强制动作。

**R-07-05 为什么不用分布式锁？** 扫描任务是多实例并发的：3 个应用实例各自每分钟跑一次扫描，如果不做互斥，同一条消息会被 3 次投递。用 Redis 锁能解决，但多了一次 Redis 往返，且锁持有者的崩溃会导致消息滞留在 `next_retry_at` 已过、状态却是 PENDING 的中间态。改用数据库的条件更新后，每个实例执行 `UPDATE ... RETURNING`，PostgreSQL 的行锁保证同一条消息只会被一个实例拿到——这是「数据库自己就是那把锁」，不需要额外组件，也没有崩溃恢复问题。

#### 10.4.1 `mpi.followup.task.updated` 是回执，不是我们的写动作

这条事件由 M03-04 在**任务状态变更时**发出，载荷为 `task_id` / `old_status` / `new_status`。它的触发源有三类：M19 回写结果、M03-04 分派、M03-04 取消。**其中只有第一类是我们引起的，而且它仍然不是「我们的写动作」**——它是 M03-04 对「我们请求它改状态」这件事的回执。

**这条区分为什么关键？**

如果把 `mpi.followup.task.updated` 当成「M19 自己发起的事件」，会写出这样的处理逻辑：「收到 updated 且 `new_status='COMPLETED'` → 把执行记录置 CLOSED」。这是错的，后果是：

1. **自证循环**：我们把结果发给 M03-04（`writeback_status='PENDING'`），M03-04 改状态并发回 `updated`，我们据此置 CLOSED。但此时我们**并不知道 M03-04 是否真的落库成功**——事件可能来自另一个随访员对同一任务的另一次操作，也可能来自 M03-04 的批量纠错作业。用回执代替「HTTP 200 响应」作为闭环判据，等于把两套可靠性机制混成一套。
2. **状态倒挂**：如果 M03-04 在我们的 HTTP 请求超时（但我们已判失败并进入重试）之后才落库成功，`updated` 事件会先于重试成功到达。此时按事件置 CLOSED，而 `m19_fu_writeback` 里那条消息仍是 PENDING，重试任务会再发一次——CLOSED 记录又被打回去，或者产生第二条冗余请求。

**正确用法是「校准」而不是「推进」**：

| 本地状态 | 收到 `new_status` | 处理 |
|---|---|---|
| SUBMITTED 且 `writeback_status='SUCCESS'` | `COMPLETED` 或 `FAILED` | 一致，无动作（这是幂等回执） |
| SUBMITTED 且 `writeback_status='SUCCESS'` | `PENDING` / `ASSIGNED` / `EXECUTING` | **告警 P2**：我们已回写成功但 M03-04 不是终态，说明上游数据被外力改回。写 `m19_fu_exec_record.sync_anomaly` 标记，人工核对，**不自动改本地状态** |
| SUBMITTED 且 `writeback_status='PENDING'` | `COMPLETED` 或 `FAILED` | **说明 M03-04 其实已经收到了**（我们的 HTTP 响应丢了）。可以提前闭环：把消息置 SUCCESS、记录置 CLOSED，并 `alert` 一条 INFO。这是唯一允许「以事件推进」的场景，且必须先反查消息状态确认是 PENDING |
| CLOSED | 任意 | 无动作 |
| DRAFT / IN_PROGRESS / ABANDONED / EXPIRED | `COMPLETED` | 告警 P2：M03-04 已完成但我们本地还没执行，可能是别人在不同通道做的，记录并展示 |

**第三行是唯一例外，且要说明白为什么可以破例**：因为此时我们处在「请求发出去了但不知道结果」的不确定态。M03-04 的事件是我们唯一能确认它收到结果的信息源。破例的前提是三个条件同时成立——本地 `writeback_status='PENDING'`（我们确实发了但没确认）、`new_status` 是终态（COMPLETED 或 FAILED）、且事件在我们的消息投递之后到达。任一条不满足就走第一、二行的路径。

#### 10.4.2 两套状态如何互相推进（不混成一套）

M19-02 的执行记录状态与 M03-04 的任务状态是**两套独立的状态机**，靠 `task_id` 关联。它们的推进关系如下：

```
M03-04 任务状态（7 值，M03-04 权威）      M19-02 执行记录状态（6 值，本模块权威）
─────────────────────────────────        ─────────────────────────────────────
PENDING / ASSIGNED                        （尚无记录）
    │  M19 调 API-34 start                 │
    ▼                                      ▼
EXECUTING  ←────── 与本地 IN_PROGRESS 对应 ────  IN_PROGRESS
    │                                      │  随访员提交
    │                                      ▼
    │                                   SUBMITTED
    │                                      │  M19 调 API-33 result
    ├────────────── 回写成功 ──────────────┤
    ▼                                      ▼
COMPLETED / FAILED                      CLOSED

由 M03-04 单方面推进（M19 不写）：
    PENDING/ASSIGNED → OVERDUE           （mpi.followup.task.overdue）
    PENDING/ASSIGNED → CANCELLED         （mpi.followup.plan.cancelled）

由 M19 单方面推进（M03-04 不写）：
    DRAFT → IN_PROGRESS → SUBMITTED      （本地生命周期）
    SUBMITTED → IN_PROGRESS              （撤回修改，仅回写未成功时）
    IN_PROGRESS → ABANDONED
    DRAFT → EXPIRED

M19 可以写 M03-04 的三个状态（共享规范 §4.1）：
    EXECUTING（API-34）、COMPLETED（API-33）、FAILED（API-33）
    —— 除此之外的四个状态（PENDING/ASSIGNED/OVERDUE/CANCELLED）M19 一律不写
```

**为什么不能合并成一套状态？**

1. **生命周期主体不同**。M03-04 的任务从「计划生成」就存在，那时 M19 还没介入（可能根本不会有随访员去执行它）。而 M19 的执行记录从「随访员点开始执行」才存在。合并会把「从未被执行的 M03-04 任务」也算成 M19 的记录，43.8 万条/年的任务里大部分从未进入 M19。
2. **一处失败不能拖垮两处**。M03-04 的 `OVERDUE` 是定时作业打的，与 M19 是否执行过无关；M19 的 `EXPIRED` 是本地超时，与 M03-04 的 `OVERDUE` 完全不是一回事（一个任务可以既 OVERDUE 又被随访员正常执行）。合并后这两个状态必须二选一，任一方都会丢失信息。
3. **权威归属不同**。强行合并必然导致「谁写谁」的争抢。现在是明确分工：M03-04 拥有它自己的 7 个状态，M19 拥有自己的 6 个状态，唯一的交界处是 `task_id` + 状态映射表。

**映射表的用途**：`ExecRecordOut` 的 `exec_status` 走 M19 的 6 值；工作台列表展示时，前端同时拿到 M19 的 `exec_status` 与 M03-04 的 `task_status`，用映射表决定那个「状态标签」显示什么——**列表标签以 M03-04 为准**（因为它是权威），**执行操作按钮以 M19 为准**（因为能不能点取决于本地记录在哪一步）。

#### 10.4.2.1 `mpi.followup.task.overdue` 的处理：只写参考位，不改状态

M19 **不**因这条事件改自己的 `status`。逾期是 M03-04 的判定，M19 只把事件载荷落成两个参考字段（数据结构 4.2 节）：

| 字段 | 类型 | 写入规则 |
|---|---|---|
| `task_overdue_flag` | `BOOLEAN NOT NULL DEFAULT FALSE` | 收到事件置 `TRUE`；**此后任何状态流转都不回退为 FALSE** |
| `task_overdue_days` | `INTEGER` | 取自事件载荷 `overdue_days`，必须 ≥ 1；**一旦置值长期保留，不清空** |

**这两个字段是「参考位，非权威」。** 逾期判定的唯一权威是 M03-04 的事件。M19 绝不自己拿 `plan_date` 与当前时间比较来算逾期——两边各算一遍，只要宽限期、时区或节假日规则有一点差异，就会出现「M19 说逾期 3 天、M03-04 说逾期 2 天」，对账时无从裁决。**算逾期的模块只能有一个。**

工作台据此给行加红色标记、在排序权重里加分（8.5 节 R-05-06），P-11 直接返回这两个字段。**如果随访员在逾期后把任务做完了，M19 照常走 IN_PROGRESS → SUBMITTED → CLOSED，且这两个字段保持不变**——M03-04 侧由 COMPLETED 覆盖 OVERDUE 是它自己的规则，M19 不去修正它。

**为什么逾期痕迹必须保留？** 因为「逾期」是一件**发生过的事**，不是「当前状态」。一个任务第 10 天逾期、第 12 天被补做完成，管理层要回答的问题是「本月有多少条逾期后补做」——如果补做完成时把标志清掉，这个数字永远是 0，因为能算出来的分母里已经没有任何逾期任务了。这与 10.4.2 开头「一个任务可以既 OVERDUE 又被正常执行」是同一个论点：**状态会前进，历史必须守恒。**

#### 10.4.2.2 本地没有执行记录时的处理：不建记录

`mpi.followup.task.overdue` 到达时，如果本地**还没有对应的 `m19_fu_exec_record`**（该任务从未被随访员点开过），M19 **不建记录、不落库、只记一条 INFO 日志后丢弃**。

**为什么不能造一条 DRAFT 空记录来承载标志？**

1. **会污染审计线**。执行记录的核心审计价值是回答「本次随访由谁在何时开始、打了几个电话、问了什么」。如果为了存一个逾期标志而建一条记录，`executor_id` / `started_at` 只能填系统账号或留空——这意味着审计表里出现了一批「没人执行过却有执行记录」的行。随访纠纷时需要举证「谁在什么时候联系了患者」，这类假记录会让整条审计线不可信。
2. **会绕过 `uk_m19_fu_exec_record_task` 的语义**。这个唯一约束的语义是「一个任务只能被执行一次」，它同时是幂等基石。如果系统会自己建记录，那么随访员真正点「开始执行」时就会撞唯一键失败——他要么改代码走「认领已有空记录」的特殊路径（复杂度陡增），要么直接拿不到任务。
3. **收益近乎为零**。逾期状态在 M03-04 侧是权威且随时可查的，M19 侧唯一需要这个标志的场景是「有执行记录的任务在 P-11 里展示得怎么样」以及「逾期后补做的统计」。没有执行记录的任务，这两个场景都不成立。

**这个选择带来的口径差异（必须在报表说明里写清）：**

```
SELECT COUNT(*) FROM m19_fu_exec_record WHERE task_overdue_flag = TRUE
```

这条查询**只覆盖「有执行记录且收到过逾期事件」的任务**，会**系统性少算**那些至今无人问津的逾期任务。因此：

| 指标 | 数据源 | 说明 |
|---|---|---|
| 逾期任务总数 | **M03-04**（`mpi_followup_task` + `mpi.followup.task.overdue` 事件流） | M19 不得作为逾期总数的数据源 |
| 逾期后补做率 | M19-02（`task_overdue_flag = TRUE` 且 `status = CLOSED`） | 分母是「有执行记录且曾逾期」的任务，M19 是权威 |
| 逾期天数分布 | **M03-04** | 同逾期总数 |
| 单任务逾期天数展示（P-11） | M19-02（参考位） | 仅供调用方快速展示，最终以 M03-04 为准 |

**如果不能接受这个口径差异怎么办？** 那就必须在 M03-04 侧把逾期任务的完整列表通过 `mpi.followup.task.overdue` 推全（包括从未被点开的任务），由 M19-08 运营分析直接消费事件流而不是查 `m19_fu_exec_record`。这是 M19-08 的设计选择，不在本子模块范围内，但本子模块已经把「M19 不能作为逾期总数数据源」这条约束写明，供 M19-08 与其评审时引用。

#### 10.4.2.3 两套状态映射表

工作台列表的**状态标签以 M03-04 为准**（它是权威），**可操作按钮以 M19 为准**（能不能点取决于本地记录走到哪一步）。两者的映射关系：

| M19 执行记录 `status` | M03-04 任务可取的 `status` | 列表标签显示 | 可用按钮 |
|---|---|---|---|
| （无记录） | PENDING / ASSIGNED / OVERDUE / CANCELLED | M03-04 的状态 | 「开始执行」（CANCELLED 除外） |
| DRAFT | PENDING / ASSIGNED / OVERDUE | 待执行 | 「开始执行」「删除」 |
| IN_PROGRESS | EXECUTING / OVERDUE | 执行中 | 「继续填写」「放弃」 |
| SUBMITTED | EXECUTING / OVERDUE | 待回写 | 「撤回修改」（仅回写未成功） |
| CLOSED | COMPLETED / FAILED | 已完成 | 「查看」 |
| ABANDONED | PENDING / ASSIGNED / OVERDUE | 已放弃 | 「查看」 |
| EXPIRED | PENDING / ASSIGNED / OVERDUE | 已失效 | 「查看」「重新开始」 |

## 11. 异常处理与日志

### 11.1 异常分类

| 类别 | 典型场景 | 处理策略 |
|---|---|---|
| 参数异常 | 必答未完成、状态不允许、枚举非法 | 返回 4xx + 明确错误码，不告警 |
| 业务冲突 | 任务已被他人接管、配置版本冲突 | 返回 409 + 冲突详情，不告警 |
| 上游不可用 | M03-04 待办接口超时、M03-05 校验超时 | 按 10.1 的表处理，P1/P2 告警 |
| 数据不一致 | M03-04 说 COMPLETED 但本地是 DRAFT | 记录并告警 P2，人工核对 |
| 消息积压 | 回写 PENDING 超过 1 小时的数量 > 100 | 告警 P1 |
| 分区缺失 | 写入命中 `p_default` | 告警 P2，触发分区补建 |

### 11.2 降级策略

| 场景 | 降级方式 | 降级红线 |
|---|---|---|
| M03-04 待办不可用 | 展示最后缓存的任务池 + 顶部横幅「数据可能不是最新」 | **不允许对缓存任务执行提交**，提交必须实时校验 |
| M03-04 回写不可用 | 本地消息表重试 | 不允许把记录冒充为 CLOSED |
| M03-05 黑名单不可用 | 全部判为 `FAIL_CLOSED` | 不允许放行发送 |
| M03-05 消息发送不可用 | 转站内信 | 转投失败则 `SUPPRESSED` 次日重试 |
| M03-01 患者服务不可用 | 降级缓存 30 分钟 | 超 30 分钟拒绝新开始执行 |
| M01 人员服务不可用 | 用执行记录里的快照姓名 | 不影响提交 |
| Redis 不可用 | 单号生成直接失败 | 不允许用其他方式生成单号 |
| Celery 全不可用 | 回写消息积压 | 不允许丢弃消息 |

**「不允许对缓存任务执行提交」的含义**：如果工作台显示的是 30 分钟前的缓存任务池，某个任务可能已经被别人做完或在 M03-04 侧被取消。用户点「提交结果」时，系统必须实时调 M03-04 确认状态仍然是 EXECUTING 且执行人是自己，否则拒绝。缓存可以让列表看起来快，但不能让状态判断也变快——状态判断错了，后果是重复随访患者。

### 11.3 日志规范

所有日志采用 JSON 结构化输出，字段如下：

| 字段 | 必填 | 说明 |
|---|---|---|
| `ts` | ✓ | ISO8601 时间戳，毫秒精度，Asia/Shanghai |
| `level` | ✓ | DEBUG/INFO/WARN/ERROR |
| `logger` | ✓ | logger 名，形如 `app.services.m19_fu_exec` |
| `trace_id` | ✓ | 全链路 ID，由网关生成 |
| `span` | ✓ | 当前操作名，如 `start_exec`、`writeback.send` |
| `exec_no` | | 执行记录号（有则必填） |
| `task_id` | | M03-04 任务 ID |
| `writeback_no` | | 回写消息号 |
| `patient_id` | | **只记 ID，绝不记姓名与手机号** |
| `operator_id` | | 操作人 ID |
| `err_code` | | 业务错误码 |
| `msg` | ✓ | 人类可读摘要 |
| `cost_ms` | | 耗时 |

**日志禁止记录的内容**：患者姓名、完整手机号、身份证号、录音 URL 的签名部分、问卷自由文本答案（可能含隐私）。

### 11.4 监控指标

| 指标名 | 类型 | 阈值 | 说明 |
|---|---|---|---|
| `m19_fu_exec_start_total` | Counter | — | 开始执行次数，按科室/随访员 |
| `m19_fu_exec_submit_total` | Counter | — | 提交结果次数 |
| `m19_fu_writeback_pending_rows` | Gauge | **> 100 告警 P1** | 待回写消息堆积量 |
| `m19_fu_writeback_dead_rows` | Gauge | **> 0 告警 P2** | 死信数量 |
| `m19_fu_writeback_attempt_p95` | Histogram | > 2 告警 P2 | 回写尝试次数分布 |
| `m19_fu_writeback_cost_ms` | Histogram | P95 > 200 告警 | 单次回写耗时 |
| `m19_fu_abnormal_overdue_rows` | Gauge | **> 0 告警 P1** | 超时未复访的异常单数 |
| `m19_fu_call_partition_default_rows` | Gauge | **> 0 告警 P2** | **哨兵指标**：`p_default` 分区行数，见下 |
| `m19_fu_p11_cost_ms` | Histogram | P95 > 100 告警 | P-11 响应时间 |
| `m19_fu_touch_suppressed_ratio` | Gauge | > 0.3 告警 P2 | 触达压制比例，异常升高说明有配置问题 |
| `m19_fu_upstream_error_total` | Counter | 按上游分 | 上游调用失败数 |
| `m19_fu_draft_expired_total` | Counter | — | 超时失效记录数 |

**`m19_fu_call_partition_default_rows` 为什么是必设的哨兵？** `m19_fu_call_log` 按月分区，写入的 `created_at` 落在哪个月就进哪个分区。如果分区维护作业失败，新月份的数据会全部堆进 `p_default` 分区。这个分区本身是有意保留的（防止写入直接报错），但它一旦行数持续增长，就意味着分区维护失效了——具体影响是查询 `2026-12` 的数据需要扫描整个 `p_default`，性能下降一个数量级。有了这个指标，运维在问题发生的当天就能看到，而不是等到某天查询变慢才去查。
