### 0.3 四条铁律（违反即返工）

| # | 铁律 | 原因 |
|---|---|---|
| **1** | **数量口径三处一致**：页面总览树 `P0x` = 第 5 章 `### 5.x P0x` 标题；表清单 = `### 4.x 表：` 标题；接口总览 `API-01` 起连续无断号且每项有 `#### API-xx` 详述 | 全仓统一标准，交叉引用依赖编号稳定 |
| **2** | **M19 只做「执行」与「运营」，不重造「任务生产」**：随访模板、随访计划、随访任务的分派规则由 **M03-04 拥有**；M19 **只调用** M03-04 的 `GET /internal/v1/followup/tasks/pending` 拉任务、`POST .../start` 标执行中、`POST .../result` 回写结果。**绝不在 M19 里再建一套 `m19_followup_plan` / `m19_followup_task`** | M03-04 已建有 11 张随访表并已上线；M19 再建一套会导致同一台手术产生两份随访任务，护士在两个系统里看到两套待办，患者被重复骚扰两次。这是本模块**最严重的架构错误** |
| **3** | **技术栈 PostgreSQL 16**：不得出现 MySQL / Oracle 专有语法（自增关键字、定长整型、旧式日期时间类型、存储引擎子句、Oracle 字符串类型均禁用，详见 §15 自检项与 §17 第 14 条） | 全仓已统一 PostgreSQL，MySQL 语法是硬错误 |
| **4** | **积分与成长值必须可追溯到每一笔业务**：`m19_points_ledger` 是**只增流水**（`REVOKE UPDATE, DELETE`），账户余额是流水的**派生值**，任何余额调整都必须有对应流水行，禁止直接 UPDATE 账户表余额 | 积分是真金白银（可抵现、可换购）。余额与流水对不上就是账实不符，且无法回答「我这个月为什么少了 200 分」。审计必查项 |

> **M19 专属铁律（第 5 条）：触达必须尊重患者意愿，且必须有频次上限。**
> 每次对外触达（电话、短信、微信、站内消息）前**必须**经过三道闸门：① 患者/会员是否已退订该渠道（M03-05 `GET /internal/v1/message/check-blacklist` + `POST /internal/v1/message/unsubscribe`）② 弹窗/免打扰时段（默认 21:00~次日 08:00 不发短信与电话）③ **同一患者 24 小时内非医疗必要触达不超过 1 次**（术后随访属医疗必要，不在此限，但同一天仍不超过 2 次）。**任何一条不过，宁可漏触达也不发**——发错一条营销短信的代价远高于少触达一次。

> **M19 专属铁律（第 6 条）：会员权益核销必须幂等，一张券只能核一次。**
> 权益核销走 `核销单号 + 权益实例号` 双唯一索引，重复核销返回首次结果原样（不报错、不双扣）。核销与业务单据必须**同库同事务**或走**本地消息表**保证最终一致——收费成功但核销失败会导致「钱收了券还在」，核销成功但收费失败会导致「券没了没收钱」，两者都是客户投诉源。

## 1. M19 模块定位与子模块划分

### 1.1 一句话定位

**M19 随访与会员管理是全院「患者关系运营」的执行层与运营层**：它一手抓**随访执行**（把 M03-04 生产的随访任务真正打出去、问出结果、把异常捞出来），一手抓**会员运营**（积分、成长值、权益核销、营销活动、关怀召回），并为视光/屈光/门诊提供统一的会员识别与触达能力。

### 1.2 与 M03-04 / M03-03 的边界（最容易做错的地方，必读）

| 维度 | M03-04 随访（已有 11 张表） | **M19 随访与会员管理** |
|---|---|---|
| **谁定义随访模板** | ✅ `mpi_followup_template` + `_node`（节点、偏移天数、随访方式、问卷结构） | ❌ **不建模板表**，只读 M03-04，或在 M19 侧定义「话术脚本 / 问卷模板」用于**执行态**（问卷答案提交给 M03-04） |
| **谁生成随访计划** | ✅ `mpi_followup_plan`（按术式/出院/诊断触发） | ❌ **不生成计划**，只通过 `POST /internal/v1/followup/plans/trigger` 请求补建 |
| **谁分派随访任务** | ✅ `mpi_followup_task` + `_assign_rule`（按科室/医生/分组/轮询） | ❌ **不分派**，只读「分给我的任务」 |
| **谁执行随访（打电话、发微信、填问卷）** | ❌ 不做 | ✅ **M19-02 随访执行工作台**：外呼、话术引导、问卷填写、结果录入 |
| **谁存随访结果** | ✅ `mpi_followup_task_result`（M19 通过 `POST .../result` 回写） | ⚠️ **结果最终落 M03-04**，M19 只存「执行过程记录」（通话时长、录音引用、话术触达次数、问卷明细快照） |
| **谁做随访依从性/失访率分析** | ❌ 不做 | ✅ **M19-08 随访运营分析** |
| **谁定义会员等级/权益** | M03-03 `mpi_member_level` / `mpi_member_benefit` | ❌ **不重定义**，只读 |
| **谁存积分账户/流水/成长值** | ❌ 明确不做（M03-03 原文：「积分账户、积分流水、成长值 → M19」） | ✅ **M19-04 积分与成长值** |
| **谁做权益核销** | ❌ 明确不做（M03-03 原文：「权益核销记录、优惠券、营销活动 → M19」） | ✅ **M19-05 会员权益核销** |
| **谁做会员消费额统计/复购分析** | ❌ 明确不做 | ✅ **M19-06 会员运营分析** |

**一句话：M03-04 回答「谁该在什么时候被随访」，M19 回答「这次随访打出去了吗、问出了什么、异常有没有捞出来」；M03-03 回答「这个患者是什么会员等级、享有哪些权益」，M19 回答「他还剩多少积分、券核销了没有、这个月他的消费比上月多还是少」。**

> ⚠️ **典型错误（务必避免）：** 在 M19 里建 `m19_followup_plan` / `m19_followup_task`。
> **正确做法：** M19-02 的待办列表直接读 M03-04 的 `GET /internal/v1/followup/tasks/pending`，本地只缓存 `task_id` 与执行态上下文（Redis TTL 30 分钟），不落库。

> ⚠️ **第二个典型错误：** 在 M19 里建 `m19_member_level`。
> **正确做法：** 等级、权益定义、标签全部读 M03-03；M19 只存「积分账户」「积分流水」「权益实例（已领的券）」「核销单」。会员等级**由 M19 计算成长值后回写**给 M03-03（见 P-03）。

### 1.3 八个子模块划分

| 编号 | 子模块 | 核心职责 | 对应总体设计关键词 |
|---|---|---|---|
| **M19-01** | 随访中心与任务调度 | 随访中心工作台、任务池聚合、待办分派、随访话术与问卷模板（执行态）、随访渠道编排 | 「随访」的基础 |

| **M19-03** | 患者关怀与召回 | 关怀规则、生日关怀、久未到店召回、术后关怀、关怀任务与触达记录 | 「消息」 |

## 2. 全局技术约定

### 2.1 技术栈（与 README 7.1 一致，不得增删主项）

| 层 | 技术 | 版本 | 用途 |
|---|---|---|---|
| 语言 | Python | 3.11+ | — |
| Web 框架 | FastAPI | 0.110+ | REST API |
| ORM | SQLAlchemy | 2.0+ | `Mapped[]` 声明式 |
| 数据库 | PostgreSQL | **16** | **唯一支持版本** |
| 缓存 | Redis | 7+ | 任务池缓存、积分缓存、幂等、锁、限流 |
| 异步任务 | Celery | 5.3+ | 外呼回调、消息批量发送、积分批算 |
| 定时任务 | APScheduler | 3.10+ | 每日待办生成、生日关怀、召回扫描、积分过期 |
| 校验 | Pydantic | V2 | Schema |
| 迁移 | Alembic | 1.13+ | DDL 版本化 |

### 2.4 时间与数值

| 类型 | 格式 / 精度 | 示例 |
|---|---|---|
| 日期 | `YYYY-MM-DD` | `2026-10-21` |
| 时间 | `YYYY-MM-DD HH:MM:SS` | `2026-10-21 10:00:00` |
| 金额 | `NUMERIC(14,2)`，接口传 `Decimal`，JSON 里写两位小数 | `1234567.89` |
| 积分 | `NUMERIC(14,2)`（支持小数积分，如停车费积分） | `128.50` |

| 手机号 | 存储明文 `VARCHAR(20)`，接口返回脱敏 `138****5678` | — |

### 2.5 幂等与并发

| 场景 | 机制 |
|---|---|
| 积分发放 | 唯一键 `(biz_type, biz_no, rule_code)`，重复发放返回首次结果原样 |
| 权益核销 | 唯一键 `(redeem_no)` + 权益实例行 `FOR UPDATE`，`status` 必须为 `AVAILABLE` |
| 消息发送 | 幂等键 `(patient_id, template_code, biz_no)` 存 Redis 24h |
| 随访结果回写 | `(task_id, submit_seq)` 唯一，M03-04 侧亦幂等 |
| 券发放 | 唯一键 `(activity_id, patient_id, grant_seq)` |

### 2.6 数据库硬规范

| 项 | 规定 |
|---|---|
| 主键 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| 公共字段 | `created_at` / `created_by` / `updated_at` / `updated_by` / `is_deleted`（逻辑删除） |
| 金额类型 | `NUMERIC(14,2)`，**禁止 FLOAT/DOUBLE/REAL** |
| 比率类型 | `NUMERIC(10,6)` |
| 布尔 | `BOOLEAN` |
| 枚举 | `VARCHAR(32)` + CHECK 约束，值全大写英文 |
| 时长分区 | 日志类表按 `created_at` 月度 RANGE 分区，**必须有 DEFAULT 分区** |
| 索引 | 高频查询必须有部分索引；唯一索引注意 `is_deleted` 参与 |
| 大字段 | `JSONB`，必须写清结构 |

> **P-06/P-07/P-08 的适用范围红线（V1.1 新增，M19-07 提出冲突后裁决）：**
>
> **「券（voucher）」与「权益实例（benefit instance）」是两个不同的东西，核销归属不同，绝不能合并。**
>
> | 维度 | 券（voucher） | 权益实例（benefit instance） |
> |---|---|---|
> | 本质 | 可核销一次的**金额型**优惠凭证 | 非金额型或**跨场景**的会员权益（免费停车、免费复查、优先预约、生日礼遇） |
> | 是否挂结算单 | **必须**（`used_settlement_no` 反向追溯） | **不挂** |
> | 是否改变应付金额 | **是**（收银链路内唯一能改金额的环节） | 通常否 |
> | 定义表 | 券模板 `m19_mkt_coupon_template` + 发放实例 `m19_mkt_coupon`（M19-07） | `mpi_member_benefit`（M03-03 定义权益）+ `m19_benefit_instance`（M19-05） |
> | **状态机唯一权威** | **M16-06 `m16_discount_voucher`**（`ISSUED`/`LOCKED`/`USED`/`EXPIRED`/`VOIDED`，含 `lock_expires_at`、`used_settlement_no`、Redis 锁 `m16:discount:voucher:{code}` 30 分钟） | **M19-05 `m19_benefit_instance`** |
> | 核销台账 | `m16_discount_apply` | `m19_benefit_redeem` |
> | 锁定（lock/release） | M16-06（收银窗口会话态，天然属于收银台） | 不适用 |
>
> **判据一句话：核销这件事是否发生在收银台且改变应付金额——是，归 M16-06；否，归 M19-05。**
>
> 推论（成员必须遵守）：
> 1. **M19 绝不建自己的券核销状态表**，也绝不定义券的生命周期状态枚举。M19-07 的 `m19_mkt_coupon` 是**发放记录**，只存 `issue_status`（`PENDING`/`ISSUED`/`ISSUE_FAILED`/`VOIDED`，这是发放流程状态，不是券状态）。
> 2. 「这张券现在能不能用」**只能实时查 M16-06 API-13 `GET /api/v1/m16/discount/vouchers/{code}`**，M19 不缓存、不落库。两份状态必然打架（券退款恢复后 M19 还写着 `USED`），判断只许一个权威。
> 3. 若某条会员权益本质是「减免金额」（如「会员免费验光券」），它必须**落成 M16-06 的 `m16_discount_voucher`**，M19 只负责发放，不重复建核销表。
> 4. M16-06 原文「M16-06 只做核销」（`M16_收费结算管理_06_优惠与折扣执行_详细设计.md:315`）与 `m16_discount_voucher.issue_source` 的取值 `M03`/`M19`/`M16` 互为印证：**券码由 M03-03 或 M19-07 发放，券状态由 M16-06 持有。**

> **关于试算路径的裁决（V1.2，**撤回 V1.1**）：M19 不调用 M16 试算，也不自行定义试算契约；优惠金额由调用方算好后随核销请求传入。**
>
> V1.1 曾登记两条试算路径（① 复用 `POST /internal/v1/m16/discount/calc`（API-27）；② 由 M19 首次定义 `POST /internal/v1/billing/discount/trial`），**两条均不成立，现予撤回**。核查事实：
>
> 1. **`calc`（API-27）在 M16-06 中没有详述块。** 全文只有总览表一行（`M16收费结算管理/M16_收费结算管理_06_优惠与折扣执行_详细设计.md:905`）与 §10.2 提供接口表一行（`:3046`），后者调用方**只写 M16-01**；无请求体、无响应体、无业务逻辑编号步骤，不构成可引用的契约。M16-01 侧另有一个名字都不一样的 `POST /internal/v1/m16/discount/calculate`（`M16_收费结算管理_01_结算单与计费引擎_详细设计.md:2508` 的 U-08），说明这条路从未定稿。
> 2. **对外的 `/api/v1/m16/discount/trial`（API-02）形态上不适合服务间调用。** 其请求体只有 `{settlement_no, policy_codes, discount_mode, top_n}`；服务实现第一步即 `_load_base(settlement_no)` 按结算单加载项目清单，随后做全组合枚举并受 500ms 超时约束（同文件 `:1917-1955`）。而 **M19 核销发生时结算单尚未建立**（核销在收银台算完价之后、落单之前），根本没有 `settlement_no` 可传；该接口还需收费员权限 `m16:discount:view`，服务间调用不持有该身份。**因此绝不可用网关把内部路径映射到该对外接口**——那会整个绕过权限校验，是安全漏洞而非解决方案。
> 3. **「M19 首次定义一个自己的试算接口」是错误方向。** 试算的本质是「给定一批优惠策略 + 项目清单，算最优组合」，由 M16-06 的 `_compute_combo` / `_is_stackable` / `_meets_conflict` 实现。M19 若提供此接口，等于把组合枚举、叠加规则、互斥表全部复制一遍，**那就是第二份算钱逻辑**，而这正是「收银台减 200、会员中心减 199.5」的成因。
>
> **正确做法：金额由调用方（M16）算好后随核销请求传入，并附计算依据快照。** 即 P-06 请求体含必填的 `discount_amount` 与 `discount_basis`（JSONB，记录参与的策略编码、叠加模式、组合序号、计税基数 base_amount、试算时刻），M19 只做合理性与一致性校验（`0 <= discount_amount <= discount_basis.base_amount`）并原样落库为 `discount_basis_snap`，**一分钱都不算，也绝不兜底重算**。
>
> 依据快照必须落库的理由：M16-06 的试算结果缓存 `m16:discount:trial:{settle}:{hash}` 只有 120s TTL（同文件 `:2655`），事后再对账已无据可查；把依据留在核销记录里，才能回答「这 200 元当时是怎么算出来的」。
>
> **连带影响：U-04（M16 优惠试算）从 M19-05 的上游依赖中删除。** M19-05 不再有「试算服务超时 → 拒绝核销」这条失败路径；取而代之的是「`discount_amount` / `discount_basis` 缺失或不合法 → 拒绝核销」，仍坚持 fail-closed。

## 11. 错误码号段分配

| 子模块 | 号段 | 可用数量 |
|---|---|---|
| M19-01 | `"1901001"` ~ `"1901999"` | 999 |
| M19-02 | `"1902001"` ~ `"1902999"` | 999 |
| M19-03 | `"1903001"` ~ `"1903999"` | 999 |
| M19-04 | `"1904001"` ~ `"1904999"` | 999 |
| M19-05 | `"1905001"` ~ `"1905999"` | 999 |
| M19-06 | `"1906001"` ~ `"1906999"` | 999 |
| M19-07 | `"1907001"` ~ `"1907999"` | 999 |
| M19-08 | `"1908001"` ~ `"1908999"` | 999 |
| **模块通用** | `"199001"` | M19 无此权限 |

> 每个子模块建议使用 **35~45 个**错误码，从 `001` 连续编号，不留空号。

### 11.1 错误码定义表的唯一权威（强制）

**每个子模块的详细设计里，错误码只有一处可以「定义」它，其余所有位置只能「引用」它。**

这条规矩是被真实事故逼出来的（M22-03 曾出现同一份文档里三套互不相干的错误码含义，40 行中 33 行不一致）。

**强制要求**：

1. **唯一权威位置**：详细设计 **6.6 节错误码定义表**（若子模块把错误码表放在 6.2 或附录 A，则该处为权威位置，且**全文只能有一处**）。该表必须是 5 列：`错误码 / HTTP / 含义 / 触发场景 / 处置建议`。
2. **其余位置只能引用**：规则映射表、附录 C 总表、状态机表、API 详述里的「错误码」行、验收标准 AC/SC 引用——含义列必须与权威表逐字一致，或直接写 `—` 表示「此处不重复含义」。
3. **纯设计约束型规则挂 `—`**：像「不得跨模块直查」「触达必须过三道闸门」这类**架构约束**，不产生用户可见错误码，硬挂一个不相干的码是伪精确。**统一写 `—`**。
4. **权威口径取「代码 + 接口层实际用义」**：文档与代码冲突时，以运行时真正会吐出来的错误码为准。
5. **号段是真满的**：某号段用尽后必须**扩号段**（如从 `1901041` 起），**不得复用一个「看起来相近」的既有码**。复用会导致同一码两种语义——这是最难查的一类缺陷。
6. **校验**：`validate_m19.py` 的 `check_errcode_semantics()` 会抽取权威定义表的 `(错误码 → 含义)`，扫描全文其余所有 `| 错误码 | 语义 |` 表格行做比对。**同义改写放行**（二元组重合度 ≥ 0.30 即视为一致），**语义不同必须报出**。
7. **号段一律用文字描述，不要写成引号数字**（V1.1 新增）。例如写「本子模块占用 `1902001` 起的连号段，已使用 16 个」，**不要写** `"1902001" ~ "199999"`——`199999` 会被 `check_errcode_semantics()` 当成一个真实错误码去比对语义，然后报「错误码格式异常」。M22 那轮的 `2202999` 是同一个坑。同理，**任何「上界示例」都不要写成 6 位或 7 位的引号数字**。
8. **固定 5 列的超集也算合格**：若权威表除 5 列外还带「错误码常量名」等列，只要 5 列齐全即可，不算违规。
