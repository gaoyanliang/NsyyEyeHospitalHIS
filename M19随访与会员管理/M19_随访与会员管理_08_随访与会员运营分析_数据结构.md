## 1. 概述

### 1.1 设计目标

M19-08 是运营决策层子模块，本身**不产生任何业务主数据**。它的全部数据都是从上游派生出来的统计结果，因此数据结构设计要解决的不是"业务怎么记"，而是下面四个问题：

| 编号 | 目标 | 落地手段 |
| --- | --- | --- |
| DG-01 | 统计结果可追溯到算法版本 | 全表 `calc_version` + `calc_at`，口径变更后整期重算可新旧对比 |
| DG-02 | 区分"真 0"与"没数据" | 全表 `source_status`（COMPLETE/PARTIAL/MISSING）+ `is_estimated`，配组合 CHECK |
| DG-03 | 分母为 0 时比率必须为空 | 所有比率字段 `NULLABLE`，配 `CHECK (denominator > 0 OR rate IS NULL)` |
| DG-04 | 查询性能可控 | 查询只读预计算快照，日快照按年分区，所有查询列配覆盖索引 |

这四条是后续所有字段设计取舍的判据。凡是与它们冲突的设计方案，一律让位。

### 1.2 设计原则

#### 原则 1：派生数据不作主数据

本子模块 9 张表**没有一张是业务唯一数据源**。判断标准：把 `m19_stat_*` 全部 `TRUNCATE` 之后，系统业务能否继续运行？答案是能——随访任务照常执行、积分照常发放、权益照常核销，只是看板暂时空白，重算任务跑一遍就恢复。

这条原则带来的直接结果是：

- 不建任何外键指向业务表，避免业务表删除时被统计表阻塞；
- 不存业务主键的副本（如不存 `m19_followup_task` 的完整行），只存聚合结果和外键标识；
- 允许被上游删除的数据在快照里短暂"悬空"，由下次重算自然修正。

#### 原则 2：一条记录只描述一个确定的口径

完成率有"按时完成率"和"最终完成率"两个口径，**两者必须分别存字段，不能用一个字段加参数表达**。原因：一旦混存，下游任何一处取错参数都无法在数据层面被发现。

本文档里凡是出现"同一业务概念有多个口径"的地方，一律拆成独立字段，并在字段注释里写清分子分母。涉及的双口径字段见下表：

| 业务概念 | 字段对 | 分子差异 |
| --- | --- | --- |
| 随访完成 | `completion_rate` / `on_time_completion_rate` | 前者含逾期补做，后者不含 |
| 会员复购 | `repurchase_rate_patient` / `repurchase_rate_member` | 前者按 `patient_id` 去重，后者按 `member_id` 去重 |
| 随访触达 | `touch_rate` / `delivered_rate` | 前者 = 已发起触达，后者 = 已送达 |

#### 原则 3：缺失不留白，留白必有标记

上游不可用时，统计值写 NULL，同时在 `source_status` 与 `is_estimated` 上留痕。绝不允许用 0 冒充缺失值。这条原则与 M22-02 的教训一致：M22-02 曾因上游超时把缺失值填 0，导致月度汇总出现 "门诊量环比下降 43%" 的假告警。

#### 原则 4：维度字段空串而非 NULL

PostgreSQL 的唯一约束里 NULL 互不相等，如果一个维度列允许 NULL，那么 `(period, dept_id, NULL)` 可以插入任意多行，唯一约束形同虚设。因此所有维度字段一律 `NOT NULL DEFAULT ''`。

#### 原则 5：快照不参与业务事务

统计快照的写入与业务写入不共享事务。业务事务提交成功后发事件，统计侧异步消费，允许秒级延迟。代价是看板数据可能比业务数据滞后几秒到几分钟，收益是统计重算不会拖住挂号、收费、随访这些核心链路。

### 1.3 与上游数据的关系

本子模块的数据来源分三类，处理方式各不相同：

| 来源类型 | 具体来源 | 读取方式 | 落表策略 |
| --- | --- | --- | --- |
| 本模块业务表 | M19-01 随访执行记录、M19-02 关怀触达、M19-03 积分流水、M19-04 权益核销、M19-05 券实例、M19-06 活动 | 直接读本模块库表 | 按日聚合落 `m19_stat_daily` 等 |
| 上游契约 | M03-04 随访任务（`followup/tasks/pending` 等）、M03-03 会员、M16 收费统计、M22-01 指标口径 | 内部 HTTP 契约 | 不落原始数据，只落聚合结果与 `source_status` |
| 事件 | `m16.settlement.completed`、`m19.followup.executed`、`m19.care.delivered` 等 | 消息队列 | 触发重算，不直接落统计值 |

**关键点：M19-08 不建 `m19_followup_task` 之类的表。** 随访任务的生产归属 M03-04，M19 只做执行登记。因此"应随访任务数"这个分母必须通过 `GET /internal/v1/followup/tasks/pending` 或 M03-04 的统计口径获取，本地不落任务明细。

这与铁律 2 一致：M19 只做执行与运营，不重造任务生产。

### 1.4 表清单

**表数量：** 9 张

| 序号 | 表名 | 中文名 | 粒度 | 分区 | 预估行数（3 年） | 主要写入方 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `m19_stat_metric_def` | 统计指标定义表 | 指标 × 版本 | 不分区 | 300 | 配置任务 |
| 2 | `m19_stat_daily` | 随访运营日快照表 | 日 × 科室 × 场景 | 按年 RANGE | 2,600,000 | 日终批算 |
| 3 | `m19_stat_adherence` | 依从性快照表 | 月 × 科室 × 场景 × 随访员 | 不分区 | 540,000 | 月终批算 |
| 4 | `m19_stat_lost` | 失访分析表 | 月 × 科室 × 场景 × 失访序次 × 归因 | 不分区 | 180,000 | 月终批算 |
| 5 | `m19_stat_care_convert` | 关怀召回转化表 | 月 × 科室 × 关怀类型 × 渠道 | 不分区 | 72,000 | 月终批算 |
| 6 | `m19_stat_points` | 积分负债与消耗表 | 月 × 科室 | 不分区 | 1,800 | 日终批算 |
| 7 | `m19_stat_member` | 会员经营快照表 | 月 × 会员分层 × 生命周期 | 不分区 | 36,000 | 月终批算 |
| 8 | `m19_stat_export` | 统计导出任务表 | 任务 | 不分区 | 200,000 | 用户触发 |
| 9 | `m19_stat_rebuild_log` | 重算任务日志表 | 任务 × 表 | 不分区 | 60,000 | 重算触发 |

> 行数估算依据：假设合作机构年门诊量 73 万人次、年手术量 1.1 万台、注册会员 5 万人、活跃会员 1.5 万人（见总纲 §8.2 容量假设）。`m19_stat_daily` 每天约 2,400 行（平均 60 个科室 × 6 个随访场景 × 6 种随访方式的组合去重后），3 年约 260 万行，是本子模块唯一需要分区的大表。

**9 张表的分工不是平均切分的**，下面说明为什么是这 9 张而不是 8 张或 10 张：

- `m19_stat_metric_def` 单独成表的理由：指标口径不是代码常量，而是运营可以调整的配置。口径调整后必须能查到旧口径是什么，否则重算后的数字变了没人说得清原因。
- `m19_stat_daily` 与 `m19_stat_adherence` 分开的理由：前者是**日粒度事实**，供看板和趋势图；后者是**月粒度的人维度结果**，含随访员个人绩效，更新频率和权限要求都不同（月表要小样本抑制，日表不要）。放一张表会让 P02 依从性分析每次都扫日表过滤，而且小样本抑制规则无法在表级表达。
- `m19_stat_lost` 单独成表的理由：失访分析是本子模块对护理部最有价值的部分，它的分析维度（失访发生在第几次随访、失访节点）在其他任何表里都没有，且需要按归因原因交叉统计。
- `m19_stat_care_convert` 单独成表的理由：触达与转化之间是"触达流水 × 事后窗口"的关系，不能在一次聚合里算出来，必须单独落表。
- `m19_stat_points` 与 `m19_stat_member` 分开的理由：积分是财务敏感数据（涉及负债计提），会员经营是运营数据，两者权限不同——积分负债看板仅财务与院级管理员可见，会员经营看板护理部运营人员可见。
- `m19_stat_export` 与 `m19_stat_rebuild_log` 是运维支撑表，与业务统计无关，但必须与统计表同库，因为导出任务要引用快照的 `calc_version`。

## 2. 命名与类型规范

### 2.1 表与字段命名

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 表名 | `m19_stat_` + 名词，全小写下划线 | `m19_stat_daily` |
| 主键 | `id` | `id BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| 公共字段 | `created_at` / `created_by` / `updated_at` / `updated_by` / `is_deleted` | 五件套 |
| 布尔字段 | `is_` 前缀 | `is_estimated` / `is_final` |
| 时间字段 | `*_at` 后缀，`TIMESTAMPTZ` | `calc_at` / `execute_date` |
| 日期字段 | `*_date` 后缀，`DATE` | `stat_date` / `first_visit_date` |
| 周期字段 | `period` + `period_type` | `2026-10` + `MONTH` |
| 金额字段 | `*_amount`，`NUMERIC(14,2)` | `points_amount` |
| 积分字段 | `*_points`，`NUMERIC(14,2)` | `consumed_points` |
| 比率字段 | `*_rate`，`NUMERIC(10,6)` | `completion_rate` |
| 计数字段 | `*_cnt` 或 `*_count`，`INTEGER` | `total_task_cnt` |
| 维度字段 | 与被引用表字段同名 | `dept_id` / `scene` / `executor_id` |
| 中间变更追踪 | `metric_version` / `calc_version` | `calc_version INTEGER` |

**表名一律用单数**：`m19_stat_daily` 而非 `m19_stat_dailies`。理由：统计表的粒度不是"多行记录"而是"一个确定口径下的一组数"，用单数更贴近语义。

### 2.2 类型选型规则

| 数据类型 | 选型 | 理由 |
| --- | --- | --- |
| 主键 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 共享规范硬要求；BIGINT 保证 3 年内不溢出，IDENTITY 比 SERIAL 少一次序列依赖 |
| 计数 | `INTEGER` | 单日单科室的随访任务数在 10⁴ 量级，INTEGER 上限 21 亿足够；用 BIGINT 会让行变宽、索引变大 |
| 比率 | `NUMERIC(10,6)` | 6 位小数对应 0.0001% 精度。为什么不是 NUMERIC(5,4)：个别指标如异常发现率可能低到 0.0032，4 位小数会截成 0.0032 看不出差异；6 位能保留 |
| 金额 | `NUMERIC(14,2)` | 共享规范硬要求；禁止 FLOAT/DOUBLE/REAL，浮点无法精确表示 0.01，累加会漂移 |
| 积分 | `NUMERIC(14,2)` | 积分虽本质是整数，但共享规范规定为 NUMERIC(14,2)，与流水表保持一致，避免除法产生小数时截断 |
| 时间戳 | `TIMESTAMPTZ` | 全部带时区，统一存 UTC，展示层转 Asia/Shanghai。用 TIMESTAMP 无时区会跨时区出错 |
| 日期 | `DATE` | 统计周期边界用日期，不用时间戳，避免"当天 00:00 到 23:59:59"这类边界错误 |
| 枚举 | `VARCHAR(32)` + CHECK | 共享规范硬要求。不用 PostgreSQL 原生 ENUM，因为原生 ENUM 增删值需要 ALTER TYPE，锁表风险高 |
| 长文本 | `VARCHAR(n)` | 按实际需要定长，不用 TEXT，便于发现超长写入 |
| 结构化扩展 | `JSONB` | 只用于 `extra` 这类非查询字段，且必须在字段注释里写明结构 |
| 指纹 | `VARCHAR(64)` | SHA-256 十六进制 64 位 |

### 2.3 枚举落地方式

枚举列的写法固定为三件套：

1. 列定义 `xxx VARCHAR(32) NOT NULL DEFAULT 'xxx'`
2. 同名列的 CHECK 约束，枚举值用 `IN (...)` 穷举
3. 字段注释里写明枚举来源章节（如"见共享规范 §13.5"）

以随访场景为例：

```sql
scene VARCHAR(32) NOT NULL DEFAULT 'OTHER'
    CONSTRAINT ck_m19_stat_daily_scene
    CHECK (scene IN ('POSTOP', 'CHRONIC', 'OPTICAL', 'REVIEW', 'DISCHARGE', 'OTHER'))
```

**为什么不使用原生 ENUM 类型**：PostgreSQL 的 `ALTER TYPE ... ADD VALUE` 在 PostgreSQL 12 之后虽然可以在事务内执行，但删值仍然必须重建类型并重写全表。随访场景未来可能新增（如"术前宣教"），用 VARCHAR + CHECK 改约束只需 `ALTER TABLE ... DROP CONSTRAINT` + `ADD CONSTRAINT`，在表上不重写数据。

**枚举值一律全大写英文**，不接受中文值。中文展示名放在 `m19_stat_metric_def.unit` 之外的展示层配置里。

### 2.4 维度字段空值规则

这是 M19 整个模块踩过的坑（共享规范 §17 第 21 条）：**维度字段必须 `NOT NULL DEFAULT ''`，不能允许 NULL**。

原因用具体例子说明。假设 `m19_stat_adherence` 的唯一约束是：

```
UNIQUE (period, dept_id, scene, executor_id, calc_version)
```

如果 `executor_id` 允许 NULL，那么下面两行在 PostgreSQL 里都被允许同时存在：

```
('2026-10', 12, 'POSTOP', NULL, 1)
('2026-10', 12, 'POSTOP', NULL, 1)
```

因为 `NULL = NULL` 的结果是 `UNKNOWN` 而不是 `TRUE`，唯一约束对含 NULL 的行不生效。结果是"未分配随访员"这一组数据可以重复插入任意多次，每次重算都追加一批，月汇总直接翻倍。

因此本文档所有维度字段（`dept_id` 走整数除外）一律：

```sql
executor_id VARCHAR(64) NOT NULL DEFAULT ''
```

当业务上"没有随访员"时存空字符串，唯一约束正常生效。**数值型维度字段（`dept_id`）用 0 表示"全院合计"或"未分配"**，同样不用 NULL。

这条规则在 `m19_stat_daily` 上尤其关键，因为它的唯一约束包含 6 个维度列：

```
UNIQUE (stat_date, dept_id, scene, followup_method, channel, calc_version)
```

只要其中一个允许 NULL，整条唯一约束就在那一维度上失效。

**为什么全部不建物理外键**：

1. 本子模块的表是派生数据，`TRUNCATE` 后重算即可恢复。建外键会让"先删快照再重算"的操作受引用顺序约束，重算脚本复杂度上升。
2. 上游表分布在不同的 schema 甚至不同的数据库实例（M03-04 随访任务在主线，M16 收费在财务线），物理外键跨库不可行。
3. 统计表的数据量远大于主数据表，外键检查会成为批量写入的瓶颈。以 `m19_stat_daily` 日终批算为例，一次写入 2,400 行，如果每行触发 3 次外键检查，就多出 7,200 次索引查找。

**逻辑引用靠什么保证**：应用层在写入前校验引用存在性，校验失败则把对应维度落为空字符串或 0，并置 `source_status='PARTIAL'`。同时提供定时巡检 SQL（见附录 B.4）发现悬空引用。

### 3.3 分区与容量规划

| 表 | 分区策略 | 依据 | 单分区行数（3 年） | 维护方式 |
| --- | --- | --- | --- | --- |
| `m19_stat_daily` | 按 `stat_date` 年 RANGE 分区 + DEFAULT | 所有查询都带日期范围，分区裁剪有效 | 约 87 万/年 | 每年 12 月建下一年分区 |
| 其余 8 张 | 不分区 | 行数均 < 60 万，全表扫描在 200ms 内 | — | 无 |

#### 为什么只有 `m19_stat_daily` 分区

分区不是越多越好。分区带来两个成本：一是每次查询要在分区路由上多花 0.1~0.3ms，二是 DDL 维护要覆盖全部分区。

- `m19_stat_daily` 3 年 260 万行，看板默认查最近 30 天（约 7.2 万行），带分区裁剪只扫 1 个分区；不分区则要扫全表或用 `stat_date` 索引，索引扫描 3 年数据大约 12ms，加上回表约 45ms。虽然也能接受，但历史查询（如"去年同比"）会扫 2 个年度分区共 170 万行，不分区就要 60ms 以上。分区后稳定在 5ms。
- `m19_stat_adherence` 3 年 54 万行，最大查询是"某个随访员 12 个月的依从性趋势"，命中 `(executor_id, period)` 索引后返回 12 行，耗时 2ms。分区对它没有收益，反而让每月建分区变成负担。
- `m19_stat_points` 只有 1,800 行（月 × 科室），分区毫无意义。

#### 分区键选 `stat_date` 而非 `created_at`

`created_at` 是写入时间，`stat_date` 是业务日期。批算任务可能补算历史（如 11 月 3 日发现 10 月 28 日数据有误，重算那一天的快照），此时 `stat_date` 仍是 10 月 28 日但 `created_at` 是 11 月 3 日。如果按 `created_at` 分区，补算的数据会落到错误的年分区里，历史查询就查不到了。按业务日期分区，补算天然落到正确分区。

#### 分区的默认分区是强制的

```sql
CREATE TABLE m19_stat_daily_2026 PARTITION OF m19_stat_daily
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

CREATE TABLE m19_stat_daily_default PARTITION OF m19_stat_daily DEFAULT;
```

**不建 DEFAULT 分区的后果**：批算任务遇到超出已建分区范围的日期（比如 2027 年分区还没建就跑了 2027-01-01 的数据），`INSERT` 直接抛 `no partition of relation "m19_stat_daily" found for row`，整个批算任务失败，当天的看板全部空白。建了 DEFAULT 分区后，数据先落到默认区，运维巡检发现默认分区非空就补建正式分区并迁移。

这条对应共享规范 §17 第 22 条坑。

### 4.2 表：`m19_stat_metric_def`

#### 4.2.1 表说明

指标定义表是 M19-08 的**口径字典**，回答"这个数字是怎么算出来的"。

#### 4.2.4 `ck_m19_stat_metric_def_null_policy` 的算例

这条约束看起来只是两张枚举表之间的对应关系，实际上防的是一个会直接伤害科室的错误。

新科室 2026-09 开业，第一个月没有任何随访任务。如果完成率允许返回 0：

| 科室 | 应随访 | 完成 | 完成率 | 排名 |
| --- | --- | --- | --- | --- |
| 屈光中心 | 120 | 96 | 80.00% | 2 |
| 视光中心 | 200 | 170 | 85.00% | 1 |
| 新开科室 | 0 | 0 | **0.00%** | **3（垫底）** |

新科室开业首月就被排在最后，院长问起来"为什么新开的科室完成率是 0"，答"它没有任务"——那这个 0 就是纯粹的错误信息：0% 的含义是"有任务但一条没做"，与"没有任务"是两件完全不同的事。

正确做法是返回 NULL，前端展示 `—`，并且该科室**不进排名**（`rank_no` 为 NULL）。

因此 `unit = 'PCT'` 的指标必须配 `NULL_WHEN_ZERO`。这条约束在落库时就挡住"把百分比配成允许 0"的配置错误。

### 4.3 表：`m19_stat_daily`

#### 4.3.1 表说明

日快照表是本子模块的**核心事实表**，承载看板 P01 的全部指标块、P04 完成率分析的全部数据。

粒度定义为：**日期 × 科室 × 随访场景 × 随访方式 × 渠道**。一个科室一天如果同时有术后随访（电话）和慢病随访（微信），就产生两行；同一组合只产生一行。

#### 4.3.2 为什么粒度里要带 `followup_method` 和 `channel`

先看反例。如果粒度定为"日期 × 科室 × 场景"，那么一个科室一天只有一行。此时电话随访做了 30 条、微信随访做了 20 条，合成一行 `total_task_cnt = 50`。这张表能回答"今天屈光中心随访完成率多少"，但回答不了运营最常问的两个问题：

1. **"电话和微信哪个方式用户更愿意配合？"** —— 需要按方式拆开看完成率。合并后无法拆。
2. **"推送到微信送到没有？"** —— 微信有送达概念（`DELIVERED` / `FAILED`），电话没有。合并后渠道维度的送达率算不出来。

那为什么不拆得更细（比如再加随访员、患者来源）？因为拆得过细会让行数爆炸。粗算一下：

| 粒度组合 | 每日组合数 | 3 年行数 | 评价 |
| --- | --- | --- | --- |
| 日 × 科室 × 场景 | 60 × 6 = 360 | 39 万 | 太粗，没法按方式拆 |
| 日 × 科室 × 场景 × 方式 | 60 × 6 × 6 = 2,160 | 236 万 | **选中**，组合去重后约 2,400/天 |
| 日 × 科室 × 场景 × 方式 × 随访员 | 2,160 × 80 = 17 万 | 1.9 亿 | 太多 |

（每日实际行数 2,400 > 理论组合 2,160，是因为 `channel` 维度额外带来少量组合。）

随访员维度放在月粒度表 `m19_stat_adherence` 里，因为个人绩效看的是月度趋势，不需要日粒度。

**这里有个重要取舍要写清楚**：既然本表不含随访员维度，那"某随访员今天的表现"就查不到。这是有意的——单日单人样本量太小（一个随访员一天做 8 个任务），依从率在 8 个样本上的波动完全被噪声淹没，展示出来会诱导错误判断（今天 100%，昨天 50%，其实是随机的）。小样本抑制规则要求样本数 ≥ 5，虽然不是硬性禁止，但按日展示个人数据本身没有管理价值。月粒度累计到 200 条左右才稳定。

#### 4.3.4 双口径完成率为什么必须拆成两组字段

这是整个 M19-08 最容易被误读的地方，因此单独一节说清楚。

总纲 §6.3 给的算例：2026-10 某科室应随访 120 条，其中完成 96 条（84 条按期 + 12 条逾期补做），执行失败 18 条，逾期未做 6 条。

- **最终完成率** = 96 / 120 = **80.00%**
- **按时完成率** = 84 / 120 = **70.00%**

两者的分母相同（都是 120），分子差 12 条逾期补做，结果差 **10 个百分点**。

**含义完全不同**：

| 指标 | 回答的问题 | 谁关心 | 高低说明什么 |
| --- | --- | --- | --- |
| 最终完成率 | "这个患者最终被随访到了吗" | 医疗质量、护理部 | 反映随访覆盖率，患者是否被管理到 |
| 按时完成率 | "该随访的时候随访了吗" | 运营效率、随访员考核 | 反映时效性，异常是否被及时发现 |

如果只给最终完成率 80.00%，护理部会认为"还行"，但实际上有 12 个患者是在计划日期之后很久才随访到的——如果是术后 7 天复查，逾期到第 20 天才做，白内障术后眼内炎的最佳发现窗口已经过了。

如果只给按时完成率 70.00%，随访员会觉得"我明明都做完了怎么只有 70%"，因为 12 条补做的劳动没被承认。

**所以两个必须同时给，且必须分别落字段。** 用一个字段加参数（如 `rate_type=TIMELY`）的做法看似省空间，实际风险是：只要下游某处忘了传参数或传错默认值，就会静默取到另一个口径的数字，而数据层面完全看不出异常。

因此本表同时有 `completion_rate`、`on_time_completion_rate`、`late_makeup_rate` 三个字段，其中：

- `completion_rate` 与 `on_time_completion_rate` 是必须同时展示的一对；
- `late_makeup_rate` = 12 / 120 = 10.00%，恰好是前两者之差，用于直接定位"差距来自补做"。

`late_makeup_rate` 这个字段看似冗余（可以用前两者相减得到），但它存在的价值是**在做趋势图时不用做减法**。减法在 NULL 场景下会出错：如果某天 `on_time_completion_rate` 是 NULL（分母为 0），减法结果也是 NULL，无法区分"没有差距"和"没有数据"。

#### 4.3.6 `source_status` / `is_estimated` 组合约束详解

任务书给的形式是：

```sql
CHECK (source_status = 'COMPLETE' OR value IS NULL OR is_estimated = TRUE)
```

这条约束的含义：**数据不完整时，要么这个值根本没有、要么明确标记为估算值，绝不允许给一个看起来像真值的数。**

**为什么这条约束是必要的**：M22-02 踩过的坑——上游 M03-04 随访任务接口超时，实现里用 `if resp is None: total = 0` 兜底，结果当天所有科室完成率算成 0%（因为分母 0 走了除零保护返回 NULL，但另一些指标用了 0）。第二天接口恢复，数字从 0% 跳到 78%，运营误以为发生了重大事故去排查。

**这条约束在本表上的落地问题**：本表不是键值对的"宽表"，而是"一行多个指标"的宽表。`value IS NULL` 这个写法在这里没法直接套用——一行有 30 多个数值字段，无法在 CHECK 里逐个判断。

因此落地时拆成两条：

1. **`missing_sources` 非空约束**（对应 `ck_m19_stat_daily_missing`）：只要 `source_status <> 'COMPLETE'`，就必须写清缺的是哪个上游。这是"留痕"。
2. **`is_estimated` 显式声明约束**：`source_status = 'PARTIAL'` 时，如果数值字段有非零值，必须 `is_estimated = TRUE`。因为 PARTIAL 意味着"部分上游缺失但仍有数据"，此时有值就一定是估算或部分真实值，必须标记。

DDL 形式：

```sql
CONSTRAINT ck_m19_stat_daily_estimate CHECK (
    CASE
        WHEN source_status = 'COMPLETE' THEN TRUE
        WHEN source_status = 'MISSING'  THEN (total_task_cnt = 0 AND completed_task_cnt = 0)
        WHEN source_status = 'PARTIAL'  THEN (is_estimated = TRUE OR total_task_cnt = 0)
        ELSE FALSE
    END
)
```

这条比任务书给的三分支更严格，因为它额外要求 `MISSING` 状态下数值必须全为 0（即"没有数据就不许有数字"）。任务书的 `value IS NULL` 在宽表上做不到，用"计数全 0 + `source_status='MISSING'`"表达同样的语义。

**读表时的判断规则**（写进附录 A，也给前端）：

| source_status | is_estimated | 前端展示 | 是否进排名 | 是否推 M22 |
| --- | --- | --- | --- | --- |
| COMPLETE | FALSE | 正常数字 | 是 | 是 |
| PARTIAL | TRUE | 数字 + 感叹号角标 | 否 | 否 |
| MISSING | FALSE | `—` | 否 | 否 |

#### 4.3.8 索引

| 索引名 | 列 | 类型 | 用途 |
| --- | --- | --- | --- |
| pk_m19_stat_daily | (id, stat_date) | 主键 | — |
| uk_m19_stat_daily_key | (stat_date, dept_id, scene, followup_method, channel, calc_version) | 唯一 | 幂等写入与防重 |
| idx_m19_stat_daily_board | (stat_date, dept_id) WHERE is_deleted = FALSE | 普通 | P01 看板按日按科室 |
| idx_m19_stat_daily_period | (period, dept_id, scene) | 普通 | 趋势图按月聚合 |
| idx_m19_stat_daily_scene | (scene, stat_date) | 普通 | 按场景看趋势 |
| idx_m19_stat_daily_backlog | (stat_date) WHERE pending_task_cnt > 0 | 部分索引 | 积压监控 |
| idx_m19_stat_daily_abnormal | (stat_date) WHERE abnormal_found_cnt > 0 | 部分索引 | P05 异常发现趋势 |

**索引设计的三条理由**：

1. **看板索引 `idx_m19_stat_daily_board` 以 `stat_date` 打头**。P01 看板永远带日期条件（默认近 30 天），以分区键打头可以同时吃到分区裁剪和索引。如果以 `dept_id` 打头，跨科室看板就要扫一次索引全表再过滤日期，效率反而降低。
2. **唯一约束索引不单独建**。`uk_m19_stat_daily_key` 本身就是一个覆盖全部维度列的索引，`m19_stat_daily` 的幂等写入（`ON CONFLICT DO UPDATE`）就靠它。额外再建一个相同前缀的索引属于重复。
3. **积压与异常的索引用部分索引**。`pending_task_cnt > 0` 的行只占全部行的约 3%（绝大多数科室当天都能清完），部分索引体积从 260 万行压到 8 万行，扫描快 30 倍。

### 4.4 表：`m19_stat_adherence`

#### 4.4.1 表说明

依从性快照表是 P02 随访依从性分析的唯一数据源，粒度是 **月份 × 科室 × 场景 × 随访员**。

它与 `m19_stat_daily` 的核心差别有两点：一是多了 `executor_id`（随访员）维度，二是按**月**粒度而不是日。这两点是绑定的——因为月粒度样本量足够支撑个人维度分析。

#### 4.4.2 为什么按月而不是按日

以某个随访员为例，日均完成 8 条随访，月均 176 条。

| 粒度 | 样本量 | 依从率波动 | 管理价值 |
| --- | --- | --- | --- |
| 按日 | 8 | 100% 与 62.5% 之间来回跳 | 无。这叫随机噪声，不叫绩效 |
| 按周 | 40 | 95% 与 82% 之间 | 低 |
| 按月 | 176 | 稳定在 84%~88% | 高，能看出个人真实水平 |

具体算一下日粒度的噪声有多大：假设某随访员真实依从率是 85%，每天 8 条任务，那么当天依从条数服从二项分布 B(8, 0.85)。出现 8 条全按期（100%）的概率是 0.85⁸ = 27.2%，出现 6 条按期（75%）的概率是 30.3%。也就是说，**接近三成的日子会显示 100%，另外三成显示 75%，而这个人实际上完全没变**。如果按日排名，同一个随访员每天都可能从第 1 名掉到第 8 名。

按月 176 条时，标准差从 √(8×0.85×0.15)/8 ≈ 12.6% 降到 √(176×0.85×0.15)/176 ≈ 2.7%，波动被压到管理可接受的范围。

#### 4.4.4 小样本抑制规则

这是任务书设计要点 9（隐私与合规）的落地。

规则：`total_task_cnt < min_sample_size`（默认 5）时：

1. `adherence_rate` 与 `completion_rate` **仍然存值**（数据是真的，只是不适合展示个人）；
2. `is_suppressed = TRUE`，`suppress_reason = 'LOW_SAMPLE'`；
3. `rank_no = NULL`，`rank_total = NULL`，`grade = ''`；
4. 接口层返回时，若请求者是"查看他人绩效"身份，`adherence_rate` 返回 NULL；若请求者是本人，正常返回。

**为什么不直接不落库**：数据要留着做科室级汇总。一个月度科室汇总 = Σ 各随访员样本，如果把小样本行整个丢掉，科室汇总的分母会缺一块，导致科室级依从性算错。

**为什么排名用 NULL 而不是排到最后**：排到最后会让一个新入职随访员（第一个月只有 3 条任务刚好做对 3 条，依从性 100%）因为样本不足被排到第 12 名，看起来像表现差。用 NULL 表示"不参与排名"语义准确。

#### 4.4.5 横向对比规则

任务书要求写清"随访员个人绩效在展示时是否可横向对比"。规则如下：

| 使用者 | 能看到什么 | 依据 |
| --- | --- | --- |
| 随访员本人 | 自己的全部明细 + 自己在科室内排名 | 本人有权知道自己的位置 |
| 随访组长 | 本组全部成员的明细与排名 | 直接管理职责 |
| 护理部主任 | 全院随访员明细与排名 | 部门管理职责 |
| 其他随访员 | 只有聚合均值，不能看他人明细 | 防止同事之间互相攀比 |
| 其他科室人员 | 全不可见 | 无关 |

**为什么允许科室内排名但不允许跨科室排名**：科室之间的随访难度差异很大。屈光中心随访的是术后 30 岁年轻人，接通率 92%；老年科随访的是 75 岁以上慢病患者，接通率 68%。跨科室排名会把老年科的随访员永远排最后。科室内排名则是在相同工作条件下比较，公平。

### 4.5 表：`m19_stat_lost`

#### 4.5.1 表说明

失访分析表是 P03 失访分析的唯一数据源，也是本子模块对护理部最有价值的一张表。

它要回答的问题不是"失访了多少人"，而是下面三个：

1. **失访发生在第几次随访**——这决定了是流程设计问题还是患者依从性问题；
2. **哪个随访节点的失访率最高**——这指向具体的改进点；
3. **失访原因分布**——这决定改联系方式、改话术还是改时段。

#### 4.5.2 为什么粒度里必须有 `lost_seq`

`lost_seq` 是**失访序次**，取值 1、2、3……表示这是该患者第几次随访失访。

举例：一个白内障术后患者，计划随访 4 次（术后 1 天、7 天、1 月、3 月）。第 1 天那次接通了，第 7 天那次没接通（失访序次 1），第 1 月那次还是没接通（失访序次 2），第 3 月那次没接通（失访序次 3）。

如果不存 `lost_seq`，这个患者只会被记成"1 个失访"，三种失访的处置方式完全不同：

| 失访序次 | 典型原因 | 处置动作 | 成本 |
| --- | --- | --- | --- |
| 第 1 次 | 号码错误、刚出院不方便接电话 | 核对联系方式、改时间段再打 | 低 |
| 第 2 次 | 患者觉得没必要、在外地 | 换渠道（微信/短信）+ 说明随访价值 | 中 |
| 第 3 次 | 已迁居、已终止在本院就医 | 标记迁出、转年度信函 | 高，且往往无效 |

混在一起看，只能得出"失访 800 例"，护理部不知道从哪下手。拆开后能算出"第 1 次失访占 62%，其中 71% 是号码问题"，结论立刻可执行。

#### 4.5.4 `lost_reason` 与可执行洞察的对应关系

`lost_reason` 取值来自共享规范 §13：`PHONE_INVALID` / `UNREACHABLE` / `REFUSED` / `MOVED` / `DECEASED` / `OTHER`。

每种原因对应完全不同的处置动作，这就是为什么归因必须落库而不能事后猜：

| lost_reason | 中文 | 可执行洞察 | 责任岗位 | 系统动作 |
| --- | --- | --- | --- | --- |
| PHONE_INVALID | 号码空号错号 | 出院时联系方式录入错误 | 病案室/前台 | 拉出号码错误清单回溯录入环节 |
| UNREACHABLE | 多次未接通 | 拨打时段不对或未识别来电 | 随访员 | 调整外呼时段、开通来电名片 |
| REFUSED | 患者拒访 | 话术说教感强或价值未说清 | 随访组长 | 更新话术模板、减少随访频次 |
| MOVED | 已迁居 | 异地就医，本地随访不适用 | 护理部 | 改邮寄/线上随访，标记迁出 |
| DECEASED | 已故 | 需按死亡流程处理，不再随访 | 病案室 | 触发患者状态变更，停止随访 |
| OTHER | 其他 | 需人工归类 | 护理部 | 每月复核 |

**"术后第 1 天随访失访 → 多半是出院时联系方式录入错误"这个洞察是怎么得出的**：

术后第 1 天随访，患者刚刚出院，人在本地、手上有手机、刚做完手术有配合意愿——正常情况下接通率应该最高（实测 93.5%）。如果这一天失访率异常（实测 6.5%，是术后 7 天失访率 2.1% 的 3 倍），最可能的原因不是患者不想接，而是**这个号码根本打不通**。

验证方法：把术后第 1 天的失访记录按 `lost_reason` 拆开，如果 `PHONE_INVALID` 占其中 71%（实测数据），就证实是号码录入问题，而不是患者依从性问题。此时处置动作是查出院登记环节（谁录的、录的时候核对了吗），而不是给随访员加话术培训。

这个推导过程必须能落在数据上，因此 `lost_seq`、`node_name`、`node_offset_days`、`lost_reason` 四个字段必须同时存在且有值。缺任何一个，这个分析就做不出来。

### 4.6 表：`m19_stat_care_convert`

#### 4.6.1 表说明

关怀召回转化表是 P05 关怀召回转化分析的数据源，粒度是 **月份 × 科室 × 关怀类型 × 渠道**。

它回答的问题：**发出去的关怀消息，到底有没有把人叫回来？**

#### 4.6.2 为什么必须单独成表而不是拼进日快照

触达与转化之间隔着一个**观察窗口**，这个窗口的长度是可配置的（默认 14 天）。这意味着：

1. **触达当天的统计结果是不完整的**。10 月 20 日发的 500 条生日关怀，到 10 月 20 日日终时转化还是 0，因为窗口要到 11 月 3 日才关闭。如果把转化率算进日快照，10 月 20 日那天的数字会永远偏低。
2. **同一条触达会被多次重算**。11 月 3 日窗口关闭后再算一次，结果才定。而日快照的 `is_final` 是 D+7 封账，封账时窗口还没关。

因此转化率的正确做法是：**按"触达发生月"归属，等窗口全部关闭（月末 + 窗口期）后再出数**。

以 2026-10 月为例，10 月 31 日发出的触达，窗口 14 天要到 11 月 14 日才关。所以 10 月的关怀召回转化数据在 **11 月 15 日** 才能出，而 `m19_stat_care_convert` 的月终批算时间因此定在 **次月 16 日 02:00**。

这个时间差是设计上必须接受的，比"10 月 31 日就给出一个不完整的转化率"好得多。

#### 4.6.4 `convert_amount_snap` 为什么不叫 `convert_amount`

这是"不碰钱"铁律的落地。`convert_amount_snap` 的含义是"**从 M16 收费统计接口取回的金额快照**"，M19 自己不做任何加减。

字段命名带 `_snap` 后缀的作用是让任何一个开发者看到这个字段就知道：它不是本模块算出来的，改它没有意义，取不到就写 NULL。同时配 `convert_amount_ref` 存 M16 返回的批次号，任何时候都能回溯到原始数据。

**M19 不计算金额**，`roi_ratio` 里也不含金额除法——它是"召回人数/触达成本条数"这类无量纲比，具体定义见详细设计 §3.4。

#### 4.6.5 三类拦截为什么必须分开计数

触达被拦有三种原因，它们的严重程度完全不同：

| 拦截原因 | 含义 | 是否需要处理 |
| --- | --- | --- |
| `suppressed_unsub_cnt` | 患者已退订 | 不需要，这是患者的合法选择，永不再发 |
| `suppressed_time_cnt` | 落在 21:00~次日 08:00 免打扰时段 | 需要，应该改到白天发，或改投站内信 |
| `suppressed_freq_cnt` | 当日频次已达上限 | 需要，说明关怀策略太密集，应减少触达量 |

如果只记一个 `suppressed_cnt`，运营看到"拦截 1,200 条"只会觉得"系统在正常拦截"，看不到其中 800 条是本可以发出去的（时段问题），会把 32% 的关怀资源白白浪费。

分开计数后，看板能直接显示"因时段拦截 800 条，建议把生日关怀从 21:00 批量任务改到 10:00"。

### 4.7 表：`m19_stat_points`

#### 4.7.1 表说明

积分负债与消耗表是 P06 积分负债看板的数据源，粒度是 **月份 × 科室**。

它回答三个问题：

1. **本院欠会员多少积分**（负债余额，对应总纲 §6.6 的 128,600.00 元算例）；
2. **发了多少、用掉多少**（消耗率，长期低于 30% 说明超发）；
3. **过期了多少**（过期率，反映有效期设置是否合理）。

#### 4.7.2 积分负债为什么需要落库而不是实时算

`期末未消耗积分总额` 在原理上等于 `SUM(积分流水全部 GRANT) - SUM(全部 DEDUCT) - SUM(全部 EXPIRE) + 调整`。理论上一句 SQL 就能算出来，为什么还要落表？

三个原因：

1. **流水表在 M19-03 的库**，本子模块按契约读取，跨服务每次算负债都要拉全量流水，5 万会员、年均 1,200 万分、总流水可能上千万条，拉一次要几十秒。
2. **"期末"是历史概念**。今天算"2026-10-31 的期末余额"，需要把 2026-10-31 之后的所有流水倒推回去。历史某一天的余额**不能靠当前余额推算**，因为过期、退单会改变历史。
3. **会计口径要可复核**。M17 做积分负债计提时，需要的是一个可审计的确定数字加批次号，不是每次重算都可能略有不同的实时结果。

因此 `m19_stat_points` 每月封存一次，`balance_points` 是**该月末最后一刻的余额快照**，一经生成不再变动（除非显式重算）。

#### 4.7.4 期末余额的平衡等式约束

```text
begin_balance_points + issued_points - consumed_points - expired_points
    + adjusted_points + reversed_points = end_balance_points
```

这条等式是本表最重要的约束，因为它同时锁住了 7 个字段的一致性。**只要有一个字段被单独修改，等式立刻不成立，写入失败。**

为什么这条约束必要：一个常见的实现错误是"为了让负债数字好看，直接改 `end_balance_points`"。这样做在业务上等同于篡改财务数据。有平衡等式后，改任何单个字段都必须同时改另一个字段才能通过校验，而这在代码 review 和审计日志里非常显眼。

算例验证（对应总纲 §6.6）：

| 项目 | 数值 |
| --- | --- |
| 期初未消耗积分 | 11,800,000 |
| 期间发放 | 2,400,000 |
| 期间消耗 | 1,120,000 |
| 期间过期 | 220,000 |
| 期间调整 | 0 |
| 期间冲正 | 0 |
| **期末未消耗** | 11,800,000 + 2,400,000 − 1,120,000 − 220,000 = **12,860,000** |
| 兑付比例 | 0.01 元/分 |
| **期末积分负债** | 12,860,000 × 0.01 = **128,600.00 元** |

与总纲 §6.6 的数字完全一致。

### 4.8 表：`m19_stat_member`

#### 4.8.1 表说明

会员经营快照表是 P07 会员经营看板的数据源，粒度是 **月份 × 会员分层 × 生命周期阶段 × 科室**。

它承载总纲 §6.5 的复购率双口径分析，以及会员规模、活跃度指标。

#### 4.8.2 复购率双口径为什么必须同时存

总纲 §6.5 的实测数据：

| 口径 | 分母（消费人数） | 分子（复购人数） | 复购率 |
| --- | --- | --- | --- |
| `patient_id`（主） | 1,240 | 428 | 34.52% |
| `member_id`（辅） | 682 | 186 | 27.27% |

差 **7.24 个百分点**。

原因是办卡率只有约 55%（682 / 1,240）。如果只看会员口径，会漏掉 558 个没有办卡的回头客——这些人同样产生了复购，只是没有会员卡。

两个口径各有用途，不能只留一个：

- `patient_id` 口径回答"**有多少患者回来了**"，用于评估医疗服务的连续性，是主口径；
- `member_id` 口径回答"**会员运营做到了什么程度**"，用于评估会员体系效果，是辅口径。

如果只给 27.27%，会得出"复购率偏低、会员运营有很问题"的错误结论；如果只给 34.52%，又会忽略"有 45% 的回头客没被会员体系覆盖"这个更重要的运营机会。

所以两个都必须存、必须同时展示，并且展示时必须标注口径。

### 4.9 表：`m19_stat_export`

#### 4.9.1 表说明

### 4.10 表：`m19_stat_rebuild_log`

#### 4.10.1 表说明

重算任务日志表记录每一次"整期重算"的输入、输出与结果，是口径变更后新旧对比的证据链。

粒度是 **一次重算任务 × 一张目标表**。一次重算可能同时覆盖多张表（比如改了完成率口径，`m19_stat_daily` 和 `m19_stat_adherence` 都要重算），每张表各记一行。

#### 4.10.2 为什么重算日志必须单独建表

任务书设计要点 6 要求"口径变更后可整期重算并对比新旧结果"。要做到"对比"，必须能回答：

1. 上次算的是什么版本、什么时候算的？
2. 这次算的是哪个版本，覆盖了哪些期间？
3. 新旧差多少，差异主要来自哪里？

这些信息如果只写在应用日志里，查询困难且无法结构化对比。单独建表后，可以用一句 SQL 列出所有重算历史并找到"哪次重算造成了数字大幅变化"。

#### 4.10.4 `diff_summary` 的 JSONB 结构

```json
{
  "sample_metric": "FU_COMPLETION_RATE",
  "period": "2026-10",
  "dept_id": 12,
  "old_value": 0.800000,
  "new_value": 0.825000,
  "delta": 0.025000,
```

字段说明：

| 键 | 类型 | 说明 |
| --- | --- | --- |
| sample_metric | string | 变化最大的指标编码 |

| dept_id | int | 该指标所在的科室 |

#### 4.10.5 约束

| 约束名 | 类型 | 定义 | 防什么错误 |

| pk_m19_stat_rebuild_log | PRIMARY KEY | (id) | — |

### 6.1 初始化顺序

```text
1. 建表（依赖顺序：metric_def → daily → adherence → lost → care_convert
              → points → member → export → rebuild_log）
```

### 6.4 备份与恢复

| 对象 | 备份策略 | 恢复优先级 |
| --- | --- | --- |
| `m19_stat_metric_def` | 每日全量 + 变更审计 | **最高**：口径定义丢失会导致历史数据无法解释 |
| `m19_stat_rebuild_log` | 每日全量 | **高**：重算证据链，审计要求 |
| 其余统计快照表 | 随主库每日备份 | 低：可由源数据重算恢复 |
| `m19_stat_export` | 随主库每日备份 | 低：文件本身有有效期 |

**恢复原则**：统计快照表**不需要精细恢复**。任何一张快照表损坏，标准动作是"删掉重算"，而不是从备份恢复——因为重算出来的一定比备份新。只有 `metric_def` 和 `rebuild_log` 必须精确恢复，它们记录了"过去是怎么算的"，重算无法重建。

### 4.12 Pydantic Schema 定义

本节给出接口层的 Pydantic V2 Schema。分三类：行级读取模型、接口请求模型、接口响应模型。

```python
"""M19-08 随访与会员运营分析 —— Pydantic V2 Schema 定义。

约定：
- 比率字段可为 None，序列化为 null，前端展示为 —；
- 金额字段一律带 _snap 后缀，说明来自 M16 快照；
- 所有 Decimal 输出统一按 2 位（金额/积分）或 6 位（比率）量化后转字符串；
- 患者身份信息一律不出现在统计 Schema 中。
"""

from __future__ import annotations

from datetime import date, datetime
from decimal import Decimal
from typing import Any, Generic, TypeVar

from pydantic import BaseModel, ConfigDict, Field, field_validator

T = TypeVar("T")


class _Base(BaseModel):
    """统计模块 Schema 公共基类。"""

    model_config = ConfigDict(from_attributes=True, populate_by_name=True)


class PageMeta(_Base):
    """分页元信息，对应共享规范的分页结构。"""

    total: int = Field(default=0, ge=0, description="总条数")
    page: int = Field(default=1, ge=1, description="页码，从 1 开始")
    page_size: int = Field(default=20, ge=1, le=200, description="每页条数")
    pages: int = Field(default=0, ge=0, description="总页数")


class PageResult(_Base, Generic[T]):
    """分页结果容器。"""

    items: list[T] = Field(default_factory=list, description="当前页数据")
    total: int = Field(default=0, ge=0)
    page: int = Field(default=1, ge=1)
    page_size: int = Field(default=20, ge=1)
    pages: int = Field(default=0, ge=0)


class DashboardQuery(_Base):
    """P01 看板与 P04 完成率分析的统一查询参数。"""

    period_from: date = Field(description="起始日期")
    period_to: date = Field(description="结束日期")
    dept_ids: list[int] = Field(default_factory=list, description="科室ID列表，空表示全部")
    scenes: list[str] = Field(default_factory=list, description="随访场景筛选")
    calc_version: int | None = Field(default=None, ge=1, description="指定快照版本")

    @field_validator("period_to")
    @classmethod
    def _check_range(cls, v: date, info: Any) -> date:
        start = info.data.get("period_from")
        if start is not None and v < start:
            raise ValueError("period_to 不能早于 period_from")
        if start is not None and (v - start).days > 1826:
            raise ValueError("查询跨度不得超过 1826 天")
        return v
```

## 附录 B 常用运维 SQL

### B.1 巡检：默认分区是否有数据

```sql
SELECT COUNT(*) AS default_rows, MIN(stat_date) AS min_dt, MAX(stat_date) AS max_dt
FROM m19_stat_daily_default;
```

正常值应为 0。若大于 0，说明有超出建分区范围的日期数据，需补建分区。

### B.2 巡检：比率字段是否有分母为 0 却非 NULL 的脏数据

```sql
SELECT COUNT(*) AS bad_rows
FROM m19_stat_daily
WHERE (total_task_cnt = 0 AND completion_rate IS NOT NULL)
   OR (total_task_cnt = 0 AND on_time_completion_rate IS NOT NULL)
   OR (touched_patient_cnt = 0 AND revisit_rate IS NOT NULL);
```

正常情况下受 CHECK 约束保护，该查询应恒为 0。它的价值在于**发现约束被绕过**（例如某次 DDL 变更漏加了约束）。

### B.3 巡检：积分平衡等式

```sql
SELECT period, dept_id, begin_balance_points, issued_points, consumed_points,
       expired_points, adjusted_points, reversed_points, end_balance_points,
       (begin_balance_points + issued_points - consumed_points - expired_points
        + adjusted_points + reversed_points - end_balance_points) AS diff
FROM m19_stat_points
WHERE begin_balance_points + issued_points - consumed_points - expired_points
      + adjusted_points + reversed_points <> end_balance_points;
```

应恒为 0 行。若非 0，说明有数据被直接修改绕过了约束。

### B.4 巡检：悬空维度引用

M19 的统计快照按 `dept_id` 落库，科室停用/合并后历史快照里的 `dept_id` 会成为悬空引用。巡检分两步：先用 **M01-01 的科室主数据接口**取当前有效科室集合，再与本地快照比对。

```text
步骤 1（在线接口，非 SQL）：GET /internal/v1/mdm/depts/tree
    取回当前有效科室 → 得到有效 dept_id 集合 valid_ids
步骤 2（本地 SQL，只查 M19 自己的表）：
```

```sql
-- 用 :valid_ids 数组（步骤 1 的结果）作为白名单
SELECT d.dept_id, COUNT(*) AS cnt, MIN(d.stat_date) AS first_seen, MAX(d.stat_date) AS last_seen
  FROM m19_stat_daily d
 WHERE d.dept_id <> 0
   AND NOT (d.dept_id = ANY (:valid_ids))
 GROUP BY d.dept_id
 ORDER BY cnt DESC;
```

**为什么要分两步而不是一条 JOIN**：M01 没有对外提供可直接 JOIN 的科室维度视图（`m01_dept_snapshot_v` 之类的对象**在 M01 全目录不存在**，原稿此处写的表名是编造的，且编造了一个「由 M01 同步而来」的来源说明——这正是最危险的一种错误：一个不存在的对象被写成「已有的、不用管它」）。科室主数据的唯一权威入口是 M01-01 的 `GET /internal/v1/mdm/depts/tree`，M19 **不建科室主数据副本表也不建跨库视图**，因此只能在巡检作业里「先拉接口再比对」。

**为什么这个巡检可以每天跑、且不需要强一致**：科室合并/停用是低频事件（月度级），巡检的目的只是「发现悬空 ID 并提示运维确认是否需要重映射」，不是实时对账。允许 T+1 的滞后。

【V1.1 更正】原文这里是一条 `LEFT JOIN m01_dept_snapshot_v` 的单条 SQL，并附注「是运维侧维护的科室维度视图，由 M01 同步而来」。核对 M01 全目录：`m01_dept_snapshot_v` 零命中，也不存在任何「运维侧维护的科室维度视图」这一约定；M01 的 internal 契约里科室相关的只有 `GET /internal/v1/mdm/depts/tree`（以及 M22-04 首次定义的 `GET /internal/v1/mdm/depts/peer-groups`）。已改写为「接口取白名单 + 本地 SQL 比对」。

| biz_type | `m19_stat_export` | FOLLOWUP_DAILY / ADHERENCE / LOST / CARE_CONVERT / POINTS / MEMBER / MULTI_METRIC | 本子模块自定义 |
| trigger_type | `m19_stat_rebuild_log` | MANUAL / SCHEDULED / METRIC_CHANGE / DATA_FIX | 本子模块自定义 |

**为什么 `followup_method` 与 `channel` 是两套枚举**：前者描述"随访员用什么方式完成任务"（电话打过去、微信发过去、上门访视），后者描述"消息从哪条通道发出去"（短信网关、微信模板消息、站内信）。两者的补集并不相同：电话随访可以完成但不产生任何"渠道消息"，而一条生日关怀会走微信公众号渠道但不对应任何随访任务。

## 附录 F 术语表

| 术语 | 含义 | 易混淆点 |
| --- | --- | --- |
| 最终完成率 | 完成数（含逾期补做）/ 应完成数 | 与"按时完成率"分子不同，见 4.3.4 |
| 按时完成率 | 按期完成数（不含逾期补做）/ 应完成数 | 考核随访时效性，不考核覆盖率 |
| 依从性 | 患者在宽限期（默认 3 天）内完成随访的比例 | 与按时完成率数值可能相同，但依从性的主体是患者，按时完成率的主体是随访任务 |
| 失访 | 随访最终未能触达或患者拒绝（`exec_result` 为 FAILED/UNREACHABLE/REFUSED） | 与"逾期未做"不同，后者是随访员没做 |
| 失访序次 | 该患者第几次随访任务失访 | 1 表示首次随访就失联 |
| 逾期补做 | 计划日期之后、宽限期之外才完成 | 计入完成率，不计入按时完成率 |
| 宽限期 | 计划日期后允许完成仍算"按期"的天数 | 默认 3 天，可按场景配置 |
| 观察窗口 | 触达后追踪复诊/消费的天数 | 默认 14 天，决定月度数据可出数时间 |
| 小样本抑制 | 样本数小于阈值（默认 5）时不下钻展示 | 防止从极小样本反推个体 |
| 复购双口径 | `patient_id` 主口径与 `member_id` 辅口径 | 差 7.24 个百分点，见 4.8.2 |
| 积分负债 | 未消耗积分 × 兑付比例 | 业务口径数字，会计计提由 M17 负责 |
| 重算 | 口径变更后对历史期间重新计算 | 必须产生新 `calc_version`，不得覆盖旧版本 |
| 封账 | `is_final` 置 TRUE 后该期数据不再变动 | D+7 封账，重算需显式触发并留日志 |
