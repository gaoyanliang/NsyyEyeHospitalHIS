## 文档说明

### 本文档定位

本文档是 **M19-06 会员运营与消费分析**子模块的数据结构设计说明书，配套《M19_随访与会员管理_06_会员运营与消费分析_详细设计.md》使用。

本文档只描述**数据库物理结构**：表、字段、类型、约束、索引、分区、SQLAlchemy 2.0 模型与 Pydantic V2 Schema。复购率双口径的推导、生命周期与分群两个维度的判定阈值、流失风险的评分算例、RFM 分档与映射规则、消费事件缺失后的补数流程，见详细设计文档第 3 章、第 7 章与附录。

本子模块与模块内其他子模块有一个根本区别：**它几乎不产生业务数据，只产生分析快照**。M19 里真正产生原始业务数据的子模块是 M19-01（随访任务）、M19-04（积分与成长值）、M19-05（权益核销）、M19-07（营销活动与优惠券）。M19-06 做的是：把 M16 的消费事实、M03-03 的会员主档、M19-04/05/07 的营销事实，按日/按月压缩成可查、可比、可重算的快照。

因此本文档的设计重心不在「表怎么建」，而在三件事：

1. **口径怎么固定在物理层**——复购率两个口径如何在数据库层面禁止混算；
2. **快照怎么可重算**——口径变更后如何整期重算并保留新旧对比；
3. **缺失怎么看得见**——上游没给数时，表里如何留下痕迹，而不是静默填 0。

## 1. 概述

### 1.1 设计目标

本子模块的数据结构要同时满足四个互相拉扯的目标：

  | 目标 | 具体含义 | 对应的物理手段 |
  | --- | --- | --- |
  | 口径不可混算 | 复购率的 `patient_id` 口径与 `member_id` 口径各自独立成行，任何 SQL 都不可能把两者加在一起 | `identity_key_type` 进唯一键 |
  | 快照可重算 | 口径变更后可整期重算，新旧结果可对比，不覆盖历史 | `calc_version` + `calc_at` 进唯一键，旧版本行保留 |
  | 缺失可追溯 | 上游没给数时留下痕迹，而不是静默填 0 | `source_status` + `missing_sources` + 独立的同步日志表 |
  | 隐私不可逆 | 分析表里不出现可用于反查身份的字段 | 手机号只存掩码与哈希，姓名不落分析表 |

### 1.2 设计原则

**原则一：只存派生数据，不存原始事实。**

`m19_member_consume_snapshot` 存的是「某会员某天消费了几笔、多少钱、最后一次什么时候」，不是消费明细。消费明细的唯一真相在 M16（`m16_settlement` / `m16_optical_order`）。本子模块若建一张 `m19_member_consume_detail` 复制 M16 的结算行，会立刻出现两个真相：M16 退费后本表不动，会员消费额虚高。

唯一例外是 `m19_member_consume_detail_snap`，它是快照的**举证副本**，只在需要复算与对账时使用，且是只增不改的（退费以冲正行表达，不 UPDATE 原行）。这张表存在的原因见 4.3 节。

**原则二：口径字段必须是物理字段，不能是查询参数。**

复购率有两个口径。如果只建一个 `repurchase_rate` 字段，靠接口参数 `?identity=patient` 区分，那么下游任何一处忘传参数、传错默认值，都会静默拿到另一个口径的数字，而数据层面完全看不出异常。2026 年 10 月市场部月报引用「复购率 27.27%」而财务口径是「34.52%」，差的 7.24 个百分点会被追责成「数据不准」，但真正的原因是两处用了不同口径且无人可知。

因此 `identity_key_type` 是**表的物理字段并进唯一键**。两个口径各存一行，查询必须显式指定口径，`GROUP BY identity_key_type` 时两行自然分列，不存在混算的可能。

**原则三：分母为 0 时值是 NULL，不是 0。**

新会员只有 1 次消费，复购次数 0，复购率 0/1 = 0%。这个 0% 放进排行会把所有新会员排到末位，而事实上它们是「样本不足」，不是「表现差」。所以所有比率字段在分母为 0 时必须是 NULL，且这个约定由 CHECK 在数据库层面强制，不依赖应用层自觉。

**原则四：小样本必须抑制。**

聚合展示时，任一分组的样本数小于 5 时不展示明细数值，只标记「样本不足」。这条规则要落到数据层：`m19_member_segment_snapshot` 有 `is_suppressed` 字段，`m19_member_profile_tag` 干脆不存明细金额，只存分档。

### 1.3 与上游数据的关系

  | 上游 | 提供什么 | 本子模块如何用 | 本子模块不允许做什么 |
  | --- | --- | --- | --- |
  | M16 收费结算（`POST /internal/v1/billing/statistics`、事件 `m16.settlement.completed` / `m16.settlement.refunded`） | 会员消费流水：结算号、患者 ID、会员 ID、金额、时间、业务类型、交付状态、退费标志 | 聚合为日粒度消费快照 | 不复制 M16 结算表；不自行计算退费金额；不改 M16 金额 |
  | M03-03 会员主数据（`GET /internal/v1/member/by-patient/{patient_id}`、`GET /internal/v1/member/by-no/{member_no}`、`GET /internal/v1/member/{id}/benefits`） | 会员号、等级、入会日期、状态、手机号掩码 | 存为快照字段 `level_code_snap` / `join_date` | **不建** `mpi_member` / `mpi_member_tag` / `mpi_member_level` |
  | M03-03 会员等级回写（`POST /internal/v1/member/{id}/level-up`、`POST /internal/v1/member/{id}/level-down`、`POST /internal/v1/member/{id}/tags/sync`） | 本子模块可回写等级与标签 | 分析结论回写为会员标签 | 不直接改会员主档金额类字段 |
  | M03-03 会员状态与标签事件（`mpi.member.status_changed`、`mpi.member.tag_changed`、`mpi.member.level_changed`） | 会员停用/注销、标签变更、等级变更 | 触发本期重算与「已注销会员」标注 | 不自行变更会员状态 |
  | M03-02 患者合并（`mpi.member.merged`、`mpi.member.merge_conflict`） | A、B 两个 patient_id 合并为一个 | 标记受影响快照待重算，重定向 `identity_value` | 不自行合并患者；不 UPDATE 已冻结期 |
  | M19-04 积分与成长值（`m19_points_rule` 只读） | 积分规则倍率 | 分析积分发放的分布 | **不建** `m19_points_rule` |
  | M19-05 会员权益核销（`m19_benefit_instance` 只读） | 券使用事实 | 分析券对复购的拉动 | **不建** `m19_benefit_instance` |
  | M19-07 营销活动 | 活动参与事实 + 事件 `m19.activity.completed` | 分析活动后续消费 | 不建活动表 |
  | M22-05 视光经营分析 | `identity_key_type` 枚举与复购事实唯一键的**口径权威** | 逐字对齐枚举与唯一键结构 | 不另起一套口径；不发布与 M22 冲突的指标 |

**口径权威的一句话总结：** M22-05 定义「指标怎么算」，本子模块定义「按这个算法算出来的每个会员是什么状态」。前者回答「本月复购率多少」，后者回答「哪些会员复购了、哪些没复购、下一步该找谁」。

### 1.5 为什么是 10 张表

模块数据结构汇总 §6.1 第 4 批已为本子模块登记了 6 张表名：`m19_member_consume_snapshot`、`m19_member_repurchase_fact`、`m19_member_lifecycle`、`m19_member_segment_snapshot`、`m19_member_churn_risk`、`m19_member_profile_tag`。本文档在此基础上增加 4 张：`m19_member_consume_detail_snap`、`m19_member_sync_log`、`m19_member_export_task`、`m19_member_oper_log`，合计 10 张。逐条说明增加与不增加的理由：

  | 候选 | 结论 | 理由 |
  | --- | --- | --- |
  | `m19_member_consume_detail_snap` | **增加** | 消费快照是聚合结果，出问题时无法自证。M22-05 已要求「报表数字必须可追溯到原始单据号」，聚合表答不了「这 3 笔是哪 3 笔」。这张表只增不改，退费写冲正行 |
  | `m19_member_sync_log` | **增加** | 事件丢失是本子模块最大的风险（`m16.settlement.completed` 丢一条，会员消费额永久缺一条记录）。没有同步日志，就无法回答「昨天到底同步了多少条、补了几次、还有没有漏」 |
  | `m19_member_export_task` | **增加** | 导出是唯一把会员数据带出系统的动作，必须留痕：谁导的、导了多少、脱敏没有、有没有触发小样本抑制。M19 模块没有公共导出骨架表（不同于 M22），只能自建 |
  | `m19_member_oper_log` | **增加** | 口径变更、手工改分群、重算这些都是高影响动作，必须留痕。归入「增加」 |
  | `m19_member_rfm_score` | **不增加** | RFM 打分与分群是同一时刻的同一份计算结果，拆两张表会出现「分数是新的、分群是旧的」的不一致。合并进 `m19_member_segment_snapshot` |
  | `m19_member_stat_daily` | **不增加** | 看板需要的是「今日/本月汇总」，可以直接对 `m19_member_consume_snapshot` 聚合，日粒度表已经是按日分行的，再加一层日汇总表是纯冗余 |
  | `m19_member_metric_def` | **不增加** | 指标定义归 M22-01（`m22_metric_def`）。本子模块只用 M22 已发布的指标编码，不另建一套指标字典 |
  | `m19_member_followup_link` | **不增加** | 召回动作由 M19-03 执行，本子模块只通过事件 `m19.member.risk_lost` 把名单推过去，不保存召回执行结果 |

回答「为什么是 10 张而不是 6 张」：若砍掉 `m19_member_consume_detail_snap` 与 `m19_member_sync_log`，系统仍能出报表，但**出不了问题查不出原因**——报表数字对不对、昨天同步漏没漏、这 3 笔是哪 3 笔，三个问题全部无解。可运维性不是可以省略的选项。

回答「为什么是 9 张而不是 12 张」：再加 `rfm_score`、`stat_daily`、`metric_def` 三张，会带来两处数据不一致风险（分数与分群不同步、两套指标定义打架）与一处纯粹的冗余。少建三张，多三道约束。

### 1.6 建表顺序

  | 批次 | 表 | 依赖 |
  | --- | --- | --- |
  | 第 1 批 | `m19_member_sync_log` | 无。它记录的是同步动作本身，不依赖任何业务表 |
  | 第 1 批 | `m19_member_consume_detail_snap` | 无。明细快照先落，聚合快照后算 |
  | 第 2 批 | `m19_member_consume_snapshot` | 逻辑依赖 `m19_member_consume_detail_snap`（聚合来源） |
  | 第 3 批 | `m19_member_repurchase_fact` | 逻辑依赖 `m19_member_consume_detail_snap`（复购判定来源） |
  | 第 3 批 | `m19_member_lifecycle` | 逻辑依赖 `m19_member_consume_snapshot` |
  | 第 3 批 | `m19_member_segment_snapshot` | 逻辑依赖 `m19_member_consume_snapshot` |
  | 第 4 批 | `m19_member_churn_risk` | 逻辑依赖 `m19_member_lifecycle` + `m19_member_segment_snapshot` + `m19_member_repurchase_fact`（平均复购周期） |
  | 第 4 批 | `m19_member_profile_tag` | 逻辑依赖 `m19_member_lifecycle` + `m19_member_segment_snapshot` |
  | 第 5 批 | `m19_member_export_task` | 逻辑依赖以上全部（导出对象是它们的结果） |
  | 第 5 批 | `m19_member_oper_log` | 无。与业务表平级，记录对业务表的操作 |

第 4 批的 `m19_member_churn_risk` 依赖链条最长：流失风险要用「平均复购周期」，而平均复购周期来自复购事实；要用「历史价值」，而历史价值来自分群快照。因此日终任务必须按这个顺序串行，不能并行。

### 2.2 类型选型规则

  | 数据类型 | 选型 | 理由 |
  | --- | --- | --- |
  | 金额 | `NUMERIC(14,2)` | 与共享规范 §2.4 一致。为什么不是 `NUMERIC(12,2)`：单会员单次消费理论上不会超过 1 亿元，但聚合行的 `total_amount` 可能到千万级，14 位整数部分留足余量 |
  | 比率 | `NUMERIC(10,6)` | 与共享规范 §2.4 一致。为什么是 6 位小数：复购率 34.52% 存成 0.345161，若只留 4 位会变成 0.3452，两个口径的差额 7.24 个百分点在拆分到科室后会失真。6 位小数在做「相差几个百分点」的比较时误差 < 0.0001 |
  | 中间计算值 | 代码层用 `Decimal`，落库前 `quantize(Decimal("0.000001"), ROUND_HALF_UP)` | 不允许在落库时让数据库做隐式舍入，舍入规则必须显式 |
  | 计数 | `INTEGER` | 会员数、笔数、分钟数远小于 21 亿。为什么不用 `BIGINT`：整表 420 万行时，`INTEGER` 比 `BIGINT` 每行省 4 字节，索引也小，实际查询更快 |
  | 天数/月数 | `SMALLINT` | 窗口天数、沉默天数最大 3650，`SMALLINT` 上限 32767 足够 |
  | 时间戳 | `TIMESTAMP`（无时区，Asia/Shanghai） | 与汇总文件 §2.3 一致。为什么不用带时区：全院单时区运营，带时区会让「同一时刻不同写法」在比对时出错 |
  | 布尔 | `BOOLEAN` | 不用 `CHAR(1)`，不用 0/1 整数 |
  | 大结构 | `JSONB` | RFM 分项、命中规则列表、抑制原因等结构会演进，用 JSONB 避免频繁加列 |
  | 绝对禁止 | `FLOAT` / `DOUBLE PRECISION` / `REAL` | 二进制浮点无法精确表示 0.1，金额累加会产生 0.01 级误差；比率比较会出现 0.345161 != 0.345161 的诡异结果 |

**为什么比率不存百分比整数（如存 3452 表示 34.52%）：** 百分比的精度需求是可变的。复购率需要 2 位小数（34.52%），渠道差异需要 4 位小数（0.0041 个百分点），积分发放率需要 6 位小数。存整数要么精度不够要么留冗余，且每种指标的缩放系数不同，下游一定会有人忘记除。存 `NUMERIC(10,6)` 的原始比值，展示层再乘 100，是唯一不需要各接口各自约定的做法。

### 2.3 维度字段空值规则

维度字段（用于 `GROUP BY` 与唯一键的字段）**必须 `NOT NULL DEFAULT ''`（字符串）或 `DEFAULT 0`（数值），不能允许 NULL。**

原因是 PostgreSQL 的 UNIQUE 约束认为 NULL 互不相等。若 `dimension_value` 允许 NULL，那么同一个窗口、同一口径、同一维度类型的两行「全院」聚合行（两条的 `dimension_value` 都是 NULL）在唯一索引看来是两个不同的值，可以重复插入。重算任务跑两次，看板数字翻倍。

这条规则在 M19-08 的 `### 2.4 维度字段空值规则` 已经列为硬性要求，本子模块沿用：

  | 维度字段 | 无值时的表示 | 不能用什么 | 后果 |
  | --- | --- | --- | --- |
  | `dimension_type` | 必有值（`HOSPITAL`） | 空串表示「全院」 | `HOSPITAL` 是一个明确的分组，不是「没分组」 |
  | `dimension_value` | `''` | NULL | NULL 让唯一约束失效，重算产生重复行 |
  | `dept_id` | `0` | NULL | 0 = 全院或未分配科室，是一个真实取值 |
  | `dept_name_snap` | `''` | NULL | 快照字段，科室改名后必须还能显示原名称 |
  | `level_code_snap` | `''` | NULL | 会员当时可能未分级，空串表示「无等级」 |
  | `channel` / `biz_type` | `''` | NULL | 同上 |

### 2.4 口径字段空值规则

本子模块有两类字段与「口径」有关，它们的空值规则与维度字段相反：

  | 字段 | 何时为 NULL | 为什么允许 NULL |
  | --- | --- | --- |
  | 比率字段（`*_rate`） | 分母为 0 时 | NULL 表达「样本不足，无法计算」，0 表达「算出来是 0」。两者语义完全不同 |
  | `prev_period_rate`（环比基期值） | 基期不存在或基期值本身为 NULL | 若基期为 0 而强行算环比，会得到无穷大或 100% 的假象 |
  | `avg_repurchase_days` | 窗口内没有任何会员达到 2 次消费 | 没有复购就没有间隔，分母为 0 |
  | `silent_days` | 会员从未消费过 | 从未消费的会员不进入流失预警（它属于「未激活」而不是「流失」） |

这个约定必须**由 CHECK 强制**，不能靠应用层。校验器的核心规则是：只要表里存在 `*_rate` 字段与对应的分母字段，就必须有 `CHECK (denominator > 0 OR ratio IS NULL)`。本文档每张含比率的表都写了这条约束，并在约束注释里写明它防的具体错误。

#### 4.2.1 为什么 `identity_key_type` 要进这张表的唯一键

这张表的自然粒度是「日期 × 会员」，看上去一个会员一天只需要一行。但复购率的两个口径需要的数据不同：

- `PATIENT_ID` 口径下，一个患者一天一行，无论他有没有会员卡、有几张卡；
- `MEMBER_ID` 口径下，一个会员一天一行，未办卡的散客根本不存在。

如果本表只按 `(stat_date, member_id)` 建唯一键，那么复购计算必须去明细快照里重新按 `patient_id` 分组，等于每天把所有明细重算一遍，且两个口径的聚合结果没有留痕，事后无法复核「34.52% 是怎么算出来的」。

因此本表的唯一键是 **`(stat_date, member_id, biz_type, identity_key_type)`**。同一会员同一天同业务类型，在 `PATIENT_ID` 口径与 `MEMBER_ID` 口径下各有一行；当会员恰好绑定了一个患者（M03-03 保证一患者一会员）时，两行的 `consume_cnt`、`net_amount` 完全相同，`identity_value` 也相同；当存在「患者未办卡」或「同手机号多卡未绑定」时，两行会有差别，**这个差别正是 7.24 个百分点的来源，必须看得见**。

**这不是冗余存储，是把「同一个事实的两种归属」显式化。** 代价是行数翻倍（约 420 万行长到 420 万行，因为大多数会员活跃天数有限，实际增量约 1.4 倍），换来的是任何一条复购数字都能直接 SQL 复现。

#### 4.2.2 为什么不在本表存 `avg_ticket`

客单价 = `net_amount ÷ consume_cnt`。本表两个字段都有，展示层一除即可。若存 `avg_ticket` 快照，会出现三个问题：

1. 后续若 `consume_cnt` 被修正（例如漏同步的一笔被补上），`avg_ticket` 会与实际不符，需要额外维护同步逻辑；
2. 聚合到月/季时，正确的算法是 `SUM(net_amount) ÷ SUM(consume_cnt)`，而不是 `AVG(avg_ticket)`。后者的加权错误在会员笔数差异大时非常明显：A 会员 1 笔 5,000 元（客单 5,000），B 会员 9 笔 900 元（客单 100），简单平均得 2,550，真实值是 590；
3. 分母为 0 的 NULL 约定要在每一层重复实现。

同样的道理，本表不存复购率、不存流失概率，所有比率都在各自的汇总表里算。

**组合语义约束（最容易漏的一类）**

```sql
-- 组合约束 1：净额必须等于实收减退费
--   防的错误：M16 退费事件到达后只更新了 refund_amount，忘了更新 net_amount，
--   于是 P01 看板的「本月净消费额」把已退的 3,200.00 元仍算在内。
ALTER TABLE m19_member_consume_snapshot
    ADD CONSTRAINT ck_m19_member_consume_snap_net
    CHECK (net_amount = total_amount - refund_amount);

-- 组合约束 2：优惠不能超过原价
--   防的错误：活动折扣与会员折扣叠加计算错误，优惠额算成 5,200.00 元，
--   而原价只有 5,000.00 元，净额变成负数，所有占比分析失效。
ALTER TABLE m19_member_consume_snapshot
    ADD CONSTRAINT ck_m19_member_consume_snap_discount
    CHECK (discount_amount <= original_amount);

-- 组合约束 3：无消费时不能有消费时间
--   防的错误：占位行为（0 笔消费但有 first_consume_at），
--   导致「首笔消费时间」统计把从未消费的会员也算成已消费。
ALTER TABLE m19_member_consume_snapshot
    ADD CONSTRAINT ck_m19_member_consume_snap_time
    CHECK ((consume_cnt = 0 AND first_consume_at IS NULL AND last_consume_at IS NULL)
        OR (consume_cnt > 0 AND first_consume_at IS NOT NULL AND last_consume_at IS NOT NULL));

-- 组合约束 4：末笔不早于首笔
--   防的错误：补数任务把昨日的 last_consume_at 写进了今日行，
--   产生 last_consume_at < first_consume_at 的畸形行。
ALTER TABLE m19_member_consume_snapshot
    ADD CONSTRAINT ck_m19_member_consume_snap_time_order
    CHECK (last_consume_at IS NULL OR first_consume_at IS NULL
        OR last_consume_at >= first_consume_at);

-- 组合约束 5：累计值不能小于当日值
--   防的错误：重算任务只重算了当日行，没有重算累计列，
--   出现 cum_consume_cnt < consume_cnt 的不可能状态。
ALTER TABLE m19_member_consume_snapshot
    ADD CONSTRAINT ck_m19_member_consume_snap_cum
    CHECK (cum_consume_cnt >= consume_cnt AND cum_net_amount >= net_amount);

-- 组合约束 6：PARTIAL / MISSING 必须写明缺失来源
--   防的错误：上游超时返回空数组，同步任务当成「当日无消费」写入一行，
--   结果会员消费额永久缺失 128 笔。写入时必须留下 missing_sources。
ALTER TABLE m19_member_consume_snapshot
    ADD CONSTRAINT ck_m19_member_consume_snap_missing
    CHECK (source_status = 'COMPLETE' OR missing_sources <> '');

-- 组合约束 7：未交付的消费必须在完整性为 COMPLETE 时才可信
--   防的错误：M16 当日结算未全部交付，本行 is_delivered 却写成 TRUE，
--   把这批尚未交付的消费计入复购分母，复购率虚高。
ALTER TABLE m19_member_consume_snapshot
    ADD CONSTRAINT ck_m19_member_consume_snap_delivered
    CHECK (is_delivered = FALSE OR source_status = 'COMPLETE');

-- 组合约束 8：身份口值与值的形态必须一致
--   防的错误：identity_key_type 写 MEMBER_ID 但 identity_value 存了 patient_id，
--   两口径的数字对不上却看不出哪一行是错的。
ALTER TABLE m19_member_consume_snapshot
    ADD CONSTRAINT ck_m19_member_consume_snap_identity_value
    CHECK ((identity_key_type = 'MEMBER_ID'
            AND identity_value = member_id::text)
        OR (identity_key_type = 'PATIENT_ID'
            AND identity_value = patient_id::text));
```

**设计说明**

- `member_id = 0` 表示未办卡散客：这类消费者在 `PATIENT_ID` 口径下计入复购分母（他们有 patient_id），在 `MEMBER_ID` 口径下完全不可见。这正是两个口径产生差异的第一类原因。
- `order_cnt` 与 `consume_cnt` 分开：一次就诊可能开 2 张单（验光单 + 配镜单），结算 2 次，但属于 1 次就诊。复购分析用的是「消费次数」而非「就诊次数」，两者都在表里，按需取用。
- `last_consume_date` 是冗余字段（可从前一行数据推出），但它是流失预警每日全表扫描的关键：`WHERE last_consume_date < CURRENT_DATE - 90` 比窗口函数自连接快两个数量级。冗余 8 字节换一次全表顺序扫描，值得。
- `is_final` 与 `calc_version` 并存不是重复：`calc_version` 表达「用第几版口径算的」，`is_final` 表达「这期还能不能改」。已封账的期可以因为口径升级而重算，重算后的行 `calc_version` 递增但 `is_final` 仍为 TRUE——口径版本与封账状态是两个正交维度。

#### 4.4.1 补数窗口为什么是「T+1 到 T+7」而不是无限追溯

消费事件 `m16.settlement.completed` 丢失的概率在正常工作时段接近 0，但在 M16 发布停机、网络分区、消费者进程 OOM 时会成片丢失。补数扫描必须回答两个问题：**扫多久以前的**、**什么时候停止**。

设计是：

  | 阶段 | 触发时刻 | 扫描窗口 | 目的 |
  |---|---|---|---|
  | 日终对账 | 每日 02:30 | 昨日（T-1） | 事件推送的主要兜底路径，正常情况覆盖全部日间事件 |
  | 短期补数 | 每日 03:00 | T-2 至 T-7 中 `is_final_pass = FALSE` 的日期 | 捕捉跨零点提交、夜间批处理、延迟入账 |
  | 封账前终检 | 次月第 3 个工作日 | 上月整月 | 封账前最后一次机会，同时触发 `is_final = TRUE` |
  | 手工回填 | 人工触发 | 任意，需审批 | 处理历史事故（如 M16 停机 2 天） |

窗口上限 7 天的理由：`POST /internal/v1/billing/statistics` 按日期区间查询，接口本身支持任意回溯，但**回溯越久，与 M16 当前数据的一致性越差**。M16 的结算在 7 天内可能经历退费与冲正，7 天后基本稳定。若无限期扫描，每次都会拉回已经被退费冲掉的原始结算，需要额外的判断逻辑去重，收益为零而风险为正。

```sql
-- 【组合约束 1】非 COMPLETE 批次必须列出缺失来源
ALTER TABLE m19_member_sync_log
    ADD CONSTRAINT ck_m19_member_sync_missing_src
    CHECK (source_status = 'COMPLETE' OR missing_sources <> '');
--   防的错误：批次标记为 PARTIAL 却把 missing_sources 留空，
--   运维打开排障页看到「部分失败」但不知道是哪个接口失败，
--   只能翻日志逐个猜。

-- 【组合约束 2】有失败条数时状态不能是 COMPLETE
ALTER TABLE m19_member_sync_log
    ADD CONSTRAINT ck_m19_member_sync_failed_not_complete
    CHECK (failed_cnt = 0 OR source_status <> 'COMPLETE');
--   防的错误：写入 20 条失败 3 条，却把批次标成 COMPLETE，
--   于是补数扫描认为该日已完整，3 笔消费永久缺失，
--   且看板上 source_status 显示「完整」，运营完全看不到问题。

-- 【组合约束 3】补数类批次必须声明窗口且有原因
ALTER TABLE m19_member_sync_log
    ADD CONSTRAINT ck_m19_member_sync_gap_reason
    CHECK (gap_fill_cnt = 0 OR sync_type = ANY (ARRAY['REPAIR', 'BACKFILL', 'MANUAL']));
--   防的错误：EVENT 类型批次却带着补数条数——
--   事件消费者不可能「补数」，出现这种组合说明调用方传错了 sync_type，
--   后续按类型统计补数率时会被算进「实时同步」分子，掩盖事件丢失的严重程度。

-- 【组合约束 4】is_final_pass 只能由终检批次设置
ALTER TABLE m19_member_sync_log
    ADD CONSTRAINT ck_m19_member_sync_final_pass
    CHECK (is_final_pass = FALSE OR sync_type = ANY (ARRAY['REPAIR', 'MANUAL']));
--   防的错误：日终批次顺手把 is_final_pass 置 TRUE，
--   于是次日 03:00 的短期补数直接跳过该日，
--   夜里延迟入账的 12 笔结算再也没有机会被补回来。
```

#### 4.5.1 为什么 `identity_key_type` 必须进唯一键

这是本子模块最关键的一条设计。先看把口径做成查询参数会怎样。

**错误做法：** 表唯一键设成 `(period, window_type, dept_id)`，在接口上加一个 `identity_key_type` 查询参数，计算时按参数切口径。

**会出什么事：**

2026 年 10 月，市场部从 P03 页面查复购率，页面默认参数 `identity_key_type = MEMBER_ID`，看到 **27.27%**。同月院办在运营会上从 M22 报表查同一指标，M22 默认 `PATIENT_ID`，看到 **34.52%**。两人拿着相差 **7.24 个百分点**的数字开会，讨论了两小时才发现在说不同的东西。

更严重的是：这个错误**在数据层完全看不出来**——表里只有一行、只有一个数，谁也没法从数据判断「这行到底按什么口径算的」。参数在 HTTP 请求里，请求过后就没了。

**正确做法：口径进唯一键，一个窗口两个口径各存一行。**

这样做的三个效果：

1. **物理上无法混算**：`PATIENT_ID` 行与 `MEMBER_ID` 行的 `repurchase_rate` 是两行独立数据，任何一条 SQL 都能 `WHERE identity_key_type = 'PATIENT_ID'` 精确取到，不存在「忘了传参数」这种失败模式。
2. **差异可量化**：两行并排一减，差异就是 7.24 个百分点，页面可以直接展示「本窗口两口径相差 X 个百分点，主要因办卡率 40%」。
3. **可审计**：`merged_card_cnt` / `phone_matched_cnt` / `conflict_cnt` 三个归并计数记录在每行上，能回答「这 7.24 个百分点里有多少是多卡归并带来的」。

**算例（与总纲 §6.5 完全一致）：**

  | 项 | `PATIENT_ID` 口径 | `MEMBER_ID` 口径 |
  |---|---|---|
  | 有效顾客数 | 1,240 | 682 |
  | 复购顾客数 | 428 | 186 |
  | 单次消费顾客数 | 812 | 496 |
  | 有效消费笔数 | 2,180 | 1,058 |
  | 复购消费笔数 | 940 | 372 |
  | 复购率 | 428 ÷ 1,240 = 0.345161 → **34.52%** | 186 ÷ 682 = 0.272727 → **27.27%** |
  | 差异 | 34.52% − 27.27% = **7.24 个百分点** | — |

校验：`812 + 428 = 1,240` ✓；`496 + 186 = 682` ✓；`1,240 + 940 = 2,180` ✓；`682 + 372 = 1,054`，与 1,058 差 4——这 4 笔属于 `member_id` 相同但 `patient_id` 不同的冲突行，已按 M22-05 规则排除（`identity_merge_rule = 'CONFLICT'`），在 `conflict_cnt` 中单独留痕。

#### 4.5.2 为什么 `repurchase_consume_cnt` 是一个独立字段而不是算出来的

看起来它是冗余的：`repurchase_consume_cnt = valid_consume_cnt − repurchase_customer_cnt`。但它必须物理存储，理由有三：

1. **减法的可读性**：运营看到「有效消费 2,180 笔、复购 940 笔」能直接理解，「2,180 减 1,240 等于 940」需要停下来算。指标表的存在意义就是让下游不用算。
2. **减法在同构口径下会出错**：冲正行的存在让 `valid_consume_cnt` 可能小于 `repurchase_customer_cnt`（某顾客 2 笔消费，其中 1 笔在窗口结束后被冲正，该顾客仍是「复购顾客」，但有效笔数只有 1）。此时减法得出 −1，而实际规则是「有效笔数减到 1 就不再算复购顾客」。存字段可以让规则体现在写入值上，而不是让读者自己推。
3. **CHECK 能兜底**：`repurchase_consume_cnt >= 0` 与 `repurchase_customer_cnt <= valid_consume_cnt` 两条 CHECK 只要存了字段就成立，靠减法的话这两条约束没法表达。

#### 4.5.3 会员注销与患者合并的口径处理

M03-03 会发出 `mpi.member.status_changed`（会员停用/注销）与 `mpi.member.merged`（患者合并）。这两个事件都会改变「谁是同一个顾客」的问题，必须给出**明确口径**，否则同一份月度报表每跑一次数都不一样。

**口径一：会员注销后，历史消费照算。**

理由：复购率的定义是「顾客在窗口内的消费行为」，不是「顾客当前是否仍是会员」。若注销就从分母里扣掉，会出现一个荒谬的结果——某会员 3 月在窗口内消费了 3 次（是复购顾客），6 月注销，8 月重跑 3 月的报表时，分子分母同时减 1，复购率从 34.52% 变成 34.41%。**月度报表无法复现，审计无法举证。**

因此主口径 `repurchase_rate` **包含已注销会员**，同时用 `cancelled_customer_cnt` / `cancelled_repurchase_cnt` 单独记录其中有多少是已注销的，并给出剔除后的 `rate_excl_cancelled`。页面并排展示两个数。

**算例（2026-10，`PATIENT_ID` 口径）：**

  | 项 | 含已注销（主口径） | 剔除已注销 |
  |---|---|---|
  | 有效顾客数 | 1,240 | 1,240 − 96 = 1,144 |
  | 复购顾客数 | 428 | 428 − 18 = 410 |
  | 复购率 | 428 ÷ 1,240 = 0.345161 → **34.52%** | 410 ÷ 1,144 = 0.358392 → **35.84%** |
  | 差异 | — | **+1.32 个百分点** |

差异方向是**剔除后更高**，这符合直觉：已注销会员里「消费过但只买一次就走」的比例明显偏高（96 人中只有 18 人复购，复购率 18.75%，远低于整体的 34.52%）。页面提示语：「本窗口有 96 名已注销会员计入分母，剔除后复购率为 35.84%，比主口径高 1.32 个百分点。」

**为什么主口径选「含已注销」而不是「剔除」：** M22-05 已定「复购率 = ≥2 次有效消费顾客数 ÷ ≥1 次有效消费顾客数」，两个集合都由**窗口内实际发生消费的人**构成，会员状态不是筛选条件。改主口径会造成与 M22 指标对不上——而任务要求 M19 出分析结论、M22 出统一口径指标，一旦主口径分叉，两张报表永远差 1.32 个百分点。

**口径二：患者合并后，合并前的消费**不重算到主会员名下，而是**按现有 patient_id 归属保留，下一期重算时自然归并**。

若采用「合并后立即把 B 的历史消费全部 `UPDATE` 到 A」的做法，会破坏已封账期间的可复现性：3 月的报表封账时 A 有 5 次消费、B 有 3 次，8 月合并后重跑 3 月报表变成 A 有 8 次，两个月的报表对不上，且 `is_final = TRUE` 的行被改写等于篡改审计证据。

落地方式是：

  | 时点 | 动作 |
  |---|---|
  | 收到 `mpi.member.merged` | 只做标记：写 `m19_member_oper_log`（`oper_type = 'CALC_RERUN'`，`target_id` = 主 patient_id），不动任何历史行 |
  | 下一期重算 | 明细快照的 `patient_id` 已由 M03-02 重定向，新一期自然按主 patient_id 归并 |
  | 已封账期（`is_final = TRUE`） | **不重算**，也不提供「强制重算」入口 |

**算例：** 患者 A（patient_id = 10086）窗口内消费 1 次，患者 B（patient_id = 20001）窗口内消费 2 次，两人实为同一人，8 月合并。合并当期的复购事实写 2 行（A 一行分母 1、B 一行分母 1），下一期重算后只写 1 行（分母 1、复购判定按 3 次消费），期间历史不变。

**若不这样处理会怎样：** 假设窗口内复购率按未合并口径是 34.52%，把 B 的 2 次消费加到 A 名下后，分子（复购人数）不变而分母（会员数）减少 1，复购率会虚高。以 1,240 人、428 人复购为例，合并 40 对之后分母变成 1,200，复购率变成 428 ÷ 1,200 = 35.67%，**凭空多出 1.15 个百分点**，而且这个偏差会随合并次数累积、无法追溯。

**合并冲突（`mpi.member.merge_conflict`）：** 两卡分属不同 patient_id 但手机号相同，M03-02 不自动合并并发出冲突事件。本子模块的处理与 M22-05 一致——**不自动归并**，明细快照标 `identity_merge_rule = 'CONFLICT'` 且 `is_valid_consume = FALSE`，计入 `conflict_cnt`，等 M03 人工合并后下一期重算。

**组合语义约束（最容易漏的一类）**

```sql
-- 【组合约束 1】三类顾客数必须加得回有效顾客数
ALTER TABLE m19_member_repurchase_fact
    ADD CONSTRAINT ck_m19_member_repurchase_cust_sum
    CHECK (single_buy_customer_cnt + repurchase_customer_cnt = valid_customer_cnt);
--   防的错误：改了复购顾客数却忘了同步单次顾客数，
--   于是「复购 428 人 + 单次 900 人 = 1,328 人」但有效顾客写 1,240 人，
--   两个派生比率（复购率、单次占比）加起来不等于 100%，页面直接自相矛盾。

-- 【组合约束 2】复购顾客数不能超过有效顾客数
ALTER TABLE m19_member_repurchase_fact
    ADD CONSTRAINT ck_m19_member_repurchase_cust_le
    CHECK (repurchase_customer_cnt <= valid_customer_cnt);
--   防的错误：把「复购笔数」错填进「复购顾客数」，
--   得出 940 > 1,240 之外的情况（如 1,500 人复购、1,240 人有效），
--   复购率算出 120.97%，页面显示超过 100% 的红线告警。

-- 【组合约束 3】复购消费笔数不能超过有效消费笔数
ALTER TABLE m19_member_repurchase_fact
    ADD CONSTRAINT ck_m19_member_repurchase_cnt_le
    CHECK (repurchase_consume_cnt <= valid_consume_cnt);
--   防的错误：把某窗口的总消费笔数（含无效行）填进 valid_consume_cnt，
--   而 repurchase_consume_cnt 用的是有效口径，两者口径不同步。

-- 【组合约束 4】interval 采样人数必须等于复购顾客数
ALTER TABLE m19_member_repurchase_fact
    ADD CONSTRAINT ck_m19_member_repurchase_days_sample
    CHECK (repurchase_days_sample_cnt = repurchase_customer_cnt);
--   防的错误：只对「复购 2 次以上且有间隔数据」的顾客算间隔，
--   于是采样人数 402、复购顾客 428，页面显示「428 人复购，
--   平均间隔基于 402 人」——运营会问剩下 26 人去哪了。
--   实际这 26 人是两天内连续消费（间隔 0 天），也应计入。

-- 【组合约束 5】PARTIAL 必须列出缺失来源
ALTER TABLE m19_member_repurchase_fact
    ADD CONSTRAINT ck_m19_member_repurchase_missing
    CHECK (source_status = 'COMPLETE' OR missing_sources <> '');
--   防的错误：M16 接口超时导致只拉到一半数据，
--   复购率照算但来源标 PARTIAL 而 missing_sources 为空，
--   页面无法告诉运营「这个数缺了哪些来源」，运营把它当准数用。

-- 【组合约束 6】三类归并计数之和不能超过有效顾客数
ALTER TABLE m19_member_repurchase_fact
    ADD CONSTRAINT ck_m19_member_repurchase_merge_sum
    CHECK (merged_card_cnt + phone_matched_cnt + conflict_cnt <= valid_customer_cnt);
--   防的错误：`MEMBER_ID` 口径下不该有任何归并（一张卡就是一个会员），
--   若出现归并计数说明写数逻辑串到了 `PATIENT_ID` 分支，
--   两个口径的数据被污染。这一条能兜住最严重的一类静默错误。
```

```sql
COMMENT ON COLUMN m19_member_repurchase_fact.repurchase_consume_cnt IS '复购消费笔数=valid_consume_cnt−repurchase_customer_cnt，物理存储便于下游直读与 CHECK 兜底';
```

**设计说明**

- **为什么 `dept_id = 0` 表示全院而不是 NULL**：PostgreSQL 的 UNIQUE 认为两个 NULL 互不相等。若用 NULL 表示全院，同一期间会插入任意多行「全院」记录而不触发唯一约束冲突。用 `0` 这个哨兵值，唯一键才真正起作用（模块数据结构汇总 §2.4 同规则）。
- **为什么 `avg_amount_per_customer` 允许 NULL**：新开科室、新开渠道的当期可能一个有效顾客都没有。此时人均消费是「无意义」而不是「0 元」——填 0 会让排序把它排到最后，看起来像「消费最低」，实际是「没有顾客」。
- **为什么 `calc_version` 也进唯一键**：口径变更要能新旧对比。V1 的 34.52% 与 V2 的 34.10% 是两条独立记录，页面可以并排展示「口径调整后复购率变化 −0.42 个百分点」，而不是把历史数字原地改掉导致趋势图断裂。

#### 4.6.1 生命周期与价值分群为什么必须是两个字段

这是任务书第 4 条要求。两者都用「会员」做主语，都描述会员状态，很容易被合并成一个 `member_status` 字段，但它们是**两个正交维度**：

  | 维度 | 生命周期 `stage` | 价值分群 `member_segment` |
  |---|---|---|
  | 回答什么问题 | 这个人在时间上走到哪一步了 | 这个人对我们值多少钱 |
  | 数据来源 | 最近消费距今天数、期比期消费次数趋势、会员年龄 | R 近期性、F 频次、M 金额三档打分 |
  | 变化规律 | **单向推进**，一般不回退 | **可双向跳动**，随消费变化 |
  | 与钱的关系 | 无关。刚办卡 90 天内的高消费客户是 `NEW` | 直接相关。同样是 `NEW`，可能是 `VIP` 也可能是 `ORDINARY` |
  | 谁在用 | 运营（决定什么时候该联系） | 市场部（决定给谁花钱） |

**反例说明为什么不能合并：** 若只存一个 `member_status`，取值会变成 `VIP` / `NEW` / `SILENT` 混在一起的大杂烩。此时：
- 运营要查「所有快流失的人」，得写 `WHERE member_status IN ('SILENT','LOST', ...)`，但 `VIP` 里也有快流失的（某高净值客户 200 天没来），漏掉了；
- 市场部要查「该重点维护的高价值客户」，得写 `WHERE member_status IN ('VIP','CORE')`，但 `SILENT` 里也有高价值客户，也漏掉了。

两个维度交叉出来的 6 × 6 = 36 种组合里，真正有运营意义的大约有 12 种，全部需要按维度分别筛选才能表达。所以必须拆成两列。

**典型组合举例（来自 2026 年 10 月真实分布）：**

  | 组合 | 人数 | 含义 | 运营动作 |
  |---|---|---|---|
  | `MATURE` + `VIP` | 186 | 稳定高价值，每月都来 | 维护，别打扰 |
  | `DECLINING` + `VIP` | 41 | 高价值但开始减少 | **最高优先级挽回** |
  | `SILENT` + `VIP` | 12 | 高价值且已沉默 | 立即人工外呼 |
  | `NEW` + `VIP` | 8 | 新会员但一次就大额 | 观察，不要过早标记 |
  | `MATURE` + `ORDINARY` | 1,204 | 稳定普通客户 | 常规运营 |
  | `LOST` + `LOST` | 327 | 已流失 | 归档，不做营销 |

`DECLINING` + `VIP` 这 41 人才是真正该花钱挽回的。若两个维度合并成一个字段，这 41 人在任何单一取值里都找不到。

#### 4.6.2 阶段判定规则（可执行、带阈值）

判定**按顺序短路**，命中第一条即停止。这是为了保证规则之间不重叠、不遗漏。

  | 顺序 | 阶段 | 判定条件 | 规则编码 |
  |---|---|---|---|
  | 1 | `LOST` | `silent_days > 365` | `LC_LOST_01` |
  | 2 | `SILENT` | `silent_days` 落在 91~365 天 | `LC_SILENT_01` |
  | 3 | `NEW` | `member_age_days <= 90` 且 `consume_cnt_total <= 2` | `LC_NEW_01` |
  | 4 | `DECLINING` | `consume_cnt_recent_3m < consume_cnt_prev_3m` 且 `silent_days <= 90` | `LC_DECLINING_01` |
  | 5 | `GROWING` | `consume_cnt_recent_3m > consume_cnt_prev_3m` 且 `consume_cnt_recent_3m >= 1` | `LC_GROWING_01` |
  | 6 | `MATURE` | `consume_cnt_recent_6m_months >= 4` 且 `silent_days <= 90` | `LC_MATURE_01` |
  | 7 | `MATURE` | 以上都不命中（兜底，视为稳定） | `LC_MATURE_02` |

**算例一（DECLINING，边界清晰）：** 会员 M000123，入会 2024-03-15（会员年龄 966 天），最近一次消费 2026-09-20（`silent_days = 47`），近 3 个月消费 1 次，前 3 个月消费 4 次。

- 规则 1：`47 > 365`？否
- 规则 2：`47` 在 91~365？否
- 规则 3：`966 <= 90`？否
- 规则 4：`1 < 4` 且 `47 <= 90`？**是** → `DECLINING`，`rule_code = 'LC_DECLINING_01'`

页面展示「该会员近 3 个月消费 1 次，前 3 个月 4 次，下降 75.00%，最近一次消费在 47 天前」。

**算例二（SILENT 与 LOST 的分界）：** 会员 M000456，`silent_days = 366`。

- 规则 1：`366 > 365`？**是** → `LOST`，`rule_code = 'LC_LOST_01'`

若 `silent_days = 365`，规则 1 不命中（365 不大于 365），规则 2 命中（在 91~365 区间内，含端点）→ `SILENT`。**分界取「大于 365」而不是「大于等于 365」，是为了让「整整一年没来」仍算沉默而不是流失**——一年是常见复诊周期，第 365 天就判流失太早。

**算例三（NEW 的边界）：** 会员 M000789，入会 2026-08-10（`member_age_days = 88`），累计消费 2 次。

- `88 <= 90` 且 `2 <= 2` → **是** → `NEW`

若累计消费 3 次，即使入会 10 天，也不判 `NEW`——10 天内消费 3 次说明已经是活跃复购客户，标成「新人」会让运营发错招新券。

**算例四（从未消费的会员）：** `last_consume_date IS NULL`，`silent_days IS NULL`。此时规则 1~2 的条件涉及 NULL，SQL 中 `NULL > 365` 结果为 NULL（非 TRUE），不命中；规则 3 正常判定。若入会超过 90 天且从未消费，落到规则 7 兜底为 `MATURE`——这显然不对。

**修正：** 对从未消费的会员，`silent_days` 的判定基准改为「入会至今」，即在写入时把 `silent_days` 直接置为 `member_age_days`，同时 `last_consume_date` 保持 NULL 以便区分。这样入会 400 天从未消费的会员 `silent_days = 400` → `LOST`，符合直觉。**但字段定义上 `silent_days` 是「距上次消费天数」，对从未消费者这个语义不成立**，因此另设 `is_never_consumed` 语义通过 `first_consume_date IS NULL` 表达，页面显示「从未消费（入会 400 天）」而不是「距上次消费 400 天」。

**组合语义约束（最容易漏的一类）**

```sql
-- 【组合约束 1】never-consumed 与 silent_days 必须互斥一致
ALTER TABLE m19_member_lifecycle
    ADD CONSTRAINT ck_m19_member_lifecycle_never
    CHECK ((first_consume_date IS NULL AND last_consume_date IS NULL)
           OR (first_consume_date IS NOT NULL AND last_consume_date IS NOT NULL));
--   防的错误：改了 first_consume_date 却没同步 last_consume_date，
--   出现「首次消费日期有值、最近消费日期为空」的行，
--   页面渲染「从未消费（上次消费 1 天前）」自相矛盾。

-- 【组合约束 2】有首次消费就必须有累计消费次数 ≥ 1
ALTER TABLE m19_member_lifecycle
    ADD CONSTRAINT ck_m19_member_lifecycle_cnt_consistency
    CHECK ((first_consume_date IS NULL AND consume_cnt_total = 0)
           OR (first_consume_date IS NOT NULL AND consume_cnt_total >= 1));
--   防的错误：同步时先把消费明细写进来，第一笔结算还没同步过来时
--   先写了 first_consume_date，导致「有首消日期但消费 0 次」。

-- 【组合约束 3】stage_changed 必须与 prev_stage 吻合
ALTER TABLE m19_member_lifecycle
    ADD CONSTRAINT ck_m19_member_lifecycle_changed
    CHECK (stage_changed = (prev_stage <> '' AND prev_stage <> stage));
--   防的错误：任务算出了新阶段但忘了置 stage_changed，
--   P04 的「阶段迁移趋势图」全是平线——看起来像「没有任何会员在迁移」，
--   实际是标记位没写。这一条让不一致的数据无法落库。

-- 【组合约束 4】LOST / SILENT 阶段必须有 silent_days 且满足阈值
ALTER TABLE m19_member_lifecycle
    ADD CONSTRAINT ck_m19_member_lifecycle_lost_days
    CHECK (stage <> 'LOST' OR (silent_days IS NOT NULL AND silent_days > 365));
--   防的错误：改了阈值常量（如从 365 改成 180）却没有重算历史行，
--   于是 LOST 阶段里混着 silent_days = 200 的会员，
--   页面上「流失会员平均沉默 380 天」实际算出 310 天，
--   管理层据此以为流失在改善。

-- 【组合约束 5】规则编码必须与阶段匹配
ALTER TABLE m19_member_lifecycle
    ADD CONSTRAINT ck_m19_member_lifecycle_rule
    CHECK (rule_code = ''
           OR (stage = 'LOST' AND rule_code LIKE 'LC\_LOST\_%')
           OR (stage = 'SILENT' AND rule_code LIKE 'LC\_SILENT\_%')
           OR (stage = 'NEW' AND rule_code LIKE 'LC\_NEW\_%')
           OR (stage = 'DECLINING' AND rule_code LIKE 'LC\_DECLINING\_%')
           OR (stage = 'GROWING' AND rule_code LIKE 'LC\_GROWING\_%')
           OR (stage = 'MATURE' AND rule_code LIKE 'LC\_MATURE\_%'));
--   防的错误：规则编码是从上一版复制过来的，改了阶段没改编码，
--   于是页面「本会员因『下降趋势』被判为 GROWING」，
--   运营看到判定依据与结论对不上，从此不再相信系统。

-- 【组合约束 6】判定阈值必须与系数和复购周期自洽
ALTER TABLE m19_member_lifecycle
    ADD CONSTRAINT ck_m19_member_lifecycle_threshold_calc
    CHECK (avg_repurchase_days IS NULL
           OR silent_threshold_days = ROUND(avg_repurchase_days * churn_factor)::INTEGER);
--   防的错误：只改了 churn_factor 却没有重算 silent_threshold_days，
--   页面同时显示「流失系数 1.5」和「阈值 240 天」，
--   而 240 ÷ 160 = 1.5 要求平均周期 160 天，会员实际是 200 天，
--   三个数自相矛盾。
```

**设计说明**

- **为什么 `consume_cnt_recent_6m_months` 是「月份数」而不是「次数」**：`MATURE` 的判定语义是「稳定」，即每月至少来一次，而不是一个月来六次然后五个月不来。次数无法区分这两种情况，月份数可以。
- **为什么把 `rule_code` 和 `rule_desc` 都存下来**：`rule_code` 给程序做统计（哪个规则命中最多），`rule_desc` 给页面直接展示。若只存编码，页面要么硬编码一份「编码到说明」的映射（规则一改就过期），要么拿编码去查配置表（多一次查询）。
- **为什么 `churn_factor` 存在每行上**：阈值参数会随业务调整（1.5 → 1.8）。存在行上，重算时能看出「这一行的判定用的是哪一版参数」，避免下次调整时不知道哪些行要重算。

#### 4.7.1 RFM 模型定义与打分

**R（Recency 近期性）** 定义：`recency_days = stat_date − last_consume_date`，即距上次有效消费天数。从未消费的会员不进入本表（无 R 可言）。

**F（Frequency 频次）** 定义：`frequency_cnt` = 观察窗口（默认近 12 个月）内有效消费次数。

**M（Monetary 金额）** 定义：`monetary_amount` = 观察窗口内有效消费金额合计。

**打分方法：分位法。** 对全体有消费记录的会员，按 R 升序（越小越好）、F 升序、M 升序分别取 20%、40%、60%、80% 分位点作为档位边界，1~5 分：

  | 分档 | R（天数，越小越好） | F（次数，越大越好） | M（金额，越大越好） |
  |---|---|---|---|
  | 5 分 | `recency_days <= R20` | `frequency_cnt >= F80` | `monetary_amount >= M80` |
  | 4 分 | `R20 < recency_days <= R40` | `F60 <= frequency_cnt < F80` | `M60 <= monetary_amount < M80` |
  | 3 分 | `R40 < recency_days <= R60` | `F40 <= frequency_cnt < F60` | `M40 <= monetary_amount < M60` |
  | 2 分 | `R60 < recency_days <= R80` | `F20 <= frequency_cnt < F40` | `M20 <= monetary_amount < M40` |
  | 1 分 | `recency_days > R80` | `frequency_cnt < F20` | `monetary_amount < M20` |

**为什么用分位法而不是固定阈值：** 固定阈值（如「消费 ≥ 5,000 元算高价值」）在业务增长后会整体过时——三年后可能一半人都超 5,000 元，分群失去区分度。分位法保证永远有 20% 的人拿 5 分，分群结构稳定，横向可比。同时把本期阈值写进 `threshold_json`，重算时能看出阈值漂移。

**算例（2026 年 10 月实际阈值）：**

  | 指标 | R20 | R40 | R60 | R80 | F20 | F40 | F60 | F80 | M20 | M40 | M60 | M80 |
  |---|---|---|---|---|---|---|---|---|---|---|---|---|
  | 阈值 | 21 天 | 58 天 | 112 天 | 210 天 | 1 次 | 2 次 | 3 次 | 5 次 | 480.00 元 | 1,250.00 元 | 2,880.00 元 | 6,400.00 元 |

会员 M000321：`recency_days = 18`、`frequency_cnt = 3`、`monetary_amount = 3,150.00`。

- R：`18 <= 21` → **5 分**
- F：`3` 落在 `F40=2 ≤ 3 < F60=3` 之外（3 不小于 3），落到 `3 <= 3 < 5` → **4 分**
- M：`2,880.00 <= 3,150.00 < 6,400.00` → **4 分**

`rfm_sum = 5 + 4 + 4 = 13`。

#### 4.7.2 分群映射规则

分群**按顺序短路**判定，命中第一条即停止：

  | 顺序 | 分群 | 判定条件 | 规则编码 |
  |---|---|---|---|
  | 1 | `LOST` | 生命周期 = `LOST`（即 `recency_days > 365`） | `SG_LOST_01` |
  | 2 | `SILENT` | 生命周期 = `SILENT`（即 `recency_days` 在 91~365 天） | `SG_SILENT_01` |
  | 3 | `VIP` | `m_score >= 4` 且 `f_score >= 4` | `SG_VIP_01` |
  | 4 | `CORE` | `m_score >= 4` 且 `f_score = 3`，或 `m_score = 3` 且 `f_score >= 4` | `SG_CORE_01` |
  | 5 | `POTENTIAL` | `r_score >= 4` 且 `m_score >= 3` | `SG_POTENTIAL_01` |
  | 6 | `ORDINARY` | 其余有消费记录的会员 | `SG_ORDINARY_01` |

**算例一：** 上面那位 M000321（R=5、F=4、M=4），`recency_days = 18`（不在 91~365，也不 > 365）。

- 规则 1、2 不命中
- 规则 3：`m_score = 4 >= 4` 且 `f_score = 4 >= 4` → **是** → `VIP`，`segment_rule_code = 'SG_VIP_01'`

**算例二（任务书指定）：** 某会员 R=5 分、F=3 分、M=4 分，`recency_days` 未超过 90 天。

- 规则 1、2 不命中
- 规则 3：`m_score = 4 >= 4` 成立，但 `f_score = 3 >= 4` **不成立** → 不命中
- 规则 4：`m_score >= 4 且 f_score = 3` → **成立** → `CORE`，`segment_rule_code = 'SG_CORE_01'`

**结论：R=5、F=3、M=4 属于 `CORE`（核心客户）**，不是 `VIP`。两者的运营差别很实际：`VIP` 是「又勤又来又花钱」，直接给权益维护；`CORE` 是「花钱多但来得不算勤」，需要**提频**动作（发到店券、做复购提醒），而不是单纯给折扣。

**算例三（POTENTIAL 与 ORDINARY 的分界）：** R=5、F=2、M=3。

- 规则 3：`m_score = 4 >= 4`？否
- 规则 4：`m_score >= 4 且 f_score = 3`？否（M=3）；`m_score = 3 且 f_score >= 4`？否（F=2）
- 规则 5：`r_score = 5 >= 4` 且 `m_score = 3 >= 3` → **是** → `POTENTIAL`

这个会员近期来过、单次消费不低但次数少，是典型「有潜力但还没养成习惯」的客户，值得给一张「第二次就诊立减」的券。

#### 4.7.3 为什么明细行和汇总行走同一张表

`row_type = MEMBER` 与 `row_type = GROUP` 共表，看起来是两种东西混在一起，但合并的理由更充分：

1. **两者必然同版本**：分群汇总是明细的聚合结果。若分两张表，重算时可能出现「明细是 V2、汇总是 V1」的窗口期，页面显示的分群人数与名单人数对不上。
2. **唯一键可以同时约束两者**：`(period, stat_date, row_type, member_id, calc_version)` 对明细行是「每会员一行」，对汇总行（`member_id = 0`）是「每分群一行」，一个唯一键管住两种粒度。
3. **页面查询一次即可**：P05 页面同时要展示「各分群人数/金额占比」饼图和「点进某个分群后的会员名单」。共表时先查 `row_type = 'GROUP'` 画饼图，再查 `row_type = 'MEMBER'` 取名单，两次查询同一个表同一个索引前缀。
4. **反例代价**：拆表后，每次重算都要在两张表间协调事务；跨表查询要 JOIN；且 `GROUP` 行的比率 NULL 规则要在两张表各自实现一遍。

代价是 `row_type` 这个判别字段必须在很多地方被记住（`WHERE row_type = 'MEMBER'`）。这个代价用一条组合约束兜住了：`row_type = 'MEMBER'` 必须有 `member_id > 0`，`row_type = 'GROUP'` 必须 `member_id = 0` 且 `member_segment` 非空。

#### 4.7.4 索引设计

  | 索引名 | 类型 | 字段 | 说明 |
  |---|---|---|---|
  | `pk_m19_member_segment_snapshot` | PRIMARY | `id` | 主键 |
  | `uk_m19_member_segment_key` | UNIQUE | `period, stat_date, row_type, member_id, calc_version` | 明细行与汇总行共用一个唯一键 |
  | `idx_m19_member_segment_group` | 部分 | `period, member_segment` WHERE `row_type = 'GROUP'` | P05 饼图只查汇总行 |
  | `idx_m19_member_segment_member` | NORMAL | `member_id, period` | P-10 按会员取最新分群 |
  | `idx_m19_member_segment_value` | NORMAL | `member_segment, rfm_sum` | P05 分群内按 RFM 总和排序 |

**组合语义约束（最容易漏的一类）**

```sql
-- 【组合约束 1】明细行必须有会员，汇总行不能有会员
ALTER TABLE m19_member_segment_snapshot
    ADD CONSTRAINT ck_m19_member_segment_row_member
    CHECK ((row_type = 'MEMBER' AND member_id > 0)
           OR (row_type = 'GROUP' AND member_id = 0));
--   防的错误：汇总行误填了 member_id（比如沿用了循环变量最后一个会员的 ID），
--   于是唯一键把「VIP 汇总行」当成了「该会员的明细行」，
--   下一期重算时覆盖掉了真实明细，P-10 接口给 M22 返回了错误的个人分群。

-- 【组合约束 2】明细行必须有完整 RFM 三项分数
ALTER TABLE m19_member_segment_snapshot
    ADD CONSTRAINT ck_m19_member_segment_member_scores
    CHECK (row_type <> 'MEMBER'
           OR (r_score >= 1 AND f_score >= 1 AND m_score >= 1
               AND r_score + f_score + m_score = rfm_sum));
--   防的错误：某项分数计算失败写了 0，导致 rfm_sum 与三项之和对不上，
--   P05 页面「RFM 得分」列的合计与列表里的分项加不起来。

-- 【组合约束 3】汇总行必须有人数且金额自洽
ALTER TABLE m19_member_segment_snapshot
    ADD CONSTRAINT ck_m19_member_segment_group_cnt
    CHECK (row_type <> 'GROUP' OR (member_cnt > 0 AND sample_size = member_cnt));
--   防的错误：汇总行的 sample_size 沿用了明细行的 1，
--   于是「VIP 分群 186 人」但「样本数 1」，
--   触发小样本抑制逻辑把整个 VIP 分群隐藏掉——最该看的群看不见了。

-- 【组合约束 4】SILENT / LOST 分群必须与生命周期一致
ALTER TABLE m19_member_segment_snapshot
    ADD CONSTRAINT ck_m19_member_segment_silent_days
    CHECK ((member_segment <> 'SILENT' OR (recency_days BETWEEN 91 AND 365))
           AND (member_segment <> 'LOST' OR recency_days > 365));
--   防的错误：分群任务与生命周期任务用了不同的基准日，
--   同一会员在生命周期表里是 SILENT，在分群表里 recency 却是 400 天，
--   两个页面对同一个会员显示不同的状态，客户经理不知该信谁。

-- 【组合约束 5】小样本抑制只对汇总行生效
ALTER TABLE m19_member_segment_snapshot
    ADD CONSTRAINT ck_m19_member_segment_suppress
    CHECK (is_suppressed = FALSE OR row_type = 'GROUP');
--   防的错误：明细行被标记抑制后页面不展示该会员，
--   于是这个人莫名其妙从所有名单里消失，运营以为他注销了。

-- 【组合约束 6】阈值必须完整落在 JSON 里
ALTER TABLE m19_member_segment_snapshot
    ADD CONSTRAINT ck_m19_member_segment_threshold
    CHECK (threshold_json ? 'r20' AND threshold_json ? 'f20' AND threshold_json ? 'm20');
--   防的错误：只写了部分阈值，重算时无法还原当期分档边界，
--   「上月 VIP 的 186 人中有 12 人本月掉出」这类问题查不出原因。
```

**设计说明**

- **为什么 `r_score` 用 `SMALLINT` 不用 `INTEGER`**：取值只有 0~5，`SMALLINT` 占 2 字节而 `INTEGER` 占 4 字节。本表 184 万行 × 3 个分数字段，省下约 11 MB，且都在同一个数据页内，扫描更快。
- **为什么 `threshold_json` 用 JSONB 不用多列**：分档阈值有 12 个（R/F/M 各 4 个分位点）。建 12 个列既占空间，又要在每次新增分档（如从 5 档改 7 档）时改表结构。JSONB 支持 `?` 运算符与 GIN 索引，且 `ck_m19_member_segment_threshold` 能校验必需键存在。
- **为什么 `is_suppressed` 只对汇总行**：小样本抑制的目的是「不让人从一个聚合数反推出个体」。明细行是单个人，抑制它反而让这个人从名单里消失。所以抑制只对 `GROUP` 行有意义，组合约束 5 把这一点落到了数据层。

#### 4.8.1 风险分公式与判定规则

**综合风险分** `risk_score` ∈ [0, 100]，由四部分相加，每部分有独立上限：

```
risk_score = score_silent_part + score_value_part + score_trend_part + score_stage_part
```

其中 `score_stage_part` 由 `lifecycle_stage` 直接决定（`LOST` 给 10 分，`SILENT` 给 0 分），不单独存字段（可由 `lifecycle_stage` 反推，存了会与阶段不一致）。

**沉默分 `score_silent_part`（上限 40）：**

```
score_silent_part = LEAST(40, silent_ratio × 20)
其中 silent_ratio = silent_days ÷ silent_threshold_days
     silent_threshold_days = ROUND(avg_repurchase_days × churn_factor)
```

- 沉默天数刚好到阈值（`silent_ratio = 1.0`）→ 20 分
- 沉默天数是阈值的 2 倍（`silent_ratio = 2.0`）→ 40 分（触顶）

**价值分 `score_value_part`（上限 35）：**

```
score_value_part = LEAST(35, amount_recent_12m ÷ 1000 × 5)
```

- 近 12 月消费 0 元 → 0 分（本来就没价值，流失无所谓）
- 近 12 月消费 3,000 元 → 15 分
- 近 12 月消费 7,000 元及以上 → 35 分（触顶）

**趋势分 `score_trend_part`（上限 15）：**

```
trend_rate = (amount_recent_3m − amount_prev_3m) ÷ amount_prev_3m
score_trend_part = CASE
    WHEN trend_rate IS NULL THEN 7          -- 前 3 月无消费，无法算趋势，给中间值
    WHEN trend_rate >= 0 THEN 0             -- 上升或持平，不扣分
    ELSE LEAST(15, abs(trend_rate) × 15)    -- 下降越多扣越多
END
```

- 前 3 月 2,000 元、近 3 月 500 元 → `trend_rate = -0.75` → 11.25 分
- 前 3 月 2,000 元、近 3 月 2,200 元 → `trend_rate = +0.10` → 0 分

**风险等级门槛：**

  | 等级 | 条件 | 处置 |
  |---|---|---|
  | `CRITICAL` | `risk_score >= 75` | 推送 M19-03，人工外呼，优先级 1 |
  | `HIGH` | `50 <= risk_score < 75` | 推送 M19-03，优先级 2 |
  | `MEDIUM` | `25 <= risk_score < 50` | 推送 M19-03，优先级 3 |
  | `LOW` | `risk_score < 25` | 不推送，仅看板展示 |

**算例一（任务书要求的可执行算例）：会员 M000888，90 天未到店 + 历史年消费 12,000 元。**

- `silent_days = 90`，`avg_repurchase_days = 200`，`churn_factor = 1.5` → `silent_threshold_days = 300`
- `silent_ratio = 90 ÷ 300 = 0.300000` → `score_silent_part = 0.3 × 20 = 6.00`
- `amount_recent_12m = 12,000.00` → `score_value_part = LEAST(35, 12 × 5) = LEAST(35, 60) = 35.00`（触顶）
- `amount_prev_3m = 3,000.00`，`amount_recent_3m = 800.00` → `trend_rate = (800 − 3,000) ÷ 3,000 = -0.733333` → `score_trend_part = LEAST(15, 0.733333 × 15) = 11.00`
- `lifecycle_stage`：`silent_days = 90` 不在 91~365 → 不是 `SILENT`；实际该会员在生命周期表里是 `DECLINING`——**此时不应出现在本表**。

修正场景：该会员实际是 95 天未到店（`SILENT`）。则 `score_stage_part = 0`，`silent_ratio = 95 ÷ 300 = 0.316667` → `score_silent_part = 6.33`。

`risk_score = 6.33 + 35.00 + 11.00 + 0 = 52.33` → **`HIGH`**，推送 M19-03，优先级 2。

页面展示：「该会员 95 天未到店（阈值 300 天），近 12 个月消费 12,000.00 元，近 3 个月消费 800.00 元环比下降 73.33%。风险分 52.33（HIGH）。建议：人工外呼 + 到店礼。」

**算例二（CRITICAL 边界）：某会员 400 天未到店，历史年消费 8,000 元，近 3 月 0 元，前 3 月 1,500 元。**

- `silent_days = 400`，`avg_repurchase_days = 180`，阈值 = `180 × 1.5 = 270`
- `silent_ratio = 400 ÷ 270 = 1.481481` → `score_silent_part = LEAST(40, 1.481481 × 20) = LEAST(40, 29.63) = 29.63`
- `score_value_part = LEAST(35, 8 × 5) = 35.00`（触顶）
- `trend_rate = (0 − 1,500) ÷ 1,500 = -1.000000` → `score_trend_part = LEAST(15, 15.00) = 15.00`（触顶）
- `lifecycle_stage = 'LOST'` → `score_stage_part = 10`

`risk_score = 29.63 + 35.00 + 15.00 + 10 = 89.63` → **`CRITICAL`**，优先级 1。

**算例三（LOW，不该打扰）：某会员 100 天未到店，近 12 月消费 200 元，前 3 月 100 元、近 3 月 100 元。**

- 阈值：无复购间隔样本 → `avg_repurchase_days IS NULL` → 兜底 `silent_threshold_days = 180`
- `silent_ratio = 100 ÷ 180 = 0.555556` → `score_silent_part = 11.11`
- `score_value_part = 200 ÷ 1000 × 5 = 1.00`
- `trend_rate = (100 − 100) ÷ 100 = 0` → `score_trend_part = 0`
- `score_stage_part = 0`

`risk_score = 11.11 + 1.00 + 0 + 0 = 12.11` → **`LOW`**，不推送。

这个会员已沉默 100 天，但历史上只花了 200 元。若只按「沉默天数」排序，他会排在很前面，触发外呼——外呼成本约 15 元/次，召回成功率不到 5%，投入产出为负。**价值分这一项的作用就是把这类打扰挡在门外。**

#### 4.8.2 为什么不能直接发消息，只能推事件

任务书要求「触发后要能对接 M19-03 召回，不直接发消息，走关怀规则」。落地方式是：

1. 本表写入 `risk_level >= MEDIUM` 的行，并置 `is_pushed = FALSE`
2. Celery 任务 `task_m19_member_churn_push`（每日 06:30）扫描 `is_pushed = FALSE` 且 `risk_level <> 'LOW'` 的行，发布事件 `m19.member.risk_lost`，载荷仅含 `member_id`、`risk_level`、`last_visit_date`、`silent_days`，不携带任何消费金额，然后把 `is_pushed` 置 TRUE
3. M19-03 收到事件后，**按自己的关怀规则**决定是否触达、用什么话术、什么时间发
4. M19-03 触达前必须过三道闸门（意愿闸门 `check-blacklist`、时段闸门 21:00~次日 08:00、频次闸门 `m19:throttle:{patient_id}`），任一道不过则 `care_task.status = 'SUPPRESSED'`

**为什么本子模块不直接调 `POST /internal/v1/message/send`：** 三个理由。

1. **规则归属**：什么情况该发、发什么、发几次，是关怀策略，归 M19-03。本子模块只负责「谁该被关怀」的判定。若本子模块直接发，规则就分裂在两个地方，运营改话术要改两处。
2. **三道闸门只有 M19-03 有完整实现**：退订名单、免打扰时段、频次控制是关怀任务执行时的统一前置逻辑。本子模块绕过它直接发消息，等于绕过了全部合规约束。
3. **可回溯**：走事件后，关怀执行结果在 `m19_care_task` 里，页面能回答「这个流失会员最后到底有没有被联系上」。直接发消息则本子模块只知道「发出去了」，不知道「对方收到了吗」。

**组合语义约束（最容易漏的一类）**

```sql
-- 【组合约束 1】分项之和必须等于总分
ALTER TABLE m19_member_churn_risk
    ADD CONSTRAINT ck_m19_member_churn_score_sum
    CHECK (score_silent_part + score_value_part + score_trend_part <= risk_score);
--   防的错误：改了某个分项公式却没重算总分，
--   页面「风险分 52.33」展开后「沉默 6.33 + 价值 35.00 + 趋势 11.00 = 52.33」
--   对得上，但实际是巧合；换成另一个会员就差 10 分，
--   运营追问「这 10 分从哪来的」答不出。
--   注：用 <= 而非 = 是因为 LOST 阶段的 10 分不存字段，总分包含它。

-- 【组合约束 2】LOST 阶段的总分必须包含阶段分
ALTER TABLE m19_member_churn_risk
    ADD CONSTRAINT ck_m19_member_churn_lost_part
    CHECK (lifecycle_stage <> 'LOST'
           OR risk_score = score_silent_part + score_value_part + score_trend_part + 10);
--   防的错误：LOST 会员的阶段分漏加，
--   于是「400 天没来」的会员风险分反而低于「100 天没来」的，
--   P06 按风险分排序时最先被看到的不是最该挽回的人。

-- 【组合约束 3】风险等级必须与分数吻合
ALTER TABLE m19_member_churn_risk
    ADD CONSTRAINT ck_m19_member_churn_level_score
    CHECK ((risk_level = 'LOW' AND risk_score < 25)
           OR (risk_level = 'MEDIUM' AND risk_score >= 25 AND risk_score < 50)
           OR (risk_level = 'HIGH' AND risk_score >= 50 AND risk_score < 75)
           OR (risk_level = 'CRITICAL' AND risk_score >= 75));
--   防的错误：等级按旧门槛算出（如 HIGH 门槛原为 60），
--   门槛改成 50 后只重算了分数没重算等级，
--   于是「65 分的 LOW」和「45 分的 HIGH」同时存在，
--   P06 按等级筛选时把真正危险的人漏掉。

-- 【组合约束 4】SILENT 阶段沉默天数必须在 91~365
ALTER TABLE m19_member_churn_risk
    ADD CONSTRAINT ck_m19_member_churn_silent_days
    CHECK ((lifecycle_stage <> 'SILENT' OR (silent_days >= 91 AND silent_days <= 365))
           AND (lifecycle_stage <> 'LOST' OR silent_days > 365));
--   防的错误：生命周期任务与本任务的基准日不同（一个是 T 日 05:00，
--   一个是 T 日 06:00），跨零点时 `silent_days` 差 1 天，
--   于是 `SILENT` 行出现 `silent_days = 90` 的不合法组合，
--   P06 的「沉默 91~365 天」筛选条件对不上。

-- 【组合约束 5】推送状态必须与等级和时刻一致
ALTER TABLE m19_member_churn_risk
    ADD CONSTRAINT ck_m19_member_churn_pushed
    CHECK ((is_pushed = FALSE AND pushed_at IS NULL)
           OR (is_pushed = TRUE AND pushed_at IS NOT NULL AND risk_level <> 'LOW'));
--   防的错误：LOW 等级也被标记为已推送——
--   M19-03 收到事件后会按关怀规则给一个本来没价值的客户发消息，
--   浪费触达额度并挤占真正需要关怀的人群。

-- 【组合约束 6】召回优先级必须与等级匹配
ALTER TABLE m19_member_churn_risk
    ADD CONSTRAINT ck_m19_member_churn_priority_level
    CHECK ((risk_level = 'LOW' AND recall_priority = 0)
           OR (risk_level = 'MEDIUM' AND (recall_priority = 3 OR recall_priority = 4))
           OR (risk_level = 'HIGH' AND recall_priority = 2)
           OR (risk_level = 'CRITICAL' AND recall_priority = 1));
--   防的错误：优先级由「等级 × 价值分群」交叉得出，
--   交叉表改了却只改了等级字段，于是「CRITICAL 但优先级 3」—— 
--   外呼团队按优先级取名单时，最危险的客户被排到第三批。
```

**设计说明**

- **为什么 `score_legal_ok` 这个看似冗余的布尔字段要保留**：它是「分数自检结果」。公式改动后，同一行数据可能同时出现「按新公式算的分数」和「按旧公式写的分项」。这个字段在写入时由程序判定：`abs(risk_score − (分项和 + 阶段分)) <= 0.000001` 则 TRUE。判 FALSE 时任务直接报错而非静默写入，避免脏数据进入页面。
- **为什么 `silent_ratio` 用 `NUMERIC(10,6)` 而阈值用 `INTEGER`**：比例要保留 6 位小数参与评分（`silent_ratio × 20` 后仍是 6 位），阈值是天数只能是整数。若两者都用 `NUMERIC`，`ROUND` 的行为会在不同版本间出现差异。
- **为什么 `recall_channel` 是建议而非决定**：本子模块推荐渠道（如高价值沉默客户建议 `PHONE`），最终发什么渠道由 M19-03 按关怀规则与患者偏好决定。存下来只是为了让 M19-03 有一个默认值，且 P06 页面能展示「建议外呼」。

#### 4.9.1 标签体系为什么用「域 + 编码 + 取值 + 分档」四段结构

最简单的做法是「一个会员一行，列是各个标签的布尔值」（`is_high_value`、`is_refractive`、`is_wechat`……）。这个做法在标签少于 20 个时可行，但它有三个致命问题：

1. **加标签要改表结构**：每新增一个标签就要 `ALTER TABLE ADD COLUMN`。M19 上线后预计每季度会加 3~5 个标签，一年就是 20 列，表结构永远在变。
2. **无法按标签值查询**：`is_high_value = TRUE` 能查，但「消费分档 = HIGH」这种带值的标签查不了，只能再建一列 `consume_level`。
3. **无法表达「为什么是这个标签」**：布尔值没有依据。运营问「为什么张三是高价值客户」，答不出。

四段结构解决这三个问题：

- `tag_domain` 把标签分组（消费 / 诊疗 / 偏好 / 渠道 / 风险），页面按域分卡片展示
- `tag_code` 是标签的唯一标识，新标签只是新增一行数据，不动表结构
- `tag_value` + `tag_level` 表达「有值标签」与「分档标签」
- `evidence_json` 存判定依据，页面可以直接展示「消费 12,000.00 元 ≥ 阈值 5,000.00 元」

代价是行数变多：每个会员平均 3 个标签，540 万行（3 年）。这个代价用 `(member_id, tag_code, tag_value, calc_version)` 唯一索引与按 `tag_code` 的部分索引控制住，查「所有做屈光手术的高价值客户」是一次 `INTERSECT` 或 `EXISTS` 子查询，都在索引内完成。

```sql

--   半年后没人知道「为什么张三被标成流失风险 HIGH」，

-- 【组合约束 4】证据必须是对象而非标量

    ADD CONSTRAINT ck_m19_member_profile_tag_evidence
    CHECK (jsonb_typeof(evidence_json) = 'object');
--   防的错误：程序把判定依据存成数组或字符串，
```

**设计说明**

- **为什么 `tag_value` 进唯一键**：同一会员可能同时有 `CONSUME_PREFERENCE` = `REFRACTIVE` 和 `CONSUME_PREFERENCE` = `OPTICAL`（既做过手术又配过镜）。若唯一键只有 `(member_id, tag_code, calc_version)`，第二个标签会把第一个覆盖掉，导致「做过屈光手术的客户」名单漏人。
- **为什么画像表不存金额**：任务书第 10 条隐私红线要求「分析结果不得输出可识别身份的信息」。金额是最敏感的字段之一。分群表已经有 `m_quantile`（分位位置），足以表达「这个人在金额维度上排第几档」，不需要再在每个标签上重复存绝对金额。需要绝对金额的页面走分群表，且受功能权限 `m19:member:analysis:sensitive:view` 保护。

#### 4.10.1 为什么导出的脱敏等级要落到表里而不是只看请求参数

导出请求里当然会带 `mask_level`，但只靠参数有一个隐患：**文件生成后，参数就消失了**。三天后审计问「2026-11-06 14:32 导出的那份 1.2 万行会员名单，手机号脱敏了没有」，如果表里没存，只能翻应用日志，而日志通常只保留 30 天。

存进表里的三个用途：

1. **事后审计可举证**：审计直接查 `WHERE export_no = 'EX202611060032'`，看到 `mask_level = 'ID_PHONE_MASKED'` 与 `suppressed_row_cnt = 12`。
2. **防止绕过审批**：含敏感字段（`has_sensitive = TRUE`）的导出必须 `approved_by` 非空。这条组合约束在数据层拦住「先导出后补审批」的做法。
3. **统计脱敏执行情况**：按月统计 `mask_level = 'NONE'` 的导出行数，若某个账号大量导出不脱敏数据，权限管理员能看到。

#### 4.10.2 小样本抑制在导出时怎么落地

页面上的小样本抑制（n < 5 不展示）在导出时同样必须生效，且要**留痕抑制了多少行**：

  | 场景 | 页面表现 | 导出表现 | 留痕 |
  |---|---|---|---|
  | 分群汇总行人数 < 5 | 显示「样本不足，已隐藏」 | 该行不写入，`suppressed_row_cnt` +1 | `suppressed_row_cnt` |
  | 各分群明细人数 < 5 | 名单为空并提示 | 名单不写入，`suppressed_row_cnt` + 该群人数 | `suppressed_row_cnt` |
  | 单会员明细行（`row_type = MEMBER`） | 正常展示 | 正常导出 | 不抑制 |

**为什么单会员明细行不抑制**：抑制的目的是防止「从一个聚合数反推出个体」。单个会员的行本身就是个体，不存在反推问题，抑制它只会让运营以为这个人不存在。

**约定：** 一次导出中若 `suppressed_row_cnt > 0`，文件首页生成一行说明「本次导出有 N 行因样本不足 5 被抑制」，并且页面下载按钮旁展示同样的提示。让拿到文件的人知道**这份名单不完整**，而不是以为就是全部。

**设计说明**

- **为什么 `filter_json` 要存筛选条件快照**：同一个月，运营可能导出 5 次「10 月分群名单」，每次筛选条件略有不同。三次后有人问「上周那版和这版差在哪」，只有存了条件才能复现。
- **为什么 `file_hash` 用 SHA-256 而不是 MD5**：MD5 已被证明可制造碰撞。这份文件可能作为「数据是否被篡改」的举证材料，用 SHA-256 才站得住。
- **为什么 `requested_by_name` 要存快照而不 JOIN m01 用户表**：导出记录要保留 3 年，用户可能离职、改名、数据被清理。存姓名快照，三年后仍能回答「是谁导的」。

#### 4.11.1 为什么口径变更必须留痕且不能原地改数

任务书第 8 条要求「口径变更后可整期重算且能对比新旧结果」。落地的前提是**旧结果不被删除**：

1. `calc_version` 升版：新版本计算写入 `calc_version = 2` 的新行，`calc_version = 1` 的行原样保留
2. 每次升版写入一条 `oper_type = 'VERSION_BUMP'` 的日志，`before_json` 记录旧口径表达式，`after_json` 记录新口径表达式
3. 页面可以并排展示「V1 复购率 34.52% / V2 复购率 34.10%，差 −0.42 个百分点」

**反例：** 若升版时直接 `UPDATE ... SET repurchase_rate = 新值 WHERE period = '2026-10'`，那么历史趋势图上 10 月会突然从 34.52% 变成 34.10%，而 9 月是 33.80%（旧口径）。跨口径的趋势线看起来像「10 月复购率大涨」，实际只是算法变了。这种误读在真实业务里非常常见，且极难事后发现——因为旧值已经不存在了。

**设计说明**

- **为什么 `operator_id` 系统任务填 `0` 而不是 NULL**：`0` 是一个显式值，可以用 `WHERE operator_id = 0` 精确筛出系统操作。用 NULL 的话，`operator_id IS NULL` 与「字段没写」无法区分。
- **为什么日志表也 `REVOKE UPDATE, DELETE`**：操作日志是审计证据。若应用账号能改日志，出事后「改掉不利记录」只需要一条 SQL。撤销权限后，应用账号只能 `INSERT`。
- **为什么 `before_json` / `after_json` 用 `{}` 而不是 NULL**：JSONB 的比较运算对 NULL 不友好（`NULL <> '{}'` 结果是 NULL 而非 TRUE）。用空对象做哨兵，`ck_m19_member_oper_log_version_bump` 中的 `<>` 比较才能可靠工作。

## 4.13 Pydantic Schema 定义

以下 Schema 与接口层一一对应，文件路径 `app/schemas/m19/member_analysis.py`。**所有 `Decimal` 字段禁止接收 `float`**，统一在 `field_validator` 中把 `float` 转成 `str` 再交给 Pydantic 解析，避免二进制浮点误差。

```python
"""M19-06 会员运营与消费分析 Pydantic Schema。

红线：金额与比率一律 Decimal，接口层禁止出现 float。
"""

from __future__ import annotations

from datetime import date, datetime
from decimal import Decimal
from typing import Generic, Literal, TypeVar

from pydantic import BaseModel, ConfigDict, Field, field_validator, model_validator

T = TypeVar("T")

IdentityKeyType = Literal["PATIENT_ID", "MEMBER_ID", "CUSTOMER_NO"]
MemberSegment = Literal["VIP", "CORE", "POTENTIAL", "ORDINARY", "SILENT", "LOST"]
LifecycleStage = Literal["NEW", "GROWING", "MATURE", "DECLINING", "SILENT", "LOST"]
RiskLevel = Literal["LOW", "MEDIUM", "HIGH", "CRITICAL"]
SourceStatus = Literal["COMPLETE", "PARTIAL", "MISSING"]
DataQuality = Literal["REALTIME", "DAILY", "ESTIMATED"]
RowType = Literal["MEMBER", "GROUP"]
ExportScope = Literal["CONSUME", "REPURCHASE", "LIFECYCLE", "SEGMENT", "CHURN", "PROFILE"]
ExportFormat = Literal["EXCEL", "CSV", "PDF"]
MaskLevel = Literal["NONE", "ID_ONLY", "ID_PHONE_MASKED"]
ExportStatus = Literal["RUNNING", "SUCCESS", "FAILED", "EXPIRED"]


class M19Schema(BaseModel):
    """全部 M19-06 Schema 的基类。"""

    model_config = ConfigDict(
        from_attributes=True,
        extra="forbid",
        str_strip_whitespace=True,
        validate_assignment=True,
    )

    @field_validator("*", mode="before")
    @classmethod
    def _reject_float(cls, value: object) -> object:
        """把 float 转成字符串，交给 Decimal 解析，杜绝二进制浮点误差。"""
        if isinstance(value, float):
            return repr(value)
        return value
```

### 6.2 分区与保留期

  | 表 | 分区方式 | 保留期 | 归档策略 |
  | --- | --- | --- | --- |
  | `m19_member_consume_snapshot` | 不分区 | 永久 | 按月索引；单表 411 万行在 PG 16 上可全表并行扫描 |
  | `m19_member_consume_detail_snap` | 不分区 | 3 年 | 3 年后按 `biz_date` 导出冷存后物理删除（需财务与合规会签） |
  | `m19_member_sync_log` | 按 `log_time` 月度 RANGE + DEFAULT | 3 年 | DETACH 后归档 |
  | `m19_member_repurchase_fact` | 不分区 | 永久 | 仅 1,200 行，永久保留用于趋势与口径对比 |
  | `m19_member_lifecycle` | 不分区 | 2 年 | 按 `period` 删除 2 年前 |

  | `m19_member_profile_tag` | 不分区 | 永久 | 画像用于长期趋势，不删 |
  | `m19_member_export_task` | 不分区 | 3 年 | 导出文件 7 天后删除，任务记录保留 |
  | `m19_member_oper_log` | 按 `log_time` 月度 RANGE + DEFAULT | 3 年 | DETACH 后归档 |

**为什么只有两张日志表分区：** 分区带来的收益主要是「按分区键批量清理」与「分区裁剪加速范围查询」。业务快照表的查询模式是 `WHERE member_id = ?` 或 `WHERE period = ?`，分区键若选 `stat_date`，按会员查询仍然要扫全部分区，收益为零，反而让唯一键必须带上分区键（PostgreSQL 要求分区表的主键包含分区键），破坏了 `uk (stat_date, member_id, biz_type, identity_key_type)` 的简洁性。日志表按时间清理是刚需，分区才有意义。

### 6.3 索引膨胀与维护

  | 表 | 索引数 | 预估索引大小 | 维护要点 |
  | --- | --- | --- | --- |
  | `m19_member_consume_snapshot` | 8 | 约 1.8 GB | 每日 `ANALYZE`；`uk` 是热更新目标，`fillfactor` 设 80 |
  | `m19_member_consume_detail_snap` | 9 | 约 1.1 GB | 只增不改，无 HOT 更新压力，`fillfactor` 保持默认 100 |
  | `m19_member_lifecycle` | 4 | 约 0.6 GB | 每日全量重写，建议 `VACUUM (FULL)` 每月一次 |
  | `m19_member_segment_snapshot` | 5 | 约 0.6 GB | 同上 |
  | `m19_member_profile_tag` | 6 | 约 1.9 GB | 每日新增，按 `created_at` 删旧 |

`m19_member_consume_snapshot` 的 `fillfactor` 设为 80 的理由：重算与补数会频繁 `UPDATE` 同一批行，留 20% 空间让 HOT 更新能落在原页，避免每次更新都写新索引项。

## 附录 C 造数要点

  | 场景 | 造数方式 | 校验点 |
  | --- | --- | --- |
  | 双口径差异 | 造 100 个 patient_id，其中 40 个有 member_id，每人 2 次消费 | 复购事实应有 2 行，`repurchase_rate` 两行差约 0.0724 |
  | 分母为 0 | 造一个会员只有 1 次消费 | 该会员不计入 `repurchase_customer_cnt` |
  | 空窗口 | 造一个期间无任何消费 | `repurchase_rate IS NULL`，不是 0 |
  | 事件丢失 | 直接写明细快照但跳过 `m16.settlement.completed` | `gap_filled = TRUE`、`gap_fill_reason = 'EVENT_LOST'` |
  | 多卡一号 | 同 patient 两张卡，两卡各一笔消费 | 明细行 `identity_merge_rule = 'MULTI_CARD_MERGED'` |
  | 手机号冲突 | 两卡不同 patient_id 但同手机号 | 明细行 `identity_merge_rule = 'CONFLICT'`、`is_valid_consume = FALSE` |
  | 小样本抑制 | 造一个分群只有 3 人 | 分群快照 `is_suppressed = TRUE` |
  | 封账保护 | 对 30 天前的期执行重算 | 任务返回拒绝，错误码 `"1906019"` |
