**设计说明：**

1. **`m11_consultation` 是本子模块唯一的主表，一次咨询一条记录。** `consult_no`（`ZX` + YYYYMMDD + 4 位）是全局唯一业务单号，被 M16-04（开单时识别来源）、M22（运营报表）、M20（特殊病例审批）以字段形式引用，同时是本子模块对外契约 P-11 的主键。**它承载的是「这个潜在患者想做什么、我们判断能不能做、他有没有来」，而不是「他花了多少钱」**——金额只存 M16 返回的快照。

2. **初筛问卷独立成表（`m11_consult_screening`）而非塞进主表。** 初筛问卷有 20 余个采集项（年龄、屈光度、角膜厚度、既往史、禁忌项勾选、佩戴史），且会被反复重填（患者补充信息、复诊时更新）。主表已有 60 余个字段，再塞 20 个会让「哪些字段必填」的语义变得模糊。独立成表后，`m11_consultation.screen_result` 只存最终结论，问卷明细全部在子表，且支持一次咨询多版本问卷（`screen_seq`）。

3. **回访跟进独立成表且按「一次回访一条」。** 一次咨询平均产生 3.6 次回访（首次接触、术前检查前提醒、方案后催单、术后关怀），每次回访有独立的计划时间、执行人、结果、下次计划。若存在主表只能保留最后一次，回访过程（这是转化漏斗分析的核心原料）就丢失了。

4. **转介绍独立成表（`m11_consult_referral`）。** 转介绍是双向关系（介绍人 A → 被介绍人 B），而咨询单是单主体的。若把 `referrer_patient_id` 塞进主表，只能表达「B 是被 A 介绍来的」，无法回答「A 一共介绍了多少人、这些人转化了多少、该给多少奖励」。独立表让关系成为一等公民。

5. **`m11_consult_stat` 是预聚合统计表**，按「日期 × 咨询师 × 渠道」汇总漏斗与业绩。转化漏斗（11 个状态逐层的转化率）是屈光中心的核心经营看板，实时从 8 万行咨询单聚合需 2~5 秒，预聚合后单次查询 < 10ms。

6. **不建物理外键。** 与 M05-01/M10-01 同一策略：`patient_id` 指向 M03、`consultant_id` 指向 M01-02，跨 schema 外键不可用；咨询单是高写入表（日均 60~80 条 INSERT + 大量 UPDATE），外键检查拖慢写入。一致性由应用层校验 + 每日 03:10 的对账任务 `reconcile_consult_refs` 保证。

7. **`m11_consult_log` 是只增表**，触发器禁止 UPDATE/DELETE，按 `created_at` 月度 RANGE 分区并带 DEFAULT 分区兜底（共享规范 2.6）。状态流转、意向等级调整、转介绍奖励认定三类动作必须留痕，这是运营争议与绩效核算的证据基础。

8. **`m11_consult_config` 单独成表而非硬编码。** 咨询超时天数、回访间隔策略、禁用人群阈值（如年龄上限、角膜厚度下限）都会随政策与临床共识调整，且屈光中心与眼科门诊的口径可能不同，需要 GLOBAL/DEPT 两级覆盖。

**设计说明：**

1. **为什么 `patient_id` 允许为空？** 屈光咨询有大量「纯线上线索」：抖音留资、美团咨询、电话询价，这些来询者尚未到院建档。若强制 `patient_id`，前台就得为每个询价者建患者主索引，M03 会被大量无业务记录污染（二级医院年咨询量约 2 万条，真正到院约 6 千条，**污染率 70%**）。允许为空后，只有到店挂号或建立联系时才回填，既保证线索不丢，又保护患者主索引的干净。约束上通过 `patient_name` 必填 + `phone` 或 `wechat_no` 至少一个联系方式的业务校验兜底。

2. **为什么 `consult_no` 在 `NEW` 状态为空？** 与 M10-01 验光单同一思路：**单号是「有效业务」的标识，不是「录入动作」的标识**。线上表单批量导入、前台快速留资每天会产生大量最终无效的线索（空号、误点、同行探价）。若每条都取号，日均 80 条咨询中约 25 条会变成废号（**废号率 31%**），单号段被大量无意义消耗。首次实际跟进（状态进入 `CONTACTING`）时才取号，`ck_m11_consultation_no_required` 保证除 `NEW` 外都必须有号。

3. **为什么 `intent_level` 用 A/B/C/D 四级而不是数字 1~5？** 这是行业通行口径（屈光中心、医美、口腔都用 ABCD）。用字母的好处是：①排序时 `A > B > C > D` 的语义直观，且不与「优先级数字越小越高」混淆 ②外部报表（M22）与集团口径一致，无需换算。四级而非五级，是因为 D（待观察）与 C（低意向）在实际业务中边界清晰，再细分没有数据支撑。

4. **为什么金额字段带 `_snap` 后缀且必须有 `quote_ref`？** M11 **不计算任何金额**（共享规范铁律 2）。咨询师在页面上看到的报价来自 M16-06 的优惠试算接口，M11 只存返回值。加 `_snap` 后缀是**命名即约束**：任何看到这个字段的人都知道它是快照、不可作为收款依据。要求同时存 `quote_ref` 是为了让快照可追溯到某一次具体试算——否则 M16 调价后，咨询单里的旧报价就变成无法解释的数字。

5. **为什么 `screen_result` 与 `status` 是两个独立字段而不是合并？** `status` 描述**患者旅程阶段**（他到哪一步了），`screen_result` 描述**医学判断结论**（能不能做）。二者正交：一个患者可能已是 `SURGERY_BOOKED`（旅程很靠后），但 `screen_result` 仍是 `HOLD`（某项检查待补）；也可能 `SCREENED` 状态下结论是 `REJECT`（已判定不能做，但患者还在犹豫要不要做其他方案）。合并会导致「阶段」与「结论」的语义互相污染，漏斗统计也会失真。

6. **为什么 `is_contraindication` 要单独一列？** 禁忌命中是**硬拦截条件**（`REJECT` 且不可被咨询师改判）。单独一列让①数据库约束 `ck_m11_consultation_contraindication` 能强制「命中禁忌必须是 REJECT」②质控可以一眼筛出所有禁忌病例做复核③统计「禁忌命中率」不需要解析 JSON。`contraindication_codes` 数组则保留具体命中了哪几条，供医师复核与科研使用。

**设计说明：**

1. **为什么初筛问卷要独立成表而不是主表加 24 个字段？** 主表已有 60 余个字段，再塞 24 个会让「这条记录是什么」的语义崩塌。更关键的是**版本化需求**：患者首次填完是 `HOLD`（缺角膜厚度），补测厚度后重填希望是 `PASS`。若字段在主表上，重填即覆盖，历史结论丢失，无法回答「这个患者被拒过几次、为什么」。独立表的 `screen_seq` + `is_locked` 让每次填写成为不可变快照。

2. **为什么既存 `sphere_od` 又存 `sphere_equiv_max_abs`？** 原始球柱轴必须保留（医师复核要看具体度数），但**术式适配判定只看球镜等效的绝对值**（因为 SSE 才是角膜切削量的决定因素）。存冗余计算列的好处是：①部分索引与筛选条件能直接用一列 ②避免每次查询都写表达式 `abs(sphere + cylinder/2)`。计算规则在服务层统一实现（`ROUND_HALF_UP` 到 0.25D），数据库层只存结果。

3. **为什么 `contraindication_count_abs` / `_rel` 要单独两列？** 绝对禁忌与相对禁忌的处置完全不同：绝对禁忌 → 结论必须 `REJECT`（不可改判）；相对禁忌 → 结论至少 `HOLD`（可补检后放行）。用两列可以让数据库约束 `ck_m11_consult_screening_abs_reject` 与 `ck_m11_consult_screening_rel_not_pass` **在存储层就拦住非法组合**，而不是依赖服务层记得判断。这是把业务规则下沉到约束的典型收益：即使有人绕过接口直接改库，数据也不会脏。

4. **为什么 `refractive_data_source` 要区分四个来源？** 因为可信度完全不同：`M10_OPTOMETRY`（本院验光，有单号可追溯）> `EXTERNAL`（外院资料，可能过期）> `SELF_REPORT`（患者自报，误差可达 1.00D）。初筛结论的可信度必须与数据来源挂钩——若仅凭患者自报就给出 `PASS`，术中可能发现实际度数超出术式范围，造成方案返工与投诉。`optometry_no_ref` 保证引用本院数据时可回溯到具体验光单。

5. **为什么 `need_preop_exam_items` 用 JSONB 而不是关联表？** 它是**一次问卷的临时建议清单**，不是需要独立管理的实体：不需要按检查项反查，不需要单独维护生命周期，写出后只读。用 JSONB 省掉一张表和一次 JOIN。若未来需要「按检查项统计补检率」，可加 GIN 索引直接聚合（`idx_m11_consult_screening_codes` 即为此预留）。

**设计说明：**

1. **为什么回访要独立成表且带 `followup_seq`？** 一次咨询平均 3.6 次回访（首次接触 → 检查前确认 → 检查后解读 → 方案后催单，部分还有术前提醒与长期唤醒）。这是**转化过程的唯一过程性证据**：老板问「为什么这个月转化率掉了」，答案在回访记录里（是异议集中在价格？还是首次接触后就没再跟进？）。塞进主表只能留最后一次，过程全丢。

2. **为什么 `overdue_days` 要落库而不是实时算？** 回访逾期统计是咨询师考核的日指标（`OVERDUE_WARN_DAYS` 默认 3 天）。若实时算，`now() - planned_at` 是每行都不同的表达式，无法建索引，也无法在部分索引里做范围筛选。落库后，定时任务每晚刷新，`idx_m11_consult_followup_overdue` 可以直接按 `overdue_days DESC` 取最该打的电话，查询 < 5ms。

3. **为什么约束 `ck_m11_consult_followup_no_fake_up` 要禁止「未接通却标记意向提升」？** 这是**防止绩效造假**的硬约束。咨询师的奖金与「意向提升数」直接挂钩，若无此约束，可以给每个未接通的电话都标「意向 UP」刷数据。约束在数据库层拦截，配合 `ck_m11_consult_followup_connected`（已接通必须有 ≥10 字内容摘要），让回访记录具备可审计性。

4. **为什么 `objection_code` 单独一列而不是混进 `content_summary` 自由文本？** 异议分布是**最具商业价值的数据**：若 `PRICE` 占 45%，说明定价或分期方案有问题；若 `FEAR` 占 30%，说明术前宣教素材不够。结构化编码才能聚合统计（`idx_m11_consult_followup_objection` 支持按异议类型分布），自由文本做不到。

5. **为什么 `material_sent` 用 JSONB 数组？** 一次回访可能发送多个素材（价格表 + 手术视频 + 案例），且素材清单会随营销活动变化，无法预定义列。JSONB 数组表达「本次发了哪些」最自然，且可加 GIN 索引支持「发过 SMILE 视频的咨询转化率是多少」这类分析。

**设计说明：**

1. **为什么渠道、话术、素材三种记录共用一张表？** 三者的字段结构高度相似（编码、名称、状态、生效期、适用术式、排序、版本），差异只有 6~8 个专属字段。拆成三张表会产生三套几乎相同的 CRUD 代码、三个下拉接口、三份权限配置。用 `record_type` 区分是**用少量稀疏列换取实现简单**——这与 M10-01 视功能竖表相反，因为那里字段完全不通用，这里大部分通用。约束 `ck_m11_consult_channel_*_required` 保证每种类型的专属字段齐全。

2. **为什么话术要存 `forbidden_words` 与 `compliance_flag`？** 屈光科普与营销受《医疗广告管理办法》约束：禁止承诺疗效（「治好」「100% 安全」）、禁止用患者形象作疗效证明。若不在系统中管控，咨询师自由发挥极易触碰红线，轻则被举报罚款，重则停业整改。`BLOCKED` 状态下约束强制不可启用，从系统层面封死违规话术的使用路径。

3. **为什么渠道成本字段都带 `_snap` 且要标明 `cost_source`？** 与主表金额字段同一原则：M11 **不算钱**。渠道投放成本的真值在 M16 的广告结算模块，M11 只做展示与粗略 ROI 估算。`cost_source` 区分数据可信度：`M16_AD`（有结算单，最可靠）> `MANUAL`（人工录入）> `ESTIMATE`（拍脑袋估算）。做渠道效果分析时必须能区分这三类，否则会把估算值当真实成本，得出错误的关停决策。

4. **为什么 `applicable_refractive_types` 是数组而不是单个术式？** 一句「术式怎么选」的科普话术通常同时适用 SMILE 与 FS-LASIK（都是无瓣/有瓣的激光类），一个价格表素材适合全部激光类。用数组 + GIN 索引，可以精确回答「给这位想做 ICL 的患者推荐哪些素材」。

**设计说明：**

1. **为什么漏斗计数用「累计进入某状态」而不是「当日处于某状态」？** 咨询旅程跨天（建单 → 3 天后到检 → 7 天后方案 → 14 天后手术）。若按「当日处于某状态」统计，一条 14 天的咨询会在 14 天里被 14 个日期计入，漏斗各层之和远超实际咨询数，转化率被稀释成无意义的小数。按「当日进入某状态」统计（`converted_at` 落在当日即计 1），漏斗是**流量口径**，各层可纵向相加，转化率才有意义。

2. **为什么要有 `ALL` 汇总行与按渠道明细行的双份冗余？** 看板有两种读法：「本月共 1,842 条咨询，转化 187 条（10.2%）」与「抖音 620 条转化 42 条（6.8%）、转介绍 180 条转化 61 条（33.9%）」。只存明细行则汇总要 `GROUP BY`；只存汇总行则渠道对比要实时聚合。两份冗余让查询永远是单行或单组，存储成本约 2 倍（年行数从 540 变 1,080），换来的是看板秒开。

3. **为什么用 `COALESCE(dept_id, 0)` 表达式唯一索引？** `dept_id` 允许 NULL（跨科室的全院汇总行）。PostgreSQL 中 `NULL` 互不相等，普通唯一约束无法阻止「同一天同一咨询师两行 `dept_id` 为 NULL」。`COALESCE(dept_id, 0)` 把 NULL 归一为 0（0 不是合法科室 ID），这是 PG 15 以下 `NULLS NOT DISTINCT` 的兼容写法。

4. **为什么 `ck_m11_consult_stat_funnel` 要强制漏斗单调？** 漏斗的自然约束是「后一层不可能多于前一层」：不可能有 20 人做了手术但只有 15 人出过方案。若统计任务有 bug（如重复计数、状态回退未扣减），单调性约束会在写入时就报错，把数据错误暴露在 T+1 的凌晨，而不是等老板看到「转化率 130%」才发现。这是**用约束做数据质量守夜人**。

5. **为什么保留 `calc_version`？** 统计口径会变：`overall_convert_rate` 的分母今天是「当日新建数」，明年可能改为「当日跟进数」。口径一变，历史与当期不可比。存版本号后，报表可标注「2026 年按 v1 口径、2027 年按 v2 口径」，避免用错基数得出错误结论。

**设计要点（设计说明）：**

1. **为什么意向调整（`INTENT_ADJUST`）要单独记一类动作？** 意向等级直接挂钩咨询师绩效与线索优先级。若不单独记，「谁把这条 C 级线索改成 A 级」无法追溯，也无法识别「批量标高意向」的刷数据行为。单独成类动作后，`idx_m11_consult_log_action` 可以按人按天统计意向调整次数，配合主管抽检形成约束。

2. **为什么记录 `from_status` 与 `to_status` 两列而不是只写在 `detail_json` 里？** 状态流转是**漏斗分析的基础事实**。若只在 JSON 里，做「平均从建单到手术多少天」这类分析需要解析 JSON，无法建索引、无法用窗口函数。独立两列后，`(consult_no, created_at)` + 相邻行的 `to_status` 可直接用 `LEAD()` 窗口函数算出各阶段停留时长。

3. **为什么 `PATIENT_VIEW` 也要记？** 咨询单含手机号、微信号、意向与初筛数据，属个人敏感信息。患者通过小程序查看自己的咨询进度是便民功能，但「谁在什么时间访问了谁的咨询记录」属于《个人信息保护法》的审计要求。与 M10-01 同一处理方式。

4. **为什么 `action_result` 要有 `DENIED`？** 咨询数据是销售资源：A 级线索被谁抢走、被谁转走，都是内部敏感事件。越权查看/修改他人线索的尝试必须留痕。`idx_m11_consult_log_failure` 支撑「同一账号 1 小时内 DENIED ≥5 次即告警」的规则。

| 年日志量 | 203,040 条 |

**分区：** **按 `created_at` 月度 RANGE 分区**，预建 36 个月并**预建 DEFAULT 分区兜底**（共享规范 2.6 硬要求）。5 年 101.5 万行、788MB 已接近单表舒适上限；且日志是纯追加、按时间范围查询的模式，分区后热查询（近 90 天）只扫描 3 个分区，从 101.5 万行降到约 10 万行。超过 36 个月的旧分区 DETACH 后可归档到冷存储，比 `DELETE` 快两个数量级。

**设计说明：**

1. **为什么转介绍要独立成表而不是主表加两个字段？** 主表加 `referrer_patient_id` 只能回答「B 是谁介绍来的」，**回答不了「A 一共介绍了多少人、转化几个、该给他多少奖励」**——而这正是转介绍机制能运转的前提。独立成表后，`idx_m11_consult_referral_referrer` 让「A 的介绍业绩」变成一次索引扫描。此外，转介绍关系有独立状态机（登记 → 接触 → 转化 → 奖励），塞进主表会让主表状态机从 11 态膨胀到 16 态。

2. **为什么 `uk_m11_consult_referral_referee` 建在 `referee_phone` 上而不是 `referee_patient_id`？** 因为**归因冲突的典型场景发生在建档之前**：同一个被介绍人可能被两个介绍人分别报了手机号（A 说「我表妹 138xxxx」、B 也说「我朋友 138xxxx」），此时还没有 `patient_id`。用手机号做唯一键能在登记环节就发现冲突，而不是等到建档后才发现。部分索引条件 `is_attributed = TRUE` 保证只约束真正认领的关系。

3. **为什么需要 `attribution_window_days` 与 `conflict_flag`？** 转介绍纠纷是屈光中心的高频内部矛盾：患者 3 月被 A 介绍来咨询但没做，9 月自己看了广告来做手术，A 要求奖励。**没有归因窗口就没有裁决依据**。`attribution_window_days`（默认 90 天）定义了「介绍在多大时间范围内仍算有效」，窗口外的转化不归因。`conflict_flag` + `arbitration_result` 则把「多人争抢同一被介绍人」的裁决过程记录下来，避免口头扯皮。

4. **为什么奖励金额必须由外部返回且带 `reward_ref`？** 与主表金额同一铁律：**M11 不算钱**。奖励金额由 M16（收费抵扣）或 M10-08（会员权益）按各自的规则计算，M11 只存返回值 + 引用号。这样月底财务核对时，每一笔奖励都能追到具体的结算单或权益流水，不会出现「系统说该发 500，财务查不到出处」。

5. **为什么 `referrer_surgery_date` 要单独记？** 这是转介绍动力的关键分析维度：患者术后 1 个月内介绍率最高（体验新鲜），3 个月后快速衰减。有了这个字段，运营可以算出「术后第 N 天的介绍转化率曲线」，从而决定「术后第 7 天发一条引导转介绍的关怀消息」是否值得。若从 `m11_consultation` 反查介绍人的手术日期，需要跨表联查且介绍人可能不是本院手术患者。

1. **为什么年龄下限、角膜厚度下限设为 `is_editable = FALSE`？** 这两条是**临床安全底线**：18 周岁以下眼球发育未稳定，做激光手术可能因眼轴继续增长而快速回退；角膜厚度 < 480μm 切削后剩余基质床不足，有角膜膨隆（ectasia）风险，属严重并发症。设为只读后，即使有配置权限的人也无法为了业绩把门槛调低到 16 岁或 400μm。真要调整必须走代码发布流程，留痕在版本历史里。这与 M10-01 散瞳强制年龄同一处理思路。

2. **为什么散瞳/停戴相关参数是三条独立参数而不是一个 JSON？** 软镜 3 天、RGP 14 天、OK 镜 30 天的差异巨大（10 倍），且各自可能由不同专科调整（视光中心管软镜、OK 镜验配师管 OK 镜）。拆成独立参数后可以按角色分别授权修改，也能按科室覆盖其中某一条。

3. **为什么 `FOLLOWUP_MAX_TIMES` 存在？** 防止过度骚扰。行业经验是超过 8 次无效接触后，患者的好感度转为负值，且投诉风险显著上升。超过阈值后咨询服务把该线索转入「长期唤醒池」（只在有新活动时群发），既控制成本也保护品牌。这是**有商业意义的上限，不是技术限制**。

4. **为什么 `DRAFT_EXPIRE_DAYS`（未跟进线索回收）要存在？** 咨询师会挑线索：A 级先跟，C 级长期躺着。若不回收，`NEW` 状态的死线索会一直挂在某人名下占额度，其他人无法接管。15 天未跟进自动判 `INVALID` 释放线索，是**保证线索公平分配与不浪费营销投放的机制**。

    "PRICE", "DISTANCE", "TIME", "FEAR", "FAMILY",
    "COMPETITOR", "WAIT", "NONE",
]


def _check_quarter(value: Optional[Decimal], field_name: str) -> Optional[Decimal]:
    """校验 0.25D 步进。"""
    if value is None:
        return value
    if (Decimal(str(value)) * 4) != (Decimal(str(value)) * 4).to_integral_value():
        raise ValueError("%s 必须为 0.25D 的整数倍" % field_name)
    return value

**关键查询示例：**

```sql
-- 咨询师今日到期回访（P01 工作台核心查询，走部分索引）
SELECT c.id, c.consult_no, c.patient_name, c.intent_level, c.status,
       c.next_followup_at, c.followup_count
FROM m11_consultation c
WHERE c.consultant_id = :consultant_id
  AND c.status NOT IN ('CONVERTED', 'LOST', 'INVALID')
  AND c.next_followup_at <= NOW()
  AND c.is_deleted = FALSE
ORDER BY c.intent_level ASC, c.next_followup_at ASC
LIMIT 50;

-- 转化漏斗（P05，按渠道分组，走 funnel 索引）
SELECT consult_channel,
       COUNT(*) AS total,
       COUNT(*) FILTER (WHERE status = 'CONTACTING') AS contacted,
       COUNT(*) FILTER (WHERE status IN ('SCREENED','EXAM_BOOKED','EXAM_DONE',
                                          'PLAN_MADE','SURGERY_BOOKED',
                                          'SURGERY_DONE','CONVERTED')) AS screened,
       COUNT(*) FILTER (WHERE status = 'CONVERTED') AS converted
FROM m11_consultation
WHERE org_id = :org_id
  AND created_at >= :date_from
  AND created_at < :date_to
  AND is_deleted = FALSE
GROUP BY consult_channel
ORDER BY converted DESC;
```

### E.3 分区建表脚本（`m11_consult_log`）

```sql
-- 主表按 created_at 月度 RANGE 分区
CREATE TABLE m11_consult_log (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY,
    consultation_id BIGINT NOT NULL,
    consult_no      VARCHAR(32),
    patient_id      BIGINT,
    action          VARCHAR(32) NOT NULL,
    action_result   VARCHAR(16) NOT NULL DEFAULT 'SUCCESS',
    from_status     VARCHAR(24),
    to_status       VARCHAR(24),
    changed_fields  JSONB,
    old_value       JSONB,
    new_value       JSONB,
    detail_json     JSONB,
    operator_id     BIGINT,
    operator_name   VARCHAR(64),
    operator_role   VARCHAR(32),
    operator_ip     VARCHAR(64),
    trace_id        VARCHAR(64),
    request_id      VARCHAR(64),
    remark          VARCHAR(512),
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- DEFAULT 分区兜底（共享规范 2.6 硬要求）
CREATE TABLE IF NOT EXISTS m11_consult_log_pdefault
    PARTITION OF m11_consult_log DEFAULT;

-- 预建 36 个月分区
DO $$
DECLARE
    i INT;
    start_date DATE;
    end_date DATE;
    part_name TEXT;
BEGIN
    FOR i IN 0..35 LOOP
        start_date := (DATE_TRUNC('month', CURRENT_DATE) + (i || ' months')::INTERVAL)::DATE;
        end_date := (start_date + INTERVAL '1 month')::DATE;
        part_name := 'm11_consult_log_p' || TO_CHAR(start_date, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m11_consult_log '
            'FOR VALUES FROM (%L) TO (%L)',
            part_name, start_date, end_date
        );
    END LOOP;
END $$;

-- 分区表上的索引
CREATE INDEX IF NOT EXISTS idx_m11_consult_log_biz
    ON m11_consult_log (consultation_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_m11_consult_log_action
    ON m11_consult_log (action, created_at DESC);
```

**为什么主键是 `(id, created_at)` 而不是 `(id)`：** PostgreSQL 要求分区表的主键必须包含分区键，因此主键改为 `(id, created_at)`。业务查日志用 `consultation_id + created_at`，不依赖主键，因此无影响。与 M05-01、M10-01 的日志表处理一致。
