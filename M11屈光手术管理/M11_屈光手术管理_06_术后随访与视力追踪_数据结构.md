**容量假设：** 二级眼科医院屈光中心日均屈光手术 4.5 台眼（年约 1,600 台眼）；单台眼随访 8 个节点（D1/W1/M1/M3/M6/Y1/Y2 + 平均 0.8 次计划外）产生约 8 条任务（年约 12,800 行）；到访达成率 75%（年约 9,600 次到访）；双眼手术占 85%，视力与角膜按眼拆行后约 13,400 行/年；异常观察登记率 33%（年约 3,200 行）；每次到访平均 2.9 条提醒（年约 28,000 条）；四项指标按 M1/M3/M6/Y1 四个评估节点计算（年约 4,800 条）。

**全局设计约定（本子模块 9 张表共同遵守）：**

| 约定 | 内容 |
|---|---|
| 主键 | `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`（SQLAlchemy `Identity()`） |
| 逻辑删除 | `is_deleted BOOLEAN NOT NULL DEFAULT FALSE`，**禁止物理 DELETE** |
| 乐观锁 | 计划、到访、视力、角膜、观察、指标表带 `version INT NOT NULL DEFAULT 0` |
| 下游状态 | `plan_ref` / `record_ref` 类字段一律为「只读引用其他子模块」，本表只存引号不存业务真值 |
| 枚举 | `VARCHAR(16/24/32)` + `CHECK` 约束，**不用 PostgreSQL ENUM 类型**，中文放附录 B |
| 物理外键 | **不建**（跨模块零外键，模块内也不建），应用层校验 + 每日 03:20 对账任务 |
| 时间 | `TIMESTAMP`（无时区，服务统一 `Asia/Shanghai`）/ `DATE`；`updated_at` 由 `trg_set_updated_at` 维护 |
| 金额 | 本子模块**不产生金额真值**，仅 `fee_*_snap` / `*_ref` 形式的 M16 快照与单号引用 |
| 索引命名 | `pk_` / `uk_` / `idx_` / `ft_`；CHECK 命名 `ck_{表名去前缀}_{语义}` |
| 中文检索 | `pg_trgm` + `GIN (name gin_trgm_ops)`；本模块用于患者姓名与随访备注 |
| 分区 | 仅 `m11_postop_remind` 按 `created_at` 月度 `RANGE` 分区，**带 DEFAULT 分区兜底** |
| 单位 | 屈光度 `NUMERIC(6,2)` 步进 0.25D；角膜厚度 `NUMERIC(6,2)` 单位 μm；眼轴 mm；角膜曲率 D 或 mm 由 `k_unit` 区分 |

**为什么本子模块不建任何物理外键：**

`m11_postop_plan` 持有 `reservation_no`（M11-05）、`plan_no`（M11-04）、`record_no`（M11-03）三类跨子模块引用。不建外键有三条理由：①M11 各子模块由不同团队并行开发，建表顺序耦合会让 M11-05 的发布成为 M11-06 的前置条件；②随访计划的生命周期比手术预约长（随访可跨越 2 年，预约术毕即归档），外键会阻止预约归档；③M11-06 的写入量（日均约 150 行）虽不高，但每日还有定时任务批量更新任务状态，外键检查会累积锁等待。代价是可能出现悬挂引用，由每日 03:20 的 `reconcile_postop_refs` 任务扫描并告警，人工决定是否置 `is_deleted`。

### 4.2 表：`m11_postop_plan`（术后随访计划主表）

**用途：** 术后随访的**主档**。一次屈光手术（一台眼）对应一条随访计划，承载术前基线快照、随访起止日期、计划状态与随访依从性汇总。这张表回答「这个患者哪天做的什么术式、术前什么水平、应该随访多少次、实际来了多少次」。

**写入方：** M11-06 随访服务（由 M11-05 `P-09` 手术完成回调或 M09 事件触发创建）。
**只读方：** M11-07 质量与并发症（计算质量指标的分母）、M11-08 运营分析、M22 报表、M03-04 随访任务调度、M19 患者运营。**M10-09 只读引用诊断与日期，不写本表**。

**设计说明：**

1. **为什么术前基线要整组快照（`preop_ucva_decimal` / `preop_bcva_decimal` / `preop_se` / `preop_thickness`）？**
   有效性、安全性、可预测性三项指标的**分母全部来自术前基线**。M11-02 术前检查数据在患者术毕后可能因设备重传、补录而被修正，如果指标计算时实时去查术前表，同一患者在不同时间算出的有效性会不一致，质控报表就无法比对。快照在计划创建时一次性固化，保证「这台手术的指标永远用同一组术前数据算」。

2. **为什么 `preop_bcva_decimal` 允许为空，但为空时该计划不参与有效性/安全性统计？**
   极少数急症或外院转来的患者，术前没有完整的矫正视力记录（如儿童配合不佳、角膜混浊遮挡）。若强行补 0 会导致分母为 0 或指标失真。数据库层不强制（允许 NULL），指标计算层显式排除并计入 `excluded_count`，让质量报表能说明「有效样本 N / 总样本 M」，而不是悄悄用 0 填坑。

3. **为什么 `eye_side` 允许 `OU`，而 `m11_postop_va` 按眼拆行？**
   双眼同期手术在**计划层**是一个事件（一次进手术室、一次麻醉、一份知情同意），所以计划表用 `OU` 表达并让 `paired_plan_id` 互指；但无论是单眼还是双眼，**视觉结果必须按眼分别记录**（右眼 1.0、左眼 0.8 是常态），因此视力表、角膜表的主键粒度是「到访 × 眼别」。这种「计划粗粒度、结果细粒度」的设计避免了双眼手术拆成两条计划导致的重复随访提醒。

4. **为什么 `target_se_tolerance_050` / `_100` 要做成字段而不是常量？**
   标准可预测性口径是 ±0.50D / ±1.00D，但不同术式与不同目标屈光度的临床可接受范围不同（如 ICL 术后允许的残留散光更宽）。做成字段后可以按术式配置（`m11_postop_node_config` 的默认值带出来），同时又不破坏「同一患者长期口径一致」——已建计划的目标容差不会被后来的配置变更改变。

5. **为什么 `adherence_rate` 与 `completed_task_count` 都要存？**
   `completed_task_count` 是**可重算的原始计数**（由任务表聚合），`adherence_rate` 是**派生比率**。两者都存的理由是：列表页展示比率（避免每次都做除法与聚合），而报表核对时用原始计数重算并比对，一旦发现不一致说明聚合逻辑有 bug，可以在对账任务中告警。这与 M05 住院主档存 `deposit_total` 快照的思路一致。

**设计说明：**

1. **为什么要从计划表拆出任务表，而不是在计划表里存 `jsonb` 节点数组？**
   随访任务需要被**外部系统按到期日批量拉取**（P-12 给 M03-04 与 M19），如果节点是 JSONB 数组，查询「今天到期的随访」必须全表扫并对每个计划展开 JSONB，无法建索引。拆表后 `idx_m11_postop_task_due` 是部分索引，只包含未完成任务（约 20% 的行），P-12 的 P95 ≤ 200ms 才有保障。

2. **为什么 `offset_days` 用固定值并用 CHECK 约束锁死？**
   随访节点的医学定义是固定的（术后 1 天、1 周、1 月、3 月、6 月、1 年、2 年），这是屈光手术疗效评价的标准时间点，不能由运营随意改动。改动会导致不同时期手术的指标无法横向比较。允许调整的是**窗口宽度**（`window_start_date` / `window_end_date`），即在标准节点前后允许多少天到访仍算该节点——这由 `m11_postop_node_config` 配置。

3. **为什么窗口止日要分段配置而不是统一 +30 天？**
   早期节点时效性强：D1 的检查结果反映术后即刻状态，拖到术后第 10 天就失去临床意义，所以窗口是 +2 天；而 Y2（术后 2 年）的随访窗口可以是 ±90 天，患者晚来一个月不影响「2 年稳定性」的判定。统一窗口会导致早期节点判 MISSED 过松、晚期节点过严。

4. **为什么 `is_data_complete` 单独存在，而不是实时算 `completed_items` 是否包含 `required_items`？**
   指标计算是一个**批量任务**（每次到访完成后触发，以及每日对账），如果每次都要解析 JSONB 判断子集关系，14 万行的计算会成为瓶颈。写入时一次性判定并落布尔值，指标计算只需 `WHERE is_data_complete = TRUE`，表达式索引也可直接支持。

**设计说明：**

1. **为什么到访与任务是一对多，而不是一对一？**
   现实中「补访」非常常见：患者因工作原因错过 D1 与 W1，术后第 10 天来一次，这一次检查的数据既反映「术后 1 周的状态」也补上了「术后 1 天」的缺项。如果强行一对一，要么产生两条内容几乎相同的到访记录（浪费且容易冲突），要么丢弃一个节点（依从性统计失真）。用 `covered_nodes` 数组 + `covered_task_count` 表达一对多，任务表每个节点各自回填同一个 `visit_id`。

2. **为什么 `days_after_surgery` 要冗余存储而不是每次用日期相减？**
   视力与屈光度追踪曲线的横轴就是「术后天数」。曲线页会一次拉取同一患者的全部到访，如果每行都做日期减法，跨 2 年、8 次到访的曲线要算 8 次减法（小事），但**统计报表**要按「术后 30±7 天」「术后 90±14 天」分组时，用固定值列可以直接建索引并做范围查询，而 `visit_date - surgery_date` 是表达式索引，跨表（`surgery_date` 在计划表）时无法建。落列后统计查询从全表扫变为索引范围扫。

3. **为什么到访记录要有 `DRAFT` / `SIGNED` 状态与签署人？**
   随访记录具有医疗文书属性。检查数据录入过程中（`DRAFT`）允许修改与补录；医师确认并签署后（`SIGNED`）即成为正式记录，修改必须走「作废 + 重开」而非直接 UPDATE，保证病历可追溯。这也是 `void_reason` 强制 ≥ 10 字的原因——作废是一个需要说明理由的严肃动作。

4. **为什么 `referral_type` / `referral_ref_no` 要在到访上记录分流？**
   术后随访最重要的产出之一是**及时把异常患者转给正确的下游**：Haze 3 级要转并发症管理（M11-07），屈光回退要转再手术评估（M11-04），视力稳定但有残余屈光不正可以转视光配镜（M10）。把分流记录在到访上，一张页面就能回答「这次随访最后怎么处理的」，而不必跨 3 个表拼装。

**设计说明：**

1. **为什么视力要同时存 `ucva_decimal` 与 `ucva_logmar`？**
   小数法（`1.0` / `0.8`）是国内眼科最常用的记录与沟通方式，但**统计上不可直接平均**：0.1、0.2、0.4 三个值的算术平均是 0.233，而它们实际对应的视觉能力差异极大（logMAR 1.0、0.7、0.4 的均值是 0.7）。安全性指标要做「平均视力丢失行数」这类统计，必须用 logMAR（等比刻度、可加减）。因此**录入口径是小数的、统计口径是 logMAR**，两列同时存，由服务层在写入时自动换算，既不增加录入负担，也不让统计失真。

2. **为什么 `se` 要存而不是每次由球柱算？**
   等效球镜是四项指标中三项（可预测性、稳定性、术前基线）的核心变量，几乎所有统计查询都会用到。若每次现算 `sphere + cylinder/2`，GROUP BY 与窗口函数里都要写表达式，且无法建索引。存列后 `se` 可直接参与索引与范围查询；同时用 CHECK 约束 `abs(se - (sphere + cylinder/2)) <= 0.13` 保证列值不被单独篡改（容差 0.13 是因为部分设备按 ±0.12D 精度输出）。

3. **为什么 `is_valid` 与 `is_refraction_complete` 要分开？**
   两个概念不同：`is_valid = FALSE` 表示「这次测量本身不可信」（患者不配合、角膜接触镜遮挡），整行都不该进统计；`is_refraction_complete = TRUE` 才表示「球柱都录了」，才可以算稳定性与可预测性。现实中常见于术后 1 天：视力测了，但验光因为患者畏光只做了电脑验光且球柱只有一个方向，此时 `is_valid = TRUE` 但 `is_refraction_complete = FALSE`。分开后，有效性/安全性统计能包含这类记录，而稳定性/可预测性统计自动排除。

4. **为什么唯一索引带 `is_valid = TRUE`？**
   同一次到访同一只眼，如果第一次测量无效（`is_valid = FALSE`），医师理应能重测并保留两条记录以示区别。若唯一索引不含 `is_valid`，重测会被拒绝或必须物理覆盖，丢失「曾测出不可信数据」的信息。带上条件后，`(visit_id, eye_side)` 下最多一条**有效**记录，无效记录可多条并存，追溯时可看到「第一次没测准，第二次重测」。

**设计说明：**

1. **为什么角膜数据要单独一张表，不并入视力表？**
   两者的**测量节奏与有效性不同**：视力与验光每次到访必测且耗时 1 分钟，角膜地形图与内皮检查耗时 5~10 分钟且部分节点（如 W1）可能因患者时间不足而跳过。若并入一张表，会因角膜列全空而污染视力数据的完整性判断；拆开后视力表的 `is_refraction_complete` 与角膜表各自判断，互不干扰。此外角膜表要多存 25 个列，合并会让视力表的行宽翻倍，而视力表是曲线页高频全量读取的表。

2. **为什么 Haze 要允许 0.5 这种半级？**
   临床上 Haze 用裂隙灯下混浊程度主观分级（Fantes 0~4 级），但不同检查者对「1 级」与「2 级」的判断常落在中间，实践中大量记录为 0.5、1.5、2.5。若数据库只允许整数，检查者会向上或向下取整，导致分级系统性偏移，而 Haze ≥ 2 是启动激素治疗的关键阈值——取整偏差会直接影响用药决策。允许 0.5 步进并配 CHECK 约束（`haze_grade × 2` 为整数）既贴合临床，又防止乱填。

3. **为什么 `residual_stroma` 要存并且要复算校验？**
   术前方案（M11-04）会算出「预计剩余基质床厚度」，术后随访实测角膜厚度与瓣厚度后复算实际值。两者对比能发现**实际切削量与计划不符**——这是欠矫/过矫、角膜膨隆风险的核心线索。用 CHECK 保证 `residual_stroma ≈ central - flap`，防止人工填错。

4. **为什么 `thickness_device` 要记录设备型号？**
   不同角膜测厚设备（如 Pentacam、Aviso、超声测厚）之间存在 ±10μm 的系统性差异。同一患者随访 2 年换了设备，厚度 "变薄 12μm" 可能纯是设备差异，若被误判为基质床变薄就会引发不必要的干预。记录设备型号后，跨设备的厚度对比可标注同质性，质控报表可按设备分层。

**设计说明：**

1. **为什么观察线索不直接写成并发症报告？**
   并发症报告（M11-07 `m11_complication`）有分级上报、不良事件闭环、质控签核等**重流程**，一旦开单就走不完回头路。而随访中大量现象是**未定性的线索**：术后 1 个月 Haze 1.5 级、眼压 24mmHg——这些多数会自行消退，若都开成并发症报告会造成过度上报与流程负担。线索表 `status = 'RESOLVED'` 就结束了；只有达到阈值（Haze ≥ 2 持续 3 个月、眼压 > 25 且用激素）才 `refer_to_complication = TRUE` 转正式报告。

2. **为什么 `measured_value` + `baseline_value` + `delta_value` 三列都要存？**
   单一数值无法判断严重性：「眼压 22mmHg」本身正常，但若比术前 14mmHg 升高 8mmHg 则是激素反应。把数值、基线、差值一起存，P06 页面可直接渲染「术前 14.00 → 本次 22.00（+8.00）」而无需回查历史；且统计「激素性高眼压发生率」时可直接用 `delta_value > 8` 过滤。

3. **为什么重度观察（GRADE_3/4）必须由医师确认？**
   分级决定处置强度（GRADE_3 需要立即干预甚至再次手术），而检查技师虽能操作设备，但没有诊断权。数据库 CHECK 强制 `GRADE_3`/`GRADE_4` 必须有 `confirmed_by` 与 `confirmed_at`，把「技师录入即定级」的越权路径堵死——即便前端被绕过，写库也会失败。

**设计说明：**

1. **为什么要按月分区而不是普通表？**
   本表是**高频写入的低价值明细**（年 2.8 万条，单行仅存发送状态），主要查询永远是「最近 3 个月的提醒」与「某个计划的提醒轨迹」。按月分区后，扫「最近 3 个月」只触达 3 个分区（约 7,000 行），而不是全表 5.6 万行；同时超期数据可直接 `DETACH` 归档，无需批量 DELETE（避免 VACUUM 压力与锁）。带 DEFAULT 分区是为了防止分区预建任务失败导致写入报错——这是分区表最常见的生产事故。

2. **为什么 `notify_target` 存脱敏手机号而不是明文？**
   本表是通知流水，若存明文等于在数据库里多存一份未脱敏的手机号副本（年 2.8 万条），显著扩大泄露面。实际发送时手机号从计划表解密后传给 M03-05，流水只记脱敏值用于证明「发给谁了」。合规审计要求的是「可证明通知行为」，脱敏号码足以满足。

3. **为什么要有 `uk_m11_postop_remind_seq` 唯一索引？**
   提醒由定时任务驱动，最容易出的故障是「同一天发了 5 条一样的短信」——患者投诉骚扰、短信费浪费。`(plan_id, node_code, remind_type, remind_seq)` 唯一索引保证同一计划同一节点的同一次提醒只发一遍，任务重跑也不会重复。序号本身承载业务含义：1 是到期前 3 天提醒、2 是到期当天、3 是逾期 3 天催告。

4. **为什么 `reply_intent` 要单独存枚举而不是只存文本？**
   `CANNOT_COME` 与 `REFUSE` 是**失访的两条主要前兆**，把它们结构化为枚举后，P07 页面可以自动把这些患者排到召回优先级最高，P09 也可统计「回复拒访者中有多少最终失访」，从而量化「识别拒访后立即电话介入」的效果。只存自由文本则永远需要人工读。

**设计说明：**

1. **为什么要把分子分母与排除原因都存下来？**
   四项指标都是**比率**（如有效性 1.20），单看比率无法回答「为什么这个患者没算进去」。质控报表被问到「你这个月有效性 1.15 是算了多少人」时，必须能回到 `efficacy_denominator IS NOT NULL` 的明细。存分子分母后，聚合查询可直接 `SELECT round(avg(efficacy_corrected),3)` 并用 `count(*) FILTER (WHERE efficacy_valid)` 给出有效样本数，排除原因分布也直接可见。只存比率会失去全部可追溯性。

2. **为什么 `stability_interval_days >= 30` 是硬约束？**
   稳定性衡量的是「屈光度是否随时间稳定」，若两次测量间隔只有 5 天（如 M3 计划期 ±2 天窗口内患者连来两次），两次数值接近是因为「本来就是同一次屈光状态」，不是「稳定」。用 30 天最小间隔作为有效样本条件，避免把重复测量当作稳定性证据。这条约束同时保护了「稳定性」这个临床指标的语义。

3. **为什么 `calc_version` 要做成字段？**
   指标口径会随行业共识变化（如安全性从「视力丢失行数」改为「logMAR 变化量」）。如果直接覆盖历史结果，质控报表跨年对比会失真。`calc_version = 'V1'` 与 `'V2'` 并存后，报表可指定版本，也可以专门出「口径切换前后对照」的分析。这是约束语义稳定性的标准做法。

4. **为什么唯一索引含 `calc_version`，而同版本重算要覆盖？**
   同一节点同一眼别在**同一口径下**只应有唯一结果（重算时应 UPDATE 而非新增），但换口径后需要保留旧口径结果以对比。唯一索引 `(plan_id, eye_side, node_code, calc_version)` 恰好表达这一点：同版本只能一条，跨版本可并存。

**设计说明：**

1. **为什么节点偏移写死、窗口可配？**
   节点偏移（D1/W1/M1/M3/M6/Y1/Y2）是**国际公认的屈光手术疗效评价时间点**，任何改动都会让不同时期手术的指标失去可比性，因此数据库 CHECK 锁死。而「患者该在哪几天内来」属于运营弹性：早期节点窗口窄（D1 前后 ±1 天）因为反映即刻状态，晚期节点窗口宽（Y2 ±90 天）因为患者异地工作常见。把可配与不可配分开，是这类配置表的核心设计原则。

2. **为什么 `is_assess_node` 要在配置里，而不是代码里硬编码「M1 及以后」？**
   有两层保护：数据库 CHECK 保证 D1/W1 一定是 FALSE（防止运营误配让 1 天就参与稳定性统计）；而 `is_assess_node` 字段本身让「EXTRA 是否参与评估」可配——计划外随访要不要计入质量指标，不同医院共识不同。硬编码在代码里则每次调整都要发版。

3. **为什么 `effective_from` / `effective_to` 而不直接改配置？**
   随访计划**跨 2 年**。若 2026 年把 Y2 窗口从 ±90 天改成 ±60 天，直接修改会让 2024 年手术患者的 Y2 任务在生成时用新窗口，但他们的 Y1 已用旧窗口完成，同一患者前后口径不一致。用生效日期后，计划创建时按「手术日的配置」加 `version` 快照锁定，历史计划永远按其创建时的配置执行。

4. **为什么 `uk_m11_postop_node_config_default` 要限定同术式同眼别模式只能一个默认？**
   计划生成时必须能**唯一定位**用哪套配置，否则「默认 A 还是默认 B」取决于查询顺序，会出现同一术式的患者随访节点不一致。部分唯一索引 `WHERE is_default = TRUE AND status = 'ENABLED'` 在数据库层杜绝这一歧义；停用旧默认后再启用新默认是安全的操作顺序。

**量级估算：**

| 项目 | 数值 | 说明 |
|---|---|---|
| 配置行数 | 约 40 行 | 5 术式 × 8 节点 |
| 单行平均长度 | 约 600 字节 | 含 JSONB 检查项与告警规则 |
| 表大小 | 约 24 KB | 常量级 |
| 缓存 | 全量缓存 | Redis `m11:postop:nodecfg:{type}` TTL 1 小时 |

**分区：** 不分区（常量级配置表）。理由：数据量极小，且需要全量加载到内存；分区会让「取该术式全部节点」变成跨分区查询，反而变慢。

```python
# ==================== 视力换算工具 ====================

class VisionConverter:
    """视力小数法与 logMAR 的换算。

    logMAR = -log10(小数视力)
    小数 1.0 -> logMAR 0.00；小数 0.1 -> logMAR 1.00；
    小数 0.05 -> logMAR 1.30；小数 2.0 -> logMAR -0.30（超常视力）。
    """

    @staticmethod
    def to_logmar(decimal_va: Optional[float]) -> Optional[float]:
        """小数视力 -> logMAR，保留 3 位小数。

        Args:
            decimal_va: 小数视力（如 0.8）。

        Returns:
            logMAR 值（如 0.097）；入参非法时返回 None。
        """
        if decimal_va is None or decimal_va <= 0:
            return None
        return round(-math.log10(decimal_va), 3)

    @staticmethod
    def to_decimal(logmar: Optional[float]) -> Optional[float]:
        """logMAR -> 小数视力，保留 3 位小数。

        Args:
            logmar: logMAR 值（如 0.097）。

        Returns:
            小数视力（如 0.800）；入参超出范围时返回 None。
        """
        if logmar is None or logmar < -0.30 or logmar > 2.00:
            return None
        return round(10 ** (-logmar), 3)

    @staticmethod
    def lines_between(logmar_from: float, logmar_to: float) -> float:
        """计算两次视力之间的行数差（每 0.1 logMAR 计为 1 行）。

        Args:
            logmar_from: 起始 logMAR（如术前 BCVA）。
            logmar_to: 目标 logMAR（如术后 BCVA）。

        Returns:
            行数差，正数表示视力提升，负数表示视力丢失。
        """
        return round((logmar_from - logmar_to) / 0.1, 2)

    bcva_decimal: Optional[float] = Field(
        None, gt=0, le=2.0, description="最佳矫正视力小数法")
    sphere: Optional[Decimal] = Field(None, description="球镜（D），如 -0.25")
    cylinder: Optional[Decimal] = Field(None, description="柱镜（D），如 -0.50")
    axis: Optional[int] = Field(None, ge=1, le=180, description="轴位（°）")

                                        "CYCLOPLEGIC", "RETINOSCOPY"]] = Field(

    iop_method: Optional[Literal["NCT", "GAT", "ICARE", "OTHER"]] = Field(
        None, description="眼压测量方式")
    pupil_size: Optional[float] = Field(None, ge=1.0, le=12.0, description="瞳孔（mm）")
    is_valid: bool = Field(True, description="测量是否有效")
    invalid_reason: Optional[InvalidReason] = Field(None, description="无效原因")
    want_buffer: Optional[Dict[str, Any]] = Field(None, description="主观问卷")
    remark: Optional[str] = Field(None, max_length=512, description="备注")

    @field_validator("sphere", "cylinder")
    @classmethod
    def validate_power(cls, v: Optional[Decimal]) -> Optional[Decimal]:
        """球柱镜必须 0.25D 步长。"""
        if v is None:
            return v
        if (v * 4) != (v * 4).to_integral_value():
            raise ValueError("球镜与柱镜必须为 0.25D 的整数倍")
        return v

    @model_validator(mode="after")
    def validate_axis(self) -> "PostopVaIn":
        """柱镜为 0 时不可填轴位；柱镜非 0 必须填轴位。"""
        has_cyl = self.cylinder is not None and self.cylinder != 0
        if has_cyl and self.axis is None:
            raise ValueError("柱镜非 0 时必须填写轴位")
        if not has_cyl and self.axis is not None:
            raise ValueError("柱镜为 0 或未填时不可填写轴位")
        return self

    @model_validator(mode="after")
    def validate_invalid(self) -> "PostopVaIn":
        """无效测量必须说明原因。"""
        if not self.is_valid and not self.invalid_reason:
            raise ValueError("测量无效时必须填写无效原因")
        return self

    @model_validator(mode="after")
    def validate_se_sanity(self) -> "PostopVaIn":
        """等效球镜合理性：术后即时极少数超高度残留，超过 ±12D 提示核对。"""
        if self.sphere is None or self.cylinder is None:
            return self
        se = self.sphere + self.cylinder / 2
        if abs(se) > Decimal("12"):
            raise ValueError("等效球镜 %.2fD 超出术后合理范围，请核对录入" % se)
        return self

    def to_row(self) -> Dict[str, Any]:
        """转换为数据库行字典，自动计算 logMAR 与等效球镜。"""
        se = None
        complete = False
        if self.sphere is not None and self.cylinder is not None:
            se = self.sphere + self.cylinder / 2
            complete = True
        return {
            "eye_side": self.eye_side,
            "ucva_decimal": Decimal(str(self.ucva_decimal)),
            "ucva_logmar": (Decimal(str(VisionConverter.to_logmar(self.ucva_decimal)))
                            if VisionConverter.to_logmar(self.ucva_decimal) is not None
                            else None),
            "ucva_method": self.ucva_method,
            "bcva_decimal": (Decimal(str(self.bcva_decimal))
                             if self.bcva_decimal is not None else None),
            "bcva_logmar": (Decimal(str(VisionConverter.to_logmar(self.bcva_decimal)))
                            if self.bcva_decimal is not None else None),
            "sphere": self.sphere,
            "cylinder": self.cylinder,
            "axis": self.axis,
            "se": se,
            "refraction_method": self.refraction_method,
            "iop": (Decimal(str(self.iop)) if self.iop is not None else None),
            "iop_method": self.iop_method,
            "pupil_size": (Decimal(str(self.pupil_size))
                           if self.pupil_size is not None else None),
            "is_valid": self.is_valid,
            "invalid_reason": self.invalid_reason,
            "is_refraction_complete": complete,
            "want_buffer": self.want_buffer,
            "remark": self.remark,
        }
```

### C.2 关键查询示例

```sql
-- 查询 1：P-12 到期随访清单（未来 N 天内到期 + 已逾期，合并排序）
SELECT t.id                                AS task_id,
       t.plan_no,
       p.patient_id,
       p.patient_name,
       p.patient_phone,
       p.surgery_date,
       p.refractive_type,
       p.eye_side,
       t.node_code,
       t.due_date,
       (t.due_date - CURRENT_DATE)          AS days_to_due,
       GREATEST(CURRENT_DATE - t.expire_date, 0) AS overdue_days,
       t.remind_count,
       p.lost_to_followup                   AS is_lost
  FROM m11_postop_task t
  JOIN m11_postop_plan p ON p.id = t.plan_id
 WHERE t.status IN ('PLANNED', 'NOTIFIED')
   AND t.is_deleted = FALSE
   AND p.is_deleted = FALSE
   AND t.due_date <= CURRENT_DATE + (:window_days || ' days')::interval
   AND p.store_id = :store_id
 ORDER BY t.due_date ASC, p.surgery_date ASC
 LIMIT 500;

-- 查询 2：P05 曲线数据（按眼别组装曲线点）
SELECT v.eye_side,
       v.days_after_surgery,
       v.node_code,
       v.ucva_decimal,
       v.ucva_logmar,
       v.bcva_decimal,
       v.se,
       v.sphere,
       v.cylinder,
       v.axis,
       v.is_refraction_complete
  FROM m11_postop_va v
 WHERE v.plan_id = :plan_id
   AND v.is_valid = TRUE
   AND v.is_deleted = FALSE
 ORDER BY v.eye_side, v.days_after_surgery;

-- 查询 3：稳定性计算（相邻两次有效屈光度）
WITH ordered AS (
    SELECT v.plan_id,
           v.eye_side,
           v.days_after_surgery,
           v.se,
           LAG(v.se) OVER (
               PARTITION BY v.plan_id, v.eye_side
               ORDER BY v.days_after_surgery
           ) AS prev_se,
           LAG(v.days_after_surgery) OVER (
               PARTITION BY v.plan_id, v.eye_side
               ORDER BY v.days_after_surgery
           ) AS prev_days
      FROM m11_postop_va v
     WHERE v.plan_id = :plan_id
       AND v.is_valid = TRUE
       AND v.is_refraction_complete = TRUE
       AND v.is_deleted = FALSE
)
SELECT o.eye_side,
       o.days_after_surgery,
       o.se                                AS curr_se,
       o.prev_se,
       abs(o.se - o.prev_se)                AS stability_delta,
       (o.days_after_surgery - o.prev_days) AS interval_days,
       (abs(o.se - o.prev_se) <= 0.50)      AS is_stable
  FROM ordered o
 WHERE o.prev_se IS NOT NULL
 ORDER BY o.eye_side, o.days_after_surgery;

-- 查询 4：可预测性（落点分布，±0.50D / ±1.00D 比例）
SELECT i.node_code,
       count(*)                                                     AS total_valid,
       count(*) FILTER (WHERE i.pred_abs_delta <= 0.50)             AS within_050,
       count(*) FILTER (WHERE i.pred_abs_delta <= 1.00)             AS within_100,
       round(100.0 * count(*) FILTER (WHERE i.pred_abs_delta <= 0.50)
             / NULLIF(count(*), 0), 2)                              AS rate_050_pct,
       round(100.0 * count(*) FILTER (WHERE i.pred_abs_delta <= 1.00)
             / NULLIF(count(*), 0), 2)                              AS rate_100_pct
  FROM m11_postop_indicator i
  JOIN m11_postop_plan p ON p.id = i.plan_id
 WHERE i.pred_valid = TRUE
   AND i.is_deleted = FALSE
   AND p.surgery_date BETWEEN :date_from AND :date_to
 GROUP BY i.node_code
 ORDER BY i.node_code;

-- 查询 5：P09 依从性（按节点分组）
SELECT t.node_code,
       count(*)                                              AS task_total,
       count(*) FILTER (WHERE t.status = 'COMPLETED')        AS completed,
       count(*) FILTER (WHERE t.status = 'MISSED')           AS missed,
       round(100.0 * count(*) FILTER (WHERE t.status = 'COMPLETED')
             / NULLIF(count(*), 0), 2)                       AS adherence_pct
  FROM m11_postop_task t
  JOIN m11_postop_plan p ON p.id = t.plan_id
 WHERE p.surgery_date BETWEEN :date_from AND :date_to
   AND t.is_extra = FALSE
   AND t.is_deleted = FALSE
 GROUP BY t.node_code
 ORDER BY t.node_code;

-- 查询 6：异常观察待处理（P06 清单）
SELECT o.observation_no,
       o.plan_no,
       p.patient_name,
       o.eye_side,
       o.observation_type,
       o.severity_grade,
       o.measured_value,
       o.measured_unit,
       o.days_after_surgery,
       o.next_check_date,
       o.refer_to_complication
  FROM m11_postop_observation o
  JOIN m11_postop_plan p ON p.id = o.plan_id
 WHERE o.status IN ('OPEN', 'OBSERVING')
   AND o.is_deleted = FALSE
 ORDER BY CASE o.severity_grade
              WHEN 'GRADE_4' THEN 1
              WHEN 'GRADE_3' THEN 2
              WHEN 'GRADE_2' THEN 3
              ELSE 4
          END,
          o.days_after_surgery DESC
 LIMIT 200;
```

### E.4 分区预建脚本（APScheduler `ensure_postop_remind_partition`）

```sql
-- 由定时任务每月 25 日执行，预建下月分区
DO $$
DECLARE
    v_next_start DATE := (date_trunc('month', CURRENT_DATE) + INTERVAL '1 month')::date;
    v_next_end   DATE := (date_trunc('month', CURRENT_DATE) + INTERVAL '2 month')::date;
    v_suffix     TEXT := to_char(v_next_start, 'YYYYMM');
BEGIN
    EXECUTE format(
        'CREATE TABLE IF NOT EXISTS m11_postop_remind_%s '
        'PARTITION OF m11_postop_remind FOR VALUES FROM (%L) TO (%L)',
        v_suffix, v_next_start, v_next_end);
    EXECUTE format(
        'CREATE INDEX IF NOT EXISTS idx_m11_postop_remind_%s_plan '
        'ON m11_postop_remind_%s (plan_id, created_at DESC)',
        v_suffix, v_suffix);
    EXECUTE format(
        'CREATE UNIQUE INDEX IF NOT EXISTS uk_m11_postop_remind_%s_seq '
        'ON m11_postop_remind_%s (plan_id, node_code, remind_type, remind_seq) '
        'WHERE is_deleted = FALSE',
        v_suffix, v_suffix);
END $$;
```
