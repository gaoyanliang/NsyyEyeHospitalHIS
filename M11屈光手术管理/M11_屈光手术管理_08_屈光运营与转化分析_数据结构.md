### 三条不可动摇的设计原则

| # | 原则 | 在本文件中的体现 |
|---|---|---|
| **1** | **M11-08 只读，不改任何业务单据** | 本模块 7 张表全部是**派生统计表**，没有一张保存业务状态；对 M11-01~M11-07 只做 `SELECT`，从不 `UPDATE` 它们的表 |
| **2** | **金额真值只在 M16** | 所有金额字段一律带 `_snap` 后缀，来源标注 `M16-01 P-05 收费统计`，且字段说明中写明「M11 不计算金额，仅镜像展示」 |
| **3** | **指标口径必须可配置、可追溯** | 每张快照表都带 `metric_version`，指标口径每次变更版本 +1；历史快照保存当时的口径版本，保证「三个月前的报表数字不会因为今天改了口径而变」 |

**为什么是这 7 张表（「一张表只表达一件事」的拆解）：**

| 表 | 回答的问题 | 若不建这张表会怎样 |
|---|---|---|
| `m11_refractive_stat_metric_def` | 每个指标怎么算（分子/分母/过滤）、口径什么时候改过 | 口径硬编码在 SQL 里，改一次要发版；且三个月前的报表无法解释「当时为什么是这个数」 |
| `m11_refractive_stat_daily` | 今天/本月整体经营怎么样（咨询量、到院、手术、客单价） | 每次看板实时扫 5 张业务表聚合，P95 超过 6 秒 |
| `m11_refractive_stat_funnel` | 咨询→到院→检查→方案→预约→手术→完成，哪一环漏了 | 漏斗需要按 7 个环节 × 9 个渠道 × 术式交叉，实时算不动 |
| `m11_refractive_stat_procedure` | 各术式占比、价格带分布、术式趋势 | 术式分析要 JOIN 方案表、预约表、结算表，且价格带需要分桶 |
| `m11_refractive_stat_doctor` | 每个医师的手术量、转化率、并发症率、满意度 | 医师维度需要跨咨询/方案/预约/随访/并发症 5 张表，实时聚合无法在医生工作站打开时完成 |
| `m11_refractive_stat_channel` | 哪个渠道 ROI 高、哪个渠道流失重 | 渠道效果需要「从最终手术倒推咨询来源」，链路跨 4 张表 |
| `m11_refractive_stat_export` | 谁在什么时候导出了什么报表（含水印与脱敏标记） | 运营报表外泄无法追溯；大报表导出阻塞请求线程 |

### 4.2 表：`m11_refractive_stat_metric_def`（指标口径定义表）

**用途：** 定义每个运营指标「怎么算」。这是本子模块的**口径唯一权威源**：所有快照表的计算都读本表，而不是把公式散落在代码里。

**写入方：** M11-08 运营（P08 指标口径配置页）。**只读方：** 本模块全部统计作业与报表、M22（质控与决策支持，按需读取口径）。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |
| metric_code | VARCHAR(48) | N | — | 指标编码 `RA{类别2位}{序号3位}`，如 `RA01001`（咨询类）、`RA03002`（术式类） |
| metric_name | VARCHAR(128) | N | — | 指标名称，如「咨询到院转化率」 |
| metric_category | VARCHAR(24) | N | — | 指标类别 `CONSULT` 咨询 / `FUNNEL` 漏斗 / `PROCEDURE` 术式 / `DOCTOR` 医师 / `CHANNEL` 渠道 / `REVENUE` 收入 / `QUALITY` 质量 |
| **口径组** | | | | |
| numerator_expr | VARCHAR(512) | N | — | **分子口径**（可读表达式），如 `COUNT(DISTINCT c.consult_no) FILTER (WHERE c.arrive_flag = TRUE)` |
| denominator_expr | VARCHAR(512) | Y | NULL | **分母口径**；比率型指标必填，总量型指标为空 |
| filter_condition | VARCHAR(1024) | Y | NULL | **过滤条件**，如 `c.trade_status <> 'INVALID' AND c.consult_date BETWEEN :start AND :end` |
| source_tables | VARCHAR(512) | N | — | 数据来源表（逗号分隔），如 `m11_consult,m11_preop_exam` |
| calc_formula | VARCHAR(256) | Y | NULL | 计算公式描述，如 `numerator / denominator * 100` |
| unit | VARCHAR(16) | N | `'CNT'` | 单位 `CNT` 个 / `RATE_PCT` 百分比 / `MONEY_SNAP` 金额快照 / `SCORE` 评分 / `DAYS` 天 |
| **粒度与刷新组** | | | | |
| stat_granularity | VARCHAR(24) | N | `'DAY'` | 统计粒度 `DAY` 日 / `WEEK` 周 / `MONTH` 月 / `QUARTER` 季；多粒度用逗号分隔 |
| refresh_freq | VARCHAR(24) | N | `'DAILY'` | 刷新频率 `REALTIME` 实时 / `HOURLY` 每小时 / `DAILY` 每日 03:30 / `WEEKLY` 每周一 / `MONTHLY` 每月 1 日 |
| refresh_delay_hours | SMALLINT | N | 6 | 数据延迟容忍小时数（业务表补录后多久重算） |
| **异常处理组** | | | | |
| zero_denominator_policy | VARCHAR(24) | N | `'NULL'` | 分母为 0 的处理 `NULL` 返回空（前端显示 —） / `ZERO` 返回 0 / `SKIP` 不输出该行 |
| missing_data_policy | VARCHAR(24) | N | `'MARK'` | 数据缺失处理 `MARK` 标记 `is_partial` / `ZERO` 按 0 / `CARRY` 沿用上期值 |
| **版本与治理组** | | | | |
| metric_version | INT | N | 1 | **口径版本号**，口径变更时 +1；快照表记录本版本 |
| effective_from | DATE | N | CURRENT_DATE | 本版本生效起始日 |
| effective_to | DATE | Y | NULL | 本版本失效日（被新版本替代时写入） |
| is_current | BOOLEAN | N | TRUE | 是否当前生效版本 |
| change_reason | VARCHAR(512) | Y | NULL | 口径变更原因（版本 >1 时必填） |
| approval_no | VARCHAR(64) | Y | NULL | 口径变更审批单号（M20 审批） |
| is_enabled | BOOLEAN | N | TRUE | 是否启用计算 |
| sort_no | INT | N | 999 | 展示排序 |
| remark | VARCHAR(512) | Y | NULL | 备注 |
| **标准字段** | | | | |
| created_by | BIGINT | Y | NULL | 创建人 |
| created_at | TIMESTAMP | N | CURRENT_TIMESTAMP | 创建时间 |
| updated_by | BIGINT | Y | NULL | 更新人 |
| updated_at | TIMESTAMP | N | CURRENT_TIMESTAMP | 更新时间（触发器维护） |
| is_deleted | BOOLEAN | N | FALSE | 逻辑删除 |

**索引：**

```sql
CREATE UNIQUE INDEX uk_m11_stat_metric_code_ver
    ON m11_refractive_stat_metric_def (metric_code, metric_version)
    WHERE is_deleted = FALSE;

CREATE UNIQUE INDEX uk_m11_stat_metric_current
    ON m11_refractive_stat_metric_def (metric_code)
    WHERE is_current = TRUE AND is_deleted = FALSE;

CREATE INDEX idx_m11_stat_metric_category
    ON m11_refractive_stat_metric_def (metric_category, sort_no)
    WHERE is_enabled = TRUE AND is_deleted = FALSE;
```

**约束：**

```sql

COMMENT ON COLUMN m11_refractive_stat_metric_def.numerator_expr
    IS '分子口径可读表达式；实际执行由 MetricCalculator 按表达式的 DSL 解析，禁止直接拼 SQL 字符串';
COMMENT ON COLUMN m11_refractive_stat_metric_def.metric_version
    IS '口径版本号；口径变更时 +1，历史快照保留旧版本以支持报表可复现';
COMMENT ON COLUMN m11_refractive_stat_metric_def.zero_denominator_policy
    IS '分母为 0 处理：NULL 返回空（前端显示 —）/ ZERO 返回 0 / SKIP 不输出该行';

**设计说明：**

1. **为什么口径要落到表里而不是代码里？** 运营口径一年会改 3~5 次（例如「咨询量」从「建单数」改成「有效建单数，剔除无效与重复」）。若写死在代码里，每次调整都要发版；落在表里后运营在 P08 自助修改，**下一次统计作业即刻生效**。
2. **为什么要 `metric_version` 且不允许改历史行？** 因为报表需要「可复现」。2026 年 8 月的月报数字在 11 月口径调整后不应变化，否则财务对不上账。做法是：口径变更 = 旧版本 `is_current = FALSE` + 写 `effective_to` + 插入新版本行；快照表的 `metric_version` 记录当时用的版本，报表按版本号回读口径说明。
3. **为什么 `numerator_expr` 是「表达式」而不是「自然语言」？** 纯自然语言无法执行，纯 SQL 又会带来注入与跨表耦合。折中方案是用受控 DSL（`COUNT` / `COUNT_DISTINCT` / `SUM` / `AVG` / `FILTER` / `RATIO` 六类算子 + 字段白名单），由 `MetricCalculator` 解析后生成参数化 SQL，**不做字符串拼接**。

**量级估算：** 配置类表，约 60 行（7 类指标 × 平均 9 个），单行约 900 字节，总计约 54 KB。**不分区。**

**为什么分区键选 `stat_date` 而不是 `created_at`？** 统计表的查询永远是「按业务日期区间取数」（看板查今天、月报查本月、导出查区间），分区键与查询条件一致才能裁剪。若用 `created_at`（写入时间），补算历史日期时数据会落到「今天」的分区，查 8 月数据反而跨全部分区扫描——这与业务语义完全相反。

**设计说明：**

1. **为什么术式拆分之和必须等于手术总数？** 这是口径一致性的硬约束。若两者不等，说明统计 SQL 有 bug（例如某术式漏映射成 `other_surgery_cnt`）。用 CHECK 约束在数据库层阻断，比事后对账发现更早。
2. **为什么金额字段要三个（`revenue_snap` / `revenue_refund_snap` / `revenue_net_snap`）而不是两个？** 因为净收入必须**由 M16 计算并下传**，不能由 M11 做减法。若 M11 自己减，退费跨期（8 月退 7 月的费）时口径会与财务系统不一致。三个字段都是 M16 返回的原值，M11 只存不算。
3. **为什么有 `data_source` 维度？** 屈光中心常同时运营门诊渠道与线上渠道，两者的转化特征差异极大（线上渠道咨询量大但转化率低）。同一 `dept_id` 下按来源分开，才能回答「线上投放到底有没有赚」。

**量级估算：**

| 项目 | 数值 | 说明 |
|---|---|---|
| 日行数 | 约 12 行 | 3 个来源 × 3 个科室 + 3 个全院汇总行 |
| 年行数 | 约 4,380 行 | — |
| 15 年总量 | 约 65,700 行 | 按年分区，每年约 4,400 行 |
| 单行平均长度 | 约 620 字节 | 30 个数值字段 |
| 表大小（15 年） | 约 41 MB | — |

**分区：** 年度 RANGE（`stat_date`），预建 5 年 + DEFAULT 兜底，保留 15 年后 `DETACH` 归档。

### 4.4 表：`m11_refractive_stat_funnel`（咨询转化漏斗表）

**用途：** 记录**七环节转化漏斗**的每个切片的每一层计数与转化率，支撑 P02 咨询转化分析与 P05 渠道分析。

**写入方：** 统计作业（每日 03:30）。**只读方：** P02、P05、P07、M22。

**为什么单独建表而不是从 `_stat_daily` 推算：** 漏斗需要「渠道 × 术式」的交叉切片（9 个渠道 × 4 类术式 = 36 个组合/日），daily 表只有「科室 × 来源」3×3 的粒度，无法下钻到渠道。若在查询时实时算交叉，需要把 4 张业务表按 7 个环节 JOIN 后 group by 36 组，P95 超过 3 秒。

| id | BIGINT | N | IDENTITY | 主键 |
| stat_no | VARCHAR(32) | N | — | 快照号 `RN` + YYYYMMDD + 5 位 |
| stat_date | DATE | N | — | 统计日期（分区键来源） |
| dept_id | BIGINT | N | 0 | 科室/院区 ID（`0` 为全院） |

**设计说明：**

1. **为什么漏斗第 7 环节是「完成」而不是「手术」？** 因为运营真正关心的是「咨询了 100 人，最终有多少人完成了整个治疗闭环（手术后做完首次随访）」。手术做完但随访不来，等于效果无法验证，客诉风险高。把「完成」定义为「术后首次随访已执行」，比「手术完成」更贴近经营目标。
2. **为什么 `channel` 与 `refractive_type` 都允许 `'ALL'`？** 避免建立 2^N 个汇总行组合。`ALL` 表示该维度不拆分，统计作业对「渠道合计」「术式合计」「全合计」分别写入，查询时直接命中而不是现场 `ROLLUP`。
3. **为什么漏斗单调性要用 CHECK 约束？** 漏斗的每一层是前一层的子集，若出现「到院 > 咨询」说明统计 SQL 有 bug（例如咨询按天过滤、到院按整单过滤，时间窗错位）。CHECK 约束在写入时就拒绝，比在看板上看到一个不可能的漏斗更早发现问题。

### 4.5 表：`m11_refractive_stat_procedure`（术式与价格带分析表）

**设计说明：**

1. **为什么价格带必须可配置而不是写死六档？** 屈光手术价格随集采与促销波动明显。2026 年 SMILE 主流价位在 15,000~18,000 元，两年后可能降到 12,000 元。写死分桶后，原本的「高档」会变成「中档」，历史对比失真。`M11.STAT.PRICE_BAND_EDGES` 允许运营调整边界，`band_version` 记录版本。
2. **为什么 `PB_UNKNOWN` 单独一档？** M16 金额快照可能失败（结算尚未生成、退费中、数据延迟）。若把这类行归入 `PB1`（最低档），会严重低估客单价。单独一档并在 P03 页面显著提示「N 例金额未同步」，让运营知道数字是「部分口径」。
3. **为什么 `revenue_share` 不算「算钱」？** 这是对**M16 已给出的快照值**求占比，属于比率展示，不产生任何新的金额真值，也没有写入任何新增金额字段。铁律约束的是「M11 不得计算应收/实收/退款金额」，占比统计不在此列（口径说明见详细设计 §3.4）。

           AND major_complication_cnt <= complication_cnt
           AND reoperation_cnt <= surgery_cnt);

-- 满意度评分区间 0~5

    ADD CONSTRAINT ck_m11_stat_doctor_score

    CHECK (rank_no IS NULL OR rank_no >= 1);

    CHECK (is_partial = FALSE OR partial_reason IS NOT NULL);

    IS '满意度评分（0~5 分），来源 M22 问卷汇总；NULL 表示当日无回访样本，不写 0';
COMMENT ON COLUMN m11_refractive_stat_doctor.personal_cvr
    IS '个人转化率 = 归属本人咨询中完成手术数 / 归属本人咨询量 × 100；分母为 0 时为 NULL';
COMMENT ON COLUMN m11_refractive_stat_doctor.complication_rate
    IS '并发症率 = 并发症例数 / 本人手术量 × 100；分级口径见 M11-07 并发症分级';
COMMENT ON COLUMN m11_refractive_stat_doctor.avg_ticket_snap
    IS '客单价快照，来源 M16；M11 不做除法，分母为 0 时由 M16 返回 NULL';
```

**设计说明：**

1. **为什么按「日期 × 医师 × 术式」而不是只按「日期 × 医师」？** 因为医师的术式能力分布差异极大：有的医师只做 SMILE，有的专做 ICL。只统计总量无法回答「张主任的 ICL 并发症率是不是高于同侪」。三个维度后，P04 可下钻到「医师 × 术式」对比。
2. **为什么满意度要带 `satisfaction_sample_cnt`？** 因为评分是均值，样本量为 1 的 5 分和样本量为 50 的 4.8 分可信度完全不同。P04 页面会对样本量 <5 的医师标注「样本不足」，避免用单例好评做绩效结论。
3. **为什么 `consult_owned_cnt`（归属本人咨询）要单独存？** 因为「咨询师」与「手术医师」常不是同一人。若用全科咨询量作分母，手术量大的医师转化率会被系统性低估。本表按「咨询单归属人 = 医师本人」口径统计，P04 页面明确标注该口径，避免误读。

**量级估算：**

| 项目 | 数值 | 说明 |
|---|---|---|
| 日行数 | 约 60 行 | 5 位医师 × (10 术式 + ALL) ≈ 55；加科室汇总约 60 |
| 年行数 | 约 21,900 行 | — |
| 15 年总量 | 约 33 万行 | — |
| 单行平均长度 | 约 700 字节 | — |
| 表大小（15 年） | 约 231 MB | — |

**分区：** 不分区（15 年 33 万行，查询均带 `stat_date` 区间与 `doctor_id`，复合索引可覆盖）。

    IS '单客成本参考值 = 成本快照 / 手术量；成本为空时为 NULL';
COMMENT ON COLUMN m11_refractive_stat_channel.channel_category
    IS '渠道大类：OFFLINE 线下 / ONLINE 线上 / REFERRAL 转介，用于大盘分组';
```

**设计说明：**

1. **为什么 `roi_ref` / `cpa_ref` 带 `_ref` 后缀而不是 `_snap`？** `_snap` 表示「M16 原值镜像」，`_ref` 表示「参考比率」。ROI 与 CPA 是本模块对**两个 M16 快照值**求商得到的展示指标，不是金额真值，因此用 `_ref` 并明确标注「仅做比率，不重算金额」。
2. **为什么 `cost_snap` 允许 NULL 而不是 0？** 转介绍（`REFERRAL`）渠道没有投放成本，线下自然到店（`OFFLINE`）也可能没有单独核算成本。若写 0，ROI 计算会除以 0；若写 NULL，报表显示「无成本数据」，语义准确。约束 `ck_m11_stat_channel_cost_pair` 保证成本值与来源标记成对出现。
3. **为什么 `channel_category` 要冗余存储？** 因为 P05 的大盘需要按「线上 / 线下 / 转介」三组汇总。若不冗余，每次分组都要 `CASE WHEN channel IN (...)` 映射，且映射规则一变历史报表口径就跟着变。冗余存储后，分组规则固化在数据里。

-- 粒度枚举
ALTER TABLE m11_refractive_stat_export
    ADD CONSTRAINT ck_m11_stat_export_granularity
    CHECK (granularity IN ('DAY', 'WEEK', 'MONTH', 'QUARTER'));

-- 日期区间正向
ALTER TABLE m11_refractive_stat_export
    ADD CONSTRAINT ck_m11_stat_export_range
    CHECK (date_to >= date_from);

-- 进度区间
ALTER TABLE m11_refractive_stat_export

    CHECK (progress >= 0 AND progress <= 100);

ALTER TABLE m11_refractive_stat_export
    ADD CONSTRAINT ck_m11_stat_export_count
    CHECK (row_cnt >= 0 AND download_cnt >= 0 AND retry_count >= 0);

-- 成功必须有文件与行数
ALTER TABLE m11_refractive_stat_export
    ADD CONSTRAINT ck_m11_stat_export_success
    CHECK (status <> 'SUCCESS'
           OR (file_url IS NOT NULL AND file_name IS NOT NULL
               AND file_sha256 IS NOT NULL AND finished_at IS NOT NULL));

-- 失败必须说明原因
ALTER TABLE m11_refractive_stat_export
    ADD CONSTRAINT ck_m11_stat_export_failed
    CHECK (status <> 'FAILED'
           OR (fail_reason IS NOT NULL AND char_length(btrim(fail_reason)) >= 4));

-- 成功任务必须挂水印（防外泄）
ALTER TABLE m11_refractive_stat_export
    ADD CONSTRAINT ck_m11_stat_export_watermark
    CHECK (status <> 'SUCCESS'
           OR (watermark_text IS NOT NULL AND watermark_hash IS NOT NULL));

-- filter_json 必须是对象
ALTER TABLE m11_refractive_stat_export
    ADD CONSTRAINT ck_m11_stat_export_filter
    CHECK (jsonb_typeof(filter_json) = 'object');

-- 失效时间必须晚于请求时间
ALTER TABLE m11_refractive_stat_export
    ADD CONSTRAINT ck_m11_stat_export_expire
    CHECK (expire_at > requested_at);

-- SHA-256 格式
ALTER TABLE m11_refractive_stat_export
    ADD CONSTRAINT ck_m11_stat_export_sha
    CHECK (file_sha256 IS NULL OR file_sha256 ~ '^[0-9a-f]{64}$');

COMMENT ON TABLE m11_refractive_stat_export
    IS '报表导出任务表：导出留痕、脱敏标记、水印校验与文件生命周期管理';

    IS '筛选条件快照 JSONB；配合 metric_version 保证导出文件可复现';

    IS '水印文案，含操作人、时间、导出单号；成功导出必须有水印（ck_m11_stat_export_watermark）';

    IS '文件 SHA-256，用于下载时完整性校验与篡改追溯';
COMMENT ON COLUMN m11_refractive_stat_export.expire_at
    IS '文件失效时间，默认 7 天后对象存储签名失效；到期由作业置 status=EXPIRED';
```

**设计说明：**

1. **为什么导出要建独立表而不是写日志文件？** 因为运营报表包含患者姓名、手术量、收入等敏感经营数据，外泄是重大合规风险。独立表可以回答三个审计问题：谁导出的、导出了什么范围、文件有没有被篡改（`file_sha256`）。仅写日志无法关联文件生命周期。
2. **为什么 `filter_json` 存 JSONB 而不是拆字段？** 报表类型不同，筛选维度差异大（漏斗报表需要 `channel`，医师业绩需要 `doctor_id`，趋势报表需要 `granularity`）。拆成宽表会有大量 NULL 列；JSONB 配合 GIN 索引可支持「查所有导出过线上渠道报表的人」这类审计查询。
3. **为什么 `expire_at` 是 NOT NULL 且必须晚于 `requested_at`？** 报表文件永不失效意味着对象存储无限增长且敏感数据永久可访问。强制设置失效期（默认 7 天）后，过期文件由 `job_m11_stat_export_expire` 清理签名并置 `EXPIRED`。

**量级估算：**

| 项目 | 数值 | 说明 |
|---|---|---|
| 年导出次数 | 约 3,600 次 | 日均 10 次（运营主管、财务、院领导） |
| 5 年总量 | 约 18,000 行 | 保留 5 年（文件本身 7 天失效） |
| 单行平均长度 | 约 1,200 字节 | 含 JSONB 筛选条件 |
| 表大小（5 年） | 约 21 MB | — |

**分区：** 不分区（5 年 1.8 万行）。文件本体存对象存储，表只存元数据。

**ORM 模型要点说明：**

| # | 要点 | 说明 |
|---|---|---|
| 1 | `DeclarativeBase` + `Mapped[]` | 全量采用 SQLAlchemy 2.0 声明式风格，与共享规范 §2.1 一致 |
| 2 | 分区表主键含分区键 | `M11RefractiveStatDaily` 与 `M11RefractiveStatFunnel` 的 `stat_date` 同时声明 `primary_key=True`，对应 PostgreSQL「分区表主键必须含分区键」 |
| 3 | `postgresql_partition_by` | 两张分区表在 `__table_args__` 中声明分区策略，Alembic 建表时自动带 `PARTITION BY RANGE` |
| 4 | 无 `ForeignKey` | 全模块零物理外键（共享规范 §2.6），引用关系由注释标注来源表 |
| 5 | 金额字段全部 nullable 或默认 0 | `revenue_snap` 等默认 `Decimal("0")`；比率型 `avg_ticket_snap` 可空以表达「无数据」 |
| 6 | `Numeric(14, 4)` | 与共享规范 §2.4「金额 `NUMERIC(14,4)`」一致；比率用 `NUMERIC(7,4)` |
| 7 | 校验约束全部落到 `CheckConstraint` | 23 类业务约束在 ORM 层同步声明，Alembic 自动生成 DDL |

**Schema 设计要点：**

| # | 要点 | 说明 |
|---|---|---|
| 1 | 金额字段类型为 `float` 输出 | ORM 层是 `Decimal`，API 层转 `float` 便于前端渲染；字段名强制保留 `_snap` / `_ref` 后缀，一眼可辨「非 M11 计算」 |
| 2 | 比率为 `Optional[float]` | 分母为 0 时返回 `null`，前端显示 `—`，**绝不用 0 代替**（0% 与「无数据」语义完全不同） |
| 3 | `MetricDefUpdateIn.change_reason` 必填且 ≥10 字 | 口径变更是不可逆决策，必须写清原因；配合 `approval_no` 形成审批链 |
| 4 | `ExportCreateIn` 强制 `masked = True` | 运营报表含患者与经营敏感数据，**不支持关闭脱敏**；`field_validator` 在入口拦截 |
| 5 | `StatQueryIn` 校验区间 ≤5 年 | 防止一次查询拉全量历史导致数据库压力 |
| 6 | `DashboardOut.data_freshness` | 显式返回各数据来源最后同步时间，让运营判断数字是否为「截至到点」 |
| 7 | `FunnelStageOut.lost_cnt` / `lost_rate` | 每环节都带流失数与流失率，避免前端自行计算导致口径不一致 |

### C.2 核心查询 SQL

**① P01 看板：取指定日期与科室的汇总行**

```sql
SELECT stat_date, dept_id, data_source,
       consult_cnt, valid_consult_cnt, arrive_cnt, preop_exam_cnt,
       plan_cnt, reservation_cnt, surgery_cnt,
       overall_cvr, revenue_snap, avg_ticket_snap,
       is_partial, partial_reason, calc_at
FROM m11_refractive_stat_daily
WHERE stat_date = :stat_date
  AND dept_id = :dept_id
  AND data_source = 'ALL';
```

**② P01 看板：近 12 期趋势（按月汇总）**

```sql
SELECT date_trunc('month', stat_date)::date AS period_start,
       SUM(consult_cnt) AS consult_cnt,
       SUM(surgery_cnt) AS surgery_cnt,
       ROUND(SUM(surgery_cnt)::numeric * 100
             / NULLIF(SUM(valid_consult_cnt), 0), 2) AS overall_cvr,
       SUM(revenue_snap) AS revenue_snap
FROM m11_refractive_stat_daily
WHERE stat_date >= :month_start_11_back
  AND stat_date <= :month_end
  AND dept_id = :dept_id
  AND data_source = 'ALL'
GROUP BY date_trunc('month', stat_date)
ORDER BY period_start;
```

**③ P02 漏斗：按期取渠道维度七环节**

```sql
SELECT channel,
       SUM(stage_consult_cnt) AS consult_cnt,
       SUM(stage_arrive_cnt)  AS arrive_cnt,
       SUM(stage_exam_cnt)    AS exam_cnt,
       SUM(stage_plan_cnt)    AS plan_cnt,
       SUM(stage_book_cnt)    AS book_cnt,
       SUM(stage_surgery_cnt) AS surgery_cnt,
       SUM(stage_done_cnt)    AS done_cnt,
       MAX(lost_stage)        AS lost_stage
FROM m11_refractive_stat_funnel
WHERE stat_date BETWEEN :date_from AND :date_to
  AND dept_id = :dept_id
  AND refractive_type = 'ALL'
  AND channel <> 'ALL'
GROUP BY channel
ORDER BY consult_cnt DESC;
```

**④ P03 术式占比：取术式合计行**

```sql
SELECT refractive_type,
       SUM(surgery_cnt)   AS surgery_cnt,
       SUM(bilateral_cnt) AS bilateral_cnt,
       SUM(revenue_snap)  AS revenue_snap,
       ROUND(SUM(surgery_cnt)::numeric * 100
             / NULLIF(SUM(SUM(surgery_cnt)) OVER (), 0), 2) AS share_rate
FROM m11_refractive_stat_procedure
WHERE stat_date BETWEEN :date_from AND :date_to
  AND dept_id = :dept_id
  AND price_band = 'ALL'
GROUP BY refractive_type
ORDER BY surgery_cnt DESC;
```

**⑤ P04 医师业绩：按期取医师排行**

```sql
SELECT doctor_id, doctor_name, doctor_title,
       SUM(surgery_cnt)        AS surgery_cnt,
       SUM(complication_cnt)   AS complication_cnt,
       ROUND(SUM(complication_cnt)::numeric * 100
             / NULLIF(SUM(surgery_cnt), 0), 2) AS complication_rate,
       ROUND(AVG(satisfaction_score), 2) AS satisfaction_score,
       SUM(satisfaction_sample_cnt)      AS satisfaction_sample_cnt,
       SUM(revenue_snap)       AS revenue_snap
FROM m11_refractive_stat_doctor
WHERE stat_date BETWEEN :date_from AND :date_to
  AND dept_id = :dept_id
  AND refractive_type = 'ALL'
GROUP BY doctor_id, doctor_name, doctor_title
HAVING SUM(surgery_cnt) > 0
ORDER BY surgery_cnt DESC, complication_rate ASC;
```

**⑥ P05 渠道效率：按期取渠道排行与 ROI 参考**

```sql
SELECT channel, channel_name, channel_category,
       SUM(consult_cnt)  AS consult_cnt,
       SUM(arrive_cnt)   AS arrive_cnt,
       SUM(surgery_cnt)  AS surgery_cnt,
       ROUND(SUM(arrive_cnt)::numeric * 100
             / NULLIF(SUM(valid_consult_cnt), 0), 2) AS arrive_rate,
       SUM(revenue_snap) AS revenue_snap,
       SUM(cost_snap)    AS cost_snap,
       ROUND(SUM(revenue_snap) / NULLIF(SUM(cost_snap), 0), 2) AS roi_ref
FROM m11_refractive_stat_channel
WHERE stat_date BETWEEN :date_from AND :date_to
  AND dept_id = :dept_id
GROUP BY channel, channel_name, channel_category
ORDER BY surgery_cnt DESC;
```

**⑦ 口径版本回读：某指标历史全部版本**

```sql
SELECT metric_code, metric_name, metric_version, numerator_expr,
       denominator_expr, filter_condition, effective_from, effective_to,
       is_current, change_reason
FROM m11_refractive_stat_metric_def
WHERE metric_code = :metric_code
  AND is_deleted = FALSE
ORDER BY metric_version DESC;
```

**⑧ 数据新鲜度检查：找出最近 N 天仍为 PARTIAL 的快照**

### E.4 年度分区预建作业

```python
"""m11_008_010 年度分区预建作业（APScheduler 每年 12 月 1 日执行）。"""

import re

from sqlalchemy import text


PARTITION_TABLES = (
    "m11_refractive_stat_daily",
    "m11_refractive_stat_funnel",
)

PARTITION_SAFE_RE = re.compile(r"^m11_refractive_stat_(daily|funnel)$")


async def job_m11_stat_partition_ensure(conn, years_ahead: int = 2) -> dict:
    """预建未来 N 年的年度分区，已存在则跳过。

    表名来自白名单常量，且再次正则校验，杜绝 SQL 注入。
    """
    created = []
    for table in PARTITION_TABLES:
        if not PARTITION_SAFE_RE.match(table):
            raise ValueError("非法分区表名：%s" % table)
        for year in range(2026, 2026 + years_ahead + 1):
            part = "%s_p%d" % (table, year)
            ddl = (
                "CREATE TABLE IF NOT EXISTS {part} "
                "PARTITION OF {tbl} "
                "FOR VALUES FROM ('{y}-01-01') TO ('{n}-01-01')"
            ).format(part=part, tbl=table, y=year, n=year + 1)
            await conn.execute(text(ddl))
            created.append(part)
    return {"ensured": created}
```
