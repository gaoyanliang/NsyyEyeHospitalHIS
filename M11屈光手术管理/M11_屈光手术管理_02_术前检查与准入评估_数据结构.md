**为什么是这 9 张表：**

| 表 | 存在的必要性 |
|---|---|
| `m11_preop_exam` | 「一次术前检查」的业务主档，`exam_no` 是对 M06/M09 提供 P-10 契约的业务主键 |
| `m11_preop_exam_item` | 检查项执行状态来自 M12（检查系统），但「本单要求做哪些项、做到哪一步、异常标记」必须由 M11 记录，否则无法计算完成度与准入前置条件 |
| `m11_preop_package` | 不同术式的必备检查项不同（ICL 必须查前房深度与内皮，SMILE 必须查角膜地形图），套餐化后开单 ≤ 10 秒 |
| `m11_preop_cornea_topo` | 角膜地形图是屈光手术准入的第一道闸门（圆锥角膜筛查），参数多（K 值、散光、e 值、SimK、最薄点）且必须按眼别与测量设备存 |
| `m11_preop_cornea_bio` | 角膜厚度决定能否手术与剩余基质床（RSB）计算，内皮细胞密度决定 ICL 能否植入；两者都是「一测一值」，独立于地形图设备 |
| `m11_preop_refraction` | 屈光度是手术切削量的输入，且必须同时保存主觉验光、散瞳验光与眼轴（儿童/高度近视评估），与 M10 验光单是两个口径 |
| `m11_preop_contraindication` | 准入判定是**可多次发生**的动作（HOLD 补检后再判定），且必须冻结「当时命中了哪些规则、M01-07 授权结果如何」，只用主表一个字段无法追溯 |
| `m11_preop_report` | 打印与签发给患者的汇总报告是一次性快照，必须与后续补检/改判解耦 |
| `m11_preop_log` | 医疗追溯要求：准入判定、参数修改、报告签发必须 100% 留痕且不可改 |

### 4.2 表：`m11_preop_exam`（术前检查单主表）

| 当前状态 | 动作 | 目标状态 | 触发方 | 前置条件 |
|---|---|---|---|---|
| —（无） | 开单 | `DRAFT` | M11-02 P02 / P03 | 患者存在；目标术式在 M01-07 存在 |
| `DRAFT` | 预约检查 | `SCHEDULED` | M11-02 P03 | 检查项齐全；生成 `exam_no`；推 M12 |
| `SCHEDULED` | 开始检查 | `IN_PROGRESS` | M11-02 P04 | 患者到检 |
| `IN_PROGRESS` | 全部完成无异常 | `COMPLETED` | M11-02 P08 | 必查项全部 `DONE`/`NOT_APPLICABLE`；异常项数 = 0 |
| `IN_PROGRESS` | 全部完成有异常 | `ABNORMAL` | M11-02 P08 | 必查项全部完成；异常项数 > 0 |

**设计说明：**

1. **为什么 `exam_no` 草稿为空？** 与全仓 `m05_admission`、`m10_prescription` 一致：草稿不占用号段。若草稿即发号，日均约 24 份检查单中约 18% 会被改期或作废，号段出现大量空洞，前台按单号核对时难以判断「QJ...0007 去哪了」。约束 `ck_m11_preop_exam_no_required` 保证非草稿必有号。

2. **为什么 `admission_result` 在主表冗余一份？** 准入结论的权威记录在 `m11_preop_contraindication`（可多次判定，含规则命中快照）。主表冗余「最新结论 + 时间 + 医师 + 有效期」是为了：①P02 列表 200 行不需要 JOIN；②M06/M09 调 P-10 时先读主表即知有无有效结论，避免每次都聚合子表；③`idx_m11_preop_exam_valid` 部分索引可让「有效 PASS 清单」查询从扫 6 万行降到扫约 900 行。冗余由 Service 在同一事务内回写，并每日对账（附录 E.4）。

3. **为什么 `completion_rate` 落库而不是实时算？** 检查完成度是 P01 工作台和 P09 统计的高频指标（每分钟刷新）。实时算需要 `COUNT(*) FILTER` 聚合 9.6 万行明细。落库后由明细写操作回写，并把一致性交给 `ck_m11_preop_exam_item_counts` 与每日对账任务，读取成本从聚合降为单点。

4. **为什么 `patient_name` / `gender` / `age` / `id_card_no` 要快照？** 医疗记录要求还原「当时」的信息。患者 2027 年改姓名后，2026 年的术前检查单必须仍显示原姓名，否则准入判定依据与病历核对不上。同时快照避免列表每次调 M03。

5. **为什么 `target_refractive_type` 与 `target_operation_code` 同时存在？** `operation_code` 是 M01-07 的具体术式主数据编码（如 `OP_SMILE_001`），`refractive_type` 是 10 类术式枚举（与 M01-07 3.1.4 一字不差）。前者用于调 `auth/check` 与 `full-config`，后者用于统计与准入规则匹配（不同术式的禁忌阈值不同）。两者都存，避免为了统计去 M01 反查。

6. **为什么 `valid_until` 独立于 `admission_at`？** 准入结论有有效期（默认 90 天）。若患者在 89 天后才来手术，角膜状态可能已变化（如干眼加重、近视进展）。有效期独立成列后，`idx_m11_preop_exam_valid` 可快速筛出「PASS 但已过期」的检查单，M06 排台前查 P-10 时能明确返回 `is_expired=true`。

7. **为什么不建物理外键？** ①`patient_id` / `doctor_id` / `package_id` 分别指向 M03、M01-02、本模块其他文件定义的表，跨 schema 外键不可用；②检查单是中等写入表（日均 16 条 INSERT + 约 60 条 UPDATE），外键检查增加写放大；③一致性由应用层校验 + 每日 04:00 的 `reconcile_preop_refs` 对账保证。**代价**：可能出现悬挂引用（包被停用但检查单仍引用），对账任务告警并保留快照字段兜底。

8. **为什么 `is_deleted` 而非物理删除？** 术前检查数据是医疗证据（《病历书写基本规范》要求保存期限不少于 15 年）。作废用 `status='CANCELLED'` 表达，`is_deleted` 只用于「误建且从未执行的空单」，且数据库账号不授予 `DELETE` 权限。

**设计说明：**

1. **为什么检查项要单独成表，而不是在 `m11_preop_exam` 里放一个 `items_json`？** ①完成度、异常项数、关键项缺失都需要按项聚合与筛选（`WHERE item_status='PENDING' AND is_required=TRUE`），JSONB 无法高效索引；②每一行都要与 M12 检查任务一对一绑定（`m12_task_id`），JSONB 无法表达这种引用关系；③P09 统计要按 `item_code` 分组算「地形图完成率、内皮完成率」，独立行才能建 `idx_m11_preop_item_code`。

2. **为什么 `item_status` 有 7 个值，而不是简单的「未做/已做」？** 真实流程里有三种「没做」：`PENDING`（还没安排）、`SCHEDULED`（已推 M12 等患者）、`NOT_APPLICABLE`（医生判定本术式不需要，如 SMILE 不需要查前房深度）。若合并成「未做」，准入判定无法区分「漏检」与「合理省略」，会大量误报 `HOLD`。

3. **为什么 `is_key_item` 单独标记？** 关键项（角膜地形图、角膜厚度、内皮细胞、屈光度、眼压）异常需要立即 `ABNORMAL` 并影响准入；非关键项（如血常规）异常可以 `HOLD` 补查但不阻断术式选择。用布尔位标记比用编码前缀判断更明确，且可配置。

4. **为什么保存 `m12_task_status` 快照？** M12 是检查执行系统，其任务状态会变（WAITING → EXAMINING → REPORTED）。M11 保留最近一次快照，使 P03 执行跟踪页不需要对 18 个检查项各调一次 M12。快照由事件订阅与「刷新按钮」两个入口更新，允许短时间不一致，但每天 05:00 全量对账。

5. **为什么 `NOT_APPLICABLE` 需要原因且 ≥ 10 字？** 这是准入审计的关键证据。若某个必查项被标记为不适用，必须有临床依据（如「患者已在外院完成 OCT 且报告在病历内」）。少于 10 字通常是敷衍填写，无法支撑事后追溯。

**设计说明：**

1. **为什么 `item_list` 用 JSONB 而不是子表？** 套餐项是「整体读取、整体套用」的数据：开单时一次性取出 12~18 项，从不按套餐项做独立筛选或统计（统计对象是 `m11_preop_exam_item` 的实际执行项）。用 JSONB 省去一张表的 CRUD 与两次 JOIN；同时 `is_required` / `is_key_item` / `source_module` 的语义可以在不改表结构的情况下扩展。

2. **为什么 `version_tag` 要快照到检查单？** 套餐会随共识更新（如 2023 年后新增「角膜生物力学」项）。若不快照，一张 2026 年的检查单在 2028 年回看时会显示「按当前套餐应有 18 项，实际只做了 15 项」，误判为漏检。开单时快照 `required_item_count` 与 `package_name` 后，历史口径固定。

3. **为什么 `for_retreatment` 是独立字段而不是塞进 `applicable_types`？** 再手术（二次切削）患者对剩余基质床（RSB）与角膜厚度要求更严，套餐必须额外包含「既往手术记录与地形图对比」。用独立枚举表达比在术式字符串里拼标志位更清晰，也便于 P03 配置页做三态筛选。

4. **为什么允许同一术式多个套餐？** 现实中有「标准套餐」与「精简套餐（快通道）」并存：高度近视患者需要更多项（含眼底、眼轴），低度患者可精简。`is_default` 标记默认项，其余供医师按需选择。

**设计说明：**

1. **为什么角膜厚度在 `m11_preop_cornea_topo` 与 `m11_preop_cornea_bio` 各有一份？** 地形图设备（Pentacam）自带的「最薄点厚度」是**形态学定位值**（带 XY 坐标，用于判断是否偏心），而超声测厚/角膜测厚仪给出的中央厚度是**点对点测量值**（用于中心切削计算）。两者测量原理不同，数值可能相差 5μm~15μm。合并会让 M11-04 无法判断该用哪个值算剩余基质床（RSB）。

2. **为什么 `k_unit` 要区分 D 与 MM？** 国产地形图设备常输出曲率半径（mm，如 `7.80mm`），进口设备输出屈光度（D，如 `43.25D`）。二者换算为 `D = 337.5 / mm`。若统一强制换算成 D，会引入换算误差并使原始记录不可追溯。保留原始单位与原始数值，由计算器按 `k_unit` 换算，是医疗数据的正确做法。

3. **为什么 `forme_fruste_flag` 与 `topo_type` 并存？** `topo_type` 是图形学分类（正常/规则散光/不规则散光/可疑圆锥/圆锥角膜），`forme_fruste_flag` 是**筛查级联开关**：只要 TKC 指数、后表面高度差、最薄点偏心任一越界，即使图形看起来规则也置 TRUE，触发「禁止 SMILE，改评估 ICL/CXL」的准入规则。临床上大量早期圆锥角膜图形「看起来正常」但指数异常，这个布尔位就是捕捉它们的手段。

4. **为什么判读要 `interpretation_sign_hash`？** 地形图判读是准入判定的关键依据。若事后有人修改判读意见（如把「可疑圆锥」改成「正常」）以放行手术，签名摘要能检测到篡改：P-10 返回时携带 `sign_hash`，M09 术前核对与质控审计可重算比对。

5. **为什么 `image_urls` 存 JSONB 数组？** 标准的地形图输出是 4 图（轴向曲率、切向曲率、厚度图、前表面高度图），有时还有 8 图模式。图数量不固定且只整体读取，用数组比 8 个固定列更合适；图片本体存对象存储，表内只存 URL。

**设计说明：**

1. **为什么厚度一律用 μm 且不做 mm 换算？** 眼科临床与设备输出统一使用微米（超声测厚仪直接输出 `520`，Pentacam 输出 `520μm`）。若入库为 mm（`0.52`），则：①`NUMERIC(6,2)` 只有 2 位小数，`0.52` 无法表达 `0.515`；②与 M01-07 手术主数据的厚度阈值（也以 μm 表达）比对时需要来回换算，每次换算都引入舍入误差；③医生看单时要心算换算，容易出错。全仓统一 μm 后，`500μm` 这个阈值在任何模块都是同一个整数比较。

2. **为什么中央厚度与最薄点厚度都要存？** 中心切削（SMILE/FS-LASIK）以**中央厚度**为基准计算 RSB；而圆锥角膜筛查与偏心切削判断以**最薄点**为准。二者可能相差 10μm~30μm，且最薄点常位于下方（`is_thinnest_inferior`）。只存一个会导致：①RSB 计算偏乐观（用最薄点，切削过深）；②或筛查漏诊（用中央厚度，忽略下方变薄）。

3. **为什么内皮细胞要存 CV 与六角形比率，而不只存密度？** 密度正常（如 2600）但 CV 高达 45%、六角形仅 35% 的内皮，提示早期功能失代偿风险。仅看密度会漏掉这类高风险患者（ICL 植入后可能出现角膜水肿）。这三个指标共同构成「内皮健康度」判断。

4. **为什么前房参数放在这张表而不是地形图表？** 前房深度、白到白、晶状体厚度由 Scheimpflug/OCT 生物测量获得，与角膜厚度/内皮同属「生物测量」范畴，且 ICL 准入判定需要它们与 ECD 一起读。放同表后，P-10 返回 ICL 准入评估只需一次查询。

5. **为什么 `predicted_rsb_available` 只是「参考提示」？** 剩余基质床的计算必须结合拟切削深度（取决于屈光度、光学区、术式），这属于 M11-04 手术方案的职责。本表只给出「角膜厚度减去通用保留阈值」的粗算值，用于在检查阶段就提示「角膜偏薄，可能不适合 SMILE」。分工清晰可避免两个模块算法不一致。

**设计说明：**

1. **为什么与 M10 验光单并存，而不是直接引用？** M10 验光单回答「给患者配什么眼镜」，其处方会刻意欠矫（如散瞳后递减 0.25D）以免过矫不适；而屈光手术必须按**足矫的真实屈光**切削，且需要「主觉 / 散瞳 / 试戴接受」多个阶段的值来对比。直接引用 M10 处方会导致切削量偏少、术后欠矫。本表以 `measure_stage` 明确区分阶段，`source_type='M10_OPTOMETRY'` 仅在需要引用时使用，并保留 `m10_optometry_no` 便于追溯。

2. **为什么必须存 `is_cycloplegic` 与用药？** 屈光手术对屈光度的准确性要求远高于配镜：未散瞳的主觉验光在年轻患者身上可受调节影响 0.50D~1.50D，直接导致切削过矫。保存散瞳标记、用药种类与时间，可让 M11-04 判断「这份屈光数据是否可信」，并在儿童与初次配镜者身上强制要求散瞳。

3. **为什么眼轴与眼压放在屈光表里？** 三者由同一台生物测量设备（IOL Master / Lenstar）一次测量输出，且都服务于「屈光手术评估」这一个目的：眼轴判断近视性质（轴性/屈光性）与回退风险，眼压排除青光眼禁忌。合并成一张表可避免为「同一次测量的三个结果」建三张表。

4. **为什么 `sphere_equivalent` 落库？** 与 M10-02 同理：屈光进展判断（术后回退「-0.50D/年」）统一用球镜等效口径。落库后 `ck_m11_preop_refr_se` 可校验一致性，且跨 10 年 12 万行历史数据口径固定，不会因公式调整而漂移。

5. **为什么 `ck_m11_preop_refr_va_order` 要求裸眼视力不优于矫正视力 + 0.30？** 这是数据异常拦截：裸眼视力显著优于矫正视力，几乎必然是录错（如把 `0.10` 录成 `1.00`）或做了其他检查。屈光手术的切削量依赖屈光度与视力的关联，异常数据会直接传导到手术方案。

**设计说明：**

1. **为什么准入是独立表而不是主表上的几个字段？** 真实的判定过程是「初判 HOLD（缺内皮数据）→ 补检 → 再判 PASS」，或「初判 PASS → 30 天后患者来手术前发现干眼加重 → 重判 REJECT」。一张检查单可对应 2~4 次判定，必须完整留痕：①术前核对时能证明「术日看到的是哪次判定」；②质控要统计「按规则拒绝的比例」「越权放行例数」；③纠纷时能还原当时的每一条依据。

2. **为什么把 M01-07 授权结果完整落库（含 `auth_response_snap`）？** 医师授权是**动态的**：医师的授权术式与等级会因考核、暂停执业、休假而变。若只存一个布尔值，事后无法解释「为什么当时允许这位医师做 SMILE」。存完整返回快照后，可追溯到「授权有效期、授权术式清单、手术分级限制」。

3. **为什么 `ck_m11_preop_adm_pass_both` 要写到数据库？** 这是本子模块最核心的合规约束：`PASS` 必须同时满足「授权通过」与「禁忌通过」。把它下沉到 CHECK 约束，即使有运维脚本或数据修复绕过 Service 层，也无法写入一个只凭单条链路放行的 `PASS`。这对应共享规范 §17 常见坑第 12 条。

4. **为什么 `rule_hits` 用 JSONB？** 规则命中是快照数据（判定后永不修改），且需要按规则编码检索（`@>` 查询走 `jsonb_path_ops` GIN）。若拆子表，10 年 7,000 次判定 × 平均 2.1 条命中 ≈ 1.5 万行，每行仅 10 个小字段，管理成本远高于收益；而「按规则统计拒绝原因」用 GIN 已可在毫秒级完成。

5. **为什么 `hold_items` 单独存？** `HOLD` 的价值在于给出「补齐这些项就能重判」的行动清单。存成结构化 JSONB 数组（含 `item_code` 与 `reason`）后，P03 执行跟踪页可直接生成「待补检查单」，不需要 NLP 解析 `result_reason` 文本。

6. **为什么 `valid_until` 只在 `PASS` 时必填？** 只有「可以手术」这个结论需要有效期（角膜状态会变化）；`REJECT` 是长期禁忌（如自身免疫病），`HOLD` 是中间态，都不设有效期。

**设计说明：**

1. **为什么报告要快照而不是每次现拼？** 报告打印件是给患者带走的医疗文书。若每次现拼，则 2027 年补打 2026 年的报告时，会因为检查项字典更新、医师改判、地形图复采而显示与原件不同的内容，这在医疗纠纷中是致命问题。存 `report_json` 快照后，补打与原件的字节级内容一致（仅打印时间不同）。

2. **为什么 `admission_no` 要绑定？** 一张检查单可能有多次判定（HOLD → PASS）。签发报告时必须明确「这份报告对应哪一次判定」，否则患者在 30 天后拿到的 ACK 报告可能与最新判定不符。绑定后，P-10 与报告可交叉验证。

3. **为什么 `uk_m11_preop_report_exam_type` 是「同单同类型唯一」且排除 `VOID`？** 一次检查的术前汇总报告应该只有一份有效件；作废后可重新签发（作废件保留，满足全文留痕要求）。

4. **为什么 `conclusion_text` 与 `advice_text` 分开？** 结论是「检查看到了什么」（客观判断），建议是「下一步做什么」（临床决策）。两者性质不同：结论要进 M11-03 屈光档案的术前基线，建议用于 M11-01 咨询回访话术。分开存储便于各自被下游引用。

**设计说明：**

1. **为什么 `target_table` + `target_id` 而不用多张日志表？** 术前检查涉及 7 类对象的变更（检查单、检查项、地形图、生物测量、屈光、判定、报告）。若每类一张日志表，P02 详情页要 UNION 7 张表才能画出完整时间轴。用单表 + 多态引用，一次查询按 `exam_id, created_at` 即可还原全流程。

2. **为什么日志表要按月分区？** 日均约 330 行、年约 12 万行、10 年 120 万行，是所有表里增长最快的。分区后：①`DROP`/`DETACH` 过期分区比 `DELETE` 快两个数量级且不产生大量 WAL；②按 `exam_id + created_at` 查询时分区裁剪可把扫描范围缩到几个月。

3. **为什么 `reason` 在 `ADMISSION_JUDGED` 时也要求 ≥ 10 字？** 准入判定是医疗决策，日志里的原因字段是「为什么这么判」的最短证据链。即使判定表已有 `judge_note`，日志侧保留一份可防「判定表被修改而日志不改」的对照。

4. **为什么保留 `before_snapshot` / `after_snapshot` 两个 JSONB？** 医疗数据更正的举证需要「原来是什么、改成了什么」。只存 `changed_fields` 无法回答「从 520μm 改成 480μm 还是 500μm」。快照只存关键字段（不是全行），把单行控制在 1KB 内。

**量级估算：**

| 项目 | 数值 | 说明 |
|---|---|---|
| 年行数 | 120,000 行 | 日均约 330 行 |
| 10 年总量 | 1,200,000 行 | — |
| 单行平均长度 | 约 700 字节 | 含两个快照 |
| 表大小（10 年） | 约 840 MB | 含 TOAST |
| 索引大小（10 年） | 约 430 MB | 7 个索引 |
| 日均写入 | 330 INSERT | 无 UPDATE |

**分区：** 按 `created_at` 月度 `RANGE` 分区，预建 3 个月，保留 24 个月热数据，冷数据归档至对象存储。分区 DDL 与维护任务见附录 E.3；分区建表用 `PARTITION OF ... FOR VALUES FROM (...) TO (...)`，并通过 `DEFAULT` 分区兜底未预建的月份，避免写入失败。

        if not self.required_item_count:

        rate = (Decimal(self.completed_item_count) * Decimal(100)

                   is_retreatment: bool) -> bool:
        """判断套餐是否适用于本次检查。"""
        if self.status != "ENABLED" or self.is_deleted:
            return False
        types = [t.strip() for t in self.applicable_types.split(",") if t.strip()]
        if refractive_type not in types:
            return False
        if age is not None:
            if self.age_min is not None and age < self.age_min:
                return False
            if self.age_max is not None and age > self.age_max:
                return False
        if self.for_retreatment == "ONLY" and not is_retreatment:
            return False
        if self.for_retreatment == "EXCLUDE" and is_retreatment:
            return False
        return True

        """球镜等效 = 球镜 + 柱镜 / 2，ROUND_HALF_UP 到 0.01。"""
        from decimal import ROUND_HALF_UP
        raw = Decimal(str(self.sphere)) + Decimal(str(self.cylinder)) / Decimal(2)
        return raw.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)

    @property
    def rx_text(self) -> str:
        """处方表述文本，如「OD -4.25D -0.75D 180°」。"""
        parts = [self.eye_side, "%+.2fD" % float(self.sphere)]
        if self.cylinder and float(self.cylinder) != 0:
            parts.append("%.2fD" % float(self.cylinder))
            parts.append("%d°" % (self.axis or 0))
        return " ".join(parts)

    """球镜/柱镜必须为 0.25 的整数倍。"""

| # | 约定 | 说明 |
|---|---|---|
| 1 | 表结构变更**以本文档为准** | 详细设计文档第 4 章仅为指引块，不承载字段定义 |
| 2 | 变更需同步更新汇总文档 | 新增/删除表须同步 `M11_屈光手术管理_数据结构设计汇总.md` 的表清单与规模统计 |
