**全局设计约定（本子模块 8 张表共同遵守）：**

| 约定 | 内容 |
|---|---|
| 主键 | `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`（SQLAlchemy `Identity()`） |
| 逻辑删除 | 仅 `m11_quality_event`、`m11_quality_retreatment` 带 `is_deleted BOOLEAN NOT NULL DEFAULT FALSE`；**主档与更正流水不带该列，从结构上杜绝删除** |
| 乐观锁 | 事件、申请、计算批次带 `version INT NOT NULL DEFAULT 0` |
| 枚举 | `VARCHAR(16/24/32)` + `CHECK` 约束，**不用 PostgreSQL ENUM 类型**，中文放附录 B |
| 物理外键 | **不建**（跨模块零外键，模块内也不建），应用层校验 + 每日 03:20 对账任务 |
| 时间 | `TIMESTAMP`（无时区，服务统一 `Asia/Shanghai`）/ `DATE`；`updated_at` 由 `trg_set_updated_at` 维护 |
| 金额 | 本子模块**不产生金额真值**，仅 `compensation_amount_snap` 形式的 M16 快照 |
| 索引命名 | `pk_` / `uk_` / `idx_` / `ft_`；CHECK 命名 `ck_{表名去前缀}_{语义}` |
| 中文检索 | `pg_trgm` + `GIN (name gin_trgm_ops)`；本模块用于患者姓名检索 |
| 分区 | 8 张表均不分区（单表最大 51 万行/10 年，未达分区阈值） |
| 单位 | 屈光度 `NUMERIC(6,2)` 步进 0.25D；角膜厚度 `NUMERIC(6,2)` 单位 μm；指标值 `NUMERIC(8,4)` |

**为什么主档与更正流水不带 `is_deleted`：**

共享规范 §2.6 要求所有表带 `is_deleted`。本子模块的两张并发症表**故意不带**，理由是医疗安全记录的性质不同：一旦有了「可逻辑删除」的字段，就总有人会去置 `TRUE`；而并发症登记是医疗事实的原始凭证，删除它等于篡改病历。去掉该列后，「删除」在表结构层面就无法表达，只能通过更正流水修改其业务取值。这一偏离已在附录 F 的文档维护约定中登记。

**索引设计：**

```sql
CREATE UNIQUE INDEX uk_m11_compl_no ON m11_complication_ledger (complication_no);

-- 列表主查询：按发现日期倒序 + 等级筛选
CREATE INDEX idx_m11_compl_found ON m11_complication_ledger (found_date DESC, eye_side);

-- 等级筛选（GRADE_3/4 是重点关注对象，用部分索引）
CREATE INDEX idx_m11_compl_grade ON m11_complication_ledger (grade, found_date DESC)
    WHERE grade IN ('GRADE_3', 'GRADE_4');

-- 按患者查并发症史
CREATE INDEX idx_m11_compl_patient ON m11_complication_ledger (patient_id, found_date DESC);

-- 按医师聚合（医师质量对比与考核）
CREATE INDEX idx_m11_compl_doctor ON m11_complication_ledger (doctor_id, found_date DESC);

-- 按术式聚合（术式维度指标）
```

**设计说明：**

1. **为什么这张表没有 `is_deleted`、`version`、`updated_at`？**
   这三个字段的存在本身就是「这行会被改」的暗示。本表是医疗安全原始凭证，删改它等价于篡改病历。去掉这些列后，「删除」与「原地修改」在表结构层面无法表达，只剩下 INSERT 一条路径。代价是查询当前值时必须 JOIN 更正流水（约 2,000 行，可忽略），收益是审计链完整不可辩驳。

2. **为什么 `grade` 存的是「首次登记等级」而不是「当前等级」？**
   两者语义不同且都需要保留。首次等级是医师当时的临床判断（质量分析的原始输入），当前等级是经复核修正后的结论（对外呈现与统计的口径）。若只存一个字段，要么丢失临床原始判断，要么丢失复核修正。本表存首次值，当前值由 4.3 回放，同时把「首次与最终差多少」变成一个可统计的质量指标——`grade_overridden` 与 amend 数量正是用来度量登记质量的。

3. **为什么 `system_suggested_grade` 与 `grade_overridden` 要落库？**
   它们的用途不是当下决策，而是长期校准：若某医师的判定与系统建议偏离率长期 > 30%，说明要么算法需要调，要么该医师的分级尺度需要统一。这两个字段让「分级标准是否被一致执行」从主观讨论变成可量化事实。

4. **为什么 `symptoms` 与 `disposition_measures` 用 JSONB 而不是关联子表？**
   两者都是短小的枚举多选（7 项 / 8 项），且永远作为整体读取，不存在「按单个症状跨病例统计」的高频需求。用 JSONB 省去两张子表与两次 JOIN；若未来需要按症状聚合，`jsonb_array_elements_text` 配合 GIN 索引也能支撑。这与「一张表只表达一件事」并不冲突——症状是并发症这一个事实的属性，不是独立实体。

5. **为什么 `eye_side` 不允许 `OU`？**
   指标计算、并发症率统计、医师考核全部按「眼」为最小单位。若允许 `OU` 存成一条，同一患者双眼计数会变成 1，导致分母偏差。强制在应用层拆两条并用 `peer_complication_no` 互指，既有正确的「眼」粒度，又保留双眼关联语义。

```sql
-- 当前有效视图：主档 + amend 按 seq 升序回放
CREATE OR REPLACE VIEW v_m11_complication_current AS
WITH last_amend AS (
    SELECT DISTINCT ON (complication_no, field_name)
           complication_no, field_name, new_value
    FROM m11_complication_amend
    WHERE action = 'AMEND'
    ORDER BY complication_no, field_name, amend_seq DESC
)
SELECT l.complication_no,
       l.reservation_no,
       l.plan_no,
       l.patient_id,
       l.eye_side,
       l.refractive_type,
       l.surgery_date,
       l.doctor_id,
       l.found_date,
       l.registered_at,
       l.grade AS original_grade,
       COALESCE(g.new_value, l.grade)                  AS current_grade,
       COALESCE(t.new_value, l.complication_type)      AS current_type,
       COALESCE(cs.new_value, 'OPEN')                  AS clinical_status,
       COALESCE(rs.new_value, 'PENDING')               AS report_status,
       COALESCE(fd.new_value, l.found_date::text)      AS current_found_date
FROM m11_complication_ledger l
LEFT JOIN last_amend g  ON g.complication_no = l.complication_no
                       AND g.field_name = 'complication_grade'
LEFT JOIN last_amend t  ON t.complication_no = l.complication_no
                       AND t.field_name = 'complication_type'
LEFT JOIN last_amend cs ON cs.complication_no = l.complication_no
                       AND cs.field_name = 'clinical_status'
LEFT JOIN last_amend rs ON rs.complication_no = l.complication_no
                       AND rs.field_name = 'report_status'
LEFT JOIN last_amend fd ON fd.complication_no = l.complication_no
                       AND fd.field_name = 'found_date';
```

**状态机（临床状态，记录在 amend 流水中）：**

```
        ┌─────────┐
        │  OPEN   │  活跃 / 观察中（登记初始状态）
        └────┬────┘
             │
     ┌───────┼───────────┬──────────────┐
     ▼       ▼           ▼              ▼
 ┌────────┐┌──────────┐┌─────────────┐┌───────────────┐
 │DISPOSING││RESOLVED ││ SEQUELAE    ││ TRANSFERRED   │
 │处置中   ││已消退（终态）││遗留后遗症（终态）││转外院（终态）   │
 └───┬────┘└──────────┘└─────────────┘└───────────────┘
     │ 处置完成
     ├──────────► RESOLVED
     ├──────────► SEQUELAE
     └──────────► LOST_FOLLOWUP（失访，终态）
```

**设计说明：**

1. **为什么 `amend_seq` 由应用层 `MAX(seq)+1` 计算而不是用序列？**
   序列是全局递增的，无法表达「同一并发症内的第几次更正」。用 `(complication_no, amend_seq)` 唯一索引 + 事务内取 `MAX+1`，既能保证同一记录内连续，又能在并发时由唯一约束兜底（后到者收到 `40900` 重试）。断号本身就是数据损坏的信号，所以索引里刻意不做「补号」逻辑。

2. **为什么 1 号固定为 `REGISTER`？**
   它让更正链自带起点：若某条并发症的 amend 链从 2 号开始，说明 1 号行丢失，`job_m11_amend_chain_check` 会立即告警。若没有这个锚点，「链从中间开始」与「这条记录本来就没有更正」无法区分。

3. **为什么 `old_value` / `new_value` 用 VARCHAR 而不是 JSONB？**
   每个更正只涉及一个字段，用两列扁平存储让「查某字段的历史变更多少次」变成一次索引扫描。若用 JSONB 存 `{field: {from, to}}`，按字段查询要解包，统计成本高一个数量级。

4. **为什么字段白名单放在数据库 CHECK 里而不是只在代码里？**
   代码可能被绕过（新接口、数据迁移脚本、临时修数）。把白名单固化在约束里，任何路径写入 `reservation_no` 这类不可更正字段都会失败。这是「不可篡改」的最后一道防线。

5. **为什么设 `evidence_ref`？**
   医疗安全调查中最常见的问题是「你凭什么把二级改成三级」。一个可追溯的佐证引用（会诊单号、检查报告号）让更正在事后可核查，而不是仅凭一句文字理由。

**设计说明：**

1. **为什么事件表可以 `UPDATE`，而并发症主档不行？**
   两者的数据性质不同。并发症是**临床事实**——「这个患者出现了 DLK」，这句话要么是真的要么是假的，不会因为管理流程推进而改变；任何对它的改写都是篡改。不良事件是**管理流程**——「这件事处理到哪一步了」本来就是流动的状态，必须原地推进。把两者分开，才能既保住医疗事实的不可篡改，又让流程可以正常流转。

2. **为什么 `action_log` 用 JSONB 追加而不是独立流水表？**
   事件平均只有 6~8 次节点推进，且永远整体读取（画时间轴）。独立流水表会让本子模块变成 9 张表，而查询时必然 `JOIN` 后再排序，收益为负。关闭后 `action_log` 只读，不会再有追加，体积可控（每事件约 2KB）。

3. **为什么三方分离用 CHECK 约束而不只在应用层？**
   职责分离是医疗安全的核心控制点，历史上大量医疗纠纷源于「自己调查自己」。CHECK 约束保证即使将来新增一条接口、一个批量修数脚本，也不可能把同一个人同时写进调查人与复核人。这是「制度固化到数据层」的典型用法。

4. **为什么 `report_delay_minutes` 冗余而不用 `reported_at − found_at` 现算？**
   及时率是月度考核指标，需要按阈值分批统计（`< 120` 分钟 / `120~1440` / `> 1440`）。落库后可以直接建部分索引与聚合计，避免每次考核都做时间差计算。它由触发器在 `reported_at` 变化时自动维护，不会漂移。

5. **为什么保留 `is_deleted` 但还是鼓励走 `VOIDED`？**
   `is_deleted` 只用于「建错了的事件占位行」（例如系统重试造成同一事件两条记录，且其中一条无任何关联数据），由数据管理员在极少数情况下使用。正常的「误报」必须走 `VOIDED`——因为它需要审批与原因，是有审计意义的业务动作，而 `is_deleted` 只是数据清理。

**设计说明：**

1. **为什么 `RE_TREATMENT` 与 `ENHANCEMENT` 放在同一张表？**
   两者的数据结构 90% 重合（都要原方案、眼别、当前屈光度、角膜厚度、同一套评估与审批流程），差异只在「是否设术后月数下限」与「是否必须有并发症依据」。合表后用 `request_type` 区分、用 CHECK 约束表达差异，比建两张几乎一样的表更易维护，也让「再手术率 + 增效率」的合并统计变成一次查询。

2. **为什么 `eligibility_checks` 存 JSONB 快照而不是每次现算？**
   「为什么这个申请被驳回」必须可追溯。若只存最终的 `eligibility_passed`，半年后上游数据变化，无法解释当时为何不通过。存下当时的五项判定与实际数值，让评估结论可复核。

3. **为什么 `current_se` 要落库且加 CHECK 校验 `sph + cyl/2`？**
   眼科数据最常见的错误是「手填 SE 与 sph/cyl 不一致」。用 CHECK 强约束保证三者自洽；同时落库避免每次查询重算，也便于按 SE 做索引与区间统计。

4. **为什么用部分唯一索引 `uk_m11_retreat_source` 而不是全局唯一？**
   同一原方案同眼可以「先被驳回、改进后再提交」，也可以「完成后再来一次增效」。因此唯一性只在「进行中」的状态集合内成立，用部分索引精确表达这个语义，避免误拦合理重提。

5. **为什么不建 `m11_quality_retreatment_log` 流水表？**
   申请的节点推进次数少（平均 3~4 次），且全部状态变更都能从 `status` + 各时间戳字段（`applied_at`/`evaluated_at`/`transferred_at`）还原。相比之下，不良事件需要完整时间轴（六步 + 退回循环），所以那张表用 `action_log`。这里的取舍标准是「是否会出现循环与退回」——有循环才需要流水。

```sql
COMMENT ON COLUMN m11_quality_indicator_version.numerator_formula IS '分子公式文字描述，与计算代码一一对应，是"这个数怎么算的"的权威答案';
```

**状态机：** 本表**无状态机，严格只增**。唯一的「修改」是新增版本时回填上一版本的 `effective_to`（这是生效期边界，不是口径定义）。所有口径定义字段（公式、规则、阈值、舍入）**永不修改**。

**设计说明：**

1. **为什么口径要版本化而不是直接在配置表里改？**
   质量指标一旦被用于医师考核或对外报送，就必须回答「去年的 1.02 是用什么口径算的」。若只保留最新口径，历史数字将无法解释，也无法判断「今年变好是真的变好还是口径放宽了」。版本化让每个指标值通过 `indicator_version` 字段指回它当时的算法定义。

2. **为什么 `threshold_direction` 要与阈值大小做 CHECK 交叉校验？**
   经验指标「越大越好」时 WARNING 阈值应高于 ALERT 阈值（如 EI：warn 0.90 > alert 0.80）；「越小越好」时相反（如 SI：warn 0.10 < alert 0.20）。写反了会导致告警级别颠倒——本该报警的显示正常，这是最危险的一类配置错误。CHECK 让它在写入时就不可能发生。

3. **为什么用部分唯一索引保证「同指标只有一个 `effective_to IS NULL`」？**
   它保证任意时刻每个指标有且仅有一个当前生效口径。若出现两个 NULL，计算服务无法确定用哪个；若一个都没有，新数据无法计算。这条约束把「口径真空」与「口径冲突」都变成写入失败。

4. **为什么 `zero_denominator_policy` 只有一个合法值？**
   这是一个刻意「锁死」的字段：本子模块的业务铁律就是分母为 0 时必须返回 NULL 而不是 0。留一个可配置字段是为了让口径文档自解释（读者能看到「这里有个策略」），但 CHECK 把它限定为唯一值，杜绝将来有人配置成「返回 0」。

5. **为什么 `requires_recalc` 是显式字段而不是自动判断？**
   是否回溯重算历史期间是一个业务决策：收紧阈值通常不回溯（历史数据已定稿），修正公式错误则必须回溯。这个判断依赖业务语义，无法从字段变化自动推导，因此由人工显式声明并留痕。

```
   └───────────┘          └──────────┘
```

**设计说明：**

1. **为什么「运行中批次」要用部分唯一索引约束？**
   同一个期间同时跑两个计算批次会产生重复的明细与快照，甚至后跑的覆盖先跑的导致结果抖动。`uk_m11_calc_batch_running (period_type, period_key) WHERE status='RUNNING'` 让第二个并发任务在 INSERT 时就失败，比查一次再插更可靠。

2. **为什么 `indicator_version_snapshot` 要存 JSONB 映射而不是引用版本表 id？**
   版本表本身就是只增的，引用 id 也能追溯。但存 JSONB 映射有两个好处：①查询指标值时不必 JOIN 版本表即可知道用了哪个版本（P-14 需要返回 `indicator_version`）；②同一批次可能因边界日期跨两个版本（例如期间跨越口径变更日），映射形式能精确表达「这个指标用 v3、那个指标用 v4」。

3. **为什么 `superseded_batch_no` 要记录而不直接删旧批次？**
   重算的意义就是把新结果推到报表。若删旧批次，就无法回答「上个月报出去的数字与这个月算出来的为什么不一样」。保留旧批次与取代关系，使「口径变更前后对比」成为可能，也是审计要求。

4. **为什么 `case_valid + case_excluded = case_total` 只在 `DONE` 时强制？**
   计算过程中三个计数是逐步累加的，中途必然不满足等式。把约束限定在 `DONE` 状态，既保证最终结果自洽，又不阻碍中途写入。这比在应用层「算完再校验」更可靠——数据库直接拒绝对不上总数的不完整批次。

5. **为什么需要 `trigger_type` 区分三种触发方式？**
   定时批次是基线，事件驱动批次是增量，人工重算是修正。三者的 `recalc_reason`、`superseded_batch_no` 要求不同，统计「本月因口径问题重算了几次」也依赖这个字段。混在一起会让「系统算的」与「人改过算的」无法区分。

**设计说明：**

1. **为什么明细要存分子分母而不是直接存算好的指标值？**
   直接存指标值会丢信息：当某个期间的结果看起来异常时，无法判断是分子偏了还是分母偏了（例如「有效率下降」可能是疗效真的差了，也可能是新增了一批高风险病例）。存分子分母后，任取一个聚合结果都能反算验证，也支持「按不同维度重新组合」而不必重跑原始数据拉取。

2. **为什么分母为 0 时不写行，而不是写一行 `denominator=0`？**
   若写入 `denominator=0`，聚合时 `SUM(numerator)/SUM(denominator)` 会因为 0 参与求和而稀释结果——10 个有效样本 + 1 个分母 0 的样本，分母会变成 10 而不是 10。排除逻辑必须发生在「是否计入样本」这一层，而不是在算术层。因此无效样本写入 `is_valid=false` 但不参与聚合。

3. **为什么要有 `comparison_value`？**
   稳定性指标的本质是「两个数之差」，可预测性的本质是「一个数与目标之差」。若只存分子（差值），无法核对差值算得对不对；把对比基准也存下来，单行即可自证。

4. **为什么冗余 `refractive_type` / `doctor_id` / `surgery_date` 等维度字段？**
   聚合查询是最热的路径（每日重算全部维度）。若每次都 JOIN M11-04 方案表取术式、JOIN M11-05 取主刀，聚合 5 万行会退化为 5 万次 JOIN。冗余后单表即可 `GROUP BY`，配合 `INCLUDE (numerator_value, denominator_value)` 的覆盖索引，聚合可走 index-only scan。

5. **为什么有效性指标的分子用比值而不是布尔？**
   「达成率」与「有效性指数」是两个指标，前者是布尔计数（`EI_AMONG`），后者是比值求和（`EI_UCVA`）。若只存布尔，就无法算指数；若只存比值，`EI_AMONG` 需要额外判断「比值是否 ≥ 1」。两个指标分别有自己的行，各存所需形态，语义清晰。

**设计说明：**

1. **为什么快照表要重复存 `warn_threshold` / `alert_threshold` / `threshold_direction`？**
   阈值会随口径版本变化。若只存 `alert_level`，半年后口径调整了阈值，「当时为什么判定为 WARNING」就无法复原。快照阈值让每一行自解释，也让「阈值调整前后告警数变化」可追溯——这是质控办最常被问到的问题之一。

2. **为什么 `ck_m11_summary_no_sample` 要写得这么严格？**
   这是本子模块最重要的一条约束。它把「无样本」与「有样本」两种状态的四种字段取值绑死，杜绝任何组合错误：不可能出现「值为 0 且 available=true」（会被误读为效果为零），也不可能出现「NO_SAMPLE 却带告警级别」（会被计入告警统计）。业务铁律固化成数据库约束后，无论哪条代码路径写入都不会错。

3. **为什么维度值用 `VARCHAR` 而不是分别建 `doctor_id BIGINT`、`refractive_type VARCHAR` 等列？**
   六个维度如果各自建列，会产生大量 NULL 与稀疏索引，且每新增一个维度就要改表结构。统一用 `dimension` + `dimension_value` 的纵表结构，新增维度只需加枚举值，查询时用 `WHERE dimension='DOCTOR'` 精确命中对应索引。代价是关联医师表时要把字符串转 ID，但这个转换只在展示层做一次。

4. **为什么 `sample_count <= expected_count` 要约束？**
   有效样本数不可能超过应纳入数。若出现，说明上游数据有重复（同一眼被算两次），这是比指标偏差更严重的数据质量问题，必须立即暴露。

5. **为什么不存 `indicator_value` 的计算明细（分子分母之和）？**
   快照的职责是「供快速查询的最终结果」，明细留在 4.8。若快照也存分子分母之和，会与明细产生第二份事实，两者不一致时无法判断谁对。保持「明细唯一真相、快照可重算验证」的单向关系，`job_m11_quality_summary_repair` 每日校验二者一致。

```sql
WITH recomputed AS (
    SELECT i.calc_batch_no,
           i.indicator_code,
           SUM(i.numerator_value)                    AS num_sum,
           SUM(i.denominator_value)                  AS den_sum,
           ROUND(SUM(i.numerator_value)
                 / NULLIF(SUM(i.denominator_value), 0), 4) AS value
    FROM m11_quality_indicator_item i
    WHERE i.is_valid = TRUE
      AND i.node_code = :node
    GROUP BY i.calc_batch_no, i.indicator_code
)
SELECT s.calc_batch_no,
       s.indicator_code,
       s.indicator_value                       AS stored_value,
       r.value                                 AS recomputed_value,
       ABS(COALESCE(s.indicator_value, 0) - COALESCE(r.value, 0)) AS diff
FROM m11_quality_summary s
JOIN recomputed r
  ON r.calc_batch_no = s.calc_batch_no
 AND r.indicator_code = s.indicator_code
WHERE s.dimension = 'ALL'
  AND ABS(COALESCE(s.indicator_value, 0) - COALESCE(r.value, 0)) > 0.0001;
```

| **修改主档结构** | **需医务科 + 质控办联合审批** | 是 | 涉及医疗安全凭证，慎之又慎 |

### F.2 已有偏离登记

| 偏离项 | 共享规范要求 | 本子模块实现 | 理由 |
|---|---|---|---|
| `is_deleted` 字段 | 全部表带 `is_deleted BOOLEAN NOT NULL DEFAULT FALSE` | `m11_complication_ledger` 与 `m11_complication_amend` **不带** | 医疗安全原始凭证必须不可删；去掉该列后删除在结构层面无法表达 |
| `version` 乐观锁 | 建议全部业务表带 | 仅事件、申请、批次带 | 只增表无并发写冲突，无需乐观锁 |
| `updated_at` 字段 | 全部表带并由触发器维护 | 只增表不带 `updated_at` | 只增表没有"更新"语义 |
| 表数量 | 建议 7~9 张 | 8 张 | 符合建议区间 |
