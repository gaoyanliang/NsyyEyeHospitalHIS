## 1. 模块概述

### 1.1 模块定位

M15-07 回答一个问题：**「这片东西，装给谁了？它出问题了，要找回哪些人？」**

它是 M15 物资耗材管理的**终点**。前面六个子模块都在回答「货怎么进来、在哪里、怎么出去、用了多少」，M15-07 回答的是最后一问：「用了之后呢？」

```
┌──────────────────────────────────────────────────────────────────────────────────┐
│                          植入物全生命周期（M15 视角）                              │
└──────────────────────────────────────────────────────────────────────────────────┘

  M15-03 采购入库            M15-01 台账              M15-04 出库             M15-06 消耗

  │ 注册证核验     │ ─────► │ 序列号实例登记 │ ─────► │ 批次锁定      │ ───► │ 扫码登记      │

                                                                                 │
```

**M15-07 与 M09-05 的分工（用户决策，见 `M09_M15_拆分方案.md` §2 决策 3）：**

| 维度 | M09-05 植入物使用与扫码绑定 | M15-07 植入物追溯与召回 |
|---|---|---|
| 时机 | **术中那 30 秒** | **术后到未来 20 年** |
| 用户 | 巡回护士、主刀 | 耗材科、医务科、质控科 |
| 核心动作 | 扫码、五道校验、三方共读 | 查询、召回分析、随访跟踪 |
| 数据 | 单片植入的**当时事实** | 全量植入的**长期档案** |
| 表 | `m09_implant_use` / `m09_implant_item` | `m15_implant_usage` / `m15_recall_*` |
| 数量级 | 年约 4,700 条 | 年约 4,700 条，累计 15 年 70,500 条 |

**一句话边界：** M09-05 说「这片晶体验证过、装到右眼了」；**M15-07 说「这片晶体装给谁了、有问题要召哪些人」**。

### 1.2 为什么独立成子模块

| 理由 | 说明 |
|---|---|
| **法规强制要求独立追溯档案** | 《医疗器械监督管理条例》第 45 条、《医疗器械召回管理办法》（国家市场监督管理总局令第 29 号）第 12 条：医疗器械经营企业、使用单位应当**建立并保存进货查验记录和销售记录**，记录保存期限**不得少于产品有效期届满后 2 年，无有效期的不得少于 5 年**；**植入类医疗器械**记录保存期限**不得少于产品有效期届满后 5 年**。若合并进 M15-06，消耗记录的归档策略（15 年）与植入物追溯档案（永久 + 有效期届满后 5 年）冲突 |
| **查询模式完全不同** | M15-06 消耗记录按「台次」查（一台 42 条）；M15-07 追溯按「患者」或「批号」或「序列号」查（一个患者 3 条，一个批号可能 200 条跨 3 年）。索引设计、数据模型必须不同 |
| **召回是独立应急流程** | 召回有独立单号、独立审批、独立执行跟踪、独立随访任务，与日常消耗完全不是一回事。合并后召回字段会让消耗表新增 30+ 个平时为 NULL 的字段 |
| **召回响应有时间红线** | 《医疗器械召回管理办法》第 18 条：一级召回**必须在 24 小时内**通知到所有应召回对象。这个 SLA 需要独立的监控、告警与演练机制 |
| **不良事件上报是法定义务** | 《医疗器械不良事件监测和再评价管理办法》（国家市场监督管理总局令第 1 号）第 21 条：导致**严重伤害**或**死亡**的，**7 日内**报告；**可能导致**严重伤害的，**20 日内**报告。上报需要独立的填报、附件、状态跟踪 |

### 1.4 概念辨析

**四个易混淆的概念：**

| 概念 | 定义 | 与 M15-07 的关系 |
|---|---|---|
| **植入物（Implant）** | 通过手术或介入操作**留置在人体内 30 日以上**的器械 | 本年植入的 8 类：人工晶体 4,700 片、青光眼引流阀 42 套、玻璃体填充物 260 支、眼眶植入物 18 个、眼表植入物（生物羊膜）180 例、泪道植入物 320 例、角膜基质环 6 例、缝线固定材料 1,200 根 |
| **高风险耗材（High-Value Consumable）** | 单价 ≥ 3,000 元的耗材，**不一定植入** | 单件 ≥ 3,000 元但非植入的（如飞秒激光耗材）走 M15-06 高值柜管理，不进 M15-07 |
| **追溯（Traceability）** | 正向（批号→患者）与反向（患者→批号）双向查询 | M15-07 的核心能力 |
| **召回（Recall）** | 厂商或药监发现批次问题后，**要求停止使用并追回/随访** | M15-07 的应急能力，依赖追溯数据完整性 |

**追溯方向：**

- **正向追溯**：给定批号/序列号/UDI-DI → 查出所有使用过该批次的患者。用于**召回**。
- **反向追溯**：给定患者 → 查出所有植入过的器械（含品牌、型号、批号、序列号、植入日期、植入医生）。用于**患者取片记录、术后影像检查（如 MRI 兼容性）、司法鉴定**。
- **中间追溯**：给定供应商/注册证 → 查出哪些批次/患者。用于**供应商质量评估、注册证过期追溯**。

**为什么「植入」与「高值」不能划等号：**

- 人工晶体单价 3,000~15,000 元，既是高值也是植入 → M15-06 管理存储与消耗，M15-07 管理追溯。
- 飞秒激光耗材单价 12,000 元，不是植入 → 只走 M15-06。
- 缝线固定材料（如眼科缝线）单价 80 元，是植入（缝在巩膜/肌肉上）→ 只走 M15-07。
- **若按「高值=植入」设计，80 元的缝线会漏追溯**；而追溯的法规要求看的是「是否植入」不是「多少钱」。

## 3. 业务模型

### 3.1 追溯数据模型

```
┌──────────────────────────────────────────────────────────────────────────────────────┐
│  追溯四元组：患者 + 耗材 + 批次/序列号 + 时间                                          │
└──────────────────────────────────────────────────────────────────────────────────────┘

  ┌────────────────────────┐
  │  m15_implant_usage     │  ← 植入使用记录（M15-07 核心表）
  │  ────────────────────  │
  │  一个患者一次植入 = 一条 │
  │                        │
  │  patient_id      ──────┼──► 患者（M03-01）
  │  material_code   ──────┼──► 耗材（M01-04）
  │  udi_di                │     UDI 产品标识
  │  batch_no              │     批号
  │  serial_no             │     序列号（一物一码）
  │  implant_site          │     植入部位（右眼/左眼/...）
  │  implanted_at          │     植入时间
  │  surgeon_id            │     主刀医生
  │  schedule_id           │ ──► 手术台次（M06-03）
  │  consume_item_id       │ ──► 消耗明细（M15-06）
  └───────────┬────────────┘
              │
              │ N:1
              ▼
  ┌────────────────────────┐         ┌──────────────────────────────┐
  │  m15_implant_batch     │         │  m15_implant_recall_item     │
  │  批次聚合（只读视图级） │  ◄──────│  召回影响明细（哪条 usage 受影响）│
  └────────────────────────┘         └──────────────┬───────────────┘
                                                    │ N:1
                                                    ▼
                                     ┌──────────────────────────────┐
                                     │  m15_implant_recall          │
                                     │  召回单（一次召回一份）        │
                                     └──────────────────────────────┘
```

**为什么使用记录与消耗明细分开：**

- 消耗明细是 M15-06 的**即时账**（一条晶体消耗 → 一条消耗明细），可能因计费拆分产生多条。
- 使用记录是 M15-07 的**永久档案**（一个患者一次植入 → 一条），承载植入部位、术后随访、不良事件关联。
- 两者是 1:0..1 关系。一条消耗明细可能没有使用记录（非植入物），也可能 1 条使用记录（植入物）。
- 分开后，M15-06 的计费逻辑与 M15-07 的追溯逻辑互不干扰。

### 3.2 植入使用记录状态机（4 态）

```
        ┌──────────┐  数据完整   ┌──────────────┐
        │ PENDING  │ ─────────► │  REGISTERED  │
        │ 待补录   │             │   已登记     │
        └──────────┘             └──────┬───────┘
             │                          │
         作废│                    召回  │  随访完成
             ▼                          ▼
        ┌──────────┐             ┌──────────────┐
        │ CANCELLED│             │   FOLLOWED   │
        └──────────┘             │   已随访     │
                                 └──────────────┘
```

- `PENDING`：消耗已确认但植入信息不全（缺序列号/缺植入部位/缺主刀），**这是常态**——术中扫码不一定完整，需要追溯专员补录。
- `REGISTERED`：信息完整，可用于追溯。
- `FOLLOWED`：召回或术后随访已完成。
- `CANCELLED`：录入错误作废，保留记录（**不删除**）。

**为什么不设「已归档」：** 植入物追溯档案的存档期限是「有效期届满后 5 年」，人工晶体终身无有效期，实际就是**永久保存**。归档反而会让查询变复杂。

### 3.3 召回模型

**召回级别（依据《医疗器械召回管理办法》第八条）：**

| 级别 | 定义 | 通知时限 | 本院子模块的时限 |
|---|---|---|---|
| 一级召回 | 使用该器械**可能引起严重健康危害** | **24 小时**内 | **4 小时**内（本院加严） |
| 二级召回 | 使用该器械**可能引起暂时的或可逆的健康危害** | **48 小时**内 | **12 小时**内 |
| 三级召回 | 使用该器械**一般不会引起危害**，但仍需召回 | **72 小时**内 | **24 小时**内 |

**召回单状态机（7 态）：**

```
   ┌─────────┐   ┌──────────────┐   ┌───────────────────┐   ┌─────────┐
   │  DRAFT  │──►│PENDING_REVIEW│──►│ ANALYSIS_COMPLETE │──►│NOTIFYING│
   └─────────┘   └──────────────┘   └───────────────────┘   └────┬────┘
                       │                    │                     │
                   驳回  │             影响为零 │             全部通知完成
                       ▼                    ▼                     ▼
                  ┌─────────┐         ┌─────────┐          ┌─────────┐
                  │REJECTED │         │ CLOSED  │          │FOLLOWING│──┐
                  └─────────┘         └─────────┘          └─────────┘  │
                                                                         │
                                                                 随访完成 ▼
                                                                   ┌─────────┐
                                                                   │ CLOSED  │
                                                                   └─────────┘
```

**七个状态的含义与转换约束：**

| 状态 | 含义 | 可转入 |
|---|---|---|
| `DRAFT` | 新建，仅创建者可编辑 | `PENDING_REVIEW` / `CLOSED`（放弃） |
| `PENDING_REVIEW` | 待审批（一级召回需耗材科长+医务科双签） | `ANALYSIS_COMPLETE` / `REJECTED` |
| `ANALYSIS_COMPLETE` | 影响范围已分析完成 | `NOTIFYING` / `CLOSED`（影响为零） |
| `NOTIFYING` | 正在通知受影响的患者 | `FOLLOWING` |
| `FOLLOWING` | 随访阶段 | `CLOSED` |
| `CLOSED` | 已关闭（终态） | 无 |
| `REJECTED` | 审批驳回（终态） | 无 |

### 3.4 影响范围分析模型

**输入：** 召回条件（任选其一或多选）

| 条件类型 | 说明 | 示例 |
|---|---|---|
| `BATCH_NO` | 批次号 | `B240815` |
| `SERIAL_NO` | 序列号（一物一码） | `SN-8829310` |
| `UDI_DI` | UDI 产品标识 | `08717648200274` |
| `MATERIAL_CODE` | 耗材编码（整类召回） | `M-00581` |
| `REGISTRATION_NO` | 注册证号（注册证注销召回） | `国械注进20203160123` |

**输出：影响清单**

```
影响数量统计
 ├── 已植入（usage 表命中）        → 必须通知 + 随访
 ├── 在库（M15-01 台账命中）       → 冻结 + 退回供应商
 ├── 在途（M15-04 出库中）         → 拦截
 └── 已消耗未植入（如缝线剪断）     → 记录，不随访
```

**分析算法：**

1. 按条件查 `m15_implant_usage`，得到已植入清单（**这是一级优先**，因为已经进了人体）。
2. 按条件查 `m15_stock` / `m15_sec_stock`，得到在库清单。
3. 按条件查 `m15_issue` / `m15_issue_batch` 中已出库未签收的，得到在途清单。
4. 按条件查 `m15_or_consume_item` 中已消耗但无 usage 的，得到「已用未登记」清单（**这部分最危险**：已经被使用但没有追溯记录）。

**为什么「已用未登记」要单列：** 如果消耗记录的 `is_implant=FALSE` 但实际是植入物（录入错误），或者 M09-05 扫码失败走了手工录入，就会出现「消耗了但 usage 表没有」。这类必须人工核实：「这些东西去哪里了？」

### 3.5 召回通知与随访模型

**通知优先级与渠道：**

| 优先级 | 场景 | 渠道 | 时限 |
|---|---|---|---|
| P1 | 一级召回 - 已植入 | 电话（主）+ 短信（辅）+ 站内信 | 4 小时内 |
| P2 | 二级召回 - 已植入 | 电话（主）+ 短信 | 12 小时内 |
| P3 | 三级召回 - 已植入 | 短信 + 站内信 | 24 小时内 |
| P4 | 召回 - 在库/在途 | 内部消息（耗材科） | 24 小时内 |

**通知送达判定（三级）：**

- `SENT`：消息已发出（M03-05 返回成功）
- `DELIVERED`：对方设备已接收（短信回执 / 站内信已读）
- `CONFIRMED`：患者/家属已明确表示收到（电话接通且确认 / 回复「1」）

**为什么需要三级：** 短信发送成功不等于患者看到了。「SENT」只是技术层面，「CONFIRMED」才是业务层面。一级召回必须达到 `CONFIRMED` 才算完成。

**随访任务：**

| 召回级别 | 随访频次 | 随访天数 |
|---|---|---|
| 一级召回 | 首次：3 日内；后续：每周 1 次，连续 4 周 | 第 1/7/14/21/28 天 |
| 二级召回 | 首次：7 日内；后续：第 14 天、第 30 天 | 第 7/14/30 天 |
| 三级召回 | 首次：14 日内 | 第 14 天 |

随访内容包括：是否取出？有无症状（如视力下降、眼痛、炎症）？是否需要复查？

### 3.6 未登记检测模型

**问题：** 消耗记录了「人工晶体 1 片」但 usage 表没有对应记录（追溯断链）。

**检测规则（每夜 01:00 扫描）：**

```
条件：m15_or_consume_item
      ├── is_implant = TRUE
      └── 无对应 m15_implant_usage（通过 consume_item_id 关联）
      AND 消耗确认时间 < NOW() - 24 小时
→ 生成【未登记告警】进入待办
```

**为什么要等 24 小时：** 术中扫码后护士可能还需要补录植入部位等信息，24 小时内都算正常。超过 24 小时需要追溯专员介入。

**告警升级：**

- 第 1 天：耗材科追溯专员
- 第 3 天：耗材科科长
- 第 7 天：医务科

### 3.7 不良事件上报模型

**上报条件（依据《医疗器械不良事件监测和再评价管理办法》）：**

| 严重程度 | 定义 | 上报时限 | 上报对象 |
|---|---|---|---|
| 死亡 | 可能导致死亡的事件 | **7 日**内 | 药监 + 卫健 |
| 严重伤害 | 危及生命、导致永久性损伤、需要住院或延长住院 | **7 日**内 | 药监 + 卫健 |
| 可能导致严重伤害 | 尚未造成但存在风险 | **20 日**内 | 药监 |
| 其他 | 一般不良事件 | **30 日**内 | 院内记录 |

**上报流程：**

```
临床发起 → 耗材科登记 → 医务科审核 → 药监上报 → 结果跟踪
   │            │            │            │            │
 发现事件    记录详情     判断等级     国家不良反应    整改与闭环
            关联植入物    确认上报     监测系统填报
```

**为什么关联植入物：** 不良事件如果与具体批次有关，可能需要升级为召回。两者是联动的：不良事件 → 分析 → 发现批次问题 → 启动召回。

### 3.8 与 M09-05 的数据一致性

**两个数据源可能不一致：**

| 场景 | M09-05 | M15-06 | M15-07 |
|---|---|---|---|
| 正常扫码植入 | 有记录 | 有消耗明细 | 自动生成 usage |
| 扫码失败改手工录 | 无记录 | 有消耗明细 | 自动生成 usage（M15-06 事件驱动） |
| 扫码了但实际未植入（临时换片） | 有记录（状态 IMPLANTED 前撤销） | 无消耗明细 | 不生成 |
| 非植入物误标为植入物 | 有记录 | 有消耗明细 | 生成 usage，需人工核实 |

**一致性保障：**

1. M15-06 消耗确认时发 `m15.consume.item.confirmed` 事件，带 `is_implant` / `serial_no` / `udi_di` 等字段。
2. M15-07 订阅该事件，若 `is_implant=TRUE` 则自动创建 `PENDING` 状态的 usage 记录。
3. 每日对账任务比对 `m15_or_consume_item.is_implant=TRUE` 与 `m15_implant_usage`，差异进待办。

### 3.9 患者自助查询模型

**患者能查到什么：**

- 自己所有植入物清单（品牌、型号、批号、植入日期、医院、主刀医生）
- 植入物是否被召回
- 植入物的注意事项（如 MRI 兼容性）

**不能查到什么：**

- 其他患者的信息
- 耗材采购价格与成本
- 供应商信息

**接口：**

- `GET /internal/v1/m15/implant/by-patient/{patient_id}` P95 ≤ 300ms，供 M03-06 患者门户调用。

### 3.10 追溯完整率计算

```
追溯完整率 =（信息完整的 usage 数 / 应登记 usage 数）× 100%

信息完整标准：
  ① 有 patient_id
  ② 有 material_code
  ③ 有 batch_no（批次管理耗材）或 serial_no（一物一码耗材）
  ④ 有 implant_site
  ⑤ 有 implanted_at
  ⑥ 有 surgeon_id
```

**为什么不用「有记录即可」：** 一条 usage 如果缺客户 ID 或植入部位，追溯时无法通知、无法判断是哪只眼，等于无效记录。

| 随访记录 | 备注 | 自由文本 |

**交互说明：**

| 操作 | 触发 | 结果 |
|---|---|---|
| 打电话 | 点击 | 弹出外呼（集成 CTI）或显示完整号码 |
| 标无法联系 | 点击 | 需填原因（≥10 字），状态置 `UNREACHABLE` |
| 记录随访 | 点击 | 展开随访表单 |
| 保存 | 点击 | 保存随访记录 |
| 转随访 | 点击 | 状态 `NOTIFYING` → `FOLLOWING`，生成随访任务 |
| 关闭召回 | 点击 | 校验全部确认或无法联系 → `CLOSED` |

**校验规则：**

| 编号 | 规则 | 说明 | 错误码 |
|---|---|---|---|
| V-33 | 无法联系须填原因 | ≥10 字 | `"1507034"` |
| V-34 | 随访内容必填 | 是否取出、症状、是否需要复查 | `"1507032"` |
| V-35 | 关召回前校验 | 所有人 `CONFIRMED` 或 `UNREACHABLE` | `"1507031"` |
| V-36 | 随访不可删除 | 只能追加新记录 | — |
| V-37 | 一级召回超时告警 | 超过 deadline 未全部确认 → 自动升级医务科 | — |

**为什么「无法联系」要单列：** 召回失败的常见原因是联系不上患者（空号、停机、换号）。这类不能简单标记「已通知」了事，必须记录原因并留档——万一患者真出了问题，这是「我们已经尽力联系」的证据。

```python
MAX_QUERY_ROWS = 500
MAX_ANALYSIS_ROWS = 2000
MAX_EXPORT_ROWS = 50000


def _next_no(prefix: str, seq: int) -> str:
    """生成单号：IM-YYYY-NNNNNNN。"""
    return "%s-%s-%07d" % (prefix, datetime.now().strftime("%Y"), seq)


# ============ 植入物使用登记 ============

class ImplantService(BaseService):
    """植入物使用记录服务。"""

    @classmethod
    async def trace(cls, query, user) -> Dict[str, Any]:
        """追溯查询：正向 / 反向 / 中间。"""
        # ① 校验参数
        if not query.condition_value:
            raise BizException("1507043", "查询条件不能为空")

        async with get_session() as db:
            # ② 按追溯类型分流
            if query.trace_type == "FORWARD":
                return await cls._forward_trace(db, query, user)
            elif query.trace_type == "REVERSE":
                return await cls._reverse_trace(db, query, user)
            elif query.trace_type == "MIDDLE":
                return await cls._middle_trace(db, query, user)
            else:
                raise BizException("1507043", "追溯类型非法")

    @classmethod
    async def _forward_trace(cls, db, query, user) -> Dict[str, Any]:
        """正向追溯：批次/序列号/UDI → 患者清单。"""
        # ① 构造条件
        cond_field = {
            "BATCH_NO": M15ImplantUsage.batch_no,
            "SERIAL_NO": M15ImplantUsage.serial_no,
            "UDI_DI": M15ImplantUsage.udi_di,
        }.get(query.condition_type)
        if cond_field is None:
            raise BizException("1507043", "正向追溯条件类型非法")

        conditions = [
            cond_field == query.condition_value,
            M15ImplantUsage.status.in_(("REGISTERED", "FOLLOWED")),
            M15ImplantUsage.is_deleted.is_(False),
        ]
        if query.date_from:
            conditions.append(M15ImplantUsage.implanted_at >= query.date_from)
        if query.date_to:
            end = datetime.combine(query.date_to, datetime.max.time())
            conditions.append(M15ImplantUsage.implanted_at <= end)

        # ② 查已植入
        stmt = (
            select(M15ImplantUsage)
            .where(and_(*conditions))
            .order_by(M15ImplantUsage.implanted_at.desc())
            .limit(MAX_QUERY_ROWS + 1)
        )
        rows = (await db.execute(stmt)).scalars().all()
        if len(rows) > MAX_QUERY_ROWS:
            raise BizException("1507044", "查询结果超过 %d 行，请缩小范围" % MAX_QUERY_ROWS)

        # ③ 查库存（M15-01 / M15-04）
        stock_sql = text(
            """
            SELECT 'PRIMARY' AS stock_type, w.warehouse_name, l.location_code,
                   s.serial_no, s.qty_on_hand AS qty, s.status
            FROM m15_stock s
            JOIN m15_warehouse w ON w.id = s.warehouse_id
            LEFT JOIN m15_location l ON l.id = s.location_id
            WHERE s.batch_no = :batch AND s.qty_on_hand > 0 AND s.is_deleted = FALSE
            UNION ALL
            SELECT 'SECONDARY' AS stock_type, ss.warehouse_name, NULL AS location_code,
                   ss.serial_no, ss.qty_on_hand AS qty,
                   CASE WHEN ss.qty_locked > 0 THEN 'HOLD' ELSE 'NORMAL' END AS status
            FROM m15_sec_stock ss
            WHERE ss.batch_no = :batch AND ss.qty_on_hand > 0 AND ss.is_deleted = FALSE
            """
        )
        stock_rows = (await db.execute(stock_sql, {"batch": query.condition_value})).fetchall()

        # ④ 查已用未登记
        unreg_sql = text(
            """
            SELECT ci.id AS consume_item_id, c.consume_no, c.created_at AS consumed_at,
                   c.schedule_no, c.patient_name, ci.qty
            FROM m15_or_consume_item ci
            JOIN m15_or_consume c ON c.id = ci.consume_id
            LEFT JOIN m15_implant_usage u ON u.consume_item_id = ci.id AND u.is_deleted = FALSE
            WHERE ci.is_implant = TRUE
              AND ci.batch_no = :batch
              AND u.id IS NULL
              AND ci.is_deleted = FALSE
            LIMIT 200
            """
        )
        unreg_rows = (await db.execute(unreg_sql, {"batch": query.condition_value})).fetchall()

        # ⑤ 组装
        return {
            "trace_type": "FORWARD",
            "condition_type": query.condition_type,
            "condition_value": query.condition_value,
            "material": cls._material_brief(rows, stock_rows),
            "summary": {
                "implanted_count": len(rows),
                "in_stock_count": len(stock_rows),
                "in_transit_count": 0,
                "consumed_unregistered_count": len(unreg_rows),
                "total_count": len(rows) + len(stock_rows) + len(unreg_rows),
            },
            "patients": [cls._usage_dict(r, user) for r in rows],
            "in_stock_items": [dict(r._mapping) for r in stock_rows],
            "unregistered_items": [dict(r._mapping) for r in unreg_rows],
            "total": len(rows),
            "page": 1,
            "page_size": MAX_QUERY_ROWS,
        }

    @classmethod
    async def _reverse_trace(cls, db, query, user) -> Dict[str, Any]:
        """反向追溯：患者 → 植入物清单。"""
        patient_id = int(query.condition_value)

        stmt = (
            select(M15ImplantUsage)
            .where(
                M15ImplantUsage.patient_id == patient_id,
                M15ImplantUsage.is_deleted.is_(False),
            )
            .order_by(M15ImplantUsage.implanted_at.desc())
        )
        rows = (await db.execute(stmt)).scalars().all()

        return {
            "trace_type": "REVERSE",
            "condition_type": "PATIENT",
            "condition_value": str(patient_id),
            "summary": {
                "implanted_count": len(rows),
                "in_stock_count": 0,
                "in_transit_count": 0,
                "consumed_unregistered_count": 0,
                "total_count": len(rows),
            },
            "items": [cls._usage_dict(r, user) for r in rows],
            "total": len(rows),
        }

    @classmethod
    async def _middle_trace(cls, db, query, user) -> Dict[str, Any]:
        """中间追溯：供应商/注册证 → 批次 → 患者。"""
        if query.condition_type == "REGISTRATION_NO":
            cond = M15ImplantUsage.registration_no == query.condition_value
        elif query.condition_type == "SUPPLIER_ID":
            cond = M15ImplantUsage.supplier_id == int(query.condition_value)
        else:
            raise BizException("1507043", "中间追溯条件类型非法")

        stmt = (
            select(
                M15ImplantUsage.batch_no,
                M15ImplantUsage.material_code,
                M15ImplantUsage.material_name,
                func.count(M15ImplantUsage.id).label("cnt"),
            )
            .where(cond, M15ImplantUsage.is_deleted.is_(False))
            .group_by(
                M15ImplantUsage.batch_no,
                M15ImplantUsage.material_code,
                M15ImplantUsage.material_name,
            )
            .order_by(text("cnt DESC"))
        )
        rows = (await db.execute(stmt)).fetchall()

        return {
            "trace_type": "MIDDLE",
            "condition_type": query.condition_type,
            "condition_value": query.condition_value,
            "batches": [dict(r._mapping) for r in rows],
            "total": len(rows),
        }

    @classmethod
    async def by_patient(cls, patient_id: int, user) -> Dict[str, Any]:
        """患者植入档案。"""
        result = await cls.internal_by_patient(patient_id)
        return result

    @classmethod
    async def get_usage(cls, usage_id: int, user) -> Dict[str, Any]:
        async with get_session() as db:
            row = await db.get(M15ImplantUsage, usage_id)
            if row is None or row.is_deleted:
                raise BizException("1507001", "使用记录不存在")
            return cls._usage_detail(row, user)

    @classmethod
    async def list_usage(
        cls, patient_id, material_code, status, date_from, date_to, page, page_size, user
    ) -> Dict[str, Any]:
        async with get_session() as db:
            conditions = [M15ImplantUsage.is_deleted.is_(False)]
            if patient_id:
                conditions.append(M15ImplantUsage.patient_id == patient_id)
            if material_code:

    @classmethod
    async def register(cls, usage_id: int, body, user) -> Dict[str, Any]:
        """补录完成：PENDING → REGISTERED。"""
        async with get_session() as db:
            row = await db.get(M15ImplantUsage, usage_id)
            if row is None or row.is_deleted:
                raise BizException("1507001", "使用记录不存在")
            if row.status != "PENDING":
                raise BizException("1507002", "仅待补录状态可提交补录")

            # ① 必填校验
            missing = [f for f in REQUIRED_FIELDS if not getattr(row, f, None)]
            if missing:
                raise BizException("1507005", "缺少必填字段：%s" % "、".join(missing))

            # ② 补录原因
            if not body.register_reason or len(body.register_reason.strip()) < 10:
                raise BizException("1507006", "补录原因不少于 10 字")

            # ③ 关键词触发附件校验
            keywords = ("扫码失败", "手工", "补录", "漏扫")
            if any(k in body.register_reason for k in keywords) and not body.attachment_url:
                raise BizException("1507030", "该补录原因必须上传附件")

            row.status = "REGISTERED"
            row.register_reason = body.register_reason
            row.attachment_url = body.attachment_url
            row.registered_at = datetime.now()
            row.registered_by = user.user_id
            row.registered_by_name = user.user_name
            await db.flush()

            # ④ 关闭对应未登记告警
            if row.consume_item_id:
                await db.execute(
                    update(M15ImplantUnregistered)
                    .where(
                        M15ImplantUnregistered.consume_item_id == row.consume_item_id,
                        M15ImplantUnregistered.resolve_status == "OPEN",
                    )
                    .values(
                        resolve_status="RESOLVED",
                        resolved_at=datetime.now(),
                        resolved_by=user.user_id,
                        resolve_type="REGISTERED",
                    )
                )

            return {"usage_id": row.id, "status": row.status}

                d["recall_nos"] = recall_map.get(r.id, [])

            return {
                "patient_id": patient_id,
                "patient_name": rows[0].patient_name if rows else None,
                "total_count": len(rows),
                "recall_count": len([x for x in items if x["recall_involved"]]),

    @classmethod
    def _mask_name(cls, name: Optional[str], user) -> Optional[str]:
        """姓名脱敏：张*明。"""
        if not name:
            return name
        if user is not None and getattr(user, "has_permission", lambda p: False)(
            "m15:implant:pii"
        ):
            return name
        if len(name) <= 1:
            return name
        if len(name) == 2:
            return name[0] + "*"
        return name[0] + "*" * (len(name) - 2) + name[-1]

                conds.append(M15ImplantUsage.batch_no == row.batch_no)
            if row.serial_no:
                conds.append(M15ImplantUsage.serial_no == row.serial_no)

                    M15ImplantUsage.is_deleted.is_(False),
                )
                .limit(MAX_ANALYSIS_ROWS + 1)
            )

            if len(usages) > MAX_ANALYSIS_ROWS:
                raise BizException("1507046", "影响范围超过 %d 条，请分批召回" % MAX_ANALYSIS_ROWS)

                update(M15ImplantRecallItem)

                )

            row.affected_usage_count = len(usages)
            row.frozen_stock_count = frozen
            row.analyzed_at = datetime.now()

                "recall analyzed",
                extra={
                    "module": "M15-07",
                    "action": "analyze",
                    "recall_no": row.recall_no,
                    "affected": len(usages),

                },
            )
```

### 6.7 专题：为什么植入物追溯必须做成独立子模块的「永久档案」

**问题的本质：** 追溯不是「查一下刚才发生了什么」，而是「二十年后来查当时发生了什么」。

**真实场景推演：**

患者 2026 年植入一片人工晶体。2041 年他因为某种原因需要做核磁共振，医生问：「你眼睛里那个晶体是什么型号？能不能做 MRI？」

- 如果系统只在 `m15_or_consume_item` 留了一条记录，而这条记录按 15 年归档策略已经在 2041 年被归档到冷存储甚至删除 —— 那这条信息就没了。
- 如果系统把植入记录作为**独立永久档案**（`m15_implant_usage` 不设归档期限），2041 年依然能查到这个患者装的是 Alcon SN60WF，MRI 兼容。

**法规要求的时间跨度：**

| 记录类型 | 保存期限 | 依据 |
|---|---|---|
| 普通耗材进货查验与销售记录 | 有效期届满后 2 年；无有效期 5 年 | 《医疗器械监督管理条例》第 45 条 |
| 植入类医疗器械记录 | **有效期届满后 5 年**（人工晶体无有效期 → **永久**） | 《医疗器械监督管理条例》第 45 条 |
| 医疗器械不良事件报告记录 | **永久** | 《医疗器械不良事件监测和再评价管理办法》 |

**因此：**

1. `m15_implant_usage` **不设归档删除**，永久在线保存。
2. `m15_implant_recall` / `m15_implant_recall_item` / `m15_implant_notify` / `m15_implant_followup` **永久保存** —— 召回是为了保护已经植入的患者，二十年后如果有迟发问题，当时的召回记录是「我们已经尽力找过、通知过、随访过」的完整证据链。
3. `m15_implant_adverse` **永久保存**。

**为什么不能靠「归档不删」而必须独立成表：**

- 归档表通常放在冷存储（对象存储 / 独立归档库），查询延迟高、不支持在线关联。
- 追溯查询是**高频的在线查询**（患者门诊时医生随手查一次、影像科做 MRI 前查一次、飞检时批量导出），必须在线。
- 因此宁可牺牲「表数量少」这样的整洁感，也要保证 `m15_implant_usage` 永远在线、永远完整。

**代价：** 年约 4,700 条 × 15 年 = 70,500 条，45 年累计约 21 万条。数据量并不大（每行约 500 字节，共约 100MB），完全可以长期在线保存。

**结论：** 植入物追溯的「永久在线」不是设计上的偷懒，而是**法规要求的时间跨度决定的**。这一点也解释了为什么它必须与 M15-06 消耗记录分开 —— 两者归档策略完全不同。

```python
async def _detect_unregistered(stat_date: str = None):
    """扫描消耗有植入但无追溯记录的情况。"""
    from sqlalchemy import text

    if stat_date:
        target = datetime.strptime(stat_date, "%Y-%m-%d").date()
    else:
        target = date.today() - timedelta(days=1)

    async with get_session() as db:
        # ① 查找游离的植入物消耗
        sql = text(
            """
            INSERT INTO m15_implant_unregistered (
                consume_item_id, consume_id, consume_no, patient_id, patient_name,
                material_code, material_name, batch_no, serial_no, qty,
                consumed_at, schedule_id, schedule_no,
                alert_level, days_pending, detected_at, resolve_status
            )
            SELECT ci.id, c.id, c.consume_no, c.patient_id, c.patient_name,
                   ci.material_code, ci.material_name, ci.batch_no, ci.serial_no, ci.qty,
                   c.created_at, c.schedule_id, c.schedule_no,
                   CASE
                     WHEN c.created_at < NOW() - INTERVAL '7 days' THEN 2
                     ELSE 1
                   END AS alert_level,
                   EXTRACT(DAY FROM NOW() - c.created_at)::INT AS days_pending,
                   NOW(), 'OPEN'
            FROM m15_or_consume_item ci
            JOIN m15_or_consume c ON c.id = ci.consume_id
            LEFT JOIN m15_implant_usage u
                   ON u.consume_item_id = ci.id AND u.is_deleted = FALSE
            LEFT JOIN m15_implant_unregistered r
                   ON r.consume_item_id = ci.id AND r.is_deleted = FALSE
            WHERE ci.is_implant = TRUE
              AND u.id IS NULL
              AND r.id IS NULL
              AND ci.is_deleted = FALSE
              AND c.created_at < NOW() - INTERVAL '24 hours'
              AND c.created_at >= :d0 AND c.created_at < :d1
            """
        )
        d0 = datetime.combine(target, datetime.min.time())
        d1 = d0 + timedelta(days=1)
        result = await db.execute(sql, {"d0": d0, "d1": d1})
        inserted = result.rowcount or 0

        logger.info(
            "unregistered detected",
            extra={
                "module": "M15-07",
                "action": "detect_unregistered",
                "date": str(target),
                "inserted": inserted,
            },
        )

async def _generate_followup(recall_id: int):
    """按召回级别生成随访计划。"""
    from sqlalchemy import select

    from app.clients.followup_client import FollowupClient
    from app.models.m15.implant import M15ImplantRecall, M15ImplantRecallItem

    async with get_session() as db:
        recall = await db.get(M15ImplantRecall, recall_id)
        if recall is None:
            return

        days_map = {
            "LEVEL_1": [1, 7, 14, 21, 28],
            "LEVEL_2": [7, 14, 30],
            "LEVEL_3": [14],

async def _retry_compensation():
    """处理到期的补偿任务。"""
    from sqlalchemy import text

    async with get_session() as db:
        sql = text(
            """
            SELECT id, biz_type, source_id, retry_count
            FROM m15_recall_compensation
            WHERE status = 'PENDING'
              AND next_retry_at <= NOW()
              AND retry_count < 10
            ORDER BY next_retry_at ASC
            LIMIT 100
            """
        )
        rows = (await db.execute(sql)).fetchall()

        for row in rows:
            try:
                if row.biz_type == "FOLLOWUP":
                    await _generate_followup(row.source_id)
                # 成功
                await db.execute(
                    text(
                        "UPDATE m15_recall_compensation "
                        "SET status = 'SUCCESS', resolved_at = NOW(), updated_at = NOW() "
                        "WHERE id = :id"
                    ),
                    {"id": row.id},
                )
            except Exception as ex:
                retry = row.retry_count + 1
                if retry >= 10:
                    await db.execute(
                        text(
                            "UPDATE m15_recall_compensation "
                            "SET status = 'FAILED', retry_count = :r, "
                            "last_error = :err, updated_at = NOW() WHERE id = :id"
                        ),
                        {"r": retry, "err": str(ex)[:500], "id": row.id},
                    )
                else:
                    delay_min = min(600 * (2 ** retry), 21600)
                    await db.execute(
                        text(
                            "UPDATE m15_recall_compensation "
                            "SET retry_count = :r, last_error = :err, "
                            "next_retry_at = NOW() + (:d || ' seconds')::INTERVAL, "
                            "updated_at = NOW() WHERE id = :id"
                        ),
                        {"r": retry, "err": str(ex)[:500], "d": delay_min, "id": row.id},
                    )

async def _daily_stat(stat_date: str = None):
    """计算并保存每日追溯统计。"""
    from sqlalchemy import text

    if stat_date:
        target = datetime.strptime(stat_date, "%Y-%m-%d").date()
    else:
        target = date.today() - timedelta(days=1)

    async with get_session() as db:
        sql = text(
            """
            INSERT INTO m15_implant_daily_stat (
                stat_date, total_usage, registered_count, pending_count,
                complete_count, complete_rate, unregistered_count,
                recall_count, adverse_count, computed_at
            )
            SELECT
                :d,
                COUNT(*) AS total_usage,
                COUNT(*) FILTER (WHERE status IN ('REGISTERED','FOLLOWED')) AS registered_count,
                COUNT(*) FILTER (WHERE status = 'PENDING') AS pending_count,
                COUNT(*) FILTER (WHERE status IN ('REGISTERED','FOLLOWED')
                    AND patient_id IS NOT NULL AND material_code IS NOT NULL
                    AND implant_site IS NOT NULL AND implanted_at IS NOT NULL
                    AND surgeon_id IS NOT NULL) AS complete_count,
                CASE WHEN COUNT(*) = 0 THEN 0
                     ELSE ROUND(COUNT(*) FILTER (WHERE status IN ('REGISTERED','FOLLOWED')
                        AND patient_id IS NOT NULL AND material_code IS NOT NULL
                        AND implant_site IS NOT NULL AND implanted_at IS NOT NULL
                        AND surgeon_id IS NOT NULL)::NUMERIC / COUNT(*) * 100, 2)
                END AS complete_rate,
                (SELECT COUNT(*) FROM m15_implant_unregistered
                  WHERE resolve_status = 'OPEN' AND is_deleted = FALSE) AS unregistered_count,
                (SELECT COUNT(*) FROM m15_implant_recall
                  WHERE recall_status NOT IN ('CLOSED','REJECTED') AND is_deleted = FALSE)
                  AS recall_count,
                (SELECT COUNT(*) FROM m15_implant_adverse
                  WHERE DATE(reported_at) = :d AND is_deleted = FALSE) AS adverse_count,
                NOW()
            FROM m15_implant_usage
            WHERE DATE(implanted_at) = :d AND is_deleted = FALSE
            ON CONFLICT (stat_date) DO UPDATE SET
                total_usage = EXCLUDED.total_usage,
                registered_count = EXCLUDED.registered_count,
                pending_count = EXCLUDED.pending_count,
                complete_count = EXCLUDED.complete_count,
                complete_rate = EXCLUDED.complete_rate,
                unregistered_count = EXCLUDED.unregistered_count,
                recall_count = EXCLUDED.recall_count,
                adverse_count = EXCLUDED.adverse_count,
                computed_at = NOW()
            """
        )
        await db.execute(sql, {"d": target})
```

### 9.3 数据权限

```python
"""M15-07 数据权限注入。"""

from typing import Tuple

from sqlalchemy import false

from app.models.m15.implant import M15ImplantUsage


def resolve_implant_scope(user) -> Tuple[str, str]:
    """解析数据权限作用域。

    返回 (scope_type, scope_name)。
    """
    if user.has_permission("m15:implant:all"):
        return ("ALL", "全部")
    if user.has_permission("m15:implant:dept") and user.dept_id:
        return ("DEPT", "本科室")
    if user.has_permission("m15:implant:self"):
        return ("SELF", "本人")
    return ("NONE", "无权限")


def apply_implant_scope(stmt, user):
    """给查询语句注入数据权限条件。"""
    if user.has_permission("m15:implant:all"):
        return stmt

    if user.has_permission("m15:implant:dept") and user.dept_id:
        # 按主刀科室过滤（植入记录归属主刀的科室）
        return stmt.where(M15ImplantUsage.surgeon_dept_id == user.dept_id)

    if user.has_permission("m15:implant:self"):
        return stmt.where(M15ImplantUsage.created_by == user.user_id)

    return stmt.where(false())
```

### 9.4 脱敏规则

| 场景 | 字段 | 规则 | 依据 |
|---|---|---|---|
| 列表页 | 患者姓名 | 非 `m15:implant:pii` 用户显示「张*明」 | 最小必要 |
| 详情页 | 患者姓名 | 同上 | — |
| 召回通知页 | 联系电话 | 非 `m15:implant:recall` 用户显示「138****5678」 | — |
| 导出 | 患者姓名 | 非 `pii` 用户导出时脱敏 | 防止数据外流 |
| 患者自助查询 | 全部 | 只能查自己 | 患者 ID 来自登录态 |
| 追溯查询 | 身份证号 | 一律不返回 | 不需要 |

**为什么姓氏保留：** 追溯专员与手术医生需要用姓名做人工核对（「我记得是这位老太太」）。完全隐藏会降低核对效率，只保留姓即可满足核对需求。

**四条敏感参数的政策来源与篡改后果：**

| 参数 | 政策来源 | 篡改后果 |
|---|---|---|
| `REGISTER_TIMEOUT_HOURS` | 植入物追溯制度 | 调大 → 补录窗口过长，追溯断链长期不被发现；调小 → 正常术中补录被误报，告警泛滥 |

| `LEVEL_2_DEADLINE_HOURS` | 同上 | 调大 → 违反 48 小时法定时限 |
| `LEVEL_3_DEADLINE_HOURS` | 同上 | 调大 → 违反 72 小时法定时限 |

## 附录 D：术语表

| 术语 | 说明 |
|---|---|
| 植入物 | 通过手术或介入操作留置在人体内 30 日以上的医疗器械 |
| UDI（Unique Device Identification） | 医疗器械唯一标识，由 DI（产品标识）与 PI（生产标识）组成 |
| UDI-DI | 器械唯一标识中的产品标识部分，标识到「型号规格」层级 |
| UDI-PI | 生产标识，含批号、序列号、生产日期、有效期 |
| 批号（Batch No） | 同一生产批次的标识，一批产品可有多个序列号 |
| 序列号（Serial No） | 单件产品的唯一标识，一物一码 |
| 正向追溯 | 从批号/序列号查到使用该批次的患者 |
| 反向追溯 | 从患者查到其植入的全部器械 |
| 中间追溯 | 从供应商/注册证查到批次与患者 |
| 一级召回 | 使用该器械可能引起严重健康危害的召回 |
| 二级召回 | 使用该器械可能引起暂时的或可逆的健康危害的召回 |
| 三级召回 | 使用该器械一般不会引起危害，但仍需召回的召回 |
| 不良事件 | 已上市的医疗器械在正常使用情况下发生的，导致或可能导致人体伤害的各种有害事件 |
| 严重伤害 | 危及生命、导致身体结构或功能永久性损伤、需要药物或手术治疗的事件 |
| MRI 兼容性 | 器械在磁共振成像环境中的安全性，分兼容、条件兼容、不兼容 |
| 手术台次（Schedule） | 手术排程中的一次手术安排，含手术间、时间、人员 |
| 消耗记录（Consume） | 手术室实际使用耗材的记录，是计费与追溯的来源 |
| 追溯完整率 | 信息完整的植入使用记录占应登记记录的百分比 |
| 召回演练 | 定期模拟召回流程，验证响应能力而不产生真实通知 |
| 召回截止时间 | 按召回级别计算的通知时限截止时刻 |
