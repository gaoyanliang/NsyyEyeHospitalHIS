**设计说明：**

| 决策 | 内容 | 理由 |
|---|---|---|
| 无物理外键 | `stock_id` / `material_code` 均为逻辑引用 | 与 M15-01 一致；跨子模块写入加锁影响并发；库存表可能归档重建 |
| 名称快照 | `m15_alloc_lock` 冗余 `material_name` / `batch_no` / `expiry_date` | 库存行被调整或归档后，锁定记录仍能说明「当时锁的是什么」 |
| 序列号数组 | `serial_nos` 用 JSONB 数组 | 一次锁定 1~10 个序列号，拆表需额外 JOIN 且永远整体读写 |
| 策略作用域 | `scope` + `target_id` / `target_code` 双列 | `WAREHOUSE`/`MATERIAL_CATEGORY` 用 `target_id`，`MATERIAL` 用 `target_code`（耗材编码非数字） |
| 日志分区 | `m15_udi_log` 按月 RANGE 分区 | 年约 40 万条，查询以时间范围为主；日志无跨年唯一约束，可自由分区 |
| 幂等键 | `m15_alloc_lock.idempotency_key` 部分唯一 | 上游重试导致的重复分配必须被拦住，否则同一批物资被锁两次 |

### 4.2 表：`m15_alloc_policy`（分配策略表）

**用途：** 定义分配引擎在什么范围内使用什么策略（FEFO/FIFO/LIFO）、是否允许跨批、距有效期多少天禁止出库。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |
| scope | VARCHAR(24) | N | — | 作用域：GLOBAL / WAREHOUSE / MATERIAL_CATEGORY / MATERIAL |
| target_id | BIGINT | Y | NULL | 作用域对象 ID（WAREHOUSE=仓库 ID，MATERIAL_CATEGORY=分类 ID，GLOBAL=0） |
| target_code | VARCHAR(64) | Y | NULL | 作用域对象编码（MATERIAL 用耗材编码；其余 NULL） |
| target_name | VARCHAR(200) | Y | NULL | 作用域对象名称快照 |
| strategy | VARCHAR(16) | N | 'FEFO' | 分配策略：FEFO / FIFO / LIFO |
| allow_split | BOOLEAN | Y | NULL | 是否允许跨批；NULL 表示按耗材 `is_serial_managed` 推导 |
| allow_partial | BOOLEAN | N | FALSE | 是否允许部分满足 |
| forbid_days | SMALLINT | N | 30 | 距有效期不足该天数禁止出库（0 = 不禁用） |
| priority | SMALLINT | N | 100 | 同一作用域内的策略排序（数字大者优先，用于未来多策略） |
| is_active | BOOLEAN | N | TRUE | 是否生效 |
| effective_at | TIMESTAMP | N | now() | 生效时刻（可预约未来） |
| expire_at | TIMESTAMP | Y | NULL | 失效时刻（NULL = 长期） |
| change_reason | VARCHAR(500) | Y | NULL | 变更原因（≥20 字） |
| remark | VARCHAR(500) | Y | NULL | 备注 |
| version | INTEGER | N | 1 | 乐观锁 |
| created_by | BIGINT | N | — | 创建人 |
| created_at | TIMESTAMP | N | now() | 创建时间 |
| updated_by | BIGINT | Y | NULL | 更新人 |
| updated_at | TIMESTAMP | N | now() | 更新时间 |
| is_deleted | BOOLEAN | N | FALSE | 逻辑删除 |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| pk_m15_alloc_policy | PRIMARY | id | 主键 |
| uk_m15_alloc_policy_scope | UNIQUE | scope, COALESCE(target_id, 0), COALESCE(target_code, '') WHERE is_active = TRUE AND is_deleted = FALSE | 同作用域同对象只允许一条生效策略 |
| idx_m15_alloc_policy_scope | NORMAL | scope, is_active | 按作用域列表查询 |
| idx_m15_alloc_policy_effective | NORMAL | effective_at, expire_at | 生效时间段查询 |

**约束说明：**

```sql
-- 作用域枚举
ALTER TABLE m15_alloc_policy ADD CONSTRAINT ck_m15_alloc_policy_scope
  CHECK (scope IN ('GLOBAL', 'WAREHOUSE', 'MATERIAL_CATEGORY', 'MATERIAL'));

-- 分配策略枚举
ALTER TABLE m15_alloc_policy ADD CONSTRAINT ck_m15_alloc_policy_strategy
  CHECK (strategy IN ('FEFO', 'FIFO', 'LIFO'));

-- 禁止出库天数 0~180
ALTER TABLE m15_alloc_policy ADD CONSTRAINT ck_m15_alloc_policy_forbid_days
  CHECK (forbid_days >= 0 AND forbid_days <= 180);

-- 优先级 1~999
ALTER TABLE m15_alloc_policy ADD CONSTRAINT ck_m15_alloc_policy_priority
  CHECK (priority >= 1 AND priority <= 999);

-- GLOBAL 作用域必须 target_id = 0 且 target_code 为空
ALTER TABLE m15_alloc_policy ADD CONSTRAINT ck_m15_alloc_policy_global
  CHECK (scope <> 'GLOBAL' OR (COALESCE(target_id, 0) = 0 AND target_code IS NULL));

-- WAREHOUSE / MATERIAL_CATEGORY 必须有 target_id
ALTER TABLE m15_alloc_policy ADD CONSTRAINT ck_m15_alloc_policy_target_id
  CHECK (scope NOT IN ('WAREHOUSE', 'MATERIAL_CATEGORY') OR target_id IS NOT NULL);

-- MATERIAL 作用域必须有 target_code
ALTER TABLE m15_alloc_policy ADD CONSTRAINT ck_m15_alloc_policy_target_code
  CHECK (scope <> 'MATERIAL' OR target_code IS NOT NULL);

-- 生效早于失效
ALTER TABLE m15_alloc_policy ADD CONSTRAINT ck_m15_alloc_policy_time
  CHECK (expire_at IS NULL OR expire_at > effective_at);

-- 停用必须有原因（change_reason）
ALTER TABLE m15_alloc_policy ADD CONSTRAINT ck_m15_alloc_policy_active
  CHECK (is_active = TRUE OR change_reason IS NOT NULL);

-- 版本号非负
ALTER TABLE m15_alloc_policy ADD CONSTRAINT ck_m15_alloc_policy_version
  CHECK (version >= 1);

COMMENT ON TABLE m15_alloc_policy IS '耗材分配策略表：定义不同作用域下的批次分配规则';
COMMENT ON COLUMN m15_alloc_policy.scope IS '作用域：GLOBAL 全院 / WAREHOUSE 仓库 / MATERIAL_CATEGORY 分类 / MATERIAL 单耗材';
COMMENT ON COLUMN m15_alloc_policy.forbid_days IS '距有效期不足该天数时禁止出库，0 表示不禁用';
COMMENT ON COLUMN m15_alloc_policy.allow_split IS '是否允许跨批；NULL 时按耗材 is_serial_managed 推导';
```

**状态机：**

```
┌────────────┐  停用（is_active=FALSE）  ┌───────────────┐
│  ACTIVE    │──────────────────────►│  INACTIVE     │
│ (生效中)    │◄──────────────────────│ (已停用)       │
└────────────┘  重新启用               └───────────────┘

  预约生效：effective_at > now() 时为 ACTIVE 但尚未参与解析
```

**量级估算：**

| 项 | 数值 |
|---|---|
| 行数 | 约 80 行（全院 1 + 仓库 7 + 分类 12 + 耗材 60） |
| 年增长 | 约 10 行 |
| 单行大小 | 约 600 B |
| 数据量 | 约 50 KB |

**分区：** 不分区。

**设计要点：**

1. **`allow_split` 允许 NULL**：NULL 表示「继承推导规则」（序列号管理 → FALSE，其余 → TRUE）。若强制填布尔值，运维每加一个耗材都要想一次，而 95% 的情况是「按默认」，允许 NULL 就把决策负担降到 5%。
2. **`target_id` 与 `target_code` 双列**：仓库和分类有数字 ID，耗材用字符串编码（`IOL-SN60WF-2100`）。为了统一一张表，用双列 + CHECK 约束区分，比拆两张表更简单。
3. **唯一索引必须 `COALESCE`**：`GLOBAL` 的 `target_id` 是 NULL，PG 认为 NULL 互不相等，不加 `COALESCE` 可以插入无数条 GLOBAL 策略，取「第一条」时会时对时错。
4. **`is_active` + `effective_at` 双控**：停用是立即生效的（`is_active=FALSE`），而切换策略可以预约（`effective_at`）。两个维度分开，避免「明天生效的新策略今天就生效了」。
5. **`change_reason` 在停用时必填**：策略停用意味着分配规则变了，一年后有人问「为什么 11 月 FEFO 失效了」，有原因可查。

### 4.3 表：`m15_alloc_lock`（分配锁定记录表）

**用途：** 记录每一次分配锁定的详细内容，是「谁在什么时候把哪些批次哪些序列号锁给了哪个业务对象」的完整台账。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |
| lock_no | VARCHAR(32) | N | — | 锁定流水号（LK+YYYYMMDD+6 位） |
| stock_id | BIGINT | N | — | 库存行 ID（m15_stock.id，逻辑引用） |
| warehouse_id | BIGINT | N | — | 仓库 ID |
| warehouse_name | VARCHAR(100) | Y | NULL | 仓库名称快照 |
| location_id | BIGINT | Y | NULL | 库位 ID |
| location_code | VARCHAR(64) | Y | NULL | 库位编码快照 |
| material_code | VARCHAR(32) | N | — | 耗材编码（逻辑引用 mdm_material） |
| material_name | VARCHAR(200) | Y | NULL | 耗材名称快照 |
| spec | VARCHAR(200) | Y | NULL | 规格快照 |
| batch_no | VARCHAR(64) | Y | NULL | 批号（非批次管理为 NULL） |
| expiry_date | DATE | Y | NULL | 有效期快照 |
| qty | NUMERIC(12,4) | N | — | 锁定数量 |
| serial_nos | JSONB | Y | NULL | 锁定的序列号数组（序列号管理时非空） |
| unit_cost | NUMERIC(14,4) | Y | NULL | 成本单价快照 |
| amount | NUMERIC(16,4) | Y | NULL | 锁定金额 = qty × unit_cost |
| strategy_used | VARCHAR(16) | Y | NULL | 本次分配采用的策略 |
| biz_type | VARCHAR(24) | N | — | 业务类型：SCHEDULE 台次 / ISSUE 出库 / CONSUME 消耗 / BATCH 批量 / PREVIEW 试算（不落库） |
| biz_id | BIGINT | Y | NULL | 业务对象 ID（台次 ID 等） |
| biz_no | VARCHAR(64) | N | — | 业务对象编号（台次号等） |
| idempotency_key | VARCHAR(128) | Y | NULL | 幂等键 |
| status | VARCHAR(16) | N | 'LOCKED' | 状态：LOCKED / RELEASED / CONSUMED |
| released_at | TIMESTAMP | Y | NULL | 释放时刻 |
| released_by | BIGINT | Y | NULL | 释放人 |
| release_reason | VARCHAR(200) | Y | NULL | 释放原因 |
| operator_id | BIGINT | N | — | 操作人 |
| operator_name | VARCHAR(64) | Y | NULL | 操作人姓名快照 |
| remark | VARCHAR(500) | Y | NULL | 备注 |
| created_at | TIMESTAMP | N | now() | 创建时间 |
| updated_at | TIMESTAMP | N | now() | 更新时间 |
| is_deleted | BOOLEAN | N | FALSE | 逻辑删除 |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| pk_m15_alloc_lock | PRIMARY | id | 主键 |
| uk_m15_alloc_lock_no | UNIQUE | lock_no WHERE is_deleted = FALSE | 锁定流水号唯一 |
| **uk_m15_alloc_lock_idem** | UNIQUE | idempotency_key WHERE idempotency_key IS NOT NULL AND is_deleted = FALSE | 幂等键唯一（防重复锁定） |
| idx_m15_alloc_lock_biz | NORMAL | biz_type, biz_no, status | 按业务对象查锁定 |
| **idx_m15_alloc_lock_active** | 部分 | stock_id WHERE status = 'LOCKED' AND is_deleted = FALSE | 在途锁定（通常仅数十条） |
| idx_m15_alloc_lock_stock | NORMAL | stock_id, created_at DESC | 某库存行的锁定历史 |
| idx_m15_alloc_lock_operator | NORMAL | operator_id, created_at DESC | 按操作人查 |
| idx_m15_alloc_lock_created | NORMAL | created_at DESC | 时间倒序列表 |

**约束说明：**

```sql
-- 状态枚举
ALTER TABLE m15_alloc_lock ADD CONSTRAINT ck_m15_alloc_lock_status
  CHECK (status IN ('LOCKED', 'RELEASED', 'CONSUMED'));

-- 业务类型枚举
ALTER TABLE m15_alloc_lock ADD CONSTRAINT ck_m15_alloc_lock_biz_type
  CHECK (biz_type IN ('SCHEDULE', 'ISSUE', 'CONSUME', 'BATCH', 'PREVIEW'));

-- 分配策略枚举
ALTER TABLE m15_alloc_lock ADD CONSTRAINT ck_m15_alloc_lock_strategy
  CHECK (strategy_used IS NULL OR strategy_used IN ('FEFO', 'FIFO', 'LIFO'));

-- 数量必须为正（方向由方向字段表达，本次无方向字段）
ALTER TABLE m15_alloc_lock ADD CONSTRAINT ck_m15_alloc_lock_qty
  CHECK (qty > 0);

-- 金额自洽
ALTER TABLE m15_alloc_lock ADD CONSTRAINT ck_m15_alloc_lock_amount
  CHECK (amount IS NULL OR unit_cost IS NULL OR ABS(amount - ROUND(qty * unit_cost, 4)) < 0.0001);

-- 已释放必须有释放时刻与原因
ALTER TABLE m15_alloc_lock ADD CONSTRAINT ck_m15_alloc_lock_released
  CHECK (status <> 'RELEASED' OR (released_at IS NOT NULL AND release_reason IS NOT NULL));

-- 未释放不得有释放信息
ALTER TABLE m15_alloc_lock ADD CONSTRAINT ck_m15_alloc_lock_not_released
  CHECK (status = 'RELEASED' OR (released_at IS NULL AND release_reason IS NULL));

-- 流水号格式
ALTER TABLE m15_alloc_lock ADD CONSTRAINT ck_m15_alloc_lock_no
  CHECK (lock_no ~ '^LK[0-9]{8}[0-9]{6}$');

-- 序列号管理的耗材必须有序列号
ALTER TABLE m15_alloc_lock ADD CONSTRAINT ck_m15_alloc_lock_serial
  CHECK (serial_nos IS NULL OR jsonb_typeof(serial_nos) = 'array');

-- 批次管理的耗材必须有批号（由服务层校验，此处只做 NOT NULL 兜底除外）

COMMENT ON TABLE m15_alloc_lock IS '耗材分配锁定记录表：记录每次分配锁定的批次、数量与序列号';
COMMENT ON COLUMN m15_alloc_lock.stock_id IS '库存行 ID，逻辑引用 m15_stock.id';
COMMENT ON COLUMN m15_alloc_lock.serial_nos IS '锁定的序列号数组，格式 ["7X2K91"]';
COMMENT ON COLUMN m15_alloc_lock.idempotency_key IS '幂等键，格式 ALLOC:{biz_no}:{material_code}';
COMMENT ON COLUMN m15_alloc_lock.biz_type IS '业务类型：SCHEDULE 台次 / ISSUE 出库 / CONSUME 消耗 / BATCH 批量';
```

**状态机：**

```
┌──────────┐   释放（release）   ┌───────────┐
│  LOCKED  │──────────────────►│ RELEASED  │  终态
│ (已锁定)  │                    │ (已释放)   │
└────┬─────┘                    └───────────┘
     │ 出库确认 / 消耗确认
     ▼
┌──────────┐
│ CONSUMED │  终态
│ (已核销)  │
└──────────┘
```

**量级估算：**

| 项 | 数值 |
|---|---|
| 行数 | 约 110,000 行/年（日均 55 台 × 50 项 = 2,750，但同批合并后约 300 条/日） |
| 年增长 | 约 110,000 行 |
| 单行大小 | 约 700 B |
| 15 年数据量 | 约 165 万行 / 1.15 GB |

**分区：** 不分区。

**设计要点：**

1. **`stock_id` 是核心关联**：锁定记录指向具体的库存行（而非耗材+批次），因为同一批次可能分布在多个库位，锁的是「某库位上的某批货」。
2. **`serial_nos` 用 JSONB 数组而非关联表**：一次锁定通常 1 个序列号（序列号管理耗材天然单件），偶有多件也是 2~5 个。关联表会多一张表、多一次 JOIN，而查询模式永远是「这条锁定锁了哪些序列号」整体读取。
3. **`idempotency_key` 部分唯一是资金安全底线**：上游（M15-04 出库、M15-06 消耗）超时重试时，若无幂等键，同一批物资会被锁两次，`qty_locked` 翻倍，可用库存虚减。
4. **`biz_type` + `biz_id` + `biz_no` 三元组**：业务对象可能是台次（有 ID 和编号）、出库单（有 ID 和编号）。三个都存是因为：按 ID 查最准、按编号查最快（DBA 手工查时只有编号）、`biz_type` 区分不同业务。
5. **`warehouse_name` / `location_code` / `material_name` / `spec` / `expiry_date` / `unit_cost` 全部快照**：锁定记录是「当时的事实」，半年后耗材改名、库位调整、库存行被归档，台账仍要能说清当时锁了什么。
6. **`strategy_used` 记录实际采用的策略**：策略可能后来被改（FEFO → FIFO），历史锁定记录要能说明「当时按什么规则分的」，这是可解释性的一部分。
7. **`unit_cost` / `amount` 用 4 位小数**：人工晶体成本 6,500 元，若用 2 位小数，多次分配累积会产生误差。行级先舍入到 4 位，汇总时再舍入到 2 位。
8. **不分区**：15 年 165 万行、1.15 GB 在单表舒适区；且 `idempotency_key` 与 `lock_no` 都是跨年唯一约束，分区必须加入分区键，会让幂等语义退化为「同年唯一」。**代价**：需在 15 年期满时整体归档到 `m15_alloc_lock_archive`。

| 索引名 | 类型 | 字段 | 说明 |

| pk_m15_udi_rule | PRIMARY | id | 主键 |
| uk_m15_udi_rule_type | UNIQUE | code_type WHERE is_deleted = FALSE | 码制唯一 |

**约束说明：**

```sql
-- 码制枚举
ALTER TABLE m15_udi_rule ADD CONSTRAINT ck_m15_udi_rule_type
  CHECK (code_type IN ('GS1_128', 'GS1_DATAMATRIX', 'HIBC', 'INTERNAL', 'VENDOR_PRIVATE'));

-- 校验算法枚举
ALTER TABLE m15_udi_rule ADD CONSTRAINT ck_m15_udi_rule_check
  CHECK (check_algorithm IS NULL OR check_algorithm IN ('MOD10', 'MOD43', 'NONE'));

-- 优先级 1~999
ALTER TABLE m15_udi_rule ADD CONSTRAINT ck_m15_udi_rule_priority
  CHECK (priority >= 1 AND priority <= 999);

-- 定长配置必须是对象
ALTER TABLE m15_udi_rule ADD CONSTRAINT ck_m15_udi_rule_fixed
  CHECK (fixed_len_ai IS NULL OR jsonb_typeof(fixed_len_ai) = 'object');

-- 变长配置必须是数组
ALTER TABLE m15_udi_rule ADD CONSTRAINT ck_m15_udi_rule_var
  CHECK (var_len_ai IS NULL OR jsonb_typeof(var_len_ai) = 'array');

-- 必填字段必须是数组
ALTER TABLE m15_udi_rule ADD CONSTRAINT ck_m15_udi_rule_required
  CHECK (jsonb_typeof(required_fields) = 'array');

-- GS1 系列必须有定长 AI 与校验算法
ALTER TABLE m15_udi_rule ADD CONSTRAINT ck_m15_udi_rule_gs1
  CHECK (code_type NOT IN ('GS1_128', 'GS1_DATAMATRIX')
         OR (fixed_len_ai IS NOT NULL AND check_algorithm = 'MOD10'));

-- HIBC 必须指定校验算法
ALTER TABLE m15_udi_rule ADD CONSTRAINT ck_m15_udi_rule_hibc
  CHECK (code_type <> 'HIBC' OR check_algorithm = 'MOD43');

COMMENT ON TABLE m15_udi_rule IS 'UDI 码制规则表：配置各码制的识别前缀、解析优先级与必填字段';
COMMENT ON COLUMN m15_udi_rule.priority IS '解析优先级，数字大者优先；启用中的码制优先级必须唯一';
COMMENT ON COLUMN m15_udi_rule.required_fields IS '解析后必须存在的字段列表，缺失时报 1502008';
```

**状态机：**

```
┌───────────┐   停用     ┌────────────┐
│ ENABLED   │──────────►│  DISABLED  │
│ (启用中)   │◄──────────│ (已停用)    │
└───────────┘   启用     └────────────┘

  约束：至少一个码制保持 ENABLED，否则解析引擎无法工作
```

**量级估算：**

| 项 | 数值 |
|---|---|
| 行数 | 5 行（固定） |
| 年增长 | 0~1 行 |
| 单行大小 | 约 1 KB |
| 数据量 | 约 5 KB |

**分区：** 不分区。

**设计要点：**

1. **`priority` 唯一索引只在启用时生效**：停用的码制可以保留历史优先级，启用时要求唯一，避免「两个码制都排第一」的歧义。
2. **`fixed_len_ai` / `var_len_ai` 用 JSONB 而非硬编码**：GS1 的应用标识符会随标准演进新增（如 2024 年新增 AI 723x），硬编码在代码里每次都要改代码发布；存配置则运维可自行添加。
3. **`prefix` 与 `prefix_hex` 双列**：`]C1` 这类前缀含不可见字符，直接在 YAML/JSON 里编辑容易丢失；存十六进制避免编码问题。
4. **CHECK 约束保证 GS1 必须有 MOD10**：GS1 标准强制要求校验位，若某次误把校验算法改成 NONE，伪造码就失去拦截能力。约束把这条写死在数据库层。
5. **`required_fields` 默认 `[]`**：默认不强制任何字段，由管理员按需开启。若默认强制全部字段，厂商条码只要缺一个字段就全部无法解析，上线第一天就会批量报错。

```sql

-- 示例条码长度
ALTER TABLE m15_udi_vendor_rule ADD CONSTRAINT ck_m15_udi_vendor_rule_sample_len
  CHECK (char_length(sample_barcode) >= 4 AND char_length(sample_barcode) <= 256);

-- 匹配顺序正数
ALTER TABLE m15_udi_vendor_rule ADD CONSTRAINT ck_m15_udi_vendor_rule_order
  CHECK (parse_order >= 1);

COMMENT ON TABLE m15_udi_vendor_rule IS '厂商私有码规则表：用于解析非 GS1/HIBC 标准的国产厂商条码';
COMMENT ON COLUMN m15_udi_vendor_rule.pattern IS '完整解析正则，须包含命名分组 di/lot/serial/exp/mfg/qty 中的至少 di';
COMMENT ON COLUMN m15_udi_vendor_rule.sample_barcode IS '示例条码，保存规则时用于验证能匹配成功';
```

**量级估算：**

| 项 | 数值 |
|---|---|
| 行数 | 3~10 行 |
| 年增长 | 1~2 行 |
| 单行大小 | 约 1.2 KB |
| 数据量 | 约 12 KB |

**分区：** 不分区。

**设计要点：**

1. **`pattern` 长度限制 500 字符**：正则越长回溯越深，500 字符以内足以覆盖所有已知厂商格式（爱博诺德 6+6+6、昊海逗号分隔等都在 100 字符内）。
2. **`sample_barcode` 必填**：保存规则时立刻用示例条码测一次，匹配失败直接拒绝保存（`"1502029"`）。没有示例条码的规则 90% 是「我以为是这样写的」，上线后才发现匹配不上。
3. **`prefix_pattern` 与 `pattern` 两级匹配**：先用前缀快速排除（`^AB` 只能匹配爱博诺德），再用完整正则。条码 5 个私码规则 ≠ 全部跑完整正则，减少回溯总量。
4. **`parse_order` 而非 `priority DESC`**：私码规则数量少（3~10 条），按声明顺序遍历最符合直觉；用「大者优先」会让运维每次新增都要考虑调数字。
5. **正则安全**：服务层在保存时拒绝含 `(?{`、`(?R)`、`(*` 等递归/执行构造的 pattern。这些构造在 PostgreSQL 之外（Python `re` 模块）可以造成栈溢出或无限递归。

```sql
ALTER TABLE m15_udi_registry ADD CONSTRAINT ck_m15_udi_registry_sync
  CHECK (source <> 'M01_SYNC' OR sync_at IS NOT NULL);

-- 歧义标记与备注（歧义必须有备注说明冲突耗材）
ALTER TABLE m15_udi_registry ADD CONSTRAINT ck_m15_udi_registry_ambiguous
  CHECK (is_ambiguous = FALSE OR remark IS NOT NULL);

COMMENT ON TABLE m15_udi_registry IS 'UDI-DI 台账表：UDI-DI 与耗材编码的映射，扫码反查耗材的依据';

```

**量级估算：**

| 项 | 数值 |
|---|---|
| 行数 | 约 500 行（84 种应追溯耗材 × 平均 6 个 DI） |
| 年增长 | 约 100 行 |
| 单行大小 | 约 400 B |
| 数据量 | 约 200 KB |

**分区：** 不分区。

**设计要点：**

1. **`uk_m15_udi_registry_primary` 部分唯一是扫码确定性的基石**：若同一个 DI 有两条 PRIMARY 记录，扫码时会随机返回其中一个耗材——今天扫出来是 A 晶体，明天是 B 晶体，护士完全无法信任系统。数据库层拦住这种重复。
2. **`is_ambiguous` 标记而非直接拒绝**：真实场景中确实存在「一个 DI 对应多个耗材」（厂商换包装未换 DI）。此时若直接拒绝录入，这类产品就永远扫码失败；标记为歧义后，扫码时弹窗让护士从候选耗材中选一个，至少能用。
3. **`gtin` 冗余列**：GS1 标准 DI 是纯数字 14 位，用于 Mod-10 校验与外部系统对接（如药监局 UDI 库）。非 GS1 的厂商编码 `gtin` 为 NULL，但保留该列便于统一查询。
4. **`source` 记录来源**：`M01_SYNC` 同步进来的记录在耗材停用时可自动清理；`MANUAL` 录入手工维护的不能自动删（可能 M01-04 数据缺失）。
5. **`status` 与 `is_deleted` 分开**：`DISABLED` 是「暂时不用」（如该 DI 已停产但耗材还有库存），历史记录仍要保留供追溯；`is_deleted` 是「录错了」。
6. **热路径索引 `idx_m15_udi_registry_lookup`**：扫码时 100% 按 DI 精确查，且只关心 ACTIVE 记录。全表 500 行虽小，但这个索引让查询从「扫 500 行索引」变成「命中 1 行」，在 4,820 次/日的扫码频率下更稳定。

```sql

-- 分区示例（由 fn_m15_create_month_partitions 批量创建）
CREATE TABLE IF NOT EXISTS m15_udi_log_p2026m10 PARTITION OF m15_udi_log
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

**设计要点：**

1. **`seq_date` 冗余列而非表达式分区**：PG 12+ 支持 `PARTITION BY RANGE ((occurred_at::date))`，但查询时 `WHERE occurred_at >= ?` 无法走分区裁剪（表达式不是普通列）。冗余 `seq_date` 后分区键是普通列，`WHERE seq_date >= ?` 走裁剪，跨 3 个月查只扫 3 个分区。
2. **`idx_m15_udi_log_failed` 部分索引**：全年 40 万条日志中失败约 1.6 万条（96% 成功率）。未识别清单页面按失败查询，部分索引只装 1.6 万条，查询快 4 倍；且失败记录增长慢，索引维护成本低。
3. **`raw_barcode` 截断 256**：正常条码 ≤128 字符，256 是安全上限。若打印机故障吐出万字乱码，截断防止单行超长拖垮表。
4. **`try_code_types` 记录尝试过程**：解析失败时最有价值的信息是「试了哪些码制都失败了」，没有这个字段，运维只能猜「是不是码制规则配错了」。
5. **`client_ip` 用 INET 类型**：支持 CIDR 匹配（如统计「PDA 扫码成功率」vs「网页扫码成功率」），且可检测异常来源。
6. **只增不改**：日志是审计证据，一旦可修改，「识别率 96%」这个数字就能被人为改高。触发器在数据库层强制。
7. **在线 3 年 + 归档**：识别率统计与问题排查需求集中在近 3 个月；3 年后转入归档表但仍可查（合规要求保存 15 年）。

### E.4 分区自动创建函数

```sql
CREATE OR REPLACE FUNCTION fn_m15_create_month_partitions(
    p_table TEXT,
    p_months INTEGER DEFAULT 3
)
RETURNS INTEGER AS $$
DECLARE
    v_i        INTEGER;
    v_start    DATE;
    v_end      DATE;
    v_name     TEXT;
    v_created  INTEGER := 0;
BEGIN
    FOR v_i IN 0..p_months - 1 LOOP
        v_start := (DATE_TRUNC('month', CURRENT_DATE) + (v_i || ' month')::INTERVAL)::DATE;
        v_end := (v_start + INTERVAL '1 month')::DATE;
        v_name := FORMAT('%s_p%s', p_table, TO_CHAR(v_start, 'YYYYMM'));
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF %I FOR VALUES FROM (%L) TO (%L)',
            v_name, p_table, v_start, v_end
        );
        v_created := v_created + 1;
    END LOOP;
    RETURN v_created;
END;
$$ LANGUAGE plpgsql;

-- 每月 25 日 02:00 预建未来 3 个月分区
SELECT cron.schedule(
    'm15_udi_log_partition',
    '0 2 25 * *',
    $$SELECT fn_m15_create_month_partitions('m15_udi_log', 3)$$
);
```

**不预建分区的后果**：PostgreSQL 写入无匹配分区时报 `no partition of relation "m15_udi_log" found for row`。若发生在 11 月 1 日 08:00 手术开始前的第一次扫码，护士无法扫码入库，只能手工录入——而手工录入序列号错一位，追溯链路就断了。

### E.5 上线前运维准备

| 序号 | 项目 | 优先级 |
|---|---|---|
| 1 | 确认 `pg_trgm` 扩展可用（需超级用户） | 🔴 |
| 2 | 预置 5 条码制规则（GS1-128 / GS1 DataMatrix / HIBC / 院内码 / 私有码） | 🔴 |
| 3 | 配置已知厂商私有码规则并用真实条码验证 | 🔴 |
| 4 | 从 M01-04 全量同步 UDI-DI 台账（约 500 条）并核对覆盖率 100% | 🔴🔴 |
| 5 | 配置全院默认策略（FEFO + forbid_days=30） | 🔴 |
| 6 | 为高值耗材配置更严格的 forbid_days（人工晶体建议 30，粘弹剂 15） | 🟡 |
| 7 | 注册分区自动创建任务并验证 | 🔴 |
| 8 | 部署扫码枪并实测识别率（要求 ≥95%） | 🔴🔴 |
| 9 | 培训手术室护士使用扫码验证页 | 🟡 |
| 10 | 培训运维使用 UDI 规则测试工具排查识别失败 | 🟡 |

**第 4 项**：若 DI 台账覆盖率不足，扫码时大量条码会报 `"1502010"`（无法识别），护士只能手工录入。**上线前必须实测：抽取 50 个常用耗材的真实条码，全部扫码识别成功的比例必须 100%**。

**第 8 项**：低端扫码枪识别 DataMatrix 的成功率约 60%，护士扫 5 次才成功 3 次，会直接放弃使用。要求上线前用真实条码实测识别率 ≥95%，不足则更换设备。
