**设计说明：**

| 决策 | 内容 | 理由 |
|---|---|---|
| 无物理外键 | 全部引用为逻辑引用 | 与 M15 其他子模块一致；`m15_or_consume_item` 属 M15-06，加外键会让归档与分区分批迁移困难 |
| 永久保存 | `m15_implant_usage` 不设归档与删除 | 人工晶体无有效期即终身可追溯（《医疗器械监督管理条例》第 45 条：植入类记录不少于有效期届满后 5 年，无有效期则为永久） |
| 名称快照 | 冗余 `patient_name`/`material_name`/`spec`/`brand`/`surgeon_name` | 患者改名、耗材改名、医生调岗后，10 年后仍要能说清「当时是谁、装的什么」 |
| 注册证状态快照 | `registration_no` + `registration_status` + `registration_expire_date` | M01-04 注册证可能被更换或吊销，历史记录要能还原「植入当时注册证是否有效」 |
| MRI 信息快照 | `mri_compatible` / `mri_condition` | 患者 20 年后做 MRI，需从本表直接回答，不能依赖 M01-04 当前状态（产品可能已停产下线） |
| 通知与召回明细分离 | `m15_implant_notify` 独立成表 | 一次召回一人可能多渠道多轮通知（短信失败改电话、电话未通改邮寄），逐次留痕 |
| 随访独立成表 | `m15_implant_followup` | 一人可能多次随访（5 次），且随访结果要能对比恶化/好转 |
| 未登记告警独立成表 | `m15_implant_unregistered` | 是待办工作项不是档案；有独立升级机制与消解路径 |
| 只增日志 | `m15_implant_log` 触发器禁止 UPDATE/DELETE | 追溯是审计对象，日志被改等于审计链断裂 |
| `m15_implant_daily_stat` 主键为 `stat_date` | 非自增 ID 主键 | 一天一行，`INSERT ... ON CONFLICT (stat_date) DO UPDATE` 幂等 |
| 全表不分区 | 11 表无分区 | 15 年约 21 万条使用记录，单表完全够用；`usage_no`/`recall_no` 是跨年唯一约束，分区会破坏语义 |

### 4.2 表：`m15_implant_usage`（植入物使用记录表）

**约束说明：**

```sql
-- 登记号格式：IMU-YYYY-NNNNNNN
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_no
    CHECK (usage_no ~ '^IMU-[0-9]{4}-[0-9]{7}$');

-- 性别枚举
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_gender
    CHECK (gender IS NULL OR gender IN ('M', 'F', 'U'));

-- 年龄合理范围
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_age
    CHECK (age IS NULL OR (age >= 0 AND age <= 150));

-- 眼别枚举
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_eye_side
    CHECK (eye_side IN ('OD', 'OS', 'NA'));

-- 植入部位枚举
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_implant_site
    CHECK (implant_site IN ('ANTERIOR_CHAMBER', 'CAPSULE', 'CILIARY_SULCUS',
                            'VITREOUS_CAVITY', 'SCLERA', 'CORNEA',
                            'CONJUNCTIVA', 'LACRIMAL_DUCT', 'ORBIT', 'EYELID'));

-- ★ 眼球内植入部位必须明确眼别（不许 NA）
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_single_eye
    CHECK (implant_site NOT IN ('ANTERIOR_CHAMBER', 'CAPSULE', 'CILIARY_SULCUS', 'VITREOUS_CAVITY')
           OR eye_side IN ('OD', 'OS'));

-- 状态枚举
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_status
    CHECK (status IN ('PENDING', 'REGISTERED', 'FOLLOWED', 'CANCELLED'));

-- 来源枚举
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_source
    CHECK (source IN ('M09_SCAN', 'MANUAL', 'CONSUME_AUTO'));

-- 注册证状态枚举
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_reg_status
    CHECK (registration_status IS NULL
           OR registration_status IN ('VALID', 'EXPIRING', 'EXPIRED', 'CANCELLED'));

-- MRI 兼容性枚举
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_mri
    CHECK (mri_compatible IS NULL
           OR mri_compatible IN ('YES', 'NO', 'CONDITIONAL', 'UNKNOWN'));

-- MRI CONDITIONAL 必须有扫描条件
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_mri_cond
    CHECK (mri_compatible <> 'CONDITIONAL'
           OR (mri_condition IS NOT NULL AND char_length(btrim(mri_condition)) >= 5));

-- 数量为正整数
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_qty
    CHECK (qty > 0);

-- 补录来源必须填原因（≥10 字）与附件
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_manual
    CHECK (source <> 'MANUAL'
           OR (register_reason IS NOT NULL AND char_length(btrim(register_reason)) >= 10
               AND attachment_url IS NOT NULL));

-- ★ 补录原因含敏感关键词必须上传附件（防"记不清"敷衍）
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_manual_attach
    CHECK (source <> 'MANUAL' OR register_reason IS NULL
           OR (register_reason NOT LIKE '%记不清%' AND register_reason NOT LIKE '%不详%')
           OR attachment_url IS NOT NULL);

-- 登记后必须有登记人与时间
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_registered
    CHECK (status NOT IN ('REGISTERED', 'FOLLOWED')
           OR (registered_at IS NOT NULL AND registered_by IS NOT NULL));

-- 已随访必须有随访标记
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_followed
    CHECK (status <> 'FOLLOWED' OR registered_at IS NOT NULL);

-- 作废必须有原因、时间、人
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_cancelled
    CHECK (status <> 'CANCELLED'
           OR (cancel_reason IS NOT NULL AND char_length(btrim(cancel_reason)) >= 10
               AND cancelled_at IS NOT NULL AND cancelled_by IS NOT NULL));

-- 植入日期不晚于今天且不早于 1990-01-01
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_date
    CHECK (implanted_at <= CURRENT_DATE AND implanted_at >= DATE '1990-01-01');

-- 一物一码耗材必须有序列号（由应用层判断，DB 层保证植入物必须有批次或序列号之一）
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_trace_key
    CHECK (batch_no IS NOT NULL OR serial_no IS NOT NULL);

-- 幂等键格式
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_idem
    CHECK (idempotency_key IS NULL OR idempotency_key ~ '^IMPLANT:[0-9]+$');

-- 注册证有效期内植入才允许 REGISTERED（EXPIRED/CANCELLED 需走 CANCELLED 或标记异常）
ALTER TABLE m15_implant_usage ADD CONSTRAINT ck_m15_usage_reg_expired
    CHECK (registration_status IS NULL OR registration_status <> 'EXPIRED'
           OR status = 'CANCELLED');

-- ★ 关键：一消耗明细只能有一条使用记录（幂等基石）
CREATE UNIQUE INDEX uk_m15_usage_consume_item
    ON m15_implant_usage (consume_item_id)
    WHERE consume_item_id IS NOT NULL AND is_deleted = FALSE;

-- ★ 关键：幂等键唯一
CREATE UNIQUE INDEX uk_m15_usage_idem
    ON m15_implant_usage (idempotency_key)
    WHERE idempotency_key IS NOT NULL AND is_deleted = FALSE;
```

**状态机：**

```
        M09 扫码 / 手工登记         随访完成
PENDING ──────────────────► REGISTERED ──────► FOLLOWED（终态）
   │                            │
   │           作废              │ 作废
   └──────────► CANCELLED ◄─────┘
                （终态，不物理删除）
```

**为什么 `PENDING` 是常态而非异常：**

M09-05 术中扫码时能拿到的是序列号、批号、UDI，但**植入部位**（囊袋内 / 睫状沟 / 前房）和**实际植入时间**往往要主刀在手术记录里才会明确。所以 M09 扫码后先落 `PENDING`，待 M09-03 手术记录签名或护士补录后转 `REGISTERED`。M15-07 的未登记检测就是盯 `PENDING` 超 24 小时的记录。

**设计要点：**

- `consume_item_id` 部分唯一索引是**幂等基石**：M15-06 消耗确认后会自动尝试生成使用记录，重试或并发时靠这个索引兜底，重复插入直接 `IntegrityError` 捕获后返回已有记录。
- 注册证与 MRI 信息**全部存快照**：这是本表能「永久有效」的关键。M01-04 的产品资料会随产品换代变更，但 20 年后患者来做 MRI 时，医生问的是「当年装的那片是什么、能不能做 MRI」，必须从本表直接回答。
- `ck_m15_usage_reg_expired`：注册证过期后植入的必须走 `CANCELLED`（并记录原因），而不是让一条「注册证过期植入」的记录以 `REGISTERED` 状态存在——那是隐患。
- `ck_m15_usage_manual_attach` 与补录原因关键词检查配合：真实场景中大量补录原因写「时间久了记不清」，等于没有记录。含此类关键词时强制上传合格证或包装照片。

| 单行大小 | 约 1,200 字节（含快照文本） |

| 保留期 | **永久** |

| 45 年累计 | 约 235 MB |

**分区：** 不分区。


**设计要点：**

- **`recall_status` 的 `NOTIFYING` 与 `FOLLOWING` 分开**：通知阶段是「把人找到」，随访阶段是「把人带回医院处理」。合并后无法回答「还有几个人没联系上」这个一级召回最关键的数字。

- **`idx_m15_recall_active` 是出库拦截的性能保障**：M15-04 每次出库都要问「这批货是否在召回中」。活跃召回通常 0~2 条，部分索引后查询 <0.1ms。

**状态机（通知状态）：**

```
PENDING ──发送──► SENT ──对方接收──► DELIVERED ──明确回应──► CONFIRMED
   │
   ├──标记无法联系──► UNREACHABLE
   │
   └──豁免（已取出/已死亡）──► EXEMPT
```

**状态机（随访状态）：**

```
NONE ──召回进入 FOLLOWING──► PENDING ──完成随访──► DONE
                                    ├──患者拒绝──► REFUSED
                                    └──失访──► LOST
```

**设计要点：**

- **`notify_status` 五态不是三态**。`SENT`（消息已发出）≠ `DELIVERED`（对方接收）≠ `CONFIRMED`（明确回应）。一级召回要求 **CONFIRMED 才算完成**——短信平台返回「发送成功」不等于患者看到了。
- **`UNREACHABLE` 与 `EXEMPT` 分开**。前者是「应该通知但联系不上」（需持续跟进、可能上报不良事件监测），后者是「不需要通知」（已取出、已死亡、迁居国外且已书面确认）。合并会让「还有几个人没找到」这个数字失真。
- **`followup_required` 按召回级别自动设定**（LEVEL_1=5 次 / LEVEL_2=3 次 / LEVEL_3=1 次），与详细设计 3.4 一致。
- **`followup_count <= followup_required + 3`** 留 3 次余量：患者改约、医生排班调整都会增加实际随访次数，硬性等于应随访次数会让正常业务被约束。

**辅助函数（症状校验）：**

```sql
CREATE OR REPLACE FUNCTION fn_m15_symptom_ok(p_symptoms JSONB)
RETURNS BOOLEAN AS $$
DECLARE
    v_item TEXT;
BEGIN
    IF jsonb_typeof(p_symptoms) <> 'array' THEN
        RETURN FALSE;
    END IF;
    FOR v_item IN SELECT jsonb_array_elements_text(p_symptoms) LOOP
        IF v_item NOT IN ('BLUR', 'PAIN', 'REDNESS', 'INFLAMMATION', 'NONE') THEN
            RETURN FALSE;
        END IF;
    END LOOP;
    RETURN TRUE;
END;
$$ LANGUAGE plpgsql IMMUTABLE;
```

**设计要点：**

- **随访计划在召回进入 `FOLLOWING` 状态时批量生成**，`plan_date` 按级别推算（一级召回：确认日 +1/+7/+14/+21/+28 天；二级：+7/+14/+30；三级：+14）。
- **`is_adverse` 与 `adverse_id` 联动**：随访中最常见的功能就是「发现不良事件」，直接在随访页登记并关联，避免医生在两处填表。
- **`vision_od` / `vision_os` 用 VARCHAR** 而非数值：视力求值有 `0.8`、`4.9`（五分记录法）、`CF/1m`（数指）、`HM`（手动）、`LP`（光感）、`NLP`（无光感）。强制数值型会让一半的眼科视力记录无法录入。
- **`iop_od` / `iop_os` 用 NUMERIC(5,1)**：眼压是单一数值（mmHg），保留 1 位小数。
- **提前 7 天允许**：患者可能提前来复查，直接按复查结果完成本次随访，不必等到计划日。

```sql
ALTER TABLE m15_implant_adverse ADD CONSTRAINT ck_m15_adverse_deadline
    CHECK (report_deadline IS NULL OR report_deadline = report_date
           + (CASE WHEN is_serious THEN 15 ELSE 30 END));

-- 事件日期不晚于报告日期
ALTER TABLE m15_implant_adverse ADD CONSTRAINT ck_m15_adverse_date_seq
    CHECK (event_date <= report_date);

-- 患者年龄范围
ALTER TABLE m15_implant_adverse ADD CONSTRAINT ck_m15_adverse_age
    CHECK (patient_age IS NULL OR (patient_age >= 0 AND patient_age <= 150));
```

**设计要点：**

- **`ck_m15_adverse_serious_flag`** 把 `severity` 与 `is_serious` 绑死：`is_serious` 是上报时限的分支依据（严重 15 日、一般 30 日），若两者不一致，时限就算错，可能构成「未按时上报」的违法行为。
- **`report_deadline` 由 `report_date` 推算并写入 CHECK**，而不是服务层计算：即使代码有 bug 也不会算出错的时限。
- 眼科的典型不良事件集中在 `ENDOPHTHALMITIS`（眼内炎，白内障术后发生率约 0.05%~0.2%，是最严重的并发症之一）与 `TASS`（中毒性眼前节综合征，多与器械或灌注液残留有关，暴发时涉及同批次耗材）。

**状态机：**

```
PENDING ──通知──► NOTIFIED ──补录──► FIXED（终态）
   │                  │
   │                  ├──忽略（≥20 字原因）──► IGNORED（终态）
   │                  │
   └──────────────────┴──超期未处理──► ESCALATED ──补录或忽略──► FIXED / IGNORED
```

**设计要点：**

- **这张表是「追溯链完整性」的唯一检测器**：植入物消耗了但没登记，就等于该患者体内有一件物品在本系统中「不存在」。召回时无法找到这个患者，不良事件追溯也断链。没有这张表，追溯率 100% 就只是一个自说自话的计算结果（`usage` 表里当然每条都有记录，问题是缺的那些根本没进表）。
- **`uk_m15_ua_consume_item` 唯一**：同一消耗明细只告警一次。定时扫描每天跑，若每次扫描都插一条，一个盲区会变成 30 条告警，通知疲劳后没人处理。
- **`fix_deadline` 落库而非实时算**：扫描任务要按「已超期」筛选并升级，实时计算 `consumed_at + interval` 无法走索引。
- **`usage_id` 记录补录结果**：告警闭环的标志不是「状态改成 FIXED」，而是「真的产生了使用记录」。这个字段让「补录了但补错了」也能被审计发现（使用记录的 `consume_item_id` 必须等于本表的 `consume_item_id`）。
- **`IGNORED` 需要 ≥20 字原因**：这是唯一允许「明知有盲区但不补录」的出口。若是消耗录错了（本来就不是植入物），写清原因后关闭；若无人负责地随手忽略，追溯率指标就被稀释了。
- **`ESCALATED` 而非直接升级字段**：升级本身是一次事件，需要记录时间与对象。用状态而非布尔，是为了在列表页一眼看出「哪些已经吵到主任那里了」。
- **`consumed_by` 用于追责与培训**：盲区集中在某个护士的班上，说明是其操作习惯问题（扫了耗材码但没扫植入物码），需要针对性培训，而不是全院发通知。

|---|---|

| 预期盲区率 | 初始 3%~5%，稳定后 <0.5% |
| 年告警数 | 约 150 条（稳定期） |

```sql
CREATE TABLE m15_implant_log (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    seq_date DATE NOT NULL,
    log_no VARCHAR(32) NOT NULL,

    PRIMARY KEY (id, seq_date)

-- 预建 36 个月分区（示例）
CREATE TABLE IF NOT EXISTS m15_implant_log_p2026m10
    PARTITION OF m15_implant_log
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

**设计要点：**

- **只增不改的理由与 M09/M15 其他日志表一致**：植入物追溯是药监飞检的核心检查项，「这条使用记录是谁在什么时候登记的、有没有被改过」必须能回答。应用层可以保证不写 UPDATE 语句，但挡不住 DBA 手工改库、迁移脚本误操作、其他服务 bug。**数据库级不可变才是真的不可变。**
- **`from_status` / `to_status` 与 `detail_json` 双轨**：状态流转看前两者（可索引、可统计），字段级变更看 `detail_json`（记录改了什么）。
- **`patient_id` / `material_code` / `serial_no` 冗余到日志**：追查「这个患者用过哪些植入物、每次谁操作的」时，只需查日志一张表，不必回表 JOIN 业务表（业务表可能已归档）。
- **`seq_date` 冗余而非表达式分区**：PostgreSQL 12+ 支持 `PARTITION BY RANGE ((occurred_at::date))`，但查询 `WHERE occurred_at >= ?` 无法走分区裁剪（表达式不是普通列，规划器不会把 `occurred_at` 的条件推导成 `occurred_at::date` 的条件）。冗余一列后 `WHERE seq_date >= ?` 直接裁剪，跨 3 个月查询只扫 3 个分区而非 36 个。
- **在线保留 6 个月**：日志查询集中在近期（排查问题、飞检抽查近半年记录），更早的日志移入 `m15_implant_log_archive` 归档表仍可查，合规要求不丢。

| 单行大小 | 约 700 字节（含 JSONB） |

| 归档保留 | 永久（法规要求） |

```sql
    CHECK (status <> 'SUCCESS' OR succeeded_at IS NOT NULL);

    CHECK (status NOT IN ('RETRYING', 'FAILED')
           OR (last_error IS NOT NULL AND char_length(btrim(last_error)) >= 5));

    CHECK (status <> 'ABANDONED'
           OR (abandon_reason IS NOT NULL AND char_length(btrim(abandon_reason)) >= 20
               AND abandoned_at IS NOT NULL));
```

**状态机：**

```
PENDING ──重试成功──► SUCCESS（终态）
   │
   ├──重试失败且未达上限──► RETRYING ──更新 next_retry_at ──► PENDING
   │
   ├──重试达上限──► FAILED ──人工干预──► PENDING / ABANDONED
   │
   └──人工放弃（≥20 字原因）──► ABANDONED（终态）
```

**设计要点：**

- **为什么需要这张表而不是 Celery 自带重试**：Celery 的重试在 worker 重启后会丢失（非持久化 broker 或任务已被 ack），而召回通知「必须送达每一位患者」是法定义务，不能因为服务重启就不了了之。落库后，即使 Celery 队列清空，定时任务仍能从表里捞出未完成的补偿继续重试。
- **`payload_json` 存完整请求体**：重试时不重新查库组装请求（业务数据可能已变化，重建的请求与首次失败的请求可能不一致，导致重试结果与幂等冲突）。**重放必须是「原样重放」**。
- **`uk_m15_cmp_biz` 部分唯一**：「同一召回明细的同一通知动作」同时只能有一条待补偿记录。若允许多条，重试时会向患者发多条相同短信——不但打扰患者，还可能在纠纷中被质疑「系统重复发通知导致患者恐慌」。
- **`next_retry_at` 落库 + 指数退避**：1 分钟 → 2 → 4 → 8 ... 上限 2 小时。落库而非内存定时器，服务重启后仍能按时重试。
- **`ABANDONED` 需要 ≥20 字原因**：某些情况下确实无法补偿（患者电话注销 + 地址变更 + 无家属联系方式），但必须写明「尝试过什么方式、结果如何」，否则「放弃」会成为偷懒的出口。
- **`target` 用枚举而非自由文本**：补偿目标有限（6 个系统），枚举让「M03 通知服务的补偿失败率」这类统计成为可能。

**量级估算：**

| 项 | 数值 |
|---|---|
| 年补偿记录数 | 约 500 条（通知失败重试为主） |
| 单行大小 | 约 1.2 KB（含 JSONB 载荷） |
| 年数据量 | 约 600 KB |
| 保留期 | 5 年在线，之后归档 |
| 5 年数据量 | 约 3 MB |

**分区：** 不分区（5 年 2,500 行）。

| `uk_m15_icfg_key` | m15_implant_config | is_deleted = FALSE | 参数唯一（含 COALESCE） | 16 条 |

**部分索引的价值（以 `idx_m15_cmp_due` 为例）：**

| 方案 | 索引大小 | 查询耗时 | 说明 |
|---|---|---|---|
| 无索引 | 0 | 约 15ms | 全表扫描 7,500 行 |
| 普通索引 | 约 900 KB | 约 4ms | 索引树遍历 |
| **部分索引** | **约 2 KB** | **约 0.05ms** | 只含 PENDING（通常 0~5 条） |

补偿重试任务每 5 分钟一次，一年 10.5 万次；15ms 是约 26 分钟 CPU，0.05ms 是约 5 秒。

**分区自动创建函数：**

```sql
CREATE OR REPLACE FUNCTION fn_m15_create_month_partitions(p_table TEXT, p_months INTEGER DEFAULT 3)
RETURNS VOID AS $$
DECLARE
    v_i     INTEGER;
    v_start DATE;
    v_end   DATE;
    v_name  TEXT;
BEGIN
    FOR v_i IN 0..p_months - 1 LOOP
        v_start := (date_trunc('month', CURRENT_DATE) + (v_i || ' month')::INTERVAL)::DATE;
        v_end   := (v_start + INTERVAL '1 month')::DATE;
        v_name  := p_table || '_p' || to_char(v_start, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF %I FOR VALUES FROM (%L) TO (%L)',
            v_name, p_table, v_start, v_end
        );
    END LOOP;
END;
$$ LANGUAGE plpgsql;

-- 每月 25 日 02:00 预建未来 3 个月分区
SELECT cron.schedule(
    'm15_implant_log_partition',
    '0 2 25 * *',
    $$SELECT fn_m15_create_month_partitions('m15_implant_log', 3)$$
);
```

> **不预建分区的后果：** 11 月 1 日第一条日志写入报 `no partition of relation "m15_implant_log" found for row`，追溯操作记录失败，术中扫码登记链路中断。

**第 3、5 项最关键：**

- **第 3 项**：`M01-04` 的 `mdm_material.is_implant` 与 `is_serial_managed` 决定了哪些耗材走追溯流程。若标记遗漏（例如某品牌人工晶体未标 `is_implant`），该耗材的植入记录不入追溯链，药监飞检时「这类植入物为什么没有追溯记录」无法解释。
