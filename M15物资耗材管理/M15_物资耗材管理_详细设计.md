## 1. 模块概述

### 1.1 模块定位

M15 物资耗材管理是眼科医院**高值植入物与手术耗材的唯一实物台账**。它回答四个问题：

1. **有什么** —— 仓库里有多少片人工晶体、多少个手术套包、多少根缝线
2. **是哪一件** —— 这条序列号对应哪一片晶体、哪个批次、哪张注册证
3. **给了谁** —— 这片晶体植入了哪位患者、哪只眼、哪台手术
4. **怎么用掉的** —— 从采购入库到术中消耗的完整链路

### 1.2 为什么 M15 是独立模块

#### 1.2.1 与药品库存平行而非合并

M14 药房药库管理已实现完整的药品库存引擎。M15 与 M14 结构高度相似（都有仓库、库位、批次、流水、盘点），**但两者不能合并**，原因有四：

| 维度 | M14 药品 | M15 耗材 | 差异后果 |
|---|---|---|---|
| 监管体系 | 《药品管理法》《药品经营质量管理规范》 | 《医疗器械监督管理条例》《医疗器械唯一标识系统规则》 | 合规要求不同，飞检检查项不同 |
| 编码体系 | 药品本位码 + 批号 | UDI-DI + 序列号（一物一码） | 耗材需解析 GS1/HIBC/厂商私有四种码制 |
| 效期维度 | 单一有效期 | 有效期 + **灭菌有效期** | 一次性无菌包厂商效期 3 年但灭菌效期仅 6 个月 |
| 追溯方向 | 药品→患者（单向） | 患者↔耗材（**双向**） | 召回时需从耗材反查所有患者 |
| 成本法 | 移动加权平均 | 批次实际成本 | 高值植入物单价 3,000~15,000 元，加权平均会稀释真实成本 |

运维层面合并会导致：一个仓库系统里同时存在"药品批次"与"耗材序列号"两套语义，查询与报表处处需要 `if 是药品 then ... else ...`。

#### 1.2.2 人工晶体与高值植入物的特殊性

眼科医院与综合医院最大的物资差异是**人工晶体（IOL）**：

- 全院年用量约 4,700 片，单价 800~15,000 元
- 同品牌同型号按**球镜度数**细分：−10.00D 到 +40.00D，步长 0.25D 或 0.50D
- 加上散光矫正型（Toric）的柱镜度数，一个品牌型号可衍生出**数百个 SKU**
- 每片晶体有独立序列号，必须一物一码追溯到患者

这决定了 M15 不能是"简化版 M14"，而必须实现**实例级库存管理**。

#### 1.2.3 手术室二级库的特殊地位

综合医院的耗材管理通常止步于"库房出库到科室"。眼科手术的特殊性在于：

- 手术室每日 30~60 台手术，每台需备台 20~50 项耗材
- 备台后未用的耗材**必须当日退回**（否则账实不符）
- 术中实际使用的才计入材料费
- 单片价值过万的晶体，**备进去没用必须知道它现在在哪**

这要求 M15 区分「出库」「备台」「消耗」「退料」「报损」五种状态（详见 3.3）。

### 1.5 与相邻模块的边界

**一句话边界：**

> M01-04 说「有哪些耗材、是不是植入物」；**M15 说「库里有几件、是哪一件、给了谁」**；M09 说「术中用了什么」；M16 说「该收多少钱」。

| 模块 | 边界 |
|---|---|

**关键依赖说明：**

- M15-01 是**所有子模块的共同底座**，任何库存变化都通过它的事务接口
- M15-02 为 M15-04 与 M15-06 提供分配能力（FEFO + 序列号选择）
- M15-03 是库存的**唯一合法入口**（除盘盈外）
- M15-04 是总库到科室的通道，产出二级库库存
- M15-06 是消耗的唯一来源，也是 M15-07 的数据源头
- M15-07 依赖 M15-06 的消耗记录生成追溯链

### 2.3 五条拆分主线

#### 主线一：按「事务边界」分，不按「数据表」分

每个子模块必须对应一个**独立的事务边界**。例如 M15-03「采购与入库」是一个完整事务：从到货登记到验收合格到入库上架，中间任何一步失败都要能回滚到一致状态。

若按表拆（采购表一个子模块、入库表一个子模块），则「入库失败后采购订单状态怎么处理」会成为跨子模块协调问题。

#### 主线二：数量真相只有一处

**只有 M15-01 拥有库存数量**。其他子模块产出的都是**事务意图**，由 M15-01 执行后变成本。这意味着：

- M15-03 的入库单不直接改库存，而是调用 M15-01 的 `POST /stock/inbound`
- M15-04 的出库单不直接改库存，而是调用 `POST /stock/outbound`
- M15-06 的消耗不直接改库存，而是调用 `POST /stock/consume`

这条主线的价值：任何时候库存数字错了，只需查 M15-01 的流水，不需要在 7 个子模块之间找「谁偷偷改了」。

#### 主线三：出库 ≠ 消耗

这是 M15 与 M14 最大的结构差异（详见 3.3）。备台 50 项、实耗 38 项、退回 12 项、报损 0 项——若只有「出库」一个概念，这四种动作混在一张表里，M06-06 的「材料退回率」指标根本无法计算。

#### 主线四：扫码动作与追溯记录分离

M09-05 负责术中扫码**动作**（护士拿扫码枪对准包装），M15-07 负责**使用登记记录**（这次扫码产生了一条永久追溯记录）。

分离理由：扫码发生在手术间（M09 的地盘），追溯查询与召回响应发生在物资科（M15 的地盘）。两边的权限、性能要求、数据保留期都不同。

#### 主线五：合规要求独立成子模块

采购验收（M15-03）、盘点调整（M15-05）、植入物追溯与召回（M15-07）三者的共同点是：**都是飞检必查项**，都有严格的签字与留痕要求，都不能因业务系统故障而简化。

独立后可以给这三个子模块配置更高的可用性与更长的数据保留期。

### 2.4 为什么不拆更多

| 候选子模块 | 不拆的理由 |
|---|---|
| 供应商管理 | 已在 M01-05 维护，M15 只读 |
| 耗材主数据维护 | 已在 M01-04 维护，M15 只读 |
| 效期管理 | 不是独立业务，是 M15-01 台账的一个属性 + M15-02 的一个分配策略 |
| 报损报废 | 仅 3 个接口，并入 M15-06 |
| 成本核算 | 属 M17 财务，M15 只提供成本数据 |
| 报表中心 | 属 M22，M15 只提供统计接口 |

## 3. 核心业务模型

### 3.1 仓库与库位模型

```
仓库（m15_warehouse）
├── CENTRAL          一级总库（唯一）
├── SECONDARY        二级库（科室库房，如手术室库房）
├── OPERATING        手术室库（备台专用）
├── HIGH_VALUE_CABINET 高值柜（人工晶体专柜，双人管理）
├── CONSIGNMENT      寄售库（厂商货物，不计入医院资产）
├── QUARANTINE       待检区（未验收或待退货）
└── VIRTUAL          虚拟库（盘盈盘亏等调整用）
        │
        ▼
库位（m15_location）
├── 区域 zone
├── 货架 shelf
├── 层 level
└── 位 position
```

**为什么必须区分仓库类型：**

不同仓库类型的库存有完全不同的**资产属性**：

| 类型 | 计入资产 | 可出库 | 需盘点 | 说明 |
|---|---|---|---|---|
| CENTRAL | 是 | 是 | 每月 | 医院自有库存主库 |
| SECONDARY | 是 | 是 | 每月 | 已划拨科室，仍是医院资产 |
| OPERATING | 是 | 是 | **每日** | 高值柜需班班交接 |
| HIGH_VALUE_CABINET | 是 | 是 | **每班次** | 人工晶体专柜，双人管理 |
| CONSIGNMENT | **否** | 是 | 每月 | 厂商寄售，用了才付款 |
| QUARANTINE | 是 | **否** | 每月 | 待处理，不能出库 |
| VIRTUAL | 否 | 否 | 否 | 仅用于账务调整 |

若不分类型，财务月报「库存资产总额」会把寄售库存算进去，虚增数百万。

### 3.2 库存数量三要素

任何一条库存台账记录都有三个数量：

| 字段 | 含义 | 说明 |
|---|---|---|
| `qty_on_hand` | 在库数量 | 物理上在这个库位的件数 |
| `qty_locked` | 锁定数量 | 已被某业务占用但尚未出库 |
| `qty_available` | 可用数量 | **生成列** `= qty_on_hand - qty_locked` |

**为什么必须区分锁定与在库：**

手术前一晚备台 50 项，此时耗材物理上还在手术室二级库（`qty_on_hand` 未变），但**不能再被另一台手术领用**（`qty_locked` 增加）。

若只有 `qty_on_hand`，则两台手术同时备台时后一台会分配走前一台已锁定的晶体，实际取货时发现没有了。

`qty_available` 是**生成列**而非应用层计算，保证数据库层面永远不会出现三者不一致。

### 3.3 出库、备台、消耗、退料、报损五态分离

这是 M15 最核心的模型设计。

| 动作 | 触发时点 | 责任角色 | 库存变化 | 财务影响 |
|---|---|---|---|---|
| **出库** | 手术前一晚备台 | 库管员 | 总库 → 二级库 | 无（资产内部转移） |
| **备台** | 手术排程确认后 | 器械护士 | 二级库内**锁定** | 无 |
| **消耗** | 术中实际使用 | 器械护士 | 二级库 → 已用 | **计入材料费** |
| **退料** | 术后未用 | 器械护士 | 已备 → 二级库可用 | 无 |
| **报损** | 发现破损/过期 | 护士长 | 二级库 → 报废 | 计入损耗 |

**为什么不能合并：**

真实场景：某台白内障手术备台 50 项，术中实耗 38 项，术后退回 12 项。

- 若只有「出库」：50 项全部计费，患者多付 12 项的钱
- 若只有「消耗」：不知道哪些备了没用，`材料退回率` 无法统计
- M06-06 的「材料退回率 ≥90%（现状 55%，日均 55 台 × 180 元 → 年多收患者约 360 万元）」这一指标，**完全依赖退料与消耗的分离**

### 3.4 批次与序列号双层粒度

| 粒度 | 适用耗材 | 标识 | 表 |
|---|---|---|---|
| **批次级** | 纱布、缝线、注射器、普通敷料 | 批号 + 效期 | `m15_stock`（`batch_no` 字段） |
| **序列号级** | 人工晶体、青光眼引流阀、玻璃体替代物 | 序列号 + UDI | `m15_stock_batch`（每件一行） |

**为什么需要两层：**

- 若全用序列号：一块纱布也要贴条码逐个录入，500 片纱布出库要写 500 条记录，护士无法接受
- 若全用批次号：一片晶体无法定位到具体哪一片，召回时只能说"这一批的全部召回"，而实际可能只有中间某一片有问题

判定规则来自 M01-04 `mdm_material.is_serial_managed`。

### 3.5 UDI 解析模型

**UDI = DI（产品标识）+ PI（生产标识）**

```
(01)08717648200274(17)261231(10)B240815(21)X2K91
 │                │        │          │
 │                │        │          └─ AI 21 序列号（变长）
 │                │        └─ AI 10 批号（变长）
 │                └─ AI 17 有效期（定长 6 位）
 └─ AI 01 产品标识 DI（定长 14 位，GS1 公司前缀 + 商品码 + 校验位）
```

**定长与变长的区分至关重要：**

- 定长 AI（01/11/17/30）：后面直接跟下一个 AI
- 变长 AI（10/21/240）：后面必须是 FNC1（ASCII 29）或条码结束

若不知道这一点，解析 `(10)B240815(21)X2K91` 时会把批号读成 `B240815(21)X2K91`。

**四种码制：**

| 码制 | 前缀 | 典型厂商 | 特例 |
|---|---|---|---|
| GS1-128 | `]C1` | 爱尔康、博士伦 | 标准 AI 结构 |
| GS1 DataMatrix | `]d2` | 蔡司、强生 | 标准 AI 结构 |
| HIBC | `+` | 部分欧美厂商 | Mod-43 校验 |
| 厂商私有 QR | 无 | 爱博诺德、昊海 | 固定长度拼接或逗号分隔 |

**解析必须分层**：按码制特征识别 → 调用对应解析器 → 按优先级取第一个成功。**不能用一个大正则覆盖四种码制**，否则要么灾难性回溯，要么覆盖不全。

### 3.6 追溯链模型

```
采购订单 (M15-03)
    │
    ▼
到货验收 (M15-03) ── 注册证号 ── 注册证有效期
    │
    ▼
批次入库 (M15-01) ── 批号 + 序列号 + 灭菌效期
    │
    ▼
出库到二级库 (M15-04) ── 领用人 + 时间
    │
    ▼
备台锁定 (M15-06) ── 台次号
    │
    ▼
术中消耗 (M15-06) ── 扫码时间 + 操作护士
    │
    ▼
植入物使用登记 (M15-07) ── 患者 ID + 眼别 + 术者
    │
    ▼
【追溯链完成】患者 ←→ 序列号 ←→ 批号 ←→ 订单 ←→ 供应商
```

**追溯完整性的两个方向：**

- **正向**（耗材→患者）：这批晶体给了哪些患者？—— 召回时用
- **反向**（患者→耗材）：这位患者体内是什么晶体？—— 复查、纠纷举证、MRI 检查前确认时用

### 3.7 盘点与差异归因

盘点流程：

```
① 发起盘点 → ② 冻结库存（写 m15_stocktake_freeze）
                              ↓
③ 盲盘录入（PDA 扫库位，不显示账面数）
                              ↓
④ 生成差异 → ⑤ 强制归因（≥10 字） → ⑥ 分级审批
                              ↓
⑦ 执行调整（写 ADJUST_STOCKTAKE 流水） → ⑧ 解冻
```

**为什么冻结必须落表：**

若只用 Redis 存冻结标记，Redis 重启或过期即解冻，管理员可能误改库存。落表后 `m15_stocktake_freeze` 是数据库级约束，任何库存变更先查此表。

**为什么盲盘：**

若 PDA 显示账面数，盘点员会受引导（"系统说 48 片，我数了 46 片，是不是我数错了"），实际差异被掩盖。

**差异分级审批：**

| 差异率 | 审批层级 |
|---|---|
| < 0.5% | 库管员自审 |
| 0.5%~2% | 耗材科科长 |
| 2%~5% | 科长 + 财务 |
| > 5% | 科长 + 财务 + 分管院长 |

### 3.8 召回响应模型

```
药监通知/厂商通知 → 创建召回单 (m15_implant_recall)
                            ↓
        ┌───────────────────┼────────────────────┐
        ▼                   ▼                    ▼
   按批号检索          按序列号检索         按 DI 型号检索
   (m15_implant_usage)                   
        │                   │                    │
        └───────────────────┴────────────────────┘
                            ▼
                    生成影响明细 (recall_item)
                            ↓
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
        在库未用        已出库未用      已植入患者
        (冻结+退回)     (通知科室)    (通知+随访)
```

**召回时限（法定）：**

| 级别 | 报告时限 | 通知时限 | 说明 |
|---|---|---|---|
| I 级（严重伤害/死亡） | 24 小时 | 24 小时 | 如晶体碎裂可能导致失明 |
| II 级（暂时性伤害） | 24 小时 | 48 小时 | 如包装破损 |
| III 级（不构成伤害） | 48 小时 | 72 小时 | 如标签印刷错误 |

`M15.IMPLANT.RECALL_REPORT_HOURS = 24` 是只读参数（法规要求）。

### 3.9 采购三单匹配模型

```
采购订单 (m15_purchase_order)
    │  订单号、耗材、数量、单价、税率、金额
    │
    ▼
入库单 (m15_inbound)
    │  入库号、关联订单、实收数量
    │
    ▼
发票 (m15_invoice)
    │  发票号、关联入库单、金额、税额
    │
    ▼
【三单匹配】
    ├─ 数量：入库数量 ≤ 订单数量
    ├─ 单价：|发票单价 - 订单单价| ≤ 0.01
    ├─ 金额：|发票不含税 - 入库不含税| ≤ 0.05
    └─ 税额：|发票税额 - 入库税额| ≤ 0.05
```

**容差的依据：**

- 单价 ±0.01：订单存 4 位小数，发票系统只有 2 位
- 金额/税额 ±0.05：发票系统与本单位计算的进位差异

**税额必须逐行先算再汇总**：含税 100 元 13% 单行 `88.50 + 11.50 = 100.00`；若 10 行先汇总再算得 `884.96 + 115.04`，逐行算再汇总得 `885.00 + 115.00`，**差 0.04 元**。长期累积导致三单匹配持续失败。

### 3.10 备台与消耗时序

```
手术前一日 16:00  ── 排程确认事件 m06.schedule.confirmed
                    ↓
                  生成备台单（DRAFT）
                    ↓
手术前一日 17:00  ── 器械护士核对备台单
                    ↓
                  提交备台单（PENDING → READY）
                    ↓
                  调用 M15-04 出库（总库 → 手术室二级库）
                    ↓
手术当日 07:30    ── 器械护士领用（备台单 → IN_USE）
                    ↓
手术中            ── 术中扫码消耗（m15_or_consume）
                    ↓
手术后            ── 未用耗材退回（m15_or_return）
                    ↓
                  备台单 → COMPLETED
                    ↓
                  触发 M16-01 计费（仅消耗部分）
```

**M06-06「材料退回率」的计算：**

```
退回率 = 退料数量 / 备台数量
```

若备台 50 项、消耗 38 项、退回 12 项，则退回率 = 12/50 = 24%——**这是要降低的指标**（退回率高说明备台不精准）。M06-06 中「材料退回率 ≥90%」指的是**备了没用的都要退回，而不是不退回**。

### 4.3 三条数据铁律

#### 铁律一：关键留痕表只增不改

| 表 | 理由 |
|---|---|
| `m15_stock_txn` | 库存流水是账实相符的唯一证据 |
| `m15_udi_log` | 解析日志是识别率 KPI 的原始数据 |
| `m15_implant_log` | 追溯操作日志是飞检证据 |

实现方式：数据库触发器 `fn_m15_txn_readonly()` 等，抛异常阻止 UPDATE/DELETE。**不用应用层保证**，因为应用层可被绕过（DBA 手改、迁移脚本、其他服务 bug）。

#### 铁律二：唯一性用部分索引 + COALESCE

```sql
-- 正确
CREATE UNIQUE INDEX uk_xxx ON t (a, COALESCE(b, 0)) WHERE is_deleted = FALSE;
-- 错误：PostgreSQL 认为 NULL 互不相等，可插入无数条 (a, NULL)
CREATE UNIQUE INDEX uk_xxx ON t (a, b) WHERE is_deleted = FALSE;
```

所有涉及可空列的唯一索引必须用 `COALESCE`。**不用 `NULLS NOT DISTINCT`**，因为它是 PostgreSQL 15+ 特性，部分环境仍为 14。

#### 铁律三：金额与数量必须精确类型 + 行级先舍入

| 字段 | 类型 | 说明 |
|---|---|---|
| 金额 | `NUMERIC(14,4)` | 禁止 FLOAT |
| 数量 | `NUMERIC(14,4)` | 支持小数（如 0.5 卷纱布） |
| 单价 | `NUMERIC(14,4)` | 4 位小数，避免入库价格累积误差 |

**行级先舍入**：`金额 = ROUND(数量 × 单价, 4)`，然后汇总各行。若先汇总数量再乘单价，多次交易后会与逐行计算产生分位差异。

### 4.4 分区策略

| 表 | 分区 | 理由 |
|---|---|---|
| `m15_stock_txn` | 月 RANGE | 年 660 万条，按月份隔离 |
| `m15_udi_log` | 月 RANGE | 年 40 万条，查询集中在近 3 个月 |
| `m15_implant_log` | 月 RANGE | 年 54 万条，同上 |
| 其余 52 张 | 不分区 | 有跨年唯一约束，分区会破坏幂等语义 |

**为什么业务表不能分区：**

`m15_stock` 的唯一键是 `(warehouse_id, location_id, material_code, batch_no)`。若按年分区，唯一索引必须包含分区键，变成「同一批次每年一行」——台账分裂，`qty_on_hand` 也会分散到多个分区，任何数量查询都要聚合全部分区。

## 7. 技术架构与部署

### 7.1 服务拆分

```
┌────────────────────────────────────────────────────────────┐
│                    M15 服务（单体，多模块）                 │
├────────────────────────────────────────────────────────────┤
│  FastAPI 应用（4 个 worker）                               │
│  ├─ /api/v1/m15/*          对外 API                        │
│  └─ /internal/v1/m15/*     内部契约                        │
├────────────────────────────────────────────────────────────┤
│  Celery Worker（2 个并发）                                 │
│  ├─ 消息通知                                               │
│  ├─ 统计计算                                               │
│  └─ 补偿重试                                               │
├────────────────────────────────────────────────────────────┤
│  APScheduler（1 进程）                                     │
│  └─ 定时任务（分区创建、快照、日结）                        │
├────────────────────────────────────────────────────────────┤
│  Redis 7（缓存 + 分布式锁 + 队列）                         │
├────────────────────────────────────────────────────────────┤
│  PostgreSQL 16（主库 + 1 只读副本）                        │
└────────────────────────────────────────────────────────────┘
```

**为什么不拆微服务：**

M15 的七个业务域共享同一个库存台账（M15-01）。若拆成 7 个服务，则每次库存变更都要跨服务调用，事务一致性极难保证。

M15 部署为单体多模块，通过 Python 包结构隔离（`app.modules.m15_01`、`app.modules.m15_02` ...），模块间只通过 Service 层接口调用，不直接访问对方的 Repository。

### 7.2 数据库连接池

| 池 | 用途 | 连接数 |
|---|---|---|
| 默认池 | 业务读写 | 20 |
| 只读池 | 报表、统计查询 | 5 |
| 报表池 | 大批量导出 | 2 |

**只读池的必要性：** 报表查询通常扫描大范围时间区间（如「近一年库存流水」），会占用大量连接。若与业务共用连接池，10 个用户同时查报表即可耗尽 20 个连接，导致扫码入库失败。

## 8. 全局业务规则

### 8.1 库存铁律

| 编号 | 规则 |
|---|---|
| I-01 | 库存数量只能通过 `m15_stock_txn` 流水变更，禁止直接 UPDATE `m15_stock` |
| I-02 | `qty_available` 必须是生成列，不得由应用层写入 |
| I-03 | `qty_on_hand` 不得为负（除虚拟库，且需科长授权） |
| I-04 | `qty_locked` 不得超过 `qty_on_hand` |
| I-05 | 库存冻结期间（盘点）任何变更必须被拒绝 |

### 8.2 批次铁律

| 编号 | 规则 |
|---|---|
| B-01 | 批次管理耗材（`is_batch_managed=TRUE`）入库必填批号 |
| B-02 | 有效期管理耗材（`is_expiry_managed=TRUE`）入库必填有效期 |
| B-03 | 一次性无菌包（`is_sterile=TRUE`）必须填灭菌有效期 |
| B-04 | 实际失效日 = `LEAST(有效期, 灭菌有效期)` |
| B-05 | 已过期批次不得出库（除报废场景） |

### 8.3 序列号铁律

| 编号 | 规则 |
|---|---|
| S-01 | 序列号管理耗材（`is_serial_managed=TRUE`）一物一码，每件一行台账 |
| S-02 | 序列号全局唯一，不允许两个耗材共用同一序列号 |
| S-03 | `USED` 状态是终态，不可撤销（撤销需走医疗流程） |
| S-04 | 序列号 `LOCKED` 期间不得被其他业务占用 |

### 8.4 UDI 铁律

| 编号 | 规则 |
|---|---|
| U-01 | UDI 管理耗材（`is_udi_managed=TRUE`）必须扫码，不允许手工输入 |
| U-02 | GS1 码制必须通过 Mod-10 校验位验证 |
| U-03 | HIBC 码制必须通过 Mod-43 校验位验证 |
| U-04 | 解析成功后必须记录 `m15_udi_log` |
| U-05 | 私有码正则必须通过安全白名单校验（拒绝 `(?{`、`(?R)` 等回溯构造） |

### 8.5 追溯铁律

| 编号 | 规则 |
|---|---|
| T-01 | 植入物管理耗材（`is_implant=TRUE`）必须登记使用记录 |
| T-02 | 使用记录必须绑定患者 ID 与眼别 |
| T-03 | 未登记告警必须在 72 小时内补录 |
| T-04 | 追溯记录永久保存，不得删除 |

### 8.6 职责分离

| 编号 | 规则 |
|---|---|
| SoD-01 | 采购申请人与审批人不得为同一人 |
| SoD-02 | **采购下单人与验收人不得为同一人** |
| SoD-03 | 出库申请人与执行人不得为同一人 |
| SoD-04 | 盘点录入人与调整审批人不得为同一人 |
| SoD-05 | 高值柜双人管理：两个账号不同人，操作时间差 ≤30 分钟 |
| SoD-06 | 二级库交接的交接双方不得为同一人 |
| SoD-07 | 召回发起人与受影响批次无关（防利益冲突） |

## 10. 异常与降级策略

### 10.1 降级矩阵

| 依赖 | 场景 | 策略 |
|---|---|---|
| M01-04 耗材主数据 | 不可用 | **阻断**——无主数据无法判断是否植入物、是否序列号管理 |
| M01-05 供应商资质 | 不可用 | **阻断（不可降级）**——资质过期仍采购一旦发生质量问题医院担全责 |
| M01-05 供应商信息 | 不可用 | 阻断（采购场景）/ 降级（查询场景，用快照） |
| M09 手术台次 | 不可用 | **阻断（备台场景）**——无台次无法备台 |
| M03-05 消息 | 不可用 | 异步重试 5 次，失败记录待补发 |
| M02-06 审计 | 不可用 | 本地缓冲 10 分钟，批量补写 |
| 药监局 UDI 库 | 超时 | 5s 超时记 `UNCHECKED`，24 小时内补做 |
| 扫码枪 | 故障 | 允许手工输入（仅序列号管理耗材，需二次确认） |

### 10.2 三层兜底

```
第 1 层：数据库约束（109 条 CHECK + 46 个唯一索引 + 3 个只增触发器）
   ↓ 违反则抛 IntegrityError，服务层捕获转业务异常
第 2 层：服务层状态机校验 + 业务规则校验
   ↓ 违反则抛 BizException（7 位错误码）
第 3 层：定时任务巡检（每日 04:00）
   ↓ 发现孤儿数据（无主记录、数量不一致、状态矛盾）则告警
```

### 10.3 补偿队列

| 场景 | 补偿方式 | 重试策略 |
|---|---|---|
| 入库单已建但库存服务失败 | `m15_consume_compensation` 表 | 每 5 分钟，最多 10 次 |
| 消耗已登记但 M16 计费失败 | 同上 | 每 10 分钟，最多 10 次 |
| 召回通知发送失败 | `m15_recall_compensation` 表 | 每 5 分钟，最多 10 次 |
| M22 统计推送失败 | 内存队列 | 每 2 分钟，最多 5 次 |

### 10.4 数据质量巡检（每日 04:00）

| 检查项 | 判定 | 处置 |
|---|---|---|
| 台账数量 vs 流水累加 | 不一致 | 告警，人工核对 |
| 序列号状态与台账 | 矛盾 | 告警 |
| 备台单未完成但台次已结束 | 应释放 | 自动释放锁定 |
| 消耗记录无 M16 计费 | 补偿失败 | 重试 |
| 植入物已消耗未登记 | 追溯断链 | 生成未登记告警 |
| 批次已过期但状态非 EXPIRED | 状态滞后 | 自动更新 |

## 12. 实施路线与验收

### 12.1 六阶段 20 周

| 阶段 | 内容 | 工期 | 说明 |
|---|---|---|---|
| ① M15-01 | 仓库库位 + 库存台账 + 序列号 + 流水 | 4 周 | 没有台账后续全部无从谈起 |
| ② M15-02 | 分配策略 + UDI 解析 + DI 台账 | 3 周 | 扫码能力是后续所有环节的基础 |
| ③ M15-03 | 采购申请 → 订单 → 到货 → 验收 → 入库 | 4 周 | 库存的合法入口 |

| ⑤ M15-06 | 备台 + 消耗 + 退料 + 报损 | 3 周 | 手术室核心场景 |
| ⑥ M15-07 | 追溯 + 召回 + 不良事件 | 3 周 | 依赖前五个阶段的完整数据 |
