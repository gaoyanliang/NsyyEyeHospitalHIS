**设计说明：**

| 决策 | 内容 | 理由 |
|---|---|---|
| 无物理外键 | 全部引用为逻辑引用 | 与 M15 其他子模块及 M16 一致；HIS 数据迁移与修复成本优先 |
| 名称快照 | `m15_issue` 冗余 `dept_name` / `warehouse_name`；`m15_issue_item` 冗余 `material_name` / `spec` / `unit` | 科室与耗材改名后，历史出库单仍显示当时的名称 |
| 明细与批次分表 | `m15_issue_item` 记业务数量，`m15_issue_batch` 记物理批次 | 一条明细可跨多批次；只记明细则库存扣减不知扣哪批，FEFO 与追溯失效 |
| 二级库独立表 | `m15_secondary_stock` 不走 M15-01 的 `m15_stock` | 二级库按「品种」聚合、无需库位与批号粒度（高值柜除外），查询快 10 倍；高值柜仍可用 M15-01 的序列号表 |
| 交接单明细分表 | `m15_secondary_handover_item` 逐品种记录 | 差异必须逐品种定位；一单合则无法统计「哪个品种最容易短少」 |
| 配置表独立 | `m15_issue_config` 11 条 | 与 M15 其他子模块配置表结构一致 |

#### 约束说明

```sql
-- 出库类型枚举
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_type
    CHECK (issue_type IN ('REQUISITION','TRANSFER','PREPARE','SCRAP','RETURN'));

-- 状态枚举
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_status
    CHECK (status IN ('DRAFT','SUBMITTED','APPROVED','REJECTED','PICKING','ISSUED','RECEIVED','CANCELLED'));

-- 用途枚举
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_purpose
    CHECK (purpose IN ('NORMAL','PREPARE','REPLENISH','NEW_PROJECT','OTHER'));

-- 报损原因枚举
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_scrap_reason
    CHECK (scrap_reason IS NULL OR scrap_reason IN ('EXPIRED','DAMAGED','RECALLED','OTHER'));

-- 报损必须有原因与照片
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_scrap
    CHECK (issue_type <> 'SCRAP' OR (scrap_reason IS NOT NULL
           AND scrap_photos IS NOT NULL AND jsonb_typeof(scrap_photos) = 'array'
           AND jsonb_array_length(scrap_photos) >= 1));

-- 非报损不得有报损字段
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_not_scrap
    CHECK (issue_type = 'SCRAP' OR (scrap_reason IS NULL AND scrap_photos IS NULL));

-- 非调拨/领用/备台的目标库为 NULL 要求
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_target
    CHECK (issue_type = 'SCRAP' OR issue_type = 'RETURN'
           OR (target_warehouse_id IS NOT NULL
               AND target_warehouse_id <> warehouse_id));

-- 出库日期不晚于期望出库日期之后的合理范围
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_date
    CHECK (issue_date <= expected_date + INTERVAL '30 days');

-- 金额非负
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_amount
    CHECK (total_amount >= 0);

-- 缺货数量非负
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_short
    CHECK (short_qty_total >= 0);

-- 明细项数非负
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_item_count
    CHECK (item_count >= 0);

-- 已提交之后必须有 required_approver
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_submitted
    CHECK (status = 'DRAFT' OR required_approver IS NOT NULL);

-- 已批准之后必须有审批信息
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_approved
    CHECK (status NOT IN ('APPROVED','PICKING','ISSUED','RECEIVED')
           OR (approved_at IS NOT NULL AND approved_by IS NOT NULL));

-- 已出库之后必须有出库信息
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_issued_ok
    CHECK (status NOT IN ('ISSUED','RECEIVED')
           OR (issued_at IS NOT NULL AND issued_by IS NOT NULL));

-- 已签收必须有签收信息
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_received_ok
    CHECK (status <> 'RECEIVED'
           OR (received_at IS NOT NULL AND received_by IS NOT NULL));

-- 已驳回必须有驳回原因
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_rejected
    CHECK (status <> 'REJECTED' OR reject_reason IS NOT NULL);

-- 已作废必须有原因
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_cancelled
    CHECK (status <> 'CANCELLED' OR (cancelled_at IS NOT NULL AND cancel_reason IS NOT NULL));

-- 时间顺序
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_time_seq
    CHECK ((submitted_at IS NULL OR submitted_at >= created_at)
       AND (approved_at IS NULL OR submitted_at IS NULL OR approved_at >= submitted_at)
       AND (issued_at IS NULL OR approved_at IS NULL OR issued_at >= approved_at)
       AND (received_at IS NULL OR issued_at IS NULL OR received_at >= issued_at));

-- 幂等键格式
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_idem
    CHECK (idempotency_key IS NULL
           OR idempotency_key ~ '^PREPARE:SCHEDULE:[0-9]+$');

-- 备台出库必须有幂等键与台次
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_prepare
    CHECK (issue_type <> 'PREPARE'
           OR (idempotency_key IS NOT NULL AND schedule_id IS NOT NULL));

-- 单号格式
ALTER TABLE m15_issue ADD CONSTRAINT ck_m15_issue_no
    CHECK (issue_no ~ '^OUT-[0-9]{4}-[0-9]{4}$');
```

#### 状态机

```
        提交                  审批通过                拣货
DRAFT ────────► SUBMITTED ────────────► APPROVED ────────► PICKING
  │                  │                       │                 │
  │ 作废              │ 驳回                   │ 作废              │ 确认出库
  ▼                  ▼                       ▼                 ▼
CANCELLED         REJECTED               CANCELLED          ISSUED
                                                                 │
                                                                 │ 签收
                                                                 ▼
                                                             RECEIVED
```

#### 设计要点

1. **`idempotency_key` 只对 PREPARE 类型允许**：备台出库由 M15-06 自动触发，可能因超时重试；约束 `ck_m15_issue_prepare` 保证「备台必须有幂等键」，其他类型不得使用（避免手工出库误用幂等键导致重复出库被跳过）。
2. **`approved_by = 0` 表示系统免审**：备台额度内免审时不写真实审批人，但 `approved_at` 必须有值，状态机与报表都能区分「免审」与「人工审批」。
3. **`short_qty_total` 单独存**：备台齐套率 = `short_qty_total = 0` 的备台单数 / 总备台单数。若实时从明细算，每次统计要 JOIN 明细表。
4. **`receive_rejected` 布尔而非独立状态**：拒收后仍回到 `ISSUED`（可由库管员重新送或作废），用布尔标记便于统计「拒收率」，若做独立状态则状态机多一条循环边，处置路径不清晰。
5. **`scrap_photos` 用 JSONB 数组**：报损照片 1~3 张，整体读写，从不单独按第 N 张查询。
6. **`schedule_id` 只在备台出库时填**：M15-06 术后核对「这台次备了几项、发了几项」靠此 JOIN。

#### 量级估算

| 项 | 数值 |
|---|---|
| 年行数 | 约 18,000 |
| 单行大小 | 约 1.2 KB |
| 年数据量 | 约 21 MB |
| 15 年数据量 | 约 315 MB |

#### 分区

不分区。年 1.8 万行，15 年 27 万行；`uk_m15_issue_no` 与 `uk_m15_issue_idem` 是跨年唯一约束，分区会迫使唯一索引包含分区键，破坏「单号全局唯一」语义。

| remark | VARCHAR(512) | Y | NULL | 备注 |
| created_at | TIMESTAMP | N | NOW() | 创建时间 |
| updated_at | TIMESTAMP | N | NOW() | 更新时间 |
| is_deleted | BOOLEAN | N | FALSE | 逻辑删除 |

#### 索引设计

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| pk_m15_issue_item | PRIMARY | id | 主键 |
| uk_m15_issue_item_seq | UNIQUE | (issue_id, line_no) WHERE is_deleted = FALSE | 同单行号唯一 |
| uk_m15_issue_item_code | UNIQUE | (issue_id, material_code) WHERE is_deleted = FALSE | 同单同耗材唯一 |
| idx_m15_issue_item_material | NORMAL | (material_code, created_at DESC) | 按耗材查历史 |

#### 约束说明

```sql
-- 申请数量为正
ALTER TABLE m15_issue_item ADD CONSTRAINT ck_m15_issue_item_req
    CHECK (requested_qty > 0);

-- 数量恒等式：批准 ≤ 申请
ALTER TABLE m15_issue_item ADD CONSTRAINT ck_m15_issue_item_approved
    CHECK (approved_qty >= 0 AND approved_qty <= requested_qty);

-- 实发 ≤ 批准
ALTER TABLE m15_issue_item ADD CONSTRAINT ck_m15_issue_item_issued
    CHECK (issued_qty >= 0 AND issued_qty <= approved_qty);

-- 缺货 = 批准 − 实发
ALTER TABLE m15_issue_item ADD CONSTRAINT ck_m15_issue_item_short
    CHECK (short_qty = approved_qty - issued_qty);

-- 签收数量不超过实发
ALTER TABLE m15_issue_item ADD CONSTRAINT ck_m15_issue_item_received
    CHECK (received_qty IS NULL OR (received_qty >= 0 AND received_qty <= issued_qty));

-- 金额非负
ALTER TABLE m15_issue_item ADD CONSTRAINT ck_m15_issue_item_amount
    CHECK (amount >= 0 AND unit_cost >= 0);

-- 金额行级舍入自洽
ALTER TABLE m15_issue_item ADD CONSTRAINT ck_m15_issue_item_amount_calc
    CHECK (issued_qty = 0 OR ABS(amount - ROUND(issued_qty * unit_cost, 2)) < 0.01);

-- 行号范围
ALTER TABLE m15_issue_item ADD CONSTRAINT ck_m15_issue_item_line
    CHECK (line_no >= 1 AND line_no <= 999);
```

#### 设计要点

1. **`requested_qty` 不可改，`approved_qty` 审批时可改，`issued_qty` 拣货时可改**：三层数量分别对应三个角色的动作，任何一层被绕过都会导致「审批形同虚设」或「账实不符」。
2. **`unit_cost` 在审批时填入、出库后按实际批次覆盖**：审批时是估值（用于档位判定与预算预警），出库后是实际（用于成本核算）；两者差异应在明细上留下痕迹——出库批次表的 `unit_cost` 之和 / 实发数量即实际单价。
3. **`amount` 行级先舍入**：`ROUND(issued_qty * unit_cost, 2)`，与 M15 全局铁律一致。若先累加再舍入，30 行明细的误差可能达数毛钱。
4. **`received_qty` 允许 NULL**：未签收时为 NULL，与「签收为 0」区分（0 表示签收时确实一件没收到）。

#### 量级估算

| 项 | 数值 |
|---|---|
| 年行数 | 约 126,000（18,000 单 × 7 项） |
| 单行大小 | 约 320 B |
| 年数据量 | 约 40 MB |
| 15 年数据量 | 约 600 MB |

#### 分区

不分区。15 年 189 万行 / 600 MB，在 PostgreSQL 16 单表舒适区（2000 万行以下主键查询仍 <1ms）。若未来行数超 5,000 万，改用 `PARTITION BY HASH (issue_id)` 分 16 区。

```sql
-- 数量为正

    CHECK (qty > 0);

-- 成本非负

    CHECK (unit_cost >= 0);

ALTER TABLE m15_issue_batch ADD CONSTRAINT ck_m15_issue_batch_amount
    CHECK (ABS(amount - ROUND(qty * unit_cost, 2)) < 0.01);

-- 序列号必须是数组
ALTER TABLE m15_issue_batch ADD CONSTRAINT ck_m15_issue_batch_serial
    CHECK (serial_nos IS NULL OR jsonb_typeof(serial_nos) = 'array');

-- 批号非空
ALTER TABLE m15_issue_batch ADD CONSTRAINT ck_m15_issue_batch_no
    CHECK (char_length(btrim(batch_no)) >= 1);
```

#### 设计要点

1. **`uk_m15_issue_batch_key` 是出库幂等的最后一道防线**：即使应用层因超时重试再次写完批次，唯一约束抛 `IntegrityError`，服务层捕获后视为「已写过」跳过；若无此约束，重试会让批次记录翻倍，`SUM(批次 qty)` 大于 `issued_qty`，明细与批次对不上。
2. **`batch_id` 允许 NULL 但要配 `batch_no`**：某些耗材在 M15-01 中的批次行可能已归档（超过在线保留期），但历史出库单仍要能显示批号，故允许 `batch_id` 为空而 `batch_no` 必填。
3. **`serial_nos` 用 JSONB 数组**：一次出库的序列号通常 1 件（高值耗材一物一码），偶有 2~5 件；关联表会多一张表与一次 JOIN，而查询模式永远是「这条批次出了哪些序列号」整体读取。
4. **`expiry_date` 快照**：批次行归档后仍能看到「当时出的是哪年到期的货」，是临期出库管控的追溯依据。

| 项 | 数值 |
|---|---|
| 年行数 | 约 240,000（126,000 明细 × 1.9 批次） |
| 单行大小 | 约 240 B |
| 年数据量 | 约 58 MB |
| 15 年数据量 | 约 870 MB |

不分区。唯一约束 `(issue_id, item_id, batch_id)` 已含 `issue_id`，若按年分区需加分区键变为 `(issue_id, item_id, batch_id, issue_date)`，语义退化为「同单同年同批次唯一」，跨年重试会重复——而备台出库跨年重试是真实场景（除夕夜手术）。

```sql
-- 可用数量为生成列

    GENERATED ALWAYS AS (qty_on_hand - qty_locked) STORED;

-- 金额非负
ALTER TABLE m15_secondary_stock ADD CONSTRAINT ck_m15_sec_stock_amount
    CHECK (amount >= 0);

-- 补货点与安全库存非负
ALTER TABLE m15_secondary_stock ADD CONSTRAINT ck_m15_sec_stock_policy
    CHECK (reorder_point >= 0 AND safety_stock >= 0 AND safety_stock >= reorder_point);

-- 版本号从 1 起

    CHECK (version >= 1);

-- 时间顺序

    CHECK (last_out_at IS NULL OR last_in_at IS NULL OR last_out_at >= last_in_at);

-- 序列号管理必须有版本号保护（高频并发的品种）
ALTER TABLE m15_secondary_stock ADD CONSTRAINT ck_m15_sec_stock_serial
    CHECK (is_serial_managed = FALSE OR version >= 1);
```

#### 设计要点

1. **`qty_available` 是生成列**：三数量恒等式由数据库强制，应用层没有机会算错。这是 M15 全局铁律（M15-01 的 `m15_stock` 同样如此）。
2. **二级库独立于 `m15_stock` 的理由**：`m15_stock` 的粒度是「仓库 × 库位 × 耗材 × 批号」，二级库无库位概念、批号也不必逐批追踪（高值柜除外）。独立后二级库查询单表扫 86 行（手术室）而非 JOIN 上万行批次，快 10 倍以上。
3. **高值柜仍用 M15-01 的序列号表**：`is_serial_managed = TRUE` 时，逐件序列号在 `m15_stock_batch` 中管理，本表只做数量聚合与补货判断。
4. **`version` 乐观锁**：备台签收与术中消耗可能并发（护士签收的同时医生已扫码消耗），用乐观锁避免数量覆盖。若并发冲突频繁，再升级为 `SELECT FOR UPDATE`。
5. **`last_handover_diff` 冗余**：交接后把差异回写本表，科主任看二级库列表时直接看到「上次交接差了几件」，无需再 JOIN 交接单。
6. **`reorder_point` / `safety_stock` 从 M01-04 同步而非实时查**：补货扫描每天扫全部二级库品种，实时查 M01-04 需 86 次 HTTP；同步后本地判断。同步频率：`job_m15_policy_sync` 每日 03:00 + `m01.material.updated` 事件增量。

#### 量级估算

| 项 | 数值 |
|---|---|
| 行数（静态，非增长） | 约 400（4 个二级库 × 100 品种） |
| 单行大小 | 约 480 B |
| 数据量 | 约 200 KB |

#### 分区

不分区。静态表，行数不随时间增长。

#### 约束说明

```sql
-- 数量非负
ALTER TABLE m15_secondary_handover_item ADD CONSTRAINT ck_m15_sec_hitem_qty
    CHECK (book_qty >= 0 AND actual_qty >= 0);

-- 差异自洽
ALTER TABLE m15_secondary_handover_item ADD CONSTRAINT ck_m15_sec_hitem_diff
    CHECK (diff_qty = actual_qty - book_qty);

-- 有差异必须说明
ALTER TABLE m15_secondary_handover_item ADD CONSTRAINT ck_m15_sec_hitem_remark
    CHECK (diff_qty = 0 OR (remark IS NOT NULL AND char_length(btrim(remark)) >= 5));

-- 金额非负
ALTER TABLE m15_secondary_handover_item ADD CONSTRAINT ck_m15_sec_hitem_amount
    CHECK (amount >= 0);

-- 序列号必须是数组
ALTER TABLE m15_secondary_handover_item ADD CONSTRAINT ck_m15_sec_hitem_serial
    CHECK (serial_nos IS NULL OR jsonb_typeof(serial_nos) = 'array');

-- 行号范围
ALTER TABLE m15_secondary_handover_item ADD CONSTRAINT ck_m15_sec_hitem_line
    CHECK (line_no >= 1 AND line_no <= 999);
```

#### 设计要点

1. **`diff_qty` 存为普通列而非生成列**：与 `book_qty` / `actual_qty` 的差在同一行内，若用生成列则该行「不能有任何列被单独更新」——交接单提交后完全不可改，但差异说明（`remark`）需要允许事后补录。故用普通列 + `CHECK` 校验自洽。
2. **`serial_nos` 数组必填于序列号耗材**：高值柜交接若只有数量没有序列号，「少了 1 片但不知道是哪一片」——序列号让差异可定位到具体实物。
3. **`idx_m15_sec_hitem_diff` 部分索引**：设计上该索引应常年 0 行（差异靠当场处理），非 0 立即告警，是运营健康度的探针。

#### 设计要点

1. **`COALESCE(scope_id, 0)` 的必要性**：PostgreSQL 认为 NULL 与 NULL 不相等，不加 COALESCE 则 `scope='GLOBAL'` 的记录可重复插入无数条，取「第一条」的代码就会时对时错。不用 `NULLS NOT DISTINCT` 因是 PG 15+ 特性，本项目部分环境仍为 PG 14。
2. **`is_sensitive` 必须可编辑**：若敏感参数被设为 `is_editable = FALSE`，则它既不能被直接修改，也不能通过变更审批流程修改，形成死参数。
3. **`default_value` 支持「恢复默认」**：真实场景——运维为排查把 `TRANSFER_ALERT_DAYS` 改成 30 天忘改回，导致三个月内没有调拨超期告警。
4. **`param_value` 统一存字符串**：配置表是异构参数容器，JSONB 存值类型更自由但无法做 SQL 范围校验；VARCHAR + `param_type` 显式声明，写入时用 `min_value` / `max_value` 校验。

**部分索引 vs 普通索引效果对比（`idx_m15_issue_pending`）：**

| 方案 | 索引大小 | 扫描行数 | 查询耗时 |
|---|---|---|---|
| 无索引 | — | 270,000（全表） | 约 48ms |
| 普通索引 | 约 9 MB | 仍扫索引全部 | 约 12ms |
| **部分索引** | **约 4 KB** | **约 7 行（待审批常态）** | **约 0.1ms** |

工作台每 30 秒刷新一次，一天 2,880 次 × 8 个仓库约 23,000 次查询。48ms 与 0.1ms 的差距是 **18 分钟 vs 2 秒 CPU**。

### `updated_at` 触发器

```sql
CREATE OR REPLACE FUNCTION fn_m15_set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m15_issue_updated_at BEFORE UPDATE ON m15_issue
    FOR EACH ROW EXECUTE FUNCTION fn_m15_set_updated_at();
```

### 上线前运维准备

| # | 事项 | 优先级 | 说明 |
|---|---|---|---|
| 1 | 建立 4 个二级库（手术室、门诊治疗室、屈光中心、门诊手术室）并指定管理员 | 🔴 | 无二级库则备台无法签收 |
| 2 | 为每个二级库品种配置补货点与安全库存 | 🔴 | 无补货点则补货建议全空 |
| 3 | 校验 `pg_trgm` 扩展可用 | 🔴 | 需超级用户 |
| 4 | 验证 M15-01 `POST /stock/outbound` 幂等性 | 🔴🔴🔴 | 用同一 `idempotency_key` 连调 3 次，库存只能减一次 |
| 5 | 验证 M15-02 `allocate` / `release` 连通性 | 🔴🔴 | 分配失败会降级为手工选批，可接受但要确认告警可见 |
| 6 | 配置 11 条参数并确认敏感参数值 | 🟡 | 尤其 `PREPARE_AUDIT_FREE` |
| 7 | 部署二级库平板/PDA 客户端 | 🟡 | 交接班与签收在库房现场操作 |
| 8 | 培训高值柜交接流程（逐品种点数量 + 序列号核对） | 🔴 | 交接是新流程，需专项培训 |
| 9 | 建立调拨超期催签机制与联系人清单 | 🟡 | 跨院区调拨常见 |
| 10 | 打印模板中文化确认（拣货单、出库单） | 🟡 | 库管员纸质拣货用 |

**第 4 项最关键**：出库补偿任务最多重试 10 次。若 M15-01 的 `POST /stock/outbound` 不幂等，每次重试都会再扣一次库存，10 次后库存虚减 10 倍，**账实严重不符且极难排查**。验证方法：

```
用同一 idempotency_key "ISSUE:999999" 连续调用 3 次
预期：第 1 次返回 code=0 且 txn_nos 非空
      第 2、3 次返回 code=0 且 idempotent=true（或返回相同的 txn_nos）
实际：查询 m15_stock.qty_on_hand 只减少了 1 次的数量
```
