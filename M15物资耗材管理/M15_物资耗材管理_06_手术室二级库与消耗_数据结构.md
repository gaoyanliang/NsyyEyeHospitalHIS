**设计说明：**

| 决策 | 内容 | 理由 |
|---|---|---|
| 无物理外键 | 全部引用为逻辑引用 | 与 M15 其他子模块一致；高频写入表加外键会带来锁竞争 |
| 名称快照 | 全部明细表冗余 `material_code`/`material_name`/`spec`/`unit` | 备台与消耗是「当时的事实」，耗材改名后历史单据仍要能说清 |
| `schedule_id` 部分唯一 | `m15_or_prepare` / `m15_or_return` 各自一台次一条有效单 | 一次手术只能有一张备台单、一张退料单（可有多张报损单） |
| 序列号数组 | `m15_or_prepare_item.serial_nos` 用 JSONB | 高值耗材备台时可能指定具体序列号（1~5 件），查询模式是整体读取 |
| 计费金额快照 | `m15_or_consume_item.unit_price`/`amount` | 计费后在耗材调价，历史消耗金额不能跟着变 |
| 补偿表独立 | `m15_consume_compensation` 而非重试表内嵌 | 四种业务（BILLING/STOCK_CONSUME/RETURN/IMPLANT）共用一个重试队列，统一调度 |
| 日统计预聚合 | `m15_consume_daily_stat` 按 `stat_date` 唯一 | 运营报表每查一次要扫 12 万条消耗明细，预聚合后查 1 行 |
| 都是普通表 | 10 表全不分区 | `record_no`/`schedule_id`/`(prepare_id, line_no)` 是跨年唯一约束，分区会迫使唯一索引含分区键从而破坏语义 |

**约束说明：**

```sql
-- 单号格式：PREP-YYYY-MMDD-NNNN
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_no
    CHECK (prepare_no ~ '^PREP-[0-9]{4}-[0-9]{4,6}$');

-- 状态枚举
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_status
    CHECK (status IN ('DRAFT', 'PENDING', 'READY', 'IN_USE', 'COMPLETED', 'CANCELLED'));

-- 眼别枚举
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_eye_side
    CHECK (eye_side IS NULL OR eye_side IN ('OD', 'OS', 'OU', 'NA'));

-- 生成来源枚举
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_source
    CHECK (generated_from IS NULL OR generated_from IN ('KIT', 'MANUAL', 'COPY'));

-- 数量与金额非负
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_amounts
    CHECK (item_count >= 0 AND total_planned_qty >= 0 AND total_planned_amount >= 0
           AND shortage_count >= 0 AND shortage_count <= item_count);

-- 缺货标记与缺货项数一致
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_shortage_flag
    CHECK (is_shortage = (shortage_count > 0));

-- 需要审批的必须有审批人
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_approved
    CHECK (need_approval = FALSE OR status IN ('DRAFT', 'PENDING', 'CANCELLED')
           OR (approved_by IS NOT NULL AND approved_at IS NOT NULL));

-- 待审批必须有提交时间
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_pending
    CHECK (status <> 'PENDING' OR submitted_at IS NOT NULL);

-- 备台完成必须有完成时间
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_ready
    CHECK (status NOT IN ('READY', 'IN_USE', 'COMPLETED') OR ready_at IS NOT NULL);

-- 开始使用必须有开始时间
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_started
    CHECK (status NOT IN ('IN_USE', 'COMPLETED') OR started_at IS NOT NULL);

-- 完成必须有完成时间
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_completed
    CHECK (status <> 'COMPLETED' OR completed_at IS NOT NULL);

-- 取消必须有原因（≥5 字）
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_cancelled
    CHECK (status <> 'CANCELLED'
           OR (cancel_reason IS NOT NULL AND char_length(btrim(cancel_reason)) >= 5
               AND cancelled_at IS NOT NULL));

-- 时间序列：提交 <= 备台完成 <= 开始使用 <= 完成
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_time_seq
    CHECK ((submitted_at IS NULL OR ready_at IS NULL OR ready_at >= submitted_at)
       AND (ready_at IS NULL OR started_at IS NULL OR started_at >= ready_at)
       AND (started_at IS NULL OR completed_at IS NULL OR completed_at >= started_at));

-- 手术日期不允许早于创建日期 30 天以上（防误录）
ALTER TABLE m15_or_prepare ADD CONSTRAINT ck_m15_prepare_date_range
    CHECK (schedule_date >= DATE '2020-01-01');

-- ★ 关键：一台次只能有一张有效备台单
CREATE UNIQUE INDEX uk_m15_prepare_schedule
    ON m15_or_prepare (schedule_id)
    WHERE is_deleted = FALSE;
```

**状态机：**

```
DRAFT ──提交──► PENDING ──审批通过──► READY ──术中首次消耗──► IN_USE ──手术结束──► COMPLETED（终态）
  │                │                     │
  │（免审批）      │驳回                 │
  └────────────────┼─────────────────────┘
                   │
              取消 │（任意非终态）
                   ▼
              CANCELLED（终态）
```

**量级估算：**

| 项 | 数值 |
|---|---|
| 年台次 | 约 18,000 台（日均 50 台 × 360 天） |
| 单行大小 | 约 900 字节（含 TEXT 快照） |
| 年数据量 | 约 16 MB |
| 保留期 | 15 年 |
| 15 年数据量 | 约 240 MB |

**分区：** 不分区（`uk_m15_prepare_schedule` 是跨年唯一约束，分区会破坏「一台次一备台单」语义）。

**约束说明：**

```sql
-- 行号必须为正
ALTER TABLE m15_or_prepare_item ADD CONSTRAINT ck_m15_prepare_item_line_no
    CHECK (line_no > 0);

-- 数量非负
ALTER TABLE m15_or_prepare_item ADD CONSTRAINT ck_m15_or_prepare_item_qty
    CHECK (planned_qty >= 0 AND issued_qty >= 0 AND returned_qty >= 0
           AND consumed_qty >= 0 AND damaged_qty >= 0 AND shortage_qty >= 0);

-- 计划数量必须为正（不可能备 0 个）
ALTER TABLE m15_or_prepare_item ADD CONSTRAINT ck_m15_prepare_item_planned
    CHECK (planned_qty > 0);

-- ★ 出库数不超过计划数
ALTER TABLE m15_or_prepare_item ADD CONSTRAINT ck_m15_prepare_item_issued
    CHECK (issued_qty <= planned_qty);

-- ★ 消耗 + 退回 + 破损不超过出库数
ALTER TABLE m15_or_prepare_item ADD CONSTRAINT ck_m15_prepare_item_balance
    CHECK (consumed_qty + returned_qty + damaged_qty <= issued_qty);

-- 出库数 + 缺货数 <= 计划数（缺货是发不出的部分）
ALTER TABLE m15_or_prepare_item ADD CONSTRAINT ck_m15_prepare_item_fulfill
    CHECK (issued_qty + shortage_qty <= planned_qty);

-- 缺货标记与缺货数一致
ALTER TABLE m15_or_prepare_item ADD CONSTRAINT ck_m15_prepare_item_shortage
    CHECK (is_shortage = (shortage_qty > 0));

-- 缺货必须填原因
ALTER TABLE m15_or_prepare_item ADD CONSTRAINT ck_m15_prepare_item_shortage_reason
    CHECK (shortage_qty = 0 OR shortage_reason IS NOT NULL);

-- 金额自洽
ALTER TABLE m15_or_prepare_item ADD CONSTRAINT ck_m15_prepare_item_amount
    CHECK (abs(planned_amount - ROUND(planned_qty * unit_price, 2)) < 0.01);

-- 单价非负
ALTER TABLE m15_or_prepare_item ADD CONSTRAINT ck_m15_prepare_item_price
    CHECK (unit_price >= 0);

-- 序列号必须是数组
ALTER TABLE m15_or_prepare_item ADD CONSTRAINT ck_m15_prepare_item_serial
    CHECK (serial_nos IS NULL OR jsonb_typeof(serial_nos) = 'array');
```

**设计要点：**

- `planned_qty`/`issued_qty`/`consumed_qty`/`returned_qty`/`damaged_qty`/`shortage_qty` 六个数量构成一条完整的**物料守恒链**：计划 → 实发 → 实际使用 / 退回 / 破损。任意两个之间的差额都能回答一个具体问题：
  - `planned − issued − shortage` = 0，说明计划要么发出要么明确标缺货
  - `issued − consumed − returned − damaged` = 0（手术结束时），说明领用的每一件都有去处
  - `returned / issued` = 退料率（M06-06 依赖的核心指标）
- `is_optional` 区分「套包强制项」与「术中用，不一定用」，缺货时可选项目不报警。

**状态机：**

```
DRAFT ──确认──► CONFIRMED ──计费成功──► BILLED ──M16 结算回调──► SETTLED（终态）
  │                │                      │
  └────────────────┴──────────────────────┘
              取消（仅 DRAFT / CONFIRMED）
                    ▼
              CANCELLED（终态）
```

**为什么三种回写状态独立：**

一台手术结束时消耗记录要同时做三件事：扣二级库库存、推送 M16 计费、回写 M15-07 植入物使用。三者依赖不同系统，任一失败时护士需知道「哪一步没完成」：

- `stock_status='FAILED'`：库存没扣对，会导致二级库台账虚高
- `billing_status='FAILED'`：没计费，医院少收钱
- `implant_status='FAILED'`：植入物没登记，追溯链断了

合并成一个 `sync_status` 会让「库存扣了但没计费」显示为失败并重试全部三步，导致库存重复扣减。

**锁定与消耗（`StockService` 中的原子更新）：**

```sql
-- 锁定（备台时）
UPDATE m15_sec_stock
SET qty_locked = qty_locked + :q, version = version + 1, updated_at = CURRENT_TIMESTAMP
WHERE id = :id AND version = :v AND qty_available >= :q;

-- 消耗（术中确认时，同时扣在库和锁定）
UPDATE m15_sec_stock
SET qty_on_hand = qty_on_hand - :q, qty_locked = qty_locked - :q,
    version = version + 1, updated_at = CURRENT_TIMESTAMP
WHERE id = :id AND version = :v AND qty_locked >= :q;

-- 解锁（备台取消或退料时）
UPDATE m15_sec_stock
SET qty_locked = qty_locked - :q, version = version + 1, updated_at = CURRENT_TIMESTAMP
WHERE id = :id AND version = :v AND qty_locked >= :q;
```

**设计要点：**

- **`qty_available` 是生成列**，`GENERATED ALWAYS AS (qty_on_hand - qty_locked) STORED`。三个数量的恒等式由数据库强制，应用层没有机会算错。代价是不能直接 UPDATE 该列（PostgreSQL 会报错），任何库存操作都必须显式改 `qty_on_hand` 或 `qty_locked`。
- **`effective_expiry_date` 是实际失效日**，取厂商有效期与灭菌有效期的最小值。一次性无菌包厂商有效期 3 年但灭菌有效期只有 6 个月，以厂商效期为准会出现「灭菌已失效但系统显示有效」→ 术后感染。FEFO 排序与近效期预警都用这个字段。
- **`version` 乐观锁**：护士签收与术中消耗可能并发（同一批次被两台手术同时备台），乐观锁避免数量被覆盖。配合 `UPDATE ... WHERE version = :v` 的 `rowcount == 0` 判定重试。
- **不存 `location_id`**：二级库是手术室内的开放货架，护士按耗材名称与批号取用，没有「库位」概念。加上 `location_id` 会让每一次取用都要先选库位，实测减慢护士操作约 40%。
- **同库同耗材同批次唯一**：`uk_m15_sec_stock_key (warehouse_id, material_code, batch_no)`。不按 `expiry_date` 拆分，因为同一批号的有效期必然相同（同一生产批次）。
- **`stock_amount` 冗余存**：二级库总金额是月报与成本分摊的核心指标，实时算 `SUM(qty_on_hand × unit_cost)` 在 3,000 行表上约 18ms，落库后直接 `SUM(stock_amount)` 约 0.5ms。每日 01:30 全量重算校正。

**量级估算：**

| 项 | 数值 |
|---|---|
| 二级库数量 | 2~4 个（主手术室、日间手术室、注药室） |
| 每库耗材种类 | 约 800 种（含批次约 2,400 行） |
| 总行数 | 约 7,200 行（稳态） |
| 单行大小 | 约 700 字节 |
| 数据量 | 约 5 MB |
| 年增长 | 约 500 行（新批号）、约 1,500 行（历史批次保留） |
| 保留期 | 15 年（历史批次置 `qty_on_hand = 0` 保留追溯） |
| 15 年数据量 | 约 30 MB |

**分区：** 不分区。行数太少（稳态 7,200 行），分区反而增加查询开销。

**状态机：**

```
PENDING ──重试成功──► SUCCESS（终态，resolved_at 有值）
   │
   ├──retry_count 达上限──► FAILED ──人工处理──► SUCCESS（manually_resolved_* 有值）
   │
   └──业务已撤销——► IGNORED（终态）
```

**重试退避逻辑（Celery `retry_consume_compensation` 实现）：**

```python
delay = min(600 * (2 ** retry_count), 21600)  # 10min → 6h 上限
```

| retry_count | 下次重试间隔 | 累计耗时 |
|---|---|---|
| 0 | 10 分钟 | 10 分钟 |
| 1 | 20 分钟 | 30 分钟 |
| 2 | 40 分钟 | 1.2 小时 |
| 3 | 80 分钟 | 2.5 小时 |
| 4 | 160 分钟 | 5.2 小时 |
| 5 | 320 分钟 | 10.5 小时 |
| 6 | 640 分钟 → 上限 360 分钟 | 16.5 小时 |
| 7~10 | 360 分钟 | 约 1.5 天 |

**为什么 `max_retry = 10` 而不是 3 或 20：**

- 3 次（约 1.2 小时）太短：M16-01 计费服务做版本升级通常会持续 30~60 分钟，3 次重试很可能全落在升级窗口内
- 20 次（约 3 天）太长：真正的问题（接口契约变更、耗材编码不存在）重试 20 次也永远不会成功，反而让运维误以为「系统在自动修复」
- 10 次（约 1.5 天）合适：覆盖绝大多数短暂故障，且 1.5 天后转 FAILED 会触发告警，运维当天就能处理

**为什么唯一索引条件含 `SUCCESS`：**

若不包含 `SUCCESS`，同一业务对象处理后 `status='SUCCESS'` 的记录会让新补偿无法插入（比如这次库存补偿成功但计费补偿失败，两种 biz_type 不同不冲突，但同一 biz_type 若重试成功后再失败需要新记录）。包含 `SUCCESS` 后，`FAILED` 与 `IGNORED` 记录不占用唯一位置，可以重新建补偿。

```sql
INSERT INTO m15_consume_daily_stat (
    stat_date, warehouse_id, dept_id, schedule_count, record_count, item_count,
    total_qty, total_amount, total_cost, implant_count, implant_amount,
    return_count, return_amount, return_rate, damage_count, damage_amount,
    avg_amount_per_case, computed_at
) VALUES (
    :d, :wh, :dept, :sc, :rc, :ic,
    :tq, :ta, :tc, :imc, :ima,
    :rtc, :rta, :rate, :dmc, :dma,
    :avg, CURRENT_TIMESTAMP
)
ON CONFLICT (stat_date, COALESCE(warehouse_id, 0), COALESCE(dept_id, 0))
DO UPDATE SET
    schedule_count = EXCLUDED.schedule_count,
    record_count = EXCLUDED.record_count,
    item_count = EXCLUDED.item_count,
    total_qty = EXCLUDED.total_qty,
    total_amount = EXCLUDED.total_amount,
    total_cost = EXCLUDED.total_cost,
    implant_count = EXCLUDED.implant_count,
    implant_amount = EXCLUDED.implant_amount,
    return_count = EXCLUDED.return_count,
    return_amount = EXCLUDED.return_amount,
    return_rate = EXCLUDED.return_rate,
    damage_count = EXCLUDED.damage_count,
    damage_amount = EXCLUDED.damage_amount,

    computed_at = CURRENT_TIMESTAMP,
```

> **注意：** `ON CONFLICT` 的推断表达式必须与唯一索引的表达式**字符级完全一致**。若索引写 `COALESCE(warehouse_id, 0)` 而 `ON CONFLICT` 写 `COALESCE(warehouse_id, 0::bigint)`，PostgreSQL 会报「no unique or exclusion constraint matching the ON CONFLICT specification」。

**为什么退料率落库：**

M06-06 日间手术结算的验收指标「材料退回率 ≥90%」直接读这张表。若不落库，每次查退料率要扫 `m15_or_prepare_item`（540,000 行/年）+ `m15_or_return`（16,000 行/年）做 JOIN 聚合，30 天报表约 1.2 秒；落库后单行读取 <1ms。且退料率是**口径敏感指标**——分子分母的取数范围一旦调整，历史值会变，落库后历史值固定，口径变更需要重建表并注明口径。

**四条敏感参数的政策来源与篡改后果：**

| 参数 | 政策来源 | 篡改后果 |
|---|---|---|
| `PREPARE_APPROVAL_AMOUNT` | 高值耗材双人复核制度 | 调高 → 十万级备台免审，一人可操作全部晶体领用，舞弊无制衡 |
| `HIGH_VALUE_THRESHOLD` | 高值耗材管理制度 | 调高 → 晶体不再纳入柜内管理，丢失无法定位；调低 → 纱布也要开柜，效率崩溃 |
| `MANUAL_ADD_LIMIT_RATIO` | 术中追加耗材管控 | 调高 → 术中可无限追加，备台形同虚设，成本失控；调低 → 真实紧急追加被阻断，影响手术 |
| `EXPIRING_DAYS` | 近效期耗材管理规范 | 调小 → 临期耗材未预警，术中才发现过期被迫临时换货 |

**上线前运维准备（10 项）：**

| # | 项目 | 优先级 | 说明 |
|---|---|---|---|
| 1 | 建二级库并配置初始库存 | 🔴🔴🔴 | `m15_sec_stock` 必须有初始数据，否则备台全部提示缺货 |
| 2 | 验证 M15-01 `POST /stock/outbound` 幂等 | 🔴🔴🔴 | 同幂等键连调 3 次总库只能减一次，否则补偿重试后库存虚减 10 倍 |
| 3 | 配置高值耗材阈值与免审额度 | 🔴🔴 | 按本院实际晶体价格分布设定 |
| 4 | 配置二级库与高值柜 | 🔴🔴 | 与 M15-01 仓库主数据对齐（`warehouse_id` 一致） |
| 5 | 验证 `pg_trgm` 扩展可用 | 🔴 | 需超级用户执行 `CREATE EXTENSION` |
| 6 | 配置手术室套包（M01-04 `mdm_surgery_kit`） | 🔴🔴 | 备台单按套包自动带出明细 |
| 7 | 验证 M15-02 序列号占用接口 | 🔴🔴 | 一物一码耗材备台即占用序列号，防重复使用 |
| 8 | 验证 M16-01 计费接口连通性 | 🔴🔴 | 计费失败虽可补偿，但上线首日不应依赖重试 |
| 9 | 培训器械护士 PDA 扫码消耗 | 🔴 | 术中扫码是消耗记录的唯一准确来源 |

**第 1、2 项最关键**：第 1 项若二级库无初始库存，所有备台全部提示缺货，流程无法启动；第 2 项若 M15-01 出库接口不幂等，补偿重试会导致总库库存虚减（重试 10 次减 10 次），且因为库存只减不增极难排查。
