### 1.2 标准字段

所有业务表必须包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 主键 |
| `created_at` | `TIMESTAMP NOT NULL DEFAULT NOW()` | 创建时间 |
| `created_by` | `BIGINT` | 创建人（员工 ID） |
| `updated_at` | `TIMESTAMP NOT NULL DEFAULT NOW()` | 更新时间（触发器 `fn_m15_*_set_updated_at()` 维护） |
| `updated_by` | `BIGINT` | 更新人 |

**例外说明：**

- 各表用业务单号（`warehouse_code` / `stock_no` / `transaction_no` 等）对外暴露，`id` 仅内部使用
- `m15_stock_txn` / `m15_udi_log` / `m15_implant_log` 三张日志表**不加 `updated_at` / `is_deleted`**（只增，有触发器禁止修改与删除）
- `m15_stock` 等台账表**不加 `is_deleted`**（库存行不可删除，只能归零）
- 配置参数表用 `param_code + scope + scope_id` 唯一，见 1.9

### 1.3 枚举用法

**统一用 `VARCHAR(32) + CHECK` 约束，不用 PostgreSQL `ENUM` 类型。**

三条理由：

1. **`ALTER TYPE ... ADD VALUE` 不能在事务中执行**——迁移脚本必须先提交再改枚举，Alembic 的版本管理会出现「迁移已执行但事务回滚」的诡异状态
2. **删除或重命名枚举值要重建整个类型**——如果有表还在用，`DROP TYPE` 会失败
3. **应用层的 `Literal[...]` 已经提供了类型安全**——数据库层面用 `CHECK (col IN (...))` 已经足够，且修改成本极低

示例：

```sql
status VARCHAR(16) NOT NULL DEFAULT 'AVAILABLE'
    CHECK (status IN ('AVAILABLE', 'LOCKED', 'ISSUED', 'USED', 'EXPIRED', 'DAMAGED', 'RECALLED'))
```

### 1.4 时间语义

M15 有 **8 个核心时刻字段**，每个都有明确语义，不能混用：

| 字段 | 类型 | 所在表 | 语义 |
|---|---|---|---|
| `production_date` | `DATE` | `m15_stock` / `m15_stock_batch` | 生产日期（厂商提供） |
| `expiry_date` | `DATE` | `m15_stock` / `m15_stock_batch` | **厂商有效期** |
| `sterile_expiry_date` | `DATE` | `m15_stock` / `m15_stock_batch` | **灭菌有效期（一次性无菌包关键）** |
| `inbound_at` | `TIMESTAMP` | `m15_inbound` | 入库时刻 |
| `issued_at` | `TIMESTAMP` | `m15_issue` | 出库时刻 |
| `consumed_at` | `TIMESTAMP` | `m15_or_consume` | **术中消耗时刻（计费依据）** |
| `implanted_at` | `TIMESTAMP` | `m15_implant_usage` | 植入时刻（追溯锚点） |
| `occurred_at` | `TIMESTAMP` | `m15_stock_txn` | 库存事务发生时刻（分区键） |

**灭菌有效期是本模块特有的时间维度：**

一次性无菌包（手术包、缝线、穿刺包）厂商标注有效期 3 年，但**灭菌有效期只有 6 个月**——过了灭菌有效期即视为非无菌，不得用于手术。若系统只记录厂商有效期，会出现「系统显示有效、实物已失去无菌状态」→ 术后感染。

**实际可用效期公式：**

```text
effective_expiry_date = LEAST(expiry_date, COALESCE(sterile_expiry_date, expiry_date))
```

- 所有出库、分配、消费的有效期校验必须用 `effective_expiry_date`
- 数据库层面用生成列或子查询约束强制，不允许应用层自行判断

**典型错误：** 用 `created_at` 代替业务时刻做统计。

- `created_at` 是记录创建的系统时间，可能是补录（补录 10 月 20 日的入库，`created_at` 是 10 月 22 日）
- 用 `created_at` 统计「日入库量」会把补录的历史单据算到今天
- **所有统计必须用业务时刻字段，禁止用 `created_at`**

**时序校验：** 每个含多时刻的表都有 `ck_*_time_seq` 约束强制时序，例如：

```sql
CONSTRAINT ck_m15_issue_time_seq CHECK (
    issued_at IS NULL OR created_at <= issued_at
)
```

### 1.5 金额与数量类型

| 数据 | 类型 | 精度 | 理由 |
|---|---|---|---|
| 采购金额 | `NUMERIC(14,4)` | 4 位小数 | 人工晶体单价 6,500 元，4 位避免舍入累积 |
| 采购单价 | `NUMERIC(14,4)` | 4 位小数 | 同上 |
| 税率 | `NUMERIC(5,4)` | 4 位小数 | 0.1300 = 13% |
| 库存数量 | `NUMERIC(12,4)` | 4 位小数 | 支持小数（液体类耗材按 ml 领用） |
| 晶体度数 | `NUMERIC(6,2)` | 2 位小数 | −10.00 ~ +40.00 D |
| 百分比/比率 | `NUMERIC(6,4)` | 4 位小数 | 0.0000 ~ 1.0000 |

**禁止 `FLOAT` / `REAL` / `DOUBLE PRECISION`：**

`0.1 + 0.2 != 0.3` 在医疗费用与库存数量上是不可接受的。PostgreSQL 的 `NUMERIC` 是精确的十进制类型。

**行级先舍入再汇总：**

税额计算必须逐行先算再汇总，不能先汇总再算：

```text
逐行：  行1 = 100.00 / 1.13 = 88.50（不含税）+ 11.50（税额）
        行2~行10 同理
        合计不含税 = 885.00，合计税额 = 115.00

先汇总：合计含税 1000.00 / 1.13 = 884.96 + 115.04

差异：0.04 元
```

长期累积会导致三单匹配（订单-入库-发票）持续失败，且与增值税发票「逐行开票、汇总计税」的口径不一致。

### 1.6 中文检索

**`pg_trgm` + GIN 索引**用于耗材名称、患者姓名的模糊搜索：

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_m15_stock_name_trgm
    ON m15_stock
    USING gin (material_name gin_trgm_ops)
    WHERE is_deleted = FALSE;
```

**效果对比（15 年 11 万行库存）：**

| 查询 | 无索引 | 有 trgm 索引 |
|---|---|---|
| `material_name LIKE '%晶体%'` | 约 42ms（全表扫） | 约 1.8ms |

**为什么不用 `tsvector` 全文索引：** 中文分词需要额外扩展（`zhparser` / `pg_jieba`），而耗材名称检索的典型模式是「输入两三个字找匹配」，`pg_trgm` 的字符 n-gram 正好匹配这种场景。

### 1.7 `updated_at` 触发器

**应用层负责更新时间必然有遗漏**（批量 SQL 绕过 ORM、DBA 手工改、其他服务写入），用数据库触发器兜底：

```sql
CREATE OR REPLACE FUNCTION fn_m15_set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = CURRENT_TIMESTAMP;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

每个含 `updated_at` 的表都绑定该触发器。

### 1.8 软删除与部分唯一索引

**所有软删除表的唯一索引必须带 `WHERE is_deleted = FALSE`：**

```sql
CREATE UNIQUE INDEX uk_m15_warehouse_code
    ON m15_warehouse (warehouse_code)
    WHERE is_deleted = FALSE;
```

**不带条件的后果：** 删除编码 `OR-01` 的仓库后再新建同编码，唯一索引会拒绝——而业务上这是完全合理的操作。

### 1.9 配置参数表统一结构

7 张参数表（`m15_warehouse_config` / `m15_alloc_*` 中的配置、`m15_purchase_config` / `m15_issue_config` / `m15_stocktake_config` / `m15_consume_config` / `m15_implant_config`）结构一致：

```sql
CREATE UNIQUE INDEX uk_m15_xxx_config
    ON m15_xxx_config (param_code, scope, COALESCE(scope_id, 0))
    WHERE is_deleted = FALSE;
```

**为什么必须 `COALESCE`：** PostgreSQL 认为 `NULL` 与 `NULL` **不相等**，若 `scope_id` 可为空且不加 `COALESCE`，同一 `param_code + GLOBAL` 可以插入无数条，代码里取「第一条」时会时对时错。

**为什么不用 `NULLS NOT DISTINCT`：** 那是 PostgreSQL 15+ 才有，本项目要求兼容 14。

### 1.10 分区表主键必须含分区键

PostgreSQL 强制：分区表的唯一约束与主键必须包含分区键。

```sql
CREATE TABLE m15_stock_txn (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    transaction_no VARCHAR(32) NOT NULL,
    occurred_at TIMESTAMP NOT NULL,
    ...
    PRIMARY KEY (id, occurred_at)
) PARTITION BY RANGE (occurred_at);
```

**代价：** `transaction_no` 的唯一索引也必须带 `occurred_at`，实际上等价于「同一时刻的编号唯一」——但因为 `transaction_no` 本身含日期前缀（`TXN-20261024-0001`），跨年份不会重复，所以这个退化在本模块不构成风险。

### 3.3 逻辑外键而非物理外键

**决策：** 全部引用均为逻辑引用，**不建物理外键**。

| 理由 | 说明 |
|---|---|
| 性能 | `m15_stock_txn` 年 44 万行，每次插入都要校验外键会带来额外锁与索引查找；库存流水是最高频写入表 |
| 解耦 | 主数据可能先删后被引用（M01-04 逻辑删除），物理外键会阻止逻辑删除 |
| 分区兼容 | PostgreSQL 分区表与引用表之间的外键成本较高，且部分组合不支持 |
| 归档迁移 | 归档时需要 `DETACH PARTITION` 与 `DROP TABLE`，物理外键会导致归档失败 |

**一致性由三层保证：**

| 层 | 手段 | 覆盖 |
|---|---|---|
| 应用层 | 事务内成对写入 | 单据与明细、台账与流水 |
| 数据库约束 | `CHECK` 校验关联标识非空（如 `ck_m15_icount_schedule`） | 已建单必须有关联对象 |
| 每日巡检 | 04:00 定时任务检查孤儿数据 | 兜底发现异常 |

**孤儿数据巡检 SQL 示例：**

```sql
-- 检查是否存在无对应台账的流水（理论上不可能，异常时告警）
SELECT t.txn_no, t.material_code, t.warehouse_id
FROM m15_stock_txn t
LEFT JOIN m15_stock s
       ON s.warehouse_id = t.warehouse_id
      AND s.material_code = t.material_code
      AND s.batch_no = t.batch_no
WHERE t.occurred_at >= CURRENT_DATE - INTERVAL '1 day'
  AND s.id IS NULL;
```

### 4.1 命名规范

### 4.2 唯一索引中的 `COALESCE`

**问题：** PostgreSQL 认为 `NULL` 与 `NULL` 不相等。若唯一索引包含可空列，两条 `NULL` 记录不会冲突。

**示例：** `m15_alloc_policy` 的 GLOBAL 策略 `target_id` 为 `NULL`。若唯一索引写成 `(scope, target_id)`，则可以插入无数条 GLOBAL 策略，查询时取「第一条」会时对时错。

**解法：**

```sql
CREATE UNIQUE INDEX uk_m15_alloc_policy_scope
    ON m15_alloc_policy (scope, COALESCE(target_id, 0), COALESCE(target_code, ''))
    WHERE is_active = TRUE AND is_deleted = FALSE;
```

**为什么不用 `NULLS NOT DISTINCT`：** 该特性是 PostgreSQL 15 引入的，本项目部分环境仍是 PG 14，无法依赖。

### 4.3 部分索引

**适用场景：** 表中绝大多数行不满足查询条件，而查询频繁。

**示例对比（`idx_m15_alloc_lock_active`）：**

| 方案 | 索引大小 | 查询耗时 | 说明 |

| 无索引 | 0 | 约 46ms | 全表 165 万行 |
| 普通索引 | 约 42MB | 约 12ms | 索引树遍历 |
| **部分索引** | **约 8KB** | **约 0.1ms** | 只含在途锁定（0~50 条） |

运维看板每 5 秒刷新一次，一年 630 万次查询。46ms 是 80 小时 CPU，0.1ms 是 10 分钟。

### 5.4 分区自动创建

```sql
CREATE OR REPLACE FUNCTION fn_m15_create_month_partitions(p_table TEXT, p_months INTEGER DEFAULT 3)
RETURNS VOID AS $$
DECLARE
    v_i     INTEGER;
    v_start DATE;
    v_end   DATE;
    v_name  TEXT;
BEGIN
    FOR v_i IN 0..p_months - 1 LOOP
        v_start := (date_trunc('month', CURRENT_DATE) + (v_i || ' month')::INTERVAL)::DATE;
        v_end   := (v_start + INTERVAL '1 month')::DATE;
        v_name  := p_table || '_p' || to_char(v_start, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF %I FOR VALUES FROM (%L) TO (%L)',
            v_name, p_table, v_start, v_end
        );
    END LOOP;
END;
$$ LANGUAGE plpgsql;

-- 每月 25 日 02:00 预建未来 3 个月分区
SELECT cron.schedule(
    'm15_stock_txn_partition',
    '0 2 25 * *',
    $$SELECT fn_m15_create_month_partitions('m15_stock_txn', 3)$$
);
```

**不预建分区的后果：** 11 月 1 日第一条流水写入报 `no partition of relation "m15_stock_txn" found for row`，入库与出库全部失败，手术室备台中断。

### 5.5 归档四步

| 步 | 操作 | 检查 |
|---|---|---|
| 1 | `CREATE TABLE m15_stock_txn_archive_2023 (LIKE m15_stock_txn INCLUDING ALL)` | — |
| 2 | `INSERT INTO ... SELECT ... WHERE occurred_at < '2024-01-01'` | 行数记录 |
| 3 | 核对归档表行数 == 待删行数 | **不等则中止** |
| 4 | `ALTER TABLE m15_stock_txn DETACH PARTITION m15_stock_txn_p2023xx` 并 `DROP TABLE` | — |

**铁律：** 归档表行数必须与被删行数完全一致才可删主表。


同理 `fn_m15_udi_log_readonly()` 与 `fn_m15_implant_log_readonly()`。

**为什么用数据库触发器而非应用层保证：** 应用层可被绕过（DBA 手动修改、迁移脚本、其他服务 bug、重构遗忘），而库存流水是 GSP 检查与财务审计的依据，数据库级不可变才是真的不可变。

### 6.5 生成列

| 表 | 生成列 | 表达式 |
|---|---|---|
| `m15_stock` | `qty_available` | `GENERATED ALWAYS AS (qty_on_hand - qty_locked) STORED` |
| `m15_secondary_stock` | `qty_available` | 同上 |
| `m15_sec_stock` | `qty_available` | 同上 |

**理由：** 三数量恒等式由数据库强制，应用层没有机会算错。

### 8.2 号段内分布建议

| 号段 | 用途 |
|---|---|
| `xxx001`~`xxx009` | 通用（不存在 / 状态不允许 / 参数非法） |
| `xxx010`~`xxx029` | 业务规则（数量 / 金额 / 时序 / 匹配） |
| `xxx030`~`xxx049` | 权限与合规（数据权限 / SoD / 审核） |
| `xxx050`~`xxx069` | 集成失败（上游不可用 / 下游失败） |
| `xxx070`~`xxx099` | 预留 |

### 8.3 格式规范

**错误码为 7 位字符串 `AABBCCC`：**

| 段 | 长度 | 含义 | 示例 |
|---|---|---|---|
| AA | 2 | 模块号 | `15` |
| BB | 2 | 子模块号 | `03` |
| CCC | 3 | 子模块内序号 | `020` |

**示例：** `"1503020"` = M15-03 采购与入库 第 20 号错误。

**为什么必须是字符串：**

````text
错误 —— Python 3 会把前导零的数字解析为八进制字面量，直接语法错误
raise BizException(0150001, "耗材不存在")

正确 —— 带引号的字符串
raise BizException("1501001", "耗材不存在")
````

JSON 中同样必须带引号：

```json
{
  "code": "1503020",
  "message": "批号重复或有效期不一致",
  "data": null,
  "trace_id": "b7c8d9e0f1a2"
}
```

**成功时 `code` 仍为整数 `0`**（成功与错误分离，前端 `code === 0` 判断成功，否则查表）。

### B.2 关键时间字段（8 个）

| 字段 | 含义 | 用途 |
|---|---|---|
| `production_date` | 生产日期 | 效期推算 |
| `expiry_date` | 有效期（厂商） | 出库校验 |
| `sterile_expiry_date` | 灭菌有效期 | 出库校验（与上取小） |
| `inbound_at` | 入库时刻 | 成本归集、FIFO |
| `issued_at` | 出库时刻 | 出库到二级库 |
| `consumed_at` | 消耗时刻 | **计费依据** |
| `implanted_at` | 植入时刻 | **追溯锚点** |
| `occurred_at` | 流水发生时刻 | 分区键 |

**有效失效日：** `effective_expiry_date = LEAST(expiry_date, COALESCE(sterile_expiry_date, expiry_date))`

### B.3 关键金额与数量字段
