### 三条数据结构铁律

本子模块的三条铁律不是风格约定，而是**在表结构层面把错误做法变成不可表达**。每一条都在下面的字段表与约束里有对应的落地位置。

| 编号 | 铁律 | 落地位置 | 不这么做的后果 |
|---|---|---|---|
| **L-01** | **病历正文只有一个 `content_hash`，由本子模块计算并固化，外部只许原样引用** | `m18_emr_record.content_hash VARCHAR(64)` + 组合约束 `ck_m18_emr_record_hash_when_finalized` + 触发器 `trg_fn_m18_emr_record_signed_guard()` | 若 M07-06 用自己的 `content_snapshot` 再算一次，同一份病历会得到两个 hash，诉讼时无法举证患者签的是哪一份 |
| **L-02** | **病历事实表没有 `is_deleted` 列，也没有 DELETE 权限** | `m18_emr_record` / `m18_emr_record_field` 字段表不含该列 + `REVOKE DELETE ON ... FROM app_m18` | 一旦表上有 `is_deleted` 与 DELETE，就存在「删了旧的插新的」这条路径，而它和「篡改」在法律上无法区分 |
| **L-03** | **定稿之后正文不可原地修改，更正只能追加** | 触发器 `trg_fn_m18_emr_record_signed_guard()` + 列级 `REVOKE UPDATE` + `GRANT UPDATE (状态与审计列清单)` | 医生「顺手补一下」的记录会覆盖原始记录，而原始记录正是纠纷时最有价值的那份 |

### 命名与类型红线

| 项 | 规定 | 反例 |
|---|---|---|
| 主键 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `SERIAL`、`BIGSERIAL` |
| 单号/编码 | `VARCHAR(32)` ~ `VARCHAR(64)` | `INT` 存病历号 |
| 状态与枚举 | `VARCHAR(32)` + `CHECK` 约束，取值全大写英文 | `SMALLINT` 状态码、中文枚举值 |
| 金额 | `NUMERIC(14,2)` | `FLOAT` / `DOUBLE PRECISION` / `REAL` |
| 比率 | `NUMERIC(10,6)`，区间 [0,1]，分母为 0 时必须 `NULL` | `FLOAT`、分母为 0 时返回 0 |
| 时间 | `TIMESTAMP`（不带时区，全系统 `Asia/Shanghai`） | 带时区的 `TIMESTAMPTZ` 与本地时间混用 |
| 哈希 | `CHAR(64)` / `VARCHAR(64)`，SHA-256 小写十六进制 | `MD5`（已可构造碰撞） |
| 布尔 | `BOOLEAN` | `CHAR(1)` 存 Y/N |
| 结构化数据 | `JSONB`，且必须在设计说明里写清结构 | `TEXT` 存 JSON 字符串 |
| 主数据引用 | 一律**逻辑外键**，不建物理 `FOREIGN KEY` | 跨模块建物理外键 |

> **为什么一律不建物理外键：** 本子模块引用的 `encounter_id` / `patient_id` / `template_id` / `staff_id` 全部来自其他模块的库表。物理外键会在三个地方出问题：① 跨库根本建不了；② 主数据变更或数据迁移时外键会阻塞操作；③ 病历是历史快照，患者信息或科室撤并之后，病历里记录的历史事实不应该因为父行变动而失效。约束由应用层与本文件的唯一索引共同保证。

**合计：10 张表**

### 1.1 为什么是 10 张，而不是 7 张或 14 张

拆分与合并的分界线只有一条：**生命周期是否一致**。同一张表里的两块数据如果「什么时候改、谁能改、改了留不留痕」三件事有三件不同，就必须拆开。

| 决定 | 候选做法 | 为什么不那么做 |
|---|---|---|
| **正文与结构化字段分表** | 把 `chief_complaint` 等段落正文与模板字段值放同一张表 | 正文按段落固定为六段，字段值随模板变化（同一就诊类型不同专科可有 8~60 个字段），行宽会从 200 字节膨胀到 12,000 字节以上；而正文的更新频率是个位数次，字段值的更新频率是数百次（每次自动保存），二者放一起会让正文行被无效刷写 |
| **门诊补充信息独立** | 并入 `m18_emr_record` | 补充信息只对门诊病历类型有意义，`record_type` 为 `INPATIENT` / `DAY_SURGERY` 时这 15 个字段全为 `NULL`，会让 M18-03 住院病历继承一张有 15 个恒空列的表 |
| **过敏史明细独立** | 并入 `m18_opd_record_ext` | 过敏史的生命周期**跨就诊**：患者三年前在某次就诊记录的药物过敏，今天开处方时必须还查得到；它挂在 `patient_id` 上而不是挂在某份病历上，与病历「一次就诊一份、签完不再变」的生命周期正好相反 |
| **病史摘要独立** | 并入 `m18_emr_record` | 病史摘要有「从上次病历继承」与「本次填写」两个来源，需要记录继承自哪一次就诊，才可能在复诊时提示「与上次不一致」；这个溯源字段只在摘要上成立 |
| **诊断文本段独立且是多行** | 用 `m18_emr_record` 里的一个 `diagnosis_text` 字段承载全部诊断 | 一次门诊可有 1~6 条诊断，每条都要单独标注「主诊断/次诊断」、对应一个 M07-02 诊断编码、单独标记「是否与编码不一致」；放单字段就只剩一段拼接文本，质控无法定位是第几条诊断缺侧别 |
| **复制溯源独立成表** | 在病历上加 `copied_from_record_id` 一个字段 | 一次复制通常是「上次的全部六段 + 40 个字段」，需要按段/按字段记录来源，才能满足「引用内容必须可溯源」的质控要求；一个字段只能记「整份来自谁」 |
| **统计与配置独立** | 统计从主表实时聚合，配置写死在代码里 | 统计实时聚合要扫 145 万行主表，P95 超过 3 秒；配置写死则「必填项策略」每次调整都要发版，而这正是质控要求最高频调整的东西 |
| **操作日志独立且分区** | 并入主表或用通用审计日志 | 操作日志年增约 350 万条，与主表 1:2.4 的比例，放主表会把主表撑大三倍；而通用审计日志（M02）只记「谁调了哪个接口」，不记「这次写操作让哪一段从什么变成什么」 |

**没有拆成 14 张的理由：** 有人会主张「既往史、家族史、个人史也各建一张表」或「每个段落一张表」。这里不采纳，因为这三类史都是**同一份病历内、同一时刻一起提交、生命周期完全一致**的短文本，拆开的唯一收益是「字段命名更整齐」，代价是每次保存要写 6 张表、每次读取要做 6 次连接，而病历保存是医生的高频操作（每 60 秒自动保存一次）。

**关系说明**

| 关系 | 基数 | 说明 |
|---|---|---|
| `m18_emr_record` → `m18_emr_record_field` | 1 : N | 一份病历按模板展开 N 个字段值。字段值随模板版本变化，删除重建时以 `record_id` 全量替换 |
| `m18_emr_record` → `m18_opd_record_ext` | 1 : 1 | 只有 `record_type='OUTPATIENT'` 才有一行 |
| `m18_emr_record` → `m18_opd_history_summary` | 1 : 1 | 病史摘要，一份病历一行 |
| `m18_emr_record` → `m18_opd_diagnosis_text` | 1 : N | 一次就诊 1~6 条诊断，每条一行 |
| `m18_emr_record` → `m18_opd_copy_ref` | 1 : N | 一次复制记一段一行，一份病历可被多次复制 |
| `m18_emr_record` → `m18_opd_oper_log` | 1 : N | 每次写操作一行，跨月分区 |
| `m18_opd_allergy_detail` → 患者 | N : 1 | **挂在患者维度**，不挂在病历上；同一患者多次就诊共用 |
| `m18_opd_stat` / `m18_opd_config` | 无 | 独立表，不进 ER 主干 |

**逻辑外键（`FK*`）说明**

| 字段 | 指向 | 为什么是逻辑外键 |
|---|---|---|
| `m18_emr_record.encounter_id` | M07-01 `m07_encounter.id` | 跨模块；就诊可能被合并或撤销，物理外键会阻塞 |
| `m18_emr_record.patient_id` | M03-01 `mpi_patient.id` | 跨模块；患者合并（`mpi.patient.merged`）时需要重定向 |
| `m18_emr_record.template_id` | M18-01 `m18_tpl_template.id` | 同模块跨子模块；模板可能被下线但仍需能查到历史 |
| `m18_emr_record_field.field_def_id` | M18-01 `m18_tpl_field_def.id` | 同上 |
| `m18_opd_allergy_detail.patient_id` | M03-01 `mpi_patient.id` | 跨模块 |
| `m18_opd_diagnosis_text.diag_code` | M01 `mdm_diagnosis.code` | 主数据；用编码而非 ID，便于跨版本对照 |

**命名映射（共享规范 §9.3 要求的裁决）**

> M07-06 的 ER 图（`M07医生工作站/M07_医生工作站_06_文书签署与打印_数据结构.md:66`）里把病历表写作 `emr_record（M18）`，那是**简写**。M18 统一表名为 **`m18_emr_record`**，不存在名为 `emr_record` 的表。M07-06 与本子模块对接时以 `m18_emr_record` 为准，通过 P-01 `GET /internal/v1/emr/record/by-encounter/{id}` 读取，不直接读表。

**为什么不建物理外键**

| 理由 | 具体场景 |
|---|---|
| 跨模块库表 | `m07_encounter` / `mpi_patient` / `mdm_diagnosis` 不在同一数据库 schema，物理外键无法建立 |
| 历史快照语义 | 病历记录的是「2026-10-21 那天这位医生写了什么」，科室撤并或医生离职之后，病历里的 `dept_name` 快照仍应保留原值。物理外键 + 级联更新会改写历史 |
| 逻辑删除与物理外键互斥 | 父表逻辑删除后子表外键仍指向「已删除」的行，任何 `DELETE` 父行的操作都会变成死结 |
| 患者合并 | `mpi.patient.merged` 发生时，物理外键需要 `ON UPDATE CASCADE` 才能跟着改，而 CASCADE 会连带改写所有历史病历的 `patient_id`——这正是我们要避免的（历史病历应保留原 `patient_id`，只在索引层重定向） |

**分区说明**

10 张表里**只有 `m18_opd_oper_log` 分区**（按月 RANGE，分区键 `created_at`，必须建 DEFAULT 分区）。其余 9 张不分区，理由见 `M18_电子病历与知识库_数据结构设计汇总.md` §4：

- `m18_emr_record` 的唯一键是 `(encounter_id, record_type) WHERE is_current = TRUE`。PostgreSQL 分区表的唯一约束**必须包含分区键**，一旦把 `created_at` 塞进这个唯一键，「同一就诊同类型只能有一份当前病历」这条约束就失效了——而它正是防止同一就诊出现两份病历的最后一道闸。
- 其余表数据量在 26 万 ~ 870 万之间，单表完全可承受，且查询总是带 `patient_id` / `record_id` 精确条件，不走时间范围扫描。

### 4.2 表：`m18_emr_record`（门诊病历主档）

**用途：** 一份病历一行。承载病历正文六段、生命周期状态、`content_hash` 固化位、签署与作废留痕。**这是全 M18 的首建表**，M18-03 住院病历、M18-04 手术麻醉病历、M18-06 归档封存、M18-07 检索统计全部引用本表定义，`record_no` 与 `content_hash` 的语义在全 M18 范围内以本表为准。

**写入方：** M18-02 门诊病历工作台（`DRAFT` 期间的全部正文写入、`DRAFT→FINALIZED`、`FINALIZED/SIGNED→VOIDED`）；M07-06 签署回调只写 `status` `SIGNED` 与 `signed_at` `signed_by` 四项（受限权限列）。 **只读方：** M18-03/04/05/06/07、M07-06（经 P-01）、M05-06 病案首页、M22 指标采集、M18-07 检索。

**为什么要有这张表：** 门诊病历是法律文书。它必须同时满足三个互相拉扯的要求：① 医生写的过程要能反复修改（自动保存每 60 秒一次）；② 一旦定稿并签署，任何人不得改动一个字；③ 修改、作废、更正这三种动作本身要留下痕迹，而且痕迹不能被当成「正文的最新版本」。

把这三件事放在一张表里，靠**一个状态字段 + 一个哈希字段 + 一个正文不可变触发器**同时解决：`status` 决定「此刻能不能改」，`content_hash` 决定「改没改过」，触发器保证「说不能改就真的改不了」。这三个字段是全表存在的理由，其余 40 余个字段都是围绕它们组织的元信息与快照。

如果只用一个布尔 `is_signed`，无法区分「已定稿但未签署」（此时作废权在医生手上）与「已签署」（此时作废要医务科审批），也没法表达「作废后保留原记录」——而这三件事在纠纷处理中的举证责任方完全不同。

**约束说明**

```sql
-- 状态取值必须来自共享规范 §13，不得自创
ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_status
  CHECK (status IN ('DRAFT', 'FINALIZED', 'SIGNED', 'VOIDED'));

ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_type
  CHECK (record_type IN ('OUTPATIENT', 'INPATIENT', 'DAY_SURGERY', 'EMERGENCY'));

-- 组合约束 1：定稿之后必须有 content_hash 与 finalized_at
ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_hash_when_finalized
  CHECK (status = 'DRAFT'
         OR (content_hash IS NOT NULL AND finalized_at IS NOT NULL AND finalized_by IS NOT NULL));

-- 组合约束 2：content_hash 必须是 64 位小写十六进制（SHA-256）
ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_hash_format
  CHECK (content_hash IS NULL OR content_hash ~ '^[0-9a-f]{64}$');

-- 组合约束 3：算法只能是 SHA256，杜绝 MD5 混入
ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_hash_algo
  CHECK (hash_algo = 'SHA256');

-- 组合约束 4：已签署必须有签署人、签署时刻与对应文书
ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_signed_fields
  CHECK (status <> 'SIGNED'
         OR (signed_at IS NOT NULL AND signed_by IS NOT NULL AND signed_document_id IS NOT NULL));

-- 组合约束 5：已作废必须有原因、时刻、操作人
ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_void_fields
  CHECK (status <> 'VOIDED'
         OR (void_reason IS NOT NULL AND voided_at IS NOT NULL AND voided_by IS NOT NULL));

-- 组合约束 6：已作废不得再是当前病历
ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_void_not_current
  CHECK (status <> 'VOIDED' OR is_current = FALSE);

-- 组合约束 7：已签署病历作废，审批人必须与操作人不同（职责分离）
ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_void_segregation
  CHECK (status <> 'VOIDED'
         OR signed_at IS NULL
         OR (void_approved_by IS NOT NULL AND void_approved_by <> voided_by));

-- 组合约束 8：签署时刻不得早于定稿时刻
ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_time_order
  CHECK (signed_at IS NULL OR finalized_at IS NULL OR signed_at >= finalized_at);

-- 组合约束 9：作废时刻不得早于创建时刻
ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_void_time_order
  CHECK (voided_at IS NULL OR voided_at >= created_at);

-- 组合约束 10：字段计数自洽，完整率必须与两个计数一致
ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_field_count
  CHECK (field_filled_count >= 0
         AND field_total_count >= 0
         AND field_filled_count <= field_total_count);

ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_completeness
  CHECK ((field_total_count = 0 AND completeness_rate IS NULL)
      OR (field_total_count > 0
          AND completeness_rate IS NOT NULL
          AND completeness_rate >= 0
          AND completeness_rate <= 1));

-- 组合约束 11：作废原因不得为纯空白
ALTER TABLE m18_emr_record
  ADD CONSTRAINT ck_m18_emr_record_void_reason
  CHECK (void_reason IS NULL OR length(btrim(void_reason)) >= 5);

-- 病历事实表：应用账号无 DELETE 权限（铁律 L-02）
REVOKE DELETE ON m18_emr_record FROM app_m18;

-- 签署后禁改：列级 REVOKE UPDATE + 显式 GRANT 允许更新的列（铁律 L-03）
REVOKE UPDATE ON m18_emr_record FROM app_m18;
GRANT UPDATE (
    status, is_current, content_hash, finalized_at, finalized_by,
    signed_at, signed_by, signed_document_id,
    void_reason, voided_at, voided_by, void_approved_by,
    amended_count, sealed_flag, version_no, updated_at, updated_by
) ON m18_emr_record TO app_m18;
```

**设计说明**

| # | 设计点 | 为什么 |
|---|---|---|
| 1 | **正文六段用 `TEXT` 而不是 `VARCHAR(n)`** | 主诉正常 20 字，但一份眼科现病史可能写 3,000 字（含既往手术史、用药史、家族史）。`VARCHAR(2000)` 会在真实场景下截断，而截断发生在数据库层时应用层收不到明确错误（部分驱动静默截断），医生看到的是「保存成功但内容少了一半」 |
| 2 | **`content_hash` 用 `CHAR(64)` 且 CHECK 强制小写十六进制** | 64 位是 SHA-256 的固定输出长度，`CHAR` 对定长串的存储与比较更省。CHECK 用 `~ '^[0-9a-f]{64}$'` 而不是 `length(content_hash) = 64`，因为后者放行大写十六进制，而大写与小写会让同一份内容算出两个字符串，比对时判定为不一致 |
| 3 | **`hash_algo` 单值约束 `= 'SHA256'`** | 字段存在是为了让未来算法升级时能区分新旧行，但当前只允许 SHA256，把 MD5 与 SHA-1 挡在数据库层。**不写这个 CHECK 的话，某天有人用 MD5 算一遍写进来，表里就有两种算法混在一起，而校验逻辑只看长度 64 位是分辨不出的**（MD5 是 32 位，但会用 `LPAD` 补齐的写法真实存在） |
| 4 | **`hash_normalize_version` 独立成列** | 规范化规则（字段排序、空值处理、时间格式）未来一定会变——比如某天决定把全角空格也纳入归一化。规则一变，旧病历按新规则重算必然对不上。把规则版本记在行上，校验时按当期版本复现，历史病历不会被判为篡改 |
| 5 | **`uk_m18_emr_record_encounter_current` 是部分唯一索引，不带 `is_deleted` 条件** | 本表没有 `is_deleted` 列（铁律 L-02），所以不存在「软删除的行占着唯一键」的问题。如果加了 `AND is_deleted = FALSE`，一旦有人给某行置 `is_deleted = TRUE`，约束就放行出现两份当前病历，M07-06 拿到 P-01 的响应时不知道用哪份 |
| 6 | **`is_current` 与 `status` 两个字段并存** | 二者正交：`status` 说的是「这份病历走到哪一步」，`is_current` 说的是「在这次就诊里它是不是生效的那份」。作废后 `status='VOIDED'` 且 `is_current=FALSE`；重开的新病历 `is_current=TRUE`。若合并成一个字段，就无法表达「作废重开后，两份历史都还在，只有一份是当前」 |
| 7 | **组合约束 1 用 `status = 'DRAFT'` 正向白名单，而不是 `status <> 'DRAFT'` 反向** | 正向白名单在新增状态取值时会自动漏掉新状态（新状态没有枚举进 CHECK 就会先被约束 1 拦住），反向写法则在新增状态时自动放行。**病历类约束宁可「多拦」不可「少拦」**；漏拦的后果是出现一份没有 hash 的已定稿病历，而这正是防篡改的基石 |
| 8 | **组合约束 7 强制 `void_approved_by <> voided_by`** | 已签署病历的作废是高风险动作（相当于宣告「之前那份不算数」）。同一个人既能发起又能审批，等于没有审批。这条约束把「自己批自己」变成数据库拒绝写入 |
| 9 | **`diagnosis_text` 与 `m18_opd_diagnosis_text` 并存** | `diagnosis_text` 是**呈现文本**（医生最终写进病历的整段话，含「双眼老年性白内障（右眼成熟期）」这类表述），`m18_opd_diagnosis_text` 是**结构化拆解**（逐条诊断码、主次、侧别）。前者进 `content_hash`（因为它是病历正文的一部分），后者供质控与统计定位到具体某条。二者由 Service 层在同一事务内同步写入；`diagnosis_text` 不由后者拼接生成，因为医生可能写表达性文字（如「双眼老年性白内障，右眼较重」），拼接会丢失这层信息 |
| 10 | **`field_filled_count` / `field_total_count` / `completeness_rate` 冗余存储** | 完整率是质控与统计的高频指标（统计口径见总纲 `M18-CALC-01`）。实时计算要连 `m18_emr_record_field` 做 `COUNT`，在 870 万行的字段表上单次超过 80ms；而病历保存是每 60 秒一次的高频操作，实时算会把保存耗时拉长三倍。冗余值在每次保存时重算一次，风险是可能与明细不一致，因此由约束 10 保证三个字段两两自洽 |
| 11 | **`sealed_flag` 是冗余快照，真相在 `m18_emr_seal`** | 封存判定在触发器 `trg_fn_m18_seal_guard()` 里查 `m18_emr_seal`（共享规范 §3.3），本字段只是给列表页做快速筛选，避免列表页每行都子查询一次封存表。**必须在文档里写明它不是权威**，否则后续维护者会拿它做写入判定，而这个字段是可以被延迟更新的 |
| 12 | **`amended_count` 而不是 `has_amendment`** | 更正可能多次。数量比布尔多一个信息量：质控可以针对「更正 3 次以上」的病历做专项审查，而布尔做不到 |
| 13 | **患者姓名/性别/年龄/身份证掩码做快照** | 患者改名或改身份证后，历史病历上记的必须是「当时那位患者叫什么」。这不是冗余，是法律文书的必备要素。身份证只存掩码，明文不出库（共享规范 §2.4） |
| 14 | **`created_at` 与 `record_date` 分离** | 门诊病历允许跨日补写（当日未写完次日补）。`record_date` 是就诊日期，是及时率的分母依据；`created_at` 是系统写入时刻。若只有一个字段，及时率会算错——补写的病历会被算成当天完成（总纲 `M18-CALC-03` 算例里 92.00% 与 87.62% 的差就出在这里） |
| 15 | **`signed_document_id` 让病历能反查 PDF** | 铁律 6 规定同意书与文书的签署状态权威在 M07-06，M18 不建签署状态表。但病历需要知道「我被哪份文书承载」，否则患者来取病历复印件时无法定位 PDF。存一个逻辑外键而不是存签署状态，既满足反查又不越权 |

### 4.3 表：`m18_emr_record_field`（病历结构化字段值）

**用途：** 按模板字段逐项存储的结构化取值。一份病历按 `template_version` 展开 N 行（眼科门诊常见 12~60 行），每行回答「这个字段填了什么」。它是结构化录入、必填项校验、质控规则命中、以及 M18-07 检索的**唯一数据来源**。

**写入方：** M18-02 门诊病历（自动保存与定稿前写入，`record.status='DRAFT'` 期间可重复覆盖）；M18-05 质控只读。 **只读方：** M18-03/04（复用同表存住院与手术病历的字段值）、M18-05 质控、M18-07 检索与统计、M07-06（经 P-01 取结构化摘要）。

**为什么要有这张表：** 病历正文六段是**给人和机器读的自然语言**，无法支撑三类硬需求：① 必填项校验（「眼底检查」这一段里有没有写黄斑情况，纯文本无法判断）；② 质控规则（「诊断缺侧别」——语文上判断不出来，必须靠字段 `diag_eye_side` 是否有值）；③ 检索统计（「本月屈光门诊有多少份病历记录了角膜厚度」——纯文本只能全文检索，误命中率超过 40%）。

但字段不能写死在表里：眼科门诊、屈光门诊、干眼门诊、青光眼门诊的字段集合各不相同（共享规范 §13 的 `field_type` 有 13 种，模板由 M18-01 定义）。**因此采用「一行一个字段值」的纵向结构**——表结构不随业务科室变化，变化的是行数与 `field_code`。

**为什么不用 JSONB 把全部字段塞进 `m18_emr_record` 的一个列：** JSONB 适合「整体读写、偶尔按键查询」的场景。病历字段值的真实使用方式是：① 按 `field_code` 跨病历聚合（统计某项检查的阳性率）；② 按字段做范围查询（眼压 > 21）；③ 按字段做唯一性与必填校验。这三类在 JSONB 上都要建表达式索引，而 `field_type` 有 13 种时表达式索引会有 13 份，维护成本与体积都高于纵向表。纵向表的代价是行数多（870 万），但行宽极小（约 120 字节），完全可承受。

  CHECK (field_type <> 'TABLE'
         OR value_table IS NULL
         OR jsonb_typeof(value_table) = 'array');

**设计说明**

| # | 设计点 | 为什么 |
|---|---|---|
| 1 | **纵向表而不是 JSONB 列** | 见本节开头的三段论证。核心判据是「字段值的读取模式是按字段跨病历聚合」——这类查询在纵向表上是一条普通的 `WHERE field_code = ? AND value_numeric > ?`，在 JSONB 上要建 13 个类型的表达式索引 |
| 2 | **`field_code` 与 `field_name` 双存** | 模板字段改名（「眼压」改成「眼内压」）是常见操作。历史病历上显示的应该是**当时的名称**，否则医生回看三年前的记录会疑惑「这个『眼内压』和我当时填的『眼压』是不是两个东西」。`field_code` 稳定用于查询，`field_name` 快照用于呈现 |
| 3 | **`value_numeric` 用 `NUMERIC(14,4)` 而非浮点** | 眼压 16mmHg、角膜厚度 512μm、屈光度 -4.75D 都是需要精确等值判断的值（质控规则会写「屈光度为 -4.75 时提示……」）。`FLOAT` 存 -4.75 会变成 -4.7500000000000001，等值比较失败。精度取 4 位小数：屈光度规范记到 0.25D 步长（1 位足够），眼压整数，角膜厚度整数，但角膜曲率 K 值要 2 位、角膜散光轴位要整数——4 位是覆盖全部已知字段的最小安全值 |
| 4 | **13 种 `field_type` 配 9 条组合约束，而不是「用哪个槽都行」** | 如果不约束，`field_type='NUMBER'` 的行可能把值写进 `value_text`，此时 `idx_m18_emr_field_code_value` 的范围查询扫不到它，统计会**静默少算**。组合约束 1/2/3/4/5 的作用是让「类型与存储槽不匹配」在数据库层写不进去 |
| 5 | **组合约束 6 用「两分支穷尽」而不是单向蕴含** | 单向 `CHECK (is_abnormal = FALSE OR abnormal_level IS NOT NULL)` 只能拦住「标记异常却没级别」，拦不住「没标异常却带着级别」——后者会造成统计口径混乱：按 `abnormal_level` 数异常项会比按 `is_abnormal` 数多。这与本子模块在 M19 那一轮的四分支穷尽经验同源 |
| 6 | **`uk_m18_emr_record_field` 让自动保存可以用 `ON CONFLICT DO UPDATE`** | 病历每 60 秒自动保存一次，覆盖同一字段是常态。有唯一键就能写成一条幂等的 upsert；没有唯一键则要「先查后插」，在并发（PC 端与移动端同时开）时会产生重复行，而重复行会让「按字段取值」的统计翻倍 |
| 7 | **`ref_range_low` / `ref_range_high` 冻结在行上** | 参考范围会随医学共识更新（比如眼压正常上限从 21mmHg 调整）。冻结在行上的意义是：三年前判为异常的那个值，今天回看仍然是异常——判据是当时的判据。若实时取当前参考范围，历史异常标记会随规则更新而变化，质控复查时无法解释 |
| 8 | **`source_type` 与 `is_carried_over` 并存** | `source_type` 说的是**值的来源机制**，`is_carried_over` 说的是**是否来自上次就诊**。二者交叉：`COPY` 可以是「复制上次病历」（此时 `is_carried_over=TRUE`）也可以是「引用同事模板」（`is_carried_over=FALSE`）。合并成一个枚举会丢失「跨就诊继承」这个质控最关心的信号——复诊时有多少字段是医生真的重新问了、多少是沿用 |
| 9 | **`carried_from_record_id <> record_id` 自引用约束** | 「继承自自己」在业务上是荒谬的，但数据库层合法。这类行会让追溯逻辑陷入无限循环（追到源病历发现源就是自己） |
| 10 | **不建 `REVOKE UPDATE`（本表允许更新）** | 字段值在 `DRAFT` 期间必须可反复覆盖，这是自动保存的前提。禁改的保护不落在本表，而落在触发器 `trg_fn_m18_emr_record_signed_guard()` 与封存守卫上——它们通过 `record_id` 找到主档判断状态，状态不允许时拒绝写入。**换句话说：本表自己不设防，防护在父表的状态上**；这条设计的前提是「所有写字段值的路径都必须携带 `record_id`」，见详细设计 §8.7 |

### 4.4 表：`m18_opd_record_ext`（门诊病历补充信息）

**用途：** 存放门诊病历特有的、不属于正文六段也不属于结构化字段的补充项：复诊标识、首诊/复诊关系、转归、随访建议、下次复诊时间、是否需住院、是否需手术等。一份门诊病历一行。

**写入方：** M18-02 门诊病历（保存正文时一并写入，`DRAFT` 期间可覆盖）。 **只读方：** M18-07 检索统计、M07-01 接诊（复诊判定）、M18-05 质控（转归与随访建议是完整性规则的一部分）。

**为什么要有这张表：** 这 16 个字段全部是**门诊独有**的。如果并入 `m18_emr_record`，那么住院病历（`record_type='INPATIENT'`）、日间手术病历（`DAY_SURGERY`）、急诊病历（`EMERGENCY`）三种类型的每一行都会有 16 个恒为 `NULL` 的列。这不是理论担忧——`m18_emr_record` 是全 M18 共用的主档表，住院病历年增约 3.2 万行，日间手术约 1.8 万行，十年下来主表会积累 50 万行「一半列永远为空」的数据，而任何一次全表扫描（备份、统计、导出）都要为这些空列付出 I/O。

更重要的是**约束**：如果把转归、复诊时间这些字段挂在主表上，就不得不在约束里写 `CHECK (record_type <> 'OUTPATIENT' OR 转归相关约束)`，主表的约束数量会从 11 条涨到 25 条，而其中 14 条对住院病历毫无意义。约束集中的表，每次写入的校验开销都是实打实的。

ALTER TABLE m18_opd_record_ext
  ADD CONSTRAINT ck_m18_opd_ext_first_visit_shape

          AND prev_record_id IS NULL
          AND prev_visit_date IS NULL

          AND prev_visit_date IS NOT NULL

ALTER TABLE m18_opd_record_ext

-- 组合约束 3：visit_type 与 is_first_visit 必须一致
ALTER TABLE m18_opd_record_ext
  ADD CONSTRAINT ck_m18_opd_ext_visit_type_pair

ALTER TABLE m18_opd_record_ext

ALTER TABLE m18_opd_record_ext

  CHECK (need_referral = FALSE

  ADD CONSTRAINT ck_m18_opd_ext_transfer_in
  CHECK (visit_type <> 'TRANSFER_IN' OR referral_source IS NOT NULL);

  ADD CONSTRAINT ck_m18_opd_ext_sick_leave
  CHECK ((work_capacity = 'SICK_LEAVE'
          AND sick_leave_days IS NOT NULL AND sick_leave_days > 0
          AND sick_leave_start IS NOT NULL)

  CHECK (next_visit_date IS NULL OR next_visit_date > record_date);

**设计说明**

| # | 设计点 | 为什么 |
|---|---|---|
| 1 | **`is_first_visit` 与 `visit_seq` 双存并强约束一致** | `visit_seq` 是「第几次」这个数量信息，`is_first_visit` 是「是否首诊」这个判定信息。有人会问「`visit_seq = 1` 不就等价于首诊吗」——不等价：患者可能在本院其他科室看过，本科室是第一次（`visit_seq=1` 且 `is_first_visit=TRUE`）；也可能首次就诊走了绿色通道未建病历（`visit_seq=2` 但业务上是初诊）。两个字段都保留，并用组合约束 2 保证「首诊必是第 1 次」，反过来「第 1 次不一定是首诊」由业务解释 |
| 2 | **组合约束 1 用的是「两分支穷尽」** | 单向写法 `CHECK (is_first_visit = FALSE OR prev_visit_date IS NULL)` 只拦住「首诊却带着上次就诊日期」，拦不住「复诊却没有上次就诊日期」。后者会让复诊间隔计算得到 `NULL`，进而在「平均复诊间隔」统计里被静默丢弃——分母少算，指标虚高 |
| 3 | **`visit_interval_days` 冗余存储** | 它是 `record_date - prev_visit_date` 的派生值。存下来的理由是：质控与统计要按它做范围筛选（「复诊间隔超过 180 天的有多少份」），而两个日期列相减无法走索引。冗余的代价是可能与两个日期不一致，因此约束 1 要求「复诊必须有值且 ≥ 0」 |
| 4 | **组合约束 9：下次复诊日期必须严格晚于就诊日期** | 允许 `next_visit_date = record_date` 会创造出「今天就诊、建议今天再来」这种无意义的行，下游的复诊提醒会在当天重复推送。严格大于（不是大于等于）是刻意的 |
| 5 | **组合约束 8 同时约束「非病假类不得写天数字段」** | 只约束「病假类必须写」会留下「工作能力填『无限制』但病假 7 天」这种矛盾行。这类行在打印病假条时会被错误地打印出来——而病假条是有法律效力的证明文件 |
| 6 | **`special_note` 单独成字段而不是塞进 `followup_advice`** | 它承载的是「患者拒绝手术，已充分告知风险」这类**免责留痕**，与随访建议的用途完全不同，且需要单独检索（医疗纠纷时第一件事就是查有没有拒绝治疗的记录）。混在一起之后，检索只能靠全文匹配，漏检率极高 |
| 7 | **`outcome='REFERRED'` 与 `need_referral=TRUE` 必须同时成立** | 转归判为「转诊他院」却没有任何转诊目标与理由，是一份无法执行也无法追溯的病历——患者拿着它不知道去哪，医院也无法证明做过转诊沟通 |

### 4.5 表：`m18_opd_allergy_detail`（过敏史明细）

**用途：** 记录患者的过敏原明细——过敏原是什么、什么类型、什么反应、多严重、什么时候发现的、谁记录的、当前是否仍有效。**这是全院的过敏信息权威来源**，M07-05 开处方时的过敏校验、M14-06 处方审核的过敏规则、M18-08 知识库的过敏禁忌判断全部以本表为准。

**写入方：** M18-02 门诊病历的「病史与过敏史」页面（新增、修改、失效）。变更后必须发布 `m18.allergy.updated` 事件。 **只读方：** M07-05 处方与用药、M14-06 处方审核、M18-08 临床知识库、M18-05 质控、M18-07 检索、M03-01 患者主索引（经事件回写冗余字段，**不直接读表**）。

**为什么要有这张表：** 全院最危险的一类缺陷是**过敏拦截静默失效**：医生开了患者过敏的药，系统没有任何提示，患者吃下去过敏。这个失效不会报错、不会告警、不会出现在任何日志里，它只是「没有提示」。而它能否生效，取决于一件事——**过敏信息有没有一个可靠的、结构化的、可查询的存放位置**。

M03-01 的 `mpi_patient.allergy_history` 是一个自由文本冗余字段（`M03_患者服务与EMPI/M03_患者服务与EMPI_01_患者主索引与建档_数据结构.md:220` 明确写「明细由 M18 过敏史模块维护，变更时通过事件更新」）。自由文本无法支撑「这个患者是否对头孢曲松过敏」这个精确判断——「青霉素过敏」与「青霉素不过敏」在文本上都是一个子串匹配能命中的。**结构化明细是过敏拦截能生效的前提。**

本表挂在 `patient_id` 上而不是挂在 `record_id` 上，因为过敏是**跨就诊的生命周期**：患者三年前在某次门诊记录的「磺胺类药物过敏」，今天在另一家分院开药时必须还查得到。挂在病历上意味着要遍历该患者全部历史病历才能拼出过敏清单，而开处方是 300ms 内的实时操作。

**设计说明**

| # | 设计点 | 为什么 |
|---|---|---|
| 1 | **挂在 `patient_id` 而非 `record_id` 上** | 见本节开头的论证。核心判据：过敏的生命周期跨就诊，而病历的生命周期是「一次就诊一份、签完不再变」。挂在病历上会让开处方时需要遍历全部历史病历，300ms 内做不到 |
| 2 | **`allergen_code` + `allergen_generic_code` 双编码，对 `DRUG` 类强制要求后者** | 过敏拦截有两种匹配：**精确匹配**（对「头孢曲松」过敏 → 拦截头孢曲松）与**类别匹配**（对「头孢曲松」过敏 → 提示所有头孢菌素类）。后者依赖通用名/类别编码。只存精确编码时，患者对头孢曲松过敏、医生开头孢呋辛，系统不会提示——而这两种药同属三代头孢，交叉过敏率不可轻视。组合约束 2 强制药品类必须写类别码，让「类别匹配」在数据层面一定可行 |
| 3 | **`allergen_raw_text` 保留口述原文** | 患者说「我对那个什么霉素过敏」，护士可能匹配不到标准编码。此时保留原文而不是拒绝录入——**宁可存一条匹配不上的记录，也不能因为匹配不上就不存**。后续由药师核实并补编码。丢掉原文等于丢掉了唯一的线索 |
| 4 | **组合约束 4：致命性过敏不能仅凭患者随口一说** | 这条看似反直觉——如果患者说「我青霉素过敏性休克」，难道不该直接标 `LIFE_THREATENING` 吗？业务上确实标，但 `severity='LIFE_THREATENING'` 会触发**最严格的处方拦截**（BLOCK 级，医生必须走特殊审批才能开药）。仅凭口述就触发 BLOCK，会让一部分记忆有误的患者无法拿到本该用的药。因此要求：要么已核实（`CONFIRMED` / `SUSPECTED`），要么来源是病历/皮试/书面资料。患者口述的致命性过敏录进来时 `severity` 先记 `SEVERE`，`verify_status='REPORTED'`，由药师核实后升级 |
| 5 | **`allergy_status` 三态而不是布尔 `is_active`** | `UNKNOWN` 这一态无法用布尔表达：「患者说不清自己有没有过敏」与「明确没有过敏」是两件事。前者在开处方时应提示医生再问一次，后者可以直接放行。合并成布尔必然丢掉一个 |
| 6 | **唯一键 `(patient_id, allergy_type, allergen_code)` 保证一个过敏原一行** | 同一个患者被三个科室分别录入「头孢曲松过敏」，如果允许三行，则：① 作废时要作废三条，漏一条就还在拦截；② 统计「有多少患者对头孢过敏」会重复计数。要求唯一后，重复录入走「更新已有行」（改严重程度、补反应描述） |
| 7 | **`idx_m18_opd_allergy_sync` 是事件补偿扫描的索引** | `m18.allergy.updated` 事件发布失败时（MQ 不可用、M03 消费者宕机），M03 的冗余字段会永远停留在旧值。补救办法是扫描 `last_changed_at > 上次同步水位` 的行重新发布。没有这个部分索引，补偿任务要全表扫 12 万行，而正常情况下只有个位数行需要重发 |
| 8 | **`version_no` 既是乐观锁也是事件版本号** | 事件载荷里的 `version` 取的就是这个字段。M03 收到事件时比对「我当前的版本 < 事件版本」才更新，从而丢弃乱序到达的旧事件。如果事件只带时间戳，同一毫秒内的两次变更会分不出先后 |
| 9 | **不设 `is_deleted`，失效用 `allergy_status='INACTIVE'`** | 过敏史是**临床证据**：患者三年前对某药过敏、现在说不清，这条记录不能消失——它解释了为什么当年的病历里避开了该类药。物理删除会让历史病历出现「无故换药」的疑点 |
| 10 | **`record_id` 可空** | 过敏可以在非就诊场景录入（患者入院时由护士站补录、药师在用药咨询时补充）。强制要求 `record_id` 会让这些入口无法写入，从而逼迫它们走「先建一份空病历」的歪路——那会在病历表里造出没有正文的记录 |

### 4.6 表：`m18_opd_history_summary`（病史摘要与既往诊疗要点）

**用途：** 保存本次门诊病历所引用的**既往病史摘要**——既是跨就诊的既往史快照（避免每次书写都去翻历史病历），也是「本次病历引用了哪些历史就诊」的可追溯凭据。一行对应一次「病史抽取」动作，包含抽取来源、抽取时间、抽象后的文本以及被引用的历史病历集合。

**写入方：** M18-02（书写时自动抽取 + 医生手工修订）

**只读方：** M18-02（下次就诊复用）、M18-05（质控：既往史与本次诊断一致性）、M18-06（归档打包：既往诊疗要点随病历归档）、M18-07（检索：按既往史关键词检索）

**为什么要有这张表：**

门诊病历的既往史段落有两个互相冲突的要求：

1. **必须准确**——「否认高血压、糖尿病史」这句话如果每次都由医生凭记忆重填，第一个月就开始失真：老患者复诊三次，三次填的既往史可能三种版本。
2. **必须反映「当时知道什么」**——一份 2026-10 的病历上若把 2027-03 才确诊的糖尿病补进既往史，这份病历就成了不实记录。病历是法律证据，既往史必须是**书写当时的事实快照**，不能随患者后来的病情变化而变。

把既往史抽出来独立成表，让「抽取来源」与「抽取时间」显式化：`extracted_at` 记录快照时刻，`source_record_ids` 记录引用了哪几份历史病历。三个月后患者确诊糖尿病，我们不改 2026-10 那份病历的既往史（改了就是伪造），而是让下一次就诊重新抽取——**新的抽取结果自然带上糖尿病，老病历保持它当时的原貌**。

另一个现实原因：本院门诊量按日均 1,200 人次计，其中复诊占比约 62%。复诊患者每次书写都把「上次的既往史」重打一遍，按平均 40 字、医嘱输入速度 60 字/分钟计，每位复诊患者多耗 40 秒——全院每天约 496 分钟医生时间（≈8.3 医生小时），一年约 1,800 医生小时。抽取 + 医生确认的模式把这部分时间压到 5 秒以内。

ALTER TABLE m18_opd_history_summary
    ADD CONSTRAINT ck_m18_opd_history_extract_mode
    CHECK (extract_mode IN ('AUTO', 'MANUAL', 'AUTO_EDITED'));

-- 组合约束 1：抽取模式与抽取元数据必须成套出现
-- AUTO / AUTO_EDITED 必须有抽取时刻与规则版本；MANUAL 必须两者皆空
ALTER TABLE m18_opd_history_summary
    ADD CONSTRAINT ck_m18_opd_history_extract_shape
    CHECK (
        (extract_mode = 'MANUAL'
             AND extracted_at IS NULL
             AND extractor_version IS NULL
             AND source_visit_count = 0)
        OR (extract_mode IN ('AUTO', 'AUTO_EDITED')
             AND extracted_at IS NOT NULL
             AND extractor_version IS NOT NULL)
    );

-- 组合约束 2：source_visit_count 必须等于 source_record_ids 的数组长度
-- 缓存字段与源数据不一致时，宁可让写入失败，也不要让两个数各自说谎
ALTER TABLE m18_opd_history_summary
    ADD CONSTRAINT ck_m18_opd_history_source_count
    CHECK (source_visit_count = jsonb_array_length(source_record_ids));

-- 组合约束 3：确认状态与确认元数据必须成套出现（两分支穷尽）
ALTER TABLE m18_opd_history_summary
    ADD CONSTRAINT ck_m18_opd_history_confirm_shape
    CHECK (
        (is_doctor_confirmed = FALSE
             AND confirmed_at IS NULL
             AND confirmed_by IS NULL)
        OR (is_doctor_confirmed = TRUE
             AND confirmed_at IS NOT NULL
             AND confirmed_by IS NOT NULL)
    );

-- 组合约束 4：源头最晚就诊日期不得晚于抽取时刻的日期（不能引用未来的病历）
ALTER TABLE m18_opd_history_summary
    ADD CONSTRAINT ck_m18_opd_history_source_date
    CHECK (extracted_at IS NULL
           OR last_source_visit_date IS NULL
           OR last_source_visit_date <= extracted_at::date);

ALTER TABLE m18_opd_history_summary
    ADD CONSTRAINT ck_m18_opd_history_version
    CHECK (version_no >= 1);

REVOKE DELETE ON m18_opd_history_summary FROM app_m18;

**分区策略：** 不分区。按病历主档同生命周期，量级与 `m18_emr_record` 同阶（每份病历一行），三年约 145 万行，`uk_m18_opd_history_record` 保证精确访问。分区反而会让「一份病历一份摘要」的唯一约束必须带上分区键，破坏语义（见数据结构汇总 §4 裁决）。

**设计说明**

| # | 设计点 | 为什么 |
|---|---|---|
| 1 | **存快照而不是外键关联历史病历** | 用外键关联历史病历看似更「规范」，但历史病历可以作废、可以被更正（`m18_emr_amendment`）。一旦历史被改，本次病历上写的既往史就会**跟着变**，而本次病历已经签署、内容哈希已固化——哈希对不上就判定被篡改。存文本快照 + 记录来源 id，让「当时看到什么」永久可查 |
| 2 | **`allergy_snapshot` 单独存一份，不与 `allergy_snapshot_at` 共享 `extracted_at`** | 提取时点与过敏时点可能相隔数天：医生 10-21 上午提取病史，10-21 下午患者做了皮试新增过敏。此时过敏信息比既往史更新。合并成一个时间戳会让审计无法判断「这句既往史记的是哪个时刻的过敏」 |
| 3 | **`source_visit_count` 冗余但用约束强制一致** | 明细统计与质控都按「病史引用深度」分组，每次都 `jsonb_array_length()` 会让 145 万行全扫。冗余缓存是常规做法，但**冗余字段最大的风险是漂移**——所以用组合约束 2 让数据库在写入时强制相等，漂移不可能发生 |
| 4 | **`is_doctor_confirmed` 独立于定稿校验** | 抽取是机器行为，机器会抽错（把别人的病史抽过来、把「否认糖尿病」抽成「糖尿病」）。定稿时若未确认就拦截，是为了让医生必须**读一眼**。但确认动作单独记录时刻与人，是为了事后能区分「医生真的看过」和「医生一路回车点过去」——后者在质控中体现为确认耗时的分布异常 |
| 5 | **`source_record_ids` 用 JSONB 数组而非关联表** | 关联表要建第 11 张表，而这张关联表永远只被「展示引用链」和「反查被引用」两个场景读，没有独立属性。用 GIN 索引的 JSONB 数组足够，且写入是单行操作。**判据：关联是否携带属性。** 携带（如「引用的是第几段」）才建表 |
| 6 | **`chronic_conditions` / `long_term_medications` 只存编码或短句，不存完整描述** | 这三个 JSONB 字段服务于**统计与质控**，不服务于书写呈现。写入完整描述会让它们变成第二份既往史正文，与 `past_history_text` 形成双写。只存编码 + 短句，既够聚合又不会漂移 |

### 4.7 表：`m18_opd_diagnosis_text`（病历诊断段落文本行）

**用途：** 保存门诊病历**诊断意见段落**的逐行文本与排序。诊断的**编码**由 M07-02 持有（`m07_diagnosis`），本子模块不建诊断表、不写诊断编码；本表只保存「这段病历纸面上印的诊断文字」及其行序号、主次关系、与 M07-02 诊断记录的引用关系。

**写入方：** M18-02（从 M07-02 拉取诊断后生成文本行；医生可在病历内调整措辞与排序）

**只读方：** M18-05（质控：诊断与主诉/检查的对应性）、M18-06（归档）、M18-07（按诊断检索病历）

**为什么要有这张表：**

诊断在这套系统里有**两个不同的事实**，必须分开存放：

1. **诊断编码事实**——M07-02 的 `m07_diagnosis`，带 ICD 编码、主诊断标志、确诊/疑诊状态，是统计、医保结算、病案首页的依据。
2. **病历文本事实**——病历纸上印出来的那行字，如「双眼老年性白内障（右眼成熟期）」。它是医生最终签字认可的表达，可能与编码不完全一致（编码是「H25.901 老年性白内障」，文本里写了分期限定）。

很多系统的做法是「编码表里存一个名称字段，打印时直接拼」，这在眼科会立刻出问题：同一 ICD 编码 H25.901 在不同病历上呈现为「老年性白内障」「老年白内障（右眼）」「白内障（成熟期）」，医生按病历书写规范各不相同。若统一按编码名称打印，等于把医生的书写权剥夺了。

反过来，若病历只存自由文本、不关联编码，则统计与医保全废。**两个事实都必须留，且必须是两处独立存储**：本表存文本，`m07_diagnosis` 存编码，用 `m07_diag_id` 逻辑关联。

再一个原因：病历诊断段落可以有**多行**（主诊断 + 并发诊断 + 并发症），且有严格的主次顺序（主诊断必须在第一行，医保规范要求）。用父表的 `diagnosis_text` 单个 TEXT 字段存不了逐行结构，质控也判断不了「第几行是主诊断」。

**字段定义**

| 字段名 | 类型 | 允许空 | 默认 | 说明 |

| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 否 | — | 主键 |

**约束说明**

```sql
ALTER TABLE m18_opd_diagnosis_text
    ADD CONSTRAINT ck_m18_opd_diagtext_diag_type
    CHECK (diag_type IN ('DEFINITE', 'SUSPECTED', 'COMPLICATION', 'COMORBIDITY'));

ALTER TABLE m18_opd_diagnosis_text
    ADD CONSTRAINT ck_m18_opd_diagtext_eye_side
    CHECK (eye_side IS NULL OR eye_side IN ('OD', 'OS', 'OU', 'NA'));

ALTER TABLE m18_opd_diagnosis_text
    ADD CONSTRAINT ck_m18_opd_diagtext_ref_status
    CHECK (ref_status IN ('SYNCED', 'TEXT_EDITED', 'M07_MISSING', 'UNLINKED'));

ALTER TABLE m18_opd_diagnosis_text
    ADD CONSTRAINT ck_m18_opd_diagtext_lock
    CHECK (ref_lock_status IN ('UNLOCKED', 'LOCKED'));

-- 组合约束 1：主诊断必须排在第一个，且只能是「确诊」性质
ALTER TABLE m18_opd_diagnosis_text
    ADD CONSTRAINT ck_m18_opd_diagtext_primary_shape
    CHECK (is_primary = FALSE OR (line_seq = 1 AND diag_type = 'DEFINITE'));

-- 组合约束 2：诊断性质与关联状态必须自洽
-- 有 m07_diag_id 就必须有 diag_code（M07-02 一定有编码）；
-- 没有 m07_diag_id 时 ref_status 只能是 UNLINKED，不能是 SYNCED
ALTER TABLE m18_opd_diagnosis_text
    ADD CONSTRAINT ck_m18_opd_diagtext_link_shape
    CHECK (
        (m07_diag_id IS NOT NULL AND diag_code IS NOT NULL
             AND ref_status IN ('SYNCED', 'TEXT_EDITED', 'M07_MISSING'))
        OR (m07_diag_id IS NULL AND ref_status = 'UNLINKED')
    );

-- 组合约束 3：行序号必须从 1 起且为正
ALTER TABLE m18_opd_diagnosis_text
    ADD CONSTRAINT ck_m18_opd_diagtext_seq
    CHECK (line_seq >= 1);

-- 组合约束 4：文本行不得为空白字符串（NOT NULL 挡不住空串）
ALTER TABLE m18_opd_diagnosis_text
    ADD CONSTRAINT ck_m18_opd_diagtext_text
    CHECK (btrim(text_line) <> '');

REVOKE DELETE ON m18_opd_diagnosis_text FROM app_m18;
```

**分区策略：** 不分区。行数约为病历主档的 2.8 倍（按眼科门诊平均每份 2.8 个诊断计），三年约 406 万行，仍可通过 `idx_m18_opd_diagtext_record` 与 `idx_m18_opd_diagtext_code` 精确访问。

**设计说明**

| # | 设计点 | 为什么 |
|---|---|---|
| 1 | **只存文本，不建 `m18_diagnosis` 表** | 诊断编码事实属于 M07-02，共享规范 §1.4 红线明确禁止建 `m18_diagnosis`。若 M18 自建一份，两张表迟早不一致，医保结算与病案首页会对不上。本表只承担「病历纸面上那句话」这一个职责 |
| 2 | **`is_primary` 用部分唯一索引而非 CHECK** | 「一份病历只能有一个主诊断」是跨行约束，`CHECK` 只能看当前行的字段，无法表达。部分唯一索引 `WHERE is_primary = TRUE` 在数据库层直接拦住第二个主诊断 |
| 3 | **组合约束 1 强制主诊断 `line_seq = 1`** | 只约束 `is_primary` 唯一还不够：可能出现主诊断排在第 3 行、第 1 行是个「并存病」的情况。医保病案首页取主诊断时若按「第一行」取就会取错。把「第一行必须是主诊断」写成约束，让排序与主次两件事绑定 |
| 4 | **`ref_status='TEXT_EDITED'` 是常态，不是异常** | 医生把「老年性白内障」写成「老年性白内障（右眼成熟期）」，这是规范允许的书写细化。若系统把措辞修改当作「不一致」告警，医生会被无意义的提示淹没，最终一律跳过不看。只在 M07-02 侧编码被**修正或删除**时（`M07_MISSING`）才告警 |
| 5 | **`ref_lock_status` 是镜像，不是权威** | 诊断锁定与否的权威在 M07-02。本表镜像一份是为了：① 定稿时不必再调 M07-02（P-11 有 300ms 预算，能省一次 RPC 就省）；② M07-02 不可用时仍能按最后已知状态保护。**镜像值一定可能过期**，所以 M07-02 的 `m07.diagnosis.revised` 订阅（§10.4）会在收到事件时刷新它 |
| 6 | **没有 `m07_diag_id` 的行允许存在** | 眼科常见「干眼症（待排）」这类暂未选到标准编码的手写诊断。**禁止手写会让医生绕到别处去记，反而丢掉记录。** 允许 `UNLINKED`，但质控（M18-05）会把它列为 MINOR 缺陷促其补齐 |

### 4.8 表：`m18_opd_copy_ref`（病历复制与模板套用溯源）

**用途：** 记录「本次病历是从哪份来源（历史病历 / 模板 / 上一段病历）复制而来的」，以及复制了哪些段落、复制后医生改了多少。既用于**医疗安全追溯**（避免复制粘贴导致把上一位患者的病情写进这一位），也用于**效率度量**（统计模板套用率、复制使用率，评估模板质量）。

**写入方：** M18-02（复制/套用动作发生时）

**只读方：** M18-05（质控：复制未修改的段落是重点核查项）、M18-01（模板使用统计）、M18-07（模板效果分析）、M18-02（页面 P08 展示复制链）

**为什么要有这张表：**

病历复制粘贴是电子病历时代最大的医疗安全隐患之一——**复制了上一位患者的现病史**、**复制了三个月前的检查结果**，是国内外病历质控通报里的高频问题。但它同时是医生效率的核心来源：眼科门诊 1,200 人次/日、单次接诊 8~12 分钟，不复制几乎无法完成书写。

正确的做法不是禁止复制（禁了就会被绕过，且真禁了医生写不完），而是**让复制可追溯、可度量、可质控**：

1. 复制时记录来源（哪份病历的哪一段），并自动打上「本段复制自 X 年 X 月 X 日病历」的可视标记；
2. 定稿时比对「复制进来」与「医生改后」的文本，算出修改率；
3. 修改率为 0 的复制段（原封不动照抄）进入质控抽样池，由 M18-05 列入重点核查。

这张表就是上述三步的数据基础。**只有记录了复制来源，才可能做后续一切。** 没有这张表，质控模块只能看到「这段写得好不好」，永远看不到「这段是从别人那抄来的」。

**字段定义**

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 否 | — | 主键 |
| `record_id` | `BIGINT` | 否 | — | 逻辑 FK* → `m18_emr_record.id`（**目标病历**） |
| `record_no` | `VARCHAR(32)` | 否 | — | 冗余目标病历号 |
| `copy_batch_no` | `VARCHAR(32)` | 否 | — | 一次复制动作的批次号，格式 `CP + yyyyMMdd + 4 位流水`。一次复制多个段落共用同一批次 |
| `copy_type` | `VARCHAR(32)` | 否 | — | 复制类型：`FROM_RECORD`（从历史病历）/`FROM_TEMPLATE`（套用模板）/`FROM_SECTION`（段内复制）/`FROM_CARRY`（上次就诊自动带入） |
| `source_record_id` | `BIGINT` | 是 | — | 来源病历 id。`copy_type='FROM_TEMPLATE'` 时为空 |
| `source_record_no` | `VARCHAR(32)` | 是 | — | 来源病历号（冗余，供展示溯源链接） |

| `source_template_version` | `INTEGER` | 是 | — | 来源模板版本 |

| `created_at` | `TIMESTAMP` | 否 | `NOW()` | 创建时间 |
| `created_by` | `BIGINT` | 否 | — | 创建人 |

| `updated_by` | `BIGINT` | 否 | — | 更新人 |

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m18_opd_copy_ref` | 主键 | `id` | — |

| `idx_m18_opd_copyref_record` | 普通 | `record_id`, `section_type` | 详情页与定稿时按段取复制记录 |

**约束说明**

```sql
ALTER TABLE m18_opd_copy_ref
    ADD CONSTRAINT ck_m18_opd_copyref_type
    CHECK (copy_type IN ('FROM_RECORD', 'FROM_TEMPLATE', 'FROM_SECTION', 'FROM_CARRY'));

-- 组合约束 1：复制类型与来源必须成套出现
ALTER TABLE m18_opd_copy_ref
    ADD CONSTRAINT ck_m18_opd_copyref_source_shape
    CHECK (
        (copy_type = 'FROM_TEMPLATE'
             AND source_template_code IS NOT NULL
             AND source_record_id IS NULL)
        OR (copy_type IN ('FROM_RECORD', 'FROM_SECTION', 'FROM_CARRY')
             AND source_record_id IS NOT NULL
             AND source_template_code IS NULL)
    );

-- 组合约束 2：规则字段三件套必须同生同灭（两分支穷尽）
ALTER TABLE m18_opd_copy_ref
    ADD CONSTRAINT ck_m18_opd_copyref_measure_shape
    CHECK (
        (measured_at IS NULL
             AND final_text_length IS NULL
             AND edited_char_count IS NULL
             AND edit_ratio IS NULL
             AND is_unchanged IS NULL)
        OR (measured_at IS NOT NULL
             AND final_text_length IS NOT NULL
             AND edited_char_count IS NOT NULL
             AND edit_ratio IS NOT NULL
             AND is_unchanged IS NOT NULL)
    );

-- 组合约束 3：修改率必须落在 [0,1]，且与 is_unchanged 自洽
-- 边界：源文本为空（source_text_length = 0）时修改率无定义，必须为 NULL
ALTER TABLE m18_opd_copy_ref
    ADD CONSTRAINT ck_m18_opd_copyref_ratio
    CHECK (
        (source_text_length = 0 AND edit_ratio IS NULL AND is_unchanged IS NULL)
        OR (source_text_length > 0
             AND (edit_ratio IS NULL
                  OR (edit_ratio >= 0 AND edit_ratio <= 1
                      AND is_unchanged = (edit_ratio = 0))))
    );

-- 组合约束 4：跨患者复制必须留下理由，非跨患者不得留理由
ALTER TABLE m18_opd_copy_ref
    ADD CONSTRAINT ck_m18_opd_copyref_cross
    CHECK (
        (cross_patient_flag = FALSE AND cross_patient_reason IS NULL)
        OR (cross_patient_flag = TRUE AND btrim(cross_patient_reason) <> '')
    );

-- 组合约束 5：确认状态与确认时刻必须成套出现（两分支穷尽）
ALTER TABLE m18_opd_copy_ref
    ADD CONSTRAINT ck_m18_opd_copyref_ack
    CHECK (
        (acknowledged = FALSE AND acknowledged_at IS NULL)
        OR (acknowledged = TRUE AND acknowledged_at IS NOT NULL)
    );

-- 组合约束 6：源文本哈希格式（SHA-256 小写十六进制 64 位）
ALTER TABLE m18_opd_copy_ref
    ADD CONSTRAINT ck_m18_opd_copyref_hash_format
    CHECK (source_text_hash IS NULL OR source_text_hash ~ '^[0-9a-f]{64}$');

REVOKE DELETE ON m18_opd_copy_ref FROM app_m18;
```

**分区策略：** 不分区。按每份病历平均 2.2 条复制记录计，三年约 319 万行，两个部分索引已覆盖全部扫描场景。

**设计说明**

| # | 设计点 | 为什么 |
|---|---|---|
| 1 | **不禁止跨患者复制，但强制标记 + 强制理由** | 临床上确实存在合法场景（双胞胎同患先天性白内障、一家人同患遗传性眼病）。一律禁止会把合法场景也堵死，医生只能想法绕过。改为「允许 + 强制说明 + 页面红字 + 质控必查」，把风险显式暴露而不是隐藏 |
| 2 | **`edit_ratio` 用编辑距离而不是「是否完全相同」** | 布尔值太粗：把「右眼」改成「左眼」在布尔上等于「改过了」，但这是**最危险的改动**（改错一只眼）。有了具体修改率，质控可以优先看「改动量极小但有关键词变化」的段落。本字段不承担识别职责，只提供排序依据，识别由 M18-05 的规则做 |
| 3 | **修改率在定稿时算，不在每次保存时算** | 医生在书写过程中会反复修改，中途算修改率没有意义且浪费算力。定稿是内容固化的时刻，此时算一次并写入，之后随 hash 一起不可变 |
| 4 | **`source_text_hash` 存源文本哈希** | 三个月后质控发现「这段是从别处抄的」，需要能证明「抄的是哪一版」。若源病历被作废或被更正，哈希能让审计确认引用的是原始版本还是更正后版本 |
| 5 | **组合约束 3 把「源文本为空」单独列为分支** | 医生可能从模板里套了一个空段落（模板该段留空待填）。此时 `source_text_length = 0`，`edit_ratio` 在数学上无定义（除以零）。若强行记 0，会被误判为「原封未动照抄」而进入质控池，制造噪音。显式允许 NULL 并在注释里写明含义 |
| 6 | **`copy_batch_no` 而不是每次复制生成独立流水** | 医生一次「套用上次病历」会带入 5~6 个段落。若每段一个流水号，页面上会显示 6 条互不相干的复制痕迹，无法表达「这是一次动作」。批次号让它们归为一组，撤销时按批次整组处理 |
| 7 | **`acknowledged` 与病历定稿的阻断关系是「软」的** | 定稿不因未确认而阻断（否则医生为了应付会盲目点确认），但在页面 P02 中未确认的复制痕迹会在保存按钮旁常驻提示。**真正有效的是让医生看到风险，而不是让医生点按钮。** 是否阻断由 §4.2 中 `m18_emr_record` 的定稿校验决定，本字段只提供展示状态 |

### 4.9 表：`m18_opd_stat`（门诊病历日统计汇总）

**用途：** 按「日期 × 科室 × 医生」维度预汇总门诊病历的书写量、及时性、完整性、签署状态分布等指标，供页面 P09 与 M22 报表取数，避免每次打开统计页都对 145 万行主表做聚合。

**写入方：** M18-02 定时任务（`stat_opd_daily`，每日 00:30 汇总前一日；`restat_opd_daily` 手工重算）

**只读方：** M18-02（页面 P09）、M18-07（检索统计）、M22 报表（通过 M18-02 的统计接口间接取）

**为什么要有这张表：**

统计页的直接做法是实时 `GROUP BY` 主表。按当前规模算：三年 145 万行、日均 1,200 份，查「上个月全科室门诊病历及时率」需要扫描约 3.6 万行并做日期比较。看似能接受，但有三个现实问题：

1. **统计口径有计算成本。** 及时率要判断「完成日期 = 就诊日期」，完整性要判 `completeness_rate >= 1`，签署率要判 `status = 'SIGNED'`，三个指标各是一次条件聚合，合并成一条 SQL 后仍有三次扫描。
2. **数据是只增不减的。** 主表永远不删（L-02），今天的查询成本就是明年的下限，一年后翻倍、三年后三倍。
3. **统计页面在早会时段被集中打开。** 全院 12 个科室的科主任集中在 08:00~08:30 看日报，正是门诊开诊高峰期，统计查询与书写保存抢同一个库的 IO。

预汇总表把「按月扫描 3.6 万行」变成「按月取 30 行」（每科室每天一行）。**代价是数据有延迟**——当日数据在 00:30 之前不准确，所以页面必须明确显示「统计截止 2026-10-31 23:59:59」，且允许「今日实时」补充查询（带 `as_of` 标记为 `REALTIME` 的实时小节，数据量仅当日，成本可控）。

ALTER TABLE m18_opd_stat
    ADD CONSTRAINT ck_m18_opd_stat_non_negative
    CHECK (encounter_count >= 0
           AND record_created_count >= 0
           AND record_finalized_count >= 0
           AND record_signed_count >= 0
           AND record_unsigned_count >= 0
           AND record_voided_count >= 0
           AND record_draft_count >= 0
           AND timely_count >= 0
           AND copy_used_count >= 0
           AND copy_unchanged_count >= 0
           AND cross_patient_count >= 0
           AND allergy_recorded_count >= 0);

ALTER TABLE m18_opd_stat
    ADD CONSTRAINT ck_m18_opd_stat_timely_rate
    CHECK (

        OR (encounter_count > 0 AND timely_rate IS NOT NULL

    ADD CONSTRAINT ck_m18_opd_stat_sign_rate
    CHECK (

        OR (record_finalized_count > 0 AND sign_rate IS NOT NULL
            AND sign_rate >= 0 AND sign_rate <= 1)
    );

-- 平均完整度：分母是 record_finalized_count
ALTER TABLE m18_opd_stat
    ADD CONSTRAINT ck_m18_opd_stat_completeness
    CHECK (

        OR (record_finalized_count > 0 AND avg_completeness_rate IS NOT NULL
            AND avg_completeness_rate >= 0 AND avg_completeness_rate <= 1)

-- 定稿份数不可能多于创建份数；签署份数不可能多于定稿份数
ALTER TABLE m18_opd_stat
    ADD CONSTRAINT ck_m18_opd_stat_nesting
    CHECK (record_finalized_count <= record_created_count
           AND record_signed_count <= record_finalized_count
           AND record_voided_count <= record_created_count

           AND copy_unchanged_count <= copy_used_count);

ALTER TABLE m18_opd_stat
    ADD CONSTRAINT ck_m18_opd_stat_missing_shape
    CHECK (
        (calc_status = 'CALCULATED' AND jsonb_array_length(missing_sources) = 0)
        OR (calc_status IN ('PARTIAL', 'FAILED')
            AND jsonb_array_length(missing_sources) > 0)
    );

-- 组合约束 5：维度聚合行的命名约定——全院行 dept_id=0 且 dept_name 为空串
ALTER TABLE m18_opd_stat
    ADD CONSTRAINT ck_m18_opd_stat_dept_sentinel

**⚠️ 必须有 `pdefault` 分区。** 分区维护任务若漏建下月分区，没有 DEFAULT 分区时写入会直接报 `no partition of relation "m18_opd_stat" found for row`，整批统计失败；有 DEFAULT 分区则数据落到兜底分区，监控告警后可由运维 `ATTACH` 迁移，**统计暂时不全但不丢数据**。

**设计说明**

| # | 设计点 | 为什么 |
|---|---|---|
| 1 | **维度值无意义时用 `0` 与空串，不用 NULL** | PostgreSQL 的 `UNIQUE` 约束认为 NULL 互不相等，`(NULL, NULL)` 可以插入无数行。汇总行的 `dept_id` 若存 NULL，`ON CONFLICT` 永远不触发，重复汇总会给全院汇总行堆出多份。用 `0` 做哨兵值，唯一约束才真正生效（共享规范 §17 第 21 条） |
| 2 | **`calc_status` 三态 + `missing_sources`** | 统计任务依赖 `m07_encounter`（就诊人次）。若 M07 侧数据还没同步完就开始统计，`encounter_count` 会偏小，及时率会虚高。此时必须标 `PARTIAL` 并记下缺哪个源，**绝不能算出一个看起来正常的数**。页面与报表取数时按 `calc_status` 决定是否显示 |
| 3 | **`as_of` 与 `created_at` 分开** | `created_at` 是这行数据什么时候写的，`as_of` 是这些数字代表到哪一刻。补算历史日期时两者相差可能数月，混用会让页面显示「统计时间 2027-01-05」而数据其实是 2026-10 的，误导使用者 |
| 4 | **比率字段分母为 0 时存 NULL，不存 0** | 某科室当天停诊，`encounter_count = 0`。若及时率记 0，月报里「停诊科室及时率 0%」会拉低全院平均，让真实问题被稀释。存 NULL 后聚合时用 `AVG()` 自动跳过该行，语义正确（总纲 §6.3 同口径） |
| 5 | **`stat_version` 单调递增** | 补算会把同一维度的行覆盖。若页面同时打开两天的数据，靠 `stat_version` 能判断「哪一份更新」。也是重算任务幂等的凭证——重算两次结果相同但版本不同 |
| 6 | **`copy_unchanged_count` / `cross_patient_count` 进日统计** | 复制风险是**趋势性**问题：单份病历照抄很难判断，但某医生连续多日照抄率 80%，就是明确信号。日粒度汇总让趋势在页面上一眼可见，无须等质控抽样 |
| 7 | **平均书写时长 `avg_write_seconds` 只统计「首次打开到定稿」** | 中途断开、次日续写会让时长失真。取首次打开时刻而非最后一次编辑时刻，且排除跨日续写（`created_at::date <> finalized_at::date`），避免出现「平均书写 86400 秒」这类荒谬数字 |

### 4.10 表：`m18_opd_config`（门诊病历参数配置）

**用途：** 保存本子模块的可配置参数——定时保存间隔、病历编辑锁 TTL、及时率口径、复制痕迹提醒策略、定稿阻断项开关等。按「作用域」分层，支持全院默认、科室覆盖、模板覆盖三个层级。

**写入方：** M18-02（页面 P10，需 `m18:opd:config:*` 权限）

**只读方：** M18-02 全部业务逻辑、M18-05（质控口径）、M18-07（检索口径）

**为什么要有这张表：**

有几类参数不能写死在代码里：

1. **医院之间口径不同。** 「门诊病历及时」在 A 院是「就诊当日完成」，在 B 院是「24 小时内完成」。写死代码后跨院部署要改代码。
2. **同一医院内部有差异。** 屈光专科门诊量大、书写要求简，白内障专科要求详细。全院统一参数会逼出「按最严的科室定」，让其他科室被无谓约束。
3. **参数需要可审计。** 「谁在什么时候把复制提醒关掉了」是管理问题，必须留痕。写死在代码里的开关做不到这一点。

分层的作用域让配置既有全院基线，又能按需覆盖。**但分层会带来「某个值到底从哪来」的困惑**，所以表里必须记清楚每一行属于哪个作用域，且查询要按「模板 > 科室 > 全院」的优先级解析。页面 P10 在展示每个参数时同时显示「当前生效值」与「生效来源」，避免运维改了半天发现被上层覆盖。

ALTER TABLE m18_opd_config

    CHECK (scope_type IN ('HOSPITAL', 'DEPT', 'TEMPLATE', 'DOCTOR'));

-- 组合约束 1：作用域与标识必须自洽（HOSPITAL 必须是 0，其余必须 > 0）
ALTER TABLE m18_opd_config
    ADD CONSTRAINT ck_m18_opd_config_scope_shape
    CHECK ((scope_type = 'HOSPITAL' AND scope_id = 0)
           OR (scope_type <> 'HOSPITAL' AND scope_id > 0));

-- 组合约束 2：ENUM 类型必须有可选值，且当前值必须在可选值内
ALTER TABLE m18_opd_config
    ADD CONSTRAINT ck_m18_opd_config_enum
    CHECK (value_type <> 'ENUM'
           OR (value_options IS NOT NULL
               AND jsonb_array_length(value_options) > 0
               AND value_options ? config_value));

-- 组合约束 3：数值上下界必须成对且有序（两分支穷尽）
ALTER TABLE m18_opd_config
    ADD CONSTRAINT ck_m18_opd_config_range
    CHECK (
        (min_value IS NULL AND max_value IS NULL)
        OR (min_value IS NOT NULL AND max_value IS NOT NULL
            AND min_value <= max_value)
    );

-- 组合约束 4：管理类参数（COPY 与 FINALIZE 分组）修改必须写理由
-- 这两组直接影响病历合规性，改动必须可追溯
ALTER TABLE m18_opd_config
    ADD CONSTRAINT ck_m18_opd_config_reason
    CHECK (config_group NOT IN ('COPY', 'FINALIZE')
           OR (config_value = default_value AND change_reason IS NULL)
           OR btrim(change_reason) <> '');

ALTER TABLE m18_opd_config
    ADD CONSTRAINT ck_m18_opd_config_version
    CHECK (version_no >= 1);

**分区策略：** 不分区。模块级参数规模在百行量级（初始 42 项参数 × 少量作用域覆盖），全表常驻内存缓存。

**设计说明**

| # | 设计点 | 为什么 |
|---|---|---|
| 1 | **`(config_key, scope_type, scope_id)` 而非 `config_key` 唯一** | 同一参数不同层级要能各存一份，否则「科室覆盖全院」这个能力无从落地。唯一性限定在「同一作用域内」 |
| 2 | **`priority` 单独存一列而不是按 `scope_type` 现场推导** | 直觉上「DOCTOR 一定优先于 DEPT」写死在代码里就行。但真实场景会出现「院长特批某科室不受个人覆盖影响」这类需求，届时需要调整优先级而**不想改代码**。存成数据后可按需重排 |
| 3 | **`default_value` 与 `config_value` 分开存** | 「恢复出厂默认」需要知道出厂值是什么；排查「为什么行为和文档不一致」时需要区分「被改过」和「本来就该这样」。只有一列时这两个需求都无法满足 |
| 4 | **`is_editable = FALSE` 的白名单机制** | 有少量参数**绝不能**被页面修改：内容哈希算法（改了历史病历全部校验失败）、单号前缀（改了会重号）。这些以行数据形式存在（便于展示与审计），但标记为不可编辑，接口层直接拒绝 |
| 5 | **组合约束 4 只约束 COPY 与 FINALIZE 两组** | 若要求所有参数修改都写理由，运维调个自动保存间隔也要写说明，久了就会变成「随手打个空格」。只在**影响病历合规性**的两组上强制，其余可选。**约束该严的地方严，该松的地方松，才有执行力** |
| 6 | **`value_options` 用 JSONB 且用 `?` 运算符校验** | `value_options ? config_value` 是 PostgreSQL JSONB 的「键是否存在」运算，对字符串数组恰好等价于「值是否存在」。这让枚举合法性在数据库层得到保证，而不是只靠接口层校验 |

### 4.11 表：`m18_opd_oper_log`（门诊病历操作日志）

**用途：** 记录门诊病历全生命周期的操作轨迹——打开、保存、定稿、签署回调、作废、复制、模板套用、过敏史变更、打印发起等。是**病历行为审计**的主数据源，也是 M18-05 质控「书写时长、修改次数、复制行为」类规则的输入。

**写入方：** M18-02（各业务动作统一埋点）

**只读方：** M18-05（质控规则取数）、M18-06（归档打包的审计附件）、M18-07（检索与追溯）、M02 审计（通过 U-16 同步重要操作）

**为什么要有这张表：**

病历的法律属性要求「谁在什么时候对这份病历做了什么」必须可完整还原。系统里有两个不同层次的审计：

1. **M02-06 的统一审计**（U-16）：记录「谁调用了哪个接口」，是**系统级**的操作日志，粒度到 API。
2. **本表**：记录「对这份病历的这个动作」的业务语义，是**病历级**的行为日志，粒度到业务动作，并携带业务上下文（改了哪一段、从什么状态到什么状态、耗时多久）。

两者不能合并：M02 的审计表在 M02，其结构是通用 KV 形式（`resource` + `action` + `detail`），要查「这份病历被改过几次正文」需要按 `detail` 里的字符串过滤，性能与准确性都不够。而质控模块每天要对数百份病历统计书写行为，必须有结构化、可索引的业务日志。

本表的另一个用途是**填补 M02 审计的盲区**：M02 审计只知道「有人调了保存接口」，不知道「这个人改的是第 3 段主诉」。病历定稿后若要追溯「这句话是谁加的」，只能靠本表。

**设计说明**

| # | 设计点 | 为什么 |
|---|---|---|
| 1 | **不写正文内容到 `detail`** | 操作日志是被所有质控人员、审计人员、信息科都能查看的表，权限面远大于病历正文。若把「医生把主诉从 A 改成 B」的 A、B 都写进来，等于绕过病历的数据权限泄露了临床内容。`detail` 只存结构化元信息（如 `{"field":"chief_complaint","length_before":12,"length_after":18}`），具体内容靠 `before_hash`/`after_hash` 证明「改过」，要看原文回到病历本身（走病历权限） |
| 2 | **`oper_category` 与 `oper_type` 两层分类** | `oper_type` 有 13 种，逐个筛选太碎；审计场景关心的是「读还是写、涉不涉及敏感数据」这层粗分类。两层并存让粗筛用 `oper_category`、细查用 `oper_type`，避免要么太粗要么太碎 |
| 3 | **失败操作也要记，且必须写原因** | 安全审计最关心的是「有人反复尝试访问不该访问的病历」。如果只记成功操作，攻击者的探测行为完全不可见。`result='DENIED'` 的记录是安全监控的输入 |
| 4 | **`duration_ms` 记录耗时** | 用途有二：① 质控判断「3 秒写完一份病历」这类异常（可能照抄）；② 排查性能问题时，操作日志里能看到每一步耗时，不必只依赖 APM |
| 5 | **`before_hash`/`after_hash` 只在关键动作记录** | 每一次自动保存都算哈希会让写入成本翻倍（哈希要对全文字段做 SHA-256），而自动保存每天每份病历可达数十次。只在 `FINALIZE`/`VOID` 这类**内容固化的边界**记录，既能证明「定稿前的内容与定稿后的内容不同」，又不拖慢日常保存 |
| 6 | **保留 36 个月** | 与《医疗机构病历管理规定》门诊病历保存期限衔接。超期分区 `DETACH` 转到冷存储而**不是 DROP**——诉讼时效可能追溯更久，冷存储的存在让「已归档数据」在法律需要时仍可调取 |
| 7 | **`trace_id` 与接口日志、M02 审计对齐** | 出事时典型的问题是「这个时间点发生了什么」。三处日志共用 `trace_id` 才能串起来看：接口日志告诉我调了什么、本表告诉我业务上做了什么、M02 告诉我谁有权限做 |

## 5. SQLAlchemy 2.0 模型定义

### 4.12 SQLAlchemy 2.0 模型定义

本节给出 10 张表的 SQLAlchemy 2.0（`Mapped[]` 声明式）模型。约定：

1. **不使用物理外键**（`ForeignKey`）。跨子模块引用一律是逻辑外键，由应用层保证；子模块内部的父子关系（如 `record_id`）同样不建约束，原因见 §4.1 论证——分区表无法引用、批量导入顺序受限、`ON DELETE` 语义在本模块根本不该存在（没有删除）。
2. **所有表共用 `m18` 元数据对象**，`schema` 留空由连接串的 `search_path` 决定，便于测试库隔离。
3. **枚举以 `VARCHAR` + `CheckConstraint` 表达**，不用 `Enum` 类型——PostgreSQL 原生枚举增加取值需要 `ALTER TYPE`，且无法回滚，与「配置驱动」的方向冲突。
4. **JSONB 字段用 `JSONB` 类型 + Python 侧 `list`/`dict`**，默认值用 `server_default` 表达，保证即使绕过 ORM 直接写 SQL 也有默认值。
5. **`content_hash` 等哈希字段在 ORM 里声明为 `String(64)`**，不用 `CHAR`——PostgreSQL 的 `CHAR` 会补空格，与 `VARCHAR` 比较时容易踩坑；DDL 层用 `CHAR(64)` 定长存储是空间优化，ORM 侧统一按字符串处理。

|---|---|---|

| 2 | 分区表主键 | ORM 只声明 `id` 为主键，而实际 DDL 是 `PRIMARY KEY (id, created_at)`。这是**已知且有意的不一致**：ORM 侧若声明复合主键，所有按 `id` 的查询都要带 `created_at`，可用性大幅下降。**插入时不指定 `created_at` 也不会出问题**（`NOW()` 默认值保证它在写入时确定），但**不接受外部传入 `id` 而省略 `created_at` 的批量导入**——这类导入必须显式给 `created_at` |
| 3 | 部分唯一索引 | `uk_m18_opd_config_scope` 与 `uk_m18_emr_record_encounter_current` 都是部分唯一索引，ORM 侧只声明不创建，实际由迁移脚本建。**应用层的幂等写入必须以这两个索引的存在为前提**（`ON CONFLICT ... WHERE` 子句要匹配） |
| 4 | `Numeric` 精度 | 所有比率字段 `Numeric(10,6)`，金额字段本项目没有（门诊病历不涉及计费）。**绝不用 `Float`**（共享规范 §2.6） |
| 5 | `DateTime` 无时区 | 全库统一 `TIMESTAMP`（无 `tz`），时区由数据库会话参数与时区表保证。ORM 侧用 `DateTime`（不带 `timezone=True`）与服务端一致 |
| 6 | `server_default` 一律用 `func.now()` | 不用 Python 侧 `datetime.now()`，避免应用服务器时区与数据库不一致导致时间错乱 |

## 6. Pydantic Schema 定义

### 4.13 Pydantic Schema 定义

本节给出对外接口与内部契约使用的 Pydantic V2 Schema。约定：

1. **字段名一律 `snake_case`**，与数据库列名保持一致，序列化时不加别名——`alias` 会让前端与文档示例产生第二套命名，是排查问题的常见干扰源。
2. **`ConfigDict(from_attributes=True)`** 用于从 ORM 对象直接构造，避免手写逐字段映射。
3. **枚举用 `Literal` 表达**，不用 `Enum` 类——`Literal` 在 OpenAPI 里生成的是 `enum` 约束，前端可直接用，且与数据库 `VARCHAR` + CHECK 的表示一致。
4. **时间统一 `datetime`**，序列化格式由全局 `json_encoders` 统一为 `YYYY-MM-DD HH:MM:SS`（共享规范 §2.4）。
5. **不定义请求体的「可选字段一律 `Optional[...] = None`」**，PATCH 语义靠 `model_dump(exclude_unset=True)` 实现，而非靠一堆 `Field(default=...)`。

class RecordFieldValue(BaseModel):
    """单个结构化字段的提交/回显结构。六个 value 槽按 field_type 二选一。"""
    model_config = ConfigDict(from_attributes=True)

    section_type: SectionType

    field_name: Optional[str] = Field(default=None, max_length=128)
    field_type: FieldType
    field_seq: int = Field(default=0, ge=0)
    is_required: bool = False
    value_text: Optional[str] = None
    value_numeric: Optional[Decimal] = None
    value_date: Optional[date] = None
    value_timestamp: Optional[datetime] = None
    value_code: Optional[str] = Field(default=None, max_length=64)
    value_codes: Optional[list[str]] = None
    value_table: Optional[list[dict[str, Any]]] = None
    value_unit: Optional[str] = Field(default=None, max_length=32)
    is_abnormal: bool = False
    abnormal_level: Optional[Literal["BLOCK", "SEVERE", "WARN", "INFO"]] = None
    version_no: int = Field(default=1, ge=1)

    @model_validator(mode="after")
    def _check_slot(self) -> "RecordFieldValue":
        text_types = ("TEXT", "TEXTAREA", "RICHTEXT")
        num_types = ("NUMBER", "DECIMAL")
        if self.field_type in text_types and self.value_text is None:
            populated = [
                self.value_numeric, self.value_date, self.value_timestamp,
                self.value_code, self.value_codes, self.value_table,
            ]
            if any(v is not None for v in populated):
                raise ValueError(f"field_type={self.field_type} 只能写 value_text")
        if self.field_type in num_types and self.value_numeric is None:
            if self.value_codes is not None or self.value_table is not None:
                raise ValueError(f"field_type={self.field_type} 不能写多选或表格槽")
        if self.field_type == "MULTI_SELECT" or self.field_type == "CHECKBOX":
            if self.value_codes is not None and not isinstance(self.value_codes, list):
                raise ValueError("value_codes 必须是数组")
        if self.is_abnormal and self.abnormal_level is None:
            raise ValueError("is_abnormal=True 时必须给 abnormal_level")
        if (not self.is_abnormal) and self.abnormal_level is not None:
            raise ValueError("is_abnormal=False 时不能有 abnormal_level")
        return self

## 附录 B　表间一致性约束清单

| 编号 | 约束 | 涉及表 | 落地方式 | 违反后果 |
|---|---|---|---|---|
| G-01 | `content_hash` 定稿后不可变 | m18_emr_record | 触发器 `trg_m18_emr_record_signed_guard` + 列级 `REVOKE UPDATE` | 法律举证时无法证明哪一版是患者签署的 |
| G-02 | 同一 `(encounter_id, record_type)` 只能有一条当前记录 | m18_emr_record | 部分唯一索引 `uk_m18_emr_record_encounter_current` | 同一就诊出现两份有效病历，P-01 返回哪份不确定 |
| G-03 | 状态只能 `DRAFT→FINALIZED→SIGNED`、`FINALIZED/SIGNED→VOIDED` | m18_emr_record | Service 层状态机 + `ck_m18_emr_record_*` | 出现 `VOIDED→DRAFT` 回退，等于篡改 |
| G-04 | 字段值只能挂在 `DRAFT` 病历上写 | m18_emr_record_field | 触发器按 `record_id` 回查父表状态 | 签署后正文被改而无任何痕迹 |
| G-05 | 封存期间正文表全部拒写 | 全部正文表 | 触发器 `trg_fn_m18_seal_guard()` 查 `m18_emr_seal` | 封存只是「发了个事件」，数据库没真锁 |
| G-06 | 一个患者同一类型的同一过敏原只有一行 | m18_opd_allergy_detail | `uk_m18_opd_allergy_patient` | 作废漏一条就还在拦截；统计重复计数 |
| G-07 | 药品类过敏必须有类别编码 | m18_opd_allergy_detail | `ck_m18_opd_allergy_drug_generic` | 交叉过敏无法判断，头孢类拦截失效 |

| G-11 | 统计行比率字段分母为 0 时必须为 `NULL` | m18_opd_stat | `ck_m18_opd_stat_timely_rate` 等三组 | 用 0 冒充「分母为 0」，报表看起来像 0% 完成 |

| 9 | m18_opd_config | 无 | 参数表，可在任意时点建 |
| 10 | m18_opd_oper_log | 无（逻辑引用 m18_emr_record） | 操作日志，分区表，须在建表时一并建当前与次月分区 |

## 附录 E　与本子模块相关的常见错误

| 编号 | 错误做法 | 正确做法 | 原因 |
|---|---|---|---|
| E-01 | 在 `m18_emr_record` 上加 `is_deleted` 列 | 用 `status='VOIDED'` 表达作废 | 有删除列就等于承认病历可以被删除，删除与篡改在数据层不可区分 |
| E-02 | M18 算一次 `content_hash`，M07-06 渲染时再算一次 | 只由 M18 定稿时算一次，M07-06 原样引用 | 两份哈希不一致时无法举证哪份是患者签的 |
| E-03 | `content_hash` 用 MD5 | SHA-256，字段 `CHAR(64)` | MD5 已可构造碰撞，病历是法律证据 |
| E-04 | 用 `REVOKE UPDATE` 后忘了 `GRANT UPDATE (列清单)` | 撤销全表 UPDATE 后按列授予状态流转所需列 | 不加 GRANT，状态流转也做不了，系统直接不可用 |
| E-05 | `GRANT UPDATE (ALL)` | 逐列显式列出 17 个可更新列 | 用 `ALL` 等于把刚撤销的权限又发回去了 |
| E-06 | 患者过敏史存成 `mpi_patient` 上一段自由文本 | 建 `m18_opd_allergy_detail` 结构化明细 | 自由文本无法支撑「是否对头孢曲松过敏」的精确判断 |
| E-07 | 过敏记录挂 `record_id` | 挂 `patient_id` | 过敏跨就诊有效，挂病历上开处方需遍历全部历史病历 |
| E-08 | 过敏失效用 DELETE | `allergy_status='INACTIVE'` + `change_reason` | 过敏史是临床证据，删除后历史病历出现「无故换药」疑点 |
| E-09 | 病历编辑锁 TTL 设 60 秒 | TTL 90 秒 + 前端 60 秒心跳续期 | 医生写一份门诊病历常需 10~20 分钟，60 秒锁必然被抢 |
| E-10 | 分区表只建当前月分区 | 当前月 + 次月 + `DEFAULT` 分区 | 跨零点写入无分区可用时会直接报错，导致夜班病历保存失败 |
| E-11 | 统计比率分母为 0 时返回 0 | 返回 `NULL` | 0 与「无法计算」是两件事，报表上无法区分 |
| E-12 | 字数统计用 `length()` | 用 `char_length()` 并按 UTF-8 字符计 | `length()` 在部分编码下返回字节数，中文病历字数会翻三倍 |
