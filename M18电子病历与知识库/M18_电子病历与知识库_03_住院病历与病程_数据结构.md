## 文档说明

本文档是 M18-03「住院病历与病程」子模块的数据结构设计，只覆盖**住院病历的病程类明细**。它所处的层级关系很简单，但必须先说清楚，否则后面的每一节都会写偏：

**`m18_emr_record` 是「一份病历」，本文档的九张表是「这份病历里的每一段」。**

住院病人一次住院会产生一条 `m18_emr_record`（`record_type = 'INPATIENT'`），但这份病历里要写的内容不是一段，而是很多段：入院记录一段、首次病程一段、日常病程十几段、查房若干段、会诊若干段、阶段小结若干段、还有出院小结和交接班。这些「段」有两种可能的落法：

- 落法一：全部塞进 `m18_emr_record` 的正文六字段（`chief_complaint`/`present_illness`/`past_history`/`physical_exam`/`diagnosis_text`/`treatment_plan`）里，按段落拼成一个大字符串；
- 落法二：`m18_emr_record` 只装**一份病历的身份与主诉性质的整体内容**，病程类的每一条独立成行，通过 `record_id` 挂回去。

本文档采用落法二。原因不在「好不好看」，而在下面三件必须成立的事：

| 必须成立的事 | 落法一为什么不成立 | 落法二怎么成立 |
|---|---|---|
| 每一条病程要能**单独定稿、单独签署、单独计时限** | 拼在一个大字符串里，「这条病程什么时候写的」只剩一个 `updated_at`，而 `updated_at` 会被下一次编辑覆盖，时限质控无法回溯 | 每条病程一行，`written_at`/`finalized_at` 各是各的，计时限不互相污染 |
| 病程要能**逐条被质控规则命中** | 质控规则要判「首次病程 8 小时内」「术后首次病程 24 小时内」，必须定位到「哪一条」，字符串里定位只能靠字符串匹配 | 每行有 `course_type` 与 `course_seq`，规则直接按列判定 |
| 病程要能**增量追加而不动已签署内容** | 追加一段等于改那个大字符串，而铁律 4 规定签署后不可原地改——追加一段就违规了 | 追加即新建一行，`m18_emr_record` 一个字节都不动，铁律 4 天然满足 |

第三条是决定性的。住院病历是**长出来的**，不是一次写完的：一份术后病历要写 7~15 天，每天都在往里加内容。如果「加内容」和「改内容」在物理上是同一个动作（都是 UPDATE 同一个字段），那么「签署后不可改」和「每天追加病程」这两条要求在落法一下是直接冲突的，只能靠应用层自觉区分——而应用层自觉恰恰是铁律 4 要防的东西。

把追加变成 INSERT，冲突就消失了：**已签署的部分是冻结的旧行，追加的部分是新行**。这也是本文档九张表存在的根本理由。

### 1.2 为什么是这九张

这套表按「一段病程属于哪种书写行为」来切，而不是按「医生在哪个界面点的」来切。切的依据来自总纲 §7.5 的容量估算与 §2.3 的划分理由③——住院病历「多次、长、时序性强」，一份病历跨 7~15 天。

**为什么不把九张表压成一张通用的「住院病历段落表」。** 有人会提出一张 `m18_ipd_segment(record_id, seg_type, content_json)` 就够了的方案，把入院记录、病程、查房、会诊、出院小结全部塞进去。这个方案在存储上确实省，但会废掉三件事：

| 被废掉的事 | 具体后果 |
|---|---|
| 差异化的时限 | 入院记录 24h、首次病程 8h、术后首次病程 24h、出院小结出院当日——这些阈值要按「段类型」查，通用表里只能塞进 JSONB，而 JSONB 里的阈值无法建 CHECK、无法建索引、改一个阈值要全表扫 |
| 差异化的权限 | 会诊回复要会诊科室的医师才能写、查房记录要主治以上、交接班要双方确认——权限点不同，通用表只能写一个粗粒度的编辑权限，等于放弃了细分 |
| 差异化的双方确认 | 交接班有「交出人」和「接交人」两个角色字段，会诊有「申请方」和「回复方」，通用表塞不下这些成对字段，只能塞 JSONB，而 CHECK 无法约束 JSONB 内的成对关系 |

放弃这三件事省下的是八张表的建表脚本，代价是把所有约束搬到应用层。而对于病历这种「写错了会被追责」的数据，把约束搬到应用层就是让约束变成「建议」。

**为什么 `m18_ipd_course_record` 一张表装得下六种病程。** 首次病程、日常病程、术后首次病程、阶段小结、抢救记录、死亡记录，这六种在**结构上完全同构**：都是「某时点写的一段病程正文 + 书写者 + 书写时间 + 相对入院的时间偏移」。它们之间的差别只有「什么时间该写、写几次」，这是**判定规则**的差别，不是**数据结构**的差别。所以用 `course_type` 一个枚举加 `course_seq` 序号就够，不必拆六张表。

> 注意这里和上一段的区别：上一段反对的是「把**不同构**的东西压成一张表」，这一段主张的是「把**同构**的东西合成一张表」。判断依据是「字段集合是否一致」，不是「业务名称是否不同」。

**为什么阶段小结要单独成表，而不并进 `m18_ipd_course_record`。** 阶段小结在结构上确实与病程同构，按刚说的判据应该并进去。但它有两个 `m18_ipd_course_record` 没有的东西：一是**触发来源**（住院满 14 天自动提醒、转科、手术前、手术后，四种来源的时限与要求不同），二是**被引用关系**（阶段小结是病案质量检查的独立检查点，M18-05 要单独判它存在与否）。给同构的东西单独开表，代价是两次查询；把它们塞进一张表再靠 `course_type` 区分，代价是这张表上的每个索引、每个约束都要写「除阶段小结外」的例外。**例外多的表比多一张表更难维护**，所以拆开。

### 1.3 本子模块不建的表

这张表是给评审者看的：以下每一个表名都曾经有人提议过，都因为归属错误被否决。

| 表名 | 归属 | 否决理由 |
|---|---|---|
| `m18_emr_record` | M18-02 | 住院病历与门诊病历是**同一份东西的两种形态**。若由 M18-03 另建一份，M18-07 检索要查两张表，M18-06 归档要推两次，`content_hash` 会有两个算法（违反铁律 5） |
| `m18_emr_record_field` | M18-02 | 同上，模板字段实例与病历绑定，与 record 同生共死 |
| `m18_home_page` | M05-06 | 病案首页是**结构化统计表**（国标 76 字段），不是病历正文。M05-06 `:201` 已明写「M18 文书存在性 → 降级 → 不阻塞首页」，M18 甚至不影响首页能否生成 |
| `m18_diagnosis` | M07-02 | 诊断编码与 ICD 归 M07-02。住院病历里的诊断段落是**给临床看的文字**，不是编码。两者的一致性问题在 M05-06 `:103` 已划清 |

### 1.4 各表写入方与只读方一览

这张表回答「谁能写」。它不只是权限清单，更是**数据流向的声明**：任何一个表如果有两个以上写入方，它的每个字段就都要问清「谁负责」，否则必然出现两个模块各写一半、互相覆盖。

| 表名 | 写入方 | 只读方 |
|---|---|---|
| `m18_ipd_admission` | M18-03 入院记录页面、M18-02 通用定稿接口 | M18-05 质控、M18-06 归档、M18-07 检索、M05-06 首页（取文书存在性） |
| `m18_ipd_course_record` | M18-03 病程页面、M18-02 通用定稿接口、**M09（经 M18-04 的 P-02 回写手术相关病程）** | M18-05 质控、M18-06 归档、M18-07 检索、M22 报表 |
| `m18_ipd_ward_round` | M18-03 查房页面、M18-02 通用定稿接口 | M18-05 质控、M18-06 归档、M18-07 检索 |
| `m18_ipd_consultation` | M18-03 会诊页面（院内申请段）、会诊科室医师（回复段） | M18-05 质控、M18-06 归档、M18-07 检索、M22 报表 |
| `m18_ipd_stage_summary` | M18-03 阶段小结页面、M18-02 通用定稿接口 | M18-05 质控、M18-06 归档、M18-07 检索 |
| `m18_ipd_discharge_summary` | M18-03 出院小结页面、M18-02 通用定稿接口 | M18-05 质控、M18-06 归档、M18-07 检索、**M05-06 首页（取出院诊断文字做一致性提示，只作提示不作写入）** |
| `m18_ipd_handover` | M18-03 交接班页面（交出人建单、接交人确认） | M18-05 质控、M18-06 归档、M18-07 检索 |
| `m18_ipd_config` | M18-03 配置页面（`m18:ipd:config:edit`） | M18-03 全部业务接口、M18-05 质控（取时限阈值）、M22 报表（取口径说明） |
| `m18_ipd_oper_log` | **仅由触发器与应用层审计切面写入，任何业务代码不得直接 INSERT** | M18-06 归档、M22 报表、M02 审计（经 U-16 转报） |

有一条必须单独强调：**`m18_ipd_oper_log` 的写入方不是某个页面，而是数据库层。** 原因是这张表的作用是「事后举证某条病程什么时候被谁写过」，如果它由业务代码自己决定写不写，那么最需要留痕的那次操作（比如程序异常中断前的最后一次写）永远留不下来。见 4.10 节的触发器设计。

| `m18_ipd_oper_log` | 36 万 | 108 万 | 0.5 KB | ≈0.55 GB | **月 RANGE 分区** | 3 年在线 |

**分区结论的依据。** 汇总 §4 已定：病程类明细表（`m18_ipd_course_record`/`m18_ipd_ward_round`）**不分区**。三年 64.8 万行、1.0 GB，单表完全在 PostgreSQL 16 的舒适区内，建索引与 VACUUM 都不构成压力。对一个不需要删数据的表做分区，只会让每次查询多一层分区裁剪的开销。

只有 `m18_ipd_oper_log` 分区，理由不是「行数大」，而是**它要能删**：日志在线只留 3 年，3 年以外的按月 `DETACH PARTITION` 秒级下线。而病历事实表 30 年不删，没有任何「按时间批量删」的需求，所以分区带不来收益。

> 有一类常见误解值得写在这里：很多人认为「大表就该分区」。实际上分区的收益来自**能按分区键做数据管理**（批量删除、按时间归档、冷热分离）。如果一个表既不会按时间删，也不会按时间拆冷热，那么分区只增加复杂度。`m18_ipd_course_record` 三年 64.8 万行听起来大，但 1.0 GB 的表在 PostgreSQL 里做一次全表顺序扫通常不到 1 秒，分区真正的意义并不在「查得快」。

### 4.3 全表公共约定

在逐表展开之前，先把九张表共有的约定说清楚。后面每张表不再重复。

**公共字段。** 除 `m18_ipd_oper_log` 外，八张表都含：`created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`、`created_by BIGINT`、`updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`、`updated_by BIGINT`。

**`is_deleted` 的取舍。** 按汇总 §2.4 硬规范第③条，`is_deleted` 只给可变配置类表。本文档九张表中**只有 `m18_ipd_config` 设 `is_deleted`**，其余八张都不设。理由：

> 病程记录、查房记录、会诊记录、交接班记录都是**已经发生过的书写行为**。一次查房写过了就是写过了，删除它不会让那次查房没发生过，只会让举证链断掉。所以它们不需要 `is_deleted`，需要的是「作废」——而作废是在记录上标 `status='VOIDED'` 并保留全部原内容，不是删。配置类表不同，规则草稿删掉就是删掉，没有举证价值。

**没有 `is_deleted` 的表，必须同时 `REVOKE DELETE`**，见 4.9 节与附录 C。只写代码层不删是不够的：运维手工执行 `DELETE` 时，代码层的约束不生效。

**`content_hash` 只出现在两处。** 本文档只在 `m18_ipd_*.content_hash` 中存放「本条病程正文的摘要」，用于本模块内部的一致性自检（防「库里存的正文和签名时拿走的正文不是同一段」）。它不是铁律 5 说的那个 `content_hash`——铁律 5 的 `content_hash` 唯一存在于 `m18_emr_record`，由 M18-02 固化，本文档只读不写。两处 `content_hash` 的职责必须在文档里说清，否则实现时一定会有人想「既然我都算了，干脆推到 M18-02 去」——那就变成了两个算法，正是坑 ⑩。

**枚举取值的来源。** 本文档新增的枚举（`course_type`/`round_type`/`consult_type`/`handover_type` 等）在共享规范 §13 公共枚举字典中没有定义，属于 M18-03 子模块私有枚举，全部在附录 E 登记。**共享规范 §13 已定义的枚举，本文档逐字引用，不新增、不改名、不加中文值。**

**时间字段一律 `TIMESTAMP` 不带时区**，全院统一 `Asia/Shanghai`。这条与 §7.2 的选型一致：带时区的时间在跨系统传输时会被各端各自解释，反而不一致。

### 4.2 表：`m18_ipd_admission`（住院入院记录）

#### 用途

记录入院记录的结构化要点。入院记录是患者住院后第一份正式病历文书，按规定应在患者入院后 **24 小时内**完成（总纲 §6 `M18-CALC-03`）。本表不存入院记录的完整富文本——完整富文本在 `m18_emr_record` 的正文六字段与 `m18_emr_record_field` 的模板字段实例中；本表存的是**为了让病程与质控能够按列判定的结构化要点**。

这一点容易被误读成「重复存了两份」。实际上边界很清楚：

| 内容 | 存在哪 | 为什么 |
|---|---|---|
| 入院记录正文（医生写的完整文字） | `m18_emr_record`（主诉/现病史/既往史/体格检查/初步诊断/处理计划） + `m18_emr_record_field` | 这是病历正文，铁律 5 要求它只有一个 `content_hash` |
| 「入院时间几点」「入院记录几点写完」 | **本表** | 时限质控要按列比较两个时间，正文里没有这两个时间 |
| 「有几个初步诊断」「诊断文字是什么」 | **本表**的 `initial_diagnosis` JSONB | 质控要判「初步诊断不能为空」「初步诊断与出院诊断不能自相矛盾」 |
| 过敏史快照 | **本表**的 `allergy_snapshot` JSONB | 入院那一刻的过敏史是**事实快照**。患者后续新增过敏，不能改写入院记录里写的「入院时无过敏史」 |

最后一条是本表存在的最强理由。**入院记录引用的是「入院那一刻患者的状态」，这个状态是不可变的。** 如果入院记录只存一个指向当前过敏史的外键，那么三个月后患者被发现有药物过敏，回看入院记录会显示「入院时有青霉素过敏」——这是对既往记录的篡改。快照是唯一正确的做法。

**写入方：** M18-03 入院记录页面、M18-02 通用定稿接口（P-11）。
**只读方：** M18-05 质控、M18-06 归档、M18-07 检索、M05-06 病案首页（取文书存在性，不取内容）。

#### 约束说明

```sql
-- 单号格式
ALTER TABLE m18_ipd_admission
  ADD CONSTRAINT ck_m18_ipd_admission_no
  CHECK (admission_no ~ '^IR[0-9]{14}$');

-- 状态取值
ALTER TABLE m18_ipd_admission
  ADD CONSTRAINT ck_m18_ipd_admission_status
  CHECK (status = ANY (ARRAY['WRITING', 'SUBMITTED', 'FINALIZED', 'VOIDED']));

-- 时限判定取值
ALTER TABLE m18_ipd_admission
  ADD CONSTRAINT ck_m18_ipd_admission_timeliness
  CHECK (timeliness IS NULL
         OR timeliness = ANY (ARRAY['TIMELY', 'OVERDUE', 'UNMEASURABLE']));

-- 组合约束一：定稿后必须齐备三要素
ALTER TABLE m18_ipd_admission
  ADD CONSTRAINT ck_m18_ipd_admission_finalized
  CHECK (status <> 'FINALIZED'
         OR (written_at IS NOT NULL
             AND content_hash IS NOT NULL
             AND finalized_at IS NOT NULL
             AND finalized_by IS NOT NULL));

-- 组合约束二：作废后必须齐备三要素
ALTER TABLE m18_ipd_admission
  ADD CONSTRAINT ck_m18_ipd_admission_voided
  CHECK (status <> 'VOIDED'
         OR (void_reason IS NOT NULL
             AND btrim(void_reason) <> ''
             AND voided_at IS NOT NULL
             AND voided_by IS NOT NULL));

-- 组合约束三：未书写完成不得有书写完成时间
ALTER TABLE m18_ipd_admission
  ADD CONSTRAINT ck_m18_ipd_admission_written_at
  CHECK (status IN ('FINALIZED', 'VOIDED') OR written_at IS NULL);

-- 组合约束四：过敏史快照与快照时刻必须成对
ALTER TABLE m18_ipd_admission
  ADD CONSTRAINT ck_m18_ipd_admission_allergy_pair
  CHECK ((allergy_snapshot IS NULL AND allergy_snapshot_at IS NULL)
         OR (allergy_snapshot IS NOT NULL AND allergy_snapshot_at IS NOT NULL));

-- 组合约束五：时限判定为 UNMEASURABLE 时，不得同时给出书写完成时间
-- 理由见 4.2.5：不可测的含义是「无法判定」，若同时有 written_at，说明其实可测，
-- 那就不是不可测而是判定逻辑有 bug。让数据库直接拒绝这种自相矛盾的数据。
ALTER TABLE m18_ipd_admission
  ADD CONSTRAINT ck_m18_ipd_admission_unmeasurable
  CHECK (timeliness <> 'UNMEASURABLE' OR written_at IS NULL);

-- 组合约束六：时限判定非空时，窗口截止时间必须非空
ALTER TABLE m18_ipd_admission
  ADD CONSTRAINT ck_m18_ipd_admission_deadline
  CHECK (timeliness IS NULL OR window_deadline_at IS NOT NULL);

-- 组合约束七：书写时长非负
ALTER TABLE m18_ipd_admission
  ADD CONSTRAINT ck_m18_ipd_admission_duration
  CHECK (written_duration_min IS NULL OR written_duration_min >= 0);

-- 组合约束八：content_hash 必须是 64 位小写十六进制
ALTER TABLE m18_ipd_admission
  ADD CONSTRAINT ck_m18_ipd_admission_hash
  CHECK (content_hash IS NULL OR content_hash ~ '^[0-9a-f]{64}$');
```

**为什么这八条组合约束值得写。** 按汇总 §7.2 的判据，`CHECK` 只保护字段自身，不保护字段之间的组合语义。上面每一条都是在保护字段之间：

| 约束 | 防的真实错误 |
|---|---|
| `ck_..._finalized` | 状态机把 `status` 推到 `FINALIZED` 但忘了写 `content_hash`——这在异步定稿里很常见（事务提交与哈希计算分成两步）。没有这条约束，库里会出现「已定稿但没有哈希」的病历，而 M18-06 归档时才发现 |
| `ck_..._voided` | 作废时只改状态不写原因。事后追责时无法回答「为什么作废」 |
| `ck_..._written_at` | 未写完的记录带着 `written_at`。这会让时限统计把「还没写完的」当成「已写完的」算进分子 |
| `ck_..._allergy_pair` | 有快照无时刻（不知道这快照是哪来的）或有时刻无快照（声称抓过但没内容） |
| `ck_..._unmeasurable` | **最重要的一条**。见下 |
| `ck_..._deadline` | 判了「按时/超时」却没有截止时间，事后无法复核这个判定 |
| `ck_..._duration` | 负数时长，通常是时区或时间字段串位 |
| `ck_..._hash` | 有人用 MD5（32 位）或截断哈希填充。铁律 5 要求 SHA-256 全 64 位 |

#### 4.2.5 关于 `UNMEASURABLE`：为什么它是独立取值

这是本子模块最容易写错、也最容易被改成「凑合用」的一处，单独展开。

**问题。** 时限质控要回答「这个科室这个月入院记录及时率多少」。算比率需要两个数：分子（按时完成的）与分母（应完成的）。但有一种情况是：**分母里的某一条记录，我们根本不知道它该不该算**——因为 `admitted_at` 拿不到。

`admitted_at` 怎么会拿不到？具体有三条路径：

| 路径 | 具体表现 | 频率估计 |
|---|---|---|
| M05 住院主档接口超时，`m18_ipd_admission` 落库时 `admitted_at` 写成了空 | `admitted_at` 为空，无法算窗口 | 罕见但发生过（M05 升级窗口） |
| 跨零点入院，M05 的 `admitted_at` 与护士站的实际上床时间不一致，差了几小时 | `admitted_at` 有值但不可信 | 每月数例 |
| 补录：患者已住院几天，入院记录是后来补建的 | `admitted_at` 有值，但记录是补录的，`written_at` 早于创建时间 | 每月数例 |

三种情况的共同点是：**这条记录究竟该算按时还是超时，无法从系统里得到确定答案。**

三种处理方式，逐一比较：

| 方式 | 及时率 | 问题 |
|---|---|---|
| 按「按时」算入分子与分母 | 分子 +1，分母 +1，比率上升 | 系统数据缺失反而让科室成绩变好。这是**激励错误**：科室没有动机去让 M05 稳定 |
| 按「未按时」算入分母 | 分母 +1，分子不变，比率下降 | 科室因为系统接口超时被扣分，而这件事科室无能为力。质控科会被反复申诉 |
| **不计入分母，单列 `UNMEASURABLE` 计数** | 分子分母都不动 | 比率只反映「能确定判定的」那部分，同时把不可测的量单独暴露出来 |

本文档选第三种。**关键不只是「不计入」，而是「单列」。** 如果只做「不计入」不单列，那么当不可测的记录多到 30% 时，及时率看起来仍然是 92.00%，而实际上只有 70% 的记录参与了计算——这个 92.00% 就成了一个没有分母支撑的假象。

所以本表同时做三件事：

1. `timeliness = 'UNMEASURABLE'` 是一个**明确的库内取值**，不是 NULL；
2. `ck_..._unmeasurable` 约束保证「判为不可测就不能有 `written_at`」，即不可测的记录一定是真的没完成书写时间，不是「其实写完了但懒得分」；
3. `idx_..._unmeasurable_partial` 部分索引让「拉出本月全部不可测记录」这个查询很快，质控页面必须能一眼看到这个数。

**及时率的口径因此写成：**

```text
timely_rate = TIMELY 条数 / (TIMELY 条数 + OVERDUE 条数)
```

分母里**不含** `UNMEASURABLE`。并且当分母为 0 时，`timely_rate` 返回 `NULL` 而不是 `0`——这与总纲 §6 `M18-CALC-03` 的边界条件「分母为 0 时 timely_rate = NULL，不返回 0」一致。返回 0 会被报表画成「及时率 0%」，而真实情况是「本月没有可判定的记录」。

**这不是本子模块自行发明的口径。** 总纲 §6 `M18-CALC-06 归档完整率` 已经对 `UNKNOWN` 做了同样的处理——「`UNKNOWN` 既不在分子也不在分母」。本文档只是把同一条原则从归档完整率延续到病历及时率。**同一个模块里两处统计对「测不准」采用同一种处理**，比各自发明更重要的是一致。

#### 4.2.6 `status` 与 `m18_emr_record.status` 的关系

本表有 `status`，`m18_emr_record` 也有 `status`，这是不是重复？

不是。两者描述的是**不同对象**的状态：

| 字段 | 描述的对象 | 取值 | 谁维护 |
|---|---|---|---|
| `m18_emr_record.status` | 整份**病历**的生命周期 | `DRAFT` / `FINALIZED` / `SIGNED` / `VOIDED` | M18-02（定稿）+ M07-06 回调（签署） |
| `m18_ipd_admission.status` | 这一条**入院记录段落**的书写状态 | `WRITING` / `SUBMITTED` / `FINALIZED` / `VOIDED` | M18-03 |

两者有一处必须保持的时序关系：**本表 `status='FINALIZED'` 必须发生在 `m18_emr_record.status` 变为 `FINALIZED` 之前或同事务内**。也就是说，一份病历不能整体定稿而入院记录还没写完。

这个关系用触发器还是应用层保证？本文档选**应用层 + 定稿前校验**，不用跨表触发器。理由：

- 跨表触发器在定稿那一刻要读 `m18_ipd_admission`，而病历整体定稿时可能有多条段落（入院记录、病程、出院小结……）都要校验。在触发器里做 N 次校验，失败时报错信息只能说出第一条，用户改完重试再报第二条，体验很差。
- 应用层可以在一次事务里把所有未完成的段落收集齐，一次性返回「以下 3 段未完成」，用户一次改完。这是**触发器做不到的**——触发器一次只报一个错。

所以这条约束的位置是：数据库负责「单表单段自身不能自相矛盾」，应用层负责「多段之间的完成性检查」。这个分工也解释了为什么 `m18_emr_record` 的签署触发器（M18-02）和本文档的段落状态**是两层**，不是一层。

#### 封存触发器挂载与权限回收

```sql
-- 封存后全部只读（汇总 §3.3 强制三）。挂载到本表。
CREATE TRIGGER trg_m18_ipd_admission_seal_guard
  BEFORE INSERT OR UPDATE ON m18_ipd_admission
  FOR EACH ROW EXECUTE FUNCTION trg_fn_m18_seal_guard();

-- 已定稿段落的正文不可改（本子模块自有的第二道闸，与 m18_emr_record 的签署闸门互补）
CREATE OR REPLACE FUNCTION trg_fn_m18_ipd_admission_finalized_guard()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.status = 'FINALIZED' THEN
    IF NEW.chief_complaint IS DISTINCT FROM OLD.chief_complaint
       OR NEW.admission_diagnosis IS DISTINCT FROM OLD.admission_diagnosis
       OR NEW.specialty_fields IS DISTINCT FROM OLD.specialty_fields
       OR NEW.content_hash IS DISTINCT FROM OLD.content_hash
       OR NEW.written_at IS DISTINCT FROM OLD.written_at
       OR NEW.timeliness IS DISTINCT FROM OLD.timeliness THEN
      RAISE EXCEPTION 'SEGMENT_FINALIZED_IMMUTABLE'
        USING HINT = '该段落已定稿，正文与时限判定不可修改。如需更正请走作废重开';
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m18_ipd_admission_finalized_guard
  BEFORE UPDATE ON m18_ipd_admission
  FOR EACH ROW EXECUTE FUNCTION trg_fn_m18_ipd_admission_finalized_guard();

-- 应用账号不得删除任何段落
REVOKE DELETE ON m18_ipd_admission FROM app_m18;
```

**为什么本表还要一道自己的定稿闸。** 汇总 §3.1 的签署闸门保护的是 `m18_emr_record.status='SIGNED'`，而**段落定稿早于整份病历签署**。中间这段时间（定稿到签名，可能几小时到几天）如果段落正文能被改，就会出现「医生定稿时写的是 A，签名时被改成了 B」——签名签的是 B，但医生的本意是 A。所以段落层必须有自己的一道闸，且这道闸的触发条件是**段落定稿**而不是**整份签署**。

两道闸的分工：

| 闸 | 触发条件 | 保护什么 |
|---|---|---|
| `trg_fn_m18_emr_record_signed_guard`（M18-02） | `m18_emr_record.status='SIGNED'` | 整份病历签署后的绝对不可改 |
| `trg_fn_m18_ipd_*_finalized_guard`（本文档，每张事实表一个） | 该段 `status='FINALIZED'` | 段落定稿后、整份签署前的不可改 |

**为什么不合并成一道闸。** 因为合并后只有一份实现，而这份实现要么放在 M18-02（对本子模块的九张表一无所知，无法逐列比对），要么放在 M18-03（对 `m18_emr_record` 的字段一无所知）。**跨模块的逐列比对只能由持有该表定义的模块写**，这是边界，不是重复。

#### 分区策略

**不分区。** 三年 5.4 万行、约 0.2 GB，无按时间批量删除的需求，住院病历留存 30 年（汇总 §10.3）。分区只增加复杂度，带不来任何收益。理由详见 1.5 节的「分区结论的依据」。

### 4.3 表：`m18_ipd_course_record`（住院病程记录）

#### 用途

住院期间**每一次病情记录**的统一定义表。本表承载六种病程类型：首次病程记录、日常病程记录、术后首次病程记录、阶段小结（不，阶段小结在 4.6，见下）、抢救记录、死亡记录。用 `course_type` 一个枚举区分。

**先说清一个问题：为什么六种病程能共用一张表，而阶段小结却单独成表？**

判据在 1.2 节已经给出：**看字段集合是否同构**。首次病程、日常病程、术后首次病程、抢救记录、死亡记录这五种，需要的字段完全一致——都是「什么时候写的、谁写的、写了什么、书写时患者处于什么状态」。而阶段小结需要额外的「触发来源」与「被质控单独检查」，字段集合不同，所以拆开。

这里还有一个必须说清的点：**日常病程的「每天至少一次」不是靠本表字段实现的。** 本表只记录「写了哪些」，不记录「应该写哪些」。应该写多少条是由 4.5 节的 `m18_ipd_ward_round`? 不，是由 3.4 节的日常病程频次规则在查询时计算的——本表没有 `expected_count` 字段。

**为什么不加一个 `expected_count` 字段把「应写几条」也存下来？** 因为「应写几条」是一个**随时间变化**的量：住院第 3 天应写 3 条，第 8 天应写 8 条。如果把第 8 天的应写数存进第 1 天的那条记录里，那么第 5 天查的时候读到的是 3（存的旧值），与实际情况不符；如果每天更新字段，那这些行就一直在被 UPDATE，破坏了「病历是追加而非修改」的基本性质。**应写条数是查询时算出来的，不是存下来的。**

**写入方：** M18-03 病程页面、M18-02 通用定稿接口（P-11）、M09 经 M18-04 的 P-02 回写手术相关病程段。

#### 4.3.2 `course_type` 六种取值与它们的判定规则

| 取值 | 中文 | 何时必须有 | 时限阈值（默认） | 窗口起点 |
|---|---|---|---|---|
| `FIRST` | 首次病程记录 | 每份住院病历**恰好一条** | 8 小时 | 入院时间 `admitted_at` |
| `DAILY` | 日常病程记录 | 住院期间**每天至少一条**（无例外），见 4.3.3 | 当日 24:00 | 当日 00:00 |
| `POSTOP_FIRST` | 术后首次病程记录 | 每次手术**恰好一条** | 24 小时 | 手术结束时间 |
| `RESCUE` | 抢救记录 | 每次抢救**恰好一条**，抢救结束后 6 小时内补记 | 6 小时 | 抢救开始时间 |
| `DEATH` | 死亡记录 | 患者死亡时**恰好一条**，24 小时内完成 | 24 小时 | 死亡时间 |
| `CONSULT_REPLY` | 会诊意见的病程侧记录 | 会诊回复后 | 24 小时 | 会诊申请时间 |

**关于 `CONSULT_REPLY` 的取舍。** 会诊回复已经在 `m18_ipd_consultation` 里有独立的行（4.5 节），为什么病程里还要再有一条？

因为这两者回答不同问题：`m18_ipd_consultation` 回答「**这次会诊，会诊科室怎么答的**」（含会诊医师、回复时间、会诊意见）；`CONSULT_REPLY` 病程回答「**会诊意见落到这次住院里，主治医师怎么执行的**」。后者会写「已按会诊意见加用局部激素滴眼，随访眼压」，这件事会诊医师不会写。

所以 `CONSULT_REPLY` 是可选的：会诊意见没被采纳或无需执行动作时，可以不写。这也是它没有「恰好一条」约束的原因。

#### 4.3.3 `course_seq` 与「每天至少一次」的真实含义

`course_seq` 是**同类型病程在同一份病历内的序号**，从 1 起，不跳号。它解决的是「第几条」的定位问题，不解决「够不够」的判定问题。

关于「日常病程每天至少一条」，本表**只用四个约束来落地**，每个约束都对应一个必须回答的判断：

**判断一：手术当天可以只写手术记录不写日常病程吗？**

可以。**但手术记录本身记作当天的病程**。落地方式：手术当天若只写了 `POSTOP_FIRST`（术后首次病程）而没有 `DAILY`，则该日的病程条数检查通过。

这个判断的依据是《病历书写基本规范》的实质要求——「病程记录应当反映患者病情变化与诊疗过程」。手术记录（在 M09）与术后首次病程已经完整反映了当天的诊疗过程，再要求单独写一条日常病程，产生的是重复内容而不是更多信息。

但有一个**必须同时成立的补充条件**：术后首次病程必须**当天内**写完，否则「手术当天有记录」这一条不成立。如果术后首次病程拖到第二天才写，那么手术当天确实没有任何病程记录——这种情况判为 `OVERDUE`，不能因为「术前有手术记录」而豁免。

**判断二：周末与节假日豁免吗？**

**不豁免。** 落地方式：频次检查按 `seq_date` 的自然日计算，不因星期或节假日跳过。

依据是三级医院住院病历的基本要求——值班医师在周末与节假日照常查房并书写病程记录。医院如果对周末豁免，那么周五晚到周一早之间出现三天无记录，而这恰恰是住院风险最集中的时段（值班人员少、交班多）。

这一点在实现上有个坑要提前说清楚：**不能把「工作日」用 `EXTRACT(DOW)` 判断**，因为中国的调休制度会制造「周六上班、周三休息」的排列。所以本文档的判断是**不区分星期，全部日期一视同仁**——这样反而绕开了调休问题。

**判断三：患者当天出院，出院小结算作当天的病历记录吗？**

算。落地方式：若某日患者出院且写了出院小结（`m18_ipd_discharge_summary`），则该日不要求再有 `DAILY` 病程。

依据与判断一相同——出院小结已经完整记录了当天的病情与处理。而且出院小结的信息量比一条日常病程更大。

补充条件同判断一：出院小结必须**当天内**完成。若出院小结实际是次日补写的，那么出院当天没有记录，判 `OVERDUE`。

**判断四：长期住院（如压疮、康复、慢性病）的频次要求降低吗？**

**不降低条数，但降低内容要求。** 落地方式：`condition_level` 影响的是**加频**，不影响**减频**。

这条是本子模块里最反直觉的一条，必须说清理由。总纲 §6 `M18-CALC-03` 给日常病程的时限是「按医嘱频次，最长不超过 3 天（病危 1 天）」。但本项目取的是**更严的院内标准：每天至少 1 次**。

为什么不用总纲那个「最长 3 天」？因为「最长 3 天」是国家规范给综合医院的**最低要求**，而三级眼科医院的住院患者以手术后病人为主，术后 3 天正是并发症（眼内炎、出血、高眼压）的高发窗口。按最低要求写，等于在最需要观察的时段允许三天不记录。

所以院内标准是「每天至少 1 次」，并按病情加频：

| `condition_level` | 每日最少条数 | 依据 |
|---|---|---|
| `CRITICAL`（病危） | 3（每 8 小时至少 1 次） | 病危患者需连续观察 |
| `SEVERE`（病重） | 2 | 同上，密度略低 |
| `STABLE` / `IMPROVING` | 1 | 常规要求 |

**长期住院患者的频次按同一标准执行**，不因住院天数长而降低。理由是：住院时间越长，越可能是复杂病例，恰恰越需要记录——如果因为「住了 40 天没什么变化」而允许每周写一次，那么哪天真的变化了，就看不出是什么时候开始变化的。

但是内容要求可以降低：稳定期的日常病程允许只写「病情稳定，无特殊变化，继续当前治疗」这样一句话加生命体征与眼科专项指标，不必每次都写完整分析。**这是内容层面的简化，不是频次层面的豁免。** 两者的区别在验收上不同：频次检查永远按上表算，不因为内容短而放宽。

#### 4.3.4 时限判定的三个取值

与 4.2.5 完全相同的逻辑，`UNMEASURABLE` 是独立取值、不计入分母、必须单列。这里多一种不可测的具体成因：

| 成因 | 表现 | 处理 |
|---|---|---|
| `window_start_at` 拿不到（如术后首次病程缺少手术结束时间） | 字段为空 | `timeliness='UNMEASURABLE'` |
| `course_type='POSTOP_FIRST'` 但 `surgery_id` 为空，无法定位窗口起点 | 相关字段为空 | 同上，且这是**数据缺陷**，要单独计数 |
| 记录的 `seq_date` 早于 `m18_ipd_admission.admitted_at` 的日期（补录时序错乱） | 日期不自洽 | 同上 |

第三条发生时会同时触发 `m18_ipd_oper_log` 的 `CRITICAL` 级别日志——因为它不是「测不准」，而是**上游数据错了**，需要人去看。

#### 4.3.5 `draft_source` 为什么必须落库

`draft_source` 记录这一条病程的草稿是怎么来的：手写、套模板、沿用上一条、还是智能辅助生成。

**落这个字段的理由不是技术，是举证。** 当一条病程的内容出现争议（比如被质疑「这段明显不是医生写的」），系统必须能回答「这条病程的草稿来源是什么」。如果 `draft_source='AI_ASSIST'`，那么审核这条病程时必须核实医师是否确实做了确认；如果 `draft_source='COPY_PREV'`，则要关注是否有「沿用上一条后忘了改」的情况——这是病程记录最常见的质量问题之一（前一天的「今日病情稳定」原样复制到今天，而今天其实做了手术）。

所以这个字段有两个消费者：审慎核查（人）与质控规则（机器）。M18-05 有一条规则专门检查「连续 3 条 `draft_source='COPY_PREV'` 且 `content_summary` 相似度 > 0.95」——命中判 `MINOR` 缺陷。没有这个字段，这条规则无法实现。

#### 4.3.6 `created_at` 与 `written_at` 的区别

这两个时间容易混，必须写清：

| 字段 | 含义 | 由谁写 | 会不会晚于定稿 |
|---|---|---|---|
| `created_at` | 这一行**在库里创建**的时刻 | 数据库 `DEFAULT CURRENT_TIMESTAMP` | 会。补录时创建时间可能晚于 `written_at`（医生先在纸上写，之后补录系统） |
| `written_at` | 医师**完成书写**的时刻 | 应用层，由医师提交时的服务器时间 | 不会晚于 `finalized_at` |

时限质控**只认 `written_at`**，不用 `created_at`。用 `created_at` 会把「医生 3 点写完、4 点才点保存」算成超时——但书写确实在 3 点就完成了。

补录场景（`written_at` 早于 `created_at`）要单独标记：质控统计里这类记录计入一次 `LATE_ENTRY` 计数，不影响时限判定本身，但要暴露出来。这是「补录」与「按时书写」在系统里的区别——如果补录不被单列，那么所有超时都可以靠补录来规避。

#### 索引定义

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m18_ipd_course_record` | PRIMARY KEY | `id` | 主键 |
| `uk_m18_ipd_course_record_no` | UNIQUE | `course_no` | 单号唯一 |
| `uk_m18_ipd_course_record_seq` | UNIQUE | `record_id, course_type, course_seq` | 同类型序号不重复。**不含 `status`**：作废后重写应生成新的 `course_seq`，不复用旧号 |
| `uk_m18_ipd_course_record_daily` | UNIQUE（部分） | `record_id, seq_date` | **部分唯一索引** `WHERE course_type = 'DAILY' AND status <> 'VOIDED'`。保证同一病历同一天不会出现两条有效日常病程 |
| `idx_m18_ipd_course_record_record` | BTREE | `record_id, seq_date, course_seq` | 按病历取全部病程（列表页按时间序）。**三列顺序**：先病历、再日期、最后序号，与页面排序一致 |
| `idx_m18_ipd_course_record_encounter_type` | BTREE | `encounter_id, course_type` | 按就诊+类型查（如「这条住院的首次病程在哪」） |
| `idx_m18_ipd_course_record_patient` | BTREE | `patient_id, seq_date DESC` | 按患者查历史病程 |
| `idx_m18_ipd_course_record_timeliness` | BTREE | `dept_id, seq_date, timeliness` | 时限质控统计 |
| `idx_m18_ipd_course_record_surgery` | BTREE（部分） | `surgery_id` | 部分索引 `WHERE surgery_id IS NOT NULL`。M09 回查「这次手术对应的术后病程」 |
| `idx_m18_ipd_course_record_overdue_partial` | BTREE | `dept_id, seq_date` | 部分索引 `WHERE timeliness = 'OVERDUE'`。超时清单页面用 |
| `idx_m18_ipd_course_record_unmeasurable_partial` | BTREE | `encounter_id` | 部分索引 `WHERE timeliness = 'UNMEASURABLE'`。不可测清单 |

**为什么 `uk_..._daily` 要用部分唯一索引而不是普通唯一索引。** 因为作废的病程不能占用当天的唯一位置。假设医生写了一条日常病程定稿后发现写错了，作废重写——如果唯一索引不含 `status` 条件，重写时会因为「当天已有一条」而插入失败。加上 `status <> 'VOIDED'` 条件后，作废的那条不参与唯一性判断，重写的可以正常插入，而**作废记录仍然保留在表里**（它是「发生过的事」，不能删）。

#### 约束说明

```sql
-- 单号格式：CR + 14 位日期数字
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_no
  CHECK (course_no ~ '^CR[0-9]{14}$');

-- 病程类型取值
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_type
  CHECK (course_type = ANY (ARRAY['FIRST', 'DAILY', 'POSTOP_FIRST',
                                  'RESCUE', 'DEATH', 'CONSULT_REPLY']));

-- 病情等级取值
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_condition
  CHECK (condition_level IS NULL
         OR condition_level = ANY (ARRAY['CRITICAL', 'SEVERE', 'STABLE', 'IMPROVING']));

-- 草稿来源取值
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_draft
  CHECK (draft_source = ANY (ARRAY['MANUAL', 'TEMPLATE', 'COPY_PREV', 'AI_ASSIST']));

-- 状态取值
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_status
  CHECK (status = ANY (ARRAY['WRITING', 'SUBMITTED', 'FINALIZED', 'VOIDED']));

-- 时限判定取值
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_timeliness
  CHECK (timeliness IS NULL
         OR timeliness = ANY (ARRAY['TIMELY', 'OVERDUE', 'UNMEASURABLE']));

-- 序号从 1 起
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_seq
  CHECK (course_seq >= 1);

-- 组合约束一：定稿后必须齐备
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_finalized
  CHECK (status <> 'FINALIZED'
         OR (written_at IS NOT NULL
             AND content_hash IS NOT NULL
             AND finalized_at IS NOT NULL
             AND finalized_by IS NOT NULL));

-- 组合约束二：作废后必须齐备
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_voided
  CHECK (status <> 'VOIDED'
         OR (void_reason IS NOT NULL
             AND btrim(void_reason) <> ''
             AND voided_at IS NOT NULL
             AND voided_by IS NOT NULL));

-- 组合约束三：术后首次病程必须关联手术并带手术结束时间
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_postop
  CHECK (course_type <> 'POSTOP_FIRST'
         OR (surgery_id IS NOT NULL AND surgery_at IS NOT NULL));

-- 组合约束四：非术后首次病程不得残留手术关联
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_surgery_clean
  CHECK (course_type = 'POSTOP_FIRST'
         OR (surgery_id IS NULL AND surgery_at IS NULL));

-- 组合约束五：首次病程的序号恒为 1
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_first_seq
  CHECK (course_type <> 'FIRST' OR course_seq = 1);

-- 组合约束六：危重记录必须带生命体征
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_vital
  CHECK (condition_level NOT IN ('CRITICAL', 'SEVERE')
         OR (vital_signs IS NOT NULL AND vital_signs <> '{}'::jsonb));

-- 组合约束七：不可测不得有书写完成时间（同 4.2.5 逻辑）
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_unmeasurable
  CHECK (timeliness <> 'UNMEASURABLE' OR written_at IS NULL);

-- 组合约束八：书写时长非负
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_duration
  CHECK (written_duration_min IS NULL OR written_duration_min >= 0);

-- 组合约束九：哈希格式
ALTER TABLE m18_ipd_course_record
  ADD CONSTRAINT ck_m18_ipd_course_record_hash
  CHECK (content_hash IS NULL OR content_hash ~ '^[0-9a-f]{64}$');
```

**九条约束里最值得注意的是第四条。** 「非术后首次病程不得残留手术关联」听起来是个很细的约束，它防的错误是：某条病程原本写成了术后首次病程，关联了 `surgery_id`，后来发现类型选错了改成 `DAILY`，应用层只改了 `course_type` 没清 `surgery_id`。结果 M09 回查「这次手术的术后病程」时，会因为 `surgery_id` 命中而多查出一条日常病程，误以为术后病程写了两条。

**组合约束无法表达的部分**（必须由应用层或定时任务保证，这里如实写出来）：

| 约束 | 为何无法用 CHECK 表达 | 由谁保证 |
|---|---|---|
| 每份病历恰好一条 `FIRST` | CHECK 只能看本行，看不到「本行插入后同 `record_id` 下有两条 FIRST」 | 应用层 + `uk_..._seq` 的唯一性把 `FIRST` 的 `course_seq` 钉死为 1，间接保证唯一 |
| 每次手术恰好一条 `POSTOP_FIRST` | 同上，且需要唯一索引 `(record_id, surgery_id)` 部分唯一 | 增加部分唯一索引 `WHERE course_type = 'POSTOP_FIRST'`，见下表说明 |
| 每日条数符合 `condition_level` 要求 | 需要聚合查询 | APScheduler 每 30 分钟扫描当日未达标病历，写 `m18_ipd_oper_log` |
| 首次病程的阈值是 8 小时 | 阈值来自配置表 | 应用层查配置后计算 `window_deadline_at` |

补充一条部分唯一索引把「每次手术一条术后病程」落到数据库层：

```sql
CREATE UNIQUE INDEX uk_m18_ipd_course_record_postop
  ON m18_ipd_course_record (record_id, surgery_id)
  WHERE course_type = 'POSTOP_FIRST' AND status <> 'VOIDED';
```

#### 封存触发器挂载与权限回收

```sql
CREATE TRIGGER trg_m18_ipd_course_record_seal_guard
  BEFORE INSERT OR UPDATE ON m18_ipd_course_record
  FOR EACH ROW EXECUTE FUNCTION trg_fn_m18_seal_guard();

CREATE OR REPLACE FUNCTION trg_fn_m18_ipd_course_record_finalized_guard()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.status = 'FINALIZED' THEN
    IF NEW.content_summary IS DISTINCT FROM OLD.content_summary
       OR NEW.vital_signs IS DISTINCT FROM OLD.vital_signs
       OR NEW.content_hash IS DISTINCT FROM OLD.content_hash
       OR NEW.course_type IS DISTINCT FROM OLD.course_type
       OR NEW.written_at IS DISTINCT FROM OLD.written_at
       OR NEW.timeliness IS DISTINCT FROM OLD.timeliness
       OR NEW.window_start_at IS DISTINCT FROM OLD.window_start_at THEN
      RAISE EXCEPTION 'SEGMENT_FINALIZED_IMMUTABLE'
        USING HINT = '该病程已定稿，正文与时限判定不可修改。如需更正请走作废重开';
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m18_ipd_course_record_finalized_guard
  BEFORE UPDATE ON m18_ipd_course_record
  FOR EACH ROW EXECUTE FUNCTION trg_fn_m18_ipd_course_record_finalized_guard();

REVOKE DELETE ON m18_ipd_course_record FROM app_m18;
```

**注意 `window_start_at` 也在禁改清单里。** 有人会想「窗口起点只是个计算依据，改了不影响正文」。但窗口起点决定了 `window_deadline_at`，而 `window_deadline_at` 决定了 `timeliness`。允许改窗口起点，就等于允许把一个超时的病程改成按时——只要把起点往后挪。

同理 `timeliness` 本身也在禁改清单里。这条看似多余（都定稿了还改判定结果干什么），但正因为它是「判定结果」而容易被认为是「系统算的，重算一下无所谓」。一旦允许重算，配置阈值一改，全体已定稿记录的判定结果都会跟着变，历史统计就不可复现了。

**不分区。** 三年 64.8 万行、约 1.0 GB。汇总 §4 已明确把本病程类明细表列入「不分区」清单。理由见 1.5 节。

### 4.4 表：`m18_ipd_ward_round`（住院查房记录）

#### 用途

记录主治医师查房、上级医师查房、主任医师查房、科主任查房的具体过程。

**查房记录与病程记录的关系，是这张表存在的前提。** 两者在文字上经常很相似（都是「某医师来看过患者，说了什么」），但在管理上是两件事：

| 维度 | 病程记录（4.3） | 查房记录（本表） |
|---|---|---|
| 回答的问题 | 「病情怎么变化了」 | 「哪一级医师来看过、什么时间来的」 |
| 频次要求 | 每天至少 1 次 | 主治医师每日至少 1 次；主任医师每周至少 1 次；手术患者术前必须有主治以上查房 |
| 质量检查 | 内容完整性 | **查房等级与频次是否达标**，这是病案质量检查中独立的一项 |
| 责任人 | 书写医师 | 查房的那位医师本人 |

第三行是分离的核心理由。查房频次达标率按「查房医师的职称」统计，而病程记录是按「书写医师」统计——同一份病历里这两个数不一样（主任来查房，住院医师写记录，查房的达标算主任的，写的质量算住院医的）。如果合并成一张表，这两个统计维度会打架。

**写入方：** M18-03 查房记录页面、M18-02 通用定稿接口。
**只读方：** M18-05 质控（查房频次达标率）、M18-06 归档、M18-07 检索、M22 报表。

#### 字段定义

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | 自增 | 主键 |
| `round_no` | VARCHAR(32) | 否 | | 查房记录号，格式 `WR + yyyyMMdd + 6位`。全表唯一 |
| `record_id` | BIGINT | 否 | | 逻辑外键 → `m18_emr_record.id` |
| `encounter_id` | BIGINT | 否 | | 就诊ID，冗余落列 |
| `patient_id` | BIGINT | 否 | | 患者ID，冗余落列 |
| `dept_id` | BIGINT | 否 | | 查房科室ID，逻辑外键 → M01 |
| `round_type` | VARCHAR(32) | 否 | | 查房类型：`ATTENDING`（主治查房）/ `SENIOR`（上级医师查房）/ `DIRECTOR`（主任查房）/ `DEPT_HEAD`（科主任查房）/ `NIGHT`（夜查房）/ `JOINT`（多学科联合查房） |

### 4.5 表：`m18_ipd_consultation`（住院会诊记录）

#### 用途

记录住院期间的一次会诊。**核心设计：一次会诊落两行——申请段一行、回复段一行。**

#### 4.5.1 为什么是两行而不是一行

这是本子模块里最需要论证的表设计，因为它看起来「明明就是一条记录的事」。

一行方案的写法是这样的：

```text
m18_ipd_consultation(id, consult_no, record_id, apply_dept, consult_dept,
                     apply_reason, urgency, applied_at,
                     reply_content, consultant_id, replied_at, reply_deadline_at, ...)
```

看起来很自然：一次会诊一行，前半是申请信息，后半是回复信息，回复来了就 UPDATE 后半部分。

这个方案的致命问题在于：**它把「两个时点的两个事实」压缩成了「一个事实的两个阶段」。**

具体会坏在哪里？三个场景：

**场景一：会诊发出去了，会诊科室三天没回。**

页面查这条会诊，读到的是 `reply_content = NULL`、`replied_at = NULL`。

那么问题来了：这条会诊是「已经申请、等待回复」，还是「申请被撤销了」，还是「压根没请过会诊」？

一行方案里，这三种状态都表现为 `reply_*` 为 NULL。要区分它们，只能再加一个 `status` 字段。而一旦加了 `status`，这个 status 就有了两种含义混在一起：它既表示「申请是否有效」，又表示「回复是否到达」。这个混合状态一旦出现，就会有人按错的意思去查它。

**这正是 lead m01585 第 5 条指出的问题**：会诊申请已发、回复未到，页面必须能看到「已申请未回复」，而不是「无会诊记录」——后者会让主管医生以为没请会诊，重复申请。

**场景二：会诊回复写错了，要改。**

一行方案下，改回复就是 UPDATE 那条已存在的记录。但这条记录里还有申请段的信息（申请科室、申请理由、申请时间），这些是不能动的。于是 UPDATE 语句必须小心地只改后半个字段集，而且每次改都要 `version_no + 1`——这让申请段的「未修改」变成了一个需要被证明的事（`version_no` 变了，说明这条记录被改过，可申请内容其实没变）。

在审计上，「一条记录被修改过 N 次」和「申请段从未被修改、回复段修改过 N 次」是两个完全不同的事实。一行方案无法表达后者。

**场景三：会诊回复超时告警。**

普通会诊 24 小时内回复、急会诊 10 分钟内回复。要判超时，需要比较「回复时间」与「申请时间 + 阈值」。

一行方案里，这个比较没问题。但**告警要在没回复的时候发出**——也就是 `replied_at IS NULL` 的时候要去扫「申请时间早于 24 小时前的行」。这个扫描本身可以写，但它的代价是要扫「所有没有回复的会诊」，并且要靠 `replied_at IS NULL` 这个条件来判定，而这个条件在语义上是「可能永远不回复」的。

**两行方案怎么解决这三点。** 两行方案下：

| 场景 | 两行方案的表现 |
|---|---|
| 申请已发、回复未到 | 申请行存在（`segment='APPLY'`），回复行不存在。**「有申请没回复」是一个物理事实，不是靠 NULL 推断出来的**。页面查「本次住院的会诊」时，以申请行为主表 LEFT JOIN 回复行，能明确区分「没有会诊记录」与「会诊申请了但没回」 |
| 回复写错了 | 回复行被 UPDATE，申请行 `updated_at` 一动不动。审计上直接能读出「只有回复段被改过」 |
| 超时告警 | 扫「有申请行、无对应回复行、且申请时间 + 阈值 < now」，这是一个**存在性检查**（NOT EXISTS），而不是 NULL 判断。数据库对 NOT EXISTS 的优化很成熟，且部分索引可以加速 |

**两行方案还有第三个好处：院外会诊天然适配。** 院外会诊的申请要有「转诊医院」「转诊科室」等字段，回复要有「外院医师签名」「外院盖章件编号」。这些字段在申请段与回复段各有一组，两行方案下各归各的，不会出现「一行里一半字段只在院外会诊时有意义」的情况。

**代价是什么？** 两行方案下，"查一次会诊"要 JOIN 两次，或者在应用层拼装。这是一个真实的代价，本文档接受它，理由：

> 会诊的发生频率是每次住院 0~3 次（3.6 万/年），不是一个高频查询。JOIN 两次的代价在毫秒级。而一行方案的代价（申请段与回复段修改历史混在一起、无法区分「没请」与「没回」）是**每一条会诊记录都存在的**、永久的、无法事后修补的信息损失。**用一次的 JOIN 代价换永久的信息完整性，这笔账在病历数据上是划算的。**

#### 4.5.2 会诊回复时限的依据

「普通会诊 24 小时、急会诊 10 分钟」这个数字不是随意定的，写清出处与理由：

| 类型 | 时限 | 依据与理由 |
|---|---|---|
| 普通会诊 | **24 小时** | 三级医院会诊制度通用要求：普通会诊应在申请后 24 小时内完成。取 24 小时而非更短，是因为会诊医师通常要在完成自己当日医疗工作后安排会诊，24 小时是「次日内必须来」的合理表达 |
| 急会诊 | **10 分钟** | 急会诊的实质是「随时可能危及生命」。10 分钟是「从接到电话到到达床旁」的行业惯例。眼科的具体场景是：**眼内炎、眶蜂窝织炎、急性闭角型青光眼发作**——这三类在 10 分钟内的处置差异会直接影响视力预后 |
| 多学科会诊 | **48 小时** | 需要协调多个科室的时间，比普通会诊宽松 |
| 远程会诊 | **24 小时** | 与普通会诊一致，但请求方需先准备资料 |
| 转诊会诊 | **24 小时** | 与普通会诊一致 |

**10 分钟这个阈值的实现要点**（容易写错）：10 分钟从「申请提交成功」算起，不是从「会诊医师看到」算起。而系统无法知道会诊医师何时看到，所以**急会诊必须同时走电话通知通道**——M18 的「10 分钟告警」不是替代电话，而是提供一个可事后举证的时间戳。

这一点必须在文档里写清，否则实现时会把「10 分钟内没回复就告警」做成唯一机制，而实际上如果一个急会诊真的是靠系统消息通知，10 分钟大概率来不及。

#### 索引定义

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m18_ipd_consultation` | PRIMARY KEY | `id` | 主键 |
| `uk_m18_ipd_consultation_no_seg` | UNIQUE | `consult_no, segment` | 一次会诊至多两行，各段各一行 |
| `idx_m18_ipd_consultation_record` | BTREE | `record_id, applied_at DESC` | 按病历取全部会诊 |
| `idx_m18_ipd_consultation_dept` | BTREE | `consult_dept_id, applied_at` | 会诊科室的待会诊列表与统计 |
| `idx_m18_ipd_consultation_pending_partial` | BTREE | `consult_dept_id, applied_at` | 部分索引 `WHERE segment = 'APPLY' AND apply_status IN ('APPLIED', 'ACCEPTED')`。**待回复清单**（与会诊超时扫描的主要查询） |

**约束二是本表最重要的组合约束。** 它规定「申请段不得有回复段字段」。防的错误是：申请时页面为了「一次填完」，把回复区留了几个字段但都提交了空串。于是库里出现一条 `segment='APPLY'` 但 `reply_opinion=''` 的记录。之后超时扫描用 `NOT EXISTS (回复段)` 判断「未回复」，这条记录会正确地被算作未回复；但如果有人用 `reply_opinion IS NULL` 判断，空串不是 NULL，就会被算成已回复。**同一个事实有两套判断方式，其中一套是错的——这就是灾难的起点。**

数据库层禁止申请段带回复字段，就把「未回复」的判断统一成了「不存在回复行」这一种，不会再有第二种写法。

**约束十是个有意思的约束。** 它用 `INTERVAL '10 minutes'` 在数据库层校验「急会诊的截止时间不能超过申请后 10 分钟」。这条约束防的是配置错误——如果 `m18_ipd_config` 里急会诊阈值被误配成 240 分钟，所有急会诊都会「按时」，超时告警永远不响。有了这条约束，配置错了会在写入第一条急会诊时立刻报错。

**组合约束无法表达的部分：**

| 约束 | 由谁保证 |
|---|---|
| 回复段必须有一条对应的申请段 | 应用层：回复段的写入必须带 `consult_no`，而这个号只能由申请接口生成 |
| 同一次会诊最多两行（一段一行） | `uk_..._no_seg` 已保证 |
| 回复时间段晚于申请时间 | 应用层校验 `replied_at > applied_at`（跨行，CHECK 看不到） |

```sql
CREATE TRIGGER trg_m18_ipd_consultation_seal_guard

CREATE OR REPLACE FUNCTION trg_fn_m18_ipd_consultation_finalized_guard()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.status = 'FINALIZED' THEN
    IF NEW.reply_opinion IS DISTINCT FROM OLD.reply_opinion
       OR NEW.consultant_id IS DISTINCT FROM OLD.consultant_id
       OR NEW.replied_at IS DISTINCT FROM OLD.replied_at

END;
```

#### 4.5.3 会诊记录与业务流转的边界

**本表只存病历侧的会诊记录，不存会诊的业务流转。** 这条边界必须写清，否则很容易把「谁接了会诊」「会诊医师排班」「会诊费怎么算」也塞进来。

| 内容 | 归属 | 说明 |
|---|---|---|
| 会诊申请的病历记录（申请科室、理由、紧急程度、申请时间） | **本表** | 病历的一部分 |
| 会诊回复的病历记录（意见、医师、回复时间） | **本表** | 病历的一部分 |
| 会诊请求的**工单流转**（谁接受、谁拒绝、转派给了谁、几点接的） | M07 / M05 的会诊管理 | 这是**业务动作**，不是病历内容 |
| 会诊排班与医师可用性 | M01 / 排班模块 | 主数据 |
| 会诊费 | M17 | 计费 |
| 会诊超时告警的**通知发送** | 本表只产出「超时」这个事实 | 通知由 M03-05 消息服务发 |

一句话：**本表回答「这次会诊在病历上留下了什么」，不回答「这次会诊在业务流程上走到了哪一步」。** 两者可能不一致——业务上会诊已接单，但病历上还没写回复，这是正常的（医师先接诊后补写记录）。**不一致不等于出错**，把两者塞进一张表反而会制造出「到底哪个对」的困惑。

**不分区。** 三年 10.8 万行、约 0.2 GB。见 1.5 节。

### 4.6 表：`m18_ipd_stage_summary`（阶段小结）

#### 用途

住院期间在特定节点写的阶段性小结。与 `m18_ipd_course_record` 结构同构，但**触发来源**不同，且它是病案质量检查的独立检查点。

#### 4.6.1 四种触发来源

| `trigger_source` | 触发条件 | 时限 | 是否强制 |
|---|---|---|---|
| `DURATION` | 住院满 14 天（连续住院） | 满 14 天当日 24:00 前 | 是 |
| `TRANSFER` | 转科（含转病区） | 转科后 24 小时内 | 是 |
| `PRE_SURGERY` | 手术前（同一次住院的第 2 次及以后手术） | 手术开始前 | 是 |
| `POST_SURGERY` | 手术后满 3 天仍住院 | 满 3 天当日 24:00 前 | 否（建议） |

**为什么「住院满 14 天」这个阈值是 14 天。** 这个数字的来源是病案质量管理中「长期住院病例需阶段性回顾」的要求。眼科住院的平均住院日是 3~5 天（白内障日间手术甚至不过夜），超过 14 天仍住院的患者基本只有两类：**术后并发症**（眼内炎、视网膜脱离复发）与**非眼科合并症**（糖尿病足、脑梗后卧床合并眼部疾病）。这两类都是高风险病例，需要阶段性回顾「诊断是否需要修正、治疗方案是否需要调整」。14 天比 7 天更合理，因为眼科的超长住院往往在第 2 周才显露出复杂性。

**为什么「手术前」只对第 2 次及以后的手术强制。** 第一次手术前的评估已经由**术前小结**（M18-04）承担，再要求一份阶段小结是重复。但从第 2 次手术开始（如白内障术后出现视网膜脱离需再次手术），患者已经历过一次治疗，术前必须回顾「第一次为什么失败、这次策略怎么调整」——这正是阶段小结的价值。

**`uk_..._trigger` 那条部分唯一索引是防重复触发用的。** 定时任务扫「住院满 14 天」时会连续几天都命中同一份病历（第 14 天、15 天、16 天都「满 14 天」）。如果没有这条唯一约束，定时任务每跑一次就会生成一条新的阶段小结，一天跑 48 次（每 30 分钟一次）就是 48 条重复记录。有了这条约束，第二次插入直接撞唯一键，任务识别到冲突就跳过——**用数据库的唯一性做幂等，比在应用层查一遍再插入更可靠**（查一遍再插入在有并发时会双写）。

### 4.7 表：`m18_ipd_discharge_summary`（出院小结）

#### 用途

出院小结是住院病历的收尾文书，规定在**出院当日**完成（总纲 §6 `M18-CALC-03`）。

#### 4.7.1 出院小结与病案首页的关系（边界必须写清）

这是最容易写错的一处边界。M05-06 与 M18 各有一份「出院时的诊断」，两者关系必须在数据结构层面就说清。

M05-06 `:109` 原文写得很明确：

> 病案首页 vs 出院小结：首页是**结构化数据表格**（国家标准 76 字段），供统计与医保使用；出院小结是**叙述性文书**（自由文本），供下次就诊参考。

M05-06 `:103` 的「唯一责任划分」：

> 一条数据在 M05 内部只允许有一个写入方。诊断的**临床文本**在 M07-02 与 M18，首页的**编码与上报字段**在 M05-06，两者通过 M07-02 的诊断主表同步，但首页字段由编码员二次确认。

据此，本文档的边界是：

| 内容 | 存在哪 | 谁写 | 谁负责一致性 |
|---|---|---|---|
| 出院诊断的**文字描述**（「左眼老年性白内障（成熟期）」） | **本表** `discharge_diagnosis` JSONB | 出院小结的书写医师 | 医师自己——文字写错由医师负责 |
| 出院诊断的 **ICD 编码**与首页上报字段 | M05-06 `m05_home_page` | 编码员 | 编码员——编码错由编码员负责 |
| 两者不一致时 | 两边都留着 | — | **M18 不修 M05，M05 不修 M18。** 不一致由 M05-06 的「首页质控」提示，编码员手工核对 |

**为什么 M18 不负责把文字描述同步成编码。** 因为这是一个**错误的自动化目标**：把「左眼老年性白内障（成熟期）」自动映射成 ICD 编码，看起来是在帮忙，实际上是在替编码员做判断，而编码是**有法律与医保后果的专业工作**，需要人确认。自动映射一旦把「成熟期」映射成「未成熟期」的编码，医保拒付的责任在谁？

所以本文档明确：**出院小结只提供文字，不提供编码，也不猜编码。** M05-06 的编码员看到出院小结的文字，自己编。两者不一致时，M05-06 的质控提示，编码员决定改哪边。

M05-06 `:201` 也定了另一条底线：「M18 文书存在性 → 降级 → **不阻塞首页**」。也就是说，即使出院小结没写、M18 接口完全不可用，病案首页仍能正常生成。本文档严格遵守这一条：**M18-03 不向 M05-06 提供任何「必须具备才能提交首页」的东西。**

**写入方：** M18-03 出院小结页面、M18-02 通用定稿接口。
**只读方：** M18-05 质控、M18-06 归档、M18-07 检索、M05-06 病案首页（取出院诊断文字，**仅作提示展示，不作写入**）。

#### 4.7.4 出院小结的合法豁免清单

这是 4.7 节最重要的业务定义。**「没有出院小结」有两种情况：合法的与不合规的。** 如果不区分，质控会把合法的判成缺陷，或者把不合规的判成合法。

豁免清单**必须与 M05-06 §3.8 的离院方式表逐条对齐**，否则两个模块对「什么情况下允许没有出院小结」会给出不同答案。

M05-06 `:476-486` 原文表：

| 代码 | 中文 | 是否可豁免出院小结 |
|---|---|---|
| `01` | 医嘱离院 | 否 |
| `02` | 医嘱转院 | 否 |
| `03` | 医嘱转社区 | 否 |
| `04` | 非医嘱离院 | 否 |
| `05` | 死亡 | 是（M05-05 机制） |
| `TRANSFER`（内部码） | 转院 | 是 |
| `AGAINST_ADVICE`（内部码） | 自动出院/非医嘱 | 是 |
| `DECEASED`（内部码） | 死亡 | 是 |

**本文档的豁免规则**（与上表逐条对应）：

| `discharge_mode` | 是否豁免 | 条件 | 依据 |
|---|---|---|---|
| `DOCTOR_ADVICE` | **不豁免** | — | 医嘱离院是标准路径，必须有出院小结 |
| `TRANSFER` | 豁免 | 必须填 `exempt_reason='TRANSFER'` + `exempt_approved_by` | 转院患者由接收医院继续诊疗，本院小结的价值降低；但转院记录本身（在 M05）必须完整 |
| `AGAINST_ADVICE` | 豁免 | 必须填 `exempt_reason='AGAINST_ADVICE'` + `exempt_approved_by` | 患者自行离院，医师无法完成完整的出院评估 |
| `DECEASED` | 豁免 | 必须填 `exempt_reason='DECEASED'` + `exempt_approved_by` | 死亡患者的收尾文书是**死亡记录**（`m18_ipd_course_record.course_type='DEATH'`）与**死亡讨论记录**，不是出院小结 |
| `OTHER` | **不豁免** | — | 无法归类的离院方式按最严处理 |

**关于 `01`~`04` 那四个国标码的映射。** M05-06 的原文里，`01 医嘱离院`~`04 非医嘱离院` 全判「否」，而内部码 `TRANSFER`/`AGAINST_ADVICE`/`DECEASED` 全判「是」。初看矛盾：`04 非医嘱离院` 与 `AGAINST_ADVICE` 不是一回事吗？

不是。M05-06 的原文紧接着写了一句：「内部码与国家标准码的映射在参数 `M05.HOME.DISCHARGE_TYPE_MAP` 中维护」。也就是说 **`discharge_mode` 存的是内部码，国标码只在首页上报时映射**。本文档因此只使用内部码这一套，不引入国标码，避免两套码在 M18 内部流转时对不上。

**为什么「自动出院」可以豁免，但「转社区」不能。** 这两条看起来都像「离开了本院」，但性质完全不同：

- **转社区**（`03`）是**医嘱行为**，患者是被安排转去的，本院医师有时间也有责任写小结，小结要交接给社区医院；
- **自动出院**（`AGAINST_ADVICE`）是**患者单方面决定**，通常发生在患者拒绝继续治疗或对疗效不满时，医师在患者已离开的情况下无法完成完整评估。

**豁免不是「不用管」，而是「换成另一种留痕」。** 每条豁免都要求 `exempt_approved_by` 与 `exempt_at`——即必须有上级医师审批。这防止了「为了方便，把每一例都标成自动出院」。审批人是谁，事后可以追。

```sql
-- 组合约束六：住院天数非负
ALTER TABLE m18_ipd_discharge_summary
  ADD CONSTRAINT ck_m18_ipd_discharge_summary_days
  CHECK (hospital_days IS NULL OR hospital_days >= 0);

-- 组合约束七：出院不得早于入院
ALTER TABLE m18_ipd_discharge_summary
  ADD CONSTRAINT ck_m18_ipd_discharge_summary_time
  CHECK (admitted_at IS NULL OR discharged_at IS NULL OR discharged_at >= admitted_at);

-- 组合约束八：不可测不得有书写时间
ALTER TABLE m18_ipd_discharge_summary
  ADD CONSTRAINT ck_m18_ipd_discharge_summary_unmeasurable
  CHECK (timeliness <> 'UNMEASURABLE' OR written_at IS NULL);

-- 组合约束九：哈希格式
ALTER TABLE m18_ipd_discharge_summary
  ADD CONSTRAINT ck_m18_ipd_discharge_summary_hash
  CHECK (content_hash IS NULL OR content_hash ~ '^[0-9a-f]{64}$');
```

**约束一是本表的核心。** `CHECK (exempt_reason IS NULL OR exempt_reason = discharge_mode)` 这一句把「豁免原因必须与离院方式一致」写成了数据库约束。

它防的错误很具体：有人把 `exempt_reason='DECEASED'` 填到了一个 `discharge_mode='DOCTOR_ADVICE'` 的记录上。这种数据在页面上看起来是「这条出院小结被豁免了，原因是患者死亡」，但实际上患者是医嘱离院——**用豁免理由洗掉一次本该写的出院小结**。数据库拦下它，因为 `DECEASED` 不等于 `DOCTOR_ADVICE`。

同理，不能给 `DOCTOR_ADVICE` 填任何 `exempt_reason`（因为 `exempt_reason` 的三个合法值里没有 `DOCTOR_ADVICE`），这就在数据库层实现了「医嘱离院不豁免」。

### 4.8 表：`m18_ipd_handover`（交接班记录）

#### 用途

记录一次交接班。交接班是住院医疗里最容易出事故的环节——**患者在这段时间里换了照护责任人，而信息没有完整传递**。

#### 4.8.1 为什么交接班必须结构化

先说结论：**交接班记录不能是自由文本。** 这个结论需要论证，因为它与「病程记录就是自由文本」看起来矛盾。

病程记录是自由文本，因为它的读者是下一个看这个患者的医师，他读的是「病情怎么变化了」这个叙述。而交接班记录的读者是**接班的那个医师**，他需要的是三样具体的东西：

| 接班医师需要的 | 自由文本能给的吗 |
|---|---|
| **哪些患者**要交 | 能在文字里写「今天有 8 个患者要交」，但系统无法据此列出清单，无法核对接班医师是否看了这 8 个 |
| 每位患者的**关键状态** | 能写「3 床眼压偏高」，但无法结构化，无法在接班医师的界面上单独高亮，无法做「哪些高危患者没有交」的检查 |
| 每项**待办**是否完成 | 能写「嘱明早复查眼压」，但无法跟踪「明早是否真的复查了」——而这恰恰是交接班失败最常见的形式：**说了但没做，且没人记得** |

第三行是最要命的一条。自由文本的交接班记录**只能证明「说了」，不能证明「做了什么」**。而交接班事故的本质不是没说，是说了没做。

所以本表的结构是：

- 交接班**本身**是一个结构化对象（类型、双方、时间、确认）；
- 交接的**患者清单**是结构化数组（每人一条，含关键状态与待办）；
- 患者的**详细描述**仍然是自由文本（`note` 字段），但它是清单里的一条属性，不是替代清单。

**结构化与自由文本不是二选一，是主从关系**：清单是主，描述是从。清单保证「不漏人、能核查」，描述保证「信息不丢」。

**写入方：** M18-03 交接班页面。交出人建单并提交，接交人确认——**两个不同的写操作，两个不同的写入者**。
**只读方：** M18-05 质控、M18-06 归档、M18-07 检索。

#### 4.8.2 四种交班类型

| `handover_type` | 中文 | 场景 | 是否必须双方确认 | 是否必须有口头交接 |
|---|---|---|---|---|
| `SHIFT` | 班次交接 | 白班→夜班、夜班→白班 | **是** | 否（书面确认即可） |
| `TRANSFER` | 转科交接 | 患者从本科转到其他科室 | **是** | **是** |
| `CRITICAL` | 危重患者交接 | 病危/病重患者的专项交接 | **是** | **是** |
| `TEMPORARY` | 临时交接 | 医师临时离开（会诊、手术、休假） | 是 | 否 |

**为什么 `CRITICAL` 必须有「已口头交接确认」字段。** 危重患者交接的核心信息（「3 床今晚可能眼压再高，超过 25 就给他用甘露醇」）在书面记录里往往写不全，也不会写全——因为书面记录有留痕压力，医师倾向于写得保守；而口头交接可以说得更直白。所以危重交班的**实际执行方式是口头 + 书面补记**，系统如果只记录书面那部分，就漏掉了最关键的那部分。

`verbal_confirmed` 字段记录的是「口头交接已完成」这个事实，以及完成时间。它不是用来存口头内容的（口头内容进不了系统），而是用来**确认这件事发生了**。

**为什么 `TRANSFER` 也必须有口头交接。** 转科交接的风险在于「两个科室都以为对方在管」。文献与行业共识都指向同一结论：转科时必须有双方医师的直接沟通，仅靠书面申请单不够。眼科的具体场景：白内障术后出现视网膜脱离需转到眼底病科，接手的眼底医师必须知道「什么时候发现的、之前用了什么药」，这些在转科申请单里写不下。

**写入方二次说明：** 本表有两个写操作时点，必须分开：

| 时点 | 写什么 | 谁写 |
|---|---|---|
| 建单提交 | 交班类型、患者清单、交出人、交班时间 | 交出人 |
| 确认接交 | `receiver_id`、`received_at`、`confirmed_at`、`verbal_confirmed`（如需） | 接交人 |

**只记交出人不算完成**——这是本表的核心状态约束，见约束三。

#### 4.8.3 `confirm_status` 与 `status` 为什么是两个字段

这两个字段经常被合并，但合并会坏。

| 字段 | 回答的问题 | 取值 |
|---|---|---|
| `status` | 这条交班记录的**书写**是否完成、是否作废 | `WRITING` / `SUBMITTED` / `FINALIZED` / `VOIDED` |
| `confirm_status` | 接交人是否**接收**了 | `PENDING` / `CONFIRMED` / `OVERDUE` / `VOIDED` |

关键区别在于：**交出人写完（`status='FINALIZED'`）与接交人接手（`confirm_status='CONFIRMED'`）是两件事，而它们的时间可能相隔很久，且可能永远不发生。**

真实的失败场景：护士站白班医师写了一整天的交班，提交了（`FINALIZED`），然后下班走了。夜班医师忙了一整晚，第二天早上才想起来确认——或者**根本没确认**。

如果两个状态合并成一个 `status`，那这条交班的 `status` 应该是什么？
- 说是 `FINALIZED`，那它看起来完成了，但根本没人接手；
- 说是 `PENDING`，那它看起来还没写完，但交出人明明写完了。

分开之后就清楚了：`status='FINALIZED'` 且 `confirm_status='OVERDUE'`——书写完成但未在规定时间被接收。**这才是真实发生的状态**，而且是一个可以被统计、可以被追责的状态。

**`confirm_status` 的 `OVERDUE` 由定时任务写，不由人写。** APScheduler 每 5 分钟扫 `confirm_status='PENDING'` 且 `expected_at < now()` 的记录，置 `OVERDUE` 并写 `m18_ipd_oper_log`。这样「有多少交班没有被确认」是一个可以每天看板的数字。

```sql
ALTER TABLE m18_ipd_handover
  ADD CONSTRAINT ck_m18_ipd_handover_hash
  CHECK (content_hash IS NULL OR content_hash ~ '^[0-9a-f]{64}$');
```

**四条约束值得单独解释：**

**约束一（`CONFIRMED` 必须齐备双方与时间）** 是 lead 任务书里「交班必须双方确认（交出人 + 接交人 + 确认时间），只记交出人不算」那句话的数据库实现。它保证了一条记录只要标记为「已确认」，就必然有接交人、接收时间、确认时间三个东西。缺任何一个都插不进去。

**约束二（不得自己交给自己）** 防的是「补签字」：事后为了凑交接班记录，用自己的账号再确认一次。这在系统里看起来是合法的（有交出人、有接交人、有时间），但两个 ID 相同，一眼可辨。数据库层禁止，比事后审计发现更有用。

**约束三（危重/转科必须有口头确认）** 是 4.8.2 那张表的实现。注意它要求 `verbal_confirmed_at IS NOT NULL`——只有布尔标记不够，还要有确认时间。这是为了能回答「什么时候口头交接的」，而不仅是「有没有口头交接」。

**约束七（危重患者数不超过清单长度）** 是个细节但有用：`critical_count=5` 而 `patients` 只有 3 条，说明计数与清单不同步，页面会显示出「5 个危重患者」但只列出 3 个，接班的医师会以为漏了。

**组合约束无法表达的部分：**

| 约束 | 由谁保证 |
|---|---|
| `patients` 里每个元素的 `encounter_id` 必须真实存在于本次住院 | 应用层校验（JSONB 内部无法建外键） |
| `pending_task_count` 必须等于 `pending_tasks` 数组长度 | 应用层写入时计算；并有定时任务每日对账 |
| `expected_at` 应按配置阈值计算 | 应用层 |

#### 封存触发器挂载与权限回收

```sql
CREATE TRIGGER trg_m18_ipd_handover_seal_guard
  BEFORE INSERT OR UPDATE ON m18_ipd_handover
  FOR EACH ROW EXECUTE FUNCTION trg_fn_m18_seal_guard();

CREATE OR REPLACE FUNCTION trg_fn_m18_ipd_handover_finalized_guard()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.status = 'FINALIZED' THEN
    -- 允许接交人确认（receiver_id/received_at/confirmed_at/verbal_*/confirm_status）
    -- 不允许修改交接内容本身
    IF NEW.patients IS DISTINCT FROM OLD.patients
       OR NEW.pending_tasks IS DISTINCT FROM OLD.pending_tasks
       OR NEW.handover_type IS DISTINCT FROM OLD.handover_type
       OR NEW.handover_by IS DISTINCT FROM OLD.handover_by
       OR NEW.handover_at IS DISTINCT FROM OLD.handover_at
       OR NEW.content_hash IS DISTINCT FROM OLD.content_hash THEN
      RAISE EXCEPTION 'SEGMENT_FINALIZED_IMMUTABLE'
        USING HINT = '交接班已提交，交接内容不可修改。接交人确认不受此限';
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m18_ipd_handover_finalized_guard
  BEFORE UPDATE ON m18_ipd_handover
  FOR EACH ROW EXECUTE FUNCTION trg_fn_m18_ipd_handover_finalized_guard();

REVOKE DELETE ON m18_ipd_handover FROM app_m18;
```

**本表的定稿闸与其它表不同，必须特别说明。** 其它表的定稿闸是「定稿后一律不可改」，而本表**必须允许接交人在交出人提交后继续写确认字段**。所以闸门只冻结「交接内容」（患者清单、待办、类型、交出人、交班时间），不冻结「确认字段」。

这意味着 `content_hash` 在定稿时计算，**计算范围是交接内容，不含确认字段**。如果计算范围含确认字段，那么接交人一确认，哈希就变了，而哈希在禁改清单里——接交人就永远无法确认。**这是一个如果写错就会导致整个交接流程卡死的细节**，所以 `content_hash` 的输入字段清单必须明确：

```text
content_hash = SHA256(
    handover_no || '|' ||
    handover_type || '|' ||
    handover_at || '|' ||
    handover_by || '|' ||
    canonical_json(patients) || '|' ||
    canonical_json(pending_tasks) || '|' ||
    note
)
```

`canonical_json` 指键排序、无多余空格的确定性 JSON 序列化。**不含** `receiver_id`/`received_at`/`confirmed_at`/`verbal_confirmed`/`verbal_confirmed_at`/`confirm_status`。

**不分区。** 三年 24 万行、约 0.7 GB。见 1.5 节。

### 4.9 表：`m18_ipd_config`（住院病历配置）

#### 用途

存放住院病历各类时限阈值、必填段落要求、查房频次要求、豁免规则。**这张表是本文档唯一带 `is_deleted` 的表**，因为它是配置类表，草稿删掉就是删掉。

#### 4.9.1 为什么配置要落表而不是写死常量

时限阈值（入院记录 24 小时、首次病程 8 小时）看起来是「国家规定，不会变」，为什么还要落表？

三个理由，按重要性排序：

1. **不同病区的阈值确实不同。** 日间手术病区的术后首次病程要求是 24 小时，但如果是日间手术当天出院，实际可用的书写窗口只有几个小时。这类差异必须按病区配置，写死常量就得改代码。
2. **阈值变化时，历史记录的口径必须保持不变。** 这是最关键的。每条记录都落了 `config_version`，并落了 `window_deadline_at`（按当时的配置算出来的绝对时间）。即使明天把入院记录时限从 24 小时改成 12 小时，昨天已产生的记录仍然按 24 小时判定，统计可复现。**如果阈值是代码常量，改一次代码，全体历史记录的口径都会变。**
3. **配置变更本身要留痕。** 谁在什么时候把阈值改松了，是一个需要审计的事实。落表才能审计。

```sql
ALTER TABLE m18_ipd_config
  ADD CONSTRAINT ck_m18_ipd_config_code
  CHECK (config_code ~ '^IPD_[A-Z0-9_]{3,58}$');

ALTER TABLE m18_ipd_config
  ADD CONSTRAINT ck_m18_ipd_config_scope
  CHECK (config_scope = ANY (ARRAY['HOSPITAL', 'DEPT', 'WARD']));

  ADD CONSTRAINT ck_m18_ipd_config_type
  CHECK (value_type = ANY (ARRAY['INT', 'DECIMAL', 'BOOL', 'STRING', 'JSON']));

ALTER TABLE m18_ipd_config
  ADD CONSTRAINT ck_m18_ipd_config_version
  CHECK (config_version >= 1);

ALTER TABLE m18_ipd_config
  ADD CONSTRAINT ck_m18_ipd_config_range
  CHECK (min_value IS NULL OR max_value IS NULL OR min_value <= max_value);

ALTER TABLE m18_ipd_config
  ADD CONSTRAINT ck_m18_ipd_config_period
  CHECK (effective_to IS NULL OR effective_to > effective_from);

-- 组合约束一：非全院范围必须有范围对象
ALTER TABLE m18_ipd_config
  ADD CONSTRAINT ck_m18_ipd_config_scope_ref
  CHECK ((config_scope = 'HOSPITAL' AND scope_ref_id IS NULL)
         OR (config_scope <> 'HOSPITAL' AND scope_ref_id IS NOT NULL));

-- 组合约束二：豁免类配置必须有审批
ALTER TABLE m18_ipd_config
  ADD CONSTRAINT ck_m18_ipd_config_exempt_approve
  CHECK (is_exempt_rule = FALSE
         OR (approved_by IS NOT NULL AND approved_at IS NOT NULL));

-- 组合约束三：INT 类型配置值必须是整数
ALTER TABLE m18_ipd_config
  ADD CONSTRAINT ck_m18_ipd_config_int
  CHECK (value_type <> 'INT' OR config_value ~ '^-?[0-9]+$');

-- 组合约束四：BOOL 类型配置值只能是 true/false
ALTER TABLE m18_ipd_config
  ADD CONSTRAINT ck_m18_ipd_config_bool
  CHECK (value_type <> 'BOOL' OR config_value IN ('true', 'false'));

-- 组合约束五：JSON 类型配置值必须是合法 JSON 数组或对象
-- 用 jsonb 转换尝试：非法 JSON 会在写入时报错
ALTER TABLE m18_ipd_config
  ADD CONSTRAINT ck_m18_ipd_config_json
  CHECK (value_type <> 'JSON' OR jsonb_typeof(config_value::jsonb) IN ('array', 'object'));
```

**约束五有个实现细节值得说明。** `config_value::jsonb` 在 `CHECK` 表达式里做类型转换，如果 `config_value` 不是合法 JSON，转换本身会抛异常——这达到了「非法 JSON 写不进去」的效果，但**异常类型是 `invalid_text_representation` 而不是约束违反**，应用层捕获时要注意区分。这是 PostgreSQL 的既定行为，不是设计缺陷。

### 4.10 表：`m18_ipd_oper_log`（住院病历操作日志）

#### 用途

记录对住院病历各段落的写操作、定稿、作废、超时告警、豁免审批。**按月 RANGE 分区**，这是本文档唯一分区的表。

#### 4.10.1 为什么这张表分区，而病历事实表不分区

1.5 节已经说了结论，这里给出对照，因为「为什么这张要分那张不要」是最容易被质疑的一处：

| 维度 | `m18_ipd_course_record`（不分） | `m18_ipd_oper_log`（分） |
|---|---|---|
| 三年行数 | 64.8 万 | 108 万 |
| 三年体积 | 1.0 GB | 0.55 GB |
| **是否按时间批量删除** | **否**（留存 30 年） | **是**（在线只留 3 年） |
| 查询是否总带时间范围 | 不一定（按患者查时全期间） | **总是**（日志查询必带期间） |
| 分区收益 | 无 | `DETACH PARTITION` 秒级下线 3 年前数据；查询自动裁剪 |

关键在第四行：**日志的每一次查询都带时间范围**（「查本月」「查昨天」），而病程的查询经常不带（「查这个患者本次住院的全部病程」）。只有查询总带分区键时，分区裁剪才有意义。

第三行是决定性理由：分区让「删除 3 年前的数据」从 `DELETE`（扫描 + 膨胀 + VACUUM）变成 `DETACH`（改元数据，秒级）。而病历数据永远不删，所以这个收益它拿不到。

#### 4.10.2 `risk_level` 的判定规则

日志表的价值取决于「哪些事件被标为高危」。如果全是 `INFO`，等于没有分级；如果全是 `CRITICAL`，等于全是噪音。

| 事件 | `risk_level` | 理由 |
|---|---|---|
| 段落 `CREATE` | `INFO` | 正常书写 |
| 段落 `UPDATE`（`WRITING` 状态内） | `INFO` | 草稿编辑 |
| 段落 `SUBMIT` | `INFO` | 正常提交 |
| 段落 `FINALIZE` | `INFO` | 正常定稿 |
| 段落 `VOID` | `WARN` | 作废是例外事件，虽然合法但需关注频率 |
| `SEAL_BLOCKED`（封存后被拒写） | `CRITICAL` | **这是本文档最重要的告警**，见下 |
| 定稿段落的改写入侵（触发器抛异常前记录） | `CRITICAL` | 有人在尝试修改已定稿内容 |
| `TIMEOUT_ALERT` | `WARN` | 时限即将超时 |
| `EXEMPT_APPROVE` | `WARN` | 出院小结豁免审批 |
| `HANDOVER_OVERDUE` | `CRITICAL` | **交班未被确认**，这是安全管理事件 |
| `CONFIRM` | `INFO` | 接交人确认 |
| 补录（`created_at` 晚于 `written_at` 超阈值） | `WARN` | 见 4.3.6 |

**`SEAL_BLOCKED` 为什么是 `CRITICAL`。** 封存是病案管理的终态——一旦封存，说明这份病案正在被用于医疗纠纷、司法调查、医保稽核。此时任何对它的写入尝试，都不是普通的误操作，而是**有人在试图改动正在被封存的证据**。这条日志必须 `CRITICAL`，必须实时告警到医务科与信息科，且必须保留完整的操作人信息。

**`HANDOVER_OVERDUE` 为什么是 `CRITICAL`。** 4.8 节已经论证：交接班未确认是住院安全管理的高风险事件。一条 `CRITICAL` 交班没被确认，意味着接班医师可能不知道某个病危患者的禁忌。这不是文书问题，是患者安全问题。

#### 4.10.3 `changed_fields` 只记字段名，不记字段值

这是一个必须解释的设计选择。常见的审计日志会存「旧值 → 新值」，本文档只存字段名数组。

理由：**存旧值会让日志表本身变成病历正文本的副本。**

假设日志存了旧值。那么：
- 一份被作废的病历，它的正文会同时存在于「作废的记录里」和「N 条日志的旧值字段里」；
- 铁律 4 要求「作废的病历正文永久留存但不可访问」——而日志表的访问权限比病历表宽（审计、运维都要看日志）；
- 于是「永久留存但有限访问」变成了「在日志里随便看」。

所以本文档的做法是：**日志只回答「哪些字段被改过、改前改后的哈希是什么」，正文本身只在业务表里。** 要取证「改前是什么」，用 `before_hash` 去 `m18_emr_amendment` 或归档副本里比对，而不是从日志里读出来。

**代价**：看日志无法直接知道「改成了什么」，要回业务表看当前值，或者靠哈希比对证明「变过」。这个代价可以接受，因为日志的用途是「发现异常」，不是「还原内容」。

```sql
ALTER TABLE m18_ipd_oper_log
  ADD CONSTRAINT ck_m18_ipd_oper_log_result

  ADD CONSTRAINT ck_m18_ipd_oper_log_risk
  CHECK (risk_level = ANY (ARRAY['INFO', 'WARN', 'CRITICAL']));

-- 组合约束一：SEAL_BLOCKED 必须是 CRITICAL
ALTER TABLE m18_ipd_oper_log
  ADD CONSTRAINT ck_m18_ipd_oper_log_seal_risk
  CHECK (action <> 'SEAL_BLOCKED' OR risk_level = 'CRITICAL');

-- 组合约束二：HANDOVER_OVERDUE 必须是 CRITICAL
ALTER TABLE m18_ipd_oper_log
  ADD CONSTRAINT ck_m18_ipd_oper_log_handover_risk
  CHECK (action <> 'HANDOVER_OVERDUE' OR risk_level = 'CRITICAL');

-- 组合约束三：被拒绝/被阻断的操作必须有原因
ALTER TABLE m18_ipd_oper_log
  ADD CONSTRAINT ck_m18_ipd_oper_log_reason
  CHECK (action_result = 'SUCCESS'
         OR (reason IS NOT NULL AND btrim(reason) <> ''));

-- 组合约束四：哈希格式
ALTER TABLE m18_ipd_oper_log
  ADD CONSTRAINT ck_m18_ipd_oper_log_hash
  CHECK ((before_hash IS NULL OR before_hash ~ '^[0-9a-f]{64}$')
         AND (after_hash IS NULL OR after_hash ~ '^[0-9a-f]{64}$'));
```

**约束一与约束二把 4.10.2 那张表里最重要的两条风险级别钉死在数据库层。** 理由很简单：`risk_level` 是应用层赋值的一个字段，如果代码里某个分支忘了赋 `CRITICAL`，那么「封存期被改写的尝试」就变成了一条不起眼的 `INFO` 日志，永远没人看见。数据库层强制它必须是 `CRITICAL`，代码写错会直接失败。

```sql
CREATE TABLE m18_ipd_oper_log_p202610 PARTITION OF m18_ipd_oper_log
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE m18_ipd_oper_log_p202611 PARTITION OF m18_ipd_oper_log
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

  FOR VALUES FROM ('2026-12-01') TO ('2027-01-01');

CREATE TABLE m18_ipd_oper_log_default PARTITION OF m18_ipd_oper_log DEFAULT;
```

**为什么 `DEFAULT` 分区不是可选项。** 汇总 §4 已明确要求。理由：分区是按月预建的，如果预建脚本某个月漏跑了（部署失败、调度器挂了、新增月份没人加），那么该月的数据插入会因为「没有匹配的分区」而**直接报错**——业务功能整个不可用。有了 `DEFAULT` 分区，数据会落到默认分区里，业务正常，只是这个默认分区的数据在清理时需要特殊处理。

**`DEFAULT` 分区的运维要求**：监控必须检查 `m18_ipd_oper_log_default` 的行数，一旦大于 0 就告警「分区预建漏跑」。**它是保险丝，不是正常路径。**

#### 权限与分区维护

```sql
-- 日志表只允许 INSERT，不允许 UPDATE / DELETE
REVOKE UPDATE, DELETE ON m18_ipd_oper_log FROM app_m18;
GRANT INSERT, SELECT ON m18_ipd_oper_log TO app_m18;

-- 分区维护作业（每月 25 日预建下月分区 + DETACH 超期分区）
-- 由 APScheduler 任务 m18_ipd_log_partition_maintain 执行
```

**为什么日志表要 `REVOKE UPDATE`。** 因为日志的作用是「证明某件事发生过」。允许 UPDATE 就等于允许「事后改写日志以掩盖」。而日志表一旦可以被 UPDATE，它作为证据的价值就归零了——对方律师只需要问一句「你们怎么证明这条日志没被改过」。

**注意：本表 `REVOKE UPDATE`，但保留了 `UPDATE` 的数据库权限给分区维护作业**（作业用独立的数据库账号 `app_m18_maintain`，不走 `app_m18`）。

#### 分区策略

**按月 RANGE 分区，在线保留 3 年**，3 年以外的分区由 `m18_ipd_log_partition_maintain` 作业 `DETACH` 后归档到离线存储。

为什么日志只留 3 年，而病历留 30 年？因为日志回答的是「当时的操作是否合规」，这是**质量管理**问题，一般追溯期在 3 年内；而病历正文是**医疗事实**，30 年内随时可能被调阅。两者的留存期不同，不是因为重要性不同，而是因为**用途的时效性不同**。
### 4.11 SQLAlchemy 2.0 模型定义

本节给出 `m18_ipd_` 九张表的 ORM 模型，供 `app/models/ipd.py` 落库。

**统一约定：**

| 约定 | 说明 |
|---|---|
| 基类 | 继承 `M18BaseMixin`（由 M18-02 在 `app/models/base.py` 定义），提供 `created_at`/`created_by`/`updated_at`/`updated_by` 四个公共字段 |

| `IpdAdmission` | `measurability`/`unmeasurable_reason`/`is_on_time` 三列的组合约束在 ORM 里也声明，防止开发绕过数据库校验直接用 ORM 写入 |
| `IpdCourseRecord` | `satisfies_daily_requirement` 与 `frequency_exempt_reason` 的组合约束保证「豁免必须有理由」 |
| `IpdConsultation` | `APPLIED_NO_REPLY` 在 ORM 里是显式常量，不是「`reply_at IS NULL` 推断出来的」 |
| `IpdHandover` | `CONFIRMED` 必须有交出人、接交人、确认时间三者，ORM 层同样拦截 |
| `IpdConfig` | 唯一带 `is_deleted` 的表；唯一索引是**部分索引**（`WHERE is_deleted = FALSE`），软删后同 key 可重建 |
| `IpdOperLog` | `__table_args__` 里第一个元素是字典（分区子句），后面才是索引与约束；SQLAlchemy 要求字典在前 |

**为什么不给 `record_id` 加 `ForeignKey`：** `m18_emr_record` 由 M18-02 首建，物理外键会把 M18-03 的建表顺序钉死在 M18-02 之后，而共享规范 §3.2 允许各子模块独立建表。代价是数据库层不做引用完整性校验，由服务层在写入前调 `assert_record_exists()` 校验，并且 `idx_m18_ipd_*_record` 索引保证校验与按 record 反查都走索引。同理，`patient_id`/`encounter_id` 也是逻辑外键。
### 4.12 Pydantic Schema 定义

本节给出对外接口的入参/出参 Schema，供 `app/schemas/ipd.py` 使用。

**统一约定：**

| 约定 | 说明 |
|---|---|
| Pydantic 版本 | V2（`model_config = ConfigDict(...)`，不用 V1 的 `class Config`） |
| 出参基类 | 所有 `*Out` 继承 `ApiData`（由 M18-02 在 `app/schemas/base.py` 定义），自动带 §8A.2 的四个质量标记 `degraded`/`degraded_sources`/`data_quality`/`as_of` |
| 集合出参 | 继承 `ApiPage`，在四标记之外再加 `record_count`/`total` |
| 枚举校验 | 用 `Literal[...]` 而非 `Enum`，与数据库 `VARCHAR(32)` + `CHECK` 的取值逐字对齐，序列化时直接是字符串 |
| 时间 | `datetime`，序列化为 `YYYY-MM-DD HH:MM:SS`（不带时区），由 `field_serializer` 保证 |
| 完整性 | 每个类都写了完整的字段校验，**没有用省略号略写的字段** |

```python
    必须能下钻看到是哪几条、为什么判定不了。
    """

    table_name: str
    biz_id: int
    patient_id: int
    encounter_id: Optional[int]
    unmeasurable_reason: UnmeasurableReason
    reason_text: str = Field(description="面向人的原因说明，如「入院时间为空」")


class TimelinessRateOut(ApiData):
    """病历及时率三元组。

    恒等式：on_time_count + overdue_count + unmeasurable_count
            = total_measured + total_unmeasurable
    其中 total_measured = on_time_count + overdue_count，
         total_unmeasurable = unmeasurable_count。
    """

    dept_id: Optional[int]
    period: str = Field(description="统计期间，格式 YYYY-MM")
    record_kind: Literal["ADMISSION", "FIRST_COURSE", "DISCHARGE_SUMMARY", "OPERATION"]

    on_time_count: int = Field(ge=0)
    overdue_count: int = Field(ge=0)
    unmeasurable_count: int = Field(ge=0)
    total_measured: int = Field(ge=0, description="= on_time_count + overdue_count")
    total_unmeasurable: int = Field(ge=0, description="= unmeasurable_count")
    total_window_entered: int = Field(
        ge=0, description="= total_measured + total_unmeasurable，即进入书写窗口的总数"
    )

    timely_rate: Optional[float] = Field(
        default=None,
        description="= on_time_count / (on_time_count + overdue_count)；分母为 0 时为 null，不是 0",
    )
    unmeasurable_items: list[TimelinessUnmeasurableItem] = Field(default_factory=list)

    @model_validator(mode="after")
    def _check_triplet(self):
        if self.total_measured != self.on_time_count + self.overdue_count:
            raise ValueError("total_measured 必须等于 on_time_count + overdue_count")
        if self.total_unmeasurable != self.unmeasurable_count:
            raise ValueError("total_unmeasurable 必须等于 unmeasurable_count")
        if (
            self.on_time_count + self.overdue_count + self.unmeasurable_count
            != self.total_window_entered
        ):
            raise ValueError("三元组之和必须等于总进入窗口数")
        denominator = self.on_time_count + self.overdue_count
        if denominator == 0:
            if self.timely_rate is not None:
                raise ValueError("分母为 0 时 timely_rate 必须为 null")
        else:
            expected = round(self.on_time_count / denominator, 6)
            if self.timely_rate is None or abs(self.timely_rate - expected) > 1e-6:
                raise ValueError("timely_rate 必须等于 on_time / (on_time + overdue)")
        return self
```

**Schema 说明：**

| Schema | 关键约束 | 为什么这样设计 |
|---|---|---|
| `ApiData` | `model_validator` 强制 `degraded` 与 `degraded_sources` 同向 | 只写 `degraded: true` 不给来源，前端只能显示「数据可能不准」，等于没告诉人哪里不准 |
| `CourseCalendarCell` | `cell_state` 是四态 `WRITTEN`/`WRITTEN_EMPTY`/`NOT_STARTED`/`MISSING` | 三态不够：还要区分「该写没写」和「窗口没到」，否则页面会把明天的空格也标红 |
| `ConsultationQuery` | `include_no_reply` 默认 `True` | 默认值必须是「包含」，因为漏掉「已申请未回复」会让主管医生重复申请 |
| `HandoverConfirm` | `oral_confirmed` 交班类型为 `CRITICAL` 时必填且必须 `true` | 只在 DDL 层约束不够，前端提交时就要拦住 |
| `TimelinessRateOut` | 恒等式 + 分母为 0 必须 `null` + 三元组校验 | 让「分子分母对不上」在反序列化阶段就报错，而不是等到医务科质疑报表 |
| `DischargeSummaryCreate` | `exempt_reason` 必须等于 `discharge_mode` | 与数据库约束同义，前端提交时先拦一次，错误信息比数据库报错更好读 |

### B.3 为什么 `uk_m18_ipd_admission_record` 是普通唯一索引而不是部分索引

`is_current` 那套部分唯一索引是 `m18_emr_record` 用的（同一就诊可有多版本记录，只有 `is_current = TRUE` 的唯一）。入院记录的粒度不同：**一次住院就只有一份入院记录**，作废后重写是新建一条 `m18_emr_record`，新的入院记录行有新的 `record_id`，旧的入院记录行仍在（`status = 'VOIDED'`）。所以这里用「`record_id` 唯一」就够了，不需要 `WHERE` 子句——加了 `WHERE status <> 'VOIDED'` 反而会允许同一 `record_id` 出现两条活着的与一条作废的，那才是真正的错误。

## 附录 D：JSONB 字段结构说明

本子模块只有一个 JSONB 字段：`m18_ipd_oper_log.changed_fields`。其余七张正文表的结构化字段一律用真正的列，不用 JSONB——用 JSONB 存会写字段，就等于放弃了数据库层的 CHECK 约束与类型校验，而病历正文恰恰是最不能靠应用层自觉的地方。

### D.1 `m18_ipd_oper_log.changed_fields`

**结构：** `string[]`，元素是发生变化的列名。

```json
["status", "content_hash", "written_at"]
```

| 规则 | 说明 |
|---|---|
| 只记字段名 | **绝不记字段值**。记值等于把病历正文复制一份到日志表，日志表没有正文表那套权限控制，反而扩大了泄露面 |
| 只记变化项 | 未变化的列不出现，避免每行都塞进全部列名 |
| 创建时为空数组 | `action = 'CREATE'` 时记 `[]`，因为「全部字段都是新的」用列表表达没有意义 |
| 上限 64 项 | 单表列数远小于 64，超过说明调用方错误地传了整个对象 |
| 顺序不保证 | 调用方不得依赖元素顺序 |

**为什么不用 `{"field": "old", "new": "value"}` 这种差分结构：** 我最初想记前后值，后来否掉了。理由是本子模块七张表里有多张含病历正文（`m18_ipd_course_record` 的病程内容、`m18_ipd_consultation` 的会诊意见），前后值一旦进日志表，日志表就成了「病历正文的第二个副本」，而它的访问控制远没有正文表严格。要查具体改了什么，正文侧有 `m18_emr_amendment` 与版本号，不需要日志表再存一份。
