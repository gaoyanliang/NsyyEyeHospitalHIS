## 1. 模块定位

### 1.1 一句话定位

**M18 电子病历与知识库是全院「临床内容」与「医学知识」的唯一权威。**

- 抓**病历内容**：门诊 / 住院 / 日间手术 / 急诊病历的正文书写、结构化字段、模板、质控、归档、封存、更正。
- 抓**临床知识**：合理用药规则、剂量上限、相互作用、临床路径、眼科专科知识、DRG 权重、分诊规则。
- 为 M07 医生工作站、M05 住院、M06 日间手术、M09 手术麻醉、M14 药房、M04 门诊、M08 护理提供内容与知识服务。

### 1.2 为什么独立成模块

| # | 理由 | 事实支撑 |
|---|---|---|
| **1** | **病历内容与业务操作必须分离，否则无法保证病历的完整性与法律效力** | M07 原文 `M07医生工作站/M07_医生工作站_详细设计.md:71`：「**内容与操作分离**：M07 做业务操作，M18 做内容与知识」。M07 已经承载了接诊、诊断、医嘱、处方、检查、手术申请 6 大操作域共 40+ 张表；若病历正文也塞进 M07，任何一次操作改动都可能波及病历正文 |
| **2** | **法定保存期限长达 15~30 年，需要一个独立的、以「不可变」为前提设计的数据域** | 门诊病历 15 年（`M16收费结算管理/M16_收费结算管理_详细设计.md:1006`）、住院病历 30 年（`M05住院管理/M05_住院管理_数据结构设计汇总.md:641`）、屈光档案永久（`M11屈光手术管理/M11_屈光手术管理_数据结构设计汇总.md:587`）。M07/M05 的业务表设计前提是「单据会流转、会变更」，而病历的设计前提是「一旦签署就永远不能变」——**两套截然相反的数据哲学不能放在同一个模块里** |
| **3** | **知识库是被多模块共享的横切能力，必须唯一** | M07-05 `M07医生工作站/M07_医生工作站_05_处方与用药_详细设计.md:238`、M14-06 `M14药房药库管理/M14_药房药库管理_06_处方审核_详细设计.md:153`（「M14-06 **不创作**任何药品知识…规则全部来自 M01-03 或 M18」）、M04 `M04门诊管理/M04_门诊管理_详细设计.md:263`（「分诊知识库谁维护？**M18**」）、M05-07 DRG 权重 `M05住院管理/M05_住院管理_07_住院统计与床位效率_详细设计.md:632`。**四个模块都依赖同一套知识，而知识的更新必须一次生效**——分散在各模块会出现「药房说禁用、医生站说可用」 |
| **4** | **质控是病历的「事后审计」维度，与「事中书写」正交** | M08-05 `M08护理工作站/M08_护理工作站_05_护理记录与文书_详细设计.md:227` 原文：「电子病历质控 / M18（未设计）/ 时限质控、逻辑质控等」——护理侧已经把自己的质控期待挂在 M18 上。质控规则会随卫健委检查标准年年变，而病历正文不该跟着改 |

### 1.3 与相邻模块的边界

> **完整边界表见 [共享规范 §1.2 / §1.3](00_M18_电子病历与知识库_模块设计_共享规范与文档模板.md)。此处只给最关键的三个。**

| 相邻方 | 一句话边界 |
|---|---|
| **M07 医生工作站** | **M07 回答「医生做了什么操作」，M18 回答「病历上写了什么、依据哪条知识判断的」。** M07-06 只做渲染 / 签名 / 打印 / 留痕（原文 `M07医生工作站/M07_医生工作站_06_文书签署与打印_详细设计.md:76`「本模块负责签名与打印，不含书写」），M18 做正文与模板；M07-05 / M14-06 只做知识**执行**，M18 做知识**内容** |

| **M06 日间手术** | **M06 负责归档动作，M18 是归档接收方与存储方。** M06-06 `:197` 原文：「封存是医务科的事（在 M18 电子病历模块，`m18_emr_seal`）」；M06 落本地 `emr_doc_id` / `emr_sync_status`，M18 是权威 |

### 1.4 一条不可逾越的红线

```
M18 只做「内容」与「知识」，不做「操作」。
```

禁止 M18 自建的表（完整清单见共享规范 §1.4）：

| 禁止的表 | 归属 |
|---|---|
| `m18_order` / `m18_order_item` | M07-03 医嘱下达 |
| `m18_diagnosis` | M07-02 诊断与印象 |
| `m18_prescription` / `m18_prescription_item` | M07-05 处方与用药 |
| `m18_document` / `m18_document_signature` / `m18_consent_sign` | M07-06 文书签署与打印 |
| `m18_home_page` | M05-06 住院病案首页 |
| `m18_surgery_record` | M09 手术麻醉管理 |
| `m18_nursing_record` | M08 护理工作站 |
| `m18_drug` / `m18_drug_interaction_master` | M01-03 药品主数据 |

> **这条红线是被真实风险逼出来的。** 若 M18 自建诊断表，医生在 M07-02 录入的「双眼老年性白内障」和 M18 病历里写的「白内障（右）」就是两条互不相干的数据，病案首页编码时统计员不知道信哪个，DRG 分组会错，医保回款会少。若 M18 自建签署表，一份同意书会出现「M07-06 说签了、M18 说没签」两个状态，**术前核对查的是哪一个，直接决定患者是否在没有签字的情况下进手术室**。

### 2.3 为什么这么分

**① 为什么把「模板」与「病历书写」拆成 M18-01 与 M18-02？**
模板是**配置类**数据（一年改动几十次，一份模板被上千份病历引用），病历是**事实类**数据（一年几十万行，一经签署不可改）。两者生命周期、写频率、修改权限完全不同：模板可以随时出新版本，病历一个字都不能改。混在一个子模块里，校验器无法区分哪些表「可以 UPDATE」、哪些「绝对不行」。**证据**：M18-02 的 `m18_emr_record` 必须 `REVOKE UPDATE`，而 M18-01 的 `m18_tpl_template` 天天在改——两张表在同一个模块里，DBA 一定会复制粘贴权限脚本。

**② 为什么把门诊病历、住院病历、手术病历拆成三个子模块？**
三者的**内容结构差异极大**，不是同一种文书的变体：
- 门诊病历是**单次、短、结构化程度低**（主诉+现病史+体格检查+处理意见），一个医生 5 分钟写完。
- 住院病历是**多次、长、时序性强**（入院记录 + 首次病程 + 日常病程 × 十几次 + 查房 + 会诊 + 出院小结），一份病历跨 7~15 天。
- 手术病历是**模板化最高、必检项最多**（术前讨论、手术记录、麻醉记录、术后首次病程，缺一项就是甲级病历缺陷）。

合并成一个子模块的结果是：三套状态机、三套校验规则塞进一张表，`section_type` 枚举膨胀到 16 个值且每个值的必填规则都不同。**证据**：全仓已定义 `SECTION` 相关字段在 M05（D-02/D-04/D-07）、M07-06（12 种文书类型）、M09（手术/麻醉记录）三处，各自的内容结构完全不同。

**③ 为什么「质控」与「合理用药审核」合在一起（M18-05）？**
两者的**输入相同（病历 + 处方）、输出形态相同（缺陷/提示 + 评分）、时效相同（事后批跑 + 事中拦截）**。合理用药审核本质上是「用药维度的一次逻辑质控」。拆成两个子模块会得到两张结构几乎一样的「规则表 + 命中记录表」，而且质控评分时还要跨子模块 JOIN 才能算出「这份病历因为用药问题扣了多少分」。**证据**：M07-05 `:4048` 的降级要求是「M18 合理用药 → 本地基础校验，记录告警」——「记录告警」正是质控缺陷表的形态。

**④ 为什么「归档封存更正」是一个子模块（M18-06）？**
归档、封存、更正、借阅、销毁**全部围绕同一个不变量：病历的不可变性**。归档是「内容冻结的前提」，封存是「更强的内容冻结」，更正是「冻结之后唯一的合法改动路径」，借阅是「冻结状态下允许的访问」。五件事共用同一套封存检查逻辑（每次读写都要先问「这份病历封了吗」）。**证据**：M05-05 与 M06-06 两个模块都在调归档/撤销归档/封存三个动作，如果拆开，两个模块要分别实现「先查封存再归档」的顺序，只要有一处写反，封存中的病历就能被重新归档覆盖。

**⑤ 为什么「检索统计」（M18-07）独立？**
它的数据源是**全部子模块**，且只读。放进任何一个业务子模块都会让它「看起来」只统计那一个域。而且检索与统计是 M22 报表体系的上游（M22 是通过下钻接口读、不落库的病历统计），独立后边界清晰：**M18-07 产事实与聚合快照，M22 做统一口径与决策呈现**。

**⑥ 为什么「知识与路径」（M18-08）独立？**
它不产生病历，但被 4 个模块消费（M07-05、M14-06、M04、M05-07）。放在任何病历子模块里都会让「知识更新」这件事必须走病历模块的发版流程。

## 3. 两条闭环（病历内容闭环 + 临床知识闭环）

### 3.1 病历内容闭环

```
   医生接诊（M07-01）
        │
        ▼
   选模板（M18-01）──▶ 写病历正文（M18-02/03/04）
        │                      │
        │                      ▼
        │            content_hash 固化，status: DRAFT → FINALIZED
        │                      │ emr.record.finalized
        │                      ▼
        │            M07-06 渲染文书 → 医生签名 → status: FINALIZED → SIGNED
        │                      │
        │                      ▼
        │            M18-05 质控批跑 ──缺陷──▶ M05-05 缺陷整改
        │                      │
        │                      ▼
        │            M05-05/M06-06 发起归档 → POST /internal/v1/emr/archive/push
        │                      │
        │                      ▼
        │            M18-06 归档校验 → 入库 → m18.archive.confirmed
        │                      │
        │                      ▼
        │            医务科封存（m18.record.locked）→ 只读
        │                      │
        │                      ▼
        │            M18-07 检索 / 统计 / 病案调阅
        │
        └──▶ 需要更正时：作废重开（VOIDED）或追加更正（m18_emr_amendment）
```

**闭环的三个断点（M18 必须处理的失败场景）：**

| 断点 | 场景 | M18 的行为 |
|---|---|---|
| **F-01 定稿后没有文书** | `emr.record.finalized` 发出，但 M07-06 挂了没收到 | M18 在 `m18_emr_document` 里保持 `document_status = 'PENDING'`，APScheduler 每 10 分钟扫一次超过 30 分钟仍未生成的，重发事件（最多 3 次），第 3 次后告警医务科 |
| **F-02 质控未完成就归档** | 月度归档高峰，质控积压 | 允许归档，但 `m18_arc_batch.qc_completed = FALSE`，归档批次状态置 `CONFIRMED_WITH_QC_PENDING`，并在病案统计里单列 |
| **F-03 归档被拒后无下文** | 归档校验失败，M06-06 收到 `m18.archive.rejected` 但没人处理 | M18-06 每批次产出一条「待整改归档」记录，超 7 天未处理在病案质量指标里计数 |

### 3.2 临床知识闭环

```
   M01 主数据（药品 / 诊断 / 手术 / 抗菌分级）
        │  mdm.drug.created / mdm.diagnosis.changed / mdm.rule.reload
        ▼
   M18-08 知识库规则（草稿 → 审核 → 发布 → 新版本取代旧版本）
        │  临床药师在本院眼科重点配置上补充规则：
        │    · 散瞳药与闭角型青光眼禁忌
        │    · 抗 VEGF 与抗凝药
        │    · 糖皮质激素滴眼液长期使用与高眼压
        │    · OK 镜护理液与角膜损伤
        ▼
   m18.kb.rule_published（带 rule_version）
        │
        ├──▶ M07-05 开处方时 POST /internal/v1/kb/medication-check → WARN / BLOCK / DEGRADED
        ├──▶ M14-06 审方时同一接口 → 与 M07-05 结果必须一致
        └──▶ M18-05 处方点评（事后抽样）
```

**知识闭环的判据：同一个医生、同一张处方，在开方时（M07-05）与审方时（M14-06）调用 M18-08 得到的结果必须完全一致。**
不一致的唯一合法原因是**两次调用之间规则发布了新版本**——因此 `medication-check` 的响应必须带 `rule_version_set`，并允许调用方传 `rule_version_set` 固定版本（审方复核场景）。**没有这个字段，就无法回答「为什么审方说不能开、开方时没说」这种最常被投诉的问题。**

### 3.3 两条闭环的交点：质控的「用药维度」

病历内容闭环的 M18-05 与知识闭环的 M18-08 在**处方点评**上相交：
- M18-08 提供规则（「左氧氟沙星 + 复方托吡卡胺存在相互作用」）。
- M18-05 提供「事后抽样 + 缺陷归因」（「这张处方在开方时应该被提示但医生强行通过」）。
- 交点数据：`m18_qc_medication_review` 记录「开方时的审核结果」与「事后点评结果」，**两者不一致的处方就是知识库需要补规则的地方**。

## 4. 全局状态机

### 4.1 病历正文状态机（`m18_emr_record.status`）

```
                  ┌─────────┐
                  │  DRAFT  │◀──────────── 新建 / 作废重开
                  └────┬────┘
                       │ 定稿（写 content_hash）
                       ▼
                  ┌───────────┐
                  │ FINALIZED │──作废──┐
                  └─────┬─────┘        │
                        │ 签署（M07-06 回调）│
                        ▼              │
                  ┌──────────┐         │
                  │  SIGNED  │──作废───┤
                  └────┬─────┘         │
                       │ 归档           │
                       ▼              ▼
                  （归档为独立维度）  ┌──────────┐
                                     │  VOIDED  │（终态）
                                     └──────────┘
```

| 状态 | 含义 | 允许的后续状态 | 正文可改 |
|---|---|---|---|
| `DRAFT` | 草稿 | `FINALIZED` | ✅ 可改 |
| `FINALIZED` | 已定稿（`content_hash` 已固化） | `SIGNED` / `VOIDED` | ❌ 不可改 |
| `SIGNED` | 已签署（法律效力生效） | `VOIDED` | ❌ 不可改 |
| `VOIDED` | 已作废（终态，记录永久留存） | 无 | ❌ 不可改 |

**流转规则：**

| 流转 | 触发 | 前置条件 | 副作用 |
|---|---|---|---|
| `DRAFT → FINALIZED` | 医生点「定稿」 | 模板必填项全部填写；`content_hash` 已计算 | 固化 `content_hash` + `finalized_at`；发 `emr.record.finalized` |
| `FINALIZED → SIGNED` | M07-06 签署回调 | 存在已签署的 `m07_document` | 记 `signed_at`；此后 `REVOKE UPDATE` 生效 |
| `FINALIZED/SIGNED → VOIDED` | 医生/医务科点「作废」 | 归档前；或归档后需医务科审批 | 记 `void_reason` + `voided_by`；发 `emr.record.voided`；**原记录永久留存** |
| `VOIDED → DRAFT` | ❌ 禁止 | — | **作废后重新书写是新建一条记录，不是把原记录改回 DRAFT** |

> ⚠️ **归档与封存不是 `record.status` 的一部分。** 归档是批次维度的状态（`m18_arc_batch.status`），封存是独立表（`m18_emr_seal.status`）。把归档塞进 `record.status` 会导致「同一份病历被多个批次归档」时状态互相覆盖。**判据：一份病历可以在 `SIGNED` 状态下被归档、被封存，`record.status` 保持 `SIGNED` 不变。**

### 4.2 质控任务状态机（`m18_qc_task.status`）

```
   PENDING ──▶ RUNNING ──┬──▶ PASSED ──▶ CLOSED
                         ├──▶ DEFECT_FOUND ──▶ RECTIFIED ──▶ CLOSED
                         └──▶ PENDING（超时重试，最多 3 次）
```

| 状态 | 含义 | 可进入的后续状态 |
|---|---|---|
| `PENDING` | 待跑 | `RUNNING` |
| `RUNNING` | 运行中 | `PASSED` / `DEFECT_FOUND` / `PENDING`（超时重试） |
| `PASSED` | 质控通过 | `CLOSED` |
| `DEFECT_FOUND` | 发现缺陷 | `RECTIFIED` / `CLOSED`（缺陷被判定为误报时直接关闭） |
| `RECTIFIED` | 已整改 | `CLOSED` |
| `CLOSED` | 已关闭（终态） | 无 |

### 4.3 归档批次状态机（`m18_arc_batch.status`）

```
   RECEIVING ──▶ CHECKING ──┬──▶ CONFIRMED ──▶ RELEASED（撤销归档）
                            └──▶ REJECTED
```

| 状态 | 含义 | 说明 |
|---|---|---|
| `RECEIVING` | 接收中 | 已收到 `archive/push`，正在落明细 |
| `CHECKING` | 校验中 | 完整性检查（文书齐全性、`content_hash` 一致性） |
| `CONFIRMED` | 已确认 | 发 `m18.archive.confirmed` |
| `REJECTED` | 已拒绝 | 发 `m18.archive.rejected`，附具体缺失项 |
| `RELEASED` | 已撤销 | 发 `m18.archive.released`；撤销后批次不可再确认，需重新推送 |

> **`RELEASED` 是终态而不是回到 `RECEIVING`**：撤销归档是一个「撤回声明」，撤销后再归档必须是一个新批次。理由：撤销归档通常发生在「归档错了」（归到了错的就诊、错的日期），如果允许在原批次上重来，新批次的 `batch_no` 还是旧的，M05 那边 `m18_archive_id` 没变而归档内容变了，账实不符。

### 4.4 封存状态机（`m18_emr_seal.status`）

```
   ACTIVE ──▶ RELEASED（解封，需医务科审批）
     │
     └──▶ SUPERSEDED（被新的更大范围封存覆盖）
```

- `ACTIVE`：封存生效，任何写操作（含归档、更正、重新签署）一律拒绝。
- `RELEASED`：解封，需医务科 + 院长双审批，全程留痕。
- `SUPERSEDED`：一个「按患者」的封存覆盖了一个「按就诊」的封存时，旧的置 `SUPERSEDED`（不是 `RELEASED`，因为它从未被解封）。

### 4.5 临床路径入径状态机（`m18_kb_path_entry.status`）

```
   ENTERED ──▶ IN_PROGRESS ──┬──▶ COMPLETED
                             ├──▶ DEVIATED ──▶ IN_PROGRESS / COMPLETED
                             └──▶ EXITED
```

### 5.4 M18 的三道不可关闭的闸门

M18 与 M19 一样，有三条**不允许存在「关掉」形态**的硬约束。它们不是「默认开启的开关」，而是「数据库层面无法表达的关闭状态」。

| 闸门 | 落地点 | 为什么不可关闭 |
|---|---|---|
| **G-1 签署后禁改** | `m18_emr_record` 触发器 `trg_m18_emr_record_signed_guard()` + `REVOKE UPDATE ON m18_emr_record` | 病历是法律证据。《医疗纠纷预防和处理条例》要求真实、完整、可追溯。**如果存在「解除锁定」的形态，医务科在压力下迟早会点它**，而那一刻造成的损失不可挽回 |
| **G-2 病历不可删除** | `m18_emr_record` / `m18_emr_amendment` / `m18_emr_seal` 三表无 `is_deleted` 列 + `REVOKE DELETE` | 门诊 15 年、住院 30 年、屈光永久是**法定义务**。物理删除一条病历不只是数据丢失，而是**医院违法** |
| **G-3 封存后全部只读** | `m18_emr_seal` 生效检查前置到**所有**写接口 + 归档/更正/重签三条路径 | 封存意味着「这份病历已作为证据提交，任何人不得改动」。M09 `:873` 订阅 `m18.record.locked` 就是为了在封存后停止回写 |

> **闸门的失败方向必须朝「更严格」。** 封存状态查不到（DB 抖动）时应当**拒绝写入**而不是放行——写一次不该写的代价（病历被篡改，诉讼中医院全责）远高于多等 3 秒。

## 6. 核心计算模型

> 每个模型都写清公式、单位、边界、舍入、失败条件和算例。子模块详细设计里要引用本节的编号。

### 6.1 病历完整性检查（`M18-CALC-01`）

**公式：**

```
integrity_result =
    COMPLETE    若 required_docs ⊆ present_docs 且 content_hash 全部一致
    INCOMPLETE  若 required_docs ⊄ present_docs 或 存在 hash 不一致
    UNKNOWN     若任一上游（M07-06 / M18 自身表）不可用
```

- `required_docs`：由 `record_type` 决定，见下表。
- `present_docs`：M18 侧 `m18_emr_document` 中该就诊的文书集合 + M07-06 `GET /internal/v1/m07/documents/by-source` 的文书集合。

| `record_type` | `required_docs` |
|---|---|
| `OUTPATIENT` | `MEDICAL_RECORD` |
| `INPATIENT` | `MEDICAL_RECORD`、`DISCHARGE_SUMMARY`（出院时） |
| `DAY_SURGERY` | `MEDICAL_RECORD`、`SURGERY_CONSENT`、`ANESTHESIA_CONSENT`、`DISCHARGE_SUMMARY` |
| `EMERGENCY` | `MEDICAL_RECORD` |

**边界：** 门诊病历在就诊未结束时 `required_docs` 为空集 → 恒为 `COMPLETE`（不能因为「还没写」就判不完整）。

**失败条件：** 上游超时 500ms → 判 `UNKNOWN`，**绝不默认 `COMPLETE`**。

**算例：** 一份日间手术就诊（encounter_id=81002）的 `required_docs` 是 4 项，`present_docs` 有 `MEDICAL_RECORD`、`SURGERY_CONSENT`、`DISCHARGE_SUMMARY` 3 项，缺 `ANESTHESIA_CONSENT` → `integrity_result = INCOMPLETE`，缺失项 `['ANESTHESIA_CONSENT']`，归档批次置 `REJECTED`。

### 6.2 质控评分与等级（`M18-CALC-02`）

**公式：**

```
base_score = 100
deduction  = Σ(每个缺陷的扣分)
             CRITICAL → 直接判 GRADE_C（不参与累加，一票否决）
             MAJOR    → 每处扣 5 分
             MINOR    → 每处扣 2 分
             HINT     → 每处扣 0.5 分
qc_score = max(0, base_score - deduction)
```

| 等级 | 条件 |
|---|---|
| `GRADE_A`（甲级） | `qc_score >= 90` 且 无 `CRITICAL` 缺陷 |
| `GRADE_B`（乙级） | `75 <= qc_score < 90` 且 无 `CRITICAL` 缺陷 |
| `GRADE_C`（丙级） | `qc_score < 75` 或 存在任一 `CRITICAL` 缺陷 |

**边界：**
- `deduction` 会累加到超过 100 → `qc_score` 下限 0，**不出现负数**。
- 甲级病历率是医院等级评审指标，**分母是当月已归档病历数，不是已质控病历数**（质控未完成的病历按乙级以下暂计，避免「少质控反而甲级率高」）。

**舍入：** `qc_score` 保留 1 位小数（`NUMERIC(5,1)`）。

**算例：** 某住院病历有 1 处 `MAJOR`（术后首次病程 25 小时才写，超过 24 小时时限）+ 3 处 `MINOR`（主诉缺时长、诊断缺侧别、处理意见缺剂量）= 扣 `5 + 2×3 = 11` 分 → `qc_score = 89.0` → `GRADE_B`。
若其中「诊断缺侧别」被人工改判为 `MAJOR`（眼科左右眼混淆属重大缺陷），则扣 `5 + 5 + 2 + 2 = 14` → `qc_score = 86.0` → 仍为 `GRADE_B`。
若存在 1 处 `CRITICAL`（手术记录未签名）→ **直接 `GRADE_C`**，无论分数多少。

### 6.3 病历及时率（`M18-CALC-03`）

**公式：**

```
timely_rate = 及时完成病历份数 / 应完成病历份数 × 100%
```

| 病历类型 | 「及时」的定义 | 依据 |
|---|---|---|
| 门诊病历 | 就诊当日完成（`record.created_at::date = encounter_date`） | 《病历书写基本规范》 |
| 入院记录 | 患者入院后 24 小时内 | 同上 |
| 首次病程记录 | 患者入院后 8 小时内 | 同上 |
| 日常病程记录 | 按医嘱频次，最长不超过 3 天（病危 1 天） | 同上 |
| 手术记录 | 术后 24 小时内 | 同上 |
| 术后首次病程 | 术后 24 小时内 | 同上 |
| 出院小结 | 出院当日 | 同上 |

**边界：**
- `应完成病历份数` 的分母**只算进入过书写窗口的**，不算「还没到期的」。**这一点与 M19 的完成率口径同源**：一次屈光手术生成 6 次随访但只有 1~2 次在当月窗口内，若用工单生成数当分母，屈光中心会永远低于 30%。**病历同理**：一份住院病历在患者出院前不该计入「应完成」，否则住院第 3 天统计时甲的及时率是 0%。
- 分母为 0 时 `timely_rate = NULL`，不返回 0。

**算例：** 2026-10 某科室门诊就診 1,200 人次，其中门诊病历当日完成 1,104 份 → `timely_rate = 1104/1200 = 92.00%`。
若改用「全部创建病历份数」当分母（含 60 份跨日补写的）→ `1104/1260 = 87.62%`，**差 4.38 个百分点**，且这个差额会随补写习惯波动，无法作为稳定的评审依据。

### 6.4 路径入径率与变异率（`M18-CALC-04`）

**公式：**

```
入径率   = 入径患者数 / 适用患者数 × 100%
变异率   = 发生变异的入径患者数 / 入径患者数 × 100%
完成率   = 完成的路径数 / 入径的路径数 × 100%
```

**边界：**
- `适用患者数` 由「路径定义的适用诊断 + 年龄 + 术式」筛选得出，**不是科室就诊总数**。
- 一个患者在同一就诊中可入多个路径（如「白内障 + 糖尿病」），入径率**按路径实例计数**而非按患者计数，但报表同时给患者口径。

**算例：** 2026-10 屈光中心白内障手术 240 台，其中符合临床路径适用条件（单眼白内障、年龄 ≤ 85、无合并症）的有 200 台，实际入径 168 台 → 入径率 `84.00%`（168/200），**不是 70.00%**（168/240）。剩余 40 台因合并症不入径，属正当排除。
入径的 168 台中发生变异 22 台（13.10%），完成 160 台（95.24%）。

### 6.5 用药审核的规则匹配度（`M18-CALC-05`）

**公式：**

```
matched_rule_count = Σ 命中的规则数（按 rule_code 去重）
alert_count        = 命中并按 alert_level 展开的提示条数
block_flag         = 存在任一 alert_level = 'BLOCK' 的提示
degraded           = 规则库加载失败 / 规则版本为空 / 超时
```

**边界：**
- **一条规则命中多个药品时只产生一条提示**（`rule_code + drug_code` 为提示的唯一键），否则「左氧 + 妥布霉素 + 加替沙星 三种喹诺酮类同时开」会产生 3 条相同的「重复用药」提示，医生会直接把这些提示一并跳过。
- `BLOCK` 只在**国家明令禁止**的场景下置位（如明确禁忌），其他一律 `SEVERE` 及以上但不拦截。

**算例：** 一张处方含 3 个药：左氧氟沙星滴眼液、复方托吡卡胺滴眼液、地塞米松滴眼液。
规则命中：「喹诺酮类 + 散瞳药」无规则；「糖皮质激素 + 长期使用」命中 1 条 `WARN`；「散瞳药 + 前房浅」命中 1 条 `SEVERE`。
→ `matched_rule_count = 2`，`alert_count = 2`，`block_flag = false`，`check_result = WARN`（按最高级别 `SEVERE` 映射到 `WARN` 综合结果，因为 `SEVERE` 不是 `BLOCK`）。

### 6.6 归档完整率（`M18-CALC-06`）

**公式：**

```
归档完整率 = 完整性判定为 COMPLETE 的批次数 / 已判定（COMPLETE + INCOMPLETE）的批次数 × 100%
```

**边界：** `UNKNOWN` 的批次**既不在分子也不在分母**，单列「待复核批次」。理由是把它算进分母会把完整率系统性压低（上游抖动天数不可控），算进分子则违反事实。

**算例：** 2026-10 归档 1,240 批次，其中 `COMPLETE` 1,208、`INCOMPLETE` 26、`UNKNOWN` 6 → `归档完整率 = 1208/1234 = 97.89%`（分母 1,234 不含 UNKNOWN）。若把 UNKNOWN 算进分母 → `1208/1240 = 97.42%`，且这个数字每天会随 M07-06 的可用性波动。

### 7.2 病历全文检索的实现选择

**选择：PostgreSQL `tsvector` + GIN 索引，不引入 Elasticsearch。**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **PostgreSQL `tsvector` + GIN** | 与业务库同事务，**归档后立即可检索，无同步延迟**；`to_tsvector('simple', ...)` 对中文可用（配合 `zhparser` 或二元切分）；运维零新增组件 | 检索能力弱于 ES（无同义词、无相关性排序调优） | ✅ **采用** |
| Elasticsearch | 检索能力强 | 需要额外同步链路；**同步延迟会导致「刚归档的病历查不到」**，而病案室最常做的事就是「马上查刚归档的那份」 | ❌ 不采用 |
| `LIKE '%关键词%'` | 无 | 全表扫描，病历 30 年存量上千万行，不可用 | ❌ 不采用 |

**中文分词处理：** 采用 PostgreSQL 的 `simple` 配置 + 二元切分函数 `fn_m18_bigram(text)`，把「双眼老年性白内障」切成「双眼 / 眼老 / 老年 / …」。理由：眼科术语（「老年性白内障」「黄斑水肿」）专有名词多，通用词典切分效果差，二元切分对短词检索召回率更高。

**索引维护：** `m18_idx_search_doc` 表的 `search_vec tsvector` 列由 AFTER INSERT/UPDATE 触发器自动维护。M18-07 负责索引重建任务（`Celery`，全量重建约 8 分钟 / 百万行）。

### 7.3 知识库的规则加载与热重载

**这是 M18 性能最敏感的一条链路（P-08 要求 P95 ≤ 300ms）。**

```
启动：M18-08 从 m18_kb_* 表加载全部 PUBLISHED 规则 → 内存规则集（RuleSet）
      → 记 rule_version_set = '20261021'（当日发布日期集合的哈希）
运行：medication-check 全程在内存做匹配，不查库
变更：M01 mdm.rule.reload 事件 / M18 KB 发布 → POST /internal/v1/m18/kb/rule-reload
      → 重建 RuleSet（双缓冲：新集就绪后原子切换指针）
      → rule_version_set 更新
```

| 指标 | 目标 |
|---|---|
| `RuleSet` 加载耗时（全量约 8,000 条规则） | ≤ 800ms |
| 单次 `medication-check` 内存匹配耗时（5 个药） | ≤ 15ms |
| 热重载期间的服务可用性 | 不中断（双缓冲） |
| `RuleSet` 内存占用 | ≈ 40MB |

**为什么不用 Redis 存规则集：** 规则匹配要做 `patient` 维度的条件求值（年龄、性别、孕产、肾功能，以及**眼科专科条件**如「前房深度」「眼压」），这是计算不是查表，放 Redis 反而增加一次反序列化 + 网络往返，300ms 的预算里经不起。

### 7.4 归档推送的幂等与重试

M06-06 与 M05-05 都会调 `P-04 POST /internal/v1/emr/archive/push`，且都配置了最多 5 次重试（`M06.ARCHIVE.EMR_MAX_RETRY = 5`）。

| 环节 | 机制 |
|---|---|
| 幂等键 | `uk_m18_arc_batch_source UNIQUE (source_module, source_biz_no)` |
| 重复推送 | 返回**首次结果原样**（同一 `batch_no`、同一 `archive_id`、同一 `integrity_result`），响应里带 `idempotent_replay = true` |
| 处理方式 | 接口**同步接收 + 异步处理**：接收后立刻返回 `batch_no` 与 `status = 'RECEIVING'`，明细落库与完整性校验走 Celery |
| 超时 | 接口本身 P95 ≤ 5000ms（只做入库 + 触发任务，不做校验） |
| 失败 | 处理失败的批次置 `REJECTED` 并发 `m18.archive.rejected`；**不静默失败** |

> **为什么把校验放异步而不是同步？** M05-05 的 PF-08 要求「提交病案室 P95 ≤ 1200ms」，其中含 M18 的调用。若 M18 同步做完整性校验（要查 M07-06、要算 hash、要检查 4 类必检文书），一次日间手术归档要 800ms~1.5s，M05 必然超时。**同步只负责「收下并保证不丢」，异步负责「校验并报结果」。**

### 7.5 数据规模与容量

| 数据 | 估算基数 | 年增量 | 3 年累计 |
|---|---|---|---|
| 门诊病历 | 门诊量约 1,200 人次/日 × 300 天 | ≈ 36.0 万份/年 | 108 万份 |
| 住院病历 | 住院约 60 人次/日 × 300 天 | ≈ 1.8 万份/年 | 5.4 万份 |
| 手术病历 | 手术约 40 台/日 × 300 天 | ≈ 1.2 万份/年 | 3.6 万份 |
| 病历段落（`m18_emr_record_field`） | 每份病历平均 12 个段落 | ≈ 470 万行/年 | 1,410 万行 |
| 病程记录 | 每份住院病历平均 12 条 | ≈ 21.6 万条/年 | 64.8 万条 |
| 质控任务 | 每份归档病历 1 条 | ≈ 39 万条/年 | 117 万条 |
| 用药审核记录 | 每张处方 1 条，日均 1,500 张 | ≈ 45 万条/年 | 135 万条 |
| 检索索引文档 | 每份病历 1 行 | ≈ 39 万行/年 | 117 万行 |

**存储估算（含索引与全文）**：病历正文平均 4KB/份 → 年增约 1.6GB；三年病历正文约 5GB；全库（含所有子表、索引、`tsvector`）三年约 **60~80GB**。**这是一个可以单机承载的规模，不支持按 M19 那样的分区是合理的**——但日志类表与质控/审核记录必须月分区。

### 8.1 性能

| 场景 | 指标 | 依据 |
|---|---|---|
| `P-01` 按就诊取病历正文 | **P95 ≤ 100ms** | M07-06：169、`:3303` |
| `P-08` 合理用药审核 | **P95 ≤ 300ms** | M07-05 `:3993` |
| `P-04` 归档推送（同步接受） | **P95 ≤ 5000ms** | M06-06 U-13 |
| `P-05/P-06/P-07` 同意书查询 | P95 ≤ 2000ms | M06-04 U-06 |
| `P-09` DRG 权重 | P95 ≤ 500ms | M05-07 U-10 |
| 门诊病历保存（草稿） | P95 ≤ 200ms | 医生打字体验到感知阈值 |
| 门诊病历定稿 | P95 ≤ 800ms | 含 `content_hash` 计算 |
| 病历全文检索 | P95 ≤ 1500ms | 千万级行 + GIN |
| 质控批跑吞吐 | ≥ 200 份/分钟 | 月归档高峰 1,240 批 |
| 归档完整性校验 | ≥ 50 批/分钟 | 同上 |

### 8.2 可用性与降级

| 依赖 | 不可用时的行为 |
|---|---|
| M07-06（签署状态） | P-05 返回 `consent_sign_status = 'UNKNOWN'`，**不报错**；降级说明写明「需人工核对纸质件」 |
| M07-02（诊断） | 病历可写，诊断段落留空并标记「待同步」；定稿时警告 |
| M03（患者信息） | 病历可写，患者基本信息显示「加载中」；不允许定稿（患者身份不确认的病历无法律效力） |
| M01（主数据） | 知识库用上次加载的 `RuleSet`（**不降级**）；药品/诊断搜索不可用提示 |
| M18 自身 DB | 整体不可用 → 上游全部降级（M07-06 用简化模板、M14-06 仅本地校验） |
| Redis | 编辑锁降级为数据库行锁（`SELECT ... FOR UPDATE`），模板缓存直读 DB |

### 8.3 安全

| 要求 | 措施 |
|---|---|
| 病历是最高等级隐私 | 所有病历正文读写走 M02 数据权限（院区 / 科室 / 本人），**越权读取必须审计** |
| 事件载荷 | 不含病历正文（§5.3） |
| 导出 | 所有导出加水印（用户名 + 时间 + trace_id），并审计 |
| 打印 | 打印次数超限需审批（与 M07-06 的 `m07_reprint_auth` 对齐，但审批记录归 M07-06） |
| 封存 | 封存后所有写接口拒绝；解封需双审批 |
| 知识库 | 规则发布需审核（`IN_REVIEW → PUBLISHED`），发布后旧版本 `SUPERSEDED` 但对已有病历的判定结果不追溯重算 |

### 8.4 一致性

| 场景 | 一致性要求 |
|---|---|
| 病历正文 vs `content_hash` | **强一致**（同一事务内计算并写入） |
| 病历状态 vs M07-06 签署状态 | **最终一致**（M07-06 回调驱动；M18 侧若 15 分钟未收到回调，APScheduler 主动查 U-04 对账） |
| 归档批次 vs M05/M06 本地状态 | **最终一致**（事件驱动；M18 侧提供 `P-10` 供对账） |
| 知识库规则 vs 各消费方 | **最终一致**（`m18.kb.rule_published` 广播，各消费方下次调用即生效） |
| 过敏史明细 vs `mpi_patient.allergy_history` | **最终一致**（`m18.allergy.updated` 事件）；**M18 是明细权威，M03 是冗余副本** |
