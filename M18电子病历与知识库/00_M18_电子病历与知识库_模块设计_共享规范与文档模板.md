### 0.3 四条铁律（违反即返工）

| # | 铁律 | 原因 |
|---|---|---|
| **1** | **数量口径三处一致**：页面总览树 `P0x` = 第 5 章 `### 5.x P0x` 标题；表清单 = `### 4.x 表：` 标题；接口总览 `API-01` 起连续无断号且每项有 `#### API-xx` 详述 | 全仓统一标准，交叉引用依赖编号稳定 |
| **2** | **M18 只做「内容」与「知识」，不做「操作」**：M07 医生工作站负责接诊、诊断、开医嘱、开检查、签名、打印（**操作中枢**）；M18 只负责病历**正文的书写、模板、结构化、质控、归档、封存**，以及**临床知识库**（合理用药、临床路径、专科知识、DRG 权重）。**绝不在 M18 里再建 `m18_order` / `m18_diagnosis` / `m18_prescription` / `m18_document_signature`** | M07 已建 40+ 张表并已上线；M18 再建一套会导致同一张处方有两个状态、同一条诊断有两个编码来源。**这是本模块最严重的架构错误** |
| **3** | **技术栈 PostgreSQL 16**：不得出现 MySQL / Oracle 专有语法（自增关键字、定长整型、旧式日期时间类型、存储引擎子句、Oracle 字符串类型均禁用，详见 §15 自检项与 §17 第 14 条） | 全仓已统一 PostgreSQL，MySQL 语法是硬错误 |
| **4** | **病历一经签署不可原地修改**：`m18_emr_record` 的 `status = 'SIGNED'` 之后，**禁止 UPDATE 正文内容字段**（`chief_complaint` / `present_illness` / `past_history` / `physical_exam` / `diagnosis_text` / `treatment_plan` 等）。更正只能走两条路：① **作废重开**（`SIGNED → VOIDED`，原记录永久留存，新建一条 `DRAFT`）② **追加更正记录**（`m18_emr_amendment` 只增不删）。数据库层用触发器 + `REVOKE UPDATE` 双保险 | 病历是**法律证据**。《医疗纠纷预防和处理条例》要求病历真实、完整、可追溯。一份能原地改的病历在诉讼中不具备证明力，且无法回答「这条记录是被谁在什么时候改的」。医院因篡改病历被判全责的案例每年都有 |

> **M18 专属铁律（第 5 条）：同一份病历只有一个 `content_hash`，只有一处权威。**
> M18 生成的病历正文其哈希（`content_hash`，SHA-256）在 M18 侧计算并固化；M07-06 若需要渲染成 PDF 存 `content_snapshot`，**必须原样引用 M18 的 `content_hash`，不得自行重新序列化后另算一个哈希**。两份哈希不一致的后果是：打官司时对方律师问「这两份文件哪份是患者签的」，医院无法举证。

> **M18 专属铁律（第 6 条）：同意书的模板在 M18，签署在 M07-06/M20，状态以签署侧为权威。**
> M18 拥有同意书**模板**（`m18_tpl_consent_template`）与**模板内容**、生成同意书**正文**；但「这份同意书签没签、谁签的、什么时候签的」的唯一权威在 **M07-06 `m07_document`**（`doc_type` ∈ `SURGERY_CONSENT` / `ANESTHESIA_CONSENT` / `SPECIAL_CONSENT`，状态 `GENERATED → SIGNED → PRINTED/CANCELLED`）。M18 **不建同意书签署状态表**，对外提供的 `GET /internal/v1/emr/consent/{apply_id}/status` 是**聚合视图**，内部实时查 M07-06 再组装。

## 1. M18 模块定位与子模块划分

### 1.1 一句话定位

**M18 电子病历与知识库是全院「临床内容」与「医学知识」的唯一权威**：一手抓**病历内容**（门诊/住院/日间病历的正文书写、结构化字段、模板、质控、归档、封存、更正），一手抓**临床知识**（合理用药规则、临床路径、眼科专科知识、DRG 权重、分诊规则），并为 M07 医生工作站、M05 住院、M06 日间手术、M09 手术麻醉、M14 药房、M04 门诊提供内容与知识服务。

### 1.2 与 M07-06 的边界（最容易做错的地方，必读）

M07-06 文书签署与打印的原文写得非常清楚（`M07医生工作站/M07_医生工作站_06_文书签署与打印_详细设计.md:76`）：

> | **病历正文** | **M18** | **本模块负责签名与打印，不含书写** |

同文件 `:78`：「本模块**不写内容**，只负责**渲染、签名、打印、留痕**」。

| 维度 | M07-06 文书签署与打印 | **M18 电子病历** |
|---|---|---|
| **谁写病历正文** | ❌ 不做（原文「不含书写」） | ✅ **M18-02 门诊/住院病历书写**：主诉、现病史、既往史、体格检查、专科检查、诊断文本、处理意见 |
| **谁定义病历模板** | ❌ 不做 | ✅ **M18-01 病历模板**：门诊病历模板、住院病历模板、专科模板（屈光/白内障/视光/青光眼） |
| **谁把正文渲染成 PDF** | ✅ **M07-06**：`content_snapshot` + `content_hash` + 签名 + 打印 + 留痕 | ❌ 不做渲染、不做签署、不做打印 |
| **谁持有签署状态** | ✅ **M07-06 `m07_document.status`**：`GENERATED → SIGNED → PRINTED/CANCELLED` | ❌ **不建签署状态表** |
| **谁算 `content_hash`** | ⚠️ 存了 `content_hash`，但**必须引用 M18 的值** | ✅ **M18 计算并固化**（铁律 5） |
| **谁定义同意书模板** | ❌ 不做（M07-06 `:130` 只写「同意书管理 / 模板 / 患者签字位」为**界面能力**） | ✅ **M18-01** `m18_tpl_consent_template`（M01-07 手术模块原文：「手术同意书模板 → M18 引用模板 ID」） |
| **谁做病历质控** | ❌ 不做（M08-05 `:227` 原文：「电子病历质控 / M18（未设计）」） | ✅ **M18-05 病历质控** |
| **谁做归档与封存** | ❌ 不做（M07-06 `:144` 范围外「病历归档」） | ✅ **M18-06 病历归档与封存** |
| **谁做病历更正** | ❌ 不做（M06-06 `:636` 原文：「修改诊断 ❌ 需走病历更正流程（M18）」） | ✅ **M18-06** |

**一句话：M18 回答「这份病历上写了什么、依据哪条知识判断的」；M07-06 回答「这份病历被谁签了、打印过几次、PDF 能不能给患者」。**

> ⚠️ **典型错误（务必避免）：** M18 把病历正文写进自己的表后，又让 M07-06 从 M18 拉一份正文自己再存一份 `content_snapshot`，两者**各自算一个 `content_hash`**。
> **后果：** 同一份门诊病历出现两个哈希值，打官司时无法举证哪份是患者签的（铁律 5）。
> **正确做法：** M18 的 `content_hash` 一经生成即固化；M07-06 渲染 PDF 时**原样写入**这个值，不重算。M18 侧在 `GET /internal/v1/emr/record/by-encounter/{id}` 响应里**必须返回 `content_hash`**，M07-06 直接采用。

> ⚠️ **第二个典型错误：** 在 M18 里建 `m18_consent_sign` / `m18_document_signature`。
> **正确做法：** 签署状态查 M07-06。M18 的 `GET /internal/v1/emr/consent/{apply_id}/status` 是**聚合接口**（内部调 M07-06 `GET /internal/v1/m07/documents/by-source`），返回「签署状态 + 见纸质件标记」。

### 1.4 一条不可逾越的红线

```
❌ 禁止：CREATE TABLE m18_order / m18_order_item            -- 医嘱归 M07-03
❌ 禁止：CREATE TABLE m18_diagnosis                         -- 诊断归 M07-02
❌ 禁止：CREATE TABLE m18_prescription                       -- 处方归 M07-05
❌ 禁止：CREATE TABLE m18_document / m18_document_signature   -- 文书签署归 M07-06
❌ 禁止：CREATE TABLE m18_home_page                          -- 病案首页归 M05-06
❌ 禁止：CREATE TABLE m18_surgery_record                     -- 手术记录归 M09
❌ 禁止：CREATE TABLE m18_nursing_record                     -- 护理记录归 M08
❌ 禁止：CREATE TABLE m18_drug / m18_drug_interaction_master -- 药品主数据归 M01-03
❌ 禁止：UPDATE m18_emr_record SET chief_complaint = ... WHERE status = 'SIGNED'  -- 铁律 4
❌ 禁止：DELETE FROM m18_emr_record                          -- 病历不可物理删除
```

### 8.2 内部接口降级语义：「降级返回」只有三种合法形态
> 本节由 V1.1 新增，**15 个内部契约（P-01~P-15）全部适用**，每个子模块在 §10.2 与 §11.2 都必须按本节写。

M18 的内部接口被 M05/M06/M07/M09 在**业务主链路**上同步调用。这些调用方对失败的处理方式是各自写死的（例如 M06-04 的降级是「项标 `NOT_EVALUATED` + 见纸质件勾选」、M05-07 是「CMI 置空并提示」、M07-06 是「用会话数据生成简化版文书并标记」）。**所以 M18 的返回形态决定了调用方会走进哪条降级分支，这不是风格问题，是链路行为问题。**

**三种合法形态，除此之外没有第四种：**

| 形态 | HTTP | 响应体 | 调用方看到的效果 | 什么情况下用 |
|---|---|---|---|---|
| **正常** | 200 | `code: 0` + 完整 `data` | 正常处理 | 数据齐全、无降级 |
| **降级返回** | 200 | `code: 0` + `data` **带质量标记** + `degraded: true` | **知道「这次不完整」并自行决定** | 部分数据源不可用、数据过期、跨模块聚合缺一路 |
| **失败** | 4xx/5xx | 非 0 `code` + 错误码 | **走自己的降级分支**（多半是更宽松的逻辑） | M18 自身不可用、参数非法、无权限 |

**红线三条：**

1. **不允许「看起来正常但不完整」的 200。** 这是最危险的一种：调用方无法区分「真的没有这类数据」与「数据源挂了」。M18 所有内部接口的响应体**必须**带 `degraded: BOOLEAN`，降级时 `degraded: true`，并**必须**在 `degraded_sources`（数组，元素为 `{source, reason}`）里列出降级的数据源与原因。
2. **不允许把「没查到」伪装成「空数组且 `degraded: false`」。** 例：P-01 的 `degraded_sources` 里出现 `{"source": "M07_DIAGNOSIS", "reason": "TIMEOUT"}` 时，调用方必须能据此把病历标成「不完整」；若 M18 悄悄返回一个 `degraded: false` 的响应，M07-06 会照常生成正式文书，**文书上少了诊断段落而没人知道**。
3. **不允许用 200 + 空 `data` 表达「无权限」。** 无权限一律 403 + 非 0 错误码，否则调用方会把它当成「没有病历」，进而在术前核对里判成「不需同意书」——这是临床安全问题。

**统一的质量标记字段（所有 `data` 对象都要有，即使 `degraded: false` 也必填）：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `degraded` | BOOLEAN | 是 | 本次返回是否降级 |
| `degraded_sources` | ARRAY | 是 | 降级的数据源清单，元素含 `source` 与 `reason`；不降级时为 `[]` |
| `data_quality` | VARCHAR(16) | 是 | `REALTIME` 实时 / `CACHED` 缓存 / `PARTIAL` 部分数据 / `UNKNOWN` 无法判定 |
| `as_of` | TIMESTAMP | 是 | 本次数据的**口径截止时刻**（不是请求时刻）。调用方据此判断「这份数据有多旧」 |
| `record_count` | INTEGER | 否 | 集合类响应的返回条数。**返回 0 条而 `degraded: true` 与返回 0 条而 `degraded: false` 是两种完全不同的事实** |

**写入型接口的 `degraded` 语义（V1.3 新增，P-02 / P-03 / P-04 / P-11 / P-13 适用）：**

读接口的 `degraded` 含义直白——「我给你的数据不全」。**写接口不一样，必须额外钉死一格：**

| 情形 | HTTP | `code` | `degraded` | 调用方应当怎么做 |
|---|---|---|---|---|
| 写入成功，后续动作也全部成功 | 200 | 0 | `false` | 正常继续 |
| **正文/主数据已落库成功，但审计、事件、索引等后续动作失败** | 200 | 0 | **`true`** + `degraded_sources` | **不要重试写入**，应针对 `degraded_sources` 里的那一项追补（补发事件、补审计） |
| 写入本身失败（封存拦截、校验不过、幂等冲突、落库失败） | 4xx/5xx | 非 0 | **不适用** | 走自己的失败分支（补缺陷 / 重试） |

> **铁律：`degraded` 绝不能用来表达「写入失败」。** 两个方向的错都致命——
>
> - 若**写入失败用 `degraded: true` 表达**，调用方会把「没写进去」理解成「写进去了只是有点小问题」，于是**不补偿**，而云端也没有任何告警。这正是 `m18_written` 那类「两不管地带」的产生机制：每一方都以为对方在处理。
> - 若**写入成功后用 4xx/5xx 表达「审计失败」**，调用方会重试正文写入。有幂等键的保护虽然不会重复插入，但**会掩盖审计丢失这个事实**——重试成功一次之后，就再没有人知道中间丢过一条审计。
>
> **两种错误必须走两种通道：内容没落库走错误码，落库了但后续没做完走 `degraded`。** 实现上不允许出现 `degraded: true` 与 `data_quality: REALTIME` 同时存在这种自相矛盾的组合——只要有降级源，`data_quality` 至少降到 `PARTIAL`。

**`data_quality = UNKNOWN` 的强制约束**（对应常见坑第 28 条）：当 M18 无法判定数据完整性时（上游超时、聚合链路断了一路），**必须返回 `UNKNOWN`，绝不能默认成 `REAL`/`COMPLETE`**。理由：M05-05 与 M06-06 的归档完整性判定会读这个值，默认成「完整」等于把「不知道」记成「没问题」，而归档一旦确认就要保存 15~30 年，事后无法更正。

> **P-08 的降级语义同上但更严格（必须写进 M18-05 / M18-08 的 §11.2）**：规则加载失败或规则库为空时，返回 `code: 0` + `check_result: "DEGRADED"` + `degraded: true` + **空 `alerts`**，**绝不返回非 0 业务码**——M07-05 的降级原文是「仅做本地基础校验，记录告警」，若 M18 返回错误码，M07-05 会认为「审核服务挂了」而走更宽松的逻辑。**返回 `DEGRADED` 是让调用方明确知道「这次没审」而不是「这次审过了」。**

> 每个子模块建议使用 **35~45 个**错误码，从 `001` 连续编号，不留空号。

### 11.1 错误码定义表的唯一权威（强制）

**每个子模块的详细设计里，错误码只有一处可以「定义」它，其余所有位置只能「引用」它。**

**强制要求**：

1. **唯一权威位置**：详细设计 **6.6 节错误码定义表**。该表必须是 5 列：`错误码 / HTTP / 含义 / 触发场景 / 处置建议`。
2. **其余位置只能引用**：规则映射表、附录 C 总表、状态机表、API 详述里的「错误码」行、验收标准 AC/SC 引用——含义列必须与权威表逐字一致，或直接写 `—` 表示「此处不重复含义」。
3. **纯设计约束型规则挂 `—`**：像「不得跨模块直查」「病历签署后不可改」这类**架构约束**，不产生用户可见错误码，硬挂一个不相干的码是伪精确。**统一写 `—`**。
4. **权威口径取「代码 + 接口层实际用义」**：文档与代码冲突时，以运行时真正会吐出来的错误码为准。
5. **号段是真满的**：某号段用尽后必须**扩号段**，**不得复用一个「看起来相近」的既有码**。复用会导致同一码两种语义——这是最难查的一类缺陷。
6. **校验**：`validate_m18.py` 的 `check_errcode_semantics()` 会抽取权威定义表的 `(错误码 → 含义)`，扫描全文其余所有 `| 错误码 | 语义 |` 表格行做比对。
7. **号段一律用文字描述，不要写成引号数字**。例如写「本子模块占用 `1802001` 起的连号段，已使用 40 个」，**不要写** `"1802001" ~ "199999"`——`199999` 会被校验器当成一个真实错误码去比对语义，然后报「错误码格式异常」。
8. **固定 5 列的超集也算合格**：若权威表除 5 列外还带「错误码常量名」等列，只要 5 列齐全即可。

## 17. 常见坑

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 页面总览写了 P10，第 5 章只写到 P09 | 先列总览，再逐页写，最后用脚本核对 |
| 2 | 接口总览跳号（API-12 直接到 API-14） | 分组标题行不占编号，写完用脚本扫 |
| 3 | 第 4 章留了表定义 | 详细设计第 4 章只放指引块 |
| 4 | 表数与指引块写的 N 不一致 | 数据结构文件写完 → 回填 N |
| 5 | 错误码用 M19 号段 `"1901xxx"` | M18 一律 `"180Nxxx"` |
| 6 | **在 M18 里建 `m18_diagnosis` / `m18_order` / `m18_prescription`** | 一概读 M07 的内部接口，M18 只写病历正文 |
| 7 | **在 M18 里建 `m18_document` / `m18_consent_sign`** | 签署状态查 M07-06；M18 只做同意书模板与正文 |
| 8 | **在 M18 里建 `m18_home_page`** | 病案首页归 M05-06 |
| 9 | **`SIGNED` 后还允许改正文** | 触发器 + `REVOKE UPDATE`；更正走作废重开或追加 `m18_emr_amendment` |
| 10 | **M18 与 M07-06 各算一个 `content_hash`** | M18 算并固化，M07-06 原样引用（铁律 5） |
| 11 | **病历物理删除** | 只能 `VOIDED`；`REVOKE DELETE ON m18_emr_record` |
| 12 | **事件名改成 `m18.record.finalized`** | M07-06 与 M07-07 已按 `emr.record.finalized` 订阅，改名会**静默收不到** |
| 13 | **事件载荷里带病历正文** | 只带 `record_id` + `content_hash`，订阅方自己去取 |
| 14 | **MySQL/Oracle 语法**：自增关键字、定长整型、旧式日期时间类型、存储引擎子句、Oracle 字符串类型 | PostgreSQL：`GENERATED BY DEFAULT AS IDENTITY`、`SMALLINT`、`TIMESTAMP`、无存储引擎子句、`VARCHAR` |
| 15 | 枚举中文值（`'已签署'`） | 枚举一律英文大写，中文放附录字典 |
| 16 | 表格单元格里出现裸竖线 | 绝对值写 `abs(x)`，含竖线的表达式移到代码块 |
| 17 | 验收表编号加粗（`\| **AC-12** \|`） | 写纯文本编号，不要加粗 |
| 18 | **FastAPI 路由示例参数顺序错误** | 无默认值的依赖参数排在有默认值的查询参数之前 |
| 19 | **计数口径假警**：接口总览里出现 `API-05 新建模板` 这类引用行被多数一次 | 统计接口数时正则必须带方法列，并限定在第 6.1 节内 |
| 20 | **重复章节假警**：共享规范里模板嵌在四反引号代码块内被误判 | 做唯一性检查前先剔除四反引号代码块 |
| 21 | 维度字段无值存 `NULL` | 存空字符串 `''`（PostgreSQL 的 `UNIQUE` 认为 `NULL` 互不相等） |
| 22 | 分区表忘记建 `DEFAULT` 分区 | 新月份第一批写入直接失败 |
| 23 | **CHECK 只保护字段自身，不保护字段之间的组合语义** | 凡是「某个类型/状态必须配一整套参数」的场景，必须另写组合约束 |
| 24 | **同意书签署状态落进 M18 表** | 签署唯一权威在 M07-06，M18 是聚合视图；落了就必然与 M07-06 打架 |
| 25 | **`content_hash` 用 MD5** | MD5 已被证明可构造碰撞，病历是法律证据，必须 SHA-256 |
| 26 | **病历编辑锁 TTL 60 秒** | 医生写 20 分钟是常态；TTL 90 秒 + 前端每 60 秒续期 |
| 27 | **质控规则命中率 100% 或 0%** | 要么规则写错（恒真/恒假），要么根本没跑；两条都要有监控指标 |
| 28 | **归档完整性判 `COMPLETE` 但缺文书** | `integrity_result` 必须是三态（`COMPLETE`/`INCOMPLETE`/`UNKNOWN`）；上游不可用时判 `UNKNOWN`，**绝不能默认 `COMPLETE`** |
| 29 | **`m18.record.locked` 只是发了个事件，数据库没真锁** | 封存必须在数据库层生效（触发器检查 `m18_emr_seal`），否则只是「君子协定」 |
| 30 | **单号用数据库序列拼日期** | 跨零点并发重号；统一 Redis `INCR` |
| 31 | **自创枚举值**（如 `RECORD_STATUS = 'ARCHIVED'`） | 必须用 §13 字典；自创值会与其他子模块的 CHECK 冲突 |
| 32 | **`m18_emr_record` 被多个子模块各建一次** | 由 M18-02 首建，其余子模块只引用（校验器会跨文件查重复建表） |
| 33 | **遇到「怎么改都过不了」的校验，先怀疑校验器，不要先改文档** | 校验器由 Lead 维护，`validate_m18.py` 在 V1.1 已修过两处把自己堵死的规则（MySQL 日期时间类型名的大小写敏感匹配误伤了 Python 的同名类；事件正文字段扫描范围过宽误伤了 10.2 接口契约）。**不要用改别名、换措辞这类会污染代码规范的绕法迁就一个有缺陷的检查**——那会把一个问题变成两个 |
| 34 | **内部接口返回「看起来正常但不完整」的 200** | 调用方无法区分「真的没有这类数据」与「数据源挂了」。必须带 `degraded`/`degraded_sources`/`data_quality`/`as_of` 四标记（§8A.2） |
| 35 | **`data_quality` 无法判定时默认成 `REALTIME`/`COMPLETE`** | 等于把「不知道」记成「没问题」。归档完整性会读这个值，而归档一旦确认要保存 15~30 年，事后无法更正 |
| 36 | **用 200 + 空 `data` 表达「无权限」** | 调用方会当成「没有这份病历」：术前核对判成「不需同意书」、M07-06 生成空文书。无权限一律 403 + 非 0 错误码 |
| 37 | **比率分母为 0 时返回 100%** | 反例见 `M07医生工作站/M07_医生工作站_07_医生工作量与效率_详细设计.md:3129` 的 `if doc["count"] else 100.0`——「当天一份文书都没写」显示及时率 100%。**分母为 0 必须返回 `NULL` + `NO_DATA`**，否则没干活的人排在干了活但迟了的人前面 |
| 38 | **把过敏史权威当成 M03 主表** | `mpi_patient.allergy_history` 是等 M18 发事件去刷的派生值，读它等于读回环；事件失败时读到过期数据且从返回值上看不出来。**权威在 `m18_opd_allergy_detail`，M18 只写不读**（§9.1 V1.1 裁决） |
| 39 | **引用一个不存在的接口并注明「由某模块提供」** | 这是最危险的一类错误——它把不存在的东西写成了「已有的、不用管它」，后续所有人都会跳过核实。M18 已遇到一次（U-07）。**引用任何上游路径前必须 grep 到行号** |
| 40 | **凭印象写具体值，没回头对权威表** | 本轮 M18 五次同根因：P-02 方法写成 GET（原文 POST）、`AR2026102800033` 算成 14 位（实际 15 字符）、同意书模板表名与校验器前缀冲突、`mpi.patient.merged` 出处文件名不存在、附录 D 接口编号与 6.1 冲突。**抽象描述错了读者会怀疑，具体值错了读者会直接引用**——具体值看起来像结论，比描述更像共识。凡写进文档的路径、行号、枚举值、位数、编号，都必须来自一次 grep 或一次当场手算。四类最容易凭印象写：HTTP 方法（被「取 / 查」这种措辞带偏）、字符串位数（肉眼数错）、表名（改了前缀忘了同步正文）、出处行号（记混文件名） |
| 41 | **追加型写作的接缝是校验盲区** | 我们都是分段追加写大文件的（`cat >>`、分段写文件、分段 heredoc），接缝处会出现：一行里粘连两个标题、重复段落、断掉的代码围栏。而校验器验证的是「有没有」，不是「有没有多出来」——`check_dup_sections` 用 `^(#{2,3})\s+(.+)$` 前缀匹配，标题前缀对上就整行收下，后面挂着的第二个标题永远看不见。已由 V1.3 的 `check_glued_headings()` 兜住标题粘连这一类，**其余形态仍需自己在接缝处复查** |
| 42 | **空串是一等公民，NULL 不是** | PostgreSQL 的 UNIQUE 认为两个 NULL 互不相等，但**空串彼此相等**。`source_record_id = ''` 的唯一索引会让第二行直接撞约束，报「唯一约束冲突」，排查时以为是数据重复。同类：M19 幂等键 `biz_type = ''` 拼出 `":ST..."`。**凡是参与唯一约束 / 幂等键的字符串列，都要 `btrim(...) <> ''` 且等于自身去空白** |
| 43 | **没有上限、没有出口的机制等于没有机制** | 「每月复审一次」「定期清理」这类规定如果没有数量上限与升级路径，实施后必然退化成「全部点维持」。M18-08 定的是「单次上限 30 条 + 超 5/15/30 工作日三级升级 + 不做自动处置」——**上限让复审可执行，升级让不执行有后果，不自动处置才暴露管理缺位**。发现机制没有出口，等于把问题换个地方堆放 |
| 44 | **参与比率计算的时间边界必须由数据库决定** | 及时率分子是 `written_at <= deadline_at`，分母由书写窗口决定。时限一旦可由应用层改写，**改一个配置就能让历史及时率变样**。做法：`deadline_at` 写进 DB CHECK（`= 起点 + 时限`），不由 Service 计算后写入 |
| 45 | **降级必须朝「少给」不能朝「多给」** | M18-07 的判据可直接复用：索引滞后 → 返回部分结果**允许**（少给）；权限过滤失败 → 退化成不过滤 **禁止**（多给 = 越权泄露，必须 500）。**应用层过滤的失败模式是「静默地少过滤了一点，结果全出」；SQL 层过滤的失败模式是「抛异常 → 500 → 什么都没出去」。** 另：应用层过滤会让 `total` 是全量数，**计数本身也是泄露** |
| 46 | **只做「发现」不做「处置」等于没做** | 三类异常清单（误报 / 死规则 / 被全忽略的告警）做出来只回答了「哪些规则有问题」，不回答「谁在什么时候看、看完怎么改、不看会怎样」。**发现机制没有出口，等于把问题换个地方堆放。** 合格做法三件套：明确责任人与固定周期 → **单次处理量上限**（不设上限必然退化成全部点「维持」）→ 未处理时的升级路径。**不做自动处置**：最需要复审的恰恰是长期无人理会的对象，自动处置会把「本该有人看但没人看」伪装成「系统正常运行」 |
| 47 | **数据字段传对了但时点传错了** | 「激素长期使用与高眼压」要的基线眼压是**用药开始之前**的值，不是「最近一次」。同一个 `patient_id`，不带时点参数拿到的是最新值——**错不在有没有这个字段，在字段能不能表达时点**。凡涉及「基线 / 变化量 / 长期使用」类判断的输入，都必须带 `as_of` 或测量时刻，且调用方要能说清取的是哪一时点 |
| 48 | **把「自动修复」当成通用的好习惯** | 「凡是『记录本身是证据』的地方都不允许自动修复」这个说法方向对，但「证据类数据」边界模糊——操作日志算不算？配置算不算？**换成可判定的判据：这个不一致本身是不是要被保留的信息？** 是 → 只能告警不能修复（例如 `content_hash` 与实际正文不一致、封存期内的字段、终态单据）；否 → 修复才是正确动作（例如冗余的展示字段、缓存、统计中间态）。M18 已按此落地两处：`m18_emr_record` 哈希巡检只标 `HASH_MISMATCH` 不自动「修复成一致」；`m18_arc_batch` 的 `RELEASED` 是终态不可复用（撤回声明改变了事实，重新归档必须新批次） |
| 49 | **写了降级/告警/巡检，却没写「如果它压根没跑」怎么办** | 沉默本身就是故障。巡检没报错可能是「跑了且全过」，也可能是「压根没跑」，**从输出上看不出区别**，而后者更危险——它让所有人以为系统在管着。做法：为每类周期性检查配一个**「最近一次执行时刻」的度量字段**（如 `m18_paper_scan_last_probe_age_hours`），超过预期周期的 3 倍即告警。**需要用专门一个数字去度量沉默，而不是指望沉默被业务告警覆盖到** |
