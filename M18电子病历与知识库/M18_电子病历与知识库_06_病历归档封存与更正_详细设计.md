## 1. 模块概述

### 1.1 模块定位

M18-06 是 M18 模块中「让病历成为法律档案」的那一环。它回答三个问题：

1. **病历归档了没有？** 一次出院或一次日间手术结束后，M05-05 / M06-06 会把该次就诊的全部病历推给病案库，本子模块负责接收、校验完整性、给出结论。
2. **病历能不能改？** 签署之后不能原地改。要改只能走两条路：作废重开，或者追加一条更正记录且原记录一个字不动。
3. **病历能不能动？** 医疗纠纷、司法取证、死亡病例讨论、院感调查四类场景下，病历要封存。封存期内任何写入都会被数据库拒绝。

一句话概括：**M18-02 记录病历上写了什么，M18-06 保证这些内容在若干年后还能被证明是真的。**

### 1.2 为什么需要独立子模块

| 理由 | 数据支撑 |
|---|---|
| **归档是高频率独立动作，不属于任何书写场景** | 日均 130 个归档批次、480 份病历，年 4.7 万批次。它同时被门诊（M05-05 出院）、日间手术（M06-06）两条业务线触发，任何一条都不能把它塞进自己的代码里 |
| **校验成本必须独立预算** | 一次日间手术的完整性校验要查 M07-06 文书、比对 SHA-256、检查 4 类必检文书，实测 800 ms~1.5 s。M05-05 的 PF-08 要求「提交病案室」含 M18 调用在内 P95 ≤ 1200 ms，同步校验必然超时。校验必须有独立的时间预算和异步容器 |
| **封存的强制力必须落在数据库层** | 应用层做「先查封存状态再写」的做法，在并发与异常下一定会漏。封存要生效，必须是数据库触发器 + `REVOKE` 权限，而不是 Service 里的一行 `if` |
| **留存期迁移是全系统唯一允许删除病历的路径** | 这条路径的设计目标是「让它极难被调用，且每一次调用都留痕」，需要专门的配置表、专门账号（`m18_archiver`）、专门的抽样校验流程。放在任何业务子模块里都会被顺手写成「定期清理」 |

### 1.4 概念辨析

#### 1.4.1 归档 ≠ 封存 ≠ 签署

这三个词在口语里常被混用，但它们分别属于三个不同的维度：

| 概念 | 回答的问题 | 作用范围 | 存哪里 | 能否撤销 |
|---|---|---|---|---|
| **签署** | 这份病历谁签的字、什么时候签的 | 单份病历 | `m18_emr_record.status = 'SIGNED'` | 不能撤销，只能作废（`VOIDED`） |
| **归档** | 这次就诊的病历进没进病案库 | 一次就诊 / 一个批次 | `m18_arc_batch.status` | 可以撤销（`RELEASED`），但撤销后必须新建批次重新归档 |
| **封存** | 这份病历现在能不能被改动 | 患者 / 就诊 / 日期段 / 批次 | `m18_emr_seal.status` | 可以解封（`RELEASED`），需两人审批 |

一份病历可以同时是 `SIGNED`、`CONFIRMED`（已归档）、`ACTIVE`（封存中）。**判据：一件病历签署之后 `record.status` 永远停在 `SIGNED`，归档与封存都不改变它。** 总纲 §4.1 的注写得很清楚，本设计严格遵守。

#### 1.4.2 「归档成功」有两层含义

| 层 | 判定标准 | 谁关心 | 不成立的后果 |
|---|---|---|---|
| **收下了** | 批次落库、幂等键占用、异步校验任务入队 | M05-05 / M06-06（它们调 P-04 只看这个） | 病历可能在传输中丢失，且调用方不知道 |
| **确认了** | 完整性校验完成且结果为 `COMPLETE`，发 `m18.archive.confirmed` | 病案室、医务科、M22 归档统计 | 病历进了病案库但内容不全，事后追责时拿不出完整档案 |

P-04 的响应表达的是**第一层**。M05-05 只有在收到 `m18.archive.confirmed` 事件后才把本地归档状态置为「确认归档成功」。这个分工是本节最重要的一条设计约束，详见 8.3。

#### 1.4.3 完整性三态里 `UNKNOWN` 与 `INCOMPLETE` 的区别

| 结果 | 含义 | 谁的问题 | 处置 |
|---|---|---|---|
| `COMPLETE` | 必检文书齐全，哈希全部一致 | 无 | 自动确认归档 |
| `INCOMPLETE` | 必检文书缺失，或哈希不一致 | **临床科室 / 病案室** | 退回补正，批次置 `REJECTED` |
| `UNKNOWN` | 有上游查不到，**无法判定齐不齐** | **系统运维** | 不自动确认，转人工复核 |

`INCOMPLETE` 与 `UNKNOWN` 最容易被错误合并。合并之后，一次 M07-06 的服务抖动会让 200 份病历全部变成「不完整」，病案室把 200 份全部退回科室，而科室拿回去一看发现病历是全的。**两次无效往返之后，病案室就不会再认真处理退回单了**——这才是把三态压成两态的真实代价。

#### 1.4.4 作废重开与追加更正的区别

| 对比项 | 作废重开 | 追加更正 |
|---|---|---|
| 原记录 | `SIGNED → VOIDED`，永久保留可查 | 原记录**一字不动**，仍是 `SIGNED` |
| 新内容 | 新建一份 `record_no` 不同的 DRAFT 病历，重新走书写与签署 | 写入 `m18_emr_amendment`，指向原 `record_id` |
| 展示方式 | 作废件与新生效件分别列出，作废件标注原因 | **原文 + 更正说明同页**，两者都完整展示 |
| 适用场景 | 病历记错了患者、整份记错就诊、签署对象错误 | 正文里某一句话写错了、漏了一项检查结果、需要补充说明 |
| 审计重点 | 作废原因、作废人、重新签署的时间差 | 更正原因（≥20 字）、审批人、更正次数 |

判定原则：**错的是「这份病历属于谁」，用作废重开；错的是「这份病历里的一句话」，用追加更正。** 用更正去处理作废场景，会导致一份病历上挂着 40 条更正记录，看起来像被反复篡改；用作废去处理更正场景，会产生一堆 `VOIDED` 病历，检索时噪音极大。

### 1.5 设计目标

| 编号 | 目标 | 可验证的指标 |
|---|---|---|
| G-1 | 归档推送不丢、不重 | 同一幂等键推 5 次只产生 1 个批次；P-04 同步阶段 P95 ≤ 200 ms |
| G-2 | 完整性判定绝不把「不知道」记成「没问题」 | 上游超时判 `UNKNOWN`；`UNKNOWN` 批次 0 例自动确认 |
| G-3 | 封存期内病历绝对不可写 | 数据库层拦截率 100%，应用层绕过也拦得住 |
| G-4 | 已签署病历不可原地修改 | 触发器 + `REVOKE UPDATE` 双保险，直接 SQL 也改不动 |
| G-5 | 病历可追溯到每一次改动 | 更正记录、操作日志、审批链三处留痕且互不覆盖 |
| G-6 | 留存期迁移可验证、不可逆操作前必有校验 | 100 份哈希抽样，抽样不过不删除 |
| G-7 | 纸质病历数字化后有据可查 | 每份扫描件有独立哈希，损坏可检出 |

## 3. 业务模型

### 3.1 核心实体关系

```
   m18_arc_batch (归档批次)
        |  1
        |              N
        +---------------- m18_arc_item (归档明细) ---> m18_emr_record (M18-02)
        |
        |------------ m18_emr_document (文书目录)
        |
        |------------ m18_arc_paper_scan (扫描件)

   m18_emr_seal (封存) ---> 约束所有病历正文表的写入
   m18_emr_amendment (更正) ---> m18_emr_record
   m18_arc_borrow (借阅) ---> 1:N ---> m18_arc_borrow_approval (审批)
   m18_arc_retention (留存期配置) ---> 驱动迁移任务
   m18_arc_oper_log (操作日志) ---> 记录以上所有动作
```

### 3.2 状态机

#### 3.2.1 归档批次状态机

```
                    +-------------+
   P-04 收到推送 --> |  RECEIVING  |  同步阶段：落批次 + 落明细 + 占用幂等键
                    +------+------+
                           | 异步任务取到该批次
                           v
                    +-------------+
                    |  CHECKING   |  查 M07-06 文书 + 比对哈希 + 判必检项
                    +------+------+
                           |
              +------------+-------------+
              |                          |
        COMPLETE 或                    INCOMPLETE 或
        UNKNOWN                       哈希不一致
              |                          |
              v                          v
      +-------------+            +-------------+
      |  CONFIRMED  |            |  REJECTED   |
      +------+------+            +------+------+
             |                          |
             | 撤销归档                  | 补正后重新推送
             v                          v
      +-------------+            +-------------+
      |  RELEASED   |            |  CHECKING   |  reopen_count + 1
      +-------------+            +-------------+
         （终态）                  （上限 3 次，超出必须新建批次）
```

**关键裁决一：`CONFIRMED` 不能回到 `CHECKING`。** 汇总 G-07 已定。已经发出 `m18.archive.confirmed` 的批次如果回退，M05-05 侧的状态需要二次回滚，而它可能已经把「归档成功」推给了患者端。

**关键裁决二：`RELEASED` 是终态，撤销后必须新建批次。** 总纲 §4.3 原文：「撤销归档是一个『撤回声明』，撤销后再归档必须是一个新批次。理由：撤销归档通常发生在『归档错了』（归到了错的就诊、错的日期），如果允许在原批次上重来，新批次的 `batch_no` 还是旧的，M05 那边 `m18_archive_id` 没变而归档内容变了，账实不符。」

**关键裁决三：`REJECTED` 可以回到 `CHECKING`，但要计数。** 详见 8.3 节，这是本子模块最重要的一处设计判断。

#### 3.2.2 封存状态机

```
   +-----------+
   |  ACTIVE   |  生效中，任何写操作被数据库拒绝
   +-----+-----+
         |
    +----+------------------+
    |                       |
 解封（双人审批）        被更大范围封存覆盖
    |                       |
    v                       v
+-----------+        +--------------+
| RELEASED  |        |  SUPERSEDED  |
+-----------+        +--------------+
  （可再封）           （从未被解封）
```

`SUPERSEDED` 与 `RELEASED` 的区别：前者是「这条封存被一条范围更大的封存接管了」，后者是「这条封存被撤销了」。做成两个状态而不是一个，是因为审计时这两个事实完全不同——前者说明封存还在，只是换了条记录；后者说明病历重新可写了。

**解封后能否再封：能。** 但要新建一条 `seal_no` 不同的记录，旧的保持 `RELEASED`。同一患者可以同时存在多条 `ACTIVE` 封存（不同范围）。

#### 3.2.3 借阅状态机

```
  SUBMITTED --> APPROVING --> APPROVED --> BORROWED --> RETURNED
      |              |            |
      |              v            +--> （到期未查阅自动 APPROVED 失效，需重新申请）
      |          REJECTED
      v
  CANCELLED
```

驳回后可重新提交，进入新的 `round_no`，历史审批链保留。

#### 3.2.4 更正状态机

```
  PENDING_APPROVAL --> APPROVED     （医务科审批通过，可展示）
        |
        +-----------> REJECTED      （驳回，不展示）
        |
        +-----------> WITHDRAWN     （申请人撤回）
```

`APPROVED` 之后不可再改状态；`REJECTED` / `WITHDRAWN` 的更正记录保留但 `is_visible = FALSE`。

### 3.4 关键计算模型

#### 3.4.1 `M18-CALC-01` 病历完整性检查

**公式：**

| 判定 | 条件 |
|---|---|
| `COMPLETE` | `required_docs ⊆ present_docs` 且全部 `content_hash` 一致 |
| `INCOMPLETE` | `required_docs ⊄ present_docs` 或存在 `content_hash` 不一致 |
| `UNKNOWN` | 任一上游（M07-06 文书清单、`m18_emr_record`）不可用 |

**`required_docs` 定义：**

| `record_type` | 必检文书 |
|---|---|
| `OUTPATIENT` | `MEDICAL_RECORD` |
| `INPATIENT` | `MEDICAL_RECORD`、`DISCHARGE_SUMMARY`（出院时） |
| `DAY_SURGERY` | `MEDICAL_RECORD`、`SURGERY_CONSENT`、`ANESTHESIA_CONSENT`、`DISCHARGE_SUMMARY` |
| `EMERGENCY` | `MEDICAL_RECORD` |

**`present_docs` 来源：** `m18_emr_document` 中该就诊的 `is_present = TRUE` 的文书集合 ∪ M07-06 `GET /internal/v1/m07/documents/by-source` 返回的已签文书集合。取并集而不是只取一边，是因为 M18 侧可能还没同步过某些 M07 文书（同步是异步的）。

**单位：** 无单位，输出三态枚举。

**边界条件：**

| 边界 | 处理 |
|---|---|
| 门诊病历就诊未结束时 `required_docs` 为空集 | 恒 `COMPLETE`。不能因为「还没写」就判不完整——门诊病历在患者离开诊室前就是空白的 |
| 上游超时（>500 ms） | 判 `UNKNOWN`，**绝不默认 `COMPLETE`** |
| 上游返回 404 | 判 `UNKNOWN`（不是「没有文书」，而是「查不到」） |
| 上游返回空数组 | 判 `COMPLETE` 的前提是 `required_docs` 也为空；否则按缺失处理判 `INCOMPLETE` |

**舍入：** 不涉及。

**失败条件：** 任一上游抛异常、超时、返回非 2xx，全部归入 `UNKNOWN`，不做降级推断。

**算例：**

日间手术就诊 `encounter_id = 81002`，`required_docs` 4 项。`present_docs` = `MEDICAL_RECORD`、`SURGERY_CONSENT`、`DISCHARGE_SUMMARY` 3 项，缺 `ANESTHESIA_CONSENT`。

- 差集 `required_docs − present_docs` = `{ANESTHESIA_CONSENT}` ≠ ∅
- 判定 `INCOMPLETE`，`missing_docs = ['ANESTHESIA_CONSENT']`
- 批次置 `REJECTED`，`reject_items` 记一条：`{"record_id": 90012, "reason": "MISSING_DOC", "missing_docs": ["ANESTHESIA_CONSENT"]}`

第二个算例（`UNKNOWN`）：

同一就诊，但 M07-06 在 500 ms 内没有返回：

- `UNKNOWN` 判定成立，`missing_docs = []`（**不推断缺失项**）
- 批次停在 `CHECKING`，不发 `m18.archive.confirmed`，也不发 `m18.archive.rejected`
- 进入人工复核队列（`idx_m18_arc_batch_unverified_partial`）

#### 3.4.2 `M18-CALC-06` 归档完整率

**公式：**

```
归档完整率 = 完整性判定为 COMPLETE 的批次数
           ÷ 已判定的批次数（COMPLETE + INCOMPLETE）
           × 100%
```

**单位：** 百分比，展示保留 2 位小数，存储 `NUMERIC(10,6)` 的比率值。

**边界条件：**

| 边界 | 处理 |
|---|---|
| 分母为 0（当期全部是 `UNKNOWN`，或当期无归档） | 完整率为 `NULL`，**不是 0%** |
| `UNKNOWN` 批次 | **既不在分子也不在分母**，单列为「待复核批次」 |
| 跨月批次 | 以 `confirmed_at` 或 `rejected_at` 所在月份归属 |

**为什么 `UNKNOWN` 不进分母——这是本子模块最需要讲清楚的一条：**

总纲 §6.6 原文：「`UNKNOWN` 的批次**既不在分子也不在分母**，单列『待复核批次』。理由是把它算进分母会把完整率系统性压低（上游抖动天数不可控），算进分子则违反事实。」

用具体数字说明。2026-10 归档 1,240 批次，`COMPLETE` 1,208、`INCOMPLETE` 26、`UNKNOWN` 6：

- 正确算法：`1208 / (1208 + 26) = 1208 / 1234 = 0.978931` → **97.89%**
- 如果把 `UNKNOWN` 算进分母：`1208 / 1240 = 0.974194` → 97.42%，且**这个数字每天会随 M07-06 的可用性波动**
- 如果把 `UNKNOWN` 算进分子（当成完整）：`(1208 + 6) / 1240 = 0.979032` → 97.90%，看起来几乎一样，**但这是把 6 批「不知道全不全」的病历标记为「完整」，而这个标记要保存 15~30 年，事后无法更正**

极端情形：假设某天 M07-06 故障 4 小时，期间归档的 240 批全部判 `UNKNOWN`。若计入分母，当月完整率变成 `1208 / (1234 + 240) = 1208 / 1474 = 81.95%`——**从 97.89% 掉到 81.95%，而实际上病历一份都没缺。** 如果院办拿着 81.95% 去问责病案室，病案室的全部辩解都建立在「那是系统故障」上，而下一次真的缺了 50 份文书时，83% 这个数字已经没有任何警示作用了。**指标一旦能被系统故障污染，就失去了度量能力。**

**展示要求（写进 P03 / P09）：** 页面必须同时显示四个数：

> 本月归档 1,234 份已判定：1,208 份完整、26 份不完整、另有 6 份无法判定

不能只显示「97.89%」——读者会拿 `1208 / 1234` 反推出「26 份不完整」，然后去问「哪 26 份」，而实际上 1,234 是**已判定**总数，不是总批次 1,240。

**舍入：** 只在展示层舍入到 2 位小数；内部统计与阈值比较一律用未舍入的 `NUMERIC(10,6)`。

**失败条件：** 当期无归档批次时返回 `NULL` 而不是 `0.00%`。`0.00%` 的含义是「有一批病历，全都不完整」，与「这个月没有归档」是完全不同的两件事。

#### 3.4.3 归档批次幂等判定

**公式：** 对每次 P-04 请求，计算 `key = (source_module, source_biz_no)`。

| 查到的既有批次 | 本次请求的处理 | 响应 `idempotent_replay` |
|---|---|---|
| 无 | 新建批次，`status = 'RECEIVING'` | `false` |
| 有，`status ∈ (RECEIVING, CHECKING, CONFIRMED)` | **原样返回该批次当前状态**，不修改任何数据 | `true` |
| 有，`status = 'REJECTED'` 且 `reopen_count < 3` | **复用该批次**：`status → CHECKING`，`reopen_count + 1`，刷新 `last_reopen_at` | `false`（这是一次真实的重开，不是重复） |
| 有，`status = 'REJECTED'` 且 `reopen_count >= 3` | 返回错误 `"1806007"`，提示必须新建批次 | — |
| 有，`status = 'RELEASED'` | 返回错误 `"1806008"`，提示已撤销归档不可复用 | — |

**单位：** 无。

**边界条件：**

| 边界 | 处理 |
|---|---|
| 两个请求同时到达且都查不到既有批次 | 唯一索引 `uk_m18_arc_batch_source` 拦住后到的那一个，捕获 `SQLSTATE 23505` 后转查既有批次，返回 `idempotent_replay = true` |
| 既有批次在 `CHECKING` 中，同一幂等键再次推送 | 原样返回，**不重置进度** |
| 既有批次是 `CONFIRMED`，同一幂等键再次推送 | 原样返回 `CONFIRMED`，**不回退** |
| 来源模块与业务单号其中一个不同 | 视为不同批次 |

**舍入：** 不涉及。

**失败条件：** 幂等键查询本身失败（DB 不可用）时返回 5xx，不返回「看起来成功」的 200。

**算例：** M06-06 推送 `source_module='M06'`、`source_biz_no='M06-SET-20261028001'` 三次（模拟网络重试）：

- 第 1 次：无既有批次 → 新建，返回 `batch_no='AR202610280033'`，`idempotent_replay=false`
- 第 2 次：查到 `status='CHECKING'` → 原样返回同一 `batch_no`，`idempotent_replay=true`
- 第 3 次：查到 `status='CONFIRMED'` → 原样返回同一 `batch_no` 与 `integrity_result='COMPLETE'`，`idempotent_replay=true`
- 结果：**1 个批次**、`reopen_count=0`、归档完整率统计里只计 1 次

### 5.2 P01 归档工作台

**页面目的：** 病案室每天早上打开这一页，5 秒内知道「今天有多少份病历等着处理、有没有卡住的、有没有判不了的」。

**布局：四象限**

| 象限 | 内容 | 数据来源 |
|---|---|---|
| 左上：今日接收 | 今日批次总数、病历份数、按来源（M05 / M06）拆分 | API-02 |
| 右上：待人工复核（`UNKNOWN`） | 数量 + 最旧一条已等待时长 | API-02 |
| 左下：被拒批次 | 数量 + 按缺失文书类型 Top5 | API-02 |
| 右下：校验中 | 数量 + 超 10 分钟未完成的批次数 | API-02 |

**关键交互：**

- 点「待人工复核」数字 → 跳 P02 并带上 `integrity_result=UNKNOWN` 筛选
- 点「被拒批次」→ 跳 P02 并带上 `status=REJECTED` 筛选
- 右上角显示当前数据截止时刻（`as_of`），例如「数据截至 2026-10-28 09:00」

**性能要求：** 工作台 P95 ≤ 1,500 ms（总纲 §8.1）。四象限全部走 `idx_m18_arc_batch_status` 与 `idx_m18_arc_batch_unverified_partial`，单次查询 ≤ 3 ms。

### 5.3 P02 归档批次管理

**页面目的：** 批次的列表、筛选、详情入口、补正重推、撤销归档。

**列表列：**

| 列 | 说明 |
|---|---|
| 批次号 | `batch_no`，点击进详情 |
| 来源 | M05 / M06 / MANUAL |
| 来源单号 | `source_biz_no` |
| 患者 | 姓名 + 就诊类型 |
| 病历份数 | `record_count` |
| 状态 | 五态标签，`REJECTED` 红色、`CONFIRMED` 绿色、`UNKNOWN` 橙色 |
| 完整性判定 | `COMPLETE` / `INCOMPLETE` / `UNKNOWN` / 空 |
| 重开次数 | `reopen_count`，≥3 加感叹号标记 |
| 接收时间 | `received_at` |

**筛选：** 状态、完整性判定、来源、日期范围、患者、批次号模糊。

**操作：**

| 操作 | 条件 | 结果 |
|---|---|---|
| 查看详情 | 任何状态 | 进 P03 |
| 补正后重新推送 | `status='REJECTED'` 且 `reopen_count < 3` | 打开补正弹窗，确认后调 API-06 |
| 撤销归档 | `status='CONFIRMED'`，权限 `m18:arc:batch:release` | 弹窗要求填原因（≥10 字），调 API-07 |
| 人工复核确认 | `integrity_result='UNKNOWN'`，权限 `m18:arc:batch:review` | 弹窗要求填复核结论与依据，调 API-09 |

> **「人工复核确认」是本页最敏感的按钮。** 它把一个 `UNKNOWN` 批次人工转成 `CONFIRMED`，等于人替系统担保「我看过了，病历是全的」。因此必须有独立权限、必须填复核依据、必须留痕到 `m18_arc_oper_log`。

### 5.4 P03 归档明细与完整性检查

**页面目的：** 看清一个批次里到底有什么、缺什么、为什么判成这样。

**分区：**

| 区域 | 内容 |
|---|---|
| 批次概要 | 批次号、来源、状态、接收/校验时间、校验耗时 |
| **完整性判定卡片** | 判定结果 + `required_docs` / `present_docs` / `missing_docs` 三列对照 |
| 明细列表 | 每份病历的 `record_no`、`status`、`content_hash` 前 8 位、哈希是否一致、是否封存 |
| 拒绝明细 | `reject_items` 逐条展开：哪份病历、缺哪份文书 |
| 文书目录 | `m18_emr_document` 中该就诊的全部文书与存在性 |

**完整性判定卡片的三列对照是本页的核心：**

```
必检文书（4）        实际存在（3）        缺失（1）
MEDICAL_RECORD      MEDICAL_RECORD
SURGERY_CONSENT     SURGERY_CONSENT
ANESTHESIA_CONSENT  ——                  ANESTHESIA_CONSENT
DISCHARGE_SUMMARY   DISCHARGE_SUMMARY
```

三列同时展示而不是只展示「缺失 1 项」，是因为病案室通知科室时要说清楚「你这台手术麻醉同意书没签」，而不是「你有一项没交」，后者会让科室反复来问。

**`UNKNOWN` 批次的特殊展示：** 判定卡片显示「无法判定——M07-06 文书服务超时（500ms）」，并禁用「自动确认」，只保留「人工复核确认」。

### 5.5 P04 病历封存（核心）

**页面目的：** 发起封存、审批封存、解封。

**列表列：** 封存编号、患者、范围、事由、生效时刻、状态、审批人、病历份数。

**封存申请表单：**

| 字段 | 必填 | 校验 |
|---|---|---|
| 患者 | 是 | 从患者选择器选，必须存在 |
| 封存范围 | 是 | `PATIENT` / `ENCOUNTER` / `DATE_RANGE` / `BATCH`，选择后动态显示对应边界字段 |
| 就诊 ID / 日期段 / 批次号 | 视范围 | 与范围匹配的边界必填，其余隐藏 |
| 封存事由 | 是 | 六选一 |
| 事由详述 | 是 | ≥10 字 |
| 外部文号 | 司法与医保必填 | 案号 / 公函号 / 医保核查编号 |

**范围选择器的动态行为：**

- 选 `PATIENT`：隐藏就诊、日期、批次三个输入，提示「将封存该患者全部病历」
- 选 `ENCOUNTER`：显示就诊选择器，必填
- 选 `DATE_RANGE`：显示起止日期，均必填，且结束不早于开始
- 选 `BATCH`：显示批次选择器，必填

这个动态行为与数据结构文件的 C-22 组合约束一致：前端隐藏的字段提交时必须为空，否则数据库会拒绝。

**解封弹窗：**

| 字段 | 必填 | 说明 |
|---|---|---|
| 解封原因 | 是，≥10 字 | — |
| 医务科审批人 | 是 | 人员选择器 |
| 院长审批人 | 是 | 人员选择器，**不得与医务科审批人相同** |

前端在提交前校验两个审批人不同，后端 `SealReleaseIn` 的 `model_validator` 再校验一次，数据库 `ck_m18_emr_seal_dual_approver` 第三次校验。

**封存生效提示：** 封存成功后页面顶部显示醒目提示「该患者病历已封存，所有写入操作将被拒绝。解封需医务科 + 院长双审批」。

### 5.6 P05 病历借阅与审批

**页面目的：** 封存期间需要查阅病历时的唯一合法通道。

**申请表单：** 患者、就诊范围、借阅用途（七选一）、用途详述（≥10 字）、借阅权限范围（查看/打印/复制/导出）、可打印页数、申请天数。

**审批链展示：** 按 `round_no` + `stage_no` 展示每一轮的每一级，驳回的轮次折叠显示。

**借阅台账：** 已批准的借阅显示有效期、查阅次数、打印次数；过期的置灰。

### 5.7 P06 病历更正与作废

**页面目的：** 已签署病历的两种修改路径。

**更正申请表单：**

| 字段 | 必填 | 校验 |
|---|---|---|
| 病历号 | 是 | 必须是 `SIGNED` 状态 |
| 更正类型 | 是 | `SUPPLEMENT` / `CORRECTION` / `APPEND` / `CLARIFY` |
| 更正段落 | 是 | 段落类型或字段编码至少一个 |
| 更正前内容 | 是 | 系统自动带出原段落的当前内容，可编辑 |
| 更正后内容 | 是 | 不得与更正前完全相同 |
| 更正原因 | 是，≥20 字 | — |

**更正详情页的展示顺序（不可调整）：**

1. 原病历正文（完整）
2. 更正说明区（更正前后对照 + 原因 + 审批人 + 审批意见 + 时间）
3. 更正历史（同一病历的全部更正，按 `seq_no`）

**打印输出必须做到「原文 + 更正说明」同页。** 只打印更正后的版本是不允许的——那等于伪造病历，因为读者会以为那就是医生当时写的。

**更正次数提示：** 同一病历 `APPROVED` 状态的更正达到 3 条时，页面顶部显示「该病历已更正 3 次，建议医务科复核书写质量」，并自动生成一条复核任务。

**作废重开入口：** 同一页面提供「作废并重开」按钮，点击后进入 M18-02 的新建病历流程，原病历置 `VOIDED`。

### 5.8 P07 纸质病历扫描

**页面目的：** 纸质病历的扫描件登记、预览、校验状态。

**列表列：** 扫描件号、患者、就诊、文书类型、页范围、页数、格式、校验状态、是否只读存储、扫描人、扫描时间。

**上传流程：**

1. 选择患者与就诊
2. 上传文件（前端算 SHA-256 并发给后端比对，或后端算）
3. 填页范围（起始页、结束页）
4. 提交 → 后端把文件写入对象存储 → 登记 `m18_arc_paper_scan` → 异步校验哈希

**校验状态展示：**

| 状态 | 颜色 | 含义 |
|---|---|---|
| `UNVERIFIED` | 灰 | 已登记，尚未校验 |
| `VERIFIED` | 绿 | 哈希一致 |
| `MISMATCH` | 红 | 哈希不一致，文件可能被替换或损坏，需要重扫 |
| `MISSING` | 红 | 对象存储中找不到该文件 |

### 5.9 P08 留存期与销毁

**页面目的：** 查看留存期配置、发起迁移（含试运行）、查看迁移历史。

**重要提示区（页面顶部固定）：**

> **本页不提供「删除病历」功能。**
> 病历保存期满后**继续保留**，不做销毁。迁移只是把 3 年以上的病历搬到只读归档库，在线库的业务表里不再保留副本。
> 迁移第 6 步的删除由专用账号 `m18_archiver` 执行，且必须先通过 100 份哈希抽样校验。

**留存期配置表格：** 病历类型、保存年限、在线年限、归档库 schema、是否销毁（恒为「否」）、法规依据、生效日期。

**迁移执行区：**

| 步骤 | 界面表现 |
|---|---|
| 1. 选病历类型与边界日期 | 表单 |
| 2. 试运行 | 按钮，返回将要迁移的行数，不实际迁移 |
| 3-5. 导出 + 校验 | 进度条，「已导出 N 行，已抽样 100 份，不一致 0 份」 |
| 6. 删除 | **不在此页面触发**，由运维在服务器上以专用账号执行 |
| 7. 日志 | 迁移历史表格 |

第 6 步不在页面触发，是刻意的：**在线库删除病历是唯一不可逆的操作，不能有一个按钮就能做到。**

### 5.10 P09 归档统计

**页面目的：** 归档完整率与趋势。

**核心展示区（按 3.4.2 的展示要求）：**

```
2026-10 归档完整率  97.89%

已判定 1,234 份：1,208 份完整、26 份不完整
另有 6 份无法判定（不进分子分母）

[趋势图]
```

**为什么把「另有 6 份无法判定」写在完整率正下方——** 用户看到 97.89% 的第一反应是「剩下 2.11% 不完整」= 26 份。如果不写明还有 6 份 `UNKNOWN`，这 6 份就被默认为「完整」或「不完整」中的一种，两种理解都是错的。

**趋势图：** 折线为完整率，柱状为 `UNKNOWN` 数量，两者同一图但不同 Y 轴，一眼能看出「完整率下降是不是因为上游抖动了」。

    "items": [],
    "total": 0,
    "page": 1,
    "page_size": 20,
    "pages": 0
  },
  "trace_id": "9f2c1d3e4b5a6c7d"
}
```

**降级三种合法形态（共享规范 §8A.2）：**

| 形态 | HTTP | 响应体 | 调用方效果 |
|---|---|---|---|
| 正常 | 200 | `code: 0` + 完整 `data` | 正常处理 |
| 降级返回 | 200 | `code: 0` + `data` 带质量标记 + `degraded: true` | 知道「这次不完整」并自行决定 |
| 失败 | 4xx/5xx | 非 0 `code` | 走自己的降级分支 |

**所有 `data` 对象必须带四个质量标记，`degraded: false` 时也必须出现：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `degraded` | BOOLEAN | 本次返回是否降级 |
| `degraded_sources` | ARRAY | 降级数据源清单，元素含 `source` 与 `reason`；不降级为 `[]` |
| `data_quality` | VARCHAR(16) | `REALTIME` / `CACHED` / `PARTIAL` / `UNKNOWN` |
| `as_of` | TIMESTAMP | **数据口径截止时刻**，不是请求时刻 |

集合类响应另加 `record_count`。

**不允许 200 + 空 `data` 表达「无权限」：** 一律 403 + 非 0 错误码。封存期病历的访问尤其如此——否则调用方会把它当成「这份病历不存在」。

  3. 按 `boundary_date` 统计范围内的病历，校验 `status ∈ ('SIGNED', 'VOIDED')`——**草稿病历永不迁移**，有草稿返回 `"1806037"`
  4. 校验范围内封存记录 `status ≠ 'ACTIVE'`——**封存中的病历不迁移**，有封存返回 `"1806037"`
  5. `dry_run = true`：只返回统计结果，不做任何写操作，`deleted = false`
  6. `dry_run = false`：执行导出到 `m18_archive` schema（`INSERT ... SELECT` 跨 schema）
  7. 抽样 `sample_size` 份，逐份比对 `content_hash`，有不一致则 `verify_result = 'FAILED'`，**终止流程**
  8. **第 6 步（在线库 DELETE）不在本接口内执行**，必须由运维以 `m18_archiver` 账号在服务器上手工执行，且执行前需人工确认第 7 步的 `verify_result = 'PASSED'`
  9. 写 `m18_arc_oper_log`，`oper_type = 'RETENTION_MIGRATE'`，必填 `row_count` / `verify_result` / `verify_detail` / `operator_id` / `operator_name`
  10. 返回

> **为什么第 6 步不放进接口：** 在线库删除病历是唯一不可逆的操作。把它做成一个接口，意味着任何人只要拿到 `m18:arc:retention:migrate` 权限就能触发删除。放进运维手工步骤之后，删除必须经过「登录服务器 + 切换到专用账号 + 手工执行 SQL」三个动作，每一步都有独立的操作日志。汇总 §10.3 的原话是：M18 的删除路径设计目标是「让它极难被调用，且每一次调用都留痕」，而不是「提供一个删除功能」。

     - 查到且 `status ∈ (RECEIVING, CHECKING, CONFIRMED)` → **原样返回首次结果，`idempotent_replay = true`，不改任何数据**，流程结束

  5. **落批次**：生成 `batch_no`，`status = 'RECEIVING'`，写 `required_docs`（按 `record_type` 从配置取）
  6. **落明细**：按 `(batch_id, record_id)` 唯一键批量 upsert，`status = 'PENDING'`
  7. **占用幂等键**：靠 `uk_m18_arc_batch_source` 唯一索引保证；捕获 `SQLSTATE 23505` 时转第 3 步重查（并发兜底）
  8. **投递异步校验任务** `task_m18_archive_check(batch_no)` 到 Celery
  9. **判定 `degraded`**：第 5、6、7、8 步**全部成功**时 `degraded = false`；任何一步失败都要 `degraded = true` + `degraded_sources` 写明是哪一步失败。**不同步骤失败的处理不同：**

| 失败步骤 | 处理 | 返回 |
|---|---|---|
| 第 5 步批次落库失败 | 不占用幂等键（事务回滚） | 5xx + `"1806043"` |
| 第 7 步幂等键冲突且重查仍找不到 | 事务回滚 | 5xx + `"1806043"` |
| 第 8 步任务入队失败 | **保留批次不删**，回滚到 `RECEIVING`，前台重试 | 200 + `degraded = true` + `degraded_sources` 写 `CELERY_QUEUE` |

  第 8 步的特殊处理原因：任务入队失败时批次已经落库且幂等键已占用。如果此时返回失败并回滚批次，M05 重试时会重新创建一个批次，但 M18 内部的批次已经没了——下次重试的 `source_biz_no` 相同所以还能覆盖。但更糟的情况是入队失败而事务未完全回滚，就会产生「批次存在但永远不会被校验」的僵尸批次。**因此本设计选择「保留批次 + 降级返回」**，并用 `idx_m18_arc_batch_checking_partial` 做扫描兜底：APScheduler 每 5 分钟扫一次 `status = 'RECEIVING'` 且 `received_at` 早于 2 分钟的批次，重新投递校验任务。

  10. **写操作日志** `ARCHIVE_PUSH`
  11. **返回**，`emr_doc_id` 取该就诊的第一条 `m18_emr_document.id` 转字符串（M06 侧 `emr_doc_id` 声明为 `VARCHAR(64)`）

> **为什么同步阶段不做完整性校验：** M05-05 的 PF-08 要求「提交病案室」含 M18 调用在内 P95 ≤ 1200 ms。一次日间手术的完整性校验要查 M07-06（500 ms 超时预算）+ 比对哈希（31 万份文书索引扫）+ 检查 4 类必检文书，实测 800 ms~1.5 s。**同步做校验必然超时。** 同步只负责「收下并保证不丢」，异步负责「校验并报结果」。
>
> **为什么返回的 `status` 是 `RECEIVING` 而不是 `CONFIRMED`：** 因为此刻还没校验。返回 `CONFIRMED` 会让 M05 以为归档成功了，而实际上病历可能缺文书。M05-05 只有在收到 `m18.archive.confirmed` 事件后才把本地状态置为「确认归档成功」。

     - M07-06 返回且含该类型 → `present = true`，`resolved = true`
     - M07-06 返回但不含该类型 → `present = false`，`resolved = true`
     - M07-06 超时（>500 ms）或非 2xx → `resolved = false`，计入 `unknown_types`

     - `missing_types` 非空 → `result = 'INCOMPLETE'`
     - `missing_types` 为空但 `unknown_types` 非空 → **`result = 'UNKNOWN'`**，`degraded = true`，`data_quality = 'UNKNOWN'`
     - 两者皆空 → `result = 'COMPLETE'`

>
> **`as_of` 的取值：** 本接口返回的是「截至某个统计时点」的文书存在性。由于文书可以随时新增，`as_of` 取**当天 00:00:00**（当日快照的起点），而不是请求时刻——这样 M05-06 在一天内多次调用同一就诊会得到稳定的 `as_of`，缓存才有意义。

  "data": null,
  "trace_id": "9f2c1d3e4b5a6c7d"
}
```

- **错误码：** `"1806045"`（封存状态查询失败，调用方必须按已封存处理）
- **业务逻辑：**
  1. 先查 Redis `m18:arc:seal:{patient_id}`，TTL 60 秒，命中直接返回
  2. 未命中查 `m18_emr_seal`，条件 `patient_id = ? AND status = 'ACTIVE'`，命中 `idx_m18_emr_seal_active_partial`
  3. 有 `ACTIVE` 记录 → `sealed = true`，返回第一条（优先 `PATIENT` 范围）
  4. 无 → `sealed = false`
  5. 写缓存
  6. 返回

> **fail-closed 是本接口最重要的设计约束。** 如果 DB 或 Redis 异常，本接口**必须返回非 0 错误码**，绝不能返回 `sealed: false`。理由：`sealed: false` 等于告诉调用方「这份病历没封存，你可以改」，而实际上可能是服务异常导致查不到封存记录。**闸门的错误方向必须是「更严格」，不能是「更宽松」。** 调用方（M07/M05/M09）收到非 0 错误码时，应当按「已封存」处理并拒绝写入，这是它们的降级分支。
>
> **为什么缓存 TTL 只有 60 秒而不是更长：** 封存是安全闸门，缓存过长会让「刚解封的病历在 5 分钟内仍被拒绝写入」，或者「刚封存的病历在 5 分钟内仍可写」。60 秒是「缓存收益足够覆盖 P95 100 ms 要求」与「状态变更延迟可接受」之间的平衡点。封存与解封的成功路径会**主动删除缓存**，所以 60 秒只覆盖异常情况下的最长延迟。

### 6.5 Service 层要点

```python
"""M18-06 归档与封存的核心服务逻辑片段。"""

import hashlib
from datetime import datetime
from decimal import Decimal
from typing import List, Optional, Sequence, Tuple

from sqlalchemy import func, select
from sqlalchemy.exc import IntegrityError
from sqlalchemy.orm import Session

from app.models.m18.archive import ArcBatch, EmrSeal
from app.schemas.m18.archive import IntegrityResult


def calc_integrity(
    required_docs: Sequence[str],
    present_docs: Sequence[str],
    hash_mismatched: bool,
    upstream_unavailable: bool,
) -> Tuple[str, List[str]]:
    """M18-CALC-01 病历完整性检查。

    判定顺序不可交换：先看上游可用性，再看缺项，最后才判完整。
    上游不可用时无论其它条件如何都返回 UNKNOWN——把「不知道」
    记成「没问题」，这个标记要保存 15~30 年且事后无法更正。
    """
    required_set = set(required_docs)
    present_set = set(present_docs)
    missing = sorted(required_set - present_set)

    if upstream_unavailable:
        return "UNKNOWN", []
    if missing or hash_mismatched:
        return "INCOMPLETE", missing
    return "COMPLETE", []


def calc_completion_rate(
    complete_count: int,
    incomplete_count: int,
) -> Optional[Decimal]:
    """M18-CALC-06 归档完整率。

    分母为 0 时返回 None 而不是 0——0.00% 的含义是「有一批病历全都
    不完整」，与「这个月没有归档」是完全不同的两件事。
    UNKNOWN 批次既不在分子也不在分母，由调用方单列。
    """
    decided = complete_count + incomplete_count
    if decided <= 0:
        return None
    return Decimal(complete_count) / Decimal(decided)


def calc_content_hash(text: str) -> str:
    """计算病历正文的 SHA-256，返回 64 位小写十六进制。

    铁律 5：同一份病历只有一个 content_hash，M18 计算并固化，
    M07-06 必须原样引用不得重算。
    """
    return hashlib.sha256(text.encode("utf-8")).hexdigest()


def ensure_not_sealed(
    db: Session,
    patient_id: int,
    encounter_id: int,
    record_date: Optional[datetime] = None,
) -> None:
    """封存前置检查。

    查不到封存记录且查询本身异常时，拒绝写入（fail-closed），
    不能因为一次 DB 抖动就放行一次本应被拦下的写入。
    """
    stmt = (
        select(EmrSeal.seal_no)
        .where(EmrSeal.patient_id == patient_id)
        .where(EmrSeal.status == "ACTIVE")
        .limit(1)
    )
    hit = db.execute(stmt).scalar_one_or_none()
    if hit is not None:
        raise BusinessError(
            code="1806016",
            message="该病历已被封存，不可写入",
            http_status=403,
        )


def resolve_reopen(db: Session, batch: ArcBatch) -> str:
    """判定一次重复推送对既有批次的处置方式。

    返回 reopen / replay / reject 三种之一：
      replay  —— 原样返回首次结果，不改数据
      reopen  —— 复用同一批次，推进 reopen_count 并重新校验
      reject  —— 拒绝，调用方必须新建 source_biz_no
    """
    if batch.status in ("RECEIVING", "CHECKING", "CONFIRMED"):
        return "replay"
    if batch.status == "RELEASED":
        raise BusinessError(
            code="1806008",
            message="归档批次已撤销，不可复用，请以新的业务单号重新推送",
            http_status=409,
        )
    if batch.status == "REJECTED":
        if batch.reopen_count >= 3:
            raise BusinessError(
                code="1806007",
                message="该批次重开次数已达上限 3 次，请以新的业务单号重新推送",
                http_status=409,
            )
        return "reopen"
    raise BusinessError(
        code="1806005",
        message="批次状态不允许重新提交",
        http_status=409,
    )


def apply_reopen(db: Session, batch: ArcBatch) -> None:
    """把被拒批次推回校验流程。"""
    batch.reopen_count = batch.reopen_count + 1
    batch.last_reopen_at = datetime.now()
    batch.status = "CHECKING"
    batch.integrity_result = None
    batch.missing_docs = []
    batch.reject_items = []
    batch.reject_reason = ""
    batch.rejected_at = None
    db.add(batch)


async def push_with_idempotency(
    db: Session,
    source_module: str,
    source_biz_no: str,
    build_new_batch,
) -> Tuple[ArcBatch, bool]:
    """P-04 幂等入口。

    先查后插，靠 uk_m18_arc_batch_source 兜住并发：
    两个请求同时查不到既有批次时，后到的那个会撞唯一键，
    捕获 SQLSTATE 23505 后重新查一次并返回既有批次。
    """
    existing = db.execute(
        select(ArcBatch)
        .where(ArcBatch.source_module == source_module)
        .where(ArcBatch.source_biz_no == source_biz_no)
    ).scalar_one_or_none()
    if existing is not None:
        return existing, True

    batch = build_new_batch()
    db.add(batch)
    try:
        db.flush()
    except IntegrityError as exc:
        db.rollback()
        if getattr(exc.orig, "pgcode", None) != "23505":
            raise
        again = db.execute(
            select(ArcBatch)
            .where(ArcBatch.source_module == source_module)
            .where(ArcBatch.source_biz_no == source_biz_no)
        ).scalar_one_or_none()
        if again is None:
            raise BusinessError(code="1806043", message="归档落库失败，请重试")
        return again, True
    return batch, False
```

**`calc_integrity` 的判定顺序为什么不能交换：** 如果先判缺项、后判上游可用性，那么当 M07-06 超时且 M18 侧恰好缺一份文书时，函数会返回 `INCOMPLETE`。但此时「缺」这个结论本身是不可信的——M18 侧可能只是还没同步到那份文书。**只有确认上游全部可用之后，缺项才是真的缺项。**

**`calc_completion_rate` 返回 `Optional[Decimal]`：** 不返回 0，是因为 0 会被上游当成「完整率 0%」渲染成红色告警。返回 `None` 强制调用方处理「无数据」这种情况。

| "1806044" | 400 | doc_types 超过 30 项 | P-10 请求的文书类型超过 30 个 | 分批查询，单次不超过 30 项 |
| "1806045" | 503 | 封存状态查询失败，调用方必须按已封存处理 | P-14 查询数据库或缓存失败，无法判定封存状态 | 调用方必须 fail-closed，按已封存处理并禁止写入 |
| "189001" | 500 | 未预期异常 | 未被上述错误码覆盖的运行时异常 | 记录 trace_id 并联系值班工程师，客户端不要提示堆栈 |

**为什么 HTTP 状态码与业务错误码要分开表达。** 调用方（M05-05、M06-06）写死的降级分支是按 HTTP 状态码分的：4xx 表示「你的请求有问题，改参数重试没用」，5xx 表示「我这边出问题，你可以按自己的节奏重试」。如果所有业务错误都返回 200 + 非 0 code，M05 的重试计数会把「参数错了」也当成「服务抖了」重试五次然后置 FAILED，运维看到的是「M18 不可用」，实际是上游传了错参数。两类错误必须走不同的门。

**为什么 P-14 的失败单独占一个错误码。** `"1806045"` 与 `"1806004"`（封存记录不存在）看起来都在说「查不到封存」，但调用方的动作完全相反：前者必须 fail-closed（按已封存处理、拒绝写入），后者表示「这份病历确实没有封存记录，可以正常处理」。合并成一个码，等于让调用方靠猜决定要不要锁病历，而猜错的方向是「把一份正被封存的病历放开了写」。

**为什么没有「未知错误」这种兜底业务码。** 兜底码会让实现者在写不出准确判定时随手用它，于是告警面板上 `"189001"` 的数量长期占比 40%，运维看到它就当作噪声跳过。宁可多定义几个具体码，也不留一个能随手续写原因的兜底项。

**`task_m18_archive_check` 的处理链路：**

```
1. SELECT ... FOR UPDATE 取批次，校验 status ∈ (RECEIVING, CHECKING)
2. status → CHECKING，写 check_started_at
3. 取该 encounter 的 required_docs（按 record_type 从配置读）
4. 查 m18_emr_document 得 present_docs_m18
5. 查 M07-06 文书（500 ms 超时）得 present_docs_m07
   - 超时/异常 → upstream_unavailable = True
6. present_docs = present_docs_m18 ∪ present_docs_m07
7. 逐份明细比对 content_hash 与 expected_hash，记录 hash_matched
8. 调 calc_integrity() 得判定结果
9. if UNKNOWN:
     保持 CHECKING，不置 CONFIRMED，不进人工队列之外的任何状态
     写 check_finished_at，结束（不发事件）
   elif COMPLETE:
     status → CONFIRMED，confirmed_at/confirmed_by(0)，发 m18.archive.confirmed
   else:
     status → REJECTED，rejected_at，reject_reason，发 m18.archive.rejected
10. 写 check_finished_at / check_duration_ms
11. 写操作日志 ARCHIVE_CONFIRM / ARCHIVE_REJECT
```

**为什么 `UNKNOWN` 时批次停在 `CHECKING` 而不是单独一个状态：** 状态机里没有「待人工复核」这个状态（共享规范 §13 的 `archive_batch.status` 只有五值，不得自创）。`UNKNOWN` 通过 `integrity_result` 字段表达，配合 `idx_m18_arc_batch_unverified_partial` 部分索引取队列。这样既不违反枚举约束，又能精确索引到待复核批次。

**`task_m18_archive_check_sweep` 的作用：** 兜住 API-34 第 8 步入队失败产生的僵尸批次。扫描条件 `status = 'RECEIVING' AND received_at < now() - interval '2 minutes'`，命中时重新投递 `task_m18_archive_check`。这是「保留批次不删」这个决策的必要配套——不留这样一个兜底扫描，入了不队的批次就真的永远不会被校验了。

**归档批次号的实际格式与 M05 的对齐说明：**

M05-05 的响应原文（`M05住院管理/M05_住院管理_05_出院办理与病历归档_详细设计.md:1091`）里，`m18_archive_id` 的值是 `"AR2026102800033"`。拆开看：`AR` + `20261028`（8 位日期）+ `00033`（5 位流水）。

共享规范 §3.3 的编码表写的是 `AR + yyyyMM + 4位流水`（如 `AR2026100001`，12 字符），而 M05-05 `:1091` 的响应里实际出现的是 `"m18_archive_id": "AR2026102800033"`。规范 `:393` 的强制注要求 M18-06 在本节写明实际使用的格式并说明这处与 M05 的对齐情况。

**本子模块实际使用的格式：`AR` + `yyyyMMdd` + 4 位流水，共 14 字符，正则 `^AR[0-9]{12}$`。**

三点说明：

1. **为什么用日流水而不是月流水：** 归档是高频率业务。月流水 4 位的容量是 9,999，按全院月均 1,240 批次计，`9999 ÷ 1240 ≈ 8.06`，**第八个月就会撞号**，连一年都撑不过。日流水 4 位按日均 130 批计算可支撑 `9999 ÷ 130 ≈ 76` 天不重号，而流水按日重置，所以日容量有 76 倍余量。
2. **与 M05 原文那串的位数差异不影响跑通：** M05 原文 `AR2026102800033` 拆开是 `AR` + `20261028`（8 位日期）+ `00033`（**5 位**流水），**共 15 字符**；M18 生成的是 `AR` + 8 位日期 + 4 位流水，**共 14 字符**。字段声明为 `VARCHAR(32)`，两种长度都装得下。**`m18_archive_id` 在 M05 侧只作为不透明的字符串做等值传递与回显，M05 与 M18 双方都不解析其内部结构，任何一侧都不得对该字段加位数或格式校验**——一旦加了，这一位之差就会让两边互相拒收，而这类失败只在生产环境的某条路径上出现，联调时未必能复现。
3. **为什么 M18 不跟着 M05 用 5 位流水：** M05 原文那个值是示例数据，不是格式契约。M05 侧真正依赖的是「M18 返回了一个可以原样存回去的字符串」。M18 内部统一 4 位流水，与封存、更正、借阅等其它单号保持同样的位宽，代码里只有一套格式化逻辑；跟着改成 5 位没有任何收益，反而要维护两套宽度。**如果将来 M05 或 M18 有一方想加格式校验，必须先由双方共同确认再统一口径**，届时 M18 只需改一处格式常量，`VARCHAR(32)` 的表结构不用动。

### 8.3 状态流转与「归档被拒 → 补缺陷 → 重新提交」

**本节是本子模块最重要的设计判断，单独成节。**

#### 8.3.1 这条路径为什么必须设计

归档被拒不是终点。真实的业务链路是：

```
M05-05 出院归档 → M18 校验发现缺麻醉同意书 → 批次 REJECTED
      ↓
m18.archive.rejected 事件 → M05 侧显示「归档被退回：缺麻醉同意书」
      ↓
病案室在 P02 看到被拒批次，打电话通知眼科一病区
      ↓
科室医生补签麻醉同意书（在 M07-06 完成签署）
      ↓
病案室在 P02 点「补正后重新推送」
      ↓
M18 重新校验 → COMPLETE → 发 m18.archive.confirmed
```

如果这条路径没设计好，**病案室退回的病历永远补不进去**——那台日间手术的病历就永久停在「归档失败」，而法定保存义务是从病历形成时就开始算的。

#### 8.3.2 唯一键带来的真实冲突

幂等键是 `uk_m18_arc_batch_source (source_module, source_biz_no)`。补正后重新推送时，**M05-05 / M06-06 手里还是同一个 `source_biz_no`**（因为它还是同一次出院、同一次日间手术），于是这次推送会撞上第一次那个被拒批次的唯一键。

#### 8.3.3 两种做法的取舍

| 方案 | 做法 | 代价 |
|---|---|---|
| **方案 A：复用同一批次** | 保持 `batch_no` 不变，`status: REJECTED → CHECKING`，`reopen_count + 1` | 需要引入 `reopen_count` 与上限；`batch_no` 会对应多个版本的明细内容 |
| **方案 B：改动幂等键** | 幂等键改成三元组 `(source_module, source_biz_no, reopen_seq)`，每次重新提交建新批次 | 破坏幂等键的语义（同一个业务单号可以对应多个批次）；M05 侧 `m18_archive_id` 会变化，需要 M05 配合改造；完整率统计要把「同一件事的多次尝试」合并还是分开，没有清晰答案 |

#### 8.3.3 本设计的裁决：**选方案 A——复用同一批次号，把状态从 `REJECTED` 推回 `CHECKING`，`reopen_count + 1`，上限 3 次。**

**三条理由：**

**理由一：业务上是同一件事。** 一次出院只产生一次归档事务。补一份麻醉同意书不改变「这是这次出院归档」这个事实。方案 B 会让 `m18_arc_batch` 里出现三条记录都指向 `source_biz_no='M05-ADM-20261028001'`，审计时问「这次出院到底归档成功了几次」需要聚合才能回答，而方案 A 一行就答完了。

**理由二：`batch_no` 的语义是「这一次归档事务的编号」，不是「这一版归档内容的编号」。** M05 侧把它存进 `m18_archive_id`，用途是「以后要查这次归档的结果，拿这个号去查」。复用同一号之后，M05 拿这个号查到的始终是**最新状态**，这正是它想要的。方案 B 会让 M05 手里那个号变成「历史版本」，得再查一次才知道最新状态，等于把状态同步的负担推给了调用方。

**理由三：上限 3 次就足够，且不会掩盖问题。** 一次性缺 3 份文书需要补 3 轮的情况几乎不存在——补正是一次性提交全部缺失文书的。3 次上限的价值不是「允许补 3 次」，而是「让第 4 次必须有人介入」。第 4 次重新推送返回 `"1806007"` 时，病案室必须找医务科，由医务科判断是该新建批次还是查清为什么补了 3 次还缺。

**上限的代价必须写清楚：** 达到 3 次上限后，M05/M06 必须用新的 `source_biz_no` 重新推送。这要求 M05-05 与 M06-06 在收到 `"1806007"` 错误时有明确处理——**新建一个 `source_biz_no` 并重新推送**。这个改造点必须在联调时验证，否则第 4 次推送会一直失败。写进验收 AC-47。

#### 8.3.4 与 `RELEASED` 的处理为什么不同

| 状态 | 能否复用 | 理由 |
|---|---|---|
| `REJECTED` | **能**（≤3 次） | 同一件事没做完。`batch_no` 与内容仍然对应同一次出院 |
| `RELEASED` | **不能** | 声明撤回，事实变了。总纲 §4.3 原文：「如果允许在原批次上重来，新批次的 `batch_no` 还是旧的，M05 那边 `m18_archive_id` 没变而归档内容变了，账实不符。」 |
| `CONFIRMED` | 不能回退 | 已发 `m18.archive.confirmed`，M05 可能已经把「归档成功」推给患者端。汇总 G-07 |

一句话区分：**`REJECTED` 是「这件事还没做完」，`RELEASED` 是「这件事被撤回了」。** 前者继续做，后者重开一张。

### 8.5 计算规则与舍入

| 计算 | 规则 | 舍入 |
|---|---|---|
| 完整性判定 | 见 3.4.1，顺序不可交换 | 不涉及 |
| 完整性得分 | `present / required × 100`，一位小数 | 四舍五入保留 1 位；`required = 0` 时返回 `NULL` |
| 归档完整率 | `complete / (complete + incomplete)` | 存储 `NUMERIC(10,6)` 不舍入；展示四舍五入到 2 位小数 |
| 哈希 | SHA-256 小写十六进制 | 不涉及 |
| 校验耗时 | `check_finished_at - check_started_at` 的毫秒数 | 取整 |

**「不允许多次舍入」：** 完整率的计算只用未舍入的整数计数算一次，不在中途舍入。如果先算每天的完整率再平均到月，得到的是「日均完整率」而不是「月完整率」，两者在每天批次数不等时会差出 0.1~0.5 个百分点。

### 8.7 并发控制

| 场景 | 手段 | 理由 |
|---|---|---|
| 同一幂等键并发推送 | 唯一索引 + 捕获 `SQLSTATE 23505` 后重查 | 不依赖 Redis 分布式锁，锁丢了会重复建批次 |
| 批次状态流转 | `SELECT ... FOR UPDATE` + Redis `m18:lock:batch:{batch_no}` | DB 行锁是最终保证，Redis 锁只是为了减少锁竞争 |
| 同一病历并发提更正 | `m18:lock:amend:{record_id}` + `uk (record_id, seq_no)` | 序号用 `MAX(seq_no) + 1` 算出，并发下会撞号，唯一键兜底 |
| 封存生效与并发写入 | 数据库触发器 | 应用层锁在跨进程场景下不可靠 |
| 单号生成 | Redis `INCR` | 数据库序列拼日期跨零点会重号 |

### 9.4 安全措施

#### 9.4.1 防篡改

| 措施 | 实现 | 生效时机 |
|---|---|---|
| **哈希固化** | 病历 `FINALIZED` 时计算 `content_hash = SHA256(正文)` 并写入 `m18_emr_record.content_hash` | 定稿瞬间，同一事务内 |

**各接口的降级语义（共享规范 §8A.2）：**

| 接口 | `degraded = false` 的前提 | 降级时返回什么 | 失败时返回什么 |
|---|---|---|---|
| **P-04** | ①批次落库成功 ②幂等键占用成功 ③异步校验任务入队成功，三者全部成功 | 200 + `status=RECEIVING` + `degraded=true` + `degraded_sources` 写失败环节；批次保留，由 `task_m18_archive_check_sweep` 兜底重投 | 5xx + `"1806043"`，调用方按 M05 AC-25 重试 |
| **P-10** | M18 侧与 M07-06 都给了确定结论 | 200 + `result=UNKNOWN` + `data_quality=UNKNOWN` + `missing_types=[]` + `unknown_types` 列出无法判定的类型 + `degraded=true`；**绝不默认成「不存在」或「存在」** | 5xx（参数错误除外） |
| **P-14** | 查到了确定的封存状态 | — | **fail-closed：必须返回非 0 错误码 `"1806045"`，绝不返回 `sealed=false`** |

**P-04 的 `degraded` 判定为什么这么严：** 如果 M18 返回「看起来正常」的 200 但批次实际没落库，调用方会以为归档成功，**而病历永远进不了病案库，法定 15 年保存义务无法履行**。三步全成功才允许 `degraded=false`。

**P-10 为什么降级而不是失败：** `M05住院管理/M05_住院管理_06_住院病案首页_详细设计.md:201` 原文「M18 文书存在性 | 首页关联文书 | 降级 | **不阻塞首页**」。调用方的降级分支是「不阻塞首页」，所以它需要的是「知道这次判断不了」，而不是「接口挂了」。返回 200 + `data_quality=UNKNOWN` 让 M05 走「不阻塞」分支并标记首页为「待复核」。

**P-14 为什么必须 fail-closed：** 返回 `sealed=false` 等于告诉调用方「没封存，你可以改」。如果服务异常导致查不到封存记录，这个返回值会让 M07 往一份处于医疗纠纷封存中的病历里写入内容——**这是本子模块最严重的一类事故**。返回非 0 错误码时，调用方（M07/M05/M09）的统一降级分支是「按已封存处理并拒绝写入」。

**不允许 200 + 空 `data` 表达「无权限」：** 三个内部接口都是权限前置的，无权限一律 403 + 非 0 错误码。封存期病历的访问尤其如此——返回 200 + 空会让调用方把它当成「这份病历不存在」。

#### 11.4.1 扫描件真实取件校验（对象存储探针）

`m18_arc_paper_scan` 里只存 `object_key` 与 `content_hash`，扫描件的文件本体在对象存储，不在数据库。这就带来一个哈希校验查不出来的失效模式：**库里的 hash 与库里的 hash 做比对永远一致，哪怕对象存储里那个对象早就没了。** 如果运维没配生命周期策略，或者误配成「30 天后删除」，`SCAN.VERIFY.BATCH` 那条比对会全部通过，而文件其实已被删除。这个错误在日常使用中完全不暴露——没有人天天去调阅三年前的病历，等到医疗纠纷要取证时才发现原件没了，此时已经无法补救。

所以需要一条**周期性真实取件校验**，它校验的不是「两个 hash 是否一致」，而是「对象存储上这个 key 现在还能不能取到、取回来算出来的 hash 与登记的是不是同一个」：

| 项 | 取值 | 说明 |
|---|---|---|
| 调度 | Celery Beat 每日 03:20 执行 `task_m18_paper_scan_probe` | 排在留存期迁移（04:30）之前，避免迁移把尚未探针过的对象迁走 |
| 抽样 | 每日抽全量的 **1%**，且**每周日全量抽 100 件** | 1% 覆盖日常漂移（按 3 年 86 万页、约 4.3 万份扫描件计，日均约 43 份）；周日 100 件保证长期未命中的冷数据每月至少被摸一次 |
| 抽样权重 | 按 `verify_age_days` 降序优先，其次随机 | **优先抽最久没被探针过的**，否则随机抽样在 4 万份里会反复命中同一批热数据，冷数据永远抽不到 |
| 校验内容 | ①对象存在（HEAD 或 GET）②取回字节流现算 SHA-256 ③与 `content_hash` 比对 ④与 `scan_status` 比对 | **必须真的 GET，不能只做 HEAD**——HEAD 只能证明对象存在，证明不了内容没被换掉 |
| 通过时 | 更新 `last_verified_at` / `verify_age_days = 0` | `verify_age_days` 由每日重算任务整体刷新 |
| 失败时 | `probe_status = 'MISSING'` 或 `'HASH_MISMATCH'`，写 `m18_arc_oper_log`（`oper_type = 'SCAN_PROBE_FAILED'`），告警 | 两种失败分开记：`MISSING` 是对象没了（生命周期配错、误删），`HASH_MISMATCH` 是对象被改过（这个更严重，等同物证被篡改） |
| 熔断 | 单日失败率 > 10% 立刻停止后续探针并升级 | 大面积失败通常是对象存储不可用或凭据问题，继续跑只会把 `failed` 计数刷满并淹没真正的单点故障 |

**为什么这条指标必须是 CRITICAL 而不是 WARN。** 其他监控指标超阈值代表「性能退化」或「功能异常」，都可以事后修复；`m18_paper_scan_probe_failed_total` 为 0 以上的含义是**某一份法律证据已经不存在了**，且不可通过重跑任务恢复——除非对象存储有独立备份。它和 `m18_retention_migrate_verify_failed_total` 是同一个严重级别，但后者至少还能中止迁移，前者只能事后追溯影响面。

**为什么必须有 `m18_paper_scan_last_probe_age_hours` 这条独立指标。** 上面两个失败计数只在探针**跑起来且失败**时才会动。如果探针任务本身因为队列阻塞或 Beat 未启动而根本没跑，失败计数会安静地停在 0，看上去一切正常。这条年龄指标就是用来区分「探针跑了且全部通过」与「探针压根没跑」——**沉默本身就是一种故障，需要一个专门度量它的数字。**

**`m18_paper_scan_mismatch_total` 与本节的区别。** 该指标（WARN）统计的是「登记扫描件时，调用方报的 hash 与 M18 现算的 hash 不一致」，属于**入库前**的即时校验失败；本节描述的是**入库后**的周期性复验。两者一个是「新件不干净」，一个是「老件不见了或被换了」，故障原因与处置动作完全不同，不能合并成一个指标。

**`m18_seal_status_error_total` 为什么是 CRITICAL 而不是 WARN：** 这是 fail-closed 接口，每返回一次非 0 错误码，就意味着有一个调用方被拒绝写入或被拒绝读取。单次是正常的（确实有服务异常），但持续出现就说明封存状态查询本身出了问题，此时整个系统的病历写入全部被拦截——业务会停摆。

## 附录 E 术语表

| 术语 | 含义 |
|---|---|
| 归档 | 一次就诊或一次日间手术的病历进入病案库的过程 |
| 封存 | 在医疗纠纷、司法取证等场景下锁定病历，使其不可写入 |
| 更正 | 已签署病历的追加修改方式，原记录一字不动 |
| 作废重开 | 已签署病历的另一种修改方式，旧件作废、新建一份 |
| `UNKNOWN` | 完整性无法判定的三态之一，与「不完整」严格区分 |
| 幂等键 | `(source_module, source_biz_no)`，保证重复推送不建多批次 |
| 重开 | 被拒批次补正后推回校验流程，计数上限 3 |
| 抽样校验 | 留存期迁移后按 100 份抽样比对哈希，不过则不删除 |
| WORM | Write Once Read Many，对象存储的只读存储模式 |
| fail-closed | 失败时向更严格方向处理（拒绝写入而非放行） |
| 归档完整率 | `COMPLETE / (COMPLETE + INCOMPLETE)`，`UNKNOWN` 不进分子分母 |
