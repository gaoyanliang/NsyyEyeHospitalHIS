## 文档四条铁律

本文件的每一张表、每一条约束都服从下面四条铁律。它们不是写作风格要求，而是**违反即返工**的硬约束。

| # | 铁律 | 在本文件中的具体落地 |
|---|---|---|
| 1 | **数量口径三处一致** | 「**合计：10 张表**」声明 = 第 1 章表清单 10 行 = `### 4.2` ~ `### 4.11` 十个 `### 4.x 表：` 标题 = 详细设计第 4 章指引块声明的 10 张 |
| 2 | **M18 只做内容与知识，不做操作** | 本子模块**没有**任何业务写表之外的越界表；`m18_idx_search_doc` 是 `m18_emr_record` 的**派生索引**，不是病历正文的第二份存储（正文永远只有一份，在 `m18_emr_record`） |
| 3 | **PostgreSQL 16** | 使用 `tsvector` + GIN、`pg_trgm`、生成列、部分唯一索引、`JSONB`、声明式分区；无任何 MySQL / Oracle 专有语法 |
| 4 | **病历正文不进索引表** | `m18_idx_search_doc` **只存二元组向量与摘要，不存正文全文**；`m18_idx_search_log` 的 `hit_summary` 存脱敏摘要（`张**`），**绝不存正文片段**。这条是「索引表被拖库不等于病历泄露」的唯一保证 |

> **为什么第 4 条要单独立为铁律：** 索引表的访问频次远高于正文表（检索是高频操作），且索引表的备份策略通常比正文表宽松。如果把正文塞进索引表，等于在「高隐私」（M02 `:758`）数据旁边开了一个低防护等级的副本。**判据：任何能从索引表还原出正文内容的字段，都不许存在。**

| 序号 | 表名 | 中文名 | 用途 | 预估行数 |
|---|---|---|---|---|

| 4.10 | `m18_idx_metric_def` | 自产指标定义 | **M22 没有的**病历维度指标的口径定义（`RZ07xxx`），含九要素与「为什么不复用 M22」 | 极小（约 60） |

**合计：10 张表**

### 1.1 为什么是这 10 张

本子模块的建议表数是 8~10 张。选到上限 10 张，是因为下面三组职责**不能合并**，合并会让「一张表只表达一件事」失效：

| 拆分对 | 合并会发生什么 | 结论 |
|---|---|---|
| `m18_idx_search_log`（搜了什么）vs `m18_idx_access_log`（看了什么） | 两者的生命周期与保留期完全不同：检索日志保留 1 年（量大、价值随时间快速衰减），访问日志保留 **10 年**（是医疗纠纷举证时「谁在什么时候看过这份病历」的唯一证据）。合并后只能取两者较长的保留期，导致检索日志的存储成本翻 10 倍 | 必须拆 |
| `m18_idx_quality_metric`（质量指标）vs `m18_idx_case_stat`（病案量指标） | 前者的分母是「进入书写窗口的病历数」，后者是「实际发生的人次数」，两者的口径来源不同（前者引用总纲 `M18-CALC-03`/`06`，后者来自 M18-06 归档口径）。合并在一个 `metric_code` 命名空间里，必然出现「同一列既存率又存量」的类型混乱 | 必须拆 |
| `m18_idx_metric_def`（自产指标定义）vs `m18_idx_config`（配置） | 指标定义是**版本化**的（口径改了必须新增版本、历史结论不重算），配置是**可原地修改**的。前者需要 `version_no` + `effective_from` 与唯一约束，后者只有一个 `config_value`。合并会让版本约束污染配置表 | 必须拆 |

**反过来，为什么不拆到 12 张：** `m18_idx_search_doc` 的「检索维度冗余列」（`dept_id`/`doctor_id`/`diagnosis_code` 等）没有拆成独立的维度表。理由：检索的**权限过滤必须在 SQL 层**（详细设计 §9.3），权限条件要 join 到维度值；如果维度在独立表，权限过滤要么多一次 join、要么在应用层拼——而后者正是任务书第 3 条明令禁止的做法。冗余在索引表里、随索引一起重建，是这个场景下唯一能保证「过滤与分页同源」的形态。

## 2. 公开列约定

本文件所有表共用下面这组约定，逐表不再重复解释。

| 项 | 约定 |
|---|---|
| 主键 | `id BIGINT GENERATED BY DEFAULT AS IDENTITY`，不用 UUID（BIGINT 索引小、JOIN 快；医疗数据不跨库合并） |
| 时间 | 一律 `TIMESTAMP`（不带时区，全院统一 Asia/Shanghai），**不用 `TIMESTAMP WITH TIME ZONE`** |
| 金额 | `NUMERIC(14,2)`；比率 `NUMERIC(10,6)`；评分 `NUMERIC(5,1)`；**禁用浮点类型**（一律用定长数值类型，金额与比率不得用二进制浮点） |
| 枚举 | `VARCHAR(32)` + `CHECK`，值全大写英文下划线 |
| 逻辑外键 | `{对象}_id BIGINT`，**物理上不建 `FOREIGN KEY`**（跨子模块引用一律逻辑外键，用索引 + 应用层保证） |
| 文件大小 | `file_size` 用 `BIGINT` 存字节数，不用浮点 |
| 快照 | `{对象}_snap JSONB`，结构示例见附录 D |
| 注释 | 每张表与关键字段必须有 `COMMENT ON` |

### 2.1 十张表都不设 `is_deleted`

数据结构汇总 §2.4 第 3 条规定：`is_deleted` 只给**可变配置类表**。本子模块十张表里：

| 表 | 性质 | 是否可删除 | `is_deleted` |
|---|---|---|---|
| `m18_idx_search_doc` | 派生索引（可由正文重建） | 可删（重建时清空） | **不设**，用 `doc_status` 表达 `ACTIVE`/`DELETED`/`VOIDED` |
| `m18_idx_search_log` | 审计留痕 | **不可删** | 不设 |
| `m18_idx_search_perm` | 可变配置 | 可停用 | **设**，用 `is_deleted` + `perm_status` 双表达 |
| `m18_idx_access_log` | 审计留痕 | **不可删** | 不设 |
| `m18_idx_case_stat` | 快照 | 可重算覆盖 | 不设 |
| `m18_idx_quality_metric` | 快照 | 可重算覆盖 | 不设 |
| `m18_idx_doctor_workload` | 快照 | 可重算覆盖 | 不设 |
| `m18_idx_export_task` | 任务单 | **不可删**（导出即留痕） | 不设，用 `task_status` 表达 |
| `m18_idx_metric_def` | 可变配置 + 版本 | 可停用 | **设** |
| `m18_idx_config` | 可变配置 | 可停用 | **设** |

**判据：一张表如果承载「谁在什么时候做了什么」的举证责任，就不设 `is_deleted`。** 检索日志、访问日志、导出任务这三张表都是纠纷时会被调取的对象——一条被逻辑删除的「某医生上周查看了某患者的病历」在法庭上没有证明力。

## 3. 分区表模板（本子模块只有 `m18_idx_search_log` 分区）

数据结构汇总 §4 把 `m18_idx_search_log` 归为「月分区 + **必须建 DEFAULT 分区**」。完整 DDL 在 4.3 节，此处先固定模板形态，避免各表写法漂移。

```sql
CREATE TABLE m18_idx_search_log (
    id             BIGINT GENERATED BY DEFAULT AS IDENTITY,
    search_no      VARCHAR(32) NOT NULL,
    created_at     TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE m18_idx_search_log_p202610 PARTITION OF m18_idx_search_log
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

CREATE TABLE m18_idx_search_log_p202611 PARTITION OF m18_idx_search_log
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

CREATE TABLE m18_idx_search_log_default PARTITION OF m18_idx_search_log DEFAULT;
```

### 3.1 三条分区硬规矩

| # | 规矩 | 违反的后果 |
|---|---|---|
| 1 | 分区表的**主键必须包含分区键** `created_at` | PostgreSQL 要求分区表的主键/唯一约束包含分区键，否则建表直接失败 |
| 2 | **必须建 DEFAULT 分区** | 分区预建任务漏跑时，`2026-12-01 00:00` 之后的 INSERT 会直接报错「no partition of relation found for row」。有 DEFAULT 分区时数据落进 default 分区，业务不中断，监控告警还能补救 |
| 3 | 分区键**一经选定不可更改** | 改成「按天分区」需要重建全表，而本表只保留 1 年（约 300 万行），重建不划算。真要改，走新建表 + `INSERT ... SELECT` + 原子换名 |

### 3.2 为什么只有检索日志分区

| 表 | 是否分区 | 理由 |
|---|---|---|
| `m18_idx_search_log` | **是（月分区）** | 年增约 300 万行，且**只保留 1 年在线**。分区使得「删除 1 年前的日志」变成 `DROP TABLE m18_idx_search_log_p202510`（秒级）而不是 `DELETE ... WHERE created_at < ?`（几十万行、长时间锁、大量膨胀） |
| `m18_idx_access_log` | 否 | 年增约 60 万行，3 年 180 万行，单表完全可承受；且保留期 10 年，分区带来的「快速删除」价值为 0（本来就不删） |
| `m18_idx_search_doc` | 否 | 117 万行，且**唯一键是 `record_id`**。分区表的唯一约束必须包含分区键，若加上 `created_at` 就会让「一份病历只有一个索引文档」这条约束失效——这是数据结构汇总 §4 里「病历事实表不分区」的同一条理由 |
| `m18_idx_export_task`、`m18_idx_case_stat`、`m18_idx_quality_metric`、`m18_idx_doctor_workload` | 否 | 行数都在 10 万以下 |
| `m18_idx_search_perm`、`m18_idx_metric_def`、`m18_idx_config` | 否 | 配置类，千行级 |

> **判据：分区的价值 = 「能快速丢弃」。** 一张只增不删的表（访问日志）分区只是徒增复杂度；一张删了还要能按条件查的表（检索日志按月份清理）才值得分区。

> **为什么连 `m18_idx_search_doc.record_id → m18_emr_record.id` 也不建物理外键：** `m18_emr_record` 是 M18-02 首建、被 5 个子模块共用的表。若本子模块对它建物理外键，就等于让 M18-02 的表结构被 M18-07 的迁移依赖锁死——M18-02 改主键或重建表时会被外键阻塞。**跨子模块引用一律逻辑外键**，这是数据结构汇总 §1.3 的既定裁决。

### 4.2 表：`m18_idx_search_doc`（病历检索索引）

**用途：** 每份**可检索**病历一行的派生检索文档。承载三件事：①`search_vec tsvector` 二元组向量供全文检索；②各项**检索维度冗余列**（科室、医生、诊断、手术、日期、病历类型）供多维检索与权限过滤；③`summary_masked` 脱敏摘要供列表页直接返回，**避免列表页去回表读正文**。

**写入方：** M18-07 索引服务（消费 `emr.record.finalized` / `emr.record.voided` 事件 + 每日全量对账任务）。**只读方：** M18-07 检索服务、M22（经 M18-07 接口，不直读表）。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |
| record_id | BIGINT | N | - | 逻辑外键 → `m18_emr_record.id`，**一份病历只能有一个索引文档** |
| record_no | VARCHAR(32) | N | - | 病历号，冗余（列表页直接返回，免 join） |
| encounter_id | BIGINT | N | - | 就诊 ID，逻辑外键 → M07 会话 |

**分区策略**

**不分区。** 理由见 §3.2：`record_id` 是唯一键，且 117 万行单表可承受。

**设计说明**

1. **为什么 `search_vec` 用二元组而不是来词：** 眼科专有名词（「视觉诱发电位」「角膜内皮细胞密度」「房角镜下分级」）在通用中文词典里切不出来，用 `simple` 配置加 `zhparser` 在很多部署环境装不上。二元切分把「角膜内皮」切成「角膜 / 膜内 / 内皮」，查询时同样切，召回率稳定。**代价是索引体积放大 3~5 倍与邻接噪声**（搜「角膜」会命中「膜角」），这个代价在详细设计 §7.2 用 `pg_trgm` 精确通道补足。
2. **为什么摘要要脱敏后存起来：** 列表页一次返回 20 条，如果每条都回表读 `m18_emr_record` 算摘要，20 次随机 IO 且**必然把正文读进应用内存**——而正文是「高隐私」，读一次就该记一条访问日志。存脱敏摘要后，列表页只查索引表，**一次正文访问都不发生**，访问日志只在用户点进详情时才写。这是权限设计（详细设计 §9.3）能成立的物理前提。
3. **为什么 `special_flag` 不放在 `m18_emr_record` 上：** 特殊模块标记是**检索侧的管理属性**（决定谁能搜到），不是病历内容属性。放进正文表会与 M18-02 的首建 DDL 产生跨子模块写冲突，且正文表对 `special_flag` 的修改会触发「签署后禁改」触发器误报。
4. **为什么 `diagnosis_codes` 用数组而 `diagnosis_code` 又冗余一个：** 数组供「并发多诊断」的 `&&` 检索（走 GIN）；单值列供「主诊断排序展示」与列表页展示。两者在同一个写入事务里由索引服务一起填，不会不一致。
5. **为什么 `index_version` 是普通列而不是配置：** 分词函数一旦调整，必须能区分「哪些文档是按旧函数建的」。全量重建是按 `index_version < 当前值` 分批捞的，如果放配置表就查不出待重建的文档集合。
6. **为什么 `content_hash` 冗余到本表：** 检索结果需要让用户「验证这份病历没被篡改」。若每次点击都回 `m18_emr_record` 查 hash，就又回到「列表页读正文表」的问题。hash 是 64 字节的定长串，冗余成本可忽略，收益是列表页能直接标「哈希已验证」。

### 4.3 表：`m18_idx_search_log`

**用途：** 每一次检索请求落一行，记录「谁在什么时候用什么条件检索了什么、命中多少、看了哪些」。这是**病历检索的唯一审计凭证**——病历是最高隐私等级数据（M02 `:758` 定级「高隐私」），「谁查过这个病人的病历」必须能逐条回答。同时它是检索性能优化与命中率分析的数据源。

**设计说明**

1. **`hit_count` 与 `returned_count` 分开记。** `hit_count` 是权限过滤后的总数（与接口返回的 `total` 一致），`returned_count` 是本页实际返回数。两者不等只说明分页，不说明权限。真正体现权限的是 `filtered_count`。
2. **`filtered_count` 只记数字，不记明细。** 如果记录「被过滤掉的是哪 18 条」，那么这份日志本身就成了一份泄露源——有日志读权限的人可以从中还原出「不该看的那 18 条病历 ID」。因此只留计数，且该列不对业务角色开放查询。
3. **`perm_snapshot` 存 JSONB 而不存外键。** 权限配置随时会变（科室调整、角色调整），如果只存 `perm_id`，三个月后复核「他当时为什么能看到」时会得到「按今天的权限算他不该看到」这种无解结论。快照把判定依据固化在当时。
4. **`keyword_raw` 入库前必须脱敏。** 用户可能直接在检索框里粘一个手机号或身份证号，日志不能原样留存。脱敏规则与 `m18_idx_search_doc` 摘要字段一致（`fn_m18_mask_phone` / `fn_m18_mask_idcard`）。
5. **`index_used` 是为了发现「索引悄悄失效」。** 全文检索最常见的事故是 GIN 索引因为某种原因没被选中，查询退化成顺序扫描——功能正常但慢 50 倍。把 `EXPLAIN` 里的索引名记下来，一旦某天的 `BIGRAM` 检索 `index_used` 全是空，运维能立刻发现。
6. **分区键用 `created_at` 而不是 `log_no` 里的日期。** 日志可能跨零点补偿写入，日期字符串与物理时间不一致；用 `created_at` 保证数据落在正确的物理分区里。

**量级估算**

| 项 | 估算 | 说明 |
|---|---|---|
| 日均检索次数 | 约 1,200 次 | 病案室 20 人 + 临床医生偶发检索 + 内部服务调用 |
| 年增行数 | 约 43.8 万行 | 1,200 × 365 |
| 行均宽度 | 约 700 B | 含 `query_cond` / `perm_snapshot` 两个 JSONB |
| 3 年累计（若全留） | 约 131 万行 / 约 0.9 GB | 实际只留 1 年，在线约 0.3 GB |
| 单分区规模 | 约 3.6 万行 / 约 25 MB | 月分区，索引与数据各约一半 |

**分区策略**

不分区。预计全院配置条目 **不超过 800 行**（医生约 60 人 + 角色约 20 个 + 科室约 15 个 + 兜底 1 条 + 临时授权少量），全表扫描成本低于任何索引开销，分区毫无意义。

**设计说明**

1. **这张表的存在本身就是「权限过滤在 SQL 层」的前提。** 应用层过滤方案不需要权限配置表——它把权限硬编码在代码里。一旦要支持「张医生临时能查全院 3 天」，就得改代码发版。有了这张表，权限是数据，可以被审计、被版本化、被到期自动回收。
2. **`DEFAULT` 兜底行必须有且只有一条。** 权限判定的算法是「个人 → 角色 → 科室 → 兜底」逐级取第一个命中，兜底行保证任何用户在任何情况下都有一个确定的范围。**没有兜底行时，未配置的用户会拿到空范围——而空范围与「无限制」在 SQL 拼装里容易写成同一个分支，这是最危险的一类 bug。** 因此 `subject_id = 0` 的哨兵行在初始化脚本里强制插入。
3. **`allow_content_view` 与列表可见性分离。** 列表页返回脱敏摘要（`张**`、`138****5678`），只要 `scope_level` 覆盖就能看到；点开看正文需要 `allow_content_view = TRUE` 并额外写一条 `m18_idx_access_log`。这样「能检索到」与「能读全文」是两道门，绝大多数岗位（如病案室编码员）只需要第一道。
4. **`allow_export` 蕴含 `allow_content_view`（数据库强制）。** 允许导出但不允许看正文是自相矛盾的配置——导出文件里必然包含正文，否则导出毫无意义。这条组合约束把矛盾配置在写入时就拦掉，而不是等到导出时才发现。
5. **`allow_special_flag` 必须双人审批（`approve_by <> grant_by`）。** 特殊模块病历（性病相关眼病、HIV 相关眼病）的泄露后果远重于普通病历。双人审批不是为了防坏人，而是为了让「谁批的」这件事有记录——出事时能定位到决策链。
6. **`expire_at` 支持临时授权自动失效。** 司法调证通常是「3 天内提供指定时间段病历」，授权到期后由 APScheduler 每小时扫描置 `EXPIRED`，不需要人工回收。**没有到期时间的高权限授权，在实践中会永久留存**——这是权限系统最常见的腐化方式。

**量级估算**

| 项 | 估算 |
|---|---|
| 配置条目总数 | 约 120 行（医生 60 + 角色 20 + 科室 15 + 兜底 1 + 临时授权约 20） |
| 行均宽度 | 约 600 B |
| 全表规模 | 约 70 KB |
| 年增行数 | 临时授权约 200 行/年（到期后置 `EXPIRED` 保留留痕，不删除） |

### 4.5 表：`m18_idx_access_log`

**用途：** 记录「谁在什么时候打开了哪一份病历、看了哪些段落、做了什么事」。与 `m18_idx_search_log`（记录「查」）区分：本表记录「**看**」。每一次正文详情查看、每一次导出、每一次打印、每一次封存期调证，都在本表留一行。

**为什么必须与检索日志分开：** 一次检索可能命中 100 条，用户只点开其中 2 条。如果只有检索日志，事后审计只能回答「他检索了关键词 X」；有了本表才能回答「**他实际打开了患者 A 和患者 B 的全文**」。医疗纠纷中最常被追问的正是后者。

    ADD CONSTRAINT ck_m18_idx_access_log_pushed
    CHECK ((audit_pushed = FALSE AND audit_pushed_at IS NULL)
           OR (audit_pushed = TRUE AND audit_pushed_at IS NOT NULL));

**分区策略**

不分区（**例外说明**）。虽然本表年增约 50 万行（见下表），但它是**审计证据**，保留期与病历本身挂钩（门诊 15 年、住院 30 年），不存在「热数据 3 年 + 归档」的分区下线场景；且查询模式固定为「按 `patient_id` 或 `record_id` 精确命中 + 时间范围」，B-Tree 索引即可满足，按时间分区反而让「查某人 15 年内的全部访问记录」变成 180 个分区的扫描。

> **与 `m18_idx_search_log` 的差别：** 检索日志是**运维数据**（保留 1 年，可整分区下线），访问日志是**合规数据**（长期保留，不可下线）。这条差别决定了前者分区、后者不分区。

**设计说明**

1. **本表与 `m18_idx_search_log` 的分离，是「查」与「看」的分离。** 合并成一张表会造成两个问题：一是检索日志要保留 1 年、访问日志要保留 15~30 年，保留期冲突；二是检索日志量大（年 43.8 万）会淹没访问日志（年 5 万），按患者查询访问轨迹时要在十倍噪声里过滤。
2. **`patient_id` 索引是本表最重要的索引。** 患者投诉「我的病历被谁看了」是最常见的维权诉求，也是《个人信息保护法》赋予患者的权利。这个查询必须快——**如果回答这个问题需要 30 秒，实践中就不会有人问，等于这项权利不存在**。
3. **`content_hash_ref` 记录访问那一刻的 hash。** 病历可能被追加更正（`m18_emr_amendment`），正文本身不变但版本会变。记录 hash 使得「他当时看的是哪一版」可被证明，这在纠纷中是关键证据。
4. **`sections_viewed` 记录到段落级。** 只说「他打开了这份病历」不够——如果他用仅展开了「诊断文本」而从没展开「现病史」，说明他只关心诊断。段落级粒度让审计能回答「他关注的是哪部分」，也用于发现「批量快速翻看」的异常行为。
5. **`access_reason` 是必填（对正文查看）。** 这一条会带来操作摩擦，但病历访问没有理由记录时，审计只能回答「有人看了」而不能回答「为什么看」，后者才是纠纷时真正需要的。**摩擦应当存在**：它让随机的好奇心止步。
6. **`audit_pushed` 支持失败补偿。** M02 审计中心（U-16，P95 ≤ 30ms）不可用时，访问日志仍然本地落库，`audit_pushed = FALSE`，由 APScheduler 每 5 分钟批量重推。**不能因为审计中心挂了就拒绝查看病历**——急诊会诊时医生必须能看到病历；但也不能不推，所以用「本地先落 + 异步补推」。

**分区策略**

不分区。按 `(period_type, period_key, dept_id, record_type)` 组织，全院 15 个科室 × 4 类病历 × 每日 1 行 → 日粒度年增约 2.2 万行，月/季/年粒度各行数量级更小，**10 年累计不超过 30 万行**。单表完全可承受，且查询总是带 `period_key` 精确条件，B-Tree 足够。

**设计说明**

1. **本表是「封存期间统计可用」这一承诺的落地物。** 总纲 §3.3 明确「封存期间检索统计要用 `m18_idx_*` 只读快照，不能再扫病历正文表」。如果没有这张表，封存一旦生效，统计页面要么报错、要么只能返回全 0——后者更糟，因为它看起来像「这个月没病人」。
2. **`source_status` 与 `source_detail` 是「不静默填 0」的强制手段。** 上游 M09 不可用时，`surgery_count` 不能写 0（那是撒谎），本表规定写**上次有效值并标 `STALE`**，或写 0 但 `source_status = 'PARTIAL'` 且 `source_detail` 注明哪个源超时。页面据 `source_status` 显示灰色角标「数据不完整」。
3. **`avg_los` 用组合约束锁死算法。** 上面的 `ck_m18_idx_case_stat_avg_los` 让「平均住院日 ≠ 床日数 ÷ 出院人数」的行写不进去。没有这条约束，不同刷新任务各自四舍五入，会出现「上下级科室汇总对不上」的经典问题。
4. **`qc_pending_archive_count` 与 `reject_overdue_count` 是总纲点名要求单列的。** 总纲 §3.1 列了病历内容闭环的三个断点，其中 F-02（质控未完成就归档）与 F-03（归档被拒后无下文）要求「在病案统计里单列」。不单列的后果是这两个问题被平均进总量后彻底消失。
5. **`frozen` 与 `freeze_reason` 分离。** 期间结账后统计不应再变，但封存影响期也需要冻结。用布尔 + 原因两列而不是单一状态列，是因为「冻结的理由」在排查「为什么这个月数据不动了」时是第一个要回答的问题。
6. **`dept_snapshot_at` 记录科室树取值时刻。** 科室会合并拆分（眼科门诊 → 白内障门诊 + 屈光门诊），如果每次刷新都按当天科室树算，历史期间的数据会在科室调整后自动「重分配」，导致去年的报表今年看数字变了。记录取值时刻让「这份数字是按哪个版本的科室树算的」可查。

| 日粒度行数 | 15 科室 × 4 类型 × 1 = 60 行/日，年增约 2.2 万行 |
| 月粒度行数 | 60 行/月，年增 720 行 |
| 季/年粒度 | 合计年增不足 300 行 |
| 行均宽度 | 约 500 B |

**唯一索引说明**

`doctor_id` 可为空，而 PostgreSQL 的唯一索引把多个 NULL 视为互不相等，会导致同一期间同一科室同一指标的「科室级行」重复插入。因此该唯一约束改用表达式索引：

```sql
CREATE UNIQUE INDEX uk_m18_idx_quality_metric_key
    ON m18_idx_quality_metric (
        period_type, period_key, dept_id,
        COALESCE(doctor_id, 0),
        metric_code
    );
```

> 用 `COALESCE(doctor_id, 0)` 而不是 `NULLS NOT DISTINCT`（PostgreSQL 15+ 支持），是因为前者在任意版本上行为一致；`doctor_id` 真实值从 1 起，0 不会与真实 ID 撞号。

**分区策略**

不分区。指标数量约 25 个（引用 M22 约 12 个 + 自产约 6 个 + 总纲模型 3 个 + 其他），维度为 15 科室 × 12 个月 → 年增约 4.5 万行（科室级）+ 医生级约 60 人 × 8 个个人指标 × 12 月 ≈ 5,800 行，合计年增约 5.1 万行，10 年约 51 万行。查询固定带 `period_key` 与 `metric_code`，B-Tree 足够。

**设计说明**

1. **`metric_source` 三值枚举是本表的核心。** 它把「这个数字是我们自己算的」与「这个数字是引用 M22 的」在数据层面区分开。页面渲染时，`M22` 来源的指标必须显示「数据来源：M22 指标中心」并可点击跳转；`M18_CALC` 来源的必须显示「口径：总纲 M18-CALC-03」。**没有这一列，用户无法判断「两个页面数字不一样时该以哪个为准」。**
2. **`calc_model_ref` 让「及时率不得另算一套」成为可验证的约束。** 病历及时率只有一个模型（`M18-CALC-03`），如果某个刷新任务偷偷写了另一套算法，它的 `calc_model_ref` 要么为空、要么写了别的值，`idx_m18_idx_quality_metric_source` 索引一次就能查出来。
3. **分母为 0 的三条约束是一组。** `denominator > 0 OR metric_value IS NULL` 保证不出现 0/0；`abs(metric_value - ROUND(numerator/denominator, 6)) <= 0.000001` 保证值确实等于算式；两者合起来才能挡住「分母为 0 时手工填 100.0」这类实现（M07-07 `:3129` 就是这个写法）。
4. **`sample_sufficient` 与 `min_sample_size` 用组合约束绑定。** 样本下限取 M22-04 `:546-549` 的分档（出院量类 30、手术类 20、危急值类 10、平均住院日类 30），但下限值本身存列不硬编码，允许按指标配置。约束保证「标了充足但没到下限」这种自相矛盾写不进去。
5. **`gating_level` 三态 + 两条互斥约束。** 全院级不能有 `doctor_id`（否则一个医生名下的行会出现在全院汇总里）；医生级必须有 `doctor_id`。这两条看起来琐碎，但少了它们，`GROUP BY dept_id` 时会把个人指标错误地算进科室合计。
6. **`std_version` 记录 M22 口径版本。** M22 的指标口径是版本化的（`M22_报表与决策支持_01_指标中心与口径管理_详细设计.md:567` 口径版本轨迹 `MV`+编码+版本号）。引用它的指标必须记下当时引的是哪一版，否则 M22 改口径后，历史月份的指标值会失去可解释性。

| 项 | 估算 |
|---|---|
| 科室级指标行 | 15 科室 × 25 指标 × 12 月 ≈ 4,500 行/年 |
| 医生级指标行 | 60 人 × 8 指标 × 12 月 ≈ 5,760 行/年 |
| 年增合计 | 约 5.1 万行（含季度/年度粒度重复计算约 1 万行） |

| 10 年累计 | 约 51 万行 / 约 230 MB |

**设计说明**

1. **本表不是「M07-07 的复制品」，而是它的补集。** 表里**没有**接诊量、手术台次、平均诊时、翻台率——这些 M07-07 §3.1 已经固化。重复统计的直接后果是「两个页面对同一个医生给出两个接诊量」，医生会来投诉，而两个模块都会拿出「我的口径有文档依据」来回踢。本表用「不含哪些字段」来守住这条边界。
2. **`record_in_window` 是整张表的口径支点。** 总纲 `M18-CALC-03` 规定分母只算进入过书写窗口的病历（算例 1104/1200=92.00% vs 1104/1260=87.62%，差 4.38 个百分点）。本表把分子分母都落列，并且用两条约束绑定比率算式——这样「及时率」无法被偷偷改成别的分母。
3. **`timely_rate` 在窗口为 0 时强制 NULL。** 这是从 M07-07 `:3129` 的实现缺陷反推出来的约束：那里的写法是 `if doc["count"] else 100.0`，导致「一份文书都没写的医生文书及时率 100%」。如果本表允许写 100%，绩效排名会把「没干活的人」排在「干了活但迟了的人」前面。数据库层强制 NULL 让这个错误无法复现。
4. **`qc_grade_a + qc_grade_b + qc_grade_c = qc_total` 是一条容易被忽略但很有用的约束。** 它保证「已质控份数」不是一个独立的、可能与分级明细脱节的计数。少了它，某个刷新任务只更新了 `qc_total` 忘了更新分级，数据会静默失真。
5. **`rejected_count` / `rewrite_count` 是 M07-07 完全没有的维度。** 退回重写是病历质量最直接的负向信号，但它发生在质控流程内部，只有 M18 知道。`rewrite_count <= rejected_count` 保证「重写完成数」不会超过「被退回数」这种荒谬数据。
6. **`calc_model_ref` 让「引用总纲模型」可查。** 与 `m18_idx_quality_metric` 同理，本表所有比率列的算法都来自 `M18-CALC-02`/`M18-CALC-03`，写明引用让审计能核对。

**与 M07-07 的口径对照**

| 项 | M07-07 已固化（不重复） | 本表补齐（M07-07 没有的） |
|---|---|---|
| 接诊量 | 是（`:182` §3.1.1） | 否 |
| 手术台次 | 是（`:229` §3.1.3） | 否 |
| 平均诊时 / 翻台率 | 是（`:205`、`:254`） | 否 |
| 文书及时率 | 是（`:250`，分母=总文书） | **否，且口径不同**（本表用 `record_in_window` 作分母） |
| 按时完成病历数 | 否 | **是**（`record_timely`） |
| 甲级/乙级/丙级病历数 | 否 | **是** |
| 退回重写数 | 否 | **是** |
| 缺陷明细与平均质控分 | 否 | **是** |

> **两个「及时率」必须并存且不得混用。** M07-07 的文书及时率是「医生个人绩效视角」（分母是总文书），本表的病历及时率是「病历书写合规视角」（分母是进入书写窗口的病历）。同一个医生同一个月，两个数字必然不同。凡两者同时出现的报表，必须各自标注来源模块与分母口径。

**分区策略**

不分区。年增约 3,000 行（日均约 8 次导出），保留期 3 年（超期由 APCheduler 置 `EXPIRED` 并清理文件，**记录本身保留**）。3 年约 9,000 行，单表完全可承受。

**设计说明**

1. **`query_cond` 快照是本表最有价值的一列。** 事后追责时，「他导出了 2,000 条病历」这句话没有意义，有意义的是「他按什么条件导出了这 2,000 条」。快照把条件固化，即使检索接口的逻辑后来改了，也能复现当时的结果集。
2. **`watermark_text` 在数据库层强制非空（SUCCESS 时）。** 水印的作用不是防止截图——它防不住——而是**泄露发生后能定位到人**。一份打印出来带着「张某某 工号 2041 2026-10-21 导出 EX20261021000123」的表格，拿到哪里都能查出是谁导的。这条约束让「忘了加水印」这种实现疏漏写不进数据库。
3. **`require_approve` 与 `approve_status` 分离。** 前者表示「这次导出按规则需要审批」，后者表示「审批的实际进展」。合成一个字段会导致「不需要审批」与「待审批」无法区分——而前者应当立即执行，后者必须等待。
4. **`ck_m18_idx_export_task_approve_gate` 是关键约束。** 它允许任务在未批准时停留在 `PENDING`/`CANCELLED`/`FAILED`，但一旦进入 `RUNNING` 或 `SUCCESS`，`require_approve` 为真的任务必须是 `APPROVED`。**只靠应用层检查顺序，可以靠「先跑后批」绕过。**
5. **`truncated` 必须与 `max_rows` 联动。** 导出被截断而不标注，是极危险的情形：用户拿到 10,000 行的文件，以为是全部，实际只导出了上限 5,000 行，据此做的统计结论全错。约束保证「标了截断就一定有上限且行数正好等于上限」。
6. **`contains_sealed` + `seal_cert_note` 落实「封存期调证」标记。** 封存期病历可以导出（司法调证恰恰需要），但导出文件必须能一眼看出「这是封存期调证件」，否则与普通导出件混淆后，在诉讼中会成为「医院私自提供病历」的口实。

**量级估算**

| 项 | 估算 |
|---|---|
| 日均导出次数 | 约 8 次 |
| 年增行数 | 约 3,000 行 |
| 行均宽度 | 约 1.2 KB（含 `query_cond` / `perm_snapshot` JSONB） |
| 3 年累计 | 约 9,000 行 / 约 11 MB |
| 文件存储 | 按每次 2 MB 估算，年约 6 GB（**文件存对象存储，不入库**） |

### 4.10 表：`m18_idx_metric_def`

**用途：** 本子模块指标注册表。登记 M18-07 产出的**每一个指标**，并强制标注它的来源：引用 M22 的哪个编码、或自产、或引用总纲哪个计算模型。

**为什么需要这张表而不是把指标写死在代码里：** 任务书第 5 条要求「凡是 M22 已有的指标，必须引用它的编码，不自创」。这条要求在代码里无法验证——只有当指标成为数据行，并带有 `metric_source` 与 `m22_metric_code` 两列时，「有没有偷偷自创一个与 M22 同名不同码的指标」才能被一条 SQL 查出来。

**写入方：** M18-07 指标注册（初始化脚本 + 配置页）

不分区。约 30 行指标定义，是全库最小的表之一。

**设计说明**

1. **`metric_source` + `m22_metric_code` 两列把「引用而不自创」这条要求变成了可执行约束。** 如果有人为「病历及时率」自创一个 `CL_MR_TIMELY_RATE`，`metric_source = 'SELF'`，`self_reason` 里必须写清「M22 无病历及时率指标，M22-07 只有病案首页甲级率 `CL_HOME_QUALITY_RATE`，语义不同」。**这段理由会被永久保留在数据库里，任何后来者都能看到当时的判断依据。**
2. **`ck_m18_idx_metric_def_m22_consistency` 是最关键的一条。** 引用 M22 却用一个不同编码，是最隐蔽的自创方式——表面上「引用了 M22」，实际用了另一个码，M22 那边永远对不上账。约束强制 `m22_metric_code = metric_code`。
3. **`uk_m18_idx_metric_def_m22` 唯一索引防止重复引用。** 如果 `CL_DISCHARGE_COUNT` 被两个不同的本模块指标都引用，那么 M22 改口径时要改两处，必然有一处漏改。唯一索引让「一个 M22 指标最多被引用一次」成为硬约束。
4. **`self_reason` 强制 ≥ 20 字。** 不是形式主义——20 字大约是一句话的长度，能逼出「M22 的 X 指标是 A 口径，我要的是 B 口径」这样有判断依据的说明；不设长度限制时，实践中 100% 会写成「本模块特有」五个字，等于没写。
5. **`period_types` 用 JSONB 存粒度数组。** 质量指标只做月度，工作量可以做月度/季度/年度，统计快照做日/月/季/年——粒度差异是逐指标不同的，用 JSONB 表达比开四个布尔列清晰。
6. **`std_version` 与 `m18_idx_quality_metric.std_version` 呼应。** 指标定义版本变化后，历史期间的行保留旧版本号，新计算的行用新版本号。**不允许重算历史**——这与共享规范「口径版本化，历史不重算」一致。

| 项 | 估算 |
|---|---|
| 指标总数 | 约 30 行（引用 M22 约 12 + 自产约 9 + 总纲模型约 9） |
| 行均宽度 | 约 700 B |
| 全表规模 | 约 21 KB |
| 年增行数 | 约 3 行（新增指标） |

### 4.11 表：`m18_idx_config`

**用途：** 检索与统计的配置项。包括全文检索参数、脱敏规则开关、导出审批阈值、快照刷新时间、索引滞后阈值等。

**写入方：** M18-07 检索配置页（需 `m18:idx:config` 权限）

**约束说明**

```sql
ALTER TABLE m18_idx_config
    ADD CONSTRAINT ck_m18_idx_config_group
    CHECK (config_group = ANY (ARRAY['SEARCH', 'MASK', 'EXPORT', 'STAT', 'PERM', 'INDEX']));

ALTER TABLE m18_idx_config
    ADD CONSTRAINT ck_m18_idx_config_value_type
    CHECK (value_type = ANY (ARRAY['STRING', 'INT', 'DECIMAL', 'BOOLEAN', 'JSON']));

ALTER TABLE m18_idx_config
    ADD CONSTRAINT ck_m18_idx_config_effect
    CHECK (effect_scope = ANY (ARRAY['RUNTIME', 'RESTART', 'SCHEDULED']));

-- 组合约束：数值型配置必须可解析且落在上下限内
ALTER TABLE m18_idx_config
    ADD CONSTRAINT ck_m18_idx_config_numeric
    CHECK (value_type = 'STRING'
           OR value_type = 'JSON'
           OR value_type = 'BOOLEAN' AND config_value = ANY (ARRAY['TRUE', 'FALSE'])
           OR value_type IN ('INT', 'DECIMAL') AND config_value ~ '^-?[0-9]+(\.[0-9]+)?$');

ALTER TABLE m18_idx_config
    ADD CONSTRAINT ck_m18_idx_config_range
    CHECK (value_type NOT IN ('INT', 'DECIMAL')
           OR ((min_value IS NULL OR config_value::numeric >= min_value)
               AND (max_value IS NULL OR config_value::numeric <= max_value)));

ALTER TABLE m18_idx_config
    ADD CONSTRAINT ck_m18_idx_config_bounds
    CHECK (min_value IS NULL OR max_value IS NULL OR max_value >= min_value);

ALTER TABLE m18_idx_config
    ADD CONSTRAINT ck_m18_idx_config_desc
    CHECK (char_length(config_desc) >= 10);

ALTER TABLE m18_idx_config
    ADD CONSTRAINT ck_m18_idx_config_version
    CHECK (version_no >= 1);

COMMENT ON TABLE m18_idx_config IS '检索与统计配置项；安全关键项 editable 为 FALSE，只能由迁移脚本修改';
COMMENT ON COLUMN m18_idx_config.config_desc IS '配置说明，必须写清「改了会怎样」，不少于 10 字';
COMMENT ON COLUMN m18_idx_config.editable IS '是否允许页面修改；脱敏开关与导出审批阈值等安全关键项为 FALSE';
```

**分区策略**

不分区。约 30 行配置，全表常驻内存缓存。

**设计说明**

1. **`editable = FALSE` 用于安全关键项。** 例如「脱敏是否启用」「导出是否必须审批」「特殊模块病历默认是否可见」这类配置，一旦允许页面修改，就等于给了一个「把脱敏关掉」的按钮。约束上允许写入（迁移脚本需要），但业务接口拒绝修改 `editable = FALSE` 的项。
2. **`config_desc` 强制 ≥ 10 字并必须写「改了会怎样」。** 配置表最常见的腐化是「一堆没人知道干什么的 key」。一条 `INDEX_LAG_ALERT_SECONDS = 60` 如果没有说明「超过此秒数标记 degraded，病案室会看到『索引尚未同步』提示」，一年后没人敢动它。
3. **`min_value` / `max_value` 与 CHECK 联动。** 数值型配置在数据库层就被限制在合理区间，防止「`EXPORT_MAX_ROWS` 被改成 100 万」这类事故。
4. **`default_value` 保留回滚依据。** 配置改坏时，页面上的「恢复默认」依赖这一列；没有它就只能翻 Git 历史。
5. **`effect_scope` 区分生效时机。** 脱敏规则改完必须立即失效缓存（`RUNTIME`）；索引重建参数需要下一轮任务才生效（`SCHEDULED`）。混在一起会导致「改了配置但行为没变」的困惑。
6. **`version_no` 用于乐观锁。** 两个人同时改同一条配置时，后提交的会因为版本号不匹配而失败，避免静默覆盖。

**量级估算**

| 项 | 估算 |
|---|---|
| 配置项总数 | 约 30 行 |
| 行均宽度 | 约 400 B |
| 全表规模 | 约 12 KB |
| 年增行数 | 约 5 行 |

### 4.12 SQLAlchemy 2.0 模型定义

本节给出 §4.2 至 §4.11 全部 10 张表的 SQLAlchemy 2.0 声明式模型。模型是数据库结构的**唯一代码真源**：迁移脚本由模型生成，服务层查询由模型驱动，任何 DDL 变更必须先改模型再生成迁移。

**建模约定：**

| 约定项 | 取值 | 理由 |
| --- | --- | --- |
| 声明风格 | `DeclarativeBase` + `Mapped[]` + `mapped_column()` | SQLAlchemy 2.0 原生风格，类型标注即字段类型，IDE 与 mypy 可校验 |
| 主键 | `Mapped[int] = mapped_column(BigInteger, Identity(), primary_key=True)` | 对应数据库 `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| 时间字段 | `Mapped[datetime]` 映射 `TIMESTAMP`（不带时区） | 全系统统一业务本地时间，跨时区换算在展示层处理 |
| 枚举字段 | `Mapped[str]` + `String(32)` | 数据库侧用 VARCHAR + CHECK 表达枚举，不用数据库原生枚举类型（加值需改类型，代价高） |
| 金额字段 | `Numeric(14, 2)` | 精确十进制，避免二进制浮点误差 |
| 比率字段 | `Numeric(10, 6)` | 六位小数足以表达百分比与千分率 |
| 评分类字段 | `Numeric(5, 1)` | 质控评分保留一位小数，与 `M18-CALC-02` 一致 |
| JSONB 字段 | `Mapped[dict]` + `JSONB` | 权限快照、查询条件快照等结构可演进的数据 |
| 数组字段 | `Mapped[list]` + `ARRAY(String)` | 科室授权范围、降级来源清单 |
| 表注释 | `__table_args__` 中 `comment=` | 与数据库 `COMMENT ON TABLE` 保持一致 |
| 逻辑外键 | 不声明 `ForeignKey`，仅建索引 | 跨子模块引用不做数据库级强约束，避免归档库脱机时写阻塞 |
| 分区表 | 模型只映射父表，分区由 DDL 管理 | 分区是存储层细节，模型层不必感知 |

**关于 `search_vec` 字段的建模说明：** 模型里 `search_vec` 声明为 `Mapped[str | None]` 映射 `Text`，而数据库物理类型是 `tsvector`。这是 SQLAlchemy 对 PostgreSQL 专有类型的一种折衷：`tsvector` 的读写由触发器与 `to_tsvector()` 函数在数据库侧完成，应用层只读不写；若一定要在应用层写，应改用 `sqlalchemy.dialects.postgresql.TSVECTOR` 类型。本设计选择前者，理由是**向量必须与正文在同一事务内生成**，由触发器维护才能保证「签署即可检索」，若交给应用层拼装，任何一次写入路径遗漏都会造成检索空白。

### 4.13 Pydantic Schema 定义

本节定义 API 层与内部契约层的数据契约。约定：

| 约定项 | 取值 | 理由 |
| --- | --- | --- |
| Pydantic 版本 | V2 | 使用 `model_config`、`Field`、`field_validator`，不使用 V1 的 `Config` 内嵌类 |
| 命名后缀 | 入参 `*Create` / `*Update` / `*Query`；出参 `*Out` / `*Item` | 一眼看出数据流向 |
| 出参基类 | 统一继承 `QualityMark` | 质量四标记在每个出参里都必须出现，靠继承强制 |
| 字段校验 | `Field(max_length=...)` + `pattern` | 与数据库 CHECK 约束保持同一套规则，双重校验 |
| 脱敏字段 | 出参只暴露 `*_masked` 字段 | 原始姓名、手机号、身份证号不进任何出参模型 |
| 枚举 | `Literal[...]` | 与数据库 CHECK 的取值集合逐字一致 |

from pydantic import BaseModel, ConfigDict, Field, field_validator


class QualityMark(BaseModel):
    """质量四标记基类。

    所有出参必须继承本类。四个字段在任何情况下都要出现，
    降级时也不能省略，只是取值不同。这是「不确定就说不确定」的落库形态。
    """

    degraded: bool = Field(default=False, description="本次返回是否降级")
    degraded_sources: list[dict[str, str]] = Field(
        default_factory=list, description="降级数据源清单，不降级时为空列表"

    data_quality: Literal["REALTIME", "CACHED", "PARTIAL", "UNKNOWN"] = Field(

class SearchQuery(BaseModel):
    """检索请求。

    keyword 只接受长度 1 到 50 的文本；空串表示只按条件筛选不做全文匹配。
    """

    model_config = ConfigDict(extra="forbid")

    keyword: str | None = Field(default=None, min_length=1, max_length=50)
    record_type: list[str] = Field(default_factory=list)
    dept_id: list[int] = Field(default_factory=list)
    doctor_id: list[int] = Field(default_factory=list)
    patient_id: int | None = None
    date_from: date | None = None
    date_to: date | None = None

        start = info.data.get("date_from")
        if v is not None and start is not None and v < start:
            raise ValueError("结束日期不得早于开始日期")

### B.2 全文检索索引

```sql
-- 二元切分向量索引：GIN 是 tsvector 的默认倒排索引类型
-- 使用 gin_trgm_ops 会意外支持模糊匹配，本设计不启用，避免索引体积翻倍
CREATE INDEX gin_m18_idx_search_doc_vec
    ON m18_idx_search_doc
    USING GIN (search_vec);

-- 检索的常用前置过滤：先按患者、科室、日期缩小范围，再走 GIN
-- 这两个 B-Tree 索引与 GIN 组合，是「先用选择性高的条件筛，再全文匹配」的关键
CREATE INDEX idx_m18_idx_search_doc_patient
    ON m18_idx_search_doc (patient_id, record_date DESC);
CREATE INDEX idx_m18_idx_search_doc_dept
    ON m18_idx_search_doc (dept_id, record_date DESC);
```

**为什么不是复合 GIN + B-Tree 索引：** PostgreSQL 的 GIN 索引不支持多列复合（除非装 `btree_gin` 扩展），而把 `dept_id` 塞进 GIN 会让索引对「只要全文匹配不要科室过滤」的查询失效。分成两个索引后，计划器可以按选择性自行组合，实测在百万行级别比单一复合索引稳定。

**三条硬规矩：**

| 规矩 | 内容 | 为什么 |
| --- | --- | --- |

**迁移硬规矩（沿用数据结构汇总 §8.2）：**

| 规矩 | 内容 |
| --- | --- |
| 必须有 downgrade | 每个 upgrade 都写对应 downgrade，禁止 `raise NotImplementedError` |
| 分区表必须含 DEFAULT | 漏跑预建任务时 INSERT 落到 DEFAULT 分区而不报错 |
| 大表加索引用 CONCURRENTLY | `m18_idx_search_doc` 的 GIN 索引必须 CONCURRENTLY，避免锁表 |
| REVOKE 放最后 | 权限收口必须在表与索引全部建完后执行，downgrade 里要 GRANT 回来 |
| 种子可重复执行 | 全部种子语句带 `ON CONFLICT DO NOTHING` |
| 迁移不依赖应用代码 | 只用 SQL 与 alembic 原生 API，不 import 业务模块 |

## 附录 E 与上游表的口径约定

| 上游对象 | 归属子模块 | 本子模块的引用方式 | 不得做什么 |
| --- | --- | --- | --- |
| `m18_emr_record` | M18-02 | 只读 `id`、`record_no`、`content_hash`、`record_status` | 不得回写、不得修改任何正文字段 |

**口径约定三条：**

| 约定 | 内容 |
| --- | --- |
| 名称快照 | 科室名、医生名在建索引时一次性落库，之后科室改名不回刷历史索引。理由：历史病历展示的应是当时的科室名 |
| 哈希引用 | 正文出参同时返回 `content_hash`，调用方可用它比对 M18-06 归档时固化的哈希，验证正文未被篡改 |
| 状态只读 | 索引行的 `doc_status` 是 `m18_emr_record.record_status` 的投影，唯一写入方是事件订阅器，不允许任何接口直接改 |
