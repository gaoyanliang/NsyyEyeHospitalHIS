### 最需要先读到的三件事

1. **规则表是「版本化只增不改」的，不是「可编辑配置」。** `m18_kb_med_rule` 的主键之外还有一个业务唯一键 `(rule_code, rule_version)`，发布新版是 **INSERT 一行新版本**、把旧行置 `SUPERSEDED`，不是 `UPDATE` 旧行。已产生的审核结果永远指向当时的 `rule_version`，所以旧行**物理上不能删、内容上不能改**。这条决定了本子模块全部表都是「配置表按事实表管理」。

2. **不是每张 `m18_kb_*` 表都能被「热重载」进内存。** 只有规则的**判定条件部分**进内存得到 `RuleSet`；规则的**展示部分**（提示语、循证依据全文、维护人）留库。原因是内存 40MB 预算里塞不下 8,000 条规则的完整说明文本，而审核时只需要 `rule_code` 与「要不要报」，提示语可以按 `rule_code` 回查缓存。这个拆分写在 3.3 与 4.2.3。

3. **DRG 权重的版本切段用「双列」表达，不是单列 `version`。** `effective_from` 与 `effective_to` 两列配合一条 `EXCLUDE` 约束表达「同一 DRG 组在同一时点只能有一套生效权重」，绝不允许出现两个版本日期重叠。用单列 `version` 排序取最大的写法，在「医保局发了更正版、生效日期早于当前已生效版本」时会静默取错。

## 1. 概述

### 1.1 设计目标

| 编号 | 目标 | 可验证的判据 |
|---|---|---|
| **DG-01** | 规则可复现 | 任意一条历史审核结果能还原出「当时用了哪一版规则集」，即 `rule_version_set` 可解析到具体的规则行 |
| **DG-02** | 规则可回滚 | 发布后发现问题，能重新发布旧版内容，且旧版行仍在库里未丢失 |
| **DG-03** | 热重载可验证 | 每次全量加载都能算出耗时与条数，写进日志表；加载失败不影响正在服务的旧规则集 |
| **DG-04** | 路径可统计 | 入径率、变异率、完成率三个指标能由本子模块的表直接算出，不需要跨模块拼数 |
| **DG-05** | 规则可自我维护 | 命中率异常（过高、过低、恒不命中）的规则能被查出来，且每个命中事件都留了可归因的明细 |

### 1.2 设计原则

| # | 原则 | 为什么 |
|---|---|---|
| 1 | **先定规则的数据形状，再定审核的算法。** | 审核逻辑（M18-05）会随临床要求变，但规则的数据形状变了就意味着 8,000 条存量规则要重新录入。数据形状必须比算法稳定。 |
| 2 | **配置表按事实表管理：只增不改、状态表达代替删除。** | 规则是「医疗判断的依据」，一旦被追溯修改，所有引用它的历史审核结果就无法解释。 |
| 3 | **能算出来的不存，除非重算代价不可接受。** | `matched_rule_count` 可以从命中明细数出来，不冗余存储；但 `m18_kb_path_entry` 的 `deviation_count` 冗余存储，因为列表页要按它排序且跨表 count 太慢。 |
| 4 | **维度字段无值存空串不存 NULL。** | 同 M19 经验：PostgreSQL 唯一约束认为 NULL 互不相等，`(path_code, patient_id, encounter_id)` 里任一列可空时唯一约束形同虚设。 |
| 5 | **组合语义必须用组合 CHECK 表达。** | 「状态是 A 就必须配一整套参数」这种约束，单字段 CHECK 全部能通过而组合是荒谬的。判别方法沿用 M19：把类型改成另一种、各字段填成另一类型的合法值，能通过吗？ |

**本子模块不读任何病历正文表。** 规则创作与路径配置只依赖主数据（药品、诊断、科室、人员）与患者标识，不依赖 `m18_emr_*`。这是刻意的：一旦规则创作依赖病历正文，规则维护人就会看到患者数据，而规则维护人（药师、医务科）通常没有病历查看权限。

|---|---|---|
| `m18_kb_triage_rule` | 是 | 分诊规则的**交付通道（M04-04 如何取得规则）尚未定案**，已在详细设计 §10.6 记为待裁决项。契约未定就建表，字段设计必然返工；契约一旦定案，DDL 追加到本文档即可，不影响其余 11 张表。 |

| `m18_kb_hit_stat` | 是 | 规则命中统计。它是**由 M18-05 的审核结果聚合出来的派生数据**，不是知识库的配置。归属上放 M18-08（知识库自我维护的依据），但物理表由 M18-08 与 M18-05 共用：M18-05 写入命中明细，M18-08 按日聚合。**为避免两个子模块各建一张同名表（共享规范 §17 坑㉜），本文档明确声明：`m18_kb_hit_stat` 由 M18-08 建，M18-05 只写不建。** DDL 见附录 A.1。 |

**汇总口径：**

| 口径 | 数量 | 说明 |
|---|---|---|
| 本文档 `### 4.x 表：` 详细定义的业务表 | **11 张** | 第 4 章逐字段定义 |
| 运维与统计表（附录 A 给完整 DDL） | **2 张** | `m18_kb_hit_stat`、`m18_kb_reload_log` |
| 物理表合计 | **13 张** | 全部带 `m18_kb_` 前缀，全部由 M18-08 定义 |
| 待契约定案后追加 | **1 张** | `m18_kb_triage_rule` |

> **为什么运维表放附录而不是第 4 章？** 第 4 章是「业务表的字段级定义」，面向开发写代码；`m18_kb_hit_stat` 与 `m18_kb_reload_log` 没有业务语义，只有写入方与保留期，写进第 4 章会稀释「11 张业务表」这个口径。但**它们的 DDL 必须完整可执行**，所以附录 A 给的是可直接运行的 `CREATE TABLE`，不是描述。

## 2. 命名与类型规范

### 2.1 表命名

全部表名格式：`m18_kb_{业务对象}[_{从属对象}]`。

| 后缀模式 | 含义 | 本子模块实例 |
|---|---|---|
| `_rule` | 规则本体 | `m18_kb_med_rule`、`m18_kb_dose_rule`、`m18_kb_interaction_rule`、`m18_kb_antibiotic_rule` |
| `_set` | 集合/快照 | `m18_kb_rule_version_set` |
| `_path` / `_node` | 路径与节点 | `m18_kb_path`、`m18_kb_path_node` |
| `_entry` / `_deviation` | 实例与变异 | `m18_kb_path_entry`、`m18_kb_path_deviation` |
| `_entry`（知识域） | 知识条目 | `m18_kb_ophth_entry` |
| `_weight` | 权重 | `m18_kb_drg_weight` |
| `_stat` / `_log` | 统计与日志（运维） | `m18_kb_hit_stat`、`m18_kb_reload_log` |

> **注意 `_entry` 在本子模块有两个含义**：路径域是「入径实例」，知识域是「知识条目」。两者靠中间段区分（`path_entry` vs `ophth_entry`），不冲突。但这确实是一个易混点，`m18_kb_ophth_entry` 在正文里一律称「知识条目」，不简称「条目」。

### 2.2 字段命名

| 类型 | 规范 | 本子模块实例 |
|---|---|---|
| 主键 | `id BIGINT GENERATED BY DEFAULT AS IDENTITY` | 全部 |
| 业务编码 | `{对象}_code VARCHAR(64)` | `rule_code`、`path_code`、`node_code`、`drg_code` |
| 业务单号 | `{对象}_no VARCHAR(32)` | `entry_no`（入径号）、`version_set_no`（版本集号） |
| 版本号 | `{对象}_version VARCHAR(32)` | `rule_version` |
| 逻辑外键 | `{对象}_id BIGINT` | `patient_id`、`encounter_id`、`rule_id`、`path_id`、`node_id` |
| 跨模块逻辑外键 | `{来源}_{对象}_id` | `dept_id`（M01）、`staff_id`（M01）、`drug_id`（M01） |
| 状态 | `status VARCHAR(32)` | 见 §3.4 |
| 类型 | `{对象}_type VARCHAR(32)` | `rule_type`、`deviation_type`、`alert_type` |
| 比率 | `{对象}_rate NUMERIC(10,6)` | `hit_rate`、`entry_rate`、`deviation_rate` |
| 计数 | `{对象}_count INT` / `BIGINT` | `hit_count`、`alert_count`、`deviation_count` |
| 日期区间 | `effective_from` / `effective_to` | DRG 权重、规则生效期 |

| 快照 | `{对象}_snap JSONB` | `rule_snap`、`applicability_snap` |
| 公共字段 | `created_at` / `created_by` / `updated_at` / `updated_by` | 见 §2.4 |

### 2.4 建表硬规范（本子模块的具体落实）

| # | 规定 | 本子模块的落实方式 |
|---|---|---|
| 1 | 主键 `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 全部 13 张表 |
| 2 | 公共字段四件套 + `is_deleted` | **`is_deleted` 只有 `m18_kb_path`、`m18_kb_path_node`、`m18_kb_ophth_entry`、`m18_kb_drg_weight` 四张可变配置表设**；规则表（`med_rule` / `dose_rule` / `interaction_rule` / `antibiotic_rule` / `rule_version_set`）与事实表（`path_entry` / `path_deviation`）**一律不设**，用状态表达 |
| 3 | 金额 `NUMERIC(14,2)`、比率 `NUMERIC(10,6)`、评分 `NUMERIC(5,1)`；禁 FLOAT/DOUBLE/REAL | `drg_weight` 用 `NUMERIC(10,6)`（权重是比值不是金额）；`hit_rate` 用 `NUMERIC(10,6)` |
| 4 | 枚举 `VARCHAR(32)` + CHECK，全大写英文 | 见 §3.4，全部对齐共享规范 §13 |
| 5 | 大字段 `JSONB` 且结构写清 | `rule_condition JSONB`、`rule_snap JSONB`、`applicability_snap JSONB`、`node_snap JSONB`，结构见附录 D |
| 6 | 时间 `TIMESTAMP` 不带时区 | 全部，统一 Asia/Shanghai |
| 7 | VARCHAR 必须给长度，结构化字段不用 TEXT | `rule_expression` 用 `VARCHAR(512)`；提示语 `alert_message` 用 `VARCHAR(1024)`；**唯一用 TEXT 的是 `evidence_text`（循证依据原文，可能含文献段落）与 `path_doc_text`（路径说明）** |
| 8 | 逻辑外键必须建索引 | `patient_id`、`encounter_id`、`path_id`、`rule_id`、`drug_id`、`drg_code` 全部建 |
| 9 | 表与字段必须有 `COMMENT ON` | 第 4 章每张表末尾给完整 `COMMENT ON` 语句 |
| 10 | **不建物理外键** | 同 M18 全局做法：跨表引用全部由应用层保证，理由见 §3.1 |

### 2.5 为什么本子模块「只有两张表分区」

数据结构设计汇总 §4 已定「配置与主数据类 `m18_kb_*` 不分区」。本文档的 13 张表里分区判定逐张走一遍：

| 表 | 分区？ | 判据 |
|---|---|---|
| `m18_kb_med_rule` 等 5 张规则表 | ❌ | 3 年 24,000 行，且**唯一键是 `(rule_code, rule_version)` 不含时间列**。分区表要求唯一约束必须包含分区键，塞时间列进唯一键会让「同一规则同一版本只能一行」这条约束失效。 |
| `m18_kb_path` / `_node` | ❌ | 24 行 / 360 行 |
| `m18_kb_ophth_entry` | ❌ | 40 行 |
| `m18_kb_drg_weight` | ❌ | 3 年 360 行 |
| `m18_kb_path_deviation` | ❌ | 3 年 7,200 行，量小且查询总带 `entry_id` |
| **`m18_kb_path_entry`** | ✅ **按年** | 3 年 54,000 行本身不大，但**入径实例会随年份无限增长**（每年 1.8 万，10 年 18 万，且医疗记录不可删）。按年分区使「3 年前的数据迁归档库」变成 `DETACH PARTITION` 秒级操作，而不是 `DELETE` 扫表。**这是唯一一张因为「保留期迁移」而不是因为「当前数据量大」而分区的表。** |
| **`m18_kb_hit_stat`** | ✅ **按年** | 3 年 525 万行，查询总带 `stat_date` 范围。按年分区使「查本月」只扫一个分区。 |

> **为什么 `m18_kb_path_entry` 不按月分区？** 年 1.8 万行按月分只有 1,500 行/月，分区数（3 年 36 个）带来的规划开销超过收益。PostgreSQL 在分区数超过 100 后查询规划时间明显上升，按年是行数与分区数的平衡点。

### 2.6 维度字段空值规则

> 沿用 M19 与 M18 全局经验：PostgreSQL 的唯一约束认为 `NULL` 互不相等，所以**任何参与唯一约束的维度字段必须 `NOT NULL DEFAULT ''`**。

| 表 | 参与唯一约束的维度字段 | 空值表达 |
|---|---|---|
| `m18_kb_med_rule` | `rule_code`、`rule_version` | 两者都是业务必填，无空值场景 |
| `m18_kb_dose_rule` | `drug_code`、`route` | **`route` 无值存 `''`**（表示「所有给药途径」），不存 `NULL` |
| `m18_kb_interaction_rule` | `drug_code_a`、`drug_code_b` | 必填 |
| `m18_kb_antibiotic_rule` | `drug_code`、`antibiotic_level` | 必填 |
| `m18_kb_path_node` | `path_id`、`node_code` | 必填 |
| `m18_kb_path_entry` | `path_code`、`patient_id`、`encounter_id` | 必填 |
| `m18_kb_drg_weight` | `drg_code`、`weight_version` | 必填 |
| `m18_kb_hit_stat` | `stat_date`、`rule_code`、`rule_version`、`scene_code` | **`scene_code` 无值存 `''`**（表示不区分场景） |

**判据**：如果一个字段在业务上可以「不指定」，它在 SQL 里就有两种写法（`NULL` 与 `''`），唯一约束只在两者一致时才有效。**统一存 `''`，并且 CHECK 约束禁止 `NULL`（`NOT NULL DEFAULT ''`）**，就只剩一种写法。

## 3. 表关系总览

### 3.1 为什么全部不建物理外键

| 理由 | 说明 |
|---|---|
| 跨模块字段本来就无法建 | `patient_id`（M03）、`drug_id`（M01）、`dept_id`（M01）等全部跨库/跨模块 |
| 同模块内也不建 | 规则表与明细表（`m18_kb_med_rule` → `m18_kb_dose_rule`）删改路径完全不同：规则表「只增不改」，明细表随规则版本一起新增。B 树外键检查会在批量导入 8,000 条规则时产生额外的共享锁竞争 |
| 分区表无法建指向非分区表的外键 | `m18_kb_path_entry` 按年分区，`m18_kb_path` 不分区，PostgreSQL 不允许分区表外键引用普通表 |
| 引用完整性由应用层与巡检 SQL 保证 | 附录 B.4 给出「悬空引用巡检」SQL，每次发布前跑一遍 |

> **代价必须写清**：不建外键意味着可能出现「`m18_kb_dose_rule.rule_id` 指向一个不存在的规则」。这个风险用三件事对冲：①明细表只能由「规则发布」这一个服务方法创建，它在同一事务里先插主表再插明细；②附录 B.4 提供巡检 SQL 挂在规则发布后的自检步骤里；③明细表的主表引用列 `rule_id` + `rule_version` 建唯一索引，重复插入会在数据库层报错。

### 3.3 「进内存」与「留库」的字段拆分

这是本子模块最重要的一个结构决策，它决定了内存 40MB 能不能装下 8,000 条规则。

| 数据 | 去向 | 理由 |
|---|---|---|
| `rule_code` / `rule_version` / `rule_type` / `severity` / `alert_level` | **进内存** | 匹配时判定要不要报、报什么级别，全是短字段 |
| `rule_condition`（触发条件表达式） | **进内存** | 匹配的核心，必须是内存里的结构化对象（不是 JSON 文本，加载时解析成 Python 对象） |
| `drug_code` 索引（该规则涉及哪些药品） | **进内存** | 匹配的第一步是「按处方药品倒排找候选规则」，必须在内存里建倒排索引 |
| `diagnosis_code` / `procedure_code` 索引 | **进内存** | 同上 |
| `alert_message`（提示语模板，最长 1,024 字符） | **留库 + Redis 缓存** | 8,000 × 1KB ≈ 8MB。进内存会让 40MB 变成 48MB，而提示语只在「已命中」后需要，命中率通常 < 5%，回查缓存完全够 |
| `evidence_text`（循证依据原文） | **留库** | 平均 2KB/条，8,000 条 ≈ 16MB，且 99% 的审核不需要返回原文 |
| `evidence_ref`（文献出处编号，短） | **进内存** | 响应里要带，且很短 |
| `created_by` / `published_by` / 维护人 | **留库** | 审核时不需要 |
| `m18_kb_path` 的节点序列 | **不进内存** | 路径不参与 P-08 审核，P-12 单次查询走库即可（200ms 预算足够） |
| `m18_kb_drg_weight` | **进内存** | P-09 是 M05-07 的 CMI 计算热路径，一次算一个科室的 CMI 要查几百个 DRG 组，出库太慢。**120 条 × 约 200B ≈ 24KB**，可忽略 |

**内存估算复核：**

| 部分 | 单条大小 | 条数 | 小计 |
|---|---|---|---|
| 规则头（编码/版本/类型/级别/条件/出处） | ≈ 600 B | 8,000 | 4.8 MB |
| `rule_condition` 解析后的 Python 对象 | ≈ 1,200 B | 8,000 | 9.6 MB |
| 药品倒排索引 | ≈ 90 B/条 | ≈ 26,000 索引项 | 2.3 MB |
| 诊断倒排索引 | ≈ 90 B/条 | ≈ 9,000 索引项 | 0.8 MB |
| DRG 权重 | ≈ 200 B | 120 | 24 KB |
| Python 对象开销（`__dict__`、引用、对齐） | — | — | ≈ 20 MB |
| **合计** | | | **≈ 37.5 MB** |

**所以 40MB 预算是成立的，余量 2.5MB。** 这个估算必须写进文档，因为「8,000 条 × 5KB」这种粗糙算法会得到 40MB，但分不清哪部分该留在库里——一旦有人把 `evidence_text` 也放进内存，直接变成 56MB 并 OOM。

### 3.4 枚举取值与落库方式

全部枚举用 `VARCHAR(32)` + CHECK，取值严格对齐共享规范 §13，不得自创。

| 枚举 | 取值 | 落在哪些字段 |
|---|---|---|
| `rule_type` | `INTERACTION` / `DOSAGE` / `CONTRAINDICATION` / `ANTIBIOTIC_LEVEL` / `DUPLICATE` / `SPECIAL_DRUG` / `OPHTHALMIC_SPECIFIC` | `m18_kb_med_rule.rule_type` |
| `rule_status` | `DRAFT` / `IN_REVIEW` / `PUBLISHED` / `SUPERSEDED` / `DISABLED` | `m18_kb_med_rule.status` |
| `alert_level` | `BLOCK` / `SEVERE` / `WARN` / `INFO` | `m18_kb_med_rule.alert_level`、`m18_kb_hit_stat.alert_level` |
| `alert_type` | `INTERACTION` / `CONTRAINDICATION` / `DOSAGE` / `ALLERGY` / `DUPLICATE` / `ANTIBIOTIC_LEVEL` / `SPECIAL_DRUG` / `PREGNANT` / `ELDERLY` / `OPHTHALMIC_SPECIFIC` | `m18_kb_hit_stat.alert_type` |
| `path_entry_status` | `ENTERED` / `IN_PROGRESS` / `COMPLETED` / `EXITED` / `DEVIATED` | `m18_kb_path_entry.status` |
| `path_node_status` | `PENDING` / `IN_PROGRESS` / `COMPLETED` / `SKIPPED` / `DEVIATED` | `m18_kb_path_entry.node_status_snap` 内的状态、`m18_kb_path_node.status` |
| `deviation_type` | `EXTEND` / `SHORTEN` / `SKIP_NODE` / `ADD_NODE` / `EXIT_PATH` / `OTHER` | `m18_kb_path_deviation.deviation_type` |
| `antibiotic_level` | `NON_RESTRICTED` / `RESTRICTED` / `SPECIAL` | `m18_kb_antibiotic_rule.antibiotic_level` |
| `data_quality` | `REALTIME` / `DAILY` / `ESTIMATED` | `m18_kb_hit_stat.data_quality` |

**注意 `rule_type` 与 `alert_type` 不是同一个枚举。** `rule_type` 是规则的**创作分类**（`SPECIAL_DRUG` 表示「特殊管理药品」这一类规则），`alert_type` 是**提示的分类**（`ELDERLY` 表示「老年患者慎用」）。一条 `SPECIAL_DRUG` 规则可能产生 `ELDERLY` 或 `PREGNANT` 的提示。**把两者合并成一个枚举是常见错误**，会让「按规则类型统计」和「按提示类型统计」两张报表打架。

### 3.5 状态机在表结构上的落点

**规则状态：**

```
DRAFT ──提交审核──▶ IN_REVIEW ──审核通过──▶ PUBLISHED
  ▲                    │                      │
  │                    │驳回                  │发布新版
  └────────────────────┘                      ▼
                                         SUPERSEDED（旧版本，永久保留）
  
DISABLED：任何非 SUPERSEDED 状态可置为 DISABLED，DISABLED 不可回到 PUBLISHED
```

**落点**：`m18_kb_med_rule.status` + 组合 CHECK：

```sql
CHECK (status <> 'PUBLISHED'  OR (published_at IS NOT NULL AND published_by IS NOT NULL))
CHECK (status <> 'SUPERSEDED' OR (superseded_at IS NOT NULL AND superseded_by_version IS NOT NULL))
CHECK (status <> 'DISABLED'   OR (disabled_reason IS NOT NULL AND disabled_at IS NOT NULL))
CHECK (status = 'DRAFT'       OR (reviewed_by IS NOT NULL AND reviewed_at IS NOT NULL))
```

**为什么最后一条是「非 DRAFT 则必须已审核」**：如果只写「`status='IN_REVIEW'` 则必须有提交人」，那么把状态改成 `PUBLISHED` 但漏填审核人也能通过——单字段 CHECK 全部满足。**必须用「非 A 则 B」的形式表达状态与其他字段的依赖**，这是 M19 与 M18 共同的经验。

**路径入径状态：**

```
ENTERED ──▶ IN_PROGRESS ──┬──▶ COMPLETED
                │          └──▶ EXITED
                └──▶ DEVIATED ──┬──▶ IN_PROGRESS（继续）
                                └──▶ COMPLETED（带变异完成）
```

**落点**：`m18_kb_path_entry.status` + 组合 CHECK：

```sql
CHECK (status <> 'COMPLETED' OR (completed_at IS NOT NULL))
CHECK (status <> 'EXITED'    OR (exit_reason IS NOT NULL AND exited_at IS NOT NULL))
CHECK (status <> 'DEVIATED'  OR (deviation_count > 0))
CHECK (exit_reason <> '')  = (status = 'EXITED')  -- 反向：非 EXITED 不得有退出原因
```

**为什么最后一条要正反双向**：只写「`EXITED` 必须有退出原因」时，一条 `COMPLETED` 的记录仍可带着 `exit_reason`，事后统计「退出原因分布」会把已完成也统计进去。

### 3.6 派生数据与冗余字段清单

| 字段 | 是否冗余 | 为什么保留/不保留 |
|---|---|---|
| `m18_kb_path_entry.deviation_count` | 冗余（可 `count(*) from path_deviation`） | 列表页按它排序，且路径详情页每次都要显示；跨表 count 在 5 万行上单次约 8ms，列表页 20 行就是 160ms |
| `m18_kb_path_entry.node_status_snap` | 冗余快照 | 节点状态在 `m18_kb_path_node` 上是**当前值**，而历史入径要知道「当时的节点定义是什么」。路径定义改版后旧入径必须仍能显示旧节点，否则改一次路径定义，所有历史入径的节点都会跟着变 |
| `m18_kb_rule_version_set.rule_count` | 冗余 | 用于校验「版本集里的规则数」与「实际 PUBLISHED 规则数」是否一致，是热重载的完整性检查依据 |
| `m18_kb_rule_version_set.checksum` | 冗余但必需 | 全部规则内容的哈希，用于回答「这次加载的规则集和昨天的是不是同一套」。**没有 checksum 就无法判断「没变化」与「加载失败但返回了旧对象」** |
| `m18_kb_hit_stat.hit_count` | 不是冗余，是聚合 | 由命中明细按日聚合，聚合后明细可以归档 |
| `m18_kb_med_rule.rule_condition` 内的药品清单 | 不冗余 | 倒排索引在加载时从它构建，不单独存 |

**判据：冗余只允许出现在「读取频率远高于写入频率」且「不一致可容忍一段时间的窗口」的字段上。** `deviation_count` 用「变异写入时同事务 `+1`」保持强一致，不靠定时任务修正。

### 4.2 表：`m18_kb_med_rule`

#### 4.2.1 表说明

用药规则主表。**全部 `rule_type` 的规则头都在这张表**，各类型的专有参数放在对应的明细表（`dose_rule` / `interaction_rule` / `antibiotic_rule`）。这样设计的理由是审核执行方（M18-05）的匹配流程是「先按药品找到一个规则头列表 → 再按 `rule_type` 分流到明细取参数」，主表统一让第一步只查一张表。

| 项 | 说明 |
|---|---|
| 表类型 | 规则配置（**只增不改**） |
| 分区 | 不分区 |
| 3 年行数 | 约 24,000（8,000 条规则 × 平均 3 个版本） |
| 主要写入方 | 规则发布（P04/P05）、CLI 初始化导入、`mdm.rule.reload` 触发的规则同步 |
| 主要读取方 | 热重载加载器（全量 `PUBLISHED`）、规则管理页面、命中统计聚合 |
| 是否进内存 | **规则头部分进内存**（见 §3.3） |

> **为什么有 `severity` 又有 `alert_level`？** 两者回答不同的问题。`severity` 是**临床严重度**（1~5，由临床专家评定，同一条规则不会因为使用场景改变），`alert_level` 是**要弹出什么级别的提示**（`BLOCK` 会拦截处方，`INFO` 只记日志，可按场景调整）。一条「散瞳药与闭角型青光眼」的规则 `severity = 5`，但在门诊快诊场景可能配成 `SEVERE`（强提示不拦截），在手术室配成 `BLOCK`。**如果只保留一个字段，要么临床严重度被使用场景绑死，要么提示级别无法按场景调整。**

> **为什么 `drug_codes` 用数组存而不是从 `rule_condition` 里解析？** 加载时建倒排索引要遍历全部 8,000 条规则并取药品清单，从 JSONB 里逐条解析（`rule_condition->'drugs'`）比读一个原生数组列慢 3~5 倍，且无法建 GIN 索引。数组列可以直接 `GIN (drug_codes)` 索引，加载时用 `SELECT unnest(drug_codes)` 一次取得全部药品的倒排关系。**代价是数组与 JSONB 两处都要维护，用组合 CHECK 保证一致：`CHECK (drug_codes <@ ARRAY(SELECT jsonb_array_elements_text(rule_condition->'drug_codes')))` —— 但 PostgreSQL 不允许在 CHECK 里用子查询，所以这个一致性由发布服务层保证，并在附录 B.5 提供巡检 SQL。** 这是一处「数据库无法强制」的约束，必须写清。

#### 4.2.3 约束定义

**主键与唯一：**

| 名称 | 定义 | 语义 |
|---|---|---|
| `pk_m18_kb_med_rule` | `PRIMARY KEY (id)` | — |
| `uk_m18_kb_med_rule_code_ver` | `UNIQUE (rule_code, rule_version)` | 同一规则的同一版本只能一行（共享规范 §2.5 唯一键） |

**枚举 CHECK：**

```sql
CONSTRAINT ck_m18_kb_med_rule_type CHECK (

                  'DUPLICATE','SPECIAL_DRUG','OPHTHALMIC_SPECIFIC')
```

**组合语义 CHECK（本表最关键的部分）：**

```sql
-- ① 非 DRAFT 状态必须已审核（堵住「直接置 PUBLISHED 不填审核人」）
CONSTRAINT ck_m18_kb_med_rule_reviewed CHECK (
    status = 'DRAFT' OR (reviewed_by IS NOT NULL AND reviewed_at IS NOT NULL)
),
-- ② PUBLISHED 必须有发布信息与所属版本集
CONSTRAINT ck_m18_kb_med_rule_published CHECK (
    status <> 'PUBLISHED'
    OR (published_at IS NOT NULL AND published_by IS NOT NULL AND version_set_id IS NOT NULL)
),
-- ③ SUPERSEDED 必须记录被谁取代
CONSTRAINT ck_m18_kb_med_rule_superseded CHECK (
    status <> 'SUPERSEDED'
    OR (superseded_at IS NOT NULL AND superseded_by_version IS NOT NULL)
),
-- ④ DISABLED 必须有原因
CONSTRAINT ck_m18_kb_med_rule_disabled CHECK (
    status <> 'DISABLED' OR (disabled_reason IS NOT NULL AND disabled_at IS NOT NULL)
),
-- ⑤ 生效区间必须正向
CONSTRAINT ck_m18_kb_med_rule_effective CHECK (
    effective_from IS NULL OR effective_to IS NULL OR effective_to >= effective_from
),
-- ⑥ BLOCK 级别必须是高严重度（堵住「轻度规则配成拦截」）
CONSTRAINT ck_m18_kb_med_rule_block_severity CHECK (
    alert_level <> 'BLOCK' OR severity >= 4
),
-- ⑦ OPHTHALMIC_SPECIFIC 类规则必须挂循证依据（眼科特有条目无出处即无法评审）
CONSTRAINT ck_m18_kb_med_rule_ophth_evidence CHECK (
    rule_type <> 'OPHTHALMIC_SPECIFIC' OR length(evidence_ref) > 0
),
-- ⑧ 触发条件不得为空对象
CONSTRAINT ck_m18_kb_med_rule_condition_not_empty CHECK (
    rule_condition <> '{}'::jsonb
)
```

**组合语义 CHECK 的判别过程（§1.2 原则 5 的实际应用）：**

| 检查项 | 只写单字段约束会漏掉什么 |
|---|---|
| ① | 「`IN_REVIEW` 必须有提交人」「`PUBLISHED` 必须有发布人」两条各自成立时，仍可构造 `status='PUBLISHED'` + `reviewed_by=NULL` + `published_by=123` 的行：**审核步骤被跳过但发布记录齐全**。这正是知识库最怕的「规则没审就上线」。 |
| ⑥ | 「`alert_level` 取值合法」「`severity` 在 1~5」两条各自成立时，仍可构造 `alert_level='BLOCK'` + `severity=1`：**一条最轻微的提示会拦截医生开药**。医生遇到一次误拦截就会集体要求关掉整个功能。 |
| ⑦ | 眼科特有规则（散瞳药禁忌等）是本院自己定的，不在国家药典里，**没有文献出处的眼科规则无法被评审、也无法在争议时说明依据**。 |

**为什么 ⑤ 允许 `effective_to = effective_from`（同日生效同日失效）**：导入过程中可能需要「先建一个当天有效的临时规则再立刻被新版取代」，同日区间是合法中间态。若强制 `>`，则这种导入会失败并留下半成品数据。

#### 4.2.4 索引定义

| 索引名 | 定义 | 用途 |
|---|---|---|
| `pk_m18_kb_med_rule` | `(id)` | — |
| `uk_m18_kb_med_rule_code_ver` | `UNIQUE (rule_code, rule_version)` | 幂等 |
| `idx_m18_kb_med_rule_type_status` | `(rule_type, status)` | 规则管理页按类型筛 |
| `idx_m18_kb_med_rule_version_set` | `(version_set_id)` | 按版本集还原规则清单 |
| `idx_m18_kb_med_rule_published_partial` | `(rule_type) WHERE status = 'PUBLISHED'` | **热重载全量加载走这个部分索引**；`PUBLISHED` 只占全部行的 1/3，部分索引比全表索引小 2/3 |
| `gin_m18_kb_med_rule_drugs` | `GIN (drug_codes)` | 「某药品涉及哪些规则」的临时排查查询 |
| `gin_m18_kb_med_rule_diag` | `GIN (diagnosis_codes)` | 「某诊断涉及哪些规则」 |

> **为什么热重载要专门建部分索引而不是全表扫？** 加载时要读 `PUBLISHED` 规则的**全部列**（含 `rule_condition`、`alert_message`），部分索引只能加速「找到哪些行」，取列仍要回表。真正省下的是**避免全表顺序扫 24,000 行再过滤**（含 16,000 行历史版本）。实测 24,000 行全表扫约 9ms，走部分索引约 4ms + 3,000 次回表 ≈ 6ms，收益有限但方向正确。**真正的优化是加载时不读 `evidence_text`**（见 §3.3），这一条省的是 16MB 的 IO，比索引优化重要得多。

#### 4.2.6 只增不改的落地

`m18_kb_med_rule` 没有 `is_deleted` 列，且**应用账号只能更新状态列，不能更新内容列**：

```sql
-- 权限：内容列一律不可更新
REVOKE UPDATE ON m18_kb_med_rule FROM app_m18;
GRANT UPDATE (
    status, published_at, published_by, version_set_id,
    reviewed_at, reviewed_by, superseded_at, superseded_by_version,
    disabled_reason, disabled_at, updated_at, updated_by
) ON m18_kb_med_rule TO app_m18;

-- 权限：规则行永远不可删除
REVOKE DELETE ON m18_kb_med_rule FROM app_m18;

-- 触发器：内容列被改时直接报错（兜住任何绕过列权限的路径，如未来的超级用户脚本）
CREATE OR REPLACE FUNCTION trg_fn_m18_kb_med_rule_content_immutable()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.rule_code      IS DISTINCT FROM OLD.rule_code
    OR NEW.rule_version   IS DISTINCT FROM OLD.rule_version
    OR NEW.rule_type      IS DISTINCT FROM OLD.rule_type
    OR NEW.rule_condition IS DISTINCT FROM OLD.rule_condition
    OR NEW.alert_level    IS DISTINCT FROM OLD.alert_level
    OR NEW.severity       IS DISTINCT FROM OLD.severity
    OR NEW.alert_message  IS DISTINCT FROM OLD.alert_message
    OR NEW.drug_codes     IS DISTINCT FROM OLD.drug_codes THEN
        RAISE EXCEPTION 'KB_RULE_CONTENT_IMMUTABLE'
            USING HINT = '规则内容不可原地修改，请创建新版本（新 rule_version 行）';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m18_kb_med_rule_content_immutable
    BEFORE UPDATE ON m18_kb_med_rule
    FOR EACH ROW EXECUTE FUNCTION trg_fn_m18_kb_med_rule_content_immutable();
```

> **为什么触发器只拦「内容列」，放行「状态列」？** 发布动作本身就是 `UPDATE status`。若连状态一起拦，发布无法完成。**内容不可变、状态可流转**，这是全部规则表的统一模式。
>
> **注意 `rule_type` 也算内容列。** 把一条 `DOSAGE` 规则改成 `INTERACTION` 会让它的明细表引用彻底错位（`dose_rule` 里还留着记录），而且历史审核结果里的 `rule_type` 与现在的对不上。

### 4.3 表：`m18_kb_dose_rule`

#### 4.3.1 表说明

剂量上限规则的专有参数表，仅 `rule_type = 'DOSAGE'` 的规则在此有明细行，与 `m18_kb_med_rule` 是 1:1。

| 分区 | 不分区 |

| 主要写入方 | 规则发布 |
| 主要读取方 | 热重载加载器（与主表一起加载进内存） |

**为什么剂量参数单独一张表而不是塞进 `rule_condition` JSONB？** 三条理由：

1. **剂量参数要做区间比较**（实际剂量 vs 上限），进内存后是数值比较，若放在 JSONB 里要每次解析。8,000 条规则里 2,400 条是剂量规则，一次审核要比较 5~8 个药品的剂量，逐次解析 JSONB 会明显拖慢。
2. **剂量参数需要按「给药途径」区分**。口服泼尼松 60mg/日 与静滴甲泼尼龙 80mg/日 是不同规则，但「药品编码」可能相同（同一药品不同规格）。用 `(drug_code, route)` 做唯一键比在 JSONB 里嵌套更清晰。
3. **剂量参数是药师维护时最常改的东西**，独立成表后规则管理页的「剂量」标签页只查这张表，不需要在界面上解析 JSONB。

**组合语义说明：**

| 约束 | 为什么必须写组合 |
|---|---|
| 至少一个上限 | 「每个剂量字段独立可空」时，一行全部为 NULL 的剂量规则在数据库层合法，但它在审核时**永远不会命中任何超限**——这就是「规则写了但从不生效」的典型死法。它不会报错，只会静默失效，直到某天医生超量开药没人拦才发现 |
| 按体重必须以年龄为界 | `weight_per_kg` 只在儿童场景有意义。若不与 `max_age <= 18` 绑定，可能出现「成人按 5mg/kg 计算」这种荒谬规则，一次算出 300mg 的超量上限 |
| `route` 取空串 | 空串表示「所有途径」，必须与 `m18_kb_med_rule` 的规则条件一致；若存 NULL，`UNIQUE (rule_id, drug_code, route)` 的 NULL 互不相等会让重复插入通过 |

**唯一约束：**

```sql
CONSTRAINT uk_m18_kb_dose_rule UNIQUE (rule_id, drug_code, route)
```

**为什么唯一键含 `route` 而不是只用 `(rule_id, drug_code)`？** 同一条「氨基糖苷类日剂量上限」规则可能对不同途径给不同上限（肌注 5mg/kg vs 静滴 7.5mg/kg），需要两行。若唯一键不含 `route`，这两行会冲突。

```sql
CONSTRAINT ck_m18_kb_interaction_rule_severity CHECK (
    severity_grade IN ('CONTRAINDICATED','MAJOR','MODERATE','MINOR')),
CONSTRAINT ck_m18_kb_interaction_rule_mechanism CHECK (
    interaction_mechanism IN ('','PHARMACODYNAMIC','PHARMACOKINETIC','UNKNOWN')),
CONSTRAINT ck_m18_kb_interaction_rule_onset CHECK (

CONSTRAINT ck_m18_kb_interaction_rule_monitor CHECK (

    severity_grade <> 'CONTRAINDICATED' OR length(clinical_effect) > 0)
```

**`ORDER CHECK (drug_code_a < drug_code_b)` 的理由：** 相互作用是无向的（A+B 与 B+A 是一回事）。若不强制字典序，`(A,B)` 与 `(B,A)` 两行都能插入，唯一约束 `UNIQUE (rule_id, drug_code_a, drug_code_b)` 拦不住——审核时会命中两次，产生两条一模一样的提示。**这是「同一条规则重复报」最常见的成因**，而医生遇到重复提示会养成全部忽略的习惯，等于规则失效。用字典序把无向关系变成唯一的有向表达，是数据库层能做的唯一强制手段。

**组合语义说明（这条是本表的核心）：**

| 约束 | 意义 | 只写单字段会漏掉什么 |
|---|---|---|
| `special_approval` | 特殊使用级必须审批且需要副主任及以上 | 「`antibiotic_level` 取值合法」「`approval_required` 是布尔值」两条各自成立时，仍可构造「特殊使用级 + 不需审批 + 住院医师可开」的行。**这是把最严管控的药品配成最松的规则**，在抗菌药物专项检查中直接判定为不合格。 |

#### 4.5.4 抗菌分级与执业资格的联动判定

本表定义的是「规则」，实际判定发生在 M18-05 的 P-08 中，链路如下：

```
P-08 收到处方（items 里某药 drug_code 命中本表）
   │
   ├─ ① 读本表：antibiotic_level / required_staff_level / approval_required / exceed_action
   │
   ├─ ② 若 practice_check_required = TRUE
   │     调 U-12  GET /internal/v1/staff/{staff_id}/practice-check   （P95 ≤ 100ms）
   │     返回该医生的处方权级别（RESIDENT/ATTENDING/SENIOR/DIRECTOR）
   │     ├─ 调用超时  → 本不产生提示，整次审核置 degraded = TRUE
   │     │             reason = "PRACTICE_CHECK_TIMEOUT"（不是"通过"，是"没审到"）
   │     └─ 调用正常  → 继续 ③
   │
   ├─ ③ 比较：医生级别 >= required_staff_level ?
   │     ├─ 是 → 不产生提示
   │     └─ 否 → 按 exceed_action 产生提示（BLOCK/SEVERE/WARN）
   │
   └─ ④ 若 approval_required = TRUE 且医生级别不足
         提示文案追加「需 {approval_role} 审批」，并在 alerts 中置 must_ack = TRUE
```

**本院是否设特例：**

| 场景 | 本院规则 | 落在哪个字段 |
|---|---|---|
| A 院区的主任医师 | **不设级别特例。** 特殊使用级抗菌药在 A 院区同样需要审批，主任医师也不例外 | `local_policy_note = '本院不设院区级别特例'` |
| 特需门诊 | **不设特例。** 特需门诊的特殊使用级抗菌药同样需审批 | `local_policy_note = '本院不设门诊类型特例'` |
| 急诊科夜间值班 | **设唯一特例：** 夜间（20:00~次日 08:00）无审批人在场时，允许先用药后补审批，但必须 `must_ack` 且在 24 小时内补办 | `approval_required = TRUE` + `local_policy_note = '急诊夜间可先用后补，24h 内补办审批'` |

> **写清「本院不设特例」比留白重要。** 留白会被实现者理解成「这里可能有特例，先按有特例实现」，而实际不存在的特例一旦被实现，就成了一条可以被利用的绕过路径——「我是主任医师」就能跳过特殊使用级审批。

### 4.6 表：`m18_kb_rule_version_set`

#### 4.6.1 表说明

**规则版本集**，本子模块最重要的设计之一。每次规则发布生成一行，代表「某时刻生效的规则全集」这一整体快照。

| 项 | 说明 |
|---|---|

| 分区 | 不分区 |
| 3 年行数 | 约 360（每次发布一行，按每周 2~3 次发布估算） |
| 主要写入方 | 规则发布服务（发布事务的最后一步） |
| 主要读取方 | P-08 响应（返回 `rule_version_set`）、历史审核结果复现、热重载加载器 |
| 是否进内存 | **是**（只进当前生效的那一个） |

#### 4.6.2 为什么需要「版本集」而不是「每条规则各自一个版本号」

这是知识类系统最容易搞错的地方，必须写清。

**问题场景**：假设有 8,000 条规则，每条有自己的 `rule_version`。某天发布了 3 条规则的新版（版本号都是 `20261021_001`），其余 7,997 条仍是旧版（版本号 `20260915_002`）。此时如果审核结果只记录「我用了哪些规则版本」，那就是 8,000 个版本号的组合，**无法归因**。

**更严重的是「单条回滚」**：如果允许把某一条规则回滚到旧版，就会出现「A 规则是新版、B 规则是旧版」的状态。此时：

- 事后问「2026-10-21 14:30 那张处方为什么被拦」——答案可能是「因为 A 规则新版」，但这个组合在历史上从没被定义为「一个版本」，任何报表都无法聚合。
- 两家医院（或多实例）在同一时刻可能处于不同的混合状态，而它们记录的都是「相同」的规则版本号组合。

**解法：版本集 = 某时刻生效的规则全集，有一个整体版本号。**

| 概念 | 字段 | 例子 |
|---|---|---|
| 版本集号（对外） | `rule_version_set` | `20261021_003` |
| 版本集流水号（对内） | `version_set_no` | `KBS20261021003` |
| 集内的规则清单 | 由 `m18_kb_med_rule.version_set_id` 反查 | 8,000 条 |

**规则发布 = 创建一个新版本集，并把「全部当前生效规则」重新挂到新集上。** 注意是「重新挂全部」，不是「只挂本次变更的 3 条」——因为版本集的含义是「全集」，不是「增量」。

> **代价必须写清：每次发布都要把 8,000 条规则行的 `version_set_id` 更新一遍。** 这个代价是可接受的：①8,000 行的 `UPDATE` 在 PostgreSQL 上是单事务约 120ms；②发布是低频操作（每周 2~3 次）；③换来的是「任意历史审核结果都能用一个字符串精确还原规则全集」。**反过来说，如果为了省这 120ms 而只改增量，就要在查询时做「按时间合并多次增量」的推导，那是每次审核都在付成本。**

```sql
    load_status IN ('PENDING','LOADED','PARTIAL','FAILED')),
CONSTRAINT ck_m18_kb_rule_version_set_count CHECK (rule_count > 0),
CONSTRAINT ck_m18_kb_rule_version_set_change CHECK (change_count >= 0),
CONSTRAINT ck_m18_kb_rule_version_set_instance CHECK (
    loaded_instance_count BETWEEN 0 AND expected_instance_count),
CONSTRAINT ck_m18_kb_rule_version_set_loaded CHECK (
    load_status <> 'LOADED'
    OR (activated_at IS NOT NULL AND loaded_instance_count = expected_instance_count)),
CONSTRAINT ck_m18_kb_rule_version_set_checksum CHECK (length(checksum) = 64)
```

**组合语义说明：**

| 约束 | 为什么必须组合 |
|---|---|
| `loaded` | 「`load_status` 取值合法」「`activated_at` 可空」两条各自成立时，仍可构造 `load_status = 'LOADED'` 但 `loaded_instance_count = 0`、`activated_at = NULL` 的行。**这等于声称「全部实例都已生效」而实际一个都没加载**。多实例部署时，如果某个实例没收到重载事件，它的 `rule_version_set` 会停留在旧值，而版本集表说「已 LOADED」—— 此时两实例审核结果不一致且无人知晓。 |
| `checksum` 长度 64 | SHA-256 十六进制固定 64 字符。若允许任意长度，运维脚本无法据此判断「这是不是完整算完了」 |

### 4.9 表：`m18_kb_path_entry`

#### 4.9.1 表说明

路径入径实例表，记录「某患者在某次就诊中实际入了哪条路径、走到了哪一步」。**本子模块唯一分区的业务表。**

| 项 | 说明 |
|---|---|
| 表类型 | 业务事实（只增不改，状态可流转） |
| 分区 | **按年 `PARTITION BY RANGE (entered_at)`** |
| 3 年行数 | 约 54,000（年均 1.8 万） |
| 主要写入方 | 入径操作（P-12 之后的写路径）、入径自动判定任务 |
| 主要读取方 | P-12、路径统计（入径率/变异率/完成率）、患者路径详情页 |
| 是否进内存 | **否** |

#### 4.9.2 为什么这张表要分区（尽管它只有 5.4 万行）

数据结构设计汇总 §4 已定「`m18_kb_*` 配置与主数据类不分区」。本表不属于配置类，是**业务事实**，且分区的理由是**保留期迁移**而不是当前数据量：

| 理由 | 展开 |
|---|---|
| **入径实例会随年份无限增长** | 年均 1.8 万，10 年 18 万，20 年 36 万。医疗记录不可删，所以这不是「到量再考虑」的问题 |
| **3 年后迁归档库要能秒级执行** | 用 `DELETE WHERE entered_at < '2024-01-01'` 删 5.4 万行会锁表并产生大量 WAL；`DETACH PARTITION` 是元数据操作，毫秒级 |
| **查询总带时间范围** | 所有统计都按期间查（「2026 年 10 月入径率」），按年分区能分区裁剪 |

**为什么按年而不是按月**：年 1.8 万行按月分只有 1,500 行/月，3 年就有 36 个分区。PostgreSQL 的查询规划时间随分区数上升（超过 100 个分区后明显），36 个分区带来的规划开销超过裁剪收益。**按年是行数与分区数的平衡点。**

**分区键选择 `entered_at` 而不是 `created_at`**：入径实例的业务时间就是入径时间，两者通常相同但语义不同（数据补录时 `created_at` 晚于 `entered_at`）。统计按 `entered_at` 筛，所以分区键必须是 `entered_at`，否则分区裁剪失效。

**唯一约束：**

```sql
CONSTRAINT uk_m18_kb_path_entry_no UNIQUE (entry_no, entered_at)
```

> ⚠️ **分区表的唯一约束必须包含分区键。** 共享规范 §2.5 要求「路径入径唯一键 `(path_code, patient_id, encounter_id)`」，但 PostgreSQL 不允许分区表的唯一约束不含分区键。**所以 `(path_code, patient_id, encounter_id)` 这条业务唯一性无法在数据库层用 UNIQUE 强制。**

**这是分区决策付出的真实代价，必须写清并用替代方案堵住：**

| 方案 | 是否可行 | 说明 |
|---|---|---|
| `UNIQUE (path_code, patient_id, encounter_id, entered_at)` | ❌ 无效 | 加了 `entered_at` 后，同患者同就诊在同一秒之外可重复插入，唯一性形同虚设 |
| 全局 `EXCLUDE` 约束 | ❌ 不支持 | PostgreSQL 的 `EXCLUDE` 在分区表上要求包含分区键，同为分区局限 |
| **应用层幂等 + Redis 唯一锁** | ✅ 采用 | 入径前用 `SET m18:idem:path-entry:{path_code}:{patient_id}:{encounter_id} NX EX 86400`，成功后写入数据库；重复请求被 Redis 拦下 |
| **巡检 SQL（附录 B.3）** | ✅ 采用 | 每日巡检「同一 `(path_code, patient_id, encounter_id)` 出现多行」，发现即告警并人工清理 |

> **这个取舍必须明确记录，不能假装分区表的唯一约束和普通表一样。** 分区带来的迁移便利，代价就是失去跨分区唯一性保证，必须用应用层 + 巡检补上。**如果评审认为「入径唯一性比迁移便利更重要」，那就应该放弃分区，这是一个需要决策者知情的权衡。**

**枚举与组合 CHECK：**

```sql
CONSTRAINT ck_m18_kb_path_entry_status CHECK (
    status IN ('ENTERED','IN_PROGRESS','COMPLETED','EXITED','DEVIATED')),
CONSTRAINT ck_m18_kb_path_entry_mode CHECK (
    entry_mode IN ('MANUAL','AUTO','IMPORT')),
CONSTRAINT ck_m18_kb_path_entry_enc_type CHECK (
    encounter_type IN ('OUTPATIENT','INPATIENT','DAY_SURGERY')),
CONSTRAINT ck_m18_kb_path_entry_exit_type CHECK (
    exit_type IS NULL OR exit_type IN ('MERGE_DISEASE','PATIENT_REFUSE','TRANSFER','DEATH','OTHER')),
CONSTRAINT ck_m18_kb_path_entry_completed CHECK (
    status <> 'COMPLETED' OR (completed_at IS NOT NULL AND actual_days IS NOT NULL)),
CONSTRAINT ck_m18_kb_path_entry_exited CHECK (
    status <> 'EXITED'
    OR (exited_at IS NOT NULL AND exit_reason IS NOT NULL AND exit_type IS NOT NULL)),
CONSTRAINT ck_m18_kb_path_entry_deviated CHECK (
    status <> 'DEVIATED' OR deviation_count > 0),
CONSTRAINT ck_m18_kb_path_entry_deviation_count CHECK (deviation_count >= 0),
CONSTRAINT ck_m18_kb_path_entry_nodes CHECK (
    completed_node_count BETWEEN 0 AND total_node_count),
CONSTRAINT ck_m18_kb_path_entry_no_exit_reason CHECK (
    status = 'EXITED' OR (exit_reason IS NULL AND exit_type IS NULL AND exited_at IS NULL))
```

**`no_exit_reason` 是反向约束，这是本表最关键的一条：**

只写「`EXITED` 必须有退出原因」时，一条 `COMPLETED` 的记录仍可携带 `exit_reason = '患者拒绝'` 与 `exit_type = 'PATIENT_REFUSE'`——**数据库层完全合法**。后果是：统计「退出原因分布」时这条已完成记录会被计入「患者拒绝退出」，退出率虚高，医务科会去追查一批根本没退出的人。

**必须正反双向**：`status = 'EXITED'` ⟺ 有退出三字段。用 SQL 表达成 `status = 'EXITED' OR (三字段都为空)`。

### 4.10 表：`m18_kb_path_deviation`

#### 4.10.1 表说明

路径变异记录表。每次发生变异（延长、缩短、跳过节点、增加节点、退出路径）写入一行，**只增不改**。

| 项 | 说明 |
|---|---|
| 表类型 | 业务事实（只增不改，无状态流转） |
| 分区 | 不分区（3 年 7,200 行，量小） |
| 主要写入方 | 变异登记（P-12 相关的写路径）、自动变异判定任务 |
| 主要读取方 | 变异分析报表、路径详情页 |
| 是否进内存 | **否** |

**为什么不分区**：3 年 7,200 行且查询总带 `entry_id`（先定位到入径实例再看它的变异），是按主键关联查询，不需要时间裁剪。

#### 4.10.3 约束定义

```sql

    deviation_type IN ('EXTEND','SHORTEN','SKIP_NODE','ADD_NODE','EXIT_PATH','OTHER')),

CONSTRAINT ck_m18_kb_path_deviation_node CHECK (
    deviation_type IN ('EXIT_PATH','EXTEND','SHORTEN','OTHER') OR length(node_code) > 0),
CONSTRAINT ck_m18_kb_path_deviation_days CHECK (
    deviation_type NOT IN ('EXTEND','SHORTEN')
    OR (affected_days IS NOT NULL AND affected_days > 0))
```

**组合语义说明：**

| 约束 | 为什么必须组合 |
|---|---|
| `node` | `SKIP_NODE` 与 `ADD_NODE` 必须指明是哪个节点。若 `node_code` 为空，这条变异在报表里就是「跳过了一个不知道是什么的节点」，无法归因到具体环节，也就无法整改 |
| `days` | 延长/缩短变异必须给出天数差。否则「平均延长天数」这个指标算不出来，而它是路径优化最直接的输入 |

**为什么本表没有唯一约束**：同一条路径的同一次入径可以在同一个节点上变异多次（先延长 2 天、又延长 3 天）。变异是事件流，不是状态，每次都该留一行。

### 4.11 表：`m18_kb_ophth_entry`

#### 4.11.1 表说明

眼科专科知识条目。存放不满足「用药规则」结构、但要作为知识沉淀下来的眼科临床要点：术式适应症与禁忌、围手术期注意、并发症识别与处置、特殊检查判读要点。

**本表与 `m18_kb_med_rule` 的区别是根本性的：**

| 维度 | `m18_kb_med_rule` | `m18_kb_ophth_entry` |
|---|---|---|
| 用途 | **机器求值**，命中即出提示 | **人读**，供医生在病历书写/术前讨论时查阅 |
| 是否进内存 | 是（37.5MB 预算的一部分） | 否，按需查库 |
| 是否影响审核结果 | 是（决定 `check_result`） | 否，**不改任何审核结论** |
| 触发方式 | P-08 请求到达时自动匹配 | 用户主动检索（关键词/诊断/术式） |
| 变更影响 | 需热重载、需版本集 | 无需热重载，发布即生效 |

> **为什么眼科知识不全部做成规则？** 能做成规则的必须满足「条件可枚举、判定可二值化」。「抗 VEGF 注射后 3 天内出现眼压升高需警惕」这种可以做成规则；而「玻璃体切除术后体位护理要点」这类是操作指导，没有触发条件，也无法给出 PASS/FAIL 结论。强行做成规则会导致两类问题：一是医生被大量无行动价值的提示淹没，最终把整个提示功能关掉；二是规则库体积膨胀，撑破 40MB 内存预算。所以本表的内容**只被检索、不被求值**，这个边界必须在开发时守住。

### 4.12 表：`m18_kb_drg_weight`

#### 4.12.1 表说明

DRG 分组权重，按医保局年度发布导入。M05-07 用它算 CMI（病例组合指数），是本子模块唯一的「主数据副本」类表。

**与规则表的根本区别：这张表的旧版本不是「被取代」，而是「曾经有效」。**

规则表里旧版本置 `SUPERSEDED` 意味着它不再适用于新业务；DRG 权重不同，2025 年的权重对 2025 年的病案永远正确，2026 年导入新权重并不使 2025 年权重变错。所以本表**不设 `status` 状态机**，而是用 `effective_from` / `effective_to` 表达时间区间，历史版本永久保留且始终可查。

> **这就是 P-09 必须支持按日期查询的原因。** M05-07 做 2025 年 11 月的 CMI 报表，必须用 2025 年的权重，用 2026 年的权重算出来的数字无法与当时的医保结算对账。任何「只保留当前权重」的设计（比如每次导入直接 UPDATE 覆盖）都会让历史报表永久失真。

#### 4.12.2 字段定义

| 字段名 | 类型 | 可空 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | IDENTITY | 主键 |
| `drg_code` | VARCHAR(32) | 否 | — | DRG 分组编码 |
| `drg_name` | VARCHAR(256) | 否 | — | 分组名称 |
| `drg_type` | VARCHAR(32) | 否 | — | 分组类型，见 4.12.3 |
| `mdc_code` | VARCHAR(16) | 否 | `''` | 主要诊断大类编码 |
| `adrg_code` | VARCHAR(32) | 否 | `''` | ADRG 编码 |
| `weight` | NUMERIC(10,6) | 否 | — | 权重值，CMI 的分子 |
| `rate_multiplier` | NUMERIC(10,6) | 否 | `1.000000` | 费率调整系数（各地政策差异） |
| `min_cost` | NUMERIC(14,2) | 是 | NULL | 最低费用参考，**留库不进内存** |
| `avg_cost` | NUMERIC(14,2) | 是 | NULL | 平均费用参考，**留库不进内存** |

| `imported_at` | TIMESTAMP | 否 | `now()` | 导入时间 |

#### 4.12.3 枚举取值

| 枚举 | 取值 |
|---|---|
| `drg_type` | `SURGICAL`（手术组）/`MEDICAL`（内科组）/`OPERATION`（操作组）/`UNGROUPED`（未入组，权重固定 0） |

> `UNGROUPED` 必须存在且必须参与统计：医保结算里确实有无法入组的病例，其权重按 0 计。如果把它们从分组表里删掉，M05-07 算 CMI 时会出现「找不到权重的病例」，进而要么报错要么被静默丢弃——**静默丢弃会让 CMI 虚高**，因为丢掉的都是低权重病例。

#### 4.12.4 约束定义

**唯一约束：**

- `uk_m18_kb_drg_weight_code_ver`：`UNIQUE (drg_code, version)` —— 同一版本内同一分组只能有一条。

**组合语义 CHECK：**

| 约束名 | 表达式 | 防住什么 |
|---|---|---|
| `ck_m18_kb_drg_weight_effective` | `effective_to IS NULL OR effective_to >= effective_from` | 生效区间反了 |
| `ck_m18_kb_drg_weight_weight_range` | `weight >= 0 AND weight <= 50` | 权重异常（本院实际分布在 0~12 之间，50 是安全上界；医保局未出现超过 50 的权重） |
| `ck_m18_kb_drg_weight_ungrouped` | `drg_type <> 'UNGROUPED' OR weight = 0` | 未入组病例权重必须为 0 |
| `ck_m18_kb_drg_weight_grouped` | `drg_type = 'UNGROUPED' OR weight > 0` | 已入组病例权重不得为 0，否则等于没分组 |
| `ck_m18_kb_drg_weight_current` | `is_current = false OR effective_to IS NULL` | 「今日生效」标记只允许打在没有截止日的版本上；若打了截止日还要标 current，说明标记没维护 |
| `ck_m18_kb_drg_weight_mdc` | `drg_type = 'UNGROUPED' OR length(mdc_code) > 0` | 已入组病例必须有 MDC 编码 |

> **`ck_..._ungrouped` 与 `ck_..._grouped` 为什么要两条？** 单独写 `weight >= 0` 只挡住了负数。把 `drg_type` 从 `SURGICAL` 改成 `UNGROUPED` 但不改权重（还是 3.5），单列约束全部通过，而这条数据在 CMI 计算里会贡献一个本不该存在的 3.5——**这正是「CHECK 只保护字段自身、不保护组合语义」的典型漏口**。两条 CHECK 一起构成双向判定：未入组必须 0，已入组必须非 0。

**`is_current` 的维护是数据一致性的关键点，写清落地方式：**

```sql
-- 导入新版本后，在同一事务里重设 is_current
WITH today AS (SELECT CURRENT_DATE AS d)
UPDATE m18_kb_drg_weight w
   SET is_current = (w.effective_from <= (SELECT d FROM today)
                     AND (w.effective_to IS NULL OR w.effective_to >= (SELECT d FROM today))),
       updated_at = now(),
       updated_by = :operator_id;
```

> 这段 SQL 每次导入后全表重算 `is_current`。它只有约 360 行（120 条 × 3 年版本），全表 UPDATE 的代价可以忽略，换来的是**单一事实来源**：`is_current` 永远是 `effective_from`/`effective_to` 的函数，不存在两处维护不同步。**替代做法是在导入时只置新版本为 true、把旧版本置 false**，那样一旦有版本的中止日期被人工改过，`is_current` 就会与实际生效区间脱节，而这种脱节没有任何约束能发现。

#### 4.12.5 索引定义

| 索引名 | 类型 | 字段 | 用途 |
|---|---|---|---|
| `pk_m18_kb_drg_weight` | PRIMARY KEY | `id` | 主键 |
| `uk_m18_kb_drg_weight_code_ver` | UNIQUE | `(drg_code, version)` | 同版本内分组唯一 |
| `idx_m18_kb_drg_weight_current_partial` | BTREE | `(drg_code, weight)` WHERE `is_current = true` | **P-09 默认查询的主索引**，只扫当日生效版本 |
| `idx_m18_kb_drg_weight_effective` | BTREE | `(effective_from, effective_to)` | 按日期查历史版本 |
| `idx_m18_kb_drg_weight_version` | BTREE | `(version)` | 版本清单、按版本导入对账 |

> **`idx_..._current_partial` 是 P-09 能否满足 500ms 的关键。** 全表 360 行，反而不用部分索引也行；但 P-09 也支持按历史日期查询，那种查询要按 `effective_from/effective_to` 区间扫描，用 `idx_..._effective`。两条索引分工明确：查今日走部分索引（只扫约 120 行），查历史走区间索引。

| 现象 | 判据 | 说明什么问题 |
|---|---|---|
| 命中率过高 | 单规则 `hit_rate > 0.8` | 多半是误报。医生不可能天天开错药，一条规则在 80% 的处方上都报警，说明条件写宽了（比如「老年人慎用」写成了「年龄 > 60」） |
| 命中率为零 | `trigger_count = 0` 连续 90 天 | 多半是死规则。要么触发条件写错、要么 P-08 请求里根本没有它依赖的字段、要么药品编码对不上 |
| 医生全部忽略 | `ignore_count / trigger_count > 0.9` | 提示语没用，或等级定错了。医生不看的东西就是在训练医生不看所有提示 |

> **为什么不用 M18-05 的审核明细直接查？** M18-05 的明细表是按次记录（日均 1,500 张处方 × 平均 2.3 条提示 ≈ 3,450 行/天），查「某规则过去 90 天命中率」要扫约 31 万行。按日聚合后，90 天 × 8,000 条规则最多 72 万行但绝大多数规则当天没命中，实际写入只有日均约 600 行（只写触发过的规则），90 天约 5.4 万行。**聚合的代价是每天一次 GROUP BY，收益是全年任何一次复审查询都不超过 10 万行扫描。**

> **`hit_rate` 的分母不是 `trigger_count`。** 命中率是「这条规则在多少比例的处方上报警」，分母是当日该规则适用范围内的审核处方总数，这个数存在聚合任务的输入参数里而不是本表。本表只存分子 `trigger_count` 与结果 `hit_rate`。把分母也存进来会让本表膨胀一倍，而分母对所有规则是同一个数，属于可推导的冗余。

#### A.1.3 聚合任务

```sql
-- 每日 03:10 聚合前一日命中明细
INSERT INTO m18_kb_hit_stat (
    stat_date, rule_id, rule_code, rule_version, rule_type,
    hit_count, trigger_count, ack_count, ignore_count, hit_rate
)
SELECT
    d.stat_date,
    d.rule_id,
    d.rule_code,
    d.rule_version,
    d.rule_type,
    COUNT(*)                                        AS hit_count,
    COUNT(*)                                        AS trigger_count,
    COUNT(*) FILTER (WHERE d.ack_flag)              AS ack_count,
    COUNT(*) FILTER (WHERE NOT d.ack_flag)          AS ignore_count,
    CASE WHEN :prescription_total > 0
         THEN ROUND(COUNT(*)::numeric / :prescription_total, 6)
         ELSE NULL
    END                                             AS hit_rate
FROM m18_qc_med_alert_hit d
WHERE d.hit_date = :yesterday
GROUP BY d.stat_date, d.rule_id, d.rule_code, d.rule_version, d.rule_type
ON CONFLICT (stat_date, rule_code, rule_version) DO UPDATE
   SET hit_count     = EXCLUDED.hit_count,
       trigger_count = EXCLUDED.trigger_count,
       ack_count     = EXCLUDED.ack_count,
       ignore_count  = EXCLUDED.ignore_count,
       hit_rate      = EXCLUDED.hit_rate,
       created_at    = now();
```

> **`ON CONFLICT DO UPDATE` 而不是 `DO NOTHING`**：M18-05 的明细可能当天晚到（比如夜间批处理延迟到次日），重跑聚合必须能把新数据算进去。`DO NOTHING` 会让重跑变成无效操作，而补数场景下这正是最需要它生效的时候。

### A.2 `m18_kb_reload_log` 规则热重载日志

#### A.2.1 设计意图

热重载是「不中断」的，但**不中断不等于无感知**。没有这张表，以下三个问题都无法回答：

1. 昨天 03:30 那次重载到底成功了吗，还是静默回退了旧规则？

3. 某次重载耗时 1,800ms 已经逼近 P-13 的 2000ms 预算，是偶发还是趋势？

```sql
       COALESCE(SUM(h.trigger_count), 0) AS total_trigger
```

```sql
-- 命中率过高（>80%）的规则（候选复审误报清单）
SELECT rule_code, rule_version, rule_type,
       SUM(trigger_count) AS triggers,
       ROUND(AVG(hit_rate)::numeric, 4) AS avg_hit_rate,
       SUM(ignore_count) AS ignores
FROM m18_kb_hit_stat
WHERE stat_date >= CURRENT_DATE - INTERVAL '90 days'
GROUP BY rule_code, rule_version, rule_type
HAVING AVG(hit_rate) > 0.8
ORDER BY AVG(hit_rate) DESC;
```

> **上面这条用 `AVG(hit_rate)` 是对的，而汇总完成率时不行。** 命中率的分母（当日审核处方数）每天不同，求平均会偏向处方量少的日子。这里之所以可以，是因为分母变化平缓（日均 1,500 上下浮动 5% 以内）且规则复审看的是量级（80% 以上一律复审），不是精确值。**如果是精确报表，必须用 `SUM(trigger_count) / SUM(分母)` 重算。** 这个区别在详细设计 §3.4.3 有完整论证。

## 附录 C 内存 RuleSet 数据结构

规则常驻内存是本子模块的硬约束（详细设计 §7.3）。本附录给出 `RuleSet` 的精确结构，使「内存 ≈ 40MB」这个数字可核对。

### C.1 顶层结构

```python
"""内存规则集结构定义（不落库，仅运行时存在）。"""

from __future__ import annotations

from dataclasses import dataclass, field
from datetime import date
from typing import Callable


@dataclass(frozen=True, slots=True)
class RuleHeader:
    """规则头。不可变（frozen），切换规则集是换引用而不是改内容。"""

    rule_code: str
    rule_version: int
    rule_type: str
    alert_level: str
    severity: int
    alert_message: str
    advice: str
    evidence_ref: str
    effective_from: date
    effective_to: date | None


@dataclass(frozen=True, slots=True)
class ConditionNode:
    """条件树节点。求值时递归遍历，不解释字符串。"""

    kind: str
    field: str = ""
    op: str = ""
    value: object = None
    children: tuple["ConditionNode", ...] = ()


@dataclass(frozen=True, slots=True)
class CompiledRule:
    """编译后的规则：条件已解析为条件树，不再保留 JSON 文本。"""

    header: RuleHeader
    condition: ConditionNode
    drug_codes: tuple[str, ...]
    diagnosis_codes: tuple[str, ...]


@dataclass(frozen=True, slots=True)
class RuleSet:
    """一个不可变的规则全集。切换 = 原子替换 self._current 引用。"""

    rule_version_set: str
    checksum: str
    loaded_at: float
    drug_index: dict[str, tuple[CompiledRule, ...]]
    diagnosis_index: dict[str, tuple[CompiledRule, ...]]
    type_index: dict[str, tuple[CompiledRule, ...]]
    universal_rules: tuple[CompiledRule, ...]
    drg_weights: dict[str, float]
    rule_total: int


@dataclass
class RuleSetHolder:
    """双缓冲持有者。后台重建新集，就绪后原子切换引用。"""

    _current: RuleSet
    _building: RuleSet | None = field(default=None, init=False)
    _refcount: dict[str, int] = field(default_factory=dict, init=False)

    def snapshot(self) -> RuleSet:
        """取当前规则集引用并加计数；调用方用完必须 release。"""
        rs = self._current
        self._refcount[rs.rule_version_set] = self._refcount.get(rs.rule_version_set, 0) + 1
        return rs

    def release(self, rs: RuleSet) -> None:
        cnt = self._refcount.get(rs.rule_version_set, 1) - 1
        if cnt <= 0:
            self._refcount.pop(rs.rule_version_set, None)
        else:
            self._refcount[rs.rule_version_set] = cnt

    def swap(self, new_set: RuleSet) -> None:
        """原子切换。旧集不立即释放，等引用计数归零。"""
        self._current = new_set


def evaluate(node: ConditionNode, ctx: dict[str, object]) -> bool:
    """条件树求值。纯函数，无副作用，可安全并发。"""
    if node.kind == "AND":
        return all(evaluate(c, ctx) for c in node.children)
    if node.kind == "OR":
        return any(evaluate(c, ctx) for c in node.children)
    if node.kind == "NOT":
        return not evaluate(node.children[0], ctx)
    left = ctx.get(node.field)
    if left is None:
        return False
    op = node.op
    if op == "EQ":
        return left == node.value
    if op == "NE":
        return left != node.value
    if op == "GT":
        return left > node.value
    if op == "GE":
        return left >= node.value
    if op == "LT":
        return left < node.value
    if op == "LE":
        return left <= node.value
    if op == "IN":
        return left in node.value
    if op == "CONTAINS_ANY":
        return bool(set(left) & set(node.value))
    return False
```

### C.2 内存占用核对

| 组成部分 | 单条/单项 | 数量 | 小计 |
|---|---|---|---|
| `RuleHeader` + Python 对象头 | 约 600 B | 8,000 条 | 4.8 MB |
| 条件树（平均 12 个节点 × 约 100 B） | 约 1,200 B | 8,000 条 | 9.6 MB |
| `drug_index` 倒排（900 个药品 × 平均 2.5 条规则 × 约 1 KB 引用开销） | — | — | 2.3 MB |
| `diagnosis_index` 倒排（400 个诊断 × 平均 2 条） | — | — | 0.8 MB |
| `type_index` + `universal_rules` | — | — | 0.1 MB |
| `drg_weights` 字典（120 条） | 约 200 B | 120 条 | 0.024 MB |
| 字符串驻留与包开销的余量 | — | — | 5.0 MB |
| **进内存小计** | | | **约 22.6 MB** |
| 运行时峰值（双缓冲期间新旧两集同时存在） | ×2 | — | **约 45.2 MB** |

> **双缓冲期间内存翻倍是必须算进去的。** 只在稳态时说「22.6MB」会让人以为 40MB 预算宽裕一倍；实际重载瞬间两集共存，若只按稳态估算，重载时就会撞上容器内存上限被 OOM Killer 杀掉——**而重载恰恰是最不能挂的时刻**。所以部署时容器内存限制应不小于 512MB，为双缓冲留出足够余量。
>
> **初始估算 37.5MB 与本次核对 22.6MB 的差异来源**：3.3 节按「字符串重新分配而不驻留」的保守口径估算，本附录按「`alert_message` 与 `evidence_ref` 在 8,000 条规则中实际去重后驻留」的口径估算。**取两者中较大的 37.5MB 作为设计值**，因为它才是上限；本附录的 22.6MB 用于解释为什么稳态下不会接近上限。

### C.3 加载与切换时序

| 步骤 | 动作 | 失败处理 |
|---|---|---|
| 1 | 记 `started_at`，写 `m18_kb_reload_log`（`load_status = 'PARTIAL'`） | 写日志失败不阻断加载 |
| 2 | 从 `m18_kb_med_rule` 及三张明细表读全部 `status = 'PUBLISHED'` 且当日生效的规则 | 读失败 → 保留旧集，写 `FAILED` + `fail_reason` |
| 3 | 逐条把 `rule_condition` 解析为条件树，建三个倒排索引 | 单条解析失败 → 跳过该条并计入 `PARTIAL`，**不整体失败** |
| 4 | 读 `m18_kb_drg_weight` 当日生效版本 | 读失败 → 权重置空字典，`PARTIAL` |
| 5 | 校验 `rule_count` 与 `m18_kb_rule_version_set.rule_count` 是否一致 | 不一致 → `PARTIAL` 并告警，但仍切换 |
| 6 | 构造新 `RuleSet`，调 `holder.swap(new_set)` | — |
| 7 | 等待旧集引用计数归零后释放 | 超时 30s 未归零 → 记日志，不强制释放 |
| 8 | 更新 `m18_kb_rule_version_set.loaded_instance_count`，写 `SUCCESS` | — |

> **第 3 步「单条失败不整体失败」是刻意的。** 8,000 条规则里有一条 JSON 结构写坏，若整体失败就意味着这次发布完全不能生效，而运营方会反复重试同一次发布、反复失败。跳过坏规则并标记 `PARTIAL`，可以让 7,999 条正常生效，同时把坏规则暴露在重载日志里等人修。**代价是「部分规则静默失效」，所以 `PARTIAL` 必须同时推告警，不能只记日志。**


## 附录 D JSONB 字段结构定义

共享规范 §2.6 要求「大字段 JSONB 必须写清结构」。本附录逐字段给出结构定义与实例。

### D.1 `m18_kb_med_rule.rule_condition`

触发条件的条件树。支持 AND / OR / NOT 三种逻辑节点与九种比较节点。

| 键 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `kind` | string | 是 | 节点类型：`AND` / `OR` / `NOT` / `COMPARE` |
| `field` | string | COMPARE 时必填 | 取值的字段名，见 D.1.1 |
| `op` | string | COMPARE 时必填 | 比较运算符，见 D.1.2 |
| `value` | any | COMPARE 时必填 | 比较值；`IN` / `CONTAINS_ANY` 时为数组 |
| `children` | array | 逻辑节点必填 | 子节点数组；`NOT` 恰好一个 |

**D.1.1 可引用字段白名单**

条件里只能引用下列字段，其它字段一律不认（校验期报错，运行期不命中）：

| 字段 | 来源 | P-08 请求是否已有 | 说明 |
|---|---|---|---|
| `drug_code` | `items[].drug_code` | 有 | 药品编码 |
| `route` | `items[].route` | 有 | 给药途径 |
| `dosage` | `items[].dosage` | 有 | 单次剂量 |
| `frequency` | `items[].frequency` | 有 | 频次 |
| `days` | `items[].days` | 有 | 用药天数 |
| `amount` | `items[].amount` | 有 | 总量 |
| `age` | 顶层 `age` | 有 | 患者年龄 |
| `gender` | 顶层 `gender` | 有 | 性别 |
| `is_pregnant` | 顶层 `is_pregnant` | 有 | 是否妊娠 |
| `renal_level` | 顶层 `renal_level` | 有 | 肾功能分级 |
| `diagnosis_codes` | 顶层 `diagnosis_codes` | 有 | 诊断编码数组 |
| `allergy_codes` | 顶层 `allergy_codes` | 有 | 过敏编码数组 |
| `check_scene` | 顶层 `check_scene` | 有 | 审核场景 |
| `iop` | — | **无** | 眼压，P-08 当前不带 |
| `acd` | — | **无** | 前房深度，P-08 当前不带 |

> **这张白名单是本子模块与 M18-05 之间最重要的一份契约。** 上表第 13、14 行的两个字段在 P-08 请求里**不存在**，所以规则若引用它们就永远不会命中。这不是设计缺陷而是硬约束：眼压与前房深度存在 M10 视光与 M12 检查，P-08 的调用方（M07-05 开方页面）在开方瞬间并不持有这两个值，为它们加一次跨模块调用会把 300ms 预算打穿。
>
> 因此「糖皮质激素滴眼液长期使用与高眼压」这条本院重点规则，**当前只能用 `days`（用药天数）与 `diagnosis_codes`（既往青光眼史）两个条件表达，不能引用实时眼压**。详细设计 §2.6 说明了这个退化写法的具体形式与噪声控制手段。

**D.1.2 比较运算符**

| `op` | value 类型 | 语义 |
|---|---|---|
| `EQ` | 标量 | 等于 |
| `NE` | 标量 | 不等于 |
| `GT` / `GE` / `LT` / `LE` | 数值或日期 | 比较 |
| `IN` | 数组 | 属于 |
| `CONTAINS_ANY` | 数组 | 与被测数组有交集 |

**D.1.3 实例：散瞳药与闭角型青光眼禁忌**

```json
{
  "kind": "AND",
  "children": [
    {
      "kind": "COMPARE",
      "field": "drug_code",
      "op": "IN",
      "value": ["DRUG_TROPICAMIDE", "DRUG_PHENYLEPHRINE", "DRUG_ATROPINE", "DRUG_CYCLOPENTOLATE"]
    },
    {
      "kind": "COMPARE",
      "field": "diagnosis_codes",
      "op": "CONTAINS_ANY",
      "value": ["H40.201", "H40.202", "H40.203"]
    },
    {
      "kind": "COMPARE",
      "field": "route",
      "op": "IN",
      "value": ["EYE_DROP", "SUB_CONJ"]
    }
  ]
}
```

**D.1.4 实例：糖皮质激素滴眼液长期使用（眼压条件已退化）**

```json
{
  "kind": "AND",
  "children": [
    {
      "kind": "COMPARE",
      "field": "drug_code",
      "op": "IN",
      "value": ["DRUG_DEXAMETHASONE_EYE", "DRUG_PREDNISOLONE_EYE", "DRUG_FLUOROMETHOLONE_EYE"]
    },
    {
      "kind": "COMPARE",
      "field": "days",
      "op": "GT",
      "value": 14
    },
    {
      "kind": "COMPARE",
      "field": "diagnosis_codes",
      "op": "CONTAINS_ANY",
      "value": ["H40.001", "H40.002", "Z98.8101"]
    }
  ]
}
```

> **注意这里少了「基线眼压值」这一条。** 完整规则应当是「激素类滴眼液 + 用药天数 > 14 + 基线眼压 > 21mmHg」，但 P-08 不传眼压，所以第 3 个条件改成「既往青光眼史」（`Z98.8101` 是青光眼术后状态）。**这条退化后的规则命中率会明显高于原意**——凡是用激素超过两周且有青光眼史的患者都会报警，其中相当比例本来就在安全监测下。这正是 §7.8 把「命中率 > 80% 一律复审」定为硬巡检的原因：这条规则很可能就是第一批被复审的对象。

### D.2 `m18_kb_med_rule.alert_message` 的变量标记

提示语用 `{变量名}` 形式做文本替换，可用变量限定为：`{drug_name}` / `{conflict_drug_name}` / `{diagnosis_name}` / `{days}` / `{dosage}` / `{limit}` / `{advice}`。

替换发生在 P-08 返回前，替换失败（变量未提供）时**保留原文标记不报错**——宁可让医生看到 `{days}` 也不能因为提示语渲染失败让整个审核返回 500。

### D.3 `m18_kb_path.applicability_rules`

路径入径标准的判定条件树。结构与 D.1 完全一致，但字段白名单不同：只能引用诊断、年龄、性别、术式，不能引用药品。

| 键 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `diagnosis_include` | array | 是 | 必须命中的诊断编码（任一） |
| `diagnosis_exclude` | array | 否 | 命中之一定不入径（合并症排除） |
| `age_min` / `age_max` | integer | 否 | 年龄区间（含端点） |
| `surgery_codes` | array | 否 | 限定术式 |
| `exclude_flags` | array | 否 | 排除标记，如 `EMERGENCY` / `MULTI_DEPT` |

```json
{
  "diagnosis_include": ["H25.901", "H25.902"],
  "diagnosis_exclude": ["H40.001", "E11.900", "I10.001"],
  "age_min": 18,
  "age_max": 85,
  "surgery_codes": ["SURG_PHACO_IOL"],
  "exclude_flags": ["EMERGENCY", "MULTI_DEPT"]
}
```

> **这份结构直接决定入径率的分母。** 详细设计 §3.4.4 论证过的 84.00%（168/200）与 70.00%（168/240）两个数，差的那 40 台正是被 `diagnosis_exclude` 与 `exclude_flags` 排除掉的病例。所以本字段一旦改动，历史入径率不再可比——这就是 `m18_kb_path_entry.applicability_snap` 必须存快照的原因。

| 降级返回 | `degraded: true` | HTTP 200 + `code: 0` 但数据不完整，调用方据此自行决定降级分支 |
| 入径 | Path Entry | 患者被纳入某条临床路径管理 |
| 变异 | Deviation | 入径后实际诊疗过程偏离标准路径，含延长、缩短、跳过节点、增加节点、退出路径 |
| 适用患者数 | Applicable Patients | 符合路径入径标准的患者数，**不是科室就诊总数**，是入径率的分母 |
| 死规则 | Dead Rule | 连续 90 天零命中的已发布规则，多半是条件写错或字段传不进来 |
| 误报规则 | False Positive Rule | 命中率超过 80% 的规则，多半是条件写宽了 |
| DRG 权重 | DRG Weight | 医保局按病组发布的相对资源消耗权重，CMI 的分子 |
| CMI | Case Mix Index | 病例组合指数 = 总权重 / 病例数 |
| ADRG | — | DRG 的核心分组，一个 DRG 由一个 ADRG 加并发症等级构成 |
| MDC | Major Diagnostic Category | 主要诊断大类 |
