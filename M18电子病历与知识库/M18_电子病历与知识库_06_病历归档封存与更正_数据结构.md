### 1.1 三张病历事实表的归属说明

`m18_emr_document`、`m18_emr_seal`、`m18_emr_amendment` 这三张表在两个上游模块的文档里已经被**按名字硬引用**，因此表名一个字都不能改：

| 表 | 硬引用出处 | 引用方要回答的问题 |
|---|---|---|
| `m18_emr_document` | `M05住院管理/M05_住院管理_数据结构设计汇总.md:740` | 住院病案首页关联的文书齐不齐 |
| `m18_emr_seal` | `M06日间手术管理/M06_日间手术管理_06_日间结算与病历归档_详细设计.md:197` | 这次日间手术的病历是否处于封存状态 |
| `m18_emr_amendment` | 总纲 §4.1（铁律 4 唯一例外路径） | 病历更正流水，M18-07 检索时必须能取到 |

这三张表由 M18-06 首建，M18-07 与其余子模块只引用、不重复建。判定理由见汇总 §1.3：「正文回答『写了什么』在 `m18_emr_record`；文书目录回答『有哪些、在不在』在 `m18_emr_document`。一份 `SIGNED` 病历可以对应多份文书。」

### 1.2 为什么是 11 张，不是更少也不是更多

| 候选 | 结论 | 理由 |
|---|---|---|
| 合并 `m18_arc_batch` 与 `m18_arc_item` | **不合并** | 批次是「一次推送」，明细是「一份病历」。一次门诊批量归档可能含 200 份病历，任何一份判 `INCOMPLETE` 不必然让整批被拒（门诊批次允许部分通过），二者生命周期不同 |
| 合并 `m18_arc_borrow` 与 `m18_arc_borrow_approval` | **不合并** | 借阅审批链有医务科 + 分管院长两级，且驳回后允许重新提交进入第二轮审批。审批记录只增不改，申请单允许回退状态 |
| 把扫描件塞进 `m18_emr_document` 存二进制 | **不建大字段** | 30 年保留期的二进制塞进数据库，备份窗口和 WAL 体积都无法承受。只存对象存储的 key 与哈希 |
| 拆出 `m18_arc_retention` 为独立表 | **独立** | 留存年限是法定参数，会随法规调整；拆出来后调参不需要动业务表，且迁移任务每次执行都读这张表 |
| 增加 `m18_arc_migration_log` | **不建** | 与 `m18_arc_oper_log` 的 `oper_type = 'RETENTION_MIGRATE'` 信息重叠。迁移日志需要的字段（迁出时间、行数、校验结果、执行人）在操作日志里全部有 |
| 增加 `m18_emr_seal_item` | **不建** | 封存的边界由 `seal_scope` + `encounter_id` / `date_from` / `date_to` / `batch_no` 四个字段表达，不需要逐份病历展开。逐份展开会在封存「按患者」时把该患者 30 年的全部病历都写一行，行数失控 |

| 批次 | 表 | 依赖 |

## 2. 命名与类型规范

### 2.1 表与字段命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 表 | `m18_{短名}_{业务对象}[_{从属}]`，短名 `arc`/`emr` | `m18_arc_batch`、`m18_emr_seal` |
| 主键 | `id BIGINT GENERATED BY DEFAULT AS IDENTITY` | `id` |
| 业务单号 | `{对象}_no VARCHAR(32)` | `batch_no`、`seal_no`、`amendment_no` |
| 逻辑外键 | `{对象}_id BIGINT` | `batch_id`、`record_id` |
| 跨模块引用 | `{来源}_{对象}_id` | `m07_document_id`、`m05_home_id` |
| 状态 | `status VARCHAR(32)` | `status` |
| 类型 | `{对象}_type VARCHAR(32)` | `doc_type`、`amendment_type` |
| 金额 | `{对象}_amount NUMERIC(14,2)` | 本子模块无金额字段（归档不收费） |
| 比率 | `{对象}_rate NUMERIC(10,6)` | `integrity_rate`、`completion_rate` |
| 哈希 | `content_hash VARCHAR(64)` | SHA-256 十六进制小写，固定 64 位 |
| 时间 | `{动作}_at TIMESTAMP` / `{动作}_date DATE` | `confirmed_at`、`archive_date` |

### 2.2 类型选型规则

| 数据类型 | 选型 | 依据 |
|---|---|---|
| 主键 | `BIGINT` 自增 | 归档明细 3 年 145 万行，`INTEGER` 已用掉 7% 空间；`BIGINT` 一次到位不迁移 |
| 时间 | `TIMESTAMP`（无时区） | 全院 Asia/Shanghai，跨时区换算只在展示层做。带时区类型会让同一时刻在两地读出来不同字面值，对账单与病历时间戳都是灾难 |
| 布尔 | `BOOLEAN` | 用 PostgreSQL 原生类型，不用 `CHAR(1)` |
| 枚举 | `VARCHAR(32)` + `CHECK` | 不用 PostgreSQL 原生 enum：加一个值需要改类型，且校验器禁 MySQL 的定长整型写法 |
| 大文本 | `TEXT` | 更正说明可能很长，`VARCHAR(2000)` 会截断 |
| 结构化快照 | `JSONB` | 缺失项清单、审批链、证据材料清单都是变长结构 |
| 哈希 | `VARCHAR(64)` | SHA-256 十六进制固定 64 位；不得用 MD5 |
| 对象存储定位 | `VARCHAR(512)` | S3 兼容 key 允许较长，实测最长 180 字符，留 2.8 倍余量 |
| 比率 | `NUMERIC(10,6)` | 完整率要能表达 0.978944；`NUMERIC(5,4)` 会把 0.0032 截成 0.0032 看不出差异（低完整率场景） |
| 评分 | `NUMERIC(5,1)` | 完整性得分 0~100 保留一位小数 |

### 2.3 维度字段空值规则

| 字段 | 无值时 | 理由 |
|---|---|---|
| `dept_id` | `0` | 表示「全院」或「不区分科室」。用 `0` 而不是 `NULL`，因为 PostgreSQL 的 `UNIQUE` 认为多个 `NULL` 互不相等，用 `NULL` 会让唯一索引失效 |
| `encounter_id` | `0` | `seal_scope = 'PATIENT'` 时不针对具体就诊，用 `0` 显式表达「不限定就诊」 |
| `batch_no` | `''` | `seal_scope` 不是 `BATCH` 时不存在批次号，存空串 |
| `reject_reason` | `''` | 非拒绝状态没有原因，存空串便于 `<> ''` 判断 |

### 2.4 口径字段空值规则

| 字段 | 无值时 | 理由 |
|---|---|---|
| `integrity_result` | 不适用，三态必填 | `COMPLETE`/`INCOMPLETE`/`UNKNOWN` 都有明确含义，不存在「空」 |
| `integrity_rate` | `NULL` | 分母为 0（批次内 0 份已判定明细）时不计算，**绝不填 0**。填 0 会让「刚创建还没校验」看起来像「全部不完整」 |
| `completion_rate` | `NULL` | 同上 |
| `released_at`/`released_by`/`release_reason` | `NULL` | 未解封时确实不存在 |

## 3. 编码与字典

### 3.1 单号规则

| 单号 | 前缀 + 格式 | 实际长度 | 示例 |
|---|---|---|---|
| 归档批次号 `batch_no` | `AR` + `yyyyMMdd` + 4 位流水 | 14 | `AR202610280033` |
| 归档流水号 | `ARD` + `yyyyMMdd` + 6 位流水 | 17 | `ARD20261021000001` |
| 封存编号 `seal_no` | `SEAL` + `yyyyMMdd` + 4 位流水 | 16 | `SEAL202610210001` |
| 借阅申请号 `borrow_no` | `BR` + `yyyyMMdd` + 4 位流水 | 14 | `BR202610280001` |
| 更正记录号 `amendment_no` | `AM` + `yyyyMMdd` + 4 位流水 | 14 | `AM202610280001` |
| 扫描件号 `scan_no` | `SC` + `yyyyMMdd` + 5 位流水 | 15 | `SC2026102800001` |
| 操作日志号 `log_no` | `AL` + `yyyyMMdd` + 6 位流水 | 16 | `AL20261028000001` |

**归档批次号为什么是日流水（14 字符）而不是月流水（12 字符）：** 共享规范 §3.3 编码表原定 `AR + yyyyMM + 4位流水`（12 字符），而 M05-05 `M05住院管理/M05_住院管理_05_出院办理与病历归档_详细设计.md:1091` 的真实响应是 `"m18_archive_id": "AR2026102800033"`——拆开是 `AR` + `20261028`（8 位日期）+ `00033`（5 位流水），**共 15 字符**。M18 侧统一生成 `AR` + `yyyyMMdd` + 4 位流水，**共 14 字符**，与 M05 那串差 1 位。字段为 `VARCHAR(32)`，两者都装得下；`m18_archive_id` 在 M05 侧只做不透明字符串等值传递与回显，**双方均不解析其内部结构、均不得加位数或格式校验**，所以这一位之差在端到端上无影响。改用日流水而非月流水的理由是容量：月流水 4 位上限 9,999，按月均 1,240 批次计 `9999 ÷ 1240 ≈ 8.06`，第八个月就会撞号；日流水按流水每日重置，日均 130 批次有 76 倍余量。

> 注意 M05 原文那串 `AR2026102800033` 的尾段是 `00033` 五位（`AR` + 8 位日期 + 5 位流水，共 15 字符），而 M18 生成的是 4 位流水。`batch_no` 字段声明为 `VARCHAR(32)`，两种长度都能存下；M18 生成的新批次一律 4 位流水，长度 14。这个差异不影响 M05 的端到端跑通，因为 M05 只是把 M18 返回的字符串原样存进 `m18_archive_id`。

**生成方式：** 统一走 Redis `INCR m18:code:{prefix}:{yyyyMMdd}`，当日首单设 TTL 到次日 00:05。禁止用数据库序列拼日期——跨零点并发时序列值已推进但日期已变，会生成重复单号。

**组合语义约束（最容易漏的一类）**

```sql
-- 【组合约束 C-01】已判定的状态必须有判定结果
--   防的错误：批次已经 CONFIRMED 但 integrity_result 还是空。
--   归档统计按 integrity_result 聚合，空值会被算进「已判定」之外的桶，
--   完整率的分子分母都与工作台显示的批次状态对不上。
ALTER TABLE m18_arc_batch
    ADD CONSTRAINT ck_m18_arc_batch_decided
    CHECK (status NOT IN ('CONFIRMED', 'REJECTED') OR integrity_result IS NOT NULL);

-- 【组合约束 C-02】COMPLETE 必须没有缺失项且没有拒绝明细
--   防的错误：判定为 COMPLETE 但 missing_docs 里还挂着缺文书。
--   这是「系统说全的」这句话最危险的一种形态——结论与证据自相矛盾。
ALTER TABLE m18_arc_batch
    ADD CONSTRAINT ck_m18_arc_batch_complete_clean
    CHECK (integrity_result <> 'COMPLETE'
           OR (jsonb_array_length(missing_docs) = 0
               AND jsonb_array_length(reject_items) = 0));

-- 【组合约束 C-03】INCOMPLETE 必须列出缺什么
--   防的错误：判了不完整却不说缺哪份文书，病案室无从通知科室补。
--   只判不列，等于把「不完整」变成一条无法处理的告警。
ALTER TABLE m18_arc_batch
    ADD CONSTRAINT ck_m18_arc_batch_incomplete_detail
    CHECK (integrity_result <> 'INCOMPLETE'
           OR (jsonb_array_length(missing_docs) > 0
               OR jsonb_array_length(reject_items) > 0));

-- 【组合约束 C-04】CONFIRMED 必须有确认时刻，且不得是 UNKNOWN
--   防的错误：UNKNOWN 批次被自动确认归档（总纲 G-08）。
--   UNKNOWN 的语义是「查不到上游，不知道全不全」，
--   自动确认等于系统替医生担保病历齐全，事后追责一句「系统说全的」。
ALTER TABLE m18_arc_batch
    ADD CONSTRAINT ck_m18_arc_batch_confirmed
    CHECK (status <> 'CONFIRMED'
           OR (confirmed_at IS NOT NULL
               AND confirmed_by IS NOT NULL
               AND integrity_result <> 'UNKNOWN'));

-- 【组合约束 C-05】重开次数与重开时刻同步
--   防的错误：reopen_count 累加但 last_reopen_at 为空，
--   或者反过来。前者让「补正后重新提交」的审计链断在没有时间戳的一行上。
ALTER TABLE m18_arc_batch
    ADD CONSTRAINT ck_m18_arc_batch_reopen
    CHECK ((reopen_count = 0 AND last_reopen_at IS NULL)
           OR (reopen_count > 0 AND last_reopen_at IS NOT NULL));

-- 【组合约束 C-06】撤销归档必须有撤销人、原因与时刻
--   防的错误：批次被置 RELEASED 但没人知道谁撤的、为什么撤。
--   M05 收到 m18.archive.released 后会回滚本地归档状态，没有原因的撤销
--   会在 M05 侧留下一条无法解释的状态回退。
ALTER TABLE m18_arc_batch
    ADD CONSTRAINT ck_m18_arc_batch_released
    CHECK (status <> 'RELEASED'
           OR (released_at IS NOT NULL
               AND released_by IS NOT NULL
               AND release_reason <> ''));

-- 【组合约束 C-07】REJECTED 必须记录拒绝时刻与原因
--   防的错误：批次卡在 REJECTED 但不知道何时被拒，工作台的「超期未处理」
--   排序取不到时间，被拒批次就永久沉底。
ALTER TABLE m18_arc_batch
    ADD CONSTRAINT ck_m18_arc_batch_rejected
    CHECK (status <> 'REJECTED'
           OR (rejected_at IS NOT NULL AND reject_reason <> ''));

-- 【组合约束 C-08】校验时刻的时间序
--   防的错误：校验结束早于开始。批量校验任务跨零点或时钟回拨时会出现，
--   一旦落库，校验耗时算出来是负数，监控告警的分位数全部失真。
ALTER TABLE m18_arc_batch
    ADD CONSTRAINT ck_m18_arc_batch_check_order
    CHECK (check_started_at IS NULL
           OR check_finished_at IS NULL
           OR check_finished_at >= check_started_at);

-- 【组合约束 C-09】只有 M06 来源才允许有 M06 结算 ID
--   防的错误：M05 来源的批次带了结算 ID，说明字段串了。
--   对账时按 m06_settlement_id 反查 M06 会查到一张不相干的日间结算单。
ALTER TABLE m18_arc_batch
    ADD CONSTRAINT ck_m18_arc_batch_src_ref
    CHECK ((source_module = 'M05' AND m06_settlement_id IS NULL)
           OR (source_module = 'M06' AND m05_home_id IS NULL)
           OR source_module = 'MANUAL');

-- 【组合约束 C-10】present_docs 与 missing_docs 不得重叠
--   防的错误：同一类文书既算存在又算缺失。M18-CALC-01 的判定是
--   required_docs 减去 present_docs 得到 missing_docs，
--   三者若不自洽，人工复核时看到的「缺什么」是错的。
ALTER TABLE m18_arc_batch
    ADD CONSTRAINT ck_m18_arc_batch_docs_disjoint
    CHECK (jsonb_array_length(missing_docs) = 0
           OR NOT (present_docs @> missing_docs));
```

**分区策略：** 不分区。三年 39 万行，全部查询都带 `batch_no` 或 `(source_module, source_biz_no)` 或时间范围 + `status`，索引可覆盖。分区表要求唯一约束包含分区键，会让 `uk_m18_arc_batch_source` 变成 `(source_module, source_biz_no, received_at)`，幂等键就不再是真正的幂等键。

**设计说明**

- 幂等键 `uk_m18_arc_batch_source` 放在**唯一索引**而不是 `UNIQUE CONSTRAINT` 上，是为了让它与 M18 共用的索引命名规范一致，且便于日后 `DROP INDEX CONCURRENTLY` 替换。
- `required_docs` / `present_docs` / `missing_docs` 三者同时落库，而不是只算 `missing_docs`：复核人员要能一眼看出「应当有几份、实际有几份、缺哪份」。只存 `missing_docs` 的话，上游把必检清单改了之后旧批次就无从解释。
- `reopen_count` + `last_reopen_at` 是本子模块对总纲的扩展。总纲 §4.3 只说 `RELEASED` 是终态，没说 `REJECTED` 是否可以回到 `CHECKING`。本设计的裁决见 4.2 的表下第 4 条说明与详细设计 §8.3。

**组合语义约束（最容易漏的一类）**

```sql
-- 【组合约束 C-11】STORED 必须有入库时刻，且完整性判定不能是 INCOMPLETE
--   防的错误：病历被判不完整却仍然入库并标记 STORED。
--   入库是「这份病历已经进了病案库」，判不完整就该停在 FAILED，
--   让病案室去补，而不是先入库再说——入库之后再改状态，
--   归档库与 M05 本地就各说一套了。
ALTER TABLE m18_arc_item
    ADD CONSTRAINT ck_m18_arc_item_stored
    CHECK (status <> 'STORED'
           OR (stored_at IS NOT NULL
               AND integrity_result IS NOT NULL
               AND integrity_result <> 'INCOMPLETE'));

-- 【组合约束 C-12】FAILED 必须说明为什么失败
--   防的错误：明细失败但 fail_reason 为空，重试队列里 200 条失败
--   全部显示空白原因，运维只能一条条手工查。
ALTER TABLE m18_arc_item
    ADD CONSTRAINT ck_m18_arc_item_failed_reason
    CHECK (status <> 'FAILED' OR fail_reason <> '');

-- 【组合约束 C-13】做过哈希比对就必须有结论
--   防的错误：expected_hash 非空（推送方给了哈希）但 hash_matched 为空。
--   铁律 5 要求哈希一旦比对必须有结论，留空会让合规检查以为
--   「这部分病历从未做过篡改校验」。
ALTER TABLE m18_arc_item
    ADD CONSTRAINT ck_m18_arc_item_hash_verdict
    CHECK (expected_hash = '' OR hash_matched IS NOT NULL);

-- 【组合约束 C-14】哈希不一致的病历不得 STORED
--   防的错误：推送方给的哈希与 M18 算出的哈希不一致，病历仍被入库。
--   不一致意味着要么推送方数据被改过、要么 M18 拿到的正文不是那份，
--   两种情况都必须在入库前拦住。
ALTER TABLE m18_arc_item
    ADD CONSTRAINT ck_m18_arc_item_hash_ok
    CHECK (status <> 'STORED' OR hash_matched IS DISTINCT FROM FALSE);

-- 【组合约束 C-15】封存的病历不得归档入库（G-3 封存只读的落地之一）
--   防的错误：对已封存病历执行归档，把它当成新数据写进病案库。
--   封存期间全表只读，归档也是一次写入。
ALTER TABLE m18_arc_item
    ADD CONSTRAINT ck_m18_arc_item_unsealed
    CHECK (status <> 'STORED' OR sealed = FALSE);

-- 【组合约束 C-16】RELEASED 只能由已入库的明细转过来
--   防的错误：从没入库成功的明细被标成撤销归档，撤销了一个不存在的东西。
ALTER TABLE m18_arc_item
    ADD CONSTRAINT ck_m18_arc_item_released
    CHECK (status <> 'RELEASED' OR stored_at IS NOT NULL);
```

**分区策略：** 不分区。三年 145 万行，主查询是 `WHERE batch_id = ?` 与 `WHERE record_id = ?`。

```sql

--   防的错误：is_present = TRUE 但没有任何能证明它存在的东西。
--   P-10 是 M05-06 判断首页能不能提交的依据，一条「存在」记录若
--   没有 doc_no 与 generated_at，M05 侧拿到的是一份查无实据的文书。
ALTER TABLE m18_emr_document
    ADD CONSTRAINT ck_m18_emr_document_present
    CHECK (is_present = FALSE
           OR (doc_no <> '' AND generated_at IS NOT NULL));

-- 【组合约束 C-18】仅纸质件的文书必须在 M18 侧明确表达
--   防的错误：paper_only 为 TRUE 但 is_present 仍为 TRUE 且无哈希。
--   M06-04 的降级场景是「只有纸质件、电子侧没有正文」，
--   这时 is_present 应为 FALSE、content_hash 为空，
--   否则完整性判定会认为电子正文存在而跳过纸质件补扫。
ALTER TABLE m18_emr_document
    ADD CONSTRAINT ck_m18_emr_document_paper
    CHECK (paper_only = FALSE
           OR (m07_document_id IS NULL AND content_hash = ''));

-- 【组合约束 C-19】有哈希就必须有生成时刻
--   防的错误：文书有内容哈希但不知道何时生成。
--   哈希是铁律 5 的防篡改锚点，锚点必须能定位到时间。
ALTER TABLE m18_emr_document
    ADD CONSTRAINT ck_m18_emr_document_hash_time
    CHECK (content_hash = '' OR generated_at IS NOT NULL);

-- 【组合约束 C-20】签署时刻不得早于生成时刻
--   防的错误：文书签署时间早于生成时间。M07-06 时钟回拨或跨系统
--   对时偏差会造成这种记录，一旦落库，病历时间线呈现「先签字后写文书」，
--   在医疗纠纷的举证里是致命伤。
ALTER TABLE m18_emr_document
    ADD CONSTRAINT ck_m18_emr_document_time_order
    CHECK (signed_at IS NULL
           OR generated_at IS NULL
           OR signed_at >= generated_at);

-- 【组合约束 C-21】M07 来源的文书必须有 M07 文书 ID
--   防的错误：doc_source 标成 M07_SYNCED 但没记 m07_document_id，
--   对账时无法回到 M07-06 核对签署状态。
ALTER TABLE m18_emr_document

    CHECK (doc_source <> 'M07_SYNCED' OR m07_document_id IS NOT NULL);
```

**组合语义约束（最容易漏的一类）**

```sql
-- 【组合约束 C-22】四种封存范围各自的边界字段必须齐备且互斥
--   防的错误：seal_scope = 'ENCOUNTER' 但 encounter_id 为 0，
--   于是触发器里 (seal_scope='ENCOUNTER' AND encounter_id = NEW.encounter_id)
--   这个分支永远不命中；病历看起来被封存了，实际一条也没锁住。
--   这是本表最危险的一类错误：封存状态显示「封存中」，写入却畅通无阻。
ALTER TABLE m18_emr_seal
    ADD CONSTRAINT ck_m18_emr_seal_scope_fields
    CHECK (
        (seal_scope = 'PATIENT'
            AND encounter_id = 0 AND date_from IS NULL
            AND date_to IS NULL AND batch_no = '')
        OR (seal_scope = 'ENCOUNTER'
            AND encounter_id > 0 AND date_from IS NULL
            AND date_to IS NULL AND batch_no = '')
        OR (seal_scope = 'DATE_RANGE'
            AND encounter_id = 0 AND date_from IS NOT NULL
            AND date_to IS NOT NULL AND batch_no = '')
        OR (seal_scope = 'BATCH'
            AND encounter_id = 0 AND date_from IS NULL
            AND date_to IS NULL AND batch_no <> '')
    );

-- 【组合约束 C-23】按时间段封存必须日期有序
--   防的错误：date_from 晚于 date_to，BETWEEN 恒不命中，
--   又是一个「显示封存中、实际锁不住」的静默失效。
ALTER TABLE m18_emr_seal
    ADD CONSTRAINT ck_m18_emr_seal_date_order
    CHECK (date_from IS NULL OR date_to IS NULL OR date_to >= date_from);

-- 【组合约束 C-24】解封必须有三人留痕（汇总 §7.2 给定并强化）
--   防的错误：状态改成 RELEASED 但没人知道谁解的、为什么解。
--   封存是医疗纠纷里医院自证清白的手段，解封却没有留痕，
--   等同于医院自己撤掉了证据保全。
ALTER TABLE m18_emr_seal
    ADD CONSTRAINT ck_m18_emr_seal_released
    CHECK (status <> 'RELEASED'
           OR (released_at IS NOT NULL
               AND released_by IS NOT NULL
               AND release_reason <> ''
               AND release_approver1 IS NOT NULL
               AND release_approver2 IS NOT NULL
               AND release_approved_at IS NOT NULL));

-- 【组合约束 C-25】双审批的两个审批人不得是同一人
--   防的错误：一个人既当医务科又当院长，双审批形同虚设。
ALTER TABLE m18_emr_seal
    ADD CONSTRAINT ck_m18_emr_seal_dual_approver
    CHECK (release_approver1 IS NULL
           OR release_approver2 IS NULL
           OR release_approver1 <> release_approver2);

-- 【组合约束 C-26】被取代必须有指向与时刻
--   防的错误：status = 'SUPERSEDED' 但 superseded_by 为空，
--   查不到是被哪条更大的封存覆盖的，封存台账出现孤儿。
ALTER TABLE m18_emr_seal
    ADD CONSTRAINT ck_m18_emr_seal_superseded
    CHECK (status <> 'SUPERSEDED'
           OR (superseded_by IS NOT NULL AND superseded_at IS NOT NULL));

-- 【组合约束 C-27】审批时刻不得早于封存时刻
--   防的错误：先审批后封存的时间序倒置（先由系统自动封存、事后补审批）。
--   医疗纠纷场景下，封存生效时刻本身就是要件之一。
ALTER TABLE m18_emr_seal
    ADD CONSTRAINT ck_m18_emr_seal_approve_time
    CHECK (approved_at IS NULL OR approved_at >= sealed_at);

-- 【组合约束 C-28】解封时刻不得早于封存时刻
--   防的错误：同一秒内封存又解封，或者时钟回拨造成的时间序倒置。
ALTER TABLE m18_emr_seal
    ADD CONSTRAINT ck_m18_emr_seal_release_time
    CHECK (released_at IS NULL OR released_at >= sealed_at);

-- 【组合约束 C-29】司法与医保场景必须记录外部文号
--   防的错误：以「司法」为由封存，却没有任何案号或公函号可查。
--   这类封存一旦被质疑「凭什么封」，拿不出文号就是滥用。
ALTER TABLE m18_emr_seal
    ADD CONSTRAINT ck_m18_emr_seal_case_no
    CHECK (seal_reason NOT IN ('JUDICIAL', 'INSURANCE_AUDIT') OR case_no <> '');

-- 【组合约束 C-30】生效中的封存不得提前拥有解封痕迹
--   防的错误：ACTIVE 状态的封存行里带着 released_at。
--   触发器只看 status = 'ACTIVE'，这种记录会一直锁着病历，
--   但页面上显示「已解封过」，运维查不出为什么写不进去。
ALTER TABLE m18_emr_seal
    ADD CONSTRAINT ck_m18_emr_seal_active_clean
    CHECK (status <> 'ACTIVE'
           OR (released_at IS NULL AND released_by IS NULL
               AND superseded_by IS NULL));
```

**设计说明**

- **为什么边界字段全部落库而不是只存一个 `scope_value`：** 触发器要按四种范围分别判定，把边界拆成四个独立字段才能写出让 PostgreSQL 用得上索引的 `OR` 条件。用一个 JSONB 存边界会让触发器变成全表扫描——P-14 的 100ms 预算要求触发器的封存检查必须走索引。
- `idx_m18_emr_seal_active_partial` 是触发器性能的关键：`WHERE status = 'ACTIVE'` 的部分索引把 600 行缩到个位数。
- **解封后能否再封：** 可以，但必须是新的一条封存记录（新 `seal_no`），旧记录保持 `RELEASED`。这一条写进详细设计 §8.3。表结构上不需要额外约束，因为 `uk_m18_emr_seal_no` 只保证编号唯一，同一 `patient_id` 可以有多条 `ACTIVE` 记录。

**组合语义约束（最容易漏的一类）**

```sql
-- 【组合约束 C-31】APPROVED 必须有审批人与审批时刻
--   防的错误：更正记录是 APPROVED 状态，但没有医务科审批。
--   铁律 4 的全部防线就压在这条上：没有审批的更正，
--   等于医生自己给自己开了一扇改病历的后门。
ALTER TABLE m18_emr_amendment
    ADD CONSTRAINT ck_m18_emr_amendment_approved
    CHECK (status <> 'APPROVED'
           OR (approved_by IS NOT NULL AND approved_at IS NOT NULL));

-- 【组合约束 C-32】审批人不得是申请人
--   防的错误：医生自己发起、自己审批。这在操作上只要给一个人
--   同时开「更正申请」和「医务科审批」两个权限就能做到，
--   制度上的双人复核完全落空。
ALTER TABLE m18_emr_amendment
    ADD CONSTRAINT ck_m18_emr_amendment_self_approve
    CHECK (approved_by IS NULL OR approved_by <> applied_by);

-- 【组合约束 C-33】审批时刻不得早于申请时刻
--   防的错误：补录审批（审批时刻人工填写成更早的时间）。
--   补录审批在审计里等同于伪造审批链。
ALTER TABLE m18_emr_amendment
    ADD CONSTRAINT ck_m18_emr_amendment_approve_time
    CHECK (approved_at IS NULL OR approved_at >= applied_at);

-- 【组合约束 C-34】更正前后内容必须真的不同
--   防的错误：更正记录的 before_snap 与 after_text 完全一样。
--   这种记录会让「更正次数」虚高，触发 3 次复核阈值，
--   而实际上一个字都没改——把监控指标做废。
ALTER TABLE m18_emr_amendment
    ADD CONSTRAINT ck_m18_emr_amendment_differs
    CHECK (btrim(before_snap) <> btrim(after_text));

-- 【组合约束 C-35】段落级更正必须指明段落或字段
--   防的错误：section_type 与 field_code 都为空串，却说这是段落级更正。
--   展示时无法定位到原病历的哪一段，打印出来的「原文 + 更正说明」
--   会让人看不懂改的是哪里。
ALTER TABLE m18_emr_amendment
    ADD CONSTRAINT ck_m18_emr_amendment_target
    CHECK (btrim(before_snap) <> '' AND (section_type <> '' OR field_code <> ''));

-- 【组合约束 C-36】更正记录自身必须有哈希
--   防的错误：after_text 有内容但 content_hash 为空串。
--   更正记录也是病历的一部分，同样受铁律 5 约束。
ALTER TABLE m18_emr_amendment
    ADD CONSTRAINT ck_m18_emr_amendment_hash
    CHECK (content_hash ~ '^[0-9a-f]{64}$');

-- 【组合约束 C-37】被驳回或撤回的更正不得可见
--   防的错误：REJECTED 的更正仍然展示在病历里。
--   展示即生效——家属看到一条被执行方驳回的更正却被印在病历上，
--   会被理解为「医院改了又不敢认」。
```

```sql
-- 【组合约束 C-38】批准必须有有效期
--   防的错误：状态 APPROVED 但 valid_from/valid_to 为空，
--   批准变成永久授权。病历借阅有时效性，尤其是科研与教学场景。
ALTER TABLE m18_arc_borrow
    ADD CONSTRAINT ck_m18_arc_borrow_valid
    CHECK (status NOT IN ('APPROVED', 'BORROWED', 'RETURNED')
           OR (valid_from IS NOT NULL AND valid_to IS NOT NULL));

-- 【组合约束 C-39】有效期必须有序
--   防的错误：valid_from 晚于 valid_to，授权窗口是负的，
--   查阅接口永远判过期，但状态显示已批准。
ALTER TABLE m18_arc_borrow
    ADD CONSTRAINT ck_m18_arc_borrow_valid_order
    CHECK (valid_from IS NULL OR valid_to IS NULL OR valid_to > valid_from);

-- 【组合约束 C-40】封存场景必须关联封存记录
--   防的错误：封存期间的借阅没有关联到具体的封存单。
--   封存台账上会看到「有 12 次借阅」却查不到每次借阅是为了哪个案子。
ALTER TABLE m18_arc_borrow
    ADD CONSTRAINT ck_m18_arc_borrow_seal_ref
    CHECK (related_seal_id >= 0);

-- 【组合约束 C-41】驳回必须说明原因
--   防的错误：驳回但原因空白，申请人不知道该补什么材料，
--   只能反复提交同一份被打回的申请。
ALTER TABLE m18_arc_borrow
    ADD CONSTRAINT ck_m18_arc_borrow_reject
    CHECK (status <> 'REJECTED' OR reject_reason <> '');

-- 【组合约束 C-42】已借出与已归还必须有时刻
--   防的错误：状态标成 RETURNED 但 borrowed_at/returned_at 为空，
--   借阅台账算不出每份病历的平均在借时长。
ALTER TABLE m18_arc_borrow
    ADD CONSTRAINT ck_m18_arc_borrow_times
    CHECK ((status NOT IN ('BORROWED', 'RETURNED')
            OR borrowed_at IS NOT NULL)
           AND (status <> 'RETURNED' OR returned_at IS NOT NULL));

-- 【组合约束 C-43】印发次数不得超过页数上限
--   防的错误：借阅申请限定打印 5 页，实际打印了 20 页。
--   page_limit 是申请人承诺的用途边界，超出即滥用。
ALTER TABLE m18_arc_borrow
    ADD CONSTRAINT ck_m18_arc_borrow_print_limit
    CHECK (page_limit = 0 OR print_count <= page_limit);
```

**组合语义约束（最容易漏的一类）**

```sql
-- 【组合约束 C-51】到期一律不销毁（汇总 §10.3 的落库表达）
--   防的错误：有人把 is_destroy_on_expire 改成 TRUE，迁移任务就会
--   在满 15 年那天真的把门诊病历删掉。法规只规定最低保存期，
--   从未规定必须销毁；销毁病历在医疗纠纷中是重大不利证据。
--   所以这条不是业务规则，是数据层的硬闸门。
ALTER TABLE m18_arc_retention
    ADD CONSTRAINT ck_m18_arc_retention_no_destroy
    CHECK (is_destroy_on_expire = FALSE);

-- 【组合约束 C-52】永久保存必须用 0 年表达，不得用超大数字
--   防的错误：为了表达「永久」填 retention_years = 999。
--   迁移脚本按日期加 999 年会溢出 DATE 上限，任务直接崩。
ALTER TABLE m18_arc_retention
    ADD CONSTRAINT ck_m18_arc_retention_permanent
    CHECK ((is_permanent = FALSE AND retention_years > 0)
           OR (is_permanent = TRUE AND retention_years = 0));

-- 【组合约束 C-53】在线保留年限不得超过法定保存年限
--   防的错误：online_years = 20 而 retention_years = 15，
--   病历在在线库待到 20 年，法定保存期满后还在被日常读写。
ALTER TABLE m18_arc_retention
    ADD CONSTRAINT ck_m18_arc_retention_online_le
    CHECK (is_permanent = TRUE OR online_years <= retention_years);

-- 【组合约束 C-54】生效区间有序
--   防的错误：effective_to 早于 effective_from，配置从生效当天就已失效。
ALTER TABLE m18_arc_retention
    ADD CONSTRAINT ck_m18_arc_retention_effective
    CHECK (effective_to IS NULL OR effective_to >= effective_from);

-- 【组合约束 C-55】改了年限必须有审批
--   防的错误：任何人直接 UPDATE retention_years 把 15 年改成 3 年，
--   迁移任务下一轮就把 3 年以上的病历全搬走。
ALTER TABLE m18_arc_retention
    ADD CONSTRAINT ck_m18_arc_retention_approved
    CHECK (approved_by IS NOT NULL AND approved_at IS NOT NULL);
```

**组合语义约束（最容易漏的一类）**

```sql
-- 【组合约束 C-59】失败操作必须记录错误码
--   防的错误：oper_result = 'FAILED' 但 fail_code 为空。
--   排查时只知道失败了不知道失败成什么样，日志等于没写。
ALTER TABLE m18_arc_oper_log
    ADD CONSTRAINT ck_m18_arc_oper_log_fail
    CHECK (oper_result <> 'FAILED' OR fail_code <> '');

-- 【组合约束 C-60】留存期迁移必须记录行数、校验结果与执行人
--   防的错误：迁移日志只有「执行了迁移」，没有迁移了多少行、
--   校验过没过、谁执行的。汇总 §10.2 第 7 步要求这三项全都有，
--   否则无法证明「删除的每一行都先在归档库里校验过」。
ALTER TABLE m18_arc_oper_log
    ADD CONSTRAINT ck_m18_arc_oper_log_migrate
    CHECK (oper_type NOT IN ('RETENTION_MIGRATE', 'RETENTION_VERIFY')
           OR (row_count > 0
               AND verify_result <> ''
               AND operator_id > 0
               AND operator_name <> ''));

-- 【组合约束 C-61】需要事由的操作必须填事由
--   防的错误：解封、撤销归档、更正审批这些操作没写事由。
--   这几类操作一旦事后被质疑，事由就是唯一的解释。
ALTER TABLE m18_arc_oper_log
    ADD CONSTRAINT ck_m18_arc_oper_log_reason
    CHECK (oper_type NOT IN ('SEAL_RELEASE', 'SEAL_SUPERSEDE',
                             'ARCHIVE_RELEASE', 'AMEND_APPROVE',
                             'AMEND_REJECT', 'BORROW_REJECT')
           OR char_length(btrim(oper_reason)) >= 10);

-- 【组合约束 C-62】系统任务与人工操作必须可区分
--   防的错误：系统自动确认归档时 operator_id 填了 NULL，
--   审计时看不出是谁批的——它本来应该明确记为 0（系统）。
ALTER TABLE m18_arc_oper_log
    ADD CONSTRAINT ck_m18_arc_oper_log_operator
    CHECK (operator_id >= 0 AND (operator_id > 0 OR operator_name <> ''));

-- 【组合约束 C-63】迁移类操作必须有前后快照
--   防的错误：迁移日志没有记录搬走了哪些行。
--   事后从归档库搬回来时，不知道原表里有哪几行被动过。
ALTER TABLE m18_arc_oper_log
    ADD CONSTRAINT ck_m18_arc_oper_log_snap
    CHECK (oper_type <> 'RETENTION_MIGRATE'
           OR (before_snap <> '{}'::JSONB AND after_snap <> '{}'::JSONB));
```

**设计说明**

```python
        from_attributes=True,
        extra="forbid",
        str_strip_whitespace=True,
        validate_assignment=True,

    @field_validator("*", mode="before")
    @classmethod
    def _decimal_from_float(cls, value: object) -> object:
        """把 float 转成字符串再交给 Decimal，规避二进制浮点误差。

        if isinstance(value, float):

        return value
```

## 5. 数据服务契约

本章说明「谁能写、谁能读、什么条件下必须拒绝写」。这些契约由数据库权限、触发器和 CHECK 三层共同保证，不依赖应用层自觉。

### 5.1 数据库账号与权限

| 账号 | 权限范围 | 用途 |
|---|---|---|
| `app_m18` | 对 11 张表的 SELECT / INSERT / 受限 UPDATE | 应用服务账号，**无 DELETE，无 DDL** |
| `m18_archiver` | 对在线库目标表有 DELETE，对归档 schema 有 INSERT / SELECT | **留存期迁移专用账号**，只在迁移任务里以专用连接使用 |
| `m18_readonly` | 对 11 张表的 SELECT | 报表与数据核查 |
| `m18_dba` | 全部权限 | 建表、迁移脚本、权限维护 |

`app_m18` 被显式 `REVOKE DELETE` 的表共 8 张：

```sql
REVOKE DELETE ON m18_arc_item FROM app_m18;
REVOKE DELETE ON m18_emr_document FROM app_m18;
REVOKE DELETE ON m18_emr_seal FROM app_m18;
REVOKE DELETE ON m18_emr_amendment FROM app_m18;
REVOKE DELETE ON m18_arc_borrow_approval FROM app_m18;
REVOKE DELETE ON m18_arc_paper_scan FROM app_m18;
REVOKE UPDATE, DELETE ON m18_arc_oper_log FROM app_m18;
REVOKE UPDATE ON m18_emr_amendment FROM app_m18;
GRANT UPDATE (status, approved_by, approved_at, approval_opinion,
              approval_no, is_visible, updated_at, updated_by)
    ON m18_emr_amendment TO app_m18;
```

`m18_arc_batch` / `m18_arc_borrow` / `m18_arc_retention` / `m18_arc_config` 四张表保留 `app_m18` 的 DELETE 权限：前三张是业务流程表（批次可撤销、借阅可作废、配置可删除），`m18_arc_config` 与 `m18_arc_retention` 走逻辑删除为主，物理删除只留给运维清理误录入的空记录。

### 5.2 写入前置检查（所有写接口共用）

任何写 `m18_emr_document` / `m18_emr_amendment` / `m18_arc_item` 的操作，必须按以下顺序检查，任何一步不通过就不写：

| 步骤 | 检查内容 | 不通过时的响应 |
|---|---|---|
| 1 | 目标病历是否处于生效封存（`m18_emr_seal.status = 'ACTIVE'` 且范围命中） | 业务错误 `"1806016"`，HTTP 403 |
| 2 | 目标病历 `status` 是否为 `SIGNED`（更正场景例外，走更正表） | 业务错误 `"1806017"` |
| 3 | `content_hash` 是否与库中固化的值一致（补录场景跳过） | 业务错误 `"1806020"` |
| 4 | 操作人是否有对应功能权限与数据权限 | 业务错误 `"1806031"`，HTTP 403 |

> 第 1 步的失败方向必须朝「更严格」：查封存状态时若 `m18_emr_seal` 查询异常，**拒绝写入**而不是放行。总纲 §5.4 的原话是「封存状态查不到（DB 抖动）时应当拒绝写入而不是放行——写一次不该写的代价远高于多等 3 秒」。

### 5.3 触发器契约

| 触发器 | 挂载表 | 事件 | 行为 |
|---|---|---|---|
| `trg_m18_seal_guard` | `m18_emr_document` | BEFORE INSERT / UPDATE | 命中生效封存则抛 `RECORD_SEALED` |
| `trg_m18_seal_guard_item` | `m18_arc_item` | BEFORE INSERT / UPDATE | 同上 |
| `trg_m18_seal_guard_amend` | `m18_emr_amendment` | BEFORE INSERT | 同上 |
| `trg_m18_arc_batch_touch` | `m18_arc_batch` | BEFORE UPDATE | 自动维护 `updated_at`，并禁止把 `CONFIRMED` 改回 `CHECKING` |

```sql
CREATE OR REPLACE FUNCTION trg_fn_m18_seal_guard()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
DECLARE
    v_patient_id BIGINT;
    v_encounter_id BIGINT;
    v_record_date DATE;
    v_hit_no VARCHAR(32);
BEGIN
    v_patient_id := NEW.patient_id;
    IF TG_TABLE_NAME = 'm18_arc_item' THEN
        v_encounter_id := NEW.encounter_id;
    ELSIF TG_TABLE_NAME = 'm18_emr_document' THEN
        v_encounter_id := NEW.encounter_id;
    ELSE
        v_encounter_id := NEW.encounter_id;
    END IF;
    v_record_date := COALESCE(NEW.created_at, now())::DATE;

    SELECT s.seal_no INTO v_hit_no
      FROM m18_emr_seal s
     WHERE s.status = 'ACTIVE'
       AND s.patient_id = v_patient_id
       AND (
             s.seal_scope = 'PATIENT'
          OR (s.seal_scope = 'ENCOUNTER' AND s.encounter_id = v_encounter_id)
          OR (s.seal_scope = 'DATE_RANGE'
              AND v_record_date BETWEEN s.date_from AND s.date_to)
       )
     LIMIT 1;

    IF v_hit_no IS NOT NULL THEN
        RAISE EXCEPTION 'RECORD_SEALED'
            USING HINT = '该病历已被封存，不可写入。如需解封请走医务科审批',
                  DETAIL = 'seal_no=' || v_hit_no;
    END IF;
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_m18_seal_guard
    BEFORE INSERT OR UPDATE ON m18_emr_document
    FOR EACH ROW EXECUTE FUNCTION trg_fn_m18_seal_guard();

CREATE TRIGGER trg_m18_seal_guard_item
    BEFORE INSERT OR UPDATE ON m18_arc_item
    FOR EACH ROW EXECUTE FUNCTION trg_fn_m18_seal_guard();

CREATE TRIGGER trg_m18_seal_guard_amend
    BEFORE INSERT ON m18_emr_amendment
    FOR EACH ROW EXECUTE FUNCTION trg_fn_m18_seal_guard();
```

**关于 `seal_scope = 'BATCH'`：** 汇总 §3.3 给的触发器 DDL 只覆盖 `PATIENT` / `ENCOUNTER` / `DATE_RANGE` 三值。本实现的判定里 `BATCH` 不参与「写病历正文」的拦截——批次封存的语义是「这一批归档结果整体冻结」，它的作用是阻止该批次被撤销、被重开（由 `m18_arc_batch` 的状态机与业务校验实现），而不是按批次号去锁病历正文。理由：一份病历可能同时属于多个批次（门诊病历在两次就诊中都被归档过），按批次号锁正文会误伤其他批次。

| 急诊病历 | 15 年 | 按门诊病历管理 |
| 屈光手术档案 | 永久 | 植入物溯源要求，需伴随患者终身 |

**到期不销毁的理由**（汇总 §10.3）：法规只规定最低保存期，从未规定「到期必须销毁」；而且销毁病历在医疗纠纷中是重大不利证据——一份已销毁的病历无法自证清白。患者书面要求删除也**不予删除**：病历属医疗机构法定档案，患者无权要求销毁，医院只能限制访问。

### 6.3 备份策略

| 对象 | 频率 | 保留 | 说明 |
|---|---|---|---|
| 全库全量 | 每日 02:00 | 30 天 | 含本子模块 11 张表 |
| WAL 归档 | 实时 | 30 天 | 支持任意时点恢复 |

| `m18_arc_retention` / `m18_arc_config` | 每次变更 | 20 个版本 | 配置回滚依据 |


病历事实表每周永久备份的原因：在线库与归档库都可能出问题，而这三张表的丢失意味着「哪些文书存在、哪些病历被封存过、哪些病历被更正过」这三类事实永久不可恢复。永久离线备份是最后一道防线。

## 附录 C 造数要点

| 场景 | 数据准备 | 验证点 |
|---|---|---|
| 归档幂等 | 同一 `(source_module='M06', source_biz_no='M06-SET-001')` 推 5 次 | 只产生 1 个批次，后 4 次返回 `idempotent_replay = true` |

## 附录 D 字段级约束速查

| 约束对象 | 约束表达 | 防什么 |
|---|---|---|
| `content_hash` | `VARCHAR(64)` + `~ '^[0-9a-f]{64}$'` | 用 MD5（32 位）或大写形式造成跨系统比对失败 |
| `batch_no` | `~ '^AR[0-9]{12}$'` | 少一位流水或误存 M05 自己的 `BA...` 批次号 |
| 完整性得分 | `NUMERIC(5,1)` + 区间 `[0,100]` | 用整数丢失小数位，或用比率 0~1 混入百分比字段 |
| 比率字段 | `NUMERIC(10,6)` | 低完整率（如 0.0032）被四舍五入成 0 |
| 时间字段 | `TIMESTAMP` 无时区 | 带时区类型让同一时刻在两地读出差值 |
| 枚举字段 | `VARCHAR(32)` + `CHECK` | 自造枚举值（汇总 §17 第 31 条） |
| 维度字段 | `0` / `''` 而非 NULL | 唯一索引因 NULL 互不相等而失效 |
| 分区主键 | `PRIMARY KEY (id, log_time)` | 分区表主键缺分区键导致建表失败 |
