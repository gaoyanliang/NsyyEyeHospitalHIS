## 文档说明

### 一、本文件回答的问题

本文件是 M18-01 病历模板与结构化的**唯一建表依据**。它回答四个问题：

1. **建哪些表**：9 张 `m18_tpl_` 前缀的表，覆盖模板定义、模板段落、结构化字段、字段校验规则、模板版本、适用规则、同意书模板、引用统计、配置与操作日志。
2. **每张表的字段是什么**：字段名、类型、可空性、默认值、含义，逐字段到 COMMENT 级。
3. **约束落在哪里**：哪些规则由 `CHECK` 保护、哪些由 `UNIQUE` 与部分索引保护、哪些必须由应用层或事务保护。**CHECK 只保护字段自身，不保护字段之间的语义**，所以「某状态必须配一整套参数」这类规则一定会另写组合约束，本文逐条说明。
4. **代码怎么映射**：SQLAlchemy 2.0 声明式模型与 Pydantic V2 Schema，供后端直接落地。

| 标记 | 含义 |
| :--- | :--- |
| `FK*` | 逻辑外键，**不建物理 FOREIGN KEY 约束** |

#### 4.1.1 逻辑外键清单

| 子表 | 字段 | 引用表 | 引用字段 | 不建物理外键的理由 |
| :--- | :--- | :--- | :--- | :--- |
| `m18_tpl_template_section` | `template_id` | `m18_tpl_template` | `id` | 模板可逻辑删除（`is_deleted`），物理外键会把「已删除模板的段落」变成孤儿被拒 |
| `m18_tpl_field_def` | `section_id` | `m18_tpl_template_section` | `id` | 段落版本切换时需保留旧段落与旧字段供历史病历复现，物理外键的级联会误删 |
| `m18_tpl_template_version` | `template_id` | `m18_tpl_template` | `id` | 版本轨迹是审计性质，模板被清理后轨迹仍需可查 |
| `m18_tpl_apply_rule` | `template_id` | `m18_tpl_template` | `id` | 规则可能先于模板建立（批量导入场景），物理外键会让导入顺序敏感 |
| `m18_tpl_apply_rule` | `consent_template_id` | `m18_tpl_consent_template` | `id` | 同上 |
| `m18_tpl_ref_stat` | 无外键 | — | — | 用 `template_code` + `version_no` 关联，模板整行重建后统计仍然对得上 |

#### 4.1.2 不建物理外键的三条理由

1. **逻辑删除与外键互斥**。本子模块 9 张表全部有 `is_deleted`（配置类表必须可变），而 PostgreSQL 的外键不认「逻辑删除」，一条被逻辑删除的模板仍会被段落引用，物理外键放行；反过来若要真正清理，物理外键会阻止清理。两种语义都无法用同一个物理外键表达。
2. **历史病历复现要求节点永久可查**。医生 6 月按 v1 模板写病历，9 月模板升到 v3，打开 6 月病历时必须仍按 v1 结构展示。这意味着 v1 的段落与字段**任何时候都不能被物理删除**，物理外键的 `ON DELETE CASCADE` 会成为事故源。
3. **建表顺序与批量初始化**。模块汇总 §9.2 规定初始化顺序为 `m18_tpl_config` → `m18_tpl_template` → 段落 → 字段 → 同意书 → 规则，物理外键会让「先建规则后建模板」的批量脚本失败；且模板导入来自医务科的 Excel，行的先后不可控。

#### 4.1.3 九张表的分层

| 层次 | 表 | 变化频率 | 可变性 |
| :--- | :--- | :--- | :--- |
| 身份层 | `m18_tpl_template`、`m18_tpl_consent_template` | 低频 | 可变（状态、当前版本号） |
| 内容层 | `m18_tpl_template_section`、`m18_tpl_field_def` | 中频（每次改模板） | 已发布内容不可改，只增新版本行 |
| 轨迹层 | `m18_tpl_template_version`、`m18_tpl_oper_log` | 高频 | **只增不改** |
| 匹配层 | `m18_tpl_apply_rule` | 低频 | 可变 |
| 度量层 | `m18_tpl_ref_stat` | 每日一批 | 按日可重算覆盖 |
| 配置层 | `m18_tpl_config` | 极低频 | 可变 |

### 4.2 表：`m18_tpl_template`（病历模板主表）

**用途：** 一条记录是一份病历模板的**逻辑身份**。它不存任何段落与字段内容（内容在 `m18_tpl_template_section` 与 `m18_tpl_field_def` 中，按版本归属），只存回答下面这些问题所需的元数据：这份模板叫什么、给哪种病历用、属于哪个科室或专科、当前是哪个版本在工作、处于什么状态、谁能改、何时生效。

把「身份」与「内容」分成两张表的直接原因是病历复现。医生 6 月按 v1 模板写的病历，9 月模板升到 v3 后打开那份病历必须仍按 v1 展示。如果模板正文是主表的一列、升级时原地覆盖，那么历史病历在打开的那一刻就会「变形」——本该 8 个段落变成 11 个，本该有的「瞳孔检查」字段消失了。因此主表只承载随版本演进整体切换的元数据，`current_version_no` 指向正在工作的版本，段落与字段按 `template_code + version_no` 归属，旧版本行永久保留。

**写入方：** M18-01 模板维护接口（创建、改名、改适用范围、状态流转）
**只读方：** M18-02 门诊病历、M18-03 住院病历、M18-04 手术麻醉与专科病历、M18-06 归档、M07-06 文书渲染

    CHECK (status <> 'DISABLED' OR char_length(trim(disable_reason)) >= 2);

    CHECK ((template_scope <> 'SPECIALTY' OR specialty_code <> '')
       AND (template_scope NOT IN ('DEPT','DOCTOR') OR dept_id > 0));

ALTER TABLE m18_tpl_template ADD CONSTRAINT ck_m18_tpl_template_hash
    CHECK (content_hash = '' OR content_hash ~ '^[0-9a-f]{64}$');

**分区策略：**

本表不分区。理由：模块汇总 §4 已裁决「配置与主数据类（`m18_tpl_*`）不分区」，模板约 300 行，全表远小于单页可缓存规模，分区只会给唯一约束与查询规划增加成本。日志类表 `m18_tpl_oper_log` 因年增 18 万行且仅按时间查询，才采用月分区。

**设计说明：**

| 编号 | 说明 |
| :--- | :--- |
| D-01 | `template_code` 的唯一索引**不含 `is_deleted`**。编码永不复用是硬规则：若某模板因故被删除，同一编码不得再建，否则历史病历里记录的 `template_code` 会指向一份完全不同的模板 |
| D-02 | `current_version_no` 与 `published_version_no` 分离。设计器改草稿只动前者，发布成功才推进后者。病历书写一律按 `published_version_no` 取内容，避免「医生正在改的新版本被实时写进病历」 |
| D-03 | `status` 用 `DISABLED` 而非 `OFFLINE`。停用后已引用该模板的历史病历**照旧能打开**（走 `published_version_no` 指向的内容），只是新病历不能再选它。这一点由服务层保证，数据库层只保证状态值合法 |
| D-04 | `ck_m18_tpl_template_published_ver` 与 `ck_m18_tpl_template_published_audit` 是**组合约束**。单列 CHECK 只能保证「状态合法」「版本号非负」，但「发布状态必须配齐版本号与审批人」是字段之间的语义，必须另写。这是模块汇总 §7.2 第 1 条的直接应用 |
| D-05 | `section_count` / `field_count` 是冗余计数，必须在同一事务内随段落/字段变更更新。它们只用于列表展示，**任何业务判断都不得依赖它们**，需要精确值时实查 |
| D-06 | `gin_m18_tpl_template_name` 用 `pg_trgm` 而非 `tsvector`。模板名是短文本（不超过 200 字符）且查询形态是包含匹配，trgm 更合适；正文检索才用 `tsvector`，那属于 M18-07 |

### 4.3 表：`m18_tpl_template_section`（模板段落表）

**用途：** 一条记录是**某模板某版本的一个段落**。段落是病历骨架的组成单位，决定「这份病历按什么顺序出现哪些章节」，例如门诊屈光病历的骨架是「主诉 → 现病史 → 既往史 → 屈光专科检查 → 诊断 → 处理意见」。

段落必须随版本归属（`template_code` + `version_no` 双字段），而不是只挂 `template_id`。理由是复现：9 月模板升级新增了「干眼相关检查」段落，6 月写的那份病历在查询它的段落列表时，`WHERE template_code=? AND version_no=1` 得到的仍是当初的 8 个段落，不会凭空多出一个从未填写过的空段落。

段落的 `section_type` 与共享规范 §13 的 16 值枚举逐字一致，这一点很关键：M18-05 病历质控判断「这份病历缺不缺现病史」，靠的就是 `section_type = 'PRESENT_ILLNESS'`，如果模板设计器允许自定义中文段落名而不做归类，质控就无法跨模板判定完整性。

**写入方：** M18-01 模板设计器（新增段落、调整顺序、改段落属性）
**只读方：** M18-02 门诊病历、M18-03 住院病历、M18-04 手术麻醉与专科病历（渲染骨架）、M18-05 质控（按 `section_type` 判完整性）

    CHECK (version_no >= 1);

-- 顺序号从 1 起
ALTER TABLE m18_tpl_template_section ADD CONSTRAINT ck_m18_tpl_template_section_sort
    CHECK (sort_no >= 1);

ALTER TABLE m18_tpl_template_section ADD CONSTRAINT ck_m18_tpl_template_section_code

**设计说明：**

| 编号 | 说明 |
| :--- | :--- |
| D-07 | 冗余 `template_code` 是本表最重要的设计。若只存 `template_id`，病历渲染必须两跳（先按 id 取模板拿 code 再取段落）；更严重的是模板被重建后 id 变化，历史病历会渲染成另一份模板。存 code + version 后，渲染只查一张表且与主表重建解耦 |
| D-08 | `uk_m18_tpl_template_section_type` 是**部分唯一索引**，条件 `is_repeatable = FALSE`。可重复段落（病程记录）允许同一版本出现多次，不可重复段落（主诉）每版本只允许一段。若不用部分索引而用普通唯一索引，病程记录就被锁死为一条 |
| D-09 | `default_content` 用 `TEXT` 而非 `VARCHAR(n)`。这是正文类大字段，模块汇总 §2.4 第 8 条明确「正文可 TEXT，不得用 TEXT 存结构化字段」，段落默认正文属于正文类 |
| D-10 | 已发布版本的段落**既不能物理删除也不能逻辑删除**。这条不在数据库层强制（本表有 `is_deleted`），而由服务层在「版本已发布」时拒绝任何段落删除动作；数据库层能强制的只有「已发布内容不可改」这类需要触发器的事，本表不做，因为模板内容允许在新版本里自由编辑，只是不允许改动已发布版本的行 —— 服务层的判据是「该 `version_no` 是否 ≤ 主表 `published_version_no`」 |
| D-11 | `is_required` 是模板级要求，与字段级 `required` 是两件事：段落必填指整段不能为空，字段必填指某字段不能为空。渲染层两者都校验，但错误提示不同 |

### 4.4 表：`m18_tpl_field_def`（结构化字段定义表）

**用途：** 一条记录是一个**可在病历里填写、可被检索统计的结构化字段**。它是 M18-01 向 M18-02/03/04 交付的核心契约：M18-02 门诊病历能填什么、M18-05 质控能查什么、M18-07 检索能统计什么，全部由这张表的行决定。

这张表的三个设计要点：

**第一，字段编码必须稳定。** `field_code` 一旦出现在任何一个已发布版本里，就永久不可修改。理由很直接：M18-02 的 `m18_emr_record_field` 按 `field_code` 存结构化值，如果 9 月把「眼压」的编码从 `IOP_OD` 改成 `INTRAOCULAR_PRESSURE_OD`，那么 6 月填的数据就再也对应不上——检索「所有眼压大于 21 的患者」会把 6 月的数据全部漏掉，而且不会报错。所以字段的**改名**只能改 `field_name`（显示名），不能改 `field_code`；若确实需要语义不同的新字段，另建新编码。

**第二，字段类型必须能表达「值不是医生手填的」。** `source_type` 与 `source_ref` 两列解决这个问题：`source_type` = MANUAL 表示医生手填；`DIAGNOSIS` 表示由 M07-02 的诊断回填；`OPERATION` 表示由 M09 手术记录回填；`PATIENT` 表示由 M03 患者主数据带入；`SYSTEM` 表示由系统计算。M07-06 文书模板里的 `{chief_complaint}`、`{present_illness}` 这类哨兵值符渲染时，需要知道该哨兵值符背后是「取字段值」还是「取回填值」，靠的就是这两列。

**第三，校验规则要能用数据表达，不能全是代码。** `validate_rule` 是 JSONB，结构在字段说明中写死，服务层按结构解释执行。这样做的好处是运营可以在 P04 页面配置「数值范围 0~60」而不需要发版；坏处是 JSONB 无法被数据库层校验，所以对最常见的三种规则（数值区间、字符串长度、枚举成员）额外做了**提升列**：`validate_min`、`validate_max`、`option_values`，让它们可以被 CHECK 保护。

**写入方：** M18-01 字段配置（P04）
**只读方：** M18-02/03/04 渲染表单与保存结构化值、M18-05 质控取字段做规则判定、M18-07 检索统计

**`validate_rule` 结构（JSONB）：**

```json
{
  "min": 0,
  "max": 60,
  "precision": 2,
  "regex": "^[0-9]{1,3}$",
  "min_len": 2,
  "max_len": 200,
  "forbidden_words": ["正常", "无异常"],
  "signature_slot": false,
  "image_upload": false,
  "cross_field": [
    {"field_code": "IOP_OD", "op": "lte_other_by", "limit": 5}
  ]
}
```

| 键 | 类型 | 适用字段类型 | 说明 |
| :--- | :--- | :--- | :--- |
| `min` / `max` | number | NUMBER、DECIMAL | 数值闭区间。同时必须写入提升列 `validate_min` / `validate_max` |
| `precision` | integer | DECIMAL | 小数位数，必须与 `decimal_scale` 一致 |
| `regex` | string | TEXT、TEXTAREA、RICHTEXT | 正则，最长 200 字符 |
| `min_len` / `max_len` | integer | TEXT、TEXTAREA、RICHTEXT | 字数区间，`max_len` 必须不超过 `max_length` |
| `forbidden_words` | string[] | TEXT、TEXTAREA | 禁止出现的词，用于拦截「无异常」这类套话填写 |
| `signature_slot` | boolean | REFERENCE | 签名位用途标记，语义见 3.3.4.1 |
| `image_upload` | boolean | REFERENCE | 图片位用途标记，语义见 3.3.4.2 |
| `max_file_mb` | integer | REFERENCE | 仅 `image_upload = true` 时可配，单文件大小上限，1~50，缺省 10 |
| `file_types` | string[] | REFERENCE | 仅 `image_upload = true` 时可配，允许的扩展名，取值 DICOM / JPG / PNG / PDF，缺省 `["JPG","PNG"]` |
| `cross_field` | object[] | 全部 | 跨字段校验，如「左眼眼压不得比右眼高 5 以上」。由服务层执行，数据库层不保护 |

**3.3.4.1 签名位标记 `signature_slot`（本节为唯一权威定义）**

`field_type` 的取值全集为共享规范 §13 的 13 个（TEXT / TEXTAREA / RICHTEXT / NUMBER / DECIMAL / DATE / TIMESTAMP / SELECT / MULTI_SELECT / CHECKBOX / RADIO / TABLE / REFERENCE），**M18 不新增任何枚举值**。签名位与图片以 `REFERENCE` 承载，用途标记放在 `validate_rule`。

为什么这么分层：字段类型回答的是「这个值是什么数据」，`REFERENCE`（指向另一处的对象）已经说清了类型；「这里要放一个签名栏」是渲染与流程属性，属于 UI 层。把渲染层的东西塞进数据层类型字典，会让所有引用同一份 §13 的子模块取值校验跟着变。

| 项 | 定义 |
| :--- | :--- |
| 键名 | `signature_slot` |
| 取值类型 | **boolean**（JSON `true` / `false`），不接受字符串、数字、null |
| 缺省 | `false`（键可省略，省略等同 `false`） |
| 允许出现的字段类型 | **仅 `field_type = 'REFERENCE'`**；出现在其它类型上，保存时返回 `"1801021"` |
| 语义 | `true` 表示该字段是签名位：填写时渲染为签名控件，结构化数据中存**签署人医师 ID（BIGINT）**，不是图片、不是手写笔迹图像 |
| 必要配套 | `true` 时 `validate_rule.source_ref` 必须存在且取值为 `SIGN` 或 `SIGN_MULTI`，否则返回 `"1801021"` |
| 与 `source_type` 的关系 | `source_type` 必须为 `SYSTEM`（值为系统回填的签署人，非医生手填），否则返回 `"1801021"` |

`source_ref` 的两种合法取值：

| `source_ref` | 含义 | 结构化数据形态 | 典型场景 |
| :--- | :--- | :--- | :--- |
| `SIGN` | 单人签署位 | 单个医师 ID（整数） | 术者签名、麻醉医师签名 |
| `SIGN_MULTI` | 多人会签位 | 医师 ID 数组，至少 1 个 | 三级查房记录、疑难病例讨论会签 |

**3.3.4.2 图片位标记 `image_upload`（本节为唯一权威定义）**

| 项 | 定义 |
| :--- | :--- |
| 键名 | `image_upload` |
| 取值类型 | **boolean**，不接受字符串、数字、null |
| 缺省 | `false` |
| 允许出现的字段类型 | **仅 `field_type = 'REFERENCE'`**；出现在其它类型上，保存时返回 `"1801021"` |
| 语义 | `true` 表示该字段是图片位：填写时渲染为上传控件，结构化数据中存**文书 ID 数组**（指向 `m18_emr_document` 的 `id`，由 M18-06 维护），不是二进制内容、不是 URL |
| 必要配套 | `true` 时 `validate_rule.source_ref` 必须存在且取值为 `IMAGE`，否则返回 `"1801021"` |
| 与 `source_type` 的关系 | `source_type` 必须为 `SYSTEM`，否则返回 `"1801021"` |
| 可配参数 | `max_file_mb`（integer，1~50，缺省 10）、`file_types`（string[]，元素取 DICOM / JPG / PNG / PDF，缺省 `["JPG","PNG"]`） |
| 多图上限 | 由 `validate_rule.max_count` 表达（integer，1~20，缺省 9）；**与 `signature_slot` 互斥，不得同时出现** |

**3.3.4.3 两个标记的合法组合（穷尽四种，无第五种）**

| `signature_slot` | `image_upload` | 是否合法 | `source_ref` 约束 | 结构化数据形态 |
| :--- | :--- | :--- | :--- | :--- |
| `false` / 省略 | `false` / 省略 | 合法 | 不受这两个标记约束，按 `source_type` 规则校验 | 按 `field_type` 决定 |
| `true` | `false` / 省略 | 合法（签名位） | 必须为 `SIGN` 或 `SIGN_MULTI` | 医师 ID；`SIGN_MULTI` 为 ID 数组 |
| `false` / 省略 | `true` | 合法（图片位） | 必须为 `IMAGE` | `m18_emr_document.id` 数组 |
| `true` | `true` | **不合法**，返回 `"1801021"` | — | — |

第四种必须禁止：签名位存的是「谁签的」，图片位存的是「哪几张图」，两者混在一个字段里，结构化数据到底存 ID 数组还是单个 ID 会变成靠数据长度猜。

**3.3.4.4 落库保证与边界**

| 项 | 说明 |
| :--- | :--- |
| 数据库层 | `validate_rule` 是 JSONB，`signature_slot` / `image_upload` **没有提升列**，由 Service 层在保存时校验（`ck_` 约束只管 JSON 是对象，不管键内容） |
| 为什么不做成提升列 | 二者只在 `REFERENCE` 字段上出现，全库这类字段预计不超过 30 个；为它们加两个布尔提升列，会让 9 张表里最宽的一张再多两列恒为 false 的空位。**代价是这两个标记的正确性完全依赖 Service 校验，不依赖数据库**，所以 AC-17 与 8.4 节必须覆盖 |
| 与 M18-02/03/04 的契约 | 这些子模块渲染字段时：`signature_slot = true` 渲染签名控件并回填医师 ID；`image_upload = true` 渲染上传控件并把 `m18_emr_document.id` 数组落库。**取值全集就是上面四行组合表，不接受其它取值** |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
| :--- | :--- | :--- | :--- |
| `pk_m18_tpl_field_def` | 主键 | `id` | 主键 |
| `uk_m18_tpl_field_def_code` | 唯一 | `template_code` + `field_code` | **字段编码在同一模板内跨版本唯一**，这是「编码稳定」的数据库级保证 |
| `uk_m18_tpl_field_def_sort` | 唯一 | `section_id` + `sort_no` | 段落内顺序号唯一 |
| `idx_m18_tpl_field_def_ver` | 普通 | `template_code` + `version_no` + `section_id` + `sort_no` | 渲染主查询：按编码与版本取全部字段并按段内顺序排 |

**设计说明：**

| 编号 | 说明 |
| :--- | :--- |
| D-12 | `uk_m18_tpl_field_def_code` 建在 `(template_code, field_code)` 而非 `(section_id, field_code)`。字段可以跨版本移动段落（例如把「眼压」从体格检查挪到专科检查），但只要在同一个模板内，编码就必须全局唯一，否则 M18-02 存值时就无法只靠编码定位 |
| D-13 | `template_id` 与 `template_code` 都冗余存。`template_id` 用于设计器内部操作（快），`template_code` 用于跨版本与跨表关联（稳）。看起来浪费，但两张表各 22,000 与 4,500 行，冗余成本可忽略，换来的是避免每次渲染都多一跳 |
| D-14 | 提升列 `validate_min` / `validate_max` 的存在是为了让「数值区间」这条最常见的规则能被 CHECK 保护，而不用在应用层解析 JSONB。代价是写入时必须两处同步，服务层用同一个 Pydantic 模型的 validator 保证一致性；若二者不一致，`validate_rule` 为准并在下次保存时修正提升列 |
| D-15 | `field_type` 的 13 个值里没有 SIGNATURE 与 IMAGE。任务要求「字段类型必须覆盖签名位/图片」，本设计的处理是：签名位用 `field_type = 'REFERENCE'` 且 `validate_rule.signature_slot = true`，图片位用 `field_type = 'REFERENCE'` 且 `validate_rule.image_upload = true`。**为什么不是新增两个枚举值**：`field_type` 是共享规范 §13 的公共枚举，M18-02/03/04 的 CHECK 约束都会引用同一份取值，单方面新增会让其他子模块的约束在联合校验时失败；而 REFERENCE 本来就表示「值指向别处的对象」，签名指向医师、图片指向文书，语义是吻合的 |
| D-16 | `option_values` 与 `validate_rule` 都是 JSONB 且都建了 GIN 索引。GIN 索引在配置类表上看起来奢侈，但这两列有一个高频运营查询：「哪些字段配了禁止词」「哪些字段有 OD 选项」，没有 GIN 就要全表扫 22,000 行解析 JSON，P95 从 8ms 升到 120ms |
| D-17 | `is_deleted` 在本表上是**危险字段**。字段一旦被写进任何已发布版本，逻辑删除会让历史病历渲染时找不到字段定义。服务层规则：字段只能在新版本里「标记不再使用」（即新版本不再创建该 `field_code` 行），不得对已发布版本的字段行置 `is_deleted` |

### 4.5 表：`m18_tpl_consent_template`（同意书模板表）

**用途：** 一条记录是一份**法定同意书的正文模板**——手术同意书、麻醉同意书、特殊检查同意书、输血同意书、自费项目同意书。它存的是「这份同意书的正文长什么样、必须包含哪几项必签声明、由哪几类角色签署、医务科何时批准生效」。

**这张表只到「模板」为止，不越过签署。** 谁签的、何时签的、签了几份、PDF 在哪里，全部权威在 M07-06 的 `m07_document`。本子模块**不建任何签署记录表**，详细设计第 10 章的 P-05/P-06/P-07 三个接口是**聚合视图**：先查本表拿到「这个申请单应该有哪些同意书、各自的模板版本是什么」，再查 M07-06 的 `GET /internal/v1/m07/documents/by-source` 拿到「哪些已经签了、签成什么样」，两者拼装后返回。

把这件事分开的真实原因是**术前核对会拦手术**。M06-04 术前核对要回答「这位患者的同意书签齐了吗」，如果签署状态被两处维护，一处是 M07-06 签完就写、一处是 M18 收到回调再写，那么回调延迟的 15 分钟里，核对读到的是旧值，患者会被判「未签同意书」而手术被拦。反过来 M18 若只认自己的表、M07-06 改了不同步，又会把纸质签字的患者判成没签。唯一不出错的做法是：**签署状态只有一个读源，就是 M07-06。**

**`consent_sign_status` 七值为什么是七个而不是四个。** M07-06 的 `m07_document.status` 有四态，但术前核对需要的表达比四个更多：一份同意书可能是**纸质签的、系统里没有电子件**（`PAPER_ONLY`），可能是**查不到任何记录**（`UNKNOWN`，例如 M07-06 不可用），也可能**根本还没生成**（`NOT_CREATED`）。这三件事的含义完全不同：

- 把 `PAPER_ONLY` 混进 `NOT_CREATED`，会在术前核对时把「纸质签了字」的患者判成「没签」而拦掉手术；
- 把 `UNKNOWN` 混进 `NOT_CREATED`，会在 M07-06 抖动时一次性拦掉所有在台手术。

因此七值不是「多造了三个」，而是**把三种必须区分的失败语义显式化**。

**写入方：** M18-01 同意书模板维护（P06）
**只读方：** M18-06 生成同意书正文、M06-01 术前准备、M07-06 签署与打印、P-05/P-06/P-07 聚合视图

### 4.6 表：`m18_tpl_template_version`（模板版本轨迹表）

**用途：** 一条记录是**一次版本动作的快照**——创建 v2 草稿、提交审核、审核通过发布、被 v3 取代、停用。它不是「当前版本是什么」（那是主表的 `current_version_no`），而是「这个版本经历了什么、谁在什么时候因为什么理由推进了它、当时的段落与字段长什么样」。

这张表**只增不改**。它承担三件事：

1. **审计**：谁在 9 月 3 日把屈光病历模板从 v2 升到 v3，理由是「新增干眼相关检查段」，审核人是医务科张主任。这是医务科年度检查必看的材料。
2. **复活**：新版本发布后若发现严重问题需要回退，回退动作是「把 `published_version_no` 指回旧版本号」而不是删掉新版本，轨迹表记录了完整过程，任何一次回退都能解释清楚。
3. **复现依据**：`section_snapshot` 与 `field_snapshot` 以 JSONB 存下发布时刻的骨架摘要（段落类型、顺序、字段编码清单）。当有人怀疑「6 月那份病历的段落顺序不对」时，可以拿快照与当时的实际渲染结果比对，确认真的是按 v1 渲染的。

**写入方：** M18-01 版本动作（创建版本、提交审核、审核通过、审核驳回、发布、取代、停用）——只增
**只读方：** M18-01 版本历史页、M07-06 追溯「当时用的是哪版」、M18-06 归档快照、M18-08 审计

COMMENT ON COLUMN m18_tpl_template_version.action_type IS '动作类型：CREATE/SUBMIT/APPROVE/REJECT/PUBLISH/SUPERSEDE/DISABLE/ROLLBACK';

COMMENT ON COLUMN m18_tpl_template_version.operator_name IS '动作执行人姓名快照，防止人员调离后无法追溯';
COMMENT ON COLUMN m18_tpl_template_version.is_major IS '是否重大变更，TRUE 时需双人审核';

**分区策略：**

本表不分区。理由：预估 6,000 行（300 模板 × 年均 4 次动作 × 5 年），远未到分区阈值；查询形态为「某模板的轨迹」与「某时间段的动作」，前者按 `template_code` 走索引，后者按 `action_at` 走索引，均无全表扫描风险。分区反而会让 `uk_m18_tpl_template_version` 这类跨时间唯一约束失效（分区表的唯一约束必须包含分区键）。

**设计说明：**

| 编号 | 说明 |
| :--- | :--- |
| D-23 | 本表**无 `is_deleted`**，并用触发器 `trg_m18_tpl_template_version_immutable` 加 `REVOKE UPDATE, DELETE` 双保险。这是全子模块唯一不可变的表，理由：审计轨迹是医务科法定检查项，能被修改的轨迹等于没有轨迹 |
| D-24 | `uk_m18_tpl_template_version_release` 是**部分唯一索引**，只对 `PUBLISH` 生效。同一版本只允许发布一次；若要重发（如发布后立刻发现错误），走 ROLLBACK 动作用旧版本号重新发布，或直接出 v+1 新版本。这与「发布后不可回改」相互呼应 |
| D-25 | 存 `section_snapshot` / `field_snapshot` 而不只存 `content_hash`。哈希能证明「没变」，但无法回答「当时是什么」。审查场景里前者不够用 |
| D-26 | `operator_name` / `operator_role` 存快照而非只存 ID。人员调离、改名、调科后，按 ID 回查 M01 得到的可能是「已离职」或另一科室，事后追溯就断链了 |
| D-27 | `effective_to` 在 SUPSERDE 动作时由系统回填（取新版本的 `effective_from`）。这样「某天生效的是哪版」可以用一条区间查询回答：`WHERE effective_from <= d AND (effective_to IS NULL OR effective_to > d)` |

### 4.7 表：`m18_tpl_apply_rule`（模板适用规则表）

**用途：** 一条记录是**「什么病历该默认用哪个模板」的一条匹配条件**。当 M07 医生工作站在门诊接诊页打开病历时，需要给医生一个默认模板；当 M18-02 在创建病历记录时，也需要知道该往哪份模板里写。这个决策不能硬编码在代码里，因为规则每周都在变——屈光专科新开了干眼门诊、某个病种改了编码、异地医保患者的模板需要不同。

本表把决策参数化。一条规则由「适用范围」+「匹配条件」+「目标模板」+「优先级」四部分组成：

- **适用范围**：`record_type`（门诊/住院/日间/急诊）+ `dept_id` + `specialty_code`，三者可以只填一部分。
- **匹配条件**：`match_conditions` JSONB，接诊时的上下文键值对，如 `{"diagnosis_code":"H25.901","age_max":14}`。
- **目标模板**：`template_id` 或 `consent_template_id` 二选一，指向具体模板。
- **优先级**：`priority` 越大越优先，命中多条取最大者；同优先级取 `sort_no` 小者。

规则的另一半价值在**可解释性**。医生问「为什么给我推荐这个模板」，系统要能回答「因为你选的诊断是 H25.901，规则 R-012 命中」。因此本表有 `rule_name` 与 `description`，且匹配结果会在 P03 页面上展示命中链路。

**写入方：** M18-01 适用规则配置（P07 专科模板管理）
**只读方：** M07 医生工作站「推荐模板」、M18-02/03/04 取默认模板、M18-06 取同意书模板

**字段定义：**

    CHECK (record_type = ANY (ARRAY['','OUTPATIENT','INPATIENT','DAY_SURGERY','EMERGENCY']));

ALTER TABLE m18_tpl_apply_rule ADD CONSTRAINT ck_m18_tpl_apply_rule_priority
    CHECK (priority >= 0 AND priority <= 999 AND sort_no >= 0);

ALTER TABLE m18_tpl_apply_rule ADD CONSTRAINT ck_m18_tpl_apply_rule_ref
    CHECK ((rule_target = 'TEMPLATE' AND template_id IS NOT NULL AND consent_template_id IS NULL)
        OR (rule_target = 'CONSENT_TEMPLATE' AND consent_template_id IS NOT NULL AND template_id IS NULL));

ALTER TABLE m18_tpl_apply_rule ADD CONSTRAINT ck_m18_tpl_apply_rule_cond
    CHECK (jsonb_typeof(match_conditions) = 'object');

    CHECK (is_default = TRUE

        OR jsonb_object_keys(match_conditions) IS NOT NULL);

-- 生效期自洽
ALTER TABLE m18_tpl_apply_rule ADD CONSTRAINT ck_m18_tpl_apply_rule_eff
    CHECK (effective_to IS NULL OR effective_from IS NULL OR effective_to >= effective_from);

    CHECK (status <> 'PUBLISHED' OR effective_from IS NOT NULL);

### 4.8 表：`m18_tpl_ref_stat`（模板引用统计表）

**用途：** 一条记录是**某模板某版本在某一天被引用的画像**：多少份病历用了它、这些病历平均写了多少字、定稿率多少、有多少份在定稿后被质控退回改过。

这张表存在的唯一理由是**回答「这个模板能不能停用」**。运营想停用一个用了一年的旧模板，必须先知道还有多少份病历在引用它、最近一次引用是哪天。如果直接查 `m18_emr_record`（那是 M18-02 的事实表，39 万行/年），一次统计要扫几十万行；把每日引用画像预先算好存本表，P08 页面打开就是两次索引扫描。

**本表不造业务数。** 所有的病历数、字数、定稿率都来自 M18-02 的 `m18_emr_record`，本表只做按日预聚合与留存。这是模块汇总对 M18-01 的一贯要求：配置类子模块不做事实计算，只做配置侧的度量。

**关联方式不用 `template_id` 而用 `template_code` + `version_no`。** 理由：统计要回答的是「v2 那版用了多少次」，而 `template_id` 指向的是模板逻辑身份、跨版本不变。若按 `template_id` 聚合，v1、v2、v3 会被混成一个数，回答不了「升级后新版被接受了吗」。

**写入方：** M18-01 每日统计任务（Celery 定时，按日重算覆盖）
**只读方：** M18-01 模板引用分析页（P08）、M18-07 病历检索与统计、运营决策

| D-36 | `data_quality` 三值取共享规范 §13。每日任务正常算出结果标 `DAILY`；若上游 M18-02 当日数据未就绪，任务不写行（而不是写 0），查询侧遇到缺行显示「待生成」而不是显示 0 —— 这是总纲「绝不把『不知道』填成 0」的直接应用 |
| D-37 | `calc_batch_no` 与 `calc_at` 让本表可审计：同一统计日出现两批时，以 `calc_at` 更大的为准，且两批都保留在日志里（`m18_tpl_oper_log`），便于排查「为什么这个数变了」 |

### 4.9 表：`m18_tpl_config`（子模块配置表）

**用途：** 一条记录是一个**配置键在某一个作用域下的取值**。本子模块的配置项不多但都比较关键：发布是否需要双人审核、审核超时多少小时提醒、编辑锁多久过期、引用统计跑在几点、同意书聚合视图缓存多久、模板编码是否允许人工指定。

三层覆盖是这张表的核心设计：

| 作用域 | `scope_type` | `scope_code` | 典型用途 |
| :--- | :--- | :--- | :--- |
| 全局 | `GLOBAL` | `''` | 全院统一基线 |
| 病历类型 | `RECORD_TYPE` | `OUTPATIENT` 等 | 门诊与住院的审核策略不同 |
| 具体模板 | `TEMPLATE` | `T0001` 般的模板编码 | 某份法定模板要求更严 |

解析顺序为「具体模板 → 病历类型 → 全局」，取第一个存在的行。这样一条「全院默认不要求双人审核、但住院病历要求、且《输血同意书》要求三人审核」的策略，只需 3 行配置而不是在代码里写 if。

**写入方：** M18-01 配置页（P09）
**只读方：** M18-01 全部服务（启动时加载，变更时刷新）

### 4.10 表：`m18_tpl_oper_log`（操作日志表）

**用途：** 一条记录是**模板侧的一次写操作留痕**。所有对模板、段落、字段、同意书模板、适用规则、配置的写操作都在这里留一行，包含谁、什么时候、对什么对象、做了什么动作、改前改后的关键值。

这张表**只增不改**，并且**按 `created_at` 月分区**。分区理由是容量与留存：日均约 500 行、年 18 万行、三年 54 万行，查询几乎总是「查最近 30 天」。若不分表，三年后一个「本月模板发布记录」的查询要扫 54 万行；按月分区后只碰一个分区，且清理历史只需 `DETACH PARTITION`。

**分区表必须有 DEFAULT 分区。** 这是模块汇总 §2.6 的硬要求：`PARTITION BY RANGE (created_at)` 若没有兜底分区，2027 年 1 月的写入会直接失败报「no partition of relation found for row」。月度分区靠 APScheduler 提前建，但任务失败或时钟异常时 DEFAULT 分区能接住数据。

**写入方：** M18-01 全部写接口（通过 AOP 切面统一记录）——只增
**只读方：** M18-01 操作日志页、M18-08 审计、M02-06 审计

**字段定义：**

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | BIGINT | 否 | 自增 | 主键（分区表主键需含分区键，实际用 `(id, created_at)` 联合） |
| `log_no` | VARCHAR(64) | 否 | 无 | 日志单号，格式 `LG{yyyyMMdd}{6位}`，全局唯一 |
| `object_type` | VARCHAR(32) | 否 | 无 | 对象类型，取值 TEMPLATE / SECTION / FIELD / CONSENT / VERSION / RULE / CONFIG |

| `object_id` | BIGINT | 否 | 0 | 对象主键 ID |
| `version_no` | INTEGER | 否 | 0 | 涉及的版本号，0 表示与版本无关 |

**索引设计：**

**分区策略：**

| 项 | 内容 |
| :--- | :--- |
| 分区方式 | `PARTITION BY RANGE (created_at)` |
| 分区粒度 | 月 |
| 预建分区 | 上线前预建 3 个月，之后由 APScheduler 每月 25 日建下月分区 |
| **默认分区** | `m18_tpl_oper_log_default`，**必须存在**，防止分区未及时创建时写入失败 |
| 历史清理 | 按 `stat.retain_days`（默认 1095 天）对整月分区执行 `DETACH PARTITION` 后归档，不做行级删除 |
| 主键 | `(id, created_at)` 联合主键，PostgreSQL 分区表要求主键包含分区键 |

**设计说明：**

| 编号 | 说明 |
| :--- | :--- |
| D-42 | `DEFAULT` 分区不是可选项。没有它，2027-01-01 凌晨若分区创建任务失败，所有模板写操作会在写日志这一步抛异常并回滚——日志表故障连带业务失败，这是最不应该发生的事故形态 |
| D-43 | 主键用 `(id, created_at)` 联合。这是 PostgreSQL 分区表的硬限制：主键必须包含分区键。若坚持单列主键，只能放弃分区或放弃主键，两者都不可接受 |
| D-44 | `before_value` / `after_value` 只记录**可审计的配置侧字段**（状态、版本号、适用范围、编码），不记录正文。这既是铁律 2（本子模块不产生病历正文），也是为了不让日志表膨胀成第二份正文库 |
| D-45 | 只增不改由触发器 `trg_m18_tpl_oper_log_immutable` 强制，同时数据库角色层面 `REVOKE UPDATE, DELETE`。双重强制的理由与模块汇总 §3.1 一致：触发器能被 `ALTER TABLE ... DISABLE TRIGGER` 关掉，权限不会被普通 DBA 随手改 |
| D-46 | `idx_m18_tpl_oper_log_failed` 是部分索引，只索引失败行。失败行占比通常低于 1%，部分索引让「最近失败操作」的告警查询从全分区扫描降到几十行 |

### 4.12 Pydantic Schema 定义

Schema 文件路径遵循共享规范 §2.7：`app/schemas/m18/template.py`。统一使用 Pydantic V2 语法，全部继承 `M18BaseModel`（`model_config = ConfigDict(from_attributes=True, str_strip_whitespace=True)`）。四类 Schema 含义：

| 类别 | 命名后缀 | 用途 | 典型入口 |
| :--- | :--- | :--- | :--- |
| Create | `Create` | 新增请求体 | `POST` 类接口 |
| Update | `Update` | 修改请求体（全字段可选） | `PUT` 类接口 |
| Out | `Out` | 响应出参 | 全部查询接口 |
| Query | `Query` | 查询条件（列表/检索） | 列表类接口的 `Depends()` |

数值铁律：所有比率字段 `Decimal` + `max_digits=10, decimal_places=6`；所有计数字段 `int` 且 `ge=0`；**不出现 `float`**。枚举字段一律用 `Literal[...]` 收窄，取值与共享规范 §13 逐字一致，不在此处重新定义中文标签。

SELECT t.template_code, t.template_name, t.record_type, t.status,
       t.published_version_no, s.section_type, s.section_title, s.sort_no,

**E.4 查某模板被哪些历史病历引用（P08 引用分析、停用前置检查）：**

SELECT template_code, version_no, SUM(record_count) AS total_records,
       MAX(stat_date) AS last_used_date,
       SUM(finalized_count) AS total_finalized
FROM m18_tpl_ref_stat
WHERE template_code = 'T_OPD_REFRACT_001'

**E.5 查近 30 天发布记录（P05 版本历史、医务科检查）：**

SELECT template_code, version_no, action_type, action_at,
       operator_name, approved_by, effective_from, change_reason

**E.6 按配置键取三层覆盖后的生效值（配置解析器）：**

SELECT config_key, scope_type, scope_code, config_value, value_type
FROM m18_tpl_config
WHERE config_key = 'template.approve.dual_sign'
  AND ((scope_type = 'TEMPLATE' AND scope_code = 'T_OPD_REFRACT_001')
    OR (scope_type = 'RECORD_TYPE' AND scope_code = 'OUTPATIENT')

**E.9 统计某科室各模板使用排名（P08）：**

```sql
SELECT template_code, SUM(record_count) AS records,
       ROUND(AVG(finalize_rate), 6) AS avg_finalize_rate,
       ROUND(AVG(field_fill_rate), 6) AS avg_field_fill_rate
FROM m18_tpl_ref_stat
WHERE dept_id = 101
  AND stat_date >= DATE_TRUNC('month', CURRENT_DATE)::date
GROUP BY template_code
ORDER BY records DESC;
```

**E.10 检查「某科室是否已有已发布门诊模板」（上线检查项）：**

```sql
SELECT d.dept_id, d.dept_name, COUNT(t.id) AS published_templates
FROM mdm_dept d
LEFT JOIN m18_tpl_template t
       ON t.dept_id = d.dept_id
      AND t.status = 'PUBLISHED'
      AND t.record_type = 'OUTPATIENT'
      AND t.is_deleted = FALSE
GROUP BY d.dept_id, d.dept_name
HAVING COUNT(t.id) = 0;
```
