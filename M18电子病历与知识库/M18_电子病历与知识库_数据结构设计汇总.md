### 1.3 跨子模块共用的表

> **M18 有 5 张表被多个子模块共用，由第一个需要的子模块定义完整 DDL，其余子模块只引用。** 这与 M19 的做法一致。

| 表 | 定义方（首建） | 引用方 | 首建理由 |
|---|---|---|---|
| **`m18_emr_record`** | **M18-02** | M18-03、M18-04、M18-05、M18-06、M18-07 | 门诊病历是最先产生病历正文的场景（门诊量 36 万份/年 vs 住院 1.8 万份/年），且 `P-01`（M07-06 取病历正文）就挂在 M18-02 上 |
| **`m18_emr_record_field`** | **M18-02** | M18-03、M18-04、M18-05 | 同上，结构化字段是正文的从属表 |
| **`m18_emr_amendment`** | **M18-06** | M18-07 | 更正与作废是 M18-06 的核心职责（铁律 4 的唯一例外路径），由它定义 |
| **`m18_emr_seal`** | **M18-06** | M18-07 | M06-06 `:197` 已把封存归 M18，封存检查是 M18-06 §5 的核心 |
| **`m18_emr_document`** | **M18-06** | M18-07 | **M05-06 `M05住院管理/M05_住院管理_数据结构设计汇总.md:740` 已硬引用这张表做「文书存在性检查」**，它本质上是归档后的病案文书目录，与归档同属 M18-06 |

> ⚠️ **`m18_emr_document` 的归表最容易搞错。** 直觉上「文书」应该归 M18-02/03/04（它们产生病历），但**M18 的文书不是病历正文，而是「病历归档后形成的病案文书目录条目」**——它记录的是「某就诊有哪些文书、文书存在与否、是否已归档」，回答的是 M05-06 的完整性问题。而 `P-01` 返回的正文来自 `m18_emr_record`。两者是不同的东西。
>
> **判据一句话：正文回答「写了什么」在 `m18_emr_record`；文书目录回答「有哪些、在不在」在 `m18_emr_document`。** 一份 `SIGNED` 病历（`m18_emr_record`）可以对应多份文书（`m18_emr_document`，如门诊病历 + 诊断证明书 + 手术同意书）。

### 2.4 建表硬规范（强制）

| # | 规定 |
|---|---|
| 1 | 主键统一 `BIGINT GENERATED BY DEFAULT AS IDENTITY`，**不用 UUID**（BIGINT 索引小、JOIN 快，医疗数据不跨库合并） |
| 2 | 公共字段必须齐：`created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`、`created_by BIGINT`、`updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`、`updated_by BIGINT` |
| 3 | `is_deleted` **只给可变配置类表**；病历事实表（`m18_emr_record` / `m18_emr_record_field` / `m18_emr_amendment` / `m18_emr_seal` / `m18_arc_batch` / `m18_arc_item` / `m18_emr_document`）**一律不设**，改用状态表示（`VOIDED` / `RELEASED`） |
| 4 | 金额 `NUMERIC(14,2)`、比率 `NUMERIC(10,6)`、评分 `NUMERIC(5,1)`；**禁 FLOAT / DOUBLE / REAL** |
| 5 | 枚举 `VARCHAR(32)` + CHECK；值全大写英文下划线，**不得中文** |
| 6 | 大字段 `JSONB`，且必须在字段说明里写清结构（示例 JSON 放附录 D） |
| 7 | 时间一律 `TIMESTAMP`（不带时区，全院统一 Asia/Shanghai）；**不用 `TIMESTAMP WITH TIME ZONE`**（混用会导致跨模块比较出错） |
| 8 | 所有 VARCHAR 必须给长度；**不得用 `TEXT` 存结构化字段**（正文用 `TEXT` 可以） |
| 9 | 逻辑外键必须建索引（`patient_id` / `encounter_id` / `record_id` 全部要） |
| 10 | 表与字段必须有 `COMMENT ON`（中文说明），无注释的表视为未交付 |

## 3. 三处数据库强制

> M18 有三条**必须在数据库层落地、不能只写在代码里**的约束。理由一致：**如果只在应用层校验，任何一个绕过应用的入口（运维直连、批量脚本、其他服务的 job）都会破坏它，而 M18 的数据一旦破坏就无法修复。**

### 3.1 强制一：病历签署后禁改（铁律 4）

**落地三件套：**

```sql
-- ① 触发器：SIGNED 之后改正文，直接抛错
CREATE OR REPLACE FUNCTION trg_fn_m18_emr_record_signed_guard()
RETURNS TRIGGER AS $$
BEGIN
    IF OLD.status = 'SIGNED' THEN
        IF NEW.chief_complaint  IS DISTINCT FROM OLD.chief_complaint
           OR NEW.present_illness IS DISTINCT FROM OLD.present_illness
           OR NEW.past_history    IS DISTINCT FROM OLD.past_history
           OR NEW.physical_exam   IS DISTINCT FROM OLD.physical_exam
           OR NEW.diagnosis_text  IS DISTINCT FROM OLD.diagnosis_text
           OR NEW.treatment_plan  IS DISTINCT FROM OLD.treatment_plan
           OR NEW.content_hash    IS DISTINCT FROM OLD.content_hash THEN
            RAISE EXCEPTION 'ALREADY_SIGNED_IMMUTABLE'
                USING HINT = '已签署病历不可修改正文，请走作废重开或追加更正';
        END IF;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m18_emr_record_signed_guard
    BEFORE UPDATE ON m18_emr_record
    FOR EACH ROW EXECUTE FUNCTION trg_fn_m18_emr_record_signed_guard();

-- ② 权限：应用账号无权 UPDATE 关键列（PostgreSQL 支持列级权限）
REVOKE UPDATE ON m18_emr_record FROM app_m18;
GRANT UPDATE (status, void_reason, voided_at, voided_by, updated_at, updated_by)
    ON m18_emr_record TO app_m18;

-- ③ 权限：应用账号对病历事实表无 DELETE
REVOKE DELETE ON m18_emr_record FROM app_m18;
```

**为什么三层而不是一层：**
- 触发器：唯一能拦住「UPDATE 语句」的层，且能给出可读的错误信息（`ALREADY_SIGNED_IMMUTABLE`）。
- 列级 `REVOKE UPDATE`：拦住任何试图更新正文列的语句，**包括未来新写的、不知道触发器存在的代码**。
- `REVOKE DELETE`：拦住删除。

> ⚠️ **注意：`REVOKE UPDATE ON m18_emr_record` 之后必须 `GRANT UPDATE (列清单)`**，否则状态流转（`FINALIZED → SIGNED → VOIDED`）也做不了。列清单必须**逐列显式列出**，不能用 `ALL`——用 `ALL` 等于 `GRANT UPDATE ON table`，把刚 revoke 的又发回去了。

### 3.2 强制二：病历不可删除（门诊 15 年 / 住院 30 年 / 屈光永久）

```sql
REVOKE DELETE ON m18_emr_record        FROM app_m18;
REVOKE DELETE ON m18_emr_record_field  FROM app_m18;
REVOKE DELETE ON m18_emr_amendment     FROM app_m18;
REVOKE DELETE ON m18_emr_seal          FROM app_m18;
REVOKE DELETE ON m18_arc_batch         FROM app_m18;
REVOKE DELETE ON m18_arc_item          FROM app_m18;
REVOKE DELETE ON m18_emr_document      FROM app_m18;
```

**表结构层面也表达「不可删除」：** 上述 7 张表**没有 `is_deleted` 列**。这个做法沿用 `M11屈光手术管理/M11_屈光手术管理_07_屈光质量与并发症管理_数据结构.md:187`、`:404` 的成熟经验——「去掉该列后，删除与原地修改在表结构层面无法表达，只剩 INSERT 一条路径」。

> **判据：如果一张表需要「删除」，说明它的设计前提是「数据会变」；病历的前提是「数据不会变」。** 病历作废用 `VOIDED` 状态，不是删除。

### 3.3 强制三：封存后全部只读

```sql
CREATE OR REPLACE FUNCTION trg_fn_m18_seal_guard()
RETURNS TRIGGER AS $$
DECLARE
    v_sealed BOOLEAN;
BEGIN
    SELECT EXISTS (
        SELECT 1 FROM m18_emr_seal s
        WHERE s.status = 'ACTIVE'
          AND s.patient_id = NEW.patient_id
          AND (s.seal_scope = 'PATIENT'
               OR (s.seal_scope = 'ENCOUNTER' AND s.encounter_id = NEW.encounter_id)
               OR (s.seal_scope = 'DATE_RANGE'
                   AND NEW.record_date BETWEEN s.date_from AND s.date_to))
    ) INTO v_sealed;

    IF v_sealed THEN
        RAISE EXCEPTION 'RECORD_SEALED'
            USING HINT = '该病历已被封存，不可写入。如需解封请走医务科审批';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

**挂载点：** `m18_emr_record`（INSERT/UPDATE）、`m18_emr_record_field`、`m18_emr_amendment`（INSERT）、`m18_emr_document`、`m18_arc_item`（INSERT/UPDATE）、`m18_opr_*`、`m18_ipd_*` 全部病历正文表。

> **为什么封存检查必须在数据库层？** 封存的法律含义是「这份病历已作为证据提交，任何人不得改动」。封存后还会改病历的情形是**真实存在的**（医疗纠纷发生后，涉事医生被要求「补一下记录」）。应用层检查可以被新写的接口漏掉，数据库触发器不行。
>
> **代价要接受：** 封存期间的检索统计要用 `m18_idx_*`（只读快照表），不能再扫病历正文表。

## 4. 分区策略

| 表类别 | 是否分区 | 策略 | 理由 |
|---|---|---|---|
| **病历事实表**（`m18_emr_record` / `_field` / `m18_emr_amendment` / `m18_emr_document` / `m18_arc_*`） | ❌ **不分区** | — | ①三年累计约 145 万份病历正文，单表完全可承受；②**分区表的唯一约束必须带分区键**，而 `m18_emr_record` 的唯一键是 `(encounter_id, record_type, is_current)`——把 `created_at` 塞进唯一键会让「同一就诊同类型只能有一份当前病历」这条约束失效；③病历查询总是带 `patient_id` / `encounter_id` 精确条件，不走时间范围扫描 |
| **病程类明细表**（`m18_ipd_course_record` / `m18_ipd_ward_round` / `m18_opr_specialty_exam`） | ❌ **不分区** | — | 三年累计约 65 万行，量级更小 |
| **质控任务与审核记录**（`m18_qc_task` / `m18_qc_medication_review` / `m18_qc_oper_log`） | ✅ **月分区** | `PARTITION BY RANGE (created_at)` + **必须建 DEFAULT 分区** | 年增约 84 万条，且**只保留 3 年在线**（更早的归档到只读库），分区使得过期数据可以 `DETACH PARTITION` 秒级下线 |
| **质控缺陷明细**（`m18_qc_defect`） | ❌ **不分区** | — | **见下方注**：它的唯一键 `uk_m18_qc_defect (qc_task_no, defect_code, defect_object)` 不含分区键，而分区表要求唯一索引必须包含分区键——把 `created_at` 塞进唯一键会让去重语义退化成「同月内唯一」，**而「同一任务同一对象的同一缺陷只记一次」正是这条约束唯一的存在理由**。量级（3 年 180 万行）单独成表完全可承受，随父表 `m18_qc_task` 一起归档即可 |

> **注（质控缺陷明细为什么不分区）**：这是「分区 vs 唯一约束」冲突的第二个现场（第一个是 `m18_emr_record`）。判据统一为：**如果这张表的某条唯一约束本身就是业务语义的一部分（不只是防重），那它就不能分区**——分区表强制唯一索引带分区键，等价于把「全局唯一」偷偷降级成「分区内唯一」，而这种降级不会报错、不会告警，只会让去重在某个月边界上突然失效。**正确做法是：宁可少分一张表，也不要让一条业务约束悄悄变弱。**
| **检索日志**（`m18_idx_search_log`） | ✅ **月分区** | 同上 | 年增可达数百万条，保留 1 年 |
| **配置与主数据类**（`m18_tpl_*` / `m18_kb_*`） | ❌ **不分区** | — | 数据量小（知识规则约 8,000 条，模板约 300 个） |
| **统计快照**（`m18_idx_case_stat` / `m18_idx_quality_metric`） | ❌ **不分区** | — | 按 `(period, dept_id)` 组织，量小 |

**分区表 DDL 模板（强制格式）：**

```sql
CREATE TABLE m18_qc_task (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY,
    qc_task_no    VARCHAR(32) NOT NULL,
    record_id     BIGINT NOT NULL,
    status        VARCHAR(32) NOT NULL DEFAULT 'PENDING',
    created_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE m18_qc_task_p202610 PARTITION OF m18_qc_task
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

CREATE TABLE m18_qc_task_default PARTITION OF m18_qc_task DEFAULT;
```

> ⚠️ **DEFAULT 分区不是可选项。** 若 2026-11 的分区还没建而 2026-11-01 00:00 就有数据写入，没有 DEFAULT 分区时 INSERT 会直接失败。DEFAULT 分区的存在使得「分区预建任务漏跑」变成「数据进了 default 分区」而不是「业务报错」。校验器 `validate_m18.py` 会检查每个 `PARTITION BY RANGE` 是否带 `DEFAULT`。

| 项 | 估算 |
|---|---|
| GIN 全文索引（`m18_idx_search_doc.search_vec`） | ≈ 病历正文的 30% → 3 年约 **1.4 GB** |
| B-Tree 索引（`patient_id` / `encounter_id` / `status` / `record_no` 等） | ≈ 主表数据的 40% → 3 年约 **5 GB** |
| 表 + 索引合计 | ≈ **25~30 GB** |

### 5.4 结论

**M18 三年数据量约 30GB，单机 PostgreSQL 完全可承载。** 年增长约 8~10GB，五年约 55GB。**不需要分库分表，不需要引入 Elasticsearch，不需要把病历正文放进对象存储**（正文放进 OSS 会让「按内容检索」变成不可能，而病案室最常做的事就是按内容检索）。

> 唯一需要提前规划的是**归档库**：法律规定门诊 15 年、住院 30 年，意味着 5 年后在线库会到 55GB、10 年后到 110GB。**方案：3 年内的数据在线（约 30GB），3 年以上迁到只读归档库（同实例的独立 schema + 独立表空间，或独立实例）。** 迁移脚本由 M18-06 的留存期任务驱动（见 §10）。

## 7. 全局约束清单

### 7.1 跨表一致性约束（应用层保证，数据库无法表达）

| # | 约束 | 落地位置 | 违反后果 |
|---|---|---|---|
| **G-01** | `m18_emr_record.content_hash` 一经固化不可变（`FINALIZED` 之后） | 触发器 `trg_fn_m18_emr_record_signed_guard()` | 病历可被篡改，诉讼中不具证明力 |
| **G-02** | 同一 `(encounter_id, record_type, is_current = TRUE)` 只能有一行 | 部分唯一索引 `uk_m18_emr_record_encounter_current` | 同一就诊出现两份「当前病历」，M07-06 不知道用哪份 |
| **G-03** | `m18_emr_record.status` 只能按 `DRAFT → FINALIZED → SIGNED`、`FINALIZED/SIGNED → VOIDED` 流转 | 触发器 + Service 层状态机 | 状态倒挂 |
| **G-04** | `m18_emr_amendment.record_id` 必须指向 `FINALIZED` 或 `SIGNED` 的记录 | Service 层 + `P-11` 校验 | 对草稿做更正毫无意义，说明调用方逻辑错了 |
| **G-05** | 封存生效期间，病历正文表全部拒绝写入 | 触发器 `trg_fn_m18_seal_guard()` | 封存病历被篡改 |
| **G-06** | `m18_arc_batch` 的 `(source_module, source_biz_no)` 幂等 | 唯一约束 `uk_m18_arc_batch_source` | 同一份归档单重复入库，病案统计翻倍 |
| **G-07** | 归档批次 `CONFIRMED` 之后不可回到 `CHECKING` | Service 层状态机（`RELEASED` 是终态，不可回） | 已确认归档的批次被重算 |
| **G-08** | `m18_emr_document.integrity_result = 'UNKNOWN'` 的批次不得自动确认归档 | Service 层（必须人工复核） | 把「查不到」当「完整」 |
| **G-09** | 知识库规则 `PUBLISHED → SUPERSEDED` 时，**不回算**已产生的审核结果 | Service 层 | 历史上「当时审核通过」的处方被追溯改判 |
| **G-10** | 过敏史明细变更必须发 `m18.allergy.updated` 事件 | Service 层 | M03 冗余字段与明细不一致，M07-05 过敏拦截失效 |
| **G-11** | `qc_level` 为 `GRADE_C` 必须有至少一个 `CRITICAL` 缺陷或 `qc_score < 75` | 组合 CHECK | 丙级病历没有依据 |

### 7.2 组合约束判别（CHECK 只保护字段自身，不保护字段之间）

> **这条与 M19 的经验完全一致**：凡是「某个类型 / 状态必须配一整套参数」的场景，必须另写组合约束，否则会出现「状态是 A 但字段是 B 的」这种数据库层面合法、业务层面荒谬的行。

| 场景 | 必须写的组合约束 | 只写单字段约束会漏掉什么 |
|---|---|---|
| `m18_emr_record` 定稿 | `CHECK (status = 'DRAFT' OR (content_hash IS NOT NULL AND finalized_at IS NOT NULL))` | `status='SIGNED'` 但 `content_hash` 为空——无法验证病历未被篡改 |
| `m18_emr_record` 作废 | `CHECK (status <> 'VOIDED' OR (void_reason IS NOT NULL AND voided_at IS NOT NULL AND voided_by IS NOT NULL))` | 作废了但不知道谁、为什么作废；审计时无法追溯 |
| `m18_emr_record` 签署 | `CHECK (status <> 'SIGNED' OR signed_at IS NOT NULL)` | 已签署但没记签署时间 |
| `m18_emr_seal` 解封 | `CHECK (status <> 'RELEASED' OR (released_at IS NOT NULL AND released_by IS NOT NULL AND release_reason IS NOT NULL))` | 解封记录缺审批信息，等于没有留痕 |
| `m18_arc_batch` 拒绝 | `CHECK (status <> 'REJECTED' OR jsonb_array_length(reject_items) > 0)` | 拒绝但没说缺什么，M05/M06 无法整改 |
| `m18_qc_defect` 整改 | `CHECK (status <> 'RECTIFIED' OR (rectified_at IS NOT NULL AND rectified_by IS NOT NULL))` | 标记已整改但没留证 |
| `m18_qc_score` 丙级 | `CHECK (qc_level <> 'GRADE_C' OR qc_score < 75 OR has_critical = TRUE)` | 丙级病历可能是「分数 92 但无任何严重缺陷」，无法解释 |
| `m18_kb_path_entry` 完成 | `CHECK (status <> 'COMPLETED' OR completed_at IS NOT NULL)` | 完成但没有完成时间，算不出路径时长 |
| `m18_arc_borrow` 已批准 | `CHECK (status <> 'APPROVED' OR (approved_by IS NOT NULL AND approved_at IS NOT NULL))` | 借阅批准了不知道谁批的——这是隐私泄露的最大风险点 |
| `m18_emr_document` 存在性 | `CHECK (is_present = FALSE OR (doc_no IS NOT NULL AND generated_at IS NOT NULL))` | 标了「存在」但没有文书号与生成时间 |

### 7.3 唯一约束与部分索引

| 表 | 约束 | 语义 |
|---|---|---|
| `m18_emr_record` | `uk_m18_emr_record_encounter_current UNIQUE (encounter_id, record_type) WHERE is_current = TRUE` | 同一就诊同类型只有一份当前病历 |
| `m18_emr_record` | `uk_m18_emr_record_no UNIQUE (record_no)` | 病历号唯一 |
| `m18_arc_batch` | `uk_m18_arc_batch_source UNIQUE (source_module, source_biz_no)` | 归档幂等 |
| `m18_arc_batch` | `uk_m18_arc_batch_no UNIQUE (batch_no)` | 批次号唯一 |
| `m18_tpl_template_version` | `uk_m18_tpl_template_version UNIQUE (template_code, version_no)` | 模板版本唯一 |
| `m18_kb_med_rule` | `uk_m18_kb_med_rule UNIQUE (rule_code, rule_version)` | 规则版本唯一 |
| `m18_kb_path_entry` | `uk_m18_kb_path_entry UNIQUE (path_code, patient_id, encounter_id)` | 同一患者同一就诊同一路径只入径一次 |
| `m18_qc_defect` | `uk_m18_qc_defect UNIQUE (qc_task_no, defect_code, defect_object)` | 同一任务同一对象的同一缺陷只记一次 |
| `m18_emr_seal` | `uk_m18_emr_seal_no UNIQUE (seal_no)` | 封存号唯一 |
| `m18_emr_document` | `uk_m18_emr_document UNIQUE (encounter_id, doc_type, doc_seq)` | 同一就诊同类型文书的序号唯一 |

> ⚠️ **注意 `is_current` 部分唯一索引不参与 `is_deleted`。** 病历不可删除（G-02 的前提），所以不需要 `AND is_deleted = FALSE`。若加了，一旦有人给某行置 `is_deleted = TRUE`，约束就放行出现两份当前病历。

## 8. Alembic 迁移策略

### 8.1 分支与版本

| 项 | 规定 |
|---|---|
| 迁移目录 | `alembic/versions/m18/` |
| 版本号 | `m18_0001_init_template` … 递增 |
| 分支 | 单一主干（不用 `branch_label`） |
| 每个迁移文件 | 一个逻辑变更单元，**不得混装多个子模块的表** |
| 强制要求 | 每个迁移必须同时写 `upgrade()` 与 `downgrade()`；若确实不可逆（如分区表转非分区），`downgrade()` 里 `raise NotImplementedError` 并在注释里写理由 |

### 8.2 迁移顺序（对应 §6）

```
m18_0001_init_template      → ① 模板类 9 张
m18_0002_init_kb            → ② 知识库 12 张
m18_0003_init_emr_record    → ③ 病历事实 10 张（含 m18_emr_record）
m18_0004_init_ipd           → ④ 住院病历 9 张
m18_0005_init_opr           → ⑤ 手术麻醉病历 9 张
m18_0006_init_qc            → ⑥ 质控与用药审核 11 张
m18_0007_init_archive       → ⑦ 归档封存更正 11 张
m18_0008_init_search        → ⑧ 检索与统计 9 张
m18_0009_add_triggers       → 三处数据库强制（触发器 + 权限）
m18_0010_init_data          → 初始化数据（见 §9）
```

### 8.3 高危迁移清单

| 变更 | 风险 | 做法 |
|---|---|---|
| 给 `m18_emr_record` 加字段 | **低**（加列为 `NULL` 安全） | 直接加，`downgrade` 删列 |
| 给 `m18_emr_record` 删字段 | **极高** | **禁止**。病历字段一旦上线不可删（数据是证据）；确要废弃就置为 `DEPRECATED` 并停止写入，字段保留 |
| 改 `content_hash` 算法 | **极高** | **禁止**。已固化的 hash 一旦改算法，所有历史病历的 hash 全部失效，等于宣告历史病历「无法验证未被篡改」 |
| 给 `m18_emr_record` 加 CHECK | 中 | 必须先用 `SELECT` 扫一遍存量数据，确认无违反再 `ADD CONSTRAINT`（否则整表加约束失败） |
| 分区表加分区 | 低 | `CREATE TABLE ... PARTITION OF ...` 即可，不锁表 |
| 给分区表加唯一约束 | **高** | PostgreSQL 要求唯一约束包含分区键；若业务唯一键不含 `created_at`，**不能加唯一约束**，只能加全局 `EXCLUDE` 或用应用层保证 |
| 重建 GIN 全文索引 | 中 | 用 `CREATE INDEX CONCURRENTLY`，避免锁表；百万行约 3 分钟 |

### 8.4 上线前必跑的三条校验 SQL

```sql
-- 1. 确认病历事实表无 is_deleted 列
SELECT table_name, column_name
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name IN ('m18_emr_record', 'm18_emr_record_field', 'm18_emr_amendment',
                     'm18_emr_seal', 'm18_arc_batch', 'm18_arc_item', 'm18_emr_document')
  AND column_name = 'is_deleted';
-- 期望：0 行

-- 2. 确认应用账号对病历事实表无 DELETE 权限
SELECT has_table_privilege('app_m18', 'm18_emr_record', 'DELETE');
-- 期望：false

-- 3. 确认所有分区表都有 DEFAULT 分区
SELECT parent.relname AS parted_table
FROM pg_inherits i
JOIN pg_class parent ON parent.oid = i.inhparent
JOIN pg_class child  ON child.oid  = i.inhrelid
WHERE parent.relname LIKE 'm18_%'
GROUP BY parent.relname
HAVING NOT bool_or(pg_get_expr(child.relpartbound, child.oid) = 'DEFAULT');
-- 期望：0 行
```

### 9.2 初始化顺序（强依赖）

```
1. m18_tpl_config / m18_kb_config / m18_qc_config / m18_arc_config / m18_idx_config
2. m18_kb_* 基础规则（依赖 M01 药品/诊断主数据已导入）
3. m18_tpl_template + m18_tpl_template_section + m18_tpl_field_def（依赖专科/科室主数据）
4. m18_tpl_consent_template（依赖医务科审核）
5. m18_kb_path + m18_kb_path_node
6. m18_kb_drg_weight
7. m18_qc_rule
8. m18_arc_retention
9. 复核：每个配置类的 PUBLISHED 记录数 > 0
```

> ⚠️ **初始化不能「先上线再补模板」。** M18-02 没有已发布模板时，医生打开病历书写页只能看到空白——M07-06 `:3357` 的降级是「用简化模板生成简化版文书」，那就是上线第一天全院病历都是简化版。**上线检查项：已发布门诊模板 ≥ 1 个/科室，已发布专科模板 ≥ 1 个/专科。**

### 9.3 初始化验证 SQL

```sql
-- 每个科室至少有 1 个已发布的门诊病历模板
SELECT d.id AS dept_id, d.name,
       count(t.id) AS published_tpl_count
FROM mdm_dept d
LEFT JOIN m18_tpl_template t
       ON t.dept_id = d.id
      AND t.status = 'PUBLISHED'
      AND t.record_type = 'OUTPATIENT'
WHERE d.is_deleted = FALSE
  AND d.dept_type = 'CLINICAL'
GROUP BY d.id, d.name
HAVING count(t.id) = 0;
-- 期望：0 行
```

## 10. 备份与归档

### 10.1 备份策略

| 级别 | 频率 | 保留 | 说明 |
|---|---|---|---|
| **全量备份** | 每日 02:00 | 30 天 | `pg_basebackup` + WAL 归档 |
| **WAL 连续归档** | 实时 | 30 天 | 支持 PITR（时间点恢复）到任意秒 |
| **病历事实表单独备份** | 每周日 | **永久** | `pg_dump -t m18_emr_record -t m18_emr_amendment -t m18_emr_seal`，加密后离线存档 |
| **配置类表导出** | 每次变更 | 20 个版本 | `m18_tpl_*` / `m18_kb_*` / `m18_qc_rule` 变更时自动导出 JSON |

> **为什么病历事实表要「永久」离线备份？** 法定保存期门诊 15 年、住院 30 年、屈光永久。在线库的保留策略是 3 年，超过 3 年迁到归档库；但**归档库本身也会被误删/磁盘损坏**。病历是法律证据，必须有一份物理隔离、加密、不依赖任何系统的副本。

### 10.2 留存期数据迁移

| 数据年龄 | 位置 | 状态 |
|---|---|---|
| 0~3 年 | 在线库 `public` schema | 读写 |
| 3~15 年（门诊）/ 3~30 年（住院） | 归档库 `m18_archive` schema（同实例或独立实例） | 只读 |
| 超过留存期 | **不销毁** | 见 10.3 |

**迁移流程（`m18_arc_retention` 配置驱动，APScheduler 每年执行）：**

```
1. 按 m18_arc_retention.retention_years 计算可迁移边界
2. 校验：该范围内所有病历 status ∈ ('SIGNED', 'VOIDED')（草稿病历永不迁移）
3. 校验：该范围内所有封存记录 status ≠ 'ACTIVE'（封存中不迁移）
4. 导出到归档库（INSERT ... SELECT 跨 schema）
5. 校验行数、content_hash 抽样 100 份逐一比对
6. 从在线库 DELETE —— ⚠️ 这一步需要特殊权限（app_m18 无 DELETE）
7. 记录迁移日志（迁出时间、行数、校验结果、执行人）
```

> ⚠️ **第 6 步是唯一允许删除病历的路径，且必须由专门的数据管理员账号 `m18_archiver` 执行，不得由 `app_m18` 执行。** 删除前必须完成第 5 步的 hash 抽样校验——**没有校验过就删除，等于用「迁移脚本肯定没问题」这个假设销毁法律证据。**

### 10.3 留存期到期后的处置

| 情形 | 处置 |
|---|---|
| 门诊病历满 15 年 | **不销毁**。法规只规定最低保存期，未规定必须销毁；销毁病历在医疗纠纷中是重大不利证据 |
| 住院病历满 30 年 | 同上 |
| 屈光档案 | **永久保存，永不销毁** |
| 患者本人书面要求删除 | **不予删除**。病历属于医疗机构的法定档案，患者无权要求销毁；只能限制访问 |

> **一句话：M18 的删除路径设计目标是「让它极难被调用，且每一次调用都留痕」，而不是「提供一个删除功能」。**
