### 最需要读到的三件事

**第一，本子模块不提供审核接口。** `POST /internal/v1/kb/medication-check`（P-08）由 M18-05 实现。M18-08 只负责把规则创作出来、审核过、发布出去、加载进内存。这个分工如果搞混，两个子模块会各写一个审核接口，最终两边的审核结论不一致，而 M14-06 引用的那句「所有判断规则来自 M18 知识库」就落不到任何一个具体实现上。

**第二，规则常驻内存，不放 Redis。** 这不是性能优化偏好，是硬约束：P-08 的预算是 P95 ≤ 300ms，而一次 Redis 往返加反序列化在这个链路上会吃掉 30~80ms，且规则匹配本身涉及患者维度与眼科专科条件的组合求值，本来就要计算而不是查表。详见 §7。

**第三，规则只增不减的系统会死。** 8,000 条规则两年后变成 15,000 条，医生会把整个提示功能关掉。所以本子模块把「命中率 > 80% 复审」「零命中清理」「全忽略干预」三类巡检做成了可查清单与定期复审机制（§10.7、附录 C）。规则命中统计不是报表，是知识库的自我维护机制。

## 1. 模块概述

### 1.1 定位

M18-08 是全院**临床知识资产的唯一创作与管理出口**。它回答一个问题：当 M07-05 的医生开出处方、当 M05-07 计算 CMI、当 M07 打开某个住院患者的临床路径提示时，那些“什么药不能一起吃”“这个剂量超了”“这个患者该走哪条路径”的知识，是从哪里来的、谁维护的、什么时候生效的。

一句话定位：**本子模块生产知识，M18-05 执行审核，M14-06 执行审方，M05/M07 消费路径与权重。**

### 1.2 为什么独立成子模块

三个原因，缺一不可：

**知识有独立的生命周期，与病历时序完全无关。** 一条用药规则的生效日期可能早于医院上线日期（沿用上级医院既有规则），也可能在半夜发布（医保新政次日起执行）。它的版本、审核、发布节奏跟任何一份病历都不同步。把规则塞在审核子模块里，等于让「规则」受「审核」的部署节奏约束。

**知识是跨科室、跨模块共享的资产，必须有唯一出口。** 同一条「散瞳药与闭角型青光眼禁忌」，M07-05 开方要用、M14-06 审方要用、M18-05 质控要用。如果每个消费方各自维护一份，两边结论不一致时无法归因。统一到本子模块，才可能实现总纲 §3.2 的临床知识闭环判据：同一张处方开方时与审方时结果必须一致。

**知识库需要一套与业务表不同的数据治理。** 规则表是「只增不改 + 版本化 + 发布审核」的结构，与病历表的「签署后禁改」、与配置表的「随时可改」都不同。它的表结构、权限、巡检 SQL 都无法与别的子模块共用。

### 1.3 与相邻子模块的分工

这是本文档最重要的一张表。**分工没写清，就会有两个审核接口。**

| 子模块 | 角色 | 在本子模块的边界上做什么 | 本子模块与它的关系 |
|---|---|---|---|
| **M18-08（本子模块）** | **规则创作方** | 规则的创作、审核、发布、版本管理、热重载、命中统计、临床路径定义与入径管理、DRG 权重导入、眼科知识条目维护 | — |
| M18-05 病历质控与合理用药审核 | **规则执行方** | 实现 `POST /internal/v1/kb/medication-check`（P-08），从内存规则集读取规则并求值，把命中明细写入 `m18_kb_hit_stat` | 本子模块向 M18-05 提供规则与匹配接口；M18-05 向本子模块回写命中统计 |
| M14-06 处方审核 | 审方执行方 | 在药房侧调用 P-08 复核处方，引用 M01-03 药品主数据与本子模块的规则 | 同 M18-05，是消费者 |
| M07-05 处方（门诊医生站） | 开方执行方 | 开方时调用 P-08 得到提示 | 消费者 |
| M07-06 病历文书 | 路径提示消费方 | 调用 P-12 得到患者当前临床路径状态 | 消费者 |
| M05-07 病案首页与 DRG | 权重消费方 | 调用 P-09 得到 DRG 权重，计算 CMI | 消费者 |
| M04-04 分诊 | 分诊规则消费方 | 引用本子模块维护的分诊规则 | 消费者，交付通道见 §10.6 |
| M01 主数据管理 | 主数据权威 | 提供药品、诊断、人员、科室；通过 CLI + MQ 分发增量；驱动 P-13 规则重载 | 上游 |

> **本子模块明确不提供 `POST /internal/v1/kb/medication-check`。** 共享规范 §8A 的契约表把 P-08 列在本子模块名下，但按 M18 内部分工，P-08 的实现归属 M18-05（它才是「审核」这件事的执行者，拥有审核场景、审核留痕、审核结果表）。本子模块提供的是内存规则集与匹配能力，被 M18-05 的 P-08 实现直接调用（进程内调用，不是 HTTP）。**这个分工已在 §10.2 与 §11.2 明确登记。**

### 1.4 概念辨析

四个容易被混用的词：

| 概念 | 定义 | 不是什么 |
|---|---|---|
| 规则（Rule） | 一条可机器求值的判定条件 + 提示内容 + 严重等级，如 `DR_INTER_001` | 不是知识条目。知识条目是给人读的 |
| 规则版本（rule_version） | 同一 `rule_code` 的第 N 次发布，整数递增 | 不是规则版本集 |
| 规则版本集（rule_version_set） | 某一时刻生效的**规则全集**的整体版本号，如 `20261021_001` | 不是单条规则的版本号 |
| 规则集（RuleSet） | 加载进内存的、不可变的规则对象集合 | 不是数据库表 |

> **「规则版本」与「规则版本集」的区别是本子模块最容易被误解的一点。** 单独回滚一条规则到旧版本，会造成「A 规则是新版、B 规则是旧版」这种状态——它不对应任何一个真实发布时刻，因而无法归因。所以每次发布都生成一个新版本集，把全部规则重新挂到新集上（详细论证见《M18_电子病历与知识库_08_临床知识库与路径_数据结构》第 4.6.1 节）。代价是每次发布一个约 120ms 的事务，收益是「任意历史审核结果都能用一个字符串精确还原当时的规则全集」。

### 1.5 模块目标

| 编号 | 目标 | 验收方式 |
|---|---|---|
| G-01 | 全院用药规则、眼科专科知识、临床路径、DRG 权重、分诊规则有唯一创作出口 | 功能验收：逐一确认五类知识资产在本子模块有创建入口，且在 M18 其他子模块中无重复创建入口 |
| G-02 | 规则发布需审核，发布后旧版本永久保留可查 | 功能验收：绕过审核直接发布必须被拒；发布后旧版本状态为 SUPERSEDED 且内容可完整读回 |
| G-03 | 规则常驻内存，P-08 匹配 ≤ 15ms，全量加载 ≤ 800ms | 性能验收：8,000 条规则全量加载计时；5 药品单次匹配计时 |
| G-04 | 热重载不中断服务，失败保留旧规则集不清空 | 故障注入验收：加载中途注入异常，确认旧规则集仍可服务且版本集编号不变 |
| G-05 | 规则升级不回算历史审核结果，历史可完整复现 | 数据一致性验收：发布新版本后重查历史审核记录，结论与 rule_version_set 均不变 |
| G-06 | 临床路径入径率按适用患者数算，不按住院总数算 | 口径验收：用 168/200 与 168/240 两组数验证分母取的是适用患者数 |
| G-07 | DRG 权重版本化，历史月份 CMI 用当时权重可复现 | 口径验收：按历史日期查权重，返回的是该日期生效版本，不是最新版本 |
| G-08 | 规则命中统计能发现误报规则、死规则、被全忽略规则 | 功能验收：三类巡检清单各能正确筛出构造的样本数据 |
| G-09 | 知识库规则变更不追溯重算已有病历的判定结果 | 数据一致性验收：同 G-05，重点验证已封账期间数据不被改写 |
| G-10 | 四条本院眼科重点规则可执行、可命中、可归因 | 功能验收：四条规则各构造一个命中样本，确认命中并能追溯到 rule_code 与 evidence_ref |

| 关系 | 基数 | 变更特性 | 加载方式 |

### 3.2 状态机

#### 3.2.1 规则状态机

```text
                    ┌──────────┐
                    │  DRAFT   │ ← 药师新建
                    └────┬─────┘
                         │ 提交审核
                         ▼
                    ┌──────────┐
              ┌─────│ IN_REVIEW│─────┐
              │     └────┬─────┘     │ 审核驳回
              │          │ 审核通过   │
              │          ▼           │
              │     ┌──────────┐     │
              │     │PUBLISHED │◀────┘（回 DRAFT 修改后重新提交）
              │     └────┬─────┘
              │          │ 新版本发布
              │          ▼
              │     ┌────────────┐
              │     │ SUPERSEDED │ 永久保留可查
              │     └────────────┘
              │
              │   ┌──────────┐
              └──▶│ DISABLED │ ← 任何非 SUPERSEDED 状态可停用
                  └──────────┘
```

| 状态 | 含义 | 可否修改内容 | 是否进内存 | 是否参与匹配 |
|---|---|---|---|---|
| `DRAFT` | 草稿，可自由修改 | 是 | 否 | 否 |
| `IN_REVIEW` | 待审核，已冻结 | 否 | 否 | 否 |
| `PUBLISHED` | 已发布生效 | 否（内容不可改） | 是 | 是 |
| `SUPERSEDED` | 被新版本取代 | 否 | 否 | 否 |
| `DISABLED` | 已停用 | 否 | 否 | 否 |

**三条硬规则：**

1. **`DRAFT → PUBLISHED` 不存在直接路径。** 必须经过 `IN_REVIEW`。绕过审核的发布等于让规则跳过专业知识把关，这是知识库最危险的漏洞。
2. **`PUBLISHED` 的内容不可修改。** 要改只能新建一个 `rule_version` 的新草稿。这保证「已发生的审核结果可复现」。
3. **`SUPERSEDED` 的记录不能被 `DISABLED`。** 被取代意味着历史，历史不可再变更状态。

#### 3.2.2 规则版本集状态机

```text
  ┌─────────┐  加载完成   ┌────────┐
  │ PENDING │───────────▶│ LOADED │
  └────┬────┘            └────────┘
       │ 部分实例加载失败
       ▼
  ┌─────────┐
  │ PARTIAL │  ← 已切换但集群不一致，告警
  └─────────┘
       │ 全部失败
       ▼
  ┌─────────┐
  │ FAILED  │  ← 未切换，继续用旧版本集
  └─────────┘
```

> **`PARTIAL` 是必须存在的中间态。** 集群 4 个实例，3 个加载成功 1 个失败，此时若记 `LOADED` 会掩盖不一致（那台实例上的患者拿到的审核结论与别的实例不同）；若记 `FAILED` 又会回滚掉已经成功切换的 3 个实例。`PARTIAL` 准确表达「已切换但不完整」，配合告警与巡检（数据结构文档附录 B.3）定位落后实例。

#### 3.2.3 路径入径状态机

```text
       ┌─────────┐
       │ ENTERED │ ← 入径
       └────┬────┘
            │ 首个节点开始
            ▼
     ┌──────────────┐  变异   ┌──────────┐
     │ IN_PROGRESS  │────────▶│ DEVIATED │
     └──────┬───────┘         └────┬─────┘
            │ 全部必需节点完成       │ 变异处理后继续
            ▼                      ▼
     ┌─────────────┐        （回 IN_PROGRESS）
     │  COMPLETED  │
     └─────────────┘

      任意非终态 ──出径──▶ ┌────────┐
                          │ EXITED │
                          └────────┘
```

| 状态 | 含义 | 终态 |
|---|---|---|
| `ENTERED` | 已入径，尚无节点开始 | 否 |
| `IN_PROGRESS` | 治疗进行中 | 否 |
| `DEVIATED` | 发生变异，待处理 | 否 |
| `COMPLETED` | 全部必需节点完成 | 是 |
| `EXITED` | 中途出径（转科/转院/退出） | 是 |

> **`DEVIATED` 不是终态，这一点最容易写错。** 变异是路径管理中的常态（本院 13.10% 的入径患者有过变异），发生变异后治疗继续，只是被标记为偏离标准。把 `DEVIATED` 设计成终态，会导致「变异后还必须重新入径一次」这种荒谬流程，而重新入径会让入径率虚高。

### 3.4 关键计算模型

#### 3.4.1 入径率（M18-CALC-04）

```text
入径率 = 入径患者数 / 适用患者数
```

**分母是适用患者数，不是住院总数。** 适用患者数由路径定义的入径标准筛出（诊断 + 年龄 + 术式 + 排除标记）。

**2026 年 10 月屈光中心白内障手术算例：**

| 项目 | 数量 | 说明 |
|---|---|---|
| 当月白内障手术总数 | 240 台 | 这是「住院总数」口径，**不是分母** |
| 符合入径标准的 | 200 台 | 单眼白内障、年龄 ≤ 85、无合并症 |
| 实际入径 | 168 台 | |
| 因合并症等正当排除 | 40 台 | 急诊手术、合并多科疾病、合并青光眼/糖尿病 |
| **入径率（正确分母）** | **168 / 200 = 84.00%** | |
| 入径率（错误分母） | 168 / 240 = 70.00% | |

> **分母选错的代价不是数字难看，是整改方向错。** 240 台里那 40 台本身就不符合任何路径的入径标准，把它们算进分母，意味着「路径覆盖率」这个指标永远上不去。医务科看到 70% 会做出「逼医生入径」的整改决定，而实际上该做的是「增加一条针对合并症患者的路径」或「调整标准」。**用 84% 才能看出来真正的问题在那 32 台（200 - 168）符合标准但没入径的病例上**，这 32 台才是需要逐个分析的。

**入径 168 台的下游指标：**

| 指标 | 计算 | 结果 |
|---|---|---|
| 变异率 | 变异入径患者数 / 入径患者数 = 22 / 168 | 13.10% |
| 完成率 | 完成的路径数 / 入径的路径数 = 160 / 168 | 95.24% |
| 出径率 | 出径数 / 入径数 = 8 / 168 | 4.76% |

> **完成率 95.24% 与出径率 4.76% 加起来正好 100%，说明 168 = 160 + 8 是闭合的。** 这个闭合关系必须作为校验项：若哪天出现「完成率 + 出径率 ≠ 100%」，说明有入径记录既没完成也没出径（卡在 `ENTERED`/`IN_PROGRESS`），那就是流程漏节点，不是统计问题。

#### 3.4.2 缺陷率（规则匹配度，M18-CALC-05）

```text
matched_rule_count = 命中的规则条数（按 rule_code 去重）
alert_count        = 提示条数（按 alert_level 展开）
```

**关键规则：一条规则命中多个药品只产生一条提示。** 唯一键是 `rule_code + drug_code`。

**算例：一张处方开具 3 种喹诺酮类滴眼液，命中 2 条规则：**

| 规则 | 涉及药品 | 命中药品数 | 产生提示数 |
|---|---|---|---|
| `DR_DUP_001`（同类重复用药） | 3 个喹诺酮 | 3 | **1**（不是 3） |
| `DR_INTER_015`（与某合并用药相互作用） | 1 个喹诺酮 | 1 | 1 |
| **合计** | | | `matched_rule_count = 2`，`alert_count = 2` |

> **如果按药品展开，这张处方会出 3 条一模一样的「重复用药」提示。** 医生看到三条相同提示的第一反应是「系统又抽风了」，然后养成全部跳过的习惯。一旦医生养成跳过习惯，那些真正重要的提示也一起失效了——**这是所有用药审核系统最终被关掉的真实原因，不是提示太多，是重复提示训练出了肌肉记忆。**
>
> 反过来，如果一条规则涉及 3 个药而只命中 1 个，就只产生 1 条提示并写明是哪个药。所以唯一键是 `rule_code + drug_code` 而不是 `rule_code`。

**`check_result` 的映射：**

| 命中最高等级 | `check_result` | `block_flag` |
|---|---|---|
| 无命中 | `PASS` | false |
| `INFO` / `WARN` | `WARN` | false |
| `SEVERE` | `WARN` | false |
| `BLOCK` | `BLOCK` | true |
| 规则集未加载 | `DEGRADED` | false |

> **`SEVERE` 映射到 `WARN` 而不是 `BLOCK`，这一点必须写死。** `BLOCK` 只在国家明令禁止的场景置位（如明确的配伍禁忌、妊娠禁忌），其余一律不拦截。原因：一旦系统可以拦截处方，医生就必须为每一条误报付出「绕过拦截」的操作成本，而误报是必然存在的（规则是人写的）。本院实践原则是**只提示不拦截，除非法律强制**。

#### 3.4.3 抗菌药物分级判定

```text
判定链：药品分级 → 医师处方权级别 → 是否允许开立
```

| 药品分级 | 要求医师等级 | 是否需审批 | 本院特例 |
|---|---|---|---|
| `NON_RESTRICTED`（非限制使用） | `RESIDENT` 及以上 | 否 | 无 |
| `RESTRICTED`（限制使用） | `ATTENDING` 及以上 | 否 | 无 |
| `SPECIAL`（特殊使用） | `SENIOR` 及以上 | **是，需抗菌药物管理小组会诊审批** | 见下 |

**医师等级来源**：`GET /internal/v1/staff/{id}/practice-check`（U-04），返回该医师的执业资格与抗菌药物处方权级别。**本子模块不存医师等级，只存规则要求的最低等级**，判定在 M18-05 执行时实时取。

**本院特例的明确结论（不留白）：**

| 场景 | 结论 | 理由 |
|---|---|---|
| A 院区主任医师 | **不设特例**，同样受 `SPECIAL` 需审批约束 | 抗菌药物分级是医疗质量红线，不因院区而异 |
| 特需门诊 | **不设特例**，同样受约束 | 特需是服务形式差异，不是医疗权限差异 |
| 急诊夜间（20:00—次日 08:00） | **允许先用后补**：可先开立 `SPECIAL`，但必须在 24 小时内补办会诊审批 | 眼科急诊（如眼内炎）需要立即用药，等审批会延误治疗；但补办时限必须硬性约束 |
| 手术室术中用药 | 由主刀医师（`SENIOR` 及以上）开立，视同已审批 | 术中用药属手术方案组成部分，术前已完成讨论 |

> **「先用后补」必须有硬性时限与未补办的后置处理。** 若只是允许先用，24 小时后没人补办，这条记录就永久缺失审批。所以规则里带 `approval_due_at` 字段，超过时限未补办的记录进入 P01 的「待补办审批」清单，并按日推送给药学部。

**`DR_OPHTH_001` 散瞳药与闭角型青光眼禁忌**

| 条件引用的 P-08 字段 | `drug_code`、`route`、`diagnosis_codes`（**全部已在请求体中**） |
| 提示语 | 「{drug_name} 为散瞳药，患者诊断 {diagnosis_name}（闭角型青光眼），散瞳可诱发急性闭角型青光眼发作，属禁忌。建议改用不散瞳的检查方式或先降眼压处理。」 |

| 已核实 | 所需字段全部在 P-08 请求体中，**规则可命中** |

**`DR_OPHTH_002` 抗 VEGF 与抗凝药联合风险**

| 项 | 内容 |
|---|---|
| 触发条件 | 药品属于抗 VEGF 类药物（雷珠单抗/康柏西普/阿柏西普/法瑞西单抗）**且** 患者同时使用抗凝或抗血小板药物（华法林/利伐沙班/阿哌沙班/阿司匹林/氯吡格雷） |
| 条件引用的 P-08 字段 | `drug_code`（两个药都在 items 中时可交叉判定） |
| 提示语 | 「患者同时使用 {conflict_drug_name}（抗凝/抗血小板）与 {drug_name}（抗 VEGF），玻璃体腔注射后出血风险升高。建议注射前评估 INR，必要时与内科协商调整方案。」 |
| 处置建议 | 评估 INR；若在治疗窗内可继续注射并加压；异常则延后注射 |
| 严重等级 | `SEVERE`（风险升高但非绝对禁忌，**不拦截**） |
| 已核实 | 双药同时在 items 中即可判定，**规则可命中** |

**`DR_OPHTH_003` 糖皮质激素滴眼液长期使用与高眼压**

| 项 | 内容 |
|---|---|
| 触发条件（完整版，**当前不可实现**） | 激素类滴眼液 **且** 用药天数 > 14 **且** 基线眼压 > 21 mmHg **或** 既往青光眼史 |
| 触发条件（当前实现版） | 激素类滴眼液（地塞米松/泼尼松龙/氟米龙）**且** `days` > 14 **且** 诊断包含既往青光眼史（`H40.001`/`H40.002`/`Z98.8101`） |
| 条件引用的 P-08 字段 | `drug_code`、`days`、`diagnosis_codes`（**已全部在请求体中**） |
| 缺少的字段 | **`iop`（基线眼压）不在 P-08 请求体中** |
| 提示语 | 「{drug_name} 已连续使用 {days} 天，患者有青光眼相关病史，长期使用糖皮质激素滴眼液可致眼压升高。建议每 2 周监测眼压，疗程超过 4 周需眼科复查。」 |
| 处置建议 | 监测眼压；必要时换用非激素类抗炎药 |
| 严重等级 | `SEVERE`（不拦截） |
| **已知限制** | 缺少眼压条件，只能靠「既往青光眼史」定位高风险人群，**会漏掉没有青光眼诊断但眼压偏高、正在用激素的患者**。这是当前实现下的漏检，非设计缺陷 |

> **这条规则的退化是本子模块必须写明的真实约束。** 完整版需要「基线眼压」，而 P-08 的调用方（M07-05 开方页面）在开方瞬间并不持有眼压值，眼压存在 M10 视光档案与 M12 检查结果里，为它加一次跨模块调用会把 P-08 的 300ms 预算打穿。所以只能退化成「激素 + 天数 + 既往史」。
>
> 退化的代价是**两类错误同时存在**：一是漏检（有高眼压风险但无青光眼诊断的患者不触发），二是噪声（有青光眼史但在安全监测下的患者也会触发）。后者可以通过「已在使用降眼压药」这个条件部分抑制，但那又需要 P-08 传更多字段。**这个取舍已经作为已知风险登记在附录 C。**

**`DR_OPHTH_004` OK 镜护理液与角膜损伤**

| 项 | 内容 |
|---|---|
| 触发条件 | 药品属于硬性接触镜护理液类（含过氧化氢/双氧水成分）**且** 诊断包含角膜损伤相关（`H18.*` 角膜病变、`H16.*` 角膜炎） |
| 条件引用的 P-08 字段 | `drug_code`、`diagnosis_codes` |
| 提示语 | 「患者存在角膜损伤（{diagnosis_name}），使用 {drug_name} 等硬镜护理液可能因过氧化氢残留加重角膜刺激。建议暂停配戴并改用无防腐剂人工泪液。」 |
| 处置建议 | 暂停配戴 OK 镜；复查角膜荧光素染色 |
| 严重等级 | `WARN`（提示性，不拦截） |
| 已核实 | 所需字段全部在 P-08 请求体中，**规则可命中** |

### 3.5 单据模型

| 单据 | 编号规则 | 何处生成 |
|---|---|---|
| 规则编码 | `DR_{类别}_{序号3位}`，如 `DR_INTER_001` | 手动指定类别前缀 + 序号流水 |
| 规则版本集编号 | `KBS + yyyyMMdd + 3位流水`，如 `KBS20261021001` | Redis `INCR m18:code:kbs:20261021` |
| 规则版本集标识 | `{yyyyMMdd}_{3位流水}`，如 `20261021_001` | 由编号推导，是 P-08 返回的 `rule_version_set` |
| 路径编码 | `CP_{专科}_{疾病}_{序号3位}`，如 `CP_REFRACT_CATARACT_001` | 手动指定 |
| 路径入径号 | `CPE + yyyyMMdd + 6位流水`，如 `CPE20261021000001` | Redis `INCR m18:code:cpe:20261021` |
| 知识条目编码 | `KB_{域}_{序号4位}`，如 `KB_OPHTH_0001` | 手动指定 |
| 热重载流水号 | `RLD + yyyyMMddHHmmss + 3位` | 时间戳 + 实例序号 |

> **单号一律走 Redis `INCR`，禁止用数据库序列拼日期。** 数据库序列在跨日时会跳号（`nextval` 在事务回滚后不复用），拼出的日期与业务日期可能不一致；Redis `INCR` 的 key 带日期，天然按日重置且并发安全。

### 4.2 分区策略

| 表 | 分区方式 | 理由 |
|---|---|---|
| `m18_kb_path_entry` | `PARTITION BY RANGE (entered_at)` 按年 + DEFAULT 分区 | 保留期迁移需要（入径记录 3 年后迁归档库），不是数据量需要 |
| 其余 10 张业务表 | 不分区 | 年增量均小于 10 万行，分区只增加复杂度 |

> **分区表的一个副作用必须说清**：`m18_kb_path_entry` 是分区表，PostgreSQL 要求分区表的主键必须包含分区键，所以主键是 `(id, entered_at)`，进而共享规范 §2.5 要求的 `(path_code, patient_id, encounter_id)` 唯一约束**无法用 UNIQUE 实现**。替代方案是 Redis 幂等键（`m18:idem:path-entry:{path_code}:{patient_id}:{encounter_id}`，TTL 24h）+ 每日巡检 SQL（数据结构文档附录 B.2）。这是一个真实的能力降级，已作为已知风险登记在附录 C。

| 列表区 | 规则编码、名称、类型、等级、状态、版本、发布人、发布时间 |
| 详情抽屉 | 触发条件（可视化条件树）、提示语、处置建议、循证依据、变更历史 |
| 操作区 | 新建草稿、编辑草稿、提交审核、审核通过/驳回、发布、停用、查看历史版本 |

**规则条件树编辑器（本页核心）：**

规则条件以可视化条件树编辑，不要求用户手写 JSON。支持：

| 节点类型 | 说明 |
|---|---|
| AND / OR | 逻辑组合，可嵌套 |
| NOT | 取反 |
| COMPARE | 字段 + 运算符 + 值，字段从白名单下拉选择（见附录 A.1.1） |

> **字段白名单必须做进下拉，不能让用户自由输入。** 用户若填了一个 P-08 不传的字段（比如 `iop`），规则保存成功但永远不命中，而界面上看不出任何异常。把白名单做成下拉，从源头堵住这类静默失效。

**发布流程的界面约束：**

| 步骤 | 界面行为 |
|---|---|
| 新建 | 只能建草稿，状态强制 `DRAFT` |
| 提交审核 | 草稿内容冻结，不可再编辑；必须填写变更说明 |
| 审核 | 审核人必须是药学部主任权限；不能是自己提交的规则（**自己审自己一律拒绝**） |
| 发布 | 发布时自动生成新版本集，把全部 PUBLISHED 规则重新挂到新集 |
| 发布确认 | 弹出确认框，明确显示「本次发布将影响 N 条规则，其中新增 X 条、修改 Y 条、停用 Z 条」 |

> **「自己审自己」必须在服务端拒绝，不能只在界面上禁按钮。** 界面上隐藏按钮只能挡住正常操作路径，直接调接口仍可绕过。这条校验放在 §8.3 的业务规则里。

### 5.6 P05 临床路径管理

**页面路径**：`/m18/kb/path/list`

**页面目标**：临床路径定义的创建与版本管理。

| 区块 | 内容 |
|---|---|
| 路径列表 | 路径编码、名称、专科、版本、状态、入径率（近 3 月）、变异率 |
| 路径详情 | 基本信息、入径标准、标准住院日、节点清单、版本历史 |
| 入径标准编辑 | 诊断包含/排除、年龄区间、术式、排除标记（结构见数据结构附录 D.3） |
| 操作 | 新建、编辑草稿、审核、发布、下线 |

**入径标准编辑区的强制校验：**

| 校验 | 说明 |
|---|---|
| 诊断包含不得为空 | 否则所有患者都符合入径标准，入径率会变成 100% |
| 排除条件与包含条件不得矛盾 | 同一诊断不能既包含又排除 |
| 年龄区间必须合理 | `age_min <= age_max`，且在 0~120 之间 |
| 修改已发布路径必须新建版本 | 直接改会让历史入径记录失去依据 |

> **「诊断包含不得为空」这条校验看着琐碎，实际是入径率口径的第一道闸门。** 一条路径如果没有诊断限制，那么全院所有住院患者都算「适用患者」，入径率的分母瞬间变成住院总数——也就是 §3.4.1 里那个 240。所以入径标准不是可选项，是入径率口径的一部分。

### 5.7 P06 路径节点配置

**页面路径**：`/m18/kb/path/{path_code}/nodes`

**页面目标**：配置路径的内部节点。用可视化流程顺序展示，而非简单的列表——因为节点有先后依赖关系。

| 区块 | 内容 |
|---|---|
| 节点序列 | 按 `seq_no` 排序的节点卡片，显示节点类型、相对天数、是否必需 |

| 预演 | 输入一个虚拟入径日，预览各节点的计划完成日期 |

**节点类型与默认相对天数（本院白内障路径示例）：**

| 序号 | 节点 | 类型 | 相对天数 | 应完成期限 | 必需 |
|---|---|---|---|---|---|
| 1 | 入院评估 | `ADMISSION` | 0 | 1 天 | 是 |
| 2 | 术前检查 | `EXAM` | 1 | 2 天 | 是 |
| 3 | 手术 | `SURGERY` | 2 | 1 天 | 是 |
| 4 | 术后第一日查房 | `REVIEW` | 3 | 1 天 | 是 |
| 5 | 出院评估 | `DISCHARGE` | 4 | 1 天 | 是 |
| 6 | 术后一周复查 | `REVIEW` | 9 | 2 天 | 否 |

> **「术后一周复查」设为非必需是有依据的。** 本院实际执行中约 12% 的患者在外地无法按期回院，改为在当地医院复查后回传结果。若把它设为必需节点，这些患者永远无法完成路径，完成率会被系统性低估。**非必需节点必须配跳过条件**（数据结构 CHECK `ck_m18_kb_path_node_skip_condition` 强制），否则「非必需」会变成「可以不解释地跳过」。

```json
  "data": {
    "path_code": "CP_REFRACT_CATARACT_001",
    "period": "2026-10",
    "surgery_total": 240,
    "applicable_total": 200,
    "entered_total": 168,
    "entry_rate": 0.840000,
    "deviation_total": 22,
    "deviation_rate": 0.130952,
    "completed_total": 160,
    "completion_rate": 0.952381,
    "exited_total": 8,
    "exit_rate": 0.047619,
    "excluded_total": 40,
    "excluded_breakdown": [
      {"reason": "diagnosis_exclude", "count": 24},
      {"reason": "age_out_of_range", "count": 6},
      {"reason": "exclude_flags", "count": 10}
    ],
    "degraded": false,
    "degraded_sources": [],
    "data_quality": "DAILY",
    "as_of": "2026-11-07T03:30:00+08:00"
  },
  "trace_id": "a1b2c3d4e5f6a7b8",
  "server_time": "2026-11-07T12:00:00+08:00"
}
```

**口径说明：**

| 指标 | 公式 | 本例取值 |
|---|---|---|
| 入径率 | 入径患者数 / 适用患者数 = `entered_total / applicable_total` | 168 / 200 = 84.00% |
| 变异率 | 变异入径患者数 / 入径患者数 = `deviation_total / entered_total` | 22 / 168 = 13.10% |
| 完成率 | 完成的路径数 / 入径的路径数 = `completed_total / entered_total` | 160 / 168 = 95.24% |
| 出径率 | 出径患者数 / 入径患者数 = `exited_total / entered_total` | 8 / 168 = 4.76% |

> **入径率的分母是 200（适用患者数），不是 240（手术总数）。** 240 台手术里有 40 台不符合入径标准：24 台有合并症（命中 `diagnosis_exclude` 里的糖尿病 `E11.900` 或高血压 `I10.001`）、6 台年龄超出 18~85 区间、10 台属于急诊或多科室联合手术（命中 `exclude_flags`）。
>
> **这 40 台本来就不该入径，把它们放进分母等于要求医生去做一件按标准不该做的事。** 用 240 算出来的 70.00% 会让科室背上「入径率不达标」的考核压力，逼着他们去把不该入径的患者也拉进路径——那是把指标做上去、把诊疗做坏。`excluded_total` 与 `excluded_breakdown` 必须一起返回，就是为了让这个差额可解释、可核对。
>
> **完成率 + 出径率 = 100%** 是本接口的闭合校验项：160/168 + 8/168 = 168/168。若不闭合，说明有入径记录既没完成也没退出，属于状态机漏口。

**错误码：** `1808021`

### 6.5 Service 层核心逻辑示例

```python
"""M18-08 临床知识库与路径 —— Service 层核心逻辑。

三个关键方法：规则发布（生成版本集）、热重载（双缓冲原子切换）、入径率统计。
"""

from __future__ import annotations

import hashlib
import json
import logging
from datetime import date, datetime
from decimal import Decimal

from sqlalchemy import select, update
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.errors import BizError
from app.core.redis import RedisLock
from app.models.m18.kb import MedRule, PathEntry, RuleVersionSet
from app.services.m18.rule_engine import RuleSet, RuleSetHolder

logger = logging.getLogger(__name__)


class KbService:
    def __init__(self, session: AsyncSession, holder: RuleSetHolder) -> None:
        self.session = session
        self.holder = holder

    async def publish_rules(self, req, operator_id: int):
        """发布规则：建版本集 -> 全量重挂 -> 提交 -> 触发重载。"""
        if not req.rule_ids:
            raise BizError("1808006", "发布批次为空")

        async with RedisLock("m18:kb:publish", ttl=60) as acquired:
            if not acquired:
                raise BizError("1808012", "有正在进行的版本集加载")

            stmt = select(MedRule).where(MedRule.id.in_(req.rule_ids))
            rules = (await self.session.scalars(stmt)).all()
            pending = [r for r in rules if r.status != "PUBLISHED"]
            if pending:
                raise BizError("1808002", "存在未审核通过的规则")

            all_rules = (
                await self.session.scalars(
                    select(MedRule).where(MedRule.status == "PUBLISHED")
                )
            ).all()
            rule_count = len(all_rules)
            checksum = self._checksum(all_rules)

            version_set = await self._create_version_set(
                rule_count=rule_count,
                checksum=checksum,
                change_summary=req.change_summary,
                operator_id=operator_id,
            )

            await self.session.execute(
                update(MedRule)
                .where(MedRule.status == "PUBLISHED")
                .values(version_set_id=version_set.id, updated_at=datetime.now())
            )
            await self.session.commit()

        if req.trigger_reload:
            await self.reload_rules(operator_id, "API_CALL")
        return self._to_publish_resp(version_set)

    @staticmethod
    def _checksum(rules: list[MedRule]) -> str:
        """规则集校验和：按 rule_code 排序后对内容取 SHA-256，用于验证各实例加载一致。"""
        payload = sorted(
            (
                {
                    "rule_code": r.rule_code,
                    "rule_version": r.rule_version,
                    "rule_type": r.rule_type,
                    "rule_condition": r.rule_condition,
                    "alert_level": r.alert_level,
                    "severity": r.severity,
                }
                for r in rules
            ),
            key=lambda x: (x["rule_code"], x["rule_version"]),
        )
        raw = json.dumps(payload, sort_keys=True, ensure_ascii=False).encode("utf-8")
        return hashlib.sha256(raw).hexdigest()

    async def reload_rules(self, operator_id: int, trigger_source: str):
        """热重载：构建新集，就绪后原子切换。失败保留旧集。"""
        old_set = self.holder.snapshot()
        old_version = old_set.rule_version_set if old_set else ""
        started = datetime.now()

        try:
            new_set = await self._build_ruleset()
        except Exception as exc:
            logger.exception("规则集构建失败，保留旧集 version_set=%s", old_version)
            await self._write_reload_log(
                old_version=old_version,
                new_version=old_version,
                load_status="FAILED",
                degraded=True,
                fail_reason=str(exc)[:512],
                started_at=started,
            )
            raise BizError(
                "1808015",
                "热重载失败，继续使用旧规则集 %s" % old_version,
                degraded=True,
                degraded_sources=[{"source": "RULE_LOAD", "reason": str(exc)[:200]}],
            ) from exc

        self.holder.swap(new_set)
        duration_ms = int((datetime.now() - started).total_seconds() * 1000)
        await self._write_reload_log(
            old_version=old_version,
            new_version=new_set.rule_version_set,
            load_status="SUCCESS",
            degraded=False,
            fail_reason="",
            started_at=started,
        )
        logger.info(
            "规则集切换 %s -> %s, %d 条, 耗时 %dms",
            old_version,
            new_set.rule_version_set,
            new_set.rule_count,
            duration_ms,
        )
        return new_set

    async def path_entry_statistics(
        self,
        path_code: str,
        date_from: date,
        date_to: date,
        dept_id: int | None,
        operator_id: int,
    ):
        """入径率统计：分母只算适用患者数。"""
        applicable = await self._count_applicable(path_code, date_from, date_to, dept_id)
        entered = await self._count_entered(path_code, date_from, date_to, dept_id)
        deviated = await self._count_deviated(path_code, date_from, date_to, dept_id)
        completed = await self._count_completed(path_code, date_from, date_to, dept_id)
        exited = await self._count_exited(path_code, date_from, date_to, dept_id)

        if completed + exited != entered:
            logger.warning(
                "入径状态未闭合 path_code=%s 入径=%d 完成=%d 出径=%d",
                path_code,
                entered,
                completed,
                exited,
            )

        return {
            "applicable_total": applicable,
            "entered_total": entered,
            "deviation_total": deviated,
            "completed_total": completed,
            "exited_total": exited,
            "entry_rate": self._ratio(entered, applicable),
            "deviation_rate": self._ratio(deviated, entered),
            "completion_rate": self._ratio(completed, entered),
            "exit_rate": self._ratio(exited, entered),
        }

    @staticmethod
    def _ratio(numerator: int, denominator: int) -> Decimal | None:
        """分母为 0 返回 None，绝不返回 0。

        「没有适用患者」与「适用患者里一个都没入径」是两种完全不同的事实，
        前者不该出现在报表里，后者才是真正的问题。返回 0 会让两者无法区分。
        """
        if not denominator:
            return None
        return (Decimal(numerator) / Decimal(denominator)).quantize(Decimal("0.000001"))
```

> **`_ratio` 返回 `None` 而不是 `0` 是这个子模块贯穿始终的口径纪律。** 报表前端遇到 `null` 显示 `—`，遇到 `0` 显示 `0.00%`。若把「分母为 0」也返回 `0.00%`，科室会看到「入径率 0%，严重不达标」而实际上这个月根本没有适用患者——这类假警报几次之后，整个报表就没人看了。

## 7. 缓存与异步任务设计

### 7.1 为什么要谈缓存：本子模块的缓存对象是「规则集」而非常规数据

本子模块的绝大多数读操作都是直接查库（规则表 24,000 行、路径 24 行、DRG 权重 360 行，全部走索引），**没有引入 Redis 缓存的必要**。唯一需要特殊处理的是「规则集」——但它要的不是缓存，是**常驻内存**。

两者的区别决定了很多设计细节：

| 维度 | Redis 缓存 | 常驻内存规则集 |
|---|---|---|
| 命中失败怎么办 | 回源查库 | **不存在未命中**，内存里永远是完整规则集 |
| 失效方式 | TTL 到期或主动删除 | 只有重载才换，且是整体换 |
| 数据形态 | 序列化后的字节 | 已解析的对象树与倒排索引 |
| 容量上限 | Redis 实例内存 | 进程堆内存 40MB 预算 |
| 多实例一致性 | 共用同一份 | **各实例独立加载，用 checksum 核对** |

> **为什么不把规则集放 Redis？** 规则求值涉及患者维度（年龄、性别、孕产、肾功能）与眼科专科条件（诊断编码集合交叠），这是**计算**不是查表。放 Redis 只能存序列化后的结构，每次匹配都要反序列化 + 网络往返，300ms 的 P-08 预算经不起；而常驻内存的已编译对象树匹配 5 个药品只需 15ms。Redis 在这里是负优化。

### 7.2 Redis Key 设计

| Key 模式 | 类型 | TTL | 容量估算 | 用途 |
|---|---|---|---|---|
| `m18:kb:reload:lock` | string | 60s | 1 个 | 热重载互斥锁，防止多实例同时重载 |
| `m18:kb:publish:lock` | string | 60s | 1 个 | 发布互斥锁，防止并发发布产生两个版本集 |
| `m18:idem:path-entry:{path_code}:{patient_id}:{encounter_id}` | string | 86400s | 约 3,000 个 | 入径幂等键，兜底分区表无法建 UNIQUE 的缺口 |
| `m18:code:CPE:{yyyyMMdd}` | string | 172800s | 2 个 | 入径号流水，`INCR` 生成 |
| `m18:code:KBS:{yyyyMMdd}` | string | 172800s | 2 个 | 版本集号流水 |
| `m18:kb:reload:progress:{instance_id}` | hash | 600s | 3 个 | 各实例加载进度，供 P-13 轮询 |
| `m18:kb:hit:today:{rule_code}` | string | 按日过期 | 约 8,000 个 | 当日命中计数增量，次日凌晨落库 |

> **`m18:kb:reload:progress` 用 Hash 而不是每实例一个 String**：一次重载要查 3 个实例的进度，Hash 可以一次 `HMGET` 全部取回，而 3 个 String 需要 3 次往返。在 2000ms 的 P-13 预算里这不算大问题，但配合重载进度轮询（前端 3 秒一次）会产生可观的请求量。
>
> **`m18:idem:path-entry` 的 TTL 是 86400s 而不是更短**：入径判定可能在一天内的多个时点被触发（入院、术前、手术当日），同一个患者同一次就诊必须是同一个入径实例。TTL 太短会让「已入径」的判断在某次触发时失效，产生第二个入径记录——而分区表建不了跨分区的 UNIQUE 约束，这种重复只能靠应用层兜。

### 7.3 Celery 异步任务清单

| 任务名 | 触发方式 | 执行周期 | 超时 | 失败重试 | 用途 |
|---|---|---|---|---|---|
| `m18.kb.aggregate_hit_stat` | APScheduler 每日 | 每日 03:30 | 600s | 3 次，间隔 300s | 把 Redis 当日命中增量聚合进 `m18_kb_hit_stat` |
| `m18.kb.detect_anomalies` | 依赖上一步 | 每日 04:00 | 300s | 2 次，间隔 120s | 生成误报/死规则/全忽略三类清单 |
| `m18.kb.sync_drg_weight` | 手工或年度 | 年度 | 1800s | 1 次 | 医保局权重文件导入 |
| `m18.kb.verify_version_set` | APScheduler 每日 | 每日 05:00 | 300s | 2 次 | 核对各实例 checksum 与数据库中版本集一致 |
| `m18.kb.import_rules` | 手工 | 按需 | 3600s | 0 次 | 批量导入规则初始数据（约 8,000 条） |
| `m18.kb.clean_reload_log` | APScheduler 每月 | 每月 1 日 02:00 | 600s | 1 次 | 清理 90 天前的重载日志 |

```python
"""M18-08 异步任务示例。"""

from __future__ import annotations

import logging
from datetime import date, datetime, timedelta
from decimal import Decimal

from celery import shared_task
from sqlalchemy import select

from app.core.db import SessionLocal
from app.models.m18.kb import HitStat, MedRule

logger = logging.getLogger(__name__)


@shared_task(name="m18.kb.aggregate_hit_stat", bind=True, max_retries=3)
def aggregate_hit_stat(self, stat_date: str | None = None) -> dict:
    """把 Redis 当日命中增量聚合进 m18_kb_hit_stat。

    口径：
    - trigger_count：该规则当日被触发的次数（按 rule_code + drug_code 去重，一条规则命中多个药品只算一次）
    - ack_count / ignore_count：医生采纳与忽略的次数
    - hit_rate = ignore_count / trigger_count，trigger_count 为 0 时存 NULL
    """
    target = date.fromisoformat(stat_date) if stat_date else date.today() - timedelta(days=1)
    aggregated = 0

    with SessionLocal() as session:
        rules = session.scalars(select(MedRule).where(MedRule.status == "PUBLISHED")).all()
        for rule in rules:
            redis_key = "m18:kb:hit:today:%s" % rule.rule_code
            raw = _read_and_reset(redis_key)
            trigger = int(raw.get("trigger", 0))
            ack = int(raw.get("ack", 0))
            ignore = int(raw.get("ignore", 0))

            hit_rate = None
            if trigger > 0:
                hit_rate = (Decimal(ignore) / Decimal(trigger)).quantize(Decimal("0.000001"))

            stmt = select(HitStat).where(
                HitStat.stat_date == target,
                HitStat.rule_code == rule.rule_code,
                HitStat.rule_version == rule.rule_version,
            )
            stat = session.scalars(stmt).first()
            if stat is None:
                stat = HitStat(stat_date=target, rule_id=rule.id, rule_code=rule.rule_code,
                               rule_version=rule.rule_version, rule_type=rule.rule_type)
                session.add(stat)
            stat.trigger_count = trigger
            stat.ack_count = ack
            stat.ignore_count = ignore
            stat.hit_rate = hit_rate
            aggregated += 1

        session.commit()

    logger.info("规则命中统计聚合完成 date=%s rules=%d", target, aggregated)
    return {"stat_date": str(target), "rules": aggregated}


@shared_task(name="m18.kb.detect_anomalies")
def detect_anomalies() -> dict:
    """生成三类异常清单。阈值来自 m18_kb_config，不写死在代码里。"""
    from app.services.m18.kb_service import KbService

    with SessionLocal() as session:
        svc = KbService(session, holder=None)
        result = svc.detect_anomalies(
            false_positive_threshold=Decimal("0.80"),
            dead_rule_days=90,
        )
    logger.info(
        "规则异常检测完成 误报=%d 死规则=%d 全忽略=%d",
        len(result["false_positive"]),
        len(result["dead_rule"]),
        len(result["all_ignored"]),
    )
    return result


def _read_and_reset(key: str) -> dict:
    """读取并清零当日计数。用 MULTI 保证读写原子，避免聚合瞬间的增量丢失。"""
    from app.core.redis import redis_client

    pipe = redis_client.pipeline(transaction=True)
    pipe.hgetall(key)
    pipe.delete(key)
    values, _ = pipe.execute()
    return {k: v for k, v in values.items()} if values else {}
```

> **`_read_and_reset` 用 `MULTI` 事务而不是先读后删。** 若分两步执行，两条命令之间的命中增量会写进一个已被删除的 key，当天的这部分命中永久丢失。而命中统计恰恰是用来判断规则该不该保留的依据——数据丢一天，误报率与死规则的判断就会失真。

|---|---|---|---|

```python
"""定时任务注册。"""

from apscheduler.schedulers.asyncio import AsyncIOScheduler
from apscheduler.triggers.cron import CronTrigger

from app.tasks.m18.kb import aggregate_hit_stat, detect_anomalies


def register_kb_jobs(scheduler: AsyncIOScheduler) -> None:
    scheduler.add_job(
        aggregate_hit_stat.delay,
        CronTrigger(hour=3, minute=30, timezone="Asia/Shanghai"),
        id="kb_hit_stat_daily",
        replace_existing=True,
        max_instances=1,
        misfire_grace_time=1800,
    )
    scheduler.add_job(
        detect_anomalies.delay,
        CronTrigger(hour=4, minute=0, timezone="Asia/Shanghai"),
        id="kb_detect_anomalies",
        replace_existing=True,
        max_instances=1,
        misfire_grace_time=1800,
    )
```

> **`max_instances=1` 必须显式设置。** APScheduler 默认允许同一任务并发执行，一旦某天的聚合因为数据量大跑超过 24 小时，第二天又会起一个实例，两个实例同时往 `m18_kb_hit_stat` 写同一批行会造成重复累加。`max_instances=1` 让第二个实例被跳过而不是排队——**跳过可以接受，重复累加不可接受**，因为累加后没有任何办法区分哪部分是多算的。

## 8. 业务规则与校验

### 8.1 编码规则

| 对象 | 规则 | 示例 | 生成方式 |
|---|---|---|---|
| 用药规则 | `DR_{类别}_{序号3位}` | `DR_INTER_001` | 保存草稿时由用户填写类别，序号系统分配 |
| 临床路径 | `CP_{专科}_{疾病}_{序号3位}` | `CP_REFRACT_CATARACT_001` | 同上 |
| 路径入径号 | `CPE + yyyyMMdd + 6位流水` | `CPE20261021000001` | Redis `INCR m18:code:CPE:{yyyyMMdd}` |
| 知识条目 | `KB_{域}_{序号4位}` | `KB_OPHTH_0001` | Redis `INCR` |
| 版本集号 | `KBS + yyyyMMdd + 3位流水` | `KBS20261107001` | Redis `INCR m18:code:KBS:{yyyyMMdd}` |
| 规则版本集号 | `{yyyyMMdd}_{3位流水}` | `20261107_001` | 由版本集号派生 |

> **入径号的日期前缀必须取入径日，不取生成日。** 入径号是分区裁剪的依据之一，若用生成时间而实际入径时间在跨年边界上（12 月 31 日 23:59 生成、次日 00:01 入径），号码会落进上一年的分区前缀而记录落在下一年分区，按号段查分区会永远查不到。

### 8.2 唯一性约束

| 对象 | 唯一键 | 落地方式 | 违反时 |
|---|---|---|---|
| 用药规则 | `(rule_code, rule_version)` | 数据库 UNIQUE | `1808001` |
| 临床路径 | `(path_code, path_version)` | 数据库 UNIQUE | `1808016` |
| 路径节点 | `(path_id, node_code)`、`(path_id, seq_no)` | 数据库 UNIQUE | `1808017` |
| 入径记录 | `(entry_no, entered_at)` | 数据库 UNIQUE | — |
| 入径实例 | `(path_code, patient_id, encounter_id)` | **Redis 幂等键 + 每日巡检** | `1808022` |
| DRG 权重 | `(drg_code, version)` | 数据库 UNIQUE | `1808029` |
| 版本集 | `version_set_no`、`rule_version_set` | 数据库 UNIQUE | — |

> **入径实例的唯一性为什么不能靠数据库？** `m18_kb_path_entry` 按 `entered_at` 年分区，PostgreSQL 要求分区表的主键与唯一约束必须包含分区键，因此 `(path_code, patient_id, encounter_id)` 无法建 UNIQUE。这不是设计选的，是数据库强制的。兜底方案是写前先 `SET NX` 抢占 Redis 幂等键，并在附录 B.2 提供每日巡检 SQL 发现已有重复。**这个缺口必须写在文档里**，否则后来的人会以为约束已经保护了。

### 8.3 状态流转规则

**规则状态流转：**

| 当前状态 | 允许操作 | 目标状态 | 约束 |
|---|---|---|---|
| `DRAFT` | 提交审核 | `IN_REVIEW` | 必填字段齐全 |
| `IN_REVIEW` | 审核通过 | `PUBLISHED` | 审核人 ≠ 创建人 |
| `IN_REVIEW` | 审核驳回 | `DRAFT` | 审核意见必填 |
| `PUBLISHED` | 发布新版本 | `SUPERSEDED` | 同 `rule_code` 新版本发布时自动置旧版 |
| `PUBLISHED` | 停用 | `DISABLED` | 停用原因必填 |
| `SUPERSEDED` | — | 终态 | 不回溯重算 |
| `DISABLED` | 重新启用 | `PUBLISHED` | 需重新审核 |

**路径入径状态流转：**

| 当前状态 | 允许操作 | 目标状态 | 约束 |
|---|---|---|---|
| `ENTERED` | 开始执行 | `IN_PROGRESS` | — |
| `IN_PROGRESS` | 完成全部节点 | `COMPLETED` | 所有必需节点已完成 |
| `IN_PROGRESS` | 发生变异 | `DEVIATED` | 变异原因必填 |
| `DEVIATED` | 恢复执行 | `IN_PROGRESS` | — |
| `DEVIATED` | 完成 | `COMPLETED` | 所有必需节点已完成 |
| 任意非终态 | 退出路径 | `EXITED` | 退出原因与退出类型必填 |
| `COMPLETED` / `EXITED` | — | 终态 | 不可再变更节点 |

> **`COMPLETED` 与 `EXITED` 之和必须等于入径总数**，这是完成率与出径率的闭合校验。若不闭合，说明有入径卡在 `IN_PROGRESS` 或 `DEVIATED` 超期未处理，需在附录 B 的巡检里报出来。

### 8.5 计算规则

| 指标 | 公式 | 分母为 0 时 | 说明 |
|---|---|---|---|
| 入径率 | `entered_total / applicable_total` | `NULL` | 分母是适用患者数，不是住院总数 |
| 变异率 | `deviation_total / entered_total` | `NULL` | 按入径实例计数 |
| 完成率 | `completed_total / entered_total` | `NULL` | 与出径率之和为 100% |
| 出径率 | `exited_total / entered_total` | `NULL` | — |
| 规则加权命中率 | `SUM(ignore_count) / SUM(trigger_count)` | `NULL` | 期间汇总后重算，不取日命中率的平均 |
| 规则匹配度 | 按 `rule_code` 去重计数 | — | 一条规则命中多药品只算一次 |

> **期间汇总必须重算，不能对日比例取平均。** 这一点已由 API-11 的算例说明：三个日命中率 64.86%、66.67%、96.15% 直接平均得 75.89%，而按触发次数加权得 68.30%。差 7.6 个百分点，足以让同一条规则在月度报表与周度报表里得出相反的结论。

### 8.6 引用完整性规则

| 引用关系 | 规则 | 落地方式 |
|---|---|---|
| 规则 → 药品 | 药品编码必须存在于 M01 主数据 | 保存时校验，M01 不可用时仅告警不阻断 |
| 规则 → 诊断 | 诊断编码必须存在于 M01 主数据 | 同上 |
| 路径 → 诊断 | 同上 | 同上 |
| 入径 → 路径 | 路径必须已发布且版本一致 | 数据库逻辑引用 + 应用校验 |
| 变异 → 入径 | 入径必须存在且非终态 | 应用校验 |

> **主数据不可用时为什么只告警不阻断？** 若 M01 短时不可用就禁止保存规则草稿，知识库维护工作会被主数据服务的可用性绑架。而规则的执行时刻（P-08）才是真正需要主数据的地方，那里 M01 不可用会走降级。草稿阶段允许引用尚不存在于主数据的编码，发布时再严格校验。

### 8.7 并发控制

| 场景 | 冲突 | 控制方式 |
|---|---|---|
| 同时发布规则 | 生成两个版本集 | Redis 锁 `m18:kb:publish:lock`，TTL 60s |
| 同时热重载 | 重复加载 | Redis 锁 `m18:kb:reload:lock`，TTL 60s |
| 同一规则并发审核 | 状态被覆盖 | 数据库乐观锁 `WHERE status = 'IN_REVIEW'`，影响行数 0 则报 `1808002` |
| 同一患者并发入径 | 重复入径记录 | Redis `SET NX` 幂等键 |
| 路径节点并发排序 | 序号冲突 | 事务内先删后插，用 `uk(path_id, seq_no)` 兜底 |
| DRG 权重并发导入 | 同版本重复 | 表级唯一约束 + 导入前加锁 |

```python
"""并发控制示例：规则审核用乐观锁，入径用 Redis 幂等键。"""

from sqlalchemy import update

from app.core.errors import BizError
from app.core.redis import redis_client
from app.models.m18.kb import MedRule


async def review_rule(session, rule_id: int, review_result: str, operator_id: int):
    """审核用状态作为乐观锁条件，避免两人同时审核覆盖彼此结论。"""
    new_status = "PUBLISHED" if review_result == "APPROVED" else "DRAFT"
    stmt = (
        update(MedRule)
        .where(MedRule.id == rule_id, MedRule.status == "IN_REVIEW")
        .values(status=new_status, reviewed_at=datetime.now(), reviewed_by=operator_id)
    )
    result = await session.execute(stmt)
    if result.rowcount == 0:
        raise BizError("1808002", "规则状态已变化，请刷新后重试")
    await session.commit()


async def enter_path(session, path_code: str, patient_id: int, encounter_id: int) -> str:
    """入径前抢占幂等键。分区表无法建跨分区 UNIQUE，只能靠这里兜。"""
    idem_key = "m18:idem:path-entry:%s:%d:%d" % (path_code, patient_id, encounter_id)
    acquired = await redis_client.set(idem_key, "1", nx=True, ex=86400)
    if not acquired:
        raise BizError("1808022", "该患者该次就诊已入径同一路径")
    try:
        entry_no = await _create_entry(session, path_code, patient_id, encounter_id)
        await session.commit()
        return entry_no
    except Exception:
        await redis_client.delete(idem_key)
        raise
```

> **`enter_path` 失败时必须删掉幂等键。** 若不删，一次写库失败会让这个患者在 24 小时内都无法重新入径，而界面只会显示「已入径」——患者明明没入径却怎么也进不去，只能等第二天。这个缺陷在上线初期极难发现，因为它只在写库失败的偶发时刻出现。

| 三段式（M01-05 附录 A） | 四段式（本规范） | 说明 |
|---|---|---|
| `m18:path:manage` | `m18:kb:path:edit` + `m18:kb:path:create` + `m18:kb:path:publish` | 路径管理整体授权 |
| `m18:template:create` | `m18:kb:rule:create` | 本子模块不涉及文书模板，该码不映射，由 M18-01 承接 |
| `m18:kb:manage` | `m18:kb:rule:create`、`m18:kb:rule:edit`、`m18:kb:path:edit`、`m18:kb:entry:edit`、`m18:kb:config` | 知识库维护整体授权 |

> **授权时四段式优先，三段式作为兼容入口。** 两套码同时存在时必须保证映射完整，否则会出现「按旧文档授权了 `m18:path:manage`、新系统却只认 `m18:kb:path:edit`」这类权限静默失效——用户点按钮没反应，也不会看到「无权限」提示，因为校验是在后端抛 403，而前端按钮的显隐判断用的是另一套码。

### 9.3 数据权限

| 数据 | 可见范围 | 说明 |
|---|---|---|
| 规则与路径配置 | 全院 | 知识资产不按科室隔离 |
| 规则命中统计 | 全院 | 同上 |
| 入径记录 | 按科室 | 只能看本科室患者的入径情况，医务科与质控科例外 |
| 变异记录 | 按科室 | 同上 |
| DRG 权重 | 全院 | 主数据副本 |

> **规则不按科室隔离是刻意的。** 有些医院会把「某科室的用药规则」只给该科室看，但在眼科专科医院里，同一套用药规则（如抗 VEGF 与抗凝药）跨屈光、白内障、眼底多个科室都在用。按科室切开会让同一条规则在三个科室各维护一份，最终三份内容不一致——而医生在哪个科室开方本来就不该改变规则判断结果。

### 9.4 安全措施

| 措施 | 实现 | 说明 |
|---|---|---|
| 越权校验 | 每个接口 `require_perm` | 权限码见 9.1 |
| 审核分离 | 审核人 ≠ 创建人 | 数据库层无法强制，Service 层校验 |
| 内容不可改 | 触发器 + 列级 REVOKE UPDATE | 见数据结构 4.2 |
| 删除保护 | REVOKE DELETE | 规则与入径记录均不可物理删除 |
| 接口鉴权 | Header `X-User-Id` + 网关校验 | 内部接口另校验 `X-Call-Source` |
| 敏感信息 | 接口不返回患者姓名等直接标识 | 入径记录只返回 `patient_id`，患者信息由调用方按需查 M03 |
| 操作留痕 | 发布、审核、停用、导入全留痕 | 谁、何时、做了什么、变更摘要 |
| 输入校验 | Pydantic 严格模式 | 拒绝未声明字段，防止通过额外字段注入 |

**内部接口的安全要求：**

| 接口 | 鉴权 | 限流 | 说明 |
|---|---|---|---|
| P-09 | `X-Call-Source` 白名单 + 网关 IP 白名单 | 500 QPS | 只允许 M05 调用 |
| P-12 | 同上 | 200 QPS | 只允许 M07、M05 调用 |
| P-13 | 同上 + 需 `m18:kb:rule:publish` 权限 | 1 次/分钟 | 只允许 M01 调用 |

> **P-13 限流 1 次/分钟是必要的保护而不是性能优化。** 一次重载要重建 8,000 条规则的索引，CPU 占用约 0.6 秒。若上游因网络重试连发十次，三个实例各自被打满，P-08 的 300ms 承诺会立刻失守——而 P-08 挂掉意味着全院所有处方都变成 DEGRADED，用药审核事实上停摆。

```json
}
```

> **`m18.kb.rule_published` 的订阅方不包含 M04。** M04 的分诊规则获取方式见 10.6。

### 10.4 事件订阅

| 事件名 | 来源 | 处理 | 幂等 |
|---|---|---|---|
| `mdm.drug.created` | M01 | 更新本地药品副本，规则创作时立即可用 | 按 `drug_code` 覆盖 |
| `mdm.drug.updated` | M01 | 同上 | 同 |
| `mdm.diagnosis.changed` | M01 | 更新本地诊断副本 | 按 `diagnosis_code` 覆盖 |
| `mdm.rule.reload` | M01 | **触发 P-13 相同逻辑的热重载** | 按 `trace_id` 去重 |
| `mpi.patient.merged` | M03 | 患者合并后，入径记录 `patient_id` 转移到主索引 | 按 `merge_id` 去重 |

> **`mdm.rule.reload` 与 P-13 走的是同一个 Service 方法。** 抗菌药物分级与相互作用规则在 M01 侧也有维护入口（M01-03），那里改动后通过 MQ 广播 `mdm.rule.reload`，本子模块收到后执行与 P-13 完全相同的重载流程。**两条路径必须共用同一份实现**，否则会出现「通过 MQ 触发的重载在失败时不保留旧集」这类只在一半路径上存在的缺陷。

### 10.6 裁决事项

本章登记两项曾经悬空、现已由模块级评审裁决的事项。**两项均已于 2026-11-07 裁决完毕，本子模块按裁决结论实现，不再列为待定项。**

| 事项 | 裁决结论 | 落地位置 |
|---|---|---|
| 分诊规则交付通道 | 方案 A：新增内部契约 **P-15** | 共享规范 §8A（模块级评审回填）、本文件 10.6.1 |
| `DR_OPHTH_003` 基线眼压 | M18 侧补取，**P-08 请求体不动** | 本文件 10.6.2、M18-05 设计 |

> **两类裁决的共同判据：** 加字段能解决的，才改契约；加字段解决不了的，改自己。`iop` 属于后者——9 个调用方没有一方拿得到眼压，往契约里加字段等于把「缺失」固化下来。分诊通道属于前者——它不是字段问题，是根本没有通道，所以必须补契约。

#### 10.6.1 分诊规则的交付通道（已裁决：方案 A，契约编号 P-15）

| 项 | 结论 |
|---|---|
| 规则创作 | 本子模块 P09 维护 |
| 规则执行 | M04-04 分诊 |
| **交付通道** | **方案 A：新增内部契约 P-15** |

**P-15 `GET /internal/v1/m18/kb/triage-rules`**

| 项 | 内容 |
|---|---|
| 调用方 | M04-04 分诊 |
| 方法 | GET |
| 路径 | `/internal/v1/m18/kb/triage-rules` |
| 性能要求 | P95 ≤ 300ms |
| 返回内容 | 当前生效的分诊规则集 + `rule_version_set` + 版本化快照能力 |
| 登记位置 | 共享规范 §8A 内部契约总线（由模块级评审回填） |

**为什么是方案 A 而不是 B（事件推送 + 本地缓存）：** 事件推送有一个致命问题——**首次加载仍缺一个取数接口**。M04-04 分诊台上线第一天，本地缓存是空的，只能等 M18 下一次发事件，而规则可能一周都不变。**空规则集下的分诊只能靠人工经验，而这恰恰是设计知识库要解决的问题。**

**为什么不是方案 C（直读对外接口）：** 违反模块间只走内部契约的原则；且对外接口的权限模型是给操作员配的，M04 服务端调它要么走超级权限（越权），要么借用某个操作员身份（无法审计）。

**为什么编号是 P-15 而不是 P-14：** P-14 已被 M18-06 的 `seal-status` 占用（`GET /internal/v1/m18/emr/seal-status/{patient_id}`）。若本子模块占用 P-14，会出现两份文档抢同一个编号。

**落地顺序：** 共享规范 §8A 登记 P-15 → 本子模块建表 `m18_kb_triage_rule` 并实现接口 → M04-04 接入。**在 P-15 实现并登记完成前，M04-04 不得依赖分诊规则做任何自动判定**，P09 页面明确提示「规则已保存但 M04 尚未接入」。

#### 10.6.2 `DR_OPHTH_003` 的基线眼压（已裁决：M18 侧补取，P-08 契约不动）

| 项 | 结论 |
|---|---|
| `iop` 字段是否加进 P-08 | **不加** |
| 眼压从哪里来 | **M18-05 审核服务在收到 P-08 后自行补取** |
| 退化条件 | 保留，作为**补取失败时的降级形态** |

**根因不在 P-08。** M07-05 自己定义的 `MedicationCheck` 请求体只有 `encounter_id` 与 `items`，连诊断都没有——M07 只能告诉服务端「开了什么药」。诊断本来就靠 M18 用 `encounter_id` 调 U-01 去取。同理，眼压也应该由 M18 补取，而不是要求 9 个调用方都学会传眼压。

**为什么不改 P-08：** P-08 的调用方（M07-05、M14-06）没有人能传 `iop`。加一个字段只会让所有调用方都传 `null`，**等于把「缺失」写进契约，而不是解决它**。

**M18-05 侧的实现要求（本子模块提出的约束）：**

| 要求 | 说明 |
|---|---|
| 取哪一次眼压 | **用药前**最近一次测量，不是用药后。激素性高眼压的判据是「相对基线的升高」 |
| 时间窗 | 基线取本次就诊前 90 天内最近一次；无记录则视为缺失 |
| 性能 | 300ms 预算下必须预取 + 缓存，不得在请求路径上串行调三个模块 |
| 失败形态 | 补取失败或超时 → `degraded: true` + 该条规则标 `DEGRADED`，**不得静默按「无眼压」处理** |

**「有眼压」与「有正确的眼压」是两件事。** 若只取到用药后的眼压，那是已经升高的值，用它做基线会把「用药后升高 8mmHg」判成「基线本就 32mmHg、无升高」，从而漏检。这个判据必须写进 M18-05 的设计里。

**退化条件保留。** 补取失败时，`DR_OPHTH_003` 退化为「既往青光眼史 OR 用药时长 > 14 天」，`severity` 保持 3（不因缺字段而降低，避免漏检时连提示都没有）。这正是共享规范 §8A.2 的降级语义：**降级要能被看见**——退化时 `degraded: true`，让医生知道「这条只跑了一半」，而不是拿到一个看起来正常的结论。

### 10.7 规则命中复审机制

规则命中统计的三类清单（API-12）如果没有人定期处理，规则库三年后就是一个没人敢关也说不清为什么存在的黑箱。本节规定复审的责任人、周期与升级路径。

#### 10.7.1 三类异常与复审动作

| 类型 | 判定条件 | 复审动作 | 处置结论 |
|---|---|---|---|
| `FALSE_POSITIVE` 疑似误报 | 加权命中率 > 80% | 抽样查看命中处方，判断是条件过宽还是场景本就应该频繁提示 | 收窄条件 / 降级 `alert_level` / 维持并注明理由 |
| `DEAD_RULE` 疑似死规则 | 连续零命中 > 90 天 | 确认规则对应药品或诊疗方式本院是否仍在使用 | 停用（`DISABLED`）/ 保留并标注「本院未开展」 |
| `ALL_IGNORED` 全忽略 | 触发 ≥ 20 次且忽略率 = 100% | 查看医生忽略原因与临床反馈 | 调整提示语或级别 / 停用 / 保留（若属强制性要求） |

#### 10.7.2 责任人与周期

| 项 | 规定 |
|---|---|
| 复审责任人 | 药学部指定 1 名规则管理员（角色 `KB_RULE_REVIEWER`） |
| 复审周期 | 每月 1 次，固定在次月前 5 个工作日 |
| 单次工作量上限 | 30 条（按命中次数降序取前 30），避免一次看太多而流于形式 |
| 复审记录 | 写入 `m18_kb_hit_stat` 的 `review_status` / `reviewed_by` / `reviewed_at` / `review_conclusion` |

#### 10.7.3 未复审的升级路径

| 超期 | 动作 |
|---|---|
| 超过 5 个工作日未复审 | P01 工作台顶部显示待复审提醒，仅规则管理员可见 |
| 超过 15 个工作日未复审 | 向药学部主任发送提醒（通过 M03-05 消息服务） |
| 超过 30 个工作日未复审 | 上报医务科；`m18_kb_pending_review` 监控指标持续告警 |

> **为什么不设「自动停用」？** 因为最需要复审的恰恰是那些长期无人理会的规则——如果系统到点自动停用，那么一个「本该有人看但没人看」的管理问题会被伪装成「系统正常运行」。**复审机制的价值在于暴露管理缺位，而不是替人做决定。**

## 11. 异常处理与日志

### 11.1 异常分类

| 类别 | 示例 | HTTP | 处理方式 | 是否告警 |
|---|---|---|---|---|
| 参数错误 | 条件树结构非法、字段不在白名单 | 400 | 返回明确错误码与字段名 | 否 |
| 状态错误 | 已发布规则被要求修改 | 400 | 提示当前状态与允许操作 | 否 |
| 权限错误 | 无发布权限 | 403 | 记录审计日志 | 是（连续 5 次） |
| 资源不存在 | 规则不存在 | 404 | 返回错误码 | 否 |
| 冲突 | 审核人等于创建人 | 409 | 返回冲突原因 | 是 |
| 依赖不可用 | M01 不可用 | 503 | 降级返回 | 是 |
| 系统错误 | 数据库异常 | 500 | 记日志带 trace_id | 是 |

### 11.2 降级形态逐接口说明

| 接口 | 正常 | 降级返回 | 失败 |
|---|---|---|---|
| API-01~API-08 | 200 + `degraded: false` | 主数据不可用时 200 + `degraded: true` + `data_quality: PARTIAL`，药品名显示为编码 | 400/403/404/409 + 非 0 code |
| API-09~API-13 | 200 + `degraded: false` | 命中统计未聚合完成时 `data_quality: CACHED`（返回上一次聚合结果） | 同上 |
| API-18~API-27 | 200 + `degraded: false` | M03 不可用时入径判定降级，`data_quality: PARTIAL` | 同上 |
| API-30~API-31 | 200 + `degraded: false` | 导入部分行失败时 `degraded: true` + `failed_rows` | 同上 |
| P-09 | 200 + 完整权重列表 | 权重表为空或超时 200 + `degraded: true` + `data_quality: UNKNOWN` + `record_count: 0` | 403 + 非 0 code |
| P-12 | 200 + `path` 完整 | 查询失败 200 + `path: null` + `degraded: true` + `data_quality: PARTIAL/UNKNOWN` | 403 + 非 0 code |
| P-13 | 200 + 新 `rule_version_set` | 重载失败 200 + `degraded: true` + 旧 `rule_version_set` 原样返回 | 403 + 非 0 code |

**三条降级红线：**

1. **不允许「看起来正常但不完整」的 200**。凡是数据不全，`degraded` 必须为 `true`。
2. **不允许把「没查到」伪装成「空列表且 `degraded: false`」**。`record_count = 0` 配 `degraded: false` 与配 `degraded: true` 是两种不同事实。
3. **不允许用 200 + 空 `data` 表达「无权限」**。无权限一律 403 + 非 0 错误码，否则调用方会把它当成「没有这份数据」——在术前核对场景里就是「不需同意书」，属于临床安全问题。

> **`data_quality` 无法判定时必须返回 `UNKNOWN`，绝不能默认成 `REALTIME`。** M05-05 与 M06-06 的归档完整性判定会读这个值，默认成「完整」等于把「不知道」记成「没问题」，而归档一旦确认要保留 15~30 年，事后无法更正。

## 12. 验收标准

本章验收分四类：功能验收（AC）、性能验收（PF）、数据准确性验收（DA）、安全性验收（SC）。每类编号从 01 连续。

### 12.1 功能验收（AC）

| 编号 | 验收项 | 验收方法 | 通过标准 |
|---|---|---|---|
| AC-01 | 用药规则创建 | 在 P02 新建一条 `INTERACTION` 规则并保存 | 返回 `rule_code` 形如 `DR_INTER_001`，状态 `DRAFT` |
| AC-02 | 规则编码自动生成 | 同一 `rule_type` 连续创建 3 条 | 序号连续递增，不跳号不重号 |
| AC-03 | 规则版本号 | 修改已发布规则 | 走 clone，新记录 `rule_version` = 旧 + 1，旧记录内容不变 |
| AC-04 | 规则提交审核 | 创建人点提交 | 状态 `DRAFT` → `IN_REVIEW`，`updated_at` 变化 |
| AC-05 | 审核人不得为创建人 | 创建人本人点审核通过 | 返回 `"1808010"` `KB_REVIEWER_IS_CREATOR` |
| AC-06 | 审核通过进入 PUBLISHED | 另一账号审核通过 | 状态 `IN_REVIEW` → `PUBLISHED`，`published_at` 非空 |
| AC-07 | PUBLISHED 不等于生效 | 审核通过后立即调 P-08 类接口（由 M18-05 执行） | 新规则**不命中**，因为尚未生成版本集 |
| AC-08 | 发布生成版本集 | P03 点发布 | 新建 `version_set_no=KBS{yyyyMMdd}{NNN}`，`rule_count` = 当前全部 PUBLISHED 数 |
| AC-09 | 发布后旧版本 SUPERSEDED | 同 `rule_code` 发布新版本 | 旧记录状态变 `SUPERSEDED`，`superseded_by_version` 指向新版本 |
| AC-10 | 旧版本内容可完整读回 | 按 `rule_code`+`rule_version` 查旧版本 | 返回全部字段，内容与发布时逐字一致 |
| AC-11 | 规则停用不删数据 | P02 停用一条规则 | 状态 `DISABLED`，记录仍在，可按编码查到 |
| AC-12 | 停用不回算历史 | 停用后重查此前审核记录 | 历史结论与 `rule_version_set` 均不变 |

## 附录 B：内存规则集与加载时序

### B.1 RuleSet 组成

| 部分 | 内容 | 约占用 |
|---|---|---|
| 规则头 | 8,000 条 × 600B | 4.8MB |
| 条件树对象 | 8,000 条 × 1,200B | 9.6MB |
| 药品倒排索引 | `drug_code` → 规则 ID 列表 | 2.3MB |
| 诊断倒排索引 | `diagnosis_code` → 规则 ID 列表 | 0.8MB |
| DRG 权重 | 当前版 120 条 | 24KB |
| Python 对象开销 | 引用、字典、列表头 | 余量 |

### B.2 加载时序

```
T+0ms    收到 reload 请求（P-13 或 mdm.rule.reload 事件）
T+5ms    读取 m18_kb_rule_version_set 取最新 LOADED 版本集
T+10ms   查询该版本集下全部 PUBLISHED 规则（单次全表扫，走 idx_partial）
T+120ms  逐条解析 rule_condition 构建 CompiledRule 对象
         ↳ 单条解析失败：跳过该条并记 WARN 日志，不整体失败
T+650ms  构建药品与诊断倒排索引
T+720ms  加载当前 DRG 权重
T+760ms  构建完成，校验 checksum
T+770ms  原子切换 current 指针（swap），旧 RuleSet 引用计数 -1
T+780ms  返回 rule_version_set 与新 checksum
```

**关键：T+120ms 到 T+760ms 期间，所有 P-08 类请求仍读旧 RuleSet。** 切换是指针赋值，是原子的，不存在「一半新一半旧」。

### B.3 加载失败处理

| 失败点 | 表现 | 处理 |
|---|---|---|
| 读版本集失败 | 数据库不可用 | 保留旧 RuleSet，返回 `degraded=true` |
| 规则查询超时（> 800ms） | 慢查询 | 放弃本次加载，保留旧集，返回 `degraded=true` |
| 单条规则解析失败 | 条件树不合法 | 跳过该条，继续加载其余，日志记 WARN |
| checksum 不一致 | 数据被并发修改 | 放弃本次加载，保留旧集，返回 `degraded=true` |
| DRG 权重缺失 | `is_current` 无记录 | 权重集为空，`data_quality=UNKNOWN`，其余规则正常 |

> **任何一种失败都不允许把规则集变空。** 空规则集意味着所有处方审核返回 `DEGRADED`，M07-05 会对每一张处方弹降级提示，全院用药审核瞬间停摆。**宁可继续用旧规则，也不能没有规则。**

### C.1 P-08 必须传递的字段与规则依赖关系

这是本子模块与 M18-05 之间最关键的接口约束。**规则写好了、但执行方收不到字段，等于没写。**

| 规则 | 必须有的字段 | 字段来源 | 缺失后果 |
|---|---|---|---|
| `DR_OPHTH_001` | `diagnosis_codes`、`items[].drug_code` | M07-02 诊断、M07-05 处方 | 完全失效（无诊断无法判定闭角型） |
| `DR_OPHTH_002` | `items[].drug_code`（含全身用药） | M07-05 处方 | **部分失效**：只传眼科用药时，全身抗凝药不在 `items` 中则漏检 |
| `DR_OPHTH_003` | `items[].days`、`diagnosis_codes`（既往青光眼史）、**基线眼压 `iop`** | M07-05 处方、M10/M12 检查 | **退化**：无 `iop` 时只能按「激素 + >14 天 + 既往史」判定，会漏掉「无青光眼史但眼压已升高」的患者 |
| `DR_OPHTH_004` | `diagnosis_codes`、`items[].drug_code` | M07-02 诊断、M07-05 处方 | 完全失效 |

### C.2 关于 `iop` 字段的明确结论

**当前 P-08 的请求体定义中没有眼压字段。** 这是共享规范 §8A 已确认的契约，本子模块不能单方面增加。

因此 `DR_OPHTH_003` 的实际判定条件退化为：

```
既往青光眼史 OR 用药时长 > 14 天
```

这个退化后的规则**能覆盖有青光眼史的患者**，但漏掉两类：
1. 无青光眼史、但用药后眼压升高的患者（激素性高眼压的典型人群）；
2. 有高眼压但未诊断为青光眼的患者。

**处理方式：**
- 规则按退化条件上线，`severity` 保持 3；
- 在 P01 的 `false_positive` 清单里监控这条规则——如果命中率高但忽略率也高，说明医生认为它在误报，实际原因是条件太宽（缺 `iop` 导致的补偿性放宽）；
- **在规则备注中标注「待 P-08 支持 `iop` 后收紧」**，并在 §10.6 登记为待裁决项。

> **为什么不在 M18-08 侧自行查眼压？** 因为 M18-08 是规则创作方，执行时是 M18-05 在同步链路上调本子模块的规则集。如果规则求值过程中反查 M10/M12，P-08 的 300ms 预算会被一次跨模块查询吃掉，而且 M18-08 就成了一个「执行时还要拉数据的」服务，与「规则常驻内存、纯函数求值」的设计目标直接冲突。**正确做法是把字段加进 P-08 请求体，由调用方带过来。**

| 知织库规则的所有金额类指标（如按规则拦截减少的药品费用） | M16 | **不计算**。M11 铁律：金额归 M16 |

| 规则命中率的对外报表 | M22 | 本子模块提供 `m18_kb_hit_stat` 按日数据 |
| 临床路径的住院天数统计 | M16 | 不计算，路径只记录标准天数定义 |

### D.1 可自产的指标编码

若需自产指标（如入径率），按 M22-01 指标编码规范：`{域}_{主题}_{指标名}`，域取 `OP`/`CL`/`OPT`/`REF`/`FIN`/`PERF`。

| 指标 | 建议编码 | 说明 |
|---|---|---|
| 临床路径入径率 | `CL_PATH_ENTRY_RATE` | 入径患者数 / 适用患者数 |
| 路径变异率 | `CL_PATH_DEVIATION_RATE` | 变异入径数 / 入径数 |
| 路径完成率 | `CL_PATH_COMPLETION_RATE` | 完成数 / 入径数 |
| 规则触发率 | `CL_KB_RULE_TRIGGER_RATE` | 触发处方数 / 审核处方数 |

> **为什么不叫 `RZ07NNN` 这类自产编码？** 因为 M22-01 已把指标编码格式定为 `{域}_{主题}_{指标名}`，自创编码会导致 M22 指标中心无法纳入。**指标编码是全院的公共语言，不能各模块各叫一套。**

## 附录 F：术语表

| 术语 | 英文/缩写 | 定义 |
|---|---|---|
| 知识库规则 | Knowledge Rule | 可执行的判定条件，有 `rule_condition`，进内存求值 |
| 知识条目 | Knowledge Entry | 仅供人阅读的循证资料，不参与求值 |
| 规则版本集 | Rule Version Set | 某一时刻生效的全部规则的整体版本号，一个字符串可还原全集 |
| 版本集校验和 | Checksum | 版本集内全部规则内容的 SHA-256，用于确认加载的是不是同一套 |
| 双缓冲切换 | Double Buffer Swap | 新规则集构建完成后原子替换指针，旧集在新集就绪前持续服务 |
| 降级返回 | Degraded Response | HTTP 200 + `degraded:true`，调用方知道本次数据不完整 |
| 入径 | Path Entry | 患者进入某条临床路径的过程 |
| 适用患者数 | Applicable Patients | 符合路径诊断、年龄、术式等条件的患者数，是入径率分母 |
| 变异 | Deviation | 实际诊疗偏离路径标准节点、天数或顺序 |
| 出径 | Exit | 患者中途退出路径（转科、拒绝、死亡等） |
| 死规则 | Dead Rule | 长期零命中的规则，可能是条件写错或已失效 |
| 误报规则 | False Positive Rule | 命中率过高但大量被忽略，可能是条件过宽 |
| 三段式权限码 | 3-segment Permission | M01-05 下发的 `m18:{资源}:{动作}` 形式 |
| 四段式权限码 | 4-segment Permission | 本规范使用的 `m18:{子模块}:{资源}:{动作}` 形式 |
