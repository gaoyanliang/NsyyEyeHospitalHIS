### 1.2 这张清单是怎么定下来的

数据结构设计汇总 §6 第 ⑥ 批已为 M18-05 登记了 11 张表名，本文件**逐一对应，一个不多一个不少**。把它们按职责重新归类，可以看出为什么正好是这 11 张：

| 职责 | 表 | 为什么必须独立成表 |
|---|---|---|
| 质控规则的判定条件 | `m18_qc_rule` | 规则要能发布新版本、能被停用，且「扣分等级」是规则属性不是缺陷属性；塞进缺陷表就无法回答「这条缺陷是按哪版规则判的」 |
| 一次质检 | `m18_qc_task` | 质控是**批量动作**：一次跑 1,200 份病历，必须能回答「哪个版本、何时、谁触发、跑了几份、失败几份」；没有任务表，缺陷就成了无主数据 |
| 缺陷明细 | `m18_qc_defect` | 一份病历可命中多条缺陷，且缺陷有独立的整改生命周期（`OPEN → RECTIFIED`），与任务的生命周期不同 |
| 评分结果 | `m18_qc_score` | 评分是**任务级结果的汇总**（扣分累加 + 一票否决 + 评级），而缺陷是明细；且评分要保留「旧版本重跑一次」的历史，不能覆盖 |
| 用药审核一次执行 | `m18_qc_medication_review` | `P-08` 每次调用都要留痕（年 45 万次），且必须存 `rule_version_set` 快照才能事后复现「当时为什么没提示」 |
| 命中明细 | `m18_qc_med_alert_hit` | 一次审核可命中多条提示；提示是 `rule_code + drug_code` 维度，与审核记录是 1:N |
| 规则执行镜像 | `m18_qc_med_rule` | 内存 RuleSet 需要一个**不依赖 M18-08 表结构**的稳定加载入口，且要与 M18-08 的发布做版本比对 |
| 事后点评 | `m18_qc_rx_review` | 处方点评是**抽查**，不是全量审核，抽样规则、点评人、点评结论都与审核记录不同 |
| 整改闭环 | `m18_qc_rectify` | 整改可能有多次动作（医生先提交、医务科驳回、再提交），是缺陷的 N:1 子表 |
| 运行参数 | `m18_qc_config` | 扣分权重、阈值要能改且要有版本，改完要能追溯「上个月为什么是甲级」 |
| 审计日志 | `m18_qc_oper_log` | 规则发布、缺陷改判、整改确认这类操作必须留审计，且要按月分区、只增不改 |

### 1.3 命名边界：`m18_qc_med_rule` 与 `m18_kb_*` 的分工

这是本文件最容易做错的一处，必须先说清。

| 表 | 归属 | 存什么 | 谁写 | 谁读 |
|---|---|---|---|---|
| `m18_kb_med_rule` / `m18_kb_dose_rule` / `m18_kb_interaction_rule` | **M18-08** | **规则本体**：触发条件的结构化定义、循证依据、审核流程、发布状态 | M18-08（知识库管理页面） | M18-08、M18-05（只读） |
| `m18_qc_med_rule` | **M18-05（本文件）** | **执行镜像**：从 M18-08 `PUBLISHED` 规则生成的一份扁平化、可直接装载进内存 RuleSet 的记录 + 加载批次登记 | M18-05 的规则加载任务 | 只有 M18-05 的规则加载器 |

**为什么不能只读 M18-08 的表、非要多一张镜像表：**

1. **内存 RuleSet 的装载需要稳定的契约。** M18-08 的规则表随知识库维护需求演进（今天加「眼科专科条件」，明天可能加「肾功能分级条件」），字段会变。若 RuleSet 装载器直接啃 `m18_kb_*` 的表结构，每次 M18-08 改字段都要改 M18-05 的装载代码并重新测试 300ms 链路。镜像表是一层防腐层。
2. **版本比对需要「我到底加载了哪些规则」。** 热重载时要比对「新集与旧集差在哪」，这需要一个按 `rule_code` 索引的本地快照。直接在内存里比对两个由 `m18_kb_*` 拼出来的对象，既慢又无法落库留证。
3. **`rule_version_set` 必须可复现。** 响应里的 `rule_version_set` 是「本次审核用的规则集指纹」。事后要证明「2026-10-21 14:20 那次审核用的是哪 8,000 条规则的哪个版本」，唯一可靠的办法是把参与装载的规则清单落库。

**镜像表不是规则的第二份权威：** `m18_qc_med_rule` 的所有字段都从 `m18_kb_*` 复制而来，**只读不编辑**，任何字段不允许在 M18-05 的界面上修改；一旦发现镜像与本体不一致，以本体为准并触发重载。`m18_qc_med_rule` 也不保存规则的循证依据全文、审核流程、发布审批记录——那些只在 `m18_kb_*` 里。

### 1.4 本子模块不自建的表（铁律 2 + 共享规范 §1.3）

| 绝不建的表 | 归属 | 本子模块的访问方式 |
|---|---|---|
| `m18_emr_record` / `m18_emr_record_field` | M18-02（首建） | **只读引用**：质控评分与缺陷对象定位要靠 `record_id`；不建 FKs、不复制正文 |
| `m18_emr_amendment` / `m18_emr_seal` / `m18_emr_document` | M18-06（首建） | 整改时若走「追加更正记录」，`m18_qc_rectify.amendment_id` 只存逻辑外键；封存状态查询走 P-14 |
| `m18_kb_med_rule` / `m18_kb_dose_rule` / `m18_kb_interaction_rule` / `m18_kb_med_knowledge` | M18-08 | 只读；执行镜像见 §1.3 |

> ⚠️ **特别注意：本子模块不建任何「审核结论」第二权威表。** `P-08` 的返回结果落 `m18_qc_medication_review`，是**留痕**不是**权威**——处方能不能发由 M14-06 的 `m14_rx_check` 决定，M18 只提供知识与提示。同理，质控评级 `GRADE_A/B/C` 在本子模块是**病历质量的度量**，不能反过来去改病历的 `status`（那是 M18-02 / M18-06 的事）。

### 1.5 表间关系总览

| 关系 | 基数 | 说明 |
|---|---|---|
| `m18_qc_rule` → `m18_qc_defect` | 1:N | 一条规则可被判出多条缺陷（不同病历、不同对象）；缺陷用 `rule_code` + `rule_version` 双字段快照，不用外键 |
| `m18_qc_task` → `m18_qc_defect` | 1:N | 一次质检产出多条缺陷 |
| `m18_qc_task` → `m18_qc_score` | 1:N | 一次质检可为 N 份病历各自评分；同一病历在同一任务下只有一行评分 |
| `m18_qc_defect` → `m18_qc_rectify` | 1:N | 一条缺陷可能经历多次整改尝试（提交 → 驳回 → 再提交） |
| `m18_qc_medication_review` → `m18_qc_med_alert_hit` | 1:N | 一次审核命中多条提示 |
| `m18_qc_med_rule` →（无下游） | — | 镜像表只被规则加载器读取，不参与业务关联 |
| `m18_qc_rx_review` → `m18_qc_medication_review` | N:1（弱） | 点评通过 `prescription_no` + `rx_check_time` 关联到开方时的那次审核记录，逻辑外键 |
| `m18_qc_config` → 全部 | 1:N（参数） | 配置被各表所在的服务读取，不做物理关联 |

> `FK*` 表示**逻辑外键**，物理上不建 `FOREIGN KEY`（跨子模块/跨模块引用一律逻辑外键，用索引 + 应用层保证）。本文件 11 张表之间也不建物理外键，原因是：①`m18_qc_task` / `m18_qc_medication_review` / `m18_qc_oper_log` 是分区表，PostgreSQL 的**分区表不支持作为外键的被引用方**；②质控任务重跑会批量插入，物理外键会显著拖慢批跑（实测 1,200 份病历的批跑，带外键时锁等待是主要耗时）；③缺陷与任务的生命周期由 Service 层状态机保证，数据库外键只能保证「存在」不能保证「状态正确」。

**ER 图的三个设计取舍（每一项都不是随手选的）：**

| 取舍 | 选了 | 为什么不选另一种 |
|---|---|---|
| `m18_qc_defect` 是否分区 | **不分区** | 分区表的**唯一约束必须包含分区键**。`uk_m18_qc_defect (qc_task_no, defect_code, defect_object)` 是「同一任务同一对象的同一缺陷只记一次」的执行者，一旦把 `created_at` 塞进唯一键，同一对象在同一任务下就能靠不同 `created_at` 建出两条记录，这条约束就废了。缺陷 3 年 180 万行单表完全可承受 |
| `m18_qc_score` 是否与 `m18_qc_task` 合并 | **分表** | 任务表一行描述的是一次批跑（1,200 份病历），评分表是 1,200 行。合并意味着任务行要重复存 1,200 次批跑元信息，且任务的 `status`（`PASSED`/`DEFECT_FOUND`）是批跑级状态，评分是病历级结果，两者生命周期不同（重跑会产生新的评分行，但沿用同一个任务号） |
| `m18_qc_med_alert_hit` 是否内嵌 JSONB | **独立表** | 提示明细要能被 SQL 直接聚合（「本月哪条规则命中最多」「哪类提示被医生忽略最多」）。内嵌 JSONB 后每个统计都要 `jsonb_array_elements`，且无法建部分索引。**代价是审核记录与提示明细要两次写入**，所以写入放在同一事务里（见 4.7 的事务骨架） |

### 4.2 表：`m18_qc_rule`（质控规则表）

**用途：** 存放时限质控 / 逻辑质控 / 完整性质控 / 一致性质控四类规则的**判定条件与扣分等级**。这是 M18-05 自有、自维护的规则，与 M18-08 的用药规则（`m18_kb_*`）是两套东西：本表回答「这份病历有没有按时写完、诊断和手术记录是否矛盾、必填段落是否缺失」，M18-08 回答「这张处方开的药有没有相互作用」。

**规则编码遵循共享规范 §3.3：`QC_{质控类型}_{序号3位}`**，例如 `QC_TIME_001`（门诊病历当日完成）、`QC_LOGIC_014`（手术眼别与诊断眼别不一致）、`QC_COMPL_003`（现病史缺失）。

**写入方：** M18-05 质控规则配置页（P02，`m18:qc:rule:create` / `m18:qc:rule:publish`）。**只读方：** M18-05 质控引擎（批跑时按 `status = 'PUBLISHED'` 且命中 `record_type` / `qc_type` 装载）、M18-05 质控工作台统计。

```sql
ALTER TABLE m18_qc_rule
    ADD CONSTRAINT ck_m18_qc_rule_type
    CHECK (qc_type IN ('TIME_LIMIT', 'LOGIC', 'COMPLETENESS', 'CONSISTENCY'));

ALTER TABLE m18_qc_rule
    ADD CONSTRAINT ck_m18_qc_rule_status
    CHECK (status IN ('DRAFT', 'PUBLISHED', 'DISABLED'));

ALTER TABLE m18_qc_rule
    ADD CONSTRAINT ck_m18_qc_rule_level
    CHECK (defect_level IN ('CRITICAL', 'MAJOR', 'MINOR', 'HINT'));

-- 等级与扣分必须匹配，否则「一个 HINT 扣 5 分」这种规则会把甲级评成丙级
ALTER TABLE m18_qc_rule
    ADD CONSTRAINT ck_m18_qc_rule_level_score
    CHECK (
        (defect_level = 'CRITICAL' AND deduction_score = 100.0)
     OR (defect_level = 'MAJOR'    AND deduction_score = 5.0)
     OR (defect_level = 'MINOR'    AND deduction_score = 2.0)
     OR (defect_level = 'HINT'     AND deduction_score = 0.5)
    );

ALTER TABLE m18_qc_rule
    ADD CONSTRAINT ck_m18_qc_rule_ver
    CHECK (rule_version >= 1);

-- 生效区间必须正向；允许 effective_to 为空（长期有效）
ALTER TABLE m18_qc_rule
    ADD CONSTRAINT ck_m18_qc_rule_effective
    CHECK (effective_to IS NULL OR effective_to > effective_from);

-- 组合语义：已发布的规则必须有提示话术，否则医生收到一条空提示
ALTER TABLE m18_qc_rule
    ADD CONSTRAINT ck_m18_qc_rule_pub_hint
    CHECK (status <> 'PUBLISHED' OR length(btrim(hint_message)) > 0);

-- 组合语义：自动判定规则必须有判定表达式，人工判定规则不需要
ALTER TABLE m18_qc_rule
    ADD CONSTRAINT ck_m18_qc_rule_judge_expr
    CHECK (is_auto = FALSE OR judge_expr <> '{}'::jsonb);

-- 判定表达式必须带 kind 键（引擎按 kind 分派求值器）
ALTER TABLE m18_qc_rule
    ADD CONSTRAINT ck_m18_qc_rule_judge_kind
    CHECK (is_auto = FALSE OR judge_expr ? 'kind');
```

**`judge_expr` 的 JSONB 结构（必须写清，否则开发各写各的）**

| `kind` | 语义 | 其余键 | 求值方式 |
|---|---|---|---|
| `TIME_WINDOW` | 某段落在相对时间窗口内完成 | `section_type`、`anchor`（`ENCOUNTER_START` / `ADMISSION` / `SURGERY_END` / `DISCHARGE`）、`limit_hours` | 取该段落 `created_at` 与锚点时间差，比较 `limit_hours` |
| `FIELD_REQUIRED` | 某结构化字段必填 | `field_code`、`min_length` | `m18_emr_record_field` 中存在且长度达标 |
| `FIELD_PATTERN` | 某字段必须匹配模式 | `field_code`、`pattern`、`pattern_desc` | 正则匹配，如主诉必须含时长 |
| `CROSS_SECTION` | 两段内容必须一致 | `left_section`、`right_section`、`compare_key` | 如手术记录的 `eye_side` 与诊断的 `laterality` |
| `CROSS_RECORD` | 跨病历比对 | `target_record_type`、`key`、`tolerance_hours` | 如术后首次病程必须在手术记录后 24h 内 |
| `MANUAL` | 人工判定 | — | `is_auto = FALSE` 时使用 |

```json
{
  "kind": "CROSS_SECTION",
  "left_section": "OPERATION_RECORD",
  "right_section": "DIAGNOSIS_TEXT",
  "compare_key": "eye_side",
  "mismatch_level": "CRITICAL"
}
```

> **为什么判定表达式不用 SQL 字符串：** 规则由质控员在页面上配置，若允许写 SQL，等于给了一个「可以在病历库上执行任意 SQL」的入口——这是不可接受的安全漏洞。结构化 JSON 由引擎按 `kind` 分派到固定求值器，求值器只接受白名单键，无法越权。

**`defect_level = 'CRITICAL'` 的扣分为什么固定 100.0 而不是 0：** 评分公式里 CRITICAL 是**一票否决、不参与累加**的，`qc_score` 由其他等级的累加值得出。但 `deduction_score` 不能填 0，否则「一条 CRITICAL 只扣 0 分」会被报表按扣分排序时排到最后，掩盖最严重的问题。填 100.0 表示「足以把任何病历压到 0 分」，同时 `m18_qc_score.has_critical` 会置 `TRUE`，评分时忽略这个数、直接判 `GRADE_C`。这个约定必须在 §3.4 与第八章 8.5 反复对读，否则很容易有人把 100 直接加进 deduction。

### 4.3 表：`m18_qc_task`（质控任务表 · 月分区）

**用途：** 记录**一次质控执行**的全部上下文。这是本子模块可追溯性的地基：任何一条缺陷、任何一份评分，都必须能回答「属于哪次质检、用的哪个规则版本、谁触发的、什么时候跑的」。

**质控任务号遵循共享规范 §3.3：`QCT + yyyyMMdd + 5位流水`**，如 `QCT2026102100001`。单号走 Redis `INCR`（`m18:code:QCT:{yyyyMMdd}`），因为质控任务可能在同一秒内由多个科室的定时任务并发创建。

**写入方：** M18-05 质控任务服务（触发方式见 `trigger_type`）。**只读方：** M18-05 质控工作台（P01）、质控评分页（P05）、M22 报表（经事件与统计接口）。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |

| id | BIGINT | N | IDENTITY | 主键 |

```sql
ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_status
    CHECK (status IN ('PENDING', 'RUNNING', 'PASSED', 'DEFECT_FOUND', 'RECTIFIED', 'CLOSED'));

ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_type
    CHECK (qc_type IN ('TIME_LIMIT', 'LOGIC', 'COMPLETENESS', 'CONSISTENCY', 'MEDICATION', 'MANUAL'));

ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_trigger
    CHECK (trigger_type IN ('SCHEDULED', 'EVENT', 'MANUAL', 'RETRY', 'RE_RUN'));

ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_scope
    CHECK (record_scope_type IN ('RECORD', 'ENCOUNTER', 'DEPT_PERIOD', 'BATCH'));

-- 计数不得为负
ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_counts
    CHECK (
        target_count >= 0 AND processed_count >= 0
    AND defect_count >= 0 AND critical_count >= 0
    AND defect_record_count >= 0 AND retry_times >= 0
    );

-- 已处理的不得超过应处理
ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_processed
    CHECK (processed_count <= target_count);

-- 缺陷病历数不得超过应处理数，缺陷条数不得少于缺陷病历数（一份病历至少 1 条缺陷）
ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_defect_math
    CHECK (defect_record_count <= processed_count AND defect_count >= defect_record_count);

-- CRITICAL 数不得超过缺陷条数
ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_critical
    CHECK (critical_count <= defect_count);

-- 组合语义：终态必须有结束时间与耗时，否则「跑完了但不知道花了多久」
ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_finish_combo
    CHECK (
        status IN ('PENDING', 'RUNNING')
     OR (finish_at IS NOT NULL AND elapsed_ms IS NOT NULL)
    );

-- 组合语义：RUNNING 必须有开始时间
ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_start_combo
    CHECK (status <> 'RUNNING' OR start_at IS NOT NULL);

-- 组合语义：有缺陷的任务必须有缺陷计数，PASSED 必须零缺陷
ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_passed_zero
    CHECK (status <> 'PASSED' OR defect_count = 0);

ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_found_nonzero
    CHECK (status <> 'DEFECT_FOUND' OR defect_count > 0);

-- 平均分的值域与精度
ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_score_avg
    CHECK (score_avg IS NULL OR (score_avg >= 0 AND score_avg <= 100));

-- 回溯试算不得参与病历质量指标（结构性约束：回溯任务不能是定时批跑）
ALTER TABLE m18_qc_task
    ADD CONSTRAINT ck_m18_qc_task_retro_trigger
    CHECK (is_retro_calc = FALSE OR trigger_type IN ('MANUAL', 'RE_RUN'));
```

**分区策略**

按 `created_at` 月度 RANGE 分区，**必须同时建 DEFAULT 分区**，在线保留 3 年（更早的分区 `DETACH` 后归档到只读库，由 M18-06 的留存期任务驱动）。

```sql
CREATE TABLE m18_qc_task (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY,
    qc_task_no          VARCHAR(32) NOT NULL,
    status              VARCHAR(32) NOT NULL DEFAULT 'PENDING',
    created_at          TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE m18_qc_task_p202610 PARTITION OF m18_qc_task
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

CREATE TABLE m18_qc_task_p202611 PARTITION OF m18_qc_task
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

CREATE TABLE m18_qc_task_p202612 PARTITION OF m18_qc_task
    FOR VALUES FROM ('2026-12-01') TO ('2027-01-01');

CREATE TABLE m18_qc_task_default PARTITION OF m18_qc_task DEFAULT;
```

> **DEFAULT 分区不是可选项。** 若 2027-01 的分区还没建而 2027-01-01 00:00 就有质控任务写入，没有 DEFAULT 分区时 INSERT 会直接失败；有 DEFAULT 分区时数据进 default 分区，业务不报错，P2 告警提示「默认分区有数据，请预建下月分区」（监控项见详细设计 §11.4）。

**四个组合约束防的真实错误（逐条说明，不是凑数）：**

| 约束 | 防的错误 | 不写会怎样 |
|---|---|---|
| `ck_m18_qc_task_finish_combo` | 任务标成 `PASSED` 但 `finish_at` 为空 | 质控工作台按「耗时」排序时这些任务排最前或最末；月度质控吞吐报表算不出平均耗时而直接跳过它们，吞吐量虚高 |
| `ck_m18_qc_task_processed` | 重跑时累加 `processed_count` 不清零 | 同一次批跑重试 3 次后 `processed_count` 变成 3 倍，进度条显示 300% |
| `ck_m18_qc_task_defect_math` | 缺陷条数少于缺陷病历数 | 一份病历标了「有缺陷」但缺陷表里查不到明细，质控员点进去是空白，只能重新跑一遍 |
| `ck_m18_qc_task_passed_zero` | 任务 `PASSED` 但缺陷计数忘了清零 | 出现「质控通过但有 12 条缺陷」的矛盾任务，甲级病历率统计直接失效 |

### 4.4 表：`m18_qc_defect`（质控缺陷表）

**用途：** 记录一次质控任务在某份病历上发现的每一个具体缺陷——哪个规则命中、命中在哪个对象上、缺陷等级是什么、出现在哪一段、原文摘要、给了什么整改建议、现在整改到哪一步。

**写入方：** M18-05 质控引擎（批跑与重跑）、P04 逻辑质控与缺陷页面（人工登记与误报标记）、P09 质控整改跟踪（状态流转）。 **只读方：** P05 质控评分与等级、P01 质控工作台、M05-05 缺陷整改（经事件）、M22 报表。

**这张表为什么是质控的账本：** 评分是缺陷的**派生结果**，缺陷才是原始事实。如果把缺陷压成一个 JSONB 塞进 `m18_qc_score`，就再也回答不了「本月 MAJOR 级缺陷里，时限类占多少」这种问题——而这正是质控科每个月要做的事。缺陷单独成表后，「按规则统计」「按科室统计」「按缺陷码统计」「按缺陷对象统计」都只是一次 `GROUP BY`。

**约束说明**

```sql
ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_type
    CHECK (qc_type IN ('TIME_LIMIT', 'LOGIC', 'COMPLETENESS', 'CONSISTENCY', 'MEDICATION', 'MANUAL'));

ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_level
    CHECK (defect_level IN ('CRITICAL', 'MAJOR', 'MINOR', 'HINT'));

ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_status
    CHECK (status IN ('OPEN', 'RECTIFYING', 'RECTIFIED', 'CONFIRMED_OK', 'WAIVED'));

ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_occur
    CHECK (occur_count >= 1);

ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_source
    CHECK (detect_source IN ('AUTO', 'MANUAL', 'IMPORT'));

-- 组合约束 1：整改闭环必须留证。数据结构设计汇总 §7.2 已登记原文。
ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_rectified_evidence
    CHECK (status <> 'RECTIFIED' OR (rectified_at IS NOT NULL AND rectified_by IS NOT NULL));

-- 组合约束 2：整改方式必须与整改留痕成套出现。
ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_rectify_combo
    CHECK (status NOT IN ('RECTIFIED', 'CONFIRMED_OK')
           OR (rectify_way IS NOT NULL AND rectified_at IS NOT NULL AND rectified_by IS NOT NULL));

-- 组合约束 3：追加更正必须回指到具体的更正记录。
ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_amendment_ref
    CHECK (rectify_way IS NULL OR rectify_way <> 'AMENDMENT' OR amendment_id IS NOT NULL);

-- 组合约束 4：误报不能还挂着待整改状态。
ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_false_pos_status
    CHECK (is_false_positive = FALSE OR status IN ('WAIVED', 'CONFIRMED_OK'));

-- 组合约束 5：豁免必须留审批链。
ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_waive_combo
    CHECK (status <> 'WAIVED'
           OR (waive_reason IS NOT NULL
               AND waiver_approved_by IS NOT NULL
               AND waiver_approved_at IS NOT NULL));

-- 组合约束 6：复核必须留复核人与复核时刻。
ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_recheck_combo
    CHECK (status <> 'CONFIRMED_OK' OR (recheck_at IS NOT NULL AND recheck_by IS NOT NULL));

-- 组合约束 7：自动缺陷必须有规则来源，人工缺陷必须没有。
ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_rule_source
    CHECK ((is_manual = TRUE AND rule_id IS NULL AND rule_code IS NULL)
           OR (is_manual = FALSE AND rule_code IS NOT NULL));

-- 组合约束 8：人工登记与检出方式一致。
ALTER TABLE m18_qc_defect
    ADD CONSTRAINT ck_m18_qc_defect_manual_consistent
    CHECK ((is_manual = TRUE AND detect_source IN ('MANUAL', 'IMPORT'))
           OR (is_manual = FALSE AND detect_source = 'AUTO'));
```

**这八个组合约束各自防的真实错误**

| # | 约束 | 只写单字段约束会漏掉什么 | 真实后果 |
|---|---|---|---|
| 1 | `ck_m18_qc_defect_rectified_evidence` | 状态改成 `RECTIFIED` 但 `rectified_at` 为空 | 整改人次月考核时算不出整改时长；医务科抽查时无法追溯到人 |
| 2 | `ck_m18_qc_defect_rectify_combo` | 有状态没方式 | 「整改了」但不知道是补写了文书还是作废重开，病案室无法核对归档件 |
| 3 | `ck_m18_qc_defect_amendment_ref` | `rectify_way = 'AMENDMENT'` 但 `amendment_id` 为空 | 声称走了更正记录，实际病历上没有任何更正，等于缺陷被伪造关闭 |
| 4 | `ck_m18_qc_defect_false_pos_status` | 误报还挂在 `OPEN` | 误报会继续出现在待办列表与超期统计里，质控员每天看到同一批假缺陷，最终会关掉此类告警 |
| 5 | `ck_m18_qc_defect_waive_combo` | 豁免无审批 | 医生与质控员私下就能「豁免」任何缺陷，质控形同虚设 |
| 6 | `ck_m18_qc_defect_recheck_combo` | 复核无复核人 | 整改由提出整改的人自己确认通过，闭环变成自证 |
| 7 | `ck_m18_qc_defect_rule_source` | 自动缺陷没有 `rule_code` | 无法回答「这条缺陷是依据哪条规则判的」，申诉时无法举证 |
| 8 | `ck_m18_qc_defect_manual_consistent` | `is_manual` 与 `detect_source` 互相矛盾 | 报表里「人工缺陷占比」会算错，掩盖规则覆盖不足 |

**「同一缺陷被多个位置命中算几次」——本表最关键的一条设计**

这是整个质控评分里最容易出错的地方，必须先把它写死。

**判据：按 `(qc_task_no, defect_code, defect_object)` 去重，重复命中累加 `occur_count`，不新增行。**

数据结构设计汇总 §7.3 已经把这个唯一约束登记了，本节说明它为什么必须是这样：

| 方案 | 「主诉缺时长」这条规则在一份病历里命中 5 处时的结果 | 问题 |
|---|---|---|
| **每个位置一条缺陷**（不考虑重） | 5 条 `MINOR` → 扣 `5 × 2 = 10` 分 | 一份病历的**一类**问题直接把分数打掉 10 分；10 分意味着从甲级（≥90）掉到乙级（<90）。**问题是「主诉未按规范书写」，不是「主诉未按规范书写了五次」** |
| **按缺陷码全局去重** | 1 条 `MINOR` → 扣 2 分 | 丢掉了位置信息，页面无法告诉医生「到底哪五处」，医生根本无从整改 |
| **按 `(defect_code, defect_object)` 去重 + `occur_count` 计数**（本方案） | 1 条 `MINOR` → 扣 2 分，`occur_count = 5`，`occur_positions` 存 5 个位置 | 扣分口径符合质控语义；页面上显示「主诉缺失（共 5 处）」，医生点开能看到五处位置 |

**算例（必须与总纲 `M18-CALC-02` 的算例对齐）：**

某住院病历命中 1 处 `MAJOR` + 3 处 `MINOR`，且其中「主诉缺时长」这一条 `MINOR` 在病历里出现了 5 次。

```
缺陷码                    等级      缺陷对象                  occur_count   参与扣分的份数
DEF_TIME_POSTOP_FIRST     MAJOR     RECORD:SELF               1             1  → 扣 5
DEF_COMPL_CHIEF_DURATION  MINOR     SECTION:CHIEF_COMPLAINT   5             1  → 扣 2
DEF_LOGIC_DIAG_NO_SIDE    MINOR     FIELD:eye_side            1             1  → 扣 2
DEF_COMPL_PLAN_NO_DOSE    MINOR     FIELD:dose                1             1  → 扣 2
────────────────────────────────────────────────────────────────────────────────────
deduction = 5 + 2 + 2 + 2 = 11
qc_score  = max(0, 100 - 11) = 89.0  → GRADE_B（乙级）
```

**若误把 3 个 `MINOR` 当成 1 个去重**（比如误按 `defect_level` 去重）：

```
deduction = 5 + 2 = 7
qc_score  = 93.0  → GRADE_A（甲级）   ← 错判，把乙级病历报成了甲级
```

甲级病历率是医院等级评审的公示指标。**这个错误不会报错、不会告警，只会让上报的甲级率系统性偏高**——而它一旦被评审组抽查发现，就是数据造假。所以三条防线缺一不可：数据库唯一约束 `uk_m18_qc_defect` 拦住重复行、应用层按 `defect_code` 分组累加、验收用例 AC-03 专门复现这个算例。

**为什么 `defect_object` 要参与去重键，而不是只用 `defect_code`**

举一个眼科的真实例子：「诊断未标注眼别」这条规则。一份病历主诊断写了「老年性白内障」（缺眼别），同时**另一条**合并诊断写了「糖尿病视网膜病变」（也缺眼别）。这两处是**两个不同的缺陷对象**——第一个是主诊断，第二个是合并诊断，整改时医生要分别补两个眼别。

- 只用 `defect_code` 去重 → 合并成 1 条，医生补完主诊断的眼别就以为改完了，合并诊断仍然缺眼别，而且**不会再被提示**。
- 用 `(defect_code, defect_object)` → 两条，`defect_object` 分别是 `DIAGNOSIS:primary` 与 `DIAGNOSIS:secondary:2`，两条都会被跟踪到闭环。

而如果规则命中在**同一段落内的多个偏移量**（如主诉段落里 5 处没写时长），它们共享同一个 `defect_object = 'SECTION:CHIEF_COMPLAINT'`，因此归并为 1 条、`occur_count = 5`——这正是上面算例里的情形。

**一句话判据：`defect_object` 回答「改哪里」，`occur_count` 回答「有几处」。同一处改一次就够了，所以按 `defect_object` 去重；不同处要分别改，所以 `defect_object` 必须区分。**

**为什么本表不分区**

数据结构设计汇总 §4 把「质控与审核记录」整体标为月分区，但本表是本子模块里唯一**不应**分区的质控表，理由与汇总 §4 对病历主表的判断同源：

1. **分区表的唯一约束必须包含分区键。** 本表的核心约束是 `uk_m18_qc_defect (qc_task_no, defect_code, defect_object)`——这三列没有一个叫 `created_at`。若把 `created_at` 塞进唯一键，约束语义就从「同一任务同一对象同一缺陷只记一次」退化为「同一任务同一对象同一缺陷在同一个月内只记一次」，跨月重跑就又能插进重复行，**「同一缺陷算几次」立刻失控**。
2. **本表查询总是带精确条件。** P04 详情页按 `record_id`、P09 待办按 `(status, due_date)`、评分按 `qc_task_no`——没有一个是时间范围扫描。`idx_m18_qc_defect_code_period` 这类统计索引本身已包含 `created_at`，分区带来的扫描裁剪收益很小。
3. **分区带来的运维成本却是实打实的。** 月分区需要预建任务；年增 60 万行、3 年 180 万行 ≈ 0.5 GB，单表完全可承受。

因此：**`m18_qc_task` 与 `m18_qc_medication_review` 分区（它们的唯一键都含 `created_at`，见各自章节），`m18_qc_defect` 不分区。** 这个取舍已在本章 4.1 的「ER 图三个设计取舍」表里登记，也需在详细设计 §7.3 的分区预建任务里明确「不为 `m18_qc_defect` 建分区」。

### 4.5 表：`m18_qc_score`（质控评分表）

**用途：** 记录一份病历在某一次质控任务下的最终评分与等级——基础分、累加扣分、最终得分、等级、是否有 `CRITICAL`、各等级缺陷各几个、按质控类型的扣分分布。

**写入方：** M18-05 评分器（任务结束前写入）、P05 质控评分与等级（人工改判缺陷等级后重算）。 **只读方：** P01 质控工作台、P05、M22 报表（甲级病历率）、M18-07 病案统计。

**为什么评分单独成表，而不是在 `m18_qc_task` 上挂几列平均值**

`m18_qc_task` 是一次**批跑**（一张任务表里 `target_count` 可能是 200 份病历），而评分是**每份病历一行**。两者是 1:N。把评分压在任务表上，就只能存 `score_avg`（平均值），存不下「这 200 份分别是多少分、几份甲级几份乙级」。而「甲级病历率」这个指标的分母与分子都要靠逐份评分才能算出来。

另外两者生命周期不同：任务跑完就定稿，评分却会因为人工改判缺陷等级（如总纲算例里「诊断缺侧别」被从 `MINOR` 改判为 `MAJOR`）而重算，需要 `score_version` 与审计留痕。

**约束说明**

```sql
ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_level
    CHECK (qc_level IN ('GRADE_A', 'GRADE_B', 'GRADE_C'));

-- 扣分上界取 500 而不是 100：deduction 是「问题总量」（各类扣分之和），
-- 一份病历若有 25 处 MAJOR，deduction = 125.0，qc_score 由 ck_m18_qc_score_final 取 GREATEST(0.0, ...) 兜底。
-- 若把 deduction 卡在 100，要么拒绝合法数据，要么写库前截断，「这份病历扣了 125 分」的事实就丢了。
ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_range
    CHECK (qc_score >= 0 AND qc_score <= 100 AND deduction >= 0 AND deduction <= 500);

-- 组合约束 1：数据结构设计汇总 §7.2 已登记原文。丙级必须有依据。
ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_grade_c_reason
    CHECK (qc_level <> 'GRADE_C' OR qc_score < 75 OR has_critical = TRUE);

-- 组合约束 2：丙级之外不可能是丙级——反过来也要挡住「有 CRITICAL 却给了甲乙级」。
ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_critical_not_passed
    CHECK (has_critical = FALSE OR qc_level = 'GRADE_C');

-- 组合约束 3：等级与分数的对应关系，甲乙级的边界必须自洽。
ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_grade_a_bound
    CHECK (qc_level <> 'GRADE_A' OR (qc_score >= 90 AND has_critical = FALSE));

ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_grade_b_bound
    CHECK (qc_level <> 'GRADE_B' OR (qc_score >= 75 AND qc_score < 90 AND has_critical = FALSE));

-- 组合约束 4：三个分项扣分之和必须等于总扣分（CRITICAL 不参与累加，故可精确核对）。
ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_deduction_sum
    CHECK (deduction = deduction_major + deduction_minor + deduction_hint);

-- 组合约束 5：分项扣分与各等级缺陷数的乘积必须一一对应，否则「数了 3 个 MINOR 却扣了 2 分」这种错无法察觉。
ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_major_math
    CHECK (deduction_major = major_count * 5.0);

ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_minor_math
    CHECK (deduction_minor = minor_count * 2.0);

ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_hint_math
    CHECK (deduction_hint = hint_count * 0.5);

-- 组合约束 6：最终得分必须等于基础分减扣分且不小于 0（下限截断）。
ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_final
    CHECK (qc_score = GREATEST(0.0, base_score - deduction));

-- 组合约束 7：has_critical 必须与 critical_count 一致。
ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_critical_flag
    CHECK ((has_critical = TRUE AND critical_count >= 1)
           OR (has_critical = FALSE AND critical_count = 0));

-- 组合约束 8：人工改判等级必须留痕。
ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_manual_level
    CHECK (is_auto_graded = TRUE
           OR (manual_level_reason IS NOT NULL
               AND manual_level_by IS NOT NULL
               AND manual_level_at IS NOT NULL));

-- 组合约束 9：锁定必须留时刻。
ALTER TABLE m18_qc_score
    ADD CONSTRAINT ck_m18_qc_score_lock_combo
    CHECK (qc_locked = FALSE OR locked_at IS NOT NULL);
```

**为什么 `CRITICAL` 的扣分是 100.0 而不是 0，且不参与累加**

`m18_qc_rule` 里 `CRITICAL` 规则的 `deduction_score` 被约束为恒等于 `100.0`（见 4.2 的 `ck_m18_qc_rule_level_score`），而本表的 `deduction` 又明确不含 `CRITICAL`。这个看似矛盾的设计有两层理由：

1. **不参与累加**：总纲 `M18-CALC-02` 的原公式是「`CRITICAL` → 直接判 `GRADE_C`（不参与累加，一票否决）」。若让 `CRITICAL` 也参与累加，`100 - 100 = 0` 与「扣 11 分得 89 分」会同时出现在报表里，前者会让「平均分」被严重拉低，掩盖其他人的真实水平。
2. **规则表里仍填 100.0**：如果规则表里 `CRITICAL` 的扣分填 0，那么「按扣分排序看最严重的规则」这个运维视图里，最致命的规则会排在最末尾——质控员在 P06 规则维护页面上按扣分降序排查规则配置时，会漏掉全部 `CRITICAL` 规则。填 100 表达的是「这条规则足以把任何病历压到 0 分」，语义正确；而**评分器靠 `has_critical` 这个布尔列显式忽略它**，不靠数值推断。

**`ck_m18_qc_score_deduction_sum` 之所以能写成等式**，正是因为 `CRITICAL` 被排除在 `deduction` 之外——否则 `deduction` 里混入一个 100.0 的项，等式就不成立。**这条 CHECK 是「实现者有没有真的按公式算」的机器化证明**：只要有人图省事把 `CRITICAL` 也加进 `deduction`，`SUM` 立刻对不上，插入直接失败。这比写一百字注释有效。

**三个分项乘积约束（`ck_m18_qc_score_major_math` 等）为什么必要**

没有它们，`major_count` 与 `deduction_major` 是两个各自可写的列，实现者很可能在算 `deduction` 时用了 `major_count`，在展示时改了 `major_count` 却忘了同步 `deduction_major`，页面上就会出现「3 个 MAJOR 扣 10 分」。这类不一致在任何一次数据核对里都要花半天定位。

**算例（复现总纲 `M18-CALC-02`）：**

```text
情形一：1 处 MAJOR + 3 处 MINOR（总纲原例）
  base_score        = 100.0
  major_count       = 1   → deduction_major = 1 × 5.0  = 5.0
  minor_count       = 3   → deduction_minor = 3 × 2.0  = 6.0
  hint_count        = 0   → deduction_hint  = 0 × 0.5  = 0.0
  deduction         = 5.0 + 6.0 + 0.0 = 11.0
  qc_score          = GREATEST(0.0, 100.0 - 11.0) = 89.0
  has_critical      = FALSE
  qc_level          = GRADE_B（89.0 < 90 且 >= 75，无 CRITICAL）
  ── 校验 ck_m18_qc_score_deduction_sum：11.0 = 5.0 + 6.0 + 0.0 ✓
  ── 校验 ck_m18_qc_score_grade_b_bound：89.0 >= 75 且 < 90 ✓

情形二：同上，但「诊断缺侧别」被人工改判为 MAJOR（总纲第二例）
  major_count       = 2   → deduction_major = 2 × 5.0  = 10.0
  minor_count       = 2   → deduction_minor = 2 × 2.0  = 4.0
  deduction         = 10.0 + 4.0 = 14.0
  qc_score          = 86.0  → GRADE_B
  is_auto_graded    = FALSE，manual_level_reason 必填

情形三：存在 1 处 CRITICAL（手术记录未签名）
  critical_count    = 1   → has_critical = TRUE
  deduction         = 0（或上例的 14.0，不含 CRITICAL）
  qc_score          = 86.0（分数仍显示 86.0）
  qc_level          = GRADE_C
  ── 校验 ck_m18_qc_score_grade_c_reason：GRADE_C 时 has_critical = TRUE ✓
  ── 校验 ck_m18_qc_score_critical_not_passed：has_critical = TRUE 时必须 GRADE_C ✓
  注意：86 分的丙级病历。这正是组合约束存在的理由——
        没有它，会出现「92 分却判丙级」或「86 分判乙级但实际有 CRITICAL」两种无法向医生解释的结果。

情形四：扣分超过 100（罕见但必须定义）
  假设 major_count = 25 → deduction_major = 125.0
  ck_m18_qc_score_range 允许 deduction 到 500，因此 125.0 可以落库
  qc_score = GREATEST(0.0, 100.0 - 125.0) = 0.0
  下限 0 的截断由 ck_m18_qc_score_final 的 GREATEST 保证，不出现负数；
  deduction 仍保留 125.0，「这份病历扣了 125 分」的事实不丢失
```

**为什么 `qc_locked` 必须有**

归档批次确认后，病案统计要出「本月甲级病历率」并上报。如果已归档病历的评分还能因为一次重跑而改变，那么 1 号报出去的数字和 15 号报出去的数字会对不上，而且**改的是已经上报的月份**。锁定之后重跑只能产生新的任务与评分行（`uk_m18_qc_score_task_record` 不冲突），但统计口径明确取「归档时锁定的那份」。

### 4.6 表：`m18_qc_medication_review`（用药审核记录表 · 月分区）

**用途：** 记录**每一次** `P-08 POST /internal/v1/kb/medication-check` 调用的完整结果快照——调用方是谁、什么场景、审了哪些药、当时用的规则版本集合、综合审核结论、命中了几条规则、几条提示、是否降级。**这是「同一张处方，开方时和审方时必须得到同一结果」这条判据唯一可复现的依据。**

**写入方：** M18-05 用药审核引擎（每次 P-08 调用成功后异步落库）。 **只读方：** P07 用药审核记录、P08 处方点评、M14-06 处方审核（复核时比对）、M22 报表、医务科申诉核查。

**为什么每次调用都要落一条记录——而且必须是异步落**

这是本表最重要的一条设计判断。

**先看如果只记录「命中的提示」会漏掉什么。** 一张 5 个药的处方，8,000 条规则跑下来一条都没命中，结论 `PASS`。这个「什么都没发生」的事实对事后核查极其重要：

- 药师审方时看到「无提示」，医生开方时也看到「无提示」，两边一致——**但一致性本身需要一个证据**。若只记录命中行，两次都是空集，空集等于空集，「一致」与「两次都没跑」在数据上完全无法区分。
- 规则升级后要做回溯分析（「新规则能多发现多少问题」），必须知道旧规则下**哪些处方是审过且通过的**，否则分母无从算起。

**再看为什么要异步落。** P-08 的预算是 **P95 ≤ 300ms**。审核本身在内存里只要 15ms，但插一条 600 字节的记录到分区表、更新索引，实测在 3~8ms 之间波动，而 PostgreSQL 的 WAL 刷盘尖峰偶尔会到 30ms 以上。**把落库放进关键路径，等于让「数据库抖动」直接变成「开处方变慢」**——医生每开一张处方都要等这一次插入。

因此：**P-08 同步返回审核结果，记录通过本地消息表（outbox）异步落库**。这带来一个必须正视的问题：**进程在返回结果之后、落库之前崩溃，会丢一条审核记录**。取舍如下：

| 方案 | 300ms 预算 | 记录完整性 | 结论 |
|---|---|---|---|
| 同步插入后返回 | 抖动直接暴露给医生 | 完整 | ✗ 不可接受，P-08 的 300ms 是硬约束 |
| **异步落库 + outbox 重投** | 只受内存匹配影响 | 进程崩溃时依赖 outbox 补偿；outbox 与审核在同一进程，极端情况下仍可能丢 | ✅ 采用，并在 §11.4 监控「落库缺口率」 |
| 只记命中、不记未命中 | 影响小 | 无法证明「两次都没命中」的一致性 | ✗ 判据无法兑现 |
| 记到 Redis 再定期刷盘 | 最快 | Redis 丢数据即丢记录；且要额外的持久化运维 | ✗ 引入第二套存储，且 Redis 不是审计级存储 |

**结论：异步 + outbox + 缺口率监控。** 缺口率长期应低于 0.01%；若持续高于此值说明 outbox 逻辑有 bug 而非偶发崩溃，需告警。

**约束说明**

```sql
ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_result
    CHECK (check_result IN ('PASS', 'WARN', 'BLOCK', 'DEGRADED'));

ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_scene
    CHECK (check_scene IN ('PRESCRIPTION', 'DISPENSE_REVIEW', 'RX_REVIEW', 'INPATIENT_ORDER', 'RETRO'));

ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_rule_source
    CHECK (rule_source IN ('MEMORY', 'SNAPSHOT', 'DEGRADED'));

ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_status
    CHECK (review_status IN ('COMPLETED', 'PARTIAL', 'DISCARDED'));

ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_counts
    CHECK (matched_rule_count >= 0 AND alert_count >= 0 AND block_count >= 0
           AND severe_count >= 0 AND warn_count >= 0 AND info_count >= 0 AND drug_count >= 0);

-- 组合约束 1：【最关键】四值语义必须自洽。degraded 与 check_result 不能各说各话。
ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_degraded_sync
    CHECK ((degraded = TRUE AND check_result = 'DEGRADED' AND degraded_reason IS NOT NULL)
           OR (degraded = FALSE AND check_result <> 'DEGRADED' AND degraded_reason IS NULL));

-- 组合约束 2：BLOCK 结论必须有 BLOCK 级提示支撑，且 block_flag 必须为真。
ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_block_sync
    CHECK ((check_result = 'BLOCK' AND block_count >= 1 AND block_flag = TRUE)
           OR (check_result <> 'BLOCK' AND block_count = 0 AND block_flag = FALSE));

-- 组合约束 3：WARN 结论必须至少有一条 WARN 或 SEVERE 级提示。
ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_warn_sync
    CHECK (check_result <> 'WARN' OR (warn_count + severe_count) >= 1);

-- 组合约束 4：PASS 结论意味着一条提示都没有（包括 INFO）。
ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_pass_sync
    CHECK (check_result <> 'PASS' OR alert_count = 0);

-- 组合约束 5：降级结论不得伴随任何提示，也不得有命中的规则。
ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_degraded_empty
    CHECK (check_result <> 'DEGRADED' OR (alert_count = 0 AND matched_rule_count = 0));

-- 组合约束 6：提示条数的分项之和必须等于总数 —— 五个计数列必须彼此对得上。
ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_alert_sum
    CHECK (alert_count = block_count + severe_count + warn_count + info_count);

-- 组合约束 7：命中规则数不可能大于提示条数（一条规则至少产生一条提示）。
ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_rule_le_alert
    CHECK (matched_rule_count <= alert_count);

-- 组合约束 8：回溯试算必须能被识别，且必须带批次号。
ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_retro_combo
    CHECK ((is_retro_calc = TRUE AND retro_batch_no IS NOT NULL)
           OR (is_retro_calc = FALSE AND retro_batch_no IS NULL));

-- 组合约束 9：规则来源与降级必须一致。
ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_rule_degraded
    CHECK ((degraded = TRUE AND rule_source = 'DEGRADED')
           OR (degraded = FALSE AND rule_source IN ('MEMORY', 'SNAPSHOT')));

-- 组合约束 10：婴幼儿月龄只在年龄 < 2 时有意义。
ALTER TABLE m18_qc_medication_review
    ADD CONSTRAINT ck_m18_qc_med_review_age_combo
    CHECK (age_months IS NULL OR (age IS NOT NULL AND age < 2));
```

**`check_result` 四值的语义——本子模块最重要的一张表**

| 值 | 含义 | 触发条件 | 调用方应当怎么反应 | 落库的 `degraded` |
|---|---|---|---|---|
| `PASS` | 审过了，没问题 | 规则完整跑完，`alert_count = 0` | 正常开方 | `FALSE` |
| `WARN` | 审过了，有问题但不阻断 | 最高级别为 `SEVERE` 或 `WARN`（或仅 `INFO`） | 展示提示，医生确认后可继续 | `FALSE` |
| `BLOCK` | 审过了，不准开 | 存在 `alert_level = 'BLOCK'` 的提示 | 阻断，需上级医师或药师介入 | `FALSE` |
| `DEGRADED` | **没审成** | RuleSet 未就绪 / 为空 / 匹配超时 / 上下文缺失 | 走本地基础校验，并按降级策略记录 | `TRUE` |

**为什么降级必须返回 `DEGRADED` 而不是 `PASS`、也不是错误码——这是本子模块与 M07-05 之间最关键的一条契约**

M07-05 的降级原文是「M18 合理用药知识库 → 仅做本地基础校验（过敏/剂量），记录告警」。两种错误做法各自的后果：

- **返回 `PASS`（假通过）**：医生看到「审核通过」的绿色标记，会认为系统已经用 8,000 条规则查过一遍。实际上一条都没查。**这是本子模块最危险的失败模式**——它不是「服务挂了」（挂了会被发现），而是「服务看起来好好的，但实际上什么都没做」。过敏拦截静默失效正是这一类。
- **返回非 0 错误码（HTTP 5xx 或业务码）**：M07-05 会把整次调用当作失败，转而在**更宽松**的路径上继续 ——因为它自己的降级逻辑是「M18 不可用 → 只做本地基础校验」。此时医生的体验是「系统卡了一下然后让我继续开」，比 `DEGRADED` 更糟，因为医生完全不知道发生了什么。

**返回 `code: 0` + `check_result: "DEGRADED"` + `degraded: true` + 空 `alerts`**，让调用方能明确区分「这次审过了」与「这次没审」，并据此决定是否阻断、是否提示医生、是否上报。这就是共享规范 §8 已定死的契约，本表的 `ck_m18_qc_med_review_degraded_sync` 与 `ck_m18_qc_med_review_degraded_empty` 两条组合约束把它钉在数据库层。

**过敏数据从哪来——与 U-07 废除的对接**

共享规范 V1.1 已废除 U-07（`GET /internal/v1/mpi/patients/{patient_id}/allergy`，M03-01 上并不存在该路径）。过敏史明细的权威表是 M18-02 定义的 **`m18_opd_allergy_detail`**，`mpi_patient.allergy_history` 是等 M18 用事件去刷的派生冗余字段，**M18-05 不读它**。

本子模块的取数规则（详细设计的 §3.4 与 §8.4 会给出同一套规则）：

```text
allergy_effective = allergen_code_set(调用方传入 allergy_codes) ∪ allergen_code_set(M18-02 有效过敏明细)
                   其中「有效」= allergy_status = 'ACTIVE'
                   若调用方还传了 allergen_generic_code 或 cross_allergy_codes，一并并入

allergy_source = 'MERGED'  若两边都非空
               = 'CALLER'  若只有调用方传入
               = 'LOCAL'   若只有本库明细
               = 'NONE'    若两边都空
```

**为什么取并集而不是以某一方为准：**

- **以调用方为准** → 调用方（M07-05）若因为上游超时漏传了一条过敏，过敏拦截就漏了这一条，而且 `allergy_source = 'CALLER'` 显示一切正常。**漏审不会报错。**
- **以本库为准** → 医生刚刚在本院门诊新登记了一条过敏（`m18_opd_allergy_detail` 已写入），但调用方缓存里还没有，此时以本库为准是对的；可如果**患者在别家医院的过敏史通过区域平台推送过来、走了调用方通道**，以本库为准就会漏。
- **取并集** → 两边的任何一条都不会漏，代价是可能多提示一条「已在本地排除但对方仍在传」的过敏。**多提示的代价是医生多点一次确认，漏审的代价是患者过敏休克。** 这个代价不对称，所以必须取并集，并由 `allergy_source` 记录实际来源。

**`missing_context` 与 `degraded` 的分工**

这两个字段回答的是两个不同的问题：

- `degraded = TRUE` 回答「**这次审核整体可不可信**」——不可信就是不代信，调用方必须知道。
- `missing_context` 回答「**这次审核缺了哪些条件，所以哪些规则跳过没跑**」——审核可能整体仍然可信（大多数规则不需要这些条件），但医生与事后核查需要知道覆盖面。

举例：一张眼科处方，调用方没传 `is_pregnant` 与 `renal_level`。此时：

- 妊娠禁忌规则与肾功能剂量规则**无法求值**，必须跳过；
- 其余 7,000 多条规则照常跑，若命中 1 条 `WARN` → `check_result = 'WARN'`、`degraded = FALSE`；
- `missing_context = ["is_pregnant","renal_level"]` 忠实记录这两类规则没跑。

**这里不做 `DEGRADED` 的理由是**：眼科局部滴眼液的全身暴露量极小，绝大多数品种的妊娠与肾功能分级不影响判定；若因为调用方没传妊娠状态就把整次审核降级，等于把 7,000 条规则的结论全部作废。**但若缺失的是 `allergy_codes` 且本库也查不到过敏明细，则必须 `DEGRADED`（`CONTEXT_MISSING`）**——过敏是唯一一条「缺了就一定不能算审过」的上下文。

**分区策略**

`m18_qc_medication_review` 采用月分区，与 `m18_qc_task` 同一套机制：

```sql
CREATE TABLE m18_qc_medication_review (
    id                BIGINT GENERATED BY DEFAULT AS IDENTITY,
    review_no         VARCHAR(32) NOT NULL,
    trace_id          VARCHAR(64) NOT NULL,
    check_result      VARCHAR(16) NOT NULL,
    rule_version_set  VARCHAR(64) NOT NULL,
    created_at        TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE m18_qc_medication_review_p202610 PARTITION OF m18_qc_medication_review
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

CREATE TABLE m18_qc_medication_review_p202611 PARTITION OF m18_qc_medication_review
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

CREATE TABLE m18_qc_medication_review_p202612 PARTITION OF m18_qc_medication_review
    FOR VALUES FROM ('2026-12-01') TO ('2027-01-01');

CREATE TABLE m18_qc_medication_review_default PARTITION OF m18_qc_medication_review
    DEFAULT;
```

**为什么这张表必须分区，而缺陷表不分：**

| | `m18_qc_medication_review` | `m18_qc_defect` |
|---|---|---|
| 核心唯一键 | `(review_no)`，加 `created_at` 后语义不变（单号本身已含日期） | `(qc_task_no, defect_code, defect_object)`，**加 `created_at` 会让去重语义失效** |
| 查询方式 | 高频按时间范围聚合（「本月审核量」「某规则版本上线后 7 天的 WARN 率」） | 总是按 `record_id` / `status` / `qc_task_no` 精确查 |
| 保留策略 | 只保留 3 年在线，更早 `DETACH PARTITION` 到只读库 | 与任务共存亡，归档策略随任务 |
| 年增行数 | 45 万，3 年 135 万 ≈ 0.8 GB | 60 万，3 年 180 万 ≈ 0.5 GB |

**关键差异在第二行**：分区对「按时间范围扫描」有裁剪收益，对「按精确条件查」收益很小，而 `m18_qc_defect` 的核心约束又会因为分区键而失效。**「能不能分区」不是一个风格问题，取决于这张表的唯一约束与查询模式长什么样。**

**DEFAULT 分区不是可选项。** 与 `m18_qc_task` 同一理由：若 2027-01 的分区还没预建而新年第一秒就有审核记录写入，没有 DEFAULT 分区时 INSERT 直接失败——而这次 INSERT 是**异步落库**，失败不会让医生看到报错，只会让那条审核记录静默消失。**DEFAULT 分区把「任务漏跑」从「数据丢失」降级为「数据进了 default 分区」，并触发告警。**

### 4.7 表：`m18_qc_med_alert_hit`（用药审核提示明细表）

**用途：** 把一次用药审核（`m18_qc_medication_review`）命中的每一条提示拆开存——哪条规则、哪个药、提示级别、标题、说明、建议、循证依据、是否需要医生确认。**这是 P-08 响应里 `alerts` 数组的落库形态。**

**写入方：** M18-05 用药审核引擎（与 `m18_qc_medication_review` 在同一事务内写入）。 **只读方：** P07 用药审核记录、P08 处方点评、M14-06 审方复核、M22 报表（规则命中率）、M18-08 规则调优（误报率反查）。

**为什么提示不内嵌成 `m18_qc_medication_review` 的一个 JSONB 列**

这是本子模块里一个必须论证的取舍，因为内嵌 JSONB 看起来更简单。

| | 内嵌 JSONB（`alerts` 一列搞定） | 独立表（本方案） |
|---|---|---|
| 写入 | 一次 INSERT | 父表 1 行 + 子表 N 行，**必须在同一事务** |
| 「某条规则本月命中多少次」 | `jsonb_array_elements` 展开，走不了索引，45 万行表上每次扫 2~8 秒 | `GROUP BY rule_code`，走 `idx_m18_qc_alert_rule_period`，毫秒级 |
| 「哪条规则误报率最高」 | 与 `m18_qc_defect.is_false_positive` 无处关联 | 提示明细行可被标记 `is_false_positive`，直接统计 |
| 「把这个药加了黑名单，会影响多少历史提示」 | 全表展开扫描 | 按 `drug_code` 索引直接数 |
| 单条提示被药师复核（确认 / 驳回） | 需要重写整个 JSONB，有并发覆盖风险 | 按 `id` 更新一行，无风险 |

**结论：独立成表。** 代价是「两次写入必须放同一事务」，这个代价换来的是一整类运维查询从不可做变成可做。**注意这也正是「一条规则命中多个药品时只产生一条提示」这个去重规则的落地位置**——`uk_m18_qc_alert_rule_drug` 把它钉在数据库上。

**`uk_m18_qc_alert_rule_drug` 为什么是 `(review_id, rule_code, drug_code)` 而不是 `(review_id, rule_code)`**

总纲原文说「一条规则命中多个药品时只产生一条提示（`rule_code + drug_code` 为提示的唯一键）」，这句话容易被误读成「一条规则一次审核只出一条提示」。两者不同：

**算例：一张处方开了三种喹诺酮类（左氧氟沙星、加替沙星、莫西沙星）。**

「重复用药」规则命中，情况是：这三种药**每个都与其他两个构成重复**。

| 去重键 | 结果 | 问题 |
|---|---|---|
| `(review_id, rule_code)` | 1 条提示，`drug_code` 只能填其中一个 | 医生只看到「加替沙星重复用药」，会误以为左氧不是重复的，只删一个药，处方仍然重复 |
| `(review_id, rule_code, drug_code)`（本方案） | 3 条提示 | 多，但每条都指向具体药品 |
| 按规则 × 药对展开 | 3 对（左-加、左-莫、加-莫）= **6 条** | 医生会看到 6 条近乎重复的提示，直接把这些提示一并跳过 |

**所以「一条规则命中多个药品时只产生一条提示」的准确含义是「不按药对展开」，而不是「不按药区分」。** 三种药 × 一条规则 = 3 条（按 `drug_code` 去重），而不是 6 条（按药对展开）。总纲这句话与唯一键 `(rule_code, drug_code)` 完全一致，本节把这个歧义在此钉死，并写进 §8.2 的唯一性规则。

**为什么 `alert_seq` 必须由服务端按确定顺序编号**

P-08 的响应是有序数组，医生从上往下读。若两次调用（开方时、审方时）返回的顺序不同，即使内容完全相同，肉眼比对也会觉得「结果变了」。因此：**先按 `alert_level` 严重度降序（`BLOCK` > `SEVERE` > `WARN` > `INFO`），同级别按 `rule_code` 字典序升序，再按 `drug_seq` 升序**，序号在内存里一次算好并落库。审方侧比对时比对的是这个确定的序列。

### 4.8 表：`m18_qc_med_rule`（用药规则执行镜像表）

**用途：** 把 M18-08 知识库里的 `m18_kb_med_rule` 规则**镜像一份到本子模块**，作为内存 RuleSet 的加载源与版本核对依据。它回答的是「这次审核到底加载了哪些规则、各是什么版本」。

**写入方：** M18-05 规则装载器（启动加载、热重载、每日版本核对时写入或更新）。 **只读方：** M18-05 审核引擎（只从内存 RuleSet 读，本表用于装载与核对）、P06 用药审核规则页面（只读展示，编辑跳转 M18-08）。

> **这张表不是规则的第二个权威，而是一个「装载契约 + 版本快照」。** 规则的增删改一律在 M18-08 的 `m18_kb_med_rule` 里进行（它经过草稿 → 审核 → 发布的流程），本表只做单向镜像。**M18-05 的任何代码都不允许写规则内容到本表以外的权威位置，也不允许本表的内容反向覆盖 `m18_kb_med_rule`。** 详见 1.3 的命名边界论证。

**为什么需要镜像，而不是每次启动直接读 `m18_kb_med_rule`**

| 问题 | 直接读 M18-08 表 | 镜像（本方案） |
|---|---|---|
| 内存 RuleSet 的加载契约 | `m18_kb_med_rule` 的字段会随 M18-08 演进（新增规则类型、新增条件维度），**每次改动都可能打断 M18-05 的加载器** | 本表是 M18-05 侧稳定的加载契约，`m18_kb_med_rule` 改了只需调整同步任务，不动引擎 |
| 「到底加载了哪些规则」 | 规则发布后旧版本置 `SUPERSEDED`，加载完成后表继续变化，无法回答「10:00 那次审核的 RuleSet 里有哪些规则」 | 本表带 `loaded_at`、`load_batch_no`、`rule_version_set`，**加载时刻的规则全集可快照** |
| `rule_version_set` 的可复现 | 它是一个日期集合的哈希，但「集合里到底是哪几条」在 M18-08 表里已经被 `SUPERSEDED` 覆盖掉一部分 | 每次加载写一个新的 `load_batch_no`，历史批次保留 |
| 加载耗时 | 8,000 条规则从 M18-08 的宽表读（含富文本依据、多语言名）比从这张瘦表读慢 | 本表只留规则引擎真正需要的字段，`RuleSet` 加载 ≤ 800ms 的预算更好达成 |

**约束说明**

```sql
ALTER TABLE m18_qc_med_rule
    ADD CONSTRAINT ck_m18_qc_med_rule_type
    CHECK (rule_type IN ('INTERACTION', 'DOSAGE', 'CONTRAINDICATION', 'ANTIBIOTIC_LEVEL',
                         'DUPLICATE', 'SPECIAL_DRUG', 'OPHTHALMIC_SPECIFIC'));

ALTER TABLE m18_qc_med_rule
    ADD CONSTRAINT ck_m18_qc_med_rule_level
    CHECK (alert_level IN ('BLOCK', 'SEVERE', 'WARN', 'INFO'));

ALTER TABLE m18_qc_med_rule
    ADD CONSTRAINT ck_m18_qc_med_rule_status
    CHECK (status IN ('PUBLISHED', 'SUPERSEDED', 'DISABLED'));

ALTER TABLE m18_qc_med_rule
    ADD CONSTRAINT ck_m18_qc_med_rule_sync
    CHECK (sync_status IN ('SYNCED', 'STALE', 'FAILED'));

-- 组合约束 1：severity_rank 必须与 alert_level 严格对应。
ALTER TABLE m18_qc_med_rule
    ADD CONSTRAINT ck_m18_qc_med_rule_rank_map
    CHECK ((alert_level = 'BLOCK'  AND severity_rank = 40)
        OR (alert_level = 'SEVERE' AND severity_rank = 30)
        OR (alert_level = 'WARN'   AND severity_rank = 20)
        OR (alert_level = 'INFO'   AND severity_rank = 10));

-- 组合约束 2：BLOCK 只允许用于「国家明令禁止」的场景。
-- 本约束把「哪些类型可以 BLOCK」写死，防止有人图省事把所有规则都设成 BLOCK。
ALTER TABLE m18_qc_med_rule
    ADD CONSTRAINT ck_m18_qc_med_rule_block_type
    CHECK (alert_level <> 'BLOCK'
           OR rule_type IN ('CONTRAINDICATION', 'SPECIAL_DRUG')
           OR alert_type = 'ALLERGY');

-- 组合约束 3：眼科专科规则必须带分组标签，非眼科规则必须没有。
ALTER TABLE m18_qc_med_rule
    ADD CONSTRAINT ck_m18_qc_med_rule_ophthalmic_combo
    CHECK ((is_ophthalmic = TRUE AND ophthalmic_rule_tag IS NOT NULL)
           OR (is_ophthalmic = FALSE AND ophthalmic_rule_tag IS NULL));

-- 组合约束 4：眼科规则标签取值必须属于本院四组重点配置。
ALTER TABLE m18_qc_med_rule
    ADD CONSTRAINT ck_m18_qc_med_rule_ophthalmic_tag
    CHECK (ophthalmic_rule_tag IS NULL
           OR ophthalmic_rule_tag IN ('MYDRIATIC_GLAUCOMA', 'ANTI_VEGF_ANTICOAGULANT',
                                      'STEROID_IOP', 'OK_LENS_CARE'));

-- 组合约束 5：触发条件至少要有一个非空，否则规则恒不命中（常见坑第 27 条「命中率 0%」）。
ALTER TABLE m18_qc_med_rule
    ADD CONSTRAINT ck_m18_qc_med_rule_has_trigger
    CHECK (jsonb_array_length(trigger_drug_codes) > 0
           OR jsonb_array_length(trigger_pharm_classes) > 0
           OR jsonb_array_length(trigger_ophthalmic_classes) > 0
           OR jsonb_array_length(trigger_antibiotic_levels) > 0);

-- 组合约束 6：规则条件不能是空对象，否则规则恒命中（常见坑第 27 条「命中率 100%」）。
ALTER TABLE m18_qc_med_rule
    ADD CONSTRAINT ck_m18_qc_med_rule_has_condition
    CHECK (condition_json <> '{}'::jsonb);

-- 组合约束 7：只有最新批次可以是生效批次。
ALTER TABLE m18_qc_med_rule
    ADD CONSTRAINT ck_m18_qc_med_rule_version_pos
    CHECK (rule_version >= 1);
```

**`condition_json` 的结构（规则条件表达式）**

规则条件必须是**结构化 JSON**，不是 SQL 字符串。理由与 4.2 的 `judge_expr` 相同：规则由临床药师在页面上配置，若允许写 SQL，等于给了业务人员在病历库上执行任意语句的入口。

```json
{
  "op": "AND",
  "children": [
    {"op": "DIAGNOSIS_IN", "codes": ["H40.2"]},
    {"op": "DRUG_IN_CLASS", "field": "ophthalmic_class", "values": ["MYDRIATIC_EYE"]},
    {"op": "CONTEXT_MISSING", "field": "anterior_chamber_depth", "on_missing": "SKIP_AND_RECORD"}
  ]
}
```

`op` 允许的取值（由 M18-05 求值器实现，M18-08 只负责存）：

| `op` | 语义 | 需要的上下文 |
|---|---|---|
| `AND` / `OR` / `NOT` | 逻辑组合，`children` 数组 | — |
| `DIAGNOSIS_IN` | 患者诊断集合与 `codes` 有交集 | `diagnosis_codes` |
| `DIAGNOSIS_PREFIX` | 诊断编码前缀匹配（ICD 章节级，如 `H40` 匹配全部青光眼） | `diagnosis_codes` |
| `DRUG_IN_CLASS` | 处方中任一药的某个分类字段命中 `values` | `item_snapshot[].pharmacology_class` 等 |
| `DRUG_CODE_IN` | 处方中任一药编码在 `codes` 内 | `item_snapshot[].drug_code` |
| `DRUG_COUNT_GE` | 同一分类的药品数 ≥ `n`（重复用药规则） | `item_snapshot[].pharmacology_class` |
| `AGE_GE` / `AGE_LE` / `AGE_BETWEEN` | 年龄条件 | `age` / `age_months` |
| `GENDER_IN` | 性别条件 | `gender` |
| `IS_PREGNANT` / `IS_LACTATING` | 妊娠/哺乳条件 | `is_pregnant` / `is_lactating` |
| `RENAL_LEVEL_IN` / `HEPATIC_LEVEL_IN` | 肝肾功能分级条件 | `renal_level` / `hepatic_level` |
| `DOSE_GT` / `DOSE_LT` / `DAYS_GT` | 剂量、频次、天数条件 | `item_snapshot[].dosage` / `frequency` / `days` |
| `ALLERGY_MATCH` | 处方药与该患者过敏原（含交叉过敏）匹配 | `allergy_effective` |
| `ANTIBIOTIC_LEVEL_IN` | 抗菌分级条件 | `item_snapshot[].antibiotic_level` |
| `CONTEXT_MISSING` | 特定上下文缺失时的处理策略 | 由 `field` 指定 |

`CONTEXT_MISSING` 的 `on_missing` 取值决定「缺上下文时怎么办」，**这是本子模块与「跳过还是降级」这条决策直接挂钩的地方**：

| `on_missing` | 行为 | 适用于 |
|---|---|---|
| `SKIP` | 跳过本规则，**不记** | 该项对判定影响很小 |
| `SKIP_AND_RECORD` | 跳过本规则，**记入 `missing_context`** | 默认，绝大多数情况 |
| `DEGRADE` | **整次审核降级** | 仅用于过敏：缺失过敏信息时不能算审过（详见 4.6 的论述） |

**四组眼科专科规则的镜像形态（对应 M01 `:735` 本院重点配置）**

| 标签 | 规则编码示例 | 触发 | 条件要点 | 级别 |
|---|---|---|---|---|
| `MYDRIATIC_GLAUCOMA` | `DR_OPHTH_001` | `ophthalmic_class = MYDRIATIC_EYE` | `DIAGNOSIS_PREFIX(H40)` 或有闭角型青光眼史；有前房深度时取数值判断 | `SEVERE`（诊断明确闭角型时升 `BLOCK`） |
| `ANTI_VEGF_ANTICOAGULANT` | `DR_OPHTH_002` | `ophthalmic_class = ANTI_VEGF_EYE` | 患者在用抗凝药（`DRUG_CODE_IN` + `DRUG_IN_CLASS`） | `WARN` |
| `STEROID_IOP` | `DR_OPHTH_003` | `ophthalmic_class = ANTI_INFLAMMATORY_EYE` 且 `pharmacology_class = GLUCOCORTICOID` | `DAYS_GT(14)` 或近 90 天内有重复开具记录 | `WARN` |
| `OK_LENS_CARE` | `DR_OPHTH_004` | 药品名含护理液/护理品类或 `drug_code` 在维护清单 | 患者有角膜损伤诊断（`H16` 前缀）或近期角膜病史 | `SEVERE` |

### 4.9 表：`m18_qc_rx_review`（处方点评表）

**用途：** 记录「处方点评」——从已发生的处方里**事后抽样**，由药师/质控员评判其合理性，并把评判结果与「开方时的自动审核结果」对比。总纲 §3.3 说得很清楚：**两者不一致的处方，就是知识库需要补规则的地方**。

**写入方：** M18-05 处方点评（P08 页面录入、抽样任务生成）。 **只读方：** P08、M18-08 规则调优（读取「漏审」样本作为补规则的依据）、M22 报表、医务科处方点评公示。

**为什么处方点评不能只靠自动审核记录**

自动审核只能回答「按现有规则有没有问题」。它回答不了两件事：

1. **规则没想到的问题。** 规则库是「已知的已知」，临床实践中总有规则覆盖不到的情形。点评由人来看，才能发现「这一类处方整体用药偏多」这种规则无法表达的问题。
2. **规则过严或过松。** 某条规则在 30% 的处方上都报 `WARN` 且被医生全部忽略，说明规则本身有问题。这种情况只能通过人工点评来确认。

**所以本表的核心字段是 `auto_result`（自动审核当时的结论）与 `manual_result`（人工点评结论）的对照。**

**字段定义**

| 字段名 | 类型 | 允许空 | 默认 | 说明 |

| sample_type | VARCHAR(32) | N | 'RANDOM' | 抽样方式：`RANDOM`（随机） / `TARGETED`（定向：某医生/某科室/某药） / `TRIGGERED`（触发式：自动审核被判可疑） / `COMPLAINT`（投诉/纠纷引发） / `ALL`（全查，用于专项整治） |

**为什么 `manual_result` 不用 `check_result` 那四个值**

两套枚举看起来都是「结论」，但它们的**取值空间根本不同**：

| 场景 | `check_result`（自动审核） | `manual_result`（人工点评） |
|---|---|---|
| 药开得对 | `PASS` | `REASONABLE` |
| 药基本对但可以更好（如能用更便宜的同效药） | 没有对应取值 —— 自动规则无法表达「可以更好」 | `IMPROVABLE` |
| 药开错了 | `WARN` 或 `BLOCK` | `UNREASONABLE` |
| 处方已作废，无从评判 | 没有对应取值 | `NOT_APPLICABLE` |
| 系统没审 | `DEGRADED` | 没有对应取值 —— 人的点评不会「降级」 |

**强行复用一套枚举的后果**：`IMPROVABLE` 这一档会被迫映射成 `WARN`，于是「可改进」与「有风险」混在一起，点评报告里无法区分「这批处方安全但不够经济」与「这批处方有安全隐患」。而抗菌药物管理与医保控费关心的正是前一件事。

同时必须承认：**两套枚举共存会带来一致性判断的复杂度**。本表的处理是把映射规则写死在一个地方（详细设计 §3.4.6 的映射表），并由 `inconsistency_type` 的三条组合约束（4、5）把非法组合挡在数据库外——而不是靠实现者在各处自行判断。

**`total_amount` 为什么是 `NUMERIC(14,2)` 且本表不参与任何金额运算**

字段存在的唯一目的是**处方面板的金额快照展示**，它的值来自 M07-05 处方主表或 M16 结算快照，**M18-05 不做任何加减乘除**。M18 不承担算钱职责（这与 M19-05 的结论一致：算钱的模块只能有一个）。因此本表没有「金额合计」「均次费用」这类派生列——那些是 M22 报表的职责，通过 M16 的统计接口取数。

### 4.10 表：`m18_qc_rectify`（质控整改跟踪表）

**用途：** 记录一条质控缺陷从发现到闭环的全过程——谁认领、怎么改的、改在哪、谁复核、什么时候关闭。**一条缺陷可以整改多轮**（第一次整改不合格，退回再改），所以本表与 `m18_qc_defect` 是 1:N。

**写入方：** M18-05 整改跟踪（P09 页面）、M05-05 病案缺陷整改（护理侧病历的缺陷）、系统自动（超期巡检更新 `is_overdue`）。 **只读方：** P09、P04、医务科质控报表、M22 报表。

**为什么整改要单独一张表，而不是在 `m18_qc_defect` 上加几个字段**

缺陷表已经有一组整改字段（`status`/`rectified_at`/`rectified_by`/`rectify_way`/`amendment_id`/`waive_reason`），看起来够用。但整改是**多轮**的：

**算例**：一份病历被指出「术后首次病程缺手术所见」（MAJOR）。医生第一次提交更正记录，质控员复核认为更正记录只补了一句话、仍不完整 → 退回（`RECTIFIED` → `RECTIFYING`）。医生第二次补写更完整的更正记录 → 复核通过（`RECTIFIED` → `CONFIRMED_OK`）。

**如果整改历史只存在缺陷表的字段里**，第二轮会把第一轮的痕迹全部覆盖：看不到「第一次为什么被退回」，而「被退回的理由」恰恰是质控持续改进最需要的数据（它说明整改指引描述得不清楚）。

**所以：缺陷表上那组字段是「当前状态」（读得多、写得少、要快）；本表是「整改过程流水」（逐轮追加、只增不改）。** 这也让 `rectify_rounds` 成为一个可统计的质量指标。

**整改与铁律 4 的对接：`rectify_way` 为什么只能是这四种**

铁律 4 规定「病历一经签署不可原地修改」。质控发现缺陷后，医生**不能**回去改那份已签署的病历原文。因此整改方式必须落在合法路径里：

| `rectify_way` | 含义 | 合法性依据 | 原病历 | 适用 |
|---|---|---|---|---|
| `AMENDMENT` | 追加一条更正记录 | 铁律 4 允许的第二种路径：`m18_emr_amendment` 只增不删 | **保持 `SIGNED`，原文一字不动** | 绝大多数缺陷（漏写、写错） |
| `VOID_REOPEN` | 作废重开 | 铁律 4 允许的第一种路径：`SIGNED → VOIDED`，再新建一份病历重新签 | **状态变 `VOIDED`，永久保留** | 缺陷是结构性的（如选错模板、患者身份写错、整篇不适用） |
| `SUPPLEMENT_DOC` | 补充独立文书 | 不动原病历，另出一份补充文书 | 保持 `SIGNED` | 需要独立成文的内容（补充说明、会诊意见） |
| `NO_CHANGE_NEEDED` | 核实后确认无需改 | 医生/科主任核实后认为缺陷不成立 | 不变 | 缺陷被核实为误报，但走正式流程而非直接标记误报 |

**关键点：`rectify_way = 'AMENDMENT'` 时必须真的有 `amendment_id`，且 `amend_content_hash` 必须与原病历的 `content_hash` 不同。** 这两条组合约束把「整改」钉在可核验的事实上——没有指向具体更正记录的「已整改」按钮是不允许存在的。这条规则与 `m18_emr_amendment` 的实际写入是**同一个事务的两半**：先由 M18-06 写入更正记录，拿到 `amendment_id` 与新的 `content_hash`，再写本表的整改记录。

**分区策略**

```sql
CREATE TABLE m18_qc_oper_log (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY,
    log_no        VARCHAR(32) NOT NULL,
    oper_type     VARCHAR(32) NOT NULL,
    biz_object    VARCHAR(64) NOT NULL,
    operator_id   BIGINT,
    result        VARCHAR(16) NOT NULL DEFAULT 'SUCCESS',
    created_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE m18_qc_oper_log_p202610 PARTITION OF m18_qc_oper_log
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

CREATE TABLE m18_qc_oper_log_p202611 PARTITION OF m18_qc_oper_log
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

CREATE TABLE m18_qc_oper_log_p202612 PARTITION OF m18_qc_oper_log
    FOR VALUES FROM ('2026-12-01') TO ('2027-01-01');

CREATE TABLE m18_qc_oper_log_default PARTITION OF m18_qc_oper_log DEFAULT;
```

**分区理由：** 日增约 3,000 条（规则发布、缺陷确认、配置变更、导出、重载等），年增约 110 万条，**只保留 3 年在线**（更早的按审计要求转入只读库）。按 `created_at` 月度分区后，过期数据用 `DETACH PARTITION` 秒级下线，不需要 `DELETE` 千万行。**与 `m18_qc_task` / `m18_qc_medication_review` 一致，DEFAULT 分区必须建**——审计日志丢一条不会报错，但会在审计时才发现，那时已经补不回来了。

**`m18_qc_oper_log` 只增不改**：本表不设 `updated_at` / `updated_by` / `is_deleted`。审计流水如果能被改，就不叫审计流水。应用账号在本表上的权限是 `INSERT` + `SELECT`，**没有 `UPDATE` / `DELETE`**：

```sql
REVOKE UPDATE, DELETE ON m18_qc_oper_log FROM app_user;
```

**模型定义的几个要点**

1. **`QcTask` / `QcMedicationReview` / `QcOperLog` 不继承 `TimestampMixin`**，而是显式声明 `created_at`。理由是这三张是分区表，`PRIMARY KEY` 必须包含 `created_at`，模型里必须能精确控制该列的默认值，不能让 mixin 隐藏它。
2. **数值列一律 `Numeric` 而非 `Float`**。评分 `NUMERIC(5,1)`、耗时 `NUMERIC(10,3)`、金额 `NUMERIC(14,2)`——**全模块没有一列是浮点**，理由见 §8.5：89.0 与 89.00000001 在等级判定上等价，但在「等于 90 吗」上不等价，而甲/乙级的分界正卡在 90。
3. **`postgresql_where` 对应部分索引**。`idx_m18_qc_med_rule_active` 的条件与 DDL 里的部分索引条件必须**逐字一致**，否则 `alembic` 生成的差异迁移会反复重建该索引。
4. **`QcDefect` 与 `QcRectify` 的 1:N 关系不在此处声明 `relationship`**，因为本子模块的查询都以「按缺陷 ID 直接查」为主，声明关系会让加载路径不可控（尤其整改记录数量不定）。Service 层显式查询。

    score_no: str = Field(max_length=32)
    qc_task_no: str = Field(max_length=32)
    record_id: int
    base_score: Decimal
    deduction: Decimal = Field(ge=Decimal("0"))
    qc_score: Decimal = Field(ge=Decimal("0"), le=Decimal("100"))
    qc_level: QcLevelEnum
    has_critical: bool
    critical_count: int = Field(ge=0)
    major_count: int = Field(ge=0)
    minor_count: int = Field(ge=0)
    hint_count: int = Field(ge=0)
    rule_version_set: str = Field(max_length=64)

    @field_validator("base_score", "deduction", "qc_score")
    @classmethod
    def _quantize_one(cls, v: Decimal) -> Decimal:
        return v.quantize(Decimal("0.1"))

    @model_validator(mode="after")
    def _check_grade_and_score(self) -> QcScoreSchema:
        expected_deduction = (
            Decimal(self.major_count) * DEDUCT_MAJOR
            + Decimal(self.minor_count) * DEDUCT_MINOR
            + Decimal(self.hint_count) * DEDUCT_HINT
        )
        if self.deduction != expected_deduction:
            raise ValueError(
                f"deduction={self.deduction} 与按等级累加结果 {expected_deduction} 不一致"
            )
        expected_score = max(Decimal("0.0"), self.base_score - self.deduction)
        if self.qc_score != expected_score:
            raise ValueError(f"qc_score={self.qc_score} 应为 {expected_score}")
        expected_level = self._resolve_level(self.qc_score, self.has_critical)
        if self.qc_level is not expected_level:
            raise ValueError(f"qc_level={self.qc_level} 应为 {expected_level}")
        return self

    @staticmethod
    def _resolve_level(score: Decimal, has_critical: bool) -> QcLevelEnum:
        if has_critical:
            return QcLevelEnum.GRADE_C
        if score >= GRADE_A_MIN:
            return QcLevelEnum.GRADE_A
        if score >= GRADE_B_MIN:
            return QcLevelEnum.GRADE_B
        return QcLevelEnum.GRADE_C

**Schema 设计的几个要点**

1. **`MedCheckResponseSchema` 的三个 `model_validator` 直接把 §10.2 / §11.2 的降级硬要求变成了代码**：`DEGRADED` 必须有 `degraded_sources`、必须 `alerts` 为空、必须 `degraded=true`。这样即便 Service 层写错，序列化时也会抛错而不是发出一个「看起来像 PASS 的响应」。这是把「不能返回假 PASS」从文档约定变成运行时断言。
2. **`QcScoreSchema._check_grade_and_score` 复算一遍扣分与等级**。它复现的正是 `M18-CALC-02`：`deduction = major×5.0 + minor×2.0 + hint×0.5`，`qc_score = max(0, 100 − deduction)`，`has_critical` 一票否决。这样任何绕过评分服务、手工拼响应的地方都会立刻暴露。
3. **`MedCheckRequestSchema.allergy_codes` 默认 `None` 而不是 `[]`**。这个区别很重要：`None` = 调用方没传（M18-05 去查本库权威过敏史）；`[]` = 调用方明确说「这个患者没有过敏史」。**两者绝不能合并**——合并后「没传」会被当成「没有过敏」而漏审，这正是 lead 强调的那类错误。
4. **`age` 与 `age_months` 的一致性校验**容忍 12 个月误差，因为调用方可能只精确到岁。但眼科用药的儿童剂量规则依赖月龄，所以两个都要能传。
5. **`QcBatchStartSchema` 的时间跨度上限 366 天**，与 `enforce` 的批跑吞吐（200 份/分钟）配合：跨度过大会让单次任务跑几小时，中途失败重试代价高。超过一年应拆成多个任务。

### C.1 P-08 主查询：RuleSet 加载（启动与热重载）

SELECT rule_code, rule_version, rule_type, alert_type, alert_level, severity_rank,

**期望计划：** `Index Scan using idx_m18_qc_med_rule_active on m18_qc_med_rule`，`rows≈8000`，耗时 `≤ 40ms`。**若出现 `Seq Scan`**，说明部分索引条件与查询条件不一致（例如索引上多了 `org_id` 条件而查询没带），需核对 DDL 与查询。

### C.2 P-08 响应复现：按审核记录取全部提示

```sql
SELECT alert_seq, alert_no, rule_code, rule_version, alert_level, alert_type,
       drug_code, drug_name, drug_seq, conflict_drug_code, alert_title,
       alert_detail, advice, evidence_ref, must_ack
  FROM m18_qc_med_alert_hit
 WHERE review_id = :review_id
 ORDER BY alert_seq ASC;
```

**期望计划：** `Index Scan using idx_m18_qc_alert_review on m18_qc_med_alert_hit`，`rows≈0~5`，耗时 `≤ 2ms`。这条查询是「事后复盘：这张处方当时到底提示了什么」的唯一依据。

### C.3 开方时与审方时结论比对（本子模块的判据查询）

```sql
SELECT r1.review_no       AS prescribe_review_no,
       r1.rule_version_set AS prescribe_rule_set,
       r1.check_result    AS prescribe_result,
       r1.alert_count     AS prescribe_alert_count,
       r2.review_no       AS dispense_review_no,
       r2.rule_version_set AS dispense_rule_set,
       r2.check_result    AS dispense_result,
       r2.alert_count     AS dispense_alert_count,
       (r1.rule_version_set = r2.rule_version_set) AS same_rule_set,
       (r1.check_result = r2.check_result)         AS same_result
  FROM m18_qc_medication_review r1
  JOIN m18_qc_medication_review r2
    ON r1.biz_no = r2.biz_no
 WHERE r1.check_scene = 'PRESCRIPTION'
   AND r2.check_scene = 'DISPENSE_REVIEW'
   AND r1.biz_no = :biz_no
   AND r1.created_at >= :from_ts
   AND r2.created_at >= :from_ts
 ORDER BY r1.created_at DESC, r2.created_at DESC;
```

**判读规则（写进 §8.4 校验规则）：**

- `same_rule_set = TRUE` 且 `same_result = FALSE` → **异常**，必须告警。同一套规则对同一张处方给出不同结论，说明引擎有状态或顺序依赖，是需要排查的缺陷。
- `same_rule_set = FALSE` 且 `same_result = FALSE` → **合法**，规则升级了。这正是 `rule_version_set` 存在的意义：能说清「审方时多出来的告警是因为 11:00 发布了新规则 DR_OPHTH_005」。
- `same_rule_set = FALSE` 且 `same_result = TRUE` → 合法，规则变了但结论未变。

**期望计划：** `Index Scan using idx_m18_qc_med_review_biz on m18_qc_medication_review`，因该表按 `created_at` 月分区，查询须带 `created_at` 范围才能做分区裁剪。

### C.4 质控评分的等级与扣分核对（数据质量巡检）

```sql
SELECT qc_task_no, record_id, qc_level, qc_score, deduction,
       major_count, minor_count, hint_count, has_critical
  FROM m18_qc_score
 WHERE (deduction <> major_count * 5.0 + minor_count * 2.0 + hint_count * 0.5)
    OR (qc_score <> GREATEST(0.0, base_score - deduction))
    OR (qc_level = 'GRADE_C' AND qc_score >= 75.0 AND has_critical = FALSE)
    OR (qc_level = 'GRADE_A' AND (qc_score < 90.0 OR has_critical = TRUE))
    OR (qc_level = 'GRADE_B' AND (qc_score < 75.0 OR qc_score >= 90.0 OR has_critical = TRUE));
```

**期望结果：0 行。** 这条查询是 DA 类验收的一部分（详细设计 DA-04）。组合 CHECK 已经在库层做了同样的约束，这条巡检是**防「约束被临时禁用」或「历史数据迁移带入脏数据」的第二道防线**——真实运维中约束被 `ALTER TABLE ... DROP CONSTRAINT` 临时关掉后再没打开的事故并不罕见。

### C.5 逾期整改清单

```sql
SELECT d.defect_no, d.defect_name, d.defect_level, d.due_date, d.dept_id,
       d.doctor_id, d.status, CURRENT_DATE - d.due_date AS overdue_days
  FROM m18_qc_defect d
 WHERE d.status IN ('OPEN', 'RECTIFYING')
   AND d.due_date < CURRENT_DATE

```

### D.2 初始化质控规则（约 180 条）

按共享规范 §9.1 的清单，来源为卫健委病历质控标准，由质控员在 P02 页面手工录入。四类规则的参考条数：

| 质控类型 | 参考条数 | 典型规则 | 主要缺陷等级 |
|---|---|---|---|
| `TIME_LIMIT` 时限质控 | 约 30 条 | 术后首次病程 24 小时内完成、入院记录 24 小时内完成、出院小结出院当日完成 | `MAJOR`、`CRITICAL`（手术记录未签名） |
| `LOGIC` 逻辑质控 | 约 60 条 | 诊断与主诉不符、手术记录与医嘱不符、男性患者出现妇科诊断、眼科诊断缺眼别 | `MAJOR`、`MINOR` |
| `COMPLETENESS` 完整性质控 | 约 70 条 | 必填章节缺失、手术记录缺术前讨论、麻醉记录缺知情同意 | `MAJOR`、`MINOR` |
| `CONSISTENCY` 一致性质控 | 约 20 条 | 主诊断与手术名称不匹配、就诊科室与诊断不符、眼别前后不一致 | `CRITICAL`（眼别不一致） |

**眼别一致性质控为什么升为 `CRITICAL`**：眼科手术左右眼搞错是不可逆的医疗事故。一份病历里「手术记录写左眼、诊断写右眼」，不是「写得不够仔细」，而是「这台手术可能开错了眼」。这条与总纲 §6.2 算例里「诊断缺侧别被人工改判为 MAJOR（眼科左右眼混淆属重大缺陷）」的口径对齐——**缺侧别是 `MINOR`，前后不一致是 `CRITICAL`**，两者严重度差三档。

**说明：本子模块的 11 张表与 M18-02/06/08 的表之间没有任何物理外键**，所以建表顺序只受本子模块内部的逻辑依赖约束，不受其他子模块进度影响。这是「跨子模块不建物理外键」这条规则带来的直接好处：各子模块的迁移脚本可以并行开发、任意顺序执行。

**迁移脚本的五条硬要求（共享规范 §8.2 与常见坑）**：

1. **每个 `upgrade()` 必须有对应的 `downgrade()`**，且顺序与建表相反。
2. **分区表必须含 DEFAULT 分区**，否则跨月第一天第一条数据写入直接失败（常见坑第 22 条）。
3. **大表加索引用 `CREATE INDEX CONCURRENTLY`**（本子模块建表时表为空，首次建索引可用普通 `CREATE INDEX`；后续补索引必须用并发方式）。
4. **`REVOKE` 放在迁移末尾**：`REVOKE UPDATE, DELETE ON m18_qc_oper_log FROM app_user;`，并在 `downgrade()` 里 `GRANT` 回来。
5. **种子数据用 `INSERT ... ON CONFLICT DO NOTHING`**，避免重复执行迁移时报唯一键冲突。

### E.3 分区维护任务

分区表的月度预建由 §7.3 的 APScheduler 任务负责（每月 20 日预建下两个月分区）。**若预建任务失败，`DEFAULT` 分区会兜住数据**（数据不会丢），但会让后续 `DETACH PARTITION` 的过期清理失效，因此 `DEFAULT` 分区一旦有数据必须告警——这条告警写进详细设计 §11.4 的监控指标表。
