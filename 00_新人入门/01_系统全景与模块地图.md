## 1. 23 个模块的全景

医院的信息系统被切成 **23 个模块**，编号 M01~M23。

**为什么是 23 个？** 按"业务领域 + 管理边界"切分：

- 太粗（比如只分"临床"和"管理"）：模块内部太杂，一个人 hold 不住
- 太细（比如每个检查项目一个模块）：模块间调用爆炸，运维成本高

23 个的粒度大约对应"一个科室一个系统"或"一个专业域一个系统"。

### 1.2 为什么先做 M01/M02/M03/M04/M07

这五个模块是**门诊闭环的主干**，也是所有其他模块的公共依赖：

```
没有 M01  → 不知道有哪些科室、哪些药品、哪些收费项
没有 M02  → 不知道谁能登录、谁能看什么
没有 M03  → 不知道患者是谁、历史记录挂在哪
没有 M04  → 门诊无从开始
没有 M07  → 患者来了没人看病
```

**如果先做 M14 药房，会发现"没有处方可发药"。**

所以推进顺序是：**底座 → 门诊主干 → 各专业模块**。

### 2.1 各层职责

| 层 | 职责 | 特征 | 变化频率 |
|---|---|---|---|
| **第 1 层 基础支撑** | 主数据、身份、权限 | 全系统共享，改动影响面极大 | 极低 |
| **第 2 层 资源保障** | 检验、药房、物资、收费、财务 | 支撑业务运转，但本身不是"看病" | 中 |
| **第 3 层 业务诊疗** | 门诊、住院、医生站、护理、手术、专科 | 医院的核心业务 | 高 |
| **第 4 层 集成通道** | 外部对接、移动端、系统管理、病历知识 | 横切能力 | 中 |
| **第 5 层 决策分析** | 报表、随访运营 | 消费数据，不产生业务数据 | 中 |

### 2.2 读架构图的三个要点

**要点 1：** 依赖是**单向**的——上层依赖下层，下层不知道上层存在。

举例：M07 调用 M01 查药品，M01 绝不会调用 M07。

**要点 2：** M18 电子病历与知识库放在第 4 层是有意的。

M18 **不存业务数据**，它存的是**内容与知识**：
- 病历模板（文书长什么样）
- 临床路径（标准治疗方案）
- 合理用药知识（药物相互作用规则）

真正的业务数据（谁在什么时候得了什么病、开了什么药）在 M07。

**这是本项目的一个重要分层决策：** M07 做**业务操作端**，M18 做**内容与知识**。

**要点 3：** M16 收费在第 2 层而不是第 3 层。

因为**收费是"执行层"**——医生开单（M07）、药房发药（M14）、检查执行（M12），每个动作都产生费用，M16 负责算钱收钱。它服务所有业务，自己不产生业务。

## 3. 六个业务域

按**业务领域**而不是技术层次划分：

```
┌─────────────────────────────────────────────────────────────────┐
│ ① 基础域     M01 主数据 · M02 权限 · M23 系统管理                 │
│              「谁知道什么、谁能做什么」                           │
├─────────────────────────────────────────────────────────────────┤
│ ② 患者域     M03 患者服务 · M19 随访会员                          │
│              「患者是谁、和医院什么关系」                         │
├─────────────────────────────────────────────────────────────────┤
│ ③ 门诊域     M04 门诊 · M07 医生工作站 · M18 病历知识              │
│              「来医院看病这件事」                                 │
├─────────────────────────────────────────────────────────────────┤
│ ④ 住院手术域 M05 住院 · M06 日间手术 · M08 护理 · M09 手术麻醉    │
│              「住院和动手术这件事」                               │
├─────────────────────────────────────────────────────────────────┤
│ ⑤ 专科域     M10 视光 · M11 屈光                                  │
│              「眼科特有的专科业务」                               │
├─────────────────────────────────────────────────────────────────┤
│ ⑥ 资源域     M12 检查 · M13 检验 · M14 药房 · M15 物资             │
│              M16 收费 · M17 财务 · M21 集成 · M22 报表            │
│              「支撑业务运转的资源与通道」                         │
└─────────────────────────────────────────────────────────────────┘
```

### 3.1 为什么要有两种分法

**五层架构**回答："这个模块在技术上是底层还是上层？"

**六个业务域**回答："这个模块属于医院的哪个业务板块？"

举例：M16 收费

- 五层架构里在第 2 层（资源保障）
- 业务域里在资源域（⑥）

两者一致。

但 M18 电子病历：

- 五层架构里在第 4 层（集成与通道）
- 业务域里在门诊域（③）

**因为它是"病历内容的提供者"，服务于门诊诊疗。**

## 4. 三条业务闭环

**这是理解整个系统最重要的视角。**

医院的业务不是零散的功能堆砌，而是**患者从进入到离开的完整旅程**。每一步都有明确的模块负责。

### 4.1 门诊闭环（已打通 ✅）

```

                                    ▼                   ▼              ▼
                              ┌──────────┐        ┌──────────┐   ┌──────────┐
                              │ 诊断     │        │ 医嘱/处方 │   │ 病历文书 │
```

**M07 是这条闭环的中枢：** 它接收挂号信息、产诊断、开医嘱、看报告、写文书、最后判断能否离院。

### 4.2 住院闭环（⏳ 未设计）

```
入院登记 → 床位分配 → 住院医嘱 → 护理执行 → 检查检验 → 手术 → 出院 → 结算
  M05        M05        M05/M07     M08        M12/M13    M09    M05    M17
```

**注意：** 住院医嘱也会走 M07（住院医生站）。M07 总纲里已经预留了住院场景的扩展点。

### 4.3 药品闭环（⏳ 部分完成）

```
处方 → 审核 → 收费 → 发药 → 退药 → 库存 → 采购
M07-05  M14   M16    M14    M14    M14    M15
```

**已完成的：** 处方开具（M07-05）

**特点：** 这条闭环**环环相扣且不可跳过**——处方必须审核才能收费，必须收费才能发药。

**M07-05 已经在关键节点设置了门禁：**

| 门禁 | 触发条件 | 处理 |
|---|---|---|
| 抗菌药物分级 | 开限制级/特殊级 | 校验医生职称 |
| 特殊级会诊 | 开特殊级抗菌药 | 必须先有会诊记录 |
| 合理用药 | 有相互作用/禁忌 | 阻断或警告 |
| 处方签名 | 提交前 | 必须 CA 签名 |

## 5. 模块依赖拓扑

### 5.1 拓扑排序（按依赖顺序）

```
第 0 层（无依赖）
  M23 系统管理
  M02 基础安全策略
  M21 集成平台（基础设施部分）

第 1 层（依赖第 0 层）
  M01 主数据管理  ← 依赖 M02（权限）、M23（参数）
  M02 统一权限    ← 依赖 M01（职工）、M23（参数）

第 2 层（依赖第 1 层）
  M03 患者服务    ← 依赖 M01（患者索引）、M02（权限）
  M18 病历知识库  ← 依赖 M01（诊断字典、药品字典）

第 3 层（依赖第 2 层）
  M04 门诊管理    ← 依赖 M01、M02、M03
  M16 收费        ← 依赖 M01（收费项）、M03（患者）

第 4 层（依赖第 3 层）
  M07 医生工作站  ← 依赖 M01、M02、M03、M04、M16、M18
  M14 药房        ← 依赖 M01（药品）、M07（处方）、M16（收费）
  M12 检查        ← 依赖 M01、M07（申请单）、M16
  M13 检验        ← 依赖 M01、M07（申请单）、M16

第 5 层（依赖第 4 层）
  M05 住院管理    ← 依赖 M07（住院医嘱）、M08（护理）
  M06 日间手术    ← 依赖 M05、M09
  M08 护理站      ← 依赖 M05、M07
  M09 手术麻醉    ← 依赖 M05、M07（手术医嘱）
  M10 视光        ← 依赖 M03、M16
  M11 屈光        ← 依赖 M09、M10

第 6 层（依赖第 5 层）
  M15 物资        ← 依赖 M09、M12、M13（消耗）
  M17 财务        ← 依赖 M16、M07（绩效数据）
  M19 随访会员    ← 依赖 M03、M04、M07
  M22 报表        ← 依赖全部（只读）
  M20 移动办公    ← 依赖全部（只读 + 部分写入）
```

### 5.2 关键依赖说明

| 依赖 | 方向 | 为什么 |
|---|---|---|
| **所有模块 → M01** | 读主数据 | 科室、职工、药品、收费项是所有业务的基础 |
| **所有模块 → M02** | 鉴权 + 审计 | 每个接口都要过鉴权，每个写操作都要审计 |
| **所有临床模块 → M03** | 患者身份 | 所有业务数据都挂在 `patient_id` 上 |
| **M07 → M04** | 就诊会话 | M07 的会话必须关联一个挂号记录 |
| **M14/M12/M13 → M07** | 医嘱/处方 | 执行方必须知道"要执行什么" |
| **M16 → 所有业务** | 计费 | 每个业务动作都产生费用 |
| **M17 ← M07** | 绩效数据 | 医生的接诊量、效率来自 M07 |

### 5.3 循环依赖的处理

**发现问题：** M01 需要 M02 的权限校验，M02 需要 M01 的职工数据 —— 循环。

**解决方案：分层解耦**

```
M01 的员工模块 → 只存"这个人是谁"（姓名、工号、科室）
M02 的账号模块 → 存"这个人能做什么"（账号、密码、角色、权限）

M01 不调用 M02 查权限
M02 不调用 M01 查姓名（存冗余快照）
```

**另一个循环：** M07 需要 M16 收费，M16 需要 M07 的待收费清单。

**解决方案：单向依赖 + 回调**

```
M07 → M16：查询价格、发起收费（同步接口）
M16 → M07：收费完成后回调 on-paid（异步回写）
```

**不是真正的循环，因为**：M07 调 M16 是为了**知道价格**，M16 调 M07 是为了**回报结果**。两者的目的不同，可以分阶段。

**第三个潜在循环：** M04 需要 M07 的"就诊开始"，M07 需要 M04 的"挂号信息"。

**解决方案：事件驱动**

```
M07 开始就诊 → 调用 M04 的 start-visit → M04 更新挂号状态并发布事件
M04 发布 visit_started 事件 → M07 订阅（但 M07 本来就是发起方，事件用于其他订阅者）
```

### 6.1 这条规则的用法

**新需求来了，怎么找归属？**

```
需求：医生想看患者上次的眼压是多少

查询 M01     → 眼压是"检查项目"，不是主数据 ❌
查询 M03     → M03 管患者身份，不管检查结果 ❌
查询 M07-04  → 报告查看，有这个能力 ✅
```

**再看 M07-04 的第 2 章：**

> 做什么：接收报告、展示报告、识别危急值、查看历史趋势
> 不做什么：生成报告（M12/M13）

**结论：** 需求属于 M07-04，且 M07-04 已有"指标趋势快照表"（`m07_report_trend`）。

## 7. 数据流向总图

### 7.1 主数据流（从 M01 流向全院）

```
                    ┌──────────────────┐
                    │  M01 主数据管理   │
                    │  科室/职工/药品   │
                    │  收费项/诊断字典  │
                    └────────┬─────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │  同步方式：        │                    │
        │  ① HTTP 查询接口   │                    │
        │  ② 本地缓存+版本号 │                    │
        │  ③ 事件通知变更    │                    │
        ▼                    ▼                    ▼
   ┌─────────┐          ┌─────────┐          ┌─────────┐
   │ M03/M04 │          │   M07   │          │ M12/M13 │
   │ 业务模块 │          │ 医生站  │          │ 执行模块 │
   └─────────┘          └─────────┘          └─────────┘
```

**关键点：** 业务模块**不复制**主数据，只**缓存 + 引用 code**。

比如 M07 的医嘱表里存 `charge_item_code = 'CHG0001234'`，不存价格。需要价格时去 M01 查（有缓存）。

**为什么？** 因为价格会变。如果 M07 存了一份价格，M01 调价后 M07 的数据就错了。

### 7.2 患者身份流

```
挂号的这一刻：

  ┌──────────────┐
  │ 患者来了      │
  │ 出示身份证    │
  └──────┬───────┘
         ▼
  ┌──────────────────────────────────┐
  │ M03-01 用身份证号查 EMPI         │
  │  - 命中 → 返回已有 patient_id     │
  │  - 未命中 → 新建，返回新 ID       │
  └──────┬───────────────────────────┘
         ▼
  ┌──────────────────────────────────┐
  │ M04-03 用 patient_id 挂号         │
  │  生成 registration_id             │
  └──────┬───────────────────────────┘
         ▼
  ┌──────────────────────────────────┐
  │ M07-01 用 registration_id 建会话  │
  │  生成 encounter_id                │
  │  同时存 patient_id（冗余，方便查） │
  └──────┬───────────────────────────┘
         ▼
  ┌──────────────────────────────────┐
  │ 所有下游数据都带 patient_id       │
  │  + encounter_id                  │
  └──────────────────────────────────┘
```

**三个 ID 的关系：**

```
patient_id      (患者终身不变)      ← M03 生成
    │
    └── registration_id  (一次挂号)  ← M04 生成
            │
            └── encounter_id  (一次就诊会话)  ← M07 生成
                    │
                    ├── diagnosis_id   (诊断)
                    ├── order_id       (医嘱)
                    ├── report_id      (报告)
                    ├── prescription_id (处方)
                    └── document_id    (文书)
```

### 7.3 医嘱数据流（最重要的一条）

```
 ① 医生开单
 ┌─────────────────────────────────────────────┐
 │ M07-03 医嘱下达                              │
 │ 创建 m07_order，status = DRAFT              │
 │ 医生点击"提交" → status = ISSUED            │
 └────────────────┬────────────────────────────┘
                  │ 发布事件 m07.order.issued
                  ▼
 ② 等待收费
 ┌─────────────────────────────────────────────┐
 │ M16 收费                                     │
 │ 从 M07 拉待收费清单                          │
 │ GET /internal/v1/m07/orders/pending-billing/{encounter_id} │
 │ 收费完成 → 回调                              │
 │ POST /internal/v1/m07/orders/on-paid        │
 └────────────────┬────────────────────────────┘
                  │ M07 status = PAID
                  ▼
 ③ 执行
 ┌─────────────────────────────────────────────┐
 │ 执行方（按医嘱类型分发）                       │
 │                                             │
 │  DRUG      → M14 药房 → 审方 → 发药         │
 │  EXAM      → M12 检查 → 检查 → 出报告       │
 │  LAB       → M13 检验 → 检验 → 出报告       │
 │  TREATMENT → M08 护理 → 治疗                │
 │  OPERATION → M09 手术 → 手术                │
 │                                             │
 │ 开始执行 → POST /internal/v1/m07/orders/on-executing │
 │ 完成执行 → POST /internal/v1/m07/orders/on-completed │
 └────────────────┬────────────────────────────┘
                  │ M07 status = EXECUTING → COMPLETED
                  ▼
 ④ 结果回流
 ┌─────────────────────────────────────────────┐
 │ M12/M13 生成报告                             │
 │ POST /internal/v1/m07/reports/on-report-ready│
 │      ↓                                       │
 │ M07-04 存储报告，status = UNREAD             │
 │      ↓                                       │
 │ 医生打开 → status = READ                     │
 │      ↓（有危急值）                            │
 │ POST /internal/v1/m07/reports/on-critical-value │
 │      ↓                                       │
 │ 危急值状态机：DETECTED → NOTIFIED →          │
 │              ACKNOWLEDGED → HANDLED          │
 └────────────────┬────────────────────────────┘
                  │
                  ▼
 ⑤ 完成就诊
 ┌─────────────────────────────────────────────┐
 │ M07-01 完成校验 8 项                          │
 │  V-08 危急值已处置（阻断）                    │
 │  V-03 无未执行医嘱（阻断）                    │
 │      ↓                                       │
 │ POST /internal/v1/m04/registration/{id}/complete │
 └─────────────────────────────────────────────┘
```

**这条链是本系统最核心的数据流。** 理解了它，就理解了整个门诊闭环。

### 7.4 为什么医嘱状态要这样流转

**核心原则：谁做的谁写。**

| 状态 | 谁能改 | 为什么 |
|---|---|---|
| `DRAFT` → `ISSUED` | **M07** | 只有医生能下达医嘱 |
| `ISSUED` → `PAID` | **M16** | 只有收费处知道钱收了没 |
| `PAID` → `EXECUTING` | **M12/M13/M14/M08/M09** | 只有执行方知道开始了没 |
| `EXECUTING` → `COMPLETED` | **执行方** | 只有执行方知道做完没 |
| `→ REFUNDED` | **M16** | 只有收费处能退钱 |
| `→ REJECTED` | **执行方** | 药房可以拒绝调配 |
| `→ CANCELLED` | **M07** | 医生可以撤销自己开的医嘱 |

**反例：如果 M07 能直接设成 `COMPLETED`**

那么系统里会出现"账面上做完了，实际药没发、检查没做"。患者拿系统截图投诉，医院无法自证。

### 8.4 规模假设

设计时基于以下业务量（`M07_医生工作站_数据结构设计汇总.md` 第 10 章）：

| 项 | 数值 |
|---|---|
| 日门诊量 | 300 人次 |
| 年门诊量 | 10.8 万人次 |
| 医生数 | 20 |
| 科室数 | 12 |
| 数据库 3 年存储 | ≥ 500 GB |
| 数据库 15 年存储 | ≥ 2 TB |

**为什么按 300 人次/天设计？** 二级医院眼科的实际量级。这个量级下单机 PostgreSQL 完全够用，不需要分库分表。

**但设计时仍然考虑了扩展性：** 无物理外键、按年分区、汇总表预聚合——为将来增长留了余地。
