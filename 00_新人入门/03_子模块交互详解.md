## 1. 为什么子模块之间要划分

**问题：** 一个模块 40 张表、200 个接口。如果全塞在一个服务里不加划分，会发生什么？

| 症状 | 后果 |
|---|---|
| 谁都能改谁的表 | 改了 A 影响的 B 没人知道 |
| 状态机散落各处 | 同一个"完成"有 5 处代码在写 |
| 责任不清 | 出问题先扯皮，找不到人 |

**子模块划分解决三件事：**

```
① 责任边界：每个子模块只对一件事负责
② 数据所有权：每张表有唯一的主人，别人只能读不能写
③ 契约显式：跨子模块的调用有明确的接口，不是直接改表
```

### 1.1 子模块不等于微服务

```
重要区分：

子模块是【逻辑划分】，不是【物理部署单元】

当前阶段：一个模块 = 一个 FastAPI 服务 = 一个数据库 schema
          子模块 = 服务内的不同 router + 不同 repository

未来可以：按负载拆成独立服务（子模块边界已经划好，拆的时候不用重构）
```

**所以子模块之间的"契约"是：**

- 同进程内：函数调用 + 明确的数据传递
- 不同进程（拆服务后）：HTTP 接口

## 2. 子模块的三种关系

```
┌───────────────────────────────────────────────────────────────┐
│ 关系 ①  依赖（A 完成才能做 B）                                  │
│                                                               │
│   M04-03 挂号 ────► M04-04 分诊 ────► M04-05 叫号             │
│                                                               │
│   A 的输出是 B 的输入。A 没做完，B 无从下手。                    │
│                                                               │
├───────────────────────────────────────────────────────────────┤
│ 关系 ②  协作（A 和 B 一起完成一件事）                            │
│                                                               │
│   M07-03 医嘱 ◄─── 双向 ───► M07-05 处方                       │
│                                                               │
│   医嘱存"开了什么药"，处方存"怎么用"。                         │
│   谁都不能单独完成"开药"这件事。                                │
│                                                               │
├───────────────────────────────────────────────────────────────┤
│ 关系 ③  旁挂（B 是 A 的横向能力，A 不知道 B 存在）               │
│                                                               │
│   M07-01 接诊 ──写──────────► 业务表                           │
│                    │                                          │
│                    └──装饰器──► M02-06 审计                     │
│                                                               │
│   A 只管写业务，审计由框架自动做。                               │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

### 2.1 判断关系的口诀

| 问自己 | 答案 | 关系 |
|---|---|---|
| "没有 B，A 还能单独运行吗？" | 能 | 旁挂 ③ |
| "没有 B，A 只能做一半吗？" | 是 | 依赖 ① |
| "A 和 B 必须一起修改才能保持一致吗？" | 是 | 协作 ② |

### 3.3 三组关键交互

**交互一：主数据变更 → 审批 → 分发（M01-11 → M01-12）**

```
① 管理员在 M01-03 药品页面修改「阿托品滴眼液」的价格
        ↓
② M01-03 生成变更单（含字段级 Diff）
        ↓
③ 提交到 M01-11 审批
        ↓
④ M01-11 按规则路由：药品价格 → 药学部 → 财务科 → 院长
        ↓
⑤ 审批通过（附电子签名）
        ↓
⑥ M01-11 调用 M01-03 的业务服务写入主表，版本 +1
        ↓
⑦ M01-11 通知 M01-12「md 药品 版本 v137 已生效」
        ↓
⑧ M01-12 生成事件 mdm.drug.changed { code, version: 137 }
        ↓
⑨ MQ 广播
        ↓
⑩ 各模块收到 → 重新拉取 → 更新本地缓存
```

**关键设计：审批与业务分离。** M01-11 不改药品表，它只做"决策"，真正写入表的是 M01-03 自己的服务。这样审批流本身的演进不影响业务表结构。

**交互二：M01-01 科室 与 M01-02 职工 的双向引用**

```
M01-01 科室.department_head_id ──► M01-02 职工.id       （科室负责人）
M01-02 职工.main_dept_id       ──► M01-01 科室.id       （职工主科室）
M01-02 职工兼任职关系表 ──► M01-01 科室.id（多对多）

这是典型的"循环引用"，怎么避免死锁？

答案：分两步校验
  ① 创建科室时，负责人可为空（先建科室）
  ② 创建职工时，科室必须存在
  ③ 指定负责人时，校验该职工确实属于可任该科室负责人的岗位
  ④ 删除科室前，检查是否有在职职工（有则拒绝）
```

**交互三：M01-10 字典 是全院最高频的引用**

```
为什么字典独立成子模块？

因为几乎所有表都有一个「状态」「类型」「分类」字段，值都来自字典。
如果字典分散在各模块，会出现：
  M04 的"性别"是 1/2，M03 的"性别"是 M/F，M07 的"性别"是 男/女

统一到 M01-10 后：
  所有模块引用 dict_item(type_code='SEX', item_code='1')

代价：所有模块都依赖 M01-10，它是全院最单点的单点
对策：
  ① 只读直连数据库（绕过 HTTP）
  ② 两级缓存（本地 + Redis）
  ③ M01 挂了，业务模块仍能读取缓存的字典运行
```

### 4.3 权限定义与权限运行的分离

**这是 M02 最重要的设计：**

```
┌────────────────────────────┐    ┌────────────────────────────┐
│  M01-05 权限（定义层）      │    │  M02-04 引擎（运行层）      │
│                            │    │                            │
│  · 菜单树                   │    │  · 缓存权限上下文（5 分钟） │
│  · 角色定义                 │───►│  · 校验 perm_code           │
│  · 角色-权限关系            │    │  · 解析数据范围             │
│  · 数据权限范围定义          │    │  · 注入 SQL WHERE           │
│  · 字段级权限规则            │    │  · 脱敏处理                 │
│  · 权限申请审批              │    │  · 鉴权日志                 │
│                            │    │                            │
│  慢速变化，有人面对面审批    │    │  高频调用，每次请求都要       │
└────────────────────────────┘    └────────────────────────────┘

为什么要分开？

如果放一起：定义和运行在同一个服务，权限计算时要查角色表、菜单表、
数据范围表 —— 每次请求 4 次数据库查询，10ms 起。

分开后：
  M02-04 有缓存，命中时 0 数据库查询，0.5ms
  定义变更时（一天几次）通过事件失效缓存
```

### 4.4 MFA 触发的判定归谁

**注意一个容易搞混的点：**

```
❌ 错误理解：
   M02-05 二次验证 决定"什么时候需要验证"

✅ 正确理解：
   M02-04 权限引擎 决定"是否需要验证"（它有权限上下文）
   M02-05 二次验证 只负责"执行验证动作"
   M01-05 权限     定义"哪些权限点需要验证、用哪种方式"
```

**代码位置：**

```python
# M02-04 权限引擎中
async def check_permission(perm_code: str, user: User):
    context = await get_permission_context(user.staff_id)

    # ① 功能权限
    if perm_code not in context.permissions:
        raise Forbidden(40301, "无此权限")

    # ② 判断是否需要 MFA
    policy = context.mfa_policies.get(perm_code)
    if policy and policy.required:
        # 检查当前会话是否已验证过
        if not await mfa_is_verified(user.session_id, perm_code):
            raise NeedMfa(428, "需要二次验证", methods=policy.methods)

    # ③ 数据权限
    return context.data_scopes
```

### 4.5 审计的旁挂设计

**M02-06 审计日志不侵入业务代码：**

```python
# 业务代码只加一个装饰器
@router.post("/m07/orders")
@audit_log(event_code="ORDER_CREATE", object_type="m07_order")
async def create_order(payload: OrderCreate, user=Depends(get_current_user)):
    order = await order_service.create(payload, user)
    return success_response(order)
```

**`@audit_log` 内部做了什么：**

```
① 请求前：记录入参、用户、IP、trace_id
② 执行中：捕获异常
③ 请求后：
   · 成功 → 记录结果、变更后值
   · 失败 → 记录错误码、错误信息
④ 异步发送到 M02-06（不阻塞业务）
```

**审计的哈希链：**

```
记录 1: hash_1 = SHA256(内容1 + "genesis")
记录 2: hash_2 = SHA256(内容2 + hash_1)
记录 3: hash_3 = SHA256(内容3 + hash_2)
...
记录 N: hash_N = SHA256(内容N + hash_(N-1))

任何一条被篡改，后续所有 hash 全部失效。
每日 02:00 校验全链完整性，不通过立即告警。
```

### 5.3 关键交互：M03-02 合并如何通知全院

**这是全系统耦合度最高的一个动作。**

```
① M03-02 发起合并（可能是人工申请，也可能是自动判定）
        ↓
② 审批通过
        ↓
③ M03-02 在自己的库里执行合并：
   · 生成 merge_id = MG20261021001
   · 记录 from_patient_id = 1002, to_patient_id = 1001
   · 更新 mpi_patient：1002.status = 'MERGED', 1002.merged_into = 1001
   · 记录关联数据清单（每个模块有哪些记录挂在 1002 上）
        ↓
④ M03-02 发布事件 mpi.patient.merged
        ↓
   ┌────┴────┬────────┬────────┬────────┬────────┐
   ▼         ▼        ▼        ▼        ▼        ▼
 M03-03    M03-04   M03-05   M04      M07      M14 ...
 会员合并   随访合并  消息重定向 挂号重定向 会话重定向  处方重定向

⑤ 各订阅方收到事件后，自己执行本地重定向：
   · 写本地重定向表（source_id → target_id）
   · 更新"进行中"的业务记录
   · 保留"已完成"的历史记录不动
```

**为什么 M03-02 不直接改其他模块的表？**

| 如果直接改 | 后果 |
|---|---|
| M03 的路由要包含全部业务表 | 每次新增业务表都要改 M03 |
| 跨库写无法事务 | 一半成功一半失败，数据不一致 |
| 订阅方的主键规则要暴露 | 耦合到表结构级别 |

**正确做法：** M03-02 只输出"合并事实"，订阅方自己决定怎么处理。这叫**事实发布 + 本地决策**。

### 6.3 号源的三种状态

**这是 M04 最容易搞混的地方：**

```
一个号源（m04_slot）从生成到用完，有三种占用状态：

① 可用（available）
   排班发布后，号源数 = 排班限额
   实际可用 = 号源数 - 已预约 - 已挂号

② 锁定（reserved）
   患者在小程序选了号，但还没付款
   Redis SETNX 锁定 15 分钟
   超时自动释放

③ 已用（used）
   挂号完成，正式占用

    排班发布
        ↓
   ┌──────────┐   预约     ┌──────────┐   支付成功   ┌──────────┐
   │ 可用     │───────────►│ 锁定     │─────────────►│ 已用     │
   │ available│            │ reserved │              │ used     │
   └──────────┘            └────┬─────┘              └──────────┘
        ▲                       │
        │    超时 15min / 取消  │  退号
        └───────────────────────┘◄──────────────────────┘
```

**关键设计：锁定写在 Redis，不写数据库。**

```python
# M04-01 提供三个原子操作
async def reserve(slot_id: int, patient_id: int) -> str:
    """锁定一个号源，返回 reservation_token"""
    key = f"m04:slot:lock:{slot_id}"
    ok = await redis.set(key, patient_id, nx=True, ex=900)
    if not ok:
        raise BizException(54301, "号源已被占用")
    return token

async def confirm(slot_id: int, token: str):
    """确认锁定，转为已用（数据库操作）"""
    await slot_repo.increment_used(slot_id)
    await redis.delete(f"m04:slot:lock:{slot_id}")

async def release(slot_id: int, token: str):
    """释放锁定"""
    await redis.delete(f"m04:slot:lock:{slot_id}")
```

### 6.4 分诊的优先级算法

**M04-04 决定排队顺序，涉及多个因素：**

```
优先级分数 = 基础分 + 特殊加分 - 等待扣分

基础分（按分诊级别）：
  1 级（危急）  → 1000
  2 级（紧急）  → 800
  3 级（普通）  → 500

特殊加分（来自 M04-06）：
  军人/烈属     → +200
  80 岁以上     → +150
  孕妇          → +100
  婴幼儿        → +100
  复诊          → +50

等待扣分：
  每等待 10 分钟 → -10（防止低优先级永远排不上）
```

**M04-06 怎么参与：**

```
M04-04 分诊时调用：
GET /internal/v1/m04/special/patient-flags/{patient_id}
  → { "is_veteran": false, "is_martyrs_family": true, "age": 82, ... }

M04-04 据此计算加分，写入队列的 priority_score 字段。
```

### 6.5 M04-07 日志统计的旁路设计

**M04-07 不主动查询其他子模块，只订阅事件：**

```
M04-03 挂号完成 ──事件──┐
M04-03 退号完成 ──事件──┤
M04-04 分诊完成 ──事件──┼──► MQ ──► M04-07 消费
M04-05 叫号完成 ──事件──┤              ↓
M07    就诊完成 ──事件──┘         写入 m04_visit_log
                                       ↓
                                  每日汇总 → m04_daily_stat
```

**为什么用事件而不是查询？**

| 方式 | 优点 | 缺点 |
|---|---|---|
| 主动查询 | 数据实时 | M04-07 挂了会影响主流程 |
| **订阅事件** | 解耦，天然可重放 | 有延迟（毫秒级） |

**统计口径固化：** M04-07 的统计规则写在文档里（挂号量 = 有效挂号数，不含退号作废；就诊量 = VISITING 转 COMPLETED 的数量），不能随意改。

### 7.6 M07-06 文书：数据快照而非引用

**为什么文书不能存"引用"？**

```
❌ 如果存引用：
   诊断证明书 → 引用 m07_diagnosis.id = 9001
   三个月后诊断被修改（误诊更正）
   打印出来的诊断证明书内容变了！

✅ 正确做法：
   生成文书时，把当时的内容完整复制到 content_snapshot（JSONB）
   计算 content_hash = SHA256(规范化快照)
   签名时 signature_hash = SHA256(content_hash + 签名人 + 时间 + 证书)
   验签时重算，不一致 → TAMPERED
```

**M07-06 与各子模块的取数关系：**

```
M07-06 生成一份「门诊病历」

  取数来源：
  ├─ M07-01 会话   ──► 患者、医生、科室、时间
  ├─ M07-02 诊断   ──► 主诊断、次诊断、眼别
  ├─ M07-03 医嘱   ──► 处置记录
  ├─ M07-05 处方   ──► 用药记录
  ├─ M07-04 报告   ──► 检查检验结果
  ├─ M08    体征   ──► 视力、眼压
  └─ M18    主诉现病史 ──► 段落文本

  以上全部取数后，拍成一个 JSON 快照存起来。
  之后病历就与这些源表脱钩了 —— 这是病历的法定要求。
```

### 7.7 M07-07 只读统计

**M07-07 的严格约束：**

```
✅ 允许：
  · 读取 m07_encounter / m07_diagnosis / m07_order / m07_prescription / m07_document
  · 写入自己的 m07_workload_* 表
  · 调用 M01/M02 查基线数据

❌ 禁止：
  · 修改任何业务表
  · 触发任何业务状态变更
  · 在业务主流程中被同步调用（只能异步/离线）
```

**为什么？**

```
如果工作量统计能改业务数据：
  · 有人为了让报表好看，去改接诊记录
  · 统计数据与业务数据对不上时，无法确定谁是真相

只读设计保证了：
  · 业务表是唯一事实来源
  · 统计表是可重算的派生数据
  · 数据可疑时删了重算即可
```

**重算的幂等保证：**

```sql
-- 唯一约束 + UPSERT
CREATE UNIQUE INDEX uk_m07_wl_daily
    ON m07_workload_daily (doctor_id, work_date);

-- 重算时
INSERT INTO m07_workload_daily (...) VALUES (...)
ON CONFLICT (doctor_id, work_date)
DO UPDATE SET
    encounter_count = EXCLUDED.encounter_count,
    avg_visit_minutes = EXCLUDED.avg_visit_minutes,
    ...
```

### 8.3 核心问题：为什么"算钱"和"收钱"必须分开

这是 M16 拆分的**第一性原理**，值得完整理解。

| 维度 | 算钱（M16-01） | 收钱（M16-02/03/04/05） |
|---|---|---|
| 本质 | 纯函数：输入清单一串，输出金额一个 | 有外部副作用：调渠道、动现金、改上游状态 |
| 能否重放 | **能**——同样的输入必得同样的输出 | **不能**——重复调用会重复扣钱 |
| 失败处理 | 报错重算即可 | 必须人工介入（`UNKNOWN`/`ABNORMAL` 状态） |
| 一致性 | 可随时校对（重算比对） | 只能事后对账 |

如果把两者放在一个子模块里，会得到什么样的代码？

```python
def settle_and_pay(settlement_id, pay_method):
    amount = calc(settlement_id)          # 算钱
    if pay_method == "CASH":
        update_settlement(settlement_id, "PAID")   # 改状态
        write_payment(settlement_id, amount)       # 记账
    else:
        return call_channel(settlement_id, amount) # 钱还没到就返回了
```

这段代码的问题：**算错了要退钱，退钱又要重算**——两条流程绕在一起，谁也理不清。拆开之后：

```
M16-01 算错了 → 作废结算单重算（钱还没收）
M16-02 收错了 → 走 M16-08 退费（钱已经收了）
```

**两个错误，两种处理，互不干扰。**

### 8.4 第二层拆分：收钱为什么又拆成四个

门诊、住院、视光是三个**场景外壳**，业务单据不同，但都用同一套计费引擎和支付网关。

| 子模块 | 场景特征 | 决定拆分的差异 |
|---|---|---|
| M16-02 门诊收费 | 挂号/医嘱即时收费，笔数多，班次管理 | 需要收银员班次、点钞、找零 |
| M16-03 住院结算 | 先交预交金，出院一次结清 | 预交金池与费用账分离 |
| M16-04 视光销售 | 先定货后收款，有加工周期与取镜 | 定金/尾款两阶段、退换判定 |
| M16-05 支付收单 | 与外部渠道交互 | 渠道适配、回调验签、对账 |

**共同的**（都在 M16-01）：价格快照、眼别倍数、优惠计算、行级舍入。
**不同的**（各自实现）：收款时机、单据状态、退款路径。

### 8.5 第三层拆分：为什么退费要单独出来

退费是收费的**逆运算，但比收费复杂得多**。

收费只需要做两件事：
1. 钱到了（M16-05 确认）
2. 单据置位（M16-01 回写上游）

退费要同时做六件事：
1. 钱原路退回（M16-05）
2. 发票红冲（M16-07）
3. 结算单回滚（M16-01）
4. 上游单据回滚（M07 医嘱、M04 挂号）
5. 会员权益回退（M03-03）
6. 库存回补（M14）

**而且这六件事不能随便排序。** 铁律是：**先红冲，再退款**。理由：

- 钱退了票不红 → 虚开风险，税务稽查必查点
- 红冲有 3 年时限，钱退了没法红冲就永久挂账

如果红冲失败，整个退费单直接 FAILED，**一分钱都不退**。这条是硬性的，不接受"先退钱后补红冲"。

单独拆出 M16-08 的价值：M16-02/03/04 可以保持"只做正向"的简单性，不用在每个收费入口里塞退费的反向流程。

### 8.6 跨日结的四个维度恒等式

M16-09 的自检逻辑不是"看起来对就行"，而是**四个维度的聚合结果必须完全相等**：

```
全院净收入 = Σ收费点净收入 = Σ科室净收入 = Σ支付方式净额 = Σ业务类型净额
```

不相等说明视图丢了行或事务漏记，**日结不允许封账**。

为什么要四个维度而不是一个？因为每个维度能抓到不同的错误：

| 维度 | 如果对不上说明 |
|---|---|
| 支付方式 | 渠道回调漏了，或有笔现金没记账 |
| 科室 | 有笔收入没归属（`dept_id` 为空） |
| 业务类型 | 有笔业务没打通计费引擎 |
| 收费点 | 有笔钱没归到某个收费员的班次 |

**一个维度只能证明"总数对"，四个维度才能定位"哪里漏"。**

| 交互 | 提供方 | 消费方 | 方向说明 |

| 挂号费金额 | M16-01 | M04-02/03 | 同步查询，P95 ≤ 50ms |

### 9.3 为什么库存必须只有一个真相源

10 个子模块中有 **6 个会改变库存数量**（采购、出库、盘点、门诊发药、住院摆药、特殊药品）。如果每个模块自己 `UPDATE` 库存表，必然出现：

- 出库扣了但入库没加
- 两个人同时扣同一批次，一个覆盖另一个
- 有人忘了写流水，事后查不出为什么少了

**解法：数量变化只有一个入口。**

```
任何模块想让数量变化
        │
        ▼
POST /internal/v1/m14/stock/apply
        ├── ① 校验幂等键（防重复提交）
        ├── ② 校验方向与流水类型匹配
        ├── ③ 条件原子更新 WHERE qty >= n AND version = v
        ├── ④ 写 m14_stock_txn（只增，触发器禁改删）
        └── ⑤ 返回 before/after
```

**为什么不用 `SELECT ... FOR UPDATE`？** 门诊高峰时热门滴眼液一天 300 张处方，5 个窗口用行锁会串行排队，单笔从 30ms 涨到 150ms。条件更新只在冲突时失败重试，无冲突时零等待。

同样的思路用在 FEFO 批次分配上——用 `FOR UPDATE SKIP LOCKED`，后到的窗口跳到下一批次。**并发下 FEFO 退化为近似，但绝不会发出过期药。**

### 9.4 为什么审核、调配、发药要拆三个子模块

法规硬性要求（《医疗机构处方审核规范》第十二条与第十五条）：

> 药师是处方审核的第一责任人，所有处方须审核通过后方可调配。
> 调配药师与核对药师不得为同一人。

这不只是流程建议，直接决定了数据结构：

| 环节 | 谁做 | 核心约束 |
|---|---|---|
| **审核**（M14-06） | 药师 | 审核人 ≠ 开方医生；BLOCK 级规则不可关闭（DB 约束） |
| **调配**（M14-07） | 药士 | 调配人 ≠ 复核人（**DB 硬约束** `ck_m14_dispense_double`） |
| **复核 + 发药**（M14-07） | 药师 | 8 项核对全勾 + 4 项交代全确认 |

**为什么审核退回是终态而非回到待审？**

医生修改后的处方是**新版本 V2**。若回 PENDING，台账看不到"退回了几次"、分不清两次审核的药师。M14-06 让退回即终结，新版本生成新任务，台账形成链条：

```
YS2026102200001  V1  RETURNED（药师甲）
YS2026102200017  V2  PASSED  （药师乙）
```

### 9.5 为什么门诊与住院必须分开

| 维度 | 门诊（M14-07） | 住院（M14-08） |
|---|---|---|
| 作业模式 | **人找药** | **药找人** |
| 触发 | 患者到窗口 | 「病区 × 时段」批量 |
| 频次来源 | 一张处方一次 | 医嘱频次展开成执行点 |
| 特有环节 | 窗口叫号、用药交代、代取人 | 摆药、药车、药筐、单剂量分包、护士签收 |
| 退药去向 | M16 退现金 | 冲减住院费用账（M16-03） |

**住院的「医嘱 → 摆药」四步转换（这是合并后写不出来的复杂度）：**

```
医嘱：「左氧氟沙星滴眼液 每日4次 连用7天」
   │
   ├─① 频次展开：28 个执行点
   ├─② 按时段归并：每时段 1 次 × 4 时段/天
   ├─③ 按病区汇总：4 病区 × 4 时段 = 16 张摆药单
   └─④ 按批次拆解（FEFO）：每行取 1~2 个批次
```

**为什么按时段而不是按天？** 护士按班次给药。一次发 24 小时的药，等于把分药工作从药房推到了病区——病区没有按人分装的设施。

### 9.6 为什么特殊管理药品要独立成子模块

| 特殊点 | 普通药品 | 特殊管理药品 |
|---|---|---|
| 数量精度 | 按盒/支 | **按最小单位逐支**（芬太尼 2ml 用 1.5ml，剩 0.5ml 必须销毁） |
| 操作人数 | 1 人 | **必须 2 人同时在场**（双人双签） |
| 用完还要管 | 不管 | **空安瓿必须回收、残液必须销毁** |
| 失窃处理 | 报主管 | **24 小时内报药监 + 公安** |

**双锁模型的代码级实现：**

```
┌────────────────────────────────────────────┐
│  麻精专柜 CAB-NR-01                         │
│  电子锁 A（药师甲持钥）+ 电子锁 B（药师乙持钥）│
│    → 任一持钥人无法单独开启                  │
└────────────────────────────────────────────┘
数据库约束（不是流程约定）：
  ck_m14_special_record_double      operator_id <> checker_id
  ck_m14_special_cabinet_double_lock  麻精毒柜必须 lock_type = 'DOUBLE'
  ck_m14_special_stock_qty          quantity >= 0（负库存必拒）
  ck_m14_special_incident_deadline  report_deadline = found_at + INTERVAL '24 hours'
```

**为什么限制双签时间差 ≤ 15 分钟？** 最常见违规做法是「一人操作、另一人下班前补签」。限制时间差 + 要求同会话 + 超时标 `is_late_check` 进季度检查清单，让这种做法既麻烦又留痕。

### 9.7 退药与退费的边界（M14 ↔ M16 最关键的接口）

```
M16-08 退费单创建
    ├──► GET  /internal/v1/m14/dispense/returnable/{rx_no}   查可退明细
    ├──► 执行退费：退款 + 回写 M07 + 通知 M14
    │    POST /internal/v1/m14/dispense/on-refunded
    │         └──► M14-07 生成退药任务，药师判定后入原批次
    └──► 若药品已开封 → M14 判定不可退 → 拒退
```

**分界线：M16 管钱，M14 管药。退费必须先确认药品实物状态**——开封的滴眼液不能退。

**退药三铁律：**

| 铁律 | 做不到的后果 |
|---|---|
| 退回药品必须入**原批次** | 新建批次 → 同批号两条记录 → 库存虚增 + 药监追溯断链 |
| 退药**不回改**发药记录 | 改记录 → 再也说不清"当时到底发了多少" |
| 退款金额 = **实付净额** | 按原价退 → 800 元打八折实收 640，退 800 等于多退 160 |

### 10.3 为什么这套方案的"命门"是 M12-02

本院的检查设备**全部无法接入 HIS**，报告只能由技师手工导出 PDF 到共享文件夹，文件名随机，**PDF 里没有本院患者 ID**。

**系统凭什么知道这份 PDF 是谁的？** 只剩两条线索：

1. **PDF 里印的患者姓名/性别/年龄** —— 靠 OCR 识别，但同名同姓同年龄的患者真实存在
2. **PDF 文件的创建时间** —— 只有技师点"开始/完成"的动作能给出这个时间的参照系

**M12-02 的技师工作台是全系统唯一产生"时间窗"的地方。** 没有它，第二条线索就不存在，只能靠姓名硬匹配——那是拿患者安全赌博。

M12-02 的四个职责：

| 职责 | 说明 |
|---|---|
| 保证窗口存在 | 技师点开始即建窗口，点完成即闭合 |
| 保证窗口正确 | 容差设计（提前 120s / 滞后 300s）、超时截断（4 小时）、重叠标记 |
| 提供窗口查询 | `GET /internal/v1/m12/exec/tasks/pending-window` **P95 ≤ 50ms** |
| 防止窗口污染 | 就诊完成时强制结束执行中任务，否则窗口永远开放 |

**时间窗容差"滞后大于提前"的原因：** 技师做完检查后要等患者离开 → 设备存盘 → 回到电脑 → 点完成，1~5 分钟常见；而开始前患者已在门外等候，点开始就立刻开始。

### 10.4 为什么采集与解析必须分开

| 维度 | M12-03 采集 | M12-04 解析 |
|---|---|---|
| 技术栈 | 文件系统 + watchdog | OCR + NLP + 模板引擎 |
| 处理时长 | ≤ 500ms | 3~12 秒（**差一个量级**） |
| 失败原因 | 文件正在写 / 被占用 / 不是 PDF | PDF 损坏 / OCR 不可用 / 模板不匹配 |
| 失败处置 | 重试或隔离 | 需要人工介入 |
| 资源占用 | 磁盘 IO | CPU（OCR 抢 Web 的 CPU） |

**合并的后果：** 解析慢会拖垮"5 秒内发现新文件"的 SLA；OCR 模型更新会重启采集服务导致漏采；镜像体积多 400 MB。

### 10.5 错绑防护四道闸门（本节最重要）

**错绑率必须是 0——不是"尽量低"，而是架构上不允许。**

```
                      ┌──────────────────────────────────────┐
   PDF 进来 ─────────►│ 闸门①：只有唯一命中才自动绑定         │
                      │   候选 ≥2 → 一律转人工                │
                      └──────────────┬───────────────────────┘
                                     ▼
                      ┌──────────────────────────────────────┐
                      │ 闸门②：is_ambiguous 的时间窗不参与     │
                      │   M12-02 窗口重叠时双方置标记          │
                      └──────────────┬───────────────────────┘
                                     ▼
                      ┌──────────────────────────────────────┐
                      │ 闸门③：一个任务只能绑一份文件          │
                      │   DB 唯一索引 uk_m12_parse_task_bound │
                      └──────────────┬───────────────────────┘
                                     ▼
                      ┌──────────────────────────────────────┐
                      │ 闸门④：双通道姓名交叉验证              │
                      │   通道A姓名 ≠ 报告抬头姓名 → 整条标红  │
                      └──────────────┬───────────────────────┘
                                     ▼
                              BOUND / UNCONFIRMED
```

**为什么自动绑定率目标只有 96% 而不是 99%：**

剩下 4% 是客观上无法自动判定的——同名同姓同年龄同时段（0.3%）、技师忘点开始/完成（1~2%）、OCR 认不出姓名（0.5%）、设备时钟偏差（0.5%）。**追求 99% 的唯一办法是放宽匹配条件，代价就是错绑。**

**姓名必须完全一致的理由：** 中文姓名去一个字就是另一个人（张伟/张玮、王芳/王方 都是真实存在的不同患者）。允许 1 字差异会把错绑率从 0 提到万分之几。

### 10.6 设备时钟为什么必须 NTP 校准

时间窗绑定的输入是 **PDF 文件的 mtime**。

| 场景 | 后果 |
|---|---|
| 设备时钟慢 20 分钟 | PDF mtime 早 20 分钟 → 落在时间窗外 → **所有报告都绑不上**，全部进待确认队列，护士一天处理 420 条 |
| 设备时钟快 20 分钟 | mtime 落在未来 → 同上 |
| 时钟偏差跨过午夜 | 归档目录分到错误日期 |

**这不是代码能修的**，必须在实施阶段用 NTP 校准，是上线前 10 项运维准备的强制项。

### 10.8 M12 的六条拆分主线

1. **按"物理动作"分，不按"数据表"分**——《医疗机构病历管理规定》要求"检查报告经审核医师签名后生效"，物理动作与法定责任一一对应
2. **时间窗是整条链路的唯一救命线索**——M12-02 因此独立
3. **采集与解析必须分开**——技术栈/耗时/失败处置三个层面都不同
4. **绑定与结构化在同一子模块内、但双通道分流**——绑定错代价灾难性，结构化错代价可控
5. **审核是法定责任不是技术流程**——M12-05 独立，审核医师资质校验
6. **配置必须独立且必须能回滚**——M12-06 承载模板版本、回归测试、能力矩阵

### 11.3 为什么检验必须有"标本"这一站

**这是 M13 与 M12 最本质的差异。** 检查没有标本：患者躺在设备前，技师直接操作。检验必须采血/尿/泪液——**标本是有物理生命周期的物体**。

| 标本独有的问题 | 检查没有的问题 |
|---|---|
| 采了几个管？ | — |
| 条码贴对了吗？ | — |
| 采血量够不够？（血清促凝管 5 mL 但离心后只有 40%） | — |
| 容器对不对？（紫帽 EDTA vs 黄帽促凝 vs 蓝帽枸橼酸） | — |
| 送检超时了吗？（全血 2h / 血清 4h / 凝血 2h） | — |
| 检验科拒收了吗？为什么？ | — |
| 要不要重采？ | — |

**结论：** 标本有独立的 8 态状态机（`PENDING → COLLECTED → DELIVERED → ACCEPTED → IN_PROCESS → COMPLETED` + `REJECTED`/`CANCELLED`）、独立的职责分离（**采集人 ≠ 签收人**）、独立的合规记录（12 个字段闭环台账）。这一整套东西检查场景完全不存在。

### 11.4 标本归并：把 N 项检验变成尽可能少的采集管

```
医生开：血常规 + 肝功能 + 凝血 + 血糖 + 血钾（5 项）
                ↓
M13-01 归并算法
                ↓
  紫帽 EDTA 一管  ← 血常规
  黄帽促凝 一管   ← 肝功能 + 血糖 + 血钾（同属血清）
  蓝帽枸橼酸 一管 ← 凝血（必须独立）
                ↓
        护士采 3 管，不是 5 管
```

**七条归并规则：**

| 编号 | 规则 |
|---|---|
| R-01 | 同 `specimen_type` + 同 `container_type` 可归并 |
| R-02 | 合计用量不超容器容量（含 20% 余量） |
| R-03 | 超容量拆管 |
| R-04 | 冷藏与常温不归并 |
| R-05 | 立即送检单独成管 |
| R-06 | 眼科特殊标本每项单管 |
| **R-07** | **凝血必须独立一管（抗凝剂 9:1 比例）** |

**采血量为什么必须算余量：** 血清促凝管标称 5 mL，但离心后血清只有约 40%。20 个生化项目需 4 mL 血清 → 需 10 mL 全血 → 需 2 管。**如果用 5 mL 单管采，检验科会发现血清不够，只能通知重采。**

### 11.5 参考区间为什么要版本化（M13-05 的核心）

```
血钾 K
  V1  3.5~5.3   生效 2024-01-01 ~ 2026-11-14   仪器 AU5800
  V2  3.4~5.3   生效 2026-11-15 ~ NULL         仪器 AU6800
```

**医院换了生化仪，参考区间会变。** 这时：

| 做法 | 后果 |
|---|---|
| 直接改 V1 的数值 | 去年所有报告重新判定一次——昨天正常的报告今天变异常，医生会质疑系统 |
| 新增 V2，不动 V1 | 2026-11-15 前的报告用 V1 判，之后用 V2 判，**历史稳定** |

**保证"任意时刻恰好一条生效"的实现：** 用 PostgreSQL 的 `EXCLUDE USING gist` 排他约束，禁止两条区间的分层条件相同且时间段重叠。

**必须 `COALESCE` 每个可空维度：** PostgreSQL 认为 `NULL` 与 `NULL` 不相等，两条 `gender IS NULL` 的通用区间可以都覆盖同一时段而约束不报错——**这正是"忘了改 V1 的 valid_to"的典型场景**。

### 11.6 危急阈值的三层结构

```
         危急低      参考低       参考高      危急高
           │           │            │           │
  ─────────●───────────●────────────●───────────●─────────►
         <2.5        3.5          5.3         >6.5    血钾
```

| 层级 | 触发 | 处理 |
|---|---|---|
| 参考区间内 | 不标记 | — |
| 参考区间外、危急阈值内 | `HIGH` / `LOW` | 标记，医生可下午处理 |
| 超过危急阈值 | `CRITICAL` | 15 分钟确认 + 2 小时处置强制闭环 |

**为什么血钾要拆成 `<2.5` 和 `>6.5` 两条而血糖可以合并成一条 `OUTSIDE`：** 血钾高低的临床意义不同（低钾→心律失常、高钾→心脏骤停），处置也不同；血糖两头都是"立即补糖或降糖"。**拆与不拆由临床决定。**

**为什么不是所有异常都标 `CRITICAL`：** 眼压 26 一天 20 例全发短信会造成短信疲劳，真正 CRITICAL 的短信反而被忽略。`WARNING` 只走站内信。

### 11.7 微生物的"多批次 + 组装"模型

普通检验一份标本出一份报告。微生物不是：

```
玻璃体液培养
  D1 10:30  PRELIMINARY  涂片初报：革兰阳性球菌   → 推送（当晚调整抗生素）
  D2 09:00  INTERIM      中报：金黄色葡萄球菌      → 推送
  D4 15:00  FINAL        终报：+ 药敏              → 推送
```

**M07 侧表现为"同一份报告被更新版本"**，锚点是 `report_key`（= `specimen_no`），版本号只增。

**为什么用"多批次 + 组装"而不是"多份独立报告"：** 医生应该看到一份完整的玻璃体液培养报告按时间线排好，而不是三个独立报告要自己关联。

**为什么中间结果必须推送：** D1 涂片发现"革兰阳性球菌"，医生当晚就能把经验用药从广谱换成窄谱。强制等终报要到 D4——对眼内炎患者 D1 的生命体征可能已经崩了。

### 11.8 外送检验的三个关键设计

| 设计 | 说明 |
|---|---|
| **`PARTIALLY_RETURNED` 中间态** | 一单 5 项可能 3 项先回 2 项后回，只有 `RETURNED` 会让"明明有进展"的单被标成逾期 |
| **`CLOSED` 与 `RETURNED` 分开** | `RETURNED` 之后还有核对份数、登记费用、归档，忘了结案逾期扫描会一直报 |
| **手工录入必须双人核对 + 附件** | 这是整条链路唯一"数据不经任何自动校验"的环节，成本每份 1 分钟，收益是消灭最原始的人为错误（尤其 S/R 一字之差） |

### 11.10 M13 的六条拆分主线

1. **标本是独有的物理链路，必须单独管**——签收前问"标本到了吗合格吗"（责任人=护士、SLA 30min、异常处置=重采），签收后问"结果出了吗准吗"（责任人=检验师、SLA 4h、异常处置=重做）
2. **采集与解析必须分开**——同 M12
3. **绑定与结构化同模块但双通道分流**——同 M12
4. **参考区间是独立规则中心**——单项目最多 160 条分层规则 + 版本化，是业务数据不是主数据字段
5. **微生物与外送是"慢检验"，结果模型不同**——血常规"20 项一次出完" vs 培养"3 任务 4 时间点"
6. **审核是法定责任**——同 M12

### 12.3 为什么必须有「准入」这一站，而且必须在排程之前

市面上多数日间手术系统把准入检查塞进排程或术前准备里。**放在排程之前是刻意的设计**：

- **如果准入在排程之后**：排程算法为了"提高手术间利用率"，会倾向于"先排上再说，反正术前准备还会筛一遍"。这是把**商业压力施加到医疗判断上**；
- **如果准入在术前准备里**：患者已经排了台次、交了费、请了假，此时查出血压 190，取消的心理与经济成本远高于排程前发现。

**两条准入并行、独立判定：**

| 准入类型 | 判定依据 | 输入 | 不通过怎么办 |
|---|---|---|---|
| **医学准入** | 11 类规则（年龄、生命体征、代谢、心血管、凝血、感染、眼部、气道、一般状况、后勤、知情同意） | 患者体检数据 | 转内科 / 转住院 / 放弃 |
| **资质准入** | M01-07 `surgery/auth/check` | 术式级别 + 主刀资质 | 换主刀 / 上调审批 / 放弃 |

**M06 唯一的「降级但不放行」依赖：**

```
M01-07 不可用
    ↓
NOT_EVALUATED（不是 PASS，也不是 BLOCK）
    ↓
申请单置 PENDING_REVIEW + 告警医务科
    ↓
人工复核（医务科确认主刀资质）
    ↓
允许进入 M06-03 排程 或 退回
```

**绝不允许的降级方式：报错放行。** 手术资质是《医疗机构手术分级管理办法》的硬性要求，让资质不符的医生上台，出事后医院承担全部责任。

### 12.4 为什么「术前准备」要单独一站

日间手术最大的医疗风险不在手术本身，而在**术后回家**——患者离开医院时是"半恢复"状态，任何术前准备漏项都会在无人监护的家中放大：

| 漏项 | 后果 |
|---|---|
| 未禁食 | 全麻下误吸，死亡率极高 |
| 未停抗凝 | 术中出血不止，眼球后出血致盲 |
| 未散瞳 | 白内障手术无法进行，台次浪费 |
| 未配抗菌药 | 眼内炎（术后最严重的并发症之一） |
| 术前检查异常未发现 | 术中血压骤升、血糖失控 |

**闭环三条件**（缺一不可）：
1. 所有必填项状态为 `DONE`，或为 `NA` 且填写了原因（患者已停抗凝 15 天，可标 NA）；
2. `is_abnormal=TRUE` 的项已处置（项做完了但结果不正常，例如凝血异常）；
3. 无 `FAILED` 状态项。

**清单必须落库而不是实时计算**，因为：
- M01-07 规则变更后，历史申请单的清单不能变（患者是按当时的规则准备的）；
- 每项要独立记录执行人与时间；
- 护士在 PDA 上逐项勾选，必须有持久化行。

### 12.5 四方核对：本院比三方多一位患者

法规最低要求是三方（手术医生 + 麻醉医生 + 巡回护士）。**本院加了患者本人**：

> 眼科术眼左右极易混淆，而患者是唯一能在术前最后确认「医生说做左眼」的人。

**四次核对的时间轴：**

```
T-60  到院扫码（腕带第一关）
        ↓
T-60 ~ T-45  病房核对 14 项（V-01~V-14）
        ↓
T-45 ~ T-40  交接一 6 类（责任转移 + 物品清单）
        ↓
T-20  进手术间二次扫码
        ↓
T-0   Time-Out 20 项 + 四方签名
```

**关键项要求输入验证值而非点选：**

| 核对项 | 验证方式 | 为什么不能点选 |
|---|---|---|
| 患者身份 | 扫描腕带条码 | 点选可在不确认情况下盲选 |
| 手术术式 | 手工输入前 4 字 | 打字必须看单据 |
| 手术眼别 | 患者自述后选择 | 必须问患者 |
| 禁食状态 | 输入最后进食时间 | 必须回忆具体时间 |

**只在有客观期望值的项上强制校验**——V-13 随身物品、V-14 代理人无正确答案，强制输入只会产生垃圾数据。

**核对记录通过后不可编辑**：法律证据一旦可改等于可伪造。要改必须医务科授权重开一轮（`round_no + 1`），原记录保留。

### 12.6 离院评估：硬门槛不可代偿

**Aldrete（能否离开复苏室）与 PADSS（能否离开医院）不是一回事。** 很多医院混用，导致「复苏室出来就让人回家」的差错。

| 判定层 | 内容 | 可代偿 |
|---|---|---|
| **① 硬门槛** | 眼压 5~25 mmHg、视力下降 ≤2 行、前房非浅非积血、出血已止 | **不可代偿** |
| ② PADSS 评分 | 标准 6 项 12 分 + 眼科 4 项 8 分 = 20 分，≥9 分且无 0 分项 | 可代偿 |
| ③ 留观时长 | 白内障 120 / 玻切 240 / 注药 60 分钟 | 硬性 |
| ④ 麻醉间隔 | 全麻距末次给药 ≥120 分钟 | 硬性 |
| ⑤ 陪护条件 | 有陪护人且能报出电话 | 硬性 |

**真实推演：**

```
白内障术后 90 分钟
  PADSS 六项：12/12    眼科四项：8/8
  眼压：      0 分（实测 38 mmHg）
  ────────────────────────────────────────
  按总分： 18/20 → 通过 → 回家 → 当晚急性高眼压 → 视神经损伤
  按两层： 眼压 38 不在 5~25 → 不通过 → 继续留观 + 降眼压
```

**DB 层最后一道闸门**：`ck_m06_dis_dischargeable` 约束要求 `conclusion='DISCHARGEABLE'` 时八个硬门槛键必须全为 `TRUE` 且 `zero_items` 为空——即便 Python 判定逻辑有 bug，数据库也拒绝写入「不满足硬门槛却标可离院」。

**为什么留观时长是硬性条件而不是加分项**：眼内炎早期症状在术后 4~24 小时出现；粘弹剂残留导致的高眼压在 4~6 小时达峰。**「最低限度观察时间」不是「评估合格就能提前走」。**

### 12.7 为什么结算锚点是「台次」而不是「申请单」

门诊结算锚点是挂号单，住院结算锚点是住院号，**日间手术结算锚点是 `schedule_id`（台次）**：

- 一次申请可能改期多次，费用发生在**实际做的那一台**上；
- 材料消耗是按台次记录的（M15 按 `schedule_id` 归集）；
- 结算必须与 M16-03 的 `admission_id` 对应，而日间入院是"当天入院"，由台次触发。

**两种结算模式按术式配置：**

| 模式 | 判定 | 适用 |
|---|---|---|
| 方式 A 预交金 | `md_operation.need_deposit=TRUE` 或预估 ≥ 3,000 元 | 玻切、多焦点晶体 |
| 方式 B 后付 | 其余 | 注药等小额 |

**术后未用材料必须先退货再结算**：先结算再退会产生「已收又退」的额外流程（M16-08 退费单 + 审批 + 银行退款），而退回材料本质是「这笔钱本来就不该收」。退回率目标 ≥90%（现状 55%）——日均 55 台 × 180 元，一年患者多付约 **360 万元**。

### 12.8 六类「没做成」必须分开统计

日均申请 60 台、实际做 45 台，剩下 15 台去哪了？**每一类归属不同的子模块，管理者才能对症下药：**

| 失败原因 | 归属 | 统计口径 |
|---|---|---|
| 医学准入不通过 | M06-01 | `INELIGIBLE` 终态 |
| 资质准入不通过 | M06-01 | `PENDING_REVIEW` → 驳回 |
| 患者主动放弃 | M06-01 | `CANCELLED` reason=`PATIENT_GIVE_UP` |
| 术前准备未完成 | M06-02 | 改期事件 |
| 排程失败 | M06-03 | 无台次或改期 |
| 当天取消 | M06-04 | `CANCELLED` after `CHECKED_IN` |

**取消率口径的两个关键约定：**

### 12.10 M06 的六条拆分主线

1. **按「时间轴的物理动作」拆，不按「数据表」拆**——七个环节各有明确的责任人与交付物；
2. **每个子模块必须有独立的「失败原因」统计口径**——否则管理者只知道"少了 15 台"却不知道卡在哪；
3. **法规留痕必须独立且只增**——核对、离院、归档三类证据必须能独立检索、打印、作为法律证据导出；
4. **配置与规则必须独立且可版本化**——只有 M06-01 准入规则与 M06-07 统计口径需要版本化 + 双签发布，因为它们是「会被事后质疑的决策依据」；
5. **M06 管全流程外壳，M09 只管术中**——M06 负责十个环节的状态机与流程控制，M09 负责手术间排班、术中记录、麻醉记录；
6. **统计独立因为是对外承诺**——等级评审核心指标、医保按病种付费，错一期可能影响评审结果与拨付金额。

### 13.3 为什么 M09-01 与 M09-02 必须分开

| 维度 | M09-01 麻醉前评估 | M09-02 麻醉记录 |
|---|---|---|
| 时间性质 | 一次性决策 | 连续时间序列 |
| 数据形态 | 结构化的十几个字段（ASA、气道、过敏史） | 每 5 分钟一组体征 + 每次给药一条 |
| 法律定位 | 麻醉方案是否合理的依据 | 麻醉过程是否规范的证据 |
| 责任人 | 麻醉医生 | 麻醉医生 + 巡回护士 |

**合并的后果**：评估表会被当成"麻醉记录的第一段"随手填写，而它其实是**整个麻醉的法律基础**——ASA 分级、气道评估、过敏史直接决定用药选择。分开后，M09-01 的表单有独立的"提交并锁定"动作，提交后进入 `READY` 状态才允许开始麻醉。

### 13.4 为什么麻醉记录与手术记录是两个独立文书

**法规要求**：《病历书写基本规范》第十八条明确「麻醉记录单应另立单页」，第十九条「手术记录术后 24 小时内完成」。

| 项目 | 麻醉记录 | 手术记录 |
|---|---|---|
| 签署人 | 麻醉医生 | 主刀医生 |
| 完成时限 | 术中实时 | 术后 24 小时内 |
| 记录频率 | 每 5 分钟一组 | 关键节点 |
| 复述内容 | 生命体征、用药、事件 | 术式、探查所见、操作步骤 |

**合并的致命缺陷**：主刀可以修改麻醉记录、麻醉医生可以修改手术记录。一旦发生纠纷，两份文书的独立性就被破坏，无法相互印证。

### 13.5 手术间占用的六时刻（本节最重要）

**这是 M09 给整个 HIS 带来的最大增量价值**——手术间占用时长的唯一可信来源。

```text
08:42  or_in_at          进间
08:50  monitoring_at     开始监护
08:55  anesthesia_start  麻醉开始
09:02  incision_at       切皮
09:14  suture_at         缝合
09:20  anesthesia_end    麻醉结束
09:27  or_out_at         离间
```

| 时长 | 计算方式 | 数值 | 说明 |
|---|---|---|---|
| 手术间占用 | 离间 − 进间 | **45 分钟** | 真正占了房间多久 |
| 净手术 | 缝合 − 切皮 | **12 分钟** | 医生动手的时间 |
| 麻醉时长 | 麻醉结束 − 麻醉开始 | **25 分钟** | |
| 术前准备 | 麻醉开始 − 进间 | **20 分钟** | 摆位、消毒、铺巾 |
| 术后清理 | 离间 − 麻醉结束 | **13 分钟** | |
| 周转 | 下台进间 − 上台离间 | **25 分钟** | 决定日台次数 |

**只有切皮缝合数据会算出 2.5%，有完整记录是 9.4%（单台）。** 日排 8 台真实利用率 75%，但如果只统计"切皮到缝合"会显示 20%——**这个差异直接决定医院是否应该增加手术间**。

### 13.6 器械清点：为什么纱布必须单独结论

国内手术遗留物事件中**纱布占 60% 以上**。

| 物品类别 | 计数方式 | 结论独立性 |
|---|---|---|
| 普通器械 | 分类计数 | 独立 |
| 关键器械 | 逐件扫码 | 独立 |
| **纱布/棉片** | **单独计数** | **独立结论** |
| **缝针** | **逐支记录使用状态** | **独立结论** |
| 植入物 | 转 M09-05 | — |

**混算的后果**：一张清单统计「42 → 42 相符」，但实际上是器械多 1 件、纱布少 1 块，**总数仍相符，掩盖了纱布遗留**。

**四次清点不可替代**：

| 次序 | 时点 | 不可替代的理由 |
|---|---|---|
| 术前 | 切皮前 | 建立基准；没有基准三次比对全失效 |
| 关腔前 | 关闭切口前 | **唯一拦截时机**——此刻发现还能取出 |
| 关腔后 | 关闭后 | 覆盖关闭过程新上台器械 |
| 缝合后 | 最终 | 覆盖缝合过程 + 最终确认 |

**不符时的处置**：`MISMATCH` 是独立状态，强制中止关腔 → 二次查找 ≤10 分钟 → **X 光复核不可跳过**（"找不到"≠"不在体内"，器械可能滑入组织间隙、藏在血凝块后）。

### 13.7 植入物五道校验为什么全部 BLOCK

| 编号 | 校验 | 失败后果 | 错误码 |
|---|---|---|---|
| V-01 | 真伪（UDI 库 + 合格供应商） | 假货 | `"0905020"` |
| V-02 | 有效期 | 过期产品植入 | `"0905021"` |
| V-03 | 重复使用 | 一物多用 | `"0905022"` |
| V-04 | 型号度数匹配预订单 | 装错类型/度数 | `"0905023"` |
| V-05 | 眼别匹配（台次 + Time-Out） | 装错眼 | `"0905024"` |

**为什么不设 WARN**：允许"警告后继续"，护士在时间压力下必然选"继续"，扫码就变成装饰品。三项里任意一项单独发生的致残致命风险都已足够阻断。

**唯一例外**：M15 库存校验与药监局 UDI 库在外部依赖超时降级为 `UNCHECKED` 并留痕，24 小时内补做——**网络不通不能把手术停掉，但必须在记录里标明"未完成真伪校验"**。

### 13.8 三方共读：为什么要把患者也拉进来

真实错用场景不是系统校验失败，而是**人的记忆错**——系统所有电子校验都对，但主刀记错度数。

| 参与方 | 动作 | 作用 |
|---|---|---|
| 主刀医生 | 说出植入部位、度数、型号 | 确认自己的意图 |
| 巡回护士 | 读出包装度数、序列号、眼别、有效期 | 确认实物 |
| **患者/家属** | 确认哪只眼、多少度 | **唯一能从"术前约定"角度校验的人** |

**必须患者参与的理由**：患者是唯一能证明"当时医生说的是什么"的证人。全麻或意识障碍时记 `UNABLE` 并填代理人。

**耗时 <5 秒标记 `is_suspicious_fast`**：纠纷中"你们说三方共读了只用了 3 秒？"

### 13.9 手术间利用率：同一指标四种算法差 36 个百分点

### 14.3 为什么 M15 与 M14 平行而不合并

| 维度 | M14 药品 | M15 耗材 |
|---|---|---|
| 监管体系 | 《药品管理法》GSP | 《医疗器械监督管理条例》+ UDI 规则 |
| 编码体系 | 本位码 + 批号 | **UDI-DI + 序列号（一物一码）** |
| 效期维度 | 有效期 | **有效期 + 灭菌有效期** |
| 追溯方向 | 药品 → 患者（单向） | **患者 ↔ 耗材（双向）** |
| 成本法 | 移动加权平均 | **批次实际成本** |

**灭菌双效期的必要性**：一次性无菌包厂商有效期 3 年，但灭菌有效期只有 6 个月。若以厂商效期为准，会出现"灭菌已失效但系统显示有效"→术后感染。实际失效日 = `LEAST(expiry_date, sterile_expiry_date)`。

**为什么高值耗材不能加权平均**：人工晶体单价 3,000~15,000 元，加权平均会稀释批次真实成本——这批 8,000 元、那批 12,000 元，平均成 10,000 元后，退费与召回时的成本核算全部失真。

### 14.4 数量三要素：为什么锁定与在库必须分离

| 字段 | 含义 |
|---|---|
| `qty_on_hand` | 在库总量 |
| `qty_locked` | 已锁定（备台预留） |
| `qty_available` | 可用 = 在库 − 锁定（**生成列，数据库强制**） |

**不分离的后果**：手术前一晚备台 50 项，物理上还在二级库但**不能再被另一台手术领用**。若只有 `qty_on_hand`，两台手术同时备台时后一台会分配走前一台已锁定的晶体，术中才发现缺货。

### 14.5 出库 ≠ 消耗（M15 最重要的一条边界）

| 动作 | 时点 | 库存变化 | 责任 |
|---|---|---|---|
| 出库 | 手术前一晚备台 | 一级库 → 手术室二级库 | 库管员 |
| 消耗 | 术中实际使用 | 二级库 → 已用 | 器械护士 |
| 退料 | 术后未用 | 二级库 ← 未用部分 | 器械护士 |
| 报损 | 发现破损 | 二级库 → 报废 | 护士长 |

**合并的后果**：备台 50 项、实耗 38 项、退回 12 项，一张表说不清"备了没用"与"备了坏了"。

**M06-06 的「材料退回率 ≥90%」指标直接依赖这个区分**——它统计的是"备台未用退回"比例，现状 55%（日均 55 台 × 平均未用材料 180 元，**一年患者多付约 360 万元**，是多收费的主要投诉来源）。

### 14.6 UDI 解析：定长与变长 AI 必须区分

UDI 结构：`DI(01)` 产品标识 + `PI` 生产信息（`11` 生产日期 / `17` 有效期 / `10` 批号 / `21` 序列号 / `240` 附加）。

| AI 类型 | 标识符 | 分隔方式 |
|---|---|---|
| 定长 | `01`(14) / `11`(6) / `17`(6) / `30`(6) | 直接跟下一个 AI |
| 变长 | `10` / `21` / `240` | **必须跟 FNC1（ASCII 29）** |

**不区分定长变长的后果**：

```text
01087176482002741726123110B240815217X2K91
                                        ▲
        没有 FNC1 时，批号会吞掉序列号
        批号被解析成 "B240815217X2K91"
```

**为什么不能用一个大正则**：四种码制（GS1-128 `]C1` / GS1 DataMatrix `]d2` / HIBC `+` / 厂商私有）的格式差异极大，一个正则要么灾难性回溯，要么覆盖不全。**必须分层**：按码制特征识别 → 调对应解析器 → 按优先级取第一个成功。

### 14.7 采购入库：税额为什么必须逐行先算再汇总

| 计算顺序 | 不含税 | 税额 | 合计 |
|---|---|---|---|
| **10 行先汇总再算** | 884.96 | 115.04 | 1000.00 |
| **逐行先算再汇总** | **885.00** | **115.00** | **1000.00** |

**差 0.04 元**。看似可忽略，但长期累积会导致三单匹配持续失败——每张发票都对不上，财务每月要人工处理几百条差异。

**必须逐行的理由**：与增值税发票"逐行开票、汇总计税"的口径一致。发票上每一行的税额是单独计算的，如果 HIS 账单按总额算，就永远对不上。

**部分合格优于整单拒收**：到货 100 支，98 支合格 2 支不良。

| 方案 | 后果 |
|---|---|
| A 整单拒收 | 98 支可用却退回，延误 3 台手术 |
| B 全部入库 | 混入不良品 |
| **C 部分合格（推荐）** | **98 入库 2 拒收**，同批号拆合格行 + 不合格行 |

### 14.8 盘点：为什么冻结必须落表、为什么必须盲盘

| 设计 | 理由 |
|---|---|
| **冻结落表**（`m15_stocktake_freeze`） | 若只放 Redis，重启或过期即解冻，盘点期间业务继续出库，差异无法归因 |
| **盲盘** | 显示账面数会受引导——看到"应有 100"就数成 100 |
| **强制归因 ≥10 字** | 只填"差异"不填原因，第二年无法分析趋势 |
| **差异四级审批** | <0.5% 库管员 / 0.5~2% 科长 / 2~5% 科长+财务 / >5% 科长+财务+分管院长 |

**为什么必须有循环盘点**：全盘一年一次，两次盘点之间 11 个月账实可能已严重偏离。循环盘点按 ABC 分类滚动盘点（A 类每月、B 类每季、C 类每半年），保证账实持续可信。

### 14.9 召回：法定时限与三路检索

| 召回级别 | 上报时限 | 通知患者时限 |
|---|---|---|
| I 级（严重危及生命） | **24 小时** | **24 小时** |
| II 级（暂时危害健康） | 24 小时 | 48 小时 |
| III 级（一般不引起危害） | 48 小时 | 72 小时 |

**三路检索**：批号 / 序列号 / DI 型号。**按批号检索不限日期跨度**——召回可能涉及 5 年前批次，限制跨度会遗漏。

**追溯链六段**：

```text
采购订单 → 到货验收（注册证 + 有效期）→ 批次入库（批号 + 序列号 + 灭菌效期）
  → 出库到二级库（领用人 + 时间）→ 备台锁定（台次号）→ 术中消耗（扫码 + 护士）
  → 植入物使用登记（患者 ID + 眼别 + 术者）
```

**植入物使用记录必须永久保存**——《医疗器械监督管理条例》要求保存至有效期届满后 2 年，人工晶体寿命期终身，实际要求终身可追溯。

### 17.5 三条原文规则

**规则一：契约表必须双向填写。** 提供方写"谁调用我"，消费方写"我调用谁"。

**规则二：每个契约必须有 SLA。** 没有 SLA 的接口无法评估性能影响。

**规则三：每个同步调用必须有降级策略。**

| 降级策略 | 适用 |
|---|---|
| 缓存兜底 | 查名字、查价格 |
| 拒绝操作 | 校验类（不能放行不合法的数据） |
| 异步重试 | 通知类 |
| 忽略并记录 | 统计类 |

## 18. 常见误区

### 误区一："子模块就是代码目录"

**错。** 子模块是**数据所有权**的划分，不是目录的划分。

```
如果一个子模块"只是写在不同的文件夹里"，但两个子模块都能改同一张表，
那就等于没有划分。
```

**判断标准：** 每张表只能有一个子模块有写权限，其他子模块只能读。

### 误区二："同模块内可以随便调"

**错。** 同模块内的子模块之间也要走契约。

**为什么？** 因为将来拆服务时，同模块的子模块可能先拆开。

```
✅ 正确：M07-04 调 M07-01 的 service 方法 get_encounter()
❌ 错误：M07-04 直接写 m07_encounter 表
```

### 误区三："状态机可以分散写"

**错。** 一个实体的状态机，变更逻辑必须集中在一处。

```
以医嘱为例：
  m07_order.status 的变更只允许三个地方：
    ① M07-03 的 OrderService（DRAFT→ISSUED, →CANCELLED）
    ② M07-03 的 on_xxx 回调接口（PAID, EXECUTING, COMPLETED, REFUNDED, REJECTED）
    ③ M07-03 的定时任务（ISSUED→ABANDONED）

  其他任何地方都不许 setattr(order, "status", ...)
```

**实现手段：** 状态变更通过 `OrderStatusMachine.transition(from, to, context)` 统一入口，非法转换直接抛异常。

### 误区四："统计可以改业务数据"

**错。** 统计子模块必须只读。

**理由：** 一旦统计能改业务数据，数据的可信度就归零了——出问题时不知道是业务错了还是统计改错了。

### 误区五："工具类查询不需要鉴权"

**错。** M02 的强制规范六条适用于**所有接口**，包括"查询字典"这种看起来无害的接口。

**为什么？** 有人可以通过遍历字典接口推断系统结构。

### 误区六："跨模块数据可以联表查"

**错。** 跨模块只能走 HTTP 或事件。

```
❌ SELECT * FROM m07_order o JOIN m04_registration r ON o.registration_id = r.id
   （跨库，做不到）

✅ 先查 m07_order，再批量调 M04 取挂号信息，应用层 join
```

**如果性能不够怎么办？**

- 冗余快照字段（挂号号直接存在 m07_encounter 里）
- 建本地只读副本（通过事件同步）
