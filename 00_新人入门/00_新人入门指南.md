## 1. 三分钟了解这是个什么系统

### 1.1 一句话

**为一家二级眼科医院做的全院级 HIS（医院信息系统）**，共 23 个业务模块，目前完成 5 个。

### 1.2 三条主线

这套系统不是"把医院每个部门各做一个系统"，而是围绕**三条业务闭环**组织：

```
门诊闭环  预约 → 挂号 → 分诊 → 叫号 → 医生站 → 诊断 → 医嘱/处方
          → 检查检验 → 收费 → 发药 → 治疗 → 离院

住院闭环  入院登记 → 床位分配 → 住院医嘱 → 护理执行
          → 检查检验 → 手术 → 出院 → 结算

药品闭环  处方 → 审核 → 收费 → 发药 → 退药 → 库存 → 采购
```

**所有模块的职责，都能说清"我在哪条闭环的哪一环"**。如果你读某个模块时说不清它在哪一环，大概率是你还没找到它的位置——这正是本文档要解决的。

### 1.3 为什么是"眼科"医院而不是"综合"医院

这一点会影响你读代码时的每一个细节。眼科的特殊性渗透到了设计的最底层：

| 维度 | 综合医院 | 眼科医院 | 设计影响 |
|---|---|---|---|
| **部位** | 器官冗余（一个人两个肾） | **眼睛成对**，左右眼可同时患病 | 所有临床数据带**眼别**（OD/OS/OU） |
| **计价** | 按次 | **按眼**计价，双眼 = 2 倍 | `charge_by_eye` 字段，数量自动翻倍 |
| **用药** | 口服、静滴为主 | **滴眼液为主**，单次 1 滴 | 用"滴"计量，一支能滴多少次要算 |
| **手术** | 可多部位联合 | **必须单眼**，左右眼分别排期 | 手术医嘱眼别选 OU 直接拒绝 |
| **检查** | 全身影像 | OCT、视野、眼压、眼底照相 | 指标趋势按眼别对比 |
| **病历** | 大段文字 | 视力、眼压、裂隙灯结构化 | 同一份文书里左右眼并列 |

**记住一个例子：** 医生开"左氧氟沙星滴眼液"，选"每日 4 次、双眼、7 天"。系统要算出：需要 2 支（不是 1 支），因为双眼每天 8 滴，7 天 56 滴，一支 100 滴——但如果医生选"每日 6 次双眼"，就需要 3 支。**这个计算在 M07-05 处方模块里。**

### 1.4 技术栈

| 层 | 选型 |
|---|---|
| 语言 | Python 3.11+ |
| Web 框架 | FastAPI |
| ORM | SQLAlchemy 2.0（async） |
| 数据库 | **PostgreSQL 16**（asyncpg） |
| 缓存 | Redis 7 |
| 异步任务 | Celery + APScheduler |
| 校验 | Pydantic V2 |
| 迁移 | Alembic |
| 实时推送 | WebSocket |

> **为什么用 PostgreSQL 而不是 MySQL？**
> 大量使用 `JSONB`（病历内容、检查结果）、部分唯一索引（"一挂号一会话"）、表分区、`pg_trgm` 中文模糊搜索。这些在 MySQL 上要么没有，要么很难做对。

### 1.5 当前进度

| 模块 | 状态 | 子模块 | 文件 | 行数 |
|---|---|---|---|---|
| M01 主数据管理 | ✅ 完成 | 13 | 28 | 75,219 |
| M02 统一权限与安全 | ✅ 完成 | 7 | 16 | 31,051 |
| M03 患者服务与 EMPI | ✅ 完成 | 6 | 14 | 22,982 |
| M04 门诊管理 | ✅ 完成 | 7 | 16 | 37,103 |
| M07 医生工作站 | ✅ 完成 | 7 | 16 | 40,219 |
| M05 M06 M08~M23 | ⏳ 待设计 | — | — | — |

**为什么先做这 5 个？** 因为它们构成**门诊闭环的主干**，而且是所有后续模块的公共底座：

- M01 提供主数据（科室、职工、药品、收费项……所有模块都要读）
- M02 提供鉴权（所有接口都要过）
- M03 提供患者身份（所有业务都挂在患者上）
- M04 提供挂号（门诊的起点）
- M07 提供诊疗（门诊的核心）

**先做底座、再做业务**，是这个项目最重要的推进策略。

**为什么分三份而不是一份？**

### 5.2 为什么详细设计和数据结构要拆开

一个子模块的详细设计 **3000~4300 行**，数据结构 **1400~2100 行**。

合起来 6000 行，打开就卡，找不到东西。

拆开后：

| 你的场景 | 打开哪个 |
|---|---|
| 要理解业务流程 | 详细设计 第 3、6 章 |
| 要看某个页面长什么样 | 详细设计 第 5 章 |
| 要对接某个接口 | 详细设计 第 6 章 |
| 要写 SQL / ORM | 数据结构 |
| 要加字段 | 数据结构 |
| 要看校验规则 | 详细设计 第 8 章 |

详细设计的第 4 章是一个**指针块**，只告诉你去数据结构文件看，不重复内容。

文档之间大量交叉引用。看到这样的链接：

## 6. 文档模板：12 章都讲什么

全部 40 个子模块的详细设计，严格遵循同一个 12 章模板。**这是最强的可预期性**——你知道第 6 章一定是接口。

| 章 | 标题 | 讲什么 | 你什么时候会看 |
|---|---|---|---|
| 1 | 模块概述 | 职责、边界、设计目标、设计原则 | 第一次接触时 |
| 2 | 业务范围与边界 | **做什么 / 不做什么**、依赖上游、服务下游 | 判断改动归属时 |
| 3 | 业务模型 | 核心概念、实体关系、角色、状态机 | 理解业务时 |
| 4 | 数据结构设计 | **指针块** → 指向数据结构文件 | 几乎不看（去数据结构文件） |
| 5 | 页面设计 | ASCII 原型 + 字段说明 + 交互规则 | 做前端 / 联调时 |
| 6 | 后端接口设计 | 接口总览 + 请求/响应示例 | **最高频** |
| 7 | 缓存与异步任务设计 | Redis Key、TTL、Celery 任务、定时任务 | 查性能 / 排障时 |
| 8 | 业务规则与校验 | 校验清单、错误码、优先级 | 写校验逻辑时 |
| 9 | 权限与安全 | 权限点、数据权限、敏感字段、审计 | 加接口时 |
| 10 | 集成与契约 | 提供的接口、消费的接口、事件发布/订阅 | **跨模块改动必看** |
| 11 | 异常处理与日志 | 异常分类、日志规范、告警 | 排障时 |
| 12 | 验收标准 | `AC-xx` 功能、`PF-xx` 性能、`DA-xx` 数据、`SC-xx` 安全 | 测试时 |

### 6.1 第 2 章「边界」为什么最重要

每个子模块的第 2 章都有一张这样的表：

| 做什么 | 不做什么 | 归属 |
|---|---|---|
| 开检查申请单 | 执行检查 | M12 |
| 接收报告 | 生成报告 | M12 |
| 识别危急值 | 采集检验结果 | M13 |

**这张表解决的是"这个功能该放哪"的争议。**

新需求来了，先查目标模块的第 2 章——如果发现"不做什么"里写了它，就去归属模块。

### 6.2 第 6 章接口编号规律

```
| API-01 | GET /api/v1/m07/encounters/{id} | 接口名 | 说明 |
```

- 编号 `API-nn` 在**每个子模块内从 01 连续编**
- 路径前缀 `/api/v1/m0X/` 是**对外开放**的（给前端）
- 路径前缀 `/internal/v1/` 是**模块间内部调用**的（不对外暴露）

> **记住这条：看到 `/internal/` 就说明"别的模块会调我"。** 改这类接口前必须查第 10 章谁在用。

## 9. 常见困惑 FAQ

### Q1：为什么两个模块之间用 HTTP 接口，不直接跨库查表？

**三个原因：**

1. **边界清晰**——M07 想读患者姓名，只能调 `GET /internal/v1/patient/{id}/brief`。如果直接 `JOIN mpi_patient`，M03 一改表结构 M07 就崩了。
2. **可换实现**——将来 M03 独立部署到另一台服务器，网络调用不用改代码。
3. **数据权限集中**——M03 的接口内部做了隐私脱敏，跨库查会绕过。

**例外：** M01 主数据被大量读取，用了**本地缓存 + 版本号**（见 02 文档第 6 章），不走每次 HTTP。

### Q2：为什么不建数据库外键？

**决策：全部不建物理外键，应用层保证。**

| 理由 | 说明 |
|---|---|
| 分库分表友好 | 未来可能按模块分库 |
| 写入性能 | 避免外键检查开销 |
| 逻辑删除 | 外键与逻辑删除语义冲突 |

**替代保障：**

- Service 层写入前校验存在性
- **冗余快照**（`item_name`、`drug_name` 直接存一份，即使主数据改名历史文书也不变）
- 每日定时校验任务查孤儿数据

**你要记住的：** 写关联数据时，**先在 Service 层查一下父记录存在**，不要指望数据库拦你。

### Q3：为什么医嘱状态要由 M16/M12/M13/M14 回写，M07 不能自己改？

因为 **M07 不知道药有没有真的发出去**。

如果 M07 把状态改成"已完成"，而实际药房没发药，患者拿着系统记录去投诉，医院无法自证清白。

所以设计成：

```
M07 下达 → ISSUED   (M07 唯一能主动设的状态)
     ↓ 收费回调
M16 回写 → PAID
     ↓ 执行回调
M14 回写 → EXECUTING → COMPLETED
```

**每个状态变更都有明确的责任方，谁做的谁写。** 这是整套设计里最重要的原则之一。

### Q4：患者合并了，M07 里旧的 patient_id 怎么办？

**不迁移数据，用重定向。**

合并后：

- 旧 `patient_id` 标记为 `MERGED`，指向新 ID
- 各模块**保留原有数据不动**（历史记录仍挂旧 ID）
- 各模块收到 `mpi.patient.merged` 事件，在本地记录重定向表
- 查询时先查重定向表，再按新 ID 过滤

**为什么不迁移？** 12 万条会话、30 万条诊断，迁移要锁表很久，而且历史记录本来就该保持原样（那时确实用的旧 ID）。

### Q5：同样一个"科室列表"，为什么 M01 有、M04 也有？

**M01 是唯一数据源，M04 提供的是"排班视角的科室"。**

| 接口 | 提供方 | 返回什么 |
|---|---|---|
| `GET /internal/v1/mdm/depts` | M01 | 全部科室 |
| `GET /internal/v1/m04/schedule/by-doctor` | M04 | 按医生排班聚合的科室 |

M04 的数据来自 M01（缓存），但**加入了排班信息**。两个都要，不是重复。

### 10.3 文档自检脚本

改完跑一遍，能防住 90% 的低级错误：

```python
import re, ast, json, glob

FENCE = chr(96) * 3

for path in sorted(glob.glob("M*/*.md")) + sorted(glob.glob("0*/**/*.md", recursive=True)):
    text = open(path, encoding="utf-8").read()
    problems = []

    # 1. 代码围栏必须成对
    if text.count(FENCE) % 2 != 0:
        problems.append("围栏不成对")

    # 2. Python 代码块必须语法正确
    for i, block in enumerate(re.findall(FENCE + r"python\n(.*?)" + FENCE, text, re.S), 1):
        try:
            ast.parse(block)
        except SyntaxError as e:
            problems.append("Python 第 %d 块: %s" % (i, e.msg))

    # 3. JSON 代码块必须可解析
    for i, block in enumerate(re.findall(FENCE + r"json\n(.*?)" + FENCE, text, re.S), 1):
        try:
            json.loads(block)
        except Exception:
            problems.append("JSON 第 %d 块" % i)

    # 4. Markdown 表格列数必须一致
    for block in re.findall(r"((?:^\|.*\|$\n?)+)", text, re.M):
        rows = block.strip().split("\n")
        if len(rows) >= 2 and len(set(r.count("|") for r in rows)) > 1:
            problems.append("表格列数不一致")
            break

    # 5. 不允许出现替换字符（乱码）
    if chr(0xFFFD) in text:
        problems.append("含乱码字符")

    if problems:
        print(path, "->", problems)
```

**运行：** `python3 check.py`，无输出即全部通过。

### 10.4 写作约定

| 约定 | 原因 |
|---|---|
| 表格内联代码不要写裸竖线字符 | 会破坏 Markdown 列数解析 |
| 代码片段用围栏标记语言，不要用 `>` 引用块 | 引用块里的代码无法被脚本校验 |
| 中文散文 + ASCII 图 | 不依赖图片，纯文本可 diff |
| 每个接口给完整请求/响应 JSON | 联调时不用猜 |
| 验收标准编号化（`AC-xx`） | 可被测试用例直接引用 |
