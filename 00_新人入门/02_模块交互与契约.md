## 1. 模块间交互的五种方式

模块之间不共享数据库、不共享内存，只有五种通信方式：

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  方式 ①  同步 HTTP 查询                                              │
│  ─────────────────────                                              │
│  A ──── GET /internal/v1/xxx ────► B                                │
│  A ◄──── 200 { data } ─────────── B                                │
│                                                                     │
│  适用：需要立即拿到结果才能继续                                       │
│  例：   M07 查患者姓名、查药品价格                                    │
│                                                                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  方式 ②  同步 HTTP 命令（回写）                                       │
│  ─────────────────────────────                                      │
│  A ──── POST /internal/v1/xxx/on-yyyy ────► B                      │
│  A ◄──── 200 { ok } ─────────────────────  B                       │
│                                                                     │
│  适用：通知对方"状态变了，请更新"                                     │
│  例：   M16 通知 M07 "钱收了"、M14 通知 M07 "药发了"                  │
│                                                                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  方式 ③  异步事件（消息队列）                                         │
│  ───────────────────────────                                        │
│  A ──── publish topic=x.xxx.yyy ────► MQ ────► B, C, D（订阅方）    │
│                                                                     │
│  适用：不关心谁订阅、不要求立即完成                                   │
│  例：   MPI 患者合并、主数据变更、报告到达                            │
│                                                                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  方式 ④  共享缓存（Redis）                                            │
│  ────────────────────────                                           │
│  A ──── SET m01:mdm:dept:v12 ────► Redis ◄──── GET ──── B          │
│                                                                     │
│  适用：高频读取的公共数据，允许短暂不一致                              │
│  例：   字典项、参数、权限上下文                                      │
│                                                                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  方式 ⑤  定时任务拉取                                                 │
│  ────────────────────                                               │
│  A ──── 每天 02:00 GET /internal/v1/xxx/dataset ────► B             │
│                                                                     │
│  适用：批量数据、报表、离线计算                                       │
│  例：   M17 财务每天拉 M04 门诊日志、M07 工作量                        │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.1 怎么选

| 场景 | 选哪种 | 理由 |
|---|---|---|
| 展示页面需要对方的数据 | ① 同步查询 | 用户等不了 |
| 对方需要立刻知道状态变了 | ② 同步回写 | 状态机要准确 |
| 一个变更多方关心 | ③ 事件 | 解耦，加订阅方不改发布方 |
| 高频读同一份数据 | ④ 缓存 | 性能 |
| 批量对账、报表 | ⑤ 定时拉取 | 不影响在线 |

### 1.2 明确不用的方式

| 方式 | 为什么不用 |
|---|---|
| **跨库直连** | 边界消失，一方改表结构另一方崩 |
| **共享数据库事务** | 分布式事务复杂度高，性能差 |
| **共享内存** | 无法多机部署 |
| **RPC（gRPC）** | 当前规模不需要，HTTP 更易调试 |

> **一个例外：** M01 主数据的 `md_dict_item` 允许业务模块**只读**直连（因为它是近乎静态的字典）。但**写入必须走 M01 接口**。

### 2.1 路径命名规律

```
/internal/v1/{模块短名}/{资源}/{动作}
              │          │        │
              │          │        └─ on-xxx 表示"回写通知"
              │          └────────── 资源名（单数）
              └───────────────────── 模块短名

模块短名不是严格等于模块号：
  M01 → /internal/v1/mdm/*      (主数据)
        /internal/v1/charge/*   (收费项，M01-06)
        /internal/v1/clinical/* (临床主数据，M01-09)
        /internal/v1/surgery/*  (手术项目，M01-07)
        /internal/v1/optical/*  (视光产品，M01-08)
        /internal/v1/dict/*     (字典，M01-10)
        /internal/v1/param/*    (参数，M01-10)
        /internal/v1/approval/* (审批，M01-11)
        /internal/v1/distribute/*(分发，M01-12)

  M02 → /internal/v1/account/*  (账号)
        /internal/v1/auth/*     (认证)
        /internal/v1/session/*  (会话)
        /internal/v1/perm/*     (权限)
        /internal/v1/mfa/*      (二次验证)
        /internal/v1/audit/*    (审计)
        /internal/v1/sec/*      (安全)

  M03 → /internal/v1/patient/*  (主索引)
        /internal/v1/mpi/*      (匹配)
        /internal/v1/member/*   (会员)
        /internal/v1/followup/* (随访)
        /internal/v1/message/*  (消息)
        /internal/v1/portal/*   (门户)

  M04 → /internal/v1/m04/*      (统一前缀)
        /internal/v1/registration/* (预约，历史遗留)
        /internal/v1/schedule/*     (排班)

  M07 → /internal/v1/m07/*      (统一前缀)
        /internal/v1/m07/orders/*
        /internal/v1/m07/reports/*
        ...
```

> **注意：** M04 和 M07 用统一的 `m04/` `m07/` 前缀，M01/M02/M03 用资源语义前缀。这是**早期模块与后期模块的命名差异**，阅读时注意。

### 2.2 动作命名规范

| 动作 | 含义 | 调用方 |
|---|---|---|
| `GET /xxx/{id}` | 查详情 | 任意 |
| `GET /xxx/by-yyy/{id}` | 按某维度查 | 任意 |
| `POST /xxx/create` | 创建 | 任意 |
| `POST /xxx/on-yyy` | **回写通知** | 状态变更方 |
| `POST /xxx/check-yyy` | 校验 | 任意 |
| `POST /xxx/validate-yyy` | 校验 | 任意 |
| `POST /xxx/resolve` | 解析/计算 | 任意 |
| `POST /xxx/publish` | 发布 | M01 |
| `GET /xxx/for-yyy` | **为某用途定制** | 特定消费方 |
| `GET /xxx/pending/{id}` | 查待办 | 上游校验 |

### 2.3 `on-xxx` 是理解系统的钥匙

**看到 `on-` 前缀，说明这个接口是"被动接收状态变更"。**

```
POST /internal/v1/m07/orders/on-paid      ← 收费方告诉 M07："钱收了"
POST /internal/v1/m07/orders/on-completed ← 执行方告诉 M07："做完了"
POST /internal/v1/m04/registration/{id}/start-visit ← M07 告诉 M04："开始看了"
POST /internal/v1/audit/record            ← 所有方告诉 M02："记一笔审计"
```

**为什么 M04 的 start-visit 不带 `on-`？** 因为它不是"回写"，而是"请求一个状态转换"——M04 会做校验（挂号状态必须是已缴费），校验通过才转。

## 3. 核心契约一：患者身份（M03）

### 3.1 唯一身份原则

**全系统只认 `patient_id`，绝不用姓名或证件号做关联键。**

```python
# ✅ 正确：用 patient_id
patient = await MpiClient().get_patient(patient_id)
```

```
# ❌ 错误：用姓名关联
SELECT * FROM m07_order WHERE patient_name = '张三'
```

**原因：** 同名同姓、证件号录入错误、患者改名——任何以姓名为键的设计都会在半年后崩溃。

### 3.2 M03 提供的核心接口

| 接口 | 用途 | 调用方 | SLA |
|---|---|---|---|
| `GET /internal/v1/patient/{id}/brief` | **患者简要**（姓名/性别/年龄/手机） | 全部 | ≤ 50ms |
| `GET /internal/v1/patient/by-empi/{empi_no}` | 按 EMPI 号查 | 全部 | ≤ 50ms |
| `POST /internal/v1/patient/ensure` | 确保存在（不存在则建） | M04 挂号 | ≤ 100ms |
| `GET /internal/v1/patient/by-id-hash` | 按证件号哈希查 | M04 挂号 | ≤ 50ms |
| `GET /internal/v1/mpi/match/instant` | 即时匹配 | M04 挂号 | ≤ 200ms |
| `GET /internal/v1/patient/changes` | 增量变更（拉取） | 全部 | ≤ 100ms |
| `GET /internal/v1/patient/{id}/primary-contact` | 主要联系人 | M07、M19 | ≤ 30ms |

### 3.3 患者合并：全系统最复杂的交互

**场景：** 张三今天用身份证挂号，上次用医保卡挂号，系统建了两个档案。合并后，历史记录怎么办？

```
【合并前】
  patient_id = 1001  （张三，身份证）  ← 12 万条历史数据挂在这
  patient_id = 1002  （张三，医保卡）  ← 3 条历史数据挂在这

【合并后】
  patient_id = 1001  （主档案，正常运行）
  patient_id = 1002  → status = 'MERGED'，merged_into = 1001
```

**关键决策：不迁移数据。**

**那怎么查到 1002 的历史记录？**

```
┌──────────────────────────────────────────────────────────────┐
│ M03-02 执行合并                                              │
│  ① 更新 1002.status = 'MERGED', 1002.merged_into = 1001     │
│  ② 记录合并日志                                             │
│  ③ 发布事件 mpi.patient.merged                              │
│     { "from_patient_id": 1002, "to_patient_id": 1001,       │
│       "merge_id": "MG20261021001" }                         │
└───────────────────┬──────────────────────────────────────────┘
                    │ 事件广播
     ┌──────────────┼──────────────┬──────────────┐
     ▼              ▼              ▼              ▼
┌─────────┐  ┌─────────┐   ┌─────────┐   ┌─────────┐
│ M04     │  │ M07     │   │ M14     │   │ M19     │
│ 挂号    │  │ 医生站  │   │ 药房    │   │ 随访    │
└────┬────┘  └────┬────┘   └────┬────┘   └────┬────┘
     │            │             │             │
     ▼            ▼             ▼             ▼
  各自记录重定向映射（本地表）
  patient_merge_redirect(旧ID → 新ID)
```

**查询时怎么用：**

```python
# 查询患者全部历史处方
async def get_all_prescriptions(patient_id: int):
    # ① 查重定向表，拿到所有等价 ID
    ids = [patient_id]
    redirect = await repo.get_redirect(patient_id)
    if redirect:
        ids.append(redirect.target_id)

    # ② 按所有 ID 查
    stmt = select(M07Prescription).where(
        M07Prescription.patient_id.in_(ids)
    )
    return await db.execute(stmt)
```

### 3.4 为什么各模块要自己记录重定向

```
M03 的重定向表：  1002 → 1001
M07 的重定向表：  1002 → 1001   （M07 自己记的）

为什么不直接查 M03？
  ① 性能：每次查询多一次 HTTP，P95 加 50ms
  ② 可用性：M03 挂了 M07 还能查历史
  ③ 解耦：M03 的重定向表结构变了不影响 M07
```

**代价：** 一致性靠事件保证。如果事件丢了，M07 的重定向表会缺数据。

**兜底：** 每日 02:00 定时任务，拉 `GET /internal/v1/patient/changes?since=昨天` 补漏。

### 3.5 M07 处理患者合并的实际代码

```python
@router.post("/internal/v1/m07/encounter/on-patient-merged")
async def on_patient_merged(
    payload: PatientMergedEvent,
    db: AsyncSession = Depends(get_db),
):
    """M03-02 患者合并后，M07 更新本地引用"""
    from_id = payload.from_patient_id
    to_id = payload.to_patient_id

    # ① 记录重定向（用于查询时扩展）
    await redirect_repo.create(
        db,
        source_patient_id=from_id,
        target_patient_id=to_id,
        merge_id=payload.merge_id,
        redirect_type="PATIENT",
    )

    # ② 未完成的会话切到新 ID（进行中的就诊不能丢）
    await db.execute(
        update(M07Encounter)
        .where(
            M07Encounter.patient_id == from_id,
            M07Encounter.status.in_(["WAITING", "CALLED", "VISITING"]),
        )
        .values(patient_id=to_id, patient_id_redirected=True)
    )

    # ③ 已完成的会话保持原样（历史记录不变）
    #    查询时通过重定向表扩展

    # ④ 清缓存
    await cache.delete_pattern(f"m07:encounter:patient:{from_id}:*")

    await db.commit()
    return {"code": 0, "message": "success", "data": {"redirected": True}}
```

**注意代码里的三个细节：**

1. **进行中的会话切 ID，已完成的保持原样** —— 因为进行中的就诊如果还是旧 ID，后续所有操作都会挂到孤儿上
2. **记录 `patient_id_redirected` 标记** —— 方便排查
3. **清缓存用模式匹配** —— 患者的缓存键都带 patient_id

## 4. 核心契约二：权限与审计（M02）

### 4.1 三个层次

```
第 1 层：认证（你是谁）
  Token → 解析出 staff_id
  
第 2 层：鉴权（你能做什么）
  权限点校验 → 能不能调这个接口
  
第 3 层：数据权限（你能看谁的）
  SQL 注入 → 只能看本科室的患者
  
第 4 层：审计（你做了什么）
  写操作 → 记一笔审计日志
```

### 4.2 M02 提供的核心接口

| 接口 | 用途 | 调用方 | SLA |
|---|---|---|---|
| `POST /internal/v1/perm/check` | 权限点校验 | 全部 | ≤ 10ms |
| `GET /internal/v1/perm/context/{staff_id}` | 权限上下文（一次性拿全） | 全部 | ≤ 20ms |
| `POST /internal/v1/perm/filter-sql` | **数据权限 SQL 片段** | 全部 | ≤ 20ms |
| `POST /internal/v1/perm/mask-fields` | 敏感字段脱敏规则 | 全部 | ≤ 10ms |
| `POST /internal/v1/audit/record` | 记审计日志 | 全部 | ≤ 30ms |
| `POST /internal/v1/audit/record-batch` | 批量审计 | 全部 | ≤ 100ms |
| `POST /internal/v1/sec/check-ip` | IP 校验 | 全部 | ≤ 20ms |
| `POST /internal/v1/sec/check-rate-limit` | 限流 | 全部 | ≤ 20ms |
| `POST /internal/v1/sec/check-malicious` | 恶意请求检测 | 全部 | ≤ 20ms |
| `POST /internal/v1/sec/risk/evaluate` | 风险评估 | 全部 | ≤ 50ms |
| `POST /internal/v1/mfa/verify` | 二次验证 | 高风险模块 | ≤ 100ms |
| `POST /internal/v1/token/validate` | Token 校验 | 全部 | ≤ 10ms |

### 4.3 数据权限：最容易被忽视的坑

**问题：** 医生只能看本科室的患者，护士只能看自己病区的，财务能看全部。

**天真的做法（❌）：**

```
# 每个查询都手写过滤条件
if user.role == 'DOCTOR':
    stmt = stmt.where(Order.dept_id == user.dept_id)
elif user.role == 'ADMIN':
    pass  # 不加过滤
elif user.role == 'FINANCE':
    ...   # 又一份逻辑
```

**问题：** 50 个接口 50 份逻辑，改一次全得改，漏一个就是数据泄露。

**正确做法（✅）：**

```python
from app.core.permission import apply_data_scope_to_stmt

@router.get("/orders")
async def list_orders(
    db: AsyncSession = Depends(get_db),
    user=Depends(get_current_user),
):
    stmt = select(M07Order)

    # 一行注入，自动按用户的数据权限加 WHERE
    stmt = await apply_data_scope_to_stmt(
        stmt, M07Order, user, domain="DEPT"
    )

    rows = (await db.execute(stmt)).scalars().all()
    return success_response(rows)
```

**`apply_data_scope_to_stmt` 内部做了什么：**

```python
async def apply_data_scope_to_stmt(stmt, model, user, domain):
    """把数据权限转换成 SQL WHERE 条件"""
    context = await get_permission_context(user.staff_id)

    scope = context.data_scopes.get(domain)  # DEPT / HOSPITAL / SELF / ALL

    if scope.type == "ALL":
        return stmt  # 不限制

    if scope.type == "HOSPITAL":
        return stmt.where(model.hospital_id == scope.hospital_id)

    if scope.type == "DEPT":
        return stmt.where(model.dept_id.in_(scope.dept_ids))

    if scope.type == "SELF":
        return stmt.where(model.doctor_id == user.staff_id)

    raise BizException(51201, "无数据权限")
```

**数据权限域（domain）取值：**

| domain | 适用表 | 含义 |
|---|---|---|
| `DEPT` | 有 `dept_id` 字段的表 | 按科室 |
| `HOSPITAL` | 有 `hospital_id` 的 | 按院区 |
| `SELF` | 有 `doctor_id`/`nurse_id` 的 | 只看自己的 |

## 5. 核心契约三：主数据（M01）

### 5.1 为什么主数据要特殊对待

| 特征 | 说明 |
|---|---|
| **读取极高频** | 每个页面都要显示科室名、药品名 |
| **变更极低频** | 药品字典一天改几次 |
| **数据量小** | 全部字典加起来几万条 |

**如果每次都 HTTP 查询：**

- M07 打开一个页面要查 10 次字典 = 10 次 HTTP = 300ms
- M01 承受全院每秒几千次字典查询

**所以：本地缓存 + 版本号。**

### 5.2 缓存 + 版本号机制

```
     ┌────────────┐
```

|---|---|---|

### 6.4 会话模型：M07 的核心设计

**M07-01 的核心规则：一次挂号对应一个会话。**

```sql
-- 部分唯一索引：未删除的挂号只能有一个会话
CREATE UNIQUE INDEX uk_m07_encounter_reg
    ON m07_encounter (registration_id)
    WHERE is_deleted = FALSE;
```

**为什么一挂号一会话？**

| 如果允许多个会话 | 后果 |
|---|---|
| 同一次挂号开出两个会话 | 诊断、医嘱不知道挂哪个 |
| 统计时重复计算 | 接诊量翻倍 |
| 完成校验时只校验一个 | 另一个遗漏 |

**如果患者需要复诊？** 重新挂号 → 新的 `registration_id` → 新的会话。**这是正确的业务语义**——复诊是新的就诊。

### 6.5 会话与挂号的字段冗余

**M07 的会话表冗余了挂号的关键字段：**

```sql
CREATE TABLE m07_encounter (
    id              BIGINT,          -- 会话 ID
    registration_id BIGINT NOT NULL, -- 挂号 ID（关联 M04）
    patient_id      BIGINT NOT NULL, -- 患者 ID（冗余，避免每次查 M03）
    doctor_id       BIGINT NOT NULL, -- 医生 ID
    dept_id         BIGINT NOT NULL, -- 科室 ID（冗余，数据权限用）
    queue_no        INT,             -- 排队号（冗余）
    patient_name_snapshot  VARCHAR(50),  -- 姓名快照
    ...
);
```

**为什么冗余？**

| 冗余字段 | 用途 |
|---|---|
| `patient_id` | 免去 "挂号 → 查 patient_id" 的步骤 |
| `dept_id` | 数据权限必须本地有 dept_id 才能过滤 |
| `queue_no` | 叫号、完成校验时直接用 |
| `patient_name_snapshot` | 患者改名后，历史文书仍显示当时姓名 |

**快照 vs 实时查询的原则：**

```
实时查询：会变且必须最新的  → 患者姓名（当前显示）、药品价格
快照：    会变但历史不该变的 → 文书上的姓名、当时的诊断名称
```

### 7.3 为什么需要 `on-executing` 这个中间状态

**如果没有 `EXECUTING`：**

```
ISSUED → PAID → COMPLETED

      无法知道"正在做"
```

**有了 `EXECUTING`：**

- 检查科室能显示"正在进行"的队列
- 患者能在大屏看到"正在检查"
- 若长时间卡在 `EXECUTING` 可以告警（可能忘了回调）

### 7.5 回写接口的幂等设计

**问题：** M16 回调超时重试，会导致 M07 收到两次 `on-paid`。

**解决方案：状态检查 + 唯一约束**

```python
async def on_paid(order_id: int, payload: OnPaidRequest, db: AsyncSession):
    order = await repo.get_for_update(db, order_id)  # 行锁

    # 幂等检查：已经是 PAID 或更后状态，直接返回成功
    if order.status in ("PAID", "EXECUTING", "COMPLETED", "REFUNDED"):
        return {
            "code": 0,
            "message": "already_paid",
            "data": {"order_id": order_id, "idempotent": True},
        }

    # 状态校验：只有 ISSUED 能转 PAID
    if order.status != "ISSUED":
        raise BizException(54765, "医嘱状态不允许缴费回写")

    order.status = "PAID"
    order.paid_at = payload.paid_at
    order.billing_no = payload.billing_no
    order.fee_amount = payload.paid_amount

    await repo.save(db, order)
    await db.commit()

    # 发布事件（异步，失败不影响主流程）
    await event_bus.publish("m07.order.paid", {...})

    return {"code": 0, "message": "success", "data": {"order_id": order_id}}
```

**三个关键点：**

1. **`SELECT ... FOR UPDATE`** —— 并发调用时只有一个能拿到锁
2. **幂等检查在状态校验之前** —— 重复调用返回成功而不是报错
3. **事件在 commit 之后发布** —— 保证数据库已提交

### 7.6 定时任务：超时未缴费自动取消

```
M07 定时任务（每小时）
      ↓
扫描 status='ISSUED' AND created_at < now() - 12h
      ↓
标记 status='ABANDONED'，记录 abandoned_at
      ↓
发布事件 m07.order.abandoned
```

**为什么 12 小时？** 参数 `M07.ORDER.ABANDON_HOURS`，默认 12。药房当天下午 5 点前没发药的处方会作废。

### 8.5 事件的可靠性设计

```
生产者                          消费者
  │                              │
  │ ① 业务事务提交（DB）          │
  │ ② 写入 outbox 表 ────────────┼── 同一事务！
  │ ③ 定时扫描 outbox            │
  │    ──── publish ────────────►│
  │                              │ ④ 幂等检查（event_id）
  │                              │ ⑤ 处理
  │                              │ ⑥ ack
  │ ⑦ 标记 outbox 已发送         │
```

**为什么用 outbox 而不是直接发？**

如果业务事务成功但消息发送失败，下游就永远不知道。outbox 保证**"要么都成功，要么都不发"**。

**消费方的幂等：**

```python
async def handle_order_paid(event: dict):
    event_id = event["event_id"]

    # 已处理过则跳过
    if await seq_seen(event_id):
        return

    # 标记已处理（Redis SETNX，TTL 7 天）
    await mark_seen(event_id, ttl=86400 * 7)

    # 处理
    await process(event)
```

### 8.6 事件的顺序性

**问题：** `m07.order.issued` 和 `m07.order.paid` 可能乱序到达。

**解决：** 消费方检查业务状态。

```python
if event_type == "m07.order.paid":
    if order.status != "ISSUED":
        # 状态不对，说明 issued 还没处理（或已处理）
        if order.status in ("PAID", "EXECUTING", "COMPLETED"):
            return  # 幂等，跳过
        else:
            # 真正的乱序，延迟重试
            raise RetryLater()
```

## 9. 数据一致性策略

### 9.1 不强求强一致

**医疗系统里，不是所有数据都需要强一致：**

| 数据类型 | 一致性要求 | 策略 |
|---|---|---|
| 收费金额 | **强一致** | 事务 + 对账 |
| 医嘱状态 | **强一致** | 状态机 + 幂等 |
| 患者身份 | **强一致** | 唯一索引 |
| 字典名称 | 最终一致 | 缓存 + 版本号 |
| 报表统计 | 最终一致 | 定时汇总（T+1） |
| 消息通知 | 最终一致 | 重试 |

### 9.2 事务边界

**原则：一个事务只操作一个模块的数据库。**

```python
# ✅ 正确：M07 的事务只碰 M07 的表
async def issue_order(order_id: int, db: AsyncSession):
    async with db.begin():
        order = await repo.get(db, order_id)
        order.status = "ISSUED"
        order.issued_at = now()
        await log_repo.create(db, order_id, "ISSUE", ...)
    # 提交后发布事件
    await event_bus.publish("m07.order.issued", {...})

# ❌ 错误：试图在 M07 事务里写 M16 的表
async def issue_order_wrong(order_id: int, db: AsyncSession):
    async with db.begin():
        order.status = "ISSUED"
        # 跨库操作，无法保证原子性
        await billing_db.execute("INSERT INTO billing ...")
```

### 9.3 分布式事务的替代方案

**场景：** 医生开医嘱 + 收费，两个模块都要写。

**方案：Saga（补偿事务）**

```
① M07 创建医嘱（status=ISSUED）
        ↓ 成功
② 调用 M16 创建收费单
        ↓ 失败
③ M07 补偿：医嘱改为 CANCELLED
```

**代码：**

```python
async def create_order_and_bill(order_data):
    order = await order_service.create(order_data)  # ①

    try:
        bill = await billing_client.create_bill(order)  # ②
    except Exception:
        await order_service.cancel(order.id, reason="收费单创建失败")  # ③
        raise

    return order, bill
```

**但本系统实际上是这样做的：**

```
不同于上面的"开单即收费"模型，
本系统采用"先开单、后收费"：

① M07 开医嘱 → ISSUED
② 患者去收费处 → M16 主动拉取待收费清单
③ M16 收费 → 回调 M07 on-paid
```

**为什么？** 因为医院的实际流程就是"先看诊，后统一缴费"，不是一个医嘱一次收费。这样：

- 一次就诊的所有医嘱可合并收费
- 不需要跨模块事务
- 补偿逻辑简单

### 9.4 对账任务

**即使有幂等和 Saga，仍然需要定时对账。**

| 对账任务 | 频率 | 检查内容 |
|---|---|---|
| 医嘱状态对账 | 每日 02:00 | M07 已付费医嘱 vs M16 收费记录 |
| 报告完整性 | 每日 02:30 | M07 收到报告数 vs M12/M13 生成报告数 |
| 患者合并一致性 | 每日 03:00 | M03 合并记录 vs 各模块重定向表 |
| 孤儿数据 | 每日 03:30 | 引用了不存在的患者/科室 |
| 工作量汇总 | 每日 04:00 | 明细重算 vs 汇总表 |

**对账不一致怎么办：**

```
严重程度分级：
  P0 收费金额不一致  → 立即告警 + 人工介入
  P1 状态不一致      → 自动修复 + 记录
  P2 统计数据偏差    → 重算 + 记录
  P3 孤儿数据        → 标记 + 保留（不删）
```

### 10.1 对称原则

**任何跨模块契约，必须在两处文档中同时出现：**

```
| 接口 | 提供方 | 说明 |
| POST /internal/v1/m07/orders/on-paid | M07 | 收费回写 |
```

**改契约时必须两边都改。**

### 10.2 变更检查清单

改任何内部接口前：

| 步骤 | 动作 |
|---|---|
| 1 | 在提供方文档第 10 章找到这个接口 |
| 2 | 查看"调用方"列，列全部消费方 |
| 3 | 逐个打开消费方文档，确认它怎么用 |
| 4 | 评估改动是否破坏兼容性 |
| 5 | 如需破坏性变更，走版本化（见 10.3） |
| 6 | 两边文档同步更新 |

### 10.3 兼容性规则

| 改动 | 是否兼容 | 处理 |
|---|---|---|
| 增加可选请求字段 | ✅ 兼容 | 直接加 |
| 增加响应字段 | ✅ 兼容 | 直接加 |
| 增加新接口 | ✅ 兼容 | 直接加 |
| **删除响应字段** | ❌ 破坏 | 先标记废弃，观察期后删 |
| **修改字段类型** | ❌ 破坏 | 新增字段，新旧并存 |
| **修改必填性**（可选→必填） | ❌ 破坏 | 先改可选 + 告警，后改必填 |
| **修改语义** | ❌ 破坏 | 新开接口 |

### 10.4 版本化策略

```
/internal/v1/m07/orders/on-paid          当前版本
/internal/v2/m07/orders/on-paid          新版本

规则：
  ① 新旧版本并存至少 3 个月
  ② 旧版本保留但记录调用量
  ③ 调用量降为 0 后再下线
  ④ 下线前 30 天通知所有消费方
```
