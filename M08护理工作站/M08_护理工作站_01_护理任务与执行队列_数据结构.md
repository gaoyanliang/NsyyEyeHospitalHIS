**设计说明：**

1. **`m08_task` 是唯一权威表**，其余四张表都是围绕它的附属记录（转派、协作、暂停）或派生数据（队列快照）。任务的任何状态变更只在 `m08_task` 上发生。

2. **不建外键（FK）约束**。理由：
   - `m08_task` 是高频写入表（每日新建数百条），外键检查会带来额外的锁开销
   - M08 各子模块可能独立部署，跨模块外键在跨库时无法工作
   - 一致性由应用层 + 定时对账保证（每日 03:00 校验孤儿记录）

3. **`m08_task_queue` 是快照表，不是权威数据**。它存在的唯一目的是让大屏与缓存预热不每次扫 `m08_task`。若两者不一致，以 `m08_task` 为准，重建队列即可。

4. **`m08_task_transfer` / `m08_task_pause` 只增不改**，用触发器强制。理由：转派与暂停是「发生过的事」，任何修改都会破坏追溯链。查当前状态读 `m08_task`，查历史读这两张表。

5. **`m08_task_collab` 用软删除而非物理删除**。移除协作人时置 `is_deleted = TRUE`，保留「谁曾经协作过」的记录——绩效考核需要。

6. **`m08_task_config` 与业务表无关联**，是纯配置表。唯一索引必须用 `COALESCE(scope_id, 0)` 而非直接 `(param_code, scope, scope_id)` 组合唯一，原因见 4.7 节说明。

7. **不建分区**。`m08_task` 年行数约 15 万（日均 400 条/院），15 年累计 225 万行，单表完全可承受。若按 `planned_date` 分区，唯一索引必须包含分区键，会导致「跨年的同一执行点可以重复生成任务」——破坏幂等性。

### 4.2 表：`m08_task`

**用途：** 护理任务主表。每条记录代表「一名护士需要在某个时刻为某个患者做的一件事」。这是 M08-01 的唯一权威数据源，所有状态变更都在这里发生。

**约束说明：**

```sql
-- 任务编号格式校验
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_no
  CHECK (task_no ~ '^TK[0-9]{8}[0-9]{6}$');

-- 来源类型枚举
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_source_type
  CHECK (source_type IN ('ORDER', 'VITAL', 'ASSESS', 'EYEDROP', 'PREPARE', 'ALERT'));

-- 任务类型枚举
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_type
  CHECK (task_type IN ('NORMAL', 'STAT', 'URGENT'));

-- 状态枚举
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_status
  CHECK (status IN ('PENDING', 'CLAIMED', 'EXECUTING', 'HOLD',
                    'COMPLETED', 'SKIPPED', 'CANCELLED', 'MERGED'));

-- 眼别枚举
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_eye_side
  CHECK (eye_side IN ('OD', 'OS', 'OU', 'NA'));

-- 滴眼任务必须有眼别（眼科核心约束）
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_eyedrop_side
  CHECK (source_type <> 'EYEDROP' OR eye_side IN ('OD', 'OS', 'OU'));

-- 护理级别枚举
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_nursing_level
  CHECK (nursing_level IS NULL
         OR nursing_level IN ('LEVEL_1', 'LEVEL_2', 'LEVEL_3'));

-- 医嘱类任务必须有关联医嘱
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_order_ref
  CHECK (source_type NOT IN ('ORDER', 'EYEDROP') OR order_id IS NOT NULL);

-- 认领状态必须有责任人
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_claimed
  CHECK (status IN ('PENDING', 'CANCELLED', 'MERGED') OR assigned_nurse_id IS NOT NULL);

-- 已完成必须有执行记录编号与完成时间
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_completed
  CHECK (status <> 'COMPLETED'
         OR (execution_no IS NOT NULL
             AND completed_at IS NOT NULL
             AND assigned_nurse_id IS NOT NULL));

-- 已跳过必须有原因与说明（≥10 字）
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_skipped
  CHECK (status <> 'SKIPPED'
         OR (skip_reason IS NOT NULL
             AND skip_note IS NOT NULL
             AND char_length(btrim(skip_note)) >= 10));

-- 已取消必须有取消时间
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_cancelled
  CHECK (status <> 'CANCELLED' OR completed_at IS NOT NULL);

-- 已合并必须有目标
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_merged
  CHECK (status <> 'MERGED'
         OR (merged_into_id IS NOT NULL AND merged_into_id <> id));

-- 计划时间必须落在计划日期当天
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_planned_date
  CHECK (planned_time::date = planned_date);

-- 超时标记必须带时间
ALTER TABLE m08_task
  ADD CONSTRAINT ck_m08_task_overdue_at
  CHECK (is_overdue = FALSE OR overdue_at IS NOT NULL);

-- 暂停原因无关：HOLD 状态由 m08_task_pause 记录

-- 表与字段注释
COMMENT ON TABLE m08_task IS 'M08-01 护理任务主表';
COMMENT ON COLUMN m08_task.task_no IS '任务编号 TK+YYYYMMDD+6位序号';
COMMENT ON COLUMN m08_task.source_type IS '来源类型 ORDER/VITAL/ASSESS/EYEDROP/PREPARE/ALERT';
COMMENT ON COLUMN m08_task.source_id IS '来源实体ID，与 source_type 组成幂等唯一键';
COMMENT ON COLUMN m08_task.task_summary IS '队列显示用摘要，生成后不再刷新';
COMMENT ON COLUMN m08_task.planned_time_snapshot IS '计划时间快照，永不修改，供执行记录溯源';
COMMENT ON COLUMN m08_task.priority_score IS '优先级分数，由 6.6 节算法计算后落库';
COMMENT ON COLUMN m08_task.execution_no IS '指向 M08-03/M08-06 执行记录';
COMMENT ON COLUMN m08_task.merge_group_key IS '合并分组键 patient_id+planned_date 的哈希前 16 位';
COMMENT ON COLUMN m08_task.is_deleted IS '软删除，任务完成后不删除只改状态';
```

```
   终态                              终态               终态

旁支：
  PENDING/CLAIMED/ASSESS/VITAL/PREPARE 可被合并 → MERGED（终态）
```

**合法状态转移表：**

| 当前状态 | 可转移至 |
|---|---|
| `PENDING` | `CLAIMED`、`CANCELLED`、`MERGED` |
| `CLAIMED` | `EXECUTING`、`HOLD`、`COMPLETED`、`SKIPPED`、`CANCELLED`、`PENDING`（释放）、`MERGED` |
| `EXECUTING` | `COMPLETED`、`HOLD`、`SKIPPED` |
| `HOLD` | `CLAIMED`、`EXECUTING`、`CANCELLED` |
| `COMPLETED` | — （终态） |
| `SKIPPED` | — （终态） |
| `CANCELLED` | — （终态） |
| `MERGED` | — （终态） |

**设计要点：**

1. **为什么 `planned_time_snapshot` 与 `planned_time` 是两个字段。**
   M08-02 的执行点可能被修改（医生改医嘱时间），此时 `planned_time` 要跟着变。但一旦任务被认领或执行，历史记录里的「原本该 8:00 做」这个事实不能被篡改。所以生成任务时把 `planned_time` 复制一份到 `planned_time_snapshot`，之后永不修改 `snapshot`。

2. **为什么冗余 `patient_name` / `bed_no` / `task_summary`。**
   队列查询要快。如果每次查任务都要 JOIN M03 患者表、M06 床位表、M07 医嘱表，单次查询 3 表 JOIN 约 40ms，86 条任务就是 400ms。冗余后只扫一张表，15ms。
   代价是「患者在 M03 改名后，队列里还是旧名」。这个代价可接受：改名极低频，且队列是当班临时数据，跨日就重建。

3. **为什么 `priority_score` 要落库。**
   排序算法依赖「当前时间」（计算超时分钟），是**动态**的。如果每次查询都算，86 条任务每条算 6 个因子，约 3ms，可接受但浪费。
   落库的好处是：①可以用 SQL 直接 `ORDER BY priority_score DESC` ②可以建索引。坏处是分数会随时间漂移（8:00 的任务在 8:50 分数应该更高）。
   **折中方案**：落库存基础分（来源+紧急+护理级别），超时加成在查询时动态加。见 6.6 节 `_calc_score`。

4. **为什么 `uk_m08_task_source` 不加 `is_deleted` 条件。**
   幂等性要求「同一执行点永远只有一个任务」。若加了 `is_deleted = FALSE` 条件，软删除后可以重新生成第二个——那就破坏了幂等。所以这里是**全表唯一**，即使软删除也不能重建。
   若要允许重建，正确做法是恢复原记录（`is_deleted = FALSE`），而不是插入新行。

5. **为什么 `ck_m08_task_planned_date` 校验 `planned_time::date = planned_date`。**
   这两个字段若不一致，按日期统计会出现「任务算在 10-20 但实际计划时间在 10-21」的错账。用 DB 约束强制一致，比应用层校验可靠。

6. **为什么滴眼任务必须有眼别（`ck_m08_task_eyedrop_side`）。**
   眼科护理最严重的差错是「滴错眼」。滴眼任务不带眼别，护士无从核对。这个约束在 DB 层强制，任何代码路径都无法绕过。

**量级估算：**

| 项目 | 数值 | 计算依据 |
|---|---|---|
| 日均任务数 | 400 | 日间手术 50 台 × 6 项 + 门诊治疗 100 人次 |
| 年任务数 | 146,000 | 400 × 365 |
| 单行平均长度 | 约 600 字节 | 含 JSONB `task_detail` 约 120 字节 |
| 年数据量 | 约 88 MB | 146,000 × 600 |
| 15 年累计 | 约 2,190,000 行 / 1.3 GB | 含索引约 2.2 GB |

**分区：** 不分区。理由见 4.1 节设计说明第 7 条。

### 4.3 表：`m08_task_queue`

**用途：** 队列快照表。为每个护士、每个病区缓存「某一天的任务 ID 列表与统计数字」，供大屏与缓存预热使用，避免每次刷新都扫 `m08_task`。

**字段定义：**

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | IDENTITY | 主键 |
| `queue_type` | VARCHAR(16) | 否 | — | 队列类型：`NURSE` 护士 / `WARD` 病区 |
| `nurse_id` | BIGINT | 是 | NULL | 护士 ID（`queue_type = 'NURSE'` 时必填） |
| `ward_id` | BIGINT | 否 | — | 病区 ID |
| `queue_date` | DATE | 否 | — | 队列日期 |
| `task_ids` | JSONB | 否 | `'[]'::jsonb` | 任务 ID 数组（按优先级降序） |
| `task_count` | INTEGER | 否 | 0 | 任务总数（`jsonb_array_length(task_ids)` 的冗余） |
| `pending_count` | INTEGER | 否 | 0 | 待认领数 |
| `claimed_count` | INTEGER | 否 | 0 | 已认领数 |
| `executing_count` | INTEGER | 否 | 0 | 执行中数 |
| `hold_count` | INTEGER | 否 | 0 | 暂停数 |
| `overdue_count` | INTEGER | 否 | 0 | 超时数 |
| `completed_count` | INTEGER | 否 | 0 | 已完成数 |
| `generated_at` | TIMESTAMP | 否 | NOW() | 快照生成时间 |
| `expire_at` | TIMESTAMP | 否 | — | 快照过期时间（跨日自动过期） |
| `created_at` | TIMESTAMP | 否 | NOW() | 创建时间 |
| `updated_at` | TIMESTAMP | 否 | NOW() | 更新时间 |
| `is_deleted` | BOOLEAN | 否 | FALSE | 软删除标记 |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m08_task_queue` | 主键 | `id` | — |
| `uk_m08_queue_nurse` | 唯一（部分） | `(nurse_id, queue_date)` WHERE `queue_type = 'NURSE' AND is_deleted = FALSE` | 一护士一日一条 |
| `uk_m08_queue_ward` | 唯一（部分） | `(ward_id, queue_date)` WHERE `queue_type = 'WARD' AND is_deleted = FALSE` | 一病区一日一条 |
| `idx_m08_queue_expire` | B-Tree | `(expire_at)` WHERE `is_deleted = FALSE` | 过期清理 |

**约束说明：**

```sql
ALTER TABLE m08_task_queue
  ADD CONSTRAINT ck_m08_queue_type
  CHECK (queue_type IN ('NURSE', 'WARD'));

-- NURSE 类型必须有护士 ID
ALTER TABLE m08_task_queue
  ADD CONSTRAINT ck_m08_queue_nurse
  CHECK (queue_type <> 'NURSE' OR nurse_id IS NOT NULL);

-- WARD 类型不能有护士 ID
ALTER TABLE m08_task_queue
  ADD CONSTRAINT ck_m08_queue_ward
  CHECK (queue_type <> 'WARD' OR nurse_id IS NULL);

-- task_count 必须与数组长度一致
ALTER TABLE m08_task_queue
  ADD CONSTRAINT ck_m08_queue_count
  CHECK (task_count = jsonb_array_length(task_ids));

-- task_ids 必须是数组
ALTER TABLE m08_task_queue
  ADD CONSTRAINT ck_m08_queue_ids_type
  CHECK (jsonb_typeof(task_ids) = 'array');

-- 需要精确计算 jsonb_array_length，用不变式而非生成列
-- （PG16 不允许在 CHECK 中使用子查询，但 jsonb_array_length 是标量函数，合法）

-- 各状态计数之和不能超过总数
ALTER TABLE m08_task_queue
  ADD CONSTRAINT ck_m08_queue_status_sum
  CHECK (pending_count + claimed_count + executing_count + hold_count
         + completed_count <= task_count);

COMMENT ON TABLE m08_task_queue IS 'M08-01 队列快照表，派生数据，以 m08_task 为准';
COMMENT ON COLUMN m08_task_queue.task_ids IS '任务ID数组，按优先级降序，仅供快速渲染';
COMMENT ON COLUMN m08_task_queue.expire_at IS '过期时间，通常为 queue_date + 1 天';
```

**设计要点：**

1. **为什么要有这张表，Redis 不够吗。**
   Redis 缓存 TTL 30 秒。若 Redis 重启/清除，全部缓存失效，200 个护士同时打开页面 → 200 次查 DB → DB 压力骤增。这张表是**持久化缓存**，Redis 失效时可以从此表读取再回填 Redis，避免雪崩。

2. **为什么 `task_ids` 存 JSONB 数组而不是关联表。**
   队列是**整体替换**语义：每次重建就是「这一天这个护士的任务变成了这些」。用关联表（`m08_queue_item`）需要先 DELETE 再 INSERT 86 行；JSONB 一次 UPDATE 就完。
   代价是无法按 task_id 反查队列（「任务 101 在哪些队列里」）。但这个查询不需要——任务表里有 `assigned_nurse_id` 与 `planned_date`，反查更快。

3. **为什么 `completed_count` 也在快照里，而不仅仅是未完成的。**
   大屏要看「今日已完成 X 项」这个进度数字。如果不存，就得每次去 `m08_task` 表 COUNT，那这张表就失去了意义。

4. **快照的刷新时机。**
   - 每日 06:00 生成任务后重建
   - 每次任务状态变更后**标记失效**（异步重建）
   - 大屏每 10 秒读取一次，若 `generated_at` 超过 60 秒则触发重建

**量级估算：**

| 项目 | 数值 |
|---|---|
| 每日队列数 | 200 护士 + 50 病区 = 250 条 |
| 年队列数 | 91,250 |
| 单行长度 | 约 800 字节（86 个 ID 的 JSON 约 300 字节） |
| 年数据量 | 约 73 MB |
| 保留期 | 30 天（过期即清理） |
| 稳态行数 | 约 7,500 行 / 6 MB |

**分区：** 不分区。稳态仅 7,500 行。

**约束说明：**

```sql
ALTER TABLE m08_task_transfer
  ADD CONSTRAINT ck_m08_transfer_reason
  CHECK (char_length(btrim(transfer_reason)) >= 5);

ALTER TABLE m08_task_transfer
  ADD CONSTRAINT ck_m08_transfer_type
  CHECK (transfer_type IN ('MANUAL', 'SHIFT_END', 'AUTO'));

-- 不能转给自己
ALTER TABLE m08_task_transfer
  ADD CONSTRAINT ck_m08_transfer_self
  CHECK (from_nurse_id IS NULL OR from_nurse_id <> to_nurse_id);

CREATE OR REPLACE FUNCTION fn_m08_task_transfer_readonly()
RETURNS TRIGGER AS $$

END;

  BEFORE UPDATE ON m08_task_transfer
  FOR EACH ROW EXECUTE FUNCTION fn_m08_task_transfer_readonly();

  FOR EACH ROW EXECUTE FUNCTION fn_m08_task_transfer_readonly();
```

**设计要点：**

1. **为什么 `transferred_by` 与 `from_nurse_id` 分开。**

   护士长把 A 的任务转给 B（A 请假）→ 两者不同。
   合并就看不出「是 A 自己转的，还是被人接管的」——这在排班分析中结论相反。

2. **为什么 `from_nurse_id` 允许 NULL。**
   待认领池的任务（`status = 'PENDING'`）被护士长直接指派给某人时，没有「转出方」。用 NULL 表示。

3. **只增触发器的作用。**
   防止有人在压力下「直接改历史记录来掩盖转派」——比如把 `to_nurse_id` 改掉，让统计显示任务没被转走。触发器让这种操作直接报错。

   因为 N:1 关系。若存 `collab_ids` 数组，就无法在 DB 层做「同一人不能重复添加」约束，也无法建索引查「我协作的任务」。

```sql
  WHERE resumed_at IS NULL;

COMMENT ON COLUMN m08_task_pause.prev_status IS '暂停前的状态，恢复时回到此状态';
COMMENT ON COLUMN m08_task_pause.duration_minutes IS '暂停时长分钟数，恢复时按 resumed_at - paused_at 计算';
```

**设计要点：**

1. **为什么记录 `prev_status`。**
   护士从 `CLAIMED` 暂停（还没开始做，患者就外出了）与从 `EXECUTING` 暂停（做了一半患者要上厕所）是两种情况，恢复时应该回到原状态。若统一回到 `CLAIMED`，执行记录里的「开始时间」就对不上了。

2. **为什么 `uk_m08_pause_open` 是部分唯一索引。**
   一个任务可以多次暂停（去检查 → 回来 → 又去拿药）→ 历史多条。但同一时刻只能有一条「未恢复」的。部分唯一索引 `WHERE resumed_at IS NULL` 精确表达了这个语义。

3. **为什么不把暂停原因直接放在 `m08_task` 上。**
   因为会多次暂停。如果只存最后一次，前面几次的暂停原因就丢了。而「患者外出检查 3 次」这件事本身就是护理工作量与流程问题的证据。

**设计要点：**

1. **为什么唯一索引用 `COALESCE(scope_id, 0)` 而不是 `(param_code, scope, scope_id)`。**
   PostgreSQL 唯一索引认为 NULL 互不相等。若用三列直接组合，`scope_id = NULL` 的全局参数可以重复插入多条（`(X, 'GLOBAL', NULL)` 插入两次不会被拒），导致读取时 `first()` 取到不确定的那条，参数时对时错。
   `COALESCE(scope_id, 0)` 把 NULL 归一为 0，唯一约束生效。

2. **为什么 `param_value` 存 VARCHAR 而不是分多个类型列。**
   参数有 INT、STRING、BOOLEAN、JSON 四种。若每类一列，表会变成 `int_value` / `string_value` / `bool_value` / `json_value` 四个几乎全 NULL 的列。用 VARCHAR + `param_type` 解析更简洁，且新增类型无需改表。

3. **为什么支持 `WARD` 级覆盖。**
   不同病区的节奏不同：手术室病区医护比高，超时阈值可设 15 分钟；普通病区设 30 分钟。全局一套参数会误报或漏报。

4. **参数读取优先级。**
   `WARD 级 > GLOBAL 级 > 代码默认值`。实现见 6.6 节。
