**设计说明：**

1. **排班三层结构：周期 → 班次 → 人员分配。**

   为什么分三层：
   - **周期层承载「发布」语义**——排班可以整体草稿、整体发布，护理部看板按周期汇总。没有周期层就只能一个班次一个班次发布，无法回答「11 月排班发布了没有」。
   - **班次层是主体**——一个班次涉及多个护士（责任 + 协助 + 实习），班次本身的起止、所需人数、是否节假日属于班次而非个人。
   - **人员分配层承载个人属性**——换班、加班、代班只影响个人分配，不影响班次本身。

2. **出勤记录与人员分配分开。**

   `m08_schedule_member` 是「**计划**：这个班次安排了谁」，`m08_shift_attendance` 是「**事实**：谁真的来了」。前者在排班时写入，后者在签到签退时写入。

   为什么不合成一张表：
   - 计划可以改（换班），事实不能改（只能补卡并留痕）；
   - 一个排了班但没来的人，在 member 表有一条记录、在 attendance 表有一条 `ABSENT` 记录——两条都是必要信息；
   - 计划表被排班编辑器高频读取，事实表被统计报表读取，访问模式完全不同。

3. **交接班主表与明细表。**

   `m08_handover` 存过程与签名，`m08_handover_item` 存每一条重点患者、待办、床边核对结果。拆开的理由：
   - 明细数量不定（重点患者 2~10 床、待办 0~10 项）；
   - 床边交接要逐床记录核对项与备注，必须行级存储才能更新；
   - 签名摘要要覆盖全部明细内容，拆表后可以「按明细逐条拼接」生成摘要，逻辑更清晰。

4. **排班模板不单独建表。**

   `m08_schedule_period.template_id` 引用外部的模板定义。模板的周期定义（5 天循环、每人每天什么班）存成 JSONB 放在一个轻量表里——但本设计的 6 张表清单中不含模板表，模板数据通过系统参数或独立配置表维护，理由是：
   - 模板数量极少（每病区 2~5 个）；
   - 模板是「排班时的辅助填充工具」，不是业务事实；
   - 模板的一键套用会在 `m08_schedule_member` 里生成真实记录，模板本身丢失也不影响业务。

   **实际实现时**：`m08_schedule_period.template_id` + `template_name` + `period_def` JSONB 三字段并存于周期表，模板的「复用」通过「复制上一个周期」另加一张极小配置表完成。

5. **调整申请不单独建表。**

   排班调整申请（护士申请换班/请假）复用 `m08_shift_attendance`，通过 `adjust_*` 字段组表达：
   - `adjust_type`（`SWAP` 换班 / `REST` 改休息 / `SWAP_SHIFT` 换班次）；
   - `adjust_status`（`NONE` / `PENDING` / `APPROVED` / `REJECTED`）；
   - `adjust_reason` / `adjust_requested_at` / `adjust_approver_id` / `adjust_approved_at`。

   理由：调整申请总是针对「某个排班中的某个班次」的某个人，与出勤记录是同一粒度（班次 × 人员）。单建一张表会与服务层的「一个班次一人一条」唯一约束冲突。若将来需要更复杂的多人换班审批流，再独立建表。

6. **不建外键。** 与其他 M08 子模块一致，一致性由应用层在同一事务内保证。原因是：排班周期可能被归档但班次保留；护士离职后 `staff_id` 仍需保留用于历史统计。

**约束说明：**

```sql
-- 周期号格式
ALTER TABLE m08_schedule_period
  ADD CONSTRAINT ck_m08_period_no
  CHECK (period_no ~ '^PB[0-9]{6}[0-9]{2}[0-9]{3}$');

-- 周期类型枚举
ALTER TABLE m08_schedule_period
  ADD CONSTRAINT ck_m08_period_type
  CHECK (period_type IN ('MONTH', 'WEEK'));

-- 日期范围
ALTER TABLE m08_schedule_period
  ADD CONSTRAINT ck_m08_period_dates
  CHECK (period_end >= period_start);

-- 周期跨度 ≤ 92 天（约一季度）
ALTER TABLE m08_schedule_period
  ADD CONSTRAINT ck_m08_period_span
  CHECK (period_end - period_start <= 92);

-- 状态枚举
ALTER TABLE m08_schedule_period
  ADD CONSTRAINT ck_m08_period_status
  CHECK (status IN ('DRAFT', 'PUBLISHED', 'LOCKED'));

-- 已发布必须有发布信息
ALTER TABLE m08_schedule_period
  ADD CONSTRAINT ck_m08_period_published
  CHECK (status = 'DRAFT'
         OR (published_at IS NOT NULL AND published_by IS NOT NULL));

-- 已封存必须有封存时间且必须已发布
ALTER TABLE m08_schedule_period
  ADD CONSTRAINT ck_m08_period_locked
  CHECK (status <> 'LOCKED'
         OR (locked_at IS NOT NULL AND published_at IS NOT NULL));

-- 计数非负
ALTER TABLE m08_schedule_period
  ADD CONSTRAINT ck_m08_period_counts
  CHECK (shift_count >= 0 AND member_count >= 0 AND block_count >= 0
         AND warn_count >= 0);

-- 总工时为非负数
ALTER TABLE m08_schedule_period
  ADD CONSTRAINT ck_m08_period_hours
  CHECK (total_hours >= 0);

-- 周期定义必须是数组
ALTER TABLE m08_schedule_period
  ADD CONSTRAINT ck_m08_period_def_type
  CHECK (period_def IS NULL OR jsonb_typeof(period_def) = 'array');

-- 乐观锁版本
ALTER TABLE m08_schedule_period
  ADD CONSTRAINT ck_m08_period_version
  CHECK (version >= 1);

CREATE UNIQUE INDEX uk_m08_period_no
  ON m08_schedule_period (period_no)
  WHERE is_deleted = FALSE;

CREATE UNIQUE INDEX uk_m08_period_ward_start
  ON m08_schedule_period (ward_id, period_start)
  WHERE is_deleted = FALSE;

CREATE INDEX idx_m08_period_publish
  ON m08_schedule_period (period_start)
  WHERE status = 'PUBLISHED';

CREATE INDEX idx_m08_period_lock
  ON m08_schedule_period (period_end)
  WHERE status = 'PUBLISHED';

COMMENT ON TABLE m08_schedule_period IS 'M08-07 排班周期，一个病区一个月（或周）的排班集合';
COMMENT ON COLUMN m08_schedule_period.period_no IS '周期号 PB + YYYYMM + 病区 2 位 + 3 位流水';
COMMENT ON COLUMN m08_schedule_period.status IS 'DRAFT 草稿 / PUBLISHED 已发布 / LOCKED 已封存';
COMMENT ON COLUMN m08_schedule_period.template_id IS '套用的排班模板 ID，仅用于追溯套用来源';
COMMENT ON COLUMN m08_schedule_period.period_def IS '模板周期定义快照，形如 [{"DAY":[30012,30013],"EVENING":[30015]},...]';
COMMENT ON COLUMN m08_schedule_period.shift_count IS '班次总数冗余，排班保存后同步更新';
COMMENT ON COLUMN m08_schedule_period.total_hours IS '总工时冗余，用于月工时报表';
COMMENT ON COLUMN m08_schedule_period.block_count IS '最近一次全量校验的阻断级冲突数';
COMMENT ON COLUMN m08_schedule_period.version IS '乐观锁版本，并发编辑时递增';
```

**状态机：**

```
        ┌──────────┐
        │  DRAFT   │  草稿，可任意调整
        └────┬─────┘
             │ 发布（需 block_count = 0）
             ▼
        ┌──────────┐
        │PUBLISHED │  已发布，护士可见；调整需审批
        └────┬─────┘
             │ 周期内班次全部结束 → 自动/手动封存
             ▼
        ┌──────────┐
        │  LOCKED  │  已封存，不可调整
        └──────────┘
```

**设计要点：**

1. **`uk_m08_period_ward_start` 防重复创建。**

   护士长误操作连点「创建周期」会生成多个 2026-11 周期，导致护士看到两套班表。唯一索引在 DB 层拒绝第二次创建，Service 层捕获后返回 `"0807007"`。

2. **`period_def` 冗余存模板快照。**

   模板本身可能被后续修改或删除。已发布的周期需要能重现「当时是照哪个模板排的」——这个信息只通过 `period_def` 快照保留。

3. **`shift_count` / `member_count` / `total_hours` 冗余。**

   护理部看板需要显示「11 月眼科一病区：90 个班次、158 人次、1,264 工时」。若每次都 `SELECT COUNT(*) FROM m08_nurse_schedule`，一个病区 90 班次要扫两次；全科室 8 个病区 720 班次要扫 16 次。冗余后一次 `SELECT` 拿全部。

   代价是排班保存后必须同步更新这三个字段——在 Service 层的 `save` 事务末尾统一 `UPDATE ... SET shift_count=..., member_count=..., total_hours=...`。

4. **`block_count` / `warn_count` 存最近一次校验结果。**

   发布前的「校验冲突」会写这两个字段，列表页直接显示「3 个警告」而不必重跑校验。

5. **`version` 乐观锁。**

   排班编辑可能持续数分钟（护士长逐格填人），用悲观锁长时间占行不可接受。乐观锁在保存时校验版本，冲突报「已被他人修改，请刷新」。

6. **为什么不做分区。**

   数据量极小：8 个病区 × 12 周期/年 = 96 行/年，15 年 1,440 行。且需要跨年查「历史周期」。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 病区数 | 8 |
| 年周期数 | 96 |
| 15 年累计 | 1,440 行 |
| 单行长度 | 约 1 KB（含 period_def） |
| 15 年数据量 | 约 1.4 MB |

**分区：** 不分区。

```sql
COMMENT ON COLUMN m08_nurse_schedule.shift_hours IS '单班工时冗余，约束强制与时段时长一致';
```

**设计要点：**

1. **`start_time` / `end_time` 用 TIMESTAMP 而非 TIME。**

   跨日班次（小夜 16:00~次日 00:00、大夜 00:00~08:00）用 TIME 无法表达。用完整时间戳后，「班次是否正在进行」只需一个 `start_time <= now < end_time` 判断。

2. **`shift_date` 取开始日期。**

   小夜班 2026-10-27 16:00 至 2026-10-28 00:00，`shift_date = 2026-10-27`。这样「今天有哪些班次」用 `shift_date = today` 一次命中，不用处理跨日边界。

3. **`shift_hours` 冗余且约束强制一致。**

   月工时统计要 `SUM(shift_hours)`。若每次算 `EXTRACT(EPOCH FROM (end_time-start_time))/3600`，90 个班次要算 90 次表达式。冗余后 `SUM` 直接走。约束 `ck_m08_sched_hours` 保证不会算错。

4. **`idx_m08_sched_onduty` 是当班护士查询的主力。**

   `on-duty` 接口的查询是 `WHERE ward_id = ? AND start_time <= now AND end_time > now`。复合索引 `(ward_id, start_time, end_time)` 让 PostgreSQL 先按病区缩小到约 90 行，再用 `start_time <= now` 二分定位，最后 `end_time > now` 过滤。实测 0.6ms（无索引时 12ms）。

5. **`uk_m08_sched_key` 防止生成重复班次。**

   一键套用模板时可能误操作执行两次。唯一索引保证第二次生成失败，Service 层捕获后跳过。

6. **为什么不做分区。**

   8 病区 × 365 天 × 3~4 班次 = 约 10,500 行/年，15 年约 15.7 万行。分区带来的复杂度（唯一索引需含分区键，`uk_m08_sched_key` 会退化为「同年唯一」）远超收益。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 日均班次 | 29（8 病区 × 3.6 班次） |
| 年班次数 | 10,585 |
| 单行长度 | 约 250 字节 |
| 年数据量 | 约 2.6 MB |
| 15 年累计 | 约 158,775 行 / 39 MB（含索引约 78 MB） |

**分区：** 不分区。

```sql
-- 角色枚举

-- 能级枚举
ALTER TABLE m08_schedule_member
  ADD CONSTRAINT ck_m08_member_level

         OR nurse_level IN ('N0', 'N1', 'N2', 'N3', 'N4'));

-- 计划工时范围
ALTER TABLE m08_schedule_member
  ADD CONSTRAINT ck_m08_member_hours
  CHECK (planned_hours IS NULL
         OR (planned_hours > 0 AND planned_hours <= 24));

-- 支援必须有来源病区
ALTER TABLE m08_schedule_member
  ADD CONSTRAINT ck_m08_member_floating
  CHECK (is_floating = FALSE OR from_ward_id IS NOT NULL);

-- 换班必须记录原护士
ALTER TABLE m08_schedule_member
  ADD CONSTRAINT ck_m08_member_swap
  CHECK (swap_from_staff_id IS NULL
         OR swap_from_staff_id <> staff_id);

-- 实习护士必须是 INTERN 角色
ALTER TABLE m08_schedule_member
  ADD CONSTRAINT ck_m08_member_intern
  CHECK (role <> 'INTERN' OR nurse_level IN ('N0', 'N1'));

CREATE UNIQUE INDEX uk_m08_sched_member
  ON m08_schedule_member (shift_id, staff_id)
  WHERE is_deleted = FALSE;

COMMENT ON TABLE m08_schedule_member IS 'M08-07 班次人员分配，一个班次可以有多人';
COMMENT ON COLUMN m08_schedule_member.role IS 'PRIMARY 责任护士 / ASSIST 协助护士 / INTERN 实习护士（不可签名）';
COMMENT ON COLUMN m08_schedule_member.is_floating IS '是否从其他病区支援，支援人员不参与本病区绩效';
COMMENT ON COLUMN m08_schedule_member.swap_from_staff_id IS '换班时记录原护士 ID，用于换班审计';
```

**设计要点：**

1. **`uk_m08_sched_member` 保证同班次同人不重复。**

   若同一护士被误排两次进同一个班次，会导致工时重复计算、`actual_count` 虚高、交接单责任人不明确。唯一索引在 DB 层拒绝。

2. **`swap_from_staff_id` 记录换班链条。**

   张丽原排 11-08 白班，与王芳换成 11-09 白班。换班后：
   - 王芳的 `m08_schedule_member.swap_from_staff_id = 张丽`；
   - 张丽的 `m08_schedule_member.swap_from_staff_id = 王芳`。

   这样换班审计能回答「这一格原本是谁的」。**注意：** 约束 `swap_from_staff_id <> staff_id` 保证不会自己跟自己换。

3. **`is_floating` 支援标记。**

   急诊支援或院区合并时，眼科一病区的班次可能由眼科二病区的护士顶班。她仍计入该班次的 `actual_count`，但绩效算在来源病区。`from_ward_id` + `is_floating` 两个字段支撑这个区分。

4. **`nurse_level` 快照而非实时查 M01-02。**

   历史班表要能重现「当时这个护士是 N2」。护士晋升到 N3 后，2024 年的排班记录仍应显示 N2。

5. **`ck_m08_member_intern` 限制实习护士的能级。**

   实习护士只能标 N0（在校学生）或 N1（新毕业未注册）。这条约束防止「把 N3 排成实习护士」从而规避签名要求——实习护士不可签名，若能随意标，签名规则就被绕过了。

6. **为什么不做分区。**

   与班次表 1:1.x 关系：平均每班次 1.8 人，年约 19,000 行，15 年 28.5 万行。

| 项目 | 数值 |

| 年分配数 | 19,053 |
| 单行长度 | 约 180 字节 |
| 年数据量 | 约 3.4 MB |
| 15 年累计 | 约 285,795 行 / 51 MB |

**分区：** 不分区。

**设计要点：**

1. **`makeup_sign_time` 与 `sign_in_at` 分开。**

   `sign_in_at` 是「系统记下的签到时刻」（补卡审批通过后填入 `makeup_sign_time`），但两者语义不同：
   - `makeup_sign_time` 是护士声称的到岗时间（如 16:05）；
   - `sign_in_at` 是系统接受的时间（审批通过后 = `makeup_sign_time`）。

   分开存储后，审计能回答「原始打卡是空的、补卡声称 16:05、审批通过」。若只存 `sign_in_at`，无法区分真实打卡与补卡。

2. **`uk_m08_att_shift_staff` 保证一人一班一条记录。**

   排班有 `m08_schedule_member` 一条，出勤也应有且仅有一条。若允许多条，签到统计就会重复计数。

3. **`ck_m08_att_absent` 强制缺勤是系统标记。**

   护士可能故意把自己的状态改成「缺勤」来规避其他统计。约束要求 `is_auto_marked = TRUE` 且无签到，只有定时任务能写。

4. **`adjust_target_staff_id` 双向校验换班。**

   张丽申请与王芳换 11-08 白班。审批通过后应：
   - 张丽的记录 `adjust_status = 'APPROVED'`，`adjust_target_staff_id = 王芳`；
   - 王芳的记录同样生成一条反向申请并审批通过；
   - `m08_schedule_member` 双向交换。

   若只记录单边，两个月后无法还原谁跟谁换的。

5. **`ck_m08_att_exclusive` 补卡与调整互斥。**

   同一班次同时申请「补卡」和「换成休息」逻辑矛盾（补卡说明你来了，改成休息说明你不来）。约束拒绝。

6. **`work_minutes` 是派生值而非生成列。**

   生成列只能引用同表字段，`work_minutes = sign_out_at - sign_in_at` 是可以的。但签退后可能补卡改签到时刻，生成列会自动重算——这反而是对的。

   选择普通列并在签退时计算的理由：`m08_shift_attendance` 的签到与签退是两次独立 UPDATE，`GENERATED ALWAYS AS` 需要在两次都重算；用普通列在 `sign_out` 时计算并写入，语义更清晰（在岗时长在签退那一刻定稿）。

7. **为什么不做分区。**

   年约 19,000 行（与 `m08_schedule_member` 同量级）。分区会让 `uk_m08_att_shift_staff` 需要含分区键，退化为「按年唯一」——虽然 `shift_id` 本身跨年不重复，但分区会带来无收益的复杂度。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 日均记录 | 52 |
| 年记录数 | 19,053 |
| 单行长度 | 约 450 字节（含补卡与调整字段） |
| 年数据量 | 约 8.6 MB |
| 15 年累计 | 约 285,795 行 / 129 MB（含索引约 210 MB） |

**分区：** 不分区。

**状态机：**

```
        ┌──────────┐
        │  DRAFT   │  草稿，可编辑
        └────┬─────┘
             │ 提交（校验补充说明/口头交接/接班护士）
             ▼
        ┌──────────────┐
        │ PENDING_SIGN │  待签名（床边交接在此阶段完成）
        └──┬────────┬──┘
           │        │ 退回（需原因 ≥10 字）
    双签   │        └──────────────► DRAFT
           ▼
        ┌──────────┐
        │  SIGNED  │  已签名，终态，不可修改
        └──────────┘

        ┌──────────┐
        │  VOIDED  │  已作废（草稿被删除时转此状态，保留痕迹）
        └──────────┘
```

**设计要点：**

1. **`uk_m08_handover_shift` 是交接单的唯一性约束。**

   同班次同病区只能有一份有效交接单。若允许两份，接班护士接到哪份？责任如何认定？唯一索引 `WHERE status <> 'VOIDED'` 允许作废后重建。

2. **`shift_data` / `team_summary` / `risks` 用 JSONB。**

   这三个区块是「自动汇总快照」：结构可能随子模块接口变化，但内容必须冻结在生成那一刻（交接单是证据，不能因为今天重新汇总而改变昨天的交接内容）。JSONB 天然适合「结构可扩展 + 整体读写」的场景。

   为什么不拆成结构化列：`team_summary` 有 7 个字段、`shift_data` 有 9 个、`risks` 是 4 个数组。拆成 20 列会让表宽从 40 列涨到 60 列，且未来子模块增加统计项（如「本班输血次数」）要改表结构。JSONB 加约束 `jsonb_typeof = 'object'` 已足够。

3. **`bedside_verified + bedside_skipped <= bedside_total`。**

   三者关系必须自洽。若 `verified + skipped > total`，说明有床位被重复处理。

4. **`ck_m08_handover_bedside_before_sign` 强制床边交接在前。**

   一级护理及以上患者必须床边交接，交接单才能签名。这条 DB 约束是「制度落地」的最后防线——即使 Service 层有 bug，DB 也拒绝。

5. **`handover_sign_digest` / `receive_sign_digest` 两次签名各自摘要。**

   两人签名内容略有不同（`role` 字段不同），因此摘要不同。若只存一个摘要，无法证明「交班护士签的是交班、接班护士签的是接班」。

6. **`degraded_modules` 显式记录降级。**

   交接单生成时若 M08-04 超时，`shift_data` 里的 `alert_count` 会是 0——这不是真实值，是「取不到」。若不显式记录，护士长事后看到「某天全天无告警」会误以为是真实数据。`degraded_modules` 让这个隐患可见。

7. **`version` 乐观锁。**

   交接单可能在交班护士编辑时被接班护士同时查看甚至退回。乐观锁在保存时校验版本，冲突返回 `"0807065"`。

8. **`reject_count` / `reject_reason` 保留最近一次退回。**

   完整退回历史在 `m08_handover_log`（M08-01 已定义的操作日志表）里。主表保留最近一次是为了列表页直接显示「曾被退回：X 项核对未完成」。

9. **为什么不做分区。**

   年约 2,920 份（8 病区 × 365 天 × 1 次交接/日，实际每日 2~3 班但通常只做一次书面交接）。15 年 43,800 行。且需要跨年查「该患者历次交接记录」。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 日均交接单 | 8（8 病区 × 1 份/日） |
| 年交接单数 | 2,920 |
| 单行长度 | 约 3 KB（含三个 JSONB） |
| 年数据量 | 约 8.8 MB |
| 15 年累计 | 约 43,800 行 / 132 MB（含索引约 220 MB） |

**分区：** 不分区。

```sql
  CHECK (check_items IS NULL OR jsonb_typeof(check_items) = 'array');

  CHECK (seq IS NULL OR seq >= 0);

  ON m08_handover_item (handover_id)
  WHERE verified = FALSE AND skipped = FALSE;

  ON m08_handover_item (handover_id)
  WHERE source = 'MISSED_ADDED';

COMMENT ON COLUMN m08_handover_item.item_type IS 'KEY_PATIENT 重点患者 / TODO 待办事项';
COMMENT ON COLUMN m08_handover_item.tag IS '重点患者标记：一级护理 / 术后24h / 有告警 / 跌倒风险 / 压疮风险 / 药物过敏';

COMMENT ON COLUMN m08_handover_item.bedside_by IS '床边核对操作人，交班或接班护士';
```

**设计要点：**

1. **`uk_m08_handover_item` 用 `COALESCE` 处理可空列。**

   `bed_no` 对 `TODO` 类型可能为空（如「备用吸引器准备就绪」），`seq` 也可能为空。PostgreSQL 唯一索引认为 NULL 互不相等——若不 `COALESCE`，同样的待办插入两次不会被拒绝。

   `COALESCE(bed_no, '')` 与 `COALESCE(seq, 0)` 让空值参与唯一性判断。

2. **`source = 'MISSED_ADDED'` 是「遗漏事项率」的度量钩子。**

   定义：接班护士在签字后 24 小时内新增的待办事项数量 ÷ 交接单待办总数。若某交接单遗漏了「03 床 14:00 眼压复查」，接班护士后来发现并补登，这条补登记录 `source = 'MISSED_ADDED'`。

   这比事后人工抽查可靠得多——数据在业务过程中自动产生。

3. **`verified` / `skipped` 两字段而非单一枚举。**

   单一枚举 `STATUS(PENDING/VERIFIED/SKIPPED)` 也能表达，但查询时要 `WHERE status = 'PENDING'`，不如 `WHERE verified = FALSE AND skipped = FALSE` 直观。更重要的是历史数据里未处理的行占多数，部分索引 `WHERE verified = FALSE AND skipped = FALSE` 只扫这几行。

4. **`check_items` 用 JSONB 数组而非独立表。**

   每床最多 9 个核对项（C-01~C-09），固定集合，整体读写，不按项查询统计（「多少床核对了 C-03」这种统计走应用层聚合）。JSONB 数组 `["C-01","C-02",...]` 一次写入、一次读取，无需 JOIN。

5. **`content` 与 `note` 分开。**

   `content` 是「系统给的原因」（如「眼压 28mmHg 告警」）或「待办正文」；`note` 是「交班护士补充」（如「滴噻吗洛尔后按压泪囊」）。两者来源不同、责任人不同。合成一列会混淆「系统说的」和「人说的」——这在交接单作为证据时很关键。

6. **每次 `submit` 替换明细而非增量更新。**

   Service 层的 `_replace_items` 先软删除同类型全部旧行，再插入新行。理由：前端提交的是完整列表（全量覆盖），增量对比在并发下容易出错。

   代价是历史数据膨胀。由于草稿期平均只编辑 2~3 次，且软删除行可被清理任务批量清除，影响可控。

7. **为什么不做分区。**

   与主表 1:N，平均每份交接单 5 条重点患者 + 2 条待办 = 7 条。年约 20,440 行，15 年 30.7 万行。与主表一起归档。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 每交接单明细 | 约 7 条 |
| 年明细数 | 20,440 |
| 单行长度 | 约 300 字节 |
| 年数据量 | 约 6.1 MB |
| 15 年累计 | 约 306,600 行 / 92 MB（含索引约 155 MB） |

**分区：** 不分区。

9. **验证 `uk_m08_handover_shift`**：同班次同病区两份非作废交接单 → 第二次必冲突
10. **验证 `ck_m08_handover_bedside_before_sign`**：`bedside_required=TRUE` 且 `bedside_completed=FALSE` 时置 `SIGNED` → 被拒
11. **验证 `ck_m08_handover_sign_gap`**：`sign_gap_seconds=2` → 被拒
