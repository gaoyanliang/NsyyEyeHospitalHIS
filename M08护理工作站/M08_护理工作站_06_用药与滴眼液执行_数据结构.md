**设计说明：**

1. **`m08_medication_admin` 与 `m08_eye_drop` 是 1:1 关系，但必须拆成两张表。**

   理由：`m08_medication_admin` 承载全部给药类型共有的字段（患者、药品、时间、签名、回写）；`m08_eye_drop` 只承载滴眼特有的字段（眼别、滴数、部位、间隔、开瓶关联）。

   为什么不合成一张表：
   - 口服药不需要 `eye_side`、`drops`、`press_lacrimal`，合成后这些字段对口服全是 NULL；
   - 滴眼记录量占比约 70%，合并后表宽 60+ 字段，日 400 条、15 年 219 万行，宽度直接影响缓存与 IO；
   - 滴眼特有的查询（查该患者该眼最后一次）只扫窄表更快；
   - 未来加「眼用凝胶/眼膏」的专属字段不影响通用给药。

2. **`m08_eye_drop_open` 与 `m08_medication_admin` 是 N:1（一瓶药可滴多次）。**

   `m08_eye_drop.open_id` 指向上次登记的开封记录。这样「这瓶药还能不能滴」只需查一条开封记录。

3. **为什么开封登记要独立成表而不是在 `m08_medication_admin` 上加「是否首次开封」标志。**

   开封是物理容器层面的状态（一瓶药、一个批次），不是给药动作的属性。而且：
   - 一瓶药可能滴 30 次，只在第一次开封时登记；
   - 开封后效期跨越多次给药；
   - 报废时要把开封记录置为 `DISCARDED`，不能靠某条给药记录表达。

4. **`m08_med_exception` 与 `m08_med_override` 不挂在 `m08_medication_admin` 下，而挂在 `m08_exec_point` 下。**

   因为异常与授权都是「这次该给但没给」或「这次该等但给了」的情形——**此时没有给药记录**。用 `point_id` 关联才能覆盖「执行点已计划但未执行」的状态。

5. **`m08_med_stock_snap` 是 M14-08 的本地只读镜像。**

   M08-06 不写库存，只读快照来判断「病区里有没有这个批次的药」。表上没有业务写权限，只有同步任务写。

6. **不建外键。** 与其他 M08 子模块一致，一致性由应用层同一事务内保证。

7. **`m08_medication_admin` 的 `point_id` 上加唯一索引（`status <> 'VOID'`）。** 一个执行点只能有一条有效给药记录，这是「同一执行点不可重复执行」的最后防线。

**约束说明：**

```sql
-- 给药单号格式
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_admin_no
  CHECK (admin_no ~ '^MD[0-9]{8}[0-9]{5}$');

-- 给药类型枚举
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_admin_type
  CHECK (admin_type IN ('EYE_DROP', 'EYE_OINTMENT', 'ORAL', 'INJECTION',
                        'TOPICAL', 'NEBULIZATION', 'SUPPOSITORY', 'OTHER'));

-- 状态枚举
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_admin_status
  CHECK (status IN ('EXECUTED', 'VOID'));

-- 剂量必须为正
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_dose
  CHECK (dose_quantity > 0);

-- 滴眼类型必须勾选部位在明细表，主表只校验单位
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_dose_unit
  CHECK (char_length(btrim(dose_unit)) >= 1);

-- admin_date 必须与 actual_time 的日期一致
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_admin_date
  CHECK (admin_date = actual_time::date);

-- 已执行必须有签名
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_signed
  CHECK (status <> 'EXECUTED'
         OR (signature_digest IS NOT NULL AND signed_at IS NOT NULL
             AND executed_by IS NOT NULL));

-- 签名摘要格式
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_digest
  CHECK (signature_digest IS NULL OR signature_digest ~ '^[0-9a-f]{64}$');

-- 签名时刻不能早于执行时间
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_sign_time
  CHECK (signed_at IS NULL OR signed_at >= actual_time);

-- 超间隔授权必须有原因
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_override
  CHECK (interval_override = FALSE
         OR (override_reason IS NOT NULL
             AND char_length(btrim(override_reason)) >= 10));

-- 双人核对：执行人 != 核对人
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_sod
  CHECK (checker_id IS NULL OR checker_id <> executed_by);

-- 双人核对完成必须有时刻与会话
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_checked
  CHECK (checker_id IS NULL
         OR (checked_at IS NOT NULL AND checker_session_id IS NOT NULL));

-- 同一会话不能同时是执行人与核对人
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_session
  CHECK (checker_session_id IS NULL OR executor_session_id IS NULL
         OR checker_session_id <> executor_session_id);

-- 回写状态枚举
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_writeback
  CHECK (writeback_status IN ('PENDING', 'SUCCESS', 'FAILED', 'DEAD', 'SKIPPED'));

-- 回写重试次数范围
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_wb_retry
  CHECK (writeback_retry >= 0 AND writeback_retry <= 10);

-- 回写成功必须有时刻
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_wb_at
  CHECK (writeback_status <> 'SUCCESS' OR writeback_at IS NOT NULL);

-- 监测配置成对出现
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_monitor
  CHECK ((monitor_code IS NULL AND monitor_after_minutes IS NULL)
         OR (monitor_code IS NOT NULL AND monitor_after_minutes IS NOT NULL
             AND monitor_after_minutes > 0));

-- 时间戳来源枚举
ALTER TABLE m08_medication_admin
  ADD CONSTRAINT ck_m08_med_sig_source
  CHECK (signature_source IS NULL OR signature_source IN ('RFC3161', 'LOCAL'));

CREATE UNIQUE INDEX uk_m08_med_admin_no
  ON m08_medication_admin (admin_no)
  WHERE is_deleted = FALSE;

CREATE UNIQUE INDEX uk_m08_med_point_active
  ON m08_medication_admin (point_id)
  WHERE status <> 'VOID' AND is_deleted = FALSE;

COMMENT ON TABLE m08_medication_admin IS 'M08-06 给药执行记录，每一次给药动作一条';
```

**状态机：**

```
        ┌────────────┐
        │  EXECUTED  │  已执行（签名后不可改）
        └─────┬──────┘
              │ 护士长作废（24 小时内）
              ▼
        ┌────────────┐
        │    VOID    │  已作废
        └────────────┘
```

**设计要点：**

1. **为什么 `point_id` 上要有 `uk_m08_med_point_active` 部分唯一索引。**
   两个护士站同时提交同一个执行点（网络慢、界面卡顿导致重复点击）时，只有一条能落库。应用层的「先查后插」在并发下必然漏。

2. **为什么 `dose_quantity` 用 `NUMERIC(12,4)` 而不是 `INT`。**
   滴眼液是整数滴，但口服液是 5.5 ml、注射是 0.75 g、雾化是 2.5 mg。统一用 NUMERIC 能覆盖全部给药类型，且与 M07 医嘱的 `quantity NUMERIC(12,4)` 对齐。

3. **`admin_date` 冗余存。**
   依从性统计按日期聚合，`DATE(actual_time)` 无法走索引。冗余后 `WHERE admin_date = ?` 直接命中 `idx_m08_med_ward_date`。

4. **`press_lacrimal` 放在主表而非明细表。**
   口服药该字段恒为 FALSE，但放在主表便于统一查询「哪些滴眼执行没有按压泪囊」——这是质控指标。若放明细表要 JOIN。

5. **`monitor_code` 与 `monitor_after_minutes` 成对出现。**
   约束强制二者同为空或同时非空。避免出现「配了监测项没配延迟」导致任务立即触发。

6. **`checker_session_id` 与 `executor_session_id` 双存。**
   SoD 第三重校验：同一浏览器窗口不可能换人。若只存 `checker_id`，同一人在两个浏览器登录两个账号仍能绕过。

7. **`writeback_retry` 上限 10。**
   指数退避 1,2,4,8,16,32,64,128,256,512 秒，累计约 17 分钟。10 次后置 `DEAD` 并告警，人工介入。

8. **为什么不做分区。**
   `m08_medication_admin` 年 146,000 行（按滴眼 70% + 全身 30% 估算约 146k），15 年约 219 万行、约 2.4 GB。PostgreSQL 16 单表可承受。若分区，唯一索引 `uk_m08_med_point_active` 需含分区键（`admin_date`），会退化为「同一年内唯一」，破坏跨年幂等——而执行点 ID 本身跨年不重复，加了分区键反而引入漏洞。

**量级估算：**

| 项目 | 数值 | 计算依据 |
|---|---|---|
| 日均给药记录 | 400 | 40 床 × 平均 10 次/床/日 |
| 其中滴眼 | 280 | 70% |
| 年记录数 | 146,000 | 400 × 365 |
| 单行长度 | 约 900 字节 | 含签名摘要与快照字段 |
| 年数据量 | 约 131 MB | — |
| 15 年累计 | 约 2,190,000 行 | 1.97 GB（含索引约 3.4 GB） |

**分区：** 不分区（理由见设计要点 8）。

```sql
COMMENT ON COLUMN m08_eye_drop.eye_side IS '眼别，只能是 OD 或 OS，双眼（OU）在执行计划层已展开为两个执行点';

COMMENT ON COLUMN m08_eye_drop.prev_gap_eye IS '上次给药的是哪只眼，用于事后核查「是否两只眼交叉滴」';
```

**设计要点：**

1. **`eye_side` 只能是 `OD` / `OS`，不能是 `OU`。**
   这是一个关键的完整性约束。M08-02 已把「双眼」展开成两个执行点，若这里允许 `OU`，就会出现「一条记录两只眼」——签名一次说不清到底滴了哪只眼，也违背了「滴错眼为零容忍」的设计目标。

2. **`patient_id`、`drug_code`、`actual_time` 三个字段从主表冗余过来。**
   间隔校验需要高频查询 `WHERE patient_id = ? AND eye_side = ? ORDER BY actual_time DESC LIMIT 1`。若每次都 JOIN 主表，索引无法覆盖，实测从 0.4ms 变成 2.1ms。冗余后 `idx_m08_drop_eye_time` 直接给出结果，且三个字段在主表中不可变（`actual_time` 是签名覆盖字段），冗余不会产生不一致。

3. **`prev_gap_seconds` 是「证据快照」而非「可重算值」。**
   事后核查时不能用「现在查一次」的结果，因为新的给药记录会改变它。必须记录当时算出来是多少——如果当时判 318 秒合规，后来发现实际是 118 秒，快照能证明系统当时算错了。

4. **`prev_gap_eye` 记录上次给的是哪只眼。**
   质控抽查时要回答「有没有把右眼的药滴到左眼」——如果上一次是 OD、这一次也是 OD，且间隔短，说明是同一只眼重复；如果上一次 OD、这一次 OS 且 `prev_gap_seconds` 很短，那可能是护士在两只眼之间快速切换（这基本不可能，因为要间隔 5 分钟），值得核查。

5. **为什么不做分区。**
   与主表 1:1，行数相同（年 146k），必须与主表一起归档。单独分区无意义。

**设计要点：**

1. **`uk_m08_open_batch_patient` 是「一瓶药不给两个患者」的硬约束。**
   这是院感防控的底线。索引列是 `(batch_no, drug_code)` 而非 `(patient_id, batch_no)`，因为一个批次理论上可以拆成多瓶（不同瓶号），但现实中眼科滴眼液多为单瓶包装，用批次号加药品编码已足够区分。若未来需要精确到瓶号，应加 `bottle_no` 字段并把索引改为 `(bottle_no)`。

2. **`shelf_life_days` 复制而非引用 M01-03。**
   M01-03 的 `after_open_shelf_life` 可能被修改（如药品说明书更新）。已开封的那一瓶应按开封当时的规则计算，不能因为主数据改了就把失效日期往后推。

3. **`expire_date` 是冗余列 + 约束强一致。**
   到期扫描需要 `WHERE expire_date <= CURRENT_DATE`，`DATE(open_time + interval)` 是表达式无法走索引。冗余后配合 `idx_m08_open_expire` 部分索引（只扫 ACTIVE 行，全表约 50 条），扫描成本趋近于零。

4. **`uk_m08_open_active` 保证同患者同药只有一个活跃开封。**
   若一个患者同时开了两瓶妥布霉素，系统不知道滴哪瓶——开封日期不同、效期不同，混用会导致「用了快过期的那瓶」。强制用完一瓶再开新瓶。

5. **报废需要销毁见证人且必须不同于开封人。**
   过期药品属于医疗废物，双人见证是院感要求。同时防止「一个人自己登记自己销毁」的作假路径。

6. **为什么 `usage_mode` 保留 `WARD_SHARED` 但不常用。**
   病区共用的眼药水（如多人共用的散瞳药）在实践中确实存在，但**必须是单剂量包装，开封即弃**。`WARD_SHARED` 情况下 `uk_m08_open_batch_patient` 会因 `patient_id` 不同而生冲突——此时 `patient_id` 填 0 表示「病区共用」，系统在 Service 层强制 `is_single_dose = TRUE`。

7. **为什么不做分区。**
   数量小：每瓶药一条，年约 12,000 条（40 床 × 平均 0.8 瓶/床/日 × 365），15 年 18 万行。且需要跨年查「该患者历史上开过多少瓶」。

| 项目 | 数值 |
|---|---|
| 日均开封 | 12（40 床 × 0.3 瓶/床） |
| 年记录数 | 4,380 |
| 单行长度 | 约 400 字节 |
| 年数据量 | 约 1.8 MB |
| 15 年累计 | 约 65,700 行 / 26 MB（含索引约 48 MB） |

**分区：** 不分区。

**设计要点：**

1. **`status` 有 `USED` 而非用 `used_at IS NOT NULL` 表达。**

   护士连点「申请授权」按钮会生成多条，这个索引保证同时只有一个有效。第二次会得到「已有待审批申请」提示。

4. **`admin_id` 反向关联给药记录。**
   用于统计「哪些授权真的被用到了」——申请了但没用，说明流程有改善空间。

5. **为什么不做分区。**
   量小：按超间隔授权率 1%~2% 估算，日约 3 条，年 1,095 条。

**设计要点：**

1. **为什么需要快照而不是每次实时查 M14。**
   给药执行是高频操作（日均 400 次），每次查 M14-08 的病区库存要跨模块调用（P95 200ms），累积起来可观。快照 10 分钟同步一次，查询本地表 <1ms。

2. **快照只作参考，不作为扣减依据。**
   真正的库存扣减在 M14-08 摆药时已完成。这里只回答「病区里现在大概有哪些批次的药」——护士选批次时用。即使快照偏差（刚被别的护士用掉了最后一支），也不影响库存正确性，只是护士要换批次。

3. **`is_recalled` 是安全字段。**
   M14-01 发布 `m14.stock.recalled` 事件时该字段置 TRUE。执行时若有 `is_recalled = TRUE` 的批次可选，必须阻断——这是药品召回的最后一道拦截。

4. **为什么不做分区。**
   一个病区约 200 种药 × 平均 2 个批次 = 400 行，全院 8 个病区 3,200 行。数据量恒定（每日 UPSERT 覆盖），不增长。

**设计要点：**

1. **`COALESCE(scope_id, 0)` 而非 `NULLS NOT DISTINCT`。**
   PostgreSQL 15+ 才有 `NULLS NOT DISTINCT`，本项目部分环境仍是 PG 14。`0` 不是合法病区 ID，没有冲突风险。

2. **参数优先级：WARD > GLOBAL > 代码默认。**
   读取顺序：先查 `scope = 'WARD' AND scope_id = ?`，没有则查 `scope = 'GLOBAL'`，再没有用代码内常量。

3. **为什么需要病区级覆盖。**
   眼科术后病房对青光眼患者的眼压控制更严，可能把最小间隔配成 10 分钟（更保守）。综合病区维持 5 分钟。

**量级估算：** 20 条 GLOBAL + 少量 WARD 覆盖，约 30 行，约 15 KB。

**分区：** 不分区。
