## 1. 模块概述

### 1.1 模块定位

**M08 护理工作站是全院护士唯一的日常作业平台。**

它回答三个问题：

1. **现在这个护士该做什么**（M08-01 任务队列）
2. **这件事具体怎么做、做完了没有、做对了没有**（M08-02 计划、M08-03 执行、M08-04 体征、M08-05 记录、M08-06 用药）
3. **下一班护士需要知道什么**（M08-07 交接）

**一句话边界：** M08 执行医嘱、记录过程、留下证据，但**不改医嘱、不做诊断、不发药、不收费**。

### 1.2 为什么 M08 是一个模块而不是散落的护理功能

**理由一：护理作业是「一个人一个班次连续做完一串事」，不是若干个孤立功能。**

护士上班后：签到 → 看本班任务 → 按时间顺序执行 → 记录体征与护理过程 → 交接给下一班。这五个动作共享同一个上下文（哪个病区、哪个班次、哪些患者、哪些任务），若拆到 M07/M14/M09 各自去做，护士要在五个系统间来回切换，且「我今天还有什么事没做」永远没有统一答案。

**理由二：护理执行有统一的状态机与签名模型。**

不管执行的是换药、滴眼、测眼压还是术前准备，都必须走「核对 → 执行 → 记录 → 签名」四步，都受「执行人 ≠ 核对人」「签名后不可改」两条规则约束。这套模型放一个模块才能保证一致；分散实现必然出现「门诊注射可以后补签名、住院换药必须当场签名」这类不一致。

**理由三：执行数据是全院多个模块的下游依据。**

| 消费方 | 消费内容 |
|---|---|
| M07 医生工作站 | 医嘱执行状态（`on-executing`/`on-completed`） |
| M06-06 日间结算与病历归档 | 护理记录（D-14）、体征完整度、用药依从性、交接单 |
| M09 手术麻醉 | 术中护理记录、术后眼压监测 |
| M16 收费结算 | 护理费/治疗费的执行依据 |
| M22 报表 | 护理工作量、执行率、交接质量 |
| M02 审计 | 执行与签名证据链 |

这些消费方需要一个**唯一的执行事实来源**。若每家各记一份，账就对不上。

**理由四：护理文书有独立的法律地位。**

护理记录、交接单、执行签名属于病历的组成部分（《医疗机构病历管理规定》《电子病历应用管理规范》），有保存年限（≥15 年）、修改规则（签名后不可改、只能作废重建）、证据效力（可作法庭证据）。它们的生命周期与医生医嘱完全不同。

**理由五：眼科护理有六项专科特殊性（详见 §1.4）。**

滴眼液最小间隔、左右眼独立执行、术后体位护理、眼罩眼垫护理、视力与眼压作为护理监测指标——这些在通用 HIS 里没有现成模型，必须专门设计。

### 1.4 眼科护理的六个特殊性

**特殊性一：滴眼液的物理约束。**

结膜囊容量 7~10 μL，一滴约 30 μL。滴一滴已经溢出 3~4 倍，第二滴必然冲走第一滴。规范要求同眼两药间隔 ≥5 分钟，凝胶/眼膏需 10 分钟，且需按压内眦泪囊 2~3 分钟（尤其 β 受体阻滞剂，不压迫则经鼻泪管全身吸收可致心率下降、支气管痉挛）。

→ 落到 M08-06 的规则：最小间隔三重校验、滴数上限 2 滴、按压泪囊必选核对项、β 阻滞类强制计时。

**特殊性二：左右眼是两次独立执行。**

「妥布霉素 双眼 QID 3 天」= 4 × 3 × 2 = **24 次独立动作**。分开记录的理由：左右眼可能间隔不同、计费按眼（`md_charge_item.charge_by_eye = TRUE`）、差错统计按眼（眼科质控按眼统计）。

→ 落到 M08-02 的规则：`eye_side = 'OU'` 必须展开成 2 条并行序列（DB 约束 `ck_m08_plan_eyes_count` 强制）。
→ 落到 M08-06 的规则：执行点只能是 `OD`/`OS`，不允许 `OU`（DB 约束 `ck_m08_drop_eye_side`）；界面右眼蓝 / 左眼橙 / 双眼灰，不预填上一次。

**特殊性三：全身 + 局部双重给药。**

典型青光眼方案 = 口服乙酰唑胺 250mg TID（全身降眼压）+ 滴眼噻吗洛尔 BID（β 阻滞）+ 口服氯化钾。叠加后果：心率过缓、低钾血症、哮喘患者可诱发支气管痉挛。

→ 落到 M08-06 的规则：交叉作用提示（INFO/WARN/BLOCK 三级）、给药后 30 分钟测脉率、出院前复查血钾。

**特殊性四：术后体位护理。**

视网膜脱离术后面朝下 7~10 天，体位依从性直接决定手术成功率；青光眼术后需半卧位。体位是护理观察项而非医疗医嘱项。

→ 落到 M08-05 的眼科补充段（E 段）与 M08-07 的床边交接 C-02 项。

**特殊性五：眼罩/眼垫护理高频。**

术后遮盖、换药、清洁是频次最高的护理操作之一。眼罩脱落可能导致感染或患者误揉眼。

→ 落到 M08-07 的床边交接 C-03 项必须单列（混在「一般情况」里易被略过）。

**特殊性六：视力与眼压是护理监测指标。**

术后视力不升反降提示眼内炎；眼压 >25 提示前房积血或恶性青光眼；双侧瞳孔不等大提示视神经损伤。这些在综合医院归医生，在眼科归护理班次监测。

→ 落到 M08-04 的体征项：23 项中含视力 4 项、眼压 2 项、瞳孔 2 项、对光反射 2 项；眼压阈值四档（≥50 CRITICAL，5 分钟内处置否则视神经不可逆损伤）。

### 2.2 六条拆分主线

**主线一：按「护士在什么时候做什么」分，不按数据表分。**

护士的班次流程是：签到 → 看队列 → 按计划执行 → 记录 → 交班。每个环节的时间粒度与可补性都不同：

| 环节 | 时间粒度 | 可补性 | 对应子模块 |
|---|---|---|---|
| 执行计划 | 天级 | 可改可重算 | M08-02 |
| 任务队列 | 分钟级 | 实时刷新 | M08-01 |
| 医嘱执行 | 秒级 | **签名后不可改** | M08-03 |
| 体征 | 时点 | 当日 24 小时内可改 | M08-04 |
| 护理记录 | 班次级 | 24 小时内可补写 | M08-05 |
| 用药给药 | 秒级 | **签名后不可改** | M08-06 |
| 交接班 | 班次级 | **双签后不可改** | M08-07 |

若按数据表分（比如「患者表」「任务表」「记录表」），每个子模块都会横跨多个环节，可补性规则必然互相冲突。

**主线二：执行计划必须独立成子模块（M08 最大增量）。**

**事实依据：** M07-03 的 `m07_order` 60+ 字段中 `frequency`/`freq`/`route`/`给药途径`/`频次`/`exec_time`/`执行时间` **grep 零命中**（唯一相关是注释「已完成必须有执行时间」，指 `executed_at` 记录已完成而非计划执行）。`m07_prescription_item` 虽有 frequency/route/days，但那是**处方**，下游是 M14 药房调配，不是护理执行。

**结论：** 不建执行计划，护士根本不知道「今天该做几次、几点做、哪只眼」。M08-02 承担三个转换：

1. 频次 → 时间点（`md_frequency.execute_times`）
2. 疗程 → 日期序列（单位可能是「天」或「次」，需换算）
3. **眼别 → 分眼执行**（双眼 QID = 8 个执行点）

**主线三：执行记录必须与执行计划分离。**

计划可改（医生停了医嘱、护士长调整给药时间），执行记录只增不改（签名后不可变更）。若合成一张表，「重算计划」的代码迟早会顺手改掉已执行的记录。

→ M08-02 的黄金原则：**已执行的执行点永不删除、永不修改。** 重算只取消未执行部分并重新生成。

**主线四：用药与滴眼必须单独成子模块。**

理由见 §1.4 特殊性一、二、三。凝练成一句：**普通给药（口服、注射）一次动作一次记录；滴眼是「同一动作在一只眼上重复 N 次且彼此有时间间隔约束」的特例，其校验逻辑（最小间隔、开封效期、分眼顺序、泪囊按压）在其他给药方式中完全不存在。**

**主线五：护理评估与护理记录分属两个子模块。**

- **评估（M08-04）** 是结构化数值：量表得分、风险等级、体征值。可聚合、可趋势、可告警。
- **记录（M08-05）** 是半结构化文书：护士写的段落。不可聚合、不触发告警、但要能作为证据。

**关键判定：** M06-06 的 D-14「护理记录」检查项必须能用一个明确 SQL 判定：

```sql
SELECT COUNT(*) FROM m08_nursing_record
WHERE admission_id = ? AND status = 'SIGNED' AND is_deleted = FALSE
```

若把评估表也算「护理记录」，只量了体温没写护理记录的患者会被误判为齐全——D-14 就失去意义。

**主线六：腕带不是 M08 的。**

- 门诊无腕带。
- 日间手术腕带由 **M06-04** 生成（`m06_wristband`，条码 `patient_id|admission_no|identity_hash`）。
- **M08 只读不生成。**

理由：腕带是「患者身份凭证」，应在患者进入手术流程时一次性生成并全程唯一；若 M08 也能生成，会出现同一患者两条有效腕带。

## 3. 核心业务模型

### 3.1 数据流总览

```
医生下达医嘱（M07-03，含 order_type / item_code / eye_side / quantity）
    │
    ▼
M08-02 展开执行计划
    ├─ 频次 → 时间点            md_frequency.execute_times
    ├─ 疗程 → 日期序列          quantity + 单位
    └─ 眼别 → 分眼序列          OD/OS/NA → 1 条；OU → 2 条
    │
    ▼ 生成 N 个执行点（m08_exec_point，状态 PLANNED）
    │
    ▼
M08-01 每日 06:00 批量生成当日任务（m08_task，状态 PENDING）
    │
    ▼
护士认领 → 执行
    ├─ M08-03 医嘱执行（换药/冲洗/治疗/术前准备）：核对 → 执行 → 签名
    ├─ M08-06 用药与滴眼：间隔校验 → 开瓶效期校验 → 分眼执行 → 签名
    └─ M08-04 体征采集：录入 → 阈值判定 → 告警
    │
    ▼
M08-05 护理记录（班次末，引用本班体征/执行/给药数据）
    │
    ▼
M08-07 交接班（六区块汇总 → 床边核对 → 双签 → 任务转移）
    │
    ▼
回写 M07（on-executing / on-completed）→ 医嘱状态 COMPLETED
    │
    ▼
M06-06 病历归档 / M16 计费 / M22 报表
```

### 3.2 执行点生命周期

执行点是 M08 的**核心连接件**——它是计划的产物、任务的来源、执行的依据、计费的凭据。

```
   PLANNED ──────► SCHEDULED ──────► EXECUTED（终态）
      │               │
      │               ├─────────────► SKIPPED（终态，需原因 ≥10 字）
      │               │
      │               └─────────────► SUSPENDED ⇄ SCHEDULED
      │
      └─────────────────────────────► CANCELLED（终态）
```

- `PLANNED`：已排计划，未到日期
- `SCHEDULED`：当日已生成任务
- `SUSPENDED`：临时停用（术前禁食、患者离院）
- `EXECUTED` / `SKIPPED` / `CANCELLED`：终态

**执行点与任务不是 1:1：**

| 来源 | 可合并 | 理由 |
|---|---|---|
| `ORDER` | ❌ | 医嘱是计费单位，一条只能被回写一次 |
| `EYEDROP` | ❌ | 左右眼是独立执行点，合并后眼别丢失 |
| `VITAL` | ✅ | 同患者同来源同 30 分钟窗口可合并 |
| `ASSESS` | ✅ | 同上 |
| `PREPARE` | ✅ | 同上 |

### 3.3 任务优先级模型

护士看到的任务列表必须有确定的顺序，否则「哪个先做」靠猜。

```
score = 基础分（来源）+ 紧急加成 + 护理级别加成 + 超时加成
```

**基础分（`SOURCE_BASE_SCORE`）：**

| 来源 | 分值 | 说明 |
|---|---|---|
| `ALERT` | 500 | 体征告警处置 |
| `EYEDROP` | 400 | 滴眼（有最小间隔约束，错过窗口影响后续所有滴眼） |
| `ORDER` | 300 | 医嘱执行 |
| `PREPARE` | 250 | 术前准备 |
| `VITAL` | 200 | 定时体征 |
| `ASSESS` | 150 | 护理评估 |

**紧急加成：** 加急 +300 / 临时医嘱 +200

**护理级别加成（`NURSING_LEVEL_BONUS`）：** `LEVEL_1` +100 / `LEVEL_2` +50 / `LEVEL_3` 0

**超时加成（`OVERDUE_BONUS`，越超时越靠前）：**

| 超时时长 | 加成 |
|---|---|
| 1~15 分钟 | +50 |
| 15~30 分钟 | +100 |
| 30~60 分钟 | +200 |
| > 60 分钟 | +400 |

**为什么超时加成是「越晚越急」而不是「越晚越废」：**

一个 8:00 该给的降压药到 8:45 还没给，患者血压可能已经飙起来。此时如果按「已超时太久放弃了」把它排到后面，正好把最危险的漏执行放在最后处理。超时加成必须递增。

**患者聚合校正：** 同患者任务分差 ≤100 时连续排列（减少护士走路），分差 >100 不聚合（保证高优先级任务不被「顺便」逻辑压后）。

### 3.4 执行四道关口（顺序不可颠倒）

```
①患者核对 → ②药品/项目核对 → ③时间与间隔校验 → ④剂量与途径核对 → 执行 + 记录 + 签名
```

**为什么顺序不能颠倒：** 若先校验间隔，护士的注意力被「才过 4 分钟」吸引，反而忽略手里拿的药是不是这个患者的。**先确认对象，再校验规则。**

### 3.5 电子签名模型

M08 有三处签名：执行签名（M08-03）、给药签名（M08-06）、记录签名（M08-05）、交接双签（M08-07）。四处共用同一套模型：

**摘要计算：**

```
digest = SHA-256(utf8(规范化串) + "|" + salt)
```

- 规范化串 = 按固定字段顺序用 `|` 拼接（None → 空串，时间 ISO8601 到秒）
- salt 存 M01-11 系统参数，不对护士暴露
- **摘要必须覆盖内容全文**，不能只覆盖 ID——否则 DBA 可直接改正文而不触发摘要变化，「签名有效」变成假象

**M08-07 交接单摘要字段（10 项 + N 条明细）：**

```
handover_no|ward_id|shift_date|shift_code|handover_staff_id|receive_staff_id
|team_summary|shift_data|supplement|role
+ 每条明细: item_type:bed_no:content
```

**M08-06 给药摘要字段（13 项）：**

```
admin_no|point_id|patient_id|drug_code|batch_no|eye_side|drops|site|actual_time
|executed_by|OVERRIDE/NORMAL|override_reason|PRESS
```

**时间戳：** 优先 M02-05 的 RFC 3161 可信时间戳；不可用时用服务器时间并标 `signature_source = 'LOCAL'`。

### 3.6 职责分离（SoD）汇总

| 编号 | 规则 | 落地位置 |
|---|---|---|
| SoD-01 | 调配/执行人 ≠ 核对人 | `ck_m08_execution_sod`、`ck_m08_med_sod`、触发器 `fn_m08_exec_nurse_sod` |
| SoD-02 | 两人签名时间差 ≥5 秒 | `ck_m08_handover_sign_gap`、服务层校验 |
| SoD-03 | 两人会话 ID 不能相同 | `ck_m08_med_session` |
| SoD-04 | 交班护士 ≠ 接班护士 | `ck_m08_handover_sod` |
| SoD-05 | 退药/退费审批人 ≠ 申请人 | 各表 `*_self_approve` 约束 |
| SoD-06 | 护士不能审批自己的作废申请 | 服务层校验 |
| SoD-07 | 排班调整审批人 ≠ 申请人 | 服务层校验 |
| SoD-08 | 补卡审批人 ≠ 申请人 | 服务层校验 |
| SoD-09 | 系统管理员无任何业务权限 | 权限矩阵 |

**SoD-02 的解释：** 一人代签两次点击通常 <2 秒。5 秒是「认真看一遍药名、剂量、浓度、途径、有效期」的最小时间。

### 3.7 三大数据铁律

**铁律一：只增表不可改。**

以下 6 张表有数据库触发器强制禁止 UPDATE/DELETE（历史数据修改只能通过作废 + 新建）：

| 表 | 触发器 | 理由 |
|---|---|---|
| `m08_task_transfer` | `fn_m08_task_transfer_readonly()` | 转派审计 |
| `m08_plan_log` | `fn_m08_plan_log_readonly()` | 计划变更审计 |
| `m08_execution_log` | 只增 | 执行审计 |
| `m08_vital_log` | 只增 | 体征修改审计 |
| `m08_nursing_record_log` | `fn_m08_record_log_readonly()` | 文书审计 |
| `m08_handover_log` | 只增 | 交接审计 |

**铁律二：签名后内容不可变。**

`EXECUTED`/`SIGNED` 状态的执行记录、给药记录、护理记录、交接单，正文与关键字段一律不可直接 UPDATE。修改走「作废 + 重建」，作废保留原记录。

**铁律三：行级先舍入再汇总。**

金额一律 `ROUND(x, 2)` 先行计算再求和。M08 涉及金额很少（主要是护理费/治疗费的执行确认），但凡是金额必须遵守。

### 3.8 数据一致性保障

M08 不建外键（与其他模块一致），一致性靠三层：

**第一层：DB 约束。** 数量自洽（`ck_m08_plan_eyes_count`、`ck_m08_dispense_item_balance` 类比）、状态自洽（`ck_m08_task_completed`）、SoD（`ck_m08_med_sod`）、唯一键（`uk_m08_task_source`、`uk_m08_point_slot`）。

**第二层：服务层事务。** 展开计划与生成执行点在同一事务；签名与回写队列在同一事务（回写异步）。

**第三层：定时对账。** 每日 03:00 校验：
- 执行计划点数 = 执行点表行数
- 任务数 = 执行点数（当日）
- 已签名执行数 = M07 回写成功数
- 交接单数 = 班次数

## 7. 技术架构与部署

### 7.1 服务架构

M08 采用**单体多模块**（`app.modules.m08_01` ~ `m08_07`），不拆微服务。

理由：
- 七个子模块共享同一执行点表与同一患者上下文，事务一致性要求高；
- 跨子模块调用是高频、同步、低延迟（执行 → 记录 → 交接）；
- 拆微服务会让一次「滴眼 + 给药记录 + 任务完成 + 医嘱回写」变成四次跨服务调用，延迟从 500ms 涨到 2 秒以上，而护士在床边只有几十秒。

### 7.2 三层数据存储

| 层 | 存储 | 内容 | 生命周期 |
|---|---|---|---|
| 热数据 | Redis | 队列缓存、配置、锁、会话 | 秒~小时 |
| 主数据 | PostgreSQL | 全部 42 张表 | 15 年（部分 3~5 年） |
| 冷数据 | 归档 CSV + 对象存储 | 超期数据 | 永久 |

### 7.3 连接池

| 用途 | 池大小 | 说明 |
|---|---|---|
| 业务（读写） | 20 | 执行、签名、体征采集 |
| 只读（查询） | 8 | 列表、详情 |
| 报表（统计） | 4 | 统计与导出 |

### 7.4 部署形态

```
                    ┌──────────────┐
                    │  Nginx/LB    │
                    └──────┬───────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
  ┌──────────┐      ┌──────────┐      ┌──────────┐
  │ Web 节点1 │      │ Web 节点2 │      │ PDA 网关  │
  │ FastAPI  │      │ FastAPI  │      │          │
  └────┬─────┘      └────┬─────┘      └────┬─────┘
       └─────────────────┼─────────────────┘
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
  ┌──────────┐    ┌──────────┐    ┌──────────┐
```

## 10. 异常与降级策略

### 10.1 降级原则

**总原则：能记的先记下来，记不下来的必须让护士知道。**

护理作业是「错过就没有第二次」的场景（8:00 该给的药 9:00 补上已经晚了）。因此：

- **执行记录、给药记录、体征采集**：优先保证「能写进去」，下游失败走补偿；
- **主数据查询**：能降级用快照就用快照，但必须留痕；
- **签名认证**：不可降级（无认证签名的记录不是证据）；
- **频次主数据**：不可降级（无频次无法展开计划）。

### 10.2 分级降级矩阵

| 依赖 | 失败时 | 是否阻断 | 留痕 |
|---|---|---|---|
| M01-10 频次 | 无法展开计划 | **阻断** | — |
| M01-10 班次定义 | 无法排班 | **阻断** | — |
| M01-03 药品 | 用本地快照 | 不阻断 | `degraded = TRUE` |
| M01-02 职工 | 拒绝签名 | **阻断** | — |
| M03-01 患者 | 拒绝（除交接单降级） | **阻断** | `degraded_modules` |
| M07-03 医嘱查询 | 用本地快照 | 不阻断 | 快照时间提示 |
| M07-03 回写 | 进补偿队列 | 不阻断 | `writeback_status` |
| M02-05 认证 | 拒绝签名 | **阻断** | — |
| M02-05 时间戳 | 本地时间 | 不阻断 | `signature_source = 'LOCAL'` |
| M14-08 病区药品 | 手工输入 | 不阻断 | 提示 |
| M02-06 审计 | 异步补偿 | 不阻断 | 补偿队列 |
| 交接单汇总（M08-01/04/05/06） | 显示「数据暂不可用」 | 不阻断 | `degraded_modules` |

### 10.3 三处关键降级的详细设计

**降级一：交接单生成（M08-07）。**

强依赖只有 M03-01（不知患者是谁交接单毫无意义）；其他五个区块（任务、体征、给药、记录、风险）每模块 800ms 超时即降级，`asyncio.gather` 并发后最坏 800ms。

降级后 `degraded_modules = ["M08-04"]`，界面显式提示「体征数据暂不可用」——不会出现「静默的 0」让护士长误以为全天无告警。

**降级二：医嘱回写（M08-03/M08-06）。**

签名先落库提交，再异步回写 M07。回写失败进补偿队列，指数退避 1/2/4/8/16/32/64/128/256/512 秒，10 次后标 `DEAD` 并告警。

**为什么不在签名事务里同步回写：** `on-completed` P95 ≤100ms 但抖动可能 1 秒。护士点签名要等 1 秒，失败还要整单回滚导致执行记录丢失——**证据优先于系统间通知**。

**降级三：体征趋势告警（M08-04）。**

单值判定同步（62ms），趋势与组合判定异步；异步失败由补偿任务每 5 分钟扫最近 1 小时约 30 行（<20ms）补生成。

### 10.4 幂等策略

| 场景 | 幂等键 |
|---|---|
| 任务生成 | `uk_m08_task_source (source_type, source_id)` 全表唯一 |
| 执行点生成 | `uk_m08_point_slot (plan_id, planned_time, eye_side)` |
| 执行记录 | `execution_no` 唯一 + `uk_m08_point_exec_no` |
| 给药记录 | `uk_m08_med_point_active (point_id) WHERE status <> 'VOID'` |
