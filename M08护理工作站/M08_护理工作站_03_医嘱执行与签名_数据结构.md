**设计说明：**

1. **`m08_execution` 与 `m08_exec_point`（M08-02）是 1:1 但不建外键**。执行点可能因作废而重新执行，产生「一执行点：1 条作废 + 1 条有效」的关系。外键会让作废时要处理引用完整性，而作废本就应当保留原记录。

2. **`m08_execution_item` 用于「一次执行涉及多个对象」**。例如一次换药涉及左眼与右眼，或一次注射涉及 2 个部位。单眼单部位的常见情形可以只在主表记录，不产生明细行（`m08_execution_item` 允许为空）。

3. **`m08_execution_check` 同时承担两种核对**：`check_type = 'PATIENT_IDENTITY'` 的行记录身份核对尝试（含失败），`check_type = 'CHECK_ITEM'` 的行记录各核对项结果。合并到一张表的原因是它们共享 `checked_by`、`checked_at` 语义，且查询时总是要一起看。

4. **`m08_execution_nurse` 是签名表而不是冗余字段**。一次执行最多 3 行（执行者、核对者、签名者），双人核对要求两人不同的约束通过索引与业务规则实现；若用主表两个字段（`executor_id`/`checker_id`）就无法表达「签名者可第三个人」。

5. **`m08_execution_attachment` 独立成表**。附件是多值（最多 5 张），且需要 SHA-256 去重和独立的存储路径。

6. **`m08_execution_log` 只增不改**，触发器强制。它是「这条记录从创建到作废经历了什么」的唯一答案。

**约束说明：**

```sql
-- 执行编号格式
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_no
  CHECK (execution_no ~ '^EX[0-9]{8}[0-9]{5}$');

-- 幂等键格式
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_idem
  CHECK (idempotency_key ~ '^EXEC:[0-9]+$');

-- 状态枚举
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_status
  CHECK (status IN ('PENDING', 'CHECKING', 'EXECUTING', 'COMPLETED',
                    'PARTIAL', 'REFUSED', 'EXCEPTION', 'SIGNED', 'VOIDED'));

-- 执行结果枚举
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_result
  CHECK (result IS NULL
         OR result IN ('COMPLETED', 'PARTIAL', 'REFUSED', 'EXCEPTION'));

-- 异常类型枚举
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_exception
  CHECK (exception_type IS NULL
         OR exception_type IN ('PATIENT_ABSENT', 'PATIENT_REFUSED', 'EXEC_FAILED',
                               'PARTIAL_DONE', 'ADVERSE_REACTION', 'OTHER'));

-- 后续处理枚举
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_followup
  CHECK (follow_up_action IS NULL
         OR follow_up_action IN ('RETURN_TO_POOL', 'NOTIFY_DOCTOR', 'REPORT_ADVERSE'));

-- 眼别枚举
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_eye
  CHECK (eye_side_plan IN ('OD', 'OS', 'OU', 'NA')
         AND (actual_eye_side IS NULL
              OR actual_eye_side IN ('OD', 'OS', 'OU', 'NA')));

-- 身份核对方式枚举
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_verify_method
  CHECK (patient_verify_method IS NULL
         OR patient_verify_method IN ('WRISTBAND', 'CARD', 'MANUAL_TWO',
                                      'DOUBLE_CONFIRM'));

-- 核对结果枚举
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_check_result
  CHECK (check_result IS NULL OR check_result IN ('OK', 'WARN'));

-- 签名后不可改：已签名必须完整记录
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_signed
  CHECK (status <> 'SIGNED'
         OR (signed_at IS NOT NULL
             AND signed_by IS NOT NULL
             AND signature_digest IS NOT NULL
             AND executed_at IS NOT NULL
             AND result IS NOT NULL));

-- 签名摘要必须是 64 位小写十六进制
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_digest
  CHECK (signature_digest IS NULL OR signature_digest ~ '^[0-9a-f]{64}$');

-- 执行完成必须有执行时刻与实际数量
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_executed
  CHECK (status NOT IN ('COMPLETED', 'PARTIAL', 'REFUSED', 'EXCEPTION', 'SIGNED')
         OR (executed_at IS NOT NULL));

-- 需要双人核对时签名前必须完成
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_double
  CHECK (status <> 'SIGNED' OR need_double_check = FALSE OR double_check_complete = TRUE);

-- 执行人与核对人不能是同一人（SoD-01 的 DB 层兜底）
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_sod
  CHECK (executor_id IS NULL OR checker_id IS NULL OR executor_id <> checker_id);

-- 作废必须完整记录
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_voided
  CHECK (status <> 'VOIDED'
         OR (void_reason IS NOT NULL
             AND char_length(btrim(void_reason)) >= 10
             AND voided_by IS NOT NULL
             AND voided_at IS NOT NULL));

-- 异常必须有类型与说明
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_exception_note
  CHECK (exception_type IS NULL
         OR (exception_note IS NOT NULL
             AND char_length(btrim(exception_note)) >= 10));

-- 不良反应必须有附件（应用层与触发器共同保证，此处只保证不与其他结果冲突）
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_adverse
  CHECK (exception_type <> 'ADVERSE_REACTION' OR result = 'EXCEPTION');

-- 回写状态枚举
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_writeback
  CHECK (writeback_status IN ('PENDING', 'SUCCESS', 'FAILED', 'DEAD'));

-- 回写成功必须有时刻
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_writeback_ok
  CHECK (writeback_status <> 'SUCCESS' OR writeback_at IS NOT NULL);

-- 回写失败必须有错误信息
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_writeback_fail
  CHECK (writeback_status NOT IN ('FAILED', 'DEAD') OR writeback_error IS NOT NULL);

-- 实际数量必须正数
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_qty
  CHECK (actual_qty IS NULL OR actual_qty > 0);

-- 说明字段长度上限
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_remark_len
  CHECK (remark IS NULL OR char_length(remark) <= 500);

-- 解锁必须有解锁人
ALTER TABLE m08_execution
  ADD CONSTRAINT ck_m08_execution_unlock
  CHECK (patient_verify_unlocked = FALSE
         OR (unlocked_by IS NOT NULL AND unlocked_at IS NOT NULL));

COMMENT ON TABLE m08_execution IS 'M08-03 执行记录主表，签名后不可修改，只能作废后重建';
COMMENT ON COLUMN m08_execution.idempotency_key IS '幂等键 EXEC:{point_id}，保证一执行点一条有效记录';
COMMENT ON COLUMN m08_execution.patient_verify_attempts IS '身份核对尝试次数，连续 2 次不符锁定';
COMMENT ON COLUMN m08_execution.signature_digest IS '签名摘要 SHA-256，覆盖 14 个关键字段';
COMMENT ON COLUMN m08_execution.writeback_status IS '回写 M07 的状态，PENDING/SUCCESS/FAILED/DEAD';
COMMENT ON COLUMN m08_execution.void_of_execution_id IS '作废后重建时指向被作废的原记录';
```

**状态机：**

```
                 PENDING（执行点已排，未开始）
                     │
                     ▼
                 CHECKING（核对中）────────────► 删除草稿（is_deleted=TRUE）
                     │
                     ▼
                 EXECUTING（已核对，执行中）
                     │
      ┌──────────────┼──────────────┬──────────────┐
      ▼              ▼              ▼              ▼
  COMPLETED      PARTIAL        REFUSED        EXCEPTION
      │              │              │              │
      └──────────────┴──────────────┴──────────────┘
                              │ 签名
                              ▼
                          SIGNED（终态）
                              │ 护士长作废
                              ▼
                          VOIDED（终态）
```

**设计要点：**

1. **`uk_m08_execution_point` 与 `uk_m08_execution_idem` 是双重保险。**
   `point_id` 条件唯一表达「一个执行点同时只能有一条有效记录」；`idempotency_key` 唯一表达「重复提交不会产生第二条」。两者都保留，因为前者允许作废后重建（`status <> 'VOIDED'`），后者在创建时立即拦截重复。

2. **为什么 `ck_m08_execution_sod` 在 DB 层？**
   「执行人与核对人不能是同一人」是医疗安全底线。服务层校验可被绕过（其他模块直接写库、数据修复脚本），DB 约束不可绕过。

3. **为什么 `signature_digest` 加格式约束。**
   SHA-256 摘要必须是 64 位小写十六进制。格式约束能在写入时就发现「摘要算法用错」或「摘要计算范围错」的问题，而不是等到复算时才发现。

4. **`ck_m08_execution_signed` 强制签名记录完整。**
   `SIGNED` 状态必须有 `signed_at`、`signed_by`、`signature_digest`、`executed_at`、`result`。这确保不存在「签名了但没有摘要」这种法律上无效的记录。

5. **为什么保留 `dose_plan`/`route_code_plan`/`eye_side_plan` 快照。**
   医嘱可能在执行后又被修改（虽然已执行后修改不常见）。执行记录必须保留「当时医嘱说该怎么做」的证据，与实际做的对比才能证明执行是否正确。

6. **`writeback_note` 的作用。**
   记录「跳过了 EXECUTING 直接完成」等异常情形。质控核查时能看出哪些记录的回写路径不标准。

7. **为什么 `executed_at` 允许为空而 `SIGNED` 时必须非空。**
   核对阶段（`CHECKING`）还没有执行，`executed_at` 自然为空。签名时一定有执行时刻，约束保证这一点。

8. **`void_of_execution_id` 形成作废链。**
   作废后重建的新记录指向旧记录。查询时可直接展示「原记录 → 作废 → 新记录」的完整链条。

**量级估算：**

| 项目 | 数值 | 计算依据 |
|---|---|---|
| 日均执行记录 | 400 | 与日均执行点数中实际执行部分相当 |
| 年执行记录 | 146,000 | 400 × 365 |
| 单行长度 | 约 1.2 KB | 含大量文本与摘要字段 |
| 年数据量 | 约 175 MB | — |
| 15 年累计 | 约 2,190,000 行 | 约 2.6 GB（含索引约 4.2 GB） |

> 保留期建议 15 年（护理执行记录属病案资料，与病历同期保存）。若实测分区分裂，可按 `executed_at` 年度 RANGE 分区，此时 `uk_m08_execution_point`/`uk_m08_execution_idem` 需含分区键，语义退化为「同年唯一」——因执行点不会跨年重复，可接受。

**分区：** 暂不分区（见上文说明）。

**设计要点：**

1. **为什么身份核对失败的记录也要存？**
   核对失败是重要的质量信号：「今天有多少次扫错患者」是评估核对机制有效性的关键指标。只存成功记录会让系统的核对看起来「零差错」，掩盖真实问题。

2. **`server_checked_at` 的防篡改作用。**
   签名时校验「核对时间 → 签名时间」的间隔。若用前端时间，护士可以改本地时钟绕过。用服务器时间作为权威依据。

3. **为什么 `uk_m08_exec_check_item` 只约束 `CHECK_ITEM`。**
   身份核对可能多次尝试（每次失败一行），不能唯一。核对项一旦提交就不能重复提交（同一项只有一条结果），所以唯一。

4. **`matched_patient_id` 的用途。**
   扫错患者时记录「扫到的是谁」，前端可以提示「核对不符：该条码属于 5床 赵明」。这既是安全功能也是易用性功能。

```sql

ALTER TABLE m08_execution_nurse
  ADD CONSTRAINT ck_m08_exec_nurse_role
  CHECK (nurse_role IN ('EXECUTOR', 'CHECKER', 'SIGNER'));

-- 签名摘要格式
ALTER TABLE m08_execution_nurse
  ADD CONSTRAINT ck_m08_exec_nurse_digest
  CHECK (signature_digest IS NULL OR signature_digest ~ '^[0-9a-f]{64}$');

-- CHECKER 与 EXECUTOR 不能是同一人（SoD-01 的第二道防线）
CREATE OR REPLACE FUNCTION fn_m08_exec_nurse_sod()
RETURNS TRIGGER AS $$
DECLARE
  v_executor BIGINT;
BEGIN
  IF NEW.nurse_role = 'CHECKER' THEN
    SELECT nurse_id INTO v_executor
    FROM m08_execution_nurse
    WHERE execution_id = NEW.execution_id AND nurse_role = 'EXECUTOR'
    LIMIT 1;
    IF v_executor IS NOT NULL AND v_executor = NEW.nurse_id THEN
      RAISE EXCEPTION 'M08-03: 执行人与核对人不能是同一人';
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m08_exec_nurse_sod
  BEFORE INSERT OR UPDATE ON m08_execution_nurse
  FOR EACH ROW EXECUTE FUNCTION fn_m08_exec_nurse_sod();

COMMENT ON TABLE m08_execution_nurse IS 'M08-03 执行护士签名表，一次执行最多 3 行';
COMMENT ON COLUMN m08_execution_nurse.nurse_role IS 'EXECUTOR 执行者 / CHECKER 核对者 / SIGNER 签名者';
COMMENT ON COLUMN m08_execution_nurse.session_id IS '登录会话 ID，用于校验两人不是同一次会话';
COMMENT ON COLUMN m08_execution_nurse.device_info IS '设备信息，形如 10.20.1.35/WS-03';
```

**设计要点：**

1. **为什么单独建表而不是主表三列。**
   主表已有 `executor_id`/`checker_id`/`signed_by` 三个字段用于快速查询。`m08_execution_nurse` 记录的是「签名事件」——包含签名摘要、会话 ID、设备信息。两者并存：主表字段供业务查询，签名表供法律取证。

2. **触发器 `fn_m08_exec_nurse_sod` 的作用。**
   主表有 `ck_m08_execution_sod` 约束 `executor_id <> checker_id`，但那是在主表更新时生效。若代码先插入签名表再更新主表，中间存在窗口。触发器在签名表插入时立即校验，堵住窗口。

3. **`session_id` 支撑 SoD-03。**
   「两人不能同时用同一台设备的同一会话」——若两人 `session_id` 相同，说明是一人切换账号代签。

4. **`uk_m08_exec_nurse_role` 的限制说明。**
   实际应为：`EXECUTOR` 唯一、`SIGNER` 唯一、`CHECKER` 可多条（一般 1 条）。当前约束 `(execution_id, nurse_role)` 全唯一，若未来需要多核对人（如输血需 3 人），需改为部分唯一索引仅约束 `EXECUTOR` 与 `SIGNER`。当前 M08-03 的双人核对只涉及 1 名核对人，暂用全唯一。

```sql
ALTER TABLE m08_execution_attachment
  ADD CONSTRAINT ck_m08_exec_att_type
  CHECK (content_type IN ('image/jpeg', 'image/png', 'application/pdf'));

-- 附件类型枚举
ALTER TABLE m08_execution_attachment
  ADD CONSTRAINT ck_m08_exec_att_kind
  CHECK (attachment_type IN ('PHOTO', 'DOC'));

-- 每次执行附件数不超过 5 张（通过触发器保证）
CREATE OR REPLACE FUNCTION fn_m08_exec_att_limit()
RETURNS TRIGGER AS $$
DECLARE
  v_count INT;
BEGIN
  SELECT COUNT(*) INTO v_count
  FROM m08_execution_attachment
  WHERE execution_id = NEW.execution_id AND is_deleted = FALSE;
  IF v_count >= 5 THEN
    RAISE EXCEPTION 'M08-03: 附件数量超出限制（最多 5 张）';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m08_exec_att_limit
  BEFORE INSERT ON m08_execution_attachment
  FOR EACH ROW EXECUTE FUNCTION fn_m08_exec_att_limit();

COMMENT ON TABLE m08_execution_attachment IS 'M08-03 执行附件表，拍照留证';
COMMENT ON COLUMN m08_execution_attachment.sha256 IS '文件 SHA-256，用于去重与完整性校验';
COMMENT ON COLUMN m08_execution_attachment.file_path IS '存储路径，如 /data/m08/exec/51288/a3f2c81e';
```

**设计要点：**

1. **为什么附件数量限制用触发器而不是应用层？**
   应用层可以在并发时被绕过：两个请求同时判断「当前 4 张，可以再加」→ 都插入 → 变 6 张。触发器在行插入时串行化判断，保证严格不超过 5 张。

2. **`uk_m08_exec_att_sha` 的作用。**
   同一份文件被重复上传（网络重试、用户连点）时，唯一索引拦截。这既是去重也节省存储。

3. **内容类型白名单而非黑名单。**
   黑名单（排除 exe/bat）永远列不全。白名单只允许 jpg/png/pdf 三种，安全且符合医疗场景。

4. **为什么把文件本体存文件系统而不是 DB？**
   2MB × 每次执行 1~2 张 × 年 14.6 万次 ≈ 年 300 GB。存 DB 会让备份与恢复变得非常笨重。文件存 NAS/S3，DB 只存路径与 SHA-256。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 有附件的执行占比 | 约 20% |
| 每次附件数 | 约 1.5 |
| 年均附件 | 43,800 |
| 单行长度 | 约 350 字节 |
| 年 DB 数据量 | 约 15 MB |
| 年文件数据量 | 约 87 GB（按单文件 2MB 平均 1MB 估） |

**分区：** DB 表不分区；文件存储按年目录组织（`/data/m08/exec/{yyyy}/{execution_id}/`），保留期与执行记录一致。

**用途：** 执行日志表。记录执行记录的全部状态变更与关键操作。**只增不改**，触发器强制。

**字段定义：**

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m08_execution_log` | 主键 | `id` | — |

| `idx_m08_exec_log_time` | B-Tree | `(operated_at)` | 按时间查询 |
| `idx_m08_exec_log_action` | B-Tree | `(action, operated_at)` | 按操作类型统计 |

**约束说明：**

```sql
-- 操作类型枚举
ALTER TABLE m08_execution_log
  ADD CONSTRAINT ck_m08_exec_log_action
  CHECK (action IN ('CREATE', 'UPDATE', 'DELETE', 'VERIFY_PATIENT', 'VERIFY_FAIL',
                    'UNLOCK_PATIENT', 'SUBMIT_CHECK', 'REQUEST_DOUBLE_CHECK',
                    'DOUBLE_CHECK_SUBMIT', 'START', 'RECORD', 'EXCEPTION',

-- 明细必须是 JSON 对象
ALTER TABLE m08_execution_log
  ADD CONSTRAINT ck_m08_exec_log_detail
  CHECK (detail IS NULL OR jsonb_typeof(detail) = 'object');

-- 只增不改：禁止 UPDATE 与 DELETE
CREATE OR REPLACE FUNCTION fn_m08_exec_log_readonly()
RETURNS TRIGGER AS $$
BEGIN
  RAISE EXCEPTION 'm08_execution_log 为只增表，禁止 UPDATE/DELETE';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m08_exec_log_update
  BEFORE UPDATE ON m08_execution_log
  FOR EACH ROW EXECUTE FUNCTION fn_m08_exec_log_readonly();

CREATE TRIGGER trg_m08_exec_log_delete
  BEFORE DELETE ON m08_execution_log
  FOR EACH ROW EXECUTE FUNCTION fn_m08_exec_log_readonly();

COMMENT ON TABLE m08_execution_log IS 'M08-03 执行日志表，只增不改';
COMMENT ON COLUMN m08_execution_log.detail IS '操作明细，结构随 action 不同，如 {"attempt":2,"barcode":"******123456"}';
```

**设计要点：**

1. **为什么日志表必须只增不改。**
   日志用于回答「这条记录为什么被作废」「谁在什么时候解锁了身份核对」。若可改，答案就可被篡改。触发器让任何 UPDATE/DELETE 直接报错。

2. **`detail` 存 JSONB 而不是展开成列。**
   不同 `action` 需要记录的明细完全不同（核对尝试记录条码，签名记录摘要，回写记录错误）。展开成列会产生大量 NULL。

3. **为什么不裁剪敏感信息。**
   `detail` 中 `barcode` 需脱敏（保留后 6 位），口令绝对不能记录。这由服务层保证。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 每次执行平均日志行 | 6 |
| 年均日志行 | 876,000 |
| 单行长度 | 约 250 字节 |
| 年数据量 | 约 219 MB |
| 分区策略 | 月度 RANGE |

**分区：** 按 `operated_at` 月度 RANGE 分区，预建 36 个月，热数据保留 180 天，冷数据归档。

```sql

  operator_id BIGINT,
  operator_name VARCHAR(64),
  operated_at TIMESTAMP NOT NULL DEFAULT NOW(),
  client_ip VARCHAR(64),
  trace_id VARCHAR(64),
  PRIMARY KEY (id, operated_at)
) PARTITION BY RANGE (operated_at);

CREATE TABLE m08_execution_log_p202610 PARTITION OF m08_execution_log
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
-- 后续分区由 pg_partman 或定时任务预建
```
