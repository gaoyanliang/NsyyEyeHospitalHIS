## 1. 模块概述

### 1.1 模块定位

M08-01 是护理工作站的**入口页与调度中枢**。护士上班第一件事是打开它，下班最后一件事是看它清空没有。

```
┌─────────────────────────────────────────────────────────────────────┐
│                        护士的一个班次（8 小时）                     │
│                                                                     │
│  07:50  登录 → ┌─────────────────────────────────┐                 │
│                │  M08-01 护理任务与执行队列       │                 │
│                │  「我这一班要做什么」            │                 │
│                └──────────┬──────────────────────┘                 │
│                           │                                         │
│         ┌─────────────────┼─────────────────┬──────────────────┐   │
│         ▼                 ▼                 ▼                  ▼   │
│   ┌──────────┐      ┌──────────┐      ┌──────────┐      ┌─────────┐│
│   │ 待执行    │      │ 定时体征  │      │ 滴眼任务  │      │ 待处理  ││
│   │ 医嘱任务  │      │ 采集任务  │      │  M08-06   │      │ 预警    ││
│   │ M08-02/03│      │  M08-04   │      │           │      │ M08-04  ││
│   └────┬─────┘      └────┬─────┘      └────┬─────┘      └────┬────┘│
│        │                 │                 │                 │     │
│        └─────────────────┴─────────────────┴─────────────────┘     │
│                           │                                         │
│                 点击 → 跳到对应子模块执行                           │
│                 完成 → 任务从队列消失                               │
│                           │                                         │
│  15:50  ┌─────────────────▼─────────────────┐                      │
│         │  队列清空 → 交接班（M08-07）       │                      │
│         └───────────────────────────────────┘                      │
└─────────────────────────────────────────────────────────────────────┘
```

**一句话职责：**

> **M08-01 负责「把分散在各子模块的待办事项，聚合成当班护士看得懂的一个有序列表，并按患者/时间/优先级正确排序」。**

**M08-01 不负责：**

- 不产生执行计划（**M08-02** 负责）
- 不写执行记录（**M08-03 / M08-06** 负责）
- 不采集体征（**M08-04** 负责）
- 不做交接班（**M08-07** 负责）

### 1.2 为什么独立成子模块

**理由一：任务队列是"派生视图"，与它聚合的对象生命周期完全不同。**

队列里的每一条任务，其实都是别的子模块某个实体的**投影**：

| 队列里的任务 | 真实来源 | 生命周期差异 |
|---|---|---|
| 「3 床 8:00 静滴头孢呋辛」 | M08-02 执行点 | 执行点存在 5 天，队列里只出现一次 |
| 「8:00 全病区生命体征」 | M08-04 排班规则 | 排班规则是常设的，任务是每天新生成的 |
| 「3 床 右眼 10:00 滴左氧」 | M08-06 滴眼任务 | 与执行点同源但多一层眼别拆分 |
| 「3 床 血压 145/90 需复测」 | M08-04 预警提示 | 预警存在到复测为止，可能 2 小时 |

**如果合进任何一边**，比如把队列合进 M08-02，那 M08-02 就不得不理解生命体征、预警规则、滴眼拆分——它会从"把医嘱展开成时间点"这个纯逻辑子模块，膨胀成一个什么都懂的巨型模块。

**理由二：队列的查询模式与所有其他数据都不同。**

| 维度 | 队列 | 执行记录 | 执行计划 |
|---|---|---|---|
| 查询频率 | **每 30 秒刷新一次** | 偶尔查 | 偶尔查 |
| 数据量 | 一个班次 20~80 条 | 15 年数百万条 | 每天新建几百条 |
| 索引 | `(nurse_id, status)` | `(patient_id, date)` | `(order_id)` |
| 一致性要求 | 允许 30 秒延迟 | 强一致 | 强一致 |
| 存储 | **Redis 缓存 + DB 落库** | DB | DB |

如果按队列的高频刷新频率去优化执行记录表，会浪费大量资源；反之如果让队列按执行记录的方式强一致查询，每 30 秒全表扫一次，护士站着等 2 秒。

**理由三：任务排序是护理专业判断，不是简单的时间排序。**

护士看到的顺序不是"8:00 的排前面"。真实排序规则：

1. **紧急优先**：心跳骤停、大出血、眼压急性升高 → 立即置顶
2. **患者优先级**：一级护理 > 二级护理 > 三级护理
3. **时间窗口**：已超过计划时间 30 分钟的标红置前（不是押后——超时任务更该先做）
4. **同患者聚合**：同一患者的多个任务放在一起，护士走一趟全做完，而非来回跑
5. **同医嘱合并**：同一医嘱的多个执行点，已完成的不再显示

这套规则需要独立设计、独立测试、独立调优。

**理由四：护士的任务来源必须是"多对一"汇聚，不能是"一对一对接"。**

如果 M08-01 不存在，那每个子模块都要自己做一套"谁能看到、谁在做、做到哪了"的机制。做五遍，五套不一致的机制。

**理由五：任务认领与协作是独立的业务概念。**

真实病区里会有：

- 护士 A 请假，她的任务要转给护士 B（**转派**）
- 某任务太重（如大换药），两人一起做（**协作**）
- 某任务护士不会做（如针灸），要请教（**求助**）
- 护士长要看到全科待办（**全科大屏**）

「任务」与「执行记录」是两个东西：任务可以被转派、被认领、被取消，而执行记录一旦写就不可改。

### 1.4 概念辨析

#### 1.4.1 任务（Task）≠ 执行点（Execution Point）

| | 任务（`m08_task`） | 执行点（`m08_exec_point`，M08-02） |
|---|---|---|
| 存在目的 | 「护士要去做一件事」 | 「医嘱在某时刻的效果」 |
| 面向对象 | 护士 | 医嘱 |
| 数量关系 | 1 个执行点 → 1 个任务（可转派） | 1 个医嘱 × N 天 × M 次 = N×M 个执行点 |
| 可否取消 | 可以（任务取消） | 不可以（执行点只能作废并留痕） |
| 可否合并 | **可以合并**：同一患者的 3 个体征可合成 1 个任务 | 不可以 |
| 生命周期 | 当班有效（跨班自动转派） | 跟随医嘱（可能 7 天） |

**关键差异举例：**一个「每日 3 次 × 5 天」的静滴医嘱，M08-02 生成 **15 个执行点**。M08-01 每天只把当天的 3 个执行点转成任务放进队列——第 4、5 天的执行点还没到，不用出现在今天的工作清单里。

#### 1.4.2 任务队列（Queue）≠ 门诊候诊队列（M04-05）

| | M08-01 任务队列 | M04-05 候诊队列 |
|---|---|---|
| 排队对象 | **护士待办事项** | 患者 |
| 谁在等 | 护士 | 患者 |
| 谁在看 | 护士 | 患者（叫号屏） |
| 排序依据 | 紧急度 + 护理级别 + 时间 | 挂号顺序 / 级别优先 |
| 涉及科室 | 护理单元 | 门诊诊室 |

#### 1.4.3 护士（Nurse）≠ 药士（Pharmacist）≠ 技师（Technician）

M08-01 的队列只有 M08 护理任务。药房调配是 M14-07、检查执行是 M12-02、手术配合是 M09——它们各自有自己的工作台，不进 M08 队列。

但有一处例外：**日间手术/住院场景的术前准备**（散瞳、禁食确认、备皮）由护士执行，属 M08 队列。

#### 1.4.4 班次（Shift）≠ 排班（Schedule）≠ 交接班（Handover）

| 概念 | 含义 | 归属 |
|---|---|---|
| **排班**（Schedule） | 提前安排「谁哪天上哪个班」 | M08-07 |
| **班次**（Shift） | 实际执行的「8:00~16:00 白班，护士 A、B、C」 | M08-07 |
| **交接班**（Handover） | 上一班向下一班口头+书面交接 | M08-07 |
| **当班任务**（Task） | 在班次时间窗内必须完成的事项 | **M08-01** |

### 1.5 模块目标

| 指标 | 目标值 | 含义 |
|---|---|---|
| 队列首屏加载 P95 | ≤ 200ms | 护士打开工作台到看到第一个任务 |
| 队列刷新延迟 | ≤ 30 秒 | 医生停药后，护士最多 30 秒内看不到该任务 |
| WebSocket 推送延迟 P95 | ≤ 500ms | 有新任务后护士端收到推送 |
| 任务超时率 | ≤ 3% | 计划时间超过 30 分钟未执行 |
| 任务完成率 | ≥ 98% | 当班应做且实际做 |
| 任务转派率 | ≤ 10% | 过高说明排班不合理 |
| 任务认领冲突率 | ≤ 0.5% | 两人同时点同一任务 |
| 全科大屏刷新周期 | 10 秒 | 大屏不需要秒级 |
| 单病区支持任务数 | ≥ 500/班 | 三级医院病区规模上限 |
| 单院并发护士数 | ≥ 200 | 峰值（早交班时段） |
| 队列缓存命中率 | ≥ 95% | 保证首屏快 |

### 1.6 关键业务角色

| 角色 | 权限范围 | 主要操作 |
|---|---|---|
| **责任护士**（Primary Nurse） | 自己分管的患者 | 查看/认领/执行自己患者任务 |
| **辅助护士**（Assistant Nurse） | 被分配的患者 | 同上 |
| **护士**（Nurse） | 全病区 | 查看看全部任务，认领 |
| **护士长**（Head Nurse） | 全病区 + 跨区 | 转派、调配、看全科大屏、强制结束 |
| **护理部**（Nursing Dept） | 全院 | 只读，看统计 |

## 3. 业务模型

### 3.1 任务的六种来源

| 来源 | 代码 | 由谁生成 | 典型任务 | 是否可合并 |
|---|---|---|---|---|
| 医嘱执行 | `ORDER` | M08-02 执行点转任务 | 静滴头孢呋辛、换药 | 否（一医嘱一任务） |
| 定时体征 | `VITAL` | M08-04 排班规则 | 全病区 8:00 测体温 | **是**（同患者合并） |
| 护理评估 | `ASSESS` | M08-04 评估计划 | 入院评估、跌倒评估 | 是 |
| 滴眼执行 | `EYEDROP` | M08-06 滴眼拆分 | 右眼 10:00 左氧 | 否（眼别独立） |
| 术前准备 | `PREPARE` | M06-02 清单同步 | 散瞳、备皮、禁食确认 | 否 |
| 预警处理 | `ALERT` | M08-04 预警引擎 | 血压 145/90 需复测 | 否 |

**为什么按来源分类而不是混在一起：**

1. **失败处理不同**：`ORDER` 任务失败要回写 M07 医嘱；`VITAL` 任务失败只标记不执行，不影响医嘱状态
2. **可合并性不同**：`VITAL` 任务可以合并（一次走过去量 3 个体温）；`EYEDROP` 不能（左眼右眼是两个独立执行点）
3. **权限不同**：`ORDER` 任务需要护理执行权限；`VITAL` 任务药士也可执行；`PREPARE` 需手术室护士资质
4. **统计口径不同**：医嘱执行率 vs 体征采集率 vs 术前准备完成率，分开统计才有意义

### 3.2 任务状态机

```
                          ┌──────────────┐
                          │   PENDING    │  待认领（进队列，无人负责）
                          └──────┬───────┘
                                 │ 认领 / 自动分配
                                 ▼
                          ┌──────────────┐
              ┌───────────│   CLAIMED    │  已认领（我负责）
              │           └──────┬───────┘
              │                  │
   ┌──────────▼─────────┐        │ 开始执行
   │      HOLD          │        ▼
   │  暂停（患者外出）   │  ┌──────────────┐
   └──────────┬─────────┘  │  EXECUTING   │  执行中
              │ 恢复        └──────┬───────┘
              └────────────────────┤
                                   │
            ┌──────────────────────┼──────────────────────┐
            ▼                      ▼                      ▼
    ┌──────────────┐       ┌──────────────┐       ┌──────────────┐
    │  COMPLETED   │       │   SKIPPED    │       │   CANCELLED  │
    │   已完成      │       │  已跳过      │       │   已取消      │
    └──────────────┘       └──────────────┘       └──────────────┘
     回写 M07 EXECUTED      记录未执行原因          医嘱停止/患者离院
```

**状态说明：**

| 状态 | 中文 | 含义 | 是否终态 |
|---|---|---|---|
| `PENDING` | 待认领 | 已进队列，无人负责 | 否 |
| `CLAIMED` | 已认领 | 某护士负责，还没开始 | 否 |
| `EXECUTING` | 执行中 | 护士点了「开始执行」 | 否 |
| `HOLD` | 暂停 | 患者外出/等设备/等家属签字 | 否 |
| `COMPLETED` | 已完成 | 执行完成，回写 M07 | **是** |
| `SKIPPED` | 已跳过 | 护士主动跳过并说明原因 | **是** |
| `CANCELLED` | 已取消 | 医嘱停止/患者离院，任务失效 | **是** |

**为什么 `SKIPPED` 与 `CANCELLED` 必须分开：**

- `SKIPPED` 是**人的决定**：「患者拒绝治疗」「患者已自行服药」——计入护士工作量，需说明原因
- `CANCELLED` 是**系统决定**：医嘱被医生停了——不计入护士工作量，无需护士负责

**如果合并**，护士工作量统计会把「医嘱被停」也算进「没做完的事」，考核失真。

**为什么 `HOLD` 不是终态：**

患者在检查科室（做 OCT 去了），护士走到床边发现人不在。这时任务不能标「跳过」（回来说不定还要做），也不能标「完成」。`HOLD` 挂起，等患者回来恢复。若到班次结束仍未恢复，M08-07 交接时会提示转派给下一班。

### 3.3 任务优先级模型

优先级用**整数 score** 表示，越高越前：

```
score = 基础分(来源) + 紧急加成 + 护理级别加成 + 超时加成 − 患者聚合校正
```

**基础分（按来源）：**

| 来源 | 基础分 | 理由 |
|---|---|---|
| `ALERT` 预警处理 | 500 | 预警意味着患者状态异常，必须立即处理 |
| `EYEDROP` 滴眼 | 400 | 间隔硬约束，晚了几分钟就是药无效 |
| `ORDER` 医嘱执行 | 300 | 医生开的，有治疗目的 |
| `PREPARE` 术前准备 | 250 | 有手术时间硬约束 |
| `VITAL` 定时体征 | 200 | 常规护理 |
| `ASSESS` 护理评估 | 150 | 有 24 小时内完成的宽限期 |

**紧急加成：**

| 条件 | 加成 |
|---|---|
| 医嘱 `is_urgent = TRUE`（M07-03 加急标记） | +300 |
| 任务 `is_stat = TRUE`（临时医嘱） | +200 |
| 一级护理患者 | +100 |
| 二级护理患者 | +50 |
| 三级护理患者 | +0 |

**超时加成（关键：越超时越靠前）：**

| 超时时长 | 加成 |
|---|---|
| 未超时 | 0 |
| 超时 1~15 分钟 | +50 |
| 超时 15~30 分钟 | +100 |
| 超时 30~60 分钟 | +200 |
| 超时 > 60 分钟 | +400 |

**为什么越超时越靠前？**

直觉上会觉得「超时的就不管了先做准时的」，但真实的护理逻辑相反：一个 8:00 该给的降压药到 8:45 还没给，患者血压可能已经飙起来了。**越晚越急，不是越晚越废。**

这个设计在 M04-05 叫号系统里也是同一个道理（过号患者可回队优先插入）。

**患者聚合校正（为了减少护士走路）：**

同一患者的多个任务，在**分数差 ≤ 100** 时按患者聚合，把同患者的任务连续排列。

```
未聚合（按分数严格排序）：
  9:00  3床 滴眼  score=400
  9:02  5床 静滴  score=350
  9:05  3床 体征  score=210   ← 要再跑回 3 床
  9:10  7床 换药  score=300

聚合后：
  9:00  3床 滴眼  score=400
  9:05  3床 体征  score=210   ← 顺手做了
  9:10  7床 换药  score=300
  9:02  5床 静滴  score=350
```

**注意**：聚合校正只在**分数差 ≤ 100** 时生效。如果 3 床的体征任务 score=210，而 5 床的静滴 score=350 差 140，就不聚合——保证高优先级任务不被"顺便"逻辑压后。

### 3.4 队列的四种视图

| 视图 | 查询条件 | 用途 |
|---|---|---|
| **我的任务** | `assigned_nurse_id = 我 AND status IN (CLAIMED, EXECUTING, HOLD)` | 责任护士日常工作 |
| **待认领** | `status = PENDING AND (ward_id IN 我的病区 OR 我是个班次护士)` | 无责任制病区的公共池 |
| **本病区任务** | `ward_id = 我的病区 AND status NOT IN (COMPLETED, CANCELLED)` | 护士长视角 |
| **超时任务** | `planned_time < NOW() - 30min AND status NOT IN (COMPLETED, SKIPPED, CANCELLED)` | 质控与交接 |

**为什么是这四种，而不是「全部任务按状态筛选」：**

真实使用中，护士 90% 时间只看两个视图——「我的任务」和「待认领」。护士长只看「超时任务」。全量视图只在排查问题时用。

**把最常用的两个视图做成独立的缓存 Key**，其余两个走查询。

### 3.5 任务与病区/床位的组织

```
医院
└── 病区（Ward，如「眼科一病区」）
    ├── 护士组（护理单元）
    │   ├── 责任护士 A → 分管床位 1~8
    │   └── 责任护士 B → 分管床位 9~16
    └── 床位（Bed，1~16 床）
        └── 患者（Patient，日间手术/住院患者）
```

**责任制 vs 功能制：**

| 模式 | 特点 | 任务分配 |
|---|---|---|
| **责任制护理**（Primary Nursing） | 每个患者固定一名责任护士 | 任务自动归该患者的分管护士 |
| **功能制护理**（Functional Nursing） | 按工作内容分工（给药组、治疗组） | 任务进公共池，谁有空谁认领 |
| **混合制**（本院默认） | 白天责任制，夜间功能制 | 白天自动分配，夜间进公共池 |

**为什么本院用混合制：**

眼科日间手术患者占多数（M06 场景），白天一个责任护士分管 3~8 床，患者术后几小时就离院，责任制更连贯。但夜间值班护士少（一个病区 1~2 名），按功能制把所有人任务合成一个池更合理。

配置参数 `M08.TASK.ASSIGNMENT_MODE`：`PRIMARY` / `FUNCTIONAL` / `HYBRID`（默认 HYBRID）。

### 3.6 任务生成时机

```
┌─────────────────────────────────────────────────────────────┐
│ 谁触发 Scheduler → 何时生成 → 生成哪些任务                    │
└─────────────────────────────────────────────────────────────┘

事件驱动（立即）：
  M08-02 执行点创建 ──────────► 立即生成任务（当日的）
  M07 医嘱停止 ────────────► 立即取消关联任务
  M06 患者离院 ────────────► 立即取消该患者全部未完成任务
  患者转入/转出病区 ─────────► 任务改派

定时驱动（批量）：
  每日 06:00  ──► 生成今日全部执行点任务（避免 8:00 集中打）
  每 30 分钟  ──► 增量扫描新执行点
  每小时     ──► 超时任务标记与推送
```

**为什么每日 06:00 批量生成，而不是执行点一创建就生成：**

一个术后患者可能同时有 30 个执行点（5 天 × 6 次）。如果一创建就全进队列，护士看到的是「今天要看 30 条」，其中 25 条是别的天的，视觉噪音极大。

**只生成当天的，未来日期的不进队列。**执行点还在（M08-02 表里），到那天早上再转任务。

### 3.7 任务认领与并发

三个人同时点「认领」同一条任务，只能有一个成功。

**三级防护：**

```
第一级：Redis 分布式锁
  SET m08:task:claim:{task_id} {nurse_id} NX EX 10
  → 10 秒内其他人拿不到锁

第二级：DB 条件更新（真正的防线）
  UPDATE m08_task
     SET status = 'CLAIMED',
         assigned_nurse_id = :nurse_id,
         claimed_at = NOW()
   WHERE id = :task_id
     AND status = 'PENDING'
  → rowcount = 0 说明被别人抢先，返回冲突

第三级：DB 约束兜底
  CHECK (status <> 'CLAIMED' OR assigned_nurse_id IS NOT NULL)
```

**为什么必须有第二级：**Redis 锁只管 10 秒，任务可能被"认领超时释放"后又被人抢走。DB 条件更新是真正的原子操作。

**不用 `SELECT ... FOR UPDATE` 的原因：**`SELECT FOR UPDATE` 在护士集中认领时会串行化，20 个护士同时点，最慢的要等 19 次。条件更新无锁竞争，P95 从 80ms 降到 5ms。

### 3.8 任务转派模型

```
护士 A 请假
  │
  ▼
┌──────────────────────────────────────┐
│ 转派操作                              │
│  from_nurse_id = A                    │
│  to_nurse_id   = B                    │
│  task_ids      = [101, 102, 103]      │
│  reason        = '临时请假'            │
└──────────────────────────────────────┘
  │
  ▼
批量更新：assigned_nurse_id = B, status 保持
  │
  ▼
写 m08_task_transfer 记录（谁转给谁、何时、为什么）
  │
  ▼
推送 B：你有 3 个新任务
```

**转派的三条规则：**

1. **只能转派 `CLAIMED` / `PENDING` / `HOLD` 状态的任务**——`EXECUTING` 的不能转（正在做）
2. **转派必须写原因**（≥5 字）——用于分析排班合理性
3. **跨班次转派不限**——A 下班时把未完成任务转给 B，是每日必做动作

**跨班次转派 vs 交接班：**

| | 转派 | 交接班（M08-07） |
|---|---|---|
| 动作 | 把任务给另一人 | 把整体情况说给下一班 |
| 粒度 | 逐条任务 | 班次级 |
| 是否自动 | 否 | 是（交接时必须清点未完成任务） |

M08-07 交接时，如果还有未完成任务，系统提示「你还有 5 个任务未完成，是否转派给接班护士？」——这是转派的典型触发点。

### 3.9 任务合并规则

只有 `VITAL` / `ASSESS` / `PREPARE` 三类可以合并，`ORDER` / `EYEDROP` / `ALERT` 不可以。

**合并条件（全部满足）：**

1. 同一患者
2. 同一来源类型
3. 计划时间相差 ≤ 30 分钟
4. 均处于 `PENDING` / `CLAIMED` 状态
5. 未被分别认领

**合并后的效果：**

```
合并前：
  m08_task 101: 3床 体温 08:00
  m08_task 102: 3床 血压 08:00
  m08_task 103: 3床 脉搏 08:15

合并后：
  m08_task 101: 3床 生命体征三项（合并 101/102/103）
  m08_task 102: status = MERGED，merged_into_id = 101
  m08_task 103: status = MERGED，merged_into_id = 101
```

**为什么 `ORDER` 不能合并：**

医嘱是计费单位。合并了怎么回写 M07？一条医嘱只能被回写一次。所以医嘱执行任务必须一医嘱一任务。

**为什么 `EYEDROP` 不能合并：**

右眼和左眼是两个独立的执行点，分别要记录眼别、分别要间隔 5 分钟。合并后眼别就丢了。

### 3.10 任务与执行记录的关系

```
m08_task（任务）
  id = 101
  source_type = 'ORDER'
  source_id = 8801            ← 指向 m08_exec_point
  order_id = 94002            ← 指向 m07_order
  status = 'COMPLETED'
  ↓ 执行完成后
m08_execution（执行记录，M08-03）
  task_id = 101
  execution_no = 'EX202610200001'
  executed_by = 护士A
  executed_at = '2026-10-20 08:07:00'
```

**两者是 1:1 但职责分离：**

| | 任务 | 执行记录 |
|---|---|---|
| 谁写 | M08-01 | M08-03 |
| 可变性 | 状态可变（PENDING→COMPLETED） | 只增不改 |
| 内容 | 「要做这件事」 | 「做完了，签名了，患者反应如何」 |
| 存在时限 | 当班有效 | 永久 |
| 分区 | 不分区 | 按日分区 |

**任务完成后不删除**，只改状态。理由：护士长要看「这一班一共做了多少」，删了就查不到。

### 6.2 错误码规范

| 错误码 | 说明 | 触发场景 |
|---|---|---|
| `"0801001"` | 任务不存在 | task_id 无效或已删除 |
| `"0801002"` | 任务状态不允许此操作 | 如对已完成任务认领 |
| `"0801003"` | 任务已被他人认领 | 并发认领冲突 |
| `"0801004"` | 无权操作他人任务 | 认领了别人的任务 |
| `"0801005"` | 不在当前班次内 | 未上班时操作 |
| `"0801006"` | 跨病区操作需要授权 | 跨区认领/转派 |
| `"0801007"` | 暂停原因不合法 | 未选或不在枚举内 |
| `"0801008"` | 跳过原因不足 10 字 | 跳过时填写太短 |
| `"0801009"` | 转派目标护士不在岗 | 转派给未排班护士 |
| `"0801010"` | 转派原因不足 5 字 | 转派原因为空或太短 |
| `"0801011"` | 执行中任务不可转派 | 状态为 EXECUTING |
| `"0801012"` | 已完成任务不可转派 | 状态为 COMPLETED |
| `"0801013"` | 批量操作数量超限 | 超过 20 条 |
| `"0801014"` | 任务不能被取消 | 已完成的不可取消 |
| `"0801015"` | 任务已超时可跳过窗口 | 超时超过最大时长已自动作废 |
| `"0801016"` | 协作人不能与负责人相同 | 添加自己的 ID |
| `"0801017"` | 协作人已达上限 | 超过 5 人 |
| `"0801018"` | 该护士已在该任务协作 | 重复添加 |
| `"0801019"` | 班次已结束 | 交接班后操作 |
| `"0801020"` | 班次服务不可用 | M08-07 挂 |
| `"0801021"` | 执行计划服务不可用 | M08-02 挂 |
| `"0801022"` | 队列刷新失败 | Redis 与 DB 都失败 |
| `"0801023"` | 任务已完成不可重复确认 | 重复调 complete |
| `"0801024"` | 任务已取消不可执行 | 状态为 CANCELLED |
| `"0801025"` | 任务不属于该患者 | 患者 ID 不符 |
| `"0801026"` | 无病区权限 | 非本病区用户查询 |
| `"0801027"` | 日期跨度超过 366 天 | 历史查询 |
| `"0801028"` | 导出行数超过 50,000 行 | 导出超限 |
| `"0801029"` | 起始日期晚于结束日期 | 时间范围错误 |
| `"0801030"` | 参数值超出允许范围 | 配置更新 |
| `"0801031"` | 任务已合并至其他任务 | 操作被合并任务 |
| `"0801032"` | 合并任务不能跨患者 | 合并校验 |
| `"0801033"` | 合并时间差超过 30 分钟 | 合并校验 |
| `"0801034"` | 暂停时长超过班次 | 恢复时校验 |
| `"0801035"` | 任务未暂停不可恢复 | 状态非 HOLD |
| `"0801036"` | 全科大屏数据为空 | 无数据 |
| `"0801037"` | 任务配置项不存在 | 配置 key 不存在 |
| `"0801038"` | 配置值类型不匹配 | 如数字填了文字 |
| `"0801039"` | 队列缓存重建失败 | Redis 异常 |
| `"0801040"` | 该任务已过期需重新生成 | 跨日未处理 |

    @classmethod
    def _sort_and_group(cls, tasks: list) -> list:
        """按 score 排序并按患者聚合。

        排序规则：
        1. 先按 score 降序
        2. 同患者且分差 <= PATIENT_GROUP_THRESHOLD 的连续排列
        """
        if not tasks:
            return []

        scored = []
        for t in tasks:
            scored.append((cls._calc_score(t), t))
        scored.sort(key=lambda x: -x[0])

        result = []
        used = set()
        for i, (score_i, task_i) in enumerate(scored):
            if i in used:
                continue
            group = [(score_i, task_i)]
            used.add(i)
            pid = task_i.get("patient_id")
            for j in range(i + 1, len(scored)):
                if j in used:
                    continue
                score_j, task_j = scored[j]
                if task_j.get("patient_id") != pid:
                    continue
                if score_i - score_j > PATIENT_GROUP_THRESHOLD:
                    continue
                group.append((score_j, task_j))
                used.add(j)
            group.sort(key=lambda x: x[1]["planned_time"])
            for _, t in group:
                result.append(t)
        return result

    @classmethod
    def _calc_score(cls, task: dict) -> int:
        """计算任务优先级分数。"""
        score = SOURCE_BASE_SCORE.get(task["source_type"], 100)

        if task.get("is_urgent"):
            score += 300
        if task.get("is_stat"):
            score += 200

        score += NURSING_LEVEL_BONUS.get(task.get("nursing_level") or "", 0)

        planned = task["planned_time"]
        if isinstance(planned, str):
            planned = datetime.fromisoformat(planned)
        overdue_min = int((now_local() - planned).total_seconds() // 60)
        for threshold, bonus in OVERDUE_BONUS:
            if overdue_min >= threshold:
                score += bonus
                break

        return score

    @classmethod
    async def claim(cls, task_id: int, user: dict) -> dict:
        """认领任务。"""
        redis = await cls._redis()
        lock_key = "m08:task:claim:%d" % task_id
        acquired = await redis.set(lock_key, str(user["staff_id"]), nx=True, ex=CLAIM_LOCK_TTL)
        if not acquired:
            raise BizException("0801003", "任务已被他人认领")

        try:
            async with cls._session() as session:
                stmt = (
                    update(M08Task)
                    .where(
                        and_(
                            M08Task.id == task_id,
                            M08Task.status == "PENDING",
                            M08Task.is_deleted.is_(False),
                        )
                    )
                    .values(
                        status="CLAIMED",
                        assigned_nurse_id=user["staff_id"],
                        assigned_nurse_name=user["staff_name"],
                        claimed_at=now_local(),
                        updated_at=now_local(),
                    )
                    .returning(
                        M08Task.id,
                        M08Task.patient_id,
                        M08Task.ward_id,
                    )
                )
                result = await session.execute(stmt)
                row = result.first()
                if row is None:
                    await session.rollback()
                    existing = await cls._get_task_brief(session, task_id)
                    raise BizException(
                        "0801003",
                        "任务已被他人认领",
                        data={
                            "task_id": task_id,
                            "assigned_nurse_name": existing.get("assigned_nurse_name", ""),
                            "claimed_at": str(existing.get("claimed_at", "")),
                        },
                    )
                if row.ward_id != user["ward_id"] and not user.get("cross_ward"):
                    await session.rollback()
                    raise BizException("0801006", "跨病区操作需要授权")
                await session.commit()

            cls._invalidate_cache(user["ward_id"], user["staff_id"])
            logger.info(
                "m08 task claimed",
                extra={"task_id": task_id, "nurse_id": user["staff_id"]},
            )
            return {
                "task_id": task_id,
                "status": "CLAIMED",
                "status_text": "已认领",
                "assigned_nurse_id": user["staff_id"],
                "assigned_nurse_name": user["staff_name"],
                "claimed_at": now_local().isoformat(),
            }
        finally:
            await redis.delete(lock_key)

                task.claimed_at = now

            ward_id = task.ward_id
            await session.commit()

        cls._invalidate_cache(ward_id, to_nurse_id)
        logger.info(
            "m08 task transferred",

    async def nurse_statistics(
        cls,
        nurse_id: Optional[int],
        ward_id: Optional[int],
        date_from: date,
        date_to: date,
        user: dict,
    ) -> dict:
        """护士工作量统计。"""
        cls._check_date_span(date_from, date_to)
        async with cls._session() as session:
            stmt = (
                select(
                    M08Task.assigned_nurse_id,
                    M08Task.assigned_nurse_name,
                    M08Task.status,
                    func.count(M08Task.id).label("cnt"),
                )
                .where(
                    and_(
                        M08Task.planned_date >= date_from,
                        M08Task.planned_date <= date_to,
                        M08Task.is_deleted.is_(False),
                    )
                )
                .group_by(
                    M08Task.assigned_nurse_id,
                    M08Task.assigned_nurse_name,
                    M08Task.status,
                )
            )
            if nurse_id:
                stmt = stmt.where(M08Task.assigned_nurse_id == nurse_id)
            if ward_id:
                stmt = stmt.where(M08Task.ward_id == ward_id)
            rows = (await session.execute(stmt)).all()

        bucket = {}
        for row in rows:
            key = row.assigned_nurse_id
            if key not in bucket:
                bucket[key] = {
                    "nurse_id": key,
                    "nurse_name": row.assigned_nurse_name,
                    "total": 0,
                    "completed": 0,
                    "skipped": 0,
                    "cancelled": 0,
                    "pending": 0,
                }
            bucket[key]["total"] += row.cnt
            if row.status == "COMPLETED":
                bucket[key]["completed"] += row.cnt
            elif row.status == "SKIPPED":
                bucket[key]["skipped"] += row.cnt
            elif row.status == "CANCELLED":
                bucket[key]["cancelled"] += row.cnt
            elif row.status in ("PENDING", "CLAIMED", "EXECUTING", "HOLD"):
                bucket[key]["pending"] += row.cnt

        items = []
        for item in bucket.values():
            effective = item["completed"] + item["skipped"]
            item["completion_rate"] = (
                round(item["completed"] / effective, 4) if effective else 0.0
            )
            items.append(item)
        items.sort(key=lambda x: -x["completed"])
        return {
            "date_from": date_from.isoformat(),
            "date_to": date_to.isoformat(),
            "nurse_count": len(items),
            "items": items,
        }

### 6.7 专题：任务队列的"聚合"与"实时性"权衡

任务队列有两个互相矛盾的要求：

1. **要聚合**：护士只看一个列表，不要开五个子模块的页面
2. **要实时**：医生停药后护士最多 30 秒内看到任务消失

**方案对比：**

| 方案 | 聚合 | 实时 | 实现复杂度 | 采用的 |
|---|---|---|---|---|
| A. 每次打开页面时 JOIN 五个子模块表 | 好 | 好 | 低 | **否** |
| B. 每个子模块变更时主动推送更新 | 好 | 最好 | 高 | 否 |
| C. 任务落库 + 事件驱动更新 + 30 秒缓存 | 好 | 好 | 中 | **是** |
| D. 物化视图定时刷新 | 好 | 差（延迟 1~5 分钟） | 中 | 否 |

**为什么不用方案 A：**

看似最简单——`SELECT ... FROM m08_exec_point UNION ALL SELECT ... FROM m08_vital_task ...` 一条 SQL 就出队列。

但实测（M12-02 的技师工作台做过同类对比）：五表 JOIN + 按 score 排序，一个病区 86 条任务耗时 **420ms**；护士每 30 秒刷新一次，200 个护士并发峰值时 PostgreSQL 会 CPU 打满。

而且**排序逻辑（score 计算）无法在 SQL 中优雅实现**——需要读参数配置、计算超时分钟、按患者分组。写进 SQL 会变成一个 200 行无法维护的存储过程。

**为什么方案 C 是最优：**

```
写路径（事件驱动，保证数据正确）：
  M08-02 执行点创建 → 事件 m08.exec_point.created → 写入 m08_task
  M07 医嘱停止     → 事件 m07.order.stopped   → 更新 m08_task.status = CANCELLED
  M08-03 执行完成  → 调 API-16 complete       → 更新 m08_task.status = COMPLETED

读路径（缓存优先，保证响应快）：
  护士打开页面 → 查 Redis m08:task:my:{nurse_id}:{date}
    ├─ 命中 → 直接返回（1ms）
    └─ 未命中 → 查 m08_task（单表，走 (nurse_id, planned_date) 索引，15ms）→ 回填缓存
```

**关键设计：任务必须是自包含的。**

`m08_task` 表里存了 `task_summary`（任务摘要文本）、`bed_no`、`patient_name`、`nursing_level`——这些是从上游**冗余**过来的，为的就是队列查询只扫一张表。

**冗余的代价是同步问题**：患者在 M03 改了名字怎么办？床位从 3 床调到 5 床怎么办？

**对策：**

1. **患者姓名/床位变更极低频**（一天可能几次），通过 `mpi.patient.updated` 与 `m05.bed.changed` 事件增量更新 `m08_task`（未设计 M05 前只处理患者改名）
2. **主数据快照有明确时效**：`m08_task.patient_name` 是「生成任务时的姓名」，用于队列显示；点开详情走 M03 取最新
3. **超过 30 天的历史任务不再同步**（已经完成的不会有人改名）

**为什么缓存 30 秒而不是 5 分钟：**

M08-01 的 SLA 是「医生停药后 30 秒内护士看不到任务」。如果缓存 5 分钟，护士点「执行」时会发现医嘱已停——虽然会被拦截（错误码 `"0801024"`），但用户体验差。30 秒是用户体验与服务器负载的平衡点。

**WebSocket 的角色：**

30 秒缓存意味着**最坏情况有 30 秒延迟**。新任务插入时需要立刻告诉护士——这时用 WebSocket 主动推送：

```
m08_task 有新记录（来源为 PENDING） → Redis Pub/Sub → WebSocket 广播到病区所有在线护士
  → 护士端收到 {type: "TASK_NEW", task: {...}} → 局部插入列表（不整页刷新）
```

**为什么用 WebSocket 而不是轮询：**

轮询是「每 30 秒问一次」，200 个护士 × 每 30 秒 = 每秒 6.7 次请求，其中 99% 的响应都是「没变化」。WebSocket 只在真正变化时推送。

## 7. 缓存与异步任务设计

### 7.1 Redis 缓存

| Key 模式 | 类型 | TTL | 说明 |
|---|---|---|---|
| `m08:task:my:{nurse_id}:{date}` | String(JSON) | 30s | 护士当日任务列表 |
| `m08:task:pending:{ward_id}` | String(JSON) | 30s | 病区待认领池 |
| `m08:task:overdue:{ward_id}` | String(JSON) | 30s | 病区超时任务 |
| `m08:task:ward:{ward_id}:{date}` | String(JSON) | 30s | 病区全量任务 |
| `m08:task:bigscreen:{ward_id}` | String(JSON) | 10s | 大屏数据 |
| `m08:task:claim:{task_id}` | String | 10s | 认领分布式锁 |
| `m08:task:stat:{ward_id}:{date}` | String(JSON) | 600s | 病区任务统计 |
| `m08:task:config:{scope}:{scope_id}` | String(JSON) | 600s | 参数配置 |
| `m08:task:seq:{yyyymmdd}` | String | 172800s | 任务号序列 |
| `m08:task:ws:{ward_id}` | Pub/Sub Channel | — | WebSocket 广播频道 |

**容量估算：**

- 单病区平均 86 条任务，每条 JSON 约 500 字节 → `pending` + `overdue` + `ward` ≈ 130 KB
- 单护士任务列表约 12 条 → 6 KB
- 200 个在线护士 × 6 KB = 1.2 MB
- 50 个病区 × 130 KB = 6.5 MB
- 大屏 = 50 × 20 KB = 1 MB
- **合计约 9 MB**

**为什么队列用 String(JSON) 而不是 Hash 或 ZSet：**

队列是**整体读、整体写**的——护士打开页面就把整个列表拿走，不会单独取其中一条。用 String 存序列化后的 JSON：

- 一次 `GET` 拿到全量（1ms）
- 一次 `SET` 写完（1ms）
- 如果每条任务一个 Hash field，读 86 条要 86 次 HGET 或者一次 HMGET，反而更慢
- 如果按 score 排序用 ZSet，还需要额外存任务详情（额外 zrange 后 mget）

**什么时候该用 ZSet：**只有在需要「按分数取前 N 条」且 N 远小于总量时才值得。本场景 N=86 就是全量，不需要。

## 8. 业务规则与校验

### 8.1 任务生成规则

| 编号 | 规则 | 说明 |
|---|---|---|
| R-01 | 只生成当日的任务 | 未来日期的执行点不进队列 |
| R-02 | 已取消的医嘱不生成任务 | 查 M07 医嘱状态 |
| R-03 | 同一执行点只生成一个任务 | `m08_task.source_id` 唯一约束 |
| R-04 | 任务生成后写入 `planned_time`（来自执行点）与 `planned_date` | 用于分日查询 |
| R-05 | 患者离院后自动取消其今天及以后的全部未完成任务 | M06 事件驱动 |
| R-06 | 医嘱停止后 30 秒内取消关联任务 | M07 事件驱动 |

### 8.2 任务状态规则

| 编号 | 规则 | 说明 |
|---|---|---|
| R-07 | 终态任务（COMPLETED/SKIPPED/CANCELLED）不可再变更 | 状态机校验 |
| R-08 | `EXECUTING` 状态不可转派 | 防止执行到一半换人 |
| R-09 | `HOLD` 状态不能完成，必须先恢复 | 保护流程完整性 |
| R-10 | 完成时必须携带 `execution_no` | 保证先有执行记录 |
| R-11 | 跳过必须填原因（≥10 字） | 质控留痕 |
| R-12 | 取消仅护士长可操作 | 权限控制 |
| R-13 | 任务一旦完成，`completed_at` 与 `assigned_nurse_id` 不可修改 | 触发器保护 |

### 8.3 权限规则

| 编号 | 规则 | 说明 |
|---|---|---|
| R-14 | 只能认领本病区任务（除非有跨区权限） | 数据权限 |
| R-15 | 只能操作自己认领的任务 | 负责人校验 |
| R-16 | 护士长可转派任何人任务 | 管理权限 |
| R-17 | 转派目标必须是当班护士 | 排班校验 |
| R-18 | 协作人上限 5 人 | 防滥用 |

### 8.4 时间规则

| 编号 | 规则 | 说明 |
|---|---|---|
| R-19 | 超时阈值默认 30 分钟（可配） | `M08.TASK.OVERDUE_MINUTES` |
| R-20 | 超时 > 60 分钟标 CRITICAL 并推护士长 | 分级预警 |
| R-21 | 跨日未处理任务在 01:00 自动取消 | 队列清洁 |
| R-22 | 班次结束后 30 分钟内仍可操作（交接宽限） | `M08.TASK.SHIFT_GRACE_MINUTES` |

### 8.5 合并规则

| 编号 | 规则 | 说明 |
|---|---|---|
| R-23 | 只有 VITAL/ASSESS/PREPARE 可合并 | ORDER/EYEDROP/ALERT 不可 |
| R-24 | 合并必须同患者 | 跨患者合并无意义 |
| R-25 | 合并的计划时间差 ≤ 30 分钟 | 太远合并会导致一次采集跨两小时 |
| R-26 | 合并后被合并任务标 `MERGED` 并指向主任务 | 保留痕迹 |
| R-27 | 已认领的任务不可被合并 | 认领代表有人开始关注 |

### 9.3 数据权限

| 角色 | 数据范围 | 实现 |
|---|---|---|
| 护士 | 本病区 | `ward_id = user.ward_id` |
| 责任护士 | 本病区（可看全病区，便于协同） | `ward_id = user.ward_id` |
| 辅助护士 | 本病区 | 同上 |
| 护士长 | 本病区（DEPT 权限） | `ward_id IN (user.dept_ward_ids)` |
| 护理部 | 全院（HOSPITAL 权限） | 无过滤 |
| 跨区支援护士 | 指定病区 | `ward_id IN (user.extra_ward_ids)` |

**数据权限通过 M02 的 `apply_data_scope_to_stmt(stmt, M08Task, user, domain="DEPT")` 注入**，与全系统一致。

### 9.4 脱敏

| 字段 | 场景 | 脱敏方式 |
|---|---|---|
| 患者身份证 | 全部场景 | 不显示（M08 任务不需要） |
| 患者手机号 | 全部场景 | 不显示 |
| 患者姓名 | 大屏（P06） | 只显示姓 + 名末字，如「张*伟」 |
| 患者姓名 | 手机端（M20） | 完整显示（登录态） |
| 诊断名称 | 任务摘要 | 不显示（任务摘要只显示操作内容） |

**为什么大屏要脱敏患者姓名：**

走廊大屏是公共区域，任何人路过都能看到。显示「3床 张伟 男45 青光眼」等于把患者隐私公开。只显示床号+姓+名末字，护士需要点开才知道是谁。

### 9.5 安全措施

| 措施 | 说明 |
|---|---|
| 所有写操作记审计 | 认领、转派、暂停、跳过、取消、完成均写 `m02:audit` |
| 任务完成不可篡改 | DB 触发器保护 `completed_at`、`assigned_nurse_id` |
| 转派完整留痕 | `m08_task_transfer` 只增不改 |
| 认领竞态防护 | Redis 锁 + DB 条件更新 + DB 约束 |
| 频率限制 | 单护士认领 ≤ 200 次/分钟 |
| WebSocket 鉴权 | 连接时校验 token，只推送病区内数据 |
| 大屏脱敏 | 见 9.4 |
| 导出审计 | 导出任务数据写审计日志 |
| 跨病区访问二次确认 | 需在界面勾选「确认跨病区操作」 |
