**设计说明：**

1. **`m08_exec_plan` 与 `m07_order` 是 1:1 但不建外键**。理由：M07 可能有历史数据、可能跨库部署；外键会让 M08 的迁移依赖 M07 的迁移顺序。一致性由「医嘱停止事件驱动 + 每日对账」保证。

2. **`m08_exec_point` 是 M08 全模块的原子单位**。M08-01 的任务来源 `source_id` 直接指向 `exec_point.id`；M08-03/M08-06 的执行记录必须记录 `point_id`。

3. **`m08_plan_log` 只增不改**，用触发器强制。它是「为什么今天多了 3 个点、少了 2 个点」的唯一答案。

4. **`m08_ward_med_time` 独立成表而不放在 `m08_exec_plan`**。病区给药时间是病区级配置（12 个病区 12 条），若冗余在计划上，改一次配置要更新上万条计划。

5. **`m08_prn_order` 独立成表**。PRN（必要时）医嘱不展开执行点，但需要「今天已用几次 / 最多几次」的计数，无法塞进 `m08_exec_plan`（那里存的是展开参数）。

**状态机：**

```
          医嘱开具 → ACTIVE
                        │
        ┌───────────────┼────────────────┐
        │               │                │
   SUPENDED         STOPPED          COMPLETED
   （临时停用）      （医嘱停止）        （疗程走完）
        │
     恢复→ACTIVE

   展开失败 → FAILED
   医嘱作废 → CANCELLED
```

**设计要点：**

1. **为什么 `uk_m08_plan_order_active` 只约束 ACTIVE 与 SUSPENDED。**
   一条医嘱可以「展开 → 停止 → 又重新开具」，这时会有多条历史计划。但**同时只能有一个活跃或挂起计划**。部分唯一索引精确表达这个语义。

2. **为什么 `expanded_eye_sides` 存 JSONB 而不存两列。**
   眼别有 4 种（OD/OS/OU/NA），展开后是 0、1 或 2 个元素。用两列 `eye1`/`eye2` 会有大量 NULL；用 JSON 数组语义清晰，且能用 `ck_m08_plan_eyes_count` 校验数量与 `eye_side` 的对应关系。

3. **`ck_m08_plan_eyes_count` 是整个 M08 最重要的数据完整性约束之一。**
   「双眼医嘱必须拆 2 个点」是眼科护理的核心规则。这个约束在 DB 层强制，任何代码路径、任何并发场景都无法写入「OU 但只展开 1 只眼」的脏数据。

4. **为什么保留 `frequency_name`/`route_name`/`item_name` 快照。**
   M01 主数据可能改名（「左氧氟沙星滴眼液」→「左氧氟沙星滴眼液 0.5%」）。计划是历史记录，必须记录「当时叫这个名字」。这样才能在纠纷追溯时说明「当时护士看到的药名就是这个」。

5. **`degraded_reason` 的作用。**
   当 `md_frequency` 不可用而降级用内置表时，必须在计划上留下痕迹。质量分析时可以统计「本月有多少计划是降级展开的」，判断依赖稳定性。

6. **为什么用乐观锁 `version` 而不是悲观锁。**
   计划重算是低频操作（日均几十次），冲突概率极低。悲观锁会让展开与重算互相阻塞。用 `version` 乐观锁 + Redis 短锁（30s）双保险，冲突时返回 `"0802030"` 让调用方重试。

**量级估算：**

| 项目 | 数值 | 计算依据 |
|---|---|---|
| 日均新建计划 | 400 | 每医嘱一个 |
| 年新建计划 | 146,000 | 400 × 365 |
| 单行长度 | 约 900 字节 | 含 JSONB 约 40 字节 |
| 年数据量 | 约 131 MB | 146,000 × 900 |
| 15 年累计 | 约 2,190,000 行 | 约 2.0 GB（含索引约 3.2 GB） |

**状态机：**

```
      PLANNED（已排计划，未入队）
          │ M08-01 当日生成任务
          ▼
      SCHEDULED（已入队）
          │
   ┌──────┼──────────┬──────────────┐
   ▼      ▼          ▼              ▼
EXECUTED SKIPPED  CANCELLED     SUSPENDED
 终态     终态      终态           │ 恢复
                                   ▼
                               SCHEDULED
```

**设计要点：**

1. **`uk_m08_point_slot (plan_id, planned_time, eye_side)` 是防重复展开的最后防线。**
   重算时若算法出错（比如日期序列多算了一天），会产生同时间同眼别的重复点，护士就会看到两条一样的任务，做了两次。这个唯一索引在 DB 层兜底。

2. **`planned_time` 与 `planned_time_snapshot` 分开的原因（同 M08-01）。**
   重算会改 `planned_time`（比如病区给药时间从 08:00 调到 07:30）。但历史记录里「原本该 08:00 做」这个事实不能被篡改——纠纷追溯时要说清。

3. **为什么 `eye_side` 在表约束里排除了 `OU`。**
   `OU` 是医嘱层的语义，在执行点层已被展开为两条独立序列。若允许执行点存 `OU`，就会在下游造成「一条记录代表两只眼」的歧义——护士签一次名就说不清滴了哪只。

4. **`execution_no` 唯一约束的作用。**
   一条执行记录只能对应一个执行点。若 M08-03/M08-06 因为重试把同一个 `execution_no` 写到两个点上，唯一索引直接拒绝。

5. **为什么冗余 `order_id`/`patient_id`/`ward_id`。**
   执行点表要承担三类高频查询：按病区查当日待执行点（M08-01 生成任务）、按患者查执行历史（M08-05 护理记录）、按医嘱查执行情况（M08-03）。若每次都 JOIN 计划表，56 条点的查询要 3 次 JOIN。冗余后单表扫描。

6. **不建分区。** 15 年约 3,900 万行（146,000 计划 × 平均 26 点）。这是全模块最大的表。但：
   - 同时保留期只有 15 年
   - 按 `planned_date` 分区会破坏 `uk_m08_point_slot`（需含分区键），导致「跨年的同一执行点可重复」——破坏幂等
   - 实际查询都带日期范围，索引 `idx_m08_point_date` 已足够
   - 若未来数据量超预期，可改为按 `planned_date` RANGE 分区，此时 `uk_m08_point_slot` 需加 `planned_date`，语义退化为「同年唯一」，可接受（同一计划的执行点不会跨年重复时间）

**量级估算：**

| 项目 | 数值 | 计算依据 |
|---|---|---|
| 日均执行点 | 400 计划 × 26 点（平均） | 平均每计划 26 点（QD~QID 混合） |
| 日均执行点 | 10,400 | — |
| 年执行点 | 3,796,000 | — |
| 单行长度 | 约 320 字节 | — |
| 年数据量 | 约 1.2 GB | — |
| 15 年累计 | 约 5,694 万行 / 18 GB（含索引约 26 GB） | — |

> ⚠️ **这是 M08 全模块最大的表**。收缩建议：保留期从 15 年调整为 5 年（护理执行记录法规要求保存 ≥5 年），可降至 1,900 万行 / 8.6 GB。若需长期保留，按 `planned_date` 年度 RANGE 分区归档。

```sql
                         'STOP', 'CANCEL', 'COMPLETE', 'FAILED'));

ALTER TABLE m08_plan_log
  ADD CONSTRAINT ck_m08_plan_log_source
  CHECK (change_source IN ('MANUAL', 'M07_EVENT', 'SYSTEM', 'CONFIG'));

-- 原因不能为空且至少 2 字
ALTER TABLE m08_plan_log
  ADD CONSTRAINT ck_m08_plan_log_reason
  CHECK (char_length(btrim(reason)) >= 2);

-- 变更计数不能为负

  ADD CONSTRAINT ck_m08_plan_log_counts
  CHECK (added_points >= 0 AND cancelled_points >= 0 AND modified_points >= 0);

RETURNS TRIGGER AS $$
BEGIN
  RAISE EXCEPTION 'm08_plan_log 为只增表，禁止 UPDATE/DELETE';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m08_plan_log_update
  BEFORE UPDATE ON m08_plan_log
  FOR EACH ROW EXECUTE FUNCTION fn_m08_plan_log_readonly();

  BEFORE DELETE ON m08_plan_log

COMMENT ON COLUMN m08_plan_log.change_source IS 'MANUAL 人工 / M07_EVENT 医嘱事件 / SYSTEM 系统任务 / CONFIG 配置变更';
```

**设计要点：**

1. **为什么必须只增不改。**
   变更日志的用途是回答「10-27 11:15 计划为什么从 56 点变成 28 点」。若日志可改，这个答案就可被篡改。触发器让任何 UPDATE/DELETE 直接报错。

2. **`point_detail` 存 JSONB 而不是关联表。**
   变更明细是「一次操作的快照」，不需要被单独查询或 JOIN。存 JSON 后一次写入、一次读取，查明细时看一个字段就够。若用关联表 `m08_plan_log_point`，15 年会产生上亿行，且永远只被整体读取。

3. **为什么同时存 `old_params` 与 `new_params`。**
   重算后计划上的 `frequency_code` 已经变成新值。若只记录「变了 28 个点」，追溯时看不到「从 QID 变成 TID」这个原因。存两份快照就能完全还原。

4. **`change_source` 四种来源的实际用途。**
   - `M07_EVENT`：医生改医嘱导致（正常业务）
   - `MANUAL`：护士长手工重算（需关注频次）
   - `SYSTEM`：每日定时全量核对（正常）
   - `CONFIG`：给药时间配置变更导致（批量影响，需评估）

   统计分析时，若 `MANUAL` 占比高，说明数据质量问题多。

| 年日志 | 116,800 |
| 单行长度 | 约 600 字节（含 JSONB） |
| 年数据量 | 约 70 MB |
| 保留期 | 5 年 |

**分区：** 保留 5 年约 58 万行 / 350 MB，暂不分区。若日志量增长至每月超 20 万行，可按 `changed_at` 月度 RANGE 分区。

**设计要点：**

1. **为什么用 TIME 类型而不是 VARCHAR。**
   TIME 类型可以直接做 `noon_time - morning_time >= INTERVAL '2 hours'` 的运算与约束校验。VARCHAR 需要应用层解析，且 DB 层无法强制格式。

2. **`is_default` 的作用。**
   病区同步任务（M01-01 → M08）会自动为新病区创建默认配置。`is_default = TRUE` 时，质量监控可以统计「还有多少病区在用默认时点」，推动实施人员按科室实际定制。

3. **为什么严格间隔频次不受此配置影响。**
   `Q8H`（每 8 小时）是医学要求（维持血药浓度），不能因为病区早上 7:30 查房就改成 7:30-15:30-23:30。这个规则在 M08-02 服务的 `_resolve_times` 里通过 `STRICT_INTERVAL_CODES` 判断。

4. **约束为什么直接在 DB 层写死 2 小时间隔。**
   这不是业务可调参数——2 小时的间隔是「早中晚三次给药的最小时长」的临床常识。若做成参数，容易被误配为 0 导致一天给药全部挤在 8:00。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 病区数 | 12 |
| 单行长度 | 约 200 字节 |
| 总量 | 约 2.4 KB |

**分区：** 不分区。

```sql
  ADD CONSTRAINT ck_m08_prn_limit

-- 已用次数不能为负

  ADD CONSTRAINT ck_m08_prn_used
  CHECK (used_times_today >= 0);

  ADD CONSTRAINT ck_m08_prn_usage_type
  CHECK (jsonb_typeof(usage_log) = 'array');
```

**状态机：**

```
   PRN 医嘱开具 → ACTIVE
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
   STOPPED      EXPIRED      （达上限暂不可用，
  （医嘱停止）  （疗程到期）     次日重置恢复）
```

**设计要点：**

1. **为什么 PRN 要单独建表，而不是在 `m08_exec_plan` 里加个 `is_prn` 标记。**
   PRN 需要的字段与计划完全不同：
   - 需要 `used_times_today` 这样的**可变计数**
   - 需要 `usage_log` 记录每次使用
   - 需要 `today_date` 做跨日重置

   这些都是「状态」而非「展开参数」，混在计划表里会让计划表既存配置又存运行时状态。

2. **为什么 `used_times_today` 要在 DB 里存，而不是实时 COUNT。**
   PRN 的「今日已用 3 次，还能用 2 次」必须能**原子地**判断与递增。若用 COUNT，两个护士同时点「使用」会都读到 2 次，都判定可用，结果用了 4 次。存计数器 + `UPDATE ... SET used_times_today = used_times_today + 1 WHERE used_times_today < max_times_per_day` 才是原子的。

3. **`today_date` 字段的存在意义。**
   跨日重置不能简单用「定时任务清零」——如果定时任务失败，昨天的计数会带到今天。保存 `today_date` 后，读取时判断 `today_date != today` 就把计数视为 0 并触发重置，不依赖定时任务。

4. **`usage_log` 只保留最近 20 次。**
   完整的使用记录由 M08-06 的用药执行记录承担，这里只是「快速看一眼最近用了什么」的便利字段。20 次足够（一般 PRN 医嘱疗程 3~7 天，每日最多 3~4 次）。

**量级估算：**

| 项目 | 数值 |
|---|---|
| PRN 医嘱数 | 约占总数 3%，约 12/日 |
| 年 PRN 记录 | 4,380 |
| 单行长度 | 约 700 字节（含 usage_log） |
| 年数据量 | 约 3 MB |

**分区：** 不分区。
