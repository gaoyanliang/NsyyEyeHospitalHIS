### 1.2 标准字段

所有业务表包含以下标准字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 主键 |
| `created_at` | `TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP` | 创建时间 |
| `created_by` | `BIGINT` | 创建人（职工 ID） |
| `updated_at` | `TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP` | 更新时间 |
| `updated_by` | `BIGINT` | 更新人 |
| `is_deleted` | `BOOLEAN NOT NULL DEFAULT FALSE` | 软删除标记 |
| `version` | `INTEGER NOT NULL DEFAULT 1` | 乐观锁版本 |

**例外（三类表不加全量标准字段）：**

| 类型 | 表 | 例外内容 |
|---|---|---|
| 只增日志表 | `m08_task_transfer` / `m08_plan_log` / `m08_execution_log` / `m08_vital_log` / `m08_nursing_record_log` | **不加** `updated_at` / `updated_by` / `is_deleted`（有触发器禁止 UPDATE/DELETE） |
| 主数据型表 | `m08_vital_threshold` / `m08_assess_template` / `m08_record_template` / `m08_ward_med_time` / 七个 `*_config` | 保留标准字段，但 `created_by`/`updated_by` 必填 |
| 配置表 | `m08_task_config` / `m08_med_config` | 唯一索引必须 `WHERE is_deleted = FALSE` |

### 1.3 枚举的存储方式

**统一用 `VARCHAR(32)` + `CHECK` 约束**，不用 PostgreSQL 原生 `ENUM` 类型。

**三条理由：**

1. **`ALTER TYPE ... ADD VALUE` 不能在事务中执行。** Alembic 迁移包在事务里，加枚举值会失败，必须拆成独立的手工迁移步骤，与 CI 流程冲突。
2. **删改枚举值要重建类型。** 如果某枚举值用错了（例如把 `PENDING_APPROVE` 误写成 `PENDING_APPROVAL`），`DROP TYPE` 在有依赖列时直接失败，必须建新类型、改列、删旧类型，三步且有锁表风险。
3. **应用层已有 `Literal[...]` 类型保护。** Pydantic 的 `Literal` 在请求入口就拦住了非法值，DB 层 `CHECK` 只作最后防线，不需要原生枚举的严格性。

### 1.4 时间语义

M08 涉及三类时间，必须区分清楚：

| 类型 | 示例字段 | 含义 |
|---|---|---|
| **计划时间** | `planned_time` / `planned_date` | 应该在什么时候做 |
| **实况时间** | `actual_time` / `executed_at` / `signed_at` | 实际什么时候做的 |
| **系统时间** | `created_at` / `updated_at` | 数据什么时候写入的 |

**铁律：** 计划时间与实况时间**永不互相覆盖**；系统时间不得参与业务判断。

**三个关键派生关系：**

```
超时时长 = actual_time - planned_time      （未执行时用 NOW() - planned_time）
签名间隔 = receive_signed_at - handover_signed_at
记录日期 = DATE(record_time)              （冗余存 record_date 供索引）
```

### 1.5 金额与数量精度

| 用途 | 类型 | 说明 |
|---|---|---|
| 金额、单价 | `NUMERIC(14,4)` | 药品单价需 4 位小数（如 0.0250 元/片） |
| 结算金额 | `NUMERIC(12,2)` | 行级先舍入再汇总 |
| 库存数量 | `NUMERIC(12,4)` | 支持拆零 |
| 体征数值 | `NUMERIC(10,2)` | 体温 36.50、眼压 18.00 |
| 量表得分 | `NUMERIC(8,2)` | Morse 总分 0~125 |
| 比率 | `NUMERIC(5,4)` | 0.9850 = 98.50% |

**行级先舍入的理由：** 30 行明细若先累加再舍入，与逐行舍入再累加可能差几毛钱。护理侧金额很少，但护理费/治疗费的执行确认涉及计费，必须遵守。

### 1.6 软删除与部分唯一索引

M08 全部业务表使用 `is_deleted` 软删除。**软删除的唯一索引必须带 `WHERE is_deleted = FALSE`**，否则删掉一条后无法重建同键记录。

```sql
-- 正确
CREATE UNIQUE INDEX uk_m08_task_no ON m08_task (task_no) WHERE is_deleted = FALSE;

-- 错误：软删除后无法复用同一 task_no
CREATE UNIQUE INDEX uk_m08_task_no ON m08_task (task_no);
```

**唯一例外：幂等键索引不带 `is_deleted` 条件。**

```sql
-- 幂等键：全表唯一，含软删除行
CREATE UNIQUE INDEX uk_m08_task_source ON m08_task (source_type, source_id);
```

**理由：** 幂等键的目的是「同一业务来源只能生成一次」。若加了 `is_deleted = FALSE`，软删除后可以再生成一个同来源任务，幂等就失效了。需要重建时应**恢复原记录**而非新建。

### 1.7 可空列参与唯一索引必须 `COALESCE`

PostgreSQL 的唯一索引认为 **NULL 互不相等**。以下写法在 PostgreSQL 中不会拒绝重复插入：

```sql
-- 危险：scope_id 为 NULL 时可以插入任意多条 (param_code, scope) 相同的记录
CREATE UNIQUE INDEX uk ON m08_med_config (param_code, scope, scope_id);
```

**正确写法：**

```sql
CREATE UNIQUE INDEX uk_m08_med_config
  ON m08_med_config (param_code, scope, COALESCE(scope_id, 0))
  WHERE is_deleted = FALSE;
```

**为什么不用 `NULLS NOT DISTINCT`：** 该特性 PostgreSQL 15+ 才支持，本项目部分环境仍为 14。`0` 不是合法的病区/科室 ID，无冲突风险。

**M08 涉及此规则的表（7 张）：**

`m08_task_config` / `m08_vital_threshold` / `m08_med_config` / `m08_ward_med_time`（单列唯一无需 COALESCE）/ `m08_handover_item` 的 `COALESCE(bed_no,'')` 与 `COALESCE(seq,0)` / `m08_assess_item`（无）/ `m08_record_template`（无）

### 1.8 触发器命名与用途

| 触发器名 | 作用表 | 函数 | 行为 |
|---|---|---|---|
| `trg_m08_task_transfer_update` / `_delete` | `m08_task_transfer` | `fn_m08_task_transfer_readonly()` | 抛异常禁止 UPDATE/DELETE |
| `trg_m08_plan_log_update` / `_delete` | `m08_plan_log` | `fn_m08_plan_log_readonly()` | 同上 |
| `trg_m08_exec_log_update` / `_delete` | `m08_execution_log` | `fn_m08_execution_log_readonly()` | 同上 |
| `trg_m08_vital_log_update` / `_delete` | `m08_vital_log` | `fn_m08_vital_log_readonly()` | 同上 |
| `trg_m08_record_log_update` / `_delete` | `m08_nursing_record_log` | `fn_m08_record_log_readonly()` | 同上 |
| `trg_m08_exec_time_immutable` | `m08_execution` | `fn_m08_exec_time_immutable()` | 已签名记录的 `executed_at` 不可改 |
| `trg_m08_exec_nurse_sod` | `m08_execution_nurse` | `fn_m08_exec_nurse_sod()` | 执行人 = 核对人时抛异常 |

**触发器而非应用层校验的理由：** 应用层校验可能被绕过（后台脚本、DBA 直接操作、未来新增的写入路径）。只增表与 SoD 是**证据链完整性**的底线，必须在数据库层强制。

### 1.9 中文检索：`pg_trgm` + GIN

| 表 | 索引 | 用途 |
|---|---|---|
| `m08_task` | `idx_m08_task_summary_trgm` | 任务摘要关键词 |
| `m08_task` | `idx_m08_task_name_trgm` | 患者姓名 |
| `m08_vital_sign` | `idx_m08_vital_name_trgm` | 患者姓名 |
| `m08_plan` | `idx_m08_plan_name_trgm` / `idx_m08_plan_item_trgm` | 患者姓名 / 药品项目名 |
| `m08_nursing_record` | `idx_m08_record_name_trgm` | 患者姓名 |
| `m08_nursing_record_section` | `idx_m08_section_text_trgm` | **护理记录正文关键词** |
| `m08_handover` | `idx_m08_handover_name_trgm` | 患者姓名 |

**为什么用 `pg_trgm` 不用 `tsvector`：** 中文分词需要 `zhparser` 或 `pg_jieba` 扩展，多数医院服务器不预装；`pg_trgm` 只需 `CREATE EXTENSION pg_trgm`，`LIKE '%关键词%'` 即可命中。

**`idx_m08_section_text_trgm` 是唯一「写代价明显高于读收益」的索引：** 每次插入约 3ms，占约 2.1GB 存储。保留理由是「按关键词抽查」是质控核心手段（如找出所有写了「已告知」的记录）。若不做关键词检索，可用参数 `M08.RECORD.ENABLE_TRGM_SEARCH=false` 关掉。

### 1.10 不建外键

M08 全部 42 张表**不建数据库外键**。

**三条理由：**

1. **性能。** `m08_exec_point` 年 380 万行，每次写入都触发外键检查；而跨子模块的 JOIN 本就不多（执行点 → 计划表已冗余了关键字段）。
2. **解耦与归档。** 归档老数据时若有外键，必须先删子表再删主表，且无法单独归档一个子模块。
3. **一致性由应用层与对账保证。** 每日 03:00 对账任务校验跨表引用完整性。

**代价与补救：** 可能出现孤儿行（引用了一个已删除的 ID）。补救：**冗余关键展示字段**（如 `m08_task` 冗余 `patient_name`/`bed_no`/`task_summary`），使展示不依赖 JOIN，同时孤儿行仍可读。

|---|---|---|---|---|
| `m08_exec_point` | M08-02 | M08-01、M08-03、M08-06 | `point_id` | **M08 的连接件** |
| `m08_execution` | M08-03 | M08-05、M07 回写 | `execution_no` | 执行事实唯一来源 |
| `m08_vital_sign` | M08-04 | M08-05、M08-07、M06-06 | `patient_id` + `vital_time` | 体征唯一来源 |
| `m08_medication_admin` | M08-06 | M08-05、M08-07、M06-06 | `admin_no` | 给药事实唯一来源 |
| `m08_nursing_record` | M08-05 | M06-06（D-14） | `admission_id` | 护理记录唯一来源 |

**共享原则：** 一张表的**定义方**拥有它的写入权；消费方**只读**。跨子模块修改必须通过定义方的内部契约接口，不得直接 UPDATE。

### 3.3 关键关联链路

**链路一：医嘱 → 执行确认（M07 → M08 → M07）**

```
m07_order.id
  → m08_exec_plan.order_id
  → m08_exec_point.plan_id
  → m08_task.point_id
  → m08_execution.point_id
  → m08_execution.execution_no
  → 回写 m07_order.status = COMPLETED
```

**链路二：滴眼全链路（M07 → M08-02 → M08-01 → M08-06 → M07）**

```
m07_order (eye_side='OU', freq='QID', days=3)
  → m08_exec_plan (expanded_eye_sides=['OD','OS'], point_count=24)
  → m08_exec_point ×24 (12 OD + 12 OS)
  → m08_task ×24 (当日 4 个)
  → m08_medication_admin + m08_eye_drop
  → m08_eye_drop_open (开封记录，1 瓶对应多次给药)
  → 回写 M07
```

**链路三：护理记录引用（M08-04/03/06 → M08-05 → M06-06）**

```
m08_vital_sign (本班体征)
m08_execution  (本班执行)
m08_medication_admin (本班给药)
  → m08_nursing_record.auto_summary JSONB（渲染快照）
  → m08_nursing_record_section（渲染后的正文，签名覆盖）
  → M06-06 D-14: SELECT COUNT(*) WHERE admission_id=? AND status='SIGNED'
```

**链路四：交接与任务转移（M08-01/07 → M08-01）**

```
m08_nurse_schedule (班次) + m08_schedule_member (人员)
  → m08_shift_attendance (签到)
  → m08_handover (交接单, 六区块)
  → m08_handover_item (明细)
  → 双签完成后: UPDATE m08_task SET assigned_nurse_id = 接班护士
                WHERE ward_id=? AND status IN ('PENDING','CLAIMED')
```

### 3.4 冗余字段清单（为减少 JOIN 而设）

| 表 | 冗余字段 | 来源 | 刷新时机 | 风险 |
|---|---|---|---|---|
| `m08_task` | `patient_name` / `bed_no` / `nursing_level` / `task_summary` | M03-01 / M08-07 | 任务生成时快照 | 患者改名不同步（极低频，可接受） |

## 4. 索引策略

### 4.1 索引命名规范

| 类型 | 前缀 | 示例 |
|---|---|---|
| 唯一索引 | `uk_` | `uk_m08_task_source` |
| 普通索引 | `idx_` | `idx_m08_task_pending` |
| 主键约束 | 自动 | `m08_task_pkey` |
| 约束 | `ck_` | `ck_m08_task_status` |
| 触发器 | `trg_` | `trg_m08_task_transfer_update` |
| 函数 | `fn_` | `fn_m08_task_transfer_readonly()` |

### 4.2 五类关键索引设计

**类型一：部分索引（Partial Index）——M08 的主力优化。**

主表行数大但「活跃子集」极小，部分索引把索引体积降到 0.1% 以下：

| 索引 | 条件 | 活跃行数 | 收益 |
|---|---|---|---|
| `idx_m08_task_pending` | `WHERE status='PENDING' AND is_deleted=FALSE` | 约 400 | 扫 1 页 vs 扫 400ms |
| `idx_m08_task_overdue` | `WHERE is_overdue=TRUE AND status IN (...)` | 约 20 | 同上 |
| `idx_m08_point_pending` | `WHERE status IN ('PLANNED','SCHEDULED')` | 约 3,800 | 同上 |
| `idx_m08_vital_alert_open` | `WHERE status IN ('PENDING','ACKNOWLEDGED')` | 约 5 | 同上 |
| `idx_m08_assess_due` | `WHERE status='SIGNED' AND next_due_at IS NOT NULL` | 约 40 | 同上 |
| `idx_m08_record_unsigned` | `WHERE status='DRAFT'` | 约 30 | 同上 |
| `idx_m08_med_override_active` | `WHERE status IN ('PENDING','APPROVED')` | 约 3 | 同上 |
| `idx_m08_handover_pending` | `WHERE status IN ('DRAFT','SUBMITTED')` | 约 8 | 同上 |

**类型二：复合索引的列序。**

原则：**等值条件在前，范围/排序条件在后。**

```sql
-- 正确：(ward_id 等值, priority_score 排序, planned_time 排序)
CREATE INDEX idx_m08_task_pending
  ON m08_task (ward_id, priority_score DESC, planned_time)
  WHERE status = 'PENDING' AND is_deleted = FALSE;

-- 错误：(priority_score 在前无法用 ward_id 过滤)
CREATE INDEX idx_bad ON m08_task (priority_score DESC, ward_id);
```

**类型三：生成列（Generated Column）。**

| 表 | 生成列 | 表达式 |
|---|---|---|
| `m08_task` | 无 | `priority_score` 是普通列（超时加成查询时动态加） |
| `m08_exec_point` | 无 | — |
| `m08_med_stock_snap` | `qty_available` | `qty_on_hand - qty_locked` STORED |

**为什么 `priority_score` 不做成生成列：** 超时加成随时间漂移（每 5 分钟可能变），生成列只在写入时计算一次，无法反映动态变化。做法是**落库基础分 + 查询时动态加超时加分**。

**类型四：GIN 索引（`pg_trgm`）。**

见 §1.9。

**类型五：唯一部分索引（幂等与唯一性的最后防线）。**

| 索引 | 条件 | 防什么 |
|---|---|---|
| `uk_m08_task_source` | **无条件** | 同一执行点重复生成任务 |
| `uk_m08_point_slot` | `(plan_id, planned_time, eye_side)` | 同一计划同一时刻同一眼重复展开 |
| `uk_m08_med_point_active` | `WHERE status <> 'VOID'` | 同一执行点两条有效给药 |
| `uk_m08_open_batch_patient` | `WHERE status='ACTIVE'` | 同一批次给两个患者开封 |
| `uk_m08_handover_shift` | `WHERE status <> 'VOIDED'` | 同班次两份有效交接单 |
| `uk_m08_record_signed` | `WHERE status='SIGNED'` | 同患者同班次同类型两条签名记录 |
| `uk_m08_period_ward_start` | `WHERE is_deleted=FALSE` | 同病区同月开始日两个周期 |

### 4.3 不用索引的场景

| 场景 | 处理 | 理由 |
|---|---|---|
| `m08_vital_sign.values_json` 内的单项查询 | 改用 `m08_vital_alert` 表 | JSONB 内字段建 GIN 索引体积大、选择性差 |
| 全表统计（`COUNT(*)`） | 预聚合表 | 146 万行全扫约 300ms |
| 低选择性布尔列（`is_deleted`） | 部分索引兼任 | 单独建索引无意义 |
| 排序字段（`priority_score`） | 复合索引后列 | 单列排序索引无法配合过滤 |

## 5. 分区与归档

### 5.1 分区表（仅 2 张）

| 表 | 分区键 | 方式 | 预建 | 理由 |
|---|---|---|---|---|
| `m08_vital_log` | `operated_at` | 月 RANGE | 36 个月 | 年 5,475 行，但 3 年后整月丢弃 |
| `m08_nursing_record_log` | `operated_at` | 月 RANGE | 36 个月 | 年 438,000 行，日志增长快 |

**分区表建表模板：**

```sql
CREATE TABLE m08_vital_log (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY,
    operated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    vital_id    BIGINT NOT NULL,
    action      VARCHAR(32) NOT NULL,
    operator_id BIGINT NOT NULL,
    detail      JSONB,
    PRIMARY KEY (id, operated_at)
) PARTITION BY RANGE (operated_at);
```

**注意：** 分区表主键**必须包含分区键**（`PRIMARY KEY (id, operated_at)`），否则无法建分区。

### 5.2 其余 40 张为什么不分区

**核心原因：分区会让跨年唯一约束退化。**

以 `m08_exec_point` 为例：

```sql
-- 不分区时：全局唯一，同一计划同一时刻同一眼只能一个点
CREATE UNIQUE INDEX uk_m08_point_slot ON m08_exec_point (plan_id, planned_time, eye_side);

-- 若按 planned_date 每年分区：唯一索引必须包含分区键
CREATE UNIQUE INDEX uk_m08_point_slot ON m08_exec_point (plan_id, planned_time, eye_side, planned_date);
-- 结果：(plan_id=1, 2026-10-27 08:00, 'OD', 2026) 与 (plan_id=1, 2026-10-27 08:00, 'OD', 2027)
-- 可以在不同分区共存 → 跨年重复展开
```

`uk_m08_task_source`（幂等）、`uk_m08_med_point_active`（一执行点一给药）、`uk_m08_record_signed`（一班次一记录）都有同样问题。

**容量验证：** 最大表 `m08_exec_point` 年 380 万行，15 年 5,694 万行，含索引约 26 GB——PostgreSQL 单表完全可承受（同类项目 5,000 万行单表查询仍在 10ms 级）。

**建议：** 将 `m08_exec_point` 保留期从 15 年降为 **5 年**（护理执行记录法规要求 ≥5 年），可降至 1,900 万行 / 8.6 GB。

### 5.3 归档四步流程

**铁律：归档表行数必须与被删行数完全一致，才可删主表。**

```sql
-- 第 1 步：导出
COPY (SELECT * FROM m08_nursing_record WHERE created_at < '2020-01-01')
  TO '/archive/m08_nursing_record_2011.csv' WITH (FORMAT csv, HEADER true);

-- 第 2 步：校验行数
SELECT COUNT(*) FROM m08_nursing_record WHERE created_at < '2020-01-01';
-- 必须等于 CSV 行数 - 1（表头）

-- 第 3 步：归档前验签（护理记录特有）
SELECT COUNT(*) FROM m08_nursing_record r
  WHERE r.created_at < '2020-01-01' AND r.status = 'SIGNED'
  -- 对每条调用 verify-signature，不一致则中止归档

-- 第 4 步：先删子表，再删主表
DELETE FROM m08_nursing_record_section WHERE record_id IN (...);
DELETE FROM m08_nursing_record WHERE created_at < '2020-01-01';
```

### 6.5 只增表触发器（完整代码）

```sql
CREATE OR REPLACE FUNCTION fn_m08_nursing_record_log_readonly()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'm08_nursing_record_log 为只增表，禁止 UPDATE/DELETE';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m08_record_log_update
    BEFORE UPDATE ON m08_nursing_record_log
    FOR EACH ROW EXECUTE FUNCTION fn_m08_nursing_record_log_readonly();

CREATE TRIGGER trg_m08_record_log_delete
    BEFORE DELETE ON m08_nursing_record_log
    FOR EACH ROW EXECUTE FUNCTION fn_m08_nursing_record_log_readonly();
```

**相同的函数为以下 5 张表各建一份：** `m08_task_transfer` / `m08_plan_log` / `m08_execution_log` / `m08_vital_log` / `m08_handover_log`（M08-01 定义）。

**为什么函数名带表名而不是一个通用函数：** 报错信息要指明是哪张表，一个通用函数只能抛泛化提示，运维排查困难。

### 6.6 执行时间不可变触发器

```sql
CREATE OR REPLACE FUNCTION fn_m08_exec_time_immutable()
RETURNS TRIGGER AS $$
BEGIN
    IF OLD.status = 'SIGNED' AND (
        NEW.executed_at IS DISTINCT FROM OLD.executed_at OR
        NEW.actual_qty IS DISTINCT FROM OLD.actual_qty OR
        NEW.actual_eye_side IS DISTINCT FROM OLD.actual_eye_side
    ) THEN
        RAISE EXCEPTION 'M08: 已签名执行记录的时间/数量/眼别不可修改，请使用作废重建';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

## 8. 错误码与参数

### 8.1 错误码区间（7 位 `AABBCCC`）

| 子模块 | 号段 | 已用 | 剩余 |
|---|---|---|---|
| M08-01 | `0801001` ~ `0801040` | 40 | 0 |
| M08-02 | `0802001` ~ `0802030` | 30 | 20 |
| M08-03 | `0803001` ~ `0803030` | 30 | 20 |
| M08-04 | `0804001` ~ `0804034` | 34 | 16 |
| M08-05 | `0805001` ~ `0805040` | 40 | 10 |
| M08-06 | `0806001` ~ `0806036` | 36 | 14 |
| M08-07 | `0807001` ~ `0807080` | 80 | 20 |
| **合计** | | **290** | **100** |

**格式：** `AA` = 模块号（08），`BB` = 子模块号（01~07），`CCC` = 子模块内序号。
**类型：** **字符串**（`"0801001"`），因为 `08` 开头的整数在 Python 中是非法八进制字面量（`SyntaxError: invalid token`）。
**成功：** 仍为整数 `0`。

### 8.2 参数表（7 张配置表）

| 表 | 所属 | 参数数 |
|---|---|---|
| `m08_task_config` | M08-01 | 19 |
| `m08_med_config` | M08-06 | 20 |
| `m08_vital_threshold`（阈值，非 `*_config` 但同构） | M08-04 | 41 |
| 其余参数散落于各子模块文档附录 | — | — |

**统一唯一索引模式：**

```sql
CREATE UNIQUE INDEX uk_m08_xxx_config
  ON m08_xxx_config (param_code, scope, COALESCE(scope_id, 0))
  WHERE is_deleted = FALSE;
```

**参数读取优先级：**

```
1. 子模块级（scope='DEVICE'/'WARD', scope_id=具体ID）
2. 全局级（scope='GLOBAL', scope_id=NULL）
3. 代码默认值（DEFAULT_*)
```

**参数缓存：** Redis `m08:*:config` TTL 600s，参数更新时主动 `DEL`。

### 8.3 M08-02 参数（5 条新增，其余在各子模块文档）
