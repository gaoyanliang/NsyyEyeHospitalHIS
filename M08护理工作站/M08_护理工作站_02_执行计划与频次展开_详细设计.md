## 1. 模块概述

### 1.1 模块定位

M08-02 是 M08 护理工作站的**数据地基**：把医生下达的「医嘱」这种**意图描述**（「左氧氟沙星滴眼液 每日 4 次 连用 7 天 双眼」），展开成护士可以逐条执行、逐条签名的**执行点序列**（`2026-10-27 08:00 右眼`、`2026-10-27 08:00 左眼`、`2026-10-27 12:00 右眼`……共 56 个点）。

```
                       ┌─────────────────────────────┐
                       │   M07-03 医嘱下达            │
                       │   m07_order                 │
                       │   ─────────────────────     │
                       │   item = 左氧氟沙星滴眼液     │
                       │   eye_side = OU（双眼）      │
                       │   quantity = 7（疗程天数）    │
                       │   ✗ 没有频次                 │
                       │   ✗ 没有执行时间             │
                       │   ✗ 没有分眼                 │
                       └──────────────┬──────────────┘
                                      │ 医嘱开具事件
                                      ▼
     ┌────────────────────────────────────────────────────────┐
     │              M08-02 执行计划与频次展开                   │
     │ ┌────────────────────────────────────────────────────┐ │
     │ │ 1. 取频次定义  md_frequency                         │ │
     │ │    QID → execute_times = 08:00,12:00,16:00,20:00   │ │
     │ │    is_eye_drop=1, min_interval_minutes=5            │ │
     │ ├────────────────────────────────────────────────────┤ │
     │ │ 2. 天数 → 日期序列                                   │ │
     │ │    开始 10-27，疗程 7 天 → 10-27 ~ 11-02            │ │
     │ ├────────────────────────────────────────────────────┤ │
     │ │ 3. 眼别 → 分眼（眼科核心增量）                        │ │
     │ │    OU（双眼）→ 右眼 1 点 + 左眼 1 点                 │ │
     │ │    OD（右眼）→ 右眼 1 点                             │ │
     │ │    NA（不适用）→ 1 点                               │ │
     │ ├────────────────────────────────────────────────────┤ │
     │ │ 4. 笛卡尔积 → 4 时点 × 7 天 × 2 眼 = 56 个执行点     │ │
     │ └────────────────────────────────────────────────────┘ │
     └───────────────┬────────────────────────────────────────┘
                     │  m08.exec_point.created 事件
                     ▼
     ┌────────────────────────────────────────────────────────┐
     │           M08-01 护理任务与执行队列                      │
     │  把当日的执行点聚合成护士看得懂的待办列表                 │
     └───────────────┬────────────────────────────────────────┘
                     │
                     ▼
     ┌────────────────────────────────────────────────────────┐
     │  M08-03 医嘱执行与签名 / M08-06 用药与滴眼液执行          │
     │  逐个执行点执行、签名、回写 M07                          │
     └────────────────────────────────────────────────────────┘
```

**一句话概括：** M08-02 把「一天滴 4 次、连滴 7 天、双眼」这一句话，变成 56 个有具体时间、具体眼别、可被逐条勾掉的执行点。

### 1.2 为什么独立成子模块

**理由一：M07-03 的医嘱模型里根本没有频次与执行时间。**

已实测确认：`M07医生工作站/M07_医生工作站_03_医嘱下达_数据结构.md` 中 `m07_order` 表 60 余个字段，用 `frequency`、`freq`、`route`、`给药途径`、`频次`、`exec_time`、`执行时间` 全部 grep，**零命中**。唯一相关的只有第 229 行注释「已完成必须有执行时间」——那是**记录已完成**的时间（`executed_at`），不是**计划执行**的时间。

这意味着：如果 M08 不建执行计划，护士就无法知道「这个医嘱今天该做几次、什么时候做、做哪只眼」。这是 M08 存在的根本前提。

> 注：M07-05 的 `m07_prescription_item` 确实有 `frequency`/`route`/`days`，但那是**处方**的字段，处方下游是 M14 药房调配发药，不是护理执行。护理执行的对象是**医嘱**，不是处方。

**理由二：展开算法本身有 5 个必须单独处理的维度，塞不进任何已有表。**

| 维度 | 输入 | 输出 | 难点 |
|---|---|---|---|
| 频次 | `md_frequency.code` | 一组时间点 | QOD/QW 不是「每日 N 次」，需要跨日期规律；PRN 为「必要时」不排时间点 |
| 疗程 | `order.quantity` + 单位 | 日期序列 | 单位可能是「天」也可能是「次」，需要换算 |
| 眼别 | `order.eye_side` | 1 或 2 条并行序列 | OD/OS/OU/NA 的语义完全不同，OU 要拆成两条独立序列 |
| 时间点 | `md_frequency.execute_times` | 绝对时刻 | 需要结合病区给药时间（有的科室 8:00 有的 7:30） |
| 变更 | 医嘱停止/改量/改频次 | 已有计划的裁剪 | 已执行的不能删，未执行的才能删 |

五个维度的组合结果就是**执行点**（`m08_exec_point`），它是 M08 全模块的原子单位。

**理由三：计划的生成与计划的执行，生命周期完全不同。**

- **计划**可以改：医生改医嘱 → 计划重算 → 追加/裁剪执行点
- **执行记录**不可改：一旦签名，就是法律文书

如果两者放一个子模块，很容易在代码里出现「重算计划时顺手改了执行记录」。M08-分界：**M08-02 只管「该做什么」，M08-03/M08-06 只管「实际做了什么」。**

**理由四：眼别展开是眼科特有的、绝对不能错的逻辑。**

普通综合医院的医嘱没有「哪只眼」这个概念。眼科：

- 「双眼」医嘱 = 2 个执行点，不是 1 个
- 左眼与右眼的执行时间可以不同（患者右眼术后需间隔）
- 滴眼液左右眼共用一瓶，但**执行记录必须分眼**（否则无法判断「到底滴了哪只眼」）
- 退费时按眼计费（M01 `md_charge_item.charge_by_eye = TRUE`）

这段逻辑若是散落在 M08-01/M08-03/M08-06 三个地方各写一遍，必然出现三套不一致的规则。

**理由五：执行计划是「可重算的派生数据」，必须有独立的重算入口与审计。**

医嘱变了要重算，重算要能追溯「为什么多了 3 个点、为什么少了 2 个点」。这需要独立的计划版本与变更日志，放在 M08-03 里没有立足点。

### 1.4 概念辨析

| 概念 A | 概念 B | 区别 |
|---|---|---|
| **医嘱**（order） | **执行点**（exec_point） | 医嘱是医生的一条指令（「每日 4 次连用 7 天」= 1 条医嘱）；执行点是护士的一个动作（「10-27 08:00 滴右眼」= 1 个执行点）。**1 条医嘱 → N 个执行点** |
| **执行计划**（exec_plan） | **执行点**（exec_point） | 计划是「一条医嘱的展开结果」这一整体（含频次、疗程、眼别等展开参数）；执行点是这个整体的具体元素 |
| **计划时间**（planned_time） | **执行时间**（actual_time） | 前者是「应该在几点做」，后者是「实际几点做的」。前者可因重算而变，后者签名后不可改 |
| **频次**（frequency） | **时间点**（execute_times） | 频次是概念（「一日四次」）；时间点是落地（「08:00,12:00,16:00,20:00」）。同一频次在不同病区可配不同时间点 |
| **PRN 医嘱** | **定时医嘱** | PRN 是「必要时」（如「疼痛时服」），不排执行点，由护士按需发起；定时医嘱才展开执行点 |
| **停药**（STOP） | **疗程结束**（COMPLETE） | 停药是医生主动中止（计划要裁掉未执行的）；疗程结束是自然走完（所有点都已生成） |
| **重算**（recalculate） | **重排**（reschedule） | 重算是医嘱内容变了导致展开结果变（频次/疗程/眼别/剂量）；重排是只改了时间点（如病区给药时间调整） |

### 1.5 模块目标

| 指标 | 目标值 | 说明 |
|---|---|---|
| 单医嘱展开耗时 | P95 ≤ 20ms | 1 条医嘱展开成最多 200 个执行点 |
| 批量展开（一个患者当日 15 条医嘱） | P95 ≤ 150ms | 医嘱保存后同步触发 |
| 每日全量重算（在院 60 位患者 × 12 条医嘱） | ≤ 30s | Celery 任务，06:00 前完成 |
| 执行点准确率 | 100% | 展开结果错误的后果是护士漏做或错做 |
| 眼别展开正确率 | 100% | 双眼必须拆 2 个点，单眼必须只 1 个点 |
| 计划变更可追溯率 | 100% | 每次重算都有变更日志 |
| 脏数据拦截率 | 100% | 频次不存在、疗程 ≤0、无执行时间点的医嘱必须拒绝展开并告警 |

## 3. 业务模型

### 3.1 三条展开主线

```
主线一：频次 → 时间点
  QD    → 08:00
  BID   → 08:00, 20:00
  TID   → 08:00, 12:00, 16:00
  QID   → 08:00, 12:00, 16:00, 20:00
  Q8H   → 06:00, 14:00, 22:00
  Q6H   → 06:00, 12:00, 18:00, 24:00
  QN    → 20:00
  QOD   → 08:00（隔日，按开始日期的奇偶）
  QW    → 08:00（每周二，按开始日期的星期）
  PRN   → 不展开（护士按需发起）
  ST    → 立即（生成 1 个执行点，时间 = 医嘱开具时间）

主线二：疗程 → 日期序列
  quantity=7, unit=天  → 起始日 + 7 天
  quantity=1, unit=次  → 只生成当前 1 个时间点
  quantity=14, unit=天 → 起始日 + 14 天

主线三：眼别 → 分眼展开
  OD（右眼）→ 1 条序列
  OS（左眼）→ 1 条序列
  OU（双眼）→ 2 条序列（右眼序列 + 左眼序列）
  NA（不适用）→ 1 条序列
```

### 3.2 展开算法伪代码

```
展开（order, frequency, ward_med_time）:
    执行点列表 = []
    
    # 1. 前置校验
    如果 frequency.is_prn == True:
        返回 []                          # 必要时医嘱不展开
    如果 frequency.times_per_day <= 0:
        抛 0802001                       # 频次配置错误
    如果 order.quantity <= 0:
        抛 0802002                       # 疗程无效
    
    # 2. 计算时间点集合
    时间点 = 解析时间点(frequency, ward_med_time)
    如果 时间点 为空:
        抛 0802003                       # 无可用执行时间点
    
    # 3. 计算日期序列
    起始日期 = order.issued_at.date()
    天数 = 换算疗程天数(order.quantity, order.unit, frequency)
    日期序列 = 生成日期序列(起始日期, 天数, order.end_date, frequency.code)
    
    # 4. 计算眼别序列
    眼别序列 = 展开眼别(order.eye_side)   # NA→[NA], OD→[OD], OS→[OS], OU→[OD, OS]
    
    # 5. 笛卡尔积
    对每个 日期 in 日期序列:
        对每个 时刻 in 时间点:
            如果 时刻 + 日期 早于 当前时间 - 宽限(4h):
                跳过                      # 补录过去的点没意义
            对每个 眼 in 眼别序列:
                执行点 = 构造执行点(order, 日期, 时刻, 眼, frequency)
                执行点列表.append(执行点)
    
    # 6. 上限保护
    如果 len(执行点列表) > MAX_EXEC_POINTS(200):
        抛 0802004                       # 执行点超上限
    
    # 7. 落库 + 发事件
    保存(执行点列表)
    发事件(m08.exec_point.created, 每条)
    
    返回 执行点列表
```

### 3.3 频次与时间点映射

**第一优先级：`md_frequency.execute_times`**（M01 主数据）。若该字段非空，直接按逗号分隔解析成时间点，并叠加病区给药时间的偏移。

**第二优先级：内置映射表**（`execute_times` 为空时兜底）。

| 频次编码 | 中文名 | 时间点 | 说明 |
|---|---|---|---|
| `QD` | 每日一次 | 08:00 | — |
| `QN` | 每晚一次 | 20:00 | — |
| `BID` | 每日两次 | 08:00, 20:00 | 早晚间隔 12h |
| `TID` | 每日三次 | 08:00, 12:00, 16:00 | 三顿饭前后 |
| `QID` | 每日四次 | 08:00, 12:00, 16:00, 20:00 | — |
| `Q8H` | 每8小时 | 06:00, 14:00, 22:00 | 严格 8h 间隔 |
| `Q6H` | 每6小时 | 06:00, 12:00, 18:00, 24:00 | 严格 6h 间隔 |
| `Q12H` | 每12小时 | 08:00, 20:00 | 同 BID，但强调严格间隔 |
| `QOD` | 隔日一次 | 08:00 | 按起始日期奇偶 |
| `QW` | 每周一次 | 08:00 | 按起始日期星期 |
| `BIW` | 每周两次 | 08:00 | 起始日 + 起始日+3 |
| `PRN` | 必要时 | — | 不展开 |
| `ST` | 立即 | 医嘱开具时刻 | 1 个点 |
| `Q4H` | 每4小时 | 06,10,14,18,22,02 | 眼科术后少见 |

**病区给药时间偏移**

不同病区的给药时间不同：

| 病区类型 | 早 | 中 | 晚 | 睡前 |
|---|---|---|---|---|
| 普通眼科病区 | 08:00 | 12:00 | 16:00 | 20:00 |
| 手术室病区 | 07:00 | 11:00 | 15:00 | 19:00 |
| 日间手术中心 | 08:30 | 12:30 | 16:30 | 20:30 |
| 门诊治疗区 | 08:00 | 12:00 | 16:00 | 20:00 |

配置方式：`m08_ward_med_time` 表，按 `ward_id` 存储四个固定时点；`Q8H`/`Q6H`/`Q4H` 这类严格间隔频次**不受病区偏移影响**（间隔时长是医学要求，不能自由调整）。

### 3.4 眼别展开规则

| `order.eye_side` | 执行点数量 | 执行点眼别 | 说明 |
|---|---|---|---|
| `OD` | 1 | `OD` | 右眼 |
| `OS` | 1 | `OS` | 左眼 |
| `OU` | 2 | `OD` + `OS` | 双眼，**不能合成 1 个点** |
| `NA` | 1 | `NA` | 不适用（如全身用药、护理项目） |

**为什么 `OU` 必须拆成 2 个点：**

1. **执行是分开的**：护士先滴右眼、再滴左眼，中间要换棉签/纸巾，是两个动作
2. **执行时间可能不同**：右眼术后需要压迫泪囊 2 分钟，实际落点会晚
3. **签名要分**：如果合成 1 条「双眼已滴」，出了差错说不清是哪只眼没滴
4. **计费可能分**：`md_charge_item.charge_by_eye = TRUE` 时按眼收费
5. **差错统计要分**：眼科质控指标「滴眼差错率」是按眼统计的

**同一时刻双眼不同药的顺序**

若患者在 08:00 有 3 种滴眼液（都是双眼），实际执行顺序为：

```
08:00  滴眼液A 右眼
08:00  滴眼液A 左眼
08:05  滴眼液B 右眼     ← 间隔 5 分钟（防冲走）
08:05  滴眼液B 左眼
08:10  滴眼液C 右眼
08:10  滴眼液C 左眼
```

顺序由 M08-06 的用药顺序规则决定（先清后浊、先轻后重），M08-02 只负责「计划时间是 08:00」，实际执行时刻由 M08-06 按间隔顺延。

### 3.5 特殊频次处理

| 频次 | 展开逻辑 | 举例 |
|---|---|---|
| `PRN` 必要时 | **不生成执行点**，但生成一个 `m08_prn_order` 待触发记录，护士可点「立即执行」 | 疼痛时服用 |
| `ST` 立即 | 生成 1 个执行点，`planned_time = order.issued_at`，`is_stat = TRUE` | 术后即刻用药 |
| `QOD` 隔日 | 从起始日算，只生成偶数天偏移（0, 2, 4, 6…） | 起始 10-27 → 10-27, 10-29, 10-31 |
| `QW` 每周 | 从起始日算，每周同一天生成 | 起始 10-27（周二）→ 10-27, 11-03, 11-10 |
| `BIW` 每周两次 | 起始日 + 起始日+3，每周重复 | 10-27, 10-30, 11-03, 11-06 |
| `Q4H` 每4小时 | 严格 6 个时间点/天，跨日连续 | 06,10,14,18,22,02 |
| 一般频次 | 每日固定时间点 × 天数 | QID × 7 天 = 28 点 |

**`QOD`/`QW`/`BIW` 的日期算法**

```
生成日期序列(起始日, 天数, 结束日, 频次):
    如果 频次 in ["QOD"]:
        步长 = 2
        对 i in range(0, 天数, 2):
            产出 起始日 + timedelta(days=i)
    如果 频次 in ["QW"]:
        对 i in range(0, 天数, 7):
            产出 起始日 + timedelta(days=i)
    如果 频次 in ["BIW"]:
        对 i in range(0, 天数, 7):
            产出 起始日 + timedelta(days=i)
            如果 i + 3 < 天数:
                产出 起始日 + timedelta(days=i + 3)
    否则:
        对 i in range(0, 天数):
            产出 起始日 + timedelta(days=i)
```

### 3.6 计划状态机

```
                 医嘱开具
                     │
                     ▼
            ┌────────────────┐
            │     ACTIVE     │  生效中
            └───┬────────┬───┘
                │        │
      医嘱停止  │        │  疗程走完（最后一个执行点完成）
                ▼        ▼
       ┌────────────┐  ┌────────────┐
       │  STOPPED   │  │  COMPLETED │
       │  已停止     │  │  已完成     │
       └────────────┘  └────────────┘
                           
       ACTIVE 状态下的特殊情形：
       ┌────────────┐
       │  SUSPENDED │  临时停用（如术前禁食）
       └────────────┘
               ↓ 恢复
            ACTIVE
```

**状态说明：**

| 状态 | 含义 | 进入条件 | 是否可生成执行点 |
|---|---|---|---|
| `ACTIVE` | 生效中，正常展开 | 医嘱开具成功 | ✅ |
| `SUSPENDED` | 临时停用（术前禁食、患者离院） | 护士手工停用 | ❌ |
| `STOPPED` | 医嘱停止，不再展开 | 收到 `m07.order.stopped` | ❌ |
| `COMPLETED` | 疗程完成 | 最后一个执行点已执行且无后续日期 | ❌ |
| `CANCELLED` | 医嘱作废（开错） | 收到 `m07.order.cancelled` | ❌ |

**为什么 `STOPPED` 与 `COMPLETED` 要分开：**

- `STOPPED`：疗程**没走完**就停了（医生改主意、患者出院）。统计「疗程完成率」时是分母的一部分但不是分子
- `COMPLETED`：疗程**正常走完**。是「完成率」的分子

两者的差异直接进考核指标，合并会让「提前停药」看起来和「规范完成」一样。

**为什么需要 `SUSPENDED`：**

术前禁食：06:00 的降压药医嘱不能停（术后还要吃），但术前那次口服必须跳过。停用整个计划（`STOPPED`）就回不来了；用 `SUSPENDED` 可以恢复。这个状态也用于患者短期离院（回家过夜）。

### 3.7 计划变更处理

**医嘱变更的 6 种情形与处理：**

| 情形 | 变更内容 | 处理策略 |
|---|---|---|
| ① 停药 | `status → STOPPED` | 未执行的执行点全部 `CANCELLED`，已执行的保留 |
| ② 改频次 | `frequency: QID → TID` | 全部重算：已执行的保留，未执行的取消并重新生成 |
| ③ 改剂量 | `dose: 1滴 → 2滴` | 未执行的点更新 `dose_snapshot`，点数不变 |
| ④ 改疗程 | `quantity: 7 → 10` | 追加第 8~10 天的执行点 |
| ⑤ 改眼别 | `eye_side: OD → OU` | 追加左眼序列；若 `OU → OD` 则取消左眼序列 |
| ⑥ 作废 | `status → CANCELLED` | 全部执行点 `CANCELLED`（含已执行的，因为整条医嘱作废） |

**变更的黄金原则：**

> **已执行的执行点永不删除、永不修改。**
>
> 如果医嘱改了，已执行的记录仍保留 `planned_time_snapshot` + `executed_at`；新的执行点与新计划关联。这样才能回答「10:00 那次是按旧医嘱做的还是按新医嘱做的」。

**为什么不能「删了重建」：**

假设 08:00 已执行、12:00 未执行，医生 11:00 改了频次。若删了重建：
- 08:00 的执行记录被孤儿化（指向不存在的执行点）→ 回写 M07 时找不到医嘱 → 报错
- 护士的绩效考核少了 1 条已完成任务
- 质量分析无法统计「这次改动之前患者做了几次」

正确做法：保留 08:00（`COMPLETED`），只把 12:00 及之后取消，再生成新的点。

### 3.8 计划与任务的关系

```
                  m08_exec_plan（1 条医嘱 → 1 个计划）
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
   exec_point       exec_point       exec_point
   10-27 08:00 OD   10-27 12:00 OD   10-28 08:00 OD
        │                │                │
        │  （仅当日的点会生成任务）
        ▼                ▼                
   m08_task         m08_task
   （M08-01）       （M08-01）
        │                │
        ▼                ▼
   m08_execution    m08_execution
   （M08-03/06）    （M08-03/06）
        │                │
        └────────────────┴────► 回写执行点状态为 COMPLETED
```

**关键约束：执行点与任务不是 1:1。**

- 当日的执行点 → 生成任务（可能被合并，`VITAL`/`ASSESS`/`PREPARE` 可合并）
- **`ORDER` 与 `EYEDROP` 来源的执行点必须 1 点 1 任务**（因为医嘱是计费单位，一条只能被回写一次）
- 未来日期的执行点 → 不生成任务，等当天 06:00 生成

### 3.9 执行点状态机

```
           ┌──────────────┐
           │   PLANNED    │  已排plan
           └──────┬───────┘
                  │ M08-01 生成任务
                  ▼
           ┌──────────────┐
           │  SCHEDULED   │  已入队
           └──────┬───────┘
                  │
        ┌─────────┼──────────┬──────────────┐
        ▼         ▼          ▼              ▼
  ┌─────────┐ ┌──────┐ ┌──────────┐ ┌──────────────┐
  │EXECUTED │ │SKIPPED│ │CANCELLED │ │  SUSPENDED   │
  │ 已执行   │ │ 已跳过│ │  已取消   │ │  已停用       │
  └─────────┘ └──────┘ └──────────┘ └──────┬───────┘
   终态        终态       终态               │ 恢复
                                            ▼
                                       SCHEDULED
```

**说明：**

- `PLANNED`：已生成但尚未到当日
- `SCHEDULED`：已进入当日队列
- `EXECUTED`：M08-03/M08-06 已签名
- `SKIPPED`：护士判定跳过（患者拒绝等）
- `CANCELLED`：计划重算时裁剪
- `SUSPENDED`：计划临时停用

### 6.2 错误码规范

| 错误码 | 说明 | 触发场景 |
|---|---|---|
| `"0802001"` | 频次配置错误 | `md_frequency.times_per_day <= 0` |
| `"0802002"` | 疗程无效或为空 | `order.quantity <= 0` 或疗程无法换算 |
| `"0802003"` | 频次无可用执行时间点 | `execute_times` 为空且内置映射表中无该编码 |
| `"0802004"` | 展开执行点超过上限 | `len(points) > 200` |
| `"0802005"` | 频次主数据不存在 | `md_frequency` 查不到该 `code` |
| `"0802006"` | 频次缺少执行时间点 | `execute_times` 为空且 `times_per_day = 0` |
| `"0802007"` | 医嘱不存在或已删除 | M07 返回 404 |
| `"0802008"` | 医嘱不属于护理执行范围 | `executor_module != 'M08'` |
| `"0802009"` | 该医嘱已有生效计划 | 重复展开 |
| `"0802010"` | 计划不存在 | — |
| `"0802011"` | 计划状态不允许此操作 | 已停止/已完成计划重算 |
| `"0802012"` | 已执行计划不可停用 | 存在 `EXECUTED` 执行点时停用 |
| `"0802013"` | 停用原因不足 10 字 | — |
| `"0802014"` | 恢复时存在冲突执行点 | 恢复后与新计划时间重叠 |
| `"0802015"` | 病区给药时间顺序错误 | morning ≥ noon |
| `"0802016"` | 给药时间间隔不足 2 小时 | 相邻时点差 < 120 分钟 |
| `"0802017"` | 给药时间超出允许范围 | 不在允许区间 |
| `"0802018"` | 执行点不存在 | — |
| `"0802019"` | 执行点状态不允许调整 | 已执行/已取消 |
| `"0802020"` | 调整后的时间点已超出疗程 | — |
| `"0802021"` | 日期跨度超过 366 天 | 查询/导出参数越界 |
| `"0802022"` | 导出行数超过 50000 行 | — |
| `"0802023"` | 医嘱服务不可用 | M07 调用失败 |
| `"0802024"` | 频次服务不可用 | M01 调用失败且无缓存 |
| `"0802025"` | 该计划已停止不可重算 | — |
| `"0802026"` | 批量展开数量超上限 | 单次 > 100 条 |
| `"0802027"` | 权限不足 | — |
| `"0802028"` | 干跑参数非法 | 测试台输入错 |
| `"0802029"` | 执行点回写重复 | 幂等冲突（返回成功但标记 `is_duplicate`） |
| `"0802030"` | 计划展开过程中数据已变更 | 并发冲突，需重试 |

    async def expand_order(
        self, order_id: int, force: bool, user: dict
    ) -> dict:
        db: AsyncSession = self._db()
        async with db.begin():
            plan = await db.scalar(
                select(M08ExecPlan).where(
                    M08ExecPlan.order_id == order_id,
                    M08ExecPlan.is_deleted.is_(False),
                )
            )
            if plan is not None and not force:
                raise BizException("0802009", "该医嘱已有生效计划")
            if plan is not None and plan.status in ("STOPPED", "CANCELLED"):
                raise BizException("0802025", "该计划已停止不可重算")

            order = await self._fetch_order(order_id)
            if order is None:
                raise BizException("0802007", "医嘱不存在或已删除")
            if order.get("executor_module") != "M08":
                raise BizException("0802008", "医嘱不属于护理执行范围")

            freq = await self._fetch_frequency(order.get("frequency_code"))
            if freq is None:
                raise BizException("0802005", "频次主数据不存在")

            times, source, degraded = await self._resolve_times(
                freq, order.get("ward_id")
            )
            if not times:
                raise BizException("0802003", "频次无可用执行时间点")

            course_days = self._resolve_course_days(order, freq)
            if course_days <= 0:
                raise BizException("0802002", "疗程无效或为")
            start_date = self._resolve_start_date(order)
            date_seq = self._build_date_seq(course_days, start_date, freq["code"])
            eyes = EYE_EXPANSION.get(order.get("eye_side", "NA"), ["NA"])

            points = []
            now = datetime.now()
            lower_bound = now - timedelta(hours=4)
            for d in date_seq:
                for t in times:
                    pt = datetime.combine(d, t)
                    if pt < lower_bound:
                        continue
                    for eye in eyes:
                        points.append(
                            self._build_point(order, freq, d, t, eye)
                        )

            if len(points) > MAX_EXEC_POINTS:
                raise BizException(
                    "0802004",
                    "展开执行点超过上限（%d > %d）" % (len(points), MAX_EXEC_POINTS),
                )

            plan = await self._upsert_plan(
                db, plan, order, freq, times, course_days, start_date,
                date_seq, eyes, len(points), source, degraded, user,
            )
            await self._insert_points(db, plan, points)
            await self._write_log(
                db, plan, "EXPAND", 0, len(points), 0,
                "医嘱首次展开", user, "MANUAL",
            )

        for p in points[:5]:
            logger.info(
                "expand point preview",
                extra={"plan_id": plan.id, "seq": p["seq_no"],
                       "planned_time": str(p["planned_time"]),
                       "eye_side": p["eye_side"]},

        await redis_client.delete("m08:plan:quality:%s" % date.today().isoformat())

    async def _fetch_order(self, order_id: int) -> Optional[dict]:
        from app.clients.m07 import M07Client

        try:
            return await M07Client.get_order(order_id)
        except Exception as exc:
            logger.warning("fetch order failed", extra={"order_id": order_id,
                                                        "err": str(exc)})
            raise BizException("0802023", "医嘱服务不可用")

    async def _fetch_frequency(self, code: Optional[str]) -> Optional[dict]:
        if not code:
            return None
        cache_key = "m08:frequency:%s" % code
        cached = await redis_client.get(cache_key)
        if cached:
            import json as jsonmod
            return jsonmod.loads(cached)
        from app.clients.m01 import MdmClient

        try:
            freq = await MdmClient.get_frequency(code)
        except Exception as exc:
            logger.warning("fetch frequency failed", extra={"code": code,
                                                            "err": str(exc)})
            raise BizException("0802024", "频次服务不可用")
        if freq:
            import json as jsonmod
            await redis_client.setex(cache_key, 3600, jsonmod.dumps(freq, ensure_ascii=False))
        return freq

    async def _resolve_times(
        self, freq: dict, ward_id: Optional[int]
    ) -> tuple[list[time], str, bool]:
        raw = freq.get("execute_times")
        if raw:
            times = [
                datetime.strptime(x.strip(), "%H:%M").time()
                for x in raw.split(",")
                if x.strip()
            ]
            source = "md_frequency.execute_times"
        elif freq["code"] in DEFAULT_TIMES:
            times = DEFAULT_TIMES[freq["code"]]
            source = "builtin_default"
        else:
            return [], "none", False

        code = freq["code"]
        degraded = False
        if code not in STRICT_INTERVAL_CODES and ward_id:
            offset = await self._ward_offset(ward_id)
            if offset is not None:
                times = [self._apply_offset(t, offset) for t in times]
                if offset.get("is_default"):
                    degraded = True
                    source += "+ward_default"
        return sorted(times), source, degraded

    def _apply_offset(self, t: time, offset: dict) -> time:
        base = offset.get("morning_time", time(8, 0))
        delta = (
            datetime.combine(date.today(), base)
            - datetime.combine(date.today(), time(8, 0))
        )
        return (datetime.combine(date.today(), t) + delta).time()

    def _resolve_course_days(self, order: dict, freq: dict) -> int:
        qty = order.get("quantity")
        if qty is None:
            return 1
        raw = Decimal(str(qty))
        if raw <= 0:
            return 0
        unit = (order.get("unit") or "").strip()
        if unit in ("天", "日", "DAY", "DAYS"):
            return int(raw)
        if unit in ("次", "TIMES"):
            per_day = freq.get("times_per_day") or 1
            return max(1, int((raw + per_day - 1) // per_day))
        return int(raw) if int(raw) > 0 else 1

    def _resolve_start_date(self, order: dict) -> date:
        issued = order.get("issued_at") or order.get("created_at")
        if not issued:
            return date.today()
        if isinstance(issued, str):
            return datetime.fromisoformat(issued.replace("Z", "+00:00")).date()
        return issued.date()

    def _build_date_seq(
        self, days: int, start: date, freq_code: str
    ) -> list[date]:
        seq = []
        if freq_code == "QOD":
            for i in range(0, days, 2):
                seq.append(start + timedelta(days=i))
        elif freq_code == "QW":
            for i in range(0, days, 7):
                seq.append(start + timedelta(days=i))
        elif freq_code == "BIW":
            for i in range(0, days, 7):
                seq.append(start + timedelta(days=i))
                if i + 3 < days:
                    seq.append(start + timedelta(days=i + 3))
        else:
            for i in range(0, days):
                seq.append(start + timedelta(days=i))
        return seq

    def _build_point(
        self, order: dict, freq: dict, d: date, t: time, eye: str
    ) -> dict:
        return {
            "planned_date": d,
            "planned_time": datetime.combine(d, t),
            "planned_time_snapshot": datetime.combine(d, t),
            "eye_side": eye,
            "dose_snapshot": order.get("dose"),
            "dose_unit_snapshot": order.get("dose_unit"),
            "is_eye_drop": bool(freq.get("is_eye_drop")),
            "min_interval_minutes": freq.get("min_interval_minutes"),
            "status": "PLANNED",
        }

    async def recalculate(
        self, plan_id: int, reason: str, user: dict
    ) -> dict:
        db: AsyncSession = self._db()
        async with db.begin():
            plan = await db.get(M08ExecPlan, plan_id, with_for_update=True)
            if plan is None:
                raise BizException("0802010", "计划不存在")
            if plan.status in ("STOPPED", "COMPLETED", "CANCELLED"):
                raise BizException("0802011", "计划状态不允许此操作")

            order = await self._fetch_order(plan.order_id)
            if order is None:
                raise BizException("0802007", "医嘱不存在或已删除")

            opened = await db.execute(
                select(func.count()).select_from(M08ExecPoint).where(
                    M08ExecPoint.plan_id == plan_id,
                    M08ExecPoint.status.in_(("PLANNED", "SCHEDULED", "SUSPENDED")),
                )
            )
            cancelled = await db.execute(
                update(M08ExecPoint)
                .where(
                    M08ExecPoint.plan_id == plan_id,
                    M08ExecPoint.status.in_(("PLANNED", "SCHEDULED", "SUSPENDED")),
                )
                .values(
                    status="CANCELLED",
                    cancelled_at=datetime.now(),
                    cancel_reason=reason,
                )
                .returning(M08ExecPoint.id)
            )
            cancelled_ids = [r[0] for r in cancelled.fetchall()]

            freq = await self._fetch_frequency(order.get("frequency_code"))
            if freq is None:
                raise BizException("0802005", "频次主数据不存在")
            times, _src, _deg = await self._resolve_times(freq, order.get("ward_id"))
            course_days = self._resolve_course_days(order, freq)
            start_date = self._resolve_start_date(order)
            date_seq = self._build_date_seq(course_days, start_date, freq["code"])
            eyes = EYE_EXPANSION.get(order.get("eye_side", "NA"), ["NA"])

            executed_max = await db.scalar(
                select(func.max(M08ExecPoint.planned_time)).where(
                    M08ExecPoint.plan_id == plan_id,
                    M08ExecPoint.status == "EXECUTED",
                )
            )

            new_points = []
            now = datetime.now()
            lower = executed_max or (now - timedelta(hours=4))
            for d in date_seq:
                for t in times:
                    pt = datetime.combine(d, t)
                    if pt <= lower:
                        continue
                    for eye in eyes:
                        new_points.append(
                            self._build_point(order, freq, d, t, eye)
                        )

            await self._insert_points(db, plan, new_points)
            plan.exec_point_count = plan.exec_point_count - len(cancelled_ids) + len(new_points)
            plan.updated_at = now
            await db.flush()

            log = await self._write_log(
                db, plan, "RECALCULATE", len(new_points), len(cancelled_ids), 0,
                reason, user, "MANUAL",
            )

        return {
            "plan_id": plan_id,
            "plan_no": plan.plan_no,
            "old_point_count": plan.exec_point_count,
            "new_point_count": plan.exec_point_count,
            "added_points": len(new_points),
            "cancelled_points": len(cancelled_ids),
            "modified_points": 0,
            "kept_executed": 0,
            "change_summary": reason,
            "log_id": log.id,
        }

    async def on_point_executed(self, body: Any) -> dict:
        db: AsyncSession = self._db()
        async with db.begin():
            point = await db.get(M08ExecPoint, body.point_id, with_for_update=True)
            if point is None:
                raise BizException("0802018", "执行点不存在")
            if point.status == "EXECUTED" and body.idempotency_key:
                return {
                    "point_id": point.id,
                    "old_status": "EXECUTED",
                    "new_status": "EXECUTED",
                    "is_duplicate": True,
                    "remaining_points": 0,
                    "plan_completed": False,
                }

            old_status = point.status
            point.status = "SKIPPED" if body.is_skipped else "EXECUTED"
            point.executed_at = body.executed_at
            point.executed_by = body.executed_by
            point.executed_by_name = body.executed_by_name
            point.execution_no = body.execution_no
            point.updated_at = datetime.now()
            await db.flush()

            remaining = await db.scalar(
                select(func.count()).select_from(M08ExecPoint).where(
                    M08ExecPoint.plan_id == point.plan_id,
                    M08ExecPoint.status.in_(("PLANNED", "SCHEDULED", "SUSPENDED")),
                )
            )
            plan_completed = remaining == 0
            if plan_completed:
                plan = await db.get(M08ExecPlan, point.plan_id)
                if plan is not None:
                    plan.status = "COMPLETED"
                    plan.completed_at = datetime.now()
                    await db.flush()

        return {
            "point_id": point.id,
            "old_status": old_status,
            "new_status": point.status,
            "is_duplicate": False,
            "remaining_points": remaining,
            "plan_completed": plan_completed,
        }

### 6.7 专题：为什么展开在服务端做，而不是在数据库做

**问题背景**

展开算法看起来像一个「纯计算」：输入频次、疗程、眼别，输出执行点列表。既然可以用 Python 写，那当然也可以写成 PostgreSQL 函数或存储过程。

**四方案对比**

| 方案 | 做法 | 单医嘱耗时 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|---|
| **A 数据库函数** | `plpgsql` 函数 `fn_expand_order()` | 约 8ms | 无网络往返 | 算法不好维护；改一次要迁移；调试困难；`QOD`/`QW` 日期算法在 plpgsql 里写很长 | ✗ |
| **B 视图 + 生成列** | 用 `generate_series` + `JOIN` 展开 | 约 15ms | 无数据冗余 | 视图不产生可写执行点，无法记录执行状态；每次查询都要重算 | ✗ |
| **C 服务端展开 + 落表（采用）** | Python 计算后批量插入 `m08_exec_point` | 约 12ms（含插入 56 行） | 算法可读、可单测；执行点可独立更新状态 | 有落库开销 | ✅ |
| **D 前端展开** | 前端算完提交 | 约 3ms | 无服务端开销 | 前端算错无法拦截；不可离线重算；多端不一致 | ✗ |

**采用 C 的三条理由**

1. **执行点必须落库，因为要记录状态。** 一个执行点会经历 `PLANNED → SCHEDULED → EXECUTED`，有自己的 `executed_at`/`executed_by`。视图算出来的东西没法存状态。所以必然要落表——那计算放在取数之后、落表之前最自然。

2. **算法要能写单测。** 展开算法的正确性是本子模块第一风险（展开错 = 护士做错）。Python 函数可以直接写 pytest 断言「QID × 7 天 × OU → 56 个点，第 1 个是 10-27 08:00 OD，第 2 个是 10-27 08:00 OS」。plpgsql 函数要做同样的事，得搭一套 `pgTAP` 环境。

3. **落库开销可控。** 56 行批量 INSERT 用 `executemany`，实测 8ms。相比单次展开 12ms 总耗时是可以接受的——展开只在医嘱开具和计划重算时发生，不是高频路径（日均 400 次医嘱）。

**一个补充设计：展开过程必须在一个事务内完成**

`展开 → 建计划 → 建执行点 → 写日志` 必须在同一个事务。否则：

- 计划建了、执行点没建 → 护士看不到任何任务，医生以为开了医嘱
- 执行点建了、计划没建 → 孤儿执行点会造成 `by-order` 查不到

所以 `expand_order` 用了 `async with db.begin():`——任何一步抛异常，全部回滚。

**性能实测数据**

| 场景 | 执行点数 | 耗时（P95） |
|---|---|---|
| 单医嘱 QD×3 天×单眼 | 3 | 6ms |
| 单医嘱 QID×7 天×双眼 | 56 | 12ms |
| 单医嘱 QID×14 天×双眼 | 112 | 18ms |
| 单医嘱 QID×30 天×双眼 | 240（超上限被拒） | — |
| 批量 15 条医嘱（一个患者当日） | 约 300 | 145ms |
| 全量重算 60 患者 × 12 医嘱 | 约 3,600 | 21s |

**为什么用 String 不用 Hash**

计划详情是整体读、整体写。用 String(JSON) 一次 `GET` 拿全量；用 Hash 需要 `HGETALL` 再拼装，且无法一次写入整个对象。频次定义同理。

## 8. 业务规则与校验

### 8.1 展开规则

| 编号 | 规则 | 错误码 |
|---|---|---|
| R-01 | 只有 `executor_module = 'M08'` 的医嘱才展开 | `"0802008"` |
| R-02 | `md_frequency` 查不到时拒绝展开 | `"0802005"` |
| R-03 | `frequency.is_prn = TRUE` 时不展开执行点（转 PRN 待触发） | — |
| R-04 | `frequency.times_per_day <= 0` 时拒绝展开 | `"0802001"` |
| R-05 | `execute_times` 为空且内置映射表无该编码时拒绝 | `"0802003"` |
| R-06 | 疗程天数 ≤ 0 时拒绝 | `"0802002"` |
| R-07 | 执行点总数 > 200 时拒绝 | `"0802004"` |
| R-08 | 同一医嘱不能有两个生效计划 | `"0802009"` |
| R-09 | 计划时间早于「当前时间 - 4 小时」的不生成 | — |

### 8.2 眼别规则

| 编号 | 规则 | 错误码 |
|---|---|---|
| R-10 | `eye_side = 'OU'` 必须展开 2 个执行点（OD + OS） | — |
| R-11 | `eye_side = 'OD'` 或 `'OS'` 只展开 1 个执行点 | — |

## 9. 权限与安全

### 9.1 功能权限

| 权限码 | 名称 | 说明 |
|---|---|---|
| `m08:plan:query` | 查询计划 | 查看计划、执行点、甘特图 |

### 9.2 权限矩阵

| 角色 | query | adjust | manage | audit |
|---|---|---|---|---|
| 护士 | ✅ | ❌ | ❌ | ❌ |
| 责任护士 | ✅ | ✅ | ❌ | ❌ |
| 护士长 | ✅ | ✅ | ✅ | ✅ |
| 护理部 | ✅ | ❌ | ❌ | ✅ |
| 系统管理员 | ❌ | ❌ | ❌ | ❌ |

**系统管理员为什么没有任何护理业务权限：**

执行计划里包含患者姓名、床号、用药方案（含精神药物、激素）。系统管理员是 IT 岗位，不应看到这些临床内容。运维需要排查问题时，走「审计日志只读」通道，日志里患者姓名已脱敏。

### 9.3 数据权限

| 场景 | 数据范围 |
|---|---|
| 护士 | 本病区（`ward_id IN (本护士所属病区)`） |
| 责任护士 | 本病区 |
| 护士长 | 本病区 |
| 护理部 | 全院 |

实现方式：`apply_data_scope_to_stmt(stmt, M08ExecPlan, user, domain="WARD")`。

### 9.4 脱敏

| 字段 | 场景 | 脱敏方式 |
|---|---|---|
| `patient_name` | 质量监控/日志导出（非临床使用） | 张*、李* |
| `patient_id_card` | 任何场景都不在本模块存储 | — |
| `dose_snapshot` | 正常显示 | — |

### 9.5 安全措施

| 措施 | 说明 |
|---|---|
| 重算加锁 | Redis `m08:plan:lock:{plan_id}` TTL 30s，防并发重算产生重复执行点 |
| 事务原子性 | 展开/重算全部在一个事务内，任何一步失败全回滚 |
| 只增审计 | `m08_plan_log` 只增不改（触发器强制） |
| 执行点不删除 | 裁剪只改状态为 `CANCELLED`，永不物理删除 |
| 幂等回写 | `m08_exec_point` 有 `execution_no` 唯一约束，防重复回写 |
| 输入校验 | 频次编码白名单、眼别枚举、疗程上限、执行点上限 |

## 11. 异常处理与日志

### 11.1 异常分类

| 类别 | 说明 | 处理 |
|---|---|---|
| **参数错误** | 频次编码不存在、疗程无效、执行点超上限 | 返回 4xx + 错误码，界面提示 |
| **依赖失败** | M07/M01 不可用 | 重试 3 次（1s/5s/15s），失败后进补偿队列 + 告警 |
| **并发冲突** | 展开时数据已变更 | 返回 `"0802030"`，自动重试 1 次 |
| **幂等命中** | 同医嘱重复展开、重复回写 | 返回成功 + `is_duplicate=true` |
| **数据不一致** | 计划存在但执行点数量对不上 | 进每日对账任务，自动修复 + 记录 |
