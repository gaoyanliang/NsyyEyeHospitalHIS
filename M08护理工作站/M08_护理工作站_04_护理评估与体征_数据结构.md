**设计说明：**

1. **体征值用 JSONB 而不是宽表（24 个字段）。** 理由有三：①体征项是「稀疏」的——一次采集通常只填 4~8 项，宽表会产生 16~20 个 NULL；②体征项会扩展（未来加「角膜水肿」「眼睑下垂」），宽表每加一项就要迁移；③查询模式是「按患者取整行，再按项提取」，不是「按某一项做范围查询」，JSONB 完全够用。

   代价是无法直接在 SQL 里对单项做范围过滤和聚合。因此所有统计查询（如「统计本月体温超阈值次数」）都走 `m08_vital_alert` 表而非从 JSONB 里提取。这个分工是清晰的：**明细在 JSONB，判定结果在告警表**。

2. **`m08_assess_template` 与 `m08_assessment` 用 `(template_code, version)` 关联而不是外键。** 评估记录保存 `template_code` + `template_version` 两个字段作为**版本快照**。这样即使模板升级到 V2，历史记录仍能按 V1 的计分规则复算。

3. **`m08_assess_item` 独立成表而不是 JSONB。** 与体征不同：①评估项需要按 `item_code` 做统计（「本月有多少患者『近三个月跌倒史』为阳性」）；②评估项数量固定（1~10 项），不稀疏；③需要按项目维度导出明细供质控分析。

4. **告警表 `m08_vital_alert` 独立于体征表。** 一条体征可能产生多条告警（体温 + 脉搏 + 组合告警）；修改体征时旧告警要撤销、新告警要生成；告警有自己的生命周期（PENDING→ACKNOWLEDGED→CLOSED）。

5. **`m08_vital_log` 只增不改。** 体征修改是敏感操作，日志必须不可篡改（触发器强制）。日志只记录「改了什么」，不记录「看了什么」（查询不写日志，避免日志爆炸）。

6. **阈值配置表带 `scope`/`scope_id`。** 支持「医院级默认 + 病区级覆盖」两级配置。眼科病区的眼压阈值与综合病区可能不同（比如眼科术后病房需要更敏感的告警）。

### 4.2 表：`m08_vital_sign`

**用途：** 体征采集记录主表。一次采集一条记录，所有体征项的值存在 `values_json` 里。

**字段定义：**

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | IDENTITY | 主键 |
| `vital_no` | VARCHAR(32) | 否 | — | 体征编号 `VS` + YYYYMMDD + 6 位序号 |
| `patient_id` | BIGINT | 否 | — | 患者 ID |
| `patient_name` | VARCHAR(64) | 否 | — | 患者姓名快照 |
| `patient_sex` | VARCHAR(8) | 是 | NULL | 性别快照 |
| `patient_age` | SMALLINT | 是 | NULL | 年龄快照 |
| `encounter_id` | BIGINT | 是 | NULL | 就诊会话 ID（门诊） |
| `admission_id` | BIGINT | 是 | NULL | 住院/日间 ID |
| `schedule_id` | BIGINT | 是 | NULL | 手术排程 ID |
| `ward_id` | BIGINT | 否 | — | 病区 ID 快照 |
| `bed_no` | VARCHAR(16) | 是 | NULL | 床号快照 |
| `nursing_level` | VARCHAR(16) | 是 | NULL | 护理级别快照 |
| `vital_time` | TIMESTAMP | 否 | — | 采集时刻（业务时间） |
| `point_id` | BIGINT | 是 | NULL | M08-02 执行点 ID |
| `task_id` | BIGINT | 是 | NULL | M08-01 任务 ID |
| `values_json` | JSONB | 否 | — | 体征值数组 |
| `bmi` | NUMERIC(4,1) | 是 | NULL | BMI（自动计算冗余，便于排序统计） |
| `values_hash` | VARCHAR(32) | 否 | — | 体征项编码集合的 MD5（用于唯一约束） |
| `item_count` | SMALLINT | 否 | — | 本次采集的体征项数量 |
| `device_code` | VARCHAR(64) | 是 | NULL | 设备编码（设备直连时） |
| `is_device_read` | BOOLEAN | 否 | FALSE | 是否设备读数导入 |
| `remark` | VARCHAR(200) | 是 | NULL | 备注 |
| `recorded_by` | BIGINT | 否 | — | 采集人 ID |
| `recorded_by_name` | VARCHAR(64) | 是 | NULL | 采集人姓名快照 |
| `is_late_corrected` | BOOLEAN | 否 | FALSE | 是否超窗口修正过 |
| `late_correct_reason` | VARCHAR(500) | 是 | NULL | 超窗口修正原因 |
| `late_correct_by` | BIGINT | 是 | NULL | 超窗口修正人 |
| `late_correct_at` | TIMESTAMP | 是 | NULL | 超窗口修正时间 |
| `edit_count` | SMALLINT | 否 | 0 | 累计修改次数 |
| `trace_id` | VARCHAR(64) | 是 | NULL | 链路追踪 |
| `created_at` | TIMESTAMP | 否 | NOW() | 创建时间 |
| `updated_by` | BIGINT | 是 | NULL | 更新人 |
| `updated_at` | TIMESTAMP | 否 | NOW() | 更新时间 |
| `is_deleted` | BOOLEAN | 否 | FALSE | 软删除 |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m08_vital_sign` | 主键 | `id` | — |
| `uk_m08_vital_no` | 唯一（部分） | `vital_no` WHERE `is_deleted = FALSE` | 体征编号唯一 |
| `uk_m08_vital_dedup` | 唯一（部分） | `(patient_id, date_trunc('minute', vital_time), values_hash)` WHERE `is_deleted = FALSE` | **防重复采集**（同一分钟同一组体征项） |
| `idx_m08_vital_patient_time` | B-Tree | `(patient_id, vital_time DESC)` | 患者体征时间序列（趋势图主力） |
| `idx_m08_vital_ward_date` | B-Tree | `(ward_id, vital_time DESC)` | 病区当日体征 |
| `idx_m08_vital_recorded` | B-Tree | `(recorded_by, created_at DESC)` | 护士工作量 |

| `idx_m08_vital_name_trgm` | GIN trgm | `patient_name gin_trgm_ops` | 患者名搜索 |

**约束说明：**

```sql
-- 体征编号格式
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_no
  CHECK (vital_no ~ '^VS[0-9]{8}[0-9]{6}$');

-- 归属键至少一个非空（R-40）
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_belonging
  CHECK (encounter_id IS NOT NULL OR admission_id IS NOT NULL OR schedule_id IS NOT NULL);

-- 体征值必须是数组（JSONB）
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_values_type
  CHECK (jsonb_typeof(values_json) = 'array');

-- 体征值数组不能为空
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_values_notempty
  CHECK (jsonb_array_length(values_json) > 0);

-- 体征项数量必须与数组长度一致
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_item_count
  CHECK (item_count = jsonb_array_length(values_json));

-- 体征项数量上限（防止异常数据）
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_item_count_max
  CHECK (item_count <= 30);

-- values_hash 格式（MD5）
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_hash
  CHECK (values_hash ~ '^[0-9a-f]{32}$');

-- BMI 合理范围
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_bmi
  CHECK (bmi IS NULL OR (bmi >= 5.0 AND bmi <= 99.0));

-- 采集时间不能是未来（留 5 分钟时钟容差）
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_time
  CHECK (vital_time <= created_at + INTERVAL '5 minutes');

-- 超窗口修正必须完整记录
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_late_correct
  CHECK (is_late_corrected = FALSE
         OR (late_correct_reason IS NOT NULL
             AND char_length(btrim(late_correct_reason)) >= 10
             AND late_correct_by IS NOT NULL
             AND late_correct_at IS NOT NULL));

-- 修改次数不为负
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_edit_count
  CHECK (edit_count >= 0);

-- 备注长度
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_remark
  CHECK (remark IS NULL OR char_length(remark) <= 200);

-- 护理级别枚举
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_nursing_level
  CHECK (nursing_level IS NULL
         OR nursing_level IN ('SPECIAL', 'LEVEL_1', 'LEVEL_2', 'LEVEL_3'));

-- 设备读数必须带设备编码
ALTER TABLE m08_vital_sign
  ADD CONSTRAINT ck_m08_vital_device
  CHECK (is_device_read = FALSE OR device_code IS NOT NULL);

COMMENT ON TABLE m08_vital_sign IS 'M08-04 体征采集记录，一次采集一条，体征值存 JSONB';
COMMENT ON COLUMN m08_vital_sign.values_json IS '体征值数组，形如 [{"code":"TEMP","value":37.8,"extra":"AXILLARY"}]';
COMMENT ON COLUMN m08_vital_sign.values_hash IS '排序后体征项编码集合的 MD5，用于防重复采集唯一约束';
COMMENT ON COLUMN m08_vital_sign.vital_time IS '业务采集时刻，用于趋势图横轴；不等于 created_at';
COMMENT ON COLUMN m08_vital_sign.bmi IS 'BMI 冗余字段，由体重身高自动计算，用于营养趋势排序';
COMMENT ON COLUMN m08_vital_sign.edit_count IS '累计修改次数，超过 3 次进质量关注名单';
```

**量级估算：**

| 项目 | 数值 | 计算依据 |
|---|---|---|
| 日均采集条数 | 400 | 40 床 × 4 次 + 门诊 |
| 年采集条数 | 146,000 | 400 × 365 |
| 单行长度 | 约 900 字节 | 含 JSONB 约 300 字节 |
| 年数据量 | 约 131 MB | — |
| 15 年累计 | 约 2,190,000 行 | 约 2.0 GB（含索引约 3.4 GB） |

**分区：** 不分区（15 年 219 万行可承受）。若未来数据量增长，可按 `vital_time` 年度 RANGE 分区，此时 `uk_m08_vital_dedup` 需含分区键，语义退化为「同年内不重复」——因防重复窗口只有 1 分钟，跨年重复不可能发生，无风险。

### 4.3 表：`m08_vital_alert`

**用途：** 体征告警记录与处置闭环。一条体征可产生多条告警。

**字段定义：**

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | IDENTITY | 主键 |
| `alert_no` | VARCHAR(32) | 否 | — | 告警编号 `AL` + YYYYMMDD + 6 位序号 |
| `vital_id` | BIGINT | 是 | NULL | 关联体征记录 ID（组合告警可为空） |
| `patient_id` | BIGINT | 否 | — | 患者 ID |
| `patient_name` | VARCHAR(64) | 是 | NULL | 患者姓名快照 |
| `bed_no` | VARCHAR(16) | 是 | NULL | 床号快照 |
| `ward_id` | BIGINT | 是 | NULL | 病区 ID |
| `vital_code` | VARCHAR(32) | 否 | — | 体征项编码（组合告警为 `COMBO`） |
| `vital_name` | VARCHAR(64) | 是 | NULL | 体征项名称 |
| `value` | NUMERIC(12,4) | 是 | NULL | 触发值（组合告警为空） |

**状态机：**

```
                       PENDING（待确认）
                           │
          ┌────────────────┼─────────────────┬──────────────┐
          │                │                 │              │
          ▼                ▼                 ▼              ▼
   ACKNOWLEDGED      ACKNOWLEDGED       AUTO_CLOSED      REVOKED
   （仅确认）         （确认+报告医生）    （超时自动关）    （体征被改）
          │                │
          ▼                ▼
      HANDLED         ESCALATED
          │                │
          └────────┬───────┘
                   ▼
               CLOSED（闭环终态）
```

**设计要点：**

1. **为什么 `vital_id` 允许为空。**
   组合告警是「多个体征项共同触发」，可能对应一条体征记录（同一时点采集多项），也可能跨多条记录（10 分钟内的两次采集）。后者没有单一 `vital_id`，只记 `patient_id` 与 `vital_code='COMBO'`。

2. **撤销（`REVOKED`）不是删除。**
   体征被修改后，基于旧值的告警要失效。但直接删除会让「曾经报过这个警」的历史消失。置 `REVOKED` 并记 `revoke_reason`，保留了完整轨迹。

3. **`response_seconds` 冗余存而不是查询时计算。**
   告警统计（「本月平均响应时间」）要扫几千行。查询时计算 `acknowledged_at - detected_at` 每行都要做时间减法，且无法走索引。落库时算好，直接 `AVG(response_seconds)` 可用索引。

4. **`partial index idx_m08_alert_open`。**
   告警中心每 30 秒刷新一次，只查「未闭环」的（稳态 3~10 条）。全表年 6,000 行，15 年 9 万行。部分索引后只扫几十行，查询从 15ms 降到 1ms。

5. **`ck_m08_alert_deadline` 强制 `deadline_at > detected_at`。**
   防止代码把截止时间算错成过去时间，导致告警一生成就超时。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 日均告警 | 16 条（约 4% 采集触发告警） |
| 年告警 | 5,840 |
| 单行长度 | 约 600 字节 |
| 年数据量 | 约 3.5 MB |
| 15 年累计 | 约 87,600 行 / 53 MB |

**分区：** 不分区。

**用途：** 体征阈值配置，支持「医院级默认 + 病区级覆盖」两级。

**约束说明：**

```sql
-- 级别枚举
ALTER TABLE m08_vital_threshold
  ADD CONSTRAINT ck_m08_threshold_level
  CHECK (level IN ('CRITICAL', 'SEVERE', 'WARNING', 'TREND'));

-- scope 枚举
ALTER TABLE m08_vital_threshold
  ADD CONSTRAINT ck_m08_threshold_scope
  CHECK (scope IN ('GLOBAL', 'WARD'));

-- GLOBAL 级 scope_id 必须为空，WARD 级必须非空
ALTER TABLE m08_vital_threshold
  ADD CONSTRAINT ck_m08_threshold_scope_id
  CHECK ((scope = 'GLOBAL' AND scope_id IS NULL)
         OR (scope = 'WARD' AND scope_id IS NOT NULL));

-- 高值与低值不能同时为空（单值阈值至少要一个）
ALTER TABLE m08_vital_threshold
  ADD CONSTRAINT ck_m08_threshold_value
  CHECK (level = 'TREND' OR high_value IS NOT NULL OR low_value IS NOT NULL);

-- 高值必须大于低值
ALTER TABLE m08_vital_threshold
  ADD CONSTRAINT ck_m08_threshold_cross
  CHECK (high_value IS NULL OR low_value IS NULL OR high_value > low_value);

-- 趋势级必须有幅度与窗口
ALTER TABLE m08_vital_threshold
  ADD CONSTRAINT ck_m08_threshold_trend
  CHECK (level <> 'TREND'
         OR (trend_delta IS NOT NULL
             AND trend_delta > 0
             AND trend_window_hours IS NOT NULL
             AND trend_window_hours > 0
             AND trend_direction IN ('RISE', 'FALL')));

-- 非趋势级不能有趋势字段
ALTER TABLE m08_vital_threshold
  ADD CONSTRAINT ck_m08_threshold_non_trend
  CHECK (level = 'TREND'
         OR (trend_delta IS NULL AND trend_window_hours IS NULL
             AND trend_direction IS NULL));

-- 版本号正数
ALTER TABLE m08_vital_threshold
  ADD CONSTRAINT ck_m08_threshold_version
  CHECK (version >= 1);

-- 使用 COALESCE 的唯一索引（PG 认为 NULL 互不相等）
CREATE UNIQUE INDEX uk_m08_threshold_key
  ON m08_vital_threshold (vital_code, level, scope, COALESCE(scope_id, 0))
  WHERE is_deleted = FALSE;

COMMENT ON TABLE m08_vital_threshold IS 'M08-04 体征阈值配置，病区级覆盖医院级';
COMMENT ON COLUMN m08_vital_threshold.high_value IS '高值阈值，值 >= high_value 时触发该级别告警';
COMMENT ON COLUMN m08_vital_threshold.low_value IS '低值阈值，值 <= low_value 时触发该级别告警';
COMMENT ON COLUMN m08_vital_threshold.trend_delta IS '趋势变化幅度，如 4 小时内体温上升 1.5℃';
COMMENT ON COLUMN m08_vital_threshold.version IS '版本号，每次修改递增，用于缓存失效与变更审计';
```

**为什么用 `COALESCE(scope_id, 0)` 而不是 `NULLS NOT DISTINCT`：**

PostgreSQL 15 引入了 `NULLS NOT DISTINCT` 语法，可以直接让唯一索引把 NULL 视为相等。但本项目目标环境包含 PG 14（部分医院还在用），且 `NULLS NOT DISTINCT` 在建索引语法与后续迁移上兼容性更差。`COALESCE(scope_id, 0)` 在所有版本都可用，且 0 不是合法的病区 ID，无冲突风险。

**状态机：**

```
      DRAFT（草稿）
        │
        │ 提交并签名（校验完整性）
        ▼
      SIGNED（已签名，终态）
        │
        │ 护士长作废（原因 ≥10 字）
        ▼
      VOIDED（已作废，终态）
```

**设计要点：**

1. **`DRAFT` 与 `SIGNED` 分离。**
   草稿可反复修改（护士可能中途被打断），签名后不可改。若只有「已保存」一种状态，无法区分「填了一半」与「正式完成」。

2. **`measures` 存 JSONB 数组而非关联表。**
   措施是「从建议清单里勾选 + 可能手填」的自由组合，数量 0~10 条，不需要独立查询或统计。存数组最简单。

3. **`next_due_at` 落库便于扫描。**
   「哪些患者该重评了」是每 2 小时跑一次的任务，若每次现算（读模板 triggers + 找最近一次评估 + 算下次时间）会很慢。落库后一条 `WHERE next_due_at <= NOW()` 走部分索引，稳态只有几十行。

4. **`void_of_assessment_id` 形成作废链。**
   签名后发现填错，作废后重建，新记录指向旧记录，可追溯。

| `selected_option` | VARCHAR(256) | 是 | NULL | 选中的选项标签 |

| `weight` | NUMERIC(6,3) | 是 | NULL | 项权重 |
| `text_value` | VARCHAR(500) | 是 | NULL | 文本类评估项的值 |
| `remark` | VARCHAR(500) | 是 | NULL | 项备注 |
| `sort_no` | SMALLINT | 否 | 1 | 显示顺序 |
| `created_at` | TIMESTAMP | 否 | NOW() | 创建时间 |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m08_assess_item` | 主键 | `id` | — |
| `uk_m08_assess_item_code` | 唯一 | `(assessment_id, item_code)` | 同一次评估同一项唯一 |
| `idx_m08_assess_item_stat` | B-Tree | `(item_code, score)` | **按评估项统计阳性分布** |

**约束说明：**

```sql
-- 项目类型枚举
ALTER TABLE m08_assess_item
  ADD CONSTRAINT ck_m08_assess_item_type
  CHECK (item_type IS NULL
         OR item_type IN ('SINGLE', 'MULTI', 'NUMBER', 'TEXT'));

-- 权重必须正数
ALTER TABLE m08_assess_item
  ADD CONSTRAINT ck_m08_assess_item_weight
  CHECK (weight IS NULL OR weight > 0);

-- 排序号正数
ALTER TABLE m08_assess_item
  ADD CONSTRAINT ck_m08_assess_item_sort
  CHECK (sort_no > 0);

-- 文本项必须有 text_value
ALTER TABLE m08_assess_item
  ADD CONSTRAINT ck_m08_assess_item_text
  CHECK (item_type <> 'TEXT' OR text_value IS NOT NULL);

COMMENT ON TABLE m08_assess_item IS 'M08-04 评估明细，逐项得分';
COMMENT ON COLUMN m08_assess_item.selected_option IS '选中的选项标签文本，便于直接展示与统计';
COMMENT ON COLUMN m08_assess_item.score IS '该项原始得分（未乘权重）';
COMMENT ON COLUMN m08_assess_item.weight IS '项权重，WEIGHTED 计分方式使用';
```

**设计要点：**

1. **为什么要存 `selected_option`（标签文本）而不只存选项索引。**
   模板升级后选项顺序可能变化（比如新增一个选项插在中间），只存索引会指错。存标签文本虽然冗余，但语义稳定。这也让「统计有多少患者『近三个月有跌倒史』」这类查询直接 `WHERE item_code='FALL_HISTORY' AND selected_option='有'`。

2. **为什么存 `score` 与 `weight` 分开而不是只存加权后得分。**
   模板升级后权重可能调整。历史记录要能「按当时权重」复算，也要能「按当前权重」重新评估（用于敏感性分析）。两者都存才能都做。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 每次评估平均项数 | 5.5 |
| 年明细行 | 180,675 |
| 单行长度 | 约 200 字节 |
| 年数据量 | 约 36 MB |
| 15 年累计 | 约 271 万行 / 540 MB |

**分区：** 不分区。
