## 4. 数据结构设计

### 4.1 ER 关系图

**设计说明：**

1. **无物理外键。** 遵循 M16 全局策略。

2. **`m16_refund_order` 是退费唯一主表。** 所有退费（门诊/住院/视光/退号）共用这一张表，用 `scene` 区分。这保证了「本月退了多少」只查一张表。

3. **`red_invoice_id` / `red_refund_order_id` 与 M16-05 / M16-07 是逻辑引用。** 退费单要知道「票红冲了哪张」和「钱从哪个渠道流水退回」，但存 ID 而非外键。

4. **`m16_refund_step` 是执行链路快照。** 六步链路每步一行，记录状态、耗时、详情。这是排查「为什么这笔退款卡住了」的第一手材料。

5. **`m16_refund_compensation` 是通用补偿队列。** 上游回写、会员权益、结算单回滚失败都进这里，用 `step_code` 区分。统一重试逻辑。

6. **`m16_refund_risk` 按日聚合。** 不是每次退费都插一条，而是每日扫描后按「规则 × 患者/收费员 × 日期」记录一条命中。索引小、查询快。

7. **分区策略。** `m16_refund_order` 与 `m16_refund_log` 按年 RANGE 分区，但**主表不分区**——理由同 M16-07：退费单是资金凭证，需要跨年唯一性与可追溯性。`m16_refund_log` 按月分区，热数据 180 天。

**两条资金安全约束的设计动机**

**`ck_m16_refund_cumulative` —— 累计退费不超过净额**

```
refunded_before + refund_amount <= net_amount
```

这是防止「退多了」的最后一道防线。服务层虽然每次都校验，但并发场景下两个请求可能同时读到相同的 `refunded_before`，都判定通过。数据库约束保证了即使应用层出 bug，也不可能多退钱。

**`uk_m16_refund_pay_no` —— 一笔资金退款只对应一个退费单**

M16-05 的 `m16_refund` 是资金层退款单。如果两个退费单指向同一个资金退款单，意味着「退了一次钱却记了两笔退费」，账上会凭空多出退款。这个唯一索引把它彻底堵死。

**状态机**

```
DRAFT ──► PENDING_APPROVAL ──► APPROVED ──► EXECUTING ──► SUCCESS

  │              ▼                              ├──► FAILED ──► EXECUTING
  │           REJECTED                          │
  ▼                                             └──► ABNORMAL ──► SUCCESS（人工）
CANCELLED
```

**尾差修正的必要性示例**

结算明细：阿托品滴眼液 45.00 × 3 = 135.00，优惠分摊 27.00，净额 108.00。

分三次各退 1 支：

| 次 | 计算 | 金额 |
|---|---|---|
| 1 | ROUND(108 × 1/3, 2) = ROUND(36.00) | 36.00 |
| 2 | ROUND(108 × 1/3, 2) = ROUND(36.00) | 36.00 |
| 3 | 36.00（按比例） | 36.00 |
| **合计** | | **108.00** ✅ |

若净额为 100.00：

| 次 | 计算 | 金额 |
|---|---|---|
| 1 | ROUND(33.333... , 2) | 33.33 |
| 2 | ROUND(33.333... , 2) | 33.33 |
| 3 | ROUND(33.333... , 2) | 33.33 |
| **合计** | | **99.99** ❌ 差 1 分 |

第 3 次用尾差修正：`refund_amount = 100.00 − 33.33 − 33.33 = 33.34`，合计 100.00 ✅

```sql
-- 步骤状态枚举
ALTER TABLE m16_refund_step
    ADD CONSTRAINT ck_m16_refund_step_status
    CHECK (status IN ('SUCCESS', 'FAILED', 'SKIPPED', 'QUEUED',
                      'RUNNING'));

-- 步骤代码枚举
ALTER TABLE m16_refund_step
    ADD CONSTRAINT ck_m16_refund_step_code
    CHECK (step_code IN ('RECALC', 'RED_FLUSH', 'PAY_REFUND',
                         'SETTLE_ROLLBACK', 'UPSTREAM_WRITEBACK',
                         'MEMBER_REVERT'));

-- 序号 1~6
ALTER TABLE m16_refund_step
    ADD CONSTRAINT ck_m16_refund_step_seq
    CHECK (seq >= 1 AND seq <= 6);

-- 尝试次数正数有界
ALTER TABLE m16_refund_step
    ADD CONSTRAINT ck_m16_refund_step_attempt
    CHECK (attempt_no >= 1 AND attempt_no <= 11);

-- 失败必须有错误信息
ALTER TABLE m16_refund_step
    ADD CONSTRAINT ck_m16_refund_step_fail
    CHECK (status <> 'FAILED'
        OR (error_code IS NOT NULL AND error_message IS NOT NULL));

-- 非 RUNNING 必须有结束时间
ALTER TABLE m16_refund_step
    ADD CONSTRAINT ck_m16_refund_step_finished
    CHECK (status = 'RUNNING' OR finished_at IS NOT NULL);

-- 耗时非负
ALTER TABLE m16_refund_step
    ADD CONSTRAINT ck_m16_refund_step_elapsed
    CHECK (elapsed_ms IS NULL OR elapsed_ms >= 0);

COMMENT ON TABLE m16_refund_step IS '退费执行步骤：六步链路每步一行，重试时 attempt_no 递增';
COMMENT ON COLUMN m16_refund_step.attempt_no IS '第几次执行尝试；重试一次整条链路的步骤全部重记一遍，便于对比差异';
COMMENT ON COLUMN m16_refund_step.target_ref IS '该步写入目标系统的引用：红票号 / 渠道退款流水号 / 上游单号';
```

**为什么重试要整套重记而不是更新原行**

如果更新原行，就丢掉了「第一次为什么失败」的信息。资金链路排查时，往往要对比「第一次红冲失败是因为税控超时，第二次成功」这类模式。保留每次尝试的全部步骤，是排查成本最低的做法。

| 每单步骤数 | 6 |
| 年行数 | 约 144,000 |
| 单行大小 | 约 350 B |
| 年数据量 | 约 50 MB |

**分区：** 按 `started_at` 年度分区，保留 3 年（超过 3 年的执行链路已无排查价值，由 `m16_refund_log` 顶替）。

**`idx_m16_refund_executing` 的作用**

退费单进入 `EXECUTING` 后若进程崩溃（部署重启、OOM），状态会永久卡住。没有这个索引，「找出所有卡住的单」需要全表扫描。有了它，扫描任务只需 5 毫秒：

```sql
SELECT id, refund_no, executing_at
  FROM m16_refund_order
 WHERE status = 'EXECUTING'
   AND executing_at <= NOW() - INTERVAL '10 minutes';
```

命中的单由运维确认后置 `FAILED` 重试，或置 `ABNORMAL` 人工处理。

**序列定义**

```sql
CREATE SEQUENCE seq_m16_refund_no
    START WITH 1
    INCREMENT BY 1
    NO MINVALUE
    NO MAXVALUE
    CACHE 20 CYCLE;

COMMENT ON SEQUENCE seq_m16_refund_no
    IS '退费单号日序号；取模 10000 后拼接日期，循环使用';
```

> `CACHE 20` 是权衡：缓存太小，高并发取号会有序列锁竞争；缓存太大，重启会浪费最多 20 个号。日退费约 90 笔，20 个缓存绰绰有余。`CYCLE` 让序号在 10000 后回绕——配合日期的 YYMMDD 前缀，重复要等到 27 年后，实际不可能冲突。

| `m16_refund_log` | 永久 | 按月分区，热 6 个月，其余冷存 |
| `m16_refund_risk` | 5 年 | 定期 DELETE |
