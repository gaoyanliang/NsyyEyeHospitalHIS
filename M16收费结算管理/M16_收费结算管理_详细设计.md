## 1. 模块概述

### 1.1 模块定位

M16 收费结算管理负责「**患者为医疗服务付的每一分钱，从计算到收讫到入账的全过程**」。

```
                    ┌─────────────────────────────────────┐
                    │         业务发生（其他模块）          │
                    │  M04 挂号  M07 医嘱  M05 住院  M10 视光 │
                    └─────────────────┬───────────────────┘
                                      │ 需要收钱
                                      ▼
     ┌──────────────────────────────────────────────────────────┐
     │                  M16 收费结算管理                          │
     │                                                            │
     │  ①算钱            ②收钱           ③给凭证      ④交账      │
     │  ┌─────────┐    ┌─────────┐    ┌─────────┐  ┌─────────┐  │
```

**一句话定义：** M16 是医院与患者之间资金关系的唯一权威记录者。

### 1.2 为什么 M16 是「模块」而不是「功能」

HIS 里最容易做错的一件事，是把收费当成其他模块的一个附属功能——挂号模块里加个「收费」按钮，医嘱模块里加个「缴费」按钮。这条路走不通，原因是：

**第一，收费对象不唯一。** 挂号要收费、医嘱要收费、住院要收预交金、视光要卖眼镜、体检要收费。如果每个业务模块自己写收费，会得到 5 套不同的支付对接、5 套不同的退费逻辑、5 套不同的发票打印。

**第二，钱的计算有唯一答案。** 同一个检查项目，门诊收 320 元，住院收 320 元，视光搭配销售可能收 288 元。如果三个模块各自算，同一项目在三个地方算出三个价格，患者会投诉，财务会对不上账。

**第三，资金必须闭环。** 收了钱要有支付流水、有发票、有日结。这三个环节跨越多个业务场景。如果分散，没有人能回答「今天医院收了多少现金」这个最基本的问题。

**第四，对账与审计的强制性。** 医院对账是法规要求，不是可选项。它必须有一个统一的落点。

### 1.3 模块目标

| 编号 | 目标 | 指标 |
|---|---|---|
| G-01 | 收费金额准确率 | 100%（不接受任何金额差错） |
| G-02 | 收费操作效率 | 单次收费 P95 ≤ 3 秒（含扫码） |
| G-03 | 支付成功率 | ≥ 99.5%（渠道正常时） |
| G-04 | 日结对账及时率 | 次日前完成率 ≥ 99% |
| G-05 | 对账差异率 | ≤ 0.05% |
| G-06 | 退费可追溯率 | 100%（每一分退出去的钱都能说明白） |
| G-07 | 发票合规率 | 100%（无虚开、无重复开） |
| G-08 | 资金数据可审计 | 全链路留痕，任一笔可下钻 |

## 2. 子模块划分

### 2.1 九个模块的划分逻辑

M16 的核心矛盾是「**算钱**」与「**收钱**」必须分开：

- **算钱**是纯计算，可重算、可回滚、无副作用。同一份项目清单算 100 遍结果必须一样。
- **收钱**有外部副作用，不可重放。支付一次就是支付一次，重放就是重复扣款。

把这两件事混在一个模块里，代码会出现大量「先算后付、付完发现算错」的补救逻辑。分开之后，算钱模块可以在任何时刻重算，收钱模块只需要保证「这笔钱到底收没收到」。

在此基础上，剩下的划分遵循「**场景外壳 vs 共享内核**」：

- 门诊、住院、视光是三个**场景外壳**，它们各自的业务单据不同，但都用同一套计费引擎和支付网关。
- 优惠、退费、发票、日结是**横切能力**——每个场景都要用，且有各自的审批流和状态机。

### 2.4 子模块依赖顺序

```
                       M16-01 结算单与计费引擎
                       （基座：没有结算单什么都做不了）
                              │
        ┌──────────┬──────────┼──────────┬──────────┐
        ▼          ▼          ▼          ▼          ▼
    M16-02     M16-03     M16-04     M16-06    M16-05
    门诊收费   住院结算   视光销售   优惠折扣  支付收单
        │          │          │          │          │
        └──────────┴──────────┴──────────┴──────────┘
                              │
                              ▼
                        M16-07 发票票据
                              │
                              ▼
                        M16-08 退费冲红
                     （需要前面所有的能力）
                              │
                              ▼
                        M16-09 日结对账
                     （需要所有流水都产生完）
```

**为什么 M16-05 在这么后面**

支付看起来是底层能力，应该最先做。但 M16-05 的支付单需要关联结算单（`settlement_ids`），而结算单由 M16-01 产生。所以 M16-05 只能在 M16-01 之后。M16-02/03/04 这三个「收钱场景」都依赖 M16-05 的支付能力，但它们的详细设计可以先写，实现时要等 M16-05。

**为什么 M16-08 在 M16-07 之后**

退费必须联动红冲发票。如果 M16-07 没做完，M16-08 执行退费时只能跳过红冲——而「钱退了票不红」正是最大的税务风险点。所以 M16-08 必须等 M16-07 完成。

### 2.5 实现优先级

| 优先级 | 子模块 | 理由 |
|---|---|---|
| P0 | M16-01, M16-05, M16-02 | 没有这三块，全院的收费跑不起来 |
| P0 | M16-07 | 没发票不能对外营业 |
| P1 | M16-08, M16-06 | 退费与优惠是高频业务，但可以先用简单版 |
| P1 | M16-09 | 日结是财务刚需 |
| P2 | M16-04 | 视光可以先用 M16-02 的通用收费顶一阵 |
| P3 | M16-03 | 等 M05 住院管理完成 |

## 3. 核心业务模型

### 3.1 一次收费的完整链路

```
   患者要做的服务
        │
        ▼
 ①业务模块产生单据（挂号单 / 医嘱 / 住院费用 / 视光订单）
        │
        ▼
 ②M16-01 生成结算单
    - 拉取价格（M01-06 价格表）
    - 按项目类型算数量（眼别 × 2 等）
    - 记录价格快照
    - 计算总额 = Σ 行金额（行级先舍入）
        │
        ▼
 ③M16-06 应用优惠
    - 查会员等级折扣
    - 查可用优惠方案
    - 计算最优组合
    - 超阈值走审批
    - 得到应收 = 总额 − 优惠
        │
        ▼
 ④M16-05 发起支付
    - 选渠道（现金/微信/支付宝/POS/储值）
    - 建支付单
    - 调渠道下单
    - 等回调 / 主动查询
        │
        ▼
 ⑤支付成功确认
    - 验签
    - 幂等校验
    - 状态机置 SUCCESS
        │
        ├──► ⑥M16-01 结算单置 PAID
        │    └──► 回写上游业务单据置 PAID
        │
        ├──► ⑦M16-07 开票
        │
        └──► ⑧M16-09 资金事务上报
             └──► 计入当日日结
```

**关键顺序：先确认钱到了，再动业务单据。**

如果反了（先置业务单据为已缴费再去确认支付），支付失败时业务单据已经是「已缴费」状态，患者没付钱就能做检查——这是真实的漏洞。

### 3.2 金额的三个层次

```
┌─────────────────────────────────────────────────────┐
│ 原价 total_amount                                    │
│   行金额 = ROUND(单价 × 数量 × 眼别倍数, 2) 逐行求   │
│   总额 = Σ 行金额                                     │
└──────────────────────┬──────────────────────────────┘
                       │ − 优惠
                       ▼
┌─────────────────────────────────────────────────────┐
│ 应收费 payable_amount = total − discount             │
│   行级先舍入再累加：否则明细多时误差累积几毛钱        │
└──────────────────────┬──────────────────────────────┘
                       │ 实收
                       ▼
┌─────────────────────────────────────────────────────┐
│ 实付 paid_amount                                     │
│   可能分多笔支付（混合支付最多 3 笔）                 │
│   实付 = Σ 各笔支付成功金额                           │
└─────────────────────────────────────────────────────┘
```

**为什么必须「行级先舍入再累加」**

假设 3 个项目，单价比例如 0.005、0.005、0.005：

- 先累加后舍入：`ROUND(0.005 × 3, 2) = ROUND(0.015, 2) = 0.02`
- 先舍入后累加：`0.01 + 0.01 + 0.01 = 0.03`

差 0.01 元，看不出问题。但当明细有 30 行、每行都需要按比例分摊优惠时，「先累加后舍入」会让各行的实收之和与结算单总额差几毛钱。退费按行退时，这几毛钱就永远对不上账。

医院的通用做法是：**每一行都是独立可退的金额单位，所以每一行独立舍入。**

### 3.3 医嘱与结算单的关系

```
    一次就诊可以产生多个结算单
    ┌──────────────────────────────────┐
    │ 就诊 E001（患者张伟）             │
    │                                    │
    │  结算单 S001  挂号费 20 元  PAID   │
    │  结算单 S002  检查费 320 元  PAID  │
    │  结算单 S003  药费  180 元  ISSUED │
    └──────────────────────────────────┘
```

**为什么一单一结，不合并成「账单」**

有人会想：一次就诊所有费用合成一张账单，患者一次性付清多方便。但这带来三个问题：

1. **退费算不清。** 账单里 500 元，退了其中 120 元的检查，「剩余应退」怎么在账面上体现？
2. **发票开不出。** 税务要求发票明细对应实际项目。合并账单会把项目明细藏在一层之后。
3. **状态不一致。** 账单里 3 个医嘱，2 个已执行 1 个取消，账单状态该是什么？

一单一结的代价是患者可能要付几次钱（挂号一次、检查一次、拿药一次），这正好符合门诊的实际动线：先挂号、看了医生再开检查、看完结果再开药。用自助机、手机支付完全可以消除排队体验问题。

### 3.4 支付单状态机

```
        ┌─────────┐
        │ CREATED │  刚建单，还没调渠道
        └────┬────┘
             │ 调渠道下单成功
             ▼
        ┌─────────┐
        │ PAYING  │  已下单，等结果
        └──┬───┬──┘
           │   │
   回调成功│   │回调失败/超时/关单
           │   │
           ▼   ├──────────► FAILED / EXPIRED / CLOSED
      ┌────────┐ │
      │SUCCESS │ │ 主动查询也无结果
      └────────┘ ▼
                ┌─────────┐
                │ UNKNOWN │ 不知道钱有没有扣
                └────┬────┘
                     │ 查单/对账/人工确认
                     ▼
                 SUCCESS 或 FAILED
```

**`SUCCESS` 是终态，任何操作不能改回。**

这是资金系统的铁律。哪怕后续发现是错收，也只能走退费（产生一笔反向流水），不能把原支付改回失败。如果允许改，支付流水的审计价值就没了，对账也无从谈起。

**`UNKNOWN` 状态为什么必须有**

真实世界存在这个窗口：渠道已经扣了钱，但回调没到，主动查询也超时。此时：

- 标 `SUCCESS` 可能错（也许渠道没扣成功）
- 标 `FAILED` 也可能错（也许扣了），而且会把结算单置成未支付

两个都错，所以必须有第三个状态。`UNKNOWN` 意味着「有人得去查」，进人工/对账流程。

**三层幂等**

| 层 | 机制 | 作用于 |
|---|---|---|
| L1 | Redis `m16:pay:idem:{key}` TTL 86400 | 短时间重复提交 |
| L2 | DB 部分唯一索引 `uk_m16_payment_idem` | 长时间重复提交 |
| L3 | 业务状态比对（已 SUCCESS 且金额相同则返回成功） | 回调重放 |

### 3.5 退费的净额原则

**退给患者的 = 实付净额，不是项目原价。**

```
检查项目原价 800 元
会员 8 折 → 实收 640 元

退这项检查 → 退 640 元，不是 800 元
```

这听起来理所当然，但实际系统经常算错。原因在于结算单只记了总额与优惠总额，没记「每个项目分摊了多少优惠」。本模块的做法：

```
行净额 line_net = 行原价 − 行优惠分摊
行优惠分摊 = 总优惠 × (行可优惠基数 / 可优惠基数合计)
```

分母是**可优惠基数**（`allow_discount=TRUE` 且非赠送、非红冲的行），不是结算单总额。因为不可优惠的项目（比如挂号费如果设为不打折）不该分担其他项目的优惠。

**尾差修正**：分次退时，最后一次退全额。

```
100 元分 3 次退：33.33 + 33.33 + 33.34 = 100.00
最后一次 = 行净额 − 已退金额
```

### 3.6 日结的层级模型

```
L4 全院日结      1 条/日     ← 财务记账依据
   ▲
   │ 汇总
L3 科室日结      ~12 条/日   ← 科室核算依据
   ▲
   │ 汇总
L2 收费点日结    ~6 条/日    ← 窗口对账依据
   ▲
   │ 汇总
L1 交班          ~24 条/日   ← 追责到人
   ▲
   │ 引用
L0 资金流水      ~1,400 条/日
```

**核心恒等式**

```
全院净收入 = Σ 各收费点净收入 = Σ 各科室收入
           = Σ 各支付方式净收入 = Σ 各业务类型收入
```

四个维度切的是同一批流水，结果必须完全相等（不是「接近」）。任何不等都是数据问题。日结每次生成都跑这个自检。

### 3.7 封账的语义

封账 = 把某天的数据冻结成不可修改。

**为什么必须有封账**

如果没有封账，10-21 的日结在 11 月还可能因为一笔补录而改变，那财务 10 月底出的报表就永远不能定稿。封账给了财务一个「可以宣布这个数字是最终版」的机制。

**封账的影响范围**

| 对象 | 封账后 |
|---|---|
| 该日日结 | 不可重算 |
| 该日支付流水 | 不可补单/撤销 |
| 该日退费单 | 不可执行 |
| 该日结算单 | 不可修改 |
| 该日班次 | 不可再开关班 |

**解封必须走审批。** 解封原因 ≥ 20 字 + 财务总监批准 + 记录次数。同一日结解封超过 2 次自动进入审计清单。

### 4.3 分区策略

| 表 | 分区 | 保留 |
|---|---|---|
| `m16_settlement` | 按 `settle_date` 年度 | 15 年 |
| `m16_payment` | **不分区** | — |
| `m16_payment_trace` | 按 `created_at` 月度 | 热 180 天 |
| `m16_deposit` | 按 `created_at` 年度 | 15 年 |
| `m16_inpatient_charge` | 按 `charge_date` 年度 | 15 年 |
| `m16_discount_apply` | 按 `settle_date` 年度 | 15 年 |
| `m16_refund_order` | **不分区** | — |
| `m16_daily_close` | 按 `close_date` 年度 | 15 年 |
| `m16_daily_transaction` | 按 `occurred_at` 月度 | 2 年 |

**`m16_payment` 与 `m16_refund_order` 为什么不分区的理由相同：**

资金凭证的跨年唯一性比查询性能更重要。如果按 `created_at` 分区，唯一索引必须包含分区键：

```sql
-- 分区后被迫这样写
CREATE UNIQUE INDEX uk_m16_payment_txn
    ON m16_payment (transaction_no, created_at);
```

这导致同一个 `transaction_no` 在不同年份可以重复——渠道交易号跨年重复的概率虽然低，但一旦发生，就是「两个人付了同一笔钱却被识别为一笔」的资金事故。

替代方案是「不分区 + 归档」：热数据 3 年留在主表，超期移入 `m16_payment_archive`。归档表不参与业务查询，只用于历史追溯。

### 4.4 金额统一规范

| 规范 | 内容 |
|---|---|
| 类型 | 一律 `NUMERIC`，**禁止 `FLOAT`/`DOUBLE`** |
| 单价精度 | `NUMERIC(12,4)`（药品按每片 0.0250 计价） |
| 金额精度 | `NUMERIC(12,2)` 或 `NUMERIC(14,2)` |
| 税率 | `NUMERIC(7,4)` 存百分比（13.0000 = 13%） |
| 折扣率 | `NUMERIC(5,4)` 存小数比率（0.8000 = 8 折） |
| JSONB 内金额 | **一律存字符串**（如 `"133660.00"`） |

**税率与折扣率语义不同的原因**

税率是税法表达，税务局写「13%」；折扣率是商业表达，商家说「8 折」。系统里照搬各自的习惯，减少人工转换错误。这一点在字段注释里必须写清楚，否则后来的开发一定会搞混。

### 5.3 页面设计的三条原则

**原则一：金额永远在右上角，用大字号。**

收费员每天看几百次金额。如果金额藏在表格里，会看错。所有涉及收款的页面，应收金额固定在右上角，字号 ≥ 24px。

**原则二：所有可点击的数字都能下钻。**

日结显示「微信 ¥179,620.00」，点一下能看到这 1,204 笔明细。这是所有财务系统的底线要求——如果一个数不能下钻，它就不能被信任。

**原则三：危险操作需要二次确认，且确认文字是具体的。**

封账的确认不是「确定吗？」，而是要求输入「确认封账」四个字。解封要求输入「确认解封」。批量退费要求输入退费总额。这样即使误触也不会造成事故。

**回写失败的补偿机制**

回写是付款成功后的动作，如果回写失败：

1. **不回滚支付**（钱已经收了，不能因为回写失败就退回）
2. 写入 `m16_rewrite_queue`
3. Celery 每 2 分钟重试，指数退避 2^n 分钟，上限 512 分钟
4. 重试 10 次仍失败 → 标 `FAILED` + 告警 + 人工处理

这个设计的原则是：**支付成功是既成事实，业务回写可以晚到，但不能丢。**

**为什么 API 与 Worker 分开部署**

支付回调的高峰是瞬时的（比如集中缴费时段），此时 API 需要大量并发处理 HTTP 请求。如果 Worker 与 API 混部，一个跑导出报表的 Worker 会把 CPU 吃满，导致回调超时——而回调超时会导致支付状态变 UNKNOWN。

## 8. 全局业务规则

### 8.1 金额计算的六条铁律

| 编号 | 规则 | 理由 |
|---|---|---|
| R-A1 | 金额全部用 `Decimal`，禁止 `float` | 浮点误差在财务上是不可接受的 |
| R-A2 | 金额保存 2 位小数，四舍五入用 `ROUND_HALF_UP` | 与银行/税务口径一致 |
| R-A3 | 行级先舍入再累加 | 保证每行可独立退费 |
| R-A4 | 前端传的金额一律忽略，后端重算 | 防止篡改 |
| R-A5 | 价格以快照为准，不实时查价 | 保证历史可追溯 |
| R-A6 | 金额变化必须留快照与日志 | 审计要求 |

### 8.2 状态机铁律

| 编号 | 规则 |
|---|---|
| R-S1 | `SUCCESS` 是终态，不可逆 |
| R-S2 | 状态只能按状态机流转，非法流转一律报错 |
| R-S3 | 每次状态变更必须记录 `old_status` / `new_status` / 操作人 / 时间 |
| R-S4 | 跨模块状态变更只能由权责方触发（M16 不改医嘱状态，只回写请求） |
| R-S5 | 并发修改用乐观锁（`version`）或行锁（`FOR UPDATE`） |

### 8.3 幂等铁律

| 场景 | 幂等键 |
|---|---|
| 结算单创建 | `(source_type, source_id)` |
| 支付创建 | `idempotency_key` = `{渠道}:{收费员}:{结算单号哈希}:{金额}` |
| 支付回调 | `payment_no` + `transaction_no` |
| 退费申请 | `(settlement_id, idempotency_key)` |
| 住院费用记账 | `(source_type, source_id)` |
| 发票开具 | `(settlement_id, invoice_type, is_red)` |
| 日结生成 | `(close_date, close_level, scope_id)` |
| 资金事务上报 | `transaction_id` |

**幂等键必须包含金额的理由**

用 `{收费员}:{结算单}` 做键，混合支付时第二笔就被误判为重复。加上金额后，同一个人对同一结算单支付两次相同金额才被拒——而这种情况本来就是重复支付，应该拒。

### 8.4 审计铁律

| 编号 | 规则 |
|---|---|
| R-U1 | 所有资金动作必须留痕，含失败动作 |
| R-U2 | 日志表只读，禁止 UPDATE/DELETE（用触发器强制） |
| R-U3 | 快照表只增不改 |
| R-U4 | 关键操作记录 IP 与 UA |
| R-U5 | 审计日志独立保留 7 年（M02） |

### 8.5 职责分离铁律

| 编号 | 规则 |
|---|---|
| R-D1 | 申请人 ≠ 审批人（DB 约束 + 服务层双校验） |
| R-D2 | 修改支付配置的人不能操作资金；操作资金的人不能改配置 |
| R-D3 | 收费员不能审核自己的交班 |
| R-D4 | 财务主管不能独自解封日结（需总监） |
| R-D5 | IT 管理员不能修改优惠方案 |

## 10. 异常与降级策略

### 10.1 降级原则

**先收上钱比优惠准确更重要，但资金准确性不能降级。**

| 场景 | 依赖 | 策略 | 理由 |
|---|---|---|---|
| 优惠方案查询超时 | M01-06 | 按原价算，标 `discount_degraded=TRUE` | 多收钱可以事后补录，收不上钱是事故 |
| 会员等级查询超时 | M03-03 | 按普通患者算 | 同上 |
| 最优组合计算超时（>500ms） | 内部 | 只应用会员折扣 | 让收费员先能收钱 |
| 审批服务不可用 | M01-11 | **不降级**，拒绝超阈值折扣 | 无审批的折扣是腐败风险 |
| 渠道账单缺失 | M16-05 | 只做现金对账，次日补 | 账账核对可以晚 |
| 红冲失败 | M16-07 | **阻断整笔退费** | 钱退了票不红是税务风险 |
| 科室名称查询失败 | M01-01 | 显示科室 ID | 少一列不影响核对总额 |
| 现金/退款数据缺失 | 内部 | **阻断日结** | 现金少了就是少了 |

**降级后的补录机制**

优惠降级后，24 小时内可调 `POST /internal/v1/m16/discount/supplement` 补录，修正账务但不改已收金额，差额走「优惠补记」科目。

### 10.2 异常分类

| 类别 | 示例 | HTTP | 处理 |
|---|---|---|---|
| 参数错误 | 金额非法、必填缺失 | 400 | 直接返回 |
| 状态错误 | 结算单已付再付 | 409 | 直接返回 |
| 权限错误 | 越权审批 | 403 | 直接返回 |
| 业务冲突 | 重复开票、券已被用 | 409 | 直接返回 |
| 外部超时 | 渠道超时 | 504 | 重试或进 UNKNOWN |
| 幂等命中 | 重复提交 | 200 | 返回首次结果 |
| 系统错误 | DB 异常 | 500 | 记录 trace_id |

### 10.3 重试策略

| 操作 | 重试次数 | 间隔 |
|---|---|---|
| 上游回写 | 10 | 2^n 分钟，上限 512 |
| 支付主动查询 | 10 | 60 秒（1~5 次）/ 5 分钟（6~10 次） |
| 退款执行 | 3 | 1 / 5 / 15 分钟 |
| 红冲 | 3 | 5 / 30 / 120 秒 |
| 日结生成 | 3 | 60 秒 |

**支付主动查询为什么前 5 次间隔短**

用户就在窗口等着。60 秒的查询间隔意味着最长等待 60 秒出结果。超过 5 次说明这个支付大概率需要人工介入，转 5 分钟检查一次即可。

**离线收费的取舍**

断网时允许收费并暂存本地，联网后同步。风险是「同一个人在断网期间被收了两次费」——所以离线收费必须限制：

- 只能现金（无法验证扫码）
- 单笔 ≤ 500 元
- 单机累计 ≤ 20,000 元
- 联网后逐笔同步，冲突标记人工处理
