## 4. 数据结构设计

### 4.1 ER 关系图

```
┌──────────────────────────────────┐
│ m16_settlement（M16-01）          │
│ settlement_no / total_amount     │
│ discount_amount / payable_amount │
└───────────┬──────────────────────┘
            │ 1:N（settlement_id）
            ▼
┌─────────────────────────────────────────────────┐        ┌────────────────────────────┐
│ m16_discount_apply                              │  1 : N │ m16_discount_item          │
│ 优惠应用明细（一个方案 × 一张结算单 = 一行）      │◄───────┤ 优惠分摊到结算单明细行      │
│ settlement_no                                   │        │ apply_id                   │
│ policy_code / policy_type                       │        │ settlement_item_id         │
│ discount_rate / base_amount / reduce_amount ★   │        │ base_amount / reduce_amount│
│ status(ACTIVE/REVOKED)                          │        └────────────────────────────┘
│ voucher_code ──────────────────────────┐        │
└────────────────────────────────────────┘        │
            │ 0:1（voucher_code 逻辑关联）         │
            ▼                                     │
┌──────────────────────────────────┐              │
│ m16_discount_voucher             │              │
│ 权益券（券码唯一）                │              │
│ voucher_code (uk)                │              │
│ status(ISSUED/LOCKED/USED/...)   │              │
│ used_settlement_no ◄─────────────┘              │
└──────────────────────────────────┘              │
                                                  │
┌──────────────────────────────────┐              │
│ m16_discount_approval            │  审批完成后 ──┘
│ 折扣审批（手动折扣必须）          │  生成 apply
│ approval_no (uk)                 │
│ settlement_no / discount_rate    │
│ status(PENDING/APPROVED/...)     │
│ approval_chain JSONB             │
└──────────────────────────────────┘

┌──────────────────────────────────┐      ┌──────────────────────────────────┐
│ m16_discount_log                 │      │ m16_discount_daily               │
│ 执行日志（只读，按月分区）        │      │ 日汇总（日期 × 方案）             │
│ action / result / detail         │      │ apply_count / reduce_amount      │
└──────────────────────────────────┘      └──────────────────────────────────┘

┌──────────────────────────────────┐
│ m16_discount_config              │
│ 参数（14 行）                     │
└──────────────────────────────────┘
```

**设计说明：**

1. **无物理外键。** 遵循 M16 全局策略。优惠计算链路在高并发下需避免外键锁等待。

2. **`m16_discount_apply` 是核心表。** 一行代表「某张结算单应用了某个优惠方案」，是「少收了多少钱、依据什么、谁操作的」的唯一事实来源。

3. **为什么 apply 与 item 分两张表。** `apply` 回答「为什么少收」，`item` 回答「哪些项目少收了」。优惠按结算单总额计算（如满 200 减 30），但退费按项目退，必须知道每行分摊了多少优惠。两表 1:N 关系。

4. **`m16_discount_voucher` 与 `m16_discount_apply` 的关系。** 一张券最多核销一次，核销后通过 `voucher_code` 与 apply 关联。`used_settlement_no` 反向指回。

5. **`m16_discount_approval` 的位置。** 审批是「优惠发生前的许可」，通过后生成 `apply`。`approval_no` 与被批准的 `apply` 通过 `settlement_no` + `policy_code='MANUAL'` 关联。

6. **`m16_discount_log` 只读。** 触发器禁止 UPDATE/DELETE，保证审计链不可篡改。

7. **分区策略。** `m16_discount_apply` / `m16_discount_item` / `m16_discount_log` 按年 RANGE 分区，保留 15 年（与结算凭证一致）。

### 4.2 表：`m16_discount_apply`（优惠应用明细表）

**用途：** 记录每一张结算单上每一个生效的优惠方案。

| `apply_no` | VARCHAR(32) | N | — | 优惠流水号 `DA` + `YYYYMMDD` + 4 位 |
| `settlement_id` | BIGINT | N | — | 结算单 ID |
| `settlement_no` | VARCHAR(32) | N | — | 结算单号（冗余） |
| `settle_date` | DATE | N | — | 结算日期（冗余，用于分区与统计） |
| `patient_id` | BIGINT | Y | NULL | 患者 ID |

| `voucher_redeem` | BOOLEAN | N | FALSE | 是否消耗券 |
| `status` | VARCHAR(16) | N | `'ACTIVE'` | `ACTIVE` 生效 / `REVOKED` 已撤销 |
| `is_supplement` | BOOLEAN | N | FALSE | 是否降级补录 |

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m16_discount_apply` | PRIMARY KEY | `id` | — |
| `uk_m16_disc_apply_no` | UNIQUE | `apply_no` | 优惠流水号唯一 |

| `idx_m16_disc_apply_no` | BTREE | `settlement_no` | 按单号查 |
| `idx_m16_disc_apply_policy` | BTREE | `policy_code`, `applied_at` | 按方案统计 |

| `idx_m16_disc_apply_approval` | BTREE | `approval_id` WHERE `approval_id IS NOT NULL` | 按审批单反查 |

| `idx_m16_disc_apply_date` | BTREE | `settle_date`, `dept_id` | 报表查询 |

**约束说明**

```sql
-- 优惠类型枚举
ALTER TABLE m16_discount_apply
    ADD CONSTRAINT ck_m16_disc_apply_type
    CHECK (policy_type IN ('DISCOUNT', 'FULL_REDUCE', 'PACKAGE',
                           'GIFT', 'MEMBER', 'IDENTITY',
                           'MANUAL', 'SUPPLEMENT'));

-- 折扣模式枚举
ALTER TABLE m16_discount_apply
    ADD CONSTRAINT ck_m16_disc_apply_mode
    CHECK (discount_mode IN ('RATE_FIRST', 'REDUCE_FIRST'));

-- 状态枚举
ALTER TABLE m16_discount_apply
    ADD CONSTRAINT ck_m16_disc_apply_status
    CHECK (status IN ('ACTIVE', 'REVOKED'));

-- 金额非负且减免不超过基数
ALTER TABLE m16_discount_apply
    ADD CONSTRAINT ck_m16_disc_apply_amount
    CHECK (base_amount >= 0
           AND reduce_amount >= 0
           AND payable_after >= 0
           AND reduce_amount <= base_amount);

-- 应付 + 减免 = 基数
ALTER TABLE m16_discount_apply
    ADD CONSTRAINT ck_m16_disc_apply_balance
    CHECK (payable_after = base_amount - reduce_amount);

-- 折扣率合理区间
ALTER TABLE m16_discount_apply
    ADD CONSTRAINT ck_m16_disc_apply_rate
    CHECK (discount_rate IS NULL
           OR (discount_rate > 0 AND discount_rate < 1));

-- 比例折扣必须有折扣率
ALTER TABLE m16_discount_apply
    ADD CONSTRAINT ck_m16_disc_apply_rate_required
    CHECK (policy_type NOT IN ('DISCOUNT', 'MEMBER', 'IDENTITY')
           OR discount_rate IS NOT NULL);

-- 手动折扣必须有审批单（阈值内自动批的允许 approval_id 为空但需 operator 记录）
ALTER TABLE m16_discount_apply
    ADD CONSTRAINT ck_m16_disc_apply_manual
    CHECK (policy_type <> 'MANUAL'
           OR applied_by IS NOT NULL);

-- 撤销必须有时间与原因
ALTER TABLE m16_discount_apply
    ADD CONSTRAINT ck_m16_disc_apply_revoked
    CHECK (status <> 'REVOKED'
           OR (revoked_at IS NOT NULL AND revoked_reason IS NOT NULL));

-- 补录必须有原因
ALTER TABLE m16_discount_apply
    ADD CONSTRAINT ck_m16_disc_apply_supplement
    CHECK (is_supplement = FALSE OR supplement_reason IS NOT NULL);

-- 消耗券必须有序号
ALTER TABLE m16_discount_apply
    ADD CONSTRAINT ck_m16_disc_apply_voucher
    CHECK (voucher_redeem = FALSE OR voucher_code IS NOT NULL);

COMMENT ON TABLE m16_discount_apply IS '优惠应用明细：一张结算单上每个生效的优惠方案一行，是"为什么少收钱"的唯一凭证';
COMMENT ON COLUMN m16_discount_apply.reduce_amount IS '本方案减免额，核心金额字段';
COMMENT ON COLUMN m16_discount_apply.base_amount IS '可优惠基数，即参与优惠的明细金额合计';
COMMENT ON COLUMN m16_discount_apply.discount_mode IS 'RATE_FIRST 先折后减 / REDUCE_FIRST 先减后折，一张结算单只用一种';
COMMENT ON COLUMN m16_discount_apply.capped IS '是否因减免超过基数被截断，截断说明方案配置有问题';
COMMENT ON COLUMN m16_discount_apply.is_supplement IS '降级补录标识：收费高峰方案服务超时降级后的事后修正';
COMMENT ON COLUMN m16_discount_apply.policy_code IS '方案代码；手动折扣为 MANUAL，降级补录在 policy_type 中标记';
```

**状态机**

```
ACTIVE ──► REVOKED（结算单作废 / 人工撤销 / 退费全额回退）
```

> 只有两个状态。`ACTIVE → REVOKED` 单向，不可恢复。要恢复只能重新应用（会生成新行，`apply_no` 不同）。

**关键设计说明：`uk_m16_disc_apply_unique` 是防重复减免的最后防线**

应用层会先查「该结算单是否已有此方案」，但有三种情况会让检查失效：

1. 并发双击（两个请求同时通过检查）
2. 消息重放
3. 代码分支遗漏

如果没有唯一索引，一次双击会让患者多享受一次满减——医院白送 30 元，而且账上出现两条相同记录，对账时无法判断哪条是真的。

**量级估算**

| 项 | 量 |
|---|---|
| 日应用条数 | 约 350 条（含会员折扣） |
| 年行数 | 约 13 万行 |
| 单行大小 | 约 500 B |
| 年数据量 | 约 65 MB |
| 保留 15 年 | 约 1 GB |

**分区：** 按 `settle_date` 年度 RANGE 分区。

```sql
CREATE TABLE m16_discount_apply (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    settle_date DATE NOT NULL,
    -- 其余字段同上
    PRIMARY KEY (id, settle_date)
) PARTITION BY RANGE (settle_date);

CREATE TABLE m16_discount_apply_2026 PARTITION OF m16_discount_apply
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
CREATE TABLE m16_discount_apply_2027 PARTITION OF m16_discount_apply
    FOR VALUES FROM ('2027-01-01') TO ('2028-01-01');
```

> **分区与唯一索引：** `uk_m16_disc_apply_unique` 在分区表上须含 `settle_date`。但由于 `settle_date` 由 `settlement_id` 唯一决定（同一结算单不可能跨年），加上 `settlement_id` 本身单调递增，跨分区重复在实践中不可达。**仍建议不分区**，理由同 M16-05：审计凭证的完整性优先于查询性能。若必须分区，则加应用层 `SELECT ... FOR UPDATE` 兜底。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |

| 索引名 | 类型 | 字段 | 说明 |

**约束说明**

```sql
-- 金额非负
ALTER TABLE m16_discount_item
    ADD CONSTRAINT ck_m16_disc_item_amount
    CHECK (base_amount >= 0 AND reduce_amount >= 0 AND payable_amount >= 0);

-- 应付 = 基数 − 分摊
ALTER TABLE m16_discount_item
    ADD CONSTRAINT ck_m16_disc_item_balance
    CHECK (payable_amount = base_amount - reduce_amount);

-- 分摊不超过基数
ALTER TABLE m16_discount_item
    ADD CONSTRAINT ck_m16_disc_item_limit
    CHECK (reduce_amount <= base_amount);

COMMENT ON TABLE m16_discount_item IS '优惠分摊明细：把优惠额按行 base 比例分摊，供退费时按比例回退';
COMMENT ON COLUMN m16_discount_item.reduce_amount IS '该行分摊的优惠额，各行之和等于对应 apply.reduce_amount';
COMMENT ON COLUMN m16_discount_item.is_tail_adjust IS '尾差调整行：分摊后各行之和与总额的几分钱差额调到 base 最大的那一行';
```

**分摊算法与尾差**

```
share_i = ROUND(reduce_total × base_i / total_base, 2)
diff = reduce_total - Σ share_i
share[argmax(base_i)] += diff
```

**举例：** 总额 1,240，减免 154，三行 base 40 / 200 / 1000。

| 行 | base | 理论分摊 | 舍入后 | 尾差调整后 |
|---|---|---|---|---|
| 1 | 40 | 4.9677 | 4.97 | 4.97 |
| 2 | 200 | 24.8387 | 24.84 | 24.84 |
| 3 | 1000 | 124.1935 | 124.19 | **124.19** |
| 合计 | 1,240 | 154.0000 | **154.00** | **154.00** |

若出现 1 分尾差，调整到 base 最大的第 3 行，并置 `is_tail_adjust=TRUE`。

**为什么不按行独立打折：** 如果每行各打 8 折并各自舍入，3 行会各产生 ±0.5 分误差，累计可达 1.5 分。先算总额再分摊，保证总额精确。

**状态机**

```
ISSUED ──► LOCKED ──► USED（终态）

   │           └──► ISSUED（锁超时自动释放 / 主动释放）
   ├──► EXPIRED（valid_to 过期，终态）
   └──► VOIDED（人工作废，终态）
```

**为什么需要 LOCKED 状态**

如果只有 `ISSUED → USED`，会出现这个竞态：

- 窗口 A：查询券 → 有效 → 计算减免 → 提交应用（耗时 2 秒）
- 窗口 B：同一秒查询券 → 仍有效 → 也提交应用
- 结果：一张「满 200 减 100」券在同一分钟内被用了两次，医院白亏 100 元

`LOCKED` 状态 + Redis NX 锁把「查询有效」和「确认使用」之间的窗口堵死。锁 30 分钟是为了防止收费员选了券后去处理别的事导致券长期不可用。
