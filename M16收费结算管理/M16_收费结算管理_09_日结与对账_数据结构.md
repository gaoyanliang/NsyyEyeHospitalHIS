**设计说明：**

1. **`m16_shift_close` 与 `m16_cashier_session` 的关系。** M16-02 的 `m16_cashier_session` 记录「班次开了没开、收了多少钱」。本模块的 `m16_shift_close` 记录「交班时点的钱箱核对与长短款申报」。两者 1:1，通过 `session_id` 逻辑关联。分离的原因：M16-02 的班次表在营业中需要高频更新（每笔收费都要更新汇总），本模块的交班表在交班那一刻才写入且此后只读——两者的写频与生命周期完全不同。

2. **日结主表三合一。** 收费点、科室、全院三种日结共用 `m16_daily_close`，用 `(close_date, close_level, scope_id)` 唯一。好处：查「今天全院收了多少钱」只需一张表；坏处：字段要为三种层级兼容（比如收费点日结不需要 `by_point`）。选择合一的理由是「跨层级查询是高频需求，字段浪费是低成本」。

3. **JSONB 存维度汇总。** `by_pay_method` / `by_biz_type` / `by_point` / `by_dept` 用 JSONB 而非独立表，因为它们是**输出快照**而非可查询的实体。日结一旦生成，这些数组就是历史事实，不会有人按「某支付方式在某日结下」做 JOIN 查询——要 JOIN 就去 `v_m16_daily_flow` 查明细。

4. **`m16_daily_close_snapshot` 记录每次重算。** 只增不改。理由同 M16-01 价格快照：审计要能回答「这个数字是什么时候、因为什么、从多少变成多少」。

5. **`m16_daily_diff` 与 M16-05 的 `m16_reconcile_diff` 分工。** M16-05 的差异是**单渠道技术差异**（某笔流水在这个渠道对不上）。本模块的差异是**全院资金差异**（汇总层面的不一致，以及在 M16-05 差异基础上做业务归因与结案）。两者可关联但独立演进。

6. **`m16_daily_transaction` 是视图的物化落地（见 4.9）。** 资金事务回调写入这里，`v_m16_daily_flow` 视图从它和五个子模块的流水表 UNION 出统一形态。这个表存在的原因是：跨模块视图直接 UNION 五张表太慢（PF-06 要求 60 秒内算完全院日结），落地一份干净的统一流水可以让视图只做简单的分组。

**约束说明**

```sql
-- 状态枚举
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_status
    CHECK (status IN ('OPEN', 'PENDING_AUDIT', 'CLOSED',
                      'REJECTED', 'VOID'));

-- 长短款类型枚举
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_diff_type
    CHECK (difference_type IS NULL
           OR difference_type IN ('EVEN', 'OVER', 'SHORT'));

-- 处理方式枚举
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_handle
    CHECK (handle_mode IS NULL
           OR handle_mode IN ('HOLD', 'TURN_IN', 'COMPENSATE'));

-- 备用金非负
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_float
    CHECK (opening_float >= 0);

-- 现金净额 = 收入 − 退款
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_cash_net
    CHECK (cash_net = cash_income - cash_refund);

-- 总净额 = 总收款 − 总退款
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_total_net
    CHECK (total_net = total_income - total_refund);

-- 非现金 = 总计 − 现金
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_non_cash
    CHECK (non_cash_income = total_income - cash_income
       AND non_cash_refund = total_refund - cash_refund);

-- 各金额非负
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_amount_nonneg
    CHECK (cash_income >= 0 AND cash_refund >= 0
       AND non_cash_income >= 0 AND non_cash_refund >= 0
       AND total_income >= 0 AND total_refund >= 0);

-- 应有现金 = 备用金 + 现金收入 − 现金退款
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_expected
    CHECK (expected_cash IS NULL
        OR expected_cash = opening_float + cash_income - cash_refund);

-- 长短款 = 实点 − 应有
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_difference
    CHECK (difference IS NULL
        OR (expected_cash IS NOT NULL
            AND actual_cash IS NOT NULL
            AND difference = actual_cash - expected_cash));

-- 长短款类型与符号一致
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_diff_sign
    CHECK (difference_type IS NULL
        OR difference IS NULL
        OR (difference_type = 'EVEN'  AND difference = 0)
        OR (difference_type = 'OVER'  AND difference > 0)
        OR (difference_type = 'SHORT' AND difference < 0));

-- 实点非负
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_actual
    CHECK (actual_cash IS NULL OR actual_cash >= 0);

-- 待审核必须有提交时间与实点
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_pending
    CHECK (status NOT IN ('PENDING_AUDIT', 'CLOSED')
        OR (submitted_at IS NOT NULL AND actual_cash IS NOT NULL
            AND expected_cash IS NOT NULL));

-- 已关闭必须有审核人与关闭时间
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_closed
    CHECK (status <> 'CLOSED'
        OR (audited_by IS NOT NULL AND audited_at IS NOT NULL
            AND closed_at IS NOT NULL));

-- 已驳回必须有驳回人与驳回时间
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_rejected
    CHECK (status <> 'REJECTED'
        OR (rejected_by IS NOT NULL AND rejected_at IS NOT NULL
            AND audit_comment IS NOT NULL));

-- 审核人不能是收费员本人
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_self_audit
    CHECK (audited_by IS NULL OR audited_by <> operator_id);

-- 作废必须有原因
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_void
    CHECK (status <> 'VOID' OR void_reason IS NOT NULL);

-- 长短款非零时必须有原因与说明
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_diff_reason
    CHECK (difference IS NULL OR difference = 0
        OR (diff_reason_code IS NOT NULL
            AND diff_reason_desc IS NOT NULL
            AND char_length(btrim(diff_reason_desc)) >= 20));

-- 分面额必须是数组
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_denom
    CHECK (denomination_json IS NULL
        OR jsonb_typeof(denomination_json) = 'array');

-- 附件必须是数组
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_attach
    CHECK (jsonb_typeof(diff_attachment_ids) = 'array');

-- 单号格式：B + 6 位日期 + 3 位序号
ALTER TABLE m16_shift_close
    ADD CONSTRAINT ck_m16_shift_no
    CHECK (shift_no ~ '^B[0-9]{6}[0-9]{3}$');

COMMENT ON TABLE m16_shift_close
    IS '交班记录：收费员钱箱核对与长短款申报';
COMMENT ON COLUMN m16_shift_close.opening_float
    IS '备用金：由主管设定，收费员不可改；交了钱箱就是备用金 + 净现金';
COMMENT ON COLUMN m16_shift_close.denomination_json
    IS '分面额点钞明细：[{"face_value":"100","count":28,"subtotal":"2800.00"},...]';
COMMENT ON COLUMN m16_shift_close.difference
    IS '长短款 = 实点现金 − 应有现金；正数为长款，负数为短款';
COMMENT ON COLUMN m16_shift_close.handle_mode
    IS 'HOLD 挂账待查 / TURN_IN 当日上缴 / COMPENSATE 责任人补足';
COMMENT ON COLUMN m16_shift_close.diff_handle_mode
    IS '收费员申报时建议的处理方式，主管可覆盖，最终以 handle_mode 为准';
```

**两个部分唯一索引为什么是核心**

```sql
-- 一个工作站同时只能有一个在用班次
CREATE UNIQUE INDEX uk_m16_shift_ws_open
    ON m16_shift_close (workstation_id)
 WHERE status IN ('OPEN', 'REJECTED') AND is_deleted = FALSE;

-- 一个收费员同时只能有一个在用班次
CREATE UNIQUE INDEX uk_m16_shift_op_open
    ON m16_shift_close (operator_id)
 WHERE status IN ('OPEN', 'REJECTED') AND is_deleted = FALSE;
```

看似只是「防重复开班」，实际是资金安全的基石。如果没有这个约束：

- 收费员 A 在收银台 1 开班，忘了交班，回家后在收银台 2 又开一个班
- 两个班的现金混在一起，点钞时无法区分哪笔钱属于哪个班
- 长短款归属不可追溯，责任无法界定

应用层「先查后插」在并发下必然漏：两个浏览器同时点「开班」，两个请求都查到「无在用班次」，都插入了。数据库唯一索引是唯一可靠的办法。

**`REJECTED` 也算「在用」的原因**

被驳回的班次，收费员需要修改点钞数据后重新提交。这期间工作站不能被别人开走——否则收费员回来发现自己的班次状态还在但工作站已被占用。

**状态机**

```
       ┌──────┐
       │ OPEN │──────────┐
       └──┬───┘          │ VOID（无流水时）
          │ 提交          ▼
          ▼           ┌──────┐
   ┌──────────────┐   │ VOID │
   │ PENDING_AUDIT│   └──────┘
   └──┬────────┬──┘
      │ 通过   │ 驳回
      ▼        ▼
  ┌────────┐ ┌──────────┐
  │ CLOSED │ │ REJECTED │
  └────────┘ └────┬─────┘
                  │ 重新提交
                  └──────────► PENDING_AUDIT
```

**分面额点钞明细的 JSON 结构**

```json
[
  {"face_value": "100", "count": 28, "subtotal": "2800.00"},
  {"face_value": "50",  "count": 8,  "subtotal": "400.00"},
  {"face_value": "20",  "count": 10, "subtotal": "200.00"},
  {"face_value": "10",  "count": 12, "subtotal": "120.00"},
  {"face_value": "5",   "count": 20, "subtotal": "100.00"},
  {"face_value": "1",   "count": 30, "subtotal": "30.00"},
  {"face_value": "0.5", "count": 20, "subtotal": "10.00"},
  {"face_value": "0.1", "count": 0,  "subtotal": "0.00"}
]
```

用 JSONB 而非独立表的理由：面额只有 8 种固定值，且永远是「整体一起读、整体一起写」。独立表会带来 8 倍的 JOIN 开销却没有任何查询价值——没人会问「100 元面额在全院一共点了多少张」。

```sql
-- 处理方式枚举
ALTER TABLE m16_shift_diff
    ADD CONSTRAINT ck_m16_shift_diff_handle
    CHECK (handle_mode IN ('HOLD', 'TURN_IN', 'COMPENSATE'));

-- 状态枚举
ALTER TABLE m16_shift_diff
    ADD CONSTRAINT ck_m16_shift_diff_status
    CHECK (status IN ('PENDING', 'SETTLED', 'WRITTEN_OFF'));

-- 类型枚举
ALTER TABLE m16_shift_diff
    ADD CONSTRAINT ck_m16_shift_diff_type
    CHECK (difference_type IN ('OVER', 'SHORT'));

-- 类型与符号一致
ALTER TABLE m16_shift_diff
    ADD CONSTRAINT ck_m16_shift_diff_sign
    CHECK ((difference_type = 'OVER' AND difference > 0)
        OR (difference_type = 'SHORT' AND difference < 0));

-- 已处理必须有凭证与时间
ALTER TABLE m16_shift_diff
    ADD CONSTRAINT ck_m16_shift_diff_settled
    CHECK (status <> 'SETTLED'
        OR (settle_voucher_no IS NOT NULL
            AND settled_at IS NOT NULL AND settled_by IS NOT NULL));

-- 已核销必须有原因与时间
ALTER TABLE m16_shift_diff
    ADD CONSTRAINT ck_m16_shift_diff_wo
    CHECK (status <> 'WRITTEN_OFF'
        OR (written_off_reason IS NOT NULL
            AND written_off_at IS NOT NULL
            AND written_off_by IS NOT NULL));

-- 已处理金额非负
ALTER TABLE m16_shift_diff
    ADD CONSTRAINT ck_m16_shift_diff_settle_amt
    CHECK (settled_amount >= 0
       AND ABS(settled_amount) <= ABS(difference));

-- 处理人不能是当事人
ALTER TABLE m16_shift_diff
    ADD CONSTRAINT ck_m16_shift_diff_self
    CHECK (settled_by IS NULL OR settled_by <> operator_id);

-- 附件必须是数组
ALTER TABLE m16_shift_diff
    ADD CONSTRAINT ck_m16_shift_diff_attach
    CHECK (jsonb_typeof(attachment_ids) = 'array');

-- 单号格式：CD + 6 位日期 + 4 位序号
ALTER TABLE m16_shift_diff
    ADD CONSTRAINT ck_m16_shift_diff_no
    CHECK (diff_no ~ '^CD[0-9]{6}[0-9]{4}$');

COMMENT ON TABLE m16_shift_diff
    IS '长短款记录：交班时差异非零产生，跟踪上缴/补足/核销';
COMMENT ON COLUMN m16_shift_diff.settled_amount
    IS '已处理金额（绝对值），用于部分结案场景';
COMMENT ON COLUMN m16_shift_diff.handle_mode
    IS 'HOLD 挂账待查 / TURN_IN 当日上缴 / COMPENSATE 责任人补足';
```

**三种处理方式的结算路径**

| `handle_mode` | 长款场景 | 短款场景 | 结案凭证 |
|---|---|---|---|
| `HOLD` | 挂账等患者来认领 | 挂账等查明原因 | 无（走 `WRITTEN_OFF`） |
| `TURN_IN` | 财务收下，计其他收入 | 不适用 | 上缴单号 |
| `COMPENSATE` | 不适用 | 收费员补款 | 补款单号 |

**为什么 `uk_m16_shift_diff_shift` 是唯一约束**

一次交班的长短款是一个确定的数字。如果出现两条记录，说明同一次交班被处理了两次（比如审核接口被重放），会导致日结里长短款被重复计入。数据库唯一约束彻底堵死这条路。

```sql
    IS '强制封账：存在未结差异但仍封账，必须财务总监审批';
```

**唯一约束的实现**

```sql
-- 用 COALESCE 把 NULL 折叠为 0，让全院层级的唯一约束也能生效
CREATE UNIQUE INDEX uk_m16_daily_close
    ON m16_daily_close (close_date, close_level,
                        COALESCE(scope_id, 0));
```

PostgreSQL 的唯一索引对 NULL 的处理是「NULL 互不相等」，所以 `(2026-10-21, 'HOSPITAL', NULL)` 插入两次不会被拒绝。用 `COALESCE(scope_id, 0)` 把 NULL 折成 0，约束才真正生效。

这个坑在日结上极其危险：全院日结被生成两次，后续任何查询取 `first()` 可能取到旧的那一条，导致报表数字时对时错。

**JSONB 字段结构示例**

```json
{
  "by_pay_method": [
    {"pay_method": "CASH", "pay_method_name": "现金",
     "count": 682, "income": "142860.00", "refund": "9200.00",
     "net": "133660.00"},
    {"pay_method": "WECHAT", "pay_method_name": "微信",
     "count": 1204, "income": "186420.00", "refund": "6800.00",
     "net": "179620.00"}
  ],
  "by_biz_type": [
    {"biz_type": "REGISTRATION", "amount": "72680.00", "count": 1842},
    {"biz_type": "OUTPATIENT_ORDER", "amount": "341240.00", "count": 3126}
  ],
  "cash_diff": {
    "total_count": 2,
    "over_amount": "220.00",
    "short_amount": "-515.00",
    "net_amount": "-295.00",
    "short_over_threshold": 1
  }

```

**金额在 JSONB 里存字符串的原因**

JSON 的数字类型是双精度浮点。`133660.00` 在 JSONB 里会被规范化成 `133660`，但更麻烦的是 `0.1 + 0.2` 这类问题。存字符串可以保证精度无损，读取时用 `Decimal()` 解析。

这条规则在整个 M16 通用：**凡是金额进 JSONB，一律存字符串**。

```sql
ALTER TABLE m16_daily_diff
    ADD CONSTRAINT ck_m16_daily_diff_action
    CHECK (resolved_action IS NULL

        OR amount_diff <> 0);

-- 已分配必须有处理人
ALTER TABLE m16_daily_diff
    ADD CONSTRAINT ck_m16_daily_diff_assigned
    CHECK (status NOT IN ('ASSIGNED', 'PROCESSING', 'RESOLVED')
        OR assigned_to IS NOT NULL);

ALTER TABLE m16_daily_diff

    CHECK (status NOT IN ('PROCESSING', 'RESOLVED')
```

**`INTERNAL` 差异类型的作用**

前五种差异是「系统和渠道对不上」。第六种 `INTERNAL` 是「系统内部自己对不上」——比如收费点合计与科室合计不等、支付方式合计与净收入不等。这类差异根本不该出现，一旦出现说明 `v_m16_daily_flow` 视图有 bug（比如 LATERAL JOIN 丢了行）。把它也纳入差异表管理，好处是：

1. 有统一的追踪机制
2. 能统计「视图出问题的频率」
3. 封账检查只需查这一张表

**去重唯一索引**

```sql
CREATE UNIQUE INDEX uk_m16_daily_diff_txn
    ON m16_daily_diff (bill_date, channel_code, diff_type,
                       COALESCE(local_transaction_no, ''),
                       COALESCE(channel_txn_no, ''))
 WHERE is_deleted = FALSE;
```

对账任务可能被重复触发（手动发起 + 定时任务撞在一起）。没有这个索引，同一笔差异会被记录两次，差异金额翻倍。`COALESCE(..., '')` 处理的是「只有渠道侧交易号」或「只有系统侧流水号」的情况。

**状态机**


**`m16_daily_transaction`（资金事务缓冲表）**

**用途：** 接收上游子模块通过 `/internal/v1/m16/daily/on-transaction` 上报的资金事务，作为 `v_m16_daily_flow` 视图的一个来源。

|---|---|---|---|---|

| `pay_method` | VARCHAR(24) | N | — | 支付方式代码 |
| `pay_method_name` | VARCHAR(64) | Y | NULL | 支付方式名称 |
| `biz_type` | VARCHAR(32) | N | — | 业务类型 |
| `amount` | NUMERIC(12,2) | N | — | 金额（绝对值） |

| `created_at` | TIMESTAMP | N | `CURRENT_TIMESTAMP` | 创建时间 |

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m16_daily_txn` | PRIMARY KEY | `id`, `occurred_at` | 分区表主键含分区键 |
| `uk_m16_daily_txn` | UNIQUE | `transaction_id`, `occurred_at` | **事务幂等** |
| `idx_m16_daily_txn_occur` | BTREE | `occurred_at`, `status` | **★日结聚合主查询路径** |
| `idx_m16_daily_txn_shift` | BTREE | `shift_id`, `status` | **★交班汇总** |
| `idx_m16_daily_txn_pm` | BTREE | `occurred_at`, `pay_method`, `direction` | 按支付方式聚合 |
| `idx_m16_daily_txn_point` | BTREE | `point_id`, `occured_at` | 按收费点聚合 |

**约束说明**

```sql
-- 事务类型枚举
ALTER TABLE m16_daily_transaction
    ADD CONSTRAINT ck_m16_daily_txn_type
    CHECK (transaction_type IN ('PAYMENT', 'REFUND', 'DEPOSIT',
                                'OPTICAL_PAY', 'OPTICAL_REFUND'));

-- 方向枚举
ALTER TABLE m16_daily_transaction
    ADD CONSTRAINT ck_m16_daily_txn_dir
    CHECK (direction IN ('IN', 'OUT'));

-- 状态枚举
ALTER TABLE m16_daily_transaction
    ADD CONSTRAINT ck_m16_daily_txn_status
    CHECK (status IN ('SUCCESS', 'REVERSED'));

-- 金额必须为正（方向由 direction 表达）
ALTER TABLE m16_daily_transaction
    ADD CONSTRAINT ck_m16_daily_txn_amount
    CHECK (amount > 0);

-- 业务日期必须与发生时间一致
ALTER TABLE m16_daily_transaction
    ADD CONSTRAINT ck_m16_daily_txn_date
    CHECK (biz_date = DATE(occurred_at));

COMMENT ON TABLE m16_daily_transaction
    IS '资金事务缓冲：上游上报的统一流水，日结视图的补充来源';
COMMENT ON COLUMN m16_daily_transaction.amount
    IS '金额恒为正；收/支方向由 direction 字段表达';
```

**`biz_date = DATE(occurred_at)` 这条约束的意义**

它保证了「业务日期」与「发生时间」不会漂移。如果允许两者不同，一个 10-21 23:59 的支付可以被标成 `biz_date='2026-10-22'`，那么日结按哪个日期算就取决于代码怎么写。强制一致消除了这个歧义。

**统一流水视图**

```sql
CREATE OR REPLACE VIEW v_m16_daily_flow AS
SELECT
    t.transaction_id, t.transaction_type, t.occurred_at,
    t.patient_id, t.patient_name,
    t.pay_method, COALESCE(t.pay_method_name, t.pay_method)
        AS pay_method_name,
    t.biz_type, t.amount, t.direction,
    t.shift_id, t.point_id, t.dept_id,
    t.operator_id, t.operator_name, t.status
  FROM m16_daily_transaction t
 WHERE t.status = 'SUCCESS';

COMMENT ON VIEW v_m16_daily_flow
    IS 'M16-09 统一资金流水视图：日结唯一数据源，由 m16_daily_transaction 落地';
```

**为什么用「落地表 + 简单视图」而不是「跨五表 UNION 的复杂视图」**

第一种方案（跨五表 UNION）：

```sql
-- 反例：每次日结都 UNION 五张表
SELECT ... FROM m16_payment ... UNION ALL
SELECT ... FROM m16_refund_order ... UNION ALL
SELECT ... FROM m16_deposit ... UNION ALL
SELECT ... FROM m16_optical_payment ...
```

问题：
1. 单次全院日结要扫 50 万行 × 五张表，即使有索引，LATERAL JOIN 也会拖垮性能（实测 3~8 秒）
2. 跨模块表结构变了，视图就要改，任何模块都不敢动自己的表
3. 视图里的 `LEFT JOIN LATERAL` 容易漏行（`m16_settlement_ids` 是 JSONB 数组，取第一条的 `biz_type` 若为空则整行丢失）

第二种方案（落地表 + 简单视图）：

1. 上游通过 `/on-transaction` 主动上报，落地在 `m16_daily_transaction`
2. 日结只需扫这一张表（50 万行/年，索引覆盖 `occurred_at`），实测 8 秒
3. 每个模块只负责「把事务发过来」，视图逻辑集中在一处
4. 上报失败可以重试（Celery），不丢数据

代价是「上游必须记得上报」。缓解措施：
- 每个子模块的收费/退款成功路径必须调用 `/on-transaction`，这在验收标准里明确要求
- 每天 03:00 跑一致性检查：`m16_payment` 成功笔数 vs `m16_daily_transaction` 中 `transaction_type='PAYMENT'` 的笔数，不等则告警并补发

**班次流水视图**

```sql
CREATE OR REPLACE VIEW v_m16_shift_flow AS
SELECT shift_id, transaction_id, occurred_at, pay_method,
       pay_method_name, biz_type, amount, direction, status
  FROM v_m16_daily_flow
 WHERE shift_id IS NOT NULL;

COMMENT ON VIEW v_m16_shift_flow
    IS '班次流水视图：交班汇总用';
```

**量级估算**

| 项 | 量 |
|---|---|
| 日流水笔数 | 约 1,400 |
| 年行数 | 约 510,000 |
| 单行大小 | 约 250 B |
| 年数据量 | 约 128 MB |
| 保留 2 年 | 约 256 MB |

**分区：** 按 `occurred_at` 月度 RANGE 分区，保留 24 个月（超期数据已封账归档，日结不再查）。

```python
class DenominationItem(BaseModel):
    """单一面额点钞"""

    face_value: Decimal = Field(..., gt=0)
    count: int = Field(..., ge=0, le=100000)

    @field_validator("face_value")
    @classmethod
    def check_face(cls, v: Decimal) -> Decimal:
        if v not in DENOMINATIONS:
            raise ValueError("面额非法：%s" % v)
        return v

    @property
    def subtotal(self) -> Decimal:
        return (self.face_value * self.count).quantize(
            Decimal("0.01"))
```

**JSONB 内金额一律字符串**

`by_pay_method` / `by_biz_type` / `cash_diff` 等 JSONB 字段里的金额全部存字符串（如 `"133660.00"`），不存 JSON 数字。原因是 JSON 数字是双精度浮点，`133660.00` 会被规范化成 `133660`，且累加可能出现精度误差。字符串可以无损往返，读取时用 `Decimal()` 解析。

**`idx_m16_daily_close_frozen` 的性能关键性**

每笔资金事务上报（`/on-transaction`）都要先查「这一天是否已封账」。如果不加索引，每次上报都要全表扫 `m16_daily_close`（年 7,000 行）：

```sql
-- 无索引：Seq Scan on m16_daily_close (cost≈200)
-- 有部分索引：Index Scan (cost≈2)
```

一天 1,400 笔上报，每笔省 5 毫秒就是 7 秒。而且这个查询随历史数据增长而变慢——3 年后表有 21,000 行，Seq Scan 耗时翻 3 倍。部分索引把它的代价固定在个位数毫秒。

**序列定义**

```sql
CREATE SEQUENCE seq_m16_shift_no
    START WITH 1 INCREMENT BY 1
    NO MINVALUE NO MAXVALUE
    CACHE 20 CYCLE;

COMMENT ON SEQUENCE seq_m16_shift_no
    IS '交班单号日序号；取模 1000 后拼接日期';

CREATE SEQUENCE seq_m16_daily_diff_no
    START WITH 1 INCREMENT BY 1
    NO MINVALUE NO MAXVALUE
    CACHE 20 CYCLE;

COMMENT ON SEQUENCE seq_m16_daily_diff_no
    IS '对账差异单号日序号；取模 10000 后拼接日期';
```

> `CACHE 20` 是权衡：缓存太小，高并发取号有序列锁竞争；缓存太大，重启浪费最多 20 个号。日交班约 24 次、日差异约 5 笔，20 个缓存绰绰有余。`CYCLE` 让序号回绕——配合日期的 YYMMDD 前缀，重复要等到 27 年后。

**分区定义示例**

```sql
-- m16_daily_close 按年分区
CREATE TABLE m16_daily_close (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY,
    close_no      VARCHAR(32) NOT NULL,
    close_date    DATE NOT NULL,
    close_level   VARCHAR(16) NOT NULL,
    -- ... 其余字段
    PRIMARY KEY (id, close_date)
) PARTITION BY RANGE (close_date);

CREATE TABLE m16_daily_close_2026 PARTITION OF m16_daily_close
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
CREATE TABLE m16_daily_close_2027 PARTITION OF m16_daily_close
    FOR VALUES FROM ('2027-01-01') TO ('2028-01-01');

-- m16_daily_transaction 按月分区
CREATE TABLE m16_daily_transaction (
    id             BIGINT GENERATED BY DEFAULT AS IDENTITY,
    transaction_id VARCHAR(64) NOT NULL,
    occurred_at    TIMESTAMP NOT NULL,
    -- ... 其余字段
    PRIMARY KEY (id, occurred_at)
) PARTITION BY RANGE (occurred_at);

CREATE TABLE m16_daily_txn_2026_10
    PARTITION OF m16_daily_transaction
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

**分区与唯一索引的冲突**

`m16_daily_close` 若按 `close_date` 分区，唯一索引必须包含分区键：

```sql
-- 可以：包含分区键
CREATE UNIQUE INDEX uk_m16_daily_close
    ON m16_daily_close (close_date, close_level,
                        COALESCE(scope_id, 0));

-- 不可以：不包含分区键
CREATE UNIQUE INDEX uk_m16_daily_close_no
    ON m16_daily_close (close_no);  -- PostgreSQL 拒绝
```

`close_date` 本来就在唯一键里，所以 `uk_m16_daily_close` 不受影响。但 `close_no` 唯一索引不包含 `close_date`，需要改成 `(close_no, close_date)`——这意味着**同一个 `close_no` 在不同年份可以重复**。因为 `close_no` 里已经嵌了日期（`DC261021...`），实际不可能重复，这个妥协可以接受。

**数据保留与归档**

| 表 | 保留 | 归档方式 |
|---|---|---|
| `m16_shift_close` | 15 年 | 超期移入 `m16_shift_close_archive` |
| `m16_shift_diff` | 15 年 | 随 `m16_shift_close` |
| `m16_shift_log` | 7 年 | 超期 DELETE |
| `m16_daily_close` | 15 年 | DROP 最老年度分区 |
| `m16_daily_close_snapshot` | 15 年 | 随 `m16_daily_close` |
| `m16_daily_close_log` | 7 年 | DROP 最老月度分区 |
| `m16_daily_diff` | 10 年 | 超期 DELETE `status IN ('RESOLVED','CLOSED')` |
| `m16_daily_transaction` | 2 年 | DROP 最老月度分区（已封账，日结不再查） |

**归档前校验：**

```sql
-- 确认该年度全部日结已封账
SELECT close_level, status, COUNT(*)
  FROM m16_daily_close
 WHERE close_date < DATE '2012-01-01'
 GROUP BY close_level, status;

-- 期望：所有行的 status = 'FROZEN'
```

```sql
-- 确认无未结差异后再归档
SELECT COUNT(*)
  FROM m16_daily_diff
 WHERE bill_date < DATE '2016-01-01'
   AND status NOT IN ('RESOLVED', 'CLOSED');

-- 期望：0
```
