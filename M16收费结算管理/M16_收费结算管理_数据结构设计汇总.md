## 1. 全局规范

### 1.1 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 表名 | `m16_` + 业务域 + 实体（小写蛇形） | `m16_settlement`、`m16_cashier_session` |
| 字段名 | 小写蛇形，不用缩写除非通用 | `net_income`、`pay_method` |
| 主键 | 一律 `id` | `id` |
| 主键索引 | `pk_` + 表名 | `pk_m16_settlement` |
| 普通索引 | `idx_` + 表名 + 用途 | `idx_m16_payment_poll` |
| 唯一索引 | `uk_` + 表名 + 用途 | `uk_m16_payment_no` |
| 检查约束 | `ck_` + 表名 + 语义 | `ck_m16_settle_payable` |
| 触发器 | `trg_` + 表名 + 动作 | `trg_m16_payment_trace_delete` |
| 序列 | `seq_` + 表名 + 用途 | `seq_m16_settlement_no` |
| 视图 | `v_` + 模块 + 用途 | `v_m16_daily_flow` |
| 枚举值 | 全大写下划线 | `PARTIAL_REFUND`、`TOPICAL_EYE` |
| 金额字段 | 后缀 `_amount` / `_price` / `_rate` | `total_amount`、`unit_price`、`fee_rate` |
| 时间字段 | `_at` 后缀 | `paid_at`、`created_at` |
| 布尔字段 | `is_` / `has_` / `allow_` / `need_` 前缀 | `is_deleted`、`allow_discount` |

**为什么表名要带模块前缀**

PostgreSQL 没有跨 schema 的命名体验问题，但一个 HIS 有 23 个模块、上百张表。不带前缀的话，`settlement`、`payment`、`order`、`config` 这种通用词会撞车。带前缀后，看一眼表名就知道归属，`grep` 也能直接定位。

### 1.2 必备字段

每张业务表必须包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 主键 |
| `created_at` | `TIMESTAMP` 默认 `CURRENT_TIMESTAMP` | 创建时间 |
| `updated_at` | `TIMESTAMP` 默认 `CURRENT_TIMESTAMP` | 更新时间（触发器维护） |
| `is_deleted` | `BOOLEAN` 默认 `FALSE` | 逻辑删除标记 |

**例外表（不需要 `is_deleted`）：**

| 表 | 理由 |
|---|---|
| `*_log`（日志表） | 只增不改，物理禁删 |
| `*_snapshot`（快照表） | 只增不改，物理禁删 |
| `*_trace`（追踪表） | 只增不改，按分区归档 |
| `*_item`（明细表） | 随主表级联，不单独软删 |

**为什么日志表不用 `is_deleted`**

逻辑删除意味着「数据还在但被标记为不可见」。对日志表来说，这跟「改过」只有一线之隔——一个有权执行 `UPDATE` 的人，可以先软删再插入一条新的，外观上就完成了篡改。物理禁删（触发器 `RAISE EXCEPTION`）是更硬的保证。

### 1.3 字段类型规范

| 用途 | 类型 | 精度 | 说明 |
|---|---|---|---|
| 主键、外键（逻辑） | `BIGINT` | — | 全模块统一 |
| 金额 | `NUMERIC(12,2)` 或 `NUMERIC(14,2)` | 2 位小数 | **禁止 FLOAT** |
| 单价 | `NUMERIC(12,4)` | 4 位小数 | 药品按每片 0.0250 计价 |
| 折扣率 | `NUMERIC(5,4)` | 4 位小数 | 0.8000 = 8 折 |
| 税率 | `NUMERIC(7,4)` | 4 位小数存百分比 | 13.0000 = 13% |
| 费率 | `NUMERIC(6,4)` | 4 位小数 | 0.0060 = 0.6% |
| 数量 | `NUMERIC(12,4)` | 4 位小数 | 支持小数数量 |
| 计数 | `INTEGER` / `SMALLINT` | — | — |
| 状态 | `VARCHAR(16)` ~ `VARCHAR(32)` | — | 不用 `ENUM` 类型 |
| 单号 | `VARCHAR(32)` ~ `VARCHAR(64)` | — | — |
| 名称快照 | `VARCHAR(64)` ~ `VARCHAR(128)` | — | — |
| 描述文本 | `VARCHAR(500)` ~ `VARCHAR(2000)` | — | 超过 2000 用 `TEXT` |
| 时间 | `TIMESTAMP` | — | 不用 `TIMESTAMPTZ` |
| 日期 | `DATE` | — | — |
| 结构化数据 | `JSONB` | — | 必须有 `jsonb_typeof` 约束 |

**为什么金额禁用 FLOAT**

```
0.1 + 0.2          → 0.30000000000000004
1.005 * 100        → 100.49999999999999
round(2.675, 2)    → 2.67（应为 2.68）
```

财务上这是不可接受的。一个 100 元的单子，`ROUND(1.005 * 100, 2)` 用 float 算得 100.49，用 Decimal 算得 100.50。差 1 分钱，退费时就对不上。

**为什么状态不用 PostgreSQL 的 `ENUM` 类型**

| 维度 | `VARCHAR` + CHECK | `ENUM` 类型 |
|---|---|---|
| 加枚举值 | `ALTER TABLE ... DROP/ADD CONSTRAINT` | `ALTER TYPE ... ADD VALUE`（不能回滚） |
| 删枚举值 | 改约束即可 | 几乎不可能（要重建类型） |
| 跨表复用 | 每表自己的约束 | 可以共享一个类型 |
| 迁移工具支持 | 好 | 差 |
| 排序 | 显式 `ORDER BY case` | 可按定义顺序 |

HIS 的状态机在实施期一定会调整（M16 的 `m16_payment` 状态就从 5 个扩到 7 个）。用 `VARCHAR` + `CHECK` 成本更低。

**为什么时间用 `TIMESTAMP` 不用 `TIMESTAMPTZ`**

HIS 是单时区部署（医院本地时间），用 `TIMESTAMPTZ` 会让所有查询都要考虑时区转换，且 `TIMESTAMP WITHOUT TIME ZONE` 的存储更紧凑。代价是「服务器时区必须固定」，这一点在部署文档里强制要求。

### 1.4 JSONB 使用规范

**允许用 JSONB 的场景**

| 场景 | 理由 | 示例 |
|---|---|---|
| 输出快照 | 生成后不再查询内部字段 | `m16_daily_close.by_pay_method` |
| 可变结构 | 结构随业务变化 | `m16_reconcile_diff.channel_raw` |
| 简单数组 | 元素不独立查询 | `settlement_ids`、`attachment_ids` |
| 配置参数 | KV 结构 | `m16_pay_config` |
| 审批链 | 层级不确定 | `approval_chain` |

**禁止用 JSONB 的场景**

| 场景 | 应该用 | 理由 |
|---|---|---|
| 需要 JOIN 的实体 | 独立表 | JSONB 无法高效 JOIN |
| 需要按字段查询 | 独立列 | JSONB 查询走 GIN 索引但比列慢 |
| 金额明细 | 独立表 | 需要 SUM/聚合 |

**JSONB 必带约束**

```sql
-- 每个 JSONB 字段都必须校验类型
ALTER TABLE m16_daily_close
    ADD CONSTRAINT ck_m16_daily_json_arr
    CHECK (jsonb_typeof(by_pay_method) = 'array'
       AND jsonb_typeof(cash_diff) = 'object');
```

不校验类型的话，`jsonb_array_elements` 遇到对象会直接报错，错误发生在运行时而非写入时，排查成本高。

**JSONB 内金额一律字符串**

```json
{"income": "142860.00", "refund": "9200.00"}
```

不用 JSON 数字的原因：JSON 的 number 类型是双精度浮点，`133660.00` 会被规范化成 `133660`，且累加可能产生精度误差。字符串可以无损往返，读时用 `Decimal()` 解析。

### 1.5 无物理外键策略

**M16 全部 63 张表均不建物理外键。**

| 替代手段 | 说明 |
|---|---|
| 应用层校验 | Service 层写入前校验引用存在 |
| 快照冗余 | 引用时同时存名称（`patient_name`、`dept_name`） |
| 定时校验 | Celery 每日扫描孤儿数据并告警 |
| 事件驱动 | 上游删除时发事件，下游标记 `xxx_deleted=TRUE` |
| 逻辑删除 | 上游不物理删，引用永不悬空 |

**为什么不用物理外键**

| 维度 | 有物理外键 | 无物理外键 |
|---|---|---|
| 写入性能 | 每次插入都校验父表（加锁） | 无额外开销 |
| 分库分表 | 几乎不可能 | 容易 |
| 数据迁移 | 必须按依赖顺序 | 任意顺序 |
| 级联删除 | 容易误删 | 绝不会 |
| 临时数据修复 | 困难（要先关约束） | 容易 |
| 数据质量 | 数据库保证 | 应用保证（较弱） |

HIS 的日结场景最能说明问题：一天 1,400 笔支付，每笔都要插 `m16_payment`、`m16_cashier_record`、`m16_settlement` 等，如果有外键，每笔都要校验父表存在，且这些父表同时在更新（结算单状态变更），会有锁竞争。

**数据质量怎么保证**

| 层面 | 措施 |
|---|---|
| 写入时 | Service 层校验 + 快照冗余（名称存一份） |
| 每日 | Celery 任务扫描孤儿：`m16_payment.settlement_ids` 中有但 `m16_settlement` 不存在的 ID |
| 上游删除时 | 逻辑删除 + `m16.daily_transaction.status` 标记 |
| 审计时 | 报表层遇到缺失引用显示「已删除」而非崩溃 |

**孤儿数据的容忍度**

不是零容忍。比如一笔 2015 年的支付引用的结算单已归档，这是正常的，不该报警。所以扫描任务的规则是：**近 3 年的数据零孤儿，3 年以上的孤儿仅记录不告警。**

**跨子模块的关联方式**

| 关联 | 方式 | 说明 |
|---|---|---|
| 结算单 ↔ 支付 | `m16_payment.settlement_ids`（JSONB 数组） | 一笔支付可覆盖多个结算单 |

**为什么支付与结算单是多对多**

混合支付：一张结算单 100 元，50 现金 + 50 微信。这是两笔 `m16_payment`，都指向同一张结算单。反过来，一次充值可以覆盖多张结算单（余额支付）。所以用 JSONB 数组存多个结算单 ID。

**`uk_m16_payment_txn` 为什么是「资金安全最后防线」**

支付回调可能重放、主动查询可能与回调同时到达、渠道可能重复推送同一笔。如果 `transaction_no` 不唯一：

```
回调到达（交易号 4200001234）→ 建支付记录 A，结算单置 PAID
回调重放（交易号 4200001234）→ 建支付记录 B，结算单已 PAID 跳过
结果：日结时同一笔钱被算了两次
```

数据库唯一索引是唯一的可靠防线。应用层的「先查后插」在并发下必然漏——两个并发请求都查到「不存在」，都插入了。

### 4.4 重要 CHECK 约束精选

| 约束 | 表 | 内容 | 语义 |
|---|---|---|---|
| `ck_m16_settle_payable` | `m16_settlement` | `payable_amount = total_amount - discount_amount` | 应收恒等 |
| `ck_m16_settle_item_bill_qty` | `m16_settlement_item` | `bill_quantity = quantity * eye_multiplier` | 眼别倍数 |
| `ck_m16_settle_item_eye_mult` | `m16_settlement_item` | `(eye_side='OU' AND eye_multiplier=2) OR (eye_side<>'OU' AND eye_multiplier=1)` | 双眼×2 |
| `ck_m16_payment_success` | `m16_payment` | 成功必须有 `paid_at` + `transaction_no` | 成功要素完整 |
| `ck_m16_payment_manual` | `m16_payment` | 补单必须有原因+证据+人+时间 | 补单可追溯 |
| `ck_m16_refund_cumulative` | `m16_refund_order` | `refunded_before + refund_amount <= net_amount` | **累计退费不超净额** |
| `ck_m16_refund_self_approve` | `m16_refund_order` | `approved_by <> created_by` | **职责分离** |
| `ck_m16_invoice_amount_balance` | `m16_invoice` | `amount_without_tax + tax_amount = total_amount` | 价税分离恒等 |
| `ck_m16_invoice_seglog_count` | `m16_invoice_segment_log` | `used_count + void_count + remain_count = total_count` | 票号账实相符 |
| `ck_m16_disc_apply_amount` | `m16_discount_apply` | `reduce_amount <= base_amount` | 减免不超基数 |
| `ck_m16_disc_appr_consistent` | `m16_discount_approval` | `ABS(reduce - ROUND(orig*(1-rate),2)) <= 0.01` | 审批金额一致 |
| `ck_m16_disc_appr_reason` | `m16_discount_approval` | `char_length(btrim(reason)) >= 10` | 折扣必须说清原因 |
| `ck_m16_deposit_acc_balance` | `m16_deposit_account` | `available = total - refund - frozen` | **预交金余额恒等** |
| `ck_m16_deposit_amount_sign` | `m16_deposit` | 充值正、退还负 | 符号约定 |
| `ck_m16_shift_expected` | `m16_shift_close` | `expected_cash = opening_float + cash_income - cash_refund` | 应有现金 |
| `ck_m16_shift_difference` | `m16_shift_close` | `difference = actual_cash - expected_cash` | 长短款 |
| `ck_m16_daily_net` | `m16_daily_close` | `net_income = total_income - total_refund` | 净收入恒等 |
| `ck_m16_daily_diff_amount` | `m16_daily_diff` | `amount_diff = channel_amount - local_amount` | 差异符号约定 |

### 4.5 恒等式约束的价值

上面这些 `CHECK` 约束的本质是**把业务恒等式写进数据库**。

举一个真实的反例：如果没有 `ck_m16_deposit_acc_balance`，代码里一个 bug 只更新了 `total_deposit` 忘了 `available_balance`，患者的预交金余额就会虚高。患者出院结算时多退钱，财务对不上账。这个 bug 可能在线上存在几个月才被发现——因为没有人天天核对每个账户的余额恒等式。

有了约束，插入/更新时数据库立刻拒绝，bug 在开发阶段就暴露。

**要注意的代价**

`CHECK` 约束在每次写入时都要计算。对于简单算术（`a = b - c`），开销可以忽略。但如果写成子查询（PostgreSQL 不允许在 `CHECK` 里用子查询），就无法实现。

跨表的恒等式（比如「结算单的优惠总额 = 所有优惠明细之和」）无法用 `CHECK` 保证，只能用：
- 应用层事务内计算并写入
- Celery 定时校验（`consistency_check_task`）
- 差异告警

**为什么有这个顺序**

因为**没有任何物理外键**，理论上可以任意顺序建表。但实际迁移仍有依赖：

1. **分区表需要先创建分区**。`m16_payment_trace` 按月度分区，建表时要同时建当月与未来 3 个月的分区。
2. **日志表的只读触发器需要函数先存在**。函数在脚本 011 建，触发器在表建完后挂。
3. **视图需要所有源表存在**。`v_m16_daily_flow` 依赖 `m16_daily_transaction`。
4. **初始化数据依赖配置表**。9 张配置表的初始数据必须在建表后立即插入。

**没有物理外键的最大好处**

数据修复时不需要先关约束：

```sql
-- 有外键：必须先禁用
ALTER TABLE m16_payment DISABLE TRIGGER ALL;
UPDATE m16_payment SET settlement_ids = ...;
ALTER TABLE m16_payment ENABLE TRIGGER ALL;

-- 无外键：直接改
UPDATE m16_payment SET settlement_ids = ...;
```

HIS 上线初期，数据修复是常态。无外键让修复成本降低一个数量级。

**迁移的幂等要求**

每一步迁移必须可重复执行。实施要求：

```python
def upgrade():
    op.execute("""
        CREATE TABLE IF NOT EXISTS m16_settlement (...)
    """)
    op.execute("""
        DO $$
        BEGIN
            IF NOT EXISTS (
                SELECT 1 FROM pg_indexes
                 WHERE indexname = 'uk_m16_settle_no') THEN
                CREATE UNIQUE INDEX uk_m16_settle_no
                    ON m16_settlement (settlement_no);
            END IF;
        END $$;
    """)
```

原因：上线后如果某次迁移中途失败（比如建分区时磁盘满），重跑必须从断点继续，不能因为「表已存在」整个失败。

**所有引用都存名称快照的理由**

上游主数据会变：患者改名、科室改名、项目改名、医生调科。如果 M16 只存 ID，历史单据显示的就是「现在的名字」而不是「当时的名字」。

**收费记录必须显示当时的名字。** 患者张三 2020 年叫「张三」，2023 年改名「张叁」。他 2020 年的收费小票上应该显示「张三」还是「张叁」？答案显然是「张三」——那才是当时的真实记录。

所以 M16 所有引用上游的字段都成对出现：`xxx_id` + `xxx_name`（快照）。

### 6.2 上游引用 M16（M16 提供）

| 引用方 | 引用的 M16 数据 | 方式 |
|---|---|---|
| M04-03 挂号 | 挂号费金额、支付状态 | 同步调用 P-02/P-04 |
| M07-03 医嘱 | 医嘱支付状态 | M16 回写 R-03 |
| M04-07 门诊日志 | 收入统计 | 同步调用 P-07 |
| M03-06 患者门户 | 未缴费清单 | 同步调用 P-06 |
| M17 财务 | 日结汇总、长短款 | 同步调用 P-12 |
| M22 报表 | 收入统计、对账差异 | 同步调用 |
| M05 住院（待） | 住院结算完成 | M16 回写 R-06 |

### 6.3 与 M01 主数据的依赖强度

| 主数据 | 变了会影响 M16 什么 | 缓存策略 |
|---|---|---|
| `md_charge_item`（价格） | 价格变化不影响历史单据（有快照） | 缓存 5 分钟 |
| `md_payment_method` | 支付方式停用影响新收费 | 缓存 1 小时 |
| `md_discount_policy` | 优惠方案变化影响新结算 | 缓存 5 分钟 |
| `md_optical_product` | 商品下架影响新开单 | 缓存 10 分钟 |
| `mdm_department` | 科室合并影响统计口径 | 缓存 1 小时 |

**价格变化为什么不影响历史单据**

因为 `m16_price_snapshot` 在计费那一刻把价格存下来，且只增不改。这张表有触发器禁止 `UPDATE`/`DELETE`：

```sql
CREATE OR REPLACE FUNCTION trg_m16_price_snap_immutable()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'm16_price_snapshot 为不可变审计表';
END;
$$ LANGUAGE plpgsql;
```

不存快照的后果：卫生局来检查 2023 年某笔收费是否合规，你去查当时的价格——查不到，因为价格表只有当前价格。

### 7.2 结算单状态机

```
       ┌───────┐
       │ DRAFT │  可加减项目
       └───┬───┘
           │ 定稿
           ▼
      ┌─────────┐
      │ PENDING │  待收费
      └────┬────┘
           │ 支付成功
           ▼
       ┌──────┐
       │ PAID │
       └──┬───┘
          │
    ┌─────┴─────┐
    │ 部分退费   │ 全额退费
    ▼           ▼
┌──────────────┐ ┌──────────┐
│PARTIAL_REFUND│ │REFUNDED  │
└──────┬───────┘ └──────────┘
       │ 全部退完
       └──────────► REFUNDED

  DRAFT ──作废──► CANCELLED（仅未收费）
```

**`CANCELLED` 只能从 `DRAFT` 出发。** 已收费的结算单不能作废，只能退费。作废是「这笔没发生过」，退费是「发生过了但不要了」。财务上两者完全不同。

**`SUCCESS` 不可逆的实现方式**

```python
async def _mark_success(self, payment, txn_no, paid_at):
    if payment.status == "SUCCESS":
        # 幂等：已成功且交易号相同，直接返回
        if payment.transaction_no == txn_no:
            return payment
        raise BizError(54906, "支付单已成功，交易号不一致")
    if payment.status not in ("CREATED", "PAYING", "UNKNOWN"):
        raise BizError(54906, "支付单状态不允许成功：%s"
                       % payment.status)
    ...
```

服务层拦截 + 数据库约束双保险。

### 7.4 退费单状态机

```
   ┌───────┐
   │ DRAFT │
   └───┬───┘
       │ 提交
       ▼
┌──────────────────┐
│ PENDING_APPROVAL │
└───┬──────────┬───┘
    │ 批准     │ 驳回
    ▼          ▼
┌──────────┐ ┌──────────┐
│ APPROVED │ │ REJECTED │  可修改重提
└────┬─────┘ └──────────┘
     │ 执行
     ▼
┌───────────┐

└──┬─────┬──┘
   │     │
成功│     │失败/超时
   ▼     ▼
┌────────┐ ┌──────────┐
│SUCCESS │ │ FAILED   │
└────────┘ └────┬─────┘

                ▼

                │
                │ 退款超时
                ▼
```

**`ABNORMAL` 为什么必须有**

退款请求发出去了，响应超时。钱可能已退，也可能没退。

- 乐观标 `SUCCESS`：如果实际没退，患者投诉少钱
- 标 `FAILED` 让用户重试：如果实际已退，重复退一次

两个都错。必须有第三个状态，交给人工或主动查询。

### 8.3 中文模糊搜索索引

```sql
CREATE INDEX idx_m16_payment_name_trgm
    ON m16_payment USING gin (patient_name gin_trgm_ops);
```

**为什么用 `pg_trgm` 而不是全文检索**

| 方案 | 中文支持 | 索引体积 | 查询速度 | 配置 |
|---|---|---|---|---|
| `pg_trgm` | ✅（3-gram） | 中 | 快 | 需 `CREATE EXTENSION` |
| `tsvector`（simple 分词） | ❌（整词匹配） | 小 | 快 | 需配分词器 |
| `zhparser` | ✅ | 中 | 快 | 需装扩展 |
| `LIKE '%xxx%'` | ✅ | 无索引 | 慢 | 无 |

`pg_trgm` 是 PostgreSQL 自带扩展，不需要额外安装，对中文的 3-gram 切分效果足够搜索姓名。`zhparser` 效果更好但要装第三方扩展，运维成本高。

**12 张表用了 trgm 索引**

`m16_settlement`、`m16_payment`、`m16_refund_order`、`m16_invoice`、`m16_optical_order`、`m16_optical_item`、`m16_deposit`、`m16_inpatient_charge`、`m16_daily_transaction`、`m16_shift_close`、`m16_discount_apply`、`m16_daily_diff`。

### 8.4 GIN 索引（JSONB 与数组）

```sql
-- 按结算单反查支付
CREATE INDEX idx_m16_payment_settle
    ON m16_payment USING gin (settlement_ids);

-- 按退费明细反查
CREATE INDEX idx_m16_refund_item_ids
    ON m16_refund_order USING gin (item_ids);
```

**JSONB GIN 索引的注意事项**

`gin (col)` 是「包含」索引，支持 `col @> '[...]'::jsonb`。不支持 `col ->> 'field' = 'value'`（那是 `gin (col jsonb_path_ops)` 或表达式索引）。

所以用法必须是：

```sql
-- 正确：走 GIN
SELECT * FROM m16_payment
 WHERE settlement_ids @> '[123]'::jsonb;

-- 错误：不走 GIN
SELECT * FROM m16_payment
 WHERE settlement_ids ->> 0 = '123';
```

这个细节必须在开发规范里写清楚，否则开发写了不走索引的查询，性能问题要到上线才发现。

### 8.5 索引维护

| 任务 | 频率 | 说明 |
|---|---|---|
| `ANALYZE` | 每日 03:00 | 更新统计信息 |
| 索引膨胀检查 | 每周 | `pg_stat_user_indexes.idx_scan` 为 0 的索引考虑删除 |
| 未使用索引清理 | 每月 | 上线 6 个月后再清 |
| `REINDEX CONCURRENTLY` | 按需 | 索引膨胀 > 30% 时 |

**为什么上线 6 个月后才清未使用索引**

刚上线时业务量小，某些索引（比如月度报表用的）可能一个月才用一次。上线 1 个月看 `idx_scan=0` 就删掉，会误删。

### 9.2 不分区的重要表

| 表 | 理由 |
|---|---|
| `m16_payment` | **资金凭证跨年唯一性 > 查询性能** |
| `m16_refund_order` | 同上 |
| `m16_invoice` | 发票号跨年唯一 |
| `m16_optical_order` | 数据量小（1.5 万/年） |
| `m16_shift_close` | 数据量小（8,800/年） |
| `m16_daily_diff` | 数据量小（1,830/年） |

**`m16_payment` 不分区的详细论证**

如果按 `created_at` 年度分区：

```sql
CREATE UNIQUE INDEX uk_m16_payment_txn
    ON m16_payment (transaction_no, created_at);
```

代价：`transaction_no` 只在同一年内唯一。虽然渠道交易号跨年重复的概率极低（微信交易号含时间戳），但一旦发生：

1. 两笔不同的支付被识别为同一笔
2. 第二笔的回调被幂等拦截，结算单不置 PAID
3. 患者付了钱但系统说没付

**收益 vs 代价**

| 维度 | 分区 | 不分区 |
|---|---|---|
| 查询「今天支付」 | 只扫 1 个分区 | 走 `paid_at` 索引 |
| 查询「历史某笔」 | 只扫 1 个分区 | 走唯一索引 |
| 唯一性保证 | **弱化** | **完整** |
| 归档 | DROP PARTITION | 需要 DELETE + VACUUM |
| 索引体积 | 每分区独立 | 单一索引 51 万行 |

实际的查询模式是「按 `payment_no` / `transaction_no` 精确查」和「按 `paid_at` 范围查」，两种都有索引。分区的收益主要体现在归档，而 M16-05 的数据保留策略是「热 3 年 + 归档表」，不需要分区。

结论：**不分区**。

### 9.3 归档策略

| 表 | 热数据 | 冷数据 | 归档方式 |
|---|---|---|---|
| `m16_payment` | 3 年 | 3 年以上 | 移入 `m16_payment_archive` |
| `m16_refund_order` | 3 年 | 3 年以上 | 移入 `m16_refund_archive` |
| `m16_invoice` | 5 年 | 5 年以上 | 移入 `m16_invoice_archive` |
| `m16_payment_trace` | 6 个月 | 超期 | DROP 最老月度分区 |
| `m16_daily_transaction` | 24 个月 | 超期 | DROP 最老月度分区 |
| `m16_settlement` | 15 年 | — | DROP 最老年度分区 |

**归档表的定义**

```sql
-- 归档表结构与主表一致，但不带业务索引
CREATE TABLE m16_payment_archive (
    LIKE m16_payment INCLUDING DEFAULTS
);
-- 只保留主键与按日期查询的索引
CREATE INDEX idx_m16_payment_arch_date
    ON m16_payment_archive (paid_at);
```

**归档流程**

```
1. 选出归档范围：paid_at < NOW() - INTERVAL '3 years'
2. 校验该范围已封账（m16_daily_close.status = 'FROZEN'）
3. 事务内：INSERT INTO archive SELECT ... ; DELETE FROM main ...
4. 记录归档日志（数量、范围、时间、操作人）
5. 校验：archive 行数 == 删除行数
```

**归档不能与业务并发**。归档期间如果有业务查询历史支付会失败（正在删除中）。所以归档必须在业务低峰（凌晨 2:00-5:00），且要加锁。

### 13.2 公共函数

```sql
-- updated_at 自动维护
CREATE OR REPLACE FUNCTION trg_m16_set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = CURRENT_TIMESTAMP;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 挂到所有业务表
DO $$
DECLARE
    t TEXT;
BEGIN
    FOR t IN
        SELECT tablename FROM pg_tables
         WHERE schemaname = 'public'
           AND tablename LIKE 'm16_%'
           AND tablename NOT LIKE '%_log'
           AND tablename NOT LIKE '%_snapshot'
           AND tablename NOT LIKE '%_trace'
           AND tablename NOT LIKE '%_archive'
    LOOP
        EXECUTE format(
            'CREATE TRIGGER trg_%s_updated BEFORE UPDATE ON %I
             FOR EACH ROW EXECUTE FUNCTION trg_m16_set_updated_at()',
            t, t);
    END LOOP;
END $$;
```

**为什么日志表不挂 `updated_at` 触发器**

因为日志表根本不允许 `UPDATE`（只读触发器会先抛异常）。挂了也没用。

### 13.4 回滚策略

| 场景 | 策略 |
|---|---|
| 迁移失败在建表阶段 | `downgrade()` 删除已建表 |
| 迁移失败在数据阶段 | 事务回滚（每个迁移一个事务） |
| 上生产后发现表结构不对 | 新增修复迁移，不修改已执行的迁移 |
| 紧急回滚 | `alembic downgrade -1` |

**为什么「不修改已执行的迁移」**

Alembic 记录的是迁移的 revision 号，不记录内容。如果修改了已执行的迁移文件，别人环境里已执行的是旧内容，新环境执行的是新内容，两边 schema 不一致，而 Alembic 认为一致。

正确做法是新增一个 `m16_026_fix_xxx` 的迁移。

| T-04 | M16-05 的储值支付依赖 M03-03 的储值账户，该表尚未定义 | 储值支付与退款无法实现 | 待 M03-03 补充 |
| T-05 | M16-07 的接口清单与 M16-08 的红冲调用点需最终对齐 | 联调时红冲可能调不通 | 联调前走查接口签名 |

### 14.2 可以延后处理的

| 编号 | 问题 | 影响 | 建议 |
|---|---|---|---|
| T-02 | M16-03 的 5 个契约接口（R-01~R-05）待 M05 定义 | 住院结算无法闭环 | M05 完成后补齐 |
| T-03 | `m16_day_surgery_settle` 为预留表，未建 | 日间手术结算未实现 | M06 完成后补齐 |
| T-06 | `m16_settlement_item` 与 `m16_invoice_item` 的税码字段未定义 | 增值税专用发票无法开 | 引入税码主数据后补 |
| T-07 | 医保结算字段（`insurance_amount` / `self_pay_amount`）已预留但未使用 | 商保/医保无法接入 | M21 集成平台接入时启用 |

### 14.3 文档债的清理机制

每次子模块定稿时，在 M16 数据结构汇总的本节追加新发现的债；每次实施前必须过一遍本节，标记「已清理」或「延后」。

**这不是文档的缺点，是文档的价值**——知道哪里没想清楚，比假装都想清楚了更安全。
