## 4. 数据结构设计

### 4.1 ER 关系图

```
┌───────────────────────────┐
│ m16_pay_channel           │
│ 支付渠道配置（6 行）       │
│ channel_code (uk)         │

└───────────┬───────────────┘

┌───────────────────────────┐        ┌────────────────────────────┐
│ m16_reconcile_task        │  1 : N │ m16_reconcile_diff         │
│ 对账任务（日 × 渠道）      │◄───────┤ 对账差异                    │
```

**设计说明：**

1. **无物理外键。** 遵循 M16 全局策略，跨表引用由应用层校验 + 定时校验任务保障。理由：支付链路在高并发下不能因为外键锁导致超时。

2. **`m16_payment` 是核心表，其余都是它的附属。** 支付流水是全系统"钱到了"的唯一事实来源，其余表要么描述它（trace），要么撤销它（refund），要么核验它（reconcile）。

3. **`m16_pay_channel` 与 `md_payment_method` 的关系。** 前者是**技术配置**（商户号、密钥、费率、限额），后者是**业务语义**（现金/微信/支付宝，供收费界面选择）。一个 `md_payment_method.code` 对应一个 `m16_pay_channel.channel_code`，通过 code 关联。

4. **`m16_payment` 与 M16-02 的关系。** M16-02 数据结构文档中已定义 `m16_payment` 的基础字段（供收银台使用）。本文档在此基础上补齐渠道配置、幂等键、手工补单、状态机所需的字段。**两处定义必须保持一致**，以本文档为准，M16-02 中的定义应视为子集。

5. **`m16_refund` 与 M16-08 的关系。** M16-08（退费与冲红）负责"该不该退、退多少"的决策并创建退款申请；M16-05 负责"怎么退"的执行并持有 `m16_refund` 表。M16-08 通过 `POST /internal/v1/m16/payments/refund` 调用，M16-05 落这张表。

6. **分区策略。** `m16_payment`、`m16_payment_trace`、`m16_refund` 按 `created_at` 年度 RANGE 分区，保留 15 年（门急诊结算凭证保存期限参照《医疗机构病历管理规定》与《会计档案管理办法》）。`m16_reconcile_*` 保留 5 年。

### 4.2 表：`m16_pay_channel`（支付渠道配置表）

**用途：** 存储每个支付渠道的技术配置。非患者数据，行数极少（≤ 10 行），全表常驻 Redis 缓存。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | N | IDENTITY | 主键 |
| `channel_code` | VARCHAR(32) | N | — | 渠道代码：`WECHAT`/`ALIPAY`/`UNIONPAY`/`POS`/`STORED`/`CASH` |
| `channel_name` | VARCHAR(64) | N | — | 渠道名称，如「微信支付」 |
| `pay_category` | VARCHAR(16) | N | — | 支付大类 `CASH`/`CARD`/`SCAN`/`STORED`/`INSURANCE`/`OTHER` |
| `pay_method_code` | VARCHAR(32) | N | — | 对应 `md_payment_method.code` |
| `env` | VARCHAR(8) | N | `'PROD'` | 环境 `PROD`/`TEST` |
| `mch_id` | VARCHAR(64) | Y | NULL | 商户号 |
| `app_id` | VARCHAR(64) | Y | NULL | 应用 ID（微信 appid / 支付宝 app_id） |
| `cert_serial_no` | VARCHAR(128) | Y | NULL | 商户 API 证书序列号（微信） |
| `cert_path` | VARCHAR(512) | Y | NULL | 商户证书路径 |
| `private_key_enc` | TEXT | Y | NULL | 商户私钥密文（AES-256-GCM 加密，KMS 托管密钥） |
| `api_v3_key_enc` | TEXT | Y | NULL | APIv3 密钥密文 |
| `platform_certs` | JSONB | Y | NULL | 平台证书集合 `{"serial": "pem_base64", ...}` |
| `alipay_public_key` | TEXT | Y | NULL | 支付宝公钥 |
| `notify_url` | VARCHAR(512) | Y | NULL | 回调地址 |
| `fee_rate` | NUMERIC(6,4) | N | 0.0000 | 手续费率（%，如 0.20 表示 0.2%） |
| `settlement_days` | SMALLINT | N | 1 | 结算周期 T+N |
| `single_limit` | NUMERIC(12,2) | Y | NULL | 单笔限额（元），NULL 不限 |
| `daily_limit` | NUMERIC(14,2) | Y | NULL | 单日限额，NULL 不限 |
| `expire_seconds` | INTEGER | N | 120 | 支付超时秒数 |
| `support_refund` | BOOLEAN | N | TRUE | 是否支持退款 |
| `support_micropay` | BOOLEAN | N | FALSE | 是否支持付款码被扫 |
| `need_reconcile` | BOOLEAN | N | TRUE | 是否需要对账 |
| `reconcile_file_format` | VARCHAR(32) | Y | NULL | 对账文件格式 `CSV`/`CSV_GZ`/`XML`/`TXT` |
| `is_enabled` | BOOLEAN | N | FALSE | 是否启用（需连通性测试通过） |
| `tested_at` | TIMESTAMP | Y | NULL | 最近一次连通性测试时间 |
| `tested_result` | VARCHAR(16) | Y | NULL | 测试结果 `OK`/`FAIL` |
| `tested_message` | VARCHAR(500) | Y | NULL | 测试失败原因 |
| `sort_no` | SMALLINT | N | 99 | 显示排序 |
| `remark` | VARCHAR(500) | Y | NULL | 备注 |
| `created_at` | TIMESTAMP | N | `CURRENT_TIMESTAMP` | 创建时间 |
| `created_by` | BIGINT | Y | NULL | 创建人 |
| `updated_at` | TIMESTAMP | N | `CURRENT_TIMESTAMP` | 更新时间（触发器维护） |
| `updated_by` | BIGINT | Y | NULL | 更新人 |
| `is_deleted` | BOOLEAN | N | `FALSE` | 逻辑删除标记 |

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m16_pay_channel` | PRIMARY KEY | `id` | — |
| `uk_m16_pay_channel_code` | UNIQUE | `channel_code` WHERE `is_deleted = FALSE` | 渠道代码唯一 |
| `uk_m16_pay_channel_method` | UNIQUE | `pay_method_code` WHERE `is_deleted = FALSE` | 一个支付方式对应一个渠道 |
| `idx_m16_pay_channel_enabled` | BTREE | `is_enabled`, `sort_no` | 启用渠道列表 |

**约束说明**

```sql
-- 渠道代码枚举
ALTER TABLE m16_pay_channel
    ADD CONSTRAINT ck_m16_pay_channel_code
    CHECK (channel_code IN ('WECHAT', 'ALIPAY', 'UNIONPAY',
                            'POS', 'STORED', 'CASH'));

-- 支付大类枚举
ALTER TABLE m16_pay_channel
    ADD CONSTRAINT ck_m16_pay_channel_category
    CHECK (pay_category IN ('CASH', 'CARD', 'SCAN', 'STORED',
                            'INSURANCE', 'OTHER'));

-- 环境枚举
ALTER TABLE m16_pay_channel
    ADD CONSTRAINT ck_m16_pay_channel_env
    CHECK (env IN ('PROD', 'TEST'));

-- 手续费率合理区间（0 ~ 10%）
ALTER TABLE m16_pay_channel
    ADD CONSTRAINT ck_m16_pay_channel_fee
    CHECK (fee_rate >= 0 AND fee_rate <= 10);

-- 结算周期非负
ALTER TABLE m16_pay_channel
    ADD CONSTRAINT ck_m16_pay_channel_settle_days
    CHECK (settlement_days >= 0);

-- 超时秒数合理区间（30 秒 ~ 30 分钟）
ALTER TABLE m16_pay_channel
    ADD CONSTRAINT ck_m16_pay_channel_expire
    CHECK (expire_seconds BETWEEN 30 AND 1800);

-- 限额必须为正
ALTER TABLE m16_pay_channel
    ADD CONSTRAINT ck_m16_pay_channel_limit
    CHECK ((single_limit IS NULL OR single_limit > 0)
       AND (daily_limit IS NULL OR daily_limit > 0));

-- 现金渠道不参与对账
ALTER TABLE m16_pay_channel
    ADD CONSTRAINT ck_m16_pay_channel_cash
    CHECK (channel_code <> 'CASH' OR (need_reconcile = FALSE
                                  AND mch_id IS NULL));

-- 第三方渠道启用时必须有商户号
ALTER TABLE m16_pay_channel
    ADD CONSTRAINT ck_m16_pay_channel_enabled
    CHECK (is_enabled = FALSE
           OR channel_code IN ('CASH', 'STORED')
           OR mch_id IS NOT NULL);

-- 启用必须先测试通过
ALTER TABLE m16_pay_channel
    ADD CONSTRAINT ck_m16_pay_channel_tested
    CHECK (is_enabled = FALSE
           OR channel_code IN ('CASH', 'STORED')
           OR tested_result = 'OK');

-- 测试结果枚举
ALTER TABLE m16_pay_channel
    ADD CONSTRAINT ck_m16_pay_channel_test_result
    CHECK (tested_result IS NULL OR tested_result IN ('OK', 'FAIL'));

COMMENT ON TABLE m16_pay_channel IS '支付渠道配置表：渠道技术参数与安全凭证';
COMMENT ON COLUMN m16_pay_channel.channel_code IS '渠道代码：WECHAT/ALIPAY/UNIONPAY/POS/STORED/CASH';
COMMENT ON COLUMN m16_pay_channel.pay_method_code IS '对应主数据 md_payment_method.code';
COMMENT ON COLUMN m16_pay_channel.private_key_enc IS '商户私钥密文，AES-256-GCM 加密，密钥由 KMS 托管';
COMMENT ON COLUMN m16_pay_channel.api_v3_key_enc IS '微信 APIv3 密钥密文，不可回显';
COMMENT ON COLUMN m16_pay_channel.platform_certs IS '平台证书集合，JSON 对象，key 为证书序列号';
COMMENT ON COLUMN m16_pay_channel.fee_rate IS '手续费率百分比，0.20 表示 0.2%';
COMMENT ON COLUMN m16_pay_channel.is_enabled IS '是否启用，启用前须连通性测试通过';
```

**状态机**

```
CREATED ──► PAYING ──► SUCCESS（终态，不可逆）
   │           │
   │           ├──► FAILED
   │           ├──► EXPIRED
   │           ├──► CLOSED
   │           └──► UNKNOWN ──► SUCCESS（补单/查单后）
   │
   ├──► FAILED
   └──► CLOSED
```

**不允许的流转（数据库层无法约束，须应用层拦截）：**

| 禁止 | 原因 |
|---|---|
| `SUCCESS → 任何状态` | 钱已到账，改状态制造账实不符 |
| `FAILED → PAYING` | 失败是终态，要重付应新建支付单 |
| `EXPIRED → PAYING` | 同理 |
| `CLOSED → PAYING` | 同理 |

**关键设计说明：为什么 `transaction_no` 唯一索引是资金安全的最后防线**

应用层的幂等逻辑可能因为以下原因失效：

1. 代码 BUG（某条分支漏了幂等检查）
2. 并发竞态（两个回调同时到达，都通过了"查是否已 SUCCESS"的检查）
3. 人工误操作（两个操作员同时补单）
4. 消息重放（事件总线重复投递）

这四种情况都会导致同一笔交易被记录两次，即患者付了 399 元，系统记了 798 元收入。数据库唯一索引是唯一不依赖应用正确性的防线。**即使所有应用层逻辑都写错了，这条索引也会拒绝第二条记录。**

**量级估算**

| 项 | 量 |
|---|---|
| 日支付笔数 | 约 1,500 笔 |
| 年行数 | 约 55 万行 |
| 单行大小 | 约 600 B |
| 年数据量 | 约 330 MB |
| 保留 15 年 | 约 5 GB |

**分区：** 按 `created_at` 年度 RANGE 分区，保留 15 年。

```sql

    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    payment_no VARCHAR(32) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    -- 其余字段同上
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE m16_payment_2026 PARTITION OF m16_payment
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
CREATE TABLE m16_payment_2027 PARTITION OF m16_payment
    FOR VALUES FROM ('2027-01-01') TO ('2028-01-01');
```

> **分区带来的索引限制：** 分区表上的唯一索引必须包含分区键 `created_at`。因此 `uk_m16_payment_txn` 实际是 `(transaction_no, created_at)` 上的唯一索引，这**削弱了跨年唯一性**（同一交易号在不同年份的分区可重复）。解决方案：`transaction_no` 本身含时间语义，且渠道不会跨年返回同一交易号；同时在应用层校验时用 `transaction_no` 全表扫描（走 `idx_m16_payment_txn_lookup`，虽跨分区但索引扫描较快）。若严格要求跨年唯一，则不分区，用普通表 + 归档。**建议采用不分区 + 归档方案**，因为支付流水是资金凭证，跨年唯一性比查询性能更重要。

**关键设计说明：退款总额不得超额**

数据库层面无法用简单的 CHECK 约束实现"累计退款 ≤ 支付金额"（需要聚合）。因此采取**三重保障：**

1. **应用层**：`RefundService.create()` 在 `SELECT FOR UPDATE` 锁住支付单后计算可退金额（见详细设计 6.5）
2. **唯一索引**：`uk_m16_refund_channel_no` 防止同一渠道退款单号被用两次
3. **定时校验**：`reconcile_deposit_balance_task` 类似的巡检任务每日核对 `sum(refund) ≤ pay_amount`，发现违规立即告警并冻结

```sql
-- 渠道枚举
ALTER TABLE m16_reconcile_task
    ADD CONSTRAINT ck_m16_reconcile_channel
    CHECK (channel_code IN ('WECHAT', 'ALIPAY', 'UNIONPAY', 'POS', 'STORED'));

-- 金额差额 = 渠道 − 本地
ALTER TABLE m16_reconcile_task
    ADD CONSTRAINT ck_m16_reconcile_diff
    CHECK (amount_diff IS NULL
           OR amount_diff = channel_amount - local_amount);

-- 笔数一致
ALTER TABLE m16_reconcile_task
    ADD CONSTRAINT ck_m16_reconcile_count
    CHECK (matched_count IS NULL OR diff_count IS NULL
           OR channel_count IS NULL
           OR matched_count + diff_count >= channel_count);

-- 平账判定一致性
ALTER TABLE m16_reconcile_task
    ADD CONSTRAINT ck_m16_reconcile_balanced
    CHECK (is_balanced IS NULL OR is_balanced = (diff_count = 0));

-- 完成后必须有结束时间
ALTER TABLE m16_reconcile_task
    ADD CONSTRAINT ck_m16_reconcile_finished
    CHECK (status NOT IN ('FINISHED', 'FAILED') OR finished_at IS NOT NULL);

-- 失败必须有原因
ALTER TABLE m16_reconcile_task
    ADD CONSTRAINT ck_m16_reconcile_fail
    CHECK (status <> 'FAILED' OR fail_reason IS NOT NULL);

-- 账单日期不得是未来
ALTER TABLE m16_reconcile_task
    ADD CONSTRAINT ck_m16_reconcile_date
    CHECK (bill_date <= CURRENT_DATE);

COMMENT ON TABLE m16_reconcile_task IS '对账任务表：每个"日期 × 渠道"一次对账的完整过程与汇总';
COMMENT ON COLUMN m16_reconcile_task.bill_date IS '渠道账单日期';
COMMENT ON COLUMN m16_reconcile_task.is_balanced IS '是否平账，即差异笔数为 0';
COMMENT ON COLUMN m16_reconcile_task.status IS 'DOWNLOADED已下载/RUNNING对账中/FINISHED完成/FAILED失败';
```

**关键约束说明：`uk_m16_reconcile_running`**

两条部分唯一索引确保：

- 同一「日期 × 渠道」**同一时刻只能有一个 RUNNING 任务** → 防止并发对账产生重复差异记录（错误码 54950）
- 同一「日期 × 渠道」可以有多个 FINISHED（重新对账覆盖），但只需保留最新一份有效结果

|---|---|---|---|

| `EXPIRED` | 已过期 | ✅ | — |
| `CLOSED` | 已关闭 | ✅ | — |
| `UNKNOWN` | 结果未知 | 否 | SUCCESS（查单/补单后） |

| 代码 | 名称 | 终态 | 可转 |
|---|---|---|---|
| `CREATED` | 已创建 | 否 | PROCESSING / SUCCESS / FAILED / ABNORMAL |

| `SUCCESS` | 退款成功 | ✅ | — |
| `FAILED` | 退款失败 | 否 | CREATED（重试）/ ABNORMAL |
