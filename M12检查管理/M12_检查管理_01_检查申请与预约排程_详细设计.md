## 1. 模块概述

### 1.1 模块定位

检查申请与预约排程是 M12 检查管理的**入口**。它回答一个问题：

> **"这个患者要做什么检查、去哪台设备做、什么时候轮到？"**

```
┌───────────────────────────────────────────────────────────────┐
│  M07-03 医嘱下达 / M07-04 检查检验申请                          │
│  "医生开了 OCT 黄斑（右眼），为什么要开，开给谁"                 │
└───────────────────────────┬───────────────────────────────────┘
                            │ 申请单（EXAM_REQUEST 已收费）
                            ▼
┌───────────────────────────────────────────────────────────────┐
│  M12-01 检查申请与预约排程（本文档）★ 检查任务的产生者          │
│  · 接住医生开的申请单，转成可执行的检查任务                       │
│  · 按设备产能生成号源，接受预约                                  │
│  · 患者到检时登记，进入叫号队列                                  │
│  · 调用检查后交给 M12-02 执行                                    │
└───────────────────────────┬───────────────────────────────────┘
                            │ 检查任务（EXAM_TASK，已到检）
                            ▼
┌───────────────────────────────────────────────────────────────┐
│  M12-02 检查执行与技师工作台                                     │
│  "技师在设备上做完检查，生成结算凭条与时间窗"                     │
└───────────────────────────────────────────────────────────────┘
```

**一句话边界：** M12-01 只管**"谁要做、什么时候、在哪台设备"**。管不了"怎么做"（M12-02）、"报告怎么来"（M12-03/04）。

### 1.2 为什么独立成子模块

有人会问：检查申请不就是医生开单、技师来做，中间有什么好设计的？把它和 M12-02 合在一起不行吗？

不行的理由有四条。

#### 理由一：检查的"号源"和门诊号源是两种东西

门诊号源是"某个医生某个时段能看多少个患者"，一维的。检查号源是"某台设备某个时段能做多少个检查"，而且**不同检查项目占用设备的时间不同**：

| 检查项目 | 单次时长 | 一台设备一天能做的量 |
|---|---|---|
| 眼压 | 3 分钟 | 100+ 人次 |
| OCT 黄斑 | 8 分钟 | 55 人次 |
| 视野 | 15 分钟 | 25 人次 |
| FFA 眼底造影 | 45 分钟 | 8 人次 |
| UBM | 20 分钟 | 18 人次 |

如果按门诊号源的逻辑（固定时段固定数量），FFA 会严重超号，眼压会严重浪费。**必须有独立的设备产能模型**。

#### 理由二：检查要"预约"，而预约意味着要管"爽约"

眼科检查里，OCT、视野、FFA 这些项目患者当天可能做不完（散瞳要等 30 分钟、FFA 要观察过敏反应），很多医院采用"预约到某天某时段"的方式分流。

一旦有预约，就有：

- 患者没来（爽约）——号源要不要释放？什么时候释放？
- 患者迟到了——还能不能插进去？
- 设备坏了——已约的患者怎么改约？
- 医生开单后患者直接去检查，不预约——这种"即时检查"怎么算？

**这些问题都属于"排程"，不属于"执行"。** 合在一起会让 M12-02 变成一个既管排队又管操作的大杂烩。

#### 理由三：检查申请会"撤销"和"退费"，这必须和执行解耦

医生开了 OCT，患者缴了费，技师刚要开始，患者说"我不做了要退费"。

这时候：

- 检查任务要作废
- 已占用的号源要释放
- 要向 M16 发退费通知
- 如果技师已经开始做了，就不能退（服务已经提供）

**"取消"和"执行"是两件不同的事，必须在不同模块、不同权限下完成。** 技师没有退费权限，收费员没有作废检查任务的权限。

#### 理由四：本项目 OCR 方案的"时间窗"必须在预约排程里打好基础

这是本项目特有的一条，也是最关键的一条。

因为检查设备无法接入 HIS，报告靠 PDF + OCR 解析。而 OCR 解析出的 PDF **没有患者 ID 号**，只有姓名、性别、年龄。要把 PDF 对应到正确的人，唯一可靠的线索是**"这份 PDF 是什么时间产生的"+"当时谁在做检查"**。

所以 M12-02 必须记录精确的时间窗（技师点"开始检查"和"完成检查"的时刻）。但时间窗要能成立，前提是**系统知道"哪些人此刻应该在设备上"**——这是 M12-01 到检登记与叫号的职责。

**M12-01 是 OCR 患者绑定的数据地基。** 如果到检登记糊涂，后面的自动绑定就不可能准。

### 1.4 概念辨析

#### 1.4.1 检查申请 ≠ 检查任务

| 概念 | 定义 | 产生方 | 关键字段 |
|---|---|---|---|
| **检查申请单**（Exam Request） | 医生在 M07 开的、已收费的单据 | M07-03 / M07-04 | `request_no` / `patient_id` / `item_code` |
| **检查任务**（Exam Task） | M12 内部可调度、可执行的作业单元 | **M12-01** | `task_no` / `device_id` / `slot_id` / `status` |

为什么要分两层？

一张检查申请单可能对应**多个检查任务**。典型场景：

- 医生开了"双眼 OCT + 双眼眼压"，这是 1 张申请单、2 个检查项目、4 个检查任务（OCT 右眼、OCT 左眼、眼压右眼、眼压左眼）
- 因为分眼别计费（`md_exam_item.is_eye_side_charge = TRUE`），每个眼别是独立的收费项，也是独立的检查动作

反过来，一个检查任务也可能来源于多个申请单（如"双眼 OCT"合并成一次设备操作）。但本项目**不做合并**——理由见 1.4.4。

#### 1.4.2 预约 ≠ 排程

| 概念 | 定义 | 谁决定 |
|---|---|---|
| **排程**（Scheduling） | 系统按设备产能生成"哪些时段可约" | 系统自动 |
| **预约**（Appointment） | 患者占用了一个具体时段 | 患者/护士选择 |

排程是"供给"，预约是"需求"。M12-01 同时管两者。

#### 1.4.3 即时检查 ≠ 预约检查

| 类型 | 场景 | 是否占用号源 | 是否进叫号队列 |
|---|---|---|---|
| **即时检查**（`WALK_IN`） | 患者开单缴完费直接去检查室 | 不占号源 | 进队列，按到检时间排 |
| **预约检查**（`APPOINTMENT`） | 患者约好明天 9:00 做 FFA | 占号源 | 进队列，按预约时间优先 |

眼科门诊高峰期（上午 8:30~11:30）绝大多数是即时检查；FFA、视野、ERG 这类耗时长的项目多采用预约。

#### 1.4.4 为什么不合并双眼检查任务

有人会问：患者做"双眼 OCT"，技师实际就是按两下按钮，为什么非要拆成两个任务？

不合并的理由：

1. **计费是分开的**。`md_exam_item.is_eye_side_charge = TRUE` 时，右眼和左眼是两笔收费（M16 里的两条结算明细）。如果任务合并，报告和收费就无法一一对应。
2. **OCR 报告是分开的**。设备导出的 PDF 通常一份一个眼别（OCT 报告右上角写"OD"或"OS"），少数设备出一份双眼报告。绑定逻辑必须按眼别处理。
3. **可能只做一只眼**。患者右眼做了，左眼因为流泪做不了，要改天再来。合并任务无法表达"右眼已完成、左眼未做"。
4. **退费是分开的**。患者只退左眼那笔钱，任务必须能独立作废。

因此**一个眼别 = 一个检查任务**，不可合并。

### 1.5 模块目标

| 指标 | 目标值 | 说明 |
|---|---|---|
| 检查申请接单成功率 | ≥ 99.5% | M07 推送后 1 秒内落库 |
| 设备号源准确率 | 100% | 号源数不超过设备日产能 |
| 号源浪费率 | ≤ 5% | 已排未用的号源占比 |
| 爽约率 | ≤ 8% | 预约未到的占比 |
| 到检登记耗时 | ≤ 20 秒 | 扫码到确认 |
| 候检平均等待时长 | ≤ 15 分钟 | 即时检查 |
| 平均等待时长 P90 | ≤ 30 分钟 | 即时检查 |
| 检查任务作废响应 | ≤ 500ms | 含退费通知 |
| 号源查询响应 | P95 ≤ 100ms | 单日单设备 |
| 排程生成耗时 | ≤ 3s | 单设备一日 |
| 并发挂号冲击 | 200 TPS | 高峰期无锁等待 |

**为什么要盯"号源浪费率"和"爽约率"？**

因为检查设备是眼科医院最贵的资产。一台 OCT 一两百万，一台视野计几十万。设备空转一小时，就是几百元的折旧与人力浪费。号源管不好，要么患者排队几小时，要么设备晒太阳。

## 3. 业务模型

### 3.1 检查任务生命周期

检查任务（`m12_exam_task`）是 M12 的核心对象，状态机如下：

```
                         ┌──────────────┐
                         │   CREATED    │  申请已接单，任务已生成
                         └──────┬───────┘
                                │ 排程/预约
                 ┌──────────────┼──────────────┐
                 │              │              │
                 ▼              ▼              ▼
          ┌───────────┐  ┌───────────┐  ┌───────────┐
          │ SCHEDULED │  │  WAITING  │  │ CANCELLED │
          │  已预约   │  │ 即时待检  │  │  已作废   │
          └─────┬─────┘  └─────┬─────┘  └───────────┘
                │              │
                │ 患者到检登记  │
                └──────┬───────┘
                       ▼
                ┌──────────────┐
                │   CHECKED_IN │  已到检，进入候检队列
                └──────┬───────┘
                       │ 叫号
                       ▼
                ┌──────────────┐
                │    CALLED    │  已叫号
                └──────┬───────┘
                       │ 技师接管
                       ▼
                ┌──────────────┐
                │   EXECUTING  │  执行中（时间窗开启）
                └──────┬───────┘
                       │ 完成检查
                       ▼
                ┌──────────────┐
                │   EXECUTED   │  已执行，等待报告文件
                └──────┬───────┘
                       │ M12-05 推送报告到 M07
                       ▼
                ┌──────────────┐
                │     DONE     │  终态：报告已发布
                └──────────────┘
```

**旁支状态：**

| 状态 | 由谁触发 | 说明 |
|---|---|---|
| `NO_SHOW` | 定时任务 | 预约时间过后 30 分钟未到检 |
| `SKIPPED` | 技师 | 到检后叫号 3 次无应答，移出队列 |
| `FAILED` | 技师 | 检查失败（患者配合不佳、设备故障） |
| `RETURNED` | 技师 | 需要重做 |
| `CANCELLED` | 医生/收费员 | 作废并退费 |

**状态转移矩阵：**

| 当前状态 | 允许转换到 | 触发方 | 说明 |
|---|---|---|---|
| `CREATED` | `SCHEDULED` / `WAITING` / `CANCELLED` | M12-01 | 预约则可约，即时则待检 |
| `SCHEDULED` | `CHECKED_IN` / `NO_SHOW` / `CANCELLED` | M12-01 / 定时 | |
| `WAITING` | `CHECKED_IN` / `CANCELLED` | M12-01 | |
| `CHECKED_IN` | `CALLED` / `SKIPPED` / `CANCELLED` | M12-01 | 到检后仍可取消（未开始执行） |
| `CALLED` | `EXECUTING` / `SKIPPED` | M12-02 | 叫号后技师接管 |
| `EXECUTING` | `EXECUTED` / `FAILED` | M12-02 | **执行中不可取消** |
| `EXECUTED` | `DONE` / `RETURNED` | M12-05 / 技师 | |
| `FAILED` | `WAITING` / `CANCELLED` | M12-02 | 可重排 |
| `RETURNED` | `WAITING` | M12-02 | 重做 |
| `SKIPPED` | `CHECKED_IN` | M12-01 | 患者回来了重新排队 |
| `NO_SHOW` | `CHECKED_IN` / `CANCELLED` | M12-01 | 患者后来到了 |

**终态：** `DONE` / `CANCELLED`

### 3.2 设备产能模型

这是 M12-01 与 M04 排班的本质区别。设备产能由三个因素决定：

```
每日可预约号源数 = MIN(
    设备日最大检查量,           ← 来自 md_device.max_daily_volume
    可用时段数 × 每时段可做数   ← 来自设备排班
)
```

**每时段可做数** = `时段长度 ÷ 项目单次时长`（向下取整）

举例：OCT 设备上午 8:00~12:00（4 小时 = 240 分钟）：

| 项目 | 单次时长 | 每台可做 | 4 小时可做 |
|---|---|---|---|
| OCT 黄斑 | 8 分钟 | 一台设备 | 30 人次 |
| OCT 视盘 | 8 分钟 | 一台设备 | 30 人次 |
| 眼压 | 3 分钟 | 一台设备 | 80 人次 |

但 OCT 设备和眼压计通常是**两台设备**，不能混算。

**产能模型的关键约束：**

1. **同一台设备同一时段只能做一个检查**。设备是独占资源。
2. **不同项目时长不同，混排会浪费**。若 8:00 排了 FFA（45 分钟），8:45 才能排下一个。
3. **产能按"项目"而非"设备"计算**。一台眼底相机既能做眼底照相（5 分钟）也能做 FFA（45 分钟），混排时产能是浮动的。

所以号源生成必须**按时段切分 + 按项目分配配额**：

```
设备 OCT-01 上午排班 08:00~12:00
├── OCT 黄斑：配额 20 个（每个 8 分钟，共 160 分钟）
├── OCT 视盘：配额 6 个（每个 8 分钟，共 48 分钟）
└── 缓冲：32 分钟（设备调整、患者准备、临时加急）

设备眼底相机 CAM-01 上午排班 08:00~12:00
├── 眼底照相：配额 20 个（每个 5 分钟，共 100 分钟）
├── FFA：配额 2 个（每个 45 分钟，共 90 分钟）
└── 缓冲：50 分钟
```

配额由 **M12-06** 维护，M12-01 只消费。

### 3.5 时间窗模型（OCR 绑定的数据基础）

这是本项目特有的一节。因为报告靠 PDF + OCR 绑定患者，时间窗是绑定的主要依据。

```
技师在 HIS 点"开始检查"
    │
    ▼
┌───────────────────────────────────────────┐
│ 写 m12_exam_task.exec_started_at = NOW()  │
│ 同时写 m12_exam_window：                   │
│   · window_start = NOW() - 120 秒（容差）  │
│   · window_end   = NOW() + 预计时长+300 秒 │
│   · device_id / item_code / eye_side      │
│   · patient_id（确定的！）                  │
└───────────────────────────────────────────┘
    │
    ▼  技师在设备上操作（HIS 不知情）
    │
    ▼  技师把 PDF 导出到共享文件夹（HIS 不知情）
    │
    ▼
┌───────────────────────────────────────────┐
│ 技师在 HIS 点"完成检查"                     │
│   · exec_finished_at = NOW()               │
│   · 窗口 window_end = NOW() + 300 秒延迟   │
└───────────────────────────────────────────┘
```

**时间窗的容差设计：**

| 容差 | 值 | 理由 |
|---|---|---|
| 开始前容差 | 120 秒 | 技师可能先做检查、后点"开始"（手忙时） |
| 结束后容差 | 300 秒 | 技师做完再看电脑点"完成"，可能滞后几分钟 |
| 最大窗口长度 | 3600 秒 | 防止技师忘记点"完成"，窗口无限拉长 |

**为什么结束容差（300 秒）比开始容差（120 秒）大？**

因为现实中技师更可能"先干活、后补录"：做完检查，患者走了，技师才回到电脑点击"完成"。而"开始"通常是在患者进门前点的，比较及时。

**窗口重叠怎么办？**

如果技师忘记点"完成"，下一个患者开始了，两个窗口会重叠。这时：

1. 系统检测到重叠，将两个窗口都标记 `is_ambiguous = TRUE`
2. 这两个窗口内收到的 PDF 全部进入"待确认队列"，不做自动绑定
3. 提醒技师补录实际完成时间

**时间窗是 M12-02 产生的，M12-04 消费的。** M12-01 只负责让"到检登记"准确，从而让时间窗有干净的起点。

### 3.6 停诊与改约模型

设备故障、医生临时停诊、系统维护，都需要"停诊"。

```
停诊发起
    │
    ├─ 单次停诊：某设备某天某时段
    ├─ 半天停诊：某设备某天上午
    └─ 长期停诊：某设备维修 N 天
    │
    ▼
┌─────────────────────────────────────┐
│ 找出受影响的患者（已约该时段的任务） │
└──────────────┬──────────────────────┘
               ▼
┌─────────────────────────────────────┐
│ 处理策略（三选一或组合）：           │
│  A. 自动改约到最近的可用时段          │
│  B. 标记"待改约"，人工电话通知        │
│  C. 作废并退费                        │
└──────────────┬──────────────────────┘
               ▼
┌─────────────────────────────────────┐
│ 通知患者（M03-05 短信/微信）         │
└─────────────────────────────────────┘
```

**默认策略是 B（待改约）**，不自动改约。理由：检查项目有准备要求（如 FFA 要空腹、要家属陪同），自动改约到不合适的时间对患者是负担。

### 6.2 错误码规范

| 错误码 | 说明 | 触发场景 |
|---|---|---|
| `"1201001"` | 检查申请不存在或未同步 | M07 未推送或已删除 |
| `"1201002"` | 检查项目不存在或已停用 | 项目编码无效 |
| `"1201003"` | 检查申请未收费 | 收费状态校验失败 |
| `"1201004"` | 检查申请状态不允许接单 | 非 SIGNED/PAID |
| `"1201005"` | 检查已开始执行，不可作废 | 状态 ≥ EXECUTING |
| `"1201006"` | 作废原因不足 5 字 | 作废参数校验 |
| `"1201007"` | 检查任务已作废 | 状态 = CANCELLED |
| `"1201008"` | 配额总数超过设备日产能 | 排程配置 |
| `"1201009"` | 该时段已停诊 | 预约时校验 |
| `"1201010"` | 所选时段号源已满 | 并发或重复预约 |
| `"1201011"` | 预约日期不能早于今天 | 日期校验 |
| `"1201012"` | 该任务已预约，不可重复预约 | 幂等 |
| `"1201013"` | 任务状态不允许到检 | 非 SCHEDULED/WAITING |
| `"1201014"` | 停诊开始时间必须早于结束时间 | 停诊参数 |
| `"1201015"` | 停诊原因必填 | 停诊参数 |
| `"1201016"` | 设备不存在或已停用 | 设备校验 |
| `"1201017"` | 设备排班未配置 | 号源生成 |
| `"1201018"` | 该任务不属于当前设备队列 | 叫号校验 |
| `"1201019"` | 检查申请服务（M07）不可用 | 上游超时 |
| `"1201020"` | 检查主数据（M01-09）不可用 | 上游超时 |
| `"1201021"` | 收费服务（M16）不可用 | 上游超时 |
| `"1201022"` | 就诊会话已结束，检查任务应作废 | 患者已离院 |
| `"1201023"` | 加急标记需说明理由（≥10 字） | 加急参数 |

### 6.7 号源并发控制

号源是稀缺资源，高峰期多个窗口同时预约同一时段，必须保证不超卖。

```python
"""M12-01 号源并发控制 —— 三级防护。"""
import logging
from datetime import datetime

from sqlalchemy import select, update

from app.core.exception import BizException
from app.core.redis_client import redis
from app.models.m12_exam import M12ExamSlot, M12ExamAppointment

logger = logging.getLogger(__name__)

SLOT_LOCK_TTL = 30


class SlotConcurrencyGuard:
    """号源并发三级防护。

    第一级：Redis 原子计数（快速失败，避免打 DB）
    第二级：DB 行锁 + 条件更新（保证不超卖）
    第三级：数据库约束（used_count <= capacity，最后防线）
    """

    @staticmethod
    async def acquire(db, slot_id: int, user: dict) -> dict:
        """占用一个号源。"""
        lock_key = "m12:slot:%d:lock" % slot_id
        counter_key = "m12:slot:%d:used" % slot_id

        # 第一级：Redis 锁，防止同一时段被并发修改
        acquired = await redis.set(lock_key, "1", nx=True, ex=SLOT_LOCK_TTL)
        if not acquired:
            raise BizException("1201010", "该时段正在被占用，请稍后重试")

        try:
            # 查询号源（预热 Redis 计数）
            slot = await db.scalar(
                select(M12ExamSlot).where(M12ExamSlot.id == slot_id)
            )
            if not slot:
                raise BizException("1201010", "号源不存在")
            if slot.is_suspended:
                raise BizException("1201009", "该时段已停诊")

            cached = await redis.get(counter_key)
            if cached is None:
                await redis.set(counter_key, slot.used_count, ex=3600)

            # 第二级：DB 条件更新（核心防超卖）
            result = await db.execute(
                update(M12ExamSlot)
                .where(
                    M12ExamSlot.id == slot_id,
                    M12ExamSlot.used_count < M12ExamSlot.capacity,
                    M12ExamSlot.is_suspended.is_(False),
                )
                .values(used_count=M12ExamSlot.used_count + 1)
            )
            if result.rowcount == 0:
                # 条件不满足：要么已满，要么已停诊
                await db.rollback()
                raise BizException("1201010", "所选时段号源已满")

            await db.flush()

            # 第一级：Redis 计数递增（仅用于快速查询展示，不作为真相）
            await redis.incr(counter_key)

            logger.info("号源占用成功 slot_id=%d operator=%s",
                        slot_id, user.get("employee_name"))
            return {"slot_id": slot_id, "acquired": True}

        finally:
            await redis.delete(lock_key)

    @staticmethod
    async def release(db, slot_id: int) -> dict:
        """释放一个号源。"""
        result = await db.execute(
            update(M12ExamSlot)
            .where(M12ExamSlot.id == slot_id, M12ExamSlot.used_count > 0)
            .values(used_count=M12ExamSlot.used_count - 1)
        )
        await redis.decr("m12:slot:%d:used" % slot_id)
        return {"slot_id": slot_id, "released": result.rowcount > 0}
```

**为什么用 Redis 锁 + DB 条件更新，而不是只用其中一种？**

| 方案 | 问题 |
|---|---|
| 只用 Redis 计数 | Redis 宕机或重启后计数丢失，会导致超卖 |
| 只用 DB 行锁 `SELECT FOR UPDATE` | 高峰期所有预约串行，P95 从 50ms 变成 300ms |
| **Redis 锁 + DB 条件更新** | Redis 只做"熔断"（防止同时冲进来），DB 条件更新是真正的不超卖保证 |

**第三级防护是数据库 CHECK 约束**：`CHECK (used_count <= capacity)`。即使应用层有 bug，DB 会拒绝超卖。

### 7.1 Redis 缓存

| Key 模式 | 类型 | TTL | 说明 |
|---|---|---|---|
| `m12:slot:{slot_id}:used` | String | 3600s | 号源已用数（仅展示用，真相在 DB） |
| `m12:slot:{slot_id}:lock` | String | 30s | 号源占用互斥锁 |
| `m12:slots:{device_id}:{date}` | Hash | 600s | 某设备某天全部号源（加速号源查询） |
| `m12:schedule:{date}` | Hash | 600s | 某天所有设备排程 |
| `m12:queue:{device_id}` | ZSet | 300s | 候检队列（score = 优先级时间戳） |
| `m12:queue:seq:{device_id}:{date}` | String | 86400s | 排队号序列 |
| `m12:device:{device_id}` | Hash | 3600s | 设备信息缓存 |
| `m12:examitem:{item_code}` | Hash | 3600s | 检查项目缓存 |
| `m12:window:{device_id}` | Set | 600s | 该设备活跃时间窗（M12-04 用） |
| `m12:stat:{start}:{end}` | String | 1800s | 统计结果缓存 |

**容量估算：**

- 号源：6 台设备 × 16 个时段 = 96 个 slot，每 key 约 200B → **约 20KB**
- 队列：每设备最多 50 人，6 台 → 300 条，每条约 100B → **约 30KB**
- 设备与项目缓存：各 100 条 → **约 100KB**
- **合计约 150KB**，极小

## 8. 业务规则与校验

### 8.1 申请接单规则

| 编号 | 规则 | 错误码 |
|---|---|---|
| R-01 | 申请单必须已收费才可接单 | `"1201003"` |
| R-02 | 检查项目必须存在且状态为 `ENABLED` | `"1201002"` |
| R-03 | 同一申请单同一项目同一眼别只生成一个任务 | 幂等 |
| R-04 | 申请单重复推送不重复建任务 | 幂等 |
| R-05 | 双眼项目（`eye_side=OU`）生成一个任务而非两个 | — |
| R-06 | `is_eye_side_charge=FALSE` 的项目双眼只收一次费 | — |

**关于 R-05：为什么 `OU` 只生成一个任务？**

`md_exam_item.laterality` 有三种取值：

- `LEFT`：只能查左眼 → 每个申请生成一个任务（`OS`）
- `RIGHT`：只能查右眼 → 一个任务（`OD`）
- `BOTH`：可查双眼 → 医生开单时指定 `OD` / `OS` / `OU`

当医生开 `OU` 时，如果 `is_eye_side_charge = TRUE`，收费是两笔，但**检查动作是一次**（技师点一次按钮，设备出双眼报告）。所以任务只生成一个，但 `charge_item_count = 2`。

**这直接影响 OCR 绑定**：一个 `OU` 任务对应一份双眼报告 PDF。
