**设计说明：**

1. **全部表不建数据库外键**。理由：
   - 检查执行是高频写入场景（日均 420 次开始 + 420 次完成），外键检查会增加写锁竞争
   - `m12_exam_task` 可归档，但 `m12_exam_node` 保留更久，外键会阻止归档
   - 一致性由应用层事务保证，跨表校验在 Service 层完成

2. **`m12_exam_window` 的主表定义在 M12-01**，本文档只追加 3 个字段。该表是 OCR 绑定的核心，两个子模块共同维护，变更需双方确认。

3. **`m12_exam_ticket` 与任务 1:1（非 VOID 时）**。凭条可以重新生成，旧凭条置 `VOID`，因此实际是 1:N 但有效记录 1:1。

4. **`m12_exam_node` 与 `m12_exam_window_log` 分离**：
   - `m12_exam_node` 记录**任务级**事件（开始、完成、失败、补录、凭条打印）
   - `m12_exam_window_log` 记录**窗口级**变更（创建、闭合、截断、重算、重叠标记）
   - 分开的原因：窗口是独立实体，一个任务可能有多个窗口（补录后重算会生成新版本），窗口变更需要独立追溯

**约束说明：**

```sql
ALTER TABLE m12_exam_correction
  ADD CONSTRAINT ck_m12_correction_no
  CHECK (correction_no ~ '^CR[0-9]{8}[0-9]{4}$');

-- 开始必须早于完成
ALTER TABLE m12_exam_correction
  ADD CONSTRAINT ck_m12_correction_order
  CHECK (new_start_at < new_finish_at);

-- 完成时间不能在未来（容忍 5 分钟时钟误差）
ALTER TABLE m12_exam_correction
  ADD CONSTRAINT ck_m12_correction_not_future
  CHECK (new_finish_at <= NOW() + INTERVAL '5 minutes');

-- 检查时长不超过 4 小时
ALTER TABLE m12_exam_correction
  ADD CONSTRAINT ck_m12_correction_duration
  CHECK (new_finish_at - new_start_at <= INTERVAL '4 hours');

-- 详细说明不足 10 字拒绝
ALTER TABLE m12_exam_correction
  ADD CONSTRAINT ck_m12_correction_desc
  CHECK (char_length(btrim(reason_desc)) >= 10);

-- 补录原因枚举
ALTER TABLE m12_exam_correction
  ADD CONSTRAINT ck_m12_correction_reason
  CHECK (correct_reason IN ('FORGOT_START','FORGOT_FINISH',
                            'SYSTEM_LAG','NETWORK_DOWN','OTHER'));

-- 状态枚举
ALTER TABLE m12_exam_correction
  ADD CONSTRAINT ck_m12_correction_status
  CHECK (status IN ('PENDING','EFFECTIVE','REJECTED'));

-- PENDING 状态不允许有审批信息
ALTER TABLE m12_exam_correction
  ADD CONSTRAINT ck_m12_correction_pending
  CHECK (status <> 'PENDING'
         OR (approver_id IS NULL AND approved_at IS NULL));

-- EFFECTIVE 必须有完整审批信息，且审批时间不早于提交时间
ALTER TABLE m12_exam_correction
  ADD CONSTRAINT ck_m12_correction_approved
  CHECK (status <> 'EFFECTIVE'
         OR (approver_id IS NOT NULL
             AND approved_at IS NOT NULL
             AND approved_at >= created_at));

-- REJECTED 必须有审批人（谁驳回的）
ALTER TABLE m12_exam_correction
  ADD CONSTRAINT ck_m12_correction_rejected
  CHECK (status <> 'REJECTED' OR approver_id IS NOT NULL);

-- 超过 24 小时标记必须为 TRUE 才可走审批通道（业务校验辅助）
ALTER TABLE m12_exam_correction
  ADD CONSTRAINT ck_m12_correction_overdue
  CHECK (is_overdue = FALSE OR status IN ('PENDING','EFFECTIVE','REJECTED'));

-- 补录人不能是审批人（职责分离）
ALTER TABLE m12_exam_correction
  ADD CONSTRAINT ck_m12_correction_self_approve
  CHECK (approver_id IS NULL OR approver_id <> operator_id);

COMMENT ON TABLE m12_exam_correction IS '检查时间补录表：记录技师忘记点开始/完成后的补录，不覆盖原值';
COMMENT ON COLUMN m12_exam_correction.correction_no IS '补录单号 CR+YYYYMMDD+4位序号';
COMMENT ON COLUMN m12_exam_correction.is_overdue IS '是否超过24小时才补录，TRUE时需科主任审批';
COMMENT ON COLUMN m12_exam_correction.window_before_start IS '补录前的时间窗开始时刻，用于追溯变更';
COMMENT ON COLUMN m12_exam_correction.window_after_start IS '补录后的时间窗开始时刻';
```

**状态机：**

```
       提交补录
          │
          ▼
    ┌───────────┐  超过24h  ┌────────────────┐
    │  PENDING  │──────────►│ 需审批（is_overdue│
    │  （待审批）│           │   = TRUE）     │
    └─────┬─────┘           └───────┬────────┘
          │                         │
    未超24h│                    ┌────┴────┐
          │                    │         │
          │                 通过│      驳回│
          ▼                    ▼         ▼
    ┌───────────┐        ┌──────────┐ ┌──────────┐
    │ EFFECTIVE │        │EFFECTIVE │ │ REJECTED │
    │ （已生效） │        │（已生效） │ │ （已驳回）│
    └───────────┘        └──────────┘ └──────────┘
```

**设计要点：**

1. **为什么保留 `old_start_at` / `old_finish_at`？** 补录后原值会写入 `m12_exam_task`，但补录记录本身需要保留"改之前是什么"，否则无法回答"这个时间改过几次、每次从多少改到多少"。

2. **为什么同时存 `window_before_*` 和 `window_after_*`？** 因为窗口是 OCR 绑定的依据，改窗口可能影响已绑定关系。记录前后值可以在纠纷时证明"当时窗口是这个范围，所以才绑定了这份 PDF"。

3. **`is_overdue` 冗余存储**：每次判断是否超过 24 小时都要跟 `created_at` 比较，但 `created_at` 是提交时间，不是实际检查时间。应该比较 `new_finish_at`（真实完成时间）。冗余存一个布尔值，查询和报表都方便。

4. **`status='PENDING'` 时窗口已重算但不生效？** 不是。**PENDING 时窗口尚未重算**，补录只在 `EFFECTIVE` 后才写入任务与窗口。因此 `window_after_*` 在 PENDING 阶段存的是"预计变更后的值"，供审批人预览。

**量级估算：**

| 指标 | 估算 |
|---|---|
| 日均补录 | 约 8 条（日任务 420 × 2%） |
| 年记录数 | 约 2,900 条 |
| 单行大小 | 约 600 字节 |
| 年增量 | 约 1.7 MB |
| 保留期 | 5 年（医疗记录追溯） |
| 5 年总量 | 约 14,500 行，8.7 MB |

**分区：** 不分区。数据量太小（5 年 1.4 万行），分区收益为负。

**凭条号生成算法：**

```
ticket_no = "DT"
          + device_seq (2 位，设备在主数据中的序号，01~99)
          + yyyyMMdd  (8 位日期)
          + daily_seq (3 位，该设备当日序号，001~999)

示例：DT 01 20261022 007
      │  │  │        └─ 该设备当日第 7 张
      │  │  └────────── 2026-10-22
      │  └───────────── 设备序号 01（OCT-01）
      └──────────────── 投递凭条前缀

冲突处理：
  当日序号 > 999 时，改用 4 位（总长 14，超出限制）
  → 实际不可能：单设备日均最多 100 例，全年不会到 999
  → 保险措施：Redis INCR 超过 999 抛异常并告警
```

**为什么凭条号里要带设备序号？**

因为如果只用 `DT + 日期 + 序号`，多台设备的技师同时打印会互相干扰序列。带设备序号后，每台设备有独立序列，不冲突。

**为什么不用 UUID？**

因为技师要手动输入或复制这个号码。13 位纯数字相对好输入，UUID 根本没法输。

```sql
-- 按 event_at 月度 RANGE 分区，预建 36 个月
CREATE TABLE m12_exam_node (
  id          BIGINT GENERATED BY DEFAULT AS IDENTITY,
  seq_date    DATE NOT NULL,
  task_id     BIGINT NOT NULL,
  -- ... 其余字段
  PRIMARY KEY (id, seq_date)
) PARTITION BY RANGE (seq_date);

DO $$
DECLARE
  base DATE := DATE_TRUNC('month', CURRENT_DATE) - INTERVAL '12 months';
BEGIN
  FOR i IN 0..35 LOOP
    EXECUTE format(
      'CREATE TABLE IF NOT EXISTS m12_exam_node_p%s PARTITION OF m12_exam_node
       FOR VALUES FROM (%L) TO (%L)',
      TO_CHAR(base + (i || ' month')::interval, 'YYYYMM'),
      base + (i || ' month')::interval,
      base + ((i + 1) || ' month')::interval
    );
  END LOOP;
END $$;
```

**为什么 `m12_exam_node` 要分区，`m12_exam_ticket` 不用？**

| 表 | 年行数 | 查询模式 | 结论 |
|---|---|---|---|
| `m12_exam_node` | 约 50 万（每任务约 8 个事件） | 主要查近期（30 天内），历史查询少 | 分区收益明显 |
| `m12_exam_ticket` | 约 15 万 | 按 ticket_no 精确查（跨年常见） | 分区会让精确查变慢 |

**关键点：分区表的唯一索引必须包含分区键。** 所以 `m12_exam_node` 的主键是 `(id, seq_date)`。

### 4.10 对 `m12_exam_window` 的字段追加

`m12_exam_window` 的主表定义在 [检查申请与预约排程数据结构](M12_检查管理_01_检查申请与预约排程_数据结构.md) 4.7 节。M12-02 的执行业务需要追加以下 **3 个字段**：

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| is_truncated | BOOLEAN | 否 | FALSE | 是否被截断（超过最大长度） |
| is_valid | BOOLEAN | 否 | TRUE | 窗口是否有效（检查失败时为 FALSE） |
| invalid_reason | VARCHAR(200) | 是 | NULL | 无效原因 |

**追加 SQL：**

```sql
ALTER TABLE m12_exam_window
  ADD COLUMN IF NOT EXISTS is_truncated BOOLEAN NOT NULL DEFAULT FALSE,
  ADD COLUMN IF NOT EXISTS is_valid BOOLEAN NOT NULL DEFAULT TRUE,
  ADD COLUMN IF NOT EXISTS invalid_reason VARCHAR(200);

ALTER TABLE m12_exam_window
  ADD CONSTRAINT ck_m12_window_truncated
  CHECK (is_truncated = FALSE OR window_end IS NOT NULL);

ALTER TABLE m12_exam_window
  ADD CONSTRAINT ck_m12_window_invalid
  CHECK (is_valid = TRUE OR invalid_reason IS NOT NULL);

COMMENT ON COLUMN m12_exam_window.is_truncated
  IS '是否被截断：技师忘记点完成，窗口超过最大长度时自动收窄';
COMMENT ON COLUMN m12_exam_window.is_valid
  IS '窗口是否有效：检查失败时为 FALSE，不参与 OCR 绑定';
COMMENT ON COLUMN m12_exam_window.invalid_reason
  IS '窗口无效原因';

-- 有效窗口索引（OCR 绑定只查有效窗口）
CREATE INDEX IF NOT EXISTS idx_m12_window_valid
  ON m12_exam_window (device_id, window_start, window_end)
  WHERE is_valid = TRUE AND is_deleted = FALSE;
```

**为什么这三个字段放在 `m12_exam_window` 而不是单独建表？**

1. **一对一关系**：一个窗口只有一组状态标记，拆表会导致每次查询都要 JOIN
2. **查询频率极高**：OCR 绑定时每份 PDF 都要查窗口有效性，JOIN 会拖慢
3. **变更频率低**：`is_truncated` / `is_valid` 只在特定事件时变一次，不会频繁更新

**两个子模块共同维护该表的约定：**

| 子模块 | 写哪些字段 |
|---|---|
| M12-01 检查申请与预约排程 | `id` / `window_no` / `task_id` / `device_id` / `patient_*` / `exec_*` / `window_start` / `window_end` / `window_source` / `is_ambiguous` |
| **M12-02 检查执行与技师工作台** | `is_truncated` / `is_valid` / `invalid_reason` / `window_end`（闭合时）/ `window_start`（截断时） |

**变更流程：** 任一方修改该表结构，需在双方文档同步更新，并在 `M12_检查管理_数据结构设计汇总.md` 记录变更。
