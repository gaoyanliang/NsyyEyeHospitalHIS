**设计说明：**

1. **`m12_parse_record` 是主表，一文件一记录。** 用 `file_id` 业务唯一（部分唯一索引 `WHERE is_deleted=FALSE`），保证同一文件不会被解析两次产生两条有效记录。历史失败记录改 `is_deleted` 或保留在 `m12_parse_failure` 中。

2. **`m12_parse_field` 是明细表，一记录 N 字段。** 加 `channel` 区分通道 A（患者身份）与通道 B（测量数据），因为两个通道的置信度策略不同。

3. **`m12_parse_template` 独立成表而不是 JSON 文件。** 理由：模板需要在页面上增删改查、需要版本控制、需要按设备查询匹配率。放文件系统会导致"改模板要发版"。

4. **`m12_unconfirmed` 与 `m12_parse_record` 一对一（0..1）。** 只有 `bind_status='UNCONFIRMED'` 的记录才有对应待确认行。独立成表而不是在主表加字段，因为待确认有独立的生命周期（认领、超期、转无主），字段多达 12 个，合进主表会让主表职责不清。

5. **不建外键，全部逻辑引用。** 理由：
   - `file_id` 引用 `m12_report_file`（M12-03 定义），跨子模块
   - `bound_task_id` 引用 `m12_exam_task`（M12-01 定义）
   - `template_code` 引用 `m12_parse_template` 的业务键（而非 ID），因为模板会被替换版本
   - 高频写入表加外键会带来锁竞争与迁移顺序耦合；一致性由应用层 + 定时对账保证

6. **`m12_parse_config` 用 `COALESCE(scope_id, 0)` 建唯一索引。** PostgreSQL 认为 NULL 互不相等，若用 `(param_code, scope, scope_id)` 直接做唯一索引，`scope=GLOBAL` 时 `scope_id IS NULL`，可以插入无数条重复。加 `COALESCE` 后 `NULL` 视为 `0`，唯一性才成立。

**约束说明：**

```sql
-- 主键与业务键
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_no
  CHECK (parse_no ~ '^PR[0-9]{8}[0-9]{6}$');

ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_sha
  CHECK (file_sha256 ~ '^[0-9a-f]{64}$');

-- 解析状态枚举
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_status
  CHECK (parse_status IN ('PENDING', 'EXTRACTING', 'OCRING',
                          'PARSING', 'PARSED', 'PARSE_FAILED'));

-- 抽取方式枚举
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_mode
  CHECK (extract_mode IS NULL OR extract_mode IN ('TEXT_LAYER', 'OCR'));

-- 绑定状态与方式
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_bind_status
  CHECK (bind_status IN ('BOUND', 'UNCONFIRMED', 'ORPHAN'));

ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_bind_type
  CHECK (bind_type IS NULL OR bind_type IN ('TICKET', 'WINDOW', 'MANUAL'));

-- BOUND 必须三者齐全：任务 + 方式 + 时间
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_bound
  CHECK (bind_status <> 'BOUND'
         OR (bound_task_id IS NOT NULL
             AND bind_type IS NOT NULL
             AND bound_at IS NOT NULL));

-- 非 BOUND 且非人工绑定时不应有任务
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_unbound
  CHECK (bind_status = 'BOUND'
         OR bound_task_id IS NULL
         OR bind_type = 'MANUAL');

-- 人工绑定必须有操作人
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_manual
  CHECK (bind_type IS NULL
         OR bind_type <> 'MANUAL'
         OR bound_by IS NOT NULL);

-- 置信度区间
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_conf
  CHECK (overall_confidence IS NULL
         OR (overall_confidence >= 0 AND overall_confidence <= 1));

ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_bind_conf
  CHECK (bind_confidence IS NULL
         OR (bind_confidence >= 0 AND bind_confidence <= 1));

-- PARSED 必须写完成时间与耗时
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_done
  CHECK (parse_status NOT IN ('PARSED', 'PARSE_FAILED')
         OR (finished_at IS NOT NULL AND elapsed_ms IS NOT NULL));

-- PARSE_FAILED 必须有失败码
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_failed
  CHECK (parse_status <> 'PARSE_FAILED'
         OR (fail_code IS NOT NULL AND finished_at IS NOT NULL));

-- 重试次数上限 3（与 M12.PARSE.MAX_RETRY 一致，DB 兜底）
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_retry
  CHECK (retry_count >= 0 AND retry_count <= 3);

-- 页数上限 50
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_pages
  CHECK (page_count > 0 AND page_count <= 50);

-- 双通道冲突必须有说明
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_cross
  CHECK (is_cross_conflict = FALSE OR cross_message IS NOT NULL);

-- 核对完成必须有时间与操作人
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_confirm
  CHECK (is_confirmed = FALSE
         OR (confirmed_at IS NOT NULL AND confirmed_by IS NOT NULL));

-- 未绑定不可核对完成（规则 V-04）
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_confirm_bound
  CHECK (is_confirmed = FALSE OR bind_status = 'BOUND');

-- 推送完成必须有时间
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_push
  CHECK (pushed_to_doctor = FALSE OR pushed_at IS NOT NULL);

-- 眼别枚举
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_eye
  CHECK (eye_side IS NULL OR eye_side IN ('OD', 'OS', 'OU', 'NA'));

-- 年龄合理区间
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_age
  CHECK (patient_age IS NULL OR (patient_age >= 0 AND patient_age <= 150));

-- 时间先后
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_time_seq
  CHECK (started_at IS NULL OR finished_at IS NULL
         OR finished_at >= started_at);

-- 原始文本长度上限 10 万字符
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_raw_len
  CHECK (raw_text IS NULL OR char_length(raw_text) <= 100000);

-- 乐观锁
ALTER TABLE m12_parse_record
  ADD CONSTRAINT ck_m12_parse_version
  CHECK (version >= 1);

-- 注释
COMMENT ON TABLE  m12_parse_record IS 'M12-04 报告解析记录主表';
COMMENT ON COLUMN m12_parse_record.file_id IS 'M12-03 m12_report_file.id（逻辑引用，无外键）';
COMMENT ON COLUMN m12_parse_record.file_mtime IS '文件修改时间，OCR 绑定算法的核心线索';
```


**设计要点：**

1. **为什么 `file_id` 要有部分唯一索引而不是普通唯一索引？**
   因为同一文件可能被"解析→失败→重新解析→成功"多次处理。若用普通唯一索引，第一次失败记录就占住了位置，重新解析会插入失败。用 `WHERE is_deleted = FALSE` 后，旧记录标 `is_deleted=TRUE` 再建新记录，历史可追溯。

2. **为什么 `file_mtime` 要单独存一份而不是每次去 M12-03 查？**
   因为绑定算法要用它做区间判断，而 M12-03 的文件记录在归档后路径会变、可能被巡检标记丢失。冗余一份 `m12_parse_record.file_mtime` 保证"即使文件没了，绑定依据还在"。

3. **为什么 `patient_name`/`patient_gender`/`patient_age` 这三个字段在主表冗余？**
   因为：
   - 待确认队列要按姓名展示与排序 → 每次 JOIN `m12_parse_field` 太慢
   - 统计报表要按姓名匹配率分析
   - 绑定算法要频繁读这三项
   它们在 `m12_parse_field` 里也有权威记录（通道 A），主表这份是**便利冗余**，写入时同源，不会不一致。

4. **为什么 `bind_message` 要存"为什么没绑上"？**
   这是给护士看的。待确认队列里如果只有"待确认"两个字，护士不知道该怎么办；有"1 小时内无该设备的检查时间窗"，护士就知道去问技师是不是忘点开始。

5. **为什么 `raw_text` 要存库而不是每次重读 PDF？**
   因为：
   - 写模板正则时需要看原始文本（P05 页面的"查看原始文本"）
   - PDF 可能归档后丢失，文本还在
   - 重新解析时如果只想改规则不想重新 OCR，可直接从库读
   代价是存储（平均 4KB/份 × 15 万份 = 600MB），可接受。截断 10 万字符防超长。

6. **为什么 `required_miss_count` 要单独存？**
   便于统计"哪台设备的报告必填字段缺失最多"，这是模板需要优化的信号。如果只存 `fail_reason` 字符串，无法聚合。

7. **为什么 `review_status` 只在 `m12_parse_record` 存一个字段，而不建审核表？**
   因为审核的完整数据归 M12-05（审核人、审核意见、签名、时间）。这里只存一个状态用于"报告列表显示审核进度"，避免跨模块查询 500 条记录要发 500 次 HTTP。

**量级估算：**

| 项 | 估算 |
|---|---|
| 日解析份数 | 420 份 |
| 年解析份数 | 153,300 份 |
| 保留期 | **15 年**（与报告同等，医疗记录法定保存期） |
| 15 年总量 | 2,299,500 行 |
| 单行平均大小 | 约 900 字节（含 raw_text 平均 4KB 但只 30% 有值） |
| 表数据 | 约 2.1 GB |
| 索引 | 约 1.1 GB |
| **合计** | **约 3.2 GB** |

**分区：** 不分区。

理由（重要）：

`uk_m12_parse_file_active` 是"一文件一有效解析记录"的幂等基石。若按 `created_at` 年度分区，PostgreSQL 要求唯一索引必须包含分区键，索引会退化为 `(file_id, created_at)` —— 意味着同一个文件在两个不同年份解析两次都能插入成功。而幂等语义必须是跨年份的（补解析去年归档的报告是真实场景）。

**性能上不需要分区：** 230 万行在 PG16 上是舒适区，主键查询 <1ms；所有高频查询（待确认、待重试、按任务查）都已经有部分索引，索引本身只有几十到几千条。

**归档策略：** 15 年内不删除。若将来确需归档，方案是"整年归档到 `m12_parse_record_archive`"，代价是那几年的文件重解析会失去幂等保护 —— 这正是选择不分区时要接受的权衡。

```sql
-- 通道枚举
ALTER TABLE m12_parse_field
  ADD CONSTRAINT ck_m12_field_channel
  CHECK (channel IN ('A', 'B'));

-- 置信度区间
ALTER TABLE m12_parse_field
  ADD CONSTRAINT ck_m12_field_conf
  CHECK (confidence >= 0 AND confidence <= 1);

-- 序号从 1 开始

-- 确认必须有时间与操作人

  ADD CONSTRAINT ck_m12_field_confirmed

         OR (confirmed_at IS NOT NULL AND confirmed_by IS NOT NULL));

  ADD CONSTRAINT ck_m12_field_edited

         OR (edit_count >= 1
             AND last_edited_at IS NOT NULL
             AND last_edited_by IS NOT NULL
             AND original_value IS NOT NULL));

  ADD CONSTRAINT ck_m12_field_numeric
  CHECK (is_in_range IS NULL
         OR numeric_value IS NOT NULL);

-- 参考区间上下限有序
ALTER TABLE m12_parse_field
  ADD CONSTRAINT ck_m12_field_ref
  CHECK (ref_min IS NULL OR ref_max IS NULL OR ref_min <= ref_max);

-- 值类型枚举

  ADD CONSTRAINT ck_m12_field_type
  CHECK (value_type IS NULL
         OR value_type IN ('TEXT', 'INTEGER', 'DECIMAL', 'DATE', 'ENUM'));

  ADD CONSTRAINT ck_m12_field_page
  CHECK (source_page IS NULL OR source_page >= 1);

-- 编辑次数

  ADD CONSTRAINT ck_m12_field_edit
  CHECK (edit_count >= 0);

-- 注释
COMMENT ON TABLE  m12_parse_field IS 'M12-04 解析字段明细（双通道）';
COMMENT ON COLUMN m12_parse_field.channel IS 'A=患者身份（绑定用），B=检查数据（展示用）';
COMMENT ON COLUMN m12_parse_field.confidence IS '字段级置信度 = 该字段涉及字符置信度的最小值（最弱一环）';
COMMENT ON COLUMN m12_parse_field.original_value IS '首次抽取的原值，人工修改后仍保留，用于追溯与准确率统计';
COMMENT ON COLUMN m12_parse_field.source_bbox IS 'OCR 四点坐标 [[x1,y1],...]，用于页面原图高亮定位';
```

**设计要点：**

1. **为什么置信度取最小值而不是平均？**
   见详细设计 3.4.1：`2.38` 认成 `2.3B`，其他 3 个字符都对（平均 0.97），但整个字段完全不可用。取最小值才能反映真实可靠性。

2. **为什么 `original_value` 要保留？**
   因为"字段抽取准确率"这个核心 KPI 只能靠"人工改了多少次"来计算。如果人工修改直接覆盖 `field_value`，就永远不知道机器原来抽的是什么，也就无法统计准确率、无法反推模板改进方向。

3. **为什么 `numeric_value` 要与 `field_value` 分开？**
   `field_value` 是"PDF 上看到的原文"（可能是 `238`、`238.0`、`约238`），`numeric_value` 是"转成数字后的值"（`238.0000`）。前者用于展示与追溯，后者用于区间判断与危急值比对。如果只存一个，要么展示不忠于原文，要么比较时反复转换。

4. **为什么 `source_bbox` 用 JSONB 而不是四个数值列？**
   因为坐标是 `[[x1,y1],[x2,y2],[x3,y3],[x4,y4]]` 的四点结构，未来若支持旋转变形可能变成多点。JSONB 灵活，且这一列不参与任何条件查询（只用于前端渲染）。

5. **为什么 `is_extracted` 与 `field_value IS NULL` 不重复？**
   二者语义不同：`is_extracted=FALSE` 表示"模板规则定义了但没抽到"（缺失）；`field_value` 可能抽到了空字符串（抽取到但内容为空）。区分它们才能准确统计"缺失率"。

6. **为什么 `uk_m12_parse_field_code` 是 `(parse_id, field_code)` 而不是 `(parse_id, channel, field_code)`？**
   因为同一个字段不应该同时出现在通道 A 和 B 里。唯一约束能防止模板写错导致重复。

| 年明细行数 | 1,226,400 行 |
| 保留期 | 15 年 |
| 15 年总量 | 18,396,000 行 |

```sql
COMMENT ON COLUMN m12_parse_template.match_rate IS '匹配率 = match_success / match_total，低于 95% 触发告警';
```

**设计要点：**

1. **为什么 `field_rules` 用 JSONB 而不是独立规则表？**
   因为规则永远是"针对一个模板整体读写"的：打开模板页面 → 加载全部规则 → 改 → 整体保存。从来没有"查所有模板里所有用到 `中心凹厚度` 的规则"这种需求。JSONB 一次读写，比 4 张关联表 JOIN 简单得多。

   代价是无法对规则内部字段建索引。但规则表本身只有 10~50 行，全表扫描无压力。

2. **为什么 `template_code` 不变而 `version` 递增？**
   因为 `m12_parse_record.template_code` 存的是业务键。若版本用编码区分（`OCT_MACULA_V1`/`V2`），则历史记录查到的编码在新版本上线后就"不存在"了。用 `(template_code, version)` 双键，主表存 `template_code='OCT_MACULA_V1'` + `template_version='V3'`，永远能定位到当时用的哪一版。

3. **为什么 `match_total`/`match_success` 是计数器而不是每次统计？**
   匹配率是高频展示指标（模板列表每行都有），若每次 `COUNT(*)` 全表扫描 `m12_parse_record`（230 万行），打开模板列表要 3 秒。用原子递增 `UPDATE ... SET match_total = match_total + 1`，读取 O(1)。

   代价：计数器可能与实际略有偏差（并发、回滚）。所以每日 08:00 的健康检查任务会用真实数据重算后校正一次。

4. **`uk_m12_template_device_title` 为什么排除 `device_code IS NULL`？**
   因为通用模板的 `device_code` 是 NULL，而 PostgreSQL 唯一索引认为 NULL 互不相等，若不排除则通用模板可以建无数个。通用模板的唯一性由 `uk_m12_template_generic` 单独保证。

5. **为什么要有 `is_system`？**
   因为 `GENERIC_V1`（通用兜底模板）是整个方案的最后一层保险。如果被误删，所有未知格式的报告都会解析失败并堆积。`is_system=TRUE` 的模板在应用层禁止删除。

**量级估算：**

| 项 | 估算 |
|---|---|
| 模板数量 | 10~50 个（按实际设备与报告类型） |
| 每模板规则数 | 5~30 条 |
| 单行大小 | 约 8 KB（含 field_rules JSON） |
| 总量 | 约 400 KB |

**不分区。** 数据量极小，无分区必要。

**状态机：**

```
        绑定失败
           │
           ▼
    ┌──────────────┐
    │   PENDING    │
    │   （待处理）  │
    └──────┬───────┘
           │ 开始处理（打开详情）
           ▼
    ┌──────────────┐
    │  HANDLING    │
    │  （处理中）   │
    └───┬──────┬───┘
        │      │
   认领绑定│      │标无主 / 超7天
        ▼      ▼
   ┌────────┐ ┌────────┐
   │RESOLVED│ │ ORPHAN │
   │（已绑定）│ │（无主） │
   └────────┘ └────────┘
```

**设计要点：**

1. **为什么要有 `HANDLING` 中间态？**
   因为护士打开详情页、查看候选、核对 PDF 可能花 1~2 分钟。如果两个人同时打开同一条，都会处理，第二个人的操作会覆盖第一个人。`HANDLING` 相当于"认领"标记，避免重复劳动。

   实现上用乐观更新：`UPDATE ... SET status='HANDLING', handled_by=? WHERE id=? AND status='PENDING'`，`rowcount=0` 表示已被他人认领。

2. **为什么 `candidate_task_ids` 冗余到待确认表？**
   因为候选任务在 `m12_exam_task` 里，且会随窗口关闭而变化。待确认队列需要"稳定快照"——护士看到的候选应该是"进队列那一刻的候选"，而不是实时变化的。快照保证了处理过程的一致性。

   同时 `candidate_count` 冗余是为了排序：`ORDER BY priority DESC, candidate_count` 不能用 JSONB 数组长度直接排（需要函数索引），冗余一列最简单。

3. **为什么 `wait_minutes` 要存成字段而不实时算？**
   因为队列列表要按"等待时长"筛选（"只看超过 1 小时的"），`WHERE CURRENT_TIMESTAMP - created_at > INTERVAL '1 hour'` 无法走索引。存成整数后可以 `WHERE wait_minutes > 60 AND status='PENDING'`，配合定时任务每 5 分钟刷新一次。

   代价是数据滞后最多 5 分钟，对于"等待时长"这个指标完全可以接受。

4. **为什么超期判定用 `is_overdue` 布尔而不是时间比较？**
   同上：为了能建部分索引 `WHERE is_overdue = TRUE`。超期记录通常只有几条，部分索引后查询几乎零成本。

5. **为什么 `uk_m12_unconf_parse` 只约束活跃状态？**
   因为同一条解析可能先进入待确认（同名歧义），被标记无主，后来发现是误判又重新打开待确认。历史记录要保留，只约束"同时只能有一条活跃"。

**量级估算：**

| 项 | 估算 |
|---|---|
| 日进入队列 | 12 条（自动绑定率 96%，420 × 4% ≈ 17，实际约 12） |
| 年进入队列 | 4,380 条 |
| 保留期 | 5 年 |
| 5 年总量 | 21,900 行 |
| 单行大小 | 约 600 字节 |
| 表数据 | 约 13 MB |
| 索引 | 约 9 MB |
| **合计** | **约 22 MB** |

**不分区。** 数据量极小（2 万行），且活跃记录只有几条到几十条，部分索引完全够用。

**设计要点：**

1. **为什么失败记录要独立成表而不合并进主表？**
   主表的 `fail_code`/`fail_reason` 只保留**最后一次**失败。而诊断"模板写错了"需要看**第一次**失败时的原始文本。独立表按 `attempt_no` 保留三次尝试的完整上下文。

2. **为什么 `raw_text_head` 存 2000 字符而不是全文？**
   因为失败诊断只需要看抬头和标签部分（标题、姓名、项目名都在前 2000 字符）。全文在 `m12_parse_record.raw_text` 已有。失败记录数量是 3 倍（每次尝试一条），存全文会让存储翻 3 倍。

3. **为什么 `can_auto_recover` 要显式标记？**
   因为不同失败原因的处置完全不同：
   - `OCR_UNAVAILABLE`/`PARSE_TIMEOUT`：系统问题，等恢复后自动重试
   - `TEMPLATE_MISMATCH`/`FIELD_MISSING`：模板问题，自动重试永远失败，必须人工
   
   如果不区分，定时任务会给模板问题也重试 3 次，白白消耗 CPU 并刷屏日志。

4. **为什么 `detected_title` 要单独存？**
   因为新建模板时需要填 `title_pattern`（标题正则）。有了检测到的真实标题，IT 可以直接复制并加 `^`/`$` 锚点，不用去翻 PDF 或日志。

**设计要点：**

1. **为什么 `param_value` 统一存字符串？**
   因为配置表是"异构参数容器"，`INT`/`FLOAT`/`STRING`/`LIST` 混在一起。若用 JSONB 存值，虽然类型自由但无法在 SQL 里做范围校验。用 VARCHAR + `param_type` 显式声明，读取时统一转，写入时用 `min_value`/`max_value` 校验。

2. **为什么区分 `GLOBAL` / `DEVICE` 两级？**
   因为不同设备的 OCR 质量差异巨大：眼压报告是纯文本（走文本层），眼底照相是图片（走 OCR）。同一台服务器上，眼压的 OCR DPI 设 150 就够，眼底要 300。如果只有全局参数，只能取最差配置，眼压解析会白白慢一倍。

3. **为什么 `is_editable`？**
   部分参数虽然存在表里但不允许页面修改（例如 `MAX_RETRY` 必须与 DB CHECK 约束 `retry_count <= 3` 保持一致，改了会冲突）。这类参数只读，避免运维改出问题。

4. **为什么有 `default_value`？**
   用于"恢复默认"。真实场景：运维为了排查问题把 DPI 改成 600，忘了改回来，导致所有解析慢了 3 倍。有默认值可以一键恢复。

**量级估算：**

| 项 | 估算 |
|---|---|
| GLOBAL 参数 | 21 条 |
| DEVICE 级参数 | 0~20 条（按需覆盖） |
| 单行大小 | 约 500 字节 |
| 总量 | 约 20 KB |

**不分区。** 数据量极小。

| `idx_m12_field_low_conf` | `m12_parse_field` | `confidence < 0.7000` | 提交校验查低置信度（每记录通常 0~3 条） |
| `idx_m12_field_edited` | `m12_parse_field` | `is_manual_edited = TRUE` | 人工修改率统计 |
| `uk_m12_template_device_title` | `m12_parse_template` | `is_enabled=TRUE AND device_code IS NOT NULL` | **同设备同标题只能一个启用** |
| `uk_m12_template_generic` | `m12_parse_template` | `device_code IS NULL AND is_current=TRUE` | 通用模板同标题唯一 |
| `idx_m12_template_enabled` | `m12_parse_template` | `is_enabled=TRUE` | **模板匹配时的候选列表** |
| `idx_m12_template_low_rate` | `m12_parse_template` | `match_rate < 0.95 AND is_enabled=TRUE` | 匹配率告警（通常 0~2 个） |
| `uk_m12_unconf_parse` | `m12_unconfirmed` | `status IN ('PENDING','HANDLING')` | 一条解析只有一个活跃待确认 |
| `idx_m12_unconf_queue` | `m12_unconfirmed` | `status='PENDING'` | **队列主查询（活跃通常几条到几十条）** |
| `idx_m12_unconf_overdue` | `m12_unconfirmed` | `is_overdue=TRUE AND status='PENDING'` | 超期扫描 |
| `idx_m12_unconf_orphan` | `m12_unconfirmed` | `status='PENDING' AND created_at < CURRENT_DATE - INTERVAL '7 days'` | 超 7 天自动转无主 |
| `idx_m12_failure_unresolved` | `m12_parse_failure` | `is_resolved=FALSE AND can_auto_recover=FALSE` | **待人工处理的失败（通常几条）** |
| `idx_m12_failure_auto` | `m12_parse_failure` | `can_auto_recover=TRUE AND is_resolved=FALSE` | 自动重试扫描 |
| `uk_m12_parse_config` | `m12_parse_config` | `is_deleted=FALSE` + `COALESCE(scope_id,'')` | 参数唯一（COALESCE 处理 NULL） |

**共 19 个关键索引，其中 13 个是部分索引。**

**为什么这么多部分索引？**

因为 `m12_parse_record` 15 年有 230 万行，但**待处理状态的数据永远是极少数**：

| 状态 | 典型数量 | 占比 |
|---|---|---|
| 待重试（PENDING/解析中） | 5~10 条 | 0.0004% |
| 待推送 | 3~5 条 | 0.0002% |
| 双通道冲突 | 0~2 条 | 0.0001% |

如果这些扫描用普通索引，每次要遍历 230 万行的索引树（约 20ms）；用部分索引后，索引里只有几十条，扫描 1 个数据页（<0.1ms）。**定时任务每 5 分钟跑一次，一年 10 万次，20ms 与 0.1ms 的差别就是 200 秒 vs 1 秒的 CPU 消耗。**

### `m12_004_007_seed.py` 预置内容要点

1. **配置**：21 条（见附录 D）
2. **通用模板 `GENERIC_V1`**：

```json
{
  "template_code": "GENERIC_V1",
  "template_name": "通用兜底模板",
  "device_code": null,
  "title_pattern": ".*",
  "field_rules": [
    {"field_code": "PATIENT_NAME", "field_name": "患者姓名", "channel": "A",
     "extract_type": "REGEX",
     "pattern": "姓[\\s]*名[\\s:：]*([\\u4e00-\\u9fa5]{2,4})",
     "value_type": "TEXT", "required": true},
    {"field_code": "GENDER", "field_name": "性别", "channel": "A",
     "extract_type": "REGEX", "pattern": "(男|女)",
     "value_type": "ENUM", "required": false},
    {"field_code": "AGE", "field_name": "年龄", "channel": "A",
     "extract_type": "REGEX", "pattern": "([0-9]{1,3})[\\s]*岁",
     "value_type": "INTEGER", "required": false},
    {"field_code": "HEADER_NAME", "field_name": "抬头姓名", "channel": "B",
     "extract_type": "REGEX",
     "pattern": "姓[\\s]*名[\\s:：]*([\\u4e00-\\u9fa5]{2,4})",
     "value_type": "TEXT", "required": false}
  ],
  "priority": 0,
  "status": "ENABLED",
  "is_enabled": true,
  "is_current": true,
  "is_system": true,
  "required_count": 1
}
```

**通用模板的定位：** 它不是"能正确抽出所有字段"的模板，而是"至少能把患者姓名抽出来、让文件能进入待确认队列"的兜底。如果没有它，未知格式的报告会直接 `TEMPLATE_MISMATCH` 失败并堆在失败列表里，无人工认领的路径。

有了它，未知格式的报告会：
1. 抽到姓名 → 走绑定算法 → 大概率进入待确认队列
2. 护士在待确认队列就能认领（不需要先建模板）
3. 测量数据虽然没抽到，但 IT 可以从 `raw_text` 里看到，随后建专用模板并重解析

**这就是"最后一层保险"的含义：保证不丢数据，允许不完整。**
