## 1. 全局设计规范

### 1.1 表名前缀

**所有 M12 的表以 `m12_` 开头，第三段表示业务对象。**

```
m12_exam_*       检查预约与执行
m12_report_*     报告相关
m12_parse_*      OCR 解析
m12_collect_*    文件采集
m12_review_*     审核
m12_critical_*   危急值
m12_device_*     设备
m12_change_*     配置变更
m12_sys_config   系统参数
```

**为什么不带子模块编号：** 子模块是"设计期的组织方式"，不是"运行期的数据归属"。`m12_report_review` 会被 M12-05（主）与 M12-03（列表页展示）共用，若命名成 `m12_05_report_review` 会让第二个使用方产生"越界"感，反而阻碍合理的复用。

### 1.2 字段规范

**每张业务表必须有 5 个标准字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 主键 |
| `created_at` | `TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP` | 创建时间 |
| `created_by` | `BIGINT` | 创建人 |
| `updated_at` | `TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP` | 更新时间 |
| `updated_by` | `BIGINT` | 更新人 |
| `is_deleted` | `BOOLEAN NOT NULL DEFAULT FALSE` | 软删除标记 |

**为什么用软删除而不是物理删除：** 医疗数据必须可追溯。一份报告被"删除"后，如果物理删除，就再也回答不了"这个患者当时做过检查吗"。

**为什么软删除一定要配合部分唯一索引：** 软删除后原记录仍在表中，若用普通唯一索引（如 `UNIQUE (order_no)`），重建同号记录会冲突。所有唯一索引都必须带 `WHERE is_deleted = FALSE`。

### 1.3 枚举用 VARCHAR + CHECK，不用 PostgreSQL ENUM

**三个理由：**

1. **PG ENUM 增加新值需要 `ALTER TYPE ... ADD VALUE`，且不能在事务中执行**——本项目有 4 个枚举（采集失败原因、解析失败原因、待确认原因、危急值状态）在开发期会频繁增删值
2. **PG ENUM 的删除/重命名操作极其麻烦**——要重建类型
3. **应用层的 `Literal[...]` 已经提供了类型安全**，数据库层只需要 `CHECK` 兜底

**统一的 CHECK 写法：**

```sql
ALTER TABLE m12_parse_record
    ADD CONSTRAINT ck_m12_parse_status
    CHECK (parse_status IN ('PENDING', 'EXTRACTING', 'OCRING',
                            'PARSING', 'PARSED', 'PARSE_FAILED'));
```

### 1.4 时间语义

| 字段类型 | 用途 | 示例 |
|---|---|---|
| `TIMESTAMP`（无时区） | 业务时刻，统一存东八区本地时间 | `exec_started_at`、`reviewed_at` |
| `DATE` | 业务日期 | `slot_date`、`seq_date` |
| `TIME` | 时段 | `start_time`、`end_time` |
| `TIMESTAMP WITH TIME ZONE` | 不用 | — |

**为什么不用 `TIMESTAMPTZ`：** 本院是单院区单时区部署，用 `TIMESTAMP` 更简单直观。所有时间字段在应用层统一用东八区 `datetime.now()` 生成，不使用数据库的 `CURRENT_TIMESTAMP`（除了 DEFAULT 值）。

### 1.5 金额与数值

| 类型 | 用途 | 精度 |
|---|---|---|
| `NUMERIC(12,2)` | 金额 | 元，2 位小数 |
| `NUMERIC(14,4)` | 单价 | 元，4 位小数 |
| `NUMERIC(5,4)` | 置信度/比例 | 0.0000~1.0000 |
| `NUMERIC(8,6)` | 错误率/占比 | 0.000000~1.000000 |
| `NUMERIC(10,2)` | 数值型字段值（如眼压 12.50） | 2 位小数 |
| `INTEGER` | 计数、分钟、秒 | — |

**禁止 `FLOAT`/`REAL`/`DOUBLE PRECISION`。** 理由：二进制浮点无法精确表示 0.1，累加会漂移；金额与服务指标一旦漂移，对账永远对不上。

**行级先舍入铁律：** 所有金额计算 `ROUND(unit_price * quantity, 2)` 在行级完成，再累加。不是先累加再舍入。

### 1.6 字符集与排序

- 数据库编码：`UTF8`
- 排序规则：`zh_CN.utf8`（中文按拼音排序）
- 中文模糊搜索：`pg_trgm` 扩展 + GIN 索引

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_m12_parse_name_trgm ON m12_parse_record
    USING gin (patient_name gin_trgm_ops);
```

**为什么用 pg_trgm 而不是 `LIKE '%张%'`：** `LIKE` 前置通配符无法走 B-tree 索引，全表扫描 230 万行约 800 ms。GIN trgm 索引后约 5 ms。

### 1.7 updated_at 自动维护

```sql
CREATE OR REPLACE FUNCTION fn_m12_set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = CURRENT_TIMESTAMP;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m12_parse_record_updated
    BEFORE UPDATE ON m12_parse_record
    FOR EACH ROW EXECUTE FUNCTION fn_m12_set_updated_at();
```

**为什么不让应用层负责：** 应用层在每个 `UPDATE` 都要手写 `updated_at`，总有遗漏的；DBA 手动改数据时更是必然遗漏。触发器是唯一可靠方式。

### 3.3 关联方式：逻辑外键而非物理外键

**M12 的所有跨表关联都是逻辑外键（不加 `FOREIGN KEY` 约束）。**

**三个理由：**

1. **性能**：`m12_exam_task` 年 6.5 万行、`m12_parse_field` 年 122 万行。物理外键会在每次插入时做一次父表存在性检查，高频写入场景下这是额外开销
2. **解耦**：`m12_exam_request` 可以归档而 `m12_exam_task` 保留，物理外键会阻止这种独立生命周期
3. **分区兼容**：分区表上的外键约束受限，`m12_exam_node` 若加外键到 `m12_exam_task`，每年重建分区都要重建约束

**一致性由三层保证：**

| 层 | 手段 | 示例 |
|---|---|---|
| 应用层 | 事务内成对写入 | `ParseService.register` 总是先建 record 再建 field |
| 约束层 | `CHECK` 验证关联标识非空 | `ck_m12_parse_bound CHECK (bind_status <> 'BOUND' OR bound_task_id IS NOT NULL)` |
| 巡检层 | 定时任务查孤儿数据 | 每日 04:00 检查孤儿记录 |

**孤儿数据检查 SQL：**

```sql
-- 检查解析记录绑定的任务是否存在
SELECT p.id, p.parse_no, p.bound_task_id
FROM m12_parse_record p
LEFT JOIN m12_exam_task t ON t.id = p.bound_task_id
WHERE p.bind_status = 'BOUND'
  AND p.is_deleted = FALSE
  AND t.id IS NULL;
```

## 4. 索引策略

### 4.1 索引命名规范

| 前缀 | 类型 | 示例 |
|---|---|---|
| `uk_` | 唯一索引（含唯一约束） | `uk_m12_file_sha256` |
| `idx_` | 普通索引 | `idx_m12_parse_status` |
| `ex_` | 排他约束（EXCLUDE） | `ex_m12_slot_overlap` |
| `ck_` | CHECK 约束 | `ck_m12_parse_status` |

**格式：** `{前缀}_{表名}_{字段或用途}`，全部小写，单词用下划线分隔。

### 4.2 三类索引

**（1）唯一索引（含部分唯一）**

部分唯一索引是 M12 的核心设计手段。

| 索引 | 表 | 作用 |
|---|---|---|
| `uk_m12_file_sha256` | `m12_report_file` | 文件去重最后防线 |
| `uk_m12_parse_file_active` | `m12_parse_record` | 一文件一活跃解析 |
| **`uk_m12_parse_task_bound`** | `m12_parse_record` | **一任务一有效报告（错绑防护 DB 兜底）** |
| `uk_m12_review_parse` | `m12_report_review` | 一解析一报告 |
| `uk_m12_task_request_item` | `m12_exam_task` | 防重复接单 |
| `uk_m12_window_task` | `m12_exam_window` | 一任务一窗口 |
| `uk_m12_ticket_task` | `m12_exam_ticket` | 一任务一有效凭条 |
| `uk_m12_unconf_parse` | `m12_unconfirmed` | 一解析一活跃待确认 |
| `uk_m12_slot_key` | `m12_exam_slot` | 设备×项目×日期×时段唯一 |
| `uk_m12_template_current` | `m12_parse_template` | 同设备唯一当前版 |
| `uk_m12_critical_rule` | `m12_critical_value` | 一报告一规则一条（M12-05） |
| `uk_m12_sys_config` | `m12_sys_config` | 参数键唯一 |

**（2）部分索引（性能优化）**

M12 有 30 多个部分索引，核心思路是：**主表行数大，但"活跃数据"永远只占极小比例。**

| 表 | 总行数（15年） | 部分索引条件 | 命中行数 | 收益 |
|---|---|---|---|---|
| `m12_report_file` | 230 万 | `archive_status='PENDING'` | ~200（0.009%） | 20ms → <1ms |
| `m12_parse_record` | 230 万 | `is_confirmed=FALSE AND bind_status='BOUND'` | ~20（0.001%） | 20ms → <1ms |
| `m12_parse_field` | 1,836 万 | `is_critical=TRUE AND is_confirmed=FALSE` | ~50 | 全表扫 → 索引扫 |
| `m12_report_review` | 237 万 | `status='PENDING'` | ~30（0.001%） | 20ms → <1ms |
| `m12_critical_value` | 7.1 万 | `status IN ('DETECTED','NOTIFIED',...)` | ~5 | 20ms → <1ms |

**为什么部分索引这么有效：** 普通索引要遍历整棵 B-tree（230 万条）才定位到命中行，部分索引直接只看那几十条。而定时任务一年执行 10 万次以上，20ms → 1ms 的差异就是 2000 秒 vs 100 秒的 CPU 差异。

**（3）GIN 索引（中文搜索与数组）**

| 索引 | 表 | 字段 | 用途 |
|---|---|---|---|
| `idx_m12_parse_name_trgm` | `m12_parse_record` | `patient_name` | 按姓名模糊搜索 |
| `idx_m12_file_name_trgm` | `m12_report_file` | `file_name` | 按文件名搜索 |
| `idx_m12_unconf_name_trgm` | `m12_unconfirmed` | `ocr_patient_name` | 待确认按姓名搜 |
| `idx_m12_review_name_trgm` | `m12_report_review` | `patient_name` | 报告按姓名搜 |

### 4.3 不用索引的场景

| 场景 | 不建索引的理由 |
|---|---|
| `m12_parse_field.value_text`（文本值） | 几乎不用于条件查询，只在详情页展示 |
| `m12_parse_field.source_bbox`（坐标） | JSONB，从不作为查询条件 |
| `m12_parse_template.field_rules`（规则） | 只整体读写，规则表仅 30~50 行，无需索引 |
| `m12_report_version.snapshot_json`（快照） | 只按 `review_id + version_no` 精确查 |
| `m12_exam_node.detail_json` | 只做展示，不做条件过滤 |
| 任何 `is_deleted` 单列索引 | 98% 以上是 `FALSE`，选择性太差 |

## 5. 分区与归档

### 5.1 分区表清单（3 张）

| 表 | 分区键 | 分区方式 | 预建分区数 | 保留期 | 热数据 |
|---|---|---|---|---|---|
| `m12_exam_node` | `seq_date`（DATE） | 月度 RANGE | 36 个月 | 15 年 | 180 天 |
| `m12_exam_window_log` | `seq_date`（DATE） | 月度 RANGE | 36 个月 | 15 年 | 180 天 |
| `m12_review_log` | `seq_date`（DATE） | 月度 RANGE | 36 个月 | 15 年 | 180 天 |

### 5.2 为什么只有这 3 张表分区

**判断标准：有没有跨年份的唯一约束。**

| 表 | 15 年行数 | 是否分区 | 决定因素 |
|---|---|---|---|
| `m12_report_file` | 230 万 | ❌ | `uk_m12_file_sha256` 需含分区键 → 去重退化为"同年唯一" |
| `m12_parse_record` | 230 万 | ❌ | `uk_m12_parse_task_bound` 需含分区键 → 约束退化为"同年唯一" |
| `m12_report_review` | 237 万 | ❌ | `uk_m12_review_parse` 需含分区键 → 幂等失效 |
| `m12_exam_task` | 65 万 | ❌ | `uk_m12_task_request_item` 需含分区键 → 幂等失效 |
| `m12_parse_field` | 1,836 万 | ❌ | `uk_m12_parse_field_code` 需含分区键 → 约束削弱 |
| `m12_review_field` | 1,896 万 | ❌ | 同上 |
| **`m12_exam_node`** | **510 万** | ✅ | 无跨年份唯一约束 |
| **`m12_exam_window_log`** | **328 万** | ✅ | 无跨年份唯一约束 |
| **`m12_review_log`** | **547 万** | ✅ | 无跨年份唯一约束 |

**核心理由：跨年份的幂等与去重语义，比查询性能更重要。**

举例：`m12_parse_field` 年 122 万行，若按年分区成 15 个分区，每个分区 122 万行，查询时还要 UNION 或分区裁剪——收益几乎没有。而不分区的单表 1,836 万行，主键查询仍在 1 ms 内，按 `parse_id` 的索引查询在 2 ms 内。

### 5.3 分区表结构模板

```sql
CREATE TABLE m12_exam_node (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY,
    task_id         BIGINT       NOT NULL,
    task_no         VARCHAR(32)  NOT NULL,
    event_type      VARCHAR(32)  NOT NULL,
    event_at        TIMESTAMP    NOT NULL,
    operator_id     BIGINT,
    operator_name   VARCHAR(64),
    detail_json     JSONB,
    remark          VARCHAR(500),
    seq_date        DATE         NOT NULL DEFAULT CURRENT_DATE,
    created_at      TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, seq_date),
    CONSTRAINT ck_m12_exam_node_seq_date CHECK (seq_date = DATE(created_at))
) PARTITION BY RANGE (seq_date);
```

**三个要点：**

1. **`PRIMARY KEY (id, seq_date)`**：PostgreSQL 要求分区表主键必须包含分区键
2. **`seq_date` 冗余列**：PG 12+ 支持表达式分区，但查询时 `WHERE created_at >= ?` 无法走分区裁剪；冗余 `seq_date` 后分区键是普通列，可裁剪
3. **`ck_*_seq_date` 约束**：保证 `seq_date = DATE(created_at)`，防两列不一致

### 5.4 分区自动创建

```sql
CREATE OR REPLACE FUNCTION fn_m12_create_month_partitions(
    p_table   TEXT,
    p_months  INTEGER DEFAULT 3
) RETURNS INTEGER AS $$
DECLARE
    v_start DATE := DATE_TRUNC('month', CURRENT_DATE)::DATE;
    v_end   DATE;
    v_name  TEXT;
    v_count INTEGER := 0;
    i       INTEGER;
BEGIN
    FOR i IN 0..(p_months - 1) LOOP
        v_end := (v_start + (i + 1) * INTERVAL '1 month')::DATE;
        v_name := p_table || '_p' || TO_CHAR(v_start + i * INTERVAL '1 month', 'YYYYMM');
        IF NOT EXISTS (
            SELECT 1 FROM pg_class WHERE relname = v_name
        ) THEN
            EXECUTE FORMAT(
                'CREATE TABLE %I PARTITION OF %I FOR VALUES FROM (%L) TO (%L)',
                v_name, p_table,
                (v_start + i * INTERVAL '1 month')::DATE,
                v_end
            );
            v_count := v_count + 1;
        END IF;
    END LOOP;
    RETURN v_count;
END;
$$ LANGUAGE plpgsql;
```

**调度：** 每月 25 日 02:00 由 APScheduler 调用 `fn_m12_create_month_partitions`，每次预建 3 个月，保证永远有 3 个月余量。

### 5.5 归档策略

| 表 | 在线保留 | 归档介质 | 归档后是否可查 |

| `m12_exam_window_log` | 180 天 | 冷表 | 同上 |
| `m12_review_log` | 180 天 | 冷表 | 同上 |
| `m12_report_file` | 15 年 | 不归档 | — |

| `m12_report_review` | 15 年 | 不归档 | — |

**归档四步流程：**

```sql
-- 第 1 步：创建归档表（结构相同，无分区）
CREATE TABLE m12_review_log_archive (LIKE m12_review_log INCLUDING ALL);

-- 第 2 步：迁入数据
INSERT INTO m12_review_log_archive
SELECT * FROM m12_review_log
WHERE seq_date < CURRENT_DATE - INTERVAL '180 days';

-- 第 3 步：核对行数（铁律：必须完全一致）
SELECT
    (SELECT COUNT(*) FROM m12_review_log_archive) AS archived,
    (SELECT COUNT(*) FROM m12_review_log
     WHERE seq_date < CURRENT_DATE - INTERVAL '180 days') AS to_delete;

-- 第 4 步：不一致则中止；一致则 DETACH 分区
ALTER TABLE m12_review_log DETACH PARTITION m12_review_log_p202501;
DROP TABLE m12_review_log_p202501;
```

**归档铁律：归档表行数必须与被删行数完全一致，才可删主表数据。** 不一致说明归档语句有 bug，继续删会永久丢失数据。

## 6. 约束设计汇总

### 6.1 约束分类统计

| 类型 | 数量 | 代表 |
|---|---|---|
| `CHECK` 状态枚举 | 42 | `ck_m12_parse_status`、`ck_m12_review_status` |
| `CHECK` 时间戳一致性 | 28 | `ck_m12_parse_done`、`ck_m12_review_done` |
| `CHECK` 金额计算 | 6 | `ck_m12_*_amount` |
| `CHECK` 职责分离（SoD） | 8 | `ck_m12_exam_double`、`ck_m12_change_self` |
| `CHECK` 关联完整性 | 15 | `ck_m12_parse_bound`、`ck_m12_review_exempt` |
| `CHECK` 格式校验（正则） | 9 | `ck_m12_file_no`、`ck_m12_parse_sha` |
| `EXCLUDE` 排他约束 | 1 | `ex_m12_slot_overlap` |

### 6.2 数值自洽约束

**原则：凡是可以由其他字段算出的字段，都要有 CHECK 保证算得对。**

| 约束 | 表 | 含义 |
|---|---|---|
| `ck_m12_slot_no_oversell` | `m12_exam_slot` | `used_count <= capacity` |
| `ck_m12_inspection_count` | `m12_inspection` | `sample_ok + missing + corrupted = total` |
| `ck_m12_unconf_cand_count` | `m12_unconfirmed` | `candidate_count = jsonb_array_length(candidate_task_ids)` |
| `ck_m12_version_field_count` | `m12_report_version` | `field_count = jsonb_array_length(snapshot_json->'fields')` |
| `ck_m12_template_field_count` | `m12_parse_template` | `field_count = jsonb_array_length(field_rules)` |

**为什么这些约束必须在数据库层：** 应用层可能有多个代码路径写同一张表（如 `m12_unconfirmed` 既被 `ParseService` 建、又被 `UnconfirmedService` 更新），任何一处漏了更新就会产生不一致数据。数据库 CHECK 是唯一能覆盖所有路径的方式。

### 6.3 职责分离（SoD）约束

| 约束 | 表 | 要求 |
|---|---|---|
| `ck_m12_exam_double` | `m12_exam_ticket` | 调配人 ≠ 复核人（M12-02） |
| `ck_m12_window_before_exec` | `m12_exam_window` | `window_start < exec_started_at` |
| `ck_m12_change_self` | `m12_change_log` | 审批人 ≠ 申请人 |
| `ck_m12_review_assign` | `m12_report_review` | 指派人与审核人分离（建议） |

**核心理由：职责分离是审计强制要求，不能只靠应用层。**

应用层可被绕过：DBA 手动改数据、其他服务 bug 写入、数据迁移脚本。DB 约束是最后一道防线。

### 6.6 为什么唯一索引一定要带 `COALESCE`

**问题：** PostgreSQL 认为 `NULL` 与 `NULL` 不相等。

```sql
-- 若写成这样
CREATE UNIQUE INDEX uk_m12_template_current
    ON m12_parse_template (device_code, template_key)
    WHERE is_current = TRUE;
```

则两条 `device_code IS NULL`（通用模板）都能插入成功，产生"两个通用模板都是当前版"的矛盾状态。

**正确写法：**

```sql
CREATE UNIQUE INDEX uk_m12_template_current
    ON m12_parse_template (COALESCE(device_code, ''), template_key)
    WHERE is_current = TRUE AND is_deleted = FALSE;
```

**为什么不用 `NULLS NOT DISTINCT`：** 那是 PostgreSQL 15+ 的特性，本项目部分测试环境仍是 PG 14。

### 6.7 EXCLUDE 排他约束

M12 有 1 处使用排他约束（M12-01 设备号源）：

```sql
ALTER TABLE m12_exam_slot
    ADD CONSTRAINT ex_m12_slot_overlap
    EXCLUDE USING gist (
        device_id WITH =,
        slot_date WITH =,
        timerange(start_time, end_time) WITH &&
    ) WHERE (is_deleted = FALSE AND is_active = TRUE);
```

**作用：** 同一设备同一天的时段不能重叠。

**前置条件：** 需要 `btree_gist` 扩展（标准 gist 不支持标量列的 `=` 比较）。

### 7.3 数据冗余策略

**M12 在多个表中冗余了患者与项目信息。**

| 表 | 冗余字段 | 理由 |
|---|---|---|
| `m12_exam_task` | `patient_name`、`patient_gender`、`patient_age` | 列表页展示、M03 挂掉降级、历史保真 |
| `m12_parse_record` | `patient_name`、`gender`、`age` | 待确认队列排序、绑定算法频繁读 |

**冗余原则：**

1. **冗余的是"展示与匹配"需要的字段**，不冗余完整患者档案
2. **冗余值是"写入时刻"的快照**，患者后来改名不影响历史记录
3. **权威数据仍在 M03**，需要完整信息时走接口

### 7.4 M01-09 主数据缺失的应对

**问题：** 若 M01-09 未配 `md_exam_item.specimen_type`（检查项目无标本概念，此处举例为检验），某些项目无法接单。

**M12 的应对：**

| 缺失项 | 影响 | 应对 |
|---|---|---|
| 检查项目不存在 | 无法接单，报 `"1201002"` | 阻断，提示去 M01 配置 |
| 项目无 `duration_minutes` | 排程用默认 15 分钟 | 降级放行，记 WARN |
| 项目无 `need_review` | 默认按"需审核"处理 | 安全默认 |
| 危急值规则缺失 | 无法判定危急值 | 仍发布 + 置 `critical_rules_missing=TRUE` + 告警 |
| 设备未在 M01 注册 | 无法排程 | 阻断 |

**危险值规则的应对最重要：** 没有规则就无法判定危急值。M12 的处理是"照常发布报告，但置标记并告警科主任，要求人工核对全部数值"。绝不静默跳过——静默跳过会让临床误以为"系统已检查过"。

### 9.1 四张参数表

| 表 | 作用域 | 参数数 | 特点 |
|---|---|---|---|
| `m12_exam_config` | GLOBAL / DEVICE / STAFF | 11 | 检查执行时间窗与并发 |

| `m12_config_template` | — | 88 | 参数定义字典（初始化用） |

**文档债（T-02）：** `m12_exam_config`、`m12_collect_config`、`m12_parse_config` 是子模块各自建的表，`m12_sys_config` 是 M12-06 建的统一表。线上实施时应统一用 `m12_sys_config`，前三张表作为"历史兼容"保留或迁移。

### 9.2 统一参数表结构

```sql
CREATE TABLE m12_sys_config (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    param_code    VARCHAR(64)  NOT NULL,
    param_name    VARCHAR(128) NOT NULL,
    param_value   VARCHAR(500) NOT NULL,
    param_type    VARCHAR(16)  NOT NULL,
    param_group   VARCHAR(32)  NOT NULL,
    scope         VARCHAR(16)  NOT NULL DEFAULT 'GLOBAL',
    scope_id      VARCHAR(64),
    min_value     VARCHAR(64),
    max_value     VARCHAR(64),
    is_sensitive  BOOLEAN      NOT NULL DEFAULT FALSE,
    is_editable   BOOLEAN      NOT NULL DEFAULT TRUE,
    sort_no       INTEGER      NOT NULL DEFAULT 0,
    remark        VARCHAR(500),
    version       INTEGER      NOT NULL DEFAULT 1,
    created_at    TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at    TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    is_deleted    BOOLEAN      NOT NULL DEFAULT FALSE,
    CONSTRAINT ck_m12_sysconfig_code
        CHECK (param_code ~ '^M12\.[A-Z][A-Z0-9_]*\.[A-Z][A-Z0-9_]*$'),
    CONSTRAINT ck_m12_sysconfig_global
        CHECK (scope <> 'GLOBAL' OR scope_id IS NULL),
    CONSTRAINT ck_m12_sysconfig_scope_id
        CHECK (scope = 'GLOBAL' OR scope_id IS NOT NULL),
    CONSTRAINT ck_m12_sysconfig_sensitive
        CHECK (is_sensitive = FALSE OR is_editable = TRUE)
);

CREATE UNIQUE INDEX uk_m12_sys_config
    ON m12_sys_config (param_code, scope, COALESCE(scope_id, ''))
    WHERE is_deleted = FALSE;
```

### 9.3 为什么要 `COALESCE(scope_id, '')`

**PostgreSQL 认为 `NULL` 与 `NULL` 不相等。** 若不 COALESCE，同一参数可以有两条 `scope='GLOBAL', scope_id=NULL` 的记录，读取时取哪条不确定，导致系统行为"时对时错"。

### 9.4 参数作用域解析顺序

```
EXAM（scope_id = 项目编码）
    ↓ 未命中
DEVICE（scope_id = 设备编码）
    ↓ 未命中
GLOBAL（scope_id = NULL）
    ↓ 未命中
抛 BizException("1206016", "参数不存在")
```

**越具体越优先。** 全局是兜底、设备是微调、项目是特例。

### 9.5 88 条参数分组

| 分组 | 数量 | 示例 |
|---|---|---|
| SCHEDULE（排程） | 8 | `M12.SCHEDULE.SLOT_INTERVAL_MINUTES` |
| EXEC（执行） | 11 | `M12.EXEC.MAX_CONCURRENT` |
| COLLECT（采集） | 27 | `M12.COLLECT.SAMPLE_INTERVAL` |
| PARSE（解析） | 21 | `M12.PARSE.CONFIDENCE_AUTO` |
| REVIEW（审核） | 10 | `M12.REVIEW.SLA_HOURS` |

### 9.6 敏感参数（8 个）

| 参数 | 为什么敏感 |
|---|---|
| `M12.PARSE.CRITICAL_FIELDS` | 改错会让关键字段不再强制确认 |
