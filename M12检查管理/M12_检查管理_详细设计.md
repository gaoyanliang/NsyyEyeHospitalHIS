## 1. 模块概述

### 1.1 模块定位

M12 检查管理是眼科医院所有**非检验类辅助检查**的业务中枢——从医生开单到医生看到报告的全过程。

### 1.2 本院的特殊约束

**这是 M12 设计的第一句话，也是最重要的一句话：**

> **本院所有检查设备均无法接入 HIS。**

具体表现：

| 设备类别 | 典型型号 | 输出方式 | 能否 DICOM |
|---|---|---|---|
| OCT | 拓普康 Triton / 蔡司 Cirrus | 自带工作站，导出 PDF | 否（未购 DICOM 授权） |
| 眼底照相 | 佳能 CR-2 / 拓普康 NW400 | 自带工作站，导出 PDF/JPG | 否 |
| 视野 | 蔡司 HFA3 / 康华 | 自带工作站，导出 PDF | 否 |
| 角膜地形图 | 拓普康 CA-800 | 自带工作站，导出 PDF | 否 |
| 眼压 | 佳能 TX-20 | 打印或导出 PDF | 否 |
| 眼部 B 超 | 迈瑞 / 索诺声 | 内置报告，导出 PDF | 否 |
| UBM | 索维 / 康华 | 内置报告，导出 PDF | 否 |
| 生物测量 | 蔡司 IOLMaster | 自带工作站，导出 PDF | 否 |

**由此推导出的三条硬约束：**

1. **报告只能是 PDF 文件**，通过共享文件夹传递，无任何接口可用
2. **PDF 由技师手工导出**，文件名随机（多数设备默认用检查时间戳或患者姓名拼音）
3. **PDF 内含患者姓名/性别/年龄，但无本院患者 ID**

**本模块的全部复杂度都来自这三条约束。** 如果设备能接 DICOM，M12 只需要 M12-01（排程）、M12-02（执行登记）、M12-05（审核发布）三个子模块，另外三个（M12-03 采集、M12-04 解析、M12-06 设备模板）整个不需要。

### 1.3 为什么 M12 是模块而不是功能

**理由一：检查是眼科的核心业务，占门诊量 60% 以上。**

一家二级眼科医院日均门诊 300 人次，其中需要做检查的约 200 人次，人均 1.5 项检查 → 日均检查 300 项。这个业务量必须有独立的排程、执行、审核、报告管理，不能塞进门诊或医生工作站。

**理由二：检查与检验的业务形态不同。**

| 维度 | 检查（M12） | 检验（M13） |
|---|---|---|
| 设备接入 | 完全不能接入（本项目特例） | 部分可接入，本项目也不能 |
| 标本 | 无标本 | 有标本（采集、条码、流转） |
| 报告形态 | PDF（图像 + 数值混合） | PDF（数值表格为主） |
| 判定逻辑 | 医生看图判断 | 对照参考区间自动判定 |
| 危急值 | 少量（眼压、视野 MD） | 大量（血钾、血糖、血红蛋白） |
| 时间窗 | 单次检查 5~45 分钟 | 结果出具 1~24 小时 |

**理由三：检查的计费模型特殊——按眼别计费。**

眼科绝大多数检查必须双眼都做（OCT 黄斑、眼底照相、眼压、视野、角膜地形图），但**收费按单眼计价 ×2**。这导致「一个检查任务」与「一笔收费」不是一对一：

- 血常规：1 个任务 = 1 笔收费
- OCT 黄斑（双眼）：1 个任务（或 2 个）= 2 笔收费
- 视野（单眼）：1 个任务 = 1 笔收费

M01-09 `md_exam_item.is_eye_side_charge` 字段就是这个规则的来源。M12 必须正确生成任务并回写 M16，否则收费口径全乱。

**理由四：检查报告是医疗纠纷的关键证据。**

眼科检查报告能在数月后回答「当时视神经有没有萎缩」「当时黄斑有没有水肿」。因此：

- PDF 原件保存 15 年（不是 3 年）
- SHA-256 指纹入库防篡改
- 报告版本不可覆盖，修订必须是新版本
- 每次修订记录原因与操作人

这些要求在其他模块都不存在。

### 2.3 六条拆分主线

**主线一：按"物理动作"分，不按"数据表"分。**

M12-01 管排程、M12-02 管执行、M12-03 管文件、M12-04 管解析、M12-05 管审核。每个子模块对应一个**明确的物理动作**，而不是"一张表的增删改查"。

理由：物理动作有清晰的起止时刻与责任人，这是权限、审计、SLA 的天然边界；数据表边界则经常跨动作。

**主线二：时间窗是整条链路的唯一救命线索。**

M12-02 是唯一产生"检查时间窗"的地方。因为 PDF 无患者 ID、文件名随机，OCR 能拿到的只有「姓名 + 性别 + 年龄 + 文件创建时间」。前三个只能缩小范围，**文件创建时间才是唯一的判别依据**，而这个时间只有技师点"开始/完成"时才能精确记录。

这条主线决定了：M12-02 不是简单的"技师打卡"，而是整条链路精度的基石。所以它独立成子模块，且在 M12-02 的设计里花了大量篇幅论证时间窗的容差、截断、重叠处理。

**主线三：采集与解析必须分开。**

M12-03 是文件系统操作（watchdog、SHA-256、归档），M12-04 是 OCR 与 NLP。两者：

- 技术栈完全不同（合并后镜像大 400 MB，OCR 模型更新会让采集服务重启）
- 处理时长差一个量级（采集 ≤ 500 ms，OCR 3~12 秒），合并后 OCR 会拖垮"5 秒检测"的 SLA
- 失败处置不同（采集失败重试或隔离；解析失败需人工介入建模板）

**主线四：绑定与结构化在同一子模块内，但双通道分流。**

M12-04 内部把 OCR 分成两条通道：

- **通道 A（绑定通道）**：姓名/性别/年龄/检查日期 → 用于确定"这是谁的"
- **通道 B（数据通道）**：项目/数值/单位/参考区间 → 用于"报告写了什么"

两者的容错策略完全相反：通道 A 宁可漏绑（错绑是灾难），通道 B 允许标黄确认（错了医生能看出来）。

**主线五：审核是法定责任，不是技术流程。**

M12-04 是"把 PDF 变成数字"的技术加工，M12-05 是"我，某某医师，对这份数字负责"的法律责任承担。两者责任主体不同，必须有独立的签字记录、资质校验、活动留痕。

这也是为什么 M12-05 有 37 个接口——签发、修订、撤回、危急值闭环、推送补偿，每一项都对应一个真实的法律责任场景。

**主线六：配置必须独立，且必须能回滚。**

M12-06 管理设备能力矩阵、OCR 模板、系统参数。这些是"规则"，不是"流水"：

- 规则会反复修改，需版本追溯
- OCR 模板改一个字符可能让历史报告解析失败，需要回归测试与回滚
- 设备能力是排程约束来源，散落多处必然出现"排程说能做、执行说不能做"

### 2.4 为什么不拆更多

有同事问过：为什么不把"危急值"独立成 M12-07？

**答案：危急值的全部数据来源是 M12-04（识别）与 M12-05（判定与处置）。** 独立之后，M12-07 需要向两个子模块拉数据、写回调、维护三套状态机，而它自己的表只有一张 `m12_critical_value`。这不是"高内聚"，是"人为制造远程调用"。

反过来，M12-05 有危急值，是因为"审核时看到红色横幅"与"危急值闭环"是同一个业务动作的两个方面——审核医师既要在报告上签字，也要对危急值负责。

## 3. 核心业务模型

### 3.1 检查任务模型

**一个眼别 = 一个检查任务。**

医生开「OCT 黄斑（双眼）」，系统生成：

| 任务 | 检查项目 | 眼别 | 收费 |
|---|---|---|---|
| T-001 | OCT 黄斑 | OD（右眼） | 1 项 |
| T-002 | OCT 黄斑 | OS（左眼） | 1 项 |

**为什么必须拆开：**

1. **计费分开**：M16 的两笔收费
2. **报告 PDF 分开**：设备导出的 PDF 是单眼的
3. **可能只做一只眼**：患者右眼刚做过、只补左眼
4. **退费分开**：只退一只眼的费用

**例外：`eye_side='OU'`（双眼同检）**

部分项目设备本身支持双眼一次成像（如某些眼底照相机的双眼模式）。此时：

- 若 `is_eye_side_charge = FALSE` → 生成 1 个任务，1 笔收费
- 若 `is_eye_side_charge = TRUE` → 生成 1 个任务，但 `charge_item_count = 2`（两笔收费）

M12-01 的 `ck_m12_task_charge_count` 约束就是这样设计的。

### 3.2 时间窗模型

**这是 M12 最核心的机制。**

**时间窗定义：**

```
处理者点击「开始」  ──┬──────────────────────┬──  处理者点击「完成」
                     │     检查执行窗口       │
                     │                       │
        window_start ◄─                       ─► window_end
```

**容差：**

| 参数 | 默认值 | 理由 |
|---|---|---|
| 提前容差 | 120 秒 | 患者已在门外等，点开始就立刻开始 |
| 滞后容差 | 300 秒 | 技师做完要等患者离开、设备存盘、回到电脑 |
| 最大窗口 | 3600 秒 | 超过则截断（防技师忘点完成） |

**"往前截"而非"往后截"：**

技师忘点完成时，真实完成时间一定**早于**系统记录。所以窗口 `[start, start+3600]` 保留靠近开始的那部分。

**重叠处理：**

两个技师在同一设备的时间窗重叠时，双方 `is_ambiguous = TRUE`，重叠区间内的 PDF **不做自动绑定**。

**设计原则：宁可漏绑（人工处理），绝不误绑。** 绑错会导致误诊、隐私泄露、医疗纠纷。

### 3.3 文件→就诊的绑定模型

**三条路径，优先级从上到下：**

```
┌─────────────────────────────────────────────────────────┐
│ 路径一：投递凭条匹配（精确，置信度 1.0）                  │
│                                                          │
│  技师导出 PDF → 文件名改为 DT{设备}{日期}{序号}.pdf      │
│  → M12-04 识别凭条号 → 查 M12-02 凭条 → 姓名一致 → 绑定  │
└─────────────────────────────────────────────────────────┘
                            │ 未命中
                            ▼
┌─────────────────────────────────────────────────────────┐
│ 路径二：时间窗匹配（概率，置信度 0.95）                   │
│                                                          │
│  PDF 文件 mtime ∈ [window_start-120s, window_end+300s]  │
│  → 排除 is_ambiguous / is_valid=FALSE 的窗口             │
│  → 用 OCR 姓名 + 性别 + 年龄筛选                          │
│  → 唯一命中才绑定                                         │
└─────────────────────────────────────────────────────────┘
                            │ 未命中
                            ▼
┌─────────────────────────────────────────────────────────┐
│ 路径三：待确认队列（人工）                                │
│                                                          │
│  护士看到"张伟 男 45 岁 OCT 黄斑"，在候选列表里点选       │
└─────────────────────────────────────────────────────────┘
```

**为什么"唯一命中才绑定"：**

中文姓名去一个字就是另一个人（张伟/张玮、王芳/王方 都是真实的不同患者）。允许"可能是这个人"的模糊匹配，就等于允许错绑。

**为什么自动绑定率目标 96% 而不是 99%：**

剩下 4% 是客观上无法自动判定的：

| 原因 | 占比 |
|---|---|
| 同名同姓同年龄同时段 | 0.3% |
| 技师忘点开始/完成 | 1~2% |
| OCR 认不出姓名 | 0.5% |
| 设备时钟偏差 | 0.5% |

追求 99% 的唯一办法是放宽匹配条件，代价是错绑。**错绑率必须是 0——不是"尽量低"，而是架构上不允许。**

### 3.4 报告版本模型

M12-05 的报告有版本概念：

```
v1 ──发布──► 医生看到 v1
 │
 │ 技师发现数值录错，修订
 ▼
v2 ──发布──► 医生看到 v2，收到「报告已更新」通知
              原 v1 标 SUPERSEDED（不删除）
```

**为什么不能覆盖：**

- 医生可能已按 v1 做了决策（开药、手术安排）
- 医疗纠纷要回答「当时医生看到的是什么」
- 追溯要求报告内容不可篡改

**修订六约束：**

| 编号 | 约束 |
|---|---|
| M-01 | 修订原因 ≥ 20 字 |
| M-02 | 必须重新审核（不能改完直接发） |
| M-03 | 原版本标 `SUPERSEDED`，不删 |
| M-04 | 已读医生必须收到「报告已更新」通知 |
| M-05 | 超 3 次修订需科主任审批 |
| M-06 | 发布超 7 天不可改，只能补充说明 |

### 3.5 危急值闭环模型

```
    ┌──────────┐
    │ DETECTED │  审核时按规则判定出危急值
    └────┬─────┘
         │ 立即推送
    ┌────▼─────┐
    │ NOTIFIED │  已推送 M07（站内信 + 短信 + WebSocket）
    └────┬─────┘
         │ 医生点击「我看到了」       ⏱ 15 分钟
    ┌────▼────────┐
    │ ACKNOWLEDGED│
    └────┬────────┘
         │ 医生填写处置措施           ⏱ 2 小时
    ┌────▼─────┐
    │ HANDLED  │
    └────┬─────┘
         │ 24 小时自动闭环
    ┌────▼─────┐
    │  CLOSED  │
    └──────────┘

超时升级：15 分钟 → 科室主任；30 分钟 → 医务科；60 分钟 → 分管院长
```

**为什么「确认」与「处置」必须分开：**

- 确认只需点一下"我看到了"（15 分钟内合理）
- 处置要联系患者、安排复诊、开药（2 小时合理）

合并成一个"已处理"状态，医生要么立刻填一堆内容（患者还没联系上），要么 15 分钟内点个"已处理"糊弄——记录失真、闭环失效。

### 3.6 设备能力矩阵模型

```
              OCT-01  OCT-02  CAM-01  VF-01  TON-01
  OCT 黄斑      ✓       ✓       ✗      ✗      ✗
  眼底照相      ✗       ✗       ✓      ✗      ✗
  视野          ✗       ✗       ✗      ✓      ✗
  眼压          ✗       ✗       ✗      ✗      ✓
  角膜地形图    ✗       ✗       ✗      ✗      ✗   ← 警告：无设备支持
```

**为什么要有这张矩阵：**

排程时必须知道"这个项目能在哪台设备做、要多久、要不要散瞳"。散落多处必然出现"排程说能做、执行说不能做"。

**优先级：** `m12_device_item.duration_minutes` > `md_exam_item.duration_minutes` > 默认 15 分钟。

因为同一项目在不同设备耗时不同（OCT 新款 5 分钟 vs 老款 8 分钟），排程必须用后者才能排满不超时。

### 4.3 三条数据铁律

**铁律一：库存/文件类数据只增不改。**

| 表 | 保护方式 |
|---|---|
| `m12_exam_node` | 触发器 `fn_m12_exam_node_readonly()` 禁止 UPDATE/DELETE |
| `m12_exam_window_log` | 触发器 `fn_m12_window_log_readonly()` |
| `m12_review_log` | 触发器 `fn_m12_review_log_readonly()` |

**为什么用触发器而不是应用层：** 应用层可被绕过（DBA 手动改、其他服务 bug、迁移脚本）。触发器是数据库层的最后防线。

**铁律二：唯一性用部分索引，不用应用层"先查后插"。**

典型例子：

```sql
-- 一挂号一会话式的约束
CREATE UNIQUE INDEX uk_m12_parse_file_active
    ON m12_parse_record (file_id)
    WHERE is_deleted = FALSE AND is_superseded = FALSE;
```

应用层"先查后插"在并发下有竞态窗口（两个请求同时查都查不到，然后都插入成功）。唯一索引是数据库级的原子保证。

**为什么是部分索引而不是普通唯一索引：** 同一文件可能"解析→失败→重新解析→成功"多次，普通唯一索引第一次失败就占住位置。

**铁律三：金额与置信度必须用 NUMERIC，禁止 FLOAT。**

- 金额：`NUMERIC(12,2)`，行级先舍入再累加
- 置信度：`NUMERIC(5,4)`（0.9500 表示 95%）
- 分位数：`NUMERIC(8,6)`

**行级先舍入的原因：** 0.005 × 3 先累加得 0.02，先舍入得 0.03。明细 30 行按比例分摊时，先累加会差几毛钱，退费按行退永远对不上。

### 4.4 分区与归档

**37 张表中只有 3 张分区：**

| 表 | 分区方式 | 保留期 |
|---|---|---|
| `m12_exam_node` | 月度 RANGE，预建 36 月 | 15 年 |
| `m12_exam_window_log` | 月度 RANGE，预建 36 月 | 15 年 |
| `m12_review_log` | 月度 RANGE，预建 36 月 | 15 年 |

**为什么主表都不分区：**

| 表 | 15 年行数 | 分区后果 |
|---|---|---|
| `m12_report_file` | 230 万 | `uk_m12_file_sha256` 需含分区键，去重退化为"同年唯一" |
| `m12_exam_task` | 65 万 | `uk_m12_task_request_item` 需含分区键，幂等失效 |
| `m12_parse_record` | 230 万 | `uk_m12_parse_file_active` 需含分区键，幂等失效 |
| `m12_report_review` | 237 万 | `uk_m12_review_parse` 需含分区键，幂等失效 |

**核心理由：跨年份的幂等与去重语义比查询性能更重要。** PostgreSQL 16 单表 2000 万行以下的主键查询仍在 1 ms 内，不需要分区。

**归档铁律：归档表行数必须与被删行数完全一致，才可删主表数据。**

### 6.2 错误码规范

**格式：`AABBCCC`，7 位字符串。**

| 位置 | 含义 | 取值 |
|---|---|---|
| AA | 模块号 | `12` |
| BB | 子模块号 | `01`~`06` |
| CCC | 子模块内序号 | `001`~`999` |

**类型必须是 `str`（带引号）：**

```python
# 正确
raise BizException("1201001", "检查申请不存在")
```

**错误写法（Python 3 会直接报 `SyntaxError: invalid token`）：**

```
raise BizException(0104001, "检查申请不存在")
```

原因：Python 3 中前导零表示八进制，而 `0104001` 含数字 `9` 之外的非法八进制位（且本项目错误码以 `0` 开头），必须写成字符串。

**系统级通用码保留 4~5 位（框架层统一抛出）：**

| 码 | 含义 |
|---|---|
| `0` | 成功（整数） |
| `40001` | 参数校验失败 |
| `40100` | 未认证 |
| `40300` | 无权限 |
| `40400` | 资源不存在 |
| `40900` | 版本冲突 |
| `42200` | 业务规则校验失败 |
| `42900` | 请求过于频繁 |
| `50000` | 服务器内部错误 |
| `50300` | 依赖服务不可用 |

```
└──────────────────────────────────────────────────────────────┘
                               │
                     ┌─────────▼─────────┐
                     │  PostgreSQL 16    │
                     │  37 张表           │
                     └───────────────────┘
```

### 7.2 为什么 watchdog 独立进程

`Observer` 走 inotify，在 SMB 网络盘上常失效。本项目**必须用 `PollingObserver(timeout=3)`**，每 3 秒轮询一次目录。

**风险：** 轮询会占用主进程 CPU。1 万文件约 3% CPU，放在 FastAPI 主进程会拖慢接口响应。

**方案：** watchdog 独立进程，把事件通过 Celery 转给主逻辑，不阻塞任何 HTTP 请求。

### 7.3 为什么 OCR 独立进程

PaddleOCR 加载模型占约 400 MB 内存，推理时 CPU 满载。

**实测数据（8 核 16 GB）：**

| OCR 并发 | 单页耗时 | CPU | Web P95 |
|---|---|---|---|
| 1 | 2.6 s | 25% | 180 ms |
| **2** | **2.8 s** | **48%** | **210 ms** |
| 4 | 4.1 s | 82% | 620 ms |
| 8 | 8.7 s | 100% | 2400 ms |

**结论：并发 2 时吞吐（0.71 页/秒）最高且 Web 不受影响。** 瓶颈不在 OCR 本身，而在"OCR 抢了 Web 的 CPU"。

## 8. 全局业务规则

### 8.1 采集铁律

| 编号 | 规则 | 理由 |
|---|---|---|
| C-01 | 文件稳定性四条件缺一不可 | 只判大小会读到写一半的 PDF |
| C-02 | SHA-256 指纹唯一 | MD5/SHA-1 已被破解，医疗报告是法律证据 |
| C-03 | 归档只移不删 | 误删无法恢复 |
| C-04 | 隔离不删除 | 可能是人工失误，保留证据 |
| C-05 | 每日抽样校验 | 共享盘单点存储，必须能发现丢失 |

### 8.2 解析铁律

| 编号 | 规则 | 理由 |
|---|---|---|
| P-01 | 文本层优先，扫描件才走 OCR | 85% 是数字 PDF，全走 OCR 慢 30 倍 |
| P-02 | 姓名必须完全一致才自动绑定 | 中文姓名去一字就是另一人 |
| P-03 | 只有唯一命中才自动绑定 | 候选 ≥ 2 一律转人工 |
| P-04 | 关键数值字段必须人工确认 | OCR 对数字错时很自信（238→288） |
| P-05 | 字段置信度取该字段所有字符的最小值 | 最弱一环决定整体 |
| P-06 | 双通道姓名冲突整条标红 | 交叉验证 |

### 8.3 审核铁律

| 编号 | 规则 | 理由 |
|---|---|---|
| R-01 | 通过也必须填意见（≥ 10 字） | 法规要求药师/医师负责 |
| R-02 | 退回是终态，不回 PENDING | 保留终态才能统计退回率 |
| R-03 | 发布与推送分开记录 | 发布成功但推送失败是常态 |
| R-04 | 修订必须重新审核 | 不能改完直接发 |
| R-05 | 批量通过单次 ≤ 20 份 | 批量意味着没看数字就签字 |
| R-06 | 含危急值的报告不允许批量通过 | 强制个体注意力 |

### 8.4 危急值铁律

| 编号 | 规则 | 理由 |
|---|---|---|
| K-01 | 危急值必须在审核前判定 | 审核时看到红色横幅会更仔细 |
| K-02 | 确认与处置分开 | 合并会导致记录失真 |
| K-03 | 短信只发 CRITICAL | 短信疲劳会让真正的危急被忽略 |
| K-04 | 修订后必须重新判定 | 改了数值可能从 WARNING 变 CRITICAL |
| K-05 | 规则不可用必须告警，不能静默 | 不知道什么是危急值比审核慢严重得多 |

### 8.5 时间窗铁律

| 编号 | 规则 | 理由 |
|---|---|---|
| W-01 | 滞后容差 > 提前容差 | 做完要等患者离开、存盘、回电脑 |
| W-02 | 超时截断必须"往前截" | 真实完成时间一定早于系统记录 |
| W-03 | 重叠窗口双方标 `is_ambiguous` | 重叠区 PDF 不自动绑定 |
| W-04 | 会话结束必须强制关闭执行中任务 | 否则时间窗永远开放 |
| W-05 | 已绑定报告的任务不可补录 | 重算窗口会连锁解绑 |

### 8.6 职责分离（SoD）

| 编号 | 分离要求 | 实现 |
|---|---|---|
| SoD-01 | 技师不能审核自己提交的报告 | 应用层 + `ck_m12_review_reviewer` |
| SoD-02 | 调配/执行人 ≠ 复核人 | `ck_m12_*_double` DB 约束 |
| SoD-03 | IT 管理员不能改业务数据 | 权限矩阵无 `edit`/`bind` |
| SoD-04 | 系统管理员无任何业务权限 | 权限矩阵全空 |
| SoD-05 | 阈值修改人 ≠ 审批人 | `ck_m12_change_self` |
