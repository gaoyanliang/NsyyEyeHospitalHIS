**设计说明：**

1. **`m12_device` 是设备运营状态的主表，与 M01-09 `md_device` 一对一。** `md_device` 存身份（编码、型号、厂商、购置日期），`m12_device` 存运营状态（当前可用性、排程参数、维护计划）。

2. **为什么不用一张表覆盖两边？**
   - `md_device` 被 M15 物资、M17 财务共同使用，加检查专属字段会污染其他模块
   - 权限不同：`md_device` 由 M01 管理员维护，`m12_device` 由检查科维护
   - 变更频率不同：设备身份几年不变，运营状态可能一天变几次

3. **`m12_device_item` 是能力矩阵，`(device_code, exam_code)` 唯一。** 用 `device_code` 而非 `device_id` 作为业务键，便于跨模块查询不需要 join。

4. **`m12_parse_template` 独立，不与设备强关联。** `device_code` 可空，NULL 表示通用模板（任何设备都能用）。

5. **`m12_sys_config` 用 `(param_code, scope, COALESCE(scope_id, ''))` 唯一。** 必须处理 NULL：PostgreSQL 认为两个 NULL 不相等，若 `scope_id` 为 NULL（GLOBAL 级），同一参数可插入两条全局配置。

6. **`m12_change_log` 存双签审批，`applicant_id <> approver_id` 是 DB 硬约束。** 这比应用层校验更可靠（DBA 手动改也会被拒）。

7. **不建外键。** 理由：跨模块引用（`md_device`）、高频写入、迁移顺序解耦。一致性由应用事务 + 定时对账保证。

**约束说明：**

```sql
-- 设备编码格式
ALTER TABLE m12_device
  ADD CONSTRAINT ck_m12_device_code
  CHECK (device_code ~ '^[A-Z0-9][A-Z0-9-]{1,31}$');

-- 状态枚举
ALTER TABLE m12_device
  ADD CONSTRAINT ck_m12_device_status
  CHECK (status IN ('ACTIVE', 'MAINTAIN', 'FAULT', 'RETIRED'));

  ADD CONSTRAINT ck_m12_device_concurrent
  CHECK (concurrent_count >= 1 AND concurrent_count <= 5);

-- 每日可约上限

  ADD CONSTRAINT ck_m12_device_capacity
  CHECK (daily_capacity >= 1 AND daily_capacity <= 200);

-- 队列前缀：1~2 位大写字母或字母数字
ALTER TABLE m12_device
  ADD CONSTRAINT ck_m12_device_prefix
  CHECK (queue_prefix ~ '^[A-Z][A-Z0-9]?$');

-- 默认时长

  ADD CONSTRAINT ck_m12_device_duration
  CHECK (default_duration_minutes IS NULL
         OR (default_duration_minutes >= 1
             AND default_duration_minutes <= 120));

-- 维护周期
ALTER TABLE m12_device
  ADD CONSTRAINT ck_m12_device_cycle
  CHECK (maint_cycle_days IS NULL
         OR (maint_cycle_days >= 1 AND maint_cycle_days <= 730));

  ADD CONSTRAINT ck_m12_device_remind
  CHECK (maint_remind_days >= 0 AND maint_remind_days <= 60);

  ADD CONSTRAINT ck_m12_device_fault_reason
  CHECK (status <> 'FAULT'
         OR (status_reason IS NOT NULL

ALTER TABLE m12_device
  ADD CONSTRAINT ck_m12_device_retired_reason
  CHECK (status <> 'RETIRED'
         OR (status_reason IS NOT NULL
             AND char_length(btrim(status_reason)) >= 20));

-- 状态变更必须有时间
ALTER TABLE m12_device
  ADD CONSTRAINT ck_m12_device_changed
  CHECK (status_changed_at IS NOT NULL OR status = 'ACTIVE');

-- 外协设备必须有外协机构

  ADD CONSTRAINT ck_m12_device_external
  CHECK (is_external = FALSE
         OR (external_org IS NOT NULL
             AND char_length(btrim(external_org)) >= 2));

-- 维护日期有序
ALTER TABLE m12_device
  ADD CONSTRAINT ck_m12_device_maint_date
  CHECK (last_maintain_date IS NULL OR next_maintain_date IS NULL
         OR next_maintain_date >= last_maintain_date);

```

            │                                 │
            ▼                                 │
      ┌──────────┐  定期保养/报修    ┌──────────────┐

           │                                  │
           │ 突发故障                          │ 无法修复
           ▼                                  ▼
      ┌──────────┐                      ┌──────────────┐
      │  FAULT   │─────────────────────►│  RETIRED     │
      │  故障中   │       报废决定         │  已报废(终态) │
      └────┬─────┘                      └──────────────┘
           │
           └──► ACTIVE（修复完成）
                MAINTAIN（转维修保养）
```

**设计要点：**

1. **为什么 `device_name` 要冗余一份而不用 `md_device` 的？**

   因为业务需要"显示别名"。M01-09 里设备名是登记名"Topcon Triton OCT"，但检查科习惯叫"OCT 1 号机"。技师工作台、叫号屏、报告都用简称更友好。

   冗余后：
   - M01-09 挂掉时 M12-06 仍能展示（降级）
   - 允许本地覆盖而不改主数据
   - 每次排程/执行不需要跨模块查（省一次 HTTP）

   一致性由每日 03:00 的 `sync_device_from_mdm_task` 保证（只在本地为空或主数据变更时才覆盖）。

2. **为什么 `queue_prefix` 用 `CHAR(2)` 而不是 `CHAR(1)`？**

   因为科室设备多时单字母不够用。OCT 有 4 台（A、B、C、D），视野有 2 台（E、F），眼压有 3 台（G、H、I）——26 个字母勉强够。但如果将来眼压增加到 30 台，就需要 `A1`~`A9` 这种扩展。

   `CHAR(2)` 留了这个余地，约束 `^[A-Z][A-Z0-9]?$` 保证两种格式都合法。

3. **为什么 `ck_m12_device_prefix` 的唯一索引要含 `dept_id`？**

   因为分院各自独立叫号。总院 OCT 用 A，分院 OCT 也用 A——这不冲突，因为它们在不同叫号屏。

   如果做全院唯一，分院新增设备时就要避让总院编号，非常不方便。

4. **为什么 `ck_m12_device_changed` 要求 `ACTIVE` 可以是 NULL？**

   因为新建记录时就是 `ACTIVE`，此时还没发生"变更"。若强制 `status_changed_at` 非空，新建时就得填一个假时间。

5. **`ck_m12_device_maint_date` 为什么要求 `next >= last`？**

   防止数据录入错误把下次维护日填到上次之前。维护周期是 30 天，正常情况下次一定在上次之后。

   唯一例外是"提前维护"（本月提前做了），此时要同时更新 `last_maintain_date`，`next` 也会相应推后。

**量级估算：**

| 项 | 估算 |
|---|---|
| 设备总数 | 约 20 台（含报废） |
| 单行大小 | 约 600 字节 |
| 总量 | 约 12 KB |
| 保留期 | **永久**（设备档案），报废后仍保留以供历史追溯 |

**不分区。** 数据量极小。

### 4.3 表：`m12_device_item`

**用途：** 设备能力矩阵。每行表示"某台设备支持某个检查项目，单次耗时多少"。

**设计要点：**

1. **为什么 `is_primary` 要单独标记？**

   同一个检查项目有多台设备可用时，排程默认分配给哪台？眼科的实际逻辑是：

   - OCT 黄斑优先分配 OCT-01（新机器、速度快）
   - OCT-01 满了才分配 OCT-02

   `is_primary` 表达这个偏好。排程时先查 `is_primary=TRUE` 的设备，满了再分配其他。

2. **为什么 `need_prepare` 与 `prepare_minutes` 要同时存在且联动？**

   因为不同检查的准备要求差异极大：

   | 检查 | 准备 | 时长 |
   |---|---|---|
   | 眼压 | 无 | 0 |
   | 视野 | 无 | 0 |
   | 眼底照相 | 需散瞳 | 30 分钟 |
   | OCT | 部分需散瞳 | 0~30 分钟 |

   排程时必须把准备时间算进去，否则"散瞳要 30 分钟"被忽略，患者按 8 分钟排 4 个，实际做不到。

   `ck_m12_devitem_prepare_flag` 保证两者同步——不能出现"需要准备但没写时长"。

3. **为什么 `exam_name` 要冗余？**

   能力矩阵页面展示的是"项目名称"，如果每次都要跨模块查 `md_exam_item`，12 台设备 × 24 个项目 = 288 次查询，即使有缓存也很浪费。

   冗余一份名称后，一次查询就够。同步由 `sync_device_from_mdm_task` 的扩展版本保证（或保存时从 M01-09 抄）。

4. **为什么 `uk_m12_devitem_key` 用部分唯一而不是普通唯一？**

   因为业务上会"取消能力"（软删除），之后可能再添加回来。如果普通唯一，软删除的旧行会占住位置，无法重新添加。

   部分唯一索引 `WHERE is_deleted=FALSE` 只对未删除的行生效，正确表达"当前有效的能力不可重复"。

**量级估算：**

| 项 | 估算 |
|---|---|
| 能力行数 | 约 80 行（20 台设备 × 平均 4 项目） |
| 单行大小 | 约 250 字节 |
| 总量 | 约 20 KB |
| 保留期 | 永久 |

**不分区。**

-- 单号格式

  ADD CONSTRAINT ck_m12_maintain_down
  CHECK ((start_at IS NULL AND end_at IS NULL
          AND downtime_minutes IS NULL)
         OR (start_at IS NOT NULL AND end_at IS NOT NULL
             AND downtime_minutes IS NOT NULL));

-- 停机时长合理
ALTER TABLE m12_device_maintain
  ADD CONSTRAINT ck_m12_maintain_down_range
  CHECK (downtime_minutes IS NULL
         OR (downtime_minutes >= 0 AND downtime_minutes <= 43200));

-- 费用非负
ALTER TABLE m12_device_maintain
  ADD CONSTRAINT ck_m12_maintain_cost
  CHECK (cost_amount IS NULL OR cost_amount >= 0);

-- 配件清单必须是数组
ALTER TABLE m12_device_maintain
  ADD CONSTRAINT ck_m12_maintain_parts
  CHECK (parts_used IS NULL OR jsonb_typeof(parts_used) = 'array');

-- FAIL 必须说明
ALTER TABLE m12_device_maintain
  ADD CONSTRAINT ck_m12_maintain_fail
  CHECK (result <> 'FAIL'
         OR (result_desc IS NOT NULL
             AND char_length(btrim(result_desc)) >= 10));

-- 注释
COMMENT ON TABLE  m12_device_maintain IS 'M12-06 设备维护记录（保养/维修/校准/巡检）';

```

**设计要点：**

1. **为什么 `result` 要分三档（PASS/PARTIAL/FAIL）？**

   真实场景：
   - `PASS`：保养完成，设备正常
   - `PARTIAL`：维修完成但功能受限（如 OCT 的血管成像模块坏了，结构扫描正常）——设备可以继续用，但能力要相应调整
   - `FAIL`：修不好，需要返厂或报废

   如果只有"完成/未完成"两档，`PARTIAL` 的情况会被记成 `PASS`，导致"设备修好了"但实际少了一项能力。

2. **为什么 `downtime_minutes` 要单独存而不从起止时间算？**

   因为维护可能跨多天（返厂维修 5 天）。起止时间是日期跨度，`downtime_minutes` 是实际停机分钟数，两者不等（返厂期间设备不在院内，但"停机"分钟数是 7200 而不是 5×1440）。

   分开存才能准确统计设备可用率。

3. **为什么 `linked_fault_status` 要标记？**

   因为"故障维修完成后设备自动恢复 ACTIVE"这个联动只在特定路径触发。若维护是计划内的（ROUTINE），完成后不改设备状态（本来就是 ACTIVE）。

   有该标记后，服务层逻辑清晰：`if record.linked_fault_status: device.status = ACTIVE`。

4. **为什么 `parts_used` 用 JSONB？**

   因为配件结构多变：可能换一个光源模块（1 项），也可能换 5 个密封圈（5 项），还可能含有规格、批次。JSONB 灵活表达。

   不需要"查所有换过某配件的设备"这种需求，所以不需要拆表。

**量级估算：**

| 项 | 估算 |
|---|---|
| 年维护记录 | 240 条（20 台设备 × 12 次/年） |
| 单行大小 | 约 400 字节 |
| 年数据量 | 约 96 KB |
| 保留期 | **10 年**（设备台账要求） |
| 10 年总量 | 约 2,400 行 |
| **合计** | **约 1 MB** |

**不分区。**

**设计要点：**

1. **为什么 `template_code` 里要含版本号（`_V3`）而 `version_no` 又单独存？**

   这是冗余设计，但两者用途不同：
   - `template_code` 是**人类可读的唯一标识**，运维在日志、告警、页面上用它指代一个具体版本。
   - `version_no` 是**结构化版本号**，用于排序、比较、生成新版本号（V3 → V4）。

   如果只靠 `version_no`，那么在告警消息里只能写"模板 27 命中率低"，运维不知道是哪个模板。如果只靠 `template_code`，那么生成新版本时要做字符串解析。

   冗余的代价：约束 `ck_m12_template_code` 只校验编码格式 `^[A-Z][A-Z0-9_]{2,63}$`，不强校验"后缀必须等于 `_V{version_no}`"。这个一致性由应用层保证（`new_version` 方法自动生成 `{base}_V{n+1}` 并同步 `version_no`）。

2. **为什么 `uk_m12_template_current` 用 `COALESCE(device_code, '')`？**

   因为部分唯一索引里的 NULL 不参与唯一性判断。若直接写 `(device_code) WHERE is_current=TRUE`，两个 `device_code IS NULL` 的通用模板都会认为"NULL 各不相同"，因此都能插入。

   `COALESCE(device_code, '')` 把 NULL 转成空字符串，使得通用模板之间也能正确互斥。

3. **为什么 `match_total`/`match_success` 用计数器而不是每次 `COUNT(*)`？**

   因为"模板匹配率"是列表页每次都要展示的指标。若每次 `COUNT(*)` 扫 `m12_parse_record` 表（230 万行），一次要 3 秒以上。

   用原子递增 `match_total = match_total + 1` （UPDATE 不锁表）后，读取是 O(1)。

   风险：并发写入会造成数值略偏（非事务性递增），但作为质量指标足够。每日 02:00 的 `job_m12_template_stat_refresh` 可从明细表重算校正。

4. **为什么 `baseline_rate` 要存？**

   因为回归对比要"与上一版本比"。若每次回归都重新跑上一版本，耗时翻倍（两次 100 份样本）。

   存下来后，新版本回归时直接与该值比较即可。

   注意：`baseline_rate` 是"上一版本在**当前**样本集上的命中率"，样本集会随时间变化（新的报告格式），所以每次回归后应更新为新版本在当前样本集上的命中率，作为下一次的基线。

5. **为什么 `is_system` 要单独标记而不是判断 `template_code='GENERIC_V1'`？**

   两者等效，但 `is_system` 表达语义更清晰：

   - 约束 `ck_m12_template_generic_sys` 用 `template_code` 判断（DB 层无法引用其他逻辑）
   - 服务层用 `is_system` 判断"系统内置，不可删除"

   将来可能有多个系统内置模板（如 `GENERIC_V2`），`is_system` 是扩展点。

6. **为什么 `field_rules` 用 JSONB 而不是独立字段规则表？**

   - 规则永远针对模板整体读写（编辑模板时一次读全、一次写全）
   - 无"查所有模板中用到 CMT 字段的规则"这种需求
   - 规则表仅 10~50 行，拆表后 JOIN 反而慢

   代价：无法对规则内部字段建索引。但规则只有几十条，全表加载后在内存里过滤即可。

**量级估算：**

| 项 | 估算 |
|---|---|
| 模板数 | 约 50 个（15 类报告 × 平均 3 版本） |
| 单行大小 | 约 4 KB（field_rules 占大头） |
| 总量 | 约 200 KB |
| 保留期 | 永久（历史版本要保留，可回滚） |

**不分区。**

**为什么唯一索引要写 `COALESCE(scope_id, '')`？**

因为 PostgreSQL 的唯一索引把 NULL 视为"各不相同"。若写 `(param_code, scope, scope_id)` 唯一，则：

```sql
INSERT INTO m12_sys_config (param_code, scope, scope_id, param_value)
VALUES ('M12.PARSE.OCR_DPI', 'GLOBAL', NULL, '200');
-- 成功
INSERT INTO m12_sys_config (param_code, scope, scope_id, param_value)
VALUES ('M12.PARSE.OCR_DPI', 'GLOBAL', NULL, '300');
-- 也成功！（因为 NULL <> NULL）
```

这样同一个参数会有两条全局配置，`LIMIT 1` 取值时可能取到旧值。**这是极隐蔽的 bug**，只在 GLOBAL 级参数上出现。

`COALESCE(scope_id, '')` 把 NULL 转成 `''`，两条都会被判定为重复。

> 补充：PostgreSQL 15+ 支持 `NULLS NOT DISTINCT`，但为兼容 14 版本，统一用 `COALESCE`。

**参数作用域解析顺序：**

```
读参数 M12.PARSE.OCR_DPI，指定 device_code=VF-01, exam_code=EXAM_VF

  ① SELECT ... WHERE param_code=? AND scope='EXAM' AND scope_id='EXAM_VF'
        ↓ 命中则返回
  ② SELECT ... WHERE param_code=? AND scope='DEVICE' AND scope_id='VF-01'
        ↓ 命中则返回
  ③ SELECT ... WHERE param_code=? AND scope='GLOBAL'
        ↓ 返回
  ④ 都没有 → 抛 1206016
```

**为什么优先级是 EXAM > DEVICE > GLOBAL？**

因为越具体的配置越贴近实际需求。视野检查在 VF-01 上做（DEVICE 级 300 DPI），但如果某项目有特殊要求（如"视野 10-2 项目要 400 DPI"），EXAM 级优先级更高。

层次：全局兜底 → 设备微调 → 项目特例。

| 项 | 估算 |
|---|---|
| 参数条目 | 约 250 条（88 个 GLOBAL + 设备级约 130 + 项目级约 30） |
| 单行大小 | 约 400 字节 |
| 总量 | 约 100 KB |
| 保留期 | 永久 |

**设计要点：**

1. **为什么非敏感变更也要记录？**

   因为**可追溯性**是配置管理的基本要求。设备从 ACTIVE 改成 MAINTAIN，虽然不需要审批，但三个月后要回答"这台设备什么时候停过、停了多久、为什么"，必须能查到。

   用同一张表记录，`need_approval=FALSE` 的立即 `EFFECTIVE`，`need_approval=TRUE` 的先 `PENDING`。

2. **为什么 `ck_m12_change_self` 要放在数据库层？**

   因为职责分离是**审计强制要求**，不能只靠应用层。应用层可能被绕过（直接调 Service 方法、其他服务写入），DB 约束无法绕过。

   这是整个 M12-06 权限设计的最后一道防线。

3. **为什么 `expire_at` 要在申请时写入而不是审批时算？**

   因为"审批时限从申请时刻起算 24 小时"是业务规则。若审批时才算，就变成"从审批时刻起算 24 小时"，永远不会超时。

   预存 `expire_at` 后，超时扫描只需 `WHERE expire_at < NOW() AND status='PENDING'`，可走索引。

4. **为什么 `change_summary` 与 `detail_json` 都要存？**

   - `change_summary` 是**人可读的一句话**（如"CONFIDENCE_AUTO 0.95 → 0.90"），列表页直接展示
   - `detail_json` 是**结构化明细**（如能力矩阵批量变更的 `[{device_code, exam_code, action}]`），供详情页展开与回放

   两者互补：summary 用于扫描，detail 用于深挖。

5. **为什么 `ROLLED_BACK` 是一个独立状态而不是把原记录改回 PENDING？**

   因为回滚是"承认之前那次变更是错的"，必须留痕。改成 PENDING 会丢失"曾经生效过又回滚"这个关键事实，审计时无法追溯。

**量级估算：**

| 项 | 估算 |
|---|---|
| 日变更 | 5~15 条（设备状态偶尔变、能力偶尔调、参数偶尔改） |
| 年变更 | 约 3,600 条 |
| 单行大小 | 约 700 字节 |
| 年数据量 | 约 2.5 MB |
| 保留期 | **5 年**（审计要求） |
| 5 年总量 | 约 18,000 行 |
| **合计** | **约 13 MB** |

**不分区。**

**约束说明：**

```sql
-- 参数编码格式
ALTER TABLE m12_config_template
  ADD CONSTRAINT ck_m12_cfgtpl_code
  CHECK (param_code ~ '^M12\.[A-Z][A-Z0-9_]*\.[A-Z][A-Z0-9_]*$');

-- 类型枚举
ALTER TABLE m12_config_template
  ADD CONSTRAINT ck_m12_cfgtpl_type
  CHECK (param_type IN ('INT', 'FLOAT', 'STRING', 'BOOL', 'LIST'));

-- 分组枚举
ALTER TABLE m12_config_template
  ADD CONSTRAINT ck_m12_cfgtpl_group
  CHECK (param_group IN ('SCHEDULE', 'EXEC', 'COLLECT', 'PARSE',
                         'REVIEW', 'CRITICAL', 'PUBLISH'));

-- 敏感参数不可只读
ALTER TABLE m12_config_template
  ADD CONSTRAINT ck_m12_cfgtpl_sensitive
  CHECK (is_sensitive = FALSE OR is_editable = TRUE);

-- 数值类型必须有值域定义
ALTER TABLE m12_config_template
  ADD CONSTRAINT ck_m12_cfgtpl_range
  CHECK (param_type NOT IN ('INT', 'FLOAT')
         OR (min_value IS NOT NULL AND max_value IS NOT NULL));

-- 枚举类型必须有可选值
ALTER TABLE m12_config_template
  ADD CONSTRAINT ck_m12_cfgtpl_options
  CHECK (param_type <> 'LIST'
         OR (value_options IS NOT NULL
             AND jsonb_typeof(value_options) = 'array'));

-- 消费方必须是数组
ALTER TABLE m12_config_template
  ADD CONSTRAINT ck_m12_cfgtpl_consumers
  CHECK (consumer_modules IS NULL
         OR jsonb_typeof(consumer_modules) = 'array');

-- 注释
COMMENT ON TABLE  m12_config_template IS 'M12 参数定义字典（初始化与升级用，非业务表）';
COMMENT ON COLUMN m12_config_template.consumer_modules IS '消费方子模块，如 ["M12-04","M12-05"]';
COMMENT ON COLUMN m12_config_template.impact_desc IS '影响面说明，用于参数变更预览';
```

**设计要点：**

1. **为什么要有这张表？**

   因为**参数的元数据必须有唯一来源**。若把"OCR_DPI 的默认值是 200、范围 50~600、是设备级参数"这些信息散落在代码里，那么：

   - 前端无法动态渲染表单（不知道哪些是数值、哪些是枚举）
   - 后端校验依赖硬编码（改参数范围要改代码）
   - 变更预览无法自动生成影响面（不知道谁在消费）

   集中到表里后，`m12_sys_config` 的插入、校验、列表渲染都从这里取元数据。

2. **为什么不把元数据字段直接放在 `m12_sys_config` 里？**

   因为 `m12_sys_config` 有 250 条**多作用域**记录，而参数定义只有 88 条。若把元数据放进去：

   - 同一参数的设备级记录会重复存 min/max（冗余 130 次）
   - 修改参数范围要更新所有作用域的记录（易漏）

   分开后：`m12_config_template` 存 88 条定义，`m12_sys_config` 存 250 条值。`JOIN` 后得到完整信息。

3. **为什么 `impact_desc` 要存在这张表里？**

   因为"这个参数改了会影响什么"是**参数的固有属性**，不是每次变更临时编的。存在这里后，`preview` 接口可直接读用，不需要在代码里写 `if param_code == 'X': ...` 这种硬编码。

   示例：`M12.COLLECT.ROOT_PATH` 的 `impact_desc` 是"共享文件夹根路径变更，需确认新路径已挂载且可读写；未挂载将导致全部报告采集失败"。

**量级估算：**

| 项 | 估算 |
|---|---|
| 参数定义 | 88 条 |
| 单行大小 | 约 500 字节 |
| 总量 | 约 45 KB |
| 保留期 | 永久 |

**不分区。**

    ref_max: Optional[float] = None
    sort_no: int = Field(100, ge=1, le=9999)

    @model_validator(mode="after")
    def _check_by_type(self):
        if self.field_type == "REGEX":
            if not self.pattern:
                raise ValueError(
                    "字段 %s 缺正则表达式" % self.field_code)
            if self.group_index is None:
                raise ValueError(
                    "字段 %s 缺捕获组" % self.field_code)
        elif self.field_type == "SECTION":
            if not self.start_marker or not self.end_marker:
                raise ValueError(
                    "字段 %s 缺起止标记" % self.field_code)
            if self.start_marker == self.end_marker:
                raise ValueError(
                    "字段 %s 的起止标记不能相同" % self.field_code)
        elif self.field_type == "COORD":
            if not self.anchor_text:
                raise ValueError(
                    "字段 %s 缺锚点文本" % self.field_code)
        if (self.ref_min is not None and self.ref_max is not None
                and self.ref_min > self.ref_max):
            raise ValueError(
                "字段 %s 参考区间下限大于上限" % self.field_code)
        return self

| `idx_m12_change_approver` | `m12_change_log` | `status='PENDING'` | 我的待审 |
| `idx_m12_change_expire` | `m12_change_log` | `status='PENDING' AND expire_at IS NOT NULL` | **超时扫描** |

**共 21 个索引，其中 12 个是部分索引。**

**为什么配置表的索引要这么多部分索引？**

因为配置类表的使用模式是"**写少读多、活跃数据极少**"：

| 表 | 总行数 | 活跃行数 | 占比 |
|---|---|---|---|
| `m12_device` | 20 | 维护到期 0~2 | 10% |
| `m12_parse_template` | 50 | 低命中率 1~3 | 6% |
| `m12_change_log` | 1.8 万（5 年） | 待审批 0~5 | **0.03%** |

对 `m12_change_log` 这种表，普通索引遍历 1.8 万行约 1.5ms，部分索引只扫 1 页 < 0.1ms。定时任务每 1 分钟一次，一年 52 万次，差别是 780 秒 vs 52 秒 CPU。

"""M12-06 预置数据：参数定义 + 通用模板。"""

# 通用兜底模板：任何标题都能匹配，保证未知格式报告不丢
GENERIC_V1_RULES = """
[
  {
    "field_code": "PATIENT_NAME",
    "field_name": "患者姓名",
    "field_type": "REGEX",
    "pattern": "姓\\\\s*名[：:\\\\s]*([\\\\u4e00-\\\\u9fa5]{2,1
5})",
    "group_index": 1,
    "value_type": "TEXT",
    "required": true,
    "is_critical": false,
    "sort_no": 1
  }
]
"""


def upgrade():
    # ① 预置通用模板（这是最后一道保险）
    op.execute(
        "INSERT INTO m12_parse_template "
        "(template_code, template_name, device_code, version_no, "

### E.4 上线前运维准备清单

| 序号 | 动作 | 说明 |
|---|---|---|
| 1 | 从 M01-09 同步设备清单 | 全院检查设备必须先在 M01-09 建档 |
| 2 | 为每台设备配置运营参数 | 排队前缀、每日容量、单次时长 |
| 3 | **配置设备能力矩阵** | **每个检查项目至少一台设备支持，否则该项目无法排号** |
| 4 | 为每台设备建专用 OCR 模板 | 从历史 PDF 样本提炼标题正则与字段规则 |
| 5 | **用 100 份样本跑回归测试** | **不通过不能启用，不能让错误模板上生产** |
| 6 | 配置设备级参数 | OCR_DPI、时间窗容差等 |
| 7 | 配置维护计划 | 每台设备的维护周期与提醒天数 |
| 8 | 分配角色权限 | IT 管理员、检查科主任、设备科工程师 |
| 9 | 培训参数变更流程 | 敏感参数走双签，非敏感直接生效 |
| 10 | 建立模板变更 SOP | 改模板 → 回归 → 主任审批 → 启用 → 观察 24 小时 |

第 3 项关键：**能力矩阵是排号的前提**。如果 OCT 黄斑没有配置任何设备支持，M12-01 无法为该检查生成号源，整个流程从第一步就断了。

第 5 项关键：**模板必须回归通过才能上线**。不上报回归，错误模板会影响所有新报告，可能出现"CMT 全部抽不出来"或"数值抽错导致误诊"。
