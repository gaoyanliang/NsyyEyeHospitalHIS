**设计说明：**

1. **全部表不建数据库外键。** 理由：
   - 采集是高频写入（日均 400+ 次登记），外键检查会增加写锁竞争
   - `m12_exam_task` 保留 5 年，`m12_report_file` 保留 15 年（医疗文书），外键会阻止任务表归档
   - 一致性由应用层事务保证，跨表校验在 Service 层完成

2. **`m12_report_file` 是唯一"文件真相源"。** 任何需要知道"这个文件在哪、是什么"的地方都必须查这张表，不允许各自维护路径缓存。

3. **`sha256` 用部分唯一索引而非全表唯一。** 因为重复文件也要入库（保留"技师导了两次"这条信息），只在 `is_duplicate = FALSE AND is_deleted = FALSE` 时要求唯一。

4. **`duplicate_of_file_id` 是自关联。** 首次出现的文件是"主文件"，后续同 SHA-256 的文件指向主文件。查询实际使用时只取主文件，查质量时看重复链长度。

5. **`m12_collect_failure` 与 `m12_report_file` 分离。** 失败的采集没有 `sha256`（文件没读完算不出来），无法放进主表；主表的 `sha256 NOT NULL` 约束不能被破坏。

6. **`m12_inspection_detail` 只记异常行。** 一次巡检抽查 320 份，其中 318 份正常。如果全部记录，一年就是 11.7 万行无用数据。只记 MISSING / CORRUPTED，正常行的"已校验"信息写入 `m12_report_file.last_verify_at` 与 `verify_count`。

7. **`m12_inspection` 与 `m12_inspection_detail` 保留 3 年，主表保留 15 年。** 巡检报告用于追责（"文件哪天丢的、系统有没有发现"），3 年足够；文件元数据必须跟医疗记录留 15 年。

### 4.2 表：`m12_report_file`（报告文件主表）

**用途：** 记录每一个被采集到的报告文件的完整生命周期：从共享文件夹被检测 → 去重 → 入库 → 派发解析 → 归档 → 绑定 → 巡检。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | 否 | IDENTITY | 主键 |
| file_no | VARCHAR(32) | 否 | — | 文件登记号，`WF`+YYYYMMDD+6 位序号 |
| file_name | VARCHAR(255) | 否 | — | 原始文件名（含扩展名） |
| original_path | VARCHAR(512) | 否 | — | 首次发现时的完整路径 |
| current_path | VARCHAR(512) | 否 | — | 当前完整路径（归档后变更） |
| size_bytes | BIGINT | 否 | — | 文件字节数 |
| sha256 | CHAR(64) | 否 | — | 文件内容 SHA-256（小写十六进制） |
| file_mtime | TIMESTAMP | 是 | NULL | 文件最后修改时间（取自 `os.stat().st_mtime`） |
| device_code | VARCHAR(32) | 是 | NULL | 设备编码（从子目录或文件名推断） |
| source | VARCHAR(16) | 否 | — | 来源：`WATCHDOG` / `AUTO_SCAN` / `MANUAL_UPLOAD` |
| page_count | SMALLINT | 是 | NULL | PDF 页数（pypdf 预解析） |
| is_encrypted | BOOLEAN | 是 | NULL | PDF 是否加密（NULL = 尚未探测成功） |
| need_password | BOOLEAN | 否 | FALSE | 是否需要人工提供密码 |
| pdf_password_enc | VARCHAR(256) | 是 | NULL | PDF 密码密文（AES-256-GCM 加密存储） |
| is_scanned | BOOLEAN | 是 | NULL | 是否扫描件（无文本层，必须 OCR） |
| status | VARCHAR(16) | 否 | 'COLLECTED' | 文件状态：`COLLECTED` / `PARSING` / `PARSED` / `PARSE_FAILED` / `QUARANTINE` / `ORPHAN` / `DUPLICATE` |
| archive_status | VARCHAR(16) | 否 | 'PENDING' | 归档状态：`PENDING` / `ARCHIVED` / `FAILED` |
| archived_at | TIMESTAMP | 是 | NULL | 归档完成时间 |
| archive_error | VARCHAR(200) | 是 | NULL | 最近一次归档失败原因 |
| archive_retry | SMALLINT | 否 | 0 | 归档重试次数（上限 3） |
| bind_status | VARCHAR(16) | 是 | NULL | 绑定状态：`UNCONFIRMED` / `BOUND` / `ORPHAN`；NULL = 尚未解析 |
| bound_task_id | BIGINT | 是 | NULL | 已绑定的检查任务 ID（逻辑关联 `m12_exam_task.id`） |
| bind_type | VARCHAR(16) | 是 | NULL | 绑定方式：`TICKET` 凭条 / `WINDOW` 时间窗 / `MANUAL` 人工 |
| parse_id | BIGINT | 是 | NULL | M12-04 的解析记录 ID |
| parse_status | VARCHAR(16) | 是 | NULL | 解析状态回写：`SUCCESS` / `FAILED` / `PARTIAL` |
| parse_retry | SMALLINT | 否 | 0 | 解析重试次数 |
| ocr_confidence | NUMERIC(5,4) | 是 | NULL | OCR 综合置信度（0~1） |
| is_duplicate | BOOLEAN | 否 | FALSE | 是否为重复文件 |
| duplicate_of_file_id | BIGINT | 是 | NULL | 重复文件指向的主文件 ID（自关联） |
| orphan_reason | VARCHAR(500) | 是 | NULL | 标记无主的原因 |
| is_missing | BOOLEAN | 否 | FALSE | 巡检发现文件已丢失 |
| missing_found_at | TIMESTAMP | 是 | NULL | 首次发现丢失的时间 |
| last_verify_at | TIMESTAMP | 是 | NULL | 最近一次巡检校验通过时间 |
| verify_count | SMALLINT | 否 | 0 | 累计巡检校验通过次数 |
| collected_at | TIMESTAMP | 否 | NOW() | 入库时间 |
| collect_seconds | NUMERIC(6,2) | 是 | NULL | 从检测到入库的耗时（秒） |
| collected_by | BIGINT | 是 | NULL | 手工上传时的操作人；自动采集为 NULL |
| remark | VARCHAR(500) | 是 | NULL | 备注 |
| created_at | TIMESTAMP | 否 | NOW() | 创建时间 |
| updated_at | TIMESTAMP | 否 | NOW() | 更新时间 |
| is_deleted | BOOLEAN | 否 | FALSE | 逻辑删除 |

**约束说明：**

```sql
-- 非重复文件的内容指纹全局唯一（去重的最后防线）
CREATE UNIQUE INDEX uk_m12_file_sha256
  ON m12_report_file (sha256)
  WHERE is_duplicate = FALSE AND is_deleted = FALSE;

CREATE UNIQUE INDEX uk_m12_file_no
  ON m12_report_file (file_no)
  WHERE is_deleted = FALSE;

-- 登记号格式：WF + 8 位日期 + 6 位序号
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_no
  CHECK (file_no ~ '^WF[0-9]{8}[0-9]{6}$');

-- SHA-256 必须是 64 位小写十六进制
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_sha256
  CHECK (sha256 ~ '^[0-9a-f]{64}$');

-- 文件大小必须为正
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_size
  CHECK (size_bytes > 0);

-- 状态枚举
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_status
  CHECK (status IN ('COLLECTED','PARSING','PARSED',
                    'PARSE_FAILED','QUARANTINE','ORPHAN','DUPLICATE'));

ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_archive_status
  CHECK (archive_status IN ('PENDING','ARCHIVED','FAILED'));

ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_bind_status
  CHECK (bind_status IS NULL
         OR bind_status IN ('UNCONFIRMED','BOUND','ORPHAN'));

ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_source
  CHECK (source IN ('WATCHDOG','AUTO_SCAN','MANUAL_UPLOAD'));

-- 重复文件必须指向主文件，且不能指向自己
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_dup
  CHECK ((is_duplicate = FALSE AND duplicate_of_file_id IS NULL)
      OR (is_duplicate = TRUE
          AND duplicate_of_file_id IS NOT NULL
          AND duplicate_of_file_id <> id));

-- 已存在的文件必须真的在库里
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_cache_exists
  CHECK (sha256 IS NOT NULL AND length(sha256) = 64);

-- 归档完成必须有时间与路径
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_archived
  CHECK (archive_status <> 'ARCHIVED'
         OR (archived_at IS NOT NULL AND current_path IS NOT NULL));

-- 归档失败必须有原因
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_archive_failed
  CHECK (archive_status <> 'FAILED' OR archive_error IS NOT NULL);

-- 归档重试次数上限 3
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_archive_retry
  CHECK (archive_retry >= 0 AND archive_retry <= 3);

-- 已绑定的文件必须有任务与绑定方式（OCR 绑定的核心一致性约束）
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_bound
  CHECK (bind_status <> 'BOUND'
         OR (bound_task_id IS NOT NULL AND bind_type IS NOT NULL));

ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_bind_type
  CHECK (bind_type IS NULL
         OR bind_type IN ('TICKET','WINDOW','MANUAL'));

-- 无主文件必须有原因（谁判定的、为什么）
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_orphan
  CHECK (bind_status <> 'ORPHAN'
         OR (orphan_reason IS NOT NULL
             AND char_length(btrim(orphan_reason)) >= 10));

-- 需要密码的文件必须有密文（除刚探测到、还没来得及落密的瞬间）
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_password
  CHECK (need_password = FALSE OR pdf_password_enc IS NOT NULL);

-- 丢失标记必须有发现时间
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_missing
  CHECK (is_missing = FALSE OR missing_found_at IS NOT NULL);

-- 巡检校验次数不能为负
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_verify
  CHECK (verify_count >= 0);

-- OCR 置信度 0~1
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_confidence
  CHECK (ocr_confidence IS NULL
         OR (ocr_confidence >= 0 AND ocr_confidence <= 1));

-- 路径分隔符统一为反斜杠（共享盘为 Windows 路径）
ALTER TABLE m12_report_file
  ADD CONSTRAINT ck_m12_file_path
  CHECK (position('/' IN current_path) = 0);

COMMENT ON TABLE m12_report_file IS
  '报告文件主表：每个采集到的 PDF 一条记录，SHA-256 去重，含归档与绑定状态';
COMMENT ON COLUMN m12_report_file.file_no IS
  '文件登记号 WF+YYYYMMDD+6位序号';
COMMENT ON COLUMN m12_report_file.sha256 IS
  '文件内容 SHA-256，64 位小写十六进制，用于去重与完整性校验';
COMMENT ON COLUMN m12_report_file.file_mtime IS
  '文件最后修改时间，用做归档目录分组依据（比 st_ctime 跨平台可靠）';
COMMENT ON COLUMN m12_report_file.current_path IS
  '当前路径：归档前在 INBOX，归档后在 ARCHIVE\yyyy\MM\dd\';
COMMENT ON COLUMN m12_report_file.is_scanned IS
  '扫描件判定：首页可提取文字少于 20 个字符，必须走 OCR';
COMMENT ON COLUMN m12_report_file.need_password IS
  '加密 PDF 标记，为 TRUE 时不派发解析，等待人工提交密码';
COMMENT ON COLUMN m12_report_file.bind_status IS
```

**归档状态机：**

```
    ┌──────────┐
    │ PENDING  │◄─────────┐
    │（待归档） │          │ 重试 < 3 次
    └────┬─────┘          │

    ┌────┴────┐       │  FAILED  │
  成功│      失败│       │（归档失败）│
    ▼         └──────►└──────────┘
┌──────────┐
│ ARCHIVED │  终态：已归档不可重复归档
│（已归档） │
└──────────┘
```

**设计要点：**

1. **为什么 `sha256` 用部分唯一索引而不建全表唯一约束？**
   因为重复文件必须入库。如果全表唯一，第二次导入同内容文件会直接报错，我们就永远不知道"技师导了两次"。而 `WHERE is_duplicate = FALSE` 的部分唯一索引，既保留了重复记录，又保证"非重复文件的内容指纹绝不重复"——这才是去重的真正语义。

2. **为什么同时存 `original_path` 和 `current_path`？**
   归档是移动操作，`current_path` 会变。保留 `original_path` 可以在出问题时回答"这个文件最初是在哪个目录被发现的"——排查"技师为什么导到错误目录"时这是唯一线索。

3. **为什么 `file_mtime` 可空？**
   因为来源不同的文件不一定能拿到 mtime：手工上传的文件只有上传时间，SMB 某些配置下 `stat` 会失败。为空时归档分组退化为用 `collected_at`。

4. **为什么 `is_encrypted` 和 `need_password` 是两个字段？**
   `is_encrypted` 是**探测结果**（NULL 表示 pypdf 没探测成功，文件可能已损坏），`need_password` 是**业务状态**（TRUE 表示正在等人工给密码）。两者语义不同：损坏的 PDF 既探测不出 `is_encrypted`，也不该进"等密码"状态。

5. **为什么 `collect_seconds` 要独立存？**
   因为采集延迟是核心 SLA 指标（目标 ≤ 60 秒）。如果只存检测时间和入库时间，归档后 `current_path` 变了就没法回溯；而且这个耗时包含"等文件写完"的时间，需要用它分析"设备导出慢"还是"系统处理慢"。

6. **为什么 `parse_retry` 与 `archive_retry` 分开？**
   两条独立的重试路径。归档失败（磁盘满、文件被占用）和解析失败（PDF 损坏、OCR 超时）是完全不同的原因，共用一个计数器会导致"归档重试耗尽把解析也堵死"。

7. **为什么 `is_missing` 不直接对应 `is_deleted`？**
   发现文件丢失 ≠ 删除记录。记录仍在（OCR 结果、报告正文都还能看到），只是原件失效。如果置 `is_deleted = TRUE`，医生就再也查不到这份报告了——那才是真正的灾难。

8. **为什么 `collected_by` 可空？**
   自动采集没有操作人。如果强制造一个"系统"用户，会让审计日志里混进一个虚假的人类身份。

**量级估算：**

| 指标 | 估算 |
|---|---|
| 日均采集 | 约 420 份（6 台设备 × 70 份） |
| 年记录数 | 约 153,300 条（含重复约 1.5 千条） |
| 单行大小 | 约 900 字节（含路径与备注） |
| 年增量 | 约 138 MB |
| 保留期 | 15 年（门诊病历法定保存期） |
| 15 年总量 | 约 230 万行，约 2.1 GB |

**分区：** 不分区。

理由：

- 单表 2.1 GB 在 PostgreSQL 16 上是舒适区间，全表扫描 230 万行约 200 ms
- 查询模式是"按 `collected_at` 倒序分页"与"按 `sha256` / `bound_task_id` 精确查"，两类都有索引覆盖
- **最关键的是 `uk_m12_file_sha256` 必须跨年份生效**。若按 `collected_at` 年分区，唯一索引就必须包含分区键，去重语义会退化成"同年唯一"——明年技师重新导出同一份报告会被当成新文件，这是不可接受的

如果未来需要归档，采用"整年导出到 `m12_report_file_hist` 冷表"的方式，并保留 `sha256` 唯一索引。

**状态机：**

```
            检测到文件但采集失败
                    │
                    ▼
              ┌──────────┐
              │ PENDING  │◄──────┐
              │（待处理） │       │ 重试
              └────┬─────┘       │

        │          │          │  │
   重试成功    超过重试上限  需隔离│
        │          │          │  │
        ▼          ▼          ▼  │
   ┌────────┐ ┌──────────┐ ┌─────────────┐
   │ FIXED  │ │ GAVE_UP  │ │ QUARANTINED │
   │（已修复）│ │ （已放弃） │ │  （已隔离）   │
   └────────┘ └──────────┘ └─────────────┘
```

**设计要点：**

1. **为什么不在 `m12_report_file` 里加一个失败状态？**
   因为失败时还没有 `sha256`（文件没读完算不出），而主表的 `sha256` 是 NOT NULL 且参与唯一索引。硬塞进去只能造一个假的 SHA-256 值，会污染去重逻辑。

2. **为什么 `uk_m12_fail_path` 是部分唯一？**
   同一个文件今天失败（共享盘暂时不可用），明天又失败（还被占用），如果每次失败都插一条，页面上就会出现十几条一模一样的记录。部分唯一索引 `WHERE status = 'PENDING'` 保证"同一路径同时只挂一条待处理记录"，重试时更新 `retry_count` 与 `last_retry_at` 即可。

3. **为什么 `QUARANTINED` 还要 `resolved_at`？**
   因为隔离本身是一个"处理完毕"的动作——系统已经把它挪到隔离区，不需要再自动重试。但隔离不等于解决（文件仍是坏的），所以通过 `status` 区分，同时 `fail_file_id` 为空表示"没有产出有效文件"。

4. **为什么 `GAVE_UP` 与 `QUARANTINED` 分两种？**
   `GAVE_UP` 是"重试多次仍不稳定，主动放弃，文件留在原地"（比如设备一直占用）；`QUARANTINED` 是"明确判断为坏文件，挪进隔离区"。前者还有救（技师重开设备后文件可能就正常了），后者需要人工介入。

5. **为什么要存 `fail_detail`？**
   页面要能告诉技师"到底为什么不行"。只给一个 `LOCKED` 代码，技师不知道是被哪个程序占用；存下异常摘要（如 `PermissionError: [WinError 32]`）才能定位。

**量级估算：**

| 指标 | 估算 |
|---|---|
| 日均失败 | 约 3 条（420 × 0.7%） |
| 年记录数 | 约 1,100 条 |
| 单行大小 | 约 600 字节 |
| 年增量 | 约 0.7 MB |
| 保留期 | 3 年（问题追溯） |
| 3 年总量 | 约 3,300 行，约 2 MB |

**分区：** 不分区。数据量太小（3 年 3 千行），分区收益为负。

```sql
  ADD CONSTRAINT ck_m12_inspection_bucket
  CHECK (bucket_recent + bucket_mid + bucket_old = sample_total);

  ADD CONSTRAINT ck_m12_inspection_rate_calc
  CHECK (sample_total = 0
         OR abs(missing_rate - sample_missing::numeric / sample_total) < 0.000001);

ALTER TABLE m12_inspection
  ADD CONSTRAINT ck_m12_inspection_corrupt_calc
  CHECK (sample_total = 0
         OR abs(corrupt_rate - sample_corrupted::numeric / sample_total) < 0.000001);

-- 完成必须有结束时间且晚于开始

  ADD CONSTRAINT ck_m12_inspection_finished
  CHECK (status <> 'FINISHED'
         OR (finished_at IS NOT NULL AND finished_at >= started_at));

-- 失败必须有原因
ALTER TABLE m12_inspection
  ADD CONSTRAINT ck_m12_inspection_failed
  CHECK (status <> 'FAILED' OR fail_reason IS NOT NULL);

-- 确认必须有确认人与备注

  ADD CONSTRAINT ck_m12_inspection_ack
  CHECK (ack_at IS NULL
         OR (ack_by IS NOT NULL AND ack_remark IS NOT NULL));

  '近 30 天抽查数，比例默认 20%';

  '30~180 天抽查数，比例默认 10%';
COMMENT ON COLUMN m12_inspection.bucket_old IS
  '180 天以上抽查数，比例默认 2%';
```

**状态机：**

```
     定时 02:00 / 手动触发
            │
            ▼
      ┌──────────┐
      │ RUNNING  │
      │ （执行中） │
      └────┬─────┘
        ┌──┴───┐
```

**设计要点：**

1. **为什么把 `sample_ok + sample_missing + sample_corrupted = sample_total` 写成数据库约束？**
   因为这是巡检报告可信度的根基。如果三个数加起来不等于总数，说明巡检代码丢了一批文件没校验，丢失率算出来是假的。用 CHECK 约束把它钉死，任何逻辑错误在写入时就会爆炸，而不是等到三个月后审计才发现。

2. **为什么 `missing_rate` 要存成 NUMERIC(8,6) 而不是每次现算？**
   因为告警阈值判断（> 0.1%）需要精确到小数点后 4 位。`0.0005` 与 `0.0015` 都显示成「0.1%」，但一个不该告警一个必须告警。存 6 位小数，配合 `ck_m12_inspection_rate_calc` 自洽校验，既不丢精度又不会算错。

3. **为什么 `bucket_recent/mid/old` 要单独存？**
   页面上要展示"近 30 天 20%、30~180 天 10%、180 天以上 2%"的抽查明细。如果不存这三个数，就得去 `m12_inspection_detail` 里 COUNT —— 而那张表**只记异常行**，正常行不在里面，根本数不出来。

4. **为什么 `ack` 用三个字段而不是一个 `is_acked` 布尔？**
   告警确认必须回答"谁确认的、什么时候、说了什么"。只置一个 TRUE，出了事无法追责——这和"责任人签字"是同一件事。

5. **为什么 `status = 'FINISHED'` 后 `ack` 不改变状态？**
   巡检是客观事实（那天确实丢了 2 个文件），确认只是"我们知道了"，不能改变事实。如果允许确认后变成"已处理"，历史巡检报告就会失真。

**量级估算：**

|---|---|
| 日均巡检 | 1 次（定时）+ 约 0.5 次（手动） |
| 年记录数 | 约 550 条 |

**设计要点：**

1. **为什么只记异常行？**
   一次巡检抽查 320 份，318 份正常。如果全部记录，一年 550 次巡检 × 320 = 17.6 万行，其中 99% 是「OK」。这些数据毫无价值，只会拖慢页面。正常行的"已校验"信息写进 `m12_report_file.last_verify_at` 与 `verify_count`，同样能回答"这份文件最后一次完好是什么时候"。

2. **为什么存 `expected_sha256` 与 `actual_sha256` 两个指纹？**
   `CORRUPTED` 是"文件还在但内容变了"。这时候必须能说清"原本应该是什么、现在是什么"。只存一个 `actual`，事后无法证明文件确实被篡改而不是我们记错了。

3. **为什么冗余 `file_name` / `file_path` / `patient_name` / `task_no`？**
   这些是**丢失现场的快照**。文件已经丢了，`m12_report_file` 里虽然还有这些信息，但如果那份记录本身也被逻辑删除了，或者路径后来又变过，就再也还原不出"当时丢的是张某哪份报告"。冗余存储的代价是几十字节，收益是纠纷时能拿出的硬证据。

4. **为什么 `MISSING` 时 `actual_sha256` 必须为 NULL？**
   文件都不存在，不可能算出实际指纹。如果允许写一个值，说明代码在做假——把所有异常都当成 `CORRUPTED` 处理会掩盖真正的问题（到底是丢了还是被改了，处理方式完全不同）。

5. **为什么 `resolved = FALSE` 时三个处理字段必须全空？**
   防止"半吊子状态"：有人点了「处理中」但没填处理方式，页面就既显示未处理又有处理痕迹。用严格的双向约束把状态钉死。

6. **为什么 `resolve_action` 要有 `ACCEPTED`（确认丢失并接受）？**
   真实场景里有些文件是真的找不回来了（备份也只保留 30 天）。这种情况下必须允许"认账"，否则异常永远挂着，待处理清单会越积越长，最后没人看。但要留下明确记录：这是**主动接受**的丢失，不是忽略。

**量级估算：**

| 指标 | 估算 |
|---|---|
| 每次巡检异常数 | 约 0.3 条（丢失率 0.1% × 320） |
| 年记录数 | 约 170 条 |
| 单行大小 | 约 700 字节 |
| 年增量 | 约 0.1 MB |
| 保留期 | 5 年 |
| 5 年总量 | 约 850 行，约 0.6 MB |

**分区：** 不分区。数据量极小。

**设计要点：**

1. **为什么全部参数都是 GLOBAL？**
   采集是"一台服务器监听一个共享盘"，不存在按科室或设备分别配置监听目录的语义。如果允许 DEVICE 级覆盖，会出现"两台设备写同一个 INBOX，但用不同的 max_size 判定"这种矛盾场景。`scope` 字段保留 `DEVICE` 枚举只是为将来可能的"按设备差异化阈值"预留，当前不写入。

2. **为什么 `param_value` 统一存字符串？**
   参数类型异构（INT / FLOAT / STRING / BOOL）。如果分别建多列，表结构会变成 `int_value` / `float_value` / `str_value` / `bool_value` 四个字段，永远有三个是 NULL。统一存字符串 + `param_type` 标注，是配置表的标准做法，且修改参数类型时不需要改表。

3. **为什么用 `COALESCE(scope_id, 0)` 而不要求 `scope_id NOT NULL DEFAULT 0`？**
   GLOBAL 语义下 `scope_id` 本应为 NULL（表示"无具体对象"）。强制写 0 会让数据失真——0 不是一个合法的设备 ID。用 `COALESCE` 只在索引层面把 NULL 视为 0，既保持数据语义正确，又让唯一索引生效。

4. **为什么单独标 `is_sensitive`？**
   未来可能存共享盘访问凭据（如果不用挂载而用 SMB API）。这类参数在读取接口必须脱敏返回 `******`，且只对 `m12:collect:config` 权限可见。提前留好字段，比事后加安全补丁稳妥。

5. **为什么 `version` 用乐观锁？**
   配置由管理员手工修改，频率极低，但改错会导致采集全停。乐观锁能防"两个人同时打开配置页，后保存的覆盖前一个"——这种事故排查起来极难（配置看起来是对的，但不知道为什么行为变了）。

```python
class BindIn(BaseModel):

    @model_validator(mode="after")

            raise ValueError("必须勾选已核对文件与任务匹配")
```

## 附录 C：关键部分索引

| 表 | 索引 | 条件 | 用途 |
|---|---|---|---|
| `m12_report_file` | `uk_m12_file_sha256` | `is_duplicate = FALSE AND is_deleted = FALSE` | **去重最后防线**：非重复文件指纹全局唯一 |
| `m12_report_file` | `uk_m12_file_no` | `is_deleted = FALSE` | 登记号唯一 |
| `m12_report_file` | `idx_m12_file_archive` | `archive_status = 'PENDING'` | 归档清扫队列，避免全表扫描 230 万行 |
| `m12_report_file` | `idx_m12_file_archive_failed` | `archive_status = 'FAILED'` | 归档失败重试队列 |
| `m12_report_file` | `idx_m12_file_unconfirmed` | `bind_status = 'UNCONFIRMED' AND is_deleted = FALSE` | 待确认队列，正常时只有几十条 |
| `m12_report_file` | `idx_m12_file_parse_failed` | `status = 'PARSE_FAILED'` | 解析失败重试队列 |
| `m12_report_file` | `idx_m12_file_missing` | `is_missing = TRUE` | 丢失清单 |
| `m12_collect_failure` | `uk_m12_fail_path` | `status = 'PENDING' AND is_deleted = FALSE` | 同路径只挂一条待处理，防刷屏 |
| `m12_inspection` | `idx_m12_inspection_running` | `status = 'RUNNING'` | 防并发巡检 |
| `m12_inspection` | `idx_m12_inspection_alert` | `sample_missing > 0 OR sample_corrupted > 0` | 异常巡检速查（正常巡检不占索引） |
| `m12_inspection_detail` | `idx_m12_inspect_detail_unresolved` | `resolved = FALSE` | 待处理异常清单 |
| `m12_collect_config` | `uk_m12_collect_config` | `is_deleted = FALSE` | 参数唯一（含 `COALESCE(scope_id, 0)`） |

**为什么部分索引这么多？**

因为主表 15 年会有 230 万行，而真正高频查询的是**很小的一批**：

| 队列 | 正常规模 | 占比 |
|---|---|---|
| 待归档 | 约 200 条 | 0.009% |
| 待确认 | 约 20 条 | 0.001% |
| 归档失败 | 约 3 条 | — |
| 解析失败 | 约 5 条 | — |
| 已丢失 | 约 5 条 | — |

如果这些队列都用全表索引，索引本身就有 230 万条目；用部分索引后，每个索引只有几十条，查询从"扫索引 20 ms"变成"扫 1 页 <1 ms"。

**上线前必须完成的运维动作：**

| 序号 | 动作 | 说明 |
|---|---|---|
| 1 | 挂载共享盘 | `\\fileserver\exam-reports` 挂到应用服务器，或改用 UNC 路径 + 服务账号 |
| 2 | 创建 4 个子目录 | `INBOX` / `ARCHIVE` / `QUARANTINE` / `MANUAL` |
| 3 | 配置服务账号权限 | 应用账号需对 INBOX/ARCHIVE/QUARANTINE/MANUAL 有读写删权限 |
| 4 | 设备电脑配置默认导出路径 | 每台设备软件的"导出目录"设为 `\\fileserver\exam-reports\INBOX\{设备编码}\` |
| 5 | 校验设备时钟 | 与 NTP 同步，误差 < 30 秒（时间窗绑定依赖此项） |
| 6 | 配置归档盘容量监控 | 接入现有监控系统，阈值 85% / 95% |
| 7 | 备份策略 | ARCHIVE 目录纳入每日增量备份，保留 30 天 |

**第 5 项为什么关键？**

M12-03 的时间窗绑定依赖 `file_mtime`。如果设备电脑时钟比服务器慢 20 分钟，一份 09:00 做完的检查，PDF 的 mtime 会是 08:40——时间窗匹配算法看到这个时间落在窗口之前，就会判失败，全部进待确认队列。**这不是代码能修复的问题，必须靠 NTP 校准。**
