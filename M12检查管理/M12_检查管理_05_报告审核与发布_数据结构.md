**设计说明：**

1. **`m12_report_review` 是主表，一报告一条。** `parse_id` 部分唯一保证"一份解析记录只建一份报告"。修订后产生 v2 记录（新 `id`，同 `report_no`），通过 `root_review_id` 串起版本链。

2. **为什么修订生成新记录而不是在原记录上改版本号？**
   因为每次修订都要独立走一次审核流程（不同审核人、不同时间、不同意见），这些信息必须各自保留。如果共用一条记录，`reviewer_id` 只能存最后一个审核人，历史审核人信息丢失。

   `root_review_id` 让同一份报告的 v1/v2/v3 可以被一条 SQL 查出（`WHERE id = root OR root_review_id = root`）。

3. **`m12_review_field` 为什么独立成表而不是复用 M12-04 的 `m12_parse_field`？**
   因为两者职责不同：
   - `m12_parse_field`（M12-04）记录的是**机器抽取的原始结果**，是解析的事实
   - `m12_review_field`（M12-05）记录的是**审核时确认/修改后的结果**，是医疗文书的内容

   如果共用，医师修改会覆盖机器抽取结果，字段准确率统计（M12-04 的核心 KPI）就无法计算了。

4. **`m12_critical_value` 一对多 `m12_report_review`。** 一份报告可能命中多条危急值规则（如 CMT 同时命中 WARNING 和 CRITICAL）。

5. **`m12_report_publish` 一对多 `m12_report_review`。** 每次发布、撤回、每次推送尝试都产生一条记录。

6. **不建外键，全部逻辑引用。** 理由：跨子模块（`parse_id` 引用 M12-04）、高频写入、迁移顺序解耦。一致性由应用层事务 + 定时对账保证。

**约束说明：**

```sql
-- 报告号格式
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_no
  CHECK (report_no ~ '^RPT[0-9]{8}[0-9]{4}$');

-- 报告状态枚举（6 态）
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_status
  CHECK (status IN ('PENDING', 'REVIEWING', 'PUBLISHED',
                    'REJECTED', 'WITHDRAWN', 'SUPERSEDED'));

-- 审核结论枚举
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_conclusion
  CHECK (conclusion_code IS NULL
         OR conclusion_code IN ('PASS', 'MODIFY', 'REJECT'));

-- 结论与状态必须一致：PUBLISHED 只能是 PASS/MODIFY
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_published_conc
  CHECK (status <> 'PUBLISHED'
         OR conclusion_code IN ('PASS', 'MODIFY'));

-- REJECTED 必须是 REJECT
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_rejected_conc
  CHECK (status <> 'REJECTED' OR conclusion_code = 'REJECT');

-- 已审核状态必须有审核人与时间
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_done
  CHECK (status NOT IN ('PUBLISHED', 'REJECTED', 'SUPERSEDED',
                        'WITHDRAWN')
         OR (reviewer_id IS NOT NULL
             AND reviewer_name IS NOT NULL
             AND reviewed_at IS NOT NULL));

-- REJECT 必须有退回原因（≥20 字）
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_reject_reason
  CHECK (conclusion_code IS NULL
         OR conclusion_code <> 'REJECT'
         OR (opinion IS NOT NULL
             AND char_length(btrim(opinion)) >= 20));

-- MODIFY 必须有修改说明（≥10 字）
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_modify_reason
  CHECK (conclusion_code IS NULL
         OR conclusion_code <> 'MODIFY'
         OR (opinion IS NOT NULL
             AND char_length(btrim(opinion)) >= 10));

-- REVIEWING 必须有认领人与时间
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_claimed
  CHECK (status <> 'REVIEWING'
         OR (reviewer_id IS NOT NULL AND claimed_at IS NOT NULL));

-- PUBLISHED 必须有发布时间
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_publish_time
  CHECK (status <> 'PUBLISHED' OR published_at IS NOT NULL);

-- WITHDRAWN 必须有撤回时间与原因
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_withdraw
  CHECK (status <> 'WITHDRAWN'
         OR (withdrawn_at IS NOT NULL
             AND withdraw_reason IS NOT NULL
             AND char_length(btrim(withdraw_reason)) >= 20));

-- 修订记录必须有修订原因
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_revise
  CHECK (version_no = 1
         OR (revise_reason IS NOT NULL
             AND char_length(btrim(revise_reason)) >= 20));

-- 修订链：version_no > 1 必须有 root_review_id
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_root
  CHECK (version_no = 1 OR root_review_id IS NOT NULL);

-- 版本号范围
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_version_no
  CHECK (version_no >= 1 AND version_no <= 99);

-- 危急值级别与数量一致
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_critical
  CHECK ((critical_count = 0 AND critical_level IS NULL)
         OR (critical_count > 0
             AND critical_level IN ('CRITICAL', 'WARNING')));

-- 置信度区间
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_confidence
  CHECK (overall_confidence IS NULL
         OR (overall_confidence >= 0 AND overall_confidence <= 1));

-- 眼别枚举
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_eye
  CHECK (eye_side IS NULL OR eye_side IN ('OD', 'OS', 'OU', 'NA'));

-- 抽取方式枚举
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_mode
  CHECK (extract_mode IS NULL
         OR extract_mode IN ('TEXT_LAYER', 'OCR'));

-- 绑定方式枚举
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_bind
  CHECK (bind_type IS NULL
         OR bind_type IN ('TICKET', 'WINDOW', 'MANUAL'));

-- 年龄合理区间
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_age
  CHECK (patient_age IS NULL OR (patient_age >= 0 AND patient_age <= 150));

-- 审核耗时非负
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_seconds
  CHECK (review_seconds IS NULL OR review_seconds >= 0);

-- 免审核的不能有审核人认领
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_exempt
  CHECK (need_review = TRUE
         OR status IN ('PUBLISHED', 'WITHDRAWN', 'SUPERSEDED'));

-- 首次已读与次数一致
ALTER TABLE m12_report_review
  ADD CONSTRAINT ck_m12_review_read
  CHECK ((read_count = 0 AND first_read_at IS NULL)
         OR (read_count > 0 AND first_read_at IS NOT NULL));

-- 注释
COMMENT ON TABLE  m12_report_review IS 'M12-05 报告审核主表';
COMMENT ON COLUMN m12_report_review.parse_id IS 'M12-04 m12_parse_record.id（逻辑引用，唯一）';
COMMENT ON COLUMN m12_report_review.root_review_id IS '修订链根记录 ID，v1 为 NULL，v2+ 指向 v1';
COMMENT ON COLUMN m12_report_review.critical_level IS '最高危急值级别，CRITICAL 优先于 WARNING';
COMMENT ON COLUMN m12_report_review.sla_deadline_at IS '审核时限（建档时按 exam_item.report_sla_hours 计算）';
COMMENT ON COLUMN m12_report_review.need_review IS 'FALSE 时建档即 PUBLISHED（眼压/视力/验光）';
COMMENT ON COLUMN m12_report_review.read_count IS 'M07-04 已读回写计数';
```

```

                              │
                              ▼
                   ┌────────────────────┐
                   │      PENDING       │ ◄──────┐
                   └─────────┬──────────┘        │
                             │ 认领               │
                             ▼                   │
                   ┌────────────────────┐        │
                   │     REVIEWING      │        │
                   └──┬──────────┬──────┘        │
                      │          │               │
              PASS/   │          │ REJECT        │
              MODIFY  │          ▼               │
                      │  ┌──────────────┐        │
                      │  │  REJECTED    │────────┘
                      │  │ （终端/退回）│  技师重做→新报告
                      │  └──────────────┘
                      ▼
              ┌──────────────┐
              │  PUBLISHED   │
              └──┬────────┬──┘
                 │        │
            修订 │        │ 撤回
                 ▼        ▼
        ┌──────────────┐ ┌──────────────┐
        │ SUPERSEDED   │ │  WITHDRAWN   │
        │（旧版被取代） │ │ （终端）      │
        └──────────────┘ └──────────────┘

             建档（need_review=FALSE）
                       │
                       ▼
              直接 PUBLISHED
```

**设计要点：**

1. **为什么 `SUPERSEDED` 与 `WITHDRAWN` 都是终态？**
   - `SUPERSEDED`：有新版本替代，旧版不能再操作（否则医生看哪一版？）
   - `WITHDRAWN`：报告作废，不能再操作（撤回是重大决定，不能反悔）
   
   两者的区别是**语义**：`SUPERSEDED` 是"被更好的一版取代"，`WITHDRAWN` 是"这一版不能用了"。统计时"当前有效报告" = `status='PUBLISHED'`。

2. **为什么 `ck_m12_review_published_conc` 要把结论与状态绑死？**
   防止代码 bug 导致"状态 PUBLISHED 但结论是 NULL"或"状态 REJECTED 但结论是 PASS"。这种脏数据在统计报表里会显示"退回率 0"但实际有退回记录。

3. **为什么 `ck_m12_review_exempt` 要求免审核项只能是三种终态？**
   免审核项（`need_review=FALSE`）建档时直接 `PUBLISHED`，不会经过 `PENDING`/`REVIEWING`。若出现免审核项处于 `PENDING`，说明建档逻辑有 bug。

4. **为什么 `critical_count` 与 `critical_level` 要一起存？**
   两者都从 `m12_critical_value` 聚合得出，冗余到主表是为了：
   - 队列排序 `ORDER BY critical_level DESC` 能走索引
   - 列表展示不用 JOIN
   - 约束 `ck_m12_review_critical` 保证两者自洽（无危急值时 level 必为 NULL）

**量级估算：**

| 项 | 估算 |
|---|---|
| 日报告数 | 420 份（含免审核） |
| 年报告数 | 153,300 份 |
| 修订率 | 3%（约 4,600/年） |
| 年总行数 | 约 158,000 行 |
| 保留期 | **15 年**（医疗文书法定保存期） |
| 15 年总量 | 约 2,370,000 行 |
| 单行大小 | 约 700 字节 |
| 表数据 | 约 1.65 GB |
| 索引 | 约 1.1 GB |
| **合计** | **约 2.75 GB** |

**分区：** 不分区。

理由（关键）：

`uk_m12_review_parse` 是"一份解析记录只建一份报告"的幂等基石。若按 `created_at` 年度分区，PostgreSQL 要求唯一索引含分区键，索引退化为 `(parse_id, created_at)` —— 同一解析记录在不同年份可能建两次报告。

而幂等语义必须跨年份（虽然实际不会跨年，但架构上不能留这个口子）。

性能上不需要分区：237 万行在 PG16 舒适区，主键 <1ms；高频查询（待审核、超时、已发布）都有部分索引，索引内只有几十到几千条。

**归档：** 15 年不删。

**约束说明：**

```sql
-- 版本号范围
ALTER TABLE m12_report_version
  ADD CONSTRAINT ck_m12_version_no
  CHECK (version_no >= 1 AND version_no <= 99);

-- 快照必须是对象且含 fields 数组
ALTER TABLE m12_report_version
  ADD CONSTRAINT ck_m12_version_snapshot
  CHECK (jsonb_typeof(snapshot_json) = 'object'
         AND snapshot_json ? 'fields'
         AND jsonb_typeof(snapshot_json -> 'fields') = 'array');

-- 字段数量与快照一致
ALTER TABLE m12_report_version
  ADD CONSTRAINT ck_m12_version_field_count
  CHECK (field_count = jsonb_array_length(snapshot_json -> 'fields'));

-- 变更列表必须是数组
ALTER TABLE m12_report_version
  ADD CONSTRAINT ck_m12_version_changed
  CHECK (changed_fields IS NULL
         OR jsonb_typeof(changed_fields) = 'array');

-- 修订版必须有变更列表
ALTER TABLE m12_report_version
  ADD CONSTRAINT ck_m12_version_revise
  CHECK (version_no = 1
         OR (changed_fields IS NOT NULL
             AND jsonb_array_length(changed_fields) > 0));

-- 已审核的必须有审核人与时间
ALTER TABLE m12_report_version
  ADD CONSTRAINT ck_m12_version_reviewed
  CHECK ((reviewed_by IS NULL AND reviewed_at IS NULL)
         OR (reviewed_by IS NOT NULL AND reviewed_at IS NOT NULL));

-- 注释
COMMENT ON TABLE  m12_report_version IS 'M12-05 报告版本快照（每次发布/修订一版）';
COMMENT ON COLUMN m12_report_version.snapshot_json IS '完整字段快照：fields + patient + exam + source';
COMMENT ON COLUMN m12_report_version.changed_fields IS '相对上一版变更的字段编码数组，v1 为 NULL';
COMMENT ON COLUMN m12_report_version.change_summary IS '人可读的变更摘要，如"CMT 468→486"';
```

**设计要点：**

1. **为什么快照要存全量而不是只存 diff？**
   因为查询"当时医生看到的是什么"需要一次读出完整内容。存 diff 需要从 v1 开始逐版回放，5 次修订后回放 5 次，且中间任何一版被删就断链。

   存全量的代价：单版约 4KB（含 8~20 个字段），一份报告平均 1.03 版，一年约 630MB。可接受。

2. **为什么 `changed_fields` 还要单独存 diff？**
   因为"报告改了什么"是审核质量分析的关键问题。有独立字段可以直接 `jsonb_array_length(changed_fields)` 统计"平均每次修订改几个字段"，不用做两次快照的 JSON diff（那是慢操作）。

3. **为什么快照里要存 `source` 段（parse_id / file_sha256 / bind_type）？**
   这是**纠纷举证的证据链**。患者说"这份报告不是我的"，我们需要能证明：
   - 这份报告来自哪个文件（`file_sha256` 可通过原文件校验）
   - 文件是怎么绑定到患者的（`bind_type` = 时间窗/凭条/人工）
   
   存进快照意味着"当时发布的正是这份报告"，事后改了解析记录也不影响证据。

4. **`uk_m12_version_report` 为什么用 `report_no` 而不是 `review_id`？**
   因为有这两个索引保护不同场景：`uk_m12_version_no (review_id, version_no)` 防同一记录重复版本；`uk_m12_version_report (report_no, version_no)` 防同一报告号的同一版本被写两次（比如两个并发修订请求）。

**量级估算：**

| 项 | 估算 |
|---|---|
| 年版本数 | 158,000（每份报告 1 版 + 修订 3%） |
| 单版快照大小 | 约 4 KB |
| 年数据量 | 约 630 MB |
| 保留期 | 15 年 |
| 15 年总量 | 约 2,370,000 行 |
| 15 年数据量 | 约 9.5 GB |
| **合计（含索引）** | **约 11 GB** |

**不分区。** `uk_m12_version_report` 是报告版本唯一性的保障，分区会削弱它。

**归档：** 15 年不删（医疗文书）。

-- 序号从 1 开始
ALTER TABLE m12_review_field
  ADD CONSTRAINT ck_m12_rfield_seq
  CHECK (seq_no >= 1);

-- 值类型枚举
ALTER TABLE m12_review_field
  ADD CONSTRAINT ck_m12_rfield_type
  CHECK (value_type IS NULL
         OR value_type IN ('TEXT', 'INTEGER', 'DECIMAL', 'DATE', 'ENUM'));

-- 置信度区间
ALTER TABLE m12_review_field
  ADD CONSTRAINT ck_m12_rfield_conf
  CHECK (confidence IS NULL OR (confidence >= 0 AND confidence <= 1));

-- 参考区间有序
ALTER TABLE m12_review_field
  ADD CONSTRAINT ck_m12_rfield_ref
  CHECK (ref_min IS NULL OR ref_max IS NULL OR ref_min <= ref_max);

-- 有区间判断必须有数值
ALTER TABLE m12_review_field
  ADD CONSTRAINT ck_m12_rfield_numeric
  CHECK (is_in_range IS NULL OR numeric_value IS NOT NULL);

-- 确认必须有时间与操作人
ALTER TABLE m12_review_field
  ADD CONSTRAINT ck_m12_rfield_confirmed
  CHECK (is_confirmed = FALSE
         OR (confirmed_at IS NOT NULL AND confirmed_by IS NOT NULL));

-- 人工修改必须留痕：必须记录原值
ALTER TABLE m12_review_field
  ADD CONSTRAINT ck_m12_rfield_edited
  CHECK (is_manual_edited = FALSE
         OR (edit_count >= 1
             AND original_value IS NOT NULL
             AND last_edited_at IS NOT NULL
             AND last_edited_by IS NOT NULL));

-- 修改次数

  ADD CONSTRAINT ck_m12_rfield_edit_count
  CHECK (edit_count >= 0);

-- 注释

COMMENT ON COLUMN m12_review_field.is_critical IS '关键数值字段（眼压/CMT/ECD/MD/PSD/AL）必须确认';
```

**设计要点：**

1. **为什么 `original_value` 必须保留且不可变？**

   这是字段抽取准确率统计的唯一来源。"准确率 = 1 - 人工修改率"，如果人工修改直接覆盖 `field_value`，就永远不知道机器原来抽了什么。

   M12-04 也有 `original_value`，但那是**审核前**的状态。M12-05 这份是**审核全过程**的原值，两者可能不同（M12-04 的字段核对阶段技师可能已改过一次）。

   > 说明：实际实现中，M12-04 的 `m12_parse_field.original_value` 是首次抽取值，M12-05 的 `m12_review_field.original_value` 是建档时从 M12-04 复制过来的 `field_value`（即技师核对后的值）。这样审核医师的修改率统计是独立于技师核对率的。

2. **为什么 `confidence` 只读不改？**
   它是解析质量的客观记录。审核医师修改值后，置信度仍然反映"机器当初有多确定"，这是分析模板质量的依据。

3. **为什么 `is_critical` 要从 M12-04 复制？**
   因为提交审核时要用它做阻断校验（`ck` 不允许存在未确认的关键字段）。如果在 M12-05 重新判定，两处判定逻辑可能不一致。

4. **为什么 `edit_reason` 是可选的？**
   因为审核医师改 486 为 468 时，原因就是"原值错误"这个显然的事。要求必填会让医师填"改错"三个字敷衍。

   强制填写的是**审核意见**（`m12_report_review.opinion`），那里要说明"为什么改"。

| 项 | 估算 |
|---|---|
| 每份报告字段数 | 8 个 |
| 年字段行数 | 1,264,000 行 |
| 单行大小 | 约 250 字节 |
| 年数据量 | 约 316 MB |
| 保留期 | 15 年 |
| 15 年总量 | 约 18,960,000 行 |
| 15 年数据量 | 约 4.7 GB |
| **合计（含索引）** | **约 7 GB** |

**不分区。** 所有查询以 `review_id` 为主（走 `idx_m12_rfield_review`），无跨时间扫描需求。

**设计要点：**

1. **为什么阈值要存快照（`threshold_min` / `threshold_max` / `operator` / `rule_desc`）？**

   因为规则会被修改。今年眼压危急阈值是 40，明年可能调到 45。三年后查"2026-10-22 那个眼压 42 为什么报危急值"，如果只存 `rule_id`，规则已经改成 45 了，系统无法回答这个问题。

   存快照意味着：**当时判定依据永久固化，与规则的后续变化无关**。这是医疗纠纷举证的基本要求。

2. **为什么 `detected_value` 存字符串而不是只存数值？**

   数值 `Decimal("486.0")` 和字符串 `"486.0"` 在展示上不同。PDF 上印的可能是 `486`，也可能是 `486.0`。存储原始字符串+独立的数值列，既能精确保真，又能精确比较。

3. **为什么 `uk_m12_critical_rule (review_id, rule_code)` 要唯一？**

   防止同一份报告同一规则产生多条危急值记录。如果发生（比如 M12-04 重解析），会产生重复通知，医生收到同一条危急值两次。

   而同一字段命中不同规则（CMT>300 WARNING 和 CMT>400 CRITICAL）时，`rule_code` 不同，各自一条，这是正确的。

4. **为什么 `is_overdue_handle` 要单独存？**

   处置时限（`handle_sla_minutes`）从 `notified_at` 算起。`WHERE notified_at + INTERVAL '120 min' < NOW()` 无法走索引，存成布尔字段后可以部分索引 `WHERE is_overdue_handle=TRUE`，超时记录通常只有几条。

   由定时任务每 5 分钟刷新。

5. **为什么 `next_escalate_at` 要落库而不只在 Redis？**

   Redis 是缓存，可能丢失（重启、内存淘汰）。落库后即使 Redis 丢了，扫描任务也能从库中恢复升级队列。

   Redis ZSet 只是加速（避免全表扫），不是唯一真相源。

**设计要点：**

1. **为什么每次推送尝试不单独建表？**
   因为重试次数固定（最多 10 次），而 `attempt_count` + `last_error` + `last_http_status` 三个字段足以回答"重试了几次、最后一次为什么失败"。

2. **为什么 `action='WITHDRAW'` 也要进这张表？**
   因为撤回同样需要"通知 M07"，同样可能失败。用同一张表、同一套推送状态机，代码复用且对账口径统一。

3. **为什么 `critical_notified` 要单独记？**
   发布报告与推送危急值是两个独立动作，可能一个成功一个失败。分开记录才能定位"报告到了但危急值没到"这种最危险的状态。

4. **为什么 `published_by` 允许 NULL？**
   免审核发布（眼压/视力）是系统自动发布，没有人工审核人。

BEGIN
  RAISE EXCEPTION 'm12_review_log 为只增表，禁止 UPDATE/DELETE';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m12_review_log_update
  BEFORE UPDATE ON m12_review_log
  FOR EACH ROW EXECUTE FUNCTION fn_m12_review_log_readonly();

CREATE TRIGGER trg_m12_review_log_delete
  BEFORE DELETE ON m12_review_log
  FOR EACH ROW EXECUTE FUNCTION fn_m12_review_log_readonly();

-- 分区：按 seq_date 月度 RANGE，预建 36 个月
-- 例如：
-- CREATE TABLE m12_review_log_2026_10
--   PARTITION OF m12_review_log
--   FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

-- 注释
COMMENT ON TABLE  m12_review_log IS 'M12-05 审核操作日志（只增表，触发器禁止改删）';
COMMENT ON COLUMN m12_review_log.seq_date IS '分区键，按 created_at 日期填充';
COMMENT ON COLUMN m12_review_log.client_ip IS '客户端 IP，审计用';
COMMENT ON COLUMN m12_review_log.detail_json IS '操作详情 JSON，如强制标记的说明文本';
```

**设计要点：**

1. **为什么这张表要分区而其他表不分区？**
   因为写量大：每天约 1,500 条（420 份报告 × 约 3.5 个动作）。15 年 820 万行，单表查询会变慢。而它**没有跨年份的唯一约束**（日志不需要"某操作只出现一次"），分区无副作用。

2. **为什么用 `seq_date` 而不是 `created_at` 直接做分区键？**
   PostgreSQL 分区键必须是列或表达式。用 `DATE` 列可以直接月度切分，而且生成分区的 DDL 更直观（`FOR VALUES FROM ('2026-10-01')`）。

   `seq_date` 由应用层在插入时填 `CURRENT_DATE`，与 `created_at` 同步。

3. **为什么 `id` 要加 `seq_date` 组成复合主键？**
   PostgreSQL 要求分区表的主键必须包含分区键。若只有 `id` 主键会创建失败。

   实践上 `id` 仍是 IDENTITY 唯一（跨分区唯一），复合主键只是语法要求。

4. **为什么触发器比应用层保护更可靠？**
   应用层可能被绕过（DBA 手动改、其他服务误写）。触发器在数据库层拦截，无法绕过（除非 `DROP TRIGGER`，那会被审计）。

5. **为什么 `client_ip` 用 `INET` 类型？**
   可以支持 IP 范围查询与格式化（`::text`），比 VARCHAR 更规范。

**量级估算：**

| 项 | 估算 |
|---|---|
| 日日志 | 1,500 条（420 × 3.5） |
| 年月度 | 45,000 条 |
| 单行大小 | 约 250 字节 |
| 年月度数据 | 约 11 MB |
| 热数据保留 | 180 天（约 66 MB） |
| 总保留期 | **15 年**（审计要求） |
| 15 年总量 | 约 8,220,000 行 |
| 15 年数据量 | 约 2 GB |

**分区：** 月度 RANGE 分区，按 `seq_date`，预建 36 个月，超出自动创建（定时任务）。超期分区归档到 `m12_review_log_archive` 后 `DETACH`。

**共 17 个关键索引，其中 12 个是部分索引。**

**为什么这么多部分索引？**

`m12_report_review` 15 年 237 万行，但**活跃数据永远是极少数**：

| 状态 | 典型数量 | 占比 |
|---|---|---|
| 待审核 | 20~50 条 | 0.002% |
| 审核中 | 1~3 条 | 0.0001% |
| 超时 | 0~5 条 | 0.0002% |
| 未闭环危急值 | 5~15 条 | 0.0006% |
| 推送失败 | 0~3 条 | 0.0001% |

普通索引遍历 237 万行索引树约 20ms；部分索引后只扫 1 个数据页（<0.1ms）。定时任务每 1~30 分钟一次，一年 5~50 万次，差别是数百秒 vs 几秒 CPU。

from alembic import op

MONTHS = [
    ("2026-10", "2026-11-01"), ("2026-11", "2026-12-01"),
    ("2026-12", "2027-01-01"), ("2027-01", "2027-02-01"),
    # ... 预建 36 个月
]


def upgrade():
    for name, next_bound in MONTHS:
        op.execute(
            "CREATE TABLE IF NOT EXISTS m12_review_log_{n} "
            "PARTITION OF m12_review_log ".format(n=name.replace("-", "_"))
            + "FOR VALUES FROM ('{n}-01') TO ('{b}')".format(
