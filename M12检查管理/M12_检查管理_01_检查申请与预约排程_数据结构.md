## 4. 数据结构设计

### 4.1 ER 关系图

```
┌──────────────────────────────────────────────────────────────────────┐
│                     M12-01 检查申请与预约排程 ER                      │
└──────────────────────────────────────────────────────────────────────┘

   ┌─────────────────────────┐
   │   m12_exam_request      │  检查申请单
   │   （来自 M07 推送）      │  1 张申请单
   └───────────┬─────────────┘
               │ 1 : N（按项目×眼别拆）
               ▼
   ┌─────────────────────────┐          ┌─────────────────────────┐
   │    m12_exam_task        │◄─────────┤   m12_exam_slot         │
   │    检查任务（核心）      │  N : 1   │   设备号源               │
   └───────────┬─────────────┘          └───────────▲─────────────┘
               │                                     │
               │ 1 : 0..1                            │ N : 1
               ▼                                     │
   ┌─────────────────────────┐                       │
   │  m12_exam_appointment   │───────────────────────┘
   │    检查预约              │   占用号源
   └─────────────────────────┘

   ┌─────────────────────────┐
   │    m12_exam_queue       │  候检队列
   │   （到检后产生）         │  task_id 1:1（活动记录）
   └─────────────────────────┘

   ┌─────────────────────────┐
   │    m12_exam_window      │  检查时间窗（OCR 绑定基础）
   │   （技师开始/完成产生）  │  task_id 1:1
   └─────────────────────────┘

   ┌─────────────────────────┐
   │  m12_exam_suspension    │  设备停诊
   │  （按设备+时段）         │  影响 slot / appointment / task
   └─────────────────────────┘
```

**设计说明：**

1. **申请单与任务是一对多，且拆分层级是「项目 × 眼别」**。一张申请单含 N 个检查项目，每个项目含 M 个眼别，生成 N×M 个任务。双眼项目（`OU`）只生成 1 个任务。
2. **号源（slot）是独立的实体，不内嵌在任务里**。原因是号源是"供给"，任务是"需求"，一个号源可以被 0..N 个任务占用（受 capacity 限制）。把号源做成任务的一个字段，就无法表达"这个时段还剩几个"。
3. **预约（appointment）与任务是一对一（0..1）**。即时检查（`WALK_IN`）没有预约记录；预约检查才有。
4. **队列（queue）与任务是一对一（活动记录）**。任务到检时创建，完成或过号时关闭。历史记录保留在同一张表（`closed_at` 非空）。
5. **时间窗（window）与任务是一对一**。这是 OCR 绑定的核心表。它独立成表而不是任务上的 4 个字段，理由见 4.7。
6. **停诊（suspension）与号源是多对多（通过设备+时段匹配）**，不建关联表，因为停诊影响的是"某设备某时段"这个时空范围，用时间区间判断即可。

**约束说明**

```sql
ALTER TABLE m12_exam_task
  ADD CONSTRAINT ck_m12_task_status
  CHECK (status IN ('CREATED','SCHEDULED','WAITING','CHECKED_IN','CALLED',
                    'EXECUTING','EXECUTED','DONE','CANCELLED','FAILED',
                    'RETURNED','SKIPPED','NO_SHOW'));

ALTER TABLE m12_exam_task
  ADD CONSTRAINT ck_m12_task_eye
  CHECK (eye_side IN ('OD','OS','OU','NA'));

-- 加急必须有理由
ALTER TABLE m12_exam_task
  ADD CONSTRAINT ck_m12_task_urgent
  CHECK (is_urgent = FALSE OR (urgent_reason IS NOT NULL AND char_length(urgent_reason) >= 10));

-- 已到检必须有到检时间
ALTER TABLE m12_exam_task
  ADD CONSTRAINT ck_m12_task_checked_in
  CHECK (status NOT IN ('CHECKED_IN','CALLED','EXECUTING','EXECUTED','DONE')
         OR checkin_at IS NOT NULL);

-- 已执行必须有开始与结束时间
ALTER TABLE m12_exam_task
  ADD CONSTRAINT ck_m12_task_executed
  CHECK (status NOT IN ('EXECUTED','DONE')
         OR (exec_started_at IS NOT NULL AND exec_finished_at IS NOT NULL));

-- 执行结束必须晚于开始
ALTER TABLE m12_exam_task
  ADD CONSTRAINT ck_m12_task_exec_order
  CHECK (exec_finished_at IS NULL OR exec_started_at IS NULL
         OR exec_finished_at >= exec_started_at);

-- 已作废必须有原因与时间
ALTER TABLE m12_exam_task
  ADD CONSTRAINT ck_m12_task_cancelled
  CHECK (status <> 'CANCELLED'
         OR (cancelled_at IS NOT NULL AND cancel_reason IS NOT NULL
             AND char_length(cancel_reason) >= 5));

-- 失败必须有原因
ALTER TABLE m12_exam_task
  ADD CONSTRAINT ck_m12_task_failed
  CHECK (status <> 'FAILED' OR fail_reason IS NOT NULL);

-- 重做必须有原因
ALTER TABLE m12_exam_task
  ADD CONSTRAINT ck_m12_task_returned
  CHECK (status <> 'RETURNED' OR return_reason IS NOT NULL);

-- 收费笔数与眼别一致性：非 OU 只能 1 笔，OU 可 1~2 笔
ALTER TABLE m12_exam_task
  ADD CONSTRAINT ck_m12_task_charge_count
  CHECK ((eye_side = 'OU' AND charge_item_count IN (1, 2))
         OR (eye_side <> 'OU' AND charge_item_count = 1));

-- 退费状态枚举
ALTER TABLE m12_exam_task
  ADD CONSTRAINT ck_m12_task_refund_status
  CHECK (refund_status IN ('NONE','PENDING','NOTIFIED','COMPLETED','FAILED'));

-- 报告状态枚举
ALTER TABLE m12_exam_task
  ADD CONSTRAINT ck_m12_task_report_status
  CHECK (report_status IS NULL OR report_status IN
         ('PENDING','PARSING','BOUND','REVIEWED','PUBLISHED'));
```

**状态机**

```
CREATED ──┬─────────────────────────────────► CANCELLED
          │
          ├─► SCHEDULED ──┬─► CHECKED_IN ──┬─► CALLED ──► EXECUTING ──┬─► EXECUTED ──► DONE
          │               │                │                        │
          │               ├─► NO_SHOW      ├─► SKIPPED              └─► FAILED ──┬─► WAITING
          │               │                │                                     └─► CANCELLED
          │               └─► CANCELLED    └─► CANCELLED
          │
          └─► WAITING ────┬─► CHECKED_IN ──► ...
                          └─► CANCELLED

EXECUTED ──► RETURNED ──► WAITING（重做）
SKIPPED / NO_SHOW ──► CHECKED_IN（患者回来了）
```

#### 为什么要独立成表而不用任务上的字段

`m12_exam_task` 上已经有 `exec_started_at` / `exec_finished_at` 两个字段，为什么还要一张独立的 `m12_exam_window` 表？理由有四条：

**理由一：时间窗需要额外的容差计算与状态**

窗口 = 执行时刻 ± 容差。如果放在任务表，就要加 `window_start` / `window_end` / `is_ambiguous` / `is_closed` / `matched_file_count` 五个字段。这几个字段只在"已执行、待绑定"这个短暂阶段有意义，却永久占用任务表空间。

**理由二：窗口需要独立的查询索引**

OCR 绑定的查询是：

```sql
SELECT * FROM m12_exam_window
WHERE device_id = ?
  AND window_start <= :pdf_time
  AND window_end >= :pdf_time
```

这是典型的区间查询，需要 `(device_id, window_start, window_end)` 的复合索引。这个索引在独立表上更小、更快。

**理由三：未来可能扩展到多窗口模型**

当前设计是"一个任务一个窗口"。但真实场景里可能出现：

- 技师做了两次（第一次失败，第二次成功）→ 需要 2 个窗口
- 技师忘记点"开始"，只点了"完成" → 窗口是反向回溯的

独立成表后，一个任务可以有多个窗口记录（改成 1:N），不需要改任务表结构。

**理由四：数据生命周期不同**

时间窗在报告绑定完成后就失去意义，可以定期归档删除。而任务表是永久保留的医疗文书。混在一起会导致归档复杂。

**时间窗的计算规则：**

| 场景 | window_start | window_end |
|---|---|---|
| 正常（有开始有完成） | `exec_started_at - 120s` | `exec_finished_at + 300s` |
| 只点了开始（未完成） | `exec_started_at - 120s` | `NULL`（开放窗口） |
| 窗口超过 3600 秒 | 截断为 `exec_finished_at - 3600s` | `exec_finished_at + 300s` |
| 与同设备其他窗口重叠 | 正常计算 | 正常计算，但 `is_ambiguous = TRUE` |

**量级估算**

| 指标 | 值 |
|---|---|
| 日增行数 | 约 420 条（每个任务一个窗口） |
| 年增行数 | 153,300 |
| 单行大小 | 约 400 B |
| 年增容量 | 约 61 MB |

## 附录 C：关键部分索引

项目中最关键的 6 个部分索引及其设计理由：

| 索引 | 定义 | 为什么需要 |
|---|---|---|
| `uk_m12_task_request_item` | `(request_id, item_code, eye_side) WHERE is_deleted=FALSE` | 防止同一申请单重复接单生成重复任务。M07 可能因网络重试重复推送，没有这个索引就会产生"张伟做了两次 OCT 黄斑右眼" |
| `uk_m12_slot_key` | `(device_id, item_code, slot_date, start_time) WHERE is_deleted=FALSE AND is_active=TRUE` | 防止排程重生成时产生重复号源。加上 `is_active` 条件后，旧批次号源可置 FALSE 保留，新批次正常插入 |
| `uk_m12_appointment_task` | `(task_id) WHERE status IN ('SCHEDULED','ARRIVED') AND is_deleted=FALSE` | 一个任务同时只能有一个有效预约。避免"患者约了 9:00 又约了 10:00" |
| `uk_m12_queue_task` | `(task_id) WHERE status IN ('WAITING','CALLED','IN_SERVICE') AND is_deleted=FALSE` | 一个任务同时在队列中只能有一条活动记录。避免叫号时找到两条 |
| `idx_m12_task_appoint` | `(appoint_start) WHERE status='SCHEDULED'` | 爽约扫描任务每 5 分钟跑一次，只扫 `SCHEDULED` 状态。部分索引让扫描量从 15 万行降到几百行 |
| `idx_m12_window_range` | `(device_id, window_start, window_end)` | **OCR 绑定的核心查询**：按设备和时间范围找候选窗口。这是 M12-04 每接收一份 PDF 就要跑一次的查询 |

**为什么 `idx_m12_window_range` 不用部分索引？**

因为窗口查询的条件是"窗口区间与目标时间点有交集"，而"未绑定"不是一个固定的过滤条件（一个窗口可能匹配 0 个或 1 个文件）。用普通复合索引 `(device_id, window_start, window_end)` 即可让 PG 走索引范围扫描。

**注意：** `m12_exam_task` 的 `request_id` 不加外键约束。原因有两个：

1. **性能**：检查任务是高频查询表，外键检查会增加每次插入的开销。
2. **解耦**：申请单可能被归档删除，但任务要保留。加外键会导致归档时冲突。

一致性由应用层保证：所有任务创建都必须先有申请单。
