## 1. 模块概述

### 1.1 模块定位

检查执行与技师工作台是 M12 检查管理的**中枢**。它同时做三件事：

1. **让技师干活**：技师在这里看到排队患者、叫号、开始检查、完成检查
2. **记录时间**：**这是全系统唯一产生"检查时间窗"的地方**
3. **告诉系统"去哪捡文件"**：生成投递凭条，让技师导出 PDF 时有据可依

```
┌───────────────────────────────────────────────────────────────┐
│  M12-01 检查申请与预约排程                                     │
│  "谁要做、什么时候轮到"                                         │
└───────────────────────────┬───────────────────────────────────┘
                            │ 已到检的任务（CHECKED_IN）
                            ▼
┌───────────────────────────────────────────────────────────────┐
│  M12-02 检查执行与技师工作台（本文档）★ 时间窗的唯一产生者      │
│                                                               │
│  ┌─────────────────────────────────────────────────────┐     │
│  │ ① 技师看到队列 → 叫号 → 患者进来                      │     │
│  │ ② 技师点【开始检查】                                 │     │
│  │      → exec_started_at = NOW()                       │     │
│  │      → ★ 创建时间窗 window_start = NOW() - 120s      │     │
│  │ ③ 技师在设备上操作（HIS 不知情）                      │     │
│  │ ④ 技师点【完成检查】                                 │     │
│  │      → exec_finished_at = NOW()                      │     │
│  │      → ★ 闭合时间窗 window_end = NOW() + 300s        │     │
│  │ ⑤ ★ 打印投递凭条（可选）                              │     │
│  │ ⑥ 技师把 PDF 导出到共享文件夹（HIS 不知情）           │     │
│  └─────────────────────────────────────────────────────┘     │
└───────────────────────────┬───────────────────────────────────┘
                            │ 已执行 + 时间窗 + 凭条
                            ▼
┌───────────────────────────────────────────────────────────────┐
│  M12-03 文件采集 → M12-04 OCR 解析与绑定                       │
│  "根据时间窗和姓名，判断这份 PDF 是谁的"                        │
└───────────────────────────────────────────────────────────────┘
```

**一句话边界：** M12-02 只管**"技师做完了没有、什么时间做的、该给系统留什么线索"**。管不了"文件怎么进来"（M12-03）、"OCR 怎么认"（M12-04）。

### 1.2 为什么独立成子模块

有人会问：技师操作不就是点两下按钮吗？值得单独一个子模块吗？

值得，理由有四条。

#### 理由一：时间窗是整个 OCR 方案的唯一救命线索

本项目最大的技术约束是：**设备无法接入 HIS，PDF 里没有患者 ID，文件名随机。**

那么系统凭什么判断"这份 PDF 是谁的"？只剩两条线索：

1. **OCR 出来的姓名、性别、年龄**
2. **PDF 文件的创建时间落在这个人做检查的时间段内**

第一条线索不可靠——眼科同名同姓、同性别同年龄的患者很常见。上午 9:00 张伟（男 45）做 OCT，9:30 陈伟（男 45）也做 OCT，两份 PDF OCR 出来都是"张伟 男 45"。

第二条线索才是决定性的。而**第二条线索的唯一来源，就是技师在这台电脑上点"开始"和"完成"的动作。**

如果这个动作没有被可靠记录、或者记录的时刻严重偏离实际（技师提前一小时点开始、做完不点完成），整个绑定系统就失效了。所以时间窗必须由一个专门的模块严肃对待，而不是散落在某个业务流程的角落里。

#### 理由二：技师操作有大量异常分支，需要一个统一处理的地方

技师做检查不是流水线。真实场景里的异常至少有以下十种：

| 异常 | 现实场景 |
|---|---|
| 患者配合不佳 | 老年人白内障看不清注视点，OCT 做不出 |
| 单眼可做、另一眼不行 | 左眼流泪不止，只做了右眼 |
| 设备故障中途中断 | 检查做一半设备死机 |
| 患者中途离开 | 交费去了 / 上厕所没回来 |
| 结果不可信需要重做 | 图像质量太差，技师自己判断重做 |
| 技师忘记点开始 | 直接在设备上做了，回头补录 |
| 技师忘记点完成 | 做完就下班了 |
| 患者做了但报告没出来 | 设备没存盘，需要补做 |
| 加急插队 | 急诊患者直接进 |
| 一个技师同时看两台设备 | 眼压和视力可以并行 |

**这十种异常，每一种都会污染时间窗。** 如果 M12-02 不集中处理，时间窗就成了垃圾数据，OCR 绑定必然失败。

#### 理由三：投递凭条是绑定精度的最后保险

虽然用户选择了"时间窗自动绑定"（D2 方案）而不是"投递凭条"（D1 方案），但凭条能力**必须保留**，原因有三：

1. **高风险项目需要精确绑定**。比如 FFA 荧光造影、视野，一天就做几例，但报告价值高、患者容易记混。这种情况下让技师打一张凭条、把文件名改成凭条号，绑定就是 100% 精确。
2. **时间窗出错时的补救手段**。如果某天系统时间错乱、或者技师大面积忘记点完成，导致时间窗全部失效，凭条就是唯一可靠的补救路径。
3. **可配置的降级策略**。系统参数 `M12.EXEC.DROP_TICKET_MODE` 支持三档：`OFF`（不用）、`OPTIONAL`（可选，默认）、`REQUIRED`（强制，用于试点或疑难科室）。

所以 M12-02 必须同时支持两条路径，而不是二选一。

#### 理由四：技师的效率数据是科室管理的唯一来源

检查科主任最关心三个数字：技师日均工作量、平均检查时长、异常率。

这三个数字都只能在 M12-02 采集：

- **工作量**：技师完成的任务数（不是到检数，不是接单数）
- **检查时长**：`exec_finished_at - exec_started_at`
- **异常率**：失败、重做、超时未完成的比例

如果执行动作分散在其他模块，这些数据就拼不出来。

### 1.4 概念辨析

#### 1.4.1 执行（Execution）≠ 操作设备

M12-02 记录的是**"系统认为技师在做检查"这个事实**，而不是"技师真的在操作设备"。

二者可能不一致：

| 现实 | 系统记录 |
|---|---|
| 技师在设备上做完，25 分钟后才回电脑点完成 | `exec_finished_at` 晚 25 分钟 |
| 技师先点开始，然后去接电话 10 分钟 | `exec_started_at` 早 10 分钟 |
| 技师完全忘记点，第二天补录 | 补录时间与真实时间偏差极大 |

**系统无法自动消除这种偏差**，只能靠：
- 容差设计（提前 120s、滞后 300s）
- 超时提醒（未完成超过 60 分钟报警）
- 补录留痕（补录必须有原因，进入数据质量报表）
- 用户习惯培养（这是管理问题，不是技术问题）

#### 1.4.2 时间窗（Window）≠ 执行记录（exec_started_at / exec_finished_at）

| 概念 | 定义 | 存储位置 |
|---|---|---|
| 执行记录 | 技师点"开始/完成"的**精确时刻** | `m12_exam_task.exec_started_at/finished_at` |
| 时间窗 | 系统认为"这份 PDF 可能属于此人"的**时间范围** | `m12_exam_window.window_start/window_end` |

时间窗 = 执行记录 ± 容差，是执行记录的派生数据。二者分开存储的理由见 M12-01 数据结构 4.7 节。

**关键点：时间窗可以重算，执行记录不可篡改。**

如果容差参数调整，可以批量重算所有未绑定的时间窗；但 `exec_started_at` 一旦写入就记录事实，补录会生成新的审计记录而不是覆盖原值。

#### 1.4.3 投递凭条（Drop Ticket）≠ 报告号（Report No）

| 概念 | 产生者 | 生命周期 | 用途 |
|---|---|---|---|
| **投递凭条** | **M12-02** | 检查完成后生成，绑定完成后作废 | **给 PDF 起文件名** |
| 报告号 | M12-05 | 报告发布后生成，永久 | 医生查看、患者查询 |

凭条号格式：`DT` + 设备号 + 日期 + 序号，如 `DT0120261022007`。技师把 PDF 存成这个名字，M12-03 一看文件名就知道是谁的。

**凭条号与任务号一一对应**，所以凭条 = 一个精确的患者标识。

#### 1.4.4 开始检查 ≠ 开始服务

| 概念 | 触发者 | 含义 |
|---|---|---|
| 开始服务（`IN_SERVICE`） | 技师叫号后接管 | 技师在操作，患者已进入检查室 |
| 开始检查（`EXECUTING`） | 技师点【开始检查】 | **设备开始输出数据，时间窗打开** |

为什么要分开？因为眼科检查有一个"准备阶段"：

- 散瞳：滴药后等 30 分钟（这段时间技师可以看别的患者）
- FFA：注射荧光素后等 5 分钟
- OCT：患者进房、坐好、下巴放支架、对准注视点，约 2 分钟

如果"进检查室"就打开时间窗，窗口会包含大段无效时间，绑定精度下降。所以时间窗必须严格锚定在"设备开始出数据"这个时刻。

### 1.5 模块目标

| 指标 | 目标值 | 说明 |
|---|---|---|
| 时间窗完整率 | ≥ 99% | 已完成任务中有有效时间窗的占比 |
| 时间窗准确率 | ≥ 95% | 真实执行时刻落在窗口内的占比 |
| 人工绑定率 | ≤ 10% | 需要人工确认的 PDF 占比（越低越好） |
| 平均检查时长记录完整率 | ≥ 98% | 有开始有完成的比例 |
| 技师操作耗时（开始/完成按钮） | ≤ 200ms | 点击到反馈 |
| 工作台响应 | P95 ≤ 300ms | 队列+任务列表加载 |
| 批量完成（10 条） | ≤ 1s | |
| 工作量统计查询 | ≤ 800ms | 月度 |
| 凭条打印 | ≤ 500ms | |
| 长时间未完成告警 | 100% | 超 60 分钟必须告警 |

**为什么把"时间窗完整率 ≥ 99%"定得这么高？**

因为只要 1% 的任务没有时间窗，这部分患者的 PDF 就全部进不了自动绑定，只能进待确认队列。按日均 420 个任务算，就是每天 4 个患者、每月 120 个患者需要人工处理。这个工作量对检查科是不可接受的。

## 3. 业务模型

### 3.1 执行流程总览

```
技师登录工作台
    │
    ▼
┌───────────────────────────────────────────────┐
│ 看到：本科室所有设备的队列 + 我的待办          │
│  · 每台设备：正在检查 / 候检队列 / 今日已做    │
│  · 我的任务：我负责的设备上的待检、执行中       │
└──────────────────┬────────────────────────────┘
                   │
                   ▼
         ┌──────────────────┐
         │ 选择一台设备      │
         └────────┬─────────┘
                  ▼
      ┌───────────────────────┐
      │ 队列中取第一个任务     │
      │ 点击【叫号】           │
      └───────────┬───────────┘
                  │
                  ▼  患者进入检查室

```

### 3.2 时间窗生成模型

这是 M12-02 最核心的模型，必须精确到秒。

```
时间轴：
        exec_started_at              exec_finished_at
              │                            │
              ▼                            ▼
  ────────────●════════════════════════════●──────────────►
              │                            │
         ┌────┴────┐                  ┌────┴────┐
         │ 120 秒  │                  │ 300 秒  │
         │ 提前容差 │                  │ 滞后容差 │
         └────┬────┘                  └────┬────┘
              ▼                            ▼
        window_start                  window_end

  ────────────○════════════════════════════════○──────────►
              │◄────── 时间窗 window ────────►│
```

**为什么提前容差是 120 秒？**

现实中技师的典型操作顺序有两种：

```
顺序 A（先点开始，再做检查）—— 大多数情况
  点开始 → 患者进门 → 坐好 → 下巴放支架 → 对注视点 → 开始采集
  时间差约 1~3 分钟

顺序 B（先做检查，再点开始）—— 手忙时
  直接操作设备 → 做完 → 想起来要点开始 → 点开始
  时间差可能负几分钟
```

120 秒覆盖了顺序 A 的准备时间，同时不至于让窗口延伸到前一个患者。

**为什么滞后容差是 300 秒？**

技师做完检查后，需要：

1. 让患者离开
2. 在设备上点击保存/导出
3. 回到 HIS 电脑
4. 点击【完成检查】

这个过程 1~5 分钟很常见。300 秒覆盖了绝大多数情况。

**为什么滞后容差 > 提前容差？**

因为数据处理顺序是不对称的：技师做完检查后，会有一段"收尾"时间；而开始前，技师通常已经准备好（患者已在门外等），点开始就立刻开始。所以结束后的偏差通常更大。

**窗口的三种状态：**

| 状态 | 条件 | 说明 |
|---|---|---|
| **开放**（open） | `exec_finished_at IS NULL` | 技师已点开始但未点完成 |
| **闭合**（closed） | `exec_finished_at IS NOT NULL` | 正常完成 |
| **截断**（truncated） | 闭合但长度 > 3600 秒 | 技师忘记点完成，窗口被截断 |

**开放窗口的处理策略：**

技师点了开始但一直没点完成，这是最常见的异常。系统这样处理：

1. **窗口保持开放**，`window_end = NULL`
2. **OCR 绑定时，开放窗口按"当前时间 + 300 秒"参与匹配**——即认为该患者"可能还在做"
3. **超过 60 分钟告警**，提醒技师补点
4. **超过 4 小时自动关闭**，`window_end = exec_started_at + 3600 秒`，并标记 `is_truncated = TRUE`

为什么不用"立即关闭"？因为技师可能只是转换到别的界面了，5 分钟后回来点完成。立即关闭会导致窗口不正确。

为什么 4 小时才强制关闭？因为眼科检查最长的是 FFA（45 分钟），加上等待，2 小时已经极端。4 小时可以确保不会误伤，同时保证数据最终收敛。

### 3.3 时间窗重叠检测模型

```
正常情况（无重叠）：
任务A  ────●═════════●────
任务B                    ────●═════════●────
                             OK

重叠情况（任务A 忘记点完成，任务B 已开始）：
任务A  ────●─────────────────────────────────●
任务B                            ●═══════●
                                 ╲_____╱
                                  重叠区

处理：两个窗口都标记 is_ambiguous = TRUE
     重叠区内的 PDF 不做自动绑定
     进入"待确认队列"，由人工选择
```

**为什么重叠就放弃自动绑定？**

因为重叠意味着"两个患者在同一时间被系统认为在做检查"，此时来了一份 PDF，无法判断属于谁。宁可让技师多点两下，也不能绑错。

**绑错患者的后果有多严重？**

1. 患者的检查报告里出现别人的数据 → 医生可能据此做出错误诊断
2. 患者隐私泄露 → 违反《个人信息保护法》
3. 医院面临医疗纠纷与行政处罚

所以设计原则是：**宁可漏绑（人工处理），绝不误绑。**

### 3.4 投递凭条模型

虽然默认不强制使用凭条，但凭条机制必须完整实现。

```
技师点【完成检查】
    │
    ├─ 系统生成投递凭条号：DT0120261022007
    │    DT      01         20261022        007
    │    │       │          │               │
    │    │       │          │               └─ 当日序号
    │    │       │          └───────────────── 日期
    │    │       └──────────────────────────── 设备序号
    │    └──────────────────────────────────── 凭条前缀
    │
    ▼
┌──────────────────────────────────────────┐
│ 屏幕上显示大号凭条号 + 二维码             │
│ 技师可以：                                │
│  · 点【打印凭条】 → 打印小票贴在设备旁    │
│  · 点【复制编号】 → 复制到剪贴板           │
│  · 忽略（按默认流程导出随机文件名）        │
└──────────────────────────────────────────┘
    │
    ▼
技师在设备上导出 PDF，文件名改为凭条号
    │
    ▼
M12-03 扫描到文件名 DT0120261022007.pdf
    │
    ▼
★ 100% 精确绑定（不需要 OCR 判断身份）
```

**凭条模式的三个档位：**

| 模式 | 参数值 | 行为 | 适用场景 |
|---|---|---|---|
| 关闭 | `OFF` | 不生成凭条，全靠时间窗 | 默认，大多数检查项目 |
| 可选 | `OPTIONAL` | 生成但技师可忽略 | **推荐默认值** |
| 强制 | `REQUIRED` | 不打印凭条不允许点完成 | FFA、视野等高价值项目 |

**为什么默认是 OPTIONAL 而不是 OFF？**

因为凭条成本极低（一行小票纸），但收益明确：即使只有 30% 的技师愿意用，也能把 30% 的绑定从"概率匹配"变成"精确匹配"。而且一旦发生时间窗失效的事故，凭条就是救命的。

**为什么不能对全部项目强制 REQUIRED？**

因为技师的工作流已经固定，强制改会引发抵触。而且很多检查项目（如眼压测量，3 分钟一个）如果每做一个人都打印凭条，打印机都扛不住。所以强制只适用于低频高价值项目。

### 3.5 执行异常分类模型

技师的异常处理必须分类，否则统计数据无意义。

| 异常类别 | 代码 | 是否可重排 | 是否退费 | 时间窗处理 |
|---|---|---|---|---|
| **患者未到** | `PATIENT_ABSENT` | 是 | 否 | 不产生窗口 |
| **患者不配合** | `POOR_COOPERATION` | 是 | 否 | 关闭窗口，标记无效 |
| **单眼失败** | `ONE_EYE_ONLY` | 是（另一眼另做） | 否 | 关闭窗口，只标一只眼 |
| **设备故障** | `EQUIPMENT_FAILURE` | 是 | 否 | 关闭窗口 |
| **图像质量差** | `POOR_QUALITY` | 是 | 否 | 关闭窗口 |
| **患者中途离开** | `PATIENT_LEFT` | 是 | 否 | 关闭窗口 |
| **检查项目错误** | `WRONG_ITEM` | 否 | 是 | 不产生窗口 |
| **患者放弃** | `PATIENT_GIVE_UP` | 否 | 是 | 关闭窗口 |
| **其他** | `OTHER` | 视情况 | 视情况 | 视情况 |

**"是否可重排"与"是否退费"的区别：**

- **可重排**：检查没做成，但钱不退，患者改天再来做（或转人工处理）
- **退费**：检查彻底不做了，走 M16 退费流程

大部分异常是"可重排不退费"——患者已经交钱了，不能因为一次没做成就不给做。

### 3.6 补录模型

技师忘记点开始/完成是最常见的操作失误。补录必须严格管控。

```
技师发现忘记点
    │
    ▼
┌────────────────────────────────────────────┐
│ 在工作台找到该任务 → 点【补录时间】          │
└──────────────────┬─────────────────────────┘
                   ▼
┌────────────────────────────────────────────┐
│ 填写：                                       │
│  · 实际开始时间（必填）                       │
│  · 实际完成时间（必填）                       │
│  · 补录原因（必选）：忘记点开始/忘记点完成/   │
│    系统卡顿/网络中断/其他                     │
│  · 详细说明（≥10 字）                        │
└──────────────────┬─────────────────────────┘
                   ▼
┌────────────────────────────────────────────┐
│ 校验：                                       │
│  · 开始 < 完成                              │
│  · 完成 ≤ 现在                              │
│  · 时长 ≤ 4 小时                             │
│  · 与同设备其他任务无重大重叠                 │
└──────────────────┬─────────────────────────┘
                   ▼
┌────────────────────────────────────────────┐
│ 写入补录记录（不覆盖原值）：                  │
│  · 原 exec_started_at 保留                   │
│  · 新增 m12_exam_time_correction 记录         │
│  · 时间窗按补录后的时间重算                   │
│  · 标记窗口 window_source = 'CORRECTED'      │
└──────────────────┬─────────────────────────┘
                   ▼
┌────────────────────────────────────────────┐
│ 进入数据质量报表                              │
│  · 按技师汇总补录次数                         │
│  · 补录率 > 5% 的技师需要培训                  │
└────────────────────────────────────────────┘
```

**为什么补录需审批？**

不需要审批，但需要留痕。理由：

- 补录是**技术性操作**，不是业务决策。技师忘记点了，事实就是忘了，审批改变不了这个事实。
- 需要审批的是**"补录成什么时间"**，而这个时间只有技师本人知道。审批人无法判断对不对。
- 所以采用**留痕 + 报表监控**，而不是审批。补录率异常的技师由科主任谈话，而不是逐笔审批。

**但有一种情况需要审批：补录时间超过 24 小时。**

因为超过 24 小时后补录，记忆已经不可靠，且可能涉及医疗纠纷。这时需要科主任确认。

### 3.7 技师工作量模型

技师工作量的计算口径必须明确，否则无法用于绩效。

| 指标 | 计算口径 | 说明 |
|---|---|---|
| **完成检查数** | `status IN ('EXECUTED','DONE')` 且 `exec_by = 该技师` | 核心指标 |
| **操作时长** | `SUM(exec_finished_at - exec_started_at)` | 设备占用时间 |
| **平均单例时长** | 操作时长 ÷ 完成检查数 | 效率指标 |
| **失败数** | `status='FAILED'` | 不计入完成数 |
| **重做数** | `status='RETURNED'` 后重做完成的 | 质量指标 |
| **超时未完成数** | 执行中超过 60 分钟 | 操作规范指标 |
| **补录次数** | 有补录记录的任务数 | 数据质量指标 |

**为什么不直接数"到检人数"？**

因为到检不等于完成。一个技师可能叫了 10 个人，但只完成了 8 个（2 个患者不配合）。用完成数才算真实工作量。

**为什么"操作时长"用 `exec_finished_at - exec_started_at` 而不是任务在医生端的停留时间？**

因为技师的成本是"占用设备和检查室的时间"，这才是可衡量的资源消耗。

**为什么 V-08 要提示"是否误点"？**

因为最容易发生的操作失误是：技师点了开始，然后立刻发现选错人了，再点完成。这时会生成一个 2 秒的时间窗，如果 PDF 恰好在这个时间到达，可能误绑。

3 秒阈值来自实测：正常检查最短的（眼压测量）也需要 20 秒以上。3 秒内的一定是误操作。

因为技师可能打错了、打印机卡纸、或者凭条被患者带走。重新生成的要求是"旧凭条从未被使用过"，否则会产生混乱（旧凭条可能还有一张纸质的小票在外面）。

### 6.6 Service 层核心逻辑

```python
"""M12-02 检查执行 —— 核心服务。"""
import logging
from datetime import datetime, timedelta
from decimal import Decimal

from sqlalchemy import select

from app.core.exception import BizException
from app.core.redis_client import redis
from app.integrations.m01_client import EmployeeClient, MdmClient
from app.integrations.m07_client import ExamRequestClient
from app.models.m12_exam import (M12ExamTask, M12ExamWindow, M12ExamTicket,
                                 M12ExamCorrection, M12ExamQueue)
from app.services.m12.no_seq import next_window_no, next_ticket_no

logger = logging.getLogger(__name__)

# 状态常量
TASK_CALLED = "CALLED"
TASK_EXECUTING = "EXECUTING"
TASK_EXECUTED = "EXECUTED"
TASK_DONE = "DONE"
TASK_FAILED = "FAILED"
TASK_CANCELLED = "CANCELLED"
TASK_SKIPPED = "SKIPPED"

# 时间窗容差（秒）
DEFAULT_BEFORE_TOLERANCE = 120
DEFAULT_AFTER_TOLERANCE = 300
MAX_WINDOW_SECONDS = 3600

# 检查时长阈值（秒）
MIN_DURATION_SECONDS = 3
MAX_DURATION_SECONDS = 4 * 3600

# 异常类别
FAIL_CATEGORIES = {
    "PATIENT_ABSENT", "POOR_COOPERATION", "ONE_EYE_ONLY",
    "EQUIPMENT_FAILURE", "POOR_QUALITY", "PATIENT_LEFT",
    "WRONG_ITEM", "PATIENT_GIVE_UP", "OTHER",
}

# 处理方式
HANDLE_MODES = {"RESCHEDULE", "CANCEL_REFUND", "PARTIAL"}

# 单技师同时执行上限
MAX_CONCURRENT_EXEC = 3


class ExecService:
    """检查执行服务。"""

    @staticmethod
    async def start(task_id: int, device_id: int, note: str, user: dict) -> dict:
        """开始检查 —— 记录 exec_started_at，创建时间窗。"""
        db = get_session()

        task = await ExecService._get_task_for_update(db, task_id, user)

        # 1. 状态校验
        if task.status not in (TASK_CALLED, "IN_SERVICE"):
            raise BizException("1202003",
                               "任务状态不允许开始检查，当前：%s" % task.status)

        # 2. 设备独占校验：同一设备不能有两个 EXECUTING
        running = await db.scalar(
            select(M12ExamTask.id).where(
                M12ExamTask.device_id == device_id,
                M12ExamTask.status == TASK_EXECUTING,
                M12ExamTask.id != task_id,
                M12ExamTask.is_deleted.is_(False),
            )
        )
        if running:
            raise BizException("1202004", "该设备已有正在执行的检查")

        # 3. 技师资质校验
        qualified = await EmployeeClient.check_device_qualification(
            user["employee_id"], device_id)
        if not qualified:
            raise BizException("1202019", "您不具备该设备的操作资质")

        # 4. 并发执行校验（一个技师最多 3 台设备并行）
        my_running = await db.scalar(
            select(func.count()).select_from(M12ExamTask).where(
                M12ExamTask.exec_by == user["employee_id"],
                M12ExamTask.status == TASK_EXECUTING,
            )
        )
        if (my_running or 0) >= MAX_CONCURRENT_EXEC:
            raise BizException("1202022",
                               "您已有 %d 个执行中的检查" % my_running)

        # 5. 写入执行开始时刻
        now = datetime.now()
        task.status = TASK_EXECUTING
        task.exec_started_at = now
        task.exec_by = user["employee_id"]
        task.exec_by_name = user.get("employee_name")
        task.exec_device_note = note
        task.device_id = device_id

        # 6. ★ 创建时间窗（本项目核心）
        before_tolerance = await ExecService._get_param(
            db, "M12.WINDOW.BEFORE_TOLERANCE", DEFAULT_BEFORE_TOLERANCE)
        window = M12ExamWindow(
            window_no=await next_window_no(db),
            task_id=task.id,
            task_no=task.task_no,
            request_no=task.request_no,
            patient_id=task.patient_id,
            patient_name=task.patient_name,
            patient_gender=task.patient_gender,
            patient_age=task.patient_age,
            item_code=task.item_code,
            item_name=task.item_name,
            eye_side=task.eye_side,
            device_id=device_id,
            device_name=task.device_name,
            exec_started_at=now,
            exec_finished_at=None,
            window_start=now - timedelta(seconds=before_tolerance),
            window_end=None,
            window_source="MANUAL",
            expected_duration=task.duration_minutes,
            is_closed=False,
            is_deleted=False,
            created_at=now,
        )
        db.add(window)
        await db.flush()

        # 7. 检测窗口重叠
        await ExecService._detect_overlap(db, window)

        await db.commit()

        # 8. 写 Redis 活跃窗口索引（M12-04 快速查询）
        await redis.zadd("m12:window:active",
                         {str(window.id): window.window_start.timestamp()})

        logger.info(
            "开始检查 task_no=%s device=%d window_no=%s window_start=%s operator=%s",
            task.task_no, device_id, window.window_no,
            window.window_start.isoformat(), user.get("employee_name"),
            extra={"module": "M12-02", "action": "EXEC_START",
                   "task_no": task.task_no, "window_no": window.window_no})

        return {
            "task_id": task.id,
            "task_no": task.task_no,
            "status": task.status,
            "exec_started_at": task.exec_started_at,
            "window": {
                "window_id": window.id,
                "window_no": window.window_no,
                "window_start": window.window_start,
                "window_end": None,
                "is_closed": False,
                "window_source": window.window_source,
            },
            "device_id": device_id,
            "device_name": task.device_name,
        }

    @staticmethod
    async def finish(task_id: int, note: str, auto_close: bool,
                     user: dict) -> dict:
        """完成检查 —— 闭合时间窗、生成凭条。"""
        db = get_session()

        task = await ExecService._get_task_for_update(db, task_id, user)

        # 1. 幂等：已完成直接返回
        if task.status in (TASK_EXECUTED, TASK_DONE):
            logger.info("任务已执行，幂等返回 task_no=%s", task.task_no)
            return await ExecService._build_finish_result(db, task)

        # 2. 状态校验
        if task.status != TASK_EXECUTING:
            raise BizException("1202003",
                               "任务状态不允许完成，当前：%s" % task.status)

        # 3. 必须有开始时间
        if not task.exec_started_at:
            raise BizException("1202005", "任务缺少开始时间，无法完成")

        now = datetime.now()
        duration = int((now - task.exec_started_at).total_seconds())

        # 4. 误点检测（时长过短）
        if duration < MIN_DURATION_SECONDS:
            logger.warning("检查时长异常短 task_no=%s duration=%ds",
                           task.task_no, duration)

        # 5. 超长警告（不阻断）
        if duration > MAX_DURATION_SECONDS:
            logger.warning("检查时长异常长 task_no=%s duration=%ds",
                           task.task_no, duration)

        # 6. 写入完成时刻
        task.exec_finished_at = now
        task.status = TASK_EXECUTED
        if note:
            task.exec_device_note = note

        # 7. ★ 闭合时间窗
        window = None
        if auto_close:
            window = await db.scalar(
                select(M12ExamWindow).where(
                    M12ExamWindow.task_id == task.id,
                    M12ExamWindow.is_deleted.is_(False),
                ).with_for_update()
            )
            if window:
                after_tolerance = await ExecService._get_param(
                    db, "M12.WINDOW.AFTER_TOLERANCE", DEFAULT_AFTER_TOLERANCE)
                window.exec_finished_at = now
                window.window_end = now + timedelta(seconds=after_tolerance)
                window.is_closed = True

                # 窗口超长则截断
                total = int((window.window_end - window.window_start).total_seconds())
                if total > MAX_WINDOW_SECONDS:
                    window.window_start = now - timedelta(
                        seconds=MAX_WINDOW_SECONDS - after_tolerance)
                    window.remark = "窗口超长已截断，技师可能忘记点完成"
                    logger.warning("时间窗超长截断 window_no=%s 原始时长=%ds",
                                   window.window_no, total)

                # 重检重叠
                await ExecService._detect_overlap(db, window)

        # 8. 生成/获取凭条
        ticket = await TicketService.ensure_ticket(db, task)

        # 9. 释放设备占用（Redis）
        await redis.delete("m12:device:%d:executing" % task.device_id)

        await db.commit()

        # 10. 回写 M12-01
        from app.tasks.m12_tasks import writeback_executed_task
        writeback_executed_task.delay(task.id)

        # 11. 取下一个队列患者（供前端提示）
        next_item = await ExecService._peek_next(task.device_id)

        logger.info(
            "完成检查 task_no=%s duration=%ds window_no=%s operator=%s",
            task.task_no, duration,
            window.window_no if window else None,
            user.get("employee_name"),
            extra={"module": "M12-02", "action": "EXEC_FINISH",
                   "task_no": task.task_no, "duration": duration})

        result = await ExecService._build_finish_result(db, task)
        result["next_queue"] = next_item
        result["ticket"] = {
            "ticket_id": ticket.id,
            "ticket_no": ticket.ticket_no,
            "qr_content": ticket.qr_content,
            "print_count": ticket.print_count,
            "is_used": ticket.is_used,
        }
        return result

    @staticmethod
    async def fail(task_id: int, body, user: dict) -> dict:
        """登记执行异常。"""
        db = get_session()
        task = await ExecService._get_task_for_update(db, task_id, user)

        # 1. 参数校验
        if body.fail_category not in FAIL_CATEGORIES:
            raise BizException("1202007", "异常类别无效：%s" % body.fail_category)
        if body.handle_mode not in HANDLE_MODES:
            raise BizException("1202008", "处理方式无效：%s" % body.handle_mode)
        if len(body.reason.strip()) < 10:
            raise BizException("1202009", "详细说明不足 10 字")
        if body.handle_mode == "PARTIAL" and not body.completed_eyes:
            raise BizException("1202010", "仅完成单眼时须指定已完成眼别")
        if task.status not in (TASK_CALLED, "IN_SERVICE", TASK_EXECUTING):
            raise BizException("1202003",
                               "任务状态不允许登记异常，当前：%s" % task.status)

        now = datetime.now()

        # 2. 按处理方式执行
        if body.handle_mode == "CANCEL_REFUND":
            task.status = TASK_CANCELLED
            task.cancel_reason = body.reason
            task.cancelled_at = now
            task.cancelled_by = user["employee_id"]
            task.cancelled_by_name = user.get("employee_name")
            task.refund_status = "PENDING"
            refund_required = True
        elif body.handle_mode == "PARTIAL":
            task.status = TASK_EXECUTED
            task.exec_finished_at = now
            task.exec_device_note = "仅完成：%s" % ",".join(body.completed_eyes)
            task.fail_reason = body.reason
            refund_required = False
        else:
            task.status = TASK_FAILED
            task.fail_reason = body.reason
            refund_required = False

        # 3. 时间窗处理：失败则关闭并标记无效
        window = await db.scalar(
            select(M12ExamWindow).where(
                M12ExamWindow.task_id == task.id,
                M12ExamWindow.is_deleted.is_(False),
            ).with_for_update()
        )
        if window:
            if not window.is_closed:
                window.exec_finished_at = now
                window.window_end = now + timedelta(seconds=60)
                window.is_closed = True
            if body.handle_mode in ("RESCHEDULE", "CANCEL_REFUND"):
                window.is_valid = False
                window.invalid_reason = "检查失败：%s" % body.fail_category

        # 4. 设备报修
        repair_no = None
        if body.need_equipment_repair and body.fail_category == "EQUIPMENT_FAILURE":
            repair_no = await ExecService._create_repair_ticket(db, task, user)

        await db.commit()

        # 5. 退费通知（异步）
        if refund_required:
            from app.tasks.m12_tasks import notify_refund_task
            notify_refund_task.delay(task.id, task.settlement_item_id, body.reason)

        logger.info(
            "登记执行异常 task_no=%s category=%s mode=%s operator=%s",
            task.task_no, body.fail_category, body.handle_mode,
            user.get("employee_name"),
            extra={"module": "M12-02", "action": "EXEC_FAIL",
                   "task_no": task.task_no, "category": body.fail_category})

        return {
            "task_id": task.id,
            "task_no": task.task_no,
            "status": task.status,
            "fail_category": body.fail_category,
            "handle_mode": body.handle_mode,
            "window": {
                "window_id": window.id if window else None,
                "window_end": window.window_end if window else None,
                "is_valid": window.is_valid if window else None,
                "invalid_reason": window.invalid_reason if window else None,
            } if window else None,
            "refund_required": refund_required,
            "repair_ticket_created": repair_no is not None,

    @staticmethod
    async def _detect_overlap(db, window) -> None:
        """检测时间窗重叠，重叠则双方标记 is_ambiguous。"""
        if not window.window_end:
            # 开放窗口：用"当前时间 + 滞后容差"参与比较
            effective_end = datetime.now() + timedelta(
                seconds=DEFAULT_AFTER_TOLERANCE)
        else:
            effective_end = window.window_end

        stmt = select(M12ExamWindow).where(
            M12ExamWindow.device_id == window.device_id,
            M12ExamWindow.id != window.id,
            M12ExamWindow.is_deleted.is_(False),
            M12ExamWindow.window_start < effective_end,
        )
        others = list((await db.scalars(stmt)).all())

        overlapped = []
        for o in others:
            o_end = o.window_end or (datetime.now() + timedelta(
                seconds=DEFAULT_AFTER_TOLERANCE))
            if o_end > window.window_start:
                overlapped.append(o)

        if overlapped:
            window.is_ambiguous = True
            for o in overlapped:
                o.is_ambiguous = True
            logger.warning(
                "时间窗重叠 window_no=%s 与 %d 个窗口重叠",
                window.window_no, len(overlapped),
                extra={"module": "M12-02", "action": "WINDOW_OVERLAP",
                       "window_no": window.window_no})
```

**时间窗的容差为什么必须从参数读而不是硬编码？**

因为不同设备的最优容差不同：

| 设备 | 建议提前容差 | 建议延后容差 | 理由 |
|---|---|---|---|
| 眼压测量 | 60 秒 | 120 秒 | 极快，容差大反而误绑 |
| OCT | 120 秒 | 300 秒 | 需要对准注视点 |
| 视野 | 180 秒 | 600 秒 | 单眼 5~8 分钟，慢 |
| FFA | 300 秒 | 900 秒 | 需要注射+等待+摄影 |
| UBM | 180 秒 | 300 秒 | 表面麻醉+耦合剂 |

所以参数设计成 `GLOBAL` 默认值 + `DEVICE` 级覆盖（`scope` / `scope_id`）。读取时优先 `DEVICE` 级，其次 `GLOBAL`。

### 6.7 时间窗与 OCR 绑定的协作模型

这是跨模块的关键协作，虽然绑定逻辑在 M12-04，但数据来源在 M12-02，必须说清楚。

```
M12-03 收到一份 PDF：OCT_20261022_091545.pdf (创建时间 09:15:45)
    │
    ▼
M12-04 发起绑定：走了三条路径
    │
    ├─【路径一】投递凭条匹配（最高优先级）
    │    文件名能否解析出 DT 开头？→ 否
    │    → 转路径二
    │
    ├─【路径二】时间窗匹配
    │    调 M12-02 API-25：查询 09:00~09:30 的活跃窗口
    │    → 返回 2 个窗口：
    │        窗口A：张伟 男45 OCT黄斑 OD  09:00:05~09:20:42
    │        窗口B：陈强 男45 OCT黄斑 OU  09:14:10~09:31:30
    │    │
    │    ├─ 09:15:45 落在窗口A内 ✅，也落在窗口B内 ✅
    │    │
    │    ├─ OCR 识别：姓名"张伟" 男 45岁
    │    │    → 匹配窗口A 的 patient_name/patient_gender/patient_age
    │    │    → 不匹配窗口B（陈强）
    │    │
    │    └─ 结果：唯一命中窗口A → 自动绑定张伟 ✅
    │
    └─【路径三】绑定失败 → 进待确认队列
```

**M12-02 在这个过程中的三个职责：**

1. **保证窗口存在**：`finish` 时必须创建/闭合窗口，不能漏
2. **提供窗口查询接口**：API-25 必须快（P95 ≤ 50ms），因为每份 PDF 都要调
3. **保证窗口正确性**：重叠检测、截断、失效标记必须准确

**如果窗口数据质量差会怎样？**

| 数据问题 | 后果 |
|---|---|
| 窗口缺失 | 该患者所有 PDF 无法自动绑定，全部进待确认 |
| 窗口过窄（技师点晚了） | PDF 时间落在窗口外，绑定失败 |
| 窗口过宽（技师忘点完成） | 多个窗口重叠，全部 `is_ambiguous`，绑定失败 |
| 窗口时间错误（系统时间不对） | 全部绑定失败 |

所以在第 12 章验收标准里，"时间窗完整率 ≥ 99%" 是最硬的指标。

### 7.1 Redis 缓存

| Key 模式 | 类型 | TTL | 说明 |
|---|---|---|---|
| `m12:device:{device_id}:executing` | String | 4h | 该设备正在执行的任务 ID（防并发） |
| `m12:device:{device_id}:queue` | ZSet | 300s | 设备候检队列缓存（score = 优先级时间戳） |
| `m12:window:active` | ZSet | — | **活跃时间窗索引**（score = window_start 时间戳），M12-04 快速查询 |
| `m12:window:{window_id}` | Hash | 3600s | 单个窗口缓存 |
| `m12:ticket:seq:{device_no}:{yyyymmdd}` | String | 172800s | 凭条序列 |
| `m12:repair:seq:{yyyymmdd}` | String | 172800s | 报修单序列 |
| `m12:exec:param:{code}` | String | 600s | 参数缓存 |
| `m12:exec:staff:{staff_id}:stats:{date}` | String | 1800s | 技师日统计缓存 |
| `m12:exec:lock:{task_id}` | String | 30s | 单任务操作锁（防重复点击） |

**容量估算：**

- 活跃窗口：日均 420 个，保留最近 2 天 → 约 840 条，每条约 100B（只存 id + 时间戳）→ **约 84KB**
- 设备执行状态：6 台设备 → **约 1KB**
- 队列缓存：6 台 × 50 人 → 300 条 → **约 30KB**
- 凭条序列：200 条 → **约 20KB**
- **合计约 140KB**，极小

| R-08 | 检查时长 > 4 小时记录告警但允许完成 | — |

**关于 R-04 为什么是 3 台：**

眼科检查里，眼压、视力、验光这类项目单次只要 20~60 秒。技师实际可以同时照看 3 台，走一圈回来就都好了。设成 1 台会严重浪费人力。设成 5 台则无法保证质量（患者会等很久）。3 台是实测的合理值。

### 8.2 时间窗规则

| 编号 | 规则 | 说明 |
|---|---|---|
| R-09 | 开始检查时必须创建时间窗 | 不能跳过 |
| R-10 | 时间窗 `window_start = exec_started_at - BEFORE_TOLERANCE` | 默认 120 秒 |
| R-11 | 时间窗 `window_end = exec_finished_at + AFTER_TOLERANCE` | 默认 300 秒 |
| R-12 | 窗口长度 > 3600 秒时截断，`is_truncated = TRUE` | 防技师忘点完成 |

| R-15 | 检查失败时窗口 `is_valid = FALSE` | 不参与绑定 |
| R-16 | 已匹配文件的窗口不可重算 | `"1202016"` |

**R-12 的截断为什么是"往前截"而不是"往后截"？**

因为技师忘记点完成时，真实的完成时间一定早于系统记录的完成时间（补录时才知道）。所以真实窗口是 `[开始-容差, 真实完成+容差]`，如果截断到 3600 秒，应该保留靠近开始的那部分（因为结束时间是错的，越靠后越不可信）。

### 9.4 安全措施

| 措施 | 说明 |
|---|---|
| 操作锁 | Redis `m12:exec:lock:{task_id}` TTL 30s，防重复点击 |
| 补录留痕 | 所有补录写审计日志，含原因与说明 |
| 异常留痕 | 所有失败/重做写审计日志 |
| 凭条防篡改 | 凭条号与任务号绑定，数据库约束 |
| 时间不可回改 | `exec_started_at` / `exec_finished_at` 一旦写入，只能通过补录新增记录，不能 UPDATE 原值 |
| 设备资质校验 | 技师必须有资质才能操作设备 |
| 敏感操作二次确认 | 作废退费、强制关闭窗口 |

**"时间不可回改"如何实现？**

在数据库层面加触发器：

```sql
CREATE OR REPLACE FUNCTION fn_m12_exec_time_immutable()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.status IN ('EXECUTED','DONE')
     AND (NEW.exec_started_at IS DISTINCT FROM OLD.exec_started_at
          OR NEW.exec_finished_at IS DISTINCT FROM OLD.exec_finished_at) THEN
    -- 允许补录专用通道：session 变量标记
    IF current_setting('m12.allow_time_correction', TRUE) = 'on' THEN
      RETURN NEW;
    END IF;
    RAISE EXCEPTION 'M12: 执行时间不可直接修改，请使用补录功能';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

补录时先用 `SET LOCAL m12.allow_time_correction = 'on'` 打开通道，写入后自动恢复（LOCAL 只对当前事务有效）。

**U-05 降级放行是否安全？**

设备资质校验降级放行（记警告）而不阻断，理由：

1. 资质数据在 M01-02，如果 M01-02 挂了，整个 HIS 都受影响，不只是检查科
2. 阻断会导致技师完全无法工作，损失大于收益
3. 降级时记录警告日志，事后可审计

但如果 M01-02 恢复了，降级记录会进入报表，由科主任复核。

**`m07.encounter.completed` 的处理为什么重要？**

因为患者就诊结束了，但技师可能还开着执行中的任务（忘记点完成）。如果不处理，这个任务会一直挂着，时间窗一直开放，导致后续 PDF 全部误判。

处理方式：就诊结束时，若该患者有 `EXECUTING` 任务，系统自动：
1. 若有 `exec_started_at` 但无完成时间，按"开始 + 预计时长"闭合窗口
2. 标记 `is_auto_closed = TRUE`
3. 通知技师

### 12.1 功能验收
