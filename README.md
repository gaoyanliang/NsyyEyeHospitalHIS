## 1. 项目概览

### 1.1 项目定位

二级眼科专科医院（**无医保、自费为主，预留商保/医保接口**）的 HIS 系统详细设计。

| 项目 | 说明 |
|---|---|
| **医院类型** | 二级眼科专科医院 |
| **支付模式** | 默认自费，支持商保、第三方支付，医保字段预留 |
| **业务特色** | 门诊为主、住院与日间手术为辅、**视光与屈光为专科特色** |
| **终端形态** | PC 工作端 + 移动端 + 患者端（公众号 / 小程序 / 自助机） |
| **设计目标** | 支撑门诊、住院、日间手术、视光销售、屈光手术、检查检验、药房药库、收费结算、移动办公 |

### 1.2 文档库定位

**本仓库不是代码仓库，而是"可直接进入开发的详细设计文档库"。**

每份文档均达到以下深度：

| 维度 | 深度 |
|---|---|
| **业务模型** | 状态机、分类体系、计算规则、边界判定 |
| **页面原型** | ASCII 线框图 + 字段表 + 交互说明 + 校验规则 |
| **接口契约** | 请求/响应 JSON 示例 + 错误码 + FastAPI 路由 + Service 逻辑 |
| **数据结构** | 字段表 + 索引 + 约束 + SQLAlchemy 2.0 模型 + Pydantic Schema |
| **验收标准** | AC/PF/DA/SC 四类编号化验收项 |

### 1.3 核心设计原则

| 原则 | 落地方式 |
|---|---|
| **统一主数据** | 所有模块通过 M01 MDM 获取科室、职工、药品、耗材、收费、权限等主数据 |
| **统一权限** | M02 提供三维权限（角色/岗位/用户组）+ 数据权限隔离 + 全量审计 |
| **统一集成** | M21 集成平台承担 ESB、EMPI、HL7、DICOM、LIS、PACS、支付、消息 |
| **模块可配置** | 二级医院可按需启用/停用模块 |
| **移动端优先** | 关键业务支持手机、平板操作，响应 ≤2 秒 |

#### 5.6.4 六条金额铁律

| 铁律 | 做法 | 违反后果 |
|---|---|---|
| **禁用浮点** | 全链路 `Decimal` / `NUMERIC` | 分位误差累积，退费对不上 |
| **行级先舍入再累加** | `ROUND(unit_price × qty, 2)` 后求和 | 明细多时差几毛，退费按行退永远差 |
| **价格快照只增不改** | 触发器禁止 `UPDATE`/`DELETE` | 查不到当时价格，审计无法举证 |
| **前端传的金额一律忽略** | 后端重算，前端值仅作展示 | 篡改请求即可少付 |
| **优惠降级不阻断收费** | 超时按原价算 + 标记 `discount_degraded` | 优惠服务挂了全院停摆 |
| **支付成功后回写失败不回滚支付** | 写补偿队列，指数退避重试 | 钱到了系统说没到，患者投诉 |

#### 5.6.5 状态不可逆的三处实现

| 对象 | 不可逆状态 | 实现方式 |
|---|---|---|
| 支付单 | `SUCCESS` | 服务层拦截 + `uk_m16_payment_txn`（交易号全局唯一） |
| 发票 | `RED_FLUSHED` | 红票自关联蓝票，`uk_m16_invoice_no` 全局唯一 |
| 日结 | `FROZEN` | 触发器禁改 + 拒绝新资金事务（报 "1609015"） |

| 约束 | 说明 |
|---|---|
| **眼别倍数** | `charge_by_eye=TRUE` 时 `OU` 自动 ×2，`bill_quantity = quantity × eye_multiplier` |
| **预交金池与费用账分离** | 预交金只增不减（除退还），费用账只增不减（除冲销），出院结算时才相遇 |
| **视光定金** | 定制商品定金 ≥30%，单笔 ≥5,000 定金 ≥50%，现货可为 0 |

#### 5.7.2 库存唯一真相模型（M14 最重要的设计）

10 个子模块中 **6 个会改变库存数量**。若各自动 `UPDATE`，必然出现「出库扣了但入库没加」「两个人同时扣同一批次、一个覆盖另一个」。

**解法：任何模块改库存都必须走同一个入口。**

```
任何模块想让数量变化
        │
        ▼
POST /internal/v1/m14/stock/apply
        ├── ① 校验幂等键（防重复提交）
        ├── ② 校验方向与流水类型匹配
        ├── ③ 条件原子更新 WHERE qty >= n AND version = v
        ├── ④ 写 m14_stock_txn（只增，触发器禁改删）
        └── ⑤ 返回 before/after
```

**为什么不用 `SELECT ... FOR UPDATE`？**

门诊高峰时热门滴眼液一天 300 张处方，5 个窗口用行锁会串行排队，单笔从 30ms 涨到 150ms。条件更新只在冲突时失败重试，无冲突时零等待。同理 FEFO 分配用 `FOR UPDATE SKIP LOCKED`——后到的窗口跳到下一批次，**并发下 FEFO 退化为近似，但绝不会发出过期药**。

#### 5.7.5 特殊药品双锁模型

```
┌────────────────────────────────────────────┐
│  麻精专柜 CAB-NR-01                         │
│  电子锁 A（药师甲持钥）+ 电子锁 B（药师乙持钥）│
│    → 任一持钥人无法单独开启                  │
└────────────────────────────────────────────┘
系统强制（数据库约束）：
  ① operator_id ≠ checker_id
  ② 两人都有专管资质
  ③ 两次签字时间差 ≤ 15 分钟
  ④ 必须同一次登录会话内完成
  ⑤ 双方勾选「实物核对已完成」
```

**为什么限制 15 分钟？** 最常见违规做法是「一人操作、另一人下班前补签」。限制时间差 + 要求同会话 + 超时标 `is_late_check` 进季度检查清单，让这种做法既麻烦又留痕。

**空安瓿守恒等式：** `发放数量 = 回收空瓿数量 + 在用数量 + 销毁数量`

**失窃时限：** T0 发现 → +2h 查明 → +4h 报药房主任 → +8h 报医务科 → **+24h 硬性上报药监 + 公安**（时限由数据库 `found_at + INTERVAL '24 hours'` 计算，防篡改）。

#### 5.7.6 退药与退费边界（M14 ↔ M16 最关键的接口）

```
M16-08 退费单创建
    ├──► GET  /internal/v1/m14/dispense/returnable/{rx_no}   查可退明细
    ├──► 执行退费：退款 + 回写 M07 + 通知 M14
    │    POST /internal/v1/m14/dispense/on-refunded
    │         └──► M14-07 生成退药任务，药师判定后入原批次
    └──► 若药品已开封 → M14 判定不可退 → 拒退
```

**分界线：M16 管钱，M14 管药。退费必须先确认药品实物状态**——因为开封的滴眼液不能退。

| 铁律 | 说明 |
|---|---|

#### 5.7.7 眼科药房七特殊性

| 特殊性 | 对设计的影响 |
|---|---|
| **滴眼液是主力剂型** | 拆零按「支」不按毫升；拆零批次批号 = 原批号 + `-S` |

#### 5.8.1 为什么 M12 的存在前提是「设备接不进来」

本院的 8 类检查设备（OCT、眼底照相、视野、角膜地形图、眼压、眼部 B 超、UBM、生物测量）**全部自带工作站、全部只能导出 PDF、全部未购 DICOM 授权**。因此 M12 必须自己造一条「数据通路」：

```
技师在设备工作站出报告 → 手工导出 PDF 到共享文件夹 → M12-03 采集
  → M12-04 OCR 解析 + 绑定 → M12-05 审核 → M07-04 医生可见
```

**若设备能接 DICOM，M12 只需 M12-01/02/05 三个子模块，M12-03/04/06 整个不需要。**

#### 5.8.2 三条硬约束与四个救命机制

| 硬约束 | 后果 |
|---|---|
| 报告只能是 PDF 走共享文件夹 | 无结构化数据，必须 OCR |
| PDF 由技师手工导出、文件名随机 | 无法从文件名提取信息 |
| PDF 含姓名/性别/年龄，但**无本院患者 ID** | 无法直接绑定患者 |

**四个机制（缺一不可）：**

| 机制 | 说明 | 归属 |
|---|---|---|
| **时间窗（D2 决策）** | 技师点「开始/完成」时记录区间，PDF 文件 mtime 落入区间为候选 | M12-02 产出、M12-04 消费 |
| **投递凭条（可选）** | 技师导出时把文件名改成凭条号 `DT`+13 位，100% 精确绑定 | M12-02 |
| **双通道 OCR** | 通道 A（姓名/性别/年龄）用于绑定；通道 B（项目/数值/区间）用于填充 | M12-04 |
| **待确认队列** | 多命中/零命中转人工，护士凭就诊号+医师+诊断快速判定 | M12-04 |

#### 5.8.3 错绑防护四道闸门（M12 最重要的安全设计）

**错绑率必须是 0——不是「尽量低」，而是架构上不允许。**

| 闸门 | 实现 |
|---|---|
| ① 只唯一命中才自动绑定 | 候选 ≥2 一律转人工 |
| ② `is_ambiguous=TRUE` 的时间窗不参与自动绑定 | M12-02 窗口重叠时双方置标记 |
| ③ 一个任务只能绑一份文件 | DB 唯一索引 `uk_m12_parse_task_bound` 兜底 |
| ④ 双通道姓名交叉验证 | 通道 A 姓名 ≠ 报告抬头姓名 → 整条标红 |

**为什么自动绑定率目标只有 96% 而不是 99%：** 剩下 4% 是客观上无法自动判定的（同名同姓同年龄同时段 0.3%、技师忘点开始/完成 1~2%、OCR 认不出姓名 0.5%、设备时钟偏差 0.5%）。追求 99% 的唯一办法是放宽匹配条件，代价就是错绑。

#### 5.8.4 四条 OCR 与置信度铁律

| 铁律 | 说明 |
|---|---|
| **文本层优先** | pypdf 首页字符 ≥20 判数字 PDF，直接取字符；本项目约 **85%** 是数字 PDF |
| **字段级置信度取最小值** | `2.38`→`2.3B` 时其他 3 字符都对（平均 0.97）但字段完全不可用 |

#### 5.9.2 标本归并模型（M13 独有的物理链路）

**系统的核心价值是把多个检验任务合理归并成尽可能少的采集管：**

```
WBC / HGB / PLT   → 紫帽 EDTA 一管（3 项合一）
ALT / AST / K     → 黄帽促凝一管（3 项合一）
PT / APTT         → 蓝帽枸橼酸一管（凝血必须独立）
```

**七条归并规则：** R-01 同标本类型+容器可归并 / R-02 合计用量不超容量 / R-03 超容量拆管 / R-04 冷藏与常温不归并 / R-05 立即送检单独成管 / R-06 眼科特殊标本每项单管 / **R-07 凝血必须独立一管（抗凝剂 9:1 比例）**。

**七类「每项单管」的标本：** `PLASMA` 血浆、`TEAR` 泪液、`AQUEOUS` 房水、`VITREOUS` 玻璃体、`CORNEA_SCRAPING` 角膜刮片、`CONJUNCTIVAL_SWAB` 结膜拭子、`STOOL` 粪便。

**为什么采血量要算余量：** 血清促凝管标称 5 mL，但离心后血清只有约 40%。20 个生化项目需 4 mL 血清 → 需 10 mL 全血 → 需 2 管。

#### 5.9.3 参考区间版本模型（M13-05 的核心）

**区间不修改，只新增版本：**

```
血钾 K
  V1  3.5~5.3   生效 2024-01-01 ~ 2026-11-14   仪器 AU5800
  V2  3.4~5.3   生效 2026-11-15 ~ NULL         仪器 AU6800
```

**为什么不能修改：** 同一份报告昨天判正常、今天判异常，医生会质疑系统。追溯要求「报告的判定依据是报告出具时的有效标准」。

**保证「任意时刻恰好一条生效」的实现：**

```sql
ALTER TABLE m13_ref_range
    ADD CONSTRAINT ex_m13_range_no_overlap
    EXCLUDE USING gist (
        lab_code WITH =,
        COALESCE(gender, '') WITH =,
        COALESCE(age_min, -1) WITH =,
        COALESCE(age_max, 999) WITH =,
        COALESCE(physiological_state, '') WITH =,
        COALESCE(device_code, '') WITH =,
        daterange(valid_from, valid_to, '[]') WITH &&
    ) WHERE (is_deleted = FALSE AND approval_status IN ('APPROVED', 'PENDING'));
```

**必须 `COALESCE` 每个可空维度：** PostgreSQL 认为 `NULL` 与 `NULL` 不相等，两条 `gender IS NULL` 的通用区间可都覆盖同一时段而约束不报错——**这正是「忘了改 V1 的 valid_to」的典型场景**。

#### 5.9.4 危急阈值的三层结构与 100% 覆盖铁律

```
         危急低      参考低       参考高      危急高
           │           │            │           │
  ─────────●───────────●────────────●───────────●─────────►
         <2.5        3.5          5.3         >6.5    血钾
           │←─危急──►│←─异常但不危急─►│          │←─危急──►│
```

| 层级 | 触发 | 处理 |
|---|---|---|
| 参考区间内 | 不标记 | — |
| 参考区间外、危急阈值内 | `HIGH`/`LOW` | 标记，医生可下午处理 |
| 超过危急阈值 | `CRITICAL` | 15 分钟确认 + 2 小时处置强制闭环 |

**`M13.LABITEM.CRITICAL_TARGET = 1.0` 是唯一一个只读参数。** 它不是「配置」，是「承诺」——危急阈值覆盖率必须 100%。缺一个阈值意味着该项目出现危急值时系统不会报警，而临床会默认「系统会报警」而放松警惕，**比没有系统更危险**。

#### 5.9.5 微生物多批次与报告组装

**普通检验：一份标本 → 一份报告。微生物：一份标本 → 多个批次 → 组装成一份报告。**

```
玻璃体液培养
  D1 10:30  PRELIMINARY  涂片初报：革兰阳性球菌   → 推送（当晚调整抗生素）
  D2 09:00  INTERIM      中报：金黄色葡萄球菌      → 推送
  D4 15:00  FINAL        终报：+ 药敏              → 推送
```

**M07 侧表现为「同一份报告被更新版本」**，锚点是 `report_key`（= `specimen_no`），版本号只增。

**眼内液最短培养 5 天：** 标本量极少、病原载量低，眼内炎玻璃体液培养阳性率仅 40~60%，3 天阴性不能排除。

#### 5.9.6 外送检验的三个关键设计

#### 5.10.3 三条存在前提

1. **业务主体独立**——`m06_day_surgery` 贯穿十个环节，把它挂在门诊挂号下或住院登记下都无法承载「准入判定 + 术前闭环 + 四方核对 + 离院评估 + 日间结算」这五件事；
2. **资源模型独立**——六类资源必须同时到位（手术间、台次、主刀、麻醉医生、器械护士、日间床位），M04 的号源与 M05 的床位都只覆盖其中一项；
3. **法规留痕独立**——《医疗质量安全核心制度要点》第十五条手术安全核查制度、《医疗机构手术分级管理办法》、《医疗机构病历管理规定》，三类证据必须只增不改、可独立检索打印、可作为法律证据导出。

#### 5.10.4 四方核对：本院比三方多一位患者

**标准三方核对**（手术医生 + 麻醉医生 + 巡回护士）是法规最低要求。本院加了**患者本人**：

> 眼科术眼左右极易混淆，而患者是唯一能在术前最后确认「医生说做左眼」的人。

**关键项要求输入验证值而非点选：**

| 核对项 | 验证方式 | 为什么不能点选 |
|---|---|---|
| 患者身份 | 扫描腕带条码 | 点选可在不确认情况下盲选 |
| 手术术式 | 手工输入前 4 字 | 打字必须看单子 |
| 手术眼别 | 患者自述后选择 | 必须问患者 |
| 禁食状态 | 输入最后进食时间 | 必须回忆具体时间 |

**成本每台多 1 分钟（日均 55 台 = 55 分钟护士工时），收益是把「心理上的核对」变成「物理上的校验」。**

**只在有客观期望值的项上强制校验**——V-13 随身物品、V-14 代理人无正确答案，强制输入只会产生垃圾数据。

#### 5.10.5 离院判定：硬门槛不可代偿

**Aldrete（能否离开复苏室）与 PADSS（能否离开医院）不是一回事。** 混用会导致「复苏室出来就让人回家」的差错。

| 判定层 | 内容 | 是否可代偿 |
|---|---|---|
| **① 硬门槛** | 眼压必须在 5~25 mmHg；视力下降 ≤2 行；前房非浅非积血；出血已止 | **不可代偿**——任一不满足直接不通过 |
| ② PADSS 评分 | 标准 6 项 12 分 + 眼科 4 项 8 分 = 20 分，≥9 分且无 0 分项 | 可代偿（某项几分其他项可补） |
| ③ 留观时长 | 白内障 120 / 玻切 240 / 注药 60 分钟 | 硬性（不是加分项） |
| ④ 麻醉间隔 | 全麻距末次给药 ≥120 分钟 | 硬性 |
| ⑤ 陪护条件 | 有陪护人且能报出电话 | 硬性 |

**为什么硬门槛必须独立于评分——真实推演：**

```
白内障术后 90 分钟
  PADSS 六项：活动 2 + 呼吸 2 + 循环 2 + 意识 2 + 氧合 2 + 疼痛 2 = 12/12
  眼科四项：  视力 2 + 前房 2 + 敷料 2 + 出血 2 = 8/8
  眼压：      0 分（实测 38 mmHg）
  ─────────────────────────────────
  按总分：18/20 → 通过 → 患者回家 → 当晚急性高眼压 → 视神经损伤
  按两层：眼压 38 不在 5~25 → 不通过 → 继续留观 + 降眼压治疗
```

**DB 层最后一道闸门**：`m06_discharge` 上的 `ck_m06_dis_dischargeable` 约束要求 `conclusion='DISCHARGEABLE'` 时八个硬门槛键必须全为 `TRUE` 且 `zero_items` 为空——即便 Python 判定逻辑有 bug，数据库也拒绝写入「不满足硬门槛却标可离院」。

#### 5.10.6 结算两模式与「先退货再结算」

| 模式 | 判定 | 适用 | 流程 |
|---|---|---|---|
| **方式 A 预交金** | `md_operation.need_deposit=TRUE`，或预估费用 ≥ 3,000 元 | 玻切、多焦点晶体等大额 | 术前交预交金 → 术后多退少补 |
| **方式 B 后付** | 其余 | 注药等小额 | 直接术后结算 |

**阈值 3,000 元的依据**：本院日间手术费用中位数约 2,800 元，超过 3,000 的占 42%——这部分患者术前筹备资金的时间成本高于预交金管理成本。

**术后未用材料必须先退货再结算。** 若先结算再退，会产生「已收又退」的额外流程（M16-08 退费单 + 审批 + 银行退款），而退回材料本质是「这笔钱本来就不该收」。

**退回率目标 ≥90%（现状 55%）**：日均 55 台 × 平均未用材料 180 元 → 一年患者多付约 **360 万元**，这是多收费，也是患者投诉的主要来源。

#### 5.10.7 六类「没做成」必须分开统计

日均申请 60 台、实际做 45 台，剩下 15 台去哪了？**每一类归属不同的子模块，管理者才能对症下药：**

|---|---|---|

**三条存在前提：**

1. **术中记录是两个独立法定文书**——《病历书写基本规范》第十八条「麻醉记录单应另立单页」、第十九条「手术记录术后 24 小时内完成」。合并则主刀能改麻醉记录、麻醉医生能改手术记录，是法规上的致命缺陷。

#### 5.11.3 器械清点：四次、双人、纱布独立

《手术室护理实践指南》要求术前/关腔前/关腔后/缝合后**四次**清点，每次双人签名。

| 次 | 时机 | 不可替代性 |
|---|---|---|
| ① 术前 | 开台前 | 建立基准——器械卡与实物不符，术前发现可换包，术中才发现无法判定是术前少还是术中丢 |
| ② 关腔前 | 缝合体腔前 | **唯一拦截时机**，此刻发现还能取出 |
| ③ 关腔后 | 体腔关闭、皮肤缝合前 | 覆盖关闭过程新上台器械 |
| ④ 缝合后 | 皮肤缝合后 | 覆盖缝合过程，最终确认 |

**纱布/棉片/缝针必须单独计数、单独结论。** 国内手术遗留物事件中**纱布占 60% 以上**。若与器械混在一张清单统计「42→42 相符」，一旦数量错位（器械多 1 件、纱布少 1 块）总数仍相符，**掩盖纱布遗留**。

**不符时 `MISMATCH` 是独立状态而非布尔字段：**

```
二次查找（≤10 分钟，七项检查）
   ↓ 未找到
X 光复核 ← 不可跳过
   ↓
不良事件上报（2h 报医务科 / 24h 书面 / 重大报卫健）
```

> **「二次查找未找到」不等于「不在体内」**——器械可能滑入组织间隙、藏在血凝块后、被组织包裹。只有影像学才能排除。跳过 X 光则事后无法举证已尽责。

#### 5.12.2 为什么与 M14 药品平行而不合并

| 维度 | M14 药品 | M15 耗材 |
|---|---|---|
| 监管体系 | 《药品管理法》+ GSP | 《医疗器械监督管理条例》+《医疗器械唯一标识系统规则》 |
| 编码体系 | 本位码 + 批号 | **UDI-DI + 序列号（一物一码）** |
| 效期维度 | 有效期 | **有效期 + 灭菌有效期** |
| 追溯方向 | 药品 → 患者（单向） | **患者 ↔ 植入物（双向）** |
| 成本法 | 移动加权平均 | **批次实际成本** |

**关键差异一：灭菌双效期。** 一次性无菌手术包厂商有效期 3 年，但灭菌有效期只有 6 个月。以厂商效期为准会出现「灭菌已失效但系统显示有效」→ 术后感染。

```
effective_expiry_date = LEAST(expiry_date, COALESCE(sterile_expiry_date, expiry_date))
```

所有出库、分配、消耗校验必须用 `effective_expiry_date`。

**关键差异二：一物一码。** 人工晶体单价 800~15,000 元，全院年用量约 4,700 片，同品牌同型号按球镜度数 −10.00D~+40.00D 步长 0.25/0.50D 细分，加 Toric 柱镜可衍生数百 SKU。**每一片必须独立序列号追溯到患者**——《医疗器械监督管理条例》强制要求。

**成本法差异：** 高值植入物单价 3,000~15,000 元，移动到加权平均会稀释批次真实成本，导致「这片晶体成本多少」永远说不清。

#### 5.12.3 数量三要素：锁定与在库必须分离

```sql
qty_available = GENERATED ALWAYS AS (qty_on_hand - qty_locked) STORED
```

**为什么不能只有 `qty_on_hand`：** 手术前一晚备台 50 项，物理上还在二级库，但**不能再被另一台手术领用**。若只记在库量，两台手术同时备台时后一台会分配走前一台已锁定的晶体。

**生成列而非应用层计算：** 三数量恒等式由数据库强制，应用层没有机会算错。

#### 5.12.4 出库 ≠ 消耗（M06-06 核心 KPI 的根基）

| 动作 | 触发时点 | 责任角色 | 库存变化 | 是否计费 |
|---|---|---|---|---|
| 出库 | 手术前一晚备台 | 库管员 | 一级库 → 二级库 | 否 |
| 消耗 | 术中实际使用 | 器械护士 | 二级库 → 已用 | **是（触发 M16-01）** |
| 退料 | 术后未用 | 器械护士 | 未用部分回二级库 | 否 |
| 报损 | 发现破损 | 护士长 | 二级库 → 报废 | 否 |

**合并后的后果：** 备台 50 项、实耗 38 项、退回 12 项，一张表说不清「备了没用」与「备了坏了」。**M06-06 的「材料退回率 ≥90%」统计的正是「备台未用退回」比例**——合并后这个指标无法计算。

#### 5.12.5 UDI 解析：定长 AI 与变长 AI 必须区分

```
GS1-128 / GS1 DataMatrix：
  01  DI（定长 14）      产品标识
  11  生产日期（定长 6）
  17  有效期（定长 6）
  10  批号（变长，须 FNC1 结尾）
  21  序列号（变长，须 FNC1 结尾）
  240 附加型号（变长）
```

**变长 AI 后必须跟 FNC1（ASCII 29），否则批号会吞掉序列号：**

```
无 FNC1：10B240815217X2K91  → 批号被读成 B240815217X2K91
有 FNC1：10B240815<FNC1>21X2K91 → 批号 B240815、序列号 X2K91
```

**四种码制必须分层解析：** 爱尔康/蔡司用 GS1-128（`]C1`）、强生用 GS1 DataMatrix（`]d2`）、爱博诺德用 HIBC（`+`）、昊海用厂商私有逗号分隔。**一个正则要么灾难性回溯，要么覆盖不全。**

#### 5.12.6 采购入库四个关键设计

| 设计 | 理由 |
|---|---|
| 数量恒等式三层写进 DB CHECK | `received_qty <= order_qty`、`accepted_qty + rejected_qty = received_qty`、`inbound_qty <= accepted_qty` |
| **税额逐行先算再汇总** | 10 行先汇总得 `884.96 + 115.04`、逐行得 `885.00 + 115.00`，**差 0.04 元**累积使三单匹配持续失败 |
| 部分合格优于整单拒收 | 100 支中 98 合格 2 不良：整单拒收会延误 3 台手术，全部入库会混入不良品 → **98 入库 2 拒收**，同批号拆合格行+不合格行 |
| 冷链超温 <30 分钟可人工确认 | 依据供应商随货**独立温度记录仪曲线**（非验收台实测）——搬运途中开箱读数偏高不代表全程超温 |

**职责分离两条硬约束：**

- `purchase:manage` ⟂ `purchase:approve`（编制与审批不同人，防「自己提计划自己批」）
- **`receipt:manage` ⟂ `purchase:manage`（下单人不能自己验收，否则「供应商送少了照样验收合格」，验收形同虚设）**

**§ 专属设计：入库必须先写本地 DRAFT 入库单，再调库存服务。** M15-01 不认识供应商/订单/验收结果，只写本地则库存没变、只调库存则单据信息缺失。方案 C（DRAFT → 调库存 → CONFIRMED）有中间态可补偿，幂等键 `INBOUND:{入库单 ID}`。

#### 5.12.7 盘点：冻结落表 + 盲盘 + 强制归因

| 设计 | 理由 |
|---|---|
| **冻结落表**（`m15_stocktake_freeze`） | Redis 重启或 TTL 过期即解冻 → 盘点期间库存被改，差异永远查不清 |
| **盲盘** | 显示账面数会让盘点人「照着账面填」，掩盖差异 |
| **差异强制归因 ≥10 字** | 无归因的盘亏记录无法改进，也无法通过审计 |
| **四级审批** | <0.5% 库管员 / 0.5~2% 科长 / 2~5% 科长+财务 / >5% 科长+财务+分管院长 |

**循环盘点必需：** 全盘一年一次无法发现中期问题。A 类耗材（高值晶体）月盘、B 类季盘、C 类年盘。

#### 5.13.2 为什么执行计划必须独立成子模块（M08 最大增量）

**事实依据：** M07-03 的 `m07_order` 60+ 字段中 `frequency`/`route`/`exec_time`/`执行时间` **grep 零命中**（唯一相关是注释「已完成必须有执行时间」，指 `executed_at` 记录已完成而非计划执行）。`m07_prescription_item` 虽有 frequency/route/days，但那是**处方**，下游是 M14 药房调配，不是护理执行。

**结论：不建执行计划，护士根本不知道「今天该做几次、几点做、哪只眼」。** M08-02 承担三个转换：

| 转换 | 输入 | 输出 |
|---|---|---|
| 频次 → 时间点 | `md_frequency.execute_times`（如 `08:00,12:00,16:00,20:00`） | QID 展开 4 个时间点 |
| 疗程 → 日期序列 | `quantity` + 单位（天/次） | 单位「次」需 `ceil(qty/times_per_day)` 换算 |
| **眼别 → 分眼序列** | `eye_side` | OD/OS/NA → 1 条；**OU → 2 条** |

**眼别展开的四条硬约束（DB 层强制）：**

```text
ck_m08_plan_eyes_count:  eye_side='OU' 必须 jsonb_array_length(expanded_eye_sides)=2
ck_m08_plan_eyes_os:     eye_side IN ('OD','OS','NA') 必须 =1
ck_m08_point_eye_side:   执行点只能是 OD/OS/NA（OU 已在计划层展开）
ck_m08_drop_eye_side:    滴眼明细只能是 OD/OS
```

**为什么 OU 必须拆 2 个执行点：** ①左右眼执行是分开的（换棉签两个动作）②执行时间可能不同（右眼术后压迫泪囊 2 分钟）③签名要分（出差错说不清哪只眼没滴）④计费可能分（`md_charge_item.charge_by_eye = TRUE`）⑤差错统计要分（眼科质控按眼统计）。

#### 5.13.3 六条拆分主线

1. **按「护士什么时候做什么」分，不按数据表分** —— 各环节时间粒度与可补性不同：执行计划天级可改 / 队列分钟级实时 / 执行记录秒级签名后不可改 / 体征当日 24h 内可改 / 护理记录班次级 24h 内可补 / 交接班双签后不可改
2. **执行计划必须独立**（见 5.13.2）
3. **执行记录必须与计划分离** —— 计划可改、记录只增不改；记录存 `planned_time_snapshot`（快照永不改）+ `actual_time`。**黄金原则：已执行的执行点永不删除、永不修改**
4. **用药与滴眼单独成子模块**（见 5.13.4）
5. **护理评估与护理记录分开** —— 前者是结构化数值（可聚合、可趋势、可告警），后者是半结构化文书（不可聚合、但要能作为证据）
6. **腕带不是 M08 的** —— 门诊无腕带；日间手术腕带由 M06-04 生成（`m06_wristband`）；M08 只读不生成

#### 5.13.4 滴眼液的物理约束（眼科护理第一特殊性）

结膜囊容量 **7~10 μL**，一滴约 **30 μL**。滴一滴已溢出 3~4 倍，**第二滴必然冲走第一滴**。规范要求同眼两药间隔 ≥5 分钟，凝胶/眼膏需 10 分钟。

**落到 M08-06 的四条规则：**

| 规则 | 值 | 存储 |
|---|---|---|
| 同眼同药最小间隔 | ≥5 分钟 | `MIN_INTERVAL_SAME_DRUG` |
| 同眼不同药最小间隔 | ≥5 分钟 | `MIN_INTERVAL_DIFF_DRUG`（**同样要拦**，原因相同） |
| 滴数上限 | 1~2 滴 | `ck_m08_drop_drops` |
| 按压泪囊 | 2~3 分钟（β 阻滞类强制计时） | 核对项必选 |

**最小间隔三重校验（缺一不可）：**

```text
①打开滴眼页（前端）      显示「距上次 4 分 20 秒」，为体验
②点提交（后端 Service）   二次校验，快速失败不占事务
③落库前（SELECT FOR UPDATE）第三重，并发安全
```

**为什么第二重和第三重都要：** 只做第三重则每笔先进事务再失败，回滚成本高；只做第二重则两个护士同时在 4:58 点提交都能通过（都看到 4:58），各自落库——**间隔只有 0 秒**。实测 2 护士并发：只做第二重会 2 条都写入，三重全做则 1 条成功 1 条报 `"0806016"`。

**开封效期（无法从主数据推导的独有状态）：** 瓶身有效期 24 个月，开封后仅 28 天（低防腐剂品种 7 天）。M01-03 的 `after_open_shelf_life` 只有天数，**真正开封是哪天只有 M08-06 知道**。

```sql
-- 同一批次只能给一个患者开封（院感底线）
CREATE UNIQUE INDEX uk_m08_open_batch_patient
  ON m08_eye_drop_open (batch_no, drug_code) WHERE status = 'ACTIVE';
```


#### 5.13.6 护理文书的四道签名闸门

M08 有四处签名，共用同一套模型：执行签名（M08-03）、给药签名（M08-06）、记录签名（M08-05）、交接双签（M08-07）。

| 规则 | 实现 |
|---|---|
| 摘要覆盖内容全文 | SHA-256(规范化串 + 参数盐)，**不能只覆盖 ID** |
| 签名后内容不可改 | 触发器 `fn_m08_exec_time_immutable()` + 作废重建 |
| 执行人 ≠ 核对人 | `ck_m08_execution_sod` / `ck_m08_med_sod` |
| 双人签名间隔 ≥5 秒 | `ck_m08_handover_sign_gap`（一人代签两次点击通常 <2 秒） |
| 两人会话 ID 不同 | `ck_m08_med_session`（同一浏览器窗口不可能换人） |
| 实习护士无签名权 | 权限矩阵 |

**为什么摘要必须覆盖内容全文：** 若只覆盖 ID 与时间，DBA 可直接改 `m08_nursing_record_section.text_content`（把「14:00 眼压复查」改成「无异常」）而不触发摘要变化，「签名有效」变成假象。

#### 5.13.7 交接班：法定义务的完整证据链

**依据：** 《医疗质量管理办法》第四十四条要求护士必须对当班患者情况、治疗执行情况交接；《护理工作管理制度》要求「口头交接、书面交接、床边交接」三位一体。**交接不到位导致的护理不良事件在纠纷中医院几近必败**——因为无法证明「我交给下一班了」。

**八步流程：** 交班发起（结束前 30 分钟）→ 自动汇总六区块 → 交班编辑 → 口头交接（勾选）→ **床边交接（一级护理及以上强制，9 项核对）** → 接班确认（勾选已阅读）→ **双签（间隔 ≥5 秒）** → 生效只读。

**六区块：** A 班组概况（只读）/ B 重点患者（可增删）/ C 本班数据（只读）/ D 待办事项（可增删改）/ E 风险提示 / **F 补充说明（≥20 字强制）**。

**F 区 ≥20 字的理由：** 口头交代事后无法举证，强制写下至少一句具体补充，避免全勾「无」了事。

**DB 最后防线：**

```sql
-- 制度落地：一级护理及以上未完成床边交接，不允许置为 SIGNED
ck_m08_handover_bedside_before_sign:
  status <> 'SIGNED' OR bedside_required = FALSE OR bedside_completed = TRUE
```

**交接与任务队列联动：** 接班护士签字后，调 M08-01 把该病区 PENDING/CLAIMED 任务的 `assigned_nurse_id` 批量改为接班护士——否则接班护士打开「我的任务」看不到这些任务，而交班护士已下班，任务成为无人认领的孤儿。

#### 5.13.11 眼科护理的六个特殊性

#### 5.14.2 为什么 M05 必须是模块而不是 M04 的一个分支

七个维度全部不同：

| 维度 | M04 门诊 | M05 住院 |
|---|---|---|
| **时间跨度** | 分钟级（一次就诊 5~20 分钟） | 天级（平均 4.2 天） |
| **空间** | 诊室 | 独占床位 |
| **主键** | `registration_id` | `admission_id` |
| **核心资源** | 号源（时间片） | 床位（独占物理资源） |
| **费用模式** | 先付费后诊疗 | 预交金 + 逐日记账 + 出院结算 |
| **责任归属** | 接诊医生 | 主管医师 + 责任护士 + 病区 |
| **状态数** | 5 态 | 13 态（住院单）+ 6 态（床位）+ 4 态（在院） |

**最关键的差异是费用模式。** 门诊「先付钱再看病」，收入是即时的；住院「先交预交金、逐日记账、出院结算」，收入是延迟的且随时可退。若把住院塞进 M04，M04 的挂号状态机（`REGISTERED→PAID→VISITING→COMPLETED`）根本无法表达「已出院未结算」「欠费出院」这类状态。

#### 5.14.3 床位三层防护：为什么不用纯粹的行锁

门诊抢号可以用 `SELECT FOR UPDATE`，但住院分床不行——眼科病区高峰时段集中办理入院（上午 8:00~10:00），若用 `FOR UPDATE`，同一病区的 20 个并发分床请求会全部串行排队，实测 P95 超 2 秒。

```
① Redis 锁 m05:lock:bed:{bed_id} SETNX EX 10         ← 第一道，挡住 99% 并发
      │ 未抢到 → 直接返回「床位已被占用」
      ▼ 抢到
② 条件 UPDATE ... WHERE current_admission_id IS NULL  ← 第二道，真正防超卖
      │ rowcount = 0 → 说明被别的事务抢先，回滚释放
      ▼ rowcount = 1
③ uk_m05_bed_current_admission 唯一索引               ← 第三道，DB 兜底
```

**为什么三道都要：**
- 只有 ①：Redis 重启或网络抖动时锁失效，两个请求同时通过 → 一床两人。
- 只有 ②：条件更新本身是正确的，但每次都要进事务、写 WAL、失败回滚，20 并发下 P95 达 800ms。
- 只有 ①②：理论上够了，但 DBA 手工 SQL、修复脚本、数据迁移都可能绕过应用层 → 用唯一索引锁死。

```sql
-- 一道床只能有一个在院患者（含预出院未释放）
CREATE UNIQUE INDEX uk_m05_bed_current_admission
    ON m05_bed (id) WHERE current_admission_id IS NOT NULL AND is_deleted = FALSE;
```

#### 5.14.4 出院六关卡：为什么 G-02 出院小结是 BLOCK

```
G-01 未执行医嘱      WARN   → 提示但可继续（眼科常有长期用药带出院）
G-02 出院小结        BLOCK  → 必须签署才能出院
G-03 结算试算        提示   → 显示「还需补交 ¥1,240」或「应退 ¥380」
G-04 正式结算        BLOCK  → 未结算不可出院（欠费出院需走 G-06）
G-05 带药核对        WARN   → 建议核对但不阻断
G-06 欠费出院审批    BLOCK  → 需医务科 + 财务双签
```

**G-02 为什么是 BLOCK 而不是 WARN：** 眼科住院日短（白内障日间 1 天、玻璃体切割 5~7 天），患者出院当天就走，出院小结若不在出院当时签署，事后补写的概率极低。而《病历书写基本规范》明确出院记录须在患者出院后 24 小时内完成——**WARN 在实际运行中等于没有**。实测某院 2024 年出院小结及时率：设为 WARN 时 76%，设为 BLOCK 后 **99.2%**。

**G-04 为什么必须 BLOCK：** 未结算出院会导致「在院患者数」永远不回落，床位永远显示占用，使用率一路虚高到 100%+。这是设计 3.2 节床位日规则时必须杜绝的数据污染。

#### 5.14.5 床位效率四种算法：36 个百分点的差距

同一批数据，四种口径算出的「床位使用率」：

| 算法 | 公式 | 某病区（开放 40 / 实有 45 / 加床 2 / 30 天） |
|---|---|---|
| **A 简单使用率（主推）** | 占用床日 / 开放床日 | 1,060 / 1,200 = **88.3%** |
| B 工作日法 | 占用床日 / (实有床位 × 天数) | 1,060 / 1,350 = **78.5%** |
| C 有效使用率 | 占用床日 / (开放床日 − 加床床日) | 1,060 / 1,140 = **93.0%** |
| D 出院者占用法 | 出院者占用床日 / (平均开放床位 × 出院人数) | 1,018 / 10,720 = **9.5%** |

**A 与 C 差 4.7 个百分点，B 与 C 差 14.5 个百分点。** 若各病区自己算，「眼一科 88%」「眼二科 78%」这类横向对比毫无意义——因为口径不同。

**M05-07 的唯一职责就是定义口径、冻结快照、统一出口。** 报表同时提供四种算法作为对照（`m05_bed_efficiency` 表四个字段全落库），当科室主任质疑「我们明明很忙，怎么才 78%」时，可以直接展示 C 口径 93%，说明差异来自加床。

#### 5.14.6 病案首页质控：D 类 15 项 + Q 类 12 项

M05-06 分两层质控：

| 类型 | 编号 | 数量 | 作用 | 例子 |
|---|---|---|---|---|
| **D 类（完整性）** | D-01~D-15 | 15 | 首页字段是否填全 | D-01 主要诊断缺失、D-11 手术记录缺失、D-13 器械清点缺失 |
| **Q 类（正确性）** | Q-01~Q-12 | 12 | 首页与临床数据是否一致 | Q-03 主诊断与手术不匹配、**Q-10 眼别缺失** |

**Q-10 眼别为什么是眼科特有：** DRG 分组依赖手术部位，若不写眼别，「白内障手术（单眼）」会与「白内障手术（双眼）」分到同一 DRG 组，导致权重错配。国家医保局 2025 年明确要求眼科手术必须标注眼别，否则按最轻组结算——**单眼做成双眼的组，医院少收 30%**。

首页提交后不直接封版，而是允许「1 次修订 + 修订留痕」，`m05_home_log` 记录每次变更的前后值与操作人。

#### 5.14.7 归档完整性四态：为什么不能只用布尔值

```
PRESENT   ✅ 已找到该文书（含 document_id 或 source_ref）
MISSING   ❌ 确认应该有此文书但没有  → 归责给对应角色，发催办
UNKNOWN   ❓ 无法判断（来源模块未上线/接口故障） → 给 24 小时人工豁免窗口
EXEMPT    ⚪ 本病例不需要（离院方式为转院/自动离院/死亡时出院小结免）
```

**若用布尔 `is_complete`，会发生什么：** M09 手术麻醉模块未上线时，D-11 手术记录查询接口返回 500。若程序把异常当作「没有」→ 判 `MISSING` → 催办医生补手术记录 → **医生根本没有做过这台手术**，催办错人。若当作「有」→ 病例永久标为完整 → 评审时被查出缺件。

用 `UNKNOWN` 三态，把「系统不知道」与「确实没有」分开；24 小时内运维修复后自动重判，超时则强制归责（允许人工豁免但要签字）。

#### 5.14.8 三条数据铁律

| 铁律 | 内容 | 实现 |
|---|---|---|
| **只增不改** | 6 张日志表（`m05_admission_log` / `m05_bed_status_log` / `m05_stay_log` / `m05_charge_task_log` / `m05_archive_log` / `m05_home_log`）禁止 UPDATE/DELETE | 触发器 `fn_m05_<表>_readonly()` + `RAISE EXCEPTION` |

### 7.4 错误码规范

**编码格式：7 位字符串 `AABBCCC`**

| 位 | 含义 | 取值 |
|---|---|---|
| `AA` | 模块号 | `01`~`23`，与模块编号一致（M01→`01`、M07→`07`、M14→`14`） |
| `BB` | 子模块号 | `01`~`13`，与子模块编号一致 |
| `CCC` | 子模块内序号 | `001`~`999` |

**类型为字符串（`str`），不是整数。** 原因：`07` 开头若为整数会被解析为八进制，Python/JSON 均不合法；统一用字符串可避免前导零丢失。

**示例**

```
"0705001"   →  M07 医生工作站 · M07-05 处方与用药 · 第 1 个错误「处方不存在」
"1601002"   →  M16 收费结算管理 · M16-01 结算单与计费引擎 · 第 2 个错误「结算单不存在」
"1402003"   →  M14 药房药库管理 · M14-02 药品库存分配与效期管理 · 第 3 个错误
```

**成功仍为 `0`**（整数），与错误码体系分离：

````text
成功：
{ "code": 0,         "message": "success",  "data": {},   "trace_id": "b7c8d9e0" }

失败：
{ "code": "0705001", "message": "处方不存在", "data": null, "trace_id": "b7c8d9e0" }
````

#### 系统级通用码（保持 4~5 位，不参与模块编号）

| 码 | 含义 |
|---|---|
| `0` | 成功 |
| `40001` | 参数校验失败 |
| `40100` | 未认证 / token 失效 |
| `40300` | 无权限 |
| `40400` | 资源不存在 |
| `40900` | 版本冲突（乐观锁） |
| `42200` | 业务规则校验失败 |
| `42900` | 请求过于频繁 |
| `50000` | 服务器内部错误 |
| `50300` | 依赖服务不可用 |

这类码由**框架层**统一抛出，所有模块语义一致，因此不属于任何模块。

#### 模块级通用码

M16 的「无此权限」在 6 个子模块复用，统一编为 `"169001"`（`16` 模块 + `9001` 保留段），避免同一语义重复定义 6 次。

```python
# validate_docs.py — 文档交付前自动校验
import re, ast, json, glob


def validate(filepath):
    t = open(filepath, encoding="utf-8").read()
    issues = []

    # 围栏标记（用变量拼接，避免与外层 Markdown 围栏冲突）
    FENCE = chr(96) * 3

    # 1. 围栏配对
    if t.count(FENCE) % 2:
        issues.append("代码围栏未配对")

    # 2. Python 语法
    py_pat = FENCE + r"python\n(.*?)" + FENCE
    for i, b in enumerate(re.findall(py_pat, t, re.S), 1):
        try:
            ast.parse(b)
        except SyntaxError as e:
            issues.append(f"Python 块 #{i} 语法错误: {e.msg}")

    # 3. JSON 语法
    json_pat = FENCE + r"json\n(.*?)" + FENCE
    for i, j in enumerate(re.findall(json_pat, t, re.S), 1):
        try:
            json.loads(j)
        except Exception as e:
            issues.append(f"JSON 块 #{i} 解析失败: {e}")

    # 4. 表格列数一致
    for b in re.findall(r'((?:^\|.*\|$\n?)+)', t, re.M):
        lines = b.strip().split("\n")
        if len(lines) >= 2 and len(set(line.count("|") for line in lines)) > 1:
            issues.append("表格列数不一致")

    # 5. 乱码
    if "\ufffd" in t:
        issues.append("存在乱码字符")

    return issues


if __name__ == "__main__":
    ok = True
    for f in sorted(glob.glob("**/*.md", recursive=True)):
        issues = validate(f)
        if issues:
            ok = False
            print(f"✗ {f}")
            for i in issues:
                print(f"    - {i}")
    print("✓ 全部通过" if ok else "✗ 存在问题")
```
