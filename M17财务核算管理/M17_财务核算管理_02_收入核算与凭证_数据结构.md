### 4.2 表：`m17_revenue_collect`（收入归集主表）

**用途：** 记录「某一天、某个业务范围、某种归集口径」的一次收入取数与归集结果。全部金额**原样取自 M16-09 日结**（`GET /internal/v1/m16/daily/summary/{date}`），本表不重算，只做归集与口径落账。

**写入方：** M17-02 收入归集任务（`m17.daily_revenue_voucher` 定时任务 / 手工取数）。**只读方：** M17-04 科室核算（读科室收入）、M17-08 财务报表（读收入汇总）、M22（经 P-06）、M16-09（回查差异）。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | N | IDENTITY | 主键 |
| `collect_no` | VARCHAR(32) | N | — | 归集单号 `RC` + `YYYYMM` + `-` + 4 位，如 `RC202610-0001` |
| `close_date` | DATE | N | — | 取数日结日期（M16-09 `close_date`） |
| `period` | VARCHAR(7) | N | — | 会计期间 `YYYY-MM`，如 `2026-10`（逻辑引用 M17-01 `m17_account_period`） |
| `biz_scope` | VARCHAR(24) | N | `ALL` | 归集业务范围 `ALL`（全院）/ `OUTPATIENT`（门诊）/ `INPATIENT`（住院）/ `DAY_SURGERY`（日间手术）/ `OPTICAL`（视光）/ `REFRACTIVE`（屈光） |
| `collect_type` | VARCHAR(16) | N | `DAILY` | 归集类型 `DAILY`（日归集）/ `MONTH_SUPPLEMENT`（月度补归集）/ `RETRY`（重取）/ `MANUAL`（手工） |
| `data_source` | VARCHAR(16) | N | `M16_DAILY` | 数据来源（共享规范 §13 `data_source`）：`M16_DAILY` / `M16_OPTICAL` / `MANUAL` |

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m17_revenue_collect` | PRIMARY KEY | `id` | — |
| `uk_m17_revenue_collect_no` | UNIQUE | `collect_no` WHERE `is_deleted = FALSE` | 归集单号唯一 |

| `idx_m17_revenue_collect_scope` | B-Tree | `(biz_scope, close_date DESC)` | 分范围统计 |

**约束说明**

```sql
-- 归集单号格式：RC + YYYYMM + - + 4 位
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_no_format
    CHECK (collect_no ~ '^RC[0-9]{6}-[0-9]{4}$');

-- 会计期间格式：YYYY-MM
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_period_format
    CHECK (period ~ '^[0-9]{4}-(0[1-9]|1[0-2])$');

-- 归集状态枚举
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_status
    CHECK (status IN ('DRAFT', 'COLLECTED', 'VOUCHERED', 'AUDITED',
                      'POSTED', 'CLOSED', 'FAILED'));

-- 业务范围枚举
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_scope
    CHECK (biz_scope IN ('ALL', 'OUTPATIENT', 'INPATIENT', 'DAY_SURGERY',
                         'OPTICAL', 'REFRACTIVE'));

-- 归集类型枚举
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_type
    CHECK (collect_type IN ('DAILY', 'MONTH_SUPPLEMENT', 'RETRY', 'MANUAL'));

-- 数据来源枚举
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_source
    CHECK (data_source IN ('M16_DAILY', 'M16_OPTICAL', 'MANUAL'));

-- 金额不得为负（退款、净收入、长短款可为负，单独约束）
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_amounts
    CHECK (total_income >= 0 AND total_refund >= 0 AND fee_amount >= 0
           AND insurance_receivable >= 0);

-- 净收入必须等于收入减退款（M16 口径原样落账，不允许出现差额）
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_net
    CHECK (abs(net_income - (total_income - total_refund)) < 0.005);

-- 已生成凭证必须有凭证号
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_vouchered
    CHECK (status NOT IN ('VOUCHERED', 'AUDITED', 'POSTED', 'CLOSED')
           OR (voucher_id IS NOT NULL AND voucher_no IS NOT NULL AND voucher_at IS NOT NULL));

-- 失败必须有错误码
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_failed
    CHECK (status <> 'FAILED' OR (error_code IS NOT NULL AND error_msg IS NOT NULL));

-- 错误码必须在本子模块号段内
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_error_range
    CHECK (error_code IS NULL OR (error_code >= '1702001' AND error_code <= '1702999'));

-- 期间必须与日结日期一致（`2026-10-21` 的期间只能是 `2026-10`）
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_period_match
    CHECK (period = to_char(close_date, 'YYYY-MM'));

-- 版本号非负
ALTER TABLE m17_revenue_collect
    ADD CONSTRAINT ck_m17_revenue_collect_version
    CHECK (version >= 0);
```

**设计说明：**

1. **为什么金额字段原样落库而不在本模块重算？** M16 的 `net_income` 已按业务口径（应收 − 减免 − 退款 + 医保）算好，M17 若用 `total_income − total_refund` 再算一次，遇到「减免」「预收结转」等场景会与 M16 差几分钱。因此本表直接存 M16 的三个数，并用 `ck_m17_revenue_collect_net` 只做**一致性校验**（`abs(net − (income − refund)) < 0.005`），不做重算落库。

2. **为什么 `(close_date, biz_scope, collect_type, org_id)` 是唯一键？** 归集的最大风险是「同一天被归集两次」。若只靠应用层「先查后插」，两个并发的定时任务（如双实例部署时 Cron 重复触发）必然产生重复凭证。数据库唯一索引是唯一可靠保证，重复插入直接抛 `IntegrityError`，Service 捕获后转为 `"1702004"`（重复归集）。

3. **为什么 `period` 用 `to_char(close_date, 'YYYY-MM')` 约束而非应用层生成？** 手工取数时若前端传错期间（如把 `2026-10-21` 归到 `2026-11`），会导致跨期收入，月末试算必然不平。把一致性下沉到 CHECK 约束后，任何入口（含运维补数脚本）都无法写入跨期数据。

4. **为什么 `is_frozen` 与 `m16_version` 两个字段并存？** `is_frozen` 回答「取数时 M16 是否已封账」（未封账的数据可能被改，不能直接出正式凭证）；`m16_version` 回答「M16 后来改没改过数」（M16 允许在封账前修改日结，版本号变化说明数据源已变，需要重取）。两者结合才能判断归集结果的可靠性。

5. **为什么 `adjust_amount` 允许非零但需审批？** 现实场景：M16 日结因系统故障漏记了一笔现金，财务在归集时手工补 300.00。若完全禁止，财务只能去改 M16 数据（更危险）；若随意允许，则可能出现「调整」掩盖问题。因此保留字段 + 默认 0.00 + 非零强制审批留痕，是可控的折中。

**设计说明：**

1. **为什么要拆成「业务线 × 支付方式」的矩阵，而不是两张独立表？** 凭证的两个方向来自两个不同维度：借方看「钱从哪来」（支付方式 → 现金/银行/应收医保），贷方看「收入属于哪条线」（业务线 → 医疗收入二级科目）。如果拆成「按支付方式汇总」和「按业务线汇总」两张表，就能编出两组各自平衡但**总额不等**的数据（因为两个维度的交叉格没有约束），会出现「借方合计 100 万、贷方合计 98 万」且两边各自「自洽」的假象。用矩阵表保证每个交叉格都唯一，且两侧汇总必然一致。

2. **为什么冗余 `period` / `close_date` / `collect_no`？** 这张表是最热的分析表（P-06 收入汇总、M17-04 科室收入、M17-08 报表都按 `period + biz_line` 聚合）。若每次都要 JOIN 主表取期间，4,380 行/年的聚合在 5 年数据量下会明显变慢；冗余后可直接走 `idx_m17_revenue_biz_line_period` 覆盖索引查询。一致性由主表同事务写入保证。

3. **为什么 `alloc_ratio` 要落库？** 它的用途不是分摊（收入不需要分摊），而是**校验尾差**：所有行 `alloc_ratio` 之和必须等于 `1.000000`，否则说明拆分时丢了钱。这是月末「收入勾稽对不上」的最早预警点，比等试算平衡再查快得多。

4. **为什么现金手续费强制为 0.00？** 现金收款没有渠道成本，若出现非零的手续费，几乎必然是录错（把 POS 手续费录到了现金行）。用 CHECK 约束直接拦截，比事后对账发现异常再改更省事。

```sql
-- 应用账号对凭证表不授予 DELETE；UPDATE 仅保留状态流转所需
REVOKE DELETE ON m17_revenue_voucher FROM app_m17;

GRANT SELECT, INSERT ON m17_revenue_voucher_entry TO app_m17;
```

> **说明：** 本表与 `m17_revenue_voucher_entry` 为**只增不改**的凭证类表。已过账（`POSTED`）/已冲销（`REVERSED`）凭证禁止 UPDATE 与 DELETE，由触发器 `trg_m17_revenue_voucher_immutable` 与 `REVOKE` 双重保证；更正只能通过「红字冲销 + 蓝字重开」两张新凭证实现。

**设计说明：**

1. **为什么分区键用 `period`（`VARCHAR(7)`）而不是 `voucher_date`？** 会计期间是财务的天然管理边界：月末结账、试算平衡、报表取数全部按期间进行。用 `period` 做 `RANGE` 分区后，`WHERE period BETWEEN '2026-01' AND '2026-12'` 能精确裁剪到 12 个分区（年度报表只扫这 12 个）；若用日期做分区键，跨月查询要扫更多分区，且 `period` 与日期的一致性问题会转移到分区层。

2. **为什么主键是 `(id, period)` 而不是单 `id`？** PostgreSQL 16 的分区表要求唯一约束必须包含分区键。`(id, period)` 既保证 `id` 全局唯一（`id` 由 IDENTITY 生成，实际不会重复），又满足分区表的技术要求。业务查询一律用 `voucher_no + period`，不受影响。

3. **`CHECK (debit_total = credit_total)` 为什么是「写在表上」而不是「写在 Service 里」？** 这是共享规范第 4 条铁律。Service 层校验只能挡住正常调用路径，挡不住运维补数脚本、数据迁移工具、DBA 手工 SQL。把平衡写进 CHECK 后，**任何入口都无法写入不平衡的凭证**——这是财务软件与普通业务系统的本质区别。

4. **为什么还需要 `fn_m17_revenue_voucher_immutable` 触发器？** `REVOKE UPDATE` 会把「状态流转」（如 `AUDITED → POSTED`）也一起禁掉，导致无法过账。因此保留 `UPDATE` 权限，但用触发器精确拦截：已过账凭证的**金额、日期、来源**不可改，只允许状态字段向 `REVERSED` 流转。这样既保住不可变性，又能正常过账与冲销。

5. **为什么 `amount_in_words` 要独立成列？** 《会计基础工作规范》要求记账凭证金额必须同时有阿拉伯数字与大写金额，两者不一致即为不合格凭证。落库后可在打印与审核时做一次比对（见业务规则），避免打印时现算导致数字漂移。

**设计说明：**

1. **为什么借方与贷方金额分成两个字段，而不是「一个金额 + 一个方向」？** 财务软件的标准做法是双金额列。原因有三：①`SUM(debit_amount)` 与 `SUM(credit_amount)` 可直接得到借贷合计，无需 `CASE WHEN` 分支，索引也更容易命中；②行级约束能强制「借方行不能有贷方金额」（`ck_m17_revenue_voucher_entry_amount_side`），单金额列无法表达这个约束；③与银行流水、总账、报表的字段口径一致，减少转换层。

2. **为什么 `subject_name` 要快照？** 科目会改名（如「医疗收入-门诊」改为「医疗收入-门诊诊疗」）。若凭证只存编码，几年后打印历史凭证会显示新名称，与原始凭证不符——《会计档案管理办法》要求凭证归档后内容不得变更。快照后历史凭证永远显示当时的名称。

3. **为什么要求「末级科目才允许记账」？** 若允许在「1001 库存现金」与「1001 库存现金-门诊窗口」同时挂明细，科目余额表的上下级汇总会重复计数（父科目余额 = 自身明细 + 子科目余额）。财务软件统一规则：只有没有下级的科目可以记账，上级科目余额由下级汇总。本表用 `subject_level` + 应用层校验（见 8.4）实现。

4. **红字冲销为什么不用负数而用 `reverse_flag` + 原方向？** 两种做法都合法。本系统选择「保留正数 + 标记 `reverse_flag` + 用相反 `dc_flag`」是因为：①`NUMERIC(18,2)` 上 `SUM` 时可以按 `reverse_flag` 加符号，避免负数混入导致某些统计口径出错；②打印红字凭证时可以直接按 `reverse_flag` 选红色样式；③符合《会计基础工作规范》「红字冲销」的表述习惯，凭证上写「红字冲销 V202610-0001」比写负数更易读。

**设计说明：**

1. **为什么连失败的调用也要落库？** 收入核算最常见的争议是「昨天怎么没出凭证」，而实际原因可能是 M16 接口超时、日结未封账、或数据缺支付方式。只有把**每次失败**连同错误码、耗时、trace_id 一起留下来，才能在月初对账时回答「是系统问题还是数据问题」。

2. **为什么存 `response_snap` 全量 JSONB 而不是只存几个金额字段？** M16 的日结汇总包含 `by_pay_method`、`by_biz_type`、`cash_diff_net`、`reconcile_diff_amount` 等多个维度。凭证生成后若发现某个维度算错，需要能回看「当时 M16 到底返回了什么」。只存金额字段无法支持事后审计。JSONB 压缩后单条约 2KB，年 1,500 条约 3MB，成本可接受。

3. **为什么 `response_hash` 要独立存？** 快照是「证据」，证据必须可验证。存 SHA-256 后，任何对 `response_snap` 的改动（含 DBA 手工 UPDATE）都会导致摘要不匹配，在审计抽查时能立即发现。

4. **为什么分区键用 `fetch_date`（取数发生日）而不是 `target_date`（被取数日）？** 取数日志是运维视角，需要按「什么时候取的」来排障与清理；跨月补取（如 11 月 2 日补取 10 月 31 日）会落在当月分区，符合「日志按写入时间归档」的惯例。

**设计说明：**

1. **为什么差异要单独成表，而不是在归集单上加几个字段？** 一次归集可能产生多条差异（如「现金收入差 0.02」「微信支付方式归属错 3,000.00」「手续费差 0.50」），每条差异的处理人、处理方式、处理时间都不同。放在主表只能记一个总差额，无法闭环。

2. **为什么 `tolerance_amount` 默认只有 0.01？** 财务对账的最小粒度是「分」。1 分以内的差异通常是浮点或四舍五入导致，可以接受；超过 1 分就是实质差异，必须查。把容差落库（而不是写死在代码里）是为了让不同医院按自身精度要求调整（如按 0.05 或 1.00）。

3. **为什么 `is_blocking` 是独立布尔位？** 并非所有差异都要挡住结账：`COUNT` 层级（笔数）差异往往可以「已认可」后继续，而 `AMOUNT` 层级（金额）差异必须处理。用独立字段而不是按 `diff_type` 硬编码判断，是为了让财务在特殊情况下能手工调整阻断策略，同时保留「默认阻断金额差异」的安全默认值。

4. **为什么 `uk_m17_revenue_diff_unique` 要把 `biz_line` / `pay_method` 放进唯一键？** 同一归集单的「现金收入差」与「微信收入差」是两条不同差异，需要分别跟踪；但**完全相同的维度**重复登记则是错误（会导致差异金额重复计算、结账校验误判）。四字段唯一键正好表达这个语义。

### 4.9 表：`m17_revenue_mapping`（收入科目映射规则表）

**设计说明：**

1. **为什么映射要配置化而不是硬编码？** 医院的科目体系会变：新增「医保应收账款-居民医保」、把「视光收入」拆成「视光-镜架」与「视光-镜片」、或者不同院区科目编码不同。硬编码意味着每次调整都要发版、回归测试、停机窗口。配置化后财务自己在 P06 改一行即可生效，并留痕。

2. **为什么 `uk_m17_revenue_mapping_target` 要保证「同一匹配维度唯一」？** 若同一支付方式有两条启用规则，凭证生成时会产生歧义：到底用哪条？靠 `priority` 取舍会让结果不可预测（两条规则谁赢取决于数据插入顺序）。因此唯一键保证一个维度一条规则，需要改就改这条规则本身。

3. **为什么 `match_scope` 要把借/贷分开？** 借方由「钱从哪来」决定（支付方式），贷方由「收入属于哪条线」决定（业务线），两个维度的匹配键完全不同。用一个字段 `match_key` 混存会导致语义模糊，且无法用唯一键表达「同一支付方式唯一、同一业务线唯一」这两个独立约束。

4. **为什么需要 `is_default` 兜底规则？** M16 可能返回新的支付方式（如新增数字人民币 `DCEP`），若没有兜底规则，凭证生成会因「找不到科目」直接失败，导致当日收入无法入账。兜底规则让它先入「其他应收款」，财务再补具体规则；保证「收入不会因为配置缺失而丢失」，这是财务系统的底线。

```sql
-- 1) 按业务线汇总净收入（走 idx_m17_revenue_biz_line_period 覆盖索引）
SELECT biz_line,
       SUM(income_amount) AS income,
       SUM(refund_amount) AS refund,
       SUM(net_amount)    AS net
FROM m17_revenue_biz_line
WHERE period BETWEEN :period_from AND :period_to
  AND is_deleted = FALSE
GROUP BY biz_line
ORDER BY net DESC;

-- 2) 按支付方式汇总净额（资金核对用）
SELECT pay_method,
       SUM(income_amount) AS income,
       SUM(refund_amount) AS refund,
       SUM(net_amount)    AS net,
       SUM(fee_amount)    AS fee
FROM m17_revenue_biz_line
WHERE period BETWEEN :period_from AND :period_to
  AND is_deleted = FALSE
GROUP BY pay_method;

-- 3) 借贷平衡校验（应为 0 行）
SELECT voucher_no, period, debit_total, credit_total
FROM m17_revenue_voucher
WHERE period = :period
  AND debit_total <> credit_total;

-- 4) 分录合计与主表合计一致性校验（应为 0 行）
SELECT v.voucher_no,
       v.debit_total,
       COALESCE(SUM(e.debit_amount), 0)  AS entry_debit,
       COALESCE(SUM(e.credit_amount), 0) AS entry_credit
FROM m17_revenue_voucher v
LEFT JOIN m17_revenue_voucher_entry e
       ON e.voucher_id = v.id AND e.period = v.period
WHERE v.period = :period
GROUP BY v.voucher_no, v.debit_total
HAVING COALESCE(SUM(e.debit_amount), 0) <> v.debit_total
    OR COALESCE(SUM(e.credit_amount), 0) <> v.debit_total;
```

### E.1 建表依赖顺序

**外部依赖（必须先于本子模块存在）：**

| 序号 | 外部对象 | 提供方 | 本模块使用方式 |
|---|---|---|---|
| 1 | `m17_account_subject` | M17-01 | 科目编码/名称/类别/级次的逻辑引用与校验 |
| 2 | `m17_account_period` | M17-01 | 期间状态校验（是否为 `OPEN`、是否已结账） |
| 3 | `m16_daily_close` | M16-09 | **不直连**，通过 `GET /internal/v1/m16/daily/summary/{date}` 取数 |
| 4 | `m16_payment_*` | M16-05 | 不直连，经 M16-09 汇总间接获取手续费 |
| 5 | `mdm_dept` | M01-01 | 科室辅助核算（`aux_type='DEPT'`）的取值来源 |
| 6 | `pg_trgm` 扩展 | PostgreSQL | 归集单号/凭证号模糊查询（可选） |

**本子模块建表顺序：**

```
第 1 层（无内部依赖）：
  m17_revenue_mapping          （纯配置）

第 2 层（依赖第 1 层的主数据，但不依赖本模块其他表）：
  m17_revenue_collect          （归集主表）

第 3 层（依赖 m17_revenue_collect）：
  m17_revenue_biz_line
  m17_revenue_source_log       （分区表，独立父表与分区）
  m17_revenue_diff
  m17_revenue_carryover

第 4 层（依赖第 2、3 层，凭证类）：
  m17_revenue_voucher          （分区表）
  m17_revenue_voucher_entry    （分区表，随主表分区键）

回滚顺序：第 4 层 → 第 3 层 → 第 2 层 → 第 1 层
```

> 本模块**不建物理外键**，上述分层仅为迁移与回滚的可读性；一致性由应用层校验 + 每日对账任务保证。

```python
def _create_month_partitions(period: str) -> None:
    """为凭证类与日志类分区表创建指定月份分区（period 为 YYYY-MM）。"""
    year, month = period.split("-")
    next_year, next_month = (int(year) + 1, 1) if month == "12" else (year, int(month) + 1)
    upper = "%s-%02d" % (next_year, next_month)
    safe = period.replace("-", "m")
    op.execute(
        "CREATE TABLE IF NOT EXISTS m17_revenue_voucher_%s "
        "PARTITION OF m17_revenue_voucher FOR VALUES FROM ('%s') TO ('%s')"
        % (safe, period, upper))
    op.execute(
        "CREATE TABLE IF NOT EXISTS m17_revenue_voucher_entry_%s "
        "PARTITION OF m17_revenue_voucher_entry FOR VALUES FROM ('%s') TO ('%s')"
        % (safe, period, upper))


def downgrade() -> None:
    """按反向顺序回滚。"""
    op.execute("DROP TABLE IF EXISTS m17_revenue_voucher_entry CASCADE")
    op.execute("DROP TABLE IF EXISTS m17_revenue_voucher CASCADE")
    op.drop_table("m17_revenue_carryover")
    op.drop_table("m17_revenue_diff")

    op.drop_table("m17_revenue_biz_line")
    op.drop_table("m17_revenue_collect")
    op.drop_table("m17_revenue_mapping")
```

## 附录 F：文档维护约定

| # | 约定 | 说明 |
|---|---|---|
| 1 | 表结构以本文档为准 | 详细设计第 4 章仅为指引块，不承载字段定义 |

| 9 | 枚举中文值 | 全局枚举一律英文大写（凭证字 `记/收/付/转` 为业务规定的中文枚举，属唯一例外）；中文名放附录 B 与 D |
