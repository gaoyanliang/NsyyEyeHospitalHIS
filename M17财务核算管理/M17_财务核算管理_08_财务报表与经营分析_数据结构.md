| # | 铁律 | 在数据结构上的体现 |
|---|---|---|

## 1. 表清单

| 序号 | 表名 | 中文名 | 用途 | 预估行数 |
|---|---|---|---|---|
| 1 | `m17_report_def` | 报表模板定义表 | 报表类型、编码、取数规则、版本、启用状态 | 极小（约 30 行） |
| 2 | `m17_report_def_line` | 报表行项目定义表 | 每张报表的行项目、层级、取数科目、计算符号 | 小（约 400 行） |
| 3 | `m17_report_instance` | 报表实例表 | 某期间某报表的一次生成结果（含状态机与勾稽结果） | 中（约 3,600 行/年） |
| 4 | `m17_report_balance` | 资产负债表快照表 | 资产负债表的合计级快照与恒等式校验结果 | 中（约 3,600 行/年） |
| 5 | `m17_report_row` | 报表行数据表 | 报表每个行项目的期初/本期/期末金额（**核心**） | 大（约 50,000 行/年） |
| 6 | `m17_report_indicator` | 财务指标配置与结果表 | 财务指标定义、计算公式、期间结果 | 中（约 24,000 行/年） |
| 7 | `m17_report_export` | 报表导出与订阅日志表 | 导出留痕、订阅推送、文件与水印 | 小（约 1,800 行/年） |

**合计：7 张表**

### 1.1 为什么是这 7 张表（「一张表只表达一件事」的拆解）

| 表 | 回答的问题 | 若不建这张表会怎样 |
|---|---|---|
| `m17_report_def` | 我们有哪些报表、每张报表怎么取数、口径版本是几 | 报表格式硬编码在代码里，调整一次格式要发版；《政府会计制度》换版时无法追溯口径 |
| `m17_report_def_line` | 一张报表里有哪些行项目、每行取哪些科目、加减号是什么 | 行项目与科目映射散落在 SQL 里，加一行报表就要改代码；无法支持不同医院自定义报表 |
| `m17_report_instance` | 某期间这张报表什么时候生成的、谁复核的、是否平衡 | 无法回答「8 月报表是谁在什么时候定稿的」；无法管理 `DRAFT→GENERATED→REVIEWED→PUBLISHED` 状态机 |
| `m17_report_balance` | 资产负债表的三大合计是多少、恒等式是否成立 | 恒等式校验只能每次现算，且无法保存「校验当时的容差与结果」；DB 层无法强制 |
| `m17_report_row` | 报表每一个行项目的数是多少、来自哪个科目余额 | 报表只能用「现查现算」的方式生成，每次打开报表都要扫全科目余额表 + 现算，P95 超过 3 秒 |
| `m17_report_indicator` | 资产负债率、流动比率、收入结余率等指标怎么算、结果是多少 | 指标公式硬编码；不同医院口径不同无法适配；无法按期间留存历史指标值做趋势 |
| `m17_report_export` | 谁在什么时候导出了哪张报表、推给了谁 | 财务报表外泄无法追溯；订阅推送无留痕；导出文件无生命周期管理 |

### 1.2 与其他子模块的表关系（只读引用）

| 上游表 | 归属 | 本模块使用方式 |
|---|---|---|
| `m17_account_subject` | M17-01 | **只读**：报表行项目映射到科目编码，取科目名称与类别 |
| `m17_account_period` | M17-01 | **只读**：校验期间状态（只有 `CLOSED` 期间才允许发布报表） |
| `m17_ledger_balance` | M17-05 | **只读（唯一数据源）**：所有金额取自该表的 `open_balance` / `period_debit` / `period_credit` / `end_balance` |
| `m17_dept_profit` | M17-04 | **只读**：科室损益报表的科室级收入/成本/结余 |
| `mdm_dept` | M01-01 | **只读**：科室名称、科室类型 |
| `m17_report_row` | 本模块 | `m17_report_row.source_balance_id` 记录该行来自哪条科目余额，保证可追溯 |

> **关键铁律的可追溯性设计：** `m17_report_row` 必须有 `source_balance_id`（指向 `m17_ledger_balance.id`）与 `source_subject_code`，任何一行金额都能回答「它来自哪个科目、哪个期间的余额」。这是「不从业务表重算」的物理证据。

### 4.2 表：`m17_report_def`（报表模板定义表）

**用途：** 定义「有哪些报表、编码是什么、取数规则是什么、口径版本是几」。这是报表体系的**元数据根**：所有实例、行项目、指标都挂在模板定义之下。报表格式调整（如《政府会计制度》换版、医院自定义报表）通过新增 `report_version` 实现，**旧版本永不删除**，已发布的历史报表按旧版本可复现。

**写入方：** M17-08 财务科（P01 报表工作台的「模板管理」）。**只读方：** 本模块全部实例生成逻辑、M22（报表清单查询）。

**约束说明**

```sql
-- 报表编码枚举（与共享规范 §13 report_type 一字不差）
ALTER TABLE m17_report_def
    ADD CONSTRAINT ck_m17_report_def_code
    CHECK (report_code IN ('BALANCE_SHEET', 'INCOME_STATEMENT',
                           'CASH_FLOW', 'DEPT_PROFIT', 'INDICATOR'));

-- 报表类型必须与编码一致（防止两者不一致造成筛选混乱）
ALTER TABLE m17_report_def
    ADD CONSTRAINT ck_m17_report_def_type_match
    CHECK (report_type = report_code);

-- 数据来源范围只允许科目余额表（铁律：不得从业务表重算）
ALTER TABLE m17_report_def
    ADD CONSTRAINT ck_m17_report_def_source
    CHECK (data_source_scope = 'LEDGER_BALANCE');

-- 取数方式枚举
ALTER TABLE m17_report_def
    ADD CONSTRAINT ck_m17_report_def_fetch
    CHECK (fetch_mode IN ('SUBJECT_SUM', 'SUBJECT_TREE', 'DEPT_PROFIT'));

-- 报表准则枚举
ALTER TABLE m17_report_def
    ADD CONSTRAINT ck_m17_report_def_standard
    CHECK (statement_standard IN ('GOV_ACCOUNTING', 'ENTERPRISE', 'CUSTOM'));

-- 统计周期枚举
ALTER TABLE m17_report_def
    ADD CONSTRAINT ck_m17_report_def_period_type
    CHECK (period_type IN ('MONTH', 'QUARTER', 'YEAR'));

-- 版本号必须为正
ALTER TABLE m17_report_def
```

**设计说明**

1. **为什么 `data_source_scope` 要被 CHECK 锁死在 `LEDGER_BALANCE`？** 这是「报表是科目余额的投影，不是业务数据的二次统计」这条铁律的**数据库级强制**。若允许配置为 `M16_DAILY` 或 `M14_ISSUE`，就等同于允许报表绕过会计科目直接读业务表，那报表与总账将出现两套真相。CHECK 约束让这条路在 DDL 层就不存在。
2. **为什么要有 `report_version` 与 `prev_def_id`？** 《政府会计制度》在 2019 年、2022 年各有一次格式调整；医院自查也可能调整报表行项目（增加「DRG 结算差额」行）。版本化后：旧报表按旧版本可复现，新报表按新版本生成，`prev_def_id` 让财务能一眼看出「这张报表改过几次」。
3. **为什么 `report_type` 与 `report_code` 冗余且用 CHECK 强制相等？** 报表类型在筛选、导出、权限判断中高频使用，单独冗余一个字段便于加索引；CHECK 保证两者永不漂移。看起来多余，但避免了「编码改成 `INCOME_STATEMENT`、类型还是 `BALANCE_SHEET`」这类脏数据。
4. **为什么 `has_balance_check` 要单独一个字段而不是只靠 `report_code` 判断？** 因为未来可能新增「预算资产负债表」等其他需要恒等式校验的报表；把这个能力做成模板属性比硬编码 `report_code = 'BALANCE_SHEET'` 更可扩展。同时用 `ck_m17_report_def_balance_check` 强制资产负债表的这个标志必须为 `TRUE`。

**量级估算：** 5 类报表 × 平均 6 个版本 ≈ 30 行，单行约 500 字节，总计约 15 KB。**不分区。**

**设计说明**

1. **为什么 `subject_codes` 用逗号分隔字符串而不是子表？** 因为一行报表项目常常对应一组科目（如「货币资金」= `1001,1002`），且这一组在业务上是**一个整体**，不需要单独查询某个科目。用字符串 + GIN 索引可支持「反查哪个报表行用了这个科目」，比建子表省一张表、省一次 JOIN。代价是无法在数据库层校验科目是否存在——由应用层在保存时调 M17-01 校验。
2. **为什么 `value_column` 要可配置？** 资产负负债表取 `END_BALANCE`（期末余额）；收入费用总表取 `PERIOD_CREDIT`（本期贷方发生额，收入类）；现金流量表可能需 `PERIOD_DEBIT` 与 `PERIOD_CREDIT` 双向。四种取值方式覆盖全部场景。
3. **为什么 `direction` 要单独一个字段？** 「累计折旧」科目本身有贷方余额（正数），但在资产总计中必须作为**减项**。若靠科目类别自动判断会出错（折旧是资产类科目却要减）。显式 `direction` 让配置者明确表达意图，也让报表能通过「资产总计 = Σ ADD - Σ SUBTRACT」解释清楚。
4. **为什么 `line_type` 要区分 `SUBTOTAL` / `TOTAL`？** 因为小计与合计在打印时的样式不同（小计加下划线，合计加双下划线），且在勾稽校验中合计行需要与恒等式比对，小计行只与上级行比对。区分后报表渲染与校验各自清晰。

**量级估算：** 5 类报表 × 平均 6 个版本 × 平均 13 行 ≈ 400 行，单行约 400 字节，总计约 160 KB。**不分区。**

**设计说明**

1. **为什么 `ck_m17_report_instance_publish_balanced` 要禁止不平衡报表发布？** 这是本子模块最重要的安全阀。若允许发布不平衡的资产负债表，财务可能拿着「资产 ≠ 负债 + 权益」的报表去报税或报院长，这会触发审计问题。数据库层直接拒绝，比在 Service 里判断更可靠。
2. **为什么要有 `instance_seq` 而不是直接覆盖？** 报表可能因为「科目余额补录」「模板换版」而重新生成。覆盖会让历史报表消失；`instance_seq + 1` 保留全部历史，财务可对比「第一次生成的数与更正后的数」。约束 `uk_m17_report_instance_period` 保证同序号不重复。
3. **为什么 `check_result` 用 JSONB？** 不同报表的勾稽规则不同（资产负债表是恒等式、收入费用表是「收入 − 费用 = 结余」、现金流量表是「流入 − 流出 = 净增加」）。用 JSONB 存完整的左右值、差额、通过与否，能在日后审计时回答「当时是怎么校验的」，比只存一个 `is_balanced` 布尔值信息量大得多。
4. **为什么 `data_freshness_at` 要单独记录？** 因为报表是科目余额的投影，若生成报表时科目余额表还在更新（如 M17-05 正在过账），报表可能取到「半成品」数据。记录当时的余额表更新时间，让财务能判断「这张报表是不是在过账过程中生成的」。

**量级估算：**

| 项目 | 数值 | 说明 |
|---|---|---|
| 日报表量 | 0 | 财务报表按期间生成，非按日 |
| 月报表量 | 约 5 实例/月 × 12 月 = 60/年 | 5 类报表各 1 个实例 |
| 重生成倍数 | ×2~3 | 含补录后重算、模板换版 |

| 10 年总量 | 约 2,000 行 | — |
| 单行平均长度 | 约 900 字节 | 含 JSONB 勾稽明细 |

**分区：** 不分区（10 年约 2,000 行，体量极小）。报表归档通过 `PUBLISHED` 后转只读表空间实现，不依赖分区。

### 4.5 表：`m17_report_balance`（资产负债表快照表）

**用途：** 保存**资产负债表的三大合计与恒等式校验结果**。这是本子模块唯一一张带「会计恒等式强制」的表，与 `m17_report_instance` 是 1:0..1 关系（只有 `BALANCE_SHEET` 类型实例才有对应行）。

**为什么单独建表而不把三个合计放在 `m17_report_instance` 上：**

| 方案 | 问题 |
|---|---|
| 三个合计放 `m17_report_instance` | 收入费用总表、现金流量表、科室损益表、指标表这四类实例的这三列永远是 `NULL`，形成大量空列；且恒等式 CHECK 会对四类报表都生效，语义混乱 |
| **单独建 `m17_report_balance`** | 只有资产负债表有这一行，恒等式 CHECK 只约束这一张表，语义精确；且能附加资产负债表专属的校验列（流动资产、非流动资产、流动负债、非流动负债） |

**写入方：** M17-08 报表生成服务。**只读方：** 报表查询、P-08 契约、导出。

**设计说明**

1. **为什么恒等式要用两条 CHECK 而不是一条？** `ck_m17_report_balance_equation` 保证「资产 = 负债 + 权益」；`ck_m17_report_balance_assets_sum` 与 `ck_m17_report_balance_liab_sum` 保证三大合计与明细之和一致。两者结合形成闭环：若某个明细行取数错误，先被明细求和约束捕获；若合计层出错，被恒等式捕获。**任何一层出错都无法落库。**
2. **为什么要有 `ck_m17_report_balance_diff` 这条「差额字段与三大合计一致」的约束？** 因为 `balance_diff` 是冗余存储的。若只靠应用层计算写入，理论上存在「三大合计不平衡但 `balance_diff` 写成 0」的可能，从而绕过 `ck_m17_report_balance_flag`。这条 CHECK 让差额字段无法被独立伪造——它必须等于 `total_assets - total_liabilities - total_equity`，而后者又被恒等式约束为 0。
3. **为什么 `tolerance_amount` 固定为 0.00 而不是可配置？** 共享规范 §6.6 明确规定「校验容差：0.00（严格相等）」。允许配置容差会给「差 1 分也算平」开口子，而这 1 分在月末年结时会被放大成对不上账。字段保留只是为了记录「当时用的容差是多少」，值必须是 0。
4. **为什么允许 `total_equity` 为负数而仍加 `abs(...) < 1e15` 约束？** 医院可能因为累计亏损导致所有者权益为负（资不抵债），这在业务上是真实的，不应禁止。但 1e15 这个上限用来拦截「金额单位用错」（如把元当成分写入、或误写成 1.23e18 这类明显错误）。

**量级估算：** 每月 1 行资产负债表快照 × 12 = 12 行/年，10 年约 120 行，单行约 500 字节，总计约 60 KB。**不分区。**

**设计说明**

1. **为什么本表刻意不设 `updated_at` 与 `is_deleted`？** 报表明细是**会计档案**的一部分，《会计档案管理办法》要求财务报表及附注保留 10 年且不可篡改。若表上有 `is_deleted`，就存在「逻辑删除报表明细」的操作路径；没有字段是最强的约束。更正只能通过「生成新实例」实现，旧实例永久保留。
2. **为什么 `REVOKE UPDATE, DELETE` 在表上而不只在 Service 层？** 与共享规范 §3.5「已过账凭证不可变」同一个思路：Service 校验可被多入口、批量导入、数据修复脚本绕过；表级 `REVOKE` 是任何路径都拦得住的最后一道防线。
3. **为什么既有 `period_amount` 又有 `period_debit_amount` / `period_credit_amount`？** `period_amount` 是**按模板规则算出来的展示值**（如收入费用表取贷方发生额、现金流量表可能要借减贷）；而 `period_debit_amount` / `period_credit_amount` 是**原始快照**。三个都存，才能既满足不同报表的展示需求，又保留完整的原始数据供审计核对。
4. **为什么 `calc_trace` 要存 JSONB 明细？** 当财务质疑「货币资金 12,345,678.90 是怎么来的」时，只看 `source_subject_codes = '1001,1002'` 还不够——需要知道 1001 贡献多少、1002 贡献多少。`calc_trace` 保存逐科目的金额，让追溯在一条 SQL 内完成，无需再去查历史余额。
5. **为什么 `source_balance_id` 只能是一个 ID 而 `source_subject_codes` 是多个？** 因为一行报表往往聚合多个科目，对应科目余额表的**多行**。这里 `source_balance_id` 记录「主来源行」（通常是第一个科目），完整的聚合明细在 `calc_trace` 与 `source_row_count` 中。若需精确定位每个来源行，通过 `idx_m17_report_row_source` 反查 + `calc_trace` 展开。

### 4.7 表：`m17_report_indicator`（财务指标配置与结果表）

**用途：** 定义财务指标（资产负债率、流动比率、收入结余率、百元医疗收入消耗卫生材料、人员支出占业务支出比例等）的**计算公式与参考值区间**，并保存**每期的计算结果**。公式基于报表行号引用，不直接引用科目。

**为什么指标公式引用报表行号而不是科目：**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 直接引用科目余额 | 少一层依赖 | 指标口径与报表口径可能不一致（如「医疗收入」在报表中是 `4001+4002` 的合计，指标若单独取 `4001` 就会与报表对不上） |
| **引用报表行号** | 指标与报表**必然一致**，因为分母分子都来自同一张报表的同一行 | 换模板版本时需同步检查指标配置（由版本化解决） |

**写入方：** M17-08 财务科（指标配置）+ 报表生成服务（结果写入）。**只读方：** 指标分析页、经营看板、P-08 契约。

**设计说明**

1. **为什么配置行与结果行放在同一张表（用 `period IS NULL` 区分）？** 因为指标配置与结果的字段高度重叠（编码、名称、公式、单位都相同），分表会造成大量重复。用 `period IS NULL` 表示配置行、`period IS NOT NULL` 表示结果行，配合两个部分索引，查询效率与分表相当，但省一张表、省一次 JOIN。
2. **为什么公式引用报表行号而不是科目编码？** 「医疗收入」在资产负债表/收入费用表里是 `4001+4002` 的合计；若指标直接取 `4001`，就会与报表出现 2 分钱以上的差异，财务会立刻质疑。引用行号保证指标与报表**必然一致**——分子分母都来自同一张报表的同一行，从架构上消除了口径分歧。
3. **为什么分母为 0 时要记 `NO_DATA` 而不是报错？** 资产负债率的分母是资产总计，新建医院首月可能资产为 0。此时不是「计算失败」，而是「无数据可算」，业务上应正常展示为 `NO_DATA` 而不是让整个指标页 500。
4. **为什么 `calc_value` 用 `NUMERIC(9,6)` 而 `calc_amount` 用 `NUMERIC(18,2)`？** 与共享规范 §2.4 一致：比率 6 位小数（`NUMERIC(9,6)` 可表示 ±999.999999，足够覆盖资产负债率 0.423456）；金额 2 位小数（`NUMERIC(18,2)`）。两个字段分开而不是共用一个，是为了让数据库层的精度约束真正生效——若共用一个 `NUMERIC(18,6)`，金额就失去了「精确到分」的约束。

**量级估算：** 每月约 30 个指标 × 12 月 = 360 行/年（结果行）+ 约 30 行配置，10 年约 3,600 行，单行约 700 字节，总计约 2.5 MB。**不分区。**

**设计说明**

1. **为什么财务报表的导出留存期是 90 天而不是业务导出的 7 天？** 因为财务报表是**会计档案**，《会计档案管理办法》规定月度财务报表保留 10 年。文件本体保留 90 天后清理（节省存储），但**导出记录永久保留**，且保留 `file_sha256` 供日后核验「当时导出的文件内容」。若需长期保存原件，由归档流程单独处理。
2. **为什么 `is_masked` 默认 `FALSE`？** 财务报表（资产负债表、收入费用总表）本身不含患者个人信息，不需要脱敏。该字段保留是为了未来「科室损益报表」若含科室级患者量明细时可按需开启脱敏。
3. **为什么要有 `subscription_id` 与 `push_*` 三件套？** 院领导和财务主管通常希望「每月报表自动生成后推送到邮箱」。订阅推送与手工导出共用同一套文件生成与留痕机制，但需要额外记录「推给了谁、推成功没有」，便于排查「为什么院长没收到报表」。
4. **为什么水印是强制项（CHECK 约束）？** 财务报表是最高敏感度的经营数据，外泄是重大事故。水印（操作人 + 时间 + 报表名 + 期间）让任何一份流出的截图都能追溯到泄露源。CHECK 约束保证「不可能生成无水印的导出文件」。

**量级估算：** 每月约 30 次导出（5 报表 × 6 人）+ 订阅推送 12 次 ≈ 40 次/月 = 480 行/年，5 年约 2,400 行，单行约 800 字节，总计约 2 MB。**不分区。**

**ORM 模型要点说明**

| # | 要点 | 说明 |
|---|---|---|
| 1 | `ck_m17_report_balance_equation` 声明在 `__table_args__` | 会计恒等式在 ORM 层同步声明，Alembic 自动生成 DDL |
| 2 | `M17ReportRow` 无 `updated_at` / `is_deleted` | 只增不改；`created_at` 注释明确「只增不改」 |
| 3 | 金额统一 `Numeric(18, 2)` | 与共享规范 §2.4 一致；**杜绝 `Float`/`Double`/`Real`** |
| 4 | 比率统一 `Numeric(9, 6)` | 资产负债率等 6 位小数 |
| 5 | `JSONB` 用于 `check_result` / `calc_trace` / `gen_params` | 结构可变的结构化数据 |
| 6 | 无物理外键 | 共享规范 §2.6 规定不建物理外键，逻辑外键由应用层保证 |
| 7 | `server_default=text("CURRENT_TIMESTAMP")` | 时间戳由数据库生成，不用 Python 时间 |

### C.2 核心查询 SQL

**① 资产负债表取数（按模板行项目聚合科目余额）**

```sql
-- 按模板行定义，从科目余额表聚合出该行金额
-- subject_codes 为逗号分隔（如 '1001,1002'），用 string_to_array 展开
SELECT d.line_no,
       d.line_name,
       d.direction,
       COALESCE(SUM(lb.open_balance), 0.00) AS open_amount,
       COALESCE(SUM(lb.period_debit), 0.00) AS period_debit_amount,
       COALESCE(SUM(lb.period_credit), 0.00) AS period_credit_amount,
       COALESCE(SUM(lb.end_balance), 0.00) AS end_amount,
       COUNT(lb.id) AS source_row_count,
       MIN(lb.id) AS source_balance_id
FROM m17_report_def_line d
LEFT JOIN m17_ledger_balance lb
       ON lb.period = :period
      AND lb.subject_code = ANY (string_to_array(d.subject_codes, ','))
      AND lb.is_deleted = FALSE
WHERE d.def_id = :def_id
  AND d.calc_type = 'SUBJECT'
  AND d.is_deleted = FALSE
GROUP BY d.line_no, d.line_name, d.direction, d.print_order
ORDER BY d.print_order;
```

**② 资产负债表恒等式校验**

```sql
-- 生成实例后校验：资产合计 = 负债合计 + 所有者权益合计
SELECT i.instance_no,
       i.period,
       b.total_assets,
       b.total_liabilities,
       b.total_equity,
       b.total_assets - b.total_liabilities - b.total_equity AS balance_diff,
       CASE WHEN b.total_assets = b.total_liabilities + b.total_equity
            THEN TRUE ELSE FALSE END AS is_balanced
FROM m17_report_instance i
JOIN m17_report_balance b ON b.instance_id = i.id
WHERE i.period = :period
  AND i.report_code = 'BALANCE_SHEET';
```

**③ 追查某个报表行的来源（可追溯性验证）**

```sql
-- 某报表实例某行的金额来自哪些科目余额
SELECT r.line_no,
       r.line_name,
       r.end_amount,
       r.source_subject_codes,
       r.source_row_count,
       r.calc_trace
FROM m17_report_row r
WHERE r.instance_id = :instance_id
  AND r.line_no = :line_no;
```

**④ 反查：某个科目余额行被哪些报表使用过**

```sql
-- 审计场景：某条科目余额是否被正确归入报表
SELECT r.report_code,
       r.period,
       r.line_no,
       r.line_name,
       r.end_amount
FROM m17_report_row r
WHERE r.source_balance_id = :balance_id
ORDER BY r.period DESC, r.report_code;
```

**⑤ 财务指标计算（引用报表行号）**

```sql
-- 资产负债率 = 负债合计行 / 资产总计行
WITH row_vals AS (
    SELECT line_no, end_amount
    FROM m17_report_row
    WHERE instance_id = :instance_id
      AND line_no IN ('30', '50')   -- 30: 负债合计  50: 资产总计
)
SELECT ROUND(
           (SELECT end_amount FROM row_vals WHERE line_no = '30')
           / NULLIF((SELECT end_amount FROM row_vals WHERE line_no = '50'), 0),
           6
       ) AS asset_liability_ratio;
```

**⑥ 指标异常清单**

```sql
SELECT period,
       indicator_code,
       indicator_name,
       indicator_category,
       calc_value,
       calc_amount,
       level,
       normal_min,
       normal_max
FROM m17_report_indicator
WHERE period = :period
  AND level IN ('WARNING', 'CRITICAL')
  AND is_deleted = FALSE
ORDER BY
    CASE level WHEN 'CRITICAL' THEN 1 WHEN 'WARNING' THEN 2 ELSE 3 END,
    indicator_category,
    sort_no;
```

## 附录 E：建表依赖顺序与 Alembic 迁移

### E.1 建表依赖顺序（4 层）

```
第 0 层（外部依赖，必须先于本子模块建表或已存在）
  ├── M17-01  m17_account_subject（科目表）
  ├── M17-01  m17_account_period（会计期间表）
  ├── M17-05  m17_ledger_balance（科目余额表，报表唯一数据源）
  ├── M17-04  m17_dept_profit（科室损益表）
  ├── M01-01  mdm_dept（科室）
  └── 扩展    CREATE EXTENSION IF NOT EXISTS pg_trgm

第 1 层（无本模块内依赖，先建）
  ├── m17_report_def            （模板定义，独立）
  └── m17_report_indicator      （指标配置，独立，结果为后续写入）

第 2 层（依赖第 1 层）
  └── m17_report_def_line       （依赖 m17_report_def.id）

第 3 层（依赖第 1、2 层）
  └── m17_report_instance       （依赖 m17_report_def.id）

第 4 层（依赖第 3 层，含恒等式强制与只增表）
  ├── m17_report_balance        （依赖 m17_report_instance.id，含恒等式 CHECK）
  ├── m17_report_row            （依赖 m17_report_instance.id，只增不改 + REVOKE）
  └── m17_report_export         （依赖 m17_report_instance.id）
```

> 本模块不建数据库外键，因此物理上可按任意顺序建表；上表表达的是**逻辑依赖**与迁移脚本的推荐执行顺序，便于回滚与故障定位。

### E.3 迁移脚本示例（恒等式约束 + 只增表 + REVOKE）

```python
"""M17-08 财务报表与经营分析 —— 资产负债表与报表行数据建表迁移。"""

from alembic import op

revision = "20261101_m17_08_005"
down_revision = "20261101_m17_08_004"


def upgrade() -> None:
    """建 m17_report_balance（恒等式强制）与 m17_report_row（只增不改）。"""
    # ---------- 资产负债表快照表：会计恒等式强制 ----------
    op.execute("""
        CREATE TABLE IF NOT EXISTS m17_report_balance (
            id                        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
            instance_id               BIGINT        NOT NULL,
            instance_no               VARCHAR(32)   NOT NULL,
            period                    VARCHAR(7)    NOT NULL,
            current_assets            NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            non_current_assets        NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            total_assets              NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            current_liabilities       NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            non_current_liabilities   NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            total_liabilities         NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            paid_in_capital           NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            special_fund              NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            accumulated_surplus       NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            current_year_surplus      NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            total_equity              NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            balance_diff              NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            is_balanced               BOOLEAN       NOT NULL DEFAULT FALSE,
            tolerance_amount          NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            check_detail              JSONB,
            checked_at                TIMESTAMP,
            prev_period_total_assets  NUMERIC(18,2),
            prev_period_total_liabilities NUMERIC(18,2),
            prev_period_total_equity  NUMERIC(18,2),
            assets_growth_ratio       NUMERIC(9,6),
            source_balance_count      INT           NOT NULL DEFAULT 0,
            data_freshness_at         TIMESTAMP,
            created_at                TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
            updated_at                TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
            is_deleted                BOOLEAN       NOT NULL DEFAULT FALSE
        );
    """)

    # 【核心】会计恒等式：资产合计 = 负债合计 + 所有者权益合计
    op.execute("""
        ALTER TABLE m17_report_balance
            ADD CONSTRAINT ck_m17_report_balance_equation
            CHECK (total_assets = total_liabilities + total_equity);
    """)
    op.execute("""
        ALTER TABLE m17_report_balance
            ADD CONSTRAINT ck_m17_report_balance_assets_sum
            CHECK (total_assets = current_assets + non_current_assets);
    """)
    op.execute("""
        ALTER TABLE m17_report_balance
            ADD CONSTRAINT ck_m17_report_balance_liab_sum
            CHECK (total_liabilities = current_liabilities + non_current_liabilities);
    """)
    op.execute("""
        ALTER TABLE m17_report_balance
            ADD CONSTRAINT ck_m17_report_balance_equity_sum
            CHECK (total_equity = paid_in_capital + special_fund
                                 + accumulated_surplus + current_year_surplus);
    """)
    op.execute("""
        ALTER TABLE m17_report_balance
            ADD CONSTRAINT ck_m17_report_balance_diff
            CHECK (balance_diff = total_assets - total_liabilities - total_equity);
    """)
    op.execute("""
        ALTER TABLE m17_report_balance
            ADD CONSTRAINT ck_m17_report_balance_tolerance
            CHECK (tolerance_amount = 0.00);
    """)
    op.execute("""
        CREATE UNIQUE INDEX uk_m17_report_balance_instance
            ON m17_report_balance (instance_id)
            WHERE is_deleted = FALSE;
    """)

    # ---------- 报表行数据表：只增不改 ----------
    op.execute("""
        CREATE TABLE IF NOT EXISTS m17_report_row (
            id                      BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
            instance_id             BIGINT        NOT NULL,
            def_line_id             BIGINT,
            report_code             VARCHAR(32)   NOT NULL,
            period                  VARCHAR(7)    NOT NULL,
            line_no                 VARCHAR(16)   NOT NULL,
            line_name               VARCHAR(128)  NOT NULL,
            line_level              SMALLINT      NOT NULL DEFAULT 1,
            line_type               VARCHAR(24)   NOT NULL DEFAULT 'DETAIL',
            open_amount             NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            period_debit_amount     NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            period_credit_amount    NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            period_amount           NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            end_amount              NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            ytd_amount              NUMERIC(18,2) NOT NULL DEFAULT 0.00,
            prev_amount             NUMERIC(18,2),
            source_balance_id       BIGINT,
            source_subject_codes    VARCHAR(512),
            source_row_count        INT           NOT NULL DEFAULT 0,
            calc_trace              JSONB,
            calc_type               VARCHAR(24)   NOT NULL DEFAULT 'SUBJECT',
            direction               VARCHAR(8)    NOT NULL DEFAULT 'ADD',
            is_zero_line            BOOLEAN       NOT NULL DEFAULT FALSE,
            print_order             INT           NOT NULL DEFAULT 0,
            is_checked              BOOLEAN       NOT NULL DEFAULT FALSE,
            check_message           VARCHAR(256),
            created_at              TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP
        );
    """)

    # 可追溯性铁律：按科目取数的行必须有来源余额 ID
    op.execute("""
        ALTER TABLE m17_report_row
            ADD CONSTRAINT ck_m17_report_row_source
            CHECK (calc_type <> 'SUBJECT'
                   OR (source_balance_id IS NOT NULL
                       AND source_subject_codes IS NOT NULL));
    """)

    op.execute("""
        CREATE UNIQUE INDEX uk_m17_report_row_line
            ON m17_report_row (instance_id, line_no);
    """)
    op.execute("""
        CREATE INDEX idx_m17_report_row_instance
            ON m17_report_row (instance_id, print_order);
    """)
    op.execute("""
        CREATE INDEX idx_m17_report_row_source
            ON m17_report_row (source_balance_id)
            WHERE source_balance_id IS NOT NULL;
    """)

    # 【核心】只增不改：回收 UPDATE / DELETE 权限
    op.execute("REVOKE UPDATE, DELETE ON m17_report_row FROM app_user;")


def downgrade() -> None:
    """回滚：先恢复权限再删表。"""
    op.execute("GRANT UPDATE, DELETE ON m17_report_row TO app_user;")
    op.execute("DROP TABLE IF EXISTS m17_report_row CASCADE;")
    op.execute("DROP TABLE IF EXISTS m17_report_balance CASCADE;")
```

### F.3 数据质量巡检（每月结账后）

| 巡检项 | 判定 | 处置 |
|---|---|---|
| 资产负债表恒等式 | 必须成立（`balance_diff = 0.00`） | 不成立则阻断发布，返回 `"1708001"` |

| 资产总计与明细之和 | 必须相等 | 不相等则拒绝落库（CHECK 已强制） |
| 指标与报表口径一致 | 指标分子分母取自同一实例 | 抽样比对，不一致告警 |
| 报表实例与科目余额时点 | `data_freshness_at` 应早于 `generated_at` | 晚于则提示「报表可能使用了滞后余额」 |

| 未发布报表积压 | 期间结账后 5 天内应发布 | 超期告警财务科 |
