## 1. 表清单

| 序号 | 表名 | 中文名 | 用途 | 预估行数 |
|---|---|---|---|---|
| 1 | `m17_bank_account` | 银行账户表 | 对账主体：开户行、账号、币种、账户性质、账面科目映射 | 小（约 20 行） |
| 2 | `m17_bank_statement` | 银行流水表 | 银行对账单逐笔流水，**按月 RANGE 分区 + DEFAULT** | 大（约 18 万/年） |
| 3 | `m17_recon_book_ledger` | 对账账面台账表 | 从 M17-05 总账取出的账面资金流水（对账的「企业侧」） | 大（约 12 万/年） |
| 4 | `m17_recon_match` | 对账匹配记录表 | 银行流水与账面台账的匹配关系（1:1 / 1:N / N:1） | 中（约 16 万/年） |
| 5 | `m17_recon_pending_item` | 未达账项表 | 四类未达账项的登记与核销 | 中（约 3 万/年） |
| 6 | `m17_recon_statement` | 余额调节表主表 | 每账户每期间一张调节表，含活期恒等式校验字段 | 小（约 240/年） |
| 7 | `m17_recon_channel` | 支付渠道对账表 | 第三方支付渠道（微信/支付宝/银联）对账结果与平台手续费 | 中（约 9 千/年） |
| 8 | `m17_recon_cash_diff` | 长短款登记表 | 收费长短款与渠道差异的登记、认定与账务处理 | 小（约 1.2 千/年） |
| 9 | `m17_recon_log` | 对账操作日志表 | 导入、匹配、确认、调节表生成的全过程留痕，**只增不改** | 大（约 30 万/年） |

**合计：9 张表**

> **为什么是 9 张而不是更少？** 银行对账的本质是「两套独立账本的核对」。银行流水（外部证据）与账面台账（内部记账）
> 必须**分表存**，否则无法表达「银行有、企业无」与「企业有、银行无」这两种天然不对称的事实；匹配记录是二者之间的
> 多对多关联，未达账项是匹配之后的差额归因，调节表是期间级的汇总校验，渠道对账与长短款是现金/第三方渠道的补充对账面。
> 一张表只表达一件事，9 张是「不可再合并」的下限。

**设计要点说明：**

1. **银行流水与账面台账为什么分成两张表？**
   二者是**两套独立账本**，来源、粒度和更新节奏完全不同：银行流水来自银行（文件导入或银行接口，外部证据，不可修改），
   账面台账来自 M17-05 总账（内部记账，随凭证过账更新）。合成一张表就只能用「一个 `source` 字段 + 大量可空列」
   的写法，无法同时对两侧建「银行流水号唯一」与「凭证分录唯一」的约束，也无法表达「同一笔业务银行记 1 笔、
   企业记 2 笔」的 N:1 匹配。分表是唯一能表达双向不对称的方案。

2. **为什么匹配关系单独建表而不是在流水表上加 `book_ledger_id`？**
   匹配是**多对多**：一笔银行汇总入账（如批量代发工资）可能对应企业侧多笔凭证（N:1）；企业一笔分录也可能因银行
   分次到账而被拆成多笔流水（1:N）。在流水表上挂单个外键只能表达 1:1。匹配表还能记录 `match_score` / `match_method`，
   保留「这笔是自动匹配的还是人工配的、分数多少」的审计信息。

3. **未达账项为什么是独立表而不是流水表上的一个状态？**
   未达账项的本质是「**一侧有、另一侧没有**」，它必须能独立存在于任一侧：
   `BANK_CREDIT_NOT_BOOK` 与 `BANK_DEBIT_NOT_BOOK` 有银行流水号但无账面分录；
   `BOOK_DEBIT_NOT_BANK` 与 `BOOK_CREDIT_NOT_BANK` 有账面分录但无银行流水。
   若挂在流水表上，后两类根本没有流水可挂。独立表用可空的 `statement_id` / `book_ledger_id` 双指针表达四种组合。

4. **为什么余额调节表的恒等式字段要落库而不是查询时计算？**
   调节表是**财务归档单据**，一旦确认（`CONFIRMED`）即成为审计证据，其数值必须冻结。若查询时从明细重算，
   而明细在后续月份被补登（如银行流水跨月到达），历史调节表的数字就会变化，导致「同一个期间的调节表每次查都不一样」，
   审计无法通过。落库 + 数据库 CHECK 保证归档后的恒等式成立且不可漂移。

### 4.2 表：`m17_bank_account`（银行账户表）

**用途：** 银行对账的**主体**。记录医院在各银行开立的账户（基本户、一般户、专用户），以及该账户对应的会计科目
（通常是 `1002 银行存款` 下的明细科目）。未达账项、余额调节表、渠道对账都以账户 + 会计期间为维度组织。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | N | IDENTITY | 主键 |

| `account_name` | VARCHAR(128) | N | — | 账户名称（对账展示用），如「南石眼科医院基本户」 |

**约束说明**

```sql
ALTER TABLE m17_bank_account
    ADD CONSTRAINT ck_m17_bank_account_no_format
    CHECK (account_no ~ '^BA[0-9]{4}$');

ALTER TABLE m17_bank_account
    ADD CONSTRAINT ck_m17_bank_account_type
    CHECK (account_type IN ('BASIC', 'GENERAL', 'SPECIAL', 'TEMPORARY'));

ALTER TABLE m17_bank_account
    ADD CONSTRAINT ck_m17_bank_account_status
    CHECK (status IN ('ACTIVE', 'FROZEN', 'CLOSED'));

ALTER TABLE m17_bank_account
    ADD CONSTRAINT ck_m17_bank_account_import_mode
    CHECK (statement_import_mode IN ('FILE', 'API', 'MANUAL'));

-- 销户必须填销户日期，且销户日期不得早于开户日期
ALTER TABLE m17_bank_account
    ADD CONSTRAINT ck_m17_bank_account_close
    CHECK (status <> 'CLOSED'
           OR (close_date IS NOT NULL
               AND (open_date IS NULL OR close_date >= open_date)));

-- 账号后 4 位必须是账号真实后缀（应用层校验，此处保证长度）
ALTER TABLE m17_bank_account
    ADD CONSTRAINT ck_m17_bank_account_tail
    CHECK (char_length(bank_account_tail) BETWEEN 4 AND 8);

-- 账户性质为专用户时必须写明用途（专户需可追溯用途）
ALTER TABLE m17_bank_account
    ADD CONSTRAINT ck_m17_bank_account_special
    CHECK (account_type <> 'SPECIAL' OR account_purpose IS NOT NULL);
```

**设计说明**

1. **为什么 `bank_account` 加密存储而 `bank_account_tail` 明文？**
   银行账号属于《个人信息保护法》下的敏感信息，完整账号泄露可被用于伪冒转账。但财务对账又必须能让
   会计一眼确认「这是哪个账户」，因此存一个明文后 4 位用于展示与人工核对，完整账号用 AES-256-GCM 加密，
   只有生成付款指令时由授权角色解密。这样即使数据库被拖，也拿不到可用账号。

2. **为什么 `subject_code` 是必填？**
   对账的另一侧是「账面」——没有科目就取不出账面余额，也就无法生成余额调节表。强制必填可以在建户时
   就暴露「这个账户还没在科目体系里建明细科目」的问题，而不是等到月末对账时才发现。「一个银行账户必须
   对应一个科目」是本子模块的基本假设，写进数据模型比写在文档里更可靠。

3. **为什么 `book_balance` / `bank_balance` 是快照而不是实时值？**
   它们只是列表页展示与调节表期初校验的便捷值，真正的权威值在 `m17_ledger_balance`（账面）与最近一期
   对账单（银行侧）。做成快照可避免列表页每次调 M17-05，同时用「快照 + 每日对账任务刷新」保证误差可控。
   命名不带 `_snap` 是因为本模块自身就是财务权威方，这里的快照是「同一系统内的缓存」，不跨模块。

ALTER TABLE m17_bank_statement
    ADD CONSTRAINT ck_m17_bank_statement_matched

ALTER TABLE m17_bank_statement
    ADD CONSTRAINT ck_m17_bank_statement_value_date
    CHECK (value_date IS NULL

**分区策略**

| 项 | 内容 |
|---|---|
| 分区键 | `trans_date`（交易日期） |
| 分区方式 | `RANGE`，按月；每月最后一个自然日为边界 |
| 保留期 | 10 年（满足《会计档案管理办法》原始凭证保管期限） |
| DEFAULT 分区 | **必须有**，名为 `m17_bank_statement_default`，兜底异常日期与分区预建失败 |
| 预建任务 | APScheduler 每月 25 日 02:00 `ensure_bank_statement_partition` 预建下月分区 |
| 归档任务 | 超 10 年分区 `DETACH` 后转冷存，不 `DROP` |

**设计说明**

1. **为什么分区键选 `trans_date` 而不是 `created_at`？**
   对账的业务维度是「**交易日期所在的会计期间**」：查 10 月的流水、算 10 月的调节表、判断 10 月的未达账项，
   全部以 `trans_date` 为条件。若按 `created_at` 分区，一笔 10 月 31 日交易、11 月 2 日才导入的流水会落到 11 月分区，
   导致 10 月对账必须扫两个分区，且分区裁剪完全失效。按业务日期分区，让「一个期间 = 一个分区」成为物理事实。

2. **为什么金额分 `amount`（无符号）+ `signed_amount`（带符号）两列？**
   银行文件里金额普遍是正数 + 独立的收付标志，直接存无符号金额是忠于原始凭证的（可回溯银行文件）。
   但所有汇总与恒等式校验都需要「带符号求和」，若每次都写 `CASE WHEN dc_flag='C' THEN amount ELSE -amount END`，
   表达式无法建索引，聚合慢且易写错符号。两列并存 + CHECK 约束 `signed_amount = ±amount` 保证自洽，
   既忠实原文又便于核算。

3. **为什么 `uk_m17_bank_statement_serial` 是部分唯一索引（`WHERE is_void = FALSE`）？**
   同一账户的银行流水号是银行给的唯一凭证号，重复导入会直接破坏对账（一笔业务被算两次）。用唯一索引把
   「重复导入」挡在数据库层，而不是靠应用层查重（并发导入下查重必然漏）。带 `is_void = FALSE` 条件是为了
   让「整批撤销后重新导入」成为合法操作——撤销的旧流水不参与唯一性。

4. **为什么 `raw_data` 用 JSONB 保留原始行？**
   各银行对账单字段差异极大，且银行会不定期改版（增列、改列名、改编码）。解析器一旦出错，若历史流水只存了
   解析后的字段，就无法追溯「当时的原始数据长什么样」，也无法在修正解析器后重跑。原样保存 `raw_data` 后，
   解析器升级可以对历史批次重新解析（写入新批次并撤销旧批次），这是对账数据可信度的最后一道保障。

5. **为什么 `is_matched` 是冗余字段而不是每次 JOIN 匹配表判断？**
   自动匹配的核心查询是「取出该账户所有未匹配流水」（待处理池），若每次都 `LEFT JOIN m17_recon_match ...
   WHERE match.id IS NULL`，在 18 万行/年的流水上会产生大量反连接。冗余一个布尔 + 部分索引
   `WHERE is_matched = FALSE`，使待处理池索引体积只有全表的 5%~10%，扫描量下降一个数量级。一致性由
   Service 层在同一事务内更新，并由每日对账任务校验「`is_matched` 与匹配表行数一致」。

**设计说明**

1. **为什么不直接 JOIN `m17_voucher_entry` 对账，而要抽一张台账？**
   原因有三：①总账分录包含全部科目（收入、成本、费用），对账只关心银行存款科目，抽出来才能只对相关数据建索引；
   ②总账是**追加式**的，凭证一旦过账分录不再变动，但科目体系或辅助核算口径可能调整，抽取时把当时的
   `counter_party` / `biz_ref_no` 快照下来，避免历史对账结果随口径漂移；③抽取动作本身可审计（有 `extract_batch_no`），
   「哪些分录参与了本次对账」有据可查。

2. **为什么记录 `signed_amount` 而不是只有 `dc_flag` + `amount`？**
   对账的核心运算是对两侧求和后比较：`SUM(银行 signed_amount)` vs `SUM(账面 signed_amount)`。
   若只有方向符号字段，聚合时需写 `CASE` 表达式（不可索引、易错符号）。统一成「资金流入为正、流出为负」的
   带符号口径后，两侧可直接相加、相减做差额，这也是余额调节表恒等式能写成简单 SQL 的前提。

3. **为什么 `ck_m17_recon_book_ledger_date_in_period` 要强制记账日期在所属期间内？**
   跨期错账是财务审计的高频问题：一张 10 月凭证的业务日期若被记成 11 月，`period` 与 `book_date` 就会不一致，
   进而导致 10 月账面少、11 月账面多，两个期间的调节表都不平。数据库层强制二者一致，把跨期问题挡在抽取环节。

4. **为什么 `uk_m17_recon_book_ledger_entry` 是部分唯一索引（`WHERE is_extracted = TRUE`）？**
   自动抽取任务可能因超时重跑，重复抽取会让同一笔分录在台账里出现两次，账面金额凭空翻倍。唯一索引保证
   「一笔分录只能被抽一次」。带条件是因为手工补登的记录 `voucher_entry_id` 可能重复引用同一凭证（如同一凭证
   拆成两笔资金业务），手工补登属于人工判断，不纳入自动抽取的唯一性约束。

**匹配项明细的存储方式**

匹配记录与流水/台账之间是多对多，需要一个关联明细。**本设计不单独建关联表**，而是在两张主表上各冗余
`match_id`，通过匹配记录号反向关联。理由与做法：

| 方案 | 做法 | 取舍 |
|---|---|---|
| 独立关联表 | 新建 `m17_recon_match_item(match_id, statement_id, book_ledger_id)` | 表数从 9 增至 10，但每次查询都要 JOIN 两次 |
| **冗余 `match_id` 列（本设计）** | 在 `m17_bank_statement` / `m17_recon_book_ledger` 上各加 `match_id BIGINT`，匹配时同事务写入 | **少一张表**；查询「这笔流水匹配了哪几笔分录」只需按 `match_id` 索引即可 |

```sql
-- 两表在实际建表时各增加一列（已在 4.5 节说明，DDL 见附录 E 的增量 ALTER）
ALTER TABLE m17_bank_statement
    ADD COLUMN match_id BIGINT;
ALTER TABLE m17_recon_book_ledger
    ADD COLUMN match_id BIGINT;

CREATE INDEX idx_m17_bank_statement_match
    ON m17_bank_statement (match_id) WHERE match_id IS NOT NULL;
CREATE INDEX idx_m17_recon_book_ledger_match
    ON m17_recon_book_ledger (match_id) WHERE match_id IS NOT NULL;
```

**设计说明**

1. **为什么匹配记录要单独一张表，而不是在流水上直接记 `book_ledger_id`？**
   一笔银行汇总入账（如一次代发工资 87 人合计 512,300.00 元）对应企业侧 87 笔分录；一笔企业分录也可能因银行
   分两次到账而对应两笔流水。在流水表上挂单个 ID 只能表达一对一，且无法记录「这组匹配整体的金额是否平衡」。
   匹配表把一组匹配作为一个整体对象，`statement_count` / `book_count` / `amount_diff` 三个字段恰好表达
   「几个对几个、差额多少」，这是 1:N / N:1 场景下唯一能自洽建模的方式。

2. **为什么 `ck_m17_recon_match_balanced` 要强制已确认匹配的 `amount_diff = 0`？**
   匹配的含义是「这两笔是同一件事」，同一件事的金额必须完全相等（精确到分）。若允许差额不为 0 还标
   `CONFIRMED`，那么「差 0.01 元」的匹配会沉淀下来，累积到调节表时表现为无法归因的尾差。强制为 0 后，
   任何差额必须拆分处理：要么走「部分匹配」（拆成多条匹配记录），要么登记为未达账项或长短款，账目始终清晰。

3. **为什么 `match_score` 与四个 `score_*` 因子都要存？**
   `match_score` 用于阈值判断与排序，四个因子用于**事后调优**：当运营发现「自动匹配率只有 62%，人工压力大」时，
   需要知道是金额因子（权重 0.60）定得太高，还是日期容差（±3 天）太窄。有分项分数就能跑
   「如果把日期容差放宽到 ±5 天，自动率会提到多少」的模拟分析。只存总分则无法归因。

4. **为什么低分自动匹配要落到 `SUSPECTED` 而不是直接 `CONFIRMED`？**
   自动匹配是概率判断。金额相同、日期相近、对方户名也相似，仍可能是「同一天同金额的两笔不同交易」。
   对这类「综合分在 0.60~0.80 之间」的匹配标为 `SUSPECTED`，进入《P04 自动匹配》页的待复核队列，
   由会计逐条确认。这样既享受自动化的效率，又不让机器决定账务。

**四类未达账项的方向关系（恒等式推导依据）**

| 类型 | 中文 | 谁有 | 谁没有 | 银行侧调节 | 企业侧调节 | 调节表加在哪一侧 |
|---|---|---|---|---|---|---|
| `BANK_CREDIT_NOT_BOOK` | 银行已收企业未收 | 银行流水（C） | 账面 | `0.00` | `+amount` | 加在**企业账面余额** |
| `BANK_DEBIT_NOT_BOOK` | 银行已付企业未付 | 银行流水（D） | 账面 | `0.00` | `-amount` | 减在**企业账面余额** |
| `BOOK_DEBIT_NOT_BANK` | 企业已收银行未收 | 账面（D） | 银行流水 | `+amount` | `0.00` | 加在**银行对账单余额** |
| `BOOK_CREDIT_NOT_BANK` | 企业已付银行未付 | 账面（C） | 银行流水 | `-amount` | `0.00` | 减在**银行对账单余额** |

**设计说明**

1. **为什么把两侧调节影响做成两个数值字段（`bank_side_effect` / `book_side_effect`）而不是只存类型？**
   恒等式的计算需要按类型分组求和：`银行侧调整合计 = Σ BOOK_DEBIT_NOT_BANK − Σ BOOK_CREDIT_NOT_BANK`，
   `企业侧调整合计 = Σ BANK_CREDIT_NOT_BOOK − Σ BANK_DEBIT_NOT_BOOK`。如果只存类型，每次都要写四段 `CASE`
   或四个子查询。落成两个字段后，调节表的两个调整项各是一条 `SUM`，SQL 简洁且可用索引。CHECK 约束保证这两列
   与类型严格自洽，不存在「类型写 A、方向写成 B」的脏数据。

2. **为什么银行侧账项必须有 `statement_id`、企业侧账项必须有 `book_ledger_id`？**
   这是「未达」的定义决定的：`BANK_*` 类账项的存在理由是「银行有这笔、企业没有」，因此必然有银行流水；
   `BOOK_*` 类则相反。用 CHECK 强制后，任何「既无流水又无台账」的空账项都无法落库，从数据层杜绝了
   「凭空造一条未达账项来调平账目」的舞弊路径。

3. **为什么 `uk_m17_recon_pending_statement` 是部分唯一索引（`WHERE status = 'OPEN'`）？**
   一笔流水同时只能有一个未核销的未达账项，否则月末汇总会把同一笔金额算两次。但一个流水在不同期间可能
   反复成为未达账项（如 10 月登记为银行已收企业未收，11 月核销时发现核销金额有误，重新登记），因此历史记录
   必须保留。带 `status = 'OPEN'` 条件后，只有「当前未核销」的那一条受唯一性约束，历史记录不受影响。

4. **为什么要记 `clear_voucher_no`？**
   未达账项的核销往往伴随补记账凭证：`BOOK_DEBIT_NOT_BANK`（企业已收银行未收）在次月银行入账后核销，
   企业侧要么已记（则无需补记），要么需补记；`BANK_CREDIT_NOT_BOOK`（银行已收企业未收）核销时必须
   补记收款凭证。记录核销凭证号后，「这条账项是怎么消失的」可以一路追到具体凭证分录，满足审计追溯要求。

### 4.7 表：`m17_recon_statement`（余额调节表主表）

**用途：** 每个**银行账户 × 会计期间**一张余额调节表。它把「银行对账单余额」与「企业账面余额」通过四类未达账项
调整到相等，是银行存款科目余额真实性的**法定证明文件**，也是审计必查单据。

> **本表的核心是恒等式。** 数据库必须能证明调节后两侧相等，否则这张调节表不成立。

**恒等式（落库为 8 个金额字段 + 1 条 CHECK）**

```
银行对账单余额 + 企业已收银行未收 − 企业已付银行未付
    = 企业账面余额 + 银行已收企业未收 − 银行已付企业未付
```

对应字段：`bank_balance + book_debit_not_bank − book_credit_not_bank`
`= book_balance + bank_credit_not_book − bank_debit_not_book`

    ADD CONSTRAINT ck_m17_recon_statement_bank_side
    CHECK (bank_side_adjusted
           = bank_balance + book_debit_not_bank - book_credit_not_bank);

-- 企业侧调节后余额 = 企业账面余额 + 银行已收企业未收 − 银行已付企业未付
ALTER TABLE m17_recon_statement
    ADD CONSTRAINT ck_m17_recon_statement_book_side
    CHECK (book_side_adjusted
           = book_balance + bank_credit_not_book - bank_debit_not_book);

-- 调节后差额 = 银行侧 − 企业侧
ALTER TABLE m17_recon_statement
    ADD CONSTRAINT ck_m17_recon_statement_adjust_diff
    CHECK (adjust_diff = bank_side_adjusted - book_side_adjusted);

-- 【核心】余额调节表恒等式：两侧调节后必须相等
-- 银行对账单余额 + 企业已收银行未收 − 企业已付银行未付
--   = 企业账面余额 + 银行已收企业未收 − 银行已付企业未付
ALTER TABLE m17_recon_statement
    ADD CONSTRAINT ck_m17_recon_statement_identity
    CHECK (bank_balance + book_debit_not_bank - book_credit_not_bank
           = book_balance + bank_credit_not_book - bank_debit_not_book);

-- is_balanced 标记与差额自洽
ALTER TABLE m17_recon_statement
    ADD CONSTRAINT ck_m17_recon_statement_balanced_flag
    CHECK ((is_balanced = TRUE AND adjust_diff = 0.00)
           OR (is_balanced = FALSE));

-- 已生成及之后状态必须恒等式成立（草稿允许不平，用于过程展示）
ALTER TABLE m17_recon_statement
    ADD CONSTRAINT ck_m17_recon_statement_generated_balanced
    CHECK (status IN ('DRAFT', 'VOID')
           OR (is_balanced = TRUE
               AND bank_balance + book_debit_not_bank - book_credit_not_bank
                   = book_balance + bank_credit_not_book - bank_debit_not_book));

-- 四类未达账项合计均为非负数（方向由恒等式中的加减号决定）
ALTER TABLE m17_recon_statement
    ADD CONSTRAINT ck_m17_recon_statement_pending_nonneg
    CHECK (book_debit_not_bank >= 0
           AND book_credit_not_bank >= 0
           AND bank_credit_not_book >= 0
           AND bank_debit_not_book >= 0);

-- 笔数统计非负
ALTER TABLE m17_recon_statement
    ADD CONSTRAINT ck_m17_recon_statement_counts
    CHECK (pending_item_count >= 0
           AND matched_count >= 0
           AND statement_count >= 0
           AND book_ledger_count >= 0
           AND unmatched_statement_count >= 0
           AND unmatched_book_count >= 0);

-- 匹配率区间
ALTER TABLE m17_recon_statement
    ADD CONSTRAINT ck_m17_recon_statement_match_rate
    CHECK (match_rate IS NULL OR (match_rate >= 0 AND match_rate <= 1));

-- 复核 / 确认 / 作废各自必须有操作人与时间
ALTER TABLE m17_recon_statement
    ADD CONSTRAINT ck_m17_recon_statement_reviewed
    CHECK (status IN ('DRAFT', 'GENERATED')
           OR status = 'VOID'
           OR (reviewed_by IS NOT NULL AND reviewed_at IS NOT NULL));

ALTER TABLE m17_recon_statement
    ADD CONSTRAINT ck_m17_recon_statement_confirmed
    CHECK (status <> 'CONFIRMED'
           OR (confirmed_by IS NOT NULL
               AND confirmed_at IS NOT NULL
               AND reviewed_by IS NOT NULL
               AND snapshot IS NOT NULL));

ALTER TABLE m17_recon_statement
    ADD CONSTRAINT ck_m17_recon_statement_void
    CHECK (status <> 'VOID'
           OR (void_reason IS NOT NULL
               AND char_length(btrim(void_reason)) >= 10
               AND voided_by IS NOT NULL
               AND voided_at IS NOT NULL));

**设计说明**

1. **为什么恒等式要写成数据库 CHECK，而不是只写在 Service 里校验？**
   恒等式是调节表的**存在理由**——它证明银行余额与账面余额指向同一个真实金额。Service 层校验可以绕过
   （手工 SQL、数据修复脚本、其他服务直连写库）。写成 CHECK 后，任何一条不平的调节表都无法落库，且
   Service 层即使出 bug 也只会得到「约束违反」而不是一条错误归档的财务凭证。这与 M17 共享规范第 4 条铁律
   「会计恒等式必须由数据库强制」一致。

2. **为什么 `status IN ('DRAFT','VOID')` 允许不平，其余状态必须平？**
   调节表在生成过程中存在**中间态**：先取银行余额、再取账面余额、再汇总未达账项，这个过程中两侧天然不等。
   若草稿也强制平，生成流程必须在一瞬间算出全部要素，无法分步保存。因此草稿（`DRAFT`）豁免，一旦进入
   `GENERATED` 即视为「汇总完成」，必须平；此后复核、确认更应平。作废（`VOID`）记录保留原始不平数据供
   追溯，也豁免。

3. **为什么四类未达账项在表上存的是「正数合计」而不是「带符号合计」？**
   会计惯例是未达账项在调节表中以「加项 / 减项」列示，数字本身为正，方向由所在列决定。若存带符号值，
   报表显示会出现「加项 −52,300.00」这样的表述，与会计人员的阅读习惯冲突，也容易在二次计算时把符号搞反。
   存正数 + 恒等式里写死加减号，语义最清晰。带符号值（供求和用）在 `m17_recon_pending_item.signed_amount`
   与 `bank_side_effect` / `book_side_effect` 中已有。

4. **为什么 `uk_m17_recon_statement_period` 是部分唯一索引（`WHERE status <> 'VOID'`）？**
   一个账户一个期间只应有一张**有效**调节表，否则月结时不知道以哪张为准。但作废后重做是正常流程
   （如发现漏登未达账项），作废的历史表必须保留以供审计。部分唯一索引让「作废 + 重做」成为合法操作，
   同时杜绝两张有效表并存。

5. **为什么 `snapshot` 存 JSONB 而不是把明细拆成子表？**
   调节表的明细是「当期的四类未达账项清单」，它属于**证据快照**，确认后不需要按明细查询或聚合，只需
   完整还原。JSONB 一个字段即可存下（典型 20~50 条账项），且随调节表一起归档、一起不可变。若拆子表，
   还要在明细上加不可变约束、防止事后改明细，反而增加复杂度。

### 4.8 表：`m17_recon_channel`（支付渠道对账表）

**用途：** 第三方支付渠道（微信支付、支付宝、银联、美团等）的**日对账结果**。医院收的钱进 M16，
M16 记的是「应收/实收」，渠道记的是「平台结算金额」，银行流水记的是「到账金额」，三者之间有手续费与清算周期差。

**设计说明**

1. **为什么渠道对账要单独一张表，而不是并入银行流水或长短款？**
   渠道对账是**三方勾稽**：平台账（微信说收了多少）、系统账（医院记了多少）、银行账（实际到账多少）。
   三者的差额来源完全不同——平台与系统的差可能是手续费、退款时序、错单；系统与银行的差是清算周期。
   银行流水表只有银行一侧，长短款表只处理现金收付差，都无法承载「平台金额、系统金额、手续费、应结算、
   实际到账」这五组数据。独立建表才能把三方差额各自归因。

2. **为什么 `settle_amount` 与 `actual_settle_amount` 分两列？**
   `settle_amount`（应结算）在拿到平台对账单当天就能算出，而 `actual_settle_amount`（实际到账）通常要
   T+1 或 T+2 才从银行流水得知。分两列后，对账页可以明确显示「已收到/未收到」，未到账的记录进入
   `idx_m17_recon_channel_unsettled` 待清算清单，由定时任务每日与银行流水按 `settle_bank_serial_no` 或
   金额 + 日期匹配后回填，并计算 `settle_diff`。

3. **为什么 `ck_m17_recon_channel_matched` 要求已匹配必须 `diff_amount = 0`？**
   「已匹配」的语义是「平台账与系统账完全一致」。若允许差异不为 0 标 `MATCHED`，那么差异会失去归属，
   月末汇总时既不在未匹配清单里、也不在长短款里，成为无声的账外差。强制为 0 后，任何差额必须走
   `UNMATCHED` + `diff_type` 归因 + `handled_action` 处理，账目始终有主。

4. **为什么 `fee_amount <= platform_amount` 要作为硬约束？**
   手续费率配错（如把 0.6% 配成 60%）会让手续费超过交易额，`settle_amount` 变成负数——即「平台向医院收钱
   倒贴」。这类错误若流入账务，会造成资金短缺的假象并触发大量错误的长短款登记。约束在数据库层拦截，
   配合 `fee_rate BETWEEN 0 AND 1` 双重防护。

**设计说明**

1. **为什么长短款不从 M16 直接取现成结论，而要在 M17 重新登记一份？**
   M16-09 的长短款是「**收费员日结的现金差异**」，属于收费结算口径；M17 的长短款是「**账务意义上的资金
   差异**」，范围更大（还包含渠道对账差异、银行对账差异）。而且 M17 需要记录**责任认定、审批、账务处理**
   三个 M16 不管的环节。M17 通过 `source_ref_no` 引用 M16 的日结单号取数，但不复制其判定逻辑——M16 说
   「今天短款 38.50」，M17 决定「这 38.50 算谁的责任、怎么记账」。

2. **为什么 `uk_m17_recon_cash_diff_source` 要带 `cashier_id` 与 `payment_method`？**
   同一个日结单号下，可能同时存在「现金短款」与「微信长款」（收费员算错支付方式）。若唯一键只有
   `(diff_source, source_ref_no)`，第二条会被误拦。带上收费员与支付方式后，唯一性表达为「同一来源、
   同一个人、同一种支付方式只登记一次」，既防重复登记（定时任务重跑），又允许多条并存。

3. **为什么 `liability = 'STAFF'` 必须带 `approval_no`？**
   让员工赔钱涉及劳动法与员工权益，必须有审批留痕（金额、依据、员工确认）。这不是流程偏好，而是
   合规要求：没有审批的员工扣款在劳动争议中无法成立。数据库强制后，任何「直接判定员工赔」的路径都必须
   先走 M20 审批，杜绝口头决定。

4. **为什么 `handle_amount <= diff_amount`？**
   处理金额是「已经解决的部分」，不可能超过原始差额。「超过」在业务上意味着凭空多出一笔钱或
   重复处理——两种情况都说明数据有问题（如同一差异被两条记录处理）。约束在数据库层拦截，避免
   「部分处理」被滥用成「重复处理」。

**分区策略**

| 项 | 内容 |
|---|---|
| 分区键 | `created_at`（操作时间） |
| 分区方式 | `RANGE`，按月 |
| 保留期 | 24 个月在线；超期 `DETACH` 转冷存 10 年 |
| DEFAULT 分区 | **必须有**，名为 `m17_recon_log_default` |
| 预建任务 | APScheduler 每月 25 日 02:10 `ensure_recon_log_partition` |
| 归档任务 | 每日 03:30 `archive_recon_log`，超 24 个月分区 `DETACH` |

**设计说明**

1. **为什么日志表也要分区？**
   对账是全流程高频操作：每月导入流水 20+ 次（每账户每次导入一行日志，加上逐笔匹配的汇总日志）、
   自动匹配每次跑一行、人工匹配逐条一行、调节表生成复核确认各一行。按年 30 万行估算，10 年 300 万行。
   更重要的是**日志的访问模式天然是时间局部**：运维看「今天导入有没有失败」、审计看「上个月的匹配谁做的」，
   几乎不会跨年查。按月分区 + 超期归档，让热数据区始终只有 24 个月（60 万行），查询稳定在毫秒级。

2. **为什么 `action_level` 要分四级，而不只有成功/失败？**
   对账的「WARN」场景非常关键：自动匹配率骤降（如从 85% 掉到 40%）、匹配到大量疑似项、导入流水但
   有 3 笔解析跳过——这些都不是失败，但都预示着数据问题。若只有成功/失败，这类「成功但有隐患」的情况
   会被淹没。设定 `WARN` 级别后可单独出告警看板，是发现「解析器因银行改版而错行」的最早信号。

3. **为什么 `detail` 用 JSONB 而不是拆成多个字段？**
   18 种操作类型的详情结构完全不同：导入详情是「文件行数、成功数、跳过行、解析器版本」；匹配详情是
   「候选列表、各因子得分、阈值」；调节表生成详情是「四类未达账项明细、两侧余额来源」。拆成字段会让
   表宽爆炸且 90% 为空。JSONB 保留各自结构，且日志不需要按详情字段查询（只按 `action_type` /
   `target_id` / `batch_no` 查），完全够用。

4. **为什么 `target_table` + `target_id` 要做成通用双列而不是每类对象一个字段？**
   日志要回答「这条匹配记录发生过什么」。若做成 `match_id` / `pending_id` / `statement_id` 等多个可空列，
   每加一种对象就要加一列（DDL 变更），且索引无法统一。通用的 `(target_table, target_id)` 二元组配一个
   复合索引即可覆盖所有对象类型，新增对象类型无需改表结构——这是审计日志表的标准做法。

            raise ValueError("渠道来源必须填写渠道对账号")
        if self.diff_source == "BANK" and not self.account_no:
            raise ValueError("银行来源必须填写账户编号")

### C.2 关键查询示例

```sql
-- 查询 1：余额调节表核心汇总（四类未达账项 + 两侧余额来源）
-- 恒等式：银行对账单余额 + 企业已收银行未收 - 企业已付银行未付
--       = 企业账面余额 + 银行已收企业未收 - 银行已付企业未付
SELECT a.account_no,
       a.account_name,
       :period                                              AS period,
       -- 银行侧三要素
       COALESCE(bank_last.balance_after, :bank_balance)     AS bank_balance,
       COALESCE(pi.book_debit_not_bank, 0.00)               AS book_debit_not_bank,
       COALESCE(pi.book_credit_not_bank, 0.00)              AS book_credit_not_bank,
       -- 企业侧三要素
       COALESCE(ledger.book_period_debit - ledger.book_period_credit
                + ledger.book_open_balance, 0.00)           AS book_balance,
       COALESCE(pi.bank_credit_not_book, 0.00)              AS bank_credit_not_book,
       COALESCE(pi.bank_debit_not_book, 0.00)               AS bank_debit_not_book
  FROM m17_bank_account a
  LEFT JOIN LATERAL (
      SELECT bs.balance_after
        FROM m17_bank_statement bs
       WHERE bs.account_id = a.id
         AND bs.trans_date <= (:period || '-01')::date + INTERVAL '1 month'
                                                          - INTERVAL '1 day'
         AND bs.is_void = FALSE
       ORDER BY bs.trans_date DESC, bs.import_seq DESC
       LIMIT 1
  ) bank_last ON TRUE
  LEFT JOIN LATERAL (
      SELECT SUM(CASE WHEN pi.item_type = 'BOOK_DEBIT_NOT_BANK'
                      THEN pi.amount ELSE 0.00 END) AS book_debit_not_bank,
             SUM(CASE WHEN pi.item_type = 'BOOK_CREDIT_NOT_BANK'
                      THEN pi.amount ELSE 0.00 END) AS book_credit_not_bank,
             SUM(CASE WHEN pi.item_type = 'BANK_CREDIT_NOT_BOOK'
                      THEN pi.amount ELSE 0.00 END) AS bank_credit_not_book,
             SUM(CASE WHEN pi.item_type = 'BANK_DEBIT_NOT_BOOK'
                      THEN pi.amount ELSE 0.00 END) AS bank_debit_not_book
        FROM m17_recon_pending_item pi
       WHERE pi.account_id = a.id
         AND pi.period <= :period
         AND pi.status = 'OPEN'
         AND pi.is_deleted = FALSE
  ) pi ON TRUE
  LEFT JOIN LATERAL (
      SELECT SUM(CASE WHEN bl.dc_flag = 'D' THEN bl.amount ELSE 0.00 END)
                 AS book_period_debit,
             SUM(CASE WHEN bl.dc_flag = 'C' THEN bl.amount ELSE 0.00 END)
                 AS book_period_credit
        FROM m17_recon_book_ledger bl
       WHERE bl.account_id = a.id
         AND bl.period = :period
  ) ledger ON TRUE
 WHERE a.account_no = :account_no
   AND a.is_deleted = FALSE;

-- 查询 2：自动匹配候选（金额精确 + 日期容差 + 对方户名相似度）
SELECT s.id                                     AS statement_id,
       s.bank_serial_no,
       s.dc_flag,
       s.amount,
       s.trans_date,
       b.id                                     AS book_ledger_id,
       b.voucher_no,
       b.book_date,
       b.counter_party,
       -- 金额因子：精确匹配 1.000000，否则 0（由应用层按金额近似匹配扩展）
       CASE WHEN s.amount = b.amount AND s.dc_flag = b.dc_flag
            THEN 1.000000 ELSE 0.000000 END     AS score_amount,
       -- 日期因子：相差 0 天 1.0，每天衰减 0.1，最多 ±3 天
       GREATEST(0.000000,
                1.000000 - 0.100000 * abs(s.trans_date - b.book_date))
                                                AS score_date,
       -- 对方户名因子：pg_trgm 相似度
       COALESCE(similarity(s.counter_account_name, b.counter_party), 0.000000)
                                                AS score_counterparty
  FROM m17_bank_statement s
  JOIN m17_recon_book_ledger b
    ON b.account_id = s.account_id
   AND b.is_matched = FALSE
   AND b.amount = s.amount
   AND b.dc_flag = s.dc_flag
   AND b.book_date BETWEEN s.trans_date - :tolerance
                       AND s.trans_date + :tolerance
 WHERE s.account_id = :account_id
   AND s.trans_date >= :date_from
   AND s.trans_date < :date_to
   AND s.is_matched = FALSE
   AND s.is_void = FALSE
 ORDER BY s.trans_date, s.id;

-- 查询 3：未达账项四类汇总（调节表两个调整项）
SELECT pi.item_type,
       COUNT(*)                                     AS item_count,
       SUM(pi.amount)                               AS total_amount,
       SUM(pi.bank_side_effect)                     AS bank_side_total,
       SUM(pi.book_side_effect)                     AS book_side_total
  FROM m17_recon_pending_item pi
 WHERE pi.account_id = :account_id
   AND pi.period = :period
   AND pi.status = 'OPEN'
   AND pi.is_deleted = FALSE
 GROUP BY pi.item_type
 ORDER BY pi.item_type;

-- 查询 4：未匹配流水与未匹配台账的对账缺口（差额归因）
SELECT 'STATEMENT_UNMATCHED' AS gap_type,
       s.dc_flag,
       COUNT(*)              AS gap_count,
       SUM(s.signed_amount)  AS gap_amount
  FROM m17_bank_statement s
 WHERE s.account_id = :account_id
   AND s.trans_date >= :date_from
   AND s.trans_date < :date_to
   AND s.is_matched = FALSE
   AND s.is_void = FALSE
 GROUP BY s.dc_flag
UNION ALL
SELECT 'BOOK_UNMATCHED',
       b.dc_flag,
       COUNT(*),
       SUM(b.signed_amount)
  FROM m17_recon_book_ledger b
 WHERE b.account_id = :account_id
   AND b.book_date >= :date_from
   AND b.book_date < :date_to
   AND b.is_matched = FALSE
 GROUP BY b.dc_flag;

-- 查询 5：P01 工作台多账户对账进度
SELECT a.account_no,
       a.account_name,
       COUNT(s.id) FILTER (WHERE s.is_matched = FALSE AND s.is_void = FALSE)
                                                    AS unmatched_statement_count,
       COUNT(s.id)                                  AS statement_count,
       COALESCE(SUM(pi.amount) FILTER (WHERE pi.status = 'OPEN'), 0.00)
                                                    AS open_pending_amount,
       COUNT(pi.id) FILTER (WHERE pi.status = 'OPEN')
                                                    AS open_pending_count,
       st.statement_no,
       st.is_balanced
  FROM m17_bank_account a
  LEFT JOIN m17_bank_statement s
         ON s.account_id = a.id
        AND s.trans_date >= :period_start
        AND s.trans_date < :period_end
  LEFT JOIN m17_recon_pending_item pi
         ON pi.account_id = a.id
        AND pi.status = 'OPEN'
        AND pi.is_deleted = FALSE
  LEFT JOIN m17_recon_statement st
         ON st.account_id = a.id
        AND st.period = :period
        AND st.status <> 'VOID'
 WHERE a.status = 'ACTIVE'
   AND a.is_deleted = FALSE
 GROUP BY a.account_no, a.account_name, st.statement_no, st.is_balanced
 ORDER BY a.account_no;

-- 查询 6：支付渠道手续费与到账勾稽
SELECT c.channel_code,
       c.channel_name,
       COUNT(*)                                      AS recon_count,
       SUM(c.platform_amount)                        AS platform_total,
       SUM(c.system_amount)                          AS system_total,
       SUM(c.diff_amount)                            AS diff_total,
       SUM(c.fee_amount)                             AS fee_total,
       SUM(c.settle_amount)                          AS should_settle_total,
       SUM(COALESCE(c.actual_settle_amount, 0.00))   AS actual_settle_total,
       SUM(COALESCE(c.settle_diff, 0.00))            AS settle_diff_total
  FROM m17_recon_channel c
 WHERE c.period = :period
   AND c.is_deleted = FALSE
 GROUP BY c.channel_code, c.channel_name
 ORDER BY c.channel_code;
```

### D.3 匹配算法默认权重与阈值

| 因子 | 权重 | 计算方式 | 典型得分 |
|---|---|---|---|
| 金额精确匹配 | `0.600000` | 金额与方向完全一致得 `1.000000`，否则 `0.000000` | 相同金额 1.000000 |
| 日期容差 | `0.200000` | `1.000000 − 0.100000 × 天数差`，下限 `0.000000` | 同日 1.000000；差 3 天 0.700000 |
| 对方户名相似度 | `0.120000` | `similarity(流水对方户名, 台账往来单位)`（pg_trgm） | 完全相同 1.000000；部分相似 0.5 左右 |
| 摘要关键词 | `0.080000` | 摘要中命中台账 `biz_ref_no` 或权重词表得分 | 命中业务单号 1.000000 |
| **综合分** | `1.000000` | `Σ(因子得分 × 权重)` | — |
| 自动确认阈值 | `0.920000` | 综合分 ≥ 此值 → `CONFIRMED` | — |
| 疑似阈值 | `0.600000` | 综合分在此值与自动确认阈值之间 → `SUSPECTED` | — |
| 低于疑似阈值 | — | 不匹配，留待人工或登记未达账项 | — |

> **权重合计必须为 `1.000000`。** 启动时由配置校验任务检查，不符则告警并回退到默认权重。
