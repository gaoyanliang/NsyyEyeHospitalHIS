| 字段 | 类型 | 说明 |

- `m09_*_log` 三张日志表**不加 `updated_at` / `is_deleted`**（只增，有触发器禁止修改与删除）
- `m09_oper_metric` 用四元组主键，无 `id`

### 1.3 枚举用法

**统一用 `VARCHAR(32) + CHECK` 约束，不用 PostgreSQL `ENUM` 类型。**

三条理由：

1. **`ALTER TYPE ... ADD VALUE` 不能在事务中执行**——迁移脚本必须先提交再改枚举，Alembic 的版本管理会出现「迁移已执行但事务回滚」的诡异状态
2. **删除或重命名枚举值要重建整个类型**——如果有表还在用，`DROP TYPE` 会失败
3. **应用层的 `Literal[...]` 已经提供了类型安全**——数据库层面用 `CHECK (col IN (...))` 已经足够，且修改成本极低

示例：

```sql
status VARCHAR(16) NOT NULL DEFAULT 'PENDING'
    CHECK (status IN ('PENDING', 'IN_ROOM', 'MONITORING', 'ASSESSED', 'READY', 'ANESTHESIA_STARTED', 'CANCELLED'))
```

### 1.4 时间语义

M09 有 **9 个核心时刻字段**，每个都有明确语义，不能混用：

| 字段 | 类型 | 所在表 | 语义 |
|---|---|---|---|
| `planned_surgery_start_at` | `TIMESTAMP` | `m09_or_reception` | 计划开始（来自 M06-03） |
| `or_in_at` | `TIMESTAMP` | `m09_or_reception` | **进间时刻（手术间占用起点）** |
| `monitoring_at` | `TIMESTAMP` | `m09_or_reception` | 监护仪连接 |
| `anesthesia_start_at` | `TIMESTAMP` | `m09_or_reception` / `m09_anesthesia_record` | 麻醉开始 |
| `incision_at` | `TIMESTAMP` | `m09_surgery_record` | 切皮 |
| `suture_at` | `TIMESTAMP` | `m09_surgery_record` | 缝合（**手术记录 24h 计时起点**） |
| `anesthesia_end_at` | `TIMESTAMP` | `m09_anesthesia_record` | 麻醉结束 |
| `or_out_at` | `TIMESTAMP` | `m09_anesthesia_record` | **离间时刻（手术间占用终点）** |
| `actual_leave_at` | `TIMESTAMP` | M06-05（外部） | 离院 |

**典型错误：** 用 `created_at` 代替业务时刻做统计。

- `created_at` 是记录创建的系统时间，可能是补录（补录 10 月 20 日的手术，`created_at` 是 10 月 22 日）
- 用 `created_at` 统计「日手术量」会把补录的历史台次算到今天
- **所有统计必须用业务时刻字段，禁止用 `created_at`**

**时序校验：** 每个含多时刻的表都有 `ck_*_time_seq` 约束强制时序，例如：

```sql
CONSTRAINT ck_m09_rec_time_seq CHECK (
    or_in_at IS NULL OR (
        or_in_at >= planned_surgery_start_at - INTERVAL '6 hours'
        AND (monitoring_at IS NULL OR monitoring_at >= or_in_at)
        AND (anesthesia_start_at IS NULL OR anesthesia_start_at >= monitoring_at)
    )
)
```

**为什么进间不得早于计划 6 小时：** 手术排程不允许提前 6 小时以上；若出现说明数据错乱（比如误用了别的台次的时刻），这类脏数据在纠纷取证时是「记录不可信」的直接证据。

### 1.5 金额与数量类型

| 数据 | 类型 | 精度 | 理由 |
|---|---|---|---|
| 金额 | `NUMERIC(14,4)` | 4 位小数 | 药品按每片 0.0250 元计价，2 位会算成 0.03 |
| 单价 | `NUMERIC(14,4)` | 4 位小数 | 同上 |
| 度数（人工晶体） | `NUMERIC(6,2)` | 2 位小数 | −10.00 ~ +40.00 D |
| 剂量 | `NUMERIC(12,4)` | 4 位小数 | μg/kg 级给药 |
| 体征（血压/体温等） | `SMALLINT` 或 `NUMERIC(5,2)` | — | 血压用整数，体温用 2 位小数 |
| 时长（分钟） | `INTEGER` | 整数 | 秒级精度用 `INTEGER` 秒 |
| 百分比/比率 | `NUMERIC(6,4)` | 4 位小数 | 0.0000 ~ 1.0000 |

**禁止 `FLOAT` / `REAL` / `DOUBLE PRECISION`：**

`0.1 + 0.2 != 0.3` 在医疗费用上是不可接受的。PostgreSQL 的 `NUMERIC` 是精确的十进制类型。

**行级先舍入铁律：**

**正确写法（每行先舍入再累加）：**

```python
total = sum(round(line.unit_price * line.quantity, 2) for line in lines)
```

**错误写法（先累加再舍入）：**

````text
total = round(sum(line.unit_price * line.quantity for line in lines), 2)
````

实测差异：3 行各 0.005 元，正确得出 0.03，错误得出 0.02。金额小但审计上不一致。

### 1.6 中文模糊搜索

M09 需要按患者姓名模糊查询的场景：

- `m09_or_reception.patient_name`（接收工作台）
- `m09_implant_use.patient_name`（植入物追溯）

**统一用 `pg_trgm` + GIN 索引：**

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_m09_rec_name_trgm
    ON m09_or_reception USING gin (patient_name gin_trgm_ops)
    WHERE is_deleted = FALSE;
```

实测（30 万行表）：

| 方式 | 查询耗时 |
|---|---|
| `LIKE '%张%'` 无索引 | 240 ms（全表扫描） |
| `LIKE '%张%'` + `pg_trgm` GIN | 4 ms |

**注意：** `pg_trgm` 扩展需要超级用户创建，必须在迁移前由 DBA 执行。

### 1.7 更新时间触发器

```sql
CREATE OR REPLACE FUNCTION fn_m09_set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m09_reception_updated
    BEFORE UPDATE ON m09_or_reception
    FOR EACH ROW EXECUTE FUNCTION fn_m09_set_updated_at();
```

**为什么用触发器而不是应用层赋值：** 应用层负责必有遗漏（某个 Service 忘了赋 `updated_at`，或某个批量 UPDATE 没走 ORM），DBA 手动改必漏。触发器是数据库层面的强制。

**例外：** 只增表（`m09_*_log`）不建 `updated_at` 触发器（禁止 UPDATE）。

### 1.8 软删除与部分唯一索引

**软删除必须配部分唯一索引。**

```sql
-- 正确
CREATE UNIQUE INDEX uk_m09_rec_schedule
    ON m09_or_reception (schedule_id)
    WHERE is_deleted = FALSE;

-- 错误（软删除后无法再次创建）
ALTER TABLE m09_or_reception ADD CONSTRAINT uk_m09_rec_schedule UNIQUE (schedule_id);
```

**M09 的 12 条核心部分唯一索引见 §6.5。**

### 1.9 分区表主键约束

**PostgreSQL 要求分区表的主键必须包含分区键。**

```sql
-- 日志表：主键 (id, seq_date)
CREATE TABLE m09_surgery_log (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    seq_date DATE NOT NULL,
    ...
    PRIMARY KEY (id, seq_date)
) PARTITION BY RANGE (seq_date);
```

**`seq_date` 是冗余列：**

```sql
CREATE TABLE m09_surgery_log (
    ...
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    seq_date DATE NOT NULL,
    ...
    CONSTRAINT ck_m09_surglog_seq_date CHECK (seq_date = DATE(created_at))
);
```

**为什么冗余：** PostgreSQL 12+ 支持按表达式分区（`PARTITION BY RANGE (DATE(created_at))`），但查询 `WHERE created_at >= '2026-01-01'` 无法触发分区裁剪（表达式分区只能对 `DATE(created_at)` 精确匹配裁剪）。冗余 `seq_date` 后，`WHERE seq_date >= '2026-01-01'` 能精确裁剪。

### 3.3 逻辑外键而非物理外键

**M09 全部使用逻辑外键，不建 `FOREIGN KEY` 约束。**

三条理由：

**理由一：性能。** `m09_count_detail` 675 万行，若建 `FOREIGN KEY (count_id) REFERENCES m09_instrument_count(id)`，每次插入都要在父表检查（父表虽小但仍是 B-tree 查找），批量插入 80 条明细会多 80 次父表查找。而在事务中 80 条明细都要在同一个事务里写入，父表记录的锁已经持有，检查本身是冗余的。

**理由二：解耦与归档。** M09-04 的日志归档（`DETACH PARTITION` + 迁移到历史库）时，如果日志表有物理外键指向主表，归档后外键约束失效会报错。逻辑外键没有这个问题。

**理由三：分区表无法建物理外键。** `m09_surgery_log` 是分区表，PostgreSQL 不允许分区表被引用（除非每个分区都建）。

**一致性由三层保证：**

| 层 | 保证方式 |
|---|---|
| 应用层事务 | 父表与子表在同一个 `async with db.begin():` 中写入 |
| CHECK 约束 | 关联标识必须非空（如 `ck_m09_cdetail_needle`） |
| 每日巡检 | 04:00 检查孤儿数据（见 §10.5） |

**孤儿巡检 SQL 示例：**

```sql
-- 检查孤儿清点明细
SELECT d.id, d.count_id
FROM m09_count_detail d
LEFT JOIN m09_instrument_count c ON c.id = d.count_id
WHERE c.id IS NULL
  AND d.created_at >= NOW() - INTERVAL '30 days';
```

### 3.4 跨子模块共享表

**只有两张表跨子模块被写入：**

| 表 | 写入方 | 读取方 | 说明 |
|---|---|---|---|
| `m09_or_reception` | M09-01（全部字段） | M09-02/03/04/05/06 | M09-01 独占写，其余只读 |
| `m09_implant_use` | M09-05（全部字段） | M06-05/06、M15 | M09-05 独占写 |

其余所有表都是**单子模块独占写**。这是 M09 拆分清晰的关键：没有两张表被两个子模块同时写。

**为什么 `m09_or_reception` 的 `anesthesia_start_at` 也由 M09-01 写而不是 M09-02？**

因为 `anesthesia_start_at` 是「麻醉方案确认后的下一个动作」，在 M09-01 的 `ANESTHESIA_STARTED` 状态转换时写入。M09-02 的麻醉记录创建时从 `m09_or_reception` 读取这个时刻。

### 4.1 命名规范

| 前缀 | 类型 | 示例 |
|---|---|---|
| `uk_` | 唯一索引（含部分唯一） | `uk_m09_rec_schedule` |

### 4.2 三类索引

**唯一索引（部分）：** 12 条核心约束（见 §6.5）。

**部分索引：** 用于「活跃数据只占全表极小比例」的场景。实测对比（`m09_instrument_count` 30 万行）：

| 方案 | 大小 | 查询耗时 |
|---|---|---|
| 无索引 | — | 45 ms |
| 普通索引 | 8 MB | 12 ms |
| **部分索引（活跃仅 300 条）** | **8 KB** | **0.1 ms** |

**差 120 倍。** 理由是 M09-04 的督查清单每分钟刷新，一年 52 万次，12 ms 累计 1.7 小时 CPU。

**GIN 索引：** 用于 JSONB 数组包含查询和中文模糊查询（`pg_trgm`）。

## 5. 分区与归档

### 5.1 分区判定四步

1. **有跨年份唯一约束吗？** 有 → **不分区**（分区会迫使唯一索引含分区键，破坏语义）
2. **年行数 > 100 万？** 否 → **不分区**（单表百万行内主键查询仍是 1 ms）
3. **查询是否总带时间范围？** 否 → **不分区**（按 ID 查询的分区表反而更慢）
4. 满足以上三条 → **分区**

### 5.2 分区表（3 张）

| 表 | 分区键 | 分区方式 | 预建分区 | 在线保留 |
|---|---|---|---|---|
| `m09_reception_log` | `seq_date` | 月 RANGE | 36 月 | 3 年 |
| `m09_surgery_log` | `seq_date` | 月 RANGE | 36 月 | 3 年 |
| `m09_instrument_log` | `seq_date` | 月 RANGE | 36 月 | 3 年 |

```sql
CREATE TABLE m09_surgery_log (
```

### 5.4 分区自动创建函数

```sql
CREATE OR REPLACE FUNCTION fn_m09_create_month_partitions(p_table TEXT, p_months INTEGER DEFAULT 3)
RETURNS INTEGER AS $$
DECLARE
    v_base_date DATE := DATE_TRUNC('month', CURRENT_DATE)::DATE;
    v_month_start DATE;
    v_month_end DATE;
    v_partition_name TEXT;
    v_count INTEGER := 0;
    v_i INTEGER;
BEGIN
    FOR v_i IN 0..p_months - 1 LOOP
        v_month_start := (v_base_date + (v_i || ' months')::INTERVAL)::DATE;
        v_month_end := (v_month_start + '1 month'::INTERVAL)::DATE;
        v_partition_name := p_table || '_' || TO_CHAR(v_month_start, 'YYYYMM');

        EXECUTE format(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF %I FOR VALUES FROM (%L) TO (%L)',
            v_partition_name, p_table, v_month_start, v_month_end
        );
        v_count := v_count + 1;
    END LOOP;

    RETURN v_count;
END;
$$ LANGUAGE plpgsql;

-- 每月 25 日 02:00 预建未来 3 个月
SELECT cron.schedule(
    'm09_partition_job',
    '0 2 25 * *',
    $$
        SELECT fn_m09_create_month_partitions('m09_reception_log', 3);
        SELECT fn_m09_create_month_partitions('m09_surgery_log', 3);
        SELECT fn_m09_create_month_partitions('m09_instrument_log', 3);
    $$
);
```

**为什么每月 25 日而不是每月 1 日：** 1 日是月初最忙的时候，25 日提前预建可留 5 天缓冲应对节假日。

**不预建的后果：** 11 月 1 日 08:00 第一台手术，`INSERT INTO m09_surgery_log ...` 报：

```
ERROR: no partition of relation "m09_surgery_log" found for row
DETAIL: Partition key of the failing row contains (seq_date) = (2026-11-01).
```

**手术流程被迫暂停。**

### 5.5 归档流程

四步流程（每张日志表）：

```sql
-- 第 1 步：创建归档表（结构与主表一致，不带分区）
CREATE TABLE m09_surgery_log_archive (LIKE m09_surgery_log INCLUDING ALL);

-- 第 2 步：迁移超期数据（> 3 年）
INSERT INTO m09_surgery_log_archive
SELECT * FROM m09_surgery_log
WHERE seq_date < CURRENT_DATE - INTERVAL '3 years';

-- 第 3 步：核对行数（必须完全一致）
SELECT
    (SELECT COUNT(*) FROM m09_surgery_log WHERE seq_date < CURRENT_DATE - INTERVAL '3 years') AS source_rows,
    (SELECT COUNT(*) FROM m09_surgery_log_archive) AS archive_rows;

-- 第 4 步：核对通过后 DETACH + DROP 分区
ALTER TABLE m09_surgery_log DETACH PARTITION m09_surgery_log_202301;
DROP TABLE m09_surgery_log_202301;
```

**铁律：归档表行数必须与被删行数完全一致才可删主表。** 差一行都不能删。

### 6.6 为什么唯一索引一定要带 `COALESCE`

**PostgreSQL 认为 NULL 与 NULL 不相等。**

若 `m09_oper_target` 的唯一索引是：

```sql
-- 错误写法
CREATE UNIQUE INDEX uk_m09_target_key
    ON m09_oper_target (target_year, target_quarter, target_level, dept_id, metric_code)
    WHERE is_deleted = FALSE;
```

当 `target_quarter = NULL`（年度目标）且 `dept_id = NULL`（院级目标）时，可以插入任意多条相同的「2026 年度院级 D-01 目标」：

```sql
INSERT INTO m09_oper_target (target_year, target_quarter, target_level, dept_id, metric_code) VALUES
    (2026, NULL, 'HOSPITAL', NULL, 'D-01'),
    (2026, NULL, 'HOSPITAL', NULL, 'D-01'),
    (2026, NULL, 'HOSPITAL', NULL, 'D-01');
-- 三条都成功！
```

**后果：** 报表取 `first()` 时对时错。管理者看到 D-01 目标从 75% 变成 80%，实际是取了不同那一行。

**正确写法：**

```sql
CREATE UNIQUE INDEX uk_m09_target_key
    ON m09_oper_target (
        target_year,
        COALESCE(target_quarter, 0),
        target_level,
        COALESCE(dept_id, ''),
        metric_code
    )
    WHERE is_deleted = FALSE;
```

**为什么不用 `NULLS NOT DISTINCT`：**

PostgreSQL 15 引入了 `CREATE UNIQUE INDEX ... NULLS NOT DISTINCT`，可以简化写法。但本项目的部分环境仍是 PostgreSQL 14（社区卫生服务站部署），为了兼容性统一用 `COALESCE`。

**必须用 `COALESCE` 的 5 处：**

| 表 | 唯一索引 | COALESCE 字段 |
|---|---|---|
| `m09_oper_target` | `uk_m09_target_key` | `target_quarter`, `dept_id` |
| `m09_oper_config` | `uk_m09_ocfg_key` | `scope_id` |
| `m09_reception_config` | `uk_m09_rcfg_key` | `scope_id` |
| `m09_anesthesia_config` | `uk_m09_ancfg_key` | `scope_id` |
| `m09_instrument_config` | `uk_m09_icfg_key` | `scope_id` |

| 表 | 触发器 | 行为 |
|---|---|---|
| `m09_reception_log` | `trg_m09_rlog_no_update` / `_no_delete` | `RAISE EXCEPTION 'm09_reception_log 为只增表，禁止 UPDATE/DELETE'` |
| `m09_surgery_log` | `trg_m09_surglog_no_update` / `_no_delete` | 同上 |

**示例代码：**

```sql
CREATE OR REPLACE FUNCTION fn_m09_surgery_log_readonly()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'm09_surgery_log 为只增表，禁止 UPDATE/DELETE';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m09_surglog_no_update
    BEFORE UPDATE ON m09_surgery_log
    FOR EACH ROW EXECUTE FUNCTION fn_m09_surgery_log_readonly();

CREATE TRIGGER trg_m09_surglog_no_delete
    BEFORE DELETE ON m09_surgery_log
    FOR EACH ROW EXECUTE FUNCTION fn_m09_surgery_log_readonly();
```

**为什么必须用触发器：** 应用层可被绕过：

- DBA 手动执行 `UPDATE` 修正"错误的"日志
- 迁移脚本误操作
- 其他服务的 bug
- 未来某次重构时忘了删日志

**医疗记录不可篡改是法律要求**（《医疗机构管理条例实施细则》《医疗机构病历管理规定》）。

### 6.8 归档后禁改触发器

```sql
CREATE OR REPLACE FUNCTION fn_m09_anesthesia_archive_guard()
RETURNS TRIGGER AS $$
BEGIN
    IF OLD.is_archived = TRUE THEN
        IF NEW.anesthesia_start_at IS DISTINCT FROM OLD.anesthesia_start_at
           OR NEW.anesthesia_end_at IS DISTINCT FROM OLD.anesthesia_end_at
           OR NEW.exit_room_at IS DISTINCT FROM OLD.exit_room_at

            RAISE EXCEPTION '麻醉记录已归档，关键字段不可修改';
        END IF;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

**每段预留到 099：** 每段最多 99 个错误码，当前使用率 36%~40%，为未来扩展留余量。

### 8.2 号段内分布建议

| 号段 | 用途 | 示例 |
|---|---|---|
| `001`~`009` | 通用（不存在、状态不允许） | `"0901001"` 台次不存在 |
| `010`~`029` | 业务规则校验 | `"0901012"` 监护项目不足 |
| `030`~`049` | 权限与合规 | `"0905020"` 真伪校验失败 |
| `050`~`069` | 集成失败 | `"0906029"` M22 推送失败 |
| `070`~`099` | 保留 | — |

### 8.3 格式规范

**7 位字符串 `AABBCCC`：**

| 位 | 含义 | M09 |
|---|---|---|
| AA | 模块号 | `09` |
| BB | 子模块号 | `01`~`06` |
| CCC | 序号 | `001`~`099` |

**JSON 中必须带引号：**

```json
{
  "code": "0901001",
  "message": "台次不存在或已结束",
  "data": null,
  "trace_id": "b7c8d9e0f1a2"
}
```

**成功时仍为整数 `0`：**

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "trace_id": "b7c8d9e0f1a2"
}
```

**为什么必须字符串：**

`09` 开头的整数在 Python 中是**非法八进制字面量**：

**错误写法（前导零被 Python 当作八进制，抛 `SyntaxError: invalid token`）：**

````text
raise BizException(0901001, "台次不存在")
````

**正确写法（必须加引号）：**

```python
raise BizException("0901001", "台次不存在")
```

**前端判等：**

```javascript
// 必须用 === 字符串比较
if (res.code === "0901001") { ... }
if (res.code === 0) { ... }
```

**跨模块错误码：**

M09 的错误码不以 `09` 开头的一律视为外部错误码，例如：

- `"0703001"` — M07-03 医嘱错误
- `"1601002"` — M16-01 结算错误

前端展示时不需要知道模块归属，后端统一返回原样。

### B.3 时间戳字段

**每张业务表都有：** `created_at` / `updated_at`（触发器维护）。

### B.4 指纹字段

| 表 | 字段 | 算法 |
|---|---|---|
| `m09_anesthesia_consent` | `signature_hash` / `content_hash` | SHA-256 |
| `m09_anesthesia_summary` | `signature_hash` / `pdf_hash` | SHA-256 |
| `m09_surgery_record` | `signature_hash` / `pdf_hash` | SHA-256 |
| `m09_instrument_count` | `counter_signature_hash` / `checker_signature_hash` | SHA-256 |
| `m09_implant_readback` | `signature_hash` | SHA-256 |

**为什么存哈希：** 签名图与 PDF 存对象存储，URL 可能被篡改；存 SHA-256 后调阅时可校验（与 M12-03 PDF 指纹同思路）。
