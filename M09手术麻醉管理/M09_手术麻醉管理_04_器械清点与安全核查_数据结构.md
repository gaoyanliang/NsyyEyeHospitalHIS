**设计说明：**

1. **`m09_instrument_count` 是唯一业务主线。** M09-04 全部数据都通过 `count_id` 挂上来，不存在「另一张主表」。这样「这台手术的四次清点」永远只有一处真相。

2. **`m09_instrument_kit` 与 `m09_instrument_item` 是只读镜像。** 权威数据在 M15 物资耗材（器械包归属 M15 管理），M09-04 只保存一份快照，用于：
   - 离线可用（M15 故障时仍能清点）
   - 历史保真（M15 改了器械卡，历史清点单不能变）
   - 查询性能（一次 JOIN 拿全明细，不跨模块 HTTP）

   同步由 `job_m09_instrument_kit_sync` 每日 03:00 执行，以及 M15 推送 `m15.kit.updated` 事件时增量更新。

3. **`m09_count_detail` 与清点单是 1:N，N 包含 4 个阶段。** 用 `phase` 字段而非 4 张表，是因为比对逻辑要「同一物品在 4 个阶段的数量」——同一张表自连接即可，四张表要 JOIN 四次。

4. **全部为逻辑外键，无物理外键。** 理由与 M09 其他子模块一致：
   - 跨子模块引用（`schedule_id` 指向 M06 或 M09-03）加物理外键会影响并发
   - `m09_count_detail` 一年 29 万行、批量 INSERT 加外键校验会显著变慢
   - 分区表无法建物理外键（`m09_instrument_log` 分区）
   - 一致性由三层保证：应用层同事务成对写入 / CHECK 验证关联标识非空 / 每日 04:00 孤儿巡检

5. **`m09_instrument_log` 是只增表，月度 RANGE 分区。** 主表都不分区（唯一索引会失语义），日志表无跨年唯一约束，可自由分区。在线保留 3 年，更早的归档到 `m09_instrument_log_archive`。

### 4.2 表：`m09_instrument_kit`

**用途：** 器械包定义（与 M15 物资耗材的器械包一对一映射）。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |
| kit_code | VARCHAR(40) | N | — | 器械包编码，如 `KIT-CATARACT-01`，唯一 |
| kit_name | VARCHAR(100) | N | — | 器械包名称，如「白内障基础包」 |
| kit_name_en | VARCHAR(100) | Y | NULL | 英文名 |
| kit_type | VARCHAR(20) | N | 'SURGERY' | 包类型：SURGERY 手术包 / DRESSING 换药包 / SPECIAL 特殊包 |
| dept_id | BIGINT | Y | NULL | 归属科室 |
| item_count | SMALLINT | N | 0 | 物品条目数（明细行数，非件数） |
| piece_count | SMALLINT | N | 0 | 物品总件数（`SUM(standard_qty)`） |
| instrument_piece_count | SMALLINT | N | 0 | 器械件数（category='INSTRUMENT' 合计） |
| gauze_piece_count | SMALLINT | N | 0 | 纱布件数 |
| cotton_piece_count | SMALLINT | N | 0 | 棉片件数 |
| needle_piece_count | SMALLINT | N | 0 | 缝针件数 |
| sterilize_method | VARCHAR(20) | Y | NULL | 灭菌方式：STEAM 高压蒸汽 / ETO 环氧乙烷 / PLASMA 低温等离子 |
| sterilize_expiry_days | SMALLINT | Y | NULL | 灭菌有效期（天） |
| storage_location | VARCHAR(50) | Y | NULL | 存放位置 |
| m15_kit_id | BIGINT | Y | NULL | M15 器械包 ID（同步来源） |
| m15_synced_at | TIMESTAMP | Y | NULL | 最近同步时刻 |
| is_enabled | BOOLEAN | N | TRUE | 是否启用 |
| sort_no | SMALLINT | N | 100 | 排序 |
| remark | VARCHAR(500) | Y | NULL | 备注 |
| is_deleted | BOOLEAN | N | FALSE | 软删除 |
| created_at | TIMESTAMP | N | NOW() | 创建时刻 |
| created_by | BIGINT | Y | NULL | 创建人 |
| updated_at | TIMESTAMP | N | NOW() | 更新时刻 |
| updated_by | BIGINT | Y | NULL | 更新人 |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m09_kit` | 主键 | id | — |
| `uk_m09_kit_code` | 唯一（部分） | kit_code WHERE is_deleted=FALSE | 编码唯一 |
| `idx_m09_kit_type` | 普通 | kit_type, is_enabled | 按类型筛选 |
| `idx_m09_kit_m15` | 普通（部分） | m15_kit_id WHERE m15_kit_id IS NOT NULL | 反向同步 |
| `idx_m09_kit_name_trgm` | GIN | kit_name gin_trgm_ops | 中文检索 |

**约束说明：**

```sql
ALTER TABLE m09_instrument_kit
  ADD CONSTRAINT ck_m09_kit_code
    CHECK (kit_code ~ '^KIT-[A-Z][A-Z0-9-]{2,30}$');

ALTER TABLE m09_instrument_kit
  ADD CONSTRAINT ck_m09_kit_type
    CHECK (kit_type IN ('SURGERY', 'DRESSING', 'SPECIAL'));

ALTER TABLE m09_instrument_kit
  ADD CONSTRAINT ck_m09_kit_counts
    CHECK (item_count >= 0 AND piece_count >= 0
           AND instrument_piece_count + gauze_piece_count
             + cotton_piece_count + needle_piece_count = piece_count);

ALTER TABLE m09_instrument_kit
  ADD CONSTRAINT ck_m09_kit_expiry
    CHECK (sterilize_expiry_days IS NULL
           OR (sterilize_expiry_days >= 1 AND sterilize_expiry_days <= 365));
```

**设计要点：**

1. **`piece_count` 等四个分类件数是冗余字段。** 清点工作台与器械卡页面要显示「器械 70 件 / 纱布 20 块 / 棉片 15 片 / 缝针 3 支」，实时 `SUM` 要扫明细表。冗余后读取 O(1)，代价是同步时要一起更新（`ck_m09_kit_counts` 保证四个分类之和等于总数，防止漏更新）。

2. **`sterilize_expiry_days` 用于开包前校验。** 器械包灭菌后有效期通常 7~30 天（棉布包装 7 天、纸塑包装 30 天、硬质容器 90 天）。开包时校验是否过期（报 `"0904033"`），过期必须换包。

3. **`m15_kit_id` + `m15_synced_at` 支持双向追溯。** M15 是权威源，M09-04 是镜像。出问题时能回答「这个包在 M15 里对应哪条记录、什么时候同步的」。

**量级估算：**

| 项目 | 数量 |
|---|---|
| 器械包数 | 30 个 |
| 年新增 | 0（基本不变） |
| 行大小 | 约 0.6 KB |
| 15 年容量 | 约 18 KB |

**分区：** 不分区（数据量极小）。

### 4.3 表：`m09_instrument_item`

**用途：** 器械卡明细——器械包内每件物品的名称、规格、标准数量、是否关键器械、条码。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT | N | IDENTITY | 主键 |
| kit_code | VARCHAR(40) | N | — | 器械包编码（逻辑外键 → `m09_instrument_kit.kit_code`） |
| seq_no | SMALLINT | N | — | 包内序号（1 起） |
| item_code | VARCHAR(40) | N | — | 物品编码，如 `INST-HEMOSTAT-01` |
| item_name | VARCHAR(100) | N | — | 物品名称，如「止血钳(蚊式)」 |
| item_name_en | VARCHAR(100) | Y | NULL | 英文名 |
| spec | VARCHAR(50) | Y | NULL | 规格，如「蚊式」「小儿」「5x5cm」 |
| category | VARCHAR(20) | N | 'INSTRUMENT' | 类别：INSTRUMENT / GAUZE / COTTON / NEEDLE |
| standard_qty | SMALLINT | N | — | 标准数量（器械卡规定数量） |
| unit | VARCHAR(10) | N | '件' | 单位：件 / 块 / 片 / 支 |
| is_key | BOOLEAN | N | FALSE | 是否关键器械（需逐件扫码） |
| barcode | VARCHAR(60) | Y | NULL | 器械条码（关键器械才有） |
| material | VARCHAR(30) | Y | NULL | 材质：不锈钢 / 钛 / 塑料 |
| is_consumable | BOOLEAN | N | FALSE | 是否一次性耗材（纱布/棉片/缝针为 TRUE） |
| replacement_cycle | SMALLINT | Y | NULL | 更换周期（次） |
| sort_no | SMALLINT | N | 100 | 排序 |
| remark | VARCHAR(300) | Y | NULL | 备注 |
| is_deleted | BOOLEAN | N | FALSE | 软删除 |
| created_at | TIMESTAMP | N | NOW() | 创建时刻 |
| updated_at | TIMESTAMP | N | NOW() | 更新时刻 |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `pk_m09_item` | 主键 | id | — |
| `uk_m09_item_seq` | 唯一（部分） | (kit_code, seq_no) WHERE is_deleted=FALSE | 包内序号唯一 |
| `uk_m09_item_code` | 唯一（部分） | (kit_code, item_code) WHERE is_deleted=FALSE | 同包内物品编码唯一 |
| `idx_m09_item_kit` | 普通 | kit_code, category, seq_no | 按包按类别取明细 |
| `idx_m09_item_barcode` | 普通（部分） | barcode WHERE barcode IS NOT NULL | 扫码查物品 |
| `idx_m09_item_key` | 普通（部分） | kit_code WHERE is_key=TRUE AND is_deleted=FALSE | 取关键器械 |
| `idx_m09_item_name_trgm` | GIN | item_name gin_trgm_ops | 中文检索 |

**约束说明：**

```sql
ALTER TABLE m09_instrument_item
  ADD CONSTRAINT ck_m09_item_category
    CHECK (category IN ('INSTRUMENT', 'GAUZE', 'COTTON', 'NEEDLE'));

ALTER TABLE m09_instrument_item
  ADD CONSTRAINT ck_m09_item_qty
    CHECK (standard_qty >= 1 AND standard_qty <= 999);

ALTER TABLE m09_instrument_item
  ADD CONSTRAINT ck_m09_item_seq
    CHECK (seq_no >= 1 AND seq_no <= 500);

ALTER TABLE m09_instrument_item
  ADD CONSTRAINT ck_m09_item_code
    CHECK (item_code ~ '^[A-Z][A-Z0-9-]{2,38}$');

-- 关键器械必须有条码（无条码无法逐件扫码）
ALTER TABLE m09_instrument_item
  ADD CONSTRAINT ck_m09_item_key_barcode
    CHECK (is_key = FALSE OR barcode IS NOT NULL);

-- 耗材类（纱布/棉片/缝针）必须是 consumable
ALTER TABLE m09_instrument_item
  ADD CONSTRAINT ck_m09_item_consumable
    CHECK (category = 'INSTRUMENT'
           OR (is_consumable = TRUE AND is_key = FALSE));

-- 缝针必须指定 needle_no 顺序（由应用层保证，DB 只能要求唯一）
ALTER TABLE m09_instrument_item
  ADD CONSTRAINT ck_m09_item_needle_unit
    CHECK (category <> 'NEEDLE' OR unit = '支');
```

**设计要点：**

1. **`category` 决定清点方式与独立结论。** 四类物品的结论独立：器械、纱布、棉片、缝针任一不符即整体不符。若混在一张清单里统计「70 件 → 70 件相符」，一旦数量错位（器械多 1、纱布少 1）总数仍相符，会**掩盖纱布遗留**——这是手术室最常见的不良事件（占遗留物事件 60% 以上）。

2. **`ck_m09_item_key_barcode` 保证关键器械必有条码。** 关键器械定义为「价值高、需追溯」的显微器械、超乳手柄、玻切头。没有条码就无法逐件扫码，也就无法实现「这把钳在哪台手术用过」的追溯。

3. **`ck_m09_item_consumable` 排除耗材被标为关键器械。** 关键器械的语义是「一件一码、逐件清点」，纱布一包 10 块无法逐片贴码，只能按包扫码计数。

4. **`spec` 对同类物品区分型号。** 「止血钳 6 把」若含直头 3 把弯头 3 把，应拆成两行（`spec='直'` / `spec='弯'`），否则清点时无法判断少了哪种。

5. **`replacement_cycle` 记录更换周期。** 显微器械有使用次数上限（如角膜剪 100 次后刃口钝化），M15 会据此提醒更换，M09-04 只读展示。

**量级估算：**

| 项目 | 数量 |
|---|---|
| 每包平均物品条目 | 20 条（42 件 / 约 2 件每条） |
| 器械包数 | 30 个 |
| 总行数 | 约 600 行 |

**状态机：**

```
  PENDING ──①──► PRE_COUNTED ──②──► PRE_CLOSE ──③──► POST_CLOSE
                                        │               │
                                        │               └──④──► COUNTED
                                        │
                                        └─────┐
                                              ▼
                                          MISMATCH ──► RESOLVING
                                                          │
                                               ┌──────────┴──────────┐
                                               ▼                     ▼
                                           RESOLVED        CONFIRMED_RETAINED
```

**设计要点：**

1. **`uk_m09_icount_schedule` 是幂等基石。** M09-01 接收与 M09-02 麻醉开始都会尝试创建清点单。应用层「先查后插」在并发下有竞态窗口（两个请求同时查不到，同时插入），唯一索引把问题暴露为 `IntegrityError`，捕获后返回已有记录。**这也是清点单不按年分区的原因**——分区后唯一索引必须包含分区键，变成「同年唯一」，明年同一台次能再插一条，产生重复清点单。

2. **`ck_m09_icount_sod` 把「双人不同」下沉到 DB。** 应用层校验可被绕过（DBA 手动改、其他服务误写、迁移脚本）。双人核对是器械清点的核心防线，若一人可同时签两个角色，整个流程失去意义。

3. **`ck_m09_icount_phase_seq*` 三条约束保证阶段顺序。** 数值上「PRE_CLOSE 完成」必须蕴含「PRE 完成」。若只靠应用层 `status` 字段，代码 bug 可能导致 `phase_completed_at` 里没有 `PRE` 却已经是 `PRE_CLOSE`。

4. **`ck_m09_icount_counted` 要求 `matched=TRUE` 才能是 `COUNTED`。** 这是「相符才终态」的硬保证——不符必须走 `MISMATCH → RESOLVING → RESOLVED` 路径，不能在 `COUNTED` 状态里藏一个不符。

5. **`kit_snapshot` 存器械卡快照。** 真实场景：半年后 M15 把 KIT-CATARACT-01 的止血钳数量从 6 改到 4。若无快照，回看半年前的清点单会用新标准复算，得出「不符 -2」的错误结论。快照后永远能还原「当时器械卡写的 6 把」。

6. **`count_date` 单独存而非从 `created_at` 派生。** 按日查询、按日统计是最高频操作，`DATE(created_at)` 无法走索引。

**生成列定义：**

```sql
ALTER TABLE m09_count_detail
  ADD COLUMN diff SMALLINT
  GENERATED ALWAYS AS (
    CASE WHEN actual_qty IS NULL THEN NULL
         ELSE actual_qty - standard_qty END
  ) STORED;
```

**设计要点：**

1. **`diff` 用生成列而非普通列。** 若 `diff` 是普通列，更新 `actual_qty` 时必须同时更新 `diff`，任何一处遗漏就会出现「实际 5、标准 6、差异 0」的矛盾数据。生成列由数据库在写入时计算，物理上不可能不一致。

2. **`ck_m09_cdetail_matched` 三方绑定。** `actual_qty`、`matched`、`diff` 三者的状态必须同步：未清点时三者都是 NULL；清点后 `matched` 必须等于 `actual_qty = standard_qty`。这防止「改了数量但 matched 还是旧值」的脏数据——那种数据在汇总时会被算错。

3. **`actual_qty` 允许 NULL 是核心设计。** 4 个阶段 × N 件物品一次性创建全部明细，未清点的阶段 `actual_qty` 为 NULL。这样可以：
   - 用 `idx_m09_cdetail_unfilled` 部分索引快速查「还有多少件没填」（提交前的完整性校验）
   - 一个结构的汇总 SQL 可同时处理「未清点」（NULL）与「清点后数量为 0」
   - 不需要「先创建已清点阶段明细、清点时再插入」的复杂逻辑

   若用 `DEFAULT 0` 就分不清「没清点」与「清点后确实是 0 件」——纱布清点为 0 是严重异常（可能与术前数量差异极大），必须能识别。

4. **`seq_no` 沿用器械卡的序号而非重新排。** 清点页要「按器械卡的顺序」显示，护士拿着纸质器械卡一一对应。若清点时重新编号，护士会找不到对应项。

5. **`kit_code` 冗余到明细行。** 一次手术可能开 2~3 个器械包（白内障包 + 超乳包），清点页要按包分组显示。若明细不存 `kit_code`，要 JOIN 器械包表才能分组。

6. **`uk_m09_cdetail_seq` 包含 `kit_code`。** 两个器械包可能有相同的 `seq_no`（各自都从 1 编号）。唯一约束若只有 `(count_id, phase, seq_no)`，第二个包的第 1 项会冲突。

7. **缝针三个字段（`needle_no`/`needle_used`/`needle_taken_at`）放在明细表。** 缝针是最易断裂留在体内的物品。断针后需要立刻知道「哪一支、什么型号、什么时候取的、用在哪一步」。若只记总数，断针后只能猜。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 每台次物品条目 | 84 条（2 个包合计） |
| 每台次明细行 | 84 × 4 = 336 行 |
| 日台次 | 55 |
| 日新增 | 18,480 行 |
| 年新增 | 6,745,200 行 |
| 行大小 | 约 220 B |
| 15 年数据 | 1.01 亿行 / 约 22 GB |

⚠️ **注意：这个量级超出单表舒适区。** 后续版本考虑按 `count_id` HASH 分区（见「分区」说明）。

**分区：**

**当前版本不分区**，理由：

1. 所有查询都以 `count_id` 为入口（清点单详情、汇总、提交），`count_id` 上的索引能覆盖全部查询模式。
2. 若按 `created_at` RANGE 分区，查询某清点单的 336 条明细会跨多个分区（如果该单被长期修改），性能反而下降。
3. `uk_m09_cdetail_seq` 若分区必须含 `create_at` 分区键，唯一性约束被破坏。

**后续优化路径（文档债 T-M09-04-01）：** 当行数超过 5,000 万时，改为 `PARTITION BY HASH (count_id)` 分 16 个分区。HASH 分区保证同一清点单的明细落在同一分区，且唯一索引可以包含 `count_id` 保持语义。这需要在数据量达到阈值前执行迁移。

**分区定义：**

```sql
CREATE TABLE m09_instrument_log (
  id            BIGINT      GENERATED BY DEFAULT AS IDENTITY,
  seq_date      DATE        NOT NULL,
  created_at    TIMESTAMP   NOT NULL DEFAULT NOW(),
  -- 其余字段…
  PRIMARY KEY (id, seq_date)
) PARTITION BY RANGE (seq_date);

-- 预建 36 个月分区
DO $$
DECLARE
  v_i    INT;
  v_date DATE;
  v_next DATE;
BEGIN
  FOR v_i IN 0..35 LOOP
    v_date := (DATE_TRUNC('month', CURRENT_DATE)
               + (v_i * INTERVAL '1 month'))::DATE;
    v_next := (v_date + INTERVAL '1 month')::DATE;
    EXECUTE FORMAT(
      'CREATE TABLE IF NOT EXISTS %I PARTITION OF m09_instrument_log '
      'FOR VALUES FROM (%L) TO (%L)',
      'm09_instrument_log_' || TO_CHAR(v_date, 'YYYYMM'),
      v_date, v_next
    );
  END LOOP;
END;
$$;
```

**设计要点：**

1. **日志只增是审计合规的硬要求。** 《医疗机构管理条例实施细则》要求医疗记录可追溯、不可篡改。应用层的「只写不改」可被绕过（DBA 手动改、迁移脚本误操作、其他服务 bug）。触发器是物理防线。

2. **月度分区而非按年。** 年 40 万条 × 15 年 = 600 万条，单表虽可承受但不理想。月度分区后：
   - 查「最近 3 个月」只扫 3 个分区（10 万条）而不是全表 600 万条
   - 归档只需 `DETACH PARTITION`
   - 在线保留 3 年（36 个分区），更早的归档到 `m09_instrument_log_archive`

3. **`seq_date` 冗余列而非直接按 `created_at` 分区。** PostgreSQL 12+ 支持表达式分区但有很多限制；普通列分区键查询时可直接裁剪。约束 `seq_date = DATE(created_at)` 保证两者一致。

4. **`count_no` / `schedule_id` 冗余到日志。** 日志是「单表可查」的审计流。若只有 `count_id`，查「某清点单的所有操作」要 JOIN 主表；冗余后单表即可（且主表可能已被归档删除）。

5. **`detail_json` 存操作明细。** 例如 `UPDATE_DETAIL` 操作记 `{"phase":"PRE_CLOSE","items":[{"detail_id":50007,"old":6,"new":5}]}`。事后能回答「这次清点里，护士把止血钳从 6 改成 5 是在几点几分」。

6. **`ip` 用 INET 类型。** 医疗纠纷场景中「什么时间从哪台机器操作的」是关键证据。INET 支持 CIDR 匹配（如查「所有从手术间网段操作的记录」）。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 每台次平均操作数 | 20 次（4 次清点 × 3~5 次操作） |
| 日新增 | 1,100 行 |
| 年新增 | 401,500 行 |
| 行大小 | 约 0.6 KB |
| 在线 3 年数据 | 120 万行 / 约 720 MB |
| 36 个分区，平均 | 33,458 行/分区 |

**分区：** 月度 RANGE 分区，预建 36 个月，在线保留 3 年。

**设计要点：**

1. **`uk_m09_icfg_key` 用 `COALESCE(scope_id, 0)`。** PostgreSQL 唯一索引认为 NULL 互不相等，两条 `scope='GLOBAL'`（`scope_id` 均为 NULL）的记录都能插入。用 `COALESCE` 把 NULL 归一为 0 才能真正唯一。（不用 `NULLS NOT DISTINCT` 因为那是 PostgreSQL 15+ 特性，部分环境还是 14。）

2. **`param_value` 统一存字符串。** 配置表是「异构参数容器」，若用 JSONB 存值类型自由但无法在 SQL 里做范围校验。VARCHAR + `param_type` 显式声明，写入时用 `min_value`/`max_value` 校验。

3. **`is_editable = FALSE` 的两个参数不可改。**
   - `MIN_COUNT_PHASES = 4`：《手术室护理实践指南》硬性要求，调小等于漏做清点
   - `MATCH_THRESHOLD = 1.0`：等级评审要求「清点正确率 100%」，调小等于允许「部分相符」
   - `REPORT_DEADLINE_HOURS = 24`：法规时限，调大等于允许瞒报

   三个参数的 `min_value = max_value` 双重锁定，即使误把 `is_editable` 改成 TRUE，范围校验也会拒绝其他值。

4. **`default_value` 支持「恢复默认」。** 真实场景：运维为排查把 `COUNT_TIMEOUT_MINUTES` 改成 30 忘改回，所有清点都显示"超时"却没人管。有默认值即可一键恢复。

5. **`version` 每次修改 +1。** 用于乐观锁与变更追溯。

6. **`is_sensitive` 参数修改需二次确认。** 前端弹「此参数影响器械清点合规性，确认修改？」，并在审计日志记录。

**量级估算：**

| 项目 | 数值 |
|---|---|
| 参数条数 | 16（GLOBAL）+ 少量科室级 |
| 行大小 | 约 0.5 KB |
| 总容量 | 约 20 KB |

**分区：** 不分区。

## 附录 B：状态与代码枚举汇总

### B.1 清点状态 `status`

| 代码 | 名称 | 是否终态 | 说明 |
|---|---|---|---|
| `PENDING` | 待清点 | 否 | 已创建清点单，术前清点未开始 |
| `PRE_COUNTED` | 术前已清点 | 否 | ①已完成 |
| `PRE_CLOSE` | 关腔前已清点 | 否 | ②已完成 |
| `POST_CLOSE` | 关腔后已清点 | 否 | ③已完成 |
| `POST_SUTURE` | 缝合后已清点 | 否 | ④已完成（中间态，立即转 COUNTED） |
| `COUNTED` | 清点完成 | **是** | 四次全部相符 |
| `MISMATCH` | 数量不符 | 否 | 发现差异，待处置 |
| `RESOLVING` | 处置中 | 否 | 二次查找 / X 光复核中 |
| `RESOLVED` | 已解决 | **是** | 不符已解决 |
| `CONFIRMED_RETAINED` | 确认遗留 | **是** | 器械遗留体内 |
| `CANCELLED` | 已取消 | **是** | 台次取消 |

### B.2 清点阶段 `phase`

| 代码 | 名称 | 时机 |
|---|---|---|
| `PRE` | 术前清点 | 开包后、切皮前 |
| `PRE_CLOSE` | 关腔前清点 | 关闭切口前 |
| `POST_CLOSE` | 关腔后清点 | 关闭切口后 |
| `POST_SUTURE` | 缝合后清点 | 缝合完成后 |

### B.3 物品类别 `category`

| 代码 | 名称 | 单位 | 独立结论 | 清点方式 |
|---|---|---|---|---|

**部分索引效果实测对比（`idx_m09_icount_status`）：**

| 方案 | 索引大小 | 查询耗时 |
|---|---|---|
| 无索引（全表扫） | — | 约 45 ms |

### E.4 分区自动创建

```sql
CREATE OR REPLACE FUNCTION fn_m09_create_month_partitions(
  p_table TEXT,
  p_months INTEGER DEFAULT 3
)
RETURNS INTEGER AS $$
DECLARE
  v_i      INTEGER;
  v_date   DATE;
  v_next   DATE;
  v_created INTEGER := 0;
  v_exists  BOOLEAN;
BEGIN
  FOR v_i IN 0..(p_months - 1) LOOP
    v_date := (DATE_TRUNC('month', CURRENT_DATE)
               + (v_i * INTERVAL '1 month'))::DATE;
    v_next := (v_date + INTERVAL '1 month')::DATE;

    SELECT EXISTS (
      SELECT 1 FROM pg_class
      WHERE relname = p_table || '_' || TO_CHAR(v_date, 'YYYYMM')
    ) INTO v_exists;

    IF NOT v_exists THEN
      EXECUTE FORMAT(
        'CREATE TABLE %I PARTITION OF %I FOR VALUES FROM (%L) TO (%L)',
        p_table || '_' || TO_CHAR(v_date, 'YYYYMM'),
        p_table, v_date, v_next
      );
      v_created := v_created + 1;
    END IF;
  END LOOP;

  RETURN v_created;
END;
$$ LANGUAGE plpgsql;

-- 每月 25 日 02:00 预建未来 3 个月分区
SELECT cron.schedule(
  'm09_instrument_log_partition',
  '0 2 25 * *',
  $$SELECT fn_m09_create_month_partitions('m09_instrument_log', 3)$$
);
```

⚠️ **不预建分区的后果：** PostgreSQL 写入找不到匹配分区时会报 `no partition of relation "m09_instrument_log" found for row`。若发生在 11 月 1 日 08:00 第一台手术的清点操作上，护士无法开始清点，手术流程被迫暂停。
