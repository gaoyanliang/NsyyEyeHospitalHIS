**设计说明：**

1. **`m09_surgery_record` 是 M09-03 的唯一主线**，7 张子表通过 `record_id` 挂上来。一台次一条记录由 `uk_m09_surg_schedule` 保证。

2. **步骤 / 日志 / 事件三张表都是"时间轴"性质**，但语义完全不同：
   - 步骤是**结构化的关键操作**（有序、有起止），用于统计与记录渲染
   - 日志是**实时流水账**（无序语义、纯追加），用于记录素材
   - 事件是**异常情况**（有序、有严重度、有处置与转归），用于质量分析

   三者共用一张表会导致：①字段大量为 NULL（事件有 severity，步骤没有）②索引无法针对各自查询模式优化 ③统计口径混乱（"这台手术记了几条"算步骤还是日志？）

3. **`record_fields` 与 `exploration` 用 JSONB 而非宽表**：
   - 眼科 40+ 个术式，每个术式的必填要素完全不同（超乳要晶体核硬度与超乳能量，玻切要填充物与激光点数，斜视要各直肌后徙毫米数）
   - 若用宽表，一张表会有 80+ 个字段，每个术式只用其中 5~8 个，其余全 NULL
   - 模板定义在 M01-07（`md_operation.record_template_id`），字段集合可随时调整而不需改表结构
   - 代价：无法对字段建索引。但手术记录查询是「按患者/日期/术式」，从未需要「按晶体核硬度检索」，代价可接受

4. **`m09_surgery_record_version` 是签名与补充的快照表**：每次 `SIGN` 与 `SUPPLEMENT` 都生成一条完整快照。手术记录是法律证据，必须能还原「签名那一刻的内容是什么」。

5. **`m09_surgery_log` 按月 RANGE 分区**：日均 55 台 × 8 条操作 = 440 条，年 16 万条。日志无跨年唯一约束，分区无代价，且「查最近 3 个月」是 90% 的查询模式。

6. **无物理外键**：跨子模块引用（`schedule_id`）与高频子表（`m09_surgery_note`）加外键会带来锁竞争与归档迁移困难。一致性由应用层事务 + CHECK + 每日孤儿巡检三层保证。

**约束说明：**

```sql
ALTER TABLE m09_surgery_record
    ADD CONSTRAINT ck_m09_surg_no CHECK (record_no ~ '^SR[0-9]{8}[A-Z0-9]{2,4}[0-9]{2}$'),
    ADD CONSTRAINT ck_m09_surg_status CHECK (status IN (
        'DRAFT','SUBMITTED','SIGNED','SUPPLEMENTED','CANCELLED'
    )),
    ADD CONSTRAINT ck_m09_surg_level CHECK (
        surgery_level IS NULL OR surgery_level IN ('LEVEL_1','LEVEL_2','LEVEL_3','LEVEL_4')
    ),
    ADD CONSTRAINT ck_m09_surg_eye CHECK (eye_side IS NULL OR eye_side IN ('OD','OS','OU','NA')),
    ADD CONSTRAINT ck_m09_surg_gender CHECK (gender IS NULL OR gender IN ('M','F')),
    ADD CONSTRAINT ck_m09_surg_seq CHECK (seq_no >= 1 AND seq_no <= 99),
    ADD CONSTRAINT ck_m09_surg_prognosis CHECK (
        prognosis IS NULL OR prognosis IN ('GOOD','FAIR','POOR','GUARDED')
    ),
    ADD CONSTRAINT ck_m09_surg_blood_level CHECK (
        blood_loss_level IS NULL OR blood_loss_level IN (
            'NONE','MINIMAL','MILD','MODERATE','SEVERE'
        )
    ),
    -- 时刻时序自洽
    ADD CONSTRAINT ck_m09_surg_time_seq CHECK (
        suture_at IS NULL OR suture_at > incise_at
    ),
    -- 时长自洽
    ADD CONSTRAINT ck_m09_surg_duration CHECK (
        incise_at IS NULL OR suture_at IS NULL OR duration_minutes IS NULL
        OR duration_minutes = GREATEST(0, EXTRACT(EPOCH FROM (suture_at - incise_at))::INT / 60)

**设计要点：**

1. **`uk_m09_surg_schedule` 是幂等的最后防线。** M09-02 麻醉开始、M06-04 Time-Out 完成都可能触发"创建手术记录"。应用层"先查后插"在并发下有竞态窗口。捕获 `IntegrityError` 后返回已有记录，实现幂等。

2. **`template_required` 存快照而非实时查。** 真实场景：M01-07 半年后把晶体超乳术式的必填项从 12 个加到 15 个。若实时查，历史记录的"完成度"会从 100% 掉到 80%，看起来像"以前没填完"。存快照后，每条记录按它签名时的模板要求判定。

3. **`instrument_count_ok` 允许 NULL。** NULL = 「不知道」（M09-04 未回写或失败），FALSE = 「清点不符」。二者临床后果完全不同：前者需要人工确认，后者是重大问题。若合并成 `BOOLEAN NOT NULL DEFAULT FALSE`，会把「未知」误报成「不符」。

4. **`no_specimen` 与 `no_specimen_reason` 联动。** 提交时若标本数=0 且未勾选「无标本」，阻断（`"0903016"`）。勾选了就必须填原因——这是防"漏送标本"的关键闸门。

5. **三个冗余计数字段（`step_count` / `note_count` / `event_count` / `specimen_count`）。** 工作台与列表要显示"已记 7 步、5 条日志、1 个事件"，若每次 `COUNT(*)` 子表，一屏 20 条记录就是 80 次子查询。冗余计数在写入时原子递增，读时 O(1)。

6. **`is_overdue` 与 `overdue_hours` 落库而非实时计算。** `WHERE NOW() > suture_at + INTERVAL '24 hours'` 无法走索引。落库后由 `job_m09_surgery_overdue_scan` 每小时维护，`idx_m09_surg_overdue` 是部分索引（超时记录常年 0~5 条）。

7. **`signed_ip` 用 INET 类型。** 医疗纠纷场景「什么时间从哪台机器签的字」是关键证据，INET 支持范围查询与格式化。

8. **无分区。** 若按 `record_date` 年度分区，`uk_m09_surg_schedule` 与 `uk_m09_surg_no` 必须含分区键，唯一性退化为"同年内一台次一条"——去年台次被重新处理会产生重复记录。15 年约 30 万行在主键查询下仍在 1ms 内。

**状态机：**

```
        auto_create（麻醉开始/切皮）
                │
                ▼
       ┌────────────────┐
       │     DRAFT      │  可编辑全部内容
       └───────┬────────┘
               │ submit（校验必填/步骤/小结/出血/标本）
               ▼
       ┌────────────────┐
       │   SUBMITTED    │  待签名
       └───┬────────┬───┘
     back  │        │ sign（生成 PDF）
           ▼        ▼
       ┌────────────────┐
       │     SIGNED     │  只读
       └───────┬────────┘
               │ supplement（≥10 字原因）
               ▼
       ┌────────────────┐
       │ SUPPLEMENTED   │  仍只读，可继续补充

```sql
ALTER TABLE m09_surgery_step
    ADD CONSTRAINT ck_m09_step_no CHECK (step_no >= 1 AND step_no <= 50),
    ADD CONSTRAINT ck_m09_step_code CHECK (
        step_code ~ '^[A-Z][A-Z0-9_]{1,31}$'
    ),
    ADD CONSTRAINT ck_m09_step_time CHECK (
        start_at IS NULL OR end_at IS NULL OR end_at > start_at
    ),
    ADD CONSTRAINT ck_m09_step_duration CHECK (
        start_at IS NULL OR end_at IS NULL OR duration_seconds IS NULL
        OR duration_seconds = EXTRACT(EPOCH FROM (end_at - start_at))::INT
    ),
    ADD CONSTRAINT ck_m09_step_duration_range CHECK (
        duration_seconds IS NULL OR (duration_seconds >= 1 AND duration_seconds <= 7200)
    ),
    ADD CONSTRAINT ck_m09_step_parallel_seq CHECK (
        (is_parallel = FALSE AND seq_in_parallel IS NULL)
        OR (is_parallel = TRUE AND seq_in_parallel IS NOT NULL AND seq_in_parallel >= 1)

COMMENT ON COLUMN m09_surgery_step.step_code IS '步骤编码，来自 M01-07 标准步骤模板或自定义';
COMMENT ON COLUMN m09_surgery_step.is_parallel IS '与上一步并行执行，时序校验跳过';
COMMENT ON COLUMN m09_surgery_step.duration_seconds IS '耗时秒数，用于步骤效率统计';
```

**设计要点：**

1. **`is_parallel` 的存在是因为眼科有真实的并行操作。** 白内障术中「上方操作 + 下方辅助」可以同时进行；玻璃体切除中「灌注 + 切割 + 光凝」三件事同时进行。若强制所有步骤串行，医生只能把并行操作拆成两个伪时序。

2. **`duration_seconds` 存冗余。** 统计「不同医生 CCC 步骤平均耗时」需要聚合，`EXTRACT(EPOCH FROM (end_at - start_at))` 无法走索引且每次计算。存整数秒后可直接 `AVG(duration_seconds) WHERE step_code='CCC'`。

3. **`step_code` 用正则约束格式但不做枚举。** 因为步骤集合随术式变化（40+ 术式 × 每术式 5~10 步 = 300+ 个步骤码），且医院可自定义步骤。约束只能保证格式规范，内容合法性由 M01-07 模板保证。

4. **`step_no` 上限 50。** 眼科手术步骤最多约 20 步（复杂玻切 + 硅油填充），50 已足够且能防止异常数据。

| 项目 | 值 |
|---|---|
| 日均步骤 | 55 台 × 7 步 = 385 条 |
| 年记录数 | 约 140,000 条 |
| 15 年记录数 | 约 2,100,000 条 |
| 单行平均长度 | 约 180 字节 |
| 15 年数据量 | 约 380 MB |

**分区：** 不分区。若未来需要，应按 `record_id` HASH 分区而非时间——所有查询从 `record_id` 进入。

COMMENT ON COLUMN m09_surgery_note.linked_step_id IS '关联的手术步骤，可空';

**设计要点：**

1. **日志与步骤分离而非合并。** 步骤是"关键操作"（有限、有序、有起止），日志是"随时想到的要点"（无限、无序、单一时刻）。合并会导致步骤表被大量非步骤日志污染，且步骤的时序校验被日志破坏。

2. **`seq_no` 而非 `noted_at` 做排序键。** 同一分钟内可能记多条日志（如连续三条 FINDING），若按 `noted_at` 排序会因秒相同而不稳定。`seq_no` 严格递增保证渲染顺序确定。

3. **`voice_raw` 存识别原文。** 语音识别有误时，医生可对照原文修改。若只存修正后的内容，无法判断"是说的不对还是识别错了"——这是 ASR 质量改进的数据来源。

4. **`content` 支持 GIN trgm 索引。** 手术日志是自由文本，质控常需检索「哪些手术记录了『后囊膜』」。不加索引时 210 万行全表扫约 600ms，加 GIN 后约 8ms。

**设计要点：**

2. **只增触发器。** 版本快照是审计证据，任何修改都会破坏"可还原"这个前提。应用层可被绕过（DBA 手动改、迁移脚本误操作），DB 层强制是唯一可靠手段。

3. **`reason` 对 SUPPLEMENT 必填 ≥10 字。** 补充记录是"事后修正"，必须说明为什么。若允许空，补充记录会沦为"偷偷改"的通道。

4. **`created_ip` 用 INET。** 「什么时间从哪台机器签的字」在纠纷举证中是关键信息。

END;

**设计要点：**

1. **按月 RANGE 分区而非不分区。** 日均 440 条，年 16 万条，15 年 240 万条。日志无跨年唯一约束（主键含 `seq_date`），分区无代价，收益是「查最近 3 个月」只扫 3~4 个分区而非全表。

2. **`seq_date` 冗余列而非用 `created_at` 表达式分区。** PostgreSQL 12+ 支持表达式分区，但查询 `WHERE created_at >= ?` 无法走分区裁剪。冗余 `seq_date` 后分区键是普通列，可裁剪。约束 `ck_m09_surglog_seq_date` 保证两者一致。

3. **`ck_m09_surglog_transit` 限制状态流转只在 4 个动作上记录。** 其他动作（如 `STEP_ADD`）不应有状态变更。这个约束防止脏数据。

4. **只增触发器。** 手术记录操作日志是审计证据，且《医疗机构病历管理规定》要求病历修改留痕。应用层可被绕过，DB 层强制。

|---|---|

| 年记录数 | 约 160,000 条 |
| 在线保留 | 3 年（36 个分区） |
| 在线数据量 | 约 720 MB |
| 归档保留 | 15 年 |
| 单行平均长度 | 约 250 字节 |

**分区：** 按月 RANGE，预建 36 个月。**在线保留 3 年**，超期分区 DETACH 后转归档（`m09_surgery_log_archive` 或对象存储）。

                raise ValueError("眼心反射必须填写最低心率")
            if not self.treatments:
                raise ValueError("眼心反射必须记录至少一项处理措施")
        if self.event_type == "RESPIRATORY_DEPRESSION" and self.lowest_spo2 is None:

        if self.event_type == "BRADYCARDIA" and self.lowest_heart_rate is None:

**分区自动创建函数：**

```sql
CREATE OR REPLACE FUNCTION fn_m09_create_month_partitions(
    p_table TEXT,
    p_months INTEGER DEFAULT 3
) RETURNS INTEGER AS $$
DECLARE
    v_i INTEGER;
    v_start DATE;
    v_end DATE;
    v_created INTEGER := 0;
    v_part TEXT;
BEGIN
    FOR v_i IN 0..(p_months - 1) LOOP
        v_start := (DATE_TRUNC('month', CURRENT_DATE)::DATE
                    + (v_i || ' months')::INTERVAL)::DATE;
        v_end := (v_start + INTERVAL '1 month')::DATE;
        v_part := p_table || '_' || TO_CHAR(v_start, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF %I FOR VALUES FROM (%L) TO (%L)',
            v_part, p_table, v_start, v_end
        );
        v_created := v_created + 1;
    END LOOP;
    RETURN v_created;
END;
$$ LANGUAGE plpgsql;

-- 每月 25 日 02:00 预建未来 3 个月分区
SELECT cron.schedule(
    'm09_surgery_log_partition',
    '0 2 25 * *',
    $$SELECT fn_m09_create_month_partitions('m09_surgery_log', 3)$$
);
```

**为什么要预建分区：** 若 11 月 1 日的分区不存在，当天 00:00 后第一条手术记录写入会报 `no partition of relation "m09_surgery_log" found for row`，导致麻醉开始动作失败。预建 3 个月给运维留足容错窗口。

**归档流程（在线保留 3 年）：**

```sql
-- 1) 建归档表
CREATE TABLE IF NOT EXISTS m09_surgery_log_archive (
    LIKE m09_surgery_log INCLUDING ALL
);

-- 2) 迁出数据
INSERT INTO m09_surgery_log_archive SELECT * FROM m09_surgery_log_202310;

-- 3) 核对行数（必须一致）
SELECT
    (SELECT COUNT(*) FROM m09_surgery_log_archive
     WHERE seq_date >= '2023-10-01' AND seq_date < '2023-11-01') AS archived,
    (SELECT COUNT(*) FROM m09_surgery_log_202310) AS original;

-- 4) 分离并删除分区
ALTER TABLE m09_surgery_log DETACH PARTITION m09_surgery_log_202310;
DROP TABLE m09_surgery_log_202310;
```

**归档铁律：归档表行数必须与被删行数完全一致才可删主表。** 这是防止归档脚本中途失败导致数据丢失的最后一道检查。
