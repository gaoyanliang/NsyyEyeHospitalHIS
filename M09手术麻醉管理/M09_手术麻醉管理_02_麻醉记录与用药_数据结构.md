**设计说明：**

1. **`m09_anesthesia_record` 是 M09-02 的唯一主线**：6 张子表全部通过 `record_id` 挂上来。一台次一记录由 `uk_m09_ans_schedule` 保证。

2. **`m09_vital_sign` 是最大的表**：日均 55 台 × 13 组 = 715 行，年 26 万行，15 年约 390 万行。它是时间序列数据，索引设计必须围绕"按 record_id + 时间排序"与"取最近 N 条"。

3. **`m09_drug_admin` 与 M14-09 是弱耦合**：只存 `narcotic_register_status` 与外部返回的 `narcotic_deposit_no`，**不存 M14-09 的任何明细**。原因为：麻醉药品的实物管理（库存、批次、空安瓿）归 M14-09，M09-02 只关心"这次给药有没有完成法规登记"这一状态。

4. **`plan_snapshot` 与 `allergy_snapshot` 用 JSONB 而非关联查询**：
   - 方案可能被 M09-01 修订（版本 2、版本 3），但**本次麻醉实际对照的是哪一版方案**必须固化
   - 过敏史可能被 M03-01 更新（患者后来说"我还对 XX 过敏"），但**给药时的禁忌判定依据**必须是当时那份
   - 这两个快照是医疗纠纷取证的关键——"当时系统凭什么允许给这个药"

5. **无任何物理外键**：`m09_or_reception_id` 跨子模块、`m09_vital_sign.record_id` 高频写入。加外键会带来锁竞争与归档迁移困难。一致性由应用层事务 + CHECK 约束 + 每日孤儿巡检三层保证。

6. **无分区**：所有表都有跨年份唯一约束（`uk_m09_ans_schedule`、`uk_m09_ans_no`），分区会迫使唯一索引含分区键从而破坏语义（详见 4.2 设计要点）。

**约束说明：**

```sql
ALTER TABLE m09_anesthesia_record
    ADD CONSTRAINT ck_m09_ans_no CHECK (record_no ~ '^ANS[0-9]{8}[A-Z0-9]{2,4}[0-9]{3}$'),
    ADD CONSTRAINT ck_m09_ans_status CHECK (status IN (
        'IN_PROGRESS','ENDED','RECOVERY_SCORING','COMPLETED','SUMMARY_SIGNED','CANCELLED'
    )),
    ADD CONSTRAINT ck_m09_ans_type CHECK (anesthesia_type IN (
        'SURFACE','LOCAL_INFILTRATION','PERIBULBAR','RETROBULBAR','SUBTENON',
        'NERVE_BLOCK','SEDATION','SPINAL','GENERAL','COMBINED'
    )),
    ADD CONSTRAINT ck_m09_ans_level CHECK (
        anesthesia_level IS NULL OR anesthesia_level IN ('LOCAL','REGIONAL','GENERAL')
    ),
    ADD CONSTRAINT ck_m09_ans_eye CHECK (eye_side IS NULL OR eye_side IN ('OD','OS','OU','NA')),
    ADD CONSTRAINT ck_m09_ans_gender CHECK (gender IS NULL OR gender IN ('M','F')),
    ADD CONSTRAINT ck_m09_ans_seq CHECK (seq_no >= 1 AND seq_no <= 99),
    -- 时间戳时序自洽（医疗纠纷举证核心）
    ADD CONSTRAINT ck_m09_ans_time_seq CHECK (
        (anesthesia_end_at IS NULL OR anesthesia_end_at > anesthesia_start_at)
        AND (exit_room_at IS NULL OR anesthesia_end_at IS NULL OR exit_room_at >= anesthesia_end_at)
        AND (extubation_at IS NULL OR extubation_at >= anesthesia_start_at)
    ),
    -- 麻醉结束态必有时长
    ADD CONSTRAINT ck_m09_ans_ended CHECK (
        anesthesia_end_at IS NULL
        OR (anesthesia_duration_minutes IS NOT NULL AND anesthesia_duration_minutes >= 0)
    ),
    -- 全麻/联合麻醉必须填拔管标志
    ADD CONSTRAINT ck_m09_ans_extubation CHECK (
        status IN ('IN_PROGRESS','CANCELLED')
        OR anesthesia_type NOT IN ('GENERAL','COMBINED')
        OR extubation IS NOT NULL
    ),
    -- 拔管为真必须有拔管时刻
    ADD CONSTRAINT ck_m09_ans_extubation_at CHECK (
        extubation IS DISTINCT FROM TRUE OR extubation_at IS NOT NULL
    ),
    -- 离室态必须有离室时刻
    ADD CONSTRAINT ck_m09_ans_exit CHECK (
        status NOT IN ('COMPLETED','SUMMARY_SIGNED') OR exit_room_at IS NOT NULL
    ),
    -- 苏醒时长自洽
    ADD CONSTRAINT ck_m09_ans_recovery CHECK (
        exit_room_at IS NULL OR anesthesia_end_at IS NULL
        OR recovery_minutes IS NULL
        OR recovery_minutes = GREATEST(0, EXTRACT(EPOCH FROM (exit_room_at - anesthesia_end_at))::INT / 60)
    ),
    -- 计数非负
    ADD CONSTRAINT ck_m09_ans_counts CHECK (
        vital_count >= 0 AND drug_count >= 0 AND event_count >= 0 AND narcotic_pending_count >= 0
    ),
    -- 归档态必须齐三要素
    ADD CONSTRAINT ck_m09_ans_archived CHECK (
        archived = FALSE OR (archived_at IS NOT NULL AND status = 'SUMMARY_SIGNED')
    ),
    -- 归档后不可再改（应用层校验为主，此处兜底禁改关键字段由触发器实现）
    ADD CONSTRAINT ck_m09_ans_summary_signed CHECK (
        status <> 'SUMMARY_SIGNED' OR (exit_room_at IS NOT NULL AND anesthesia_end_at IS NOT NULL)
    );

COMMENT ON TABLE m09_anesthesia_record IS 'M09-02 麻醉记录主表（一台次一条）';

```

**设计要点：**

1. **`uk_m09_ans_schedule` 是幂等的最后防线。** M09-01 可能因网络重试多次触发"开始麻醉"。应用层"先查后插"在并发下有竞态窗口（两个请求同时查不到然后都插入）。捕获 `IntegrityError` 后返回已有记录，实现幂等——这是唯一可靠的保证。

2. **三个快照字段（`plan_snapshot` / `allergy_snapshot`）比关联查询重要。** 真实场景：患者术后说"我对利多卡因过敏"，M03-01 的记录被更新，家属质疑"系统明知过敏还给这个药"。此时必须能证明"给药当时 M03-01 返回的是无过敏"。快照就是这份证据。

3. **`anesthesia_duration_minutes` 与 `recovery_minutes` 存储而非计算。** 理由有三：①M16-01 计费按麻醉时长分档，每秒重复计算不必要 ②报表按麻醉时长分布统计需索引 ③`ck_m09_ans_recovery` 保证与原始时刻一致。

4. **四个冗余计数（`vital_count` / `drug_count` / `event_count` / `narcotic_pending_count`）**：工作台与列表要显示"已录 10 组体征、5 条给药"，若每次 `COUNT(*)` 子表，一屏 20 条记录就是 80 次子查询。冗余计数在写入时原子递增，读时 O(1)。

5. **无分区。** 若按 `record_date` 年度分区，`uk_m09_ans_schedule` 必须含分区键变为 `(schedule_id, record_date)`，唯一性退化为"同年内一台次一条"——去年台次被重新处理会产生重复记录。同理 `uk_m09_ans_no`。15 年约 30 万行在主键查询下仍在 1ms 内，分区收益远小于代价。

```sql
    ),

        interval_minutes IS NULL OR interval_minutes >= 0
    ),

        mean_bp IS NULL OR systolic_bp IS NULL OR diastolic_bp IS NULL

    );

-- 平均压生成列
ALTER TABLE m09_vital_sign DROP COLUMN IF EXISTS mean_bp;
ALTER TABLE m09_vital_sign
    ADD COLUMN mean_bp SMALLINT GENERATED ALWAYS AS (
        CASE WHEN systolic_bp IS NOT NULL AND diastolic_bp IS NOT NULL
             THEN ROUND((systolic_bp + 2 * diastolic_bp) / 3.0)::SMALLINT

COMMENT ON COLUMN m09_vital_sign.interval_minutes IS '距上一条记录的分钟数，第一条为 NULL';
COMMENT ON COLUMN m09_vital_sign.suggested_events IS '系统根据体征建议记录的术中事件类型';
```

**设计要点：**

1. **`mean_bp` 是生成列而非普通字段。** 平均压由收缩压与舒张压唯一确定，应用层忘记更新会导致三者不一致。生成列零维护成本，且 `ck_m09_vital_mean` 可以移除——但保留一个基于生成列的断言无意义，所以此处用生成列 + 单独约束只在首次建表时校验一致（PostgreSQL 会对生成列自动校验）。

2. **`interval_minutes` 与 `is_interval_ok` 存快照。** "体征间隔达标率"是麻醉质控核心指标。事后若要重算，需要按麻醉类型判断间隔要求（全麻 5 分钟 / 局麻 15 分钟），若配置改了则历史达标率会变化。存快照后历史记录不可篡改。

3. **`suggested_events` 只记录系统建议，不代表已记录事件。** 系统检测到心率 42 建议"眼心反射"，但麻醉医生可能判断是"麻醉过深"而记录别的事件。两个字段分开，才能统计"系统建议的采纳率"。

4. **`schedule_id` 冗余。** 主查询是"按 record_id 查"，但 M06-07 内部契约要"按台次查全部术中数据"，若只存 record_id 需要先关联主表。冗余 schedule_id 后单表可查。

5. **无 `updated_at`。** 体征录入后 5 分钟内可删除，但不可修改——修改等于篡改监护记录。删除后重录，`is_deleted=TRUE` 保留痕迹。

```sql
    ADD CONSTRAINT ck_m09_drug_narcotic_success CHECK (
        narcotic_register_status IS DISTINCT FROM 'SUCCESS'
        OR (narcotic_deposit_no IS NOT NULL AND narcotic_registered_at IS NOT NULL)
    ),
    -- 登记失败必须有错误信息
    ADD CONSTRAINT ck_m09_drug_narcotic_fail CHECK (
```

**设计要点：**

1. **`narcotic_register_status` 有 4 态（NONE/PENDING/SUCCESS/FAILED）而非 2 态。** `NONE` 与 `PENDING` 必须区分：非麻醉药是 `NONE`，麻醉药已提交待登记是 `PENDING`。若共用 NULL 则无法区分"这条记录不该有登记"与"这条记录待登记"。

2. **登记失败不阻断给药保存。** 给药是临床事实（药已推入），登记是管理动作。若强制"登记成功才保存"，M14-09 一故障麻醉医生就无法记录——而药已经推进去了，记录必须落下。**临床事实永远优先于管理流程。** 失败后进入重试队列（10/30/60/120/300 秒），5 次全失败标 `FAILED` 并告警。

3. **`is_voided` 而非物理删除。** 给药记录是法律文书的一部分。误录后的正确处置是"作废并留痕"，不是"删掉当没发生"。作废必须有原因，且物理行保留供审计。

4. **`dose_exceed_approved_by` 允许 `is_voided=TRUE` 时为空。** 作废的超量给药无需审批人——它已经不存在了。

5. **三个药品属性布尔冗余（`is_narcotic` / `is_local_anesthetic` / `is_anticholinergic`）。** 这三个属性在方案确认与给药时反复用，每次都查 M01-03 一个 5 药方案要发 5 次请求。冗余存为快照后 O(1) 判断，且历史记录的属性不随主数据变化。

6. **无 `is_deleted`。** 给药记录只作废不删除，物理行永久保留。

```sql
    ),
    -- 加药干预必须有药品与剂量
```

**设计要点：**

1. **目标区间（`target_min` / `target_max`）存快照而非实时查配置。** 若某天科室把 Ramsay 目标从 2~3 调为 2~2，历史记录的"是否达标"会重算变化。存快照后"当时按什么标准判的"可还原。

2. **`is_cooperative` 是眼科特有的关键指标。** 白内障手术需要患者按指令转动眼球，镇静过深会导致眼球上翻（Bell 现象）。这个字段让质控能分析"有多少台手术因镇静过深影响了配合"。

3. **`intervention` 与 `intervention_drug_code/dose` 分开。** 干预措施可能只是"唤醒"（无药），也可能"加药"。分开后能统计"深度不足时有多少次通过加药纠正"。

4. **三种评分字段并存而非统一成 `score` + `scale`。** 用 `CHECK` 按 `method` 精确绑定哪个字段必填，让 `is_in_target` 的比较有明确的数值范围（Ramsay 1~6 vs BIS 0~100 不能混算）。若统一成 `score`，`CHECK` 无法表达"Ramsay 模式必须 1~6，BIS 模式必须 0~100"。

```sql
    ADD CONSTRAINT ck_m09_aldrete_activity CHECK (activity IN (0,1,2)),
    ADD CONSTRAINT ck_m09_aldrete_respiration CHECK (respiration IN (0,1,2)),
    ADD CONSTRAINT ck_m09_aldrete_circulation CHECK (circulation IN (0,1,2)),
    ADD CONSTRAINT ck_m09_aldrete_consciousness CHECK (consciousness IN (0,1,2)),

    ADD CONSTRAINT ck_m09_aldrete_seq CHECK (seq_no >= 1 AND seq_no <= 99),

    ADD CONSTRAINT ck_m09_aldrete_exit CHECK (
        can_exit_room = FALSE OR (
            total_score >= 9
            AND (zero_items IS NULL OR jsonb_array_length(zero_items) = 0)
        )
    ),
    -- 0 分项与各项一致

    -- 苏醒时长非负

        recovery_minutes IS NULL OR recovery_minutes >= 0
    );

ALTER TABLE m09_aldrete_score
    ADD COLUMN total_score SMALLINT GENERATED ALWAYS AS (
        activity + respiration + circulation + consciousness + oxygen_saturation
    ) STORED;

COMMENT ON COLUMN m09_aldrete_score.total_score IS '总分=5项之和，生成列 0~10';
COMMENT ON COLUMN m09_aldrete_score.can_exit_room IS '可离室：总分≥9 且无 0 分项（硬门槛）';
COMMENT ON COLUMN m09_aldrete_score.zero_items IS '0 分项列表，硬门槛不可代偿的依据';
```

**设计要点：**

1. **`total_score` 是生成列。** 由五项零和确定，应用层忘记更新会导致总分与实际不符。生成列保证永远一致。

2. **`can_exit_room` 在 DB 层强制 `total_score >= 9 AND 无 0 分项`。** 这条约束是最后防线：即便服务层判定逻辑有 bug（比如只判了总分），DB 也拒绝写入"总分 8 分却标可离室"。

3. **`zero_items` 单独存。** "为什么不能离室"若只存 `can_exit_room=false`，事后无法知道是因为总分低（比如 8 分）还是因为有 0 分项（比如血氧 0 分）。两者临床后果完全不同：前者多观察一会就行，后者可能需延长留观或转住院。

4. **多次评分保留全部记录（`seq_no`）。** 患者第一次评 8 分不能走，15 分钟后评 10 分可以走。两次都要留痕——这才是"何时达到离室标准"的完整证据。

```sql

    ADD CONSTRAINT ck_m09_sum_effect CHECK (
        effect_evaluation IS NULL OR effect_evaluation IN ('SATISFIED','BASIC','UNSATISFIED')
    ),
    ADD CONSTRAINT ck_m09_sum_followup CHECK (
        followup_suggestion IS NULL OR followup_suggestion IN (
            'NONE','ROUTINE','IOP_ATTENTION','HR_ATTENTION'
        )
    ),
    ADD CONSTRAINT ck_m09_sum_review CHECK (
        review_status IN ('NONE','PENDING','APPROVED')
    ),
    -- 不满意必须填说明（≥10 字）
    ADD CONSTRAINT ck_m09_sum_unsatisfied CHECK (
        effect_evaluation IS DISTINCT FROM 'UNSATISFIED'
        OR (effect_note IS NOT NULL AND char_length(btrim(effect_note)) >= 10)
    ),
    -- 签名必须齐五要素
    ADD CONSTRAINT ck_m09_sum_signed CHECK (
        signed_at IS NULL OR (
            signed_by IS NOT NULL AND signed_by_name IS NOT NULL
            AND signature_image_url IS NOT NULL AND signature_hash IS NOT NULL
            AND effect_evaluation IS NOT NULL AND followup_suggestion IS NOT NULL
            AND final_content_json IS NOT NULL
        )
    ),
    -- 签名哈希格式
    ADD CONSTRAINT ck_m09_sum_sig_hash CHECK (
        signature_hash IS NULL OR signature_hash ~ '^[0-9a-f]{64}$'
    ),
    -- PDF 哈希格式
    ADD CONSTRAINT ck_m09_sum_pdf_hash CHECK (
        pdf_hash IS NULL OR pdf_hash ~ '^[0-9a-f]{64}$'
    ),
    -- PDF URL 与哈希同有同空
    ADD CONSTRAINT ck_m09_sum_pdf CHECK (
        (pdf_url IS NULL AND pdf_hash IS NULL) OR (pdf_url IS NOT NULL AND pdf_hash IS NOT NULL)
    ),
    -- 审阅通过必须有意见
    ADD CONSTRAINT ck_m09_sum_reviewed CHECK (
        review_status <> 'APPROVED' OR (reviewed_by IS NOT NULL AND reviewed_at IS NOT NULL)
    ),
    -- 人工修改必须有说明
    ADD CONSTRAINT ck_m09_sum_manual CHECK (
        is_manual_edited = FALSE OR manual_edit_note IS NOT NULL
    );

COMMENT ON TABLE m09_anesthesia_summary IS 'M09-02 麻醉小结（六段+签名+PDF）';
COMMENT ON COLUMN m09_anesthesia_summary.content_json IS '系统自动生成的六段草稿（一~四、六自动，五为空）';
COMMENT ON COLUMN m09_anesthesia_summary.final_content_json IS '签名后的最终内容快照，不可变';
COMMENT ON COLUMN m09_anesthesia_summary.effect_evaluation IS '麻醉效果评价，必须人工填写';
COMMENT ON COLUMN m09_anesthesia_summary.pdf_hash IS '记录单 PDF 的 SHA-256，防篡改';
```

**设计要点：**

1. **`content_json` 与 `final_content_json` 双字段。** 草稿是系统生成的可变内容，最终是签名后的快照不可变。分离后可以对比"人工改了什么"——这是质控分析"系统自动生成质量"的数据基础。

2. **`ck_m09_sum_signed` 把"签名即责任"下沉到 DB。** 签名意味着麻醉医生对整份小结负责。若允许"签名了但没有签名图"或"签名了但没有麻醉效果评价"，这份小结在法律上是残缺的。DB 层强制保证 7 项齐全。

3. **`pdf_hash` 与 M12-03 的 PDF 指纹同一思路。** PDF 存对象存储，URL 可能被替换。存 SHA-256 后，调阅时可校验文件未被篡改。

4. **`review_status` 支持麻醉科主任审阅但非必需。** `NONE` 是默认（不审阅），只有抽查或严重事件才置 `PENDING`。这样避免了"每份都要主任看"的流程负担。

5. **`is_manual_edited` 记录草稿是否被人工修改。** 若 90% 的草稿都被大幅修改，说明自动生成逻辑有问题需要优化。这是产品迭代的数据依据。

```sql
CREATE OR REPLACE FUNCTION fn_m09_anesthesia_archive_guard()
RETURNS TRIGGER AS $$
BEGIN
    IF OLD.archived = TRUE AND NEW.archived = TRUE THEN
        IF NEW.anesthesia_start_at IS DISTINCT FROM OLD.anesthesia_start_at
           OR NEW.anesthesia_end_at IS DISTINCT FROM OLD.anesthesia_end_at
           OR NEW.exit_room_at IS DISTINCT FROM OLD.exit_room_at

        THEN
            RAISE EXCEPTION 'M09: 麻醉记录已归档，关键字段不可修改';
        END IF;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m09_ans_archive_guard
```

```python
    event_type: EventType
    severity: Severity = "MEDIUM"
    occurred_at: Optional[datetime] = None
    description: str = Field(..., min_length=10, max_length=1000)
    lowest_heart_rate: Optional[int] = Field(None, ge=20, le=250)
    lowest_spo2: Optional[int] = Field(None, ge=30, le=100)
    lowest_sbp: Optional[int] = Field(None, ge=40, le=300)
    highest_sbp: Optional[int] = Field(None, ge=40, le=300)
    treatments: List[str] = Field(default_factory=list, max_length=10)
    treatment_drug_code: Optional[str] = Field(None, max_length=32)
    treatment_drug_dose: Optional[Decimal] = Field(None, gt=0)
    treatment_drug_unit: Optional[str] = Field(None, max_length=16)
    recovery_at: Optional[datetime] = None
    outcome: Optional[EventOutcome] = None
    delay_surgery: bool = False
    convert_to_inpatient: bool = False
    notified_surgeon: bool = False
    notified_medical_affairs: bool = False
    remark: Optional[str] = Field(None, max_length=500)

    @model_validator(mode="after")
    def _check_specific(self) -> "EventIn":
        if self.event_type == "OCULOCARDIAC_REFLEX":
            if self.lowest_heart_rate is None:
                raise ValueError("眼心反射必须填写最低心率")
            if not self.treatments:
                raise ValueError("眼心反射必须记录至少一项处理措施")
        if self.event_type == "RESPIRATORY_DEPRESSION" and self.lowest_spo2 is None:
            raise ValueError("呼吸抑制必须填写最低血氧")
        if self.event_type == "BRADYCARDIA" and self.lowest_heart_rate is None:
            raise ValueError("心动过缓必须填写最低心率")
        if self.event_type == "HYPOTENSION" and self.lowest_sbp is None:
            raise ValueError("低血压必须填写最低收缩压")
        if self.severity == "CRITICAL" and not self.notified_medical_affairs:
            raise ValueError("严重级事件必须通知医务科")
        if self.recovery_at and self.occurred_at and self.recovery_at < self.occurred_at:
            raise ValueError("恢复时刻不得早于发生时刻")
        return self
```
