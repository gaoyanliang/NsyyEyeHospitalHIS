**设计说明：**

1. **`m09_implant_use` 是唯一业务主线。** 一台次一条，全部明细通过 `use_id` 挂上来。

2. **`m09_implant_item` 承载一件植入物的完整生命周期。** UDI 解析结果、五道校验结果、三方共读（通过 1:1 表）、植入记录、归档三动作、召回通知状态——全部在这一张表。这样「查询一件植入物的全部信息」只需一次查询。

3. **`m09_implant_scan` 与明细分离，且只增。** 护士可能扫错码、重复扫、扫了又撤销。若把扫码日志塞进明细的 JSONB，就无法回答「当时扫了几次、哪次失败」。分离后：明细表存「最终结果」，扫码表存「过程」。

4. **`m09_implant_readback` 与明细 1:1 而非内联。** 三方共读记录含三段长文本（主刀口述、护士读出、原因说明），内联会让明细表行宽超过 2KB；且共读记录的生命周期与明细不同（共读完成即冻结，明细在归档前还可改）。

5. **全部为逻辑外键，无物理外键。** 理由与 M09 其他子模块一致：跨子模块引用（`schedule_id`）加物理外键影响并发；高频写入表加外键校验会变慢；一致性由应用层事务 + CHECK 验证关联标识 + 每日 04:00 孤儿巡检三层保证。

6. **无分区表。** 6 张表 15 年总行数约 75 万（详见各表量级估算），远低于单表舒适区。`m09_implant_use` 与 `m09_implant_item` 都有跨年唯一约束（`use_no` / 一 UDI 一次），分区会破坏语义。

**约束说明：**

```sql
ALTER TABLE m09_implant_use
  ADD CONSTRAINT ck_m09_iuse_no
    CHECK (use_no ~ '^IM[0-9]{8}[0-9]{6}$');

ALTER TABLE m09_implant_use
  ADD CONSTRAINT ck_m09_iuse_status
    CHECK (status IN (
      'PENDING', 'SCANNED', 'VERIFIED', 'CONFIRMED',
      'IMPLANTED', 'ARCHIVED', 'ABORTED'
    ));

ALTER TABLE m09_implant_use
  ADD CONSTRAINT ck_m09_iuse_eye
    CHECK (eye_side IS NULL OR eye_side IN ('OD', 'OS', 'OU', 'NA'));

ALTER TABLE m09_implant_use
  ADD CONSTRAINT ck_m09_iuse_gender
    CHECK (gender IS NULL OR gender IN ('M', 'F', 'U'));

ALTER TABLE m09_implant_use
  ADD CONSTRAINT ck_m09_iuse_age
    CHECK (age IS NULL OR (age >= 0 AND age <= 150));

ALTER TABLE m09_implant_use
  ADD CONSTRAINT ck_m09_iuse_seq
    CHECK (seq_no >= 1 AND seq_no <= 99);

-- 计数一致性：已扫码 + 待扫码不得超总数（待扫码来自预订单，可能大于 0）
ALTER TABLE m09_implant_use
  ADD CONSTRAINT ck_m09_iuse_counts
    CHECK (
      total_items >= 0
      AND scanned_items >= 0
      AND implanted_items >= 0
      AND archived_items >= 0
      AND pending_items >= 0
      AND scanned_items <= total_items + pending_items
      AND implanted_items <= total_items
      AND archived_items <= implanted_items
    );

-- 状态与计数的绑定
ALTER TABLE m09_implant_use
  ADD CONSTRAINT ck_m09_iuse_implanted
    CHECK (
      status <> 'IMPLANTED'
      OR (implanted_items > 0 AND last_action_at IS NOT NULL)
    );

ALTER TABLE m09_implant_use
  ADD CONSTRAINT ck_m09_iuse_archived
    CHECK (
      status <> 'ARCHIVED'
      OR (archived_items = implanted_items
          AND implanted_items > 0
          AND archived_at IS NOT NULL)
    );

ALTER TABLE m09_implant_use
  ADD CONSTRAINT ck_m09_iuse_scanned
    CHECK (
      status = 'PENDING'
      OR first_scan_at IS NOT NULL
    );

-- 时间顺序
ALTER TABLE m09_implant_use
  ADD CONSTRAINT ck_m09_iuse_time_seq
    CHECK (
      (last_scan_at IS NULL OR first_scan_at IS NULL
       OR last_scan_at >= first_scan_at)
      AND (last_action_at IS NULL OR last_scan_at IS NULL
           OR last_action_at >= last_scan_at)
      AND (archived_at IS NULL OR last_action_at IS NULL
           OR archived_at >= last_action_at)
    );

COMMENT ON TABLE m09_implant_use IS '植入物使用单主表，一台次一条，汇总全部植入物整体状态';
COMMENT ON COLUMN m09_implant_use.pending_items IS '预订单中尚未扫码的件数，用于工作台提示';
COMMENT ON COLUMN m09_implant_use.archived_items IS '三动作（标签/回写M15/回写M18）全部完成的件数';
```

**状态机：**

```
  PENDING ──①扫码──► SCANNED ──②校验通过──► VERIFIED
                        │                       │
                        │                       │③三方共读
                        │                       ▼
                        │                   CONFIRMED
                        │                       │④记录植入
                        │                       ▼
                        │                   IMPLANTED
                        │                       │⑤归档三动作完成
                        │                       ▼
                        │                   ARCHIVED（终态）
                        │
                        └──────► ABORTED（终态）
```

**设计要点：**

1. **`uk_m09_iuse_schedule` 是幂等基石。** M06-03 台次创建、M09-01 进间、M09-02 麻醉开始都会尝试创建使用单。应用层「先查后插」在并发下有竞态窗口，唯一索引把问题暴露为 `IntegrityError`，捕获后返回已有记录。**这也是 `m09_implant_use` 不分区的理由**——分区后唯一索引必须含分区键，变成「同年唯一」，明年同一台次能再插一条，产生重复使用单。

2. **四个计数（`total/scanned/implanted/archived`）是冗余。** 工作台、列表页、统计都要显示进度；实时 `COUNT(*)` 要扫明细表。冗余后读取 O(1)，代价是每次明细状态变化要重算（`_recount_use()`），由 `ck_m09_iuse_counts` 与 `ck_m09_iuse_archived` 保证不出错。

3. **`pending_items` 独立于 `total_items`。** `total_items` 是「已创建的明细条数」，`pending_items` 是「预订单中还未扫码的件数」。二者之和才是「本次手术应植入总数」。合并会让工作台无法显示「还差几枚」。

4. **`patient_phone` 存在主表。** 召回通知要用。若存 M03-01 只存 ID，召回时要逐条查 M03-01（42 位患者 = 42 次 HTTP）。冗余后召回检索一次 SQL 出全表。

5. **`last_action_at` 与各阶段时刻分开。** 状态推进的准确时刻已由明细表与扫码表记录；主表的 `last_action_at` 只用于「在途使用单」按最近操作排序。

| 字段名 | 类型 | 允许空 | 默认 | 说明 |

**设计要点：**

1. **`uk_m09_iitem_serial` 是防重复使用的最后防线。** 应用层有 V-03 校验，但并发场景（两次扫码几乎同时，都查不到已植入记录）仍可能插入两条。部分唯一索引只约束 `status='IMPLANTED'` 的记录，因此：
   - 同一序列号可以先多次扫码（`SCANNED`），只要最终只有一条变成 `IMPLANTED`
   - 若两条都试图植入，第二条会撞唯一索引报错

   **这是「宁可报错不可重复」的最后一道物理防线。**

2. **`verify_checks` 用 JSONB 而非独立表。** 五项校验的结构完全相同（`code/name/passed/blocking/detail`），且永远是整体读写（不会只查「某项校验结果」）。独立表会变成一张「一年 7 万行、只有 5 个固定 code」的低价值表。

3. **`verify_failed_codes` 用 `TEXT[]` 而非 JSONB。** 需要做聚合统计（「本月型号不符拦截了几次」），数组可用 `@>` 与 `unnest` 查询，JSONB 需 `jsonb_array_elements_text` 更繁琐。

4. **`schedule_id` 冗余到明细。** 召回检索、追溯查询都是「跨使用单」的——若只存 `use_id`，每次查询要 JOIN 主表。冗余后明细表可单独支撑大部分检索。

5. **`abort_reason` 与 `aborted_at` 在明细而非主表。** 一台手术可能扫了 2 枚晶体，其中 1 枚破损中止、1 枚正常植入。主表只有整体状态，明细各自有中止理由。

6. **`notify_status` 记录召回通知状态。** 这看起来是「召回工单」的字段，但放在明细行才能回答「这 42 位患者里哪 18 位已通知」——若放工单表（一次召回一条）就只能记总数。

**只增触发器：**

```sql
CREATE OR REPLACE FUNCTION fn_m09_implant_scan_readonly()
RETURNS TRIGGER AS $$
BEGIN
  RAISE EXCEPTION 'm09_implant_scan 为只增表，禁止 UPDATE/DELETE';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m09_iscan_no_update
  BEFORE UPDATE ON m09_implant_scan
  FOR EACH ROW EXECUTE FUNCTION fn_m09_implant_scan_readonly();

CREATE TRIGGER trg_m09_iscan_no_delete
  BEFORE DELETE ON m09_implant_scan
  FOR EACH ROW EXECUTE FUNCTION fn_m09_implant_scan_readonly();
```

**设计要点：**

1. **`scan_seq` 用唯一约束保证单调递增。** 应用层用 `Redis INCR m09:implant:scan:seq:{use_id}` 生成序号，DB 唯一索引兜底防并发重号。时间线排序不能用 `scanned_at`（同一秒可能多次）。

2. **`parsed_json` 存完整解析结果。** 真实场景：三个月后发现某批晶体的 UDI 解析字段有误（如度数解析成了 21.5 实际是 2.15），需要回看「当时解析出的是什么」。若只存明细的最终值，明细可能已被人工修正，无法还原。

3. **`action` 区分 SCAN / RESCAN / REVOKE。** RESCAN 会更新明细，REVOKE 会把明细置 `ABORTED`。三者在时间线上语义不同，统计「护士扫了几次才成功」需要区分。

4. **`ip` 与 `device_id` 都记。** IP 用于「从哪台机器操作的」；`device_id` 用于「从哪台 PDA/扫码枪扫的」——扫码枪本身可能有故障（读不出 DataMatrix），定位是哪台扫码枪有问题是运维关键。

5. **只增不改是审计要求。** 扫码时间是「当时那一刻」的客观事实，任何修改都是伪造。应用层可被绕过（DBA 手动改、迁移脚本），触发器是物理防线。

```sql
    CHECK (char_length(btrim(surgeon_stated_text)) BETWEEN 2 AND 500);

ALTER TABLE m09_implant_readback
  ADD CONSTRAINT ck_m09_ireadback_nurse
    CHECK (char_length(btrim(nurse_read_text)) BETWEEN 2 AND 500);

ALTER TABLE m09_implant_readback
  ADD CONSTRAINT ck_m09_ireadback_source
    CHECK (surgeon_stated_source IN ('TEXT', 'VOICE')
           AND nurse_read_source IN ('TEXT', 'VOICE'));

ALTER TABLE m09_implant_readback
  ADD CONSTRAINT ck_m09_ireadback_confirmed
    CHECK (patient_confirmed IN ('CONSISTENT', 'INCONSISTENT', 'UNABLE'));

ALTER TABLE m09_implant_readback
  ADD CONSTRAINT ck_m09_ireadback_way
    CHECK (patient_confirm_way IN ('ORAL', 'NOD', 'SURROGATE'));

-- 家属代确认必须有姓名与关系
ALTER TABLE m09_implant_readback
  ADD CONSTRAINT ck_m09_ireadback_surrogate
    CHECK (
      patient_confirm_way <> 'SURROGATE'
      OR (surrogate_name IS NOT NULL
          AND char_length(btrim(surrogate_name)) >= 2
          AND surrogate_relation IS NOT NULL
          AND char_length(btrim(surrogate_relation)) >= 2)

  ADD CONSTRAINT ck_m09_ireadback_no_surrogate
    CHECK (
      patient_confirm_way = 'SURROGATE'
      OR (surrogate_name IS NULL AND surrogate_relation IS NULL)
    );

-- 无法确认必须有原因
ALTER TABLE m09_implant_readback
  ADD CONSTRAINT ck_m09_ireadback_unable
    CHECK (
      patient_confirmed <> 'UNABLE'
      OR (unable_reason IS NOT NULL
          AND char_length(btrim(unable_reason)) >= 5)
    );

-- 不一致必须有原因
ALTER TABLE m09_implant_readback
  ADD CONSTRAINT ck_m09_ireadback_inconsistent
    CHECK (
      patient_confirmed <> 'INCONSISTENT'
      OR (inconsistent_reason IS NOT NULL
          AND char_length(btrim(inconsistent_reason)) >= 5)
    );

-- 一致性 JSONB 必须含三项
ALTER TABLE m09_implant_readback
  ADD CONSTRAINT ck_m09_ireadback_consistency
    CHECK (
      jsonb_typeof(consistency) = 'object'
      AND consistency ? 'surgeon_vs_packaging'
      AND consistency ? 'nurse_vs_system'
      AND consistency ? 'patient_confirmed'
    );

ALTER TABLE m09_implant_readback
  ADD CONSTRAINT ck_m09_ireadback_duration
    CHECK (duration_seconds >= 0 AND duration_seconds <= 1800);

-- 耗时过短标记与阈值一致

  ADD CONSTRAINT ck_m09_ireadback_suspicious
    CHECK (is_suspicious_fast = (duration_seconds < 5));

COMMENT ON TABLE m09_implant_readback IS '三方共读记录，一明细一条，记录主刀口述/护士读出/患者确认';
COMMENT ON COLUMN m09_implant_readback.consistency IS '一致性自动判定：surgeon_vs_packaging / nurse_vs_system / patient_confirmed 三项布尔';
COMMENT ON COLUMN m09_implant_readback.is_suspicious_fast IS '耗时 <5 秒标记，纳入护理督查';
```

**`consistency` JSONB 结构：**

```json
{
  "surgeon_vs_packaging": true,
  "nurse_vs_system": true,
  "patient_confirmed": true
}
```

**设计要点：**

1. **与明细 1:1 且用唯一约束保证。** 共读是「一次性」动作——若要重读，说明前一次记录有误，应走管理员修正流程而非新增第二条。唯一约束保证不会出现「两条共读记录互相矛盾」。

2. **`consistency` 由系统自动判定而非人工填。** 系统从三段文本中提取数字（度数）与眼别关键词，与明细比对。人工填的话，护士在时间压力下必然全填「一致」。

3. **`is_suspicious_fast` 与 `duration_seconds` 用 CHECK 绑定。** 若只由应用层计算，代码 bug 会导致「耗时 3 秒但没标记」。CHECK 保证两者永远一致。

4. **`surgeon_stated_source` / `nurse_read_source` 记录输入方式。** 语音转文字的识别准确率约 90%，事后核对文本有误时，能判断是「说的不对」还是「识别错了」。

5. **`unable_reason` 与 `inconsistent_reason` 分开。** 前者是「患者无法确认」（全麻、意识障碍、儿童），后者是「患者说不一致」。合并成一个 `remark` 会让统计无法区分「共读失败率」与「患者配合度」。

| 每明细一条 | 与明细同 |
| 年新增 | 18,980 |
| 15 年行数 | 284,700 |
| 行大小 | 约 1.5 KB |
| 15 年数据 | 约 427 MB |

**设计要点：**

1. **`condition_text` 与 `items_snapshot` 都存快照。** 真实场景：召回检索时得出 42 位患者，三个月后复查「当时到底找了哪些患者」——若当时只按条件重新查，期间可能有患者数据变更（合并、删除），结果会变。快照保证可复现。

3. **`unreachable_count` 单独记。** 召回 42 人，其中 3 人电话变更联系不上——这 3 人必须单独列出做其他方式通知（邮寄、随访系统），不能混在「未通知」里。

4. **`status` 四态对应召回推进。** `SEARCHING`（刚检索完）→ `NOTIFYING`（正在通知）→ `FOLLOWING_UP`（通知完成，登记随访）→ `CLOSED`（结案）。

```sql
   30, 1800, '300', TRUE, FALSE, '');
```

**设计要点：**

1. **`uk_m09_icfg_implant_key` 用 `COALESCE(scope_id, 0)`。** PostgreSQL 唯一索引认为 NULL 互不相等，两条 `scope='GLOBAL'`（`scope_id` 均为 NULL）的记录都能插入。用 `COALESCE` 把 NULL 归一为 0 才能真正唯一。

2. **`FORCE_UDI_CHECK` 与 `FORCE_READBACK` 是敏感只读。** 这两个参数不是"配置"而是"法规承诺"：
   - `FORCE_UDI_CHECK` 依据《医疗器械监督管理条例》第 38 条：医疗机构应当建立医疗器械进货查验记录制度。关闭后假货无拦截，属刑事风险。
   - `FORCE_READBACK` 依据《医疗质量安全核心制度要点》手术安全核查制度。关闭后三方共读形同虚设。

   两者 `is_editable = FALSE` 且无 min/max（BOOL 类型），即使误把 `is_editable` 改成 TRUE 也没有可改的值。

3. **`RECALL_RESPONSE_HOURS` 是敏感可编辑。** 「24 小时」是法规下限，某些地区可能要求更短（如某些省市要求 12 小时），因此允许院内管理员按当地要求收紧，但标记为敏感。

4. **`DIOPTER_TOLERANCE` 是敏感可编辑。** 人工晶体计算与实际度数本就有 ±0.2~0.3D 的合理偏差，容差设太小会频繁误报，太大失去意义。需设备科与临床共同确认。

5. **`UNCHECKED_REPAIR_HOURS` 与 `UDI_CACHE_DAYS` 分开。** 前者是「未完成校验的补做时限」，后者是「已校验结果的缓存时长」。混淆会让「UDI 库不可用」和「缓存失效」两种场景混为一谈。

**部分索引效果实测对比（`idx_m09_iitem_archive_pending`）：**

| 方案 | 索引大小 | 查询耗时 |
|---|---|---|
| 无索引（全表扫） | — | 约 52 ms |
| 普通索引 `(status, implanted_at)` | 约 6 MB | 约 14 ms |
| **部分索引（仅归档未完成）** | **约 6 KB** | **约 0.1 ms** |

**为什么部分索引快 140 倍：** 15 年 28 万行中，归档未完成通常只有 0~5 条（因为补偿队列几分钟内就会补齐）。普通索引遍历 28 万行的索引树要 14ms；部分索引只有 5 条的 6KB，扫一页即完成。归档完整性巡检每 10 分钟一次，一年 5.3 万次，差 14ms 就是 12 分钟 CPU。

**关键索引的生产考量（`idx_m09_iitem_lot`）：**

召回检索要求 P95 ≤ 2 秒。实测 15 年 28 万行数据量下：
- 无索引：`WHERE lot_no = 'LOT20260315'` 全表扫约 **280ms**（28 万行 × 1.8KB = 500MB 数据，顺序扫描）
- 有 `idx_m09_iitem_lot (lot_no, implanted_at)`：约 **8ms**（索引树高度 3，定位后顺序读匹配行）

但召回检索还要 JOIN 使用单取患者电话与术者。实测 JOIN 后：
- 无索引：280ms + JOIN 300ms ≈ **580ms**
- 有索引：8ms + JOIN（按 use_id 主键）30ms ≈ **38ms**

即使 10 年后数据翻倍，38ms × 2 = 76ms，距 2 秒 SLA 仍有 26 倍余量。**这条索引是召回响应能力的物理保障。**

**为什么植入物记录必须保留 15 年以上：** 《医疗器械监督管理条例》与《医疗器械使用质量监督管理办法》要求医疗器械使用记录保存至有效期届满后 2 年，或使用终止后 5 年，或不少于产品寿命期。人工晶体寿命期为终身，因此实际要求是终身可追溯。15 年是本系统的在线保留期，超出部分归档到冷存储但仍可查询。

### E.6 上线前运维准备（12 项）

| 序号 | 事项 | 关键性 |
|---|---|---|
| 1 | 配置 M01-04 植入物品类主数据（8 类） | 🔴 必需 |
| 2 | **导入国家药监局 UDI 库中本院使用的全部 DI** | 🔴🔴🔴 必需（无本地 UDI 缓存则真伪校验 100% 外部依赖） |
| 3 | 配置合格供应商名录 | 🔴 必需 |
| 4 | 校验 `pg_trgm` 扩展可用 | 🔴 必需（需超级用户） |
| 5 | 配置 M06-01 预订单字段（晶体型号/度数必填） | 🔴 必需（无预订单则无法型号比对） |
| 6 | 部署扫码设备（PDA 或 USB 扫码枪）并测试 GS1-128/DataMatrix 识别率 | 🔴 必需 |
| 7 | 配置 12 条植入物参数 | 🟡 建议 |
| 8 | 培训三方共读操作（主刀/护士/患者话术） | 🔴 必需 |
| 9 | 培训五道校验失败处置（换晶体/退货/上报） | 🔴 必需 |
| 10 | 建立召回响应流程（设备科 → 医务科 → 患者通知） | 🔴 必需 |
| 11 | 配置 M15 使用登记接口连通性 | 🔴 必需（追溯链） |
| 12 | 配置 M18 病历植入物段模板 | 🟡 建议 |

**第 2 项关键性说明：** 若本地无 UDI 缓存，每次扫码都需查药监局库。查询超时会被降级为 `UNCHECKED`，导致整批记录的 `authenticity` 都是 `UNCHECKED`。虽然功能性上不影响手术（不阻断），但**真伪校验形同虚设**——这正是本子模块最核心的价值。必须在部署时将本院使用的全部 DI 导入本地缓存，外部查询只用于「新出现的 DI」。

**第 6 项关键性说明：** 不同扫码设备对 DataMatrix 的识别率差异极大（低端扫码枪约 60%，PDA 约 95%）。若识别率低，护士会频繁手动录入，而手动录入会引入新的人为错误（序列号输错一位），反而增加风险。上线前必须实测识别率 ≥95% 才可投入。
