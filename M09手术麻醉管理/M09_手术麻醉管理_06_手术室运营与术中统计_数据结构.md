**设计说明：**

1. **`m09_oper_metric` 是纯结果表，不是事实表。** 它的每一行都可以由业务表重新计算得到，因此**允许删除重建**（日统计任务每次先 DELETE 后 INSERT）。这与 M09-01~05 的「业务事实只增不改」形成鲜明对比

2. **宽表主键是四元组 `(stat_date, granularity, dimension_type, dimension_value)`**，不是自增 ID。理由：
   - 天然幂等：重算同一行只需 `ON CONFLICT DO UPDATE`，不需要额外唯一索引
   - 查询天然按主键定位：报表查询总是「某日期区间 × 某粒度 × 某维度 × 某维度值」
   - 但 PostgreSQL 分区要求主键含分区键，本表不分区（见 4.2 设计要点）

3. **`metric_version` 在宽表中存的是字符串标签（`'V3'`）而非外键 ID。**
   - 理由一：宽表是快照，即使 `m09_metric_version` 记录被归档，历史宽表仍能说明「当时按哪个口径算的」
   - 理由二：跨版本对比时可直接按标签筛选
   - 代价：改名不可追溯。因此 `version_label` 一旦生效即**不可修改**（`ck_m09_mver_label_immutable`）

4. **`m09_metric_config` 与 `m09_metric_version` 是 1:N，不是 1:1。** 每个版本含 36 条指标定义（18 原子 + 14 派生 + 4 复合）。新建版本时整体复制，只有变更的项内容不同

5. **`m09_oper_target` 的 `dept_id` 允许 NULL（院级目标）。** 用 `COALESCE(dept_id, 0)` 参与唯一索引——PostgreSQL 认为 NULL 互不相等，若不加 COALESCE，同一个 `(2026, NULL, 'HOSPITAL', 'D-01')` 可以插入无数次

6. **`m09_oper_recalc_task` 独立成表而不是只记日志。** 理由：重算可能耗时数分钟（5 维度 × 365 天），需要可查询的进度与结果；且重算是需要审计的操作（谁在什么时候重算了哪段时间、为什么）

### 4.2 表：`m09_oper_metric`

**用途：** 运营指标预聚合宽表——36 项指标在 5 维度 × 5 粒度上的预计算结果。

**字段设计：**

| 字段名 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| stat_date | DATE | N | — | 统计日期（DAILY 为当日；MONTHLY 为当月 1 日；QUARTERLY 为季首日；YEARLY 为年首日）【PK1】 |
| granularity | VARCHAR(16) | N | — | 粒度：DAILY / WEEKLY / MONTHLY / QUARTERLY / YEARLY【PK2】 |
| dimension_type | VARCHAR(16) | N | — | 维度类型：DIM_HOSPITAL / DIM_DEPT / DIM_DOCTOR / DIM_ROOM / DIM_PROCEDURE【PK3】 |
| dimension_value | VARCHAR(64) | N | — | 维度值：ALL / DEPT_0102 / EMP_10023 / OR-01 / OP_CAT_IOL【PK4】 |
| dimension_name | VARCHAR(128) | Y | NULL | 维度显示名快照（白内障科 / 张明 / OR-01 / 白内障超声乳化术） |
| A-01 至 A-18 共 18 个原子指标 | | | | 见下方「L1 原子指标字段」 |
| D-01 至 D-14 共 14 个派生指标 | NUMERIC 系列 | Y | NULL | 见下方「L2 派生指标字段」；分母为 0 时为 NULL |
| C-01 至 C-04 共 4 个复合指标 | NUMERIC 系列 | Y | NULL | 见下方「L3 复合指标字段」 |
| metric_version | VARCHAR(16) | N | — | 计算时的口径版本标签（如 `'V3'`） |
| source_row_count | INTEGER | N | 0 | 参与计算的源行数（用于对账） |
| excluded_row_count | INTEGER | N | 0 | 被排除的源行数（缺时刻、时序颠倒等） |
| cross_month_flag | BOOLEAN | N | FALSE | 是否含跨月台次 |
| data_completeness | NUMERIC(5,2) | Y | NULL | 数据完整率（有完整进间离间的台次占比，%） |
| computed_at | TIMESTAMP | N | NOW() | 计算时刻 |
| computed_by | VARCHAR(64) | N | 'SYSTEM' | 计算者（SYSTEM / 手动重算的操作人工号） |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|---|---|---|---|

**约束说明：**

```sql
-- 主键
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT pk_m09_oper_metric
    PRIMARY KEY (stat_date, granularity, dimension_type, dimension_value);

-- 粒度枚举
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_granularity
    CHECK (granularity IN ('DAILY', 'WEEKLY', 'MONTHLY', 'QUARTERLY', 'YEARLY'));

-- 维度类型枚举
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_dim_type
    CHECK (dimension_type IN ('DIM_HOSPITAL', 'DIM_DEPT', 'DIM_DOCTOR',
                              'DIM_ROOM', 'DIM_PROCEDURE'));

-- 维度值非空
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_dim_value
    CHECK (char_length(btrim(dimension_value)) > 0);

-- 原子指标非负（时长、次数、金额均不可能为负）
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_atomic_nonneg
    CHECK (a01_schedule_count >= 0 AND a02_completed_count >= 0
       AND a03_cancelled_count >= 0 AND a04_first_case_count >= 0
       AND a05_punctual_count >= 0 AND a06_available_minutes >= 0
       AND a07_occupied_minutes >= 0 AND a08_net_surgery_minutes >= 0
       AND a09_turnover_minutes >= 0 AND a10_turnover_count >= 0
       AND a11_anesthesia_count >= 0 AND a12_anesthesia_minutes >= 0
       AND a13_count_checked_count >= 0 AND a14_count_mismatch_count >= 0
       AND a15_implant_item_count >= 0 AND a16_implant_amount >= 0
       AND a17_event_count >= 0 AND a18_critical_event_count >= 0);

-- 完成台次 + 取消台次 不得超过台次总数
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_count_sum
    CHECK (a02_completed_count + a03_cancelled_count <= a01_schedule_count);

-- 准点台次不得超过完成台次
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_punctual
    CHECK (a05_punctual_count <= a02_completed_count);

-- 首台台次不得超过台次总数
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_first_case
    CHECK (a04_first_case_count <= a01_schedule_count);

-- 占用分钟不得超过可用分钟（超出说明数据异常）
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_occupied
    CHECK (a07_occupied_minutes <= a06_available_minutes * 2);

-- 净手术分钟不得超过占用分钟
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_net_surgery
    CHECK (a08_net_surgery_minutes <= a07_occupied_minutes);

-- 危急事件数不得超过事件数
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_critical
    CHECK (a18_critical_event_count <= a17_event_count);

-- 源行数非负
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_row_count
    CHECK (source_row_count >= 0 AND excluded_row_count >= 0);

-- 数据完整率 0~100
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_completeness
    CHECK (data_completeness IS NULL
           OR (data_completeness >= 0 AND data_completeness <= 100));

-- 计算者非空
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_computed_by
    CHECK (char_length(btrim(computed_by)) > 0);

-- 口径版本标签非空
ALTER TABLE m09_oper_metric
    ADD CONSTRAINT ck_m09_om_metric_version
    CHECK (char_length(btrim(metric_version)) > 0);

-- 注释
COMMENT ON TABLE m09_oper_metric IS '运营指标预聚合宽表（可由业务表重算，允许删除重建）';
COMMENT ON COLUMN m09_oper_metric.stat_date IS '统计日期（按粒度对齐：DAILY 当日，MONTHLY 当月 1 日）';
COMMENT ON COLUMN m09_oper_metric.granularity IS '时间粒度';
COMMENT ON COLUMN m09_oper_metric.dimension_type IS '维度类型';
COMMENT ON COLUMN m09_oper_metric.dimension_value IS '维度值（ALL 表示全院）';
COMMENT ON COLUMN m09_oper_metric.a06_available_minutes IS '手术间可用分钟（分母，含维修与半日使用的扣减）';
COMMENT ON COLUMN m09_oper_metric.a07_occupied_minutes IS '手术间占用分钟（离间 − 进间，仅统计已完成的台次）';
COMMENT ON COLUMN m09_oper_metric.d01_utilization_rate IS '手术间利用率 = A-07 / A-06，百分比 2 位小数';
COMMENT ON COLUMN m09_oper_metric.metric_version IS '计算时的口径版本标签（字符串快照，不随版本表变化）';
COMMENT ON COLUMN m09_oper_metric.source_row_count IS '参与计算的源行数，用于与业务表对账';
COMMENT ON COLUMN m09_oper_metric.excluded_row_count IS '被排除的源行数（缺时刻、时序颠倒等）';
COMMENT ON COLUMN m09_oper_metric.cross_month_flag IS '是否含跨月台次（跨月手术按台次日期归属）';
COMMENT ON COLUMN m09_oper_metric.computed_by IS '计算者：SYSTEM 或手动重算操作人工号';
```

**量级估算：**

| 维度 | 每行数 | 说明 |
|---|---|---|
| DIM_HOSPITAL | 1 | 全院 |
| DIM_DEPT | 约 10 | 手术科室数 |
| DIM_DOCTOR | 约 48 | 主刀医生数 |
| DIM_ROOM | 4 | 手术间数 |
| DIM_PROCEDURE | 约 40 | 主要术式数 |

| **年合计（DAILY）** | **约 26,400**（255 工作日） | |

15 年数据量：26,400 × 15 + 1,236 × 15 ≈ **414,540 行**

单行估算：36 个数值列 × 平均 8 字节 + 4 个主键列约 60 字节 + 其他约 80 字节 ≈ **430 字节**

15 年容量：414,540 × 430 ≈ **178 MB**（数据）+ 索引约 **45 MB** = **约 223 MB**

**分区：**

**不分区。**

理由：

1. **主键是四元组**（含 `stat_date`）。若按 `stat_date` 做 RANGE 分区，主键必须含分区键——这在语法上可行（`stat_date` 已是 PK1），但会导致：
   - 跨年查询（如「近 3 年趋势」）必须扫描多个分区，且某些查询模式（如「按维度值查全部时间序列」）会退化为全分区扫描
   - 分区裁剪对 `stat_date` 有效，但对 `dimension_value` 无效

2. **数据量小。** 15 年 41.5 万行、223 MB，远未到需要分区的量级（PostgreSQL 单表 2,000 万行以下主键查询仍在 1 ms 内）

3. **需要跨年聚合。** 报表常查「今年 vs 去年」「近 3 年」，分区反而增加管理复杂度

4. **归档策略简单。** 15 年后整表归档到 `m09_oper_metric_archive`，无需按月切分

**状态机：**

```
                    ┌─────────┐
                    │  DRAFT  │ 草稿（可编辑，可删除）
                    └────┬────┘
                         │ 提交审批
                         ▼
                    ┌─────────┐
              ┌─────┤ PENDING │ 待审批
              │     └────┬────┘
       驳回   │          │ 第一签
              │          ▼
              │     ┌─────────┐
              │     │ PENDING │ 待第二签
              │     └────┬────┘
              │          │ 第二签
              │          ▼
              │     ┌──────────┐
              │     │ APPROVED │ 已批准（待生效）
              │     └────┬─────┘
              │          │ 定时任务到 effective_at
              │          ▼
              │     ┌────────────┐        新版本生效        ┌─────────────┐
              │     │ EFFECTIVE  │───────────────────────►│ SUPERSEDED  │
              │     └────────────┘                        └─────────────┘
              │
              ▼
        ┌──────────┐
        │ REJECTED │ 已驳回（终态，可复制重建）
        └──────────┘
```

**设计要点：**

1. **`uk_m09_mver_effective` 保证同时只有一个生效版本。** 这条部分唯一索引是整个口径体系的基石：
   - 没有它，两个人各自批准一个版本，两个都标 `EFFECTIVE`，统计任务不知道该用哪个
   - 定时任务生效逻辑：`UPDATE ... SET status='EFFECTIVE' WHERE status='APPROVED' AND effective_at<=now()` 在 `EFFECTIVE` 已存在时会失败（唯一冲突），必须先 `UPDATE 旧版本 SET status='SUPERSEDED', superseded_at=now()`

2. **`ck_m09_mver_effective_after_approve` 把「延后 24 小时」下沉到 DB。** 应用层校验 `"0906012"`，DB 层用 `effective_at > approved_at` 兜底。**为什么不校验 ≥ 24 小时**：DB 无法知道「申请时刻」，只能校验「晚于批准时刻」；且测试环境下允许缩短。

3. **`version_label` 一旦生效不可改**（虽然 DB 只能通过触发器强制，但本表规模极小（年 6 行），应用层简单禁止即可，不引入触发器）。理由：`m09_oper_metric.metric_version` 是字符串快照，改名会让历史宽表的标签对不上版本表。

4. **`test_result_json` 存测试快照而非只记「已测试」。** 真实场景：V4 声称「准点阈值改为 5 分钟后准点率从 80.6% 降到 72.1%」，若有人质疑「这数字哪来的」，测试快照能直接回答。

5. **不分区。** 年 6 行，15 年 90 行。

**量级估算：** 15 年约 **90 行**，约 **90 KB**。

```sql

ALTER TABLE m09_metric_config

    ADD CONSTRAINT ck_m09_mcfg_time_basis
    CHECK (time_basis IN ('SCHEDULE_DATE', 'INCISION_AT', 'CANCEL_AT'));

-- 派生指标必须有分子分母
ALTER TABLE m09_metric_config
    ADD CONSTRAINT ck_m09_mcfg_derived
    CHECK (metric_type <> 'DERIVED'
        OR (numerator_code IS NOT NULL AND denominator_code IS NOT NULL
            AND formula IS NOT NULL));

-- 复合指标必须有权重
ALTER TABLE m09_metric_config
    ADD CONSTRAINT ck_m09_mcfg_composite
    CHECK (metric_type <> 'COMPOSITE'
        OR (weight_json IS NOT NULL
            AND jsonb_typeof(weight_json) = 'object'
            AND formula IS NOT NULL));

-- 复合指标权重之和必须为 1（精度 1e-6）
ALTER TABLE m09_metric_config
    ADD CONSTRAINT ck_m09_mcfg_weight_sum
    CHECK (metric_type <> 'COMPOSITE'
        OR abs((SELECT COALESCE(SUM(value::numeric), 0)
                  FROM jsonb_each_text(weight_json)) - 1.0) < 0.000001);

-- 原子指标不可编辑
ALTER TABLE m09_metric_config

ALTER TABLE m09_metric_config

    CHECK ((threshold_value IS NULL AND threshold_operator IS NULL)

-- 小数位数 0~4
ALTER TABLE m09_metric_config
    ADD CONSTRAINT ck_m09_mcfg_decimal
    CHECK (decimal_places >= 0 AND decimal_places <= 4);

-- 排除规则必须是数组

COMMENT ON COLUMN m09_metric_config.denominator_code IS '分母指标编码（派生指标必填）';

COMMENT ON COLUMN m09_metric_config.threshold_operator IS '阈值方向：GTE 越高越好 / LTE 越低越好（取消率等反向指标）';
COMMENT ON COLUMN m09_metric_config.is_editable IS '原子指标从业务表直接聚合，口径不可改';
```

**设计要点：**

1. **`formula` 是「人类可读」的展示文本，不是可执行表达式。**
   - 若做成可执行表达式（如 `A-07 / A-06`），需要实现解析器与沙箱，安全风险与实现成本都高
   - 实际计算由代码按 `metric_code` 分支实现，`formula` 只用于页面展示与文档
   - 代价：新增指标要改代码。**但指标是低频的**（一年新增 1~2 个），可接受

2. **`numerator_code` / `denominator_code` 只支持两级（原子 → 派生）。** 不支持「派生 → 派生」是因为会引入依赖环风险（虽然 `"0906007"` 有检测），且实际业务中没有这种需求。

3. **`ck_m09_mcfg_code_type` 把编码前缀与类型绑死。** 防止「D-01 被标成 ATOMIC」这种脏数据——一旦出现，指标列表页的筛选会失效。

4. **`ck_m09_mcfg_weight_sum` 用子查询校验权重之和。** PostgreSQL 的 CHECK 约束**不允许**子查询，实际上这条约束无法直接实现。正确做法：
   - 应用层校验（`"0906009"`）
   - 或用一个 `IMMUTABLE` 函数封装求和逻辑
   - 本文档保留这条约束作为**设计意图表达**，实施时改为函数形式：
   ```sql
   CREATE OR REPLACE FUNCTION fn_m09_weight_sum_ok(p JSONB)
   RETURNS BOOLEAN AS $$
   DECLARE
       v_sum NUMERIC;
   BEGIN
       SELECT COALESCE(SUM(value::numeric), 0) INTO v_sum
         FROM jsonb_each_text(p);
       RETURN abs(v_sum - 1.0) < 0.000001;
   END;
   $$ LANGUAGE plpgsql IMMUTABLE;

   ALTER TABLE m09_metric_config
       ADD CONSTRAINT ck_m09_mcfg_weight_sum
       CHECK (metric_type <> 'COMPOSITE' OR fn_m09_weight_sum_ok(weight_json));
   ```

5. **不分区。** 36 条/版本 × 年 6 版 = 216 条/年，15 年 3,240 条。

**量级估算：** 15 年约 **3,240 行**，约 **1.6 MB**。

**设计要点：**

1. **`uk_m09_target_key` 用 `COALESCE(target_quarter, 0)` 与 `COALESCE(dept_id, '')`。**
   - PostgreSQL 唯一索引认为 `NULL` 互不相等，若不加 COALESCE，同一个 `(2026, NULL, 'HOSPITAL', NULL, 'D-01')` 年度目标可以插入无数次，报表取 `first()` 会拿到旧的那条，数字时对时错
   - 不用 `NULLS NOT DISTINCT`（PG 15+ 特性），因本项目部分环境仍是 PG 14

2. **`ck_m09_target_dept` 双向钉死院级与科室级。** 防止「院级目标带了 dept_id」或「科室级目标没有 dept_id」这种脏数据——前者会导致院级统计按科室过滤后为空。

3. **`ck_m09_target_actual` 强制实际值与达成率成组。** 防止「只更新了实际值忘了算达成率」——页面显示达成率是旧值而实际值是新值，管理者会看到「实际 80% 达成率 93.7%」这种矛盾数字。

4. **`ck_m09_target_sod` 把职责分离下沉 DB。** 调整申请人不能自己批准，否则「已开始季度改目标」的防护形同虚设。

5. **`dept_name` 存快照而非实时 JOIN。** 理由：科室改名后，历史目标仍应显示当时的科室名称；且避免每次查询目标列表 JOIN M01-01。

**量级估算：** 5 指标 × (1 院级 + 10 科室) × 4 季度 + 5 × 1 年度 = 225 条/年；15 年约 **3,375 行**，约 **1.4 MB**。

**设计要点：**

1. **`idx_m09_recalc_status` 用部分索引。** 理由：
   - 全表 15 年约 **7.5 万行**（日均 0.3 次手动 + 事件触发合并后约 10 次/天）
   - 进行中的任务通常只有 **0~2 条**
   - 无索引遍历 7.5 万行约 **18 ms**；普通索引约 **4 ms**；**部分索引约 8 KB / 0.1 ms**
   - 任务列表页每 5 秒刷新一次，一天 17,280 次 → 18 ms 是 5.2 分钟 CPU，0.1 ms 是 1.7 秒

2. **`PARTIAL` 状态独立存在。** 真实场景：重算 90 天，第 45 天因 M06-03 数据问题失败。若只标 `FAILED`，运维会以为全部白做；标 `SUCCESS` 又会掩盖问题。`PARTIAL` + `failed_dates` 让运维精确知道「第 45 天要重算」。

3. **`failed_dates` 用 JSONB 数组而非独立表。** 理由：失败日期通常 1~5 个，最多 30 个；查询模式是「打开任务详情看哪些天失败」，不按日期检索。

4. **`client_ip` 用 INET 类型。** 审计场景「谁从哪台机器重算了历史数据」，INET 支持 CIDR 匹配（如「只允许院内网 10.0.0.0/8 重算」）。

**量级估算：** 日均约 12 次（手动 0.3 + 事件触发合并后 10 + 定时 2）；年约 **4,380 行**；15 年约 **65,700 行**，约 **26 MB**。

**设计要点：**

1. **`uk_m09_ocfg_key` 用 `COALESCE(scope_id, '')`。** 与 M09-01~05 的配置表一致：
   - PostgreSQL 认为 `NULL` 互不相等，不加 COALESCE 则同一 GLOBAL 参数可插两条
   - 不用 `NULLS NOT DISTINCT`（PG 15+）

2. **`min_value` / `max_value` 强制 INT/FLOAT 必填。** 理由：防止未来新增参数忘了配范围，导致写入时无校验依据，运维可把 `PUNCTUAL_THRESHOLD_MINUTES` 改成 300。

3. **三个敏感参数 + 一个不可编辑参数。**
   - `PUNCTUAL_THRESHOLD_MINUTES`（敏感）：直接放大准点率
   - `METRIC_MIN_EFFECTIVE_HOURS`（敏感+只读）：关闭延后生效保护
   - `STAT_TIME_HOUR` / `STAT_SLA_HOUR`（只读）：改动会与全院日结冲突，读到未落定的结算数据

4. **`default_value` 支持「恢复默认」。** 真实场景：运维为排查把 `PUNCTUAL_THRESHOLD_MINUTES` 改成 30 忘了改回，导致三天内准点率虚高，无人察觉——有「恢复默认」按钮至少能一键纠正。

5. **`param_value` 统一存字符串。** 用 JSONB 存值类型自由，但无法在 SQL 里做范围校验；VARCHAR + `param_type` 显式声明，写入时按类型校验。

6. **不分区。** 15 条参数，规模固定。

**量级估算：** **15 行**，约 **8 KB**。

    granularity: Granularity = Field(..., description="时间粒度")
    date_from: date = Field(..., description="起始日期")
    date_to: date = Field(..., description="结束日期")

        if self.date_from > self.date_to:

        days = (self.date_to - self.date_from).days + 1
        limit = {
            "DAILY": 92,
            "WEEKLY": 364,
            "MONTHLY": 730,
            "QUARTERLY": 1825,
            "YEARLY": 1825,
        }[self.granularity]
        if days > limit:
            raise ValueError(
                "%s 粒度日期跨度不得超过 %d 天（当前 %d 天）"
                % (self.granularity, limit, days)
            )

        if self.metric_codes and len(self.metric_codes) > 12:
            raise ValueError("单次最多查询 12 个指标")
        return self

| 9 | 培训目标调整流程 | 🟡 | 已开始季度不可直改，需走调整审批 |
| 10 | 培训口径变更流程 | 🔴 | 双签 + 延后 24 小时，改错会让全院报表数字突变 |

**第 2 项与第 4 项最关键：**

- **第 2 项**：无目标则「达成率」「预警」「目标管理」全部失效。目标须在系统上线首月内由医务科与院领导确认
- **第 4 项**：本子模块所有时长类指标依赖 M06-03 与 M09-01/02 的时刻字段。若数据缺失，系统能跑但数字全错——**错的数字比没有数字更危险**，因为管理者会据此做决策。上线前必须抽样核对 30 台次，确认进间、离间、切皮、缝合四个时刻齐全且合理
