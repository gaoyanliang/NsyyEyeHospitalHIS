**设计说明：**

1. **`m09_or_reception` 是唯一业务主线**：M09-02~M09-06 全部通过 `reception_id` 或 `schedule_id` 挂上来，不各建一套主表。否则会出现"接收记录状态与麻醉记录状态不一致"的经典问题。

2. **评估与方案都是多版本（`version_no`）而非单条覆盖**：麻醉医生 A 评完接班给 B，B 重新评一次，两次都必须可追溯。理由与 M13-05 参考区间版本化一致——**事后追责问的是"当时怎么判的"，不是"最后一次怎么判的"**。

3. **无任何物理外键**：跨子模块引用（`m06_or_schedule`）与高频写入表（`m09_reception_log`）加外键会带来锁竞争与归档迁移困难。一致性由三层保证：
   - 应用层事务内成对写入
   - CHECK 约束验证关联标识非空
   - 每日 04:00 定时巡检孤儿数据

4. **`m09_reception_log` 分区而主表不分区**：日志是按时间查询的只增数据（一年 25 万条），分区后归档与查询都高效；主表有跨年份唯一约束（`uk_m09_rec_no`、`uk_m09_rec_schedule`），分区会迫使唯一索引含分区键从而破坏语义。

**约束说明：**

```sql
ALTER TABLE m09_or_reception
    ADD CONSTRAINT ck_m09_rec_no CHECK (reception_no ~ '^RCV[0-9]{8}[A-Z0-9]{2,4}[0-9]{3}$'),
    ADD CONSTRAINT ck_m09_rec_status CHECK (status IN (
        'PENDING','IN_ROOM','MONITORING','ASSESSED','READY','ANESTHESIA_STARTED','CANCELLED'
    )),
    ADD CONSTRAINT ck_m09_rec_eye CHECK (eye_side IS NULL OR eye_side IN ('OD','OS','OU','NA')),
    ADD CONSTRAINT ck_m09_rec_gender CHECK (gender IS NULL OR gender IN ('M','F')),
    ADD CONSTRAINT ck_m09_rec_seq CHECK (seq_no >= 1 AND seq_no <= 99),
    ADD CONSTRAINT ck_m09_rec_age CHECK (age IS NULL OR (age >= 0 AND age <= 150)),
    ADD CONSTRAINT ck_m09_rec_weight CHECK (weight_kg IS NULL OR (weight_kg >= 1 AND weight_kg <= 300)),
    ADD CONSTRAINT ck_m09_rec_height CHECK (height_cm IS NULL OR (height_cm >= 30 AND height_cm <= 250)),
    -- 时间戳时序自洽（医疗纠纷举证核心）
    ADD CONSTRAINT ck_m09_rec_time_seq CHECK (
        (or_in_at IS NULL OR planned_surgery_start_at IS NULL OR or_in_at >= planned_surgery_start_at - INTERVAL '6 hours')
        AND (monitoring_at IS NULL OR or_in_at IS NULL OR monitoring_at >= or_in_at)
        AND (anesthesia_start_at IS NULL OR monitoring_at IS NULL OR anesthesia_start_at >= monitoring_at)
    ),
    -- 进间后必有进间人与时刻
    ADD CONSTRAINT ck_m09_rec_or_in CHECK (
        status IN ('PENDING','CANCELLED') OR (or_in_at IS NOT NULL AND or_in_by IS NOT NULL)
    ),
    -- 监护后必有监护项
    ADD CONSTRAINT ck_m09_rec_monitoring CHECK (
        monitoring_at IS NULL OR (monitoring_items IS NOT NULL AND jsonb_array_length(monitoring_items) >= 3)
    ),
    -- 麻醉开始须有同意与监护前置（结构性兜底，业务层另有完整校验）
    ADD CONSTRAINT ck_m09_rec_anes_start CHECK (
        status <> 'ANESTHESIA_STARTED' OR (anesthesia_start_at IS NOT NULL AND monitoring_at IS NOT NULL)
    ),
    -- 取消必须有原因
    ADD CONSTRAINT ck_m09_rec_cancelled CHECK (
        status <> 'CANCELLED' OR (
            cancel_reason IS NOT NULL AND char_length(btrim(cancel_reason)) >= 10
            AND cancelled_at IS NOT NULL AND cancelled_by IS NOT NULL
        )
    ),
    -- 预警内容完整
    ADD CONSTRAINT ck_m09_rec_alert CHECK (
        has_alert = FALSE OR (alert_type IS NOT NULL AND alert_message IS NOT NULL)
    ),
    -- 预警处置需三要素齐全
    ADD CONSTRAINT ck_m09_rec_alert_handled CHECK (
        alert_handled = FALSE OR (alert_handled_at IS NOT NULL AND alert_handled_by IS NOT NULL)
    ),
    -- 回写失败须有原因
    ADD CONSTRAINT ck_m09_rec_writeback_fail CHECK (
        writeback_status <> 'FAILED' OR writeback_error IS NOT NULL
    );

COMMENT ON TABLE m09_or_reception IS 'M09-01 手术室接收记录（一台次一条）';
COMMENT ON COLUMN m09_or_reception.reception_no IS '接收编号 RCV+日期+手术间+台次';
COMMENT ON COLUMN m09_or_reception.schedule_id IS '台次ID，逻辑外键 m06_or_schedule.id';
COMMENT ON COLUMN m09_or_reception.status IS '接收状态 PENDING/IN_ROOM/MONITORING/ASSESSED/READY/ANESTHESIA_STARTED/CANCELLED';
COMMENT ON COLUMN m09_or_reception.or_in_at IS '进间时刻，术中时长统计起点';
COMMENT ON COLUMN m09_or_reception.anesthesia_start_at IS '麻醉开始时刻，触发 M09-02';
COMMENT ON COLUMN m09_or_reception.writeback_status IS '回写 M06-04 状态';

**设计要点：**

1. **`uk_m09_rec_schedule` 是幂等的最后防线**：M06-04 可能因网络重试多次发送 `on-timeout-completed`。应用层"先查后插"在并发下有竞态窗口（两个请求同时查不到然后都插入），**数据库唯一索引是唯一可靠保证**。捕获 `IntegrityError` 后返回已有记录，实现幂等。

2. **`ck_m09_rec_time_seq` 捕获了三类致命矛盾**：进间早于计划 6 小时以上（说明数据错乱）、监护早于进间、麻醉早于监护。这三条在纠纷取证时都是"记录不可信"的直接证据。

3. **`ck_m09_rec_or_in` 允许 `CANCELLED` 无进间时刻**：患者在门口因故不做了，从未进间就取消，这是正常流程。

4. **`ck_m09_rec_monitoring` 要求 ≥3 项而非仅非空**：业务规则要求"至少心电、血压、血氧"，若只校验非空，插一条 `["ECG"]` 就能绕过。**这条约束把业务规则下沉到了数据库层。**

5. **`writeback_status` 有 `NONE` 初始态**：不是所有接收记录都需要回写（`PENDING`/`IN_ROOM` 阶段未发生麻醉开始）。`NONE` 与 `PENDING`（待回写）必须区分，否则补偿任务会把所有记录都扫一遍。

6. **冗余了大量 M06/M03 字段的快照**：患者姓名、术式名、主刀名、麻醉医生名。理由有三：①工作台一次查 12 条不必跨 4 个模块发 48 次请求 ②M03 患者改名后历史记录保持原样（医疗记录保真）③M06 台次归档后仍能还原当时信息。

    ),

        status <> 'SUBMITTED' OR (
            asa_level IS NOT NULL AND assessed_by IS NOT NULL
            AND assessed_at IS NOT NULL AND fasting_ok IS NOT NULL
        )
    ),
    -- 主任确认三要素齐全
    ADD CONSTRAINT ck_m09_ase_chief CHECK (
        chief_confirmed_at IS NULL OR (chief_confirmed_by IS NOT NULL AND chief_confirmed_by_name IS NOT NULL)
    ),
    -- 需确认则确认前不可提交（结构兜底，业务层另有服务校验）
    ADD CONSTRAINT ck_m09_ase_chief_pending CHECK (
        need_chief_confirm = FALSE OR chief_confirmed_at IS NOT NULL OR status = 'DRAFT'
    );

-- BMI 生成列
ALTER TABLE m09_pre_anesthesia_assessment
    ADD COLUMN bmi GENERATED ALWAYS AS (
        CASE WHEN weight_kg IS NOT NULL AND height_cm IS NOT NULL AND height_cm > 0
             THEN ROUND(weight_kg / ((height_cm / 100.0) ^ 2), 1)
             ELSE NULL END
    ) STORED;

COMMENT ON COLUMN m09_pre_anesthesia_assessment.local_anesthetic_allergy IS '局麻药过敏，安全红线，方案不得含局麻药';
COMMENT ON COLUMN m09_pre_anesthesia_assessment.glaucoma IS '青光眼，抗胆碱药禁用';
COMMENT ON COLUMN m09_pre_anesthesia_assessment.asa_from_eligibility IS 'M06-01 准入时 ASA 分级，用于差异比对';
COMMENT ON COLUMN m09_pre_anesthesia_assessment.need_chief_confirm IS 'ASA III 或上感+全麻时需麻醉科主任确认';
```

**设计要点：**

1. **`bmi` 是生成列而非普通字段**：避免应用层忘记更新导致 BMI 与体重身高不一致。PostgreSQL 生成列在读取时计算，零维护成本。

2. **`ck_m09_ase_glaucoma` 要求勾青光眼必须选类型**：开角型青光眼对阿托品的风险远低于闭角型，但两者都禁（保守原则）。没有类型信息，质控无法分析"到底哪些青光眼患者用了抗胆碱药"。

3. **`ck_m09_ase_asa_diff` 只校验"填了就要够长"**：ASA 是否真的与准入值不同由服务层判断。若在 DB 层写"ASA 不同则必填原因"，需要跨列比较并处理 NULL，逻辑复杂且难以维护。

4. **`ck_m09_ase_chief_pending` 允许 DRAFT 态未确认**：评估草稿阶段主任还没看，这是正常的。只有提交时必须确认。

5. **`fasting_required_hours` 单独存**：规则来自配置（全麻 8h / 镇静 6h），事后若配置改了，"当时按几小时判的"必须可还原。这与 M06-01 阈值快照同源。

6. **`asm_from_eligibility` 存快照而非关联查询**：M06-01 的准入记录可能已被修订，但麻醉评估当时看到的是哪个值，必须固化。

**设计要点：**

1. **`ck_m09_plan_need_anes` 把"全麻必须有麻醉医生"下沉到 DB**：这条是法规要求（麻醉药品使用与麻醉操作须由具备资质的麻醉医生执行）。若只在服务层校验，任何绕过 API 的直接写入都会产生违规数据。

2. **`removed_default_drugs` 与 `added_drugs_reason` 用 JSONB 而非独立表**：这两种差异是方案级的整体信息，查询模式是"这个方案相对默认改了什么"，一次性读出。独立表在 95% 的情况下返回空结果，却要多一次 JOIN。

3. **`anesthesia_level` 与 `anesthesia_type` 都存**：前者是 LOCLA/REGIONAL/GENERAL 三分类（用于统计与权限），后者是 10 种细分（用于业务规则）。M01-07 主数据同时提供两者，快照下来避免跨模块查询。

4. **`version_no` 递增而非覆盖**：麻醉医生改方案必须留痕。真实场景：球后阻滞改全麻——为什么改？患者体位配合不佳？术中出血？改方案的原因与变更本身一样重要。

    ADD CONSTRAINT ck_m09_consent_sign_type CHECK (

    ADD CONSTRAINT ck_m09_consent_signed CHECK (
        status <> 'SIGNED'
        OR (sign_type IS NOT NULL AND signer_name IS NOT NULL AND signed_at IS NOT NULL)
    ),
    -- 患者本人签字必须有签名图（口头除外）
    ADD CONSTRAINT ck_m09_consent_patient_sign CHECK (
        sign_type <> 'PATIENT' OR signature_image_url IS NOT NULL
    ),
    -- 代理人签字必须有关系、姓名、证件后4位
    ADD CONSTRAINT ck_m09_consent_surrogate CHECK (
        sign_type <> 'SURROGATE'

    ),
    -- 口头同意必须有见证人
    ADD CONSTRAINT ck_m09_consent_oral CHECK (
        sign_type <> 'ORAL' OR witness_name IS NOT NULL
    ),
    -- 失效必须留痕
    ADD CONSTRAINT ck_m09_consent_supersede CHECK (
        status <> 'SUPERSEDED' OR (superseded_at IS NOT NULL AND superseded_by IS NOT NULL)
    ),
    -- 签名哈希格式
    ADD CONSTRAINT ck_m09_consent_hash CHECK (
        signature_hash IS NULL OR signature_hash ~ '^[0-9a-f]{64}$'
    );

**设计要点：**

1. **`uk_m09_consent_active` 是"同意书唯一有效"的结构保证**：麻醉方式一改，原同意书失效，患者须重新签署。若允许同时有多份 `SIGNED`，事后无法判断哪份对应最终方案。

2. **`ck_m09_consent_items` 硬编码 8**：告知要点数量是法规约定（8 项），防悄悄减少。若未来法规要求增加，改约束并升版本。

3. **`signature_hash` 的用途是防替换**：签名图存对象存储，URL 可能被篡改。存 SHA-256 后，调阅时可以校验图片未被换过。这与 M12-03 的 PDF 指纹同一思路。

4. **口头同意的 `witness_signature_url` 不强制**：紧急情况下见证人可能来不及签名，但必须有姓名。24 小时内补签由业务层提醒（`M09.CONSENT.ORAL_BACKFILL_HOURS`）。

5. **`relation` 允许"本人"**：患者本人签字时关系填"本人"。这看起来冗余，但统计"有多少份是本人签的"时不需要额外判断 `sign_type`。

$$ LANGUAGE plpgsql;

COMMENT ON COLUMN m09_reception_log.seq_date IS '分区键，必须等于 DATE(created_at)';

**设计要点：**

1. **只增触发器是审计合规的硬要求**：《医疗机构管理条例实施细则》要求医疗记录可追溯且不可篡改。应用层可被绕过（DBA 手动改、迁移脚本误操作），数据库触发器是最后防线。

2. **`detail_json` 记录操作明细**：如 `{"or_in_at": "...", "manual_barcode": true}`、`{"asa_from": "II", "asa_to": "III"}`。LATER 可做变更分析。

3. **`ck_m09_rlog_transit` 要求状态变更类动作必有前后状态**：审计时最常问的是"这个记录什么时候从 IN_ROOM 变成 MONITORING 的"，只有 to_status 没 from_status 就无法建立链条。

4. **`seq_date` 冗余列**：PostgreSQL 分区键不能是表达式（除非 PG 12+ 的表达式分区，但那样无法用 `WHERE created_at >= ?` 做分区裁剪）。冗余一个 `DATE(created_at)` 列后，查询可精确裁剪。

**分区策略：**

```sql
-- 按月 RANGE 分区，预建 36 个月
CREATE TABLE m09_reception_log (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    seq_date DATE NOT NULL,
    reception_id BIGINT NOT NULL,
    reception_no VARCHAR(32),
    schedule_id BIGINT,
    action VARCHAR(32) NOT NULL,
    from_status VARCHAR(24),
    to_status VARCHAR(24),
    result VARCHAR(16) NOT NULL DEFAULT 'SUCCESS',
    error_code VARCHAR(16),
    error_message VARCHAR(500),
    detail_json JSONB,
    operator_id BIGINT,
    operator_name VARCHAR(64),
    operator_role VARCHAR(32),
    client_ip INET,
    trace_id VARCHAR(32),
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    PRIMARY KEY (id, seq_date)
) PARTITION BY RANGE (seq_date);

DO $$
DECLARE
    v_i INTEGER;
    v_start DATE;
    v_end DATE;
BEGIN
    FOR v_i IN 0..35 LOOP
        v_start := DATE_TRUNC('month', DATE '2026-10-01') + (v_i || ' months')::INTERVAL;
        v_end := v_start + INTERVAL '1 month';
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m09_reception_log FOR VALUES FROM (%L) TO (%L)',
            'm09_reception_log_' || TO_CHAR(v_start, 'YYYYMM'), v_start, v_end
        );
    END LOOP;
END $$;
```

| 项目 | 值 |

| 年记录数 | 约 240,000 条 |

| 年数据量 | 约 72 MB |
| 在线 3 年 | 约 216 MB |
| 15 年合计（归档后保留分区） | 约 1.1 GB |

**分区：** 月度 RANGE 分区，预建 36 个月，在线保留 36 个月，之后归档到 `m09_reception_log_archive`（保留 15 年）。

**约束说明：**

```sql
ALTER TABLE m09_reception_config
    ADD CONSTRAINT ck_m09_rcfg_code CHECK (
        param_code ~ '^M09\.(RECEPTION|ASSESSMENT|FASTING|PLAN|CONSENT|WRITEBACK|CACHE|LIMIT)\.[A-Z][A-Z0-9_]*$'
    ),
    ADD CONSTRAINT ck_m09_rcfg_type CHECK (param_type IN ('INT','FLOAT','STRING','BOOL')),
    ADD CONSTRAINT ck_m09_rcfg_group CHECK (param_group IN (
        'RECEPTION','ASSESSMENT','FASTING','PLAN','CONSENT','WRITEBACK','CACHE','LIMIT'
    )),
    ADD CONSTRAINT ck_m09_rcfg_scope CHECK (scope IN ('GLOBAL','DEPT')),
    -- GLOBAL 作用域不得有 scope_id；DEPT 必须有
    ADD CONSTRAINT ck_m09_rcfg_global CHECK (scope <> 'GLOBAL' OR scope_id IS NULL),
    ADD CONSTRAINT ck_m09_rcfg_dept CHECK (scope = 'GLOBAL' OR scope_id IS NOT NULL),
    -- 数值型必须有范围
    ADD CONSTRAINT ck_m09_rcfg_range CHECK (
        param_type NOT IN ('INT','FLOAT') OR (min_value IS NOT NULL AND max_value IS NOT NULL)
    ),
    -- 敏感参数必须可编辑（否则既不能改也不能批）
    ADD CONSTRAINT ck_m09_rcfg_sensitive_editable CHECK (is_sensitive = FALSE OR is_editable = TRUE);

CREATE UNIQUE INDEX uk_m09_rcfg_key ON m09_reception_config (
    param_code, scope, COALESCE(scope_id, 0)
) WHERE is_deleted = FALSE;

COMMENT ON TABLE m09_reception_config IS 'M09-01 配置参数（23 条）';
COMMENT ON COLUMN m09_reception_config.param_value IS '统一存字符串，按 param_type 解释';
```

**设计要点：**

1. **`param_value` 统一存字符串**：JSONB 存值虽然灵活但无法在 SQL 层做范围校验。字符串 + `param_type` + `min_value`/`max_value` 可以在写入时精确校验。

2. **`COALESCE(scope_id, 0)` 而非 `NULLS NOT DISTINCT`**：后者是 PostgreSQL 15+ 特性，本项目部分环境仍是 PG 14。PostgreSQL 认为 NULL 与 NULL 不相等，不加 COALESCE 会导致同一参数可以有两条 GLOBAL 记录，读取时数值时对时错。

3. **配置表统一命名 `m09_reception_config`**：M09-02~M09-06 将各自建 `m09_*_config`，汇总时应考虑合并为 `m09_sys_config`。当前分表是为了子模块独立演进。

**量级估算：** 23 条，可忽略。

CREATE OR REPLACE FUNCTION fn_m09_create_month_partitions(p_table TEXT, p_months INT DEFAULT 3)
RETURNS INTEGER AS $$
DECLARE
    v_i INTEGER;
    v_start DATE;
    v_end DATE;
    v_created INTEGER := 0;
BEGIN
    FOR v_i IN 1..p_months LOOP
        v_start := DATE_TRUNC('month', CURRENT_DATE) + (v_i || ' months')::INTERVAL;
        v_end := v_start + INTERVAL '1 month';
        IF NOT EXISTS (
            SELECT 1 FROM pg_class WHERE relname = p_table || '_' || TO_CHAR(v_start, 'YYYYMM')
        ) THEN
            EXECUTE FORMAT(
                'CREATE TABLE %I PARTITION OF %I FOR VALUES FROM (%L) TO (%L)',
                p_table || '_' || TO_CHAR(v_start, 'YYYYMM'), p_table, v_start, v_end
            );
            v_created := v_created + 1;
        END IF;
    END LOOP;
    RETURN v_created;
END;
$$ LANGUAGE plpgsql;
