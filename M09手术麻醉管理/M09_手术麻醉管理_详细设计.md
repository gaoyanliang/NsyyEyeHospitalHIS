## 1. 模块概述

### 1.1 模块定位

**M09 手术麻醉管理回答一个问题：「这台手术在手术间里，具体发生了什么？」**

它承接 M06 日间手术管理交过来的台次，记录从患者进入手术间到离开手术间的全部医疗事实：谁在什么时候做了什么、用了什么药、切了什么、出了多少血、取出了什么标本、清点对不对、植入了什么、最后怎么写的记录。

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                    M09 在眼科日间手术全流程中的位置                            │
└──────────────────────────────────────────────────────────────────────────────┘

  M06 日间手术管理（全流程外壳）
  │
  ├─ M06-01 申请与准入        患者能不能做？医生有没有资质？
  ├─ M06-02 术前准备闭环      禁食、散瞳、术前检查
  ├─ M06-03 排程与手术室      哪天、哪个房间、第几台
  ├─ M06-04 核对与交接        四方核对、Time-Out、腕带
  │
  │        ┌─────────────────────────────────────────────┐
  │        │  ★ M09 手术麻醉管理（术中）                  │
  ├───────►│                                             │
  │        │  M09-01 接收与麻醉前评估                     │
  │        │    ↓ 进间 / 监护 / ASA 评级 / 麻醉方案        │
  │        │  M09-02 麻醉记录与用药                       │
  │        │    ↓ 生命体征 / 给药 / 麻醉深度 / Aldrete     │
  │        │  M09-03 手术记录与术中事件                   │
  │        │    ↓ 切皮缝合 / 手术步骤 / 出血 / 标本        │
  │        │  M09-04 器械清点与安全核查                   │
  │        │    ↓ 四次清点 / 双人签名 / 不符处置           │
  │        │  M09-05 植入物使用与扫码绑定                 │
  │        │    ↓ UDI 扫码 / 五道校验 / 三方共读           │
  │        │  M09-06 手术室运营与术中统计                 │

  │        └─────────────────────────────────────────────┘
  │                        │
  │                        │ 手术结束、离间
  │                        ▼
```

**一句话边界：**

> **M01-07 说「有哪些手术、几级、谁有资格做、需要准备什么」；M06 说「这一整天怎么组织」；M09 说「术中发生了什么」；M16 说「花多少钱」；M15 说「用了哪些耗材、植入物从哪来」。**

### 1.2 三条存在前提

M09 之所以必须独立存在，是因为有三件事只有它能回答：

**前提一：术中记录是两个独立的法定文书，不是一个。**

《病历书写基本规范》第十八条：「麻醉记录单应另立单页」；第十九条：「手术记录应由手术者书写，术后 24 小时内完成」。

- **手术记录**：主刀医生签，术后 24 小时内补写，内容是「切了什么、看到什么、怎么处理」
- **麻醉记录**：麻醉医生签，术中实时记录（每 5 分钟一组体征），内容是「给了什么药、生命体征如何变化、何时清醒」

如果把这两个挤进同一张表或同一个模块：

- 主刀能改麻醉记录，麻醉医生能改手术记录 —— **法规上是致命缺陷**
- 24 小时的补写窗口 vs 术中实时的分钟级记录 —— **时效要求完全不同**
- 手术记录是事件流，麻醉记录是时间序列 —— **数据形态完全不同**

**前提二：手术间占用时长唯一可信的来源是「进间」与「离间」时刻。**

一台白内障超声乳化手术：

- 切皮到缝合：**12 分钟**
- 患者进间到离间：**45 分钟**（含摆体位、消毒铺巾、麻醉、器械准备、纱布清点）

如果用手术后补写的切皮缝合时刻算手术间利用率，会把 45 分钟的占用算成 12 分钟，利用率虚高 275%。而「进间」「离间」这两个时刻，只有 M09-01 的记录能提供。

**前提三：植入物植入时刻与手术时间轴绑定，只有 M09 能表达。**

人工晶体的植入时刻必须在「切皮之后、缝合之前」。这个约束：

- M15 物资只知道「这批晶体出库了」，不知道「装进了哪只眼睛、什么时候装的」
- M06 全流程只知道「这台手术完成了」，不知道「晶体是 10:23 植入的」
- 只有 M09-05 能记录「在手术时间轴的 10:23，序列号 XXX 的晶体植入右眼囊袋内」

### 1.3 为什么是模块而不是功能

**理由一：手术麻醉占医院核心业务量与收入的绝对主体。**

| 维度 | 数据 |
|---|---|
| 日间手术台次 | 日均 30~60 台 |
| 占全部手术量 | 80% 以上（眼科特性） |
| 人工晶体单项占手术总费用 | 55%~75% |
| 手术收入占医院总收入 | 约 45%~55% |

**理由二：手术室是医院最贵、最稀缺的资源。**

一间标准眼科手术间（层流 + 显微镜 + 超乳仪 + 玻切机）：设备投入 **80 万~150 万元**，日运行成本（人力 + 折旧 + 耗材 + 层流能耗）**3,000~5,000 元**。

- 日排 8 台：单台分摊 375~625 元
- 日排 5 台：单台分摊 600~1,000 元
- **利用率每提升 10 个百分点，年节约成本约 100 万元**

**理由三：术中环节的医疗风险密度最高。**

| 风险 | 眼科发生率 | 后果 |
|---|---|---|
| 术眼错误 | 万分级 | 好眼受损，医疗事故 |
| 人工晶体型号/度数错 | 千分级 | 二次手术，纠纷 |
| 器械/纱布遗留 | 万分级 | 二次开刀，事故 |
| 眼心反射（心率骤降） | **1.5%** | 心脏停搏 |
| 后囊膜破裂 | **1%~2%** | 视力预后下降 |
| 球后出血 | **0.1%~0.5%** | 手术延期 |
| 眼球穿孔 | **0.05%** | 失明 |

**理由四：术中记录是医疗纠纷举证的核心证据。**

纠纷场景中，法院与鉴定机构必查：

1. 手术记录是否在 24 小时内完成
2. 麻醉记录是否完整（每 5 分钟一次体征）
3. Time-Out 是否执行、四方是否签名
4. 器械清点是否四次、是否双人签名
5. 植入物是否有 UDI 追溯、三方共读记录
6. 术中事件是否记录、是否及时处置

**这六项全部由 M09 承载。** 任何一项缺失，医院在纠纷中处于绝对劣势。

**关键依赖点：**

1. **M09-01 是唯一入口。** 没有接收记录：M09-02 无法开始麻醉、M09-03 无法记录切皮（切皮时刻必须 ≥ 麻醉开始时刻）、M09-04 无法开始清点
2. **M09-02 与 M09-03 并行但时刻交叉校验。** 手术切皮时刻必须晚于麻醉开始时刻；手术缝合时刻必须早于麻醉结束时刻
3. **M09-04 与 M09-05 独立于 M09-02/03。** 清点由护士执行、植入物由护士扫码，与医生书写并行
4. **M09-06 只读。** 唯一一个不产生业务事实的子模块，只聚合 M09-01~05 + M06 的数据

### 2.3 六条拆分主线

**主线一：按「手术室里谁在做什么」拆分，不按「数据表」拆分。**

手术间里同时有 **四类人** 在做四件不同的事：

| 人 | 在做什么 | 子模块 | 数据特征 |
|---|---|---|---|
| 麻醉医生 | 给药、看监护仪、记麻醉记录 | M09-02 | 时间序列（每 5 分钟） |
| 主刀医生 | 切、缝、写手术记录 | M09-03 | 事件流（切皮、步骤、缝合） |
| 器械护士 | 递器械、数器械 | M09-04 | 4 次 × N 件的矩阵 |
| 巡回护士 | 扫码、计数纱布、登记标本 | M09-05、M09-04 | 逐件扫码 |
| 有人汇总 | 看运营数据 | M09-06 | 预聚合宽表 |

如果按数据表拆，会把「麻醉记录 + 手术记录」合成一个「术中记录」子模块，导致两种完全不同的数据模型挤在一个 Service 层里。

**主线二：法规留痕必须独立且只增。**

三类证据链各有独立的表与只增保护：

| 证据 | 子模块 | 表 | 保护方式 |
|---|---|---|---|
| 麻醉记录 | M09-02 | `m09_anesthesia_summary` | 归档后禁改触发器 |
| 手术记录 | M09-03 | `m09_surgery_record` + `m09_surgery_log` | 记录版本快照 + 日志只增触发器 |
| 器械清点 | M09-04 | `m09_instrument_count` + `m09_count_detail` | 双人签名 + 日志只增触发器 |
| 植入物追溯 | M09-05 | `m09_implant_scan` | 只增触发器 |
| 运营口径 | M09-06 | `m09_metric_version` | 版本化 + 双签，不可修改 |

**主线三：医师与护士的职责必须分开到不同子模块。**

| 子模块 | 主要由谁操作 | 为什么必须独立 |
|---|---|---|
| M09-02 麻醉记录 | 麻醉医生 | 麻醉医生签的名字 |
| M09-03 手术记录 | 主刀医生 | 主刀签的名字 |
| M09-04 器械清点 | 器械护士 + 巡回护士 | 护士双签的名字 |
| M09-05 植入物扫码 | 巡回护士 | 护士扫的码 |

四条独立的签字链，不能互相覆盖。把 M09-03 与 M09-04 合成一个模块，Service 层的权限校验会变成「手术记录可写的人、清点可写的人、两个都不行的人」三重分支。

**主线四：M06 管外壳，M09 管术中（用户决策）。**

用户明确决策（m02290）：

- **M06 负责**：预约 → 术前 → 交接 → 术后复苏 → 离院的全流程状态机与流程控制
- **M09 负责**：手术间排班、术中记录、麻醉记录、器械护士清点、植入物扫码
- 具体边界：

| 事项 | 归属 | 说明 |
|---|---|---|
| 手术间排班与台次编号 | **M06-03** | M09 不排台次，只接收 |
| Time-Out 与四方核对 | **M06-04** | M09 不重复核对 |
| 进间登记 | **M09-01** | 唯一可信起点 |
| 麻醉前评估与方案 | **M09-01** | 麻醉医生的法定责任 |
| 麻醉记录与用药 | **M09-02** | 麻醉医生的法定责任 |
| 手术记录与术中事件 | **M09-03** | 主刀的法定责任 |
| 器械清点 | **M09-04** | 护士的法定责任 |
| 植入物扫码验证 | **M09-05** | 术中动作 |
| 植入物使用登记记录 | **M15** | 全院植入物台账（决策 3） |
| 复苏与离院评估 | **M06-05** | M09 只提供 Aldrete 评分 |
| 结算与归档 | **M06-06** | M09 只提供数据 |

**M09 未设计期间 M06 的处理**：M06-05/M06-06 对 M09 采用「本地快照 + 接口预留」，与 M16-03 对 M05 的做法一致（见 M06-06 详细设计 §10.1 U-05~U-08）。

**主线五：M09-06 统计独立，因为统计是对外承诺。**

等级评审、DRG-DIP 付费、院务会月报 — 三处都用 M09-06 的数字。而「手术间利用率」这一项就有四种算法（按台次时长 72% / 按占用 58% / 按进间到离间 81% / 按麻醉开始到离院 94%），差异达 **36 个百分点**。

统计口径必须是**显式定义、版本化、可追溯**的，不能散落在各 Service 层。

**主线六：配置与规则必须版本化（仅 M09-06 需要）。**

| 子模块 | 需要版本化吗 | 理由 |
|---|---|---|
| M09-01~05 | 否 | 记录事实，不存在「口径」问题 |
| M09-06 指标口径 | **是** | 口径变更会影响历史报表的可比性 |

M09-06 的口径版本化 + 双签审批 + 延后 24 小时生效，是整个行业中少数会对「统计口径」做治理的设计。

### 2.4 为什么不拆更多

**M09-07 术中并发症与不良事件：不拆。**

并发症数据分散在 M09-02（麻醉事件）、M09-03（手术事件）、M06-05（离院后并发症），要做完整的不良事件统计需要反向依赖 4 个模块，而自己的核心表只有 1~2 张。这是人为制造远程调用。

**M09-08 手术室床位与设备管理：不拆。**

- 手术间的设备台账在 M01-09 `md_device`
- 设备维修保养在 M15
- M09 只在 M09-04 需要「器械包」的信息，通过 M15 同步镜像

**M09-09 麻醉药品管理：不拆。**

麻醉药品（芬太尼、瑞芬太尼、丙泊酚）的库存、逐支登记、印鉴卡管理全部在 **M14-09 特殊管理药品**。M09-02 只在给药时调用 M14-09 的登记接口，不维护库存。

**等等 — 术中用完的麻醉药品空安瓿回收呢？**

由 M14-09 负责（`AMPOULE_BACK` 动作），M09-02 记录给药事实即可。

### 3.3 手术间占用的精确语义

这是 M09 给医院管理带来的最大增量价值。

```
时间轴（一台白内障手术）：

08:30 计划开始
  │
  ├─ 08:42 患者进间（or_in_at）          ← M09-01 进间登记
  │        扫腕带、摆体位、消毒铺巾
  ├─ 08:50 监护仪连接（monitoring_at）    ← M09-01
  ├─ 08:55 麻醉开始（anesthesia_start_at）← M09-01
  ├─ 09:02 切皮（incision_at）            ← M09-03
  │        超乳、吸皮质、植晶体
  ├─ 09:14 缝合（suture_at）              ← M09-03
  ├─ 09:20 麻醉结束（anesthesia_end_at）  ← M09-02
  ├─ 09:27 患者离间（or_out_at）          ← M09-02
  │
  ├─ 09:27~09:52 清台、清洁、器械再处理  ← 周转时间 25 分钟
  │
  └─ 09:52 下一台患者进间
```

**六个时刻的时长分解：**

| 时长 | 计算 | 本台值 | 意义 |
|---|---|---|---|
| 手术间占用 | `or_out_at − or_in_at` | **45 分钟** | 手术间被这台手术占用的真实时长 |
| 净手术 | `suture_at − incision_at` | **12 分钟** | 纯粹的"开刀时间" |
| 麻醉时长 | `anesthesia_end_at − anesthesia_start_at` | **25 分钟** | 麻醉医生的工作量 |
| 术前准备 | `incision_at − or_in_at` | **20 分钟** | 摆位、消毒、铺巾、麻醉 |
| 术后清理 | `or_out_at − suture_at` | **13 分钟** | 包扎、擦血、撤台 |
| 周转时间 | `next.or_in_at − or_out_at` | **25 分钟** | 手术间停用时长 |

**手术间利用率 = Σ占用 ÷ Σ可用。** 若只有切皮缝合数据，利用率会被算成 `12 ÷ 480 = 2.5%`；有完整记录则是 `45 ÷ 480 = 9.4%`（单台）。日排 8 台的真实利用率是 `8 × 45 ÷ 480 = 75%`，而只看切皮缝合会算出 `8 × 12 ÷ 480 = 20%`。

**这个差异直接决定了医院是否应该增加手术间。**

### 3.4 麻醉记录的三个维度

M09-02 的核心洞见：**体征、给药、事件必须是同一条时间轴上的三件事。**

```
09:00   ┃ 体征：血压 138/82, 心率 76, SpO2 98%
09:02   ┃ 给药：丙泊酚 120mg IV（麻醉诱导）
09:03   ┃ 体征：血压 112/68, 心率 68, SpO2 99%
09:05   ┃ 给药：咪达唑仑 2mg IV
09:07   ┃ 事件：球后阻滞注射
09:08   ┃ 事件：眼心反射触发
09:09   ┃ 体征：心率 42 ← 骤降
09:09   ┃ 事件：眼心反射（LOWEST_HR=42）
09:10   ┃ 给药：阿托品 0.5mg IV
09:12   ┃ 体征：心率 68 ← 恢复
```

如果这三类数据分散在三个不同的页面/接口，麻醉医生在紧急情况下（心率从 76 骤降到 42）需要切换页面看三处 —— 这在手术台边是不可接受的。

**设计方案：** M09-02 P01 一屏内曲线 + 给药标记 + 事件标记并列显示，曲线上给药用小三角、事件用红点标注。

### 3.5 器械清点的四次不可替代性

| 阶段 | 时机 | 为什么不可替代 |
|---|---|---|
| PRE（术前） | 患者进间前 | **建立基准。** 没有基准，后三次比对全失效 |
| PRE_CLOSE（关腔前） | 缝合前 | **唯一拦截时机。** 此刻发现还能取出 |
| POST_CLOSE（关腔后） | 缝合过程中 | 覆盖关闭过程新上台的器械 |
| POST_SUTURE（缝合后） | 缝合完成 | 覆盖缝合过程 + 最终确认 |

**为什么纱布必须单独结论：**

国内手术遗留物事件中，**纱布占 60% 以上**。如果纱布与器械混在一张清单统计「42 → 42 相符」，一旦数量错位（器械多 1 件、纱布少 1 块），总数仍然相符，**掩盖了纱布遗留**。

因此 M09-04 强制四类物品（器械 / 纱布 / 棉片 / 缝针）**各自独立得出结论**。

### 3.6 植入物的五道校验

人工晶体占手术总费用的 55%~75%（单焦点 800~2,500 元、多焦点 6,000~15,000 元、散光矫正 8,000~18,000 元）。

**装错类型 = 医疗纠纷 + 欺诈指控；装错度数 = 二次手术；假货 = 刑事风险。**

M09-05 五道校验全部 **BLOCK**：

| 校验 | 查什么 | 失败错误码 |
|---|---|---|
| V-01 真伪 | DI 在国家药监局 UDI 库 + 厂商在合格供应商名录 | `"0905020"` |
| V-02 有效期 | 有效期 ≥ 手术日期 | `"0905021"` |
| V-03 重复使用 | 该序列号未被任一台次使用 | `"0905022"` |
| V-04 型号匹配 | 扫码型号/规格/度数 vs 预订单 | `"0905023"` |
| V-05 眼别匹配 | vs 台次术眼 vs Time-Out 核对眼别 | `"0905024"` |

**为什么全部 BLOCK 不 WARN：**

型号错、眼别错、过期、假货、重复使用 — 任一单独就足以造成致残致命风险。如果允许「警告后继续」，护士在时间压力下必然选「继续」，扫码就变成装饰品。

**唯一例外：** M15 库存校验（E-01）与药监局 UDI 校验在外部依赖超时时降级为 `UNCHECKED` 并留痕，24 小时内补做 —— 网络不通不能把手术停掉，但必须在记录里标明「未完成真伪校验」。

### 3.7 三方共读

真实的错用场景不是系统校验失败，而是**人的记忆错**：系统所有电子校验都通过，但主刀记错了度数（本应 +21.0D 却说是 +20.0D）。

M09-05 的设计让三方在同一时刻用同一个数字互相校正：

1. **主刀口述**：植入部位、度数、型号
2. **护士读出包装**：度数、序列号、眼别、有效期
3. **患者或家属确认**：哪只眼、多少度

**为什么必须患者参与：** 患者是唯一能从「术前约定」角度校验的人；且一旦出事，患者是唯一能证明「当时医生说的是什么」的证人。

**共读耗时 < 5 秒标记 `is_suspicious_fast`：** 医疗纠纷中"你们说三方共读了只用了 3 秒？" — 5 秒是最低合理时长，标记后纳入护理督查。

### 3.8 手术记录的时限模型

《病历书写基本规范》第十九条：**手术记录应当在术后 24 小时内完成。**

M09-03 五级督查：

| 时刻 | 动作 | 对象 |
|---|---|---|
| T+12h | 首次提醒（站内信 + 短信） | 主刀 |
| T+18h | 二次提醒 | 主刀 + 一助 |
| T+24h | 超时标记 + 升级 | 科主任 |
| T+36h | 三级升级 | 医务科 |
| T+48h | 四级升级 | 分管院长 |

**时限从缝合时刻（`suture_at`）起算**，因为法规说的是「术后」。实测从 T+12h 开始提醒可以把按时完成率从 72% 提到 95%。

### 3.9 运营指标的三层模型

M09-06 的 36 个指标分三层：

| 层级 | 数量 | 特点 |
|---|---|---|
| L1 原子指标 | 18 | 从业务表直接聚合 |
| L2 派生指标 | 14 | 原子指标的四则运算 |
| L3 复合指标 | 4 | 派生指标的加权 |

**为什么分三层：**

1. **原子指标可复用**：一个「台次总数」被 6 个派生指标使用
2. **口径可追溯**：指标定义（分子/分母/排除/时间口径）显式存在 `m09_metric_config`
3. **性能可控**：18 个原子指标一次聚合，14 个派生 + 4 个复合在内存中计算

### 3.10 预聚合宽表

M09-06 的 `m09_oper_metric` 是纯结果表，可由业务表重新计算。

**实测对比（30 天 × 5 维度 × 36 指标）：**

| 方案 | P50 | P95 | 并发能力 |
|---|---|---|---|
| 实时 6 表 JOIN（无索引） | 2.8 秒 | 6.2 秒 | 不可用 |
| 实时 6 表 JOIN（加索引） | 420 ms | 1.1 秒 | 10 人打满连接池 |
| **预聚合宽表** | **28 ms** | **48 ms** | **100 人无压力** |

**58 倍差距，并发能力差 10 倍以上 — 这不是优化问题而是架构问题。**

### 4.3 三条数据铁律

**铁律一：关键留痕表只增不改。**

8 张表有只增触发器：

| 表 | 触发器 | 说明 |
|---|---|---|
| `m09_reception_log` | `fn_m09_reception_log_readonly()` | 禁止 UPDATE / DELETE |
| `m09_surgery_log` | `fn_m09_surglog_readonly()` | 同上 |
| `m09_instrument_log` | `fn_m09_instrument_log_readonly()` | 同上 |
| `m09_implant_scan` | `fn_m09_implant_scan_readonly()` | 同上 |
| `m09_surgery_record_version` | `fn_m09_surgver_readonly()` | 同上 |
| `m09_anesthesia_summary` | `fn_m09_anesthesia_archive_guard()` | 归档后禁改关键字段 |

**为什么用触发器而不是只靠应用层：** 应用层可被绕过 — DBA 手动改、迁移脚本误操作、其他服务的 bug。医疗记录不可篡改是法律要求（《医疗机构管理条例实施细则》）。

**铁律二：唯一性用部分索引，不用「先查后插」。**

| 场景 | 部分唯一索引 | 病态后果 |
|---|---|---|
| 一台次一接收记录 | `uk_m09_rec_schedule (schedule_id) WHERE is_deleted=FALSE` | 重复进间登记，进间时刻失真 |
| 一台次一麻醉记录 | `uk_m09_ans_schedule (schedule_id) WHERE is_deleted=FALSE` | 两份麻醉记录，体征数据分裂 |
| 一台次一手术记录 | `uk_m09_surg_schedule (schedule_id) WHERE is_deleted=FALSE` | 两份手术记录，纠纷时以哪份为准 |
| 一台次一清点单 | `uk_m09_icount_schedule (schedule_id) WHERE is_deleted=FALSE` | 两份清点单，标准数量冲突 |
| 一台次一使用单 | `uk_m09_iuse_schedule (schedule_id) WHERE is_deleted=FALSE` | 植入物重复登记 |
| 一个 UDI 一次植入 | `uk_m09_iitem_serial (serial_no) WHERE status='IMPLANTED'` | 同一晶体"植入"两次 |

应用层「先 SELECT 再 INSERT」在并发下有竞态窗口（两个请求同时 SELECT 到空，都 INSERT 成功）。

**铁律三：金额与时长必须精确类型。**

- **金额一律 `NUMERIC`，禁止 `FLOAT`。** `0.1 + 0.2 != 0.3` 的问题在金额上是不可接受的
- **行级先舍入**：`line_amount = ROUND(unit_price × quantity, 2)` 再累加，不是先累加再舍入
- **时长用 `INTEGER` 秒或分钟**，不用 `NUMERIC` 小时

### 4.4 分区与归档

| 表 | 分区 | 保留期 | 理由 |
|---|---|---|---|
| `m09_reception_log` | 月 RANGE（预建 36 月） | 在线 3 年 | 查最近 3 个月只扫 3 个分区 |
| `m09_surgery_log` | 月 RANGE（预建 36 月） | 在线 3 年 | 同上 |
| `m09_instrument_log` | 月 RANGE（预建 36 月） | 在线 3 年 | 同上 |
| 其余 37 张表 | **不分区** | 15 年 | 见下 |

**业务表不分区的核心理由：分区会破坏幂等与唯一性语义。**

以 `m09_or_reception` 为例：若按 `reception_date` 做年度 RANGE 分区，`uk_m09_rec_schedule (schedule_id)` 必须改为 `(schedule_id, reception_date)`，唯一性从「一台次一条记录」退化为「一台次一年一条记录」。跨年重复进间登记将无法被拦截。

**日志表为什么可以分区：** 日志无跨年份唯一约束（主键已含 `seq_date`）。

**不预建分区的后果：** PostgreSQL 写入报 `no partition of relation "m09_surgery_log" found for row`。若发生在 11 月 1 日 08:00 第一台手术，麻醉开始动作失败，整台手术流程被迫暂停。因此 `fn_m09_create_month_partitions` 由 cron 每月 25 日 02:00 预建未来 3 个月。

### 6.2 错误码规范

**格式：** 7 位字符串 `AABBCCC`

| 位 | 含义 | M09 取值 |
|---|---|---|
| AA | 模块号 | `09` |
| BB | 子模块号 | `01`~`06` |
| CCC | 子模块内序号 | `001`~`099` |

**错误码在响应中必须带引号：**

```json
{
  "code": "0901001",
  "message": "台次不存在或已结束",
  "data": null,
  "trace_id": "b7c8d9e0f1a2"
}
```

**为什么必须字符串：** `09` 开头的整数在 Python 中是非法八进制字面量（`0104001` 报 `SyntaxError: invalid token`）。这也意味着**系统级通用码仍为整数 0**：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "trace_id": "b7c8d9e0f1a2"
}
```

**M09 错误码区间：**

| 子模块 | 区间 | 实用数量 |

### 7.2 为什么需要独立的 m09-beat

Celery Beat 的精度是分钟级，且任务堆积时会延迟。而 M09 有三类「时间窗口」的作业：

| 作业 | 精度要求 | 后果 |
|---|---|---|
| 24h 时限督查 | 分钟级 | 晚了就没意义（已经超时） |
| 准入/术前准备提醒 | 分钟级 | 晚了手术已经开始了 |
| 分区自动创建 | 天级 | 可以用 Beat |

因此 **m09-beat 用独立 APScheduler 进程**，内存占用 < 100 MB，与 API 完全隔离。

### 10.1 降级矩阵

| M03-05 消息 | 通知 | 异步重试 | 不影响业务 |

### 10.2 四条降级铁律

**铁律一：安全相关依赖降级但不放行。**

M01-07 手术资质校验失败 → `NOT_EVALUATED` → 转人工复核。**绝不允许"报错放行"**。让资质不符的医生上台出事后医院承担全部责任。

**铁律二：医疗文书相关依赖失败标 UNKNOWN 不标缺件。**

M09 未上线时，M06-06 的 D-11~D-14（手术记录/麻醉记录/器械清点/护理记录）全部标 `UNKNOWN` 而非 `MISSING`。理由：宁可漏判不误判，误判会让护士去补一份本来就有的单据。

**铁律三：资金与追溯相关依赖失败必须阻断或补偿。**

- M14-09 印鉴卡不可用 → **阻断**（不能给无资质患者用麻精）
- M14-09 逐支登记不可用 → **补偿队列**（已给的药必须能记录，登记稍后补）
- 植入物 UDI 校验不可用 → 记 `UNCHECKED`（不能停手术，但必须标明未完成）

**铁律四：通知类依赖失败全部降级。**

M03-05 消息发送失败不影响任何业务动作，异步重试即可。

### 10.3 三层兜底

**第一层：数据库约束。** 189 条 CHECK 约束 + 40 张表的唯一索引 + 8 个只增触发器。

**第二层：服务层校验与状态机。** 每个业务动作前校验前置状态、并发锁、权限。

**第三层：定时巡检。** 每日 04:00 检查孤儿数据：
