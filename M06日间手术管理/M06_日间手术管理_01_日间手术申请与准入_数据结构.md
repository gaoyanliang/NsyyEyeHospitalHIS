**设计说明**

1. **`m06_day_surgery` 是唯一的业务主线**。后续 M06-02~07 的所有表都通过 `apply_id` 挂到它上面，不使用各自的一套"主表"。理由：日间手术是一次业务，不是七次业务。如果每个子模块都建自己的主表，会出现"申请单状态"与"排程状态"不一致、"准备清单属于哪张单"这类问题。

2. **没有任何物理外键**。全部用逻辑外键 + 应用层保证。理由：
   - `m06_day_surgery` 会与 M06-02~07 的表频繁 JOIN，物理外键在跨子模块写入时会加锁，影响并发
   - M06-02~07 的表在同一事务里成对写入，应用层一致性可控
   - 每日 04:00 有孤儿数据巡检（见汇总文档 3.3 节）

3. **`m06_eligibility_result` 是"历史快照"而不是"当前状态"**。判定了 5 次就有 5 批记录，用 `evaluate_round` 区分。理由：准入判定的价值在于可追溯——"这个患者当时为什么被拒"必须能答出来。

4. **`m06_rule_version` 与 `m06_eligibility_rule` 是 1:N**。改一条规则不是原地改，而是在新版本里加一行。理由：规则一改，历史判定的依据就变了。版本化后每条规则记录都能追溯"哪一版、什么时候生效"。

5. **`m06_prepare_item` 由主表持有而不是 M06-02**。理由：清单是申请单的组成部分（生成于 M06-01），M06-02 只是执行它。如果清单表归属 M06-02，M06-01 创建申请单时要跨子模块写数据。

```sql
ALTER TABLE m06_day_surgery

ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_status
    CHECK (status IN ('DRAFT', 'PENDING_REVIEW', 'ELIGIBLE', 'INELIGIBLE',
                      'SCHEDULED', 'PREPARED', 'CHECKED_IN', 'IN_SURGERY',
                      'RECOVERING', 'DISCHARGED', 'CLOSED', 'CANCELLED'));

ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_eligibility
    CHECK (eligibility_status IS NULL
           OR eligibility_status IN ('ELIGIBLE', 'PENDING_REVIEW', 'INELIGIBLE'));

-- 状态与准入结论的一致性
ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_elig_status
    CHECK (
        (status = 'INELIGIBLE' AND eligibility_status = 'INELIGIBLE')
        OR (status = 'PENDING_REVIEW' AND eligibility_status = 'PENDING_REVIEW')
        OR (status IN ('ELIGIBLE', 'SCHEDULED', 'PREPARED', 'CHECKED_IN',
                       'IN_SURGERY', 'RECOVERING', 'DISCHARGED', 'CLOSED'))
        OR (status = 'DRAFT')
        OR (status = 'CANCELLED')
    );

-- 未判定前不得进入 ELIGIBLE 之后的任何状态
ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_evaluated
    CHECK (status NOT IN ('ELIGIBLE', 'SCHEDULED', 'PREPARED', 'CHECKED_IN',
                          'IN_SURGERY', 'RECOVERING', 'DISCHARGED', 'CLOSED')
           OR (eligibility_status = 'ELIGIBLE'
               AND evaluated_at IS NOT NULL
               AND rule_version IS NOT NULL));

-- 复核结论必须成对
ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_reviewed
    CHECK (status NOT IN ('ELIGIBLE', 'INELIGIBLE')
           OR reviewed_at IS NULL
           OR (reviewed_by IS NOT NULL AND review_opinion IS NOT NULL));

-- 复核人不得是申请人（SoD-01 的 DB 层兜底）
ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_review_sod
    CHECK (reviewed_by IS NULL OR reviewed_by <> creator_id);

-- 取消必须有原因
ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_cancelled
    CHECK (status <> 'CANCELLED'
           OR (cancel_reason IS NOT NULL
               AND cancel_desc IS NOT NULL
               AND char_length(btrim(cancel_desc)) >= 10));

-- 已排程必须有排程时间
ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_scheduled
    CHECK (status NOT IN ('SCHEDULED', 'PREPARED', 'CHECKED_IN', 'IN_SURGERY',
                          'RECOVERING', 'DISCHARGED', 'CLOSED')
           OR (scheduled_at IS NOT NULL AND scheduled_date IS NOT NULL));

-- 已报到必须有结算住院号
ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_admitted
    CHECK (status NOT IN ('CHECKED_IN', 'IN_SURGERY', 'RECOVERING',
                          'DISCHARGED', 'CLOSED')
           OR (admission_at IS NOT NULL AND admission_id IS NOT NULL));

-- 已离院必须有离院时间
ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_discharged
    CHECK (status NOT IN ('DISCHARGED', 'CLOSED')
           OR (discharge_at IS NOT NULL AND surgery_end_at IS NOT NULL));

-- 已结案必须有结案时间与结算记录
ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_closed
    CHECK (status <> 'CLOSED' OR closed_at IS NOT NULL);

-- 时间戳先后顺序
ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_time_seq
    CHECK (
        (scheduled_at IS NULL OR admission_at IS NULL OR admission_at >= scheduled_at)
        AND (admission_at IS NULL OR surgery_start_at IS NULL OR surgery_start_at >= admission_at)
        AND (surgery_start_at IS NULL OR surgery_end_at IS NULL OR surgery_end_at >= surgery_start_at)
        AND (surgery_end_at IS NULL OR discharge_at IS NULL OR discharge_at >= surgery_end_at)
        AND (discharge_at IS NULL OR closed_at IS NULL OR closed_at >= discharge_at)
    );

-- 警告计数非负
ALTER TABLE m06_day_surgery
    ADD CONSTRAINT ck_m06_ds_counts
```

**状态机：**

```
DRAFT ──► PENDING_REVIEW ──► ELIGIBLE ──► SCHEDULED ──► PREPARED
  │             │                 │            │             │
  │             │                 │            │             ▼
  │             │                 │            │         CHECKED_IN
  │             │                 │            │             │
  │             │                 │            │             ▼
  │             │                 │            │         IN_SURGERY
  │             │                 │            │             │
  │             │                 │            │             ▼
  │             │                 │            │         RECOVERING
  │             │                 │            │             │
  │             │                 │            │             ▼
  │             │                 │            │         DISCHARGED
  │             │                 │            │             │
  │             │                 │            │             ▼
  │             │                 │            │          CLOSED
  │             │                 │            │
  ▼             ▼                 ▼            ▼
DRAFT ──► INELIGIBLE          CANCELLED ◄──────┘
```

**设计要点**

1. **`uk_m06_ds_order` 是幂等基石**。M07-03 在创建手术医嘱后会调用 `POST /internal/v1/m06/apply`，网络重试、消息重投都可能重复调用。这条唯一索引让重复创建在数据库层直接失败，应用层捕获 `IntegrityError` 后返回已有记录。**不用"先查后插"**——并发下有竞态窗口，两个线程可能同时查到"不存在"然后都插入。

2. **`uk_m06_ds_patient_active` 三字段部分唯一索引是"一患者一进行中申请"的 DB 兜底**。用户可能会绕过页面（直接调 API）重复提交，服务层校验可能因为并发而漏。DB 唯一索引是最后一道防线。

3. **`ck_m06_ds_elig_status` 把状态与准入结论绑死**。应用层 bug 可能写出"status=SCHEDULED 但 eligibility_status=NULL"这种脏数据——那意味着一个没做过准入判定的患者被排了手术。这类数据在报表里会显示"所有申请都通过"但实际不是。

4. **`ck_m06_ds_time_seq` 是医疗纠纷举证的核心约束**。出院时间早于手术结束时间、结案早于离院——这些在事后取证的场景下都是致命的数据矛盾。数据库层堵死比应用层可靠。

5. **`ck_m06_ds_review_sod` 是 SoD-01 的 DB 层兜底**。申请人可以绕过页面直接调 API 自审自批，服务层校验可能被绕过（比如其他子模块的内部接口）。DB 约束在最小权限原则下不可绕过（除非 DBA 手动删约束，那本身就会留痕）。

6. **`id_card_hash` 而不是明文**。身份证号是最高敏感度的个人身份信息，泄露的法律后果远大于它的业务价值。系统内部只需要"同一人只能建一份 MPI"的判定能力，SHA-256 足够（配合盐）。

7. **`admission_id` 在报到时才生成**。日间手术在结算体系里是一条"住院记录"（M16-03 用 `admission_type='DAY_SURGERY'`），但这条记录只在患者真正到院报到时才存在。提前生成会让"预交金余额查询"这类操作产生大量空记录。

| 年申请量 | 18,250 |

```sql

    ADD CONSTRAINT ck_m06_er_acked

    ADD CONSTRAINT ck_m06_er_not_acked

    ADD CONSTRAINT ck_m06_er_threshold
    CHECK (jsonb_typeof(threshold_json) = 'object');

    ADD CONSTRAINT ck_m06_er_message
    CHECK (verdict NOT IN ('WARN', 'BLOCK')
           OR (message IS NOT NULL AND char_length(btrim(message)) >= 5));

```

**阈值快照 JSONB 结构**

```json
{
  "operator": "LT",
  "value": 160,
  "value2": null,
  "unit": "mmHg",
  "rule_text": "收缩压 <160",
  "source": "m06_eligibility_rule#1024",
  "scope": "GLOBAL",
  "effective_from": "2026-09-01"
}
```

**设计要点**

1. **`threshold_json` 是这张表存在的核心理由**。医务科半年后把血压阈值从 180 改成 160，此时查看一位老患者的准入记录，必须能答出"当时是按 180 还是 160 判的"。只存 `rule_id` 的话，规则一改历史就还原不出来。

2. **`evaluate_round` 而不是覆盖**。医生可能改了几次指标、判了几次。每次都保留能看出"医生调整了多少次才通过"——这是医生熟悉度的信号，也是准入规则是否合理的信号。用 `is_current` 标出最后一轮，查询时 `WHERE is_current = TRUE` 即可。

3. **`is_acknowledged` 只能对 WARN 置 TRUE**。PASS 项没有"知悉"的必要（本来就没风险），BLOCK 项不应该被"知悉"（知悉了也不能做）。约束让语义边界清晰。

4. **`acknowledged_ip` 用 `INET` 类型**。医生点"已知悉"的法律含义是"我看到了风险并决定继续"。在医疗纠纷场景里，什么时间、从哪台机器点的，都是关键证据。

5. **`message` 至少 5 字**。见过太多系统把说明写成"异常"，那种消息对医生毫无价值。≥5 字强制要求写出具体含义（如"血压偏高，术中可能出现血压波动"）。

**量级估算：**

| 项 | 估算 |
|---|---|
| 每次判定项数 | 平均 18 项 |
| 每申请单判定次数 | 平均 1.0 次（多数一次通过） |
| 年记录数 | 18,250 × 18 × 1.0 = 328,500 |
| 单行平均大小 | 约 420 字节 |
| 年数据量 | 约 138 MB |
| 15 年数据量 | 约 2.1 GB |
| 索引开销 | 约 1.5 GB |
| **合计** | **约 3.6 GB** |

**分区：** 不分区。唯一索引 `uk_m06_er_seq` 若分区必须含分区键 `apply_date`，但该索引的语义是"同申请单同轮次同项唯一"，加分区键会变成"同日期同申请单同轮次同项唯一"——跨日期重复判定会漏检。15 年 500 万行仍在 PG16 舒适区。

**运算符说明**

| 运算符 | 含义 | 阈值要求 | 示例 |
|---|---|---|---|
| `LT` | 小于 | `threshold_value` | 收缩压 `<180` |
| `LTE` | 小于等于 | `threshold_value` | INR `≤1.5` |
| `GT` | 大于 | `threshold_value` | 角膜内皮 `≥1500`（实际是 GTE） |
| `GTE` | 大于等于 | `threshold_value` | 停药天数 `≥7` |
| `EQ` | 等于 | `threshold_value` | — |
| `NE` | 不等于 | `threshold_value` | — |
| `BETWEEN` | 区间内 | `value` + `value2` | 心率 `50~100` |
| `OUTSIDE` | 区间外 | `value` + `value2` | 体温 `<36.0` 或 `>37.3` |
| `IN` | 属于集合 | `threshold_text` | 麻醉方式 in `SURFACE,PERIBULBAR` |
| `NOT_IN` | 不属于集合 | `threshold_text` | 合并症 not in `UNCONTROLLED_HTN` |
| `MUST_BE_TRUE` | 必须为真 | 无 | 陪护人必须填写 |
| `MUST_BE_FALSE` | 必须为假 | 无 | 独眼患者必须为否 |
| `EXISTS` | 必须存在 | 无 | 同意书必须已签 |

**设计要点**

1. **`is_mandatory` 是法规红线标记**。「独眼患者」「手术同意书未签」「ASA IV 级以上」这些不是医院的自由选择，是《医疗质量安全核心制度》《医疗机构手术分级管理办法》的硬性要求。把它标为 `is_mandatory=TRUE` 后，约束 `ck_m06_rl_mandatory` 强制：不可停用、严重度必须是 BLOCK。即使医务科想"临时放宽"，系统也不允许。

2. **唯一索引必须带 `COALESCE(scope_key, '')`**。PostgreSQL 认为 `NULL` 与 `NULL` 不相等，`scope='GLOBAL'` 时 `scope_key IS NULL`，如果不加 COALESCE，可以插入两条 `(v3, GLOBAL, NULL, SYSTOLIC)` 都启用。那样判定时可能出现两条收缩压规则，结果不确定。这与 M12-06 模板唯一索引遇到的坑完全一样。

3. **`value_source` 而是不硬编码字段**。准入项的值可能来自 `vitals.systolic`、`vitals.inr`、`logistics.companion_name`、`anticoagulant.planned_stop_days`。用 JSON 路径让新增准入项不需要改代码，只需配一条规则。

4. **规则不原地修改，只在新版本里加行**。理由同 4.5 节。

**量级估算：**

| 项 | 估算 |
|---|---|
| 当前版本规则数 | 20~60 条 |
| 年新增版本 | 12 个 |
| 年新增规则行 | 240~720 |
| `is_deleted=FALSE` 的当期行 | 约 60 |
| 单行大小 | 约 600 字节 |
| 永久保留（含历史版本） | 10 年约 6,000 行 / 3.6 MB |

**版本生命周期**

```
DRAFT ──提交──► PENDING ──第一签(科主任)──► PENDING ──第二签(医务科长)──► APPROVED
   │               │                                                        │
   │               │                                                        │ 次日 00:05
   │               └──驳回──► REJECTED                                       ▼
   │                                                                    EFFECTIVE
   │                                                                        │
   │                                                                 新版本生效
   │                                                                        ▼
   └──────────────────────────────────────────────────────────────────  EXPIRED
```

**设计要点**

1. **`uk_m06_rv_effective` 保证同时只有一个生效版本**。如果同时有两个 EFFECTIVE 版本，`_current_rule_version()` 查出来的是哪个取决于排序，判定结果不确定。这条部分唯一索引让"同时两个生效"在 DB 层不可能发生。

2. **`ck_m06_rv_double_sign` 把审批步数与签名字段绑死**。`approve_step=2` 时必须有两个人两个时间，且 `approved_by_1 <> approved_by_2`。这防止应用层 bug 让同一个人签两次。

3. **`effective_date` 与 `applied_at` 是两个概念**。前者是"从哪一天起生效"（业务日期），后者是"定时任务什么时候真正把它置为 EFFECTIVE"（系统时刻）。两者可能有几十秒偏差（定时任务 00:05 执行）。分开存才能在排查"为什么 00:02 的判定用的还是旧版本"时有据可查。

4. **`change_detail_json` 存变更差异**。回滚一个版本时要知道它到底改了什么。用 JSONB 存 `[{"rule_code": "SYSTOLIC", "old": 180, "new": 160}]` 这类结构，比逐条比对新旧版本的规则表简单得多。

| 项 | 估算 |
|---|---|
| 年新增版本 | 12 个（每月一次调整） |
| 10 年累计 | 120 行 |
| 单行大小 | 约 2 KB（含 change_detail_json） |
| 合计 | 约 240 KB |

**分区：** 不分区。表极小。

| `ANTIBIOTIC` | 预防性抗菌药物 | 左氧氟沙星滴眼液，术前 30 分钟 | 护士 |
| `CONSENT` | 知情同意 | 手术/麻醉/植入物同意书 | 医生 |
| `ANESTHESIA_VISIT` | 麻醉术前访视 | 麻醉医生评估 | 麻醉医生 |
| `EXAM` | 术前检查 | IOL Master、角膜内皮、B 超 | 检查科室 |
| `LAB` | 术前检验 | 血常规、凝血、传染病八项 | 检验科室 |
| `NURSING` | 护理准备 | 更换病号服、摘除义齿 | 护士 |
| `PREP` | 其他准备 | 自定义 | 按配置 |

**设计要点**

1. **`status='NA'` 是必要的第四态**。某些准备项对特定患者不适用——比如患者已经停抗凝药 15 天，"抗凝停药"这一项可以标 `NA` 并写原因。如果只有 PENDING/DONE/FAILED 三态，护士只能被迫勾 DONE 或让整单卡住。

2. **`done_source='AUTO'` 支持自动关联**。术前检查（IOL Master、血常规）的结果在 M12/M13 里已经产生。如果系统能自动读取结果并标记该项完成，护士不用手工再勾一遍——这是减少"漏勾"与"假勾"的关键。`auto_ref_type`/`auto_ref_id` 记录关联的是哪条结果，可追溯。

3. **`is_abnormal` + `abnormal_desc`** 记录"项做完了但结果不正常"。术前检查出"凝血异常"时，这一项技术上完成了，但整台手术不能做。把异常单独标记，M06-02 提交时才能拦住。

4. **`timing_offset_minutes` 与 `timing` 并存**。`timing` 给人看（"术前 30 分钟"），`offset` 给机器算（`surgery_start_at - 30min`）。只有 `timing` 的话，护士板上的"该做什么"没法按时间排序。

5. **唯一索引 `uk_m06_pi_seq` 用 `item_code` 而不是 `seq_no`**。同一个申请单可以有多种 EXAM，但同一 `item_code`（如 `EXAM_IOL_MASTER`）只能出现一次。用 `seq_no` 做唯一键没意义（seq 就是按顺序生成的）。

| 年记录数 | 18,250 × 8 = 146,000 |
| 单行平均大小 | 约 380 字节 |
| 年数据量 | 约 55 MB |
| 15 年数据量 | 约 830 MB |
| 索引开销 | 约 500 MB |
| **合计** | **约 1.3 GB** |

```sql
           OR (approved_by_2 IS NOT NULL AND approved_at_2 IS NOT NULL));

           AND (approved_by_2 IS NULL OR approved_by_2 <> requested_by));

```

**审批层级判定表**

| 申请单状态 | 审批层级 | 审批人 |
|---|---|---|
| `DRAFT` / `PENDING_REVIEW` / `ELIGIBLE` | `NONE` | 无需审批 |
| `SCHEDULED` | `CHIEF` | 科主任 |
| `PREPARED` | `CHIEF_MAF` | 科主任 + 医务科 |
| `CHECKED_IN` / `IN_SURGERY` | `MAF_CHIEF` | 医务科长 |

**设计要点**

1. **`uk_m06_cr_active` 保证一单一条待审批取消**。医生可能反复点"取消"，产生多条 PENDING 记录。如果没有唯一约束，审批人看到 3 条相同申请不知道该批哪个，批准后可能重复执行取消（释放两次台次、退两次费）。

2. **`impact_json` 存影响评估快照**。取消时系统要告诉医生"你将释放 X 台次、作废 Y 项准备、退 Z 元"。这个评估在申请时算一次存下来，审批人看到的是**申请时的状态**，而不是审批时的实时状态。理由：审批人看到"退 3,280 元"就要判断这个金额对不对，而实时算可能因为中间产生了新费用而变化，让审批人困惑。

3. **`ck_m06_cr_reschedule` 要求 `new_scheduled_date > old_scheduled_date`**。改期只能往后不能往前——往前改意味着准备时间更短，可能准备不完。真要往前改应该取消后重新申请。

4. **`ck_m06_cr_sod` 是 SoD-03 的 DB 层兜底**。申请人自己批自己的取消申请，等于"我想取消就能取消"，审批形同虚设。

**量级估算：**

| 项 | 估算 |
|---|---|
| 取消率（行业经验） | 8~12% |
| 年取消量 | 约 1,600 |
| 年改期量 | 约 200 |
| 年记录数 | 1,800 |
| 单行大小 | 约 1.5 KB（含 impact_json） |
| 15 年数据量 | 约 40 MB |

| **合计** | **约 65 MB** |

**分区定义**

```sql
-- 预建 36 个月分区（2026-10 ~ 2029-09）
DO $$
DECLARE
    v_start DATE := DATE '2026-10-01';
    v_i INT;
    v_name TEXT;
    v_from DATE;
    v_to DATE;
BEGIN
    FOR v_i IN 0..35 LOOP
        v_from := (v_start + (v_i || ' months')::INTERVAL)::DATE;
        v_to := (v_from + '1 month'::INTERVAL)::DATE;
        v_name := 'm06_apply_log_' || TO_CHAR(v_from, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m06_apply_log '
            'FOR VALUES FROM (%L) TO (%L)',
            v_name, v_from, v_to
        );
        EXECUTE FORMAT('COMMENT ON TABLE %I IS %L',
            v_name, 'm06_apply_log 分区 ' || TO_CHAR(v_from, 'YYYY-MM'));
    END LOOP;
END $$;
```

**操作类型说明**

| 操作 | 中文 | 是否记前后状态 |
|---|---|---|
| `CREATE` | 创建申请单 | ❌ |
| `UPDATE` | 修改申请单 | ❌（记 before/after） |
| `DELETE_DRAFT` | 删除草稿 | ❌ |
| `EVALUATE` | 准入判定 | ❌ |
| `ACKNOWLEDGE` | 确认警告项 | ❌ |
| `SUBMIT` | 提交审核 | ✅ |
| `REVIEW_APPROVE` | 复核通过 | ✅ |
| `REVIEW_REJECT` | 复核不通过 | ✅ |
| `ABANDON` | 放弃申请 | ✅ |
| `CANCEL_REQUEST` | 提交取消申请 | ❌ |
| `CANCEL_APPROVE` | 取消审批通过 | ✅ |
| `CANCEL_REJECT` | 取消审批驳回 | ❌ |
| `RESCHEDULE` | 改期 | ✅ |
| `STATUS_CHANGE` | 状态变更（跨模块回写） | ✅ |
| `RULE_CHANGE` | 规则变更 | ❌ |
| `RULE_APPROVE` | 规则审批 | ❌ |
| `EXPORT` | 导出 | ❌ |
| `VIEW` | 查看（敏感数据访问） | ❌ |

**设计要点**

1. **只增触发器优于应用层保护**。应用层可以被绕过（DBA 手动改、其他服务误写、迁移脚本）。触发器在数据库层，任何绕过都会抛异常。

2. **`before_json` / `after_json` 双快照**。只记 "UPDATE" 无法回答"改了什么"。双快照让日志可回放。

3. **`source_module` 记录跨模块回写来源**。M06-02 把状态从 SCHEDULED 改到 PREPARED 时，日志要能看出"是准备模块改的，不是我改的"。排查问题时这是第一手信息。

4. **`client_ip` 用 `INET`**。支持 IP 范围查询（`WHERE client_ip << '192.168.1.0/24'`），也便于识别异常访问。

5. **为什么分区而不归档**。日志表年 45 万行、15 年 675 万行，单表也能扛；但日志的合规价值随时间衰减——2 年内的日志用于日常追溯，2~15 年只在纠纷时查。分区让"只扫最近 3 个月"的查询物理隔离，性能提升 10 倍以上。同时分区表可以按月归档为冷存储。

**量级估算：**

| 项 | 估算 |
|---|---|
| 每申请单日志数 | 平均 25 条（创建/判定/确认/提交/复核/排程/准备/报到/核对/手术/复苏/离院/结算/归档 + 查看） |
| 年记录数 | 18,250 × 25 = 456,250 |
| 单行平均大小 | 约 600 字节（多数 before_json 为空） |
| 年数据量 | 约 274 MB |
| 15 年数据量 | 约 4.1 GB |
| 索引开销 | 约 2.5 GB |
| **合计** | **约 6.6 GB** |

**分区：** 按 `seq_date` 月度 RANGE 分区，预建 36 个月。保留 15 年（180 个分区），在线热数据 180 天，2 年后归档到冷存储。

```python
class RuleCreate(BaseModel):
    """新建准入规则。"""

    rule_code: str = Field(..., min_length=2, max_length=64,
                           pattern=r"^[A-Z][A-Z0-9_]+$")
    item_code: str = Field(..., min_length=2, max_length=64)
    item_name: str = Field(..., min_length=1, max_length=128)
    category: RuleCategory
    judgement_mode: JudgementMode = "AUTO"
    severity: Severity = "WARN"
    operator: RuleOperator
    threshold_value: Optional[Decimal] = None
    threshold_value2: Optional[Decimal] = None
    threshold_text: Optional[str] = Field(None, max_length=128)
    threshold_unit: Optional[str] = Field(None, max_length=32)
    value_source: str = Field(..., min_length=1, max_length=64,
                              description="取值 JSON 路径，如 vitals.systolic")
    value_type: Literal["NUMBER", "BOOL", "STRING", "DATE"] = "NUMBER"
    scope: RuleScope = "GLOBAL"
    scope_key: Optional[str] = Field(None, max_length=256)
    need_review: bool = False
    is_mandatory: bool = False
    is_required: bool = True
    is_enabled: bool = True
    message_template: Optional[str] = Field(None, max_length=500)
    sort_no: int = Field(999, ge=0, le=9999)
    remark: Optional[str] = Field(None, max_length=512)

    @model_validator(mode="after")
    def _check_scope(self):
        if self.scope == "GLOBAL":
            if self.scope_key:
                raise ValueError("GLOBAL 作用域不应填写 scope_key")
        else:
            if not self.scope_key:
                raise ValueError("非 GLOBAL 作用域必须填写 scope_key")
        return self

    @model_validator(mode="after")
    def _check_threshold(self):
        single = {"LT", "LTE", "GT", "GTE", "EQ", "NE"}
        double = {"BETWEEN", "OUTSIDE"}
        none_ops = {"MUST_BE_TRUE", "MUST_BE_FALSE", "EXISTS"}
        if self.operator in single:
            if self.threshold_value is None:
                raise ValueError("该运算符必须填写 threshold_value")
            if self.threshold_value2 is not None:
                raise ValueError("该运算符不应填写 threshold_value2")
        elif self.operator in double:
            if self.threshold_value is None or self.threshold_value2 is None:
                raise ValueError("区间运算符必须填写两个阈值")
            if self.threshold_value >= self.threshold_value2:
                raise ValueError("阈值下限必须小于上限")
        elif self.operator in ("IN", "NOT_IN"):
            if not self.threshold_text:
                raise ValueError("集合运算符必须填写 threshold_text")
        elif self.operator in none_ops:
            if self.threshold_value is not None:
                raise ValueError("该运算符不应填写阈值")
        return self

    @model_validator(mode="after")
    def _check_mandatory(self):
        if self.is_mandatory:
            if not self.is_enabled:
                raise ValueError("法规底线规则不可停用")
            if self.severity != "BLOCK":
                raise ValueError("法规底线规则的严重度必须是 BLOCK")
        return self
```
