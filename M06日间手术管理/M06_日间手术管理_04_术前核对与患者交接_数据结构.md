**设计说明**

1. **`m06_verify_record` 是 M06-04 的唯一主表**：
   - 四种核对类型（`WARD` / `TIMEOUT` / `HANDOVER_A` / `HANDOVER_B`）共用一张记录表，靠 `verify_type` 区分。
   - **为什么不分四张表**：四种核对的字段 90% 相同（都有患者、术眼、术式、执行人、时间、状态），只有核对项清单不同；分表后要做四次相同的分页、筛选、统计，而共用一张表只需在 `verify_type` 上加一个部分索引。
   - 交接虽有独立的 `m06_handover` 表（因为交接有双方签名、物品清单等独有字段），但仍然在 `m06_verify_record` 里有一条 `verify_type` 为 `HANDOVER_A`/`HANDOVER_B` 的记录用于时间线汇总。

2. **`(apply_id, verify_type, round_no)` 唯一**：
   - 一次核对的重做必须用 `round_no` 递增，不允许覆盖。
   - 这是"核对记录不可篡改"的**结构级保障**——不能改，只能新增。

3. **`m06_verify_signature` 同时挂核对记录与交接单**：
   - `record_id` 与 `handover_id` **二选一非空**（`CHECK` 约束）。
   - 交接签名与核对签名共用一张表，是因为签名数据结构完全一致（角色、签名人、签名图片、时间），且统计"谁签了多少次"要跨两者汇总。

4. **`m06_wristband` 与核对记录分开**：
   - 腕带的生命周期独立于核对（可在核对前生成，核对后仍要打印/补打）。
   - 一条腕带可能被多次核对扫描（病房核对、进手术间扫描、Time-Out 扫描），三者共用同一条腕带记录。
   - 补打会新建记录并通过 `reprint_from` 指向原记录，形成链。

5. **无物理外键**（与 M06-01~03 一致）：
   - 跨子模块写入加锁影响并发。
   - 应用层事务成对写入 + 每日 04:00 孤儿巡检。

6. **`m06_verify_log` 分区**：
   - 年 55 万行 × 15 年 = 825 万行，不分区单表体积超 4 GB。
   - 分区后"只扫最近 3 个月"物理隔离，时间线查询性能提升 10 倍。

```
                   ┌──────────────┐
                   │  CANCELLED   │
                   └──────────────┘

            ▼
    ┌──────────────┐
    │   EXPIRED    │
    └──────────────┘
```

**设计要点**

1. **`uk_m06_vrecord_round` 是"核对不可篡改"的结构级保障**：

   ```sql
   ALTER TABLE m06_verify_record
       ADD CONSTRAINT uk_m06_vrecord_round
       UNIQUE (apply_id, verify_type, round_no);
   ```

   - 应用层已禁止修改 `PASSED` 记录，但应用层可被绕过（其他服务误写、DBA 手动改）。
   - 唯一约束意味着**同一个 `(apply_id, verify_type, round_no)` 只能有一条**，想改只能改 `round_no` 新建一条 —— 而 `round_no` 递增的历史就自然形成了核对轮次链。

2. **`uk_m06_vrecord_schedule` 保证一台次只有一个有效 Time-Out**：

   ```sql
   CREATE UNIQUE INDEX uk_m06_vrecord_schedule
       ON m06_verify_record (schedule_id, verify_type)
       WHERE verify_type = 'TIMEOUT'
         AND status <> 'EXPIRED'
         AND is_deleted = FALSE;
   ```

   - 排除 `EXPIRED`：超时后可以新建一轮，旧的保持 `EXPIRED`。
   - 为什么不是所有 `verify_type` 都唯一：`WARD` 可能有 5 轮重核；`TIMEOUT` 是"一次性事件"，同一台次出现两个有效 Time-Out 意味着有人绕过流程。

3. **`is_passable` 冗余存储**：
   - 判定逻辑是「无关键项 `MISMATCH` 且全部项已完成」。若实时算，需要 JOIN `m06_verify_item` 并判断 `is_key`。
   - 落库后 `WHERE is_passable = FALSE` 可直接扫出阻断队列（M09 开台前校验、M06-05 前置校验都用）。
   - 一致性由 `ck_m06_vrecord_passed` 部分保证（`PASSED` ⟹ `is_passable = TRUE`）。

4. **`verify_date` 冗余存储而非从 `created_at` 派生**：
   - 工作台按日期查询是最高频（护士每天打开），`DATE(created_at)` 无法走索引。
   - 冗余后 `WHERE verify_date = '2026-10-24'` 走 `idx_m06_vrecord_date`。

5. **`device_no` 记录设备编号**：
   - Time-Out 有 4 个客户端（大屏 + 3 个 Pad），纠纷时要知道"当时是谁在哪个设备上点的确认"。
   - 也与 IP 一起用于排查"签名为空是因为 Pad 掉线还是护士忘了"。

6. **`patient_gender` / `patient_age` / `bed_no` 冗余**：
   - 工作台、大屏、Pad 全部要显示这些信息，不冗余则每屏 20~50 条记录要跨模块查。
   - 与 M06-01~03 的冗余策略一致（申请单快照）。

**分区：** 不分区。理由：
- `uk_m06_vrecord_round` 若分区必须含分区键 `verify_date`，会破坏"同申请同类型同轮次唯一"的语义（跨年份允许重复）。
- 15 年 132 万行在 PG16 单表舒适区（主键查询 <1ms）。

**设计要点**

1. **`uk_m06_vitem_code` 保证同记录同核对项唯一**：

   ```sql
   ALTER TABLE m06_verify_item
       ADD CONSTRAINT uk_m06_vitem_code
       UNIQUE (record_id, item_code);
   ```

   - 防止"生成核对项时重复执行生成了两套 V-05"，导致显示两个"手术眼别"、进度显示 28/14。
   - 这个错误在并发场景（两个护士同时点"开始核对"）下极易发生。

2. **`expected_value` 与 `actual_value` 双列**：

   | 字段 | 含义 | 来源 |
   |---|---|---|
   | `expected_value` | 文件上写的 | 申请单 / 腕带 / 系统计算 |
   | `actual_value` | 眼前看到的 | 护士输入 / 患者自述 / 扫码结果 |

   - **只存一个值就永远说不清"到底是文件错了还是事实错了"**。
   - 例：`expected_value='OS'`（申请单写左眼），`actual_value='OD'`（患者说右眼）→ 明确知道是文件与事实不符，可追溯。
   - 只存 `verdict='MISMATCH'` 则事后无法还原。

3. **`is_key` 与 `verdict` 的联合部分索引**：

   ```sql
   CREATE INDEX idx_m06_vitem_key
       ON m06_verify_item (record_id)
       WHERE is_key = TRUE AND verdict = 'MISMATCH';
   ```

   - 全院 200 万核对项中，关键项不一致的只有每年几条到几十条。
   - 普通索引遍历 200 万行约 20ms；部分索引扫 1 页 <0.1ms。
   - 这个索引服务于**每日质量巡检**与**任何关键项异常的即时告警**。

4. **`na_reason` 与 `mismatch_desc` 双向钉死**：

   ```sql
   CHECK (verdict <> 'NA' OR (na_reason IS NOT NULL AND ...));
   CHECK (verdict = 'NA' OR na_reason IS NULL);
   ```

   - 只有 `NA` 能有 `na_reason`，只有 `MISMATCH` 能有 `mismatch_desc`。
   - 防止"选中 MATCH 但还留着上次的 na_reason"这种脏数据。

5. **`auto_filled` ⟹ `editable = FALSE`**：
   - 自动填充的项（如腕带扫描得到的姓名）如果还能手动改，等于可以绕过系统校验。
   - 唯一约束保证不可改，护士若发现自动值不对，只能标 `MISMATCH` 走异常处置。

6. **`sort_no` 独立于 `item_code` 排序**：
   - 主键排序是插入顺序，但页面要按业务流程排序（V-01 到 V-14、T-01 到 T-20）。
   - `order by sort_no` 保证稳定顺序。

7. **不存核对项的"模板"**：
   - 核对项清单（`WARD_ITEMS` / `TIMEOUT_ITEMS`）写死在代码里，不入库。
   - **为什么不入库**：核对项清单对应的是**法规要求的核查表内容**，不是可配置项。国家卫健委的手术安全核查表内容是固定的 20 项，医院不能自己增删。若做成配置表，会被随意修改导致飞检时"核查表少了 3 项"。
   - 只有 `is_key` 的判定可通过参数 `M06.VERIFY.KEY_ITEMS` 调整（不同医院对哪些项算"关键"可能有不同理解）。

**量级估算：**

| 项 | 估算 |
|---|---|
| 日核对记录 | 242 |
| 每记录核对项数 | 平均 16（病房 14 / Time-Out 20 / 交接 12） |
| 日项数 | 242 × 16 ≈ 3,900 |
| 年项数 | 3,900 × 365 ≈ 1,420,000 |
| 单行平均大小 | 约 420 字节 |
| 年数据量 | 约 596 MB |
| 15 年数据量 | 约 8.9 GB |
| 索引开销 | 约 5 GB |
| **合计（15 年）** | **约 14 GB** |

**分区：论争与结论**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 不分区 | 唯一约束简单、查询简单 | 15 年 2,100 万行单表 | **采用** |
| 按 `verify_date` 年度分区 | 单一老年度查询快 | `uk_m06_vitem_code` 必须含分区键，**同记录同核对项唯一退化为"同年唯一"** | 否 |
| 按 `record_id` HASH 分区 | 唯一约束与查询都能保持 | 时间范围查询要扫全部分区 | 备选 |

**最终采用不分区**，理由：
1. `uk_m06_vitem_code` 是"防止重复生成核对项"的核心约束，**分区会削弱它**。
2. 所有查询都以 `record_id` 为入口（"看这次核对的所有项"），`record_id` 上有普通索引，单次查询 <1ms。
3. 唯一需要跨记录查询的场景是"按类型统计核对项"，用 `idx_m06_vitem_type`，年 142 万行扫描约 200ms，月度统计完全可接受。

**若未来超过 5,000 万行，改用 `HASH(record_id)` 分区**：`record_id` 天然包含在唯一键里，分区后唯一约束语义不变；查询仍以 `record_id` 为入口，HASH 分区能精确定位到单一分区。

```sql

    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m06_vsig_update
    BEFORE UPDATE ON m06_verify_signature
    FOR EACH ROW EXECUTE FUNCTION fn_m06_vsig_readonly();

CREATE TRIGGER trg_m06_vsig_delete
    BEFORE DELETE ON m06_verify_signature
    FOR EACH ROW EXECUTE FUNCTION fn_m06_vsig_readonly();
```

**设计要点**

1. **`signature_hash` 防篡改**：
   - 签名数据（图片 URL 指向文件、指纹模板）可能被替换。
   - 存 SHA-256 后，任何时候重算都能验证"签名图片是不是当时的"。
   - 与 M12-03/04 的文件指纹是同一思路。

2. **`ck_m06_vsig_target` 强制二选一**：
   - 签名要么挂核对记录，要么挂交接单，不能都不挂（孤儿签名）。
   - 也不能都挂（歧义：这个签名属于哪次核对？）。

3. **`uk_m06_vsig_record_role` 保证一记录一角色只签一次**：

   ```sql
   CREATE UNIQUE INDEX uk_m06_vsig_record_role
       ON m06_verify_signature (record_id, signer_role)
       WHERE record_id IS NOT NULL;
   ```

   - 防止"医生签了两次"或"两个主治都用 SURGEON 角色签"。
   - 若签名有误需要更正，只能通过作废整个核对记录重开（`round_no` 递增），不能单独删签名。

4. **`signature_type` 五类**：

   | 类型 | 场景 | 数据 |
   |---|---|---|
   | `HANDWRITTEN` | Pad 上手写签名 | 图片 URL + hash |
   | `FINGERPRINT` | 指纹签名 | 模板 ID + hash |
   | `CA_CERT` | 第三方 CA 电子签名 | 证书序列号 |
   | `PATIENT_CONFIRM` | 患者在 Pad 上点"确认术眼" | 仅记时刻 |
   | `ACCOUNT` | 账号密码确认（降级场景） | 仅记时刻 |

   **为什么患者确认算一种签名**：患者点"确认术眼是左眼"这个动作有法律意义（是他本人的确认）。虽无手写签名，但记录时间戳 + 设备 + IP 同样构成证据。

5. **不存 `is_deleted`**：
   - 签名记录用只增触发器保护，删除都做不到，`is_deleted` 无从谈起。
   - 这比"有 `is_deleted` 但代码保证不删"更可靠。

| 年签名数 | 363 × 365 ≈ 132,500 |

```
                ▼
        ┌──────────────┐
        │   RESOLVED   │
        └──────────────┘
```

**设计要点**

1. **`ck_m06_vabn_disposed` 强制处置说明 ≥20 字**：
   - 只写"已处理"等于没处理。
   - 必须写清"为什么不一致、怎么处理的、谁同意的"。
   - 与 M06-01 的取消原因、M06-02 的异常处置说明是同一标准。

2. **`is_contacted_surgeon` / `is_contacted_patient` 单独标记**：
   - 核对异常时，即使系统记录了处置，真实世界还要打电话。
   - 这两个勾选记录"信息是否传达给人"，是纠纷时的关键证据。
   - **为什么不写进 `dispose_desc`**：勾选可被统计（"多少异常没联系主刀"），文本无法聚合。

3. **`idx_m06_vabn_pending` 按 `is_key DESC, detected_at ASC` 排序**：
   - 关键项异常置顶（`is_key = TRUE` 排前面）。
   - 同级别按等待时长升序（最久的先处理）。
   - 一个索引同时满足两个排序需求，避免额外排序开销。

4. **`idx_m06_vabn_overdue` 用 `NOW()` 的部分索引**：

   ```sql
   CREATE INDEX idx_m06_vabn_overdue
       ON m06_verify_abnormal (detected_at)
       WHERE status = 'PENDING'
         AND detected_at < NOW() - INTERVAL '30 minutes';
   ```

   - **这是一个有陷阱的写法**：PostgreSQL 部分索引的 `WHERE` 中若含 `NOW()`，索引本身不会自动更新——行在索引里的状态在插入时决定。
   - **正确做法**：改为普通部分索引 `WHERE status = 'PENDING'`，查询时带时间条件：
     ```sql
     CREATE INDEX idx_m06_vabn_pending_time
         ON m06_verify_abnormal (detected_at)
         WHERE status = 'PENDING';
     ```
   - 定时任务扫描 `WHERE status='PENDING' AND detected_at < NOW() - INTERVAL '30 minutes'`，利用 `idx_m06_vabn_pending_time` 的范围扫描。
   - **本表最终采用后者**，上文索引表已修正为 `idx_m06_vabn_overdue` 的语义描述，实际 DDL 见附录 C。

5. **不做逻辑删除**：
   - 异常记录是质量问题证据，不能删。
   - 表结构里仍保留 `is_deleted` 是为与其他表一致（可被 ORM 统一处理），但业务层无删除接口。

**设计要点**

1. **`uk_m06_handover_active` 保证同申请同类型只有一个进行中**：

   ```sql

       ON m06_handover (apply_id, handover_type)
       WHERE status IN ('IN_PROGRESS', 'SIGNED')
         AND is_deleted = FALSE;
   ```

   - 防止护士点两次"发起交接"生成两张单子。
   - 交接一唯一性约束（`apply_id, 'HANDOVER_A'`）比台次更合适：同一患者在一天内可能改台次，但交接还是那一次。

2. **`ck_m06_handover_distinct` 保证发起方 ≠ 接收方**：
   - 自己交给自己等于没交接（责任未转移）。
   - 数据库层兜底，应用层也校验（`"0604022"`）。

3. **`ck_m06_handover_template` 单号前缀与类型一致**：

   | 类型 | 前缀 | 说明 |
   |---|---|---|
   | `HANDOVER_A` | `HO` | 交接一（Out of ward） |
   | `HANDOVER_B` | `HR` | 交接二（Recovery） |

   - 前缀不同便于人眼识别，也便于按类型分区间统计。

4. **`implant_info` 用 JSONB 存植入物快照**：
   - 交接一的晶体 информация来自 M06-03/M15，交接二来自 M09 术中记录。
   - 结构可能变化（未来可能加"批次号"、"灭菌批号"）。
   - 拆成独立表成本高：交接一平均只有 1 个晶体，独立表一年也只有 5 万行且每次只读整体。
   - **但不放入交接明细**：交接明细是"勾选项"，晶体是"带数据的内容"，混在一起会让交接明细的约束（`is_checked` 布尔）无法表达。

   ```json
   {
     "model": "SA60AT",
     "power": "+21.0D",
     "serial_no": "SN2026102400123",
     "outbound_no": "CK20261024000123",
     "manufacturer": "ALCON"
   }
   ```

5. **`belongings_disposal` 三选一 + 单号约束**：
   - `FAMILY` 交家属：不记单号
   - `STORED` 寄存：必须有寄存单号
   - `NONE` 无随身物品

   - **为什么必须三选一不能留空**：忘了处理随身物品 → 患者进手术间后手机丢了 → 家属投诉。强制选择让护士必须处理这一步。

6. **`duration_seconds` 落库**：
   - 交接耗时是流程效率核心指标（目标 ≤5 分钟）。
   - 实时算 `completed_at - started_at` 无法聚合与索引。
   - 落库后可 `WHERE duration_seconds > 300` 快速找出慢的交接案例。

**设计要点**

1. **`uk_m06_wb_active` 保证一台次仅一个有效腕带**：

   ```sql
   CREATE UNIQUE INDEX uk_m06_wb_active
       ON m06_wristband (schedule_id)
       WHERE status = 'ACTIVE' AND is_deleted = FALSE;
   ```

   - 如果两个有效腕带同时存在，患者身上可能带着旧腕带（术眼不对），扫码时扫到哪个是随机的。
   - 唯一约束彻底堵死这个口子：补打必须先把旧腕带置为 `REPLACED`。

2. **`ck_m06_wb_barcode` 用表达式校验条码由三部分拼接**：

   ```sql
   CHECK (barcode = patient_id::TEXT || '|' || admission_no
          || '|' || identity_hash)
   ```

   - 这不仅校验格式，还保证**条码内容与字段值实时一致**。
   - 若有人改了 `patient_id` 但忘改 `barcode`，约束立刻拒绝。
   - 这是"冗余数据必须一致"的强表达。

3. **`identity_hash` 防伪机制**：

   ```
   identity_hash = SHA256(patient_id | admission_no | 生成时间戳)[:16]
   barcode = patient_id | admission_no | identity_hash
   ```

   - 扫腕带时：
     1. 解析三段。
     2. 按 `patient_id` + `admission_no` 查当前腕带记录。
     3. 比对 `identity_hash` 是否与记录一致。
   - 若有人伪造腕带（打印一张新标签），他不知道哈希算法与时间戳，无法生成合法的 `identity_hash`。
   - 若有人拿旧腕带换人扫描（同一患者不同台次），旧腕带的 `identity_hash` 与当前记录不一致，校验失败。

4. **`eye_side` 印在腕带上**：
   - 普通医院腕带只有姓名 + 住院号，护士核对术眼看申请单。
   - 眼科腕带额外印术眼并用红框高亮，护士每次扫腕带都会看到"左眼"。
   - **这是眼科特有的双保险**：申请单写左眼 + 腕带印左眼，两处独立确认。

5. **`ck_m06_wb_status` 三态**：

   | 状态 | 含义 |
   |---|---|
   | `ACTIVE` | 在使用 |
   | `VOID` | 已作废（患者取消手术、出院） |
   | `REPLACED` | 被新腕带取代（补打、术眼变更） |

   - **`VOID` 与 `REPLACED` 分开**：前者是"不再需要腕带"，后者是"换了一个"。统计补打率时只算 `REPLACED`。

6. **`printer_no` 记录打印机**：
   - 打印失败时，"是打印机问题还是腕带问题"需要这个信息。
   - 若某台打印机的失败率异常高，是设备故障信号。

```sql
DO $$
DECLARE
    v_start DATE := DATE '2026-10-01';
    v_i INT;
    v_name TEXT;
    v_from DATE;
    v_to DATE;
BEGIN
    FOR v_i IN 0..35 LOOP
        v_from := (v_start + (v_i || ' months')::INTERVAL)::DATE;
        v_to := (v_from + '1 month'::INTERVAL)::DATE;
        v_name := 'm06_verify_log_' || TO_CHAR(v_from, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m06_verify_log '
            'FOR VALUES FROM (%L) TO (%L)',
            v_name, v_from, v_to
        );
    END LOOP;
END $$;
```

   - Time-Out（4）：TIMEOUT_ITEM / TIMEOUT_SIGN / TIMEOUT_COMPLETE / TIMEOUT_ABORT

   - 状态（2）：EXPIRE / REOPEN

3. **`before_json` / `after_json` 用于复杂变更**：
   - 状态流转用 `from_status` / `to_status`，简洁可索引。
   - 核对项判定用 `item_code` + `after_json`（含 `verdict` / `actual_value`）。
   - 配置修改用 `before_json` / `after_json`（含参数旧值与新值）。

```python
    surrogate_relation: Mapped[Optional[str]] = mapped_column(String(32))

        SmallInteger, nullable=False, default=0,
        server_default=text("0"))

        SmallInteger, nullable=False, default=0,
        server_default=text("0"))

        Boolean, nullable=False, default=False,
        server_default=text("FALSE"))

    started_at: Mapped[Optional[datetime]] = mapped_column(DateTime)
    verified_at: Mapped[Optional[datetime]] = mapped_column(DateTime)
    verified_by: Mapped[Optional[int]] = mapped_column(BigInteger)
    verified_by_name: Mapped[Optional[str]] = mapped_column(String(64))
    expired_at: Mapped[Optional[datetime]] = mapped_column(DateTime)

    remark: Mapped[Optional[str]] = mapped_column(String(1000))
    client_ip: Mapped[Optional[str]] = mapped_column(INET)
    device_no: Mapped[Optional[str]] = mapped_column(String(64))
    trace_id: Mapped[Optional[str]] = mapped_column(String(64))
    created_by: Mapped[Optional[int]] = mapped_column(BigInteger)
    created_at: Mapped[datetime] = mapped_column(

    updated_at: Mapped[datetime] = mapped_column(
        DateTime, nullable=False, server_default=func.now(),

        Boolean, nullable=False, default=False,

            "AND is_passable = TRUE AND mismatch_count = 0 "

            name="ck_m06_vrecord_abnormal"),
        CheckConstraint(
            "status <> 'EXPIRED' OR expired_at IS NOT NULL",
            name="ck_m06_vrecord_expired"),
```

**三个「敏感 + 只读」参数的制度来源：**

- `REQUIRE_PATIENT_CONFIRM` ← 《患者安全目标》手术安全核查要求
- `REQUIRE_IMPLANT_READBACK` ← 《医疗器械临床使用管理办法》植入物核对要求
- `KEY_ITEMS` ← 《医疗质量安全核心制度要点》第十五条手术安全核查制度

三者对应法律要求，**不允许通过改配置绕过**；如需调整必须走制度变更流程。
