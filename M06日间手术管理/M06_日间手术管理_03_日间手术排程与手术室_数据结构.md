**设计说明**

1. **`m06_or_schedule` 是唯一业务主线**：M06-04 术前核对、M06-05 术后复苏、M06-06 日间结算、M06-07 统计全部通过 `schedule_id` 或 `apply_id` 挂上来。这与 M06-01 的 `m06_day_surgery` 形成"申请主线 + 排程主线"双主线的结构。

   **为什么需要两条主线**：一张申请单可能因为改期产生多个台次（原台次 `RESCHEDULED` + 新台次）。如果只有申请为主线，改期历史就无处存放。两条主线通过 `apply_id` 连接（1:N）。

2. **`m06_or_slot` 与 `m06_or_schedule` 一对一占用**：
   - `slot.schedule_id` 指向当前占用它的台次。
   - `schedule.slot_id` 指向它占用的时段。
   - 双向冗余是为了两个方向的查询都快（"这个时段被谁占了" vs "这台次在哪个时段"）。
   - 一致性由 `uk_m06_slot_schedule` 与 `uk_m06_schedule_slot` 双向部分唯一索引 + 应用层事务保证。

3. **`m06_staff_leave` 独立于 M01-02 排班**：
   - M01-02 记录"员工哪天上班"，粒度是天。
   - `m06_staff_leave` 记录"员工哪天的哪个时段在忙什么"，粒度是小时甚至分钟。
   - 二者是"粗粒度 + 细粒度"关系，不是重复。
   - **为什么不复用 M01-02**：M01-02 是全院人事系统，加"手术占用"字段会让它被手术业务污染；而且手术占用变动频繁（每排一台就增一条），不适合放在人事主数据。

4. **无物理外键**（与 M06-01、M06-02 一致）：跨子模块写入加锁影响并发；应用层事务成对写入 + 每日 04:00 孤儿巡检。

5. **`m06_or_room` 与 `m06_or_session` 是配置表，可以加物理外键**：同模块、强从属、变动极少。但为了与其余表风格一致，仍用逻辑外键 + 应用层校验，只在 Alembic 迁移中建普通索引。

6. **`m06_schedule_conflict` 之所以独立成表而不是塞进 `m06_or_schedule` 的 JSONB**：
   - 冲突要按类型、按严重度、按时间段聚合统计（"本月时段冲突几次""人员冲突集中在哪个科室"）。
   - 塞 JSONB 无法聚合。
   - 一条台次可能有 0~8 个冲突，1:N 关系。

ALTER TABLE m06_or_session
    ADD CONSTRAINT ck_m06_session_weekdays
    CHECK (array_length(weekdays, 1) >= 1
           AND weekdays <@ ARRAY[1,2,3,4,5,6,7]::smallint[]);

    ADD CONSTRAINT ck_m06_session_max
    CHECK (max_per_day IS NULL OR max_per_day > 0);

    ADD CONSTRAINT ck_m06_session_fit
    CHECK (EXTRACT(EPOCH FROM (end_time - start_time)) / 60

    '专场配置（某手术间某时段的特殊编排）';

    '覆盖手术间默认接台间隔，注药专场可降到 5 分钟';
COMMENT ON COLUMN m06_or_session.weekdays IS
    '适用星期，1=周一 7=周日';

**预置数据**

| session_code | session_name | room_code | session_type | start | end | weekdays | slot | turnover |
|---|---|---|---|---|---|---|---|---|
| `SES-INJ-AM` | 注药专场（上午） | INJ-01 | INJECTION | 08:00 | 12:00 | {1,2,3,4,5,6} | 15 | 5 |
| `SES-INJ-PM` | 注药室常规（下午） | INJ-01 | NORMAL | 13:30 | 17:30 | {1,2,3,4,5} | 45 | 20 |
| `SES-VIT-WK` | 玻切专场 | OR-03 | VITRECTOMY | 08:00 | 12:00 | {2,5} | 90 | 25 |

**设计要点**

1. **`turnover_minutes` 覆盖手术间默认值**：
   - 注药室默认接台 20 分钟，一天只能做 8 台；专场覆盖成 5 分钟，一天能做 30 台。这是注药大批量开展的前提。
   - 玻切默认 20 分钟不够（器械复杂、消毒要求高），覆盖成 25 分钟。

2. **`weekdays` 用 `SMALLINT[]` 而非位图**：
   - 数组可 `@>` 判断、可 GIN 索引、可读性好。
   - 位图（`weekdays_mask INT`）虽然省空间但不可读，且需要位运算。

3. **`operation_codes` 限定专场适用术式**：
   - 注药专场只做注药，不能排白内障。
   - 排程时校验 `apply.operation_code IN session.operation_codes`（若数组非空）。

4. **`ck_m06_session_fit`**：时间窗口必须能放下至少一台。8:00~12:00 四小时放不下一台 90 分钟的玻切显然配置错误。

**量级估算：** 10~30 行，永久保留。

**分区：** 不分区。

**状态机**

```
        ┌────────────┐
        │   FREE     │  ← 初始 / 释放后
        └─────┬──────┘
              │ 排程
              ▼
        ┌────────────┐
        │  BOOKED    │
        └─────┬──────┘
              │ 停台
              ▼
        ┌────────────┐
        │ SUSPENDED  │
        └─────┬──────┘
              │ 解除
              ▼
        ┌────────────┐
        │   FREE     │
        └────────────┘

        ┌────────────┐
        │  RESERVED  │  ← 急诊预留（配置生成）
        └─────┬──────┘
              │ 10:00 未使用自动释放
              ▼
        ┌────────────┐
        │   FREE     │
        └────────────┘
```

**设计要点**

1. **`uk_m06_slot_key` 用 `(room_code, slot_date, start_time)` 而非 `(room_code, slot_date, start_time, end_time)`**：
   - 同一手术间同一天同一开始的时刻不可能有两个时段（哪怕结束不同）。
   - 简化后唯一性更强。

2. **`uk_m06_slot_schedule` 保证"一台次只占一时段"**：
   - 这是排程幂等的物理基础。
   - 改期时"释放原时段 + 占用新时段"如果中途失败，会出现"一台次占两个时段"或"零个时段"。唯一索引拦住前者。

3. **`status` 与 `schedule_id` 双向钉死**（`ck_m06_slot_booked` / `ck_m06_slot_not_booked`）：
   - `BOOKED` ⟺ `schedule_id 非空`。
   - 防止"状态是 FREE 但还挂着台次 ID"这种脏数据。

4. **`duration_minutes` 用 CHECK 与时间差一致**：
   - 也可以写成生成列，但生成列在 `start_time`/`end_time` 变更时会重算（好事），
   - 用 CHECK 让写入方显式提供（避免隐式行为）。

5. **`released_from_reserve` 记录来源**：
   - 统计"急诊预留释放了多少时段"是评估预留比例是否合理的依据。
   - 若某手术间每天 4 小时预留全部释放，说明该手术间不需要预留。

**量级估算：**

| 项 | 估算 |
|---|---|
| 手术间数 | 5 |
| 每手术间日时段数 | 8（普通）+ 30（注药） |
| 日时段数 | 5 × 8 + 30 ≈ 70 |
| 年记录数 | 70 × 365 ≈ 25,550 |
| 单行平均大小 | 约 180 字节 |
| 年数据量 | 约 4.4 MB |
| 10 年数据量 | 约 44 MB |
| 索引开销 | 约 30 MB |
| **合计（10 年）** | **约 75 MB** |

**分区：** 不分区。`uk_m06_slot_key` 与 `uk_m06_slot_schedule` 若分区要含分区键，**"一台次只占一时段"会被破坏**（跨年份重复）。10 年 25 万行在单表舒适区。

**设计要点**

1. **`uk_m06_schedule_slot` 是"一时段一台次"的最后防线**：

   ```sql
   CREATE UNIQUE INDEX uk_m06_schedule_slot
       ON m06_or_schedule (slot_id)
       WHERE status NOT IN ('RESCHEDULED', 'CANCELLED')
         AND is_deleted = FALSE;
   ```

   - 应用层有 Redis 锁 + DB 行锁双重保护，但唯一索引是"即使锁全失效也不会超排"的底线。
   - 为什么排除 `RESCHEDULED` / `CANCELLED`：这些是历史台次，它们的 `slot_id` 已被释放给新台次。不排除会让新台次插入失败。

2. **`uk_m06_schedule_seq` 保证台次号连续且唯一**：

   ```sql
   CREATE UNIQUE INDEX uk_m06_schedule_seq
       ON m06_or_schedule (room_code, schedule_date, seq_no)
       WHERE status NOT IN ('RESCHEDULED', 'CANCELLED')
         AND is_deleted = FALSE;
   ```

   - 当日某手术间的"第 3 台"只有一个。
   - 插台时后续台次顺延（`seq_no += 1`），若中途失败会违反此索引，自动回滚。

3. **`surgery_start_at` 存 TIMESTAMP 而非 DATE + TIME**：
   - 排程计算频繁做时间加减（+ duration、+ turnover）。
   - TIMESTAMP 运算直观且可建索引。
   - `schedule_date` 单独存 DATE 是因为按日期分组是最高频查询（看板、统计）。

4. **`planned_duration_minutes` 冗余存储而不是每次用 `end - start` 算**：
   - 统计"平均计划时长"要聚合，算表达式无法用简单索引。
   - 且术式时长在 M01-07 可能被改，存快照才能还原"当时排的是多长"。

5. **`delay_minutes` 落库而非实时算**：
   - 准点率统计按延误分钟数分组（`delay_minutes > 10`），实时算会全表扫描。
   - 落库后 `WHERE delay_minutes > 10` 走索引。

6. **`previous_schedule_id` 支持改期链追溯**：
   - 台次 A（RESCHEDULED）→ 台次 B（previous=B）→ 台次 C（previous=B）
   - 形成链条，可以回答"这台手术改了几次期"。

7. **`patient_gender` / `patient_age` / `operation_name` / 各类姓名全部冗余**：
   - 看板、时间轴、统计报表全部要高频率读取这些字段。
   - 若不冗余，每屏 50 台次就要 50 次跨模块 HTTP。
   - 与 M06-01、M06-02 的冗余策略一致。

8. **`ck_m06_sched_completed` 要求 `completed_at` 非空**：
   - `completed_at` 是系统完成时刻（可能是 M09 回写时刻或人工登记时刻）。
   - `actual_end_at` 是手术实际结束时刻（医生说法）。
   - 两者可能相差几分钟（医生说完到下台登记）。分开存便于分析"登记延迟"。

9. **`is_infection_risk` 标记用于 R-09 校验**：
   - 感染手术必须当日最后一台 + 术后终末消毒 60 分钟。
   - 这个规则无法用 CHECK 表达（需查同日其他台次），放应用层。
   - 但字段落库后可被扫描任务批量校验。

**量级估算：**

| 项 | 估算 |
|---|---|
| 日手术台次 | 55 |
| 改期率 10% → 年台次 | 55 × 365 × 1.1 ≈ 22,000 |
| 单行平均大小 | 约 1.2 KB |
| 年数据量 | 约 26 MB |
| 15 年数据量 | 约 390 MB |
| 索引开销 | 约 270 MB |
| **合计** | **约 660 MB** |

**分区：** 不分区。理由同前：`uk_m06_schedule_slot` 与 `uk_m06_schedule_seq` 若分区要含分区键，**"一时段一台次"与"台次号唯一"会被破坏**。15 年 33 万行在单表舒适区（主键查询 <1ms）。

**冲突明细结构（`conflict_detail`）**

```json

  "role": "surgeon",
  "occupied_by": {

    "room_code": "OR-02",
    "surgery_start_at": "2026-10-24T08:30:00"
  }

```

**设计要点**

1. **`ck_m06_conflict_ack` 强制只有 WARN 可确认**：
   - BLOCK 级冲突（时段占用、人员冲突）必须真正解决，不能"确认后继续"。
   - 这是安全设计的硬约束——若能确认 BLOCK，等于排程员可以架空冲突检测。

2. **`is_resolved` 与 `is_acknowledged` 是两个概念**：
   - `is_acknowledged`：WARN 级"我知道有这个问题但我接受"。
   - `is_resolved`：冲突后来被真正解决（换手术间、换人）。
   - 一条 WARN 可能既不确认也不解决（随手排了，后面忘了），这种记录在 `idx_m06_conflict_unresolved` 里可以被扫描出来告警。

3. **`conflict_detail` 用 JSONB**：
   - 八类冲突的明细结构完全不同（时段冲突要记录占用方台次，人员冲突要记录冲突人）。
   - 拆成八个子表是本末倒置。
   - 查询只按 `conflict_type` + `schedule_id`，不需要按明细字段过滤。

| 年数据量 | 约 3 MB |

**分区定义**

```sql
DO $$
DECLARE
    v_start DATE := DATE '2026-10-01';
    v_i INT;
    v_name TEXT;
    v_from DATE;
    v_to DATE;
BEGIN
    FOR v_i IN 0..35 LOOP
        v_from := (v_start + (v_i || ' months')::INTERVAL)::DATE;
        v_to := (v_from + '1 month'::INTERVAL)::DATE;
        v_name := 'm06_schedule_log_' || TO_CHAR(v_from, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m06_schedule_log '
            'FOR VALUES FROM (%L) TO (%L)',
            v_name, v_from, v_to
        );
    END LOOP;
END $$;
```

**设计要点**

1. **只增触发器与 M06-01、M06-02 完全一致的模式**：
   - 应用层可绕过（DBA 手动改、其他服务误写、迁移脚本）。
   - 触发器在数据库层，任何绕过都会抛异常。

2. **`from_status` / `to_status` 与 `before_json` / `after_json` 双轨**：
   - 状态类操作用 `from/to` 字段，简洁可索引。
   - 复杂变更（如改期改了 10 个字段）用 JSON 快照，完整可回放。

3. **为什么分区而不归档**：
   - 日志合规价值随时间衰减（2 年内日常追溯，2~15 年只在纠纷时查）。
   - 分区让"只扫最近 3 个月"物理隔离，性能提升 10 倍以上。

4. **22 种 action 覆盖全流程**：
   - 排程（8）：CREATE/CONFIRM/UPDATE/RESCHEDULE_OUT/RESCHEDULE_IN/MOVE_ROOM/CHANGE_SURGEON/INSERT
   - 停台取消（3）：CANCEL/SUSPEND/SUSPEND_RESCHEDULE
   - 执行（4）：CHECK_IN/SURGERY_STARTED/SURGERY_ENDED/COMPLETED
   - 冲突（2）：CONFLICT_DETECTED/CONFLICT_RESOLVED
   - 配置（5）：ROOM_CREATE/ROOM_UPDATE/ROOM_TOGGLE/SLOT_GENERATE/SLOT_RESERVE/SLOT_RELEASE/CONFIG_UPDATE/EXPORT

**量级估算：**

| 项 | 估算 |
|---|---|
| 每台次日志数 | 约 5.5（创建 1 + 确认 1 + 报到 1 + 开台 1 + 下台 1 + 变更 0.5） |
| 年记录数 | 22,000 × 5.5 ≈ 121,000 |
| 单行平均大小 | 约 500 字节 |
| 年数据量 | 约 58 MB |
| 15 年数据量 | 约 870 MB |
| 索引开销 | 约 500 MB |
| **合计** | **约 1.4 GB** |

**分区：** 按 `seq_date` 月度 RANGE 分区，预建 36 个月。保留 15 年（180 个分区），在线热数据 180 天。
