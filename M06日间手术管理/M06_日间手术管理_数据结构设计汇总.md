## 1. 全局设计规范

### 1.1 表名前缀

M06 全部表使用 `m06_` 前缀，按业务域二级前缀分组：

| 二级前缀 | 业务域 | 表数 | 所属子模块 |
|---|---|---|---|
| `m06_day_` / `m06_eligibility_` / `m06_rule_` / `m06_prepare_` / `m06_cancel_` / `m06_apply_` | 申请与准入 | 7 | M06-01 |
| `m06_prepare_` | 术前准备 | 8 | M06-02 |
| `m06_or_` / `m06_schedule_` / `m06_staff_` | 排程与手术室 | 8 | M06-03 |
| `m06_verify_` / `m06_handover` / `m06_wristband` | 核对与交接 | 9 | M06-04 |
| `m06_recovery_` / `m06_discharge_` / `m06_delay` | 复苏与离院 | 10 | M06-05 |
| `m06_settle_` / `m06_settlement` / `m06_archive_` / `m06_qc_` | 结算与归档 | 8 | M06-06 |
| `m06_stat_` / `m06_metric_` / `m06_target` / `m06_export_` | 质量与统计 | 7 | M06-07 |

**为什么 `m06_prepare_` 前缀跨 M06-01 与 M06-02**：`m06_prepare_item`（准备清单）由 M06-01 在申请单创建时生成，由 M06-02 执行。表归属 M06-01（生成方），业务归属 M06-02（执行方）——这是**唯一跨子模块共享的表**，文档债 **T-01**。

### 1.3 枚举字段：VARCHAR + CHECK，不用 PG ENUM

**三条理由：**

1. **`ALTER TYPE ... ADD VALUE` 不能在事务块内执行**——Alembic 迁移会被卡住，必须用 `COMMIT` 拆分；
2. **删除或重命名枚举值需要重建整个类型**——业务演进（如新增"核销"状态）需要 `DROP TYPE` + 重建 + 全部表 `ALTER COLUMN`，风险极高；
3. **应用层 `Literal` 已提供类型安全**——Pydantic V2 的 `Literal["A","B"]` 在反序列化时即校验，DB 层 CHECK 只是最后防线。

```sql
-- 采用
status VARCHAR(24) NOT NULL DEFAULT 'DRAFT'
    CHECK (status IN ('DRAFT','PENDING_REVIEW','ELIGIBLE',...))
```

### 1.4 时间语义

| 字段后缀 | 类型 | 语义 |
|---|---|---|
| `_at` | `TIMESTAMP` | 精确时刻（秒级） |
| `_date` | `DATE` | 业务日期 |
| `_time` | `TIME` | 时刻（无日期，时段用） |
| `_minutes` / `_seconds` | `INTEGER` | 时长 |

**`created_at` 与业务时刻必须区分：**

| 场景 | 用哪个 |
|---|---|
| "什么时候排的台次" | `created_at` |
| "手术计划什么时候开始" | `surgery_start_at` |
| "什么时候统计的" | `calc_at` |
| "统计的是哪一天" | `stat_date` |

**典型错误**：用 `created_at` 代替 `surgery_start_at` 统计准点率——补录历史台次时 `created_at` 是补录时刻而非手术时刻，准点率会完全失真。

### 1.5 金额与数量类型

| 用途 | 类型 | 说明 |
|---|---|---|
| 金额 | `NUMERIC(16,2)` | 总额、减免、余额 |
| **单价** | **`NUMERIC(14,4)`** | **药品按每片 0.0250 元计价** |
| 数量 | `NUMERIC(12,3)` | 药品可拆零（0.333 片） |
| 整数计数 | `INTEGER` | 台次、人数 |
| 时长（分钟） | `INTEGER` | 非负数 |
| 比率（%） | `NUMERIC(6,2)` | 0.00~100.00 |
| 比率（小数） | `NUMERIC(6,4)` | 0.0000~1.0000（权重、置信度） |
| 得分 | `NUMERIC(6,2)` | 0.00~100.00 |
| 阈值（参考区间） | `NUMERIC(12,4)` | 检验/生命体征 |

**禁止使用 `FLOAT` / `REAL` / `DOUBLE PRECISION` 存储金额、数量、比率。**

**行级先舍入铁律（DB 层落地）：**

```sql
-- m06_settle_cost
CHECK (amount = ROUND(quantity * unit_price, 2))

-- m06_stat_daily
CHECK (archive_score_avg IS NULL
       OR (archive_score_avg >= 0 AND archive_score_avg <= 100))
```

### 1.7 `updated_at` 自动更新触发器

```sql
CREATE OR REPLACE FUNCTION fn_m06_set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = CURRENT_TIMESTAMP;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 每张可变表挂载
CREATE TRIGGER trg_m06_ds_updated_at
    BEFORE UPDATE ON m06_day_surgery
    FOR EACH ROW EXECUTE FUNCTION fn_m06_set_updated_at();
```

**为什么用触发器而非应用层：** 应用层负责更新必有遗漏（批量 SQL、DBA 手动修数、迁移脚本），触发器是唯一可靠的兜底。

### 1.8 软删除与部分唯一索引

**软删除必须配部分唯一索引：**

```sql
-- 错误：删除后无法重新创建同编码
CREATE UNIQUE INDEX uk_m06_ds_no ON m06_day_surgery (ds_no);

-- 正确
CREATE UNIQUE INDEX uk_m06_ds_no
    ON m06_day_surgery (ds_no)
    WHERE is_deleted = FALSE;
```

**M06 的 12 个核心部分唯一索引见 [6.5 节](#65-部分唯一索引12-条核心)。**

### 1.9 主键与分区表

**普通表**：`id BIGINT IDENTITY` 单列主键。

**分区表**（7 张日志表 + `m06_or_slot`）：

```sql
CREATE TABLE m06_apply_log (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    seq_date DATE NOT NULL,
    ...
    PRIMARY KEY (id, seq_date)   -- 分区键必须进主键
) PARTITION BY RANGE (seq_date);
```

**`seq_date` 冗余列的必要性：**
- PostgreSQL 分区键必须是列或表达式；
- 用 `seq_date = DATE(created_at)` 冗余普通列，分区裁剪走普通列索引更快；
- 约束 `CHECK (seq_date = DATE(created_at))` 保证一致。

### 3.3 逻辑外键而非物理外键

**M06 全部表之间不建物理外键。** 三条理由：

1. **性能**：`m06_verify_item` 有 213 万行/15 年，插入 20 条/次核对，物理外键每次插入要查父表；
2. **解耦**：`m06_day_surgery` 归档后可能被移到历史库，子表仍在主库；
3. **分区兼容**：分区表之间无法建物理外键（PostgreSQL 限制）。

**一致性三层保证：**

| 层 | 机制 |
|---|---|
| 第一层 | 应用层事务成对写入（`apply_id` 创建与子表插入同事务） |
| 第二层 | CHECK 约束验证关联标识非空 |

### 3.4 跨子模块共享表

**只有 1 张：`m06_prepare_item`**

| 属性 | 值 |
|---|---|
| 主定义 | M06-01 数据结构 4.6 节 |
| 生成方 | M06-01（申请单创建时按 M01-07 规则展开） |
| 执行方 | M06-02（逐项 DONE / NA / FAILED） |
| 扩展字段 | M06-02 的 `m06_prepare_item_ext`（1:1 补充执行细节） |

**为什么必须共享而非各建一套：**

## 5. 分区与归档

### 5.1 分区判定原则

**判定顺序：**

1. 是否有跨年份唯一约束？→ 有则**不能分区**（分区会迫使唯一索引含分区键）；
2. 年行数是否 >50 万？→ 否且 15 年 <300 万则**不必分区**；
3. 查询是否总是"最近 N 天"？→ 是则分区收益最大；
4. 是否需要定期归档历史数据？→ 是则分区可 `DETACH` 归档。

### 5.4 分区自动创建

```sql
CREATE OR REPLACE FUNCTION fn_m06_create_month_partitions(
    p_table TEXT,
    p_months INT DEFAULT 3
) RETURNS INT AS $$
DECLARE
    v_start DATE;
    v_i INT;
    v_name TEXT;
    v_from DATE;
    v_to DATE;
    v_count INT := 0;
BEGIN
    v_start := DATE_TRUNC('month', CURRENT_DATE)::DATE;

    FOR v_i IN 0..(p_months - 1) LOOP
        v_from := (v_start + (v_i || ' months')::INTERVAL)::DATE;
        v_to := (v_from + '1 month'::INTERVAL)::DATE;
        v_name := p_table || '_' || TO_CHAR(v_from, 'YYYYMM');

        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF %I '
            'FOR VALUES FROM (%L) TO (%L)',
            v_name, p_table, v_from, v_to
        );
        v_count := v_count + 1;
    END LOOP;

    RETURN v_count;
END;
$$ LANGUAGE plpgsql;
```

**调度**：每月 25 日 02:00 `job_m06_create_partitions` 为全部 7 张月分区表预建未来 3 个月分区。

**为什么提前 3 个月**：若分区不存在，插入会报 `no partition of relation found for row`，手术台次数据写入失败——提前 3 个月留足修复窗口。

### 5.5 归档流程

**四步归档（不可跳过）：**

```sql
-- 第 1 步：创建归档表（结构相同）
CREATE TABLE m06_apply_log_202401
    (LIKE m06_apply_log INCLUDING DEFAULTS INCLUDING CONSTRAINTS);

-- 第 2 步：搬迁数据
INSERT INTO m06_apply_log_202401
SELECT * FROM m06_apply_log_202401_orig;

-- 第 3 步：核对行数（铁律）
SELECT
    (SELECT COUNT(*) FROM m06_apply_log_202401) AS archived,
    (SELECT COUNT(*) FROM m06_apply_log_202401_orig) AS orig;

-- 第 4 步：行数一致才可删除
DROP TABLE m06_apply_log_202401_orig;
```

**归档铁律：归档表行数必须与被删行数完全一致才可删主表。** 差异哪怕 1 行也必须停下来查原因——这 1 行可能是唯一一份证明某台手术合规的记录。

### 6.6 为什么唯一索引一定要带 `COALESCE`

**PostgreSQL 认为 `NULL` 与 `NULL` 不相等。**

```sql
-- 反面示例
CREATE UNIQUE INDEX uk_m06_stat_daily_key
    ON m06_stat_daily (stat_date, dimension_code, dimension_value);
```

**后果**：全院维度 `dimension_value = NULL`，可以有**无限条**重复记录。查询 `SUM(total_count)` 会得到 3 倍数据——管理者看到的台次从 1,286 变成 3,858。

```sql
-- 正确写法
CREATE UNIQUE INDEX uk_m06_stat_daily_key
    ON m06_stat_daily (stat_date, dimension_code,
                       COALESCE(dimension_value, ''))
    WHERE is_deleted IS DISTINCT FROM TRUE;
```

**为什么不用 `NULLS NOT DISTINCT`**：这是 PostgreSQL 15+ 特性，本项目部分环境仍是 PG 14。

**M06 中必须用 `COALESCE` 的 5 处：**

| 表 | 索引 |
|---|---|
| `m06_stat_daily` | `uk_m06_stat_daily_key` |
| `m06_stat_monthly` | `uk_m06_stat_monthly_key` |
| `m06_target` | `uk_m06_target_key`（`COALESCE(scope_id, 0)`） |
| `m06_eligibility_rule` | `uk_m06_rl_item`（`COALESCE(scope_key,'')`） |
| `m06_parse_config` 类 | 各参数表（`COALESCE(scope_id,'')`） |

## 7. 与外部模块的数据边界

### 7.1 M06 只读的外部表中转

M06 **不直接读取外部模块的表**，全部通过 HTTP 契约。但以下数据会**冗余一份快照**到 M06：

| 外部数据 | 冗余到 | 冗余字段 | 理由 |

| 主刀姓名 | `m06_day_surgery` | `surgeon_name` | 同上 |

| 员工姓名 | 各表 | `*_name` 字段 | 同上 |

## 8. 错误码区间

### 8.1 六段错误码

| 子模块 | 号段 | 实用数量 |
|---|---|---|
| M06-01 日间手术申请与准入 | `"0601001"`~`"0601049"` | 36 |
| M06-02 术前准备与检查闭环 | `"0602001"`~`"0602064"` | 41 |
| M06-03 日间手术排程与手术室 | `"0603001"`~`"0603049"` | 36 |
| M06-04 术前核对与患者交接 | `"0604001"`~`"0604049"` | 49 |
| M06-05 术后复苏与离院评估 | `"0605001"`~`"0605049"` | 42 |
| M06-06 日间结算与病历归档 | `"0606001"`~`"0606049"` | 42 |
| M06-07 日间手术质量与统计 | `"0607001"`~`"0607049"` | 35 |
| **合计** | `"0600001"`~`"0607999"` | **281** |

### 8.2 号段内分布建议

| 区间 | 用途 |
|---|---|
| `001`~`009` | 通用错误（不存在、参数非法） |
| `010`~`029` | 业务规则违反 |
| `030`~`039` | 权限与合规 |
| `040`~`049` | 集成失败 |
| `050`~`099` | 预留扩展 |

### 8.3 格式规范

- **7 位字符串**：`AABBCCC`，`AA`=模块号（06），`BB`=子模块号（01~07），`CCC`=序号；
- **必须以字符串形式返回**：JSON 中为 `"code": "0601001"`（带引号）；
- **成功仍为整数 0**：`"code": 0`；
- **系统级通用码保留 4~5 位**：`40001` 参数校验失败 / `40100` 未认证 / `40300` 无权限 / `50000` 服务器错误。

**为什么必须是字符串**：`06` 开头的整数在 Python 是非法八进制字面量（`BizException(0601001, ...)` 报 `SyntaxError: invalid token`），必须写成 `BizException("0601001", ...)`。

**文档债 T-02**：M06 没有统一的全局参数表，与 M12/M13 的设计一致性问题相同。建议后续统一为 `m06_sys_config`（`param_code` 前缀区分），当前五张表的命名规范与字段结构已一致，合并成本低。

### 9.2 统一参数表结构

```sql
CREATE TABLE m06_xxx_config (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    param_code    VARCHAR(64) NOT NULL,
    param_name    VARCHAR(128) NOT NULL,
    param_value   VARCHAR(500) NOT NULL,
    param_type    VARCHAR(16) NOT NULL,
    param_group   VARCHAR(24) NOT NULL,
    scope         VARCHAR(16) NOT NULL DEFAULT 'GLOBAL',
    scope_id      BIGINT,
    default_value VARCHAR(500),
    min_value     VARCHAR(64),
    max_value     VARCHAR(64),
    is_sensitive  BOOLEAN NOT NULL DEFAULT FALSE,
    is_editable   BOOLEAN NOT NULL DEFAULT TRUE,
    remark        VARCHAR(500),
    version       INT NOT NULL DEFAULT 1,
    updated_by    BIGINT,
    created_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    is_deleted    BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE UNIQUE INDEX uk_m06_xxx_config
    ON m06_xxx_config (param_code, scope, COALESCE(scope_id, ''))
    WHERE is_deleted = FALSE;
```

**`COALESCE(scope_id, '')` 的必要性**：`GLOBAL` 作用域的 `scope_id` 为 NULL，若不加 COALESCE，同一参数可以有无限条 GLOBAL 记录，读取 `LIMIT 1` 取到哪个不确定。

### 9.3 关键参数（安全红线，敏感 + 只读）

| 参数 | 默认 | 所属 | 敏感 | 只读 | 依据 | 篡改后果 |
|---|---|---|---|---|---|---|
| `M06.VERIFY.PADSS_MIN` | 9 | M06-05 | ✅ | ✅ | 日间手术离院标准 | 调低 → 未达离院标准患者被放回家 |
| `M06.VERIFY.ALDRETE_MIN_EXIT` | 9 | M06-05 | ✅ | ✅ | 麻醉复苏标准 | 调低 → 未清醒患者被推出复苏室 |
| `M06.VERIFY.IOP_MIN` / `IOP_MAX` | 5 / 25 | M06-05 | ✅ | ✅ | 眼科临床规范 | 放宽 → 高眼压患者被放回家，视神经损伤 |
| `M06.VERIFY.MIN_OBSERVE_CATARACT` | 120 | M06-05 | ✅ | ✅ | 本院日间手术管理制度 | 调低 → 粘弹剂残留高眼压漏诊 |
| `M06.VERIFY.MIN_OBSERVE_VITRECTOMY` | 240 | 同上 | ✅ | ✅ | 同上 | 同上 |
| `M06.VERIFY.MIN_OBSERVE_IVI` | 60 | 同上 | ✅ | ✅ | 同上 | 同上 |
| `M06.VERIFY.ANESTHESIA_GAP_MIN` | 120 | 同上 | ✅ | ✅ | 麻醉安全要求 | 调低 → 二次镇静导致回家途中呼吸抑制 |
| `M06.VERIFY.REVISIT_WINDOW_HOURS` | 72 | 同上 | ✅ | ✅ | 质控指标定义 | 改动 → 指标失真，无法衡量离院质量 |
| `M06.SCHEDULE.TURNOVER_INFECTION_MINUTES` | 60 | M06-03 | ✅ | ✅ | 感染控制规范 | 调低 → 术后感染暴发 |
| `M06.STOCK.SCORE_MIN` | 90 | M06-06 | ✅ | ✅ | 病历质量评定标准 | 调低 → 缺件病历被归档封存 |
| `M06.STATS.RECONCILE_THRESHOLD` | 0.001 | M06-07 | ✅ | ❌ | 数据质量要求 | 调到 10% → 对账差异 5% 不告警 |

**为什么这些参数必须"敏感 + 只读"：**
- **敏感**：修改需医务科审批（`m06:config:manage` + 医务科会签）；
- **只读**：不允许任何人修改——它们是**法规与临床规范的数字表达，不是可调参数**。

**唯一的例外**：`M06.STATS.RECONCILE_THRESHOLD` 是敏感可编辑（数据质量阈值可以调整，但需审批）。

### 9.4 参数作用域解析顺序

```
EXAM（项目级，scope_id=operation_code）
  ↓ 未命中
DEPT（科室级，scope_id=dept_id）
  ↓ 未命中
GLOBAL（全局，scope_id=NULL）
  ↓ 未命中
抛 "0601016" 参数未配置
```

**越具体越优先**：全局兜底 → 科室微调 → 项目特例。
