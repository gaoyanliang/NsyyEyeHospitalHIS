## 1. 模块概述

### 1.1 模块定位

M06-02 是日间手术的**安全准备引擎**。它回答一个问题：

> **这台手术，该准备的都准备齐了吗？**

日间手术与住院手术最大的区别不在手术本身，而在于**住院手术可以在病区里慢慢补，日间手术没有第二次机会**。患者早上 8 点来，10 点就要上台，如果发现血糖没测、抗凝药没停、知情同意书没签，整台手术只能取消——患者白跑一趟，手术间空转，医生排班打乱。

M06-02 的全部设计目标，就是把这类"当天才发现"的意外压到接近零。

```
┌──────────────────────────────────────────────────────────────────────────┐
│                      M06 日间手术全流程                                   │
│                                                                          │
│  ┌─────────────┐                                                         │
│  │ 「能不能做」 │◄── M06-01 申请与准入                                    │
│  └──────┬──────┘                                                         │
│         │ 生成准备清单（10 类）                                           │
│         ▼                                                                │
│  ┌─────────────────────────────────────────────┐                        │
│  │ 「准备齐了吗」 ◄── M06-02 术前准备与检查闭环 │                        │
│  │                                              │                        │
│  │  T-7 天  开检查检验单、预约检查              │                        │
│  │  T-3 天  检查检验结果回报，异常则干预        │                        │
│  │  T-1 天  停抗凝药核对、麻醉访视、术前宣教    │                        │
│  │  T-0 当天 禁食确认、散瞳、抗菌药、同意书     │                        │
│  │  T-0 上台前 准备就绪判定 → 放行到 M06-04      │                        │
│  └──────┬──────────────────────────────────────┘                        │
│         │ 准备就绪                                                  │
│         ▼                                                                │
│  ┌─────────────┐                                                         │
│  │ 「排到哪天」 │◄── M06-03 日间手术排程与手术室                          │
│  └─────────────┘                                                         │
└──────────────────────────────────────────────────────────────────────────┘
```

**M06-02 在整条链路中是唯一"能提前发现问题"的环节。** M06-03 排程、M06-04 核对都只能"发现得太晚"——病人都来了、手术间都排了，才发现血糖 12.8，此时取消的成本最高。

### 1.2 为什么独立成子模块

#### 理由一：术前准备是日间手术最大的医疗风险来源

日间手术的四大类风险中，**三类出在术前准备**：

| 风险类型 | 典型场景 | 后果 | 归属 |
|---|---|---|---|
| 准备漏项 | 未禁食做全麻 → 呕吐误吸 | 窒息、吸入性肺炎、可致死 | **M06-02** |
| 准备漏项 | 未停华法林 → 术中出血 | 球后出血、眶内血肿、压迫视神经致盲 | **M06-02** |
| 准备漏项 | 未散瞳 → 晶状体手术视野受限 | 手术中断、改期 | **M06-02** |
| 准备漏项 | 未签同意书 → 术后纠纷 | 举证不能 | **M06-02** |
| 检查异常未拦截 | 血糖 15.6 强行手术 → 术后感染 | 眼内炎 | **M06-02** |
| 术眼错误 | 左眼写成右眼 | 做错眼、法律事故 | M06-04 |
| 术后离院过早 | PADSS 4 分就放走 | 迟发性出血无人发现 | M06-05 |
| 术中并发症 | 后囊破裂 | 需转住院 | M09 |

如果把术前准备拆散到各处（检查归 M12、检验归 M13、禁食护士记纸上、同意书归 M18），**没有任何一个地方能回答"这个患者明天到底能不能上台"**。这正是 M06-02 存在的理由。

#### 理由二：准备是有时序的，不是一张清单

术前准备不是"勾完了就行"，而是**在正确的时间做正确的事**：

| 时间点 | 要做的事 | 漏做的后果 |
|---|---|---|
| T-7 天 | 开术前检查检验单；预约检查 | 结果赶不上手术日 |
| T-3 天 | 检查检验结果回报；异常项干预 | 到术日才发现血糖超标 |
| T-1 天 | 抗凝药停药确认；麻醉术前访视；术前宣教与禁食告知 | 全麻误吸；抗凝未停致出血 |
| T-0 术前 2h | 禁食禁水最终确认 | 全麻误吸 |
| T-0 术前 60min | 散瞳滴眼 | 术中视野受限 |
| T-0 术前 30min | 预防性抗菌药滴眼 | 术后眼内炎风险上升 |
| T-0 术前 15min | 同意书核对、腕带核对 | 举证不能 |

**如果这张清单只是"10 个复选框"，它无法回答"现在几点、这一步该不该已经做了"**。M06-02 用 `timing_offset_minutes` 把每一项锚定在术前时间轴上，才能主动提醒"散瞳还差 20 分钟没人做"。

#### 理由三：闭环的关键是"自动关联结果"，不是"人工勾选"

术前检查检验的结果在 M12/M13 里已经存在。如果让护士看着报告手工勾"已完成"，会出现两种问题：

- **漏勾**：护士忙起来忘了勾，准备清单一直显示"未完成"，但实际已经做了 → 反复催、反复核对，浪费人力
- **假勾**：护士为了推进流程，没看到结果也先勾上 → 记录合规了，风险没消除

M06-02 的做法是：**拉着 M12/M13 的结果自动完成对应项**（`done_source='AUTO'` + `auto_ref_type`/`auto_ref_id`），护士只需要关注"结果有没有异常"而不是"有没有勾"。人工勾选只保留给无法自动判定的项（禁食确认、散瞳、腕带核对）。

#### 理由四：准备就绪判定是 M06-04 的放行前置，必须有独立的口径

M06-04 术前核对要做四方 Time-Out。但在做 Time-Out 之前，必须有一个明确的"准备就绪"信号，否则四种角色（主刀、麻醉、病区护士、手术室护士）会在"这个患者到底准备好了没有"上各说各话。

M06-02 提供的 `GET /internal/v1/m06/prepare/readiness/{apply_id}` 就是这个唯一口径：**返回 `READY` / `NOT_READY` / `EXPIRED` 三态 + 阻塞项明细**。M06-04 只认这一个信号，不自己判断。

| 生成准备清单 | ✅ 从 M01-07 规则展开 | ❌ 只消费 | ❌ | ❌ | ❌ |
| 执行准备项（禁食/散瞳/给药） | ❌ | ✅ | ❌ | ❌ | ❌ |
| 术前检查检验开单 | ❌ | ✅ 调 M07-03 生成医嘱 | ❌ | ❌ | ❌ |
| 术前检查检验执行 | ❌ | ❌ | ❌ | ✅ | ❌ |
| 检查检验结果判读 | ❌ | ✅ 拉结果判异常 | ❌ | ❌ 结果本身归 M12/M13 | ❌ |

**唯一责任（用 ✅ 标出的）**：M06-02 是**唯一**执行术前准备项、唯一判定"准备就绪"的地方。其他任何模块都不得自行修改准备项状态或自行判断是否就绪。

### 1.4 概念辨析

#### 1.4.1 术前准备 vs 术前检查

| 概念 | 内容 | 执行方 | 是否算准备项 |
|---|---|---|---|
| **术前检查** | IOL Master、角膜内皮、B 超、OCT | 检查科室（M12） | ✅ 算（EXAM 类） |
| **术前检验** | 血常规、凝血、传染病八项、血糖 | 检验科室（M13） | ✅ 算（LAB 类） |
| **术前准备（狭义）** | 禁食、散瞳、抗菌药、备皮 | 护士/患者 | ✅ 算 |
| **术前访视** | 麻醉访视、主刀访视 | 麻醉医生/主刀 | ✅ 算（ANESTHESIA_VISIT 类） |
| **术前宣教** | 讲解手术流程、告知注意事项 | 护士 | ❌ 不算（无强制留痕要求） |

**为什么术前检查检验算准备项**：因为它们的**结果**决定能不能上台。IOL Master 没做出来，人工晶体度数就没有，手术无从谈起。

**为什么术前宣教不算准备项**：宣教是过程性的，难以客观判定"讲到位了"。如果算准备项，就变成了"护士自己勾自己有没有讲"，没有约束力，只会污染准备率统计。

#### 1.4.2 准备完成 vs 准备就绪

| 概念 | 定义 | 判定条件 | 用途 |
|---|---|---|---|
| **准备完成** | 每一项状态都不是 `PENDING` | 全部 `DONE` / `NA` / `FAILED` | 进度展示 |
| **准备就绪** | 全部必做项完成**且无异常** | 必做项全 `DONE` 或 `NA`；`FAILED` 项已处置；`is_abnormal` 项已闭环 | M06-04 放行前置 |

**关键区别**：一个患者可能"准备完成"但"不就绪"——比如凝血检查做了（DONE），但 INR 2.8（`is_abnormal=TRUE`）。此时清单不打红叉，但就绪判定必须是 `NOT_READY`。

**为什么这两个概念必须分开**：如果混为一个，护士看到"100% 完成"会以为没问题，实际上有个致命异常。分开后，"完成度"给护士看进度条，"就绪度"给系统做放行判定。

#### 1.4.3 异常项处置 vs 改期

| 场景 | 处置动作 | 申请单状态变化 |
|---|---|---|
| 轻微异常可干预 | `RESOLVED`（已干预），继续准备 | 不变 |
| 需复查 | `RECHECK`（复查），生成复查项 | 不变 |
| 需改期 | `DEFER`（延迟），触发 M06-01 改期流程 | → `ELIGIBLE` 待重新排程 |
| 需转内科治疗 | `REFER`（转诊），触发申请单取消 | → `CANCELLED` |

M06-02 **不直接改申请单状态**，只发出事件 `m06.prepare.blocked`，由 M06-01 处理状态流转。理由：M06-02 的职责是"发现问题"，"决定怎么办"是临床决策，责任在 M06-01 的取消/改期审批链上。

### 1.5 模块目标

| 指标 | 目标值 | 测量方式 |
|---|---|---|
| 术前准备就绪率（上台前） | ≥ 99.5% | 就绪判定为 `READY` 的台次 ÷ 总台次 |
| T-1 天前发现问题比例 | ≥ 95% | T-1 天前有异常记录且已处置的 ÷ 总异常数 |
| 检查检验结果自动关联率 | ≥ 90% | `done_source='AUTO'` 的 ÷ EXAM+LAB 类项 |
| 当天取消率（因准备不足） | ≤ 0.5% | 因准备项失败或缺失导致取消的 ÷ 总台次 |
| 准备清单完成率（术日 08:00） | ≥ 98% | 必做项全 `DONE`/`NA` 的 ÷ 总台次 |
| 就绪判定响应时间 | P95 ≤ 150ms | 接口埋点 |
| 自动关联延迟（结果就绪 → 更新清单项） | ≤ 60 秒 | 事件到达 → 清单项 DONE 的时间差 |
| 术前检查检验完成率 | ≥ 99% | 已出结果 ÷ 已开单 |

**为什么"当天取消率"目标定在 0.5% 而不是 0**：真实世界里总有患者临时不配合（早上吃了东西不肯承认）、有设备突然故障、有检验结果异常到必须取消。目标 0 会逼团队把数据做假；0.5% 是一个可以公开追踪、可以逐案复盘的诚实目标。

### 2.4 依赖清单与失败影响

| 依赖 | 接口 | 超时 | 失败影响 | 降级策略 |

| M12 检查报告 | `GET /internal/v1/m12/review/{id}` | 2s | 无法自动关联检查结果 | 转人工勾选 + 告警 |

| M13-05 参考区间 | `GET /internal/v1/m13/lab-item/rule/{code}` | 1s | 无法判高低 | 只标数值不标高低 |
| M01-07 术前规则 | `GET /internal/v1/surgery/operations/{code}/full-config` | 2s | 无法扩展清单 | 用 M06-01 已存清单 |
| M01-02 员工 | `GET /internal/v1/employee/{id}` | 1s | 无法显示执行人姓名 | 显示工号 |
| M03-05 消息 | `POST /internal/v1/message/send` | 2s | 提醒发不出去 | Celery 重试 5 次 + 站内信兜底 |
| M02-06 审计 | `POST /internal/v1/audit/record` | 1s | 审计缺失 | 异步补偿队列 |

**关键判据**：M06-02 的所有外部依赖**都不阻断主流程**。理由：术前准备是"可以让护士手工记在纸上"的业务，系统挂掉不能导致手术无法进行。所有降级都保留"人工兜底"路径，并在页面上明确标注"当前为手工模式"。

## 3. 业务模型

### 3.1 准备清单模型

#### 3.1.1 清单来源与扩展

M06-01 在建申请单时，从 M01-07 拉取 `prepareRule` 展开成 `m06_prepare_item`。M06-02 拿到清单后做两件事：

1. **补算绝对时间**：`absolute_time = surgery_start_at - timing_offset_minutes`
2. **按需扩展**：某些项目需要在 M06-02 里追加（如检查异常后追加复查项）

```
│  6. ANTIBIOTIC     抗菌药      offset -30 min   [必做]            │
│  7. CONSENT        同意书      offset -1440 min [必做]            │
```

**为什么时间用偏移量而不是绝对时间存**：手术时间可能改。如果存绝对时间（"10 月 22 日 10:00 做 IOL Master"），手术从 10 月 24 日改到 10 月 26 日时，所有绝对时间都要重算并更新 —— 谁负责更新？如果 M06-03 改了排程，M06-02 不知道，清单时间就全都错了。

用 `timing_offset_minutes` 相对偏移，**手术时间一变，绝对时间自动跟着变**，无需跨模块同步。

#### 3.1.2 七段时序模型

把术前准备按"需要提前多久"切成七段：

| 时段 | 时间窗 | 典型项目 | 责任方 | 漏做后果 |
|---|---|---|---|---|
| **P1 检查期** | T-7 ~ T-3 | 术前检查（IOL Master、角膜内皮、B 超） | 检查科室 | 没数据无法定晶体度数 |
| **P2 检验期** | T-7 ~ T-3 | 术前检验（血常规、凝血、传染病、血糖） | 检验科室 | 异常未发现 |
| **P3 干预期** | T-3 ~ T-2 | 异常项干预（控糖、降压、停抗凝） | 门诊医生 | 到术日血糖仍高 |
| **P4 访视期** | T-2 ~ T-1 | 麻醉访视、主刀访视、同意书签署 | 麻醉/主刀/护士 | 全麻风险未评估 |
| **P5 宣教期** | T-1 | 禁食告知、停抗凝确认、来院时间告知 | 护士 | 患者早上吃东西 |
| **P6 术日准备** | T-0 术前 2h ~ 30min | 禁食确认、散瞳、抗菌药、备皮、腕带 | 日间病房护士 | 无法上台 |
| **P7 就绪判定** | T-0 术前 15min | 就绪判定、放行 | 系统 + 护士长 | 带缺陷上台 |

**七段模型的价值**：每一段都有自己的"最后期限"。系统在每一段的截止时刻做一次扫描，把"该做没做"的项目推给责任方。**这是把"被动等出问题"变成"主动提前发现"的关键。**

#### 3.1.3 准备项状态机

```

                        └──────┬───────┘
                               │
          ┌────────────────────┼────────────────────┐
          │ 护士勾选            │ 自动关联结果        │ 不需要做（写原因）
          ▼                    ▼                    ▼
    ┌──────────┐        ┌──────────┐         ┌──────────┐
    │   DONE   │◄───────│   DONE   │         │    NA    │
    │ (MANUAL) │        │  (AUTO)  │         │ (不适用) │

         │                   │
         │ 结果异常           │ 结果异常

    ┌─────────────────────────────┐
```

**状态说明：**

| 状态 | 中文 | 是否计入"已完成" | 说明 |
|---|---|---|---|
| `PENDING` | 待执行 | ❌ | 初始态 |
| `DONE` | 已完成 | ✅ | 人工勾选或自动关联 |
| `NA` | 不适用 | ✅ | 需写 ≥5 字原因 |
| `FAILED` | 未通过 | ❌ | 做了但结果不合格 |

**为什么 `FAILED` 不计入已完成**：这是**整个准备闭环的核心判定**。如果 `FAILED` 算完成，那么"凝血异常"这一项会显示绿色勾，护士会以为可以上台。

**但 `FAILED` 也不能一直卡住**——所以要区分"已处置"和"未处置"：`FAILED` + `处置动作 != NULL` 时，就绪判定把它算作"已闭环"，允许上台。

#### 3.1.4 为什么禁食要有"确认"这一步而不只是"告知"

禁食是全麻手术最基础也最容易出问题的准备项。真实场景：

- 护士 T-1 天电话告知"明早别吃饭别喝水"
- 患者理解成"别吃饭，可以喝点牛奶"
- 术日早上 8 点患者说"我只喝了杯牛奶"
- 全麻诱导 → 呕吐 → 误吸

**告知 ≠ 理解 ≠ 做到**。所以 M06-02 要求术日早上有一步**主动确认**：

| 确认项 | 内容 | 记录方式 |
|---|---|---|
| 最后进食时间 | 具体几点吃了什么 | 患者口述 + 护士记录 |
| 最后饮水时间 | 具体几点喝了多少 | 患者口述 + 护士记录 |
| 是否达到禁食时长 | 系统按 `fasting_solid_hours`/`fasting_liquid_hours` 计算 | 自动判 + 护士确认 |
| 患者是否理解 | 复述一遍 | 勾选确认 |

**禁食时长的计算**：

```
禁食时长 = surgery_start_at - last_intake_at
固体达标 = 禁食时长 >= fasting_solid_hours  (全麻默认 8h)
清饮达标 = 禁食时长 >= fasting_liquid_hours  (全麻默认 2h)
```

如果 `固体达标 = FALSE`，`status` 直接置 `FAILED`，就绪判定 `NOT_READY`，**这是硬阻断**——不允许"医生决定照做"。理由：误吸可致死，没有任何手术收益能抵这个风险。

### 3.2 检查检验闭环模型

#### 3.2.1 开单 → 执行 → 回报 → 关联 → 判读 五段

```
┌────────────┐   ┌────────────┐   ┌────────────┐   ┌────────────┐   ┌────────────┐
│ 1. 开单     │──►│ 2. 执行     │──►│ 3. 回报     │──►│ 4. 关联     │──►│ 5. 判读     │
│            │   │            │   │            │   │            │   │            │
│ 调 M07-03  │   │ M12/M13    │   │ 报告就绪   │   │ 事件驱动   │   │ 查参考区间  │
│ 生成医嘱   │   │ 技师/仪器   │   │ 事件发出   │   │ 自动 DONE  │   │ 判高低/异常 │
└────────────┘   └────────────┘   └────────────┘   └────────────┘   └────────────┘
      │                 │                │                │                │
      ▼                 ▼                ▼                ▼                ▼
  order_id          report_id        事件载荷         auto_ref_id      is_abnormal
  order_no          报告人            含 task_no      done_source=AUTO  abnormal_desc
```

**为什么是事件驱动而不是定时轮询**：

- 轮询：每 5 分钟查一次"有没有新结果"，晚发现最多 5 分钟。术前检查检验都是 T-3 天前完成，5 分钟无感。但**每次轮询扫描全部申请单的检查检验状态**，日 60 台 × 8 项 × 每 5 分钟 = 每天 14 万次查询
- 事件：M12/M13 在报告发布时发 `m12.review.published` / `m13.review.published`，M06-02 收到后只处理相关的申请单。**延迟 < 10 秒，零无效查询**

选事件驱动。但事件不是 100% 可靠（消息可能丢），所以补一条**兜底轮询**：每小时扫一次"已过 expected_time 但仍 PENDING 的 EXAM/LAB 项"，触发补偿查询。

#### 3.2.2 异常判定的三层

```
┌────────────────────────────────────────────────────────────────────────────┐
│ 第 1 层：参考区间判定（M13-05 提供）                                        │
│   field_code: GLU  value: 12.8  ref: 3.9~6.1                              │
│   → flag = HIGH                                                           │
├────────────────────────────────────────────────────────────────────────────┤
│ 第 2 层：术前准备规则判定（M06-02 配置）                                    │
│   rule: PREP.GLUCOSE.BLOCK  阈值 >11.1                                    │
│   → 12.8 > 11.1  →  verdict = BLOCK                                       │
├────────────────────────────────────────────────────────────────────────────┤
│ 第 3 层：临床决策（主刀/麻醉医生）                                          │
│   医生看到 BLOCK → 选择：干预后复查 / 改期 / 转内科                         │
│   → disposition = RECHECK | DEFER | REFER                                 │
└────────────────────────────────────────────────────────────────────────────┘
```

**为什么分三层**：

- 第 1 层是**客观事实**（这个值超出正常范围了）
- 第 2 层是**本院标准**（超出多少就不能做日间手术）
- 第 3 层是**临床判断**（这个患者怎么办）

如果三层合一，系统会试图"替医生做决定"。而实际上"血糖 12.8 能不能做白内障"取决于患者整体状况、是否急诊、有无感染征象——这些系统无法判断。

### 3.3 就绪判定模型

#### 3.3.1 判定算法

```python
def judge_readiness(apply, items, now):
    """准备就绪判定。

    返回值：
      READY      全部必做项完成且无未处置异常
      NOT_READY  存在阻塞项
      EXPIRED    申请单状态不允许（已取消/已改期/已过手术日）
    """
    # ① 申请单状态
    if apply.status not in ("SCHEDULED", "PREPARED"):
        return "EXPIRED", {"reason": "申请单状态为 %s" % apply.status}

    # ② 手术时间窗
    if now > apply.surgery_start_at:
        return "EXPIRED", {"reason": "已过手术开始时间"}

    # ③ 必做项
    blockers = []
    for item in items:
        if not item.is_required:
            continue
        if item.status == "DONE":
            continue
        if item.status == "NA":
            continue
        if item.status == "FAILED":
            # 已处置的异常不算阻塞
            if item.disposition:
                continue
            blockers.append(item)
            continue
        # PENDING
        blockers.append(item)

    if blockers:
        return "NOT_READY", {"blockers": blockers}

    # ④ 时间窗提醒（不阻塞，但提示）
    warnings = []
    for item in items:
        if item.status != "DONE" or item.timing_offset_minutes is None:
            continue
        deadline = apply.surgery_start_at + timedelta(
            minutes=item.timing_offset_minutes)
        if item.done_at and item.done_at > deadline:
            warnings.append(item)

    return "READY", {"warnings": warnings}
```

**关键设计点：**

1. **`EXPIRED` 与 `NOT_READY` 必须分开**。`NOT_READY` 是"还能补救"（散瞳没做 → 现在滴，等 20 分钟）；`EXPIRED` 是"补救也没用"（已过手术时间）。合并成一个"不就绪"，M06-04 无法判断是"再等等"还是"取消"。

2. **`FAILED` + `disposition` 视为通过**。凝血异常做了干预（调整华法林剂量）后，虽然结果仍异常但已闭环。这是**临床决策的结果，系统必须尊重**。

3. **超时完成只告警不阻塞**。散瞳要求术前 60 分钟，实际术前 30 分钟才滴 —— 瞳孔可能还没散够，但**这是手术室护士能现场判断的**（看瞳孔大小），不该由系统的时序规则来决定手术做不做。

#### 3.3.2 判定时机

| 时机 | 触发者 | 用途 |
|---|---|---|
| 术日 T-0 07:00 | 定时任务 | 生成"今日未就绪清单"推护士长 |
| 术日 每小时 | 定时任务 | 刷新就绪状态看板 |
| M06-04 请求时 | 实时 | 放行判定（不缓存） |
| 任意准备项变更 | 事件 | 立即重判，刷新缓存 |

**M06-04 请求时必须实时判定，不能用缓存**。理由：放行决定的是"人要不要进手术间"，用 30 秒前的缓存判断可能错过一个刚发生的变更（如护士刚发现患者偷喝了水）。判定本身 ≤50ms，没有理由缓存。

### 3.4 时间轴与提醒模型

#### 3.4.1 提醒矩阵

| 时点 | 计算方式 | 提醒对象 | 提醒内容 | 通道 |
|---|---|---|---|---|
| T-7 天 | `surgery_start_at - 7d` | 门诊医生 | 该开术前检查检验单了 | 站内信 |
| T-3 天 | `surgery_start_at - 3d` | 门诊医生 | 检查检验结果已回报，请查看异常 | 站内信 |
| T-2 天 | `surgery_start_at - 2d` | 麻醉医生 | 待访视 | 站内信 + 待办 |
| T-1 天 16:00 | 固定时刻 | 日间病房护士 | 明日手术 X 台，需电话确认禁食与来院时间 | 站内信 + 短信 |
| T-1 天 | `surgery_start_at - 1d` | 患者（经 M03-05） | 明早禁食、来院时间、携带物品 | 短信 |
| T-0 06:00 | 固定时刻 | 日间病房护士 | 今日手术 X 台，准备项完成度 Y% | 站内信 + 待办 |
| 术前 2h | `-120min` | 护士 | 该做禁食最终确认了 | 站内信 |
| 术前 90min | `-90min` | 护士 | 该通知患者到院了 | 站内信 |
| 术前 60min | `-60min` | 护士 | 该散瞳了 | 站内信 + 看板闪烁 |
| 术前 30min | `-30min` | 护士 | 该滴抗菌药 + 术眼标记 | 站内信 + 看板闪烁 |
| 术前 15min | `-15min` | 护士长 + 手术室护士 | 就绪判定结果 | 站内信 + 大屏 |

**为什么 T-1 天 16:00 有个固定时刻的提醒**：这是护士下班的边界。16:00 还没打电话确认的，当天就确认不了了，必须赶在下班前完成。用相对时间（`surgery_start_at - 1d`）会落在不同时刻（有的 10:00 有的 14:00），与护士班次对不上。

**为什么术前提醒越来越密**：术前 2h 漏做还有 2 小时补救；术前 15min 漏做就没有补救空间。提醒密度必须与剩余补救时间成反比。

#### 3.4.2 提醒去重与升级

| 情况 | 处理 |
|---|---|
| 同一项已提醒 1 次未处理 | 30 分钟后重复提醒 |
| 同一项已提醒 3 次未处理 | 升级到护士长 |
| 同一项已提醒 5 次未处理 | 升级到医务科 + 记入工作质量 |
| 项已完成 | 取消未发送的提醒 |

**去重实现**：Redis `m06:prep:remind:{item_id}` 存提醒次数（TTL 24h），每次发送前 `INCR`，按次数决定通知层级。

### 3.5 异常处置模型

#### 3.5.1 四种处置动作

| 处置码 | 中文 | 含义 | 后续动作 | 对就绪的影响 |
|---|---|---|---|---|
| `RESOLVED` | 已干预 | 采取措施后继续 | 记录干预内容，项置 DONE | ✅ 算完成 |
| `RECHECK` | 需复查 | 生成复查项，等新结果 | 新建一条复查清单项 | ⏳ 复查项 PENDING 时阻塞 |
| `DEFER` | 延迟手术 | 当前手术做不了 | 发 `m06.prepare.blocked` 给 M06-01 | ❌ 阻塞，待改期 |
| `REFER` | 转诊 | 需专科治疗 | 发 `m06.prepare.blocked` + 建议转诊 | ❌ 阻塞，待取消 |

**为什么处置动作要单独建模而不是随便写个备注**：因为**每种处置对就绪判定的影响不同**。`RESOLVED` 让项通过，`DEFER` 让项继续阻塞。如果只有备注文本，系统无法判断。

#### 3.5.2 处置的权限与时限

| 处置动作 | 谁可以做 | 时限 | 理由 |
|---|---|---|---|
| `RESOLVED` | 主刀 / 麻醉医生 | 术日前 | 医疗决策 |
| `RECHECK` | 主刀 / 麻醉医生 / 门诊医生 | 术日前 | 医疗决策 |
| `DEFER` | 主刀 / 麻醉医生 | 术日前 | 医疗决策 |
| `REFER` | 主刀 / 医务科 | 任意时刻 | 需协调转诊 |

**护士不能做处置决策**。护士可以记录"测出血压 190/110"，但"这个血压能不能做手术"是医生的判断。这是**执业范围**问题，不是权限设置问题。

### 3.6 术前访视模型

#### 3.6.1 麻醉术前访视

| 字段 | 类型 | 说明 |
|---|---|---|
| 访视医生 | 麻醉医生 ID | 必须有麻醉资质 |
| ASA 分级 | `ASA_I`~`ASA_VI` | 核心评估结果 |
| 气道评估 | Mallampati I~IV | 影响插管难度 |
| 禁食评估 | 达标/不达标 | 与 T-0 确认相互印证 |
| 过敏史核对 | 文本 | 尤其是麻醉药过敏 |
| 合并症评估 | 结构化 | 高血压/糖尿病/冠心病等 |
| 用药评估 | 结构化 | 抗凝药、降压药、降糖药 |
| 麻醉方式确认 | 与 M01-07 一致 | 与手术项目的要求核对 |
| **麻醉结论** | `FEASIBLE`/`ADJUST`/`INFEASIBLE` | 关键结论 |
| 结论说明 | 文本 | `ADJUST`/`INFEASIBLE` 必填 |

**麻醉结论三态：**

| 结论 | 含义 | 后续 |
|---|---|---|
| `FEASIBLE` | 可以按原方案麻醉 | 继续准备 |
| `ADJUST` | 需调整方案（如局麻改全麻，或调整用药） | 记录调整内容，继续准备 |
| `INFEASIBLE` | 不能麻醉 | 阻断，触发改期或转诊 |

**为什么 `ADJUST` 单独一档**：真实场景里最常见的不是"能做/不能做"，而是"要换个方式做"。比如患者血压 170/100，局麻可以做，全麻风险高 —— 此时应"改成局麻"。如果只有两态，医生只能选 `FEASIBLE`（然后备注改局麻，但系统不知道），或选 `INFEASIBLE`（过度保守，白白耽误患者）。

#### 3.6.2 主刀术前访视

| 字段 | 类型 | 说明 |
|---|---|---|
| 访视医生 | 主刀 ID | 必须与申请单主刀一致 |
| 术眼确认 | OD/OS | 与申请单核对，不一致则阻断 |
| 手术方式确认 | 与申请单一致 | 变更需重新走 M06-01 |
| 术式沟通 | 结构化 | 告知手术步骤、预期效果 |
| 风险告知 | 结构化 | 告知并发症、转住院可能 |
| 患者意愿 | 确认/存疑/拒绝 | 存疑需进一步沟通 |
| 结论 | `FEASIBLE`/`ADJUST`/`INFEASIBLE` | 同麻醉 |

**术眼确认是主刀访视的必填项**。理由：术眼错误是眼科最常见也最严重的差错之一（做错眼 = 不可逆伤害）。访视时让主刀再确认一次，配合 M06-04 的 Time-Out，形成双重保险。

### 3.7 准备进度模型

**完成度** = 已完成项 ÷ 必做项

```
完成度 = COUNT(status IN ('DONE','NA') AND is_required) / COUNT(is_required)
```

**但完成度不能只看数字**，必须配合"关键项"标识：

| 关键项 | 说明 | 缺失后果 |
|---|---|---|
| `FASTING` | 禁食确认 | 全麻误吸，可致死 |
| `CONSENT` | 知情同意 | 无法举证，医疗纠纷必败 |
| `EYE_MARK` | 术眼标记 | 做错眼 |
| `EXAM_IOL_MASTER` | 白内障必做 | 无法定晶体度数 |

**关键项未完成时，完成度即使 90% 也必须显示红色告警**。理由：护士长看到"90% 完成"会认为进展良好，看到"90% 完成 + 禁食未确认"才知道问题严重。

| V-06 | 已完成项 30 分钟内可撤销（仅本人） | 防误点 |

**为什么检查检验类项不允许人工置 DONE：**

这是本子模块最重要的一条约束。如果允许护士手工勾"血常规已完成"，就等于允许在没看到结果的情况下标记完成。系统会认为准备就绪、放行到手术间，而实际上凝血结果可能是 INR 2.8。

允许人工勾选 = 允许跳过结果判读 = 允许带缺陷上台。

**但存在合理的例外场景**：外院做的检查（患者在外院刚做过血常规）。这时用"手工登记"路径：上传外院报告 → 主刀确认 → 才置 DONE，且必须留痕 `done_source='MANUAL_EXTERNAL'` + `attachment_id`。

**为什么禁食要记录"最后饮水时间"而不只是"最后进食时间"：**

全麻禁食规则是**固体 8 小时 + 清饮 2 小时**两条。只记"最后进食"会漏掉"患者早上 7 点喝了口水"这种情况——此时固体已经 12 小时达标，但清饮只 3 小时，勉强够；如果只 1 小时就不够。**两个字段是两个判据。**

**字段说明：**

| 区域 | 字段 | 说明 |
|---|---|---|
| 判定结果 | 阻断项 | 状态非 DONE/NA 且非已处置的 FAILED |
| 判定结果 | 已完成项 | 状态为 DONE/NA |
| 判定结果 | 警告项 | 有 is_abnormal 但已处置 |
| 放行 | 放行选项 | 允许/延迟/取消 |
| 放行 | 护士长签名 | 当前登录用户 |

**交互说明：**

| 操作 | 触发 | 结果 |
|---|---|---|
| 立即确认 / 立即标记 | 点击 | 跳 P02 定位到该项 |
| 重新判定 | 点击 | 调判定接口刷新结果 |
| 确认放行 | 点击 | 仅 READY 可用，置 `released_at` |
| 通知手术室延迟 | 点击 | 发消息到 M06-03，记录延迟原因 |
| 自动刷新 | 15 秒 | 术临近时加快刷新 |

**校验规则：**

| 编号 | 规则 | 说明 |
|---|---|---|
| V-01 | 只有 `READY` 才能放行 | `"0602051"` |
| V-02 | 放行人必须是护士长或以上 | `"0602052"` |
| V-03 | 延迟必须填原因 ≥10 字 | `"0602053"` |
| V-04 | 取消必须走 M06-01 取消流程 | `"0602054"` |
| V-05 | 放行后不可撤销（需重新走判定） | 留痕 |

**为什么放行需要护士长签名而不是系统自动放行：**

系统判定 `READY` 只能说明"清单上该做的都做了"。但真实世界里有清单覆盖不到的情况：患者脸色不对、家属说昨晚没睡好、走廊里发现患者在咳嗽。

**护士长是那个"最后看一眼"的人**。她签字放行，意味着"我看过这个患者，我确认可以"——这是系统无法替代的人工判断。同时，签名也是责任落点：万一出了问题，"是系统自动放行的"不是一个可以接受的解释。

**为什么改进建议用规则生成而不是 AI：**

- 规则生成的可追溯："术眼标记漏项 4.4% 且集中在王护士"这句话，护士长能点进去看到 18 条原始记录，能反驳
- AI 生成的可能流畅但空洞（"建议加强培训"）甚至错误（把 7 例说成 17 例）
- **管理决策的依据必须可验证**，不可验证的建议只会消耗管理者的注意力

```python
    @classmethod
    def _check_fasting(cls, row, body, apply_id):
        """禁食达标校验。"""
        detail = body.detail or {}
        surgery_at = row_apply_time = None
        # 手术时间来自申请单，由调用方注入；此处从 row 上取缓存值
        surgery_at = getattr(row, "_surgery_start_at", None) or now_local()

        solid_hours = liquid_hours = 0.0
        last_solid = detail.get("last_solid_intake_at")
        last_liquid = detail.get("last_liquid_intake_at")
        if last_solid:
            solid_hours = round(
                (surgery_at - last_solid).total_seconds() / 3600, 2)
        if last_liquid:
            liquid_hours = round(
                (surgery_at - last_liquid).total_seconds() / 3600, 2)

        rule = cls._fasting_rule(row.item_desc)
        required_solid = rule["solid_hours"]
        required_liquid = rule["liquid_hours"]

        return {
            "solid_hours": solid_hours,
            "liquid_hours": liquid_hours,
            "required_solid_hours": required_solid,
            "required_liquid_hours": required_liquid,
            "solid_pass": solid_hours >= required_solid,
            "liquid_pass": liquid_hours >= required_liquid,
        }

                        func.to_timestamp(
                            func.extract(
                                "epoch",

                                    text(":start"), text("timestamp")))
                        )
                    )
                ),
            )
            .execution_options(synchronize_session=False)
        )
        # 实际重算在 Python 层完成（避免复杂 SQL），逐行更新

            select(M06PrepareItem).where(
                M06PrepareItem.apply_id == apply_id,
                M06PrepareItem.is_deleted == False,

                continue
            r.planned_at = new_start + timedelta(
                minutes=r.timing_offset_minutes)
            updated += 1

        }

    @classmethod
    async def internal_judge(cls, db: AsyncSession, apply_id: int):
        """核心判定算法（P95 ≤ 50ms）。"""
        started = now_local()

        apply_row = await db.get(M06DaySurgery, apply_id)
        if not apply_row:
            raise BizException("0602001", "申请单不存在")

        if apply_row.status not in ("SCHEDULED", "PREPARED"):
            return {
                "readiness": "EXPIRED",
                "reason": "申请单状态为 %s" % apply_row.status,
                "blocker_count": 0,
                "_blocker_rows": [],
                "_warning_rows": [],
                "summary": {},
            }

        now = now_local()
        if apply_row.surgery_start_at and now > apply_row.surgery_start_at:
            return {
                "readiness": "EXPIRED",
                "reason": "已过手术开始时间",
                "blocker_count": 0,
                "_blocker_rows": [],
                "_warning_rows": [],
                "summary": {},
            }

        items = (await db.execute(
            select(M06PrepareItem).where(
                M06PrepareItem.apply_id == apply_id,
                M06PrepareItem.is_deleted == False,
            )
        )).scalars().all()

        blocker_rows = []
        warning_rows = []
        pending_count = failed_count = 0
        na_count = done_count = 0

        for item in items:
            if not item.is_required:
                continue
            if item.status == "DONE":
                done_count += 1
                if item.is_abnormal:
                    warning_rows.append(item)
                continue
            if item.status == "NA":
                na_count += 1
                continue
            if item.status == "FAILED":
                failed_count += 1
                # 已处置的异常视为闭环
                if item.disposition:
                    warning_rows.append(item)
                    continue
                blocker_rows.append(item)
                continue
            # PENDING
            pending_count += 1
            blocker_rows.append(item)

        readiness = "READY" if not blocker_rows else "NOT_READY"
        elapsed = int(
            (now_local() - started).total_seconds() * 1000)

        return {
            "readiness": readiness,
            "readiness_text": READINESS_TEXT[readiness],
            "blocker_count": len(blocker_rows),
            "warning_count": len(warning_rows),
            "elapsed_ms": elapsed,
            "summary": {
                "required_count": done_count + na_count + failed_count
                + pending_count,
                "done_count": done_count,
                "na_count": na_count,
                "failed_count": failed_count,
                "pending_count": pending_count,
            },
            "_blocker_rows": blocker_rows,
            "_warning_rows": warning_rows,
        }

    @classmethod
    async def today(cls, db, target_date, dept_id):
        """今日手术就绪列表。"""
        stmt = select(M06DaySurgery).where(
            M06DaySurgery.scheduled_date == (target_date or date.today()),
            M06DaySurgery.status.in_(
                ("SCHEDULED", "PREPARED")),
            M06DaySurgery.is_deleted == False,

class ResultSyncService:
    """检查检验结果同步与自动关联服务。"""

    @classmethod
    async def on_result_ready(cls, db, body):
        """结果就绪回调：自动关联准备项。"""
        apply_id = body.get("apply_id")
        item_code = body.get("item_code")
        result_type = body.get("result_type")
        ref_id = body.get("ref_id")

        rows = (await db.execute(
            select(M06PrepareItem).where(
                M06PrepareItem.apply_id == apply_id,
                M06PrepareItem.is_deleted == False,
            )
        )).scalars().all()

        matched = None
        for r in rows:
            if r.item_code == item_code:
                matched = r
                break
            if r.item_code == "EXAM_IOL_MASTER" and item_code in (
                "EXAM_AXIAL_LENGTH", "EXAM_KERATOMETRY"):
                matched = r
                break
            if r.item_code == "LAB_CBC" and item_code in (
                "LAB_HB", "LAB_WBC", "LAB_PLT"):
                matched = r
                break
            if r.item_code == "LAB_COAG" and item_code in (
                "LAB_INR", "LAB_PT", "LAB_APTT"):
                matched = r
                break

        if not matched:
            return {"matched": False, "reason": "无对应准备项"}

        matched.status = "DONE"
        matched.done_at = now_local()
        matched.done_source = "AUTO"
        matched.auto_ref_type = result_type or "LAB"
        matched.auto_ref_id = ref_id
        matched.auto_ref_no = body.get("ref_no")
        matched.result_summary = body.get("result_summary")

        is_abnormal, desc = cls._judge_abnormal(body)
        matched.is_abnormal = is_abnormal
        matched.abnormal_desc = desc
        if is_abnormal:
            matched.status = "FAILED"

        await db.flush()
        await redis_client.delete("m06:prep:readiness:%s" % apply_id)
        logger.info(
            "结果自动关联 apply_id=%s code=%s abnormal=%s",
            apply_id, item_code, is_abnormal)
        return {"matched": True, "item_id": matched.id,
                "is_abnormal": is_abnormal}

    @classmethod
    def _judge_abnormal(cls, body):
        """异常判定：参考区间 + 术前规则阈值。"""
        value = body.get("numeric_value")
        if value is None:
            return False, None
        value = Decimal(str(value))

        rule = PREP_THRESHOLDS.get(body.get("item_code"))
        if not rule:
            return False, None

        if rule.get("block_gt") is not None and value > rule["block_gt"]:
            return True, "超出阻断阈值 %s" % rule["block_gt"]
        if rule.get("block_lt") is not None and value < rule["block_lt"]:
            return True, "低于阻断阈值 %s" % rule["block_lt"]
        if rule.get("warn_gt") is not None and value > rule["warn_gt"]:
            return True, "超出警戒阈值 %s" % rule["warn_gt"]
        if rule.get("warn_lt") is not None and value < rule["warn_lt"]:
            return True, "低于警戒阈值 %s" % rule["warn_lt"]
        return False, None


class DisposeService:
    """异常处置服务。"""

    ALLOWED_ROLES = {
        "SURGEON", "ANESTHETIST", "DOCTOR", "MEDICAL_AFFAIRS",
    }

    @classmethod
    async def dispose(cls, db, apply_id, abnormal_id, body, user):
        """异常处置。"""
        if user.role_code not in cls.ALLOWED_ROLES:
            raise BizException("0602023", "无权处置异常")

        row = (await db.execute(
            select(M06PrepareItem)
            .where(
                M06PrepareItem.id == abnormal_id,
                M06PrepareItem.apply_id == apply_id,
                M06PrepareItem.is_deleted == False,
            )
            .with_for_update()
        )).scalar_one_or_none()
        if not row:
            raise BizException("0602002", "准备项不存在")
        if row.disposition:
            raise BizException("0602025", "异常已处置不可重复处置")

        if not body.disposition_desc or \
                len(body.disposition_desc.strip()) < 10:
            raise BizException("0602022", "处置说明不足 10 字")

        if body.disposition == "RECHECK":
            if not body.recheck_item_code or not body.recheck_deadline:
                raise BizException(
                    "0602024", "复查必须指定项目与时限")
        if body.disposition == "REFER":
            if not body.refer_dept_id:
                raise BizException("0602026", "转诊必须填写建议科室")

        row.disposition = body.disposition
        row.disposition_desc = body.disposition_desc
        row.disposition_by = user.employee_id
        row.disposition_by_name = user.employee_name
        row.disposition_at = now_local()

        if body.disposition == "RESOLVED":
            row.status = "DONE"
        elif body.disposition == "RECHECK":
            new_item = M06PrepareItem(
                apply_id=apply_id,
                ds_no=row.ds_no,
                seq_no=row.seq_no + 100,
                item_type="LAB" if row.item_type == "LAB" else "EXAM",
                item_code=body.recheck_item_code,
                item_name="复查：" + row.item_name,
                is_required=True,
                planned_at=body.recheck_deadline,
                status="PENDING",
                source_type="RECHECK",
            )
            db.add(new_item)

        await db.flush()

        if body.disposition in ("DEFER", "REFER"):
            # 通知 M06-01 处理取消/改期
            logger.warning(
                "异常触发阻塞 apply_id=%s disposition=%s",
                apply_id, body.disposition)

        judge = await ReadinessService.internal_judge(db, apply_id)
        return {
            "abnormal_id": abnormal_id,
            "item_code": row.item_code,
            "disposition": body.disposition,
            "item_status": row.status,
            "readiness": judge["readiness"],
            "blocker_count": judge["blocker_count"],
        }

    @classmethod
    async def list_abnormal(
        cls, db, status, dept_id, date_from, date_to, page, page_size, user,
    ):
        """异常列表。"""
        stmt = select(M06PrepareItem).where(
            M06PrepareItem.is_abnormal == True,

            stmt = stmt.where(M06PrepareItem.disposition.is_(None))

            stmt = stmt.where(M06PrepareItem.disposition.isnot(None))

        total = (await db.execute(
            select(func.count()).select_from(stmt.subquery())
        )).scalar() or 0

        rows = (await db.execute(
            stmt.order_by(M06PrepareItem.created_at.desc())
            .offset((page - 1) * page_size)
            .limit(page_size)
        )).scalars().all()

        items = [{

            "disposition_by_name": r.disposition_by_name,

        }

class OrderService:
    """术前检查检验医嘱生成服务。"""

    @classmethod
    async def create(cls, db, apply_id, body, user):
        """调 M07-03 生成医嘱。"""
        apply_row = await db.get(M06DaySurgery, apply_id)
        if not apply_row:
            raise BizException("0602001", "申请单不存在")

        created = []
        failed = []

        for item_id in body.item_ids:
            item = (await db.execute(
                select(M06PrepareItem).where(
                    M06PrepareItem.id == item_id,
                    M06PrepareItem.apply_id == apply_id,
                    M06PrepareItem.is_deleted == False,
                )
            )).scalar_one_or_none()
            if not item:
                failed.append({
                    "item_id": item_id,
                    "reason": "准备项不存在",
                    "error_code": "0602002",
                })
                continue
            if item.order_id:
                failed.append({
                    "item_id": item_id,
                    "item_code": item.item_code,
                    "reason": "该准备项已生成医嘱",
                    "error_code": "0602009",
                })
                continue

            order_type = "EXAM" if item.item_type == "EXAM" else "LAB"
            try:
                resp = await M07OrderClient.create_order(
                    encounter_id=apply_row.encounter_id,
                    patient_id=apply_row.patient_id,
                    order_type=order_type,
                    item_code=item.item_code,
                    eye_side=(
                        apply_row.eye_side
                        if order_type == "EXAM" else None),
                    idempotency_key="%s-%s" % (body.idempotency_key, item_id),
                    doctor_id=apply_row.surgeon_id,
                    priority=body.priority,
                )
            except Exception as exc:
                logger.error("医嘱生成失败 apply_id=%s code=%s err=%s",
                             apply_id, item.item_code, exc)
                failed.append({
                    "item_id": item_id,
                    "item_code": item.item_code,
                    "reason": "医嘱生成失败：%s" % exc,
                    "error_code": "0602008",
                })
                continue

            item.order_id = resp["order_id"]
            item.order_no = resp["order_no"]
            created.append({
                "item_id": item_id,
                "order_id": resp["order_id"],
                "order_no": resp["order_no"],
                "order_type": order_type,
                "item_code": item.item_code,
                "is_idempotent": resp.get("is_idempotent", False),
            })

        await db.flush()
        return {
            "apply_id": apply_id,
            "created_orders": created,
            "failed": failed,
        }


class BoardService:
    """准备看板服务。"""

    @classmethod
    async def build(cls, db, target_date, dept_id, user):
        """构建看板数据。"""
        cache_key = "m06:prep:board:%s:%s" % (
            target_date, dept_id or 0)
        cached = await redis_client.get_json(cache_key)
        if cached:
            return cached

        stmt = select(M06DaySurgery).where(
            M06DaySurgery.scheduled_date == target_date,
            M06DaySurgery.is_deleted == False,
        )
        if dept_id:
            stmt = stmt.where(M06DaySurgery.dept_id == dept_id)
        stmt = stmt.order_by(M06DaySurgery.surgery_start_at)
        rows = (await db.execute(stmt)).scalars().all()

        surgery_list = []
        counters = {"ready": 0, "preparing": 0, "blocked": 0,
                    "cancelled": 0}

        for r in rows:
            if r.status == "CANCELLED":
                counters["cancelled"] += 1
                continue
            judge = await ReadinessService.internal_judge(db, r.id)
            if judge["readiness"] == "READY":
                counters["ready"] += 1
            elif judge["blocker_count"] > 0:
                counters["blocked"] += 1
            else:
                counters["preparing"] += 1
            surgery_list.append({
                "apply_id": r.id,
                "ds_no": r.ds_no,
                "surgery_time": r.surgery_start_at,
                "patient_name": r.patient_name,
                "gender": r.gender,
                "age": r.age,
                "operation_name": r.operation_name,
                "eye_side": r.eye_side,
                "eye_side_text": EYE_TEXT.get(r.eye_side, ""),
                "readiness": judge["readiness"],
                "blocker_count": judge["blocker_count"],
                "summary": judge["summary"],
            })

        total = len(surgery_list) + counters["cancelled"]
        data = {
            "date": str(target_date),
            "summary": {
                "total": total,
                "ready": counters["ready"],
                "preparing": counters["preparing"],
                "blocked": counters["blocked"],
                "cancelled": counters["cancelled"],
                "readiness_rate": (
                    round(counters["ready"] / total, 3) if total else 0.0),
            },
            "surgery_list": surgery_list,
        }
        await redis_client.set_json(cache_key, data, ex=30)
        return data

    async def list(cls, db, user):
        """待处理提醒。"""
        now = now_local()
        rows = (await db.execute(
            select(M06PrepareItem)
            .where(
                M06PrepareItem.status == "PENDING",
                M06PrepareItem.is_required == True,
                M06PrepareItem.is_deleted == False,
                M06PrepareItem.planned_at.isnot(None),
                M06PrepareItem.planned_at <= now,
            )
            .order_by(M06PrepareItem.planned_at)
            .limit(50)
        )).scalars().all()

        items = []
        for r in rows:
            key = "m06:prep:remind:%s" % r.id
            count = await redis_client.get_int(key) or 0
            items.append({
                "id": r.id,
                "apply_id": r.apply_id,
                "item_code": r.item_code,
                "item_name": r.item_name,
                "planned_at": r.planned_at,
                "overdue_minutes": int(
                    (now - r.planned_at).total_seconds() // 60),
                "remind_level": min(count + 1, 5),
            })
        return {"items": items, "total": len(items)}

    @classmethod
    async def ack(cls, db, remind_id, body, user):
        """确认提醒。"""
        await redis_client.set_int(
            "m06:prep:remind:%s" % remind_id, 0, ex=86400)
        await db.execute(
            update(M06PrepareRemind)
            .where(M06PrepareRemind.id == remind_id)
            .values(acked_at=now_local(), acked_by=user.employee_id)
        )
        return {"remind_id": remind_id, "acked": True}

    @classmethod
    async def batch_urge(cls, db, body, user):
        """批量催办。"""
        sent = 0
        for apply_id in body.apply_ids:
            rows = (await db.execute(
                select(M06PrepareItem).where(
                    M06PrepareItem.apply_id == apply_id,
                    M06PrepareItem.status == "PENDING",
                    M06PrepareItem.is_deleted == False,
                )
            )).scalars().all()
            if not rows:
                continue
            names = "、".join(r.item_name for r in rows[:5])
            await M03MessageClient.send(
                receiver_id=body.receiver_id,
                title="术前准备催办",
                content="申请单 %s 还有 %s 项准备未完成：%s" % (
                    apply_id, len(rows), names),
                channel="INBOX",
            )
            sent += 1
        return {"urged_count": sent}


class StatisticsService:
    """统计服务。"""

    @classmethod
    async def quality(cls, db, date_from, date_to, dept_id):
        """准备质量统计。"""
        span = (date_to - date_from).days
        if span > 366:
            raise BizException("0602061", "统计周期超过 366 天")

        rows = (await db.execute(
            select(
                func.count(M06DaySurgery.id).label("total"),
                func.sum(
                    func.cast(M06DaySurgery.prepared_at.isnot(None),
                              "int")
                ).label("prepared"),
            ).where(
                M06DaySurgery.scheduled_date.between(date_from, date_to),
                M06DaySurgery.is_deleted == False,
            )
        )).one()

        total = rows.total or 0
        prepared = rows.prepared or 0

        item_rows = (await db.execute(
            select(
                M06PrepareItem.done_source,
                func.count(M06PrepareItem.id),
            )
            .where(
                M06PrepareItem.item_type.in_(("EXAM", "LAB")),
                M06PrepareItem.is_deleted == False,
            )
            .group_by(M06PrepareItem.done_source)
        )).all()

        auto_count = sum(c for s, c in item_rows if s == "AUTO")
        total_item = sum(c for s, c in item_rows)
        auto_rate = round(auto_count / total_item, 3) if total_item else 0.0

        return {
            "date_from": str(date_from),
            "date_to": str(date_to),
            "surgery_total": total,
            "prepared_count": prepared,
            "prepared_rate": round(prepared / total, 3) if total else 0.0,
            "auto_link_count": auto_count,
            "auto_link_total": total_item,
            "auto_link_rate": auto_rate,
        }
```

### 7.3 APScheduler 任务

| 任务 | Cron | 说明 |
|---|---|---|
| `job_m06_prep_timeline_remind` | `*/5 * * * *` | 每 5 分钟扫描到点未执行的准备项，发提醒 |
| `job_m06_prep_remind_escalate` | `*/30 * * * *` | 提醒升级（3 次升级护士长，5 次升级医务科） |
| `job_m06_prep_board_refresh` | `*/1 * * * *` | 刷新看板缓存 |
| `job_m06_prep_result_poll` | `0 * * * *` | 每小时兜底轮询（事件丢失补偿） |
| `job_m06_prep_daily_ready` | `0 7 * * *` | 术日 07:00 生成未就绪清单推护士长 |
| `job_m06_prep_tomorrow_todo` | `0 16 * * *` | T-1 天 16:00 推明日待办给责任人 |
| `job_m06_prep_stat_daily` | `30 1 * * *` | 每日 01:30 统计落库 |
| `job_m06_prep_clean_expired` | `30 3 * * *` | 清理过期缓存与已完成申请单的锁 |

**为什么时间轴提醒用 5 分钟粒度而不是 1 分钟：**

术前准备的时序精度是"分钟级"到"小时级"（禁食按小时算、散瞳按分钟算），5 分钟误差对决策无影响。1 分钟扫描会让每次扫描都要查全部进行中的申请单（日 60 台 × 10 项 = 600 项），一天 1440 次 × 600 = 86 万次查询，而 5 分钟只需 17 万次。

**为什么 T-1 天 16:00 的提醒用固定时刻：**

与 3.4.1 节一致 —— 16:00 是护士下班边界，这个提醒必须与班次对齐而不是与手术时间对齐。

**为什么兜底轮询用 1 小时：**

事件驱动已经覆盖了绝大部分场景（延迟 < 10 秒）。轮询只处理"事件彻底丢失"这种极罕见情况，1 小时延迟可接受，且查询量（每天 24 次 × 600 项 = 1.4 万次）远小于 5 分钟粒度。

## 11. 异常处理与日志

### 11.1 异常分类

| 类别 | 场景 | 处理策略 | HTTP 状态 |
|---|---|---|---|
| **参数校验** | 入参格式错误、必填缺失 | 框架层统一拦截，返回 `"40001"` | 422 |

| **系统异常** | 数据库连接失败、Redis 不可达 | 记录日志 + 返回 `"50000"` | 500 |
| **并发冲突** | 同一项并发操作 | `SELECT FOR UPDATE` 串行化 | 200（排队后返回） |

## 12. 验收标准

### 12.1 功能验收

| 编号 | 验收项 | 验收方法 | 通过标准 |
|---|---|---|---|
| AC-01 | 清单接收与时间补算 | 创建申请单并排程 | 各准备项 `planned_at` = `surgery_start_at + offset` |
| AC-02 | 排程变更重算时间 | 修改手术时间 | 所有项 `planned_at` 同步变更 |
| AC-03 | 人工完成准备项 | 护士勾选 | 状态置 DONE，`done_source='MANUAL'`，记录执行人与时间 |
| AC-04 | 禁食达标校验 | 提交禁食详情（达标） | 完成成功，返回禁食判定明细 |
| AC-05 | 禁食不达标阻断 | 提交禁食详情（固体 5h） | 返回 `"0602005"`，项置 FAILED |
| AC-06 | 检查检验不可人工完成 | 对 EXAM 项点完成 | 返回 `"0602004"` |
| AC-07 | 标记不适用 | 填 ≥5 字原因 | 状态置 NA |
| AC-08 | 原因过短拦截 | 填 3 字原因 | 返回 `"0602012"` |
| AC-09 | 撤销完成 | 30 分钟内本人撤销 | 状态回 PENDING |
| AC-10 | 撤销超时拦截 | 31 分钟后撤销 | 返回 `"0602006"` |
| AC-11 | 他人撤销拦截 | 非本人撤销 | 返回 `"0602007"` |
| AC-12 | 外院结果登记 | 上传附件并提交 | 状态置 DONE，`done_source='MANUAL_EXTERNAL'` |
| AC-13 | 外院结果无附件拦截 | 不传附件提交 | 返回 `"0602010"` |
| AC-14 | 生成术前医嘱 | 选中 3 项生成 | 返回 3 个 order_id，项写入 order_no |
| AC-15 | 医嘱重复生成拦截 | 对已开单项再生成 | 返回 `"0602009"` |
| AC-16 | 检查结果自动关联 | M12 报告发布 | 对应项自动 DONE，`done_source='AUTO'` |
| AC-17 | 检验结果自动关联 | M13 结果发布 | 对应项自动 DONE |
| AC-18 | 结果异常自动标 FAILED | 血糖 12.8 到达 | 项置 FAILED，`is_abnormal=TRUE` |
| AC-19 | 异常处置已干预 | 医生选 RESOLVED | 项置 DONE，`disposition='RESOLVED'` |
