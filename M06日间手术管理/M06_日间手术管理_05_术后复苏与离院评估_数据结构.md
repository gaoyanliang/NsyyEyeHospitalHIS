**设计说明**

1. **`m06_recovery` 是 M06-05 唯一主表**：
   - 一个台次（`schedule_id`）对应一条留观记录，用 `uk_m06_rec_schedule` 保证唯一。
   - 从入复苏室到离院，所有阶段信息都在主表上（`phase`、时间戳、时长）。

2. **生命体征、眼科专项、评分是三张独立的时序表**：
   - `m06_recovery_vital` 记录生命体征（心率、血压等）
   - `m06_recovery_eye` 记录眼科专项（眼压、视力、前房等）
   - `m06_recovery_score` 记录评分（Aldrete / PADSS）
   - **为什么不合并成一张"观察记录表"**：三者的字段完全不同（体征有 5 个数值，眼科有 4 个枚举 + 2 个数值，评分有 5~10 个 0-2 分项），合并后单表字段超过 40 个且大量 NULL；且三者的记录频次不同（体征 15 分钟、眼科 30 分钟、评分按需）。

3. **`m06_discharge` 与 `m06_discharge_instruction` 分开**：
   - 评估是"能不能走"的医学判断，交代是"告知了什么"的法律行为。
   - 两者完成时间不同（评估 12:00、交代 12:03），责任人可能不同（评估护士 + 确认医生、交代护士）。
   - **分开后可以分别查询"有评估无交代"的记录** —— 这是离院流程最典型的漏洞。

4. **`m06_delay` 独立于主表**：
   - 一次留观可能有多次延期（先延 2 小时，再延 2 小时）。
   - 延期有独立的审批链（申请人、审批人、路由层级）。

5. **无物理外键**（与 M06-01~04 一致）：
   - 跨子模块写入加锁影响并发。
   - 应用层事务成对写入 + 每日 04:00 孤儿巡检。

6. **`m06_recovery_log` 分区**：
   - 年 32 万行 × 15 年 = 480 万行，不分区单表体积超 2.5 GB。
   - 分区后"只扫最近 3 个月"物理隔离。

```sql
    ADD CONSTRAINT ck_m06_rec_eye
    CHECK (eye_side IN ('OD', 'OS', 'OU', 'NA'));

    ADD CONSTRAINT ck_m06_rec_monitor
    CHECK (monitor_level IN ('FULL', 'BASIC', 'SIMPLE'));

    ADD CONSTRAINT ck_m06_rec_interval
    CHECK (vital_interval_minutes >= 5 AND vital_interval_minutes <= 240);

    ADD CONSTRAINT ck_m06_rec_min_observe
    CHECK (min_observe_minutes >= 30 AND min_observe_minutes <= 1440);

-- 全麻/镇静/联合必须评 Aldrete，其余不评
ALTER TABLE m06_recovery
    ADD CONSTRAINT ck_m06_rec_aldrete
    CHECK ((anesthesia_type IN ('GENERAL', 'SEDATION', 'COMBINED')
            AND need_aldrete = TRUE
            AND monitor_level = 'FULL')
           OR (anesthesia_type IS NULL AND need_aldrete = FALSE)
           OR (anesthesia_type NOT IN ('GENERAL', 'SEDATION', 'COMBINED')
               AND need_aldrete = FALSE));

-- 阶段与时间戳一致性
ALTER TABLE m06_recovery
    ADD CONSTRAINT ck_m06_rec_ward
    CHECK (phase NOT IN ('WARD_OBSERVE', 'READY_DISCHARGE',
                         'DISCHARGED', 'READMITTED')
           OR recovery_end_at IS NOT NULL);

ALTER TABLE m06_recovery
    ADD CONSTRAINT ck_m06_rec_ready
    CHECK (phase NOT IN ('READY_DISCHARGE', 'DISCHARGED', 'READMITTED')
           OR ready_discharge_at IS NOT NULL);

ALTER TABLE m06_recovery
    ADD CONSTRAINT ck_m06_rec_discharged
    CHECK (phase <> 'DISCHARGED'
           OR (actual_leave_at IS NOT NULL
               AND total_observe_minutes IS NOT NULL
               AND leave_mode IS NOT NULL));

ALTER TABLE m06_recovery
    ADD CONSTRAINT ck_m06_rec_transferred
    CHECK (phase <> 'TRANSFERRED'
           OR (transfer_at IS NOT NULL
               AND transfer_reason IS NOT NULL
               AND char_length(btrim(transfer_reason)) >= 10));

ALTER TABLE m06_recovery
    ADD CONSTRAINT ck_m06_rec_readmitted
    CHECK (phase <> 'READMITTED'
           OR (revisit_at IS NOT NULL
               AND actual_leave_at IS NOT NULL
               AND revisit_complaint IS NOT NULL));

ALTER TABLE m06_recovery
    ADD CONSTRAINT ck_m06_rec_transfer_done
    CHECK (transfer_done = FALSE OR transfer_at IS NOT NULL);

-- 留观时长必须与时间戳自洽
ALTER TABLE m06_recovery
    ADD CONSTRAINT ck_m06_rec_duration
    CHECK (total_observe_minutes IS NULL
           OR (actual_leave_at IS NOT NULL
               AND total_observe_minutes =
                   GREATEST(0, EXTRACT(EPOCH FROM
                       (actual_leave_at - recovery_start_at))::INT / 60)));

-- 时间序
ALTER TABLE m06_recovery
    ADD CONSTRAINT ck_m06_rec_time_seq
    CHECK ((recovery_end_at IS NULL OR recovery_end_at >= recovery_start_at)
           AND (actual_leave_at IS NULL OR actual_leave_at >= recovery_start_at)
           AND (revisit_at IS NULL OR revisit_at > actual_leave_at));

ALTER TABLE m06_recovery

COMMENT ON COLUMN m06_recovery.total_observe_minutes IS
    '总留观分钟 = actual_leave_at - recovery_start_at';
```

**状态机**

```
        ┌──────────────────┐
        │  RECOVERY_ROOM   │  入复苏室
        └────────┬─────────┘
                 │ Aldrete ≥9 + 麻醉医生确认
                 ▼
        ┌──────────────────┐
        │  WARD_OBSERVE    │◄───────────┐
        └────────┬─────────┘            │
                 │ PADSS + 硬门槛通过     │ 重新评估未通过
                 ▼                      │
        ┌──────────────────┐            │
        │ READY_DISCHARGE  │────────────┘
        └────────┬─────────┘
                 │ 离院登记
                 ▼
        ┌──────────────────┐   72h 内再就诊   ┌──────────────────┐
        │   DISCHARGED     │─────────────────►│   READMITTED     │
        └──────────────────┘                  └──────────────────┘

        任意阶段 ──转住院──► TRANSFERRED
```

**设计要点**

1. **`uk_m06_rec_schedule` 是"一台次一留观"的结构级保障**：

   ```sql
   CREATE UNIQUE INDEX uk_m06_rec_schedule
       ON m06_recovery (schedule_id)
       WHERE is_deleted = FALSE;
   ```

   - 应用层先查后插在并发下有竞态窗口（两个护士同时点"入复苏室"）。
   - 唯一约束让第二次插入直接失败，返回 `"0605003"`。
   - 为什么不是普通唯一索引：`is_deleted` 逻辑删除的记录不应阻止重建（虽然业务上不会删留观记录，但保持与其他表一致）。

2. **`ck_m06_rec_aldrete` 把麻醉方式与监护强度绑死**：

   ```sql
   CHECK ((anesthesia_type IN ('GENERAL','SEDATION','COMBINED')
           AND need_aldrete = TRUE AND monitor_level = 'FULL')
          OR (anesthesia_type NOT IN (...) AND need_aldrete = FALSE))
   ```

   - 这表达的是业务规则 R-05/R-06：**全麻必须全套监护并评 Aldrete**。
   - 应用层已按 `ANESTHESIA_MONITOR` 字典计算，但若代码有 bug（比如字典写错），约束会阻止写入不一致的数据。
   - **为什么值得加这个约束**：如果全麻患者被误设为 `BASIC` 监护（30 分钟一次、不评 Aldrete），出室时无法判断麻醉复苏状态，可能导致患者在未完全清醒时被推出复苏室。这是真实的医疗风险。

3. **`ck_m06_rec_duration` 用表达式校验时长自洽**：

   ```sql
   CHECK (total_observe_minutes = GREATEST(0, EXTRACT(EPOCH FROM
              (actual_leave_at - recovery_start_at))::INT / 60))
   ```

   - 时长是冗余字段（为统计与排序），必须与时间戳一致。
   - `GREATEST(0, ...)` 防负数：若系统时钟回拨或补录错误导致 `actual_leave_at < recovery_start_at`，约束会报错而不是写入负时长。

4. **`preop_vision` / `preop_iop` 冗余存储**：
   - 离院时必须判断"视力较术前下降几行"，这需要术前值。
   - 术前值在 M06-02 的术前检查里，跨子模块查要 HTTP。
   - 冗余后离院评估一次 SQL 就能拿到，且**存快照意味着即使术前记录被改，离院评估用的是当时的值**。

5. **`last_vital_at` / `next_vital_due_at` 冗余到主表**：
   - 工作台要按"下次体征到期时间"排序（最急的在最上）。
   - 若实时算需 `JOIN m06_recovery_vital` 取 `MAX(measured_at)` 再加间隔，每次工作台刷新扫 4 张床 × 100 条体征记录。
   - 冗余后 `ORDER BY next_vital_due_at` 直接走索引。

6. **`abnormal_count` 冗余计数**：
   - 工作台要显示"该患者已发生 N 次异常"给护士警示。
   - 实时 `COUNT(*)` 需 JOIN `m06_recovery_abnormal`。

7. **`transfer_*` 与 `revisit_*` 字段直接放主表而不单独建表**：

   | 情况 | 记录数 | 判断 |
   |---|---|---|
   | 转住院 | 一次留观最多 1 次 | 主表字段足够 |
   | 非计划再就诊 | 一次留观最多 1 次（72h 窗口内） | 主表字段足够 |

   - 若单独建表，一年只有 400 行（转住院）+ 300 行（再就诊），维护成本大于收益。
   - **延期离院不同**：一次留观可能延期多次，所以 `m06_delay` 独立建表。

**量级估算：**

| 项 | 估算 |
|---|---|
| 日手术 | 55 |
| 年留观记录 | 55 × 365 ≈ 20,000 |
| 单行平均大小 | 约 1,100 字节 |
| 年数据量 | 约 22 MB |
| 15 年数据量 | 约 330 MB |
| 索引开销 | 约 210 MB |
| **合计（15 年）** | **约 540 MB** |

- `uk_m06_rec_schedule` 与 `uk_m06_rec_no` 若分区必须含分区键，会破坏"一台次一留观"的语义。
- 15 年 30 万行在 PG16 单表舒适区。

**设计要点**

1. **`abnormal_flags` 用 JSONB，`is_abnormal` 冗余布尔**：

   ```sql
   CHECK ((is_abnormal = FALSE AND (abnormal_flags IS NULL
                                    OR jsonb_array_length(abnormal_flags) = 0))
          OR (is_abnormal = TRUE AND jsonb_array_length(abnormal_flags) > 0))
   ```

   - 标记具体类型才能做"哪个异常最多"的统计（`BP_HIGH` 占比多少）。
   - 冗余布尔让部分索引 `WHERE is_abnormal = TRUE` 能建（JSONB 数组长度表达式不能直接建部分索引）。
   - 双向 CHECK 保证两者一致，防止"标了异常但数组空"。

2. **`ck_m06_rv_bp_order` 保证收缩压 > 舒张压**：
   - 录入 90/120 这种反了的错误在手工录入中很常见。
   - 应用层已校验，DB 层再兜一层。

3. **`ck_m06_rv_at_least_one` 防止空记录**：
   - 如果全字段为 NULL，这条记录毫无意义，只会污染统计。
   - 但允许"只记血压不记体温"这种部分记录（手工录入常见）。

4. **`consciousness` 用 5 级枚举**：
   - `AWAKE` 清醒
   - `DROWSY` 嗜睡
   - `RESPONSIVE_TO_VOICE` 呼唤能应
   - `RESPONSIVE_TO_PAIN` 疼痛刺激能应
   - `UNRESPONSIVE` 无反应

   - **不用自由文本**：意识状态是麻醉复苏的核心判断依据，自由文本无法统计也无法与 Aldrete 的"意识 2 分"对照。

| 项 | 估算 |
|---|---|
| 年留观 | 20,000 |
| 平均每条记录体征数 | 12（15~60 分钟一次，平均留观 170 分钟） |
| 年体征数 | 20,000 × 12 = 240,000 |
| 单行平均大小 | 约 240 字节 |
| 年数据量 | 约 55 MB |
| 15 年数据量 | 约 825 MB |

**设计要点**

1. **`ck_m06_re_iop_notified` 是这张表最重要的约束**：

   ```sql
   CHECK (iop IS NULL OR (iop >= 5 AND iop <= 25) OR doctor_notified = TRUE)
   ```

   - 这条约束直接对应业务规则 R-19：**眼压 >25 或 <5 必须勾选"已通知医生"**。
   - **为什么放在数据库层**：这是医疗安全红线。应用层校验可能因为接口改造、新前端漏传被绕过，DB 层是最后一道闸门。
   - 造成的效果：护士录眼压 28 时，若没勾选"已通知医生"，INSERT 直接失败。

2. **`ck_m06_re_pain_managed` 只约束 pain_score ≥7**：

   ```sql
   CHECK (pain_score IS NULL OR pain_score < 7 OR pain_managed = TRUE)
   ```

   - VAS ≤6 的疼痛不需要处置（可接受范围）。
   - VAS ≥7 属于中重度疼痛，必须记录处置（用药名称、剂量、方式）。

3. **`eye_side` 必填而非从主表继承**：
   - 虽然一次留观对应一个术眼，但留观期间可能对侧眼也要观察（如对侧眼有青光眼需要监测眼压）。
   - 独立存储让眼科观察更灵活。

4. **`iop_method` 记录测量方式**：
   - 非接触眼压计（NCT）与 Goldmann 压平眼压计的读数有系统性差异（NCT 通常略高）。
   - 纠纷时若质疑"眼压为什么比门诊高"，测量方式是关键解释依据。

5. **`notified_doctor_id` 记录具体通知了谁**：
   - 只记"已通知"不够——半年后查"当时通知的是哪个医生？他做了什么？"需要具体实名。
   - 这也是审计要求（责任到人）。

| 年眼科观察数 | 20,000 × 6 = 120,000 |

| 15 年数据量 | 约 550 MB |

```sql
    ADD CONSTRAINT ck_m06_rs_total_aldrete

            AND can_exit_room IS NOT NULL
            AND can_exit_room = (total_score >= 9))
           OR (score_type = 'PADSS' AND can_exit_room IS NULL));

-- 0 分项必须是数组

    ADD CONSTRAINT ck_m06_rs_zero
    CHECK (zero_items IS NULL OR jsonb_typeof(zero_items) = 'array');

    'Aldrete ≥9 可出复苏室，PADSS 不适用此字段';
COMMENT ON COLUMN m06_recovery_score.zero_items IS
    '0 分项数组，存在 0 分项时不可离院';
```

**设计要点**

1. **`ck_m06_rs_total_aldrete` / `ck_m06_rs_total_padss` 强制总分自洽**：

   ```sql
   CHECK (score_type <> 'ALDRETE' OR (max_score = 10
       AND total_score = activity + respiration + circulation
                        + consciousness + oxygen))
   ```

   - 应用层已计算总分，但**这个约束能防止"改了某一项但忘改总分"**。
   - 真实风险：护士发现"活动原来是 1 分，改成 2 分"，但前端只提交了 `activity=2` 没重算 `total_score`。约束会拒绝。

2. **`ck_m06_rs_exit` 把 `can_exit_room` 与总分绑死**：

   ```sql
   CHECK ((score_type = 'ALDRETE' AND can_exit_room = (total_score >= 9))
          OR (score_type = 'PADSS' AND can_exit_room IS NULL))
   ```

   - 出室门槛 9 分是业务规则 R-27，写在约束里保证不会被改分数绕过。
   - **注意**：这个硬编码 9 分与参数 `M06.RECOVERY.ALDRETE_MIN_EXIT = 9` 是同一概念的两处表达。参数是业务可配（虽然标了只读），约束是物理底线。
   - **若未来要改门槛**（比如改成 8 分），必须同时改约束与参数。文档里已明确说明这一点。

3. **Aldrete 与 PADSS 共用一张表的理由**：

   | 方案 | 优点 | 缺点 |
   |---|---|---|
   | 合并（采用） | 一次查询拿到全部评分；统计"平均 Aldrete"和"平均 PADSS"用同一张表 | 字段较多（12 个分项字段）且 PADSS 时 Aldrete 字段为 NULL |
   | 拆分两张表 | 每张表字段少 | 两表结构几乎一样，维护翻倍；查询时 UNION |

   - 选择合并：两者语义相同（"由若干 0~2 分项组成的评分"），差异只在项目清单。
   - 分项字段全部允许 NULL，由 CHECK 约束按 `score_type` 决定哪些必填。

4. **`zero_items` 存快照数组**：
   - 离院判定时要检查"是否有 0 分项"（R-34）。
   - 存数组后，事后查询"这次评估哪些项是 0 分"不用再解析各分项字段。

**量级估算：**

| 项 | 估算 |
|---|---|
| 年留观 | 20,000 |
| 平均每条记录评分数 | 5（3~5 次 Aldrete + 1 次 PADSS） |
| 年评分记录 | 20,000 × 5 = 100,000 |
| 单行平均大小 | 约 220 字节 |
| 年数据量 | 约 22 MB |
| 15 年数据量 | 约 330 MB |
| 索引开销 | 约 200 MB |
| **合计（15 年）** | **约 530 MB** |

**分区：** 不分区。

> 说明：PADSS 评分的完整十项（含眼科四项）存在 `m06_discharge` 表，而非本表。本表的 PADSS 只记录六项标准项。**这是有意的**：本表用于"趋势"（每 15 分钟的 Aldrete），`m06_discharge` 用于"最终判定"（含眼科专项 + 硬门槛）。

**设计要点**

1. **`ck_m06_ra_severe_notify` 强制 SEVERE 必须通知主刀**：

   ```sql
   CHECK (severity <> 'SEVERE' OR is_notified_surgeon = TRUE)
   ```

   - SEVERE 定义：眼压 >35、视力下降 ≥2 行、前房积血、活动性出血。
   - 这些情况主刀必须知道（可能需返台处理）。
   - **为什么不靠应用层**：护士可能觉得"先观察一下再说"，勾了 SEVERE 却没通知。DB 层拒绝入库，逼着护士打电话。

2. **`detail_json` 存异常快照**：
   - 异常发生时的体征值、眼压、视力等上下文，事后要追查"当时是什么情况触发的"。
   - 若只存 `abnormal_type='IOP_HIGH'` 不存具体值，无法还原。
   - 结构示例：
     ```json
     {
       "trigger": "IOP_HIGH",
       "iop": 32.5,
       "threshold": 25,
       "measured_at": "2026-10-24T10:20:00",
       "last_iop": 20.0,
       "delta": 12.5
     }
     ```

3. **`is_notified_family` 记录家属告知**：
   - 异常发生后是否告知家属，是纠纷时的关键证据。
   - 严重异常（如视力下降）不告知家属，事后家属会说"你们瞒着我们"。

```sql
               AND (hard_gates ->> 'companion_ready')::BOOLEAN = TRUE

                    OR jsonb_array_length(zero_items) = 0)));

    CHECK (blockers IS NULL OR jsonb_typeof(blockers) = 'array');

    CHECK ((companion_name IS NULL AND companion_relation IS NULL)
           OR (companion_name IS NOT NULL AND companion_relation IS NOT NULL));

    ADD CONSTRAINT ck_m06_dis_assessor
    CHECK (doctor_id IS NULL OR assessor_id <> doctor_id);

    '八项硬门槛快照，DISCHARGEABLE 时全部为 TRUE';

    '评估时已留观分钟数快照，用于后续追查是否满足最短留观';
COMMENT ON COLUMN m06_discharge.preop_vision IS
    '术前视力快照，用于判断视力下降幅度';
```

**设计要点**

1. **`ck_m06_dis_dischargeable` 是最核心的约束**：

   ```sql
   CHECK (conclusion <> 'DISCHARGEABLE'
          OR ((hard_gates ->> 'iop_in_range')::BOOLEAN = TRUE
              AND ... 共 8 项全部 TRUE
              AND (zero_items IS NULL OR jsonb_array_length(zero_items) = 0)))
   ```

   - 这条约束把"能离院"的**全部硬条件**写在数据库里。
   - **为什么这么写**：应用层判定逻辑是 Python 代码，可能有 bug（比如 `_check_gates` 里某个条件写反了）。如果那段代码误判了，患者可能被放行。
   - 有了这条约束，即便 Python 代码有 bug，数据库也会拒绝写入"不满足硬门槛却标 DISCHARGEABLE"的数据 —— **这是最后一道闸门**。
   - 代价：JSONB 取值 + 布尔转换在 CHECK 里性能一般，但离院评估是低频操作（日 55 次），完全可接受。

2. **`observe_minutes_at_assess` 存快照**：
   - 若实时计算，需 `assessed_at - recovery_start_at`。
   - 存快照的价值在于：**如果事后 `recovery_start_at` 被修正（补录），这个字段保留当时评估的事实**。
   - 纠纷调查时问"评估时留观多久"，这个字段直接回答。

3. **`preop_vision` 再次冗余**：
   - 主表已有 `preop_vision`，这里再存一份。
   - 理由：评估时的术前视力是**判定依据**，必须与评估结果绑定存证。若只存主表，主表被改会影响历史评估的可解释性。

4. **`assessor_id` 与 `doctor_id` 分开且不同**：
   - 评估由护士做，医生确认。
   - `ck_m06_dis_assessor` 保证两者不同 —— 若同一人评估又确认，等于没有独立的第二双眼睛。

5. **为什么 PADSS 与眼科专项分别存 `padss_total` / `eye_total` 而不存总合**

   前文讨论过：合并算总分会让"PADSS 9 分、眼科 3 分"被判通过。分开存两个总分，判定时分别判断，才不会出错。

1. **`ck_m06_di_lists` 强制四大类清单非空**：

   ```sql
   CHECK (jsonb_array_length(emergency_items) > 0 AND ...)
   ```

   - 这表达的是"交代不能有空项"：如果某术式缺少紧急提示模板，护士就不能完成交代，必须找医务科补模板。
   - **为什么这样设计**：真实风险是"模板没配，护士随手跳过"，患者出院后不知道什么情况要来急诊。约束强制暴露配置缺失。

2. **`ck_m06_di_confirmed` 强制四大类全部确认才可签字**：

   ```sql
   CHECK (signed_at IS NULL OR (confirmed_medication = TRUE
       AND confirmed_followup = TRUE
       AND confirmed_emergency = TRUE
       AND confirmed_taboo = TRUE))
   ```

   - 对应业务规则 R-43 / V-21。
   - **一个总勾不会被接受**：四个独立布尔字段强制护士至少看四眼。

3. **`ck_m06_di_surrogate` 与 `ck_m06_di_self` 双向钉死关系字段**：

   ```sql
   CHECK (sign_type <> 'SURROGATE_SIGN' OR (signer_relation <> '本人' AND ...))
   CHECK (sign_type <> 'PATIENT_SIGN' OR signer_relation = '本人')
   ```

   - 防"选了家属代签但关系填本人"这种逻辑矛盾。
   - 纠纷时如果发现签名人身份与关系不符，整份交代的法律效力会被质疑。

4. **`ck_m06_di_witness` 要求口头确认必须有见证人**：
   - 口头确认是"没有书面证据"的最弱确认方式。
   - 见证人的存在至少提供第二人证。

5. **四个 JSONB 数组而非四张明细表**：

   | 方案 | 优点 | 缺点 |
   |---|---|---|
   | JSONB 数组（采用） | 一次读写整个交代；字段结构灵活 | 无法单独索引某个药名 |
   | 四张明细表 | 可单独查询 | 四张表 × 一年 2 万条 = 8 万行，全是"读完即忘"的数据 |

   - 选择 JSONB：交代内容是"一次性整体呈现给患者"的，从不需要单独查"哪个患者被交代了左氧氟沙星"。
   - 若未来有这需求，可以加 GIN 索引 `USING gin (medication_items jsonb_path_ops)`。

   **数据结构示例**：
   ```json
   [
     {"drug_name": "左氧氟沙星滴眼液", "usage": "每日4次",
      "dosage": "1滴", "duration_days": 14, "eye_side": "OS"},
     {"drug_name": "普拉洛芬滴眼液", "usage": "每日4次",
      "dosage": "1滴", "duration_days": 30, "eye_side": "OS"}
   ]
   ```

6. **`idx_m06_di_unsigned` 部分索引用于漏洞排查**：
   - 每天定时任务扫"有留观记录但没有交代记录"或"有交代但未签字"的情况。
   - 这是质控指标"离院交代签字率"的数据来源。

   ```sql
       WHERE status = 'PENDING' AND is_deleted = FALSE;
   ```

   - 对应业务规则 R-56 / V-29。
   - 防护士连点"发起延期"生成两条待审批单，导致两个审批人各批一次、消息重复。

2. **`ck_m06_dl_expected_check` 用 `expected_leave_at > created_at` 而非 `> NOW()`**：
   - `created_at` 在 INSERT 时由 `CURRENT_TIMESTAMP` 生成，`expected_leave_at` 是提交值。
   - 用 `created_at` 而非 `NOW()` 保证约束是确定性的（`NOW()` 在 CHECK 中不被推荐，且每次评估结果不同）。
   - 应用层已用 `datetime.now()` 校验，DB 层用 `created_at` 兜底。

3. **`notify_targets` 与 `notify_status` 双 JSONB**：

   `notify_targets` 示例（数组）：

   ```json
   ["FAMILY", "SURGEON", "ANESTHETIST", "BED_MANAGER"]
   ```

   `notify_status` 示例（对象）：

   ```json
   {"FAMILY": "SENT", "SURGEON": "SENT", "ANESTHETIST": "FAILED", "BED_MANAGER": "SENT"}
   ```

   - 延期通知是"多目标异步"操作，部分成功是常态。
   - **为什么不单独建通知明细表**：一年只有 1,600 条延期 × 4 个目标 = 6,400 行，独立建表维护成本大于收益。

4. **`status` 与 `is_transfer` 双字段**：
   - `TRANSFER_APPROVED` 状态与 `is_transfer=TRUE` 由 `ck_m06_dl_transfer_status` 强制同步。
   - 冗余 `is_transfer` 是为了"快速筛出转住院的延期"（`WHERE is_transfer = TRUE` 比 `WHERE status = 'TRANSFER_APPROVED'` 语义更直接）。

**分区定义**

```sql
DO $$
DECLARE
    v_start DATE := DATE '2026-10-01';
    v_i INT;
    v_name TEXT;
    v_from DATE;
    v_to DATE;
BEGIN
    FOR v_i IN 0..35 LOOP
        v_from := (v_start + (v_i || ' months')::INTERVAL)::DATE;
        v_to := (v_from + '1 month'::INTERVAL)::DATE;
        v_name := 'm06_recovery_log_' || TO_CHAR(v_from, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m06_recovery_log '
            'FOR VALUES FROM (%L) TO (%L)',
            v_name, v_from, v_to
        );
    END LOOP;
END $$;
```

**设计要点**

1. **16 种 action 覆盖全流程**：
   - 留观（5）：`RECOVERY_CREATE` / `VITAL_RECORD` / `EYE_RECORD` / `SCORE_RECORD` / `EXIT_ROOM`
   - 异常（2）：`ABNORMAL_RECORD` / `ABNORMAL_DISPOSE`
   - 离院（5）：`DISCHARGE_ASSESS` / `DISCHARGE_APPROVE` / `INSTRUCTION_SAVE` / `INSTRUCTION_SIGN` / `DEPART`
   - 延期（2）：`DELAY_CREATE` / `DELAY_APPROVE`
   - 其他（2）：`TRANSFER` / `READMIT`

2. **分区理由**：
   - 年 32 万条 × 15 年 = 480 万行，单表体积超 2.5 GB。
   - 分区后时间线查询（只扫 1 个分区）性能提升 10 倍。

3. **`before_json` / `after_json` 只在复杂变更时使用**：
   - 状态流转用 `from_phase` / `to_phase`（简洁可索引）。
   - 数据修改（如体征更正、评估值修改）才用 JSONB 存前后快照。

**量级估算：**

| 项 | 估算 |
|---|---|
| 年留观 | 20,000 |
| 每留观日志数 | 16（创建 1 + 体征 12 + 眼科 6 + 评分 5 + 离院 5，部分合并） |
| 年日志数 | 20,000 × 16 = 320,000 |
| 单行平均大小 | 约 420 字节 |
| 年数据量 | 约 134 MB |
| 15 年数据量 | 约 2 GB |
| 索引开销 | 约 1.2 GB |
| **合计（15 年）** | **约 3.2 GB** |

**分区：** 按 `seq_date` 月度 RANGE 分区，预建 36 个月。

**八个「敏感 + 只读」参数的制度来源：**

| 参数 | 依据 | 若被篡改的后果 |
|---|---|---|
| `ALDRETE_MIN_EXIT` | 麻醉复苏标准 | 未完全清醒的患者被推出复苏室，可能发生误吸 |
| `PADSS_MIN` | 日间手术离院标准 | 未达标患者被放行，术后并发症无法及时发现 |
| `IOP_MIN` / `IOP_MAX` | 眼科临床规范 | 高眼压/低眼压患者被放行，致视神经损伤或脉络膜脱离 |
| `MIN_OBSERVE_CATARACT` | 本院日间手术管理制度 | 留观时间不足，粘弹剂残留高眼压漏诊 |
| `MIN_OBSERVE_VITRECTOMY` | 同上 | 玻切术后出血、视网膜脱离漏诊 |
| `ANESTHESIA_GAP_MIN` | 麻醉安全要求 | 全麻药物再分布导致二次镇静，回家途中呼吸抑制 |
| `REVISIT_WINDOW_HOURS` | 质控指标定义 | 指标失真，无法衡量离院判定质量 |
