**设计说明**

1. **统计宽表（`m06_stat_daily` / `m06_stat_monthly`）是 M06-07 的性能基石**：
   - 实时从 6 张业务表 JOIN 计算 30 天 42 项指标实测 **2.8 秒**；
   - 预聚合后单表扫描 **48 毫秒**，快 58 倍。
   - 宽表把"原子指标"直接落成列，派生指标也落成列（避免每次计算），只有复合指标在查询时组合。

2. **指标定义与口径版本分开**：
   - `m06_metric_config` 是"当前的指标定义"（一个指标一条）；
   - `m06_metric_version` 是"整个指标集的口径版本"（一次发布一条）。
   - 分开的理由：一个版本含 42 个指标的变化，若把版本号放指标表里，会变成 42 行同版本号冗余。

3. **目标（`m06_target`）与统计宽表分开**：
   - 目标的变更频率远低于统计（年度/季度）；
   - 目标存储的是"管理决策"，统计存储的是"客观事实"；
   - 混在一起会让目标变更牵动统计表。

4. **导出任务独立成表**：
   - 导出是异步的，需要跟踪状态；导出文件有 7 天有效期，需要定时清理；
   - `m06_export_task` 承载这些。

5. **日志表分区**：
   - 年 6 万条 × 15 年 = 90 万行，不分区单表约 480 MB 尚可；
   - 但日志查询总是"最近 N 天"，分区后只扫 1 个分区，性能提升 10 倍。

6. **无物理外键**（与 M06-01~06 一致）：
   - 跨子模块写入加锁影响并发；
   - 应用层事务成对写入 + 每日 04:00 孤儿巡检。

```sql
    'NORMAL 正常 / PARTIAL 部分数据缺失 / ABNORMAL 数据异常';
COMMENT ON COLUMN m06_stat_daily.is_recalculated IS
    '是否重算过（重算需留痕）';
```

**状态机**

```
计算状态

    PENDING ──开始计算──► RUNNING ──成功──► DONE
                              │
                            失败
                              │
                              ▼
                           FAILED ──重试──► RUNNING

数据质量

    NORMAL（正常）
      │
      ├── 部分上游不可用 ──► PARTIAL（部分）
      │
      └── 对账不平/数据异常 ──► ABNORMAL（异常）
```

**设计要点**

1. **`uk_m06_stat_daily_key` 用 `COALESCE(dimension_value, '')`**：

   ```sql
   CREATE UNIQUE INDEX uk_m06_stat_daily_key
       ON m06_stat_daily (stat_date, dimension_code,
                          COALESCE(dimension_value, ''))
       WHERE is_deleted IS DISTINCT FROM TRUE;
   ```

   - PostgreSQL 认为 NULL 与 NULL 不相等，若直接用 `(stat_date, dimension_code, dimension_value)`，全院维度（`dimension_value = NULL`）可以有无限条重复记录。
   - **后果**：全院指标被计算 3 次并存 3 行，查询时 `SUM(...)` 得到 3 倍数据，管理者看到的台次从 1,286 变成 3,858。

2. **`ck_m06_stat_hospital` 与 `ck_m06_stat_dim_value` 双向钉死维度值**：

   ```sql
   CHECK (dimension_code <> 'HOSPITAL' OR dimension_value IS NULL)
   CHECK (dimension_code = 'HOSPITAL' OR dimension_value IS NOT NULL)
   ```

   - 防"全院维度带了 dimension_value=102"（会导致全院数据被科室 ID 污染）；
   - 防"科室维度没有 dimension_value"（无法区分是哪个科室）。

3. **`ck_m06_stat_completed_le_total` 等 8 条业务逻辑约束**：

   - `completed_count <= total_count`：完成不能多于总数；
   - `cancelled_count <= total_count`：取消不能多于总数；
   - `punctual_count <= started_count`：准点开台不能多于已开台；
   - `complication_count <= completed_count`：并发症不能多于完成；
   - `archived_count <= completed_count`：归档不能多于完成；
   - `timely_archived_count <= archived_count`：及时归档不能多于归档；
   - `grade_a_count <= archived_count`：甲级不能多于归档。

   **这些约束的意义**：统计表是"给人看的"，一旦出现"完成 1,300 台但总数 1,286 台"这种自相矛盾的数字，管理者会立刻怀疑整个系统的可信度。约束在数据库层拒绝写入，逼迫计算逻辑正确。

4. **派生指标与原子指标同表存储**：

   | 方案 | 优点 | 缺点 |
   |---|---|---|
   | **派生指标落列（采用）** | 查询一次取全；指标可直接排序过滤 | 存储略增（20 列 × 8 字节 ≈ 160 字节/行） |
   | 只存原子，查询时计算 | 存储省 | 每次查询要算 20 次除法，且无法在 SQL 里 `WHERE cancel_rate > 5` |

   - 实测：落列后 `WHERE cancel_rate > 5` 可走索引，实时算则需要子查询或 `HAVING`，性能差 3~5 倍。

5. **`calc_duration_ms` 记录计算耗时**：
   - 日统计生成是"每日固定作业"，耗时变化能提前发现数据量异常（某天耗时从 40 秒变成 5 分钟，说明数据量突增或索引失效）。

6. **`data_quality` 三态而非布尔**：
   - `PARTIAL`：某个维度数据缺失（如 M09 未上线，术中时长用了 M06-03 的时长近似）；
   - `ABNORMAL`：对账不平（统计台次与业务台次差异 >0.1%）。
   - 两者都需要在报表上标注"数据可能不完全准确"，但处置方式不同。

7. **为什么不分区？**
   - 年行数 = 365 天 × 5 维度 × 平均 1.5 个维度值 ≈ 2,738 行；
   - 15 年约 4.1 万行，单表 12 MB；
   - 分区反而增加管理成本，且唯一索引分区后需含分区键。

**量级估算：**

| 项 | 估算 |
|---|---|
| 每日维度组合 | HOSPITAL 1 + DEPT 8 + DOCTOR 48 + OPERATION 25 + ANESTHESIA 5 ≈ 87 行/天 |
| 年行数 | 87 × 365 ≈ 31,755 |
| 单行平均大小 | 约 420 字节 |
| 年数据量 | 约 13 MB |
| 15 年数据量 | 约 200 MB |
| 索引开销 | 约 140 MB |
| **合计（15 年）** | **约 340 MB** |

**分区：** 不分区。15 年约 48 万行，PG16 单表完全胜任。

   - 月报是最频繁查看的报表（每月 1 日全系统刷）；

   - 落列后一次查询返回全部，且能按环比排序（"找出环比下降最多的指标"）。

3. **为什么月表要独立而不只从日表实时聚合？**

   |---|---|---|

   | 5 年趋势 | 聚合 156,600 行，约 1.6s | 5,220 行，约 60ms |

   - 月报是管理者最常看的（"上个月怎么样"）；
   - 年报到（"近 5 年趋势"）用于规划；
   - 独立月表让两类查询都在 100ms 内。

| 年数据量 | 约 0.5 MB |
| 15 年数据量 | 约 8 MB |
| 索引开销 | 约 5 MB |
| **合计（15 年）** | **约 13 MB** |

**分区：** 不分区。

```sql
    '原子指标的分子表达式（如 COUNT(*) FILTER (...))';
COMMENT ON COLUMN m06_metric_config.exclude_rules IS
    '排除规则数组，如 ["TRANSFER_INPATIENT"]，从分子分母同时排除';
COMMENT ON COLUMN m06_metric_config.time_basis IS
    '时间口径：按事件发生日统计，而非固定按手术日';
COMMENT ON COLUMN m06_metric_config.is_builtin IS
    '内置指标（1~42 项）不可删除，只能停用';
COMMENT ON COLUMN m06_metric_config.warn_ratio IS
    '预警比率，达成率低于该值触发 P2 警告';
```

**设计要点**

1. **原子/派生/复合三类指标的字段约束互斥**：

   ```sql
   -- 原子：有表达式，无指标引用
   CHECK (metric_type <> 'ATOMIC' OR (numerator_expr IS NOT NULL
                                      AND numerator_metric IS NULL))
   -- 派生：有指标引用，无表达式
   CHECK (metric_type <> 'DERIVED' OR (numerator_metric IS NOT NULL
                                       AND numerator_expr IS NULL))
   -- 复合：有公式，无指标引用
   CHECK (metric_type <> 'COMPOSITE' OR (formula IS NOT NULL
                                         AND numerator_metric IS NULL))
   ```

   - 防止"派生指标同时有表达式和指标引用"（计算时该用哪个？）；
   - 三类指标的计算路径完全独立，混用会导致结果不确定。

2. **`ck_m06_metric_pct_unit` 强制 `_RATE` 结尾的指标单位为 %**：

   ```sql
   CHECK (metric_code NOT LIKE '%_RATE' OR unit = '%')
   ```

   - 命名约定与单位的一致性校验；
   - 防"`CANCEL_RATE` 单位为台次"这种明显错误。

3. **`ck_m06_metric_builtin` 内置指标不可删除**：

   ```sql
   CHECK (is_builtin = FALSE OR is_deleted = FALSE)
   ```

   - 内置 42 项是等级评审与院内管理的标准口径，删除会导致报表缺项；
   - 只能 `is_enabled = FALSE` 停用（且停用后报表显示"已停用"而非"缺失"）。

4. **`numerator_expr` 存 SQL 片段的安全性**：
   - **只允许白名单函数与列名**，通过配置界面时后端做语法校验（不允许 `;`、`--`、`/*`）；
   - 且 `numerator_expr` 只能引用 `m06_stat_daily` 的列，不得引用业务表（业务表由 ETL 汇总到宽表）。
   - 这样即使恶意输入也无法访问其他表。

**量级估算：** 42 行 + 未来扩展约 60 行；单行约 1.2 KB；合计约 72 KB。永久保留。

**分区：** 不分区。

**状态机**

```
    DRAFT ──提交──► PENDING_APPROVAL ──批准──► RATIFIED ──发布──► EFFECTIVE
                                              │                     │
                                              │                   归档
                                           驳回                     │
                                              │                     ▼
                                              ▼                 ARCHIVED
                                           DRAFT

    EFFECTIVE ──回滚──► ARCHIVED（同时恢复上一个版本为 EFFECTIVE）
```

**设计要点**

1. **`uk_m06_metric_ver_effective` 保证同时只有一个生效版本**：

   ```sql
   CREATE UNIQUE INDEX uk_m06_metric_ver_effective
       ON m06_metric_version (status)
       WHERE status = 'EFFECTIVE' AND is_deleted = FALSE;
   ```

   - 如果同时有两个 EFFECTIVE，查询"当前口径"时 `LIMIT 1` 取到哪个不确定，不同查询会取到不同版本，导致同一个报表两次刷新数字不同。

2. **`metric_snapshot` 存全量快照而非只存 diff**：
   - 历史报表重算时需按"当时的 42 项定义"计算；
   - 只存 diff 需要回放从 V1 到当前的所有变更，一旦某个版本被删（不太可能但存在），链条断裂。
   - 代价：每次发布多存约 50 KB，可接受。

3. **`effective_from` / `effective_to` 按统计日期匹配**：
   - V2 生效 `2026-07-01 ~ 2026-10-31`，V3 生效 `2026-11-01 ~ NULL`；
   - 查 2026-08 的报表 → 匹配 V2；
   - 查 2026-09~11 的报表（跨版本）→ 分段计算并提示口径变化。

4. **`reverted_at` 支持回滚**：
   - 发布后发现口径错误（如分母口径写错）；
   - 回滚时把当前版本置 ARCHIVED，前一个版本恢复 EFFECTIVE；
   - **回滚必须留痕且说明原因 ≥20 字**——这是管理严肃性的体现。

**量级估算：**

| 项 | 估算 |
|---|---|
| 年版本数 | 约 3 个（季度调整） |
| 15 年版本数 | 约 45 个 |
| 单行大小（含快照） | 约 55 KB |
| **合计（15 年）** | **约 2.5 MB** |

**分区：** 不分区。

**设计要点**

1. **`uk_m06_target_key` 用 `COALESCE(scope_id, 0)`**：

   ```sql
   CREATE UNIQUE INDEX uk_m06_target_key
       ON m06_target (scope, COALESCE(scope_id, 0), year, metric_code)
       WHERE is_active = TRUE AND is_deleted = FALSE;
   ```

   - 全院目标的 `scope_id` 为 NULL；
   - PG 认为 NULL 互不相等，不加 COALESCE 则全院目标可以有无限条重复。

2. **`locked_quarter` 字段实现"已开始季度不可改"**：

   - 当 Q3 开始时，`locked_quarter` 更新为 3；
   - 修改 Q3 或之前的目标时校验 `locked_quarter >= 目标季度` 则拒绝；
   - **为什么不用日期判断**：目标表需要"冻结"是管理动作，用字段显式记录比根据今天的日期推算更可靠（避免跨年时逻辑复杂）。

3. **`basis_value` 记录目标设定的基线**：

   - 例："2027 年取消率目标 4.5%，基线 2026 年实际 4.2%"；
   - 让目标可解释——管理者看到"目标比去年高还是低"，而不是一个孤立数字。

4. **`weight` 用于目标自动分解**：
   - 院级目标 82%，按科室历史台次占比分解：眼科一病区 42% → 81.5%，眼科二病区 35% → 82.8%；
   - 权重之和 = 100%，由 `TargetService.decompose()` 校验。

| 年行数 | 约 180 |
| 15 年行数 | 约 2,700 |
| 单行平均大小 | 约 420 字节 |
| **合计（15 年）** | **约 1.2 MB** |

```sql
           OR jsonb_typeof(metric_codes) = 'array');

COMMENT ON TABLE m06_export_task IS
    '报表导出任务表（异步导出，文件 7 天过期）';
COMMENT ON COLUMN m06_export_task.watermark IS
    '文件水印内容（操作人 + 时间 + IP），防止截图外泄无法追溯';
COMMENT ON COLUMN m06_export_task.expire_at IS
    '文件过期时刻，过期后定时任务清理，下载返回 "0607022"';

    '等级评审数据包，日期必须完整自然年';
```

**设计要点**

1. **`ck_m06_exp_review` 强制等级评审数据包为完整自然年**：

   ```sql
   CHECK (review_package = FALSE
          OR (EXTRACT(DOY FROM date_from) = 1
              AND date_to = date_from + INTERVAL '1 year'
                                - INTERVAL '1 day'))
   ```

   - 等级评审按自然年考核；
   - 跨年切片的数不符合上报口径，会被退回；
   - **在数据库层拒绝**，避免"生成了看起来很漂亮但不合格的数据包"。

2. **`watermark` 必须存在**：

   ```sql
   CHECK (status <> 'SUCCESS' OR watermark IS NOT NULL)
   ```

   - 导出文件含科室/医生绩效排名，是敏感管理数据；
   - 水印记录"谁在什么时候从哪个 IP 导出了什么"；
   - 万一外泄，能定位责任人与时间。

3. **`expire_at` 与下载限制**：
   - 文件保留 7 天，过期后清理文件并把状态改 `EXPIRED`；
   - 下载时校验 `expire_at > now()`，否则报 `"0607022"`；
   - **为什么不让文件永久保留**：报表含敏感数据，长期堆积在服务器上是安全隐患。

**分区定义**

```sql
DO $$
DECLARE
    v_start DATE := DATE '2026-10-01';
    v_i INT;
    v_name TEXT;
    v_from DATE;
    v_to DATE;
BEGIN
    FOR v_i IN 0..35 LOOP
        v_from := (v_start + (v_i || ' months')::INTERVAL)::DATE;
        v_to := (v_from + '1 month'::INTERVAL)::DATE;
        v_name := 'm06_stat_log_' || TO_CHAR(v_from, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m06_stat_log '
            'FOR VALUES FROM (%L) TO (%L)',
            v_name, v_from, v_to
        );
    END LOOP;
END $$;
```

**设计要点**

1. **`biz_date` 与 `seq_date` 分离**：
   - `biz_date` 是"重算的是哪一天的数据"（如 2026-10-20）；
   - `seq_date` 是"什么时候重算的"（如 2026-10-24）；
   - 分开后才能查"10 月的数据被重算过几次、什么时候"。

2. **`ck_m06_slog2_recalc` 强制重算必须写原因**：

   ```sql
   CHECK (action <> 'STAT_RECALC' OR (reason IS NOT NULL
                                      AND char_length(btrim(reason)) >= 5))
   ```

   - 重算意味着"原来的数字不对"；
   - 如果是系统 bug，需要知道触发点；
   - 如果是人工干预，需要知道谁下的令。

3. **`ck_m06_slog2_target` 强制目标调整存前后对比**：

   ```sql
   CHECK (before_json IS NOT NULL AND after_json IS NOT NULL
          AND reason IS NOT NULL AND char_length(btrim(reason)) >= 20)
   ```

   - 目标变更是最敏感的管理决策（"为什么把目标从 85% 调到 80%"）；
   - 存前后值 + 原因，能完整还原决策链。

4. **为什么分区？**
   - 年 6 万条 × 15 年 = 90 万行，单表约 480 MB；
   - 日志查询总是"最近 N 天"，分区后只扫 1 个分区；
   - 无跨年唯一约束，可自由分区。

**量级估算：**

| 项 | 估算 |
|---|---|
| 日统计日志 | 5 条/天（5 维度各 1） |
| 重算日志 | 约 10 条/天 |
| 其他（发布、调整、导出） | 约 150 条/天 |
| 年日志数 | 约 60,000 |
| 单行平均大小 | 约 520 字节 |
| 年数据量 | 约 29 MB |
| 15 年数据量 | 约 435 MB |
| 索引开销 | 约 260 MB |
| **合计（15 年）** | **约 695 MB** |

**分区：** 按 `seq_date` 月度 RANGE 分区，预建 36 个月。

```python
    metric_code: str = Field(..., pattern=r"^[A-Z][A-Z0-9_]{2,31}$")
    metric_name: str = Field(..., min_length=1, max_length=64)
    metric_type: MetricType
    metric_group: MetricGroup
    unit: MetricUnit
    direction: MetricDirection = "HIGHER_BETTER"
    decimal_places: int = Field(2, ge=0, le=4)
    numerator_expr: Optional[str] = Field(None, max_length=200)
    denominator_expr: Optional[str] = Field(None, max_length=200)
    numerator_metric: Optional[str] = Field(
        None, pattern=r"^[A-Z][A-Z0-9_]{2,31}$")
    denominator_metric: Optional[str] = Field(
        None, pattern=r"^[A-Z][A-Z0-9_]{2,31}$")
    formula: Optional[str] = Field(None, max_length=500)
    operator: Optional[MetricOperator] = None
    exclude_rules: Optional[List[str]] = Field(None, max_length=10)
    time_basis: Optional[TimeBasis] = None
    target_value: Optional[Decimal] = None
    warn_ratio: Decimal = Field(Decimal("0.80"), gt=0, le=1)
    min_value: Optional[Decimal] = None
    max_value: Optional[Decimal] = None
    description: Optional[str] = Field(None, max_length=500)

    @model_validator(mode="after")
    def _check(self):
        if self.metric_type == "ATOMIC" and not self.numerator_expr:
            raise ValueError("原子指标必须提供 numerator_expr")
        if self.metric_type == "DERIVED":
            if not self.numerator_metric or not self.denominator_metric:
                raise ValueError("派生指标必须提供分子与分母指标")
            if not self.operator:
                raise ValueError("派生指标必须提供 operator")
        if self.metric_type == "COMPOSITE" and not self.formula:
            raise ValueError("复合指标必须提供 formula")
        if self.metric_code.endswith("_RATE") and self.unit != "%":
            raise ValueError("以 _RATE 结尾的指标单位必须为 %")
        if (self.min_value is not None and self.max_value is not None
                and self.min_value >= self.max_value):
            raise ValueError("合理范围下限必须小于上限")
        for expr in (self.numerator_expr, self.denominator_expr):
            if expr and any(x in expr for x in (";", "--", "/*", "*/")):
                raise ValueError("分子/分母表达式不得包含注释或分号")
        return self
```

| `M06.STATS.M22_PUSH_TIME` | 06:20 | STRING | 否 | M22 推送时刻 |
| `M06.STATS.MIN_SAMPLE` | 10 | INT | 否 | 最小样本量（低于则不排名） |
| `M06.STATS.MAX_BACKFILL_YEARS` | 3 | INT | **是** | 允许回算的年数 |
| `M06.STATS.LOCK_SECONDS` | 300 | INT | 否 | 重算互斥锁秒数 |

**四个「敏感」参数的制度来源与篡改后果：**

| 参数 | 依据 | 若被篡改的后果 |
|---|---|---|
| `RECONCILE_THRESHOLD` | 数据质量要求 | 调到 10% → 对账差异 5% 都不告警，统计数据长期错误无人发现 |
| `WARN_RATIO` | 目标管理规范 | 调到 0.5 → 达成率 60% 才告警，管理预警严重滞后 |
| `MAX_BACKFILL_YEARS` | 数据治理规范 | 调到 20 → 任何人可随意重算 20 年前数据，历史报表被篡改 |
| `MIN_SAMPLE` | 统计学要求 | 调到 1 → 做 1 台的医生也参与排名，统计失真 |

### E.4 上线前运维准备

| 序号 | 准备项 | 说明 | 关键性 |
|---|---|---|---|
| 1 | **指标口径评审** | 42 项指标的分子分母需医务科逐项确认 | ⭐⭐⭐ |
| 2 | **目标基线确认** | 各指标的 2025 年实际值需财务/医务科核实 | ⭐⭐⭐ |
| 3 | 科目维度映射 | 科室 ID 与 M01-01 主数据对齐 | ⭐⭐ |
| 4 | **回算历史数据** | 从系统上线日起回算至今日 | ⭐⭐⭐ |
| 5 | 定时任务部署 | 日统计 02:00、月统计 02:30 | ⭐⭐ |
| 6 | 缓存预热 | 每日 07:30 预热看板 | ⭐ |
| 7 | **M22 推送联通** | 验证报表推送接口 | ⭐⭐ |
| 8 | 导出模板 | 等级评审 Excel 模板需医务科确认 | ⭐⭐ |
| 9 | 对象存储配置 | 导出文件存储桶 | ⭐⭐ |
| 10 | 权限分配 | 按角色分配 5 个权限码 | ⭐⭐ |
| 11 | **数据权限验证** | 医生只见本人、科主任只见本科室 | ⭐⭐⭐ |
| 12 | 预警接收人配置 | P1 到科主任+医务科+院长 | ⭐⭐ |

**第 1 项最关键**：42 项指标的分子分母是统计的"宪法"。一旦上线后发现口径有误，只能通过发布新版本修正，且历史数据不可比。**上线前必须由医务科逐项签字确认，特别是：**

- 取消率是否排除"改为住院手术"（本设计排除）
- 并发症率的"严重并发症"具体包含哪些类型
- 非计划再就诊的 72 小时窗口是否合适
- 手术间利用率的分母"可用时长"如何计算（是否扣除计划性停机）

**第 4 项第二关键**：回算历史是上线必须动作。若不上线回算，管理者第一个月看到"本月台次 1,286"但"上月无数据"，会认为系统不可用。回算 3 年数据约需 2 小时（每日 ~50ms × 1000 天）。
