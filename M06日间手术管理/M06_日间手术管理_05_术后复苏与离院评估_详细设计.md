## 1. 模块概述

### 1.1 模块定位

M06-05 回答一个问题：**「这位患者现在能不能回家？」**

这是日间手术全流程中**法律责任转移的那一刻**。手术做完了、麻醉醒了，但只要没有完成离院评估并签字，患者的监护责任还在这家医院；一旦签下名字，责任就转移给了患者本人和家属。

```

                              │
                              ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  M06-05 术后复苏与离院评估                                                │
│                                                                          │
│  ① 交接二：手术室 → 复苏室（Handover B）                                   │
│     巡回护士 交给 复苏室护士：患者 / 术中情况 / 用药 / 标本 / 晶体 / 设备    │
│     → 双方电子签名（由 M06-04 完成，本子模块消费）                          │
│                              │                                            │
│                              ▼                                            │
│  ② 复苏监护（Recovery Monitoring）                                        │
│     每 15 分钟记录一次生命体征，评估 Aldrete 评分                            │
│     眼压 / 视力 / 房水 / 前房 / 出血 —— 眼科特有观察项                      │

│     不达标 → 继续留观 / 延期离院 / 转住院                                   │
│                              │                                            │
```

**一句话边界**：M06-05 只管「手术后到患者真正走出医院大门这一段」，不管手术本身（M09）、不管术前核对（M06-04）、不管结算（M06-06）。

### 1.2 为什么独立成子模块

**理由一：离院判定是法律责任转移点，是最需要独立留痕的环节。**

日间手术最大的法律风险不是手术本身，而是**"患者不该走的时候让他走了"**。真实案例：

- 白内障术后 2 小时患者自觉良好要求回家，护士放行；当晚发生急性眼内炎，视力永久丧失。家属起诉：「你们为什么让他走？」
- 玻璃体腔注药后患者主诉轻微头痛，医生判断为"紧张"，离院 6 小时后因眼压升高导致视神经损伤。

这类纠纷的核心问题永远是：**「离院时你们评估了什么？结论是什么？谁签的字？有没有告诉患者出现什么情况要立刻回来？」** 如果这些答案在系统里找不到，医院必然败诉。

所以离院评估必须：
- 有明确的评估项清单（不是"看着还行"）
- 有量化标准（不是"血压正常"而是"收缩压 90~160"）
- 有签字确认（患者本人或家属）
- 有离院交代记录（告知了什么、患者是否表示理解）
- 有独立的记录表（不是散落在护理记录里）

这四条构成一个独立子模块的完整理由。

**理由二：复苏监护与手术记录是两套数据，责任人也不同。**

| 维度 | 手术（M09） | 复苏监护（M06-05） |
|---|---|---|
| 责任人 | 主刀医生 | 麻醉医生 / 复苏室护士 |
| 记录频率 | 术中随时（事件驱动） | 每 15 分钟（时间驱动） |
| 数据性质 | 手术过程事实 | 生命体征趋势 |
| 数据来源 | 手动记录 + 设备 | 监护仪 + 手动录入 |
| 异常处置 | 术中决策 | 延长留观 / 转住院 |

如果把复苏监护塞进 M09 术中记录，会出现两个问题：一是 M09 的表结构要同时容纳"术中事件"与"周期性体征"，字段臃肿；二是 M09 的权限（手术医生）与复苏（复苏室护士）完全不同，混在一起会架空权限。

**理由三：延期离院与转住院必须有独立流程。**

日间手术 5%~8% 的患者会因为各种原因无法当天离院：

| 原因 | 处理 |
|---|---|
| 眼压持续升高 | 继续留观 2 小时复查，仍高则转住院 |
| 术后出血 | 压迫止血 + 留观，必要时返台 |
| 恶心呕吐严重 | 留观至症状缓解 |
| 疼痛控制不佳 | 镇痛处理 + 留观 |
| 独居无人陪护 | 联系家属 / 转住院 / 社工介入 |
| 全身情况不稳 | 转内科会诊 / 转住院 |

延期离院不是"在原来那张表里改个时间"，而是：
- 要通知家属（可能已经来了）
- 要占用床位（后面还有下一台患者要用）
- 要通知手术医生、麻醉医生
- 要评估是否需要转住院（跨业务形态，M16-03 日间结算要改成住院结算）
- 要记录延期原因（质量指标「延期离院率」）

这些动作需要一个独立的「延期离院」流程与状态机。

**理由四：离院后的随访计划必须在离院那一刻生成。**

眼科术后随访是有强制时间点的（M01-07 定义：白内障术后 1 天 / 1 周 / 1 月；玻璃体腔注药术后 1 天 / 1 月）：

- 术后第 1 天复查，发现眼内炎可以挽救视力
- 术后 1 周复查，发现眼压升高可以调整用药
- 术后 1 月复查，评估最终效果

**如果不在离院时生成随访任务，患者回家后就没人管了。** 随访任务需要：
- 带术式信息（决定随访间隔）
- 带离院时间（决定具体日期）
- 带医生信息（决定找谁看）
- 带紧急联系提示（出现什么情况要提前来）

这些都在离院那一刻才能确定，所以生成随访计划必须挂在离院流程里。

**理由五：统计口径完全不同。**

日间手术质量核心指标中，有三个只属于 M06-05：

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| 平均留观时长 | 从入复苏室到实际离院 | 效率指标（床位周转） |
| 延期离院率 | 延期离院台次 / 总台次 | 安全与效率双重信号 |
| 非计划再就诊率 | 离院 72 小时内因手术相关问题再就诊 | 离院判定质量的核心反向指标 |

第三个指标尤其重要：如果某个月非计划再就诊率从 1% 涨到 5%，说明离院评估标准放松了或者术后交代不到位。

### 1.3 与相邻子模块的分工

| 子模块 | 管什么 | 与 M06-05 的关系 |
|---|---|---|
| **M06-01 申请与准入** | 能不能做、谁做 | M06-05 完成后回写 `CLOSED` 状态 |
| **M06-02 术前准备** | 术前该做的做了吗 | 无直接关系；M06-05 用术前基线值（如术前眼压） |
| **M06-03 排程与手术室** | 什么时候做、哪一台 | M06-05 消费 `actual_end_at`、`expected_leave_at`；回写 `actual_leave_at` |
| **M06-04 核对与交接** | 现场确认、责任转移 | M06-05 消费交接二结果；不复做核对 |
| **M09 手术麻醉**（未设计） | 术中记录、麻醉记录、术后复苏记录 | M06-05 **只做日间手术的复苏监护**；M09 若提供复苏记录则 M06-05 消费，否则自建 |
| **M06-06 结算与归档** | 结算触发、病历完整性 | M06-05 触发结算（`DEPARTED` 事件） |
| **M06-07 质量与统计** | 台数、取消率、延期率 | M06-05 提供原始数据 |

**与 M09 的边界细化（重要）**：

M09 未设计期间，M06-05 采用「本地记录 + 接口预留」策略：

| 数据 | 当前来源 | M09 就绪后 |
|---|---|---|
| 手术结束时刻 | M06-03 `actual_end_at`（M09 回写） | 同 |
| 麻醉方式与用药 | M06-03 本地快照 | M09 `GET /internal/v1/m09/anesthesia/{schedule_id}` |
| 术中出血量 | M06-03 本地字段 | M09 提供 |
| 复苏室监护记录 | **M06-05 本地记录** | ⚠️ M09 若自建则本模块降级为消费方 |
| 离院评估 | **M06-05 本地记录** | 不回退（离院是日间业务，不属于手术麻醉） |

**明确一件事**：**离院评估永远归 M06-05**，因为"能不能回家"是日间手术业务判断，不是麻醉复苏判断。即便 M09 提供 PADSS 评分，M06-05 仍要基于它做日间特有的眼科专项评估。

### 1.4 概念辨析

| 概念 | 定义 | 容易混淆的对象 |
|---|---|---|
| **复苏** | 麻醉药物作用消退、生命体征趋于稳定的过程 | 不是"休息"，是有医学标准的观察期 |
| **苏醒** | 意识恢复、能应答 | 不是复苏完成，苏醒≠可离院 |
| **Aldrete 评分** | 麻醉后复苏评分（活动/呼吸/循环/意识/氧饱和，0~10 分） | 用于判断**何时可以出复苏室**，不是离院 |
| **PADSS 评分** | 离院评分（生命体征/活动/疼痛/恶心/出血/排尿，0~10 分） | 用于判断**何时可以离院**，≥9 分才达标 |
| **留观** | 手术后到实际离院的时间段 | 不等于复苏（复苏是其中前半段） |
| **延期离院** | 超过计划离院时间仍不能离院 | 不等于"转住院"（后者是业务形态变更） |
| **非计划再就诊** | 离院 72 小时内因手术相关问题再回院 | 不等于"复诊"（复诊是计划内的随访） |
| **离院交代** | 告知患者术后注意事项并确认理解 | 不等于"出院小结"（那是书面文书） |

**重点：Aldrete 与 PADSS 不是一回事。**

- Aldrete ≥9 分 → 可以离开复苏室，回到日间病房（或直接准备离院）
- PADSS ≥9 分 → 可以离院

很多医院把两者混用，导致"复苏室出来就让人回家"的差错。日间手术的标准流程是：

```
手术结束 → 入复苏室 → 每 15 分钟评估 Aldrete
   → Aldrete ≥9 分 → 出复苏室，回日间病房
   → 在病房继续观察（眼压、视力、出血）
   → 达到计划留观时长（通常 2~4 小时）
   → 做 PADSS 评估
   → PADSS ≥9 分且眼科专项达标
   → 离院交代 → 签字 → 离院登记
```

**本院特殊处理**：眼科日间手术多数为局麻/表面麻醉，Aldrete 评分意义有限（患者全程清醒）。所以本院采用：

- 全麻/静脉镇静 → 完整 Aldrete 评分
- 局麻/表面麻醉 → 简化监护（只记录生命体征与眼科专项）

这一点在 §3.3 会详细展开。

### 1.5 模块目标

| 指标 | 目标值 | 当前（纸质/人工） | 说明 |
|---|---|---|---|
| 留观记录完整率 | ≥99% | 约 70% | 纸质记录常漏填 |
| 离院评估完成率 | **100%** | 约 85% | 未评估就离院在法律上不可接受 |
| 离院交代签字率 | **100%** | 约 60% | 纸质交代单常丢失 |
| 平均留观时长 | ≤180 分钟 | 未知 | 效率指标 |
| 延期离院率 | ≤8% | 未知 | 安全与效率双重信号 |
| **非计划再就诊率** | **≤2%** | 未知 | **离院判定质量核心反向指标** |
| 随访计划生成率 | **100%** | 约 40% | 手工登记，经常遗漏 |
| 离院评估耗时 | ≤5 分钟 | 约 10 分钟 | 效率指标 |

**三个 100% 说明**：留观记录完整率允许 99%（个别患者极不配合记录），但离院评估完成率、离院交代签字率、随访计划生成率必须是 100% —— 这三个是法律与安全底线，缺一条就构成流程漏洞。

### 1.6 关键业务角色

| 角色 | 在 M06-05 的职责 | 关键动作 |
|---|---|---|
| **麻醉医生** | 复苏期医疗责任 | 评估 Aldrete、处理麻醉相关并发症、签署复苏记录 |
| **复苏室护士** | 留观监护执行 | 每 15 分钟记录体征、初步判断异常、上报医生 |
| **日间病房护士** | 回病房后的观察与离院执行 | 继续观察、做 PADSS 评估、做离院交代、登记离院 |
| **日间病房护士长** | 离院审批 | 审核离院评估结论、签字放行 |
| **手术医生** | 医嘱与并发症处置 | 开具术后用药、处理出血/眼压异常、决定是否延期离院 |
| **医务科** | 纠纷调查与制度监督 | 查阅离院记录、处理非计划再就诊案例 |

| 编号 | 依赖 | 超时 | 失败影响 | 降级策略 |
|---|---|---|---|---|
| U-01 | M06-03 `schedule/{id}` | 2s | 无法确定术式与手术结束时刻 | **阻断**（没有台次就没有复苏记录） |
| U-02 | M06-04 `handover/{apply_id}` | 2s | 无法确认交接二完成 | 允许护士手工确认（记录降级标记） |
| U-03 | M01-07 `followup-rule` | 2s | 无法生成随访计划 | 用默认规则（1/7/30 天）+ WARN |
| U-04 | M03-04 `plans/trigger` | 3s | 随访计划未生成 | Celery 重试 5 次；仍失败进补偿队列 |
| U-05 | M03-05 `message/send` | 2s | 患者收不到离院提醒 | 异步重试，页面提示"短信发送中" |
| U-06 | M01-02 `employee` | 1s | 无法校验资质 | 用本地缓存快照 |
| U-07 | M02-06 `audit` | 1s | 审计未记录 | 异步补偿队列 |
| U-08 | M06-01 `apply/{id}/brief` | 2s | 无法回写申请单状态 | Celery 重试 3 次 |

**关键原则：M06-05 的所有外部依赖都不阻断"记录"本身。**

患者在复苏室需要记录体征这一刻，系统挂了不能导致护士无法记录 —— 那会逼着护士回到纸质。所以：

- 监护记录、离院评估、离院交代**全部本地落库，不依赖任何外部服务**
- 只有「随访计划生成」与「通知患者」是外部动作，失败可重试
- **唯一阻断项是 U-01**：没有台次就不知道该给谁做复苏记录

## 3. 业务模型

### 3.1 留观主模型

一次日间手术对应**一条留观记录**（`m06_recovery`），记录从入复苏室到实际离院的完整过程。

```
手术结束 actual_end_at
   │
   ▼
入复苏室 ──── m06_recovery.create（recovery_start_at）
   │              │
   │              ├── m06_recovery_vital（每 15 分钟一条）
   │              ├── m06_recovery_eye（眼科专项，每次评估一组）
   │              └── m06_recovery_score（Aldrete / PADSS 评分）
   │
   ▼
出复苏室 ──── recovery_end_at（Aldrete ≥9）
   │
   ▼
病房留观 ──── 继续 m06_recovery_vital / m06_recovery_eye
   │
   ▼
离院评估 ──── m06_discharge（PADSS + 眼科专项）
   │
   ▼
离院交代 ──── m06_discharge_instruction（患者签字）
   │
   ▼
实际离院 ──── actual_leave_at
   │
   ▼
随访计划 ──── m06_followup_plan（调 M03-04）
```

**为什么留观主记录与离院评估分两张表**：

| 理由 | 说明 |
|---|---|
| 生命周期不同 | 留观从入复苏室开始，离院评估只在最后一刻做一次 |
| 责任人不同 | 留观由复苏室护士，离院评估由日间病房护士 |
| 一张表会让空值太多 | 若合并，离院评估的 20 多个字段在留观期间全是 NULL |
| 允许"未完成离院评估"状态独立查询 | `m06_discharge` 有空记录 = 做了评估但未完成，一目了然 |

### 3.2 留观阶段模型

```
┌──────────────┐   Aldrete    ┌──────────────┐   PADSS    ┌──────────────┐
│ RECOVERY_ROOM│──────────────►│  WARD_OBSERVE│───────────►│   DISCHARGED │
│  复苏室监护   │   ≥9 分        │  病房留观     │   ≥9 分     │   已离院      │
└──────────────┘               └──────────────┘            └──────────────┘
       │                              │                           │
       │ 异常                          │ 异常                       │
       ▼                              ▼                           ▼
┌──────────────┐               ┌──────────────┐            ┌──────────────┐
│  EXTENDED    │               │  TRANSFER    │            │ READMITTED   │
│  延长留观     │               │  转住院审批   │            │ 非计划再就诊  │
└──────────────┘               └──────────────┘            └──────────────┘
```

**阶段字段**：`phase` ∈ `RECOVERY_ROOM` / `WARD_OBSERVE` / `READY_DISCHARGE` / `DISCHARGED` / `TRANSFERRED` / `READMITTED`

**6 态定义**：

| 阶段 | 含义 | 进入条件 |
|---|---|---|
| `RECOVERY_ROOM` | 在复苏室 | 交接二完成 |
| `WARD_OBSERVE` | 已回日间病房 | Aldrete ≥9 且麻醉医生签署出室 |
| `READY_DISCHARGE` | 已通过离院评估，等待离院 | PADSS ≥9 且眼科专项达标 |
| `DISCHARGED` | 已离院 | 登记 `actual_leave_at` |
| `TRANSFERRED` | 转住院 | 转住院审批通过 |
| `READMITTED` | 非计划再就诊 | 72 小时内再就诊登记 |

**关键设计：`READY_DISCHARGE` 单独一档。**

真实场景：患者上午 11:00 通过离院评估，但家属 14:00 才来接。中间这 3 小时患者状态是什么？如果是 `WARD_OBSERVE`，会被误认为"还没评估完"；如果是 `DISCHARGED`，实际还没走。

单独一档后：
- 床位显示"待离院"（护士知道这个床位可以准备给下一台了，但还不能真让出）
- 统计"从达标到实际离院"的等待时间（家属接送效率）
- 若在 `READY_DISCHARGE` 期间出现新症状，可以退回 `WARD_OBSERVE`

### 3.3 Aldrete 评分模型

**Aldrete 评分（麻醉后复苏评分）**：用于判断何时可以出复苏室。

| 项目 | 2 分 | 1 分 | 0 分 |
|---|---|---|---|
| 活动能力 | 主动活动四肢 | 需指令才能活动两个肢体 | 无法活动 |
| 呼吸 | 深呼吸咳嗽 | 呼吸浅但正常 | 呼吸暂停/需辅助 |
| 循环（血压） | 术前基础值 ±20% | ±20%~50% | ±50% 以上 |
| 意识 | 完全清醒 | 可唤醒 | 无应答 |
| 氧饱和度 | >92% 吸空气 | 需吸氧维持 >90% | <90% 即使吸氧 |

**总分 10 分，≥9 分可出复苏室。**

**本院眼科特殊处理**：

眼科日间手术 80% 以上采用表面麻醉 / 局部浸润麻醉 / 球后阻滞，患者全程清醒，**Aldrete 评分意义有限**。所以本院按麻醉方式分流：

| 麻醉方式 | 监护强度 | 是否评 Aldrete |
|---|---|---|
| `GENERAL` 全麻 | 全套监护（监护仪 + 每 15 分钟记录） | ✅ 必须评 |
| `SEDATION` 静脉镇静 | 全套监护 | ✅ 必须评 |
| `COMBINED` 联合麻醉 | 全套监护 | ✅ 必须评 |
| `PERIBULBAR` / `RETROBULBAR` / `SUBTENON` / `NERVE_BLOCK` | 基础监护（每 30 分钟） | ❌ 不评，只记录生命体征 |
| `SURFACE` / `LOCAL_INFILTRATION` | 简化监护（每 60 分钟） | ❌ 不评 |

**为什么局部麻醉还要监护**：球后阻滞可能引起眼心反射（心率骤降）、球后出血；表面麻醉可能引起迷走神经反应。监护强度低但不等于不监护。

### 3.4 眼科专项观察模型

这是 M06-05 里**最眼科特异的部分**。普通外科术后看切口，眼科术后看的是「**眼内压、视力、前房、敷料**」。

| 观察项 | 代码 | 正常范围 | 异常信号 |
|---|---|---|---|
| 眼压 | `IOP` | 10~21 mmHg | >25 或 <5（低眼压提示渗漏） |
| 视力 | `VA` | ≥术前或接近术前 | 明显下降（提示眼内炎/出血/晶体脱位） |
| 前房 | `AC` | 深、清 | 变浅（提示切口渗漏/恶性青光眼）、积血、渗出 |
| 敷料 | `DRESSING` | 干燥在位 | 渗血、脱落、污染 |
| 结膜出血 | `CONJ_HEMORRHAGE` | 轻度 | 大片新鲜出血 |
| 眼睑肿胀 | `LID_EDEMA` | 轻度 | 明显肿胀睁眼不能 |
| 疼痛 | `PAIN` | VAS ≤3 | VAS ≥7 |
| 恶心呕吐 | `NAUSEA` | 无 | 频繁呕吐（眼压升高） |

**为什么眼压是核心**：

白内障术后眼压升高是最常见的并发症（发生率 5%~15%），原因是粘弹剂残留。如果不及时发现，持续高眼压可在数小时内损伤视神经。

**低眼压同样危险**：切口渗漏导致低眼压，可引起脉络膜脱离、黄斑水肿。

所以眼压的观察是 `眼压必须落在 5~25 mmHg`，两端都查。

**眼科专项评估的时点**：

| 时点 | 内容 | 责任人 |
|---|---|---|
| 入复苏室即刻 | 眼压、视力、敷料 | 复苏室护士 |
| 每 30 分钟（复苏室） | 眼压（重点）、敷料 | 复苏室护士 |
| 出复苏室 | 眼压、视力、前房 | 麻醉医生 + 护士 |
| 病房每 1 小时 | 眼压、敷料、疼痛 | 日间病房护士 |
| **离院评估** | 全部 8 项 | 日间病房护士 + 医生 |

### 3.5 PADSS 离院评分模型（改良版）

**PADSS（Post Anesthetic Discharge Scoring System）** 标准 6 项：

| 项目 | 2 分 | 1 分 | 0 分 |
|---|---|---|---|
| 生命体征 | 血压/心率在基础值 ±20% 内 | ±20%~40% | ±40% 以上 |
| 活动能力 | 步态平稳无头晕 | 需搀扶 | 无法站立 |
| 疼痛（VAS） | ≤3 | 4~6 | ≥7 |
| 恶心呕吐 | 无 | 轻度 | 中重度/频繁 |
| 出血 | 无或少量 | 中等 | 多量 |
| 自主排尿 | 已排尿且正常 | 有排尿困难 | 无尿 |

**总分 10 分（部分医院用 12 分制含进食），≥9 分可离院。**

**本院改良点：增加第 7 项「眼科专项」**

| 眼科专项 | 2 分 | 1 分 | 0 分 |
|---|---|---|---|
| 眼压 | 10~21 mmHg | 22~25 或 5~9 | >25 或 <5 |
| 视力 | ≥术前（或预期） | 略低于预期但不影响行动 | 明显下降 |
| 前房 | 深浅正常、清 | 轻度浅或轻度渗出 | 明显变浅/积血 |
| 敷料 | 干燥在位 | 少量渗血 | 脱落/明显渗血 |

**第一项眼压是硬门槛**：无论 PADSS 总分多少，眼压不在 `5~25` 区间一律不可离院。

**为什么眼科要单独加项**：标准 PADSS 是麻醉复苏的通用评估，不看手术部位。白内障患者完全可能 PADSS 10 分但眼压 35 mmHg。若只看 PADSS，会放走一个需要在院观察的患者。

### 3.6 离院判定算法

```
输入：留观记录 + 最新体征 + 最新眼科专项 + PADSS 七项评分
输出：DISCHARGEABLE / OBSERVE_MORE / TO_INPATIENT

① 硬门槛（任一不满足 → TO_INPATIENT 或 OBSERVE_MORE）
   1.1 眼压 ∉ [5, 25]           → OBSERVE_MORE（先降眼压，2 小时后复查）
   1.2 眼压 >30 且用药无效       → TO_INPATIENT
   1.3 视力较术前下降 ≥2 行      → TO_INPATIENT（怀疑眼内炎/出血）
   1.4 前房明显变浅或积血         → TO_INPATIENT
   1.5 出血持续活动              → TO_INPATIENT
   1.6 生命体征：收缩压 >180 或 <90
                 心率 >120 或 <50
                 体温 >38.5℃      → OBSERVE_MORE

② PADSS 评分
   2.1 总分 ≥9 且 无 0 分项  → 通过
   2.2 总分 ≥9 但 有 0 分项  → 不通过（0 分项必须处置）
   2.3 总分 7~8             → OBSERVE_MORE
   2.4 总分 ≤6              → TO_INPATIENT

③ 留观时长
   3.1 实际留观 < 计划最短留观时长 → 不通过（即使 PADSS 满分）
        白内障 120 分钟 / 玻切 240 分钟 / 注药 60 分钟

④ 麻醉方式
   4.1 全麻/镇静：距末次给药 < 120 分钟  → 不通过
        理由：麻醉药物可能再分布，出现二次镇静

⑤ 陪护条件
   5.1 无陪护人（且非独居可自理）        → 需社工介入或转住院
   5.2 陪护人未到场                      → 不能离院

判定：
   全部通过 → DISCHARGEABLE
   有可处置项（①②③④）→ OBSERVE_MORE（处置后重新评估）
   有不可处置项 → TO_INPATIENT
```

**为什么"留观时长"是硬性条件而不是加分项**：

真实案例：白内障患者术后 40 分钟自我感觉良好，PADSS 10 分，护士放行。回家后 2 小时发生急性眼内炎。

**眼内炎的潜伏期是 2~5 天，但早期症状通常在术后 4~24 小时出现。** 留观 2 小时不能预防眼内炎，但能发现：
- 早期眼压升高（粘弹剂残留 4~6 小时内峰值）
- 早期出血（术后 1~2 小时内渗血）
- 麻醉药物的迟发反应

**所以留观时长是"最低限度观察时间"，不是"评估合格就能提前走"。**

### 3.7 延期离院模型

**触发条件**（任一）：
- 离院评估判定为 `OBSERVE_MORE` 或 `TO_INPATIENT`
- 患者主动要求延期（如家属未到）
- 医生认为需要继续观察

**延期离院流程**：

```
① 发起（护士/医生）
   ├── 延期原因（必选）
   ├── 预计离院时间
   └── 补充说明（≥10 字）
            │
            ▼
② 通知
   ├── 通知家属（M03-05 短信/电话）
   ├── 通知手术医生
   ├── 通知麻醉医生（如为麻醉相关）
   └── 通知床位管理（M06-05 内部）
            │
            ▼
③ 审批（护士长）
   ├── ≤2 小时：护士长直接确认
   ├── 2~6 小时：护士长 + 手术医生
   └── >6 小时或转住院：医务科
            │
            ▼
④ 处置
   ├── 继续留观 → 回到 WARD_OBSERVE
   ├── 转住院  → 调 M05 建住院单（未实现则本地标记 + 通知）
   └── 出院    → 继续评估流程
```

**8 类延期原因**：

| 代码 | 中文 | 是否可自动判断 |
|---|---|---|
| `IOP_HIGH` | 眼压偏高 | ✅ |
| `VISION_DROP` | 视力下降 | ✅ |
| `BLEEDING` | 出血未止 | ✅ |
| `PAIN_UNCONTROLLED` | 疼痛未控制 | ✅ |
| `NAUSEA_SEVERE` | 恶心呕吐严重 | ✅ |
| `VITAL_UNSTABLE` | 生命体征不稳 | ✅ |
| `NO_COMPANION` | 无陪护人 | ✅ |
| `PATIENT_REQUEST` | 患者要求延期 | ❌ 人工 |
| `DOCTOR_DECISION` | 医生决定留观 | ❌ 人工 |
| `OTHER` | 其他 | ❌ 人工 |

### 3.8 离院交代模型

离院交代是**法律责任的关键一环**。告知了没记 = 没告知。

**交代四大类**：

| 类别 | 内容 | 是否强制签字 |
|---|---|---|
| **用药交代** | 药名、用法、频次、疗程、注意事项 | ✅ |
| **复诊安排** | 复诊时间、地点、找谁、挂号方式 | ✅ |
| **紧急提示** | 出现什么情况必须立即就诊 | ✅ **最重要** |
| **禁忌事项** | 术后不能做什么（揉眼、低头、剧烈运动等） | ✅ |

**紧急提示的标准内容（按术式区分）**：

| 术式 | 必须告知的紧急情况 |
|---|---|
| 白内障 | 剧烈眼痛 / 视力骤降 / 恶心呕吐伴眼痛 / 大量出血 |
| 玻璃体腔注药 | 视力持续下降 / 眼红加重 / 出现黑影增多 / 眼痛 |
| 玻璃体切割 | 眼痛剧烈 / 视力骤降 / 出现闪光感 / 大量出血 |
| 青光眼 | 眼痛头痛伴恶心 / 视力骤降 |
| 翼状胬肉 | 大量出血 / 剧烈疼痛 |

**为什么强调"恶心呕吐伴眼痛"**：这是急性高眼压的典型表现，患者往往以为是胃肠问题，延误就诊。

**签字确认方式**：

| 方式 | 适用 | 数据 |
|---|---|---|
| `PATIENT_SIGN` | 患者本人能签 | 手写签名图片 |
| `SURROGATE_SIGN` | 患者不能签（视力差/高龄） | 家属手写 + 关系 |
| `ORAL_CONFIRM` | 患者无法签字（极少数） | 护士记录 + 见证人 |

**全部记录"已理解"确认**：不是签个字就完事，护士要逐项确认患者理解了。

### 3.9 随访计划生成模型

**触发时机**：离院登记成功后立即触发（异步，不阻断离院）。

**随访规则来源**：M01-07 `md_operation_followup_rule`

| 术式 | 随访天数 | 方式 |
|---|---|---|
| 白内障超声乳化 | 1 / 7 / 30 | 门诊 |
| 玻璃体腔注药 | 1 / 30 | 门诊 |
| 玻璃体切割 | 1 / 7 / 30 / 90 | 门诊 |
| 青光眼手术 | 1 / 7 / 30 | 门诊 |
| 翼状胬肉 | 7 / 30 | 门诊 |
| 斜视矫正 | 7 / 30 / 90 | 门诊 |

**调 M03-04 的参数**：

```json
{
  "trigger_source": "M06",
  "trigger_type": "DAY_SURGERY_DISCHARGE",
  "source_id": "DS20261024000012",
  "patient_id": 1024,
  "followup_days": [1, 7, 30],
  "followup_mode": "OUTPATIENT",
  "dept_id": 301,
  "doctor_id": 5012,
  "baseline_date": "2026-10-24",
  "extras": {
    "operation_code": "CATARACT_PHACO",
    "operation_name": "白内障超声乳化摘除+人工晶体植入术",
    "eye_side": "OD",
    "emergency_contact": "0710-1234567"
  }

```

**降级**：M03-04 不可用时，M06-05 先在本地生成 `m06_followup_plan` 记录（`sync_status='PENDING'`），由 Celery 定时任务补偿推送。

**为什么随访必须由系统生成而不是护士手工排**：

真实场景：护士离院交代时说"回去一周后来复查"，患者记住"一周后"，但没记具体哪天、找哪个医生。

系统生成后：
- 随访任务在 M03-04 里，到期自动发短信提醒
- 患者可通过 M03-06 门户查看自己的复诊安排
- 复诊时医生能直接看到"这是白内障术后 7 天复查"

**为什么 PADSS 改成满分 14 而不是标准的 12 或 10**：

标准 PADSS 是 6 项各 0~2 分共 12 分，部分版本加进食是 14 分。本院把眼科专项加入后变成 10 项共 20 分，但**判定门槛仍用"PADSS 六项 ≥9 且无 0 分项 + 眼科四项全部 ≥1 且眼压在 5~25"**，不是用总分 20 分算。

**理由**：合并算总分会让"PADSS 9 分、眼科 3 分"这种明显不能离院的情况被判为"总分 12 分通过"。分两块独立判定才安全。

```json
  "code": 0,
  "message": "success",
```

**失败：**

```json
{
  "code": "0605014",
  "message": "眼压不在安全区间，不可离院（当前 28 mmHg）",
  "data": {
    "iop": 28,
```

成功时 `code` 为整数 `0`；失败时为 7 位字符串错误码（`AABBCCC`，`AA = 06` 表示 M06）。

```python
    @classmethod
    async def create(cls, db: AsyncSession, user, body) -> Dict[str, Any]:
        """入复苏室登记。"""
        # ① 校验台次
        sch = await ScheduleClient.get_schedule(db, body.schedule_id)
        if not sch or sch["status"] != "COMPLETED":
            raise BizException("0605001", "台次不存在或未完成手术")

        # ② 校验交接二
        handover_ok = True
        if body.handover_id:
            ho = await HandoverClient.get_handover(db, body.handover_id)
            handover_ok = ho is not None and ho["status"] == "COMPLETED"
        if not handover_ok:
            logger.warning(
                "交接二未完成即入复苏室 schedule_id=%s", body.schedule_id)
            raise BizException("0605002", "交接二尚未完成")

        # ③ 幂等：同台次已有留观记录
        exists = await db.scalar(
            select(M06Recovery.id).where(
                and_(
                    M06Recovery.schedule_id == body.schedule_id,
                    M06Recovery.is_deleted.is_(False),
                )
            )
        )
        if exists:
            raise BizException("0605003", "该台次已有留观记录")

        # ④ 计算监护强度
        level, interval, need_aldrete = ANESTHESIA_MONITOR.get(
            body.anesthesia_type, ("BASIC", 30, False))
        min_obs = MIN_OBSERVE_MINUTES.get(
            sch.get("operation_code", ""), MIN_OBSERVE_MINUTES["DEFAULT"])

        # ⑤ 生成记录号
        recovery_no = await cls._next_recovery_no(db)

        # ⑥ 落库
        rec = M06Recovery(
            recovery_no=recovery_no,
            schedule_id=body.schedule_id,
            apply_id=sch["apply_id"],
            patient_id=sch["patient_id"],
            patient_name=sch["patient_name"],
            gender=sch.get("gender"),
            age=sch.get("age"),
            operation_code=sch.get("operation_code"),
            operation_name=sch["operation_name"],
            eye_side=sch["eye_side"],
            anesthesia_type=body.anesthesia_type,
            anesthesia_end_at=body.anesthesia_end_at,
            bed_no=body.bed_no,
            handover_id=body.handover_id,
            phase="RECOVERY_ROOM",
            monitor_level=level,
            vital_interval_minutes=interval,
            need_aldrete=need_aldrete,
            min_observe_minutes=min_obs,
            recovery_start_at=body.recovery_start_at,
            next_vital_due_at=(
                body.recovery_start_at + timedelta(minutes=interval)),
            created_by=user["employee_id"],
        )
        db.add(rec)
        await db.commit()
        await db.refresh(rec)

        # ⑦ 清缓存
        await redis_client.delete(
            "m06:rec:workbench:%s" % sch.get("dept_id", 0))

        return {
            "recovery_id": rec.id,
            "recovery_no": rec.recovery_no,
            "phase": rec.phase,
            "bed_no": rec.bed_no,
            "monitor_level": level,
            "need_aldrete": need_aldrete,
            "min_observe_minutes": min_obs,
            "next_vital_due_at": rec.next_vital_due_at.isoformat(),
        }

    @classmethod
    async def add_vital(
        cls, db: AsyncSession, user, recovery_id: int, body,
    ) -> Dict[str, Any]:
        """记录生命体征。"""
        rec = await cls._get_for_update(db, recovery_id)
        if rec.phase in ("DISCHARGED", "TRANSFERRED"):
            raise BizException("0605004", "留观记录状态不允许此操作")

        # ① 数值校验
        if not (60 <= body.sbp <= 260 and 30 <= body.dbp <= 180):
            raise BizException("0605005", "血压超出合理范围")
        if not (30 <= body.heart_rate <= 200):
            raise BizException("0605005", "心率超出合理范围")
        if not (33.0 <= body.temperature <= 42.0):
            raise BizException("0605005", "体温超出合理范围")
        if not (50 <= body.spo2 <= 100):
            raise BizException("0605005", "血氧饱和度超出合理范围")

        # ② 防抖
        lock_key = "m06:rec:vital:lock:%s" % recovery_id
        if not await redis_client.set(
                lock_key, "1", ex=120, nx=True):
            raise BizException("0605006", "同一患者 2 分钟内不可重复提交")

        # ③ 异常判定
        flags = cls._vital_flags(rec, body)

        # ④ 落库
        vital = M06RecoveryVital(
            recovery_id=recovery_id,
            measured_at=body.measured_at,
            sbp=body.sbp,
            dbp=body.dbp,
            heart_rate=body.heart_rate,
            temperature=body.temperature,
            spo2=body.spo2,
            respiratory_rate=body.respiratory_rate,
            consciousness=body.consciousness,
            abnormal_flags=flags,
            remark=body.remark,
            recorded_by=user["employee_id"],
        )
        db.add(vital)

        # ⑤ 更新下次记录时间
        rec.last_vital_at = body.measured_at
        rec.next_vital_due_at = (
            body.measured_at
            + timedelta(minutes=rec.vital_interval_minutes))
        await db.commit()
        await db.refresh(vital)

        return {
            "vital_id": vital.id,
            "abnormal_flags": flags,
            "remind_doctor": "BP_HIGH" in flags or "SPO2_LOW" in flags,
            "next_vital_due_at": rec.next_vital_due_at.isoformat(),
        }

    @classmethod
    def _vital_flags(cls, rec, body) -> List[str]:
        """生命体征异常标记。"""
        flags: List[str] = []
        if body.sbp > 180 or body.sbp < 90:
            flags.append("BP_HIGH" if body.sbp > 180 else "BP_LOW")
        if body.heart_rate > 120:
            flags.append("HR_HIGH")
        elif body.heart_rate < 50:
            flags.append("HR_LOW")
        if body.temperature > 38.5:
            flags.append("FEVER")
        if body.spo2 < 92:
            flags.append("SPO2_LOW")
        return flags

    @classmethod
    async def add_score(
        cls, db: AsyncSession, user, recovery_id: int, body,
    ) -> Dict[str, Any]:

        rec = await cls._get_for_update(db, recovery_id)
        if not rec.need_aldrete:
            raise BizException(
                "0605004", "该麻醉方式无需 Aldrete 评分")

        # ① 每项 0~2
        for name, val in (
            ("activity", body.activity),
            ("respiration", body.respiration),
            ("circulation", body.circulation),
            ("consciousness", body.consciousness),
            ("oxygen", body.oxygen),
        ):

                raise BizException(
                    "0605005", "Aldrete %s 评分必须在 0~2" % name)

        total = (body.activity + body.respiration + body.circulation
                 + body.consciousness + body.oxygen)

        score = M06RecoveryScore(
            recovery_id=recovery_id,
            score_type="ALDRETE",
            activity=body.activity,
            respiration=body.respiration,
            circulation=body.circulation,

            total_score=total,
            can_exit_room=(total >= 9),
            scored_at=body.scored_at,
            scored_by=user["employee_id"],
            remark=body.remark,
        )
        db.add(score)
        rec.last_aldrete = total
        await db.commit()
        await db.refresh(score)

        return {
            "score_id": score.id,
            "total_score": total,
            "can_exit_room": total >= 9,
        }

    @classmethod

        if not rec:
            raise BizException("0605042", "留观记录不存在")

    @classmethod
    async def _next_recovery_no(cls, db) -> str:
        today = date.today()
        key = "m06:rec:seq:%s" % today.strftime("%Y%m%d")
        seq = await redis_client.incr(key)
        await redis_client.expire(key, 172800)
        return "RC%s%04d" % (today.strftime("%Y%m%d"), seq % 10000)

    @classmethod
    async def workbench(cls, db, user, dept_id) -> Dict[str, Any]:
        """复苏监护工作站。"""
        cache_key = "m06:rec:workbench:%s" % (dept_id or 0)
        cached = await redis_client.get(cache_key)
        if cached:
            return cached

        stmt = select(M06Recovery).where(
            M06Recovery.is_deleted.is_(False),
            M06Recovery.phase == "RECOVERY_ROOM",
        ).order_by(M06Recovery.last_vital_at.asc().nullsfirst())
        rows = (await db.scalars(stmt)).all()

        now = datetime.now()
        items = []
        for r in rows:
            waited = int((now - r.recovery_start_at).total_seconds() / 60)
            last_gap = (
                int((now - r.last_vital_at).total_seconds() / 60)
                if r.last_vital_at else waited)
            items.append({
                "recovery_id": r.id,
                "bed_no": r.bed_no,
                "patient_name": r.patient_name,
                "operation_name": r.operation_name,
                "eye_side": r.eye_side,
                "recovery_start_at": r.recovery_start_at.isoformat(),
                "observe_minutes": waited,
                "last_vital_minutes": last_gap,
                "last_aldrete": r.last_aldrete,
                "status": (
                    "CAN_EXIT" if (r.need_aldrete and (r.last_aldrete or 0) >= 9)
                    else "MONITORING"),
            })

        result = {
            "biz_date": str(date.today()),

    @classmethod
    def _check_gates(cls, db, rec, body) -> Dict[str, bool]:
        """硬门槛检查。"""
        now = datetime.now()
        waited = int((now - rec.recovery_start_at).total_seconds() / 60)
        gates = {}

        # 眼压
        gates["iop_in_range"] = (
            body.iop_value is not None
            and 5 <= body.iop_value <= 25)
        # 视力
        if rec.preop_vision is not None and body.vision_value is not None:
            gates["vision_not_dropped"] = (
                body.vision_value >= rec.preop_vision)
        else:
            gates["vision_not_dropped"] = True
        # 前房
        gates["anterior_chamber_ok"] = body.eye_ac >= 1
        # 出血
        gates["no_active_bleeding"] = body.padss_bleeding >= 1
        # 生命体征
        gates["vitals_stable"] = body.padss_vital >= 1
        # 留观时长
        gates["observe_duration_ok"] = (
            waited >= rec.min_observe_minutes)
        # 麻醉间隔
        if rec.anesthesia_type in ("GENERAL", "SEDATION", "COMBINED") \
                and rec.anesthesia_end_at:
            gap = int(
                (now - rec.anesthesia_end_at).total_seconds() / 60)
            gates["anesthesia_interval_ok"] = gap >= 120
        else:
            gates["anesthesia_interval_ok"] = True
        # 陪护
        gates["companion_ready"] = bool(body.companion_name)

        return gates
```

### 6.7 专题：为什么离院判定要分成"硬门槛 + 评分"两层

**如果只用 PADSS 总分判定会出什么事：**

真实场景推演（白内障术后 90 分钟）：

| 项 | 分 | 说明 |
|---|---|---|
| 生命体征 | 2 | 血压心率正常 |
| 活动能力 | 2 | 步态平稳 |
| 疼痛 | 2 | VAS 2 |
| 恶心呕吐 | 2 | 无 |
| 出血 | 2 | 无 |
| 自主排尿 | 2 | 正常 |
| **眼压** | **0** | **38 mmHg（严重偏高）** |
| 视力 | 2 | 符合预期 |
| 前房 | 2 | 深清 |
| 敷料 | 2 | 干燥 |

PADSS 六项 = 12 分（满分），眼科四项 = 6 分。

**若按总分判定**：18/20 分，通过 → 患者回家 → 当晚急性高眼压损伤视神经。

**若按两层判定**：眼压 38 是硬门槛（不在 5~25）→ 不通过 → 继续留观或转住院。

**这就是为什么硬门槛必须独立于评分：**

| 判定层 | 特点 | 例子 |
|---|---|---|
| **硬门槛** | 单项否决，不能被其他项的高分抵消 | 眼压、视力、前房、出血 |
| **评分** | 综合评估，多项互补 | 活动、疼痛、恶心、排尿 |

**医学上这两类指标性质不同**：
- 评分项衡量"患者舒适与自理能力"，是可代偿的（疼痛 1 分但活动 2 分，总体还行）
- 硬门槛衡量"是否存在需要立即处理的风险"，不可代偿（眼压 38 再舒适也不能回家）

**在数据结构上如何体现**：

`m06_discharge` 表里 `hard_gates` 是 JSONB 字段，存八项布尔值：

```json
{
  "iop_in_range": true,
  "vision_not_dropped": true,
  "anterior_chamber_ok": true,
  "no_active_bleeding": true,
  "vitals_stable": true,
  "observe_duration_ok": true,
  "anesthesia_interval_ok": true,
  "companion_ready": true
}
```

**为什么存快照而不是实时算**：离院评估是通过或未通过都是**当时的事实**。半年后纠纷调查时，要看的是"当时检查时这些值是什么"，而不是"用今天的标准重算会怎样"。

```python
import asyncio

logger = logging.getLogger("m06.recovery.task")


@shared_task(bind=True, max_retries=5, default_retry_delay=60)
def create_followup_task(self, recovery_id: int):
    """离院后生成随访计划。"""

    async def _run():
        from app.db.session import async_session
        from app.services.m06.recovery_service import (
            RecoveryService)
        from app.services.m06.clients import FollowupClient

        async with async_session() as db:
            rec = await RecoveryService.internal_get(db, recovery_id)
            try:
                res = await FollowupClient.trigger(
                    db,
                    source_id=rec["recovery_no"],
                    patient_id=rec["patient_id"],
                    operation_code=rec.get("operation_code"),
                    baseline_date=rec["actual_leave_at"][:10],
                )
                return {"status": "SUCCESS", "plan_id": res.get("plan_id")}
            except Exception as exc:  # noqa: BLE001
                logger.error(
                    "随访计划生成失败 recovery_id=%s err=%s",
                    recovery_id, exc)
                # 落本地待补偿
                await RecoveryService.save_pending_followup(
                    db, recovery_id,
                    followup_days=[1, 7, 30])
                raise self.retry(exc=exc)

    return asyncio.run(_run())

                raise self.retry(exc=exc)

@shared_task(bind=True, max_retries=3, default_retry_delay=30)
def notify_delay_task(self, delay_id: int):
    """延期离院通知。"""

    async def _run():
        from app.db.session import async_session
        from app.models.m06 import M06Delay
        from app.services.m06.clients import MessageClient

                    targets=d.notify_targets,
                    expected_leave_at=d.expected_leave_at,
                )
                return {"status": "SUCCESS"}
            except Exception as exc:  # noqa: BLE001
                raise self.retry(exc=exc)

    return asyncio.run(_run())


@shared_task(bind=True, max_retries=5, default_retry_delay=120)
def sync_pending_followup_task(self):
    """补偿未同步的随访计划。"""

    async def _run():
        from app.db.session import async_session
        from sqlalchemy import select, text

        async with async_session() as db:
            rows = (await db.execute(text(
                "SELECT recovery_id FROM m06_followup_plan "
                "WHERE sync_status = 'PENDING' "
                "AND retry_count < 10 "
                "ORDER BY created_at LIMIT 50"
            ))).all()
            synced = 0
            for (rid,) in rows:
                try:
                    await create_followup_task.delay(rid)
                    synced += 1
                except Exception:  # noqa: BLE001
                    continue
            return {"synced": synced, "pending": len(rows)}

    return asyncio.run(_run())
```

| `job_m06_rec_clean_cache` | `0 4 * * *` | 清理过期缓存 |
| `job_m06_rec_warmup` | `0 7 * * *` | 缓存预热 |

**为什么体征超时扫描是 5 分钟粒度：**

体征录入间隔是 15~60 分钟（按麻醉方式分流），超时提醒预留 10 分钟。5 分钟扫描意味着：
- 最多 5 分钟延迟才提醒
- 一天扫描 288 次 × 4 张床 = 1,152 次查询，负载可忽略

若改成 1 分钟：一天 1,440 次，收益是提醒快 4 分钟，成本是查询量 5 倍。

**为什么手术医生没有 `execute` 权限**：

手术医生不参与留观监护执行——那是护士的工作。医生只做两件事：
- 处置异常（`dispose`）
- 查看记录（`query`/`report`）

这与 M06-04 的设计一致：执行动作由护士完成，医生只做决策与签署。

**为什么系统管理员连 `query` 都没有**：

留观记录包含患者的眼压、视力、诊断信息。系统管理员负责部署与运维，不应看到患者隐私。这与全仓最小权限原则一致。

**六个「敏感 + 只读」参数的制度来源：**

| 参数 | 依据 |
|---|---|
| `ALDRETE_MIN_EXIT` | 麻醉复苏标准（教材与行业共识） |
| `PADSS_MIN` | 日间手术离院标准（国际通行） |
| `IOP_MIN` / `IOP_MAX` | 眼科临床规范（正常眼压 10~21，安全区间 5~25） |
| `MIN_OBSERVE_*` | 本院日间手术管理制度（需院级审批） |
| `ANESTHESIA_GAP_MIN` | 麻醉安全要求（防止二次镇静） |
| `REVISIT_WINDOW_HOURS` | 质控指标定义（72 小时为行业标准） |

**这些参数不允许在系统里随便改**，如需调整必须走院级制度变更流程（医务科审批 + 留痕）。
