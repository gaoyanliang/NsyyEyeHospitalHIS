**设计说明**

1. **为什么 `m06_prepare_item_ext` 是扩展表而不是直接改 M06-01 的 `m06_prepare_item`**：
   - M06-01 的 `m06_prepare_item` 已经承载了「清单是什么」（`item_type`/`item_code`/`is_required`/`status`），这些是 M06-01 的职责（生成清单）与 M06-02 的职责（执行清单）共同需要的字段。
   - 但 M06-02 独占一批字段：`planned_at`（绝对时间）、`detail_json`（禁食详情）、`result_summary`（结果摘要）、`disposition`（处置）、`fail_reason`（失败原因）——这些字段 M06-01 完全不需要，如果塞进主表会让 M06-01 的表结构被下游需求污染。
   - 拆表后，M06-01 可以独立演进自己的清单模型，M06-02 可以独立演进自己的执行模型。**唯一代价是每次查准备详情要 JOIN 一次**（主键关联，<1ms，可接受）。

   **但注意**：`status`/`done_at`/`done_by`/`done_source`/`is_abnormal` 这几个字段**留在 M06-01 主表**，因为它们既是"清单的一部分"（M06-01 也要看准备进度来更新申请单状态）也是"执行结果"（M06-02 更新它们）。放主表让 M06-01 不用 JOIN 就能算进度。

2. **`m06_prepare_visit` 三类访视共用一张表**：
   - 麻醉访视、主刀访视、护士长放行，三者的共同点是"某人在某时对这台手术做了一个结论性判断"。
   - 差异字段（ASA、气道、晶体、告知项）放 `detail_json`。
   - 不建三张表的理由：三种访视的**查询模式完全一致**（"这台手术的访视记录"），建三张表后每个查询都要 UNION 三次，且新增一类访视（如"医务科审批"）要加一张表。
   - 用 `visit_type` 区分即可。

3. **`m06_prepare_order` 与 `m06_prepare_result` 分开**：
   - 一条医嘱（一次开单）可能对应多条结果（如"生化全套"一条医嘱出 20 个结果项）。
   - 一次开单的结果可能分多次到达（先出血常规、次日出凝血）。
   - 合并成一张表会让"一次开单 N 个结果"变成 N 行重复存 `order_id`，且无法表达"这条医嘱的结果到齐了没有"。

4. **无任何物理外键**（与 M06-01 一致）：跨子模块写入加锁影响并发；应用层事务成对写入 + 每日 04:00 孤儿巡检。

5. **`m06_prepare_item_ext` 与 `m06_prepare_item` 之间可用物理外键**：这是同一个模块（M06）内的两个表，且 ext 是 item 的严格附属（没有 item 就没有 ext）。加 `ON DELETE CASCADE` 可以保证 M06-01 删清单项时自动清理扩展行。**这是本项目里少见的加物理外键的场景**，理由是"同模块 + 强从属 + 级联删除语义明确"。

**设计要点**

1. **`planned_at` 落地为物理列而不是每次实时算**：
   - 实时算意味着每个查询都要 JOIN `m06_day_surgery` 拿 `surgery_start_at` 再算偏移，30 台手术 × 10 项 = 300 次计算，且无法建索引。
   - 落地后 `WHERE planned_at < NOW() AND actual_at IS NULL` 直接走 `idx_m06_pie_overdue`，扫描 O(log n)。

2. **`actual_at` 与主表 `done_at` 双存**：
   - 主表 `done_at` 是权威源（M06-01 也要读）。
   - 扩展表存一份让本表能独立完成"迟延分析"的查询（`ORDER BY delay_minutes DESC`），不用 JOIN 主表。
   - 用触发器保证两者同步：

```sql
CREATE OR REPLACE FUNCTION fn_m06_pie_sync_actual()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.status = 'DONE' AND NEW.done_at IS NOT NULL THEN
        UPDATE m06_prepare_item_ext
        SET actual_at = NEW.done_at,
            delay_minutes = CASE
                WHEN planned_at IS NULL THEN NULL
                ELSE FLOOR(EXTRACT(EPOCH FROM (NEW.done_at - planned_at))
                           / 60)::INT
            END
        WHERE item_id = NEW.id;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_m06_pi_sync_ext
    AFTER UPDATE OF status, done_at ON m06_prepare_item
    FOR EACH ROW EXECUTE FUNCTION fn_m06_pie_sync_actual();
```

3. **禁食详情存 JSONB 而不是拆成多列**：
   ```json
   {
     "last_solid_intake_at": "2026-10-22T19:30:00",
     "last_liquid_intake_at": "2026-10-23T06:10:00",
     "solid_intake_desc": "米饭、青菜、少量肉",
     "liquid_intake_desc": "温开水约 150ml",
     "solid_hours": 14.5,
     "liquid_hours": 3.83,
     "required_solid_hours": 8.0,
     "required_liquid_hours": 2.0,
     "patient_repeat_confirmed": true,
     "patient_note": "患者复述：明早不吃不喝"
   }
   ```
   - 禁食详情字段多（8 个）且**从不作为查询条件**（没人会 `WHERE solid_intake_desc LIKE '%米饭%'`）。
   - 结果判定用 `fasting_solid_pass` / `fasting_liquid_pass` 两个独立列（要查询、要统计）。
   - **判定结果拆出来、过程详情塞 JSONB**，是这张表最重要的设计取舍。

4. **`external_report_no` 与 `external_attachment_id` 配对约束**：
   - 外院登记必须两者都有。只有报告号没附件 → 无法追溯原件；只有附件没报告号 → 无法与报告系统对账。
   - 约束 `ck_m06_pie_external` 保证配对。

5. **`delay_minutes` 用生成列语义的手算 + CHECK 校验**：
   - 可以直接用 `GENERATED ALWAYS AS` 生成列。但 PostgreSQL 的生成列不允许跨表引用（这里只需要本表的两列，可以）。
   - 选择 `CHECK` 而非生成列的理由：**`planned_at` 会被排程变更重算**（`on-scheduled` 回调），生成列会自动重算（好事），但也意味着每次 `planned_at` 更新都触发全表重算该列。显式写入 + CHECK 校验让重算只在需要时发生。

   ```sql
   -- 若后续确认性能可接受，可改为生成列：
   -- ALTER TABLE m06_prepare_item_ext
   --     ADD COLUMN delay_minutes INT
   --     GENERATED ALWAYS AS (
   --         CASE WHEN actual_at IS NULL OR planned_at IS NULL THEN NULL
   --              ELSE FLOOR(EXTRACT(EPOCH FROM (actual_at - planned_at))
   --                         / 60)::INT
   --         END
   --     ) STORED;
   ```

6. **`timing_segment` 冗余存储而不是每次按偏移算**：
   - 分段规则（P1~P7 的边界）将来可能调整（如把 P5 从 -1440 改成 -2160）。调整后按偏移实时算会对历史数据重新分段，历史报表口径就变了。
   - 落地分段值后，历史项的分段保持不变，口径稳定。

7. **`result_value` 用 VARCHAR 而不是 NUMERIC**：
   - 检查结果有大量非数值：`眼轴 OD 23.82 / OS 23.75`、`玻璃体清，后极部平`、`未见异常`。
   - 只有数值型结果需要参与阈值判定，判定时用 `CAST(result_value AS NUMERIC)` 并在转换失败时跳过。

8. **`remind_count` 上限 20**：
   - 每 30 分钟提醒一次 → 10 小时才提醒 20 次。超过 20 次说明提醒机制本身失效（如消息通道全挂），继续计数无意义。
   - 上限防应用层 bug 无限累加。

2. **`uk_m06_po_idem` 保证幂等**：
   - 幂等键格式 `PREP-ORDER-{apply_id}-{item_id}`，由调用方传入。
   - 网络重试、用户重复点击都命中同一键，`IntegrityError` 后返回已有记录（`is_idempotent=TRUE`）。
   - 这也是 M07-03 契约要求的写法（`idempotency_key` 必传）。

3. **`order_status` 是快照不是权威**：
   - 医嘱状态的权威源在 M07-03。这里冗余一份是为了**本模块能独立回答"术前检查做了没有"**而不必每次调 M07。
   - 通过订阅 `m07.order.*` 事件更新 `sync_at`，每日 04:00 巡检不一致的（如事件丢失）触发补偿。

4. **`order_no` 正则 `^YZ[0-9]{12,20}$`**：M07-03 的医嘱号格式是 `YZ` + 12 位日期时间/序号。放宽到 12~20 位是因为 M07-03 未最终定稿数字长度，用区间兼容。

5. **为什么不让 M06-02 直接写 M07 的 `m07_order` 表**：
   - M07 的医嘱有自己的生命周期（`DRAFT → ISSUED → PAID → EXECUTING → COMPLETED`）、自己的收费联动、自己的执行方回写。
   - 直连会让 M06-02 绕过 M07 的所有业务规则（如"未见诊不能开单"、"重复开单校验"）。
   - 映射表的方式把关系显式化，也便于统计"术前检查开单量"。

**设计要点**

1. **`uk_m06_pr_result_field` 用 `COALESCE(field_code, '')`**：
   - 检查报告（如 OCT 黄斑）通常无 `field_code`，整份报告一条记录。
   - 检验结果（如生化）有多个 `field_code`，一份报告 N 条记录。
   - 不加 `COALESCE` 时，两条 `field_code IS NULL` 的记录可以共存（PostgreSQL 认为 NULL 互不相等），会产生重复。
   - **这是全项目第 6 次遇到"唯一索引必须带 COALESCE"的坑**（前 5 次：M12-06 模板、M12-04 配置、M13-02 采集配置、M13-03 解析配置、M06-01 规则）。

2. **`raw_json` 存完整原始结果**：
   - M12/M13 的报告结构可能演进（增加字段、改字段名）。快照后"当时系统看到的是什么"可完整还原。
   - 单条约 1~3 KB，年 11 万条约 300 MB，可接受。

3. **`result_value` VARCHAR + `numeric_value` NUMERIC 双列**：
   - `result_value` 是原文（"12.8"、"<0.5"、"阴性"），用于展示与追溯。
   - `numeric_value` 是转换后的数值，用于阈值比较。无法转换时 NULL。
   - 分开存避免"为了比较而丢失原文格式"。

4. **`severity` 四档（含 `PASS`）而不是三档**：
   - M06-01 的准入判定用三档（BLOCK/WARN/INFO）。
   - 术前检查检验需要显式表达"判过了且通过（PASS）"，否则无法区分"还没判"和"判了没问题"。

5. **`ck_m06_pr_flag_ref` 要求 HIGH/LOW 必须有参考区间**：
   - "偏高"这个判定没有参考区间作为依据是不可信的。
   - 如果 M13-05 没配区间，系统应只显示数值不标高低（降级），而不是标个没依据的 HIGH。

6. **`sync_source` 三值区分事件/轮询/手工**：
   - 事件驱动（99%）应该占绝大多数。
   - 轮询占比超过 5% 说明事件通道有问题，是重要运维指标。
   - 手工同步用于排查"结果明明出来了但系统没关联"。

| 年数据量 | 约 497 MB |
| 15 年数据量 | 约 7.5 GB |
| 索引开销 | 约 3.5 GB |
| **合计** | **约 11 GB** |

**设计要点**

1. **`uk_m06_pv_apply_type` 保证一单每类一条**：
   - 一个患者只能有一份麻醉访视、一份主刀访视、一次放行。
   - 重复提交应该是"更新"而不是"新增"。应用层用 upsert 实现，唯一索引兜底防并发插入两条。

2. **`conclusion` 的合法值随 `visit_type` 变化**：
   - 访视：`FEASIBLE`/`ADJUST`/`INFEASIBLE`
   - 放行：`RELEASE`/`DELAY`
   - 用 CHECK 约束把三种类型的合法结论分开，比建三张表省事，又比"允许任意字符串"严谨。

3. **`is_submitted` 支持草稿**：
   - 麻醉访视要填 10+ 个字段，医生可能填到一半被叫走。
   - 草稿不算完成（不影响就绪判定），只有 `is_submitted=TRUE` 才算。
   - 与 M06-01 的申请单草稿逻辑一致。

4. **`visitor_role` 存角色码快照**：
   - 员工角色会变（升职、调岗）。事后追溯"当时他是什么角色"很重要。
   - 尤其是放行——"当时这个人是不是护士长"决定了放行是否有效。

5. **`client_ip` 用 INET**：
   - 与 M06-01 一致。医疗纠纷场景里，什么时间从哪台机器做了什么操作，是关键证据。
   - 大屏终端与管理终端的 IP 段不同，也能用来排查"谁在手术室大屏上误操作了"。

6. **为什么三类访视共用表而不是三张表**：
   - 共同字段 12 个（appy_id/ds_no/visit_time/visitor/conclusion/remark/ip/trace），差异全部在 `detail_json`。
   - 三张表意味着三个 ORM 类、三套路由、三个 Service，以及"查这台手术的全部访视"要 UNION。
   - **一张表 + `visit_type` 让查询、统计、权限都统一**。

**设计要点**

1. **为什么既要 `m06_prepare_item_ext.disposition` 又要 `m06_prepare_dispose`**：
   - `ext.disposition` 是**当前有效处置**的单值缓存。就绪判定只需读这一个字段（`WHERE disposition IS NOT NULL` 判断是否已闭环），不用 JOIN 处置表。
   - `m06_prepare_dispose` 是**完整历史**。撤销后重处置、多次处置，都能追溯。
   - 这是典型的"当前态 + 历史表"模式：查询用当前态（快）、追溯用历史表（全）。

2. **`uk_m06_pd_item_active` 保证一准备项同时只有一条有效处置**：
   - 撤销后（`is_revoked=TRUE`）才能插入新处置。
   - 防并发：两个医生同时处置同一项，唯一索引拦住第二个。

3. **`ck_m06_pd_exclusive` 强制处置专属字段互斥**：
   - `RESOLVED` 有 `intervention`，`RECHECK` 有 `recheck_*`，`REFER` 有 `refer_dept_id`，`DEFER` 有 `new_surgery_date`。
   - 不允许"处置选了 RESOLVED 但也填了 recheck_item_code"——那种记录在报表里会被算两次。

4. **撤销而不是修改**：
   - 处置是医疗决策记录。改过了就说不清"当初是怎么判的"。
   - 撤销时保留原记录（`is_revoked=TRUE` + 撤销原因 ≥10 字），新处置是另一条记录。
   - 与 M06-01 的 `INELIGIBLE` 终态设计一致：**保留历史比修改历史更重要**。

5. **`notify_status` 三态跟踪通知 M06-01**：
   - `DEFER`/`REFER` 必须通知 M06-01 触发改期/取消。
   - 通知失败（M06-01 挂、消息丢）时进补偿队列，`notify_status='FAILED'` 有部分索引可扫。
   - 与 M16-01 的"支付成功回写失败不回滚支付"同理：**本地决策先落地，跨模块通知异步补偿**。

6. **`dispose_by_role` 存角色快照**：
   - 必须是医生才能处置（`ALLOWED_ROLES`）。
   - 事后追溯"这个人当时是不是医生"——如果角色有变更（离职、转岗），这条记录能证明当时合规。

7. **`abnormal_value` / `ref_range` 冗余存**：
   - 处置时的异常值与参考区间，可能后来又变了（如患者复查了）。冗余快照让处置记录本身自洽。
   - 处置单可以作为"医生看到了什么、判断了什么"的独立证据。

**提醒类型与对象**

| 类型 | 中文 | 时点 | 层级 | 接收对象 |
|---|---|---|---|---|
| `T7_ORDER` | 该开检查检验单了 | T-7 天 | 1 | 门诊医生 |
| `T3_RESULT` | 结果已回报，查看异常 | T-3 天 | 1 | 门诊医生 |
| `T2_VISIT` | 待麻醉访视 | T-2 天 | 1 | 麻醉医生 |

| `T1_PATIENT` | 患者提醒 | T-1 天 | 1 | 患者（经 M03-05） |
| `T0_MORNING` | 今日手术提醒 | T-0 06:00 | 1 | 日间病房护士 |

**设计要点**

1. **`uk_m06_prm_key` 是提醒幂等的关键**：
   - `(apply_id, COALESCE(item_id, 0), remind_type, remind_level)` 唯一。
   - 定时任务每 5 分钟扫一次，同一提醒不会因为扫描多次而重复发送。
   - `COALESCE(item_id, 0)` 再次出现——本次是**全项目第 7 次**遇到同一问题。

2. **`remind_level` 用层级而非计数**：
   - 同一类型的提醒有 3 个层级（L1 责任人→L2 护士长→L3 医务科），每层一条记录。
   - 用 `remind_count` 单条记录 + 升级字段也行，但那样无法记录"护士长那份提醒是什么时候发的、确认了没有"。
   - 三层各一条记录，每层独立确认，审计清晰。

3. **`is_obsolete` 与 `send_status` 分离**：
   - 项已完成 → `is_obsolete=TRUE`，取消未发送的提醒。
   - 已发送但项已完成 → 保留记录（历史），但不再触发升级。
   - 两个字段表达"提醒还在不在生命周期内"和"发没发出去"两件不同的事。

4. **`receiver_ids` / `receiver_roles` 用数组**：
   - 一条提醒可能发给多人（如 PRE_15M 发给护士长 + 手术室护士）。
   - 用数组避免"N 个接收人 N 条记录"，且按角色（`receiver_roles`）可以动态解析当时在岗的人。
   - `receiver_roles` 与 `receiver_ids` 至少一个非空（`ck_m06_prm_receiver`）。

5. **`send_attempts` 上限 10**：
   - Celery 重试 5 次 + 人工重试，10 次足够。
   - 超过说明消息通道不可用，继续重试无意义。

**分区定义**

```sql
DO $$
DECLARE
    v_start DATE := DATE '2026-10-01';
    v_i INT;
    v_name TEXT;
    v_from DATE;
    v_to DATE;
BEGIN
    FOR v_i IN 0..35 LOOP
        v_from := (v_start + (v_i || ' months')::INTERVAL)::DATE;
        v_to := (v_from + '1 month'::INTERVAL)::DATE;
        v_name := 'm06_prepare_log_' || TO_CHAR(v_from, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m06_prepare_log '
            'FOR VALUES FROM (%L) TO (%L)',
            v_name, v_from, v_to
        );
        EXECUTE FORMAT('COMMENT ON TABLE %I IS %L',
            v_name,
            'm06_prepare_log 分区 ' || TO_CHAR(v_from, 'YYYY-MM'));
    END LOOP;
END $$;
```

**设计要点**

1. **只增触发器优于应用层保护**：
   - 应用层可绕过（DBA 手动改、其他服务误写、迁移脚本）。
   - 触发器在数据库层，任何绕过都会抛异常。
   - 与 M06-01 的 `m06_apply_log` 完全一致的模式。

2. **`from_value` / `to_value` 与 `before_json` / `after_json` 双轨**：
   - 状态类变更（ITEM_DONE）用 `from_value='PENDING'` / `to_value='DONE'` 表达，简洁可索引。
   - 复杂变更（VISIT_ANESTHESIA 提交 10 个字段）用 JSON 快照，完整可回放。
   - 两套并存的代价是冗余，收益是"日常查询用前者（走索引）、深度追溯用后者"。

3. **为什么分区而不归档**：
   - 日志的合规价值随时间衰减：2 年内日常追溯，2~15 年只在纠纷时查。
   - 分区让"只扫最近 3 个月"物理隔离，性能提升 10 倍以上。
   - 月度分区可独立归档到冷存储。

4. **`action` 列表 24 种（超出注释说 22 种）**：
   - 覆盖准备项（6）、医嘱（5）、结果（3）、处置（2）、访视（3）、提醒（3）、判定与导出（2）。
   - 枚举固定，新增操作类型需 ALTER 约束——这是有意的"摩擦"，防止随意加操作类型导致统计口径混乱。

**分区：** 按 `seq_date` 月度 RANGE 分区，预建 36 个月。保留 15 年（180 个分区），在线热数据 180 天。
