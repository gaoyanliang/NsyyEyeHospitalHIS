## 1. 模块概述

### 1.1 模块定位

**M06 回答一个问题：患者当天来、当天做、当天走，这一整天怎么组织。**

日间手术不是「缩短版的住院」，而是介于门诊与住院之间的独立业务形态：

| 维度 | 门诊 | **日间手术** | 住院 |
|---|---|---|---|
| 患者停留 | 看完就走 | **当天入院、当日手术、当日或次日出院（≤24 小时）** | 数天到数周 |
| 责任主体 | 门诊医生 | **主刀 + 麻醉医生 + 日间病房护士 + 手术室护士，四方交接** | 主管医生 + 病区 |
| 关键风险 | 诊断错误 | **术前准备漏项（未禁食/未散瞳/未停抗凝）、术眼错误、术后离院过早** | 院内感染、并发症 |
| 收费模式 | 门诊结算，开单即结 | **日间手术结算（M16-03 `admission_type='DAY_SURGERY'`）** | 住院结算，按天累计 |
| 病历要求 | 门诊病历 | **完整住院病历 18 项，保存 30 年** | 住院病历 30 年 |
| 随访 | 无强制 | **强制 1/7/30 天（M01-07 随访规则）** | 出院随访 |

**眼科是日间手术最典型的场景。** 白内障超声乳化、玻璃体腔注药、翼状胬肉切除、部分青光眼手术、斜视矫正——全部是「当天来、当天走」。一家二级眼科医院日均 30~60 台日间手术，占全部手术量的 **80% 以上**。

### 1.2 M06 的存在前提

M06 之所以是一个**模块**而非散落在门诊/住院里的功能，基于三条前提：

**前提一：日间手术有独立的业务主体。**
`m06_day_surgery`（申请单）是贯穿全流程的业务主线：申请 → 准入 → 准备 → 排程 → 核对 → 复苏 → 离院 → 结算 → 归档 → 质控。这条主线跨 7 个子模块、6 个外部模块，任何一环缺失都无法闭环。挂在门诊（M04）或住院（M05）下，会变成"门诊的一个特殊挂号类型"或"住院的一种特殊入院方式"，都无法承载独立的准入判定、术前准备闭环、四方核对、离院评估。

**前提二：日间手术的资源模型与门诊、住院都不同。**
- 门诊资源是**号源**（医生 × 时段 × 数量）；
- 住院资源是**床位**（病区 × 床位 × 日期）；
- 日间资源同时需要 **手术间 + 台次 + 主刀 + 麻醉医生 + 器械护士 + 日间病房床位**——这六类资源必须同时到位，缺一项手术就做不成。M06-03 是这个多维资源编排的唯一场所。

**前提三：日间手术的质量与合规要求最高。**
《医疗质量安全核心制度要点》第十五条手术安全核查制度、《医疗机构手术分级管理办法》、《医疗机构病历管理规定》——三份法规对日间手术的要求比门诊高、与住院同等。M06-04（四方核对）与 M06-06（病历完整性 18 项）不是"可选功能"，是**法规强制留痕**。

### 1.3 为什么 M06 是一个模块而不是几个功能

| 理由 | 说明 |
|---|---|
| **业务主线唯一** | 一张申请单贯穿 10 个环节，主线必须唯一 |
| **资源模型唯一** | 手术间 + 台次 + 人员 + 床位的六维编排，只有 M06-03 一个场所 |
| **法规留痕唯一** | 四方核对、离院评估、病历完整性的证据链必须集中 |
| **统计口径唯一** | 日间手术占比是等级评审核心指标，口径必须集中定义 |
| **与 M09 边界清晰** | M06 管全流程外壳，M09 只管术中；分开后 M06 可独立交付 |

| 指标 | 现状 | 目标 | 说明 |

| 离院评估完成率 | 未度量 | **100%** | 法律责任转移点 |

### 2.3 六条拆分主线

**主线一：按「时间轴的物理动作」拆，不按「数据表」拆。**

```
申请准入 → 术前准备 → 排程 → 核对交接 → 术后离院 → 结算归档 → 统计
  (T-7)      (T-7~T-1)   (T-1)    (T-0)      (T+0)      (T+0~T+3)   (T+1~)
```

每一个环节都有明确的**责任人与交付物**：
- 申请准入 → 主刀 + 科主任，交付物 = 准入结论；
- 术前准备 → 护士，交付物 = 准备清单全部 DONE；
- 排程 → 护士长，交付物 = 带台次号的手术间安排；
- 核对交接 → 四方，交付物 = 四方签名的 Time-Out 记录；
- 术后离院 → 麻醉医生 + 护士，交付物 = PADSS 评估 + 交代签字；
- 结算归档 → 收费员 + 质控员，交付物 = 结算单 + 归档病历；
- 统计 → 无（自动），交付物 = 报表。

**这七个环节的合并方式（若合并）**：
- 准入 + 排程合并 → 排程算法为"提高手术间利用率"会放宽准入，把商业压力施加到医疗判断上；
- 准备 + 核对合并 → 准备是可提前一天反复做的，核对只能在术前 30 分钟做一次，节奏完全不同；
- 离院 + 结算合并 → 离院是医学判断（能不能走），结算是财务动作（钱够不够），主体完全不同。

**主线二：每个子模块必须有独立的"失败原因"统计口径。**

一家日均申请 60 台的医院，实际做 45 台，剩下 15 台去哪了？

| 流失原因 | 归属 |
|---|---|
| 医学准入不通过 | **M06-01** |
| 资质准入不通过 | **M06-01** |
| 患者主动放弃 | **M06-01** |
| 术前准备未完成 | **M06-02** |
| 排程不下（无手术间/无人员） | **M06-03** |
| 当天取消 | **M06-04** 汇总，源头在各处 |

**M06-01 只负责前三类。** 如果把这六类混在一张表里，永远算不出"是多少人本来就不该做，是多少人因为我们组织不好流失了"——这是最核心的管理问题。

**主线三：法规留痕必须独立且只增。**

- 四方核对（M06-04）→ `m06_verify_record` + `m06_verify_signature`；
- 离院评估（M06-05）→ `m06_discharge` + `m06_discharge_instruction`；
- 病历完整性（M06-06）→ `m06_archive_check` + `m06_archive_supplement`。

三者都是「事后追溯时最关键的证据」，都必须**只增不改**（触发器保护）。合并到业务表里会让"修改"变得轻而易举。

**主线四：配置与规则必须独立成表并可版本化。**

| 子模块 | 规则表 | 版本化 |
|---|---|---|
| M06-01 | `m06_eligibility_rule` + `m06_rule_version` | ✅ 双签发布 |
| M06-02 | `m06_prepare_template` | 否（引用 M01-07） |
| M06-03 | `m06_or_session` + `m06_schedule_config` | 否 |
| M06-05 | `m06_recovery_config` | 否 |
| M06-06 | `m06_settle_config` | 否 |
| M06-07 | `m06_metric_config` + `m06_metric_version` | ✅ 双签发布 |

**M06-01 与 M06-07 的规则必须版本化**，其余不必须——因为准入规则（血压阈值、年龄上限、ASA 等级）与统计口径（取消率算法、时间口径）是**会被事后质疑的决策依据**：半年后医务科把血压阈值从 180 改到 160，查看老患者准入记录必须能答"当时按 180 还是 160 判的"；统计口径改了，历史报表必须能答"这份报表按哪版口径算的"。

**主线五：M06 与 M09 的边界——M06 管外壳，M09 管术中。**

| 内容 | 归属 |
|---|---|
| 手术间排班与台次编排 | **M06-03** |
| 台次的计划开始/结束时刻 | **M06-03** |
| 实际开台/结束时刻 | M09 记录，回写 M06-03 |
| 术中记录（手术过程、出血量） | M09 |
| 麻醉记录（用药、体征、事件） | M09 |
| 器械清点 | M09 |
| 术前核对与 Time-Out | **M06-04** |
| 术后复苏与离院评估 | **M06-05** |

**为什么这么分**：M09 是「手术间内部的记录系统」，与手术间的设备、器械、麻醉机深度绑定；M06 是「手术间外部的组织系统」，与患者、家属、病房、收费关联。两者数据源不同、使用者不同、交付节奏不同。

**M09 未设计期间的应对**：M06-04/05/06 用「本地状态字段 + 接口预留」（R-01~R-04），术中相关检查项标 `UNKNOWN` 而非 `MISSING`，由人工确认降级，M09 上线后自动恢复。

**主线六：统计独立，因为它是对外承诺。**

日间手术占比是**等级评审的核心指标**，也是医保按病种付费的依据。统计口径错了，影响的是评审结果与拨付金额。M06-07 把口径显式定义成可配置、可版本化、可追溯的表，而不是散落在各处的 SQL。

### 2.4 为什么不拆更多

**为什么不把「危急/并发症」拆出 M06-05？**
并发症的判定需要「术后观察 + 随访 + 再就诊」三段数据，横跨 M06-05（留观异常）、M03-04（随访）、M04（再就诊）。若独立成 M06-08，它要反向依赖 4 个模块、维护 3 套状态机，而自己的核心表只有一张 `m06_complication`。这不是高内聚，是人为制造远程调用。

**为什么不把「日间病房床位」拆成独立子模块？**
床位管理的核心动作只有三个：分配、占用、释放，总计约 8 个接口。它没有独立的状态机（床位状态只有 FREE/OCCUPIED/CLEANING/MAINTENANCE 四态）、没有独立审批流、没有独立统计报表。放 M06-05（离院时释放）与 M06-03（排程时预留）中合计约 300 行代码。独立成子模块会导致"排一次手术要跨 3 个子模块"。

**为什么不把「材料退回」拆出 M06-06？**
材料退回本质是"结算前把不该收的钱去掉"，与结算触发是同一决策链上的先后两步。拆开后 M06-06 要调用 M06-0X 才知道"退完了没"，且两处都要维护结算前置条件，反而增加耦合。

## 3. 核心业务模型

### 3.1 申请单主模型

`m06_day_surgery`（申请单）是 M06 的唯一业务主线，后续 6 个子模块全部通过 `apply_id` 挂上来，不各建一套主表。

```
申请单 m06_day_surgery（apply_id, ds_no）
   │
   ├── 准入结果 m06_eligibility_result（evaluate_round 1..N）
   ├── 准备清单 m06_prepare_item（item_code 1..N）
   ├── 排程台次 m06_or_schedule（schedule_id, 一申请单可多台次：改期链）
   ├── 核对记录 m06_verify_record（verify_type WARD/TIMEOUT, round_no 1..N）
   ├── 交接记录 m06_handover（HANDOVER_A / HANDOVER_B）
   ├── 碗带 m06_wristband
   ├── 留观记录 m06_recovery（一申请单一留观）
   ├── 离院评估 m06_discharge + 交代 m06_discharge_instruction
   ├── 结算 m06_settlement + 费用明细 m06_settle_cost
   ├── 病历完整性 m06_archive_check + 归档 m06_archive + 补录 m06_archive_supplement
   └── 质控 m06_qc_record
```

**为什么必须唯一？**
- 若有 3 套主表（申请表 + 排程表 + 住院表），必然出现"申请单状态与排程状态不一致""准备清单属于哪张单"的混乱；
- 一次日间手术对应一个 `apply_id`，从申请到质控归档都围绕它。

### 3.2 申请单状态机（12 态）

```
                   ┌──────────────────────────────────────────────┐
                   │                                              │
              ┌────▼────┐   提交复核   ┌────────────────┐  通过  ┌──────────┐
   开单 ─────►│  DRAFT  │─────────────►│ PENDING_REVIEW │───────►│ ELIGIBLE │
              └────┬────┘              └───────┬────────┘        └────┬─────┘
                   │                           │ 驳回                   │ 排程
                   │ 作废                       ▼                      ▼
                   │                      ┌──────────┐          ┌────────────┐
                   │                      │INELIGIBLE│          │ SCHEDULED  │
                   │                      └──────────┘          └─────┬──────┘
                   │                           ▲                      │ 准备完成
                   │                           │ 准入不通过             ▼
                   │                           │                ┌────────────┐
                   │                           └────────────────│  PREPARED  │
                   │                                            └─────┬──────┘
                   ▼                                                  │ 到院报到
              ┌───────────┐                                           ▼
              │ CANCELLED │                                     ┌────────────┐
              └───────────┘                                     │ CHECKED_IN │
                   ▲                                            └─────┬──────┘
                   │                                                  │ 进手术间
                   │ 取消审批                                          ▼
                   └──────────────────────────────────────────  ┌────────────┐

                                                                └─────┬──────┘
                                                                      │ 离开手术间
                                                                      ▼
                                                                ┌────────────┐
                                                                │ RECOVERING │
                                                                └─────┬──────┘
                                                                      │ 离院登记
                                                                      ▼
                                                                ┌────────────┐
                                                                │ DISCHARGED │
                                                                └─────┬──────┘
                                                                      │ 归档完成
                                                                      ▼
                                                                ┌────────────┐
                                                                │   CLOSED   │
                                                                └────────────┘
```

**关键设计决策：**

**`INELIGIBLE` 是终态而非回 `DRAFT`。**
患者血压 190/110 被拒，去内科控制两周后 150/90 重新申请——这是**新的医疗决策**，不是"把上次申请改一改"。保留终态才能统计"多少人被拒、因为什么、后来回来多少"；允许回 DRAFT 这个数字永远算不出来。

**`CANCELLED` 可从 `ELIGIBLE` 之后任意状态进入**，但触发不同档位的审批：
- `ELIGIBLE`/`SCHEDULED` → 科主任审批；
- `PREPARED` → 科主任 + 医务科；
- `CHECKED_IN` → 科主任 + 医务科；
- `IN_SURGERY` → 医务科（术中终止属医疗事件）。

**状态与准入结论绑死（DB 约束）：**

```sql
CHECK (status NOT IN ('ELIGIBLE','SCHEDULED','PREPARED','CHECKED_IN',
                      'IN_SURGERY','RECOVERING','DISCHARGED','CLOSED')
       OR (eligibility_status = 'ELIGIBLE'
           AND evaluated_at IS NOT NULL
           AND rule_version IS NOT NULL))
```

防"status=SCHEDULED 但 eligibility_status=NULL"——那意味着**没做过准入判定的人被排了手术**。

### 3.3 准入判定模型

**三种属性分类**：

| 分类 | 取值 | 说明 |
|---|---|---|
| 判定方式 | `AUTO` / `MANUAL` / `HYBRID` | 系统自动 / 人工判定 / 系统给建议人工确认 |
| 严重度 | `BLOCK` / `WARN` / `INFO` | 阻断 / 警告（需确认） / 提示 |
| 类别（11 类） | `AGE` / `VITAL` / `METABOLIC` / `CARDIO` / `COAG` / `INFECTION` / `OCULAR` / `AIRWAY` / `GENERAL` / `LOGISTIC` / `CONSENT` | 按医学领域分类，便于统计"哪类问题最常见" |

**判定算法四步**：

```
① 拉取规则
   优先级：术式专属（scope=OPERATION, scope_key=手术编码）
         > 亚专科（scope=SPECIALTY, scope_key=CATARACT）
         > 全院默认（scope=GLOBAL, scope_key=NULL）
   同一 item_code 取最具体的；不同 item_code 累积

② 逐项判定
   AUTO    → 比较患者实际值与阈值
   MANUAL  → 待人工填写结论
   HYBRID  → 系统给建议，人工确认

③ 汇总
   任一 BLOCK 命中        → INELIGIBLE
   任一 NOT_EVALUATED     → PENDING_REVIEW（转人工）
   任一 WARN 且 need_review → PENDING_REVIEW
   否则                   → ELIGIBLE

④ 落库 + 阈值快照
   结果写 m06_eligibility_result，含 threshold_json
```

**阈值快照的必要性（这张表存在的核心理由）：**

医务科半年后把血压阈值从 180 改到 160，查看老患者准入记录必须能答"当时按 180 还是 160 判的"。只存规则 ID 则规则一改历史就还原不出来——这在医疗纠纷中是致命的。

```json
{
  "operator": "LT",
  "threshold": 180,
  "unit": "mmHg",
  "value": 172,
  "rule_code": "SYSTOLIC_BLOCK",
  "rule_version": "V1"
}
```

**判定结果四态**：

| 结果 | 含义 |
|---|---|
| `PASS` | 通过 |
| `WARN` | 需医生确认已知悉 |
| `BLOCK` | 阻断 |
| `NOT_EVALUATED` | 无法判定（数据缺失或依赖不可用） |

**为什么 WARN 单独一档而非并入 PASS：**
血压 165/95 按严格标准超标、按宽松标准允许。记 WARN 后：①医生提交前看到黄色提示 ②系统记录医生点了"已知悉"③万一术后出现高血压并发症，这记录是"医生在知情情况下做了决策"的证据。

### 3.4 资质准入模型

完全委托 M01-07（`POST /internal/v1/surgery/auth/check`），M06-01 只做调用、记录、判定降级。

**返回字段处理**：

| 字段 | 处理 |
|---|---|
| `allowed` | 直接决定 PASS/BLOCK |
| `reason` | 写入 `m06_eligibility_result.message` |
| `requiredLevel` | 写入快照（统计"是资质级别不够还是白名单没加"） |
| `approved` 为 false 且 `need_chief_approve` | 转审批（PENDING_REVIEW） |
| `auth_scope` | 写入快照 |
| `expire_at` | 30 天内到期 → WARN |

**降级策略（铁律）：M01-07 不可用 → `NOT_EVALUATED` → 申请单置 `PENDING_REVIEW` + 备注 + 告警医务科 → 人工复核。**

**绝不允许的降级方式：报错放行。**

手术资质是《医疗机构手术分级管理办法》的硬性要求，让资质不符的医生上台出事后医院承担全部责任。**这是 M06 唯一「降级但不放行」的依赖**——M01-07 不可用时申请单可保存为待复核，但不允许进入 M06-03 排程。

### 3.5 术前准备闭环模型

**11 类准备项**：

| 类型 | 代码 | 典型项 | 执行方 | 时效 |
|---|---|---|---|---|
| 禁食禁饮 | `FASTING` | 全麻禁食 8h / 禁清饮 2h | 患者 | T-8h |
| 术眼标记 | `EYE_MARK` | 主刀在术眼上方标记 | 主刀 | T-24h ~ T-2h |
| 散瞳 | `DILATE` | 复方托吡卡胺，每 10 分钟 1 次共 3 次 | 护士 | T-60min |
| 抗菌药物预防 | `ANTIBIOTIC` | 术前 30~120 分钟静脉给药 | 护士 | T-120min ~ T-30min |
| 知情同意 | `CONSENT` | 手术/麻醉/晶体三份 | 医生 + 患者 | T-24h |
| 麻醉访视 | `ANESTHESIA_VISIT` | ASA 分级、气道评估 | 麻醉医生 | T-24h |
| 主刀访视 | `SURGEON_VISIT` | 术式确认、术眼确认 | 主刀 | T-24h |
| 术前检查 | `EXAM` | OCT、角膜内皮、眼部 B 超 | M12 | T-7d |
| 术前检验 | `LAB` | 血常规、凝血、肝肾功能、传染病 | M13 | T-7d |
| 护理准备 | `NURSING` | 换病号服、去除饰品、假牙 | 护士 | T-30min |
| 其他 | `PREP` | 停抗凝药、停用某些药物 | 医生 | T-7d |

**闭环判定三条件：**
1. 所有 `is_required = TRUE` 的项状态为 `DONE` 或 `NA`（`NA` 须有原因）；
2. `is_abnormal = TRUE` 的项已被处置（医生确认可继续或已改期）；
3. 无 `FAILED` 状态的项。

**为什么清单要落库而非实时算：**
① M01-07 规则变更后历史申请清单不能变（患者是按当时规则准备的）；
② 每项要独立记录执行人与时间；
③ PDA 上逐项勾选必须有持久化行。

**关键设计：术前检查检验结果自动关联。**
M12/M13 出报告后触发 `m06.prepare.result_ready` 事件，M06-02 自动把对应准备项标 `DONE` + `done_source='AUTO'`。减少"漏勾"与"假勾"——护士不去看报告就不知道结果出来了，但系统知道。

### 3.6 排程资源模型

**六类资源必须同时到位：**

```
                     ┌──────────────┐
                     │  手术间       │  房间 × 时段
                     └──────┬───────┘
                            │
   ┌──────────────┐   ┌─────▼─────┐   ┌──────────────┐
   │  台次（第几台）│──►│  一台手术  │◄──│  主刀医生     │
   └──────────────┘   └─────┬─────┘   └──────────────┘
                            │
   ┌──────────────┐   ┌─────▼─────┐   ┌──────────────┐
   │  麻醉医生     │──►│           │◄──│  器械/巡回护士 │
   └──────────────┘   └───────────┘   └──────────────┘
                            │
                     ┌──────▼───────┐
                     │ 日间病房床位   │  患者术后留观
                     └──────────────┘
```

**时间轴四个时刻：**

```
计划手术开始      计划手术结束    计划出院
     │                │             │
     ▼                ▼             ▼
─────┬────────────────┬─────────────┬──────────────► 时间
     │   planned_duration  │  留观期  │
     │                     │          │
     │◄── 上一个台次的接台间隔 ──►│   │

实际手术开始      实际手术结束    实际离院
```

| 字段 | 含义 | 缺了会怎样 |
|---|---|---|
| `surgery_start_at` | 计划开始 | 无法判断准点率 |
| `surgery_end_at` | 计划结束 | 无法判断接台间隔 |
| `actual_start_at` | 实际开始 | 无法计算准点率 |
| `actual_end_at` | 实际结束 | 无法计算周转时间 |
| `expected_leave_at` | 计划出院 | 无法判断延期离院 |
| `actual_leave_at` | 实际离院 | 无法计算留观时长 |

**台次状态机（9 态）：**

```
DRAFT ──► PENDING ──确认──► CONFIRMED ──到院──► CHECKED_IN ──进间──► IN_SURGERY
                                │                                          │
                              改期                                       完成
                                │                                          ▼
                                ▼                                    ┌──────────┐
                          RESCHEDULED                                │COMPLETED │
                                                                     └──────────┘

旁支：SUSPENDED（停台，资源不可用）/ CANCELLED（手术不做）
```

**`RESCHEDULED` 是终态而非原地改日期**——改期后术前准备全部时序要重算；保留原台次 + 新建台次形成链条才能统计改期率（`previous_schedule_id`）。

**接台间隔 Turnover：**
- 默认 20 分钟（清洁 5 + 器械准备 8 + 患者交接 4 + 缓冲 3）；
- **感染术后接台需终末消毒 60 分钟（硬约束，敏感只读参数）**；
- `m06_or_session.turnover_minutes` 可覆盖手术间默认值（注药室默认 20 分钟一天只能 8 台，覆盖 5 分钟能做 30 台）。

### 3.7 四方核对模型

**四方（本院加严）：**

```
┌──────────────────────────────────────────────────────────┐
│  手术医生（主刀）  +  麻醉医生  +  巡回护士  +  患者本人  │
└──────────────────────────────────────────────────────────┘
```

**为什么要患者本人而非只三方：** 眼科术眼左右极易混淆，患者是唯一能在术前最后确认「医生说做左眼」的人。让患者自己说出"左眼"并签字，是最后一道防线。

**四次核对的时序：**

```
T-60 到院扫码（核对腕带 + 申请单）
   │
T-60~T-45  病房核对 14 项（护士 + 患者）
   │
T-45~T-40  交接一 6 类（病房护士 → 手术室护士）
   │
T-20 进手术间二次扫码
   │
T-0  Time-Out 20 项 + 四方签名
```

**核对项三态判定 `MATCH` / `MISMATCH` / `NA`，不用二态。**

**关键项要求输入验证值而非点选：**

| 关键项 | 验证方式 |
|---|---|
| 患者身份 | 扫描腕带 |
| 术式 | 输入前 4 字 |
| 术眼 | 患者自述后选择 |
| 禁食 | 输入最后进食时间 |

**理由：点选可盲选，输入/扫描无法盲输。** 第 30 台手术时手指已记住位置，14 项点完只需 20 秒；输入必须找到腕带、必须看申请单、必须问患者。

**`ck_m06_rs_*` 等约束把评分与总分绑死**：

```sql
CHECK (score_type <> 'ALDRETE'
       OR (total_score = activity + respiration + circulation
                            + consciousness + oxygen))
```

防"改了某一项但忘改总分"。

### 3.8 离院评估模型

**Aldrete vs PADSS 不是一回事：**

| 评分 | 用途 | 通过线 |
|---|---|---|
| **Aldrete** | 能否**离开复苏室** | ≥9 分（满分 10） |
| **PADSS** | 能否**离开医院** | ≥9 分且无 0 分项（满分 12） |

很多医院混用，导致"复苏室出来就让人回家"的差错。

**本院 PADSS 改良版（+眼科 4 项）：**

| 组 | 项 | 分值 |
|---|---|---|
| 标准 6 项 | 生命体征 / 活动 / 疼痛 / 恶心呕吐 / 出血 / 自主排尿 | 各 0~2，共 12 |
| **眼科 4 项** | **眼压 / 视力 / 前房 / 敷料** | 各 0~2，共 8 |
| **合计** | — | **20** |

**为什么分开算两个总分而非合并：** 合并算总分会让"PADSS 9 分、眼科 3 分"被判通过。

**离院判定两层：**

```
第一层 硬门槛（不可代偿）
   ├─ 眼压 ∉ [5, 25]        → OBSERVE_MORE
   ├─ 眼压 > 30 且用药无效   → TO_INPATIENT
   ├─ 视力较术前降 ≥2 行     → TO_INPATIENT
   ├─ 前房明显浅 / 积血      → TO_INPATIENT
   ├─ 敷料大量渗血           → TO_INPATIENT
   ├─ 生命体征不稳           → OBSERVE_MORE
   └─ 全麻末次给药 < 120 分钟 → OBSERVE_MORE（防二次镇静）

第二层 评分（可代偿）
   ├─ PADSS ≥ 9 且无 0 分项 → 通过
   ├─ PADSS 7~8              → OBSERVE_MORE
   └─ PADSS ≤ 6              → TO_INPATIENT

第三层 留观时长
   ├─ 白内障 < 120 分钟
   ├─ 玻切 < 240 分钟
   └─ 注药 < 60 分钟
      → 即使满分也不通过

第四层 陪护条件
   └─ 无陪护且非本地 → OBSERVE_MORE
```

**为什么硬门槛必须独立于评分——真实推演：**

白内障术后 90 分钟，PADSS 六项全 2 分（12/12）+ 眼科三项 2 分 + **眼压 0 分（38 mmHg）**。

- 按总分 18/20 通过 → 患者回家当晚急性高眼压损伤视神经；
- 按两层判定 → 眼压 38 不在 [5, 25] → 不通过。

**硬门槛不可代偿，评分可代偿。**

**为什么留观时长是硬性条件不是加分项：**
眼内炎潜伏期 2~5 天，但早期症状术后 4~24 小时出现；留观 2 小时能发现粘弹剂残留高眼压（4~6 小时峰值）、术后 1~2 小时渗血、麻醉药物迟发反应。"最低限度观察时间"不是"评估合格就能提前走"。

### 3.9 结算与归档模型

**日间结算的锚点是台次 `schedule_id`**，不是挂号单也不是住院号。

**费用构成（量级参考）：**

| 类别 | 占比 | 数据来源 |
|---|---|---|
| 手术包干费 | 30~40% | M01-06 收费标准 |
| 麻醉费 | 8~15% | M01-07 麻醉基础费 + 监护费 |
| 材料费 | 35~55%（晶体主导） | M15 实际消耗 |
| 药品费 | 3~8% | M14 发药 |

**前三项必须由 M06-06 归集后一次性提交 M16-03**，否则 M16 要理解 M06/M15 的业务知识。

**两种结算模式：**

```
优先 md_operation.need_deposit
   │
   ├─ 是 → 方式 A（预交金）
   │
   └─ 否 → 预估费用 ≥ DEPOSIT_THRESHOLD(3000)
             ├─ 是 → 方式 A
             └─ 否 → 方式 B（后付）
```

**阈值 3000 的依据**：本院日间手术费用中位数约 2,800 元，超过 3,000 的占 42%；这部分患者术前筹备资金的时间成本高于预交金管理成本。

**结算状态机（6 态）：**

```
PENDING ──触发──► TRIGGERED ──成功──► SETTLED ──调整──► ADJUSTED
                     │
                    失败
                     ▼
                  FAILED ──重试──► TRIGGERED

任意状态 ──异常──► ABNORMAL
```

**`TRIGGERED` 单独成态的必要性**：M16-03 执行涉及 6 步（试算 → 冻结预交金 → 建单 → 补退 → SETTLED → 解冻），耗时 5~30 秒。护士刷新时若显示"待触发"会重复点击 → 重复结算。

**未用材料必须先退货再结算：**
先结算再退会产生"已收又退"的额外流程（M16-08 退费单 + 审批 + 银行退款），而退回材料本质是"这笔钱本来不该收"。

**病历完整性 18 项：**

| 类别 | 项 | 来源模块 |
|---|---|---|
| 申请类 | D-01 申请单 / D-02 准入判定 | M06-01 |
| 同意类 | D-03 手术知情同意 / D-04 麻醉知情同意 | M18 |
| 术前类 | D-05 术前检查 / D-06 术前检验 / D-07 术前准备 / D-08 排程 | M12/M13/M06-02/03 |
| 术中类 | D-09 Time-Out / D-10 交接 / D-11 手术记录 / D-12 麻醉记录 / D-13 器械清点 | M06-04 / M09 |
| 术后类 | D-14 护理记录 / D-15 留观记录 / D-16 离院评估 / D-17 离院交代签字 | M08 / M06-05 |
| 随访类 | D-18 随访计划 | M03-04 |

**三种检查结果 `PRESENT` / `MISSING` / `UNKNOWN`。**

**`UNKNOWN` 的关键理由**：M09 手术麻醉、M08 护理站尚未设计，D-11~D-14 永远"不存在"，若标 `MISSING` 则所有病历都无法归档、功能报废 → **降级为人工确认并留痕**（护士勾"手术记录已纸介质存档"），M09 上线后自动检查失效。

**完整性得分 = (PRESENT + UNKNOWN) / 应检 × 100**；≥90 才可归档。

**归档 ≠ 封存**：归档后仍可补录（留痕），封存是医务科在 M18 做。归档后 **30 分钟冷却**内不可补录（防误操作）。

### 3.10 质量与统计模型

**三层指标模型：**

```
18 个原子指标（从业务表直接聚合）
   │
   ├──► 20 个派生指标（原子四则运算）
   │
   └──► 4 个复合指标（派生加权）
        │
        ▼
     42 项核心指标
```

**为什么分三层：** ①原子可复用（一个"台次数"被 8 个派生使用）②口径可追溯（看到"取消率 6.8%"能一路查到"取消 88 台 / 台次 1,294 台"）③性能可控（原子落宽表，派生计算在 SQL 里做除法）。

**口径五要素：**

| 要素 | 说明 | 例（取消率） |
|---|---|---|
| **分子** | 计数什么样的事件 | 状态变为 CANCELLED 的台次 |
| **分母** | 以什么为基数 | 统计期内新增的台次 |
| **排除规则** | 哪些不计入 | 排除 `TRANSFER_INPATIENT`（改为住院手术） |
| **时间口径** | 按哪天归类 | 按**取消发生日**，非手术日 |
| **维度** | 按什么分组 | 全院 / 科室 / 医生 / 术式 / 麻醉方式 |

**取消率排除 `TRANSFER_INPATIENT` 的理由：**
"改为住院手术"是正确的医疗决策（术前发现患者不适合日间手术）。把它计入取消率，会打击医生"发现问题及时转"的积极性，助长"硬着头皮做"。

**时间口径按取消发生日的理由：**
10 月 31 日的手术在 11 月 1 日取消，按手术日算属于 10 月，按取消日算属于 11 月。**应归 11 月**——因为 11 月承担了"打电话改约通知"的管理成本。

**统计维度与频率：**

| 维度 | 值来源 | 示例 |
|---|---|---|
| `HOSPITAL` | 无（全院） | — |
| `DEPT` | `dept_id` | 眼科一病区 |
| `DOCTOR` | `employee_id` | 张医生 |
| `OPERATION` | `operation_code` | 白内障超声乳化 |
| `ANESTHESIA` | `anesthesia_type` | 表面麻醉 |

**时间粒度**：日 / 周 / 月 / 季 / 年。**只预计算日与月两档**——周/季/年从日/月聚合，聚合 3~12 行 <10ms。

**预聚合必要性（实测）：**

| 方式 | 30 天 1,650 台次 42 项指标 |
|---|---|
| 实时 6 表 JOIN | **2.8 秒** |
| 预聚合宽表（31 行） | **48 毫秒** |

**快 58 倍。**

**目标两级分解：**

```
院级目标（医务科/院领导年度设定）
   │ 按科室历史台次占比加权
   ▼
科室目标（科主任承接）
   │
   ✗ 医生层面：只展示不分解
```

**为什么不分解到医生：** ①48 名医生逐一设定 42 项目标需管理成本极高 ②手术类型差异大（做玻切的与做注药的台次目标不可能一样），简单按权重分解不公平 ③医生绩效应由科室内部管理，M06 只提供数据不替代管理。

### 4.3 三条数据铁律

**铁律一：关键留痕表只增不改（5 张）。**

| 表 | 触发器函数 | 保护内容 |
|---|---|---|
| `m06_apply_log` | `fn_m06_apply_log_readonly()` | 全部禁止 UPDATE/DELETE |
| `m06_verify_signature` | `fn_m06_vsig_readonly()` | 全部禁止 |
| `m06_verify_log` | `fn_m06_vlog_readonly()` | 全部禁止 |
| `m06_recovery_log` | `fn_m06_rlog_readonly()` | 全部禁止 |
| `m06_stat_log` | `fn_m06_slog2_readonly()` | 全部禁止 |

**理由**：应用层可以被绕过（DBA 手动改、其他服务 bug、迁移脚本）。三方签名、核对记录、日志这类"事后追溯时最关键的证据"，必须在数据库层禁止修改。

**铁律二：唯一性用部分索引，不用"先查后插"。**

```sql
-- 正确
CREATE UNIQUE INDEX uk_m06_ds_order
    ON m06_day_surgery (order_id)
    WHERE order_id IS NOT NULL AND is_deleted = FALSE;

-- 错误：先 SELECT 再 INSERT
-- 并发下两个请求都 SELECT 到不存在，都 INSERT 成功
```

**病态使用部分唯一索引的场景**（必须用部分索引而非普通唯一）：

| 表 | 索引 | 为什么必须部分 |
|---|---|---|
| `m06_day_surgery` | `uk_m06_ds_order` | 允许"医嘱取消后重新申请" |
| `m06_day_surgery` | `uk_m06_ds_patient_active` | 已终态的申请不算占用 |
| `m06_or_schedule` | `uk_m06_schedule_slot` | 已改期/取消的台次应释放时段 |
| `m06_verify_record` | `uk_m06_vrecord_round` | 同一申请单允许多轮（病房核对 round1/round2） |
| `m06_wristband` | `uk_m06_wb_active` | 作废的腕带不占位 |
| `m06_settlement` | `uk_m06_settle_apply` | 一申请单一结算，但重算不算新建 |
| `m06_archive_check` | `uk_m06_check_apply` | 重跑更新同一行 |

**铁律三：金额与置信度必须 NUMERIC，禁 FLOAT；行级先舍入。**

```sql
-- 正确
quantity   NUMERIC(12,3)
unit_price NUMERIC(14,4)
amount     NUMERIC(14,2)

-- 行级先舍入
CHECK (amount = ROUND(quantity * unit_price, 2))
```

**为什么行级先舍入**：`0.005 × 3` 先累加得 `0.02`，先舍入得 `0.03`；明细 30 行按比例分摊优惠时，先累加会差几毛，退费按行退永远对不上账。

**分区判定（8 张分区表）：**

| 表 | 分区键 | 粒度 | 预建 | 理由 |
|---|---|---|---|---|
| `m06_apply_log` | `seq_date` | 月 | 36 | 无跨年唯一约束 |

**为什么业务表都不分区：**
- `m06_day_surgery`：15 年 27 万行；
- `m06_or_schedule`：15 年 33 万行；
- `m06_verify_item`：15 年 213 万行（最大）；

**更重要的理由：分区会破坏幂等与唯一性语义。**
`uk_m06_ds_order` 要保证"一医嘱一申请单"，若按年分区则唯一索引必须含分区键，变成"同年唯一"——明年同一个医嘱可以再插一条，产生重复申请。

**归档铁律**：归档表行数必须与被删行数**完全一致**才可删主表。

### 7.2 为什么需要独立的术前准备监控进程（m06-watchdog）

**术前准备是"有时间窗口"的作业**，不是"事件触发"的作业：

- 禁食：需在 T-8h 提醒患者（早上 6:00 提醒下午 14:00 手术的患者）；
- 抗菌药物：需在 T-120~T-30 分钟给药（错过窗口药效下降）；
- 散瞳：需在 T-60 分钟开始滴药（提前太多恢复、太晚瞳孔不够）。

**用 Celery 定时任务的缺点**：Celery beat 精度为分钟级，且大量定时任务堆积时会延迟。

**独立进程的做法**：`m06-watchdog` 每 60 秒扫描 `m06_prepare_item` 中 `planned_at` 在 [now-5min, now+5min] 的项，推送提醒。资源占用 <100 MB，与 API 进程完全隔离，不受业务高峰影响。

### 7.3 为什么 M06-07 用宽表而非实时计算

实测对比（30 天 1,650 台次）：

| 方式 | 耗时 | 说明 |
|---|---|---|
| 实时 6 表 JOIN | 2.8 秒 | 医院管理者打开报表等 3 秒会想刷新第二次 |
| 预聚合宽表 | 48 毫秒 | — |

**另外**：实时计算无法支持"按 42 项指标任意排序"（每个都要重算），宽表可以。

## 8. 全局业务规则

### 8.1 准入铁律（E-01~E-05）

| 编号 | 规则 | 理由 |
|---|---|---|
| E-01 | **M01-07 不可用时一律 `NOT_EVALUATED` + 转人工，绝不报错放行** | 资质不符上台出事，医院承担全部责任 |
| E-02 | **`INELIGIBLE` 是终态，不回 DRAFT** | 保留终态才能统计"被拒多少人、后来回来多少" |
| E-03 | **ASA 分级必须由麻醉医生评定** | ASA 核心是麻醉风险判断，只有麻醉医生有资质 |
| E-04 | **准入规则变更必须双签（科主任 + 医务科长）且 24 小时后生效** | 改错阈值会让大量患者被误拒或误放 |
| E-05 | **`is_mandatory` 规则（独眼、同意书、ASA IV）不可停用、严重度必须 BLOCK** | 法规红线不是医院自由选择 |

### 8.2 准备铁律（P-01~P-06）

| 编号 | 规则 | 理由 |
|---|---|---|
| P-01 | **准备清单必须落库，不实时算** | M01-07 规则变更后历史清单不能变 |
| P-02 | **术前检查检验结果自动关联（done_source=AUTO）** | 减少漏勾与假勾 |
| P-03 | **禁食时限以 M01-07 规则为准，全麻 8h/2h** | 法规与麻醉安全 |
| P-04 | **抗菌药物必须在 T-120~T-30 分钟给药** | 错过窗口药效下降 |
| P-05 | **异常项未处置不得进入 PREPARED** | 凝血异常做手术风险极高 |
| P-06 | **准备未完成可在 M06-03 排程但不可 CHECKED_IN** | 提前排台次是为了排满，但报到前必须齐 |

### 8.3 排程铁律（S-01~S-06）

| 编号 | 规则 | 理由 |

| S-01 | **一个时段只能一个台次（DB 部分唯一索引）** | 最后防线 |

| S-03 | **改期只能往后改，往前必须取消重申请** | 往前意味着准备时间更短 |
| S-04 | **改期必须联动六处（M06-02/04/05、M14-08、M16-03、M03-05）** | 漏一处会导致准备时序错乱 |
| S-05 | **停台自动方案不全自动执行** | 主刀可能有会议、晶体已到货 |
| S-06 | **同患者双眼手术间隔 ≥14 天** | 避免双眼同时感染致双盲 |

1. **安全相关依赖（资质）降级但不放行**——宁可流程卡住，不可让资质不符医生上台。

## 12. 实施路线与验收

### 12.1 六阶段 22 周

| 阶段 | 内容 | 周期 | 交付 |
|---|---|---|---|
| **① 基座** | M06-01 + M06-03（申请准入 + 排程） | 5 周 | 能开单、能判定准入、能排台次 |
| **② 准备闭环** | M06-02 | 3 周 | 准备清单自动生成、逐项闭环 |
| **③ 现场核对** | M06-04 | 4 周 | 四方核对、腕带、交接 |
| **④ 术后离院** | M06-05 | 3 周 | 复苏监护、离院评估、延期转住院 |
| **⑤ 结算归档** | M06-06 | 4 周 | 结算触发、完整性、归档、质控 |
| **⑥ 统计复盘** | M06-07 | 3 周 | 看板、报表、专题、目标 |

**为什么这个顺序：**

1. **先做 M06-01 + M06-03**：没有申请单与台次，后面 5 个子模块全部无从谈起。这两个是"能跑起来"的最小集。
2. **M06-02 紧跟**：排了台次但准备没闭环，手术当天一定会出问题（未禁食/未散瞳）。
3. **M06-04 独立成阶段**：法规留痕要求最高，需单独的 PDA/签字 Pad 硬件与培训。
4. **M06-05 在术中数据可用后**：离院评估依赖留观记录，而留观记录由 M06-05 自己产生（不依赖 M09）。
5. **M06-06 倒数第二**：结算依赖 M15（材料）与 M16-03（日间结算），这两个外部依赖必须先就绪。
6. **M06-07 最后**：统计依赖全部业务数据，最后做才有数据可统计。
