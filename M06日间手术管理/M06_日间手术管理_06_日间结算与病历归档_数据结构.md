**设计说明**

1. **`m06_settlement` 是 M06-06 的唯一结算主表**：
   - 一个申请单（`apply_id`）对应一条结算记录，用 `uk_m06_settle_apply` 保证唯一。
   - 结算的全生命周期（PENDING → TRIGGERED → SETTLED/FAILED → ADJUSTED）都在这张表上。
   - 归档相关字段（`archive_status`/`archive_no`/`archive_pdf_url`）也放在这张表，因为归档是结算之后的连续动作。

2. **费用明细（`m06_settle_cost`）独立成表**：
   - 一台手术 15~30 条费用项（手术 2 + 麻醉 2 + 材料 5~12 + 药品 2~5 + 检查检验 2~6）。
   - 明细必须保存**归集时的快照**，因为事后 M15/M14 的数据可能变化。
   - 结算重算时对比新旧明细，可以定位"哪一项金额变了"。

3. **完整性检查（`m06_archive_check`）与归档（`m06_archive`）分开**：
   - 检查可以多次执行（每改一次病历重跑一次），归档只做一次。
   - 检查是"18 项结果 + 得分"，归档是"归档号 + PDF + 时间"。
   - **分开后才可查"检查通过但没归档"、"归档了但没通过检查"两种异常**。

4. **归档后补录（`m06_archive_supplement`）独立成表且只增**：
   - 补录、催办、纸介质标记三种动作都进这张表。
   - **只增不改**，因为它是"归档后发生了什么事"的永久痕迹。
   - 一个归档可有多条补录记录。

5. **质控（`m06_qc_record`）独立**：
   - 质控是对已归档病历的检查评价，与归档是两个不同时间点。
   - 一份病历质控一次，用 `uk_m06_qc_archive` 保证。

6. **无物理外键**（与 M06-01~05 一致）：
   - 跨子模块写入加锁影响并发。
   - 应用层事务成对写入 + 每日 04:00 孤儿巡检。

7. **`m06_settle_log` 分区**：
   - 年 16 万行 × 15 年 = 240 万行，不分区单表体积超 1.2 GB。
   - 分区后"只扫最近 3 个月"物理隔离，性能提升 10 倍以上。

**约束说明：**

```sql
ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_mode
    CHECK (settle_mode IN ('DEPOSIT', 'POSTPAY'));

ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_status
    CHECK (status IN ('PENDING', 'TRIGGERED', 'SETTLED',
                      'FAILED', 'ADJUSTED', 'ABNORMAL'));

ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_direction
    CHECK (settle_direction IS NULL
           OR settle_direction IN ('PAYABLE', 'REFUNDABLE', 'EVEN'));

ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_archive_status
    CHECK (archive_status IN ('NOT_READY', 'READY',
                              'ARCHIVED', 'SEALED'));

ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_qc_status
    CHECK (qc_status IN ('NOT_CHECKED', 'PENDING',
                         'PASSED', 'FAILED', 'NEED_FIX'));

ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_qc_level
    CHECK (qc_level IS NULL OR qc_level IN ('A', 'B', 'C'));

ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_emr_status
    CHECK (emr_sync_status IN ('NOT_SYNCED', 'PENDING',
                               'SYNCED', 'FAILED'));

-- 金额非负
ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_amount_nonneg
    CHECK (discount_amount >= 0
           AND deposit_amount >= 0
           AND supplement_amount >= 0
           AND refund_amount >= 0
           AND material_return_amount >= 0);

-- 结算完成必须齐要素
ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_settled
    CHECK (status NOT IN ('SETTLED', 'ADJUSTED')
           OR (settlement_no IS NOT NULL
               AND settled_at IS NOT NULL
               AND total_amount IS NOT NULL
               AND settle_direction IS NOT NULL
               AND settle_amount IS NOT NULL));

-- 失败必须有错误码与原因
ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_failed
    CHECK (status <> 'FAILED'
           OR (fail_code IS NOT NULL
               AND fail_reason IS NOT NULL
               AND char_length(btrim(fail_reason)) >= 5));

-- 触发必须有触发时刻
ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_triggered
    CHECK (status <> 'TRIGGERED' OR triggered_at IS NOT NULL);

-- 结算方向与金额一致
ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_direction_amount
    CHECK (settle_direction IS NULL
           OR settle_direction = 'EVEN' OR settle_amount > 0);

-- 重试次数范围
ALTER TABLE m06_settlement
    ADD CONSTRAINT ck_m06_settle_retry
    CHECK (retry_count >= 0 AND retry_count <= 20);

-- 待结算数快照
```

**设计要点**

1. **`uk_m06_settle_apply` 是"一申请单一结算"的结构级保障**：

   ```sql
   CREATE UNIQUE INDEX uk_m06_settle_apply
       ON m06_settlement (apply_id)
       WHERE is_deleted = FALSE;
   ```

   - 应用层"先查后插"在并发下有竞态窗口（两个收费员同时点"结算"）。
   - 唯一约束让第二次插入直接失败，返回 `"0606006"`。

2. **`ck_m06_settle_direction_amount` 防止"应退 0 元却标 REFUNDABLE"**：

   ```sql
   CHECK (settle_direction IS NULL OR settle_direction = 'EVEN'
          OR settle_amount > 0)
   ```

   - 如果应收 = 预交金，`settle_amount = 0`，必须标 `EVEN`。
   - 若标 `REFUNDABLE` 且金额 0，收银台会出现"退 0 元"的荒诞单据。

3. **`ck_m06_settle_qc_level_match` 把等级与分数区间钉死**：

   ```sql
   CHECK (qc_level = 'A' AND qc_score >= 90
          OR qc_level = 'B' AND qc_score >= 75 AND qc_score < 90
          OR qc_level = 'C' AND qc_score < 75)
   ```

   - 应用层已按分数判等级，但若代码有 bug（比如把 88 分判成 A），约束会拒绝写入。
   - **这个约束的意义**：病历等级是等级评审的核心指标，一旦统计数据失真，医院的评审等级直接受影响。

4. **`ck_m06_settle_time_seq` 用五段时间序校验**：

   ```sql
   CHECK (triggered_at >= actual_leave_at
          AND settled_at >= triggered_at
          AND archived_at >= settled_at
          AND qc_at >= archived_at)
   ```

   - 真实场景：系统时钟回拨、补录错误、跨时区数据导入。
   - **这类错误在统计中会造成"负的归档耗时"，无法解释**。

5. **`archive_pdf_hash` 存 SHA-256 而非 MD5**：
   - MD5 已被破解（SHAttered 攻击），医疗病历是法律证据。
   - SHA-256 碰撞概率 2^-128，实务上不可破解。

6. **`pending_order_count` 存快照而非实时计算**：
   - 触发结算时的"未终态医嘱数"是判定"是否强制结算"的依据。
   - 事后分析"这个月有 15 台是强制结算的"，需要这个快照。
   - 实时算的话，医嘱后来完成了，数字就变了。

7. **`deposit_balance` 存结算前余额快照**：
   - 结算会消耗预交金，结算后余额就变了。
   - 事后追查"当时预交金够不够"，需要这个快照。

8. **`is_overdue_archive` 存布尔而非实时算**：

   ```sql
   -- 实时算（无法走索引）
   WHERE actual_leave_at < NOW() - INTERVAL '30 days'
     AND archive_status NOT IN ('ARCHIVED','SEALED')

   -- 落库后（可走部分索引）
   WHERE is_overdue_archive = TRUE
   ```

   - 由 `job_m06_archive_30day_scan` 每日 03:00 维护。
   - 滞后 24 小时可接受（超期告警不是秒级需求）。

9. **`status` 与 `archive_status` 是两条独立状态机**：
   - 结算完成后才可能归档，但两者不是简单的线性关系。
   - 真实场景：结算 `ABNORMAL`（对账差异）但病历完整性检查已通过、PDF 也生成了 —— 这时能否归档？
   - **答案是可以**：归档是病历的完整性判断，与钱有没有算清是两件事。财务差异可以事后处理，病历必须及时归档。所以 `ck_m06_settle_archived` 不要求 `status = SETTLED`。

**设计要点**

1. **`ck_m06_cost_amount` 强制"行级先舍入"**：

   ```sql
   CHECK (amount = ROUND(quantity * unit_price, 2))
   ```

   - **这是金额计算铁律在数据库层的落地。**
   - 举例：单价 0.0250，数量 3，先累加得 `0.075` 再舍入 = `0.08`；先舍入每行 = `0.01 × 3 = 0.03`。
   - 若 30 行明细都这么算，差额可达几毛钱，导致"预交金 20,000 元，结算出来差 3 毛"这种无法解释的差异。
   - **行业通则：行级先舍入，再累加。**

2. **`ck_m06_cost_return_sign` 双向钉死符号**：

   ```sql
   CHECK ((is_return = FALSE AND quantity > 0 AND amount > 0)
          OR (is_return = TRUE AND quantity < 0 AND amount < 0))
   ```

   - 防"标了退回但数量是正数"（会导致总费用增加）。
   - 防"标了非退回但金额是负数"（会导致总费用减少）。

3. **`ck_m06_cost_iol` 强制晶体必须有序列号**：

   ```sql
   CHECK (charge_name NOT LIKE '%晶体%'
          OR material_sn IS NOT NULL OR is_return = TRUE)
   ```

   - 人工晶体是**唯一需要序列号追溯的耗材**：药监召回时（如某批次晶体存在混浊问题），必须能查到"哪台手术用了这个序列号"。
   - 没有序列号，召回时只能按批号粗筛（一批可能 50 片，实际用在哪 3 台不知道）。

4. **`unit_price` 用 `NUMERIC(14,4)` 四位小数**：
   - 药品常按"每片"计价，如 0.0250 元/片（一盒 100 片 2.5 元）。
   - 用 2 位小数会算成 `0.03 × 100 = 3.00`（误差 0.5 元/盒）。

5. **`quantity` 用 `NUMERIC(12,4)` 支持小数**：
   - 检验试剂、麻药按毫升计（0.5 ml）。
   - 高值耗材按"个"，整数。

6. **为什么明细必须存快照而不引用源单**：

   | 方案 | 优点 | 缺点 |
   |---|---|---|
   | 存快照（采用） | 结算金额可复现、可追溯、源单变了不影响 | 占用存储（450,000 行/年） |
   | 只存源单 ID | 节省存储 | 源单变了结算金额就算不出来 |

   - 真实场景：结算后 3 天，M15 因为盘点调整了某批次材料的价格。此时查"这台手术为什么收 18,650"，若只存源单 ID，重算变成 18,720，永远说不清。
   - **医疗收费必须可复现**：任何时刻重算同一台手术，结果必须完全相同。

**分区定义**

```sql
DO $$
DECLARE
    v_start DATE := DATE '2026-10-01';
    v_i INT;
    v_name TEXT;
    v_from DATE;
    v_to DATE;
BEGIN
    FOR v_i IN 0..35 LOOP
        v_from := (v_start + (v_i || ' months')::INTERVAL)::DATE;
        v_to := (v_from + '1 month'::INTERVAL)::DATE;
        v_name := 'm06_settle_log_' || TO_CHAR(v_from, 'YYYYMM');
        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF m06_settle_log '
            'FOR VALUES FROM (%L) TO (%L)',
            v_name, v_from, v_to
        );
    END LOOP;
END $$;
```

**设计要点**

1. **18 种 action 覆盖结算与归档全流程**：
   - 结算（9）：`CREATE` / `TRIGGER` / `SETTLE_SUCCESS` / `SETTLE_FAIL` / `RETRY` / `SWITCH_MODE` / `MANUAL_ADJUST` / `RETURN_MATERIAL` / `REPORT_DIFF`
   - 检查（5）：`CHECK_RUN` / `CHECK_PASS` / `CHECK_FAIL` / `URGE` / `MARK_PAPER`
   - 归档（3）：`PDF_GENERATE` / `ARCHIVE` / `SUPPLEMENT`
   - 质控（1）：`QC_SCORE`

2. **`ck_m06_slog_amount` 强制金额变动类必须有金额**：
   - `MANUAL_ADJUST`（人工调整）、`RETURN_MATERIAL`（材料退回）、`REPORT_DIFF`（对账差异）都必须记录金额。
   - 事后查"这个月人工调整了多少钱"，靠这个字段聚合。

3. **分区理由**：
   - 年 16 万条 × 15 年 = 240 万行，单表体积超 1.2 GB。
   - 分区后时间线查询（只扫 1 个分区）性能提升 10 倍。

|---|---|
| 年结算 | 20,000 |
| 每结算日志数 | 8（创建 1 + 触发 1 + 成功 1 + 检查 3 + 归档 2） |
| 年日志数 | 20,000 × 8 = 160,000 |
| 单行平均大小 | 约 480 字节 |
| 年数据量 | 约 77 MB |
| 15 年数据量 | 约 1.15 GB |
| 索引开销 | 约 0.7 GB |
| **合计（15 年）** | **约 1.85 GB** |

**分区：** 按 `seq_date` 月度 RANGE 分区，预建 36 个月。

**18 项检查结果结构（`items_json` 单元素）：**

```json
{
  "code": "D-15",
  "name": "留观记录",
  "owner": "M06-05",
  "applicable": true,
  "result": "PRESENT",
  "result_text": "齐全",
  "detail": "留观记录已建立",
  "responsible_party": "M06-05",
  "paper_marked": null
}
```

**设计要点**

1. **`ck_m06_check_items` 强制 18 项**：

   ```sql
   CHECK (jsonb_typeof(items_json) = 'array'
          AND jsonb_array_length(items_json) = 18)
   ```

   - 防"只检查了 15 项就标通过"。
   - **为什么是硬编码 18**：18 项检查项是法规与质控要求定义的，不是可配置的数量。若未来增删检查项，需要同时改约束与迁移（这是有意的，防止悄悄减少检查项）。

2. **`ck_m06_check_score_calc` 用表达式校验得分**：

   ```sql
   CHECK (score = ROUND((present_count + unknown_count) * 100.0
                        / applicable_count)::SMALLINT)
   ```

   - **UNKNOWN 计入"通过"是有意的**：UNKNOWN 意味着"无法判定"，不是"确定缺失"。
   - 若不算作通过，M09 未上线时所有病历都不及格。
   - 但这个口径必须在数据库层固定，否则不同代码路径算出不同分数。

3. **`ck_m06_check_level_match` 把等级与分数钉死**：
   - 完整 ≥95 / 基本完整 90~94 / 不完整 70~89 / 严重缺失 <70。
   - 与 `is_passed = (score >= 90)` 联立，保证"基本完整"及以上才能归档。

4. **`uk_m06_check_apply` 一申请单一条**：
   - 重跑检查时**更新同一行**，不新建行。
   - 好处：查询"当前检查结果"不用取最新（避免 `ORDER BY ... LIMIT 1`）。
   - 代价：丢失历史检查结果 —— **但这正是我们要的**：检查结果的意义是"当前是否齐全"，而不是"曾经检查过几次"。
   - 若需保留历史，看 `m06_settle_log`（每次 `CHECK_RUN` 有一条日志）。

5. **`missing_codes` / `unknown_codes` 冗余数组**：
   - 用 `jsonb_array_length(missing_codes) = missing_count` 保证一致。
   - 用途：部分索引 `WHERE jsonb_array_length(missing_codes) > 0`、催办时直接读数组不用解析 `items_json`。

| 年申请单 | 20,000 |
| 年检查记录 | 20,000（一申请单一层） |
| 单行平均大小 | 约 6,000 字节（18 项 × 320 字节） |
| 年数据量 | 约 114 MB |
| 15 年数据量 | 约 1.7 GB |

| **合计（15 年）** | **约 2 GB** |

```sql
    '病历归档主表（一申请单一归档，含封存状态）';
COMMENT ON COLUMN m06_archive.archive_no IS
    '归档号 AR + YYYYMMDD + DL + 5 位序号';
COMMENT ON COLUMN m06_archive.pdf_hash IS
    '归档 PDF 的 SHA-256，防篡改，可重新校验';
COMMENT ON COLUMN m06_archive.pdf_version IS
    'PDF 版本，归档后每次补录递增（生成增量页）';
COMMENT ON COLUMN m06_archive.retention_years IS
    '保留年限，日间手术按住院病历管理为 30 年';
COMMENT ON COLUMN m06_archive.destroy_at IS
    '可销毁日期 = 归档日 + 保留年限，用于到期提醒';
```

**状态机**

```
归档状态

    ARCHIVED ──医务科封存──► SEALED ──特殊授权解封──► ARCHIVED
        │
      到期
        │
        ▼
    DESTROYED（仅标记，实际销毁需医务科审批）
```

**质控状态**

```
    PENDING ──质控评分 A/B──► PASSED
       │
       └──质控评分 C / 有缺陷──► FAILED
                    │
                  退回整改
                    │
                    ▼
                NEED_FIX ──整改完成后重新质控──► PENDING
```

**设计要点**

1. **`ck_m06_archive_score_min` 强制归档时得分 ≥90**：

   ```sql
   CHECK (completeness_score IS NULL OR completeness_score >= 90)
   ```

   - 应用层已校验 `archive_check_passed`，但若前端绕过或接口改造漏传，约束会拒绝。
   - **医疗意义**：<90 分的病历有缺件，归档后缺件会被"封存"，再补录就有篡改嫌疑。

2. **`ck_m06_archive_not_sealed` 双向钉死封存字段**：

   ```sql
   CHECK (status = 'SEALED' OR sealed_at IS NULL)
   ```

   - 防"状态是 ARCHIVED 但已有 sealed_at"这种不一致（说明有人手工改过状态字段）。

3. **`destroy_at` 用表达式校验**：

   ```sql
   CHECK (destroy_at = (archived_at::DATE
                        + (retention_years || ' years')::INTERVAL)::DATE)
   ```

   - 保证"可销毁日期"与"归档日期 + 保留年限"完全一致。
   - 防止有人手动改 `destroy_at` 让病历提前到期销毁。

4. **`pdf_version` 而非覆盖**：
   - 归档后补录时生成**增量页**（不重做全量 PDF）。
   - `pdf_version` 递增，`pdf_url` 指向最新版本。
   - **旧版本的 PDF 保留**（存对象存储，路径带版本号），可追溯。

5. **`retention_years` 默认 30 年**：
   - 《医疗机构病历管理规定》第二十九条：**"住院病历保存期不少于 30 年"**。
   - 日间手术按住院病历管理（有住院号、有手术记录）。
   - 门诊病历保存期 15 年，日间手术不适用。

| 30 年数据量 | 约 492 MB |
| 索引开销 | 约 320 MB |
| **合计（30 年）** | **约 810 MB** |

**分区：** 不分区。30 年 60 万行。

**设计要点**

1. **七种 `supplement_type` 区分三类动作**：
   - 纸介质标记（1）：`PAPER_MARK`
   - 正式补录（3）：`SUPPLEMENT_RECORD` / `SUPPLEMENT_SIGN` / `SUPPLEMENT_REPORT`
   - 过程记录（3）：`URGE`（催办）/ `FIX_REQUEST`（整改通知）/ `OTHER`

2. **`ck_m06_sup_paper` 强制纸介质标记必须有位置**：

   ```sql
   CHECK (item_code IS NOT NULL
          AND char_length(btrim(remark)) >= 10)
   ```

   - "归档时 D-11 手术记录在纸质病历柜 A-3 第 12 本"——没有具体位置，半年后等级评审抽查时找不到。
   - 位置说明必须 ≥10 字，防止填"有"这种废话。

3. **`ck_m06_sup_record` 区分不同补录类型的说明长度**：
   - 纸介质标记 ≥10 字（位置说明）
   - 正式补录 ≥20 字（原因说明）
   - 催办无要求（催办本身有记录价值）

4. **`idx_m06_sup_paper` 部分索引的必要性**：

   ```sql
   CREATE INDEX idx_m06_sup_paper
       ON m06_archive_supplement (apply_id)
       WHERE supplement_type = 'PAPER_MARK';
   ```

   - 完整性检查每次执行都要读纸介质标记（18 项中最多 3 项依赖它）。
   - 一年 2 万个申请单，若 20% 有纸介质标记 = 4,000 条。
   - 普通索引要扫 8 万行索引树，部分索引只需 4,000 行 → 快 20 倍。

5. **为什么只增**：
   - 补录是"归档后又做了什么"的永久痕迹。
   - 允许修改等于允许抹去历史。
   - **医疗纠纷场景**："这份手术记录是归档时有还是后来补的？"——只能靠只增的补录记录回答。

| 索引开销 | 约 90 MB |
| **合计（30 年）** | **约 240 MB** |

**分区：** 不分区。永久保留，30 年 24 万行。

**设计要点**

1. **`ck_m06_qc_total_match` 用表达式校验总分 = 六类之和**：

   ```sql
   CHECK (total_score =
          COALESCE((scores_json ->> 'HOME')::INT, 0)
          + COALESCE((scores_json ->> 'SURGERY')::INT, 0)
          + ...)
   ```

   - 应用层已计算，但这个约束防止"改了某一类但没改总分"。
   - 真实风险：质控员发现"手术相关记录应该是 27 不是 25"，改了 `SURGERY` 但页面没刷新 `total_score`。

2. **`ck_m06_qc_scores_max` 各类不得超满分**：

   | 大类 | 满分 |
   |---|---|
   | HOME 首页与基本信息 | 15 |
   | SURGERY 手术相关记录 | 30 |
   | ANESTHESIA 麻醉相关记录 | 15 |
   | COURSE 病程记录 | 20 |
   | EXAM_LAB 检查检验 | 10 |
   | DISCHARGE 出院记录 | 10 |
   | **合计** | **100** |

   - 防"手术相关记录给 35 分"导致总分虚高。

3. **`ck_m06_qc_a_no_defect` 强制甲级无缺陷**：

   ```sql
   CHECK (level <> 'A' OR defect_count = 0)
   ```

   - 应用层已校验，DB 层兜底。
   - **意义**：甲级病历是等级评审的"优质病案"，有缺陷的不能算甲级。

4. **`ck_m06_qc_fix_pending` 强制整改要素齐全**：

   ```sql
   CHECK (fix_required_by IS NOT NULL AND fix_target_staff_id IS NOT NULL
          AND char_length(btrim(fix_remark)) >= 10)
   ```

   - 没有截止时刻 → 整改永远不催
   - 没有责任人 → 不知道给谁退回
   - 没有要求 → 责任人不知道改什么

5. **`idx_m06_qc_grade_c` 部分索引的意义**：

   ```sql
   CREATE INDEX idx_m06_qc_grade_c
       ON m06_qc_record (qc_at)
       WHERE level = 'C';
   ```

   - 丙级病历是"不合格病历"，医务科必须逐份复核。
   - 一年约 320 份（1.6%），普通索引扫 30 万行，部分索引扫 320 行 → 快 900 倍。

6. **`auto_score` + `adjust_points` 双字段**：
   - `auto_score` 是系统计算（完整性 + 及时性 + 关键项），占参考值。
   - `adjust_points` 是质控员的人工调整（-50~+50）。

```python
class QcScoreIn(BaseModel):
    """保存质控评分。"""

    scores: Dict[str, int] = Field(..., description="六大类得分")
    defects: List[QcDefectIn] = Field(default_factory=list)
    surgeon_id: Optional[int] = Field(None, gt=0)
    remark: Optional[str] = Field(None, max_length=1000)

    @field_validator("scores")
    @classmethod
    def _check_scores(cls, v):
        for code, score in v.items():
            if code not in QC_MAX_SCORES:
                raise ValueError("未知质控大类：%s" % code)
            if score < 0 or score > QC_MAX_SCORES[code]:
                raise ValueError(
                    "质控得分超出范围：%s = %d（上限 %d）"
                    % (code, score, QC_MAX_SCORES[code]))
        if set(v.keys()) != set(QC_MAX_SCORES.keys()):
            raise ValueError("必须给出全部六大类的得分")
        return v

    @field_validator("defects")
    @classmethod
    def _check_defects(cls, v):
        seqs = [d.seq for d in v]
        if len(set(seqs)) != len(seqs):
            raise ValueError("缺陷项序号不得重复")
        return v
```

### E.4 上线前运维准备

| 序号 | 准备项 | 说明 | 关键性 |
|---|---|---|---|
| 1 | **M16-03 日间结算联通性** | 验证 `POST /inpatient/settle` 与 `on-settled` 回调双向可达 | ⭐⭐⭐ |
| 2 | **M15 材料消耗冻结机制** | 验证 `is_frozen` 接口，未冻结则无法结算 | ⭐⭐⭐ |
| 3 | 结算模式阈值确认 | 与财务确认 `DEPOSIT_THRESHOLD`（默认 3000） | ⭐⭐⭐ |
| 4 | 归档得分线确认 | 与医务科确认 `SCORE_MIN`（默认 90） | ⭐⭐⭐ |
| 5 | **质控等级线确认** | 与医务科确认甲级/乙级分数线（默认 90/75） | ⭐⭐⭐ |
| 6 | 对象存储配置 | 归档 PDF 存储桶、容量、备份策略 | ⭐⭐ |
| 7 | **M18 电子病历联通** | 验证归档推送接口；未上线则跳过 | ⭐⭐ |
| 8 | 归档 PDF 模板确认 | 11 类单据的版式需医务科签字确认 | ⭐⭐ |
| 9 | 催办消息通道 | 验证 M03-05 消息发送 | ⭐⭐ |
| 10 | 分区自动创建任务 | `m06_settle_log` 每月 25 日预建下 3 个月分区 | ⭐⭐ |
| 11 | 对账流程培训 | 与财务对账的月度流程与差异处理 SOP | ⭐⭐⭐ |
| 12 | 超期未归档告警 | 配置告警接收人（医务科 + 病案室） | ⭐⭐⭐ |

**第 1 项最关键**：M16-03 的 `on-settled` 回调是 M06-06 结算状态的唯一更新来源。若回调不通，所有结算会永远停在 `TRIGGERED`，看板一直显示"结算中"，收费员无法确认患者是否结算完毕。上线前必须做双向联调（含幂等验证）。

**第 5 项第二关键**：质控等级线直接决定病历甲级率。本院历史甲级率约 70%，若按国标 90 分线统计会更低。与医务科确认后可能调整为"甲级 85 分"（本院内部标准），这一调整必须在上线前一次确定，事后修改会导致历史数据与新数据不可比。
