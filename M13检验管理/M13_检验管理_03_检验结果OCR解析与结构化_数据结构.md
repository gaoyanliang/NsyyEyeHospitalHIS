**设计说明：**

1. **`m13_parse_record` 是本文档的中心表**。六张表中四张围绕它：`m13_parse_field`（字段明细）、`m13_unconfirmed`（待确认状态）、`m13_parse_failure`（失败历史）。`m13_parse_template` 与 `m13_parse_config` 是独立的规则表。

2. **一个文件可以有多条解析记录**（"解析失败 → 改模板 → 重新解析 → 成功"），通过 `is_superseded` 标记历史版本。所以 `file_id` 上的唯一索引是 **部分唯一索引**（`WHERE is_deleted=FALSE AND is_superseded=FALSE`），而不是普通唯一索引——后者会让第一次失败就锁死位置，再也无法重新解析。

3. **一个检验任务只能绑一份有效报告**。同样用部分唯一索引 `uk_m13_parse_task_bound (bound_task_id) WHERE bind_status='BOUND' AND is_superseded=FALSE AND is_deleted=FALSE`。这是"错绑防护"的第四道闸门的数据库兜底。

4. **`m13_unconfirmed` 与 `m13_parse_record` 是 1:1（活跃时）**。用部分唯一索引 `uk_m13_unconf_parse (parse_id) WHERE status IN ('PENDING','HANDLING') AND is_deleted=FALSE`。一条解析记录在同一时刻只能有一个活跃的待确认条目，但历史条目可以有多条（认领后重新打开）。

5. **六张表全部不分区**。理由：
   - `m13_parse_record` 15 年约 230 万行，主键查询 <1ms，PG 16 舒适区。
   - **关键理由**：`uk_m13_parse_task_bound` 是"一任务一报告"的唯一防线，按年分区会迫使索引含分区键，约束退化为"同年唯一"。若去年归档的报告被重新解析，就会出现同一任务同一年的两份有效报告。
   - `m13_parse_field` 15 年约 1,226 万行，虽有分区价值，但所有查询都以 `parse_id` 为主（会带分区键），分区收益有限；且 `uk_m13_parse_field_code (parse_id, field_code)` 已是理想的分区候选——**但如果未来需要分区，应改用 HASH(parse_id) 而非 RANGE(created_at)**，因为按 parse_id 查询时 RANGE 会跨分区。当前不分区。

6. **`m13_parse_field` 用 `value_text` 与 `numeric_value` 双列**。前者是 PDF 原文（可能是"约 6.2"或"6.2↑"），用于展示与追溯；后者是转数字后的值，用于区间与危急值比对。只有一列会出现"把'↑'存进 numeric"或"把 Decimal 转字符串丢失精度的两难"。

**约束说明：**

```sql
-- 一文件一活跃解析（部分唯一索引）
CREATE UNIQUE INDEX uk_m13_parse_file_active
    ON m13_parse_record (file_id)
    WHERE is_deleted = FALSE AND is_superseded = FALSE;

-- 一任务一有效报告（错绑防护第四道闸门的数据库兜底）
CREATE UNIQUE INDEX uk_m13_parse_task_bound
    ON m13_parse_record (bound_task_id)
    WHERE bind_status = 'BOUND'
      AND is_superseded = FALSE
      AND is_deleted = FALSE;

CREATE UNIQUE INDEX uk_m13_parse_no
    ON m13_parse_record (parse_no)
    WHERE is_deleted = FALSE;

ALTER TABLE m13_parse_record
    ADD CONSTRAINT ck_m13_parse_no
    CHECK (parse_no ~ '^PR[0-9]{8}[0-9]{6}$');

ALTER TABLE m13_parse_record
    ADD CONSTRAINT ck_m13_parse_sha
    CHECK (file_sha256 ~ '^[0-9a-f]{64}$');

ALTER TABLE m13_parse_record
    ADD CONSTRAINT ck_m13_parse_status
    CHECK (parse_status IN (
        'PENDING', 'EXTRACTING', 'OCRING',
        'PARSING', 'PARSED', 'PARSE_FAILED'));

ALTER TABLE m13_parse_record
    ADD CONSTRAINT ck_m13_parse_mode
    CHECK (extract_mode IS NULL
           OR extract_mode IN ('TEXT_LAYER', 'OCR'));

ALTER TABLE m13_parse_record
    ADD CONSTRAINT ck_m13_parse_bind_status
    CHECK (bind_status IN ('UNCONFIRMED', 'BOUND', 'ORPHAN'));

ALTER TABLE m13_parse_record
    ADD CONSTRAINT ck_m13_parse_bind_type
    CHECK (bind_type IS NULL
           OR bind_type IN ('TICKET', 'WINDOW', 'MANUAL'));

-- 绑定四要素齐全
ALTER TABLE m13_parse_record
    ADD CONSTRAINT ck_m13_parse_bound
    CHECK (bind_status <> 'BOUND'
           OR (bound_task_id IS NOT NULL
               AND bind_type IS NOT NULL
               AND bound_at IS NOT NULL));

-- 未绑定时不得有任务（人工绑定除外已由上面覆盖）
ALTER TABLE m13_parse_record
    ADD CONSTRAINT ck_m13_parse_unbound
    CHECK (bind_status = 'BOUND'
           OR bound_task_id IS NULL
           OR bind_type = 'MANUAL');

-- 人工绑定必须有操作人
ALTER TABLE m13_parse_record
    ADD CONSTRAINT ck_m13_parse_manual
    CHECK (bind_type IS NULL
           OR bind_type <> 'MANUAL'
           OR bound_by IS NOT NULL);

-- 解析完成必须有结束时刻与耗时
ALTER TABLE m13_parse_record
    ADD CONSTRAINT ck_m13_parse_done
    CHECK (parse_status NOT IN ('PARSED', 'PARSE_FAILED')
```

**状态机：**

```
                   ┌──────────┐
                   │ PENDING  │
                   └────┬─────┘
                        │
                        ▼
                 ┌─────────────┐
                 │ EXTRACTING  │
                 └──────┬──────┘
            有文本层 │    │ 无文本层
                    │    ▼
                    │ ┌─────────┐
                    │ │ OCRING  │
                    │ └────┬────┘
                    ▼      ▼
                 ┌──────────┐
                 │ PARSING  │
                 └──┬────┬──┘
              成功  │    │ 失败
                    ▼    ▼
           ┌──────────┐ ┌──────────────┐
           │  PARSED  │ │ PARSE_FAILED │
           └──────────┘ └──────┬───────┘
                               │ retry < 3
                               ▼
                           （回 PENDING）

绑定状态（与解析状态独立）：
  UNCONFIRMED ──► BOUND     （自动或人工绑定成功）
       │
       └──────► ORPHAN      （超过 7 天无人认领）
```

**设计要点：**

1. **`file_sha256` 冗余一份**。M13-02 的文件记录可能因归档迁移改了路径、可能因巡检标记丢失。解析记录冗余指纹后，"即使原件没了，绑定依据与内容摘要还在"。

2. **`patient_name` / `gender` / `age` 在主表冗余**。这三个字段是通道 A 的核心输出，待确认队列要按姓名展示与排序、质量报表要按姓名匹配率分析、绑定算法频繁读取。若每次都去 `m13_parse_field` 里捞，一次列表查询要 20 次 JOIN。

3. **权威数据在 `m13_parse_field`**。主表的三个字段是**快照冗余**，字段明细表才是真相源。字段被人工修改后，主表也要同步更新（由 `ParseService.update_fields` 保证）。

4. **`bind_message` 必须存"为什么没绑上"**。只有 `bind_status='UNCONFIRMED'` 两个字，护士不知道怎么办；有"N 小时内无该设备的检查时间窗"，护士就知道去问技师。

5. **`raw_text` 存库（截断 10 万字符）**。三个用途：
   - 写模板正则时直接看原文，不用翻 PDF
   - PDF 归档后丢失时，文本仍在
   - 只改规则不想重跑 OCR 时，可直接从库里读原文重试

   代价：15 年约 230 万行 × 2.6KB（截断后平均）约 600MB，可接受。

6. **`required_miss_count` 单独存**。统计"哪台设备必填字段缺失最多"是模板优化的重要信号。只存 `fail_reason` 字符串无法聚合。

7. **`review_status` 只在主表存一个字段，不建审核表**。审核的完整数据（结论、意见、签字、时间）归 M13-04。这里存一个状态字段是为了列表页显示"待审核/已审核/已退回"，避免跨模块查询——500 条记录要发 500 次 HTTP。

8. **`critical_field_unconfirmed` 单独计数**。这是"提交前校验"的快速判断依据：直接看这个数是否为 0，不用遍历 `m13_parse_field`。

9. **`is_superseded` 而非直接删除**。重新解析生成新记录，旧记录标 `is_superseded=TRUE` + `superseded_by_id`。保留理由：纠纷取证时能看到"第一次解析出了什么"；质量分析能看到"同一份报告解析了几次"。

10. **`ck_m13_parse_confirm_bound`（未绑定不可核对完成）**。核对字段的目的是让人确认"这些值对应的是这个患者的这份报告"，没有绑定就无法核对。

| 项 | 值 |
|---|---|
| 每日新增 | 约 420 条 |
| 每年新增 | 153,300 条 |
| 15 年累计 | 约 230 万条 |
| 单行平均 | 约 3,200 字节（含截断的 raw_text） |
| 总容量 | 约 7.4 GB（含索引约 9.5 GB） |

**分区：** 否。理由见 4.1 设计说明第 5 条。

```sql
    '数值化后的值，用于参考区间与危急值比对';

    '机器抽取的原值，人工修改时保留，不可覆盖，是准确率统计的基石';

    '关键字段：无论置信度多高都必须人工确认';

    '原文四点坐标 [[x1,y1],[x2,y2],[x3,y3],[x4,y4]]，用于跳转定位';
```

**设计要点：**

1. **`value_text` 与 `numeric_value` 双列**。只存一列会有两难：
   - 只存 `numeric_value`：丢失原文（"约 6.2"变成 6.200000，追溯时看不出原文有"约"字）
   - 只存 `value_text`：每次比对都要实时解析字符串，且"↑↓"标记无法存入

   双列设计：`value_text` 用于展示，`numeric_value` 用于计算，二者同源。

2. **`original_value` 必存且不可覆盖**。字段抽取准确率（核心 KPI）只能由"人工改了多少次"计算。如果直接覆盖 `value_text`，就永远不知道机器原来抽的是什么，也无法优化模板。

3. **`is_extracted` 与 `value_text IS NULL` 语义不同**：
   - `is_extracted=FALSE`：模板定义了该字段，但抽取规则没匹配到
   - `is_extracted=TRUE, value_text=""`：匹配到了但内容为空（报告上真的空着）

   区分才能准确统计"缺失率"。

4. **`source_bbox` 用 JSONB**。四点坐标 `[[x1,y1],...]`，未来可能变多点（不规则区域），且它不参与任何条件查询，只用于前端跳转定位。用 JSONB 比建四列 `x1,y1,x2,y2` 更灵活。

5. **`is_critical` 从模板复制而非实时查模板**。模板的关键字段清单可能变（今天加了 K，明天加了 NA），如果实时查会导致历史记录的"是否需要确认"随模板变化而变。固化在字段行上，锁定"当时按什么规则判定"。

6. **`ck_m13_field_critical_result` 把危急值与标记绑死**。`is_critical_result=TRUE` 时 flag 必须是 `CRITICAL_*`。防止出现"标了危急值但 flag 是 HIGH"这种数据。

7. **`ck_m13_field_flag_ref`（高低标记必须有区间）**。没有区间的 `HIGH` 无意义——高到什么程度、相对什么高，必须能追溯到区间。

8. **`edit_reason` 可选而 `bind_message` 强制**。改一个值的原因往往就是"原值错了"，强制只会填"改错"敷衍；而"为什么没绑上"是对护士的行动指引，必须说清。

| 每条记录字段数 | 平均 8 个（含患者信息 4 个 + 结果 4 项） |
| 每日新增 | 约 3,360 行 |
| 每年新增 | 1,226,400 行 |
| 15 年累计 | 约 1,840 万行 |
| 单行平均 | 约 280 字节 |
| 总容量 | 约 5.1 GB（含索引约 8 GB） |

**分区：** 否。若未来需要，用 `HASH(parse_id)` 而非 `RANGE(created_at)`——所有查询都以 `parse_id` 为入口。

**设计要点：**

1. **`template_code` 含版本，`template_key` 不含**。`template_code='OCT_MACULA_V3'` 供运维在告警中精确指代，`template_key='OCT_MACULA'` 供查询"这个模板有哪些版本"。若只用含版本的编码，新版本上线后，"这个模板的历史版本"就只能是字符串前缀匹配。

2. **`uk_m13_template_current` 用 `COALESCE(device_code, '')`**。PG 唯一索引认为 NULL 互不相等，不加 COALESCE 则两个通用模板（`device_code` 均 NULL）都能标记 `is_current=TRUE`，匹配时不知道用哪个。

3. **`is_current` 与 `is_enabled` 是两个独立维度**。见上表 4 种组合。"紧急下线"必须是"停用但保留 current"，否则恢复时要重新找哪个是当前版本。

4. **`ck_m13_template_current_enabled`（当前版本必须启用）**。防止出现"当前版本已停用"——匹配逻辑按 `is_current` 找模板，找到了却是停用的，行为未定义。

5. **`match_total` / `match_success` 用计数器而非每次统计**。模板匹配率是列表页的高频指标，每次 `COUNT(*)` 全表扫 230 万行（解析记录表）要 3 秒。计数器原子递增后读取 O(1)。风险是并发下数值略偏，每日 02:00 的健康检查重算校正。

6. **`baseline_rate` 存上一版本命中率**。回归测试要与上一版对比，如果每次都重跑旧版本，成本翻倍。存下基准值，只需跑新版本。

7. **`is_system` 保护 `GENERIC_V1`**。这是整个方案的最后一层保险，被误删会导致所有未知格式报告解析失败并堆积在失败列表，且没有自动认领路径。DB 层约束 `ck_m13_template_generic_sys` 强制它永远启用、永远是当前版本。

8. **`field_rules` 用 JSONB 而非独立规则表**。理由：
   - 规则永远整体读写（编辑模板时一次性提交全部规则），没有"只查某个字段规则"的场景
   - 规则表只有 10~50 行，不值得为它建一张表
   - 代价：无法对规则内部字段建索引，但本来也不按规则字段查询

9. **`regression_json` 存最近回归结果**。启用时自动跑回归，结果存下来供事后审计（"当时凭什么认为这个模板是好的"）。

**状态机：**

```
                  ┌─────────┐
     进队列 ─────►│ PENDING │
                  └────┬────┘
          认领（乐观更新）│
                       ▼
                  ┌──────────┐
                  │ HANDLING │  中间态：护士正在核对
                  └────┬─────┘
         确认绑定 │    │ 标记无主
                ▼    ▼
     ┌──────────┐  ┌──────────┐
     │ HANDLED  │  │  ORPHAN  │
     │ (BOUND)  │  │          │
     └──────────┘  └──────────┘
                       ▲
        等待 > 7 天     │
     ┌─────────┐       │
     │ PENDING │───────┘（定时任务自动置）
     └─────────┘
```

**设计要点：**

1. **`candidate_task_ids` 冗余目录快照**。候选任务在 `m13_lab_task` 表，且随时间窗关闭、任务取消而变化。待确认队列需要的是"进队列那一刻的候选"，稳定、可重复。如果每次重新查，护士看到的候选可能已经变了。

2. **`candidate_count` 冗余**。为了能用部分索引按"候选数 = 1"快速筛选可批量处理的项。`jsonb_array_length()` 在 WHERE 里无法走索引。

3. **`priority` 用权重数字而非枚举**。排序 `ORDER BY priority DESC, created_at ASC` 需要数字；用 `SMALLINT` 并加 CHECK 约束限定只有 5 个取值，兼顾可排序与可读。

4. **`wait_minutes` 与 `is_overdue` 落库**。`WHERE CURRENT_TIMESTAMP - created_at > INTERVAL '1 hour'` 无法走索引。存成整数后可 `WHERE wait_minutes > 60 AND status='PENDING'` 走索引。定时任务每 5 分钟刷新，滞后 5 分钟可接受。

5. **`HANDLING` 中间态的必要性**。护士打开认领弹窗后要花 1~2 分钟核对（看 PDF、看就诊号、看诊断）。两个护士同时打开同一条，都点确认，后者会覆盖前者的绑定。实现乐观更新：

```sql
UPDATE m13_unconfirmed
SET status = 'HANDLING', handled_by = :uid, handled_at = now()
WHERE id = :id AND status = 'PENDING';
-- rowcount = 0 说明已被他人认领
```

6. **`ck_m13_unconf_handled` 与 `ck_m13_unconf_bound` 双向钉死**。防止出现"标了 HANDLED 但没有 resolved_type"或"resolved_type=BOUND 但没有 bound_task_id"的脏数据。

7. **`uk_m13_unconf_parse` 是部分唯一索引**。一条解析记录同时只有一个活跃条目，但历史条目可以有多条（认领后因为某些原因重新打开、无主后重新认领）。用部分唯一索引约束"活跃"部分。

**设计要点：**

1. **独立成表的理由**：主表 `m13_parse_record` 只保留**最后一次**失败的信息（`fail_code` / `fail_reason`）。但诊断"模板写错了"需要看**第一次**失败时的原始文本——如果中间换过模板，最后一次的原文可能已经不是最初那份。按 `attempt_no` 保留每次尝试的完整上下文。

2. **`raw_text_head` 存 2000 字符而非全文**。失败诊断只需要看抬头与标签部分（前 2000 字符足够）。失败记录数是解析记录的 3 倍，存全文会让存储翻 3 倍（1.8GB vs 6GB）。全文在 `m13_parse_record.raw_text` 已经有。

3. **`can_auto_recover` 显式标记**。`OCR_UNAVAILABLE` / `OCR_TIMEOUT` 是系统问题，恢复后自动重试即可；`TEMPLATE_MISMATCH` / `FIELD_MISSING` 是模板问题，自动重试永远失败，必须人工介入。不区分会让定时任务给模板问题也重试 3 次，白白消耗 CPU。

4. **`detected_title` 单独存**。新建模板时要填 `title_pattern`，有真实标题可以直接复制加 `^`/`$` 锚点，不用翻 PDF 或日志。

5. **`missing_fields` 存数组**。用于聚合统计"血常规设备平均缺几个必填字段"——这是模板质量的核心指标。只存 `fail_detail` 字符串无法聚合。

**为什么通用模板只抽姓名？**

它不是"能正确抽出所有字段"，而是"至少能抽出姓名，让文件进待确认队列"的兜底。多抽字段会增加误抽风险——在未知格式上抽出的错误值比没有值更糟。只抽姓名，抽不到就进 `OCR_FAILED`，抽到了就进待确认，护士能认领。

| 10 | 验证 pg_trgm 扩展 | `CREATE EXTENSION` 需超级用户权限 |

**第 6 项为什么最重要：**

时间窗绑定依赖 `file_mtime`。仪器电脑时钟慢 20 分钟，PDF 的 mtime 就早 20 分钟，落在时间窗之外，**所有报告都绑不上**，全部进待确认队列，护士一天要处理 420 条。这不是代码能修的，必须靠 NTP 校准。
