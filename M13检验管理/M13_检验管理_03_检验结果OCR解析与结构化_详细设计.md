## 1. 模块概述

M13-03 是整条检验链路的技术心脏。它把 M13-02 采集进来的**一张 PDF**，变成 M13-04 可以审核、M07-04 可以展示、M13-05 可以比对参考区间的**结构化结果**。

M13-03 回答两个问题：

1. **这份报告是谁的**（患者绑定）—— 错了就是灾难，会导致把 A 的血钾报告挂到 B 名下，医生据此调药。
2. **上面写了什么**（结果结构化）—— 错了还有救，因为结果旁边有参考区间，医生能看出来异常。

这个不对称是本子模块全部设计的起点。

### 1.2 为什么独立成子模块

| 维度 | 若合并在 M13-02 | 独立为 M13-03 |
|---|---|---|
| 技术栈 | 文件系统操作 + watchdog，纯 IO | OCR + 文本解析 + 正则引擎 + 模板管理 |
| 单次耗时 | 入库 ≤ 500ms | 文本层 0.3~0.8 秒，OCR 3~12 秒 |
| 失败影响 | 采集失败 → 该文件没进系统 | 解析失败 → 文件在，但数据不可用 |
| 重试语义 | 重读文件即可 | 要区分文本层失败、OCR 失败、模板不匹配、字段缺失 |
| 资源类型 | 磁盘 + 网络 | CPU + 内存 + OCR 模型（约 15MB） |
| 变更频率 | 极低（路径与阈值固定） | 高（每台新设备都要加模板） |
| 责任边界 | 运维 + 检验科信息员 | 检验科 + 医务科（数据正确性） |

四条核心理由：

1. **技术栈完全不同**。M13-02 是文件系统操作加 watchdog 监听，纯 IO 密集；M13-03 是 OCR 加文本解析加正则引擎，纯 CPU 密集。合并后镜像会大 400MB（PaddleOCR 模型 + OpenCV + numpy），OCR 模型更新会重启采集服务，导致正在写入的文件被漏掉。

2. **处理时长差一个量级**。采集入库 ≤ 500ms，OCR 解析 3~12 秒。同进程处理会让"5 秒内完成文件采集"的 SLA 无法保证。

3. **绑定是全局最难的业务问题**。这在本项目里尤其突出：设备无法接入 HIS，PDF 里没有就诊号，文件名是设备随机生成的，唯一线索只有"报告上的姓名"与"文件创建时间"。这是一个需要独立设计、独立测试、独立监控的子系统，不是随手能加的某个函数。

4. **失败后的处置完全不同**。采集失败 = 重试或隔离；解析失败 = 人工介入改模板或手工录入；绑定失败 = 进待确认队列由护士认领。三种失败三种流程三种角色，混在一起会让"待确认队列"变成什么都往里塞的垃圾桶。

**唯一责任：** M13-03 是唯一把"文件"翻译成"数据"的地方。它**不产生任何业务动作**——不审核、不推送、不改任务状态，只输出解析记录等待下游消费。

**关键分工：参考区间判定的边界。** M13-03 做"初判"：按 M13-05 提供的区间算出 `NORMAL` / `HIGH` / `LOW` / `CRITICAL_HIGH` / `CRITICAL_LOW`。M13-04 做"复核"：审核医师看到标记后确认或修正。二者不重复，因为初判是机械计算，复核是临床判断。

### 1.4 概念辨析

**解析 ≠ 识别。** 识别（OCR）只负责把图片变成字符，包含错字、错位、断行。解析（Parsing）负责在字符流里找到"白细胞计数是 6.2"这个结构化事实。一件 OCR 准确率 99% 的报告，如果解析规则写错，仍然可能把所有项目的值都对到上一行。

**文本层 ≠ OCR。** 数字 PDF（打印机直接生成的）内部含文本层，`pypdf.extract_text()` 可以直接取出 100% 准确的字符，不需要 OCR。扫描件（纸质报告扫描或拍照）只有像素，必须 OCR。本项目约 85% 是数字 PDF。

**绑定 ≠ 归档。** 绑定是把文件关联到检验任务（"这是张三的血常规"），归档是把文件挪到长期存储目录（"这个文件放在 ARCHIVE\2026\10\22"）。先绑定后归档，二者互不影响。

**置信度 ≠ 准确率。** OCR 引擎给出的 confidence 是它对自己识别结果的把握程度，不是正确率。`238` 被识别成 `288` 时，字符置信度仍可能是 0.98。这就是为什么关键数值字段必须强制人工确认（见 3.4 节）。

**无主 ≠ 丢失。** 无主（`ORPHAN`）指文件在、解析成功，但绑不到任何检验任务。丢失（`is_missing`）指文件本身从磁盘上消失了。前者是数据问题，后者是存储问题。

### 1.5 模块目标

| 指标 | 目标 | 衡量方式 |
|---|---|---|
| 自动绑定率 | ≥ 96% | `bind_status='BOUND'` / 总解析数 |
| **错绑率** | **0** | 人工抽查 + 医生投诉 |
| 文本层识别耗时 | P95 ≤ 800ms | APM 埋点 |
| OCR 识别耗时 | P95 ≤ 12s | APM 埋点 |
| 字段抽取准确率 | ≥ 98% | 人工修改数 / 总字段数 |
| 关键字段确认率 | 100% | 关键字段未确认不可发布 |
| 模板覆盖率 | ≥ 99.5% | 匹配到专用模板的比例 |
| 解析失败率 | ≤ 0.5% | `PARSE_FAILED` / 总解析数 |
| 待确认队列存量 | ≤ 30 条 | 实时监控 |
| 待确认处理时长 | P95 ≤ 30 分钟 | 队列进出时间差 |

**为什么自动绑定率目标定 96% 而不是 99%？**

剩下 4% 是客观上无法自动判定的：

| 场景 | 占比 | 为什么自动不了 |
|---|---|---|
| 同名同姓同年龄同时段 | 约 0.3% | 姓名+性别+年龄完全相同，只能靠就诊号/诊断区分 |
| 技师忘点开始/完成 | 1~2% | 没有时间窗，无从匹配 |
| OCR 认不出姓名 | 约 0.5% | 打印模糊或字体特殊 |
| 跨院区/跨科室时间窗重叠 | 约 0.2% | 多候选 |
| 设备时钟偏差过大 | 约 0.5% | 文件时间落在窗口外 |

追求 99% 的唯一办法是放宽匹配条件（允许姓名差一个字、允许时间窗扩大到几小时），代价就是错绑。**错绑必须是 0——不是"尽量低"，而是架构上不允许。** 详见 3.4 节的四道闸门。

### 1.6 关键业务角色

| 角色 | 职责 | 在本子模块的权限 |
|---|---|---|
| 检验技师 | 处理待确认队列、修正解析字段 | `query` + `edit` + `bind` |
| 检验科信息员 | 维护解析模板、处理解析失败 | `query` + `manage` + `template` |
| 检验科主任 | 全流程监督、模板审批 | 全部（除 `config`） |
| 医务科 | 查看解析质量、处理投诉 | `query` + `stat` |
| 质控科 | 抽查解析准确率 | `query` + `stat` |
| 临床医师 | 只读查看解析结果（实际从 M07-04 看） | `query` |
| IT 管理员 | 部署 OCR、维护配置 | `query` + `manage` + `template` + `config` |

**为什么临床医师只有 `query`？** 医师需要理解报告内容（在 M07-04 看已发布的结果），但不需要也不应该修改解析字段。修改解析字段是检验科的职责——数据源头改错要由数据源头改。

```
│                        M13-03 六阶段流水线                            │
├───────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐          │
│  │ PENDING  │──►│EXTRACTING│──►│  OCRING  │──►│ PARSING  │          │
│  │ 待解析    │   │ 提取文本  │   │ 图像识别  │   │ 字段抽取  │          │
│  └──────────┘   └────┬─────┘   └────┬─────┘   └────┬─────┘          │
│                      │              │              │                 │
│             有文本层  │     无文本层   │              │                 │
│                      │              │              ▼                 │
│                      │              │        ┌──────────┐            │
│                      │              │        │  PARSED  │            │
│                      │              │        │ 解析完成  │            │
│                      │              │        └──────────┘            │
│                      └──────────────┴──────────────┘                 │
│                                          │                            │
│                       任一步骤失败        │                            │
│                                          ▼                            │
│                                 ┌────────────────┐                    │
│                                 │  PARSE_FAILED  │                    │
│                                 │   解析失败      │                    │
│                                 └────────┬───────┘                    │
│                                          │ retry < 3                  │
│                                          ▼                            │
│                                    （回 PENDING）                     │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

**为什么把 `EXTRACTING` / `OCRING` / `PARSING` 分成三个状态？**

| 状态 | 耗时 | 失败原因 | 人工处置 |
|---|---|---|---|
| `EXTRACTING` | 50~200ms | PDF 损坏、加密、超大 | 换文件或提供密码 |
| `OCRING` | 3~10s | OCR 服务不可用、图像质量差 | 等恢复或手工录入 |
| `PARSING` | 100~500ms | 模板不匹配、字段缺失 | 改模板或手工录入 |

三者的耗时差 50 倍，失败原因完全不同，处置方式也完全不同。如果只有一个 `PARSING` 状态，页面上会显示"解析中"卡了 10 秒，运维完全不知道卡在 OCR 还是卡在模板。

### 3.2 双通道抽取模型

这是本子模块的核心设计。同一份 PDF 要抽取两类信息，它们的错误代价相差一个数量级。

```
┌───────────────────────────────────────────────────────────────────────┐
│                          双通道抽取                                   │
├───────────────────────────────────────────────────────────────────────┤
│                                                                       │
│   PDF 文本（或 OCR 文本）                                             │
│         │                                                             │
│    ┌────┴────┐                                                        │
│    │         │                                                        │
│    ▼         ▼                                                        │
│  ┌──────────────┐              ┌──────────────────────────────┐      │
│  │  通道 A       │              │        通道 B                │      │
│  │ 患者身份信息  │              │      检验结果数据             │      │
│  ├──────────────┤              ├──────────────────────────────┤      │
│  │ 姓名          │              │ 项目名（白细胞计数）          │      │
│  │ 性别          │              │ 结果值（6.2）                │      │
│  │ 年龄          │              │ 单位（10^9/L）               │      │
│  │ 检验日期      │              │ 参考区间（3.5-9.5）          │      │
│  │              │              │ 异常标记（↑）                │      │
│  └──────┬───────┘              └──────────────┬───────────────┘      │
│         │                                     │                       │
│         ▼                                     ▼                       │
│  ┌──────────────┐              ┌──────────────────────────────┐      │
│  │ 用于患者绑定  │              │      用于医生查看             │      │
│  └──────────────┘              └──────────────────────────────┘      │
│         │                                     │                       │
│         ▼                                     ▼                       │
│  错误代价：灾难性                     错误代价：可控                   │
│  · 隐私泄露                          · 医生能看到参考区间              │
│  · 误诊                              · 异常值会被标红                  │
│  · 医疗纠纷                          · 可重新解析                      │
│  · 无补救可能                        · 有多次机会                     │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

**两通道的策略差异：**

| 处理动作 | 通道 A（身份） | 通道 B（数据） |
|---|---|---|
| 姓名匹配 | **必须完全一致**才自动绑定 | 不做匹配判断 |
| 置信度阈值 | 不适用（只有 0/1） | ≥95% 自动采用，70~95% 标黄，<70% 标红 |
| 缺失处理 | 无法绑定 → 进待确认 | 该字段留空，其余正常 |
| 数值校验 | 不做 | 用 M13-05 的小数位与单位校验 |
| 交叉验证 | **必须与报告抬头姓名一致** | 不适用 |
| 人工确认 | 全部需要（绑定本身是人工动作） | 仅关键字段需确认 |

**为什么姓名必须完全一致？**

中文姓名的编辑距离小到危险：

| 对 | 编辑距离 | 是同一人吗 |
|---|---|---|
| 张伟 / 张玮 | 1 | **否** |
| 王芳 / 王方 | 1 | **否** |
| 李娜 / 李那 | 1 | **否** |
| 陈静 / 陈靖 | 1 | **否** |
| 刘阳 / 刘洋 | 1 | **否** |

允许"1 个字的容错"，正确率提升不到 0.5%（真正属于同一人的情况极罕见），但错绑风险从 0 提到万分之几。按每年 15 万份报告算，万分之三就是 45 次错绑——45 次隐私泄露。

**为什么年龄允许 1 岁容差？**

不同设备软件的年龄算法不同：

```python
# 算法 1：完整年数
age = (today - birth).days // 365

# 算法 2：年份相减
age = today.year - birth.year

# 算法 3：按周岁（含生日判断）
age = today.year - birth.year - ((today.month, today.day) < (birth.month, birth.day))
```

在患者生日当天，算法 2 与算法 5 会差 1 岁。这个容差**仅用于多候选辅助筛选**，不单独作为绑定依据——即便年龄对上，姓名也必须完全一致。

### 3.4 错绑防护四道闸门

**闸门一：只有唯一命中才自动绑定。** 命中 ≥2 个候选任务一律进待确认队列。这条最重要——它把"错绑"从概率问题变成了不可能事件。

```python
if len(matched) == 1:
    bind_type = "WINDOW"
    bind_status = "BOUND"
elif len(matched) == 0:
    bind_status = "UNCONFIRMED"
    unconfirmed_reason = "NO_MATCHING_WINDOW"
else:
    bind_status = "UNCONFIRMED"
    unconfirmed_reason = "SAME_NAME_AMBIGUOUS"
```

**闸门二：`is_ambiguous=TRUE` 的窗口不参与自动绑定。** 当两个技师的操作时间窗重叠（比如共用同一台设备的两个操作位），该时段任何 PDF 都可能是其中任何一次检查的产物，一律进待确认。

**闸门三：一个检验任务只能有一份有效报告。** 数据库唯一索引兜底：

```sql
CREATE UNIQUE INDEX uk_m13_parse_task_bound
    ON m13_parse_record (bound_task_id)
    WHERE bind_status = 'BOUND'
      AND is_deleted = FALSE
      AND is_superseded = FALSE;
```

**闸门四：双通道交叉验证。** 通道 A 抽出的姓名与报告抬头姓名不一致时，`is_cross_conflict=TRUE`，整条记录标红并强制进待确认。这一闸防的是模板抽错位置——比如某台仪器的姓名印在第二页，模板加了 `page=1` 限制导致抽到空值，或者抽到了"主治医师：张伟"。

### 3.5 置信度分级模型

```
┌───────────────────────────────────────────────────────────────────────┐
│                      置信度三层计算                                   │
├───────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  层 1：字符级                                                        │
│  ┌────────────────────────────────────────────────┐                   │
│  │ PaddleOCR 为每个识别框给出 confidence            │                   │
│  │ '白' 0.998  '细' 0.995  '胞' 0.992  '6' 0.981   │                   │
│  │ '.' 0.976  '2' 0.958                            │                   │
│  └────────────────────────────────────────────────┘                   │
│                        │                                             │
│                        ▼                                             │
│  层 2：字段级 = 该字段涉及字符的【最小值】                            │
│  ┌────────────────────────────────────────────────┐                   │
│  │ 项目名"白细胞计数" = min(0.998,0.995,0.992) = 0.992                │
│  │ 结果值"6.2"       = min(0.981,0.976,0.958) = 0.958                │
│  └────────────────────────────────────────────────┘                   │
│                        │                                             │
│                        ▼                                             │
│  层 3：整体 = 全部 required 字段的算术平均                            │
│  ┌────────────────────────────────────────────────┐                   │
│  │ (0.992+0.958+0.987+…) / N                       │                   │
│  └────────────────────────────────────────────────┘                   │
│                                                                       │
│  为什么字段级取最小值？                                               │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │ 数字 '2.38' 被识别成 '2.3B'                                    │  │
│  │ 字符置信度：'2'0.99  '.'0.97  '3'0.99  'B'0.96                 │  │
│  │ 平均值 = 0.9775 → 高于 0.95 阈值 → 自动采用                     │  │
│  │ 但 'B' 意味着这个数完全不可用！                                 │  │
│  │ 取最小值 = 0.96 → 仍需人工，正确的做法                          │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

**三档处理：**

| 字段置信度 | 标记 | 处理方式 |
|---|---|---|
| ≥ 0.95 | 正常 | 自动采用，仅留痕 |
| 0.70 ~ 0.95 | `WARN` | 标黄，进待确认队列建议核对 |
| < 0.70 | `DANGER` | 标红，必须人工修改后才能确认 |

**关键数值字段清单（无论置信度多高都强制人工确认）：**

| 字段 | 中文 | 为什么 |
|---|---|---|
| `WBC` | 白细胞计数 | 判断感染与血液系统疾病的核心指标 |
| `HGB` | 血红蛋白 | 判断贫血程度，决定是否输血 |
| `PLT` | 血小板计数 | 低于 20 需紧急处理 |
| `K` | 血钾 | 高于 6.0 可致心脏骤停 |
| `NA` | 血钠 | 低于 120 可致意识障碍 |
| `GLU` | 血糖 | 低于 2.8 可致昏迷 |
| `ALT` | 谷丙转氨酶 | 判断肝损伤 |
| `CR` | 肌酐 | 决定用药剂量 |
| `PT` | 凝血酶原时间 | 术前必查 |
| `INR` | 国际标准化比值 | 抗凝治疗监测 |

**为什么这些字段强制确认？**

OCR 对数字的错误有一个危险特性：**错的时候看起来非常自信**。`238` → `288`，`6.2` → `6.7`，`3.5-9.5` → `3.5-3.5`，字符置信度都可能 0.97 以上，因为字形本身相似，引擎没有理由怀疑自己。

代价：每份含 10 个关键字段的报告多花约 15 秒确认。
收益：危急值误判率从约 0.5% 降到 0。

按每年 15 万份检验报告、其中 30% 是需要确认的类型算，每年多花 187 小时工时（约 1 个人月），换来的是 225 次危急值误判的避免。**这个交换是值得的。**

### 3.7 参考区间与危急值初判

```
┌───────────────────────────────────────────────────────────────────────┐
│                     结果值判定流程                                    │
├───────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  解析出的结果值（字符串）                                             │
│         │                                                             │
│         ▼                                                             │
│  ① 类型判定（用 M13-05 的 result_type）                                │
│     ├─ QUANTITATIVE      → 转 Decimal，做数值判定                     │
│     ├─ QUALITATIVE       → 阴性/阳性，按参考值文本比对                │
│     ├─ SEMI_QUANTITATIVE → -/±/+/++/+++，按序数比对                   │
│     └─ TEXT              → 不做判定，原样展示                         │
│         │                                                             │
│         ▼                                                             │
│  ② 参考区间查找（M13-05，按 性别 + 年龄 匹配）                         │
│     ├─ 命中 → 得到 [low, high]                                        │
│     └─ 未命中 → 用报告上的区间文本，标记 ref_source='REPORT'           │
│         │                                                             │
│         ▼                                                             │
│  ③ 高低标记                                                           │
│     value < low   → 'LOW'                                             │
│     value > high  → 'HIGH'                                            │
│     其他          → 'NORMAL'                                          │
│         │                                                             │
│         ▼                                                             │
│  ④ 危急值判定（M01-09 阈值 + M13-05 区间上的 is_critical_low/high）    │
│     value < critical_min  → 'CRITICAL_LOW'                            │
│     value > critical_max  → 'CRITICAL_HIGH'                           │
│     否则沿用 ③ 的结果                                                  │
│         │                                                             │
│         ▼                                                             │
│  ⑤ 写入 m13_parse_lab_item                                            │
│     flag 字段 + is_critical + critical_direction                      │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

**判定粒度：** M13-03 只做机械判定，标出 `HIGH`/`LOW`/`CRITICAL_*`。**是否真的要报危急值，由 M13-04 的审核医师决定**——因为有些"危急值"可能是标本溶血导致的假性高钾。

**无规则时的处理：**

| 情况 | 处理 | 原因 |
|---|---|---|
| M13-05 无参考区间 | 用报告上的区间文本，`ref_source='REPORT'` | 报告上通常印了区间 |
| 报告也无区间 | `flag=NULL`，`ref_source='NONE'` | 无法判定 ≠ 正常 |
| M01-09 无危急规则 | 不判危急值，记 `skipped_critical=TRUE` | 主数据缺失，不能凭空报 |
| 结果值非数值型 | 跳过数值判定 | 定性结果不适用 |

### 3.8 待确认队列模型

```
┌───────────────────────────────────────────────────────────────────────┐
│                     待确认队列五原因                                  │
├───────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  原因代码              优先级权重    典型处理动作                      │
│  ────────────────────────────────────────────────────────────────     │
│  OCR_FAILED              30       重新 OCR 或手工录入                 │
│  NO_MATCHING_WINDOW      20       查该时段做过的检验，看缺哪一份       │
│  PATIENT_NOT_FOUND       15       核对姓名，可能是模板抽错位置         │
│  WINDOW_OVERLAP          10       看两次检查的科室/医师区分            │
│  SAME_NAME_AMBIGUOUS      5       看就诊号/诊断/医师区分同名患者       │
│                                                                       │
│  排序：priority DESC, created_at ASC                                  │
│  （先处理权重高的，同权重先处理等待久的）                              │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

**为什么 `SAME_NAME_AMBIGUOUS` 优先级最低？**

因为它需要人工查更多信息（就诊号、诊断、接诊医师），一单 2~3 分钟；而 `NO_MATCHING_WINDOW` 是一眼就能认的情况（"那个时段只做了一次血常规，就是这个文件"），一单 10 秒。

把耗时的放前面会堵住队列，把快的放前面能快速清空。

**待确认页必须显示的信息：**

| 信息 | 来源 | 作用 |
|---|---|---|
| 报告缩略图 | M13-02 文件预览 | 一眼核对真实内容 |
| OCR 出的姓名/性别/年龄 | 通道 A | 与缩略图对照 |
| 候选任务列表 | 时间窗匹配结果 | 直接选人 |
| **候选的就诊号/接诊医师/诊断** | M13-01 关联 M07 | **同名歧义时唯一能区分的依据** |
| 文件时间 vs 时间窗 | M13-01 | 判断时间是否合理 |

**为什么必须显示就诊号/医师/诊断？**

同名歧义时，两个"李娜"的唯一区别就是"一个是白内障门诊、一个是青光眼门诊"，"一个是张医生接的、一个是王医生接的"。没有这些信息，护士只能去翻 PDF 或查病历系统，一单 3 分钟；有了这些信息，一单 10 秒。

### 3.9 超期与升级模型

```
┌───────────────────────────────────────────────────────────────────────┐
│                     待确认超期升级                                    │
├───────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  等待时长         状态        通知对象          通知方式               │
│  ────────────────────────────────────────────────────────────────     │
│  0 ~ 30 分钟     正常        —                 —                      │
│  30 分钟 ~ 4 小时 提醒       检验科护士          站内信                 │
│  4 ~ 24 小时      催办       检验科主任          站内信 + 短信          │
│  24 小时 ~ 7 天   待办       科主任待办          待办列表               │
│  > 7 天           无主       自动置 ORPHAN      标记为无主报告          │
│                                                                       │
│  置 ORPHAN 后：                                                       │
│  · 文件仍保留，数据不丢失                                             │
│  · 从待确认队列移出                                                  │

│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

**为什么 7 天就置无主？** 检验报告的有效临床意义约为 7 天（超过这个时间的门诊检验通常已重做）。留太久会让待确认队列膨胀，反而掩盖新问题。置 `ORPHAN` 不是删除数据，仍可重新认领。

解析成功率是滞后的——报告解析失败时人已经知道去处理了。模板命中率是**先行的**：某台仪器升级了软件、报告标题变了，命中率会从 99% 掉到 68%，但因为有 GENERIC_V1 兜底，解析仍然"成功"（只是没抽到结果）。这时成功率还是 100%，只有命中率能暴露问题。

**为什么用"双击修改"而不是"每行一个输入框"？**

正常情况 95% 的字段都是对的。如果每行都放输入框，页面看起来像一张全是方框的表单，眼睛反而看不清数据；而且鼠标移到输入框就会误触发。

双击才进入编辑，是"默认只读、需要时才改"的最小干扰设计。

**为什么允许"新增行"？**

仪器出的报告有时缺项：血常规报告里印了"镜检：白细胞形态"，但仪器的结构化输出里没有这一项。检验技师需要用镜检结果补充。没有新增功能，技师只能放弃，导致医生少看到一条信息。

**为什么标题正则必须带锚点？**

不带锚点的 `血常规` 会在"尿常规 血常规 生化"这种组合报告标题里误命中。带锚点的 `^血常规(检验)?报告单?$` 才精确。

**为什么强制"启用前回归"？**

真实场景：某台仪器软件升级，报告标题从"尿常规分析报告"变成"尿常规分析报告(新版)"。信息员新建 V2 模板，但正则写成了 `^尿常规分析报告$`（忘了加"(新版)"），启用后所有尿常规报告都匹配不上，全部进失败列表。

回归测试用最近 100 份同设备样本跑一遍。判据三条全满足才能启用：

| 判据 | 阈值 | 理由 |
|---|---|---|
| 整体命中率 | ≥ 98% | 抽到大部分字段 |
| 每个必填字段命中率 | ≥ 90% | 必填抽不到就是解析失败 |
| 单个字段相比旧版下降 | ≤ 2% | **防止"总体达标但关键字段恶化"** |

第三条是关键：若 CMT 从 99% 降到 88%（-11%）而其他字段大幅改善，整体仍可能 98% 达标，但 CMT 每 10 份有 1 份抽不到。对检验项目来说，这个字段可能是"血钾"——抽不到医生就看不到血钾。

| `"1303021"` | 查询日期跨度超过 366 天 | 日期区间过大 |
| `"1303022"` | 导出行数超过 50000 行 | 导出范围过大 |
| `"1303023"` | 模板编码格式错误 | 非大写字母下划线 |
| `"1303024"` | 标题正则格式错误 | 缺少 `^` `$` 锚点或编译失败 |
| `"1303025"` | 字段编码重复 | 同模板内 `field_code` 重复 |
| `"1303026"` | 至少需要一个必填字段 | `required_count = 0` |
| `"1303027"` | 正则抽取规则不完整 | `REGEX` 缺 pattern 或 group_index |
| `"1303028"` | 抽取规则参数缺失 | `SECTION` 起止相同 / `COORD` 无锚点 |
| `"1303029"` | 回归测试未通过，禁止启用 | 命中率或字段下降超阈值 |
| `"1303030"` | 系统模板不可停用或删除 | `GENERIC_V1` 被停用 |
| `"1303031"` | 模板不存在 | 模板 ID 无效 |
| `"1303032"` | 该设备已有同名当前版本 | 唯一索引冲突 |
| `"1303033"` | 数据源服务不可用 | M13-02 / M13-01 调用失败 |
| `"1303034"` | 解析记录不存在 | 记录 ID 无效 |
| `"1303035"` | 配置参数值超出范围 | 参数校验失败 |

```python
        logger.info(

    @classmethod
    async def run_pipeline(
        cls, db: AsyncSession, parse_id: int
    ) -> M13ParseRecord:
        """执行完整解析流水线。"""
        record = await cls._get_for_update(db, parse_id)
        started = time.monotonic()

        try:
            # ① 提取文本
            await cls._set_status(db, record, "EXTRACTING")
            filed = await CollectClient.get_file(db, record.file_id)
            if not filed.get("found"):
                raise BizException("1303001", "文件不存在")

            pdf_bytes = await CollectClient.get_content(
                db, record.file_id)
            raw_text, mode, conf, page_count = await cls._extract(
                pdf_bytes, record)

            record.extract_mode = mode
            record.page_count = page_count
            record.raw_text = raw_text[:100_000]
            record.ocr_confidence = (
                Decimal(str(round(conf, 4))) if conf else None)

            # ② 模板匹配
            await cls._set_status(db, record, "PARSING")
            template = await TemplateMatcher.match(
                db, record.device_code, raw_text)

            if template is None:
                raise BizException(
                    "1303029", "模板不匹配：未找到可用模板")

            record.template_code = template.template_code
            record.template_version = template.version_no

            # ③ 字段抽取
            extractor = FieldExtractor(template)
            fields, missing_required = await asyncio.get_event_loop(
            ).run_in_executor(
                None, extractor.extract, raw_text)

            if missing_required:
                raise BizException(
                    "1303006",
                    "必填字段缺失：%s" % "、".join(missing_required))

            await cls._save_fields(db, record, fields)

            # ④ 患者绑定
            bind_result = await BindingService.resolve(
                db, record, fields)

            # ⑤ 参考区间与危急值判定
            await cls._judge_results(db, record, fields)

            # ⑥ 完成
            elapsed = int((time.monotonic() - started) * 1000)
            record.parse_status = "PARSED"
            record.finished_at = datetime.now()
            record.elapsed_ms = elapsed
            record.match_template_id = template.id
            record.bind_status = bind_result["bind_status"]
            record.bound_task_id = bind_result.get("task_id")
            record.bind_type = bind_result.get("bind_type")
            record.bound_at = bind_result.get("bound_at")
            record.bind_message = bind_result.get("message")
            record.patient_name = bind_result.get("patient_name")
            record.gender = bind_result.get("gender")
            record.age = bind_result.get("age")
            record.lab_count = bind_result.get("lab_count", 0)
            record.cross_conflict = bind_result.get(
                "cross_conflict", False)
            await db.commit()

            # ⑦ 模板计数
            await TemplateMatcher.bump(
                db, template.id, success=True)

            # ⑧ 推 M13-02
            await cls._notify_collect(db, record)

            # ⑨ 待确认入库
            if record.bind_status == "UNCONFIRMED":
                await UnconfirmedService.enqueue(
                    db, record, bind_result.get("reason"))

            return record

        except BizException as exc:
            await cls._mark_failed(db, record, exc.code, exc.message)
            raise
        except Exception as exc:
            logger.exception(
                "解析流水线异常",
                extra={"module": "M13-03",
                       "action": "run_pipeline",
                       "parse_id": parse_id})
            await cls._mark_failed(
                db, record, "1303006", str(exc)[:200])
            raise

    @classmethod
    async def _extract(
        cls, pdf_bytes: bytes, record: M13ParseRecord
    ) -> Tuple[str, str, Optional[float], int]:
        """提取文本：文本层优先，否则 OCR。"""
        reader = pypdf.PdfReader(
            __import__("io").BytesIO(pdf_bytes))

        if reader.is_encrypted:
            raise BizException("1303003", "PDF 已加密需要密码")

        page_count = len(reader.pages)
        if page_count > 50:
            raise BizException("1303005", "PDF 页数超限")

        # 文本层
        try:
            parts = [page.extract_text() or ""
                     for page in reader.pages]
            text_layer = "\n".join(parts).strip()
        except Exception:
            text_layer = ""

        if len(text_layer) >= cls.MIN_TEXT_LENGTH:
            return text_layer, "TEXT_LAYER", None, page_count

        # OCR
        await cls._set_status(
            __import__("contextlib")._threading_local, record,
            "OCRING") if False else None
        record.parse_status = "OCRING"
        await db_commit_silent()

        images = await OcrEngine.rasterize(
            pdf_bytes, dpi=int(await cls._cfg(
                "M13.PARSE.OCR_DPI", "200")))
        text, confidence = await OcrEngine.recognize(images)
        return text, "OCR", confidence, page_count

    @classmethod
    async def _judge_results(
        cls, db: AsyncSession, record: M13ParseRecord,
        fields: List[Dict[str, Any]]
    ) -> None:
        """参考区间判定与危急值初判。"""
        refs = await ClinicalClient.get_ref_ranges(
            db, [f["field_code"] for f in fields
                 if f.get("is_measure")])
        criticals = await ClinicalClient.get_critical_rules(
            db, [f["field_code"] for f in fields
                 if f.get("is_measure")])

        for field in fields:
            if not field.get("is_measure"):
                continue
            code = field["field_code"]
            raw = field.get("value")
            try:
                num = Decimal(str(raw))
            except (InvalidOperation, TypeError):
                field["flag"] = None
                field["ref_source"] = "NONE"
                continue

            ref = refs.get(code, {})
            low = ref.get("range_low")
            high = ref.get("range_high")
            if low is not None and high is not None:
                field["ref_source"] = "MDM"
                field["ref_low"] = low
                field["ref_high"] = high
            else:
                field["ref_source"] = "REPORT"
                low = field.get("ref_low")
                high = field.get("ref_high")

            flag = "NORMAL"
            if low is not None and num < Decimal(str(low)):
                flag = "LOW"
            elif high is not None and num > Decimal(str(high)):
                flag = "HIGH"

            crit = criticals.get(code, {})
            cmin = crit.get("critical_min")
            cmax = crit.get("critical_max")
            if cmin is not None and num < Decimal(str(cmin)):
                flag = "CRITICAL_LOW"
                field["is_critical_result"] = True
            elif cmax is not None and num > Decimal(str(cmax)):
                flag = "CRITICAL_HIGH"
                field["is_critical_result"] = True

            field["flag"] = flag

    @classmethod
    async def _mark_failed(
        cls, db: AsyncSession, record: M13ParseRecord,
        code: str, message: str
    ) -> None:
        """标记失败并记录快照。"""
        record.parse_status = "PARSE_FAILED"
        record.fail_code = code
        record.fail_reason = message[:500]
        record.finished_at = datetime.now()
        record.retry_count += 1

        failure = M13ParseFailure(
            parse_id=record.id,
            parse_no=record.parse_no,
            file_id=record.file_id,
            attempt_no=min(record.retry_count, 3),
            fail_reason=cls._reason_of(code),
            fail_detail=message[:500],
            detected_title=cls._detect_title(record.raw_text),
            raw_text_head=(record.raw_text or "")[:2000],
            can_auto_recover=code in (
                "1303007", "1303008", "1303033"),
        )
        db.add(failure)
        await db.commit()

class TemplateService:
    """模板管理服务。"""

    MIN_OVERALL_RATE = Decimal("0.98")
    MIN_FIELD_RATE = Decimal("0.90")
    MAX_FIELD_DROP = Decimal("0.02")

    @classmethod
    async def regression(
        cls, db: AsyncSession, template_id: int, body: Any,
        user: Any
    ) -> Dict[str, Any]:
        """回归测试：最近 N 份同设备样本。"""
        tpl = await db.get(M13ParseTemplate, template_id)
        if not tpl:
            raise BizException("1303031", "模板不存在")

        samples = await cls._load_samples(
            db, tpl.device_code, body.sample_size or 100)
        if not samples:
            raise BizException("1303033", "无可用样本")

        extractor = FieldExtractor(tpl)
        total_ok = 0
        field_stat: Dict[str, Dict[str, int]] = {}

        for sample in samples:
            try:
                fields, _ = extractor.extract(sample["raw_text"])
            except Exception:
                continue
            hit = {f["field_code"]: f.get("value")
                   for f in fields}
            all_ok = True
            for rule in tpl.field_rules:
                code = rule["field_code"]
                bucket = field_stat.setdefault(
                    code, {"total": 0, "ok": 0})
                bucket["total"] += 1
                if hit.get(code) not in (None, ""):
                    bucket["ok"] += 1
                else:
                    all_ok = False
            if all_ok:
                total_ok += 1

        overall = (Decimal(total_ok) / Decimal(len(samples))
                   ).quantize(Decimal("0.0001"))
        failed = []
        if overall < cls.MIN_OVERALL_RATE:
            failed.append("整体命中率 %.2f%% 低于 98%%"
                          % (float(overall) * 100))
        for code, stat in field_stat.items():
            rate = Decimal(stat["ok"]) / Decimal(stat["total"])
            if rate < cls.MIN_FIELD_RATE:
                failed.append("字段 %s 命中率 %.2f%% 低于 90%%"
                              % (code, float(rate) * 100))

        passed = not failed
        return {
            "template_code": tpl.template_code,
            "version_no": tpl.version_no,
            "sample_size": len(samples),
            "overall_rate": float(overall),
            "criteria": {
                "min_overall_rate": 0.98,
                "min_field_rate": 0.90,
                "max_field_drop": 0.02,
            },
            "field_rates": [
                {
                    "field_code": code,
                    "rate": float(
                        Decimal(stat["ok"])
                        / Decimal(stat["total"])),
                }
                for code, stat in field_stat.items()
            ],
            "passed": passed,
            "failures": failed,
        }
```

**本项目约 85% 是数字 PDF，为什么？**

本项目检验仪器（血细胞分析仪、生化分析仪、凝血仪、尿液分析仪、化学发光免疫分析仪）的报告都是工作站软件直接生成的 PDF 打印件，是标准的数字 PDF：内置 TrueType 字体，文本对象完整，`extract_text()` 一次就能取出全部文字。

只有两类是扫描件：

1. **手工打印再扫描的报告**：仪器不支持 PDF 导出，只能打印纸质报告，再用扫描仪扫成 PDF。约 10%。
2. **外送检验的回传报告**：外送机构发来的是扫描件。约 5%。

**不做判断的代价：**

| 项目 | 数字 PDF（85%） | 扫描件（15%） |
|---|---|---|
| 不做判断全部 OCR | 3~12s | 3~12s |
| 判断后 | 0.05~0.2s | 3~12s |
| 每 1000 份总耗时 | 3,000~12,000s | 约 1,000s |

按每天 420 份算：

| 策略 | 每日总耗时 | 需要并发 |
|---|---|---|
| 全部 OCR | 1,260~5,040 秒 | 4~16 |
| 文本层优先 | 约 300 秒 | 1~2 |

差了 4~17 倍。而且 OCR 会引入本可避免的识别错误——数字 PDF 走 OCR，等于故意把 100% 准确的信息降级成 97% 准确。

**判定阈值的取值：**

首页文本层字符数 ≥ 20 才认为是数字 PDF。为什么是 20？

| 字符数 | 判断 |
|---|---|
| 0 | 纯图像 |
| 1~5 | 可能是水印或页码，内容仍是图像 |
| 6~19 | 可能是标题文字 + 图像正文（如扫描件带了 OCR 层但没做完） |
| **≥ 20** | 有实质文字内容，是数字 PDF |

阈值配成参数 `M13.PARSE.MIN_TEXT_LENGTH`，默认 20，可按实际情况调整。

| **合计** | — | — | **约 590KB** |

**为什么模板缓存 TTL 1800s？** 模板变更频率很低（一周可能改一次），长 TTL 减少数据库压力。模板更新时主动删除缓存（`TemplateService.update` 末尾 `redis.delete`）。

**为什么模板匹配缓存要按"文本前 100 字符哈希"？** 同一模板处理不同报告时匹配结果相同，但按模板 ID 缓存会漏——因为要先知道用哪个模板才能查 ID。用报告特征（前 100 字符）做 key，直接把"特征 → 模板"缓存下来。

### 7.4 OCR 并发控制

**实测数据（服务器 8 核 16GB，PaddleOCR 中文模型）：**

| 并发数 | 单页耗时 | CPU 占用 | Web 接口 P95 | 吞吐（页/秒） |
|---|---|---|---|---|
| 1 | 2.6s | 25% | 180ms | 0.38 |
| **2** | **2.8s** | **48%** | **210ms** | **0.71** |
| 4 | 4.1s | 82% | 620ms | 0.98 |
| 8 | 8.7s | 100% | 2,400ms | 0.92 |

**结论：并发 2 时吞吐最优且不影响 Web 接口。**

为什么并发 4 吞吐更高却不用？因为 82% CPU 下 Web 接口 P95 从 210ms 升到 620ms，超过 300ms 的验收线。而并发 8 时吞吐反而下降（0.92 < 0.98），原因是 CPU 争抢导致上下文切换开销吃掉收益。

**瓶颈不在 OCR，而在"OCR 抢了 Web 的 CPU"。** 配置 `M13.PARSE.OCR_CONCURRENCY=2`，用 Redis 信号量控制。

### 9.4 安全措施

1. **正则 ReDoS 防护**：`safe_search(pattern, text)` 用 `signal.SIGALRM` 设 2 秒超时，超时抛错。`MAX_PATTERN_LEN=500`、`MAX_TEXT_LEN=200000`。

```python
"""正则安全执行。"""
import re
import signal

from app.core.exceptions import BizException

MAX_PATTERN_LEN = 500
MAX_TEXT_LEN = 200_000
REGEX_TIMEOUT = 2


def safe_search(
    pattern: str, text_src: str, group: int = 1
) -> str:
    """带超时保护的正则搜索。"""
    if len(pattern) > MAX_PATTERN_LEN:
        raise BizException("1303024", "正则长度超限")
    if len(text_src) > MAX_TEXT_LEN:
        text_src = text_src[:MAX_TEXT_LEN]

    def _handler(signum, frame):
        """超时处理。"""
        raise BizException("1303024", "正则执行超时")

    old = signal.signal(signal.SIGALRM, _handler)
    signal.alarm(REGEX_TIMEOUT)
    try:
        matched = re.search(pattern, text_src, re.M)
        if not matched:
            return ""
        return (matched.group(group) or "").strip()
    finally:
        signal.alarm(0)
        signal.signal(signal.SIGALRM, old)
```

恶意正则如 `(a+)+b` 在长文本上会指数级回溯。若模板由不可信来源导入（如从其他医院复制），没有超时保护会让整个解析服务卡死。

2. **原始文本不含隐私字段**：`raw_text` 存全文，但审计日志中不打印全文（只打印前 200 字符）。

3. **文件路径校验**：所有文件操作走 M13-02 的 `safe_join`，禁止 `..` 路径。

4. **模板字段规则校验**：新建模板时用 OWASP 正则安全规则检查可疑模式（嵌套量词、回溯引用）。

5. **操作审计**：修改字段、认领绑定、启用模板、修改配置都写 M02-06 审计（`user_id`、`action`、`before`、`after`、`ip`、`trace_id`）。

6. **配置敏感参数保护**：`CRITICAL_FIELDS`、`CONFIDENCE_AUTO`、`CONFIDENCE_WARN` 修改需二次确认（前端弹框 + 后端校验 `X-Confirm-Header`）。

## 11. 异常处理与日志

### 11.1 异常分类

| 类别 | 场景 | 处置 |
|---|---|---|
| 文件不可读 | PDF 损坏、路径失效 | 标 `PARSE_FAILED` + 转人工 |
| 加密 | `is_encrypted=TRUE` | 标 `PARSE_FAILED` + 通知 M13-02 走密码流程 |
| OCR 不可用 | 进程崩溃、模型加载失败 | 重试 3 次后标失败；恢复后批量重试 |
| OCR 超时 | 超过 `MAX_ELAPSED_MS` | 同上 |
| 模板不匹配 | 无匹配模板 | 用 GENERIC_V1 兜底；无通用模板则失败 |
| 必填字段缺失 | 抽取结果为 NULL | 标 `PARSE_FAILED`，记录缺失字段名 |
| 字段类型错误 | 定量项目抽到非数字 | 该字段置空继续，其余正常 |
| 绑定多命中 | 同名同姓同时段 | 进待确认 `SAME_NAME_AMBIGUOUS` |
| 绑定时窗缺失 | 技师未点开始/完成 | 进待确认 `NO_MATCHING_WINDOW` |
| 双通道冲突 | 姓名不一致 | 进待确认 + `cross_conflict=TRUE` |
| 上游不可用 | M13-02/M13-01 超时 | 依赖不同：阻断或降级（见 2.4） |
