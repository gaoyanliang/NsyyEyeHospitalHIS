**设计说明：**

1. **`m13_report_review` 是中心表**，五张表围绕它展开。这份表既承载"谁审了什么"的法律责任，又承载"发没发出去"的推送状态。

2. **`m13_review_field` 是 M13-03 字段的审核时副本，而不是直接引用**。理由：
   - 审核医师可能修改结果值，修改必须记在审核域，不能污染 M13-03 的解析记录
   - M13-03 的解析记录可能被"重新解析"取代（`is_superseded`），但审核域需要稳定引用
   - 审核域的 `original_value`（M13-03 抽取原值）与 `value_text`（审核后值）需成对保留，这是准确率统计的基础

3. **`m13_report_version` 保存完整快照而非增量 diff**。查询"当时医生看到什么"需要一次读出；存 diff 要逐版回放 5 次，中间任何一版被删就断链。代价是每年约 630MB，可接受。

4. **`m13_report_publish` 与主表的状态字段并存**。主表 `push_status` 是"当前推送状态"（快速查询用），发布表是"每次发布动作的完整记录"（一次发布 + N 次重试 + 一次修订 = 多条记录）。二者不是冗余，是"当前态"与"流水账"的关系。

5. **`m13_critical_value` 独立成表**，因为危急值有独立的 8 状态机、独立的升级链路、独立的时效指标，塞进主表会让主表状态字段爆炸。

6. **七张表全部不分区，唯独日志表分区**。理由：
   - `m13_report_review` 的 `uk_m13_review_parse (parse_id)` 是"一解析一报告"的唯一防线，按年分区会迫使索引含分区键，约束退化为"同年唯一"
   - `m13_report_version` 的 `uk_m13_version_report (report_no, version_no)` 同理
   - `m13_review_log` 没有跨年唯一约束（主键已含 `seq_date`），可自由分区。日约 1,500 条 × 15 年 = 820 万行，不分区会成为最大的表。

**约束说明：**

```sql
-- 一解析一报告（部分唯一索引，重新解析生成新报告时旧记录已 is_superseded）
CREATE UNIQUE INDEX uk_m13_review_parse
    ON m13_report_review (parse_id)
    WHERE is_deleted = FALSE;

-- 一任务一有效报告（退回后技师重做会产生新任务，因此排除终态）
CREATE UNIQUE INDEX uk_m13_review_task
    ON m13_report_review (task_id)
    WHERE status NOT IN ('REJECTED', 'WITHDRAWN')
      AND is_deleted = FALSE;

CREATE UNIQUE INDEX uk_m13_review_no
    ON m13_report_review (review_no)
    WHERE is_deleted = FALSE;

-- 审核队列：危急优先，同优先级先入队先审
CREATE INDEX idx_m13_review_queue
    ON m13_report_review (
        critical_level DESC NULLS LAST, queued_at ASC)
    WHERE status = 'PENDING' AND is_deleted = FALSE;

-- 待推送与推送失败
CREATE INDEX idx_m13_review_publish
    ON m13_report_review (published_at)
    WHERE push_status IN ('PENDING', 'FAILED')
      AND is_deleted = FALSE;

ALTER TABLE m13_report_review
    ADD CONSTRAINT ck_m13_review_no
    CHECK (review_no ~ '^LBR[0-9]{8}[0-9]{5}$');

ALTER TABLE m13_report_review
    ADD CONSTRAINT ck_m13_review_status
    CHECK (status IN (
        'PENDING', 'REVIEWING', 'PUBLISHED',
        'REJECTED', 'SUPERSEDED', 'WITHDRAWN'));

ALTER TABLE m13_report_review
    ADD CONSTRAINT ck_m13_review_conclusion
    CHECK (conclusion IS NULL
           OR conclusion IN ('PASS', 'MODIFY', 'REJECT'));

ALTER TABLE m13_report_review
    ADD CONSTRAINT ck_m13_review_eye_side
    CHECK (eye_side IN ('OD', 'OS', 'OU', 'NA'));

ALTER TABLE m13_report_review
    ADD CONSTRAINT ck_m13_review_gender
    CHECK (gender IS NULL OR gender IN ('M', 'F', 'U'));

-- 已发布必须是 PASS 或 MODIFY
ALTER TABLE m13_report_review
    ADD CONSTRAINT ck_m13_review_published_conc
    CHECK (status <> 'PUBLISHED'
           OR conclusion IN ('PASS', 'MODIFY'));

-- 已退回必须是 REJECT
```

**状态机：**

```
                    ┌─────────┐
       建档 ───────►│ PENDING │
                    └────┬────┘
              认领（乐观锁）│
                         ▼
                    ┌──────────┐
                    │ REVIEWING│
                    └────┬─────┘
              PASS/MODIFY │ REJECT
                         ▼    ▼
              ┌──────────┐ ┌────────┐
              │PUBLISHED │ │REJECTED│（终态）
              └────┬─────┘ └────────┘
         修订 │    │ 撤回
              ▼    ▼
     ┌──────────┐ ┌──────────┐
     │SUPERSEDED│ │WITHDRAWN │（终态）
     │（终态）   │ └──────────┘
     └──────────┘
         │
         │ 新版本发布时旧版本置此状态
         ▼
     （新记录仍为 PUBLISHED）
```

**设计要点：**

1. **`review_no` 跨版本不变，版本号另存 `version_no`。** 医生看到的、病历引用的、发票关联的永远是同一个报告号，版本只是修正记录。如果改报告号，所有已引用它的地方（病历、医生笔记）都会断链。

2. **`uk_m13_review_parse` 是"一解析一报告"的数据库兜底。** 应用层做幂等键校验，DB 层做最后防线。两者共存是因为应用层可能被绕过（并发、重放、脚本导入）。

3. **`ck_m13_review_version_revise` 把 `version_no` 与 `revise_count` 绑死。** 防止出现"版本号 5 但修订 2 次"这种不一致。这条约束让所有代码路径都必须同时维护两个字段，是最廉价的防错手段。

4. **`opinion` 长度校验下沉到 DB。** 应用层校验容易被绕过（DBA 手工改、其他服务误写），而这条规则是法规性的——退回必须有清楚的理由。

5. **`critical_rules_missing` 单独存。** 危急规则获取失败时报告仍可发布（业务不能停），但必须留痕，让审核界面红色横幅提示、让质控科事后抽查、让规则恢复后可自动补判。

6. **`push_status` 与 `m13_report_publish.push_status` 并存。** 前者是"当前推送状态"（一次查询扫描数千条用），后者是"每次发布动作的记录"（追溯用）。主表冗余一份是为了避免列表页 JOIN。

7. **`read_count` / `first_read_at` 由 M07-04 回写。** 修订后需要清零重新统计——"医生看过修订版没有"是 M-04 约束的执行依据。

8. **`is_superseded` 与 `status='SUPERSEDED'` 的关系。** 两者语义重叠但用途不同：
   - `status` 是审核状态机的一部分，参与状态校验
   - `is_superseded` 是快速过滤标记（如"当前有效报告"查询用 `is_superseded=FALSE`）

   实际上两者同步维护，保留两个字段是为了查询语义清晰与将来扩展。

|---|---|

| 每年新增 | 157,000 条 |
| 15 年累计 | 约 235 万条 |
| 单行平均 | 约 1,100 字节 |
| 总容量 | 约 2.6 GB（含索引约 3.8 GB） |

**分区：** 否。`uk_m13_review_parse` 与 `uk_m13_review_task` 必须跨年份生效，按年分区会迫使索引含分区键，约束退化为"同年唯一"。

**设计要点：**

1. **为什么要有这张表而不直接用 M13-03 的 `m13_parse_field`？** 三个理由：
   - 审核医师的修改不能污染 M13-03 的解析结果（否则准确率统计被污染）
   - M13-03 的解析记录可能被"重新解析"取代（`is_superseded=TRUE`），但审核需要稳定引用
   - 审核域的关键字段清单、确认状态是独立于解析域的

2. **`original_value` 存的是 M13-03 的抽取原值。** 建档时从 `m13_parse_field.field_value` 复制过来。之后审核医师怎么改，`original_value` 都不变——这是"机器原来抽的是什么"的唯一记录。

3. **`ck_m13_rfield_edited` 强制修改必须记录原值。** 如果允许"改了但 `original_value` 为空"，就永远无法回答"机器原来抽的是什么、被改了什么"。

4. **`is_critical` 在建档时从 M13-03 复制。** 之后即使参数里的关键字段清单变了，历史记录仍按建档时的规则。

**`source` 段是关键。** `file_sha256` 可通过原文件校验、`bind_type` 说明文件怎么绑到患者。患者说"这不是我的报告"时，能举证：文件指纹是什么、从哪来、怎么绑上的、用什么模板抽的。

**为什么存完整快照而非增量？**

查询"当时医生看到什么"需要一次读出；存 diff 要逐版回放 5 次，中间任何一版被删就断链。代价：单版约 4KB × 15.7 万/年 = 630MB/年，可接受。

**为什么 `changed_fields` 还要单独存 diff？** `jsonb_array_length(changed_fields)` 可快速统计"平均每次修订改几个字段"，不用做两次快照的 JSON diff（慢操作）。

**量级估算：**

| 项 | 值 |
|---|---|
| 每年新增 | 约 160,000 行（含少量修订） |
| 15 年累计 | 约 240 万行 |
| 单行平均 | 约 4 KB |
| 总容量 | 约 9.6 GB |

**分区：** 否。`uk_m13_version_report (report_no, version_no)` 必须跨年生效。

```sql
           OR last_attempt_at IS NOT NULL);

    CHECK (version_no >= 1 AND version_no <= 100);

    'PUBLISH 首次发布 / REVISE 修订发布 / WITHDRAW 撤回';

    '推送尝试次数，上限 20（业务上限 10，DB 留余量）';
COMMENT ON COLUMN m13_report_publish.last_http_status IS
```

**设计要点：**

1. **为什么发布与推送分开记录？** 发布是本地状态变更（一次 UPDATE），推送是跨模块 HTTP 调用（可能超时、500）。**发布成功但推送失败是常态**——M07 重启 30 秒，这期间发布的 12 份报告全部推送失败。合并成一个状态会出现"报告在 M13 已发布、医生却看不到"的黑洞。

2. **撤回也进这张表。** 撤回同样要通知 M07（让医生知道报告作废了），同样可能失败。同表同状态机代码复用、对账口径统一。

3. **`attempt_count` 上限 20（业务 10 + 余量）。** 业务上限是 10 次，DB 留一倍余量是为了参数可调（调到 15 时不至于立刻违反约束）。

4. **`last_http_status` 单独存。** 只存 `last_error` 字符串无法聚合"是 400 还是 500 导致的失败"。400 是契约问题需要改代码，500 是对方故障可以重试——处置完全不同。

5. **不建 attempt 明细表。** 99.9% 记录只有 1 次尝试，建明细表 99.9% 是浪费。三次以上尝试的详细情况可通过审计日志（M02-06）查。

| 保留期 | 5 年 → 约 81 万行 |
| 单行平均 | 约 400 字节 |
| 总容量 | 约 320 MB |

**分区：** 否。

**状态机：**

```
    ┌───────────┐
    │ DETECTED  │  判定
    └─────┬─────┘
          │ 推送通知成功
          ▼
    ┌───────────┐  15min 未确认   ┌──────────────┐
    │ NOTIFIED  │────────────────►│ ESCALATED_1  │
    └─────┬─────┘                 └──────┬───────┘
          │ 医生确认                     │ 30min 未确认
          ▼                              ▼
    ┌──────────────┐              ┌──────────────┐
    │ACKNOWLEDGED  │              │ ESCALATED_2  │
    └──────┬───────┘              └──────┬───────┘
           │ 医生处置                    │ 60min 未确认
           ▼                             ▼
    ┌───────────┐                 ┌──────────────┐
    │  HANDLED  │                 │ ESCALATED_3  │
    └─────┬─────┘                 └──────────────┘
          │ 24h 自动 / 人工
          ▼
    ┌───────────┐
    │  CLOSED   │（终态）
    └───────────┘

  任意阶段 ──修订重判──► SUPERSEDED（终态）
```

**设计要点：**

1. **阈值与运算符全部快照。** 规律可能被调整（比如血钾危急下限从 2.8 调到 3.0），历史记录必须能回答"当时为什么判危急"。只存 `rule_code` 会在规则被改后失去解释力。

2. **`ck_m13_critical_esc_match` 把状态与层级绑死。** 防止出现"状态是 ESCALATED_1 但级别是 2"的脏数据。这类不一致会让督办统计失真。

3. **`ck_m13_critical_seq` 五重时序校验。** 通知 ≥ 判定、确认 ≥ 通知、处置 ≥ 确认、闭环 ≥ 处置。任何一环时间倒置都说明代码有 bug，DB 层直接拒绝。

4. **`ack_deadline_at` 与 `wait_minutes` 落库。** 实时算 `notified_at + INTERVAL '15 minutes'` 无法走索引；落库后 `WHERE ack_deadline_at < now()` 可走部分索引。这是每分钟执行的升级扫描任务的前提。

5. **`escalation_chain` 存完整升级记录。** 纠纷时需要证明"我们 15 分钟升级了、30 分钟又升级了、60 分钟报了院长"。只存 `escalation_level` 无法证明何时升级给谁。

6. **`force_close` + `force_remark` 独立于 `close_type`。** 强制关闭是"医生一直不确认，主任手动关掉"的特例，必须与正常闭环区分统计。

| 危急值比例 | 约 3% |
| 每日新增 | 约 13 条 |
| 每年新增 | 约 4,745 行 |

**设计要点：**

1. **用 `biz_type` + `biz_id` 而非三张表。** 审核、危急值、推送三类操作的查询模式一致："给我这个对象的全部操作记录"。三张表要 UNION，查询和统计都变复杂。

2. **`before_status` / `after_status` 成对存。** 追溯"状态是怎么变的"不用反查历史记录，一次查询就能画出时间线。

3. **`keep_forever` 保护关键记录。** 纠纷时相关的日志不能被归档清理，标记后归档任务跳过。

4. **只有这张表分区。** 日约 1,500 条 × 15 年 = 820 万行，不分区会成为最大的表。且**这张表没有跨年份唯一约束**（主键已含 `seq_date`），分区无副作用。

| 总容量 | 约 2.9 GB |

**分区：** 是。`PARTITION BY RANGE (seq_date)`，月度分区，预建 36 个月，热数据 180 天。

```python
        codes = [e.field_code for e in self.field_edits]
        if len(codes) != len(set(codes)):

        for e in self.field_edits:
            if e.value is not None and not (e.edit_reason or "").strip():
```

**分区预建脚本（`m13_004_008_log`）：**

```sql
DO $$
DECLARE
    m DATE := DATE_TRUNC('month', CURRENT_DATE)::date;
    p TEXT;
    n TEXT;
BEGIN
    FOR i IN 0..35 LOOP
        p := TO_CHAR((m + (i || ' month')::interval)::date,
                     'YYYY_MM');
        n := 'm13_review_log_' || p;
        EXECUTE format(
            'CREATE TABLE IF NOT EXISTS %I '
            'PARTITION OF m13_review_log '
            'FOR VALUES FROM (%L) TO (%L)',
            n,
            (m + (i || ' month')::interval)::date,
            (m + ((i + 1) || ' month')::interval)::date);
    END LOOP;
END $$;
```
