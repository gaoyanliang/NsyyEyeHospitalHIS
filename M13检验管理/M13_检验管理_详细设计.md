### 1.2 本院的特殊约束

**与 M12 检查相同的核心约束：**

> **本院所有检验仪器均无法接入 HIS。**

| 仪器类别 | 典型型号 | 输出方式 | 能否 LIS 直连 |
|---|---|---|---|
| 血球分析仪 | 迈瑞 BC-5390 / 希森美康 XN-550 | 自带工作站，导出 PDF | 否 |
| 生化分析仪 | 迈瑞 BS-480 / 日立 7180 | 自带工作站，导出 PDF | 否 |
| 凝血分析仪 | 赛科希德 SF-8100 | 自带工作站，导出 PDF | 否 |
| 尿液分析仪 | 优利特 URIT-1600 | 自带工作站，导出 PDF | 否 |
| 免疫分析仪 | 安图 / 迈瑞 CL-1200 | 自带工作站，导出 PDF | 否 |
| 糖化血红蛋白仪 | 普门 H9 | 内置报告，导出 PDF | 否 |
| 微生物鉴定药敏仪 | 生物梅里埃 VITEK 2 | 自带工作站，导出 PDF | 否 |

**三条硬约束（与 M12 相同）：**

1. **结果只能是 PDF 文件**，通过共享文件夹传递
2. **PDF 由技师手工导出**，文件名随机
3. **PDF 内含患者姓名/性别/年龄，但无本院患者 ID**

**M13 比 M12 多两条约束：**

4. **标本是实体，必须管理它的采集、标记、流转、签收**
5. **参考区间随仪器、性别、年龄、生理状态分层**——同一份血钾在不同人群参考区间不同

### 1.3 为什么 M13 是模块而不是功能

**理由一：检验与检查的业务形态根本不同。**

| 维度 | 检验（M13） | 检查（M12） |
|---|---|---|
| 标本 | **有**（采集、条码、流转、签收） | 无 |
| 前置环节 | 护士采集 → 送检 → 签收 | 直接到检 |
| 结果判定 | **对照参考区间自动判定** | 医生看图判断 |
| 报告形态 | 数值表格为主 | 图像 + 数值混合 |
| 危急值密度 | **高**（血钾、血糖、血红蛋白） | 低（眼压、视野 MD） |
| 异常处置 | 标本溶血/凝块/量不足需重采 | 图像质量差需重做 |

**"有标本"这一条差异，就足以支撑一个独立模块。** 标本有物理生命周期，需要条码、需要签收、需要拒收、需要重采，这些在检查模块里完全不存在。

**理由二：参考区间的复杂度远超检查。**

同是"血钾"：

| 人群 | 参考区间 | 危急低值 | 危急高值 |
|---|---|---|---|
| 成人男 | 3.5~5.3 | < 2.5 | > 6.5 |
| 成人女 | 3.4~5.1 | < 2.5 | > 6.5 |
| 儿童（1~12岁） | 3.4~5.6 | < 2.5 | > 6.0 |
| 新生儿 | 3.7~5.9 | < 3.0 | > 7.0 |
| 妊娠期 | 3.1~5.0 | < 2.5 | > 6.0 |

**单个项目最多 3（性别）× 6（年龄）× 3（生理）× 3（仪器）≈ 160 条规则**，血常规 24 项 × 6 = 144 条，生化 40 项 × 8 = 320 条，合计近 500 条 + 版本化约 1,500 条。这是业务数据，不是主数据字段。

**理由三：检验是临床决策最密集的数据源。**

一位眼科患者的术前检查包含：血常规、凝血功能、肝肾功能、血糖、电解质、传染病筛查。每项都可能有异常甚至危急值。M13 必须保证：

- 危急值 15 分钟内医生确认
- 参考区间判定准确（不能把正常判成异常）
- 报告完整（少一项会被术前评估漏掉）

**理由四：外送检验是一门独立的协作业务。**

本院不做的检验（如某些特殊免疫、基因检测）需外送到第三方检验机构。这涉及：

- 机构资质核验（CMA/CNAS）
- 冷链运输与温度记录
- 回报缺失发现
- 双人核对（手工录入）
- 成本记账（与收费分离）

### 2.3 六条拆分主线

**主线一：标本是 M13 独有的物理链路，必须单独管。**

M13-01 管"从开单到标本签收"这段人跑腿的过程，M13-02 管"从签收到 PDF 落库"这段机器跑数的过程。

**为什么这是分界线：** 签收之前，问题是"标本到了吗、合格吗"；签收之后，问题是"结果出了吗、准吗"。责任人不同（护士 vs 技师），SLA 不同（30 分钟 vs 4 小时），异常处置不同（重采 vs 重做）。

**主线二：采集与解析必须分开（同 M12）。**

M13-02 是文件系统操作，M13-03 是 OCR + NLP。技术栈、耗时、失败处置三者都不同。

**主线三：绑定与结构化同模块，但双通道分流（同 M12）。**

通道 A（姓名/性别/年龄/检验日期）用于绑定，通道 B（项目/数值/单位/区间）用于填充。容错策略相反。

**主线四：参考区间是独立规则中心。**

M13-05 独立成子模块，因为它管的是"随时间、随人群变化的多版本规则"，不是"一张配置表"：

- 单项目最多 160 条分层规则
- 换仪器要新增版本，旧报告必须按旧区间判定
- 危急阈值是医疗安全红线，需独立权限 + 双人复核

**主线五：微生物与外送是"慢检验"，结果模型不同。**

血常规"20 项一次出完"，培养"3 个任务 4 个时间点"，外送"3~7 天后回报"。M13-04 的 `uk_m13_review_parse` 是"一解析一报告"，装不下"一个标本多批次结果"。

**主线六：审核是法定责任（同 M12）。**

M13-03 是技术加工，M13-04 是法律责任承担。

### 2.4 与 M12 的对称与不对称

**六个子模块完全对称：**

| M12 检查 | M13 检验 | 差异 |
|---|---|---|
| M12-01 申请与预约排程 | M13-01 申请与**标本**管理 | 检验多了标本 |
| M12-02 执行与技师工作台 | —— | **检验无此对应**（标本采集即执行） |
| M12-03 报告文件采集与归档 | M13-02 结果文件采集 | 基本一致 |
| M12-04 报告 OCR 解析 | M13-03 结果 OCR 解析 | 基本一致 |
| M12-05 报告审核与发布 | M13-04 结果审核与发布 | 基本一致 |
| M12-06 设备与模板管理 | M13-05 **项目与参考区间**管理 | 检验管规则不管设备 |
| —— | M13-06 **微生物与外送** | **检查无此对应** |

**两处不对称的原因：**

1. **检验没有"技师工作台"**——标本采集由护士完成（归 M13-01），仪器自动出数（无人工执行环节）。时间窗的精度问题在检验场景下不存在：一件标本同时只属于一个患者，条码精确标识
2. **检查没有"项目与参考区间管理"**——检查结果多为图像与形态描述，无参考区间判定
3. **检验有"微生物与外送"**——培养是慢过程，外送是跨机构，检查都不涉及

## 3. 核心业务模型

### 3.1 三层结构：申请 → 项目 → 任务

```
┌─────────────────────┐
│  m13_lab_request    │  检验申请单（一张单）
│  request_no: LQ...  │
└──────────┬──────────┘
           │ 1:N
     ┌─────┴─────┐
     ▼           ▼
┌─────────────┐ ┌─────────────┐
│ m13_lab_item│ │ m13_lab_item│  检验项目（收费层）
│  血常规组合  │ │  肝功能组合  │
└──────┬──────┘ └──────┬──────┘
       │ 1:N           │ 1:N
       ▼               ▼
┌──────────────┐ ┌──────────────┐
│m13_lab_task  │ │m13_lab_task  │  检验任务（执行层）
│ WBC 白细胞    │ │ ALT 转氨酶    │
│ HGB 血红蛋白  │ │ AST 谷草转氨酶│
│ ...24 项      │ │ ...12 项      │
└──────────────┘ └──────────────┘
```

**为什么组合项目与明细都要存：**

- `m13_lab_item` 是**收费/退费依据**（一个组合 = 一笔收费）
- `m13_lab_task` 是**执行/结果依据**（一个明细 = 一个结果）

医生开"血常规（五分类）"，M16 收一笔费用，但实验室要出 24 个数值结果。两层都必须存，缺一不可。

### 3.2 标本归并模型

**系统的核心价值是：把多个检验任务合理归并成尽可能少的采集管。**

```
检验任务：
  WBC  需要 全血（紫帽 EDTA）2.0 mL
  HGB  需要 全血（紫帽 EDTA）
  PLT  需要 全血（紫帽 EDTA）
  ALT  需要 血清（黄帽促凝）5.0 mL
  AST  需要 血清（黄帽促凝）
  K    需要 血清（黄帽促凝）
  PT   需要 血浆（蓝帽枸橼酸）2.7 mL
  APTT 需要 血浆（蓝帽枸橼酸）

归并结果：
  管 1：紫帽 EDTA —— WBC, HGB, PLT（3 项合一管）
  管 2：黄帽促凝 —— ALT, AST, K（3 项合一管）
  管 3：蓝帽枸橼酸 —— PT, APTT（2 项合一管）
                        ↑ 凝血必须独立一管
```

**七条归并规则：**

| 编号 | 规则 | 理由 |
|---|---|---|
| R-01 | 同 `specimen_type` + `container_type` 可归并 | 同一物理容器 |
| R-02 | 合计用量不超容器容量 | 采多了浪费、采少了不够做 |
| R-03 | 超容量必须拆管 | 5 mL 管不能装 6 mL |
| R-04 | 冷藏与常温不归并 | 温度要求冲突 |
| R-05 | 立即送检项目单独成管 | 泪液/房水/玻璃体病原体 30 分钟内必须接种 |
| R-06 | 眼科特殊标本每项单管 | 标本量极少的项目不能共享 |
| R-07 | **凝血（PLASMA 蓝帽枸橼酸）必须独立一管** | 抗凝剂 9:1 比例 |

**六条"每项单管"的标本类型（`SINGLE_ONLY`）：**

`PLASMA`、`TEAR`（泪液）、`AQUEOUS`（房水）、`VITREOUS`（玻璃体）、`CORNEA_SCRAPING`（角膜刮片）、`CONJUNCTIVAL_SWAB`（结膜拭子）、`STOOL`（粪便）

**为什么采血量要算余量（20%）：**

血清促凝管标称 5 mL，但离心后血清只有约 40%（2 mL）。20 个生化项目需 4 mL 血清 → 需 10 mL 全血 → 需 2 管。

所以 `ITEM_CONSUME` 存的是**全血消耗量**，且已隐含"血清产出率 40%"的换算。

### 3.3 标的状态机

```
   ┌─────────┐
   │ PENDING │  待采集
   └────┬────┘
        │ collect
   ┌────▼──────┐
   │ COLLECTED │  已采集（条码打印，送检时限开始计时）
   └────┬──────┘
        │ deliver
   ┌────▼──────┐
   │ DELIVERED │  已送检
   └────┬──────┘
        │ accept              ┌──────────┐
   ┌────▼──────┐  reject      │ REJECTED │  拒收（终态，触发重采）
   │ ACCEPTED  │─────────────►└──────────┘
   └────┬──────┘
        │ 上机
   ┌────▼──────┐
   │ IN_PROCESS│  检验中
   └────┬──────┘
        │ 结果出
   ┌────▼──────┐
   │ COMPLETED │  已完成
   └───────────┘

旁支：PENDING / COLLECTED → CANCELLED（取消）
```

**八种拒收原因：**

| 代码 | 中文 | 处理 |
|---|---|---|
| `HEMOLYSIS` | 溶血 | 重采 |
| `CLOTTED` | 凝块 | 重采 |
| `INSUFFICIENT` | 量不足 | 重采 |
| `WRONG_CONTAINER` | 容器错误 | 重采 |
| `UNLABELED` | 未贴标签 | 重采 |
| `MISMATCH` | 标签与患者不符 | 重采 + 差错记录 |
| `DELAYED` | 送检超时 | 检验科判断是否可做 |
| `CONTAMINATED` | 污染 | 重采 |

**超时标本仍允许送检（不阻断）：** 血清超 4 小时血糖可能偏低但肝肾功能仍可靠。护士不应因超时直接丢弃标本，责任交给检验科判断。

### 3.4 时间窗与绑定（同 M12，但检验更简单）

**检验的绑定比检查简单，因为：**

1. 标本有条码，标签上已写下 `specimen_no`
2. 一份标本同时只属于一个患者
3. 检验报告 PDF 上通常印有标本号

**但本项目仍有约束：**

- 仪器导出的 PDF **可能不含本院标本号**（尤其外送仪器）
- 文件名随机
- 所以仍需要时间窗作为兜底

**绑定路径（同 M12）：**

```
路径一：报告 PDF 含标本号 → 查 m13_lab_task → 精确绑定（置信度 1.0）
路径二：时间窗（标本签收后 SIGN_REPORT_WINDOW 小时内）+ OCR 姓名 → 唯一命中（0.95）
路径三：待确认队列（人工）
```

**时间窗参数：** `REPORT_WINDOW_HOURS = 8`（从标本签收时刻起算，比检查的 1 小时宽得多，因仪器批量出数）

### 3.5 参考区间版本模型

**M13-05 的核心机制：区间不修改，只新增版本。**

```
项目：血钾 K

V1  3.5~5.3   生效 2024-01-01 ~ 2026-11-14   仪器 AU5800
V2  3.4~5.3   生效 2026-11-15 ~ NULL         仪器 AU6800
                  ↑ 换仪器后参考区间变化

查询"2026-10-20 的血钾报告"用 V1
查询"2026-12-01 的血钾报告"用 V2
```

**为什么不能修改：**

- 同一份报告昨天判正常、今天判异常，医生会质疑系统
- 追溯要求"报告的判定依据是报告出具时的有效标准"
- 靠推导 `valid_to` 会因版本撤回而改历史

**为什么用 `EXCLUDE USING gist` 排他约束：**

保证"任意时刻、同一分层条件恰好只有一条生效区间"。两条区间同时覆盖 11-15 是典型的"忘了改 V1 的 valid_to"错误。

**`COALESCE` 在排他约束中的必要性：** PG 认为 `NULL` 与 `NULL` 不相等，两条 `gender IS NULL` 的通用区间可都覆盖同一时段而约束不报错。

**`age_min = -1` / `age_max = 999` 的语义相反：** 无下限 = 从 0 岁起；无上限 = 到 150 岁止。统一用同一个值会让两者被视为相同产生错误冲突。

### 3.6 危急阈值模型

**参考区间 vs 危急阈值 vs 缓冲区：**

```
         危急低      参考低       参考高      危急高
           │           │            │           │
  ─────────●───────────●────────────●───────────●─────────►
         <2.5        3.5          5.3         >6.5    血钾
           │←─危急──►│←─异常但─►│            │←─危急──►│
                      不危急                    │
```

- **参考区间内** → 正常（不标记）
- **参考区间外、危急阈值内** → HIGH / LOW（标记，医生可下午处理）
- **超过危急阈值** → CRITICAL（触发 15 分钟确认闭环）

**四种运算符：**

| 运算符 | 含义 | 适用 |
|---|---|---|
| `LT` | 低于 lb_threshold | 低钾（心律失常）、低血糖 |
| `GT` | 高于 ub_threshold | 高钾（心脏骤停）、高血糖 |
| `BETWEEN` | 两限之间 | 少见 |
| `OUTSIDE` | 两限之外 | 高低意义相同（血糖 <2.5 或 >25） |

**为什么血钾必须拆 `LT`/`GT` 两条而血糖可以 `OUTSIDE` 一条：** 血钾高低临床意义不同（低钾心律失常、高钾心脏骤停），处置也不同；血糖两头都是"立即补糖或降糖"，处置相似。**拆与不拆由临床决定。**

**两级严重度：**

| 级别 | 通知方式 | 时限 |
|---|---|---|
| `CRITICAL` | 站内信 + **短信** + 弹窗 | 15 分钟确认 / 2 小时处置 |
| `WARNING` | 仅站内信 | 无强制确认 |

**为什么不是所有异常都 CRITICAL：** 眼压 26 一天 20 例全发短信，会造成短信疲劳，真正 CRITICAL 的短信反而被忽略。

### 3.7 微生物多批次结果模型

**普通检验：一份标本 → 一份报告。**

**微生物：一份标本 → 多个结果批次 → 组装成一份报告。**

```
玻璃体液培养

D1 10:30  PRELIMINARY  涂片初报：革兰阳性球菌
              ↓ 推送医生（当晚调整抗生素）
D2 09:00  INTERIM      中报：金黄色葡萄球菌
              ↓ 推送医生
D4 15:00  FINAL        终报：金黄色葡萄球菌 + 药敏（苯唑西林 R、万古霉素 S）
              ↓ 推送医生
```

**为什么用"多批次 + 组装"而不是"多份报告"：**

- 医生应看到"一份完整的玻璃体液培养报告"按时间线排好
- 而不是三个独立的"报告"，看的时候还要自己去关联

**组装模型：**

| `report_key` | `report_version` | 内容 |
|---|---|---|
| `SPL2026102200012` | v1 | 初报 |
| `SPL2026102200012` | v2 | 初报 + 中报 |
| `SPL2026102200012` | v3 | 初报 + 中报 + 终报 |

M07 侧表现为"同一份报告被更新版本"，锚点是 `report_key`。

**为什么批次独立走审核：** 每个批次都是独立的法律文件，都要有审核医师签字。

**阴性判定时长：**

| 标本类型 | 最短培养天数 | 理由 |
|---|---|---|
| 一般细菌 | 3 天 | |
| 真菌 | 5 天 | 真菌生长慢 |
| 分枝杆菌 | 42 天 | 结核菌极慢 |
| 厌氧菌 | 5 天 | |
| **眼内液** | **5 天** | 标本量极少、病原载量低；眼内炎玻璃体液培养阳性率仅 40~60% |

### 3.8 外送检验模型

**外送委托 12 态：**

```
DRAFT → PENDING_APPROVAL → APPROVED → PACKED → SHIPPED → RECEIVED
                                                          ↓
                                                    REPORTING
                                                          ↓
                                              PARTIALLY_RETURNED
                                                          ↓
                                                     RETURNED → CLOSED

旁支：CANCELLED、OVERDUE
```

**`PARTIALLY_RETURNED` 为什么必需：** 一单 5 项，可能 3 项先回、2 项后回。只有 `RETURNED` 会让"明明有进展"的委托单被标成逾期。

**`CLOSED` 与 `RETURNED` 为什么分开：** `RETURNED` 之后还有核对份数、登记费用、归档。若把 `RETURNED` 当终态，会忘掉这些步骤，逾期扫描也会一直报。

**三种回报方式：**

| 方式 | 说明 | 校验 |
|---|---|---|
| `PDF_FILE` | 第三方出 PDF → 走 M13-02 采集 → M13-03 解析 | 自动 |
| `INTERFACE` | 直连锁机构系统拉取 | 自动 |
| `MANUAL` | 电话/邮件通知，人工录入 | **必须双人核对 + 附件** |

**为什么手工录入必须双人核对：** 这是整条链路唯一"数据不经任何自动校验"的环节。成本每份 1 分钟，收益是消灭最原始的人为错误（尤其 S/R 一字之差）。

### 4.3 三条数据铁律（同 M12）

**铁律一：标本流水与日志只增不改。**

| 表 | 保护方式 |
|---|---|
| `m13_specimen_log` | 触发器 `fn_m13_spec_log_readonly()` |
| `m13_review_log` | 触发器 |
| `m13_item_change_log` | **部分保护**：DELETE 一律拒绝；UPDATE 只允许改审批字段，核心字段（`change_no`/`lab_code`/`change_type`/`action`/`changes_json`/`operator_id`/`created_at`）拒改 |
| `m13_report_version` | 触发器禁止 UPDATE/DELETE |

**`m13_item_change_log` 为什么允许部分 UPDATE：** 完全禁止会让审批无法落地（审批结果要写回同一条记录）。折中为"核心字段不可改、审批字段可改"——即使有人想篡改，也无法改变"变更内容是什么"和"谁提交的"。

**铁律二：唯一性用部分索引。**

关键约束：

```sql
-- 一医嘱一申请
CREATE UNIQUE INDEX uk_m13_lab_req_order ON m13_lab_request (order_no)
    WHERE is_deleted = FALSE;

-- 一条码一标本（条码全局唯一＝资金安全底线）
CREATE UNIQUE INDEX uk_m13_spec_no ON m13_specimen (specimen_no)
    WHERE is_deleted = FALSE;

-- 一任务一有效报告
CREATE UNIQUE INDEX uk_m13_parse_task_bound ON m13_parse_record (bound_task_id)
    WHERE bind_status = 'BOUND' AND is_superseded = FALSE AND is_deleted = FALSE;

-- 一解析一报告
CREATE UNIQUE INDEX uk_m13_review_parse ON m13_report_review (parse_id)
    WHERE is_deleted = FALSE;
```

**铁律三：金额、浓度、置信度必须 NUMERIC。**

| 类型 | 用途 |
|---|---|
| `NUMERIC(12,2)` | 金额 |
| `NUMERIC(12,4)` | 检验结果数值（血钾 5.2530） |
| `NUMERIC(5,4)` | 置信度 |
| `NUMERIC(8,6)` | 覆盖率/错误率 |

**禁止 `FLOAT`。** 理由同 M12：二进制浮点无法精确表示 0.1，判定区间时会误判。

### 4.4 分区与归档

**42 张表中只有 2 张分区：**

| 表 | 分区方式 | 保留期 |
|---|---|---|
| `m13_specimen_log` | 月度 RANGE，预建 36 月 | 15 年 |
| `m13_review_log` | 月度 RANGE，预建 36 月 | 15 年 |

**为什么 `m13_item_change_log`（年约 5,500 行）也分区：** M13-05 数据结构中定义为月度分区，行数虽小但增长平滑，统一分区策略便于运维。

**为什么主表都不分区：** 同 M12——跨年份幂等与去重语义比查询性能更重要。

| 表 | 15 年行数 | 若分区的后果 |

### 6.2 错误码规范

## 8. 全局业务规则

### 8.1 标本铁律

| 编号 | 规则 | 理由 |
|---|---|---|
| S-01 | 条码全局唯一 | 扫码时不能扫出两件标本 |
| S-02 | 凝血必须独立一管 | 抗凝剂 9:1 比例 |
| S-03 | 血清与血浆不能混 | 血钾用血清会假性升高 0.3~0.5 |
| S-04 | 退回药品必须入原批次 | 新建批次会造成同批号两条记录、追溯断链 |
| S-05 | 采集人 ≠ 签收人 | 防"既当运动员又当裁判" |
| S-06 | 采集人 ≠ 拒收人 | 同上 |
| S-07 | 超时标本仍允许送检 | 血清超 4h 血糖偏低但肝肾功能仍可靠 |

### 8.2 参考区间铁律

| 编号 | 规则 | 理由 |
|---|---|---|
| I-01 | 区间不修改，只新增版本 | 历史报告必须按当时标准判定 |
| I-02 | 按 `test_time` 匹配版本 | 不是按查询时间 |
| I-03 | 任意时刻同一分层恰好一条生效 | `EXCLUDE USING gist` 排他约束 |
| I-04 | 匹配权重：性别 8 > 年龄 4 > 生理 2 > 仪器 1 | 最具体的规则优先 |
| I-05 | 未配齐区间不允许启用项目 | 启用后会收到"只有数值没有标记"的报告 |

### 8.3 危急值铁律（同 M12）

| 编号 | 规则 | 理由 |
|---|---|---|
| K-01 | 危急阈值必须位于参考区间之外 | 否则缓冲区无意义 |
| K-02 | 危急阈值双人复核 + 延后 ≥24 小时生效 | 改错的人自己看不出来 |
| K-03 | 确认与处置分开 | 15 分钟确认 / 2 小时处置 |
| K-04 | 短信只发 CRITICAL | 短信疲劳 |
| K-05 | 修订后必须重新判定 | 改了数值可能从 WARNING 变 CRITICAL |
| K-06 | **危急阈值覆盖率必须 100%** | 缺一个阈值意味着该项目出现危急值时不会报警 |

**K-06 是安全红线：** 临床会默认"系统会报警"而放松警惕。时间紧张时分批配置，其余项目临时置 `is_critical_applicable=FALSE` 列入待办，**绝不能留着 TRUE 但没配阈值**。

### 8.4 微生物与外送铁律

| 编号 | 规则 | 理由 |
|---|---|---|
| M-01 | 手工录入必须双人核对 + 附件 | 唯一不经自动校验的环节 |
| M-02 | 眼内液最短培养 5 天 | 标本量少、载量低，阳性率仅 40~60% |
| M-03 | 专家规则（MRSA/ESBL/CRE/VRE）必须配 | 否则耐药漏判 |
| M-04 | 外送机构资质变更需双签 | |
| M-05 | 委托不能自审 | `ck_m13_order_self_approve` |
| M-06 | 外送金额对技师脱敏 | 成本可见性必须与决策权匹配 |

### 8.5 职责分离（SoD）

| 编号 | 分离要求 | 实现 |
|---|---|---|
| SoD-01 | 标本采集人 ≠ 签收人 | `ck_m13_spec_sod` |
| SoD-02 | 标本采集人 ≠ 拒收人 | `ck_m13_spec_sod_reject` |
| SoD-03 | 审核人 ≠ 开方医生 | 应用层 |
| SoD-04 | 规则配置人 ≠ 日常审核人 | 权限矩阵 |
| SoD-05 | 危急阈值编辑人 ≠ 审批人 | 权限矩阵（主任编辑、医务科审批） |
| SoD-06 | 外送委托申请人 ≠ 审批人 | `ck_m13_order_self_approve` |
| SoD-07 | 手工录入操作人 ≠ 核对人 | `ck_m13_return_double` |
| SoD-08 | IT 管理员不能改业务数据 | 权限矩阵 |

## 12. 实施路线与验收

### 12.1 六阶段实施

| 阶段 | 内容 | 工期 | 交付 |
|---|---|---|---|
| 一 | M13-05 规则中心 | 3 周 | 项目属性、参考区间、危急阈值 |
| 二 | M13-01 | 4 周 | 接单、标本、条码、签收 |
| 三 | M13-02 + M13-03 | 5 周 | 采集、OCR、绑定 |
| 四 | M13-04 | 3 周 | 审核、危急值、发布 |
| 五 | M13-06 | 3 周 | 微生物、外送 |
| 六 | 联调与试点 | 3 周 | 试运行 + 全院推广 |
| **合计** | | **21 周** | |

**为什么先做 M13-05：** 它是规则中心。没有参考区间，M13-04 无法判定 HIGH/LOW；没有危急阈值，无法判定 CRITICAL。

**为什么 M13-06 放最后：** 微生物与外送是低频业务（日约 12 例培养 + 0.5 单外送），可以后上线。

### 12.2 验收标准

### 12.3 上线前运维准备（关键 12 项）

| 序号 | 事项 | 后果 |
|---|---|---|
| 1 | 挂载共享文件夹 `\\fileserver\lab-reports` | 采集完全失效 |
| 2 | 创建 INBOX/ARCHIVE/QUARANTINE/MANUAL | 采集失败 |
| 3 | 配置服务账号读写权限 | 采集失败 |
| 4 | 配置各仪器默认导出路径 | 文件乱放 |
| 5 | **校准仪器电脑时钟（NTP，误差 < 30 秒）** | **时间窗绑定全失效** |
| 6 | 为每类报告建 OCR 模板 | 解析全失败 |
| 7 | 用 100 份样本跑回归 | 模板错误无感知 |
| 8 | 配置标本类型与容器（M01-09） | 接单失败 |
| 9 | **配置全部参考区间（覆盖率 ≥95%）** | 报告无正常/异常标记 |
| 10 | **配置全部危急阈值（覆盖率必须 100%）** | **危急值不报警，比没系统更危险** |
| 11 | 验证 `btree_gist` 与 `pg_trgm` 扩展 | 迁移失败 |
| 12 | 培训护士采集三步、检验科签收 | 流程走不通 |

**第 5 项与第 10 项最关键：**

- **第 5 项**：仪器时钟慢 20 分钟 → PDF mtime 早 20 分钟 → 绑定全部失败，一天 400 份全进待确认队列。**这不是代码能修的。**
- **第 10 项**：缺一个阈值意味着该项目出现危急值时系统不会报警，而临床会默认"系统会报警"而放松警惕。
