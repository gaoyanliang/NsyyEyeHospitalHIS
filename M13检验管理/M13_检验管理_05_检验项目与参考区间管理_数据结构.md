**设计说明：**

1. **`m13_lab_item_ext` 是中心表**，一份检验项目一条记录。它是 M01-09 `md_lab_item` 的本地扩展，通过 `lab_code` 一对一关联，但不建外键（跨模块逻辑关联）。

2. **`m13_ref_range` 与 `m13_critical_rule` 都是版本化表**。同一个 `lab_code` 有多条记录，通过 `version_no`（区间）或 `valid_from`（阈值）区分版本，通过 `is_current` 标记当前版。

3. **`m13_report_format` 单独成表而非并入 `m13_lab_item_ext`**。理由：
   - 格式模板可能需要按仪器区分（同一项目不同仪器的展示精度不同）
   - 格式变更的频率与属性变更不同（格式很少改，属性经常调）
   - 格式模板包含较多结构化配置（`value_options`、`normal_values`），放进主表会撑大行宽

4. **`m13_item_change_log` 是三张规则表共用的变更留痕表**。理由：查询模式统一（"给我这个项目的所有变更"），分表要 UNION；且审批流程（P05）需要跨类型统一列表。

5. **`m13_coverage_snapshot` 是快照表而非即时计算表**。理由：覆盖率需要历史趋势（近 30 天覆盖率变化），只算当前值无法画趋势图。

6. **`m13_lab_item_config` 与各子模块配置表结构一致**，便于统一管理。

**约束说明：**

```sql
CREATE UNIQUE INDEX uk_m13_lab_ext_code
    ON m13_lab_item_ext (lab_code)
    WHERE is_deleted = FALSE;

-- 区间缺失项目（覆盖率看板核心查询）
CREATE INDEX idx_m13_lab_ext_missing
    ON m13_lab_item_ext (lab_code)
    WHERE is_enabled = TRUE AND is_range_ready = FALSE
      AND is_deleted = FALSE;

-- 危急缺失项目（安全红线）
CREATE INDEX idx_m13_lab_ext_missing_c
    ON m13_lab_item_ext (lab_code)
    WHERE is_enabled = TRUE
      AND is_critical_applicable = TRUE
      AND is_critical_ready = FALSE
      AND is_deleted = FALSE;

-- 别名搜索（支持 array && array 操作符）
CREATE INDEX idx_m13_lab_ext_aliases
    ON m13_lab_item_ext USING gin (alias_names);

CREATE INDEX idx_m13_lab_ext_name_trgm
    ON m13_lab_item_ext USING gin (lab_name gin_trgm_ops);

ALTER TABLE m13_lab_item_ext
    ADD CONSTRAINT ck_m13_lab_ext_code
    CHECK (lab_code ~ '^LAB_[A-Z0-9_]{2,28}$');

ALTER TABLE m13_lab_item_ext
    ADD CONSTRAINT ck_m13_lab_ext_name
    CHECK (char_length(btrim(lab_name)) >= 1
           AND char_length(lab_name) <= 100);

ALTER TABLE m13_lab_item_ext
    ADD CONSTRAINT ck_m13_lab_ext_aliases
    CHECK (array_length(alias_names, 1) BETWEEN 1 AND 10);

ALTER TABLE m13_lab_item_ext
    ADD CONSTRAINT ck_m13_lab_ext_alias_len
    CHECK (array_length(alias_names, 1) IS NULL
           OR NOT EXISTS (
               SELECT 1 FROM unnest(alias_names) AS a
                WHERE char_length(btrim(a)) < 2
                   OR char_length(btrim(a)) > 50));

    ADD CONSTRAINT ck_m13_lab_ext_format
    CHECK (report_format IN (
        'NUMERIC', 'QUALITATIVE', 'SEMI_QUANTITATIVE',

ALTER TABLE m13_lab_item_ext
    ADD CONSTRAINT ck_m13_lab_ext_result_type
    CHECK (result_type IN (
        'QUANTITATIVE', 'QUALITATIVE',
        'SEMI_QUANTITATIVE', 'TEXT'));

ALTER TABLE m13_lab_item_ext
    ADD CONSTRAINT ck_m13_lab_ext_order
    CHECK (display_order >= 0 AND display_order <= 9999);

    CHECK (turnaround_hours >= 1 AND turnaround_hours <= 168);

ALTER TABLE m13_lab_item_ext
    ADD CONSTRAINT ck_m13_lab_ext_short
    CHECK (char_length(btrim(short_name)) >= 1
           AND char_length(short_name) <= 50);

ALTER TABLE m13_lab_item_ext
    ADD CONSTRAINT ck_m13_lab_ext_charge
    CHECK (char_length(btrim(charge_item_code)) >= 1);

-- 非定量项目不适宜配危急阈值（由应用层保证，DB 只记录结果）
ALTER TABLE m13_lab_item_ext
    ADD CONSTRAINT ck_m13_lab_ext_qual_critical
    CHECK (result_type <> 'QUALITATIVE'
           OR is_critical_applicable = FALSE);

ALTER TABLE m13_lab_item_ext

    '项目本地扩展：M01-09 项目的院内属性补充与就绪标记';
COMMENT ON COLUMN m13_lab_item_ext.lab_code IS

    '危急就绪：is_critical_applicable=FALSE 时恒 TRUE';
COMMENT ON COLUMN m13_lab_item_ext.version IS
    '乐观锁版本，防并发覆盖';

**设计要点：**

1. **`lab_code` 用正则约束 `^LAB_[A-Z0-9_]{2,28}$`。** 统一的编码前缀让所有 M13 表都能按前缀快速识别；后缀长度限制防止编码乱填。虽然 M01-09 已经有自己的编码校验，但本地表加约束是"防御性复制"——万一同步逻辑出 bug，DB 层能拦住。

2. **`alias_names` 用 `TEXT[]` 而非 JSONB。** 理由：
   - 数组支持 `&&`（重叠）、`@>`（包含）操作符，可以走 GIN 索引
   - 数组支持 `unnest` 展开，便于"按别名反查项目"统计
   - 别名语义就是"一组字符串"，数组是最自然的类型

3. **`ck_m13_lab_ext_qual_critical` 把"定性不宜配危急"的规则固化到 DB。** 应用层也会校验，但 DB 层保证了"即使有人绕过应用层直接改数据，也不会出现定性项目配危急阈值的荒谬状态"。

4. **`is_range_ready` / `is_critical_ready` 两个派生态落库。** 它们是覆盖率看板的核心查询字段，实时算需要 JOIN 两张子表。落库后看板查询 < 10ms。每日 04:00 全量重算校正偏差。

5. **`version` 乐观锁。** 两人同时编辑同一项目的属性时，后提交者收到 `rowcount=0`，提示"数据已被他人修改，请刷新"。

6. **`result_unit` 与 `decimal_places` 同步自 M01-09 但允许本地覆盖吗？** 本设计选择**不允许**——单位与精度必须与主数据一致，否则报告上的单位和系统判定的单位不同会导致判定错误。所以这两个字段是只读的（同步时覆盖）。

**版本化的排除约束详解：**

`EXCLUDE USING gist` 是本表设计的核心。它保证：

> 同一个 `(lab_code, gender, age_min, age_max, physiological_state, device_code)` 组合下，任意两个已批准/待审批版本的有效期 `[valid_from, valid_to]` 不重叠。

**为什么用 `COALESCE` 而不是让 NULL 参与？**

PostgreSQL 的排他约束中，`NULL` 与 `NULL` **不相等**（`NULL = NULL` 返回 NULL，不被视为冲突）。如果不加 `COALESCE`，两条 `gender IS NULL` 的通用区间可以都覆盖 2026-11-15 而约束不报错——这正好是"忘了改 V1 的 valid_to"的典型场景。

用 `COALESCE(gender, '')` 把 NULL 转成空串，两个空串相等，约束正常生效。

**为什么 `age_min` 用 `COALESCE(age_min, -1)` 而 `age_max` 用 `COALESCE(age_max, 999)`？**

因为年龄的"无下限"和"无上限"语义相反：

- `age_min IS NULL` 表示"从 0 岁起"→ 等价于 `age_min = -1`（比 0 还小）
- `age_max IS NULL` 表示"到 150 岁止"→ 等价于 `age_max = 999`

如果统一用 `-1` 或统一用 `999`，会让"无下限"与"无上限"在约束里被视为相同的值，产生错误的冲突判定。

**为什么约束只对 `APPROVED` 与 `PENDING` 生效？**

因为 `DRAFT` 是编辑中的草稿，允许与当前版"临时重叠"——用户正在把 V3 的 `valid_to` 改成 V2 生效前一天，中间状态必然有重叠。加 `WHERE approval_status IN ('APPROVED','PENDING')` 让草稿阶段不受限制，提交时自然校验。

**但 `PENDING` 也在约束内，意味着两个人同时提交重叠版本时，后提交者会立即收到约束冲突。** 这是正确行为——审批队列里不应该有两个互相矛盾的待审版本。

**`daterange(valid_from, valid_to, '[]')` 的含义：**

`'[]'` 表示闭区间（含两端）。`valid_to = NULL` 时 `daterange` 的上界自动视为无穷大。这保证：

- V1: `2024-01-01` ~ `2026-11-14` → `[2024-01-01, 2026-11-14]`
- V2: `2026-11-15` ~ `NULL` → `[2026-11-15, ∞)`

两者不重叠（`2026-11-14 < 2026-11-15`）。如果 V1 的 `valid_to` 忘了改成 `2026-11-14`（还是 NULL），V1 就是 `[2024-01-01, ∞)`，与 V2 的 `[2026-11-15, ∞)` 重叠，约束报错。

**这个约束的价值：把"任意时刻恰好有一条生效区间"从应用层承诺变成数据库保证。**

COMMENT ON COLUMN m13_critical_rule.severity IS
    'CRITICAL 强闭环（短信+15分钟确认）/ WARNING 仅站内信';
COMMENT ON COLUMN m13_critical_rule.notify_roles IS
    '通知角色数组 DOCTOR/DEPT_DIRECTOR/MEDICAL_AFFAIRS';
COMMENT ON COLUMN m13_critical_rule.notify_channels IS
    '通知渠道数组 WEBSOCKET/INBOX/SMS';
COMMENT ON COLUMN m13_critical_rule.effective_at IS
    '计划生效时刻，审批通过后由定时任务在此时刻置 is_current';
COMMENT ON COLUMN m13_critical_rule.apply_scope IS
    'ALL 全院 / INPATIENT 仅住院 / OUTPATIENT 仅门诊';
```

**设计要点：**

1. **`ck_m13_critical_op_threshold` 是"运算符与阈值必须自洽"的数据库级保证。** `LT` 有上限没下限、`BETWEEN` 只有一个限，这些在业务上都无意义。DB 层拒绝比应用层校验更可靠。

2. **`ck_m13_critical_level` 把"CRITICAL 必须有时限"固化。** 这条规则的依据是《医疗机构危急值报告制度》——危急值必须有时限要求，否则闭环无从考核。

3. **`uk_m13_critical_cur` 保证同项目同规则只有一个当前版。** 与区间的处理方式不同：区间用排他约束（因为要防有效期重叠），阈值用普通部分唯一索引（因为同一时刻只允许一条）。为什么阈值不做版本化日期范围？

   **因为阈值的"临时并行"没有意义。** 区间可能因为"旧仪器还在用、新仪器已上线"而需要两条并行；但危急阈值是"血钾多少算危急"这个医学判断，全院应该只有一个答案。**不允许并行是刻意的设计约束。**

   历史版本靠 `valid_from`/`valid_to` 记录，但同一时刻只有一条 `is_current=TRUE`。

4. **`effective_at` 与 `valid_from` 两个字段的分工：**
   - `effective_at`（TIMESTAMP）：计划生效的精确时刻，用于定时任务扫描
   - `valid_from`（DATE）：业务语义上的生效日期，用于历史查询

   两者通常相同（`effective_at` 的日期部分 = `valid_from`），但保留两个字段是因为：定时任务需要精确到分钟，历史查询只需要日期。

5. **`apply_scope` 支持住院/门诊区分。** 有些项目的危急阈值在不同场景下不同——比如新生儿胆红素在住院（持续监测）与门诊（一次性）的警戒线不同。这个字段让同一项目可以配两条规则，按场景选择。

    RETURN NEW;
END;

**为什么这个只增表的触发器允许 UPDATE（部分字段）？**

因为审批流程需要更新 `approval_status`、`approved_by`、`applied_at` 等字段。完全禁止 UPDATE 会让审批无法落地。折中方案是：**核心字段（变更号、项目、类型、差异内容、提交人、创建时刻）不可改，其余可改。**

这比"允许全部 UPDATE"安全得多——即使有人想篡改，也无法改变"变更内容是什么"和"谁提交的"。

**为什么按月分区？**

每天约 1 条变更（一年 365 条），15 年 5,500 条，其实很小。但考虑到：
- 归档时按月 DROP 分区比 DELETE 快得多
- 查询时按时间过滤可分区裁剪
- 未来如果增加"每次保存草稿都记一条"的策略，行数会大幅增加

分区成本低（预建 36 个月），收益明确。

| 15 年累计 | 约 5,500 条 |
| 单行平均 | 约 1.5 KB（含 before/after JSONB） |
| 总容量 | 约 8 MB |

**分区：** 是。`PARTITION BY RANGE (seq_date)`，月度分区，预建 36 个月，热数据 24 个月。

**设计要点：**

1. **`lab_category='ALL'` 表示汇总行。** 这让"全院趋势"与"分类趋势"共用一张表与一套查询逻辑，不必写两个接口。

2. **`ck_m13_cov_range_calc` 与 `ck_m13_cov_critical_calc` 强制"覆盖率与计数一致"。** 如果只存计数，趋势图要实时算；如果只存覆盖率，无法还原"当时有多少项目"。两者都存，并用约束保证一致，是最稳妥的方案。

3. **`idx_m13_cov_alert` 部分索引用于告警扫描。** 危急覆盖率 < 100% 的日子应该被快速查出（用于复盘"哪段时间有安全缺口"）。

**量级估算：**

| 项 | 值 |
|---|---|
| 每日行数 | 1（ALL）+ 9（类别）= 10 |
| 每年行数 | 3,650 |
| 保留期 | 5 年 → 18,250 行 |
| 单行平均 | 约 120 字节 |
| 总容量 | 约 2 MB |

**分区：** 否。5 年 1.8 万行，不需要分区。

        """规则自洽校验。"""
        if self.operator == "LT" and self.lb_threshold is None:
            raise ValueError("LT 必须配置低限")
        if self.operator == "GT" and self.ub_threshold is None:
            raise ValueError("GT 必须配置高限")
        if self.operator in ("BETWEEN", "OUTSIDE"):
            if (self.lb_threshold is None
                    or self.ub_threshold is None):
                raise ValueError(
                    "%s 必须同时配置上下限" % self.operator)
            if self.lb_threshold >= self.ub_threshold:
                raise ValueError("低限必须小于高限")
        if self.severity == "CRITICAL":
            if not self.ack_minutes or not self.handle_minutes:
                raise ValueError(
                    "CRITICAL 必须设置确认与处置时限")
        elif self.severity == "WARNING":
            if self.ack_minutes:
                raise ValueError("WARNING 不可设置确认时限")
        if not self.notify_roles:
            raise ValueError("通知角色不得为空")
        if not self.notify_channels:
            raise ValueError("通知渠道不得为空")
        return self

| **`idx_m13_chg_overdue`** | `m13_item_change_log` | `PENDING AND reminded_at IS NULL` | **超时提醒** |
| `idx_m13_chg_apply` | `m13_item_change_log` | `APPROVED AND applied_at IS NULL` | 待应用 |
| **`uk_m13_cov_date`** | `m13_coverage_snapshot` | 无 | **日期+类别唯一** |
| `idx_m13_cov_alert` | `m13_coverage_snapshot` | `critical_coverage < 1.0` | 覆盖缺口 |
| **`uk_m13_lic_key`** | `m13_lab_item_config` | `is_deleted=FALSE`（含 COALESCE） | **参数唯一** |

**为什么这张表集的部分索引特别重要？**

| 表 | 总行数 | 活跃/异常数据 | 占比 |
|---|---|---|---|
| `m13_lab_item_ext` | 500 | 区间缺失 11 / 危急缺失 19 | 6% |
| `m13_ref_range` | 2,240 | 待审批 3 / 待生效 2 | 0.2% |
| `m13_critical_rule` | 560 | 待审批 2 / 待生效 1 | 0.5% |
| `m13_item_change_log` | 5,500 | 待审批 3 | 0.05% |

数据量不大，部分索引的收益不如 M13-03/04 那么显著。**真正重要的是 `ex_m13_range_no_overlap` 这条排他约束**——它不是性能优化，而是数据正确性的保证。

**扩展依赖：**

本模块需要两个 PostgreSQL 扩展：

```sql
-- 1. btree_gist：让标量列参与 gist 排他约束（区间不重叠）
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- 2. pg_trgm：项目名称模糊搜索
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

**`btree_gist` 是必需扩展，不是可选优化。** 没有它，`EXCLUDE USING gist (lab_code WITH =, daterange(...) WITH &&)` 无法创建——gist 索引默认只支持 range/geometry 等类型，标量列的 `=` 比较需要 btree_gist 桥接。

**分区预建脚本（`m13_005_007_change_log`）：**

```sql
DO $$
DECLARE
    m DATE := DATE_TRUNC('month', CURRENT_DATE)::date;
    p TEXT;
    n TEXT;
BEGIN
    FOR i IN 0..35 LOOP
        p := TO_CHAR((m + (i || ' month')::interval)::date,
                     'YYYY_MM');
        n := 'm13_item_change_log_' || p;
        EXECUTE format(
            'CREATE TABLE IF NOT EXISTS %I '
            'PARTITION OF m13_item_change_log '
            'FOR VALUES FROM (%L) TO (%L)',
            n,
            (m + (i || ' month')::interval)::date,
            (m + ((i + 1) || ' month')::interval)::date);
    END LOOP;
END $$;
```

**归档策略：**

| 表 | 保留期 | 方式 |
|---|---|---|
| `m13_lab_item_ext` | 永久 | 不归档 |
| `m13_ref_range` | 15 年 | 归档历史版本（`is_current=FALSE` 且 `valid_to < 15 年前`） |
| `m13_critical_rule` | 15 年 | 同上 |
| `m13_report_format` | 永久 | 只保留当前版 |
| `m13_item_change_log` | 15 年 | 分区 DROP，`keep_forever` 跳转 |

**上线前运维准备清单（10 项）：**

| 序号 | 事项 | 说明 |
|---|---|---|
| 1 | **验证 `btree_gist` 扩展** | 需超级用户执行 `CREATE EXTENSION` |
| 2 | **验证 `pg_trgm` 扩展** | 同上 |
| 3 | 从 M01-09 全量同步项目 | 生成 500 条扩展记录（`is_enabled=FALSE`） |
| 4 | 为全部项目配置别名与收费关联 | 否则医生端搜不到 |
| 5 | **为全部项目配置参考区间** | 覆盖率需达 95% 才能批量启用 |
| 6 | **为 150 个适宜项目配置危急阈值** | **覆盖率必须 100%**，这是安全红线 |
| 7 | 配置报告格式模板 | 定性项目必须配正常值集合 |
| 8 | 确认审批人清单 | 科主任 + 医务科各至少 2 人（防请假阻塞） |
| 9 | 培训规则变更流程 | 双人复核、24 小时缓冲的意义 |
| 10 | 建立每月覆盖率复盘机制 | 缺失清单清零 |

**第 6 项是全表最关键的上线前置条件。**

危急阈值覆盖率达到 100% 才能上线，理由：

- 每个未配阈值的有临床意义的项目，都意味着"这个项目出现危急值时系统不会报警"
- 临床医生会默认"系统会报警"而放松警惕，这比没有系统更危险
- 覆盖率看板的红色横幅是最后一道提醒，但它不能替代配置本身

**如果时间紧张无法一次配齐 150 个怎么办？** 分批：先配最常用的 50 个（血常规、电解质、凝血、心肌、肝肾功能核心项），其余项目的 `is_critical_applicable` 临时置 FALSE（明确标注"暂不考核"），并列入待办清单。**绝不能留着 `is_critical_applicable=TRUE` 但没配阈值**——那是自欺欺人。
