**设计说明：**

1. **`m13_lab_request` 与 M07 医嘱一对一。** `order_no` 加唯一索引实现幂等：M07 网络抖动重发时，`INSERT` 冲突直接返回已有记录。

2. **`m13_lab_item` 与 `m13_lab_task` 是"收费层 → 执行层"的转换。** 一个组合项目（`is_combo=TRUE`）在 `m13_lab_item` 只有 1 行（对应 1 笔收费），展开后 `m13_lab_task` 有 N 行（对应 N 个结果）。

3. **`m13_specimen` 与 `m13_lab_task` 是 M:N。** 一管 EDTA 血可以做血常规 + 血型 + 糖化血红蛋白（3 个任务），一个血气分析任务可能需要动脉血 + 静脉血（2 管）。关联表 `m13_specimen_task_rel` 承载这个关系。

4. **`m13_specimen.parent_specimen_id` 自关联形成重采链。** 首次采集 `parent_specimen_id IS NULL`，重采指向被拒标本。

5. **`m13_specimen_log` 是只增日志表，按 `created_at` 月度分区。** 标本操作日志年量约 50 万条，5 年 250 万条，分区后可快速归档。

6. **不建物理外键。** `request_id`、`specimen_id`、`task_id` 均为逻辑引用。理由：
   - 分区表（`m13_specimen_log`）不能有指向非分区表的外键方向约束
   - 高频写入场景下外键检查有性能开销
   - 跨模块引用（M01-09）无法建外键
   - 一致性由应用事务 + 每日 03:00 的 `check_orphan_task_task` 保证

**状态机：**

```
                  接单成功
                     │
                     ▼
              ┌─────────────┐
              │  RECEIVED   │  已接单，等待采集
              │  （待采集）   │

                 ▼       ▼

       │ DISPATCHED   │ │  CANCELLED   │
       │ （已派发）     │ │  （已取消）   │
       └──────────────┘ └──────────────┘
```

**设计要点：**

1. **为什么 `order_no` 唯一索引是幂等的核心？**

   M07 推送医嘱后网络抖动，重试发送 P-01 请求。如果没有唯一索引，会产生两张申请单、两套标本、两倍收费。有了唯一索引：
   - 第二次 `INSERT` 触发 `IntegrityError`
   - 服务层捕获后 `SELECT` 已有记录并返回 `is_duplicate=true`
   - 客户端拿到相同的 `request_no`，不会重复打印

   这个模式比"先查后插"更可靠，因为"先查后插"在并发下有竞态窗口。

2. **为什么 `patient_name` / `gender` / `age` 要冗余？**

   - 列表页展示需要姓名（不查 M03）
   - 标本标签打印需要姓名（不查 M03）
   - M03 挂掉时仍能工作（降级）
   - 历史申请单要保留开单时的患者信息（患者改名后不能影响历史）

3. **为什么 `specimen_count >= 1` 硬约束？**

   因为逻辑上不可能有"0 管标本的检验申请"。如果真的算出 0 管，说明项目配置有问题（如项目没配标本类型），此时应该报错而不是写入一条异常数据。

4. **为什么 `status` 只有三个值？**

   申请单的状态是"粗粒度"的，细粒度在标本和任务上。申请单只需回答"这张单还要不要继续处理"。

   - `RECEIVED`：还在处理
   - `DISPATCHED`：至少一管已采集，进入正常流程
   - `CANCELLED`：不处理了

   如果需要"所有标本都采集完了"这种细粒度状态，通过 `COUNT(m13_specimen WHERE status='PENDING') = 0` 派生即可，不必冗余到申请单。

5. **`total_amount` 为什么允许空？**

   因为检验费由 M16 计算与收取，M13-01 只是记录快照。若 M07 传来的 `charge_amount` 缺失，该字段为 NULL，不影响业务流程。

**量级估算：**

| 项 | 估算 |
|---|---|
| 日申请量 | 50 张（门诊 350 人次 × 15% 需检验） |
| 年申请量 | 18,250 张 |
| 单行大小 | 约 450 字节 |
| 年数据量 | 约 8.2 MB |

**不分区。** 273,750 行在单表内完全可承受（索引 5 个，总大小约 350 MB）。155 亿级才需要考虑分区。

**设计要点：**

1. **为什么要有 `m13_lab_item` 而不是直接从 M07 医嘱取？**

   因为 M07 的医嘱是"医生意图"，M13 的申请单是"检验科接单的结果"。两者可能不同：

   - 医生开"术前八项"，M13 展开成 8 个项目执行
   - 医生开"血常规"，但标本问题是"需 2 管"，M13 拆成 2 管
   - 医生可能后续撤回部分项目

   申请单是快照：即使 M07 的医嘱改了，M13 侧的已接单内容不变（除非显式撤回）。

2. **为什么 `combo_code` 在明细行上也要记？**

   退费场景：医生开了"术前八项"（1 笔收费 200 元），但 M13 展开成 8 个任务。如果患者要退其中 1 项（如梅毒），系统需要知道"这 8 个项目同属一个组合"，才能正确处理"组合退费需要整组退"或"允许部分退"。

   如果只记 `is_combo=TRUE` 在组合行上，从任务反查组合要遍历匹配，O(N)。记在每行上 O(1)。

3. **为什么 `total_amount` 要单独存而不实时计算？**

   因为 `charge_amount` 可能变（调价）。如果只存单价，历史账单的金额会随调价而变，与发票不符。

   存 `total_amount` 快照后，历史数据不变。

   代价：增加一个冗余字段。收益：账单可复现。

4. **为什么 `quantity` 上限是 99？**

   检验项目没有"做 100 次"的场景。1 是常态，2~3 是"复查"，超过 5 就是配置错误。

   上限设为 99 留了足够余量，同时防止恶意输入（如数量填 999999 生成大量任务把系统打死）。

**状态机：**

```
   ┌──────────────────┐
   │ PENDING_COLLECT  │ 待采集
   └────────┬─────────┘
            │ 标本采集
            ▼
   ┌──────────────────┐
   │    COLLECTED     │ 已采集
   └────────┬─────────┘
            │ 标本送检
            ▼
   ┌──────────────────┐
   │    DELIVERED     │ 已送检
   └────────┬─────────┘
            │ 检验科签收
            ▼
   ┌──────────────────┐
   │    ACCEPTED      │ 已签收
   └────────┬─────────┘
            │ 报告生成
            ▼
   ┌──────────────────┐
   │    REPORTED      │ 已出报告（终态）
   └──────────────────┘

   旁支：
   ① 任一状态 ──► CANCELLED（医嘱作废）
   ② 标本拒收：DELIVERED/ACCEPTED ──► PENDING_COLLECT（回退）
```

**设计要点：**

1. **为什么 `uk_m13_lab_task_item` 唯一？**

   防止同一申请单展开出重复任务。比如"术前八项"里配置了两次 HBsAg（配置错误），展开会生成 2 个 HBsAg 任务，检验科会出 2 份报告，收费也是 2 笔。

   唯一索引 `(request_id, lab_code, specimen_type)` 让第二种情况直接失败，暴露配置错误。

   为什么带上 `specimen_type`？因为极少数项目需要同时出"血清结果"和"血浆结果"（如血糖），同项目不同标本视为不同任务。

2. **为什么 `primary_specimen_id` 允许 NULL？**

   三个场景：
   - 刚创建任务，还没归并到标本（理论上不出现，因为接单时就归并了）
   - **标本拒收后回退到 `PENDING_COLLECT`，此时主标本已失效，置 NULL 等重采**
   - 一个任务需要多管标本（如血气分析要动脉血+静脉血），`primary_specimen_id` 指向其中一管，其余在关联表

   第三点决定了不能设 `NOT NULL`。

3. **为什么 `report_id` 由 M13-04 回写而不是 M13-03？**

   因为 M13-03 解析出的报告需要经过审核才算"最终报告"。M13-03 只产生"草稿报告"，M13-04 审核通过后才回写 `report_id`。

   如果 M13-03 就回写 `report_id`，M13-01 会以为"任务已完成"，而实际报告还在审核中。

4. **为什么 `external_flag` 和 `is_outsourced` 两个字段都有？**

   - `is_outsourced`：该**检验项目本身**就是外送项目（M01-09 `md_lab_item.is_outsourced=TRUE`），如某些特殊病原体检测
   - `external_flag`：本次**任务实际走了外送**（可能是本地设备故障临时外送）

   前者是静态属性，后者是运行时决策。两个都要记录才能准确统计"外送率"。

**设计要点：**

1. **为什么 `specimen_no` 的唯一索引是"资金安全底线"？**

   条码错误会导致标本错配，最严重后果是"给 A 用了 B 的治疗方案"。

   场景：护士采集时扫码，如果两个标本条码相同：
   - 系统无法区分这是哪一管
   - 采集 A 时状态变 `COLLECTED`，采集 B 时状态变 `COLLECTED`（覆盖）
   - 检验科签收时不知道对应哪个任务
   - 结果挂到错误的患者

   唯一索引让重复条码直接插入失败，从数据库层面杜绝这个风险。

2. **为什么 `ck_m13_spec_sod`（采集人≠签收人）要放在 DB 层？**

   因为职责分离是**防止"既当运动员又当裁判"**。如果护士可以自己签收自己采的标本，"标本溶血"这种问题就永远不会被发现——护士不会主动承认自己采集失误。

   放在应用层的问题是：可能被绕过（比如 M08 护理站直接调 Service 时忘了传 user，或者 DBA 手动改）。DB 约束无法绕过。

   例外：单人夜班时确实可能一人完成所有操作。此时通过 `M13.SPECIMEN.SINGLE_STAFF_MODE` 参数可以关闭——但需科主任授权且每次操作记审计。

3. **为什么 `delivery_deadline` 要落库而不是实时计算？**

   因为要按截止时刻排序查待送检队列。如果实时算 `collected_at + delivery_minutes`，无法走索引：

   ```sql
   -- 走不了索引（表达式不能走普通索引）
   WHERE collected_at + interval '120 min' < NOW()
   ```

   落库后：

   ```sql
   -- 走 idx_m13_spec_deliver 索引
   WHERE delivery_deadline < NOW()
   ```

   代价：`delivery_minutes` 变（配置变更）时，已采集标本的 `delivery_deadline` 不更新（保持采集时的规则快照）。这其实是对的：规则变更不应追溯影响已采集标本。

4. **为什么 `appearance_check` 用 JSONB 而不是 5 个独立字段？**

   外观检查项会随检验科管理要求变化：
   - 现在：量、外观、溶血、凝块、容器
   - 未来可能加：黄疸、脂血、气泡

   用 JSONB 只需改代码，不必 ALTER TABLE。而且这个字段从不作为查询条件（不需要 `WHERE hemolysis = TRUE` 这种查询，那是 `reject_reason` 的职责）。

   但 `reject_reason` 必须是独立枚举字段，因为拒收统计要按原因分组。

5. **为什么 `print_count` 上限是 20（而不是 3）？**

   业务上限 3 次，但 DB 上限设 20 是因为：
   - 业务校验在服务层（`M13.SPECIMEN.MAX_PRINT` 参数）
   - DB 约束是"绝对不可能"的兜底，设 20 留了调整参数的余地
   - 如果 DB 也设 3，运维把参数改到 5 时会插入失败

   这类"业务值 vs 物理上限"分层是常规做法。

6. **为什么不用触发器保证"已采集状态必须采集人是护士"？**

   因为"是否护士"需要查 M02 的账号角色，跨模块。DB 触发器里不能调外部服务（无法保证一致性）。这类校验放服务层，DB 只保证"字段非空"这个物理事实。

| 年标本数 | 36,500 管 |
| 单行大小 | 约 700 字节 |

**设计要点：**

1. **为什么不直接在 `m13_lab_task` 上放 `specimen_id`？**

   因为需要 M:N：
   - 一管 EDTA 血 → 血常规 + 血型 + 糖化血红蛋白（1 管对 3 任务）
   - 血气分析 → 动脉血 + 静脉血（1 任务对 2 管）

   如果只在任务上放 `specimen_id`，只能表达 1:N（一标本多任务），无法表达 N:1（一任务多管）。

2. **`is_primary` 与 `m13_lab_task.primary_specimen_id` 的关系？**

   冗余设计：
   - `m13_lab_task.primary_specimen_id`：快速查主标本，不用 JOIN
   - `m13_specimen_task_rel.is_primary`：完整表达哪个是主标本

   应用层要保持一致：写 `is_primary=TRUE` 时同时更新任务表 `primary_specimen_id`。

   一致性由 `job_m13_check_primary_consistency` 每日校验。

3. **为什么 `lab_code` 要冗余？**

   查询"某管血服务哪些检验项目"时：

   ```sql
   -- 不冗余：需 JOIN 任务表
   SELECT t.lab_code FROM m13_specimen_task_rel r
   JOIN m13_lab_task t ON t.id = r.task_id WHERE r.specimen_id = ?

   -- 冗余：直接查
   SELECT lab_code FROM m13_specimen_task_rel WHERE specimen_id = ?
   ```

   标签打印、标本详情页每次都要查这个，冗余后省一次 JOIN。

| 年行数 | 146,000 行 |
| 单行大小 | 约 100 字节 |
| 年数据量 | 约 14 MB |
| 保留期 | 10 年 |
| **10 年合计** | **1,460,000 行 / 约 140 MB** |

**不分区。**

**分区方案：**

```sql
-- 月度 RANGE 分区，预建 36 个月
CREATE TABLE m13_specimen_log (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY,
    seq_date     DATE NOT NULL,
    biz_type     VARCHAR(16) NOT NULL,
    biz_id       BIGINT NOT NULL,
    biz_no       VARCHAR(32),
    action       VARCHAR(32) NOT NULL,
    operator_id  BIGINT,
    operator_name VARCHAR(64),
    operator_role VARCHAR(32),
    from_status  VARCHAR(16),
    to_status    VARCHAR(16),
    detail_json  JSONB,
    client_ip    INET,
    trace_id     VARCHAR(32),
    created_at   TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id, seq_date)
) PARTITION BY RANGE (seq_date);

-- ER 预建脚本：从 2026-10 起 36 个月
DO $$
DECLARE
    m DATE := DATE '2026-10-01';
    i INT;
    pname TEXT;
BEGIN
    FOR i IN 0..35 LOOP
        pname := 'm13_specimen_log_' || TO_CHAR(m, 'YYYYMM');
        EXECUTE format(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF '
            'm13_specimen_log FOR VALUES FROM (%L) TO (%L)',
            pname, m, m + INTERVAL '1 month');
        m := m + INTERVAL '1 month';
    END LOOP;
END $$;
```

**设计要点：**

1. **为什么要用 `seq_date` 冗余而不是直接用 `created_at` 分区？**

   PostgreSQL 支持 `PARTITION BY RANGE (created_at)`，但 `created_at` 是带时区的 `TIMESTAMP`，分区边界是 `DATE`。直接分区需要：

   ```sql
   PARTITION BY RANGE (DATE(created_at))
   ```

   但 `DATE(created_at)` 是表达式，PostgreSQL 12+ 支持表达式分区，但查询时 `WHERE created_at >= ?` 无法走分区裁剪（要先看表达式）。

   冗余 `seq_date` 列后：
   - 分区键是普通列，查询可走分区裁剪
   - 约束 `seq_date = DATE(created_at)` 保证两者一致
   - 应用层写入时同时赋值

   代价：多一列（4 字节）+ 一条 CHECK。收益：分区裁剪准确，归档时按 `seq_date` 直接 DETACH。

2. **为什么 `m13_specimen_log` 要分区而 `m13_specimen` 不分区？**

   | 表 | 10 年行数 | 是否有跨年份唯一约束 |
   |---|---|---|
   | `m13_specimen` | 365,000 | **有**（`specimen_no`） |
   | `m13_specimen_log` | 5,000,000 | **无** |

   分区会把唯一索引强行加入分区键，破坏 `specimen_no` 的全局唯一性。而日志表没有任何唯一约束，分区无副作用。

3. **为什么用触发器而不是应用层保护？**

   应用层可以被绕过：
   - DBA 手动 `UPDATE` 修正数据
   - 其他服务的 bug 误写
   - 数据迁移脚本

   触发器是最后一道防线，无法绕过（除非 `ALTER TABLE ... DISABLE TRIGGER`，那是显式的 DBA 操作，会留审计）。

4. **为什么 `biz_type` + `biz_id` 而不是分三张日志表？**

   因为查询模式统一："给我这个业务对象的所有操作记录"。三张表要 UNION，而单表加 `biz_type` 只多一个条件。

   且三张表的结构完全相同，分开没有收益。

**状态机：**

```
          ┌─────────────┐
   拒收   │   PENDING   │  待确认重采
  生成 ──►│  （待确认）   │
          └──┬───────┬──┘
             │       │
     确认重采│       │ 取消（如患者放弃、医生撤销项目）
             ▼       ▼
     ┌───────────┐ ┌───────────────┐
     │ CONFIRMED │ │  CANCELLED    │
     │ （已确认）  │ │  （已取消）     │
     └───────────┘ └───────────────┘
```

**设计要点：**

1. **为什么 `origin_specimen_id` 要唯一？**

   防止同一标本被拒收多次后生成多条重采记录。虽然 `m13_specimen` 的状态机保证 `REJECTED` 是终态（不能再次拒收），但唯一索引是兜底。

   更重要的是：重采统计需要准确。若一个标本产生 2 条重采记录，重采率会虚高。

2. **为什么把 `reject_reason` / `reject_desc` 冗余到重采表？**

   因为重采统计要按拒收原因分组，而 `m13_specimen.reject_reason` 在 JOIN 时是"当前状态"，若原标本记录被逻辑删除（极少但可能），统计会丢失。

   冗余后，重采记录自身完整，不受原标本状态影响。

3. **为什么 `status` 有 `CANCELLED` 而没有"失败"？**

   重采失败（护士尝试后仍无法采集）的处理方式是：
   - 患者放弃 → `CANCELLED` + 原因"患者放弃"
   - 医生撤销项目 → `CANCELLED` + 原因"医嘱已撤销"

   没有"失败"状态是因为重采要么成功（有新标本）要么不做（取消）。中间状态（正在重采）由 `PENDING` 表达。

4. **为什么 `notify_status` 只记状态不记重试次数？**

   因为通知是通过 Celery 任务发起的，重试次数在 Celery 侧管理（`max_retries=3`）。表里只需记"通知成没成"。

   若需要详细的通知日志，应查 M03-05 消息模块的消息表，而不是在业务表里堆日志字段。


**唯一索引为什么用 `COALESCE(scope_id, '')`？**

因为 PostgreSQL 认为两个 `NULL` 不相等。若写 `(param_code, scope, scope_id)` 唯一，则两条 `scope='GLOBAL' AND scope_id=NULL` 的记录不冲突，可以同时插入：

```sql
INSERT INTO m13_sys_config
  (param_code, scope, scope_id, param_value)
VALUES ('M13.SPECIMEN.MAX_PRINT', 'GLOBAL', NULL, '3');
-- 成功

INSERT INTO m13_sys_config
  (param_code, scope, scope_id, param_value)
VALUES ('M13.SPECIMEN.MAX_PRINT', 'GLOBAL', NULL, '5');
-- 也成功！（NULL <> NULL）
```

这样同一个参数会有两条全局配置，读取时 `LIMIT 1` 可能取到旧值。`COALESCE(scope_id, '')` 把 NULL 转成空串，两条会冲突。

> PostgreSQL 15+ 支持 `NULLS NOT DISTINCT`，但为兼容 14 版本统一用 `COALESCE`。

**参数作用域解析顺序：**

```
读参数 M13.SPECIMEN.MAX_PRINT，指定 dept_id=12

  ① SELECT ... WHERE param_code=? AND scope='DEPT' AND scope_id='12'
        ↓ 命中则返回
  ② SELECT ... WHERE param_code=? AND scope='GLOBAL'
        ↓ 返回
  ③ 都没有 → 用 default_value
```

分区会把唯一索引强制加入分区键。如果 `m13_specimen` 按 `created_at` 分区，`uk_m13_spec_no` 会变成 `(specimen_no, created_at)`，意味着**同一张条码在不同年份可以重复**，这彻底破坏了条码的唯一性。

日志表没有任何唯一约束（主键 `(id, seq_date)` 已含分区键），所以可以自由分区。

| **`uk_m13_recollect_origin`** | `m13_recollect` | `is_deleted=FALSE` | **一标本只重采一次** |
| `idx_m13_recollect_pending` | `m13_recollect` | `status='PENDING'` | 待确认重采 |

**共 45 个索引，其中 15 个部分索引。**

**为什么部分索引在标本表上特别重要？**

`m13_specimen` 保留 10 年（365,000 行），但活跃数据永远极少数：

| 队列 | 活跃量 | 占比 |
|---|---|---|
| 待采集 | 10~30 管 | 0.008% |
| 待送检 | 5~20 管 | 0.005% |
| 待签收 | 3~15 管 | 0.004% |
| 超时 | 0~5 管 | 0.001% |

对 `idx_m13_spec_overtime`：普通索引要遍历 365,000 行索引树约 3ms，部分索引只扫 1 页 < 0.1ms。超时扫描每 10 分钟一次，一年 52,560 次，差别是 158 秒 vs 5 秒 CPU。

### E.4 分区维护任务

```python
"""每月自动创建下个月分区。"""
from datetime import date, timedelta


def next_month(d: date) -> date:
    """返回下月1日。"""
    if d.month == 12:
        return date(d.year + 1, 1, 1)
    return date(d.year, d.month + 1, 1)


async def ensure_next_partition(db, table: str) -> None:
    """确保下月分区存在。"""
    today = date.today()
    nm_start = next_month(today)
    nm_end = next_month(nm_start)
    pname = "%s_%s" % (table, nm_start.strftime("%Y%m"))
    sql = (
        "CREATE TABLE IF NOT EXISTS %s PARTITION OF %s "
        "FOR VALUES FROM ('%s') TO ('%s')"
        % (pname, table, nm_start, nm_end))
    await db.execute(sql)
    await db.commit()
```
