**设计说明：**

1. **`m13_micro_culture` 是微生物链路的根表**，一份标本的一个微生物项目对应一条培养记录。它不建外键到 `m13_specimen`（跨子模块逻辑关联，避免 M13-01 归档时级联问题）。

2. **`m13_micro_isolate` 与 `m13_micro_result` 是 1:N 关系**。一份培养可能分离出多个菌株（如同时长革兰阳性球菌与革兰阴性杆菌），每个菌株有各自的鉴定与药敏。首个菌株在主结果里，后续菌株通过 `isolate_id` 关联到补充报告。

3. **`m13_micro_ast` 关联 `result_id` 而非 `culture_id`**。理由：药敏随批次走——中报可能有"初步药敏"（快速方法），终报有"完整药敏"（标准方法）。两批药敏都挂在各自的 `result_id` 下，避免覆盖。

4. **`m13_report_assembly` 的 `report_key` 是标本号**。所有批次共享同一个 `report_key`，`report_version` 递增，这是 M07-04 侧"一份报告多版本"的锚点。

5. **`m13_referral_item` 承载回报结果**，不另建"回报明细表"。理由：一个委托项只会有一次最终回报（拒收后补发的情况通过 `m13_referral_return` 的多条记录 + `is_superseded` 表达）。把结果字段放在委托项上，查询"这个项目回没回、回了什么"是一次查询，不用三表 JOIN。

6. **`m13_referral_return` 是回报事件表**，记录每次回报动作（含拒收、部分回报）。它与 `m13_referral_item` 是 N:1（一次回报可以覆盖多个委托项）。

**约束说明：**

```sql
CREATE UNIQUE INDEX uk_m13_culture_no
    ON m13_micro_culture (culture_no)
    WHERE is_deleted = FALSE;

-- 同标本同项目只能有一条培养
CREATE UNIQUE INDEX uk_m13_culture_spec_lab
    ON m13_micro_culture (specimen_no, lab_code)
    WHERE is_deleted = FALSE;

-- 待观察清单（工作台核心查询）
CREATE INDEX idx_m13_culture_observe
    ON m13_micro_culture (inoculate_date)
    WHERE culture_status IN (
        'INOCULATED', 'OBSERVING', 'NEGATIVE_PENDING')
      AND is_deleted = FALSE;

-- 超时扫描
CREATE INDEX idx_m13_culture_overdue
    ON m13_micro_culture (expected_final_date)
    WHERE culture_status IN (
        'INOCULATED', 'OBSERVING', 'POSITIVE', 'IDENTIFIED')
      AND is_deleted = FALSE;

-- 待出终报
CREATE INDEX idx_m13_culture_identified
    ON m13_micro_culture (identify_date)
    WHERE culture_status = 'IDENTIFIED'
      AND is_deleted = FALSE;

CREATE INDEX idx_m13_culture_specimen
    ON m13_micro_culture (specimen_no);

CREATE INDEX idx_m13_culture_patient
    ON m13_micro_culture (patient_id, inoculate_date DESC);

CREATE INDEX idx_m13_culture_status
    ON m13_micro_culture (culture_status, inoculate_date DESC);

CREATE INDEX idx_m13_culture_task
    ON m13_micro_culture (task_no);

ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_no
    CHECK (culture_no ~ '^MC[0-9]{8}[0-9]{6}$');

ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_status
    CHECK (culture_status IN (
        'PENDING_INOCULATE', 'INOCULATED', 'OBSERVING',
        'POSITIVE', 'IDENTIFIED', 'AST_DONE',
        'NEGATIVE_PENDING', 'NEGATIVE', 'CONTAMINATED',
        'FINAL'));

ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_type
    CHECK (culture_type IN (
        'GENERAL', 'FUNGAL', 'MYCOBACTERIA',
        'ANAEROBIC', 'INTRAOCULAR'));

ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_observe_result
    CHECK (last_observe_result IS NULL
           OR last_observe_result IN (
               'POSITIVE', 'NEGATIVE', 'CONTAMINATED'));

-- 培养天数合理范围
ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_days
    CHECK (min_culture_days >= 1 AND min_culture_days <= 60);

ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_observe_count
    CHECK (observe_count >= 0 AND observe_count <= 200);

-- 已接种必须有接种日期与人
ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_inoculated
    CHECK (culture_status = 'PENDING_INOCULATE'
        OR (inoculate_date IS NOT NULL
            AND inoculate_at IS NOT NULL
            AND inoculate_by IS NOT NULL));

-- 阳性必须有阳性日期与天数
ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_positive
    CHECK (culture_status NOT IN (
            'POSITIVE', 'IDENTIFIED', 'AST_DONE',
            'FINAL', 'NEGATIVE')
        OR (positive_date IS NOT NULL
            AND positive_days IS NOT NULL));

-- 已鉴定必须有鉴定日期
ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_identified
    CHECK (culture_status NOT IN (
            'IDENTIFIED', 'AST_DONE')
        OR identify_date IS NOT NULL);

-- 阴性必须有阴性日期
ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_negative
    CHECK (culture_status <> 'NEGATIVE'
        OR negative_date IS NOT NULL);

-- 污染必须有污染日期
ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_contaminated
    CHECK (culture_status <> 'CONTAMINATED'
        OR contaminate_date IS NOT NULL);

-- 已出终报必须有终报结果 ID
ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_final
    CHECK (culture_status <> 'FINAL'
        OR final_result_id IS NOT NULL);

-- 超时已处理必须填原因 >= 10 字
ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_overdue
    CHECK (overdue_handled = FALSE
        OR (overdue_reason IS NOT NULL
            AND char_length(btrim(overdue_reason)) >= 10));

-- 眼内液最短培养天数不得低于 5 天
ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_intraocular
    CHECK (culture_type <> 'INTRAOCULAR'
        OR min_culture_days >= 5);

-- 阳性日期不早于接种日期
ALTER TABLE m13_micro_culture
    ADD CONSTRAINT ck_m13_culture_date_seq
    CHECK (positive_date IS NULL
        OR inoculate_date IS NULL
        OR positive_date >= inoculate_date);

COMMENT ON TABLE m13_micro_culture IS
    '微生物培养：一任务一条，跟踪从接种到终报';
COMMENT ON COLUMN m13_micro_culture.specimen_no IS
    '标本号，逻辑关联 M13-01，不建外键避免归档级联';
COMMENT ON COLUMN m13_micro_culture.min_culture_days IS
    '最短培养天数，由 culture_type 决定；眼内液固定 5 天';
COMMENT ON COLUMN m13_micro_culture.expected_final_date IS
    '承诺出终报日期 = inoculate_date + min_culture_days';
COMMENT ON COLUMN m13_micro_culture.positive_days IS
    '阳性发现时已培养天数，用于统计平均阳性时间';
COMMENT ON COLUMN m13_micro_culture.overdue_handled IS
    '超时是否已处理；处理必须填原因';
```

**设计要点：**

1. **`uk_m13_culture_spec_lab` 是幂等基石。** 标本签收触发的自动创建与技师手工创建必须走同一逻辑，靠唯一索引兜住重复。

2. **`culture_status` 有 10 态但含 `PENDING_INOCULATE`。** 标本签收后自动创建培养记录时还没接种，需要一个"待接种"状态。技师看到工作台里"待接种"清单，接种后转 `INOCULATED` → `OBSERVING`。

3. **`ck_m13_culture_intraocular` 把"眼内液至少 5 天"下沉到 DB。** 这条规则来自临床实践（眼内液病原载量低，3 天培养阴性不能排除），应用层校验可能被参数调小绕过，DB 层是最后防线。

4. **`positive_days` 单独存。** 统计"平均阳性发现时间"是微生物质控的核心指标（反映培养基与操作水平），实时算需要 `JOIN` 与日期差，落库后直接聚合。

5. **`last_observe_date` 冗余而非查日志表。** 工作台的核心查询是"今天还没观察的培养"，用 `WHERE last_observe_date != CURRENT_DATE` 可走索引；若查日志表要 `NOT EXISTS` 子查询。

6. **不建"观察记录表"而只留最近一次。** 理由：观察次数很少（3~5 次），完整观察历史对业务价值有限（技师只看"上次观察结论"），存一张表会让它成为 M13 里第 4 大的表却几乎不被查询。**如果要完整留痕，应写 `m13_micro_log`（本文档未建表，采用通用日志表）。**

|---|---|
| 日送检微生物标本 | 约 8 份 |
| 日培养记录 | 约 12 条（一标本可能 1~3 个项目） |
| 年行数 | 约 4,380 |
| 单行平均 | 约 400 字节 |
| 5 年容量 | 约 8.8 MB |

**分区：** 否。5 年 2.2 万行，不分区。

```sql

    ON m13_micro_isolate USING gin (special_phenotypes);

ALTER TABLE m13_micro_isolate
    ADD CONSTRAINT ck_m13_isolate_no
    CHECK (isolate_no ~ '^ISO[0-9]{8}[0-9]{6}$');

ALTER TABLE m13_micro_isolate

    ADD CONSTRAINT ck_m13_isolate_name

           AND char_length(isolate_name) <= 100);

ALTER TABLE m13_micro_isolate
    ADD CONSTRAINT ck_m13_isolate_method
    CHECK (identify_method IN (
        'MALDI_TOF', 'BIOCHEMICAL', 'MOLECULAR',
        'SEROLOGICAL', 'MANUAL'));

ALTER TABLE m13_micro_isolate
    ADD CONSTRAINT ck_m13_isolate_confidence
    CHECK (identify_confidence IS NULL
        OR (identify_confidence >= 0
            AND identify_confidence <= 100));

-- 药敏判读的耐药表型只允许这几种
ALTER TABLE m13_micro_isolate
    ADD CONSTRAINT ck_m13_isolate_phenotypes
    CHECK (array_length(special_phenotypes, 1) IS NULL
        OR special_phenotypes <@ ARRAY[
            'MRSA', 'MRSE', 'ESBL', 'CRE', 'VRE',
            'MDR', 'XDR', 'PDR', 'AmpC', 'iMLSB']
           ::text[]);

ALTER TABLE m13_micro_isolate
    ADD CONSTRAINT ck_m13_isolate_gram
    CHECK (gram_stain IS NULL
        OR gram_stain IN ('POSITIVE', 'NEGATIVE',
                          'VARIABLE', 'NONE'));

COMMENT ON TABLE m13_micro_isolate IS
    '分离菌株：培养阳性后分离出的菌株，鉴定与药敏的主体';
COMMENT ON COLUMN m13_micro_isolate.special_phenotypes IS
    '特殊耐药表型数组 {MRSA,ESBL,CRE,VRE,...}，GIN 索引支持 @> 检索';
COMMENT ON COLUMN m13_micro_isolate.identify_confidence IS
    '鉴定置信度 0~100；< 90 需组长复核';
COMMENT ON COLUMN m13_micro_isolate.is_primary IS
    '主要菌株：混合感染时用于报告中"主要致病菌"的标识';
```

**设计要点：**

1. **`special_phenotypes` 用 `TEXT[]` 而非 JSONB。** 数组支持 `@>`（包含）操作符可走 GIN 索引——统计"本月 MRSA 株数"是高频查询，JSONB 的 `?` 操作符虽然也能走 GIN 但表达不如数组直观。

2. **`ck_m13_isolate_phenotypes` 用 `<@`（被包含）约束枚举。** 这保证不会出现"技师手工输入了拼错的表型"（如 `MRAS`）——拼错的表型永远不会匹配专家规则，导致本该改判的耐药被漏判。

3. **`isolate_seq` 而非全局编号排序。** 一个培养的菌株按发现顺序编号（1、2、3），报告中显示"菌株 1：金黄色葡萄球菌；菌株 2：铜绿假单胞菌"。全局编号只能用在 `isolate_no`。

4. **`is_primary` 支持混合感染。** 玻璃体液培养可能同时出革兰阳性球菌与革兰阴性杆菌，哪个是主要致病菌由技师判断。报告结论里"主要致病菌"取自 `is_primary=TRUE` 的那个。

2. **`ck_m13_micro_final_conc` 对阴性报告豁免 20 字结论。** 阴性结论是固定句式"经 X 天培养无细菌生长"，不需要 20 字。要求它写 20 字只会让技师编废话。

3. **`ck_m13_micro_negative` 保证阴性报告无药敏。** 没长菌哪来的药敏，这条约束拦住明显的逻辑错误。

4. **`specimen_no` 冗余而非 JOIN 到 culture。** 报告组装的核心查询是"按标本查全部批次"，冗余后单表扫；不冗余要 JOIN `m13_micro_culture`，且组装表也用 `specimen_no` 作 `report_key`。

5. **`report_version` 冗余到结果表。** 让"这批结果属于报告第几版"一次查到，不用 JOIN 组装表。

**约束说明：**

```sql

    ON m13_micro_ast (result_id, drug_code)
    WHERE is_deleted = FALSE;

CREATE INDEX idx_m13_ast_isolate
    ON m13_micro_ast (isolate_id, sort_no);

CREATE INDEX idx_m13_ast_drug
    ON m13_micro_ast (drug_code, interpretation);

-- 耐药率快速统计（本表最大用途）
CREATE INDEX idx_m13_ast_resistant
    ON m13_micro_ast (drug_code)
    WHERE interpretation = 'R' AND is_deleted = FALSE;

-- 专家规则修正审计
CREATE INDEX idx_m13_ast_corrected
    ON m13_micro_ast (result_id)
    WHERE is_corrected = TRUE AND is_deleted = FALSE;

ALTER TABLE m13_micro_ast
    ADD CONSTRAINT ck_m13_ast_method
    CHECK (ast_method IN (
        'MIC', 'DISK', 'E_TEST', 'AUTOMATED'));

-- 方法必须与结果字段匹配
ALTER TABLE m13_micro_ast
    ADD CONSTRAINT ck_m13_ast_method_value
    CHECK ((ast_method IN ('MIC', 'E_TEST', 'AUTOMATED')
            AND mic_value IS NOT NULL)
        OR (ast_method = 'DISK'
            AND zone_diameter IS NOT NULL));

-- MIC 值可以带 > < 前缀
ALTER TABLE m13_micro_ast
    ADD CONSTRAINT ck_m13_ast_mic
    CHECK (mic_value IS NULL
        OR mic_value ~ '^[<>]?[0-9]+(\.[0-9]+)?$');

ALTER TABLE m13_micro_ast
    ADD CONSTRAINT ck_m13_ast_zone
    CHECK (zone_diameter IS NULL
        OR (zone_diameter >= 6 AND zone_diameter <= 60));

ALTER TABLE m13_micro_ast
    ADD CONSTRAINT ck_m13_ast_interp
    CHECK (interpretation IN ('S', 'I', 'R', 'SDD'));

ALTER TABLE m13_micro_ast
    ADD CONSTRAINT ck_m13_ast_original
    CHECK (original_interpretation IS NULL
        OR original_interpretation IN ('S', 'I', 'R', 'SDD'));

-- 被修正必须有原始判读与原因
ALTER TABLE m13_micro_ast
    ADD CONSTRAINT ck_m13_ast_corrected
    CHECK (is_corrected = FALSE
        OR (original_interpretation IS NOT NULL
            AND correction_reason IS NOT NULL
            AND char_length(btrim(correction_reason)) >= 2));

-- 未修正则原始判读必须等于最终判读
ALTER TABLE m13_micro_ast
    ADD CONSTRAINT ck_m13_ast_not_corrected
    CHECK (is_corrected = TRUE
        OR original_interpretation IS NULL
        OR original_interpretation = interpretation);

ALTER TABLE m13_micro_ast
    ADD CONSTRAINT ck_m13_ast_sort
    CHECK (sort_no >= 0 AND sort_no <= 200);

COMMENT ON TABLE m13_micro_ast IS
    '药敏结果：一个菌株一个药物一条，含专家规则修正';
COMMENT ON COLUMN m13_micro_ast.mic_value IS
    'MIC 值，可带 > < 前缀，如 ">32"、"<=0.25"';
COMMENT ON COLUMN m13_micro_ast.interpretation IS
    '最终判读，专家规则修正后的值';
COMMENT ON COLUMN m13_micro_ast.original_interpretation IS
    '原始判读，技师录入未经修正的值；未修正时为 NULL';
COMMENT ON COLUMN m13_micro_ast.is_essential IS
    '是否 CLSI 必报药物，用于报告完整性检查';
```

**设计要点：**

1. **`mic_value` 用 `VARCHAR` 而非 `NUMERIC`。** MIC 的标准表达是 `>32`（实测超过最高浓度）、`<=0.25`（低于最低浓度），带运算符。用 `NUMERIC` 要拆成"值 + 运算符"两列，且排序困难。字符串 + 正则约束是最实用的方案。

2. **`ck_m13_ast_method_value` 保证方法与结果字段匹配。** 纸片法没有 MIC 值，肉汤稀释没有抑菌圈——两者混填说明录入错误。

3. **`ck_m13_ast_corrected` 与 `ck_m13_ast_not_corrected` 是双向钉死。** 被修正必须有原始值与原因；未修正则原始值必须与最终值一致（或者是 NULL，即技师从没录过原始值）。

   **为什么允许未修正时 `original_interpretation` 为 NULL？** 因为大多数字段不经过专家规则，录入时只写 `interpretation` 一个字段。只有当专家规则触发时才同时写两个值。

4. **`is_essential` 标记 CLSI 必报药物。** 某些药物（如金黄色葡萄球菌的苯唑西林）是必报的，必须在药敏表里出现。报告审核时检查"必报药物是否齐全"，缺了要退回。

5. **`idx_m13_ast_resistant` 是耐药率统计的核心索引。** "本月 MRSA 对万古霉素的耐药率"这类查询要用到 `WHERE interpretation='R'`，部分索引让扫描集从 12 万行降到 3 万行。

**量级估算：**

| 项 | 值 |
|---|---|
| 阳性批次 | 约 8,500/年（3,400 阳性 × 2.5 批） |
| 平均药物数 | 12 |
| 年行数 | 约 102,000 |
| 单行平均 | 约 150 字节 |
| 年容量 | 约 15 MB |
| 5 年容量 | 约 76 MB，加索引约 110 MB |

**分区：** 否。5 年 51 万行，主键查询 <1ms，`idx_m13_ast_resistant` 部分索引后耐药统计 <50ms。**若未来需要 10 年以上，可按 `created_at` 年度分区**，但 `uk_m13_ast_result_drug` 需改为含分区键（这与"同批次同药唯一"的语义冲突，故不推荐分区）。

ALTER TABLE m13_referral_order

ALTER TABLE m13_referral_order
    ADD CONSTRAINT ck_m13_order_missing
    CHECK (is_missing = FALSE
        OR (missing_reason IS NOT NULL
            AND char_length(btrim(missing_reason)) >= 10));

-- 已结案必须有结案时刻

    ADD CONSTRAINT ck_m13_order_closed
    CHECK (status <> 'CLOSED' OR closed_at IS NOT NULL);

-- 承诺日期不早于创建日

    '超 15 天未回报标记缺失，标记后不计入逾期扫描';
COMMENT ON COLUMN m13_referral_order.closed_at IS
    '结案时刻；CLOSED 是业务完结标志';

**设计要点：**

1. **`ck_m13_order_self_approve` 下沉到 DB。** 职责分离（创建人不能审批自己）是审计要求，应用层可绕过（DBA 改数据、其他服务 bug），DB 层是最后防线。

2. **`ck_m13_order_shipped` 强制三要素（快递单号、寄出时刻、寄出人）。** 标本寄丢了要能追责到"谁在什么时候用哪个单号寄的"，缺任何一项都无法追溯。

3. **`is_missing` 与 `status='OVERDUE'` 的关系。** 逾期（`OVERDUE`）是系统根据日期自动标记的，会自己恢复（回报到了就转 `RETURNED`）；缺失（`is_missing=TRUE`）是人工确认"这个真的回不来了"，一旦标记就不再多报逾期。两者不冲突。

   **但 `status` 里没有 `MISSING`（只有 `is_missing` 布尔字段）**，理由：缺失是终态之一，但后续仍可能需要"补一份报告"或"机构正式说明"，`status` 保持 `OVERDUE` 更灵活。

   **注意：`status` 枚举包含 `OVERDUE`，但 CHECK 里写的 `REJECTED_PLACEHOLDER` 是个错误。** 委托单驳回后应回到 `DRAFT`，没有 `REJECTED` 状态。此处约束应改为 `status` 无关的独立约束。见下方修正。

   **拒收后重新回报的场景如何处理？** 用 `return_id` 指向最新的那次回报记录，`result_value` 等字段被新回报覆盖，历史在 `m13_referral_return` 里（含 `is_superseded`）。

2. **`ck_m13_item_amount` 保证 `amount = ROUND(unit_price × quantity, 2)`。** 金额三字段（单价、数量、金额）必须自洽，否则对账时"明细加起来不等于合计"。

3. **`ck_m13_item_merged` 保证"合并"三要素。** `merged_at` 有值但没 `task_no`，说明合并逻辑有缺陷（合并了但没关联任务），结果永远不会出现在 M07。

4. **`idx_m13_item_lab` 支持"按项目统计回报及时率"。** 这是外送机构考核的核心指标，必须能快速聚合。

5. **`return_status` 用 4 态而非直接复用委托单状态。** 委托项的状态更细：一单 5 项可能 3 项 RECEIVED、1 项 REJECTED、1 项 PENDING，委托单层面只能看到 `PARTIALLY_RETURNED`。

**设计要点：**

1. **`ck_m13_return_double` 是手工录入的安全底线。** `verifier_id ≠ operator_id` 保证双人核对；`verified_at IS NOT NULL` 保证核对真的发生过（不是空填了个 ID）。

   **为什么这条约束放 DB 层？** 手工录入是整条链路唯一"数据不经过任何自动校验"的环节，双人核对是唯一的控制。应用层 bug 或绕过会导致单人录入无人复核。

2. **`ck_m13_return_attachment` 强制手工录入必须有附件。** 附件是原始报告的扫描件——事后核对"系统里的值与机构给的值是否一致"的唯一依据。

3. **`item_ids` 用 JSONB 数组。** 一次回报可能覆盖 1~10 个委托项，用关联表要多一张表且查询需 JOIN。JSONB 数组配合 `jsonb_array_length` 可做计数约束，且 `@>` 可做包含查询。

4. **`is_superseded` 处理"拒收后重新回报"。** 原回报拒收 → `status='REJECTED'`；机构补发新报告 → 新回报记录，原记录置 `is_superseded=TRUE` + `status='SUPERSEDED'`。这样能追溯"这份报告来回了几次"。

5. **`parse_record_id` 关联 M13-03 解析记录。** PDF 回报的数据来自解析，关联后可以追溯"这个结果是从哪份 PDF 的哪次解析来的"。

| 项 | 值 |
|---|---|
| 日回报 | 约 0.5 次 |
| 年行数 | 约 180 |
| 单行平均 | 约 400 字节 |
| 5 年容量 | 约 360 KB |

**分区：** 否。

```sql
-- 同报告同版本唯一（并发提交防重）
CREATE UNIQUE INDEX uk_m13_asm_key_ver
    ON m13_report_assembly (report_key, report_version)
    WHERE is_deleted = FALSE;

CREATE INDEX idx_m13_asm_key
    ON m13_report_assembly (report_key, report_version DESC);

CREATE INDEX idx_m13_asm_result
    ON m13_report_assembly (result_id);

CREATE INDEX idx_m13_asm_pending
    ON m13_report_assembly (created_at)
    WHERE status = 'SUBMITTED' AND is_deleted = FALSE;

CREATE INDEX idx_m13_asm_published
    ON m13_report_assembly (published_at DESC)
    WHERE published_at IS NOT NULL;

ALTER TABLE m13_report_assembly
    ADD CONSTRAINT ck_m13_asm_version
    CHECK (report_version >= 1 AND report_version <= 100);

ALTER TABLE m13_report_assembly
    ADD CONSTRAINT ck_m13_asm_batch
    CHECK (batch_type IN (
        'PRELIMINARY', 'INTERIM', 'FINAL',
        'SUPPLEMENTARY'));

ALTER TABLE m13_report_assembly
    ADD CONSTRAINT ck_m13_asm_status
    CHECK (status IN (
        'SUBMITTED', 'PUBLISHED', 'REJECTED'));

ALTER TABLE m13_report_assembly
    ADD CONSTRAINT ck_m13_asm_included
    CHECK (jsonb_typeof(included_result_ids) = 'array'
       AND jsonb_array_length(included_result_ids) >= 1);

ALTER TABLE m13_report_assembly
    ADD CONSTRAINT ck_m13_asm_count
    CHECK (result_count >= 1
       AND result_count
           = jsonb_array_length(included_result_ids));

-- 已发布必须有发布时刻与审核 ID
ALTER TABLE m13_report_assembly
    ADD CONSTRAINT ck_m13_asm_published
    CHECK (status <> 'PUBLISHED'
        OR (published_at IS NOT NULL
            AND review_id IS NOT NULL));

-- 版本的批次类型决定最小批次序号
ALTER TABLE m13_report_assembly
    ADD CONSTRAINT ck_m13_asm_seq
    CHECK (report_version >= 1);

COMMENT ON TABLE m13_report_assembly IS
    '报告组装版本：把标本的多批结果组装成一份报告的多个版本';
COMMENT ON COLUMN m13_report_assembly.report_key IS
    '报告键 = 标本号；所有批次共享同一 report_key';
COMMENT ON COLUMN m13_report_assembly.report_version IS
    '报告版本号，1 起递增；M07-04 侧表现为同一报告被更新';
COMMENT ON COLUMN m13_report_assembly.included_result_ids IS
    '本版本包含的全部结果批次 ID 数组';
COMMENT ON COLUMN m13_report_assembly.result_id IS
    '触发本次版本的结果批次 ID（即本次新增的那一批）';
```

**设计要点：**

1. **`uk_m13_asm_key_ver` 是并发提交防重的唯一防线。** 两个技师几乎同时提交不同批次时，版本号分配用 `SELECT MAX(version) FOR UPDATE` 串行化；即使应用层有 bug 重复分配，唯一索引会拒绝第二次插入。

2. **`included_result_ids` 是"版本快照"。** 报告 v3 包含批次 1/2/3；v4 包含批次 1/2/3/4。存完整数组而非只存增量，因为"打开 v3 看当时的内容"需要立即知道包含哪些批次——如果只存增量，要回溯 v1→v2→v3 累加。

3. **`result_count` 冗余并约束等于数组长度。** 便于"报告包含几批结果"的列表展示与统计，且约束保证不漂移。

4. **`status` 三态与 `m13_micro_result.status` 的对应关系：**

   | 组装状态 | 结果状态 | 说明 |
   |---|---|---|
   | `SUBMITTED` | `SUBMITTED` | 已提交待审 |
   | `PUBLISHED` | `PUBLISHED` | 审核通过已发布 |
   | `REJECTED` | `REJECTED` | 审核退回 |

   两者的同步由 `on_reviewed` 回调在**同一事务**内完成。

5. **不做 `PARENT_VERSION` 自关联。** 版本之间是线性的（v1→v2→v3），父子关系由版本号隐含，不需要额外字段。若要支持分支（如补充报告基于 v2 而非 v3），才需要，但业务上不存在这种场景。

**量级估算：**

| 项 | 值 |
|---|---|
| 阳性标本批次数 | 约 2.5 版/标本 |
| 阴性标本批次数 | 1 版/标本 |
| 年行数 | 约 12,000 |
| 单行平均 | 约 300 字节 |
| 5 年容量 | 约 18 MB |

**分区：** 否。

                raise ValueError("终报结论不得少于 20 个字符")

            raise ValueError("阴性报告不可包含药敏")
        if self.ast_results and not self.ast_method:
            raise ValueError("有药敏结果必须指定药敏方法")
        if self.ast_results:
            codes = [a.drug_code for a in self.ast_results]

| **`idx_m13_ast_resistant`** | `m13_micro_ast` | `interpretation='R'` | **耐药率统计** |
| `idx_m13_ast_corrected` | `m13_micro_ast` | `is_corrected=TRUE` | 专家规则修正审计 |
| **`idx_m13_org_expiring`** | `m13_referral_org` | `is_enabled` | **资质到期扫描** |
| **`idx_m13_order_pending`** | `m13_referral_order` | `status='PENDING_APPROVAL'` | 待审批 |
| **`idx_m13_order_pack`** | `m13_referral_order` | `status='APPROVED'` | 待打包 |
| **`idx_m13_order_overdue`** | `m13_referral_order` | 在途且非缺失 | **逾期扫描** |
| **`uk_m13_item_spec_lab`** | `m13_referral_item` | `is_deleted=FALSE` | **同单同标本同项目唯一** |
| **`idx_m13_item_lab`** | `m13_referral_item` | 无 | **回报及时率统计** |
| **`idx_m13_return_pending`** | `m13_referral_return` | `status='PENDING_CONFIRM'` | 待确认合并 |
| **`uk_m13_asm_key_ver`** | `m13_report_assembly` | `is_deleted=FALSE` | **同报告版本唯一** |
| **`idx_m13_asm_pending`** | `m13_report_assembly` | `status='SUBMITTED'` | **发布对账** |

**为什么这组索引是关键？**

| 场景 | 无索引 | 有部分索引 |
|---|---|---|
| 工作台加载待观察清单 | 全表扫 4,380 行 → 12ms | 扫 60 行 → 0.3ms |
| 逾期扫描（每日） | 4,380 行 → 12ms | 扫 5 行 → 0.1ms |
| 耐药率统计（年度 10 万行） | 102,000 行 → 180ms | 扫 30,000 行 → 55ms |
| 资质到期扫描（每日） | 8 行（本身很小） | 同 |
| 逾期委托单扫描 | 180 行 → 0.5ms | 扫 5 行 → 0.05ms |

在 4 千~10 万行这个量级，索引收益不如 M13-03/04 那些百万级表显著。**真正的价值在于"超时扫描"这类定时任务——它们每分钟跑一次，一年 50 万次，即使每次只差 10ms 也是 5000 秒 CPU。**

**上线前运维准备清单（10 项）：**

| 序号 | 事项 | 说明 |
|---|---|---|
| 1 | 录入外送机构与资质 | 至少 3 家，含许可证与 CMA/CNAS 有效期 |
| 2 | 配置机构可承接项目范围 | 委托时校验 |
| 3 | 配置各机构承诺天数 | 普通与加急 |
| 4 | 配置培养基字典 | 推荐培养基组合 |
| 5 | 配置菌种字典 | 与本院实际鉴定系统对齐 |
| 6 | 配置抗菌药物与折点 | 读 M01-03，补 CLSI 折点表 |
| 7 | **配置专家规则** | MRSA/ESBL/CRE/VRE 四条，与检验科确认 |
| 8 | 配置眼内液最短培养天数 | **固定 5 天，需临床确认** |
| 9 | 培训技师分批登记流程 | 初报/中报/终报/补充报告的区分 |
| 10 | 培训外送管理员流程 | 委托、打包、寄出、催单、接收回报 |

**第 7 项与第 8 项最重要：**

- **专家规则配错会让耐药被漏判**：如 MRSA 未配置，技师录了苯唑西林 R 但其他 β-内酰胺类可能是 S（表征与表型不一致），医生看到"头孢唑林敏感"就会用错药
- **眼内液培养天数调小会让眼内感染漏诊**：眼内炎患者玻璃体液培养阳性率仅 40~60%，短培养会进一步降低检出
