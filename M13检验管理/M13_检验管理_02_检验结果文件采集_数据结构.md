**设计说明：**

1. **`m13_report_file` 是本文档的中心表**，其他四张表都围绕它展开：`m13_inspection_detail` 记录"哪个文件出了问题"，`m13_collect_failure` 记录"哪个路径没能进系统"，`m13_collect_config` 是运行参数。
2. **`sha256` 上建部分唯一索引**（`WHERE is_duplicate = FALSE AND is_deleted = FALSE`）。这是去重的最后防线：即使应用层有并发 bug，数据库也拒绝插入两份指纹相同的非重复文件。
3. **`duplicate_of_file_id` 自关联而非外键约束**：重复文件指向原件，但原件可能因归档迁移被更新路径。用应用层保证指向有效记录，不用外键（避免删除限制）。
4. **`m13_inspection_detail` 只记异常行**：一次巡检抽查 320 份，318 份正常，全记一年 17.6 万行毫无价值。正常行的"已校验"信息写回 `m13_report_file.last_verify_at` 与 `verify_count`。
5. **`m13_collect_failure` 与主表分离**：失败时文件还没读完整，算不出 `sha256`，而主表 `sha256 NOT NULL` 且参与唯一索引。硬塞进去只能造假值，会污染去重。
6. **五张表全部不分区**：`m13_report_file` 15 年约 230 万行 / 2.1 GB，在 PostgreSQL 16 的舒适区间。**关键理由是按年分区会迫使 `uk_m13_file_sha256` 把分区键纳入索引，去重语义退化为"同年唯一"**，而"补采去年的历史报告"是真实场景。
7. **所有表都有 `is_deleted`**：软删除。医疗数据 15 年内不可物理删除。

```sql
    CHECK (source IN ('AUTO_SCAN', 'WATCHDOG', 'MANUAL_UPLOAD'));

    ADD CONSTRAINT ck_m13_file_bind_type
    CHECK (bind_type IS NULL

ALTER TABLE m13_report_file
    ADD CONSTRAINT ck_m13_file_dup
    CHECK (
        (is_duplicate = FALSE AND duplicate_of_file_id IS NULL)
        OR (is_duplicate = TRUE
            AND duplicate_of_file_id IS NOT NULL
            AND duplicate_of_file_id <> id)
    );

-- 绑定：BOUND 必须有任务与方式
ALTER TABLE m13_report_file
    ADD CONSTRAINT ck_m13_file_bound
    CHECK (bind_status <> 'BOUND'
           OR (bound_task_id IS NOT NULL AND bind_type IS NOT NULL));

-- 隔离：QUARANTINE 必须有原因
ALTER TABLE m13_report_file
    ADD CONSTRAINT ck_m13_file_quarantine
    CHECK (status <> 'QUARANTINE'

-- 归档：ARCHIVED 必须有归档时刻与当前路径
ALTER TABLE m13_report_file
    ADD CONSTRAINT ck_m13_file_archived
    CHECK (archive_status <> 'ARCHIVED'
           OR (archived_at IS NOT NULL AND current_path IS NOT NULL));

-- 归档失败：FAILED 必须有错误与重试计数
ALTER TABLE m13_report_file
    ADD CONSTRAINT ck_m13_file_archive_failed
    CHECK (archive_status <> 'FAILED'
           OR (archive_error IS NOT NULL AND archive_retry > 0));

-- 密码：waiting 必须有加密密码
ALTER TABLE m13_report_file
    ADD CONSTRAINT ck_m13_file_password
    CHECK (need_password = FALSE OR pdf_password_enc IS NOT NULL);

ALTER TABLE m13_report_file
    ADD CONSTRAINT ck_m13_file_pwd_fail
    CHECK (password_fail_count >= 0 AND password_fail_count <= 10);

-- 丢失：is_missing 必须有发现时刻
ALTER TABLE m13_report_file
    ADD CONSTRAINT ck_m13_file_missing
    CHECK (is_missing = FALSE OR missing_found_at IS NOT NULL);

-- 采集延迟非负
ALTER TABLE m13_report_file
    ADD CONSTRAINT ck_m13_file_delay
    CHECK (collected_seconds >= 0);

-- 检索路径：共享盘为 Windows 路径，不允许正斜杠
ALTER TABLE m13_report_file
    ADD CONSTRAINT ck_m13_file_path
    CHECK (position('/' IN original_path) = 0);

-- 解析完成：PARSED 必须有解析时刻
ALTER TABLE m13_report_file
    ADD CONSTRAINT ck_m13_file_parsed
    CHECK (status <> 'PARSED' OR parsed_at IS NOT NULL);

COMMENT ON TABLE m13_report_file IS '报告文件主表：每份进入系统的 PDF 一行';
```


**设计要点：**

1. **`sha256` 用 `CHAR(64)` 而非 `VARCHAR(64)`**：定长，PostgreSQL 内部存储与访问都略快；`CHECK` 正则保证内容合法。
2. **`original_path` 与 `current_path` 分两列**：`original_path` 是采集时的历史路径（归档后仍可追溯"从哪来的"），`current_path` 随归档变化。合并成一列会丢失"原始路径"这个证据。
3. **`collected_seconds` 冗余存储而非实时计算**：采集延迟是核心 SLA 指标，需要按分位统计（P95）。实时算 `collected_at - file_mtime` 需要全表扫，冗余后可直接建索引与聚合。
4. **`is_encrypted` 与 `need_password` 是两个字段**：前者是**探测结果**（PDF 是否加密，客观事实），后者是**业务状态**（是否在等人工给密码）。损坏的 PDF 既探测不出也不该进"等密码"状态。
5. **`parse_status` 与 `status` 并存**：`status` 是文件主状态（含隔离、重复等），`parse_status` 是解析侧的子状态。二者有关联但不等价——例如 `status='PARSED'` 时 `parse_status='PARSED'`；`status='DUPLICATE'` 时 `parse_status=NULL`。
6. **`parsed_patient_name` 冗余**：列表页要显示"张伟 血常规"便于人工核对，每次都去 M13-03 取要发 500 次 HTTP。冗余一份，M13-03 回写时更新。
7. **`archive_retry` 与 `parse_retry` 分开**：归档失败（磁盘满/占用）与解析失败（PDF 损坏/OCR 超时）原因完全不同，共用计数器会导致"归档重试耗尽把解析也堵死"。
8. **`is_missing` 不对应 `is_deleted`**：发现丢失 ≠ 删除记录。记录还在，只是原件没了；OCR 结果（在 M13-03）仍可用，报告正文仍可看。置 `is_deleted=TRUE` 医生就再也查不到那份报告。
9. **`ck_m13_file_path` 强制反斜杠**：共享盘是 Windows 路径，混入正斜杠会导致 `safe_join` 判错。
10. **`password_fail_count` 上限 10**：应用层 3 次锁 30 分钟，数据库兜底 10 次（防止应用层 bug 无限累加）。

**量级估算：**

| 项 | 值 |
|---|---|
| 每日新增 | 约 420 份（含重复） |
| 每年新增 | 153,300 行 |
| 15 年累计 | 约 230 万行 |
| 单行平均 | 约 900 字节 |
| 总容量 | 约 2.1 GB（含索引约 3.2 GB） |

**分区：** 否。原因见 4.1 设计说明第 6 条。

3. **`can_auto_recover` 显式标注**：`UNSTABLE`/`LOCKED`/`SHARE_UNAVAILABLE`/`DISK_FULL` 是环境问题，等一等可能就好了；`NOT_PDF`/`CORRUPTED`/`TOO_LARGE`/`BAD_PATH` 是文件本身的问题，自动重试永远不会成功，白耗 CPU。
4. **`quarantine_path` 独立存**：隔离后原路径失效，需要记新路径才能找回。
5. **`retry_count` 上限 100 而非 20**：稳定性判定内部重试 20 次，失败后 30 分钟再扫一次，一天最多 48 次。上限 100 约 2 天，之后标 GAVE_UP 转人工。

```sql

    ADD CONSTRAINT ck_m13_inspect_no
    CHECK (inspection_no ~ '^IJ[0-9]{8}[0-9]{3}$');

ALTER TABLE m13_inspection
    ADD CONSTRAINT ck_m13_inspect_status
    CHECK (status IN ('RUNNING', 'FINISHED', 'FAILED'));

ALTER TABLE m13_inspection
    ADD CONSTRAINT ck_m13_inspect_trigger
    CHECK (triggered_by IN ('SCHEDULE', 'MANUAL'));

-- 抽样结果必须自洽：正常 + 丢失 + 损坏 = 总数
ALTER TABLE m13_inspection
    ADD CONSTRAINT ck_m13_inspect_count
    CHECK (sample_ok + sample_missing + sample_corrupted
           = sample_total);

ALTER TABLE m13_inspection
    ADD CONSTRAINT ck_m13_inspect_rate
    CHECK (missing_rate >= 0 AND missing_rate <= 1);

-- 丢失率必须与计数一致
ALTER TABLE m13_inspection
    ADD CONSTRAINT ck_m13_inspect_rate_calc
    CHECK (sample_total = 0
           OR abs(missing_rate
                  - sample_missing::numeric / sample_total)
              < 0.000001);

ALTER TABLE m13_inspection
    ADD CONSTRAINT ck_m13_inspect_finished
    CHECK (status <> 'FINISHED'
           OR (finished_at IS NOT NULL
               AND finished_at >= started_at));

ALTER TABLE m13_inspection
    ADD CONSTRAINT ck_m13_inspect_manual
    CHECK (triggered_by <> 'MANUAL' OR triggered_by_id IS NOT NULL);

COMMENT ON TABLE m13_inspection IS
    '巡检主表：每次抽样校验原件是否仍存在且未变';
COMMENT ON COLUMN m13_inspection.missing_rate IS
    '丢失率 = sample_missing / sample_total';
```

**设计要点：**

1. **`ck_m13_inspect_count` 是巡检报告可信度的根基**：三个计数必须严格等于总数。若这条约束不成立，报表可能显示"抽样 320，正常 318，丢失 2"但实际只校验了 300 份——那 20 份的结论是哪来的？
2. **`ck_m13_inspect_rate_calc` 强制丢失率与计数一致**：浮点除法在数据库层算一次，防止应用层算错。
3. **`idx_m13_inspect_running` 是部分索引**：正常每份巡检都是一次性的（几秒内 FINISHED），`RUNNING` 的记录永远最多一条。用普通索引会扫全部历史；部分索引只扫 0~1 行。
4. **`duration_seconds` 冗余**：巡检耗时是运维关注指标（若从 26 秒涨到 3 分钟说明文件数暴涨或磁盘变慢），实时算不方便聚合。

| 项 | 值 |

| 每日新增 | 1~2 条（自动 + 偶尔手工） |
| 每年新增 | 550 行 |
| 保留期 | 5 年 → 2,750 行 |
| 总容量 | 约 800 KB |

**分区：** 否。

**设计要点：**

5. **`file_no`/`file_name` 冗余**：巡检报告可能多年后查看，届时文件记录可能已归档/迁移，冗余快照保证报告可读。

**参数读取优先级：**

```
1. 数据库 m13_collect_config（唯一来源）
   ↓ 未命中
2. 代码内 DEFAULT_VALUES 常量（兜底）
   ↓ 仍未命中
3. 抛错（pipeline 启动自检失败）
```

**为什么所有参数只用 GLOBAL 作用域？**

采集是"一台服务器监听一个共享盘"的单一部署，不存在"按科室/按设备配不同监听目录"的语义。`scope` 字段保留 `GLOBAL` 枚举是为了与 M12 的配置表结构保持一致，未来若需要"分院落独立采集"，可扩展为 `SITE` 作用域。

**为什么用 `COALESCE(scope_id, '')` 而不是 `NULLS NOT DISTINCT`？**

PostgreSQL 唯一索引认为 `NULL` 互不相等。若不加 `COALESCE`，同一 `param_code` 可以有两条 `GLOBAL`（`scope_id` 均为 NULL）记录，读取时 `first()` 取到哪条不确定。

`NULLS NOT DISTINCT` 是 PostgreSQL 15+ 特性，本项目部分环境仍是 PG 14，用 `COALESCE` 更兼容。

**量级估算：**

| 项 | 值 |
|---|---|
| 行数 | 25 条（固定） |
| 总容量 | 约 20 KB |

**分区：** 否。

**为什么需要这么多部分索引？**

`m13_report_file` 15 年约 230 万行，但活跃数据永远极少数：

| 状态 | 典型行数 | 占全表 |
|---|---|---|
| 待归档 | 约 200 | 0.009% |
| 待密码 | 约 2 | 0.0001% |
| 隔离 | 约 3 | 0.0001% |
| 解析失败 | 约 5 | 0.0002% |
| 待确认 | 约 20 | 0.0009% |
| 已丢失 | 约 5 | 0.0002% |
| 归档失败 | 约 3 | 0.0001% |

用普通索引，每次查询要遍历 230 万行的索引树（约 20ms）。用部分索引后，每个索引只有几十条（<1 个数据页），查询 <1ms。

定时任务每天跑数千次，差别是几百秒的 CPU。

**上线前运维准备清单（10 项）：**

| 序号 | 事项 | 说明 |
|---|---|---|
| 1 | 挂载共享盘 | `\\fileserver\lab-reports` 可读写 |
| 2 | 创建 4 个子目录 | `INBOX` / `ARCHIVE` / `QUARANTINE` / `MANUAL` |
| 3 | 配置服务账号权限 | 服务账号对 4 个目录有读写权限 |
| 4 | 配置仪器导出路径 | 每台仪器工作站默认导出到 `INBOX` |
| 5 | **校准仪器电脑时钟（NTP）** | 误差 < 30 秒；时钟不准会导致采集延迟为负 |
| 6 | 配置归档盘容量监控 | 建议 SAN 卷告警阈值 80% |
| 7 | 配置备份策略 | `ARCHIVE` 每日增量，保留 30 天 |
| 8 | 部署 watchdog 服务 | 独立进程，systemd/supervisor 托管 |
| 9 | 验证文件系统权限 | `open(path,'rb')` 能成功（非独占锁） |
| 10 | 验证 pg_trgm 扩展 | `CREATE EXTENSION` 需超级用户权限 |

**第 5 项为什么重要：**

`collected_seconds = collected_at - file_mtime`。若仪器电脑时钟慢 20 分钟，PDF 的 mtime 比实际早 20 分钟，采集延迟就变成 +20 分钟（1200 秒），P95 严重超标；若时钟快，则为负值，触发 `ck_m13_file_delay` 约束报错。

**这不是代码能修的，必须靠 NTP 校准。**
